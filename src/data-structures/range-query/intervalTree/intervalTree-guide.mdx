# IntervalTree — 부분 트리 하나를 한 번 보고 통째로 버리는 색인

## 개요

구간 색인(IntervalTree)은 구간 `[low, high]` 들을 담아 두고 **주어진 점이나 구간과 겹치는 것을 전부** 돌려주는 구조입니다. 설계 핵심은 부분 트리마다 **그 안의 끝점 최댓값 하나**를 들고 있는 것이고, 그 값 하나로 "이 아래에는 답이 없다"를 한 번에 판정합니다. 질의 비용은 저장된 구간 수 `n` 이 아니라 답의 수 `k` 에 매여 `O((k+1) log n)` 이 됩니다.

## 이 구조가 필요한 이유

이 구조가 동시에 요구받는 연산은 넷입니다 — **넣기 · 빼기 · 점 질의 · 구간 질의**. 넷 중 질의만 필요하고 집합이 변하지 않는다면 미리 정렬해 두는 편이 낫고, 넣고 빼기만 필요하다면 아무 컨테이너나 됩니다. **집합이 계속 변하면서 겹침을 계속 물어볼 때** 비로소 이 구조가 필요합니다.

어려운 점은 "겹친다"가 부등식 **둘**이라는 데 있습니다. 두 구간이 겹치려면 `저장low <= 질의high` 이면서 `질의low <= 저장high` 여야 합니다. 시작점으로 정렬하면 첫 번째 부등식은 이진 탐색으로 좁혀지지만, 그렇게 좁힌 후보들 중 어느 것이 두 번째를 만족하는지는 정렬이 말해 주지 않습니다. 한 축을 정리하면 다른 축이 흐트러진 채로 남습니다.

이 계약에 **없는 것**도 분명합니다. 겹친 구간을 하나로 합치기, 덮인 총 길이 구하기, k 번째 구간 꺼내기가 없습니다. 그것들이 필요하면 다른 계약을 찾아야 합니다.

### 쓰이는 자리

사례를 **연산 집합과 호출 빈도**로 옮겨 적습니다. 옮겨 적어 보면 그 자리가 정말 이 구조를 요구하는지가 드러납니다.

- **회의실 예약 충돌 검사** — 요청 하나마다 `overlapQuery(시작, 끝)` 1회, 비어 있으면 `insert` 1회, 취소는 `delete` 1회. 요청 수만큼 반복합니다. **세 연산이 모두 계약에 있습니다.** 그리고 이 사례는 3단계에서 한 번 더 나옵니다 — 예약이 시작 시각 순으로 쌓인다는 사실이 어떤 설계를 최악으로 몰아넣기 때문입니다.
- **유전체 좌표의 주석 조회** — 좌표 `p` 하나마다 `stabQuery(p)` 1회, 조회 수만큼 반복합니다. 한 좌표를 덮는 주석은 대개 몇 개뿐이라 **`k` 가 작습니다.** 이 "`k` 가 작다"가 계약이 상한을 `k` 로 적는 이유이자, 전부 훑는 설계가 여기서 걸리는 이유입니다.
- **캘린더 화면 갱신** — 화면에 보이는 시간 범위마다 `overlapQuery` 1회, 스크롤·확대할 때마다 반복합니다. 여기서 `k` 는 화면에 그릴 일정 수이므로, 비용이 전체 일정 수에 비례하면 일정이 쌓일수록 스크롤이 느려집니다.

k 번째로 이른 구간을 꺼내는 사례는 위에 없습니다. 있었다면 그것은 이 구조의 사례가 아니라 순위 질의를 계약에 담은 다른 구조의 사례입니다.

## 단순한 구현의 한계

### 순진한 설계는 어디서 상한을 넘는가

이 구조를 모른 채 같은 요구를 받으면 가장 먼저 나오는 답은 **구간을 배열에 담고 질의마다 전부 확인하기**입니다. 겹침 판정은 부등식 두 개면 끝나니 코드가 다섯 줄입니다.

넘어가는 자리는 질의입니다. 답이 하나뿐이어도 저장된 것을 전부 봅니다.

```text
값 범위를 n 에 비례해 넓혀 한 점을 덮는 구간 수를 상수로 눌러 놓고,
점 질의 한 번에 들여다본 구간 수를 셌다.

        n        배열에 담고 전부 훑기        증강 트리
    1,024              1,024.00                18.23
    4,096              4,096.00                21.89
   16,384             16,384.00                26.20

n을 4배로 키우면 훑는 쪽은 비용도 4배가 된다 (r = 4.00).
계약이 요구하는 값은 O(log n) 의 r = 1.20 이다.
```

정렬로는 이 클래스가 바뀌지 않습니다. 시작점으로 정렬해 두고 이진 탐색으로 `저장low <= p` 인 앞쪽을 잘라내도, **그 앞쪽 안에서 끝점이 `p` 를 넘는 것이 어느 것인지는 정렬이 말해 주지 않습니다.** 위 측정처럼 점이 값 범위 한가운데 놓이면 앞쪽이 대략 절반이므로, 확인해야 할 후보는 여전히 `n` 에 비례합니다. 상수만 반으로 줄고 성장률은 그대로입니다.

그래서 다음 수는 **부분 트리 단위로 "여기엔 없다"를 말하게 하는 것**입니다. 시작점을 키로 이진 탐색 트리를 세우고, 노드마다 자기 부분 트리의 끝점 최댓값(`maxHigh`)을 얹습니다. 질의 `p` 가 `maxHigh` 보다 뒤에 있으면 그 부분 트리는 통째로 버립니다.

이 설계는 **여섯 시나리오 중 다섯을 통과합니다.** 질의에서는 정본과 사실상 구별되지 않습니다.

```text
같은 점 질의 시나리오 — 연산당 들여다본 노드 수

        n      균형 없는 증강 트리        증강 트립(정본)
    1,024            18.22                   18.23
    4,096            21.80                   21.89
   16,384            26.19                   26.20
```

무너지는 자리는 삽입 하나뿐이고, 그것도 입력이 특정 모양일 때만입니다.

```text
삽입 n회 — 연산당 들여다본 노드 수

  입력            n         균형 없는 증강 트리      증강 트립(정본)
  무작위      1,024                12.10                26.39
              4,096                14.97                32.70
             16,384                17.68                39.51   ← r = 1.20, 통과

  시작점      1,024               512.50                15.46
  오름차순    4,096             2,048.50                17.81
             16,384             8,192.50                21.64   ← r = 4.00, 실패
```

무작위 입력에서는 균형을 안 잡는 쪽이 오히려 **싸게** 나옵니다(12.10 대 26.39). 우선순위를 섞고 자르고 붙이는 일을 하지 않으니 당연합니다. 그 이득이 사라지는 자리가 오름차순이고, 거기서는 8,192.50 대 21.64로 갈립니다.

**그리고 오름차순은 지어낸 입력이 아닙니다.** 2단계에서 첫 번째 사례로 꼽은 예약 시스템에서 예약은 시작 시각 순으로 쌓입니다. 이 구조를 쓰는 대표적인 이유 하나가 이 설계를 최악으로 몰아넣습니다.

### 실패에서 끌어내는 설계 규칙

두 실패에서 관찰이 하나씩 나옵니다.

**관찰 하나 — 한 축의 정렬만으로는 후보가 좁혀지지 않는다.** 겹침이 부등식 둘이기 때문입니다. 그렇다면 나머지 한 축에 대해서도 무언가를 미리 알고 있어야 하는데, 그것이 구간마다 있을 필요는 없습니다. **부분 트리 하나당 값 하나**면 "이 아래에는 답이 없다"를 말하기에 충분합니다. 그 값이 끝점의 최댓값입니다.

여기서 어디까지가 필연이고 어디부터가 관례인지를 갈라 둘게요. 필연인 것은 *"한 축으로 순서를 잡고, 나머지 축의 극값을 부분 트리마다 들고 있는다"* 까지입니다. **시작점을 키로 잡고 끝점의 최댓값을 얹는 것은 관례입니다** — 끝점을 키로 잡고 시작점의 최솟값을 얹어도 같은 구조가 나옵니다.

**관찰 둘 — 버리는 말이 이득이 되려면 버릴 것이 커야 한다.** 부분 트리 하나를 한 번 보고 버리는 이득은 그 부분 트리가 클 때 나옵니다. 사슬에서는 노드 하나가 곧 부분 트리 하나이므로 버려도 하나가 줄 뿐이고, 그러면 위 표의 8,192.50 이 됩니다. 그런데 트리 모양을 정하는 것은 **입력 순서**입니다. 정렬된 입력이 사슬을 만듭니다.

그래서 두 번째 조건은 이것입니다 — **트리 모양이 입력 순서에 매이면 안 된다.** 모양을 정하는 축을 키 말고 하나 더 두고, 그 축을 입력과 무관하게 정하면 됩니다. 그 축이 다음 절의 우선순위입니다.

두 관찰이 계약의 두 요구로 그대로 이어집니다. 첫째가 질의 상한을 `k` 에 매이게 하고, 둘째가 그 상한을 **어떤 입력에서도** 지키게 합니다.

## 불변식과 연산별 복잡도 조건

계약 전문은 `intervalTree.ts` 헤더에 있습니다. 여기서는 그 조건이 **왜 그 모양인지**를 봅니다.

**불변식이 둘 있고, 둘 다 `maxHigh` 를 들고 다니기로 한 순간 생긴 빚입니다.**

첫째는 *"넣은 것을 전부 되찾는다"* 입니다. 자식이 바뀐 노드의 `maxHigh` 를 다시 계산하는 일을 한 자리라도 빠뜨리면, 그 값은 **작은 쪽으로** 낡습니다. 작게 낡은 값은 가지치기를 과하게 만들고, 그러면 있는 구간을 못 찾습니다. 여기서 비대칭 하나를 짚어 둘게요 — **낡은 값이 작으면 답을 잃고, 크면 느려질 뿐입니다.** 삭제 뒤에 갱신을 빠뜨리면 값이 크게 남아 필요 없는 곳까지 내려가지만 답은 맞습니다. 삽입 뒤에 빠뜨리면 답이 사라집니다. 이 불변식이 잡는 것은 후자입니다.

둘째는 *"두 질의가 갈리지 않는다"* 입니다. 점 질의와 구간 질의를 각각 쓰면 가지치기 규칙이 두 벌이 되고, 한쪽만 틀려도 각각은 그럴듯하게 동작합니다. 이 불변식은 그 갈림을 상태에서 직접 봅니다.

**셋째 후보였던 건전성은 불변식이 아닙니다.** *"돌려준 구간이 실제로 겹친다"* 는 상태의 성질이 아니라 `overlapQuery` 라는 **한 연산의 의미 그 자체**입니다. 불변식은 연산들 사이에서 상태가 지켜야 할 성질이고, 한 연산의 의미가 맞는지는 참조 모델과의 대조가 봅니다. 검사를 안 한다는 뜻이 아니라 검사하는 자리가 다르다는 뜻입니다.

**한정자는 다섯 연산 중 넷이 `expected`, `size` 만 `worst` 입니다.** 계약이 **가장 약한 한정자**를 적는 이유는 강한 한정자가 우회로 낸 처방이기 때문입니다. `insert` 를 `worst O(log n)` 으로 적으면 우선순위를 무작위로 뽑는 설계가 통째로 계약 위반이 됩니다 — 아무도 무작위를 금지한 적이 없는데 금지됩니다. `expected` 로 적으면 무작위 설계도, 상각으로 균형을 맞추는 설계도, 회전으로 최악을 보장하는 설계도 모두 통과합니다.

**질의 상한에 `k + 1` 이 곱해져 있는 것도 같은 이유입니다.** 더 강한 `O(log n + k)` 를 적으면, 답 하나를 찾을 때마다 위쪽에서 다시 내려오는 방식이 전부 계약 위반이 됩니다. 이 색인이 하는 일이 바로 그것이라 그 상한은 이 설계를 배제합니다. 계약은 상한이므로 배제하지 않는 쪽을 적습니다.

**검증 등급은 `complexity` 입니다.** 상한이 자명한 구현으로 달성되지 않기 때문이고, 그 반례 둘이 위 3단계에서 실제로 돌려 본 배열과 균형 없는 트리입니다. 등급을 고른 것이 아니라 계약에서 따라 나온 것이라는 점이 중요합니다 — 계약이 바뀌면 등급도 다시 판정됩니다.

## 구현 (TypeScript)

아래 코드는 `_reference/intervalTree.ts` 에서 그대로 가져온 것입니다. 손으로 옮겨 적지 않았고, 정본이 바뀌면 이 블록도 함께 바뀝니다.

```ts guide-core=src/data-structures/range-query/intervalTree/_reference/intervalTree.ts
interface Node {
  low: number;
  high: number;
  /** 트리 모양을 정하는 값. 키가 아니라 이것이 균형을 만든다. */
  prio: number;
  /** 이 부분 트리에 든 구간들의 `high` 최댓값. 가지치기의 유일한 근거다. */
  maxHigh: number;
  left: Node | null;
  right: Node | null;
}

/** 빈 부분 트리는 어떤 질의에도 걸리지 않아야 하므로 가장 작은 값으로 둔다. */
function maxHighOf(node: Node | null): number {
  return node === null ? Number.NEGATIVE_INFINITY : node.maxHigh;
}

export class IntervalTree {
  #root: Node | null = null;
  #count = 0;
  #seq = 0;

  insert(low: number, high: number): void {
    const [smaller, larger] = this.#split(
      this.#root,
      (node) => this.#compare(node, low, high) <= 0,
    );
    const node: Node = {
      low,
      high,
      prio: this.#nextPrio(),
      maxHigh: high,
      left: null,
      right: null,
    };
    this.#root = this.#merge(this.#merge(smaller, node), larger);
    this.#count += 1;
  }

  delete(low: number, high: number): boolean {
    const [smaller, rest] = this.#split(
      this.#root,
      (node) => this.#compare(node, low, high) < 0,
    );
    const [same, larger] = this.#split(
      rest,
      (node) => this.#compare(node, low, high) <= 0,
    );
    if (same === null) {
      this.#root = this.#merge(smaller, larger);
      return false;
    }
    // `same` 에는 같은 키만 들어 있다. 그 뿌리 하나를 빼고 좌우를 도로 붙인다.
    const shrunk = this.#merge(same.left, same.right);
    this.#root = this.#merge(this.#merge(smaller, shrunk), larger);
    this.#count -= 1;
    return true;
  }

  /** 점 질의는 폭이 0인 구간 질의다. 따로 쓰면 두 벌의 가지치기가 갈릴 자리를 만든다. */
  stabQuery(point: number): [number, number][] {
    return this.overlapQuery(point, point);
  }

  overlapQuery(low: number, high: number): [number, number][] {
    const found: [number, number][] = [];
    this.#collect(this.#root, low, high, found);
    return found;
  }

  size(): number {
    return this.#count;
  }

  #collect(
    node: Node | null,
    low: number,
    high: number,
    found: [number, number][],
  ): void {
    if (node === null) return;
    // 이 부분 트리의 구간이 전부 질의보다 먼저 끝난다. 더 내려갈 이유가 없다.
    if (node.maxHigh < low) return;
    this.#collect(node.left, low, high, found);
    // 오른쪽은 시작점이 이 노드 이상이다. 이 노드가 이미 질의 뒤에서 시작하면 오른쪽도 그렇다.
    if (node.low > high) return;
    if (low <= node.high) found.push([node.low, node.high]);
    this.#collect(node.right, low, high, found);
  }

  /** 시작점이 먼저, 같으면 끝점이 다음. 같은 구간을 여러 벌 담을 수 있게 전순서로 둔다. */
  #compare(node: Node, low: number, high: number): number {
    if (node.low !== low) return node.low < low ? -1 : 1;
    if (node.high !== high) return node.high < high ? -1 : 1;
    return 0;
  }

  /** `goesLeft` 를 만족하는 앞쪽과 나머지 뒤쪽으로 가른다. */
  #split(
    node: Node | null,
    goesLeft: (node: Node) => boolean,
  ): [Node | null, Node | null] {
    if (node === null) return [null, null];
    if (goesLeft(node)) {
      const [middle, larger] = this.#split(node.right, goesLeft);
      node.right = middle;
      this.#pull(node);
      return [node, larger];
    }
    const [smaller, middle] = this.#split(node.left, goesLeft);
    node.left = middle;
    this.#pull(node);
    return [smaller, node];
  }

  /** 왼쪽 전부가 오른쪽 전부보다 작다는 전제로 잇는다. 모양은 우선순위가 정한다. */
  #merge(left: Node | null, right: Node | null): Node | null {
    if (left === null) return right;
    if (right === null) return left;
    if (left.prio > right.prio) {
      left.right = this.#merge(left.right, right);
      this.#pull(left);
      return left;
    }
    right.left = this.#merge(left, right.left);
    this.#pull(right);
    return right;
  }

  /**
   * 자식이 바뀐 노드의 `maxHigh` 를 다시 끌어올린다.
   *
   * 자르고 붙이는 **모든** 자리에서 불러야 한다. 한 자리라도 빠뜨리면 트리 모양은 멀쩡한데
   * 가지치기만 조용히 틀리고, 질의가 있는 구간을 못 찾는다.
   */
  #pull(node: Node): void {
    node.maxHigh = Math.max(
      node.high,
      maxHighOf(node.left),
      maxHighOf(node.right),
    );
  }

  /** 삽입 순번을 섞어 우선순위를 만든다. 입력 순서와 트리 모양을 끊는 자리다. */
  #nextPrio(): number {
    this.#seq = (this.#seq + 1) >>> 0;
    let x = this.#seq;
    x ^= x >>> 16;
    x = Math.imul(x, 0x85ebca6b) >>> 0;
    x ^= x >>> 13;
    x = Math.imul(x, 0xc2b2ae35) >>> 0;
    x ^= x >>> 16;
    return x >>> 0;
  }
}
```

**가장 중요한 부분은 `#pull` 하나입니다.** 자르고 붙이는 과정에서 자식이 바뀐 노드마다 이것을 부르는 것이 이 구조의 전부입니다. 3단계에서 얻은 *"부분 트리 하나당 값 하나"* 라는 결론이 이 한 함수로 코드가 되고, 나머지는 그 값을 유지하기 위한 배관입니다.

놓치기 쉬운 자리 넷을 짚어 둘게요.

- **`#split` 과 `#merge` 안의 `#pull` 호출.** 자식이 바뀐 **모든** 자리에서 불러야 합니다. 하나를 빠뜨리면 트리 모양은 멀쩡하고 값도 대부분 맞아서, 특정 배치에서만 조용히 답이 사라집니다. 4단계의 첫 번째 불변식이 이 자리를 지킵니다.
- **`#collect` 에서 `node.low > high` 검사가 왼쪽 재귀 *뒤에* 오는 것.** 앞으로 옮기면 왼쪽 부분 트리가 통째로 사라집니다. 왼쪽에는 시작점이 더 이른 구간들이 있고, 이른 구간일수록 질의와 겹칠 여지가 큽니다.
- **`maxHighOf` 가 빈 자리에 `Number.NEGATIVE_INFINITY` 를 주는 것.** 0 을 주면 좌표가 음수인 순간 없는 구간이 있는 것처럼 보입니다. 계약이 좌표 범위를 제한하지 않으므로 이 값은 "가장 작은 값"이어야 합니다.
- **`#compare` 가 시작점이 같을 때 끝점까지 보는 것.** 시작점만 키로 잡으면 시작점이 같은 두 구간이 한 자리를 다투게 되고, 계약이 *"같은 구간을 여러 번 넣으면 여러 벌로 센다"* 고 적은 것이 지켜지지 않습니다.

**성장률로 조건 충족을 확인합니다.** 계약 스위트 축3이 여섯 시나리오를 판별 수준(±30%)으로 잽니다.

**사용 조건이 달라지면 다른 구현이 적합합니다.** 계약은 구현을 처방하지 않으므로 여기 실린 것은 계약을 만족하는 여럿 중 하나입니다. 개별 호출의 최악까지 묶어야 한다면 회전으로 균형을 강제하는 설계가 `worst` 보장을 주지만 코드가 몇 배로 늘고, 계약은 그 보장을 요구하지 않습니다. 반대로 구간 집합이 처음에 정해지고 변하지 않는다면 삽입·삭제를 포기하는 대신 미리 나눠 정렬해 두는 설계가 더 낫습니다 — 계약에서 두 연산을 빼는 순간 그것은 다른 구조입니다.

1. 같은 다섯 구간이 든 트리에서 `stabQuery(4)` 를 손으로 따라가 보세요. 어느 노드를 들여다보고 어느 부분 트리를 버리는지, 그리고 이번에는 **어느 규칙이 오른쪽을 잘랐는지**를 답하세요. `max` 로 자른 것과 시작점으로 자른 것은 다른 규칙입니다. (정답은 `[[1,5],[3,8]]` 입니다.)
2. `#split` 안의 두 `#pull` 중 **아래쪽 하나만** 지웠다고 합시다. 트리 모양과 순서는 그대로인데 어떤 질의가 언제부터 답을 잃기 시작하는지 설명해 보세요. 4단계에서 말한 "작게 낡는다"가 어떤 뜻인지가 답에 들어가야 합니다.
3. `#collect` 에서 `if (node.low > high) return;` 을 왼쪽 재귀 **앞으로** 옮기면 어떤 입력에서 처음 어긋날까요? 위 다섯 구간과 `stabQuery(4)` 로 확인해 보세요.
4. 3단계에서 균형을 안 잡는 트리가 무작위 삽입에서는 정본보다 **싸게** 나왔습니다(12.10 대 26.39). 그런데도 그 설계를 쓰지 않는 이유를 "평균이 아니라 무엇을 보는가"로 설명해 보세요.
