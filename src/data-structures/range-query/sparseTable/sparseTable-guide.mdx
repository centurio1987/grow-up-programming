# Sparse Table — 겹쳐도 무해한 구간을 미리 쌓아 두기

## 한눈에 보는 컨셉

희소 테이블은 **바뀌지 않는 배열**에서 `min`, `max`, `gcd`처럼 같은 값을 두 번 세어도 결과가 그대로인 연산의 구간 질의를, 길이가 2의 거듭제곱인 구간들을 몽땅 미리 계산해 두고 즉시 답하는 자료구조예요. 비결은 임의 구간 `[l, r]`을 **겹쳐도 되는** 두 개의 `2^k` 길이 구간으로 덮어, 미리 저장해 둔 두 값을 merge 한 번으로 합치는 것입니다. 전처리에 `O(n log n)` 시간·공간을 투자한 대가로, 질의는 세그먼트 트리(`O(log n)`)보다도 빠른 `O(1)`에 끝나요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 희소 테이블을 떠올리세요.

- 배열이 **생성된 뒤 절대 바뀌지 않는다** (삽입·삭제·값 변경이 없음)
- 같은 배열에 대해 구간 질의가 **아주 여러 번**(수만~수십만 회) 들어온다
- 질의 연산이 `min`, `max`, `gcd`처럼 **같은 원소를 두 번 포함해도 결과가 변하지 않는(멱등, idempotent)** 연산이다

naive 순회·세그먼트 트리와 비교하면 이렇습니다(질의 1회 기준).

```text
naive 순회 [l, r]      O(n)        ← 매번 구간을 다시 훑는다
세그먼트 트리 질의       O(log n)    ← 갱신도 지원하지만 질의가 log n
희소 테이블 질의         O(1)        ← 정적 배열 + 멱등 연산일 때만
```

선택 기준은 한 문장으로 정리됩니다: **배열이 정적이고 merge가 멱등이면 희소 테이블, 값이 바뀌거나 merge가 구간 합처럼 멱등이 아니면 세그먼트 트리·펜윅 트리**를 씁니다. 업데이트가 하나라도 있다면 희소 테이블의 `O(1)` 질의는 애초에 성립하지 않아요 — 전처리 자체를 다시 해야 하니까요.

### 문제 사례와 적용 예시

- **RMQ(Range Minimum Query) → LCA의 O(1) 질의**: 트리를 오일러 투어로 평탄화하면 두 노드의 최소 공통 조상(LCA) 질의가 구간 최솟값 질의로 바뀝니다. 트리는 질의 전에 고정되어 있으므로 희소 테이블로 LCA를 `O(1)`에 답할 수 있어요.
- **DNS 캐시 TTL 최소값 스캔**: 한 번 등록되면 바뀌지 않는 수백만 개의 레코드에서, 임의 구간의 최소 TTL을 초당 수십만 번 질의해야 하는 상황(이 가이드의 예시 데이터).
- **정적 로그/시계열의 구간 최댓값**: 하루치 주가나 센서값이 고정된 뒤, "이 구간의 최고가는?" 같은 질의가 반복되는 분석 파이프라인.
- **코딩 테스트의 "배열 고정 + 질의 R개" 유형**: 문제 본문에 "배열은 변하지 않는다"는 조건과 함께 구간 질의가 여러 번 나오면, 세그먼트 트리보다 구현이 단순한 희소 테이블이 먼저 후보에 올라야 합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드는 다음 인터페이스를 스스로 정의하고, 이하 서술 전체를 여기에 맞춥니다.

```ts
class SparseTable {
  private n: number;
  private log: number[];       // log[i] = floor(log2(i))
  private table: number[][];   // table[k][i]: arr[i..i+2^k-1] 구간의 merge 결과
  private merge: (a: number, b: number) => number;

  constructor(arr: number[], merge: (a: number, b: number) => number) {}
  query(l: number, r: number): number {}
}
```

지켜야 할 불변식은 세 가지예요.

1. **`table[0][i] = arr[i]`** — 길이 1 구간의 merge 결과는 원소 자기 자신입니다.
2. **`table[k][i]`는 정확히 그 구간의 merge 결과**입니다. 정식으로 쓰면:

$$
table[k][i] = \mathrm{merge}\bigl(arr[i],\, arr[i+1],\, \dots,\, arr[i+2^{k}-1]\bigr), \quad 0 \le i \le n - 2^{k}
$$

3. **`log[i] = \lfloor \log_2 i \rfloor`** (`1 \le i \le n`) — 질의마다 로그를 다시 계산하지 않도록 미리 저장해 둡니다.

`n = 5`, `arr = [8, 6, 7, 3, 5]`, `merge = min`일 때 테이블 전체를 그리면 이렇습니다.

```text
인덱스:      0    1    2    3    4
table[0]:    8    6    7    3    5     ← 길이 1  (2^0)
table[1]:    6    6    3    3    ·     ← 길이 2  (2^1), i=4는 범위 밖(2+4>5)이라 없음
table[2]:    3    3    ·    ·    ·     ← 길이 4  (2^2), i=0,1만 유효(4+4≤5, 4+... i=2는 2+4=6>5)

레벨이 하나 올라갈 때마다 유효한 i의 범위가 줄어든다 — table[k]는 i가 0 ~ n-2^k까지만 존재.
```

**액션(연산)** — 이 자료구조가 제공하는 연산은 두 개뿐입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(arr, merge)` | `table[0]`을 원본 배열로 채운 뒤, `k`를 1부터 늘려가며 아래 레벨 두 블록을 merge해 위 레벨을 채운다 | `O(n log n)` 시간·공간 |
| `query(l, r)` | `k = ⌊log2(len)⌋`을 골라 왼쪽·오른쪽 `2^k` 블록을 merge한다 | `O(1)` |

**빌드(전처리)** 를 before/after로 보면, 인접한 두 `2^{k-1}` 블록이 합쳐져 하나의 `2^k` 블록이 됩니다.

```text
Before (table[k-1], 길이 2^(k-1) 블록들이 빈틈없이 나열):
  [——— 2^(k-1) ———][——— 2^(k-1) ———][——— 2^(k-1) ———] ...
        i                i+2^(k-1)

After (table[k], 인접한 두 블록을 merge해 길이 2^k 블록 하나로):
  [————————— 2^k —————————][————————— 2^k —————————] ...
   table[k][i] = merge(table[k-1][i], table[k-1][i + 2^(k-1)])
```

**질의**의 두 블록이 겹치는 정도는 구간 길이에 따라 달라집니다. 두 극단을 나란히 보면:

```text
query(1, 4)  — 최대로 겹치는 경우 (len=4, k=2, 2^k=4, len이 2^k와 정확히 같음)
  구간 [1,4] 전체:        1    2    3    4
  왼쪽 블록 table[2][1]:  1    2    3    4
  오른쪽 블록 table[2][1]: 1    2    3    4     ← r-2^k+1 = 4-4+1 = 1 = l, 왼쪽과 완전히 같은 블록!
  결과 = merge(table[2][1], table[2][1]) = merge(3, 3) = 3

query(0, 2)  — 최소로 겹치는 경우 (len=3, k=1, 2^k=2)
  구간 [0,2] 전체:        0    1    2
  왼쪽 블록 table[1][0]:  0    1
  오른쪽 블록 table[1][1]:     1    2          ← 인덱스 1 딱 한 칸만 겹친다
  결과 = merge(table[1][0], table[1][1]) = merge(6, 6) = 6
```

`query(1, 4)`처럼 구간 길이가 정확히 `2^k`이면 `r - 2^k + 1 = l`이 되어 왼쪽·오른쪽 블록이 **완전히 같은 블록**이 됩니다(겹침이 없는 게 아니라 오히려 최대로 겹치는 경우예요). 반대로 길이가 `2^{k+1}-1`에 가까워질수록 겹치는 구간은 줄어들어 최소 1칸까지 좁혀집니다. 즉 이 알고리즘에서 두 블록이 **완전히 분리되는 경우는 없습니다** — 항상 최소 1칸 이상 겹치거나(때로는 블록 전체가) 겹칩니다.

### 왜 모순 없이 작동하는가

**빌드가 항상 옳은 이유(귀납)**: `table[0][i] = arr[i]`는 길이 1 구간의 merge이므로 자명하게 참입니다. `table[k-1][*]`가 모두 정확하다고 가정하면, `table[k][i] = merge(table[k-1][i], table[k-1][i+2^{k-1}])`는 `[i, i+2^{k-1}-1]`과 `[i+2^{k-1}, i+2^k-1]`이라는 **겹치지 않고 딱 맞붙는 두 구간**의 merge입니다. 이 둘을 합치면 `[i, i+2^k-1]` 전체를 빠짐없이 정확히 한 번씩 덮으므로, merge가 결합법칙을 만족하는 한(`min`, `max`, `gcd` 모두 만족) `table[k][i]`도 정확합니다. 빌드 단계에서는 애초에 겹침이 없다는 점이 핵심이에요 — 멱등성은 아직 필요 없습니다.

**질의가 항상 옳은 이유(멱등성이 필요한 순간)**: `len = r - l + 1`, `k = ⌊log2 len⌋`이면 `2^k \le len < 2^{k+1}`이 성립합니다. 왼쪽 블록 `[l, l+2^k-1]`과 오른쪽 블록 `[r-2^k+1, r]`의 교집합 크기를 정리하면 정확히 `2^{k+1} - len`이 나옵니다. `2^k \le len < 2^{k+1}`이므로 이 값은 **항상 1 이상 `2^k` 이하** — 절대 0이 될 수 없습니다. 즉 두 블록은 합쳐서 `[l, r]`을 빠짐없이 덮으면서도, 반드시 어딘가에서 겹칩니다. 겹치는 원소가 있어도 답이 맞으려면 `merge(merge(x, y), y) = merge(x, y)` — 즉 **같은 원소를 두 번 포함해도 결과가 바뀌지 않는 멱등성**이 필요합니다. `min`, `max`, `gcd`는 이 성질을 만족하지만(예: `min(min(6,3),3) = min(6,3) = 3`), **구간 합은 만족하지 않습니다**.

잠깐, 확인 하나만 해 볼까요? `query(0, 0)`은 표에서 어떤 값을 가리킬까요? `len=1`이므로 `k=0`, 왼쪽·오른쪽 블록이 모두 `table[0][0]`이에요. 답은 `merge(8, 8) = 8` — `table[0][0]`을 그대로 읽는 것과 같습니다.

**여기서 헷갈리기 쉬운 포인트는 "멱등이면 무조건 된다"가 아니라 "합(sum)에는 왜 못 쓰는가"입니다.** 같은 배열 `[1, 2, 3, 4, 5]`에 `merge = sum`을 넣고 `query(0, 4)`를 계산해 보면:

```text
len=5, k=⌊log2 5⌋=2, 2^k=4
왼쪽 블록 [0,3] 합 = 1+2+3+4 = 10
오른쪽 블록 [1,4] 합 = 2+3+4+5 = 14
merge(10, 14) = 24                    ← 희소 테이블이 내놓는 값

실제 [0,4] 전체 합 = 1+2+3+4+5 = 15   ← 정답
차이 = 24 - 15 = 9 = 2+3+4            ← 겹친 인덱스 1,2,3이 두 번 더해졌다
```

구간 합은 `sum(sum(x,y),y) ≠ sum(x,y)`이므로(같은 원소를 두 번 더하면 그만큼 더 커짐) 겹치는 두 블록을 그대로 합칠 수 없습니다. 값이 바뀌지 않는 배열이라도 합·곱처럼 멱등이 아닌 연산에는 희소 테이블 대신 누적합(prefix sum)이나 세그먼트 트리를 써야 해요.

엣지 케이스를 점검해 볼게요.

```text
n = 1 (단일 원소)          → log[1]=0, table=[[arr[0]]], query(0,0) = table[0][0]
구간 길이가 정확히 2^k     → 왼쪽·오른쪽 블록이 완전히 같아짐(최대 겹침), merge(x,x)=x (query(1,4) 사례)
구간 길이가 2^{k+1}-1에 근접 → 겹침이 최소 1칸까지 줄어듦, 그래도 0은 아님 (query(0,2) 사례)
l === r (길이 1 구간)      → k=0, 왼쪽=오른쪽=table[0][l], merge(x,x)=x
```

## 아이디어를 코드로 옮기기

```ts
class SparseTable {
  private n: number;
  private log: number[];
  private table: number[][];
  private merge: (a: number, b: number) => number;

  constructor(arr: number[], merge: (a: number, b: number) => number) {
    const n = arr.length;
    this.n = n;
    this.merge = merge;

    // log[i] = floor(log2(i)): 질의마다 다시 계산하지 않도록 미리 채운다.
    this.log = new Array(n + 1).fill(0);
    for (let i = 2; i <= n; i++) {
      this.log[i] = this.log[Math.floor(i / 2)]! + 1;
    }

    const LOG = this.log[n]! + 1;
    this.table = Array.from({ length: LOG }, () => new Array(n).fill(0));
    this.table[0] = arr.slice();

    for (let k = 1; k < LOG; k++) {
      for (let i = 0; i + (1 << k) <= n; i++) {
        this.table[k]![i] = merge(this.table[k - 1]![i]!, this.table[k - 1]![i + (1 << (k - 1))]!);
      }
    }
  }

  query(l: number, r: number): number {
    const len = r - l + 1;
    const k = this.log[len]!;
    const left = this.table[k]![l]!;
    const right = this.table[k]![r - (1 << k) + 1]!;
    return this.merge(left, right);
  }
}
```

가장 중요한 부분은 `constructor`의 이중 루프에서 **`k`가 바깥, `i`가 안쪽**이라는 순서입니다. `table[k][i]`는 `table[k-1]`이 이미 완성되어 있어야 계산할 수 있으므로, `k`를 오름차순으로 완전히 끝내고 다음 레벨로 넘어가야 해요. 만약 두 반복문을 뒤집거나 `k`를 안쪽에 두면, 아직 채워지지 않은(0으로 초기화된) `table[k-1]`을 읽어 틀린 값이 조용히 저장됩니다.

`query`에서 가장 중요한 줄은 `r - (1 << k) + 1`입니다. 이건 **오른쪽 블록의 시작 인덱스**예요 — "r에서 `2^k`칸만큼 왼쪽으로 물러난 지점"이지, `l + (1 << k)`(왼쪽 블록이 끝나는 다음 칸)가 아닙니다. 두 식을 헷갈리면 구간 길이가 `2^k`의 배수가 아닐 때 엉뚱한 인덱스를 읽거나 범위를 벗어납니다.

> 기억법: "왼쪽은 `l`에서 오른쪽으로 `2^k`칸, 오른쪽은 `r`에서 왼쪽으로 `2^k`칸 — 가운데서 겹쳐도 멱등이라 무해하다."
