# Fenwick Tree — 인덱스의 낮은 비트에 구간 합을 나눠 맡기기

## 한눈에 보는 컨셉

배열 하나로 **점 갱신**과 **접두사 합 조회**를 모두 `O(log n)`에 처리하는 자료구조예요. 비결은 각 칸 `tree[i]`가 "길이 `lowbit(i)`짜리 구간의 합"을 책임지도록 나눠 맡긴 것 — 그게 전부입니다. 갱신은 비트를 더하며 위로, 조회는 비트를 빼며 아래로 이동합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

문제에서 다음 신호들이 **동시에** 보이면 Fenwick Tree를 떠올리세요.

- 배열 원소의 값이 **계속 바뀐다** (점 갱신: "인덱스 `i`에 `delta`를 더해라")
- **구간 합**(또는 접두사 합)을 반복해서 묻는다
- 두 종류의 연산이 **섞여서 대량으로** 들어온다 (예: 각각 `10^5`번)

둘 중 하나만 있다면 더 단순한 도구로 충분합니다. 문제는 섞였을 때예요.

```text
                     갱신        조회        q번 섞이면
배열 그대로 유지     O(1)        O(n)        O(qn) ≈ 10^10  ✗
접두사 합 미리 계산  O(n)        O(1)        O(qn) ≈ 10^10  ✗
Fenwick Tree         O(log n)    O(log n)    O(q log n) ≈ 1.7×10^6  ✓
```

한쪽을 빠르게 만들면 다른 쪽이 느려지는 시소 관계를, Fenwick Tree는 **양쪽 다 `O(log n)`** 으로 타협해서 끊어냅니다. 같은 복잡도를 내는 Segment Tree보다 코드가 훨씬 짧고(배열 하나 + 루프 두 개), 공간도 `O(n)`으로 작다는 것이 실전에서의 매력이에요. 단, **구간 갱신**(range update)이 필요해지면 lazy propagation을 갖춘 Segment Tree가 더 적합합니다.

### 문제 사례와 적용 예시

- **실시간 순위표**: `10^5`명의 점수가 계속 바뀌는 게임에서 "1번~k번 선수의 총점"을 매번 물을 때.
- **inversion 개수 세기**: 배열을 왼쪽부터 읽으며 "지금까지 등장한 값 중 나보다 큰 것의 개수"를 누적할 때, 값을 인덱스로 하는 Fenwick Tree로 `O(n log n)`에 셉니다.
- **k번째 원소 찾기**: 존재 여부를 0/1로 저장하면 접두사 합이 "k번째로 작은 원소" 탐색의 기반이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성**은 단 하나, 크기 `n+1`의 배열입니다.

- `tree: number[]` — **1-기반** 인덱스를 사용하고 `tree[0]`은 사용하지 않습니다. 각 칸이 지키는 약속(불변식)은 이것 하나예요:

$$tree[i] = \sum_{k = i - \text{lowbit}(i) + 1}^{i} A[k], \qquad \text{lowbit}(i) = i \,\&\, (-i)$$

`lowbit(i)`는 `i`의 이진 표현에서 **가장 낮은 set 비트의 값**입니다. 2의 보수 표현 덕분에 `i & -i` 한 번으로 구해져요.

```text
i  = 6 = 0110₂
-i     = 1010₂  (비트 반전 + 1)
────────────────
i & -i = 0010₂ = 2   →  tree[6]은 "끝점이 6이고 길이가 2인 구간" A[5..6]의 합을 맡는다
```

`n = 8`일 때 각 칸의 책임 구간을 그려 보면 구조가 한눈에 들어옵니다.

```text
A:        1    2    3    4    5    6    7    8
tree[1]  [——]                                     lowbit(1)=1
tree[2]  [————————]                               lowbit(2)=2
tree[3]            [——]                           lowbit(3)=1
tree[4]  [——————————————————]                     lowbit(4)=4
tree[5]                      [——]                 lowbit(5)=1
tree[6]                      [————————]           lowbit(6)=2
tree[7]                                [——]       lowbit(7)=1
tree[8]  [————————————————————————————————————]  lowbit(8)=8
```

**액션**은 세 가지입니다.

**① `update(i, delta)`** — `A[i]`에 `delta`를 더합니다. `A[i]`를 책임 구간에 포함하는 모든 `tree` 칸을 고쳐야 하는데, 그 칸들은 `i`에서 출발해 `lowbit`를 **더하면** 차례로 만납니다.

$$i \;\to\; i + \text{lowbit}(i) \;\to\; \cdots \quad (i \leq n \text{인 동안})$$

```text
update(3, Δ):   3 ─(+1)→ 4 ─(+4)→ 8 ─(+8)→ 16 > n, 종료

위 그림에서 확인: A[3]을 덮는 구간은 tree[3], tree[4], tree[8] — 정확히 방문한 칸들
```

**② `prefixSum(i)`** — `A[1..i]`의 합을 반환합니다. `i`에서 출발해 `lowbit`를 **빼면**, 서로 겹치지 않는 책임 구간들이 `[1, i]`를 정확히 덮습니다.

$$i \;\to\; i - \text{lowbit}(i) \;\to\; \cdots \quad (i > 0 \text{인 동안})$$

```text
prefixSum(7):   7 ─(-1)→ 6 ─(-2)→ 4 ─(-4)→ 0, 종료

수집한 구간:   tree[7] = A[7..7]
             + tree[6] = A[5..6]
             + tree[4] = A[1..4]
             ────────────────────
             = A[1..7]   빠짐도 겹침도 없다
```

**③ `rangeSum(l, r)`** — 임의 구간 합은 접두사 합 두 개의 차이입니다.

$$\text{rangeSum}(l, r) = \text{prefixSum}(r) - \text{prefixSum}(l-1)$$

### 왜 모순 없이 작동하는가

핵심 불변식은 "각 `tree[i]`는 끝점 `i`, 길이 `lowbit(i)`인 구간의 합"입니다. 두 액션이 이 불변식과 모순 없이 맞물리는지 확인해 봅시다.

**prefixSum이 `[1, i]`를 정확히 덮는 이유**: `i`에서 `lowbit(i)`를 빼는 것은 이진 표현에서 **가장 낮은 set 비트를 하나 지우는 것**입니다.

```text
7 = 0111₂  ─ 지우기 →  6 = 0110₂  ─ 지우기 →  4 = 0100₂  ─ 지우기 →  0
```

지금 위치가 `i`일 때 `tree[i]`는 `(i - lowbit(i), i]` 구간을 보태고, 다음 위치는 정확히 그 구간의 왼쪽 끝인 `i - lowbit(i)`입니다. 즉 **방금 덮은 구간의 바로 왼쪽에서 이어서 덮기 때문에** 겹침도 빠짐도 생길 수 없어요. set 비트는 최대 `log n`개이므로 반복도 최대 `log n`번에 끝납니다.

**update가 필요한 칸을 전부, 그리고 그 칸만 방문하는 이유**: `A[i]`를 덮는 칸 `j`는 "`j ≥ i`이면서 책임 구간의 시작 `j - lowbit(j) + 1 ≤ i`"를 만족하는 칸입니다. `i`에 `lowbit(i)`를 더하면 지금 칸을 덮는 **가장 가까운 더 큰 책임 구간**으로 올라가는데, 이 경로가 그런 `j`들을 빠짐없이, 순서대로 지나갑니다. 위 그림에서 `A[3]`으로 직접 확인해 보세요 — `tree[3] → tree[4] → tree[8]`, 정확히 3을 덮는 칸 전부입니다.

여기서 **헷갈리기 쉬운 포인트** 세 가지를 짚어 둘게요.

- **왜 1-기반인가?** `lowbit(0) = 0`이기 때문입니다. 0-기반으로 쓰면 인덱스 0에서 `i += lowbit(i)`가 `0 += 0`이 되어 **무한 루프**에 빠져요. 인덱스 0을 "비워 두는" 것이 이 함정을 구조적으로 차단합니다.
- **`prefixSum(0)`은 뭘 반환해야 하나?** 빈 구간의 합인 `0`입니다. 루프 조건 `i > 0`이 첫 반복부터 거짓이라 자연스럽게 `0`이 반환되고, 덕분에 `rangeSum(1, r) = prefixSum(r) - prefixSum(0)`도 특별 취급 없이 성립해요.
- **`tree`에는 원소 값 자체가 없다.** `tree[5] = A[5]`처럼 보이는 칸(lowbit이 1인 홀수 칸)도 있지만 `tree[6]`은 `A[5]+A[6]`입니다. "현재 `A[i]` 값이 얼마인가"가 필요하면 `rangeSum(i, i)`로 묻거나 원본 배열을 따로 유지해야 합니다.

엣지 케이스도 불변식 위에서 자연스럽게 처리됩니다.

```text
rangeSum(l, l)   = prefixSum(l) - prefixSum(l-1)  → 단일 원소 A[l]
prefixSum(n)     = 전체 합 (n=8이면 tree[8] 하나로 끝나기도 한다)
update(i, 음수)  = 빼기와 동일 — delta 부호에 제약 없음
```

잠깐, 확인 하나만 해 볼까요? `prefixSum(5)`는 어떤 칸들을 방문할까요?

`5 = 0101₂ ─(-1)→ 4 = 0100₂ ─(-4)→ 0` — `tree[5](A[5..5]) + tree[4](A[1..4])`, 두 번에 `[1, 5]`를 덮습니다.

## 아이디어를 코드로 옮기기

이 프로젝트의 `fenwickTree.ts`가 선언한 인터페이스(1-기반, `update`/`prefixSum`/`rangeSum`) 그대로 구현합니다.

```ts
class FenwickTree {
  private tree: number[];
  private n: number;

  constructor(n: number) {
    this.n = n;
    this.tree = new Array(n + 1).fill(0); // 1-기반: tree[0]은 사용하지 않음
  }

  update(i: number, delta: number): void {
    for (; i <= this.n; i += i & -i) {
      this.tree[i] += delta;
    }
  }

  prefixSum(i: number): number {
    let s = 0;
    for (; i > 0; i -= i & -i) {
      s += this.tree[i];
    }
    return s;
  }

  rangeSum(l: number, r: number): number {
    return this.prefixSum(r) - this.prefixSum(l - 1);
  }
}
```

**가장 중요한 부분은 두 루프의 증감식입니다** — `i += i & -i`(위로), `i -= i & -i`(아래로). 나머지는 전부 이 두 줄을 감싸는 포장이에요. 구현할 때 놓치기 쉬운 지점들:

- **0-기반 데이터를 다룰 때의 `+1` 변환.** 문제의 배열이 0-기반이라면 Fenwick에 넣을 때 `update(idx + 1, v)`로 옮겨야 합니다. 변환을 잊고 `update(0, v)`를 호출하면 `0 += lowbit(0) = 0`으로 첫 칸에서 무한 루프에 빠져요 — 가장 흔하고 치명적인 실수입니다.
- **`rangeSum`의 두 번째 인자는 `l`이 아니라 `l - 1`.** `prefixSum(l)`을 빼면 `A[l]`까지 같이 빠져서 구간이 한 칸 어긋납니다.
- **기존 배열로 초기화**할 때는 각 원소마다 `update(i, A[i])`를 호출하면 `O(n log n)`으로 충분합니다. (더 빠른 `O(n)` 초기화도 있지만, 필요해질 때 찾아도 늦지 않아요.)
- `i & -i`는 JavaScript/TypeScript의 32비트 정수 연산 범위에서 올바르게 동작하므로 `n ≤ 10^5` 수준에서는 걱정할 것이 없습니다.
