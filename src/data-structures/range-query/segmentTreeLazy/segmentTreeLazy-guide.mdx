# Segment Tree with Lazy Propagation — 지금 안 내려가도 되면, 태그만 남기고 미룬다

## 한눈에 보는 컨셉

구간 전체에 값을 더하는 갱신과 구간 합 조회를 둘 다 $O(\log n)$에 처리하는 세그먼트 트리의 확장이에요. 비결은 하나입니다 — 갱신이 어떤 노드의 담당 구간을 완전히 덮으면, 그 노드의 합만 즉시 고치고 "자식에게 아직 안 알렸다"는 사실을 `lazy` 태그로 남긴 채 멈춥니다. 자식은 나중에 실제로 방문할 때만 태그를 넘겨받아요. 덕분에 리프까지 매번 내려가지 않고도 구간 갱신과 구간 합 조회 모두 $O(\log n)$을 유지합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Lazy Segment Tree를 떠올리세요.

- **구간 갱신**("$[l,r]$ 전체에 $v$를 더하라/곱하라/대입하라")과 **구간 집계 조회**("$[l,r]$의 합/최솟값/최댓값은?")가 **번갈아** 섞여 들어온다
- 두 연산 모두 $n$이 커도($10^5$ 이상) 빠르게 처리해야 한다
- 점 갱신(원소 하나만 바꾸기)만 있다면 이 구조는 과합니다 — 그때는 lazy 없는 일반 세그먼트 트리나 Fenwick Tree가 더 단순해요. Lazy Segment Tree는 **구간 갱신**이 있을 때만 필요합니다.

naive 대안들과 비교하면 왜 필요한지 체감됩니다. 배열 $A[0..n-1]$에 구간 가산 $q$번과 구간 합 조회 $q$번이 섞여 온다고 해봅시다.

```text
방법 A: 매번 A[l..r] 직접 갱신           갱신 O(n), 조회 O(n)   → O(qn)
방법 B: 접두사 합 배열 유지               조회 O(1), 갱신 O(n)   → O(qn) (재계산 비용)
방법 C: lazy 없는 세그먼트 트리로 구간 갱신  갱신이 리프까지 전파 → O(n) → O(qn)
방법 D: Lazy Segment Tree                갱신 O(log n), 조회 O(log n) → O(q log n)
```

$n = q = 10^5$이면 $qn = 10^{10}$(불가능)인 반면, $q \log n \approx 10^5 \times 17 \approx 1.7 \times 10^6$(충분)이에요. 구간 갱신을 "완전히 덮이는 노드에서 멈추는" 전략 하나가 이 격차를 만듭니다.

### 문제 사례와 적용 예시

- **재고·매출 집계 시스템**: 특정 기간(구간) 전체 매장에 프로모션 할인율을 일괄 적용하고, 임의의 기간 범위의 매출 합계를 수시로 조회하는 대시보드.
- **게임 서버의 광역 효과**: 맵의 특정 좌표 구간에 있는 모든 유닛에게 버프/디버프 값을 일괄 부여하고, 특정 구간의 총 전투력을 조회.
- **코딩 테스트 맥락**: "구간에 값을 더하라"와 "구간 합/최댓값을 구하라"가 쿼리로 번갈아 $10^5$번 주어지는 전형적인 구간 문제 — Lazy Propagation이 표준 해법입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

배열 기반으로 구현합니다. 루트를 인덱스 1로 두고 $\text{left}(v) = 2v$, $\text{right}(v) = 2v+1$이면 포인터 없이도 트리가 완성돼요.

```ts
class SegmentTreeLazy {
  private n: number;
  private sum: number[];    // sum[v]: 노드 v가 담당하는 구간의 합
  private lazy: number[];   // lazy[v]: 아직 자식에게 전파 안 한 구간 가산 값
}
```

`sum`과 `lazy` 모두 크기 $4n$이면 어떤 $n$에서도 트리가 들어갑니다(완전 이진트리가 아니어도 안전 여유분).

지켜야 할 불변식은 두 가지예요.

1. **`sum[v]`는 항상 최신값이다.** 노드 $v$가 담당하는 구간 $[lo, hi]$에 대해 $\text{sum}[v] = \sum_{i=lo}^{hi} A[i]$이며, 이때 $A$는 지금까지의 모든 `rangeAdd`가 반영된 값입니다. `lazy[v]`가 아직 자식에게 안 내려갔어도 `sum[v]` 자체는 항상 맞아야 해요.
2. **`lazy[v]`는 "자식에게 아직 전달 안 한 몫"이다.** $\text{lazy}[v] \neq 0$이면, 자식 두 개는 아직 이 값을 반영받지 못한 상태입니다. 자식을 실제로 건드리기 직전에 반드시 전파해야 합니다.

```text
              sum[1]=25 (lazy=0)         ← 루트: [0,3] 담당
             /                \
     sum[2]=8 (lazy=0)      sum[3]=17 (lazy=5)   ← 오른쪽: 아직 자식에게 안 넘긴 +5가 걸려 있다
     /        \                /        \
sum[4]=1   sum[5]=7        sum[6]=3   sum[7]=4   ← 이 두 리프는 여전히 옛날 값(+5 못 받음)
 [0,0]      [1,1]           [2,2]      [3,3]
```

위 그림에서 `sum[3] = 17`은 이미 $+5$가 반영된 최신 합이지만, 자식 `sum[6]`, `sum[7]`은 아직 원래 값(3, 4) 그대로입니다. 이게 바로 불변식 2가 허용하는 "지연된" 상태예요.

액션은 두 가지뿐이지만, 내부적으로 세 개의 보조 연산이 이를 지탱합니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `rangeAdd(l, r, val)` | $[l, r]$ 전체 원소에 `val`을 더한다 | $O(\log n)$ |
| `rangeSum(l, r)` | $[l, r]$ 구간 합을 반환한다 | $O(\log n)$ |
| (내부) `apply(v, lo, hi, val)` | 노드 $v$에 즉시 반영 + lazy 누적 | $O(1)$ |
| (내부) `pushDown(v, lo, hi)` | lazy를 두 자식에게 전파 | $O(1)$ |

핵심 연산인 `rangeAdd`의 진행을 그림으로 봅니다. `n=4`, 초기 `A=[1,2,3,4]`에서 `rangeAdd(1,3,+5)`를 실행하면:

```text
Before: [0,3] 담당 노드가 [1,3]을 부분 포함 → 내려가야 함
        [0,3]
       /      \
   [0,1]      [2,3]        [1,3]과 겹치지만 완전 포함 아님(둘 다 부분)
   /   \       /   \
 [0,0] [1,1] [2,2] [3,3]

After:  [1,1]과 [2,3]은 [1,3]에 완전 포함 → apply로 즉시 반영, 자식엔 lazy만
        [0,3] sum=25                         ← 자식 합으로 재계산
       /            \
   [0,1] sum=8    [2,3] sum=17 (lazy=5)      ← 완전 포함: sum만 갱신, 자식 안 건드림
   /        \        /       \
 [0,0]=1  [1,1]=7  [2,2]=3  [3,3]=4          ← [2,2],[3,3]은 아직 옛값(lazy가 안 내려감)
         (lazy=5로 apply됨)
```

$[1,3]$을 완전히 덮는 노드는 $[1,1]$과 $[2,3]$ 딱 둘뿐이었고, 나머지는 이 둘의 조상이거나 교차 없는 노드였습니다. 그래서 방문한 노드 수가 트리 높이에 비례하는 $O(\log n)$개로 끝나요.

### 왜 모순 없이 작동하는가

**귀납 논증**: 트리를 처음 만들 때는 모든 `lazy`가 0이고 `sum`은 초기 배열 그대로이니 불변식이 성립합니다. 이제 `apply`, `pushDown`, `rangeAdd`, `rangeSum` 각각이 불변식을 보존함을 봅니다.

- `apply(v, lo, hi, val)`은 $[lo,hi]$ 전체에 `val`이 더해졌다고 가정하고 $\text{sum}[v] \mathrel{+}= \text{val} \times (hi-lo+1)$로 즉시 반영합니다. 이건 산수적으로 참이므로 불변식 1이 유지돼요. 동시에 $\text{lazy}[v] \mathrel{+}= \text{val}$로 "자식에게 아직 안 알림"을 기록하니 불변식 2도 유지됩니다.
- `pushDown(v, lo, hi)`는 `lazy[v]`를 그대로 두 자식에게 `apply`로 넘기고 `lazy[v] = 0`으로 지웁니다. 자식 쪽에서 보면 방금 전달받은 값을 자기 `sum`에 반영하고 자기 `lazy`에 누적했으니 불변식 1·2가 자식에서도 유지되고, 부모는 이제 "전달할 몫이 없다"는 참인 상태가 됩니다.
- `rangeAdd`가 노드를 완전 포함으로 판정하면 `apply` 한 번으로 끝내고 자식은 건드리지 않습니다 — 자식의 불변식은 그대로 보존됩니다(아직 반영 안 된 게 맞으니까요). 부분 포함이면 재귀 전에 반드시 `pushDown`을 먼저 호출해 자식의 `sum`을 최신으로 만든 다음 내려가고, 재귀가 끝나면 $\text{sum}[v] = \text{sum}[\text{left}] + \text{sum}[\text{right}]$로 다시 계산합니다. 자식들이 불변식 1을 만족하는 채로 돌아왔으므로 이 합산도 참입니다.
- `rangeSum`도 완전 포함 노드에서는 불변식 1 덕분에 `sum[v]`를 그대로 반환하면 되고, 부분 포함이면 `pushDown` 후 좌우 재귀 합으로 정확한 값을 얻습니다.

바닥(리프)에서 시작해 위로 귀납하면, 트리의 어느 시점 어느 노드를 봐도 불변식 1·2가 성립합니다.

**여기서 헷갈리기 쉬운 포인트는 "완전 포함이면 자식을 아예 안 봐도 되는가"입니다.** 답은 "봐도 되지만 안 봐도 정확하다"입니다. `sum[v]`가 이미 최신이므로 조회는 자식 없이 끝낼 수 있고, 그 사실을 자식에게 알리는 시점만 다음 방문으로 미루는 것뿐이에요. 자식이 실제로 필요해지는 순간(그 자식을 재귀로 내려가야 하는 순간)에는 반드시 `pushDown`을 거치므로 늦게 알려져도 틀리지 않습니다.

또 하나, **`pushDown`은 리프에서 호출하면 안 됩니다.** 리프는 자식이 없으니 `left(v) = 2v`, `right(v) = 2v+1`에 접근해도 그 인덱스는 애초에 쓰인 적 없는 값(0)입니다. 완전 포함/교차 없음 판정에서 이미 걸러지긴 하지만("부분 포함"은 반드시 자식이 있는 내부 노드에서만 일어남), 구현 시 재귀 조건을 `lo == hi`로 리프를 먼저 가르는 습관을 들이면 안전합니다.

엣지 케이스를 점검해 봅니다.

```text
n = 1                     → 트리는 루트(=리프) 하나. rangeAdd(0,0,v), rangeSum(0,0) 정상 동작.
rangeAdd(0, n-1, val)     → 루트가 곧 완전 포함 → apply 한 번, O(1)로 끝남(자식 안 내려감).
rangeSum(i, i)            → 단일 원소 조회. 리프까지 내려가 pushDown 누적을 그대로 받음.
val이 음수                → apply의 산수는 부호와 무관하게 그대로 성립. 감산과 동일하게 처리됨.
rangeAdd 없이 rangeSum만  → lazy가 전부 0인 채로 sum만 조회 → pushDown이 실질적으로 아무것도 안 함.
```

잠깐, 확인 하나만 해볼까요? 위 그림에서 `rangeAdd(1,3,+5)` 직후 곧바로 `rangeSum(2,2)`를 호출하면 어떻게 될까요 — `sum[6]`은 여전히 3인데 정답이 나올까요? 정답은 "예"입니다. `rangeSum`이 `[2,2]`로 내려가려면 부모 `[2,3]`에서 반드시 `pushDown`을 거치고, 그 순간 `lazy[3]=5`가 `sum[6]`에 `apply`되어 $3+5=8$로 갱신된 뒤에 재귀가 진행되기 때문이에요.

## 아이디어를 코드로 옮기기

배열 기반 인덱싱(`root=1`, `left=2v`, `right=2v+1`)에 맞춰 그대로 구현합니다. 원형인 "lazy 없는 세그먼트 트리"와 다른 점은 `apply`/`pushDown` 두 함수가 추가되고, 재귀 진입 직전에 `pushDown`을 끼워 넣는다는 것뿐이에요.

```ts
class SegmentTreeLazy {
  private n: number;
  private sum: number[];
  private lazy: number[];

  constructor(input: number | number[]) {
    const arr = typeof input === "number" ? new Array(input).fill(0) : input;
    this.n = arr.length;
    this.sum = new Array(4 * Math.max(this.n, 1)).fill(0);
    this.lazy = new Array(4 * Math.max(this.n, 1)).fill(0);
    if (this.n > 0) this.build(1, 0, this.n - 1, arr);
  }

  private build(v: number, lo: number, hi: number, arr: number[]): void {
    if (lo === hi) {
      this.sum[v] = arr[lo];
      return;
    }
    const mid = Math.floor((lo + hi) / 2);
    this.build(2 * v, lo, mid, arr);
    this.build(2 * v + 1, mid + 1, hi, arr);
    this.sum[v] = this.sum[2 * v] + this.sum[2 * v + 1];
  }

  private apply(v: number, lo: number, hi: number, val: number): void {
    this.sum[v] += val * (hi - lo + 1);
    this.lazy[v] += val;
  }

  private pushDown(v: number, lo: number, hi: number): void {
    if (this.lazy[v] === 0) return;
    const mid = Math.floor((lo + hi) / 2);
    this.apply(2 * v, lo, mid, this.lazy[v]);
    this.apply(2 * v + 1, mid + 1, hi, this.lazy[v]);
    this.lazy[v] = 0;
  }

  private updateRange(v: number, lo: number, hi: number, l: number, r: number, val: number): void {
    if (r < lo || hi < l) return;
    if (l <= lo && hi <= r) {
      this.apply(v, lo, hi, val);
      return;
    }
    this.pushDown(v, lo, hi);
    const mid = Math.floor((lo + hi) / 2);
    this.updateRange(2 * v, lo, mid, l, r, val);
    this.updateRange(2 * v + 1, mid + 1, hi, l, r, val);
    this.sum[v] = this.sum[2 * v] + this.sum[2 * v + 1];
  }

  private queryRange(v: number, lo: number, hi: number, l: number, r: number): number {
    if (r < lo || hi < l) return 0;
    if (l <= lo && hi <= r) return this.sum[v];
    this.pushDown(v, lo, hi);
    const mid = Math.floor((lo + hi) / 2);
    return this.queryRange(2 * v, lo, mid, l, r) + this.queryRange(2 * v + 1, mid + 1, hi, l, r);
  }

  rangeAdd(l: number, r: number, val: number): void {
    this.updateRange(1, 0, this.n - 1, l, r, val);
  }

  rangeSum(l: number, r: number): number {
    return this.queryRange(1, 0, this.n - 1, l, r);
  }
}
```

가장 중요한 부분은 `updateRange`와 `queryRange`의 이 두 줄입니다.

```ts
this.pushDown(v, lo, hi);   // ① 재귀로 내려가기 직전, 반드시 먼저
const mid = Math.floor((lo + hi) / 2);
```

이 순서를 지키지 않으면 — 즉 `pushDown` 없이 곧장 `this.updateRange(2*v, ...)`를 호출하면 — 자식의 `sum`이 예전 값 그대로인 채로 그 위에 또 다른 값을 쌓거나 조회하게 됩니다. `apply`에서 `lazy[v] += val`처럼 **누적**(대입이 아님)을 쓰는 것도 놓치기 쉬운 지점이에요. 같은 노드가 완전 포함으로 여러 번 `apply`될 수 있으므로(예: `rangeAdd`를 반복 호출), `lazy[v] = val`로 덮어쓰면 이전에 쌓인 몫이 사라집니다.

기억법: **"완전히 덮으면 지금 계산하고 다음으로 미루되, 내려갈 땐 미룬 것부터 갚는다."**

## 실행 시각화

`n = 4`, 초기 배열 `A = [1, 2, 3, 4]`로 만든 Lazy Segment Tree에서 `rangeAdd(1, 3, +5)` 후 `rangeSum(1, 3)`을 수행합니다. 각 노드 라벨은 담당 구간과 `sum`(필요 시 lazy 표시)입니다. `active`(빨강)는 현재 방문 중, `visited`(회색)는 완전 포함되어 즉시 처리된 노드, `frontier`(노랑)는 lazy 태그가 걸린 채 자식에게 아직 안 내려간 노드를 뜻합니다.

고정 입력 `A=[1,2,3,4]`에 `rangeAdd(1,3,5)`를 실행한 뒤 `rangeSum(1,3)`을 호출하면 실제 반환값은 `24`입니다(갱신 후 `A=[1,7,8,9]`의 `[1..3]` 합 `7+8+9=24`) — 아래 시뮬레이션 마지막 프레임과 일치합니다.

> 대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.

export const steps = [
  {
    title: "초기 트리",

정리하면, Lazy Segment Tree는 "완전히 덮이는 노드에서 즉시 계산하고 자식 전달은 미룬다"는 결정 하나로 구간 갱신을 $O(\log n)$까지 끌어내립니다. 미뤄 둔 몫은 `lazy` 배열에 정확히 기록되고, 그 자식이 실제로 필요해지는 순간(`pushDown`)에만 전달되므로 정확성이 조회 시점과 무관하게 유지돼요. 그 결과 `rangeAdd`와 `rangeSum` 모두 트리 높이에 비례하는 $O(\log n)$이 되어, 애초에 목표했던 $q \log n \approx 1.7 \times 10^6$ 수준의 처리량을 얻습니다.
