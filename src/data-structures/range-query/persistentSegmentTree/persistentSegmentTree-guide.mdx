# PersistentSegmentTree — 고치지 않고 이어붙여서 과거를 통째로 남기는 세그먼트 트리

## 한눈에 보는 컨셉

한 번 만든 노드는 절대 고치지 않고, 값이 바뀌는 경로만 새로 만들어 이어붙이는 세그먼트 트리예요. `update` 한 번에 딱 $O(\log n)$개의 새 노드만 생기고, 나머지 서브트리는 이전 버전과 포인터를 그대로 공유합니다. 그 덕분에 "버전 v 시점 기준으로 구간 $[l, r]$의 합은?" 같은 시간여행 질의를, 버전 하나당 $O(\log n)$의 추가 공간·$O(\log n)$ 시간만으로 답할 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 영속 세그먼트 트리를 떠올리세요.

- 질의에 "몇 번째 시점/버전/커밋 기준으로"라는 표현이 섞여 있다 — **시간여행 질의**
- 값이 계속 바뀌는데도 **과거 상태 전체를 버리지 않고** 나중에 다시 조회해야 한다
- 이력이 사슬(한 줄)이 아니라 **임의의 과거 시점에서 다시 갈라져 나갈 수 있다**(브랜치·분기)

이 세 가지가 없다면 굳이 영속성을 들고 올 필요가 없습니다. "가장 최근 상태만" 필요하면 일반 세그먼트 트리로 충분하고, "변경 로그만 있으면 되고 임의 시점 트리 자체에 질의할 필요는 없다"면 단순히 변경 이력을 배열에 쌓아두는 것으로 족해요. 반대로 "특정 시점의 구조 자체에 대고 질의(합, 최솟값, K번째 값 등)"를 해야 한다면 영속 자료구조가 필요합니다.

naive하게 "버전마다 배열을 통째로 복사해서 보관"하는 방법과 비교하면 차이가 분명해집니다.

```text
버전 수를 v, 배열 크기를 n이라 할 때

방법                         버전당 추가 공간   업데이트 비용   과거 버전 접근
전체 배열 복사                O(n)              O(n)           O(1) (배열 인덱싱)
영속 세그먼트 트리(경로 복사)  O(log n)          O(log n)       O(1) (루트 포인터)

업데이트가 1000번 쌓인 n=10^4 배열이라면:
전체 복사   → 1000 × 10^4 = 10^7개의 원소를 들고 있어야 함
경로 복사   → 1000 × log2(10^4) ≈ 1000 × 14 = 14,000개의 노드만 추가
```

n이 커질수록, 그리고 버전이 늘어날수록 이 차이는 기하급수적으로 벌어집니다.

### 문제 사례와 적용 예시

- **버전 관리 시스템의 통계 질의**: Git처럼 수천 개의 커밋이 있고, "3번 커밋 기준 파일 [0..10]의 총 크기는?" 같은 질의가 초당 수천 번 들어오는 경우.
- **코딩 테스트의 시간여행 쿼리**: "배열이 시점마다 바뀌는데, 특정 시점의 구간 [l,r] 안에서 K번째로 작은 값은?" — 값의 개수를 세는 영속 세그먼트 트리(persistent segment tree of counts)로 처리하는 대표 유형입니다.
- **에디터의 undo/redo + 부분 통계**: 문서를 되돌릴 수 있어야 하는 동시에, "되돌린 시점의 특정 구간 글자 수 합"처럼 부분 통계도 함께 물어야 하는 경우.
- **불변(immutable) 함수형 자료구조**: Clojure의 persistent vector처럼, "수정"이 사실은 "약간만 다른 새 버전을 만들고 나머지는 공유"로 구현되는 설계 패턴의 세그먼트 트리 버전입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드에서 정의하는 인터페이스는 이렇습니다.

```ts
interface SegNode {
  sum: number;                  // 이 노드가 담당하는 구간의 합
  left: SegNode | null;         // 왼쪽 자식 (리프면 null)
  right: SegNode | null;        // 오른쪽 자식 (리프면 null)
}

class PersistentSegmentTree {
  private roots: (SegNode | null)[];  // roots[v] = 버전 v의 루트 포인터
  private n: number;                  // 배열 크기 (모든 버전 공통, 불변)
}
```

`lo === hi`이면서 `left`와 `right`가 둘 다 `null`인 노드가 리프입니다. 지켜야 할 불변식은 네 가지예요.

1. **구조적 불변(persistence).** 한 번 생성된 `SegNode` 객체는 `sum`도 `left`/`right` 포인터도 **절대로 다시 대입되지 않습니다.** 바뀐 값이 필요하면 반드시 새 객체를 만듭니다.
2. **구간 합 정확성.** 구간 $[lo, hi]$를 담당하는 버전 $v$의 노드는 그 시점 배열 $A_v$에 대해 다음을 만족합니다.

$$
\text{node}_{v}[lo, hi].\text{sum} = \sum_{k=lo}^{hi} A_v[k]
$$

3. **분할 경계는 버전 독립적.** $n$이 모든 버전에서 동일하므로, 각 노드가 담당하는 $(lo, hi)$와 분할점 $mid = \lfloor (lo+hi)/2 \rfloor$은 버전과 무관하게 항상 같습니다. 버전이 달라져도 바뀌는 건 오직 리프 값과 그 조상들의 `sum`뿐입니다.
4. **버전 그래프는 사슬이 아니라 트리(DAG).** `update(version, i, val)`은 `version`으로 지정된 **임의의 과거 버전**을 기반으로 새 버전을 만듭니다. 그래서 버전들은 일렬로 이어지는 체인이 아니라, 어느 시점에서든 다시 갈라질 수 있는 트리 구조를 이룹니다.

`arr = [1, 2, 3, 4]`로 버전 0을 만들고 `update(0, i=1, val=20)`을 실행하면 이렇게 됩니다.

```text
roots[0] ──▶ [sum=10]                arr = [1, 2, 3, 4]
              /      \
        [sum=3]      [sum=7]
          /  \          /  \
        [1]  [2]      [3]  [4]

update(0, i=1, val=20) 이후:

roots[1] ──▶ [sum=28]  ← 새 노드
              /      \
       [sum=21]      [sum=7] ─────────┐
   (새 노드)  \                       │
             [1]  [20]                │  버전0의 [sum=7] 서브트리를
        (공유)  (새 노드)              │  포인터만 그대로 재사용(공유)
                                       └─▶ (버전0과 동일 객체)

roots[0]은 여전히 최초의 [sum=10] 트리를 가리킨다 — 아무 노드도 바뀌지 않았다.
새로 생성된 노드: [sum=28], [sum=21], [20] → 딱 3개 = 트리 높이만큼(O(log n))
```

**액션(연산)** — 이 가이드가 다루는 4종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(arr)` | 초기 배열로 버전 0 구성 | $O(n)$ |
| `update(version, i, val)` | `version` 기반, 인덱스 `i`를 `val`로 바꾼 새 버전 생성. 새 버전 번호 반환 | $O(\log n)$ |
| `query(version, l, r)` | 버전 `version`의 구간 $[l, r]$ 합 반환 | $O(\log n)$ |
| `versionCount()` | 현재 총 버전 수 반환 | $O(1)$ |

핵심 연산 두 개를 자세히 볼게요.

**① `update` — 경로 복사(path copying).** 위 그림처럼, 루트에서 대상 리프까지의 경로에 있는 노드만 새로 만들고, 그 경로에서 벗어난 형제 서브트리는 **참조만 재사용**합니다. 경로 길이가 트리 높이 $h = \lceil \log_2 n \rceil + 1$이므로, 새로 생기는 노드 수는 정확히 $h$개예요.

**② `query` — 조기 가지치기(pruning) + 완전 커버 단축.** `arr = [10, 20, 30, 40, 50, 60, 70]`에서 `query(0, 3, 5)`를 실행하면:

```text
                         [0,6] sum=280
                        /            \
                 [0,3] sum=100      [4,6] sum=180
                 /         \          /        \
          [0,1] sum=30  [2,3] sum=70 [4,5] sum=110 [6,6] sum=70
          (l=3>hi=1        /    \      (l<=lo && hi<=r  (r=5<lo=6
           → 가지치기)  [2,2]  [3,3]     → 완전 커버!     → 가지치기)
                        (가지침) sum=40   재귀 없이 즉시    
                                (완전커버) 110 반환)

방문한 리프는 [3,3]=40 하나뿐. [4,5]는 리프 두 개(50,60)를 갖고 있지만
"질의 구간이 이 노드를 통째로 덮는다" 조건(l<=lo && hi<=r)을 만족해서
sum=110을 그대로 반환하고 더 내려가지 않습니다.

결과: 40 + 110 = 150 (= 40+50+60, 실제 실행값과 일치)
```

이 "완전 커버 단축"이 있어서 세그먼트 트리는 구간의 크기와 무관하게 $O(\log n)$에 끝납니다 — 리프를 하나씩 다 들르지 않습니다.

### 왜 모순 없이 작동하는가

**불변식 보존을 귀납으로 봅니다.** 기저(버전 0): `build`는 리프에서 시작해 부모의 `sum`을 자식 합으로 채워 올라가므로, 완성된 트리는 처음부터 불변식 2를 만족합니다. 귀납 단계: 어떤 버전이 불변식 2를 만족한다고 가정하면, `update`가 만드는 새 버전은 (a) 변경 경로 밖의 노드는 옛 버전과 **완전히 동일한 객체**이므로 그대로 불변식을 만족하고, (b) 경로 위의 새 노드는 `sum = newLeft.sum + oldRight.sum`(또는 그 대칭)처럼 **자식의 최신 sum을 그대로 재계산**하므로 새 버전에서도 불변식 2가 성립합니다. 그리고 불변식 1(구조적 불변) 덕분에, 옛 버전의 `roots[v]`가 가리키는 객체들은 이후 어떤 `update`가 일어나도 절대 값이 바뀌지 않습니다 — 그래서 `roots[0]`은 영원히 처음 만든 그 트리를 가리킵니다.

여기서 헷갈리기 쉬운 포인트 세 가지를 짚어 둘게요.

- **`update`가 항상 "가장 최근 버전"을 기반으로 한다고 착각하기 쉽습니다.** 실제로는 `update(version, i, val)`의 `version`으로 **임의의 과거 버전**을 지정할 수 있습니다. 예를 들어 `v1 = update(0, 2, 100)`으로 버전 1을 만든 뒤, 다시 `vA = update(0, 4, 99)`처럼 **버전 0에서 새로 분기**할 수 있어요. 이때 `query(vA, 3, 4)`와 `query(v1, 3, 4)`는 서로 완전히 독립된 값(각각 103과 9)을 냅니다 — v1을 건드리지 않고 버전 0에서 갈라져 나간 것이니까요. 버전은 사슬이 아니라 나무입니다.
- **공유된 서브트리를 실수로 "제자리 수정"하면 과거 버전까지 오염됩니다.** 만약 `updateNode`가 새 리프를 만드는 대신 `node.sum = val`처럼 기존 리프 객체를 직접 고치고 그 객체를 그대로 반환한다고 해봅시다. `arr=[1,2,3,4]`에서 이렇게 구현하고 `update(0, 1, 20)`을 실행하면, 실측 결과 `query(0, 0, 3)`이 버전 0인데도 원래 값 10이 아니라 **28**을 반환합니다 — update 이전 시점을 물었는데 update 이후 값이 나온 거예요. 영속성이 완전히 깨진 것이고, 원인은 "새 노드를 만들지 않고 기존 노드를 고쳤다"는 단 한 줄의 실수입니다.
- **분기 조건의 경계(`i <= mid`)를 `i < mid`로 잘못 쓰면 엉뚱한 리프가 바뀝니다.** `arr=[1,2,3,4]`에서 `mid=(0+3)>>1=1`인데, 조건을 `i < mid`로 쓰면 `update(0, i=1, val=20)`이 "왼쪽(인덱스 0~1)"이 아니라 "오른쪽(인덱스 2~3)"으로 잘못 내려갑니다. 실제로 이렇게 구현해 실행해 보면, 인덱스 1이 아니라 **인덱스 2의 값(3)이 20으로 덮어써져서** 새 버전의 합이 정답 28이 아니라 **27**이 나옵니다. 경계 하나 차이로 완전히 다른 원소가 바뀌는 셈입니다.

잠깐 확인 하나만 해볼까요? `arr = [5]`처럼 크기 1인 배열에서 `update(0, 0, -3)`을 하면 새로 생기는 노드는 몇 개일까요? — 트리 높이가 1(루트 자체가 리프)이므로 딱 **1개**입니다. 루트=리프이니 경로 길이가 곧 1이에요.

엣지 케이스를 점검해 둡니다.

```text
크기 1 배열              → 루트가 곧 리프. update는 새 리프 1개만 생성
같은 인덱스를 두 번 갱신   → 매번 새 버전이 늘어남 (덮어쓰지 않고 계속 분기)
질의 구간이 배열 전체     → 루트에서 완전 커버로 즉시 종료 (O(1)에 가까움)
l == r (점 질의)         → 리프까지 내려가는 일반 질의와 동일하게 동작
버전 0에서 여러 번 분기   → 각 분기는 서로 독립, versionCount()만 계속 증가
```

## 아이디어를 코드로 옮기기

가장 먼저 naive한 원형을 봅니다. "과거 버전을 보존한다"는 요구사항만 보면 제일 단순한 구현은 매 버전마다 배열을 통째로 복사하는 것입니다.

```ts
// 원형: 버전마다 배열 전체를 복사
const versions: number[][] = [initialArr.slice()];

function naiveUpdate(version: number, i: number, val: number): number {
  const newArr = versions[version]!.slice(); // O(n) 복사
  newArr[i] = val;
  versions.push(newArr);
  return versions.length - 1;
}
```

`n=10^4`에 업데이트가 1000번이면 `1000 × 10^4`개의 숫자를 들고 있어야 합니다. 여기서 돌파구는 "세그먼트 트리에서 인덱스 하나를 바꿀 때, 실제로 값이 달라지는 노드는 루트에서 리프까지의 경로 $O(\log n)$개뿐"이라는 관찰이에요. 나머지는 이전 버전과 동일하니, **바뀐 경로만 새로 만들고 나머지는 포인터로 공유**하면 됩니다. 이 관찰을 코드로 옮기면 이렇게 개선됩니다.

```ts
// 개선: 경로 복사 — 바뀐 노드만 새로 만들고 나머지는 참조 공유
function updateNodeV2(node: SegNode, lo: number, hi: number, i: number, val: number): SegNode {
  if (lo === hi) return { sum: val, left: null, right: null }; // 새 리프
  const mid = (lo + hi) >> 1;
  if (i <= mid) {
    const newLeft = updateNodeV2(node.left!, lo, mid, i, val);
    return { sum: newLeft.sum + node.right!.sum, left: newLeft, right: node.right }; // right는 공유
  } else {
    const newRight = updateNodeV2(node.right!, mid + 1, hi, i, val);
    return { sum: node.left!.sum + newRight.sum, left: node.left, right: newRight }; // left는 공유
  }
}
```

이 조각만으로는 아직 "버전 몇 번을 기준으로 시작하는가", "버전 번호를 어떻게 매기는가"가 빠져 있습니다. 최종 구현에서 `roots` 배열과 `build`/`query`까지 묶어 완성합니다.

```ts
interface SegNode {
  sum: number;
  left: SegNode | null;
  right: SegNode | null;
}

class PersistentSegmentTree {
  private roots: (SegNode | null)[] = [];
  private n: number;

  constructor(arr: number[]) {
    this.n = arr.length;
    this.roots.push(this.build(arr, 0, this.n - 1));
  }

  private build(arr: number[], lo: number, hi: number): SegNode {
    if (lo === hi) return { sum: arr[lo]!, left: null, right: null };
    const mid = (lo + hi) >> 1;
    const left = this.build(arr, lo, mid);
    const right = this.build(arr, mid + 1, hi);
    return { sum: left.sum + right.sum, left, right };
  }

  private updateNode(node: SegNode, lo: number, hi: number, i: number, val: number): SegNode {
    if (lo === hi) return { sum: val, left: null, right: null };
    const mid = (lo + hi) >> 1;
    if (i <= mid) {
      const newLeft = this.updateNode(node.left!, lo, mid, i, val);
      return { sum: newLeft.sum + node.right!.sum, left: newLeft, right: node.right };
    } else {
      const newRight = this.updateNode(node.right!, mid + 1, hi, i, val);
      return { sum: node.left!.sum + newRight.sum, left: node.left, right: newRight };
    }
  }

  update(version: number, i: number, val: number): number {
    const root = this.roots[version]!;
    const newRoot = this.updateNode(root, 0, this.n - 1, i, val);
    this.roots.push(newRoot);
    return this.roots.length - 1;
  }

  private queryNode(node: SegNode | null, lo: number, hi: number, l: number, r: number): number {
    if (node === null || l > hi || r < lo) return 0;
    if (l <= lo && hi <= r) return node.sum;
    const mid = (lo + hi) >> 1;
    return this.queryNode(node.left, lo, mid, l, r) + this.queryNode(node.right, mid + 1, hi, l, r);
  }

  query(version: number, l: number, r: number): number {
    return this.queryNode(this.roots[version]!, 0, this.n - 1, l, r);
  }

  versionCount(): number {
    return this.roots.length;
  }
}
```

가장 중요한 부분은 `updateNode`의 두 분기에서 **경로 밖 자식을 새로 만들지 않고 그대로 참조하는 자리**입니다.

- `return { sum: ..., left: newLeft, right: node.right }` — 여기서 `node.right`는 **새로 만든 객체가 아니라 이전 버전의 바로 그 객체**입니다. 이 한 줄이 "공유"의 전부예요. 실수로 `{ ...node.right }`처럼 복제하면 공간 이점이 사라지고, 반대로 `node.right.sum = ...`처럼 고치면 과거 버전이 오염됩니다.
- `if (i <= mid)` — 등호를 빠뜨리면(=`i < mid`) 경계 인덱스가 반대쪽으로 새어나가 엉뚱한 리프가 바뀝니다(앞서 27 vs 28로 확인한 그 버그).
- `if (l <= lo && hi <= r) return node.sum;` — "질의 구간이 이 노드를 완전히 덮는다"는 조건입니다. 이 줄이 있어야 리프까지 내려가지 않고 조기 반환할 수 있어요.

> 기억법: "바뀌는 길만 새로 깔고, 나머지 길은 이정표만 빌려 쓴다."

정리하면, 영속 세그먼트 트리는 "한 번 만든 노드는 절대 고치지 않는다"는 원칙 하나로 두 가지를 동시에 얻습니다. `update`는 루트에서 리프까지의 경로 $O(\log n)$개만 새로 만들고 나머지는 이전 버전과 공유하니 **버전당 추가 공간이 $O(\log n)$**이고, `roots[v]`가 가리키는 트리는 이후 어떤 업데이트가 일어나도 변하지 않으니 **과거 버전 조회가 항상 $O(1)$ 포인터 접근 + $O(\log n)$ 질의**로 끝납니다. `update`가 어느 버전이든 기반으로 삼을 수 있다는 점 덕분에 버전들은 사슬이 아니라 자유롭게 갈라지는 트리를 이루고, 이 자유도가 "임의 시점에서 분기해 시뮬레이션해 본다"는 활용까지 가능하게 합니다.
