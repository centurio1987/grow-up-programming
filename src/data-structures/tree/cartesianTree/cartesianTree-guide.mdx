# CartesianTree — 인덱스는 BST, 값은 힙, 두 얼굴을 한 몸에

## 한눈에 보는 컨셉

배열 하나를 두고 "인덱스 순서로는 BST, 값 크기로는 힙"이라는 두 규칙을 동시에 만족시키는 트리예요. 비결은 왼쪽부터 하나씩 넣으면서 **항상 오른쪽 경계(오른쪽 스파인)에만 삽입 위치를 정한다**는 관찰 하나입니다. 이 관찰 덕분에 naive하게 매번 최솟값을 찾는 $O(n^2)$ 대신, 스택 하나로 전체를 $O(n)$에 구성할 수 있어요. Range Minimum Query(RMQ) 전처리와 Treap의 뼈대가 되는 자료구조입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 카르테시안 트리를 떠올리세요.

- "구간 $[l, r]$의 최솟값(또는 최댓값)을 여러 번 물어본다" — RMQ(Range Minimum Query) 신호
- "배열 하나로 트리를 만드는데, 그 트리가 인덱스 순서(BST)와 값 크기(힙)를 동시에 지켜야 한다"
- "배열은 고정이고(삽입·삭제 없이), 질의만 반복된다" — 정적 배열 + 반복 질의 조합

RMQ 관점에서 접근법별 비용을 비교하면 이렇습니다($n$번 전처리 후 $q$번 질의).

```text
매번 구간 스캔(naive)      전처리 O(1),        질의 O(n)     → 총 O(qn)
Sparse Table               전처리 O(n log n),  질의 O(1)     → 총 O(n log n + q)
카르테시안 트리 + LCA        전처리 O(n),        질의 O(1)*    → 총 O(n + q)
                              (*LCA를 O(1)에 답하려면 오일러 투어 + Sparse Table을
                               트리 위에 한 번 더 얹어야 합니다. 그래도 트리 구성
                               자체는 O(n)이라 "구간 질의를 트리 문제로 바꾸는" 전처리
                               비용이 가장 쌉니다.)
```

선택 기준은 이렇습니다: 배열이 계속 삽입·삭제된다면 카르테시안 트리 대신 세그먼트 트리가 낫습니다(카르테시안 트리는 배열이 바뀔 때마다 재구성해야 함). 배열이 고정이고 질의만 반복된다면 카르테시안 트리(+LCA) 또는 Sparse Table이 유리합니다. 노드마다 무작위 우선순위를 힙 키로 쓰는 변형은 **Treap**이라 부르며, 삽입·삭제가 잦은 상황에서 self-balancing BST로 씁니다.

### 문제 사례와 적용 예시

- **RMQ 전처리**: 배열에서 카르테시안 트리를 구성해두면, 구간 $[l, r]$의 최솟값은 정확히 인덱스 $l$과 $r$에 해당하는 두 리프의 LCA(최소 공통 조상)입니다.
- **Treap**: 노드마다 무작위 우선순위를 부여해 힙 키로 쓰면, 삽입 순서에 무관하게 기대 높이 $O(\log n)$의 self-balancing BST가 됩니다 — 함수형 자료구조나 정렬 인덱스 구현에 쓰입니다.
- **단조 스택(monotonic stack) 계열 문제와의 근친성**: "히스토그램에서 최대 직사각형" 같은 문제에서 쓰는 단조 스택이, 카르테시안 트리를 구성하는 스택 로직과 본질적으로 같은 패턴입니다.
- **코딩 테스트 맥락**: "수백만 개의 센서 데이터에서 구간 최솟값을 반복 조회해야 하는 모니터링 시스템" — 정적 배열 + 반복 구간 질의라는 조합이 나오면 카르테시안 트리 전처리를 의심해 보세요.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드 하나는 이렇게 생겼습니다.

```ts
class CartesianNode<T> {
  value: T;
  left: CartesianNode<T> | undefined = undefined;
  right: CartesianNode<T> | undefined = undefined;
  size = 1; // 자신을 포함한 서브트리의 노드 수
}
```

트리 전체는 `root`와 비교자 `cmp`를 들고 있습니다. `cmp(a, b) < 0`이면 `a`가 부모 후보(기본값은 min-heap 기준, 즉 작은 값이 위로).

지켜야 할 불변식은 네 가지입니다.

1. **BST 성질(인덱스 기준)**: 중위 순회(inorder) 결과가 원래 배열 순서와 정확히 같습니다.
   $$\text{inorder}(T) = [\,arr[0],\ arr[1],\ \dots,\ arr[n-1]\,]$$
2. **힙 성질(값 기준)**: 루트가 아닌 모든 노드 $x$에 대해 부모의 값이 자식의 값보다 앞섭니다.
   $$\forall x \ne \text{root},\quad \text{cmp}(\text{value}(\text{parent}(x)),\ \text{value}(x)) \le 0$$
3. **동률 처리 규칙**: `cmp(a, b) === 0`인 두 값 중 배열에서 **먼저 나온 값이 항상 나중 값의 조상**(더 위)에 위치합니다.
4. **유일성**: 위 세 규칙을 고정하면, 같은 배열 + 같은 비교자에 대해 트리는 유일하게 결정됩니다.

배열 `[5, 10, 40, 10, 20]`(min-heap)을 실제로 구성하면 이런 모양이 나옵니다(직접 실행해 확인한 결과입니다 — 뒤의 "아이디어를 코드로 옮기기"에서 같은 코드로 재현합니다).

```text
        5
         \
          10ᵃ        ← 인덱스 1의 10
            \
             10ᵇ      ← 인덱스 3의 10 (10ᵃ보다 나중에 들어와 그 아래로)
            /   \
          40     20
```

`value()`는 `5`, `inOrder()`는 `[5, 10, 40, 10, 20]`(원배열 그대로), `size()`는 `5`를 반환합니다. `10ᵃ`가 `10ᵇ`의 조상인 것이 불변식 3(동률 처리 규칙)의 실물입니다.

**액션(연산)** — 이 가이드가 정의하는 인터페이스 6개입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `fromArray(arr, cmp?)` | 배열에서 스택 기반으로 트리 구성(정적 메서드) | $O(n)$ |
| `value()` | 루트 값 (빈 트리면 `undefined`) | $O(1)$ |
| `left()` | 왼쪽 서브트리(`CartesianTree`로 래핑) | $O(1)$ |
| `right()` | 오른쪽 서브트리 | $O(1)$ |
| `inOrder()` | 중위 순회 = 원배열 복원 | $O(n)$ |
| `size()` | 전체 노드 수 | $O(1)$ |

핵심 연산은 단연 `fromArray`입니다. 두 번째 `10`(인덱스 3)을 처리하는 순간을 before/after로 자세히 보겠습니다.

```text
Before — v=10(인덱스 3) 처리 직전
스택(바닥→탑): [5, 10ᵃ, 40]

① cmp(10, 40) < 0 → 참 → 40을 팝. last = 40
② 스택 탑은 이제 10ᵃ. cmp(10, 10ᵃ) < 0 → 거짓(동률은 팝하지 않는다) → 중단

After
스택(바닥→탑): [5, 10ᵃ, 10ᵇ]
10ᵇ.left = 40        (마지막으로 팝된 노드)
10ᵃ.right = 10ᵇ      (스택에 남은 탑의 오른쪽 자식으로 연결)
```

### 왜 모순 없이 작동하는가

**스택 불변식부터 정의합니다.** 배열 앞부분 $arr[0..i-1]$까지 처리한 시점에서, 스택 $[s_1, s_2, \dots, s_k]$(바닥→탑)은 정확히 지금까지 만들어진 트리의 **오른쪽 경로(오른쪽 스파인)**이고, $s_1$이 루트이며 $s_{j+1} = s_j.\text{right}$이고 $\text{value}(s_1) \le \text{value}(s_2) \le \cdots \le \text{value}(s_k)$입니다.

이 불변식이 처음(빈 배열, 빈 스택)에 성립하는 건 자명합니다. 이제 $v = arr[i]$를 처리하며 이 불변식이 그대로 유지됨을 봅니다.

- **BST 성질 보존**: $v$는 지금까지 나온 어떤 원소보다도 배열 인덱스가 큽니다(가장 마지막에 추가됨). 그러니 $v$가 삽입될 수 있는 자리는 "지금까지 만들어진 트리에서 인덱스가 가장 큰 경로", 즉 오른쪽 스파인뿐입니다. 그 경로가 정확히 스택이므로, 스택만 보고 삽입 위치를 결정해도 BST 성질이 깨지지 않습니다.
- **힙 성질 보존**: pop 조건이 `cmp(v, top) < 0`이므로, 루프가 멈춘 시점의 스택 탑(있다면)은 `cmp(v, top) < 0`이 거짓, 즉 $\text{value}(\text{top}) \le v$입니다. 새 노드는 이 `top`의 오른쪽 자식이 되므로 부모(`top`) $\le$ 자식($v$)이 그대로 성립합니다. 한편 팝된 노드들은 전부 $v$보다 큰 값이었으므로($cmp(v, \cdot) < 0$을 만족해서 팝됨), $v \le$ (팝된 노드들)도 성립합니다 — 팝된 마지막 노드가 $v$의 왼쪽 자식이 되어도 부모($v$) $\le$ 자식(팝된 노드) 관계가 유지됩니다.
- **유일성**: 루트는 항상 배열 전체의 최솟값(동률이면 가장 왼쪽 인덱스)으로 결정됩니다. 루트가 정해지면 왼쪽 부분 배열과 오른쪽 부분 배열이 각각 독립적으로 같은 규칙을 재귀적으로 적용받으므로, 귀납적으로 트리 전체가 유일하게 결정됩니다.

잠깐, 확인 하나만 해볼까요? 배열이 `[3, 1, 2]`라면 루트는 무엇일까요? 최솟값은 `1`(인덱스 1)이니 `1`이 루트이고, 왼쪽 부분 배열 `[3]`이 왼쪽 서브트리, 오른쪽 부분 배열 `[2]`가 오른쪽 서브트리가 됩니다.

**여기서 헷갈리기 쉬운 포인트는 "pop 조건에 등호를 넣어도 되지 않을까"라는 생각입니다.** 실제로 `cmp(v, top) < 0`을 `cmp(v, top) <= 0`으로 바꾸면(등호 추가), 동률인 원소까지 팝해 버려 트리 모양이 달라집니다. 배열 `[10, 5, 5, 20]`로 확인해 봅시다.

```text
올바른 구현(< , 동률은 안 팝음):
  value() = 5,  right()?.value() = 5,   right()?.right()?.value() = 20
  (첫 번째 5가 두 번째 5의 조상 — 불변식 3대로)

`<=` 버그 버전(동률도 팝함):
  value() = 5,  right()?.value() = 20,  right()?.right()?.value() = undefined
  (두 번째 5가 오히려 새 루트가 되고, 첫 번째 5는 그 왼쪽 아래로 밀려납니다.
   inOrder()는 우연히 [10, 5, 5, 20]로 똑같이 나오지만, right() 체인을 타고
   내려가는 구조 자체가 달라져 있습니다 — 값만 보고는 눈치채기 어려운 함정입니다.)
```

엣지 케이스도 점검해 둡니다.

```text
빈 배열               → value()=undefined, size()=0, inOrder()=[], left()=undefined
원소 1개 [7]           → value()=7, size()=1, left()/right() 모두 undefined
오름차순 [1,2,3,4,5]    → 완전히 오른쪽으로 치우친 사슬(모든 left===undefined),
                         inOrder()는 그대로 [1,2,3,4,5]
내림차순 [5,4,3,2,1]    → 완전히 왼쪽으로 치우친 사슬(모든 right===undefined),
                         value()=1(마지막 원소가 루트), inOrder()는 그대로 [5,4,3,2,1]
완전 동률 [3,3,3]       → inOrder()=[3,3,3], 먼저 들어온 3이 조상, 오른쪽으로 사슬
```

## 아이디어를 코드로 옮기기

**원형 — naive 재귀, $O(n^2)$.** 정의를 그대로 옮기면 이렇습니다: 최솟값을 찾아 루트로 삼고, 그 왼쪽·오른쪽 부분 배열로 재귀합니다.

```ts
function buildNaive<T>(arr: T[], cmp: Cmp<T>): CartesianNode<T> | undefined {
  if (arr.length === 0) return undefined;
  let minIdx = 0;
  for (let i = 1; i < arr.length; i++) {
    if (cmp(arr[i]!, arr[minIdx]!) < 0) minIdx = i;
  }
  const node = new CartesianNode(arr[minIdx]!);
  node.left = buildNaive(arr.slice(0, minIdx), cmp);
  node.right = buildNaive(arr.slice(minIdx + 1), cmp);
  return node;
}
```

이미 정렬된 배열을 넣으면 매번 맨 앞이 최솟값이라, 최솟값 탐색 $O(n)$을 $n$번 반복 — $O(n^2)$입니다. 여기서 낭비되는 지점은 "매번 처음부터 최솟값을 다시 찾는다"는 것입니다.

**개선 — 오른쪽 스파인을 직접 타고 내려가며 삽입, 여전히 $O(n^2)$.** "왜 모순 없이 작동하는가"에서 본 관찰(새 원소는 항상 오른쪽 스파인에만 들어간다)을 그대로 코드로 옮기면, 매번 루트부터 오른쪽 스파인을 걸어 내려가며 삽입 위치를 찾을 수 있습니다.

```ts
function insertViaSpineWalk<T>(
  root: CartesianNode<T> | undefined,
  value: T,
  cmp: Cmp<T>,
): CartesianNode<T> {
  const node = new CartesianNode(value);
  if (root === undefined) return node;

  if (cmp(value, root.value) < 0) {
    // 새 값이 루트보다 작다 → 새 값이 새 루트, 기존 트리 전체가 왼쪽 자식
    node.left = root;
    return node;
  }

  // 오른쪽 스파인을 타고 내려가며, "이 아래는 전부 새 값보다 크다"인 지점을 찾는다
  let cur = root;
  while (cur.right !== undefined && cmp(value, cur.right.value) >= 0) {
    cur = cur.right;
  }
  node.left = cur.right; // cur.right 아래 서브트리는 전부 새 값보다 큼 → 새 노드의 왼쪽으로
  cur.right = node;
  return root;
}
```

관찰 자체는 옳아서 최종 결과는 스택 버전과 완전히 같습니다(실행해 확인했습니다). 하지만 매 삽입마다 **루트부터 다시 걸어 내려가므로** 스파인 길이에 비례하는 $O(n)$이 걸리고, $n$번 반복하면 $O(n^2)$입니다. 여기서 다음 단계로 가는 이유는 명확합니다: 직전 삽입이 스파인의 어디서 끝났는지 우리는 이미 알고 있는데, 매번 루트부터 다시 찾는 건 낭비입니다.

**최종 — 스택으로 위치를 기억, $O(n)$ 상각.** 스택이 정확히 "지금 오른쪽 스파인"을 들고 있게 하면, 각 원소는 스택에 최대 한 번 push되고 최대 한 번 pop됩니다. 전체 push/pop 횟수가 $O(n)$이니, 반복문 안의 while이 가끔 여러 번 도는 것까지 합쳐도 총합은 $O(n)$입니다(각 원소가 자기 자신 딱 한 번만 pop될 수 있으므로).

```ts
type Cmp<T> = (a: T, b: T) => number;

class CartesianNode<T> {
  value: T;
  left: CartesianNode<T> | undefined = undefined;
  right: CartesianNode<T> | undefined = undefined;
  size = 1;

  constructor(value: T) {
    this.value = value;
  }
}

function subtreeSize<T>(node: CartesianNode<T> | undefined): number {
  return node === undefined ? 0 : node.size;
}

function computeSizes<T>(node: CartesianNode<T> | undefined): number {
  if (node === undefined) return 0;
  node.size = computeSizes(node.left) + computeSizes(node.right) + 1;
  return node.size;
}

class CartesianTree<T> {
  private constructor(
    private readonly root: CartesianNode<T> | undefined,
    private readonly cmp: Cmp<T>,
  ) {}

  static fromArray<T>(
    arr: T[],
    cmp: Cmp<T> = (a, b) => (a < b ? -1 : a > b ? 1 : 0),
  ): CartesianTree<T> {
    const stack: CartesianNode<T>[] = [];

    for (const v of arr) {
      const node = new CartesianNode(v);
      let last: CartesianNode<T> | undefined;

      // 새 값보다 "작지 않은(>=)" 스택 탑을 팝 — 마지막으로 팝된 노드가 새 노드의 왼쪽 자식
      while (stack.length > 0 && cmp(v, stack[stack.length - 1]!.value) < 0) {
        last = stack.pop();
      }
      node.left = last;

      if (stack.length > 0) {
        stack[stack.length - 1]!.right = node;
      }

      stack.push(node);
    }

    const root = stack.length > 0 ? stack[0] : undefined;
    computeSizes(root); // 트리가 완성된 뒤 한 번의 후위 순회로 size를 채운다 — O(n)
    return new CartesianTree(root, cmp);
  }

  private static wrap<T>(
    node: CartesianNode<T> | undefined,
    cmp: Cmp<T>,
  ): CartesianTree<T> | undefined {
    return node === undefined ? undefined : new CartesianTree(node, cmp);
  }

  value(): T | undefined {
    return this.root?.value;
  }

  left(): CartesianTree<T> | undefined {
    return CartesianTree.wrap(this.root?.left, this.cmp);
  }

  right(): CartesianTree<T> | undefined {
    return CartesianTree.wrap(this.root?.right, this.cmp);
  }

  size(): number {
    return subtreeSize(this.root);
  }

  inOrder(): T[] {
    const out: T[] = [];
    const visit = (node: CartesianNode<T> | undefined): void => {
      if (node === undefined) return;
      visit(node.left);
      out.push(node.value);
      visit(node.right);
    };
    visit(this.root);
    return out;
  }
}
```

**가장 중요한 부분은 while 루프 다음 두 줄의 순서입니다.**

```ts
node.left = last;                              // ①
if (stack.length > 0) {
  stack[stack.length - 1]!.right = node;       // ②
}
```

②는 반드시 while 루프(pop)가 **끝난 뒤**의 스택 탑을 봐야 합니다. 만약 pop 루프보다 **먼저** `stack.top.right = node`를 실행해 버리면, 아직 팝되지 않은(곧 사라질) 옛 탑에 연결해 버립니다. `[5, 10, 40, 10, 20]`의 두 번째 `10`을 처리할 때로 확인해 보면: pop 전에 `40.right = node`를 먼저 실행하고, 이어서 `40`이 팝되어 `node.left = 40`이 되면 — `40.right`와 `node.left`가 서로를 가리키는 **사이클**이 생겨 버립니다. 실제로 이 순서로 짜서 `inOrder()`를 돌려보면 재귀가 끝나지 않고 스택 오버플로우가 납니다(직접 실행해 확인했습니다).

놓치기 쉬운 지점을 몇 개 더 짚습니다.

- **pop 조건은 반드시 엄격한 `<`.** `<=`로 바꾸면 앞서 본 것처럼 동률 처리 규칙(불변식 3)이 깨집니다.
- **`last`는 "마지막으로 팝된 노드"이지 "첫 번째로 팝된 노드"가 아닙니다.** while 루프가 여러 번 돌면 `last`는 계속 갱신되어, 루프가 끝났을 때는 가장 마지막에 팝된(= 스택에서 가장 아래 있던, 즉 서브트리 관점에서 가장 위에 있던) 노드가 남습니다. 이 노드가 지금까지 팝된 전체 서브트리의 루트입니다.
- **size 계산은 트리가 완성된 뒤 한 번의 후위 순회로.** 삽입 도중에 매번 조상들의 size를 갱신하려 들면 어떤 조상까지 갱신해야 하는지 추적이 번거롭습니다. 스택 알고리즘이 끝난 뒤 루트에서 한 번의 후위 순회(`computeSizes`)로 계산하는 편이 훨씬 단순하고 여전히 $O(n)$입니다.

기억법 한 줄로 정리하면 이렇습니다.

> 오른쪽으로 계속 자라던 가지 중, 나보다 무거운(큰) 놈들은 팝해서 내 왼쪽 밑에 깔고, 남은 놈의 오른쪽에 내가 올라선다.

정리하면, 카르테시안 트리는 "새 원소는 항상 오른쪽 스파인에만 들어간다"는 관찰 하나로 두 가지 성질(BST + 힙)을 동시에 $O(n)$에 지켜냅니다. 스택이 오른쪽 스파인을 그대로 담고 있다는 사실 덕분에, naive $O(n^2)$의 "매번 최솟값을 다시 찾는" 낭비도, 개선판의 "매번 루트부터 다시 걸어 내려가는" 낭비도 사라지고, 각 원소가 스택에서 딱 한 번 push되고 한 번 pop되는 것으로 전체가 끝납니다.
