# Link-Cut Tree — 트리를 수직 경로로 쪼개 Splay Tree에 맡기기

## 한눈에 보는 컨셉

동적으로 간선이 추가·삭제되는 포레스트(forest)에서, 두 노드가 같은 트리에 속하는지를 빠르게 판정하는 자료구조예요. 비결은 트리를 여러 개의 수직 "선호 경로(preferred path)"로 쪼개고, 각 경로를 Splay Tree 하나로 표현하는 것입니다. 그 덕분에 간선 연결(`link`)·간선 제거(`cut`)·연결성 확인(`connected`)이 모두 분할 상환 $O(\log n)$에 끝나요 — Union-Find가 하지 못하는 간선 삭제까지 지원하면서도요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

핵심 아이디어를 한 문장으로 요약하면 이렇습니다. "트리를 여러 개의 수직 경로로 쪼개고 각 경로를 Splay Tree로 관리하면, 경로 하나를 재배치하는 것만으로 트리 전체의 모양(어느 노드가 루트인지, 어떤 간선이 살아있는지)을 바꿀 수 있다." 이 아이디어는 Union-Find가 못 하는 지점에서 출발합니다 — Union-Find는 `link`를 $O(\alpha(n))$에 처리하지만 `cut`을 아예 지원하지 않아요.

다음 신호가 겹치면 Link-Cut Tree를 떠올리세요.

- 그래프의 간선이 **동적으로 추가되고 삭제**되는데(`link`·`cut`), 그 와중에 "두 정점이 연결돼 있는가"를 반복 질의해야 한다.
- 정적인 트리라면 DFS/BFS 전처리 한 번으로 끝나지만, 이 문제는 질의와 질의 사이에 구조가 계속 바뀐다.
- Union-Find로 풀고 싶은데 **간선 삭제**가 걸림돌이 되는 경우.
- (경우에 따라) 경로 위의 집계(구간 최댓값, 합 등)까지 요구되면, 이는 Link-Cut Tree를 확장(augment)해야 한다는 신호이기도 하다.

세 가지 대안의 비용을 나란히 놓고 보면 차이가 분명해집니다($q$는 질의 횟수, `deg`는 정점의 차수).

```text
연산              인접리스트+BFS/DFS    Union-Find      Link-Cut Tree
link(u, v)             O(1)             O(α(n))       O(log n) 분할상환
cut(u, v)             O(deg(u))         지원 안 함      O(log n) 분할상환
connected(u, v)         O(n)            O(α(n))       O(log n) 분할상환

q번의 질의 총합:        O(q·n)          (cut 불가로 탈락)    O(q log n)
```

`cut`이 필요 없다면 Union-Find가 훨씬 단순하고 상수도 작으니 그걸 쓰세요. `cut`까지 필요한데 경로·서브트리 집계는 필요 없다면 Link-Cut Tree의 경량 버전(경로 반전만 지원)으로 충분하고, 서브트리 전체의 집계(부분합, 서브트리 크기 등)까지 필요하면 Euler Tour Tree 같은 다른 동적 트리 자료구조를 고려하는 편이 낫습니다.

### 문제 사례와 적용 예시

- **동적 그래프 연결성**: 통신망·전력망처럼 간선이 수시로 끊기고 복구되는 네트워크에서 "지금 발전소 A와 변전소 B가 연결돼 있는가"를 실시간으로 답해야 하는 관제 시스템.
- **동적 최소 신장 트리(Dynamic MST)**: Holm–de Lichtenberg–Thorup류 알고리즘에서, 간선 추가·삭제가 섞인 그래프의 MST를 유지할 때 트리 간선을 Link-Cut Tree로 관리해 각 갱신을 준선형 시간에 처리합니다.
- **동적 LCA·경로 질의**: `access(v)` 연산 자체가 "두 노드의 최소 공통 조상(LCA)"을 부산물로 얻을 수 있어, 트리가 계속 변하는 상황에서의 LCA·경로 최댓값 질의에 활용됩니다.
- **코딩 테스트 맥락**: "간선 추가(`link`)·삭제(`cut`)·연결성 질의(`connected`)가 뒤섞여 반복되는데, 매번 $O(n)$ BFS로는 시간 초과"인 문제 — 이 가이드가 다루는 문제가 정확히 이 유형입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드에서는 0-기반 정수 노드 인덱스 $[0, n)$과 다음 인터페이스를 정의합니다. `link`는 서로 다른 트리에 속한 두 노드에서만, `cut`은 실제로 존재하는 간선에서만 호출된다고 가정합니다(사이클 생성이나 존재하지 않는 간선 삭제는 호출자 책임으로 둡니다).

```ts
class LinkCutTree {
  constructor(n: number): LinkCutTree;
  link(u: number, v: number): void;
  cut(u: number, v: number): void;
  connected(u: number, v: number): boolean;
}
```

내부적으로 각 노드는 다음 필드를 가집니다.

```ts
class LCTNode {
  left: LCTNode | null = null;   // 보조 Splay Tree의 왼쪽 자식 (원래 트리에서 더 얕음)
  right: LCTNode | null = null;  // 보조 Splay Tree의 오른쪽 자식 (원래 트리에서 더 깊음)
  parent: LCTNode | null = null; // 보조 트리 내부 부모 *또는* 다른 경로로 넘어가는 path-parent
  rev = false;                   // 경로 방향 반전 지연 태그
}
```

지켜야 할 불변식은 다섯 가지입니다.

1. 각 노드는 원래 트리에서 자식 중 최대 하나만 "선호 자식(preferred child)"으로 지정하고, 선호 자식으로 이어지는 사슬이 "선호 경로(preferred path)"를 이룬다.
2. 하나의 선호 경로는 하나의 보조 Splay Tree로 표현되며, 정렬 기준은 원래 트리에서의 **깊이(depth) 오름차순**이다. 정식으로 쓰면, 보조 트리의 어떤 노드 $v$에 대해
   $$\forall x \in \mathrm{left}(v),\ \forall y \in \mathrm{right}(v): \quad depth(x) < depth(v) < depth(y)$$
3. 서로 다른 보조 Splay Tree는 `parent` 포인터로만 연결된다("path-parent"). 이 포인터는 보조 트리 안의 진짜 부모-자식 관계가 **아니라**, 다른 선호 경로로 넘어가는 경계선일 뿐이다.
4. $x$가 자신이 속한 보조 트리의 루트인지는 `isRoot(x) := x.parent === null || (x.parent.left !== x && x.parent.right !== x)`로 판별한다.
5. `rev` 플래그가 세워진 노드는 `pushDown`을 거치기 전까지 왼쪽·오른쪽 자식의 의미가 반전된 상태로 "지연"되어 있다.

작은 예로 원래 트리와 그 분해를 함께 그려 봅시다. 원래 트리가 `1`을 루트로 `0`, `2`를 자식으로 두고 `2` 아래에 `3`이 있다고 하고, 선호 경로가 `1→2→3`으로 잡혀 있다고 해 볼게요.

```text
원래 트리:                선호 경로 분해:                보조 Splay Tree로 표현:

      1                   {1, 2, 3} : 선호 경로              1
     / \                  {0}       : 독립 경로               \
    0   2                                                      2      ← depth 오름차순으로 오른쪽
        |                 0 --path_parent--> 1                  \      (자식 = 더 깊은 노드)
        3                                                         3

                          0은 자신만의 보조 트리(단일 노드)이고,
                          parent 포인터로만 1과 이어져 있다(진짜 부모-자식 아님).
```

**액션(연산)** — 공개 연산 셋과, 그것을 구현하는 내부 보조 연산입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(n)` | 독립된 노드 $n$개로 초기화 | $O(n)$ |
| `link(u, v)` | 서로 다른 트리의 $u$, $v$를 간선으로 연결 | $O(\log n)$ 분할상환 |
| `cut(u, v)` | $u$-$v$ 직접 간선을 제거해 트리를 둘로 분리 | $O(\log n)$ 분할상환 |
| `connected(u, v)` | $u$, $v$가 같은 트리인지 판정 | $O(\log n)$ 분할상환 |
| `access(v)` *(내부)* | $v$~실제 루트 경로를 하나의 선호 경로로 합침 | $O(\log n)$ 분할상환 |
| `makeRoot(v)` *(내부)* | `access(v)` 후 $v$를 실제 루트로 지정(경로 반전) | $O(\log n)$ 분할상환 |
| `findRoot(v)` *(내부)* | $v$가 속한 트리의 실제 루트 탐색 | $O(\log n)$ 분할상환 |

핵심 연산 두 가지를 그림으로 자세히 볼게요.

**① `access(v)` — 선호 자식을 바꿔서 경로를 재배치**. 위 예시에서 `access(0)`을 호출하면 무슨 일이 일어날까요? $0$은 `1`의 자식이지만 지금은 선호 경로 `{1,2,3}`에 들어있지 않습니다. `access(0)`은 "$0$을 루트까지 잇는 새 선호 경로"를 만들면서, 기존에 `1`의 선호 자식이던 `2`를 떼어냅니다.

```text
Before access(0):                        After access(0):

보조 트리 A (선호경로 1→2→3):              보조 트리 (선호경로 1→0):
      1                                        0
       \                                      /
        2                                    1        ← 1의 오른쪽 자식이
         \                                              2에서 0으로 교체됨
          3

보조 트리 B (독립, path_parent=1):         분리된 보조 트리 (path_parent=1로 유지):
      0                                        2
                                                 \
                                                  3
```

`access`는 뿌리 방향으로 올라가며 매 단계에서 "지금까지 처리한 아래쪽 경로"를 `x.right`에 이어 붙입니다. `x.right = last`라는 한 줄이 곧 "선호 자식을 갈아 끼우는" 동작이고, 이때 밀려난 옛 선호 자식은 `parent` 포인터만 남긴 채(path-parent) 독립된 보조 트리로 떨어져 나갑니다.

**② `link`/`cut` — 트리 두 개를 잇고 끊기**. 시뮬레이션의 실제 시퀀스로 보면(뒤 "실행 시각화" 절에서 그대로 실행해 검증합니다):

```text
Before link(1, 2):     {0, 1}   {2}   {3}   {4}
After  link(1, 2):     {0, 1, 2}      {3}   {4}
```

```text
Before cut(1, 2):      {0, 1, 2}      {3, 4}
After  cut(1, 2):      {0, 1}   {2}   {3, 4}
```

`link(u, v)`는 `makeRoot(u)`로 $u$를 자기 트리의 실제 루트로 만든 다음, `u.parent = v`라는 단 한 줄로 두 트리를 잇습니다(진짜 부모-자식이 아니라 path-parent 연결). `cut(u, v)`는 `makeRoot(u)` 후 `access(v)`를 호출하면 $u$가 정확히 `v.left` 자리에 오는 성질을 이용해, `v.left`를 떼어내는 것만으로 간선을 제거합니다.

### 왜 모순 없이 작동하는가

**불변식이 보존되는 이유(귀납)**: 빈 포레스트(모든 노드가 각자 보조 트리 하나)에서 시작하면 불변식 1~5가 자명하게 성립합니다. 이제 `access`가 이 불변식을 보존함을 봅시다. `splay(x)` 자체는 하나의 보조 트리 **안에서** 이진 탐색 트리 순서를 보존하는 회전이므로 불변식 2(깊이 오름차순)를 깨지 않습니다. `x.right = last`로 선호 자식을 바꾸는 것은 "옛 선호 자식을 path-parent로 떼어내고 새 선호 자식을 붙이는" 재분배일 뿐, 그 결과도 여전히 유효한 선호 경로 분해입니다(불변식 1, 3 유지). `makeRoot`는 `access` 이후 `rev` 플래그 하나만 세우는데, 이 플래그가 `pushDown`을 통해 정확히 자식에게 전파되는 한 "깊이 오름차순"의 해석이 일관되게 뒤집힐 뿐 구조 자체(불변식 2)는 재귀적으로 유지됩니다.

**`cut`이 항상 옳은 이유**: `makeRoot(u)` 이후 $u$는 자기 트리에서 깊이 0(실제 루트)입니다. `access(v)`를 하면 $v$가 보조 트리의 루트가 되고, $v$보다 얕은 모든 노드(= $u$에서 $v$ 직전까지의 경로 전체)가 `v.left` 서브트리에 모입니다. 문제 제약상 간선 $(u,v)$가 실제로 존재하면 $u$-$v$ 사이의 경로 길이는 정확히 1이므로, `v.left` 서브트리는 $u$ 단 하나뿐입니다. 그래서 `v.left.parent = null; v.left = null` 두 줄로 간선 제거가 끝납니다.

**`connected`가 항상 옳은 이유**: `makeRoot(u)`로 $u$를 자기 트리의 실제 루트로 만든 뒤 `findRoot(v)`를 부르면, $v$가 $u$와 같은 트리에 있을 때만 `access(v)`가 $u$까지 포함한 하나의 보조 트리를 만들고, 그 트리의 최소 깊이 노드(= 실제 루트)가 정확히 $u$가 됩니다. $v$가 다른 트리에 있다면 `access(v)`는 $v$가 속한 트리 안에서만 동작하므로 최소 깊이 노드는 $u$가 아닌 그 트리 자신의 루트입니다.

**분할 상환 $O(\log n)$인 이유**: `access` 한 번에서 선호 자식이 바뀌는 횟수(= 이 함수 안에서 도는 while 루프 반복 수)를 퍼텐셜 함수(각 노드가 속한 보조 트리 크기의 로그 합)로 분석하면, 전체 $n$번의 `access` 합계가 $O(n \log n)$임이 증명됩니다(Sleator & Tarjan, "A Data Structure for Dynamic Trees", *J. Comput. Syst. Sci.* 26(3), 1983). `splay` 자체도 잘 알려진 분할 상환 $O(\log n)$이므로, `link`·`cut`·`connected`는 모두 상수 번의 `access`/`splay` 호출로 구성되어 분할 상환 $O(\log n)$을 유지합니다.

잠깐, 확인 질문 하나만 해 볼까요? `access(0)`을 호출한 뒤 예시 트리의 `{2, 3}` 가지는 완전히 사라지나요? 아닙니다 — `path_parent`(= `parent` 포인터)로 `1`에 매달린 채 남아 있고, 나중에 `2`나 `3`을 `access`하면 다시 선호 경로로 등장합니다. 사라지는 게 아니라 "지금 당장 안 보이는 곳으로 치워지는" 것뿐이에요.

**여기서 헷갈리기 쉬운 포인트**를 세 가지 짚어 둡니다.

- **`isRoot`가 `true`인데 `parent`가 `null`이 아닐 수 있다는 점입니다.** 이때의 `parent`는 진짜 부모가 아니라 path-parent이고, `splay` 회전은 이 경계를 절대 넘지 않습니다(그래서 `isRoot`에서 멈춥니다). 이 구분을 놓치면 `access`가 엉뚱한 보조 트리까지 회전시켜 구조가 깨집니다.
- **`pushDown`을 회전 직전에, 위에서 아래 순서로 호출하지 않으면 조용히 틀린 답이 나온다는 점입니다.** 구체적으로 확인해 보죠. `splay(x)`에서 회전하기 전에 `pushDown(g)`, `pushDown(p)`를 생략한 버전으로, 이 가이드의 시뮬레이션과 **똑같은** `link(0, 1); link(1, 2)` 시퀀스를 실행하면 `connected(0, 2)`가 `true`가 아니라 **`false`**를 반환합니다(직접 실행해 확인한 결과입니다). `rev` 플래그가 자식에게 전파되지 않은 채로 회전이 왼쪽/오른쪽 자식을 잘못 읽어 depth 순서가 뒤집히기 때문이에요.
- **`cut(u, v)`를 실제로 존재하지 않는 간선에 호출하면 정의되지 않은 동작이라는 점입니다.** `v.left`가 $u$가 아니거나 아예 `null`일 수 있어 `left.parent = null`에서 예외가 나거나 엉뚱한 서브트리가 잘려 나갑니다. 문제 제약이 이 상황을 막아 주지만, 직접 만든 테스트에서 이 조건을 깨면 바로 드러납니다.

엣지 케이스도 점검해 둡니다.

```text
n = 1 (단일 노드)          → connected(0, 0) = true (link/cut 대상 자체가 없음)
connected(v, v)            → 노드 하나짜리 경우를 포함해 항상 true (u === v로 즉시 판정)
link 직후 바로 cut          → 원상복구, connected는 다시 false
u, v를 바꿔서 link(v, u)    → link(u, v)와 동일한 트리를 만든다 (makeRoot가 방향을 흡수)
직접 간선이 없는 cut(u, v)  → v.left가 u가 아닐 수 있음 → 정의되지 않은 동작(문제 제약이 보장)
```

## 아이디어를 코드로 옮기기

위에서 정의한 인터페이스와 불변식을 그대로 TypeScript로 옮깁니다. `isRoot`·`pushDown`·`rotate`·`splay`가 Splay Tree의 기계 장치이고, 그 위에 `access`·`makeRoot`·`findRoot`가 Link-Cut Tree 고유의 로직을 얹습니다.

```ts
class LCTNode {
  left: LCTNode | null = null;
  right: LCTNode | null = null;
  parent: LCTNode | null = null;
  rev = false;
  readonly id: number;

  constructor(id: number) {
    this.id = id;
  }
}

class LinkCutTree {
  private nodes: LCTNode[];

  constructor(n: number) {
    this.nodes = Array.from({ length: n }, (_, i) => new LCTNode(i));
  }

  private isRoot(x: LCTNode): boolean {
    const p = x.parent;
    return p === null || (p.left !== x && p.right !== x);
  }

  private pushDown(x: LCTNode): void {
    if (!x.rev) return;
    const { left, right } = x;
    x.left = right;
    x.right = left;
    if (x.left) x.left.rev = !x.left.rev;
    if (x.right) x.right.rev = !x.right.rev;
    x.rev = false;
  }

  private rotate(x: LCTNode): void {
    const p = x.parent!;
    const g = p.parent;
    const wasRoot = this.isRoot(p);
    const isLeft = p.left === x;

    // x의 안쪽 자식을 p에게 넘기고, p를 x의 자식으로 끌어내린다.
    if (isLeft) {
      p.left = x.right;
      if (x.right) x.right.parent = p;
      x.right = p;
    } else {
      p.right = x.left;
      if (x.left) x.left.parent = p;
      x.left = p;
    }
    p.parent = x;
    x.parent = g;

    // g가 진짜 부모였을 때만(선호 경로 안이었을 때만) g의 자식 포인터를 갱신한다.
    // wasRoot면 g는 path-parent였을 뿐이므로 g.left/right는 건드리지 않는다.
    if (!wasRoot && g) {
      if (g.left === p) g.left = x;
      else if (g.right === p) g.right = x;
    }
  }

  private splay(x: LCTNode): void {
    while (!this.isRoot(x)) {
      const p = x.parent!;
      const g = p.parent;
      if (!this.isRoot(p)) this.pushDown(g!); // 위에서
      this.pushDown(p);                       // 아래로
      this.pushDown(x);                       // 순서대로 밀어 내린 뒤에만 회전한다
      if (!this.isRoot(p)) {
        const zigzig = (g!.left === p) === (p.left === x);
        this.rotate(zigzig ? p : x);
      }
      this.rotate(x);
    }
    this.pushDown(x);
  }

  /** v에서 (makeRoot로 지정된) 실제 루트까지의 경로를 하나의 선호 경로로 합친다. */
  private access(v: LCTNode): void {
    let last: LCTNode | null = null;
    let x: LCTNode | null = v;
    while (x !== null) {
      this.splay(x);
      x.right = last; // 선호 자식을 last로 교체 — access의 핵심 한 줄
      last = x;
      x = x.parent; // isRoot였으므로 이 parent는 path-parent
    }
    this.splay(v);
  }

  /** access(v) 후 v를 원래 트리의 루트로 만든다(경로 반전 태그). */
  private makeRoot(v: LCTNode): void {
    this.access(v);
    v.rev = !v.rev;
  }

  /** x가 속한 보조 트리(선호 경로)의 최소 깊이 노드 = 그 트리의 실제 루트. */
  private findRoot(x: LCTNode): LCTNode {
    this.access(x);
    let cur = x;
    this.pushDown(cur);
    while (cur.left !== null) {
      cur = cur.left;
      this.pushDown(cur);
    }
    this.splay(cur);
    return cur;
  }

  link(u: number, v: number): void {
    const nu = this.nodes[u]!;
    const nv = this.nodes[v]!;
    this.makeRoot(nu);
    nu.parent = nv; // path-parent 포인터로 두 트리를 잇는다
  }

  cut(u: number, v: number): void {
    const nu = this.nodes[u]!;
    const nv = this.nodes[v]!;
    this.makeRoot(nu);
    this.access(nv);
    // 직접 간선이면 nv.left는 정확히 nu 하나뿐이다.
    const left = nv.left!;
    left.parent = null;
    nv.left = null;
  }

  connected(u: number, v: number): boolean {
    if (u === v) return true;
    const nu = this.nodes[u]!;
    const nv = this.nodes[v]!;
    this.makeRoot(nu);
    return this.findRoot(nv) === nu;
  }
}
```

가장 중요한 부분은 `access`의 `x.right = last` 한 줄과, `splay` 안에서 회전 직전에 `pushDown(g)` → `pushDown(p)` → `pushDown(x)`를 **위에서 아래 순서**로 호출하는 부분입니다. 놓치기 쉬운 지점을 더 짚어 볼게요.

- **`rotate`에서 `p.left = x.right`가 `x.right = p`보다 먼저 와야 합니다.** 순서를 바꾸면 `x.right`가 이미 `p`로 바뀐 뒤에 그 값을 다시 `p.left`에 대입하게 되어, `p.left`가 `p` 자기 자신을 가리키는 자기 참조가 만들어집니다.
- **`isRoot`는 `parent`의 `left`/`right` 어느 쪽도 자신이 아닌지로 판별합니다.** `parent === null` 조건만 확인하면 path-parent로 매달린 노드를 놓쳐 `splay`가 엉뚱한 보조 트리를 침범합니다.
- **`cut`에서 `left.parent = null`을 빠뜨리면** 방금 잘라낸 노드가 여전히 옛 부모를 path-parent로 기억한 채 남아, 다음 `access`가 이미 끊어진 간선을 타고 잘못된 트리로 올라갈 수 있습니다.

> 회전하기 전엔 항상 위에서 아래로 밀어내려라(`pushDown`) — 안 그러면 뒤집힌 자식을 잘못 읽는다.
