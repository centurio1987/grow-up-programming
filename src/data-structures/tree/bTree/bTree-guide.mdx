# BTree — 노드 하나를 페이지 하나로 삼아, 트리를 납작하게 누르기

## 한눈에 보는 컨셉

B-트리는 이진 탐색 트리처럼 정렬을 유지하되, 노드 하나에 키를 여러 개(최소 차수 $t$ 기준, **루트를 제외한** 노드는 $t-1$개 이상 $2t-1$개 이하) 담아 분기 수를 2가 아니라 $t \sim 2t$로 늘린 다진(multiway) 탐색 트리예요. 비결은 **비용의 단위를 "비교 횟수"가 아니라 "노드 접근 횟수"로 바꿔 잡은 것**입니다 — 노드 하나가 디스크 페이지 하나에 대응하면, 트리 높이가 곧 디스크 I/O 횟수가 되니까요. 높이를 $O(\log_t n)$으로 눌러 $10^8$개의 키를 접근 네 번에 찾아내고, 삽입·삭제는 "내려가면서 미리 쪼개고 미리 채우는" 선제적(preemptive) 정책 덕분에 위로 되돌아 올라가는 뒷정리 없이 한 번 내려가는 것만으로 끝납니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 B-트리를 떠올리세요.

- 저장할 원소 수가 아주 크고(수백만~수십억), **노드 하나에 접근하는 비용 자체가 비쌀 때**(디스크 페이지 읽기, 네트워크 왕복, 캐시 미스)
- 삽입·삭제가 끊임없이 섞이는데도 항상 정렬 순서와 균형 잡힌 높이를 유지해야 할 때
- 분기가 2뿐인 이진 탐색 트리로는 높이가 너무 커서, **접근 횟수 자체를 줄이고 싶을 때**

분기 수가 접근 횟수에 미치는 영향부터 체감해 봅시다. 키 $10^8$개를 저장했다고 하고, 각 구조의 최악 높이를 공식으로 계산한 값입니다(뒤에서 그 공식을 직접 유도합니다).

```text
n = 10^8 일 때 루트에서 리프까지 "방문하는 노드 수" (= 접근 횟수)
  아래 숫자의 단위는 전부 '방문 노드 수' 로 통일했다.
  (간선 기준 높이 h 인 트리는 노드를 h+1 개 방문한다)

완전 균형 이진 트리 (이론상 최선)  log2(n+1)          →  27
AVL 트리, 최악                    1.44 log2(n+1)      →  38
레드블랙 트리, 최악                2 log2(n+1) + 1     →  54
B-트리 t=10   (키 9~19개),   최악  간선 높이 7         →   8
B-트리 t=100  (키 99~199개), 최악  간선 높이 3         →   4
B-트리 t=1000 (키 999~1999개),최악 간선 높이 2         →   3

노드 접근 1회가 디스크 I/O 라면:
  HDD 랜덤 읽기 ≈ 10ms   →  27회 = 270ms   vs  4회 = 40ms
  NVMe SSD      ≈ 0.05ms →  27회 = 1.35ms  vs  4회 = 0.2ms
```

여기서 이진 트리 쪽 27회는 **가장 유리하게 잡아 준 값(완전 균형)** 이라는 점을 짚어 둘게요. 실제 자기 균형 트리의 최악값은 그보다 커서 AVL은 38회, 레드블랙은 54회입니다. 반면 B-트리 쪽 숫자는 전부 **최악 상한**이에요. 즉 위 표는 이진 트리에 유리하게 기울여 놓은 비교인데도 자릿수가 갈립니다. 그리고 저장 장치가 HDD에서 NVMe로 바뀌어 절대 시간이 200배 빨라져도 **비율은 그대로**입니다 — 접근 횟수를 줄이는 이득은 장치가 빨라진다고 사라지지 않아요.

$t$를 키우면 트리는 얕아지지만 공짜는 아니에요. 노드 하나에서 원하는 키를 찾는 비용이 최대 $O(t)$(노드 안에서 이진 탐색을 하면 $O(\log t)$)로 늘어납니다. 실제로 이진 탐색을 쓰면 **CPU 비교 횟수는 이진 트리와 정확히 같아집니다**.

$$
O(\log t) \times O(\log_t n) \;=\; O\!\left(\log t \cdot \frac{\log n}{\log t}\right) \;=\; O(\log n)
$$

밑 변환 공식 $\log_t n = \frac{\log n}{\log t}$를 넣으면 $\log t$가 약분되어 $t$가 통째로 사라져요. 그러니까 B-트리가 줄이는 것은 **비교 횟수가 아니라 접근 횟수**입니다 — 접근 횟수만 $\frac{1}{\log_2 t}$ 배로 줄고, CPU가 하는 비교의 총량은 그대로예요. 이것이 "노드 접근이 비교보다 훨씬 비쌀 때만 이득"이라는 말의 정확한 의미입니다. 비교와 포인터 추적 비용이 비슷한 순수 인메모리 상황이라면 분기 2인 AVL·레드블랙 트리도 충분히 경쟁력이 있습니다(다만 인메모리에서도 캐시 라인 단위 접근을 고려해 다진 트리를 쓰는 구현이 있습니다 — "메모리면 무조건 이진 트리"는 아닙니다).

> **B+ 트리와의 선택 기준**: 지금 보는 B-트리는 데이터를 내부 노드에도 둡니다. 그래서 점 조회는 운이 좋으면 리프까지 안 가고 끝나지만, 범위 질의(`[low, high]` 전체 나열)는 트리를 오르내려야 해서 불리해요. 범위 질의가 잦다면 데이터를 리프에만 모으고 리프끼리 연결 리스트로 잇는 B+ 트리가 유리합니다. 반대로 B-트리는 같은 키를 내부 노드와 리프에 중복 저장하지 않는다는 이점이 있는데, 실제 데이터베이스·파일 시스템에서는 레코드 크기·내부 노드 fanout·페이지 캐시 효율까지 함께 따져 B+ 트리를 고르는 경우가 많습니다. 즉 "점 조회면 B-트리"로 단정할 문제는 아니에요.

### 문제 사례와 적용 예시

- **파일 시스템 인덱스**: btrfs는 메타데이터 전반을 B-트리로 관리하고, HFS+는 카탈로그를 B-트리로, NTFS는 디렉터리 인덱스를 B+ 트리 성격의 구조로, ext4는 해시를 키로 쓰는 변형(HTree)으로 관리합니다. 세부 변형은 제각각이지만 공통점은 하나예요 — **노드 하나를 디스크 페이지(4KB~16KB) 크기에 맞춘다**는 것입니다.
- **임베디드 키-값 스토어**: Berkeley DB의 B-트리 액세스 메서드처럼, 파일 하나에 정렬된 인덱스를 통째로 얹는 저장소 엔진의 기본 구조입니다.
- **외부 정렬·페이지 인덱스**: 메모리에 한 번에 올릴 수 없는 데이터를 페이지 단위로 인덱싱할 때, 페이지 하나를 노드 하나에 대응시킵니다.
- **코딩 테스트 맥락**: "삽입·삭제가 뒤섞이는 동적 정렬 컨테이너를 구현하라" — JS/TS에는 정렬 상태를 유지하는 내장 컨테이너가 없어 직접 구현 대상이 됩니다.

## 왜 이 모양이어야 하는가

"노드에 키를 여러 개 담는다"는 결론만 보면 시시해 보입니다. 그런데 왜 하필 **한 노드에 상한과 하한을 동시에** 두고, 왜 새 노드가 **리프가 아니라 루트 쪽으로** 자라며, 왜 하필 상한이 하한의 **2배 + 1**일까요? 이 절은 B-트리를 모른 채 같은 문제를 만났을 때 떠올릴 설계들을 차례로 무너뜨리면서 그 답을 만들어 갑니다.

### 순진한 설계와 그 실패

문제는 이겁니다: **키 $10^8$개를 정렬 상태로 디스크에 두고, 조회·삽입·삭제를 모두 지원할 것.** 여기서 비용은 CPU 비교 횟수가 아니라 **디스크 접근 횟수**로 셉니다(비교 한 번이 나노초 단위라면 디스크 접근은 밀리초 단위라, 백만 배 차이 나는 두 비용을 같은 자로 잴 수는 없어요).

**후보 ① 정렬 배열을 파일에 그대로.** 이진 탐색이면 27번 비교로 찾습니다. 문제는 삽입이에요 — 가운데에 키 하나를 끼우려면 뒤쪽 전부를 밀어야 합니다.

```text
n = 10^8, 4KB 페이지에 키 512개(8바이트 키 기준)가 들어간다고 하자

조회: 이진 탐색 27회 비교 → 서로 다른 페이지를 최대 ~18개 읽는다   (감당 가능)
삽입: 평균 5 x 10^7 개의 키를 한 칸씩 이동
      = 약 10만 개의 페이지를 읽고 다시 쓴다                        (사실상 불가능)
```

**후보 ② AVL·레드블랙 같은 이진 균형 트리를 디스크에.** 앞선 가이드의 답을 그대로 가져오는 셈입니다. 삽입은 $O(\log n)$으로 해결됐지만, 이번엔 **조회 비용이 접근 횟수로 환산되는 순간** 무너집니다.

```text
가장 유리하게 잡아도(완전 균형) 노드 27개 방문 → 27번의 디스크 I/O = 270ms
AVL 의 최악(38회)이나 레드블랙의 최악(54회)이면 그보다 더 나쁘다

게다가 노드 하나의 크기는:
  키 8B + 자식 포인터 8B x 2 = 24B
  그런데 디스크는 4096B(4KB) 단위로만 읽는다
  → 한 번 읽은 4096B 중 24B만 쓰고 나머지 4072B(99.4%)는 버린다
```

이게 이진 트리의 진짜 문제예요. **접근 단위(4KB)와 정보 단위(24B)가 어긋나 있습니다.** 트리가 균형 잡혀 있느냐 아니냐 이전에, 한 번의 접근으로 가져온 데이터의 0.6%만 쓰고 있는 거죠.

**후보 ③ 이진 트리를 페이지 단위로 묶어 담기.** 어긋남이 문제라면 붙여 보면 어떨까요? 이진 트리의 서브트리를 통째로 한 페이지에 담는 겁니다. 4KB에 노드 170개면 높이 7~8짜리 서브트리가 들어가니, 접근 횟수가 $27 \div 8 \approx 4$회로 줄어요. **아이디어의 방향은 정확히 맞습니다.**

무너지는 곳은 **유지**입니다.

```text
[페이지 1]  루트 근처 서브트리 (노드 170개)
[페이지 2]  그 아래 서브트리
   ...

삽입/삭제가 회전을 일으키면?
  - 회전은 부모-자식 관계를 바꾼다 → 어떤 노드가 어느 페이지에 속해야 하는지가 바뀐다
  - 페이지 경계를 넘는 회전이 생기면 두 페이지를 모두 다시 쓴다
  - 노드가 늘어나면 묶음이 넘쳐, 어느 서브트리를 어느 페이지에 담을지 재배치해야 한다
```

즉 "묶음"이 **자료구조의 불변식이 아니라 그때그때의 배치**일 뿐입니다. 여기서 문제는 "재작성이 몇 번이냐"가 아니라, 연산이 묶음을 보존한다고 **아무도 보장하지 않는다**는 점이에요. 어떤 삽입 순서에서 어느 페이지에 몇 개의 노드가 남는지가 불변식으로 고정돼 있지 않으니, 최악의 접근 횟수를 위에서 눌러 줄 근거가 사라집니다. 후보 ②의 27회를 4회로 줄였다는 계산도 "묶음이 잘 유지된다면"이라는 가정 위에서만 성립하고요.

> 여기서 결정적인 전환이 나옵니다. 묶음이 연산에 의해 깨진다면, **묶음 자체를 자료구조의 1급 단위로 승격**시키면 됩니다. "한 페이지에 담긴 정렬된 키 배열"을 노드 하나로 정의하고, 모든 연산이 그 단위를 직접 다루게 하는 거예요.

**후보 ④ 다진 트리인데, 이진 탐색 트리처럼 리프에서 자라기.** 노드에 키를 여러 개 담기로 했으니 이제 삽입을 정의해야 합니다. 가장 익숙한 방식은 BST처럼 "내려가서 리프에 매다는" 것이겠죠. 그런데 이러면 후보 ②가 겪은 문제가 그대로 돌아옵니다.

```text
1, 2, 3, ... 을 순서대로 넣으면 (노드당 최대 3개, 리프에서 자라기)

[1,2,3]
   \
   [4,5,6]
      \
      [7,8,9]
         \        ← 오른쪽으로만 자란다. 리프 깊이가 제각각이고 높이는 n/3 규모
```

리프에서 자라게 두면 **어느 리프는 깊고 어느 리프는 얕은** 상태를 막을 방법이 없습니다. 접근 횟수의 최악값은 가장 깊은 리프가 정하니, 평균이 좋아도 소용없어요.

**후보 ⑤ 상한만 두고 하한은 두지 않기.** "노드가 페이지보다 커지면 안 된다"는 상한($2t-1$)은 물리적으로 당연합니다. 그럼 하한도 필요할까요? 필요합니다. 하한이 없으면 삭제를 반복해 키가 1개뿐인 노드가 잔뜩 생길 수 있고, 그러면 분기 수가 2로 떨어져 **후보 ②의 이진 트리로 되돌아갑니다.**

```text
t = 100 인데 모든 노드가 키 1개만 들고 있다면
  분기 수 2  →  n = 10^8 에서 높이 ≈ 27  →  디스크 I/O 27회
  4KB 페이지에 키 하나(8B)만 담아 읽는 셈 → 사용률 0.2%

= 후보 ② 와 정확히 같은 실패. 상한만으로는 아무것도 보장되지 않는다.
```

### 실패가 가리키는 설계 규칙

다섯 실패에서 규칙을 하나씩 뽑아냅니다.

**관찰 ①: 비용의 단위는 비교가 아니라 노드 접근이다.** 후보 ②의 27회 I/O가 그것을 보여 줬어요. 그러니 목표는 하나입니다 — **트리의 높이(= 접근 횟수)를 줄여라.**

**관찰 ②: 높이는 분기 수가 정한다.** 한 번의 접근으로 $m$갈래를 가를 수 있으면 높이는 $\log_m n$ 규모로 줄어듭니다. 후보 ③이 접근 횟수를 4회로 줄인 것도 이 원리였어요. 다만 정확히 말하면 **높이를 위에서 눌러 주는 것은 최대 분기 수가 아니라 최소 분기 수**입니다 — 어떤 노드는 200갈래이고 어떤 노드는 2갈래라면, 최악 경로는 2갈래짜리만 골라 내려가니까요. 이 구멍은 관찰 ⑤에서 메웁니다.

> 규칙 A: **접근 단위(페이지)를 꽉 채워 분기 수를 키운다.** 4KB 페이지에 키 8B + 자식 포인터 8B라면 노드 하나에 키를 약 256개까지 담을 수 있고, 그러면 분기가 257갈래라 $10^8$개도 높이 3~4에 들어옵니다.

**관찰 ③: 묶음이 연산에 의해 깨지면 소용없다(후보 ③).** 그래서 묶음을 노드로 승격시키되, 노드에는 **크기 상한**이 있어야 합니다 — 페이지에 안 들어가는 노드는 규칙 A의 전제를 무너뜨리니까요.

> 규칙 B: 노드의 키 개수에 **상한 $2t-1$**을 둔다. 상한을 넘으면 노드를 **분할**한다.

**관찰 ④: 리프에서 자라면 깊이가 제각각이 된다(후보 ④).** 그렇다면 자라는 방향을 뒤집어야 합니다. 분할할 때 가운데 키를 **부모로 밀어 올리면**, 새 노드는 아래가 아니라 **옆(같은 깊이의 형제)** 으로 생겨요. 그러면 리프들의 깊이는 서로 같은 채로 유지되고, 깊이가 늘어나는 경우는 딱 하나 — **루트가 분할될 때**뿐입니다. 루트가 쪼개지면 그 위에 새 루트가 하나 생기면서 **모든 리프가 동시에 한 칸씩 깊어지니까요.**

```text
리프에서 자라기 (후보 ④)          위로 자라기 (분할·승격)

  [A]                                     [ 가운데 키 ]
    \                                     /          \
    [B]        깊이 제각각            [왼쪽 반]     [오른쪽 반]
      \                                  ↑ 같은 깊이의 형제로 생긴다
      [C]                          루트가 쪼개질 때만 전체가 한 칸 깊어진다
```

> 규칙 C: 노드는 **위로 자란다.** 그 결과 "모든 리프는 같은 깊이"가 불변식으로 유지된다.

**관찰 ⑤: 상한만으로는 분기 수가 보장되지 않는다(후보 ⑤).** 높이 상한을 실제로 묶으려면 노드마다 **최소한 이만큼은 채워져 있다**는 보증이 필요합니다.

> 규칙 D: 루트가 아닌 모든 노드에 키 개수 **하한 $t-1$**을 둔다. 하한 아래로 내려가면 형제에게서 **빌리거나**, 형제와 **병합**한다.

**그럼 상한과 하한의 비율은 왜 하필 $2t-1$ 대 $t-1$일까요?** 여기에는 필연과 관례가 섞여 있으니 나눠서 밝힐게요. 필연인 부분은 **분할의 결과가 곧바로 유효해야 한다**는 요구입니다. 키가 꽉 찬 노드를 쪼갤 때 가운데 키 하나가 부모로 올라가므로, 남는 키는 두 조각으로 갈립니다.

$$
(2t-1) - 1 = 2(t-1)
$$

즉 상한을 하한의 **2배 + 1**로 잡으면 분할 결과가 정확히 $(t-1) + (t-1)$이 되어, 두 조각이 **딱 하한을 채운 상태**로 태어납니다. 상한이 이보다 작으면(예: $2t-2$) 분할 결과가 $2t-3 = (t-1) + (t-2)$라 한쪽이 하한에 하나 모자란 채로 태어나고, 그럼 만들자마자 다시 병합해야 하는 자기모순이 생겨요. 실무에서 $t$를 정하는 순서도 이 관계를 씁니다 — **페이지 크기가 담을 수 있는 최대 키 수를 $2t-1$로 놓고 거꾸로 $t$를 정하는** 것이지, $t$를 먼저 정하고 페이지를 맞추는 게 아닙니다. 반면 **관례인 부분**도 있습니다. $t$ 대신 "최대 자식 수 $m$"으로 세는 표기도 널리 쓰이고(그때는 최소 채움이 $\lceil m/2 \rceil - 1$), 최소 채움을 절반이 아니라 2/3로 올려 공간 효율을 높인 변종(B\* 트리)도 있어요. 즉 **"절반 채움"은 유일한 정답이 아니라 가장 단순한 선택**입니다.

여기까지 오면 규칙 A~D가 그대로 다음 절의 불변식 여섯 줄이 됩니다 — 노드 크기의 상한과 하한, 자식 수와 키 수의 관계, 정렬 성질, 그리고 모든 리프가 같은 깊이라는 조건이요.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드는 한 종류뿐입니다. 리프인지 아닌지만 플래그로 구분해요.

```ts
class BTreeNode<T> {
  keys: T[] = [];                 // 정렬된 키 배열
  children: BTreeNode<T>[] = [];  // isLeaf가 false면 keys.length + 1개
  isLeaf: boolean = true;
}
```

트리 전체는 `root`, 원소 수 `_size`, 최소 차수 `t`, 비교 함수 `compare`를 유지합니다. 앞 절에서 유도한 규칙을 정식으로 적으면 여섯 줄입니다.

1. **크기 하한·상한(비루트)**: 루트가 아닌 모든 노드 $v$에서 $t-1 \le |\mathrm{keys}(v)| \le 2t-1$ (규칙 B·D)
2. **루트의 크기**: $1 \le |\mathrm{keys}(\text{root})| \le 2t-1$. 트리가 완전히 비면 루트 자체가 `undefined`. (루트에 하한을 걸지 않는 이유는, 원소가 1개뿐인 트리도 표현할 수 있어야 하기 때문이에요.)
3. **리프**: $|\mathrm{children}(v)| = 0$
4. **내부 노드**: $|\mathrm{children}(v)| = |\mathrm{keys}(v)| + 1$ — 키 $k$개가 값의 범위를 $k+1$개 구간으로 나누니까요.
5. **정렬 성질**: 내부 노드 $v$의 모든 $0 \le i < |\mathrm{keys}(v)|$에 대해 $\max(\mathrm{children}(v)[i]) < \mathrm{keys}(v)[i] < \min(\mathrm{children}(v)[i+1])$
6. **모든 리프는 같은 깊이** (규칙 C)

여섯 줄은 **연산이 끝난 시점**의 트리를 규정합니다. 연산 도중에는 잠깐 어겨지는 상태가 있어요 — 병합 직후 루트의 키가 0개가 되는 순간이 대표적이고, `delete`의 마지막 세 줄이 그 상태를 정리합니다. 아래 정당성 논증도 "각 연산이 끝났을 때 여섯 줄이 다시 성립한다"를 보이는 방식으로 진행합니다.

$t=2$로 `1`부터 `7`까지 순서대로 넣으면 실제로 이런 모양이 됩니다(뒤 코드 절의 구현을 그대로 실행한 결과입니다).

```text
                [ 2 , 4 ]              ← 루트(내부 노드): 키 2개, 자식 3개
               /    |    \
            [1]    [3]   [5, 6, 7]     ← 리프 3개, 모두 같은 깊이

inOrder() = [1, 2, 3, 4, 5, 6, 7]   size() = 7
```

**높이 상한을 끝까지 유도하기.** 불변식 1의 **하한** $t-1$이 실제로 높이를 묶어 주는지 세어 봅시다. 여기서 높이 $h$는 루트에서 리프까지의 **간선 수**입니다(루트 하나뿐인 트리는 $h=0$).

- **깊이 $0$(루트)**: 노드 $1$개. 키는 최소 $1$개입니다(불변식 2).
- **깊이 $1$**: 루트가 리프가 아니라면($h \ge 1$) 루트는 키를 최소 1개 가지므로 자식이 최소 $2$개입니다(불변식 4).
- **깊이 $i$ ($2 \le i \le h$)**: 깊이 $i-1$의 노드는 루트가 아니므로 키를 최소 $t-1$개 갖고(불변식 1), 따라서 자식이 최소 $t$개입니다(불변식 4). 그러므로 깊이 $i$의 노드 수는 깊이 $i-1$ 노드 수의 최소 $t$배예요. 깊이 1에서 $2$개로 시작했으니, 깊이 $i$에는 최소 $2t^{\,i-1}$개의 노드가 있습니다.

$h = 0$이면(루트가 곧 리프) 셀 것도 없습니다 — 불변식 2에 의해 $n \ge 1 = 2t^0 - 1$이라 아래 결론이 그대로 성립해요. 그러니 $h \ge 1$인 경우를 봅시다. 깊이 $1$부터 $h$까지의 노드는 각각 키를 최소 $t-1$개씩 갖고, 루트는 최소 1개를 가지므로

$$
n \;\ge\; 1 + \sum_{i=1}^{h} 2t^{\,i-1}(t-1) \;=\; 1 + 2(t-1)\cdot\frac{t^{h}-1}{t-1} \;=\; 1 + 2(t^{h} - 1) \;=\; 2t^{h} - 1
$$

가운데 등호에서 쓴 것은 등비수열의 합 $\sum_{i=1}^{h} t^{\,i-1} = \frac{t^{h}-1}{t-1}$이고, $t \ge 2$라 분모 $t-1 \ge 1 > 0$이니 약분에 문제가 없습니다. 마지막으로 $n \ge 2t^h - 1$을 $h$에 대해 풀면

$$
t^{h} \le \frac{n+1}{2} \quad\Longrightarrow\quad h \;\le\; \log_t\!\left(\frac{n+1}{2}\right)
$$

로그의 밑 $t \ge 2 > 1$이므로 $\log_t$는 증가함수이고, 그래서 부등호 방향이 유지됩니다. 높이는 정수이므로 실제로 쓸 때는 $h \le \left\lfloor \log_t\frac{n+1}{2} \right\rfloor$로 읽으면 돼요. (밑을 $t-1$로 두는 형태도 있지만 그러면 $t=2$에서 $\log_1$이 되어 정의되지 않아요. 위 형태는 $t \ge 2$ 전 범위에서 안전합니다.)

이 프로젝트의 제약($n \le 10^4$)에 넣어 보면 이렇습니다. 두 열 모두 **간선 기준 높이**이고(방문 노드 수는 여기에 1을 더한 값입니다), 오른쪽 열은 $1$부터 $10^4$까지 중복 없이 순서대로 삽입한 뒤 루트에서 리프까지 내려가며 잰 실제 값이에요.

| $t$ | 노드당 키 수 | 상한식이 주는 최악 높이 | 1..10⁴ 삽입 실측 높이 |
|---|---|---|---|
| 2 | 1 ~ 3 | 12 | 12 |
| 3 | 2 ~ 5 | 7 | 7 |
| 10 | 9 ~ 19 | 3 | 3 |
| 100 | 99 ~ 199 | 1 | 1 |

$t=100$에서 높이가 1이 되는 것은 손으로도 검산됩니다 — 리프가 최대 $199$개의 키를 담고 루트가 자식을 최대 $200$개 가지므로, 한 층만으로 $199 \times 200 + 199 = 39{,}999$개까지 담을 수 있어서 $10^4$개는 여유롭게 들어가요.

**액션(연산)** — 이 가이드가 정의하는 인터페이스입니다. 중복은 무시하는 집합 의미론을 씁니다.

| 액션 | 시그니처 | 하는 일 | 비용 |
|------|----------|---------|------|
| `insert(value)` | `(value: T) => void` | 가득 찬 노드를 선제 분할하며 리프까지 내려가 삽입 | $O(t \log_t n)$ |
| `delete(value)` | `(value: T) => boolean` | 하한 미달을 선제 보충하며 내려가 삭제. 성공 여부 반환 | $O(t \log_t n)$ |
| `has(value)` | `(value: T) => boolean` | 루트부터 구간을 좁히며 하향 탐색 | $O(t \log_t n)$ |
| `size()` | `() => number` | 원소 개수 | $O(1)$ |
| `inOrder()` | `() => T[]` | 중위 순회로 정렬된 전체 배열 | $O(n)$ |

세 연산이 $O(t \log_t n)$인 이유는 이렇습니다. 높이가 $O(\log_t n)$이라 노드를 그만큼 방문하고, 노드 하나에서 최대 $2t-1$개의 키를 선형으로 훑으므로 노드당 $O(t)$가 듭니다. 노드 안에서 이진 탐색을 쓰면 앞서 계산했듯 전체가 $O(\log n)$이 되고요. 어느 쪽이든 **디스크 기준으로 진짜 중요한 값은 $\log_t n$(접근 횟수)** 이고, 노드 내부 비용은 메모리 안에서 벌어지는 일이라 훨씬 쌉니다.

구현 하나를 미리 밝혀 둘게요. 아래 코드의 `insert`와 `delete`는 시작하면서 `has(value)`를 부릅니다. 그래서 **알고리즘 자체는 한 번의 하향 패스로 끝나지만, 이 구현은 값이 존재할 때 경로를 두 번 탑니다.** 집합 의미론(중복 무시)을 단순하게 얻으려고 택한 구조인데, 접근 횟수가 곧 비용인 디스크 환경이라면 하향 중에 존재 여부까지 함께 판정해 한 번의 패스로 합치는 편이 낫습니다.

**핵심 연산 ① — 선제적 분할(`splitChild`).** $t=2$(노드당 최대 $2t-1=3$개)에서 가득 찬 리프를 쪼개는 장면입니다.

```text
Before: 가득 찬 노드 [1, 2, 3]   (2t-1 = 3개, 더 넣을 수 없다)

  중간 키(인덱스 t-1 = 1) = 2 를 부모로 승격
  왼쪽  = keys[0 .. t-2]   = [1]      (t-1 = 1개)
  오른쪽 = keys[t .. 2t-2]  = [3]      (t-1 = 1개)

After:          부모에 2 가 삽입된다
             [ ... , 2 , ... ]
              /            \
            [1]            [3]        ← 둘 다 정확히 하한 t-1 개
```

여기서 규칙 D의 계산이 눈에 보입니다 — $2t-1$에서 승격 1개를 빼면 $2(t-1)$이라, 두 조각이 **정확히 하한을 채운 채로** 태어나요.

**핵심 연산 ② — 하한 미달 보충(`fixup`).** 삭제 경로에서 다음에 내려갈 자식의 키가 $t-1$개(하한)임을 발견하면, **내려가기 전에** 먼저 채웁니다. 우선순위는 왼쪽 형제에게 빌리기 → 오른쪽 형제에게 빌리기 → 병합입니다.

```text
[빌리기] 오른쪽 형제에게 여유가 있을 때 (t=2)

Before:      부모 [ 2 ]                After:      부모 [ 3 ]
             /       \                             /       \
          [1]       [3, 4]                    [1, 2]      [4]
           ↑ 여기로 내려갈 참인데 1개뿐        ↑ 2개가 되어 안전하게 내려갈 수 있다

  부모 키 2 가 왼쪽 자식으로 내려가고, 형제의 첫 키 3 이 부모로 올라간다 (3자 순환)

[병합] 양쪽 형제 모두 하한이라 빌릴 수 없을 때 (t=2)

Before:      부모 [ 2 ]                After:      부모 [ ]
             /       \                              |
          [1]        [3]                        [1, 2, 3]
           ↑ 둘 다 1개뿐                         ↑ (t-1) + 1 + (t-1) = 2t-1 = 상한에 딱 맞는다
```

병합에서도 산술이 정확히 맞아떨어집니다 — $(t-1) + 1 + (t-1) = 2t-1$이라 **상한을 넘지 않아요.** 키 개수만 보면 분할과 병합은 서로를 되돌리는 계산이고(둘 다 경계에 딱 맞습니다), 이는 우연이 아니라 규칙 D에서 상한을 하한의 2배+1로 잡았기 때문입니다. 다만 자식 포인터 배치와 부모 문맥까지 포함하면 둘이 완전한 역연산은 아니에요 — 분할은 한 노드의 중앙 키를 위로 올리고, 병합은 부모 키를 아래로 내려 형제 둘을 합칩니다.

### 왜 모순 없이 작동하는가

**(1) 삽입이 크기 불변식을 지키는 이유 — 귀납.** 명제는 이겁니다.

> **P(삽입)**: `insertNonFull(node, v)`를 호출하는 시점에 `node`의 키는 항상 $2t-1$개 **미만**이고, 호출이 끝난 뒤에도 모든 노드가 불변식 1~4를 만족한다.

- *기저*: 루트에서 시작할 때, `insert`가 먼저 루트가 가득 찼는지 보고 가득 찼으면 새 루트를 만들어 분할합니다. 그러면 옛 루트는 $t-1$개짜리 두 조각이 되고 새 루트는 키 1개를 가지므로, 진입 시점에 루트는 확실히 가득 차 있지 않습니다.
- *단계*: `node`가 가득 차 있지 않다고 가정합시다(귀납 가정). 리프면 키를 하나 꽂는데, $|keys| \le 2t-2$였으므로 삽입 후에도 $\le 2t-1$이라 상한을 지킵니다. 리프가 아니면 내려갈 자식 $c$를 고르고, **$c$가 가득 찼는지 먼저 확인합니다.**
  - $c$가 가득 찼으면 분할합니다. 그 결과 두 조각은 각각 $t-1$개가 되고, 부모인 `node`는 키가 하나 늘어 $\le 2t-1$입니다(귀납 가정에서 $\le 2t-2$였으니까요). 이때 `node`가 상한 $2t-1$에 **딱 도달할 수는 있어도 넘지는 않습니다** — 이 호출 프레임은 자기 노드에 키를 더 넣지 않고 곧바로 자식으로 내려가기 때문에, `node`에 키가 추가되는 일은 이 분할 한 번뿐이거든요. 그다음 값과 승격된 키를 비교해 어느 조각으로 갈지 정합니다.
  - $c$가 가득 차지 않았으면 그대로 내려갑니다.
  - 어느 쪽이든 **다음 호출의 대상 노드는 가득 차 있지 않습니다** — 분할 직후라면 $t-1 \le 2t-2$이고($t \ge 2$이므로 $t-1 \le 2t-2 \iff t \ge 1$), 분할하지 않았다면 검사로 확인했으니까요. 이것이 P(삽입)의 가정을 다음 단계로 그대로 넘겨줍니다.

  이 귀납이 성립하는 덕분에 **분할 정보를 부모로 되돌려 보낼 일이 없습니다.** 부모는 자식이 쪼개지기 **전에** 이미 자리를 만들어 뒀거든요. 그래서 `insert`는 한 번 내려가기만 하는 `void` 함수가 됩니다.

**(2) 삭제가 크기 불변식을 지키는 이유 — 귀납.** 대칭인 명제를 씁니다.

> **P(삭제)**: `deleteHelper(node, v)`를 호출하는 시점에 `node`는 루트이거나 키를 $t$개 **이상** 갖고 있다.

이 명제가 왜 필요할까요? 노드에서 키를 하나 빼도 하한 $t-1$을 지키려면 빼기 **전에** $t$개 이상이어야 하기 때문입니다.

- *기저*: 루트에서 시작하고, 루트에는 하한이 없습니다(불변식 2).
- *단계*: 내려갈 자식 $c$의 키가 정확히 $t-1$개면 `fixup`이 먼저 채웁니다.
  - **왼쪽/오른쪽 형제에게 빌리기**: 형제가 $t$개 이상이었으므로 하나를 내줘도 $t-1$개 이상을 유지하고(하한 유지), $c$는 $t$개가 됩니다.
  - **병합**: 양쪽 형제가 모두 $t-1$개일 때만 합칩니다. 결과는 $(t-1) + 1 + (t-1) = 2t-1$개라 상한에 딱 맞고, $t \ge 2$이므로 $2t-1 \ge t$라 P(삭제)의 조건도 만족합니다.
  - 병합으로 부모는 키를 하나 잃습니다. 그래도 괜찮은 이유는 **부모가 이미 자기 차례에 $t$개 이상임을 보장받았기 때문**이에요(귀납 가정). 그래서 하나를 잃어도 $t-1$개 이상입니다. 루트가 부모인 경우에는 키가 0개가 될 수 있는데, 그때는 `delete`가 마지막에 루트를 유일한 자식으로 교체합니다 — 이것이 트리 높이가 줄어드는 **유일한** 경로예요.
  - 값이 내부 노드에서 발견된 경우: 왼쪽 자식이 $t$개 이상이면 그 서브트리의 최댓값(predecessor)으로 값을 덮고 그 최댓값을 다시 지우러 내려가고, 오른쪽이 $t$개 이상이면 최솟값(successor)으로 같은 일을 합니다. **둘 다 $t-1$개면 대체가 아니라 병합**이고, 병합된 노드로 다시 내려가 거기서 값을 지웁니다. 어느 갈래든 **다음 호출 대상이 $t$개 이상**이라(대체 갈래는 조건이 $\ge t$였고, 병합 결과는 $2t-1 \ge t$입니다) P(삭제)의 진입 조건이 그대로 이어집니다. 그 아래로 더 내려가는 동안에도 같은 선제 보충 논리가 반복 적용되므로, predecessor를 찾아 가장 오른쪽 경로를 타고 내려가는 중에 만나는 $t-1$개짜리 자식들도 `fixup`이 먼저 채워 줍니다.

**(3) 정렬 성질(불변식 5)이 유지되는 이유.** 세 연산 각각에서 키의 상대 순서를 따라가 봅시다.

```text
분할: [ ... k1 ... ]  부모의 i 번 자리에 중간 키 m 을 넣는다
      자식 = [a0 ... a_{t-2}] m [b0 ... b_{t-2}]   (원래 한 노드 안에서 정렬돼 있었다)
      → 왼쪽 조각의 모든 키 < m < 오른쪽 조각의 모든 키   (원래 순서 그대로)
      → 그리고 원래 자식 전체가 부모의 keys[i-1] 과 keys[i] 사이에 있었으므로
        m 도 그 사이에 있다 → 부모의 정렬도 유지된다

빌리기: 부모 키 p 가 자식으로 내려가고, 형제의 끝 키 s 가 p 자리로 올라간다
      (오른쪽 형제에서 빌릴 때)  자식의 모든 키 < p < s < 형제의 남은 키
      → 자식 끝에 p 를 붙이고 부모에 s 를 두면 순서가 그대로 성립한다

병합: 왼쪽 [a...] + 부모 키 p + 오른쪽 [b...]  →  [a... p b...]
      정렬 성질에 의해 이미 모든 a < p < 모든 b 였으므로 이어 붙이면 정렬 상태다
```

**(4) 모든 리프가 같은 깊이인 이유(불변식 6).** 세 연산 모두 깊이를 다루는 방식이 정해져 있습니다. 분할은 자식을 **같은 깊이의 형제**로 만들고, 병합은 같은 깊이의 형제 둘을 하나로 합칩니다 — 둘 다 리프의 깊이를 바꾸지 않아요. 깊이가 변하는 경우는 두 가지뿐입니다. 루트가 분할되면 새 루트가 위에 생겨 **모든** 리프가 동시에 1 깊어지고, 루트의 키가 0이 되어 유일한 자식으로 교체되면 **모든** 리프가 동시에 1 얕아집니다. 어느 쪽이든 전체가 함께 움직이므로 "모두 같은 깊이"가 깨지지 않습니다. 이것이 규칙 C가 실제로 지켜지는 메커니즘이에요.

여기서 확인 질문 하나 드릴게요. **$t=2$일 때 리프가 아닌 노드의 자식 수는 최소 몇 개, 최대 몇 개일까요?** 루트가 아닌 내부 노드는 키가 $t-1 \sim 2t-1$개이므로 자식은 그보다 하나 많은 $t \sim 2t$개, 즉 $t=2$면 **2개에서 4개**입니다. 그래서 $t=2$인 B-트리를 2-3-4 트리라고도 불러요. 단 **루트는 예외**입니다 — 불변식 2에 의해 키를 1개만 가질 수 있으므로 내부 루트의 자식 수 하한은 $t$가 아니라 $2$예요. 위 높이 유도에서 깊이 1의 노드 수를 $t$가 아니라 $2$로 잡은 것도 이 때문입니다.

**헷갈리기 쉬운 포인트** 세 가지를 짚어 둡니다.

- **"분할·보충은 넣은 뒤가 아니라 내려가기 전"입니다.** "일단 넣고 넘치면 그때 쪼개기"(사후 처리)도 동작은 합니다. 다만 그러면 분할 정보를 재귀 반환값으로 부모까지 계속 들고 올라와야 해요. 선제적 방식은 위 (1)의 귀납이 보증하듯 **부모가 미리 자리를 비워 두기 때문에** 그 배관 자체가 필요 없습니다.
- **"삭제는 항상 predecessor/successor로 대체된다"는 오해입니다.** 양쪽 자식이 모두 딱 $t-1$개면 빌려올 곳이 없어서 **병합**이 일어납니다. 아래 `delete(2)` 트레이스가 정확히 그 경우예요 — 왼쪽 `[1]`도 오른쪽 `[3]`도 1개뿐이라, 두 자식이 부모 키 `2`와 함께 `[1, 2, 3]`으로 합쳐집니다. 이때 `2`는 병합 과정에서 사라지는 게 아니라 **합쳐진 노드 안으로 내려간 것**이고, 코드는 그 노드로 다시 재귀해(`deleteHelper(left, value)`) 리프에서 `splice`로 제거합니다.
- **`rotateLeft`/`rotateRight`라는 이름이 회전처럼 보이지만, 실제로는 3자 순환입니다.** 노드가 통째로 도는 게 아니라 부모 키가 자식으로 **내려가고** 형제 키가 부모로 **올라갑니다.** 위 도식에서 부모가 `[2]`에서 `[3]`으로 바뀐 것이 그 증거예요 — 부모의 값 자체가 달라진다는 점을 놓치기 쉽습니다.

경계 상황도 점검해 둡시다. 아래 값은 모두 실행해서 확인한 결과입니다.

```text
빈 트리                    → has: false, delete: false, inOrder: [], size: 0
원소 1개                   → 루트 자신이 리프. insert(42) 후 [42], delete(42) 후 다시 빈 트리
중복 insert                → has 로 걸러 무시 (size 불변)
t < 2                      → 생성자가 예외를 던진다.
                              t=1 이면 하한 t-1 = 0, 상한 2t-1 = 1 이라
                              "키 0개 · 자식 1개" 노드가 허용된다 → 최소 분기 수가 1
                              → 위 높이 유도(n ≥ 2t^h - 1)의 전제가 무너져 로그 높이 보장이 사라진다
루트 붕괴 (t=2)            → insert(1..5):  루트 [2], 자식 [1], [3,4,5]
                              delete(4):     루트 [2], 자식 [1], [3,5]
                              delete(5):     루트 [2], 자식 [1], [3]
                              delete(1):     양쪽 자식 모두 t-1=1개 → 병합 →
                                             루트 자체가 리프 [2,3] 으로 붕괴 (높이 1 → 0)
```

## 아이디어를 코드로 옮기기

**원형과 개선.** 노드 분할·병합 규칙은 2-3 트리(키 최대 2개)에서 이미 알려진 것이고, 경계값만 $2t-1$로 일반화하면 그대로 통합니다. 갈리는 지점은 **분할·보충의 시점**이에요.

- **원형(사후 처리)**: 일단 자식에 넣고, 자식이 넘쳤으면 분할한 뒤 `{ 승격키, 오른쪽노드 }`를 부모에게 **반환**해서 부모가 자기 자리에 꽂게 합니다.

  ```ts
  // 원형 스케치 — 비교용이며 아래 최종 구현에는 쓰지 않습니다
  function insertPostSplit(node: BTreeNode<number>, x: number): { promoted: number; right: BTreeNode<number> } | undefined {
    // 1) 리프면 그 자리에 꽂고, 아니면 알맞은 자식으로 재귀
    // 2) 재귀가 돌려준 { promoted, right } 가 있으면 내 keys/children 에 꽂는다
    // 3) 그러다 내가 2t-1 개를 넘겼으면 나를 쪼개서 { promoted, right } 를 위로 돌려준다
    return undefined;
  }
  ```

  동작은 합니다. 대신 모든 재귀 프레임이 "위로 돌려줄 것이 있는지"를 확인해야 하고, 분할이 루트까지 연쇄될 수 있어 호출자 쪽 처리도 필요해요.

- **최종(선제적)**: 내려가기 **전에** 다음 자식이 가득 찼는지 보고 미리 쪼갭니다. 위 (1)의 귀납이 보증하듯 부모에는 항상 자리가 있으므로 반환값이 필요 없고, `insert`는 순수하게 한 번 내려가는 `void` 함수가 됩니다. 아래가 실제로 채택하고 검증한 구현입니다.

```ts
class BTreeNode<T> {
  keys: T[] = [];
  children: BTreeNode<T>[] = [];
  isLeaf = true;
}

export class BTree<T> {
  private root: BTreeNode<T> | undefined = undefined;
  private _size = 0;
  private t: number;
  private compare: (a: T, b: T) => number;

  constructor(t: number = 3, comparator?: (a: T, b: T) => number) {
    if (t < 2) throw new Error("t must be >= 2");
    this.t = t;
    this.compare = comparator ?? ((a, b) => (a < b ? -1 : a > b ? 1 : 0));
  }

  size(): number {
    return this._size;
  }

  has(value: T): boolean {
    return this.findNode(this.root, value) !== undefined;
  }

  private findNode(node: BTreeNode<T> | undefined, value: T): BTreeNode<T> | undefined {
    if (node === undefined) return undefined;
    let i = 0;
    while (i < node.keys.length && this.compare(value, node.keys[i]!) > 0) i++;
    if (i < node.keys.length && this.compare(value, node.keys[i]!) === 0) return node;
    if (node.isLeaf) return undefined;
    return this.findNode(node.children[i], value);
  }

  insert(value: T): void {
    if (this.has(value)) return; // 집합 의미론: 중복 무시

    if (this.root === undefined) {
      const root = new BTreeNode<T>();
      root.keys = [value];
      this.root = root;
      this._size = 1;
      return;
    }

    // 루트가 가득 찼으면 새 루트를 세우고 먼저 쪼갠다 — 높이가 자라는 유일한 지점
    if (this.root.keys.length === 2 * this.t - 1) {
      const oldRoot = this.root;
      const newRoot = new BTreeNode<T>();
      newRoot.isLeaf = false;
      newRoot.children = [oldRoot];
      this.splitChild(newRoot, 0);
      this.root = newRoot;
    }

    this.insertNonFull(this.root, value);
    this._size++;
  }

  private splitChild(parent: BTreeNode<T>, i: number): void {
    const t = this.t;
    const child = parent.children[i]!;
    const midKey = child.keys[t - 1]!;

    const right = new BTreeNode<T>();
    right.isLeaf = child.isLeaf;
    right.keys = child.keys.slice(t);
    if (!child.isLeaf) right.children = child.children.slice(t);

    child.keys = child.keys.slice(0, t - 1);
    if (!child.isLeaf) child.children = child.children.slice(0, t);

    parent.keys.splice(i, 0, midKey);
    parent.children.splice(i + 1, 0, right);
  }

  private insertNonFull(node: BTreeNode<T>, value: T): void {
    let i = node.keys.length - 1;
    if (node.isLeaf) {
      while (i >= 0 && this.compare(value, node.keys[i]!) < 0) i--;
      node.keys.splice(i + 1, 0, value);
      return;
    }
    while (i >= 0 && this.compare(value, node.keys[i]!) < 0) i--;
    i++;
    if (node.children[i]!.keys.length === 2 * this.t - 1) {
      this.splitChild(node, i);
      if (this.compare(value, node.keys[i]!) > 0) i++; // 분할 직후 어느 반쪽인지 다시 고른다
    }
    this.insertNonFull(node.children[i]!, value);
  }

  delete(value: T): boolean {
    if (this.root === undefined || !this.has(value)) return false;
    this.deleteHelper(this.root, value);
    if (this.root.keys.length === 0) {
      this.root = this.root.isLeaf ? undefined : this.root.children[0];
    }
    this._size--;
    return true;
  }

  private deleteHelper(node: BTreeNode<T>, value: T): void {
    const t = this.t;
    let i = 0;
    while (i < node.keys.length && this.compare(value, node.keys[i]!) > 0) i++;

    if (i < node.keys.length && this.compare(value, node.keys[i]!) === 0) {
      if (node.isLeaf) {
        node.keys.splice(i, 1);
        return;
      }
      const left = node.children[i]!;
      const right = node.children[i + 1]!;
      if (left.keys.length >= t) {
        const pred = this.maxKey(left);
        node.keys[i] = pred;
        this.deleteHelper(left, pred);
      } else if (right.keys.length >= t) {
        const succ = this.minKey(right);
        node.keys[i] = succ;
        this.deleteHelper(right, succ);
      } else {
        this.mergeChildren(node, i); // 양쪽 다 t-1개 → 대체가 아니라 병합
        this.deleteHelper(left, value);
      }
      return;
    }

    if (node.isLeaf) return; // has()로 걸렀으므로 실제로는 도달하지 않는다

    const child = node.children[i]!;
    if (child.keys.length === t - 1) {
      this.fixup(node, i);
      // fixup으로 부모의 키 배치와 자식 배열이 바뀌므로 값 기준으로 다시 고른다.
      // j는 0..node.keys.length 범위이고 자식 수는 keys.length + 1이라 항상 존재한다.
      let j = 0;
      while (j < node.keys.length && this.compare(value, node.keys[j]!) > 0) j++;
      this.deleteHelper(node.children[j]!, value);
    } else {
      this.deleteHelper(child, value);
    }
  }

  private fixup(node: BTreeNode<T>, i: number): void {
    const t = this.t;
    if (i > 0 && node.children[i - 1]!.keys.length >= t) {
      this.rotateRight(node, i);          // 왼쪽 형제에게 빌린다
    } else if (i < node.children.length - 1 && node.children[i + 1]!.keys.length >= t) {
      this.rotateLeft(node, i);           // 오른쪽 형제에게 빌린다
    } else if (i < node.children.length - 1) {
      this.mergeChildren(node, i);        // 오른쪽 형제와 병합
    } else {
      this.mergeChildren(node, i - 1);    // 막내라면 왼쪽 형제와 병합
    }
  }

  private rotateRight(node: BTreeNode<T>, i: number): void {
    const child = node.children[i]!;
    const leftSibling = node.children[i - 1]!;
    child.keys.unshift(node.keys[i - 1]!);
    node.keys[i - 1] = leftSibling.keys.pop()!;
    if (!child.isLeaf) child.children.unshift(leftSibling.children.pop()!);
  }

  private rotateLeft(node: BTreeNode<T>, i: number): void {
    const child = node.children[i]!;
    const rightSibling = node.children[i + 1]!;
    child.keys.push(node.keys[i]!);
    node.keys[i] = rightSibling.keys.shift()!;
    if (!child.isLeaf) child.children.push(rightSibling.children.shift()!);
  }

  private mergeChildren(node: BTreeNode<T>, i: number): void {
    const left = node.children[i]!;
    const right = node.children[i + 1]!;
    left.keys.push(node.keys[i]!, ...right.keys); // 왼쪽 + 부모 키 + 오른쪽 순서가 생명이다
    if (!left.isLeaf) left.children.push(...right.children);
    node.keys.splice(i, 1);
    node.children.splice(i + 1, 1);
  }

  private minKey(node: BTreeNode<T>): T {
    let cur = node;
    while (!cur.isLeaf) cur = cur.children[0]!;
    return cur.keys[0]!;
  }

  private maxKey(node: BTreeNode<T>): T {
    let cur = node;
    while (!cur.isLeaf) cur = cur.children[cur.children.length - 1]!;
    return cur.keys[cur.keys.length - 1]!;
  }

  inOrder(): T[] {
    const result: T[] = [];
    const walk = (node: BTreeNode<T> | undefined) => {
      if (node === undefined) return;
      for (let i = 0; i < node.keys.length; i++) {
        if (!node.isLeaf) walk(node.children[i]);
        result.push(node.keys[i]!);
      }
      if (!node.isLeaf) walk(node.children[node.keys.length]);
    };
    walk(this.root);
    return result;
  }
}
```

**가장 실수가 잦은 줄은 `insertNonFull`의 `if (this.compare(value, node.keys[i]!) > 0) i++;` 입니다.** 방금 분할한 자리에서 어느 반쪽으로 내려갈지 다시 고르는 분기예요. 이 줄이 없으면 어떻게 되는지 실제로 지워서 돌려 봤습니다. $t=2$에서 `1`부터 `7`까지 넣으면 이렇게 갈립니다.

```text
정상(줄 있음):                       버그(줄 없음):
     [ 2 , 4 ]                            [ 2 , 4 ]
    /    |    \                          /    |    \
 [1]   [3]  [5,6,7]                   [1]   [3,6]  [5,7]
                                              ↑ 6이 4보다 큰데 4의 왼쪽 자식에 들어갔다

inOrder() 정상: [1, 2, 3, 4, 5, 6, 7]     inOrder() 버그: [1, 2, 3, 6, 4, 5, 7]  ← 정렬이 깨졌다
has(6)   정상: true                        has(6)   버그: false  ← 넣었는데 못 찾는다
```

불변식 5(정렬 성질)가 깨지면 탐색이 조용히 거짓을 말합니다. `has(6)`은 "6은 4보다 크니 오른쪽" 규칙만 믿고 `[5, 7]`로 내려가 실패하는데, 정작 `6`은 트리 안에 멀쩡히 들어 있어요. **데이터는 있는데 못 찾는** 이 조합이 가장 잡기 어려운 종류의 버그입니다.

> 기억법: **쪼갠 다음엔 어느 쪽 반쪽인지 다시 확인한다.** 승격된 키와 한 번 더 비교하지 않으면, 방금 만든 경계를 무시하고 내려가게 된다.

`delete` 쪽에서 가장 실수가 잦은 곳은 `mergeChildren`의 붙이는 **순서**입니다. `left.keys.push(node.keys[i]!, ...right.keys)`처럼 **부모 키를 먼저, 오른쪽 키들을 그다음**에 붙여야 해요. 순서를 바꿔 `push(...right.keys, node.keys[i]!)`로 쓰면 어떻게 되는지도 돌려 봤습니다.

```text
t=2, 1..7 삽입 후 delete(2)

정상:  루트 [4],  자식 [1, 3]  [5, 6, 7]     inOrder: [1, 3, 4, 5, 6, 7]
버그:  루트 [4],  자식 [1, 3, 2] [5, 6, 7]   inOrder: [1, 3, 2, 4, 5, 6, 7]
                        ↑ 부모 키 2가 맨 뒤에 붙어 노드 내부 정렬이 깨졌다
```

노드 안이 `[1, 3, 2]`처럼 어긋나면 `while` 비교로 자리를 찾는 탐색·삽입이 전부 어긋납니다. 여기서도 결과는 "터지지 않고 조용히 틀린 답"이에요.

한 가지 더. `delete`의 마지막 세 줄, 루트의 키가 0개가 되면 유일한 자식으로 갈아 끼우는 부분을 빼면 어떻게 될까요? `t=2`에서 `1..5`를 넣고 `4, 5, 1`을 지우면 **키가 하나도 없는 빈 루트가 `[2, 3]` 위에 남습니다.** 탐색은 여전히 답을 내지만(빈 루트를 지나 자식으로 내려가니까요), 불변식 2가 깨진 상태로 트리가 계속 자라면서 접근 횟수만 늘어나는 유령 층이 쌓입니다.

정리하면, B-트리는 "노드 하나가 곧 접근 단위(페이지) 하나"라는 대응 하나로 이진 트리의 문제를 통째로 옮겨 풀었습니다. 노드를 꽉 채워 분기 수를 키웠고(규칙 A), 페이지를 넘지 않도록 상한을 두고 분할했으며(규칙 B), 리프 깊이를 고르게 하려고 위로 자라게 했고(규칙 C), 분기 수가 보장되도록 하한을 두어 빌리기·병합을 넣었습니다(규칙 D). 그 결과 삽입·삭제·탐색이 모두 $O(t \log_t n)$이고, 디스크 기준으로 진짜 중요한 접근 횟수는 $\log_t n$입니다 — $n = 10^4$에서 $t=10$이면 높이 3, $t=100$이면 1이라는 것을 상한식과 실측으로 확인했어요. 구현에서는 두 가지만 정확히 지키면 됩니다. **분할 직후 자식 인덱스를 다시 고를 것**, 그리고 **병합에서 부모 키를 가운데에 끼울 것.**

이 글의 수치는 모두 위 코드를 그대로 스크래치 파일로 추출해 실행한 결과입니다. 검증은 이렇게 했어요 — 고정 시드 난수로 $0$부터 $299$ 사이의 값을 뽑아 60% 확률로 삽입, 40% 확률로 삭제를 $8{,}000$번 섞어 돌리고, **매 연산마다** 불변식 여섯 줄을 전부 검사하는 함수(키 개수 상·하한, 자식 수 = 키 수 + 1, 노드 내부 정렬, 부모 키를 경계로 한 구간 조건, 리프 깊이 일치)를 호출했습니다. 동시에 같은 연산을 표준 `Set`에도 적용해 두고, `inOrder()`가 그 `Set`을 정렬한 결과와 매번 일치하는지, `size()`가 `Set`의 크기와 같은지, `delete()`의 반환값이 `Set.delete()`와 같은지를 대조했습니다. $t = 2, 3, 5$ 세 경우 모두 위반 0건이었어요.
