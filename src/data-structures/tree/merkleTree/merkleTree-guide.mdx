# 머클 트리 (Merkle Tree) — 루트 하나로 전체를, 형제 해시 몇 개로 하나를

## 한눈에 보는 컨셉

머클 트리는 데이터 블록들을 각각 해시로 감싸고, 그 해시 두 개를 이어붙여 다시 해싱하는 과정을 루트 노드 하나가 남을 때까지 반복하는 이진 트리예요. 비결은 "전체를 대변하는 요약값(루트 해시)"과 "블록 하나만 증명하는 데 필요한 정보(루트까지 가는 길의 형제 해시들)"를 분리한 것입니다. 리프가 $n$개면 트리 높이가 $O(\log n)$이라, 특정 블록이 트리에 포함됐는지 확인하는 데 전체 데이터가 아니라 딱 $O(\log n)$개의 해시만 있으면 충분해요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 머클 트리를 떠올리세요.

- 전체 데이터를 갖고 있지 않은 쪽(경량 클라이언트, 원격 피어, 캐시 서버)이 "이 항목이 원본에 포함돼 있는가"만 검증하고 싶다
- 데이터셋이 자주 갱신되는데, 매번 전체를 다시 훑어 무결성을 확인하기엔 비용이 크다
- 위·변조를 조기에 감지해야 하는데, 원본 전체를 매번 전송하거나 저장할 여유가 없다

가장 단순한 대안은 전체 블록을 한꺼번에 해싱하는 것입니다. 이 방식은 블록 하나를 검증하는 데도 전체 $n$개 블록이 필요해요.

```text
naive: 전체를 이어붙여 한 번 해싱     검증 비용 O(n)    -- 블록 1개만 확인해도 n개 전부 필요
merkle: 트리로 구성해 둔다            구성 O(n) 1회,  이후 증명·검증은 O(log n)
```

비슷한 목적의 다른 구조와 헷갈릴 수 있어요. **Bloom Filter**는 "포함될 수도 있다"는 확률적 답만 주고 거짓 양성이 있는 대신 공간이 훨씬 작습니다. **평문 해시 리스트**(각 블록의 해시를 그냥 배열로 나열)는 구현이 단순하지만 증명 크기가 $O(n)$이라 경량 클라이언트에겐 부담이에요. 즉, **위조 불가능한 정확한 포함 증명이 필요하고 그 증명 크기를 $O(\log n)$으로 눌러야 한다면 머클 트리**를, 근사 멤버십으로 충분하면 Bloom Filter를, 증명 자체가 필요 없고 단순함이 우선이면 해시 리스트를 선택합니다.

### 문제 사례와 적용 예시

- **비트코인/이더리움의 SPV(경량) 노드**: 블록 헤더에는 트랜잭션 전체의 머클 루트만 담겨 있고, 특정 트랜잭션이 블록에 포함됐는지는 $O(\log n)$개의 형제 해시(머클 증명)만으로 검증합니다.
- **분산 데이터베이스의 anti-entropy 복구**(Cassandra, DynamoDB 계열): 두 복제본의 머클 트리를 루트부터 비교해 나가면, 값이 다른 서브트리만 골라내 그 부분만 데이터를 주고받으면 됩니다. 전체를 비교할 필요가 없어요.
- **콘텐츠 주소 기반 저장소**(IPFS, Git의 객체 트리): 데이터 자체가 아니라 그 해시로 콘텐츠를 식별하고, 중간 노드의 해시가 하위 콘텐츠 전체를 요약합니다.
- **코딩 테스트 맥락**: "블록 배열이 주어지고, 특정 인덱스의 블록이 위조되지 않았음을 $O(\log n)$ 크기의 증명으로 검증하는 자료구조를 구현하라" 유형으로 직접 등장합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드는 포인터 없이 **1-based 배열**로 완전 이진 트리를 표현하는 인터페이스를 정의합니다. 캐시 친화적이고 인덱스 계산이 간단해서예요.

```ts
class MerkleTree {
  private tree: string[];     // 1-based 배열. tree[0]은 사용하지 않는다
  private leafCount: number;  // n 이상인 최소 2의 거듭제곱
  private n: number;          // 원본 블록 개수(패딩 전)
}
```

지켜야 할 불변식은 다섯 가지예요.

1. **배열 크기**: $|\text{tree}| = 2 \cdot \text{leafCount}$, 여기서 $\text{leafCount} = 2^{\lceil \log_2 n \rceil}$ (n 이상인 최소 2의 거듭제곱).
2. **인덱스 관계**: 노드 $i$의 왼쪽 자식은 $2i$, 오른쪽 자식은 $2i+1$, 부모는 $\lfloor i/2 \rfloor$ ($i \geq 1$).
3. **리프 해시**: $0 \le i < n$이면 $\text{tree}[\text{leafCount}+i] = H(\text{blocks}[i])$. $n \le i < \text{leafCount}$이면 $\text{tree}[\text{leafCount}+i] = \text{tree}[\text{leafCount}+n-1]$ — 홀수라서 남는 자리는 **마지막 리프를 복제**해 채운다.
4. **내부 노드 해시**: $1 \le i < \text{leafCount}$이면 $\text{tree}[i] = H(\text{tree}[2i] \,\Vert\, \text{tree}[2i+1])$ (단, $\Vert$는 문자열 이어붙이기이고 **왼쪽이 항상 앞**에 온다).
5. **루트**: $\text{rootHash()} = \text{tree}[1]$.

$n = 4$일 때 인덱스를 직접 그려 보면 이렇습니다.

```text
인덱스:        1                ← 루트 = rootHash()
             /   \
            2     3             ← 내부 노드
           / \   / \
          4   5 6   7           ← 리프 (leafCount=4, 원본 블록 0..3)

tree[4] = H(blocks[0])    tree[5] = H(blocks[1])
tree[6] = H(blocks[2])    tree[7] = H(blocks[3])
tree[2] = H(tree[4] + tree[5])
tree[3] = H(tree[6] + tree[7])
tree[1] = H(tree[2] + tree[3])    ← 루트
```

**액션(연산)** — 이 가이드가 정의한 인터페이스 5종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(blocks)` | 리프 해시 계산 → bottom-up으로 내부 노드까지 트리 전체 구성 | $O(n)$ |
| `rootHash()` | `tree[1]` 반환 | $O(1)$ |
| `getProof(index)` | 해당 리프에서 루트까지 올라가며 형제 해시를 수집 | $O(\log n)$ |
| `verify(index, block, proof)` | `block`을 재해싱한 뒤 `proof`로 루트까지 재계산해 일치 여부 확인 | $O(\log n)$ |
| `update(index, newBlock)` | 해당 리프만 재계산하고, 루트 방향 조상 체인만 재계산 | $O(\log n)$ |

핵심 연산 세 개를 자세히 볼게요. 대표 예시로 `blocks = ["tx1", "tx2", "tx3", "tx4"]`를 씁니다(모든 값은 실제 SHA-256을 실행해 얻은 값이고, 지면 관계상 앞 6자만 적습니다).

```text
h0 = SHA256("tx1") = 709b55...   h1 = SHA256("tx2") = 27ca64...
h2 = SHA256("tx3") = 1f3cb1...   h3 = SHA256("tx4") = 41b637...
n1 = SHA256(h0+h1) = f8f28e...   n2 = SHA256(h2+h3) = 850cf3...
root = SHA256(n1+n2) = 773bc3...
```

**① `getProof(0)` — 형제만 골라 담는다.** 리프 0(=배열 인덱스 4)에서 시작해 부모로 올라가며, 매 층에서 "나와 짝을 이루는 형제"의 해시만 담습니다. 짝을 찾는 공식은 $\text{sibling}(p) = p \oplus 1$(XOR)입니다 — 인덱스 4와 5, 6과 7처럼 부모가 같은 두 자식은 이진수 마지막 한 비트만 다르기 때문에, 그 비트를 뒤집으면 바로 형제가 나옵니다.

```text
Before: pos = leafCount + 0 = 4 (아직 아무것도 수집하지 않음)

1단계: sibling = 4 ⊕ 1 = 5 → tree[5](h1=27ca64) 수집, pos = ⌊4/2⌋ = 2
2단계: sibling = 2 ⊕ 1 = 3 → tree[3](n2=850cf3) 수집, pos = ⌊2/2⌋ = 1 → pos=1이므로 종료

After: proof = [27ca64, 850cf3]
```

**② `verify(0, "tx1", proof)` — 같은 길을 거슬러 다시 계산한다.** `block`을 해싱한 값에서 시작해, `proof`의 형제 해시를 매 층 이어붙이며 재해싱합니다. 이때 **내가 왼쪽 자식(짝수 인덱스)인지 오른쪽 자식(홀수 인덱스)인지에 따라 이어붙이는 순서가 바뀝니다** — 불변식 4가 "왼쪽이 항상 앞"이라고 정했기 때문이에요.

```text
Before: current = SHA256("tx1") = 709b55, pos = 4(짝수 → 내가 왼쪽)

1단계(pos=4, 짝수): current = SHA256(current + h1) = SHA256(709b55+27ca64) = f8f28e, pos = 2
2단계(pos=2, 짝수): current = SHA256(current + n2)  = SHA256(f8f28e+850cf3) = 773bc3, pos = 1 → 종료

After: current(773bc3) == rootHash()(773bc3) → true
```

**③ `update(1, "tx2-new")` — 조상 체인만 다시 계산한다.** 리프 하나만 바뀌었어도, 그 리프를 포함하는 모든 조상 노드는 값이 달라져야 정직한 요약이 유지됩니다. 조상은 최대 $\log n$개뿐이므로 재계산 비용도 $O(\log n)$에 그칩니다.

```text
Before: tree[5](h1)=27ca64   tree[2](n1)=f8f28e   tree[1](root)=773bc3
        tree[3](n2)=850cf3는 이번 update와 무관 — 그대로

update(1, "tx2-new")를 적용하면:
  tree[5] = SHA256("tx2-new") = 75aff7      ← 리프 자신
  tree[2] = SHA256(tree[4] + tree[5]) = fb8c8c   ← 부모
  tree[1] = SHA256(tree[2] + tree[3]) = 7cb8e7   ← 루트

After: tree[5]=75aff7, tree[2]=fb8c8c, tree[1](root)=7cb8e7 (773bc3 → 7cb8e7로 변경)
       tree[3], tree[6], tree[7]은 인덱스 1의 조상 경로 밖이라 손대지 않는다
```

### 왜 모순 없이 작동하는가

**루트가 항상 정직한 요약인 이유**는 귀납으로 보일 수 있어요. 리프는 정의상(불변식 3) 자기 블록의 정직한 해시입니다. 내부 노드는 정의상(불변식 4) 두 자식의 정직한 해시고요. 트리 높이만큼 이 귀납을 반복하면, 루트는 "모든 리프를 정해진 순서로 조합해 해싱한 값"이 됩니다. 해시 함수의 충돌 저항성 덕분에 이 조합을 다르게 만들 수 있는 입력을 찾는 것은 사실상 불가능하므로, 루트 하나가 바뀌면 최소 하나의 리프가 바뀐 것이고, 어떤 리프도 안 바뀌었다면 루트도 그대로입니다.

**증명이 항상 옳은 답을 내는 이유**는 `getProof`와 `verify`가 **완전히 같은 인덱스 계산 규칙**(`pos = leafCount + index`로 시작해서 `pos = ⌊pos/2⌋`로 올라가기)을 공유하기 때문입니다. `getProof`가 층마다 실제로 존재하는 형제 노드를 담아 왔으므로, `verify`가 그 형제들을 같은 순서로 재해싱하면 트리 구성 때와 완전히 동일한 계산을 재현하게 되고, 결과가 `tree[1]`과 같아지는 건 당연한 귀결이에요.

여기서 헷갈리기 쉬운 포인트 세 가지를 짚어 둘게요.

- **이어붙이는 순서를 홀짝과 무관하게 고정하면 안 됩니다.** $H(a \Vert b) \ne H(b \Vert a)$이므로(해시 함수는 순서에 민감합니다), 왼쪽 자식일 때 `current + sibling`, 오른쪽 자식일 때 `sibling + current`로 정확히 나눠야 트리 구성 때의 계산과 일치합니다. 구체적으로 어떻게 틀어지는지는 아래 "함정" 절에서 실측 값으로 보여드릴게요.
- **홀수 패딩과 "진짜 중복 트랜잭션"을 구분해야 합니다.** 리프가 홀수 개일 때 마지막 리프를 복제해 짝수로 맞추는 규칙 자체가 함정입니다 — 원래 리프가 3개인 트리(패딩으로 자동 복제된 트리)와, 실제로 세 번째 트랜잭션이 통째로 한 번 더 들어와 리프가 4개가 된 트리가 **완전히 같은 루트 해시**를 만들어냅니다. 비트코인 초기 구현이 이 허점(CVE-2012-2459)으로 실제 공격을 받았어요. 실무에서는 리프 개수를 트리와 별도로 커밋하거나, 패딩 여부를 명시적으로 구분해 막습니다.
- **`update` 이후에는 이전에 발급한 `proof`가 무효가 될 수 있습니다.** 조상 체인이 재계산되면서 형제로 쓰였던 노드의 값 자체가 바뀔 수 있기 때문이에요. 아래에서 직접 확인해 봅시다 — `update(1, "tx2-new")` 이후에 인덱스 0의 예전 `proof`로 `verify(0, "tx1", oldProof)`를 부르면 어떤 값이 나올까요? 형제였던 `tree[5]`가 `27ca64`에서 `75aff7`로 바뀌었으니, 예전 `proof`는 더 이상 실제 트리 상태와 맞물리지 않아 **`false`가 나옵니다.** 인덱스 0의 증명을 다시 받으려면 `getProof(0)`을 새로 호출해야 해요.

엣지 케이스도 점검해 둘게요.

```text
빈 배열                → new MerkleTree([])는 에러를 던진다 ("blocks must not be empty")
블록 1개 (n=1)          → leafCount=1이라 내부 노드 계산 루프가 아예 안 돈다
                         rootHash() = H(blocks[0]) 그 자체, getProof(0) = [] (형제가 없다)
홀수 블록 (n=3)          → leafCount=4, 인덱스 3 리프는 인덱스 2 리프의 복제(H(blocks[2]))
큰 패딩 (n=5)            → leafCount=8, 인덱스 5,6,7 리프 모두 인덱스 4 리프의 복제 (패딩 3개)
```

잠깐, 확인 하나만 해 볼까요? 블록이 5개면 `leafCount`는 몇일까요? 답: $2^{\lceil \log_2 5 \rceil} = 8$이고, 패딩되는 리프는 $8 - 5 = 3$개예요(인덱스 5, 6, 7이 모두 인덱스 4의 복제).

## 아이디어를 코드로 옮기기

가이드가 정의한 인터페이스(1-based 배열, `leafCount`, `n`)에 맞춰 그대로 구현합니다. 해시 함수는 Bun 내장 `Bun.CryptoHasher`로 SHA-256을 계산해요.

```ts
function sha256(data: string): string {
  const hasher = new Bun.CryptoHasher("sha256");
  hasher.update(data);
  return hasher.digest("hex");
}

function nextPowerOfTwo(n: number): number {
  let p = 1;
  while (p < n) p *= 2;
  return p;
}

class MerkleTree {
  private tree: string[];
  private leafCount: number;
  private n: number;

  constructor(blocks: string[]) {
    if (blocks.length === 0) throw new Error("blocks must not be empty");
    this.n = blocks.length;
    this.leafCount = nextPowerOfTwo(this.n);
    this.tree = new Array(2 * this.leafCount).fill("");

    for (let i = 0; i < this.n; i++) {
      this.tree[this.leafCount + i] = sha256(blocks[i]!);
    }
    for (let i = this.n; i < this.leafCount; i++) {
      this.tree[this.leafCount + i] = this.tree[this.leafCount + this.n - 1]!; // 마지막 리프 복제 패딩
    }
    for (let i = this.leafCount - 1; i >= 1; i--) {
      this.tree[i] = sha256(this.tree[2 * i]! + this.tree[2 * i + 1]!); // 왼쪽이 항상 앞
    }
  }

  rootHash(): string {
    return this.tree[1]!;
  }

  getProof(index: number): string[] {
    let pos = this.leafCount + index;
    const proof: string[] = [];
    while (pos > 1) {
      proof.push(this.tree[pos ^ 1]!); // XOR 트릭으로 형제 인덱스
      pos = pos >> 1;
    }
    return proof;
  }

  verify(index: number, block: string, proof: string[]): boolean {
    let current = sha256(block);
    let pos = this.leafCount + index;
    for (const sibling of proof) {
      current = pos % 2 === 0 ? sha256(current + sibling) : sha256(sibling + current);
      pos = pos >> 1;
    }
    return current === this.rootHash();
  }

  update(index: number, newBlock: string): void {
    let pos = this.leafCount + index;
    this.tree[pos] = sha256(newBlock);
    pos = pos >> 1;
    while (pos >= 1) {
      this.tree[pos] = sha256(this.tree[2 * pos]! + this.tree[2 * pos + 1]!);
      pos = pos >> 1;
    }
  }
}
```

가장 중요한 부분은 `getProof`와 `verify`가 **똑같은 `pos = leafCount + index` 출발점과 `pos = pos >> 1` 이동 규칙**을 공유한다는 것입니다. 이 두 함수가 서로 다른 인덱스 계산을 쓰면, 증명은 올바르게 수집됐어도 검증이 엉뚱한 층을 재구성해 절대 맞물리지 않아요.

놓치기 쉬운 구현 지점들을 짚어 둡니다.

- `pos % 2 === 0 ? sha256(current + sibling) : sha256(sibling + current)` — **이 삼항 연산자 한 줄이 전체 정확성을 결정합니다.** 순서를 홀짝과 무관하게 고정하면 트리 구성 때와 다른 계산이 되어 정당한 블록도 검증에 실패해요.
- `this.tree[pos ^ 1]` — XOR 트릭은 짝수 인덱스엔 `+1`, 홀수 인덱스엔 `-1`로 작동해 형제를 O(1)에 찾습니다. `pos + 1`로 잘못 쓰면 홀수 인덱스에서 엉뚱한(자기 자신 다음) 노드를 형제로 착각합니다.
- `update` 이후 재계산 루프의 시작이 `pos >> 1`(리프 자신이 아니라 **부모부터**)이라는 점 — 리프는 이미 위에서 갱신했으니 중복 계산을 피합니다.
- `update`가 끝난 뒤 예전에 발급한 `proof`는 재사용할 수 없다는 점(위 절에서 실측으로 확인했어요). 새 `getProof`를 다시 호출해야 합니다.

**함정**: 이어붙이는 순서를 홀짝 구분 없이 항상 `sibling + current`로 고정한 잘못된 `verify`를 같은 트리·같은 `proof`로 돌리면 어떻게 될까요? 정상 구현은 최종 해시로 `773bc3`(=루트, 일치)을 내지만, 순서를 고정한 잘못된 구현은 `d92fcb`를 내서 루트와 어긋나 `verify`가 `false`를 반환합니다 — **정당한 블록인데도 검증에 실패하는 거짓 음성**이 발생하는 겁니다.

> 왼쪽 자식이면 내가 앞, 오른쪽 자식이면 내가 뒤 — 짝을 이어붙일 땐 항상 "내 자리"를 기억한다.
