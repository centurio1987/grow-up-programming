# Order Statistic Tree — 노드마다 크기 하나만 얹으면 순위가 보인다

## 한눈에 보는 컨셉

Order Statistic Tree는 정수의 동적 다중 집합을 유지하면서 "$k$번째로 작은 값은?"(`kth`)과 "이 값보다 작은 원소가 몇 개인가?"(`rank`)에 빠르게 답하는 자료구조예요. 비결은 딱 하나, 균형 이진 탐색 트리(BST)의 각 노드에 **자기 서브트리에 원소가 몇 개 있는지**(`size`)를 저장해 두는 것뿐입니다. 이 필드 하나 덕분에 중위 순회 없이 루트에서 한 번의 하향 탐색만으로 삽입·삭제·`kth`·`rank` 네 연산 모두 기대 $O(\log n)$에 처리할 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 Order Statistic Tree를 떠올리세요.

- 정수(또는 비교 가능한 값)를 계속 **삽입·삭제**하면서 정렬 순서를 유지해야 한다
- "$k$번째 원소"나 "이 값의 순위(더 작은 원소 개수)"를 **반복 조회**해야 한다
- 값의 범위가 넓어서($|x| \leq 10^9$ 같은 제약) 배열 인덱스로 직접 셀 수 없다

정렬 배열은 `kth`·`rank`를 이진 탐색으로 $O(\log n)$에 답하지만, 삽입·삭제 때마다 뒤 원소를 밀어야 해서 $O(n)$이 듭니다. 반대로 `size` 필드가 없는 일반 BST는 삽입·삭제는 $O(\log n)$(균형 가정)이지만, `kth`나 `rank`를 구하려면 중위 순회로 트리 전체를 훑어야 해 $O(n)$이 됩니다. 즉 "삽입·삭제가 빠른 것"과 "순서 통계가 빠른 것"이 서로 시소처럼 부딪히는 상황인데, `size` 필드 하나가 이 시소를 끊어 줍니다.

```text
                  insert/delete      kth/rank
정렬 배열              O(n)            O(log n)
일반 BST(균형)      O(log n)             O(n)      ← 시소 관계
Order Statistic Tree  O(log n)         O(log n)    ← size 필드로 둘 다 해결
```

값의 범위가 좁고 미리 알 수 있다면(예: $1 \leq x \leq 10^5$가 사전에 확정) 좌표 압축 + Fenwick Tree(BIT)로도 같은 문제를 풀 수 있고 상수도 더 작습니다. 하지만 값이 동적으로 늘어나거나 범위가 넓어 좌표 압축이 어려우면 Order Statistic Tree(Treap이나 AVL 위에 `size`를 얹은 구조)를 선택하세요.

### 문제 사례와 적용 예시

- **실시간 리더보드**: $10^5$명의 점수가 계속 갱신되는 순위표에서 "현재 $k$등의 점수는?"과 "이 점수의 현재 순위는?"을 매 갱신마다 $O(\log n)$에 응답합니다.
- **온라인 저지 채점 순위**: 참가자가 점수를 제출·취소할 때마다 특정 등수의 점수나 특정 점수의 등수를 실시간으로 알려줘야 하는 시스템입니다(이 가이드의 문제 상황).
- **경쟁 프로그래밍의 `ordered_set`**: C++ PBDS(policy-based data structure)의 `order_of_key`/`find_by_order`가 바로 이 자료구조의 표준 라이브러리 버전입니다.
- **코딩 테스트 맥락**: 삽입·삭제가 섞인 스트림에서 "중앙값 유지", "$k$번째 최댓값 추적" 류의 문제가 이 구조로 직결됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드 하나는 이렇게 생겼습니다.

```ts
class OSTNode {
  key: number;
  priority: number;      // 균형 유지용 무작위 우선순위 (Treap)
  size: number;           // 자기 서브트리에 있는 원소 개수
  left: OSTNode | null = null;
  right: OSTNode | null = null;
}
```

트리 전체로는 `root: OSTNode | null` 하나만 유지합니다. 지켜야 할 불변식은 세 가지예요.

1. **BST 순서**: 왼쪽 서브트리의 모든 키 $\leq$ 현재 노드의 키 $\leq$ 오른쪽 서브트리의 모든 키. (동일 키는 왼쪽으로 정렬 — 이유는 바로 아래에서 다룹니다.)
2. **힙 순서(Treap)**: 부모의 `priority` $\geq$ 자식의 `priority`. 무작위 `priority`가 이 조건을 지키도록 회전(여기서는 `split`/`merge`)하면서 트리가 통계적으로 균형을 이룹니다.
3. **크기 불변식**: 모든 노드 $v$에서 다음이 성립합니다.

$$\text{size}(v) = \text{size}(\text{left}(v)) + \text{size}(\text{right}(v)) + 1, \qquad \text{size}(\text{null}) = 0$$

값 `{1, 3, 4, 5, 7, 8, 9}`를 담은 트리를 그려 보면:

```text
              5 (size=7)
            /            \
      3 (size=3)        8 (size=3)
      /       \          /       \
1 (size=1)  4 (size=1) 7 (size=1) 9 (size=1)

각 노드 옆 size는 "나를 포함한 내 서브트리의 원소 개수"
루트의 size=7 = 전체 원소 개수와 항상 같다
```

**액션(연산)** — 이 자료구조가 제공하는 전부입니다.

| 액션 | 하는 일 | 비용(기대) |
|------|---------|------|
| `insert(x)` | $x$를 삽입(중복 허용) | $O(\log n)$ |
| `delete(x)` | $x$를 하나만 삭제(없으면 무시) | $O(\log n)$ |
| `kth(k)` | 정렬 순서 $k$번째($1$-기반) 값 반환 | $O(\log n)$ |
| `rank(x)` | $x$보다 엄격히 작은 원소 개수 반환 | $O(\log n)$ |

핵심 연산 두 개를 자세히 볼게요.

**① `kth(k)` — 왼쪽 서브트리 크기로 방향을 정한다.** 현재 노드의 왼쪽 서브트리 크기를 $ls$라 하면:

$$\text{kth}(v, k) = \begin{cases} \text{kth}(\text{left}(v), k) & k \leq ls \\ v.key & k = ls + 1 \\ \text{kth}(\text{right}(v), k - ls - 1) & k > ls + 1 \end{cases}$$

```text
Before(탐색 전): kth(root=5, k=5)를 구하고 싶다
  root 5의 ls = size(left=3) = 3
  k=5 > ls+1=4 이므로 오른쪽으로, k' = 5-3-1 = 1

After(한 걸음 이동): kth(노드8, k=1)로 범위가 절반 이하로 줄어들었다
```

**② `rank(x)` — 왼쪽 전체 + 자신을 조건부로 누적한다.**

$$\text{rank}(v, x) = \begin{cases} 0 & v = \text{null} \\ \text{rank}(\text{left}(v), x) & x \leq v.key \\ \text{size}(\text{left}(v)) + 1 + \text{rank}(\text{right}(v), x) & x > v.key \end{cases}$$

```text
Before: rank(root=5, x=7) — 아직 누적값 0
  x=7 > key=5 이므로 "왼쪽 전체 + 나" = size(left=3)+1 = 4 를 누적, 오른쪽으로

After: rank(노드8, x=7) — 누적값 4를 들고 내려간다
```

**균형 유지**: `split(node, x)`는 노드를 "키 $\leq x$"와 "키 $> x$" 두 서브트리로 쪼개고, `merge(a, b)`는 ($a$의 모든 키 $\leq$ $b$의 모든 키라는 전제로) 우선순위 힙 조건을 지키며 두 서브트리를 하나로 합칩니다. `insert`는 새 노드의 무작위 `priority`가 기존 노드보다 크면 그 자리에서 `split`으로 새 루트가 되고, 아니면 더 내려가 재귀합니다. `delete`는 찾은 노드의 두 자식을 `merge`로 이어 붙여 그 자리를 메웁니다. 두 함수 모두 구조를 바꾼 노드에서 반드시 `pullUp`(=`size` 재계산)을 호출합니다.

### 왜 모순 없이 작동하는가

**크기 불변식이 항상 유지되는 이유**: `insert`·`delete`가 구조를 바꾸는 지점은 오직 `split`·`merge`·재귀 대입 세 곳뿐이고, 이 세 곳 모두 자식을 다시 연결한 직후 `pullUp`을 호출합니다. `pullUp`은 "왼쪽 크기 + 오른쪽 크기 + 1"을 그 자리에서 다시 계산하므로, 자식 쪽 크기가 이미 옳다면(귀납 가정) 부모 쪽 크기도 즉시 옳아집니다. 리프 노드는 생성 시 `size = 1`로 시작하므로 귀납의 기초도 성립합니다. 따라서 어떤 연산 시퀀스 뒤에도 크기 불변식은 깨지지 않습니다.

**`kth` 정당성**: 왼쪽 서브트리 크기가 $ls$일 때, BST 순서상 왼쪽 서브트리에는 정확히 작은 쪽 $ls$개가 모여 있습니다. $k \leq ls$면 답은 왼쪽 안에 있고, $k = ls+1$이면 그 경계가 바로 현재 노드이며, $k > ls+1$이면 왼쪽 $ls$개와 현재 노드를 제외한 나머지에서 $(k-ls-1)$번째를 오른쪽에서 찾으면 됩니다. 세 경우가 배타적이고 전체를 덮으므로 항상 유일한 답에 도달합니다.

**`rank` 정당성**: $x > v.key$이면 왼쪽 서브트리의 모든 원소와 현재 노드까지 총 $\text{size}(\text{left})+1$개가 확실히 $x$보다 작으므로 누적하고 오른쪽으로 계속합니다. $x \leq v.key$이면 현재 노드와 오른쪽 서브트리는 전부 $\geq v.key \geq x$이므로 카운트에서 제외하고 왼쪽만 봅니다.

여기서 헷갈리기 쉬운 포인트는 **중복 키의 방향 일치**입니다. `insert`는 "새 키 $\leq$ 기존 키면 왼쪽"으로 내려가고(즉 동일 값은 왼쪽에 쌓입니다), `split`도 "키 $\leq x$는 왼쪽 부분"으로 나눕니다. `rank`도 "$x \leq v.key$면 왼쪽"으로 내려갑니다. 세 규칙의 동점 처리 방향이 전부 "왼쪽"으로 통일되어 있지 않으면, 예를 들어 `insert`는 동점을 오른쪽으로 보내는데 `rank`는 왼쪽만 보고 내려간다면 — 오른쪽에 숨어 있는 동일 키 사본들을 아예 못 만나 카운트가 틀어지거나, 반대로 자기 자신과 값이 같은 원소를 실수로 세어 버릴 수 있습니다. 이 프로젝트의 구현은 세 곳 모두 "$\leq$는 왼쪽"으로 통일해 이 문제를 피합니다.

엣지 케이스를 점검해 봅니다.

```text
빈 트리에서 rank(x)         → 0 (재귀 기저 조건에서 바로 반환)
원소 1개 트리에서 kth(1)    → 그 원소 자신
원소 1개 트리에서 rank(자기 자신) → 0 (자기 자신은 "더 작은" 원소가 아니다)
중복 삽입 후 delete 1회      → 나머지 사본은 그대로 유지 (delete는 첫 매치 1개만 제거)
존재하지 않는 값 delete      → 트리 변화 없음 (재귀가 null까지 내려가 조용히 끝남)
음수·큰 값 혼합               → key 비교만으로 동작하므로 부호·크기에 무관
```

잠깐, 확인 하나만 해 볼까요? $S = \{1, 3, 5\}$일 때 `rank(4)`는 얼마일까요? $4$는 집합에 없지만 `rank`는 "얼마나 존재하냐"가 아니라 "얼마나 작냐"를 묻는 연산이므로, $4$보다 작은 원소 $\{1, 3\}$ 두 개를 세어 **2**를 반환합니다.

## 아이디어를 코드로 옮기기

**원형(naive)**: `size` 필드는 있지만 균형을 신경 쓰지 않는 순수 BST부터 시작해 볼게요.

```ts
class NaiveNode {
  key: number;
  size = 1;
  left: NaiveNode | null = null;
  right: NaiveNode | null = null;
  constructor(key: number) { this.key = key; }
}
function naiveInsert(node: NaiveNode | null, x: number): NaiveNode {
  if (node === null) return new NaiveNode(x);
  if (x <= node.key) node.left = naiveInsert(node.left, x);
  else node.right = naiveInsert(node.right, x);
  node.size = (node.left?.size ?? 0) + (node.right?.size ?? 0) + 1;
  return node;
}
```

`kth`·`rank`는 앞서 본 점화식 그대로 얹으면 되니 정확성에는 문제가 없습니다. 하지만 여기엔 **함정**이 있습니다. $1, 2, \dots, 1000$을 오름차순으로 삽입하면 매번 "기존 최댓값보다 크다"는 이유로 계속 오른쪽으로만 붙어, 트리가 한 줄짜리 사슬이 됩니다. 실제로 이 코드로 $n=1000$을 오름차순 삽입해 높이를 재면 **정확히 1000**이 나옵니다 — $\log_2 1000 \approx 10$이어야 할 높이가 $n$과 같아진 겁니다. 이 상태에서 `kth`·`rank`는 $O(\log n)$이 아니라 $O(n)$이 되어, $q=10^5$번 질의하면 목표했던 $1.7\times10^6$ 대신 $10^5 \times 1000 = 10^8$에 근접하는 연산이 걸립니다.

**개선(최종)**: 무작위 `priority`를 얹은 Treap으로 만들면, 삽입 순서가 무엇이든 트리 모양이 그 순서에 매이지 않고 우선순위의 무작위성에 좌우됩니다. 같은 $n=1000$ 오름차순 삽입을 Treap으로 실행하면 높이가 **21**로 나옵니다(측정값) — $\log_2 1000 \approx 10$의 약 2배 이내로, naive의 1000에 비해 극적으로 낮습니다.

```ts
class OSTNode {
  key: number;
  priority: number;
  size: number;
  left: OSTNode | null = null;
  right: OSTNode | null = null;
  constructor(key: number) {
    this.key = key;
    this.priority = Math.random();
    this.size = 1;
  }
}

function sz(node: OSTNode | null): number {
  return node ? node.size : 0;
}
function pullUp(node: OSTNode): void {
  node.size = sz(node.left) + sz(node.right) + 1;
}

// split(node, x): key <= x 인 것들(left)과 key > x 인 것들(right)로 분리
function split(node: OSTNode | null, x: number): [OSTNode | null, OSTNode | null] {
  if (node === null) return [null, null];
  if (node.key <= x) {
    const [l, r] = split(node.right, x);
    node.right = l;
    pullUp(node);
    return [node, r];
  } else {
    const [l, r] = split(node.left, x);
    node.left = r;
    pullUp(node);
    return [l, node];
  }
}

// merge(a, b): a의 모든 키 <= b의 모든 키라는 전제 하에 힙 조건을 지키며 합친다
function merge(a: OSTNode | null, b: OSTNode | null): OSTNode | null {
  if (a === null) return b;
  if (b === null) return a;
  if (a.priority > b.priority) {
    a.right = merge(a.right, b);
    pullUp(a);
    return a;
  } else {
    b.left = merge(a, b.left);
    pullUp(b);
    return b;
  }
}

function insertNode(node: OSTNode | null, newNode: OSTNode): OSTNode {
  if (node === null) return newNode;
  if (newNode.priority > node.priority) {
    const [l, r] = split(node, newNode.key);
    newNode.left = l;
    newNode.right = r;
    pullUp(newNode);
    return newNode;
  }
  if (newNode.key <= node.key) node.left = insertNode(node.left, newNode);
  else node.right = insertNode(node.right, newNode);
  pullUp(node);
  return node;
}

function deleteNode(node: OSTNode | null, x: number): OSTNode | null {
  if (node === null) return null;
  if (x < node.key) {
    node.left = deleteNode(node.left, x);
    pullUp(node);
    return node;
  }
  if (x > node.key) {
    node.right = deleteNode(node.right, x);
    pullUp(node);
    return node;
  }
  return merge(node.left, node.right); // x == node.key: 이 노드를 제거
}

function kth(node: OSTNode | null, k: number): number {
  if (node === null) throw new Error("k out of range");
  const ls = sz(node.left);
  if (k <= ls) return kth(node.left, k);
  if (k === ls + 1) return node.key;
  return kth(node.right, k - ls - 1);
}

function rank(node: OSTNode | null, x: number): number {
  if (node === null) return 0;
  if (x <= node.key) return rank(node.left, x);
  return sz(node.left) + 1 + rank(node.right, x);
}

class OrderStatisticTree {
  private root: OSTNode | null = null;

  insert(x: number): void {
    this.root = insertNode(this.root, new OSTNode(x));
  }
  delete(x: number): void {
    this.root = deleteNode(this.root, x);
  }
  kth(k: number): number {
    return kth(this.root, k);
  }
  rank(x: number): number {
    return rank(this.root, x);
  }
}
```

가장 중요한 부분은 `insertNode`의 우선순위 비교 한 줄입니다.

- **`if (newNode.priority > node.priority)`** — 새 노드의 우선순위가 더 높으면 그 자리에서 `split`으로 새 루트가 됩니다. 이 조건을 빼먹고 항상 아래로만 내려가며 삽입하면 원형(naive)과 똑같은 사슬 트리로 퇴화합니다. **무작위 `priority` + 이 비교 한 줄이 균형의 전부입니다.**
- **`merge`의 `a.priority > b.priority` 분기** — 삭제 후 두 자식을 이어 붙일 때도 힙 조건을 지키는 쪽이 위로 올라와야, 삭제를 반복해도 트리가 다시 사슬로 무너지지 않습니다.
- **`split`·`rank`·`insertNode`의 동점 처리(`<=`)가 전부 "왼쪽"으로 통일**되어야 앞서 짚은 중복 키 카운트 오류를 피합니다.

> 기억법: "우선순위가 이기면 내가 루트, 지면 내가 자식."
