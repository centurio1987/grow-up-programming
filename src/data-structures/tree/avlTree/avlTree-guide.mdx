# AVL Tree — 완벽한 균형을 포기하고, "한 칸 차이"까지만 허용하기

## 한눈에 보는 컨셉

AVL 트리는 이진 탐색 트리(BST)의 정렬 규칙을 그대로 지키면서, 모든 노드에서 왼쪽·오른쪽 서브트리의 **높이 차이가 1을 넘지 않도록** 삽입·삭제마다 스스로 교정하는 자기 균형 트리예요. 비결은 "완벽한 균형"을 목표로 삼지 않는 것입니다 — 한 칸까지의 어긋남은 눈감아 주는 대신, 두 칸이 되는 순간 **회전**이라는 상수 시간 수선으로 되돌립니다(삽입은 그런 자리가 많아야 한 곳, 삭제는 조상 체인을 따라 여러 곳일 수 있는데, 이 차이도 뒤에서 증명과 실측으로 다룹니다). 그 덕분에 탐색·삽입·삭제가 최악의 입력에서도 항상 $O(\log n)$을 지킵니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 AVL 트리를 떠올리세요.

- 정렬 순서를 계속 유지해야 하는데, 삽입·삭제가 **빈번하게 섞여서** 들어온다
- 입력이 이미 정렬된 순서로 들어올 수 있고, **최악의 경우에도** $O(\log n)$을 보장해야 한다
- 값 하나를 찾는 것뿐 아니라 **최솟값·최댓값·정렬된 전체 목록**도 함께 필요하다
- 삽입·삭제보다 **조회가 압도적으로 많다** — AVL은 균형 기준이 엄격해서 트리가 더 납작하고, 그만큼 조회가 조금 더 빠릅니다

원소 $n = 10^4$개를 다룬다고 할 때, 이 요구를 후보 구조들이 각각 어떻게 감당하는지 먼저 비교해 두겠습니다. 아래 표의 "정렬 입력" 열이 이 자료구조가 태어난 이유예요.

```text
n = 10,000 기준. * 표시는 실제로 돌려서 잰 값이다.

                   탐색 1회        삽입 1회           min/max/정렬 목록   1..n 을 순서대로
                                                                          넣었을 때 탐색
정렬 배열          비교 14회       원소 이동 5,000회   즉시 / O(n)         비교 14회
정렬 연결 리스트   비교 5,000회    연결 1회            즉시 / O(n)         비교 5,000회
해시맵             해시 1회        해시 1회            지원 안 함          해시 1회
단순 BST           *평균 15.39회*  *평균 15.39회*      O(log n) / O(n)     *평균 5,000.5회*
AVL 트리           *평균 12.56회*  *평균 12.56회*+회전 O(log n) / O(n)     *평균 12.36회*
                                                                           ↑ 여기서 갈린다
(단순 BST·AVL 의 "탐색 1회" 열은 무작위 순서로 넣었을 때의 평균 비교 횟수다.)
```

> **레드블랙 트리와의 선택 기준**: 조회가 압도적으로 많으면 AVL을 고릅니다 — 균형 기준이 더 엄격해 트리가 더 낮고, 그만큼 비교 횟수가 적어요. 갱신이 잦다면 레드블랙 트리 쪽이 유리한데, 그 이유는 "회전이 무조건 적어서"가 아닙니다(삽입만 보면 최악 회전 수는 오히려 레드블랙이 더 많습니다). 진짜 차이는 **삭제**에 있어요 — 뒤에서 보겠지만 AVL의 삭제는 회전이 조상 체인을 따라 $O(\log n)$번까지 연쇄될 수 있는 반면, 레드블랙은 재균형의 상당 부분을 회전 없는 **색 변경(recoloring)** 으로 처리하고 삭제의 회전 수가 상수(최대 3회)로 묶입니다. 균형 기준을 얼마나 느슨하게 잡느냐가 왜 이런 차이를 만드는지는 다음 절에서 숫자로 봅니다.

### 문제 사례와 적용 예시

- **원조 자기 균형 트리**: 1962년 Adelson-Velsky와 Landis가 고안한, 세계 최초의 자기 균형 BST입니다. 이후 재균형 비용이 더 싼 레드블랙 트리가 여러 표준 라이브러리의 기본 선택지가 됐지만, 조회가 압도적으로 많은 워크로드에서는 지금도 AVL이 선택됩니다.
- **랭킹판·리더보드**: 점수가 계속 삽입·삭제되는 와중에도 항상 정렬된 순서(중위 순회)로 상위권을 뽑아내야 하는 상황.
- **구간 이벤트 스케줄러**: 시작 시각 순으로 정렬을 유지하면서 이벤트가 수시로 추가·취소되는 경우. 시각은 **거의 정렬된 순서로 들어오기 때문에** 단순 BST가 가장 잘 무너지는 입력이기도 합니다.
- **코딩 테스트 맥락**: `insert`·`delete`·`has`·`min`·`max`·`inOrder`를 모두 지원하는 정렬 컨테이너를 직접 구현해야 하는 문제. JS/TS에는 정렬 상태를 유지하는 내장 컨테이너가 없습니다.

## 왜 이 모양이어야 하는가

완성된 AVL 트리를 설명하기 전에, **AVL 트리를 모른 채 같은 요구를 만났다면 무엇을 만들었을지**부터 따라가 봅시다. 그 설계들이 어디서 무너지는지를 봐야, 뒤에 나올 불변식이 "외워야 할 규칙"이 아니라 "그렇게 될 수밖에 없었던 결론"으로 읽힙니다.

### 순진한 설계와 그 실패

요구사항은 이겁니다: **정렬 순서를 유지하면서 삽입·삭제·탐색·최소·최대·전체 나열을 모두 지원할 것.** $n \le 10^4$입니다.

**후보 ① 정렬 배열.** 가장 먼저 떠오르는 답입니다. 이진 탐색으로 $\lceil \log_2 10^4 \rceil = 14$번 비교면 값을 찾고, 최솟값·최댓값은 양 끝이라 즉시 나오고, 전체 나열은 그냥 배열 그 자체예요. 탐색만 보면 흠잡을 데가 없습니다.

무너지는 곳은 **삽입**입니다. 배열 한가운데에 값을 끼워 넣으려면 뒤쪽 원소를 전부 한 칸씩 밀어야 해요.

```text
[10, 20, 30, 40, 50] 에 25 삽입
        ↓ 삽입 위치는 이진 탐색으로 14번 비교면 찾는다 (빠름)
[10, 20, __, 30, 40, 50]
            ←──────────  30,40,50 을 한 칸씩 뒤로 (이게 비싸다)

n = 10^4 에서 평균 이동량 = n/2 = 5,000개
탐색 14회 : 이동 5,000회  →  이동이 350배 비싸다
```

**후보 ② 정렬 연결 리스트.** "그럼 이동이 필요 없는 연결 리스트로 바꾸자"가 자연스러운 다음 수입니다. 실제로 삽입 자체는 포인터 두 개만 고치면 끝나요. 그런데 이번에는 **어디에 넣을지 찾는 일**이 무너집니다. 연결 리스트는 임의 접근이 안 되니까 이진 탐색을 쓸 수 없고, 앞에서부터 순서대로 따라가야 해요.

```text
정렬 배열        : 탐색 14회      + 이동 5,000회
정렬 연결 리스트 : 탐색 5,000회   + 이동 0회
                        ↑ 비용이 사라진 게 아니라 옮겨 갔을 뿐이다
```

**후보 ③ 해시맵.** 점 조회만 보면 상수 시간이라 두 후보를 압도합니다. 하지만 해시맵은 **순서를 아예 버리는 구조**예요. `min()`·`max()`·`inOrder()`를 지원하려면 매 호출마다 전체를 훑거나 정렬해야 합니다 — $n\log_2 n \approx 1.3 \times 10^5$번의 비교가 호출 한 번마다 듭니다. 요구사항 목록의 절반을 못 채우니 후보에서 탈락이에요.

**후보 ④ 단순 이진 탐색 트리.** 여기서 방향이 잡힙니다. 트리는 "찾는 일"과 "넣는 일"을 **같은 경로 한 번**으로 처리해요 — 내려가면서 위치를 찾고, 도착한 자리에 매달면 끝입니다. 후보 ①·②가 겪은 "한쪽이 싸지면 다른 쪽이 비싸지는" 시소가 여기서 끊깁니다.

문제는 트리의 **모양**이 입력 순서에 좌우된다는 점이에요. 값 $1$부터 $n$까지를 순서대로 넣어 보면 이렇게 됩니다.

```text
1,2,3,4,5 를 순서대로 삽입한 단순 BST

1
 \
  2
   \
    3
     \
      4
       \
        5     ← 매번 오른쪽으로만 내려간다. 사실상 연결 리스트다.
```

실제로 돌려서 잰 값입니다. 아래 절의 본문 코드를 그대로 스크래치 파일로 추출해 단순 BST 구현과 나란히 실행했고, 무작위가 필요한 측정에는 고정 시드를 썼습니다.

```text
1..n 을 순서대로 삽입한 뒤, 모든 값을 한 번씩 탐색했을 때 평균 비교 횟수

n = 1,000    단순 BST: 높이 1,000     평균 500.5회    최악 1,000회
             AVL     : 높이 10        평균 8.99회     최악 10회

n = 10,000   단순 BST: 높이 10,000    평균 5,000.5회  최악 10,000회
             AVL     : 높이 14        평균 12.36회    최악 14회
                                         ↑ 404배 차이

(여기 적힌 AVL 높이 14는 "1..n 을 이 순서로 넣었을 때 나온 실제 높이"다.
 모든 AVL 트리를 통틀어 n=10^4 에서 가능한 최악 높이는 18이며, 뒤에서 유도한다.)
```

여기서 중요한 것은 **이 실패가 우연이 아니라 구조적**이라는 점입니다. 트리를 사슬로 만드는 입력은 정렬된 입력, 역정렬된 입력, 거의 정렬된 입력인데 — 자동 증가 ID, 타임스탬프, 이미 정렬된 파일에서 읽어 들인 데이터처럼 **자주 마주치는 패턴이 정확히 그 모양**입니다. 무작위 입력에서 평균이 좋다는 사실이 이 패턴을 막아 주지 못한다는 게 문제예요. "평균은 좋은데 최악이 나쁘다"가 아니라, **최악이 흔하다**는 뜻입니다.

**후보 ⑤ 매번 높이가 최소가 되게 다시 짓기.** 모양이 문제라면 모양을 강제하면 되지 않을까요? 삽입할 때마다 트리를 중위 순회로 펼치고(BST의 중위 순회는 이미 정렬된 순서라 따로 정렬할 필요가 없습니다 — $O(n)$입니다), 가운데 값을 루트로 삼아 재귀적으로 다시 세우는 겁니다. 높이는 항상 최소인 $\lceil \log_2 (n+1) \rceil$가 됩니다 — 이 방법의 탐색 성능은 이론상 최고예요.

대신 삽입 한 번에 **트리 전체**를 건드립니다.

```text
삽입 1회 비용 = 현재 노드 수 n  (전부 펼쳐서 전부 다시 매단다)

1..10,000 을 순서대로 삽입할 때 총 노드 방문 수
  = 1 + 2 + ... + 10,000 = 50,005,000회   (≈ n²/2)

같은 입력에서 AVL 의 총 회전 횟수 = 9,986회
```

원소 하나 넣자고 5,000만 번을 움직이는 셈이니, 후보 ①의 "이동 5,000회"보다 오히려 나빠졌습니다.

### 실패가 가리키는 설계 규칙

다섯 번의 실패가 각각 무엇을 알려 줬는지 한 줄씩 정리하고, 거기서 규칙을 뽑아내겠습니다.

**관찰 ①: 비용을 결정하는 것은 값이 아니라 트리의 "높이"다.** 후보 ④에서 탐색 비용은 정확히 뿌리부터 잎까지의 깊이였습니다. 그러니 목표는 하나로 좁혀집니다 — **높이를 $\log n$의 상수 배로 묶어라.**

**관찰 ②: 그런데 "높이 최소"를 불변식으로 삼으면 국소 수선이 불가능해진다.** 후보 ⑤가 비쌌던 이유는 "높이가 최소"라는 조건이 **트리 전체를 한꺼번에 보는 전역 조건**이기 때문이에요. 노드 하나만 늘어도 어느 값이 가운데인지가 바뀌므로, 루트부터 다시 정해야 합니다.

> 규칙 A: **균형을 느슨하게 정의한다.** 어긋남을 조금 허용하는 대신, 어긋남이 생긴 자리 근처만 고쳐서 원상복구할 수 있게 만든다.

**그럼 얼마나 느슨해도 되는가?** 이 질문에 답하려면 거꾸로 세어 봐야 합니다 — "높이 $h$짜리 트리가 가질 수 있는 **최소** 노드 수 $N(h)$"가 $h$에 대해 **지수적으로** 커지면, 노드 $n$개를 담을 때 높이는 $\log n$ 규모에 묶입니다. 반대로 $N(h)$가 천천히 커지면(극단적으로 $N(h)=h$인 사슬처럼) 높이가 폭발하죠.

높이 차 허용치를 $k$로 두고 $N_k(h)$를 실제로 세어 봤습니다. 높이 $h$를 만들려면 한쪽 자식이 높이 $h-1$이어야 하고, 반대쪽은 허용치를 꽉 채워 $h-1-k$까지 낮출 수 있으므로

$$
N_k(h) = 1 + N_k(h-1) + N_k(h-1-k), \qquad N_k(j) = 0 \ \ (j \le 0)
$$

입니다. 인덱스가 $0$ 이하로 내려가면 그 자식은 아예 없는 것이니 $0$으로 셉니다.

```text
k=1 (|높이차| ≤ 1)   N: 0,1,2,4,7,12,20,33,...    n=10^4 일 때 최악 높이 18
k=2 (|높이차| ≤ 2)   N: 0,1,2,3,5,8,12,18,...     n=10^4 일 때 최악 높이 23
k=3 (|높이차| ≤ 3)   N: 0,1,2,3,4,6,9,13,...      n=10^4 일 때 최악 높이 27
```

셋 다 여전히 $O(\log n)$입니다. **즉 "1"은 필연이 아니라 선택이에요.** 허용치를 키우면 트리가 높아지는 대신 재균형이 덜 일어나고, 줄이면 반대가 됩니다. AVL은 이 저울에서 **가장 엄격한 쪽 끝**을 택했고, 레드블랙 트리는 같은 저울의 느슨한 쪽을 택했습니다(색 규칙에서 "가장 긴 루트–리프 경로 ≤ 가장 짧은 경로의 2배"가 따라 나옵니다). 앞 절의 선택 기준이 바로 이 표에서 나옵니다.

허용치를 $0$으로 두는 것은 아예 불가능해요. $k=0$은 "모든 노드에서 두 자식의 높이가 정확히 같다"는 뜻인데, 노드가 2개인 트리만 봐도 한쪽 자식은 높이 1, 반대쪽은 높이 0이라 이미 위반입니다. 노드 수가 $2^h - 1$ 꼴이 아니면 **만족시킬 수 있는 트리 자체가 없어요.** 즉 $k=0$은 "비싼 불변식"이 아니라 **불변식이 될 수 없는 조건**입니다. (후보 ⑤가 지킨 것은 "높이가 최소"라는 더 약한 조건이었고, 그건 만족 가능하지만 전역 조건이라 비쌌던 거예요.)

**관찰 ③: 삽입 한 번은 딱 한 칸만 어긋나게 만든다.** 새 노드는 리프로 매달리므로, 그 경로 위 노드들의 높이는 **많아야 1** 늘어납니다. 어긋남이 1까지 허용된 상태에서 한 칸이 더해지면 최악이 2예요. **깨짐의 크기가 항상 "허용치보다 딱 한 칸 초과"로 제한된다**는 뜻입니다.

> 규칙 B: 깨짐의 크기가 상수로 제한되므로, **상수 시간짜리 수선 연산 한 종류**면 충분하다. (수선 자체는 $O(1)$이지만, 삭제에서는 그 수선이 조상마다 반복될 수 있습니다 — 왜 삽입과 삭제가 다른지는 뒤에서 계산합니다.)

**관찰 ④: 수선은 정렬 순서를 절대 건드리면 안 된다.** 우리가 지키려는 것은 애초에 BST 규칙이었습니다. 그러니 수선 연산은 "중위 순회 결과를 그대로 둔 채 부모–자식 관계만 바꾸는" 것이어야 해요. 그 조건을 만족하는 가장 작은 연산이 바로 **회전**입니다.

```text
          y                            x
         / \      ─ 오른쪽 회전 →      / \
        x   T3                       T1  y
       / \        ← 왼쪽 회전 ─          / \
     T1   T2                          T2  T3

중위 순회:  T1  x  T2  y  T3      (회전 전)
            T1  x  T2  y  T3      (회전 후 — 완전히 같다)
```

**관찰 ⑤: 높이를 그때그때 재는 것은 너무 비싸다.** 균형 여부를 판정하려면 양쪽 서브트리의 높이를 알아야 하는데, 높이를 매번 다시 재면 서브트리 전체를 훑어 $O(n)$이 듭니다. 삽입 하나에 $O(n)$이면 후보 ⑤와 다를 게 없어요.

> 규칙 C: **높이를 노드에 저장하고**, 변경된 경로에서만 갱신한다. 갱신은 자식이 확정된 뒤 부모 순서(아래에서 위로)여야 한다.

여기까지 오면 세 가지 규칙이 그대로 **세 가지 불변식**이 됩니다. 그래서 이 구조는 다음을 불변식으로 갖습니다 — ⓐ 모든 노드에서 BST 정렬 규칙, ⓑ 모든 노드에서 두 자식의 높이 차가 1 이하, ⓒ 모든 노드의 `height` 필드가 실제 높이와 일치. 다음 절은 이 셋을 정식으로 적는 것부터 시작합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 규칙 C에 따라, 노드마다 자기 서브트리의 높이를 직접 들고 있습니다.

```ts
class AVLNode<T> {
  value: T;
  left: AVLNode<T> | undefined = undefined;
  right: AVLNode<T> | undefined = undefined;
  height: number = 1;   // 이 노드를 루트로 하는 서브트리의 높이
}
```

트리 전체로는 `root`, 원소 수 `_size`, 비교 함수 `comparator`를 유지합니다. 앞 절에서 유도한 불변식을 정식으로 적으면 이렇습니다. 빈 자리(노드 없음)의 높이는 $0$, 리프의 높이는 $1$로 셉니다.

1. **BST 규칙**: 모든 노드 $v$에서, 왼쪽 서브트리의 모든 값 $x$에 대해 $x < v.\text{value}$이고 오른쪽 서브트리의 모든 값 $y$에 대해 $v.\text{value} < y$. 서브트리가 비어 있으면 조건은 자동으로 성립합니다. 부등호가 엄격하다는 것은 같은 값이 두 번 들어오지 않는다는 뜻이고, 그래서 `insert`가 중복을 걸러 냅니다 — `comparator`가 $0$을 돌려주는 두 값은 **같은 원소로 취급**됩니다.
2. **균형 인수 불변식**: 모든 노드 $v$에서

$$
bf(v) = h(v.\text{left}) - h(v.\text{right}), \qquad |bf(v)| \le 1
$$

3. **높이 필드의 정확성**: 모든 노드 $v$에서 $v.\text{height} = 1 + \max(h(v.\text{left}),\, h(v.\text{right}))$.

`5, 3, 7, 1, 4, 6, 8`을 순서대로 넣으면(뒤 코드 절의 구현을 그대로 실행해 얻은 결과입니다) 균형 인수가 전부 $0$인 이상적인 모양이 나옵니다.

```text
                5 (h=3, bf=0)
              /               \
       3 (h=2, bf=0)        7 (h=2, bf=0)
       /        \            /        \
  1(h=1,bf=0) 4(h=1,bf=0) 6(h=1,bf=0) 8(h=1,bf=0)

inOrder() = [1, 3, 4, 5, 6, 7, 8]   height() = 3   min() = 1   max() = 8
```

**액션(연산)** — 이 가이드가 정의하는 인터페이스입니다. `insert`는 중복을 무시하는 집합(set) 의미론을 씁니다.

| 액션 | 시그니처 | 하는 일 | 비용 |
|------|----------|---------|------|
| `insert(value)` | `(value: T) => void` | BST 규칙으로 삽입 후 조상 체인을 거슬러 올라오며 재균형 | $O(\log n)$, 재균형 최대 1회(= `rotate` 호출 1~2번) |
| `delete(value)` | `(value: T) => boolean` | BST 규칙으로 삭제(두 자식이면 중위 후계자로 교체) 후 재균형. 성공 여부 반환 | $O(\log n)$, 재균형 최대 $O(\log n)$회 |
| `has(value)` | `(value: T) => boolean` | 일반 BST 탐색 | $O(\log n)$ |
| `min()` / `max()` | `() => T \| undefined` | 가장 왼쪽 / 오른쪽으로 끝까지 이동 | $O(\log n)$ |
| `inOrder()` | `() => T[]` | 중위 순회 결과 배열 | $O(n)$ |
| `size()` | `() => number` | 내부 카운터 반환 | $O(1)$ |
| `height()` | `() => number` | 루트의 `height` 필드 반환 | $O(1)$ |

두 가지를 표에 붙여 둡니다. 첫째, `insert`와 `delete`의 재균형 횟수가 다릅니다 — 이 차이는 뒤 "왜 모순 없이 작동하는가"에서 계산으로 확인합니다. 둘째, `min()`·`max()`가 $O(\log n)$인 이유는 한쪽 방향으로만 내려가는 경로 길이가 트리 높이를 넘을 수 없고, 그 높이가 $O(\log n)$으로 묶여 있기 때문이에요(바로 아래에서 유도합니다).

**높이가 정말 $O(\log n)$인지 — 끝까지 유도하기.** 앞 절에서 $N(h)$가 지수적으로 커지면 높이가 묶인다고 했는데, 그 "지수적"을 증명 없이 넘기지 않겠습니다. 네 단계로 갑니다.

**1단계 — 점화식.** $N(h)$를 "높이가 정확히 $h$이면서 불변식 2를 지키는 트리의 최소 노드 수"라고 둡시다. 높이가 $h$이려면 루트의 자식 중 적어도 하나는 높이 $h-1$이어야 합니다(그래야 루트가 $h$가 되니까요). 반대쪽 자식은 노드를 최대한 아끼고 싶은데, 불변식 2 때문에 $h-2$보다 더 낮출 수는 없습니다. 그러므로

$$
N(h) = N(h-1) + N(h-2) + 1, \qquad N(0) = 0,\quad N(1) = 1
$$

마지막 $+1$은 루트 자신입니다. 실제로 세어 보면 $N(2)=2,\ N(3)=4,\ N(4)=7,\ N(5)=12,\ N(6)=20$이고, $h=4$의 최소 트리는 이렇게 생겼어요(높이 3짜리 왼쪽 + 높이 2짜리 오른쪽).

```text
h=4 인데 노드가 7개뿐인 트리 (이보다 적을 수 없다)

            5 (h=4, bf=1)
          /            \
     3 (h=3, bf=1)    7 (h=2, bf=1)
     /       \          /
2 (h=2, bf=1) 4       6
  /
1
```

**2단계 — 피보나치와 같은 수열임을 확인.** 피보나치 수를 $F(1)=1,\ F(2)=1,\ F(k)=F(k-1)+F(k-2)$로 두면, 주장은 $N(h) = F(h+2) - 1$입니다. 귀납으로 확인합시다.

- *기저*: $N(1) = 1 = F(3) - 1 = 2 - 1$. $N(2) = 2 = F(4) - 1 = 3 - 1$. 둘 다 맞습니다.
- *단계*: $h \ge 3$에서 $N(h-1) = F(h+1)-1$, $N(h-2) = F(h)-1$이라고 가정하면
  $N(h) = (F(h+1)-1) + (F(h)-1) + 1 = F(h+1)+F(h) - 1 = F(h+2)-1$.

**3단계 — 피보나치 수가 지수적으로 커진다는 것 자체를 증명.** 황금비 $\varphi = \frac{1+\sqrt5}{2} \approx 1.618$은 $\varphi > 1 > 0$인 양수이고 $\varphi^2 = \varphi + 1$을 만족합니다($\varphi^2 = \frac{3+\sqrt5}{2} = 1 + \frac{1+\sqrt5}{2}$이니까요). 양수라는 점은 뒤에서 부등식 양변에 $\varphi$의 거듭제곱을 곱하거나 나눌 때 부등호 방향이 유지되는 근거로 쓰입니다. 이 두 성질만으로 $F(k) \ge \varphi^{\,k-2}$를 귀납 증명할 수 있어요.

- *기저*: $F(1) = 1 \ge \varphi^{-1} \approx 0.618$, $F(2) = 1 \ge \varphi^{0} = 1$. 둘 다 성립합니다.
- *단계*: $k \ge 3$에서 $F(k-1) \ge \varphi^{\,k-3}$, $F(k-2) \ge \varphi^{\,k-4}$라고 가정하면
  $$F(k) = F(k-1)+F(k-2) \ge \varphi^{\,k-3} + \varphi^{\,k-4} = \varphi^{\,k-4}(\varphi + 1) = \varphi^{\,k-4}\cdot\varphi^{2} = \varphi^{\,k-2}$$
  세 번째 등호에서 $\varphi + 1$을 $\varphi^2$으로 바꾼 것이 유일한 기술이고, 그게 가능한 이유가 바로 위의 $\varphi^2 = \varphi+1$입니다.

**4단계 — 높이 상한.** 노드가 $n$개인 높이 $h$짜리 AVL 트리는 정의상 $n \ge N(h)$를 만족합니다. 2·3단계를 이어 붙이면

$$
n \;\ge\; N(h) \;=\; F(h+2) - 1 \;\ge\; \varphi^{\,h} - 1
$$

양변에 $1$을 더하면 $\varphi^{\,h} \le n+1$이고, 양변에 $\log_2$를 취하면 $h \log_2 \varphi \le \log_2(n+1)$입니다. $\log_2\varphi \approx 0.6942$는 **양수**라서 부등호 방향이 유지된 채 나눌 수 있어요. 따라서

$$
h \;\le\; \frac{\log_2 (n+1)}{\log_2 \varphi} \;\approx\; 1.4404\,\log_2 (n+1)
$$

즉 AVL 트리의 높이는 높이가 최소인 트리($\log_2 n$)보다 최대 **약 1.44배**까지만 나빠지고, 그래서 $O(\log n)$입니다.

$n = 10^4$을 넣으면 $h \le 1.4404 \times 13.29 \approx 19.1$, 즉 $h \le 19$입니다. 한편 정확한 최악값은 위 점화식을 직접 세어 구할 수 있어요 — $N(18) = 6{,}764 \le 10^4 < N(19) = 10{,}945$이므로 높이 19짜리 트리는 노드를 $10{,}945$개 이상 필요로 해서 만들 수 없고, **실제 최악은 18**입니다. 상한식이 한 칸 헐거운 이유는 3단계에서 $F(h+2) - 1 \ge \varphi^{\,h} - 1$로 **넉넉하게** 눌러 잡았기 때문이에요(실제 $F(h+2)-1$은 $\varphi^{\,h}-1$보다 꽤 큽니다). 상한식은 "어떤 $n$에서도 이보다 높아질 수 없다"를 보증하는 용도이고, 특정 $n$의 정확한 최악값이 필요하면 점화식을 세는 쪽이 정확합니다.

**핵심 연산 — 네 가지 회전.** 재균형은 항상 "불균형이 처음 감지된 노드"(아래에서 $z$라 부릅니다)에서 일어납니다. $z$의 어느 쪽이 무거운지, 그리고 그 무거운 자식이 **바깥쪽**(같은 방향)으로 뻗었는지 **안쪽**(반대 방향)으로 꺾였는지에 따라 네 경우로 나뉩니다. 아래 도식의 수치는 모두 실행해서 얻은 값입니다.

**① LL(왼쪽-왼쪽) — 오른쪽 단일 회전.** `insert(30)`, `insert(20)`, `insert(10)` 순서입니다.

```text
Before (10 삽입 직후)          After (30에서 오른쪽 회전)
     30 (h=3, bf=2)                20 (h=2, bf=0)
    /                             /          \
  20 (h=2, bf=1)               10 (h=1)     30 (h=1)
  /
10 (h=1)
```

**② RR(오른쪽-오른쪽) — 왼쪽 단일 회전.** LL의 좌우 대칭입니다. `insert(10)`, `insert(20)`, `insert(30)` 순서.

```text
Before (30 삽입 직후)          After (10에서 왼쪽 회전)
10 (h=3, bf=-2)                20 (h=2, bf=0)
   \                            /          \
   20 (h=2, bf=-1)           10 (h=1)     30 (h=1)
      \
      30 (h=1)
```

**③ LR(왼쪽-오른쪽) — 왼쪽 자식을 먼저 왼쪽 회전, 그다음 오른쪽 회전.** `insert(30)`, `insert(10)`, `insert(20)` 순서.

```text
Before (20 삽입 직후)      1단계: 10에서 왼쪽 회전     2단계: 30에서 오른쪽 회전
   30 (bf=2)                  30 (bf=2)                20 (h=2, bf=0)
  /                          /                          /          \
10 (bf=-1)                 20                        10 (h=1)     30 (h=1)
   \                       /
   20                    10
```

**④ RL(오른쪽-왼쪽) — 오른쪽 자식을 먼저 오른쪽 회전, 그다음 왼쪽 회전.** LR의 대칭입니다. `insert(10)`, `insert(30)`, `insert(20)` 순서.

```text
Before (20 삽입 직후)      1단계: 30에서 오른쪽 회전   2단계: 10에서 왼쪽 회전
10 (bf=-2)                 10 (bf=-2)                  20 (h=2, bf=0)
   \                          \                         /          \
   30 (bf=1)                  20                      10 (h=1)     30 (h=1)
   /                             \
  20                             30
```

네 경우 모두 **최종 모양이 똑같습니다**(루트 20, 왼쪽 10, 오른쪽 30). 어느 쪽에서 불균형이 왔든, 회전이 하는 일은 "세 값 중 가운데를 위로 올리고 나머지 둘을 좌우 자식으로 붙이는" 동일한 재배치이기 때문이에요.

> 기억법: **무거운 쪽의 반대 방향으로 회전한다.** 왼쪽이 무거우면 오른쪽 회전, 오른쪽이 무거우면 왼쪽 회전. 안쪽으로 꺾여 있으면(LR/RL) 자식부터 한 번 더 펴 준다.

### 왜 모순 없이 작동하는가

**(1) 회전이 BST 규칙을 깨지 않는 이유.** 회전 전후의 중위 순회 결과를 직접 나열해서 확인합니다. 위 관찰 ④의 그림에서 세 서브트리를 $T_1, T_2, T_3$이라 두면, BST 규칙에 의해 회전 **전**에 $T_1 < x < T_2 < y < T_3$이 성립합니다($x$는 $y$의 왼쪽 자식이므로 $x < y$이고, $T_2$는 $x$의 오른쪽 서브트리이자 $y$의 왼쪽 서브트리라 $x < T_2 < y$입니다). 회전 **후**의 구조에서 중위 순회를 다시 적으면 $T_1,\ x,\ T_2,\ y,\ T_3$ — 나열이 글자 그대로 동일합니다. 회전은 "누가 부모인가"만 바꾸고 **값의 좌우 순서는 한 번도 건드리지 않기** 때문입니다. 그래서 회전을 몇 번 하든 `inOrder()`의 결과는 변하지 않습니다.

**(2) 삽입이 불변식 2를 되돌린다는 것 — 귀납 논증.** 재귀 함수 `insertNode(node, v)`가 돌려주는 서브트리에 대해 다음 명제를 증명합니다.

> **P**: 반환된 서브트리는 (i) BST 규칙과 $|bf| \le 1$을 만족하고, (ii) `height` 필드가 정확하며, (iii) 그 높이는 **삽입 전과 같거나 정확히 1 크다**.

- *기저*: `node === undefined`인 자리에 새 리프를 만들어 반환합니다. 높이는 $0 \to 1$이니 (iii)의 "정확히 1 증가"에 해당하고, 자식이 없으니 $bf = 0$이라 (i)도, `height = 1`이라 (ii)도 성립합니다.
- *단계*: 값이 왼쪽으로 내려갔다고 합시다(오른쪽은 좌우 대칭이라 같은 논증입니다). 귀납 가정에 의해 새 왼쪽 서브트리는 균형 상태이고, 그 높이는 $h_L$ 그대로이거나 $h_L + 1$입니다.
  - **왼쪽 높이가 그대로면**: $bf$도 그대로라 회전이 필요 없고, `updateHeight`를 해도 값이 변하지 않습니다 → 높이 증가량 $0$.
  - **왼쪽 높이가 1 늘었으면**: $bf(z)$가 정확히 $1$ 증가합니다. 삽입 전 $bf(z) \in \{-1, 0, 1\}$이었으므로 삽입 후는 $\{0, 1, 2\}$ 중 하나예요.
    - $bf(z) = 0$ (전 $-1$): 짧던 왼쪽이 오른쪽과 같아진 것이니 최댓값이 안 변합니다 → 높이 증가량 $0$, 회전 불필요.
    - $bf(z) = 1$ (전 $0$): 왼쪽이 더 커졌으니 → 높이 증가량 $1$, 회전 불필요.
    - $bf(z) = 2$ (전 $1$): 여기서만 회전합니다. 아래에서 따로 봅니다.

  $bf(z) = 2$인 경우를 높이로 정확히 따라가 봅시다. 삽입 전 $bf(z)=1$이었으므로 오른쪽 높이는 $h_R = h_L - 1$이고, 삽입 전 $z$의 높이는 $1 + h_L$이었습니다. 삽입 후 왼쪽 자식 $y$의 높이는 $h_L + 1$이고요.

  **먼저 $bf(y) = 0$이 불가능하다는 것부터 확실히 해 둡시다.** 삽입 직전 $y$의 두 자식 높이를 $a$(값이 들어간 쪽), $b$(반대쪽)라고 두면, 삽입 전 $y$의 높이는 $1 + \max(a, b)$이고 삽입 후에는 $1 + \max(a+1,\, b)$입니다. 우리는 $y$의 높이가 **실제로 1 늘었다**는 것을 알고 있으므로

  $$\max(a+1,\ b) > \max(a,\ b) \iff a + 1 > \max(a, b) \iff a \ge b$$

  가 성립합니다(가운데 동치는 $a+1 > a$가 항상 참이라, 좌변이 커지려면 $a+1$이 최댓값을 새로 차지해야 한다는 뜻이에요). 한편 삽입 후에도 $y$는 균형을 지키므로(귀납 가정 (i)) $bf(y) = (a+1) - b \le 1$, 즉 $a \le b$입니다. 두 부등식을 합치면 $a = b$이고, 따라서

  $$bf(y) = (a+1) - b = 1$$

  왼쪽에 삽입했을 때 $y$의 높이가 늘었다면 $bf(y)$는 **정확히 $+1$**, 오른쪽에 삽입했다면 대칭으로 $-1$입니다. $0$은 나올 수 없어요. 이 부호가 곧 LL이냐 LR이냐를 가릅니다.

  ```text
  ● bf(y) = +1  (LL):  y.left = T1 높이 h_L,  y.right = T2 높이 h_L - 1
      rotateRight(z) 후 →  새 루트 y
          y.left  = T1                          (높이 h_L)
          y.right = z,  z 의 자식 = T2(h_L-1), T_R(h_R = h_L-1)
                                                → z 높이 = h_L,  bf(z) = 0
          ⇒ y 높이 = 1 + h_L = 삽입 전 z 의 높이,  bf(y) = h_L - h_L = 0

  ● bf(y) = -1  (LR):  y.left = T1 높이 h_L - 1,  y.right = x 높이 h_L
      x 의 두 자식 높이를 a, b 라 두면 max(a, b) = h_L - 1 이고 |a - b| ≤ 1
      (즉 (a,b) 는 (h_L-1, h_L-1), (h_L-1, h_L-2), (h_L-2, h_L-1) 중 하나)

      이중 회전(먼저 y 에서 왼쪽, 다음 z 에서 오른쪽) 후 → 새 루트 x
          x.left  = y,  y 의 자식 = T1(h_L-1), a
                        a ≤ h_L-1 이므로     → y 높이 = 1 + (h_L-1) = h_L
                                                bf(y) = (h_L-1) - a ∈ {0, 1}
          x.right = z,  z 의 자식 = b, T_R(h_L-1)
                        b ≤ h_L-1 이므로     → z 높이 = 1 + (h_L-1) = h_L
                                                bf(z) = b - (h_L-1) ∈ {-1, 0}
          ⇒ x 높이 = 1 + h_L = 삽입 전 z 의 높이,  bf(x) = h_L - h_L = 0
  ```

  LR에서 $a$와 $b$가 셋 중 무엇이든 **$y$와 $z$의 새 높이는 똑같이 $h_L$**이 됩니다. $T_1$과 $T_R$이 이미 $h_L - 1$이라 $a, b$가 그보다 작아져도 최댓값이 바뀌지 않기 때문이에요. 그리고 $bf(y) \in \{0, 1\}$, $bf(z) \in \{-1, 0\}$이라 세 노드 모두 불변식 2를 지킵니다.

  두 경우 모두 **회전 후 서브트리 높이가 삽입 전 높이와 같아집니다.** 그러면 이 서브트리의 부모 입장에서는 자식 높이가 하나도 안 변한 것이므로, (iii)의 "증가량 $0$" 경로를 타고 위로 올라가며 **더 이상 회전이 일어나지 않습니다.** 그래서 삽입 한 번에 재균형은 **많아야 한 곳**에서 일어나고, 그곳에서 `rotate` 함수를 1번(단일) 또는 2번(이중) 부릅니다. 본문 코드를 그대로 추출해 무작위 삽입·삭제 2만 회를 돌려 봐도, 삽입 하나가 부른 `rotate` 호출은 최대 2번(=이중 회전 1회)이었습니다.

**(3) 삭제는 왜 회전이 여러 번 일어날 수 있는가.** 같은 계산을 삭제에서 해 보면 결론이 갈립니다. 삭제로 오른쪽이 짧아져 $bf(z) = 2$가 됐다고 하고, 삭제 **후** 오른쪽 높이를 $h_R$이라 둡시다. 그러면 왼쪽 자식 $y$의 높이는 $h_R + 2$이고, 삭제 **전** $z$의 높이는 $1 + \max(h_R+2,\ h_R+1) = h_R + 3$이었습니다.

여기서 삽입과 결정적으로 다른 점이 나옵니다. 삽입에서는 "높이가 늘어난 쪽"이 $y$였기 때문에 $bf(y) \ne 0$이 강제됐는데, 삭제에서는 **$y$가 아무 변화도 겪지 않았습니다**(줄어든 쪽은 반대편이니까요). 그래서 $bf(y) = 0$이 얼마든지 가능하고, 이 부호가 회전 후 높이를 갈라놓습니다. `rotateRight(z)`를 적용해 새 높이를 계산해 봅시다.

```text
● bf(y) = 0  :  y 의 두 자식 높이 = (h_R+1), (h_R+1)
    회전 후 →  z 의 자식 = y.right(h_R+1), T_R(h_R)   → z 높이 = h_R + 2
               새 루트 y 높이 = 1 + max(h_R+1, h_R+2) = h_R + 3
    ⇒ 삭제 전 z 높이(h_R+3) 와 같다 → 조상은 변화를 못 느낀다 → 여기서 끝

● bf(y) = +1 :  y 의 두 자식 높이 = (h_R+1), (h_R)
    회전 후 →  z 의 자식 = y.right(h_R), T_R(h_R)      → z 높이 = h_R + 1
               새 루트 y 높이 = 1 + max(h_R+1, h_R+1) = h_R + 2
    ⇒ 삭제 전보다 1 작다 → 부모에게 "한쪽이 짧아졌다"로 전달
                          → 부모에서 다시 |bf| = 2 가 될 수 있다
```

두 경우를 실제 트리로 확인해 봤습니다. 같은 `delete(60)`인데 왼쪽 자식의 균형 인수만 다릅니다.

```text
[ bf(y)=0 ]  삭제 전 (z=50 의 높이 4)            delete(60) → 오른쪽 회전 1회
              50                                        30 (h=4)
        30(bf=0)      70                            /          \
      20      40    60                          20 (h=2)      50 (h=3)
    10      35                                  /              /     \
                                              10             40      70
                                                             /
                                                           35
              → 회전 후 서브트리 높이 4. 삭제 전과 같아서 조상은 아무 영향도 받지 않는다.

[ bf(y)=+1 ] 삭제 전 (z=50 의 높이 4)            delete(60) → 오른쪽 회전 1회
              50                                        30 (h=3)
        30(bf=1)      70                            /          \
      20      40    60                          20 (h=2)      50 (h=2)
    10                                          /              /     \
                                              10             40      70
              → 회전 후 서브트리 높이 3. 1 줄었으므로 이 사실이 부모로 올라간다.
```

두 트리를 각각 더 큰 트리의 왼쪽 서브트리로 매달고 같은 삭제를 돌려 보면 차이가 그대로 드러납니다 — 첫 번째는 전체 높이가 5에서 5로 그대로였고, 두 번째는 5에서 4로 줄면서 부모 쪽 균형 인수가 다시 계산됐습니다.

그러면 연쇄는 얼마나 길어질 수 있을까요? 한 레벨에서 재균형은 많아야 한 번 일어나고(그 자리를 고치고 나면 위로 올라갑니다), 재귀는 삭제 경로의 조상들을 리프에서 루트까지 한 번씩만 훑습니다. 그 경로 길이가 트리 높이 $h$이므로 **재균형 횟수의 상한은 $h = O(\log n)$**입니다. 그리고 이 상한이 헐거운 값이 아니라는 것도 확인할 수 있어요 — 최소 노드 트리(위 $N(h)$를 실현하는 모양, 모든 노드의 $bf$가 $+1$이라 위의 두 번째 경우만 계속 발생합니다)에서 짧은 쪽 끝 값을 지워 실제로 세어 봤습니다.

```text
트리 높이 h   노드 수 n    delete 1회가 부른 회전 횟수
     4            7                  1
     6           20                  2
     8           54                  3
    10          143                  4
    12          376                  5
    14          986                  6      ← 대략 h/2 로 증가한다
```

무작위 스트레스(2만 회 연산)에서도 삭제 한 번의 최대 회전은 5회였고, 삽입은 끝까지 2회(=이중 회전 1회)를 넘지 않았습니다. **삽입의 재균형은 한 곳, 삭제의 재균형은 최대 $O(\log n)$곳** — 이것이 두 연산의 진짜 차이이고, 앞서 레드블랙 트리와의 선택 기준에서 말한 "갱신이 잦으면 레드블랙"의 근거이기도 합니다. 그래도 회전 하나가 $O(1)$이고 경로 길이가 $O(\log n)$이라, 삭제 **전체** 비용은 여전히 $O(\log n)$입니다.

**여기서 헷갈리기 쉬운 포인트 ①: 노드 개수와 높이를 섞는 것입니다.** 왼쪽에 노드가 3개, 오른쪽에 1개 있으면 불변식 위반일까요? **모양에 따라 다릅니다.**

```text
같은 "왼쪽 3개, 오른쪽 1개"인데 판정이 갈리는 두 경우

  사슬(왼쪽 높이 3, 위반)      균형(왼쪽 높이 2, 정상)
     x                          x
    /  \                       /  \
   a    d                     a     d
    \                        / \
     b                      b   c
      \
       c
  bf = |3 - 1| = 2  (X)      bf = |2 - 1| = 1  (O)
```

균형 인수는 **개수가 아니라 높이**로 계산합니다. 개수로 판정하려는 구조도 실제로 존재하지만(무게 균형 트리) 그건 다른 자료구조예요.

**헷갈리기 쉬운 포인트 ②: "안쪽으로 꺾인 경우도 단일 회전으로 되지 않나요?"** LR 상황(`30-10-20`)에서 $z=30$을 바로 오른쪽으로 회전해 보면, 실행 결과가 이렇습니다.

```text
잘못된 시도: LR 상황에서 z=30 을 바로 오른쪽 회전

    30 (h=3, bf=2)                        10 (h=3, bf=-2)   ← 불균형이 그대로!
   /                                          \
 10 (h=2, bf=-1)   --- rotateRight(30) --->    30 (h=2, bf=1)
    \                                          /
    20 (h=1)                                 20 (h=1)

높이 3 → 3 (안 줄었다), bf 2 → -2 (부호만 뒤집혔다)
```

불균형이 사라지기는커녕 반대편으로 옮겨 갈 뿐입니다. 단일 회전은 "무거운 자식이 바깥쪽으로 곧게 뻗어 있을 때"만 통하기 때문이에요. 안쪽으로 꺾여 있으면 먼저 그 자식을 반대 방향으로 회전시켜 **바깥쪽 모양(LL 또는 RR)으로 바꾼 뒤**에야 부모 회전이 먹힙니다.

**헷갈리기 쉬운 포인트 ③: "모든 삽입은 회전을 부른다"는 오해.** `10, 20, 5, 1, 15`를 순서대로 넣으면 회전은 **0회**입니다. 실제로 돌려 확인한 최종 모양이에요.

```text
        10 (h=3, bf=0)
       /            \
    5 (h=2, bf=1)   20 (h=2, bf=1)
    /                /
  1 (h=1)          15 (h=1)
```

균형 인수가 $\pm1$인 노드가 여럿 있지만 전부 허용 범위 안이라 손댈 이유가 없습니다. 규칙 A에서 "느슨하게 정의한다"고 한 것의 실제 효과가 이겁니다 — **어긋남을 허용했기 때문에 대부분의 삽입이 공짜로 끝납니다.**

> 잠깐, 확인 하나만 해 볼까요? 위 트리에 `2`를 넣으면 어떻게 될까요?
>
> `2`는 `10 → 5 → 1`을 지나 `1`의 오른쪽에 붙습니다. 그러면 `1`의 높이가 2가 되고 `5`의 균형 인수는 $2 - 0 = 2$ → 위반이에요. `5`의 왼쪽 자식 `1`은 오른쪽이 무거우니(bf = $-1$) **LR 경우**입니다. `1`에서 왼쪽 회전 → `5`에서 오른쪽 회전을 하면 `2`가 그 자리의 루트가 되고, 왼쪽에 `1`, 오른쪽에 `5`가 붙습니다.

마지막으로 경계 상황을 점검해 둡시다.

```text
빈 트리에 has/min/max        → false / undefined / undefined (루트가 undefined)
루트 하나짜리 트리            → 삽입·삭제·조회 모두 회전 없이 성립 (h=1, bf=0)
중복 insert                   → has()로 먼저 걸러져 size 불변
delete(존재하지 않는 값)      → false 반환, 트리 변화 없음
자식이 0개/1개인 노드 삭제     → 남은 자식(또는 undefined)을 그대로 승계
자식이 2개인 노드 삭제         → 오른쪽 서브트리의 최솟값(중위 후계자)으로 값 교체 후
                                 그 후계자를 오른쪽 서브트리에서 실제로 삭제
마지막 원소 삭제               → 루트가 undefined 로 돌아가고 height() = 0
```

## 아이디어를 코드로 옮기기

먼저 회전이 전혀 없는 **평범한 BST 삽입**부터 놓고 보겠습니다. 후보 ④가 이 코드였고, 정렬 입력에서 사슬로 퇴화하던 그 코드예요.

```ts
// 1단계 — 평범한 BST 삽입(균형 없음, 정렬 입력에 취약)
function insertPlain<T>(node: AVLNode<T> | undefined, value: T, cmp: (a: T, b: T) => number): AVLNode<T> {
  if (node === undefined) return new AVLNode(value);
  if (cmp(value, node.value) < 0) node.left = insertPlain(node.left, value, cmp);
  else node.right = insertPlain(node.right, value, cmp);
  return node; // 여기서 그냥 반환 — 높이도, 균형도 보지 않는다
}
```

AVL은 이 재귀 **구조를 그대로 두고** 마지막 `return node`만 `return rebalance(node)`로 바꿉니다. 재귀가 되돌아오는 길이 곧 조상 체인을 거슬러 올라가는 길이라, 이 한 줄이 "아래에서 위로 높이 갱신 + 필요하면 회전"을 전부 맡아요. 다만 이 한 줄이 전부라는 뜻은 아닙니다 — 노드에 `height` 필드가 새로 생기고, 중복을 무시하는 집합 의미론은 `insert` 진입부에서 따로 처리하며, 회전으로 서브트리 루트가 바뀌므로 `node.left = ...` 형태의 **재대입이 필수**가 됩니다(위 `insertPlain`은 `cmp >= 0`이면 오른쪽으로 보내 중복을 허용하는 점도 다릅니다).

```ts
class AVLNode<T> {
  value: T;
  left: AVLNode<T> | undefined = undefined;
  right: AVLNode<T> | undefined = undefined;
  height: number = 1;

  constructor(value: T) {
    this.value = value;
  }
}

// 없는 노드의 높이는 0으로 봅니다 — 리프의 높이가 1이 되도록 맞추는 관례예요.
function h<T>(node: AVLNode<T> | undefined): number {
  return node?.height ?? 0;
}

function bf<T>(node: AVLNode<T>): number {
  return h(node.left) - h(node.right);
}

function updateHeight<T>(node: AVLNode<T>): void {
  node.height = 1 + Math.max(h(node.left), h(node.right));
}

function rotateRight<T>(z: AVLNode<T>): AVLNode<T> {
  const y = z.left!;
  z.left = y.right;
  y.right = z;
  updateHeight(z); // 아래로 내려간 z 부터
  updateHeight(y); // 그다음 새 루트 y
  return y;
}

function rotateLeft<T>(z: AVLNode<T>): AVLNode<T> {
  const y = z.right!;
  z.right = y.left;
  y.left = z;
  updateHeight(z);
  updateHeight(y);
  return y;
}

function rebalance<T>(node: AVLNode<T>): AVLNode<T> {
  updateHeight(node);
  const balance = bf(node);

  if (balance > 1) {
    if (bf(node.left!) < 0) {
      node.left = rotateLeft(node.left!); // LR: 안쪽으로 꺾인 자식을 먼저 편다
    }
    return rotateRight(node); // LL, 또는 방금 편 LR
  }

  if (balance < -1) {
    if (bf(node.right!) > 0) {
      node.right = rotateRight(node.right!); // RL: 안쪽으로 꺾인 자식을 먼저 편다
    }
    return rotateLeft(node); // RR, 또는 방금 편 RL
  }

  return node;
}

export class AVLTree<T> {
  private root: AVLNode<T> | undefined = undefined;
  private _size = 0;
  private comparator: (a: T, b: T) => number;

  constructor(comparator?: (a: T, b: T) => number) {
    this.comparator = comparator ?? ((a, b) => (a < b ? -1 : a > b ? 1 : 0));
  }

  insert(value: T): void {
    if (this.has(value)) return; // 집합 의미론: 중복은 무시
    this.root = this.insertNode(this.root, value);
    this._size++;
  }

  private insertNode(node: AVLNode<T> | undefined, value: T): AVLNode<T> {
    if (node === undefined) return new AVLNode(value);
    const cmp = this.comparator(value, node.value);
    if (cmp < 0) node.left = this.insertNode(node.left, value);
    else node.right = this.insertNode(node.right, value);
    return rebalance(node); // 재귀가 돌아오는 길에서 아래→위로 재균형
  }

  delete(value: T): boolean {
    if (!this.has(value)) return false;
    this.root = this.deleteNode(this.root, value);
    this._size--;
    return true;
  }

  private deleteNode(node: AVLNode<T> | undefined, value: T): AVLNode<T> | undefined {
    if (node === undefined) return undefined;
    const cmp = this.comparator(value, node.value);
    if (cmp < 0) {
      node.left = this.deleteNode(node.left, value);
    } else if (cmp > 0) {
      node.right = this.deleteNode(node.right, value);
    } else {
      if (node.left === undefined) return node.right;
      if (node.right === undefined) return node.left;
      // 자식이 둘: 중위 후계자(오른쪽 서브트리의 최솟값)로 값을 옮긴 뒤
      // 그 후계자를 오른쪽 서브트리에서 실제로 지운다.
      let successor = node.right;
      while (successor.left !== undefined) successor = successor.left;
      node.value = successor.value;
      node.right = this.deleteNode(node.right, successor.value);
    }
    return rebalance(node);
  }

  has(value: T): boolean {
    let node = this.root;
    while (node !== undefined) {
      const cmp = this.comparator(value, node.value);
      if (cmp === 0) return true;
      node = cmp < 0 ? node.left : node.right;
    }
    return false;
  }

  min(): T | undefined {
    let node = this.root;
    if (node === undefined) return undefined;
    while (node.left !== undefined) node = node.left;
    return node.value;
  }

  max(): T | undefined {
    let node = this.root;
    if (node === undefined) return undefined;
    while (node.right !== undefined) node = node.right;
    return node.value;
  }

  inOrder(): T[] {
    const result: T[] = [];
    const walk = (node: AVLNode<T> | undefined) => {
      if (node === undefined) return;
      walk(node.left);
      result.push(node.value);
      walk(node.right);
    };
    walk(this.root);
    return result;
  }

  size(): number {
    return this._size;
  }

  height(): number {
    return h(this.root);
  }
}
```

**가장 중요한 두 줄은 `rotateRight`의 `z.left = y.right; y.right = z;`입니다.** 이 두 줄이 회전의 전부이고, 나머지는 높이 뒷정리예요. 첫 줄이 "$y$의 오른쪽에 매달려 있던 $T_2$를 $z$의 왼쪽으로 옮겨 자리를 비우는" 일이고, 둘째 줄이 "그 빈자리에 $z$를 매다는" 일입니다. 순서를 바꿔 `y.right = z`를 먼저 쓰면 두 가지가 한꺼번에 망가져요 — $T_2$를 가리키던 유일한 포인터가 덮어써져 그 서브트리가 통째로 사라지고, 이어지는 `z.left = y.right`는 이제 `z` 자신을 대입합니다. `30, 20, 10`으로 실행해 보면 `30.left === 30`인 **자기 참조 고리**가 실제로 만들어집니다.

구현에서 놓치기 쉬운 지점을, **틀렸을 때 실제로 나오는 값**과 함께 짚어 둘게요. 아래 값은 전부 해당 버그를 넣은 코드를 실행해서 얻은 결과입니다.

- **`updateHeight(z)` → `updateHeight(y)` 순서를 뒤집으면**: `y`가 아직 갱신되지 않은 `z`의 **회전 전 높이**를 보고 계산합니다. `30, 20, 10`을 넣으면 트리는 정상 모양(루트 20)인데 루트의 `height` 필드가 **4**로 기록돼요(실제 높이는 2). 이어서 `5, 3`을 더 넣으면 그 거짓 높이 때문에 회전 판정이 어긋나 루트가 `5`가 되고 `height()`는 **6**을 반환합니다 — 실제 높이는 3인데도요. 트리는 겉보기에 멀쩡히 동작하다가 균형만 조용히 무너집니다.
- **`rebalance`에서 `bf(node.left!) < 0` 검사를 빼면**: LR을 LL로 착각해 단일 회전만 합니다. `30, 10, 20`을 넣으면 위 반례 그대로 루트가 `10`, $bf = -2$인 **위반 상태로 끝납니다**.
- **재귀 반환값을 부모에 다시 대입하지 않으면**(`node.left = this.insertNode(...)`의 좌변을 생략): 회전으로 서브트리 루트가 바뀌었는데 부모는 옛 루트를 계속 가리킵니다. `10, 20, 30, 40, 50`을 넣고 `inOrder()`를 찍으면 `[10, 20, 30]` — **40과 50이 트리에서 사라집니다.** 부모 포인터 없이 회전 결과를 잇는 장치가 바로 이 대입이에요.
- **삭제에서 후계자를 실제로 지우지 않으면**(`node.value = successor.value`만 하고 끝내면): `5,3,7,1,4,6,8`을 넣고 `delete(5)`를 하면 `inOrder()`가 `[1, 3, 4, 6, 6, 7, 8]`이 됩니다 — **6이 두 번** 남아요. 값을 복사한 것이지 옮긴 것이 아니기 때문입니다.

> 기억법: **재귀가 돌아오는 길이 곧 조상 체인이다.** 내려갈 때는 자리를 찾고, 올라올 때는 높이를 고치고 균형을 맞춘다.

두 가지 설계 선택도 밝혀 둘게요. 첫째, `insert`와 `delete`가 시작하면서 `has(value)`를 부르기 때문에 트리를 **두 번 내려갑니다**. 비교 횟수가 2배가 되는 대신 "중복 판정"과 "삽입·삭제"를 분리해 코드가 단순해지는 쪽을 택한 것이고, 한 번의 순회 안에서 존재 여부까지 처리하도록 합칠 수도 있습니다. 둘째, 두 자식 노드를 지울 때 **값만 옮기고 노드 객체는 그대로 둡니다.** 이 컨테이너는 노드 참조를 밖으로 내주지 않는 값 기반 자료구조라 문제가 없지만, 노드 핸들을 외부에 노출하는 설계라면 후계자 노드 자체를 재연결하는 방식으로 바꿔야 합니다.

정리하면, AVL 트리는 **높이를 최소로 만들겠다는 목표를 포기하는 대신** 두 가지를 얻습니다. 하나는 어긋남이 항상 "허용치보다 한 칸 초과"로 제한된다는 것이고(그래서 상수 시간 수선 한 종류로 충분합니다), 다른 하나는 회전이 필요 없는 삽입이 실제로 존재한다는 것입니다 — 위 `10, 20, 5, 1, 15`처럼요. 그 대가로 높이는 최소 높이보다 최대 1.44배까지 높아질 수 있지만, $n = 10^4$에서 그 최악값은 18로 여전히 스무 번 이하의 비교예요.

이 글의 수치는 모두 위 코드를 그대로 스크래치 파일로 추출해 실행한 결과입니다. 무작위 검증은 이렇게 했어요 — 고정 시드 난수로 $0$부터 $499$ 사이의 값을 뽑아 60% 확률로 삽입, 40% 확률로 삭제를 $20{,}000$번 섞어 돌리면서, **매 연산마다** 모든 노드의 $|bf| \le 1$과 `height` 필드의 정확성을 재귀로 검사하고, `inOrder()`를 표준 `Set`을 정렬한 결과와 대조했습니다. 위반은 0건이었고, 삽입 하나가 부른 `rotate` 호출은 최대 2번, 삭제는 최대 5번이었으며, 관측된 최대 높이는 노드 235개일 때 10으로 이론 상한(약 11.4) 아래였습니다.
