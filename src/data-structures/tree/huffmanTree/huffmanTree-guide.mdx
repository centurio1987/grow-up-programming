# HuffmanTree — 빈도가 높을수록 짧은 코드를, 문자는 리프에만

## 한눈에 보는 컨셉

문자마다 등장 빈도가 다르다는 사실 하나를 이용해, 이진 트리의 **리프에만 문자를 배치**하고 빈도가 높은 문자일수록 루트에 가깝게(짧은 경로에) 두는 자료구조예요. 리프에만 문자가 있으므로 어떤 코드도 다른 코드의 접두사가 될 수 없고("prefix-free"), 구분자 없이 비트열만으로 원문을 복원할 수 있습니다. 최소 힙으로 이 트리를 아래에서 위로 쌓으면 $O(n \log n)$에 이론적으로 최적인 압축 코드가 나와요 — ZIP/DEFLATE, JPEG, MP3가 모두 이 원리를 쓰고 있습니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 허프만 트리를 떠올리세요.

- 심볼(문자/바이트)마다 **등장 빈도가 크게 치우쳐** 있다 ("어떤 문자는 자주, 어떤 문자는 드물게")
- **무손실**로 원본을 완벽히 복원해야 한다 (손실 압축이 아니다)
- 심볼 하나하나를 독립적인 코드로 치환하는 방식이면 충분하다 (반복되는 긴 패턴 자체를 압축하는 게 목적이 아니다)

고정 길이 코드(예: ASCII 8비트)는 이런 치우침을 전혀 활용하지 못해요. "abracadabra"라는 11글자 텍스트를 예로 비용을 비교해 봅시다.

```text
고정 길이(8비트/문자)     11 × 8 = 88 bit
허프만(빈도 기반 가변 길이) 23 bit   ← 실측(아래에서 검증)

88비트 중 23비트만 쓰니 압축률 23/88 ≈ 0.261
```

빈도가 안 갈리고 전부 균등하면 고정 길이와 별 차이가 없다는 것도 함께 기억해 두세요 — 허프만이 이기는 이유는 어디까지나 "빈도 치우침"입니다.

비슷한 목적의 다른 기법들과 선택 기준도 짚어 둘게요.

- **RLE(Run-Length Encoding)**: 같은 문자가 길게 반복될 때("aaaaaaaa") 강합니다. 문자 단위 빈도가 아니라 "연속 반복"을 노려요. 반복이 아니라 빈도 치우침이 신호라면 허프만입니다.
- **LZ77/사전 기반 압축**: "이미 나온 부분 문자열"을 참조로 대체합니다. 긴 패턴이 되풀이될 때 유리해요. 실제 DEFLATE는 LZ77로 패턴을 줄인 뒤 그 결과를 다시 허프만으로 압축하는 2단계 구조입니다.
- **산술 코딩(arithmetic coding)**: 허프만보다 이론적 한계(엔트로피)에 더 가깝게 갈 수 있지만 구현이 복잡합니다. 심볼당 1비트 미만 표현이 필요할 정도로 빈도가 극단적이면 산술 코딩을, 구현 단순성이 중요하면 허프만을 고릅니다.

### 문제 사례와 적용 예시

- **ZIP/DEFLATE**: LZ77로 반복 패턴을 줄인 뒤, 남은 심볼 스트림을 허프만 코딩으로 한 번 더 압축합니다.
- **JPEG**: 이산 코사인 변환(DCT) 계수를 양자화한 뒤, 마지막 무손실 단계로 허프만 코딩을 씁니다.
- **MP3**: 오디오를 지각적으로 압축한 결과물의 엔트로피 코딩 단계에 허프만(또는 그 변형)을 사용합니다.
- **코딩 테스트 맥락**: "문자 빈도가 주어졌을 때 최적 이진 코드를 구성하라", "우선순위 큐로 그리디 결합을 반복하라" 같은 문제가 허프만 트리 구현 그 자체를 요구합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드는 두 종류로 나뉩니다. 리프는 문자를 갖고, 내부 노드는 문자 없이 자식 둘을 묶는 역할만 해요.

```ts
interface HuffmanLeaf {
  char: string;   // 리프: 실제 문자
  freq: number;
  seq: number;    // 삽입/생성 순서 — 동점(같은 빈도) 처리용
}
interface HuffmanInternal {
  char: null;     // 내부 노드는 문자를 갖지 않는다
  freq: number;
  seq: number;
  left: HuffmanNode;
  right: HuffmanNode;
}
type HuffmanNode = HuffmanLeaf | HuffmanInternal;
```

트리 전체로는 `root: HuffmanNode`와 `codes: Map<string, string>`(문자 → 비트 코드)을 유지합니다. 지켜야 할 불변식은 네 가지예요.

1. **리프에만 문자가 있다.** $\text{char}(v) \neq \text{null} \iff v$는 자식이 없는 리프.
2. **접두어 없음(prefix-free).** 서로 다른 두 리프 $x, y$에 대해 $code(x)$는 $code(y)$의 접두사가 아니다.
3. **이진성.** 모든 내부 노드는 자식이 정확히 둘이다. (힙에서 항상 2개씩 꺼내 합치므로 자동 성립)
4. **최소 가중 경로 길이.** 트리의 총 비용 $\text{WPL}(T) = \sum_{c \in \text{Leaves}} freq(c) \cdot depth_T(c)$가 같은 빈도 분포를 갖는 모든 이진 트리 중 최소다.

이 네 불변식이 함께 작동하는 모습을 "abracadabra"(a:5, b:2, r:2, c:1, d:1)로 그려 보면 이렇습니다. (아래 코드는 전부 실측 검증된 값입니다 — 뒤의 "아이디어를 코드로 옮기기"에서 같은 코드를 실행해 확인해요.)

```text
                        루트:11
                       /        \
                    a:5          내부:6
                  (code:0)      /      \
                          내부:2         내부:4
                         /    \        /    \
                       c:1    d:1    b:2    r:2
                     (100)  (101)  (110)  (111)
```

**액션(연산)** — 이 가이드가 정의한 인터페이스 5종입니다. $n$ = 고유 문자 수, $m$ = 텍스트(또는 비트열) 길이.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(frequencies)` | 최소 힙으로 결합을 반복해 트리 구성 + DFS로 코드 테이블 생성 | $O(n \log n)$ |
| `encode(text)` | 각 문자를 코드로 치환해 이어붙인다 | $O(m)$ |
| `decode(bits)` | 루트에서 시작해 비트 0/1 따라 이동, 리프마다 문자를 출력하고 루트로 복귀 | $O(m)$ |
| `codeTable()` | 코드 맵의 복사본을 반환 | $O(n)$ |
| `compressionRatio(text)` | `encode(text).length / (text.length * 8)` | $O(m)$ |

핵심 연산 두 개만 자세히 볼게요.

**① 트리 구성 — 최솟값 두 개를 반복 결합.** 매 단계 힙에서 빈도가 가장 작은 두 노드를 꺼내 부모를 만들고 다시 넣습니다. "abracadabra"에서 실제로 일어나는 4번의 결합은 이렇습니다.

```text
Before: [a:5, b:2, r:2, c:1, d:1]         (5개 리프, 힙에 삽입 직후)

1단계: c:1 + d:1 → 내부:2                  Before [a:5,b:2,r:2,c:1,d:1]
                                            After  [a:5,b:2,r:2,내부:2(c,d)]

2단계: b:2 + r:2 → 내부:4                  Before [a:5,b:2,r:2,내부:2]
                                            After  [a:5,내부:4(b,r),내부:2(c,d)]

3단계: 내부:2 + 내부:4 → 내부:6            Before [a:5,내부:4,내부:2]
                                            After  [a:5,내부:6(b,r,c,d)]

4단계: a:5 + 내부:6 → 루트:11              Before [a:5,내부:6]
                                            After  [루트:11]   ← 힙 크기 1, 종료
```

**② 디코딩 — 루트에서 시작해 비트를 따라 걷기.** `encode("ab")`의 결과 `"0110"`을 디코딩하는 과정을 트리 위에서 따라가 봅니다.

```text
current = 루트:11
bit '0' → current.left  = a:5 (리프!) → 'a' 출력, current = 루트로 복귀
bit '1' → current.right = 내부:6
bit '1' → current.right = 내부:4(b,r)
bit '0' → current.left  = b:2 (리프!) → 'b' 출력, current = 루트로 복귀

결과: "ab"
```

### 왜 모순 없이 작동하는가

**불변식 2(접두어 없음)가 항상 지켜지는 이유**는 귀납으로 보일 수 있어요. 리프 하나짜리 트리(결합이 아직 없는 상태)는 코드가 하나뿐이니 자명히 접두어 없음을 만족합니다. 결합 단계에서 왼쪽 서브트리의 모든 코드 앞에 `"0"`을, 오른쪽 서브트리의 모든 코드 앞에 `"1"`을 붙이는데, 왼쪽 서브트리 내부에서는 귀납 가정으로 이미 접두어 없음이 성립하고(앞에 똑같이 `"0"`을 붙여도 유지), 왼쪽과 오른쪽 사이는 **첫 비트가 다르므로** 애초에 한쪽이 다른 쪽의 접두사가 될 수 없습니다. 힙이 크기 1이 될 때까지 이 결합을 반복하므로, 최종 트리도 접두어 없음을 만족합니다.

**불변식 4(최소 가중 경로 길이)**는 조금 더 깊은 논증이 필요합니다 — 이른바 **교환 논증(exchange argument)**이에요. 어떤 최적 트리 $T^*$를 잡아도, 빈도가 가장 작은 두 심볼 $x, y$를 최대 깊이의 형제 자리로 옮겨도 비용이 늘지 않는다는 걸 보이는 방식입니다. 최대 깊이의 두 리프 $p, q$(반드시 존재)와 $x, y$의 자리를 맞바꾼다고 해봅시다. $freq(x), freq(y)$가 최솟값이고 $depth(p), depth(q)$가 최댓값이므로, 교환으로 인한 비용 변화

$$\Delta = \big(freq(x)-freq(p)\big)\big(depth(p)-depth(x)\big) + \big(freq(y)-freq(q)\big)\big(depth(q)-depth(y)\big) \le 0$$

이 성립해서 비용이 늘지 않습니다. 즉 $x, y$를 형제로 묶어도 여전히 최적이라는 뜻이고, 이 사실을 반복 적용하면 "매 단계 최솟값 두 개를 결합"하는 탐욕 선택이 전역 최적을 보장한다는 결론에 도달합니다.

확인 질문 하나 짚고 갈게요 — **3단계에서 정말 최솟값 두 개(내부:2, 내부:4)가 아니라 a:5와 내부:2를 먼저 결합했다면 어떻게 될까요?** 실제로 계산해 보면:

```text
잘못된 결합: a:5 + 내부:2(c,d) → 내부:7,  이후 내부:4(b,r) + 내부:7 → 루트:11

가중 경로 길이(WPL) 재계산:
  b:2×depth2=4, r:2×depth2=4  (내부:4가 루트의 자식이라 깊이 2)
  a:5×depth2=10               (내부:7 아래, 깊이 2)
  c:1×depth3=3, d:1×depth3=3  (내부:7 안의 내부:2 아래, 깊이 3)
  합계 = 4+4+10+3+3 = 24 bit

올바른(최적) 결합의 합계 = 23 bit (위에서 실측)
```

**단 1비트 차이지만 명백히 손해입니다.** "빈도가 가장 작은 두 개"라는 조건을 어기는 순간 최적성이 깨진다는 걸 숫자로 확인했어요.

**여기서 헷갈리기 쉬운 포인트**를 두 가지 짚어 둡니다.

- **동점 처리(tie-break)는 최적성을 깨지 않습니다.** 힙에 빈도가 같은 노드가 여럿(예: 위 1단계 직후 b:2, r:2, 내부:2가 모두 후보)이면 어느 것을 먼저 꺼내든 트리 모양은 달라지지만, 교환 논증의 $x, y$ 자리에 **동점인 후보 중 아무거나** 넣어도 부등식이 그대로 성립하므로 총 비트 수(WPL)는 항상 동일하게 최적입니다. 개별 문자의 코드 길이가 구현마다 달라질 뿐이에요.
- **encode와 decode는 반드시 같은 트리 인스턴스를 공유해야 합니다.** 동점 처리 규칙이 실행마다 달라질 수 있는 구현(예: 힙 안에서 정렬 기준이 불안정)이라면, 같은 frequencies로 트리를 두 번 만들었을 때 코드 테이블이 달라질 수 있어요. `encode`로 만든 비트열을 다른 트리 인스턴스의 `decode`에 넣으면 조용히 틀린 문자가 나오거나 중간에 트리 경로를 벗어납니다.

엣지 케이스도 점검해 둡시다.

```text
frequencies가 비어 있음        → 트리를 만들 수 없으므로 Error
고유 문자 1개(예: x:7)         → 결합이 한 번도 없어 루트 자체가 리프.
                                  코드는 "0"(빈 문자열이면 encode 결과가 "" 가 되어버리는 함정,
                                  아래 "함정 포인팅"에서 다룸)
frequencies에 없는 문자 encode → Error ("frequencies에 없는 문자: z")
텍스트가 빈 문자열              → encode("") = "", compressionRatio = 0/0 (0으로 나눔 주의)
```

## 아이디어를 코드로 옮기기

이 가이드가 정의한 인터페이스대로 최소 힙(`MinHeap`)과 `HuffmanTree`를 구현합니다. 힙은 `(freq, seq)` 튜플로 비교해 **동점을 삽입 순서로 안정적으로 처리**하는 것이 가장 중요한 설계 포인트예요.

```ts
interface HuffmanLeaf {
  char: string;
  freq: number;
  seq: number;
}
interface HuffmanInternal {
  char: null;
  freq: number;
  seq: number;
  left: HuffmanNode;
  right: HuffmanNode;
}
type HuffmanNode = HuffmanLeaf | HuffmanInternal;

class MinHeap {
  private items: HuffmanNode[] = [];

  get size(): number {
    return this.items.length;
  }

  insert(node: HuffmanNode): void {
    this.items.push(node);
    this.bubbleUp(this.items.length - 1);
  }

  extractMin(): HuffmanNode {
    const min = this.items[0];
    const last = this.items.pop() as HuffmanNode;
    if (this.items.length > 0) {
      this.items[0] = last;
      this.bubbleDown(0);
    }
    return min as HuffmanNode;
  }

  // freq가 같으면 seq(삽입 순서)로 비긴다 — 안정적인 트리 구성의 핵심
  private less(a: HuffmanNode, b: HuffmanNode): boolean {
    return a.freq !== b.freq ? a.freq < b.freq : a.seq < b.seq;
  }

  private bubbleUp(i: number): void {
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (this.less(this.items[i], this.items[parent])) {
        [this.items[i], this.items[parent]] = [this.items[parent], this.items[i]];
        i = parent;
      } else break;
    }
  }

  private bubbleDown(i: number): void {
    const n = this.items.length;
    while (true) {
      let smallest = i;
      const l = 2 * i + 1;
      const r = 2 * i + 2;
      if (l < n && this.less(this.items[l], this.items[smallest])) smallest = l;
      if (r < n && this.less(this.items[r], this.items[smallest])) smallest = r;
      if (smallest === i) break;
      [this.items[i], this.items[smallest]] = [this.items[smallest], this.items[i]];
      i = smallest;
    }
  }
}

export class HuffmanTree {
  private root: HuffmanNode;
  private codes = new Map<string, string>();

  constructor(frequencies: Map<string, number>) {
    if (frequencies.size === 0) throw new Error("frequencies는 비어 있을 수 없습니다");

    const heap = new MinHeap();
    let seq = 0;
    for (const [char, freq] of frequencies) {
      heap.insert({ char, freq, seq: seq++ });
    }

    while (heap.size > 1) {
      const left = heap.extractMin();
      const right = heap.extractMin();
      heap.insert({ char: null, freq: left.freq + right.freq, seq: seq++, left, right });
    }
    this.root = heap.extractMin();
    this.buildCodes(this.root, "");
  }

  private buildCodes(node: HuffmanNode, prefix: string): void {
    if (node.char !== null) {
      this.codes.set(node.char, prefix || "0"); // 단일 문자 예외
      return;
    }
    this.buildCodes(node.left, prefix + "0");
    this.buildCodes(node.right, prefix + "1");
  }

  encode(text: string): string {
    let result = "";
    for (const ch of text) {
      const code = this.codes.get(ch);
      if (code === undefined) throw new Error(`frequencies에 없는 문자: ${ch}`);
      result += code;
    }
    return result;
  }

  decode(bits: string): string {
    if (this.root.char !== null) {
      // 리프 하나뿐인 트리 — 좌우 이동 없이 비트 수만큼 같은 문자를 반복
      return this.root.char.repeat(bits.length);
    }
    let node: HuffmanNode = this.root;
    let result = "";
    for (const bit of bits) {
      node = bit === "0" ? (node as HuffmanInternal).left : (node as HuffmanInternal).right;
      if (node.char !== null) {
        result += node.char;
        node = this.root; // 리프 도달 시 반드시 루트로 복귀
      }
    }
    return result;
  }

  codeTable(): Map<string, string> {
    return new Map(this.codes);
  }

  compressionRatio(text: string): number {
    return this.encode(text).length / (text.length * 8);
  }
}
```

**가장 중요한 부분은 `decode`의 `node = this.root` 한 줄입니다.** 리프에 도달해 문자를 출력한 직후 반드시 루트로 되돌아가야, 다음 비트가 새 문자의 시작으로 해석됩니다. 이 줄을 빼먹으면 어떤 일이 벌어지는지 직접 확인해 보죠 — `encode("ab")`의 결과 `"0110"`을 그 버그 있는 코드로 디코딩하면, 첫 비트 `'0'`에서 리프 `a`에 도달해 `'a'`를 출력한 뒤 `current`가 리프 `a`에 **그대로 머뭅니다.** 다음 비트 `'1'`에서 `current.right`를 읽으려 하는데 리프 `a`에는 `right` 자식이 없으므로(`undefined`), 실행하면 다음 런타임 에러가 그대로 발생합니다.

```text
TypeError: undefined is not an object (evaluating 'current.char')
```

놓치기 쉬운 지점을 더 짚어 둡니다.

- **`prefix || "0"`의 존재 이유.** 고유 문자가 1개뿐이면 결합이 한 번도 일어나지 않아 루트가 곧 리프이고, DFS 시작 시 `prefix`가 `""`입니다. 이 보정이 없으면 코드가 빈 문자열이 되어 `encode("xxxx")`가 `"xxxx"`(길이 4) 대신 `""`(길이 0)를 반환하고, `compressionRatio`가 실제로는 `4×1/(4×8)=0.125`여야 할 값을 `0`으로 잘못 보고합니다 — "압축률 0%"라는 있을 수 없는 결과가 조용히 나오는 함정입니다.
- **`decode`의 단일 리프 분기.** 루트 자체가 리프인 경우 `current.left`/`current.right` 접근 자체가 애초에 불가능하므로, 일반 루프를 태우기 전에 따로 처리해야 합니다.
- **`(freq, seq)` 비교 순서.** `less`에서 `freq`가 같을 때만 `seq`를 보는 순서를 지켜야 합니다. `seq`를 먼저 비교하면 빈도가 다른데도 삽입 순서로 우선순위가 뒤집혀 최솟값 추출이 깨집니다.

> 기억법: "리프를 만나면 결과에 적고, 루트로 돌아간다." 디코딩은 이 한 문장의 반복입니다.
