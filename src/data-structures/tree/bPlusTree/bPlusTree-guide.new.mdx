# B+ Tree — 데이터는 리프에만, 리프는 한 줄로 꿰기

## 한눈에 보는 컨셉

모든 실제 데이터를 **리프에만** 저장하고, 내부 노드는 길 안내(라우팅)만 하는 B-트리의 변형이에요. 리프들은 정렬된 순서 그대로 연결 리스트로 꿰어져 있어, 범위 질의가 "첫 리프 찾기 `O(log n)` + 체인 따라가기 `O(k)`"로 끝납니다. MySQL InnoDB를 비롯한 데이터베이스 인덱스가 바로 이 구조입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 B+ Tree를 떠올리세요.

- 점 조회(`has`)뿐 아니라 **범위 질의**("low 이상 high 이하 전부")가 자주 나온다
- 데이터가 계속 **삽입·삭제**되는데도 정렬 순서를 유지한 채 위 질의를 받아야 한다
- 정렬 순서대로 **전체를 순회**하는 요구(`inOrder`)도 있다

정렬 배열은 범위 질의에 강하지만 삽입이 `O(n)`이고, 보통의 이진 탐색 트리나 B-트리는 삽입에 강하지만 범위 질의가 아쉽습니다. B-트리로 "10 이상 20 이하"를 모으려면 트리를 **오르락내리락하는 중위 순회**를 해야 해요 — 데이터가 내부 노드 곳곳에 흩어져 있기 때문입니다.

```text
        B-트리: 데이터가 모든 노드에 있다        B+ 트리: 데이터는 리프에만
                                                  내부는 이정표만
              [ 10 ]                                   [ 10 ]
             /      \                                 /      \
        [ 3, 7 ]  [ 15 ]                        [ 3, 7 ]   [ 15 ]
        범위 질의 = 재귀 순회로                  /  |  \    /   \
        노드들을 오르내림  ↑↓↑↓             [1,2][3..][7..][10..][15..]
                                              →    →    →    →      리프 체인
                                             범위 질의 = 체인 직진  →→→
```

B+ Tree의 효과를 연산별로 요약하면 이렇습니다($t$는 최소 차수, $n$은 원소 수, $k$는 결과 개수).

```text
insert / delete / has     O(log_t n)
range(low, high)          O(log_t n + k)   ← 핵심 이점
inOrder                   O(n)             ← 체인만 따라가면 끝
```

### 문제 사례와 적용 예시

- **데이터베이스 인덱스**: `WHERE date BETWEEN '2024-01-01' AND '2024-12-31'` 같은 질의가 "첫 리프 탐색 + 체인 스캔"으로 처리됩니다. MySQL InnoDB의 클러스터드 인덱스가 이 구조예요.
- **파일 시스템**: 디렉터리 엔트리·익스텐트 관리(NTFS, XFS 등)에서 키 순 범위 접근이 필요한 곳.
- **코딩 테스트 맥락**: "삽입·삭제가 섞이는 와중에 구간 [low, high]의 원소를 정렬 순으로 모두 내놓아라" — 정렬 컨테이너가 없는 JS/TS 환경에서 직접 구현 대상이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 프로젝트의 `bPlusTree.ts`가 요구하는 스펙 그대로 살펴봅니다.

**속성(내부 상태)** — 노드는 두 종류입니다.

```ts
class BPlusLeafNode<T> {
  keys: T[] = [];                      // 실제 데이터 (정렬 유지)
  next: BPlusLeafNode<T> | undefined;  // 오른쪽 이웃 리프 (체인)
  readonly isLeaf = true;
}

class BPlusInternalNode<T> {
  keys: T[] = [];                                              // 라우팅 키 (이정표)
  children: (BPlusInternalNode<T> | BPlusLeafNode<T>)[] = [];  // 항상 keys보다 1개 많음
  readonly isLeaf = false;
}

type BPlusNode<T> = BPlusInternalNode<T> | BPlusLeafNode<T>;
```

트리 전체로는 `root`, 원소 수 `_size`, 최소 차수 `t`(기본 3), 비교 함수 `compare`를 유지합니다. 지켜야 할 불변식은 네 가지예요.

1. **모든 실제 데이터는 리프에만 있다.** 내부 노드의 키는 라우팅용 **복사본**이다.
2. 비루트 노드의 키 개수는 $t-1$ 이상 $2t-1$ 이하. 내부 노드의 자식 수는 키 수 + 1.
3. 내부 노드의 `keys[i]`를 기준으로: 왼쪽 서브트리의 모든 값 < `keys[i]` ≤ 오른쪽 서브트리의 모든 값.
4. 리프 체인(`next`)을 따라가면 전체 데이터가 **정렬 순서**로 나온다.

키가 $t-1$~$2t-1$개이므로 트리 높이는 $h = O(\log_t n)$입니다 — 노드 하나가 가지를 $t$~$2t$개로 벌리니, 층을 하나 내려갈 때마다 후보가 $t$분의 1로 줄어들어요.

`t = 2`로 작은 트리를 그려 보면:

```text
내부(이정표):            [ 3 , 5 ]
                        /    |    \
리프(데이터):    [1, 2] → [3, 4] → [5, 6, 7]
                       next     next            ← 체인이 정렬 순서를 실어 나른다

이정표 3, 5는 각각 "오른쪽 서브트리의 최솟값"의 복사본.
같은 3이 내부에도, 리프에도 있는 게 정상이다 (B-트리와 다른 점!)
```

**액션(연산)** — `bPlusTree.ts`가 선언한 6종 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(v)` | 리프까지 내려가 삽입, 넘치면 분할 | $O(\log_t n)$ |
| `delete(v)` | 리프에서 제거, 모자라면 빌리기/병합. 성공 여부 반환 | $O(\log_t n)$ |
| `has(v)` | 리프까지 내려가 존재 확인 | $O(\log_t n)$ |
| `range(low, high)` | 첫 리프 탐색 후 체인 순회 | $O(\log_t n + k)$ |
| `size()` | 원소 수 | $O(1)$ |
| `inOrder()` | 첫 리프부터 체인 전체 순회 | $O(n)$ |

핵심 연산 두 개만 그림으로 자세히 볼게요.

**① 리프 분할 — "복사 승격"**. `t = 2`면 노드당 키는 최대 $2t-1 = 3$개입니다. 4개가 되는 순간 분할해요.

```text
insert(4) 직후:   [ 1, 2, 3, 4 ]        ← 4개: 넘침!

                  mid = ⌈4/2⌉ = 2 에서 절단

분할 후:               [ 3 ]             ← 새 루트(내부): 3은 "복사"된 것
                      /     \
               [1, 2]  →  [3, 4]         ← 3이 리프에도 그대로 남아 있다!
                      next
```

B-트리는 분할할 때 가운데 키가 부모로 **이사**(리프에서 사라짐)하지만, B+ 트리는 오른쪽 리프의 첫 키를 부모로 **복사**합니다. 데이터는 전부 리프에 있어야 한다는 불변식 1을 지키기 위해서예요.

**② range — 내려간 뒤 옆으로**. `range(2, 3)`을 위 트리에서 실행하면:

```text
1단계: low=2로 라우팅.  루트 [3]에서 2 < 3 → 왼쪽 →  리프 [1, 2] 도착   O(log n)
2단계: 체인 직진.       [1, 2]에서 2 수집 → next → [3, 4]에서 3 수집,
                        4 > high 만나는 순간 중단                        O(k)
결과: [2, 3]
```

### 왜 모순 없이 작동하는가

**라우팅이 항상 옳은 이유**: 불변식 3("왼쪽 < `keys[i]` ≤ 오른쪽")이 살아 있는 한, "찾는 값이 `keys[i]`보다 작으면 왼쪽, 아니면 오른쪽" 규칙은 목표 리프를 정확히 찾습니다. 그럼 이 불변식은 누가 지켜 주나요? **분할이 지켜 줍니다.** 승격되는 키가 "새 오른쪽 리프의 첫 키(=그쪽 최솟값)"이므로, 승격 직후에도 왼쪽엔 그보다 작은 값만, 오른쪽엔 그 이상만 있어요. 귀납적으로: 빈 트리에서 시작해 모든 변형(삽입·분할·삭제·병합)이 불변식을 보존하므로, 어느 시점의 트리에서도 라우팅은 옳습니다.

**체인이 항상 정렬을 유지하는 이유**: 분할할 때 딱 두 줄이 체인을 잇습니다.

```text
newLeaf.next = leaf.next     ← ① 새 리프가 기존 오른쪽 이웃을 물려받고
leaf.next    = newLeaf       ← ② 원래 리프가 새 리프를 가리킨다

leaf → newLeaf → (원래 leaf.next)   : 잘린 두 조각이 제자리 순서로 꿰어진다
```

분할은 "정렬된 리프를 반으로 자르는" 연산이므로 체인의 정렬 순서가 깨질 틈이 없어요.

**range의 조기 중단이 안전한 이유**: 체인이 정렬되어 있으므로, `high`보다 큰 키를 처음 만난 순간 그 뒤의 모든 키도 `high`보다 큽니다. 더 볼 필요가 없어요.

**헷갈리기 쉬운 포인트** 세 가지를 짚어 둡니다.

- **`has`는 내부 노드에서 키를 발견해도 멈추면 안 됩니다.** 내부 키는 복사본이라, 리프의 원본이 삭제된 뒤에도 이정표로 남아 있을 수 있어요. 존재의 진실은 **리프에만** 있습니다. 반드시 리프까지 내려가 확인하세요.
- **B-트리 분할과 혼동.** "가운데 키가 올라간다"까지는 같지만, B-트리는 이동·B+는 복사입니다. 복사를 잊으면 리프에서 값이 사라져 range가 데이터를 잃어버려요.
- **삭제는 라우팅 키의 사후 관리가 필요합니다.** 리프에서 어떤 구간의 최솟값을 지우면 부모의 이정표가 낡은 값이 될 수 있어요. 라우팅 불변식은 "왼쪽 < 키 ≤ 오른쪽"이므로 낡은 이정표도 당장 라우팅을 틀리게 하진 않지만, 형제에게서 **빌리기(재분배)** 를 하거나 **병합**할 때는 부모 키를 새 경계값으로 갱신해야 합니다. 병합 시엔 체인도 `left.next = right.next`로 잇는 것을 잊지 마세요.

엣지 케이스 점검:

```text
빈 트리에 range/has     → [] / false (root가 undefined인 분기)
루트가 리프인 초기 단계 → 내부 노드 없이도 모든 연산 성립
중복 insert             → has로 확인 후 무시 (size 불변)
range(low, high)에 해당 값 없음 → 첫 리프부터 스캔하다 조건 미달로 빈 배열
```

## 아이디어를 코드로 옮기기

`bPlusTree.ts`의 인터페이스(제네릭 `T`, comparator, 기본 `t = 3`)에 맞춰 핵심 연산을 구현합니다. 재귀 삽입이 "분할이 일어났으면 (승격 키, 새 오른쪽 자식)을 반환"하는 패턴이 가장 깔끔해요.

```ts
class BPlusTree<T> {
  private root: BPlusNode<T> | undefined = undefined;
  private firstLeaf: BPlusLeafNode<T> | undefined = undefined;
  private _size = 0;
  private t: number;
  private compare: (a: T, b: T) => number;

  constructor(t: number = 3, comparator?: (a: T, b: T) => number) {
    this.t = t;
    this.compare = comparator ?? ((a, b) => (a < b ? -1 : a > b ? 1 : 0));
  }

  private findLeaf(value: T): BPlusLeafNode<T> | undefined {
    let node = this.root;
    while (node !== undefined && !node.isLeaf) {
      // value보다 큰 첫 라우팅 키의 위치가 내려갈 자식 번호
      let i = 0;
      while (i < node.keys.length && this.compare(value, node.keys[i]) >= 0) i++;
      node = node.children[i];
    }
    return node;
  }

  has(value: T): boolean {
    const leaf = this.findLeaf(value); // 내부에서 멈추지 않고 리프까지!
    return leaf !== undefined && leaf.keys.some((k) => this.compare(k, value) === 0);
  }

  insert(value: T): void {
    if (this.has(value)) return; // 중복 무시
    if (this.root === undefined) {
      const leaf = new BPlusLeafNode<T>();
      leaf.keys.push(value);
      this.root = leaf;
      this.firstLeaf = leaf;
      this._size = 1;
      return;
    }
    const split = this.insertInto(this.root, value);
    if (split !== undefined) {
      // 루트가 쪼개졌으면 한 층 올린다
      const newRoot = new BPlusInternalNode<T>();
      newRoot.keys = [split.key];
      newRoot.children = [this.root, split.right];
      this.root = newRoot;
    }
    this._size++;
  }

  // 분할이 없으면 undefined, 있으면 부모에 넣을 (승격 키, 새 오른쪽 노드)
  private insertInto(node: BPlusNode<T>, value: T): { key: T; right: BPlusNode<T> } | undefined {
    if (node.isLeaf) {
      let i = 0;
      while (i < node.keys.length && this.compare(node.keys[i], value) < 0) i++;
      node.keys.splice(i, 0, value); // 정렬 위치에 삽입

      if (node.keys.length <= 2 * this.t - 1) return undefined;

      // 리프 분할: 오른쪽 절반을 새 리프로, 첫 키를 "복사" 승격
      const mid = Math.ceil(node.keys.length / 2);
      const right = new BPlusLeafNode<T>();
      right.keys = node.keys.splice(mid);
      right.next = node.next; // ① 체인 잇기 — 순서가 생명
      node.next = right;      // ②
      return { key: right.keys[0], right }; // 복사 (리프에도 남는다)
    }

    let i = 0;
    while (i < node.keys.length && this.compare(value, node.keys[i]) >= 0) i++;
    const split = this.insertInto(node.children[i], value);
    if (split === undefined) return undefined;

    node.keys.splice(i, 0, split.key);
    node.children.splice(i + 1, 0, split.right);

    if (node.keys.length <= 2 * this.t - 1) return undefined;

    // 내부 분할: 가운데 키는 "이동" 승격 (B-트리와 동일)
    const mid = Math.floor(node.keys.length / 2);
    const promoted = node.keys[mid];
    const right = new BPlusInternalNode<T>();
    right.keys = node.keys.splice(mid + 1);
    right.children = node.children.splice(mid + 1);
    node.keys.pop(); // promoted를 내부에서 제거
    return { key: promoted, right };
  }

  range(low: T, high: T): T[] {
    const result: T[] = [];
    let leaf = this.findLeaf(low); // O(log n): 시작 리프
    while (leaf !== undefined) {
      for (const key of leaf.keys) {
        if (this.compare(key, high) > 0) return result; // 조기 중단
        if (this.compare(key, low) >= 0) result.push(key);
      }
      leaf = leaf.next; // O(k): 체인 직진
    }
    return result;
  }

  size(): number {
    return this._size;
  }

  inOrder(): T[] {
    const result: T[] = [];
    for (let leaf = this.firstLeaf; leaf !== undefined; leaf = leaf.next) {
      result.push(...leaf.keys);
    }
    return result;
  }
}
```

`delete`는 위 삽입의 거울상입니다 — 리프에서 제거 후 키가 $t-1$개 미만이면 **형제에게서 빌리고(재분배 + 부모 라우팅 키 갱신)**, 형제도 여유가 없으면 **병합(부모 키 제거 + `left.next = right.next`로 체인 잇기)** 하며 위로 전파합니다. 분량상 코드 전체 대신 흐름만 적었지만, "리프에서 처리 → 넘침/모자람을 부모로 전파"라는 골격은 삽입과 완전히 같아요.

구현에서 놓치기 쉬운 지점들:

- **체인 잇기 두 줄의 순서.** `node.next = right`를 먼저 쓰면 원래의 오른쪽 이웃을 잃어버립니다. **반드시 `right.next = node.next`가 먼저**예요. 기억법: "새 리프가 유산(이웃)을 물려받은 다음에 상속자로 지명한다".
- **리프 분할은 복사(`right.keys[0]`이 리프에 남음), 내부 분할은 이동(`node.keys.pop()`).** 두 분할이 다르다는 것이 B+ 구현의 축입니다. 리프에서 `pop`을 해 버리면 데이터가 유실되고, 내부에서 복사를 하면 같은 이정표가 두 번 나와 자식 수가 어긋나요.
- **라우팅 비교는 `>=`.** 불변식이 "키 ≤ 오른쪽"이므로, 찾는 값이 라우팅 키와 같으면 **오른쪽**으로 가야 합니다. `>`로 쓰면 경계값이 왼쪽으로 새서 `has`가 거짓 음성을 냅니다.
- **`firstLeaf` 유지.** 첫 리프 포인터가 있어야 `inOrder`가 라우팅 없이 `O(n)`에 끝납니다. 루트 생성 시 함께 세팅하세요.

## 실행 시각화

`t = 2`인 B+ 트리에 `1, 2, 3, 4`를 차례로 삽입하면 리프가 넘쳐 분할이 일어나고(3이 내부로 **복사** 승격), 이어서 `range(2, 3)`이 리프 체인을 타고 두 리프에 걸친 결과를 모읍니다. 이어서 `delete(3)`을 실행하면 오른쪽 리프에서 3이 사라지지만 — 남은 키 1개는 최소치($t-1=1$)를 만족하므로 언더플로우가 아니에요 — 부모의 라우팅 키는 **3 그대로** 남습니다(낡았지만 무해). 마지막 `delete(4)`에서 그 리프가 완전히 비어 진짜 언더플로우가 나고, 그제서야 왼쪽 형제에게서 빌려오며 라우팅 키가 새 경계값 2로 갱신돼요. array 패널은 리프 체인에 실린 데이터 전체(정렬 순서)를 보여줍니다.

정리하면, B+ Tree의 세 가지 설계 결정이 서로 맞물려 목표를 달성합니다. **실제 데이터는 리프에만** 두고 내부 노드는 라우팅 키(리프 값의 복사본)만 들며, 그 **리프들을 `next` 체인으로 꿰어** 정렬 순서를 실어 나릅니다. 덕분에 리프까지 내려가는 `insert`·`delete`·`has`는 트리 높이에 비례하는 $O(\log_t n)$이고, `range`는 "첫 리프 탐색 $O(\log_t n)$ + 체인 직진 $O(k)$"로 정확히 $O(\log_t n + k)$에 끝나 — 애초에 노렸던 범위 질의 이점을 그대로 얻습니다. 라우팅 키가 낡아도 라우팅이 틀리지 않고, 빌리기·병합 때만 경계값을 갱신한다는 점만 지키면 이 복잡도가 삽입·삭제가 섞이는 내내 유지돼요.
