# Binary Search Tree 솔루션 분석 보고서

## 1. 방향성 분석

문제는 정수 키를 저장하는 이진 탐색 트리(BST)에 `insert` / `search` / `delete` / `inorder` / `min` / `max` 여섯 연산을 구현하는 표준 문제이다. 솔루션의 큰 그림은 다음과 같다.

- `Node` 클래스에 `key`, `left`, `right` 세 필드를 두고, `BinarySearchTree`는 `root` 하나만 보유한다.
- 여섯 연산 모두 **재귀 없이 반복문(iterative)** 으로 구현한다. `insert` / `search` / `min` / `max` / `delete`의 탐색 단계는 `while` 루프로 루트에서 아래로 내려가고, `inorder`는 명시적 스택 배열로 재귀를 대체한다.
- `delete`는 삭제 대상의 자식 개수에 따라 세 경우(0개 / 1개 / 2개)로 분기하고, 자식이 둘인 경우 오른쪽 서브트리의 최솟값(in-order successor)을 찾아 키를 옮긴 뒤 후계자 노드를 다시 삭제하는 방식을 취한다.

이 설계 방향은 **전부 올바르다.** 특히 다음 두 가지는 이 문제에서 요구되는 정석 그대로이다.

1. `delete`의 3분기 구조와 "자식이 둘인 경우를 후계자 키 이동으로 자식 0~1개 문제로 환원한다"는 발상은 Hibbard 삭제(Hibbard deletion)라 불리는 표준 알고리즘과 정확히 일치한다.
2. 반복문 기반 구현은 트리가 한쪽으로 치우쳐 높이가 $O(n)$이 되어도 재귀 호출 스택이 넘치지 않는다는 실질적 이점이 있다. 이 문제의 BST는 자체 균형(self-balancing) 기능이 없어 오름차순 삽입 시 높이가 $n$까지 자라므로, 재귀를 피한 선택은 방향성 측면에서 오히려 더 안전한 쪽이다.

다만 세부 구현에서 다음 두 가지 설계 판단이 결함으로 이어졌다(2장에서 재현과 함께 다룬다).

- **`delete`의 보조 함수가 "부모의 어느 쪽 자식인가"를 판정할 때 `parent.right.key === node.key`처럼 키를 비교한다.** 참조 동일성(`parent.right === node`)이 아니라 키 값을 비교하므로 `parent.right`가 `null`인 경우를 표현할 수 없고, 그 상황에서 널 역참조가 발생한다.
- **`inorder`의 스택 순회가 "현재 노드(`node`)와 스택 최상단이 같다"는 불변식을 한 분기에서 깨뜨린다.** 그 결과 이미 방문한 서브트리를 다시 순회하며, 최악의 경우 출력 길이가 노드 수의 지수 함수로 폭발한다.

`insert`, `search`, `min`, `max`는 결함 없이 정확하다.

### 결함 A. `delete` 보조 함수의 널 역참조 (실행 중단, TypeError)

```ts
private deleteNoChild(parent: Node | null, node: Node) {
  if (parent === null) { this.root = null; return; }

  if (parent!.right!.key === node.key) {   // ← parent.right 가 null 이면 크래시
    parent.right = null;
  } else {
    parent.left = null;
  }
}
```

`deleteOneChild`도 동일한 형태의 판정(`parent!.right!.key === node.key`)을 갖고 있다.

이 판정의 의도는 "삭제 대상 `node`가 `parent`의 오른쪽 자식인가, 왼쪽 자식인가"를 구분하는 것이다. 그런데 `parent.right`가 `null`인 경우, 즉 **`parent`가 왼쪽 자식만 가진 노드인 경우**에는 `null.key`를 읽으려 하므로 `TypeError`가 발생한다. `!` 비-널 단정(non-null assertion)은 타입 검사기의 경고만 지우는 표기이며 실행 시점의 값이 `null`인 사실은 바꾸지 못한다.

실제 재현 결과는 다음과 같다.

```
=== B. delete: 부모의 right 가 null 인 왼쪽 자식 리프 삭제 ===
  insert(50) insert(30) → delete(30)
  THROW: null is not an object (evaluating 'parent.right.key')

=== C. delete: 두 자식 노드, successor 가 깊은 왼쪽 ===
  insert(50) insert(30) insert(70) insert(60) insert(55) → delete(50)
  THROW: null is not an object (evaluating 'parent.right.key')

=== D. delete: 자식 하나(왼쪽만) 노드 삭제, 부모 right null ===
  insert(50) insert(30) insert(20) → delete(30)
  THROW: null is not an object (evaluating 'parent.right.key')
```

케이스 B는 `insert(50); insert(30); delete(30);` 세 줄로 즉시 터지는, 가장 기본적인 리프 삭제이다.

케이스 C는 자식이 둘인 노드를 삭제할 때 후계자가 오른쪽 서브트리의 깊은 왼쪽에 있는 경우이다. `findSuccessor(50, 70)`은 `70 → 60 → 55`로 내려가 `{ parent: 60, node: 55 }`를 반환하고, `deleteNoChild(60, 55)`가 호출된다. 노드 `60`은 왼쪽 자식 `55`만 갖고 오른쪽 자식이 없으므로 `parent.right`가 `null`이어서 크래시한다.

**왜 5개 `delete` 테스트가 모두 통과했는가**: 현재 테스트의 `delete` 케이스는 `[5,3,7]`, `[5,3,7,6]`, `[5,3,7,6,8]` 세 가지 트리에서만 삭제를 수행한다. 이 트리들에서는 `deleteNoChild` / `deleteOneChild`에 전달되는 `parent`가 **항상 오른쪽 자식을 갖고 있다.**

| 테스트 | 삭제 | 전달되는 parent | parent.right | 결과 |
|---|---|---|---|---|
| 리프 노드 삭제 | `delete(3)` on `[5,3,7]` | `5` | `7` (존재) | 우회 |
| 자식 하나짜리 | `delete(7)` on `[5,3,7,6]` | `5` | `7` (존재) | 우회 |
| 자식 둘짜리 | `delete(7)` on `[5,3,7,6,8]` | 키가 옮겨진 `7` | `8` (존재) | 우회 |
| 루트 삭제 | `delete(5)` on `[5,3,7]` | 키가 옮겨진 `5` | `7` (존재) | 우회 |
| 없는 키 삭제 | `delete(99)` | — | 탐색 실패로 조기 반환 | 우회 |

"부모가 왼쪽 자식만 가진 상태"를 만드는 테스트가 하나도 없어서 결함 A가 드러나지 않았다.

### 결함 B. `inorder` 스택 순회의 불변식 붕괴 (오답 + 지수 시간)

```ts
let node: Node | null = this.root as Node;
stack.push(node);

while (stack.length !== 0) {
  if (node.left !== null) {
    node = node.left;
    stack.push(node);
  } else {
    node = stack.pop() as Node;
    arr.push(node.key);

    if (node.right !== null) {
      node = node.right;
      stack.push(node);
    }
    // node.right === null 이면 node 가 갱신되지 않는다 ← 여기가 결함
  }
}
```

이 순회가 성립하려면 **반복문 진입 시점마다 `node`가 스택 최상단과 같은 노드여야 한다**는 불변식이 유지되어야 한다. 코드를 분기별로 점검하면 다음과 같다.

- `node.left !== null`인 분기: `node`를 왼쪽 자식으로 옮기고 곧바로 `push`한다 → 불변식 유지.
- `node.left === null`이고 `node.right !== null`인 분기: `pop`으로 자기 자신을 꺼내 방문한 뒤, `node`를 오른쪽 자식으로 옮기고 `push`한다 → 불변식 유지.
- **`node.left === null`이고 `node.right === null`인 분기: `pop`으로 자기 자신을 꺼내 방문했지만 `node`는 그 노드를 계속 가리킨다. 스택 최상단은 아직 방문하지 않은 조상으로 바뀌었으므로 → 불변식 붕괴.**

불변식이 깨진 뒤에도 우연히 정답이 나오는 경우가 있어서 결함이 잘 드러나지 않는다. `node`가 방문 완료된 노드를 가리키는 상태에서 다음 반복에 진입하면 `node.left`는 `null`이므로 `else` 분기로 들어가 조상 $A$를 `pop`하고 방문하는데, 그 조상이 실제로 중위 순회의 다음 노드이기 때문이다. 문제는 이때 `node`가 $A$로 갱신된다는 점이다.

- $A$의 오른쪽 자식이 존재하면 `node`는 오른쪽 자식으로 옮겨지고 `push`되어 불변식이 회복된다.
- **$A$의 오른쪽 자식이 없고 왼쪽 자식이 있으면**, 다음 반복에서 `node.left !== null`이 참이 되어 **이미 전부 방문한 $A$의 왼쪽 서브트리로 다시 내려간다.** 같은 키들이 `arr`에 중복 기록되고, 그 왼쪽 서브트리에 동일 조건의 노드가 또 있으면 재순회가 중첩되어 횟수가 배로 늘어난다.

정리하면 결함 B는 **왼쪽 자식이 있고 오른쪽 자식이 없는 노드 $A$가 존재하며, $A$를 방문하는 시점에 스택에 아직 방문하지 않은 조상이 남아 있을 때**(즉 $A$가 중위 순회의 마지막 노드가 아닐 때) 발동한다. 스택이 마침 비어 있으면 `while` 조건이 거짓이 되어 루프가 종료되므로 결과가 우연히 옳게 나온다.

재현 결과:

```
=== A. inorder: 왼쪽 자식만 가진 노드 + 스택에 남은 조상 ===
  insert(100) insert(50) insert(30) insert(200)
  inorder = [30, 50, 30, 100, 200]      expected = [30, 50, 100, 200]

=== A2. 내림차순 삽입 inorder ===
  insert(50) insert(40) insert(30) insert(20) insert(10)
  inorder = [10,20,10,30,10,20,10,40,10,20,10,30,10,20,10,50]   expected = [10,20,30,40,50]
```

케이스 A는 노드 4개로 재현되는 최소 사례이다. 노드 `50`은 왼쪽 자식 `30`만 갖고 오른쪽 자식이 없으며, `50`을 방문할 때 스택에 조상 `100`이 남아 있으므로 `30`이 두 번 출력된다.

**출력 길이가 지수적으로 증가한다.** 왼쪽 자식만 이어지는 사슬(내림차순 삽입) $n$개에 대해 출력 길이를 측정한 결과, 정확히 $2^{\,n-1}$이었다.

```
n= 1 출력길이=      1 (2^(n-1)=1)
n= 5 출력길이=     16 (2^(n-1)=16)
n=10 출력길이=    512 (2^(n-1)=512)
n=15 출력길이=  16384 (2^(n-1)=16384)
n=20 출력길이= 524288 (2^(n-1)=524288)
```

즉 `inorder`의 시간 복잡도는 최악의 경우 명세가 요구하는 $O(n)$이 아니라 $\Theta(2^{n})$이다. 노드 40개짜리 내림차순 사슬만 만들어도 출력 원소가 약 $5.5 \times 10^{11}$개가 되어 사실상 종료하지 않는다.

**왜 `inorder` 테스트 4개가 모두 통과했는가**: 통과한 테스트의 트리들은 결함 B의 발동 조건("왼쪽 자식만 가진 노드"의 존재)을 우연히 전부 회피한다.

| 테스트 | 삽입 키 | 트리 특성 | 결과 |
|---|---|---|---|
| inorder 오름차순 반환 | `5,3,7,1,4,6,8` | 완전 이진 트리. 내부 노드 `5`, `3`, `7`은 모두 자식이 둘, 나머지는 리프 → 왼쪽 자식만 가진 노드가 없다 | 우회 |
| 오름차순 삽입 | `1,2,3,4,5` | 오른쪽 자식만 이어지는 사슬 → 왼쪽 자식을 가진 노드가 아예 없다 | 우회 |
| 빈 트리 | — | 조기 반환 `[]` | 우회 |
| 리프/루트 삭제 후 inorder | `[5,7]`, `[3,7]` 등 | 노드 2개짜리 트리라 왼쪽 자식만 가진 노드를 방문할 때 스택이 이미 비어 루프가 종료된다 | 우회 |

특히 "오름차순으로 삽입해도 search/inorder가 올바르다" 테스트는 치우친 트리를 검사하려는 의도였으나, **오른쪽으로만** 치우친 트리를 만들었기 때문에 결함 B와 정확히 반대쪽 모양이 되어 통과했다. 만약 같은 테스트가 내림차순(`5,4,3,2,1`)이었다면 즉시 실패한다.

### 결함이 아닌 것 — 키 비교 방식 자체는 이 구현 안에서 우연히 안전하다

결함 A의 판정식은 참조 비교가 아니라 키 비교인데, 자식이 둘인 노드를 삭제할 때 `node.key = successor.node.key`를 먼저 수행하므로 **트리에 같은 키를 가진 노드가 일시적으로 두 개 존재하는 상태**가 만들어진다. 이 상태에서 키 비교가 엉뚱한 자식을 가리킬 위험이 있는지 별도로 확인했다.

널 역참조만 방어하고(자식 판정은 키 비교로 그대로 유지) 나머지 로직을 원본과 동일하게 둔 버전으로 무작위 대조 검증을 수행한 결과:

```
널 가드만 추가한 delete: 실패 시도 0/5000
```

키가 중복되는 유일한 시점은 삭제 대상 노드와 후계자 노드 사이이며, 후계자를 실제로 떼어낼 때 전달되는 `parent`의 오른쪽 자식이 후계자 자신이거나 후계자보다 큰 키를 갖기 때문에 오판이 발생하지 않는다. 따라서 **`delete`에서 실제로 관측되는 결함은 널 역참조 하나뿐**이다. 다만 이 안전성은 "삽입이 중복 키를 거부한다"와 "키 이동 직후 곧바로 후계자를 제거한다"는 두 전제에 의존하는 우연한 성질이므로, 3장에서 제시하는 참조 비교 방식으로 바꾸는 편이 견고하다.

## 3. 최적화 분석

`insert` / `search` / `min` / `max`는 이미 트리 높이 $h$에 비례하는 $O(h)$ 시간, $O(1)$ 추가 공간으로 최적이며 개선할 지점이 없다. 개선이 필요한 대상은 `inorder`(정확성 + 지수 시간)와 `delete`(널 역참조)이다.

### 3.1. 개선 가능한 핵심 아이디어

#### 3.1.1. 원형에서 문제 해결책을 유도하는 전개 과정 — 중위 순회

**원형 1: 중위 순회의 재귀적 정의**

중위 순회(in-order traversal)는 이진 트리 $T$에 대해 다음과 같이 정의된다. $T.left$는 왼쪽 서브트리, $T.right$는 오른쪽 서브트리, $T.key$는 뿌리 노드의 키이고, $\mathrm{nil}$은 빈 트리를 뜻한다. 연산자 $+\!\!+$는 두 수열을 앞뒤로 이어 붙이는 연결(concatenation)이다.

$$
\mathrm{inorder}(T) =
\begin{cases}
\langle\,\rangle & (T = \mathrm{nil}) \\[2pt]
\mathrm{inorder}(T.left) \;+\!\!+\; \langle T.key \rangle \;+\!\!+\; \mathrm{inorder}(T.right) & (T \neq \mathrm{nil})
\end{cases}
$$

BST의 정의상 왼쪽 서브트리의 모든 키는 $T.key$보다 작고 오른쪽 서브트리의 모든 키는 $T.key$보다 크므로, 이 정의를 따르면 결과는 반드시 오름차순 수열이 된다.

**원형 2: 재귀를 명시적 스택으로 바꿀 때 지켜야 하는 상태**

위 정의를 반복문으로 바꾸려면, 재귀 호출이 자동으로 기억해 주던 정보를 스택에 직접 담아야 한다. 필요한 정보는 정확히 하나이다.

> **"왼쪽 서브트리 처리는 끝났지만, 자기 자신은 아직 방문하지 않은 노드들"의 목록.**

이 노드들은 방문 순서를 거꾸로 뒤집은 순서로 처리되어야 한다. 가장 최근에 지나온 노드가 가장 먼저 방문되어야 하므로, 후입선출(LIFO) 자료구조인 스택이 정확히 들어맞는다.

여기에 "지금 어느 서브트리를 처리해야 하는가"를 가리키는 포인터 $cur$ 하나를 추가한다. $cur$의 의미를 다음과 같이 **엄격하게** 고정한다.

> $cur$ = **아직 아무 처리도 시작하지 않은** 서브트리의 뿌리. 처리할 서브트리가 없으면 $cur = \mathrm{nil}$.

이 정의에서 두 가지 규칙이 자동으로 따라 나온다.

- 규칙 1: $cur \neq \mathrm{nil}$이면, 아직 왼쪽부터 내려가야 한다. $cur$을 스택에 넣고 $cur \leftarrow cur.left$로 옮긴다. 이 과정을 $cur = \mathrm{nil}$이 될 때까지 반복하면, 스택에는 "왼쪽 서브트리 처리가 끝났고 아직 방문하지 않은 노드들"이 쌓인다.
- 규칙 2: $cur = \mathrm{nil}$이면 새로 시작할 서브트리가 없다는 뜻이므로, 스택에서 노드 하나를 꺼내 방문(키를 결과에 추가)한다. 그 노드의 왼쪽과 자기 자신은 처리가 끝났으므로 남은 일은 오른쪽 서브트리뿐이다. 따라서 $cur \leftarrow (\text{꺼낸 노드}).right$로 설정한다. **오른쪽 자식이 없으면 $cur$은 $\mathrm{nil}$이 되고, 이는 "새로 시작할 서브트리가 없다"는 올바른 상태이다.**

종료 조건은 "$cur = \mathrm{nil}$이면서 스택도 비어 있음"이다. 새로 시작할 서브트리도 없고 방문을 기다리는 노드도 없다는 뜻이다.

이를 그대로 옮기면 표준 반복형 중위 순회가 된다.

```
cur ← root
stack ← 빈 스택

while cur ≠ nil 또는 stack 이 비어있지 않은 동안:
    while cur ≠ nil:            # 규칙 1
        stack 에 cur 를 넣는다
        cur ← cur.left
    top ← stack 에서 꺼낸다      # 규칙 2
    결과에 top.key 를 추가한다
    cur ← top.right
```

각 노드는 정확히 한 번 `push`되고 한 번 `pop`되므로 시간 복잡도는 $O(n)$이고, 스택에 동시에 들어가는 노드 수는 트리 높이를 넘지 않으므로 추가 공간은 $O(h)$이다.

**현재 솔루션이 원형에서 이탈한 지점**

현재 구현은 위 두 규칙과 거의 같은 동작을 하지만, $cur$($=$ 코드의 `node`)의 의미를 "아직 처리를 시작하지 않은 서브트리의 뿌리"로 고정하지 않았다. 규칙 2에 해당하는 분기에서 오른쪽 자식이 없을 때 `node`를 `null`로 되돌리지 않고, **방금 방문을 마친 노드를 계속 가리키게** 두었다.

```ts
node = stack.pop() as Node;
arr.push(node.key);

if (node.right !== null) {
  node = node.right;   // 오른쪽이 있을 때는 cur ← top.right 와 동일 (올바름)
  stack.push(node);
}
// 오른쪽이 없을 때 node ← null 이 빠져 있다
```

`node`가 "처리를 시작하지 않은 서브트리"가 아니라 "이미 방문을 끝낸 노드"를 가리키게 되면, 다음 반복에서 검사하는 `node.left`는 **이미 전부 방문한 왼쪽 서브트리**를 가리킨다. 2장에서 확인한 재순회와 지수적 폭발이 여기서 비롯된다.

또한 현재 구현은 종료 조건을 `stack.length !== 0` 하나로만 두었다. 원형의 종료 조건은 "$cur = \mathrm{nil}$ **그리고** 스택이 비어 있음"이며, `cur`에 해당하는 조건이 빠져 있다. 규칙 1을 내부 `while` 루프로 묶지 않고 외부 루프의 `if` 분기로 펼친 것 자체는 동작상 동등하지만, `cur`의 의미가 흐려지면서 이 조건 누락과 결합해 결함으로 이어졌다.

**최소 수정**: 방문 후 `node`를 항상 `top.right`로 설정한다(오른쪽이 없으면 `null`). 스택 `push`는 규칙 1의 하강 루프에서만 수행한다.

```ts
inorder(): number[] {
  const arr: number[] = [];
  const stack: Node[] = [];
  let node: Node | null = this.root;

  while (node !== null || stack.length > 0) {
    while (node !== null) {      // 규칙 1: 왼쪽 끝까지 내려가며 쌓는다
      stack.push(node);
      node = node.left;
    }
    const top = stack.pop()!;    // 규칙 2: 방문하고 오른쪽으로 넘어간다
    arr.push(top.key);
    node = top.right;
  }

  return arr;
}
```

이 형태에서는 `this.root === null`인 경우도 별도 분기 없이 처리된다. `node`가 `null`이고 스택이 비어 있어 루프에 진입하지 않고 `[]`를 반환한다. 원본의 `if (this.root === null) return []` 조기 반환과 `as Node` 단정도 함께 불필요해진다.

검증 결과, 왼쪽 사슬 2000개(내림차순 삽입)에 대해 출력 길이 2000, 완전 오름차순, 0.20ms로 처리된다. 원본은 같은 입력에서 $2^{1999}$개를 출력하려 하므로 종료하지 않는다.

#### 3.1.2. 원형에서 문제 해결책을 유도하는 전개 과정 — BST 삭제

**원형: Hibbard 삭제**

BST에서 키 $k$를 가진 노드 $x$를 제거하는 표준 절차는 자식 수에 따라 세 경우로 나뉜다. 이때 지켜야 하는 불변식은 "삭제 후에도 모든 노드에 대해 왼쪽 서브트리의 키 $<$ 자기 키 $<$ 오른쪽 서브트리의 키"가 성립해야 한다는 것이다.

1. **자식이 0개**: $x$를 부모에서 떼어낸다. 부모의 해당 자식 포인터를 $\mathrm{nil}$로 만든다.
2. **자식이 1개**: 그 유일한 자식 $c$를 $x$의 자리에 올린다. $c$의 서브트리에 속한 모든 키는 $x$가 원래 있던 위치에 요구되는 대소 범위 안에 이미 들어 있으므로, 부모의 자식 포인터를 $c$로 바꾸기만 하면 불변식이 유지된다.
3. **자식이 2개**: $x$를 곧바로 떼어낼 수 없다(자식 둘을 한 자리에 올릴 수 없다). 대신 $x$의 자리에 들어가도 불변식을 깨지 않는 키를 찾아 옮긴다. 그 키는 **$x$의 오른쪽 서브트리의 최솟값**(중위 순회 기준 $x$의 바로 다음 노드, in-order successor) $s$ 또는 $x$의 왼쪽 서브트리의 최댓값(predecessor)이다. $s.key$를 $x.key$에 복사한 다음, **$s$를 삭제 대상으로 삼아 다시 삭제한다.**

3번에서 재삭제가 반복되지 않는 이유가 이 알고리즘의 핵심이다. $s$는 오른쪽 서브트리에서 왼쪽 자식을 따라 끝까지 내려가서 찾은 노드이므로, **정의상 $s.left = \mathrm{nil}$이다.** 따라서 $s$의 자식 수는 0개 또는 1개(오른쪽 자식만)이며, 3번 경우가 다시 발생하는 일은 없다. 즉 **자식 2개 문제는 항상 자식 0~1개 문제로 한 번에 환원된다.**

**환원 구조를 코드에 반영하는 방법**

원형의 3번이 "자식 0~1개 문제로 환원된다"는 사실은, 코드에서 **분기를 세 개 유지할 필요가 없다**는 뜻이다. 자식이 둘인 경우 삭제 대상 포인터와 부모 포인터를 후계자 쪽으로 갱신해 버리면, 그 뒤로는 자식 0~1개 처리 코드 하나만 있으면 된다. 자식 0개는 "떼어낼 자식이 $\mathrm{nil}$인 1개짜리"와 동일하게 다룰 수 있으므로(`node.left ?? node.right`가 `null`이 되는 것이 곧 0개 경우), 결국 필요한 것은 다음 두 조각뿐이다.

- 후계자 환원: 자식이 둘이면 키를 옮기고 `(parent, node)`를 `(후계자의 부모, 후계자)`로 바꾼다.
- 자식 연결: 부모의 자식 포인터를 `node.left ?? node.right`로 교체한다.

두 번째 조각에서 "부모의 어느 쪽 자식인가"는 **참조 동일성**으로 판정해야 한다. `parent.left === node`는 `parent.left`가 `null`이어도 안전하게 `false`가 되므로(널 역참조가 발생하지 않는다), 결함 A가 구조적으로 제거된다. 키 비교는 값이 같은 다른 노드를 오판할 여지가 있고 `null` 자식을 표현하지 못한다는 두 가지 약점을 동시에 갖는다.

```ts
/** parent 의 자식 중 child(참조 동일)를 next 로 교체한다. parent 가 null 이면 root 를 교체한다. */
private replaceChild(parent: Node | null, child: Node, next: Node | null): void {
  if (parent === null) this.root = next;
  else if (parent.left === child) parent.left = next;
  else parent.right = next;
}

delete(key: number): void {
  let parent: Node | null = null;
  let node: Node | null = this.root;

  while (node !== null && node.key !== key) {   // 1. 대상과 그 부모를 찾는다
    parent = node;
    node = key > node.key ? node.right : node.left;
  }
  if (node === null) return;                     // 없는 키는 무시

  if (node.left !== null && node.right !== null) {
    // 2. 자식 2개 → 후계자 키를 옮기고 삭제 대상을 후계자로 교체 (자식 0~1개로 환원)
    let sParent: Node = node;
    let s: Node = node.right;
    while (s.left !== null) {
      sParent = s;
      s = s.left;
    }
    node.key = s.key;
    parent = sParent;
    node = s;                                    // s.left === null 이 보장된다
  }

  // 3. 자식 0개 또는 1개 → 유일한 자식(없으면 null)을 자기 자리에 올린다
  this.replaceChild(parent, node, node.left ?? node.right);
}
```

원본과 비교하면 `deleteNoChild`, `deleteOneChild`, `findSuccessor` 세 보조 함수가 `replaceChild` 하나로 통합된다. 원본이 자식 0개와 1개를 별도 함수로 나눈 것은 "0개는 `null`을 연결하고 1개는 자식을 연결한다"는 차이 때문이지만, `node.left ?? node.right`가 자식이 없을 때 `null`을 내놓으므로 두 경우는 같은 식으로 처리된다. 또한 원본이 후계자 처리에서 `successor.node.right !== null` 여부로 다시 두 함수를 나눈 분기도 함께 사라진다.

**검증 결과**: 위 `delete`와 3.1.1의 `inorder`를 적용한 구현으로 무작위 대조 검증(2000회 시도 × 40연산, `insert`/`delete` 혼합, 매 연산마다 `inorder`·`search`·`min`·`max`를 `Set` 모델과 대조)을 수행한 결과 **실패 0건**이었다.

```
=== 수정판 무작위 대조 테스트 (2000 시도 x 40 연산) ===
실패 시도: 0/2000

=== 수정판 왼쪽 사슬 / 성능 ===
왼쪽 사슬 2000개: 출력길이=2000, 정렬여부=true, 0.20ms
```

같은 검증을 원본에 수행한 결과가 290/300 실패였으므로, 두 결함이 모두 제거되었음이 확인된다.

### 3.2. 복잡도 정리

수정 후 각 연산의 복잡도는 다음과 같다. $h$는 트리 높이이며, 이 BST는 자체 균형 기능이 없으므로 무작위 삽입에서 $h = O(\log n)$, 정렬된 순서로 삽입하는 최악의 경우 $h = n$이다.

| 연산 | 시간 | 추가 공간 | 비고 |
|---|---|---|---|
| `insert` | $O(h)$ | $O(1)$ | 원본도 최적 |
| `search` | $O(h)$ | $O(1)$ | 원본도 최적 |
| `delete` | $O(h)$ | $O(1)$ | 후계자 탐색을 포함해도 경로 길이 합은 $O(h)$ |
| `inorder` | $O(n)$ | $O(h)$ | 원본은 최악 $\Theta(2^{n})$ |
| `min` / `max` | $O(h)$ | $O(1)$ | 원본도 최적 |

문제 주석이 명시한 목표(균형 트리 기준 `insert`/`search`/`delete` $O(\log n)$ 평균·$O(n)$ 최악, `inorder` $O(n)$)와 정확히 일치한다.

### 3.3. 부수적으로 정리할 수 있는 지점

정확성과 무관하나, 위 수정을 적용하면 자연히 해소되는 항목들이다.

- **불필요한 비-널 단정 `!`와 옵셔널 체이닝 `?.`**: `delete` 본문의 `node?.right === null`은 바로 위의 `if (node === null) return;`으로 이미 `node`가 `Node`로 좁혀진 뒤이므로 `?.`가 필요 없다. `node!.right`, `parent!.right!`의 `!`도 마찬가지이다. `!`는 타입 검사기의 경고만 제거하므로, 결함 A처럼 실제 `null`을 가리는 방향으로 작용할 수 있다. `while (node !== null && node.key !== key)` 형태로 조건을 합치면 좁히기(narrowing)가 자연히 이루어져 단정 표기가 사라진다.
- **`search`의 중복 널 검사**: 첫 줄의 `if (this.root === null) return false;`는 뒤따르는 `while (node)`가 같은 조건을 이미 처리하므로 제거해도 동작이 같다.
- **`insert`의 도달 불가 코드**: `while (node !== null)` 루프는 모든 분기가 `return`으로 끝나거나 자식으로 내려가므로 정상 종료되지 않는다. 루프 뒤로는 제어가 도달하지 않는다(동작상 문제는 없다).
- **`inorder`의 주석**: 본문에 남아 있는 절차 메모("노드 푸시 / 왼쪽 있으면 넘어가기 / …")는 결함 B의 원인이 된 순서를 그대로 서술하고 있다. 3.1.1의 규칙 1·2로 갱신하면 이후 재발을 막는 데 도움이 된다.

### 3.4. 테스트 보강 제안

현재 테스트가 두 결함을 모두 통과시킨 원인은 트리 모양의 편향이다. 다음 케이스를 추가하면 결함 A·B가 즉시 검출된다.

- `inorder`에 **내림차순 삽입**(`[5,4,3,2,1]`) 케이스 — 결함 B 검출.
- `inorder`에 **왼쪽 자식만 가진 내부 노드 + 조상**(`[100,50,30,200]`) 케이스 — 결함 B의 최소 재현.
- `delete`에 **부모가 오른쪽 자식을 갖지 않는** 케이스(`[50,30]`에서 `delete(30)`) — 결함 A 검출.
- `delete`에 **후계자가 오른쪽 서브트리의 깊은 왼쪽에 있는** 케이스(`[50,30,70,60,55]`에서 `delete(50)`) — 결함 A의 자식 2개 경로 검출.
- `Set`을 기준 모델로 삼아 `insert`/`delete`를 무작위로 섞어 매 연산 후 `inorder`를 대조하는 **무작위 대조 테스트** — 위 개별 케이스를 일반화해 미지의 결함까지 포착한다.

## 4. 재진단 — 결함 A·B 수정 확인

2장에서 지적한 두 결함에 대한 수정이 적용되었다. 제약 조건("버그 수정의 경우, 보고서에 개선된 내용과 남은 버그에 대한 내용을 추가해 달라")에 따라 1~3장은 그대로 두고, 수정된 코드에 대한 재진단을 이 장에 추가한다.

### 4.1. 수정된 내용

수정은 정확히 두 지점, 세 줄이다.

**수정 1 — 결함 A 대응: 널 역참조를 옵셔널 체이닝으로 방어** (`deleteNoChild`, `deleteOneChild` 각 1줄)

```ts
// 수정 전
if (parent!.right!.key === node.key) {
// 수정 후
if (parent!.right?.key === node.key) {
```

**수정 2 — 결함 B 대응: 방문 후 `node`를 항상 갱신 + 하강 분기에 널 검사 추가** (`inorder`)

```ts
while (stack.length !== 0) {
  if (node !== null && node.left !== null) {   // ← node !== null 검사 추가
    node = node.left;
    stack.push(node);
  } else {
    node = stack.pop() as Node;
    arr.push(node.key);

    if (node.right !== null) {
      node = node.right;
      stack.push(node);
    } else {
      node = null;                              // ← 추가: 처리할 서브트리가 없음을 명시
    }
  }
}
```

3.1.1에서 제시한 "`node`의 의미를 '아직 처리를 시작하지 않은 서브트리의 뿌리'로 고정한다"는 원칙을, 기존 코드 구조(외부 루프의 `if` 분기로 하강을 펼친 형태)를 유지한 채 반영한 형태이다.

### 4.3. 결함 B가 해결된 이유 — 불변식 복원과 종료 조건의 타당성

2장에서 결함 B의 원인은 "**반복문 진입 시점마다 `node`가 스택 최상단과 같다**"는 불변식이 한 분기에서 깨진다는 점이었다. 수정 후 이 불변식은 다음과 같이 완화된 형태로 복원되며, 이 형태가 알고리즘 성립에 필요한 전부이다.

> **불변식 I**: 반복문 진입 시점에 `node === null`이거나, `node`가 스택 최상단 노드와 같다.

각 분기에서 불변식 I이 유지되는지 확인한다.

- **초기 상태**: `node = this.root`를 `push`한 직후이므로 `node`가 스택 최상단이다. ✓
- **분기 1 (`node !== null && node.left !== null`)**: `node`를 왼쪽 자식으로 옮긴 직후 곧바로 `push`하므로 `node`가 다시 스택 최상단이 된다. ✓
- **분기 2 (`node === null` 또는 `node.left === null`)**: `pop`으로 꺼낸 노드를 방문한 뒤,
  - 오른쪽 자식이 있으면 `node`를 그 자식으로 옮기고 `push`한다 → `node`가 스택 최상단. ✓
  - 오른쪽 자식이 없으면 `node = null`로 설정한다 → 불변식 I의 첫 번째 경우에 해당. ✓ **(수정 2가 채운 부분)**

불변식 I이 유지되면 분기 2에서 `pop`이 꺼내는 노드가 항상 옳다는 것이 따라 나온다. `node !== null`이면 `pop`은 `node` 자신을 꺼내며(그 노드는 왼쪽 자식이 없으므로 중위 순회에서 바로 방문해도 옳다), `node === null`이면 `pop`은 "왼쪽 서브트리 처리를 끝내고 방문을 기다리던 가장 최근 조상"을 꺼낸다. 어느 경우도 이미 방문한 서브트리로 되돌아가지 않는다.

**분기 1에 `node !== null` 검사를 추가한 것이 필수인 이유**: 수정 2로 `node`가 `null`이 될 수 있게 되었으므로, `node.left`를 읽기 전에 `node`가 `null`인지 확인해야 한다. 이 검사가 없으면 `null.left`를 읽어 `TypeError`가 발생한다. 즉 두 줄의 수정은 한 쌍으로만 성립한다.

**종료 조건 `stack.length !== 0`이 단독으로 충분한 이유**: 3.1.1의 원형은 종료 조건을 "`node === null` **그리고** 스택이 비어 있음"으로 두었는데, 수정된 코드는 여전히 `stack.length !== 0` 하나만 검사한다. 그럼에도 처리가 누락되지 않는 이유는 다음 명제가 성립하기 때문이다.

> **명제**: 반복문 진입 시점에 `node !== null`이면, 스택은 비어 있지 않다.

`node`가 `null`이 아닌 값으로 설정되는 지점은 코드 전체에서 세 곳뿐이며, 세 곳 모두 **설정 직후 같은 노드를 `push`한다**(초기화 `node = this.root` 다음 줄의 `stack.push(node)`, 분기 1의 `node = node.left` 다음 줄, 분기 2의 `node = node.right` 다음 줄). 따라서 `node !== null`인 상태에서는 그 노드가 반드시 스택에 들어 있으므로 스택이 비어 있을 수 없다. 명제의 대우를 취하면 "스택이 비어 있으면 `node === null`"이므로, `stack.length !== 0`이 거짓이 되는 순간은 원형의 종료 조건 두 개가 동시에 성립하는 순간과 정확히 일치한다. ✓

**`if (this.root === null) return []` 조기 반환이 이제 필수라는 점**: 이 조기 반환을 제거하면 빈 트리에서 `stack.push(this.root as Node)`가 스택에 `null`을 넣게 되고, 첫 반복에서 분기 2로 들어가 `arr.push(node.key)`가 `null.key`를 읽어 `TypeError`가 발생한다. 3.1.1의 원형(`while (node !== null || stack.length > 0)`으로 조건을 합치고 루프 안에서 `push`하는 형태)은 빈 트리를 별도 분기 없이 처리하지만, 현재 구조는 루프 진입 전에 무조건 한 번 `push`하므로 이 조기 반환에 의존한다. 현재 코드에 조기 반환이 존재하므로 동작상 문제는 없으나, 두 코드가 한 쌍으로 묶여 있다는 사실은 인지할 필요가 있다.

### 4.4. 결함 A가 해결된 이유 — 그리고 키 비교의 안전성 근거

`parent!.right?.key`는 `parent.right`가 `null`이면 프로퍼티 접근을 수행하지 않고 `undefined`를 반환한다. `node.key`는 `number` 타입이므로 `undefined === node.key`는 항상 `false`이고, 따라서 제어는 `else` 분기로 넘어가 `parent.left`를 조작한다. `parent.right`가 `null`이라는 것은 `node`가 `parent`의 왼쪽 자식이라는 뜻이므로(호출 규약상 `node`는 `parent`의 자식이다), `else` 분기로 가는 것이 정확히 옳은 동작이다. 널 역참조와 오판이 동시에 해소된다.

이는 2장 마지막 절에서 "널 역참조만 방어하고 자식 판정은 키 비교로 유지한" 버전으로 미리 검증했던 것과 동일한 의미(semantics)이며, 그때의 결과(5000회 시도 실패 0건)와 이번 전수 검증 결과가 일치한다.

**키 비교가 참조 비교와 동등해지는 조건**: 이 구현에서 `parent.right?.key === node.key`가 `parent.right === node`와 항상 같은 결과를 내는 이유를 정식으로 정리하면 다음과 같다. 호출 시점에 `node`는 `parent`의 자식이다.

1. `node`가 `parent.right`인 경우: 같은 노드의 키를 비교하므로 참이다. ✓
2. `node`가 `parent.left`인 경우, `parent.right?.key ≠ node.key`여야 한다.
   - `parent.right === null`이면 `undefined ≠ node.key`로 참이다(수정 1이 보장). ✓
   - `parent.right !== null`이면, `parent.right`는 `parent`의 오른쪽 서브트리에 있으므로 BST 조건에 의해 `parent.right.key > parent.key > node.key`이다. 따라서 키가 다르다. ✓
3. 예외 상황 — 자식이 둘인 노드를 삭제할 때 `node.key = successor.node.key`로 **일시적으로 같은 키를 가진 노드가 두 개** 생긴다. 이때 삭제 대상 노드를 $T$, 후계자를 $S$라 하면 $T.key = S.key$이다. 이 상태에서 호출되는 것은 `deleteXChild(successor.parent, S)`이다.
   - `successor.parent === T`인 경우: `findSuccessor`가 부모로 $T$를 반환하는 것은 `T.right.left === null`일 때뿐이므로 $S = T.right$이다. 즉 1번 경우에 해당해 참이 되고, 올바른 분기로 간다. ✓
   - `successor.parent !== T`인 경우: $S$는 `successor.parent`의 왼쪽 자식이며, `successor.parent.right`(존재한다면)는 `successor.parent`의 오른쪽 서브트리 노드이므로 그 키는 `successor.parent.key`보다 크고, `successor.parent.key`는 $S.key$보다 크다. 즉 $S.key$와 다르다. 키가 중복된 다른 한쪽인 $T$는 `successor.parent`의 **조상**이므로 `successor.parent.right`가 될 수 없다. ✓

따라서 "삽입이 중복 키를 거부한다"와 "키를 옮긴 직후 곧바로 후계자를 떼어낸다"는 두 전제가 유지되는 한 키 비교는 참조 비교와 동등하다. 3.1.2에서 제시한 참조 비교(`parent.left === node`)는 이 두 전제에 의존하지 않으므로 여전히 더 견고한 선택이며, 특히 다음과 같은 변경이 생기면 키 비교는 즉시 깨진다.

- 중복 키를 허용하도록 확장하는 경우(다중집합, 개수 카운트 방식 등).
- 후계자(successor) 대신 선행자(predecessor, 왼쪽 서브트리의 최댓값)를 쓰도록 바꾸는 경우 — 이때는 키가 중복된 다른 한쪽이 `parent.right` 위치에 올 수 있는지 위 3번과 같은 논증을 처음부터 다시 해야 한다.
- 키 이동과 후계자 제거 사이에 다른 트리 조작을 끼워 넣는 경우.

### 4.5. 남아있는 버그

**정확성 버그는 남아 있지 않다.** 4.2절의 66,249개 시나리오(전수 46,232 + 삭제 순서 전수 15,017 + 무작위 5,000)에서 `insert`·`search`·`delete`·`inorder`·`min`·`max` 전부 기준 모델과 일치했고, 널 역참조와 재순회는 모두 재현되지 않는다. 복잡도도 문제 주석이 명시한 목표를 만족한다(4.6절).

정확성과 무관하게 남아 있는 항목은 다음과 같다. 모두 현재 동작을 깨뜨리지 않으며, 3.3절에서 이미 지적한 것들이다.

1. **키 비교 방식의 전제 의존** (4.4절): 참조 비교로 바꾸면 전제 없이 성립한다. 함께 `deleteNoChild` / `deleteOneChild` / `findSuccessor` 세 함수를 3.1.2의 `replaceChild` 하나로 통합할 수 있다.
2. **`inorder`의 조기 반환과 루프 진입 전 `push`의 결합** (4.3절 마지막): 3.1.1의 형태로 바꾸면 조기 반환과 `as Node` 단정이 함께 불필요해진다.
3. **불필요한 비-널 단정 `!`와 옵셔널 체이닝 `?.`**: `delete` 본문의 `node?.right === null`은 바로 위 `if (node === null) return;`으로 이미 좁혀진 뒤이므로 `?.`가 필요 없다. `node!.right`, `node!.key`, `parent!.right`의 `!`도 마찬가지이다. 특히 `parent!`는 같은 함수 안에서 `if (parent === null) return;`으로 이미 좁혀진 뒤에 쓰이고 있어 완전히 불필요하다. `!`는 실행 시점의 값을 바꾸지 않고 타입 검사기의 경고만 지우므로, 결함 A처럼 실제 `null`을 가리는 방향으로 작용할 수 있다는 점을 기억할 필요가 있다.
4. **`inorder`의 주석이 수정 내용을 반영하지 않음**: 본문 주석("노드 푸시 / 왼쪽 있으면 넘어가기 / 없으면 팝 / …")에는 이번에 추가한 "오른쪽이 없으면 `node`를 비운다"는 핵심 단계가 빠져 있다. 이 단계가 결함 B의 원인이자 해결책이므로 주석에 명시하는 편이 재발 방지에 도움이 된다.
5. **`search`의 중복 널 검사와 `insert`의 도달 불가 코드**: 동작상 무해하다.
6. **`let successor`는 재대입되지 않으므로 `const`가 적절하다**.
7. **테스트 스위트의 사각지대는 그대로 남아 있다**: 코드는 고쳐졌지만 테스트는 여전히 결함 A·B를 검출할 수 없는 구성이다. 3.4절의 5개 케이스(특히 내림차순 삽입 `inorder`와 `[50,30]`에서 `delete(30)`)를 추가해 두면 이후 회귀(regression)를 스위트가 직접 잡아낸다. 현재는 회귀가 발생해도 `14 pass`가 그대로 나온다. → **4.7절에서 해소되었다.**

### 4.6. 복잡도 재확인

| 연산 | 시간 | 추가 공간 | 원본 대비 |
|---|---|---|---|
| `insert` | $O(h)$ | $O(1)$ | 동일 |
| `search` | $O(h)$ | $O(1)$ | 동일 |
| `delete` | $O(h)$ | $O(1)$ | 크래시 → 정상 |
| `inorder` | $O(n)$ | $O(h)$ | $\Theta(2^{n})$ → $O(n)$ |
| `min` / `max` | $O(h)$ | $O(1)$ | 동일 |

각 노드가 정확히 한 번 `push`되고 한 번 `pop`되므로 `inorder`는 $O(n)$이고, 스택에 동시에 존재하는 노드 수는 트리 높이를 넘지 않으므로 추가 공간은 $O(h)$이다. 문제 주석이 명시한 목표(`insert`/`search`/`delete` $O(\log n)$ 평균·$O(n)$ 최악, `inorder` $O(n)$)와 정확히 일치한다.

### 4.7. 테스트 보강 (4.5절 7번 해소)

3.4절의 제안을 `main` 브랜치에 반영했다(커밋 `9820ea4`, `binarySearchTree.test.ts` +242줄). 이 저장소는 `main`이 문제와 명세 테스트를, `solutions`가 구현을 갖는 구조이므로 테스트 보강은 `main`에서 수행했다.

기존 14개 테스트는 그대로 두고 14개를 추가해 총 28개가 되었다.

| 그룹 | 테스트 | 겨냥한 결함 |
|---|---|---|
| 왼쪽으로 치우친 모양 | 왼쪽 자식만 가진 내부 노드 + 조상 잔존 (`[100,50,30,200]`) | B 최소 재현 |
| | 내림차순 삽입 (`[5,4,3,2,1]`) | B |
| | 왼쪽 사슬 $N = 20$의 `inorder` 길이가 노드 수와 같음 | B (지수 폭발) |
| | 치우친 트리에서 삭제 후 순회 | B |
| `delete` — 부모가 오른쪽 자식 없음 | 왼쪽 리프 삭제 (`[50,30]`에서 `delete(30)`) | A |
| | 왼쪽 자식만 가진 노드 삭제 (`[50,30,20]`) | A |
| | 왼쪽 자식만 가진 루트 삭제 | 경계 |
| | 후계자가 깊은 왼쪽 (`[50,30,70,60,55]`) | A (자식 2개 경로) |
| | 후계자가 오른쪽 자식을 가진 경우 (`[50,30,70,60,55,57]`) | A (분기 반대쪽) |
| | 단일 노드 루트 삭제 후 재삽입 | 경계 |
| 전수 검증 | $n \leq 6$ 모든 삽입 순열, 삽입 직후 상태 | 모든 BST 모양 |
| | $n \leq 6$ 모든 삽입 순열 × 각 키 삭제 | 모든 BST 모양 |
| | $n \leq 4$ 모든 삽입 순열 × 모든 삭제 순서 | 삭제 연쇄 |
| 무작위 대조 | 시드 고정 난수로 200시도 × 30연산, `Set` 모델 대조 | 미지의 결함 |

**검증 — 세 가지 구현체 대상으로 교차 확인**

```
수정된 구현체 대상 : 28 pass /  0 fail   (122,463 expect 호출, 41ms)
버그 구현체 대상   : 16 pass / 12 fail   ← 새 테스트 14개 중 12개가 검출
main 스텁 대상     :  0 pass / 28 fail   ← main 규약(구현이 스텁)대로
```

두 번째 줄이 보강의 핵심 근거이다. 4.1절의 수정을 되돌린 버그 구현체에 대해 **기존 14개는 전부 통과**하는데 새 테스트는 즉시 실패한다. 2장에서 "통과한 14개 테스트는 결함을 우회하는 트리 모양만 검사한다"고 지적한 사각지대가 실제로 메워졌음을 뜻한다. 통과한 2개(왼쪽 자식만 가진 루트 삭제, 단일 노드 루트 삭제)는 `parent === null` 경로만 지나가므로 결함 A의 판정식에 도달하지 않는 경계 테스트이며, 결함 검출용이 아니다.

**설계 판단 두 가지**

1. **왼쪽 사슬 길이 검사에서 $N = 20$을 고른 이유**: 결함 B가 있는 구현은 왼쪽 사슬 $n$개에 대해 $2^{\,n-1}$개를 출력한다(2장). $N = 20$이면 524,288개가 되어 길이 비교로 약 4ms 만에 검출되고 메모리도 수 MB 수준이다. $N$을 크게 잡으면 검출력이 오르는 것이 아니라 오히려 테스트 프로세스가 메모리 부족으로 죽어 다른 테스트 결과까지 잃는다. 즉 이 검사는 $N$이 작을수록 실패 양상이 깨끗하며, 재순회를 잡아내는 데는 $N = 20$으로 충분하다.
2. **무작위 대조에 시드를 고정한 이유**: 기존 성능 테스트는 `Math.random()`을 쓰지만, 대조 검증은 실패를 재현할 수 있어야 진단에 쓸 수 있다. 시드를 고정한 xorshift32를 쓰고, 실패 시 `재현 연산열: insert(12) delete(19) …` 형태로 연산열 전체를 메시지에 담아 그대로 재현할 수 있게 했다.

`main`에서는 구현이 스텁이므로 28개 전부 실패하는 것이 정상이며, 이는 보강 전 14개도 마찬가지였다. 보강의 효과는 구현이 올라오는 시점부터 회귀 방지로 작동한다.
