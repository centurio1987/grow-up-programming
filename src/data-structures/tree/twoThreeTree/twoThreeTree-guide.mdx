# TwoThreeTree — 넘치면 위로, 모자라면 옆에서

## 한눈에 보는 컨셉

노드 하나에 키를 1~2개까지 허용하는 탐색 트리예요. 키가 3개로 넘치면(오버플로우) 가운데 키를 부모로 밀어 올려 분할하고, 키가 0개로 모자라면(언더플로우) 형제에게 빌리거나 부모와 함께 합칩니다. 이 "넘치면 위로, 모자라면 옆에서"라는 두 규칙만으로 회전(rotation) 없이도 모든 리프가 항상 같은 깊이를 유지하고, 삽입·삭제·탐색이 전부 $O(\log n)$을 보장합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 2-3 트리(혹은 그 일반화인 B-트리 계열)를 떠올리세요.

- 삽입·삭제가 계속 섞여 들어오는데, 탐색 성능이 **최악의 경우에도** $O(\log n)$이어야 한다
- 회전 로직 없이 균형을 유지하는 **단순한** 자료구조가 필요하다(AVL의 회전 케이스 분기를 피하고 싶다)
- 정렬 순서 순회(`inOrder`)도 함께 요구된다

정렬 배열은 탐색은 빠르지만 삽입·삭제 때 뒤 원소를 밀어야 해서 느리고, 균형을 신경 쓰지 않은 이진 탐색 트리(BST)는 삽입 순서가 나쁘면 사슬처럼 늘어져 최악의 경우 탐색마저 $O(n)$으로 무너집니다.

```text
연산       정렬 배열       불균형 BST(최악)   2-3 트리(항상)
insert      O(n)            O(n)              O(log n)
delete      O(n)            O(n)              O(log n)
has         O(log n)*       O(n)              O(log n)

* 이진 탐색 자체는 O(log n)이지만, 정렬 유지를 위한 삽입/삭제 비용이 O(n)입니다.
```

AVL 트리나 레드-블랙 트리도 $O(\log n)$을 보장하지만, 그 대가로 회전(rotation)이라는 별도의 케이스 분기가 필요합니다. 2-3 트리는 분할·병합만으로 균형을 유지해 구현이 더 직관적인 대신, 노드마다 키 개수가 가변이라 메모리 레이아웃이 덜 균일합니다 — 구현 단순성과 학습 목적이 우선이면 2-3 트리, 캐시 지역성과 고정 크기 노드가 중요한 실무 구현이면 레드-블랙 트리를 선택하는 경우가 많습니다.

### 문제 사례와 적용 예시

- **데이터베이스·파일시스템 인덱스의 원형**: 2-3 트리를 노드당 키 개수를 더 늘린 것이 B-트리이고, 이는 디스크 블록 단위 I/O에 최적화되어 현대 데이터베이스 인덱스의 기반이 됩니다.
- **컴파일러 심볼 테이블**: 스코프가 계속 열리고 닫히며 식별자가 삽입·삭제되는 와중에도 정렬된 순회(이름순 나열 등)가 필요한 associative container 구현에 쓰입니다.
- **코딩 테스트 맥락**: "삽입과 삭제가 반복되는데 항상 균형 잡힌 탐색 트리를 직접 구현하라"처럼, 언어 내장 정렬 컨테이너를 쓸 수 없는 환경에서 균형 트리를 처음부터 만들어야 하는 문제로 나옵니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드가 정의하는 인터페이스는 다음과 같습니다.

```ts
class TwoThreeTree<T> {
  constructor(comparator?: (a: T, b: T) => number)
  insert(value: T): void      // O(log n), 중복은 무시
  delete(value: T): boolean   // O(log n), 삭제 성공 여부 반환
  has(value: T): boolean      // O(log n)
  size(): number              // O(1)
  inOrder(): T[]               // O(n), 정렬된 배열
}
```

**속성(내부 상태)** — 노드는 한 종류뿐이고, 키 개수로만 리프/내부를 구분합니다.

```ts
class TwoThreeNode<T> {
  keys: T[] = [];                    // 1~2개 (일시적으로 3개까지 허용 후 즉시 분할)
  children: TwoThreeNode<T>[] = [];  // 0개(리프) 또는 keys.length + 1개
}
```

지켜야 할 불변식은 네 가지입니다.

1. 루트가 아닌 모든 노드는 $|keys| \in \{1, 2\}$이다. 삽입 중 일시적으로 $|keys| = 3$이 될 수 있지만, 연산이 끝나기 전에 반드시 분할되어 사라진다.
2. 내부 노드의 자식 수는 항상 $|children| = |keys| + 1$이다.
3. 모든 리프는 같은 깊이 $h$에 있다 — "완전 균형".
4. 내부 노드의 $keys[i]$에 대해, $children[i]$의 모든 값 $<$ $keys[i]$ $<$ $children[i+1]$의 모든 값이다(BST 성질이 모든 갈래에 사슬처럼 이어진다).

`1, 2, ..., 7`을 순서대로 삽입한 뒤의 모양을 그려보면 이렇습니다(뒤에서 실행으로 직접 검증합니다).

```text
                 [ 4 ]                 ← 루트 (키 1개, 자식 2개)
               /       \
          [ 2 ]         [ 6 ]          ← 내부 노드 (키 1개씩)
         /     \        /     \
      [ 1 ]   [ 3 ]  [ 5 ]   [ 7 ]      ← 리프, 모두 깊이 2로 동일
```

키가 항상 1개 이상이라는 점(불변식 1)이 트리 높이를 눌러줍니다. 내부 노드는 키 1개여도 자식이 2개이므로, 매 층마다 자식 수가 최소 2배로 늘어나요. 그러면 높이 $h$인 트리는 리프가 최소 $2^h$개이고, 리프마다 키가 최소 1개이니 전체 키 개수 $n$은 $n \ge 2^h$을 만족합니다. 정리하면

$$h \le \log_2 n$$

이므로 삽입·삭제·탐색이 트리를 한 번 오르내리는 한 항상 $O(\log n)$이 보장됩니다.

**액션(연산)**은 다음 5종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(v)` | 리프까지 내려가 삽입, 3키(오버플로우) 되면 분할 후 위로 전파 | $O(\log n)$ |
| `delete(v)` | 리프에서 제거(내부 노드면 후속자로 대체 후 리프에서 제거), 0키(언더플로우) 되면 재분배/병합 후 위로 전파 | $O(\log n)$ |
| `has(v)` | 루트부터 리프까지 내려가며 키 비교 | $O(\log n)$ |
| `size()` | 내부 카운터 반환 | $O(1)$ |
| `inOrder()` | 중위 순회로 정렬 배열 생성 | $O(n)$ |

핵심 연산 세 가지를 그림으로 자세히 봅니다.

**① 분할(split)** — 리프에 키를 정렬 삽입했더니 3개가 되면, 가운데 키를 부모로 올리고 나머지 둘로 좌우 리프를 만듭니다.

```text
Before (리프에 임시로 3키): [ 3, 5, 7 ]

분할: 가운데 키 5를 부모로 승격
  왼쪽 리프: [ 3 ]        오른쪽 리프: [ 7 ]

After:
        [ 5 ]          ← 새 루트(승격된 키)
       /     \
    [ 3 ]   [ 7 ]       ← 분할된 두 리프
```

**② 재분배(borrow)** — 삭제로 리프가 0개가 됐는데, 형제가 키 2개를 갖고 있으면 부모를 경유해 하나를 빌립니다.

```text
Before: delete(7) 직후 오른쪽 리프가 0키(언더플로우)
        [ 5 ]
       /     \
   [1, 3]    [ ]      ← 왼쪽 형제는 2키(여유 있음)

재분배: ① 부모의 키 5가 비어있던 오른쪽 자리로 내려간다
        ② 왼쪽 형제의 마지막 키 3이 부모로 올라간다

After:
        [ 3 ]
       /     \
    [ 1 ]   [ 5 ]
```

**③ 병합(merge)** — 형제도 키 1개뿐이라 빌려줄 여유가 없으면, 부모의 키 하나를 끌어내려 형제와 하나로 합칩니다. 병합으로 부모가 다시 0키가 될 수 있고, 이 언더플로우는 조부모로 재귀 전파됩니다.

```text
Before: [1] 삭제 직전
                 [ 4 ]
               /       \
          [ 2 ]         [ 6 ]
         /     \        /     \
      [ 1 ]   [ 3 ]  [ 5 ]   [ 7 ]

1단계: [1] 삭제 → 빈 노드. 형제 [3]도 1키뿐 → 병합
       부모 키 2가 내려와 형제와 합쳐진다 → [2, 3]
       부모였던 노드는 0키가 되어 다시 언더플로우 → 조부모로 전파

2단계: 조부모 [4]에서도 처리. 오른쪽 형제(내부 노드)도 키 1개뿐 → 다시 병합
       루트 키 4가 내려와 두 내부 노드가 하나로 합쳐진다

After: 병합이 루트까지 전파되어 트리 높이가 1 감소
        [ 4, 6 ]
       /    |    \
   [2,3]  [ 5 ]  [ 7 ]
```

### 왜 모순 없이 작동하는가

**삽입이 불변식을 지키는 이유**: 리프에 값을 정렬 위치에 넣으면 일시적으로 키가 3개가 될 수 있어요(불변식 1 일시 위반). 분할은 이를 즉시 복구합니다 — 왼쪽·오른쪽 리프는 각각 키 1개로 시작하고, 승격된 가운데 키가 부모에 정렬 위치로 삽입되니 불변식 4(BST 성질)도 그대로 이어집니다. 부모가 이 때문에 다시 3키가 되면 같은 분할이 부모에서 재귀적으로 일어나고, 결국 루트에서 멈추거나(불변식 1 복구) 루트 자체가 분할되어 새 루트가 생기며 트리 높이가 1 증가합니다(불변식 3 유지 — 모든 리프가 동시에 한 층씩 내려가므로 깊이가 계속 같습니다).

**삭제가 불변식을 지키는 이유**: 리프에서 키를 지우면 일시적으로 0개가 될 수 있어요(불변식 1 일시 위반). `fixChild`는 이를 즉시 복구합니다 — 형제가 2키면 재분배로 양쪽 다 1개 이상을 유지하고, 형제도 1키면 병합으로 셋(부모 키 1개 + 두 형제)을 하나의 노드로 합쳐 불변식을 만족시킵니다. 병합은 부모의 키를 하나 소비하므로 부모가 다시 0키가 될 수 있고, 이 언더플로우가 조부모로 재귀 전파됩니다. 루트까지 전파되어 루트가 0키(자식 1개)가 되면, 그 자식이 새 루트가 되어 높이가 1 감소합니다.

잠깐, 확인 하나만 해볼까요? "형제가 2키일 때는 왜 재분배로 충분하고, 1키일 때는 왜 병합이 필요할까요?" — 형제가 2키면 하나를 내줘도 1개가 남아 불변식을 지키지만, 형제가 1키뿐이면 하나를 내주는 순간 형제 자신이 0개가 되어 위반이 옆으로 옮겨갈 뿐입니다. 그래서 형제가 1키일 때는 아예 합쳐서 언더플로우 자체를 부모 층으로 밀어 올려야 해요.

**헷갈리기 쉬운 포인트**를 세 가지 짚어 둡니다.

- **삭제가 항상 재분배나 병합을 부른다고 생각하기 쉽습니다.** 실제로는 삭제된 값이 있던 리프에 아직 다른 키가 남아 있으면 아무 재조정도 필요 없습니다. 예를 들어 `[5]{[1,3]|[7]}` 상태에서 `delete(3)`을 하면 리프 `[1,3]`에서 3만 제거되어 `[1]`이 되는데, 키 1개는 최소치를 그대로 만족하므로 트리는 `[5]{[1]|[7]}`로 끝나고 재분배·병합은 전혀 일어나지 않습니다.
- **재분배와 병합을 형제 키 개수 확인 없이 섞어 쓰면 안 됩니다.** 형제가 1키뿐인데 억지로 재분배를 시도하면, 방금 살펴본 이유대로 형제가 빈 노드가 되어 언더플로우가 해결되지 않고 자리만 옮깁니다. 반드시 "형제가 2키인가?"를 먼저 확인해야 합니다.
- **내부 노드에서 키를 지울 때는 그 자리에서 바로 지우면 안 됩니다.** 내부 노드의 키를 빼면 자식 수와 키 수의 관계(불변식 2)가 깨져 버려요. 그래서 중위 후속자(오른쪽 서브트리의 최솟값)로 값을 먼저 바꿔치기하고, 실제 제거는 그 후속자가 있던 리프에서 수행합니다. `[4]{[2]{[1]|[3]}|[6]{[5]|[7]}}`에서 `delete(4)`를 하면 4가 후속자 5로 대체된 뒤 리프에서 5가 지워지고, 그 언더플로우가 병합으로 전파되어 최종적으로 `[2,5]{[1]|[3]|[6,7]}`이 됩니다.

엣지 케이스도 점검해 둡니다.

```text
빈 트리에 has/delete       → false / false (root가 undefined인 분기)
원소 1개 트리에서 delete    → 리프가 0키가 되지만 루트이므로 fixChild 없이
                             root = undefined 로 정리 (형제가 없다)
중복 insert                → has로 먼저 확인 후 무시 (size 불변)
음수·문자열 등 임의 타입    → comparator만 일관되면 구조에 영향 없음
```

## 아이디어를 코드로 옮기기

바로 2-3 트리로 가기 전에, 이 문제를 어떻게 안 풀면 안 되는지부터 봅니다.

**원형(naive)**: 정렬 배열에 `splice`로 삽입·삭제하면 어떨까요?

```ts
class NaiveSortedArray<T> {
  private data: T[] = [];
  insert(v: T) {
    let i = 0;
    while (i < this.data.length && this.data[i]! < v) i++;
    this.data.splice(i, 0, v); // 뒤 원소를 전부 한 칸씩 밀어야 한다
  }
}
```

`insert`마다 뒤 원소를 밀어야 해서 $O(n)$이에요. $n = 10^4$개를 순서대로 삽입하면 총 비용이 $O(n^2) = 10^8$에 근접해, 1초 제한을 넘길 위험이 큽니다.

**개선**: 그럼 단순 이진 탐색 트리(BST)로 균형을 신경 쓰지 않고 삽입하면 어떨까요?

```ts
class NaiveBst<T> {
  private root?: { value: T; left?: any; right?: any };
  insert(v: T) {
    // 재귀적으로 v < node.value면 왼쪽, 아니면 오른쪽에 삽입
    // 회전 없음 — 삽입 순서에 따라 모양이 정해진다
  }
}
```

삽입은 평균적으로 빠르지만, 입력이 이미 정렬된 순서(`1, 2, 3, ..., n`)로 들어오면 트리가 오른쪽으로만 자라는 사슬이 되어 높이가 $n$에 이릅니다. 그러면 `has(n)` 하나가 $O(n)$이 되어 역시 최악의 경우 시간 제한을 넘깁니다. **여기서 필요한 것이 "삽입 순서와 무관하게 항상 균형을 유지하는" 장치**이고, 그게 분할/병합입니다.

**최종**: 2-3 트리 전체 구현입니다.

```ts
type Compare<T> = (a: T, b: T) => number;

class TwoThreeNode<T> {
  keys: T[];
  children: TwoThreeNode<T>[];

  constructor(keys: T[] = [], children: TwoThreeNode<T>[] = []) {
    this.keys = keys;
    this.children = children;
  }

  get isLeaf(): boolean {
    return this.children.length === 0;
  }
}

type SplitResult<T> = { promoted: T; left: TwoThreeNode<T>; right: TwoThreeNode<T> };

class TwoThreeTree<T> {
  private root: TwoThreeNode<T> | undefined = undefined;
  private _size = 0;
  private compare: Compare<T>;

  constructor(comparator?: Compare<T>) {
    this.compare = comparator ?? ((a, b) => (a < b ? -1 : a > b ? 1 : 0));
  }

  has(value: T): boolean {
    let node = this.root;
    while (node !== undefined) {
      let i = 0;
      while (i < node.keys.length) {
        const cmp = this.compare(value, node.keys[i]!);
        if (cmp === 0) return true;
        if (cmp < 0) break;
        i++;
      }
      if (node.isLeaf) return false;
      node = node.children[i];
    }
    return false;
  }

  insert(value: T): void {
    if (this.has(value)) return; // 중복 무시

    if (this.root === undefined) {
      this.root = new TwoThreeNode<T>([value]);
      this._size = 1;
      return;
    }

    const split = this.insertInto(this.root, value);
    if (split !== undefined) {
      this.root = new TwoThreeNode<T>([split.promoted], [split.left, split.right]);
    }
    this._size++;
  }

  private insertInto(node: TwoThreeNode<T>, value: T): SplitResult<T> | undefined {
    if (node.isLeaf) {
      let i = 0;
      while (i < node.keys.length && this.compare(node.keys[i]!, value) < 0) i++;
      node.keys.splice(i, 0, value);
      if (node.keys.length <= 2) return undefined;
      return this.splitLeaf(node);
    }

    let i = 0;
    while (i < node.keys.length && this.compare(value, node.keys[i]!) > 0) i++;
    const split = this.insertInto(node.children[i]!, value);
    if (split === undefined) return undefined;

    node.keys.splice(i, 0, split.promoted);
    node.children.splice(i, 1, split.left, split.right);
    if (node.keys.length <= 2) return undefined;
    return this.splitInternal(node);
  }

  private splitLeaf(node: TwoThreeNode<T>): SplitResult<T> {
    const [k0, k1, k2] = node.keys as [T, T, T];
    return { promoted: k1, left: new TwoThreeNode<T>([k0]), right: new TwoThreeNode<T>([k2]) };
  }

  private splitInternal(node: TwoThreeNode<T>): SplitResult<T> {
    const [k0, k1, k2] = node.keys as [T, T, T];
    const [c0, c1, c2, c3] = node.children as [
      TwoThreeNode<T>, TwoThreeNode<T>, TwoThreeNode<T>, TwoThreeNode<T>,
    ];
    return {
      promoted: k1,
      left: new TwoThreeNode<T>([k0], [c0, c1]),
      right: new TwoThreeNode<T>([k2], [c2, c3]),
    };
  }

  delete(value: T): boolean {
    if (this.root === undefined || !this.has(value)) return false;

    this.deleteFrom(this.root, value);
    if (this.root.keys.length === 0) {
      this.root = this.root.isLeaf ? undefined : this.root.children[0];
    }
    this._size--;
    return true;
  }

  private deleteFrom(node: TwoThreeNode<T>, value: T): void {
    if (node.isLeaf) {
      const idx = node.keys.findIndex((k) => this.compare(k, value) === 0);
      node.keys.splice(idx, 1);
      return;
    }

    const idx = node.keys.findIndex((k) => this.compare(k, value) === 0);
    if (idx !== -1) {
      // 내부 노드에서 발견: 중위 후속자로 대체 후 후속자를 리프에서 삭제
      let succNode = node.children[idx + 1]!;
      while (!succNode.isLeaf) succNode = succNode.children[0]!;
      const succValue = succNode.keys[0]!;
      node.keys[idx] = succValue;
      this.deleteFrom(node.children[idx + 1]!, succValue);
      this.fixChild(node, idx + 1);
    } else {
      let i = 0;
      while (i < node.keys.length && this.compare(value, node.keys[i]!) > 0) i++;
      this.deleteFrom(node.children[i]!, value);
      this.fixChild(node, i);
    }
  }

  private fixChild(parent: TwoThreeNode<T>, i: number): void {
    const child = parent.children[i]!;
    if (child.keys.length > 0) return; // 언더플로우 아님

    const hasLeft = i > 0;
    const hasRight = i < parent.children.length - 1;

    if (hasLeft && parent.children[i - 1]!.keys.length === 2) {
      this.borrowFromLeft(parent, i);
    } else if (hasRight && parent.children[i + 1]!.keys.length === 2) {
      this.borrowFromRight(parent, i);
    } else if (hasLeft) {
      this.mergeWithLeft(parent, i);
    } else {
      this.mergeWithRight(parent, i);
    }
  }

  private borrowFromLeft(parent: TwoThreeNode<T>, i: number): void {
    const left = parent.children[i - 1]!;
    const child = parent.children[i]!;
    child.keys.unshift(parent.keys[i - 1]!);
    parent.keys[i - 1] = left.keys.pop()!;
    if (!left.isLeaf) child.children.unshift(left.children.pop()!);
  }

  private borrowFromRight(parent: TwoThreeNode<T>, i: number): void {
    const right = parent.children[i + 1]!;
    const child = parent.children[i]!;
    child.keys.push(parent.keys[i]!);
    parent.keys[i] = right.keys.shift()!;
    if (!right.isLeaf) child.children.push(right.children.shift()!);
  }

  private mergeWithLeft(parent: TwoThreeNode<T>, i: number): void {
    const left = parent.children[i - 1]!;
    const child = parent.children[i]!;
    left.keys.push(parent.keys[i - 1]!, ...child.keys);
    if (!left.isLeaf) left.children.push(...child.children);
    parent.keys.splice(i - 1, 1);
    parent.children.splice(i, 1);
  }

  private mergeWithRight(parent: TwoThreeNode<T>, i: number): void {
    const child = parent.children[i]!;
    const right = parent.children[i + 1]!;
    child.keys.push(parent.keys[i]!, ...right.keys);
    if (!child.isLeaf) child.children.push(...right.children);
    parent.keys.splice(i, 1);
    parent.children.splice(i + 1, 1);
  }

  size(): number {
    return this._size;
  }

  inOrder(): T[] {
    const result: T[] = [];
    const walk = (node: TwoThreeNode<T> | undefined) => {
      if (node === undefined) return;
      if (node.isLeaf) {
        result.push(...node.keys);
        return;
      }
      for (let i = 0; i < node.keys.length; i++) {
        walk(node.children[i]);
        result.push(node.keys[i]!);
      }
      walk(node.children[node.keys.length]);
    };
    walk(this.root);
    return result;
  }
}
```

**가장 중요한 부분은 `insertInto`와 `deleteFrom`이 재귀 반환값으로 "위로 전파할 일"을 알린다는 점입니다.** `insertInto`는 분할이 없으면 `undefined`, 있으면 `{promoted, left, right}`를 반환해 호출자(부모)가 그것을 자기 키·자식 배열에 끼워 넣게 만듭니다. `fixChild`도 마찬가지로, 자식을 고친 뒤 부모 자신이 다시 언더플로우가 될 수 있다는 걸 알아서 다음 재귀 단계(`fixChild`를 호출한 그 위 레벨)가 감지하도록 맡깁니다 — 명시적인 "위로 보고하는 큐" 없이도 함수 호출 스택 자체가 전파 경로가 되는 것이 재귀 설계의 핵심입니다.

놓치기 쉬운 지점들을 짚어 둡니다.

- **`splitLeaf`에서 승격하는 키는 반드시 가운데 키(`k1`)여야 합니다.** 만약 실수로 첫 번째 키(`k0`)를 승격시키면(`promoted = k0`, `left = [k1]`, `right = [k2]`), `insert(5), insert(3), insert(7)` 이후 모양이 `[3]{[5]|[7]}`가 됩니다 — 왼쪽 자식 `[5]`에 3보다 **큰** 값이 남아 불변식 4("왼쪽 자식은 3보다 작은 값만")를 이미 위반한 상태예요. 여기서 `insert(1)`을 이어 하면 `[3]{[1,5]|[7]}`가 되고, 이 상태에서 `has(5)`를 호출하면 루트에서 `5 > 3`이므로 오른쪽 `[7]`로 내려가 5를 찾지 못하고 **`false`를 반환합니다**(실제로 이 버그 버전을 실행해 확인한 값입니다) — 방금 넣은 값을 잃어버리는 겁니다.
- **`borrowFromLeft`·`borrowFromRight`는 순서가 생명입니다.** `child.keys.unshift(parent.keys[i-1])`를 먼저 하고 `parent.keys[i-1] = left.keys.pop()`를 나중에 해야, 부모의 "낡은" 키가 자식으로 내려간 뒤에 부모가 새 경계값으로 갱신됩니다. 순서를 바꾸면 부모가 먼저 갱신되어 자식이 잘못된(형제의 새 값과 같은) 키를 받게 됩니다.
- **재분배 vs 병합은 형제의 키 개수(`=== 2`)로만 결정합니다.** 형제 키 개수를 확인하지 않고 항상 재분배를 시도하면, 위 "왜 모순 없이 작동하는가"에서 본 것처럼 언더플로우가 형제로 옮겨갈 뿐 해결되지 않습니다.

> 기억법: "분할은 가운데를 올리고, 병합은 부모를 내린다."

## 실행 시각화

`insert(5), insert(3), insert(7), insert(1)`을 차례로 실행하면 `insert(7)`에서 리프가 3키로 넘쳐 분할이 일어나 루트가 `[5]{[3]|[7]}`가 되고, 이어서 `insert(1)`은 왼쪽 리프에 들어가 `[5]{[1,3]|[7]}`가 됩니다. 마지막 `delete(7)`은 오른쪽 리프를 비워(언더플로우) 왼쪽 형제(키 2개)에게서 재분배를 받아 `[3]{[1]|[5]}`로 정리됩니다. 최종 `inOrder()`는 `[1, 3, 5]`입니다(위 코드를 그대로 실행해 확인한 값입니다). array 패널은 각 단계의 `inOrder()` 결과를 보여주고, highlight는 승격되거나 새로 갱신된 경계 키, marked는 그 좌우 리프의 값입니다.
