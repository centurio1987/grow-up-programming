# Treap — 무작위 우선순위 하나로 회전을 지운다

## 한눈에 보는 컨셉

Treap은 이진 탐색 트리(BST) 위에 무작위 우선순위(priority) 하나를 더 얹어, 어떤 순서로 키가 들어와도 트리가 한쪽으로 쏠리지 않게 만드는 자료구조예요. 비결은 딱 하나 — 모든 노드에 난수 priority를 매기고 "키로는 BST, priority로는 최대 힙"이라는 두 조건을 동시에 만족시키는 겁니다. 그 결과 회전(rotation) 없이 `split`(자르기)과 `merge`(합치기) 두 연산만으로 삽입·삭제·$k$번째 원소 조회를 모두 기대 $O(\log n)$에 처리합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Treap을 떠올리세요.

- 정수(또는 비교 가능한 값)들의 동적 다중집합(multiset)에서 삽입·삭제가 계속 일어나는데, "지금 $k$번째로 작은 값은?"(순서 통계, order statistics) 질의도 함께 필요하다
- 입력 순서를 신뢰할 수 없다 — 정렬된 순서로 삽입될 가능성이 있어 일반 BST가 사슬처럼 한쪽으로 쏠릴 위험이 있다
- 구간을 통째로 잘라 옮기거나 뒤집는 연산(구간 반전 등)이 필요해서, "자르고(split) 붙이는(merge)" 표현이 자연스러운 문제다

naive 접근들과 비용을 비교하면 왜 Treap을 쓰는지 체감됩니다. 직접 $1..1000$을 정렬된 순서로 넣어 높이를 재 보면 이렇습니다.

```text
naive 정렬 배열       삽입/삭제 O(n) (원소 이동)     findKth O(1) (인덱스 접근)
naive BST(회전 없음)   삽입/삭제 O(h)
                       정렬된 1..1000을 순서대로 삽입 → 높이 h = 1000 (완전한 사슬!)
Treap                 삽입/삭제/findKth 기대 O(log n) — 입력 순서 무관
                       같은 1..1000 삽입 → 높이 = 23 (log2(1000) ≈ 10.0의 약 2배 수준)
```

즉 naive BST는 "입력 순서가 나쁘면" $O(n)$으로 퇴화하지만, Treap은 난수 priority가 입력 순서를 사실상 "무작위로 섞어" 넣은 것과 같은 효과를 내서 입력 순서와 무관하게 균형을 유지합니다.

**선택 기준**: AVL 트리나 레드-블랙 트리는 항상 최악 $O(\log n)$을 엄격히 보장하지만, 그 대가로 회전 케이스(LL/LR/RL/RR, 색 재조정)가 많아 구현이 복잡합니다. Treap은 기대값 기준 $O(\log n)$(확률적 보장)이라는 점에서 이론적으로는 조금 약하지만, `split`/`merge` 두 함수만 정확히 짜면 되므로 코딩 테스트나 실무에서 빠르고 정확한 구현을 뽑아낼 때 유리합니다. 적대적 입력이 확실하고 최악 성능을 절대적으로 보장해야 하는 상황이라면 레드-블랙 트리 쪽을 선택하세요.

### 문제 사례와 적용 예시

- **거래소 호가창(order book)**: 매수·매도 주문 가격을 실시간으로 삽입·삭제하며 "현재 $k$번째로 낮은 매도 호가는?"을 반복 조회합니다. 같은 가격에 여러 주문이 겹칠 수 있어 중복 키 지원이 필요합니다.
- **암묵적 Treap(implicit treap)으로 구간 연산**: 배열의 특정 구간을 잘라 반전·이동시키는 문제에서 키를 "값"이 아니라 "배열 인덱스"로 두면, `split`/`merge`가 그대로 구간 자르기·붙이기가 됩니다.
- **코딩 테스트의 순서 통계 문제**: "삽입·삭제가 섞이는 동안 $k$번째 원소를 계속 물어보라"는 유형(정렬 컨테이너가 기본 제공되지 않는 JS/TS 환경에서 직접 구현 대상이 됩니다).
- **정렬 순서를 유지하는 캐시/인덱스 계층**: skip list가 쓰이는 자리(예: Redis의 정렬 집합류 자료구조)에서, 트리 기반 대안으로 Treap을 쓸 수 있습니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드 하나는 다섯 개 필드를 가집니다.

```ts
interface TreapNode {
  key: number; // BST 정렬 기준
  priority: number; // 힙 정렬 기준 (무작위)
  left: TreapNode | null;
  right: TreapNode | null;
  size: number; // 자신을 포함한 서브트리 크기
}
```

지켜야 할 불변식은 세 가지입니다.

1. **BST 조건**: 왼쪽 서브트리의 모든 키 $\leq$ 현재 키 $\leq$ 오른쪽 서브트리의 모든 키.
   $$\forall u \in \text{left}(v),\ u.key \leq v.key \leq \forall w \in \text{right}(v),\ w.key$$
2. **최대 힙 조건**: 루트 방향으로 갈수록 priority가 커진다.
   $$v.priority \geq \max(\text{priority}(\text{left}(v)),\ \text{priority}(\text{right}(v)))$$
3. **크기 불변식**: 서브트리 크기는 자식 크기의 합 + 1.
   $$v.size = \text{size}(\text{left}(v)) + \text{size}(\text{right}(v)) + 1$$

키 `{3, 5, 8}`에 priority `3→20, 5→30, 8→25`를 부여하면 이런 모양이 됩니다(직접 실행해 확인한 구조입니다).

```text
                 5·p30 (size=3)
                /              \
         3·p20 (size=1)    8·p25 (size=1)

가로로 읽으면 BST: 3 < 5 < 8
세로로 읽으면 최대 힙: 30 ≥ 20, 30 ≥ 25
```

**액션(연산)** — Treap이 제공하는 연산 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor()` | 빈 Treap 생성 | $O(1)$ |
| `insert(x)` | `split` → 새 노드 생성 → `merge` 두 번 | 기대 $O(\log n)$ |
| `delete(x)` | `split` 두 번 → 루트 하나 제거 → `merge` 두 번 | 기대 $O(\log n)$ |
| `findKth(k)` | `size`로 좌/우 방향을 정하며 하강 | 기대 $O(\log n)$ |
| `split(T, x)` (내부) | 키 기준으로 두 Treap으로 분리 | 기대 $O(\log n)$ |
| `merge(L, R)` (내부) | priority 기준으로 두 Treap을 합치기 | 기대 $O(\log n)$ |

핵심 연산인 `split`과 `merge`를 자세히 봅니다.

**`split(T, x)`**: 키 $< x$인 부분을 $L$로, 키 $\geq x$인 부분을 $R$로 분리합니다.

$$
\text{split}(T, x) =
\begin{cases}
(\text{null}, \text{null}) & T = \text{null} \\
(T \text{ with right} \leftarrow L',\ R') \text{ where } (L', R') = \text{split}(T.\text{right}, x) & T.key < x \\
(L',\ T \text{ with left} \leftarrow R') \text{ where } (L', R') = \text{split}(T.\text{left}, x) & T.key \geq x
\end{cases}
$$

`{3, 5, 8}` 트리를 $x=5$로 split하면(실제 실행 결과):

```text
Before:              5·p30 (size=3)
                     /             \
              3·p20 (size=1)   8·p25 (size=1)

After split(T, 5):
  L = 3·p20 (size=1)                 ← 키 < 5
  R = 5·p30 (size=2)                 ← 키 ≥ 5
        \
       8·p25 (size=1)
```

**`merge(L, R)`**: $\max(\text{keys}(L)) < \min(\text{keys}(R))$인 두 Treap을, priority가 높은 쪽이 루트가 되도록 합칩니다.

$$
\text{merge}(L, R) =
\begin{cases}
R & L = \text{null} \\
L & R = \text{null} \\
L \text{ with right} \leftarrow \text{merge}(L.\text{right}, R) & L.priority \geq R.priority \\
R \text{ with left} \leftarrow \text{merge}(L, R.\text{left}) & \text{otherwise}
\end{cases}
$$

방금 나눈 $L=\{3\}$, $R=\{5,8\}$을 다시 합치면(실제 실행 결과, split의 역연산처럼 원래 모양으로 복원됩니다):

```text
Before:  L = 3·p20 (size=1)         R = 5·p30 (size=2)
                                            \
                                         8·p25 (size=1)

After merge(L, R): 3.priority(20) < 5.priority(30) → R이 루트
                 5·p30 (size=3)
                /              \
         3·p20 (size=1)    8·p25 (size=1)
```

### 왜 모순 없이 작동하는가

**불변식이 항상 보존되는 이유(귀납)**: 빈 Treap은 세 불변식을 공허하게 만족합니다(귀납 기초). `split`은 재귀 호출이 반환한 $L', R'$을 그대로 자식으로 붙이고 `pullUp`으로 size만 갱신하므로, 자식 쪽에서 이미 성립하던 BST·힙 조건은 그대로 유지되고 size만 새로 맞춰집니다. `merge`도 마찬가지로 "priority가 높은 쪽이 루트, 낮은 쪽이 그 자식 서브트리로 재귀 병합"되므로 힙 조건이 매 단계 유지되고, 병합 전 $\max(L) < \min(R)$ 전제 덕분에 BST 조건도 유지됩니다. `insert`·`delete`는 `split`/`merge`의 합성이므로, 두 연산이 불변식을 보존하는 한 `insert`·`delete`도 보존합니다.

**기대 높이 $O(\log n)$인 이유**: priority가 균등 분포인 난수라면, "키를 입력 순서대로 넣은 트리"가 아니라 "키를 priority 내림차순(=무작위 순서)으로 넣은 것과 동일한 BST"가 만들어집니다. 무작위 순서로 삽입된 BST의 기대 높이가 $O(\log n)$이라는 것은 잘 알려진 결과입니다. 즉 Treap은 "입력이 정렬돼 있으면 위험하다"는 naive BST의 약점을, priority로 입력 순서를 무력화시켜서 피해 갑니다.

여기서 헷갈리기 쉬운 포인트는 **`delete`의 두 번째 `split` 기준**입니다. `delete(x)`는 `split(root, x)`로 $(L, R)$을 얻은 뒤, $R$에서 키 $x$인 노드들만 떼어내려고 `split(R, x+1)`을 호출해 $(M, R_2)$를 얻습니다. 만약 실수로 `split(R, x+1)` 대신 `split(R, x)`를 쓰면 어떻게 될까요? $R$의 모든 키는 이미 $\geq x$이므로, `split(R, x)`는 "키 $< x$"인 부분이 항상 비어 $M = \text{null}$이 되고 $R_2 = R$ 그대로 남습니다. 실제로 `{2, 2, 5, 8}`에서 `delete(2)`를 이 오답 버전으로 실행해 확인해 보면, 정렬된 키가 `[2, 2, 5, 8]` → `[2, 2, 5, 8]`로 **전혀 줄지 않습니다**. 반드시 `x+1`을 써서 "키 $x$인 노드들"만 정확히 떼어내야 합니다.

두 번째로 헷갈리기 쉬운 포인트는 **`pullUp` 호출 타이밍**입니다. `split`과 `merge`는 재귀로 자식을 먼저 바꾼 뒤 **반환 직전에** `pullUp`을 호출해 size를 다시 계산해야 합니다. 위 split 예시에서 `pullUp`을 생략하면 $R$의 size는 새 값 $2$ 대신 분리 전 값인 $3$으로 남아 있게 되어, 실제 자식 수(1개, `8`뿐)와 어긋납니다. `findKth`는 오직 `size`만 보고 좌우를 판단하므로, size가 틀리면 존재하지 않는 원소를 세거나 있는 원소를 건너뛰며 엉뚱한 값을 반환합니다.

잠깐, 확인 하나만 해 볼까요? `{1, 3, 5, 8}`(priority: $1{\to}40,\ 5{\to}30,\ 3{\to}20,\ 8{\to}25$)에서 `delete(5)`를 하면 어떤 모양이 될까요? 힌트: `split(root, 5)`와 `split(R, 6)`을 순서대로 적용해 보세요. 실제로 실행해 보면 `1·p40(size=3)`이 루트가 되고 오른쪽 자식이 `8·p25(size=2)`, 그 왼쪽 자식이 `3·p20(size=1)`이 됩니다 — `findKth(1..3)`은 `1, 3, 8`을 돌려줍니다.

엣지 케이스를 점검해 둡니다.

```text
빈 Treap에서 findKth        → 1 ≤ k ≤ |T| 전제가 깨지므로 정의되지 않음
delete(x), x ∉ T             → split(R, x+1)에서 M = null → 아무 변화 없음
동일 키 3개 삽입 후 delete   → 하나만 제거되고 나머지 두 개는 유지 (실측: 7,7,7 → delete → 7,7)
중복 삽입 후 findKth         → 같은 키가 연속된 순위를 차지 (실측: {2,2,5,8}에서 findKth(1)=2, findKth(2)=2)
음수 키 포함                 → BST 조건은 부호와 무관하게 그대로 성립 (실측: {-3,0,-1,2}에서 findKth(1)=-3)
```

## 아이디어를 코드로 옮기기

먼저 **원형(naive)**: priority 없이 그냥 BST에 삽입만 하면 어떻게 될까요.

```ts
interface BstNode {
  key: number;
  left: BstNode | null;
  right: BstNode | null;
}

function bstInsert(root: BstNode | null, key: number): BstNode {
  if (root === null) return { key, left: null, right: null };
  if (key < root.key) root.left = bstInsert(root.left, key);
  else root.right = bstInsert(root.right, key);
  return root;
}
```

이 코드에 $1, 2, \dots, 1000$을 정렬된 순서로 넣어 높이를 재 보면 **높이가 정확히 1000**입니다(오른쪽 자식만 계속 생기는 사슬). 모든 연산이 $O(n)$으로 퇴화한다는 뜻이죠. Treap이 필요한 이유가 바로 여기서 드러납니다 — priority라는 축을 하나 더 두면 이 퇴화를 막을 수 있습니다.

다음은 **최종 구현**입니다. `split`/`merge`를 먼저 짜고, `insert`/`delete`/`findKth`는 그 위에 얹습니다.

```ts
interface TreapNode {
  key: number;
  priority: number;
  left: TreapNode | null;
  right: TreapNode | null;
  size: number;
}

function makeNode(key: number, priority: number): TreapNode {
  return { key, priority, left: null, right: null, size: 1 };
}

function sz(v: TreapNode | null): number {
  return v === null ? 0 : v.size;
}

function pullUp(v: TreapNode): void {
  v.size = sz(v.left) + sz(v.right) + 1;
}

function split(t: TreapNode | null, x: number): [TreapNode | null, TreapNode | null] {
  if (t === null) return [null, null];
  if (t.key < x) {
    const [l, r] = split(t.right, x);
    t.right = l;
    pullUp(t);
    return [t, r];
  } else {
    const [l, r] = split(t.left, x);
    t.left = r;
    pullUp(t);
    return [l, t];
  }
}

function merge(l: TreapNode | null, r: TreapNode | null): TreapNode | null {
  if (l === null) return r;
  if (r === null) return l;
  if (l.priority >= r.priority) {
    l.right = merge(l.right, r);
    pullUp(l);
    return l;
  } else {
    r.left = merge(l, r.left);
    pullUp(r);
    return r;
  }
}

class Treap {
  private root: TreapNode | null = null;
  private priorityFn: () => number;

  // priorityFn은 테스트에서 결정적 priority를 주입하기 위한 것으로,
  // 기본값 Math.random을 쓰면 constructor()를 인자 없이 호출해도 됩니다.
  constructor(priorityFn: () => number = Math.random) {
    this.priorityFn = priorityFn;
  }

  insert(x: number): void {
    const node = makeNode(x, this.priorityFn());
    const [l, r] = split(this.root, x);
    this.root = merge(merge(l, node), r);
  }

  delete(x: number): void {
    const [l, r] = split(this.root, x);
    const [m, r2] = split(r, x + 1); // x+1! (x만 쓰면 아무것도 안 지워짐)
    const mReduced = m === null ? null : merge(m.left, m.right);
    this.root = merge(merge(l, mReduced), r2);
  }

  findKth(k: number): number {
    let v = this.root;
    while (v !== null) {
      const ls = sz(v.left);
      if (k <= ls) {
        v = v.left;
      } else if (k === ls + 1) {
        return v.key;
      } else {
        k -= ls + 1;
        v = v.right;
      }
    }
    throw new Error("k out of range");
  }
}
```

가장 중요한 부분은 `split`과 `merge` 두 함수입니다. 나머지 `insert`·`delete`·`findKth`는 이 둘의 조합이거나(size를 읽는 하강)일 뿐, 새로운 아이디어가 없습니다.

놓치기 쉬운 구현부를 짚어 둡니다.

- **`pullUp`은 반드시 재귀 호출 다음, 반환 직전에.** `split`/`merge` 안에서 자식 포인터(`t.right`, `t.left`, `l.right`, `r.left`)를 바꾼 **직후**에 호출해야 size가 정확합니다. 순서를 바꿔 자식 갱신 전에 부르면 옛날 size를 그대로 쓰는 것과 같은 실수가 됩니다.
- **`delete`의 두 번째 `split` 기준은 `x + 1`.** `x`를 쓰면 위에서 확인했듯 아무것도 지워지지 않습니다.
- **`merge`의 비교는 `>=`.** priority가 같을 때 어느 쪽이 루트가 되든 정확성에는 영향이 없지만(둘 다 유효한 최대 힙), 코드 안에서 `l.priority >= r.priority`로 일관되게 정하면 동일 priority 충돌 시에도 결정적으로 동작합니다.

> split은 크기(`< x` / `≥ x`)로 자르고, merge는 힘(priority)이 센 쪽이 위로 온다.

정리하면, Treap은 **priority라는 축 하나를 추가**해서 "BST 조건(키)"과 "균형(무작위 힙)"이라는 서로 다른 목표를 동시에 만족시킵니다. `split`은 그 두 조건을 유지한 채 트리를 자르고, `merge`는 유지한 채 붙이며, `insert`·`delete`는 이 둘의 조합으로 끝납니다. `size` 필드 하나를 얹으면 `findKth`도 같은 하강 패턴으로 기대 $O(\log n)$에 답이 나옵니다 — naive BST가 정렬 입력에서 $O(n)$으로 무너지는 것과 대조적으로, 처음 목표했던 "입력 순서 무관 균형"을 그대로 달성한 셈입니다.
