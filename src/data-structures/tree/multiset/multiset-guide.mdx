# Multiset — 정렬을 유지한 채 중복을 허용하는 이진 탐색 컨테이너

## 한눈에 보는 컨셉

정렬된 순서를 유지하면서 같은 값을 몇 번이든 담을 수 있는 컨테이너예요. 비결은 배열을 항상 정렬 상태로 묶어 두고, 삽입·탐색 위치를 이진 탐색(`lowerBound`/`upperBound`)으로 $O(\log n)$에 찾아내는 것입니다. 덕분에 `count`·`has`·`min`·`max` 같은 조회가 빨라지고, `std::multiset`이 없는 JavaScript/TypeScript에서도 같은 효과를 낼 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 Multiset을 떠올리세요.

- 데이터가 계속 삽입·삭제되는데도 **정렬된 상태**를 유지한 채 조회해야 한다
- 같은 값이 몇 번 들어왔는지(`count`)를 자주 세야 한다
- 최솟값/최댓값을 반복적으로 물어본다
- 사용 언어에 정렬 컨테이너가 기본 제공되지 않는다(JS/TS에는 `std::multiset`이 없어요)

naive한 접근들과 비교하면 왜 이 구조가 필요한지 보입니다.

```text
연산        배열(정렬 안 함)   배열(매번 재정렬)     Multiset(이진 탐색)         균형 BST 기반
add         O(1)              O(n log n)            O(log n) 탐색 + O(n) 이동   O(log n)
delete      O(n)              O(n log n)            O(log n) 탐색 + O(n) 이동   O(log n)
has/count   O(n)              O(log n)              O(log n)                    O(log n)
min/max     O(n)              O(1)                  O(1)                        O(log n)*
```

*균형 BST는 min/max를 별도로 캐싱해 두지 않으면 왼쪽/오른쪽 끝까지 내려가야 해서 $O(\log n)$이에요.

**선택 기준**: $n \le 10^4$ 정도면 배열 + 이진 탐색 방식으로 충분합니다 — 삽입 자체는 $O(n)$이지만 상수가 작아 실전에서는 오히려 빠르게 동작해요. $n$이 $10^5$를 넘거나 삽입/삭제가 지배적인 워크로드라면 균형 이진 트리(AVL, 레드-블랙, B+ Tree) 기반 multiset이 필요합니다.

### 문제 사례와 적용 예시

- **슬라이딩 윈도우 중앙값**: 실시간 센서 스트림에서 최근 K개 값의 중앙값을 계속 보고해야 할 때, 작은 절반을 담는 `lower`와 큰 절반을 담는 `upper` 두 개의 Multiset으로 관리하면 삽입·삭제·중앙값 조회가 모두 $O(\log n)$이 됩니다.
- **리더보드/랭킹 시스템**: 동점자가 흔한 점수 분포에서 "특정 점수를 가진 인원 수"(`count`)와 정렬된 순위 구간을 함께 다뤄야 하는 상황.
- **이벤트 스케줄러**: 타임스탬프를 계속 삽입·삭제하면서도 항상 정렬된 순서로 다음 이벤트를 꺼내야 하는 큐.
- **코딩 테스트**: "정렬 순서를 유지한 채 k번째로 작은/큰 원소를 구하라" 류의 order-statistics 문제.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**은 정렬된 배열 하나와 비교 함수 하나면 충분해요.

```ts
class Multiset<T> {
  private _data: T[];                          // comparator 기준 오름차순 정렬, 중복 허용
  private _comparator: (a: T, b: T) => number;  // 기본값: a < b ? -1 : a > b ? 1 : 0
}
```

지켜야 할 불변식은 하나입니다. 정식으로 쓰면:

$$
\forall\, 0 \le i < j < |\_data|:\ \text{comparator}(\_data[i],\, \_data[j]) \le 0
$$

즉 배열 어느 두 지점을 봐도 앞쪽이 comparator 기준으로 뒤쪽보다 크지 않습니다. 같은 값끼리는 정렬의 자연스러운 결과로 서로 인접하게 모여요.

```text
인덱스:   0   1   2   3   4   5
값:       1   2   2   2   5   7
                └───┬───┘
              값 2가 세 번, 항상 인접해 있다
```

**액션(연산)** — 이 자료구조가 제공하는 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `add(item)` | comparator 기준 정렬 위치를 찾아 삽입 | $O(\log n)$ 탐색 + $O(n)$ 이동 |
| `delete(item)` | 해당 값을 하나만 제거, 없으면 `false` | $O(\log n)$ 탐색 + $O(n)$ 이동 |
| `deleteAll(item)` | 해당 값 전부 제거, 제거된 개수 반환 | $O(\log n)$ 탐색 + $O(n)$ 이동 |
| `has(item)` | 존재 여부 | $O(\log n)$ |
| `count(item)` | 해당 값의 개수 | $O(\log n)$ |
| `min()` / `max()` | 최솟값/최댓값, 비어 있으면 `undefined` | $O(1)$ |
| `size()` | 총 원소 수(중복 포함) | $O(1)$ |
| `toArray()` | 정렬된 배열의 복사본 | $O(n)$ |

핵심 연산은 `lowerBound`/`upperBound` 두 개예요. 정식 정의는 이렇습니다.

$$
\text{lowerBound}(x) = \min\{\, i \mid \text{comparator}(\_data[i], x) \ge 0 \,\}
$$
$$
\text{upperBound}(x) = \min\{\, i \mid \text{comparator}(\_data[i], x) > 0 \,\}
$$

(만족하는 `i`가 없으면 배열 길이를 반환한다고 약속합니다.)

`[1, 2, 2, 2, 5, 7]`에서 `lowerBound(2)`를 이진 탐색으로 좁혀 가는 과정을 그대로 그려 보면:

```text
[lo, hi) 구간을 반씩 좁힌다 (comparator(data[mid], 2) 부호로 판단)

lo=0, hi=6, mid=3, data[3]=2, cmp=0(>=0)     → hi=3
lo=0, hi=3, mid=1, data[1]=2, cmp=0(>=0)     → hi=1
lo=0, hi=1, mid=0, data[0]=1, cmp=-1(<0)     → lo=1
lo=1, hi=1                                    → 종료, lowerBound(2)=1
```

같은 방식으로 `upperBound(2)`는 조건이 `<= 0`으로 한 칸 더 밀려 `4`가 됩니다. 그래서 `count(2) = upperBound(2) - lowerBound(2) = 4 - 1 = 3`이에요 — 실제로 배열에 2가 인덱스 1, 2, 3에 세 번 있는 것과 정확히 일치합니다.

`add`가 이 위치를 어떻게 쓰는지도 Before/After로 보겠습니다. `[1, 2, 2, 2, 5, 7]`에 `add(4)`를 실행하면 `lowerBound(4) = 4`이므로 인덱스 4에 `splice`로 끼워 넣습니다.

```text
Before: [1, 2, 2, 2, 5, 7]
                       ↑ lowerBound(4) = 4 (5 앞자리)
After:  [1, 2, 2, 2, 4, 5, 7]
                       └── 새로 삽입된 4
```

### 왜 모순 없이 작동하는가

**`add`가 불변식을 보존하는 이유**: `lowerBound(x)`는 "comparator 기준으로 `x` 이상인 첫 위치"이므로, 그 앞쪽 원소는 전부 `x`보다 작고 뒤쪽 원소는 전부 `x` 이상입니다. 그 지점에 `x`를 끼워 넣으면 왼쪽 구간(`< x`) - `x` - 오른쪽 구간(`>= x`) 순서가 그대로 유지돼요. 즉 삽입 전에 정렬 상태였다면 삽입 후에도 정렬 상태입니다. 빈 배열(정렬 상태가 자명하게 성립)에서 출발해 모든 `add`가 이 성질을 보존하므로, 귀납적으로 어느 시점에도 배열은 정렬 상태예요.

**`delete`/`deleteAll`이 불변식을 보존하는 이유**: 정렬된 배열에서 원소를 하나 또는 연속 구간만큼 제거해도 남은 원소들의 상대적 순서는 바뀌지 않습니다. `deleteAll`이 `lowerBound`~`upperBound` 구간을 한 번에 잘라내는 것도 마찬가지예요 — 그 구간이 정확히 "값이 `x`인 원소들의 모임"이라는 사실은 위에서 본 `lowerBound`/`upperBound` 정의 자체가 보장합니다.

여기서 헷갈리기 쉬운 포인트는 **`lowerBound`와 `upperBound`를 가르는 것이 비교 조건의 `<`와 `<=` 딱 한 글자 차이**라는 점입니다. 만약 `delete`에서 `lowerBound` 대신 실수로 `upperBound` 공식(조건을 `<=`로)을 써 버리면 어떻게 될까요? `[1, 2, 2, 3]`에서 `delete(2)`를 예로 들어 보면:

```text
정상: lowerBound(2) = 1 → data[1] === 2 → splice(1,1) → [1, 2, 3], true 반환

버그: upperBound(2) 공식을 lowerBound 자리에 쓰면 pos = upperBound(2) = 3
      → data[3] === 3 (2가 아님!) → 아무것도 지우지 못하고 false를 반환
      → 배열에 2가 분명히 있는데도 delete(2)가 실패한 것처럼 보인다
```

두 함수 다 "어떤 조건을 만족하는 첫 인덱스"를 찾는 이진 탐색이라 겉보기엔 거의 같아 보이지만, 조건의 등호 하나가 결과를 통째로 어긋나게 만듭니다.

> 확인 질문 하나만 해 볼까요? 배열이 `[5, 5, 5]`일 때 `count(5)`는 얼마일까요? — `lowerBound(5) = 0`, `upperBound(5) = 3`이므로 `count(5) = 3 - 0 = 3`입니다. 원소 3개가 모두 5니까 직관과도 맞아떨어져요.

엣지 케이스도 점검해 둡니다.

```text
빈 배열              → min()/max() = undefined, has = false, count = 0, delete = false
원소 1개             → min() === max() === 그 원소
삽입 위치가 맨 끝     → lowerBound(모든 원소보다 큰 값) = data.length
삽입 위치가 맨 앞     → lowerBound(모든 원소보다 작은 값) = 0
모든 원소가 동일      → lowerBound = 0, upperBound = length, count = length
```

## 아이디어를 코드로 옮기기

가장 단순한 원형부터 시작해서 왜 다음 단계로 넘어가야 하는지 순서대로 짚어 볼게요.

**원형(naive)**: "일단 넣고 매번 다시 정렬한다"는 접근이 가장 쉽게 떠오릅니다.

```ts
class MultisetNaive {
  private data: number[] = [];
  add(item: number): void {
    this.data.push(item);
    this.data.sort(); // 함정: comparator 없이 기본 sort() 호출
  }
}
```

이 코드는 매번 $O(n \log n)$이 드는 것도 아쉽지만, 진짜 함정은 따로 있습니다. JS의 기본 `sort()`는 **comparator를 안 주면 원소를 문자열로 바꿔 사전식으로 비교**해요. `add(10)`, `add(1)`, `add(2)`를 순서대로 실행하면:

```text
add(10) → data=[10] → sort() → [10]
add(1)  → data=[10,1] → sort() → "1" < "10" → [1, 10]
add(2)  → data=[1,10,2] → sort() → "1" < "10" < "2" (사전식!) → [1, 10, 2]
```

숫자로는 `[1, 2, 10]`이 맞는데 실제로는 `[1, 10, 2]`가 나와요 — 실측으로 확인한 값입니다. 정렬 컨테이너를 만든다면서 정렬조차 틀리는 셈이니, comparator를 명시하는 개선이 필요합니다.

**개선**: comparator를 쓰는 선형 탐색으로 삽입 위치를 직접 찾습니다.

```ts
class MultisetLinear<T> {
  private data: T[] = [];
  private cmp: (a: T, b: T) => number = (a, b) => (a < b ? -1 : a > b ? 1 : 0);
  add(item: T): void {
    let i = 0;
    while (i < this.data.length && this.cmp(this.data[i]!, item) < 0) i++;
    this.data.splice(i, 0, item);
  }
}
```

이제 정렬은 항상 올바릅니다(`add(10)`, `add(1)`, `add(2)` → `[1, 2, 10]`, 실측 확인 완료). 하지만 삽입 위치를 찾는 `while` 루프가 여전히 $O(n)$이에요 — 배열이 이미 정렬돼 있다는 정보를 전혀 활용하지 못하고 있습니다.

**최종**: 이미 정렬된 배열이라는 사실을 이진 탐색으로 활용합니다.

```ts
export class Multiset<T> {
  private _data: T[];
  private _comparator: (a: T, b: T) => number;

  constructor(comparator?: (a: T, b: T) => number) {
    this._data = [];
    this._comparator = comparator ?? ((a, b) => (a < b ? -1 : a > b ? 1 : 0));
  }

  private lowerBound(item: T): number {
    let lo = 0, hi = this._data.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this._comparator(this._data[mid]!, item) < 0) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }

  private upperBound(item: T): number {
    let lo = 0, hi = this._data.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this._comparator(this._data[mid]!, item) <= 0) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }

  add(item: T): void {
    const pos = this.lowerBound(item);
    this._data.splice(pos, 0, item);
  }

  delete(item: T): boolean {
    const pos = this.lowerBound(item);
    if (pos < this._data.length && this._comparator(this._data[pos]!, item) === 0) {
      this._data.splice(pos, 1);
      return true;
    }
    return false;
  }

  deleteAll(item: T): number {
    const lo = this.lowerBound(item);
    const hi = this.upperBound(item);
    this._data.splice(lo, hi - lo);
    return hi - lo;
  }

  has(item: T): boolean {
    const pos = this.lowerBound(item);
    return pos < this._data.length && this._comparator(this._data[pos]!, item) === 0;
  }

  count(item: T): number {
    return this.upperBound(item) - this.lowerBound(item);
  }

  min(): T | undefined {
    return this._data[0];
  }

  max(): T | undefined {
    return this._data[this._data.length - 1];
  }

  size(): number {
    return this._data.length;
  }

  toArray(): T[] {
    return [...this._data];
  }
}
```

가장 중요한 부분은 `lowerBound`의 `if (this._comparator(this._data[mid]!, item) < 0) lo = mid + 1; else hi = mid;` 두 줄입니다. `upperBound`는 이 조건을 `<=`로 딱 한 글자만 바꾼 거울상이에요 — 앞서 본 함정처럼, 이 부호 하나가 "값이 같을 때 왼쪽 경계에서 멈출지, 오른쪽 경계까지 밀고 갈지"를 가릅니다.

놓치기 쉬운 구현부를 짚어 두면:

- `delete`는 `lowerBound`로 찾은 위치의 값이 실제로 `item`과 같은지(`comparator(...) === 0`)를 반드시 확인해야 합니다. `item`이 아예 없어도 `lowerBound`는 "삽입될 위치"를 반환하니, 이 확인 없이 바로 `splice`하면 엉뚱한 원소를 지웁니다.
- `deleteAll`은 `lowerBound`~`upperBound` 구간 전체를 한 번의 `splice(lo, hi - lo)`로 지웁니다. 하나씩 반복해서 지우면 매번 인덱스가 밀려 버그가 나기 쉬워요.
- `min`/`max`는 정렬이 유지된다는 불변식 덕분에 `_data[0]`/`_data[_data.length - 1]`을 읽기만 하면 됩니다 — 별도 탐색이 필요 없어요.

> 기억법: "lower는 `<` 로 멈추고, upper는 `<=` 로 한 칸 더 간다."
