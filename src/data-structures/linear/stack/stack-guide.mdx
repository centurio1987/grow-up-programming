# Stack — 배열 끝에서만 여닫는 LIFO 통

## 한눈에 보는 컨셉

한쪽 끝(top)에서만 넣고(push) 빼는(pop) LIFO(Last-In-First-Out) 자료구조예요. 비결은 딱 하나, **top을 배열의 맨 앞이 아니라 맨 뒤로 고정**하는 것입니다. 그러면 push/pop/peek 모두 O(1)에 끝나요. 실행취소, 함수 호출, 괄호 짝 맞추기처럼 "가장 최근 것부터 되돌린다"는 상황 전부가 이 구조 하나로 풀립니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Stack을 떠올리세요.

- "가장 최근에 처리한 것을 가장 먼저 되돌려야/꺼내야 한다" — 실행취소(undo), 함수 호출 복귀, 브라우저 뒤로가기
- 삽입·삭제가 **오직 한쪽 끝**에서만 일어나고, 중간 원소에 직접 접근할 필요가 없다
- 짝을 맞추거나 순서를 뒤집어야 한다 — 괄호 검사, 재귀를 반복문으로 바꾸는 작업

naive하게 배열의 **맨 앞**을 top으로 삼으면 어떻게 될까요? 앞에 넣거나 빼려면 나머지 원소를 전부 한 칸씩 밀거나 당겨야 합니다. 반대로 배열의 **맨 뒤**를 top으로 삼으면 다른 원소를 건드릴 필요가 없어요.

```text
연산               naive (배열 앞 = top)     Stack (배열 뒤 = top)
push 1회           O(n) — 뒤 원소 전부 시프트   O(1) amortized
pop 1회            O(n) — 나머지 전부 당김      O(1)
n회 연산 총합       O(n^2)                     O(n)
```

$n = 10^6$번 연산이면 naive 방식은 $O(n^2) = 10^{12}$로 1초를 훌쩍 넘기지만, 배열 뒤를 top으로 쓰면 $O(n) = 10^6$으로 끝납니다.

비슷하게 헷갈리는 자료구조로 **Queue**가 있어요. "먼저 넣은 것을 먼저 꺼내야" 하면 Queue(FIFO), "나중에 넣은 것을 먼저 꺼내야" 하면 Stack(LIFO)입니다. 양쪽 끝에서 모두 넣고 빼야 한다면 Deque를 고려하세요.

### 문제 사례와 적용 예시

- **에디터의 실행취소(undo/redo)**: 편집 동작을 push로 기록해두고, Ctrl+Z를 누르면 pop으로 가장 최근 동작부터 되돌립니다.
- **함수 호출 스택**: 함수를 호출할 때마다 지역 변수·복귀 주소가 push되고, 함수가 끝나면 pop되어 호출자로 되돌아갑니다. 재귀를 반복문으로 바꿀 때도 이 스택을 직접 흉내 냅니다.
- **괄호/문법 짝 검사**: 여는 괄호를 push하고 닫는 괄호를 만나면 pop해서 짝이 맞는지 확인합니다. 컴파일러의 구문 분석기, JSON 파서가 이 방식을 씁니다.
- **코딩 테스트 맥락**: DFS의 명시적 스택 구현, "직전 상태로 되돌리기"가 필요한 백트래킹 문제에서 Stack이 그대로 등장합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 배열 하나면 충분합니다.

```ts
class Stack<T> {
  private items: T[] = []; // 유일한 내부 저장소
}
```

top은 별도 필드가 아니라 배열 길이로부터 계산되는 개념적 위치예요.

$$
\text{top 인덱스} = |{\text{items}}| - 1
$$

지켜야 할 불변식은 두 가지입니다.

1. **top은 항상 배열의 마지막 인덱스다.** `items[items.length - 1]`이 곧 top이고, 그 외의 위치는 top이 될 수 없다.
2. **push/pop은 반드시 배열의 같은 끝(뒤)에서만 일어난다.** 앞쪽 원소는 절대 직접 밀거나 당기지 않는다.

구조를 그림으로 보면:

```text
items:  [ 10 | 20 | 30 ]
          idx0  idx1  idx2
                        ↑
                       top (length - 1 = 2)
```

**액션(연산)** — 이 자료구조가 제공하는 다섯 가지 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `push(item)` | top 뒤에 새 원소를 추가 | $O(1)$ amortized |
| `pop()` | top 원소를 제거하고 반환. 비어있으면 `undefined` | $O(1)$ |
| `peek()` | top 원소를 제거 없이 반환. 비어있으면 `undefined` | $O(1)$ |
| `isEmpty()` | 원소가 하나도 없는지 확인 | $O(1)$ |
| `size()` | 현재 원소 개수 | $O(1)$ |

핵심 연산인 `push`와 `pop`을 before/after로 자세히 볼게요.

**① push — top 뒤에 한 칸 늘리기**

$$
\text{push}(x): \quad \text{items}[|{\text{items}}|] \leftarrow x, \quad |{\text{items}}| \leftarrow |{\text{items}}| + 1
$$

```text
Before: items = [ 10 | 20 ]              length = 2
push(30)
After:  items = [ 10 | 20 | 30 ]         length = 3
                              ↑ 새 top
```

**② pop — top 한 칸 떼어내기**

$$
\text{pop}(): \quad x \leftarrow \text{items}[|{\text{items}}| - 1], \quad |{\text{items}}| \leftarrow |{\text{items}}| - 1, \quad \text{return } x
$$

```text
Before: items = [ 10 | 20 | 30 ]         length = 3
pop() → 30
After:  items = [ 10 | 20 ]              length = 2
                        ↑ 새 top
```

### 왜 모순 없이 작동하는가

불변식 1("top = length - 1")이 모든 연산 뒤에도 살아있는지 귀납적으로 확인해봅시다.

- **기저**: 빈 스택은 `items = []`, length = 0. top이 가리킬 원소가 없으니 불변식은 자명하게 성립합니다.
- **push 유지**: length가 $k$일 때 불변식이 성립한다고 가정하면 top은 인덱스 $k-1$입니다. `push`는 인덱스 $k$에 새 값을 쓰고 length를 $k+1$로 늘리므로, 새 top은 인덱스 $k = (k+1)-1$ — 불변식이 그대로 유지됩니다.
- **pop 유지**: length가 $k$일 때 top(인덱스 $k-1$)을 제거하고 length를 $k-1$로 줄이면, 새 top은 인덱스 $k-2 = (k-1)-1$ — 역시 유지됩니다.

배열의 앞쪽은 push/pop 어느 쪽도 건드리지 않으므로 불변식 2도 자동으로 지켜집니다.

**여기서 헷갈리기 쉬운 포인트는 top을 배열의 인덱스 0으로 착각하는 것입니다.** "맨 처음 넣은 자리가 위쪽 아닌가?" 하는 직관 때문에 종종 벌어지는 실수예요. 실제로 확인해봅시다 — `push("A")`, `push("B")`, `push("C")`를 순서대로 실행하면 `items = ["A", "B", "C"]`가 됩니다.

```text
착각(top = index 0)한 사람의 예상 pop 순서:  A, B, C   (push한 순서 그대로)
실제 pop 순서(top = index length-1, LIFO):  C, B, A   (push의 역순)
```

두 순서를 나란히 비교하면 1번째(`A` vs `C`)와 3번째(`C` vs `A`)는 확실히 어긋나지만, **2번째(`B` vs `B`)는 우연히 일치**합니다. 홀수 개 원소를 뒤집으면 가운데 원소는 항상 제자리이기 때문이에요. 그래서 이 착각은 더 위험합니다 — 두세 번 pop 해보고 값이 맞아떨어지면 "역시 index 0이 top이었구나" 하고 착각을 굳혀버리기 쉽습니다. 항상 push의 **역순**으로 나온다는 규칙 자체를 기준으로 삼아야, 이런 우연한 일치에 속지 않습니다.

잠깐, 확인 하나만 해볼까요? 스택에 A, B, C를 순서대로 push한 뒤 pop을 두 번 하면 어떤 값이 어떤 순서로 나올까요? — 정답은 **C, 그다음 B**입니다. 마지막에 넣은 것부터 거꾸로 나오니까요.

엣지 케이스도 점검해둡니다.

```text
빈 스택에서 pop()/peek()   → undefined (에러 아님, size는 여전히 0)
원소 1개 상태에서 pop()    → 빈 스택. 이후 isEmpty() === true
연속 push 후 즉시 peek     → 방금 push한 값과 정확히 같아야 함(제거 없음)
```

## 아이디어를 코드로 옮기기

**가장 중요한 부분은 "배열의 어느 쪽 끝을 top으로 삼는가" 하나뿐입니다.** 이 결정이 O(n)과 O(1)을 가릅니다. 진화 단계로 보여드릴게요.

**원형(naive) — 배열의 맨 앞을 top으로 삼는다.** 직관적으로는 "가장 최근 것이 맨 위(앞)"라는 그림이 자연스러워서 이렇게 짜기 쉽습니다.

```ts
class NaiveStack<T> {
  private items: T[] = [];

  push(item: T): void {
    this.items.unshift(item); // 앞에 넣으려면 기존 원소를 전부 한 칸씩 밀어야 한다 — O(n)
  }

  pop(): T | undefined {
    return this.items.shift(); // 앞에서 빼려면 나머지를 전부 한 칸씩 당겨야 한다 — O(n)
  }
}
```

`unshift`/`shift`는 배열 앞에서 삽입/삭제하는 순간, 자바스크립트 엔진이 나머지 모든 원소의 인덱스를 다시 매겨야 합니다. $n = 10^6$번 push하면 이 시프트 비용의 합이 $O(n^2)$까지 쌓여 1초 제한을 훌쩍 넘깁니다.

**개선 — top을 배열의 맨 뒤로 옮긴다.** 관찰: LIFO는 "마지막에 넣은 것을 먼저 꺼낸다"는 뜻일 뿐, top이 물리적으로 어느 쪽 인덱스에 있어야 하는지는 규정하지 않습니다. 배열의 끝은 다른 원소를 밀 필요가 없으니, 끝을 top으로 삼으면 됩니다.

```ts
push(item: T): void {
  this.items.push(item); // 배열 끝에 추가 — 다른 원소는 그대로
}

pop(): T | undefined {
  return this.items.pop(); // 배열 끝에서 제거 — 다른 원소는 그대로
}
```

왜 다음 단계로 가야 할까요? 위 두 메서드만으로 이미 O(n) → O(1)이 달성됐지만, 아직 `peek`/`isEmpty`/`size`가 빠져 있고 캡슐화도 안 돼 있습니다. 최종 형태로 정리합니다.

**최종 구현**

```ts
class Stack<T> {
  private items: T[] = [];

  push(item: T): void {
    this.items.push(item);
  }

  pop(): T | undefined {
    return this.items.pop();
  }

  peek(): T | undefined {
    return this.items[this.items.length - 1];
  }

  isEmpty(): boolean {
    return this.items.length === 0;
  }

  size(): number {
    return this.items.length;
  }
}
```

놓치기 쉬운 지점 두 가지를 짚어둡니다.

- **`peek()`은 `items[items.length - 1]`로 직접 인덱싱하고, `pop()`처럼 배열을 변형하면 안 됩니다.** `peek()` 안에서 실수로 `this.items.pop()`을 부르면 조회만 하려던 원소가 실제로 사라져버립니다.
- **빈 배열에서 `items[items.length - 1]`은 `items[-1]`이 되어 `undefined`를 반환합니다.** `noUncheckedIndexedAccess` 설정 덕분에 이 반환 타입이 `T | undefined`로 자동 추론되므로, 별도의 빈 검사 분기 없이도 스펙(빈 스택에서 `undefined`)이 그대로 충족됩니다.

> 기억법: "넣을 때 민 곳에서 뺀다 — 앞을 밀지 말고 뒤를 밀어라."

## 스스로 점검하기

1. 빈 스택에 `push(1), push(2), pop(), push(3), peek()`을 순서대로 실행하면 최종 `peek()`의 반환값과 그 시점의 `size()`는 각각 무엇일까요? 손으로 배열 상태를 따라가며 확인해보세요.
2. `pop()`을 `this.items.shift()`로, `push()`를 `this.items.unshift()`로 바꿔도 LIFO 순서 자체는 똑같이 유지됩니다. 그런데 왜 이 구현은 여전히 나쁜 선택일까요? (힌트: 정답의 순서가 아니라 비용을 보세요.)
3. `peek()`을 `this.items.pop()`으로 잘못 구현했다고 가정해봅시다. `push(10), push(20), peek(), peek(), size()`를 순서대로 실행하면 마지막 `size()`는 원래 구현과 비교해 어떻게 달라질까요?
