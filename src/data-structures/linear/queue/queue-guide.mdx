# Queue — 지우지 않고 손가락만 옮기기

## 한눈에 보는 컨셉

먼저 들어온 것이 먼저 나가는(FIFO) 자료구조예요. 비결은 딱 하나입니다 — 원소를 실제로 배열 앞에서 밀어내는 대신, "지금 꺼낼 위치"를 가리키는 `head` 포인터만 한 칸씩 옮기는 것입니다. 덕분에 enqueue·dequeue·front 모두 amortized $O(1)$에 끝나고, 프린터 대기열이나 BFS처럼 "도착 순서를 지키며 계속 넣고 빼는" 문제에서 표준으로 쓰입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Queue를 떠올리세요.

- 처리 순서가 "먼저 들어온 것부터"(FIFO)여야 한다는 요구가 명시적으로 있다
- 데이터가 계속 들어오고(enqueue) 나가는(dequeue) 스트리밍·버퍼링 상황이다
- 배열 앞에서 원소를 자주 꺼내야 하는데 `shift()`/`unshift()`를 쓰면 성능이 걱정된다
- 그래프·트리를 "레벨 순서"로 순회해야 한다(BFS의 핵심 신호)

이 프로젝트의 문제 제약을 보면 목표 복잡도가 명확해져요. 최대 연산 횟수가 $10^6$, 시간 제한 1초, 메모리 256MB — 이 조건에서 enqueue·dequeue·front는 모두 amortized $O(1)$이어야 합니다. `Array.shift()`는 사양상 배열 앞의 원소를 지우고 나머지를 전부 한 칸씩 당기는 연산이라 이론적으로 원소 개수에 비례하는 비용을 집니다. $10^6$번 반복 호출하면 이론적 최악은 $O(n^2)$까지 벌어질 수 있어요 — 그래서 이 문제도 "`Array.shift()`를 직접 쓰지 말 것"을 제약으로 명시합니다.

```text
naive(Array + shift)   dequeue 이론적 최악 O(n)   n=10^6 반복 시 최악 O(n^2)
head 포인터 방식        dequeue O(1)              배열 압축까지 포함해도 amortized O(1)
연결 리스트 큐           dequeue O(1)              노드마다 할당 필요 — JS에서는 대개 배열보다 느림
```

비슷한 모양의 다른 자료구조와 헷갈릴 수 있어요. 양쪽 끝에서 모두 넣고 빼야 하면 Deque(양방향 큐), 나중에 넣은 것부터 꺼내야 하면 Stack, 도착 순서가 아니라 우선순위 기준으로 꺼내야 하면 우선순위 큐(힙)를 쓰세요. Queue는 오직 "들어온 순서 = 나가는 순서"가 기준일 때만 씁니다.

### 문제 사례와 적용 예시

- **프린터 대기열**: 사무실 공용 프린터는 문서가 도착한 순서대로 출력해야 합니다. 나중에 보낸 사람이 먼저 뽑히면 불공평하죠 — 전형적인 FIFO 요구입니다.
- **BFS(너비 우선 탐색)**: 그래프나 트리를 레벨 순서로 순회할 때, "지금 레벨에서 발견한 이웃들을 다음 레벨로 넘기기 전에 먼저 처리"하는 순서를 큐가 그대로 보장합니다.
- **메시지 큐 / 이벤트 루프**: RabbitMQ, SQS 같은 메시지 브로커나 JS 런타임의 매크로태스크 큐는 모두 "먼저 등록된 작업부터 처리"라는 큐의 계약 위에 서 있습니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드가 정의하는 인터페이스는 다음과 같습니다.

**속성(내부 상태)**

```ts
class Queue<T> {
  private items: T[] = [];   // 저장 배열 (뒤에만 추가)
  private head: number = 0;  // 현재 front를 가리키는 인덱스
}
```

지켜야 할 불변식은 세 가지예요.

1. $0 \le \text{head} \le n$ (단, $n = |\text{items}|$) — head는 배열 범위를 벗어나지 않는다.
2. 논리적 큐의 내용은 항상 $\text{items}[\text{head} .. n-1]$ 구간이고, $\text{size} = n - \text{head}$다.
3. FIFO 순서 — `items` 배열 내 인덱스 오름차순이 곧 enqueue된 순서이고, dequeue는 항상 그 순서대로 빠져나간다.

```text
items:  [ □  □  □  4  5  6  7 ]
          └─ 이미 나간 칸(참조 해제됨) ─┘   ↑
                                          head (= 3) → 현재 front

유효 구간: items[head .. items.length - 1] = [4, 5, 6, 7]
size = items.length(7) - head(3) = 4
```

**액션(연산)**

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `enqueue(item)` | rear(배열 끝)에 아이템 추가 | amortized $O(1)$ |
| `dequeue()` | front(head 위치) 제거 후 반환. 비어있으면 `undefined` | amortized $O(1)$ |
| `front()` | front 조회, 제거 없음. 비어있으면 `undefined` | $O(1)$ |
| `isEmpty()` | 비어있는지 확인 | $O(1)$ |
| `size()` | 현재 원소 수 | $O(1)$ |

핵심 연산 세 가지를 before/after로 자세히 볼게요.

**① enqueue** — 배열 끝에 붙이기만 합니다. head는 건드리지 않아요.

```text
Before: items = [1, 2, 3], head = 0
enqueue(4)
After:  items = [1, 2, 3, 4], head = 0    ← 배열 끝에 추가, head는 그대로
```

**② dequeue** — 배열은 그대로 두고 head만 전진시킵니다.

```text
Before: items = [1, 2, 3], head = 0
dequeue() → 1 반환
After:  items = [1, 2, 3], head = 1       ← 배열은 그대로, head만 한 칸 전진
        유효 구간: items[1..2] = [2, 3]
```

**③ 압축(compact)** — head가 충분히 커지면 앞의 죽은 칸을 잘라내 배열을 되돌립니다.

```text
Before: items 길이 1,000,000, head = 999,998 (유효 원소는 단 2개인데 배열은 100만 칸)
compactIfNeeded() 조건 충족 (head > 1000 && head * 2 > items.length)
After:  items = [999998, 999999] (길이 2), head = 0
```

### 왜 모순 없이 작동하는가

**불변식이 각 연산에서 보존되는 이유**를 하나씩 봅니다.

- `enqueue`는 배열 끝에 `push`만 합니다. `head`를 건드리지 않으므로 $\text{head} \le n$은 그대로 유지되고, $n$만 늘어나 size가 정확히 1 증가합니다.
- `dequeue`는 `isEmpty()`(= $\text{head} \ge n$)를 먼저 확인하고, 아니라면 `items[head]`를 반환한 뒤 `head`를 1 증가시킵니다. 증가 전에 $\text{head} < n$이었으므로 증가 후에도 $\text{head} \le n$이 유지됩니다 — 불변식 1이 깨지지 않아요.
- `front`는 아무것도 바꾸지 않으므로 불변식이 자동으로 유지됩니다.
- FIFO 순서(불변식 3)는 `push`가 항상 배열의 물리적 끝에 추가하고, `head`가 항상 물리적으로 가장 앞선(=가장 먼저 들어온) 유효 원소를 가리키기 때문에 성립합니다. 빈 큐에서 시작해 어떤 enqueue/dequeue 시퀀스를 거쳐도 이 관계는 귀납적으로 보존됩니다.

잠깐, 확인 하나만 해볼까요? `head`가 3이고 `items.length`가 5일 때 `size()`는 얼마일까요? — $5 - 3 = 2$입니다. `items[3]`과 `items[4]`가 유효 원소예요.

**여기서 헷갈리기 쉬운 포인트**가 두 가지 있습니다.

- **`size() === 0`이라고 해서 내부 배열도 비어있는 건 아닙니다.** `head`가 `items.length`와 같아지면 논리적으로는 빈 큐지만, 물리적 배열은 지금까지 들어온 원소를 전부 쥐고 있을 수 있어요. 압축을 하지 않으면 이 배열은 계속 자라기만 합니다(뒤에서 실측 수치로 확인합니다).
- **`isEmpty()`를 `items.length === 0`으로 판단하면 틀립니다.** dequeue를 거친 큐는 `items.length`가 0이 아니어도(과거 원소가 남아있어도) 논리적으로 비어있을 수 있어요. 반드시 `head >= items.length` 관계식으로 판단해야 합니다.

엣지 케이스를 점검해 둡니다.

```text
빈 큐에서 dequeue()/front()        → undefined (head === items.length === 0)
enqueue 후 즉시 front()            → 처음 enqueue한 값 (FIFO 첫 원소)
1개 남은 상태에서 dequeue()        → 이후 isEmpty() === true
head가 items.length에 근접(거의 다 뺀 상태) → 압축 조건 충족 시 배열이 다시 작아짐
```

## 아이디어를 코드로 옮기기

**가장 중요한 부분은 "배열에서 원소를 실제로 지우지 않는다"는 결정입니다.** 이 결정 하나가 dequeue를 $O(n)$에서 $O(1)$로 바꿉니다. 이 결정에 이르는 과정을 원형 → 개선 → 최종 세 단계로 밟아봅니다.

**0단계 — 원형(naive)**: 배열의 `push`/`shift`를 그대로 씁니다.

```ts
class NaiveQueue<T> {
  private items: T[] = [];

  enqueue(item: T): void {
    this.items.push(item);
  }

  dequeue(): T | undefined {
    return this.items.shift(); // 앞의 원소를 지우고 나머지를 전부 한 칸씩 당긴다
  }

  front(): T | undefined {
    return this.items[0];
  }

  isEmpty(): boolean {
    return this.items.length === 0;
  }

  size(): number {
    return this.items.length;
  }
}
```

**왜 다음 단계로 가는가**: `shift()`는 사양상 원소 개수에 비례하는 비용을 집니다. 실측해 보면(이 프로젝트가 쓰는 Bun/JavaScriptCore 기준, $n = 10^6$회 연속 dequeue), naive는 17.8ms, 뒤에서 만들 head 포인터 방식은 4.1ms로 이미 4배 넘게 벌어집니다. Bun의 JavaScriptCore가 배열 시작 위치를 내부적으로 조정해 주는 최적화 덕분에 이론상 최악($O(n^2)$)만큼 극단적이진 않지만, 이런 최적화는 엔진·버전마다 다르고 보장되지 않습니다. 문제 제약도 `shift()` 직접 사용을 명시적으로 금지하고 있으니, 최적화에 기대지 않는 편이 안전합니다.

**1단계 — 개선(head 포인터)**: 지우는 대신 "다음에 꺼낼 위치"만 기억합니다.

```ts
class HeadPointerQueue<T> {
  private items: T[] = [];
  private head = 0;

  enqueue(item: T): void {
    this.items.push(item);
  }

  dequeue(): T | undefined {
    if (this.isEmpty()) return undefined;
    const x = this.items[this.head];
    this.head++;
    return x;
  }

  front(): T | undefined {
    return this.isEmpty() ? undefined : this.items[this.head];
  }

  isEmpty(): boolean {
    return this.head >= this.items.length;
  }

  size(): number {
    return this.items.length - this.head;
  }
}
```

**왜 다음 단계로 가는가**: dequeue는 확실히 $O(1)$이 됐지만, `items` 배열이 절대 줄어들지 않는다는 함정이 남아 있습니다. 실측으로 확인해 보면, enqueue 1회 + dequeue 1회를 100만 번 반복한 뒤 `size()`는 정확히 0인데 내부 배열의 실제 길이(`items.length`)는 그대로 1,000,000입니다. 요청이 끊임없이 들어오고 나가는 장기 실행 서버(프린터 서버 등)라면 이 배열이 영원히 자라기만 해 결국 256MB 메모리 제한을 위협합니다. 이 함정은 바로 다음 2단계(압축 로직)에서 해결합니다.

**2단계 — 최종(head 포인터 + 압축)**: `head`가 일정 이상 커지면 앞쪽 죽은 칸을 잘라냅니다.

```ts
class Queue<T> {
  private items: T[] = [];
  private head = 0;

  enqueue(item: T): void {
    this.items.push(item);
  }

  dequeue(): T | undefined {
    if (this.isEmpty()) return undefined;
    const x = this.items[this.head];
    this.items[this.head] = undefined as unknown as T; // 참조 해제 (GC 도움)
    this.head++;
    this.compactIfNeeded();
    return x;
  }

  front(): T | undefined {
    return this.isEmpty() ? undefined : this.items[this.head];
  }

  isEmpty(): boolean {
    return this.head >= this.items.length;
  }

  size(): number {
    return this.items.length - this.head;
  }

  private compactIfNeeded(): void {
    // head가 1000을 넘고 배열 절반 이상을 차지하면 압축한다
    if (this.head > 1000 && this.head * 2 > this.items.length) {
      this.items = this.items.slice(this.head);
      this.head = 0;
    }
  }
}
```

- **가장 실수가 잦은 부분은 `compactIfNeeded`의 호출 위치**입니다. `head++` **다음에** 호출해야 압축 여부 판단이 최신 `head` 값을 반영합니다. 먼저 호출하면 한 원소 늦게 판단해 압축 시점이 항상 하나씩 밀립니다.
- 압축 조건에서 `head > 1000`이라는 하한을 두는 이유는, `head`가 작을 때마다 매번 `slice`(그 자체로 $O(n)$)를 하면 오히려 손해이기 때문입니다. 충분히 죽은 칸이 쌓였을 때만 압축해야 압축 비용이 전체 연산에 걸쳐 상각(amortize)되어 $O(1)$을 유지합니다.
- `items[this.head] = undefined`로 참조를 끊는 줄은 선택 사항이지만, 객체를 담는 큐라면 압축 전까지 죽은 칸이 그 객체를 계속 붙잡아 GC를 막는 걸 방지합니다.

> 지운 게 아니라, 안 본다고 치는 것뿐이다 — 그리고 안 본다고 친 칸이 너무 쌓이면 그제서야 진짜로 자른다.

정리하면, Queue의 설계 결정은 하나로 요약됩니다. **원소를 물리적으로 지우지 않고, "다음에 꺼낼 위치"만 `head`로 기억한다.** 이 덕분에 enqueue는 배열 끝에 붙이는 $O(1)$, dequeue는 `head`를 한 칸 옮기는 $O(1)$로 끝나고, 배열이 무한정 자라는 부작용은 `head`가 충분히 쌓였을 때만 압축하는 방식으로 상각(amortize)해 해결합니다. $n = 10^6$ 규모에서 head 포인터 방식이 naive(`shift`) 대비 실측 4배 이상 빠르고, 압축까지 더하면 메모리도 목표(256MB) 안에서 안정적으로 유지된다는 것을 확인했습니다 — 애초에 이 문제가 요구한 amortized $O(1)$ 목표를 그대로 달성한 것입니다.
