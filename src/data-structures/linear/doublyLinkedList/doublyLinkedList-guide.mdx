# DoublyLinkedList — 포인터 두 개면 어디서든 O(1)

## 한눈에 보는 컨셉

각 노드가 다음 노드뿐 아니라 이전 노드까지 직접 가리키는 연결 리스트예요. 비결은 딱 하나입니다 — **이미 손에 쥔 노드 참조가 있으면, 그 노드를 지우거나 그 옆에 무언가를 끼워 넣는 데 리스트를 순회할 필요가 없다**는 것이죠. 그 결과 배열에서는 O(n)이 걸리던 임의 위치 삽입·삭제가 O(1)로 떨어집니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 이중 연결 리스트를 떠올리세요.

- "현재 위치/커서/재생 중인 항목"처럼 **이미 알고 있는 노드**를 기준으로 삽입·삭제를 반복해야 한다
- 앞으로도 뒤로도 자유롭게 **양방향 이동**이 필요하다
- 삭제가 "값을 검색해서 지우는" 게 아니라 "이미 손에 쥔 노드를 지우는" 형태다

배열과 단일 연결 리스트(singly linked list) 대비 비용을 비교하면 이렇습니다.

```text
연산                  배열          단일 연결 리스트         이중 연결 리스트
임의 위치 삽입/삭제     O(n) 이동     O(n) 이전 노드 재탐색     O(1) (노드 참조 보유 시)
이전 노드로 이동        O(1) 인덱스   O(n) 처음부터 재탐색      O(1) prev 포인터
```

단일 연결 리스트는 `next`만 있어서, 노드 `B`를 지우려면 `B` 바로 앞의 노드 `A`를 알아야 하는데 `A`를 찾으려면 head부터 다시 순회해야 합니다(O(n)). 이중 연결 리스트는 `B.prev`로 `A`에 즉시 접근하므로 이 탐색이 통째로 사라집니다. 반대로 **순방향 순회만 필요하고 메모리를 아끼고 싶다면** 포인터를 하나 덜 쓰는 단일 연결 리스트로 충분해요 — `prev` 포인터 하나가 그저 아까운 상황이라면 이중 연결 리스트를 쓸 이유가 없습니다.

### 문제 사례와 적용 예시

- **음악 플레이리스트**: 재생 중인 곡에서 "이전 곡"·"다음 곡"으로 즉시 이동하고, 현재 곡을 그 자리에서 바로 삭제한다.
- **LRU 캐시의 사용 순서 리스트**: 방금 접근한 노드를 O(1)에 리스트 맨 앞으로 옮긴다(레퍼런스만 있으면 위치 이동이 삭제+삽입 두 번의 O(1) 연산으로 끝난다).
- **브라우저 히스토리 / 실행취소(undo-redo)**: 현재 지점에서 앞뒤로 이동하다가, 새 동작이 들어오면 현재 지점 뒤를 잘라내고 이어 붙인다.
- **코딩 테스트 맥락**: "노드 참조를 인자로 받아 그 노드를 O(1)에 삭제하라" 또는 "그 노드 바로 뒤에 새 값을 O(1)에 삽입하라" 유형의 문제.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**

```ts
class ListNode<T> {
  value: T;
  prev: ListNode<T> | null = null;
  next: ListNode<T> | null = null;
}

class DoublyLinkedList<T> {
  private head: ListNode<T> | null = null;
  private tail: ListNode<T> | null = null;
  private _size = 0;
}
```

구조 전체를 그리면 이렇습니다.

```text
head → [N1] ⇄ [N2] ⇄ ... ⇄ [Nk] ← tail
      prev=null              next=null
```

지켜야 할 불변식은 다섯 가지예요.

1. 모든 노드 $n$에 대해 $n.\text{next} \neq \text{null} \implies n.\text{next}.\text{prev} = n$
2. 모든 노드 $n$에 대해 $n.\text{prev} \neq \text{null} \implies n.\text{prev}.\text{next} = n$
3. `head === null` 이면 리스트가 비어 있고, 그때 그리고 그때만 `tail === null`이다
4. `head.prev === null`, `tail.next === null` — 양 끝은 경계표시로 `null`을 갖는다
5. `_size`는 리스트에 실제로 연결된 노드 개수와 항상 같다

**액션(연산)** — 이 가이드가 정의하는 인터페이스는 다음과 같습니다.

| 액션 | 시그니처 | 하는 일 | 비용 |
|------|---------|---------|------|
| `prepend` | `(value: T) => ListNode<T>` | 맨 앞에 노드 추가, 새 노드 반환 | O(1) |
| `append` | `(value: T) => ListNode<T>` | 맨 뒤에 노드 추가, 새 노드 반환 | O(1) |
| `insertAfter` | `(node: ListNode<T>, value: T) => ListNode<T>` | `node` 바로 뒤에 삽입, 새 노드 반환 | O(1) |
| `remove` | `(node: ListNode<T>) => void` | `node`를 리스트에서 제거 | O(1) |
| `toArray` | `() => T[]` | head→tail 순서로 전체를 배열화 | O(n) |
| `size` | `() => number` | 현재 노드 개수 반환 | O(1) |

핵심 연산 두 개는 Before/After로 자세히 볼게요. 리스트가 `A ⇄ B ⇄ C` 상태라고 합시다.

**① insertAfter(A, 'D')** — A와 B 사이에 D를 끼워 넣습니다.

```text
Before: head → [A] ⇄ [B] ⇄ [C] ← tail
                (A.next=B, B.prev=A)

insertAfter(A, 'D'):
  D.prev = A          D.next = A.next(=B)
  B.prev = D          A.next = D

After:  head → [A] ⇄ [D] ⇄ [B] ⇄ [C] ← tail
```

**② remove(B)** — 위 상태에서 이어서 B를 지웁니다(현재 리스트는 `A ⇄ D ⇄ B ⇄ C`).

```text
Before: head → [A] ⇄ [D] ⇄ [B] ⇄ [C] ← tail

remove(B):
  D.next = B.next(=C)          C.prev = D
  B.prev = B.next = null       (B를 완전히 고립)

After:  head → [A] ⇄ [D] ⇄ [C] ← tail
```

### 왜 모순 없이 작동하는가

**귀납 논증**: 빈 리스트는 노드가 없으니 불변식 1·2가 공허하게 참이고, 불변식 3(`head === tail === null`)도 자명하게 성립합니다. 이제 각 연산이 "불변식을 만족하는 리스트"를 받아 "불변식을 만족하는 리스트"를 돌려준다는 것만 보이면 됩니다.

- `prepend`/`append`: 새 노드의 `prev`/`next` 중 리스트 안쪽을 향하는 포인터와, 기존 경계 노드의 반대편 포인터를 **항상 쌍으로** 설정합니다(`node.next = head`와 `head.prev = node`가 함께 실행). 빈 리스트일 때는 `head = tail = node`로 새 경계를 세우므로 불변식 3·4가 그대로 유지됩니다.
- `insertAfter`: `node.prev = refNode`, `refNode.next = node` 한 쌍과 `node.next = refNode.next`, `refNode.next.prev = node`(있다면) 한 쌍, 총 두 쌍을 설정합니다. `refNode`가 기존 tail이었다면 `tail = node`로 경계를 다시 세워 불변식 4를 지킵니다.
- `remove`: `node.prev`가 있으면 `node.prev.next = node.next`로 왼쪽 이웃을 이어 주고, 없으면(= node가 head) `head = node.next`로 경계 자체를 옮깁니다. 오른쪽도 대칭으로 처리합니다. 양쪽 다 처리한 뒤에야 `node`를 `prev = next = null`로 고립시키므로, 고립 시점에 이미 나머지 리스트는 완결된 상태입니다.

포인터 수정이 항상 "양쪽에서 서로를 가리키게" 쌍으로 이루어진다는 점이 불변식 1·2가 절대 깨지지 않는 이유입니다.

**여기서 헷갈리기 쉬운 포인트는 remove에서 head/tail 갱신을 "선택적인 예외 처리"로 여기는 것입니다.** `node.prev !== null`이 거짓이라는 것은 예외 상황이 아니라 "node가 지금 head다"라는 정상적인 케이스예요. 이 분기를 빼먹으면 리스트 안쪽 연결은 멀쩡해 보여도 head/tail이라는 진입점 자체가 낡은 값을 계속 가리키게 됩니다(구체적인 사고 사례는 아래 "아이디어를 코드로 옮기기"에서 실측으로 보여드릴게요).

잠깐, 확인 하나만 해 볼까요? 리스트에 노드가 A 하나뿐일 때 `remove(A)`를 호출하면 head와 tail은 각각 어떻게 될까요? — A는 `prev === null`이면서 동시에 `next === null`이므로, `head = A.next = null`이고 `tail = A.prev = null`이 됩니다. 즉 두 경계 모두 한 번에 비워지죠.

엣지 케이스를 점검해 봅시다.

```text
단일 노드 하나를 remove         → head = tail = null, size = 0
head 노드를 remove              → head = node.next로 갱신, 새 head.prev = null 유지
tail 노드를 remove              → tail = node.prev로 갱신, 새 tail.next = null 유지
insertAfter(tail 노드, value)   → 새 노드가 tail이 되도록 tail 갱신 필요
빈 리스트에서 toArray/size      → [] / 0
```

## 아이디어를 코드로 옮기기

앞서 정의한 인터페이스 그대로 TypeScript로 옮기면 다음과 같습니다.

```ts
class ListNode<T> {
  value: T;
  prev: ListNode<T> | null = null;
  next: ListNode<T> | null = null;

  constructor(value: T) {
    this.value = value;
  }
}

class DoublyLinkedList<T> {
  private head: ListNode<T> | null = null;
  private tail: ListNode<T> | null = null;
  private _size = 0;

  prepend(value: T): ListNode<T> {
    const node = new ListNode(value);
    if (this.head === null) {
      this.head = this.tail = node;
    } else {
      node.next = this.head;
      this.head.prev = node;
      this.head = node;
    }
    this._size++;
    return node;
  }

  append(value: T): ListNode<T> {
    const node = new ListNode(value);
    if (this.tail === null) {
      this.head = this.tail = node;
    } else {
      this.tail.next = node;
      node.prev = this.tail;
      this.tail = node;
    }
    this._size++;
    return node;
  }

  insertAfter(refNode: ListNode<T>, value: T): ListNode<T> {
    const node = new ListNode(value);
    node.prev = refNode;
    node.next = refNode.next;
    if (refNode.next !== null) {
      refNode.next.prev = node;
    }
    refNode.next = node;
    if (refNode === this.tail) {
      this.tail = node;
    }
    this._size++;
    return node;
  }

  remove(node: ListNode<T>): void {
    if (node.prev !== null) {
      node.prev.next = node.next;
    } else {
      this.head = node.next;
    }
    if (node.next !== null) {
      node.next.prev = node.prev;
    } else {
      this.tail = node.prev;
    }
    node.prev = null;
    node.next = null;
    this._size--;
  }

  toArray(): T[] {
    const result: T[] = [];
    let cur = this.head;
    while (cur !== null) {
      result.push(cur.value);
      cur = cur.next;
    }
    return result;
  }

  size(): number {
    return this._size;
  }
}
```

가장 중요한 부분은 `remove`의 네 줄입니다. `node.prev`의 유무로 "왼쪽 이웃을 이을지, head를 옮길지"를 결정하고, `node.next`의 유무로 "오른쪽 이웃을 이을지, tail을 옮길지"를 결정합니다. 이 두 판단은 서로 독립적이라 각각 따로 검사해야 해요(둘 다 참일 수도, 하나만 참일 수도, 둘 다 거짓일 수도 있습니다 — 마지막 경우가 바로 "노드 하나짜리 리스트"입니다).

구현에서 놓치기 쉬운 지점들:

- **`insertAfter`의 순서가 생명인 두 줄.** `refNode.next.prev = node`는 반드시 `refNode.next = node`보다 **먼저** 실행해야 합니다. 먼저 `refNode.next`를 덮어써 버리면 원래의 다음 노드(B)를 가리키는 참조 자체를 잃어버려서 `B.prev`를 더 이상 고칠 수 없어요.
- **`insertAfter`에서 tail 갱신 조건(`refNode === this.tail`)을 빼먹기 쉽습니다.** refNode가 기존 tail이었다면 새로 삽입된 노드가 새 tail이 돼야 하는데, 이걸 빼먹으면 tail이 리스트의 실제 끝이 아닌 중간 노드를 계속 가리키게 됩니다.
- **`remove`의 두 `else` 분기(head 갱신, tail 갱신)는 "예외 처리"가 아니라 정상 케이스입니다.** 둘 중 하나라도 빼먹으면 어떻게 되는지, 바로 아래에서 구체적인 수치로 보여드릴게요.

> 기억법: "지운 자리의 양쪽 이웃에게 서로를 알려주고, 잘린 끝이 경계였다면 경계 표지판(head/tail)까지 새로 세운다."

**함정 — remove에서 tail 갱신(else 분기)을 빼먹으면 실제로 무슨 일이 벌어지는가.** `append('A')`, `append('B')`를 실행하면 `tail = B`입니다. 여기서 `remove(B)`를 호출하는데 "B.next가 null이면 tail = B.prev로 갱신" 분기를 빼먹었다고 해 봅시다. `B.prev.next(=A.next) = B.next(=null)`은 정상 실행되어 `A.next = null`이 되므로 `toArray()`는 여전히 올바르게 `["A"]`를 돌려줍니다 — **여기서는 아직 버그가 안 보입니다.** 문제는 그다음 `append('C')`입니다. 코드는 `if (this.tail === null)`을 검사하는데, tail은 여전히(갱신 안 됐으니) 고립된 B를 가리키고 있어서 `null`이 아닙니다. 그래서 `else` 분기로 들어가 `tail.next = C`, 즉 **이미 리스트에서 떨어져 나간 B에 C를 붙이고** `tail = C`로 갱신합니다. `_size`는 정상적으로 2로 증가하지만, head부터 순회하는 `toArray()`는 `A`에서 멈춰 버려 `["A"]`(길이 1)만 돌려줍니다. **`size()`는 2인데 `toArray()`는 원소 1개** — 이 불일치가 tail 갱신 누락의 증거입니다(직접 스크래치로 실행해 확인한 수치입니다).

정리하면, 이중 연결 리스트는 "포인터 두 개를 항상 쌍으로 갱신한다"는 단 하나의 규율로 삽입·삭제를 O(1)에 묶어 둡니다. `prev`가 있다는 것 자체가 "이전 노드를 찾는 순회"를 완전히 없애 주고, head/tail을 경계 케이스가 아니라 "prev 또는 next가 null인 정상 케이스"로 다루면 노드 하나짜리 리스트든 빈 리스트든 같은 코드 경로로 처리됩니다. 대신 임의 인덱스 접근(random access)은 여전히 O(n)이라는 점은 배열 대비 트레이드오프로 남습니다.

## 스스로 점검하기

1. 빈 리스트에서 `append('A')` → `append('B')` → `prepend('Z')` → `remove(A)` 순서로 연산을 실행했을 때, 최종 `head`·`tail`은 각각 어떤 노드이고 `toArray()`의 결과는 무엇일까요? 손으로 포인터를 따라가며 확인해 보세요.
2. `remove(node)`에서 head/tail을 갱신하는 `else` 분기 두 개를 "어차피 마지막에나 필요한 예외 처리"라고 생각해서 나중에 추가하기로 미뤘다면, 위 "함정" 사례처럼 `size()`와 `toArray().length`가 어긋나는 정확히 어떤 상황에서 처음 드러날까요?
3. `insertAfter(refNode, value)`를 구현할 때 `refNode.next.prev = node`와 `refNode.next = node` 두 줄의 순서를 바꾸면, 원래 `refNode` 뒤에 있던 노드의 `prev` 포인터에는 어떤 값이 남게 될까요?
