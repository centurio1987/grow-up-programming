# 덱 — 세 가지 구현과 선택 기준

## 파트 1 — 연산에서 저장 방식으로

### 전체 컨셉

덱(deque)은 **맨 앞과 맨 뒤에서 원소를 넣거나 꺼낼 수 있는 자료구조**입니다. 뒤에 1과 2를 넣고 앞에 0을 넣으면 `[0, 1, 2]`가 됩니다. 여기서 앞을 꺼내면 0, 뒤를 꺼내면 2가 나옵니다. 어느 쪽을 사용할지는 호출할 때마다 정할 수 있습니다.

```text
뒤에 1 삽입     [1]
뒤에 2 삽입     [1, 2]
앞에 0 삽입     [0, 1, 2]
앞에서 꺼냄     [1, 2]       반환값 0
뒤에서 꺼냄     [1]          반환값 2
```

이 순서를 저장하는 방법은 하나가 아닙니다. **두 스택**은 앞쪽과 뒤쪽 원소를 나누어 보관하고, **원형 버퍼**는 배열의 시작 위치를 바꾸며, **이중 연결 리스트**는 노드 사이의 연결을 바꿉니다. 세 방법 모두 양 끝의 원소를 찾기 위해 전체를 순회할 필요가 없습니다.

| 구현 | 양 끝을 찾는 방법 | 원소가 많아질 때 생기는 작업 |
| --- | --- | --- |
| 두 스택 | 앞쪽 스택과 뒤쪽 스택의 꼭대기 | 한쪽이 비면 원소를 절반씩 재분배 |
| 원형 버퍼 | 첫 원소의 인덱스와 원소 수로 계산 | 배열이 가득 차면 더 큰 배열로 복사 |
| 이중 연결 리스트 | 첫 노드와 마지막 노드를 직접 참조 | 삽입할 때 새 노드 생성 |

덱의 동작과 저장 방식을 구분하면 세 구현을 비교하기 쉽습니다. 사용자에게 보이는 순서는 같고, 그 순서를 유지하기 위해 수행하는 작업이 다릅니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

배열의 인덱스로 값을 읽는 방법, 스택에서 마지막에 넣은 값을 먼저 꺼내는 규칙, 객체가 다른 객체를 참조하는 방식을 알고 있으면 됩니다. 필요하면 스택 가이드(`linear/stack`)를 먼저 읽어 보세요. 원형 인덱스와 양방향 연결은 여기서 작은 예로 설명합니다.

이 글에서 사용할 연산은 여섯 개입니다. 아래 표는 [이 프로젝트의 덱 명세](./deque.ts)를 요약한 것입니다. 빈 덱의 조회와 삭제는 `null`을 반환합니다.

<!--contract-summary-->

| 연산 | 의미 | 상한 | 한정자 |
| --- | --- | --- | --- |
| `pushFront(item)` | 앞에 원소 삽입 | O(1) | 상각 |
| `pushBack(item)` | 뒤에 원소 삽입 | O(1) | 상각 |
| `popFront()` | 앞 원소를 제거하고 반환, 비어 있으면 null | O(1) | 상각 |
| `popBack()` | 뒤 원소를 제거하고 반환, 비어 있으면 null | O(1) | 상각 |
| `peekFront()` | 앞 원소를 제거하지 않고 반환, 비어 있으면 null | O(1) | 최악 |
| `peekBack()` | 뒤 원소를 제거하지 않고 반환, 비어 있으면 null | O(1) | 최악 |

**최악 시간**이 O(1)이면 한 번의 호출에 필요한 작업량이 원소 수와 무관하게 제한됩니다. **상각 시간**이 O(1)이면 빈 상태에서 시작한 m번의 연산에 총 O(m)의 작업이 필요합니다. 어떤 한 번은 오래 걸려도 되며, 입력이 무작위라는 가정은 필요하지 않습니다.

```ts
const d = new Deque<number>();
d.pushBack(1);
d.pushBack(2);
d.pushFront(0);
d.peekFront(); // 0 — 아직 [0, 1, 2]
d.popBack();   // 2 — 이제 [0, 1]
d.popFront();  // 0 — 이제 [1]
d.peekBack();  // 1
```

원소 값으로 비어 있는지 판단하지는 않습니다. `0`, `false`, `undefined`도 저장할 수 있기 때문입니다. 저장한 값이 `null`이면 빈 덱의 반환값과 구분되지 않는다는 제약은 있습니다. 세 구현 모두 이 반환 규칙을 따릅니다.

### 설계 상세 — 앞에 넣을 때 무엇을 바꿔야 할까

배열 하나를 그대로 사용하면 뒤쪽 삽입과 삭제는 `push`와 `pop`으로 처리할 수 있습니다. 앞쪽은 `unshift`와 `shift`로 처리할 수 있지만, 원소를 연속된 인덱스에 유지하는 배열 모델에서는 기존 원소를 옮겨야 합니다.

```text
기존 배열       [1, 2, 3]
앞에 0을 넣기   3을 뒤로 → 2를 뒤로 → 1을 뒤로 → 0 저장
결과            [0, 1, 2, 3]

원소 이동 3회 + 새 값 저장 1회
```

빈 배열에 원소 네 개를 계속 앞에 넣으면 기존 원소를 `0 + 1 + 2 + 3 = 6`번 옮깁니다. n개라면 이동량은 `n(n - 1) / 2`이므로 전체가 O(n²)입니다. 실제 JavaScript 엔진이 일부 경우를 최적화할 수 있어도, 그것만으로 원하는 비용을 보장할 수는 없습니다.

그런데 덱을 사용하는 사람에게 중요한 것은 **어떤 값이 앞이고 뒤인가**입니다. 맨 앞 원소가 반드시 배열의 0번 칸에 있어야 하는 것은 아닙니다. 이 조건을 바꾸면 다음 세 방법을 생각할 수 있습니다.

```text
두 스택          앞에 넣을 값도 배열의 마지막 칸에 저장한다.
원형 버퍼        첫 원소의 인덱스를 따로 기억한다.
이중 연결 리스트 원소를 옮기는 대신 이웃 노드의 참조를 바꾼다.
```

예를 들어 덱 `[1, 2, 3, 4]`를 두 배열 `[2, 1]`, `[3, 4]`에 나누어 보관해도 됩니다. 앞 배열만 거꾸로 읽으면 원래 순서가 나옵니다. 원형 버퍼에서는 `[2, 3, 4, 1]`을 저장하고 3번 인덱스부터 읽어도 같은 순서가 됩니다. 저장 규칙을 정하고 연산 뒤에도 그 규칙을 유지하면 됩니다.

### 수행으로 알아보는 자료구조 — 저장 상태를 바꾸며 구현하기

세 구현에서 공통으로 확인할 것은 삽입한 순서와 반환값입니다. 먼저 `[1, 2, 3, 4, 5, 6]`을 저장한 뒤 앞뒤를 번갈아 삭제해 보겠습니다. 원형 버퍼에서는 배열 끝을 넘는 인덱스와 용량 확장을, 연결 리스트에서는 마지막 원소 삭제를 추가로 살펴봅니다.

```text
공통 확인: [1,2,3,4,5,6] → 앞 1 → 뒤 6 → 앞 2 → 뒤 5 → 앞 3 → 뒤 4
추가 확인: 빈 상태 · 원소 한 개 · 양쪽 삽입 · 조회 후 상태 유지
```

세 구현을 하나씩 만듭니다. 소절 번호의 앞자리가 구현이고 뒷자리가 그 구현 안의 순서입니다. 실수하기 쉬운 자리를 짚는 「짚고 가기」 소절은 그 구현의 소절 사이에 둡니다.

| 구현 | 소절 | 그 구현에서 따로 볼 것 |
| --- | --- | --- |
| 두 스택 | 1-1 · 1-2 | 한쪽이 비었을 때 원소를 나누는 방법 |
| 원형 버퍼 | 2-1 · 2-2 · 전체 코드 | 배열 끝을 넘는 인덱스와 용량 확장 |
| 이중 연결 리스트 | 3-1 | 마지막 원소를 지울 때 양 끝 처리 |

#### 1-1. 두 스택 — 앞쪽 원소는 역순으로 저장한다

배열로 만든 두 스택을 `front`와 `back`이라고 하겠습니다. 배열의 마지막 원소가 스택의 꼭대기입니다. `front`에는 덱의 앞쪽을 역순으로, `back`에는 뒤쪽을 정순으로 보관합니다.

```text
덱의 순서     [1, 2, 3, 4, 5, 6]
front         [3, 2, 1]   꼭대기 1 = 덱의 맨 앞
back          [4, 5, 6]   꼭대기 6 = 덱의 맨 뒤

읽는 순서     front를 거꾸로 읽고 → back을 그대로 읽는다.
```

이 상태에서 `pushFront(0)`은 `front.push(0)`입니다. 앞 배열이 `[3, 2, 1, 0]`이 되므로 거꾸로 읽으면 0이 맨 앞에 옵니다. `pushBack(7)`은 `back.push(7)`입니다. `popFront()`와 `popBack()`도 해당 스택에 원소가 있으면 그 스택의 `pop()`으로 처리할 수 있습니다.

#### 짚고 가기 — 두 스택에서 한쪽이 비었다고 전부 옮기면 생기는 문제

뒤로만 여섯 개를 넣으면 `front`는 비어 있고 `back`은 `[1, 2, 3, 4, 5, 6]`입니다. 이때 앞에서 삭제하려면 저장 상태를 바꿔야 합니다. 반대쪽 스택의 원소를 전부 옮기는 방법은 큐에서 사용하지만, 덱에서는 다음 호출이 어느 쪽일지 모릅니다.

```text
전부 옮기는 방법으로 앞뒤를 번갈아 삭제:
앞 삭제: 6개를 front로 이동 → 1 반환
뒤 삭제: 5개를 back으로 이동 → 6 반환
앞 삭제: 4개를 front로 이동 → 2 반환
...
이동 횟수: 6 + 5 + 4 + 3 + 2 + 1 = 21
```

원소가 n개면 이 이동량은 O(n²)이 됩니다. 원인은 두 스택 자체가 아니라 **반대쪽을 다시 비우는 재분배 방식**입니다. 두 스택에 절반씩 남기면 바로 다음 호출이 반대쪽 삭제여도 재분배할 필요가 없습니다.

#### 1-2. 두 스택 — 양쪽에 절반씩 남긴다

한쪽이 비었고 원소가 둘 이상이면 덱의 순서를 임시 배열로 복원합니다. 앞쪽 절반을 뒤집어 `front`에, 나머지를 `back`에 넣습니다. 여섯 개라면 `[3, 2, 1]`과 `[4, 5, 6]`이 됩니다. 홀수 개라면 앞쪽에 한 개를 더 둡니다.

<!--proof:stack-trace-->

```text
뒤에 1~6 삽입: front=[], back=[1,2,3,4,5,6]
popFront → 1: front=[3,2], back=[4,5,6]
popBack → 6: front=[3,2], back=[4,5]
popFront → 2: front=[3], back=[4,5]
popBack → 5: front=[3], back=[4]
popFront → 3: front=[], back=[4]
popBack → 4: front=[], back=[]
```

첫 삭제에서만 재분배했습니다. 마지막 한 개는 어느 스택에 있든 직접 꺼내면 됩니다. 이 예외가 없으면 한 개를 나눈 결과에서 삭제할 쪽이 여전히 비어 있을 수 있습니다.

조회는 원소를 옮기지 않아도 됩니다. `front`가 비어 있으면 맨 앞 값은 `back[0]`이고, `back`이 비어 있으면 맨 뒤 값은 `front[0]`입니다. 여기서는 스택을 배열로 구현했기 때문에 바닥에 해당하는 0번 인덱스도 읽을 수 있습니다.

```text
front=[3,2,1], back=[] → 앞 값 1, 뒤 값 3
front=[], back=[1,2,3] → 앞 값 1, 뒤 값 3
```

꼭대기 접근만 제공하는 스택 객체 두 개로 구현한다면 바닥을 직접 조회할 수 없습니다. 그 경우 양 끝 값을 별도로 유지하거나 재분배 시점을 조절해야 합니다. 아래 구현은 배열 접근과 임시 배열을 사용하는 두 스택 방식입니다.

```ts
export class StackDeque<T> {
  private front: T[] = [];
  private back: T[] = [];

  private size(): number { return this.front.length + this.back.length; }
  private isEmpty(): boolean { return this.size() === 0; }
  pushFront(item: T): void { this.front.push(item); }
  pushBack(item: T): void { this.back.push(item); }

  peekFront(): T | null {
    if (this.isEmpty()) return null;
    return this.front.length > 0
      ? this.front[this.front.length - 1] as T
      : this.back[0] as T;
  }

  peekBack(): T | null {
    if (this.isEmpty()) return null;
    return this.back.length > 0
      ? this.back[this.back.length - 1] as T
      : this.front[0] as T;
  }

  popFront(): T | null {
    if (this.isEmpty()) return null;
    if (this.front.length === 0) {
      if (this.back.length === 1) return this.back.pop() as T;
      this.rebalance();
    }
    return this.front.pop() as T;
  }

  popBack(): T | null {
    if (this.isEmpty()) return null;
    if (this.back.length === 0) {
      if (this.front.length === 1) return this.front.pop() as T;
      this.rebalance();
    }
    return this.back.pop() as T;
  }

  private rebalance(): void {
    // 먼저 덱의 논리적인 순서를 복원한다.
    const items = this.front.slice().reverse().concat(this.back);
    const middle = Math.ceil(items.length / 2);
    this.front = items.slice(0, middle).reverse();
    this.back = items.slice(middle);
  }
}
```

`rebalance()`에서 복원한 원소 순서를 기준으로 나누는 것이 중요합니다. 두 배열의 길이만 절반으로 맞추고 순서를 잘못 뒤집으면 삽입은 맞아 보여도 이후 반환값이 달라집니다. 여러 임시 배열을 만들지만 복사량은 원소 수에 비례합니다.

#### 2-1. 원형 버퍼 — 첫 원소의 위치를 기억한다

이번에는 배열 하나를 사용하되, 첫 원소가 저장된 인덱스를 `head`로 기억합니다. 배열 길이를 C, 저장한 원소 수를 `count`라고 하겠습니다. `·`는 사용하지 않는 칸입니다.

```text
용량 C=4
배열 인덱스    0   1   2   3
실제 저장      1   2   ·   0
                          ↑ head=3
읽는 순서      3번 → 0번 → 1번
덱의 순서      [0, 1, 2], count=3
```

배열의 마지막 칸 다음을 첫 칸으로 계산하므로 원형 버퍼라고 부릅니다. 앞에 새 값을 넣으려면 `head`의 이전 칸을 사용합니다. 뒤에 넣으려면 현재 마지막 원소의 다음 칸을 사용합니다. 빈칸이 있는 동안에는 기존 원소를 옮기지 않습니다.

앞에서 i번째 원소의 실제 인덱스는 `wrap(head + i)`입니다. `wrap`은 계산한 인덱스를 `0`부터 `C - 1` 사이로 맞추는 함수입니다. TypeScript의 나머지 연산은 음수 결과를 낼 수 있으므로 한 번 보정합니다.

```text
C=4일 때
wrap(4)  = 0    마지막 칸 다음은 첫 칸
wrap(-1) = 3    첫 칸 이전은 마지막 칸

wrap(x) = ((x % C) + C) % C
```

`pushFront(x)`는 공간을 확보한 뒤 `head = wrap(head - 1)`로 바꾸고 그 위치에 값을 씁니다. `pushBack(x)`는 `wrap(head + count)`에 씁니다. 두 연산 모두 마지막에 `count`를 1 늘립니다.

| 호출 | 실제 배열 | head | count | 덱의 순서 |
| --- | --- | --- | --- | --- |
| 시작 | `[·,·,·,·]` | 0 | 0 | `[]` |
| `pushBack(1)` | `[1,·,·,·]` | 0 | 1 | `[1]` |
| `pushBack(2)` | `[1,2,·,·]` | 0 | 2 | `[1,2]` |
| `pushFront(0)` | `[1,2,·,0]` | 3 | 3 | `[0,1,2]` |
| `pushBack(3)` | `[1,2,3,0]` | 3 | 4 | `[0,1,2,3]` |

삭제할 때는 해당 원소를 읽고 그 칸을 비운 뒤 `count`를 줄입니다. 앞에서 삭제했다면 `head`도 다음 칸으로 옮깁니다. 조회는 같은 위치를 읽기만 합니다. 뒤쪽 조회·삭제의 위치는 `wrap(head + count - 1)`이고, 뒤쪽 삽입 위치에는 `-1`이 없다는 차이를 기억하세요.

#### 짚고 가기 — 원형 버퍼의 배열을 늘릴 때는 덱의 순서로 복사한다

위 배열에 4를 추가하려면 용량을 늘려야 합니다. 기존 배열의 0번 칸부터 그대로 복사하면 `[1, 2, 3, 0]`이 됩니다. 그러나 덱의 첫 원소는 3번 칸의 0입니다. **`head`부터 논리적인 순서로 복사**해야 합니다.

```text
확장 전: [1,2,3,0], head=3, count=4
복사할 기존 인덱스: 3 → 0 → 1 → 2
확장 후: [0,1,2,3,·,·,·,·], head=0
뒤에 4 삽입: [0,1,2,3,4,·,·,·], count=5
```

새 배열을 사용하기 시작할 때 `head`를 0으로 바꾸는 것까지 한 작업입니다. 용량만 바꾸면 `wrap`이 계산하는 위치가 달라집니다. 원소를 복사하고 나서 새 배열로 교체해야 복사 도중의 인덱스 계산도 기존 용량을 사용합니다.

#### 원형 버퍼 전체 코드

`#grow()`가 원소 순서를 유지하면서 용량을 늘립니다. 각 삽입 메서드는 이 작업이 끝난 뒤 위치를 계산하므로 새 용량을 사용합니다. 삭제한 칸에 `undefined`를 쓰는 것은 제거한 객체의 참조를 남기지 않기 위해서이며, 빈 상태는 `#count`로 판단합니다.

```ts guide-core=src/data-structures/linear/deque/_reference/deque.ts
/** 처음 잡는 칸 수. 2의 거듭제곱일 필요는 없다 — 나머지 연산으로 감싸기 때문이다. */
const INITIAL_SLOTS = 8;

export class Deque<T> {
  #slots: (T | undefined)[] = new Array(INITIAL_SLOTS);
  /** 앞 끝 원소가 놓인 칸. 비어 있을 때는 다음 `pushBack` 이 쓸 칸이다. */
  #head = 0;
  #count = 0;

  pushFront(item: T): void {
    if (this.#count === this.#slots.length) this.#grow();
    this.#head = this.#wrap(this.#head - 1);
    this.#slots[this.#head] = item;
    this.#count += 1;
  }

  pushBack(item: T): void {
    if (this.#count === this.#slots.length) this.#grow();
    const at = this.#wrap(this.#head + this.#count);
    this.#slots[at] = item;
    this.#count += 1;
  }

  popFront(): T | null {
    if (this.#count === 0) return null;
    const item = this.#slots[this.#head] as T;
    this.#slots[this.#head] = undefined;
    this.#head = this.#wrap(this.#head + 1);
    this.#count -= 1;
    return item;
  }

  popBack(): T | null {
    if (this.#count === 0) return null;
    const at = this.#wrap(this.#head + this.#count - 1);
    const item = this.#slots[at] as T;
    this.#slots[at] = undefined;
    this.#count -= 1;
    return item;
  }

  peekFront(): T | null {
    if (this.#count === 0) return null;
    return this.#slots[this.#head] as T;
  }

  peekBack(): T | null {
    if (this.#count === 0) return null;
    return this.#slots[this.#wrap(this.#head + this.#count - 1)] as T;
  }

  /**
   * 논리 위치를 칸 번호로 감싼다. 음수도 받으므로 `pushFront` 가 따로 분기하지 않는다.
   */
  #wrap(index: number): number {
    const total = this.#slots.length;
    return ((index % total) + total) % total;
  }

  /**
   * 칸을 두 배로 늘리고 원소를 **앞에서부터 차례로** 새 칸에 옮긴다.
   *
   * 옮기고 나서 `#head` 를 0으로 되돌리는 것이 중요하다. 감긴 상태를 그대로 두고 칸만
   * 늘리면 앞 끝과 뒤 끝 사이에 빈 칸이 끼어 순서가 어긋난다.
   */
  #grow(): void {
    const grown: (T | undefined)[] = new Array(this.#slots.length * 2);
    for (let offset = 0; offset < this.#count; offset++) {
      grown[offset] = this.#slots[this.#wrap(this.#head + offset)];
    }
    this.#slots = grown;
    this.#head = 0;
  }
}
```

이 코드는 [참조 구현](./_reference/deque.ts)에서 계측 코드만 제외한 것입니다. 덱을 구현하는 한 가지 방법이며, 다른 두 구현도 같은 연산 의미와 비용 요구를 만족합니다.

#### 3-1. 이중 연결 리스트 — 원소 대신 연결을 바꾼다

이중 연결 리스트에서는 각 원소를 노드 하나에 저장합니다. 노드는 이전 노드를 `prev`, 다음 노드를 `next`로 참조합니다. 덱은 첫 노드 `head`와 마지막 노드 `tail`을 기억합니다.

```text
head                               tail
 ↓                                   ↓
[1] ←→ [2] ←→ [3] ←→ [4]
prev=null                         next=null
```

앞에 0을 넣으려면 새 노드의 `next`를 기존 첫 노드에 연결하고, 기존 첫 노드의 `prev`를 새 노드로 바꿉니다. 그런 다음 `head`를 새 노드로 바꿉니다. 원소가 몇 개이든 같은 수의 참조를 수정합니다.

단일 연결 리스트와 달리 `prev`가 필요한 이유는 뒤쪽 삭제 때문입니다. 마지막 노드를 제거한 뒤 이전 노드가 새 `tail`이 되어야 합니다. 다음 노드만 참조한다면 이전 노드를 찾으러 앞에서부터 순회해야 합니다.

```text
뒤 삭제 전: head → [1] ←→ [2] ←→ [3] ← tail
3의 prev를 읽음 → 새 tail은 노드 2
새 tail의 next를 null로 변경
뒤 삭제 후: head → [1] ←→ [2] ← tail
반환값: 3
```

#### 짚고 가기 — 이중 연결 리스트에서 마지막 원소를 지우면 양 끝을 함께 비운다

원소가 하나면 `head`와 `tail`이 같은 노드를 가리킵니다. 앞에서 그 노드를 지워 `head`가 `null`이 됐다면 `tail`도 `null`로 바꿔야 합니다. 그대로 두면 뒤쪽 조회가 이미 삭제한 값을 반환합니다.

<!--proof:linked-trace-->

```text
pushBack(7): head=7, tail=7
popFront → 7: head=null, tail=null
peekBack → null
pushFront(8): head=8, tail=8
popBack → 8: head=null, tail=null
```

아래 코드의 삭제 메서드는 새 끝 노드가 있는 경우와 없는 경우를 나누어 처리합니다. 새 노드가 있으면 바깥쪽 참조를 끊고, 없으면 반대쪽 끝도 비웁니다.

```ts
type Link<T> = {
  value: T;
  prev: Link<T> | null;
  next: Link<T> | null;
};

export class LinkedDeque<T> {
  private head: Link<T> | null = null;
  private tail: Link<T> | null = null;

  peekFront(): T | null { return this.head === null ? null : this.head.value; }
  peekBack(): T | null { return this.tail === null ? null : this.tail.value; }

  pushFront(item: T): void {
    const node: Link<T> = { value: item, prev: null, next: this.head };
    if (this.head === null) this.tail = node;
    else this.head.prev = node;
    this.head = node;
  }

  pushBack(item: T): void {
    const node: Link<T> = { value: item, prev: this.tail, next: null };
    if (this.tail === null) this.head = node;
    else this.tail.next = node;
    this.tail = node;
  }

  popFront(): T | null {
    if (this.head === null) return null;
    const node = this.head;
    this.head = node.next;
    if (this.head === null) this.tail = null;
    else this.head.prev = null;
    node.next = null;
    return node.value;
  }

  popBack(): T | null {
    if (this.tail === null) return null;
    const node = this.tail;
    this.tail = node.prev;
    if (this.tail === null) this.head = null;
    else this.tail.next = null;
    node.prev = null;
    return node.value;
  }
}
```

`peekFront()`와 `peekBack()`은 끝 노드의 값만 읽습니다. 크기를 구하려고 노드를 순회하는 과정이나 배열을 다시 배치하는 과정은 없습니다. 같은 값을 여러 번 넣어도 각각 별도 노드를 만들므로 삽입 횟수만큼 삭제할 수 있습니다.

## 파트 2 — 순서 보존, 비용, 선택 기준

### 불변식 — 저장 상태를 덱의 순서로 읽는 규칙

세 구현이 같은 결과를 내려면, 저장한 상태를 원소의 순서로 해석하는 규칙이 연산 뒤에도 유지되어야 합니다. 여기서는 각 구현의 내부 표현을 설명합니다. 덱의 공개 연산이 특정한 배열 배치나 노드 연결을 요구하는 것은 아닙니다.

| 구현 | 저장 상태를 읽는 규칙 | 연산 뒤 확인할 것 |
| --- | --- | --- |
| 두 스택 | `reverse(front) + back` | 재분배 전후에 같은 수열인지 |
| 원형 버퍼 | i번째 원소는 `wrap(head + i)` | 유효 원소 수와 시작 위치가 맞는지 |
| 이중 연결 리스트 | head에서 next를 따라 읽음 | 이웃의 prev가 역방향으로 연결되는지 |

두 스택의 재분배는 읽은 수열을 절반으로 나눠 다시 저장하므로 순서를 보존합니다. 원형 버퍼의 확장도 같은 수열을 새 배열의 앞부분으로 복사합니다. 연결 리스트의 삽입은 기존 연결을 보존하면서 양 끝에 새 노드만 추가합니다. 그래서 내부 배치가 달라도 사용자에게 보이는 순서는 같습니다.

### 비용 계산

#### 비용을 세는 과정

현재 원소 수를 n, 빈 상태부터 실행한 연산 횟수를 m이라고 하겠습니다. 먼저 **원형 버퍼**를 보겠습니다. 빈칸이 있는 삽입과 모든 삭제·조회는 배열의 일정한 수의 칸만 읽고 씁니다. T17처럼 확장하는 삽입만 기존 원소 전체를 복사합니다.

```text
초기 용량 8 → 16 → 32 → 64
확장할 때 복사한 수: 8 + 16 + 32 = 56
마지막 복사량 32의 두 배보다 작다.
```

마지막 확장에서 L개를 복사했다면 이전 복사를 모두 합해도 `8 + 16 + … + L < 2L`입니다. L개가 저장될 때까지 적어도 L번 삽입했으므로 L은 m을 넘지 않습니다. 일반 연산의 O(m)에 복사 비용 O(m)을 더해도 전체는 O(m)입니다. 삭제할 때 축소하지 않기 때문에 삭제가 섞여도 확장 비용이 더 자주 발생하지 않습니다.

**두 스택**도 한 번의 재분배에는 O(n)이 필요합니다. 다만 재분배 직전의 크기 차이는 n이고, 직후에는 최대 1입니다. 보통의 삽입·삭제는 이 차이를 한 번에 최대 1만 바꿉니다. 크기 차이가 커지는 동안의 연산에 재분배 비용을 나누어 부담시키는 방식으로 분석할 수 있습니다.

```text
차이 d = abs(front.length - back.length)
재분배 직전 d=n → 재분배 직후 d≤1
일반 삽입·삭제 한 번: d의 변화량은 최대 1
```

이를 식으로 쓰면 저장된 비용을 `Φ = k × d`로 둡니다. 재분배 한 번의 실제 비용이 `a × n + b` 이하라면 k를 a 이상으로 잡습니다. 그러면 실제 비용에 Φ의 변화량을 더한 값은 `a × n + b + k × (1 - n)` 이하이며, n에 따라 증가하지 않습니다. 일반 연산에서도 Φ는 최대 k만 늘어납니다. 처음 Φ가 0이고 끝에서도 음수가 아니므로 m번의 실제 총비용은 O(m)입니다. 스택 배열 자체가 커지는 비용도 동적 배열의 상각 비용으로 더해집니다.

**이중 연결 리스트**는 한 호출에서 끝 노드와 그 이웃만 다룹니다. 노드 할당을 O(1)로 보는 분석 모델에서는 삽입·삭제·조회가 각각 최악 O(1)입니다. 이는 메모리 할당기나 가비지 컬렉션까지 포함한 응답 시간이 항상 일정하다는 뜻은 아닙니다.

#### 케이스별 비용과 그 경계

| 연산 | 두 스택 | 원형 버퍼 | 이중 연결 리스트 |
| --- | --- | --- | --- |
| `pushFront`, `pushBack` | 상각 O(1) | 상각 O(1) | 최악 O(1) |
| `popFront`, `popBack` | 상각 O(1) | 최악 O(1) | 최악 O(1) |
| `peekFront`, `peekBack` | 최악 O(1) | 최악 O(1) | 최악 O(1) |
| 한 번의 큰 작업 | 재분배 또는 배열 확장 O(n) | 배열 확장 O(n) | 전체 원소를 처리하는 작업 없음 |
| 저장 공간 | 원소 O(n), 배열 여유 공간 별도 | O(C), C는 용량 | O(n), 노드마다 참조 두 개 |

이 표는 각 구현의 보장입니다. 앞의 계약 표가 삭제를 상각 O(1)로 허용해도, 원형 버퍼와 연결 리스트는 삭제마다 최악 O(1)을 제공할 수 있습니다. 더 강한 보장을 주는 구현도 계약을 만족합니다.

원형 버퍼는 삭제해도 용량을 줄이지 않습니다. 따라서 현재 원소 수 n이 작아져도 C는 클 수 있습니다. 최대 저장 원소 수를 N이라고 하면 용량은 O(N + 1)입니다. 두 스택은 재분배 중 O(n)의 임시 배열이 추가로 필요하고, JavaScript 배열의 실제 여유 용량은 엔진의 관리 방식에 영향을 받습니다.

#### 최악을 만드는 입력

오류와 큰 비용은 같은 입력에서 발생하지 않을 수 있습니다. 두 스택에서는 한쪽에 몰아 넣은 뒤 앞뒤를 번갈아 삭제하는 경우가 중요하고, 원형 버퍼에서는 `head`가 0이 아닌 상태에서 확장하는 경우가 중요합니다.

| 확인할 입력 | 확인할 동작 |
| --- | --- |
| 뒤로 n개 삽입 후 앞뒤 교대 삭제 | 재분배 때 순서가 유지되는지, 전부 이동을 반복하지 않는지 |
| 앞으로 계속 삽입해 용량 초과 | 음수 인덱스 보정과 논리 순서 복사 |
| 한 개 삽입 후 반대쪽 삭제 | 양 끝이 같은 원소를 가리키는 경계 처리 |
| 비운 뒤 다시 삽입 | 오래된 참조나 인덱스 때문에 값이 남지 않는지 |
| 중복값·0·false·undefined 삽입 | 값의 참·거짓으로 빈 상태를 판단하지 않는지 |

세 구현에 같은 연산을 보내고, 단순 배열로 계산한 결과와 매번 비교할 수 있습니다. 배열은 정답을 확인하기 위한 모델이므로 느려도 괜찮습니다. 이 비교는 동작을 검사하며, 상각 시간의 근거는 앞의 비용 분석입니다.

원형 버퍼의 [계약 스위트](./deque.contract.ts)는 입력 규모를 늘려 내부 작업량의 증가도 확인합니다. 이런 유한한 실행 검사는 잘못된 구현을 찾는 데 도움이 되지만, 모든 크기에 대한 상각 분석을 대신하지는 않습니다.

### 이 구조가 최적의 선택인 경우

#### 최적인 요구의 모양

양쪽 끝에서 삽입·삭제할 수 있어야 하고, 가운데 원소를 찾을 필요가 없다면 덱이 적합합니다. 어떤 구현을 고를지는 별도의 선택입니다. 배열 공간을 재사용하려면 원형 버퍼를, 전체 복사 없이 노드를 추가하려면 연결 리스트를 검토할 수 있습니다. 두 스택은 배열 끝 연산으로 구현하되 재분배 비용을 관리하는 방법입니다.

| 먼저 확인할 요구 | 검토할 구현 | 함께 고려할 비용 |
| --- | --- | --- |
| 배열 기반 저장과 공간 재사용 | 원형 버퍼 | 용량 확장 때 전체 복사 |
| 원소 전체를 한 번에 옮기지 않기 | 이중 연결 리스트 | 노드 할당과 참조 저장 |
| 배열 끝 연산으로 구현하기 | 두 스택 | 절반 재분배와 임시 배열 |

#### 이 구조를 떠올리게 하는 연산 조합

뒤에 넣고 앞에서만 꺼내면 큐로 충분합니다. 같은 끝에서만 넣고 꺼내면 스택으로 충분합니다. 덱은 실행 중에 사용할 끝이 바뀌거나, 앞쪽과 뒤쪽에서 각각 다른 조건으로 원소를 제거해야 할 때 필요합니다.

```text
스택: 같은 끝에서 삽입·삭제
큐:   뒤에서 삽입, 앞에서 삭제
덱:   필요에 따라 양쪽에서 삽입·삭제
```

반대로 최솟값을 위치와 무관하게 꺼내야 한다면 덱의 연산만으로는 부족합니다. 양 끝 접근과 우선순위에 따른 접근은 다른 요구입니다.

#### 실제로 쓰이는 곳

슬라이딩 윈도우 최댓값에서는 후보 인덱스를 덱에 보관합니다. 범위를 벗어난 오래된 인덱스는 앞에서 제거하고, 새 값보다 작아 앞으로 최댓값이 될 수 없는 후보는 뒤에서 제거합니다. 어느 원소를 제거할지는 알고리즘이 정하고, 덱은 그 양쪽 삭제를 빠르게 수행합니다.

가중치가 0 또는 1인 그래프의 0–1 BFS에서는 다음에 처리할 정점을 간선 가중치에 따라 앞이나 뒤에 넣습니다. 삽입 방향을 달리해서 처리 순서를 유지하는 사례입니다.

#### 경쟁 설계와의 대조

한 번의 큰 복사를 허용하는지와 저장 공간의 부담을 비교해 보겠습니다. 아래 [측정 코드](./deque-guide.alt.ts)는 뒤에 1,024개를 넣고 앞에서 모두 꺼내는 같은 연산열을 실행합니다. 배열에서는 칸 접근을, 연결 리스트에서는 값·연결 필드 접근을 세므로 **실제 실행 시간의 비교는 아닙니다.**

| 측정 항목 | 원형 버퍼 | 측정용 연결 리스트 |
| --- | --- | --- |
| 한 호출의 칸·필드 접근 수 최댓값 | 513 | 4 |
| 전체 접근 수 | 3064 | 7166 |
| 최대로 보관한 칸·필드 수 | 1024 | 3072 |
| 모두 삭제한 뒤 보관하는 칸·필드 수 | 1024 | 0 |

원형 버퍼는 용량을 늘리는 한 번의 호출에서 많은 원소를 처리합니다. 연결 리스트는 전체 복사가 없지만 각 노드에 연결 정보를 보관합니다. 따라서 큰 복사를 피하려는 조건에서는 연결 리스트가 유리하고, 노드별 연결 저장을 줄이려는 조건에서는 원형 버퍼가 유리합니다. 이 계수만으로 어느 쪽이 실제로 더 빠르다고 결론 내릴 수는 없습니다.

최대 원소 수를 미리 안다면 고정 용량 원형 버퍼로 확장을 없앨 수도 있습니다. 그 경우 가득 찼을 때의 처리 규칙을 따로 정해야 합니다. 오래된 원소를 덮어쓰는 방식은 이 글처럼 명시적으로 삭제하기 전까지 값을 보존하는 덱과 동작이 다릅니다.

### 스스로 점검하기

1. `front=[]`, `back=[1,2,3,4,5]`에서 `popFront()`를 한 뒤 두 배열은 어떻게 될까요? **답:** 재분배 후 `[3,2,1]`, `[4,5]`에서 1을 꺼내므로 `[3,2]`, `[4,5]`가 됩니다.
2. T17에서 용량을 늘릴 때 기존 배열의 0번부터 복사하면 왜 틀릴까요? **답:** 첫 원소는 `head`가 가리키는 위치에 있습니다. 물리적 인덱스 순서로 복사하면 덱의 순서가 바뀝니다.
3. 연결 리스트의 마지막 노드를 앞에서 삭제하면서 `tail`을 남겨 두면 어떤 문제가 생길까요? **답:** `peekBack()`이 이미 삭제한 값을 반환합니다. 양 끝을 함께 `null`로 만들어야 합니다.
4. 원형 버퍼에서 한 번의 삽입이 O(n)일 수 있는데도 상각 O(1)이라고 하는 이유는 무엇일까요? **답:** 확장 시 복사량의 합이 마지막 복사량의 두 배보다 작고, 그 크기까지 채우려면 그에 비례하는 삽입이 필요하기 때문입니다.
