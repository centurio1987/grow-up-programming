# Deque — 한 수열의 양 끝을 모두 상수 비용으로

## 개요

덱(Deque, Double-Ended Queue)은 한 수열의 **앞 끝과 뒤 끝 양쪽**에서 넣고 빼고 볼 수 있는 컨테이너입니다. 설계 핵심은 원소를 옮기지 않고 **"어디가 앞인가"를 가리키는 정수 하나를 움직이는 것**이고, 그 대가로 여덟 연산이 모두 `amortized O(1)`에 끝납니다.

## 이 구조가 필요한 이유

덱이 약속하는 것은 하나입니다 — **양 끝 어느 쪽을 건드리든 원소 수와 무관한 비용**. 한쪽 끝만 필요하면 스택으로 충분하고, 넣는 끝과 빼는 끝이 서로 고정되어 있으면 큐로 충분합니다. **양쪽이 동시에 열려 있어야 할 때** 비로소 덱이 필요합니다.

어려운 점은 "양쪽"이라는 말에 있습니다. 배열은 뒤 끝 하나만 싸게 다루고, 앞을 건드리면 뒤 원소 전부의 자리가 바뀝니다. 그래서 덱은 **한 끝을 싸게 만드는 방법을 두 끝에 동시에 적용하는 문제**가 됩니다.

이 계약에 **없는 것**도 분명합니다. 가운데 원소를 인덱스로 꺼내는 연산, 값으로 찾는 연산, 순회가 없습니다. 그것들이 필요하면 덱이 아니라 다른 계약을 찾아야 합니다.

### 쓰이는 자리

사례를 **연산 집합과 호출 빈도**로 옮겨 적습니다. 옮겨 적어 보면 그 자리가 정말 덱을 요구하는지가 드러납니다.

- **슬라이딩 윈도우 최댓값(단조 덱)** — 창이 한 칸 밀릴 때마다 `popFront` 로 만료된 후보를 버리고, `popBack` 으로 새 값보다 작은 후보를 솎아내고, `pushBack` 으로 새 값을 넣고, `peekFront` 로 답을 읽습니다. 네 연산이 스트림 길이만큼 반복되고 각 원소가 많아야 한 번 들어왔다 한 번 나가므로 전체가 `O(n)` 입니다. **네 연산이 모두 계약에 있습니다.**
- **팰린드롬 검사** — `popFront` 와 `popBack` 을 **번갈아** 부르며 안쪽으로 좁힙니다. 길이의 절반만큼 반복합니다. 이 호출 패턴은 아래 3단계에서 다시 나옵니다 — 어떤 설계를 최악으로 몰아넣는 자리이기 때문입니다.
- **0-1 BFS** — 간선 가중치가 0이면 `pushFront`, 1이면 `pushBack`. 간선 수만큼 반복하고, 우선순위 큐 없이 최단 경로를 얻습니다. **여기서는 앞뒤가 우선순위를 대신합니다.**
- **작업 훔치기 스케줄러** — 자기 작업은 한쪽 끝에서 `pop`, 노는 스레드는 반대쪽 끝에서 `pop`. 같은 자리를 다툴 확률을 낮추려고 일부러 양 끝을 씁니다.

가운데를 인덱스로 읽는 사례는 위에 없습니다. 있었다면 그것은 덱의 사례가 아니라 다른 구조의 사례입니다.

## 단순한 구현의 한계

### 순진한 설계는 어디서 상한을 넘는가

덱을 모른 채 이 요구를 받으면 가장 먼저 나오는 답은 **배열 하나**입니다. 뒤는 `push`/`pop`, 앞은 `unshift`/`shift` 를 쓰면 코드가 여덟 줄이면 끝납니다.

넘어가는 자리는 `unshift` 입니다. 배열 앞에 자리를 만들려면 이미 들어 있는 원소를 전부 한 칸씩 뒤로 밀어야 합니다. 연산당 몇 칸을 건드리는지 실제로 세면 이렇습니다.

```text
앞으로만 n번 넣기 — 연산당 건드린 칸 수 (성장률 판정과 같은 계측)

        n        배열 하나(unshift)      링 버퍼
    1,024              512.50              1.99
    4,096            2,048.50              2.00
   16,384            8,192.50              2.00

n을 4배로 키우면 배열 하나는 연산당 비용도 4배가 된다 (r = 4.00).
계약이 요구하는 값은 r = 1.00 이다.
```

이 실패는 가끔이 아니라 **구조적**입니다. 어떤 입력을 넣어도 앞쪽 삽입은 뒤 전부를 옮깁니다. 입력을 잘 고르면 피할 수 있는 종류의 문제가 아닙니다.

여기서 **벽시계를 근거로 쓰지 않는 이유**를 짚어 둘게요. 같은 배열의 `shift` 를 시간으로 재면 크기에 비례해 늘지 않습니다 — 엔진이 "시작 위치만 민다" 같은 최적화를 걸어 두었기 때문입니다. 명세는 `shift` 를 "나머지를 전부 앞으로 다시 인덱싱한다"는 **의미**로 정의할 뿐, 상수 시간을 보장하지 않습니다. 시간만 재면 이 구현이 통과해 버리고, 그러면 **성능의 근거를 엔진 사정에 맡긴 것**이 됩니다. 위 표가 세는 것은 시간이 아니라 계약이 요구하는 작업량입니다.

### 실패에서 끌어내는 설계 규칙

관찰은 하나입니다 — **배열에서 비용이 보장되는 자리는 끝 하나뿐이다.**

여기서 자연스러운 다음 수가 **배열 두 개**입니다. 앞쪽 절반을 거꾸로 담는 배열과 뒤쪽 절반을 정순으로 담는 배열을 등 맞대어 두면, 논리적인 앞도 물리적인 끝이 됩니다. 한쪽이 바닥나면 반대쪽 원소를 옮겨 채웁니다.

이 설계는 **큐 패턴에서 실제로 옳습니다.** 뒤로 넣고 앞으로만 빼면 원소마다 한 번씩만 옮겨지므로 연산당 상수입니다.

```text
뒤로 n번 넣고 앞으로 n번 빼기 (큐 패턴) — 연산당 건드린 칸 수

        n         배열 두 개       링 버퍼
    1,024            1.50           1.50
    4,096            1.50           1.50
   16,384            1.50           1.50      ← 둘 다 r = 1.00, 통과
```

그런데 **앞뒤를 번갈아 빼면** 무너집니다.

```text
n개를 채운 뒤 popFront / popBack 을 번갈아 n번 — 연산당 건드린 칸 수

        n         배열 두 개       링 버퍼
    1,024          513.50           1.00
    4,096        2,049.50           1.00
   16,384        8,193.50           1.00

배열 두 개는 r = 4.00 으로 걸린다. 링 버퍼는 r = 1.00 이다.
```

왜 그런지는 손으로 따라가면 바로 보입니다. 한쪽이 비었을 때 반대쪽을 **전부** 옮기므로, 옮기고 나면 준 쪽이 반드시 0개가 됩니다. 그리고 교대 호출은 바로 그 빈 쪽을 다음 차례에 찌릅니다.

```text
앞=[]  뒤=[1..8]
  popFront → 뒤 8개를 전부 앞으로 (8칸)  → 1 반환, 뒤가 비었다
  popBack  → 앞 7개를 전부 뒤로   (7칸)  → 8 반환, 앞이 비었다
  popFront → 뒤 6개를 전부 앞으로 (6칸)  → 2 반환, 뒤가 비었다
  ...
8 + 7 + 6 + … = n²/2
```

**이 입력은 지어낸 것이 아닙니다.** 2단계에서 덱의 대표 용도로 꼽은 팰린드롬 검사가 정확히 이 호출 패턴입니다. 덱을 쓰는 대표적인 이유 하나가 이 설계를 최악으로 몰아넣습니다.

두 실패가 같은 것을 가리킵니다. **원소를 옮기는 일이 연산의 정상 경로에 있으면 안 됩니다.** 배열 하나는 앞을 건드릴 때마다 옮기고, 배열 두 개는 한쪽이 빌 때마다 옮깁니다. 옮기는 일이 남아도 되려면 그것이 **원소 수가 바뀔 때가 아니라 그릇 크기가 바뀔 때만** 일어나야 합니다.

그래서 이 구조는 **"앞이 어디인가"를 값이 아니라 정수 하나로 들고 있는 것**을 조건으로 갖습니다. 앞에 넣는 일이 그 정수를 하나 물리는 일이 되면, 옮길 원소가 애초에 없습니다.

## 불변식과 연산별 복잡도 조건

계약 전문은 `deque.ts` 헤더에 있습니다. 여기서는 그 조건이 **왜 그 모양인지**를 봅니다.

**불변식 절은 비어 있습니다.** 각 연산의 의미가 각각 옳으면 따로 깨질 수 있는 상태 성질이 남지 않기 때문입니다. 앞과 뒤가 같은 수열의 두 끝이라는 사실은 `peekFront`·`peekBack` 의 의미가 그대로 정의합니다. 여기서 "없다"는 **아직 안 적었다는 뜻이 아니라 공집합이라는 뜻**입니다.

**한정자가 연산마다 갈립니다.** 넣고 빼기 넷은 `amortized`, 보기 넷(`peekFront`·`peekBack`·`isEmpty`·`size`)은 `worst` 입니다. 계약이 **가장 약한 한정자**를 적는 이유는 강한 한정자가 우회로 낸 처방이기 때문입니다. `pushBack` 을 `worst O(1)` 로 적으면 용량을 늘리는 구현이 전부 계약 위반이 됩니다 — 그릇을 늘리는 그 한 번의 호출이 상수를 넘기니까요. 아무도 배열을 금지한 적이 없는데 배열이 금지됩니다.

**검증 등급은 `complexity` 입니다.** 상한이 자명한 구현으로 달성되지 않기 때문이고, 그 반례가 위 3단계에서 실제로 돌려 본 배열 하나입니다. 등급을 고른 것이 아니라 계약에서 따라 나온 것이라는 점이 중요합니다 — 계약이 바뀌면 등급도 다시 판정됩니다.

한 조건을 풀어 주면 무엇이 되는지도 분명합니다. 앞쪽 상한만 `O(n)` 으로 풀면 그것은 덱이 아니라 **앞뒤로 읽을 수 있는 배열**이고, 위 네 가지 사례가 그 자리에서 한 차수 느려집니다.

## 구현 (TypeScript)

아래 코드는 `_reference/deque.ts` 에서 그대로 가져온 것입니다. 손으로 옮겨 적지 않았고, 정본이 바뀌면 이 블록도 함께 바뀝니다.

```ts guide-core=src/data-structures/linear/deque/_reference/deque.ts
/** 처음 잡는 칸 수. 2의 거듭제곱일 필요는 없다 — 나머지 연산으로 감싸기 때문이다. */
const INITIAL_SLOTS = 8;

export class Deque<T> {
  #slots: (T | undefined)[] = new Array(INITIAL_SLOTS);
  /** 앞 끝 원소가 놓인 칸. 비어 있을 때는 다음 `pushBack` 이 쓸 칸이다. */
  #head = 0;
  #count = 0;

  pushFront(item: T): void {
    if (this.#count === this.#slots.length) this.#grow();
    this.#head = this.#wrap(this.#head - 1);
    this.#slots[this.#head] = item;
    this.#count += 1;
  }

  pushBack(item: T): void {
    if (this.#count === this.#slots.length) this.#grow();
    const at = this.#wrap(this.#head + this.#count);
    this.#slots[at] = item;
    this.#count += 1;
  }

  popFront(): T | null {
    if (this.#count === 0) return null;
    const item = this.#slots[this.#head] as T;
    this.#slots[this.#head] = undefined;
    this.#head = this.#wrap(this.#head + 1);
    this.#count -= 1;
    return item;
  }

  popBack(): T | null {
    if (this.#count === 0) return null;
    const at = this.#wrap(this.#head + this.#count - 1);
    const item = this.#slots[at] as T;
    this.#slots[at] = undefined;
    this.#count -= 1;
    return item;
  }

  peekFront(): T | null {
    if (this.#count === 0) return null;
    return this.#slots[this.#head] as T;
  }

  peekBack(): T | null {
    if (this.#count === 0) return null;
    return this.#slots[this.#wrap(this.#head + this.#count - 1)] as T;
  }

  isEmpty(): boolean {
    return this.#count === 0;
  }

  size(): number {
    return this.#count;
  }

  /**
   * 논리 위치를 칸 번호로 감싼다. 음수도 받으므로 `pushFront` 가 따로 분기하지 않는다.
   */
  #wrap(index: number): number {
    const total = this.#slots.length;
    return ((index % total) + total) % total;
  }

  /**
   * 칸을 두 배로 늘리고 원소를 **앞에서부터 차례로** 새 칸에 옮긴다.
   *
   * 옮기고 나서 `#head` 를 0으로 되돌리는 것이 중요하다. 감긴 상태를 그대로 두고 칸만
   * 늘리면 앞 끝과 뒤 끝 사이에 빈 칸이 끼어 순서가 어긋난다.
   */
  #grow(): void {
    const grown: (T | undefined)[] = new Array(this.#slots.length * 2);
    for (let offset = 0; offset < this.#count; offset++) {
      grown[offset] = this.#slots[this.#wrap(this.#head + offset)];
    }
    this.#slots = grown;
    this.#head = 0;
  }
}
```

**가장 중요한 부분은 `#wrap` 하나입니다.** 앞에 넣는 일이 `#head` 를 하나 물리는 일로 바뀌고, 물린 결과가 음수가 되면 반대쪽 끝으로 감깁니다. 옮길 원소가 애초에 없다는 3단계의 결론이 이 한 줄로 코드가 됩니다.

놓치기 쉬운 자리 셋을 짚어 둘게요.

- **`#grow` 가 `#head` 를 0으로 되돌리는 두 줄의 순서.** 원소를 앞에서부터 차례로 옮긴 뒤에 되돌려야 합니다. 감긴 상태를 그대로 두고 칸만 늘리면 앞 끝과 뒤 끝 사이에 빈 칸이 끼어 순서가 어긋납니다.
- **`#wrap` 의 이중 나머지 연산.** `index % total` 하나만 쓰면 음수 입력에서 음수가 나옵니다. `pushFront` 가 `#head - 1` 을 넘기므로 이 자리가 실제로 걸립니다.
- **`popFront` 가 칸을 `undefined` 로 비우는 줄.** 지우지 않아도 동작은 옳지만, 꺼낸 원소를 배열이 계속 붙들고 있어 회수되지 않습니다.

**성장률로 조건 충족을 확인합니다.** 계약 스위트 축3이 다섯 시나리오를 판별 수준(±30%)으로 재고, 다섯 모두 $r = 1.00$ 입니다 — 계약이 요구하는 값과 같습니다. 시간이 아니라 건드린 칸 수를 세므로, 이 판정은 이 기계의 상수가 아니라 계약을 잽니다.

**사용 조건이 달라지면 다른 구현이 적합합니다.** 계약은 구현을 처방하지 않으므로 여기 실린 것은 계약을 만족하는 여럿 중 하나입니다. 최악 지연이 균일해야 하면 확장 순간의 스파이크가 없는 이중 연결 리스트가 낫고, 그 대신 원소마다 노드 객체를 상시로 물게 됩니다. 앞쪽을 아예 쓰지 않는다면 링도 필요 없습니다.
