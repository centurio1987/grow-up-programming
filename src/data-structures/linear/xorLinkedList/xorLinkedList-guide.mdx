# XorLinkedList — 이음을 하나만 들고 양쪽으로 걷는, 실패한 절약

## 개요

XOR 연결 리스트는 앞 이웃과 뒤 이웃의 위치를 **XOR 한 값 하나**로 들고, 그 하나에서 양쪽 방향을 모두 복원하는 수열입니다. 설계 핵심은 *"직전에 어디 있었는가"* 를 알면 나머지 하나가 계산된다는 것이고, 그래서 뒤에 붙이기는 `amortized O(1)`, 두 방향 순회는 각각 `worst O(n)` 입니다. 다만 이 구조가 태어난 이유는 시간이 아니라 **원소당 저장을 하나 줄이는 것**이었고, TypeScript에서는 그 절약이 음수입니다.

## 이 구조가 필요한 이유

이 계약이 약속하는 것은 셋입니다 — **뒤 끝에만 붙이기**, **저장된 전체를 두 방향으로 읽기**, **개수**. 한 방향만 읽으면 되면 단일 연결 리스트로 충분하고, 가운데를 건드려야 하면 이 계약이 아닙니다.

이 계약에 **없는 것**이 특히 분명합니다. 중간 삽입, 중간 삭제, 인덱스 접근, 값 탐색이 없습니다. 그것들이 필요하면 `doublyLinkedList` 의 계약을 찾아야 합니다 — 그쪽은 노드 손잡이를 밖으로 내주고 `insertAfter`·`remove` 를 상수에 약속합니다. 두 구조가 갈리는 자리가 이름이 아니라 **연산 집합**이라는 점이 중요합니다.

**공간도 이 계약에 없습니다.** 그런데 이 구조는 공간 때문에 태어났습니다. 계약이 약속하지 않는 것을 존재 이유로 삼은 구조라서, 6단계가 그 자리를 따로 봅니다.

### 쓰이는 자리

사례를 **연산 집합과 호출 빈도**로 옮겨 적습니다. 옮겨 적어 보면 그 자리가 정말 이 구조를 요구하는지가 드러납니다.

- **센서 로그 되감기** — 측정값이 들어올 때마다 `append`, 화면에 뿌릴 때 최신순으로 `toArrayReverse`, 파일로 넘길 때 발생순으로 `toArray`. 붙이기가 측정 횟수만큼, 순회가 요청마다 한 번씩입니다. **세 연산이 모두 계약에 있습니다.**
- **실행 취소 기록의 양방향 재생** — 조작마다 `append`, 되돌리기는 뒤에서부터, 다시 하기는 앞에서부터. 다만 **중간 잘라내기가 있으면 이 계약이 아닙니다** — 되돌린 뒤 새 조작을 하면 뒤쪽을 버려야 하는데, 그 연산이 계약에 없습니다.
- **한 번 쓰고 두 번 읽는 추적 버퍼** — 붙이기가 이벤트 수만큼, 읽기가 덤프 시점에 두 번.

번역하고 나면 한 가지가 드러납니다. **위 사례는 전부 배열로도 됩니다.** 뒤로 붙이고, 그대로 읽고, 거꾸로 읽으면 끝입니다. 그러니 이 구조가 설 자리는 계약이 아니라 계약 **밖**에 있어야 합니다 — 원소당 몇 바이트가 실제로 문제가 되는 환경이요. 그 자리가 실제로 있는지가 이 가이드의 내용입니다.

## 단순한 구현의 한계

### 순진한 설계는 어디서 상한을 넘는가

**넘지 않습니다.** 이 절이 다른 가이드와 다른 자리가 여기입니다.

이 요구를 받고 가장 먼저 나오는 답은 배열 하나입니다. 뒤로 붙이기는 `push`, 앞→뒤는 그대로 복사, 뒤→앞은 거꾸로 복사, 개수는 `length`. 네 줄이고, **네 행이 전부 계약 안에 있습니다.** 계약이 요구하는 상한을 자명한 구현이 그대로 달성합니다. 검증 등급이 `complexity` 가 아니라 `invariant` 인 이유가 바로 이것입니다 — 상한을 넘기는 반례를 적을 수 없습니다.

시간이 실제로 요구하는 것은 딱 한 줄입니다. **뒤 끝을 기억하라.** 기억하지 않고 붙일 때마다 앞에서부터 훑으면 이렇게 됩니다.

```text
뒤로 n번 붙이기 — 연산당 들여다본 노드 수 (성장률 판정과 같은 계측)

        n      뒤 끝을 안 드는 사슬      뒤 끝을 드는 사슬
    1,024              512.50                 2.00
    4,096            2,048.50                 2.00

n을 4배로 키우면 앞의 것은 연산당 비용도 4배가 된다 (r = 4.00).
계약이 요구하는 값은 r = 1.00 이다.
```

그리고 **거기까지입니다.** 같은 두 구현을 순회에서 재면 구별되지 않습니다.

```text
n개를 채운 뒤 toArray / toArrayReverse — 연산당 들여다본 노드 수

        n      뒤 끝을 안 드는 사슬      뒤 끝을 드는 사슬
    1,024            1,024.00              1,024.00
    4,096            4,096.00              4,096.00

둘 다 r = 4.00. O(n) 계약이 요구하는 값과 같으므로 둘 다 통과한다.
```

당연합니다. 원소 n 개를 돌려주는 연산은 어떤 구현에서도 n 에 비례합니다. 순회의 상한은 **아무 구현도 배제하지 못하는 상한**입니다.

### 실패에서 끌어내는 설계 규칙

관찰이 둘입니다.

**하나 — 끝을 상수 비용에 다루려면 끝을 기억해야 합니다.** 뒤 끝을 들고 있으면 붙이기가 상수가 되고, 이것이 시간 쪽에서 이 구조에 요구되는 전부입니다.

**둘 — 시간은 이 구조를 정당화하지 않습니다.** 배열이 네 행을 다 지키는데 굳이 노드를 만들고 이음을 계산할 이유가 없습니다. 그러니 이 구조가 존재하려면 근거가 시간 밖에 있어야 하고, 실제로 그렇게 주장되어 왔습니다 — **이중 연결 리스트가 원소당 이음 둘을 저장하는 자리에서 하나만 저장한다**는 것이요.

그 주장이 이 구조의 전부입니다. 그래서 이 가이드의 나머지는 그 주장을 검사합니다. 먼저 이음 하나로 양쪽을 걷는 것이 **정말 되는지**(4·5단계), 그리고 그것이 **정말 아끼는지**(6단계).

## 불변식과 연산별 복잡도 조건

계약 전문은 `xorLinkedList.ts` 헤더에 있습니다. 여기서는 그 조건이 **왜 그 모양인지**를 봅니다.

**불변식이 둘입니다.** 둘 다 같은 이유로 성립합니다 — **관측 경로가 둘**이라서요. 상태를 읽는 길이 하나뿐이면 그 길이 무엇을 내놓든 그것이 곧 상태이고, 대조할 상대가 없어 정합을 물을 수 없습니다. 길이 둘이면 구현이 둘을 따로 유지할 수 있고, 따로 유지하는 순간 갈릴 수 있습니다.

1. **세고 있는 수와 내놓을 수 있는 수가 같다.** `size()` 는 세어 둔 값을 읽고 `toArray()` 는 이음을 밟아 갑니다. 이음이 중간에서 끊기면 순회는 거기서 조용히 멈추는데, 그때도 `append` 는 자기 자리에서 옳고 `size()` 도 자기 자리에서 옳습니다. **못 지키면 이건 수열이 아니라 "세어 둔 수와 담긴 수가 다른 그릇"입니다.**
2. **두 방향이 같은 수열을 읽는다.** 방향마다 이음을 따로 들고 한쪽 갱신을 빠뜨리면 두 순회가 각각 완주하면서 서로 다른 수열을 내놓습니다. **못 지키면 이건 한 수열이 아니라 두 수열이고**, 그러면 양방향 순회라는 말 자체가 성립하지 않습니다.

두 불변식이 진짜 일을 한다는 것은 손으로 만든 결함으로 확인됩니다. 옛 꼬리를 갱신하는 자리에서 `^=` 를 `=` 로 한 글자 바꾸면 이렇게 됩니다.

```text
n=1   앞→뒤 [10]           뒤→앞 [10]        size 1     통과
n=2   앞→뒤 [10,20]        뒤→앞 [20,10]     size 2     통과
n=3   앞→뒤 [10,20,20,10]  뒤→앞 [30,20]     size 3     불변식 1 위반
```

원소가 둘일 때까지 멀쩡한 이유는 첫 꼬리의 앞 이웃이 없어서(`NIL = 0`) `^= id` 와 `= id` 의 결과가 같기 때문입니다. 셋째를 붙이는 순간 앞 이웃 정보가 덮여 사라지고, 순회가 **되돌아와** 같은 노드를 두 번 밟습니다. 불변식 1이 이것을 `순회 4개 / size 3` 으로 말합니다 — 끊겨서 짧아지는 것만이 아니라 **길어지는 것도** 같은 불변식이 잡습니다.

**한정자가 연산마다 갈립니다.** 붙이기는 `amortized`, 나머지 셋은 `worst` 입니다. 계약이 **가장 약한 한정자**를 적는 이유는 강한 한정자가 우회로 낸 처방이기 때문인데, 순회 둘에서는 두 한정자가 **같은 구현 집합을 배제합니다.** 원소 n 개를 돌려주는 연산은 어느 구현에서도 호출 하나가 n 에 비례하므로 상각할 여지가 없습니다. 배제하는 것이 같으면 강한 쪽을 적어도 처방이 되지 않습니다.

**검증 등급은 `invariant` 입니다.** 판정 절차를 위에서부터 읽습니다 — 동시 접근이 없고, 상한이 자명한 구현으로 달성되고(3단계의 배열), 불변식 절에 내용이 있습니다. 세 번째에서 걸리므로 `invariant` 입니다. 등급을 고른 것이 아니라 계약에서 따라 나온 것이고, 계약이 바뀌면 다시 판정됩니다.

이 등급이 뜻하는 것은 축3이 **회귀 수준**으로 돈다는 것입니다(±60%, n ∈ {2¹⁰, 2¹²}). 판별 수준이 아닌 이유는 판별할 상한이 없어서입니다 — 이 계약에서 축3이 잡을 수 있는 것은 3단계의 "뒤 끝을 기억하라" 한 자리뿐입니다.

## 구현 (TypeScript)

아래 코드는 `_reference/xorLinkedList.ts` 에서 그대로 가져온 것입니다. 손으로 옮겨 적지 않았고, 정본이 바뀌면 이 블록도 함께 바뀝니다.

```ts guide-core=src/data-structures/linear/xorLinkedList/_reference/xorLinkedList.ts
/** 표의 빈자리를 가리키는 값. 실제 id 는 1부터 나가므로 0 과 겹치지 않는다. */
const NIL = 0;

interface XorNode {
  id: number;
  value: number;
  /** 앞 이웃 id 와 뒤 이웃 id 의 XOR. 어느 한쪽도 이 값만으로는 복원되지 않는다. */
  xorId: number;
}

export class XorLinkedList {
  #nodes = new Map<number, XorNode>();
  #headId = NIL;
  #tailId = NIL;
  #count = 0;
  /** 다음에 나눠 줄 id. 한 번 쓴 값을 다시 쓰지 않는다. */
  #nextId = 1;

  append(value: number): void {
    const id = this.#nextId++;
    // 새 노드의 뒤 이웃은 아직 없다 — 그래서 앞 이웃 id 하나가 그대로 XOR 값이 된다.
    this.#nodes.set(id, { id, value, xorId: this.#tailId });

    if (this.#tailId === NIL) {
      this.#headId = id;
    } else {
      // 옛 꼬리의 뒤 이웃 자리는 NIL 이었다. NIL 을 지우고 새 id 를 넣는 것이 이 XOR 한 번이다.
      const tail = this.#at(this.#tailId);
      tail.xorId ^= id;
    }

    this.#tailId = id;
    this.#count += 1;
  }

  toArray(): number[] {
    return this.#walk(this.#headId);
  }

  toArrayReverse(): number[] {
    return this.#walk(this.#tailId);
  }

  size(): number {
    return this.#count;
  }

  /**
   * 한쪽 끝에서 반대쪽 끝까지 걷는다.
   *
   * **두 방향이 같은 코드다.** 시작점만 다르다. 양쪽 끝 어디서 출발하든 직전에 밟은 노드가
   * 곧 이웃 하나이므로, 저장된 XOR 값에서 나머지 하나가 나온다.
   */
  #walk(startId: number): number[] {
    const values: number[] = [];
    let prevId = NIL;
    let currId = startId;

    while (currId !== NIL) {
      const node = this.#at(currId);
      values.push(node.value);
      const nextId = node.xorId ^ prevId;
      prevId = currId;
      currId = nextId;
    }

    return values;
  }

  #at(id: number): XorNode {
    const node = this.#nodes.get(id);
    if (node === undefined) {
      throw new Error(`표에 없는 id 를 따라갔다: ${id}`);
    }
    return node;
  }
}
```

**가장 중요한 부분은 `#walk` 하나입니다.** 방향을 인자로 받지 않는다는 점을 보세요. 두 순회가 부르는 것이 같은 함수이고 다른 것은 시작점뿐입니다. 어느 끝에서 출발하든 직전에 밟은 노드가 곧 이웃 하나이므로, 저장된 XOR 값에서 나머지 하나가 나옵니다. **이음을 하나만 들고도 양쪽으로 걸을 수 있다는 주장이 이 열두 줄입니다.**

놓치기 쉬운 자리 셋을 짚어 둘게요.

- **옛 꼬리를 갱신하는 `tail.xorId ^= id` 가 `=` 이 아니라는 것.** 꼬리는 뒤 이웃이 없어서 그 자리에 `NIL` 이 들어 있고, `^=` 는 그 `NIL` 을 새 id 로 갈아 끼우면서 앞 이웃 정보를 보존합니다. `=` 로 쓰면 앞 이웃이 지워지는데, **원소가 둘일 때까지는 결과가 같아서 드러나지 않습니다.** 4단계의 표가 그 자리입니다.
- **새 노드의 `xorId` 를 `this.#tailId` 로 두고 분기하지 않는 것.** 빈 수열이면 `#tailId` 가 `NIL` 이고, `NIL ^ NIL` 이 곧 `NIL` 이라 첫 노드에도 그대로 맞습니다. `NIL` 을 0 으로 잡은 값어치가 여기서 나옵니다.
- **`#walk` 의 `prevId` 초기값이 `NIL` 이라는 것.** 양쪽 끝 바깥은 둘 다 "없음"이므로 같은 값으로 출발할 수 있고, 그래서 방향 분기가 필요 없습니다.

**성장률로 조건 충족을 확인합니다.** 계약 스위트 축3이 네 시나리오를 회귀 수준(±60%)으로 재고, 붙이기와 `size` 가 $r = 1.00$, 순회 둘이 $r = 4.00$ 입니다 — 각각 `O(1)`, `O(n)` 계약이 요구하는 값과 같습니다. 시간이 아니라 들여다본 노드 수를 세므로, 이 판정은 이 기계의 상수가 아니라 계약을 잽니다.

**사용 조건이 달라지면 다른 구현이 적합합니다.** 계약은 구현을 처방하지 않으므로 여기 실린 것은 계약을 만족하는 여럿 중 하나이고, **가장 싼 것은 아닙니다.** 배열 하나가 네 행을 더 적은 저장으로 지킵니다. 그런데도 이 구현을 정본에 둔 이유는 다음 절에 있습니다.

## TypeScript의 한계와 대체 언어

이 구조의 규약4 등급은 **(나)** 입니다. 계약은 TypeScript로 충족되는데, 그 계약이 왜 이 형태여야 하는지를 뒷받침할 수치를 TypeScript에서 낼 수 없습니다.

**(가)가 아닌 이유.** 계약 네 행이 전부 TypeScript로 표현되고, 실제로 지켜지며, 축3이 그것을 잽니다. 표현조차 안 되는 항목이 하나도 없으므로 (가)가 아닙니다.

**(-)가 아닌 이유.** 이 구조의 존재 이유가 계약 밖에 있고, 그 밖의 것을 여기서 못 잽니다. 셀 수 있는 만큼만 세면 이렇습니다. **슬롯 하나 = 저장되는 값 하나**(수 하나 또는 참조 하나)로 놓습니다.

```text
원소당 저장 슬롯 수

  이상적 XOR 노드 (주소를 정수로 다룰 수 있는 곳)
      value + (prev XOR next)                          = 2
  이중 연결 노드
      value + prev + next                              = 3
                                             ← 여기까지가 이 구조의 주장: 3 → 2

  이 저장소의 XOR 시뮬레이션 (_reference/xorLinkedList.ts)
      노드 객체  { id, value, xorId }                   = 3
      Map 항목   키(수) + 값(참조)                       = 2
                                                        합 5
  TypeScript 이중 연결 노드
      { value, prev, next }                            = 3
                                             ← 실제로 일어난 일: 3 → 5
```

하나를 아끼려다 둘을 더 씁니다. **메모리 이득이 0이 아니라 마이너스입니다.**

그리고 이 수는 **하한입니다.** 해시 표의 여유 칸, 객체 헤더, 정렬 여백을 하나도 세지 않았습니다. 그것들을 세면 격차는 커지지 작아지지 않습니다. 세지 않은 이유가 곧 (나) 판정의 내용입니다 — 객체 하나가 몇 바이트인지, 표가 실제로 몇 칸을 잡고 있는지를 언어가 노출하지 않습니다. 위 표는 소스를 세어 얻은 것이지 측정한 것이 아닙니다.

**Rust로 옮겨도 정직해지지 않습니다.** 규약4 (나)는 Rust 산출물을 강제하지 않고, 이 구조에서는 붙이지 않는 것이 옳습니다. 주소 둘을 XOR 한 정수에서 유효한 포인터를 복원하는 일이 Rust의 엄격 프로버넌스(strict provenance — 포인터가 어느 할당에서 왔는지를 값과 함께 따라다니게 하는 메모리 모델) 아래에서 성립하지 않기 때문입니다. 노출 프로버넌스 API를 거쳐야 하고, 그러면 그 할당들에 대한 최적화 가정이 통째로 풀립니다. Miri 검증도 까다롭습니다. 산출물을 붙여 봐야 *"Rust에서도 안 된다"* 를 더 긴 코드로 다시 말하게 됩니다.

그럼 어디서 성립하느냐 — 세 조건을 **동시에** 통과하는 곳입니다.

- **가비지 컬렉션이 없어야 합니다.** 이동 수집기는 객체를 옮기면서 그것을 가리키는 포인터를 갱신합니다. XOR 값은 포인터로 보이지 않으므로 갱신 대상에서 빠지고, 수집기가 한 번 도는 순간 사슬이 끊깁니다. 관리 런타임에서는 원리적으로 못 씁니다.
- **주소를 정수로 다루는 것이 언어 의미론에 있어야 합니다.** TypeScript에는 주소라는 개념이 없어서 표를 대신 세웠고, 그 표가 곧 위의 +2입니다.
- **계산해 만든 주소를 컴파일러가 유효하다고 인정해야 합니다.** 이것이 프로버넌스이고, 안전을 앞세우는 언어일수록 인정하지 않습니다.

셋을 모두 통과하는 자리는 임베디드 C와 어셈블리입니다. **이 구조는 거기서 태어났고 거기서만 삽니다.** 옮겨 온 언어가 셋 중 하나라도 어기면, 남는 것은 트릭의 모양뿐이고 이득은 남지 않습니다.

**정본이 이 구현인 이유도 여기 있습니다.** 계약을 지키는 가장 싼 구현은 배열인데도 `_reference/` 에 XOR 시뮬레이션을 두었습니다. 이 구조에서 검사받아야 할 것이 계약이 아니라 **주장**이기 때문입니다. 주장이 돌아가는 코드로 있어야 그 대가를 셀 수 있고, 세어 보니 음수였다는 것이 이 가이드의 결론입니다.

## 스스로 점검하기

1. `#walk` 은 방향 인자를 받지 않고 시작점만 바꿔 씁니다. 만약 `toArrayReverse()` 를 `this.toArray().reverse()` 로 바꾸면 두 불변식 중 어느 쪽이 **항상 참이 되어 버리는지**, 그래서 어떤 종류의 결함을 못 잡게 되는지 답해 보세요.
2. `^=` 를 `=` 로 바꾼 결함이 원소 둘까지는 통과했습니다. 이 사실이 "경계 케이스를 손으로 짚어야 한다"로 이어지는 이유를 설명해 보세요. 무작위로 붙이기만 500번 시키는 시험이 이 결함을 몇 번째에 잡을지도 함께 답해 보세요.
3. 3단계에서 배열 하나가 계약 네 행을 전부 지켰습니다. 검증 등급이 `invariant` 가 아니라 `complexity` 가 되려면 계약에 어떤 연산이 하나 더 있어야 할까요? 그 연산을 적어 보고, 그것을 넣은 결과가 여전히 이 구조인지 아니면 `doublyLinkedList` 인지도 판단해 보세요.
4. 6단계의 슬롯 수를 **하한**이라고 적었습니다. 세지 않은 것을 셋 이상 들어 보고, 그것들을 세면 3 → 5 라는 격차가 커지는지 작아지는지 답해 보세요.
