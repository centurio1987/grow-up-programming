# XorLinkedList — 포인터 두 개를 XOR 하나로 접어넣기

## 한눈에 보는 컨셉

이중 연결 리스트가 노드마다 들고 있는 `prev`, `next` 두 포인터를 `xorId` 하나로 압축한 연결 리스트예요. `xorId = prevId ^ nextId`만 저장해두고, 순회 중에 XOR의 자기 역원 성질(`(A ^ B) ^ A = B`)로 "지금 어느 쪽에서 왔는지"만 알면 다음 노드의 id를 그 자리에서 복원합니다. 포인터 필드가 절반으로 줄면서도 정방향·역방향 순회를 그대로 지원하는 게 이 구조의 핵심 효과예요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 XOR 연결 리스트를 떠올리세요.

- 메모리가 극도로 빠듯한 환경(임베디드, 초저사양 장치)에서 **양방향 순회**가 필요하다
- 노드 수가 아주 많아서 포인터 필드 하나(8바이트)를 줄이는 것만으로 유의미한 절감이 생긴다
- 삽입/삭제가 주로 끝(또는 순회 도중 알게 되는 위치)에서만 일어나고, "임의의 노드를 id 하나만 들고 즉시 삭제"할 필요는 없다

노드 하나가 차지하는 포인터 공간을 비교하면 절감 폭이 바로 보입니다.

```text
이중 연결 리스트 노드 하나:        XOR 연결 리스트 노드 하나:
+--------+--------+--------+      +--------+--------+
| value  |  prev  |  next  |      | value  | xorId  |
+--------+--------+--------+      +--------+--------+
   8B       8B       8B              8B       8B
   포인터 몫: 16B                     포인터 몫: 8B (절반)
```

비슷한 용도의 자료구조로 이중 연결 리스트가 있는데, 선택 기준은 이렇습니다: **임의의 노드를 id 하나만 들고 O(1)로 즉시 삭제**해야 한다면 이중 연결 리스트를 쓰세요 — XOR 리스트는 `xorId`만으로는 그 노드의 prev/next를 분리해낼 수 없고, 순회 중에 "방금 어디서 왔는지"를 반드시 함께 들고 있어야 이웃을 알 수 있습니다. 반대로 순회가 주된 용도이고 메모리가 궁핍하다면 XOR 연결 리스트가 유리합니다.

### 문제 사례와 적용 예시

- **임베디드 센서 로그 모듈**: 메모리가 수 KB뿐인 장치에서 로그를 최신 순·과거 순 양쪽으로 읽어야 할 때, `prev`/`next` 대신 `xorId` 하나로 양방향 순회를 구현합니다.
- **초저전력 IoT 장치의 이벤트 큐**: RAM이 킬로바이트 단위인 마이크로컨트롤러에서 이벤트를 순서대로 쌓고 되짚어야 하는 펌웨어 코드.
- **코딩 테스트 맥락**: "이중 연결 리스트 기능을 구현하되 노드당 포인터 필드는 하나만 허용한다"는 제약이 걸린 문제에서 직접 구현 대상이 됩니다.
- **시스템 프로그래밍 고전 트릭의 변형**: C에서 실제 메모리 주소를 XOR하는 원조 기법을, 포인터 산술이 없는 JavaScript/TypeScript에서는 `Map<id, Node>`로 id를 포인터처럼 다뤄 시뮬레이션합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**은 이렇게 정의합니다.

```ts
class XorNode {
  id: number;      // 1 이상의 고유 정수. 0은 "없음"을 뜻하는 센티넬
  value: number;
  xorId: number;   // prevId XOR nextId
}

class XorLinkedList {
  store: Map<number, XorNode>; // id → 노드
  headId: number;               // 0이면 빈 리스트
  tailId: number;               // 0이면 빈 리스트
  count: number;
  nextSeq: number;              // 다음에 발급할 id, 1부터 시작
}
```

지켜야 할 불변식은 네 가지예요.

1. 리스트가 비었는지 여부는 세 값이 함께 결정합니다: $\text{headId}=0 \iff \text{tailId}=0 \iff \text{count}=0$.
2. head 노드는 "이전"이 없으므로 $\text{head.xorId} = 0 \oplus \text{next}(\text{head}) = \text{next}(\text{head})$.
3. tail 노드는 "다음"이 없으므로 $\text{tail.xorId} = \text{prev}(\text{tail}) \oplus 0 = \text{prev}(\text{tail})$.
4. 일반 노드는 양쪽을 모두 접어 넣습니다: $\text{node.xorId} = \text{prev}(\text{node}) \oplus \text{next}(\text{node})$. XOR의 자기 역원 성질 $A \oplus B \oplus A = B$ 덕분에, 순회 중 한쪽(방금 온 방향)만 알아도 반대쪽을 그 자리에서 복원할 수 있습니다.

`append(10)`, `append(20)`, `append(30)`을 차례로 실행한 뒤의 구조를 그려보면 이렇습니다.

```text
store:  {1: {v:10, xorId:2}, 2: {v:20, xorId:2}, 3: {v:30, xorId:2}}
headId=1                                                    tailId=3

  [id=1, v=10]          [id=2, v=20]          [id=3, v=30]
   xorId=0^2=2 -------- xorId=1^3=2 -------- xorId=2^0=2
   (prev=0, next=2)     (prev=1, next=3)     (prev=2, next=0)
```

**액션(연산)**은 문제가 요구하는 4종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `append(value)` | 맨 뒤에 새 노드를 삽입하고 head/tail·이웃의 `xorId`를 갱신 | $O(1)$ |
| `toArray()` | head→tail로 순회하며 XOR로 다음 id를 복원 | $O(n)$ |
| `toArrayReverse()` | tail→head로 순회하며 XOR로 이전 id를 복원 | $O(n)$ |
| `size()` | 내부 카운터 반환 | $O(1)$ |

핵심 연산 두 개를 자세히 볼게요.

**① append — 새 노드가 태어나고 옛 tail이 손을 바꿔 잡는 순간.** `append(30)`을 앞서 만든 2노드 리스트(`10, 20`) 위에서 실행하면:

```text
Before append(30):                              tailId=2
  [id=1, v=10, xorId=2] ---- [id=2, v=20, xorId=1]
   (prev=0, next=2)           (prev=1, next=0)

새 노드 생성: id=3, xorId = tailId ^ 0 = 2 ^ 0 = 2   (prev=2, next=0)
옛 tail 갱신: node(2).xorId = 1 ^ 3 = 2               (prev=1, next=0→3으로 바뀜)

After append(30):                               tailId=3
  [id=1, v=10, xorId=2] --- [id=2, v=20, xorId=2] --- [id=3, v=30, xorId=2]
   (prev=0, next=2)           (prev=1, next=3)           (prev=2, next=0)
```

수식으로 정리하면: 새 노드는 $\text{new.xorId} = \text{tailId} \oplus 0$, 옛 tail은 $\text{tail.xorId} \mathrel{\oplus}= \text{new.id}$ 한 번으로 "next=0"이 "next=new.id"로 정확히 바뀝니다 — $0 \oplus x = x$이기 때문에 XOR을 한 번 더 먹이는 것만으로 없던 값이 그대로 채워져요.

**② toArray — 온 길을 등에 지고 다음 칸을 여는 순회.** 위 3노드 리스트에서 `toArray()`를 실행하면:

```text
prevId=0, currId=1  → node(1).xorId=2 → nextId = 2^0 = 2  → "10" 수집, prevId=1, currId=2
prevId=1, currId=2  → node(2).xorId=2 → nextId = 2^1 = 3  → "20" 수집, prevId=2, currId=3
prevId=2, currId=3  → node(3).xorId=2 → nextId = 2^2 = 0  → "30" 수집, prevId=3, currId=0 (종료)

결과: [10, 20, 30]
```

### 왜 모순 없이 작동하는가

**불변식이 계속 보존되는 이유**는 귀납으로 확인할 수 있습니다. 빈 리스트(base case)는 `headId=tailId=count=0`이라 불변식 1이 자명하게 성립합니다. `append`가 불변식을 보존한다고 가정하고 한 번 더 `append`를 실행해보면: 새 노드는 태어나자마자 `xorId = tailId ^ 0`으로 설정되어 불변식 3(자신이 새 tail이므로 next=0)을 만족합니다. 옛 tail은 `xorId ^= newId`로 갱신되는데, 옛 tail의 원래 xorId는 불변식 3에 의해 `prevOfOldTail ^ 0`이었으니 여기에 `newId`를 XOR하면 정확히 `prevOfOldTail ^ newId`가 되어 불변식 4(이제는 중간 노드, next=newId)로 자연스럽게 옮겨갑니다. 리스트가 처음 비어 있었다면 `headId`도 새 노드로 설정되어 불변식 2까지 함께 성립하고요. 따라서 몇 번을 `append`하든 불변식은 깨지지 않습니다.

**여기서 헷갈리기 쉬운 포인트는 `xorId` 값 자체를 "이웃의 id"로 착각하는 것입니다.** 위 3노드 예시에서 `node(2).xorId = 2`인데, 이 값 `2`가 마치 "다음 노드는 id=2"라고 가리키는 것처럼 보이기 쉬워요. 하지만 실제로는 `1 ^ 3 = 2`가 우연히 `2`라는 숫자로 계산된 것일 뿐, node(2)의 진짜 이웃은 id=1(prev)과 id=3(next)입니다. `xorId` 하나만 봐서는 절대 prev와 next를 분리할 수 없고, 반드시 "방금 어느 id에서 왔는지(prevId)"를 순회 컨텍스트로 들고 있어야만 `nextId = xorId ^ prevId`로 진짜 다음 id를 복원할 수 있습니다.

잠깐, 확인 하나만 해볼까요? node(2)의 `xorId=2`가 node(2) 자신의 `id=2`와 같은 숫자인 건 필연일까요, 우연일까요? — **우연입니다.** `1 ^ 3`을 계산하다 보니 마침 `2`가 나온 것뿐이고, 일반적으로 `xorId`와 자기 `id`는 아무 관계가 없습니다. 다른 값(예: 15, 27, 8)으로 3개를 append해보면 바로 확인할 수 있어요.

엣지 케이스를 점검해봅니다.

```text
빈 리스트에서 toArray()/toArrayReverse() → []  (headId=tailId=0이라 while 루프에 진입조차 안 함)
빈 리스트에 첫 append(v)                  → headId=tailId=새id, 새 노드의 xorId=0^0=0
단일 노드 리스트                          → toArray()와 toArrayReverse() 둘 다 [value] (순서 문제 없음)
value에 0 또는 음수                       → id는 별도 카운터(nextSeq)로 발급되므로 value와 절대 혼동되지 않음
```

## 아이디어를 코드로 옮기기

**원형(naive) 아이디어**는 이중 연결 리스트 그대로예요 — 노드마다 `prev`, `next` 두 필드를 따로 둡니다.

```ts
class DoublyNode {
  value: number;
  prev: DoublyNode | null = null;
  next: DoublyNode | null = null;
  constructor(value: number) {
    this.value = value;
  }
}
```

이걸 XOR 하나로 줄이려는 **개선 시도**에서 가장 흔한 실수는 순회 시 "지금 위치를 갱신하는 시점"을 착각하는 것입니다. 아래는 `prevId`를 먼저 갱신해버린(순서가 뒤바뀐) 잘못된 버전이에요.

```ts
// 잘못된 순서 — prevId를 currId 처리 전에 미리 갱신해버림
toArrayWrongOrder(): number[] {
  const result: number[] = [];
  let prevId = 0;
  let currId = this.headId;
  while (currId !== 0) {
    const node = this.store.get(currId)!;
    result.push(node.value);
    prevId = currId;                    // ← 여기서 먼저 갱신해버리면
    const nextId = node.xorId ^ prevId; // 이미 바뀐 prevId를 써버린다
    currId = nextId;
  }
  return result;
}
```

값 `10, 20, 30`이 담긴 리스트(앞서 본 것과 동일: `xorId`는 세 노드 모두 `2`)에 이 버전을 돌리면 실제로 이렇게 망가집니다.

```text
prevId=0, currId=1 → "10" 수집 → prevId를 1로 먼저 갱신 → nextId = node(1).xorId(2) ^ prevId(1) = 3
prevId=1, currId=3 → "30" 수집 → prevId를 3으로 먼저 갱신 → nextId = node(3).xorId(2) ^ prevId(3) = 1
prevId=3, currId=1 → "10" 다시 수집 → ... (1과 3 사이를 영원히 왕복)

결과: [10, 30, 10, 30, 10, 30, ...]  ← id=2(값 20)는 한 번도 방문되지 않고 무한 루프
```

`nextId`를 계산하기 **전에** `prevId`를 이미 바꿔버렸기 때문에, XOR 공식이 "방금 온 방향"이 아니라 "지금 있는 위치"를 기준으로 계산돼 버립니다. 이 실수를 고친 **최종 구현**은 다음과 같습니다.

```ts
class XorNode {
  id: number;
  value: number;
  /** prevId XOR nextId */
  xorId: number;

  constructor(id: number, value: number) {
    this.id = id;
    this.value = value;
    this.xorId = 0;
  }
}

class XorLinkedList {
  private store = new Map<number, XorNode>();
  private headId = 0; // 0 = null
  private tailId = 0;
  private count = 0;
  private nextSeq = 1; // 다음에 발급할 id (1부터)

  append(value: number): void {
    const id = this.nextSeq++;
    const node = new XorNode(id, value);
    node.xorId = this.tailId ^ 0; // prev=tail, next=null(0)

    if (this.tailId !== 0) {
      const tail = this.store.get(this.tailId);
      if (tail === undefined) throw new Error("tail node missing");
      tail.xorId = tail.xorId ^ id; // 옛 tail의 next를 새 노드로 갱신
    } else {
      this.headId = id; // 빈 리스트였다면 head도 새 노드
    }

    this.store.set(id, node);
    this.tailId = id;
    this.count++;
  }

  toArray(): number[] {
    const result: number[] = [];
    let prevId = 0;
    let currId = this.headId;
    while (currId !== 0) {
      const node = this.store.get(currId);
      if (node === undefined) throw new Error("node missing");
      result.push(node.value);
      const nextId = node.xorId ^ prevId; // ① 먼저 다음 id를 복원하고
      prevId = currId;                    // ② 그다음 "온 길"을 갱신한다
      currId = nextId;
    }
    return result;
  }

  toArrayReverse(): number[] {
    const result: number[] = [];
    let nextId = 0;
    let currId = this.tailId;
    while (currId !== 0) {
      const node = this.store.get(currId);
      if (node === undefined) throw new Error("node missing");
      result.push(node.value);
      const prevId = node.xorId ^ nextId;
      nextId = currId;
      currId = prevId;
    }
    return result;
  }

  size(): number {
    return this.count;
  }
}
```

가장 중요한 부분은 `toArray`의 이 두 줄입니다.

```ts
const nextId = node.xorId ^ prevId; // ① 먼저 다음 id를 복원하고
prevId = currId;                    // ② 그다음 "온 길"을 갱신한다
```

- **순서가 생명입니다.** ①에서 아직 갱신 전인 `prevId`(= 방금 온 방향)를 써서 `nextId`를 복원한 다음, ②에서 비로소 "지금 위치"를 새 `prevId`로 저장해야 합니다. 순서를 바꾸면 바로 앞에서 본 `[10, 30, 10, 30, ...]` 무한 루프가 재현됩니다.
- **`append`에서는 새 노드 생성 직후 옛 tail의 `xorId`를 반드시 갱신**해야 합니다. 이 줄(`tail.xorId = tail.xorId ^ id`)을 빼먹으면 `size()`는 정상적으로 3을 반환하는데도 `toArray()`는 `[10]`만 반환합니다 — head 노드의 `xorId`가 계속 `0`으로 남아 있어서 첫 순회에서 곧바로 `nextId=0`이 나와버리기 때문이에요.
- **`store.get`이 `XorNode | undefined`를 반환**하므로(TypeScript strict 모드), `!` 단언 대신 명시적으로 `undefined` 체크를 하는 편이 안전합니다.

> 새 노드를 만든 직후엔 다음 id부터 복원하고, "온 길" 갱신은 그다음이다 — 순서를 바꾸면 길을 잃는다.

## 실행 시각화

`append(10)`, `append(20)`, `append(30)`을 차례로 실행한 뒤 `toArray()`와 `toArrayReverse()`를 호출하는 고정 입력으로 살펴봅니다. 실제 반환값은 `toArray() → [10, 20, 30]`, `toArrayReverse() → [30, 20, 10]`이고(위 코드로 직접 실행해 확인한 값입니다), 각 프레임의 `array` 패널은 그 시점까지 쌓인 값의 배열을, `highlight`는 이번 단계에서 새로 계산된 노드를, `marked`는 이번 단계에서 `xorId`가 갱신된 기존 노드를 나타냅니다.

> 대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.

export const steps = [
  {
    title: "초기 상태 (빈 리스트)",
    detail: "headId=0, tailId=0, size=0. ID 0은 null 센티넬.",
    array: [],
    highlight: [],
    marked: [],

정리하면, XOR 연결 리스트는 **"한쪽만 알아도 반대쪽을 복원할 수 있다"**는 XOR의 자기 역원 성질 하나로 포인터 필드를 절반으로 줄입니다. `append`는 새 노드를 tail 자리에 꽂고 옛 tail의 `xorId`를 한 번 갱신하는 것만으로 끝나 목표대로 $O(1)$이고, `toArray`/`toArrayReverse`는 "온 길(prevId 또는 nextId)"을 등에 지고 한 칸씩 전진하며 다음 자리를 그 자리에서 계산하므로 각각 $O(n)$입니다. `size`는 별도 카운터를 두었으니 $O(1)$이고요 — 애초에 목표했던 복잡도를 모두 그대로 달성하면서, 노드당 메모리는 이중 연결 리스트의 절반(포인터 8바이트)으로 줄어듭니다. 다만 이 절감은 공짜가 아니라서, 순회 컨텍스트(prevId 또는 nextId) 없이 임의의 노드 하나만 들고 그 이웃을 알아내는 것은 불가능하다는 트레이드오프를 항상 기억해야 합니다.
