# XOR 연결 리스트 — 이웃 id 두 개를 XOR 한 값 하나로 두 방향을 순회한다

## 파트 1 — 계약에서 동작하는 코드까지

XOR 연결 리스트가 약속하는 것을 먼저 한 장으로 보고, 그 약속을 가장 단순한 구현들이 어디까지 지키는지
수치로 확인한 다음, 노드마다 이웃 정보를 값 하나로 줄이는 설계에 이르러 실제로 동작하는 코드를 한 조각씩
만듭니다.

### 전체 컨셉

XOR 연결 리스트는 **뒤 끝에만 원소를 붙이고, 담긴 전체를 앞→뒤와 뒤→앞 두 방향으로 읽어 주는** 수열입니다.
연산은 넷이고, 하나는 붙이는 일이고 셋은 상태를 바꾸지 않고 읽는 일이에요.

```text
  append(value)      뒤 끝에 붙인다          [ 10  0  30 ]  ← append(30)
  toArray()          앞 끝부터 전부 읽는다    → [10, 0, 30]
  toArrayReverse()   뒤 끝부터 전부 읽는다    → [30, 0, 10]
  size()             원소가 몇 개인가         → 3
```

두 방향으로 읽으려면 원소마다 앞 이웃과 뒤 이웃을 알아야 합니다. 흔한 설계인 이중 연결 리스트는 노드마다
**이웃을 가리키는 값 둘**을 둬요. 이 글이 만드는 설계는 그 둘을 **값 하나로 줄입니다.** 노드마다 번호
`id` 를 1 부터 차례로 매기고, 앞 이웃 id 와 뒤 이웃 id 를 비트 XOR 한 값 `x` 하나만 저장해요. 이웃이 없는
끝 바깥은 번호 0 으로 적고, 그 번호를 `NIL` 이라고 부릅니다.

비트 XOR(`^`)은 두 수를 2진수로 놓고 자리마다 두 비트가 다르면 1, 같으면 0 을 적는 연산이에요. 그래서 같은
수를 두 번 섞으면 0 이 되고, 0 을 섞으면 그대로입니다.

```text
1 ^ 3 = 01 ^ 11 = 10 = 2        2 ^ 1 = 10 ^ 01 = 11 = 3        2 ^ 2 = 0        2 ^ 0 = 2

값 10 · 20 · 30 을 차례로 붙인 뒤
  id             1           2           3
  값             10          20          30
  앞 이웃 id     0 (NIL)     1           2
  뒤 이웃 id     2           3           0 (NIL)
  x = 앞 ^ 뒤    0 ^ 2 = 2   1 ^ 3 = 2   2 ^ 0 = 2
```

세 노드의 `x` 가 모두 2 입니다. **저장된 값만 봐서는 어느 쪽이 앞인지 알 수 없어요.** 방향을 정하는 것은
저장된 값이 아니라 「직전에 어느 노드를 읽었는가」입니다. 직전에 읽은 노드 id 를 `prev` 라 하면, `x` 에는
`prev` 와 반대쪽 이웃 id 가 섞여 있으니 `x ^ prev` 가 반대쪽 이웃 id 가 돼요.

```text
앞 끝 id 1 에서 출발    prev 0   x 2   다음 = 2 ^ 0 = 2
                        prev 1   x 2   다음 = 2 ^ 1 = 3
                        prev 2   x 2   다음 = 2 ^ 2 = 0 = NIL   끝
뒤 끝 id 3 에서 출발    prev 0   x 2   다음 = 2 ^ 0 = 2
                        prev 3   x 2   다음 = 2 ^ 3 = 1
                        prev 2   x 2   다음 = 2 ^ 2 = 0 = NIL   끝
```

같은 식이 출발점만 바꾸면 반대 방향으로 갑니다. 그래서 두 순회가 코드 한 벌을 나눠 써요. 붙일 때는 새 노드의
`x` 를 옛 꼬리 id 로 두고, 옛 꼬리의 `x` 에 새 id 를 한 번 XOR 합니다. 옛 꼬리의 뒤 이웃 자리에 있던 `NIL` 이
0 이라서, 그 한 번이 `NIL` 을 새 id 로 바꾸는 일이 돼요.

| 연산 묶음 | 한 번 부를 때 하는 일 | 여러 번 부른 평균 |
| --- | --- | --- |
| 붙이기 | 노드 하나를 만들고, 원소가 있었으면 옛 꼬리 노드 하나를 찾아 고친다 | 원소 수와 무관한 상수 |
| 두 방향 순회 | 원소마다 노드 하나를 찾아 읽는다 | 원소 수에 비례 |
| 개수 | 세어 둔 수를 읽는다 | 원소 수와 무관한 상수 |

이 설계가 생긴 이유는 시간이 아니라 **메모리**입니다. 노드마다 이웃 값 둘을 하나로 줄이는 것이 목표였고,
그 목표는 주소를 정수로 다룰 수 있는 언어에서만 성립해요. 이 글의 정본은 TypeScript 라 주소 대신 `id` 를
쓰고, `id` 로 노드를 찾는 표를 따로 둡니다.

```text
주소를 정수로 다루는 언어    노드 = 값 + x                    x = 앞 노드 주소 ^ 뒤 노드 주소
이 글의 TypeScript 정본      노드 = id + 값 + x  그리고 표   x = 앞 노드 id ^ 뒤 노드 id,  표: id → 노드
```

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **비트 XOR 의 세 성질.** `a ^ a = 0` 이고, `a ^ 0 = a` 이고, 순서와 묶음을 바꿔도 결과가 같습니다. 셋을
  합치면 `(a ^ b) ^ a = b` 예요 — 둘을 섞은 값에서 하나를 알면 나머지가 나옵니다. 흐릿하면 같은 성질로
  문제를 푸는 [`singleNumberXor` 가이드](../../../algorithms/bit-manipulation/singleNumberXor/singleNumberXor-guide.md)를
  먼저 보세요.

```text
a = 1 (01)    b = 3 (11)
a ^ b         = 01 ^ 11 = 10 = 2
(a ^ b) ^ a   = 10 ^ 01 = 11 = 3 = b
(a ^ b) ^ b   = 10 ^ 11 = 01 = 1 = a
```

- **연결 리스트.** 노드가 값과 이웃을 가리키는 정보를 함께 두고, 그 정보를 따라가며 순서대로 읽는 수열입니다.
  이웃 정보가 한 방향이면 [`singlyLinkedList`](../singlyLinkedList/singlyLinkedList-guide.mdx), 두 방향이면
  [`doublyLinkedList`](../doublyLinkedList/doublyLinkedList-guide.mdx) 가이드에 있어요.
- **`Map` 으로 키 하나에 값 하나를 찾는 일.** 이 글은 표에서 한 번 찾는 일을 비용 1 로 셉니다. 정본의
  계측 규약이 그렇게 정했고, 정본 [`_reference/xorLinkedList.ts`](./_reference/xorLinkedList.ts) 머리 주석이
  이유를 적었어요 — 주소 하나를 따라가던 자리를 표 한 번 찾기가 대신하기 때문입니다.

```text
이 글이 다루는 것          뒤로 붙이고, 두 방향으로 전부 읽고, 개수를 묻는 네 연산
이 글이 다루지 않는 것     가운데에 넣거나 빼기          → doublyLinkedList
                          번호로 원소 하나를 읽기        → dynamicArray
                          앞 끝에서 넣고 빼기            → deque
```

- 칸 수를 두 배로 늘리는 배열은 [`dynamicArray` 가이드](../dynamicArray/dynamicArray-guide.mdx)가, 양 끝에서
  넣고 빼는 구조는 [`deque` 가이드](../deque/deque-guide.md)가 다룹니다. 이 글은 배열을 비교 상대로만 씁니다.

### 설계 상세 — XOR 연결 리스트에 이르는 과정

**먼저 계약을 읽습니다.** 자료구조는 문제를 고정하지 않아요 — 무엇을 지켜야 하는지가 이미
[`xorLinkedList.ts`](./xorLinkedList.ts) 헤더에 계약으로 적혀 있습니다. 여기서 볼 것은 그 계약이 **무엇을
막는지**와 **조건 하나를 풀면 무엇이 되는지**예요.

```text
계약에 없는 것     가운데에 넣기 · 가운데에서 빼기 · 번호로 읽기 · 값으로 찾기 · 공간 비용
                   └ 공간 비용이 없다는 것을 기억해 둔다. 이 구조는 공간 때문에 생겼는데, 계약은 그것을 약속하지 않는다

조건 하나를 풀면
  한 방향으로만 읽어도 되면                → 단일 연결 리스트
  두 방향이 서로 다른 수열을 읽어도 되면   → 한 수열이 아니라 수열 둘
  붙이기 비용이 원소 수에 비례해도 되면    → 뒤 끝을 모르는 수열
```

이 글이 끝까지 쓰는 기호는 아홉이에요. 여기서 정하고 뒤에서 뜻을 바꾸지 않습니다.

| 기호 | 무엇인가 | 코드에서 |
| --- | --- | --- |
| `n` | 원소 수. 비용을 잴 때는 같은 `n` 으로 붙이기 횟수도 정한다 — 붙이기만 `n` 번이면 원소가 `n` 개다 | — |
| `id` | 노드마다 1 부터 차례로 매기는 번호. 한 번 쓴 번호를 다시 쓰지 않는다 | `id` · `this.#nextId` |
| `NIL` | 이웃이 없는 자리를 뜻하는 번호 0 | `NIL` |
| `x` | 노드가 저장하는 값. 앞 이웃 id `^` 뒤 이웃 id | `xorId` |
| `head` | 앞 끝 노드의 id. 비었으면 `NIL` | `this.#headId` |
| `tail` | 뒤 끝 노드의 id. 비었으면 `NIL` | `this.#tailId` |
| `count` | 지금 담긴 원소 수 | `this.#count` |
| `C(n)` | 크기 `n` 에서 잰 연산 한 번당 비용. 붙이기는 평균, 순회와 개수는 가장 큰 값 | 계약 스위트 축3 |
| `r` | 성장률 `C(4n) / C(n)` — `n` 을 네 배로 키웠을 때 연산당 비용이 몇 배가 되는가 | 계약 스위트 축3 |

순회에서만 쓰는 이름 둘은 그 자리에서 정합니다 — 직전에 읽은 노드 id `prev` 와 지금 읽는 노드 id `curr`
예요. 정본은 둘을 `prevId` · `currId` 로 적습니다. 비용의 단위는 **표에서 노드 하나를 찾을 때 1, 새 노드를 하나 만들 때 1** 입니다.

**자료구조에서는 입력 크기 하나가 비용을 정하지 않습니다.** 어떤 연산이 어떤 순서로 섞여 들어오는가가
정해요. 계약 스위트가 재는 호출 패턴은 넷이고, 이 글도 그 넷으로 구현을 시험합니다.

```text
뒤로만 붙이기               append 를 n 번
붙인 뒤 앞→뒤로 읽기        append 를 n 번 → toArray 를 3 번
붙인 뒤 뒤→앞으로 읽기      append 를 n 번 → toArrayReverse 를 3 번
붙인 뒤 개수 묻기           append 를 n 번 → size 를 n 번
```

**가장 단순한 구현부터 세웁시다.** 노드도 이웃도 없이 배열 하나를 둡니다. 네 연산이 한 줄씩이면 끝나요.

```ts
class OneArray {
  #a: number[] = [];
  append(value: number): void { this.#a.push(value); }
  toArray(): number[] { return [...this.#a]; }
  toArrayReverse(): number[] { return [...this.#a].reverse(); }
  size(): number { return this.#a.length; }
}
```

이 구현을 계약 스위트의 네 시나리오에 넣고, 정본과 같은 뜻의 단위(**원소 하나를 건드릴 때마다 1**)로 셉니다.
`push` 가 속에서 칸을 늘리는 일도 세려고, 배열이 칸 8 개로 시작해 가득 차면 두 배로 늘리고 원소를 옮긴다고
두었어요.

<!--proof:array-rates-->

```text
시나리오가 부르는 연산   상한   n = 1,024   n = 4,096      r   판정
append                   O(1)        1.99        2.00   1.00   통과
toArray                  O(n)    1,024.00    4,096.00   4.00   통과
toArrayReverse           O(n)    1,024.00    4,096.00   4.00   통과
size                     O(1)        1.00        1.00   1.00   통과
```

**네 줄 모두 통과합니다.** 붙이기와 개수는 `n` 을 네 배로 키워도 연산당 비용이 그대로이고, 두 순회는 네 배가
됩니다. 순회는 원소 `n` 개를 돌려주는 연산이라 어떤 구현에서도 호출 하나가 `n` 에 비례하므로, 계약이 요구하는
값이 바로 4.00 이에요.

```text
r = 1.00   n 을 네 배로 키워도 연산당 비용이 그대로   → 원소 수와 무관하다는 계약이 요구하는 값
r = 4.00   n 을 네 배로 키우면 연산당 비용도 네 배    → 원소 수에 비례한다는 계약이 요구하는 값
```

가장 단순한 구현이 계약을 다 지킵니다. 계약 헤더가 이 구조의 검증 등급을 `invariant` 로 적은 이유가 이
사실이에요 — 상한을 넘기는 단순한 구현을 적을 수 없으니 성장률을 가려내는 등급이 아니라, 불변식을 지키는지를
보는 등급입니다.

```text
검증 등급을 가르는 물음     계약의 상한을 넘기는 단순한 구현이 있는가
  있다   → complexity       성장률로 그 구현을 가려낸다
  없다   → invariant        불변식을 지키는지를 본다      ← 배열 하나가 네 연산을 다 지켰다
```

**시간 쪽에서 계약이 요구하는 것은 하나뿐입니다 — 뒤 끝을 기억하는 것.** 노드를 이어 붙이되 뒤 끝을 안
들고, 붙일 때마다 앞 끝에서부터 뒤 끝을 찾으면 이렇게 됩니다.

<!--proof:no-tail-rates-->

```text
뒤로만 n 번 붙이기 — 뒤 끝을 안 드는 사슬

n       연산당 들여다본 노드   r = C(4n)/C(n)
1,024                 512.50                —
4,096               2,048.50             4.00

계약 스위트 판정: 실패 (O(1) 상한의 기대 r = 1.00, 허용 ±60%)
```

`n` 을 네 배로 키우니 붙이기 한 번에 들여다본 노드도 네 배가 됐어요. 붙일 때마다 그때까지 붙인 노드를 전부
지나가기 때문입니다. 뒤 끝 노드의 id 하나만 들고 있으면 이 비용이 사라지고, 계약이 시간으로 요구하는 것은
거기까지예요.

```text
뒤 끝을 안 들 때    k 번째 붙이기   앞 노드 k − 1 개를 지나 뒤 끝을 찾고 + 새 노드 1  = k
                    n 번의 합       1 + 2 + … + n = n(n + 1) / 2      연산당 (n + 1) / 2   n = 1,024 이면 512.50
뒤 끝 id 를 들 때   k 번째 붙이기   옛 꼬리 1 + 새 노드 1                              = 2 이하
```

**그러면 무엇이 노드와 이웃 정보를 부를까요?** 배열이 네 연산을 다 지키니 시간은 이유가 되지 못합니다. 이
구조에 붙어 온 주장은 공간이에요 — 이중 연결 리스트가 노드마다 이웃 값 둘을 두는 자리에 하나만 둔다는 것.
그 주장이 뜻을 가지려면 두 가지가 먼저 되어야 합니다. 값 하나로 **정말 두 방향을 순회할 수 있는가**, 그리고
붙일 때 그 값을 **원소 수와 무관한 비용으로 유지할 수 있는가**. 값 10 · 20 · 30 을 붙인 수열로 시작합니다.

<!--proof:doubly-links-->

```text
id   값   앞 이웃 id   뒤 이웃 id   x = 앞 ^ 뒤
1    10            0            2     0 ^ 2 = 2
2    20            1            3     1 ^ 3 = 2
3    30            2            0     2 ^ 0 = 2
```

가운데 두 열이 이중 연결 리스트가 노드마다 드는 것이고, 마지막 열이 XOR 연결 리스트가 드는 것입니다. 세 노드가
모두 2 를 들고 있어서, 이 열 하나만으로는 어느 노드가 앞 끝인지도 어느 쪽으로 가야 하는지도 정해지지 않아요.
여기까지가 준비이고, 이제 물음은 「노드 하나를 읽고 다음 id 를 얻는 데 무엇이 더 필요한가」 하나로
정리됩니다.

```text
다음 id 를 얻는 데 드는 것
  이중 연결 리스트   노드 하나 찾기 → next(또는 prev) 칸 읽기
  XOR 연결 리스트    노드 하나 찾기 → x 칸 읽기 → 그리고 무엇이 더?
```

**두 방향을 실제로 순회해 봅시다.** 같은 노드 표를 앞 끝 id 1 과 뒤 끝 id 3 에서 한 번씩 출발하고, 출발할
때 `prev` 를 `NIL` 로 둡니다. 걸음마다 다음 id 를 `x ^ prev` 로 얻고, 옮기기 전에 지금 노드 id 를 `prev` 에
넣어요.

<!--proof:two-directions-->

```text
출발        prev   curr   x(curr)   다음 = x ^ prev      담은 값
앞 끝에서      0      1         2   2 ^ 0 = 2               [10]
앞 끝에서      1      2         2   2 ^ 1 = 3            [10 20]
앞 끝에서      2      3         2   2 ^ 2 = 0         [10 20 30]
뒤 끝에서      0      3         2   2 ^ 0 = 2               [30]
뒤 끝에서      3      2         2   2 ^ 3 = 1            [30 20]
뒤 끝에서      2      1         2   2 ^ 2 = 0         [30 20 10]
```

두 출발 모두 세 걸음에 끝났고, 걸음마다 노드를 한 번 찾았습니다. 이중 연결 리스트도 세 걸음에 세 번 찾아요.
**둘째 줄과 다섯째 줄을 견줘 보세요.** 같은 id 2 노드의 같은 `x` 2 에서, 앞 끝에서 온 순회는 `prev` 가 1 이라
3 을 얻었고 뒤 끝에서 온 순회는 `prev` 가 3 이라 1 을 얻었습니다. 관찰은 이것입니다 — **직전 id 하나를 들고
걸으면 `x` 에서 반대쪽 이웃이 나오고, 걸음마다 드는 일은 이중 연결 리스트와 같다.**

```text
앞 끝에서 온 순회    id 2 의 x = 1 ^ 3,  prev = 1  →  1 ^ 3 ^ 1 = 3   뒤 이웃
뒤 끝에서 온 순회    id 2 의 x = 1 ^ 3,  prev = 3  →  1 ^ 3 ^ 3 = 1   앞 이웃
```

**이제 개념을 정의합니다.** 노드마다 저장하는 값과 순회에서 다음 id 를 얻는 규칙은 이렇습니다.

```text
x(id)  = 앞 이웃 id ^ 뒤 이웃 id          끝 바깥의 이웃은 NIL = 0
다음   = x(curr) ^ prev                    prev 는 직전에 읽은 노드 id, 출발할 때는 NIL
```

규칙이 끝에서도 맞는지 값으로 확인합니다. 앞 끝 노드는 앞 이웃이 `NIL` 이라 `x = 0 ^ 뒤 이웃 = 뒤 이웃` 이고,
출발할 때 `prev` 가 `NIL` 이라 `x ^ 0` 이 곧 뒤 이웃이에요. 뒤 끝 노드에 이르면 `x = 앞 이웃 ^ 0` 이고 `prev`
가 바로 그 앞 이웃이니, `x ^ prev = 0` 이 되어 다음이 `NIL` 입니다. **반복은 `curr` 가 `NIL` 이 되는 순간에만
멈추므로 뒤 끝 노드를 읽은 직후에 정확히 멈추고, 그 전에는 한 노드도 건너뛰지 않아요** — 걸음마다 다음 id 가
실제 이웃이기 때문입니다.

```text
출발   앞 끝 노드   x = NIL ^ 뒤 이웃 = 뒤 이웃   prev = NIL       → 다음 = 뒤 이웃 ^ 0         = 뒤 이웃
중간   노드 c       x = 앞 이웃 ^ 뒤 이웃         prev = 앞 이웃   → 다음 = x ^ 앞 이웃         = 뒤 이웃
끝     뒤 끝 노드   x = 앞 이웃 ^ NIL = 앞 이웃   prev = 앞 이웃   → 다음 = 앞 이웃 ^ 앞 이웃   = NIL       멈춘다
```

**상태가 붙이기에서도 유지되는지 값으로 확인합시다.** 쉬운 경우는 빈 수열에 붙일 때예요 — 새 노드가 앞 끝이자
뒤 끝이라 두 이웃이 모두 `NIL` 이고 `x` 는 0 입니다. 불안한 경우는 **원소가 있을 때**입니다. 새 노드만이 아니라
옛 꼬리의 `x` 도 바뀌어야 해요 — 옛 꼬리는 뒤 이웃이 `NIL` 이었다가 새 노드가 됩니다. 값 10 · 20 · 30 · 40 을
차례로 붙이며 두 노드의 `x` 를 적었어요.

<!--proof:append-states-->

```text
호출         새 id   새 노드의 x   옛 꼬리의 x              head   tail
append(10)       1             0   빈 수열 — 옛 꼬리 없음      1      1
append(20)       2             1   id 1: 0 ^ 2 = 2             1      2
append(30)       3             2   id 2: 1 ^ 3 = 2             1      3
append(40)       4             3   id 3: 2 ^ 4 = 6             1      4
```

새 노드의 `x` 는 늘 그때의 `tail` 이에요. 새 노드의 뒤 이웃은 아직 `NIL` 이라 `앞 이웃 ^ 0 = 앞 이웃` 이기
때문입니다. 첫 줄은 `tail` 이 `NIL` 이라 0 이 들어갔고, 따로 분기할 필요가 없었어요. 옛 꼬리의 `x` 는
`앞 이웃 ^ NIL` 이었으니, 새 id 를 한 번 XOR 하면 `앞 이웃 ^ 새 id` 가 되어 정의와 같아집니다. 넷째 줄의
id 3 이 `2 ^ 4 = 6` 으로, 앞 이웃 2 와 뒤 이웃 4 를 섞은 값이 됐어요.

```text
옛 꼬리의 x          앞 이웃 ^ NIL      = 앞 이웃 ^ 0        = 앞 이웃
새 id 를 XOR 한 뒤   앞 이웃 ^ 0 ^ 새 id                    = 앞 이웃 ^ 새 id    ← 정의 그대로
붙이기 한 번이 고치는 노드   새 노드 하나 · 옛 꼬리 하나   → 원소 수와 무관하다
```

한 가지를 이 자리에서 정해 둡니다. **`id` 는 0 이 될 수 없어요.** 0 은 `NIL` 이 쓰는 번호라, 어떤 노드가 0 번을
받으면 그 노드와 「이웃 없음」이 같은 수가 됩니다. 그래서 번호를 1 부터 매겨요.

```text
어떤 노드가 id 0 을 받으면
  그 노드가 뒤 끝일 때   tail = 0          → 빈 수열의 tail = NIL 과 같은 값이다
  이웃의 x 에 섞일 때    x ^ 0 = x         → 섞어도 x 가 안 바뀌어 「이웃 없음」과 같다
```

마지막으로 지금까지 세운 설계를 모두 계약 스위트의 네 시나리오에 넣습니다. 칸마다 `n = 4,096` 과 `n = 1,024`
의 비율 `r` 과 판정을 적었어요. 이중 연결 리스트는 같은 단위(노드를 찾거나 만들 때 1)로 셌습니다.

<!--proof:designs-rates-->

```text
설계                       append     toArray   toArrayReverse        size
배열 하나               1.00 통과   4.00 통과        4.00 통과   1.00 통과
뒤 끝을 안 드는 사슬    4.00 실패   4.00 통과        4.00 통과   1.00 통과
이중 연결 리스트        1.00 통과   4.00 통과        4.00 통과   1.00 통과
XOR 연결 리스트(정본)   1.00 통과   4.00 통과        4.00 통과   1.00 통과
```

```text
XOR 연결 리스트 한 벌이 나왔다
  노드마다 id · 값 · x = 앞 이웃 id ^ 뒤 이웃 id 를 둔다. 끝 바깥은 NIL = 0, id 는 1 부터
  붙이면 새 노드의 x ← tail, 옛 꼬리의 x ← x ^ 새 id, tail ← 새 id
  순회는 prev ← NIL 에서 출발해 다음 = x(curr) ^ prev, 옮기기 전에 prev ← curr
      └ 뒤 끝을 안 드는 사슬의 붙이기 r = 4.00 이 1.00 이 되고, 네 시나리오 판정이 배열·이중 연결 리스트와 같다
```

**시간으로는 세 설계가 구별되지 않습니다.** 계약 스위트는 공간을 재지 않으므로, 이 구조가 생긴 이유인 「이웃
값 하나를 줄인다」는 여기 표 어디에도 없어요. 그 주장이 TypeScript 에서 성립하는지는 슬롯을 세어 따로 답해야
합니다.

### 수행으로 알아보는 자료구조 — 10 · 0 · 30 을 붙이고 같은 노드 표를 두 방향으로 읽는다

설계를 세웠으니 이제 **실제로 동작하는 코드**로 옮깁니다. 호출 열 하나를 잡고 끝까지 가되, 조각마다 그 조각만
실행해서 나온 값을 확인하고 넘어가요.

```ts
const list = new XorLinkedList();
// T1 · T2    빈 수열에서   toArray() · size()
// T3~T5      append(10) · append(0) · append(30)
// T6         size()
// T7~T9      toArray()          노드 하나를 읽을 때마다 한 걸음
// T10~T12    toArrayReverse()   마지막 걸음이 [30, 0, 10] 을 돌려준다
```

여덟 번을 왜 이렇게 골랐을까요? **네 연산이 전부 한 번 이상 나오고**, 반복을 한 번도 안 하는 빈 수열의 순회
(T1), 빈 수열에 붙이는 자리(T3), 옛 꼬리에 잇는 자리(T4·T5), 두 방향 순회가 한 번씩 들어 있어요. 둘째 값을
**0** 으로 고른 것은 `NIL` 과 같은 수가 **값** 자리에 들어가도 순회가 끝을 잘못 판단하지 않는지 보려는
것입니다. 순회는 노드 하나를 읽을 때마다 한 걸음으로 셉니다.

```text
append(value):
    id ← nextId,  nextId ← nextId + 1
    새 노드 { id, value, x ← tail } 을 표에 넣는다
    tail = NIL 이면  head ← id                               ① 빈 수열에 붙인다
    아니면           옛 꼬리의 x ← x ^ id                     ② 옛 꼬리에 잇는다
    tail ← id,  count ← count + 1

walk(start):             toArray 는 start = head,  toArrayReverse 는 start = tail
    prev ← NIL,  curr ← start
    curr ≠ NIL 인 동안:                                      ③ 노드를 읽는다
        curr 의 값을 담는다
        다음 ← x(curr) ^ prev,  prev ← curr,  curr ← 다음
    담은 값을 돌려준다                                        ④ 순회를 끝낸다

size:   count
```

#### 1. 노드 표와 id 넷을 둔다

붙이기·순회·개수가 모두 같은 상태를 읽고 쓰므로, 그 상태와 표에서 노드를 찾는 함수부터 둡니다. 표는 `id` 를
키로 노드를 찾는 `Map` 이에요.

```ts
const NIL = 0;

interface XorNode {
  id: number;
  value: number;
  xorId: number;
}

export class XorLinkedList {
  #nodes = new Map<number, XorNode>();
  #headId = NIL;
  #tailId = NIL;
  #count = 0;
  #nextId = 1;

  #at(id: number): XorNode {
    const node = this.#nodes.get(id);
    if (node === undefined) {
      throw new Error(`표에 없는 id 를 따라갔다: ${id}`);
    }
    return node;
  }
}
```

만든 직후의 상태와 `#at` 이 내는 것은 이렇습니다.

```text
노드 표   (비었다)       head 0   tail 0   count 0   nextId 1
#at(1)    오류: 표에 없는 id 를 따라갔다: 1
```

`#at` 이 없는 id 에서 조용히 `undefined` 를 돌려주지 않고 던지는 것은 뒤에서 값을 합니다. 순회가 잘못된 id 를
계산하면 그 자리에서 멈춰서, 틀린 수열을 돌려주는 대신 틀렸다는 사실을 알려 줘요.

#### 2. append — 새 노드의 x 를 옛 꼬리 id 로 두고 옛 꼬리의 x 에 새 id 를 섞는다

붙이는 연산은 `append` 하나뿐이라 묶을 것이 없습니다. 이 연산이 표 · `head` · `tail` · `count` 를 바꾸는 유일한
자리예요.

```ts
append(value: number): void {
  const id = this.#nextId++;
  this.#nodes.set(id, { id, value, xorId: this.#tailId });

  if (this.#tailId === NIL) {
    this.#headId = id;                        // ① 빈 수열에 붙인다
  } else {
    const tail = this.#at(this.#tailId);      // ② 옛 꼬리에 잇는다
    tail.xorId ^= id;
  }

  this.#tailId = id;
  this.#count += 1;
}
```

T3~T5 가 이 조각입니다.

<!--proof:append-steps-->

```text
단계   호출         조건                 새 id · x    옛 꼬리의 x       head   tail   count
T3     append(10)   tailId 0 = NIL → ①   id 1 · x 0   —                    1      1       1
T4     append(0)    tailId 1 ≠ NIL → ②   id 2 · x 1   id 1: 0 ^ 2 = 2      1      2       2
T5     append(30)   tailId 2 ≠ NIL → ②   id 3 · x 2   id 2: 1 ^ 3 = 2      1      3       3
```

여기서 가장 중요한 줄은 `tail.xorId ^= id;` 예요. T4 에서 옛 꼬리 id 1 의 `x` 가 0 이었고, 이 줄이 `0 ^ 2 = 2`
로 바꿔 「앞 이웃 `NIL`, 뒤 이웃 2」가 됐습니다. T5 에서는 id 2 의 `x` 가 1 이었고 `1 ^ 3 = 2` 가 되어 「앞 이웃
1, 뒤 이웃 3」이 됐어요. 새 노드의 `x` 를 `this.#tailId` 로 두는 줄은 분기가 없습니다. T3 에서 `tailId` 가 0
이라 `x` 가 0 이 됐고, 그것이 「두 이웃 모두 `NIL`」과 같은 값이기 때문이에요.

#### 멈춤 — id 를 0 부터 나눠 주면 첫 원소가 사라진다

번호는 0 부터 세는 것이 익숙합니다. 배열 칸도 0 번부터이고요. **`#nextId` 를 0 에서 시작해도 될 것
같습니다.** 그 감각대로 한 줄을 바꿔 봅시다.

```ts
#nextId = 0; // ← 1 에서 바꿨다
```

전개가 붙이는 값 그대로, 붙일 때마다 세 가지를 읽어 두 코드를 견줍니다.

<!--proof:pause-id0-->

```text
붙인 값              호출               바른 코드   0 부터 준 코드       판정
append 10            toArray()          [10]        []               어긋난다
append 10            toArrayReverse()   [10]        []               어긋난다
append 10            size()             1           1                    같다
append 10 · 0        toArray()          [10 0]      [0]              어긋난다
append 10 · 0        toArrayReverse()   [0 10]      [0]              어긋난다
append 10 · 0        size()             2           2                    같다

append 10 · 0 · 30   toArrayReverse()   [30 0 10]   [30 0]           어긋난다
append 10 · 0 · 30   size()             3           3                    같다
```

**원소 하나를 붙인 직후부터 순회가 틀립니다.** `size()` 만 계속 맞아서, 개수만 확인하는 테스트는 통과해요.
붙일 때마다 네 가지 상태를 적으면 이유가 확인됩니다.

<!--proof:pause-id0-state-->

```text

append(0)        1               참      1      1         [0]
append(30)       2             거짓      1      2      [0 30]
```

첫 노드가 id 0 을 받았는데 0 은 `NIL` 이 쓰는 번호예요. `head` 와 `tail` 이 0 이 되자 수열은 원소가 하나 있는데도
**비어 있는 모양**이 됐고, 둘째 붙이기에서 `tailId === NIL` 이 참이라 ① 로 가서 `head` 를 1 로 덮어썼습니다.
id 0 노드의 값 10 은 표에 남아 있지만 어느 순회도 거기로 가지 않아요.

```text
                       id 를 0 부터            id 를 1 부터
append(10) 뒤          head 0 · tail 0         head 1 · tail 1
                       └ 0 = NIL 이라 빈 수열과 같은 모양
append(0) 의 조건      tailId 0 === NIL → 참    tailId 1 === NIL → 거짓
                       └ ① 로 가서 head ← 1     └ ② 로 가서 옛 꼬리 id 1 에 잇는다
```

#### 3. toArray · toArrayReverse · size — 상태를 바꾸지 않고 읽는다

세 연산을 한 벌로 묶는 근거는 **어느 것도 노드 표나 id 넷을 바꾸지 않기** 때문입니다. `toArray` 와
`toArrayReverse` 는 같은 `#walk` 를 시작 id 만 바꿔 부르고, `size` 는 `#count` 를 읽기만 해요.

```ts
toArray(): number[] {
  return this.#walk(this.#headId);
}

toArrayReverse(): number[] {
  return this.#walk(this.#tailId);
}

size(): number {
  return this.#count;
}

#walk(startId: number): number[] {
  const values: number[] = [];
  let prevId = NIL;
  let currId = startId;

  while (currId !== NIL) {                    // ③ 노드를 읽는다
    const node = this.#at(currId);
    values.push(node.value);
    const nextId = node.xorId ^ prevId;
    prevId = currId;
    currId = nextId;
  }

  return values;                              // ④ 순회를 끝낸다
}
```

T1 · T2 는 빈 수열, T6 은 원소 셋의 개수, T7~T12 는 두 순회입니다.

<!--proof:read-steps-->

```text
단계   호출               조건                                    다음 = x ^ prev   돌려준 값   비용
T1     toArray()          currId 0 = NIL → ④                      —                        []      0
T2     size()             —                                       —                         0      1
T6     size()             —                                       —                         3      1
T7     toArray()          currId 1 ≠ NIL → ③                      2 ^ 0 = 2                 —      1
T8     toArray()          currId 2 ≠ NIL → ③                      2 ^ 1 = 3                 —      1
T9     toArray()          currId 3 ≠ NIL → ③ · 다음 0 = NIL → ④   2 ^ 2 = 0         [10 0 30]      1
T10    toArrayReverse()   currId 3 ≠ NIL → ③                      2 ^ 0 = 2                 —      1
T11    toArrayReverse()   currId 2 ≠ NIL → ③                      2 ^ 3 = 1                 —      1
T12    toArrayReverse()   currId 1 ≠ NIL → ③ · 다음 0 = NIL → ④   2 ^ 2 = 0         [30 0 10]      1
```

여기서 가장 중요한 줄은 `const nextId = node.xorId ^ prevId;` 예요. T8 과 T11 이 같은 id 2 노드의 같은 `x` 2 를
읽었는데, T8 은 `prev` 가 1 이라 3 을, T11 은 `prev` 가 3 이라 1 을 얻었습니다. T9 에서 값 0 을 담은 뒤에도
순회가 멈추지 않은 것은 반복 조건이 **값이 아니라 id** 를 `NIL` 과 견주기 때문이에요. T1 은 시작 id 가 `NIL`
이라 ③ 을 한 번도 안 하고 ④ 로 갔고, 노드를 하나도 찾지 않아 비용이 0 입니다.

`size` 를 `this.toArray().length` 로 쓰지 않고 `#count` 를 따로 드는 이유도 이 표에 있어요. T6 의 `size()` 는
비용 1 이고, 같은 원소 셋을 `toArray()` 로 세면 T7~T9 처럼 비용 3 입니다. 원소가 `n` 개면 `n` 이에요.

```text
size() 를 세는 두 방법     #count 를 읽는다          1
                           toArray().length          원소 수만큼   ← 개수를 묻는 호출마다 전부 순회한다
```

#### 멈춤 — prevId 에 다음 id 를 넣으면 순회가 짧아지거나 없는 id 로 간다

반복문 끝의 두 줄이 헷갈리는 자리입니다. 「다음 걸음에서 `prev` 는 **다음 걸음의 직전**이니, 방금 계산한
`nextId` 를 넣어도 되지 않을까?」 순서를 바꿔 `currId ← nextId` 를 먼저 하고 `prevId ← currId` 를 하면 실제로
그 모양이 돼요. 한 줄로 적으면 이렇습니다.

```ts
prevId = nextId; // ← currId 에서 바꿨다
```

**원소가 하나면 답이 안 틀립니다.** 첫 걸음에서 다음이 곧바로 `NIL` 이라 `prev` 를 쓸 일이 없기 때문이에요.
원소가 둘 이상이면 달라집니다.

<!--proof:pause-prev-->

```text
붙인 값                    호출               바른 코드       prev 에 다음을 넣은 코드                판정
append 10                  toArray()          [10]            [10]                                    같다
append 10                  toArrayReverse()   [10]            [10]                                    같다
append 10 · 0              toArray()          [10 0]          오류: 표에 없는 id 를 따라갔다: 3   어긋난다
append 10 · 0              toArrayReverse()   [0 10]          오류: 표에 없는 id 를 따라갔다: 3   어긋난다
append 10 · 0 · 30         toArray()          [10 0 30]       [10 0]                              어긋난다
append 10 · 0 · 30         toArrayReverse()   [30 0 10]       [30 0]                              어긋난다
append 10 · 20 · 30 · 40   toArray()          [10 20 30 40]   [10 20]                             어긋난다
append 10 · 20 · 30 · 40   toArrayReverse()   [40 30 20 10]   오류: 표에 없는 id 를 따라갔다: 5   어긋난다
```

같은 코드가 어떤 수열에서는 짧은 배열을 돌려주고, 어떤 수열에서는 없는 id 를 따라가다 던집니다. 앞→뒤 순회를
걸음마다 펼치면 이유가 확인돼요.

<!--proof:pause-prev-trace-->

```text
붙인 값              prev   curr   다음 = x ^ prev   다음 걸음으로                          담은 값
append 10 · 0 · 30      0      1   2 ^ 0 = 2         prev ← 2 · curr ← 2                       [10]
—                       2      2   2 ^ 2 = 0         prev ← 0 · curr ← 0                     [10 0]
—                       —      —   —                 curr 0 = NIL → 끝                            —
append 10 · 0           0      1   2 ^ 0 = 2         prev ← 2 · curr ← 2                       [10]
—                       2      2   1 ^ 2 = 3         prev ← 3 · curr ← 3                     [10 0]
—                       —      —   —                 표에 없는 id 를 따라갔다: 3 → 던진다         —
```

둘째 걸음부터 `prev` 가 `curr` 와 같은 수가 됐습니다. 그러면 계산이 `x ^ prev` 가 아니라 `x ^ curr` 인데, `x` 에는
`curr` 자신이 섞여 있지 않으니 이웃이 나오지 않아요. [10 0 30] 에서는 id 2 의 `x` 2 와 섞여 0 이 되어 원소 둘에서
멈췄고, [10 0] 에서는 id 2 의 `x` 1 과 섞여 3 이 되어 표에 없는 id 로 갔습니다. `#at` 이 던지지 않았다면 이 줄은
틀린 수열을 조용히 돌려줬을 거예요.

```text
바른 갱신   prev ← curr     다음 걸음:  x(다음) ^ curr   = 반대쪽 이웃 ^ curr ^ curr = 반대쪽 이웃
바꾼 갱신   prev ← 다음     다음 걸음:  x(다음) ^ 다음   = 두 이웃 ^ 다음            → 이웃이 아니다
```

#### 5. 전체 코드

조각을 하나로 잇습니다. 아래는 정본 [`_reference/xorLinkedList.ts`](./_reference/xorLinkedList.ts) 의 구간을
**추출한 것**이라 손으로 옮기지 않았어요. 앞의 조각에 없던 것은 주석들뿐입니다. 정본이 비용을 세려고 두는
`__cost` 줄은 추출할 때 걷혀서 여기 없어요.

```ts guide-core=src/data-structures/linear/xorLinkedList/_reference/xorLinkedList.ts
/** 표의 빈자리를 가리키는 값. 실제 id 는 1부터 나가므로 0 과 겹치지 않는다. */
const NIL = 0;

interface XorNode {
  id: number;
  value: number;
  /** 앞 이웃 id 와 뒤 이웃 id 의 XOR. 어느 한쪽도 이 값만으로는 복원되지 않는다. */
  xorId: number;
}

export class XorLinkedList {
  #nodes = new Map<number, XorNode>();
  #headId = NIL;
  #tailId = NIL;
  #count = 0;
  /** 다음에 나눠 줄 id. 한 번 쓴 값을 다시 쓰지 않는다. */
  #nextId = 1;

  append(value: number): void {
    const id = this.#nextId++;
    // 새 노드의 뒤 이웃은 아직 없다 — 그래서 앞 이웃 id 하나가 그대로 XOR 값이 된다.
    this.#nodes.set(id, { id, value, xorId: this.#tailId });

    if (this.#tailId === NIL) {
      this.#headId = id;
    } else {
      // 옛 꼬리의 뒤 이웃 자리는 NIL 이었다. NIL 을 지우고 새 id 를 넣는 것이 이 XOR 한 번이다.
      const tail = this.#at(this.#tailId);
      tail.xorId ^= id;
    }

    this.#tailId = id;
    this.#count += 1;
  }

  toArray(): number[] {
    return this.#walk(this.#headId);
  }

  toArrayReverse(): number[] {
    return this.#walk(this.#tailId);
  }

  size(): number {
    return this.#count;
  }

  /**
   * 한쪽 끝에서 반대쪽 끝까지 걷는다.
   *
   * **두 방향이 같은 코드다.** 시작점만 다르다. 양쪽 끝 어디서 출발하든 직전에 읽은 노드가
   * 곧 이웃 하나이므로, 저장된 XOR 값에서 나머지 하나가 나온다.
   */
  #walk(startId: number): number[] {
    const values: number[] = [];
    let prevId = NIL;
    let currId = startId;

    while (currId !== NIL) {
      const node = this.#at(currId);
      values.push(node.value);
      const nextId = node.xorId ^ prevId;
      prevId = currId;
      currId = nextId;
    }

    return values;
  }

  #at(id: number): XorNode {
    const node = this.#nodes.get(id);
    if (node === undefined) {
      throw new Error(`표에 없는 id 를 따라갔다: ${id}`);
    }
    return node;
  }
}
```

```text
const list = new XorLinkedList()
list.toArray()          → []
list.append(10); list.append(0); list.append(30)
list.toArray()          → [10, 0, 30]      list.toArrayReverse()   → [30, 0, 10]
list.size()             → 3
```

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 요구에 이 구조를 쓰는지, 무엇이 매 호출 뒤에 참으로 남는지, 비용과 그
보장이 무엇인지, 그리고 이 구조가 생긴 이유인 공간 절약이 TypeScript 에서 성립하는지를 순서로 봅니다.

### 이 구조가 최적의 선택인 경우

#### 최적인 요구의 모양

주어가 문제가 아니라 **연산**입니다. 그런데 이 구조는 연산만으로는 자리가 정해지지 않아요. 셋이 함께 맞을
때입니다.

- **뒤로만 붙이고, 담긴 전체를 두 방향으로 읽고, 가운데는 건드리지 않습니다.** 한 방향만 읽으면 단일 연결
  리스트로 충분하고, 가운데에 넣거나 빼야 하면 이 계약 밖입니다.
- **노드마다 이웃 정보 하나를 줄이는 것이 실제로 제약입니다.** 원소 수가 크고 노드 하나의 크기가 메모리를
  정할 때예요. 앞의 조건만 맞으면 배열이 같은 네 연산을 지키고, 설계 상세에서 본 대로 시간으로는 구별되지
  않습니다.
- **주소를 정수로 다루고, 계산해 얻은 주소를 다시 포인터로 쓸 수 있는 언어입니다.** TypeScript 에는 주소가
  없어서 정본이 `id` 와 표를 따로 둡니다. 이 조건이 안 맞으면 둘째 조건의 절약이 생기지 않아요.

```text
세 조건이 코드의 모양을 정한다
  두 방향으로 읽는다          → 노드마다 앞·뒤 이웃 정보가 필요하다
  이웃 정보 하나가 제약이다   → 둘을 x = 앞 ^ 뒤 하나로 줄인다
  주소를 정수로 다룬다        → x 를 주소로 계산해 표 없이 다음 노드로 간다
      └ 셋째가 없으면 표가 따로 필요하고, 줄인 것보다 표가 더 많이 잡는다
```

TypeScript 에서는 셋째 조건이 성립하지 않으므로, 이 구조가 최적인 요구가 없습니다. 이 글이 정본을 TypeScript 로
둔 것은 쓰라고가 아니라 **그 절약의 대가를 세려고**예요.

#### 이 구조를 떠올리게 하는 연산 조합

독자가 다음에 만나는 것은 자기 코드의 요구예요. 요구를 **연산과 호출 횟수로 옮겨** 적어 보면 이 계약이
맞는지가 정해집니다.

```text
측정값이 들어올 때마다 기록하고, 화면에는 최신순으로, 파일로는 발생순으로 내보낸다
  → append · toArrayReverse · toArray
  → 측정 m 번이면 붙이기 m 번 · 화면 갱신마다 순회 한 번 · 내보낼 때마다 순회 한 번
  → 세 연산이 모두 계약에 있다. 붙이기 m 번이 m 에 비례하고, 순회 한 번이 그때의 원소 수에 비례한다

조작마다 기록하고, 되돌리기는 최신부터, 다시 하기는 오래된 것부터 재생한다
  → append · toArrayReverse · toArray
  → 되돌린 뒤 새 조작을 하면 뒤쪽 기록을 버려야 한다 — 그 연산이 계약에 없다

이벤트를 한 번 쓰고, 덤프할 때 두 순서로 한 번씩 읽는다
  → append 를 이벤트 수만큼 · toArray 한 번 · toArrayReverse 한 번
```

**옮긴 연산이 계약에 없으면 그 요구는 이 구조의 사례가 아닙니다.** 둘째 요구는 뒤쪽을 잘라 내는 연산이 섞여서
이중 연결 리스트를 찾아야 해요. 첫째와 셋째는 계약에 맞지만, 옮기고 나면 **배열로도 같은 네 연산이 된다**는
것이 확인됩니다. 이 구조를 떠올릴 신호는 연산 조합에 더해 「노드당 메모리가 제약이고, 주소를 정수로 다루는
언어로 쓴다」가 함께 있을 때예요.

#### 실제로 쓰이는 곳

- **Linux Journal 의 「A Memory-Efficient Doubly Linked List」(Prokash Sinha, 2004)** — 이 구조를 C 로 제안한
  글입니다. 첫 문단이 동기를 적었어요. *"In the quest to make small devices cost effective, manufacturers often
  need to think about reducing the memory size."* 작은 기기에서 메모리를 줄이려는 목적이고, 방법은 *"Pointer
  difference is captured by using exclusive OR."* 입니다. 제안이지 제품에 들어간 기록은 아니에요.
  ([linuxjournal.com/article/6828](https://www.linuxjournal.com/article/6828), 조회 2026-09-13)
- **리눅스 커널의 연결 리스트** — 커널의 기본 리스트 노드는 포인터 둘을 따로 둡니다.
  `struct list_head { struct list_head *next, *prev; };` 가 그 정의예요. 메모리를 줄여야 했던 해시 표에서는 XOR
  이 아니라 **머리를 포인터 하나로 줄인** `hlist_head` 를 따로 두었고, 주석이 대가를 적었습니다. *"Double linked
  lists with a single pointer list head. Mostly useful for hash tables where the two pointer list head is too
  wasteful. You lose the ability to access the tail in O(1)."*
  ([`include/linux/types.h`](https://github.com/torvalds/linux/blob/master/include/linux/types.h) ·
  [`include/linux/list.h`](https://github.com/torvalds/linux/blob/master/include/linux/list.h), 조회 2026-09-13)
- **실제 제품 코드에 XOR 연결 리스트가 들어간 사례는 찾지 못했습니다**(조회 2026-09-13).

```text
두 자리가 고른 것
  Linux Journal 제안   노드마다 이웃 포인터 둘 → XOR 하나      C · 작은 기기
  리눅스 커널          노드는 포인터 둘 그대로                 해시 표 머리만 포인터 하나로 줄이고 뒤 끝 접근을 포기
```

#### 경쟁 설계와의 대조

같은 계약을 지키는 **다른 설계** 둘을 세웁니다 — **배열 하나**(칸 8 개에서 시작해 가득 차면 두 배로 늘린다)와
**이중 연결 리스트**(노드가 `value` · `prev` · `next` 를 참조로 든다)예요. 셋의 시간 판정은 설계 상세에서 같게
나왔으니, 여기서는 이 구조가 생긴 이유인 공간을 **슬롯**으로 셉니다. 슬롯은 원소를 담으려고 잡는 값 자리 하나
(수 하나 또는 참조 하나)이고, 수열 전체가 하나씩 드는 `head` · `tail` · `count` 는 세 설계에 다 있어 넣지
않았어요.

입력은 계약 스위트의 붙이기 시나리오와 같은 모양으로, 뒤로 `n = 1,024` 번 붙였습니다. 전개의 세 번 붙이기를
쓰지 않은 이유는 하나예요 — 배열이 칸을 한 번도 늘리지 않아서 설계가 갈리는 값이 한 자릿수로 붙어 나오고,
`n` 이 커질 때 어떻게 벌어지는지가 안 보입니다.

| 설계 | 붙이기 한 번이 쓴 슬롯의 최댓값 | 붙이기 1,024 번이 쓴 슬롯 | 잡고 있는 슬롯 |
| --- | --- | --- | --- |
| XOR 연결 리스트 (이 가이드) | 6 | 6,143 | 5,120 |
| 배열 하나 | 513 | **2,040** | **1,024** |
| 이중 연결 리스트 | **4** | 4,095 | 3,072 |

**어느 축을 보느냐로 배열과 연결 리스트의 순서가 뒤집힙니다.** 붙이기 한 번의 최댓값은 연결 리스트 쪽이 4 와
6 이고 배열이 513 이에요 — 배열은 칸이 가득 찬 513 번째 붙이기에서 원소 512 개를 옮기고 한 칸을 씁니다. 전체로
쓴 슬롯과 잡고 있는 슬롯은 배열이 2,040 과 1,024 로 가장 적어요.

```text
축을 셋으로 갈라 적으면
                                   XOR (이 가이드)   배열 하나   이중 연결 리스트
  붙이기 한 번이 쓴 슬롯 최댓값     6                  513         4        ← 연결 리스트 쪽이 적다
  붙이기 1,024 번이 쓴 슬롯         6,143              2,040       4,095    ← 배열이 적다
  잡고 있는 슬롯                    5,120              1,024       3,072    ← 배열이 적다
```

**이 가이드의 구현은 세 축 모두에서 이중 연결 리스트보다 많습니다.** 노드 하나에 슬롯이 5 개이기 때문이에요 —
노드 객체 `{ id, value, xorId }` 의 셋과, 그 노드를 `id` 로 찾게 하는 `Map` 항목의 키 · 값 둘. 이웃 정보를
하나 줄였는데 그 정보를 주소로 쓸 수 없어 표가 둘을 더 잡았습니다. 그래서 TypeScript 에서 이 대조의 연결
리스트 쪽 자리는 이중 연결 리스트가 더 적은 수로 차지해요.

**우열이 반대가 되는 조건은 분명합니다.** 붙이기 한 번의 지연에 상한을 약속해야 하면 연결 리스트 쪽이고,
전체 작업량과 잡는 메모리가 중요하면 배열입니다. XOR 연결 리스트가 이중 연결 리스트보다 적어지는 조건은
노드가 `값 + x` 두 슬롯이 되는 것 — 주소를 정수로 다룰 수 있어 표가 필요 없을 때 — 하나뿐이에요.

### 불변식 — size 와 두 방향 순회가 늘 한 수열을 가리킨다

> 호출 하나가 끝날 때마다 `size()` 는 `toArray()` 가 돌려주는 배열의 길이와 같고, `toArrayReverse()` 는
> `toArray()` 를 뒤집은 배열과 같습니다.

```text
toArray()           [ a₀  a₁  …  a_(size−1) ]    길이 = size()
toArrayReverse()    [ a_(size−1)  …  a₁  a₀ ]    같은 원소를 반대 순서로
```

**계약 헤더는 불변식을 둘로 적고, 둘 다 같은 이유로 둡니다 — 상태를 읽는 길이 둘이기 때문이에요.** 읽는 길이
하나뿐이면 그 길이 무엇을 내놓든 그것이 곧 상태라 견줄 상대가 없습니다. 길이 둘이면 구현이 둘을 따로 유지할
수 있고, 따로 유지하는 순간 갈릴 수 있어요. 둘을 버리면 무엇이 되는지 이름으로 보면 확인됩니다.

```text
size() 와 순회 길이가 달라도 되면        → 세어 둔 수와 담긴 수가 다른 그릇
두 방향 순회가 다른 수열이어도 되면      → 한 수열이 아니라 수열 둘
```

이 구현이 두 문장을 지키는 방법은 「노드마다 `x = 앞 이웃 id ^ 뒤 이웃 id` 이고 끝 바깥은 `NIL`」이라는
대응이에요. **이 대응은 계약에 적지 않습니다.** 적는 순간 XOR 이 처방이 되고, 배열처럼 같은 계약을 다르게
지키는 구현이 계약 위반이 됩니다. 여기서는 이 구현이 두 문장을 어떻게 지키는지 보이는 데만 씁니다.

**각 연산이 문장을 어떻게 지키는지 전수로 봅시다.** 상태를 바꾸는 갈래는 붙이기의 둘이고, 읽기 셋은 상태를 안
바꾸니 직전에 참이면 직후에도 참이에요.

| 갈래 | 하는 일 | 두 문장이 유지되는 근거 |
| --- | --- | --- |
| 빈 수열에 붙이기 | 새 노드 `x ← NIL`, `head ← tail ← 새 id`, `count ← 1` | 앞 끝에서도 뒤 끝에서도 새 노드 하나를 읽고 `x ^ NIL = 0` 에서 멈춘다. 두 순회가 `[값]` 이고 길이 1 이 `count` 와 같다 |
| 원소가 있는 수열에 붙이기 | 새 노드 `x ← tail`, 옛 꼬리 `x ← x ^ 새 id`, `tail ← 새 id`, `count` 를 1 늘린다 | 대응이 두 노드에서 다시 참이 된다. 앞 끝에서의 순회는 옛 꼬리에서 멈추던 자리가 새 노드로 이어져 한 칸 길어지고, 뒤 끝에서의 순회는 새 노드에서 출발해 옛 순서를 그대로 거친다. 둘 다 1 늘고 `count` 도 1 는다 |
| 앞→뒤 순회 · 뒤→앞 순회 · 개수 | 노드 표와 id 넷을 읽기만 한다 | 상태가 그대로이니 직전의 두 문장이 그대로다 |

**경계 입력에서도 확인합니다.** 계약 스위트가 경계로 정해 둔 입력 일곱을 정본으로 실행하고, 호출 하나가 끝날 때마다
계약 스위트의 불변식 검사 함수 둘을 그대로 불렀어요. 하나라도 어기면 실행이 멈추게 해 두었습니다. 표는 각
입력이 끝났을 때의 세 읽기입니다.

<!--proof:invariant-edges-->

```text
붙인 값                                     toArray()                                 toArrayReverse()                          size()
붙인 값 없음                                []                                        []                                             0
42                                          [42]                                      [42]                                           1
100 · 200                                   [100 200]                                 [200 100]                                      2
0 · 0                                       [0 0]                                     [0 0]                                          2
7 · 7 · 7                                   [7 7 7]                                   [7 7 7]                                        3
1 · 2                                       [1 2]                                     [2 1]                                          2
-1 · 9007199254740991 · -9007199254740991   [-1 9007199254740991 -9007199254740991]   [-9007199254740991 9007199254740991 -1]        3
```

일곱 줄 모두 두 문장이 성립합니다. 원소가 하나인 줄은 두 순회가 같은 배열이고, 값 0 을 두 번 붙인 줄은 값이
`NIL` 과 같은 수여도 개수 2 와 두 순회 길이 2 가 같아요. 같은 값 7 을 세 번 붙인 줄은 뒤집어도 같은 배열이라
두 번째 문장이 자명하게 참이 되는 자리이고, 붙이는 도중에 읽은 줄은 읽기가 상태를 바꾸지 않았다는 것을 끝의 세
값으로 보입니다.

**이제 깨뜨려 봅시다.** 위 표에서 대응을 지키던 줄 가운데 원소가 있는 수열에 붙이기의 `옛 꼬리 x ← x ^ 새 id` 를
고릅니다. 다른 곳은 그대로 두고 **XOR 로 섞는 대신 덮어쓰도록** 한 글자만 바꿔요.

```ts
tail.xorId = id; // ← tail.xorId ^= id 에서 바꿨다
```

값 10 · 20 과 10 · 20 · 30 을 붙인 뒤 두 코드로 견줍니다.

<!--proof:mutant-overwrite-->

```text
붙인 값               호출               바른 코드    덮어쓴 코드         판정
append 10 · 20        toArray()          [10 20]      [10 20]             같다
append 10 · 20        toArrayReverse()   [20 10]      [20 10]             같다
append 10 · 20        size()             2            2                   같다
append 10 · 20 · 30   toArray()          [10 20 30]   [10 20 20 10]   어긋난다
append 10 · 20 · 30   toArrayReverse()   [30 20 10]   [30 20]         어긋난다
append 10 · 20 · 30   size()             3            3                   같다
```

**원소가 둘일 때까지는 답이 같습니다.** 둘째 붙이기에서 옛 꼬리 id 1 의 `x` 가 0 이었고, `0 ^ 2` 와 `= 2` 가 같은
2 이기 때문이에요. 셋째 붙이기에서 id 2 의 `x` 가 1 이었는데, 섞으면 `1 ^ 3 = 2` 이고 덮어쓰면 3 입니다. 앞 이웃
1 이 지워졌어요.

```text
                   id 1   id 2   id 3
바른 코드의 x       2      2      2     ← id 2 = 1 ^ 3
덮어쓴 코드의 x     2      3      2     ← id 2 = 3, 앞 이웃 1 이 지워졌다

앞 끝에서 순회    id 1: 2 ^ 0 = 2 → id 2: 3 ^ 1 = 2 → id 2: 3 ^ 2 = 1 → id 1: 2 ^ 2 = 0   값 10 20 20 10
뒤 끝에서 순회    id 3: 2 ^ 0 = 2 → id 2: 3 ^ 3 = 0                                      값 30 20
```

앞 끝에서의 순회는 id 2 에서 되돌아가 같은 노드를 두 번 읽었고, 뒤 끝에서의 순회는 id 2 에서 멈췄습니다. 계약
스위트의 불변식 검사 함수 둘을 같은 두 입력의 결과에 부르면 이렇게 말해요.

<!--proof:mutant-overwrite-invariants-->

```text
붙인 값               불변식                       덮어쓴 코드에서
append 10 · 20        첫째 — size() 와 순회 길이   지킨다
append 10 · 20        둘째 — 두 방향의 수열        지킨다
append 10 · 20 · 30   첫째 — size() 와 순회 길이   순회 4개 / size 3
append 10 · 20 · 30   둘째 — 두 방향의 수열        앞→뒤 4개 / 뒤→앞 2개
```

첫 번째 문장은 순회가 **짧아지는 것만이 아니라 길어지는 것도** 잡고, 두 번째 문장은 두 방향의 길이가 갈린 것을
잡았습니다. 원소 둘까지만 붙이는 테스트는 이 결함을 못 잡아요.

### 비용 계산

#### 비용을 세는 과정

비용의 단위는 **표에서 노드 하나를 찾을 때 1, 새 노드를 하나 만들 때 1** 입니다. 전개의 걸음 표에 그 값이
걸음마다 적혀 있어요. T3 이 붙이기 한 번에 1, T4 · T5 가 2, T7~T9 와 T10~T12 가 노드 하나를 읽을 때마다 1,
T2 · T6 이 개수 한 번에 1 이었고, T1 은 0 이었습니다. 연산별로 모으면 이렇습니다.

<!--proof:cost-by-group-->

```text
연산                       호출 수   비용 합   걸음별 비용
append                           3         5   T3=1 · T4=2 · T5=2
toArray · toArrayReverse         3         6   T1=0 · T7=1 · T8=1 · T9=1 · T10=1 · T11=1 · T12=1
size                             2         2   T2=1 · T6=1
합                               8        13   —
```

그러니 호출 하나의 비용은 이렇게 적힙니다. 붙이기는 새 노드를 만드는 1 에, 옛 꼬리가 있었으면 그것을 찾는 1 이
더해져요. 순회는 그때 담긴 원소 수이고, 개수는 1 입니다.

```text
빈 수열에 붙이기        1                   새 노드
원소가 있는 붙이기      2                   새 노드 + 옛 꼬리 찾기
순회 한 번              그때의 원소 수      원소마다 노드 하나 찾기
개수 한 번              1

여러 호출의 비용 합 = (붙이기 횟수) + (원소가 있을 때의 붙이기 횟수) + (순회마다 그때의 원소 수) + (개수 횟수)
전개의 여덟 호출     3 + 2 + (0 + 3 + 3) + 2 = 13
```

빈 수열에서 붙이기만 `n` 번 하면 첫 번은 1, 나머지 `n − 1` 번은 2 라 합이 `2n − 1` 이에요. 추가로 잡는 메모리는
노드 표의 항목 `n` 개입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 호출인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 이 구현의 호출을 두 축으로 가르면
이렇습니다.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **빈 수열에 붙이기 한 번** | `O(1)` | `Θ(1)` — 정확히 1 |
| **원소가 있는 수열에 붙이기 한 번** | `O(1)` | `Θ(1)` — 정확히 2 |
| **원소 `n` 개를 순회 한 번** (어느 방향이든) | `O(n)` | `Θ(n)` — 정확히 `n` |
| **개수 한 번** | `O(1)` | `Θ(1)` — 정확히 1 |

이 구현은 입력에 따라 케이스가 갈리는 호출이 없어요. 붙이기는 원소가 있느냐만 보고, 순회는 원소 수만 봅니다.

**한정자는 집필자가 고르는 값이 아니라 계약 헤더에 연산마다 적혀 있습니다.** 붙이기는 `amortized`, 두 순회와
개수는 `worst` 예요. **붙이기가 `amortized` 인 것은 이 구현이 필요로 해서가 아닙니다** — 이 구현의 붙이기는 호출
하나하나가 2 이하라 `worst` 로 적어도 지켜요. 칸을 늘려 가며 담는 구현도 계약을 지킬 수 있게 남겨 둔 자리이고,
경쟁 설계의 배열이 그 경우입니다 — 칸이 가득 찬 순간의 붙이기 한 번이 원소 수만큼 옮겨요. 두 순회가 `worst` 인
것은 원소 `n` 개를 돌려주는 연산이 어느 구현에서도 호출 하나가 `n` 에 비례해서, 상각할 여지가 없기 때문입니다.
그 자리에서는 두 한정자가 같은 구현을 배제하므로 강한 쪽을 적어도 어떤 구현도 새로 막지 않아요.

```text
세 한정자는 한 줄로 서지 않는다
  worst        호출 한 번마다 그 상한                        → 나머지 둘을 함의한다
  amortized    어떤 호출 순서든 n 번의 합을 n 으로 나눈 값     → 난수와 무관한 최악의 평균
  expected     난수에 대한 평균                               → amortized 와 서로를 함의하지 않는다
```

**보장의 종류를 밝힙니다.** 이 구현에는 난수가 하나도 없어요. 그래서 `amortized` 는 기댓값이 아니라 **어떤 호출
순서를 넣어도 성립하는 합의 상한**입니다. 빈 수열에서 시작해 붙이기 `p` 번(`p ≥ 1`)을 하면 붙이기 비용의 합은
정확히 `2p − 1` 이에요. 한 가지는 적어 둡니다 — 정본의 계측은 `Map` 에서 한 번 찾거나 넣는 일을 1 로 세고, 엔진이
표를 늘릴 때 하는 일은 세지 않아요. 위 수치는 그 계측 규약 아래의 값입니다.

```text
붙이기 p 번(p ≥ 1) · 개수 s 번 · 순회 w 번을 어떤 순서로 섞든
  총비용 = (2p − 1) + s + (순회마다 그때의 원소 수를 더한 값)
         ≤ (2p − 1) + s + w·p        순회 한 번의 원소 수는 그때까지 붙인 수라 p 를 넘지 않는다
```

계약 스위트 축3 이 정본에 대해 내는 값 전부입니다. 이 구조의 검증 등급은 `invariant` 라 두 크기에서 재고,
기대하는 `r` 에서 ±60% 안이면 통과로 봐요.

<!--proof:growth-rate-->

```text
시나리오가 부르는 연산   한정자      상한   n = 1,024   n = 4,096      r   판정
append                   amortized   O(1)        2.00        2.00   1.00   통과
toArray                  worst       O(n)    1,024.00    4,096.00   4.00   통과
toArrayReverse           worst       O(n)    1,024.00    4,096.00   4.00   통과
size                     worst       O(1)        1.00        1.00   1.00   통과
```

붙이기와 개수는 `r` 이 1.00 이고, 두 순회는 4.00 입니다. 붙이기의 2.00 은 `2n − 1` 을 `n` 으로 나눈 값이 소수
둘째 자리에서 반올림된 것이고, 순회의 1,024.00 과 4,096.00 은 순회 한 번이 원소 수만큼 노드를 찾은 값이에요.
시간이 아니라 찾고 만든 노드 수를 세므로, 이 판정은 이 기계의 속도가 아니라 구현의 작업량을 잽니다.

#### 최악을 만드는 입력

**이 계약에는 적대적 입력이 정의되어 있지 않습니다.** 계약 스위트의 시나리오 넷이 모두 적대적이 아니라고 적혀
있어요. 붙이기의 비용은 값에 기대지 않고, 두 순회와 개수는 인자가 없습니다. 남는 자유도는 호출 순서 하나인데,
붙이기와 읽기만 있는 순서에서는 이 구현에 대해 어떤 순서가 다른 순서보다 나쁘지 않아요.

```text
계약 스위트의 시나리오 넷      append · toArray · toArrayReverse · size    넷 다 adversarial: false
  붙이기 비용이 값에 기대는가   아니다 — 새 노드 1 과 옛 꼬리 찾기 1
  순회 · 개수에 인자가 있는가   없다 — 그때 담긴 원소 수만 비용을 정한다
```

그래도 **적대적 입력은 하나로 부족합니다.** 최악은 계약이 아니라 구현에 대해 정해지기 때문이에요. 파트 1 의 세
설계를 각자의 최악 입력에 모두 넣어 `n = 4,096` 에서 셉니다.

<!--proof:worst-inputs-->

```text
입력 (n = 4,096)                      설계                    호출당 평균   한 호출 최대
뒤로 n 번 붙이기                      배열 하나                      2.00          2,049
뒤로 n 번 붙이기                      뒤 끝을 안 드는 사슬       2,048.50          4,096
뒤로 n 번 붙이기                      XOR 연결 리스트(정본)          2.00              2
n 개를 채운 뒤 한 번 더 붙이기        배열 하나                  4,097.00          4,097
n 개를 채운 뒤 한 번 더 붙이기        뒤 끝을 안 드는 사슬       4,097.00          4,097
n 개를 채운 뒤 한 번 더 붙이기        XOR 연결 리스트(정본)          2.00              2
n 개를 채운 뒤 toArrayReverse 한 번   배열 하나                  4,096.00          4,096
n 개를 채운 뒤 toArrayReverse 한 번   뒤 끝을 안 드는 사슬       4,096.00          4,096
n 개를 채운 뒤 toArrayReverse 한 번   XOR 연결 리스트(정본)      4,096.00          4,096
```

같은 입력이 설계마다 달리 작용합니다. 「`n` 개를 채운 뒤 한 번 더 붙이기」는 배열에 4,097 이에요 — 칸 4,096 개가
막 가득 찬 순간이라 원소 4,096 개를 옮기고 한 칸을 씁니다. 뒤 끝을 안 드는 사슬도 4,097 인데, 이쪽은 옮기는 것이
아니라 노드 4,096 개를 지나 뒤 끝을 찾고 새 노드 하나를 만든 값이에요. **본문에 실린 XOR 연결 리스트는 어느
붙이기든 2 를 넘지 않고**, 순회는 세 설계 모두 원소 수만큼입니다.

```ts
const d = new GrowArray();                  // 칸 8 개에서 시작해 두 배로 늘리는 배열
for (let i = 0; i < 4096; i++) d.append(i); // 칸 4,096 개가 가득 찬다
d.append(4096);                             // 이 한 번이 원소 4,096 개를 옮긴다
```

그러니 이 구현의 최악은 입력이 아니라 크기가 정합니다 — 원소 `n` 개를 담은 뒤의 순회 한 번이 `n` 이에요. **다른
정당한 구현에는 다른 입력이 최악입니다** — 배열이라면 원소 수가 칸 수와 같아진 순간의 붙이기가, 뒤 끝을 안 드는
사슬이라면 긴 수열 끝의 붙이기가 최악이고, 그 사슬은 계약의 붙이기 상한을 못 지킵니다.

#### TypeScript 의 한계와 대체 언어

이 저장소는 자료구조마다 **TypeScript 만으로 계약과 그 근거를 댈 수 있는가**를 세 등급으로 정해 둡니다
(`docs/ORD-006-conventions.md` 의 규약4). (가)는 계약 자체를 TypeScript 로 표현할 수 없어 Rust 가 필요한 구조,
(나)는 계약은 TypeScript 로 지켜지는데 **그 구조가 왜 그 모양이어야 하는지의 근거**를 TypeScript 에서 잴 수 없는
구조, (-)는 둘 다 아닌 구조예요. XOR 연결 리스트는 **(나)** 입니다.

```text
(가)   계약을 TypeScript 로 표현할 수 없다         → Rust 가 필요하다
(나)   계약은 지켜진다. 구조의 근거를 잴 수 없다   → XOR 연결 리스트
(-)    둘 다 아니다                                → 이 절이 없다
```

**(가)가 아닌 이유.** 계약의 네 연산이 전부 TypeScript 로 표현되고 실제로 지켜지며, 계약 스위트 축3 이 네 시나리오
모두에서 그것을 잽니다. 표현조차 안 되는 항목이 하나도 없어요.

**(-)가 아닌 이유.** 이 구조가 생긴 이유는 계약 밖의 공간인데, 그것을 TypeScript 에서 잴 수 없습니다. 셀 수 있는
만큼만 세면 이렇습니다. 슬롯은 경쟁 설계와의 대조와 같게, 값 자리 하나(수 하나 또는 참조 하나)예요.

```text
노드 하나에 딸린 슬롯 수

  주소를 정수로 다루는 언어의 XOR 노드
      값 + (앞 주소 ^ 뒤 주소)                              = 2
  같은 언어의 이중 연결 노드
      값 + 앞 + 뒤                                          = 3
                                            ← 이 구조의 주장: 3 → 2

  이 저장소의 TypeScript 정본 (_reference/xorLinkedList.ts)
      노드 객체  { id, value, xorId }                       = 3
      Map 항목   키 + 값                                     = 2
                                                            합 5
  TypeScript 이중 연결 노드
      { value, prev, next }                                 = 3
                                            ← 실제로 일어난 일: 3 → 5
```

하나를 줄이려다 둘을 더 씁니다. **메모리 이득이 0 이 아니라 마이너스예요.** 그리고 이 수는 **하한**입니다. 객체
머리, 해시 표의 여유 칸, 정렬을 위한 빈 바이트를 하나도 세지 않았어요. 그것들을 세면 격차는 커지지 작아지지
않습니다. 세지 않은 이유가 곧 (나) 판정의 내용이에요 — 객체 하나가 몇 바이트인지, 표가 실제로 몇 칸을 잡고
있는지를 언어가 노출하지 않습니다. 위 표는 소스를 세어 얻은 것이지 측정한 것이 아닙니다.

**Rust 로 옮겨도 이 절약이 곧바로 성립하지는 않습니다.** Rust 는 포인터가 어느 할당에서 왔는지(출처, provenance)를
주소와 함께 따라다니게 하는 규칙을 문서화해 두었고, 주소로 비트 계산을 하는 것은 허용하되 조건을 답니다. *"So
you're still able to drop down to the address representation and do whatever clever bit tricks you want as long as
you're able to keep around a pointer into the allocation you care about that can "reconstitute" the provenance."* XOR
노드는 두 주소를 섞은 정수 하나만 들고, 다음 노드의 할당을 가리키는 포인터를 따로 들지 않아요. 노드마다 따로
할당하면 출처를 되살릴 포인터가 없고, 정수에서 포인터를 만드는 다른 길(노출된 출처, exposed provenance)은 문서가
이렇게 적습니다. *"the semantics of Exposed Provenance are on much less solid footing than Strict Provenance"* ·
*"Exposed Provenance will not work (well) with tools like Miri and CHERI."*
([`std::ptr` 모듈 문서](https://doc.rust-lang.org/std/ptr/index.html), 조회 2026-09-13)

```text
Rust 에서 XOR 노드를 두는 두 길
  노드마다 따로 할당     x 에서 주소를 얻어도 그 할당의 출처가 없다   → 노출된 출처로 가야 하고 검증 도구가 제대로 못 본다
  노드를 한 덩어리에      덩어리 포인터로 출처를 되살릴 수 있다        → 주소 XOR 이 덩어리 안 번호 XOR 과 같아진다
                                                                   └ TypeScript 정본이 id 와 표로 한 것과 같은 모양이다
```

그래서 규약4 (나)는 Rust 산출물을 강제하지 않고, 이 구조에는 붙이지 않았습니다. 이 절약이 성립하는 곳은 세 조건을
**동시에** 만족하는 곳이에요.

```text
조건                                            어기면 무엇이 되는가
객체를 옮기는 가비지 수집기가 없다              두 주소를 섞은 정수는 포인터로 보이지 않아, 수집기가 객체를 옮길 때 고칠 대상에서 빠진다
주소를 정수로 다루는 것이 언어 규칙 안에 있다   주소가 없으면 id 와 표를 따로 세워야 하고, 그 표가 위의 +2 다
계산해 만든 주소를 유효한 포인터로 인정한다     출처를 따지는 언어에서는 출처를 되살릴 포인터를 따로 들어야 한다
```

셋을 모두 만족하는 자리는 C 와 어셈블리이고, 실제로 쓰이는 곳에서 본 제안 글도 C 로 쓰였어요. **정본이 이 구현인
이유도 여기 있습니다.** 계약을 지키는 가장 적은 슬롯의 구현은 배열인데도 `_reference/` 에 XOR 을 흉내 낸 구현을
두었어요. 이 구조에서 검사받아야 할 것이 계약이 아니라 공간 주장이기 때문이고, 주장이 동작하는 코드로 있어야 그
대가를 셀 수 있습니다. 세어 보니 TypeScript 에서는 마이너스였어요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 노드마다 앞 이웃 id 와 뒤 이웃 id 를 XOR 한 값 하나를 두고 끝
바깥을 `NIL = 0` 으로 적으면, 직전 id 하나를 들고 걷는 것만으로 같은 표를 두 방향으로 순회할 수 있고, 붙이기는 새
노드와 옛 꼬리 두 노드만 고칩니다. 다만 그 절약은 주소를 정수로 다루는 언어에서만 성립합니다.

```text
노드마다 x = 앞 이웃 id ^ 뒤 이웃 id,  끝 바깥은 NIL = 0,  id 는 1 부터
   → 붙이면 새 노드 x ← tail,  옛 꼬리 x ← x ^ 새 id                       비용 2 (빈 수열이면 1)
   → 순회는 prev ← NIL 에서 출발해 다음 = x(curr) ^ prev,  prev ← curr     노드마다 1
   → 개수는 세어 둔 count                                                  비용 1
       └ 시간은 배열·이중 연결 리스트와 같다. 공간은 TypeScript 에서 노드당 5 슬롯이라 이중 연결 리스트의 3 보다 많다
```

먼저 답이 붙는 문제 하나입니다. 전개가 T12 에서 끝난 상태에서 `append(40)` 을 한 번 더 부르면 `x` 가 바뀌는 노드는
어느 것이고 그 값은 얼마일까요? 그 호출의 비용은 얼마일까요?

```text
T12 뒤    노드 표  id 1: 10/x2 · id 2: 0/x2 · id 3: 30/x2      head 1   tail 3   count 3
그다음    append(40)   → x 가 바뀌는 노드 ?   비용 ?
```

<!--check:append40-->
`tail` 이 3 이라 ② 로 갑니다. 새 노드 id 4 의 `x` 는 그때의 `tail` 인 **3** 이고, 옛 꼬리 id 3 의 `x` 가
`2 ^ 4` 로 **6** 이 돼요. id 1 과 id 2 는 이웃이 그대로라 안 바뀝니다. 새 노드를 만드는 1 에 옛 꼬리를 찾는 1 이
더해져 비용은 **2** 예요.

<!--proof:check-append40-->

```text
append(40)   tailId 3 ≠ NIL → ②   새 id 4 · x 3   비용 2
옛 꼬리  id 3: 2 ^ 4 = 6
노드 표  id 1: x 2 · id 2: x 2 · id 3: x 6 · id 4: x 3
head 1  tail 4  count 4
```

됐고, 이 표에서 세 노드가 같은 `x` 를 들고 있던 모양이 여기서 처음 깨졌습니다.
