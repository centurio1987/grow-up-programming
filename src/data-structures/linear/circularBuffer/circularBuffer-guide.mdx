# CircularBuffer — 자르지 않고 감아 도는 고정 배열

## 한눈에 보는 컨셉

고정 크기 배열 하나에 `head`(가장 오래된 항목의 위치)와 `tail`(다음에 쓸 위치) 두 포인터만 얹어, 배열 끝에 닿으면 다시 0으로 감아 도는 자료구조예요. 비결은 딱 하나, `(index + 1) % capacity` 연산으로 "배열의 끝"과 "배열의 처음"을 이어 붙이는 것입니다. 덕분에 앞을 잘라내는 시프트 연산 없이 `write` / `read` / `peek`이 모두 `O(1)`로 끝나고, 메모리는 처음 잡은 `capacity` 그대로 고정됩니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 CircularBuffer를 떠올리세요.

- "최신 N개만 있으면 된다" — 그보다 오래된 데이터는 자동으로 버려도 무방하다
- 쓰기(write)가 끊임없이 들어오는데, 메모리는 **고정 상한**을 넘으면 안 된다
- 넣는 순서와 꺼내는 순서가 같은 FIFO(선입선출)이면서, 꽉 찼을 때는 "가장 오래된 것을 덮어쓴다"는 정책이 자연스럽다

일반 배열로 이 문제를 풀면 앞을 잘라내는 비용이 발목을 잡습니다.

```text
동적 배열 + splice(0, 1)         고정 배열 + head/tail 순환
write 1회당 O(n) 시프트           write 1회당 O(1) — 포인터만 이동
n번 write 총 O(n^2)               n번 write 총 O(n)
메모리: 계속 늘었다 줄었다        메모리: capacity로 고정
```

$10^6$번 write가 들어오는 로그 스트림이라면 $O(n^2)$은 1초 제한을 가볍게 넘습니다. CircularBuffer는 시프트를 아예 없애 이 시소를 끊습니다.

비슷한 용도의 다른 자료구조와 헷갈리기 쉬운데, 기준은 이렇습니다 — **무제한으로 계속 쌓아야 하면 Queue(동적 배열/연결 리스트)**, **양쪽 끝에서 넣고 빼야 하면 Deque**, **크기 상한이 있고 넘치면 오래된 것을 자동으로 버려도 되면 CircularBuffer**입니다.

### 문제 사례와 적용 예시

- **스트리밍 로그 유지**: 서버가 초당 수천 건의 로그를 쏟아낼 때, 디스크에 전부 쌓지 않고 최신 N개만 메모리에 유지해 실시간 분석에 쓴다.
- **오디오/비디오 버퍼링**: 디코더가 프레임을 일정 개수만 앞서 채워 두고, 재생기가 소비한 자리에 다음 프레임을 덮어쓴다.
- **네트워크 패킷 버퍼**: 수신 큐가 처리 속도를 앞지를 때, 가장 오래된 미처리 패킷을 버리고 최신 패킷을 우선한다.
- **코딩 테스트 맥락**: "최근 K개의 이동 평균/최댓값을 유지하라" 류의 슬라이딩 윈도우 문제에서, 윈도우 내용 자체를 고정 크기로 들고 있어야 할 때 직접 구현 대상이 된다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**은 이렇게 정의합니다.

```ts
class CircularBuffer<T> {
  private buf: (T | undefined)[]; // 크기 capacity로 고정된 배열
  private head: number = 0;       // 가장 오래된 원소의 위치
  private tail: number = 0;       // 다음에 쓸 위치
  private count: number = 0;      // 현재 원소 수
  private capacity: number;
}
```

지켜야 할 불변식은 세 가지입니다.

1. $0 \leq \text{head} < \text{capacity}$ 이고 $0 \leq \text{tail} < \text{capacity}$ — 두 포인터는 항상 유효한 배열 인덱스다.
2. $0 \leq \text{count} \leq \text{capacity}$ — `count`가 현재 채워진 칸의 수를 정확히 센다.
3. $\text{isEmpty} \iff \text{count} = 0$, $\text{isFull} \iff \text{count} = \text{capacity}$ — full/empty 판정은 오직 `count`로만 한다.

배열을 시계판처럼 둥글게 그리면 이렇습니다(`capacity = 3`, 3칸 write 후).

```text
        buf[0]
       /      \
  buf[2]      buf[1]

  head 는 "다음에 읽을 자리"를 가리키고
  tail 은 "다음에 쓸 자리"를 가리키며
  둘 다 capacity에 닿으면 0으로 감아 돕니다.
```

**액션(연산)**은 이 자료구조가 제공하는 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(capacity)` | 크기 `capacity`인 고정 배열 준비 | $O(\text{capacity})$ |
| `write(item)` | `tail` 자리에 쓰고 전진. 꽉 찼으면 `head`도 같이 전진(oldest 자동 제거) | $O(1)$ |
| `read()` | `head` 자리를 꺼내고 전진. 비었으면 `undefined` | $O(1)$ |
| `peek()` | `head` 자리를 제거 없이 조회 | $O(1)$ |
| `isFull()` | `count === capacity` | $O(1)$ |
| `isEmpty()` | `count === 0` | $O(1)$ |
| `size()` | `count` 반환 | $O(1)$ |

핵심 연산인 `write`를 두 경우로 나눠 자세히 볼게요. `capacity = 3`인 버퍼에 이미 `1, 2, 3`이 채워진 상태(`isFull`)에서 `write(4)`를 호출하면:

```text
Before: head=0, tail=0, count=3      buf = [1, 2, 3]
                                             ↑head/tail(같은 자리, 가득 참)

write(4):
  ① buf[tail=0] = 4          →  buf = [4, 2, 3]
  ② tail = (0+1) % 3 = 1
  ③ count(3) == capacity(3) 이므로 head도 전진: head = (0+1) % 3 = 1

After:  head=1, tail=1, count=3      buf = [4, 2, 3]
                                             oldest였던 1은 사라지고 4가 대신 자리잡음
```

$\text{count}$가 이미 $\text{capacity}$였으므로 늘지 않고, 대신 `head`가 한 칸 전진해 "가장 오래된 것"이 옛 2번째 원소(값 2)로 바뀝니다. 반대로 `count < capacity`일 때는 `head`를 건드리지 않고 `count`만 증가시킵니다 — 이 분기 하나가 write의 전부입니다.

### 왜 모순 없이 작동하는가

**불변식 1(포인터 범위)이 항상 지켜지는 이유**: `tail`과 `head`는 오직 `(x + 1) % capacity` 형태로만 갱신됩니다. 모듈러 연산의 결과는 정의상 $[0, \text{capacity})$ 범위를 벗어날 수 없으므로, 초기값 0에서 시작해 어떤 순서로 write/read를 반복해도 두 포인터는 유효 인덱스를 벗어나지 않습니다.

**불변식 2, 3(count가 진실)이 항상 지켜지는 이유**: `count`를 바꾸는 곳은 `write`(조건부 `count++`)와 `read`(무조건 `count--`, 단 `count === 0`이면 아예 실행하지 않음) 두 곳뿐입니다. 귀납적으로: `count = 0`에서 시작해, write는 최대 `capacity`까지만 늘리고(그 이상은 `head`를 밀어내는 쪽으로 전환), read는 0 미만으로 내려가지 않습니다(가드가 막음). 그러므로 `count`는 항상 실제로 채워진 칸의 수와 일치합니다.

여기서 헷갈리기 쉬운 포인트는 **`head === tail`만 보고 "비었다" 또는 "꽉 찼다"를 판정하려는 유혹**입니다. 두 상태 모두 `head`와 `tail`이 같은 자리를 가리킬 수 있기 때문에, 포인터만으로는 두 상태를 구별할 수 없어요. 직접 확인해 볼까요? `capacity = 3`인 버퍼에 `write`를 5번 연달아 호출하면 `head`와 `tail`은 각각 몇이 될까요?

> 정답: `head = 2`, `tail = 2`. 다섯 번째 write 이후 두 포인터가 같은 자리(2)를 가리키지만, `count = 3`이라 버퍼는 **가득 차 있습니다**. `head === tail`만 보고 판단했다면 "비었다"고 착각했을 상황이에요. 이 착각이 실제로 데이터를 잃어버리는 과정은 다음 절(코드로 옮기기)에서 그대로 재현합니다.

엣지 케이스를 점검합니다.

```text
capacity = 1              → write 두 번째부터 매번 직전 값을 덮어씀(항상 1개만 유지)
빈 상태에서 read()/peek() → count === 0 가드에 걸려 undefined
꽉 찬 상태에서 write       → count 그대로, head가 전진하며 oldest 자동 제거
write N번 → read N번 → 재사용 → count가 0으로 돌아온 뒤에도 head/tail이 같은 값에서
                              다시 정상적으로 전진(포인터는 "감아 도는" 값일 뿐, 방향은
                              그대로이므로 재사용에 특별 처리가 필요 없음)
```

## 아이디어를 코드로 옮기기

CircularBuffer의 구현은 세 단계를 거쳐 자연스럽게 완성됩니다.

**① 원형(naive) — 동적 배열 + `splice`.** 가장 먼저 떠오르는 구현은 그냥 배열에 밀어 넣고, 넘치면 앞을 잘라내는 것입니다.

```ts
class NaiveLogBuffer<T> {
  private buf: T[] = [];
  constructor(private capacity: number) {}

  write(item: T): void {
    this.buf.push(item);
    if (this.buf.length > this.capacity) {
      this.buf.splice(0, 1); // O(n) 시프트 — 모든 뒤 원소가 한 칸씩 당겨짐
    }
  }

  read(): T | undefined {
    return this.buf.shift(); // 이것도 O(n)
  }
}
```

`capacity = 3`인 버퍼에 `1, 2, 3`을 넣고 `4`를 더 넣으면 결과는 `[2, 3, 4]`로 정확합니다. 문제는 정확성이 아니라 **속도**예요. `splice(0, 1)`과 `shift()`는 매번 나머지 원소를 전부 한 칸씩 옮기므로 $O(n)$이고, $10^6$번 반복하면 $O(n^2)$이 되어 시간 제한을 넘깁니다.

**② 개선 — 고정 배열 + `head`/`tail`, 그런데 슬롯 하나를 예약.** 시프트를 없애려고 고정 배열과 포인터를 도입하는데, 이번엔 포인터만으로 empty/full을 구분하려는 유혹에 빠지기 쉽습니다. 그 유혹을 따라가 보죠.

```ts
class ReserveSlotRingBuffer<T> {
  private buf: (T | undefined)[];
  private head = 0;
  private tail = 0;
  constructor(private capacity: number) {
    this.buf = new Array(capacity);
  }

  isFull(): boolean {
    return (this.tail + 1) % this.capacity === this.head;
  }
  isEmpty(): boolean {
    return this.head === this.tail;
  }

  write(item: T): void {
    if (this.isFull()) {
      this.head = (this.head + 1) % this.capacity; // oldest 제거
    }
    this.buf[this.tail] = item;
    this.tail = (this.tail + 1) % this.capacity;
  }

  read(): T | undefined {
    if (this.isEmpty()) return undefined;
    const x = this.buf[this.head];
    this.head = (this.head + 1) % this.capacity;
    return x;
  }
}
```

`isFull`을 "`tail`이 한 칸만 더 가면 `head`와 겹친다"로 정의해서 `head === tail`을 순수하게 "비었다"는 뜻으로만 쓰겠다는 전략입니다. 그런데 이렇게 하면 **`tail`이 진짜로 `head`까지 따라잡는 자리는 절대 못 씁니다** — 그 자리를 쓰는 순간 `head === tail`이 되어 "비었다"로 오인되니까요. 실측으로 확인해 봅시다. `capacity = 3`인 버퍼에 `write(1)`, `write(2)`만 해도:

```text
write(1) 후: head=0, tail=1
write(2) 후: head=0, tail=2  →  isFull()? (2+1)%3 == 0(head) → true!

capacity는 3인데, 겨우 2개 넣고 벌써 "가득 찼다"고 오판합니다.
```

여기서 `write(3)`을 호출하면 `isFull()`이 참이므로 `head`가 먼저 `(0+1)%3=1`로 전진한 뒤 `buf[tail=2]`에 3을 씁니다. 그 결과 `read()`를 두 번 호출하면 `1`이 아니라 **`2`, `3`**이 나옵니다 — 맨 처음 넣은 `1`이 조용히 유실된 것입니다. `capacity = 3`으로 선언해 놓고 실제로는 2칸만 쓸 수 있는 이 결함은, "한 슬롯을 늘 비워 둔다"는 트레이드오프를 감수하면 표준적인 해법이 되기도 하지만, 지금 문제는 **capacity를 온전히 다 채워야 한다**는 요구를 명시하고 있으므로 받아들일 수 없습니다.

**③ 최종 — `count` 필드로 슬롯 낭비 없이 해결.** `head`와 `tail`만으로 상태를 구분하길 포기하고, "지금 몇 개 들어있는지"를 별도 변수로 직접 셉니다.

```ts
export class CircularBuffer<T> {
  private buf: (T | undefined)[];
  private head = 0;
  private tail = 0;
  private count = 0;
  constructor(private capacity: number) {
    this.buf = new Array(capacity);
  }

  write(item: T): void {
    this.buf[this.tail] = item;
    this.tail = (this.tail + 1) % this.capacity;
    if (this.count < this.capacity) {
      this.count++;
    } else {
      this.head = (this.head + 1) % this.capacity; // oldest 자동 제거
    }
  }

  read(): T | undefined {
    if (this.count === 0) return undefined;
    const x = this.buf[this.head];
    this.buf[this.head] = undefined; // GC 도움
    this.head = (this.head + 1) % this.capacity;
    this.count--;
    return x;
  }

  peek(): T | undefined {
    if (this.count === 0) return undefined;
    return this.buf[this.head];
  }

  isFull(): boolean {
    return this.count === this.capacity;
  }
  isEmpty(): boolean {
    return this.count === 0;
  }
  size(): number {
    return this.count;
  }
}
```

가장 중요한 부분은 `write`의 `if (this.count < this.capacity)` 분기입니다. **이 조건 하나가 "아직 빈 자리가 있다(count 증가)"와 "이미 가득 찼다(head도 밀어낸다)"를 완전히 갈라줍니다.** 순서도 중요한데, `buf[tail] = item`과 `tail` 전진은 항상 먼저 실행하고 그 다음에 `count`/`head` 처리를 판단합니다 — 쓰기 자체는 조건과 무관하게 항상 일어나기 때문이에요. 놓치기 쉬운 구현부를 짚어 둘게요.

- **`count < capacity` 비교는 전진 전의 값 기준입니다.** 전진 후 값으로 비교하면 한 칸씩 밀려 마지막 write에서 `count`가 실제보다 하나 적게 잡힙니다.
- **`read`의 `count === 0` 가드가 먼저입니다.** 이 가드를 빼먹으면 빈 버퍼에서 `buf[head]`가 `undefined`를 반환하긴 해도, `head`가 계속 전진해 버려 다음 write 때 엉뚱한 자리부터 채우게 됩니다.
- **capacity가 2의 거듭제곱이면** `(index + 1) % capacity`를 `(index + 1) & (capacity - 1)`로 바꿀 수 있습니다. 나눗셈(모듈로)보다 비트 AND가 더 저렴하기 때문인데, 이 치환이 성립하는 이유는 $2^k$로 나눈 나머지가 하위 $k$비트와 정확히 같기 때문입니다($n \bmod 2^k = n \mathbin{\&} (2^k - 1)$). capacity가 2의 거듭제곱이 아니면 이 치환은 틀린 값을 낼 수 있으니 일반적인 상황에선 그대로 `%`를 씁니다.

> 기억법: "쓰기는 무조건, count가 안 찼으면 늘리고, 찼으면 head를 밀어낸다."

## 실행 시각화

`capacity = 3`인 버퍼에 `write(1)` → `write(2)` → `write(3)` → `write(4)`(오버플로우) → `read()` 순서로 실행합니다. 세 번째 write까지 `buf = [1, 2, 3]`이 되어 가득 차고, `write(4)`에서 `head`가 가리키던 값 1이 4로 덮어써지며 `buf = [4, 2, 3]`이 됩니다. 마지막 `read()`는 그 시점의 oldest인 2를 반환합니다(실측: `buf.write(4)` 후 `peek() === 2`, 이어서 `read() === 2`). 패널의 `highlight`는 방금 쓴 자리, `marked`는 현재 유효 데이터 구간을 나타냅니다.
