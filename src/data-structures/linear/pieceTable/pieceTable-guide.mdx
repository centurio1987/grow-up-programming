# PieceTable — 글자는 그대로 두고, 순서만 다시 적어 내려가기

## 한눈에 보는 컨셉

원본 텍스트는 절대 건드리지 않고, 새로 추가된 글자만 별도의 버퍼에 쌓아 두는 텍스트 저장 구조예요. 비결은 "실제 문자를 옮기지 않고, 조각(Piece) 목록이라는 메타데이터만 다시 배열한다"는 것입니다. 그 덕분에 삽입·삭제가 조각 수 $p$에 비례하는 $O(p)$로 끝나서, VS Code 같은 에디터가 기가바이트급 파일도 매끄럽게 편집할 수 있습니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 PieceTable을 떠올리세요.

- 텍스트가 아주 커서(수백 MB~GB급) 삽입·삭제마다 전체를 복사할 여유가 없다
- 실행 취소(undo)·다시 실행(redo)을 안전하게 구현해야 한다 — 원본을 훼손하지 않아야 되돌리기가 쉽다
- 삽입·삭제 위치가 파일 여기저기로 튄다 — 한 커서 자리에서 타이핑만 이어지는 상황이 아니다

단순 배열(문자열)로 관리하면 중간 삽입마다 이후 내용을 전부 밀어내야 합니다. GapBuffer는 커서가 한 자리에 머물 때는 유리하지만, 커서가 멀리 튈 때마다 그 사이 내용을 밀어 옮겨야 해서(커서 이동 비용 $O(k)$) 편집 위치가 계속 바뀌는 상황엔 불리해요.

```text
연산                 단순 배열(문자열)   GapBuffer            PieceTable
insert(임의 위치)     O(n)               O(1) + 커서이동 O(k)   O(p)
delete(임의 위치)     O(n)               O(1) + 커서이동 O(k)   O(p)
getText              O(1)               O(n)                  O(n)
원본 불변성            없음                없음                  보장

n = 텍스트 전체 길이, p = 조각 수, k = 커서 이동 거리.
편집 세션에서는 보통 p ≪ n이라 O(p)는 사실상 상수처럼 느껴진다.
```

선택 기준은 이렇습니다 — 커서가 한자리에서 계속 타이핑하듯 이어지면 GapBuffer가 더 가볍고, 편집 위치가 파일 곳곳으로 튀거나(diff 적용, 여러 커서 동시 편집) undo/redo를 조각 단위 기록으로 다뤄야 하면 PieceTable이 더 적합합니다.

### 문제 사례와 적용 예시

- **VS Code / Monaco 에디터**: 2016년부터 텍스트 버퍼를 PieceTable(이후 Piece Tree로 발전)로 관리해, 대용량 파일에서도 타이핑 지연 없이 편집을 지원합니다.
- **AbiWord**: 1990년대에 이 구조를 처음 대중화한 워드프로세서로, 이후 여러 에디터 구현의 참고가 됐습니다.
- **실무 확장 — undo/redo 히스토리 뷰어**: 조각 목록의 변경 이력만 기록하면 되므로, "몇 번째 조작으로 되돌리기"가 배열 전체를 스냅샷하지 않고도 가능해집니다.
- **코딩 테스트 맥락**: "문자열에 임의 위치 삽입·삭제가 다수 주어지고, 마지막에 최종 문자열(또는 특정 구간)을 답하라"는 유형에서, naive 배열 시뮬레이션이 시간 초과가 날 때 조각 기반 구조가 대안이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드에서 정의하는 인터페이스는 이렇습니다.

```ts
interface Piece {
  buffer: "original" | "add"; // 어느 버퍼를 가리키는지
  start: number;               // 버퍼 내 시작 인덱스
  length: number;              // 조각 길이
}

class PieceTable {
  private originalBuffer: string;   // 원본 텍스트. 생성 후 절대 수정하지 않는다
  private addBuffer: string = "";   // 삽입된 텍스트. append-only
  private pieces: Piece[] = [];     // 조각 목록 — 텍스트의 논리적 순서
  private totalLength = 0;          // 현재 텍스트 총 길이
}
```

지켜야 할 불변식은 네 가지예요.

1. **원본 버퍼 불변**: 어떤 연산 후에도 $\text{originalBuffer}$는 생성 시점 값 그대로다.
2. **추가 버퍼는 append-only**: 매 `insert`는 $\text{addBuffer}$의 끝에 문자열을 이어 붙일 뿐, 기존 내용을 바꾸지 않는다.
3. **길이 일치**: $\text{totalLength} = \sum_{i} \text{pieces}[i].\text{length}$
4. **조각은 항상 자기 버퍼의 유효 범위 안**: 모든 조각 $i$에 대해 $0 \le \text{pieces}[i].\text{start} \le \text{pieces}[i].\text{start} + \text{pieces}[i].\text{length} \le |\text{buffer}(\text{pieces}[i])|$

전체 구조를 그림으로 보면 이렇습니다. `PieceTable("hello world")`에 `insert(5, "!!!")`를 실행한 직후예요.

```text
originalBuffer: "hello world"                    (불변)
addBuffer:      "!!!"                             (append-only)

pieces:  [ original 0..5 ] → [ add 0..3 ] → [ original 5..11 ]
              "hello"            "!!!"              " world"

getText() = 화살표를 따라 이어붙이기 = "hello!!! world"
```

**액션(연산)** — 이 가이드가 정의한 5개 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(originalText)` | 원본 버퍼 설정, 텍스트가 있으면 단일 조각 생성 | $O(1)$ |
| `insert(offset, text)` | offset이 속한 조각을 찾아 분할·삽입. 새 텍스트는 addBuffer에 append | $O(p)$ |
| `delete(offset, length)` | 삭제 범위와 겹치는 조각들을 잘라내고 재구성 | $O(p)$ |
| `getText()` | 조각을 순서대로 이어붙임 | $O(n)$ |
| `length()` | `totalLength` 필드를 그대로 반환 | $O(1)$ |

핵심 연산 두 개만 자세히 볼게요.

**① insert — 조각 분할(3-way split)**. offset이 어느 조각의 한가운데에 걸리면, 그 조각을 앞/뒤로 쪼개고 사이에 새 조각을 끼워 넣습니다. 로컬 오프셋은 이렇게 구해요.

$$\text{localOffset} = \text{offset} - \sum_{j < i} \text{pieces}[j].\text{length}$$

`"hello world"`에 `insert(5, "!!!")`를 실행하는 과정입니다.

```text
Before: pieces = [ { original, 0, 11 } ]                    "hello world"

offset=5 → findPiece(5): piece 0의 length는 11이라 0+11>5를 만족 → index=0, localOffset=5-0=5. piece 0의 length(11)와 localOffset(5)이 다르므로(5≠11) 경계가 아니라 조각 중간 → 3-way split 분기가 실행된다.

After:  pieces = [ { original,0,5 }, { add,0,3 }, { original,5,6 } ]
              "hello"          "!!!"          " world"
              → getText() = "hello!!! world"
```

**② delete — 겹치는 범위 잘라내기**. 삭제 구간 $[\text{start}, \text{end})$와 겹치는 조각마다, 살아남는 앞부분과 뒷부분을 계산합니다.

$$\text{localStart} = \max(0,\ \text{start} - \text{pieceStart}) \qquad \text{localEnd} = \min(\text{piece.length},\ \text{end} - \text{pieceStart})$$

`"abcdefgh"`에서 `delete(2, 3)`(즉 `"cde"` 삭제)을 실행하는 과정입니다.

```text
Before: pieces = [ { original, 0, 8 } ]                      "abcdefgh"

삭제 구간 [2, 5) — 조각 하나가 통째로 걸침
  localStart = max(0, 2-0) = 2   → 앞부분 [0,2) 생존 = "ab"
  localEnd   = min(8, 5-0) = 5   → 뒷부분 [5,8) 생존 = "fgh"

After:  pieces = [ { original,0,2 }, { original,5,3 } ]
              "ab"              "fgh"
              → getText() = "abfgh"
```

### 왜 모순 없이 작동하는가

**귀납으로 확인해 봅시다.** 생성자는 원본 텍스트가 있으면 조각 하나로 시작합니다 — 길이 합은 그 조각의 길이와 같고(불변식 3), 시작·끝이 버퍼 범위 안입니다(불변식 4). 텍스트가 없으면 조각 목록이 비고 `totalLength = 0`으로 역시 성립해요.

`insert`가 불변식을 지키는 이유: 새 텍스트는 반드시 `addBuffer` 끝에만 붙으므로(불변식 1, 2는 애초에 깨질 여지가 없음), 남은 건 3·4번입니다. 경계(조각 맨 앞/맨 뒤)에 꽂히는 경우엔 기존 조각을 전혀 건드리지 않고 새 조각 하나만 끼워 넣으므로, 길이 합은 정확히 `text.length`만큼 늘고 `totalLength`도 같은 양만큼 늘어 3번이 유지됩니다. 조각 중간에 꽂히는 경우엔 원래 조각 `[start, start+length)`를 `localOffset` 지점에서 `[start, start+localOffset)`과 `[start+localOffset, start+length)`로 쪼개는데, 둘 다 원래 유효 범위의 부분 구간이라 4번이 그대로 유지되고, 두 조각 길이의 합은 원래 조각 길이와 같으니(그 사이 새 조각의 `text.length`를 더하면) 3번도 유지됩니다.

`delete`가 불변식을 지키는 이유: 버퍼를 전혀 건드리지 않으므로 1·2번은 자동으로 유지됩니다. 겹치지 않는 조각은 그대로 두고, 겹치는 조각은 `[0, localStart)`와 `[localEnd, length)`만 남기는데 이 둘은 항상 원래 조각의 부분 구간이라 4번이 유지됩니다. 살아남는 길이의 총합은 원래 조각들의 길이 합에서 정확히 삭제 구간 길이(`end - start`)를 뺀 값과 같아서(겹치는 부분이 정확히 한 번씩만 제거되므로) 3번도 유지됩니다.

**여기서 헷갈리기 쉬운 포인트**를 짚어 둘게요.

- **물리적 저장 위치와 논리적 순서를 같은 것으로 착각하기 쉽습니다.** `addBuffer`에는 텍스트가 입력된 순서대로만 쌓이지만, `pieces` 배열에서의 위치는 전혀 다를 수 있어요. 예를 들어 `insert(0, "X")`를 하면 `X`는 `addBuffer`의 맨 끝(혹은 처음, 누적 상황에 따라 다름)에 저장되지만, `pieces` 배열에서는 맨 **앞**에 놓입니다 — "버퍼 안 위치"와 "텍스트 안 위치"는 별개의 좌표계예요.
- **경계 분기를 생략하고 항상 3-way split을 하면 안 됩니다.** `localOffset === 0`이거나 `localOffset === piece.length`인 경우까지 무조건 앞/뒤로 쪼개면, 길이가 0인 "좀비 조각"이 생깁니다. `getText()`엔 영향이 없지만(빈 문자열을 이어붙일 뿐) 조각 수 $p$가 불필요하게 계속 늘어나 $O(p)$ 성능이 서서히 나빠집니다. 그래서 경계 두 가지를 먼저 걸러내는 겁니다.

확인 질문 하나만 해 볼까요? `pieces = [{original,0,5}, {add,0,3}, {original,5,6}]`인 상태(`"hello!!! world"`)에서 `insert(5, "X")`를 하면 `X`는 어디에 꽂힐까요? — `findPiece(5)`를 실제로 돌려 보면, 조각 0(`length=5`)까지의 누적 길이가 정확히 5라서 판정식 `cumulative + piece.length > offset`이 `0+5>5`로 거짓이 되어 조각 0을 건너뛰고, 조각 1(`{add,0,3}`, "!!!")에서 `5+3>5`가 참이 되어 멈춥니다. 즉 `index=1, localOffset=5-5=0`이에요 — "조각 0의 길이와 같다"가 아니라 **조각 1의 `localOffset === 0` 앞 경계** 분기입니다. 이 분기는 `this.pieces.splice(1, 0, newPiece)`를 실행해 인덱스 1 자리(조각 0과 조각 1 사이)에 새 조각을 끼워 넣으므로, 최종 위치는 우연히 같아 보이지만 근거는 다릅니다. 결과는 `"helloX!!! world"`예요.

엣지 케이스도 점검해 둡시다.

```text
빈 텍스트로 생성              → pieces=[], length()=0, getText()=""
빈 문자열 insert               → 무시(조각 변화 없음)
length <= 0인 delete           → 무시
offset이 범위를 벗어난 insert   → [0, length()]로 클램프
delete 범위가 끝을 초과         → end를 length()로 클램프, 끝까지만 삭제
전체 삭제 후 pieces=[]         → 이후 insert는 빈 배열에 새 조각 하나만 추가
```

## 아이디어를 코드로 옮기기

가이드가 정의한 인터페이스 그대로 구현합니다. `findPiece`가 "논리적 offset → (조각 인덱스, 그 조각 안에서의 로컬 offset)" 변환을 전담하고, `insert`·`delete`는 그 결과를 받아 조각 배열만 재구성해요.

```ts
type BufferKind = "original" | "add";

interface Piece {
  buffer: BufferKind;
  start: number;
  length: number;
}

class PieceTable {
  private originalBuffer: string;
  private addBuffer: string = "";
  private pieces: Piece[] = [];
  private totalLength = 0;

  constructor(originalText: string = "") {
    this.originalBuffer = originalText;
    if (originalText.length > 0) {
      this.pieces = [{ buffer: "original", start: 0, length: originalText.length }];
      this.totalLength = originalText.length;
    }
  }

  length(): number {
    return this.totalLength;
  }

  private findPiece(offset: number): { index: number; localOffset: number } {
    let cumulative = 0;
    for (let i = 0; i < this.pieces.length; i++) {
      const piece = this.pieces[i]!;
      if (cumulative + piece.length > offset) {
        return { index: i, localOffset: offset - cumulative };
      }
      cumulative += piece.length;
    }
    return { index: this.pieces.length, localOffset: 0 };
  }

  insert(offset: number, text: string): void {
    if (text.length === 0) return;
    const clamped = Math.max(0, Math.min(offset, this.totalLength));
    const { index, localOffset } = this.findPiece(clamped);

    const newPiece: Piece = { buffer: "add", start: this.addBuffer.length, length: text.length };
    this.addBuffer += text;

    if (index === this.pieces.length || localOffset === 0) {
      this.pieces.splice(index, 0, newPiece);
    } else if (localOffset === this.pieces[index]!.length) {
      this.pieces.splice(index + 1, 0, newPiece);
    } else {
      const original = this.pieces[index]!;
      const left: Piece = { ...original, length: localOffset };
      const right: Piece = {
        ...original,
        start: original.start + localOffset,
        length: original.length - localOffset,
      };
      this.pieces.splice(index, 1, left, newPiece, right);
    }

    this.totalLength += text.length;
  }

  delete(offset: number, length: number): void {
    if (length <= 0 || this.totalLength === 0) return;
    const start = Math.max(0, Math.min(offset, this.totalLength));
    const end = Math.max(0, Math.min(offset + length, this.totalLength));
    if (start >= end) return;

    const result: Piece[] = [];
    let cumulative = 0;
    for (const piece of this.pieces) {
      const pieceStart = cumulative;
      const pieceEnd = cumulative + piece.length;
      cumulative = pieceEnd;

      if (pieceEnd <= start || pieceStart >= end) {
        result.push(piece); // 삭제 범위와 안 겹침 → 그대로 보존
        continue;
      }

      const localStart = Math.max(0, start - pieceStart);
      const localEnd = Math.min(piece.length, end - pieceStart);

      if (localStart > 0) {
        result.push({ ...piece, length: localStart }); // 앞부분 생존
      }
      if (localEnd < piece.length) {
        result.push({ ...piece, start: piece.start + localEnd, length: piece.length - localEnd }); // 뒷부분 생존
      }
    }

    this.pieces = result;
    this.totalLength -= end - start;
  }

  getText(): string {
    let result = "";
    for (const piece of this.pieces) {
      const buffer = piece.buffer === "original" ? this.originalBuffer : this.addBuffer;
      result += buffer.slice(piece.start, piece.start + piece.length);
    }
    return result;
  }
}
```

가장 중요한 부분은 `findPiece`의 판정식 `cumulative + piece.length > offset`입니다. `>=`가 아니라 `>`를 써야, offset이 정확히 조각의 끝과 같을 때 그 조각을 "포함"하지 않고 다음 조각의 시작(또는 경계)으로 넘어갑니다 — 이게 `insert`의 두 경계 분기(`localOffset === 0` / `localOffset === piece.length`)가 정확히 맞물리는 이유예요.

놓치기 쉬운 구현부를 짚어 둡니다.

- **`offset` 클램프는 하한·상한 둘 다 필요합니다.** 상한만 클램프하고 하한(음수)을 빠뜨리면, `findPiece`가 음수 `localOffset`을 반환해서 분할된 조각의 `length`가 음수가 됩니다 — "헷갈리기 쉬운 포인트"에서 다룬 좀비 조각보다 훨씬 심각하게, 이후 연산의 오프셋 계산 전체가 어긋나 버립니다.
- **`delete`의 `end`도 반드시 `length()`로 클램프해야 합니다.** `start`만 클램프하고 `end = offset + length`를 그대로 쓰면, `getText()`는 (개별 조각의 `localEnd`가 `Math.min`으로 알아서 잘리기 때문에) 우연히 맞는 것처럼 보일 수 있지만, `this.totalLength -= end - start`에서 실제 삭제된 길이보다 훨씬 큰 값을 빼게 됩니다. 실측으로 확인해 보면 `"abcdef"`(길이 6)에 `delete(4, 100)`을 `end` 클램프 없이 실행할 때 `getText()`는 `"abcd"`로 정상처럼 보이지만 `length()`는 **-94**를 반환합니다 — 텍스트 길이와 완전히 어긋난 값이에요.
- **겹침 판정 `pieceEnd <= start || pieceStart >= end`의 등호.** 조각의 끝이 정확히 삭제 시작점과 같은 경우(`pieceEnd === start`)는 "안 겹침"으로 봐야 합니다. 등호를 빠뜨리면 경계에 붙어 있을 뿐인 조각까지 불필요하게 재구성 대상이 됩니다.

기억법 하나 드립니다.

> 자르지 말고 이어 붙여라 — 실제 글자는 그대로 두고, 조각 목록만 다시 적는다.

## 스스로 점검하기

1. `PieceTable("abcdefgh")`에 `delete(2, 3)`을 실행하면 조각 목록이 어떻게 바뀌는지, 위 "delete — 겹치는 범위 잘라내기" 도식을 참고하지 말고 손으로 먼저 그려 본 뒤 맞춰 보세요.
2. `insert`에서 `localOffset === 0`과 `localOffset === piece.length` 경계 분기를 없애고 항상 3-way split만 하도록 바꾸면, 같은 위치에 100번 연속으로 한 글자씩 삽입했을 때 조각 수 $p$는 어떻게 달라질까요? `getText()` 결과도 달라질까요?
3. `delete`의 `end = offset + length`를 `length()`로 클램프하지 않으면 `length()`가 실제와 다른 값을 반환하는 걸 위 본문에서 확인했습니다. 그렇다면 `getText()`는 왜 (이 경우엔) 여전히 정상 값을 돌려주는지, `localEnd = Math.min(piece.length, end - pieceStart)` 식을 근거로 설명해 보세요.
