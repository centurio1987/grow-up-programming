# BitArray — 참/거짓 32개를 정수 한 칸에 욱여넣기

## 한눈에 보는 컨셉

"있다/없다"만 구분하면 되는 정보를 `boolean` 배열로 저장하면 원소 하나마다 최소 1바이트가 소모돼요. BitArray는 이 낭비를 없애려고 `Uint32Array`의 워드 한 칸(32비트)에 플래그 32개를 비트 단위로 욱여넣습니다. 비트 연산(OR·AND-NOT·XOR·시프트)은 CPU가 한 사이클에 처리하므로, 메모리를 최대 32배 줄이면서도 `set`·`get`·`toggle`은 여전히 `O(1)`을 유지할 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 BitArray를 떠올리세요.

- 각 항목에 대해 "있다/없다(0 또는 1)"만 저장하면 되는데, 항목 수가 수십만~수천만 개다
- 메모리 제한이 빡빡한데 `Set`이나 `boolean[]`로는 넘칠 것 같다
- 집합의 합집합·교집합이나 "1인 개수(popcount)"를 반복적으로, 빠르게 구해야 한다

naive 대안들과 메모리 비용을 비교하면 체감이 확실합니다.

```text
n = 10^6개의 방문 여부를 저장할 때:
  Array<boolean>       ≈ 1.0   MB  (원소당 최소 1바이트)
  Set<number>          ≈ 8.0   MB  (원소당 8바이트 + 해시 오버헤드)
  BitArray             ≈ 0.125 MB  (원소당 1비트)
                          → Set 대비 약 64배, boolean 배열 대비 8배 절약
```

비슷한 역할을 하는 자료구조와 헷갈릴 수 있어요. **원소 자체가 희소(sparse)하고 최댓값을 모르면 `Set`이 낫고, 인덱스 범위가 처음부터 고정돼 있고 촘촘(dense)하게 쓰인다면 BitArray가 유리합니다.**

### 문제 사례와 적용 예시

- **대규모 방문자 추적**: 유저 ID(0 ~ N-1)별 "오늘 방문했는가"를 저장한다. N이 천만이어도 BitArray는 1.25MB면 충분하다.
- **Bloom Filter의 내부 저장소**: 여러 해시 함수로 계산한 위치의 비트를 세팅해 "원소가 집합에 없을 가능성"을 빠르게 판정하는 확률적 자료구조의 뼈대가 BitArray다.
- **에라토스테네스의 체**: 소수 판별용 `is_composite` 배열을 비트로 압축하면 캐시에 더 많이 올라가 체 자체가 빨라진다.
- **코딩 테스트 맥락**: 그래프 탐색의 `visited` 배열이나 DP의 상태 비트마스크를 극단적으로 압축해야 하는 문제에서 직접 구현 대상이 된다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 이 가이드가 정의하는 인터페이스는 다음과 같습니다.

```ts
class BitArray {
  private words: Uint32Array;  // ceil(size / 32)개의 32비트 워드
  private _size: number;       // 유효 비트 개수 (0 <= index < _size)
}
```

지켜야 할 불변식은 두 가지예요.

1. $|\text{words}| = \lceil \text{size} / 32 \rceil$ — 워드 개수는 항상 비트 수를 32로 나눠 올림한 값이다.
2. $\forall i \ge \text{size}: \text{bit}_i = 0$ — 유효 범위를 벗어난 패딩 비트는 항상 0이다.

구조를 그림으로 그리면 이렇습니다(`size = 70`인 경우).

```text
size = 70  →  words.length = ceil(70/32) = 3

word0: bit  0..31          word1: bit 32..63          word2: bit 64..95
[........................] [........................] [xxxxxx..................]
전부 유효                   전부 유효                    64..69만 유효, 70..95는 항상 0(패딩)
```

**액션(연산)** — 이 가이드가 다루는 6종 전부입니다.

| 연산 | 하는 일 | 비용 |
|------|---------|------|
| `set(i)` | i번 비트를 1로 설정 | $O(1)$ |
| `clear(i)` | i번 비트를 0으로 설정 | $O(1)$ |
| `get(i)` | i번 비트 값 조회 | $O(1)$ |
| `toggle(i)` | i번 비트를 반전 | $O(1)$ |
| `count()` | 1인 비트 개수(popcount) | $O(\lceil \text{size}/32 \rceil)$ |
| `size()` | 총 비트 수 | $O(1)$ |

모든 비트 연산의 출발점은 "주소 계산"입니다. 인덱스 $i$가 몇 번째 워드의 몇 번째 자리인지부터 알아야 해요.

$$
\text{wordIndex} = \left\lfloor \frac{i}{32} \right\rfloor = i \ggg 5, \qquad
\text{bitIndex} = i \bmod 32 = i \,\&\, 31, \qquad
\text{mask} = 1 \ll \text{bitIndex}
$$

$i \ggg 5$는 상위 비트를 5칸 밀어내 "32로 나눈 몫"을 얻고, $i \,\&\, 31$은 하위 5비트만 남겨 "32로 나눈 나머지"를 얻습니다 — 나눗셈·나머지 연산을 시프트·마스크로 대체하는 흔한 트릭이에요.

핵심 연산 두 개를 Before/After로 자세히 볼게요. `words[0] = 00000001₂`(비트0만 1)인 상태에서 `set(3)`을 실행하면:

```text
Before: words[0] = 00000001₂        (bit0=1, 나머지 0)
mask = 1 << 3 = 00001000₂
words[0] |= mask
After:  words[0] = 00001001₂        (bit0=1, bit3=1 추가, 나머지 불변)
```

`count()`는 워드 하나를 통째로 계산하는 SWAR(SIMD Within A Register) popcount를 씁니다. `word = 10001000₂`(=136, 비트 3과 7이 1)를 넣으면:

```text
n = 10001000₂  (=136, 2진수 2자리씩 묶어 "그 안의 1 개수"를 담게 만든다)
① n - ((n>>>1) & 0x55555555)         →  01000100₂ (=68)   ← 2비트쌍별 부분합
② (n&0x33333333)+((n>>>2)&0x33333333) → 00010001₂ (=17)   ← 4비트 그룹별 합
③ (n + (n>>>4)) & 0x0f0f0f0f          →  00000010₂ (=2)   ← 8비트 그룹별 합
④ (n * 0x01010101) >>> 24             →  2                 ← 바이트 4개를 곱셈으로 한 번에 합산
```

최종값 2가 실제로 세워진 비트 개수(3번, 7번)와 일치합니다.

### 왜 모순 없이 작동하는가

먼저 왜 이 방식이 항상 옳은지부터 짚고 갈게요. `set`·`clear`·`toggle`은 모두 "정확히 `mask` 하나가 가리키는 비트만 건드리고 나머지는 그대로 둔다"는 성질을 갖습니다.

- `words[w] |= mask` — mask에서 1인 자리만 강제로 1이 되고, 나머지는 `x | 0 = x`로 보존된다.
- `words[w] &= ~mask` — mask에서 1인 자리만 `~mask`에서 0이 되어 AND로 지워지고, 나머지는 `x & 1 = x`로 보존된다.
- `words[w] ^= mask` — mask에서 1인 자리만 `x ^ 1`로 반전되고, 나머지는 `x ^ 0 = x`로 보존된다.

그리고 range guard(`index < 0 || index >= _size`면 즉시 반환)가 모든 메서드 앞에 있으므로, 유효 범위 밖의 비트는 애초에 건드릴 방법이 없어요. `Uint32Array`는 생성 시 자동으로 0 초기화되므로 초기 상태에서 불변식 2("패딩은 항상 0")가 성립하고, 이후 모든 연산이 유효 범위 안쪽만 건드리니 귀납적으로 항상 성립합니다. `count()`는 words를 그대로 읽을 뿐이므로 패딩이 늘 0인 한 오차가 생기지 않습니다.

여기서 헷갈리기 쉬운 포인트 세 가지를 짚어 둘게요.

- **가드 조건의 경계 연산자.** `index >= _size`가 올바른 조건인데, 실수로 `index > _size`를 쓰면 어떻게 될까요? `BitArray(8)`처럼 유효 인덱스가 0~7인 구조에서 `index = 8`은 `8 > 8`이 거짓이라 **거부되지 않고 통과**해 버립니다. 그 결과 `wordIndex = 0`, `mask = 1 << 8 = 256`인 채로 `words[0]`에 OR가 실행돼 패딩 비트가 오염되고, 이후 `count()`가 유효 비트가 하나도 없는데도 **1을 반환**합니다(직접 확인한 값). 부등호 하나 차이가 불변식 2를 깨뜨리는 셈이에요.
- **`>>` 대 `>>>`, 그리고 그 영향이 미치는 자리.** `get`처럼 "시프트 후 `& 1`로 최하위 비트만 뽑는" 연산에서는 사실 `>>`(부호 있는 시프트)를 써도 결과가 같습니다 — 상위 비트에 무엇이 채워지든 `& 1`이 그걸 잘라내기 때문이에요. 하지만 `count()`를 "비트를 하나씩 오른쪽으로 밀며 `n !== 0`을 검사"하는 단순 반복으로 짤 때는 얘기가 다릅니다. `words[0] = 2147483648`(비트31만 1)처럼 최상위 비트가 선 워드에서 `n >>= 1`(부호 있는 시프트)을 쓰면, 부호 비트가 계속 1로 채워져 `n`이 `-1`에 도달한 뒤 **영원히 `-1`에 머무릅니다**(직접 40번 반복해도 `n = -1`). 같은 자리에서 `n >>>= 1`(부호 없는 시프트)을 쓰면 정확히 32번 만에 0에 도달해요. 시프트가 어디에 쓰이느냐에 따라 안전 여부가 갈립니다.
- **`words[w]`는 `noUncheckedIndexedAccess` 아래에서 `number | undefined`입니다.** range guard 덕분에 실제로는 항상 유효한 워드에 접근하지만, 타입 시스템은 그걸 정적으로 증명하지 못해요. `words[w] ?? 0`처럼 기본값을 명시해 안전하게 처리합니다.

확인 질문 하나만 해 볼게요. `BitArray(32)`를 만들면 패딩 비트가 몇 개일까요? — 정답은 0개입니다. `size`가 정확히 32의 배수라서 `words.length = ceil(32/32) = 1`이고, 워드 한 칸이 정확히 다 찹니다.

엣지 케이스를 점검해 볼게요.

```text
size = 1                → words.length = 1, 유효 인덱스는 0 하나뿐
size가 32의 배수(=32)   → 패딩 없음, 워드가 정확히 꽉 찬다
index < 0 또는 >= size  → set/clear/toggle은 no-op, get은 false
constructor(size < 1)   → RangeError를 던진다
```

## 아이디어를 코드로 옮기기

`set`·`clear`·`get`·`toggle`은 모두 같은 골격입니다 — guard로 범위를 거르고, 주소를 계산하고, mask로 비트 하나만 건드립니다.

```ts
class BitArray {
  private words: Uint32Array;
  private _size: number;

  constructor(size: number) {
    if (size < 1) throw new RangeError("size must be >= 1");
    this._size = size;
    this.words = new Uint32Array(Math.ceil(size / 32));
  }

  private addr(index: number): [number, number] {
    return [index >>> 5, 1 << (index & 31)];
  }

  set(index: number): void {
    if (index < 0 || index >= this._size) return;
    const [w, mask] = this.addr(index);
    this.words[w] = (this.words[w] ?? 0) | mask;
  }

  clear(index: number): void {
    if (index < 0 || index >= this._size) return;
    const [w, mask] = this.addr(index);
    this.words[w] = (this.words[w] ?? 0) & ~mask;
  }

  get(index: number): boolean {
    if (index < 0 || index >= this._size) return false;
    const [w, mask] = this.addr(index);
    return ((this.words[w] ?? 0) & mask) !== 0;
  }

  toggle(index: number): void {
    if (index < 0 || index >= this._size) return;
    const [w, mask] = this.addr(index);
    this.words[w] = (this.words[w] ?? 0) ^ mask;
  }

  size(): number {
    return this._size;
  }
}
```

가장 중요한 부분은 `addr()`이 만들어내는 `mask` 하나입니다 — `set`은 OR, `clear`는 AND-NOT, `toggle`은 XOR로 정확히 이 비트 하나만 건드리고 나머지 31비트는 그대로 둡니다. 놓치기 쉬운 지점은 `this.words[w] ?? 0`입니다. range guard가 인덱스 범위를 이미 보장하지만, 컴파일러 입장에서는 `w`가 항상 유효하다는 걸 알 수 없으므로 `??`로 안전하게 처리해야 컴파일이 통과합니다.

`count()`는 조금 더 흥미로운 진화를 거칩니다. 자연스러운 3단계가 있어요.

**원형 — 비트를 하나씩 밀며 세기.** 워드 하나마다 최대 32번, 비트가 0이든 1이든 전부 순회합니다.

```ts
function countBitsNaive(words: Uint32Array): number {
  let total = 0;
  for (const word of words) {
    let n = word;
    while (n !== 0) {
      total += n & 1;
      n >>>= 1; // 반드시 >>> — >>였다면 bit31이 선 워드에서 무한 루프에 빠진다
    }
  }
  return total;
}
```

위에서 짚었듯 `n >>>= 1`을 `n >>= 1`로 잘못 쓰면 `words[0] = 2147483648`(비트31만 1)인 워드에서 40번을 반복해도 `n`이 `-1`에 갇혀 끝나지 않습니다. 부호 없는 시프트를 반드시 써야 하는 자리예요.

**개선 — Kernighan의 비트 트릭.** `n &= n - 1`은 `n`에서 가장 낮은 1비트 하나를 정확히 지웁니다. 세워진 비트 수만큼만 반복하면 되니, 0인 비트가 많은(=희소한) 워드일수록 빨라져요.

```ts
function countBitsKernighan(words: Uint32Array): number {
  let total = 0;
  for (const word of words) {
    let n = word;
    while (n !== 0) {
      n &= n - 1; // 최하위 1비트를 지운다
      total++;
    }
  }
  return total;
}
```

`word = 8`(=`0b1000`, 비트3 하나만 1)이면 원형은 비트0~3을 전부 순회해 4번 반복하지만, Kernighan은 세워진 비트가 1개뿐이니 **단 1번**만 반복합니다(직접 확인한 값). 다만 여전히 워스트케이스가 남아 있어요 — `word = 0xFFFFFFFF`(32비트 전부 1)라면 Kernighan도 32번을 그대로 반복해야 하므로 원형과 다르지 않습니다.

**최종 — SWAR 병렬 비트 합산.** 비트를 순회하는 대신, 2비트씩 → 4비트씩 → 8비트씩 부분합을 산술 연산 몇 번으로 한꺼번에 구한 뒤 마지막에 곱셈으로 합칩니다. 세워진 비트가 몇 개든 상관없이 **워드당 정확히 5번의 산술 연산**으로 끝나는 상수 시간이에요.

```ts
function countBits(words: Uint32Array): number {
  let total = 0;
  for (let n of words) {
    n = n - ((n >>> 1) & 0x55555555);
    n = (n & 0x33333333) + ((n >>> 2) & 0x33333333);
    n = (n + (n >>> 4)) & 0x0f0f0f0f;
    total += (n * 0x01010101) >>> 24;
  }
  return total;
}
```

이 SWAR 본문을 그대로 `BitArray` 클래스 안에 `count()` 메서드로 넣으면 완성됩니다 — `private words`에 클래스 내부에서 바로 접근할 수 있으니 별도 인자도 필요 없어요.

```ts
// BitArray 클래스 본문 안에 그대로 추가한다
count(): number {
  let total = 0;
  for (let n of this.words) {
    n = n - ((n >>> 1) & 0x55555555);
    n = (n & 0x33333333) + ((n >>> 2) & 0x33333333);
    n = (n + (n >>> 4)) & 0x0f0f0f0f;
    total += (n * 0x01010101) >>> 24;
  }
  return total;
}
```

기억법 하나: **"원형은 다 세고, Kernighan은 선 것만 세고, SWAR는 아예 세지 않고 더한다."**

## 실행 시각화

`size = 8`인 BitArray 하나에 `set(0)` → `set(3)` → `toggle(0)` → `set(7)` → `count()`를 순서대로 실행합니다. 실측 결과 `words[0]`은 `0 → 1 → 9 → 8 → 136`으로 바뀌고, 마지막 `count()`는 `2`를 반환합니다(비트 3, 7이 살아있는 상태). array 패널은 8개 칸(비트 0~7)의 값을 보여주고, highlight는 방금 건드린 비트, marked는 이전에 세팅된 비트를 표시합니다.

> 대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.

정리하면, BitArray는 "각 비트 위치 = 워드 인덱스 + 워드 내 오프셋"이라는 주소 계산 하나로 모든 걸 풀어냅니다. `set`·`clear`·`get`·`toggle`은 mask 하나로 비트 하나만 건드리므로 항상 $O(1)$이고, `count()`는 SWAR 트릭 덕분에 워드 수에 비례하는 $O(\lceil \text{size}/32 \rceil)$에 끝나 — naive한 boolean 배열보다 메모리는 최대 32배 절약하면서 연산 복잡도는 그대로 지킵니다. range guard와 `Uint32Array`의 자동 0 초기화만 지키면 패딩 비트가 절대 오염되지 않는다는 것도 확인했어요.

1. `BitArray(70)`을 만들면 `words.length`는 몇일까요? `set(69)`와 `set(70)`을 각각 실행하면 어떤 차이가 생기나요? 직접 계산해 보세요.
