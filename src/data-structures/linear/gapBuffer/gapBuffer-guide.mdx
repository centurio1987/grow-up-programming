# GapBuffer — 커서 옆에 빈 자리를 미리 파두면 밀 필요가 없다

## 한눈에 보는 컨셉

텍스트 편집기에서 커서 위치의 삽입·삭제를 빠르게 만드는 배열 기반 버퍼예요. 비결은 커서 바로 옆에 "갭(gap)"이라는 빈 슬롯 구간을 미리 파 두고, 삽입은 그 갭의 첫 칸에 쓰기만 하면 끝나도록 만드는 것입니다. 커서가 한 자리에 머무는 한 삽입·삭제가 $O(1)$이라, Emacs와 초기 vi 계열 에디터가 이 방식을 내부 버퍼로 채택했습니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 GapBuffer를 떠올리세요.

- 문제에 "커서", "캐럿(caret)", "현재 편집 위치"라는 개념이 있고, 그 위치에서의 삽입·삭제가 **연속으로 반복**된다
- 커서 이동은 삽입·삭제보다 상대적으로 **드물게** 일어난다(타이핑은 연속, 이동은 가끔)
- 전체 텍스트 조회(`getText`)는 매 연산마다가 아니라 가끔(렌더링 시점)만 필요하다

단순 배열로 버퍼를 만들면 커서 위치에 삽입할 때마다 그 뒤 원소를 전부 밀어야 합니다. 연결 리스트를 쓰면 삽입은 빠르지만 커서를 옮기려면 노드를 하나씩 따라가야 하고, 캐시 지역성도 나쁩니다.

```text
연산                단순 배열      GapBuffer         연결 리스트
커서 위치 insert     O(n) 밀기      O(1) amortized    O(1) (탐색 제외)
커서 위치 delete     O(n)          O(1)               O(1)
커서 이동(k칸)       O(1)          O(k)               O(k)
getText             O(1)          O(n) 갭 건너뛰기    O(n)
```

일반적인 편집 패턴(한 자리에서 타이핑을 몰아치고, 가끔 커서를 옮기는)에서는 삽입·삭제가 이동보다 압도적으로 많으므로 GapBuffer의 $O(1)$ 삽입이 실질적인 이득을 줍니다. 반대로 **커서 이동 자체가 삽입만큼 잦다면**(여러 위치를 계속 오가며 편집) 그 이동 비용이 $O(k)$로 커져 이점이 줄어듭니다 — 이런 경우엔 이 저장소의 `pieceTable`처럼 원본을 복사하지 않고 조각(piece)들의 리스트로 편집을 기록하는 자료구조를 검토하는 편이 낫습니다. 기준은 간단합니다: **커서가 한곳에 머무는 시간이 길면 GapBuffer, 여러 위치를 넘나들며 undo 이력까지 필요하면 PieceTable**입니다.

### 문제 사례와 적용 예시

- **Emacs, 초기 vi 계열 에디터의 내부 텍스트 버퍼**: 사용자가 타이핑하는 동안 커서 주변 삽입이 끊임없이 반복됩니다.
- **코드 에디터의 자동완성 삽입**: 커서 위치에 스니펫 텍스트를 한 번에 밀어 넣는 연산도 갭을 그만큼 확보해 두면 한 번의 `insert` 반복으로 처리됩니다.
- **코딩 테스트 맥락**: "커서를 이동하며 문자를 삽입·삭제하는 연산 시퀀스가 주어졌을 때 최종 문자열(또는 특정 시점의 문자열)을 구하라"는 텍스트 편집 시뮬레이션 문제.
- **설정 파일·로그 뷰어의 인라인 편집기**: 사용자가 특정 줄 근처에서 반복적으로 수정하는 인터랙티브 편집 도구.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**

```ts
class GapBuffer {
  private buffer: string[];  // 전체 슬롯 = 텍스트 + 갭
  private gapStart: number;  // 갭의 시작 인덱스 = 커서 위치
  private gapEnd: number;    // 갭의 끝 인덱스 (exclusive)
  private _length: number;   // 실제 문자 수 (갭 제외)
}
```

지켜야 할 불변식은 네 가지입니다.

1. $0 \le \text{gapStart} \le \text{gapEnd} \le |\text{buffer}|$
2. `buffer[0..gapStart)`는 커서 왼쪽 텍스트, `buffer[gapEnd..|buffer|)`는 커서 오른쪽 텍스트, `buffer[gapStart..gapEnd)`는 갭 — 이 구간의 내용은 **정의되지 않는다**(무엇이 들어있든 무방하다).
3. $\text{length} = |\text{buffer}| - (\text{gapEnd} - \text{gapStart})$
4. 커서 위치는 항상 `gapStart`와 같다.

`capacity = 8`인 버퍼에 `"Hi!"`를 입력한 직후를 그려 보면:

```text
buffer:  [ H ][ i ][ ! ][ _ ][ _ ][ _ ][ _ ][ _ ]
index:      0    1    2    3    4    5    6    7
                             ^gapStart=3          ^gapEnd=8
         └──── 커서 왼쪽 텍스트 ────┘└──────────── 갭 ────────────┘
```

**액션(연산)** — 이 가이드가 정의하는 인터페이스 전부입니다.

| 연산 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(capacity)` | 크기 `capacity`인 빈 버퍼, `gapStart=0`, `gapEnd=capacity` | $O(1)$ |
| `insert(char)` | 갭의 첫 칸에 문자를 쓰고 `gapStart++`. 갭이 가득 찼으면 먼저 `grow()` | $O(1)$ amortized |
| `delete()` | `gapStart`를 1 줄여 왼쪽 문자를 갭으로 편입시킨다(사실상 삭제) | $O(1)$ |
| `moveCursor(pos)` | 목표 위치까지 갭 전체를 밀며, 지나치는 문자를 반대편으로 복사한다 | $O(\lvert pos - \text{gapStart} \rvert)$ |
| `getCursorPosition()` | `gapStart`를 그대로 반환 | $O(1)$ |
| `getText()` | 왼쪽 텍스트 + 오른쪽 텍스트를 이어붙인다(갭은 건너뜀) | $O(n)$ |
| `length()` | `_length`를 그대로 반환 | $O(1)$ |

핵심 연산 두 개를 자세히 볼게요.

**① insert — 갭의 첫 칸을 채운다.** `gapStart = 3, gapEnd = 8`인 위 버퍼에 `insert('e')`를 실행하면:

```text
Before:  [ H ][ i ][ ! ][ _ ][ _ ][ _ ][ _ ][ _ ]      gapStart=3, gapEnd=8
After:   [ H ][ i ][ ! ][ e ][ _ ][ _ ][ _ ][ _ ]      gapStart=4, gapEnd=8
                          ^ 갭의 첫 칸에 쓰고 gapStart만 +1
```

원소를 단 하나도 옮기지 않았습니다. 갭이 "미리 확보해 둔 자리"이기 때문에 쓰기 한 번과 포인터 증가 한 번으로 끝나요.

**② moveCursor — 갭 자체를 밀어서 옮긴다.** 같은 상태(`gapStart=3, gapEnd=8`, 텍스트 `"Hi!"`)에서 `moveCursor(1)`을 실행하면, 커서가 `i`와 `!`보다 왼쪽으로 이동하므로 그 두 글자가 이제 "커서 오른쪽 텍스트"에 속해야 합니다. 갭을 왼쪽으로 두 칸 밀면서, 지나치는 문자를 갭의 반대편(오른쪽 끝)으로 하나씩 복사합니다.

```text
Before:  [ H ][ i ][ ! ][ _ ][ _ ][ _ ][ _ ][ _ ]      gapStart=3, gapEnd=8
After:   [ H ][ i ][ ! ][ _ ][ _ ][ _ ][ i ][ ! ]      gapStart=1, gapEnd=6
              └──더 이상 안 읽음──┘         ↑    ↑
                                     복사된 i와 !가 새 오른쪽 텍스트
```

index 1, 2의 `i`, `!`는 지워지지 않고 그대로 남아 있습니다(실측: 105, 33). 하지만 이제 그 자리는 `gapStart(1)..gapEnd(6)` 범위, 즉 갭 안이므로 아무도 읽지 않습니다. **갭 안의 내용은 쓰레기 값이어도 무방하다**는 것이 이 자료구조 전체의 트릭입니다.

### 왜 모순 없이 작동하는가

빈 버퍼(생성자 직후)는 `gapStart=0, gapEnd=capacity, length=0`이므로 네 불변식이 자명하게 성립합니다. 이제 각 연산이 이 불변식을 계속 지키는지 봅시다.

- **insert**: 갭이 가득 찼으면(`gapStart===gapEnd`) 먼저 `grow()`로 갭을 늘려 불변식 1을 회복한 뒤, `buffer[gapStart]`에 문자를 쓰고 `gapStart++`합니다. 방금 쓴 칸은 원래 갭(불변식 2에서 "내용 무관"이던 자리)이었으므로 새 값으로 덮어써도 무방하고, 경계가 오른쪽으로 한 칸 이동했을 뿐 "왼쪽 텍스트 / 갭 / 오른쪽 텍스트" 삼분할은 그대로입니다. `length`도 정의($|\text{buffer}| - $ 갭 크기)대로 함께 1 증가하므로 불변식 3도 유지됩니다.
- **delete**: `gapStart===0`이면 지울 왼쪽 텍스트가 없으므로 그대로 반환합니다(불변식 위반 없음). 아니라면 `gapStart--`만 하는데, 이는 "직전까지 왼쪽 텍스트였던 한 칸을 갭으로 편입시킨다"는 뜻이라 삼분할 구조가 정확히 유지됩니다.
- **moveCursor**: 두 while 루프 모두 "경계를 한 칸 옮기면서, 지나치는 칸의 값을 갭 건너편으로 복사"하는 원자적 단계의 반복입니다. 오른쪽 이동 한 단계는 `buffer[gapEnd]`(오른쪽 텍스트의 맨 앞 글자)를 `buffer[gapStart]`(갭의 첫 칸)로 옮긴 뒤 양쪽 경계를 함께 +1 하므로, 그 글자가 왼쪽 텍스트의 새 마지막 글자가 됩니다. 왼쪽 이동은 대칭입니다. 매 단계가 삼분할 불변식을 보존하므로, 여러 단계를 반복해도 불변식은 깨지지 않습니다.
- **grow**: 새 버퍼를 2배 크기로 만들고 왼쪽 텍스트는 앞쪽 그대로, 오른쪽 텍스트는 새 버퍼의 꼬리로 복사합니다. 두 텍스트 조각의 **내용과 순서**는 전혀 바뀌지 않고 가운데 갭만 커지므로, `getText()`가 반환할 문자열은 `grow()` 전후로 동일합니다.

여기서 헷갈리기 쉬운 포인트가 두 가지 있습니다.

- **`delete()`가 "문자를 지운다"는 이름 때문에, `buffer` 배열에서 값이 실제로 사라진다고 생각하기 쉽습니다.** 실제로는 `gapStart` 인덱스만 줄어들 뿐, 그 위치의 문자는 배열에 그대로 남아 있습니다. 다만 이제 갭 범위 안에 들어가서 `getText()`가 절대 읽지 않을 뿐이에요. 실측으로 확인해 보면, `capacity=8` 버퍼에 `"abc"`를 넣고(`buffer = [97, 98, 99, 0, 0, 0, 0, 0]`) `delete()`를 세 번 연속 호출해도 `buffer` 배열은 `[97, 98, 99, 0, 0, 0, 0, 0]` 그대로입니다 — 바뀌는 건 `gapStart`가 `3 → 0`이라는 것뿐이고, 그 결과 `getText()`만 `""`로 바뀝니다.
- **`moveCursor`의 두 while 루프에서 "감소·증가"와 "복사"의 순서가 서로 반대라는 점을 놓치기 쉽습니다.** 오른쪽 이동은 "먼저 복사하고 나중에 증가"(`buffer[gapStart] = buffer[gapEnd]` 후 `gapStart++; gapEnd++`)이고, 왼쪽 이동은 "먼저 감소하고 나중에 복사"(`gapStart--; gapEnd--` 후 `buffer[gapEnd] = buffer[gapStart]`)입니다. 왼쪽 이동에서 이 순서를 뒤집어 감소 전에 복사부터 하면, `gapStart=3, gapEnd=8`(텍스트 `"Hi!"`)인 상태에서 `moveCursor(1)`을 호출했을 때 정답은 텍스트가 그대로 `"Hi!"`여야 하는데, 실제로는 `"H!"`가 나옵니다 — `i`가 통째로 사라지는 구체적인 오답입니다(실측 확인).

잠깐, 확인 하나만 해 볼까요? `capacity=8` 버퍼에 `"Hi!"`를 넣은 뒤(`gapStart=3, gapEnd=8`) 바로 `moveCursor(3)`을 호출하면 무슨 일이 일어날까요? 정답은 "아무 일도 없다"입니다 — `target === gapStart`이므로 두 while 루프 조건이 모두 거짓이라 즉시 반환되고, 복사도 배열 변경도 일어나지 않습니다.

엣지 케이스를 점검해 봅시다.

```text
빈 버퍼에서 delete()               → gapStart===0이므로 no-op, length는 0 그대로
갭이 꽉 찬 상태에서 insert()       → grow() 먼저 호출해 버퍼 2배 확장 후 삽입
moveCursor(음수)                   → 0으로 클램프
moveCursor(length() 초과)          → length()로 클램프
현재 커서 위치로 moveCursor(같은 값) → 두 while 루프 모두 즉시 종료, O(1)
```

## 아이디어를 코드로 옮기기

GapBuffer로 가는 길은 자연스러운 세 단계를 거칩니다.

**① 원형(naive array) — 매번 밀어낸다.**

```ts
class NaiveTextBuffer {
  private chars: string[] = [];
  insert(pos: number, char: string): void {
    this.chars.splice(pos, 0, char); // pos 뒤 원소를 전부 한 칸씩 민다 — O(n)
  }
}
```

`splice`가 내부적으로 뒤 원소를 전부 밀어내므로, 커서가 배열 앞쪽에 있을수록 한 번의 삽입 비용이 커집니다.

**② 개선(고정 크기 갭) — 갭은 도입했지만 늘릴 줄 모른다.**

"삽입할 위치에 미리 빈 공간을 확보해 두면 어떨까?"라는 관찰에서 갭을 도입합니다. 하지만 갭이 다 찼을 때 대비가 없다면:

```ts
class FixedGapBuffer {
  private buffer: string[];
  private gapStart = 0;
  private gapEnd: number;
  constructor(capacity: number) {
    this.buffer = new Array(capacity).fill("");
    this.gapEnd = capacity;
  }
  insert(char: string): void {
    // grow() 호출이 없다 — 갭이 가득 차도 그냥 쓴다
    this.buffer[this.gapStart] = char;
    this.gapStart++;
  }
  getText(): string {
    return this.buffer.slice(0, this.gapStart).join("") + this.buffer.slice(this.gapEnd).join("");
  }
}
```

`capacity=4`인 `FixedGapBuffer`에 `"abcde"`를 한 글자씩 넣으면, 네 번째 삽입까지는 `gapStart===gapEnd===4`가 되어 갭이 완전히 소진됩니다. 다섯 번째 `insert('e')`는 `buffer[4]`에 쓰는데, `gapEnd`는 여전히 4이므로 `gapStart(5)`가 `gapEnd(4)`를 넘어서 버립니다. 이 상태에서 `getText()`는 `buffer.slice(0, 5)`(`"abcde"`)와 `buffer.slice(4)`(`"e"`)를 이어붙여 **`"abcdee"`** — 마지막 글자가 중복되는 구체적인 오답을 냅니다(실측 확인).

**③ 최종 — 갭이 소진되기 전에 늘린다.**

```ts
class GapBuffer {
  private buffer: string[];
  private gapStart: number;
  private gapEnd: number;
  private _length: number;

  constructor(initialCapacity: number = 16) {
    this.buffer = new Array(initialCapacity).fill("");
    this.gapStart = 0;
    this.gapEnd = initialCapacity;
    this._length = 0;
  }

  private grow(): void {
    const newSize = this.buffer.length === 0 ? 1 : this.buffer.length * 2;
    const newBuffer = new Array(newSize).fill("");
    for (let i = 0; i < this.gapStart; i++) newBuffer[i] = this.buffer[i];
    const tailLen = this.buffer.length - this.gapEnd;
    for (let i = 0; i < tailLen; i++) {
      newBuffer[newSize - tailLen + i] = this.buffer[this.gapEnd + i];
    }
    this.gapEnd = newSize - tailLen;
    this.buffer = newBuffer;
  }

  insert(char: string): void {
    if (this.gapStart === this.gapEnd) this.grow();
    this.buffer[this.gapStart] = char;
    this.gapStart++;
    this._length++;
  }

  delete(): void {
    if (this.gapStart === 0) return;
    this.gapStart--;
    this._length--;
  }

  moveCursor(position: number): void {
    const target = Math.max(0, Math.min(position, this._length));
    while (this.gapStart < target) {
      this.buffer[this.gapStart] = this.buffer[this.gapEnd];
      this.gapStart++;
      this.gapEnd++;
    }
    while (this.gapStart > target) {
      this.gapStart--;
      this.gapEnd--;
      this.buffer[this.gapEnd] = this.buffer[this.gapStart];
    }
  }

  getCursorPosition(): number {
    return this.gapStart;
  }

  getText(): string {
    return this.buffer.slice(0, this.gapStart).join("") + this.buffer.slice(this.gapEnd).join("");
  }

  length(): number {
    return this._length;
  }
}
```

**가장 중요한 부분은 `insert`의 첫 줄, `if (this.gapStart === this.gapEnd) this.grow();`입니다.** 이 한 줄이 없으면 방금 본 `FixedGapBuffer`의 중복 버그로 되돌아갑니다. `grow()`가 갭 소진을 항상 삽입보다 먼저 감지하기 때문에, 호출자 입장에서 `insert`는 절대 실패하지 않는 것처럼 보입니다.

놓치기 쉬운 구현 지점을 정리하면:

- **`moveCursor`의 순서가 생명입니다.** 오른쪽 이동은 복사 → 증가, 왼쪽 이동은 감소 → 복사입니다. 방향마다 순서가 다르다는 것 자체가 헷갈리는 지점이에요.
- **`grow()`의 두 복사 루프는 서로 다른 목적지를 향합니다.** 왼쪽 텍스트는 새 버퍼의 **같은 인덱스**로, 오른쪽 텍스트는 새 버퍼의 **꼬리**(`newSize - tailLen` 이후)로 복사됩니다. 오른쪽 텍스트를 그대로 `gapEnd..`에 복사하면 새로 커진 갭 공간을 활용하지 못합니다.
- **`getCursorPosition()`과 `length()`는 계산이 아니라 캐시된 값을 반환합니다.** `gapStart`가 곧 커서 위치이고, `_length`는 매 연산에서 함께 갱신되므로 다시 셀 필요가 없습니다.

기억법: **"이동은 감소 먼저 왼쪽, 증가 먼저 오른쪽 — 방향을 먼저 정하고 나서 발을 뗀다."**

## 실행 시각화

`capacity=8`인 버퍼에 `insert('H')`, `insert('i')`, `insert('!')`를 차례로 실행하면 `gapStart`가 `0 → 3`으로 움직이며 텍스트는 `"Hi!"`가 됩니다. 이어서 `moveCursor(1)`을 호출하면 갭이 왼쪽으로 밀리면서 `i`, `!`가 배열 뒤쪽(인덱스 6, 7)으로 복사되지만 — 원래 자리(인덱스 1, 2)의 값은 지워지지 않고 그대로 남습니다(단지 이제 갭 안이라 무시될 뿐). `insert('e')`로 `"Hei!"`가 된 뒤 `delete()`를 하면 `gapStart`만 `2 → 1`로 줄어 `getText()`가 다시 `"Hi!"`를 돌려주는데, `buffer` 배열 자체는(인덱스 1의 `'e'` 잔재를 포함해) 마지막 두 프레임에서 완전히 동일합니다. array 패널은 버퍼의 코드포인트 전체, highlight는 현재 갭 범위, marked는 실제로 읽히는 텍스트 칸을 보여줍니다.

정리하면, GapBuffer는 "커서 옆에 빈 슬롯을 미리 파 두고, 그 슬롯을 채우거나 경계만 옮긴다"는 한 가지 아이디어로 커서 위치의 삽입·삭제를 $O(1)$로 만듭니다. 갭이 소진되면 `grow()`가 조용히 버퍼를 두 배로 늘려 amortized $O(1)$을 유지하고, 커서를 다른 위치로 옮길 때만 갭 전체를 밀어야 하므로 그 비용 $O(\lvert\Delta\rvert)$을 감수합니다. 이 트레이드오프가 "한곳에서 몰아치듯 타이핑하고 가끔 커서를 옮기는" 일반적인 편집 패턴과 정확히 들어맞기 때문에 실전 에디터들이 오랫동안 이 구조를 써 온 것입니다.
