# MonotonicStack — 튕겨 나가는 순간이 곧 답이다

## 한눈에 보는 컨셉

단조 스택(Monotonic Stack)은 원소를 하나씩 밀어 넣으면서, 스택에 쌓인 값이 항상 오름차순 또는 내림차순을 유지하도록 관리하는 보조 스택이에요. 비결은 단 하나입니다 — 새 원소가 스택의 단조 규칙을 깨뜨려서 어떤 원소가 튕겨 나가는(pop되는) 바로 그 순간, 그 원소의 "다음/이전 조건을 만족하는 원소"가 새 원소로 확정된다는 것입니다. 이 덕분에 각 원소가 스택에 최대 한 번 push, 한 번 pop되는 것만으로, 배열 전체에 대한 "다음 더 큰/작은 원소" 질의를 O(n)에 한 번에 풀 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 단조 스택을 떠올리세요.

- 배열의 각 원소에 대해 "다음(또는 이전)에 처음 나타나는 더 크거나/작은 원소의 위치"를 묻는다
- 구간 전체의 최댓값이 아니라 "조건을 만족하는 가장 가까운 하나"를 원한다
- 정렬되지 않은 배열을 한 번의 선형 스캔만으로 처리해야 한다(미리 정렬하면 원래 인덱스 순서 정보가 사라져 버립니다)
- 순진하게 짜면 "각 원소마다 나머지를 훑는" 이중 반복문이 자연스럽게 나오는 문제(주가 분석, 히스토그램, 온도 대기일수 등)

이중 반복 대비 효과를 체감해 볼게요.

```text
n = 10,000    이중 반복 O(n²) ≈ 10^8회 비교   → 수백 ms
              단조 스택 O(n)  ≈ 10^4회 push/pop → 1ms 미만

n = 100,000   이중 반복 O(n²) ≈ 10^10회 비교  → 시간 제한(보통 1~2초) 초과
              단조 스택 O(n)  ≈ 10^5회 push/pop → 수 ms
```

이중 반복은 매 원소마다 나머지 원소를 다시 훑기 때문에 원소 수가 늘어날수록 비교 횟수가 제곱으로 불어납니다. 단조 스택은 "한 번 pop되면 다시는 스택에 안 올라온다"는 성질 덕분에, 전체 push/pop 횟수의 합이 아무리 많아도 $2n$을 넘지 않아요.

비슷한 용도의 다른 자료구조와는 이렇게 구분하세요 — 구간 전체의 최댓값·최솟값을 자주 갱신·질의해야 한다면 세그먼트 트리나 스파스 테이블을, 윈도우가 고정 크기로 미끄러지며 그 안의 최댓값을 구해야 한다면 단조 데크(Monotonic Deque)를, "각 원소 기준으로 가장 가까운 조건 만족 원소 하나"만 필요하다면 단조 스택을 쓰세요.

### 문제 사례와 적용 예시

- **주가 분석**: 오늘 이후 처음으로 오늘보다 비싼 날이 언제인지 대량의 주가 기록에서 한 번에 구합니다. `nextGreater`가 정확히 이 질의예요.
- **Daily Temperatures(며칠을 기다려야 더 따뜻해지는가)**: `nextGreater`로 "다음 더 높은 온도의 인덱스"를 구한 뒤, 그 인덱스에서 현재 인덱스를 빼면 "기다려야 하는 날 수"가 나옵니다.
- **히스토그램에서 가장 큰 직사각형(Largest Rectangle in Histogram)**: 각 막대가 좌우로 얼마나 넓게 자신의 높이를 유지할 수 있는지를 `nextSmaller`(오른쪽 경계)와 그 반대 방향 스캔(왼쪽 경계)으로 구해서, 막대별 최대 사각형 넓이를 O(n)에 계산합니다.
- **코딩 테스트 맥락**: "빌딩이 일렬로 서 있을 때, 각 빌딩에서 오른쪽을 보면 처음 나오는 자신보다 높은 빌딩이 몇 번째인가" 같은 문제가 이 자료구조를 직접 요구하는 전형적인 형태입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드에서는 아래 인터페이스로 `MonotonicStack`을 정의합니다. 인스턴스 자체는 상태를 갖지 않는 무상태 유틸리티이고, "스택"은 각 메서드가 호출될 때마다 새로 구성하는 로컬 작업 구조예요.

```ts
class MonotonicStack {
  nextGreater(arr: number[]): number[]  // 각 i의 오른쪽에서 처음 나오는 arr[j] > arr[i]의 j, 없으면 -1
  prevGreater(arr: number[]): number[]  // 각 i의 왼쪽에서 처음 나오는 arr[j] > arr[i]의 j, 없으면 -1
  nextSmaller(arr: number[]): number[]  // 각 i의 오른쪽에서 처음 나오는 arr[j] < arr[i]의 j, 없으면 -1

  // 메서드 내부에서 구성하는 로컬 스택: 값이 아니라 "인덱스"를 저장한다
  // stack: number[]
}
```

스택이 지켜야 할 불변식은 두 가지입니다.

1. **단조성.** 스택에 담긴 인덱스들을 바닥(bottom)에서 꼭대기(top) 순서로 나열했을 때, 그 값들은 `nextGreater`/`prevGreater` 계열에서는 비증가, `nextSmaller` 계열에서는 비감소를 유지합니다. 스택 내용을 인덱스 수열 $S = (S_0, S_1, \dots, S_{k-1})$($S_0$이 바닥)이라 하면:
   $$\forall\, 0 \le p < q < k:\quad arr[S_p] \ge arr[S_q] \quad (\text{next/prevGreater 계열, 비증가})$$
2. **미확정성.** 스택에 남아 있는 인덱스는 아직 답이 결정되지 않은 인덱스뿐입니다. 어떤 인덱스가 pop되는 순간, 그 인덱스의 답은 바로 그 자리에서 확정되고 다시는 스택에 오르지 않습니다.

`nextGreater` 진행 중 임의의 한 시점을 그려 보면 이렇습니다(값이 큰 쪽이 바닥, 작은 쪽이 top).

```text
스택 (bottom → top, 인덱스와 그 값)

bottom [ i=0, arr[i]=9 ]
       [ i=3, arr[i]=6 ]
       [ i=5, arr[i]=6 ]
top    [ i=7, arr[i]=2 ]   ← 새 원소와 가장 먼저 비교되는 자리

값 기준 bottom→top: 9 ≥ 6 ≥ 6 ≥ 2  (비증가 유지, 인덱스는 크기 순서가 아니라 push된 순서)
```

이 자료구조가 제공하는 세 액션은 다음과 같습니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `nextGreater(arr)` | 왼→오 스캔, 단조 비증가 스택 유지. pop되는 순간 "다음 더 큰 원소"가 확정 | O(n) 시간, O(n) 공간 |
| `prevGreater(arr)` | 왼→오 스캔, 단조 비증가 스택 유지. push 직전 스택 top이 곧 "이전 더 큰 원소" | O(n) 시간, O(n) 공간 |
| `nextSmaller(arr)` | 왼→오 스캔, 단조 비감소 스택 유지. pop되는 순간 "다음 더 작은 원소"가 확정 | O(n) 시간, O(n) 공간 |

핵심 연산 두 개를 실제 배열 `arr = [2, 1, 2, 4, 3]`로 자세히 볼게요(아래 실행 결과는 뒤의 "아이디어를 코드로 옮기기" 코드를 직접 실행해서 확인한 값입니다).

**① `nextGreater`의 pop 사이클 — `j=3`, `arr[3]=4` 처리 순간.**

```text
Before (j=3 진입 전 스택):        pop 진행 (arr[3]=4와 비교):              After (push(3) 완료):
top    [ i=2, arr=2 ]  ─┐          arr[2]=2 < 4 → pop, result[2]=3         top/bottom [ i=3, arr=4 ]
bottom [ i=0, arr=2 ]  ─┘          arr[0]=2 < 4 → pop, result[0]=3
                                    스택 완전히 빔
```

두 원소가 같은 값(4보다 작은 2)을 갖고 있어도 순서대로 하나씩 비교하며 pop한다는 점이 포인트입니다 — 한 번에 "다 지워도 되는지" 미리 판단하지 않고, top부터 차례로 비교합니다.

**② `prevGreater`의 방향 — `i=2`, `arr[2]=2` 처리 순간.**

```text
Before (i=2 진입 전 스택):        pop 진행 (arr[2]=2와 비교):              After (push(2) 완료):
top    [ i=1, arr=1 ]  ─┐          arr[1]=1 <= 2 → pop                    top/bottom [ i=2, arr=2 ]
bottom [ i=0, arr=2 ]  ─┘          arr[0]=2 <= 2 → pop(같은 값도 제거)     result[2] = -1 (스택 빔)
```

`nextGreater`는 pop되는 원소의 답을 채우지만, `prevGreater`는 **pop을 끝내고 남은 top**이 현재 원소의 답이 됩니다 — 같은 왼→오 스캔인데도 "누구의 답을 채우는가"가 반대라는 점이 이 두 연산의 결정적 차이예요.

### 왜 모순 없이 작동하는가

**단조성이 왜 깨지지 않는가.** `nextGreater`에서 새 원소 `arr[j]`를 넣기 전에, `arr[j]`보다 작은 top을 모두 pop합니다. pop이 끝난 시점에는 top이 없거나(스택 빔) `arr[j]` 이상인 값만 남아 있으므로, 거기에 `j`를 push해도 "bottom→top 비증가"는 그대로 유지됩니다. 빈 스택에서 시작해 이 과정을 귀납적으로 반복하므로, 스캔 중 어느 시점에도 불변식 1이 성립합니다.

**미확정성이 왜 옳은가.** `arr[stack.top] < arr[j]`로 pop되는 인덱스 `i`를 봅시다. `i`와 `j` 사이에 있던 원소들은 이미 스캔되면서 `i`보다 먼저 pop되었거나(그렇다면 그 값은 `arr[i]`보다 컸다는 뜻인데, 그 경우 `i`가 아니라 그 원소가 먼저 확정됐어야 하므로 모순), 혹은 아직 스택에 남아 `arr[i]` 이하였다는 뜻입니다. 즉 `i`와 `j` 사이의 모든 원소는 `arr[i]`보다 크지 않았고, `j`에서 처음으로 `arr[i]`보다 큰 값이 나온 것이므로 `j`가 정확히 "다음 더 큰 원소"입니다.

**복잡도가 왜 O(n)인가.** 각 인덱스는 정확히 한 번 push되고, 최대 한 번 pop됩니다. 전체 반복문의 pop 횟수 합은 push 횟수 합(=n)을 넘을 수 없으므로, while 루프 안쪽까지 합쳐도 총 연산은 $O(2n) = O(n)$입니다.

잠깐, 확인 하나만 해 볼까요? `arr = [5, 5, 5]`에 `nextGreater`를 실행하면 결과가 어떻게 나올까요? — 모든 값이 같아서 어느 쪽도 "더 크지" 않으니 아무도 pop되지 않고, 세 인덱스 모두 결과는 `-1`입니다. 실제로 실행해 보면 `[-1, -1, -1]`이 나와요.

**여기서 헷갈리기 쉬운 포인트**는 세 가지입니다.

- **`nextGreater`용 pop 조건(`<`)과 `prevGreater`용 pop 조건(`<=`)을 섞어 쓰는 것입니다.** `arr = [2, 1, 2, 4, 3]`에서 `nextGreater`의 pop 조건을 실수로 `<=`(같아도 pop)로 쓰면 어떻게 될까요? 정상 구현은 `[3, 2, 3, -1, -1]`을 내놓지만, `<=`로 바꾼 버그 버전은 인덱스 0의 답이 `2`로 잘못 나옵니다 — 결과가 `[2, 2, 3, -1, -1]`이 됩니다. `arr[2]=2`는 `arr[0]=2`보다 "더 크지" 않은데, `<=`가 이 둘을 같다고 취급해 pop해 버린 탓입니다.
- **반대로 `prevGreater`의 pop 조건(`<=`)을 `nextGreater`처럼 `<`로 좁혀 쓰는 것입니다.** `arr = [4, 4, 4]`에서 정상 `prevGreater`는 모든 값이 같으므로 `[-1, -1, -1]`을 내놓습니다. 그런데 pop 조건을 `<`로 바꾸면, 인덱스 1을 처리할 때 top(인덱스 0, 값 4)이 "4 < 4가 아니므로" pop되지 않고 그대로 답으로 채택되어 버립니다. 실제 결과는 `[-1, 0, 1]`로, 동일한 값끼리 서로를 "이전 더 큰 원소"라고 잘못 가리키게 됩니다.
- **스택에 값이 아니라 인덱스를 저장해야 한다는 점입니다.** 값만 저장하면 나중에 "몇 번째 원소였는지" 알 수 없어서 `result[i] = j`를 채울 방법이 없어요. 인덱스를 저장해야 `arr[stack.top]`으로 값도 조회하고 `result[i]`도 채울 수 있습니다.

엣지 케이스를 실제 실행값으로 점검해 둡니다.

```text
빈 배열 []                → nextGreater([]) = []
단일 원소 [5]              → nextGreater([5]) = [-1]           (비교 대상이 없음)
동일값 [4, 4, 4]           → nextGreater = [-1,-1,-1], prevGreater = [-1,-1,-1]  (strict 비교라 아무도 안 됨)
음수 포함 [-1, -3, -2, 0]  → nextGreater = [3, 2, 3, -1]        (대소 비교는 부호와 무관하게 동일)
```

## 아이디어를 코드로 옮기기

원형(brute force)에서 출발해서, 왜 다음 단계로 가야 하는지를 짚으며 최종 구현까지 올라갑니다.

**원형 — 각 인덱스에서 오른쪽을 전부 훑기.** 가장 직관적인 접근이에요.

```ts
function bruteNextGreater(arr: number[]): number[] {
  const n = arr.length;
  const result = new Array<number>(n).fill(-1);
  for (let i = 0; i < n; i++) {
    for (let j = i + 1; j < n; j++) {
      if (arr[j]! > arr[i]!) {
        result[i] = j;
        break;
      }
    }
  }
  return result;
}
```

정확하지만 최악의 경우(단조 감소 배열, 아무도 다음 더 큰 원소를 못 찾는 경우) 안쪽 루프가 매번 끝까지 돌아 O(n²)입니다. n=10^5이면 시간 제한을 넘깁니다 — "이런 단서가 보이면"에서 본 비용 표 그대로예요.

**개선 — 매번 다시 훑지 않고, 스택에 "아직 답을 모르는 인덱스"만 남긴다.** 관찰은 이렇습니다: `arr[j]`를 처리할 때, 그보다 작은 값을 가진 인덱스들은 이제 막 자신의 "다음 더 큰 원소"를 찾았으니 더는 들고 있을 필요가 없습니다. 이 관찰을 그대로 코드로 옮기면:

```ts
function stackNextGreater(arr: number[]): number[] {
  const n = arr.length;
  const result = new Array<number>(n).fill(-1);
  const stack: number[] = []; // 단조 비증가, 인덱스 저장
  for (let j = 0; j < n; j++) {
    while (stack.length > 0 && arr[stack[stack.length - 1]!]! < arr[j]!) {
      result[stack.pop()!] = j;
    }
    stack.push(j);
  }
  return result;
}
```

각 인덱스가 최대 한 번 push, 한 번 pop되므로 O(n)입니다. 이제 같은 골격을 `prevGreater`(방향과 "누구의 답을 채우는지"만 다름), `nextSmaller`(부등호 방향만 반전)에도 적용해 하나의 클래스로 묶습니다.

**최종 — `MonotonicStack` 클래스.**

```ts
class MonotonicStack {
  nextGreater(arr: number[]): number[] {
    const n = arr.length;
    const result = new Array<number>(n).fill(-1);
    const stack: number[] = []; // 인덱스 저장, 값 기준 단조 비증가

    for (let j = 0; j < n; j++) {
      while (stack.length > 0 && arr[stack[stack.length - 1]!]! < arr[j]!) {
        const i = stack.pop()!;
        result[i] = j;
      }
      stack.push(j);
    }
    return result;
  }

  prevGreater(arr: number[]): number[] {
    const n = arr.length;
    const result = new Array<number>(n).fill(-1);
    const stack: number[] = []; // 인덱스 저장, 값 기준 단조 비증가

    for (let i = 0; i < n; i++) {
      while (stack.length > 0 && arr[stack[stack.length - 1]!]! <= arr[i]!) {
        stack.pop();
      }
      result[i] = stack.length > 0 ? stack[stack.length - 1]! : -1;
      stack.push(i);
    }
    return result;
  }

  nextSmaller(arr: number[]): number[] {
    const n = arr.length;
    const result = new Array<number>(n).fill(-1);
    const stack: number[] = []; // 인덱스 저장, 값 기준 단조 비감소

    for (let j = 0; j < n; j++) {
      while (stack.length > 0 && arr[stack[stack.length - 1]!]! > arr[j]!) {
        const i = stack.pop()!;
        result[i] = j;
      }
      stack.push(j);
    }
    return result;
  }
}
```

가장 중요한 부분은 각 메서드의 while 조건 부등호입니다. `nextGreater`는 `<`, `prevGreater`는 `<=`, `nextSmaller`는 `>`를 씁니다. 이 부등호 하나가 "strict 비교(같으면 답 아님)"와 "동일값 처리 방향"을 전부 결정하기 때문에, 위 헷갈리기 쉬운 포인트에서 본 것처럼 하나만 잘못 베껴도 결과가 조용히 틀어집니다.

- `nextGreater`/`nextSmaller`는 **pop되는 인덱스**의 답을 채웁니다(`result[stack.pop()!] = j`).
- `prevGreater`는 **pop을 마치고 남은 top**이 현재 인덱스의 답입니다(`result[i] = stack.length > 0 ? stack[...] : -1`, 그 다음에 push).
- 세 메서드 모두 `stack.push(...)`를 while 루프 **다음에** 실행합니다. 루프 안에서 push해 버리면 아직 비교가 끝나지 않은 원소를 스택에 올리게 됩니다.

기억법: "pop이 정리를 끝낸 뒤에야 새 식구를 들인다."
