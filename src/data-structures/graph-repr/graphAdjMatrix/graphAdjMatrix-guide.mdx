# GraphAdjMatrix — 정점 쌍마다 칸 하나씩 내주는 그래프

## 한눈에 보는 컨셉

그래프의 정점이 $V$개면 $V \times V$ 크기의 표(행렬)를 만들어 두고, `matrix[u][v]` 칸에 "u에서 v로 가는 간선의 가중치"를 적어 두는 방식이에요. 간선이 없으면 그 칸은 비워 둡니다(`undefined`). 비결은 단 하나 — **"u와 v가 연결되어 있나?"라는 질문을 배열 인덱싱 한 번으로 끝낸다**는 것입니다. 그 대가로 정점 수의 제곱만큼 칸을 미리 마련해 둬야 해서, 정점이 적고 간선이 촘촘한 밀집 그래프(dense graph)에서 특히 유리합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 인접 행렬을 떠올리세요.

- 정점 수 $V$가 그리 크지 않다(수백~수천 단위) — $V^2$ 칸을 감당할 수 있다
- "이 두 정점, 연결돼 있나?"를 **반복적으로** 물어본다 — 매번 O(1)로 답해야 유리하다
- 모든 정점 쌍의 관계를 다뤄야 한다(Floyd-Warshall 같은 전체 쌍 최단 경로 알고리즘)

인접 리스트(각 정점마다 이웃 목록만 저장)와 비교하면 이런 시소 관계가 보입니다.

```text
연산            인접 리스트       인접 행렬
공간            O(V + E)         O(V²)
addEdge         O(1)             O(1)
removeEdge      O(degree)        O(1)      ← 행렬이 유리
hasEdge         O(degree)        O(1)      ← 행렬이 유리
weight 조회      O(degree)        O(1)      ← 행렬이 유리
neighbors       O(degree)        O(V)      ← 리스트가 유리
BFS / DFS       O(V + E)         O(V²)
```

간선이 적은 희소 그래프(sparse, $E \ll V^2$)라면 인접 리스트가 공간도 적게 쓰고 순회도 빠릅니다. 반대로 간선이 많아 $E \approx V^2$에 가까운 밀집 그래프라면 두 방식의 순회 복잡도가 사실상 같아지고, 그 대신 행렬 쪽은 `hasEdge`·`weight`가 항상 O(1)이라는 이점만 남아요. **선택 기준은 한 줄로 요약됩니다 — 간선 존재 확인이 잦고 그래프가 조밀하면 행렬, 이웃 목록 순회가 잦고 그래프가 성기면 리스트.**

### 문제 사례와 적용 예시

- **전체 쌍 최단 경로(Floyd-Warshall)**: 도시 30개짜리 물류망에서 모든 도시 쌍의 최단 거리를 구할 때, `dist[i][j]` 배열을 직접 갱신하는 이 알고리즘은 인접 행렬과 자료구조가 이미 똑같아 변환 비용이 없습니다.
- **소규모 소셜 그래프의 팔로우 여부 조회**: 사용자 수가 제한된 그룹(동아리, 팀 채널 등)에서 "A가 B를 팔로우하나?"를 매 요청마다 O(1)로 답해야 하는 경우.
- **격자/보드 게임의 이동 가능 여부 판정**: 체스판이나 퍼즐 게임처럼 칸(정점) 수가 고정돼 있고 두 칸이 인접한지 자주 물어보는 상황.
- **코딩 테스트 맥락**: "정점 수 ≤ 1000, 간선 존재 여부 질의가 다수 주어진다" 같은 제약이 보이면, 인접 리스트로 매번 이웃을 뒤지는 대신 행렬 한 칸을 확인하는 쪽이 시간 제한을 통과시켜 줍니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 이 가이드에서는 다음 인터페이스로 통일합니다.

```ts
class GraphAdjMatrix {
  private matrix: (number | undefined)[][]; // V×V, matrix[u][v] = 가중치 | undefined
  private size: number;                     // 정점 수 V
  private directed: boolean;                // 방향 그래프 여부
}
```

지켜야 할 불변식은 세 가지입니다.

1. **크기 고정**: $\text{matrix}$는 항상 $V \times V$ 정사각 배열이고, $\forall u, v \in [0, V) : \text{matrix}[u][v] \in \mathbb{Z}^{+} \cup \{\text{undefined}\}$.
2. **대칭성(무방향일 때만)**: $\text{directed} = \text{false} \Rightarrow \forall u, v : \text{matrix}[u][v] = \text{matrix}[v][u]$.
3. **존재 판정 일치**: $\text{hasEdge}(u, v) \iff \text{matrix}[u][v] \neq \text{undefined}$ — 이 동치가 깨지면 `hasEdge`와 `weight`가 서로 다른 답을 낼 수 있습니다.

작은 예로 감을 잡아 봅시다. 정점 4개(서울=0, 부산=1, 대구=2, 광주=3)짜리 무방향 그래프에서 `addEdge(0, 1, 325)`와 `addEdge(1, 2, 88)`만 실행한 상태를 행렬로 그리면:

```text
        0     1     2     3
   0 [  ·   325    ·     ·  ]
   1 [ 325   ·    88     ·  ]
   2 [  ·   88     ·     ·  ]
   3 [  ·    ·     ·     ·  ]

· = undefined(간선 없음).  행 0과 열 0을 봤을 때 matrix[0][1] = matrix[1][0] = 325 — 대칭!
정점 3은 행·열 전체가 비어 있음 — 아직 어디와도 연결되지 않은 고립 정점.
```

**액션(연산)** — 이 자료구조가 제공하는 연산 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `addEdge(u, v, weight=1)` | 간선 추가(무방향이면 양쪽 칸 동시 갱신, 기존 간선 있으면 덮어씀) | O(1) |
| `removeEdge(u, v)` | 간선 제거(무방향이면 양쪽 칸 동시 `undefined`) | O(1) |
| `hasEdge(u, v)` | 두 정점 사이 간선 존재 여부 | O(1) |
| `weight(u, v)` | 간선 가중치, 없으면 `undefined` | O(1) |
| `neighbors(v)` | v의 이웃 정점 목록 | O(V) |
| `bfs(start)` | 너비 우선 탐색 방문 순서 | O(V²) |
| `dfs(start)` | 깊이 우선 탐색 방문 순서 | O(V²) |
| `vertexCount()` | 정점 수 | O(1) |

핵심 연산 두 개를 자세히 볼게요.

**① addEdge — "무방향이면 거울처럼 두 칸을 동시에 쓴다"**

```text
Before: addEdge(1, 2, 88) 호출 전
        0     1     2     3
   0 [  ·   325    ·     ·  ]
   1 [ 325   ·     ·     ·  ]
   2 [  ·    ·     ·     ·  ]
   3 [  ·    ·     ·     ·  ]

After: addEdge(1, 2, 88) 실행 직후 — matrix[1][2]와 matrix[2][1] 둘 다 88
        0     1     2     3
   0 [  ·   325    ·     ·  ]
   1 [ 325   ·    88     ·  ]
   2 [  ·   88     ·     ·  ]
   3 [  ·    ·     ·     ·  ]
```

**② bfs — "정점 하나를 꺼낼 때마다 행 전체를 훑는다"**

`bfs(0)`을 위 행렬(간선 두 개가 들어간 상태)에서 실행하면:

```text
단계               visited        queue      result
시작               {0}            [0]        []
0 방문, 행 0 스캔   {0,1}          [1]        [0]     ← matrix[0][1]=325 발견
1 방문, 행 1 스캔   {0,1,2}        [2]        [0,1]   ← matrix[1][2]=88 발견 (matrix[1][0]은 이미 방문)
2 방문, 행 2 스캔   {0,1,2}        []         [0,1,2] ← matrix[2][1]은 이미 방문, 더 나올 이웃 없음
큐 빔 → 종료                                  [0,1,2]
```

정점마다 행 전체(길이 $V$)를 스캔하므로 방문 $V$번 × 스캔 $O(V)$ = **O(V²)**. 정점 3은 어느 행에도 걸리지 않아 끝내 방문되지 않습니다.

### 왜 모순 없이 작동하는가

**대칭 불변식이 깨지지 않는 이유**를 귀납으로 봅시다. 빈 행렬(모두 `undefined`)은 자명하게 대칭입니다. 이제 `addEdge`와 `removeEdge`가 항상 "무방향이면 두 칸을 한 호출 안에서 함께" 갱신한다고 하면, 그 직후에도 대칭이 유지돼요. 어떤 시점까지 대칭이었다면 다음 호출 이후에도 대칭이라는 뜻이므로, 모든 호출 이후 행렬은 항상 대칭입니다.

잠깐, 확인 하나만 해 볼까요? `directed=true`인 그래프에서 `addEdge(0, 1, 7)`만 호출했다면 `hasEdge(1, 0)`은 무엇일까요? 답은 **false**입니다 — 방향 그래프는 애초에 대칭 불변식 자체가 적용되지 않고, `matrix[0][1]`만 채워지기 때문이에요(실제로 `gd.hasEdge(1, 0)`을 실행하면 `false`가 나옵니다).

**여기서 헷갈리기 쉬운 포인트**는 무방향 그래프에서 "한쪽 칸만 갱신해도 괜찮겠지"라는 착각입니다. `addEdge`를 `matrix[u][v] = weight`만 쓰고 `matrix[v][u]`를 빠뜨리면 어떻게 될까요? 실제로 그렇게 짠 버전으로 `addEdge(0, 1, 40)`을 실행해 보면:

```text
hasEdge(0, 1) → true   (matrix[0][1] = 40 이 채워졌으니까)
hasEdge(1, 0) → false  (matrix[1][0]은 여전히 undefined — 대칭이 깨짐!)
neighbors(0)  → [1]
neighbors(1)  → []     ← 0을 이웃으로 보지 못한다. 같은 간선인데 방향에 따라 답이 다르다!
```

"무방향 간선인데 한쪽만 보인다"는 것이 바로 이 버그의 증상입니다. 무방향 그래프에서 `addEdge`·`removeEdge`는 **반드시 두 칸을 한 번에** 건드려야 합니다.

또 하나 짚어 둘 점은 **BFS/DFS가 O(V²)라는 게 항상 손해는 아니라는 것**입니다. 인접 리스트의 O(V+E)가 이론적으로는 더 좋아 보이지만, 밀집 그래프에서는 $E \approx V^2$이므로 두 식이 사실상 같아집니다 — "행렬이 항상 느리다"는 생각은 희소 그래프에만 해당하는 이야기예요.

엣지 케이스를 점검해 봅니다.

```text
자기 루프 matrix[v][v] = w   → 허용됨. bfs에서 v가 이미 visited이므로 자기 자신을 다시 큐에 넣지 않아 무한루프 없음
addEdge를 같은 (u,v)에 두 번  → 나중 값으로 덮어씀(가중치 갱신 용도로 그대로 사용)
연결 안 된 정점에서 bfs      → 방문 결과에 아예 나타나지 않음(고립 정점은 결과에서 빠짐, 에러 아님)
directed 그래프의 역방향 질의 → hasEdge(v, u)가 hasEdge(u, v)와 다를 수 있음(정상 동작, 버그 아님)
```

## 아이디어를 코드로 옮기기

가이드가 정의한 인터페이스(`constructor(size, directed=false)`, 가중치 기본값 1)에 맞춘 구현입니다. 본문 코드 그대로 실행해 검증했습니다.

```ts
class GraphAdjMatrix {
  private matrix: (number | undefined)[][];
  private size: number;
  private directed: boolean;

  constructor(size: number, directed: boolean = false) {
    this.size = size;
    this.directed = directed;
    this.matrix = Array.from({ length: size }, () =>
      new Array<number | undefined>(size).fill(undefined),
    );
  }

  addEdge(u: number, v: number, weight: number = 1): void {
    this.matrix[u]![v] = weight;
    if (!this.directed) this.matrix[v]![u] = weight; // 무방향이면 거울 칸도 갱신
  }

  removeEdge(u: number, v: number): void {
    this.matrix[u]![v] = undefined;
    if (!this.directed) this.matrix[v]![u] = undefined;
  }

  hasEdge(u: number, v: number): boolean {
    return this.matrix[u]![v] !== undefined;
  }

  weight(u: number, v: number): number | undefined {
    return this.matrix[u]![v];
  }

  neighbors(v: number): number[] {
    const result: number[] = [];
    for (let u = 0; u < this.size; u++) {
      if (this.matrix[v]![u] !== undefined) result.push(u);
    }
    return result;
  }

  bfs(start: number): number[] {
    const visited = new Set<number>([start]);
    const queue: number[] = [start];
    const result: number[] = [];
    while (queue.length > 0) {
      const v = queue.shift()!;
      result.push(v);
      for (let u = 0; u < this.size; u++) {
        if (this.matrix[v]![u] !== undefined && !visited.has(u)) {
          visited.add(u);
          queue.push(u);
        }
      }
    }
    return result;
  }

  dfs(start: number): number[] {
    const visited = new Set<number>([start]);
    const stack: number[] = [start];
    const result: number[] = [];
    while (stack.length > 0) {
      const v = stack.pop()!;
      result.push(v);
      for (let u = this.size - 1; u >= 0; u--) {
        if (this.matrix[v]![u] !== undefined && !visited.has(u)) {
          visited.add(u);
          stack.push(u);
        }
      }
    }
    return result;
  }

  vertexCount(): number {
    return this.size;
  }
}
```

**가장 중요한 부분은 `addEdge`의 두 줄입니다.**

```ts
this.matrix[u]![v] = weight;
if (!this.directed) this.matrix[v]![u] = weight;
```

이 조건문 한 줄을 빠뜨리면 앞서 본 대칭 붕괴 버그가 그대로 재현됩니다. `removeEdge`도 완전히 같은 패턴이에요.

> 기억법: "무방향 간선을 그을 때는 양쪽에 도장을 함께 찍는다."

`dfs`에서 놓치기 쉬운 지점은 스캔 방향입니다. **`u`를 `size - 1`부터 거꾸로 훑어 스택에 push**하는 이유는, 스택이 LIFO라 나중에 push한 값이 먼저 pop되기 때문이에요. 정방향(`u = 0`부터)으로 push하면 어떻게 될까요? 이웃이 1, 2, 3인 정점 0에서 시작하는 `dfs(0)`을 정방향 스캔으로 돌리면 실제로 결과가 `[0, 3, 2, 1]`로 나옵니다(방문 순서가 인덱스 역순으로 뒤집힘) — 반대로 이 가이드처럼 역순 스캔을 쓰면 `[0, 1, 2, 3]`으로 자연스러운 오름차순이 나옵니다. "이웃을 낮은 인덱스부터 방문하고 싶다면 스택에는 반대 순서로 넣어야 한다"는 점이 스택 기반 DFS의 흔한 함정입니다.

`neighbors`와 `bfs`·`dfs`가 굳이 행 전체(O(V))를 스캔하는 이유는 행렬이 "고정 크기 2차원 배열"이라 이웃 목록을 별도로 유지하지 않기 때문입니다 — 대신 그 덕분에 경계 검사나 별도 자료구조 없이 단순 반복문만으로 이웃을 찾을 수 있어요.

정리하면, 인접 행렬은 "정점 쌍마다 칸 하나"라는 단순한 규칙 하나로 `hasEdge`·`weight`·`addEdge`·`removeEdge`를 전부 O(1)에 처리합니다. 무방향 그래프에서는 두 칸을 항상 함께 갱신하는 것만 지키면 대칭 불변식이 깨질 일이 없고, `neighbors`·`bfs`·`dfs`는 행 전체를 훑어야 해서 O(V)·O(V²)로 인접 리스트보다 느리지만 — 애초에 이 자료구조를 고르는 상황(밀집 그래프, 잦은 간선 조회)에서는 그 손해가 이점에 비해 작거나 아예 사라집니다.

## 스스로 점검하기

1. 정점 5개(0~4)짜리 무방향 그래프에 `addEdge(0,1)`, `addEdge(1,3)`, `addEdge(3,4)`만 추가했습니다. `bfs(0)`의 방문 순서를 손으로 그려 보고, 정점 2가 왜 결과에 나타나지 않는지 설명해 보세요.
