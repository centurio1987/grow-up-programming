# DAG — 순환이 생기려는 순간 간선을 거절하는 그래프

## 한눈에 보는 컨셉

DAG(Directed Acyclic Graph, 방향 비순환 그래프)는 방향 그래프 중에서 **어떤 정점에서 출발해도 자기 자신으로 되돌아오는 경로가 없는** 그래프예요. 비결은 간선을 "일단 추가하고 나중에 검사"하는 게 아니라, **간선을 넣는 그 순간 사이클이 생기는지 미리 확인해서 거절**해 버리는 것입니다. 그 덕분에 그래프는 항상 유효하고, 진입 차수(in-degree)가 0인 정점부터 순서대로 처리하는 위상 정렬(Kahn's Algorithm)이 언제나 성공하며 — 그 순서를 한 번 더 타면 최장 경로(critical path)까지 $O(V+E)$에 계산됩니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

문제 지문에서 다음 신호들이 보이면 DAG를 떠올리세요.

- "A가 끝나야 B를 시작할 수 있다"처럼 **선후 관계**가 여러 개 나열된다 (의존성 그래프)
- "실행 가능한 순서 하나를 찾아라" 또는 "모든 작업을 완료할 수 있는 순서를 나열하라"는 요구가 있다
- "이 의존성에 순환이 있으면 실패로 처리하라"처럼 **순환 자체가 논리적으로 있으면 안 된다**
- 각 작업에 소요 시간(가중치)이 있고 "전체를 마치는 데 최소 몇 분 걸리나"를 묻는다 (critical path)

naive하게 풀면 "아직 처리 안 된 작업 중 지금 실행 가능한 것"을 매번 전체 스캔으로 찾아야 해요. 이걸 $V$번 반복하면 $O(V^2)$입니다. DAG는 진입 차수를 미리 계산해 두고 큐만 소비하므로 스캔이 없습니다.

```text
naive: 매 라운드 "실행 가능한 작업"을 O(V) 전체 스캔 → V라운드 = O(V^2)
Kahn's: in-degree를 미리 계산 + 큐에 쌓아둔 것만 꺼냄     → O(V+E), 스캔 없음
```

비슷한 용도의 다른 자료구조와 헷갈릴 수 있어요. **사이클이 있어도 그 자체가 유효한 그래프**(소셜 네트워크, 상태 머신처럼 되돌아가는 게 정상)라면 일반 방향 그래프 + DFS 기반 사이클 검출/SCC(타잔 알고리즘)을 쓰고, **사이클이 생기면 안 되는 의존성**이라면 DAG로 표현해 간선을 넣는 시점에 막습니다. 트리와도 다릅니다 — 트리는 각 정점에 부모가 최대 1개지만, DAG는 한 정점이 여러 정점에 동시에 의존할 수 있어요(예: `package`가 `test`와 `lint` 둘 다에 의존하는 다이아몬드 모양).

### 문제 사례와 적용 예시

- **빌드 시스템**: Gradle·Bazel·Make에서 `compile → test → package → deploy` 같은 태스크 의존성을 표현하고, 어떤 순서로 실행해야 하는지 위상 정렬로 결정합니다.
- **강좌 선수과목 그래프**: "이 과목을 들으려면 저 과목을 먼저 들어야 한다"는 제약을 모아 두고, 전체 이수 가능한 순서가 있는지 확인합니다(순환 = 졸업 불가능).
- **스프레드시트 재계산**: 셀 A가 셀 B의 수식을 참조하면 B가 먼저 계산돼야 합니다. 순환 참조가 생기면 에러로 처리해야 하죠.
- **코딩 테스트 맥락**: "N개의 작업이 있고 일부 쌍에 `[a, b]`(b는 a보다 먼저)라는 선후 제약이 주어질 때, 모든 작업을 완료할 수 있는 순서를 찾아라(또는 불가능하면 판별하라)" — LeetCode의 Course Schedule 계열 문제가 정확히 이 형태입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 인접 리스트 하나와 간선 카운터만 있으면 됩니다.

```ts
interface DagEdge {
  to: number;
  weight: number;
}

class DAG {
  private adjList: Map<number, DagEdge[]>;  // 정점 -> (도착 정점, 가중치) 리스트
  private _edgeCount: number;               // 누적 간선 수
}
```

지켜야 할 불변식은 세 가지입니다.

1. **비순환성.** 위상 순서 $\sigma: V \to \{1, \dots, |V|\}$가 항상 존재해서, 모든 간선 $(u, v) \in E$에 대해 $\sigma(u) < \sigma(v)$가 성립한다. (즉 어떤 정점에서 출발해도 자기 자신으로 돌아오는 방향 경로가 없다.)
2. **간선 추가의 사전 조건.** `addEdge(u, v)`가 성공적으로 반환했다면, 그 호출 **이전**의 그래프에는 $v$에서 $u$로 가는 방향 경로가 존재하지 않았다.
3. **카운터 일관성.** `edgeCount() === `누적 `push`된 간선 객체 수. `addVertex`의 중복 호출이나 거절된 `addEdge`는 카운터를 건드리지 않는다.

빌드 태스크 예시(`compile(0) → test(1)`, `compile(0) → lint(2)`, `test(1) → package(3)`, `lint(2) → package(3)`, `package(3) → deploy(4)`)로 인접 리스트를 그려보면:

```text
adjList:
  0 → [ {to:1, w:3}, {to:2, w:1} ]
  1 → [ {to:3, w:2} ]
  2 → [ {to:3, w:1} ]
  3 → [ {to:4, w:1} ]
  4 → [ ]

정점 그림:
        0
       / \
     w=3  w=1
     /     \
    1       2
     \     /
    w=2  w=1
       \ /
        3
        |
       w=1
        |
        4
```

**액션(연산)** — 이 가이드가 구현하는 7종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `addVertex(v)` | 정점 등록(이미 있으면 무시) | $O(1)$ |
| `addEdge(u, v, weight=1)` | 사이클 검사 후 간선 추가, 사이클/자기루프면 throw | $O(V+E)$ |
| `topologicalSort()` | Kahn's Algorithm으로 위상 순서 계산 | $O(V+E)$ |
| `longestPath()` | 위상 순서 DP로 최장 가중치 경로 계산 | $O(V+E)$ |
| `hasCycle()` | 항상 `false` (애초에 사이클을 만들 수 없으므로) | $O(1)$ |
| `vertexCount()` | 정점 수 | $O(1)$ |
| `edgeCount()` | 간선 수 | $O(1)$ |

핵심 연산 두 개를 자세히 볼게요.

**① `addEdge`의 사이클 검사 — "v가 이미 u에 도달할 수 있는가?"**

$u \to v$ 간선을 추가하면 $v$에서 다시 $u$로 가는 경로가 이미 있을 때만 사이클이 닫힙니다($v \to \dots \to u \to v$). 그래서 간선을 넣기 **직전**에 "$v$에서 DFS를 시작해서 $u$에 닿는지"를 확인합니다.

```text
그래프: 0→1→3→4  (기존 간선)

addEdge(4, 0) 시도 — u=4, v=0
  Before: 0에서 4로 가는 경로는 있지만(0→1→3→4), 4→0 간선은 아직 없다.
  검사: v(=0)에서 DFS 시작 → 0→1→3→4 를 타고 결국 u(=4)에 도달! → true

  After: 사이클로 판정되어 throw. 그래프 상태는 변경 없음(간선 추가 안 됨).
```

**② `longestPath`의 DP — 위상 순서를 한 번 더 활용**

$dp[v]$를 "$v$까지 도달하는 최장 가중치 합"이라 정의하면 점화식은 이렇습니다.

$$dp[v] = \max_{(u, v) \in E} \big(dp[u] + \mathrm{weight}(u, v)\big), \quad dp[\text{시작 정점}] = 0$$

이 점화식이 성립하려면 $v$를 계산할 때 모든 선행 정점 $u$의 $dp[u]$가 **이미 확정**되어 있어야 합니다. 위상 순서로 처리하면 정의상 $u$가 $v$보다 먼저 오므로 이 조건이 항상 만족됩니다.

```text
위상 순서: [0, 1, 2, 3, 4]

Before (모두 0):        dp = {0:0, 1:0, 2:0, 3:0, 4:0}
v=0 처리 → 1:0+3=3, 2:0+1=1        dp = {0:0, 1:3, 2:1, 3:0, 4:0}
v=1 처리 → 3:3+2=5                 dp = {0:0, 1:3, 2:1, 3:5, 4:0}
v=2 처리 → 3 후보 1+1=2 (5보다 작아 무시)
v=3 처리 → 4:5+1=6                 dp = {0:0, 1:3, 2:1, 3:5, 4:6}
v=4 처리 → 나가는 간선 없음

After: max(dp.values()) = 6  ← longestPath()
```

### 왜 모순 없이 작동하는가

**비순환성이 귀납적으로 보존되는 이유**를 봅시다. 빈 그래프는 자명하게 사이클이 없습니다(기저 사례). 어느 시점에 그래프가 사이클이 없다고 가정하고, `addEdge(u, v)`가 호출됐다고 해봐요. 새로 생기는 유일한 간선은 $u \to v$뿐이므로, 이 호출로 사이클이 생긴다면 그 사이클은 반드시 새 간선을 지나야 하고, 그러려면 **기존 그래프에 $v$에서 $u$로 가는 경로**가 있어야 합니다(그래야 $v \to \dots \to u \to v$로 닫히니까요). `wouldCreateCycle`이 정확히 이 조건을 DFS로 검사해서, 경로가 있으면 거절합니다. 즉 사이클을 만들 수 있는 간선은 애초에 들어오지 못하므로, 불변식은 매 `addEdge` 호출 후에도 유지됩니다.

**여기서 헷갈리기 쉬운 포인트 첫 번째**: `wouldCreateCycle(u, v)`는 "$u$가 $v$에 도달할 수 있는가"가 아니라 "**$v$가 $u$에 도달할 수 있는가**"를 검사합니다. 방향을 반대로 짜기 쉬운데, 반대로 짜면 정상적인 DAG 간선까지 사이클로 오판합니다. 예를 들어 `0→1`, `1→2`가 있는 상태에서 `0→2`라는 **지름길**을 추가하는 건 완전히 유효해요(간접 경로 위에 직접 간선을 하나 더 놓는 것뿐, 사이클이 아닙니다). 그런데 "$u(=0)$가 $v(=2)$에 이미 도달 가능한가"를 검사하는 버그 버전은 `0→1→2` 경로를 발견하고 이를 사이클로 오판해 `0→2` 추가를 거부해 버립니다. 실제로 이렇게 짠 버전으로 `addEdge(0,1)`, `addEdge(1,2)`, `addEdge(0,2)`를 순서대로 실행해 보면 세 번째 호출에서 엉뚱하게 `throw`가 발생합니다.

**여기서 헷갈리기 쉬운 포인트 두 번째**: 자기 루프 `u === v`는 사실 `wouldCreateCycle` 로직만으로도 걸러집니다 — 탐색을 $v$에서 시작하자마자 `curr === u`(= v 자신)가 참이 되니까요. 그런데도 별도로 즉시 `throw`하는 이유는, 불필요한 DFS 호출 없이 더 명확한 에러 메시지("self-loop")를 주기 위해서입니다. 이 자기 루프 특수 처리를 빼도 정확성은 깨지지 않는다는 걸 기억해 두면, "왜 굳이 두 번 검사하나"라는 의문이 풀립니다.

**여기서 헷갈리기 쉬운 포인트 세 번째**: `longestPath`에서 순서가 왜 중요한지입니다. 만약 `topologicalSort()`를 쓰지 않고 `adjList`에 정점이 삽입된 순서 그대로 DP를 돌리면 어떻게 될까요? `addEdge(2, 3, 5)`를 먼저, `addEdge(1, 2, 1)`을 나중에 호출하면 `adjList`의 키 순서는 `2, 3, 1`이 됩니다(2와 3이 먼저 등록되고 1은 나중에 등록되니까요). 이 순서로 DP를 돌리면 $v=2$를 처리할 때 아직 $dp[1] \to dp[2]$ 갱신이 일어나기 전이라 $dp[2]=0$인 채로 $dp[3] = 0+5 = 5$가 확정돼 버립니다. 나중에 $v=1$을 처리하며 $dp[2]$가 1로 갱신되어도 $dp[3]$은 이미 지나쳐서 다시 계산되지 않습니다. 결과는 5. 하지만 실제 최장 경로는 $1 \to 2 \to 3 = 1 + 5 = 6$이에요. 삽입 순서 대신 `topologicalSort()`가 반환하는 순서(`[1, 2, 3]`)로 처리하면 정확히 6이 나옵니다. **DP 순서는 반드시 위상 순서여야 합니다.**

잠깐, 확인 하나만 해 볼까요? 위 빌드 태스크 그래프에 `addEdge(3, 0)`을 시도하면 어떻게 될까요? — $u=3, v=0$이니 "$v(=0)$가 $u(=3)$에 도달할 수 있는가"를 봐야 합니다. `0 → 1 → 3` 또는 `0 → 2 → 3` 경로로 0은 3에 도달할 수 있으니 `true` — 사이클로 판정되어 거절됩니다.

엣지 케이스도 점검해 둡시다.

```text
빈 그래프                     → topologicalSort() = [], longestPath() = 0
정점은 있지만 간선 없음(고립)  → topologicalSort()에 정점은 포함되지만 longestPath()는 0
같은 정점 중복 addVertex       → 무시. 기존 간선/카운트는 그대로 유지
자기 루프 addEdge(v, v)        → 즉시 throw("self-loop")
사이클을 만드는 addEdge         → throw("Cycle detected"), 그래프 상태 변경 없음
```

## 아이디어를 코드로 옮기기

이 가이드가 정의한 인터페이스 그대로 구현합니다. 가장 중요한 부분은 `addEdge`가 **먼저 사이클을 검사하고, 통과한 뒤에야 간선을 넣는다**는 순서예요 — 순서를 바꿔 먼저 넣고 나중에 검사하면, 검사에서 걸렸을 때 이미 망가진 그래프를 되돌려야 하는 번거로움이 생깁니다.

```ts
interface DagEdge {
  to: number;
  weight: number;
}

class DAG {
  private adjList: Map<number, DagEdge[]> = new Map();
  private _edgeCount = 0;

  addVertex(v: number): void {
    if (!this.adjList.has(v)) {
      this.adjList.set(v, []);
    }
  }

  addEdge(u: number, v: number, weight: number = 1): void {
    this.addVertex(u);
    this.addVertex(v);
    if (u === v) {
      throw new Error("Cycle detected: self-loop");
    }
    if (this.wouldCreateCycle(u, v)) {
      throw new Error("Cycle detected");
    }
    this.adjList.get(u)!.push({ to: v, weight });
    this._edgeCount++;
  }

  // u->v를 추가하기 "전"에 묻는다: v에서 출발해 u에 도달할 수 있는가?
  private wouldCreateCycle(u: number, v: number): boolean {
    const visited = new Set<number>([v]);
    const stack: number[] = [v];
    while (stack.length > 0) {
      const curr = stack.pop()!;
      if (curr === u) return true;
      for (const edge of this.adjList.get(curr) ?? []) {
        if (!visited.has(edge.to)) {
          visited.add(edge.to);
          stack.push(edge.to);
        }
      }
    }
    return false;
  }

  topologicalSort(): number[] {
    const inDegree = new Map<number, number>();
    for (const v of this.adjList.keys()) inDegree.set(v, 0);
    for (const [, edges] of this.adjList) {
      for (const e of edges) {
        inDegree.set(e.to, (inDegree.get(e.to) ?? 0) + 1);
      }
    }
    const queue: number[] = [];
    for (const [v, d] of inDegree) if (d === 0) queue.push(v);

    const result: number[] = [];
    while (queue.length > 0) {
      const v = queue.shift()!;
      result.push(v);
      for (const e of this.adjList.get(v) ?? []) {
        const nd = (inDegree.get(e.to) ?? 0) - 1;
        inDegree.set(e.to, nd);
        if (nd === 0) queue.push(e.to);
      }
    }
    return result;
  }

  longestPath(): number {
    const order = this.topologicalSort(); // 반드시 위상 순서로!
    const dp = new Map<number, number>();
    for (const v of order) dp.set(v, 0);

    for (const v of order) {
      for (const e of this.adjList.get(v) ?? []) {
        const candidate = (dp.get(v) ?? 0) + e.weight;
        if (candidate > (dp.get(e.to) ?? 0)) dp.set(e.to, candidate);
      }
    }

    let max = 0;
    for (const d of dp.values()) if (d > max) max = d;
    return max;
  }

  hasCycle(): boolean {
    return false;
  }

  vertexCount(): number {
    return this.adjList.size;
  }

  edgeCount(): number {
    return this._edgeCount;
  }
}
```

놓치기 쉬운 구현부를 짚어 둘게요.

- **`wouldCreateCycle`의 탐색 시작점은 `v`, 목표는 `u`.** 반대로 짜면 위에서 본 것처럼 유효한 지름길 간선까지 거부해 버립니다.
- **`addEdge`는 사이클 검사를 통과한 뒤에만 `push`합니다.** 검사와 삽입 순서를 바꾸지 마세요 — 먼저 넣고 나중에 검사하면 실패 시 롤백이 필요해집니다.
- **`longestPath`의 순회 순서는 `topologicalSort()`의 반환값이지, `adjList.keys()`의 삽입 순서가 아닙니다.** 이 둘을 혼동하면 위에서 본 대로(6 대신 5) 조용히 틀린 값이 나옵니다.
- **`topologicalSort`의 큐는 `shift()`로 앞에서 뺍니다(FIFO).** `pop()`으로 바꾸면 같은 in-degree 0 그룹 안에서 처리 순서가 뒤집혀, 결과 자체는 여전히 유효한 위상 순서지만 이 가이드의 트레이스와는 다른 순서가 나옵니다.

기억법: **"검사 먼저, 삽입 나중"** — `addEdge`든 다른 어떤 상태 변경이든, 실패할 수 있는 검사는 되돌릴 게 없는 상태에서 먼저 끝내 두는 게 안전합니다.

정리하면, DAG의 핵심은 "사이클을 사후에 찾아내는 것"이 아니라 **"애초에 만들 수 없게 막는 것"**입니다. `addEdge`가 매번 $O(V+E)$의 DFS로 이 방어선을 지키기 때문에, 이후의 `topologicalSort`와 `longestPath`는 사이클 걱정 없이 각각 $O(V+E)$에 정확한 결과를 냅니다 — 목표했던 성능과 정확성을 둘 다 얻는 거예요.
