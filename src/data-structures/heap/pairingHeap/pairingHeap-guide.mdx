# PairingHeap — 자식은 형제 체인 하나로, 병합은 두 번 훑어서

## 한눈에 보는 컨셉

PairingHeap(쌍 힙)은 각 노드가 자식 배열 대신 "첫 자식 하나(`leftChild`) + 오른쪽 형제(`nextSibling`)"만 갖는 단순한 트리 기반 힙이에요. 두 힙을 합칠 때는 두 루트 중 작은 쪽이 큰 쪽을 자식으로 삼는 `link` 연산 하나면 끝나기 때문에 insert와 merge가 `O(1)`이고, extractMin만 남은 자식들을 **Two-Pass**로 다시 이어 붙여 `O(log n)` 상각을 냅니다. Fibonacci Heap만큼 이론적으로 정교하진 않지만 구현이 훨씬 쉬우면서 실측 성능은 밀리지 않아 실무에서 즐겨 쓰입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 PairingHeap을 떠올리세요.

- 우선순위 큐 여러 개를 자주 **하나로 합쳐야** 한다(merge가 빈번하다)
- **삽입은 아주 잦고** 최솟값 추출은 상대적으로 드물다
- Fibonacci Heap을 쓰기엔 포인터 조작이 많아 구현 복잡도가 부담스럽다

naive 대안들과 비교하면 PairingHeap이 노리는 자리가 뚜렷이 보입니다.

```text
연산          정렬 배열    이진 힙       피보나치 힙        PairingHeap
insert        O(n)         O(log n)      O(1) 상각          O(1)
merge         O(n)         O(n)          O(1)                O(1)
extractMin    O(1)         O(log n)      O(log n) 상각       O(log n) 상각
구현 난이도    낮음          낮음          매우 높음            낮음
```

decreaseKey를 아주 많이 호출하는 그래프 알고리즘(프림·다익스트라의 이론적 최적 구현)이라면 피보나치 힙의 `O(1)` decreaseKey가 아쉽지만, 실제 상수 비용까지 고려하면 PairingHeap이 더 유리한 경우가 많습니다. 반대로 merge가 전혀 없고 삽입·추출만 반복한다면 굳이 포인터 트리를 쓸 필요 없이, 배열 기반이라 캐시 친화적인 이진 힙이 더 낫습니다 — "merge가 자주 나오는가"가 이진 힙과 PairingHeap을 가르는 기준선입니다.

### 문제 사례와 적용 예시

- **게임 서버 이벤트 큐 병합**: 몬스터 스폰, 아이템 드랍, 플레이어 액션처럼 이벤트 타입별로 따로 쌓이는 큐들을 시간 순으로 처리하려고 자주 하나로 합칩니다.
- **이산 사건 시뮬레이션(DES)의 이벤트 스케줄러**: 네트워크 시뮬레이터나 물류 시뮬레이터에서 서브 스케줄러들의 이벤트 큐를 병합하는 연산이 반복됩니다.
- **그래프 알고리즘의 우선순위 큐 구현체**: Prim·Dijkstra류 알고리즘에서 실무 라이브러리가 실제로 채택하는 힙 구현 중 하나입니다.
- **코딩 테스트 맥락**: "K개의 정렬된 스트림을 병합해서 최솟값 우선으로 꺼내라", "여러 워커 큐를 합쳐 처리하라"처럼 merge 자체가 비용 병목이 되는 문제에서 등장합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**

```ts
class PairingNode<T> {
  item: T;
  leftChild: PairingNode<T> | null = null;   // 첫 번째 자식
  nextSibling: PairingNode<T> | null = null; // 오른쪽 형제(부모의 자식 체인에서 다음 칸)

  constructor(item: T) {
    this.item = item;
  }
}

class PairingHeap<T> {
  private root: PairingNode<T> | null = null;
  private count = 0;
  private compare: (a: T, b: T) => number;
}
```

지켜야 할 불변식은 두 가지입니다.

1. **최소 힙 속성**: $\forall v \neq root:\ item(parent(v)) \le item(v)$
2. **루트가 전체 최솟값**: $item(root) = \min_{v \in H} item(v)$

자식은 배열이 아니라 형제 체인으로 표현됩니다 — 부모의 `leftChild`가 체인의 시작점입니다.

```text
                     부모
                      │ leftChild
                      ▼
                    child1 ── nextSibling ──▶ child2 ── nextSibling ──▶ child3 ──▶ null

     (가장 최근에 자식이 된 노드가 항상 맨 왼쪽 = leftChild 자리)
```

**액션(연산)** — 이 가이드가 정의하는 6종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(item)` | `link(root, 새 노드)`로 삽입 | $O(1)$ |
| `extractMin()` | root 반환 후 `twoPassMerge(root.leftChild)`로 교체 | $O(\log n)$ 상각 |
| `merge(other)` | `link(this.root, other.root)` | $O(1)$ |
| `peek()` | `root.item` 조회 | $O(1)$ |
| `size()` | 카운터 반환 | $O(1)$ |
| `isEmpty()` | `size() === 0` | $O(1)$ |

핵심 연산 두 개를 그림으로 자세히 볼게요.

**① link — "진 쪽이 이긴 쪽의 새 첫 자식이 된다".** 예시로 `link(3, 5)`를 실행합니다.

```text
Before: 독립된 두 싱글턴 트리
   3 (leftChild: ∅)        5 (leftChild: ∅)

compare(3, 5) ≤ 0 → 3이 승자, 5는 3의 자식이 된다

After:
   3
   └─ leftChild → 5 (nextSibling: ∅)
```

**② Two-Pass merge — "두 개씩 짝짓고(forward), 오른쪽부터 결합한다(backward)".** `insert(1), insert(8), insert(5), insert(3)`을 차례로 실행하면(각 삽입이 `link(root, 새 노드)`이므로 root는 계속 최솟값 1로 유지되고, 나중에 넣을수록 앞자리에 쌓입니다) root(1)의 자식 체인은 왼쪽부터 `[3, 5, 8]`이 됩니다. 이제 `extractMin()`을 호출한 직후를 봅니다.

```text
Before (root 1을 뗀 직후, root.leftChild 체인):
   3 ── nextSibling ──▶ 5 ── nextSibling ──▶ 8 ── nextSibling ──▶ null

Forward pass: 왼쪽부터 두 개씩 link
   link(3, 5) → compare(3,5) ≤ 0 → 3 승리, 5는 3의 자식
   짝지어진 결과: 3(leftChild: 5) , 나머지: [8]

Backward pass: 남은 것을 오른쪽부터(재귀가 되돌아오며) 결합
   link(3(leftChild:5), 8) → compare(3,8) ≤ 0 → 3 승리, 8이 3의 새 첫 자식(기존 5 앞에 붙는다)

After:
   3
   └─ leftChild → 8 ── nextSibling ──▶ 5 ── nextSibling ──▶ null
```

$m$번의 insert와 $k$번의 extractMin이 섞인 시퀀스 전체 비용은 $O((m+k)\log k)$입니다 — extractMin 1회당 상각 $O(\log k)$. 왜 하필 Two-Pass여야 이 상각이 나오는지는 바로 다음 절과 "아이디어를 코드로 옮기기"의 실측 비교에서 확인합니다.

### 왜 모순 없이 작동하는가

**link가 최소 힙 속성을 보존하는 이유(귀납)**: 삽입 직후의 싱글턴 노드는 자식이 없어 불변식을 자명하게 만족합니다(기저 사례). `link(a, b)`가 호출될 때 `a`, `b`는 각각 이미 최소 힙 속성을 만족하는 트리의 루트라고 가정합시다(귀납 가정). 비교에서 진 쪽(예: `b`)이 이긴 쪽(`a`)의 새 자식이 될 때 `item(a) ≤ item(b)`가 보장된 상태이므로 새로 생긴 부모-자식 관계도 곧바로 불변식을 만족합니다. 나머지 서브트리들의 내부 관계는 건드리지 않았으니 그대로 유지됩니다. `extractMin`의 `twoPassMerge`는 `link`만 반복 호출하므로 결과 트리 역시 귀납적으로 불변식을 만족하고, 남은 노드들 중 최솟값이 매 `link`에서 승자로 계속 끌어올려지므로 최종 루트는 전체 최솟값이 됩니다.

**여기서 헷갈리기 쉬운 포인트**는 naive 방식이든 Two-Pass든 "만들어지는 최종 루트 값" 자체는 항상 같다는 점입니다 — 아이디어를 코드로 옮기며 검증하겠지만, 자식 체인 `[6, 5, 4, 3, 2]`를 naive로 합치든 Two-Pass로 합치든 최종 루트는 똑같이 `2`입니다. 둘의 차이는 정답 여부가 아니라 결과 트리의 **깊이(모양)** 입니다. naive는 깊이 5의 사슬을 만들고 Two-Pass는 깊이 3의 균형 잡힌 트리를 만듭니다. 이 모양 차이가 이후 반복되는 extractMin들의 누적 비용을 가릅니다 — 사슬이 계속 만들어지면 후속 extractMin마다 다시 그 사슬 전체를 훑어야 해서, 내림차순으로 계속 삽입한 뒤 반복 추출하는 패턴에서는 총 비용이 $O(n^2)$까지 치솟을 수 있습니다.

두 번째로 헷갈리는 지점은 forward/backward 방향입니다. Forward는 왼쪽부터 "두 개씩" 짝짓고, Backward는 그 결과를 재귀 호출이 가장 안쪽(리스트 끝)까지 내려갔다가 되돌아오면서 "오른쪽부터" 결합합니다. 코드에서는 `twoPassMerge(rest)`가 완전히 끝난 뒤에야 바깥쪽 `link(paired, ...)`가 실행되므로, 실질적인 결합 순서는 오른쪽에서 왼쪽입니다. 잠깐, 확인 하나 해 볼까요? "forward pass만 하고 그 결과를 다시 naive처럼 왼쪽부터 합치면 어떻게 될까요?" — 짝의 개수가 절반(5개→3개)으로 줄긴 하지만, 그 3개를 naive로 또 이어 붙이면 3개짜리 사슬이 다시 생길 수 있어 근본 해결이 아닙니다. 재귀적으로 "오른쪽부터" 결합해야 매 층마다 절반씩 줄어드는 효과가 유지됩니다.

세 번째: `parent` 포인터입니다. 이 가이드가 정의한 6개 연산에는 decreaseKey가 없으므로 parent 포인터가 사실상 불필요합니다. 굳이 유지하려면 `link`·`twoPassMerge` 안에서 매번 갱신해야 하는데, 쓰지도 않을 필드를 갱신하면 코드만 늘어납니다.

엣지 케이스 점검:

```text
빈 힙 extractMin() / peek()            → undefined (root === null 분기)
원소 1개 힙 extractMin()                → 그 값 반환, twoPassMerge(null) = null → root = null
insert 중복 값(5, 5, 1)                 → size 정상 누적, extractMin 순서 1, 5, 5 (compare가 0이면 어느 쪽이 부모여도 무방)
merge(빈 힙)                            → link(root, null) = root 그대로, size 그대로
빈 힙.merge(비어있지 않은 힙)             → link(null, other.root) = other.root, size는 other 것
```

## 아이디어를 코드로 옮기기

가이드가 정의한 인터페이스(`PairingNode`/`PairingHeap`, `compare` 비교자)에 맞춰 원형 → 개선 → 최종 순서로 Two-Pass merge에 도달하는 과정을 코드로 밟아봅니다.

**원형(naive): 왼쪽부터 순서대로 이어 붙이기.**

```ts
function naiveMerge<T>(
  node: PairingNode<T> | null,
  link: (a: PairingNode<T> | null, b: PairingNode<T> | null) => PairingNode<T> | null,
): PairingNode<T> | null {
  if (node === null) return null;
  let result: PairingNode<T> | null = node;
  let cur = node.nextSibling;
  result.nextSibling = null;
  while (cur !== null) {
    const next = cur.nextSibling;
    cur.nextSibling = null;
    result = link(result, cur); // 왼쪽 결과에 계속 이어 붙인다
    cur = next;
  }
  return result;
}
```

`insert(1)`부터 `insert(6)`까지 오름차순으로 넣으면 root는 계속 `1`로 유지되고, 나중에 넣은 값일수록 앞자리(prepend)에 쌓여 root(1)의 자식 체인은 왼쪽부터 `[6, 5, 4, 3, 2]`가 됩니다. `extractMin()`으로 `1`을 떼어낸 뒤 이 5개짜리 체인에 `naiveMerge`를 실행하면 root는 `2`로 정확하지만(값은 맞습니다!), 깊이 5의 완전한 사슬(linked list 모양)이 만들어집니다 — 실측: naive 결과의 트리 깊이는 5. 이 사슬 모양이 문제입니다. 내림차순 삽입 뒤 반복 추출 같은 패턴에서는 매 extractMin마다 $O(n)$짜리 사슬을 다시 훑어야 해서, $n$번 반복하면 총 비용이 $O(n^2)$까지 치솟을 수 있습니다.

**개선: forward pass만 먼저 적용해 보기.** 사슬이 생기는 이유는 "이미 만든 결과에 하나씩 계속 이어 붙이기" 때문입니다. 그럼 처음부터 두 개씩 미리 짝지어 두면 어떨까요?

```ts
function forwardPass<T>(
  node: PairingNode<T> | null,
  link: (a: PairingNode<T> | null, b: PairingNode<T> | null) => PairingNode<T> | null,
): PairingNode<T>[] {
  const pairedRoots: PairingNode<T>[] = [];
  let cur = node;
  while (cur !== null) {
    const first = cur;
    const second: PairingNode<T> | null = cur.nextSibling;
    if (second === null) {
      first.nextSibling = null;
      pairedRoots.push(first);
      cur = null;
    } else {
      const rest = second.nextSibling;
      first.nextSibling = null;
      second.nextSibling = null;
      pairedRoots.push(link(first, second)!);
      cur = rest;
    }
  }
  return pairedRoots;
}
```

같은 5개짜리 체인 `[6, 5, 4, 3, 2]`에 `forwardPass`만 실행하면 짝 `(6,5)→5`, 짝 `(4,3)→3`, 그리고 홀로 남은 `2`, 이렇게 3개의 서브트리로 줄어듭니다 — 실측: 결과 루트 값은 `[5, 3, 2]`, 개수는 5개에서 3개로 줄었습니다. 개수는 절반 가까이 줄었지만, 이 3개를 다시 naive처럼 왼쪽부터 이어 붙이면 3개짜리 사슬이 또 생겨요. 절반씩 줄어드는 효과가 재귀적으로 이어지지 않으면 결국 다시 $O(n)$ 깊이로 돌아갑니다. 필요한 마지막 조각은 "이 축소된 목록도 같은 전략으로, 그것도 오른쪽부터 재귀적으로 결합"하는 것입니다.

**최종: Two-Pass merge(forward + backward 재귀)와 전체 구현.**

```ts
class PairingNode<T> {
  item: T;
  leftChild: PairingNode<T> | null = null;
  nextSibling: PairingNode<T> | null = null;

  constructor(item: T) {
    this.item = item;
  }
}

class PairingHeap<T> {
  private root: PairingNode<T> | null = null;
  private count = 0;
  private compare: (a: T, b: T) => number;

  constructor(compare: (a: T, b: T) => number) {
    this.compare = compare;
  }

  private link(a: PairingNode<T> | null, b: PairingNode<T> | null): PairingNode<T> | null {
    if (a === null) return b;
    if (b === null) return a;
    if (this.compare(a.item, b.item) <= 0) {
      b.nextSibling = a.leftChild;
      a.leftChild = b;
      return a;
    } else {
      a.nextSibling = b.leftChild;
      b.leftChild = a;
      return b;
    }
  }

  private twoPassMerge(node: PairingNode<T> | null): PairingNode<T> | null {
    if (node === null || node.nextSibling === null) return node;
    const first = node;
    const second = node.nextSibling;
    const rest = second.nextSibling;
    first.nextSibling = null;
    second.nextSibling = null;
    const paired = this.link(first, second);
    return this.link(paired, this.twoPassMerge(rest));
  }

  insert(item: T): void {
    const node = new PairingNode(item);
    this.root = this.link(this.root, node);
    this.count++;
  }

  extractMin(): T | undefined {
    if (this.root === null) return undefined;
    const item = this.root.item;
    this.root = this.twoPassMerge(this.root.leftChild);
    this.count--;
    return item;
  }

  merge(other: PairingHeap<T>): PairingHeap<T> {
    const result = new PairingHeap<T>(this.compare);
    result.root = this.link(this.root, other.root);
    result.count = this.count + other.count;
    return result;
  }

  peek(): T | undefined {
    return this.root?.item;
  }

  size(): number {
    return this.count;
  }

  isEmpty(): boolean {
    return this.count === 0;
  }
}
```

`twoPassMerge`가 개선 단계의 `forwardPass`와 다른 점은, 첫 두 개만 즉시 짝짓고 나머지 전체는 재귀 호출 `twoPassMerge(rest)`에 통째로 맡긴다는 것입니다. 재귀가 리스트 끝까지 내려갔다가 되돌아오면서 결합되므로 실질적인 결합은 오른쪽에서 왼쪽으로 진행됩니다. 같은 `[6, 5, 4, 3, 2]`에 `twoPassMerge`를 실행하면 root는 여전히 `2`로 같지만 깊이는 3으로 줄어듭니다 — 실측: naive 깊이 5 → Two-Pass 깊이 3.

가장 중요한 부분은 `link`의 이 두 줄입니다.

```ts
b.nextSibling = a.leftChild;
a.leftChild = b;
```

진 쪽(`b`)이 이긴 쪽(`a`)의 **새 첫 자식**이 되는 전부가 이 두 줄에 있습니다. 순서를 바꿔 `a.leftChild = b`를 먼저 쓰면, `b.nextSibling`에 대입할 때 이미 덮어써진 `a.leftChild`(= `b` 자신)를 읽게 되어 `b.nextSibling = b`라는 자기 참조가 생기고, `a`의 기존 자식들은 통째로 유실됩니다.

놓치기 쉬운 지점을 몇 가지 더 짚습니다.

- `twoPassMerge`에서 `first.nextSibling = null; second.nextSibling = null;`을 재귀 호출 전에 반드시 끊어야 합니다. 안 끊으면 `link` 내부에서 `nextSibling`을 새로 쓸 때 원래 형제 체인 참조가 남아 있어 예상과 다른 노드가 딸려 옵니다.
- `extractMin`은 `root` 자체가 아니라 `root.leftChild`(자식 체인)를 `twoPassMerge`에 넘깁니다. `root` 자신은 이미 값을 꺼내 반환하고 버려지는 노드이기 때문입니다.
- `merge`는 `this.root`와 `other.root`를 직접 `link`할 뿐 두 힙의 `compare`가 같은 규칙이라고 가정합니다. 서로 다른 비교자를 쓰는 힙끼리 합치면 불변식이 깨질 수 있어요.

> 기억법: 진 사람이 이긴 사람의 맨 앞자리 자식이 된다 — link는 늘 앞에 꽂는다.
