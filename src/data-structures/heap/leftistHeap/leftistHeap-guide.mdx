# LeftistHeap — 오른쪽 경로만 짧게 유지해서 병합을 로그 시간에 끝내기

## 한눈에 보는 컨셉

좌향 힙(Leftist Heap)은 두 힙을 합치는 병합(merge) 연산을 $O(\log n)$에 끝내려고 설계된 이진 트리 힙이에요. 비결은 모든 노드에서 "왼쪽 서브트리의 rank가 오른쪽 이상"이라는 좌향 속성을 강제해, 오른쪽 경로(rightmost path) 길이를 항상 $O(\log n)$으로 눌러두는 것입니다. 그러면 삽입·삭제·병합을 전부 "오른쪽 경로만 타고 내려가며 병합한다"는 단 하나의 연산으로 통일할 수 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 좌향 힙을 떠올리세요.

- 서로 다른 두 우선순위 큐(작업 큐, 이벤트 큐 등)를 자주 하나로 합쳐야 한다
- 삽입·삭제뿐 아니라 **병합(merge) 자체가 빈번한 연산**으로 등장한다
- 병합한 뒤에도 여전히 최솟값 우선 처리가 필요하다(단순히 두 리스트를 이어붙이는 게 아니다)

정렬 배열이나 이진 힙으로 같은 일을 하면 병합 비용이 원소 수에 비례해 커집니다.

```text
merge(두 힙, 총 n개 원소)를 만드는 세 가지 방법
정렬 배열 재구성(합친 뒤 정렬)     O(n log n)
이진 힙(한쪽 원소를 전부 재삽입)   O(n)
좌향 힙(오른쪽 경로만 훑는다)      O(log n)   ← 병합에서만 나오는 이점
```

병합이 거의 없다면 굳이 좌향 힙을 쓸 필요가 없습니다 — 이진 힙이 구현도 간단하고 배열 기반이라 캐시 효율도 더 좋아요. 병합이 잦고 코드 단순성이 중요하면 좌향 힙이 첫 번째 선택이고, 병합도 잦은데 decrease-key 연산까지 많다면(다익스트라의 우선순위 큐 등) 이항 힙·피보나치 힙 쪽이 이론적으로 더 유리합니다.

### 문제 사례와 적용 예시

- **온라인 저지(Online Judge) 채점 큐 병합**: 언어별·문제별로 독립된 채점 큐가 있다가, 트래픽이 몰리면 여러 큐를 즉시 하나로 합쳐야 합니다. 큐가 수만 건이면 이진 힙의 $O(n)$ 병합이 병목이 되지만 좌향 힙은 $O(\log n)$에 끝납니다.
- **이산 사건 시뮬레이션**: 여러 프로세스가 각자의 이벤트 큐(다음 실행 시각 기준 최소 힙)를 들고 있다가, 프로세스가 합쳐질 때 이벤트 큐도 함께 병합해야 하는 경우.
- **분산 작업 스케줄러**: 노드 여러 대의 작업 큐를 통합해 하나의 글로벌 큐로 재배치할 때, 각 노드 큐를 좌향 힙으로 유지하면 병합 비용이 노드 수가 아니라 트리 높이에만 비례합니다.
- **코딩 테스트 맥락**: "두 개의 힙(또는 우선순위 큐)을 합쳐서 반환하라"처럼 병합 자체가 채점 포인트인 문제. Union-Find가 집합 병합을 담당하듯, 좌향 힙은 "우선순위가 있는 집합"의 병합을 담당합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드와 힙 두 클래스로 구성됩니다.

```ts
class LeftistNode<T> {
  item: T;
  rank: number;                    // 오른쪽으로 null까지 가는 최단 경로 길이
  left: LeftistNode<T> | null;
  right: LeftistNode<T> | null;
}

class LeftistHeap<T> {
  root: LeftistNode<T> | null;
  _size: number;
  compare: (a: T, b: T) => number; // a<b면 음수, a===b면 0, a>b면 양수
}
```

지켜야 할 불변식은 세 가지입니다.

1. **최소 힙 속성**: 모든 노드에서 $u.\text{item} \le v.\text{item}$ ($v$는 $u$의 자식).
2. **좌향(leftist) 속성**: 모든 노드에서 $\text{rank}(u.\text{left}) \ge \text{rank}(u.\text{right})$. null의 rank는 $0$으로 정의합니다.
3. **rank 재귀식**: $\text{rank}(u) = \text{rank}(u.\text{right}) + 1$ (좌향 속성 때문에 오른쪽이 항상 더 짧은 쪽입니다).

4개 원소(1, 3, 5, 7)를 넣은 뒤의 좌향 힙은 이런 모양이 됩니다.

```text
              1  (rank=1)
             /
        3   (rank=2)
       /   \
      5     7
   (rank=1)(rank=1)

확인: rank(1.left=3)=2 ≥ rank(1.right=null)=0  → 좌향 속성 만족
      rank(3.left=5)=1 ≥ rank(3.right=7)=1     → 좌향 속성 만족 (같아도 OK)
      rank(1) = rank(1.right=null) + 1 = 0 + 1 = 1
```

**액션(연산)** — 이 가이드가 정의하는 인터페이스는 다음과 같습니다.

| 연산 | 하는 일 | 비용 |
|------|---------|------|
| `insert(item)` | 크기 1짜리 힙을 만들어 `merge`로 흡수 | $O(\log n)$ |
| `extractMin()` | 루트를 꺼내고 좌우 서브트리를 `merge`. 빈 힙 → `undefined` | $O(\log n)$ |
| `merge(other)` | 두 힙을 합친 새 힙을 반환(내부 노드는 공유, 파괴적) | $O(\log n)$ |
| `peek()` | 루트 값만 확인. 빈 힙 → `undefined` | $O(1)$ |
| `size()` | 원소 개수 | $O(1)$ |
| `isEmpty()` | `size() === 0`과 동치 | $O(1)$ |

핵심 연산은 `merge` 하나뿐입니다 — `insert`와 `extractMin`도 결국 `merge`를 한 번 호출하는 것으로 끝나니까요. `merge`를 자세히 봅시다.

**merge의 재귀 규칙**: 두 힙 $A$(루트 3), $B$(원소 1짜리 싱글턴)를 합친다고 해 봅시다.

```text
Before                              After merge(A, B)
Heap A (root=3)   Heap B (root=1)         1  ← 더 작은 쪽(1)이 새 루트
        3               1                /
       / \                          3    ← 1.right = merge(null, 3) = 3
      5   7                        / \      그런데 rank(1.left=null)=0 < rank(1.right=3)=2
                                  5   7      이므로 좌우를 swap → 1.left=3, 1.right=null
```

두 루트 중 더 작은 쪽(여기서는 1)이 이깁니다. 이긴 노드의 **오른쪽 자식**과 진 쪽(여기서는 3짜리 서브트리 전체)을 재귀적으로 병합하고, 그 결과를 오른쪽 자식 자리에 겁니다. 마지막으로 좌향 속성이 깨졌으면(왼쪽 rank < 오른쪽 rank) 좌우를 바꿔서 복원합니다.

$$
\text{rank}(u) \le \lfloor \log_2(n+1) \rfloor \quad (n = u\text{를 루트로 하는 서브트리의 노드 수})
$$

이 상한 덕분에 재귀가 오른쪽 경로만 타고 내려가도 깊이가 $O(\log n)$에서 멈춥니다 — 왜 이 상한이 성립하는지는 다음 절에서 증명합니다.

### 왜 모순 없이 작동하는가

**최소 힙 속성이 보존되는 이유**: `mergeNodes(a, b)`가 항상 두 루트 중 더 작은 쪽을 새 루트로 고른다고 해 봅시다. 이긴 노드 `a`의 아이템은 정의상 `b`의 아이템보다 작거나 같고, 원래 `a`의 서브트리에 있던 모든 값보다도 작거나 같습니다(가정: 병합 전 두 힙 모두 최소 힙 속성을 만족). 재귀 호출 `mergeNodes(a.right, b)`가 만드는 새 오른쪽 서브트리는 `a.right`의 원소와 `b`의 원소로만 이루어지는데, 둘 다 `a.item`보다 크거나 같으므로, `a`를 루트로 하는 결과도 여전히 최소 힙 속성을 만족합니다. 왼쪽 자식은 손대지 않았으니 그대로 성립하고요. 재귀의 바닥(둘 중 하나가 `null`)에서는 나머지 하나를 그대로 반환하니 자명하게 성립합니다. 따라서 귀납적으로 모든 깊이에서 성립합니다.

**좌향 속성이 보존되는 이유**: 재귀 호출 직후 `a.right`가 바뀌었으니 `rank(a.left) ≥ rank(a.right)`가 깨졌을 수 있습니다. 그래서 매 호출마다 `if (rank(a.left) < rank(a.right)) swap(a.left, a.right)`를 실행해 **그 자리에서 즉시 복원**합니다. 복원 후에는 정의상 `rank(a.left) ≥ rank(a.right)`이니 위반될 수가 없어요.

여기서 헷갈리기 쉬운 포인트 두 가지를 짚고 갈게요.

- **복원 스왑은 재귀의 "매 층"에서 해야 합니다.** 최상위 호출에서만 스왑하고 재귀 내부에서 생략하면 무슨 일이 생길까요? 오름차순으로 1부터 8까지 삽입했을 때, 정상 구현은 오른쪽 경로 길이가 3(=⌊log₂9⌋)에서 멈추지만, 재귀 내부 스왑을 생략한 버전은 오른쪽 경로 길이가 **8**까지, 즉 노드 수만큼 그대로 늘어납니다(실측 확인: 아래 "아이디어를 코드로 옮기기"의 함정 절 참고). 오른쪽 경로가 곧 병합의 재귀 깊이이므로, 이 버그는 $O(\log n)$ 이점을 통째로 날려버립니다.
- **rank는 서브트리 크기도, 트리 높이도 아닙니다.** 앞서 그린 4-노드 트리를 다시 보세요 — 노드가 4개나 있는데도 루트 `1`의 rank는 **1**입니다. `1.right`가 `null`이라 `rank(1) = rank(null) + 1 = 1`이 되기 때문이에요. rank는 오로지 "오른쪽으로만 내려가서 null을 만나기까지의 최단 거리"입니다. 왼쪽에 아무리 큰 서브트리가 매달려 있어도 rank는 작을 수 있습니다.

확인 질문 하나: 어떤 노드의 `rank(left) = 1`, `rank(right) = 2`라면 이 노드는 좌향 속성을 만족할까요? — 아니요. $1 < 2$라서 위반이고, 좌우를 swap해야 `rank(left)=2 ≥ rank(right)=1`로 복원됩니다.

엣지 케이스를 점검해 봅시다.

```text
빈 힙에서 peek() / extractMin()   → undefined (root가 null)
크기 1 힙에서 extractMin()        → 그 원소 반환, mergeNodes(null, null) = null → 다시 빈 힙
빈 힙끼리 merge()                 → 빈 힙(root=null, size=0)
비어있지 않은 힙과 빈 힙의 merge() → 비어있지 않은 쪽 구조가 그대로 이식됨
중복 값 삽입                      → compare()가 0을 반환하는 경우도 정상 처리, 상대적 순서는 보장 안 함
merge에 쓰인 원본 힙을 계속 사용   → 파괴적 구현이라 노드가 공유됨 — 원본 heapA/heapB를 병합 후 다시 쓰면 예상 밖의 변경이 전파될 수 있음(주의)
```

## 아이디어를 코드로 옮기기

앞서 정의한 인터페이스대로 구현합니다. `mergeNodes`가 재귀적으로 오른쪽 경로만 훑고, `insert`·`extractMin`은 이 함수를 한 번씩 호출하는 얇은 래퍼입니다.

```ts
class LeftistNode<T> {
  item: T;
  rank: number;
  left: LeftistNode<T> | null;
  right: LeftistNode<T> | null;

  constructor(item: T) {
    this.item = item;
    this.rank = 1;
    this.left = null;
    this.right = null;
  }
}

function rank<T>(node: LeftistNode<T> | null): number {
  return node === null ? 0 : node.rank;
}

function mergeNodes<T>(
  a: LeftistNode<T> | null,
  b: LeftistNode<T> | null,
  compare: (a: T, b: T) => number,
): LeftistNode<T> | null {
  if (a === null) return b;
  if (b === null) return a;
  if (compare(a.item, b.item) > 0) {
    [a, b] = [b, a]; // a가 항상 더 작은(또는 같은) 루트가 되도록
  }
  a.right = mergeNodes(a.right, b, compare); // 오른쪽 경로만 재귀적으로 병합

  const leftRank = rank(a.left);
  const rightRank = rank(a.right);
  if (leftRank < rightRank) {
    [a.left, a.right] = [a.right, a.left]; // 좌향 속성 즉시 복원
  }
  a.rank = Math.min(leftRank, rightRank) + 1;
  return a;
}

class LeftistHeap<T> {
  private root: LeftistNode<T> | null = null;
  private _size = 0;
  private compare: (a: T, b: T) => number;

  constructor(compare: (a: T, b: T) => number) {
    this.compare = compare;
  }

  insert(item: T): void {
    const node = new LeftistNode(item);
    this.root = mergeNodes(this.root, node, this.compare);
    this._size++;
  }

  extractMin(): T | undefined {
    if (this.root === null) return undefined;
    const item = this.root.item;
    this.root = mergeNodes(this.root.left, this.root.right, this.compare);
    this._size--;
    return item;
  }

  merge(other: LeftistHeap<T>): LeftistHeap<T> {
    const result = new LeftistHeap<T>(this.compare);
    result.root = mergeNodes(this.root, other.root, this.compare);
    result._size = this._size + other._size;
    return result;
  }

  peek(): T | undefined {
    return this.root === null ? undefined : this.root.item;
  }

  size(): number {
    return this._size;
  }

  isEmpty(): boolean {
    return this._size === 0;
  }
}
```

가장 중요한 부분은 `mergeNodes` 안의 이 두 줄입니다.

```ts
a.right = mergeNodes(a.right, b, compare);
if (leftRank < rightRank) [a.left, a.right] = [a.right, a.left];
```

첫 줄이 "오른쪽 경로만 병합"이라는 핵심 아이디어 그 자체이고, 둘째 줄이 그 결과로 깨질 수 있는 좌향 속성을 매 호출마다 즉시 복원합니다. 이 둘째 줄을 재귀 내부에서 빼먹으면 어떻게 되는지 실측으로 보여드릴게요.

**함정: 복원 스왑을 재귀 내부에서 생략한 버전**

```ts
// 버그 버전 — 좌향 속성 복원을 빼먹었다
function buggyMerge<T>(a, b, compare) {
  if (a === null) return b;
  if (b === null) return a;
  if (compare(a.item, b.item) > 0) [a, b] = [b, a];
  a.right = buggyMerge(a.right, b, compare);
  // (복원 스왑 없음 — 이게 함정)
  a.rank = rank(a.right) + 1;
  return a;
}
```

이 버전으로 `1, 2, 3, ..., 8`을 오름차순으로 삽입하면, 매번 새 원소가 항상 더 크므로 `a`는 계속 기존 루트가 되고 `a.right`에만 노드가 쌓입니다. 실제로 실행해 보면 오른쪽 경로 길이가 **8** — 즉 전체 노드 수와 같아집니다. 정상 구현(복원 스왑 포함)으로 같은 입력을 넣으면 오른쪽 경로 길이는 **3**(= $\lfloor \log_2 9 \rfloor$)에서 멈춥니다. 오른쪽 경로 길이가 곧 `extractMin`의 재귀 깊이이므로, 이 버그는 $O(\log n)$을 $O(n)$으로 되돌려 놓는 셈입니다.

> 기억법: "이긴 쪽은 왼쪽을 지키고, 방금 합친 결과만 오른쪽에 잠깐 걸쳤다가, 무거운 쪽(rank 큰 쪽)을 왼쪽으로 되돌린다."

## 실행 시각화

`insert(5)` → `insert(3)` → `insert(7)` → `insert(1)` → `extractMin()` 순서로 실행합니다. 고정 입력이고, 실제 반환값은 `extractMin() === 1`이며 그 뒤 남은 힙에서 정렬 순서로 꺼내면 `[3, 5, 7]`입니다(위 "전체 스펙" ascii 그림의 4-노드 힙에서 루트만 뽑아낸 상태와 같습니다). array 패널은 각 단계 직후 힙에 들어있는 원소를 **정렬된 순서로** 나열한 스냅샷이고(트리의 좌우 배치 자체를 그대로 옮긴 그림은 아닙니다), highlight는 그 연산 직후의 새 루트(최솟값) 위치를 가리킵니다.

> 대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.
