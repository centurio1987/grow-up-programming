# Fibonacci Heap — 지금 정리하지 않고, extractMin 한 번에 몰아서 정리하기

## 한눈에 보는 컨셉

여러 개의 트리를 느슨하게 묶어 둔 병합 가능한 힙이에요. 삽입·병합·decrease-key는 트리를 당장 정리하지 않고 루트 리스트에 슬쩍 끼워 넣기만 하며(지연 전략), 실제 정리는 `extractMin`이 호출될 때 한 번에 몰아서 처리합니다. 이 덕분에 삽입·병합·decrease-key는 $O(1)$ 상각, `extractMin`만 $O(\log n)$ 상각이 되어 — decrease-key가 폭주하는 다익스트라 알고리즘의 복잡도를 $O((V+E) \log V)$에서 $O(E + V \log V)$로 낮춰줍니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 Fibonacci heap을 떠올리세요.

- 우선순위 큐에서 **decrease-key가 반복적으로**(다익스트라라면 최대 $O(E)$번) 호출된다
- 여러 힙을 자주 **병합(merge)**해야 한다
- 삽입은 아주 잦은데 **최솟값 추출은 상대적으로 드물다** — 정리 비용을 추출 시점에 몰아도 손해가 아니다

이진 힙은 decrease-key 한 번에 트리 높이만큼(=$O(\log n)$) 비교·스왑을 합니다. 힙에 원소가 많고 decrease-key가 자주 불리면 이 비용이 누적됩니다.

```text
연산            Binary Heap      Fibonacci Heap
insert          O(log n)         O(1) 상각        ← 즉시 정렬 안 함
decreaseKey     O(log n)         O(1) 상각        ← FH 최강점, 지연 처리
merge           O(n)             O(1)             ← 리스트만 이어붙임
extractMin      O(log n)         O(log n) 상각    ← 비용이 여기로 몰린다
```

다익스트라 알고리즘 전체 복잡도: Binary Heap → $O((V+E)\log V)$, Fibonacci Heap → $O(E + V\log V)$.

**선택 기준**: 삽입·추출만 반복되고 decrease-key가 없다면 binary heap으로 충분합니다. 삽입·병합은 잦은데 decrease-key가 없다면 binomial heap이 더 단순하고 상수도 작습니다. decrease-key가 반복적으로 필요할 때만 Fibonacci heap의 지연 전략이 진가를 발휘합니다 — 구현이 훨씬 복잡한 대가로 얻는 이점이니, decrease-key가 드문 문제에까지 쓸 필요는 없어요.

### 문제 사례와 적용 예시

- **다익스트라 최단 경로**: 지도 서비스에서 수백만 정점의 최단 경로를 계산할 때, 더 짧은 경로를 발견할 때마다 decrease-key가 발생합니다. 이 호출이 총 $O(E)$번이라 Fibonacci heap의 이점이 그대로 복잡도에 반영됩니다.
- **Prim의 최소 신장 트리(MST)**: 다익스트라와 구조가 같습니다 — 간선을 볼 때마다 후보 정점의 키를 낮추는 패턴이라 동일한 이점을 얻습니다.
- **네트워크 라우팅 실무**: OSPF 같은 링크-상태 라우팅 프로토콜은 내부적으로 다익스트라를 돌립니다. 노드 수가 많은 백본 네트워크일수록 decrease-key 비용 절감이 체감됩니다.
- **코딩 테스트 맥락**: "정점이 매우 많고 decrease-key가 반복되는 최단경로 문제" 또는 "여러 우선순위 큐를 계속 병합해야 하는 작업 스케줄링 문제"에서 직접 구현 대상이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드와 힙 두 클래스로 구성됩니다.

```ts
class FibNode<T> {
  item: T;
  degree: number;             // 자식 수
  marked: boolean;            // 자식을 잃은 적이 있는가
  parent: FibNode<T> | null;
  child: FibNode<T> | null;   // 자식 리스트 중 하나 (원형 이중 연결)
  left: FibNode<T>;           // 같은 리스트(루트 또는 형제)에서 좌측
  right: FibNode<T>;          // 같은 리스트(루트 또는 형제)에서 우측
}

class FibonacciHeap<T> {
  min: FibNode<T> | null;     // 루트 리스트 중 최솟값 노드
  size: number;
  compare: (a: T, b: T) => number;
}
```

지켜야 할 불변식은 네 가지예요.

1. **힙-순서**: 모든 노드 $x$와 그 부모 $p$에 대해 $\mathrm{key}(p) \le \mathrm{key}(x)$.
2. **min 포인터**: `min`은 루트 리스트에서 키가 가장 작은 노드를 가리킨다.
3. **차수 하한**: 차수 $k$인 노드의 서브트리 크기 $S_k$는 $S_k \ge F_{k+2}$를 만족한다 (단 $F_0=0,\ F_1=1$인 피보나치 수).
4. **마크**: $\mathrm{mark}(x)=\mathrm{true}$는 $x$가 루트가 아니면서, 현재 부모의 자식이 된 이후 자식을 정확히 한 번 잃었다는 뜻이다.

불변식 3 덕분에 최대 차수 $D(n)$은 $O(\log_\phi n)$으로 묶입니다 ($\phi = \frac{1+\sqrt5}{2} \approx 1.618$). 이게 왜 중요한지는 다음 절에서 실제 트리로 확인할게요.

`insert(1..16)`을 한 뒤 `extractMin()`을 한 번 호출하면(=1을 제거) 실제로 이런 구조가 만들어집니다.

```text
루트 리스트(원형): 2 ⇄ 9 ⇄ 5 ⇄ 3 ⇄ (다시 2로)      min → 2

  2(d0)     9(d3)              5(d2)      3(d1)
           / | \               /  \         |
         10 13  11            6    7        4
            /\    \                |
          14  15   12              8
                \
                16
```

9의 서브트리는 `9,10,13,14,15,16,11,12` 8개 노드입니다. 불변식 3의 하한 $F_{3+2}=F_5=5$보다 크니 여유 있게 성립하죠. 3의 서브트리는 `3,4` 2개로, 하한 $F_3=2$와 **정확히 일치**합니다 — 갓 두 개의 차수 0 트리가 링크된 직후라 하한이 가장 빡빡한 경우예요.

**액션(연산)** — 이 힙이 제공하는 전체 연산입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(item)` | 새 노드를 루트 리스트에 즉시 추가, 필요하면 min 갱신 | $O(1)$ |
| `extractMin()` | min 제거 → 자식을 루트로 승격 → consolidate | $O(\log n)$ 상각 |
| `decreaseKey(node, newItem)` | 힙-순서 위반 시 cut + cascadingCut | $O(1)$ 상각 |
| `merge(other)` | 두 루트 리스트를 이어붙인 새 힙 반환 | $O(1)$ |
| `peek()` | `min.item` 반환 | $O(1)$ |
| `size()` | 원소 수 | $O(1)$ |
| `isEmpty()` | `size === 0`과 동치 | $O(1)$ |

핵심 연산 두 개를 실제 값으로 자세히 볼게요.

**① consolidate — 같은 차수 트리를 짝지어 합친다.** `insert(10)`, `insert(5)`, `insert(15)` 후 `extractMin()`을 호출하면(5가 제거됩니다) 남는 두 루트 10, 15는 둘 다 차수 0이라 즉시 링크됩니다.

```text
Before (5 제거 직후, consolidate 시작 전):
  루트 리스트: 10(d0) ⇄ 15(d0)

link(10, 15): 10 < 15이므로 10이 부모, 15가 자식.

After:
  루트 리스트: 10(d1)
                 │
                15(d0)

min = 10
```

**② cut + cascadingCut — 힙-순서 위반을 잘라내고, 두 번째 손실부터 위로 전파한다.** 위 16개 노드 예시(9의 서브트리)로 봅니다. `decreaseKey(14, 0)`을 호출하면:

```text
Before:                       After decreaseKey(14, 0):
    9(d3)                         0(신규 루트, d0)     9(d3, 그대로!)
   / | \                                              / | \
 10 13  11                                          10  13  11
    /\    \                                              \    \
  14  15  12                                             15   12
        \                                                  \
        16                                                 16

13.marked: false → true   (자식 14를 "처음" 잃었으므로 자르지 않고 표시만)
9.degree는 그대로 3 — 14는 9의 손자였지, 자식이 아니었으니까요.
```

이어서 `decreaseKey(15, 0.5)`를 호출하면 13은 **두 번째로** 자식을 잃습니다. 이때 cascadingCut이 실제로 전파됩니다.

```text
Before:                              After decreaseKey(15, 0.5):
    9(d3)                              13(신규 루트, d0)   0.5(신규 루트, d1)   9(d2 ← 3에서 감소!)
   / | \                                                     │                / \
 10 13  11                                                  16              10   11
      \    \                                                                       \
      15   12                                                                      12
        \
        16

13.marked=true였는데 또 자식(15)을 잃음 → cut(13, 9) 실행 → cascadingCut(9) 호출
9는 루트(parent=null)라 여기서 전파가 멈춘다. 13은 잘려 나가며 marked가 다시 false로 초기화된다.
```

### 왜 모순 없이 작동하는가

**힙-순서가 항상 유지되는 이유**: `insert`는 크기 1짜리 트리를 만드니 자명하게 성립합니다. `link(a, b)`는 항상 **더 작은 쪽을 부모로** 선택하므로 새로 생기는 부모-자식 간선은 그 자체로 힙-순서를 만족합니다. `consolidate`는 오직 `link`만 반복하니 위반이 생길 여지가 없어요. `decreaseKey`는 값을 낮췄을 때 부모보다 작아지면 그 간선을 아예 **잘라내** 버립니다 — 위반된 간선이 존재하지 않게 되는 것이지, 위반을 방치하는 게 아니에요. 잘려 나온 노드는 루트가 되어 "부모가 없으니 위반도 없는" 상태가 됩니다. 즉 빈 힙에서 시작해 어떤 연산을 거쳐도 매 순간 힙-순서를 만족하는 간선만 존재합니다.

**차수 상한이 유지되는 이유(납득 수준)**: 어떤 노드 $x$가 차수 $k$를 갖게 됐다고 합시다. $x$의 $i$번째 자식은 "$x$에 링크되던 순간" $x$와 같은 차수(즉 $i-1$)를 갖고 있었습니다(같은 차수끼리만 링크하니까요). 그 이후 이 자식은 cascading cut 규칙 때문에 자식을 **많아야 한 번**까지만 잃고도 살아남을 수 있습니다(두 번째로 잃으면 곧바로 잘려 나가 $x$의 자식 목록에서 사라지므로). 그래서 $i$번째 자식의 현재 차수는 최소 $i-2$입니다. 이 재귀를 풀면 차수 $k$ 트리의 최소 크기 $S_k$가 피보나치 점화식 $S_k \ge S_{k-2} + S_{k-1}$을 만족하게 되고, 결국 $S_k \ge F_{k+2}$입니다. $F_{k+2} \approx \phi^k/\sqrt5$이므로 $n$개 노드가 있으면 $k = O(\log_\phi n) = O(\log n)$이 상한입니다. cascading cut이 "두 번째 손실부터" 자른다는 조건이 바로 이 하한을 지키는 장치예요.

**상각 비용이 실제로 $O(1)$·$O(\log n)$이 되는 이유**: 포텐셜 함수 $\Phi(H) = t(H) + 2m(H)$를 씁니다($t(H)$ = 루트 리스트의 트리 개수, $m(H)$ = mark=true인 노드 수).

- `insert`: 실제 비용 $O(1)$, $\Delta\Phi = +1$(루트 하나 증가) → 상각 $O(1)$.
- `extractMin`: 실제 비용은 자식 승격 $O(D(n))$ + consolidate 스캔 $O(D(n)+t(H))$. consolidate 후에는 차수가 모두 달라야 하므로 남는 트리 수 $t(H') \le D(n)+1$, 즉 $\Delta\Phi \le (D(n)+1) - t(H)$. 실제 비용과 더하면 상쇄되어 상각 $O(D(n)) = O(\log n)$.
- `decreaseKey`: cascading cut이 $c$번 일어났다면 실제 비용은 $O(c)$. 잘려 나간 $c$개의 노드가 새 루트가 되니 $t(H)$는 $c$ 증가하고, 그중 $c-1$개는 mark가 `true`→`false`로 초기화되니 $m(H)$는 최소 $c-1$ 감소합니다. $\Delta\Phi \le c - 2(c-1) = -c+2$. 실제 비용과 더하면 상수로 수렴 → 상각 $O(1)$.

**여기서 헷갈리기 쉬운 포인트는 세 가지입니다.**

- **cascading cut이 "자식을 잃을 때마다" 일어난다고 착각하기 쉽습니다.** 실제로는 **처음** 잃으면 mark만 세팅하고 멈춥니다. 위 예시에서 `decreaseKey(14, 0)` 이후에도 9의 degree는 여전히 3이었죠 — 13이 자식 하나(14)를 잃었을 뿐 9는 전혀 영향받지 않았습니다. 자식을 **두 번째**로 잃을 때(=13이 이미 marked인 상태에서 15까지 잃을 때)만 13 자신이 잘려 나가며 9의 degree가 3→2로 줄어듭니다.
- **`merge`는 새 힙 객체를 반환하지만, 내부적으로는 두 원본 힙의 루트 리스트 자체를 이어붙입니다.** 즉 원본 두 힙은 병합 이후 독립적으로 쓰면 안 됩니다. 실제로 `h1.insert(1)`, `h2.insert(3)`, `h2.insert(7)`, `h1.insert(5)`, `h1.insert(9)`로 만든 두 힙을 `merged = h1.merge(h2)`한 뒤 원본 `h1`에 `h1.insert(1)`을 추가로 호출하면, `1`은 같은 원형 리스트를 공유하는 `merged`에도 구조적으로 딸려 들어갑니다. 하지만 `merged.min`은 갱신되지 않아 `merged.peek()`은 여전히 `3`을 반환하고(`1`이 더 작은데도), `merged.size()`도 그대로 `4`로 남습니다. 실제로 `merged.extractMin()`을 연달아 호출하면 `3 → 1 → 5` 순서로 나옵니다 — `peek()`이 거짓말을 했던 셈이죠. 병합 후에는 원본 힙 변수를 더 쓰지 않는 것이 안전합니다.
- **`decreaseKey`는 값을 늘리는 방향으로 호출하면 안 됩니다.** `compare(newItem, node.item) > 0`이면 계약 위반이므로 구현은 반드시 이 경우를 예외로 막아야 합니다. 이 가드를 빼먹으면 힙-순서가 조용히 깨집니다.

잠깐 확인 하나만 해볼까요? 위 9번 노드 서브트리처럼 차수 3인 트리는 최소 몇 개의 노드를 가져야 할까요? — 정답은 $F_{3+2}=F_5=5$개 이상입니다. 실제 예시에서는 8개였으니 여유가 있었던 거예요.

엣지 케이스 점검:

```text
빈 힙에서 extractMin() / peek()        → undefined
원소 1개 힙에서 extractMin()           → 그 값 반환, 이후 isEmpty() === true
decreaseKey(node, 같은 값)             → 힙-순서 위반 아님(등호 허용), cut 없음
decreaseKey(node, 더 큰 값)            → 계약 위반 → 예외
merge(빈 힙, 빈 힙)                    → 빈 힙
루트 노드에 decreaseKey                → parent === null이라 cut 없이 값만 갱신, min 후보 비교만 수행
```

## 아이디어를 코드로 옮기기

`decreaseKey`가 이 자료구조의 핵심이니, 먼저 "만약 이진 힙처럼 즉시 재정렬했다면"이라는 원형(eager) 버전과 비교하며 봅니다.

```ts
// 원형(eager): 이진 힙이었다면 decrease-key를 이렇게 짰을 것이다 — 즉시 재정렬
function eagerDecreaseKey(heap: number[], index: number, newValue: number) {
  heap[index] = newValue;
  while (index > 0) {
    const parentIdx = Math.floor((index - 1) / 2);
    if (heap[parentIdx] <= heap[index]) break;
    [heap[parentIdx], heap[index]] = [heap[index], heap[parentIdx]];
    index = parentIdx;
  }
} // 트리 높이만큼 비교·스왑 → 호출마다 O(log n)
```

이 버전은 값을 낮출 때마다 트리 높이(=$\log n$)만큼 위로 거슬러 올라가며 비교·스왑합니다. 다익스트라처럼 decrease-key가 $O(E)$번 불리면 이 비용이 그대로 $O(E \log V)$로 누적돼요. Fibonacci heap의 발상은 "지금 정렬하지 않아도 된다"는 것 — 위반된 간선 하나만 $O(1)$에 잘라내고, 실제 재조립(트리를 다시 촘촘하게 만드는 일)은 `extractMin`의 consolidate로 미룹니다.

```ts
class FibNode<T> {
  item: T;
  degree = 0;
  marked = false;
  parent: FibNode<T> | null = null;
  child: FibNode<T> | null = null;
  left: FibNode<T>;
  right: FibNode<T>;

  constructor(item: T) {
    this.item = item;
    this.left = this;
    this.right = this;
  }
}

class FibonacciHeap<T> {
  private min: FibNode<T> | null = null;
  private count = 0;
  private compare: (a: T, b: T) => number;

  constructor(compare: (a: T, b: T) => number) {
    this.compare = compare;
  }

  private insertToRootList(node: FibNode<T>): void {
    if (this.min === null) {
      node.left = node;
      node.right = node;
      this.min = node;
      return;
    }
    node.left = this.min;
    node.right = this.min.right;
    this.min.right.left = node;
    this.min.right = node;
  }

  insert(item: T): FibNode<T> {
    const node = new FibNode(item);
    this.insertToRootList(node);
    if (this.compare(item, this.min!.item) < 0) this.min = node;
    this.count++;
    return node;
  }

  peek(): T | undefined {
    return this.min === null ? undefined : this.min.item;
  }

  size(): number {
    return this.count;
  }

  isEmpty(): boolean {
    return this.count === 0;
  }

  private removeFromList(node: FibNode<T>): void {
    node.left.right = node.right;
    node.right.left = node.left;
  }

  private addChild(parent: FibNode<T>, node: FibNode<T>): void {
    node.parent = parent;
    if (parent.child === null) {
      node.left = node;
      node.right = node;
      parent.child = node;
    } else {
      node.left = parent.child;
      node.right = parent.child.right;
      parent.child.right.left = node;
      parent.child.right = node;
    }
    parent.degree++;
  }

  // 더 작은 쪽이 부모가 된다.
  private link(a: FibNode<T>, b: FibNode<T>): FibNode<T> {
    let parent = a;
    let child = b;
    if (this.compare(b.item, a.item) < 0) {
      parent = b;
      child = a;
    }
    this.removeFromList(child);
    child.left = child;
    child.right = child;
    this.addChild(parent, child);
    child.marked = false;
    return parent;
  }

  private consolidate(): void {
    if (this.min === null) return;
    const maxDegree = Math.floor(Math.log2(Math.max(this.count, 1))) + 2;
    const table: (FibNode<T> | undefined)[] = new Array(maxDegree + 1).fill(undefined);

    const roots: FibNode<T>[] = [];
    let node = this.min;
    do {
      roots.push(node);
      node = node.right;
    } while (node !== this.min);

    for (let r of roots) {
      let d = r.degree;
      while (table[d] !== undefined) {
        let other = table[d]!;
        r = this.link(r, other); // 같은 차수 충돌마다 d를 한 칸씩 올리며 흡수
        table[d] = undefined;
        d++;
      }
      table[d] = r;
    }

    this.min = null;
    for (const r of table) {
      if (r === undefined) continue;
      r.left = r;
      r.right = r;
      if (this.min === null) {
        this.min = r;
      } else {
        this.insertToRootList(r);
        if (this.compare(r.item, this.min.item) < 0) this.min = r;
      }
    }
  }

  extractMin(): T | undefined {
    const z = this.min;
    if (z === null) return undefined;

    if (z.child !== null) {
      const children: FibNode<T>[] = [];
      let c = z.child;
      do {
        children.push(c);
        c = c.right;
      } while (c !== z.child);
      for (const child of children) {
        this.removeFromList(child);
        child.parent = null;
        child.left = child;
        child.right = child;
        this.insertToRootList(child);
      }
    }

    this.removeFromList(z);
    if (z.right === z) {
      this.min = null;
    } else {
      this.min = z.right;
      this.consolidate();
    }

    this.count--;
    return z.item;
  }

  private cut(node: FibNode<T>, parent: FibNode<T>): void {
    if (node.right === node) {
      parent.child = null;
    } else {
      if (parent.child === node) parent.child = node.right;
      this.removeFromList(node);
    }
    parent.degree--;
    node.left = node;
    node.right = node;
    node.parent = null;
    node.marked = false;
    this.insertToRootList(node); // cut 먼저: node를 루트 리스트로 물리적으로 옮긴다
  }

  private cascadingCut(node: FibNode<T>): void {
    const parent = node.parent;
    if (parent === null) return;
    if (!node.marked) {
      node.marked = true; // 첫 손실 — 표시만
    } else {
      this.cut(node, parent); // 두 번째 손실 — 잘라서 위로 전파
      this.cascadingCut(parent);
    }
  }

  decreaseKey(node: FibNode<T>, newItem: T): void {
    if (this.compare(newItem, node.item) > 0) {
      throw new Error("newItem must be <= current item");
    }
    node.item = newItem;
    const parent = node.parent;
    if (parent !== null && this.compare(node.item, parent.item) < 0) {
      this.cut(node, parent);
      this.cascadingCut(parent);
    }
    if (this.min === null || this.compare(node.item, this.min.item) < 0) {
      this.min = node;
    }
  }

  merge(other: FibonacciHeap<T>): FibonacciHeap<T> {
    const result = new FibonacciHeap<T>(this.compare);
    if (this.min === null) {
      result.min = other.min;
    } else if (other.min === null) {
      result.min = this.min;
    } else {
      const aRight = this.min.right;
      const bLeft = other.min.left;
      this.min.right = other.min;
      other.min.left = this.min;
      aRight.left = bLeft;
      bLeft.right = aRight;
      result.min = this.compare(this.min.item, other.min.item) <= 0 ? this.min : other.min;
    }
    result.count = this.count + other.count;
    return result;
  }
}
```

가장 중요한 부분은 `cut`과 `cascadingCut`의 순서입니다. `decreaseKey` 안에서 반드시 `cut(node, parent)`를 **먼저** 실행해 노드를 물리적으로 루트 리스트로 옮긴 다음, 그 부모에 대해 `cascadingCut(parent)`를 호출해야 합니다. 순서를 바꾸면 아직 부모에 붙어 있는 노드를 대상으로 부모 판정을 하게 되어 원형 연결 리스트 포인터가 꼬입니다.

놓치기 쉬운 지점들:

- `consolidate`의 `while (table[d] !== undefined)` 루프 — 링크할 때마다 `d++`로 한 칸씩 옮겨가며 충돌을 계속 흡수해야 합니다. `d++`를 빼먹으면 같은 칸을 계속 링크하려다 무한 루프에 빠지거나, 서로 다른 차수의 트리를 덮어씁니다.
- `cut` 안에서 `node.marked = false`를 반드시 리셋해야 합니다. 잘려서 루트가 된 노드는 더 이상 "누군가의 자식으로서 자식을 잃은 상태"가 아니니까요. 이걸 빼먹으면 나중에 이 노드가 다시 어딘가의 자식이 됐을 때 첫 손실인데도 곧바로 cascading cut이 발동합니다.
- `decreaseKey` 맨 앞의 `compare(newItem, node.item) > 0` 가드 — 이걸 빼면 사용자가 실수로 키를 늘렸을 때도 조용히 힙-순서를 깨뜨립니다.

기억법:

> cut은 잘라서 루트로 올리고, cascadingCut은 그 부모부터 위로 "아직 표시 안 됐으면 표시, 이미 표시돼 있으면 또 자르기"를 반복한다.

## 실행 시각화

정리하면, Fibonacci heap은 두 가지 지연 전략이 맞물려 목표를 달성합니다. **삽입·병합·decrease-key는 정리를 미루고 루트 리스트에 끼워 넣거나 잘라내기만** 하고, **실제 재조립은 `extractMin`의 consolidate 한 번에 몰아서** 처리합니다. cascading cut이 "자식을 두 번째로 잃을 때만 전파"하도록 강제하기 때문에 트리의 차수가 피보나치 수 하한 $F_{k+2}$ 아래로 내려가지 않고, 그 결과 최대 차수가 $O(\log n)$으로 묶여 consolidate가 $O(\log n)$ 상각에 끝납니다. 애초에 노렸던 것 — decrease-key를 $O(1)$ 상각으로 만들어 다익스트라를 $O(E + V\log V)$까지 낮추는 것 — 을 그대로 얻습니다.
