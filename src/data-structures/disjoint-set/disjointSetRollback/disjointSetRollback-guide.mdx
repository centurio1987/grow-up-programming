# DisjointSetRollback — 경로 압축을 포기하고, 되감기 가능한 유니온-파인드를 얻는다

## 한눈에 보는 컨셉

일반 유니온-파인드의 속도 비결이던 **경로 압축을 의도적으로 포기**하고, union by rank만으로 트리 높이를 $O(\log n)$에 묶어 두는 분리 집합이에요. 그 대가로 `union` 한 번이 `parent` 배열에서 정확히 한 자리, `rank` 배열에서 최대 한 자리만 바꾸게 되는데, 이 "변경 한 점"만 스택에 적어 두면 `rollback()`이 $O(1)$에 끝납니다. `snapshot()`/`restore(version)`까지 얹으면 특정 시점의 상태로 자유롭게 되감을 수 있는, 시간을 거스를 수 있는 유니온-파인드가 완성됩니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 DisjointSetRollback을 떠올리세요.

- union을 여러 번 수행한 뒤 "방금 합친 것들을 취소하고 이전 상태로 되돌리고 싶다"는 요구가 있다
- "시간 t 시점에 x와 y가 같은 그룹이었나?" 처럼 **시간을 되짚는 질의**가 반복된다
- 간선(또는 관계)이 특정 구간 `[l, r]`에서만 존재하는 오프라인 그래프 문제에서, 분할정복으로 "합치기 → 하위 구간 처리 → 되돌리기"를 반복해야 한다

일반 유니온-파인드는 경로 압축 덕분에 `find`가 사실상 $O(1)$이지만, 그 경로 압축이 정확히 문제입니다 — `find` 한 번이 조상 경로에 있는 **모든** 노드의 부모 포인터를 루트로 다시 연결해 버리기 때문에, 몇 개가 바뀌었는지조차 예측할 수 없어요. 롤백을 naive하게 구현한다면 union 전 상태 전체를 통째로 복사해 두는 방법이 있지만, 이건 원소 수 $n$에 비례하는 복사 비용을 union마다 물게 됩니다.

```text
매 union마다 parent/rank 전체를 deep copy       O(n) / union   → union이 m번이면 O(n·m) 시간·메모리
경로 압축을 포기하고 "바뀐 한 자리"만 기록        O(1) / union   → union이 m번이면 O(m) 시간·메모리
```

$n = 10^4$, union이 최악 $10^4$번 일어난다고 하면 전자는 대략 $10^8$개의 숫자를 복사해야 하지만, 후자는 딱 $10^4$개의 기록만 쌓으면 됩니다. **경로 압축을 포기하는 대신 "변경의 국소성"을 얻는 것** — 이게 이 자료구조의 트레이드오프입니다.

비슷한 목적의 다른 자료구조와는 이렇게 구분하세요: 롤백 없이 순수한 속도만 필요하면 **경로 압축 + union by rank를 쓰는 일반 유니온-파인드**, 시간 순서를 거스르는 되돌리기만 필요하면 **DisjointSetRollback**, 임의 시점의 임의 간선을 개별적으로 삭제해야 한다면(스택처럼 마지막 것부터 되돌리는 게 아니라) 훨씬 무거운 **Link-Cut Tree**를 고릅니다.

### 문제 사례와 적용 예시

- **오프라인 동적 연결성(분할정복 on time)**: 간선이 시간 구간 `[l, r]`에만 존재할 때, 구간을 반으로 나누며 걸쳐 있는 간선을 union하고, 재귀가 끝나면 그 union들만 정확히 되돌립니다. Link-Cut Tree 없이도 $O(m \log^2 n)$에 오프라인 동적 연결성을 풉니다.
- **게임 서버 파티 이력 분석**: "시간 t에 A와 B가 같은 파티였나?"를 수천 번 물어야 할 때, 파티 합류·해산 이벤트를 시간순으로 재생하며 union/rollback으로 그 순간의 그룹 상태를 복원합니다.
- **Kruskal MST 변형 실험**: 특정 간선을 강제로 배제/포함했을 때 MST가 어떻게 바뀌는지 실험(what-if)하고 원래 상태로 되돌아가야 하는 시나리오.
- **코딩 테스트 맥락**: "union 연산 여러 번 후, 최근 union을 되돌리거나 특정 시점으로 복원하라" — 일반 유니온-파인드에 상태 되돌리기 기능을 추가하는 문제로 자주 출제됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드가 정의하는 인터페이스는 다음과 같습니다.

```ts
type HistoryEntry =
  | { merged: false }
  | { merged: true; rootSmall: number; rootBig: number; oldRank: number };

class DisjointSetRollback {
  private parent: number[];       // parent[i] === i 면 i가 자기 트리의 루트
  private rank: number[];         // 루트일 때만 의미 있음: 그 트리 높이의 상한
  private count: number;          // 현재 독립 집합(컴포넌트) 수
  private history: HistoryEntry[]; // union이 남긴 변경 기록 스택
  private snapshots: number[];    // 버전 번호 → 그 시점의 history.length
}
```

지켜야 할 불변식은 다섯 가지예요.

1. **루트 판별**: `parent[x] === x` $\iff$ x가 자기 트리의 루트다.
2. **rank는 높이 상한**: 루트 $r$에 대해 $\mathrm{height}(T_r) \le \mathrm{rank}[r]$ (비루트 노드의 rank 값은 의미 없음, 과거 값이 남아 있을 뿐).
3. **union by rank 성립**: 루트 $r$의 rank가 $k$면 그 트리의 크기 $|T_r| \ge 2^k$ — 여기서 $\mathrm{rank}[r] \le \log_2 n$이 따라 나옵니다.
4. **기록의 완전성**: `history.length`는 지금까지 호출된 `union()`의 총 횟수(성공 + 실패)와 같다.
5. **카운트 정합성**: `count` = (초기 원소 수) − (아직 rollback되지 않은 **성공** union 수).

`t=0` 시점(초기 상태, $n=5$)과 몇 번의 union이 지난 뒤를 나란히 그려보면:

```text
초기:  parent=[0,1,2,3,4]  rank=[0,0,0,0,0]  count=5
       0    1    2    3    4        ← 5개의 독립된 트리(각자 자기 자신이 루트)

union(0,1), union(2,3) 이후:
       parent=[0,0,2,2,4]  rank=[1,0,1,0,0]  count=3

            0(rank1)      2(rank1)      4(rank0)
            |                |
            1                3
```

**액션(연산)** — 이 가이드가 구현하는 7종 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `find(x)` | 부모를 반복해서 따라가 루트 반환 (경로 압축 없음) | $O(\log n)$ |
| `union(x, y)` | rank 낮은(또는 동률인) 루트를 다른 루트 아래 붙이고, 변경 1건 기록 | $O(\log n)$ |
| `rollback()` | history 마지막 항목을 pop하고 그 변경만 되돌림 | $O(1)$ |
| `snapshot()` | 현재 `history.length`를 새 버전 번호로 저장 | $O(1)$ |
| `restore(v)` | `history.length`가 `snapshots[v]`에 이를 때까지 `rollback()` 반복 | $O(\text{되돌린 rollback 수})$ |
| `same(x, y)` | `find(x) === find(y)` | $O(\log n)$ |
| `groupCount()` | `count` 그대로 반환 | $O(1)$ |

핵심 연산 두 개만 자세히 볼게요.

**① union — 동률이면 y의 루트가 x의 루트 아래로.** 두 루트의 rank를 비교해 낮은 쪽을 높은 쪽 아래 붙이는데, **rank가 같을 때는 y쪽 루트(`ry`)가 x쪽 루트(`rx`) 아래로 들어가고 `rx`의 rank가 1 증가**하는 규칙으로 통일합니다.

```text
union(0, 1) 실행:  rx=find(0)=0, ry=find(1)=1, rank[0]=rank[1]=0 (동률)
  → 동률이므로 ry(=1)가 rx(=0) 아래로: small=1, big=0

Before: parent=[0,1,2,3,4]  rank=[0,0,0,0,0]
                                                     0(rank 0→1)
After:  parent=[0,0,2,3,4]  rank=[1,0,0,0,0]         |
                                                     1
history에 쌓인 기록: { merged: true, rootSmall: 1, rootBig: 0, oldRank: 0 }
```

**② rollback — 기록된 두 자리만 원위치.** 방금 union의 기록 `{ rootSmall: 1, rootBig: 0, oldRank: 0 }`을 되돌리면:

```text
Before: parent=[0,0,2,3,4]  rank=[1,0,0,0,0]  (union(0,1) 직후)
  parent[rootSmall] = rootSmall   →  parent[1] = 1
  rank[rootBig] = oldRank         →  rank[0] = 0
After:  parent=[0,1,2,3,4]  rank=[0,0,0,0,0]  (union 이전과 완전히 동일)
```

### 왜 모순 없이 작동하는가

**불변식 2·3(rank ↔ 높이 상한)이 보존되는 이유를 귀납으로 봅시다.**

- **기저**: 각 원소는 처음에 자기 자신이 루트, `rank=0`, 크기 1 $\ge 2^0 = 1$ — 불변식 3이 성립합니다.
- **귀납 단계**: 두 루트를 합칠 때 두 경우뿐입니다.
  - **rank가 다르면**: 낮은 쪽이 높은 쪽 아래 그대로 매달립니다. 큰 쪽 트리의 rank·높이는 바뀌지 않고, 낮은 쪽 서브트리는 이미 그보다 낮은 높이였으므로 전체 높이도 그대로예요. 불변식 그대로 유지됩니다.
  - **rank가 같으면(동률)**: 둘 다 크기 $\ge 2^k$인 트리이므로 합친 크기는 $\ge 2^{k+1}$이고, 새 rank도 정확히 $k+1$로 올라갑니다. 불변식 3이 그대로 다음 단계로 이어집니다.

  따라서 높이 $h$인 트리는 최소 $2^h$개의 노드를 가지므로 $h \le \log_2 n$이 항상 성립합니다.

**rollback이 딱 두 필드만 복원해도 충분한 이유**: 경로 압축이 없으므로 `union` 하나가 실제로 건드리는 셀은 `parent[rootSmall]`과(조건부로) `rank[rootBig]`, 이 두 개뿐입니다. 다른 어떤 노드의 `parent`나 `rank`도 이 union으로 인해 변한 적이 없어요. 그러니 이 두 필드를 union 이전 값으로 되돌리기만 하면, 배열 전체가 union 이전과 **완전히 동일한 상태**로 복원됩니다. 이것이 "변경의 국소성"이 곧 "롤백 비용 $O(1)$"으로 이어지는 이유예요.

여기서 헷갈리기 쉬운 포인트 몇 가지를 짚고 갈게요.

- **"실패한 union도 history에 기록해야 하나요?" — 네, 반드시요.** 기록하지 않으면 어떤 일이 벌어지는지 구체적으로 봅시다. `union(0,1)`이 성공(기록 #1), 그다음 `union(0,1)`을 다시 호출하면 이미 같은 집합이라 실패하는데 — 이걸 기록하지 않으면 history는 여전히 항목 1개뿐입니다. 이어서 `union(2,3)`이 성공(기록 #2, 하지만 실제 union 호출은 3번째). 이제 "union 호출 3번 중 마지막 2번(실패한 union + `union(2,3)`)을 되돌리자"며 `rollback()`을 2번 부르면, history엔 성공 기록 2개(`union(0,1)`, `union(2,3)`)밖에 없으므로 **둘 다 풀려버립니다** — `union(0,1)`까지 취소되어 `parent`가 `[0,1,2,3,4]`(전부 독립, `groupCount=5`)로 돌아가 버려요. 원래 의도는 `union(2,3)`만 취소하고 `union(0,1)`의 병합은 살아 있는 `groupCount=4` 상태였는데 말이죠. 실패한 union도 `{ merged: false }`로 push해 두면 "union 호출 횟수 = history 길이"가 항상 성립해 이런 어긋남이 생기지 않습니다.
- **`find`에 경로 압축을 슬쩍 넣고 싶은 유혹.** 성능이 좋아 보이니 습관적으로 넣기 쉽지만, 경로 압축은 `find` 호출 한 번으로 조상 경로의 여러 `parent`를 한꺼번에 바꿔 버립니다. `union`이 기록하는 항목은 "루트 하나의 `parent`, 루트 하나의 `rank`"뿐이라, 경로 압축이 만든 나머지 변경은 **어디에도 기록되지 않고 조용히 남습니다**. 이후 `rollback()`을 아무리 정확히 해도 이 압축된 포인터들은 되돌아오지 않아요 — 그래서 이 자료구조는 경로 압축을 아예 쓰지 않습니다.
- **`restore(v)`는 새로운 메커니즘이 아니라 `rollback()`의 반복일 뿐.** `snapshot()`이 저장하는 건 상태의 복사본이 아니라 **그 시점의 `history.length`** 하나뿐이에요. `restore(v)`는 그 숫자에 도달할 때까지 `rollback()`을 계속 부르는 것으로 끝입니다 — 별도의 "점프" 로직이 없습니다.

잠깐, 확인 하나만 해 볼까요? `history.length`가 3인 상태에서 `snapshot()`을 두 번 연달아 호출하면 어떻게 될까요? — 두 번 모두 `history.length`가 안 바뀐 채로 호출되므로, 서로 다른 버전 번호(예: `v3`, `v4`)가 발급되지만 `snapshots[3]`과 `snapshots[4]`에는 똑같이 `3`이 저장됩니다. 둘 중 어느 버전으로 `restore`해도 결과는 같아요.

엣지 케이스를 점검해 봅시다.

```text
n = 1                        → union(0,0)은 find(0)===find(0)이라 항상 false, groupCount는 항상 1
빈 history에서 rollback()    → history.pop()이 undefined → 아무 일도 안 함(no-op)
restore(현재 버전)            → snapshots[v] === history.length → while 조건이 거짓 → no-op
union(x, x) 자기 자신         → rx===ry이므로 항상 false, 그래도 { merged: false }로 기록은 남음
연속된 성공 union 후 즉시 전부 rollback → parent/rank/count가 초기 생성 시점과 완전히 동일해짐
```

## 아이디어를 코드로 옮기기

**원형(naive) — union 전마다 전체 상태를 deep copy.** 가장 단순한 접근은 "되돌리려면 이전 상태를 통째로 저장해 두면 된다"는 발상입니다.

```ts
class NaiveRollbackDSU {
  private parent: number[];
  private rank: number[];
  private count: number;
  private snapshots: { parent: number[]; rank: number[]; count: number }[] = [];

  constructor(n: number) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
    this.count = n;
  }

  find(x: number): number {
    while (this.parent[x] !== x) x = this.parent[x];
    return x;
  }

  union(x: number, y: number): boolean {
    // 매 union 전에 parent/rank 전체를 통째로 복사해 둔다 — O(n)
    this.snapshots.push({ parent: [...this.parent], rank: [...this.rank], count: this.count });
    const rx = this.find(x);
    const ry = this.find(y);
    if (rx === ry) return false;
    const [small, big] = this.rank[ry] > this.rank[rx] ? [rx, ry] : [ry, rx];
    this.parent[small] = big;
    if (this.rank[small] === this.rank[big]) this.rank[big]++;
    this.count--;
    return true;
  }

  rollback(): void {
    const prev = this.snapshots.pop();
    if (!prev) return;
    this.parent = prev.parent;
    this.rank = prev.rank;
    this.count = prev.count;
  }
}
```

이 방식은 정확하지만, union 하나마다 배열 두 개를 통째로 복사합니다 — $n = 10^4$이고 union이 최악 $10^4$번이면 대략 $10^8$개 숫자를 복사하는 셈이라, 메모리도 시간도 감당하기 어렵습니다.

**개선 — "바뀐 한 자리"만 기록.** 경로 압축을 포기하고 union by rank만 쓰면, union 하나가 실제로 바꾸는 셀은 `parent[rootSmall]` 하나와 `rank[rootBig]`(조건부) 하나뿐이라는 걸 앞서 확인했습니다. 전체 배열 대신 이 변경 하나만 기록하면 충분해요.

```ts
type HistoryEntry =
  | { merged: false }
  | { merged: true; rootSmall: number; rootBig: number; oldRank: number };

class DiffRollbackDSU {
  private parent: number[];
  private rank: number[];
  private count: number;
  private history: HistoryEntry[] = [];

  constructor(n: number) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
    this.count = n;
  }

  find(x: number): number {
    while (this.parent[x] !== x) x = this.parent[x]; // 경로 압축 없음 — 반드시!
    return x;
  }

  union(x: number, y: number): boolean {
    const rx = this.find(x);
    const ry = this.find(y);
    if (rx === ry) {
      this.history.push({ merged: false }); // 실패도 반드시 기록
      return false;
    }
    const [small, big] = this.rank[ry] > this.rank[rx] ? [rx, ry] : [ry, rx];
    this.history.push({ merged: true, rootSmall: small, rootBig: big, oldRank: this.rank[big] });
    this.parent[small] = big;
    if (this.rank[small] === this.rank[big]) this.rank[big]++;
    this.count--;
    return true;
  }

  rollback(): void {
    const entry = this.history.pop();
    if (!entry || !entry.merged) return;
    this.parent[entry.rootSmall] = entry.rootSmall;
    this.rank[entry.rootBig] = entry.oldRank;
    this.count++;
  }
}
```

union 하나당 메모리·시간이 $O(1)$로 줄었습니다. 이제 여기에 `snapshot`/`restore`만 얹으면 원하는 시점으로 자유롭게 되감을 수 있어요.

**최종 — snapshot/restore와 조회 연산까지.**

```ts
type HistoryEntry =
  | { merged: false }
  | { merged: true; rootSmall: number; rootBig: number; oldRank: number };

class DisjointSetRollback {
  private parent: number[];
  private rank: number[];
  private count: number;
  private history: HistoryEntry[] = [];
  private snapshots: number[] = [];

  constructor(n: number) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
    this.count = n;
  }

  find(x: number): number {
    while (this.parent[x] !== x) x = this.parent[x];
    return x;
  }

  union(x: number, y: number): boolean {
    const rx = this.find(x);
    const ry = this.find(y);
    if (rx === ry) {
      this.history.push({ merged: false });
      return false;
    }
    const [small, big] = this.rank[ry] > this.rank[rx] ? [rx, ry] : [ry, rx];
    this.history.push({ merged: true, rootSmall: small, rootBig: big, oldRank: this.rank[big] });
    this.parent[small] = big;
    if (this.rank[small] === this.rank[big]) this.rank[big]++;
    this.count--;
    return true;
  }

  rollback(): void {
    const entry = this.history.pop();
    if (!entry || !entry.merged) return;
    this.parent[entry.rootSmall] = entry.rootSmall;
    this.rank[entry.rootBig] = entry.oldRank;
    this.count++;
  }

  snapshot(): number {
    const version = this.snapshots.length;
    this.snapshots.push(this.history.length);
    return version;
  }

  restore(version: number): void {
    const target = this.snapshots[version];
    while (this.history.length > target) this.rollback();
  }

  same(x: number, y: number): boolean {
    return this.find(x) === this.find(y);
  }

  groupCount(): number {
    return this.count;
  }
}
```

가장 중요한 부분은 `union`의 이 한 줄입니다.

```ts
const [small, big] = this.rank[ry] > this.rank[rx] ? [rx, ry] : [ry, rx];
```

`rank[ry]`가 `rank[rx]`보다 **엄격히** 클 때만 `rx`가 밑으로 가고, 그 외(더 작거나 **동률**일 때)는 `ry`가 밑으로 갑니다. 이 삼항식이 곧 union by rank 규칙 전체이고, `rollback`이 되돌려야 할 "바뀐 자리"가 정확히 어디인지도 이 한 줄에서 결정됩니다.

구현에서 놓치기 쉬운 지점들:

- **`find`에 경로 압축을 넣지 않기.** 앞서 봤듯 경로 압축은 기록되지 않는 변경을 만들어 rollback을 깨뜨립니다. 성능을 위해 습관적으로 추가하고 싶은 유혹이 있지만, 이 자료구조에서는 절대 금지입니다.
- **`merged: false`도 반드시 push.** 실패한 union을 기록에서 빼면 `history.length`(= union 호출 횟수)와 `snapshots`가 저장하는 인덱스가 어긋나 `restore`가 엉뚱한 시점으로 돌아갑니다.
- **`rollback`은 정확히 두 필드만 되돌린다.** `parent[rootSmall] = rootSmall`과 `rank[rootBig] = oldRank` — 이 두 줄의 순서는 사실 상관없지만(서로 다른 배열이므로), 둘 다 빠짐없이 실행돼야 합니다. 하나라도 빠지면 `rank`가 부풀려진 채로 남아 다음 union의 tie-break 결과가 틀어집니다.
- **`restore`는 `rollback`을 재사용.** 별도로 상태를 복원하는 로직을 새로 짜지 말고, 이미 검증된 `rollback()`을 반복 호출하는 것으로 충분합니다 — 로직 중복도 줄고 버그 표면도 줄어듭니다.

> 기억법: "되감기는 딱 그 프레임에서 바뀐 값만 원위치 — union이 바꾼 자리가 한 곳(많아야 두 곳)이니, 되돌릴 자리도 딱 그만큼."
