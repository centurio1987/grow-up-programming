# Union-Find — 흩어진 원소를 트리 하나로 묶어 순식간에 묻는 자료구조

## 한눈에 보는 컨셉

여러 원소를 그룹(집합)으로 묶고, "이 두 원소가 같은 그룹인가?"를 반복해서 물어야 할 때 쓰는 자료구조예요. 비결은 각 집합을 루트 하나가 대표하는 **트리**로 표현하고, 트리가 삐뚤어지지 않도록 항상 낮은 트리를 높은 트리 아래에 붙이면서(랭크 합치기), 질문이 들어올 때마다 지나간 경로를 루트에 바로 이어 붙이는 것(경로 압축)입니다. 이 두 가지만 지키면 그룹 병합과 소속 확인 모두 사실상 $O(1)$ — 정확히는 $O(\alpha(n))$ — 에 끝나요. 여기서 $\alpha(n)$은 **역 아커만 함수(inverse Ackermann function)** 로, 극단적으로 느리게 커지는 함수예요. 우주의 원자 수보다도 큰 $n \le 10^{600}$에서도 $\alpha(n) \le 4$를 넘지 않으니, 실무에서는 사실상 상수로 봐도 됩니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Union-Find를 떠올리세요.

- "두 원소가 같은 그룹/컴포넌트/클러스터에 속하는가?"를 **반복해서** 물어본다
- 그룹을 **합치는(merge)** 연산은 있지만, 그룹을 **쪼개는(split)** 연산은 없다
- 최종적으로 "몇 개의 그룹이 남았는가", "가장 큰 그룹의 크기는?" 같은 집계 질문이 따라온다

집합을 배열 `id[x]`에 대표를 직접 저장하는 방식으로 풀면 `union`마다 배열 전체를 훑어야 해서 $O(n)$이고, 그래프로 만들어 매번 BFS/DFS로 연결성을 확인하면 질의 한 번에 $O(n+m)$입니다. $q$번의 질의가 섞이면 각각 $O(qn)$인데, $n, q \leq 10^5$이면 $10^{10}$ 규모라 시간 제한 안에 못 끝나요.

```text
방식                      union 비용     find/조회 비용     q번 반복 시 총비용
배열에 대표 직접 저장      O(n)           O(1)               O(qn)
그래프 + 매번 BFS/DFS      O(1)(간선추가)  O(n + m)           O(q(n+m))
Union-Find(랭크+압축)      O(α(n))        O(α(n))            O(qα(n)) ≈ O(q)
```

**비슷한 자료구조와의 선택 기준**: 그래프 자체의 경로·거리 정보가 필요하면 BFS/DFS나 최단거리 알고리즘을 쓰고, 연결 여부만 반복해서 물으면 Union-Find가 압도적으로 쌉니다. 다만 간선을 **삭제**해야 하는 상황(동적 연결성에서 cut까지 필요)이라면 Union-Find로는 부족하고 Link-Cut Tree 같은 고급 구조로 넘어가야 해요.

### 문제 사례와 적용 예시

- **Kruskal 최소 신장 트리**: 간선을 가중치 순으로 정렬한 뒤 하나씩 추가하면서 "두 끝점이 이미 같은 집합인가"를 확인해 사이클을 걸러냅니다. Union-Find 없이는 이 사이클 판정이 알고리즘 전체를 $O(n)$짜리 병목으로 만들어요.
- **소셜 네트워크 그룹 관리**: 사용자 수십만 명 사이에 "친구 추가" 이벤트가 들어올 때마다 두 그룹을 합치고, "이 두 사람이 같은 커뮤니티인가"를 수시로 조회합니다.
- **이미지 연결 요소 라벨링**: 픽셀을 순회하며 인접 픽셀이 같은 색이면 union하는 방식으로, 재귀 DFS 없이도 스택 오버플로 걱정 없이 연결 요소를 구합니다.
- **코딩 테스트 맥락**: "친구 관계/네트워크 간선이 하나씩 들어올 때마다 두 노드가 이미 연결되어 있는지 판정하라" 유형은 거의 예외 없이 이 구조로 풀립니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 배열 두 개만 유지합니다.

```ts
class UnionFind {
  parent: number[]; // parent[x] = x의 부모. 루트면 parent[x] === x
  rank: number[];   // rank[x] = x를 루트로 하는 트리의 높이 상한(루트에서만 의미 있음)
}
```

지켜야 할 불변식은 두 가지입니다.

1. **루트 자기 참조**: $\text{parent}[r] = r \iff r\text{이 대표(루트)}$.
2. **랭크는 높이 상한**: 루트 $r$에 대해, $r$을 루트로 하는 트리의 (경로 압축을 적용하기 전 기준) 높이는 $\text{rank}[r]$을 넘지 않는다.

초기값은 $\text{parent}[i] = i$, $\text{rank}[i] = 0$ ($0 \leq i < n$) — 모든 원소가 자기 자신만의 집합입니다.

```text
초기 상태 (n=5): 모든 원소가 독립된 트리(자기 자신이 루트)

  (0)   (1)   (2)   (3)   (4)      parent = [0,1,2,3,4]
                                    rank   = [0,0,0,0,0]

union이 진행되면 작은 트리가 큰 트리의 자식으로 붙어 이런 모양이 됩니다.

        (0) rank=2
       /  |  \
     (1) (2) ...                   parent[1]=0, parent[2]=0
                                    루트만 rank가 의미를 가진다
```

**액션(연산)** — 이 자료구조가 제공하는 연산 전부입니다. 비용은 **분할 상환(amortized)** 기준인데, 이는 한 번의 최악 호출이 아니라 여러 번의 호출에 걸쳐 평균 낸 비용을 뜻해요(경로 압축은 한 번 값을 치르면 그 경로가 짧아져 다음 호출들이 싸지므로, 개별 최악이 아닌 평균으로 재는 게 공정합니다).

| 액션 | 하는 일 | 비용(분할 상환) |
|------|---------|------|
| `find(x)` | $x$가 속한 집합의 대표(루트)를 반환. 지나간 경로를 루트에 압축 | $O(\alpha(n))$ |
| `union(x, y)` | $x$, $y$가 속한 두 집합을 하나로 합침. 이미 같으면 아무 일도 안 함 | $O(\alpha(n))$ |
| `connected(x, y)` | $\text{find}(x) = \text{find}(y)$ 여부 반환 | $O(\alpha(n))$ |

핵심 연산 두 개를 그림으로 자세히 볼게요.

**① find — 경로 압축(before/after)**. 사슬처럼 늘어진 경로를 한 번 훑으면서 전부 루트에 직접 연결합니다.

```text
Before find(3):        0
                        \
                         2
                          \
                           3          parent = [0, 0, 2, 2, 4]  (3은 루트 0까지 2홉)

find(3) 호출 → 재귀로 루트(0)까지 올라간 뒤, 돌아오면서 즉시 재배선

After find(3):         0
                      / \
                     2   3            parent = [0, 0, 0, 0, 4]  (3은 이제 1홉)

3뿐 아니라 경로 위의 모든 노드(여기서는 2도)가 루트에 바로 연결됩니다.
```

**② union — 랭크 기준 합치기(before/after)**. 항상 낮은 트리를 높은 트리 아래에 붙여, 합친 트리의 높이가 함부로 늘지 않게 합니다.

```text
Before union(1, 2):   (0)rank=1        (2)rank=1
                        |                |
                       (1)              (3)

두 루트(0, 2)의 rank가 같다(1 = 1) → 어느 한쪽 아래에 붙이고, rank를 1만 올린다.

After union(1, 2):     (0)rank=2
                      /   \
                    (1)   (2)
                            |
                           (3)

루트가 하나로 합쳐졌고, rank가 같았던 경우에만 rank[0]이 2로 올라간다.
```

### 왜 모순 없이 작동하는가

**루트 자기 참조가 항상 유지되는 이유**: 초기 상태에서 모든 원소가 자기 자신을 부모로 가지므로 불변식 1이 성립합니다. `union(x, y)`는 두 루트 중 하나($r_y$)의 부모만 바꾸고, 그 루트는 더 이상 루트가 아니게 됩니다. 남은 루트($r_x$)는 그대로 자기 자신을 가리키므로, 어떤 시점에도 "루트 ⟺ `parent[r] = r`"이 깨지지 않습니다. `find`의 경로 압축은 루트가 아닌 노드들의 부모만 바꾸므로 이 불변식에 영향을 주지 않습니다.

**랭크가 높이 상한을 유지하는 이유**: 두 트리(높이 상한 $h_x$, $h_y$)를 합칠 때, 낮은 쪽을 높은 쪽 아래에 붙이면 합친 트리의 높이는 $\max(h_x, h_y)$를 넘지 않습니다. 오직 두 랭크가 같을 때($h_x = h_y$)만 새 트리의 높이가 $h_x + 1$이 될 수 있어서, 그때만 랭크를 1 올립니다. 이 규칙을 지키는 한 랭크는 항상 실제 높이의 상한으로 남습니다 — 이 상한이 $O(\log n)$을 넘지 않는다는 사실(랭크가 $k$인 트리는 최소 $2^k$개의 원소를 담아야 함)과, 여기에 경로 압축을 더하면 분할 상환 $O(\alpha(n))$이 나온다는 것이 Tarjan(1975)의 고전적인 결과입니다 — 앞서 봤듯 $\alpha(n)$은 $n \le 10^{600}$에서도 4를 넘지 않으므로, 이 상한이 곧 "사실상 $O(1)$"의 근거입니다.

여기서 헷갈리기 쉬운 포인트는 **"랭크가 항상 원소 개수와 비례한다"는 오해**입니다. 랭크는 트리의 **높이** 상한이지 원소 개수가 아니에요. 경로 압축이 여러 번 일어나면 트리 안의 원소 수는 늘어도 실제 높이는 오히려 줄어들 수 있는데, 이때 랭크 값은 갱신되지 않고 예전 상한 그대로 남습니다(무해하지만 더 이상 "정확한" 높이는 아니고 "상한"일 뿐입니다).

또 하나, **`union(x, y)`에서 `find(x) === find(y)`를 확인하지 않고 바로 진행하면 안 됩니다.** 이미 같은 집합인데 이 확인을 생략하면, 코드가 `rank[rx] === rank[ry]`(자기 자신과 비교하니 항상 참)를 만족해 매번 `rank[rx]`를 올려버립니다. 아래 "함정" 절에서 이 상황을 100번 반복했을 때 랭크가 실제 필요치보다 100배 부풀어 오르는 것을 실측으로 보여드릴게요.

확인 질문 하나 — `n = 1`일 때 `connected(0, 0)`은 무엇을 반환해야 할까요? 정답은 `true`입니다. `find(0)`은 `parent[0] === 0`이므로 즉시 `0`을 반환하고, `find(0) === find(0)`은 항상 참이니까요.

엣지 케이스 점검:

```text
n = 1                     → find(0) = 0, connected(0,0) = true (유일한 원소)
초기 상태 connected(x,y)   → x != y이면 항상 false (모두 독립)
union(x, x)               → find(x) === find(x)로 조기 반환, 변화 없음
루트인 x에 대한 find(x)    → parent[x] === x이므로 재귀 없이 즉시 반환
같은 union을 반복 호출     → 두 번째 호출부터는 rx === ry로 조기 반환, 무해
```

## 아이디어를 코드로 옮기기

Union-Find는 "왜 이 구조에 도달했는가"가 성능과 직결되는 자료구조라서, 원형부터 최종까지 단계를 밟아 봅니다.

**원형(naive)**: 대표를 배열 `id[x]`에 직접 저장합니다. `find`는 배열을 읽기만 하면 되니 $O(1)$이지만, `union`은 한쪽 그룹 전체의 `id`를 새 대표로 바꿔야 해서 $O(n)$입니다.

```ts
class NaiveUnionFind {
  id: number[];
  constructor(n: number) {
    this.id = Array.from({ length: n }, (_, i) => i);
  }
  find(x: number): number {
    return this.id[x]!;
  }
  union(x: number, y: number): void {
    const from = this.id[x]!;
    const to = this.id[y]!;
    if (from === to) return;
    for (let i = 0; i < this.id.length; i++) {
      if (this.id[i] === from) this.id[i] = to; // 그룹 전체를 훑는다 → O(n)
    }
  }
  connected(x: number, y: number): boolean {
    return this.find(x) === this.find(y);
  }
}
```

$n = 1000$인 배열에서 원소를 순서대로 사슬처럼 묶어 가며(`union(0,1), union(1,2), ..., union(998,999)`) 999번 `union`을 호출하면, 매번 최악 $n$칸을 훑는다고 볼 때 총 스캔 횟수가 $999 \times 1000 = 999000$에 달합니다. $n, q \leq 10^5$ 제약에서는 이 방식이 곧바로 시간 초과로 이어져요.

**폭발 지점**: 대표를 직접 유지하니 `union`이 $O(n)$입니다. 그럼 트리로 바꿔서 `union`을 $O(1)$로 만들면 될까요? 시도해 봅니다.

**개선(트리, 랭크 없음)**: 각 원소가 부모를 가리키게 하고, `union`은 그저 한쪽 루트를 다른 쪽 루트 아래에 붙이기만 합니다.

```ts
class TreeOnlyUnionFind {
  parent: number[];
  constructor(n: number) {
    this.parent = Array.from({ length: n }, (_, i) => i);
  }
  find(x: number): number {
    let cur = x;
    while (this.parent[cur] !== cur) cur = this.parent[cur]!;
    return cur;
  }
  union(x: number, y: number): void {
    const rx = this.find(x);
    const ry = this.find(y);
    if (rx === ry) return;
    this.parent[rx] = ry; // 방향을 고정해서 붙인다 — 편향 위험!
  }
  connected(x: number, y: number): boolean {
    return this.find(x) === this.find(y);
  }
}
```

이제 `union`은 $O(\text{find 비용})$까지 줄었지만, **어느 쪽을 아래에 붙일지 랭크로 판단하지 않고 방향을 고정**해 버리면 문제가 생깁니다. `union(0,1), union(1,2), union(2,3), union(3,4), union(4,5)`를 차례로 호출하면 `parent = [1, 2, 3, 4, 5, 5]` — 완전히 늘어진 사슬이 만들어집니다. 이 상태에서 `find(0)`을 호출하면 실제로 **5홉**(원소 6개 중 최악)을 거쳐야 루트에 도달해요. $n = 10^5$ 규모로 이런 패턴이 반복되면 `find` 한 번이 $O(n)$이 되어, $q$번 반복 시 다시 $O(qn)$으로 되돌아갑니다 — 트리로 바꾼 보람이 없어지는 것이죠.

**최종(랭크 합치기 + 경로 압축)**: 낮은 트리를 높은 트리 아래에 붙이고(랭크), `find`가 지나간 경로를 루트에 바로 이어 붙입니다(경로 압축).

```ts
class UnionFind {
  parent: number[];
  rank: number[];

  constructor(n: number) {
    this.parent = Array.from({ length: n }, (_, i) => i);
    this.rank = new Array(n).fill(0);
  }

  find(x: number): number {
    if (this.parent[x] !== x) {
      this.parent[x] = this.find(this.parent[x]!); // 경로 압축
    }
    return this.parent[x]!;
  }

  union(x: number, y: number): void {
    let rx = this.find(x);
    let ry = this.find(y);
    if (rx === ry) return; // 이미 같은 집합 — 반드시 여기서 멈춰야 한다
    if (this.rank[rx]! < this.rank[ry]!) {
      [rx, ry] = [ry, rx]; // rx가 항상 랭크가 같거나 더 높도록 정렬
    }
    this.parent[ry] = rx; // 낮은 쪽을 높은 쪽 아래로
    if (this.rank[rx] === this.rank[ry]) {
      this.rank[rx]!++; // 랭크가 같았을 때만 높이가 늘어난다
    }
  }

  connected(x: number, y: number): boolean {
    return this.find(x) === this.find(y);
  }
}
```

**가장 중요한 부분은 `find`의 `this.parent[x] = this.find(this.parent[x]!)` 한 줄입니다.** 재귀 호출로 루트를 찾아낸 뒤, 그 반환값을 **바로 `parent[x]`에 대입**하기 때문에 재귀가 돌아오는 매 단계마다 경로 위의 노드가 루트에 직결됩니다. 이 대입을 빼고 `return this.find(this.parent[x])`만 하면 반환값은 똑같이 맞지만 압축이 전혀 일어나지 않아, 트리가 계속 예전 모양 그대로 남습니다.

또 하나 놓치기 쉬운 부분은 **`union` 맨 앞의 `if (rx === ry) return;`**입니다. 이 줄을 빼면 어떻게 되는지는 바로 아래 함정에서 실측으로 보여드릴게요.

> 기억법: "낮은 놈이 높은 놈 밑으로, 지나간 길은 전부 지름길로."

**함정**: `rx === ry` 조기 반환을 빼고 `union(0, 0)`을 100번 반복하면, 코드는 매번 `rank[rx] === rank[ry]`(자기 자신이니 항상 참)를 만족해 `rank[0]`을 계속 올립니다. 실측해 보면 조기 반환이 있는 정상 버전은 100번 반복 후에도 `rank[0] = 0` 그대로인 반면, 조기 반환을 뺀 버전은 `rank[0]`이 그대로 **100**까지 부풀어 오릅니다. 랭크가 실제 트리 높이와 무관하게 커지면 "낮은 쪽을 높은 쪽 아래에" 판단 기준 자체가 왜곡되어, 이후의 `union`들이 필요 이상으로 큰 트리 아래에 원소를 계속 쌓게 되고 결국 `find`가 다시 느려질 수 있습니다.
