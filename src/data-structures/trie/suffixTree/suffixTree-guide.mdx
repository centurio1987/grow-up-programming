# SuffixTree — 모든 접미사를 한 트라이에 몰아넣고, 패턴 검색을 접두사 찾기로 바꾸기

## 한눈에 보는 컨셉

문자열 $s$의 모든 접미사 $s[0..n{-}1],\, s[1..n{-}1],\, \dots,\, s[n{-}1..n{-}1]$을 압축 트라이(Radix Tree) 하나에 삽입해 두는 자료구조예요. 비결은 딱 한 줄로 요약됩니다 — **패턴 $p$가 $s$의 부분 문자열이라는 것은, $p$가 $s$의 어떤 접미사의 접두사라는 것과 정확히 같은 말**입니다. 이 동치 관계 덕분에 "부분 문자열 검색"이라는 문제가 "트라이에서 접두사 따라 내려가기"로 바뀌고, 전처리에 Naive $O(n^2)$를 한 번 들이면 이후 패턴 검색은 패턴 길이 $m$에만 비례하는 $O(m)$으로 끝납니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 접미사 트리를 떠올리세요.

- 같은 문자열 $s$에 대해 **서로 다른 패턴으로 존재 여부·등장 위치를 반복해서** 물어야 한다
- "가장 긴 반복되는 부분 문자열"처럼 **문자열 내부의 반복 구조 자체**를 물어보는 요구가 있다
- $s$는 한 번만 정해지고, 그 위에서 짧은 패턴 $m$에 대한 쿼리를 **아주 많이** 던진다(쿼리당 비용을 $m$에만 묶고 싶다)

매번 KMP로 검색하는 방식과 비교하면 효과가 뚜렷합니다.

```text
전략             1회 쿼리        q회 쿼리 누적                비고
KMP (매번 처음부터)  O(n+m)       O(q(n+m))                  전처리 없음, s가 커지면 쿼리마다 비쌈
접미사 배열         O(m log n)    O(n log n) + O(q · m log n)  이진 탐색 필요, 공간은 절약
접미사 트리         O(m)         O(n²) + O(q · m)            Naive 구성, 쿼리는 이 중 가장 빠름
```

선택 기준은 간단해요. **구성 비용을 감당할 수 있고 쿼리를 많이 던질 것이라면 접미사 트리**, 반대로 $n$이 매우 커서 $O(n^2)$ 구성 자체가 부담이라면 접미사 배열이나(구성 $O(n \log n)$) Ukkonen's 알고리즘(구성 $O(n)$)을 고려합니다.

### 문제 사례와 적용 예시

- **유전체 서열 분석(BLAST 등)**: 약 30억 염기로 이루어진 DNA 문자열에서 특정 패턴이 어디에, 몇 번 등장하는지를 수시로 검색합니다.
- **텍스트 에디터의 Find 최적화**: 같은 문서에서 사용자가 검색어를 바꿔가며 여러 번 찾을 때, 문서를 매번 처음부터 훑지 않습니다.
- **데이터 압축(LZ 계열)**: 반복되는 부분 문자열을 찾아 짧은 참조로 치환하는 것이 압축의 핵심인데, 이 반복 구조를 접미사 트리로 빠르게 찾습니다.
- **코딩 테스트 맥락**: "문자열 $s$에서 패턴 여러 개를 검색하라", "$s$에서 두 번 이상 등장하는 가장 긴 부분 문자열을 구하라" 같은 문제가 직접적인 적용 대상입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 트리는 다음 형태의 노드로 구성됩니다.

```ts
interface SuffixNode {
  children: Map<string, SuffixNode>; // 에지 첫 글자 → 자식 노드
  label: string;                     // 이 에지의 레이블(압축된 문자열 조각)
  indices: number[];                 // 이 노드를 지나는 모든 접미사의 시작 인덱스 (합집합)
}
```

루트에서 어떤 노드 $v$까지 에지 레이블을 순서대로 이어 붙인 문자열을 $P_v$(경로 문자열)라 부를게요. 지켜야 할 불변식은 두 가지입니다.

1. **경로 압축**: 형제 에지는 첫 글자가 겹치지 않는다. 한 노드의 두 자식 에지는 항상 서로 다른 문자로 시작한다.
2. **indices의 정의**: 각 노드 $v$의 `indices`는 정확히 이 집합과 같다.

$$
\text{indices}(v) = \{\, i \mid 0 \le i < n,\ s[i .. i+|P_v|) = P_v \,\}
$$

말로 풀면 "$v$까지의 경로 문자열 $P_v$를 접두사로 갖는 접미사들의 시작 인덱스 전체"입니다. 이 정의가 바로 `findAll`과 `longestRepeatedSubstring`의 정확성 근거가 됩니다 — **`indices(v)`의 크기는 곧 $P_v$가 $s$에 등장하는 횟수**예요.

$s = \text{"banana"}$의 접미사 6개(`banana(0) anana(1) nana(2) ana(3) na(4) a(5)`)를 전부 삽입한 최종 트리는 이렇게 생겼습니다.

```text
                    ROOT
        ┌────────────┼────────────┐
     "banana"        "a"          "na"
     idx=[0]      idx=[1,3,5]   idx=[2,4]
                      │             │
                     "na"          "na"
                   idx=[1,3]      idx=[2]
                      │
                     "na"
                   idx=[1]
```

`"a"` 노드의 경로 문자열은 `"a"`(등장 3회), 그 아래 `"na"` 노드의 경로 문자열은 `"a"+"na"="ana"`(등장 2회) — 실제로 "ana"는 인덱스 1과 3에서 시작하는 두 접미사가 공유하는 접두사입니다.

**액션(연산)** — 이 가이드가 정의하는 인터페이스는 4가지입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(s)` | 접미사 $s[i..n{-}1]$ ($i=0,\dots,n{-}1$)을 순서대로 압축 트라이에 삽입 | $O(n^2)$ (Naive: 접미사 $n$개 × 평균 삽입 비교 $O(n)$) |
| `search(pattern)` | 루트에서 패턴을 따라 내려가며 존재 여부 확인 | $O(m)$ |
| `findAll(pattern)` | 패턴이 끝나는 노드의 `indices`를 반환 | $O(m + k)$ ($k$ = 등장 횟수) |
| `longestRepeatedSubstring()` | `indices.length >= 2`인 가장 깊은 노드의 경로 문자열 | $O(n)$ (DFS 1회, 전체 에지 길이 합은 $O(n^2)$이지만 순회 자체는 노드 수·에지 수에 비례) |

핵심 연산인 **삽입 중 에지 분할**을 자세히 볼게요. `"anana"`(idx=1)가 이미 있는 상태에서 `"ana"`(idx=3)를 삽입하면 두 문자열의 공통 접두사 `"ana"`(3글자) 지점에서 에지가 갈라집니다.

```text
Before:  ROOT ── "anana"  idx=[1]

After:   ROOT ── "ana"  idx=[1, 3]     ← 새 분기점. 공통 접두사 길이만큼만 자른 것
                   │
                  "na"  idx=[1]         ← 원래 "anana" 에지의 나머지 조각
```

여기서 분기점(`mid`)의 `indices`는 **원래 자식이 갖고 있던 `[1]`에 새 인덱스 `3`을 더한 `[1, 3]`**이 되어야 합니다. 왜 그래야 하는지는 바로 다음 절에서 짚어 볼게요.

### 왜 모순 없이 작동하는가

**`indices(v)` 불변식이 삽입 내내 보존되는 이유**를 귀납적으로 봅시다.

- **기저**: 빈 트리에서는 모든 `indices`가 공집합이고, 이는 정의를 공허하게 만족합니다.
- **귀납 단계**: 접미사 $i$를 삽입하는 도중 노드 $v$를 방문할 때마다 $i$를 `indices(v)`에 더합니다(`insertSuffix` 진입 시 `node.indices.push(idx)`). $v$를 방문했다는 것은 접미사 $i$가 $P_v$를 접두사로 갖는다는 뜻이므로, 이 갱신은 정의와 정확히 일치합니다.
- **분할이 있는 경우**: 에지를 자를 때 경로 문자열 $P_v$ 자체는 바뀌지 않습니다 — `"anana"`가 `"ana"+"na"`로 나뉘어도 이어 붙이면 여전히 `"anana"`예요. 다만 자식(`"na"`)이 이제 새 분기점(`"ana"`) 아래 놓이므로, 분기점의 경로 문자열은 원래 자식의 경로 문자열보다 **짧은 접두사**가 됩니다. 그 짧은 접두사를 가진 접미사는 (a) 기존 자식으로 내려갔던 접미사들 전부(그들도 당연히 더 짧은 접두사를 갖습니다)와 (b) 지금 삽입 중인 새 접미사입니다. 그래서 `mid.indices = [...child.indices(분할 전), idx]`가 정확히 옳은 값이에요.

**여기서 헷갈리기 쉬운 포인트는 mid.indices를 `[idx]`로만 채워도 된다고 착각하는 것입니다.** "새로 만든 분기점이니 새 인덱스만 넣으면 되지 않나?"라고 생각하기 쉬운데, 분기점은 기존 자식의 새로운 조상이 된 것이지 기존 접미사들과 무관한 노드가 아닙니다. 실제로 이렇게 잘못 짜면 `findAll("ana")`가 `[1, 3]` 대신 `[3]`만 반환합니다 — 인덱스 1에서 시작하는 `"anana"` 접미사가 `"ana"`를 접두사로 갖는다는 사실이 통째로 누락되는 거예요. 코드 절에서 이 버그를 실제로 재현하고 고쳐 보겠습니다.

잠깐, 확인 하나만 해 볼까요? 위 최종 트리에서 `findAll("na")`를 부르면 어떤 인덱스가 나올까요? (힌트: 패턴 `"na"`는 루트에서 첫 글자 `'n'`을 따라갑니다.) — 정답은 `[2, 4]`입니다. `'a'` 쪽 자식 아래에도 `"na"`라는 레이블이 있지만, 그건 경로 문자열이 `"a"+"na"="ana"`인 별개의 노드예요. 패턴이 `'n'`으로 시작하니 루트에서 바로 오른쪽 `"na"`(경로 문자열 자체가 `"na"`, indices=`[2, 4]`) 노드로 가야 합니다. 레이블 문자열이 같아도 경로가 다르면 완전히 다른 노드라는 걸 확인하는 질문이었어요.

**두 번째로 헷갈리기 쉬운 포인트는 "가장 긴 반복 부분 문자열 = 자식이 2개 이상인 노드"라고 단정하는 것입니다.** 자식 수가 아니라 **`indices.length >= 2`**가 정확한 기준이에요. 예를 들어 $s = \text{"abbb"}$를 생각해 보면, 경로 문자열 `"bb"`에 해당하는 노드는 자식이 딱 1개뿐인데도(한쪽 접미사는 여기서 끝나고, 다른 한쪽만 더 이어짐) `"bb"`는 인덱스 1과 2에서 두 번 등장하는 진짜 반복 문자열입니다. 자식 수 기준으로 판정하면 이 경우를 통째로 놓칩니다 — 코드 절에서 실측으로 확인해 볼게요.

**세 번째로 헷갈리기 쉬운 포인트는 패턴이 에지 레이블의 정확히 끝에서 끝나야 존재로 인정된다고 생각하는 것입니다.** `search("ban")`을 `"banana"` 트리에서 실행하면, 루트의 `"banana"` 에지 중간(3글자)에서 패턴이 소진됩니다. 에지를 끝까지 다 타지 않았어도 **패턴이 그 에지의 접두사이기만 하면** 존재하는 겁니다. "에지 끝까지 다 못 갔으니 실패"라고 잘못 판단하면 `search("ban")`이 거짓으로 나오는데, 실제로는 `"ban"`이 `"banana"`의 부분 문자열이므로 참이어야 합니다.

엣지 케이스도 점검해 둡시다.

```text
|s| = 1 (예: "a")           → search("a")=true, findAll("a")=[0], LRS=""(반복 없음)
모든 문자가 같음 (예: "aaaa") → findAll("a")=[0,1,2,3], findAll("aa")=[0,1,2], LRS="aaa"
반복이 전혀 없음 (예: "abc")  → longestRepeatedSubstring()="" (indices.length>=2인 노드가 없음)
pattern = s 전체              → findAll(s) = [0] (접미사 중 딱 하나만 s 전체와 일치)
```

## 아이디어를 코드로 옮기기

먼저 삽입과 `findAll`을 원형대로 짜 보고, 실측으로 버그를 잡은 뒤 최종 코드로 갑니다.

**시도 1 (원형, 버그 있음)** — "분기점이니 새 인덱스만 담으면 된다"는 직관을 그대로 코드로 옮기면 이렇게 됩니다.

```ts
// 버그 버전: mid.indices를 새 idx로만 초기화 (child의 기존 indices를 물려받지 않음)
const mid: SuffixNode = {
  children: new Map(),
  label: child.label.slice(0, common),
  indices: [idx], // ← 여기가 문제
};
```

이 버전으로 `"banana"`를 구성하고 `findAll("ana")`를 부르면 실측 결과는 다음과 같습니다.

```text
buggy.findAll('ana').sort()  = [3]        ← 잘못된 결과
정상 버전.findAll('ana').sort() = [1, 3]   ← 올바른 결과
```

인덱스 1(`"anana"`가 시작하는 자리)이 통째로 빠졌어요. **관찰**: 분기점은 기존 자식의 새 조상이므로, 기존 자식이 이미 갖고 있던 `indices`를 그대로 물려받아야 합니다.

**최종 코드**입니다.

```ts
interface SuffixNode {
  children: Map<string, SuffixNode>;
  label: string;
  indices: number[];
}

function commonPrefixLength(a: string, b: string): number {
  const max = Math.min(a.length, b.length);
  let i = 0;
  while (i < max && a[i] === b[i]) i++;
  return i;
}

class SuffixTree {
  private root: SuffixNode;
  private s: string;

  constructor(s: string) {
    this.s = s;
    this.root = { children: new Map(), label: "", indices: [] };
    for (let i = 0; i < s.length; i++) {
      this.insertSuffix(this.root, s.slice(i), i);
    }
  }

  private insertSuffix(node: SuffixNode, remaining: string, idx: number): void {
    node.indices.push(idx); // 이 노드를 지나는 접미사 목록에 idx를 더한다
    if (remaining === "") return;

    const firstChar = remaining[0]!;
    const child = node.children.get(firstChar);

    if (child === undefined) {
      // 이 글자로 시작하는 에지가 없다 → 새 에지를 그대로 삽입
      node.children.set(firstChar, { children: new Map(), label: remaining, indices: [idx] });
      return;
    }

    const common = commonPrefixLength(child.label, remaining);

    if (common === child.label.length) {
      // 자식 에지를 완전히 소비했다 → 더 내려간다 (idx는 재귀 진입 시 자동으로 기록됨)
      this.insertSuffix(child, remaining.slice(common), idx);
      return;
    }

    // 에지 분할: 공통 접두사 지점에서 자른다
    const mid: SuffixNode = {
      children: new Map(),
      label: child.label.slice(0, common),
      indices: [...child.indices, idx], // 기존 자식의 접미사들 + 새 idx (합집합!)
    };
    child.label = child.label.slice(common);
    mid.children.set(child.label[0]!, child);

    const rest = remaining.slice(common);
    if (rest !== "") {
      mid.children.set(rest[0]!, { children: new Map(), label: rest, indices: [idx] });
    }
    node.children.set(firstChar, mid);
  }

  private findNode(pattern: string): SuffixNode | undefined {
    let node = this.root;
    let remaining = pattern;
    while (remaining.length > 0) {
      const child = node.children.get(remaining[0]!);
      if (child === undefined) return undefined;
      const common = commonPrefixLength(child.label, remaining);
      if (common === remaining.length) return child; // 에지 중간이든 끝이든, 패턴이 소진되면 존재
      if (common < child.label.length) return undefined; // 에지 끝까지 못 감 = 불일치
      remaining = remaining.slice(common);
      node = child;
    }
    return node;
  }

  search(pattern: string): boolean {
    if (pattern === "") return true;
    return this.findNode(pattern) !== undefined;
  }

  findAll(pattern: string): number[] {
    if (pattern === "") return this.root.indices.slice();
    const node = this.findNode(pattern);
    return node ? node.indices.slice() : [];
  }

  longestRepeatedSubstring(): string {
    let best = "";
    const dfs = (node: SuffixNode, path: string) => {
      if (node !== this.root && node.indices.length >= 2 && path.length > best.length) {
        best = path; // indices.length >= 2 = 이 경로 문자열이 실제로 두 번 이상 등장한다
      }
      for (const child of node.children.values()) {
        dfs(child, path + child.label);
      }
    };
    dfs(this.root, "");
    return best;
  }
}
```

`longestRepeatedSubstring`도 같은 방식으로 검증했습니다. $s = \text{"abbb"}$에서 "자식 수 $\ge 2$" 기준과 "`indices.length` $\ge 2$" 기준을 나란히 실행하면:

```text
s="abbb": children.size>=2 기준 = ""    ← "bb" 노드의 자식이 1개뿐이라 놓친다
          indices.length>=2 기준 = "bb"  ← 올바른 답 (브루트포스로도 "bb" 확인됨)
```

가장 중요한 부분은 두 곳입니다.

- **`mid.indices: [...child.indices, idx]`** — 분할 시 기존 접미사 목록을 물려받는 이 한 줄이 없으면 `findAll`이 결과를 빠뜨립니다.
- **`node.indices.length >= 2` (LRS 판정)** — `children.size` 대신 `indices.length`를 써야, "한쪽은 여기서 끝나고 다른 쪽은 계속되는" 경우도 반복으로 잡아냅니다.
- **`findNode`의 `common === remaining.length` 조기 반환** — 에지 끝까지 다 가지 않아도 패턴이 소진되면 존재로 인정해야 합니다. 순서를 바꿔 `common === child.label.length`를 먼저 검사하면 `search("ban")`처럼 에지 중간에서 끝나는 패턴이 거짓으로 잘못 판정됩니다.

> 에지를 자르면 발자국(indices)도 그대로 상속해야 한다 — 안 그러면 발자국을 잃어버린다.
