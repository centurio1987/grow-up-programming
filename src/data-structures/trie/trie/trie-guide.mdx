# Trie — 접두사를 공유하는 문자열은 같은 길을 걷는다

## 한눈에 보는 컨셉

문자열 하나하나를 통째로 저장하는 대신, **문자 하나하나를 트리의 간선**으로 바꿔 저장하는 자료구조예요. 공통 접두사를 가진 단어들은 뿌리에서부터 같은 경로를 함께 걷다가 서로 다른 지점에서 갈라지기 때문에, 접두사 하나만 훑으면 그 아래 매달린 모든 단어에 한 번에 도달할 수 있습니다. 자동완성·사전·라우팅 테이블처럼 "접두사로 무리 지어 찾는" 질의에서 해시셋보다 근본적으로 유리한 이유가 여기 있어요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 Trie를 떠올려 보세요.

- 검색어를 입력할 때마다 "이 문자열로 **시작하는** 것들"을 몽땅 꺼내야 한다 (자동완성, IDE 코드 제안)
- 단어 집합에 대해 접두사 존재 여부(`startsWith`)를 반복적으로 물어봐야 한다
- 데이터가 계속 삽입·삭제되는 와중에도 위 질의들을 빠르게 유지해야 한다
- 저장할 문자열들이 서로 접두사를 많이 공유한다 (사전 단어, IP 프리픽스, 파일 경로)

해시셋과 비교하면 비용 차이가 분명해집니다.

```text
집합을 해시셋으로 저장하면:
  search(word)             O(len)          ← 괜찮음
  startsWith(prefix)       O(N × len)      ← 전체 단어를 다 순회해야 함
  wordsWithPrefix(prefix)  O(N × len)      ← 마찬가지, 접두사만으로는 좁혀지지 않음

Trie로 저장하면:
  search(word)             O(len)
  startsWith(prefix)       O(len)          ← 경로만 확인하면 끝
  wordsWithPrefix(prefix)  O(len + k)      ← 접두사 노드에서 DFS, k = 결과 글자 수 합
```

해시셋은 문자열을 "덩어리"로 취급해 서로의 관계를 모릅니다. 그래서 접두사 질의가 들어오면 전체를 훑는 수밖에 없어요. Trie는 공유되는 접두사를 아예 하나의 경로로 합쳐 놓기 때문에, 접두사 노드에 도착하는 순간 그 서브트리 전체가 곧 답의 후보군이 됩니다.

비슷한 목적의 자료구조로 RadixTree(경로 압축 트라이)가 있어요. 문자 집합이 작고(알파벳 소문자 26개 등) 단어들이 접두사를 많이 공유하면 일반 Trie가 단순하고 충분하고, 문자 집합이 크거나(유니코드) 공유가 드물어 한 글자짜리 체인 노드가 메모리를 낭비하면 RadixTree가 유리합니다.

### 문제 사례와 적용 예시

- **자동완성**: 구글 검색창이나 IDE 코드 제안기는 입력된 접두사 노드까지 내려간 뒤 그 서브트리를 DFS로 훑어 후보를 제시합니다.
- **사전·맞춤법 검사기**: `search`로 정확한 단어의 존재를 확인하고, 인접한 경로를 탐색해 오타 후보를 제안합니다.
- **IP 라우팅 테이블(최장 접두사 매칭)**: 이진 문자열(0/1)을 경로로 하는 Trie에 라우팅 규칙을 저장하고, 목적지 주소가 내려가다 멈추는 가장 깊은 지점을 "최장 일치 규칙"으로 씁니다.
- **코딩 테스트 맥락**: "여러 단어를 미리 넣어두고 수많은 접두사 질의에 빠르게 답하라"(자동완성 구현, Word Search 계열) 유형에서 전형적으로 요구되는 자료구조입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드는 자식 맵과 종료 플래그만 가진 단순한 구조예요.

```ts
interface TrieNode {
  children: Map<string, TrieNode>;  // 다음 문자 → 다음 노드
  isEnd: boolean;                    // 루트에서 이 노드까지의 경로가 완결된 단어인가
}
```

Trie 클래스 전체로는 `root: TrieNode`와 저장된 단어 수를 세는 `count: number`를 유지합니다.

노드 $v$까지 루트에서 이어진 간선 라벨을 이어붙인 문자열을 $s(v)$라 하고, 현재 트라이에 저장된 단어 집합을 $W$라 하면, 지켜야 할 불변식은 세 가지입니다.

1. $\forall v,\ \text{isEnd}(v) = \text{true} \iff s(v) \in W$ — isEnd는 오직 "완결된 단어"만을 가리킵니다.
2. $\text{count} = |W| = |\{v : \text{isEnd}(v) = \text{true}\}|$ — count는 isEnd 노드 수와 항상 같습니다.
3. 노드 $v$가 존재 $\iff$ $s(v)$가 $W$의 어느 한 단어의 접두사(자기 자신 포함)다 — 즉 "아무도 참조하지 않는 죽은 노드"가 트리 안에 남아 있지 않습니다.

`cat`, `car`, `card`를 순서대로 넣은 트라이는 이렇게 생겼습니다.

```text
루트(빈 문자열)
 └─ c
     └─ a
         ├─ t (isEnd=true)     ← "cat"
         └─ r (isEnd=true)     ← "car"
             └─ d (isEnd=true) ← "card"
```

`r` 노드는 `isEnd=true`이면서 동시에 자식 `d`를 가지고 있어요 — "car"라는 완결된 단어이면서, 동시에 "card"로 가는 경로의 일부이기도 한 겁니다.

**액션(연산)** — 이 자료구조가 제공하는 연산 전부입니다($m$ = 대상 단어/접두사 길이, $k$ = 결과로 나온 단어들의 글자 수 총합).

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(word)` | 경로를 없으면 생성, 있으면 재사용하며 내려가 끝 노드의 `isEnd=true`. 중복이면 무시 | $O(m)$ |
| `search(word)` | 경로가 끝까지 존재하고 끝 노드의 `isEnd`가 true인지 확인 | $O(m)$ |
| `startsWith(prefix)` | 경로 존재 여부만 확인 (`isEnd` 무관) | $O(m)$ |
| `delete(word)` | 끝 노드의 `isEnd=false` 처리 + 불필요해진 노드를 bottom-up으로 정리(pruning) | $O(m)$ |
| `wordsWithPrefix(prefix)` | 접두사 노드까지 내려가 그 서브트리를 DFS로 훑어 `isEnd` 노드 전부 수집 | $O(m+k)$ |
| `size()` | `count` 반환 | $O(1)$ |

핵심 연산 두 개를 Before/After로 자세히 봅니다.

**① insert — 공유되는 부분은 그대로 두고 새 부분만 만든다.** `cat`, `car`가 이미 들어있는 트라이(단어 수 2개)에 `card`를 삽입하면:

```text
Before (insert 전, count=2):        After insert("card") (count=3):
ROOT─c─a─t(END)                     ROOT─c─a─t(END)
          └─r(END)                            └─r(END)─d(END)
                                     c, a, r 노드는 재사용(공유). d만 신규 생성 + isEnd=true.
```

**② delete — 끝부터 지우고, 지워도 되는지는 아래에서 위로 물어본다.** 위 상태(`cat`, `car`, `card`, count=3)에서 `delete("car")`를 실행하면:

```text
Before (delete 전, count=3):        After delete("car") (count=2):
ROOT─c─a─t(END)                     ROOT─c─a─t(END)
          └─r(END)─d(END)                     └─r─d(END)   ← r는 남지만 isEnd=false
```

`r` 노드는 `isEnd`가 false가 됐지만 자식 `d`가 남아 있으므로(`children.size !== 0`) 노드 자체는 삭제되지 않습니다. 그 결과 `search("car")`는 false가 되지만 `startsWith("car")`는 여전히 true예요 — "card"가 그 경로를 계속 붙잡고 있기 때문입니다.

### 왜 모순 없이 작동하는가

불변식이 모든 연산을 거치며 유지되는지 귀납적으로 확인해 봅시다.

- **기저**: 빈 트라이는 루트 하나뿐이고 $W = \emptyset$입니다. 루트의 `isEnd`는 초기값 false이고 $s(\text{root}) = ""$는 $W$에 없으니 불변식 1이 성립합니다.
- **insert 단계**: 경로에 없는 노드만 새로 만들고, 있는 노드는 재사용합니다. 새로 만든 노드들은 다른 어떤 단어와도 무관하므로 불변식 3을 해치지 않고, 끝 노드의 `isEnd`만 true로 바뀌므로 $W' = W \cup \{\text{word}\}$에 대해 불변식 1이 그대로 성립합니다. `isEnd`가 이미 true였다면(중복) 아무것도 바꾸지 않으니 자명하게 유지됩니다.
- **delete 단계**: 끝 노드의 `isEnd`를 false로 바꿔 $W' = W \setminus \{\text{word}\}$를 반영합니다. 이후 pruning은 "`isEnd=false`이고 자식이 없는" 노드, 즉 어떤 단어의 경로도 더 이상 거치지 않는 노드만 부모의 `children`에서 제거합니다. 이 조건을 만족하는 노드는 정의상 $W'$의 어느 단어의 접두사도 아니므로, 지워도 불변식 3이 계속 성립합니다. 재귀가 자식 쪽부터 판정 결과를 부모로 전달하기 때문에(bottom-up), 부모는 항상 "자식을 지운 뒤"의 최신 상태를 보고 자신의 pruning 여부를 결정합니다.

**여기서 헷갈리기 쉬운 포인트**를 세 가지 짚어 둘게요.

- **"리프여야 단어의 끝이다"라는 착각.** 위 그림에서 `r` 노드는 자식 `d`를 가지고 있으면서도 `isEnd=true`입니다. 만약 `search`를 "경로 끝에 도달했고 **자식이 없어야** 참"이라고 잘못 구현하면, `cat/car/card`가 모두 들어있는 트라이에서 실제로는 true여야 할 `search("car")`가 **false를 반환**하는 구체적인 오류가 생깁니다. 단어의 끝은 오직 `isEnd` 플래그로만 판정해야 해요.
- **delete의 pruning을 top-down으로 처리하는 착각.** 자식 쪽 재귀 결과를 받기 전에 부모가 먼저 `children.delete(ch)`를 실행해 버리면, 그 아래에 살아있는 다른 단어까지 통째로 날아갑니다. 예컨대 `cat/car/card`(count=3)에서 `delete("car")`를 top-down으로 짜서 `a` 노드가 곧장 `r` 자식을 지워 버리면, `"card"`까지 함께 사라져 count가 3에서 2가 아니라 **1로 잘못 줄어듭니다**. 반드시 자식의 재귀 결과(지워도 되는지)를 먼저 받아 부모가 판단해야 합니다.
- **"경로가 존재한다"와 "그 단어가 존재한다"를 혼동하는 착각.** `"ca"`만 들어있고 `"car"`는 없는 트라이에서, `delete("car")`가 경로 탐색만 성공하면 곧바로 true를 반환하도록 짜면 실제로 지운 것이 없는데도 성공을 보고하는 오류가 생깁니다. 뒤에서 볼 구현은 `delete` 진입 시 `search(word)`로 "정말 그 단어가 있는지"부터 확인해 이 문제를 원천 차단합니다.

확인 하나 해 볼까요? `apple`, `application`, `apt`, `banana`가 모두 들어있는 트라이에서 `delete("apple")`을 실행하면, 이후 `startsWith("appl")`은 true일까요, false일까요? — 답은 **true**입니다. `apple`과 `application`은 `"appl"`까지 경로를 공유하는데, `apple`을 지워도 `application`이 살아있어서 그 경로가 여전히 유효하기 때문이에요.

엣지 케이스를 점검해 봅니다.

```text
빈 트라이: search('x') → false, startsWith('x') → false, wordsWithPrefix('x') → []
빈 문자열 자체를 insert(''): 루트의 isEnd만 true가 됨 → search('') → true, size() → 1
  (참고: 이때도 startsWith('')는 항상 true — 루트 자체가 빈 문자열의 접두사이므로 트라이가 비어 있어도 성립)
중복 insert(같은 단어 두 번): count 불변 (isEnd가 이미 true라 두 번째 삽입은 무시됨)
delete 후 pruning: 형제/자식 경로가 살아있으면 노드는 isEnd만 false로 남고,
                    완전히 고립되면(자식 없고 isEnd false) 노드까지 위로 연쇄 삭제됨
```

## 아이디어를 코드로 옮기기

인터페이스는 문제가 요구하는 6개 연산 그대로 사용합니다. 노드는 클래스 대신 가벼운 인터페이스 + 팩토리 함수로 만들어 생성 비용을 낮췄어요.

```ts
interface TrieNode {
  children: Map<string, TrieNode>;
  isEnd: boolean;
}

function createNode(): TrieNode {
  return { children: new Map(), isEnd: false };
}

class Trie {
  private root: TrieNode = createNode();
  private count = 0;

  insert(word: string): void {
    let node = this.root;
    for (const ch of word) {
      let next = node.children.get(ch);
      if (!next) {
        next = createNode();
        node.children.set(ch, next);
      }
      node = next;
    }
    if (!node.isEnd) {
      node.isEnd = true;
      this.count++;
    }
  }

  private traverse(prefix: string): TrieNode | undefined {
    let node = this.root;
    for (const ch of prefix) {
      const next = node.children.get(ch);
      if (!next) return undefined;
      node = next;
    }
    return node;
  }

  search(word: string): boolean {
    const node = this.traverse(word);
    return node !== undefined && node.isEnd;
  }

  startsWith(prefix: string): boolean {
    return this.traverse(prefix) !== undefined;
  }

  delete(word: string): boolean {
    if (!this.search(word)) return false; // 존재 확인을 성공 신호로 분리
    this.deleteHelper(this.root, word, 0); // 반환값은 pruning 신호일 뿐, 성공 여부가 아니다
    this.count--;
    return true;
  }

  private deleteHelper(node: TrieNode, word: string, depth: number): boolean {
    if (depth === word.length) {
      node.isEnd = false; // 존재는 이미 search로 확인했으니 바로 끈다
      return node.children.size === 0;
    }
    const ch = word[depth]!;
    const child = node.children.get(ch);
    if (!child) return false;
    const shouldDeleteChild = this.deleteHelper(child, word, depth + 1); // 자식부터 재귀 (bottom-up)
    if (shouldDeleteChild) {
      node.children.delete(ch);
      return !node.isEnd && node.children.size === 0;
    }
    return false;
  }

  wordsWithPrefix(prefix: string): string[] {
    const node = this.traverse(prefix);
    if (!node) return [];
    const results: string[] = [];
    this.dfs(node, prefix, results);
    return results.sort(); // Map 삽입 순서는 사전순이 아니므로 마지막에 정렬
  }

  private dfs(node: TrieNode, current: string, results: string[]): void {
    if (node.isEnd) results.push(current);
    for (const [ch, child] of node.children) {
      this.dfs(child, current + ch, results);
    }
  }

  size(): number {
    return this.count;
  }
}
```

**가장 중요한 부분은 `delete`가 "존재 확인"과 "구조 정리"를 분리한 것입니다.**

```ts
if (!this.search(word)) return false;
this.deleteHelper(this.root, word, 0);
this.count--;
return true;
```

`deleteHelper`의 반환값은 어디까지나 "부모가 나를 지워도 되는가"라는 pruning 신호일 뿐, "삭제가 성공했는가"라는 의미가 아니에요. 이 둘을 같은 값으로 취급하면, 경로만 있고 단어는 없는 상황(`"ca"`는 있지만 `"car"`는 없는 경우)에서 잘못된 성공을 보고하는 버그로 이어집니다.

놓치기 쉬운 지점을 더 짚어 둡니다.

- **`if (!node.isEnd) { node.isEnd = true; this.count++; }` 이 조건문.** 조건 없이 매번 `count++`를 하면, 같은 단어를 두 번 삽입했을 때 count가 1이 아니라 2로 잘못 올라갑니다. 조건이 있어야 중복 삽입이 무시됩니다.
- **`deleteHelper`가 자식을 먼저 재귀 호출한 뒤 그 결과로 자신을 판단하는 순서.** 순서를 바꿔 부모가 먼저 지워 버리면 위에서 본 대로 살아있는 다른 단어까지 함께 사라집니다.
- **`wordsWithPrefix`의 `results.sort()`.** `Map`은 삽입 순서를 유지할 뿐 사전순을 보장하지 않으므로, DFS만으로는 결과 순서가 뒤죽박죽일 수 있어요. 마지막에 정렬해야 사전순이 보장됩니다.

기억법: "지우기 전에 있는지부터 확인하고, 지운 다음엔 자식부터 위로 청소한다."
