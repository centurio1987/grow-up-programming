# TernarySearchTree — 좌우는 제자리 걸음, 가운데만 다음 글자로

## 한눈에 보는 컨셉

트라이(Trie)의 각 노드가 알파벳 크기만큼의 자식 배열을 통째로 들고 있는 대신, 문자 하나만 들고 왼쪽·가운데·오른쪽 세 자식만 갖도록 재구성한 자료구조예요. 같은 문자 위치에 있는 형제 문자들은 이진 탐색 트리(BST)처럼 좌우로 비교하며 찾다가, "같다"고 판정되는 순간에만 가운데 자식으로 내려가 다음 문자로 넘어갑니다. 그 결과 저장 공간은 총 문자 수에 비례하면서도, 삽입·탐색·접두사 질의는 모두 단어 길이에 비례한 시간에 끝나요.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 TernarySearchTree(TST)를 떠올리세요.

- "단어가 있는지"뿐 아니라 "이 접두사로 시작하는 단어를 전부 나열하라"는 요구가 있다
- 저장할 문자열이 수십만 개 단위로 많은데, 메모리가 빠듯하다(문자 집합이 크거나 희소하게 갈라진다)
- 사전 순으로 정렬된 순회(자동완성 후보 정렬 등)도 필요하다

naive 대안들과 비교하면 TST가 왜 필요한지 체감이 됩니다. $n$을 단어 수, $m$을 단어 길이, $\sigma$를 알파벳 크기(소문자 알파벳이면 26)라 할게요.

```text
배열 + 선형 탐색          O(n·m)              단어마다 매번 전체를 다시 비교
정렬 배열 + 이진 탐색      O(m·log n)          접두사 나열은 결과를 위한 별도 스캔이 필요
해시맵(Set/Map)           O(m)                조회는 빠르지만 접두사 질의 자체가 불가능
일반 Trie                 O(m)                노드마다 O(σ) 배열 — 문자열이 희소하면 메모리 낭비
TernarySearchTree(TST)    O(m·log σ) 평균      노드마다 포인터 3개(O(1) 공간)뿐
                          O(m·σ) 최악(문자가 정렬 순서로만 삽입될 때)
```

TST의 시간복잡도가 "평균/최악"으로 나뉘는 이유는 뒤에서 다시 짚을게요. $\sigma$가 26 같은 상수인 한, 평균이든 최악이든 결국 $m$에 대한 선형 시간이라는 점은 변하지 않습니다.

비슷한 용도의 다른 자료구조와 선택 기준도 정리해 둡니다.

- **해시맵 vs TST**: 접두사 질의·정렬 순회가 전혀 필요 없다면 해시맵이 상수 계수가 작아 더 빠릅니다. "이 접두사로 시작하는 모든 단어" 같은 질의가 등장하는 순간부터 해시맵은 후보가 될 수 없고 TST(또는 일반 Trie)로 넘어가야 해요.
- **일반 Trie vs TST**: 알파벳이 아주 작고(예: DNA 서열의 4염기) 저장된 문자열들이 촘촘하게 겹친다면 일반 Trie의 배열 인덱싱이 상수 시간이라 오히려 더 빠릅니다. 알파벳이 크거나(영소문자 26개, 유니코드) 문자열들이 희소하게 갈라진다면 TST가 메모리에서 뚜렷하게 유리해요.

### 문제 사례와 적용 예시

- **철자 검사기**: GNU Aspell, ispell 같은 도구가 대형 사전을 TST로 유지하며 "이 단어가 사전에 있는가"를 빠르게 확인합니다.
- **IDE 자동완성**: 사용자가 입력 중인 심볼 접두사로 시작하는 후보들을 사전 순으로 즉시 뽑아 보여줍니다.
- **URL 라우터의 세그먼트 매칭**: 경로를 문자 단위로 쪼개 트리로 관리하면 동적 라우트 매칭에도 응용할 수 있습니다.
- **코딩 테스트 맥락**: "단어 목록이 주어지고, 특정 접두사로 시작하는 단어를 모두 사전 순으로 출력하라" 같은 문제에서 직접 구현 대상이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드 하나는 문자 하나와 세 자식, 종료 표시만 가집니다.

```ts
class TSTNode {
  char: string;
  left: TSTNode | null = null;   // char보다 작은 문자
  mid: TSTNode | null = null;    // char와 같음 → 다음 문자로 진행
  right: TSTNode | null = null;  // char보다 큰 문자
  isEnd = false;                 // 이 노드에서 어떤 단어가 끝나는지
}

class TernarySearchTree {
  private root: TSTNode | null = null;
  private _size = 0;
  private emptyWordInserted = false; // 빈 문자열은 노드로 표현할 수 없어 별도 관리
}
```

지켜야 할 불변식은 네 가지예요.

1. **경로-인덱스 일치.** 노드 $n$에 처음 도달했을 때 아직 소비하지 않은 문자 인덱스를 $i(n)$이라 하면, 루트에서 $n$까지의 경로 중 지나온 **가운데(mid) 간선의 개수**가 정확히 $i(n)$과 같습니다. 왼쪽·오른쪽 이동은 인덱스를 전혀 소비하지 않기 때문이에요.
2. **수평 BST 순서.** 같은 부모를 공유하는 노드들 사이에서 $\forall x \in \mathrm{left}(n),\ x.\mathrm{char} < n.\mathrm{char}$이고 $\forall y \in \mathrm{right}(n),\ y.\mathrm{char} > n.\mathrm{char}$입니다.
3. **종료 표시의 의미.** $n.\mathrm{isEnd} = \mathrm{true}$인 노드 $n$에 대해, 루트에서 $n$까지 가는 동안 가운데 간선을 지날 때마다 지나온 노드의 `char`를 순서대로 이어붙인 문자열이 정확히 트리에 저장된 한 단어와 같습니다.
4. **빈 문자열의 특수성.** 빈 문자열은 트리의 어떤 노드에도 대응하지 않습니다(노드는 반드시 문자 하나를 가져야 하니까요). 존재 여부는 `emptyWordInserted` 플래그만으로 관리합니다.

`insert("cat")`, `insert("car")`, `insert("card")`, `insert("care")`, `insert("bat")`를 순서대로 넣으면 이런 모양이 됩니다.

```text
c                                   (root)
├─L→ b                              b < c → 왼쪽
│    └─M→ a                        b 확정, 다음 문자 a로
│         └─M→ t*                  a 확정, 다음 문자 t → "bat" 종료
├─M→ a                              c 확정, 다음 문자 a로
│    └─M→ t*                       a 확정, 다음 문자 t → "cat" 종료
│         └─L→ r*                  r < t → 왼쪽, "car" 종료
│              └─M→ d*             r 확정, 다음 문자 d → "card" 종료
│                   └─R→ e*        e > d → 오른쪽, "care" 종료
└─R→ (없음)                         c보다 큰 시작 문자는 없음
```

**액션(연산)** — 이 자료구조가 제공하는 6개 연산입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `insert(word)` | 문자별로 좌/우 비교 후 필요하면 노드를 새로 만들고, 같으면 가운데로 하강. 끝나면 `isEnd = true` | $O(m \log \sigma)$ 평균, $O(m\sigma)$ 최악 |
| `search(word)` | 같은 경로를 따라 내려가며 존재를 확인 | 위와 동일 |
| `startsWith(prefix)` | 접두사에 대응하는 노드가 있는지만 확인 | $O(p \log \sigma)$ ($p$ = 접두사 길이) |
| `delete(word)` | 대상 노드를 찾아 `isEnd`만 해제. 성공 여부를 반환 | $O(m \log \sigma)$ |
| `wordsWithPrefix(prefix)` | 접두사 끝 노드부터 DFS로 모든 `isEnd` 노드를 수집 | $O(p \log \sigma + k)$ ($k$ = 결과 총 문자 수) |
| `size()` | 저장된 단어 수 | $O(1)$ |

핵심 연산 두 개를 자세히 볼게요.

**① insert — 없으면 새 가지가 돋는다.** 위 트리에서 `bat`을 넣기 **전**에는 `root.left`가 비어 있었어요. 각 위치에서 다음 이동은 이렇게 결정됩니다.

$$
\mathrm{next}(node, i) =
\begin{cases}
(\mathrm{node.left},\ i) & w_i < node.\mathrm{char} \\
(\mathrm{node.right},\ i) & w_i > node.\mathrm{char} \\
(\mathrm{node.mid},\ i+1) & w_i = node.\mathrm{char}
\end{cases}
$$

```text
Before (bat 삽입 전):            After (insert("bat") 후):
c                                 c
└─M→ a─M→t*─L→r*─M→d*─R→e*        ├─L→ b─M→a─M→t*        ← 새로 돋은 가지
                                  └─M→ a─M→t*─L→r*─M→d*─R→e*
```

`b < c`이므로 `root.left`로 이동해야 하는데 자리가 비어 있었으니, 그 즉시 `b` 노드가 새로 생기고 그 밑으로 `a`, `t*`가 가운데 간선을 따라 이어집니다.

**② delete — 지우는 건 표시일 뿐, 가지는 남는다.** `delete("card")`를 실행하면 무슨 일이 일어날까요?

```text
Before (card 삭제 전):          After (delete("card") 후):
r*─M→ d*─R→ e*                  r*─M→ d(isEnd=false)─R→ e*
                                        ↑ 노드는 그대로 남는다 — "care"가 d.right = e를 필요로 하니까
```

`d.isEnd`만 `false`로 바뀌고 노드 자체는 사라지지 않습니다. 왜냐하면 `d`는 여전히 `care`가 지나가는 경로의 일부(`d.right = e`)이기 때문이에요. 만약 `d`를 통째로 지워버리면 `care`로 가는 길이 끊깁니다.

### 왜 모순 없이 작동하는가

**불변식 1(경로-인덱스 일치)이 항상 지켜지는 이유**: 빈 트리에서는 자명하게 성립합니다(경로가 없으니 소비할 인덱스도 없어요). `insert`/`search`가 왼쪽·오른쪽으로 이동할 때는 인덱스 `i`를 그대로 넘기고, 가운데로 이동할 때만 `i + 1`을 넘깁니다. 즉 매 호출이 이 불변식을 그대로 물려주므로, 어떤 깊이의 어떤 노드에서도 "가운데 간선 개수 = 소비한 문자 수"가 귀납적으로 유지됩니다.

**불변식 2(수평 BST 순서)가 항상 지켜지는 이유**: 새 노드는 `ch < node.char`거나 `ch > node.char`로 판정된 그 방향에만 생성되므로, 생성되는 순간부터 이미 순서가 맞습니다. 이후 삽입도 같은 규칙으로만 자식을 늘리므로 순서가 깨질 여지가 없습니다.

여기서 헷갈리기 쉬운 포인트 세 가지를 짚어 둘게요.

- **왼쪽·오른쪽 이동도 문자 하나를 처리한 거라고 착각하기 쉽습니다.** 하지만 왼쪽·오른쪽은 "이 노드가 담당하는 문자와 다르다"는 걸 확인했을 뿐, 아직 그 문자 위치를 통과하지 못한 상태예요. 실제로 인덱스를 증가시키는 버그를 내 보면 결과가 어떻게 망가지는지 뒤 "함정" 절에서 실측으로 보여드릴게요.
- **`isEnd = false`로 바뀐 노드가 무조건 트리에서 사라진다고 생각하기 쉽습니다.** 방금 본 것처럼 `card` 삭제 후에도 `d` 노드는 남아 있어요 — `care`가 그 경로를 공유하기 때문입니다. 삭제는 "이 지점에서 단어가 끝난다"는 표시만 지우고, 구조 정리(진짜 가지치기)는 이 가이드의 구현에서는 하지 않는 선택을 했습니다. 자식이 있는지 확인해 없을 때만 부모까지 거슬러 올라가며 지우는 로직을 추가할 수도 있지만, 구현 복잡도 대비 이득이 크지 않아 생략했어요(추가 메모리 비용은 안 쓰는 노드 몇 개뿐).
- **빈 문자열이 있는 트리와 완전히 빈 트리를 혼동하기 쉽습니다.** `insert("")`는 `root`를 전혀 건드리지 않고 `emptyWordInserted` 플래그만 켭니다. 그래서 `root === null`이면서 `size() === 1`인 상태가 있을 수 있어요 — "루트가 비었다 = 저장된 게 없다"는 직관이 이 경우에는 틀립니다.

확인 질문 하나 드릴게요. `startsWith("")`는 완전히 빈 트리와, 빈 문자열만 삽입된 트리에서 각각 어떤 값을 반환해야 할까요? — 정답은 각각 `false`, `true`입니다. "접두사가 빈 문자열"이라는 건 "저장된 단어가 하나라도 있는가"와 같은 질문이라서, `root`가 아니라 `size() > 0` 여부로 판단해야 두 경우 모두 올바르게 갈립니다.

엣지 케이스를 마저 점검합니다.

```text
빈 트리에서 search("a")           → false (root가 null이라 즉시 종료)
빈 트리에서 wordsWithPrefix("")   → []    (emptyWordInserted도 false)
길이 1짜리 단어("a")만 삽입        → 노드 1개, 그 자리에서 바로 isEnd = true
중복 삽입(같은 단어 두 번)         → size 불변(이미 isEnd인 노드는 다시 세지 않음)
존재하지 않는 단어 delete          → false 반환, size 불변
```

## 아이디어를 코드로 옮기기

가이드가 정의한 인터페이스(`TSTNode` + `TernarySearchTree`) 그대로 옮긴 구현입니다.

```ts
class TSTNode {
  char: string;
  left: TSTNode | null = null;
  mid: TSTNode | null = null;
  right: TSTNode | null = null;
  isEnd = false;

  constructor(char: string) {
    this.char = char;
  }
}

class TernarySearchTree {
  private root: TSTNode | null = null;
  private _size = 0;
  private emptyWordInserted = false;

  insert(word: string): void {
    if (word.length === 0) {
      if (!this.emptyWordInserted) {
        this.emptyWordInserted = true;
        this._size++;
      }
      return;
    }
    const existed = this.search(word); // 삽입 전에 먼저 확인 — 순서가 중요!
    this.root = this._insert(this.root, word, 0);
    if (!existed) this._size++;
  }

  private _insert(node: TSTNode | null, word: string, i: number): TSTNode {
    const ch = word[i]!;
    if (node === null) node = new TSTNode(ch);

    if (ch < node.char) {
      node.left = this._insert(node.left, word, i); // i 유지 — 자리 걸음
    } else if (ch > node.char) {
      node.right = this._insert(node.right, word, i); // i 유지 — 자리 걸음
    } else if (i === word.length - 1) {
      node.isEnd = true;
    } else {
      node.mid = this._insert(node.mid, word, i + 1); // i 증가 — 다음 문자로 전진
    }
    return node;
  }

  search(word: string): boolean {
    if (word.length === 0) return this.emptyWordInserted;
    return this._search(this.root, word, 0);
  }

  private _search(node: TSTNode | null, word: string, i: number): boolean {
    if (node === null) return false;
    const ch = word[i]!;
    if (ch < node.char) return this._search(node.left, word, i);
    if (ch > node.char) return this._search(node.right, word, i);
    if (i === word.length - 1) return node.isEnd;
    return this._search(node.mid, word, i + 1);
  }

  startsWith(prefix: string): boolean {
    if (prefix.length === 0) return this._size > 0;
    return this._getNode(this.root, prefix, 0) !== null;
  }

  private _getNode(node: TSTNode | null, word: string, i: number): TSTNode | null {
    if (node === null) return null;
    const ch = word[i]!;
    if (ch < node.char) return this._getNode(node.left, word, i);
    if (ch > node.char) return this._getNode(node.right, word, i);
    if (i === word.length - 1) return node;
    return this._getNode(node.mid, word, i + 1);
  }

  delete(word: string): boolean {
    if (word.length === 0) {
      if (!this.emptyWordInserted) return false;
      this.emptyWordInserted = false;
      this._size--;
      return true;
    }
    const node = this._getNode(this.root, word, 0);
    if (node === null || !node.isEnd) return false; // 존재하지 않으면 false
    node.isEnd = false; // 구조는 그대로, 표시만 해제
    this._size--;
    return true;
  }

  wordsWithPrefix(prefix: string): string[] {
    const result: string[] = [];
    if (prefix.length === 0) {
      if (this.emptyWordInserted) result.push("");
      this._collect(this.root, "", result);
      return result;
    }
    const node = this._getNode(this.root, prefix, 0);
    if (node === null) return result;
    if (node.isEnd) result.push(prefix);
    this._collect(node.mid, prefix, result); // 접두사 확정 지점부터는 mid만
    return result;
  }

  private _collect(node: TSTNode | null, current: string, result: string[]): void {
    if (node === null) return;
    this._collect(node.left, current, result);
    if (node.isEnd) result.push(current + node.char);
    this._collect(node.mid, current + node.char, result);
    this._collect(node.right, current, result);
  }

  size(): number {
    return this._size;
  }
}
```

가장 중요한 부분은 `_insert`의 세 갈래 분기입니다.

```ts
if (ch < node.char) {
  node.left = this._insert(node.left, word, i);   // i 그대로
} else if (ch > node.char) {
  node.right = this._insert(node.right, word, i);  // i 그대로
} else {
  ...
  node.mid = this._insert(node.mid, word, i + 1);  // i + 1
}
```

왼쪽·오른쪽 분기는 `i`를 그대로 넘기고, 같음이 확인된 가운데 분기만 `i + 1`을 넘긴다는 것 — 이 세 줄이 TST 전체의 정확성을 떠받칩니다.

여기서 실수가 잦은 지점을 구체적인 오답으로 보여드릴게요. 만약 왼쪽 분기에서 실수로 `this._insert(node.left, word, i + 1)`처럼 인덱스를 증가시켜 버리면 어떻게 될까요? `insert("cat")` 후 `insert("bat")`을 이 버그가 있는 채로 실행하면, `'b' < 'c'`라 왼쪽으로 가면서 인덱스가 실수로 1 증가해 `word[1] = 'a'`부터 노드를 만들기 시작합니다 — 첫 글자 `'b'`가 통째로 유실되는 거예요. 실제로 이 버그 버전을 그대로 돌려 확인해 보면:

```text
버그 버전: node.left = this._insert(node.left, word, i + 1)
insert("cat"); insert("bat");
search("bat") => false   ← 분명히 삽입했는데 사라졌다!
search("cat") => true
```

`search("bat")`이 `false`를 반환하는 이유는, 삽입 때 `'b'`를 건너뛰고 `'a'`부터 노드를 만들어 버렸기 때문에 탐색 시 `word[0] = 'b'`가 그 노드의 `char('a')`보다 크다고 판정되어 엉뚱하게 오른쪽 자식을 찾으러 가고, 거기엔 아무것도 없어서 실패하는 거예요. **왼쪽·오른쪽은 제자리 걸음, 가운데만 다음 글자로 전진한다** — 이 한 줄을 기억법으로 챙겨 두세요.

또 하나 놓치기 쉬운 지점은 `insert`에서 `existed = this.search(word)`를 **먼저** 호출하는 순서입니다. 이 검사를 삽입 뒤로 미루면, 삽입 과정에서 이미 `isEnd`가 `true`로 바뀐 뒤라 "원래 있었는지"를 더는 알 수 없어 중복 삽입에도 `size`가 계속 증가하는 버그가 생깁니다.

## 실행 시각화
