# Suffix Array — 접미사를 통째로 정렬해두면 이진 탐색이 열린다

## 한눈에 보는 컨셉

문자열의 모든 접미사를 만들어 사전순으로 정렬해 둔 인덱스 배열이에요. 비결은 딱 하나입니다 — "패턴 `p`가 어디서 등장하는가"라는 질문을, "`p`를 접두사로 가지는 접미사들은 정렬된 배열에서 어디에 몰려 있는가"라는 질문으로 바꿔치기하는 거예요. 한 번만 O(n² log n)에 정렬해 두면, 이후 패턴이 몇 개가 오든 각각 O(m log n)의 이진 탐색으로 처리할 수 있습니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 보이면 접미사 배열을 떠올리세요.

- 텍스트는 **한 번 고정**되고, 그 위에서 패턴 검색을 **여러 번, 반복적으로** 수행해야 한다
- "부분 문자열이 몇 번, 어디서 등장하는가" 외에도 "가장 긴 반복되는 부분 문자열은?" 같은 **구조적 질의**가 함께 필요하다
- 패턴 하나당 텍스트를 매번 처음부터 스캔하기엔 텍스트가 너무 길다(게놈 서열처럼 수억 자 단위)

naive 스캔과 비교하면 효과가 뚜렷합니다. 패턴 길이 m, 텍스트 길이 n, 패턴 개수 k라고 하면:

```text
naive 스캔 (패턴마다 텍스트 전체를 다시 훑음)
  패턴 1개:  O(n · m)
  패턴 k개:  O(k · n · m)          ← k가 커지면 감당 불가

접미사 배열 (텍스트를 딱 한 번 전처리)
  구성:        O(n² log n)         ← 딱 한 번만 지불하는 비용
  패턴 1개당:  O(m log n)
  패턴 k개:    O(n² log n) + O(k · m log n)   ← k가 커질수록 압도적으로 유리
```

비슷한 목적의 구조들과 헷갈릴 수 있어 선택 기준을 짚어 둘게요. **텍스트가 고정이고 패턴이 여러 번, 계속 바뀐다면 접미사 배열**을 씁니다. 반대로 **패턴 하나가 고정이고 텍스트 쪽이 매번 바뀐다면 KMP/Z-알고리즘**이 O(n+m)으로 더 가볍습니다. **여러 패턴을 사전 등록해두고 텍스트에서 한 번에 찾고 싶다면 Trie(Aho-Corasick)** 쪽이 적합해요 — 접미사 배열은 "부분 문자열 검색"에, Trie는 "접두사/사전 매칭"에 특화되어 있습니다.

### 문제 사례와 적용 예시

- **유전체 서열 분석(BLAST 등)**: 30억 염기쌍짜리 게놈을 한 번 색인해두고, 수천 개의 유전자 서열 패턴을 차례로 검색합니다.
- **표절 검사·중복 탐지**: 두 문서를 이어 붙인 뒤 "가장 긴 반복 부분 문자열"을 구하면 표절 의심 구간을 잡아낼 수 있습니다.
- **텍스트 편집기/검색 엔진의 고정 코퍼스 검색**: 문서 내용은 안 바뀌는데 사용자가 검색어를 계속 바꿔 입력하는 상황.
- **코딩 테스트 맥락**: "문자열 s에서 패턴이 몇 번 등장하는지, 쿼리마다 다른 패턴으로 여러 번 묻는다"는 유형의 표준 해법입니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** 은 단순합니다 — 원본 문자열과 정렬된 인덱스 배열, 딱 둘이에요.

```ts
class SuffixArray {
  private s: string;     // 원본 텍스트 (불변)
  private sa: number[];  // 정렬된 접미사의 "시작 인덱스" 배열, 길이 n
}
```

지켜야 할 불변식은 하나입니다.

$$
\forall\, 0 \le i < j < n,\quad s[\,SA[i]\,{:}\,] \;\prec\; s[\,SA[j]\,{:}\,]
$$

($s[k{:}]$는 인덱스 $k$부터 끝까지의 접미사, $\prec$는 사전식 순서)

`s = "banana"`로 그려보면 이렇습니다.

```text
접미사 생성 (원래 인덱스)        사전순 정렬 후                  SA 배열
  0: banana                      a         (원래 5)          SA = [5, 3, 1, 0, 4, 2]
  1: anana                       ana       (원래 3)                 │  │  │  │  │  │
  2: nana                        anana     (원래 1)                 │  │  │  │  │  └─ "nana"
  3: ana                         banana    (원래 0)                 │  │  │  │  └──── "na"
  4: na                          na        (원래 4)                 │  │  │  └─────── "banana"
  5: a                           nana      (원래 2)                 │  │  └────────── "anana"
                                                                     │  └───────────── "ana"
                                                                     └──────────────── "a"
```

여기서 헷갈리기 쉬운 포인트는 **SA에 저장되는 값이 "정렬 후 순위"가 아니라 "원래 문자열에서의 시작 인덱스"** 라는 점입니다. `SA[0] = 5`는 "정렬했더니 5등"이라는 뜻이 아니라 "사전순으로 가장 작은 접미사는 원래 인덱스 5에서 시작한다"는 뜻이에요.

**액션(연산)** 은 다섯 가지입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(s)` | 모든 접미사를 생성해 사전순 정렬 | $O(n^2 \log n)$ |
| `search(pattern)` | 이진 탐색으로 패턴이 시작하는 위치 전부 반환(정렬됨) | $O(m \log n)$ |
| `lcp(i, j)` | SA상의 $i$, $j$번째 접미사(정렬 순서 기준 인덱스) 사이 최장 공통 접두사 길이 | $O(m)$ |
| `longestRepeatedSubstring()` | 인접한 두 접미사의 lcp 최댓값에 해당하는 문자열 | $O(n^2)$ |
| `suffixes()` | 정렬된 접미사 문자열 배열(디버깅용) | $O(n)$ |

핵심 연산인 `search`를 자세히 볼게요. 전체 구간 `[0, n)`에서 시작해, "패턴보다 작은 접미사"와 "패턴 이상인 접미사"의 경계(lower bound), 그리고 "패턴 이하인 접미사"와 "패턴보다 큰 접미사"의 경계(upper bound)를 각각 이진 탐색으로 찾습니다. `search("ana")`를 실행하면 실제로 이렇게 좁혀집니다(SA = [5, 3, 1, 0, 4, 2]).

```text
Before: 전체 구간 탐색                     After: lower bound 확정
lo=0, hi=6                                  mid=3 → SA[3]=0 → s[0:3]="ban" > "ana" → hi=3
[5, 3, 1, 0, 4, 2]                          lo=0, hi=3
 ↑              ↑                           mid=1 → SA[1]=3 → s[3:6]="ana" == "ana" → hi=1
lo             hi                           lo=0, hi=1
                                             mid=0 → SA[0]=5 → s[5:8]="a" < "ana" → lo=1
                                             lo=1, hi=1 → 종료. lowerBound = 1

Before: lower bound 이후 이어서             After: upper bound 확정
lo=0, hi=6 (독립적으로 다시 탐색)            mid=3 → "ban" <= "ana"? 아니오 → hi=3
                                             mid=1 → "ana" <= "ana"? 예(같아도 포함!) → lo=2
                                             mid=2 → SA[2]=1 → s[1:4]="ana" <= "ana"? 예 → lo=3
                                             lo=3, hi=3 → 종료. upperBound = 3
```

그래서 `[lowerBound, upperBound) = [1, 3)`이고, `SA.slice(1, 3) = [3, 1]`을 오름차순 정렬하면 `[1, 3]`이 나옵니다. 이건 실제로 실행해서 확인한 값입니다: `search("ana")`는 정확히 `[1, 3]`을 반환해요.

### 왜 모순 없이 작동하는가

**정렬이 불변식을 만드는 이유**: 생성자에서 비교 함수가 "두 접미사를 문자 단위로 사전식 비교"하도록 정의되어 있고, 이 비교는 전순서(total order)입니다. 정렬 알고리즘은 전순서 아래에서 항상 배열을 그 순서대로 재배치하므로, 정렬이 끝난 직후 불변식은 자동으로 성립합니다. 이후 `sa` 배열은 다시 바뀌지 않으므로(구조가 불변) 불변식은 생성 이후 영원히 유지됩니다 — 삽입·삭제가 없는 정적 구조라는 점이 오히려 증명을 단순하게 만들어 줘요.

**이진 탐색이 항상 옳은 이유**: 배열이 정렬되어 있으므로 "패턴 `p`를 접두사로 가지는 접미사들"은 사전순으로 `p` 이상이고 `p`보다 "한 글자만 더 큰" 극한값 미만인 구간에 정확히 몰려 있습니다. lower bound는 "이 접미사 ≥ p"가 처음 참이 되는 위치를, upper bound는 "이 접미사 > p"가 처음 참이 되는 위치를 찾으므로, 그 사이 `[lowerBound, upperBound)`는 정확히 "p로 시작하는 접미사들의 구간"이 됩니다. 정렬된 배열에서 이런 경계는 항상 유일하게 존재하고, 이진 탐색은 그 경계를 놓치지 않고 찾아냅니다(각 단계마다 후보 구간이 절반으로 줄어들며 경계를 포함한 채로 수렴하기 때문입니다).

여기서 헷갈리기 쉬운 포인트가 두 가지 있습니다.

- **upper bound 조건에서 `<=`를 빠뜨리는 실수.** upper bound는 "패턴과 같은 것도 왼쪽에 포함"해야 하므로 비교 조건이 `suffix <= pattern`이어야 합니다. 만약 실수로 `suffix < pattern`으로 짜면(lower bound와 똑같은 조건), `search("ana")`에서 upperBound가 3이 아니라 **1**로 계산되어 `SA.slice(1, 1) = []`가 나옵니다 — 실제로 존재하는 인덱스 1의 매치(`"anana"`)를 통째로 빠뜨리는 겁니다. 직접 계산해 확인한 값이에요: 정상 upperBound는 3, `<`로 잘못 짠 버전은 1이 나옵니다.
- **빈 패턴의 취급을 정의해 두지 않으면 헷갈립니다.** 이 가이드에서는 "빈 문자열은 모든 위치의 접두사이므로 모든 인덱스가 매치"로 정의합니다. `search("")`는 `"banana"`에서 `[0, 1, 2, 3, 4, 5]`를 반환하도록 구현해요(정렬된 전체 인덱스).

확인 질문 하나 짚고 갈게요 — `"aaaa"`에서 `search("aa")`를 하면 결과가 몇 개일까요? 접미사들이 `"a", "aa", "aaa", "aaaa"`로 정렬되는데, 이 중 `"aa"`를 접두사로 가지는 건 `"aa"`(인덱스 2), `"aaa"`(인덱스 1), `"aaaa"`(인덱스 0) 세 개입니다. 겹치는 매칭도 모두 세므로 정답은 `[0, 1, 2]`예요 — 실제로 실행해도 정확히 이 값이 나옵니다.

엣지 케이스를 점검해 봅시다.

```text
빈 문자열("")                → suffixes() = [], search(아무 패턴) = []
길이 1 문자열("a")            → suffixes() = ["a"], search("") = [0], search("a") = [0]
반복 없는 문자열("abcde")     → longestRepeatedSubstring() = "" (인접 lcp가 전부 0)
전부 같은 문자("aaaa")        → longestRepeatedSubstring() = "aaa" (n-1 길이까지 반복)
lcp(i, i) (자기 자신)         → 그 접미사의 전체 길이 (예: suffixes()[0]="a"에 대해 lcp(0,0)=1)
```

## 아이디어를 코드로 옮기기

바로 이진 탐색 버전을 짜지 않고, 세 단계를 밟아 봅니다. 왜 접미사 배열 + 이진 탐색까지 가야 하는지 몸으로 느끼기 위해서예요.

**원형 — 매 패턴마다 텍스트 전체를 스캔**합니다. 가장 직관적이지만, 패턴이 바뀔 때마다 O(n·m)을 다시 지불해요.

```ts
function bruteForceSearch(s: string, pattern: string): number[] {
  const result: number[] = [];
  if (pattern.length === 0) return result;
  for (let i = 0; i + pattern.length <= s.length; i++) {
    if (s.slice(i, i + pattern.length) === pattern) result.push(i);
  }
  return result;
}
```

**개선 — 접미사를 미리 정렬해 두되, 아직 이진 탐색은 안 씀**. 정렬만 해둬도 "일치하는 것들이 이웃해 있다"는 사실을 알 수 있지만, 이 버전은 여전히 정렬된 배열 전체를 선형으로 훑습니다. 왜 다음 단계로 가야 할까요? 패턴이 많아지면 이 O(n) 선형 스캔이 다시 병목이 되기 때문입니다 — 정렬해 둔 구조의 이점(경계를 O(log n)에 찾을 수 있다는 것)을 아직 안 쓰고 있는 거예요.

```ts
function sortedLinearSearch(s: string, pattern: string): number[] {
  const n = s.length;
  const sa = Array.from({ length: n }, (_, i) => i);
  sa.sort((i, j) => {
    const a = s.slice(i);
    const b = s.slice(j);
    return a < b ? -1 : a > b ? 1 : 0;
  });
  const result: number[] = [];
  for (const idx of sa) {
    if (s.slice(idx, idx + pattern.length) === pattern) result.push(idx);
  }
  return result.sort((a, b) => a - b);
}
```

**최종 — 정렬된 접미사 배열 위에서 lower/upper bound 이진 탐색**. 정렬되어 있다는 사실을 실제로 활용해 O(m log n)까지 끌어내립니다.

```ts
class SuffixArray {
  private s: string;
  private sa: number[];

  constructor(s: string) {
    this.s = s;
    const n = s.length;
    this.sa = Array.from({ length: n }, (_, i) => i);
    this.sa.sort((i, j) => {
      const a = s.slice(i);
      const b = s.slice(j);
      return a < b ? -1 : a > b ? 1 : 0;
    });
  }

  private lowerBound(pattern: string): number {
    let lo = 0;
    let hi = this.sa.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      const suffix = this.s.slice(this.sa[mid], this.sa[mid] + pattern.length);
      if (suffix < pattern) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }

  private upperBound(pattern: string): number {
    let lo = 0;
    let hi = this.sa.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      const suffix = this.s.slice(this.sa[mid], this.sa[mid] + pattern.length);
      if (suffix <= pattern) lo = mid + 1;
      else hi = mid;
    }
    return lo;
  }

  search(pattern: string): number[] {
    if (this.s.length === 0) return [];
    if (pattern.length === 0) return [...this.sa].sort((a, b) => a - b);
    const lo = this.lowerBound(pattern);
    const hi = this.upperBound(pattern);
    return this.sa.slice(lo, hi).sort((a, b) => a - b);
  }

  lcp(i: number, j: number): number {
    const a = this.sa[i];
    const b = this.sa[j];
    let count = 0;
    while (a + count < this.s.length && b + count < this.s.length) {
      if (this.s[a + count] !== this.s[b + count]) break;
      count++;
    }
    return count;
  }

  longestRepeatedSubstring(): string {
    let best = "";
    for (let k = 0; k < this.sa.length - 1; k++) {
      const len = this.lcp(k, k + 1);
      if (len > best.length) {
        best = this.s.slice(this.sa[k], this.sa[k] + len);
      }
    }
    return best;
  }

  suffixes(): string[] {
    return this.sa.map((i) => this.s.slice(i));
  }
}
```

가장 중요한 부분은 `upperBound`의 비교 조건 `suffix <= pattern`입니다 — `lowerBound`와 딱 한 글자(`=`) 차이지만, 이 한 글자가 "패턴과 정확히 같은 접미사"를 왼쪽(포함)에 둘지 오른쪽(제외)에 둘지를 가릅니다. 놓치기 쉬운 지점을 몇 가지 더 짚을게요.

- **`s.slice(idx, idx + pattern.length)`로 패턴 길이만큼만 자릅니다.** 접미사 전체를 비교하면 느려질 뿐 아니라, `"ana"`와 `"anana"`처럼 한쪽이 다른 쪽의 진짜 접두사인 경우를 다르게 처리해야 해서 번거로워져요. 길이를 맞춰 자르면 이 문제가 자연히 사라집니다.
- **`longestRepeatedSubstring`은 인접한 쌍만 봅니다.** 정렬된 배열에서는 어떤 두 접미사의 공통 접두사도 그 사이에 있는 모든 접미사와 최소한 그만큼은 공통 접두사를 가지므로, 최댓값은 항상 "바로 옆" 쌍에서 나옵니다. 멀리 떨어진 쌍까지 다 비교할 필요가 없어요.
- **`lcp(i, j)`의 인자는 원본 문자열의 인덱스가 아니라 SA(정렬 순서) 상의 인덱스입니다.** `lcp(1, 2)`는 "원본에서 인덱스 1, 2 접미사"가 아니라 "정렬 후 1등, 2등 접미사"를 비교해요. 헷갈리면 `suffixes()[i]`, `suffixes()[j]`를 먼저 찍어보는 습관을 들이세요.

기억법 한 줄로 정리하면:

> lower는 "크거나 같으면 멈춤", upper는 "크면(only) 멈춤" — `<=` 하나가 upper의 전유물입니다.
