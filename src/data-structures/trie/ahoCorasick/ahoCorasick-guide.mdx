# 아호-코라식(Aho-Corasick) — 실패해도 되돌아가지 않는 다중 패턴 오토마톤

## 한눈에 보는 컨셉

여러 개의 패턴을 하나의 트라이(trie)에 합쳐 넣고, 매칭이 실패하는 순간 처음부터 다시 훑지 않고 **실패 링크(failure link)** 를 따라 "지금까지 읽은 텍스트의 접미사이면서 동시에 어떤 패턴의 접두사인 가장 긴 위치"로 곧장 점프하는 오토마톤이에요. KMP의 실패 함수를 트라이 전체로 확장한 것이라고 보면 됩니다. 그 결과 텍스트를 **딱 한 번만** 스캔하면서, 패턴이 몇 개든 $O(\text{텍스트 길이} + \text{매칭 수})$ 에 전부 찾아냅니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호들이 겹치면 아호-코라식을 떠올리세요.

- 찾아야 할 패턴이 **여러 개**(배열·집합으로 주어짐)이고, 텍스트는 **한 번만** 훑고 싶다
- 패턴 수가 늘어나도 검색 시간이 그만큼 늘어나면 곤란하다(스트리밍·실시간 필터링 맥락)
- "여러 단어가 텍스트 어디에 등장하는지 전부 구하라"는 요구가 명시적으로 나온다

패턴 하나를 KMP로 찾는 건 $O(n)$ 이지만, 그런 검색을 패턴 $k$개에 대해 반복하면 $k$배로 느려집니다. 아호-코라식은 $k$개의 패턴을 "구성 단계"에서 미리 하나의 오토마톤으로 합쳐 두기 때문에, 검색 단계에서는 패턴 수가 아예 등장하지 않습니다.

```text
패턴 k개, 평균 길이 m, 텍스트 길이 n, 총 매칭 수 z

패턴마다 KMP 반복       O(k · n)         패턴이 늘수록 텍스트를 그만큼 더 훑는다
아호-코라식 1회 스캔    O(n + z)         패턴 수는 "구성" 비용 O(Σm)에만 영향
```

비슷한 용도의 다른 구조와 헷갈릴 수 있는데, 기준은 간단합니다 — **패턴이 딱 1개**면 KMP나 Z-알고리즘으로 충분합니다(트라이 + BFS 구성 비용이 오히려 낭비예요). **패턴이 다수이고 텍스트는 한 번만** 본다면 아호-코라식입니다.

### 문제 사례와 적용 예시

- **안티바이러스 엔진**: 악성코드 시그니처 수만~수십만 개를 하나의 오토마톤으로 컴파일해 네트워크 패킷을 한 번만 스캔합니다.
- **네트워크 침입 탐지(IDS)**: Snort, 리눅스 커널의 `netfilter` 모듈이 다중 패턴 매칭에 이 알고리즘을 씁니다.
- **금칙어·스팸 필터**: 채팅 서비스에서 수천 개의 금칙어를 실시간으로 걸러낼 때.
- **코딩 테스트 맥락**: "문자열 배열이 주어질 때, 각 단어가 텍스트의 어느 위치들에서 등장하는지 전부 구하라" — 패턴 수가 많아 KMP 반복으로는 시간 제한을 넘기는 문제.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 노드 하나는 이렇게 생겼습니다.

```ts
interface ACNode {
  children: Map<string, ACNode>; // 문자 → 자식 노드 (트라이 간선)
  fail: ACNode | null;           // 실패 링크
  output: string[];              // 이 노드에서 "매칭 완료"로 확정되는 패턴들 (누적됨)
}
```

트라이의 각 노드 $v$가 나타내는 문자열(루트에서 $v$까지의 경로 문자열)을 $s(v)$라고 둘게요. 지켜야 할 불변식은 세 가지입니다.

1. **트라이 규칙**: `children`은 한 문자당 자식 노드가 최대 하나이고, 루트에서 임의의 노드까지의 경로 문자열은 반드시 어떤 패턴의 접두사입니다.
2. **실패 링크의 시작점**: 루트의 직계 자식(깊이 1)은 실패 링크가 항상 루트입니다 — 한 글자짜리 문자열의 "진접두사"는 빈 문자열뿐이고, 빈 문자열에 대응하는 노드가 루트니까요.
3. **핵심 불변식(실패 링크의 정의)**: 노드 $v$($v \ne \text{root}$)에 대해,

$$
f(v) = \text{node representing } \operatorname*{arg\,max}_{u \ne v,\ s(u)\ \text{is a proper suffix of}\ s(v),\ u \in \text{Trie}} |s(u)|
$$

즉 $f(v)$는 "$s(v)$의 진접미사(proper suffix)이면서 동시에 트라이 어딘가에 나타나는(=어떤 패턴의 접두사인) 문자열 중 가장 긴 것"에 대응하는 노드예요. 그리고 `output`은 실패 링크를 따라 누적됩니다.

$$
\text{output}(v) = \bigl(\{p : p\text{는 } v\text{에서 끝나는 패턴}\}\bigr) \cup \text{output}(f(v))
$$

패턴 `["he", "she", "his", "hers"]`로 트라이 + 실패 링크를 그려보면 이렇습니다(점선 화살표가 실패 링크, `*`는 패턴이 끝나는 노드).

```text
                         root
                    ┌──── h ────┐      ┌── s
                    │           │      │
                    e           i      h
                 ┌──┘           │      │
                 r              s*     e*  ·······┐
                 │             (his)  (she)       │
                 s*                    ·          │
               (hers)                  │ fail     │ fail
                                        ▼          ▼
                                    "s" 노드     "he" 노드

fail(h)=root   fail(s)=root   fail(he)=root   fail(hi)=root
fail(sh)=h     fail(her)=root
fail(his)=s   ← his의 진접미사 "is","s" 중 트라이에 있는 건 "s" 뿐!
fail(she)=he  ← she의 진접미사 "he","e" 중 트라이에 있는 건 "he"!
fail(hers)=s  ← hers의 진접미사 "ers","rs","s" 중 트라이에 있는 건 "s" 뿐!
```

**액션(연산)** — 이 자료구조가 제공하는 연산은 두 가지뿐입니다. 대신 `constructor`가 트라이·실패 링크·출력 링크를 한 번에 구성해 두기 때문에 `search`가 아주 가벼워져요.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(patterns)` | 패턴들을 트라이로 삽입 + BFS로 실패 링크·출력 링크 구성 | $O(\Sigma m)$ ($\Sigma m$ = 모든 패턴 길이 합) |
| `search(text)` | 텍스트를 한 번 스캔하며 모든 패턴의 등장 시작 인덱스를 수집 | $O(n + z)$ ($n$ = 텍스트 길이, $z$ = 총 매칭 수) |

핵심 연산 두 개를 자세히 볼게요.

**① 실패 링크 구성(BFS) — "얕은 데서 깊은 데로, 부모의 답을 재사용"**. 루트의 자식들부터 큐에 넣고, 얕은 노드부터 순서대로 처리합니다. 노드 $v$의 자식 $u$(문자 $c$로 연결)의 실패 링크를 구할 때는, **$v$의 실패 링크에서 시작해 $c$로 갈 수 있는 자리를 찾을 때까지** 실패 링크 체인을 타고 올라갑니다.

```text
Before: v.fail 은 이미 계산돼 있음(BFS라서 부모가 먼저 처리됨)
        u = v의 자식(문자 c)

cur = v.fail
cur가 c로 가는 자식을 가질 때까지 cur = cur.fail 반복 (root에서 멈춤)

After:  cur가 c로 가는 자식을 가지면 → u.fail = 그 자식
        못 찾고 root까지 왔으면    → u.fail = root
        u.output = u.output ∪ u.fail.output   ← 출력 링크 누적!
```

예를 들어 `his`의 실패 링크를 구하는 과정: `his`의 부모는 `hi`, `hi.fail = root`. `cur = root`에서 문자 `s`로 가는 자식이 있는지 보면 — 있습니다(`s` 패턴의 시작 노드, `she`로 이어지는 그 노드예요). 그래서 `fail(his) = "s" 노드`이지, **root가 아닙니다.**

**② search — "실패해도 되돌아가지 않는다"**. 텍스트를 한 글자씩 읽으며 현재 노드 `cur`를 갱신합니다.

```text
문자 ch 도착
cur가 ch로 가는 자식을 가질 때까지 cur = cur.fail 반복 (root에서 멈춤)
cur가 ch로 가는 자식을 가지면 cur = 그 자식
cur.output에 있는 모든 패턴을 결과에 기록 (시작 인덱스 = i - 패턴길이 + 1)
```

패턴 `["he","she","his","hers"]`, 텍스트 `"ahishers"`(인덱스 0~7: a h i s h e r s)로 실제 실행한 결과가 이렇습니다(직접 코드를 돌려 확인한 값이에요).

```text
i=0 'a'  cur=root                 (매칭 없음)
i=1 'h'  cur=h                    (매칭 없음)
i=2 'i'  cur=hi                   (매칭 없음)
i=3 's'  cur=his   output=["his"] → 시작 인덱스 3-3+1=1
i=4 'h'  실패 링크 1회 이동(his→s) 후 cur=sh   ← root로 돌아간 게 아니라 "s"를 거쳐 "sh"로!
i=5 'e'  cur=she   output=["she","he"] → she 시작 5-3+1=3, he 시작 5-2+1=4
i=6 'r'  실패 링크 1회 이동(she→he) 후 cur=her
i=7 's'  cur=hers  output=["hers"] → 시작 7-4+1=4
```

최종 결과: `he→[4], she→[3], his→[1], hers→[4]`.

### 왜 모순 없이 작동하는가

**실패 링크가 항상 옳은 이유(귀납)**: BFS는 얕은 노드부터 처리하므로, 노드 $u$의 실패 링크를 계산할 때 그 부모 $v$의 실패 링크는 **이미 정확하게** 계산돼 있습니다. $v.fail$에서 시작해 문자 $c$를 따라갈 수 있는 자리를 찾을 때까지 체인을 타고 올라가는 과정 자체가, "$s(u)$의 진접미사 중 트라이에 있는 가장 긴 것"을 정확히 찾는 절차예요(실패 링크 체인은 접미사 길이가 짧아지는 방향으로만 진행되고, 루트에서 반드시 멈추니 무한 루프도 없습니다). 그러므로 빈 트라이에서 시작해 BFS 순서로 모든 노드를 처리하면, 어느 시점에도 실패 링크 불변식이 깨지지 않습니다.

**헷갈리기 쉬운 포인트 하나** — "실패 링크는 항상 루트로 돌아간다"고 생각하기 쉽습니다. 위에서 봤듯 `his`의 실패 링크는 루트가 아니라 `"s"` 노드입니다. `his`의 진접미사는 `"is"`와 `"s"`인데, `"is"`는 어떤 패턴의 접두사도 아니지만 `"s"`는 `she`의 접두사라서 트라이에 존재하거든요. 이걸 놓치고 "실패하면 무조건 루트로 리셋"하도록 짜면, 정답은 맞아도(결과가 우연히 같을 수 있어서) 매 시작 위치를 사실상 다시 훑는 셈이 되어 시간복잡도가 무너집니다 — 구체적인 수치는 아래 코드 절에서 직접 확인해요.

**헷갈리기 쉬운 포인트 둘** — "output은 자기 노드에서 끝나는 패턴만 기록하면 충분하다"고 생각하기 쉽습니다. 위 트레이스의 `i=5`를 보세요: `cur=she` 노드에 도달했는데 `output=["she","he"]`로 **두 패턴이 동시에** 매칭 완료됩니다. `she`가 끝나는 순간 그 접미사인 `he`도 텍스트 어딘가에서 끝난 걸로 확정되기 때문이에요(`fail(she)=he`이고 `he` 노드가 패턴의 끝이니까). 이 출력 링크 누적을 빼먹으면 `he` 패턴은 영영 발견되지 않습니다 — 실제로 그 버그를 넣고 돌려보면 `he: []`가 나와요(정상은 `he: [4]`).

잠깐, 확인 하나만 해볼까요? 텍스트 `"ahishers"`에서 `i=5`(문자 `'e'`)에 도달했을 때 몇 개의 패턴이 동시에 매칭 완료될까요? — 정답은 **2개**(`she`, `he`)입니다. 위 트레이스의 `output=["she","he"]`가 그 증거예요.

엣지 케이스도 점검해 둡니다(모두 실제 실행으로 확인한 값입니다).

```text
빈 패턴 배열              → search는 빈 Map({}) 반환 (patterns가 없으니 키도 없음)
빈 텍스트                 → 모든 패턴이 키로 있고 값은 전부 []
중복 패턴 ["ab","ab","b"] → 하나로 합쳐져 {"ab":[...], "b":[...]} (중복 키 없음)
서로 접두사 관계 ["a","ab","abc"], text="xabcabx"
                          → a:[1,4], ab:[1,4], abc:[1]  (한 위치에서 여러 패턴이 동시 종료)
매칭이 전혀 없는 텍스트   → 모든 패턴 값이 []
```

## 아이디어를 코드로 옮기기

`constructor(patterns: string[])`와 `search(text: string): Map<string, number[]>` 인터페이스에 맞춰, 원형 → 개선 → 최종 3단계로 발전시켜 봅니다.

**원형(naive)**: 패턴마다 텍스트를 처음부터 슬라이딩 비교합니다.

```ts
function naiveMultiSearch(patterns: string[], text: string): Map<string, number[]> {
  const result = new Map<string, number[]>();
  for (const p of patterns) {
    const hits: number[] = [];
    for (let i = 0; i + p.length <= text.length; i++) {
      if (text.slice(i, i + p.length) === p) hits.push(i);
    }
    result.set(p, hits);
  }
  return result;
}
```

패턴이 $k$개면 텍스트를 $k$번 훑습니다 — $O(k \cdot n)$. 공통 접두사(`he`, `hers`가 `h`를 공유하는 것처럼)를 매번 따로 비교하는 것도 낭비예요. **왜 다음 단계로 가는가**: 공통 접두사를 트라이 하나로 묶으면 이 중복을 없앨 수 있습니다.

**개선(Trie만, 실패 링크 없음)**: 패턴들을 트라이로 합치되, 매칭이 실패하면 다음 시작 위치에서 루트부터 다시 훑습니다.

```ts
class TrieOnlyMatcher {
  private root: ACNode = { children: new Map(), fail: null, output: [] };
  private patterns: string[];

  constructor(patterns: string[]) {
    this.patterns = Array.from(new Set(patterns));
    for (const p of this.patterns) {
      let node = this.root;
      for (const ch of p) {
        if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), fail: null, output: [] });
        node = node.children.get(ch)!;
      }
      node.output.push(p);
    }
  }

  search(text: string): Map<string, number[]> {
    const result = new Map<string, number[]>();
    for (const p of this.patterns) result.set(p, []);
    for (let start = 0; start < text.length; start++) {
      let node = this.root;
      for (let i = start; i < text.length; i++) {
        const next = node.children.get(text[i]);
        if (!next) break;
        node = next;
        for (const p of node.output) result.get(p)!.push(i - p.length + 1);
      }
    }
    return result;
  }
}
```

정답은 맞습니다 — 하지만 텍스트의 매 시작 위치마다 루트에서 다시 내려가므로 최악의 경우 $O(n \cdot m)$ 입니다. 직접 재보면 차이가 확 드러나요: 패턴 `"a".repeat(49) + "b"`(길이 50), 텍스트 `"a".repeat(2000)`에 대해 문자 처리 횟수를 세어 보면 **실패 링크 있는 버전은 3,951회, 이 버전은 98,775회**입니다(약 25배). 텍스트에 `'b'`가 한 번도 안 나오니 매 시작 위치에서 49글자를 헛되이 훑고서야 포기하기 때문이에요. **왜 다음 단계로 가는가**: 매칭에 실패했을 때 "지금까지 읽은 것 중 재사용 가능한 접두사"를 버리지 않고 이어갈 방법이 필요합니다 — 그게 실패 링크입니다.

**최종(Aho-Corasick 오토마톤)**:

```ts
interface ACNode {
  children: Map<string, ACNode>;
  fail: ACNode | null;
  output: string[];
}

export class AhoCorasick {
  private root: ACNode = { children: new Map(), fail: null, output: [] };
  private patterns: string[];

  constructor(patterns: string[]) {
    this.patterns = Array.from(new Set(patterns));

    // 1단계: 트라이 구성 (goto 함수)
    for (const p of this.patterns) {
      let node = this.root;
      for (const ch of p) {
        if (!node.children.has(ch)) node.children.set(ch, { children: new Map(), fail: null, output: [] });
        node = node.children.get(ch)!;
      }
      node.output.push(p);
    }

    // 2단계: BFS로 실패 링크 + 출력 링크 구성
    const queue: ACNode[] = [];
    for (const child of this.root.children.values()) {
      child.fail = this.root;
      queue.push(child);
    }
    while (queue.length > 0) {
      const v = queue.shift()!;
      for (const [c, u] of v.children) {
        let cur = v.fail!;
        while (cur !== this.root && !cur.children.has(c)) {
          cur = cur.fail!;
        }
        if (cur.children.has(c) && cur.children.get(c) !== u) {
          u.fail = cur.children.get(c)!;
        } else {
          u.fail = this.root;
        }
        u.output = u.output.concat(u.fail.output); // 출력 링크 누적
        queue.push(u);
      }
    }
  }

  search(text: string): Map<string, number[]> {
    const result = new Map<string, number[]>();
    for (const p of this.patterns) result.set(p, []);

    let cur = this.root;
    for (let i = 0; i < text.length; i++) {
      const ch = text[i];
      while (cur !== this.root && !cur.children.has(ch)) {
        cur = cur.fail!; // 실패해도 되돌아가지 않는다 — root로 리셋이 아니라 체인을 탄다
      }
      if (cur.children.has(ch)) {
        cur = cur.children.get(ch)!;
      }
      for (const p of cur.output) {
        result.get(p)!.push(i - p.length + 1);
      }
    }
    return result;
  }
}
```

가장 중요한 부분은 `search`의 이 두 줄입니다.

```ts
while (cur !== this.root && !cur.children.has(ch)) {
  cur = cur.fail!;
}
```

여기가 "실패해도 되돌아가지 않는다"의 전부예요. `cur`가 `root`가 아닌 한 실패 링크를 타고 이동하지, 텍스트의 다음 시작 위치로 되돌아가는 게 아닙니다. 그리고 구성 단계의 `u.output = u.output.concat(u.fail.output)` 한 줄이 출력 링크 누적입니다 — 이 줄을 빼먹으면 위에서 본 것처럼 `he` 같은 패턴이 조용히 사라집니다.

> 실패 링크는 리셋 버튼이 아니라 단축키다.

`delete`나 다른 갱신 연산은 없습니다 — 아호-코라식은 패턴 집합이 고정된 뒤 텍스트를 검색하는 정적(static) 오토마톤이라, 구성이 끝나면 구조가 변하지 않습니다. (위 구현은 대표 예시·엣지 케이스·200회 무작위 교차검증까지 `naiveMultiSearch`와 결과가 전부 일치함을 실행으로 확인했습니다.)

정리하면, 아호-코라식은 두 가지 발상을 결합합니다. **트라이**로 모든 패턴의 공통 접두사를 공유하고, **실패 링크**로 KMP의 실패 함수를 트라이 전체에 확장해 "매칭 실패 시 되돌아가지 않고 이어가기"를 가능하게 합니다. 여기에 **출력 링크 누적**을 더해, 한 노드에서 여러 패턴이 동시에 끝나는 경우(`she`가 끝나면 `he`도 끝난다)까지 놓치지 않고 잡아냅니다. 그 결과 구성에 $O(\Sigma m)$, 검색에 $O(n+z)$ — 패턴 수 $k$가 검색 시간에 전혀 등장하지 않는다는, 애초에 노렸던 목표를 정확히 달성합니다.
