# Rolling Hash — 왼쪽을 밀어내고 오른쪽을 끌어들이기

## 한눈에 보는 컨셉

긴 텍스트 위에서 슬라이딩 윈도우를 한 칸 옮길 때마다 해시를 처음부터 다시 계산하지 않고, 왼쪽 끝 글자의 기여분만 빼고 오른쪽 끝 글자만 더해 `O(1)`에 새 해시를 얻는 기법이에요. 비결은 문자열을 `base`진법 다항식으로 보는 것입니다 — 윈도우 이동은 이 다항식에서 최고차항을 떼어내고 한 자리씩 밀어 올린 뒤 새 항을 더하는 산술 연산과 똑같아요. 이 원리 위에서 패턴과 윈도우의 해시가 다르면 문자열도 반드시 다르다는 사실을 이용하는 것이 **Rabin-Karp** 알고리즘이고, 평균 `O(n+m)`에 패턴 매칭을 끝냅니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 rolling hash를 떠올리세요.

- 긴 텍스트 안에서 패턴(또는 여러 패턴)의 **모든 등장 위치**를 찾아야 한다
- 부분 문자열들이 서로 같은지를 **반복적으로, 빠르게** 비교해야 한다(중복 부분 문자열 탐지, 최장 공통 부분 문자열)
- 윈도우가 한 칸씩 움직이는데, "윈도우 전체를 요약한 값"(여기서는 해시)을 매번 처음부터 다시 구하면 손해를 보는 구조다

naive 비교와 "해시는 쓰지만 매번 새로 계산"하는 절반 최적화, 그리고 rolling hash의 비용을 나란히 놓으면 차이가 뚜렷합니다.

```text
비교 방식                    윈도우 1개 처리      n-m+1개 윈도우 전체
문자열 직접 비교               O(m)               O(nm)
해시로 비교하되 매번 재계산     O(m)               O(nm)   ← 해시라고 공짜가 아니다!
rolling hash (O(1) 갱신)      O(1)               O(n + m) 평균
```

두 번째 줄이 헷갈리기 쉬운데요, "해시를 쓴다"는 것 자체가 빠름을 보장하지 않습니다. 매 윈도우마다 해시를 처음부터 `O(m)`에 계산하면 여전히 `O(nm)`이에요. **이전 해시에서 다음 해시를 O(1)에 유도하는 것**이 진짜 돌파구입니다.

비슷한 자리를 놓고 경쟁하는 **KMP**와는 선택 기준이 갈립니다 — worst case에서도 `O(n+m)`을 보장해야 하면 KMP, 구현이 짧고 다중 패턴·부분 문자열 비교로 확장하기 쉬운 쪽이 필요하면 rolling hash(단 해시 충돌 방지를 위한 검증이 필수)를 씁니다.

### 문제 사례와 적용 예시

- **표절 검사 시스템**: 대규모 코드 제출물 사이에서 복사된 구간을 찾을 때, 모든 부분 문자열을 rolling hash로 요약해 빠르게 비교합니다.
- **`git diff`, rsync 델타 동기화**: 파일의 어느 구간이 바뀌었는지 찾을 때 블록 해시를 굴려가며 비교합니다.
- **최장 중복 부분 문자열(LeetCode 1044 스타일)**: "길이 `L`짜리 중복 부분 문자열이 있는가?"를 이진 탐색으로 좁히고, 각 `L`에서 모든 부분 문자열의 해시를 집합에 넣어 `O(n)`에 판정합니다.
- **DNA 시퀀스 검색**: 짧은 유전 서열이 긴 시퀀스 안에 등장하는 위치를 찾는 생물정보학 도구.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — rolling hash는 노드를 두지 않고, 두 개의 파라미터만 유지합니다.

```ts
class RollingHash {
  private base: number;  // 다항식의 밑 (예: 31)
  private mod: number;   // 나머지 연산의 법 (예: 1_000_000_007)
}
```

문자열 `s[0..m-1]`의 해시는 `base`진법 다항식으로 정의됩니다.

$$
H(s) = \left( \sum_{k=0}^{m-1} s[k] \cdot \text{base}^{\,m-1-k} \right) \bmod \text{mod}
$$

이걸 Horner's rule로 풀어 쓰면 계산 순서가 보여요. `"cab"`을 예로 들면(문자는 `charCodeAt` 값):

```text
h = 0
h = h*base + code('c')   ← 최고차항이 먼저 자리를 잡고
h = h*base + code('a')   ← 한 자리씩 밀려 올라가고
h = h*base + code('b')   ← 마지막 글자가 1의 자리
```

지켜야 할 불변식은 세 가지입니다.

1. **범위 정규화.** `hash(s)`와 윈도우 해시 `winHash`는 항상 `[0, mod)` 범위의 정수입니다. 음수가 잠깐이라도 남으면 비교가 깨집니다(3.2절에서 구체 수치로 확인).
2. **정의와의 일치.** 롤링으로 갱신된 `winHash`는 항상 그 시점 윈도우 문자열을 처음부터 다항식 정의로 계산한 값과 같습니다. 이 불변식은 최초 1회 `O(m)` 계산으로 성립하고, 롤링 갱신이 매번 보존합니다(증명은 3.2절).
3. **`highPow` 고정.** `highPow = base^(m-1) mod p`는 패턴 길이 `m`이 정해지면 탐색이 끝날 때까지 **한 번만** 계산되고 재사용됩니다. 매 스텝 다시 구하면 `O(1)` 갱신이라는 이점이 사라져요.

**액션(연산)** — 이 자료구조가 제공하는 연산 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `constructor(base, mod)` | 다항식 해시 파라미터 초기화 | $O(1)$ |
| `hash(s)` | 문자열 전체의 다항식 해시를 처음부터 계산 (Horner's rule) | $O(m)$ |
| `search(text, pattern)` | 패턴이 등장하는 모든 시작 인덱스를 오름차순으로 반환 | $O(n+m)$ 평균, $O(nm)$ 최악 |

핵심 연산인 `search`의 윈도우 이동을 자세히 볼게요. `base=31, mod=1{,}000{,}000{,}007`로 실측한 값입니다. `text = "ababab"`, 윈도우 크기 `m=2`일 때 `hash("ab") = 3105`, `hash("ba") = 3135`입니다.

```text
Before: 윈도우 [a b]ab ab   winHash = hash("ab") = 3105
              i=0  i+m=2

  ① 왼쪽 끝 기여분 제거:  winHash - code('a')*highPow
  ② base만큼 자리 밀기:   (위 값) * base
  ③ 오른쪽 새 글자 추가:  (위 값) + code(text[i+m])

After:  a[b a]bab   winHash = hash("ba") = 3135
          i=1 i+m=3
```

`highPow = base^(m-1) = 31^1 = 31`이 이 갱신에서 "왼쪽 끝 글자가 다항식에서 몇 자리 밀려나 있는지"를 알려주는 값입니다.

### 왜 모순 없이 작동하는가

**갱신식이 정의와 일치하는 이유(귀납)**. 윈도우가 `s[i..i+m-1]`에서 `s[i+1..i+m]`으로 이동할 때, 정의를 그대로 전개하면:

$$
H(s[i{+}1..i{+}m]) = \big(H(s[i..i{+}m{-}1]) - s[i]\cdot \text{base}^{m-1}\big)\cdot \text{base} + s[i+m] \pmod{\text{mod}}
$$

왼쪽 항 `s[i]·base^(m-1)`은 옛 윈도우에서 최고차항(맨 왼쪽 글자)이 기여한 몫이라 그대로 빼면 나머지 `m-1`개 항만 남고, 여기에 `base`를 곱하면 각 항의 지수가 정확히 하나씩 올라가 새 윈도우에서의 자릿값과 일치합니다. 마지막으로 새로 들어온 글자 `s[i+m]`을 `base^0` 자리에 더하면 새 윈도우의 다항식 정의와 완전히 같아져요. 베이스 케이스(`i=0`)는 `hash()`로 직접 `O(m)` 계산해 정의와 일치시켜 두었으므로, 이후 모든 `i`에서 귀납적으로 정의와 일치합니다.

잠깐, 확인 하나만 해볼까요? `highPow`가 `base^(m-1)`이 아니라 `base^m`이면 어떻게 될까요? — 왼쪽 항의 지수가 하나 어긋나 엉뚱한 값을 빼게 되고, 이후 모든 윈도우 해시가 정의와 어긋나 버립니다. 지수를 `m-1`로 정확히 맞추는 것이 이 공식의 핵심이에요.

**여기서 헷갈리기 쉬운 포인트 세 가지**를 짚어 둡니다.

- **음수 모듈로 정규화를 빼먹기 쉽습니다.** JavaScript의 `%`는 피연산자가 음수면 음수를 돌려줍니다(`-5 % 3 === -2`). `winHash - s[i]*highPow`가 음수로 떨어지면, `+mod`를 해 주지 않은 채 다음 곱셈·비교로 넘어가는 순간 `winHash`가 `patHash`(항상 `[0, mod)` 범위)와 영원히 같아질 수 없는 값으로 굳어 버립니다. `m=2`처럼 `highPow`가 작을 땐 우연히 음수가 안 나서 버그가 숨어 있다가, `m`이 커져 `highPow`가 커지는 순간 터집니다 — 코드 절에서 실측 수치로 보여드릴게요.
- **해시가 같다고 문자열이 같다고 단정하면 안 됩니다.** `winHash == patHash`는 "다르면 확실히 다른 문자열"이라는 한쪽 방향만 보장합니다. 같을 때는 반드시 `text.slice(i, i+m) === pattern`으로 직접 비교해 충돌(다른 문자열인데 같은 해시)을 걸러내야 해요.
- **`highPow`는 패턴 길이당 한 번만 계산합니다.** 매 윈도우 이동마다 `base^(m-1)`을 다시 구하면 `O(m)` 루프가 매번 돌아 `O(1)` 갱신이라는 이점이 사라집니다. `search` 시작할 때 딱 한 번 구해서 재사용하세요.

엣지 케이스를 점검해 봅니다(실측 결과, 4단계에서 검증).

```text
빈 패턴(m=0)         → [] (반환 규약상 허용, 매칭 시도 자체를 하지 않음)
패턴이 텍스트보다 김(m>n) → []
패턴 길이 == 텍스트 길이  → text === pattern이면 [0], 아니면 []
텍스트·패턴 모두 빈 문자열 → []
전부 같은 문자('aaaa'에서 'aa') → 겹치는 위치 전부 등록 [0,1,2] (겹침을 막지 않는다)
```

## 아이디어를 코드로 옮기기

`RollingHash` 클래스는 `constructor(base, mod)`, `hash(s)`, `search(text, pattern)` 세 개의 연산을 제공합니다. 자연스러운 진화 단계를 코드로 밟아 볼게요.

**원형: 아무 최적화 없는 직접 비교.** 모든 시작 위치에서 부분 문자열을 슬라이스해 그대로 비교합니다.

```ts
function bruteForceSearch(text: string, pattern: string): number[] {
  const n = text.length, m = pattern.length;
  if (m === 0 || m > n) return [];
  const result: number[] = [];
  for (let i = 0; i <= n - m; i++) {
    if (text.slice(i, i + m) === pattern) result.push(i);
  }
  return result;
}
```

`n-m+1`개 위치마다 `O(m)` 비교를 하니 `O(nm)`입니다.

**개선: 해시를 쓰지만 매번 재계산.** "같은 문자열이면 같은 해시"라는 성질을 이용해 보지만, 아직 롤링을 안 했다면 이득이 없습니다.

```ts
function recomputeHashSearch(rh: RollingHash, text: string, pattern: string): number[] {
  const n = text.length, m = pattern.length;
  if (m === 0 || m > n) return [];
  const patHash = rh.hash(pattern);
  const result: number[] = [];
  for (let i = 0; i <= n - m; i++) {
    const windowHash = rh.hash(text.slice(i, i + m)); // O(m) — 매번 처음부터!
    if (windowHash === patHash && text.slice(i, i + m) === pattern) result.push(i);
  }
  return result;
}
```

여전히 `O(m)`짜리 `hash()` 호출이 `n-m+1`번 도니 `O(nm)`이에요. 실측으로도 원형과 완전히 같은 결과를 냅니다(4단계 교차검증에서 확인). 이 단계에서 부족한 건 딱 하나 — **이전 해시를 재사용해 O(1)에 다음 해시를 얻는 법**입니다.

**최종: 롤링 갱신으로 O(1) 이동.**

```ts
class RollingHash {
  private base: number;
  private mod: number;

  constructor(base: number = 31, mod: number = 1_000_000_007) {
    this.base = base;
    this.mod = mod;
  }

  hash(s: string): number {
    let h = 0;
    for (let i = 0; i < s.length; i++) {
      h = (h * this.base + s.charCodeAt(i)) % this.mod;
    }
    return h;
  }

  search(text: string, pattern: string): number[] {
    const n = text.length;
    const m = pattern.length;
    if (m === 0 || m > n) return [];

    // base^(m-1) mod p — 왼쪽 끝 글자를 뺄 때 쓸 자릿값, 한 번만 계산
    let highPow = 1;
    for (let i = 1; i < m; i++) highPow = (highPow * this.base) % this.mod;

    const patHash = this.hash(pattern);
    let winHash = this.hash(text.slice(0, m));

    const result: number[] = [];
    for (let i = 0; i <= n - m; i++) {
      if (winHash === patHash && text.slice(i, i + m) === pattern) {
        result.push(i);
      }
      if (i < n - m) {
        const leftCode = text.charCodeAt(i);
        const rightCode = text.charCodeAt(i + m);
        winHash = (winHash - leftCode * highPow) % this.mod;
        winHash = (winHash + this.mod) % this.mod; // 음수 방지 — 이 줄이 핵심
        winHash = (winHash * this.base + rightCode) % this.mod;
      }
    }
    return result;
  }
}
```

**가장 중요한 부분은 `winHash = (winHash + this.mod) % this.mod;` 이 한 줄입니다.** 이걸 빼면 어떤 일이 벌어지는지 실측으로 보여드릴게요. `base=31, mod=1{,}000{,}000{,}007`, 패턴 길이를 `m=20`으로 키우면(`highPow`가 커야 재현됩니다) `text = "a".repeat(25)`, `pattern = "a".repeat(20)`에서:

```text
highPow = base^19 mod p = 783,945,459   (m=2였을 땐 31이라 우연히 안 터졌다)

i=0: winHash = patHash = 644,132,625   ("aaaa...a" 20개, 정상 일치)

+mod 정규화를 뺀 버그 버전:
  buggyWin(i=1) = -355,867,382    ← 음수!
  patHash        =  644,132,625
  버그 버전은 이후 i=1..5에서도 계속 -355,867,382 로 고정되어
  patHash와 영원히 다른 값 → 실제로는 "aaaa..." 반복이라 매 위치 매칭인데
  전부 놓쳐 버린다

정상 버전(+mod 정규화 포함):
  correctWin(i=1..5) = 644,132,625  = patHash  → 매 위치 정상 매칭
```

한 줄이 빠졌을 뿐인데, 명백히 겹쳐 있는 매칭을 전부 놓치는 조용한 버그가 생깁니다. 기억법으로 정리하면:

> "뺀 다음엔 반드시 mod를 한 번 더한다 — 음수는 자릿수 밀기·곱셈을 타고 영원히 따라온다."

그 외 놓치기 쉬운 지점들:

- **`winHash == patHash`만 보고 등록하면 안 됩니다.** 반드시 `text.slice(i, i+m) === pattern`으로 실제 문자열을 검증해야 해시 충돌(다른 문자열인데 같은 해시)을 걸러냅니다.
- **`highPow`는 `search` 시작할 때 딱 한 번만 계산합니다.** 루프 안에서 다시 구하면 `O(1)` 갱신의 의미가 없어져요.
- **첫 윈도우는 롤링이 아니라 `hash()`로 처음부터 계산합니다.** 롤링은 "이전 윈도우가 있을 때"만 쓸 수 있는 기법이라, `i=0`의 시작값은 반드시 정의대로 `O(m)`에 구해야 해요.

## 실행 시각화

`base=31, mod=1{,}000{,}000{,}007`로 `text="ababab"`, `pattern="ab"`(`m=2`)를 검색한 고정 입력입니다. 실제 반환값은 `search("ababab", "ab") === [0, 2, 4]`이고, `hash("ab") = 3105`, `hash("ba") = 3135`로 두 값이 뚜렷이 다릅니다(4단계 실측). array 패널은 `text`를 문자 배열로 보여주고, `highlight`는 현재 검사 중인 윈도우 `[i, i+m-1]`, `marked`는 지금까지 등록된 매칭 시작 인덱스입니다.

> 대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.

정리하면, rolling hash는 문자열을 다항식으로 보는 관점 하나로 두 가지를 동시에 얻습니다. **해시 비교**로 대부분의 위치를 `O(1)`에 배제하고, **롤링 갱신**으로 그 해시 자체를 매번 새로 구하지 않아도 되게 만들죠. 그 결과 `search`는 평균 `O(n+m)`에 끝나고, 해시 충돌이 몰아쳐도(설계상 드묾) 최악 `O(nm)`을 넘지 않습니다 — 애초에 노렸던 목표 그대로예요.

## 스스로 점검하기

1. `base=31, mod=1{,}000{,}000{,}007`로 `hash("ba")`를 손으로 계산해 `3135`가 나오는지 확인해 보세요. (`code('b')=98, code('a')=97`)
2. `+mod` 정규화를 빼먹은 버그 버전이 `m=2`인 `"ababab"`/`"ab"` 예제에서는 왜 티가 안 났는데, `m=20`인 `"a".repeat(25)`/`"a".repeat(20)` 예제에서는 티가 났을까요? `highPow`의 크기와 연결지어 설명해 보세요.
3. `search`에서 `winHash == patHash`일 때 문자열 직접 비교(`text.slice(...) === pattern`)를 생략하면, `"aaaa"`에서 패턴 `"ab"`를 찾을 때 어떤 잘못된 결과가 나올 수 있을까요? (힌트: 같은 해시를 만드는 다른 문자열 쌍을 만들 수 있는지 생각해 보세요)
