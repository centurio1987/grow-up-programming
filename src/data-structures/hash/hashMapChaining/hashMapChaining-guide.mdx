# HashMapChaining — 키를 인덱스로, 충돌은 체인으로

## 한눈에 보는 컨셉

임의의 키를 정수 인덱스로 바꾸는 **해시 함수** 하나로, 배열의 O(1) 인덱스 접근 능력을 키-값 저장에 그대로 빌려오는 자료구조예요. 서로 다른 키가 같은 인덱스로 몰리는 **충돌**은 그 버킷에 작은 리스트(체인)를 매달아 해결하고, 리스트가 너무 길어지기 전에 버킷 수를 2배로 늘려(재해시) 평균 O(1)을 유지합니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 체이닝 해시맵을 떠올리세요.

- **순서 없이, 키로만** 빠르게 찾고/넣고/지워야 한다 ("범위 질의"나 "정렬 순회" 요구가 없다)
- 삽입·삭제가 **자유롭게 섞여서** 계속 일어난다 (정적으로 한 번 정렬해 두는 걸로는 부족하다)
- "이미 본 적 있는 값인가?", "이 키의 값을 즉시 갱신하고 싶다" 같은 **존재/갱신 질의**가 반복된다

naive한 대안들과 비교하면 왜 해시맵이 필요한지 체감이 됩니다.

```text
연산            배열(선형 탐색)   정렬 배열(이진탐색+삽입)   체이닝 해시맵(평균)
get(key)        O(n)              O(log n)                   O(1)
set(key,value)  O(n)              O(n) ← splice가 병목        O(1)
range 질의      O(n)              O(log n + k) 지원          지원 안 함(정렬 없음)
```

범위 질의("low 이상 high 이하 전부")가 필요하다면 정렬 구조나 B+Tree가 낫습니다. 하지만 **점 조회·점 갱신만 반복**된다면, 정렬을 유지하는 비용 자체가 낭비예요 — 해시맵은 애초에 정렬을 포기하고 그 자리를 O(1) 인덱스 접근으로 채웁니다. 같은 해시맵 계열 안에서도 선택이 갈리는데, 삭제가 잦고 구현을 단순하게 유지하고 싶다면 체이닝을, 메모리 오버헤드와 캐시 지역성이 중요하다면 오픈 어드레싱(open addressing)을 고려합니다.

### 문제 사례와 적용 예시

- **인터프리터 심볼 테이블**: `let x = 10` 실행 시 `"x"` → `10`을 저장하고, `x + 1` 평가 시 `"x"`를 즉시 조회합니다. 변수가 수백 개여도 조회 속도가 떨어지면 안 됩니다.
- **캐시 백엔드**: LRU/LFU 캐시는 "이 키가 캐시에 있는가?"를 O(1)에 답해야 캐시로서 의미가 있습니다. 내부적으로 체이닝 해시맵(또는 유사 구조) 위에 정책을 얹습니다.
- **그래프 알고리즘의 방문 표시**: 정점 id가 촘촘한 정수가 아니라 문자열·객체일 때, `visited: Map<Node, boolean>`로 방문 여부를 O(1)에 확인합니다.
- **코딩 테스트의 빈도수 집계**: Two Sum처럼 "지금까지 본 값 중 짝이 있는가?"를 매 원소마다 즉시 확인해야 하는 문제는 해시맵 없이는 O(n²)로 떨어집니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드는 다음 인터페이스를 기준으로 설명합니다.

**속성(내부 상태)**

```ts
class HashMapChaining<K, V> {
  private buckets: Array<Array<[K, V]>>;  // 길이 = capacity, 각 원소는 체인(배열)
  private capacity: number;                // 버킷 개수 (2배씩 증가)
  private count: number;                   // 저장된 키-값 쌍 개수
  private readonly LOAD_FACTOR = 0.75;     // 재해시 임계값
}
```

지켜야 할 불변식은 네 가지예요.

1. `buckets.length === capacity`가 항상 성립한다.
2. `count`는 모든 체인 길이의 합과 같다: $\text{count} = \sum_{i=0}^{\text{capacity}-1} |\text{buckets}[i]|$.
3. 각 체인 안에서 키는 유일하다 — 같은 키가 같은 체인에 두 번 들어가지 않는다(재삽입은 덮어쓴다).
4. `set` 호출이 끝난 직후에는 항상 $\dfrac{\text{count}}{\text{capacity}} \le 0.75$가 성립한다.

`capacity = 4`인 해시맵에 `"a"`, `"b"`, `"c"`를 순서대로 넣은 직후 상태를 그려 보면 이렇습니다.

```text
buckets (capacity=4)
 [0] → (비어있음)
 [1] → [("a", 1)]
 [2] → [("b", 2)]
 [3] → [("c", 3)]
```

**액션(연산)** — 이 자료구조가 제공하는 전체 연산입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `set(key, value)` | 해시로 버킷을 찾아 존재하면 값 갱신, 없으면 추가. load factor 초과 시 `resize` 호출 | O(1) 평균, O(n) 최악 |
| `get(key)` | 버킷의 체인을 선형 탐색해 값 반환, 없으면 `undefined` | O(1) 평균, O(n) 최악 |
| `has(key)` | `get`과 같은 경로로 존재 여부만 반환 | O(1) 평균, O(n) 최악 |
| `delete(key)` | 체인에서 항목 제거, 성공 시 `count--` | O(1) 평균, O(n) 최악 |
| `size()` | `count` 반환 | O(1) |
| `keys()` / `values()` | 모든 버킷을 순회하며 키/값 수집 | O(n) |
| `resize()` (내부) | `capacity`를 2배로 늘리고 전체 항목을 새 버킷으로 재해시 | O(n), 삽입당 분할 상환 O(1) |

해시 함수는 문자열로 변환한 키를 Horner's method로 누적합니다.

$$
h(k) = \Big(\sum_{i=0}^{n-1} s_i \cdot 31^{\,n-1-i}\Big) \mod \text{capacity}, \quad s = \text{String}(k),\ n = |s|
$$

핵심 연산 두 개를 before/after로 자세히 볼게요.

**① 충돌 삽입 — 체인에 이어 붙이기.** 위 상태(`capacity=4`)에서 `set("e", 5)`를 호출하면, `"e"`의 해시값도 1이라 `"a"`와 충돌합니다.

```text
Before: buckets[1] = [("a", 1)]
After:  buckets[1] = [("a", 1), ("e", 5)]   ← 체인 뒤에 이어 붙임, 다른 버킷은 그대로
```

**② resize — 전체 재해시.** 위 삽입으로 `count`가 4, `capacity`가 4가 되어 $4/4 = 1.0 > 0.75$이므로 재해시가 트리거됩니다. `capacity`가 8이 되면 같은 키라도 해시값이 달라질 수 있습니다.

```text
Before (capacity=4): [0]:[]  [1]:[("a",1),("e",5)]  [2]:[("b",2)]  [3]:[("c",3)]
After  (capacity=8): [0]:[]  [1]:[("a",1)]  [2]:[("b",2)]  [3]:[("c",3)]  [4]:[]  [5]:[("e",5)]  [6]:[]  [7]:[]

capacity가 바뀌면 h(k) mod capacity도 바뀐다 → "e"는 더 이상 버킷 1이 아니라 버킷 5로 이동
```

### 왜 모순 없이 작동하는가

빈 해시맵(`buckets`가 전부 빈 배열, `count = 0`)에서 시작하면 불변식 네 개는 자명하게 성립합니다. 이제 각 연산이 불변식을 깨지 않고 그대로 보존한다는 것을 볼게요.

- **`set`은 불변식 1·2·3을 지킵니다.** 버킷 개수는 `set` 도중 바뀌지 않으니 1은 자동 유지됩니다. 기존 키를 찾으면 값만 바꾸고 `count`를 건드리지 않으니 2가 유지되고, 새 키만 `push`하고 `count++`하니 역시 2가 유지됩니다. 삽입 전에 반드시 체인을 선형 탐색해 같은 키가 있는지 먼저 확인하므로 3(키 유일성)도 깨지지 않습니다.
- **`resize`는 불변식 1을 새 값으로 다시 세우고, 2·3을 보존합니다.** 새 `buckets`를 `capacity`만큼 만들고 그 즉시 `capacity`도 함께 갱신하므로 1이 성립합니다. 기존 항목을 하나도 빠짐없이, 정확히 한 번씩 새 버킷으로 옮기므로(원본을 지우고 복사가 아니라 전량 이동) `count`도 키 유일성도 그대로예요.
- **불변식 4는 `set`의 마지막 줄이 지킵니다.** `set`은 항목을 추가한 직후 `count / capacity`를 확인해서, 0.75를 **초과하는 순간** 바로 `resize`를 호출합니다. 따라서 `set`이 반환된 시점에는 항상 $\text{count}/\text{capacity} \le 0.75$입니다.

**여기서 헷갈리기 쉬운 포인트는 "정확히 0.75"를 경계로 착각하는 것입니다.** `capacity=4`, `count=3`이면 $3/4 = 0.75$인데, 이건 "초과"가 아니라 "같음"이라 재해시가 일어나지 않습니다. 그다음 `set` 한 번으로 `count`가 4가 되어야(=`4/4=1.0>0.75`) 비로소 재해시가 트리거됩니다. `>` 대신 `>=`를 쓰면 정확히 0.75인 시점에도 불필요하게 재해시가 일어나 버립니다.

> 확인 질문 하나 해 볼게요: `capacity=4`에서 `count=3`인 상태로 `set`을 한 번 더 호출하면 재해시가 일어날까요? 정답은 "그 호출이 새 키를 추가한다면 예"입니다 — `count`가 4가 되는 순간 $4/4=1.0>0.75$라서 트리거됩니다. 반대로 이미 있는 키를 덮어쓰는 `set`이라면 `count`가 그대로라 재해시는 일어나지 않아요.

**또 하나 헷갈리기 쉬운 포인트는 키 비교 방식입니다.** 이 구조는 키를 `===`로 비교합니다. 문자열·숫자 키는 값이 같으면 같은 키로 인식되지만, 객체 키(`{ id: 1 }`)는 내용이 같아도 참조가 다르면 다른 키로 취급됩니다 — `set({id:1}, "x"); get({id:1})`은 새 객체 리터럴이라 `undefined`를 반환합니다.

엣지 케이스를 점검해 볼게요.

```text
빈 맵에서 get/has/delete             → undefined / false / false
같은 키 재삽입(set)                   → 값만 갱신, count 불변 (검증: get="k"→2, size=1)
없는 키 delete                        → false, count 불변
capacity=4, count=3 (경계값)          → 3/4=0.75, resize 트리거 안 함 ('초과'만 트리거)
빈 문자열 키 ""                       → String("")="" → h=0, 정상적으로 버킷 0 사용
```

## 아이디어를 코드로 옮기기

바로 체이닝 해시맵을 코딩하기 전에, 이 자료구조가 어떤 단계를 거쳐 만들어지는지 코드로 따라가 봅니다.

**원형(naive) — 배열 + 선형 탐색.** 가장 단순하게 `[K, V][]`에 순서대로 쌓고, 찾을 때마다 처음부터 훑습니다.

```ts
class NaiveMap<K, V> {
  private items: [K, V][] = [];

  set(key: K, value: V): void {
    for (const item of this.items) {
      if (item[0] === key) {
        item[1] = value;
        return;
      }
    }
    this.items.push([key, value]);
  }

  get(key: K): V | undefined {
    for (const [k, v] of this.items) if (k === key) return v;
    return undefined; // 매번 처음부터 끝까지 훑는다 → O(n)
  }
}
```

이 버전은 `get`/`set` 모두 항목 수 `n`에 비례해 느려집니다. 데이터가 10만 개면 조회 한 번에 최악 10만 번 비교합니다.

**개선 — 정렬 배열 + 이진 탐색.** 키를 정렬 상태로 유지하면 `get`은 이진 탐색으로 O(log n)까지 빨라집니다.

```ts
class SortedMap<K extends string, V> {
  private items: [K, V][] = []; // key 오름차순 유지

  private indexOf(key: K): number {
    let lo = 0, hi = this.items.length;
    while (lo < hi) {
      const mid = (lo + hi) >> 1;
      if (this.items[mid]![0] < key) lo = mid + 1;
      else hi = mid;
    }
    return lo; // key가 들어갈(또는 있는) 위치
  }

  get(key: K): V | undefined {
    const i = this.indexOf(key); // O(log n)
    return this.items[i] && this.items[i]![0] === key ? this.items[i]![1] : undefined;
  }

  set(key: K, value: V): void {
    const i = this.indexOf(key);
    if (this.items[i] && this.items[i]![0] === key) this.items[i] = [key, value];
    else this.items.splice(i, 0, [key, value]); // 여전히 O(n) — 병목이 set으로 옮겨갔을 뿐
  }
}
```

`get`은 빨라졌지만 `set`의 `splice`는 삽입 위치 뒤 원소를 전부 한 칸씩 밀어야 해서 여전히 O(n)입니다. 정렬을 유지하는 대가를 삽입이 지불하는 거예요 — 여기서 돌파구가 필요합니다: **"정렬을 포기하고, 키 자체로 위치를 계산하면 탐색이 아예 필요 없어진다."** 이게 해시맵의 관찰입니다.

**최종 — 해시 + 체이닝.** 앞서 정의한 스펙을 그대로 구현합니다.

```ts
class HashMapChaining<K, V> {
  private buckets: Array<Array<[K, V]>>;
  private capacity: number;
  private count: number;
  private readonly LOAD_FACTOR = 0.75;

  constructor(initialCapacity: number = 16) {
    this.capacity = initialCapacity;
    this.buckets = Array.from({ length: this.capacity }, () => []);
    this.count = 0;
  }

  private hashWith(key: K, capacity: number): number {
    const s = String(key);
    let h = 0;
    for (let i = 0; i < s.length; i++) {
      h = (h * 31 + s.charCodeAt(i)) % capacity;
    }
    return h;
  }

  private hash(key: K): number {
    return this.hashWith(key, this.capacity);
  }

  private resize(): void {
    const newCapacity = this.capacity * 2;
    const newBuckets: Array<Array<[K, V]>> = Array.from({ length: newCapacity }, () => []);
    for (const chain of this.buckets) {
      for (const [k, v] of chain) {
        const newIndex = this.hashWith(k, newCapacity); // 새 capacity로 다시 계산
        newBuckets[newIndex]!.push([k, v]);
      }
    }
    this.buckets = newBuckets;
    this.capacity = newCapacity;
  }

  set(key: K, value: V): void {
    const index = this.hash(key);
    const chain = this.buckets[index]!;
    for (let i = 0; i < chain.length; i++) {
      if (chain[i]![0] === key) {
        chain[i] = [key, value];
        return;
      }
    }
    chain.push([key, value]);
    this.count++;
    if (this.count / this.capacity > this.LOAD_FACTOR) {
      this.resize();
    }
  }

  get(key: K): V | undefined {
    const chain = this.buckets[this.hash(key)]!;
    for (const [k, v] of chain) if (k === key) return v;
    return undefined;
  }

  has(key: K): boolean {
    return this.buckets[this.hash(key)]!.some(([k]) => k === key);
  }

  delete(key: K): boolean {
    const chain = this.buckets[this.hash(key)]!;
    for (let i = 0; i < chain.length; i++) {
      if (chain[i]![0] === key) {
        chain.splice(i, 1);
        this.count--;
        return true;
      }
    }
    return false;
  }

  size(): number {
    return this.count;
  }

  keys(): K[] {
    const result: K[] = [];
    for (const chain of this.buckets) for (const [k] of chain) result.push(k);
    return result;
  }

  values(): V[] {
    const result: V[] = [];
    for (const chain of this.buckets) for (const [, v] of chain) result.push(v);
    return result;
  }
}
```

가장 중요한 부분은 `constructor`의 `Array.from({ length: this.capacity }, () => [])`입니다. 놓치기 쉬운 구현부를 짚어 볼게요.

- **`Array(capacity).fill([])`을 쓰면 안 됩니다.** `fill`은 인자로 준 배열 **하나**를 모든 칸에 복사가 아니라 참조로 채웁니다. 실제로 재현해 보면:
  ```ts
  const bad = Array(4).fill([]);
  bad[1].push(["a", 1]);
  console.log(bad[0]); // [["a", 1]] ← 넣지도 않은 버킷 0에 나타남!
  console.log(bad[0] === bad[1]); // true — 사실 4칸 모두 같은 배열
  ```
  `Array.from`은 콜백을 칸마다 새로 실행해 서로 다른 배열을 만들기 때문에 이 문제가 없습니다.
- **`resize`에서 `hashWith(k, newCapacity)`로 다시 계산하는 줄이 핵심입니다.** 만약 재해시를 생략하고 기존 체인을 그대로 새 배열의 같은 인덱스에 복사만 한다면, `capacity=4→8` 예시에서 `"e"`는 여전히 인덱스 1에 남습니다. 하지만 이후 `get("e")`는 새 `capacity=8` 기준 해시(`hash("e")=5`)로 버킷 5를 보러 가므로, 분명히 넣은 값인데도 `undefined`를 반환하는 버그가 생깁니다.
- **`set`에서 존재 여부 확인이 `push`보다 먼저입니다.** 순서를 바꿔 먼저 `push`하면 같은 키가 체인에 두 번 쌓여 불변식 3이 깨지고, `keys()`에 중복 키가 나타납니다.

> 기억법: "버킷마다 자기 배열을 새로 받는다 — fill은 나눠주고, from은 새로 만든다."
