# HashMapOpenAddressing — 충돌은 옆 슬롯으로, 삭제는 팻말로

## 한눈에 보는 컨셉

개방 주소법(open addressing) 해시맵은 충돌이 나도 링크드 리스트를 새로 만들지 않고, 같은 배열 안의 다음 빈 슬롯을 순서대로 찾아가 저장해요(선형 탐사, linear probing). 삭제는 슬롯을 진짜로 비우는 대신 tombstone이라는 팻말을 남겨서, 그 뒤에 있는 다른 키를 찾는 탐사가 중간에 끊기지 않게 합니다. 포인터 없는 연속 배열이라 캐시 지역성이 좋고, 평균 O(1)에 삽입·조회·삭제를 처리해요 — CPython의 dict, Rust의 `HashMap`이 이 계열입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 개방 주소법을 떠올리세요.

- 메모리가 빠듯해서 체이닝의 링크드 리스트(노드마다 포인터 오버헤드)를 피하고 싶다
- 조회가 압도적으로 많아서 캐시 미스 한 번의 비용이 무시 못 할 정도로 크다(임베디드, 저지연 서비스)
- 슬롯을 절반 이상 비워 둘 메모리 여유가 있다 — load factor를 낮게 유지해야 하기 때문

체이닝과 비교하면 트레이드오프가 뚜렷합니다.

```text
                체이닝(링크드 리스트)          개방 주소법(선형 탐사)
메모리 배치      버킷 배열 + 노드 포인터 산재     배열 하나, 연속 메모리
캐시 미스        충돌마다 포인터 추적 → 미스↑    슬롯만 이동 → 프리페치 효과
load factor 한계 1을 넘어도 동작(체인이 길어질 뿐) 1을 넘으면 삽입 불가 → 0.5에서 미리 확장
삭제             노드 제거만 하면 끝             tombstone 관리 필요(구현 복잡도↑)
```

선택 기준은 이렇습니다: **삭제가 잦고 load factor가 들쭉날쭉해도 괜찮은 범용 상황**이면 체이닝이 편하고, **조회가 압도적으로 많고 메모리 지역성이 성능을 좌우하는 상황**이면 개방 주소법이 유리합니다.

연산별 비용을 요약하면($n$은 저장된 원소 수):

```text
set / get / has / delete   O(1) 평균, O(n) 최악(탐사 체인이 전체 길이인 경우)
resize                      O(n), 상환(amortized) O(1)
```

### 문제 사례와 적용 예시

- **CPython의 `dict`/`set`**: 실제로 개방 주소법(의사난수 탐사)을 사용합니다.
- **Rust의 `std::collections::HashMap`**: SwissTable 계열의 개방 주소법으로 구현돼 있습니다.
- **임베디드/게임 엔진의 캐시 테이블**: 동적 할당을 피해야 하는 환경에서 고정 크기 배열 하나로 캐시를 구현할 때.
- **코딩 테스트 맥락**: "언어 내장 `Map`/`Object` 없이 배열 하나로 해시맵을 직접 구현하라" 류의 문제 — 충돌 처리와 삭제 설계 능력을 함께 확인합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)** — 슬롯은 세 가지 상태 중 하나입니다.

```ts
type Slot<K, V> =
  | { state: "empty" }
  | { state: "occupied"; key: K; value: V }
  | { state: "tombstone" };

class HashMapOpenAddressing<K, V> {
  private slots: Slot<K, V>[]; // 길이 capacity의 고정 배열
  private capacity: number; // 슬롯 총 개수
  private count: number; // 살아있는(occupied) 슬롯 수 — tombstone은 미포함
  private readonly LOAD_FACTOR = 0.5;
}
```

지켜야 할 불변식은 네 가지예요.

1. 매 시점 각 슬롯은 `empty` / `occupied` / `tombstone` 중 정확히 하나의 상태를 가집니다.
2. $\text{count} = |\{\, i : \text{slots}[i].\text{state} = \text{occupied} \,\}|$ — tombstone은 count에서 제외됩니다.
3. `set()` 호출이 끝난 시점에는 항상 $\lambda = \text{count}/\text{capacity} \le 0.5$ 를 만족합니다(초과하는 순간 resize가 동기적으로 일어나기 때문).
4. 키 $k$가 슬롯 $i$에 저장돼 있다면, $\text{probe}(k, 0), \text{probe}(k, 1), \dots$ 로 슬롯 $i$에 도달하기까지 지나친 모든 슬롯은 `empty`가 아닙니다(`occupied` 또는 `tombstone`). 이게 탐사가 중간에 끊기지 않는 이유입니다.

capacity=8인 배열에 `dog`, `owl`, `elk`를 순서대로 넣은 실제 상태를 그려 보면(세 키는 이 가이드의 해시 함수로 **실제로** 슬롯 4에 충돌합니다):

```text
index:     0      1      2      3      4      5      6      7
state:  [empty][empty][empty][empty][ occ ][ occ ][ occ ][empty]
                                       dog    owl    elk
                                        ↑
                          hash("dog") = hash("owl") = hash("elk") = 4  (capacity=8, 실측)
```

**액션(연산)** — 이 자료구조가 제공하는 다섯 가지 연산입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `set(key, value)` | 탐사로 자리를 찾아 삽입/갱신, 필요하면 resize | 평균 $O(1)$, 최악 $O(n)$ |
| `get(key)` | 탐사로 값을 조회 | 평균 $O(1)$, 최악 $O(n)$ |
| `has(key)` | 탐사로 존재 여부 확인 | 평균 $O(1)$, 최악 $O(n)$ |
| `delete(key)` | 탐사로 찾아 tombstone 마킹 | 평균 $O(1)$, 최악 $O(n)$ |
| `size()` | 살아있는 원소 수 반환 | $O(1)$ |

핵심 연산 두 개를 실제 값으로 자세히 볼게요. 탐사 규칙은 $\text{probe}(k, i) = (h(k) + i) \bmod m$ 입니다($m$은 capacity).

**① `set` — 선형 탐사로 자리 찾기.**

```text
capacity=8, hash("dog") = hash("owl") = hash("elk") = 4  (실측)

set("dog", 10):  probe(4,0)=4 → empty → 삽입
  Before: [ _, _, _, _, _, _, _, _ ]
  After : [ _, _, _, _,dog, _, _, _ ]

set("owl", 20):  probe(4,0)=4 → occupied(dog, 키 불일치) → probe(4,1)=5 → empty → 삽입
  Before: [ _, _, _, _,dog, _, _, _ ]
  After : [ _, _, _, _,dog,owl, _, _ ]

set("elk", 30):  4(occupied,dog)→5(occupied,owl)→6(empty)→삽입
  After : [ _, _, _, _,dog,owl,elk, _ ]
```

**② `delete` + tombstone skip — 왜 탐사가 끊기지 않는가.**

```text
delete("owl"): 슬롯5를 tombstone으로 마킹합니다(empty가 아닙니다!)
  Before: [ _, _, _, _,dog,owl,elk, _ ]
  After : [ _, _, _, _,dog, † ,elk, _ ]     († = tombstone)

get("elk"): probe(4,0)=4(occupied,dog,불일치)
          → probe(4,1)=5(tombstone → 건너뛰고 계속)
          → probe(4,2)=6(occupied,elk,일치) → 30 반환
```

### 왜 모순 없이 작동하는가

빈 배열에서 시작하면 불변식은 자명하게 성립합니다(모든 슬롯이 `empty`, count=0). 이제 각 연산이 불변식을 보존하는지 봅시다.

**`set`이 불변식을 보존하는 이유.** 삽입 위치는 항상 `empty` 슬롯이거나(count가 없던 자리를 채움) 이미 `tombstone`이던 슬롯(죽은 자리를 되살림)입니다. 두 경우 모두 정확히 하나의 `occupied` 슬롯이 늘어나므로 count가 정확히 반영되고, 그 직후 $\lambda > 0.5$면 즉시 resize로 다시 $\lambda \le 0.5$를 복구합니다(불변식 3).

**`delete`가 불변식을 보존하는 이유.** 슬롯을 `empty`가 아니라 `tombstone`으로 바꿉니다. 불변식 4가 "지나친 슬롯은 empty가 아니다"였죠 — tombstone은 empty가 아니므로, 그 슬롯 뒤에 저장된 다른 키로 가는 탐사 경로가 계속 살아 있습니다.

여기서 헷갈리기 쉬운 포인트를 몇 가지 짚어 둘게요.

- **load factor가 정확히 0.5일 때는 resize가 일어나지 않습니다.** 조건이 `count / capacity > LOAD_FACTOR`로 **초과**만 체크하기 때문이에요. 실측으로 확인해 보면, capacity=4에서 2개를 넣으면 $2/4=0.5$인데도 resize가 일어나지 않고, 3개째($3/4=0.75$)에서야 비로소 capacity가 8로 늘어납니다. "0.5 이하로 유지"가 아니라 "0.5 초과 시에만 확장"이라는 정확한 조건을 기억하세요.
  > 확인 질문 하나만 해 볼까요? capacity=4에서 count=2일 때, 다음 삽입 없이 지금 당장 resize가 일어날까요? — 아니요. resize는 `set()`이 count를 늘린 **직후**에만 검사하므로, 삽입이 일어나지 않으면 검사 자체가 없습니다.
- **tombstone과 empty를 혼동하면 존재하는 키를 못 찾습니다.** `delete("owl")`을 `empty`로 처리해 버리면 어떻게 될까요? `get("elk")`가 슬롯4(dog, 불일치)를 지나 슬롯5에서 `empty`를 만나 탐사를 즉시 멈춰 버립니다. 슬롯6에 진짜로 있는 `elk`(값 30)를 못 보고 `undefined`를 반환하는 거예요 — 아래 코드 절의 Stage 1에서 이 오류를 직접 재현합니다.
- **tombstone을 마킹만 하고 재사용하지 않아도 문제가 생깁니다.** 정답을 찾긴 하지만 탐사 거리가 계속 낭비돼요 — 아래 코드 절의 Stage 2에서 실측치로 보여드립니다.
- **`has`를 `get(key) !== undefined`로 구현하면 안전하지 않습니다.** 만약 `V`에 `undefined`를 실제 값으로 저장한 경우, 존재하는 키인데도 `has`가 `false`를 반환할 수 있어요. `has`는 `get`과 별개로 자기 탐사 로직을 가져야 합니다.

엣지 케이스를 점검해 봅시다(모두 실측 확인됨).

```text
빈 맵에 get/has/delete       → undefined / false / false
capacity=1로 시작            → 첫 삽입 직후 1/1=1 > 0.5 → 즉시 resize(capacity=2)
동일 키 재삽입                → 값만 갱신, count 불변(size 그대로)
없는 키 delete                → 첫 empty를 만나 즉시 false
resize 도중 재귀 삽입          → count를 0으로 리셋한 뒤 재계산하므로,
                               재해시 중 load factor가 다시 0.5를 넘어
                               연쇄적으로 resize가 겹치지 않습니다
                               (원래 count ≤ 0.5·capacity_old 이므로
                               재해시 중 최대 λ = count/(2·capacity_old) ≤ 0.25)
```

## 아이디어를 코드로 옮기기

`set`/`get`/`has`/`delete`는 모두 같은 탐사 루프의 변주입니다. 다만 삭제를 어떻게 다루느냐에 따라 정확성과 성능이 완전히 달라져요. 세 단계로 나눠서 볼게요 — 세 단계 모두 capacity=8에서 `dog`, `owl`, `elk`가 실제로 슬롯 4에 충돌하는 상황으로 검증했습니다.

**Stage 1 — 원형: tombstone 없이 그냥 비운다.**

```ts
delete(key: K): void {
  const start = this.hash(key);
  for (let step = 0; step < this.capacity; step++) {
    const idx = (start + step) % this.capacity;
    const slot = this.slots[idx];
    if (slot.state === "empty") return;
    if (slot.state === "occupied" && slot.key === key) {
      this.slots[idx] = { state: "empty" }; // ← 진짜로 비워버린다
      return;
    }
  }
}
```

`dog`, `owl`, `elk`를 슬롯 4, 5, 6에 넣은 뒤 `delete("owl")`을 이렇게 처리하면:

```text
Stage 1(tombstone 없음) — delete("owl") 후:
 idx:     0     1     2     3     4      5      6      7
 state: [ _ ][ _ ][ _ ][ _ ][dog ][ _  ][elk ][ _ ]

get("elk"): probe 4(dog,불일치) → probe 5(EMPTY!) → 탐사가 여기서 멈춰 버림
반환값: undefined   ← 실제로는 슬롯6에 30이 멀쩡히 있는데도 못 찾습니다(실측 재현)
```

여기가 tombstone이 필요한 이유예요. 슬롯을 비우는 순간 그 뒤로 가는 다리가 끊깁니다.

**Stage 2 — 개선: tombstone은 마킹하지만 재사용은 안 한다.**

```ts
set(key: K, value: V): void {
  const start = this.hash(key);
  for (let step = 0; step < this.capacity; step++) {
    const idx = (start + step) % this.capacity;
    const slot = this.slots[idx];
    if (slot.state === "occupied" && slot.key === key) { slot.value = value; return; }
    if (slot.state === "empty") { this.slots[idx] = { state: "occupied", key, value }; return; }
    // tombstone이어도 그냥 지나친다(재사용 안 함)
  }
}
```

`delete("dog")`로 슬롯4를 tombstone으로 만든 뒤 `set("dog", 999)`로 재삽입하면:

```text
Stage 2(재사용 안 함) — delete("dog") 후 set("dog", 999):
 idx:     0     1     2     3     4     5      6      7
 state: [ _ ][ _ ][ _ ][ _ ][ † ][owl ][elk ][dog ]
                              ↑                 ↑
                        원래 자리인데 방치됨   3칸 밀려서 재삽입(낭비된 탐사 3스텝, 실측)
```

정답은 맞지만 탐사 거리가 공짜로 늘어났죠. 죽은 슬롯을 방치하면 배열이 실제보다 더 꽉 찬 것처럼 동작합니다.

**Stage 3 — 최종: tombstone을 마킹하고 첫 번째로 만난 자리를 재사용한다.**

```ts
class HashMapOpenAddressing<K, V> {
  private slots: Slot<K, V>[];
  private capacity: number;
  private count: number;
  private readonly LOAD_FACTOR = 0.5;

  constructor(initialCapacity: number = 16) {
    this.capacity = initialCapacity;
    this.slots = Array.from({ length: this.capacity }, () => ({ state: "empty" as const }));
    this.count = 0;
  }

  private hash(key: K): number {
    const s = String(key);
    let h = 0;
    for (let i = 0; i < s.length; i++) {
      h = (Math.imul(h, 31) + s.charCodeAt(i)) | 0;
    }
    return ((h % this.capacity) + this.capacity) % this.capacity;
  }

  private resize(): void {
    const oldSlots = this.slots;
    this.capacity *= 2;
    this.slots = Array.from({ length: this.capacity }, () => ({ state: "empty" as const }));
    this.count = 0;
    for (const slot of oldSlots) {
      if (slot.state === "occupied") this.set(slot.key, slot.value); // tombstone은 자연히 버려진다
    }
  }

  set(key: K, value: V): void {
    let firstTombstone = -1;
    const start = this.hash(key);
    for (let step = 0; step < this.capacity; step++) {
      const idx = (start + step) % this.capacity;
      const slot = this.slots[idx];
      if (slot.state === "occupied" && slot.key === key) {
        slot.value = value;
        return;
      }
      if (slot.state === "tombstone") {
        if (firstTombstone === -1) firstTombstone = idx;
        continue;
      }
      if (slot.state === "empty") {
        const insertAt = firstTombstone !== -1 ? firstTombstone : idx;
        this.slots[insertAt] = { state: "occupied", key, value };
        this.count++;
        if (this.count / this.capacity > this.LOAD_FACTOR) this.resize();
        return;
      }
    }
  }

  get(key: K): V | undefined {
    const start = this.hash(key);
    for (let step = 0; step < this.capacity; step++) {
      const idx = (start + step) % this.capacity;
      const slot = this.slots[idx];
      if (slot.state === "empty") return undefined;
      if (slot.state === "occupied" && slot.key === key) return slot.value;
    }
    return undefined;
  }

  has(key: K): boolean {
    const start = this.hash(key);
    for (let step = 0; step < this.capacity; step++) {
      const idx = (start + step) % this.capacity;
      const slot = this.slots[idx];
      if (slot.state === "empty") return false;
      if (slot.state === "occupied" && slot.key === key) return true;
    }
    return false;
  }

  delete(key: K): boolean {
    const start = this.hash(key);
    for (let step = 0; step < this.capacity; step++) {
      const idx = (start + step) % this.capacity;
      const slot = this.slots[idx];
      if (slot.state === "empty") return false;
      if (slot.state === "occupied" && slot.key === key) {
        this.slots[idx] = { state: "tombstone" };
        this.count--;
        return true;
      }
    }
    return false;
  }

  size(): number {
    return this.count;
  }
}
```

같은 시나리오(`delete("dog")` 후 `set("dog", 999)`)를 이 최종 버전으로 돌리면:

```text
Stage 3(재사용) — delete("dog") 후 set("dog", 999):
 idx:     0     1     2     3     4     5      6      7
 state: [ _ ][ _ ][ _ ][ _ ][dog ][owl ][elk ][ _ ]
                              ↑
                        원래 자리로 정확히 복귀(낭비 0스텝, 실측)
```

가장 중요한 부분은 이 두 줄입니다.

```ts
if (slot.state === "tombstone") {
  if (firstTombstone === -1) firstTombstone = idx;
  continue;
}
```

**처음 만난** tombstone만 기억해 두고, 그 뒤로도 계속 탐사를 이어 간다는 게 핵심이에요. 여기서 `continue`를 빼먹고 바로 삽입해 버리면 동일 키가 이미 더 뒤쪽에 있는지 확인하지 못한 채 중복 슬롯을 만들 수 있고, `firstTombstone`을 매번 갱신하면 가장 먼 tombstone을 쓰게 되어 오히려 손해입니다.

```ts
if (this.count / this.capacity > this.LOAD_FACTOR) this.resize();
```

이 한 줄의 비교 연산자도 놓치기 쉬운 지점입니다. `>`를 `>=`로 바꾸면 load factor가 정확히 0.5에 도달하는 순간(예: capacity=4, count=2)에도 resize가 발생해 버려, 위 엣지 케이스 표에서 확인한 "정확히 0.5에서는 유지" 동작이 깨집니다.

`resize()`가 새 배열에 재삽입할 때 `this.set()`을 재귀적으로 호출하는 게 안전한 이유도 짚어 둘게요. `count`를 0으로 리셋한 뒤 하나씩 채우므로, 재해시 도중의 load factor는 최대 $count_{old}/(2 \cdot capacity_{old}) \le 0.25$를 넘지 않습니다 — 재해시 중에 또 resize가 겹쳐 걸릴 일이 없다는 뜻이에요.

capacity를 매번 2배로 늘리는 이유도 상환분석(amortized analysis)으로 설명됩니다. $n$번 삽입하는 동안 resize가 일어난 시점들의 capacity를 모두 더하면 $c_0 + 2c_0 + 4c_0 + \dots \le 2n$이라는 등비수열이 되므로, 재해시에 든 총 비용은 $O(n)$이고 삽입 1회당 상환 비용은 $O(1)$입니다.

> 기억법: "빈 자리를 만나면 멈추고 채운다. 무덤을 만나면 기억만 하고 지나간다."

## 실행 시각화

아래 시뮬레이션은 capacity=8인 배열에서 `set("a",1)` → `set("b",2)` → `set("c",3)` → `delete("b")` → `get("c")` 순서로 진행됩니다. 설명 편의를 위해 이 데모에서는 `hash("a") = hash("b") = hash("c") = 3`이라고 **가정**합니다. 실제로 이 가이드의 해시 함수로 계산하면 `hash("a")=1`, `hash("b")=2`, `hash("c")=3`이라 세 키는 원래 서로 충돌하지 않습니다(위 `dog`/`owl`/`elk` 예시가 실제 충돌 사례였죠) — 여기서는 세 키가 모두 슬롯 3에 몰리는 상황을 일부러 만들어, 선형 탐사와 tombstone 스킵이 한 번에 이어지는 장면을 보여 드립니다. 배열 패널의 값은 `0`=empty, `1`=occupied, `-1`=tombstone을 뜻하고, `get("c")`의 실제 반환값은 `3`입니다.
