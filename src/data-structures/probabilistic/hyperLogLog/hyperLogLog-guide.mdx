# HyperLogLog — 다 세지 않고, 버킷마다 "가장 희귀했던 순간"만 기억하기

## 한눈에 보는 컨셉

HyperLogLog는 집합에 어떤 원소가 들어왔는지는 전혀 기억하지 않고, 서로 다른(유니크한) 원소가 몇 개였는지만 근사하는 확률적 자료구조예요. 비결은 "해시값에 선행 0이 많이 나오는 건 드문 사건이고, 드문 사건을 보려면 그만큼 많은 원소가 필요하다"는 확률론적 관찰을 $m$개의 버킷에 나눠 기록한 뒤, 극단값에 잘 흔들리지 않는 조화 평균으로 합치는 것입니다. 그 결과 수억 개 원소를 단 몇 KB의 메모리로, 표준 오차 $1.04/\sqrt{m}$ 이내에 추정할 수 있어 Redis의 `PFCOUNT`나 BigQuery의 `APPROX_COUNT_DISTINCT` 같은 기능의 핵심 엔진으로 쓰입니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 HyperLogLog를 떠올리세요.

- "정확한 개수"가 아니라 **오차를 허용하는 근사 카디널리티**로 충분하다는 요구가 명시돼 있다
- 원소 수가 너무 많아서(수백만 ~ 수억) `Set`/`HashSet`을 메모리에 그대로 올릴 수 없다
- 나중에 **여러 스트림·여러 날짜의 결과를 합쳐야** 한다(예: "이번 주 유니크 방문자 = 월~일 각각의 집합을 합집합")
- 원소 자체를 다시 나열할 필요는 없고, "몇 명/몇 개였는지" **숫자만** 필요하다

정확한 `Set`과 비교하면 메모리 격차가 극명합니다.

```text
정확한 Set(HashSet)                HyperLogLog
메모리: O(n)                       메모리: O(m) = O(log log n)
n=1억 유니크 문자열 → 수 GB        m=2^14=16384버킷 → 16KB
count(): O(1)                      count(): O(m)  (m은 수만 단위라 사실상 즉시)
정확도: 100%                       정확도: 근사, 오차 ≈ 1.04/√m
```

비슷한 목적의 확률적 자료구조와 헷갈릴 수 있어요. **존재 여부**(이 원소가 집합에 있었나?)만 필요하면 Bloom filter, **개별 원소의 등장 빈도**가 필요하면 Count-Min Sketch, **유니크 개수** 하나만 근사하면 충분하면 HyperLogLog를 고르세요.

### 문제 사례와 적용 예시

- **Redis `PFADD`/`PFCOUNT`/`PFMERGE`**: 내부적으로 HyperLogLog를 구현해 대규모 유니크 카운팅을 O(1)에 가까운 비용으로 제공합니다.
- **Google BigQuery `APPROX_COUNT_DISTINCT`, Spark `approx_count_distinct`**: 수십억 행짜리 SQL 집계에서 정확한 `COUNT(DISTINCT ...)` 대신 근사치를 빠르게 계산합니다.
- **네트워크 트래픽 분석**: 초당 수백만 패킷이 오가는 상황에서 유니크 소스 IP 수를 실시간 집계해 이상 트래픽(DDoS 등)을 탐지합니다.
- **코딩 테스트 맥락**: "끝없이 흘러오는 로그 스트림에서 유니크 사용자 수를 메모리 제약 안에서 근사하라" 류의 스트리밍 문제에서 직접 구현 대상이 됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드가 정의하는 인터페이스는 이렇습니다.

```ts
class HyperLogLog {
  private readonly p: number;       // precision, 4 <= p <= 16
  private readonly m: number;       // 버킷 수 = 2^p
  private readonly M: Uint8Array;   // M[j] = j번 버킷에서 관측된 최대 rho
  private readonly alphaM: number;  // 편향 보정 상수
}
```

`M`을 `Uint8Array`로 잡는 이유가 있어요. `rho`(선행 0 개수 + 1)의 이론적 최댓값은 `tail`의 비트 폭인 $32-p$보다 1 큰 $32-p+1$이고, $p \ge 4$라는 제약에서 이 값은 최대 29입니다. 1바이트(0~255)면 충분하고도 남아요. 일반 `number[]`를 쓰면 원소 하나에 8바이트(Float64)가 들어가니, `Uint8Array`로 바꾸는 것만으로 버킷 배열 메모리가 8분의 1로 줄어듭니다 — $m$이 수만 단위로 커지는 실무 정밀도(precision 12~14)에서 체감되는 최적화예요.

지켜야 할 불변식은 세 가지입니다.

1. $\forall j \in [0, m): 0 \le M[j] \le (32-p)+1$ — 버킷 값은 항상 이 범위 안에 있다(`rho`의 최댓값을 못 넘는다).
2. $M[j] = \max\{\rho(x) : x \in S,\ \mathrm{bucket}(x) = j\}$ — `add`를 몇 번을 호출하든 버킷 값은 절대 줄어들지 않는다(단조 비감소).
3. 두 인스턴스를 합칠 때 $M_{merged}[j] = \max(M_A[j],\ M_B[j])$ — 병합 결과의 각 버킷은 원본 두 버킷의 원소별 최댓값이다.

해시 32비트가 버킷 인덱스와 `rho` 계산용 꼬리로 어떻게 쪼개지는지 그려보면 이렇습니다.

```text
32비트 해시 h(x)
┌────────── p비트 ──────────┬─────────── (32-p)비트 ───────────┐
│       버킷 인덱스 j          │        rho 계산용 tail w           │
└────────────────────────────┴────────────────────────────────┘
   j = h >>> (32-p)              w = h & ((1 << (32-p)) - 1)

버킷 배열 M (m = 2^p개):
 [ M0 | M1 | M2 | ... | M(m-1) ]     각 칸은 Uint8Array (rho ≤ 29이므로 1바이트로 충분)
```

**액션(연산)** 4종입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `add(item)` | 해시 → 버킷/`rho` 계산 → 해당 버킷을 최댓값으로 갱신 | $O(1)$ |
| `count()` | $m$개 버킷의 조화 평균 + 소·대규모 보정 | $O(m)$ |
| `merge(other)` | 버킷별 최댓값으로 **새 인스턴스** 생성(원본 불변) | $O(m)$ |
| `error()` | $1.04/\sqrt{m}$ 반환 | $O(1)$ |

핵심 연산 세 개를 실제 값으로 자세히 따라가 볼게요(뒤의 실행 시각화와 같은 입력입니다).

**① `add` — 버킷 갱신과 "충돌 흡수".** `precision=3`(`m=8`)에서 `'alice'`를 넣으면:

```text
Before: M = [0, 0, 0, 0, 0, 0, 0, 0]

h('alice') = 10000111 00100010 00010011 11100111   (32비트, 실측)
             └ 상위 3비트 = 100 → j=4              └ 나머지 29비트의 선행 0 개수 → rho=3

After:  M = [0, 0, 0, 0, 3, 0, 0, 0]
```

바로 이어서 `'bob'`을 넣으면 우연히 **같은 버킷(j=4), 같은 rho=3**이 나옵니다.

```text
Before: M = [0, 0, 0, 0, 3, 0, 0, 0]
h('bob') → j=4, rho=3
max(기존 3, 새 3) = 3  →  변화 없음

After:  M = [0, 0, 0, 0, 3, 0, 0, 0]   (그대로!)
```

`bob`이 추가됐다는 정보 자체는 버킷에 남지 않아요 — HyperLogLog가 "몇 개 봤는지"가 아니라 "가장 희귀한 패턴이 뭐였는지"만 기억하는 자료구조라는 걸 이 장면이 잘 보여줍니다.

**② `count` — 조화 평균과 3단 보정.** `'carol'`, `'dave'`, `'eve'`까지 마저 넣으면 최종 버킷은 $M=[0,0,1,3,3,0,1,0]$입니다(뒤 실행 시각화에서 전 과정을 봅니다). 공식은 이렇습니다.

$$
Z = \frac{1}{\displaystyle\sum_{j=0}^{m-1} 2^{-M[j]}}, \qquad
E = \alpha_m\, m^2\, Z, \qquad
\alpha_m = \frac{0.7213}{1 + 1.079/m}\ \ (m \ge 128)
$$

$$
\hat{n} =
\begin{cases}
m \ln(m/V), & E \le \tfrac{5}{2}m \text{ 이고 } V>0 & (\text{선형 카운팅, } V = \text{빈 버킷 수}) \\[4pt]
E, & \tfrac{5}{2}m < E \le \tfrac{1}{30}\cdot 2^{32} \\[4pt]
-2^{32}\ln\!\left(1-\dfrac{E}{2^{32}}\right), & E > \tfrac{1}{30}\cdot 2^{32} & (\text{32비트 해시 충돌 보정})
\end{cases}
$$

$M=[0,0,1,3,3,0,1,0]$을 실제로 대입하면(직접 실행해 검증한 값입니다):

```text
sum(2^-M[j]) = 2^0+2^0+2^-1+2^-3+2^-3+2^0+2^-1+2^0 = 6.25
Z = 1/6.25 = 0.16
α_8 = 0.7213/(1+1.079/8) ≈ 0.63563
E(raw) = α_8 × 64 × 0.16 ≈ 6.508

분기 판정: E(raw)=6.508 ≤ 2.5×8=20 → 선형 카운팅 분기
V(빈 버킷 수) = 4개(인덱스 0,1,5,7)  →  V>0 이므로
E = 8 × ln(8/4) = 8 × ln 2 ≈ 5.545 → round → 6

count() = 6   (실제 유니크 원소 수 = 5)
```

원시 조화 평균값(6.508)이 아니라 **선형 카운팅으로 보정된 값(5.545 → 6)** 이 최종 반환값이라는 점이 포인트예요. $m=8$처럼 버킷이 아주 적을 때는 이 예시처럼 완벽히 들어맞지 않을 수 있습니다 — 그래서 실무에서는 precision을 10 이상으로 씁니다(뒤 코드 절에서 $n=100{,}000$ 규모로 오차 3.01%를 직접 확인합니다).

**③ `merge` — 버킷별 최댓값, 원본은 그대로.** `a`에 `'alice'`, `'bob'`을, `b`에 `'carol'`, `'dave'`, `'eve'`를 넣고 합치면(실측):

```text
a.M      = [0, 0, 0, 0, 3, 0, 0, 0]
b.M      = [0, 0, 1, 3, 0, 0, 1, 0]
merged.M = [0, 0, 1, 3, 3, 0, 1, 0]   ← 인덱스별 max(a, b)

merged.count() = 6
a.M (병합 후에도) = [0, 0, 0, 0, 3, 0, 0, 0]   ← 원본 불변 확인
```

`merged.M`이 정확히 5개 전부를 한 인스턴스에 넣었을 때의 $M$과 같다는 점을 눈여겨보세요 — 버킷별 max를 취하는 것만으로 "두 집합의 합집합"을 정확히 재현합니다.

### 왜 모순 없이 작동하는가

**단조성(불변식 2)이 보존되는 이유**는 귀납으로 보일 수 있어요. 빈 인스턴스는 모든 버킷이 0이라 자명하게 성립합니다. 어떤 시점에 불변식이 성립한다고 가정하고 `add(x)`를 한 번 더 호출하면, 코드는 `M[j] = max(M[j], rho(x))`만 실행합니다 — 기존 값보다 작으면 그대로 두고, 크면 그 값으로 바꾸죠. 어느 경우든 결과는 "지금까지 그 버킷에 들어온 모든 원소의 rho 중 최댓값"이라는 정의를 그대로 유지합니다. `merge`도 마찬가지로 두 유효한 배열의 원소별 max를 취할 뿐이므로, 결과 역시 "두 원본 집합을 합친 것"의 정의를 만족합니다.

**헷갈리기 쉬운 포인트**를 세 가지 짚어 둘게요.

- **`Math.clz32`는 항상 32비트 전체를 기준으로 선행 0을 셉니다.** `w = h & ((1 << (32-p)) - 1)`로 마스킹하면 `w`의 상위 `p`비트는 인위적으로 0이 됩니다. 이 상태에서 `rho = Math.clz32(w) + 1`처럼 `p`를 빼지 않고 그대로 쓰면, 그 인위적인 `p`개의 0비트까지 "선행 0"으로 잡혀버려요. `precision=10`(m=1024)에서 유니크 문자열 100,000개를 넣고 이 실수를 그대로 재현해 실행하면 `count()`가 **99,318,430**이 나옵니다 — 실제 값(100,000)의 993배입니다(직접 실행해 확인한 수치). 올바른 식은 `rho = Math.clz32(w) - p + 1`입니다.
- **`max` 비교를 빼먹고 덮어쓰면 단조성이 깨집니다.** `if (rho > M[j]) M[j] = rho`를 `M[j] = rho`로 바꾸면, 예를 들어 버킷에 `rho=3`이 기록된 뒤 같은 버킷에 `rho=1`짜리 원소가 들어오는 순간 버킷 값이 3에서 1로 **줄어듭니다**. 그러면 그 버킷이 실제보다 훨씬 흔한 패턴만 봤다고 착각해 `count()`가 실제보다 작게 나옵니다.
- **precision이 다른 두 인스턴스는 병합할 수 없습니다.** `m`이 다르면 버킷 개수 자체가 다르므로 인덱스가 서로 대응하지 않아요. 구현에서 `other.p !== this.p`를 명시적으로 막아야 조용히 틀린 값을 내놓는 사고를 피할 수 있습니다.

> 잠깐, 확인 하나만 해 볼까요? 원소를 하나도 넣지 않은 상태(모든 버킷이 0)에서 `count()`를 부르면 어떤 값이 나올까요?
>
> 정답: 모든 버킷이 비어 있으니 $V=m$(빈 버킷 수 = 전체 버킷 수)이고, $E(\text{raw}) \le 2.5m$이 항상 성립하니 선형 카운팅 분기로 들어갑니다. $E = m \ln(m/m) = m \ln 1 = 0$ — 실제로 실행해도 `count()`는 정확히 `0`입니다(직접 실행해 확인).

엣지 케이스를 점검해 봅시다.

```text
빈 구조(add 0번)          → M 전부 0 → count() = 0
precision 최솟값(4, m=16)  → error() ≈ 26%. 표본이 작을수록 선형 카운팅 보정이 자주 발동
precision 최댓값(16, m=65536) → error() ≈ 0.4%
동일 원소 중복 add          → 같은 (j, rho)가 반복 계산될 뿐 → M 변화 없음 → count() 불변(멱등)
서로 다른 precision끼리 merge → 버킷 개수 불일치 → 구현에서 명시적으로 막아야 하는 오용
```

## 아이디어를 코드로 옮기기

자연스러운 세 단계로 코드를 발전시켜 볼게요. **원형 → 개선 → 최종** 순서로, 각 단계에서 왜 다음 단계가 필요한지 실측값으로 확인합니다.

**원형(brute force): 정확한 `Set`.** 가장 단순하고 정확하지만 메모리가 원소 수에 비례합니다.

```ts
class ExactCounter {
  private seen = new Set<string>();
  add(item: string): void {
    this.seen.add(item);
  }
  count(): number {
    return this.seen.size;
  }
}
```

문자열 하나에 최소 수십 바이트가 든다고 하면, 유니크 원소 1억 개에서는 수 GB가 필요합니다. **목표**는 이걸 로그 스케일(KB 단위)로 줄이는 것입니다.

**개선 1단계: 버킷 없이 "가장 희귀한 관측 하나"로 추정.** 해시의 선행 0 개수가 클수록 드문 사건이라는 관찰만 가지고, 버킷을 나누지 않은 채 전체 원소 중 최댓값 하나로 승부해 봅니다.

```ts
class SingleObservationEstimator {
  private maxRho = 0;
  private hash(item: string): number {
    let h = 0x811c9dc5;
    for (let i = 0; i < item.length; i++) {
      h ^= item.charCodeAt(i);
      h = Math.imul(h, 0x01000193);
    }
    return h >>> 0;
  }
  add(item: string): void {
    const h = this.hash(item);
    const rho = Math.clz32(h) + 1; // 버킷 분할이 없으니 32비트 전체가 그대로 tail
    if (rho > this.maxRho) this.maxRho = rho;
  }
  count(): number {
    return 2 ** this.maxRho;
  }
}
```

메모리는 숫자 하나(`O(1)`)로 줄었지만, 대가가 있습니다. 이 방식을 5명(`alice`~`eve`)에 실제로 돌리면 `maxRho=2`가 나와 `count() = 4`(실제 5)로 그런대로 맞지만, 같은 방식을 `precision=10` 트레이스와 동일한 유니크 문자열 100,000개에 돌리면 `maxRho=18`이 나와 `count() = 2^18 = 262{,}144`(실제 100,000의 2.62배, 오차 162%)로 크게 빗나갑니다(직접 실행해 확인한 수치). **왜 다음 단계로 가는가**: 관측치를 딱 하나만 쓰면 "운 좋게 선행 0이 아주 많은 해시값" 하나가 전체 추정을 좌우해 버립니다 — 분산이 너무 큽니다. 분산을 줄이려면 독립적인 관측치를 여러 개 모아서 평균을 내야 합니다.

**최종: 버킷 $m$개로 나누고 조화 평균 + 보정.** 여러 개의 독립적인 "최댓값 관측치"(버킷마다 하나씩)를 모아 조화 평균을 내면 한 버킷의 극단값이 전체를 흔드는 힘이 줄어듭니다.

```ts
class HyperLogLog {
  private readonly p: number;
  private readonly m: number;
  private readonly M: Uint8Array;
  private readonly alphaM: number;

  constructor(precision: number = 10) {
    this.p = precision;
    this.m = 1 << precision;
    this.M = new Uint8Array(this.m);
    this.alphaM = 0.7213 / (1 + 1.079 / this.m);
  }

  private hash(item: string): number {
    let h = 0x811c9dc5; // FNV-1a 32비트 offset basis
    for (let i = 0; i < item.length; i++) {
      h ^= item.charCodeAt(i);
      h = Math.imul(h, 0x01000193); // FNV prime
    }
    return h >>> 0;
  }

  add(item: string): void {
    const h = this.hash(item);
    const j = h >>> (32 - this.p);
    const w = this.p === 32 ? 0 : h & ((1 << (32 - this.p)) - 1);
    // Math.clz32(w)는 항상 32비트 전체를 기준으로 선행 0을 센다.
    // w는 상위 p비트가 마스킹으로 이미 0인 상태이므로, 그 p개를 빼야
    // (32-p)비트짜리 실제 tail 안에서의 선행 0 개수가 된다.
    const rho = Math.clz32(w) - this.p + 1;
    if (rho > this.M[j]!) this.M[j] = rho;
  }

  count(): number {
    let sum = 0;
    let zeros = 0;
    for (let j = 0; j < this.m; j++) {
      sum += 2 ** -this.M[j]!;
      if (this.M[j] === 0) zeros++;
    }
    let E = (this.alphaM * this.m * this.m) / sum;

    if (E <= 2.5 * this.m) {
      if (zeros > 0) E = this.m * Math.log(this.m / zeros);
    } else if (E > (1 / 30) * 2 ** 32) {
      E = -(2 ** 32) * Math.log(1 - E / 2 ** 32);
    }
    return Math.round(E);
  }

  merge(other: HyperLogLog): HyperLogLog {
    if (other.p !== this.p) throw new Error("precision mismatch");
    const result = new HyperLogLog(this.p);
    for (let j = 0; j < this.m; j++) {
      result.M[j] = Math.max(this.M[j]!, other.M[j]!);
    }
    return result;
  }

  error(): number {
    return 1.04 / Math.sqrt(this.m);
  }
}
```

`precision=10`(m=1024)에서 유니크 문자열 100,000개를 넣고 직접 실행하면 `count() = 96,991`이 나옵니다 — 실제 100,000 대비 상대 오차 **3.01%**로, `error()`가 예측한 상한(3.25%) 안에 들어옵니다(직접 실행해 확인한 수치). 단일 관측치 방식의 오차 162%와 비교하면, 버킷을 나눠 평균을 내는 것만으로 정확도가 완전히 다른 수준이 된다는 걸 알 수 있어요.

가장 중요한 부분과 실수가 잦은 부분을 짚고 갈게요.

- **`const rho = Math.clz32(w) - this.p + 1;`** — 이 한 줄이 이 절 전체의 함정입니다. `- this.p`를 빼먹으면 위 "헷갈리기 쉬운 포인트"에서 본 것처럼 `count()`가 실제 값의 수백~수천 배로 폭주합니다.
- **`if (rho > this.M[j]!) this.M[j] = rho;`** — 반드시 `>` 비교 후 갱신(max)입니다. 무조건 대입하면 단조성이 깨져 `count()`가 실제보다 작게 나옵니다.
- `count()`의 분기 순서: 원시 `E`를 먼저 구하고, **작은 쪽(선형 카운팅) 조건을 먼저** 검사합니다. 순서를 바꿔 큰 쪽 보정을 먼저 검사하면 소규모 케이스에서 불필요한 대규모 보정 공식이 적용될 수 있습니다.

> 버킷은 "가장 놀라웠던 순간"만 기억한다 — 평범한 값이 나중에 와도 잊지 않는다(max).

정리하면, HyperLogLog는 "해시값의 선행 0 개수 = 드문 정도"라는 확률론적 관찰 하나를 $m$개의 버킷으로 나눠 독립적으로 관측하고, 극단값에 강한 조화 평균으로 합치는 두 가지 설계 결정으로 목표를 달성합니다. 버킷을 나누지 않은 단일 관측(개선 1단계)은 분산이 너무 커서 오차 162%까지 벌어졌지만, $m$개로 나눠 평균을 내는 최종 버전은 `precision=10`에서 오차 3.01%로 `error()`가 약속한 상한(3.25%) 안에 들어옵니다. `add`는 버킷 하나만 건드리므로 $O(1)$, `count`·`merge`는 버킷 전체를 훑으므로 $O(m)$이며, $m$이 원소 수 $n$과 무관하게 고정이라는 점이 바로 "메모리가 $n$이 아니라 $\log\log n$ 수준으로 줄어든다"는 이 자료구조의 핵심 효과입니다.

## 스스로 점검하기

1. `precision=2`(`m=4`버킷)에서 해시값의 상위 2비트로 버킷을, 나머지 30비트의 선행 0 개수로 `rho`를 구한다고 합시다. 세 원소를 추가했더니 버킷 인덱스/`rho` 쌍이 각각 `(j=0, rho=1)`, `(j=2, rho=4)`, `(j=0, rho=3)`이 나왔습니다. 최종 `M` 배열을 손으로 채우고, `count()`가 어느 보정 분기(선형 카운팅/원시값/대규모 보정)로 계산될지 판단해 보세요.
2. `add`에서 `if (rho > M[j]) M[j] = rho` 대신 항상 `M[j] = rho`로 덮어쓴다면, `'alice'`(버킷 4, rho=3)를 넣은 다음 우연히 같은 버킷에 rho=1인 원소를 넣었을 때 `M[4]`는 어떻게 바뀌고, 그 결과 `count()`는 실제보다 커질까요 작아질까요?
3. 본문 최종 구현의 `rho = Math.clz32(w) - this.p + 1`에서 `- this.p`를 빼먹은 채로 `precision=10`, 유니크 원소 100,000개를 넣고 `count()`를 호출하면 어떤 자릿수의 값이 나올지 먼저 예측해 보고, 본문에 실측으로 적힌 수치와 비교해 보세요.
