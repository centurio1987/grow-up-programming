# Count-Min Sketch — 여러 번 겹쳐 세고, 가장 깨끗한 값만 믿는다

## 한눈에 보는 컨셉

원소별 정확한 빈도를 저장하는 대신, $d \times w$ 크기의 작은 정수 행렬 하나만 유지하면서 $d$개의 독립 해시로 값을 겹쳐서 셉니다. 조회할 때는 그 원소가 해시된 $d$개 칸 중 **최솟값**을 돌려주는데, 이 한 번의 선택이 해시 충돌로 인한 과대추정을 크게 눌러줍니다. 카운터는 오직 증가만 하므로 추정값은 항상 실제 빈도 이상이라는 것(과소추정 없음)이 수학적으로 보장되고, 이 성질 덕분에 "많이 등장한 원소만 정확하면 되는" 스트리밍 집계 문제의 표준 도구가 되었습니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 겹치면 Count-Min Sketch를 떠올리세요.

- 스트림에 등장하는 **고유 원소 종류가 너무 많아서** 전부 저장하면 메모리가 감당 안 된다
- "정확한 빈도"보다 **빈도 상위 원소(Heavy Hitter)** 를 가려내는 것이 진짜 목적이다
- 메모리 상한은 고정하고 싶은데, 입력 스트림의 길이나 고유 원소 수는 사전에 알 수 없다
- 오차가 있어도 **과소추정만은 절대 안 되는** 요구사항이다(과대추정은 허용)

정확한 `Map<string, number>` 카운팅과 비교하면 공간 사용의 성격 자체가 다릅니다.

```text
Map<string, number> 기반 정확 카운팅     공간 O(u)   ← u = 고유 원소 수, 무한정 증가 가능
Count-Min Sketch (w × d 행렬)            공간 O(w·d) ← 스트림 길이·고유 원소 수와 무관하게 고정
```

$w = 10^4$, $d = 16$이면 카운터는 $1.6 \times 10^5$개이고, 정수 4바이트 기준으로 약 640,000바이트(640KB)면 충분합니다. 고유 IP가 수백만 개인 네트워크 트래픽이라도 이 크기는 그대로예요 — **정확도를 조금 포기하고 공간을 스트림 크기와 분리시킨 것**이 핵심 트레이드오프입니다. 정확도 파라미터 $\varepsilon$(허용 오차 비율)과 실패 확률 $\delta$로부터 $w = \lceil e/\varepsilon \rceil$, $d = \lceil \ln(1/\delta) \rceil$을 계산해서 이 트레이드오프를 조절합니다.

비슷한 목적의 확률적 자료구조와 헷갈릴 수 있는데, 묻고 싶은 질문으로 구분하면 쉽습니다: **존재 여부만 궁금하면 Bloom Filter, 고유 원소 "개수"(카디널리티)만 궁금하면 HyperLogLog, 원소별 "등장 횟수"(빈도) 자체가 궁금하면 Count-Min Sketch**를 씁니다.

### 문제 사례와 적용 예시

- **네트워크 트래픽 Heavy Hitter 탐지**: 초당 수백만 패킷이 오가는 라우터에서 특정 출발지 IP의 요청 횟수를 추적합니다. 자주 등장하는 IP(공격자 후보, 인기 서비스)는 추정값이 실제와 거의 일치하고, 희귀 IP는 오차가 있어도 탐지 목적엔 지장이 없습니다.
- **캐시 교체 정책(TinyLFU 계열)**: 캐시에 새 항목을 넣을지 결정할 때 "이 키가 최근 얼마나 자주 요청됐는가"를 Count-Min Sketch로 근사해, 정확한 LFU 카운터를 위한 큰 메모리를 쓰지 않습니다.
- **검색 로그 상위 쿼리 집계**: 하루 수억 건의 검색어 로그에서 인기 검색어 순위를 추정할 때, 모든 검색어를 해시 맵에 쌓는 대신 고정 크기 스케치로 근사치를 냅니다.
- **코딩 테스트 맥락**: "스트림 길이 $n \leq 10^5$, 고유 원소 수는 알 수 없음. 원소별 등장 횟수를 과소추정 없이 근사하라" — 정확한 집계 자료구조 없이 고정 크기 자료구조로 근사해야 하는 문제로 출제됩니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

이 가이드가 정의하는 인터페이스는 다음과 같습니다.

```ts
class CountMinSketch {
  constructor(width: number, depth: number)
  update(item: string, count: number): void
  estimate(item: string): number
}
```

| 파라미터 | 의미 | 제약 |
|---------|------|------|
| `width` | 각 행의 카운터 수 $w$ | $1 \leq w \leq 10^4$ |
| `depth` | 해시 함수(행) 수 $d$ | $1 \leq d \leq 16$ |
| `item` | 빈도를 갱신·조회할 문자열 원소 | 임의 문자열 |
| `count` | 이번 `update`에서 더할 등장 횟수 | $\geq 1$ |

**속성(내부 상태)** — $d \times w$ 정수 행렬 하나가 전부입니다.

```ts
class CountMinSketch {
  private counters: number[][];   // counters[j][k], j ∈ [0,d), k ∈ [0,w)
  private width: number;
  private depth: number;
}
```

각 행 $j$는 독립 해시 함수 $h_j$ 하나에 대응합니다.

$$C \in \mathbb{Z}_{\geq 0}^{d \times w}, \quad h_j : \Sigma^* \to [0, w), \quad j = 0, 1, \ldots, d-1$$

`width = 4`, `depth = 3`일 때 행렬을 그려보면 이렇습니다.

```text
        col0  col1  col2  col3
h0    [  0     0     0     0  ]
h1    [  0     0     0     0  ]
h2    [  0     0     0     0  ]

한 원소 x는 각 행에서 정확히 한 칸(h_j(x) mod w)을 갖는다 — 총 d개의 목격 지점.
```

지켜야 할 불변식은 두 가지입니다.

1. **단조성**: 모든 카운터는 0에서 시작해 오직 증가만 한다. $C[j][k]$는 감소하지 않는다.
2. **하한 불변식**: 임의 시점에서 모든 $j \in [0, d)$에 대해 $C[j][h_j(x) \bmod w] \geq f(x)$가 성립한다. 여기서 $f(x)$는 지금까지 `update`로 누적된 $x$의 실제 빈도.

**액션(연산)** — 이 자료구조가 제공하는 연산은 두 개뿐입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `update(item, count)` | $d$개 행 각각의 해당 칸에 `count`를 더한다 | $O(d)$ |
| `estimate(item)` | $d$개 행의 해당 칸 값 중 최솟값을 반환한다 | $O(d)$ |

$d \leq 16$이므로 사실상 $O(1)$이고, 스트림 전체 처리는 $O(nd)$입니다($n$ = 스트림 이벤트 수).

핵심 연산인 `update`를 before/after로 자세히 봅니다. `width=4, depth=3`에서 `update("ip_a", 3)`을 실행하면, $h_j(\text{"ip\_a"})$가 각각 $3, 3, 2$인 경우(뒤에서 실제 해시로 검증합니다):

```text
Before                              After update("ip_a", 3)
        c0 c1 c2 c3                        c0 c1 c2 c3
h0   [   0  0  0  0 ]                h0 [   0  0  0  3 ]  ← col3 += 3
h1   [   0  0  0  0 ]                h1 [   0  0  0  3 ]  ← col3 += 3
h2   [   0  0  0  0 ]                h2 [   0  0  3  0 ]  ← col2 += 3
```

세 행이 서로 다른 칸(3, 3, 2)을 가리키는 게 아니라 **같은 원소인데 행마다 다른 위치**를 가리킨다는 점에 주목하세요 — 이게 "독립 해시 $d$개"의 실체입니다.

### 왜 모순 없이 작동하는가

**하한 불변식이 보존되는 이유(귀납)**: 빈 스케치는 모든 칸이 0이므로 모든 원소에 대해 $f(x) = 0 = C[j][\cdot]$로 불변식이 성립합니다(기저). 이제 `update(y, c)`가 한 번 더 일어났다고 합시다.

- $y = x$인 경우: $f(x)$가 $c$만큼 늘고, $C[j][h_j(x)]$도 정확히 $c$만큼 늘어납니다(같은 칸이 갱신되므로). 양쪽이 같이 늘어나니 부등식 방향은 그대로 유지됩니다.
- $y \neq x$인 경우: $f(x)$는 그대로인데, 해시 충돌로 $h_j(y) = h_j(x)$라면 $C[j][h_j(x)]$가 오히려 더 커집니다. 부등식은 더 여유 있게 성립합니다.

두 경우 모두 $C[j][h_j(x)] \geq f(x)$가 깨지지 않으므로, 임의 시점 · 임의 행에서 불변식이 유지됩니다. `estimate`는 이 $d$개 값의 최솟값을 취하는데, 최솟값도 각 항 이상은 아니므로(최솟값 ≤ 각 항이지만, 각 항이 이미 $f(x)$ 이상이니) 여전히 $\hat{f}(x) = \min_j C[j][h_j(x)] \geq f(x)$입니다. **과소추정은 구조적으로 불가능합니다.**

**여기서 헷갈리기 쉬운 포인트 첫 번째는 min과 max를 혼동하는 것입니다.** "여러 행을 봤으니 더 큰 값이 더 믿을 만하지 않나?"라고 생각하기 쉬운데, 정반대입니다. 충돌은 값을 실제보다 부풀리기만 하지 줄이지는 않으므로, **가장 적게 오염된(=가장 작은) 값이 실제에 가장 가깝습니다.** 앞서 계산한 대표 시나리오에서 실제로 확인해 보면, `estimate("ip_b")`를 구할 때 세 행의 값이 $[2, 6, 2]$였습니다. 만약 실수로 max를 썼다면 $6$을 반환했을 텐데, 이는 실제 빈도 $2$의 3배에 달하는 심각한 과대추정입니다. min을 쓰면 정확히 $2$가 나옵니다(실측: 뒤의 실행 시각화에서 그대로 확인됩니다).

**두 번째 헷갈리기 쉬운 포인트는 "행을 늘리면 오차가 0이 된다"는 오해입니다.** $d$를 늘리는 것은 오차를 없애는 게 아니라 **큰 오차가 날 확률을 지수적으로 줄이는 것**입니다. 행 하나가 임계 오차 $\varepsilon N$을 넘길 확률이 대략 $1/e$ 미만이라면, $d$개 행이 전부 동시에 그 임계를 넘길 확률은 $(1/e)^d$로 지수 감소합니다. 그래도 확률이 정확히 0이 되지는 않아요 — 확률적 보장이지, 결정적 보장이 아닙니다.

**세 번째 헷갈리기 쉬운 포인트는 "$w$를 넓히면 $d$가 필요 없다"는 오해입니다.** $w$(폭)는 한 행에서 발생하는 오차의 **크기**($\varepsilon N$)를 줄이고, $d$(깊이)는 그 오차가 **동시에 모든 행에서** 발생할 **확률**($\delta$)을 줄입니다. 둘은 서로 다른 축을 제어하므로 하나만 키워서는 다른 쪽 보장을 얻을 수 없습니다.

잠깐, 확인 질문 하나 — `width = 1, depth = 1`인 극단적인 스케치에 `update("x", 5)`, `update("y", 7)`을 차례로 호출하면 `estimate("x")`와 `estimate("y")`는 각각 무엇을 반환할까요? 답: **둘 다 12를 반환합니다.** 칸이 하나뿐이라 모든 원소가 `counters[0][0]`에 합쳐지기 때문에, 사실상 "전체 이벤트 합산 카운터"가 되어버립니다(실측: 스크래치 실행에서 `x=12, y=12` 확인).

엣지 케이스를 마저 점검합니다.

```text
width = 1                  → 모든 원소가 같은 칸을 공유. 오차가 최대.
depth = 1                  → 보정할 다른 행이 없음. 충돌이 나면 그대로 부풀려진 값을 반환.
update 안 한 원소 조회       → 모든 칸이 0이므로 estimate = 0 (실측: 검증됨)
동일 원소 여러 번 update     → count가 그대로 누적. update(x,3) 후 update(x,1) → 실제 빈도 4.
스트림 총합 N이 매우 큰 경우  → 오차 상한 εN도 함께 커져 희귀 원소의 추정 정확도가 떨어짐.
```

## 아이디어를 코드로 옮기기

세 단계로 좁혀갑니다: **정확하지만 무거운 원형 → 가볍지만 보정이 없는 개선 1 → 여러 행 + 최솟값으로 보정하는 최종판.**

**원형 — 정확한 카운팅.** 가장 단순한 방법은 해시 맵에 원소별 정확한 빈도를 저장하는 것입니다.

```ts
class ExactCounter {
  private counts = new Map<string, number>();

  update(item: string, count: number): void {
    this.counts.set(item, (this.counts.get(item) ?? 0) + count);
  }

  estimate(item: string): number {
    return this.counts.get(item) ?? 0;
  }
}
```

정확도는 완벽하지만 공간이 고유 원소 수 $u$에 비례해 무한정 자랍니다. **폭발 지점**: 정확한 빈도를 유지하는 한 공간을 줄일 방법이 없습니다.

**개선 1 — 단일 해시 배열로 압축.** 정확도를 조금 포기하고, 고정 크기 배열 하나에 해시로 눌러 담아 봅니다.

```ts
class SingleRowSketch {
  private counters: number[];

  constructor(private readonly width: number) {
    this.counters = new Array(width).fill(0);
  }

  private position(item: string): number {
    return hashToRange("1:" + item, this.width); // 아래 최종판의 해시 함수 재사용
  }

  update(item: string, count: number): void {
    this.counters[this.position(item)] += count;
  }

  estimate(item: string): number {
    return this.counters[this.position(item)]; // 보정 수단이 없다 — 충돌나면 그대로 반환
  }
}
```

공간은 $O(w)$로 고정됐지만, 두 원소가 같은 칸에 충돌하면 **되돌릴 방법이 없습니다.** `width=4`인 스케치에 `update("ip_a", 3)`, `update("ip_b", 2)`, `update("ip_a", 1)`을 순서대로 넣으면 `"ip_a"`와 `"ip_b"`가 같은 칸에서 충돌해(실측: 뒤에서 검증), `estimate("ip_b")`가 실제 빈도 $2$가 아니라 $6$을 반환합니다 — 실제의 3배. **관찰**: 이 문제를 없앨 수는 없지만, 서로 다른 해시로 여러 번 반복하고 그중 가장 오염이 적은(작은) 값을 취하면 오차를 줄일 수 있습니다.

**최종 — 여러 행 + 최솟값.**

```ts
class CountMinSketch {
  private width: number;
  private depth: number;
  private counters: number[][];

  constructor(width: number, depth: number) {
    this.width = width;
    this.depth = depth;
    this.counters = Array.from({ length: depth }, () => new Array(width).fill(0));
  }

  private djb2(s: string): number {
    let h = 5381 >>> 0;
    for (let i = 0; i < s.length; i++) {
      h = (Math.imul(h, 33) + s.charCodeAt(i)) >>> 0;
    }
    return h;
  }

  private mix(h: number): number {
    h = h >>> 0;
    h ^= h >>> 16;
    h = Math.imul(h, 0x85ebca6b) >>> 0;
    h ^= h >>> 13;
    h = Math.imul(h, 0xc2b2ae35) >>> 0;
    h ^= h >>> 16;
    return h >>> 0;
  }

  private position(row: number, item: string): number {
    return this.mix(this.djb2(`${row}:${item}`)) % this.width; // row를 salt로 섞어 행마다 독립적인 해시를 만든다
  }

  update(item: string, count: number): void {
    for (let j = 0; j < this.depth; j++) {
      const pos = this.position(j, item);
      this.counters[j][pos] += count;      // 무조건 더한다 — 감소는 절대 없다
    }
  }

  estimate(item: string): number {
    let result = Infinity;
    for (let j = 0; j < this.depth; j++) {
      const pos = this.position(j, item);
      result = Math.min(result, this.counters[j][pos]); // 무조건 최솟값
    }
    return result;
  }
}
```

**가장 중요한 부분은 `position` 메서드에서 `row`를 문자열 앞에 붙여 해시에 섞는 것입니다.** `` `${row}:${item}` ``처럼 행 번호를 해시 입력에 포함시키지 않고 모든 행이 `djb2(item)`만 사용하면, $d$개 행이 사실상 똑같은 위치에 똑같은 패턴으로 충돌합니다. 그러면 `min`을 아무리 여러 행에 대해 계산해도 값이 똑같으니 오차 보정 효과가 전혀 없습니다 — 행을 늘린 게 헛수고가 되는 거예요. 그리고 `update`의 `+=`와 `estimate`의 `Math.min`, 이 두 방향성이 정확도 보장의 전부입니다.

> 넣을 땐 다 더하고, 꺼낼 땐 가장 작은 목격자만 믿는다.

## 실행 시각화

`width = 4`, `depth = 3`인 스케치에 `update("ip_a", 3)`, `update("ip_b", 2)`, `update("ip_a", 1)`을 차례로 실행한 뒤 `estimate("ip_a")`, `estimate("ip_b")`를 조회합니다. 실제 해시 위치는 `position(j, item)`을 그대로 실행해서 얻었습니다: `ip_a`는 행별로 $[3, 3, 2]$, `ip_b`는 $[2, 3, 0]$ — 행1(h1)의 열3에서 두 원소가 충돌합니다. matrix 패널은 $d \times w$ 카운터 행렬이고, 강조된 셀(`cells`)은 현재 원소가 매핑된 $d$개 위치입니다. 실제 반환값은 `estimate("ip_a") = 4`(실제 빈도와 일치), `estimate("ip_b") = 2`(충돌난 행1의 값 6을 min이 걸러내 정확한 값을 회복)이며, 아래 스크래치 실행 로그와 정확히 일치합니다.

## 스스로 점검하기

1. `width = 6, depth = 2`인 스케치에 `update("p", 4)`, `update("q", 5)`를 순서대로 넣었더니 우연히 두 행 모두에서 `"p"`와 `"q"`가 같은 칸에 충돌했습니다. 이때 `estimate("p")`와 `estimate("q")`는 각각 얼마가 나올까요? (힌트: 두 행 모두 충돌하면 min이 보정할 다른 행이 없습니다)
2. 본문의 대표 시나리오에서, `estimate` 구현이 실수로 `Math.min` 대신 배열의 **첫 번째 행 값만** 반환하도록 바뀌었다고 합시다. `estimate("ip_a")`와 `estimate("ip_b")`의 결과가 각각 어떻게 달라질까요? 실제 실행 로그의 행렬 값을 보고 계산해 보세요.
3. `position(row, item)` 구현에서 `` `${row}:${item}` `` 대신 그냥 `item`만 해시한다면(행 번호를 섞지 않는다면), `depth`를 3에서 10으로 늘려도 정확도가 왜 전혀 개선되지 않는지 한 문장으로 설명해 보세요.
