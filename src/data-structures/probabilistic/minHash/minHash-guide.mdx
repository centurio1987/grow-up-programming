# MinHash — 무작위 해시 하나의 최솟값이 집합 전체를 대신한다

## 한눈에 보는 컨셉

두 집합이 얼마나 겹치는지(Jaccard 유사도)를 원본 집합 없이, 정수 몇 개짜리 **서명(signature)** 만으로 근사하는 확률적 해시 기법이에요. 비결은 하나입니다 — 무작위 해시 함수를 여러 개 준비해 각각의 최솟값만 남기면, "두 집합의 최솟값이 같을 확률"이 곧 Jaccard 유사도와 같아집니다. 그 결과 원본을 몇 KB씩 들고 비교하던 일이, 정수 배열 하나(`O(k)`)를 비교하는 일로 줄어듭니다.

## 언제, 왜 쓰는가

### 이런 단서가 보이면

다음 신호가 보이면 MinHash를 떠올리세요.

- 두 데이터(문서, 태그 집합, 방문 URL 집합 등)가 **대략 얼마나 겹치는지**를 대량으로, 반복적으로 물어야 한다
- 원본 집합을 계속 들고 비교하기엔 **메모리·비교 비용**이 부담스럽다(집합 하나가 수천 개 원소)
- 정확한 교집합/합집합이 아니라 **근사값으로 충분**하다(중복 탐지, 클러스터링 후보 스크리닝 등)

정확한 Jaccard는 두 집합을 직접 비교해야 해서 원소 수에 비례하는 비용이 듭니다. MinHash는 이 비용을 서명 길이 `k`로 고정시켜 버립니다.

```text
naive: 두 집합 직접 비교      O(min(|A|,|B|)) 시간, O(|A|+|B|) 메모리(원본 통째로 보관)
MinHash: 서명(k개 정수) 비교   O(k) 시간, O(k) 메모리(서명만 보관)

문서 100만 개, 평균 1,000 단어, k=128이라면:
  원본 저장   : 100만 × 1,000단어 × 평균 8바이트 ≈ 8 GB
  서명 저장   : 100만 × 128개 정수 × 8바이트     ≈ 1 GB
  쌍별 비교   : 원본 비교 O(1,000) vs 서명 비교 O(128) → 약 8배 빠르고,
               LSH(구간 나눠 버킷팅)와 결합하면 전수비교 자체를 생략할 수 있다
```

비슷한 목적의 도구와 헷갈리지 않도록 기준을 하나 둡니다. **"집합 소속 여부"의 겹침**을 재려면 MinHash, **벡터의 방향(코사인 유사도)**을 재려면 SimHash를 씁니다. Bloom Filter는 "이 원소가 집합에 있는가"만 답할 뿐 두 집합의 유사도는 재지 못해요 — 애초에 목적이 다릅니다.

### 문제 사례와 적용 예시

- **검색엔진의 near-duplicate 탐지**: 뉴스 재배포, 미러 사이트, 스팸 페이지처럼 내용이 거의 같은 문서를 단어 집합의 서명 비교만으로 걸러냅니다.
- **추천 시스템**: 사용자별 관심 태그 집합의 유사도로 협업 필터링 후보를 빠르게 좁힙니다.
- **표절/중복 코드 탐지**: 문서나 코드를 n-gram 집합으로 바꾼 뒤 서명 비교로 1차 스크리닝합니다.
- **코딩 테스트 맥락**: "집합 쌍이 수백만 개인데, 유사도 0.8 이상인 쌍만 찾아라"처럼 전수비교가 애초에 불가능한 규모의 문제에서 등장합니다.

## 자료구조 자세히 들여다보기

### 전체 스펙: 속성과 액션

**속성(내부 상태)**은 다음 네 가지입니다.

```text
MinHash 인스턴스
┌───────────────────────────────────────────┐
│ k     : 4                    (해시 함수 개수)  │
│ a[]   : [a0, a1, a2, a3]     (곱셈 계수, 홀수) │
│ b[]   : [b0, b1, b2, b3]     (덧셈 계수)      │
│ sig[] : [s0, s1, s2, s3]     (현재 서명)      │
└───────────────────────────────────────────┘
      h_i(x) = (a_i · fnv1a(x) + b_i) mod P
```

지켜야 할 불변식은 세 가지예요.

1. $\text{sig}[i] = \min_{x \in S} h_i(x)$ — $S$는 가장 최근 `update`에 전달된 집합. $S = \emptyset$이면 $\text{sig}[i] = +\infty$.
2. $h_i(x) = (a_i \cdot \text{fnv1a}(x) + b_i) \bmod P$, $P = 2^{31}-1$(메르센 소수).
3. **모든 MinHash 인스턴스가 같은 $\{(a_i, b_i)\}_{i=0}^{k-1}$ 계열을 공유**해야, 서로 다른 인스턴스의 서명 비교가 의미를 가집니다.

**액션(연산)**은 문제 인터페이스가 요구하는 4종 전부입니다.

| 액션 | 하는 일 | 비용 |
|------|---------|------|
| `update(set)` | 서명을 처음부터 다시 계산(이전 서명 덮어씀) | $O(n \cdot k)$ |
| `signature()` | 현재 서명 배열의 복사본 반환 | $O(k)$ |
| `MinHash.jaccard(a, b)` (static) | 두 서명을 자리별로 비교해 일치 비율 반환 | $O(k)$ |
| `MinHash.exact(a, b)` (static) | 두 `Set`의 실제 교집합/합집합 비율 계산(검증용) | $O(n + m)$ |

핵심 연산은 `update`예요. 집합 A = {'apple', 'banana', 'cherry'}, k=4로 실제 계산한 값을 따라가 봅시다(아래 코드를 그대로 실행한 결과입니다).

**Before**(원소 처리 전): `sig = [+∞, +∞, +∞, +∞]`

`'apple'`을 처리하면 `h('apple') = [221110886, 1723428888, 373011792, 1122902441]`. 전부 $+\infty$보다 작으니 네 자리 모두 갱신됩니다.

```text
Before: [ +∞,        +∞,         +∞,        +∞        ]
After:  [ 221110886, 1723428888, 373011792, 1122902441 ]   ← apple이 4자리 모두 차지
```

이어서 `'banana'`를 처리하면 `h('banana') = [414808902, 2045917703, 494993347, 1983190097]`. 네 값 모두 현재 서명보다 **커서 아무 자리도 갱신되지 않습니다** — 원소를 실제로 처리했다고 해서 서명에 반드시 기여하는 건 아니에요.

```text
Before: [ 221110886, 1723428888, 373011792, 1122902441 ]
After:  [ 221110886, 1723428888, 373011792, 1122902441 ]   ← banana는 흔적을 남기지 못함
```

마지막으로 `'cherry'`: `h('cherry') = [541046940, 1526040473, 1666286719, 307308684]`. idx1(1526040473 < 1723428888)과 idx3(307308684 < 1122902441)만 더 작아 갱신됩니다.

```text
Before: [ 221110886, 1723428888, 373011792, 1122902441 ]
After:  [ 221110886, 1526040473, 373011792, 307308684  ]   ← idx1, idx3만 cherry로 교체
```

집합 A의 최종 서명은 `[221110886, 1526040473, 373011792, 307308684]`입니다.

### 왜 모순 없이 작동하는가

**`sig`가 항상 "지금까지 본 원소들의 자리별 최솟값"이라는 불변식이 보존되는 이유**는 간단한 귀납으로 확인됩니다. 원소를 0개 처리했을 때 `sig[i] = +\infty`이고, 이는 빈 집합의 최솟값이라는 수학적 관례와 일치합니다(base case). $t$개를 처리한 뒤 `sig[i]`가 그 $t$개에 대한 최솟값이라고 가정하면, $(t{+}1)$번째 원소 $x$를 처리할 때 `sig[i] = min(sig[i], h_i(x))`로 갱신하므로 결과는 정확히 $t{+}1$개에 대한 최솟값입니다(inductive step). 그래서 `update`가 끝난 시점의 `sig`는 항상 전체 집합에 대한 자리별 최솟값이에요.

이제 "왜 서명 비교가 Jaccard를 추정하는가"를 봅시다. 전체 원소를 $U = A \cup B$로 두고, 무작위 순열 $\pi$를 $U$에 적용한다고 상상해 보세요.

```text
π(U) 순서:   ...  x2   x5   x1   x4   x3  ...
                   ↑
              가장 먼저 오는 원소 (= argmin)

이 원소가 A∩B에 속할 확률 = |A∩B| / |A∪B| = J(A, B)

이 원소가 A에만 속하면: min(h(A)) = 그 값 < min(h(B))  → 불일치
이 원소가 B에만 속하면: min(h(A)) > min(h(B)) = 그 값  → 불일치
이 원소가 A∩B에 속하면: min(h(A)) = min(h(B)) = 그 값  → 일치
```

즉 $P[\min h(A) = \min h(B)] = J(A, B)$입니다. 해시 함수 하나는 무작위 순열의 근사이므로, 이 등식이 $h_i$ 각각에 대해 (근사적으로) 성립합니다. $k$개의 독립적인 해시 함수로 얻은 $k$번의 베르누이 시행을 평균 내면 — 즉 `matches / k` — $J(A,B)$의 불편 추정량이 됩니다. 분산은 $\mathrm{Var}[\hat J] = \dfrac{J(1-J)}{k}$이고, 표준오차는 $\sqrt{J(1-J)/k} \le \dfrac{1}{2\sqrt{k}}$입니다.

실제로 이걸 확인해 볼까요? A, B(위 예시, k=4)의 추정 Jaccard는 `matches/k = 2/4 = 0.5`이고, 실제(exact) Jaccard도 `|{apple,cherry}| / |{apple,banana,cherry,durian}| = 2/4 = 0.5`로 **정확히 일치**합니다. k=4처럼 작을 때 이렇게 딱 맞아떨어지는 건 필연이 아니라 우연입니다 — 표본이 작을수록 우연한 일치·불일치가 잦거든요. 표본이 큰 경우로 확인해 보면, 원소 200개짜리 두 집합(100개 겹침, 합집합 300개, 실제 Jaccard = 1/3 ≈ 0.3333)을 k=256으로 측정했을 때 추정값은 0.3516이 나왔습니다. 오차는 약 0.0182로, 예측된 표준오차 상한 $1/(2\sqrt{256}) = 0.03125$ 안에 들어옵니다.

**헷갈리기 쉬운 포인트**를 두 가지 짚어 둘게요.

- **인스턴스마다 다른 $a_i, b_i$를 쓰면 비교 자체가 무의미해집니다.** 만약 생성자가 매번 새 무작위 시드로 $a_i, b_i$를 뽑는다면, **완전히 같은 집합**을 두 인스턴스에 넣어도 서명이 어긋날 수 있습니다. 실측으로 확인해 보면 — 같은 시드를 쓴 두 인스턴스는 동일 집합에 대해 `matches = 8/8`(추정 Jaccard = 1.0, 정답)이지만, 시드가 다른 두 인스턴스는 같은 집합인데도 `matches = 0/8`(추정 Jaccard = 0.0, 완전히 틀림)이 나옵니다. 해시 계열은 인스턴스 개인 소지품이 아니라 **모든 인스턴스가 공유해야 하는 규칙**입니다.
- **빈 집합 두 개의 Jaccard = 1이라는 관례가 직관과 부딪힐 수 있습니다.** "겹치는 게 없으니 0 아닌가?"라고 생각하기 쉽지만, 두 빈 집합은 교집합도 합집합도 공집합이라 $0/0$이 되어 정의가 안 됩니다. 수학적 관례로 이 경우를 1로 정의해서 "완전히 같은 집합(둘 다 텅 빈 상태로 같음)"으로 취급합니다.

확인 질문 하나 — k=4일 때 A, B의 추정치가 exact와 정확히 같았는데, 이게 "k가 작아도 항상 정확하다"는 뜻일까요? 아니요. 방금 본 k=256 사례처럼 k가 커질수록 오차가 **예측 가능한 범위 안으로** 좁혀지는 것이지, k가 작을 때 우연히 맞은 것을 일반화할 수는 없습니다.

엣지 케이스를 점검해 봅시다.

```text
update([]) 호출                   → sig = [+∞, +∞, ...] (원소가 없으니 최솟값도 없음)
두 빈 집합의 jaccard               → +∞ === +∞이므로 matches = k → 추정 1.0 (exact 관례와 일치)
numHashes = 1                     → 서명 길이 1, 추정값은 0 또는 1만 가능 (표준오차가 매우 큼)
동일 집합을 순서만 바꿔 update      → 최솟값 연산은 순서 무관 → 서명 완전히 동일 (실측 확인됨)
update를 두 번 호출                → 이전 서명은 버려지고 최신 집합 기준으로 재계산됨
```

## 아이디어를 코드로 옮기기

문제 인터페이스(`constructor(numHashes)`, `update`, `signature`, 정적 `jaccard`/`exact`)에 맞춰 구현합니다. `update`가 어떻게 지금의 형태에 이르렀는지 진화 단계를 따라가 볼게요.

**원형(비효율)** — 해시 함수마다 집합을 처음부터 다시 훑습니다.

```ts
// 원형: 바깥 루프가 해시 함수, 안쪽 루프가 원소 — fnv1a를 (i, x) 조합마다 재계산
function updateNaive(
  set: Iterable<string>,
  k: number,
  a: number[],
  b: number[],
  PRIME: number,
): number[] {
  const items = Array.from(set);
  const sig = new Array(k).fill(Infinity);
  for (let i = 0; i < k; i++) {
    for (const x of items) {
      const base = BigInt(fnv1a(x)); // (i, x) 조합마다 매번 재계산!
      const h = Number((BigInt(a[i]!) * base + BigInt(b[i]!)) % BigInt(PRIME));
      if (h < sig[i]!) sig[i] = h;
    }
  }
  return sig;
}
```

`fnv1a` 호출이 $n \cdot k$번입니다. $n=10{,}000$, $k=128$이면 1,280,000번 — 원소 수와 해시 함수 수가 함께 커지면 비용이 곱으로 폭발해요.

**개선** — 루프 순서를 뒤집어 원소당 `baseHash`를 한 번만 계산합니다.

```ts
// 개선: 바깥 루프가 원소, 안쪽 루프가 해시 함수 — fnv1a는 원소당 1번
function updateImproved(
  set: Iterable<string>,
  k: number,
  a: number[],
  b: number[],
  PRIME: number,
): number[] {
  const sig = new Array(k).fill(Infinity);
  for (const x of set) {
    const base = BigInt(fnv1a(x)); // 원소당 1번
    for (let i = 0; i < k; i++) {
      const h = Number((BigInt(a[i]!) * base + BigInt(b[i]!)) % BigInt(PRIME));
      if (h < sig[i]!) sig[i] = h;
    }
  }
  return sig;
}
```

`fnv1a` 호출은 $n$번으로 줄었습니다. 그런데 `a[i] * base`를 `Number`로 그대로 곱하면 안전 정수 범위($2^{53}$)를 넘길 수 있어요. 예를 들어 `a0 = 1943956585`, `base = 280767167`(= `fnv1a('apple')`)일 때, `Number` 곱셈으로 그대로 `% PRIME`을 하면 `221110895`가 나오지만 **정답은 `221110886`** 입니다. 겨우 9 차이지만, 이 미세한 오차가 다른 원소와의 최솟값 비교 순서를 뒤집어 서명 전체를 조용히 틀리게 만들 수 있어요. 최종 구현은 이 곱셈-모듈러 구간만 `BigInt`로 승격합니다.

**최종 구현**입니다.

```ts
// FNV-1a 32비트 해시 — 문자열을 결정론적으로 하나의 정수로 압축한다.
function fnv1a(str: string): number {
  let hash = 0x811c9dc5; // FNV offset basis
  for (let i = 0; i < str.length; i++) {
    hash ^= str.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193); // FNV prime
  }
  return hash >>> 0; // 부호 없는 32비트 정수로 변환
}

// sfc32 — 작은 상태로 빠르게 도는 시드 기반 PRNG. 같은 시드면 항상 같은 수열을 낸다.
function sfc32(a: number, b: number, c: number, d: number) {
  return function (): number {
    a >>>= 0;
    b >>>= 0;
    c >>>= 0;
    d >>>= 0;
    let t = (a + b) | 0;
    a = b ^ (b >>> 9);
    b = (c + (c << 3)) | 0;
    c = (c << 21) | (c >>> 11);
    d = (d + 1) | 0;
    t = (t + d) | 0;
    c = (c + t) | 0;
    return (t >>> 0) / 4294967296;
  };
}

const PRIME = 2147483647; // 2^31 - 1 (메르센 소수)

export class MinHash {
  private readonly k: number;
  private readonly a: number[];
  private readonly b: number[];
  private sig: number[];

  constructor(numHashes: number) {
    this.k = numHashes;
    // 고정 시드 — 모든 인스턴스가 같은 해시 계열을 공유해야 비교가 유효하다
    const rand = sfc32(0x9e3779b9, 0x243f6a88, 0xb7e15162, 0x2545f491);
    this.a = [];
    this.b = [];
    for (let i = 0; i < numHashes; i++) {
      let ai = Math.floor(rand() * (PRIME - 1)) + 1;
      if (ai % 2 === 0) ai += 1; // 홀수로 강제(PRIME과 서로소 보장)
      this.a.push(ai);
      this.b.push(Math.floor(rand() * PRIME));
    }
    this.sig = new Array(numHashes).fill(Infinity);
  }

  update(set: Iterable<string>): void {
    this.sig = new Array(this.k).fill(Infinity);
    for (const x of set) {
      const base = BigInt(fnv1a(x)); // 원소당 1번
      for (let i = 0; i < this.k; i++) {
        // a*base가 안전 정수 범위를 넘으므로 BigInt로 모듈러 연산
        const h = Number(
          (BigInt(this.a[i]!) * base + BigInt(this.b[i]!)) % BigInt(PRIME),
        );
        if (h < this.sig[i]!) this.sig[i] = h;
      }
    }
  }

  signature(): number[] {
    return this.sig.slice();
  }

  static jaccard(a: MinHash, b: MinHash): number {
    let matches = 0;
    for (let i = 0; i < a.k; i++) {
      if (a.sig[i] === b.sig[i]) matches++;
    }
    return matches / a.k;
  }

  static exact(a: Set<string>, b: Set<string>): number {
    if (a.size === 0 && b.size === 0) return 1;
    let interCount = 0;
    for (const x of a) if (b.has(x)) interCount++;
    const unionCount = a.size + b.size - interCount;
    return interCount / unionCount;
  }
}
```

가장 중요한 부분은 `update`의 루프 순서와 `BigInt` 승격입니다 — 바깥은 원소, 안은 해시 함수(`for (const x of set) { const base = ...; for (let i ...) {...} }`). 놓치기 쉬운 지점을 정리하면:

- **`BigInt(this.a[i]!) * base + BigInt(this.b[i]!)) % BigInt(PRIME)`** — 이 변환을 건너뛰면 위에서 본 정밀도 손실(`221110895` vs `221110886`)이 조용히 발생합니다.
- **생성자의 고정 시드.** `sfc32(0x9e3779b9, ...)`처럼 상수를 박아 두어야 모든 인스턴스가 같은 `a[]`, `b[]`를 공유합니다. `Math.random()`으로 바꾸면 앞서 본 `matches = 0/8` 사고가 재현됩니다.
- **`ai % 2 === 0`이면 홀수로 보정.** $a_i$가 짝수면 $P$(홀수인 메르센 소수)와 공약수를 가질 가능성이 생겨 해시 분포가 나빠집니다.

기억법: "해시 계열은 인스턴스 개인 소지품이 아니라 학급 전체가 공유하는 규칙이다."

정리하면, MinHash는 "무작위 해시 함수 하나의 최솟값이 곧 무작위 순열의 argmin을 흉내 낸다"는 관찰 하나로 집합 유사도 문제를 정수 배열 비교 문제로 바꿉니다. $k$개의 독립 해시로 이 관찰을 반복하면 `matches / k`가 Jaccard의 불편 추정량이 되고, 표준오차는 $1/(2\sqrt{k})$로 예측 가능하게 줄어듭니다. 실제 계산에서도 작은 표본(k=4)에서는 우연히 정확히 맞아떨어졌고, 큰 표본(k=256)에서는 예측된 오차 범위 안에서 실제 값(1/3)에 가까운 추정(0.3516)을 얻었습니다 — 이론과 실측이 맞물려 돌아간다는 뜻입니다.

## 스스로 점검하기

1. $k=2$인 MinHash에서 $h_0(x) = (3x+1) \bmod 7$, $h_1(x) = (5x+2) \bmod 7$이라 하고, 집합 $A=\{2,4\}$, 집합 $B=\{4,6\}$의 서명을 손으로 계산해 보세요. 추정 Jaccard와 실제(exact) Jaccard를 비교하면 어떤 차이가 나나요?
2. 만약 `MinHash`의 생성자가 인스턴스마다 새로운 무작위 시드로 `a[]`, `b[]`를 뽑는다면, **완전히 동일한 집합**을 두 인스턴스에 넣어도 추정 Jaccard가 1이 아닐 수 있는 이유를 설명해 보세요. (힌트: 본문의 "해시 계열 불일치" 실측 수치)
3. `update`에서 해시 함수 순회를 바깥 루프, 원소 순회를 안쪽 루프로 두면(원형 코드처럼) `fnv1a`가 몇 번 호출되나요? $n=10{,}000$, $k=128$일 때 개선된 순서(원소가 바깥 루프)와 비교해 호출 횟수 차이를 계산해 보세요.
