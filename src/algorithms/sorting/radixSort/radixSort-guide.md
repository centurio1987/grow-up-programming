# 자릿수 정렬 — 가장 높은 자리를 마지막에 처리해야 앞 바퀴의 순서가 남는다

## 파트 1 — 아이디어에서 동작하는 코드까지

값의 범위가 너무 넓어 칸을 만들 수 없는 자리에서 시작해, 값을 자리 여럿으로 쪼개 여러 번
정렬하는 방법까지 갑니다. 마지막에는 일곱 칸짜리 입력 하나를 끝까지 실행해 실제로 동작하는
코드를 만듭니다.

### 전체 컨셉

정렬을 「두 값의 크기를 견주어 순서를 정하는 일」로만 보면 이 문제도 견주기로 풀어야 할 것
같습니다. 그런데 제약이 하나 더 붙어 있어요 — **값이 0 이상 10^9 이하의 정수**입니다. 값의
종류가 정해져 있으면 값 자체를 배열의 자리 번호로 쓸 수 있는데, 여기서는 그 칸을 만들 수가
없습니다.

```text
값 하나가 칸 하나를 맡으려면

  값이 0 … 1,000 이면   칸 1,001 개   만들 수 있다
  값이 0 … 10^9 이면    칸 10 억 개   한 칸을 8 바이트로 잡아도 8 GB 다
                        └ 메모리 제한이 256 MB 라 아래 줄은 칸을 만드는 자리에서 끝난다
```

칸을 만들 수 없는 이유는 **키가 넓기** 때문입니다. 그러면 키를 좁히면 되는데, 값을 통째로
쓰는 대신 **자리 하나씩만** 키로 쓰면 그렇게 됩니다. 값을 256 진법으로 적으면 자리 하나가
담는 값은 0 부터 255 까지 256 가지뿐이에요.

```text
값을 256 진법으로 적으면 자리 하나가 담는 값은 256 가지다

  513    = 2 × 256 + 1           자리 1 은 2 · 자리 0 은 1
  258    = 1 × 256 + 2           자리 1 은 1 · 자리 0 은 2
  2      = 0 × 256 + 2           자리 1 은 0 · 자리 0 은 2
  10^9   = 59 × 256^3 + 나머지   자리가 넷이라 10^9 까지 담긴다
         └ 어느 자리든 값이 0 … 255 라 칸 256 개면 센다
```

자리 하나로 정렬하는 데는 견주기가 필요 없습니다. 자리 값이 곧 칸 번호이므로 그 칸의 개수를
하나 늘리기만 하면 되고, 칸을 0 부터 차례로 읽으면 그 자리 기준의 오름차순이 나와요. 문제는
자리가 여럿이라는 것입니다 — 자리마다 한 번씩 정렬하면 **나중에 한 정렬이 먼저 한 정렬을
덮어쓸 것처럼** 보입니다.

```text
A = [513 45 258 2 66 90 301] 을 자리 0 · 자리 1 순서로 정렬하면

  처음           [513 45 258 2 66 90 301]   자리 0 의 값 1 45 2 2 66 90 45
  첫 바퀴 뒤     [513 258 2 45 301 66 90]   자리 0 기준 오름차순
  둘째 바퀴 뒤   [2 45 66 90 258 301 513]   자리 1 기준 오름차순 · 같으면 앞 순서 그대로
                 └ 마지막 바퀴가 자리 1 이라 자리 1 이 가장 높은 자리가 된다
```

지워지지 않는 이유는 마지막 줄에 있습니다. 둘째 바퀴가 자리 1 이 **같은** 원소끼리는 앞뒤를
바꾸지 않으므로, 그 안에서는 첫 바퀴가 만든 자리 0 기준의 순서가 그대로 남아요. 두 수의 대소는
「높은 자리부터 견주어 처음 달라지는 자리」가 정하니까, 높은 자리를 **마지막에** 처리하면 그것이
최종 순서를 정하고 낮은 자리는 동점을 가르는 데 쓰입니다. 자리 하나를 처리하는 한 번의 반복을
이 글에서는 **바퀴**라고 부르겠습니다.

```text
비용이 두 조각으로 갈린다

  입력 칸 수 N 에 붙는 몫         바퀴마다 값을 세고 옮긴다
  자리의 가짓수 B 에 붙는 몫      바퀴마다 칸 B 개를 만들고 전부 읽는다
  바퀴 수 d 는 둘을 함께 곱한다   최댓값이 몇 자리인가로 정해진다
                                  └ B 를 키우면 d 가 줄고, 그 대신 바퀴마다 읽을 칸이 는다
```

배열 칸을 읽거나 쓴 횟수를 세면 `4N + d(7N + 4B − 3)` 번이고 견주기는 0 번입니다. 이 문제는
`B` 를 256 으로 두면 `d` 가 넷 이하이고 `N` 이 최대 100,000 이라, 제약 상한에서 320 만 번
남짓이에요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **오름차순 정렬의 뜻** — 모든 이웃 쌍에서 앞 칸이 뒤 칸보다 크지 않고, 결과에 담긴 값들이 입력의
  값들과 **개수까지 같아야** 합니다. 뒤쪽 조건이 흐릿하면 「정렬됐는가」만 보는 검사를 통과
  하면서 값이 사라진 코드를 알아볼 수 없습니다.
- **안정 정렬(stable sort)** — 정렬 기준으로 봤을 때 값이 같은 원소들의 **앞뒤가 바뀌지 않는**
  정렬입니다. 이 글의 절차는 안정성을 근거로 삼아서, 그것이 없으면 바퀴 둘이 서로를 덮어씁니다.
- **위치 기수법** — `513` 을 `2 × 256 + 1` 처럼 진법 하나로 자리 여럿에 나눠 적는 방식입니다.
  자리는 낮은 쪽부터 0 · 1 · 2 … 로 세고, 어느 자리든 값이 진법보다 작습니다.
- **계수 정렬** — 값의 종류가 적을 때 개수만 세어 정렬하는 절차입니다. 이 글은 그 절차를 자리
  하나에 적용해 되풀이해요. 모르면 [계수 정렬 가이드](../countingSort/countingSort-guide.md)를
  먼저 보세요.
- **배열의 임의 접근** — 배열의 여덟 번째 칸을 읽는 데 앞의 일곱 칸을 지날 필요가 없습니다.
  자리 번호만 있으면 한 번에 그 칸입니다.

같은 문제를 견주기로 푸는 편이 저장소에 둘 있습니다 —
[병합 정렬 가이드](../sortArray/sortArray-guide.md)와
[삽입 정렬 가이드](../insertionSort/insertionSort-guide.md)입니다.

### 아이디어 상세 — 값을 자리로 쪼개 되풀이하는 방법을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function radixSort(A: number[]): number[];
```

- 입력: 비음 정수 배열 `A`.
- 출력: `A` 의 모든 값을 오름차순으로 담은 **새 배열**. 입력 `A` 자체는 바뀌지 않습니다.
- 제약: 칸 수 `N` 은 100,000 이하, 값은 0 이상 10^9 이하의 정수, 시간 제한 1 초, 메모리 제한
  256 MB 입니다. 같은 값이 여럿이면 그 개수 그대로 결과에 담깁니다.
- 값의 **상한이 제약에 명시돼 있다**는 것이 이 문제의 특징입니다. 다만 그 상한이 10^9 이라
  「값마다 칸 하나」로는 감당이 안 됩니다.

이 글이 쓰는 기호는 10 개예요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `N` | 입력 배열 `A` 의 칸 수 | `1 ≤ N ≤ 100,000` |
| `A` | 정렬할 입력 배열. `A[i]` 가 `i` 번째 값 | `0 ≤ A[i] ≤ 10^9` |
| `M` | 입력의 최댓값 | `M ≤ 10^9` |
| `B` | 자리 하나가 담는 값의 가짓수. 곧 진법 | `B = 256` 으로 고정 |
| `d` | 바퀴 수. `M` 을 `B` 진법으로 적은 자릿수 | `d ≤ 4` |
| `place` | 지금 보는 자리의 크기. 바퀴마다 `B` 배가 된다 | `1 · 256 · 65,536 · 16,777,216` |
| `i` | 입력에서 지금 읽고 있는 자리 | `0 ≤ i ≤ N − 1` |
| `count` | 자리 값마다의 개수를 담는 배열 | 칸 수 `B` |
| `src` | 이번 바퀴가 읽는 배열 | 칸 수 `N` |
| `dst` | 이번 바퀴가 쓰는 배열 | 칸 수 `N` |

가장 먼저 떠오르는 방법은 **모든 쌍을 견주어 순서가 틀렸으면 맞바꾸는 것**입니다. 두 자리를
아무렇게나 잡아 앞이 더 크면 바꾸는 일을 모든 쌍에 대해 하면 남는 역순쌍이 없으니 정렬이
끝나요. 값이 정수라는 것도, 상한이 있다는 것도 하나도 쓰지 않습니다.

```ts
function sortNaive(A: number[]): number[] {
  const copy = Array.from(A);
  for (let j = 0; j < copy.length; j++) {
    for (let t = j + 1; t < copy.length; t++) {
      if ((copy[j] as number) > (copy[t] as number)) {
        const tmp = copy[j] as number;
        copy[j] = copy[t] as number;
        copy[t] = tmp;
      }
    }
  }
  return copy;
}
```

이 방법은 답을 틀리지 않습니다. 문제는 견주기 횟수인데, `j` 번째 바퀴가 `N − j − 1` 번을
견주므로 전부 더하면 `N(N−1)/2` 이고 **입력이 어떻게 놓여 있든 이 값 그대로**입니다.
제약 상한 `N = 100,000` 까지 칸 수를 넓혀 가며 실제로 재 봅시다.

<!--proof:scale-100k-->

```text
입력 칸 수          모든 쌍 견주기   이 절차의 견주기   이 절차의 배열 접근
전개 입력 일곱 칸               21                  0                 2,168
100 칸                       4,950                  0                 7,284
1,000 칸                   499,500                  0                36,084
100,000 칸           4,999,950,000                  0             3,204,084
                                                        └ 가운데 열이 0 이다. 이 절차에는 두 값을 견주는 자리가 없다
```

**제약 상한에서 49 억 9,995 만 번을 견줍니다.** 초당 1 억 번으로 잡으면 약 50 초이고, 시간
제한 1 초의 오십 배예요. 오른쪽 열은 같은 입력에서 320 만 번 남짓이라 제한 안에 들어옵니다.

견주기를 없애는 방법은 이미 하나 있습니다 — 값을 그대로 칸 번호로 쓰는 계수 정렬이에요. 값
`v` 를 `count` 의 자리 `v` 로 쓰면 자리를 찾는 데 견주기가 한 번도 들지 않습니다. 그런데 이
문제의 제약을 넣어 보면 그 절차가 어디서 걸리는지가 값으로 나와요.

```text
값을 그대로 칸 번호로 쓰는 계수 정렬을 이 제약에 적용하면

  칸 수            10^9 + 1 개     값 10^9 도 자기 칸을 가져야 한다
  칸을 만드는 일   10 억 번 쓰기   입력이 일곱 칸이어도 그대로 든다
  칸을 읽는 일     10 억 번 읽기   개수가 0 인 칸도 읽어야 한다
                   └ 입력 칸 수 N 이 아니라 값의 상한이 비용을 정한다
```

**걸리는 것은 견주기가 아니라 키의 넓이입니다.** 일곱 칸을 정렬하는 데도 10 억 칸을 만들어야
하니까요. 그러면 키를 좁히면 되는데, 좁히는 방법이 **값을 자리 여럿으로 쪼개는 것**입니다.
`513` 을 `2 × 256 + 1` 로 적으면 키가 두 개로 갈리고 각각은 0 … 255 예요. 키를 그대로 두는
쪽과 자리로 쪼개는 쪽을 **같은 입력에서** 나란히 재 봅시다 — 자리로 쪼개면 칸 수가 줄고 그
대신 바퀴가 늡니다.

<!--proof:wide-vs-split-->

```text
입력                     최댓값   키 그대로 접근   키 그대로 칸 수   자리로 쪼갠 접근
전개 입력 일곱 칸           513            2,130               514              2,168
1,000 칸            998,983,017    3,995,943,069       998,983,018             36,084
100,000 칸          999,996,925    4,001,087,701       999,996,926          3,204,084
                                                                     └ 오른쪽 열의 count 는 최댓값이 얼마든 256 칸이다
```

**일곱 칸에서는 자리로 쪼갠 쪽이 오히려 접근이 많습니다** — 2,168 대 2,130 이에요. 최댓값이
513 뿐이라 키를 그대로 둬도 칸이 514 개면 되고, 그러면 바퀴 하나로 끝나니까요. 그런데 최댓값이
10^9 에 가까워지는 아래 두 줄에서는 왼쪽이 40 억 번이 되고 칸도 10 억 개가 됩니다.

```text
두 열이 무엇을 따라가는가

  키를 그대로     칸 수가 최댓값 M 을 그대로 따라간다   M 이 곱으로 들어온다
  자리로 쪼갬     칸 수가 B 로 고정이고 바퀴가 d 다     M 이 로그로 들어온다
                  └ 100,000 칸에서 40 억 대 320 만이라 약 1,249 배 차이다
```

여기까지가 「무엇을 줄여야 하는가」입니다. 남은 것은 **바퀴 여럿이 실제로 맞는 답을 내는가**
인데, 그것이 아직 안 정해졌어요. 자리를 쪼갠 것만으로는 바퀴들을 어떤 순서로 어떻게 이어야
하는지가 나오지 않습니다.

**여기서 개념을 세웁니다.** 자리 하나를 키로 하는 **안정 정렬**을 **낮은 자리부터** `d` 번
되풀이하는 것 — 이것을 이 글에서 **자리로 쪼개 되풀이하기**라고 부르겠습니다. 붙은 조건이
둘인데(안정 · 낮은 자리부터) 둘 다 없으면 안 되는지를 값으로 확인해 봅시다.

```text
자리로 쪼개 되풀이하기가 붙이는 조건 둘

  낮은 자리부터   마지막 바퀴가 가장 높은 자리여야 한다
  안정 정렬       자리 값이 같으면 앞 바퀴의 앞뒤를 그대로 둔다
                  └ 둘을 하나씩 빼 보고 답이 어떻게 되는지 값으로 확인한다
```

**가장 단순한 후보를 먼저 시험합시다.** 우리가 수를 견줄 때는 높은 자리부터 보므로, 바퀴도
높은 자리부터 하는 것이 자연스럽습니다. 같은 절차를 자리 순서만 뒤집어 실행해 보겠습니다.

<!--proof:msd-repeat-->

```text
입력                         낮은 자리부터                높은 자리부터
[513 45 258 2 66 90 301]     [2 45 66 90 258 301 513]     [513 2 258 45 301 66 90]
[170 45 75 90 802 24 2 66]   [2 24 45 66 75 90 170 802]   [2 24 802 45 66 75 90 170]
[321 213 132 123]            [123 132 213 321]            [321 123 132 213]
[12 12 1 1 100 100]          [1 1 12 12 100 100]          [1 1 12 12 100 100]
[0 10 0 1]                   [0 0 1 10]                   [0 0 1 10]
                                                          └ 다섯 벌 중 3 벌에서 답이 어긋난다
```

**높은 자리부터 하면 마지막 바퀴가 자리 0 입니다.** 마지막 바퀴가 그 자리 기준의 순서를 만드
니까, 결과는 자리 0 만 오름차순인 배열이 돼요. `[513 2 258 45 301 66 90]` 의 자리 0 을 적으면
`1 2 2 45 45 66 90` 으로 정확히 오름차순입니다.

```text
같은 두 바퀴를 순서만 바꿔 실행하면

  낮은 자리부터   자리 0 → 자리 1   [2 45 66 90 258 301 513]
  높은 자리부터   자리 1 → 자리 0   [513 2 258 45 301 66 90]
                  └ 아래 줄은 자리 0 기준으로만 오름차순이다 — 1 2 2 45 45 66 90
```

**마지막에 처리한 자리가 가장 높은 자리가 됩니다.** 그러니 진짜 가장 높은 자리를 마지막에
두어야 하고, 그것이 「낮은 자리부터」의 뜻이에요. 아래 두 벌에서 답이 안 어긋난 것은 최댓값이
100 과 10 이라 바퀴가 하나뿐이어서, 순서를 뒤집을 자리가 없었기 때문입니다.

**남은 조건은 안정성입니다.** 마지막 바퀴가 자리 1 기준으로 정렬할 때, 자리 1 이 같은 원소가
여럿이면 그 안의 순서는 정하지 않고 앞 바퀴가 만든 것을 그대로 둬야 해요. 전개 입력의 둘째
바퀴에서 그 상황이 실제로 나옵니다.

| 둘째 바퀴가 만나는 자리 | 그 원소들 | 어떻게 놓이는가 |
| --- | --- | --- |
| 자리 1 이 0 인 넷 | 2 · 45 · 66 · 90 | 첫 바퀴의 앞뒤 그대로 칸 0 … 3 |
| 자리 1 이 1 인 둘 | 258 · 301 | 첫 바퀴의 앞뒤 그대로 칸 4 · 5 |
| 자리 1 이 2 인 하나 | 513 | 칸 6 |

첫 바퀴가 만든 순서가 자리 0 기준이므로, 자리 1 이 같은 넷의 순서 `2 · 45 · 66 · 90` 은 그들의
자리 0 순서 `2 · 45 · 66 · 90` 입니다. 자리 1 이 같으면 자리 0 이 대소를 정하니까, 그 넷은
이미 최종 순서로 놓여 있어요.

```text
값 하나가 지나가는 길 — 258 과 301

  처음        258 은 칸 2, 301 은 칸 6
  첫 바퀴 뒤  258 은 칸 1, 301 은 칸 4   자리 0 이 2 와 45 라 258 이 앞
  둘째 바퀴   둘 다 자리 1 이 1 이라 앞뒤를 안 바꾼다 → 258 · 301
              └ 258 < 301 이 자리 0 에서 정해졌고 그 결과가 그대로 남았다
```

**이제 자리 하나의 가짓수 `B` 를 몇 가지로 바꿔 재 봅시다.** `B` 를 키우면 바퀴 `d` 가 줄고
`count` 의 칸이 늘어요. 최댓값을 10^9 으로 고정하고 칸 수 `N` 만 셋으로 바꿔 실제 접근을
셉니다.

<!--proof:base-sweep-->

```text
자리 하나의 가짓수 B   바퀴 수 d     N = 1   N = 1,000   N = 100,000
2                             30       364     214,150    21,400,150
16                             8       548      60,488     6,000,488
64                             5     1,304      40,265     3,901,265
256                            4     4,116      36,084     3,204,084
1,024                          3    12,304      37,279     2,512,279
32,768                         2   262,156     280,138     2,062,138
                                                         └ 가장 적은 값이 N = 1 에서 B = 2, N = 1,000 에서 B = 256, N = 100,000 에서 B = 32,768 로 옮겨 간다
```

**최소가 한 값으로 정해지지 않습니다.** `N` 이 100 배 늘 때마다 최소가 큰 진법 쪽으로 한 칸씩
옮겨 가요. 칸 수가 작으면 바퀴마다 만드는 `count` 가 전체를 차지하고, 칸 수가 크면 바퀴 수가
전체를 차지하기 때문입니다.

```text
이 편이 B = 256 을 고정하고 내주는 것

  N = 100,000 에서   3,204,084 번   최솟값 2,062,138 번의 약 1.55 배
  N = 1 에서             4,116 번   최솟값 364 번의 약 11.3 배지만 절대값이 작다
                         └ B 를 N 에 맞춰 고르면 더 줄일 수 있고, 이 절차는 그 자리를 남겨 둔다
```

`B = 256` 은 자리 하나가 정확히 한 바이트라는 뜻이고, 뒤에서 볼 실제 구현 셋이 전부 이 값을
씁니다. 접근 수만 재는 이 계수로는 그 셋이 8 비트를 고른 근거가 나오지 않아요 — 그 근거는 이
계수 밖에 있고, 이 글은 그것을 재지 않았습니다.

### 수행으로 알아보는 알고리즘 — 일곱 칸을 두 바퀴로 정렬한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const A = [513, 45, 258, 2, 66, 90, 301];
// 이 절이 끝나면 [2, 45, 66, 90, 258, 301, 513] 이 나와야 한다
```

`A` 를 왜 하필 이 일곱 칸으로 뒀을까요? 갈래를 **모두 실행하게** 하려는 것입니다. 최댓값 513 이
256 진법 두 자리라 바퀴가 둘이고, 첫 바퀴에 자리 값이 겹치는 짝이 둘(자리 값 2 와 45), 둘째
바퀴에 자리 값 0 인 원소가 넷 몰려 있어요. 안정성이 실제로 답을 정하는 자리가 그 넷입니다.

```text
radixSort(A):

  src ← A 의 사본, dst ← 같은 칸 수의 배열
  max 는 src 의 최댓값                          ① 바퀴 수를 정한다
  place 를 1 부터 max 를 덮을 때까지 B 배씩:    ② 낮은 자리부터 하나씩
      count ← 0 으로 채운 B 칸짜리 배열
      src 의 값 x 마다: count[자리 값] += 1     ③ 자리 값을 센다
      count 를 왼쪽부터 누적합으로 덮는다       ④ 놓을 칸을 정한다
      i 를 N-1 부터 0 까지:                     ⑤ 뒤에서 앞으로 놓는다
          count[자리 값] -= 1
          dst[count[자리 값]] ← src[i]
      src 와 dst 의 역할을 맞바꾼다             ⑥ 다음 바퀴가 방금 쓴 쪽을 읽는다
  return src
```

#### 1. 값을 자리 둘로 나눈다

먼저 바퀴를 몇 번 실행할지 정합니다. 자리를 몇 개까지 볼지는 **최댓값**이 정해요 — 최댓값이
담기면 나머지는 저절로 담기니까요.

```ts
let max = 0; // ① 바퀴 수를 정한다
for (const x of A) if (x > max) max = x;
// max = 513 이고, 513 < 256^2 이라 자리는 둘이다
```

이 조각만 실행하면 `max` 가 513 이고, 그 값이 256 진법으로 두 자리라 바퀴가 둘이라는 것까지
나옵니다(T1). 일곱 값의 자리를 미리 펼쳐 두면 뒤가 읽기 쉬워요.

| 값 | 자리 1 (`⌊x/256⌋ mod 256`) | 자리 0 (`x mod 256`) |
| --- | --- | --- |
| 513 | 2 | 1 |
| 45 | 0 | 45 |
| 258 | 1 | 2 |
| 2 | 0 | 2 |
| 66 | 0 | 66 |
| 90 | 0 | 90 |
| 301 | 1 | 45 |

**자리 0 에 겹치는 값이 둘 있습니다** — 258 과 2 가 둘 다 2 이고, 45 와 301 이 둘 다 45 예요.
자리 1 에는 0 이 넷, 1 이 둘, 2 가 하나입니다. 두 바퀴 모두 「자리 값이 같은 원소」를 만나게
되어 있어요.

#### 짚고 가기 — 자리를 왼쪽 끝에 맞추면 사전식 순서가 된다

자릿수가 다른 값이 섞여 있으면 자리를 어느 쪽 끝에 맞출지가 헷갈립니다. 우리가 종이에 수를
적을 때는 왼쪽부터 읽으니까, 자리도 왼쪽 끝에 맞춰 견주고 싶어져요. 그렇게 하면 `2` 의 첫
자리 `2` 와 `513` 의 첫 자리 `2` 가 같은 자리에서 만납니다.

```text
왼쪽 끝에 맞추면 무엇과 무엇이 만나는가

  513 의 자리 목록   [2 1]     첫 칸이 2
  2 의 자리 목록     [2]       첫 칸이 2
  258 의 자리 목록   [1 2]     첫 칸이 1
                     └ 첫 칸만 보면 258 이 513 보다 앞이고 2 는 513 과 동점이다
```

실제로 그 순서를 만들어 보면 답이 어긋납니다. 오른쪽 끝에 맞춘 이 절차와 나란히 놓고 값을
확인해 봅시다.

<!--proof:pause-left-align-->

```text
입력                         오른쪽 끝에 맞춤(이 절차)    왼쪽 끝에 맞춤
[513 45 258 2 66 90 301]     [2 45 66 90 258 301 513]     [258 301 2 513 45 66 90]
[1 10 100 1000]              [1 10 100 1000]              [1 1000 10 100]
[170 45 75 90 802 24 2 66]   [2 24 45 66 75 90 170 802]   [2 802 24 45 66 75 90 170]
[0 10 0 1]                   [0 0 1 10]                   [0 0 1 10]
                                                          └ 네 벌 중 3 벌에서 답이 어긋난다
```

`[1 10 100 1000]` 이 `[1 1000 10 100]` 이 된 줄이 이 오해의 모양을 그대로 보입니다 — 문자열로
정렬했을 때 10 이 9 보다 앞에 오는 것과 같은 자리예요. **자리는 오른쪽 끝에 맞춥니다.** 자리 0
은 언제나 `x mod B` 이고, 값이 짧으면 없는 높은 자리가 0 으로 채워져 저절로 앞에 옵니다.

#### 2. 첫 바퀴 — 자리 0 을 세고 놓는다

자리 하나를 정했으면 그 자리 값마다 몇 개인지 셉니다. 자리 값이 곧 칸 번호라 견주기가 필요
없어요.

```ts
const count = new Array<number>(256).fill(0);
for (const x of src) {
  // ③ 자리 값을 센다
  const dig = Math.floor(x / place) % 256;
  count[dig] = (count[dig] as number) + 1;
}
for (let dig = 1; dig < 256; dig++) {
  // ④ 놓을 칸을 정한다
  count[dig] = (count[dig] as number) + (count[dig - 1] as number);
}
```

`place` 가 1 이니 자리 값은 `x` 를 256 으로 나눈 나머지입니다. 세고(T2) 누적합으로 덮으면(T3)
`count[dig]` 가 **자리 값이 `dig` 이하인 원소의 개수**가 되고, 그 수가 곧 그 값이 놓일 칸의
끝 번호가 돼요.

| 자리 값 | 개수 | 누적합 | 그 값이 차지하는 칸 |
| --- | --- | --- | --- |
| 1 | 1 | 1 | 0 |
| 2 | 2 | 3 | 1 · 2 |
| 45 | 2 | 5 | 3 · 4 |
| 66 | 1 | 6 | 5 |
| 90 | 1 | 7 | 6 |
| 그 밖 251 가지 | 0 | 앞과 같음 | 없음 |

이제 원소를 놓습니다. `src` 를 **뒤에서 앞으로** 읽으며 그 자리의 누적합을 하나 줄이고 그
칸에 적어요.

```ts
for (let i = src.length - 1; i >= 0; i--) {
  // ⑤ 뒤에서 앞으로 놓는다
  const x = src[i] as number;
  const dig = Math.floor(x / place) % 256;
  count[dig] = (count[dig] as number) - 1;
  dst[count[dig] as number] = x;
}
```

| 단계 | `i` | 값 | 자리 값 | `count` 갱신 | 놓는 칸 | 놓은 뒤 `dst` |
| --- | --- | --- | --- | --- | --- | --- |
| T4 | 6 | 301 | 45 | 5 → 4 | 4 | `_ _ _ _ 301 _ _` |
| T5 | 5 | 90 | 90 | 7 → 6 | 6 | `_ _ _ _ 301 _ 90` |
| T6 | 4 | 66 | 66 | 6 → 5 | 5 | `_ _ _ _ 301 66 90` |
| T7 | 3 | 2 | 2 | 3 → 2 | 2 | `_ _ 2 _ 301 66 90` |
| T8 | 2 | 258 | 2 | 2 → 1 | 1 | `_ 258 2 _ 301 66 90` |
| T9 | 1 | 45 | 45 | 4 → 3 | 3 | `_ 258 2 45 301 66 90` |
| T10 | 0 | 513 | 1 | 1 → 0 | 0 | `513 258 2 45 301 66 90` |

**T7 과 T8 이 자리 값 2 를 나눠 가진 짝입니다.** 뒤쪽에 있던 2 가 먼저 읽혀 칸 2 를, 앞쪽에
있던 258 이 나중에 읽혀 칸 1 을 받았어요. 뒤에서 앞으로 읽었는데 결과는 원래 앞뒤 그대로
입니다(T11 의 `dst` 에서 258 이 2 보다 앞). T9 와 T4 의 45 · 301 짝도 같은 모양이에요.

#### 짚고 가기 — 누적합이 없으면 원래 값이 사라진다

계수 정렬은 개수만 세고 값을 이어 쓰면 끝났습니다. 그러면 여기서도 자리 값 `dig` 를
`count[dig]` 번 이어 쓰면 되지 않을까요? 그 절차를 그대로 실행하면 무엇이 나오는지부터 봅시다.

<!--proof:pause-no-prefix-->

```text
한 바퀴                      누적합을 쓴 쪽             개수만 세어 이어 쓴 쪽
전개 입력 자리 0             [513 258 2 45 301 66 90]   [1 2 2 45 45 66 90]
전개 입력 자리 1             [45 2 66 90 258 301 513]   [0 0 0 0 1 1 2]
[12 12 1 1 100 100] 자리 0   [1 1 12 12 100 100]        [1 1 12 12 100 100]
                                                        └ 오른쪽에 남은 것은 원래 값이 아니라 자리 값이다
```

**오른쪽 열에 남은 것은 자리 값입니다.** 첫 줄의 `[1 2 2 45 45 66 90]` 은 입력 513 · 45 · 258 ·
2 · 66 · 90 · 301 의 자리 0 을 모아 정렬한 것이고, 원래 값 513 과 301 은 어디에도 없어요. 둘째
줄은 더 분명합니다 — 자리 1 만 남아 `[0 0 0 0 1 1 2]` 가 됐습니다.

```text
두 절차가 결과를 만드는 방법이 다르다

  계수 정렬     자리 번호에서 값을 다시 만들어 쓴다   키가 곧 값이라 그것으로 충분하다
  이 절차       원소를 통째로 다른 칸에 옮긴다        키는 값의 일부일 뿐이다
                └ 옮기려면 「어느 칸에 놓을지」가 먼저 필요하고, 그것이 누적합이다
```

셋째 줄이 같은 값을 낸 것은 그 입력의 모든 값이 256 보다 작아 **값과 자리 0 이 같기** 때문
입니다. 그런 입력만 보면 두 방식이 같아 보이지만, 원래 값과 자리 값이 갈리는 순간 오른쪽은
답이 아니게 돼요.

#### 3. 둘째 바퀴 — 자리 1 이 앞 바퀴의 순서를 이어받는다

첫 바퀴가 끝나면 `src` 와 `dst` 의 역할을 맞바꿉니다. 그래야 둘째 바퀴가 방금 쓴 쪽을 읽어요.

```ts
[src, dst] = [dst, src]; // ⑥ 다음 바퀴가 방금 쓴 쪽을 읽는다
// src = [513, 258, 2, 45, 301, 66, 90],  place 는 1 에서 256 으로
```

둘째 바퀴의 자리 값은 `⌊x/256⌋ mod 256` 입니다. 세면 자리 값 0 이 넷, 1 이 둘, 2 가 하나
이고(T12), 누적합은 4 · 6 · 7 이에요(T13).

| 자리 값 | 개수 | 누적합 | 그 값이 차지하는 칸 |
| --- | --- | --- | --- |
| 0 | 4 | 4 | 0 · 1 · 2 · 3 |
| 1 | 2 | 6 | 4 · 5 |
| 2 | 1 | 7 | 6 |

| 단계 | `i` | 값 | 자리 값 | `count` 갱신 | 놓는 칸 | 놓은 뒤 `dst` |
| --- | --- | --- | --- | --- | --- | --- |
| T14 | 6 | 90 | 0 | 4 → 3 | 3 | `_ _ _ 90 _ _ _` |
| T15 | 5 | 66 | 0 | 3 → 2 | 2 | `_ _ 66 90 _ _ _` |
| T16 | 4 | 301 | 1 | 6 → 5 | 5 | `_ _ 66 90 _ 301 _` |
| T17 | 3 | 45 | 0 | 2 → 1 | 1 | `_ 45 66 90 _ 301 _` |
| T18 | 2 | 2 | 0 | 1 → 0 | 0 | `2 45 66 90 _ 301 _` |
| T19 | 1 | 258 | 1 | 5 → 4 | 4 | `2 45 66 90 258 301 _` |
| T20 | 0 | 513 | 2 | 7 → 6 | 6 | `2 45 66 90 258 301 513` |

**자리 값 0 인 넷이 칸 0 … 3 에 첫 바퀴의 앞뒤 그대로 들어갔습니다**(T14 · T15 · T17 · T18).
첫 바퀴가 만든 그 넷의 순서가 `2 · 45 · 66 · 90` 이었고 그것이 자리 0 기준이라, 자리 1 이
같은 이 넷은 자리 0 이 대소를 정합니다. 그래서 그 순서가 곧 최종 순서예요(T21).

```text
바퀴가 둘로 끝나는 이유

  자리 1 이 다르면   그 자리가 대소를 정한다          258 · 301 은 513 보다 앞
  자리 1 이 같으면   자리 0 이 대소를 정한다          2 45 66 90 이 그 순서
                     └ 두 자리로 값 전체가 표현되므로 남는 경우가 없다
```

#### 4. 일곱 칸을 끝까지 정렬한다

접근이 2,168 번이고 반환값이 `[2, 45, 66, 90, 258, 301, 513]` 입니다. 스물두 단계를 한 자리에

갈래마다 조건이 어떻게 판정되는지 옮기면 아래 여섯입니다. ② 의 조건은 자리의 크기에 대한

| ② | `⌊max/place⌋ > 0` 이 **참**인 동안 | `place` 가 1 · 256 에서 참, 65,536 에서 거짓 | 2 |
| ③ | 바퀴마다 원소 일곱 개에 | T2 와 T12 | 14 |
| ④ | 바퀴마다 `count` 의 칸 255 개에 | T3 와 T13 | 510 |
| ⑤ | `i >= 0` 이 **참**인 동안 | T4 … T10 과 T14 … T20 | 14 |
| ⑥ | 바퀴 하나가 끝날 때마다 | T11 과 T21 | 2 |

**갈래 여섯이 모두 나왔습니다.** ② 가 **참**이 되는 자리(`place` 가 1 과 256)와 **거짓**이 되는
자리(`place` 가 65,536)가 둘 다 있고, ⑤ 도 일곱 번 참이 된 뒤 `i` 가 −1 이 되어 끝납니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 없어요 — 조각을 그대로 붙이고
`B` 를 상수로 뺐습니다.

```ts
/**
 * 자리 하나가 담는 값의 가짓수. 값을 256 진법으로 본다 — 자리 하나가 한 바이트다.
 * 이 값이 커지면 바퀴 수가 줄고 `count` 의 칸 수가 는다.
 */
const BASE = 256;

/** `A` 를 오름차순으로 정렬한 **새 배열**을 돌려준다. `A` 자체는 바뀌지 않는다. */
export function radixSort(A: number[]): number[] {
  let src = [...A];
  let dst = new Array<number>(A.length).fill(0);

  // ① 최댓값이 바퀴 수를 정한다. 값이 큰 만큼만 자리를 본다.
  let max = 0;
  for (const x of src) if (x > max) max = x;

  // ② 자리를 낮은 쪽부터 하나씩 올린다. `place` 가 지금 보는 자리의 크기다.
  for (let place = 1; Math.floor(max / place) > 0; place *= BASE) {
    // ③ 이 자리의 값마다 몇 개인지 센다. 여기에 두 값을 견주는 자리가 없다.
    const count = new Array<number>(BASE).fill(0);
    for (const x of src) {
      const dig = Math.floor(x / place) % BASE;
      count[dig] = (count[dig] as number) + 1;
    }

    // ④ 누적합으로 덮는다. `count[dig]` 가 「자리 값이 `dig` 이하인 원소의 개수」가 된다.
    for (let dig = 1; dig < BASE; dig++) {
      count[dig] = (count[dig] as number) + (count[dig - 1] as number);
    }

    // ⑤ 뒤에서 앞으로 읽으며 놓는다. 이 방향이라야 같은 자리 값의 순서가 유지된다.
    for (let i = src.length - 1; i >= 0; i--) {
      const x = src[i] as number;
      const dig = Math.floor(x / place) % BASE;
      count[dig] = (count[dig] as number) - 1;
      dst[count[dig] as number] = x;
    }

    // ⑥ 두 배열의 역할을 맞바꾼다. 다음 바퀴가 방금 쓴 쪽을 읽는다.
    [src, dst] = [dst, src];
  }

  return src;
}
```

```text
radixSort([513, 45, 258, 2, 66, 90, 301])  →  [2, 45, 66, 90, 258, 301, 513]
radixSort([170, 45, 75, 90, 802, 24, 2, 66]) → [2, 24, 45, 66, 75, 90, 170, 802]
radixSort([1000000000, 0, 999999999, 1])   →  [0, 1, 999999999, 1000000000]
radixSort([0, 0, 0])                       →  [0, 0, 0]
radixSort([12345])                         →  [12345]
radixSort([])                              →  []
```

### 알아 두면 좋은 개념 — 다중 키 정렬

앞에서 자리 0 과 자리 1 을 **키 둘**로 보고, 덜 높은 키부터 안정 정렬을 되풀이했습니다. 키가
자릿수일 필요는 없어요. 레코드를 「부서 오름차순, 같으면 이름 오름차순」으로 정렬하는 일도 같은
모양이고, 이것을 다중 키 정렬(multi-key sort)이라고 부릅니다.

```text
자리를 키로 바꿔 읽으면

  자리 0 과 자리 1            →  키 둘짜리 레코드
  낮은 자리부터               →  덜 높은 키부터
  같은 자리 값끼리 앞뒤 유지  →  안정 정렬
```

본문의 어느 값이 그것이었는지 확인하면, 둘째 바퀴에서 자리 1 이 0 인 넷 `2 · 45 · 66 · 90` 이
자리 0 순서로 남은 자리입니다. 「덜 높은 키를 먼저, 더 높은 키를 나중에」가 그 넷을 그대로
남긴 규칙이에요.

| 같은 규칙이 나오는 자리 | 덜 높은 키 | 더 높은 키 |
| --- | --- | --- |
| 이 편의 자릿수 정렬 | 자리 0 | 자리 1 |
| 표를 두 열로 정렬하기 | 이름 | 부서 |
| 좌표를 정렬해 스위핑 준비 | `y` | `x` |

**되풀이 순서를 반대로 하면 안 됩니다.** 더 높은 키를 먼저 정렬하면 나중 정렬이 그 순서를
덮어써요 — 앞에서 값으로 본 `[513 2 258 45 301 66 90]` 이 그 결과입니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 임의의 `N` 과 `M` 으로 비용을
어떻게 내는지, 무엇이 매 바퀴 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 걸리면 이 절차가 답이 됩니다. 앞의 둘이 필수이고 뒤의 둘은 이 절차가 덤으로
주는 것이에요.

- **키가 고정 폭 정수이고 상한을 압니다.** 값에서 자리 값을 나눗셈과 나머지로 바로 얻을 수
  있어야 합니다. 실수나 길이가 제각각인 문자열은 그대로는 자리로 갈리지 않아요.
- **값의 상한 `M` 이 커서 계수 정렬을 그대로 쓸 수 없습니다.** `M` 이 `N` 과 비슷하거나
  작으면 자리로 쪼갤 이유가 없고, 계수 정렬 한 바퀴가 더 적습니다.
- **최악에도 같은 시간이 나와야 합니다.** 값의 순서가 비용을 하나도 바꾸지 않습니다.
- **같은 값에 딸린 정보의 앞뒤를 지켜야 합니다.** 이 절차는 원소를 통째로 옮기므로 딸린
  정보가 함께 가고, 안정성까지 그대로 얻습니다.

```text
조건이 코드의 모양을 그대로 정한다

  키가 고정 폭 정수다           →  자리를 나눗셈과 나머지로 뽑는다
  값의 상한을 안다              →  바퀴 수를 최댓값에서 정한다
  견주기가 비용이 크다          →  코드에 견주기가 한 줄도 없다
  같은 값의 앞뒤를 지켜야 한다  →  뒤에서 앞으로 놓는다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "0 이상 10^9 이하의 정수"      "32 비트 정수 배열을 정렬하라"
  "O(N) 에 정렬하라"             "비교 정렬의 하한보다 빨라야 한다"
  "IP 주소, 타임스탬프, 아이디"  "고정 길이 문자열을 사전순으로"

제약에 이런 모양이 보이면
  값의 상한이 N 보다 훨씬 크다   ← 계수 정렬을 그대로 쓸 수 없는 구간이다
  키가 여러 항목으로 이루어진다  ← 자리 대신 항목을 키로 두면 그대로 통한다
```

「값의 상한이 크다」가 단서인 이유는 그 문장이 **계수 정렬을 막는 조건**이면서 동시에 **자리로
쪼갤 수 있는 조건**이기 때문입니다. 상한을 알아야 자릿수가 정해지고, 자릿수가 정해져야 바퀴
수가 상수가 돼요.

반대로 「값이 임의의 실수다」거나 「키를 견주는 함수만 주어진다」는 말이 있으면 이 단서는 해당
하지 않습니다. 그때는 견주기만으로 순서를 정하는 절차를 골라야 해요.

#### 실제로 쓰이는 곳

- **Apache Spark 의 `RadixSort`** — *"Sorts a given array of longs using least-significant-digit
  radix sort"* 라고 소스가 적어 두었고, **이 편이 가르치는 모양 그대로**입니다. 한 바퀴가 1
  바이트(자리 값 256 가지)이고, 미리 한 번 차례로 읽어 **모든 원소의 그 바이트가 같으면 그 바퀴를
  건너뜁니다** — *"Optimization: do a fast pre-pass to determine which byte indices we can skip
  for sorting"*.
  ([`org/apache/spark/util/collection/unsafe/sort/RadixSort.java`](https://github.com/apache/spark/blob/master/core/src/main/java/org/apache/spark/util/collection/unsafe/sort/RadixSort.java),
  조회 2026-08-30)
- **NumPy 의 `np.sort(kind="stable")`** — 정수 타입에서 이 절차로 갑니다. 자리 하나가 한
  바이트라 `cnt[l][nth_byte(k, l)]` 로 바이트마다 히스토그램을 만들고, 값이 한 가지뿐인 바이트는
  건너뛰어요(`if (cnt[l][nth_byte(key0, l)] != num) { cols[ncols++] = l; }`).
  ([`numpy/_core/src/npysort/radixsort.hpp`](https://github.com/numpy/numpy/blob/main/numpy/_core/src/npysort/radixsort.hpp),
  조회 2026-08-30)
- **ClickHouse 의 `RadixSort`** — `radixSortLSDInternal()` 과 `executeLSD()` 가 이 절차이고,
  자리 폭이 상수로 박혀 있습니다 — `static constexpr size_t PART_SIZE_BITS = 8;` 과
  `static constexpr size_t HISTOGRAM_SIZE = 1 << Traits::PART_SIZE_BITS;` 라 히스토그램이
  256 칸이에요.
  ([`src/Common/RadixSort.h`](https://github.com/ClickHouse/ClickHouse/blob/master/src/Common/RadixSort.h),
  조회 2026-08-30)

**셋 다 자리 하나를 8 비트로 둡니다.** 이 글이 `B = 256` 을 쓴 것과 같은 값이에요. 그리고 셋 중
둘은 **자리 값이 한 가지뿐인 바퀴를 건너뛰는** 손질을 더해 두었는데, 그 손질은 이 편의 코드에
없습니다 — 최댓값으로 바퀴 수를 줄이는 것까지만 합니다.

#### 경쟁 설계와의 대조

같은 목표를 노리는 **다른 절차**가 있습니다 — **병합 정렬**입니다. 값을 자리로 쪼개지 않고 두
값을 견주는 것만으로 순서를 정해요. 그래서 값이 고정 폭 정수가 아니어도, 심지어 견주기만 되는
값(문자열·객체)이어도 그대로 통합니다.

```text
병합 정렬이 하는 일
  구간을 반씩 가른다  →  각각을 정렬한다  →  정렬된 둘을 보조 배열을 거쳐 합친다
       └ 합치는 데 구간 길이만큼 견주고, 층수가 log2 N 이다
```

같은 입력에 둘을 실행해 **배열 접근 횟수와 견주기 횟수**를 셌습니다. 배열 접근은 배열 칸을 읽거나
쓴 횟수 전부이고, 두 설계가 쓰는 배열이 서로 달라(`count`·`src`·`dst` 대 복사본·보조 배열)
어느 한쪽만 빼면 대조가 성립하지 않습니다. 입력은 셋인데 하나는 전개가 쓰는 일곱 칸 그대로이고
나머지 둘은 난수 없이 식으로 만들었어요 — `A[i] = (i × 999,983) mod (10^9 + 1)` 로 200 칸 ·
100,000 칸입니다. 일곱 칸에서는 이 절차의 비용이 거의 전부 `count` 의 256 칸에서 나와 두
설계의 성질이 안 갈리기 때문에 큰 입력을 함께 잽니다.

| 계수 | 자릿수 정렬 (이 가이드) | 병합 정렬 |
| --- | --- | --- |
| 일곱 칸 배열 접근 | 2,168 | **129** |
| 일곱 칸 견주기 | **0** | 14 |
| 200 칸 배열 접근 | 10,484 | **8,400** |
| 200 칸 견주기 | **0** | 812 |
| 10 만 칸 배열 접근 | **3,204,084** | 9,455,258 |
| 10 만 칸 견주기 | **0** | 1,239,773 |
| 10 만 칸 새로 잡는 칸 | 201,024 | **200,000** |

**견주기 축에서는 이 절차가 0 번으로 앞섭니다.** 어느 칸 수에서도 0 이고, 병합 정렬은 10 만
칸에서 1,239,773 번을 견줍니다. 견주기 하나가 값 하나를 읽는 것보다 비용이 큰 자리 — 문자열
대조나 사용자 함수 호출 — 에서는 그 0 이 그대로 이득이에요.

**배열 접근 축에서는 칸 수가 갈립니다.** 일곱 칸에서 2,168 대 129 이고 200 칸에서 10,484 대
8,400 이라 병합 정렬이 적은데, 10 만 칸에서는 3,204,084 대 9,455,258 로 이 절차가 약 2.95 배
적습니다. 새로 잡는 칸은 201,024 대 200,000 으로 병합 정렬이 1,024 칸 적어요 — 그 1,024 가
바퀴 넷의 `count` 입니다.

```text
축을 넷으로 갈라 적으면
                            자릿수 정렬     병합 정렬
  200 칸 배열 접근               10,484         8,400     ← 병합이 적다
  10 만 칸 배열 접근          3,204,084     9,455,258     ← 자릿수가 적다
  10 만 칸 견주기                     0     1,239,773     ← 자릿수가 적다
  10 만 칸 새로 잡는 칸         201,024       200,000     ← 병합이 적다
```

**이 절차가 내주는 것은 적용 범위입니다.** 키가 고정 폭 정수가 아니면 자리로 갈리지 않아 아예
쓸 수 없어요. 병합 정렬은 견주기만 되면 무엇이든 정렬합니다. 그리고 값의 상한이 커지면 바퀴가
느는데, 그것은 병합 정렬에는 없는 비용이에요.

```text
같은 목표에 두 설계가 요구하는 것

  자릿수 정렬   키가 고정 폭 정수다           못 지키면 아예 쓸 수 없다
  병합 정렬     두 값을 견줄 수 있다          정수든 문자열이든 객체든 통한다
                └ 적용 범위가 좁은 쪽이 그 대가로 견주기 0 번을 얻는다
```

**우열이 반대가 되는 자리를 값으로 댈 수 있습니다.** 같은 생성식으로 칸 수만 늘려 가며 두
설계의 배열 접근을 재면, 순서가 뒤집히는 지점이 하나로 정해집니다.

<!--proof:alt-crossover-->

```text
생성식으로 만든 입력   자릿수 정렬 접근   병합 정렬 접근     어느 쪽이 적은가
200 칸                           10,484            8,400     병합 정렬이 적다
309 칸                           13,972           13,955     병합 정렬이 적다
310 칸                           14,004           14,008   자릿수 정렬이 적다
100,000 칸                    3,204,084        9,455,258   자릿수 정렬이 적다
                                                           └ 310 칸에서 처음으로 순서가 뒤집힌다
```

값의 상한이 10^9 인 이 문제에서 경계는 310 칸입니다. 그보다 작은 입력이 아주 많이 들어오는
상황이라면 병합 정렬이 답이고, 제약 상한 쪽인 100,000 칸이면 이 절차가 답이에요. 경계를
정하는 것은 칸 수 하나가 아니라 **`N` 과 `d·B` 의 대소**입니다.

### 수식 정의와 유도

값 `x` 의 `p` 번째 자리 값을 $\mathrm{digit}(x, p)$ 로, 최댓값 $M$ 에 필요한 바퀴 수를 $d(M)$
으로 정의합니다. 자리는 0 부터 세고, 0 번째가 가장 낮은 자리예요.

$$\mathrm{digit}(x, p) \;=\; \left\lfloor \frac{x}{B^{p}} \right\rfloor \bmod B$$

| 식의 조각 | 무엇인가 | `x = 513` · `p = 1` 일 때 |
| --- | --- | --- |
| $B^{p}$ | `p` 번째 자리의 크기 | 256 |
| $\lfloor x / B^{p} \rfloor$ | 그 자리 위쪽까지 남긴 몫 | 2 |
| $\dots \bmod B$ | 그 자리 하나만 남긴 나머지 | 2 |

$$d(M) \;=\; \lfloor \log_B M \rfloor + 1 \quad (M \ge 1), \qquad d(0) = 0$$

정의를 전개 입력의 값에 넣어 검산해 봅시다. $B = 256$ 이고 $M = 513$ 입니다.

| 넣는 값 | 계산 | 결과 |
| --- | --- | --- |
| $\mathrm{digit}(513, 0)$ | $\lfloor 513/1 \rfloor \bmod 256 = 513 \bmod 256$ | 1 |
| $\mathrm{digit}(513, 1)$ | $\lfloor 513/256 \rfloor \bmod 256 = 2 \bmod 256$ | 2 |
| $\mathrm{digit}(2, 1)$ | $\lfloor 2/256 \rfloor \bmod 256 = 0 \bmod 256$ | 0 |
| $d(513)$ | $\lfloor \log_{256} 513 \rfloor + 1 = \lfloor 1.0016 \rfloor + 1$ | 2 |
| $d(10^9)$ | $\lfloor \log_{256} 10^9 \rfloor + 1 = \lfloor 3.7369 \rfloor + 1$ | 4 |

$d(2) = 1$ 인데 전개는 값 2 에도 바퀴를 둘 실행합니다. 바퀴 수를 원소마다 따로 정하지 않고
**최댓값 하나로** 정하기 때문이고, 값 2 의 없는 자리 1 은 $\mathrm{digit}(2,1) = 0$ 으로
채워져요. 그래서 짧은 값이 저절로 앞에 옵니다.

**이제 비용을 유도합니다.** 배열 칸을 읽거나 쓴 횟수를 $T$ 라 두고 준비와 바퀴로 가릅니다.
바퀴 하나는 다시 넷으로 갈리는데, 자리 값 세기가 원소마다 세 번(입력 읽기 · 개수 읽기 · 개수
쓰기)이고 놓기가 원소마다 네 번(입력 읽기 · 개수 읽기 · 개수 쓰기 · 결과 쓰기)이에요.

| 조각 | 무엇을 하는가 | 접근 횟수 |
| --- | --- | --- |
| 준비 | 사본 만들기 · `dst` 초기화 · 최댓값 찾기 | `2N + N + N` |
| 바퀴 하나 | 칸 만들기 · 자리 값 세기 · 누적합 · 놓기 | `B + 3N + 3(B−1) + 4N` |

$$T_{\text{준비}} \;=\; \underbrace{2N}_{\text{사본}} + \underbrace{N}_{\text{dst 초기화}} + \underbrace{N}_{\text{최댓값}} \;=\; 4N$$

$$T_{\text{바퀴}} \;=\; B + 3N + 3(B-1) + 4N \;=\; 7N + 4B - 3$$

```text
B = 256 · N = 7 을 두 식에 넣으면

  준비        28      4 × 7
  바퀴 하나   1,070   7×7 + 4×256 − 3
  바퀴 둘     2,140   2 × 1,070
              └ 합 2,168 로 전개 입력의 실측과 같다
```

바퀴가 $d(M)$ 번이므로 둘을 합치면 총식이 나옵니다.

$$T(N, B, M) \;=\; 4N + d(M)\,\bigl(7N + 4B - 3\bigr)$$

```ts
const total = (N: number, B: number, d: number): number =>
  4 * N + d * (7 * N + 4 * B - 3);

total(7, 256, 2);       // = 2168     전개 입력의 실측과 같다
total(100_000, 256, 4); // = 3204084  제약 상한의 실측과 같다
```

| 식의 기호 | 코드에서는 | 어디에 있는가 |
| --- | --- | --- |
| $B$ | `BASE` | 상수로 뺀 자리 하나의 가짓수 |
| $B^{p}$ | `place` | 바퀴마다 `BASE` 배가 된다 |
| $M$ | `max` | ① 이 찾아 두는 최댓값 |
| $d$ | 이름이 없다 | `place` 가 `max` 를 넘을 때까지 반복하는 것으로 대신한다 |

**여기서 `B` 를 자유롭게 두면 본문의 표가 못 주는 것이 나옵니다.** 바퀴를 $d$ 번으로 정하면 한
자리가 담아야 하는 값의 가짓수는 $B^{d} > M$ 을 만족하는 최소값이므로 $B = \lceil (M+1)^{1/d}
\rceil$ 이고, 그것을 위 식에 넣으면 비용이 $d$ 하나의 함수가 돼요.

$$T^{*}(d) \;=\; 4N + d\,\Bigl(7N + 4\bigl\lceil (M+1)^{1/d} \bigr\rceil - 3\Bigr)$$

| `d` 를 하나 줄이면 | 무엇이 달라지는가 | 어느 쪽이 커지는가 |
| --- | --- | --- |
| 줄어드는 항 | `7N` 이 한 벌 빠진다 | `N` 이 클수록 크다 |
| 늘어나는 항 | `B` 가 `(M+1)^(1/d)` 로 커진다 | `M` 이 클수록 크다 |

두 $d$ 를 견주는 부등식을 $N$ 에 대해 풀면 어느 쪽이 적어지는 경계가 값으로 나옵니다.
$M = 10^9$ 을 넣고 $d$ 를 다섯까지 봅시다.

<!--proof:math-scale-->

```text
바퀴 수 d   한 자리 최소 가짓수   N = 100,000 에서의 T   d + 1 바퀴보다 적어지는 첫 N
2                        31,623              2,052,978                  34,425 칸부터
3                         1,001              2,512,003                   1,310 칸부터
4                           178              3,202,836                     225 칸부터
5                            64              3,901,265                      74 칸부터
                                                         └ 이 편의 B = 256 은 같은 자리에서 3,204,084 번이라 최솟값 2,052,978 번의 1.6 배다
```

닫힌 형태가 주는 것이 여기 있습니다. 파트 1 의 스윕 표는 잰 여섯 값에서만 답을 냈는데, 이 식은
**임의의 `N` 에서 최적 바퀴 수를 내요** — 74 · 225 · 1,310 · 34,425 를 넘을 때마다 바퀴가
하나씩 줄어드는 것이 그 답입니다. 실제로 정렬해 보지 않고도 「칸이 34,425 개를 넘으면 두
바퀴짜리가 가장 적다」고 말할 수 있어요.

### 불변식 — 바퀴 하나가 끝날 때마다 그때까지 본 자리들 기준으로 정렬돼 있다

파트 1 에서 코드가 동작하는 것을 스물두 단계로 확인했습니다. 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 문장으로 세우고, 그것이
실제로 유지되는지 확인해 봅시다.

> **자리 `p` 를 처리한 바퀴가 끝난 시점마다**, `src` 는 각 값의 **자리 0 부터 자리 `p` 까지만
> 남긴 수**를 기준으로 오름차순이고, 그 수가 같은 원소끼리는 입력에서의 앞뒤가 그대로입니다.

```text
바퀴 하나가 끝난 시점의 src

  첫 바퀴 뒤     [513 258 2 45 301 66 90]   자리 0 만 보면 1 2 2 45 45 66 90
  둘째 바퀴 뒤   [2 45 66 90 258 301 513]   자리 1 만 보면 0 0 0 0 1 1 2
                 └ 자리 값이 같은 칸끼리는 앞 바퀴의 앞뒤가 그대로 남아 있다
```

「자리 0 부터 자리 `p` 까지만 남긴 수」가 중요합니다. 첫 바퀴 뒤의 배열은 값 전체로 보면 정렬이
아니지만 `x mod 256` 으로 보면 오름차순이고, 마지막 바퀴에서 `p` 가 최고 자리에 이르면 그
「남긴 수」가 값 전체와 같아져 정렬이 끝나요.

**출발점부터 봅시다.** 바퀴를 한 번도 실행하지 않은 시점에는 `p` 가 없고 「남긴 수」가 모두 0
이라 어느 배열이든 오름차순이며 앞뒤도 입력 그대로입니다. 그다음 바퀴 하나가 무엇을 하는지 세
조각으로 갈라 봅니다.

| 바퀴의 조각 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| 자리 값 세기 | `count[dig]` 가 자리 값 `dig` 인 원소의 개수 | 원소마다 정확히 한 칸을 1 늘리므로 개수의 합이 `N` 이다 |
| 누적합 | `count[dig]` 가 자리 값 `dig` 이하인 개수 | 자리 값이 작은 원소가 먼저 놓일 칸을 받으므로 결과가 자리 `p` 기준 오름차순이 된다 |
| 뒤에서 앞으로 놓기 | 자리 값이 같으면 `src` 의 뒤쪽이 큰 칸부터 | `count[dig]` 를 줄이며 놓으므로 뒤쪽 원소가 뒤쪽 칸을 받고, 앞뒤가 그대로 남는다 |

셋이 전부입니다. 자리 `p` 가 다른 원소끼리는 두 번째 조각이 순서를 정하고, 자리 `p` 가 같은
원소끼리는 세 번째 조각이 앞 바퀴의 순서를 그대로 넘겨요. 앞 바퀴의 순서는 「자리 0 부터
자리 `p−1` 까지만 남긴 수」 기준이므로, 둘을 합치면 자리 `p` 까지의 수 기준이 됩니다.

**경계에 있는 입력도 확인하고 갑시다.** 아래 여섯 줄이 이 함수가 받을 수 있는 모양의 끝입니다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 빈 배열 `[]` | 최댓값이 0 이라 바퀴가 한 번도 실행되지 않는다 | `[]` (새 배열) |
| 값이 전부 0 인 `[0 0 0]` | 같은 이유로 바퀴가 없고 사본이 그대로 나온다 | `[0 0 0]` |
| 칸 하나 `[12345]` | 최댓값이 12,345 라 바퀴가 둘, 칸이 하나뿐이다 | `[12345]` |
| 값이 전부 같음 `[7 7 7]` | 바퀴마다 자리 값이 같아 앞뒤가 그대로 유지된다 | `[7 7 7]` |
| 자릿수가 섞임 `[1 10 100 1000]` | 짧은 값의 높은 자리가 0 이라 앞에 온다 | `[1 10 100 1000]` |
| 값의 상한 `[10^9 0]` | 최댓값이 10^9 이라 바퀴가 넷이다 | `[0 10^9]` |

**이제 깨뜨려 봅시다.** 불변식의 뒷문장 — 자리 값이 같으면 앞뒤가 그대로다 — 을 지키는 줄은
`for (let i = src.length - 1; i >= 0; i--)` 하나입니다. 그 줄을 앞에서 뒤로 읽는 반복으로
바꾸면 같은 자리 값끼리의 앞뒤가 뒤집혀요. 바꾸고 실행해 봅니다.

```ts
// for (let i = src.length - 1; i >= 0; i--) {
for (let i = 0; i < src.length; i++) { // ← 이 한 줄만 바꿨다
```

```text

[513 45 258 2 66 90 301]     [2 45 66 90 258 301 513]     [90 66 45 2 301 258 513]
[170 45 75 90 802 24 2 66]   [2 24 45 66 75 90 170 802]   [170 90 75 66 45 24 2 802]
[12 12 1 1 100 100]          [1 1 12 12 100 100]          [1 1 12 12 100 100]
[0 10 0 1]                   [0 0 1 10]                   [0 0 1 10]
[12345]                      [12345]                      [12345]
                                                          └ 다섯 벌 중 2 벌에서 답이 어긋난다
```

`[513 45 258 2 66 90 301]` 이 `[90 66 45 2 301 258 513]` 이 됐습니다. 앞의 넷 `90 66 45 2` 는
자리 1 이 0 인 넷인데 **내림차순**이에요. 첫 바퀴가 낸 그 넷의 앞뒤와 마지막 바퀴가 낸 앞뒤를
나란히 보면 어디서 뒤집혔는지가 나옵니다.

<!--proof:mutant-forward-groups-->

```text
자리 1 이 0 인 넷의 앞뒤   첫 바퀴 뒤   마지막 바퀴 뒤
뒤에서 앞으로(바른 코드)   2 45 66 90   2 45 66 90
앞에서 뒤로 놓은 코드      2 45 66 90   90 66 45 2
                                        └ 첫 바퀴가 낸 앞뒤는 같고, 마지막 바퀴가 그 넷을 뒤집었다
```

아래 세 벌에서 답이 안 어긋난 것은 뒤집을 것이 없었기 때문입니다. `[12345]` 는 칸이 하나이고,
`[12 12 1 1 100 100]` 과 `[0 10 0 1]` 은 자리 값이 같은 원소가 **값까지 같아서** 앞뒤가 바뀌어도
결과에서 구별되지 않아요. 이 절차의 안정성은 값이 같은 원소가 아니라 **자리 값만 같은 원소**를
위한 것입니다.

### 비용 계산

배열 접근이 어디서 나오는지를 전개의 값으로 세고, 케이스와 경계를 갈라 적은 다음, 최악을 실제로
내는 입력을 만들어 봅니다.

#### 비용을 세는 과정

전개의 스물두 단계를 갈래별로 묶으면 여섯입니다. T1 이 ①, 바퀴가 시작될 때마다 ②,
T2 · T12 가 ③, T3 · T13 이 ④, T4 … T10 과 T14 … T20 이 ⑤, T11 과 T21 이 ⑥ 이에요.

```text
한 바퀴가 배열을 몇 번 건드리는가

  칸 만들기      B 번 쓰기         256
  자리 값 세기   원소마다 3 번     21
  누적합         (B-1) 마다 3 번   765
  놓기           원소마다 4 번     28
                 └ 한 바퀴 합 1,070 번. 바퀴가 둘이라 2,140 번이고 준비가 28 번 더 든다
```

`count` 를 만들고 누적합으로 덮는 데만 한 바퀴 1,021 번이 듭니다. 일곱 칸을 세고 놓는 데 드는
49 번의 스무 배가 넘어요 — 그 1,021 번은 입력이 몇 칸이든 바퀴마다 그대로 나는 비용입니다.

```text
네 조각을 기호로 다시 적으면

  칸 만들기      B 번            입력과 무관
  자리 값 세기   3N 번           원소마다 세 번
  누적합         3(B-1) 번       입력과 무관
  놓기           4N 번           원소마다 네 번
                 └ 바퀴 합 7N + 4B − 3. 바퀴가 d 번이고 준비가 4N 이라 4N + d(7N + 4B − 3)
```

나머지 작업 — `place` 와 `i` 의 증감 · 반복 조건 판정 — 은 걸음마다 상수 번이라 위 네 항에 상수
배로 묶입니다. 그리고 두 값을 견주는 자리는 코드 어디에도 없어서 견주기 항이 아예 없어요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (`1 ≤ M < B` 라 바퀴가 하나) | `O(N + B)` | `Θ(N + B)` — 실제로 도달한다 |
| **평균적인 경우** (어떤 입력 분포에서든) | `O(d(N + B))` | `Θ(d(N + B))` — 값의 순서가 비용을 안 바꾼다 |
| **최악의 경우** (최댓값이 `M` 의 상한) | `O(d(N + B))` | `Θ(d(N + B))` — 실제로 도달한다 |

**케이스를 가르는 것은 값의 순서가 아니라 최댓값입니다.** 입력을 보고 갈라지는 분기가 코드에
없어서, 칸 수와 최댓값이 같으면 접근 횟수가 글자 그대로 같아요. 견주기 횟수로 갈리는 절차 —
삽입 정렬이 그렇습니다 — 와 반대되는 자리입니다.

**총식을 한 번은 정확히 적습니다.** 아래 값은 **배열 접근만** 센 것이고, 인덱스 증감처럼
걸음마다 상수 번인 일은 상수 배로 묶었습니다.

| 조각 | 무엇을 세는가 | 접근 |
| --- | --- | --- |
| 준비 | 사본 · `dst` 초기화 · 최댓값 찾기 | `4N` |
| 바퀴 `d` 번 | 바퀴마다 세고 · 누적하고 · 놓는다 | `d(7N + 4B − 3)` |
| 시간 | 두 항을 더한 것 | `Θ(d(N + B))` · 이 문제는 `d ≤ 4` |
| 새로 잡는 칸 | `src` · `dst` 가 각각 `N` 칸, `count` 가 바퀴마다 `B` 칸 | `Θ(N + dB)` |

`B` 와 `M` 이 둘 다 상수인 이 문제에서는 `d` 도 상수라 `Θ(N)` 이 됩니다. 두 표기가 같은 것을
말하는데 앞쪽이 더 정확해요 — 뒤쪽은 「값의 상한이 커지면 바퀴가 는다」를 표현할 자리가
없습니다.

**보장의 종류는 최악 보장입니다.** 코드에 난수가 없고, 같은 칸 수와 같은 최댓값에는 입력이
무엇이든 늘 같은 횟수가 나와요. 평균을 말할 때 흔히 붙는 입력 분포 가정도 여기서는 필요가
없습니다 — 분포를 무엇으로 두든 최댓값이 같은 모든 입력의 값이 같으므로 기댓값이 그 값입니다.

#### 최악을 만드는 입력

「역순 입력이 최악」이라는 말이 이 절차에서는 **참이 아닙니다.** 값을 어떤 순서로 놓아도 비용이
같아요. 전개 입력 일곱 칸의 서로 다른 배치를 전부 세어 확인하고, 최댓값과 칸 수를 바꿔 가며
함께 잽니다.

<!--proof:worst-input-->

```text
입력                             바퀴 수   배열 접근   원소당 접근
최댓값 255 인 일곱 칸                  1       1,098         156.9
전개 입력 일곱 칸 (최댓값 513)         2       2,168         309.7
최댓값 10^9 인 일곱 칸                 4       4,308         615.4
최댓값 10^9 인 한 칸                   4       4,116       4,116.0
최댓값 10^9 인 100,000 칸              4   3,204,084          32.0
                                                       └ 전개 입력의 배치 5,040 가지는 접근이 전부 2,168 번으로 같다
```

**배치 5,040 가지가 전부 2,168 번입니다.** 그러니 이 절차의 최악은 「값을 어떻게 놓는가」가
아니라 **「최댓값이 몇 자리인가」와 「칸 수에 견주어 바퀴가 얼마나 무거운가」** 에서 나옵니다.
값 하나만 10^9 으로 바꾸면 같은 일곱 칸이 1,098 번에서 4,308 번이 돼요.

```text
최악을 실제로 만드는 방법

  일곱 칸 중 하나를 10^9 으로 둔다          바퀴가 1 에서 4 로 늘어 접근이 3.9 배
  칸 수 N 을 1 로 두고 최댓값을 10^9 으로   접근 4,116 번, 원소당 4,116 번
                                            └ 최악은 바퀴 수와 B 의 곱이 N 보다 클 때다. 값의 순서는 영향이 없다
```

이 최악을 **피하는 장치가 이 절차에 하나 있습니다** — 바퀴 수를 최댓값에서 정하는 ① 이 그것
이고, 그래서 최댓값 255 인 일곱 칸은 바퀴가 하나로 끝납니다. 다만 최댓값이 정말 10^9 이면 그
장치가 할 일이 없어요. 그때는 자리 하나의 가짓수 `B` 를 칸 수에 맞춰 키우는 것이 남은 길이고,
이 편은 `B` 를 256 으로 고정했으므로 그 길을 쓰지 않습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 값의 상한이 커서 칸을 만들 수 없을 때 값을
자리 여럿으로 쪼개고, 자리 하나를 키로 하는 안정 정렬을 낮은 자리부터 되풀이하면, 마지막
바퀴가 가장 높은 자리를 정하고 앞 바퀴들이 동점을 가릅니다.

```text
최댓값의 자릿수만큼 되풀이한다

  자리 값을 센다 → 누적합으로 칸을 정한다 → 뒤에서 앞으로 놓는다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T17 에서 45 가 칸 1 에 놓였고, 그 앞뒤로 T14 · T15 ·
T18 이 자리 값 0 인 나머지 셋을 칸 3 · 2 · 0 에 놓았습니다. 둘째 바퀴만 **앞에서 뒤로** 읽도록
바꾸면 그 넷은 어느 칸에 놓이고 최종 결과는 무엇이 될까요?

```text
자리 값 0 인 넷은 첫 바퀴 뒤 배열에서 i = 2 · 3 · 5 · 6 (값 2 · 45 · 66 · 90) 이다
```

<!--check:passOrder-->
**칸 3 · 2 · 1 · 0 에 그 순서로 놓여 `[90 66 45 2 301 258 513]` 이 됩니다.** 앞에서 뒤로
읽으면 `i` 가 작은 원소가 먼저 `count[0]` 을 줄이므로 큰 칸을 받고, 그 결과 넷의 앞뒤가
뒤집혀요. 이 값은 두 바퀴를 다 바꾼 「불변식」 절의 결과와 **같습니다** — 그 절의 증명 블록이
보인 대로 첫 바퀴는 이 넷의 앞뒤를 바꾸지 않기 때문이에요.

```text
같은 넷이 어느 칸을 받는가

  뒤에서 앞으로   i = 6 → 칸 3, i = 5 → 칸 2, i = 3 → 칸 1, i = 2 → 칸 0
  앞에서 뒤로     i = 2 → 칸 3, i = 3 → 칸 2, i = 5 → 칸 1, i = 6 → 칸 0
                  └ 같은 자리 값을 받는 칸 묶음은 같고, 그 안의 배정 순서만 반대다
```

정렬 결과만 보면 값이 다른 원소는 어차피 자리 값이 갈리니 괜찮아 보이지만, 자리 값이 같은
원소끼리는 앞 바퀴의 순서가 유일한 근거라 그것을 뒤집으면 답이 어긋납니다.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「비용 계산」의 총식과 파트 1 의 스윕 표     3 → 「실제로 쓰이는 곳」
  2 → 「수행으로 알아보는 알고리즘」의 T2 와 T12
```

- 이 편은 `B` 를 256 으로 고정했습니다. 같은 코드에서 `B` 만 32,768 로 바꾸면 최댓값 10^9 인
  입력에서 바퀴가 넷에서 둘로 줍니다. 그때 100,000 칸과 1 칸에서 배열 접근이 각각 어떻게
  변하는지, 그리고 그 둘 중 어느 쪽이 이 문제의 제약에서 더 중요한지 답해 보세요.
- T2 는 자리 0 을, T12 는 자리 1 을 셌고 둘 다 `count` 를 새로 만들어 썼습니다. 만약 `count` 를
  바퀴마다 새로 만들지 않고 첫 바퀴의 것을 그대로 이어 쓰면 둘째 바퀴의 누적합이 무엇이 되고,
  `dst` 의 어느 칸이 어긋나는지 답해 보세요.
- 입력에 음수가 섞이면(`-10^9 ≤ A[i] ≤ 10^9`) 이 절차를 그대로 쓸 수 없습니다. 「실제로 쓰이는
  곳」의 세 구현은 부호 있는 정수를 정렬하는데, 그 셋이 어떤 손질을 넣었을지 추측하고 그
  손질이 이 편의 어느 줄에 들어가야 하는지 적어 보세요.
