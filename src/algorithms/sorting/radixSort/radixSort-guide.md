# 자릿수 정렬 — 가장 높은 자리를 마지막에 처리해야 앞 바퀴의 순서가 남는다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 모든 쌍을 비교하는
방법에서 출발해 값을 자리로 쪼개 낮은 자리부터 정렬을 되풀이하는 방법까지 가고, 그 방법을 단계마다 값으로 푼
뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

정수 `513` 을 256 진법으로 적으면 `2 × 256 + 1` 입니다. 이때 256 으로 나눈 나머지 `1` 을 **자리 0**, 256 으로
나눈 몫 `2` 를 **자리 1** 이라 부르겠습니다. 어느 자리든 값이 0 부터 255 까지 256 가지뿐이에요. 값 일곱 개를
이렇게 자리 둘로 나누면 아래와 같습니다.

<!--fig:concept-digits-->
![[513 45 258 2 66 90 301] 의 값마다 256 진법 자리 둘](./figs/concept-digits.svg)

자리 값이 256 가지뿐이면 그 자리 하나를 기준으로 정렬하는 데 두 값을 비교할 필요가 없습니다. 자리 값을 그대로
칸 번호로 삼아 개수를 세고, 칸 0 부터 차례로 꺼내면 그 자리 기준의 오름차순이 나와요. 자리 하나를 기준으로
배열 전체를 한 번 정렬하는 일을 이 글에서는 **바퀴**라고 부르겠습니다.

**자릿수 정렬**(LSD radix sort)은 이 바퀴를 **낮은 자리부터** 한 번씩 실행합니다. 바퀴마다 지키는 규칙이
하나 있어요. **자리 값이 같은 원소끼리는 앞 바퀴가 만든 앞뒤를 바꾸지 않습니다.** 이 규칙을 지키는 정렬을
안정 정렬이라고 해요. 같은 일곱 값에 자리 0 바퀴와 자리 1 바퀴를 차례로 실행하면 이렇게 됩니다.

<!--fig:concept-passes-->
![자리 0 바퀴 다음 자리 1 바퀴](./figs/concept-passes.svg)

바퀴 1 이 끝나면 자리 0 줄이 오름차순이고, 바퀴 2 가 끝나면 자리 1 줄이 오름차순입니다. 바퀴 2 뒤에 자리 1 이
0 으로 같은 넷(2 · 45 · 66 · 90)은 바퀴 1 이 정한 앞뒤를 그대로 가졌고, 그 앞뒤가 자리 0 기준이라 넷이 이미
바른 순서예요. 두 수의 대소는 높은 자리부터 보아 처음 달라지는 자리가 정하니까, **가장 높은 자리를 마지막
바퀴에 두면** 그 자리가 순서를 정하고 앞 바퀴들이 동점을 가릅니다.

이 절차에는 두 값을 비교하는 자리가 없습니다. 비용은 배열 칸을 읽거나 쓴 횟수(칸 접근)로 셉니다.

<!--proof:concept-cost-->

| 입력 | 최댓값 | 바퀴 | 비교 | 칸 접근 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 일곱 칸 | 513 | 2 | 0 | 2,168 |
| 생성식 100,000 칸 | 999,996,925 | 4 | 0 | 3,204,084 |

<!--/proof-->

바퀴 수는 최댓값이 256 진법으로 몇 자리인가가 정합니다. 결과만 적으면 비용은 `O(d(N + B))` 이고, `N` 은 칸
수, `B` 는 자리 하나의 가짓수 256, `d` 는 바퀴 수예요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **오름차순 정렬의 뜻** — 모든 이웃 쌍에서 앞 칸이 뒤 칸보다 크지 않고, 결과에 담긴 값들이 입력의 값들과
  **개수까지 같아야** 합니다. 뒤쪽 조건이 흐릿하면 「정렬됐는가」만 보는 검사를 통과하면서 값이 사라진 코드를
  알아볼 수 없습니다.
- **안정 정렬(stable sort)** — 정렬 기준으로 봤을 때 값이 같은 원소들의 **앞뒤가 바뀌지 않는** 정렬입니다.
  이 글의 절차는 안정성을 근거로 삼아서, 그것이 없으면 바퀴 둘이 서로의 결과를 덮어씁니다.
- **위치 기수법** — `513` 을 `2 × 256 + 1` 처럼 진법 하나로 자리 여럿에 나눠 적는 방식입니다. 자리는 낮은
  쪽부터 0 · 1 · 2 … 로 세고, 어느 자리든 값이 진법보다 작습니다.
- **계수 정렬** — 값의 종류가 적을 때 값마다 개수만 세어 정렬하는 절차입니다. 이 글은 그 절차를 자리 하나에
  적용해 되풀이해요. 모르면 [계수 정렬 가이드](../countingSort/countingSort-guide.md)를 먼저 보세요.
- **배열의 임의 접근** — 배열의 여덟 번째 칸을 읽는 데 앞의 일곱 칸을 지날 필요가 없습니다. 자리 번호만 있으면
  한 번에 그 칸입니다.

비교만으로 정렬하는 절차는 저장소에 둘 있습니다 — [병합 정렬 가이드](../sortArray/sortArray-guide.md)와
[삽입 정렬 가이드](../insertionSort/insertionSort-guide.md)입니다. 이 글을 읽고 나서 비교하면 비교하는
절차와 자리로 가르는 절차가 어느 기준에서 갈리는지 확인할 수 있어요.

### 아이디어를 떠올리는 과정 — 모든 쌍 비교에서 낮은 자리부터 되풀이하는 안정 정렬까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 0 이상의 정수 배열을 받아,
오름차순으로 정렬한 새 배열을 돌려줍니다.

```ts
function radixSort(A: number[]): number[];
```

- 입력: 0 이상의 정수 배열 `A`.
- 출력: `A` 의 모든 값을 오름차순으로 담은 **새 배열**. 입력 `A` 자체는 바뀌지 않습니다. 같은 값이 여럿이면
  그 개수 그대로 담깁니다. 빈 배열에는 빈 배열을 돌려줍니다.
- 규모: 칸 수 `N` 은 100,000 이하이고, 값은 0 이상 10^9 이하입니다. 비용은 흔한 채점 환경의 예산인 1 초 ·
  256 MB 에 대어 잽니다.
- 값의 상한이 정해져 있다는 것이 이 과제의 특징입니다. 다만 그 상한이 10^9 이라 넓습니다.

이 글이 끝까지 쓰는 기호는 아래 열 개이고, 여기서 정한 뜻을 바꾸지 않습니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 입력 배열 `A` 의 칸 수 | `0 ≤ N ≤ 100,000` |
| `A` | 정렬할 입력 배열. `A[i]` 가 `i` 번째 값 | `0 ≤ A[i] ≤ 10^9` |
| `M` | 입력의 최댓값 | `M ≤ 10^9` |
| `B` | 자리 하나가 담는 값의 가짓수. 곧 진법 | `B = 256` 으로 고정 |
| `d` | 바퀴 수. `M` 을 `B` 진법으로 적은 자릿수 | `M` 이 정한다 |
| `place` | 지금 보는 자리의 크기. 바퀴마다 `B` 배가 된다 | `1 · 256 · 65,536 · …` |
| `i` | 입력에서 지금 읽고 있는 자리 | `0 ≤ i ≤ N − 1` |
| `count` | 자리 값마다의 개수를 담는 배열 | 칸 수 `B` |
| `src` | 이번 바퀴가 읽는 배열 | 칸 수 `N` |
| `dst` | 이번 바퀴가 쓰는 배열 | 칸 수 `N` |

가장 먼저 떠오르는 방법은 **모든 쌍을 비교해 순서가 틀렸으면 맞바꾸는 것**입니다. 앞 자리 `j` 를 하나 잡고 그
뒤의 모든 자리 `t` 와 비교해 앞이 더 크면 맞바꾸는 일을, `j` 를 하나씩 늘려 가며 되풀이해요. 값이 정수라는
것도, 상한이 있다는 것도 하나도 쓰지 않습니다.

```ts
function sortNaive(A: number[]): number[] {
  const copy = Array.from(A);
  for (let j = 0; j < copy.length; j++) {
    for (let t = j + 1; t < copy.length; t++) {
      if ((copy[j] as number) > (copy[t] as number)) {
        const tmp = copy[j] as number;
        copy[j] = copy[t] as number;
        copy[t] = tmp;
      }
    }
  }
  return copy;
}
```

이 방법은 답을 틀리지 않습니다. 비용은 비교 횟수인데, `j` 번째 바퀴가 뒤의 `N − j − 1` 칸을 전부 비교하므로
**입력이 어떻게 놓여 있든** 합이 `N(N−1)/2` 입니다.

<!--proof:origin-naive-->

| 칸 수 | 모든 쌍 비교 | 시간(초당 1 억 번) |
| ---: | ---: | ---: |
| 7 | 21 | 0.00 초 |
| 1,000 | 499,500 | 0.00 초 |
| 100,000 | 4,999,950,000 | 50.00 초 |

칸 0 개부터 200 개까지 입력 세 모양에서 실제로 세어 모든 쌍 비교가 N(N−1)/2 번인 것을 확인했고, 큰 칸 수는 이 식으로 냈습니다.

<!--/proof-->

칸 100,000 개에서 비교가 약 50 억 번이고, 예산 1 초의 쉰 배입니다. 그러면 비교를 아예 안 하는 길이 있는지
봅시다. 값이 0 이상의 정수이니 **값 `v` 를 그대로 `count` 의 칸 번호로** 쓰면, 값의 자리를 찾는 데 비교가
한 번도 들지 않습니다. 계수 정렬이 이 방법이에요. 칸을 최댓값까지 만들어야 하는데, 실제로 만들어 보면 칸 수가
이렇게 됩니다.

<!--proof:origin-wide-->

| 입력 | 최댓값 | count 칸 수 | 칸 접근 | count 의 메모리(8 바이트씩) |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 일곱 칸 | 513 | 514 | 2,130 | 5 KB |
| 생성식 1,000 칸 | 998,983,017 | 998,983,018 | 3,995,943,069 | 8.0 GB |
| 생성식 100,000 칸 | 999,996,925 | 999,996,926 | 4,001,087,701 | 8.0 GB |

일곱 칸은 count 를 514 칸으로 잡아 실제로 실행해 센 값이고, 큰 두 입력은 같은 식에 칸 수를 넣은 값입니다.

<!--/proof-->

**걸리는 것이 비교가 아니라 키의 넓이로 바뀌었습니다.** 최댓값이 10^9 에 가까우면 `count` 가 약 10 억 칸이고,
한 칸을 8 바이트로 잡으면 예산 256 MB 를 한참 넘어요. 칸 1,000 개를 정렬하는 데도 그렇습니다. 칸 수를 정하는
것이 입력의 칸 수 `N` 이 아니라 값의 상한이기 때문입니다.

키를 좁히는 방법이 **값을 자리 여럿으로 쪼개는 것**입니다. 256 진법으로 적으면 자리 하나의 값은 0 … 255 라
`count` 가 256 칸이면 돼요. 그 대신 자리마다 한 바퀴씩, 최댓값의 자릿수만큼 바퀴를 실행해야 합니다. 값을 그대로
키로 쓰는 쪽과 자리로 쪼개는 쪽을 같은 입력에서 나란히 재 봅시다.

<!--proof:origin-split-->

| 입력 | 값 그대로 — count 칸 수 | 값 그대로 — 칸 접근 | 자리로 쪼갬 — 바퀴 | 자리로 쪼갬 — 칸 접근 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 일곱 칸 | 514 | 2,130 | 2 | 2,168 |
| 생성식 1,000 칸 | 998,983,018 | 3,995,943,069 | 4 | 36,084 |
| 생성식 100,000 칸 | 999,996,926 | 4,001,087,701 | 4 | 3,204,084 |

<!--/proof-->

일곱 칸에서는 자리로 쪼갠 쪽의 접근이 오히려 조금 많습니다. 최댓값이 513 뿐이라 값을 그대로 써도 `count` 가
514 칸이면 되고 바퀴도 하나로 끝나니까요. 최댓값이 10^9 에 가까운 두 입력에서는 값 그대로가 약 40 억 번이고,
자리로 쪼개면 칸 100,000 개에서도 320 만 번 남짓입니다. 여기서 관찰한 것은 둘입니다. **자리로 쪼개면
`count` 가 256 칸으로 묶이고, 그 대가로 바퀴가 여럿이 됩니다.** 그리고 바퀴 여럿을 어떤 순서로 이어야 맞는
답이 나오는지는 아직 정하지 않았어요.

가장 단순한 후보는 **높은 자리부터** 바퀴를 실행하는 것입니다. 사람이 두 수를 비교할 때 높은 자리부터 보니까
자연스러워 보여요. 반대쪽 후보는 **낮은 자리부터** 실행하는 것입니다. 두 쪽 모두 바퀴 하나는 자리 값이 같은
원소의 앞뒤를 바꾸지 않는 계수 정렬로 두고, 입력 다섯 벌에 실행했습니다.

<!--proof:msd-repeat-->

| 입력 | 낮은 자리부터 | 높은 자리부터 |
| --- | --- | --- |
| [513 45 258 2 66 90 301] | [2 45 66 90 258 301 513] | [513 2 258 45 301 66 90] |
| [170 45 75 90 802 24 2 66] | [2 24 45 66 75 90 170 802] | [2 24 802 45 66 75 90 170] |
| [321 213 132 123] | [123 132 213 321] | [321 123 132 213] |
| [12 12 1 1 100 100] | [1 1 12 12 100 100] | [1 1 12 12 100 100] |
| [0 10 0 1] | [0 0 1 10] | [0 0 1 10] |

5 벌 중 높은 자리부터 한 쪽은 3 벌이 틀렸고, 낮은 자리부터 한 쪽은 5 벌이 모두 맞았습니다.

<!--/proof-->

높은 자리부터 한 쪽은 첫 줄에서 `[513 2 258 45 301 66 90]` 을 냈습니다. 두 바퀴의 순서만 바꿨을 뿐인데 결과가
갈리는 이유는 마지막 바퀴에 있어요.

<!--proof:msd-why-->

```text
낮은 자리부터   자리 0 → 자리 1   [2 45 66 90 258 301 513]
높은 자리부터   자리 1 → 자리 0   [513 2 258 45 301 66 90]
높은 자리부터 낸 배열의 자리 0 은 1 2 2 45 45 66 90 — 마지막 바퀴의 자리만 오름차순이다
```

**마지막에 처리한 자리가 가장 높은 자리 노릇을 합니다.** 마지막 바퀴가 그 자리 기준의 순서를 새로 만들고,
앞 바퀴가 만든 순서는 그 자리 값이 같은 원소끼리의 동점을 가르는 데만 남으니까요. 그러니 진짜 가장 높은 자리가
마지막 바퀴여야 하고, 그것이 「낮은 자리부터」의 뜻입니다. 아래 두 벌에서 답이 같았던 것은 최댓값이 100 과
10 이라 바퀴가 하나뿐이어서 순서를 뒤집을 자리가 없었기 때문이에요. 지금까지 해 본 방법을 차례로 놓으면
이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법은 **자리 하나를 키로 하는 안정 정렬을 낮은 자리부터 최댓값의 자릿수만큼 되풀이하는 것**이고, 이
절차를 자릿수 정렬이라고 부릅니다. 바퀴 하나를 어떻게 안정하게 만드는지, 자리 값이 같은 원소가 어느 칸에
들어가는지, 바퀴 사이에 무엇이 넘어가는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 낮은 자리부터 되풀이하는 안정 정렬

이 아이디어를 한 문장으로 줄이면 이렇습니다. **최댓값의 자릿수만큼 바퀴를 실행하되, 바퀴마다 자리 값의 개수를
세고 누적합으로 자리 값마다 들어갈 칸 묶음을 정한 다음, 원소를 뒤에서 앞으로 읽어 그 칸 묶음의 끝부터
채웁니다.** 실현하는 순서대로 네 단계로 나누면 이렇습니다. 1단계는 함수를 시작할 때 한 번, 2~4단계는 바퀴마다
합니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 최댓값으로 바퀴 수 정하기 | `max` 를 찾고, `place` 를 1 부터 `B` 배씩 올릴 횟수를 정한다 | — |
| 2단계 자리 값을 세고 누적합으로 통 정하기 | 자리 값마다 개수를 `count` 에 세고, 누적합으로 덮어 통의 끝을 정한다 | 1단계가 정한 이번 바퀴의 `place` |
| 3단계 뒤에서 앞으로 통에 놓기 | `src` 를 뒤에서 앞으로 읽어 원소마다 그 통의 남은 끝 칸에 놓는다 | 2단계의 누적 `count` |
| 4단계 두 배열을 맞바꿔 다음 자리로 | `src` 와 `dst` 를 맞바꾸고 `place` 를 `B` 배로 올린다 | 3단계가 채운 `dst` |

3단계가 이 방법의 중심입니다. 거기서 쓰는 「통」이 이 글에서 처음 보는 모양이라 먼저 따로 봅니다.

#### 먼저 알아 둘 개념 — 통

##### 통의 정의

**통**(bucket)은 한 바퀴에서 **자리 값이 같은 원소들이 `dst` 에서 차지하는 이어진 칸 묶음**입니다. 자리 값
`d` 의 통은 자리 값이 `d` 보다 작은 원소들의 칸 바로 뒤에서 시작하고, 자리 값이 `d` 인 원소의 개수만큼 칸을
가져요. 누적합으로 덮은 `count[d]` 는 자리 값이 `d` 이하인 원소의 개수이므로, 통 `d` 는 칸 `count[d] − 1`
에서 끝납니다.

##### 입력 위의 통

전개 입력의 바퀴 1 이 끝난 `dst` 위에 통을 그리면 이렇습니다. 자리 0 의 값마다 통이 하나씩이고, 맨 아래 줄이
누적 `count` 입니다.

<!--fig:build-buckets-->
![바퀴 1 의 통 다섯과 누적 count](./figs/build-buckets.svg)

##### 통 하나를 읽는 법

통 하나를 골라 이름에서 칸과 값까지 따라가 봅시다. 통의 끝은 자기 누적 `count` 에서, 시작은 바로 앞 통의 누적
`count` 에서 나옵니다.

<!--proof:bucket-read-->

```text
통 45       자리 0 이 45 인 원소가 들어갈 칸
끝 칸       누적 count[45] = 5 에서 1 을 뺀 칸 4
첫 칸       바로 앞 통의 누적 count[2] = 3 인 칸 3
칸          [3,4] — 2 칸
들어간 값   45 301 — 자리 0 은 둘 다 45
```

##### 이웃한 통끼리

통은 자리 값이 작은 쪽부터 빈틈없이 이어 붙습니다. 개수가 0 인 자리 값은 칸을 하나도 갖지 않아 통이 보이지
않아요. 바퀴가 바뀌면 자리가 바뀌므로 통도 새로 나뉩니다.

<!--proof:bucket-rounds-->

| 바퀴 | 통 | 칸 | 들어간 값 |
| --- | --- | --- | --- |
| 바퀴 1 (자리 0) | 통 1 | [0,0] | 513 |
| 바퀴 1 (자리 0) | 통 2 | [1,2] | 258 2 |
| 바퀴 1 (자리 0) | 통 45 | [3,4] | 45 301 |
| 바퀴 1 (자리 0) | 통 66 | [5,5] | 66 |
| 바퀴 1 (자리 0) | 통 90 | [6,6] | 90 |
| 바퀴 2 (자리 1) | 통 0 | [0,3] | 2 45 66 90 |
| 바퀴 2 (자리 1) | 통 1 | [4,5] | 258 301 |
| 바퀴 2 (자리 1) | 통 2 | [6,6] | 513 |

전개 입력의 배치 5,040 가지에서 바퀴 10,080 개를 모두 보았고, 통은 자리 값이 작은 쪽부터 빈틈없이 이어 붙어 dst 를 덮었습니다.

<!--/proof-->

##### 값마다 칸 하나와의 차이

통을 계수 정렬의 칸과 같은 것으로 읽기 쉽습니다. 둘 다 `count` 의 칸 하나가 맡는 자리이니까요. 같은 전개
입력에서 두 모양을 나란히 세면 차이가 보입니다.

<!--proof:bucket-vs-cell-->

| 모양 | count 칸 수 | 원소가 든 칸 또는 통 | 서로 다른 값이 함께 든 통 |
| --- | ---: | --- | --- |
| 값마다 칸 하나(계수 정렬) | 514 | 7 칸 | 0 개 |
| 자리 값마다 통 하나 — 바퀴 1 | 256 | 5 통 | 2 개 |
| 자리 값마다 통 하나 — 바퀴 2 | 256 | 3 통 | 2 개 |

서로 다른 값이 함께 든 통은 통 2(258 2) · 통 45(45 301) · 통 0(2 45 66 90) · 통 1(258 301) 입니다.

<!--/proof-->

계수 정렬의 칸 하나에는 **값이 같은** 원소만 들어가서, 그 안의 순서가 결과에서 구별되지 않습니다. 통 하나에는
자리 값만 같고 **값은 다른** 원소가 들어가요. 바퀴 1 의 통 2 에는 258 과 2 가 함께 듭니다. 그래서 통 안에서
누가 앞 칸을 받는지가 결과를 바꿉니다.

##### 통이 이렇게 생긴 까닭

통 안에 값이 다른 원소가 여럿 들어가니, 그 안의 순서를 앞 바퀴가 만든 순서로 두어야 안정 정렬이 됩니다. 그러려면
원소를 한 칸씩 **정해진 자리에** 놓아야 하고, 통이 어디서 시작해 어디서 끝나는지 미리 알아야 해요. 누적합이 그
경계를 한 번에 줍니다. 통을 이어 붙인 칸 묶음으로 두는 까닭은 `dst` 하나에 모든 통이 들어가 따로 목록을 만들지
않아도 되기 때문입니다.

#### 1단계 — 최댓값으로 바퀴 수 정하기

바퀴를 몇 번 실행할지는 **최댓값**이 정합니다. 최댓값의 자리가 다 담기면 나머지 값의 자리도 담기니까요.
`place` 를 1 에서 시작해 `⌊M / place⌋ > 0` 인 동안 바퀴를 실행하고 `place` 를 `B` 배로 올리면, 바퀴 수가
`M` 의 256 진법 자릿수가 됩니다. 최댓값을 여러 값으로 두고 실제로 실행해 센 바퀴 수입니다.

<!--proof:build-passes-->

| 최댓값 M | 바퀴 d | 바퀴마다의 place |
| ---: | ---: | --- |
| 0 | 0 | 없음 |
| 255 | 1 | 1 |
| 256 | 2 | 1 · 256 |
| 513 | 2 | 1 · 256 |
| 65,535 | 2 | 1 · 256 |
| 65,536 | 3 | 1 · 256 · 65,536 |
| 16,777,216 | 4 | 1 · 256 · 65,536 · 16,777,216 |
| 1,000,000,000 | 4 | 1 · 256 · 65,536 · 16,777,216 |

<!--/proof-->

최댓값이 0 이면 바퀴가 없습니다. 빈 배열과 값이 전부 0 인 배열이 그렇고, 그때는 사본이 그대로 답이에요.
과제의 상한 10^9 에서는 바퀴가 넷을 넘지 않습니다. 전개 입력의 최댓값은 513 이라 바퀴가 둘이고, 값마다 자리
둘은 이렇습니다.

<!--proof:build-digits-->

| 값 | 자리 1 = ⌊x / 256⌋ mod 256 | 자리 0 = x mod 256 |
| ---: | ---: | ---: |
| 513 | 2 | 1 |
| 45 | 0 | 45 |
| 258 | 1 | 2 |
| 2 | 0 | 2 |
| 66 | 0 | 66 |
| 90 | 0 | 90 |
| 301 | 1 | 45 |

<!--/proof-->

자리 0 에서 258 과 2 가 둘 다 2 이고, 45 와 301 이 둘 다 45 입니다. 자리 1 에서는 0 이 넷이에요. 두 바퀴 모두
자리 값이 같은 원소를 만납니다.

#### 2단계 — 자리 값을 세고 누적합으로 통 정하기

바퀴 하나는 `count` 를 256 칸짜리 0 으로 새로 만들고, `src` 의 값마다 자리 값 `⌊x / place⌋ mod 256` 의 칸을
1 늘립니다. 그다음 칸 1 부터 255 까지 앞 칸의 값을 더해 누적합으로 덮어요. 누적 `count[d]` 가 통 `d` 의 끝 칸
바로 다음 번호입니다. 전개 입력의 바퀴 1 을 세면 이렇습니다.

<!--proof:build-count-->

| 자리 값 | 개수 | 누적 count | 통의 칸 |
| --- | ---: | ---: | --- |
| 1 | 1 | 1 | 0 |
| 2 | 2 | 3 | 1 · 2 |
| 45 | 2 | 5 | 3 · 4 |
| 66 | 1 | 6 | 5 |
| 90 | 1 | 7 | 6 |
| 그 밖 251 가지 | 0 | 앞 칸과 같음 | 없음 |

바퀴 2 에서 자리 1 로 세면 이렇습니다.

| 자리 값 | 개수 | 누적 count | 통의 칸 |
| --- | ---: | ---: | --- |
| 0 | 4 | 4 | 0 · 1 · 2 · 3 |
| 1 | 2 | 6 | 4 · 5 |
| 2 | 1 | 7 | 6 |
| 그 밖 253 가지 | 0 | 앞 칸과 같음 | 없음 |

<!--/proof-->

`count` 는 바퀴마다 256 칸이고, 누적합은 바퀴마다 덧셈 255 번입니다. 입력이 일곱 칸이어도 이 크기는 그대로예요.

#### 3단계 — 뒤에서 앞으로 통에 놓기

이제 원소를 놓습니다. `src` 를 **뒤에서 앞으로** 읽으며, 원소의 자리 값 `d` 에 대해 `count[d]` 를 하나 줄이고
줄어든 값의 칸에 원소를 적어요. 통 `d` 의 끝 칸부터 앞쪽으로 채우는 셈입니다. 쉬운 경우는 통에 원소가 하나뿐인
자리 값입니다. 자리 값 90 은 원소가 90 하나라, `count[90]` 을 7 에서 6 으로 줄이고 칸 6 에 놓으면 끝나요.

불안한 경우는 한 통을 원소 둘이 나눠 가질 때입니다. 바퀴 1 의 통 2(258 과 2)와 통 45(45 와 301)가 그래요.
매 걸음의 `count` 와 `dst` 를 전부 적으면 이렇습니다.

<!--proof:build-place-->

| i | 값 | 자리 0 | count 갱신 | 놓는 칸 | 놓은 뒤 dst |
| ---: | ---: | ---: | --- | ---: | --- |
| 6 | 301 | 45 | 5 → 4 | 4 | [_ _ _ _ 301 _ _] |
| 5 | 90 | 90 | 7 → 6 | 6 | [_ _ _ _ 301 _ 90] |
| 4 | 66 | 66 | 6 → 5 | 5 | [_ _ _ _ 301 66 90] |
| 3 | 2 | 2 | 3 → 2 | 2 | [_ _ 2 _ 301 66 90] |
| 2 | 258 | 2 | 2 → 1 | 1 | [_ 258 2 _ 301 66 90] |
| 1 | 45 | 45 | 4 → 3 | 3 | [_ 258 2 45 301 66 90] |
| 0 | 513 | 1 | 1 → 0 | 0 | [513 258 2 45 301 66 90] |

전개 입력의 배치 5,040 가지에서 바퀴 10,080 개를 확인했습니다. 칸마다 정확히 한 번 놓였고, 통마다 마지막으로 놓인 값은 그 통의 첫 칸에 들어갔습니다.

<!--/proof-->

통 2 에서는 `src` 의 뒤쪽(칸 3)에 있던 2 가 먼저 읽혀 통의 끝 칸 2 를, 앞쪽(칸 2)에 있던 258 이 나중에 읽혀 칸
1 을 받았습니다. 뒤에서 앞으로 읽었는데 결과는 `src` 의 앞뒤 그대로예요. 통 45 의 45 와 301 도 같은 모양입니다.
반복은 `i` 가 −1 이 될 때 끝나므로 `src` 의 칸이 하나도 빠지지 않고 한 번씩 읽히고, 원소 하나가 통의 칸 하나를
줄여 가져가므로 두 원소가 한 칸에 겹치지 않아요.

#### 4단계 — 두 배열을 맞바꿔 다음 자리로

바퀴가 끝나면 `src` 와 `dst` 의 역할을 맞바꿉니다. 방금 채운 배열이 다음 바퀴가 읽는 `src` 가 되고, 옛 `src`
는 다음 바퀴가 덮어쓸 `dst` 가 돼요. `place` 는 256 배가 됩니다. 바퀴 2 가 바퀴 1 의 결과를 이어받는 자리를,
자리 1 이 0 인 값들의 앞뒤로 확인해 봅시다.

<!--proof:build-carry-->

| 시점 | 자리 1 이 0 인 값의 앞뒤 |
| --- | --- |
| 입력 | 45 2 66 90 |
| 바퀴 1 뒤 | 2 45 66 90 |
| 바퀴 2 뒤 | 2 45 66 90 |

바퀴 2 는 이 값 4 개의 앞뒤를 바퀴 1 뒤 그대로 두었고, 그 순서가 자리 0 오름차순이라 곧 최종 순서입니다.

<!--/proof-->

값 하나가 두 바퀴를 지나는 길을 따라가 보면, 앞 바퀴가 정한 대소가 어떻게 남는지 보입니다.

<!--proof:build-path-->

```text
처음        258 은 칸 2, 301 은 칸 6
바퀴 1 뒤   258 은 칸 1, 301 은 칸 4   자리 0 이 2 와 45 라 258 이 앞
바퀴 2 뒤   258 은 칸 4, 301 은 칸 5   자리 1 이 둘 다 1 이라 앞뒤를 그대로 둔다
```

258 과 301 의 대소는 자리 0 에서 정해졌고, 자리 1 이 같은 바퀴 2 가 그 앞뒤를 건드리지 않았습니다. 자리 1 이
다른 원소끼리는 바퀴 2 가 새로 순서를 정해요. 값 전체가 자리 둘로 표현되므로 남는 경우가 없습니다.

#### 이 방법이 기대는 전제

낮은 자리부터 되풀이하는 안정 정렬은 아래 세 전제에 기대고 있습니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 바퀴 하나가 안정하다 | 3단계의 뒤에서 앞으로 놓기 | 앞 바퀴가 가른 동점이 뒤집힌다 |
| 값이 0 이상의 정수다 | 2단계의 `⌊x / place⌋ mod 256` 가 0 … 255 | 자리 값이 음수가 되어 `count` 의 칸이 아니다 |
| 최댓값이 모든 값의 자릿수를 담는다 | 1단계의 바퀴 수 | 짧은 값의 없는 높은 자리는 0 으로 채워진다 |

첫 전제가 깨지는 모습은 「불변식」 절이 변이로 보입니다. 둘째 전제가 깨지면 오류가 나지 않고 값이 사라져요.
음수가 섞인 입력을 정본에 그대로 넣은 결과입니다.

<!--proof:build-negative-->

| 입력 | radixSort 결과 | 바른 답 | 사라진 값 |
| --- | --- | --- | --- |
| [5 -3 2] | [2 5 0] | [-3 2 5] | -3 |
| [300 -1 7] | [7 0 300] | [-1 7 300] | -1 |
| [-3 -1 -2] | [-3 -1 -2] | [-3 -2 -1] | 없음 |

<!--/proof-->

`-3` 의 자리 0 은 `-3 mod 256` 이 아니라 자바스크립트의 나머지 `-3` 이고, `count[-3]` 은 배열의 칸이 아니라
이름이 `"-3"` 인 속성입니다. 그 자리에 놓인 원소는 `dst` 의 칸에 들어가지 못하고, 비어 있던 칸에는 `dst` 를
처음 채운 0 이 남아요. 값이 전부 음수이면 최댓값이 0 으로 남아 바퀴가 없고, 입력이 정렬되지 않은 채
돌아옵니다.

#### 자리 하나를 256 가지로 두는 까닭

`B` 를 키우면 바퀴 `d` 가 줄고 바퀴마다 `count` 의 칸이 늡니다. 최댓값을 10^9 으로 고정하고, `B` 를 여섯 가지로
두어 칸 수 `N` 셋에서 칸 접근을 실제로 셌습니다.

<!--proof:base-sweep-->

| B | 바퀴 d | N = 1 | N = 1,000 | N = 100,000 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 30 | 364 | 214,150 | 21,400,150 |
| 16 | 8 | 548 | 60,488 | 6,000,488 |
| 64 | 5 | 1,304 | 40,265 | 3,901,265 |
| 256 | 4 | 4,116 | 36,084 | 3,204,084 |
| 1,024 | 3 | 12,304 | 37,279 | 2,512,279 |
| 32,768 | 2 | 262,156 | 280,138 | 2,062,138 |

가장 적은 칸은 N = 1 에서 B = 2, N = 1,000 에서 B = 256, N = 100,000 에서 B = 32,768 입니다. B = 256 은 N = 100,000 에서 3,204,084 번으로 가장 적은 2,062,138 번의 1.55 배이고, N = 1 에서 4,116 번으로 가장 적은 364 번의 11.3 배입니다.

<!--/proof-->

**가장 적은 `B` 가 칸 수를 따라 옮겨 갑니다.** 칸 수가 작으면 바퀴마다 만드는 `count` 가 비용을 차지하고, 칸
수가 크면 바퀴 수가 비용을 차지하기 때문이에요. `B = 256` 은 어느 열에서도 가장 적은 값이 아니지만 자리 하나가
정확히 한 바이트라 자리 값을 뽑기 쉽고, 파트 2 의 「실제로 쓰이는 곳」에서 볼 구현 셋이 전부 이 값을 씁니다.
칸 접근만 재는 이 표로는 그 셋이 8 비트를 고른 근거가 나오지 않고, 이 글은 그 근거를 재지 않았습니다.
임의의 `N` 에서 가장 적은 바퀴 수를 식으로 푸는 일은 파트 2 의 「수식 정의와 유도」가 합니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 여섯 걸음이 됩니다.

1. `src` 를 `A` 의 사본으로, `dst` 를 같은 칸 수의 배열로 둔다
2. `src` 의 최댓값 `max` 를 찾는다
3. `place` 를 1 부터 `⌊max / place⌋ > 0` 인 동안 `B` 배씩 올리며 아래를 되풀이한다
4. `count` 를 0 으로 새로 만들어 자리 값마다 세고, 누적합으로 덮는다
5. `i` 를 `N − 1` 부터 0 까지 줄이며 `count[자리 값]` 을 하나 줄이고 그 칸에 `src[i]` 를 놓은 뒤, `src` 와
   `dst` 를 맞바꾼다
6. `src` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 일곱 칸을 두 바퀴로 정렬한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const A = [513, 45, 258, 2, 66, 90, 301];
// 이 절이 끝나면 [2, 45, 66, 90, 258, 301, 513] 이 나와야 한다
```

`A` 를 왜 하필 이 일곱 칸으로 뒀을까요? 갈래를 **모두 실행하게** 하려는 것입니다. 최댓값 513 이 256 진법 두
자리라 바퀴가 둘이고, 첫 바퀴에는 한 통을 원소 둘이 나눠 갖는 자리 값이 둘(2 와 45), 둘째 바퀴에는 원소 넷이
든 통이 하나 있어요. 안정성이 실제로 답을 정하는 자리가 그 통들입니다.

```text
radixSort(A):

  src ← A 의 사본, dst ← 같은 칸 수의 배열
  max 는 src 의 최댓값                          ① 바퀴 수를 정한다
  place 를 1 부터 max 를 덮을 때까지 B 배씩:    ② 낮은 자리부터 하나씩
      count ← 0 으로 채운 B 칸짜리 배열
      src 의 값 x 마다: count[자리 값] += 1     ③ 자리 값을 센다
      count 를 왼쪽부터 누적합으로 덮는다       ④ 통의 끝을 정한다
      i 를 N-1 부터 0 까지:                     ⑤ 뒤에서 앞으로 놓는다
          count[자리 값] -= 1
          dst[count[자리 값]] ← src[i]
      src 와 dst 의 역할을 맞바꾼다             ⑥ 다음 바퀴가 방금 쓴 쪽을 읽는다
  return src
```

#### 1. 최댓값으로 바퀴 수를 정한다

먼저 바퀴를 몇 번 실행할지 정합니다. 최댓값 하나만 알면 돼요.

```ts
let max = 0; // ① 최댓값이 바퀴 수를 정한다
for (const x of src) if (x > max) max = x;
```

이 조각만 실행하면 `max` 가 나오고, 반복 조건 `⌊max / place⌋ > 0` 이 어느 `place` 까지 참인지도 정해집니다.

<!--proof:walk-max-->

```text
T1      max = 513   256 ≤ 513 < 65,536 → 256 진법 2 자리 → 바퀴 2 번
place   1 에서 ⌊513/1⌋ = 513 > 0 참 · 256 에서 ⌊513/256⌋ = 2 > 0 참 · 65,536 에서 ⌊513/65,536⌋ = 0 거짓
```

#### 짚고 가기 — 자리를 왼쪽 끝에 맞추면 사전식 순서가 된다

자릿수가 다른 값이 섞여 있으면 자리를 어느 쪽 끝에 맞출지가 헷갈립니다. 종이에 수를 적을 때 왼쪽부터 읽으니까,
자리도 왼쪽 끝에 맞춰 비교하고 싶어져요. 그렇게 하면 `2` 의 첫 자리와 `513` 의 첫 자리가 같은 자리에서
만납니다.

<!--proof:pause-left-digits-->

```text
513 의 자리 목록   [2 1]   첫 칸이 2
2 의 자리 목록     [2]     첫 칸이 2
258 의 자리 목록   [1 2]   첫 칸이 1
첫 칸만 보면 258 이 513 보다 앞이고, 2 는 513 과 첫 칸이 같다
```

실제로 그 순서로 정렬해 보면 답이 어긋납니다. 오른쪽 끝에 맞춘 자릿수 정렬과 나란히 놓고 확인해 봅시다.

<!--proof:pause-left-align-->

| 입력 | 오른쪽 끝에 맞춤(자릿수 정렬) | 왼쪽 끝에 맞춤 |
| --- | --- | --- |
| [513 45 258 2 66 90 301] | [2 45 66 90 258 301 513] | [258 301 2 513 45 66 90] |
| [1 10 100 1000] | [1 10 100 1000] | [1 1000 10 100] |
| [170 45 75 90 802 24 2 66] | [2 24 45 66 75 90 170 802] | [2 802 24 45 66 75 90 170] |
| [0 10 0 1] | [0 0 1 10] | [0 0 1 10] |

4 벌 중 3 벌에서 왼쪽 끝에 맞춘 쪽이 틀렸습니다.

<!--/proof-->

`[1 10 100 1000]` 이 `[1 1000 10 100]` 이 된 줄이 이 오해의 모양을 그대로 보입니다 — 문자열로 정렬했을 때
「10」이 「9」보다 앞에 오는 것과 같은 자리예요. **자리는 오른쪽 끝에 맞춥니다.** 자리 0 은 언제나
`x mod B` 이고, 값이 짧으면 없는 높은 자리가 0 이 되어 저절로 앞에 옵니다.

#### 2. 자리 값을 세고 누적합으로 통을 정한다

자리 하나를 정했으면 그 자리 값마다 몇 개인지 셉니다. 자리 값이 곧 칸 번호라 비교가 필요 없어요.

```ts
const count = new Array<number>(BASE).fill(0);
for (const x of src) {
  // ③ 자리 값을 센다
  const dig = Math.floor(x / place) % BASE;
  count[dig] = (count[dig] as number) + 1;
}
for (let dig = 1; dig < BASE; dig++) {
  // ④ 누적합으로 통의 끝을 정한다
  count[dig] = (count[dig] as number) + (count[dig - 1] as number);
}
```

`place` 가 1 인 첫 바퀴에서 이 조각을 실행하면 이렇게 나옵니다. T2 가 세기, T3 이 누적합이에요.

<!--proof:walk-count-->

```text
T2   place = 1   자리 0 의 값 1 45 2 2 66 90 45
     개수        count[1] = 1 · count[2] = 2 · count[45] = 2 · count[66] = 1 · count[90] = 1
T3   누적합      count[1] = 1 · count[2] = 3 · count[45] = 5 · count[66] = 6 · count[90] = 7
```

#### 짚고 가기 — 누적합이 없으면 원래 값이 사라진다

계수 정렬은 개수만 세고 값을 이어 쓰면 끝났습니다. 그러면 여기서도 자리 값 `d` 를 `count[d]` 번 이어 쓰면 되지
않을까요? 그 절차를 그대로 실행하면 무엇이 나오는지부터 봅시다.

<!--proof:pause-no-prefix-->

| 한 바퀴 | 누적합으로 통에 놓은 쪽 | 개수만 세어 이어 쓴 쪽 |
| --- | --- | --- |
| 전개 입력 · 자리 0 | [513 258 2 45 301 66 90] | [1 2 2 45 45 66 90] |
| 전개 입력 · 자리 1 | [45 2 66 90 258 301 513] | [0 0 0 0 1 1 2] |
| [12 12 1 1 100 100] · 자리 0 | [1 1 12 12 100 100] | [1 1 12 12 100 100] |

3 벌 중 2 벌에서 개수만 세어 이어 쓴 쪽이 원래 값 대신 자리 값을 남겼습니다.

<!--/proof-->

**오른쪽 열에 남은 것은 자리 값입니다.** 첫 줄의 `[1 2 2 45 45 66 90]` 은 일곱 값의 자리 0 을 모아 정렬한
것이고, 원래 값 513 과 301 은 어디에도 없어요. 계수 정렬에서는 키가 곧 값이라 칸 번호에서 값을 다시 만들 수
있지만, 여기서 키는 값의 한 자리일 뿐이라 원소를 통째로 옮겨야 합니다. 옮기려면 「어느 칸에 놓을지」가 먼저
필요하고, 그것이 누적합이에요. 셋째 줄이 같은 값을 낸 것은 그 입력의 모든 값이 256 보다 작아 **값과 자리 0
이 같기** 때문입니다. 그런 입력만 보면 두 방식이 같아 보입니다.

#### 3. 뒤에서 앞으로 통에 놓는다

이제 원소를 놓습니다. `src` 를 **뒤에서 앞으로** 읽으며 그 자리 값의 누적합을 하나 줄이고 그 칸에 적어요.

```ts
for (let i = src.length - 1; i >= 0; i--) {
  // ⑤ 뒤에서 앞으로 놓는다
  const x = src[i] as number;
  const dig = Math.floor(x / place) % BASE;
  count[dig] = (count[dig] as number) - 1;
  dst[count[dig] as number] = x;
}
```

첫 바퀴에서 이 조각을 실행한 걸음 일곱입니다.

| T4 | 6 | 301 | 45 | 5 → 4 | 4 | [_ _ _ _ 301 _ _] |
| T5 | 5 | 90 | 90 | 7 → 6 | 6 | [_ _ _ _ 301 _ 90] |
| T6 | 4 | 66 | 66 | 6 → 5 | 5 | [_ _ _ _ 301 66 90] |
| T7 | 3 | 2 | 2 | 3 → 2 | 2 | [_ _ 2 _ 301 66 90] |
| T8 | 2 | 258 | 2 | 2 → 1 | 1 | [_ 258 2 _ 301 66 90] |

**T7 과 T8 이 통 2 를 나눠 가진 짝입니다.** 뒤쪽에 있던 2 가 먼저 읽혀 칸 2 를, 앞쪽에 있던 258 이 나중에 읽혀
칸 1 을 받았어요. T9 와 T4 의 45 · 301 짝도 같은 모양입니다. 여기서 가장 중요한 줄은 반복의 머리
`for (let i = src.length - 1; i >= 0; i--)` 입니다. 이 방향이 통 안의 앞뒤를 지키고, 방향을 바꾸면 무엇이
깨지는지는 「불변식」 절에서 봅니다.

#### 4. 두 배열을 맞바꿔 둘째 바퀴를 실행한다

첫 바퀴가 끝나면 `src` 와 `dst` 의 역할을 맞바꿉니다. 그래야 둘째 바퀴가 방금 쓴 쪽을 읽어요.

```ts
[src, dst] = [dst, src]; // ⑥ 다음 바퀴가 방금 쓴 쪽을 읽는다
```

맞바꾼 뒤 `place` 가 256 이 되고, 같은 세기와 누적합을 자리 1 로 실행합니다.

```text
T13   누적합         count[0] = 4 · count[1] = 6 · count[2] = 7
```

두 배열을 다시 맞바꾸면 `src` 가 답입니다.

#### 5. 일곱 칸을 끝까지 정렬한다

앞의 조각을 이어 `radixSort([513, 45, 258, 2, 66, 90, 301])` 을 끝까지 실행합니다. 무대의 값 줄은 그 바퀴가
읽는 `src` 이고, 그 아래 줄이 칸마다의 자리 값, 그다음이 이번 바퀴가 채우는 `dst` 입니다. 맨 아래 두 줄이
`count` 인데, 256 칸 중 그 바퀴에 나온 자리 값의 칸만 적고 나머지 칸이 0 인 것은 곁말에 적었습니다. 강조한 칸이
이번에 쓴 칸이고, ▲ 는 이번에 읽은 칸이에요.

**갈래 여섯이 모두 나왔습니다.** ② 가 참이 되는 자리와 거짓이 되는 자리가 둘 다 있고, ⑤ 도 바퀴마다 일곱 번
참이 된 뒤 `i` 가 −1 이 되어 끝납니다.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 없어요 — 조각을 그대로 붙이고 `B` 를 상수
`BASE` 로 뺐습니다. 빈 배열과 값이 전부 0 인 배열은 바퀴가 한 번도 실행되지 않아 사본이 그대로 답이 됩니다.

```ts
/**
 * 자리 하나가 담는 값의 가짓수. 값을 256 진법으로 본다 — 자리 하나가 한 바이트다.
 * 이 값이 커지면 바퀴 수가 줄고 `count` 의 칸 수가 는다.
 */
const BASE = 256;

/** `A` 를 오름차순으로 정렬한 **새 배열**을 돌려준다. `A` 자체는 바뀌지 않는다. */
export function radixSort(A: number[]): number[] {
  let src = [...A];
  let dst = new Array<number>(A.length).fill(0);

  // ① 최댓값이 바퀴 수를 정한다. 값이 큰 만큼만 자리를 본다.
  let max = 0;
  for (const x of src) if (x > max) max = x;

  // ② 자리를 낮은 쪽부터 하나씩 올린다. `place` 가 지금 보는 자리의 크기다.
  for (let place = 1; Math.floor(max / place) > 0; place *= BASE) {
    // ③ 이 자리의 값마다 몇 개인지 센다. 여기에 두 값을 비교하는 자리가 없다.
    const count = new Array<number>(BASE).fill(0);
    for (const x of src) {
      const dig = Math.floor(x / place) % BASE;
      count[dig] = (count[dig] as number) + 1;
    }

    // ④ 누적합으로 덮는다. `count[dig]` 가 「자리 값이 `dig` 이하인 원소의 개수」가 된다.
    for (let dig = 1; dig < BASE; dig++) {
      count[dig] = (count[dig] as number) + (count[dig - 1] as number);
    }

    // ⑤ 뒤에서 앞으로 읽으며 놓는다. 이 방향이라야 같은 자리 값의 순서가 유지된다.
    for (let i = src.length - 1; i >= 0; i--) {
      const x = src[i] as number;
      const dig = Math.floor(x / place) % BASE;
      count[dig] = (count[dig] as number) - 1;
      dst[count[dig] as number] = x;
    }

    // ⑥ 두 배열의 역할을 맞바꾼다. 다음 바퀴가 방금 쓴 쪽을 읽는다.
    [src, dst] = [dst, src];
  }

  return src;
}
```

<!--proof:final-calls-->

```text
radixSort([513, 45, 258, 2, 66, 90, 301])      →   [2, 45, 66, 90, 258, 301, 513]
radixSort([170, 45, 75, 90, 802, 24, 2, 66])   →   [2, 24, 45, 66, 75, 90, 170, 802]
radixSort([1000000000, 0, 999999999, 1])       →   [0, 1, 999999999, 1000000000]
radixSort([0, 0, 0])                           →   [0, 0, 0]
radixSort([12345])                             →   [12345]
radixSort([])                                  →   []
```

### 알아 두면 좋은 개념 — 다중 키 정렬

앞에서 자리 0 과 자리 1 을 **키 둘**로 보고, 덜 높은 키부터 안정 정렬을 되풀이했습니다. 키가 자릿수일 필요는
없어요. 레코드를 「부서 오름차순, 같으면 이름 오름차순」으로 정렬하는 일도 같은 모양이고, 이것을 다중 키
정렬(multi-key sort)이라고 부릅니다. 규칙은 하나입니다. **덜 높은 키를 먼저, 더 높은 키를 나중에 안정
정렬합니다.** 전개 입력에서 되풀이 순서를 두 가지로 두면 결과가 이렇게 갈립니다.

<!--proof:related-keys-->

| 되풀이 순서 | 결과 | 결과의 자리 1 | 결과의 자리 0 |
| --- | --- | --- | --- |
| 덜 높은 키(자리 0) 먼저 | [2 45 66 90 258 301 513] | 0 0 0 0 1 1 2 | 2 45 66 90 2 45 1 |
| 더 높은 키(자리 1) 먼저 | [513 2 258 45 301 66 90] | 2 0 1 0 1 0 0 | 1 2 2 45 45 66 90 |

<!--/proof-->

덜 높은 키를 먼저 한 쪽은 자리 1 줄이 오름차순이고, 자리 1 이 같은 칸끼리 자리 0 이 오름차순입니다. 더 높은
키를 먼저 한 쪽은 자리 0 줄만 오름차순이에요 — 나중 정렬이 먼저 한 정렬의 순서를 덮어썼습니다. 같은 규칙을
다시 만나는 자리를 모으면 이렇습니다.

| 같은 규칙이 나오는 자리 | 덜 높은 키 | 더 높은 키 |
| --- | --- | --- |
| 이 편의 자릿수 정렬 | 자리 0 | 자리 1 |
| 표를 두 열로 정렬하기 | 이름 | 부서 |
| 좌표를 정렬해 스위핑 준비 | `y` | `x` |

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 임의의 `N` 과 `M` 으로 비용을 어떻게 내는지,
무엇이 매 바퀴 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 걸리면 이 절차가 답이 됩니다. 앞의 둘이 필수이고 뒤의 둘은 이 절차가 덤으로 주는 것이에요. 조건마다
코드의 어느 모양이 그것을 받는지 함께 적었습니다.

| 조건 | 구분 | 까닭 | 코드에서 |
| --- | --- | --- | --- |
| 키가 고정 폭의 0 이상 정수이고 상한을 안다 | 필수 | 자리 값을 나눗셈과 나머지로 바로 얻어야 한다. 실수나 길이가 제각각인 문자열은 그대로는 자리로 갈리지 않는다 | 자리를 `⌊x / place⌋ mod B` 로 뽑는다 |
| 값의 상한 `M` 이 커서 계수 정렬을 그대로 쓸 수 없다 | 필수 | `M` 이 `N` 과 비슷하거나 작으면 계수 정렬 한 바퀴가 더 적다 | 바퀴 수를 최댓값에서 정한다 |
| 최악에도 같은 비용이 나와야 한다 | 덤 | 값의 순서가 비용을 하나도 바꾸지 않는다 | 코드에 비교가 한 줄도 없다 |
| 같은 값에 딸린 정보의 앞뒤를 지켜야 한다 | 덤 | 원소를 통째로 옮기므로 딸린 정보가 함께 가고 안정성까지 얻는다 | 뒤에서 앞으로 놓는다 |

#### 문제에서 이것을 떠올리게 하는 단서

지문이나 제약에 아래 신호가 보이면 이 절차를 떠올립니다.

| 신호 | 지문의 예 | 가리키는 것 |
| --- | --- | --- |
| 값이 고정 폭 정수로 못 박혀 있다 | 「0 이상 10^9 이하의 정수」 · 「32 비트 정수 배열을 정렬하라」 | 자리 값을 나눗셈으로 뽑을 수 있다 |
| 비교 횟수의 하한을 넘으라고 한다 | 「O(N) 에 정렬하라」 · 「비교 정렬의 하한보다 빨라야 한다」 | 비교하지 않는 정렬이 필요하다 |
| 키가 같은 폭의 조각으로 나뉜다 | IP 주소 · 타임스탬프 · 아이디 · 고정 길이 문자열 | 조각 하나를 자리 하나로 둔다 |
| 값의 상한이 `N` 보다 훨씬 크다 | 「N ≤ 10^5, 값 ≤ 10^9」 | 계수 정렬을 그대로 쓸 수 없는 구간이다 |
| 키가 여러 항목으로 이루어진다 | 「부서순, 같으면 이름순」 | 자리 대신 항목을 키로 두면 그대로 통한다 |

「값의 상한이 크다」가 단서인 이유는 그 문장이 **계수 정렬을 막는 조건**이면서 동시에 **자리로 쪼갤 수 있는
조건**이기 때문입니다. 상한을 알아야 자릿수가 정해지고, 자릿수가 정해져야 바퀴 수가 상수가 돼요. 반대로
「값이 임의의 실수다」거나 「키를 비교하는 함수만 주어진다」는 말이 있으면 이 단서는 해당하지 않습니다. 그때는
비교만으로 순서를 정하는 절차를 골라야 해요.

#### 실제로 쓰이는 곳

- **Apache Spark 의 `RadixSort`** — *"Sorts a given array of longs using least-significant-digit radix sort"*
  라고 소스가 적어 두었고, **이 편이 가르치는 모양 그대로**입니다. 한 바퀴가 1 바이트(자리 값 256 가지)이고,
  미리 한 번 차례로 읽어 **모든 원소의 그 바이트가 같으면 그 바퀴를 건너뜁니다** — *"Optimization: do a fast
  pre-pass to determine which byte indices we can skip for sorting"*.
  ([`org/apache/spark/util/collection/unsafe/sort/RadixSort.java`](https://github.com/apache/spark/blob/master/core/src/main/java/org/apache/spark/util/collection/unsafe/sort/RadixSort.java),
  조회 2026-08-30)
- **NumPy 의 `np.sort(kind="stable")`** — 정수 타입에서 이 절차로 갑니다. 자리 하나가 한 바이트라
  `cnt[l][nth_byte(k, l)]` 로 바이트마다 히스토그램을 만들고, 값이 한 가지뿐인 바이트는 건너뛰어요
  (`if (cnt[l][nth_byte(key0, l)] != num) { cols[ncols++] = l; }`).
  ([`numpy/_core/src/npysort/radixsort.hpp`](https://github.com/numpy/numpy/blob/main/numpy/_core/src/npysort/radixsort.hpp),
  조회 2026-08-30)
- **ClickHouse 의 `RadixSort`** — `radixSortLSDInternal()` 과 `executeLSD()` 가 이 절차이고, 자리 폭이 상수로
  박혀 있습니다 — `static constexpr size_t PART_SIZE_BITS = 8;` 과
  `static constexpr size_t HISTOGRAM_SIZE = 1 << Traits::PART_SIZE_BITS;` 라 히스토그램이 256 칸이에요.
  ([`src/Common/RadixSort.h`](https://github.com/ClickHouse/ClickHouse/blob/master/src/Common/RadixSort.h),
  조회 2026-08-30)

**셋 다 자리 하나를 8 비트로 둡니다.** 이 글이 `B = 256` 을 쓴 것과 같은 값이에요. 그리고 셋 중 둘은 **자리
값이 한 가지뿐인 바퀴를 건너뛰는** 손질을 더해 두었는데, 그 손질은 이 편의 코드에 없습니다 — 최댓값으로 바퀴
수를 줄이는 것까지만 합니다.

#### 경쟁 설계와의 대조

같은 목표를 노리는 **다른 절차**가 있습니다 — **병합 정렬**입니다. 값을 자리로 쪼개지 않고 두 값을 비교하는
것만으로 순서를 정해요. 그래서 값이 고정 폭 정수가 아니어도, 비교만 되는 값(문자열·객체)이어도 그대로
통합니다. 구간을 반씩 갈라 각각을 정렬하고, 정렬된 둘을 보조 배열을 거쳐 합칩니다. 합치는 데 구간 길이만큼
비교하고, 가르는 층이 `log₂ N` 개입니다.

같은 입력에 둘을 실행해 **칸 접근과 비교**를 셌습니다. 칸 접근은 배열 칸을 읽거나 쓴 횟수 전부이고, 쓰는 쪽
배열과 `count` 를 0 으로 채우는 초기화 쓰기도 넣었어요. 두 설계가 쓰는 배열이 서로 달라(`count`·`src`·`dst` 대 복사본·보조 배열) 어느 한쪽만 빼면 대조가
성립하지 않습니다. 입력은 셋인데 하나는 전개가 쓰는 일곱 칸 그대로이고 나머지 둘은 난수 없이 식으로
만들었어요 — `A[i] = (i × 999,983) mod (10^9 + 1)` 로 200 칸 · 100,000 칸입니다. 일곱 칸에서는 이 절차의 비용이
거의 전부 `count` 의 256 칸에서 나와 두 설계의 성질이 안 갈리기 때문에 큰 입력을 함께 잽니다.

| 계수 | 자릿수 정렬 (이 가이드) | 병합 정렬 |
| --- | --- | --- |
| 일곱 칸 입력의 칸 접근 | 2,168 | **129** |
| 일곱 칸 입력의 비교 | **0** | 14 |
| 200 칸 입력의 칸 접근 | 10,484 | **8,400** |
| 200 칸 입력의 비교 | **0** | 812 |
| 10 만 칸 입력의 칸 접근 | **3,204,084** | 9,455,258 |
| 10 만 칸 입력의 비교 | **0** | 1,239,773 |
| 10 만 칸 입력의 할당 칸 | 201,024 | **200,000** |

**비교에서는 이 절차가 0 번으로 앞섭니다.** 어느 칸 수에서도 0 이고, 병합 정렬은 10 만 칸에서 1,239,773
번을 비교합니다. 비교 한 번의 비용이 값 하나를 읽는 비용보다 큰 자리 — 문자열 대조나 사용자 함수 호출 — 에서는 그 0 이
그대로 이득이에요.

**칸 접근에서는 칸 수가 우열을 가릅니다.** 일곱 칸과 200 칸에서는 병합 정렬이 적고, 10 만 칸에서는 이 절차가
적습니다. 할당 칸(입력 밖에 새로 잡은 칸을 잡을 때마다 더한 값)은 병합 정렬이 1,024 칸 적어요 — 그 1,024 가 바퀴 넷이 256 칸씩 새로 만든 `count`
입니다. 칸 접근의 **우열이 반대가 되는 자리를 값으로 댈 수 있습니다.** 같은 생성식으로 칸 수만 늘려 가며 두 설계의 칸 접근을
재면, 순서가 뒤집히는 지점이 하나로 정해집니다.

<!--proof:alt-crossover-->

| 생성식으로 만든 입력 | 자릿수 정렬 접근 | 병합 정렬 접근 | 적은 쪽 |
| --- | ---: | ---: | --- |
| 200 칸 | 10,484 | 8,400 | 병합 정렬 |
| 309 칸 | 13,972 | 13,955 | 병합 정렬 |
| 310 칸 | 14,004 | 14,008 | 자릿수 정렬 |
| 100,000 칸 | 3,204,084 | 9,455,258 | 자릿수 정렬 |

310 칸에서 처음으로 순서가 뒤집히고, 100,000 칸에서는 병합 정렬의 접근이 자릿수 정렬의 2.95 배입니다.

<!--/proof-->

값의 상한이 10^9 인 입력에서 경계는 이 칸 수입니다. 그보다 작은 입력이 아주 많이 들어오는 상황이라면 병합
정렬이 적고, 과제 규모의 상한 쪽인 100,000 칸이면 이 절차가 적어요. 경계를 정하는 것은 칸 수 하나가 아니라
**`N` 과 `d·B` 의 대소**입니다.

**이 절차가 내주는 것은 적용 범위입니다.** 키가 고정 폭 정수가 아니면 자리로 갈리지 않아 아예 쓸 수 없어요.
병합 정렬은 비교만 되면 무엇이든 정렬합니다. 그리고 값의 상한이 커지면 바퀴가 느는데, 그것은 병합 정렬에는
없는 비용이에요. 두 설계가 요구하는 것을 나란히 적으면 이렇습니다.

| 설계 | 요구하는 것 | 못 지키면 |
| --- | --- | --- |
| 자릿수 정렬 | 키가 고정 폭의 0 이상 정수다 | 아예 쓸 수 없다 |
| 병합 정렬 | 두 값을 비교할 수 있다 | 정수든 문자열이든 객체든 통한다 |

### 수식 정의와 유도

값 `x` 의 `p` 번째 자리 값을 $\mathrm{digit}(x, p)$ 로, 최댓값 $M$ 에 필요한 바퀴 수를 $d(M)$ 으로
정의합니다. 자리는 0 부터 세고, 0 번째가 가장 낮은 자리예요.

$$\mathrm{digit}(x, p) \;=\; \left\lfloor \frac{x}{B^{p}} \right\rfloor \bmod B$$

식의 조각을 하나씩 값에 넣어 보면 이렇습니다.

<!--proof:math-pieces-->

| 식의 조각 | 뜻 | x = 513 · p = 1 일 때 |
| --- | --- | ---: |
| $B^{p}$ | p 번째 자리의 크기 | 256 |
| $\lfloor x / B^{p} \rfloor$ | 그 자리 위쪽까지 남긴 몫 | 2 |
| $\dots \bmod B$ | 그 자리 하나만 남긴 나머지 | 2 |

<!--/proof-->

$$d(M) \;=\; \lfloor \log_B M \rfloor + 1 \quad (M \ge 1), \qquad d(0) = 0$$

정의를 전개 입력의 값에 넣어 검산해 봅시다. $B = 256$ 이고 $M = 513$ 입니다.

<!--proof:math-check-->

| 넣는 값 | 계산 | 결과 |
| --- | --- | ---: |
| $\mathrm{digit}(513, 0)$ | $513 \bmod 256$ | 1 |
| $\mathrm{digit}(513, 1)$ | $\lfloor 513/256 \rfloor \bmod 256$ | 2 |
| $\mathrm{digit}(2, 1)$ | $\lfloor 2/256 \rfloor \bmod 256$ | 0 |
| $d(513)$ | $\lfloor \log_{256} 513 \rfloor + 1 = \lfloor 1.1254 \rfloor + 1$ | 2 |
| $d(10^9)$ | $\lfloor \log_{256} 10^9 \rfloor + 1 = \lfloor 3.7372 \rfloor + 1$ | 4 |

<!--/proof-->

$d(2) = 1$ 인데 전개는 값 2 에도 바퀴를 둘 실행합니다. 바퀴 수를 원소마다 따로 정하지 않고 **최댓값 하나로**
정하기 때문이고, 값 2 의 없는 자리 1 은 $\mathrm{digit}(2,1) = 0$ 으로 채워져요. 그래서 짧은 값이 저절로 앞에
옵니다.

**이제 비용을 유도합니다.** 배열 칸을 읽거나 쓴 횟수를 $T$ 라 두고 준비와 바퀴로 가릅니다. 바퀴 하나는 다시
넷으로 갈리는데, 자리 값 세기가 원소마다 세 번(입력 읽기 · 개수 읽기 · 개수 쓰기)이고 놓기가 원소마다 네
번(입력 읽기 · 개수 읽기 · 개수 쓰기 · 결과 쓰기)이에요.

| 조각 | 하는 일 | 접근 횟수 |
| --- | --- | --- |
| 준비 | 사본 만들기 · `dst` 초기화 · 최댓값 찾기 | `2N + N + N` |
| 바퀴 하나 | 칸 만들기 · 자리 값 세기 · 누적합 · 놓기 | `B + 3N + 3(B−1) + 4N` |

$$T_{\text{준비}} \;=\; \underbrace{2N}_{\text{사본}} + \underbrace{N}_{\text{dst 초기화}} + \underbrace{N}_{\text{최댓값}} \;=\; 4N$$

$$T_{\text{바퀴}} \;=\; B + 3N + 3(B-1) + 4N \;=\; 7N + 4B - 3$$

전개 입력의 $N$ 과 $B$ 를 두 식에 넣으면 이렇습니다.

<!--proof:math-total-->

```text
준비        4 × 7                 28
바퀴 하나   7 × 7 + 4 × 256 − 3   1,070
바퀴 2 번   2 × 1,070             2,140
합 2,168 — 전개 입력을 계측한 칸 접근 2,168 과 같다
```

바퀴가 $d(M)$ 번이므로 둘을 합치면 총식이 나옵니다.

$$T(N, B, M) \;=\; 4N + d(M)\,\bigl(7N + 4B - 3\bigr)$$

<!--proof:math-code-->

```ts
const total = (N: number, B: number, d: number): number =>
  4 * N + d * (7 * N + 4 * B - 3);

total(7, 256, 2);       // = 2168     전개 입력을 계측한 값과 같다
total(100_000, 256, 4); // = 3204084  최댓값 10^9 인 100,000 칸을 계측한 값과 같다
```

식의 기호가 코드의 어느 이름인지 맞춰 두면 이렇습니다.

| 식의 기호 | 코드의 이름 | 코드에서 하는 일 |
| --- | --- | --- |
| $B$ | `BASE` | 상수로 뺀 자리 하나의 가짓수 |
| $B^{p}$ | `place` | 바퀴마다 `BASE` 배가 된다 |
| $M$ | `max` | ① 이 찾아 두는 최댓값 |
| $d$ | 이름이 없다 | `place` 가 `max` 를 넘을 때까지 반복하는 것으로 대신한다 |

**여기서 `B` 를 자유롭게 두면 본문의 표가 못 주는 것이 나옵니다.** 바퀴를 $d$ 번으로 정하면 한 자리가 담아야
하는 값의 가짓수는 $B^{d} > M$ 을 만족하는 최소값이므로 $B = \lceil (M+1)^{1/d} \rceil$ 이고, 그것을 위 식에
넣으면 비용이 $d$ 하나의 함수가 돼요.

$$T^{*}(d) \;=\; 4N + d\,\Bigl(7N + 4\bigl\lceil (M+1)^{1/d} \bigr\rceil - 3\Bigr)$$

`d` 를 하나 줄이면 두 항이 반대로 움직입니다.

| 항 | 달라지는 것 | 커지는 조건 |
| --- | --- | --- |
| 줄어드는 항 | `7N` 이 한 벌 빠진다 | `N` 이 클수록 크다 |
| 늘어나는 항 | `B` 가 `(M+1)^(1/d)` 로 커진다 | `M` 이 클수록 크다 |

두 $d$ 의 $T^{*}$ 를 비교하는 부등식을 $N$ 에 대해 풀면 어느 쪽이 적어지는 경계가 값으로 나옵니다. $M = 10^9$
을 넣고 $d$ 를 다섯까지 봅시다.

<!--proof:math-scale-->

| 바퀴 d | 한 자리 최소 가짓수 | N = 100,000 에서의 T | d + 1 바퀴보다 적어지는 첫 N |
| ---: | ---: | ---: | ---: |
| 2 | 31,623 | 2,052,978 | 34,425 칸부터 |
| 3 | 1,001 | 2,512,003 | 1,310 칸부터 |
| 4 | 178 | 3,202,836 | 225 칸부터 |
| 5 | 64 | 3,901,265 | 74 칸부터 |

이 편의 B = 256 은 같은 N 에서 3,204,084 번이라 가장 적은 2,052,978 번의 1.6 배입니다.

<!--/proof-->

닫힌 형태가 주는 것이 여기 있습니다. 파트 1 의 표는 잰 여섯 값에서만 답을 냈는데, 이 식은 **임의의 `N` 에서
가장 적은 바퀴 수를 내요** — 마지막 열의 칸 수를 넘을 때마다 바퀴가 하나씩 줄어드는 것이 그 답입니다. 실제로
정렬해 보지 않고도 「칸이 34,425 개를 넘으면 두 바퀴짜리가 가장 적다」고 말할 수 있어요.

### 불변식 — 바퀴 하나가 끝날 때마다 그때까지 본 자리들 기준으로 정렬돼 있다

파트 1 에서 코드가 동작하는 것을 스물두 단계로 확인했습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 아래 문장으로 세우고, 그 아래 표에서 전개 입력의 두 바퀴가
끝난 시점과 많은 입력에서 되풀이한 대조로 그것이 실제로 유지되는지 확인합니다.

> **자리 `p` 를 처리한 바퀴가 끝난 시점마다**, `src` 는 각 값의 **자리 0 부터 자리 `p` 까지만 남긴 수**
> (`x mod B^(p+1)`)를 기준으로 오름차순이고, 그 수가 같은 원소끼리는 입력에서의 앞뒤가 그대로입니다.

<!--proof:invariant-rounds-->

| 시점 | src | 자리 p 까지만 남긴 수 | 남긴 수의 순서 |
| --- | --- | --- | --- |
| 바퀴 1 뒤 (자리 0 까지) | [513 258 2 45 301 66 90] | [1 2 2 45 45 66 90] | 오름차순 |
| 바퀴 2 뒤 (자리 1 까지) | [2 45 66 90 258 301 513] | [2 45 66 90 258 301 513] | 오름차순 |

전개 입력의 배치 전부와 시험 입력을 합해 5,052 벌 · 바퀴 10,100 개에서 대조했고, 불변식이 어긋난 바퀴는 0 개입니다.

<!--/proof-->

「자리 0 부터 자리 `p` 까지만 남긴 수」가 중요합니다. 바퀴 1 뒤의 배열은 값 전체로 보면 정렬이 아니지만
`x mod 256` 으로 보면 오름차순이고, 마지막 바퀴에서 `p` 가 최고 자리에 이르면 그 「남긴 수」가 값 전체와 같아져
정렬이 끝나요.

**출발점부터 봅시다.** 바퀴를 한 번도 실행하지 않은 시점에는 「남긴 수」가 모두 0 이라 어느 배열이든
오름차순이며 앞뒤도 입력 그대로입니다. 그다음 바퀴 하나가 무엇을 하는지 세 조각으로 갈라 봅니다.

| 바퀴의 조각 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| 자리 값 세기 | `count[dig]` 가 자리 값 `dig` 인 원소의 개수 | 원소마다 정확히 한 칸을 1 늘리므로 개수의 합이 `N` 이다 |
| 누적합 | `count[dig]` 가 자리 값 `dig` 이하인 개수 | 자리 값이 작은 원소가 앞쪽 통을 받으므로 결과가 자리 `p` 기준 오름차순이 된다 |
| 뒤에서 앞으로 놓기 | 자리 값이 같으면 `src` 의 뒤쪽이 통의 뒤쪽 칸부터 | `count[dig]` 를 줄이며 놓으므로 뒤쪽 원소가 뒤쪽 칸을 받고, 앞뒤가 그대로 남는다 |

셋이 전부입니다. 자리 `p` 가 다른 원소끼리는 두 번째 조각이 순서를 정하고, 자리 `p` 가 같은 원소끼리는 세 번째
조각이 앞 바퀴의 순서를 그대로 넘겨요. 앞 바퀴의 순서는 「자리 0 부터 자리 `p−1` 까지만 남긴 수」 기준이므로,
둘을 합치면 자리 `p` 까지의 수 기준이 됩니다. 이것이 귀납의 단계이고, 바퀴 0 번인 출발점이 기저입니다.

**경계에 있는 입력도 확인하고 갑시다.** 아래 여섯 줄이 이 함수가 받을 수 있는 모양의 끝입니다.

<!--proof:invariant-edges-->

| 입력 | 모양 | 바퀴 수 | 결과 | 반환 배열 |
| --- | --- | ---: | --- | --- |
| [] | 빈 배열 | 0 | [] | 새 배열 |
| [0 0 0] | 값이 전부 0 | 0 | [0 0 0] | 새 배열 |
| [12345] | 칸 하나 | 2 | [12345] | 새 배열 |
| [7 7 7] | 값이 전부 같음 | 1 | [7 7 7] | 새 배열 |
| [1 10 100 1000] | 자릿수가 섞임 | 2 | [1 10 100 1000] | 새 배열 |
| [1000000000 0] | 값의 상한 | 4 | [0 1000000000] | 새 배열 |

<!--/proof-->

빈 배열과 값이 전부 0 인 배열은 최댓값이 0 이라 바퀴가 없고 사본이 그대로 나옵니다. 값이 전부 같으면 바퀴마다
자리 값이 같아 앞뒤가 그대로이고, 짧은 값은 높은 자리가 0 이라 앞에 옵니다.

**이제 깨뜨려 봅시다.** 불변식의 뒷문장 — 남긴 수가 같으면 앞뒤가 그대로다 — 을 지키는 줄은
`for (let i = src.length - 1; i >= 0; i--)` 하나입니다. 그 줄을 앞에서 뒤로 읽는 반복으로 바꾸면 같은 통 안의
앞뒤가 뒤집혀요. 바꾸고 실행해 봅니다.

```ts
// for (let i = src.length - 1; i >= 0; i--) {
for (let i = 0; i < src.length; i++) { // ← 이 한 줄만 바꿨다
```

<!--proof:mutant-forward-->

| 입력 | 뒤에서 앞으로(바른 코드) | 앞에서 뒤로 놓은 코드 |
| --- | --- | --- |
| [513 45 258 2 66 90 301] | [2 45 66 90 258 301 513] | [90 66 45 2 301 258 513] |
| [170 45 75 90 802 24 2 66] | [2 24 45 66 75 90 170 802] | [170 90 75 66 45 24 2 802] |
| [12 12 1 1 100 100] | [1 1 12 12 100 100] | [1 1 12 12 100 100] |
| [0 10 0 1] | [0 0 1 10] | [0 0 1 10] |
| [12345] | [12345] | [12345] |

5 벌 중 2 벌에서 답이 어긋납니다.

<!--/proof-->

`[513 45 258 2 66 90 301]` 이 `[90 66 45 2 301 258 513]` 이 됐습니다. 앞의 넷 `90 66 45 2` 는 자리 1 이 0 인
넷인데 **내림차순**이에요. 첫 바퀴가 낸 그 넷의 앞뒤와 마지막 바퀴가 낸 앞뒤를 나란히 보면 어디서 뒤집혔는지가
나옵니다.

<!--proof:mutant-forward-groups-->

| 자리 1 이 0 인 넷의 앞뒤 | 첫 바퀴 뒤 | 마지막 바퀴 뒤 |
| --- | --- | --- |
| 뒤에서 앞으로(바른 코드) | 2 45 66 90 | 2 45 66 90 |
| 앞에서 뒤로 놓은 코드 | 2 45 66 90 | 90 66 45 2 |

첫 바퀴가 낸 앞뒤는 같고, 마지막 바퀴에서 두 줄이 갈립니다.

<!--/proof-->

첫 바퀴에서 이 넷은 서로 다른 통에 들어가서 놓는 방향과 상관없이 자리 0 순서로 나왔습니다. 마지막 바퀴에서는
넷이 한 통에 들어가고, 앞에서 뒤로 읽으면 앞쪽 원소가 통의 뒤쪽 칸을 받아 순서가 뒤집혀요. 답이 안 어긋난
세 벌은 뒤집을 것이 없었습니다. `[12345]` 는 칸이 하나이고, `[12 12 1 1 100 100]` 과 `[0 10 0 1]` 은 한 통에
든 원소가 **값까지 같아서** 앞뒤가 바뀌어도 결과에서 구별되지 않아요. 이 절차의 안정성은 값이 같은 원소가
아니라 **자리 값만 같은 원소**를 위한 것입니다.

### 비용 계산

칸 접근이 어디서 나오는지를 전개의 값으로 세고, 케이스와 경계를 갈라 적은 다음, 최악을 실제로 내는 입력을
만들어 봅니다.

#### 비용을 세는 과정

전개의 스물두 단계를 갈래별로 묶으면 여섯입니다. T1 이 ①, 바퀴가 시작될 때마다 ②, T2 · T12 가 ③, T3 · T13 이
④, T4 … T10 과 T14 … T20 이 ⑤, T11 과 T21 이 ⑥ 이에요. 한 바퀴가 배열을 몇 번 건드리는지 조각별로 세면
이렇습니다.

<!--proof:perf-derive-->

| 한 바퀴의 조각 | 세는 법 | 전개 입력에서 |
| --- | --- | ---: |
| 칸 만들기 | B 번 쓰기 | 256 |
| 자리 값 세기 | 원소마다 3 번 | 21 |
| 누적합 | (B − 1) 칸마다 3 번 | 765 |
| 놓기 | 원소마다 4 번 | 28 |
| 바퀴 하나의 합 | 7N + 4B − 3 | 1,070 |

바퀴가 2 번이라 2,140 번이고, 준비(사본 · dst 초기화 · 최댓값 찾기)가 4N = 28 번 더 들어 합이 2,168 번입니다. 계측한 칸 접근과 같습니다. 칸 만들기와 누적합만 한 바퀴 1,021 번으로, 원소를 세고 놓는 49 번의 20 배가 넘습니다.

<!--/proof-->

네 조각을 기호로 다시 적으면 칸 만들기가 `B` 번, 자리 값 세기가 `3N` 번, 누적합이 `3(B − 1)` 번, 놓기가 `4N`
번이라 바퀴 하나가 `7N + 4B − 3` 번입니다. 바퀴가 `d` 번이고 준비가 `4N` 이라 합은 `4N + d(7N + 4B − 3)` 이에요.
나머지 작업 — `place` 와 `i` 의 증감 · 반복 조건 판정 — 은 걸음마다 상수 번이라 위 네 조각에 상수 배로
묶입니다. 그리고 두 값을 비교하는 자리는 코드 어디에도 없어서 비교 항이 아예 없어요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (`1 ≤ M < B` 라 바퀴가 하나) | `O(N + B)` | `Θ(N + B)` — 실제로 도달한다 |
| **평균적인 경우** (어떤 입력 분포에서든) | `O(d(N + B))` | `Θ(d(N + B))` — 값의 순서가 비용을 안 바꾼다 |
| **최악의 경우** (최댓값이 `M` 의 상한) | `O(d(N + B))` | `Θ(d(N + B))` — 실제로 도달한다 |

**케이스를 가르는 것은 값의 순서가 아니라 최댓값입니다.** 입력을 보고 갈라지는 분기가 코드에 없어서, 칸 수와
최댓값이 같으면 접근 횟수가 글자 그대로 같아요. 비교 횟수로 갈리는 절차 — 삽입 정렬이 그렇습니다 — 와 반대되는
자리입니다.

**총식을 한 번은 정확히 적습니다.** 아래 값은 **칸 접근만** 센 것이고, 인덱스 증감처럼 걸음마다 상수 번인
일은 상수 배로 묶었습니다.

| 조각 | 세는 것 | 접근 |
| --- | --- | --- |
| 준비 | 사본 · `dst` 초기화 · 최댓값 찾기 | `4N` |
| 바퀴 `d` 번 | 바퀴마다 세고 · 누적하고 · 놓는다 | `d(7N + 4B − 3)` |
| 시간 | 두 항을 더한 것 | `Θ(d(N + B))` |
| 할당 칸 | `src` · `dst` 가 각각 `N` 칸, `count` 가 바퀴마다 `B` 칸 | `Θ(N + dB)` |

`B` 를 고정하고 값의 상한이 정해진 과제에서는 `d` 도 상수라 `Θ(N)` 이 됩니다. 두 표기가 같은 것을 말하는데
앞쪽이 더 정확해요 — 뒤쪽은 「값의 상한이 커지면 바퀴가 는다」를 표현할 자리가 없습니다.

**보장의 종류는 최악 보장입니다.** 코드에 난수가 없고, 같은 칸 수와 같은 최댓값에는 입력이 무엇이든 늘 같은
횟수가 나와요. 평균을 말할 때 흔히 붙는 입력 분포 가정도 여기서는 필요가 없습니다 — 분포를 무엇으로 두든
최댓값이 같은 모든 입력의 값이 같으므로 기댓값이 그 값입니다.

#### 최악을 만드는 입력

「역순 입력이 최악」이라는 말이 이 절차에서는 **참이 아닙니다.** 값을 어떤 순서로 놓아도 비용이 같아요. 전개
입력 일곱 칸의 서로 다른 배치를 전부 세어 확인하고, 최댓값과 칸 수를 바꿔 가며 함께 잽니다.

<!--proof:worst-input-->

| 입력 | 바퀴 수 | 칸 접근 | 원소당 접근 |
| --- | ---: | ---: | ---: |
| 최댓값 255 인 일곱 칸 | 1 | 1,098 | 156.9 |
| 전개 입력 일곱 칸 (최댓값 513) | 2 | 2,168 | 309.7 |
| 최댓값 10^9 인 일곱 칸 | 4 | 4,308 | 615.4 |
| 최댓값 10^9 인 한 칸 | 4 | 4,116 | 4,116.0 |
| 최댓값 10^9 인 100,000 칸 | 4 | 3,204,084 | 32.0 |

전개 입력의 배치 5,040 가지는 칸 접근이 전부 2,168 번으로 같습니다. 일곱 칸 중 최댓값 하나만 255 에서 10^9 으로 바꾸면 바퀴가 1 에서 4 로 늘어 접근이 1,098 번에서 4,308 번, 3.9 배가 됩니다.

<!--/proof-->

그러니 이 절차의 최악은 「값을 어떻게 놓는가」가 아니라 **「최댓값이 몇 자리인가」와 「칸 수에 비해 바퀴가
얼마나 무거운가」** 에서 나옵니다. 최악을 실제로 만드는 방법은 둘이에요. 최댓값 하나를 10^9 으로 두어 바퀴를
넷으로 늘리는 것, 그리고 칸 수를 1 로 줄여 바퀴마다 만드는 `count` 256 칸이 원소 하나에 다 실리게 하는 것입니다.
표의 넷째 줄이 둘을 함께 한 입력이라 원소당 접근이 가장 큽니다.

이 최악을 **피하는 장치가 이 절차에 하나 있습니다** — 바퀴 수를 최댓값에서 정하는 ① 이 그것이고, 그래서
최댓값 255 인 일곱 칸은 바퀴가 하나로 끝납니다. 다만 최댓값이 정말 10^9 이면 그 장치가 할 일이 없어요. 그때는
자리 하나의 가짓수 `B` 를 칸 수에 맞춰 고르는 것이 남은 길이고, 이 편은 `B` 를 256 으로 고정했으므로 그 길을
쓰지 않습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 값의 상한이 커서 값마다 칸을 만들 수 없을 때 값을 자리 여럿으로
쪼개고, 자리 하나를 키로 하는 안정 정렬을 낮은 자리부터 되풀이하면, 마지막 바퀴가 가장 높은 자리를 정하고 앞
바퀴들이 동점을 가릅니다. 바퀴 하나는 세 걸음입니다.

```text
자리 값을 센다 → 누적합으로 통의 끝을 정한다 → 뒤에서 앞으로 통에 놓는다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T17 에서 45 가 칸 1 에 놓였고, T14 · T15 · T18 이 통 0 의 나머지 셋을
놓았습니다. 둘째 바퀴만 **앞에서 뒤로** 읽도록 바꾸면 그 넷은 어느 칸에 놓이고 최종 결과는 무엇이 될까요?

<!--proof:self-given-->

```text
자리 1 이 0 인 넷은 첫 바퀴 뒤 배열 [513 258 2 45 301 66 90] 의 i = 2 · 3 · 5 · 6 (값 2 · 45 · 66 · 90) 이다
```

<!--check:passOrder-->
**통 0 의 네 칸을 받는 순서가 반대가 됩니다.** 앞에서 뒤로 읽으면 `i` 가 작은 원소가 먼저 `count[0]` 을 줄이므로
통의 뒤쪽 칸을 받고, 그 결과 넷의 앞뒤가 뒤집혀요. 한 통에 든 원소끼리는 앞 바퀴의 순서가 유일한 근거라 그것을
뒤집으면 답이 어긋납니다. 결과는 두 바퀴를 다 바꾼 「불변식」 절의 결과와 같은데, 그 절에서 본 대로 첫 바퀴는
이 넷의 앞뒤를 바꾸지 않기 때문이에요.

<!--proof:self-answer-->

```text
뒤에서 앞으로   i = 6 → 칸 3, i = 5 → 칸 2, i = 3 → 칸 1, i = 2 → 칸 0
앞에서 뒤로     i = 2 → 칸 3, i = 3 → 칸 2, i = 5 → 칸 1, i = 6 → 칸 0
```

- 이 편은 `B` 를 256 으로 고정했습니다. 같은 코드에서 `B` 만 32,768 로 바꾸면 최댓값 10^9 인 입력에서 바퀴가

  이하인 과제에서 어느 쪽이 더 중요한지 답해 보세요. (「비용 계산」의 총식과 「자리 하나를 256 가지로 두는
  까닭」)
- T2 는 자리 0 을, T12 는 자리 1 을 셌고 둘 다 `count` 를 새로 만들어 썼습니다. 만약 `count` 를 바퀴마다 새로

  답해 보세요. (「수행으로 알아보는 알고리즘」의 T2 와 T12)
- 입력에 음수가 섞이면(`-10^9 ≤ A[i] ≤ 10^9`) 이 절차를 그대로 쓸 수 없습니다. 「실제로 쓰이는 곳」의 세
  구현은 부호 있는 정수를 정렬하는데, 그 셋이 어떤 손질을 넣었을지 추측하고 그 손질이 이 편의 어느 줄에
  들어가야 하는지 적어 보세요. (「이 방법이 기대는 전제」와 「실제로 쓰이는 곳」)

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Radix Sort

풀 파일: [`radixSort.ts`](./radixSort.ts) · 테스트: [`radixSort.test.ts`](./radixSort.test.ts) · 실행: `bun test src/algorithms/sorting/radixSort/radixSort.test.ts`

#### 한 줄 요약

> $0$ 이상의 정수로만 이루어진 배열 `A`를 받아 **오름차순으로 정렬된 새 배열**을 반환한다.

#### 스토리

우편물 분류 센터. 오늘 처리해야 할 **`N`건** 소포의 우편번호가 무작위 순서로 넘어왔다.
분류기는 한 번에 숫자 한 자릿수만 읽을 수 있어서, 자릿수를 반복하며 순서를 맞춰나간다.

우편번호는 항상 $0$ 이상의 정수이며, 같은 번호가 여럿 있을 수 있다.
숫자가 딱 하나뿐이어도 정상 처리해야 한다.

#### 함수 인터페이스

```ts
export function radixSort(A: number[]): number[];
```

- `A` — 정렬할 비음 정수 배열 (각 원소 $0 \leq A[i] \leq 10^9$)
- 반환 — `A`의 모든 원소를 오름차순으로 정렬한 새 배열

#### 제약 조건

- $1 \leq N \leq 100{,}000$ — 여기서 $N$은 배열 `A`의 길이다.
- $0 \leq A[i] \leq 10^9$ — 각 원소는 이 범위의 **비음 정수**다. 음수나 소수는 입력으로 주어지지 않는다.
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

배열 `A`를 **오름차순(작은 값 → 큰 값)** 으로 정렬한 결과를 새 배열로 반환한다. 다음 규칙을 따른다.

- **값 범위.** 모든 원소가 $[0, 10^9]$ 비음 정수 범위 안에 있다. 최대 10자리 수까지 처리해야 한다.
- **원소 집합 보존.** 반환 배열의 다중집합(multiset)은 입력 `A`의 다중집합과 같아야 한다.
- **빈 배열.** `A`가 비어 있으면 빈 배열을 반환한다.
- **중복 허용.** 같은 값이 여럿이면 그 개수 전부 결과에 포함된다.
- **0 포함.** 0은 유효한 원소이며, $0$이 여럿이면 그 개수만큼 결과 앞자리에 포함된다.

#### 예시

```ts
radixSort([170, 45, 75, 90, 802, 24, 2, 66]);
// [2, 24, 45, 66, 75, 90, 170, 802] — 여러 자릿수 혼재

radixSort([5, 4, 3, 2, 1]);
// [1, 2, 3, 4, 5] — 역순 입력

radixSort([0, 10, 0, 1]);
// [0, 0, 1, 10] — 0 포함(경계: 0이 여럿)

radixSort([12345]);
// [12345] — 원소가 하나(경계: N=1)

radixSort([7, 7, 7]);
// [7, 7, 7] — 전부 동일(경계: 모든 값 같음)

radixSort([1_000_000_000, 0, 999_999_999, 1]);
// [0, 1, 999999999, 1000000000] — 최댓값 포함(경계: A[i]=10^9)

radixSort([]);
// [] — 빈 배열(경계: N=0)
```
