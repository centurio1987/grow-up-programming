# 두 힙으로 구하는 스트림 중앙값 — 정렬된 수열 전체가 아니라 가운데 두 자리만 알면 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 물어볼 때마다
전부 정렬하는 방법에서 출발해 두 힙까지 가고, 두 힙을 단계마다 값으로 푼 뒤, 실제로 동작하는 코드를 한
조각씩 만듭니다.

### 전체 컨셉

정수가 하나씩 들어오는 동안 **지금까지 들어온 수 전부의 중앙값**을 언제든 답하는 자료구조를 만듭니다.
`addNum(num)` 이 수 하나를 더하고, `findMedian()` 이 그 시점의 중앙값을 돌려줘요. 중앙값은 들어온 수를
정렬했을 때, 개수가 홀수면 가운데 값이고 짝수면 가운데 두 값의 평균입니다. 수 다섯을 차례로 넣으면서
넣을 때마다 물어보면 이렇게 나옵니다.

<!--proof:concept-stream-->

| 넣은 순서 | 정렬하면 | 중앙값 |
| --- | --- | ---: |
| 5 | 5 | 5 |
| 5 15 | 5 15 | 10 |
| 5 15 1 | 1 5 15 | 5 |
| 5 15 1 3 | 1 3 5 15 | 4 |
| 5 15 1 3 5 | 1 3 5 5 15 | 5 |

중앙값 열은 정본이 낸 답이고, 5 줄 중 5 줄에서 정렬한 줄의 가운데 자리로 고른 값과 같습니다.

<!--/proof-->

오른쪽 열의 답은 늘 **정렬된 수열의 가운데 한 자리나 두 자리**에서 나옵니다. 나머지 자리에 어떤 값이
어떤 순서로 있는지는 답에 영향을 주지 않아요. 그렇다면 정렬된 수열을 통째로 들고 있을 이유가 없습니다.
들어온 수를 **작은 쪽 절반과 큰 쪽 절반으로 갈라** 두면 가운데 자리는 두 절반이 맞닿는 경계에 놓이고,
필요한 값은 작은 쪽의 최댓값과 큰 쪽의 최솟값 둘뿐이에요. 다섯 수를 다 넣은 상태를 정렬한 수열 위에
그리면 이렇습니다.

<!--fig:concept-halves-->
![정렬하면 두 절반이 가운데에서 맞닿는다 — 작은 쪽 최댓값과 큰 쪽 최솟값](./figs/concept-halves.svg)

두 절반 안의 순서는 몰라도 됩니다. 한쪽 끝값 하나만 바로 꺼낼 수 있으면 되니까, 그 일을 하는 자료구조인
힙을 씁니다. 작은 쪽 절반은 최댓값을 꼭대기에 두는 **최대 힙**에, 큰 쪽 절반은 최솟값을 꼭대기에 두는
**최소 힙**에 담아요. 이 한 쌍을 **두 힙**(two heaps)이라고 부르고, 이 글은 끝까지 이 이름을 씁니다.

| 두 힙의 부분 | 담는 것 | 꼭대기 | 코드의 이름 |
| --- | --- | --- | --- |
| 작은 쪽 | 정렬했을 때 앞 절반 | 그 절반의 최댓값 | 최대 힙 `low` |
| 큰 쪽 | 정렬했을 때 뒤 절반 | 그 절반의 최솟값 | 최소 힙 `high` |
| 크기 규칙 | 두 크기가 같거나 작은 쪽이 하나 더 많다 | — | 수 하나를 넣을 때마다 맞춘다 |

크기 규칙이 값의 규칙만큼 중요합니다. 값으로만 갈라 두면 한쪽이 계속 커져서 경계가 가운데를 벗어나요.
그래서 수 하나가 들어올 때마다 두 크기를 다시 맞춥니다. 비용을 결과만 적으면 수 하나를 넣는 데 힙 연산
몇 번이라 `O(log N)`, 물어보는 데 꼭대기 둘을 읽는 것이라 `O(1)` 이고, 추가로 잡는 칸은 들어온 수를 담는
자리뿐이라 `O(N)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **힙이 무엇인지.** 배열 하나로 완전 이진 트리를 담고 「부모가 자식보다 꼭대기에 가깝다」 하나만 지키는
  자료구조예요. 배열이 정렬돼 있지 않은데도 뿌리가 늘 끝값입니다. 넣기와 꺼내기가 트리 높이만큼의 비교로
  끝난다는 것도 알고 있어야 해요. 모르면
  [`minHeap` 가이드](../../../data-structures/heap/minHeap/minHeap-guide.mdx)를 보세요.
- **최소 힙과 최대 힙의 차이.** 비교하는 방향 하나만 뒤집으면 꼭대기에 오는 값이 최솟값에서 최댓값으로
  바뀝니다. 이 글은 두 방향을 한 클래스로 다룹니다.
- **다중집합.** 같은 수가 여러 번 들어오면 각각이 따로 세어지는 모임이에요. 중앙값을 정할 때 중복된 값도
  자기 자리를 하나씩 차지합니다.
- **중앙값의 정의.** 정렬했을 때 개수가 홀수면 가운데 값, 짝수면 가운데 두 값의 평균입니다. 두 값이
  정수여도 평균은 소수점 아래가 생길 수 있어요.

이 글이 다루는 것은 **수가 하나씩 들어오는 동안 중앙값을 계속 답하는 과제**입니다. 한 번 주어진 배열을
통째로 정렬하는 과제는 [`sortArray`](../sortArray/sortArray-guide.md) 가, 한 번 주어진 배열에서 `k` 번째
값을 한 번만 고르는 과제는 [`kthSmallest`](../kthSmallest/kthSmallest-guide.md) 가 다뤄요. 들어온 값을
지우는 연산까지 있는 경우는 이 글의 범위 밖입니다.

### 아이디어를 떠올리는 과정 — 물어볼 때마다 전부 정렬하기에서 두 힙까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 클래스 하나가 수를 받는 메서드와 중앙값을
돌려주는 메서드를 가집니다.

```ts
class MedianFinder {
  addNum(num: number): void; // 정수 하나를 더한다. 돌려주는 값은 없다
  findMedian(): number; // 지금까지 더한 수 전부의 중앙값을 돌려준다
}
```

- 입력: `addNum` 은 정수 하나를 받습니다. 값은 `-10^9` 이상 `10^9` 이하예요. `findMedian` 은 받는 것이
  없습니다.
- 출력: `findMedian` 은 수 하나를 돌려줍니다. 개수가 짝수면 소수점 아래가 생길 수 있어요.
- 규모: 두 메서드를 합쳐 `Q = 100,000` 번 부르고, 이 글은 넣기 50,000 번 · 묻기 50,000 번으로 잽니다.
  `findMedian` 은 `addNum` 이 한 번은 불린 뒤에만 불려요. 비용은 흔한 채점 환경의 예산인 1 초(단순 연산
  1 초에 1 억 번)에 대어 잽니다.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `Q` | `addNum` 과 `findMedian` 을 합친 총 호출 횟수 | `1 ≤ Q ≤ 100,000` |
| `N` | 지금까지 들어온 수의 개수. `addNum` 이 불린 횟수입니다 | `0 ≤ N ≤ Q` |
| `num` | 이번 `addNum` 이 받은 수 | `-10^9 ≤ num ≤ 10^9` |
| `low` | 두 힙의 작은 쪽. 최대 힙입니다 | 크기가 `k` |
| `high` | 두 힙의 큰 쪽. 최소 힙입니다 | 크기가 `N − k` |
| `k` | 작은 쪽의 크기로 정하는 값 `⌈N/2⌉` | `N = 5` 면 3 |
| `h` | 힙 하나의 높이 상한 `⌈log₂ N⌉` | `N = 100,000` 이면 17 |

`Q` 와 `N` 을 가르는 것이 이 글의 뼈대입니다. 앞은 호출 횟수이고 뒤는 담긴 수의 개수예요. `addNum` 만
`Q` 번 불리면 둘이 같아지고, 절반씩 나뉘면 `N` 이 `Q` 의 절반입니다.

가장 먼저 떠오르는 방법으로 시작합시다. 중앙값의 정의가 「정렬했을 때 가운데」이니, **물어볼 때마다 전부
정렬해서** 가운데를 읽으면 됩니다. 넣기는 배열 끝에 칸 하나를 쓰는 것으로 끝나요.

```ts
const kept: number[] = [];
function addNum(num: number): void {
  kept.push(num);
}
function findMedian(): number {
  const s = [...kept].sort((a, b) => a - b); // 물을 때마다 전부 정렬한다
  const n = s.length;
  return n % 2 === 1 ? s[(n - 1) / 2]! : (s[n / 2 - 1]! + s[n / 2]!) / 2;
}
```

이 방법은 답을 틀리지 않습니다. 비용은 **값의 비교와 배열 칸 쓰기를 합친 횟수**로 세고, 정렬은 실행마다
횟수가 같도록 병합 정렬로 두었어요. 넣을 때마다 물어보는 작업을 수의 개수별로 실제로 세고, 닫힌 형태의
상한을 나란히 놓았습니다.

<!--proof:naiveScale-->

```text
수의 개수 N  실측 비교 + 칸 쓰기  닫힌 형태 상한
         32                3,959           4,257
         64               19,550          20,865
        128               93,892          99,201
        256              439,446         460,801

호출 100,000 번 (넣기 50,000 · 묻기 50,000) 이면
  물어볼 때마다 전부 정렬한다  36,723,984,465 번 이하
  초당 1 억 번 기준            367 초
```

수의 개수가 두 배가 될 때마다 횟수가 네 배를 넘습니다. 과제 규모에서는 367 억 번이라 예산 1 초의 수백
배예요. 그 367 억 번이 무엇을 만드는지 봅시다. 전개 입력 `5 15 1 3 5` 로 정렬한 결과와 답이 읽는 자리를
나란히 놓았습니다.

<!--proof:halfOnly-->

```text
넣은 수     정렬 결과   답이 읽는 자리  답
5           5           1 번째          5
5 15        5 15        1·2 번째        10
5 15 1      1 5 15      2 번째          5
5 15 1 3    1 3 5 15    2·3 번째        4
5 15 1 3 5  1 3 5 5 15  3 번째          5

정렬이 만든 자리 15 개 중 답이 읽은 자리는 7 개다
```

정렬은 열다섯 자리의 순서를 전부 정해 주는데 답이 읽는 자리는 일곱입니다. 나머지 여덟 자리는 만들어
놓고 한 번도 읽지 않아요. 수가 늘수록 만드는 자리는 `N` 에 비례해 늘고, 읽는 자리는 늘 하나나 둘입니다.

그러면 순서를 처음부터 다시 만들지 않으면 어떨까요. **정렬된 배열을 그대로 두고 새 수만 알맞은 자리에
끼워 넣는** 방식과 매번 정렬하는 방식을 같은 입력으로 실행하고 횟수를 나란히 셉니다. 끼워 넣을 자리는 이분
탐색으로 찾아요.

<!--proof:twoWays-->

```text
수의 개수 N  방식                        비교  칸 쓰기       합
          5  물어볼 때마다 전부 정렬       15       32       47
          5  정렬된 자리에 끼워 넣기        7       11       18
        256  물어볼 때마다 전부 정렬  197,867  241,579  439,446
        256  정렬된 자리에 끼워 넣기    1,702   16,123   17,825

N = 256 에서 끼워 넣기의 비교는 1,702 번인데 칸 쓰기가 16,123 번이다
```

끼워 넣기가 훨씬 적습니다. 그런데 그 안을 갈라 보면 비교는 1,702 번인데 칸 쓰기가 16,123 번이에요.
자리 하나를 비우려고 뒤의 값을 한 칸씩 옮겨 적은 것이고, 그 값들은 답이 읽지도 않는 자리입니다. 여기서
관찰한 것이 하나예요. **남은 비용은 전부 가운데가 아닌 자리들의 순서를 지키는 일입니다.**

| 방식 | 비교 | 칸 쓰기 | 횟수를 정하는 일 |
| --- | --- | --- | --- |
| 물어볼 때마다 전부 정렬 | `N log N` 에 비례 | `N log N` 에 비례 | 매번 순서를 처음부터 만든다 |
| 정렬된 자리에 끼워 넣기 | `log N` 에 비례 | `N` 에 비례 | 순서를 지키려고 뒤를 옮긴다 |

그렇다면 순서를 얼마나 덜 지켜도 되는지 정해야 합니다. 가장 단순한 후보는 **중앙값 하나만 변수에 담아
두는 것**이에요. 새 수가 오면 옛 중앙값과 새 수로 새 중앙값을 적는 방식입니다. 옛 중앙값과 새 수가 같은
두 경우를 실제로 계산해 봅시다.

<!--proof:origin-one-value-->

| 담긴 수 | 중앙값 | 새로 넣은 수 | 넣은 뒤의 정렬 | 새 중앙값 |
| --- | ---: | ---: | --- | ---: |
| 1 5 15 | 5 | 3 | 1 3 5 15 | 4 |
| 4 5 15 | 5 | 3 | 3 4 5 15 | 4.5 |

두 줄 다 옛 중앙값이 5 · 새로 넣은 수가 3 인데, 새 중앙값은 4 와 4.5 로 갈립니다.

<!--/proof-->

두 줄에서 이 방식이 쥔 값은 똑같이 5 와 3 인데 답은 4 와 4.5 로 달라야 합니다. 그러니 이 두 값만으로는
새 중앙값을 정할 수 없어요. 새 수가 들어오면 가운데 자리가 옮겨 가고, 그 옆에 무엇이 있는지 모르면 새
가운데 값을 못 적습니다. **가운데 둘레의 값을 바로 꺼낼 수 있는 상태**가 필요해요. 지금까지 해 본 방법을
차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **두 힙**입니다. 들어온 수를 작은 쪽 절반과 큰 쪽 절반으로 갈라, 작은 쪽은
최댓값을, 큰 쪽은 최솟값을 바로 꺼낼 수 있게 담아요. 두 절반 안의 순서는 지키지 않습니다. 두 힙이 무엇을
담는지, 수를 넣을 때 두 절반을 어떻게 맞추는지, 답을 어떻게 읽는지는 다음 절에서 실현하는 순서대로
확인합니다.

### 아이디어 상세 — 두 힙

이 아이디어를 한 문장으로 줄이면 이렇습니다. **들어온 수를 정렬했을 때의 앞 절반을 최대 힙에, 뒤 절반을
최소 힙에 담고, 수가 들어올 때마다 두 절반의 경계와 크기를 다시 맞추면, 중앙값은 두 꼭대기에서 읽힙니다.**
이 방법이 기대는 구조 두 힙은 힙 하나를 알아도 처음 보면 낯설어요 — 왜 작은 쪽이 최대 힙인지, 두 꼭대기가
정렬한 수열의 어느 자리인지가 바로 떠오르지 않습니다. 그래서 두 힙을 먼저 따로 설명하고, 그다음 실현하는
순서대로 네 단계를 설명합니다. 앞 단계에서 만든 것을 뒤 단계에서 쓰는 순서예요.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 만들 때 한 번 | 1단계 방향이 반대인 두 힙 두기 | 최대 힙 `low` 와 최소 힙 `high` 를 빈 채로 만든다 | — |
| `addNum` 마다 | 2단계 새 수를 넣고 꼭대기를 넘기기 | 새 수를 `low` 에 넣고, `low` 의 꼭대기를 `high` 로 옮긴다 | 1단계의 두 힙 |
| `addNum` 마다 | 3단계 두 크기를 맞추기 | `high` 가 더 많으면 `high` 의 꼭대기를 `low` 로 도로 옮긴다 | 2단계가 맞춘 경계 |
| `findMedian` 마다 | 4단계 두 꼭대기로 답 읽기 | 두 크기가 같으면 두 꼭대기의 평균, 다르면 `low` 의 꼭대기 | 2단계의 경계 · 3단계의 크기 |

#### 먼저 알아 둘 개념 — 두 힙

두 힙은 **들어온 수를 정렬했을 때의 앞 절반을 최대 힙에, 뒤 절반을 최소 힙에 나눠 담은 한 쌍**입니다.
앞 절반을 작은 쪽, 뒤 절반을 큰 쪽이라고 부르고, 작은 쪽의 크기는 `k = ⌈N/2⌉` 로 둬요. 그러면 작은 쪽의
꼭대기가 정렬했을 때 `k` 번째 값이고, 큰 쪽의 꼭대기가 `k + 1` 번째 값입니다.

##### 정렬한 수열 위의 두 힙

전개 입력 `5 15 1 3 5` 를 다 넣은 상태입니다. 윗줄은 정렬한 수열이고, 괄호 둘이 작은 쪽과 큰 쪽이 맡은
자리예요. 아래 두 줄은 각 힙의 값을 **꺼낼 차례대로** 늘어놓은 것이라 첫 칸이 곧 꼭대기입니다.

<!--fig:build-two-heaps-->
![두 힙 — 정렬한 수열의 앞 절반과 뒤 절반, 첫 칸이 꼭대기](./figs/build-two-heaps.svg)

작은 쪽은 앞 세 자리 `1 3 5` 를, 큰 쪽은 뒤 두 자리 `5 15` 를 맡습니다. 작은 쪽은 최대 힙이라 큰 값부터
꺼내므로 정렬한 수열을 **오른쪽에서 왼쪽으로** 읽는 차례이고, 큰 쪽은 최소 힙이라 **왼쪽에서 오른쪽으로**
읽는 차례예요. 두 줄의 첫 칸, 곧 두 꼭대기가 정렬한 수열에서 서로 이웃한 3 번째와 4 번째 자리입니다.

##### 두 힙 하나를 읽는 법

두 힙에서 값을 하나씩 꺼낸다고 두고, 꺼낸 값이 정렬했을 때 몇 번째 자리인지 따라가 봅시다. 작은 쪽에서
`i` 번째로 꺼내는 값은 `k − i + 1` 번째 자리이고, 큰 쪽에서 `i` 번째로 꺼내는 값은 `k + i` 번째 자리예요.
다섯 칸을 모두 대조했습니다.

<!--proof:build-read-->

| 힙 | 꺼내는 차례 | 값 | 정렬했을 때의 자리 |
| --- | ---: | ---: | --- |
| 작은 쪽 low | 1 | 5 | 3 번째 |
| 작은 쪽 low | 2 | 3 | 2 번째 |
| 작은 쪽 low | 3 | 1 | 1 번째 |
| 큰 쪽 high | 1 | 5 | 4 번째 |
| 큰 쪽 high | 2 | 15 | 5 번째 |

정렬하면 1 3 5 5 15 이고, 5 칸 모두 그 자리의 값과 같습니다.

<!--/proof-->

`findMedian` 이 읽는 것은 두 줄의 첫 칸뿐입니다. 표의 나머지 칸은 두 힙이 담고는 있지만 꺼낼 때까지 순서가
정해지지 않은 값이에요.

##### 두 힙 사이의 관계

두 힙이 이 모양을 지키려면 두 가지가 늘 참이어야 합니다. 작은 쪽의 어떤 값도 큰 쪽의 어떤 값보다 크지
않다는 것, 그리고 작은 쪽이 큰 쪽과 크기가 같거나 하나 많다는 것이에요. 앞의 것이 참이면 작은 쪽의
최댓값과 큰 쪽의 최솟값 둘만 비교해도 충분합니다. 전개 입력을 하나씩 넣을 때마다 쟀습니다.

<!--proof:build-relation-->

| N | 작은 쪽(꺼낼 차례) | 큰 쪽(꺼낼 차례) | 작은 쪽 최댓값 | 큰 쪽 최솟값 | 크기 차 |
| ---: | --- | --- | ---: | ---: | ---: |
| 1 | 5 | 비어 있음 | 5 | 없음 | 1 |
| 2 | 5 | 15 | 5 | 15 | 0 |
| 3 | 5 1 | 15 | 5 | 15 | 1 |
| 4 | 3 1 | 5 15 | 3 | 5 | 0 |
| 5 | 5 3 1 | 5 15 | 5 | 5 | 1 |

5 줄 중 5 줄에서 작은 쪽 최댓값이 큰 쪽 최솟값 이하이고(큰 쪽이 빈 줄 포함), 5 줄에서 크기 차가 0 또는 1 입니다.

<!--/proof-->

`N = 5` 줄에서 두 꼭대기가 5 와 5 로 같습니다. 같은 값이 두 절반에 하나씩 놓여도 「크지 않다」는 참이라
문제가 없어요. 값의 관계는 **두 절반의 경계**를, 크기 차는 **그 경계가 어디인가**를 정합니다. 둘 중
하나만 지켜서는 꼭대기가 가운데 자리를 가리키지 않는데, 그 모습은 「수행으로 알아보는 알고리즘」의 두 번째
「짚고 가기」에서 실행 결과로 봅니다.

##### 힙 배열과 정렬한 반쪽의 차이

두 힙을 처음 보면 **두 반쪽을 정렬해 둔 것**으로 읽기 쉽습니다. 그림의 띠가 꺼낼 차례대로 늘어놓은 것이라
정렬된 것처럼 보이기도 해요. 실제로 힙 배열에 놓인 순서와 꺼낼 차례, 그리고 그 반쪽을 정렬한 것을 나란히
놓았습니다.

<!--proof:build-array-->

| N | 힙 | 배열에 놓인 순서 | 꺼낼 차례 | 정렬한 반쪽 | 배열의 오름차순 여부 |
| ---: | --- | --- | --- | --- | --- |
| 4 | 작은 쪽 low | 3 1 | 3 1 | 1 3 | 아니오 |
| 4 | 큰 쪽 high | 5 15 | 5 15 | 5 15 | 예 |
| 5 | 작은 쪽 low | 5 1 3 | 5 3 1 | 1 3 5 | 아니오 |
| 5 | 큰 쪽 high | 5 15 | 5 15 | 5 15 | 예 |

네 줄 중 2 줄은 배열이 오름차순으로 놓여 있지 않고, 4 줄에서 배열의 첫 칸과 꺼낼 차례의 첫 값이 그 반쪽의 끝값입니다.

<!--/proof-->

`N = 5` 에서 작은 쪽 배열은 `5 1 3` 입니다. 오름차순도 내림차순도 아닌데 첫 칸이 최댓값 5 예요. 힙이
지키는 것은 「부모가 자식보다 꼭대기에 가깝다」 하나라 첫 칸만 정해지고 나머지 칸의 순서는 정해지지
않습니다. 반쪽을 정말로 정렬된 채 두려면 「아이디어를 떠올리는 과정」에서 센 끼워 넣기처럼 새 수가 올
때마다 뒤의 값을 옮겨야 하고, 그 칸 쓰기가 바로 버린 비용이었어요.

##### 두 힙이 이렇게 생긴 까닭

중앙값은 정렬한 수열의 `k` 번째와 `k + 1` 번째 값만 씁니다. 그 둘은 앞 절반의 **가장 큰 값**과 뒤 절반의
**가장 작은 값**이에요. 그래서 앞 절반은 최댓값을 바로 꺼내는 최대 힙이어야 하고, 뒤 절반은 최솟값을 바로
꺼내는 최소 힙이어야 합니다. 두 힙의 방향이 서로 반대인 까닭이 이것이고, 방향을 같게 두면 무엇이
어긋나는지는 「수행으로 알아보는 알고리즘」의 첫 「짚고 가기」에서 봅니다.

| 두 힙의 요구 | 필요한 값 | 채우는 성질 |
| --- | --- | --- |
| 가운데 두 자리를 바로 읽는다 | 앞 절반의 최댓값 · 뒤 절반의 최솟값 | 두 힙의 꼭대기 |
| 수가 들어와도 가운데가 경계에 남는다 | 두 절반의 크기를 `k` 와 `N − k` 로 | 크기 규칙 |
| 가운데가 아닌 자리의 순서를 안 지킨다 | 반쪽 안의 순서를 정하지 않는 구조 | 힙은 첫 칸만 정한다 |

#### 1단계 — 방향이 반대인 두 힙 두기

작은 쪽 `low` 는 최대 힙, 큰 쪽 `high` 는 최소 힙으로 빈 채 만듭니다. 두 힙은 비교 방향만 다르고 넣기와
꺼내기 절차는 같으므로, 힙 클래스 하나에 방향을 정하는 수 `sign` 을 줍니다.

| 힙 | `sign` | 꼭대기에 오는 값 | 담는 절반 |
| --- | --- | --- | --- |
| `low` | `-1` | 가장 큰 값 | 작은 쪽 |
| `high` | `+1` | 가장 작은 값 | 큰 쪽 |

처음에는 두 힙이 비어 있으니 `N = 0`, 두 크기는 0 과 0 이에요. 이 뒤로 두 힙의 크기는 늘 `k` 와 `N − k`
로 남고, 어느 힙도 `k` 를 넘지 않으므로 힙 하나의 높이는 `h = ⌈log₂ N⌉` 이하입니다. 그 크기가 어떻게
지켜지는지는 3단계에서 값으로 봅니다.

#### 2단계 — 새 수를 작은 쪽에 넣고 꼭대기를 큰 쪽으로 넘기기

새 수를 받으면 **어느 쪽에 속하는지 비교하지 않고** 먼저 작은 쪽에 넣습니다. 그다음 작은 쪽의 꼭대기를
꺼내 큰 쪽에 넣어요. 쉬운 경우는 새 수가 이미 작은 쪽에 속하는 값일 때이고, 불안한 경우는 **새 수가 큰
쪽에 속하는 값**일 때입니다. 뒤의 경우에는 그 수가 작은 쪽에 잘못 들어간 셈이라 경계를 넘어가야 하거든요.
전개에서 두 경우를 하나씩 골라 두 줄마다의 상태를 적었습니다.

<!--proof:build-cases-->

| 경우 | 줄 | 작은 쪽(꺼낼 차례) | 큰 쪽(꺼낼 차례) | 넘어간 값 |
| --- | --- | --- | --- | ---: |
| 새 수가 작은 쪽에 속한다 (1) | 넣기 전 | 5 | 15 | - |
| 새 수가 작은 쪽에 속한다 (1) | ① 1 을 작은 쪽에 넣는다 | 5 1 | 15 | - |
| 새 수가 작은 쪽에 속한다 (1) | ② 작은 쪽 꼭대기를 큰 쪽으로 | 1 | 5 15 | 5 |
| 새 수가 큰 쪽에 속한다 (15) | 넣기 전 | 5 | 비어 있음 | - |
| 새 수가 큰 쪽에 속한다 (15) | ① 15 를 작은 쪽에 넣는다 | 15 5 | 비어 있음 | - |
| 새 수가 큰 쪽에 속한다 (15) | ② 작은 쪽 꼭대기를 큰 쪽으로 | 5 | 15 | 15 |

두 경우 중 2 경우에서 ② 가 끝났을 때 작은 쪽 최댓값이 큰 쪽 최솟값 이하입니다.

<!--/proof-->

새 수 1 은 작은 쪽의 최댓값 5 보다 작아서 꼭대기가 되지 못하고, 원래 꼭대기 5 가 대신 넘어갑니다. 새 수
15 는 작은 쪽에 들어간 순간 그 무리의 최댓값이 되므로 ② 가 바로 그 15 를 큰 쪽으로 옮겨요. **두 경우가
같은 두 줄로 처리됩니다.** 알맞은 쪽에 속하는 값이면 다른 값이 대신 넘어가고, 반대쪽에 속하는 값이면 그
값 자신이 넘어가요.

왜 ② 뒤에 늘 「작은 쪽 최댓값 ≤ 큰 쪽 최솟값」이 되는지는 넘어간 값으로 말할 수 있습니다. ② 가 옮기는 값은
① 을 마친 작은 쪽의 최댓값이라, 작은 쪽에 남은 값은 전부 그 이하입니다. 넘어간 값이 큰 쪽에 들어가면 큰
쪽의 최솟값은 넘어간 값과 원래 최솟값 중 작은 것이 돼요. 넘어간 값 쪽은 방금 본 대로 작은 쪽에 남은 값
이상입니다. 원래 최솟값 쪽도 그렇습니다 — 작은 쪽에 남은 값은 넣기 전부터 있던 값이거나 새 수인데, 넣기
전부터 있던 값은 그때 이미 원래 최솟값 이하였고, 새 수가 남았다면 넘어간 것은 옛 최댓값이라 새 수는 옛
최댓값 이하, 곧 원래 최솟값 이하예요. 어느 쪽이든 작은 쪽의 최댓값은 큰 쪽의 최솟값을 넘지 않습니다.

#### 3단계 — 두 크기를 맞추기

2단계는 작은 쪽에서 하나를 빼 큰 쪽에 더하므로, 넣기 전에 두 크기가 같았다면 큰 쪽이 하나 많아집니다.
그때는 큰 쪽의 꼭대기를 꺼내 작은 쪽에 **도로 옮겨요**(③). 도로 옮기는 값은 큰 쪽의 최솟값이라, 작은
쪽에 들어가면 그대로 새 최댓값이 되고 2단계가 맞춘 값의 관계도 깨지지 않습니다. 전개 입력을 하나씩 넣을
때마다 ② 뒤와 ③ 뒤의 두 크기를 쟀습니다.

<!--proof:build-sizes-->

| N | ② 뒤 두 크기(작은 쪽 · 큰 쪽) | ③ | ③ 뒤 두 크기 | ⌈N/2⌉ |
| ---: | --- | --- | --- | ---: |
| 1 | 0 · 1 | 참 — 5 를 도로 옮긴다 | 1 · 0 | 1 |
| 2 | 1 · 1 | 거짓 | 1 · 1 | 1 |
| 3 | 1 · 2 | 참 — 5 를 도로 옮긴다 | 2 · 1 | 2 |
| 4 | 2 · 2 | 거짓 | 2 · 2 | 2 |
| 5 | 2 · 3 | 참 — 5 를 도로 옮긴다 | 3 · 2 | 3 |

5 줄 중 5 줄에서 ③ 뒤 작은 쪽 크기가 ⌈N/2⌉ 와 같습니다.

<!--/proof-->

③ 은 `N` 이 홀수가 되는 걸음에서만 참이고 짝수가 되는 걸음에서는 거짓입니다. 넣기 전 두 크기가 같으면(`N`
이 짝수에서 홀수로) ② 뒤 큰 쪽이 하나 많아져 도로 옮기고, 넣기 전 작은 쪽이 하나 많으면(`N` 이 홀수에서
짝수로) ② 뒤 두 크기가 같아져 옮길 것이 없어요. 그래서 한 번의 `addNum` 이 끝날 때 작은 쪽의 크기는 늘
`k = ⌈N/2⌉` 이고, 두 크기의 차이는 0 또는 1 입니다. 빠뜨리는 수가 없는 것도 같은 표에서 확인돼요. 두 크기의
합이 매 줄 `N` 과 같습니다.

#### 4단계 — 두 꼭대기로 답 읽기

`findMedian` 은 두 크기를 비교합니다. 같으면 `N` 이 짝수라 두 꼭대기의 평균이 답이고, 다르면 `N` 이 홀수라
작은 쪽의 꼭대기 하나가 답이에요. 큰 쪽이 비어 있는 `N = 1` 도 두 크기가 달라 큰 쪽 꼭대기를 읽지 않습니다.

<!--proof:build-answer-->

| N | 두 크기 | 두 크기의 비교 | 답을 만드는 식 | 정본의 답 | 정렬해서 고른 답 |
| ---: | --- | --- | --- | ---: | ---: |
| 1 | 1 · 0 | 다르다 | 작은 쪽 꼭대기 5 | 5 | 5 |
| 2 | 1 · 1 | 같다 | (5 + 15) / 2 | 10 | 10 |
| 3 | 2 · 1 | 다르다 | 작은 쪽 꼭대기 5 | 5 | 5 |
| 4 | 2 · 2 | 같다 | (3 + 5) / 2 | 4 | 4 |
| 5 | 3 · 2 | 다르다 | 작은 쪽 꼭대기 5 | 5 | 5 |

5 줄 중 5 줄에서 정본의 답이 정렬해서 고른 답과 같습니다.

<!--/proof-->

두 크기가 같은 두 줄(`N = 2` · `N = 4`)은 가운데 두 자리의 평균이고, 다른 세 줄은 가운데 한 자리입니다.
3단계가 작은 쪽의 크기를 `k` 로 맞춰 두었기 때문에, 작은 쪽 꼭대기가 곧 `k` 번째 값이고 큰 쪽 꼭대기가
`k + 1` 번째 값이에요.

#### 이 방법이 기대는 전제

두 힙은 아래 세 전제 위에서 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 들어온 수는 지워지지 않는다 | 두 힙이 넣기와 꼭대기 꺼내기만 한다 | 힙은 가운데의 값을 바로 빼지 못해, 값마다 힙 안의 자리를 따로 기억해야 한다 |
| 값에 전순서가 있다 | 2단계 · 3단계의 꼭대기 비교 | 「작은 쪽의 모든 값 ≤ 큰 쪽의 모든 값」을 말할 수 없다 |
| 두 꼭대기의 합이 정확히 표현된다 | 4단계의 평균 | 평균이 어긋난다. 값의 범위가 `±10^9` 이면 합이 `2 × 10^9` 이하라 자바스크립트의 수가 정확히 담는다 |

마지막 전제는 「불변식」 절의 경계 입력 표에서 양 끝 값을 넣어 확인합니다.

#### 작은 쪽을 ⌈N/2⌉ 칸으로 두는 까닭

작은 쪽의 크기를 `⌈N/2⌉` 에서 위아래로 옮겨 놓고, 두 꼭대기만 읽어 낸 답이 참 중앙값과 몇 번 같은지
세어 봅시다. 전개 입력 다섯에 일곱을 이어 붙인 수열 `5 15 1 3 5 9 2 12 7 4 11 8` 을 `N = 5` 부터 `12` 까지
잘라 넣었어요.

<!--proof:boundarySweep-->

```text
작은 쪽의 크기  맞은 답  처음 어긋나는 N  그때 낸 답  참 중앙값
⌈N/2⌉ − 2       0 / 8    5                1           5
⌈N/2⌉ − 1       2 / 8    5                3           5
⌈N/2⌉ 그대로    8 / 8    -                -           -
⌈N/2⌉ + 1       5 / 8    9                7           5
⌈N/2⌉ + 2       0 / 8    5                15          5

N = 5 … 12 을 전부 시험한 값이다. 가운데 줄만 8 번 다 맞다
```

`⌈N/2⌉` 만 여덟 번 다 맞습니다. 하나 적게 두면 여덟 중 둘, 하나 많게 두면 다섯이고, 둘 이상 옮기면 하나도
안 맞아요. 하나 많게 둔 줄이 다섯 번이나 맞는 것은 우연이 섞여서입니다. 전개 입력 `N = 5` 한 곳에서 크기를
2 부터 5 까지 옮겨 보면 그 우연이 보여요.

<!--proof:boundary-n5-->

| 작은 쪽의 크기 | 작은 쪽에 드는 값 | 큰 쪽에 드는 값 | 꼭대기로 낸 답 | 참 중앙값 | 판정 |
| --- | --- | --- | ---: | ---: | --- |
| 2 | 1 3 | 5 5 15 | 3 | 5 | 틀리다 |
| 3 (= ⌈5/2⌉) | 1 3 5 | 5 15 | 5 | 5 | 맞다 |
| 4 | 1 3 5 5 | 15 | 5 | 5 | 맞다 |
| 5 | 1 3 5 5 15 | 비어 있음 | 15 | 5 | 틀리다 |

크기 4 는 N = 5 에서는 맞지만, 같은 규칙으로 수를 더 넣으면 N = 9 에서 7 을 내어 참 중앙값 5 와 어긋납니다.

<!--/proof-->

크기 4 는 가운데 두 값 5 · 5 가 같아서 우연히 맞았습니다. 크기를 옮기면 꼭대기가 가운데가 아닌 자리를
가리키고, 가운데 둘레의 값이 우연히 같을 때만 답이 맞아요. 그래서 크기 규칙은 `⌈N/2⌉` 하나로 정합니다.
`⌊N/2⌋` 로 두고 큰 쪽이 하나 많게 해도 대칭이라 같은 절차가 나오는데, 이 글은 작은 쪽이 하나 많은 쪽을
씁니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇습니다. 2단계와 3단계가 `addNum` 한 번, 4단계가 `findMedian` 한
번이에요.

1. 작은 쪽 `low` 를 최대 힙으로, 큰 쪽 `high` 를 최소 힙으로 빈 채 만든다
2. `addNum` 은 새 수를 `low` 에 넣고, `low` 의 꼭대기를 꺼내 `high` 에 넣는다
3. 이어서 `high` 가 `low` 보다 크면 `high` 의 꼭대기를 꺼내 `low` 에 넣는다
4. `findMedian` 은 두 크기가 같으면 두 꼭대기의 평균을, 다르면 `low` 의 꼭대기를 돌려준다

### 수행으로 알아보는 알고리즘 — 다섯 수를 아홉 걸음으로 넣고 묻는다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 수열 하나를 잡고 끝까지 가되, 조각마다
그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const stream = [5, 15, 1, 3, 5];
// 넣을 때마다 findMedian 을 부르면 5 · 10 · 5 · 4 · 5 가 나와야 한다
```

왜 하필 이 다섯 수일까요? **라벨 넷이 한 수열에서 모두 실행되고, 갈래가 있는 두 라벨은 참과 거짓이 다
나오기** 때문이에요. 수를 하나 넣을 때마다 `N` 의 홀짝이 바뀌니 크기를 맞추는 갈래와 답을 고르는 갈래가
번갈아 참이 됩니다. 15 는 작은 쪽의 꼭대기가 되어 그대로 넘어가는 값이고 1 · 3 은 그러지 못하는 값이라
2단계의 두 경우가 다 나오고, 마지막 `5` 는 앞에 이미 있는 값이라 중복이 어떻게 다뤄지는지도 같은 자리에서
나와요.

```text
MedianFinder:
    low  ← 빈 최대 힙,  high ← 빈 최소 힙
    addNum(num):
        low 에 num 을 넣는다                         ① 넣기
        low 의 꼭대기를 꺼내 high 에 넣는다          ② 옮기기
        high 가 low 보다 크면                        ③ 크기 맞추기
            high 의 꼭대기를 꺼내 low 에 넣는다
    findMedian():
        두 크기가 같으면  두 꼭대기의 평균           ④ 답 고르기
        다르면            low 의 꼭대기
```

#### 1. 힙 하나를 방향만 바꿔 쓴다

첫 조각은 힙입니다. 작은 쪽과 큰 쪽은 꼭대기에 오는 값만 다르고 넣기와 꺼내기 절차는 똑같아요. 그래서
클래스를 둘 만들지 않고 **비교하는 방향 하나를 인자로** 받습니다.

```ts
class Heap {
  private items: number[] = [];
  constructor(private readonly sign: number) {} // +1 이면 최소 힙, -1 이면 최대 힙

  private prior(a: number, b: number): boolean {
    return this.sign * ((this.items[a] as number) - (this.items[b] as number)) < 0;
  }
}
```

`sign` 이 `+1` 이면 `items[a] - items[b] < 0`, 곧 작은 값이 꼭대기에 가깝습니다. `-1` 이면 부호가 뒤집혀
큰 값이 꼭대기에 가까워요. 이 한 줄이 두 힙의 차이 전부입니다. 같은 수를 두 방향의 힙에 넣고 배열을
들여다보면 이렇게 나옵니다.

<!--proof:walk-heap-sign-->

```text
같은 수 5 · 1 · 3 을 차례로 넣으면

  sign = +1 (최소 힙)  배열 1 5 3  꼭대기 1
  sign = -1 (최대 힙)  배열 5 1 3  꼭대기 5
```

두 배열의 순서가 다르고, 둘 다 정렬돼 있지 않습니다. 지키는 것은 「부모가 자식보다 꼭대기에 가깝다」
하나라 첫 칸만 끝값이에요.

#### 짚고 가기 — 두 힙을 같은 방향으로 두면 경계의 값이 꼭대기에 오지 않는다

여기서 헷갈리기 쉬운 포인트는 **두 힙의 방향이 서로 반대라는 것**입니다. 「힙은 최솟값을 내주는
자료구조」로 배운 뒤라 둘 다 최소 힙으로 두기 쉬워요. 작은 쪽을 `new Heap(1)` 로 바꿔 봅시다.

```ts
private readonly low = new Heap(1); // ← 최대 힙이어야 하는 자리를 최소 힙으로 두었다
private readonly high = new Heap(1);
```

<!--proof:pauseSameDirection-->

```text
수열            정본이 낸 답       둘 다 최소 힙인 답  판정
전개 입력       5 10 5 4 5         5 10 1 2 1          틀리다
오름차순 1 … 6  1 1.5 2 2.5 3 3.5  1 1.5 1 2 1 2.5     틀리다
```

전개 입력에서 셋째 답이 5 가 아니라 1 로 나옵니다. 두 판의 두 힙을 수 하나마다 꺼낼 차례로 떠 보면 갈리는
자리가 보여요.

<!--proof:pause-same-states-->

| 넣은 수 | 판 | 작은 쪽(꺼낼 차례) | 큰 쪽(꺼낼 차례) | 답 |
| --- | --- | --- | --- | ---: |
| 1 번째 수 5 | 정본 | 5 | 비어 있음 | 5 |
| 1 번째 수 5 | 둘 다 최소 힙 | 5 | 비어 있음 | 5 |
| 2 번째 수 15 | 정본 | 5 | 15 | 10 |
| 2 번째 수 15 | 둘 다 최소 힙 | 15 | 5 | 10 |
| 3 번째 수 1 | 정본 | 5 1 | 15 | 5 |
| 3 번째 수 1 | 둘 다 최소 힙 | 1 15 | 5 | 1 |

3 번째 수 1 을 넣은 뒤 두 판의 답이 5 와 1 로 처음 갈립니다.

<!--/proof-->

둘째 수 15 를 넣은 뒤에 이미 두 판의 두 무리가 뒤바뀌어 있습니다. 바뀐 판은 작은 쪽에 15, 큰 쪽에 5 를
두었는데, 이 걸음은 평균을 내는 걸음이라 답이 10 으로 같아서 아직 티가 나지 않아요. 셋째 수 1 에서 작은
쪽의 꼭대기가 1 이 되고, 가장 작은 값이 답으로 나옵니다. 작은 쪽이 최솟값을 꼭대기에 두면 ② 가 옮기는
것이 경계의 값이 아니라 반대쪽 끝의 값이 되기 때문이에요. 작은 쪽에서 꺼내야 하는 것은 그 무리의
**최댓값**입니다.

#### 2. 새 수를 작은 쪽에 넣고 꼭대기를 옮긴다

둘째 조각이 `addNum` 입니다. 세 줄이고, 갈래는 마지막 줄 하나뿐이에요.

```ts
addNum(num: number): void {
  this.low.push(num); // ① 비교하지 않고 작은 쪽에 넣는다
  this.high.push(this.low.pop()); // ② 작은 쪽의 최댓값을 큰 쪽으로 옮긴다
  if (this.high.size() > this.low.size()) { // ③ 큰 쪽이 더 많아졌으면
    this.low.push(this.high.pop()); //    최솟값 하나를 도로 옮긴다
  }
}
```

첫 두 수를 넣으면서 세 줄마다 두 힙을 꺼낼 차례로 떠 보면 이렇게 나옵니다.

<!--proof:walk-add-two-->

```text
addNum(5) 만 실행하면
  ① 작은 쪽에 5 를 넣는다      작은 쪽 5          큰 쪽 비어 있음
  ② 꼭대기 5 를 큰 쪽으로      작은 쪽 비어 있음  큰 쪽 5
  ③ 큰 쪽 1 > 작은 쪽 0 이 참  작은 쪽 5          큰 쪽 비어 있음

이어서 addNum(15) 까지 실행하면
  ① 작은 쪽에 15 를 넣는다       작은 쪽 15 5  큰 쪽 비어 있음
  ② 꼭대기 15 를 큰 쪽으로       작은 쪽 5     큰 쪽 15
  ③ 큰 쪽 1 > 작은 쪽 1 이 거짓  작은 쪽 5     큰 쪽 15
```

② 가 「경계를 맞추는 줄」입니다. 15 처럼 큰 쪽에 속하는 수는 작은 쪽의 꼭대기가 되어 그 수 자신이
넘어가요. 첫 수 5 에서는 ③ 이 참이고 둘째 수 15 에서는 거짓이라, 3단계에서 본 홀짝의 규칙이 그대로
나옵니다.

#### 짚고 가기 — 값의 크기로만 가르고 개수를 안 맞추면 꼭대기가 가운데 자리를 벗어난다

여기서 헷갈리기 쉬운 포인트는 **①과 ②를 「알맞은 쪽에 넣기」로 줄이는 것**입니다. 「어차피 작은 값은
작은 쪽, 큰 값은 큰 쪽 아닌가, 비교해서 바로 넣으면 되지」로 읽기 쉬워요. 그 생각대로 개수를 맞추는 ③ 까지
함께 걷어내 봅시다.

```ts
addNum(num: number): void {
  if (this.low.size() === 0 || num <= this.low.peek()) this.low.push(num);
  else this.high.push(num);
  // ← 개수를 맞추는 줄이 없다
}
```

<!--proof:pauseValueSplit-->

```text
수열            정본이 낸 답       값으로만 가른 답  판정
전개 입력       5 10 5 4 5         5 10 5 5 5        틀리다
오름차순 1 … 6  1 1.5 2 2.5 3 3.5  1 1.5 1 1 1 1     틀리다
```

오름차순 수열에서 답이 1 에 굳습니다. 수 하나마다 두 힙을 떠 보면 까닭이 보여요.

<!--proof:pause-split-states-->

| 넣은 수 | 작은 쪽(꺼낼 차례) | 큰 쪽(꺼낼 차례) | 값으로만 가른 답 | 정본이 낸 답 |
| ---: | --- | --- | ---: | ---: |
| 1 | 1 | 비어 있음 | 1 | 1 |
| 2 | 1 | 2 | 1.5 | 1.5 |
| 3 | 1 | 2 3 | 1 | 2 |
| 4 | 1 | 2 3 4 | 1 | 2.5 |
| 5 | 1 | 2 3 4 5 | 1 | 3 |
| 6 | 1 | 2 3 4 5 6 | 1 | 3.5 |

여섯 걸음 내내 작은 쪽의 크기가 1 에 머물고, 둘째 수부터는 전부 큰 쪽으로 갑니다.

<!--/proof-->

첫 수 1 이 작은 쪽의 꼭대기가 된 뒤로, 그보다 큰 수는 전부 큰 쪽으로 갑니다. 작은 쪽의 크기가 1 에 굳어서
꼭대기가 정렬한 수열의 첫 자리를 가리키고, 가운데 자리와는 점점 멀어져요. 값의 규칙은 **어느 쪽에
들어가는가**를 정하고, 개수의 규칙은 **경계가 어디인가**를 정합니다. 둘 중 하나만 지키면 꼭대기는 여전히
「작은 쪽의 최댓값」이지만 그 자리가 가운데가 아니에요.

#### 3. 두 꼭대기로 답을 만들고 다섯 수를 끝까지 넣는다

셋째 조각이 `findMedian` 입니다. 두 크기가 같으면 두 꼭대기의 평균, 다르면 작은 쪽 꼭대기 하나예요.

```ts
findMedian(): number {
  if (this.low.size() === this.high.size()) { // ④ 두 크기가 같은가
    return (this.low.peek() + this.high.peek()) / 2;
  }
  return this.low.peek();
}
```

두 조각을 이어 다섯 수에 실행하면 아홉 걸음이 나옵니다. T1 은 시작값, T2 부터 T4 까지가 첫 `addNum` 을
세 줄로 갈라 본 것, T5 부터 T8 까지가 나머지 네 수, T9 가 마지막 상태예요. 무대의 윗줄은 들어오는 수이고
괄호가 지금까지 들어온 수, ▲ 가 이번 걸음에 넣는 수입니다. 아래 두 줄이 작은 쪽과 큰 쪽을 꺼낼 차례대로
늘어놓은 것이라 첫 칸이 꼭대기이고, 강조한 칸은 이번 걸음에 새로 들어온 값, ▲ 가 달린 칸은 `findMedian`
이 읽은 꼭대기예요.

걸음마다 무엇이 일어났는지 펼치면 이렇습니다.

| --- | --- | --- | --- | --- | ---: | ---: |
| T1 | 시작값 | - | 비어 있음 | 비어 있음 | 0 | - |

마지막 findMedian 이 돌려준 값 5 는 정렬한 수열 1 3 5 5 15 의 가운데 자리 값과 같습니다.

T6 에서는 1 을 넣었는데 5 가 큰 쪽으로 갔다가 도로 돌아왔습니다. 1 이 작은 쪽의 꼭대기가 되지 못해 원래
꼭대기 5 가 넘어갔고, 그 바람에 큰 쪽이 둘이 되어 최솟값 5 가 돌아온 거예요. T8 에서는 이미 있던 5 가 한 번
더 들어와 두 힙에 5 가 하나씩 놓였고, 두 힙 어디에도 중복을 따로 다루는 자리가 없습니다. 라벨 넷이 어느
걸음에서 실행됐는지 모으면 이렇습니다.

<!--proof:walk-labels-->

| 라벨 | 하는 일 | 실행된 걸음 · 참인 걸음 | 거짓인 걸음 |
| --- | --- | --- | --- |
| ① | 새 수를 작은 쪽에 넣는다 | T2 T5 T6 T7 T8 | - |
| ② | 작은 쪽 꼭대기를 큰 쪽으로 옮긴다 | T3 T5 T6 T7 T8 | - |
| ③ | 큰 쪽이 더 많은가 | T4 T6 T8 | T5 T7 |
| ④ | 두 크기가 같은가 | T5 T7 | T4 T6 T8 |

라벨 넷이 모두 실행됐고, ③ 과 ④ 는 참과 거짓이 둘 다 나왔습니다.

<!--/proof-->

③ 과 ④ 가 정확히 엇갈리는 것도 봐 주세요. 도로 옮긴 걸음은 작은 쪽이 하나 더 많아진 걸음이고, 그때 두
크기가 다르니 답이 꼭대기 하나입니다.

#### 짚고 가기 — 알맞은 쪽에 바로 넣어도 답은 안 틀린다

앞의 「짚고 가기」에서 걷어낸 것은 개수 규칙이었지, 「알맞은 쪽에 바로 넣기」 자체가 아니었어요.
**개수 규칙을 그대로 두고** 넣는 자리만 비교하면 어떻게 되는지 봅시다.

```ts
addNum(num: number): void {
  if (this.low.size() === 0 || num <= this.low.peek()) this.low.push(num);
  else this.high.push(num);
  if (this.low.size() > this.high.size() + 1) this.high.push(this.low.pop());
  else if (this.high.size() > this.low.size()) this.low.push(this.high.pop());
}
```

두 힙의 세 줄은 새 수가 어느 쪽에 속하든 넣기 · 꺼내기 · 넣기를 늘 하고, 크기를 맞출 때 둘을 더 합니다.
바로 넣은 판은 대개 넣기 하나로 끝나고, 크기가 어긋날 때만 둘을 더해요. 그럼에도 이 글이 세 줄짜리를
정본으로 삼는 이유는 **갈래가 하나**라서입니다. 바로 넣는 판은 빈 힙을 따로 다뤄야 하고 도로 옮기는 방향이
둘로 갈리는데, 그 셋 중 하나만 빠져도 앞의 두 「짚고 가기」에서 본 실패로 이어져요. 횟수가 중요한 자리라면
바로 넣는 쪽이 낫습니다.

#### 4. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 셋이에요 — `push` 가 부모와 비교하며 위로
올라가는 부분, `pop` 이 마지막 원소를 뿌리로 옮긴 뒤 아래로 내려가는 부분, 그리고 빈 힙에서는 `peek` 과
`pop` 을 부르지 않는다는 약속입니다.

```ts
export class Heap {
  private items: number[] = [];

  /** `+1` 이면 최소 힙, `-1` 이면 최대 힙이다. */
  constructor(private readonly sign: number) {}

  size(): number {
    return this.items.length;
  }

  /** 꼭대기 값. 빈 힙에서는 부르지 않는다. */
  peek(): number {
    return this.items[0] as number;
  }

  push(value: number): void {
    this.items.push(value);
    let i = this.items.length - 1;
    while (i > 0) {
      const parent = (i - 1) >> 1;
      if (!this.prior(i, parent)) break;
      this.swap(i, parent);
      i = parent;
    }
  }

  /** 꼭대기를 빼고 돌려준다. 빈 힙에서는 부르지 않는다. */
  pop(): number {
    const top = this.items[0] as number;
    const last = this.items.pop() as number;
    if (this.items.length > 0) {
      this.items[0] = last;
      let i = 0;
      for (;;) {
        const left = 2 * i + 1;
        const right = 2 * i + 2;
        let best = i;
        if (left < this.items.length && this.prior(left, best)) best = left;
        if (right < this.items.length && this.prior(right, best)) best = right;
        if (best === i) break;
        this.swap(i, best);
        i = best;
      }
    }
    return top;
  }

  /** 자리 `a` 의 값이 자리 `b` 의 값보다 꼭대기에 가까운가. 방향은 `sign` 이 정한다. */
  private prior(a: number, b: number): boolean {
    return (
      this.sign * ((this.items[a] as number) - (this.items[b] as number)) < 0
    );
  }

  private swap(a: number, b: number): void {
    const t = this.items[a] as number;
    this.items[a] = this.items[b] as number;
    this.items[b] = t;
  }
}

export class MedianFinder {
  /** 작은 쪽 절반. 최대 힙이라 꼭대기가 그 절반의 최댓값이다. */
  private readonly low = new Heap(-1);
  /** 큰 쪽 절반. 최소 힙이라 꼭대기가 그 절반의 최솟값이다. */
  private readonly high = new Heap(1);

  addNum(num: number): void {
    // ① 값이 어느 쪽에 속하는지 비교하지 않고 작은 쪽에 먼저 넣는다.
    this.low.push(num);

    // ② 작은 쪽의 최댓값을 큰 쪽으로 옮긴다 — 두 절반의 경계가 이 줄에서 맞춰진다.
    this.high.push(this.low.pop());

    // ③ 큰 쪽이 더 많아졌으면 최솟값 하나를 작은 쪽으로 도로 옮긴다.
    if (this.high.size() > this.low.size()) {
      this.low.push(this.high.pop());
    }
  }

  findMedian(): number {
    // ④ 개수가 같으면 두 꼭대기의 평균, 다르면 작은 쪽 꼭대기 하나가 답이다.
    if (this.low.size() === this.high.size()) {
      return (this.low.peek() + this.high.peek()) / 2;
    }
    return this.low.peek();
  }
}
```

### 알아 두면 좋은 개념 — 순서통계량

두 힙이 유지한 것에는 이름이 붙어 있습니다. 작은 쪽의 크기를 `k = ⌈N/2⌉` 로 맞춰 두었더니 그 꼭대기가
**정렬했을 때 `k` 번째로 작은 값**이 됐어요. 정렬된 수열의 `k` 번째 값을 **`k` 번째 순서통계량**이라고
부릅니다. 전개의 T8 상태에서 자리마다 값과 그 값이 담긴 힙을 적으면 이렇습니다.

<!--proof:related-rank-->

| 자리 | 1 | 2 | 3 | 4 | 5 |
| --- | --- | --- | --- | --- | --- |
| 값 | 1 | 3 | 5 | 5 | 15 |
| 담긴 힙 | 작은 쪽 | 작은 쪽 | 작은 쪽 | 큰 쪽 | 큰 쪽 |

작은 쪽 꼭대기 5 는 자리 3 의 값이고, 수 5 개에서 ⌈5/2⌉ = 3 번째 순서통계량입니다.

<!--/proof-->

크기를 3 이 아니라 다른 `k` 로 맞추면 꼭대기가 그 `k` 번째 순서통계량이 됩니다. 작은 쪽의 크기를 `⌈N/2⌉`
대신 `⌈0.95N⌉` 로 맞추도록 크기 규칙만 바꾸면 두 힙이 95 백분위수를 답해요. 중앙값은 그 가족의 한 자리입니다.

| 다시 나오는 자리 | `k` 번째 값 |
| --- | --- |
| 선택 알고리즘 (quickselect) | 정렬하지 않고 `k` 번째 값 하나만 골라 낸다 |
| 응답 시간 감시 | 95 백분위수 · 99 백분위수 지연 시간 |
| 슬라이딩 창의 중앙값 | 창의 크기가 `w` 면 그 안의 `⌈w/2⌉` 번째 값 |

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 두 꼭대기가 답이라는 것을 식으로 어떻게
적는지, 무엇이 매 걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 수가 하나씩 들어오고 지워지지 않는다 | 지우는 연산이 있으면 힙에서 가운데의 값을 빼야 하는데 힙은 그것을 바로 못 한다 | 넣기와 꼭대기 꺼내기만 있다 |
| 묻는 것이 가운데 자리로 정해져 있다 | 매번 다른 `k` 를 물으면 두 크기를 그때마다 다시 맞춰야 한다 | 크기 규칙이 `⌈N/2⌉` 하나로 정해진다 |
| 답을 자주 물어본다 | 묻기는 꼭대기 둘을 읽는 것이라 비용이 없다시피 하고, 그 대신 넣을 때 비용을 치른다 | 묻기가 `O(1)` 이다 |
| 값의 범위가 넓거나 미리 알려지지 않았다 | 값이 좁은 정수 범위에 있으면 개수 배열 하나로 세는 편이 더 적다 | 값으로 자리를 잡는 배열이 없다 |

첫 줄이 이 절차의 경계입니다. 지우는 연산이 붙으면 두 힙만으로는 부족하고, 그때는 균형 이진 탐색 트리나
값 범위 위의 세그먼트 트리 쪽으로 가야 해요.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "스트림으로 들어온다" "실시간으로" "지금까지의"   ← 값이 하나씩 늘어난다
  "중앙값" "가운데 값" "50 백분위수"                ← 가운데 자리 하나를 묻는다
  "언제든 물어볼 수 있다" "매번 답한다"             ← 묻기가 잦다
  "추가와 조회가 섞여서 온다"                       ← 모아 두었다가 한 번에 처리할 수 없다

제약에 이런 모양이 보이면
  추가와 조회를 합쳐 10^5 번 안팎이고, 조회마다 정렬하면 예산을 넘는다
  값의 범위가 10^9 규모라 값마다 칸을 두는 배열을 못 만든다

반대로 이런 말이 보이면 해당하지 않는다
  "배열이 한 번에 주어진다"                         ← 한 번 정렬하거나 골라내면 끝난다
  "k 번째 값을 매번 다른 k 로 묻는다"               ← 크기 규칙이 하나로 정해지지 않는다
  "값을 지우는 연산도 있다"                         ← 힙이 가운데의 값을 못 뺀다
  "값이 0 … 100 사이의 정수다"                      ← 개수 배열이 더 적다
```

마지막 무리가 보이면 다른 절차로 갑니다. 배열이 한 번에 주어지면
[`kthSmallest`](../kthSmallest/kthSmallest-guide.md) 쪽이 정렬 없이 답을 내고, 전체 순서가 필요하면
[`sortArray`](../sortArray/sortArray-guide.md) 로 갑니다.

#### 실제로 쓰이는 곳

- **CPython 의 `heapq` 공식 문서** — 「Other Applications」 절이 이 방법을 이름으로 지정하고 예제 코드까지
  싣습니다. *"A running median can be efficiently implemented by balancing two heaps, a max-heap for values
  at or below the midpoint and a min-heap for values above the midpoint."* 예제의 변수 주석도
  `lo = []  # max-heap` · `hi = []  # min-heap (same size as or one smaller than lo)` 로, 이 글의 크기 규칙과
  같은 문장이 그대로 들어가 있어요.
  ([`heapq` — Heap queue algorithm](https://docs.python.org/3/library/heapq.html), 조회 2026-08-30)
- **아파치 스파크의 `PercentileHeap`** — 스케줄러가 **느린 작업을 다시 띄울지 정하는 자리**에 씁니다. 파일
  머리 주석이 *"The implementation keeps two heaps: a small heap (`smallHeap`) and a large heap
  (`largeHeap`). The small heap stores all the numbers below the percentile and the large heap stores the
  ones above the percentile."* 이고, 필드 주석은 *"This is a min-heap so it works out of the box."* 와
  *"This is a max-heap. … Instead we negate values when we offer/poll/peek."* 로 두 방향을 갈라 적어
  뒀어요. 값을 뒤집어 담아 최대 힙을 만든 것이 이 글의 `sign` 과 같은 자리입니다.
  ([`PercentileHeap.scala`](https://github.com/apache/spark/blob/master/core/src/main/scala/org/apache/spark/util/collection/PercentileHeap.scala),
  조회 2026-08-30)
- **pydata 의 Bottleneck `move_median`** — 창을 옮기며 중앙값을 내는 수치 함수이고, C 소스의 `mm_new()`
  바로 위 주석이 *"At the start of bn.move_median two heaps are created. One heap contains the small values
  (a max heap); the other heap contains the large values (a min heap)."* 입니다. 이쪽은 창이 움직이므로 값을
  **지우는** 연산이 붙고, 그래서 힙 안의 자리를 따로 기억하는 손잡이(`mm_handle`)를 함께 둡니다.
  ([`move_median.c`](https://github.com/pydata/bottleneck/blob/master/bottleneck/src/move_median/move_median.c),
  조회 2026-08-30)

세 자리가 두 힙을 쓰는 목적은 조금씩 다릅니다.

| 쓰는 곳 | 두 힙으로 하는 일 | 지우는 연산 |
| --- | --- | --- |
| CPython 문서 | 힙 API 의 쓰임새로 이 방법을 예제 코드로 싣는다 | 없다 |
| 스파크 | 작업 시간의 백분위수를 보고 느린 작업을 다시 띄울지 정한다 | 없다 |
| Bottleneck | 창을 옮기며 중앙값을 낸다 | 있다 — 힙 안의 자리를 따로 기억한다 |

#### 경쟁 설계와의 대조

같은 목표(수가 하나씩 들어오는 동안 중앙값을 답하는 것)를 노리는 다른 절차로 **매번 선택 알고리즘으로
가운데 자리를 골라내는 설계**가 있습니다. 추가는 배열 끝에 칸 하나를 쓰는 것으로 끝나고, 물어볼 때 기준값을
잡아 배열을 두 조각으로 가르기를 되풀이해 그 자리 하나만 확정해요. 두 설계가 비용을 치르는 자리가
반대입니다.

| 설계 | 넣을 때 | 물어볼 때 |
| --- | --- | --- |
| 두 힙 | 힙 연산 셋이나 다섯 | 꼭대기 둘 읽기 |
| 매번 골라내기 | 칸 하나 쓰기 | 배열을 여러 번 가르기 |

같은 입력 · 같은 작업 목록에 두 설계를 실행하고 **기본 연산 수**(값 비교 + 배열 칸 쓰기)를 셌습니다. 입력은
수 4,096 개이고 생성식은 `s ← (s × 1,103,515,245 + 12,345) mod 2^32` 에서 `s mod 2,000,000,001 − 10^9` 를
값으로 쓰며 시작 상태는 `1` 입니다. 작업 목록은 그 4,096 개를 넣는 동안 `q` 번 물어보는 것이고, `t` 번째
질의는 수를 `⌈4096 · t / q⌉` 개 넣은 직후예요. **전개 입력을 그대로 쓰지 않은 이유**는 그것이 수 다섯
개라 물어보는 횟수를 다섯까지밖에 못 늘려서, 우열이 뒤집히는 자리를 만들 수 없기 때문입니다.

| 물어본 횟수 `q` | 두 힙 | 매번 골라내기 | 적은 쪽 |
| --- | --- | --- | --- |
| 0 회 | 404,830 | **4,096** | 매번 골라내기 |
| 16 회 | 404,830 | **125,180** | 매번 골라내기 |
| 71 회 | 404,830 | **392,754** | 매번 골라내기 |
| 72 회 | **404,830** | 413,848 | 두 힙 — **여기서 순서가 뒤집힙니다** |
| 4,096 회 | **404,830** | 16,818,833 | 두 힙 |

**저장 칸은 4,096 개 대 4,096 개입니다.** 둘 다 들어온 수를 그대로 담으므로 메모리에서는 안 갈려요 —
갈리는 것은 연산 수이고, 그 경계가 이 입력에서 **물어본 횟수 72 회**입니다. 경계 둘레를 한 회씩 재 보면
이렇게 나옵니다. 골라내기 쪽의 값이 오르내리는 것은 질의가 놓인 자리가 `q` 마다 달라지기 때문이에요 —
늦게 물어볼수록 그때의 배열이 길어서 한 번의 값이 커집니다.

<!--proof:altAround-->

```text
물어본 횟수 q    두 힙  매번 골라내기  적은 쪽
           69  404,830        389,371  매번 골라내기
           70  404,830        394,018  매번 골라내기
           71  404,830        392,754  매번 골라내기

           73  404,830        410,012  두 힙

q 를 0 부터 300 까지 전부 재면 골라내기가 마지막으로 적은 자리가 71 회다
그 뒤로는 다시 뒤집히지 않는다
```

**두 힙이 내주는 것은 물어보는 일이 드문 작업입니다.** 한 번도 안 물어보면 두 힙의 404,830 번이 고스란히
쓸모없는 비용이 되고, 골라내기 쪽은 4,096 번으로 끝나요. 그 대신 두 힙이 얻는 것이 셋입니다.

| 축 | 두 힙 | 매번 골라내기 |
| --- | --- | --- |
| 물어보기 한 번 | 꼭대기 둘 읽기 | 배열 길이에 비례한다 |
| 전체 비용과 `q` | `q` 와 무관하게 일정하다 | 물어볼수록 늘어난다 |
| 최악 보장 | 힙 높이로 닫힌다 | 기준값 선택에 달렸다 |

**우열이 반대가 되는 조건이 분명합니다.** `findMedian` 이 언제 몇 번 불릴지 모르는 과제라면 두 힙이
답이고, 같은 입력에서 **물어보는 횟수가 71 회 이하로 정해져 있다면** 골라내기 쪽이 적어요.

### 수식 정의와 유도

지금까지 들어온 수를 오름차순으로 늘어놓은 것을 $s_1 \le s_2 \le \cdots \le s_N$ 이라 쓰고, 중앙값을 이렇게
정의합니다.

$$\operatorname{med}(N) = \begin{cases} s_{(N+1)/2} & (N \text{ 이 홀수}) \\[4pt] \dfrac{s_{N/2} + s_{N/2+1}}{2} & (N \text{ 이 짝수}) \end{cases}$$

정의를 자리 번호로 읽으면 이렇습니다. 전개 입력의 수 다섯과, 넷까지 넣었을 때예요.

<!--proof:math-positions-->

```text
  자리  1  2  3  4  5
  값    1  3  5  5  15
  N = 5 는 홀수라 (5+1)/2 = 3 번째 자리 → 답 5

  자리  1  2  3  4
  값    1  3  5  15
  N = 4 는 짝수라 2 번째와 3 번째 자리 → 답 4
```

두 무리는 그 수열을 앞뒤로 자른 것입니다. 자르는 자리를 $k = \lceil N/2 \rceil$ 로 두면 $L_N$ 이 앞의
$k$ 개, $H_N$ 이 나머지예요.

$$L_N = \{\, s_1, \dots, s_k \,\}, \qquad H_N = \{\, s_{k+1}, \dots, s_N \,\}, \qquad k = \lceil N/2 \rceil$$

<!--proof:math-cut-->

```text
  N = 5  k = 3  1 3 5 | 5 15  L 의 원소 3 개 · H 의 원소 2 개
  N = 4  k = 2  1 3 | 5 15    L 의 원소 2 개 · H 의 원소 2 개
  N = 3  k = 2  1 5 | 15      L 의 원소 2 개 · H 의 원소 1 개
```

$L_N$ 의 원소 수가 늘 $H_N$ 과 같거나 하나 많습니다. 정의를 전개 입력에 넣어 확인하고 갑시다. 왼쪽 네 열이
정의가 정하는 값이고, 오른쪽 두 열은 그 값으로 만든 답과 정본이 낸 답입니다.

<!--proof:mathCheck-->

```text
N  정렬 수열   ⌈N/2⌉  작은 쪽 꼭대기  큰 쪽 꼭대기  식이 내는 값  정본의 답
1  5               1               5          없음             5          5
2  5 15            1               5            15            10         10
3  1 5 15          2               5            15             5          5
4  1 3 5 15        2               3             5             4          4
5  1 3 5 5 15      3               5             5             5          5
```

이제 유도합니다. 먼저 **작은 쪽의 크기가 늘 $k$ 라는 것**을 넣은 수의 개수에 대한 귀납으로 얻어요.

- **기저.** $N = 0$ 일 때 두 무리가 비어 있고 $\lceil 0/2 \rceil = 0$ 이라 성립합니다.
- **단계.** $N$ 에서 $|L_N| = \lceil N/2 \rceil$ 이라고 두고 수 하나를 더합니다. 절차는 작은 쪽에 하나를
  넣어 $\lceil N/2 \rceil + 1$ 로 만들고, 꼭대기 하나를 큰 쪽으로 옮겨 $\lceil N/2 \rceil$ 로 다시 줄입니다.
  이때 큰 쪽은 $\lfloor N/2 \rfloor + 1$ 이 돼요.
- $N$ 이 짝수면 $\lceil N/2 \rceil = \lfloor N/2 \rfloor = N/2$ 이므로 큰 쪽이 하나 더 많고, 도로 옮기는 줄이
  실행되어 작은 쪽이 $N/2 + 1 = \lceil (N+1)/2 \rceil$ 이 됩니다.
- $N$ 이 홀수면 $\lceil N/2 \rceil = (N+1)/2$ 이고 $\lfloor N/2 \rfloor + 1 = (N+1)/2$ 라 두 크기가 같으므로
  도로 옮기는 줄이 실행되지 않고, 작은 쪽이 $(N+1)/2 = \lceil (N+1)/2 \rceil$ 그대로입니다.

| $N$ 의 홀짝 | 넣고 옮긴 직후의 두 크기 | 도로 옮기는 줄 | $\lvert L_{N+1} \rvert$ |
| --- | --- | --- | --- |
| $N$ 이 짝수 | $N/2$ 와 $N/2 + 1$ | 실행된다 | $N/2 + 1 = \lceil (N+1)/2 \rceil$ |
| $N$ 이 홀수 | $(N+1)/2$ 와 $(N+1)/2$ | 실행되지 않는다 | $(N+1)/2 = \lceil (N+1)/2 \rceil$ |

두 갈래 다 $|L_{N+1}| = \lceil (N+1)/2 \rceil$ 이 되므로 귀납이 끝납니다. 크기가 정해지면 두 꼭대기가 어느
자리인지도 정해져요. 「아이디어 상세」 2단계에서 보인 대로 작은 쪽의 모든 값이 큰 쪽의 모든 값 이하이므로,
작은 쪽은 정렬한 수열의 앞 $k$ 자리이고 그 최댓값이 $s_k$ 입니다.

$$\max L_N = s_k, \qquad \min H_N = s_{k+1}, \qquad k = \lceil N/2 \rceil$$

<!--proof:math-tops-->

```text
  N = 5 · k = 3  L 은 자리 1 2 3  max L = 자리 3 의 값 5
                 H 는 자리 4 5    min H = 자리 4 의 값 5
  N = 4 · k = 2  L 은 자리 1 2    max L = 자리 2 의 값 3
                 H 는 자리 3 4    min H = 자리 3 의 값 5
```

$N$ 이 홀수면 $k = (N+1)/2$ 라 $\max L_N$ 이 곧 중앙값이고, $N$ 이 짝수면 $k = N/2$ 라 $s_{N/2}$ 와
$s_{N/2+1}$ 이 두 꼭대기입니다. 그래서 두 갈래가 하나의 꼴로 닫힙니다.

$$\operatorname{med}(N) = \begin{cases} \max L_N & (N \text{ 이 홀수}) \\[4pt] \dfrac{\max L_N + \min H_N}{2} & (N \text{ 이 짝수}) \end{cases}$$

정의 그대로 쓰면 $s_1 \dots s_N$ 을 전부 정렬해 두고 자리 번호로 읽어야 하는데, 닫힌 꼴은 두 힙의 꼭대기
둘만 읽습니다. 닫힌 꼴은 임의의 $N$ 에서 성립해요. 식에서 코드로 옮기면 두 이름이 그대로 대응합니다.
코드에서는 $\max L_N$ 이 `low` 의 꼭대기, $\min H_N$ 이 `high` 의 꼭대기예요.

```ts
if (low.size() === high.size()) return (low.peek() + high.peek()) / 2;
return low.peek();
```

여기서 본문의 값만으로는 안 나오는 것이 나옵니다. **임의의 `N` 에서의 비용 상한**이에요. 힙 하나의 크기가
$\lceil N/2 \rceil$ 을 넘지 않으므로 높이는 $h = \lceil \log_2 N \rceil$ 이하이고, 한 번의 `addNum` 은 힙
연산 다섯을 넘지 않습니다. 넣기는 올라가는 동안 한 층에 비교 하나와 맞바꿈 하나(칸 쓰기 둘), 꺼내기는
내려가는 동안 한 층에 비교 둘과 맞바꿈 하나를 씁니다.

| 연산 | 비교 | 칸 쓰기 | 합 |
| --- | --- | --- | --- |
| 넣기 하나 | $h$ 이하 | $2h + 1$ 이하 | $3h + 1$ |
| 꺼내기 하나 | $2h$ 이하 | $2h + 1$ 이하 | $4h + 1$ |
| `addNum` 하나 (넣기 셋 · 꺼내기 둘) | — | — | $3(3h+1) + 2(4h+1) = 17h + 5$ |

$i$ 번째 `addNum` 의 힙 높이는 $\lceil \log_2 i \rceil$ 이하이므로 전부 더하면 다음과 같고, 합은 닫힌 형태로
풀립니다.

$$\sum_{i=1}^{N} \lceil \log_2 i \rceil = N \lceil \log_2 N \rceil - 2^{\lceil \log_2 N \rceil} + 1, \qquad \text{총 비용} \le 17 \sum_{i=1}^{N} \lceil \log_2 i \rceil + 5N$$

닫힌 형태를 작은 값에 넣어 확인합니다.

<!--proof:math-logsum-->

```text
  N = 4  더해 보면 0 + 1 + 2 + 2 = 5                   식으로 4·2 − 2^2 + 1 = 5   같다
  N = 8  더해 보면 0 + 1 + 2 + 2 + 3 + 3 + 3 + 3 = 17  식으로 8·3 − 2^3 + 1 = 17  같다
```

이 닫힌 형태에 규모를 넣으면 물어볼 때마다 정렬하는 설계와 갈리는 자리가 값으로 나옵니다.

<!--proof:mathScale-->

```text
수의 개수 N  실측 비교 + 칸 쓰기  17·Σ⌈log2 i⌉ + 5N 상한
        256               14,602                  31,761
      1,024               79,773                 161,809
      4,096              404,830                 786,449

호출 100,000 번 (넣기 50,000 · 묻기 50,000) 이면
  두 힙                        12,735,905 번 이하
  물어볼 때마다 전부 정렬한다  36,723,984,465 번 이하
  두 값의 비                   2,884 배
```

마지막 세 줄이 이 절이 주는 것입니다. 과제 규모에서 두 설계가 **2,884 배** 갈리고, 그 값은 본문의 어느
걸음을 세어서도 안 나와요 — 수 50,000 개짜리 실행을 실제로 하지 않고 식으로만 낸 값입니다.

### 불변식 — 작은 쪽의 어떤 값도 큰 쪽의 어떤 값보다 크지 않고, 작은 쪽이 ⌈N/2⌉ 칸이다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그건 수열 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해 봅시다.

> `addNum` 하나가 끝난 시점마다 둘이 참입니다. **(값)** `low` 에 담긴 어떤 값도 `high` 에 담긴 어떤 값보다
> 크지 않습니다. **(개수)** `low` 의 크기에서 `high` 의 크기를 뺀 값이 0 또는 1 입니다.

<!--fig:invariant-boundary-->
![addNum 이 끝날 때마다 두 절반의 경계가 정렬한 수열의 가운데에 놓인다](./figs/invariant-boundary.svg)

그림은 전개 입력을 하나씩 넣을 때마다 두 절반을 정렬한 수열 위에 그린 것이고, 경계가 늘 가운데에 놓입니다.
앞 문장은 두 무리 사이에 경계선을 그을 수 있다는 뜻이고, 뒤 문장은 그 경계선이 정확히 가운데 자리에 있다는
뜻입니다. 둘 다 「`addNum` 하나가 끝난 시점」에만 말해요 — 세 줄의 중간에서는 깨져 있어도 됩니다. 문장이
둘인 것에도 이유가 있습니다. 앞 문장만으로는 경계가 어디에 있는지 모르고, 뒤 문장만으로는 꼭대기가
경계값인지 모르니까요. 둘이 함께 있어야 「작은 쪽의 꼭대기가 `⌈N/2⌉` 번째로 작은 값」이 나옵니다.

**출발점부터 봅시다.** 아무것도 넣지 않은 상태에서 두 힙이 비어 있습니다. 값 문장은 비교할 쌍이 없어
참이고, 개수 문장은 0 − 0 = 0 이라 참이에요. 그다음 한 번의 `addNum` 이 세 줄을 실행합니다.

| 세 줄 중 어디 | 하는 일 | 값 문장 | 개수 문장 |
| --- | --- | --- | --- |
| 넣는 줄 | 새 수를 `low` 에 넣는다 | 깨질 수 있다 — 새 수가 `high` 의 값보다 클 수 있다 | 차이가 1 또는 2 가 된다 |
| 옮기는 줄 | `low` 의 최댓값을 `high` 로 옮긴다 | 옮긴 값이 `low` 의 최댓값이라 남은 값은 전부 그 이하다 | 차이가 −1 또는 0 이 된다 |
| 도로 옮기는 줄 | `high` 가 더 많으면 최솟값을 도로 옮긴다 | 도로 옮긴 값이 `high` 의 최솟값이라 남은 값은 전부 그 이상이다 | 차이가 0 또는 1 로 정해진다 |

옮기는 줄이 이 논증의 핵심입니다. 새 수가 `high` 의 어떤 값보다 크더라도, 그 수는 `low` 에 들어간 순간
`low` 의 최댓값이 되므로 옮기는 줄이 바로 그 수를 `high` 로 옮겨요. 새 수가 그렇게 크지 않으면 원래 `low` 에 있던 최댓값이
옮겨 가는데, 그 값은 이미 `high` 의 모든 값 이하였던 값이라 옮겨도 `high` 의 최솟값 자리를 넘지 않습니다.

| `high` 로 옮겨 간 값 | `high` 의 최솟값과의 관계 | 근거 |
| --- | --- | --- |
| 새 수 자신 | 이하일 수도, 클 수도 있다 | 어느 쪽이든 `low` 에 남은 값이 전부 그 이하다 |
| 원래 `low` 의 최댓값 | 이하다 | 넣기 전 값 문장이 참이었다 |

도로 옮기는 줄이 값 문장을 다시 깨지 않는 것도 봐 주세요. 도로 옮기는 값은 `high` 의 **최솟값**이고, 값 문장이 참인
상태에서 그 값은 `low` 의 모든 값 이상이므로 `low` 에 들어가면 그대로 새 최댓값이 됩니다.

**경계에 있는 입력도 확인하고 갑시다.** 수가 하나뿐일 때는 첫 걸음에서 도로 옮기는 줄이 실행되어 그 수 자신이 답이고,
전부 같은 값이면 비교가 늘 거짓이라 자리를 안 바꿉니다. 음수는 부호를 따로 다루는 자리가 없고, 값의 양
끝이 함께 들어오면 두 꼭대기의 합이 많아야 `2 × 10^9` 이라 정확히 더해져요. 내림차순이면 새 수가 늘
최솟값이라 도로 옮기는 줄이 자주 실행됩니다. 여섯 경우를 정의대로 고른 답과 나란히 놓았습니다.

<!--proof:edgeCases-->

```text
경계 입력              넣은 수                 정본의 답  정의대로 고른 답
수가 하나뿐이다        7                       7          7
수가 둘이다            7 8                     7.5        7.5
전부 같은 값이다       5 5 5 5                 5          5
음수만 들어온다        -5 -10                  -7.5       -7.5
값의 양 끝             -1000000000 1000000000  0          0
내림차순으로 들어온다  5 4 3 2 1               3          3
```

**이제 깨뜨려 봅시다.** 개수 문장을 지키던 줄은 도로 옮길지 정하는 `if (this.high.size() > this.low.size())`
한 줄이에요. 「크기가 같을 때도 도로 옮겨 두면 작은 쪽이 늘 하나 많아서 더 단순하지 않나」라는 생각으로
`>` 를 `>=` 로 바꿔 봅시다.

```ts
this.low.push(num);
this.high.push(this.low.pop());
if (this.high.size() >= this.low.size()) { // ← > 를 >= 로 바꾸었다
  this.low.push(this.high.pop());
}
```

<!--proof:mutantSizeRule-->

```text
수열            정본이 낸 답       `>` 를 `>=` 로 바꾼 답  판정
전개 입력       5 10 5 4 5         5 15 5 5 5              틀리다
오름차순 1 … 6  1 1.5 2 2.5 3 3.5  1 2 2 3 3 4             틀리다
```

개수 문장이 깨지면 작은 쪽의 크기가 `⌈N/2⌉` 를 넘어갑니다. 전개 입력에서 둘째 답이 10 이 아니라 15 로
나오는데, 두 판의 두 힙을 나란히 놓으면 까닭이 보여요.

<!--proof:mutant-size-states-->

| 자리 | 판 | 작은 쪽(꺼낼 차례) | 큰 쪽(꺼낼 차례) | 두 크기 | 답 |
| --- | --- | --- | --- | --- | ---: |
| 전개 입력 · 2 번째 수 15 뒤 | 정본 | 5 | 15 | 1 · 1 | 10 |
| 전개 입력 · 2 번째 수 15 뒤 | >= 로 바꾼 판 | 15 5 | 비어 있음 | 2 · 0 | 15 |
| 오름차순 1 … 6 · 6 번째 수 6 뒤 | 정본 | 3 2 1 | 4 5 6 | 3 · 3 | 3.5 |
| 오름차순 1 … 6 · 6 번째 수 6 뒤 | >= 로 바꾼 판 | 4 3 2 1 | 5 6 | 4 · 2 | 4 |

<!--/proof-->

크기가 같을 때도 도로 옮기면 두 크기의 차이가 0 에서 멈추지 않고 2 까지 벌어집니다. 둘째 수 15 뒤에 작은
쪽이 5 와 15 를 다 담아 꼭대기가 최댓값 15 가 되고, 오름차순 1 … 6 의 여섯째 걸음에서는 작은 쪽 4 개 ·
큰 쪽 2 개가 되어 답이 3.5 가 아니라 4 입니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 두 무리입니다 — `addNum` 이 치르는 힙 연산과, `findMedian` 이 읽는 꼭대기 둘이에요.
전개의 걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perfCount-->

```text
무리                어느 걸음에서      횟수
작은 쪽에 넣기      T2 T4 T5 T6 T7 T8     8
작은 쪽에서 꺼내기  T3 T5 T6 T7 T8        5
큰 쪽에 넣기        T3 T5 T6 T7 T8        5
큰 쪽에서 꺼내기    T4 T6 T8              3

수 5 개를 넣고 그때마다 물어본 실측
  힙 연산                               넣기 13 · 꺼내기 8
  비교                                  12 번
  칸 쓰기                               31 번
  합                                    43 번
  물어보기 한 번이 더한 비교와 칸 쓰기  0 번
```

`addNum` 다섯 번에 힙 연산이 스물한 번입니다. 넣기 열셋은 ① 과 ② 의 넣기가 다섯씩 열, 그리고 도로 옮긴 걸음
T4 · T6 · T8 의 넣기 셋이에요. 꺼내기 여덟은 ② 의 꺼내기 다섯과 도로 옮긴 걸음의 셋입니다. 묻기는 꼭대기를
읽기만 해서 비교와 칸 쓰기를 더하지 않아요.

그러니 총식은 두 항의 합입니다. `addNum` 을 부른 횟수를 `A`, `findMedian` 을 부른 횟수를 `F` 라 하면
`A + F = Q` 이고, 두 항은 이렇게 나뉩니다.

| 항 | 한 번의 비용 | 횟수 |
| --- | --- | --- |
| `addNum` | 힙 연산 셋이나 다섯 · 비교와 칸 쓰기 `17h + 5` 이하 | `A` |
| `findMedian` | 크기 비교와 꼭대기 읽기 — 상수 `c` | `F` |

$$\text{총 비용} \;\le\; \sum_{i=1}^{A} \bigl(17\lceil \log_2 i \rceil + 5\bigr) + c \cdot F$$

$c$ 는 이 글이 세는 비교와 칸 쓰기로는 0 이고, $A = F = 50{,}000$ 을 넣은 값이 「수식 정의와 유도」의 12,735,905 번 이하입니다. **여기서 센 것은 값 비교와
배열 칸 쓰기 전부예요.** 힙의 크기를 읽는 것과 반복 변수를 올리는 것은 세지 않았는데, 둘 다 위 값들에
비례하므로 총식의 차수가 그대로입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (모든 수가 같은 값이다) | `O(A log A + F)` | `Θ(A + F)` — 자리바꿈이 첫 비교에서 끝난다 |
| **평균적인 경우** (값의 분포를 정의하지 않는다) | `O(A log A + F)` | 정의하지 않는다 |
| **최악의 경우** (새 수가 늘 두 꼭대기 사이로 들어온다) | `O(A log A + F)` | `Θ(A log A + F)` — 실제로 도달한다 |

평균을 정의하지 않는 이유는 **값의 분포를 정할 방법이 없기 때문**입니다. 과제는 값의 범위만 정하고 어떤
분포로 들어오는지는 말하지 않아요. 실제로 「최악을 만드는 입력」의 표가 보이듯 같은 개수에서도 모양에 따라
값이 크게 갈립니다. 힙 부분을 모든 입력에서 `Θ(A log A)` 로 못 적는 것도 같은 이유예요 — 자리바꿈이 몇 번
일어나는지가 값의 모양에 달렸습니다.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없어요 — 정렬도 좌표 압축도 하지 않고, 두
힙을 비어 있는 상태로 만드는 것이 전부입니다. `addNum` 을 `A` 번 부르면 `O(A log A)`, `findMedian` 을 `F` 번
부르면 `Θ(F)` 이고 `A + F = Q` 입니다.

```text
총식  시간 = O(A log A) + Θ(F) = O(A log A + F)      addNum 이 A 번 · findMedian 이 F 번
      공간 = Θ(A)                                   두 힙이 들어온 수를 하나씩 담는다
```

**보장의 종류는 전부 최악 보장입니다.** 기댓값이 끼어들 자리가 없어요.

| 비용을 정하는 것 | 정하는 기준 | 무작위성 |
| --- | --- | --- |
| 자리를 정하는 방법 | 힙의 부모 자식 관계 | 난수를 안 쓴다 |
| 값을 비교하는 순서 | 배열 자리 | 해시가 없다 |
| 힙의 높이 | 담긴 개수 | 분포를 가정할 필요가 없다 |

해시도, 무작위성도, 분할 상환도 쓰지 않으므로 어떤 수열을 넣어도 위 상한을 넘지 않습니다. 경쟁 설계로 세운
골라내기 쪽이 기준값 선택에 따라 값이 갈리는 것과 여기서 갈려요.

#### 최악을 만드는 입력

연산 수를 최대로 만드는 모양이 무엇인지는 세어 봐야 합니다. 「정렬된 입력이면 힙이 느리다」는 말이 자주
쓰이는데, 이 절차에서 그것이 참인지부터 확인해요. 수 4,096 개를 여섯 모양으로 만들어 재 봤습니다.

<!--proof:worstShape-->

| 입력 모양 | 비교 | 칸 쓰기 | 합 |
| --- | ---: | ---: | ---: |
| 오름차순 | 160,733 | 226,330 | 387,063 |
| 내림차순 | 162,749 | 230,382 | 393,131 |
| 전부 같은 값 | 22,511 | 16,382 | 38,893 |
| 작은 값과 큰 값을 번갈아 | 162,944 | 229,554 | 392,498 |
| 바깥에서 가운데로 | 193,714 | 299,262 | 492,976 |
| 생성식 입력 | 167,742 | 237,088 | 404,830 |

수 4,096 개를 넣는 동안의 값입니다. 합이 가장 큰 모양은 「바깥에서 가운데로」이고, 「전부 같은 값」을 빼면 가장 작은 모양은 「오름차순」입니다. 「바깥에서 가운데로」의 합이 「오름차순」보다 27 % 많습니다. 질의를 4,096 번 섞어도 생성식 입력의 합은 404,830 그대로입니다.

<!--/proof-->

**「정렬된 입력이 최악이다」는 이 절차에서 성립하지 않습니다.** 가장 많은 것은 **바깥에서 가운데로** 좁혀
오는 모양이에요. 그 수열의 앞부분을 넣기 전의 두 꼭대기와 나란히 놓으면 까닭이 나옵니다.

<!--proof:worst-sequence-->

| 들어온 수 | 넣기 전 작은 쪽 꼭대기 | 넣기 전 큰 쪽 꼭대기 | 들어온 수의 자리 |
| ---: | ---: | ---: | --- |
| -4096 | 없음 | 없음 | 두 힙이 비어 있다 |
| 4096 | -4096 | 없음 | 작은 쪽 꼭대기보다 크다 |
| -4095 | -4096 | 4096 | 두 꼭대기 사이 |
| 4095 | -4095 | 4096 | 두 꼭대기 사이 |
| -4094 | -4095 | 4095 | 두 꼭대기 사이 |
| 4094 | -4094 | 4095 | 두 꼭대기 사이 |
| -4093 | -4094 | 4094 | 두 꼭대기 사이 |
| 4093 | -4093 | 4094 | 두 꼭대기 사이 |

앞 8 개 중 6 개가 두 꼭대기 사이에 들어옵니다.

<!--/proof-->

셋째 수부터 새 수가 늘 **두 꼭대기 사이**로 들어옵니다. 그러면 새 수는 ① 에서 작은 쪽의 새 최댓값이 되어
뿌리까지 올라가고, ② 에서 꺼내져 큰 쪽의 새 최솟값이 되어 다시 뿌리까지 올라가며, 두 크기가 같았던
걸음에서는 ③ 이 그 값을 또 작은 쪽의 뿌리까지 올립니다. 넣기마다 올라가는 층 수가 가장 많아지는 모양이에요.
반대로 전부 같은 값이면 올라가기도 내려가기도 첫 비교에서 끝납니다. 축마다 최악을 만드는 입력을 모으면
이렇습니다.

<!--proof:worst-axes-->

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 비교 | 「바깥에서 가운데로」 | 수 4,096 개에 193,714 번 |
| 칸 쓰기 | 「바깥에서 가운데로」 | 수 4,096 개에 299,262 번 |
| 힙의 크기 | addNum 만 100,000 번 | 작은 쪽 50,000 칸 |
| 값의 크기 | 양 끝 값 -1000000000 · 1000000000 | 정본의 답 0 |

<!--/proof-->

값의 크기는 자릿수를 한 번 볼 만합니다. 두 꼭대기를 더한 값은 많아야 `2 × 10^9` 인데, 자바스크립트의 수가
정확히 표현하는 정수의 한계가 `2^53 − 1`(약 `9 × 10^15`)이라 이 범위 안에서는 평균을 낼 때 값이 어긋나지
않아요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 들어온 수를 **작은 쪽 절반과 큰 쪽 절반으로 갈라** 두 힙에
담고, 수 하나마다 경계와 크기를 다시 맞추면, 중앙값은 두 꼭대기를 읽는 것으로 끝납니다.

```text
작은 쪽은 최대 힙, 큰 쪽은 최소 힙 → 새 수를 작은 쪽에 넣고 꼭대기를 큰 쪽으로 → 큰 쪽이 많으면 도로 하나
                                      └ 두 크기가 같으면 두 꼭대기의 평균, 다르면 작은 쪽 꼭대기가 답이다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 에서 `addNum(15)` 를 실행했는데, 15 는 그때 담긴 유일한 수 5 보다
큽니다. 그런데도 절차는 15 를 **작은 쪽에** 먼저 넣었어요. 왜 비교하지 않고 그렇게 해도 될까요?

<!--proof:selfcheck-t5-->

```text
T5 가 실행한 세 줄
  ① 작은 쪽 5 에 15 를 넣는다  작은 쪽 15 5
  ② 꼭대기를 큰 쪽으로         작은 쪽 5 · 큰 쪽 15
  ③ 크기 1 과 1 이라 거짓      그대로
```

<!--check:whyPushLowFirst-->
새 수가 큰 쪽에 속하는 값이면 **그 수 자신이 작은 쪽의 최댓값이 되기** 때문입니다. 그러면 ② 가 바로 그 수를
큰 쪽으로 옮겨요. 반대로 작은 쪽에 속하는 값이면 최댓값이 되지 못하고, 그때는 원래 있던 최댓값이 대신
넘어갑니다. 어느 쪽이든 ② 가 끝난 시점에 「작은 쪽의 모든 값 ≤ 큰 쪽의 모든 값」이 참이에요. 비교하는 줄을
넣으면 갈래가 하나 늘고, 빈 힙에서 꼭대기를 읽지 않도록 조건을 하나 더 붙여야 합니다. 절차가 그 둘을 안 쓰고도
같은 답을 내는 것이 이 설계의 요점이에요.

| 새 수 | ① 뒤 작은 쪽의 최댓값 | ② 에서 넘어가는 값 |
| --- | --- | --- |
| 큰 쪽에 속한다 | 새 수 자신 | 새 수 |
| 작은 쪽에 속한다 | 옛 최댓값 그대로 | 옛 최댓값 |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「아이디어 상세」의 「힙 배열과 정렬한 반쪽의 차이」,
「수행으로 알아보는 알고리즘」의 두 번째 「짚고 가기」, 「경쟁 설계와의 대조」를 다시 보세요.

- `N = 5` 에서 작은 쪽 배열이 `5 1 3` 이었고, T8 의 무대는 같은 힙을 `5 3 1` 로 그렸습니다. 불변식의 값
  문장이 **배열의 순서**가 아니라 **두 무리의 관계**를 말한다는 것을 이 두 줄로 설명해 보세요. 배열이
  `5 3 1` 로 놓였어도 불변식이 참인 이유가 실마리입니다.
- 두 번째 「짚고 가기」에서 개수 규칙을 걷어냈더니 오름차순 입력에서 답이 1 에 굳었습니다. 같은 코드에
  **내림차순** 6 … 1 을 넣으면 답이 어떻게 될지 먼저 예측하고, 그다음 손으로 여섯 걸음을 세어 확인해 보세요.
  오름차순과 대칭이 되는지 아닌지가 핵심입니다.
- 물어보는 횟수 `q` 에 대해 두 설계의 기본 연산 수를 각각 `q` 의 식으로 쓸 수 있을까요? 두 힙은 `q` 가 안
  들어가는 상수 하나이고, 골라내기 쪽은 질의가 놓인 자리에 따라 값이 달라집니다. 두 식을 세우고 72 라는
  경계가 그 식에서 어떻게 나오는지 따져 보세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Find Median from Data Stream

풀 파일: [`medianFromDataStream.ts`](./medianFromDataStream.ts) · 테스트: [`medianFromDataStream.test.ts`](./medianFromDataStream.test.ts) · 실행: `bun test src/algorithms/sorting/medianFromDataStream/medianFromDataStream.test.ts`

#### 한 줄 요약

> 정수가 하나씩 스트림으로 들어올 때, `addNum`으로 수를 추가하고 `findMedian`으로 **지금까지 들어온 모든 수의 중앙값**을 즉시 반환하는 자료구조를 구현한다.

#### 스토리

실시간 주식 거래소 모니터링 시스템. 매 거래마다 체결 가격이 하나씩 들어온다.
분석팀은 언제든 "지금까지 체결된 가격들의 중앙값이 얼마야?"라고 물어볼 수 있다.

거래 건수가 홀수이면 가운데 값, 짝수이면 가운데 두 값의 평균을 답해야 한다.
음수 가격(정산 후 조정치)도 포함될 수 있고, 같은 가격이 반복될 수 있다.

#### 함수 인터페이스

```ts
export class MedianFinder {
  addNum(num: number): void;
  findMedian(): number;
}
```

- `addNum(num)` — 스트림에 정수 `num`을 추가한다. 반환값 없음.
- `findMedian()` — 지금까지 추가된 모든 수의 중앙값을 반환한다. 원소 개수가 짝수이면 가운데 두 값의 평균을 반환한다.

#### 제약 조건

- 총 호출 횟수 $1 \leq Q \leq 100{,}000$
- $-10^9 \leq \text{num} \leq 10^9$ — 각 수는 이 범위의 정수이며 음수일 수 있다.
- `findMedian`은 적어도 한 번 이상 `addNum`이 호출된 뒤에만 호출된다.
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

지금까지 추가된 수들의 다중집합을 $S$라 하고 $N = |S|$라 할 때, 중앙값은 다음과 같이 정의된다.

$$
\text{median}(S) = \begin{cases}
  \text{sort}(S)\!\left[\tfrac{N-1}{2}\right] & (N \text{이 홀수}) \\[4pt]
  \dfrac{\text{sort}(S)\!\left[\tfrac{N}{2}-1\right] + \text{sort}(S)\!\left[\tfrac{N}{2}\right]}{2} & (N \text{이 짝수})
\end{cases}
$$

- **홀수 개일 때.** 정렬된 수열의 정확히 가운데 인덱스 $\lfloor (N-1)/2 \rfloor$에 해당하는 값을 반환한다.
- **짝수 개일 때.** 가운데 두 값 $(\text{index } N/2-1,\ N/2)$의 산술 평균을 반환한다. 두 값이 정수여도 평균은 소수점 이하가 생길 수 있다 (예: $(1+2)/2 = 1.5$).
- **중복.** 같은 수가 여럿 들어오면 각각이 독립적인 원소로 취급된다.
- **음수.** 음수도 일반 정수로 취급하며, 중앙값 계산에 포함된다.

#### 예시

```ts
const mf = new MedianFinder();

mf.addNum(1);
mf.findMedian();   // 1    — 원소 [1], 홀수 개이므로 유일한 값

mf.addNum(2);
mf.findMedian();   // 1.5  — 원소 [1,2], 짝수 개이므로 (1+2)/2

mf.addNum(3);
mf.findMedian();   // 2    — 원소 [1,2,3], 홀수 개이므로 가운데 값

mf.addNum(4);
mf.findMedian();   // 2.5  — 원소 [1,2,3,4], 짝수 개이므로 (2+3)/2

// 음수 포함(경계: 값이 음수)
const mf2 = new MedianFinder();
mf2.addNum(-1_000_000_000);
mf2.addNum(1_000_000_000);
mf2.findMedian();  // 0    — 짝수 개이므로 (-1e9+1e9)/2 = 0

// 중복(경계: 모든 값 동일)
const mf3 = new MedianFinder();
mf3.addNum(5);
mf3.addNum(5);
mf3.addNum(5);
mf3.findMedian();  // 5    — 정렬 결과 [5,5,5], 홀수 개이므로 가운데 값
```
