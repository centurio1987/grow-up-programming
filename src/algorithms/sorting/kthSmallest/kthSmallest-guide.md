# k 번째로 작은 값 — 자리 하나가 정해지면 남은 절반은 볼 이유가 없다

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 값을 하나씩 뽑는 방법에서
구간을 한쪽만 남기는 분할까지 가는 경로를 따라갑니다. 마지막에는 실제로 동작하는 코드를 한
조각씩 만듭니다.

### 전체 컨셉

배열에서 값 하나를 **기준값**으로 고르고, 그보다 작은 값을 전부 왼쪽으로 옮긴 다음 기준값을
그 경계에 놓아 봅시다. 그러면 기준값의 왼쪽에 있는 칸 수가 곧 **그 값이 정렬된 줄에서 앉을
자리 번호**입니다. 줄 전체를 세우지 않고도 값 하나의 자리는 한 번의 순회로 정해져요.

```text
[7 10 4 3 20 15] 에서 기준값을 4 로 잡고 한 번 순회하면

  4 보다 작은 값   3            한 개
  4 보다 큰 값     7 10 20 15   네 개

  결과  [3 4 15 7 20 10]
         │ │
         │ └ 4 의 자리가 인덱스 1 로 확정됐다
         └ 이 한 칸만 4 보다 작다
           오른쪽 네 칸은 4 보다 크다는 것 말고 순서가 정해지지 않았다
```

우리가 찾는 것은 **`k` 번째로 작은 값**이고, `k` 는 1 부터 세므로 0 부터 세는 자리로는
`k − 1` 번입니다. 그러니 방금 확정된 자리 번호와 이 목표 자리 번호를 견주기만 하면 다음에
어디를 봐야 할지 정해집니다. 세 갈래뿐이에요.

```text
확정된 자리 p 와 목표 자리 target = k − 1 을 견준다

  p = target   →  기준값이 곧 답이다. 더 볼 것이 없다
  p > target   →  답은 기준값보다 작은 쪽에 있다. 오른쪽 덩어리는 버린다
  p < target   →  답은 기준값보다 큰 쪽에 있다.  왼쪽 덩어리는 버린다
```

**버린 쪽을 다시 안 본다는 것이 정렬과 갈리는 자리입니다.** 정렬은 갈라진 두 덩어리를 둘 다
이어서 처리하는데, 여기서는 답이 든 한쪽만 남깁니다. 층마다 구간이 절반이 된다고 하면 정렬은
층마다 합이 `n` 이라 층 수만큼 곱해지고, 이쪽은 층마다 절반씩 줄어드는 등비수열이라 합이 `2n`
근처에서 멈춰요.

```text
양쪽을 다 처리한다 (정렬)          한쪽만 남긴다 (이 글)
  n + 2·(n/2) + 4·(n/4) + …          n + n/2 + n/4 + n/8 + …
  = 층마다 n 이 log₂ n 개             = 2n 에 수렴한다
```

다만 절반씩 갈리는 것은 **보장이 아닙니다.** 고른 값이 그 구간의 최솟값이면 왼쪽이 비고
구간이 한 칸만 줄어드니, 그때는 순회가 `n` 번 되풀이됩니다. 그래서 견주기 횟수는 평균
`O(n)` 이고 최악은 `O(n²)` 이며, 어느 쪽이 되는지는 **값을 어디서 고르느냐**가 정합니다.

```text
좋은 갈림   구간 100,000 → 50,000 → 25,000 → …        합이 20 만 근처
나쁜 갈림   구간 100,000 → 99,999 → 99,998 → …        합이 50 억 근처
```

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **정렬된 줄에서 「`k` 번째」가 무엇인지.** 오름차순으로 세웠을 때 앞에서 `k` 칸째이고,
  같은 값이 여럿이면 그 값들이 개수만큼 연속된 칸을 차지합니다. `k = 1` 이 최솟값이에요.
- **배열의 자리 바꾸기가 `O(1)`** 이라는 것. `A[i]` 와 `A[j]` 를 맞바꾸는 데 배열 길이는
  상관없습니다.
- **분할(partition)이 무엇인지.** 기준값 하나로 배열을 「작은 쪽 · 기준값 · 큰 쪽」으로
  재배열하는 한 번의 순회예요. 흐릿하면 [`quicksort` 가이드](../quicksort/quicksort-guide.md)의
  「수행으로 알아보는 알고리즘」 절이 같은 순회를 단계마다 값으로 보여 줍니다.
- **구간을 좁혀 가는 반복문의 꼴.** `lo` 와 `hi` 두 변수로 남은 범위를 들고, 한 바퀴마다 한쪽
  끝을 옮기는 모양입니다. [`binarySearch` 가이드](../../binary-search/binarySearch/binarySearch-guide.md)가
  같은 뼈대를 씁니다.

세 번째가 흐릿하면 여기서부터 어긋납니다. 분할이 「정렬을 조금 한 것」이라고 알고 있으면, 한
번의 순회가 **값 하나의 자리를 완전히 확정한다**는 것이 무엇을 보장하는지 확인할 수 없어요.

```text
이 글이 다루는 것          한 번 주어진 배열에서 k 번째 값을 한 번 고른다
이 글이 다루지 않는 것     수가 하나씩 들어오는 동안 계속 답한다   → medianFromDataStream
                          등장 횟수 상위 k 개를 모두 낸다        → topKFrequent
                          줄 전체의 순서가 필요하다              → quicksort · sortArray
```

- 스트림에서 중앙값을 계속 답하는 문제는
  [`medianFromDataStream`](../medianFromDataStream/medianFromDataStream-problem.md) 이,
  상위 `k` 개를 **모두** 내는 문제는
  [`topKFrequent`](../topKFrequent/topKFrequent-problem.md) 이 다룹니다.

### 아이디어 상세 — 한쪽만 남기는 분할을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function kthSmallest(A: number[], k: number): number;
```

- 입력: 정수 배열 `A` 와 순번 `k`. `A` 를 **제자리에서 고쳐도 됩니다** — 호출이 끝난 뒤 원소
  순서는 보장하지 않습니다.
- 출력: `A` 를 오름차순으로 세웠을 때 앞에서 `k` 번째에 오는 **값 하나**. 인덱스가 아닙니다.
- 제약: 칸 수 `1 ≤ n ≤ 100,000`, 값 `−10⁹ ≤ A[i] ≤ 10⁹` 인 정수, 순번 `1 ≤ k ≤ n`,
  시간 1 초, 메모리 256 MB. 값은 음수일 수 있고 같은 값이 여럿일 수 있습니다.

이 글이 쓰는 기호는 여덟이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 배열 `A` 의 칸 수 | `1 ≤ n ≤ 100,000` |
| `k` | 1 부터 세는 순번 | `1 ≤ k ≤ n` |
| `target` | `k − 1`. 0 부터 세는 **목표 자리** | `0 ≤ target ≤ n−1` |
| `lo` · `hi` | 아직 남아 있는 구간의 왼쪽 끝 · 오른쪽 끝. 폐구간입니다 | `0 ≤ lo ≤ hi < n` |
| `pivot` | 지금 구간에서 고른 **기준값**. 산문에서는 「기준값」으로 부르고 코드에서는 `pivot` 으로 씁니다 | 바퀴마다 새로 고른다 |
| `i` | 기준값보다 작은 값이 놓일 다음 자리 | `lo ≤ i ≤ hi` |
| `j` | 분할 루프가 지금 읽는 자리 | `lo` 부터 `hi−1` 까지 |
| `p` | 분할이 끝난 뒤 기준값이 자리 잡은 인덱스 | `lo ≤ p ≤ hi` |

**아무 기법 없이 푸는 법부터 세웁시다.** 남은 값 중 가장 작은 것을 찾아 빼내는 일을 `k` 번
되풀이하면 됩니다. 한 번 찾는 데 남은 칸을 전부 읽어야 하니 견주기가 이렇게 쌓여요.

```text
1 회차   n 칸을 읽어 최솟값 하나
2 회차   n 칸을 읽어 그다음 값 하나
  …
k 회차   n 칸을 읽어 k 번째 값

견주기 ≈ k × n
```

| 칸 수 `n` | 순번 `k` | 견주기 | 초당 1 억 번 기준 |
| --- | --- | --- | --- |
| 1,000 | 500 | 500,000 | 0.005 초 |
| 100,000 | 1 | 100,000 | 0.001 초 |
| **100,000** | **50,000** | **5,000,000,000** | **50 초** |

`k` 가 가운데일 때 50 억 번입니다. 1 초 제한을 50 배 넘겨요. `k` 가 작으면 통과하지만 문제는
`k` 를 고르지 못하게 하므로, 가운데가 들어오는 것을 막을 수 없습니다. **그러면 정렬이라는 기법을
쓰면 어떻게 되는지부터 확인합시다.** `A` 를 정렬하고 `A[k-1]` 을
읽으면 됩니다. 비교 정렬이 줄 전체의 순서를 알아내려면 `log₂(n!)` 번 이상 견주어야 하는데,
`n = 100,000` 에서 그 값은 1 초 안에 들어와요. 그러니 정렬은 **틀린 방법이 아니라 낭비하는
방법**입니다 — 우리가 묻는 것은 자리 하나뿐인데, 자리 하나를 정하는 데 필요한 견주기의 하한은
「모든 칸을 최소 한 번은 읽는다」인 `n − 1` 이거든요.

<!--proof:lower-bounds-->

```text
n = 100,000 에서 알아내는 것   견주기 하한
줄 전체의 순서   log₂(n!)        1,516,704
자리 하나        n − 1              99,999
                                   15.2 배
```

15 배가 낭비의 크기입니다. 그러면 그 낭비를 걷어낼 수 있을까요 — 자리 하나만 확정하는 순회가
따로 있는지부터 봅시다. 작은 입력 `[7 10 4 3 20 15]` 을 잡고, 값 하나를 고른 뒤 **그보다 작은
값이 몇 개인지만** 세어 봅니다.

```text
[7 10 4 3 20 15]   정렬하면 [3 4 7 10 15 20]

  고른 값 7   →  작은 값 3 4      두 개  →  7 의 자리는 2   ✓ 정렬 결과의 인덱스 2 가 7
  고른 값 4   →  작은 값 3        한 개  →  4 의 자리는 1   ✓
  고른 값 15  →  작은 값 3 4 7 10 네 개  →  15 의 자리는 4  ✓
```

**세 번 다 맞았습니다.** 값 하나의 자리는 「그보다 작은 값의 개수」와 같고, 그 개수는 배열을 한
번 읽으면 나옵니다. 게다가 읽으면서 작은 값을 앞쪽으로 맞바꿔 두면 개수를 세는 김에 **두 덩어리
로 갈라 놓는 일까지** 끝나요. 여기까지가 준비입니다. 이제 비용은 「몇 번 순회하고 그때마다
구간이 몇 칸이었는가」의 합이 됐어요.

```text
견주기 = Σ (그 순회가 받은 구간의 크기 − 1)
          └ 이 식에 배열의 값이 없다. 남은 변수는 "구간이 어떻게 줄어드는가" 하나다
```

**그러면 무엇이 구간을 줄이는지 재 봅시다.** 같은 배열에 같은 분할 규칙을 걸고, 갈라진 두 덩어리를
**둘 다** 이어서 처리할 때와 **한쪽만** 남길 때의 견주기를 나란히 셉니다. 입력은 생성식
`A[i] = (i × 7919) mod 10,007` 로 만들고 순번은 `k = n/2` 로 뒀어요.

<!--proof:split-vs-sort-->

```text
칸 수 n   양쪽 재귀   한쪽 재귀     차이
16               45          23   2.0 배
64              347         126   2.8 배
256           2,015         449   4.5 배
1,024        11,091       2,979   3.7 배
```

칸이 늘수록 차이가 벌어집니다. **갈리는 것은 분할 규칙이 아니라 「목표가 없는 쪽을 보는가」
하나예요** — 두 열의 코드는 기준값을 고르는 줄까지 같고, 이어서 처리하는 구간이 하나인가
둘인가만 다릅니다. 전개에 쓸 여섯 칸짜리 입력에서는 이 차이가 11 대 11 로 안 나타나요.
그 입력에서는 한쪽만 남기는 쪽이 네 번 갈라지는 동안 **버린 쪽이 매번 한 칸 이하**라, 양쪽을
다 처리해도 더 할 견주기가 0 번이기 때문입니다.

**이제 「어느 쪽을 남길지」를 정하는 기준을 세웁니다.** 가장 단순한 후보를 먼저 시험해 보죠 —
「구간을 칸 수로 반 잘라 목표 자리가 든 쪽만 본다」입니다. 값이 아니라 자리 번호만 보는 것이라
읽을 것도 없어요.

```text
[7 10 4 3 20 15]  target = 3 (k = 4, 답은 10)

  칸 수로 반 자르면   왼쪽 [0,2] = 값 7 10 4      오른쪽 [3,5] = 값 3 20 15
  target = 3 이 오른쪽에 드니 오른쪽만 본다
       └ 그런데 오른쪽 세 칸에 10 이 없다. 답을 버렸다
```

**자리 번호로 자르려면 배열이 이미 정렬돼 있어야 합니다.** 정렬돼 있지 않으면 자리 `3` 에
`k = 4` 번째 값이 있다는 보장이 없어요. 그래서 자르기 **전에** 자리 하나를 실제로 확정해야
하고, 방금 확인한 분할이 그 일을 합니다. 기준은 이렇게 적혀요.

```text
분할이 끝나 기준값이 자리 p 에 놓였다.  target = k − 1 과 견준다

  p = target   답이다.        반환한다
  p > target   답은 더 앞이다. 다음 구간은 [lo, p−1]
  p < target   답은 더 뒤다.   다음 구간은 [p+1, hi]
       └ 세 갈래가 서로 겹치지 않고 p 의 모든 값을 덮는다
```

이 기준을 전개에 쓸 입력에 걸음마다 적용해 봅시다. 구간이 어떻게 줄어드는지가 그대로 나옵니다.

```text
[7 10 4 3 20 15]  k = 4  target = 3

  구간 [0,5] 여섯 칸   기준값 4    p = 1   1 < 3  → 오른쪽 [2,5]
  구간 [2,5] 네 칸     기준값 7    p = 2   2 < 3  → 오른쪽 [3,5]
  구간 [3,5] 세 칸     기준값 20   p = 5   5 > 3  → 왼쪽  [3,4]
  구간 [3,4] 두 칸     기준값 10   p = 3   3 = 3  → 반환 10
       └ 견주기 5 + 3 + 2 + 1 = 11 번
```

**기준이 각 변수의 이동 범위를 정합니다.** 위에서 실제로 순회한 자취가 그대로 범위예요.

```text
j       한 순회에서 lo 부터 hi−1 까지 한 방향으로만 간다  → 순회당 정확히 (hi − lo) 칸
i       lo 에서 시작해 작은 값을 만날 때만 한 칸씩 는다   → 순회당 0 부터 (hi − lo) 칸
lo·hi   한쪽 끝만 옮기고 되돌아오지 않는다                 → 구간 크기가 매번 최소 1 줄어든다
target  한 번 정하고 끝까지 안 바꾼다                      → 늘 0 부터 n−1 사이의 절대 번호
```

**목표 자리가 그대로여도 되는 것을 값으로 확인해 봅시다.** 쉬운 경우는 오른쪽을 버릴 때예요 —
왼쪽 칸들의 번호가 하나도 안 바뀌니 `target` 을 손댈 이유가 없습니다. 불안한 경우는 **왼쪽을
버릴 때**입니다. 앞쪽 칸이 통째로 사라지는데 절대 번호를 그대로 써도 되는지 확인해야 해요.

```text
구간 [0,5] 에서 p = 1 로 확정하고 오른쪽 [2,5] 만 남길 때

  버린 칸    인덱스 0 과 1   값 3 4       ← 정렬된 줄의 자리 0 과 1 을 이미 차지했다
  남은 칸    인덱스 2 3 4 5  값 15 7 20 10
  target = 3 은 여전히 인덱스 3 을 가리킨다
       └ 버린 칸이 target 보다 앞자리뿐이라 남은 칸의 번호가 밀리지 않는다
```

`p < target` 로 갈라진 상황에서 버려지는 칸은 인덱스 `lo` 부터 `p` 까지이고, 그 번호는 전부
`target` 보다 작습니다. 자리 번호는 배열 전체를 기준으로 매겨져 있으니 앞쪽을 안 보기로 했다고
뒤쪽 번호가 바뀌지 않아요. 왜 맞는지를 루프의 종료 조건으로 말하면, `j` 가 `hi` 에 이를 때까지
`lo … hi−1` 의 모든 칸을 정확히 한 번씩 읽으므로 **어느 칸도 분류되지 않은 채 남지 않고**,
구간이 매번 최소 한 칸(기준값 자신)씩 줄어드니 `lo = hi` 에 이릅니다.

```text
한 바퀴가 끝나면 구간이 셋으로 나뉜다
  확정된 자리 하나    다시 안 본다
  버린 구역           다시 안 본다
  남긴 구역           다음 바퀴가 받는다
       └ 셋의 칸 수를 더하면 이 바퀴가 받았던 구간의 크기다
```

**마지막으로 기준값을 어느 자리에서 고를지가 남았습니다.** 자리를 셋으로 두고 입력 넷에 걸어
견주기를 셉니다. `k` 는 어느 것이 들어올지 모르니 `k = 1` 부터 `8` 까지 전부 더했어요.

<!--proof:pivot-places-->

```text
입력 (n = 8)                  첫 칸   중앙   끝 칸
정렬된 [0 1 2 3 4 5 6 7]        168     76     168
역순 [7 6 5 4 3 2 1 0]          168     82     168
뒤섞인 [5 2 8 1 9 3 7 4]         82    138      84
전부 같음 [2 2 2 2 2 2 2 2]     168    168     168
```

**어느 자리도 네 입력 전부에서 가장 적지는 않습니다.** 중앙은 정렬된 입력과 역순 입력에서
168 을 76 과 82 로 내리는데, 뒤섞인 입력에서는 138 로 첫 칸의 82 보다 많아요. 그래도 이 글은
**중앙 하나**를 고릅니다 — 한 줄로 끝나고, 실무에서 흔히 들어오는 「이미 정렬된 배열」이라는
모양을 막기 때문이에요. 전부 같은 값은 셋 다 168 이라 자리 선택으로는 못 막습니다.

```text
제자리 분할 한 벌이 나왔다
  구간의 중앙을 기준값으로 고른다
  한 번 순회하며 작은 값을 왼쪽으로 맞바꾸고 기준값을 경계에 놓는다
  확정된 자리 p 와 target 을 견주어 한쪽 구간만 남긴다
       └ 10 만 칸에서 50 억 번이던 견주기가 평균적으로 20 만 번 규모가 된다
```

### 수행으로 알아보는 알고리즘 — 한 번의 순회가 자리 하나를 확정한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const A = [7, 10, 4, 3, 20, 15];
const k = 4;
// 이 절이 끝나면 10 이 나와야 한다 (정렬하면 [3, 4, 7, 10, 15, 20] 의 4 번째)
```

여섯 칸에 `k = 4` 를 왜 골랐을까요? 이 입력은 네 번 갈라지고, 그 사이에 **세 갈래가 전부
실행됩니다** — 오른쪽으로 두 번, 왼쪽으로 한 번, 그리고 마지막에 자리가 일치해요. 분할 루프의
두 갈래도 둘 다 나옵니다.

```text
select(A, k):
    target ← k − 1
    lo ← 0,  hi ← A.length − 1
    lo < hi 인 동안:
        구간 [lo,hi] 의 중앙을 기준값으로 골라 hi 자리로 옮긴다
        i ← lo
        j 를 lo 부터 hi−1 까지:
            A[j] < 기준값 이면 A[i] 와 맞바꾸고 i 를 늘린다    ① 작다
            아니면 그대로 둔다                                  ② 크거나 같다
        기준값을 i 자리에 놓는다.  p ← i
        p = target 이면 A[p] 를 돌려준다                        ③ 자리가 같다
        p > target 이면 hi ← p − 1                              ④ 목표가 앞
        아니면        lo ← p + 1                                ⑤ 목표가 뒤
    A[lo] 를 돌려준다
```

#### 1. 순번을 자리 번호 하나로 옮긴다

`k` 는 1 부터 세고 배열 인덱스는 0 부터 셉니다. 이 변환을 **맨 앞에서 한 번만** 하고, 뒤에서는
자리 번호끼리만 견주게 두면 견주는 자리마다 `−1` 을 다시 챙길 이유가 없어요.

```ts
const target = k - 1;
```

```text
k = 4  →  target = k − 1 = 3
```

| 자리 번호 | 0 | 1 | 2 | **3** | 4 | 5 |
| --- | --- | --- | --- | --- | --- | --- |
| 정렬된 줄의 값 | 3 | 4 | 7 | **10** | 15 | 20 |

`target` 이 가리키는 자리의 값 `10` 이 답입니다.

#### 2. 기준값을 골라 끝으로 옮긴다

분할 루프는 「작은 것」과 「나머지」 두 구역만 관리하면 됩니다. 기준값이 구간 한가운데 있으면 그
자리를 매번 비켜 가야 하므로, **먼저 끝으로 옮겨** 루프가 `hi` 앞까지만 보게 만들어요. 구간의
중앙 인덱스를 `m` 이라 두고 그 칸을 `hi` 와 맞바꿉니다.

```ts
const m = lo + Math.floor((hi - lo) / 2);
[A[m], A[hi]] = [A[hi] as number, A[m] as number];
const pivot = A[hi] as number;
```

실행하면 T1 이 이렇게 나옵니다. 값 `4` 가 끝으로 갔고 원래 그 자리에 있던 `15` 가 안쪽으로
들어왔어요.

```text
[7 10 4 3 20 15]  lo=0 hi=5  →  m = 0 + ⌊5/2⌋ = 2
      ↑      ↑
      인덱스 2 와 인덱스 5 를 맞바꾼다
[7 10 15 3 20 4]  pivot = 4 가 hi=5 에 있다
```

중앙을 고르는 것은 「아이디어 상세」의 표에서 확인한 선택입니다. 첫 칸을 고르면 정렬된 여덟 칸
입력에서 `k` 여덟 벌의 견주기 합이 76 번에서 168 번으로 늘어요.

#### 3. 한 번 순회하며 두 구역을 넓힌다

`i` 는 「기준값보다 작은 값이 놓일 다음 자리」이고 `j` 는 읽는 자리입니다. 둘 사이가 기준값 이상인
값들의 구역이에요.

```ts
let i = lo;
for (let j = lo; j < hi; j++) {
  if ((A[j] as number) < pivot) {
    // ① 작은 쪽으로 보내고 그 구역을 한 칸 넓힌다
    [A[i], A[j]] = [A[j] as number, A[i] as number];
    i++;
  }
  // ② 크거나 같다 — 그대로 둔다. j 만 나아간다
}
[A[i], A[hi]] = [A[hi] as number, A[i] as number];
```

T2 부터 T7 까지가 이 조각입니다. 다섯 번 견주고 나면 `i` 가 1 이 되고, 마지막 맞바꾸기가 기준값
`4` 를 그 자리에 놓아요.

```text
[7 10 15 3 20 4]   i=0
  j=0  7 < 4  거짓 → ②      i 그대로
  j=1  10 < 4 거짓 → ②      i 그대로
  j=2  15 < 4 거짓 → ②      i 그대로
  j=3  3 < 4  참   → ①      [3 10 15 7 20 4]  i 0→1
  j=4  20 < 4 거짓 → ②      i 그대로
루프 끝  A[1] 과 A[5] 를 맞바꾼다 → [3 4 15 7 20 10]   p = 1
```

여기서 가장 중요한 줄은 `i++` 입니다. 이 줄이 작은 구역의 오른쪽 끝을 한 칸 옮겨서, 다음에
만나는 작은 값이 앞서 넣은 값을 덮어쓰지 않게 해요. 그리고 루프가 끝났을 때 `i` 가 곧 **작은 값의
개수**이므로, 그 자리가 기준값의 최종 자리입니다.

#### 멈춤 — 오른쪽으로 갈 때 순번을 다시 세지 않는다

구간이 `[0,5]` 에서 `[2,5]` 로 줄었으니, 앞쪽 두 칸이 빠진 만큼 **목표 순번도 두 칸 당겨야
할 것 같지 않나요?** 재귀로 부분 배열을 넘기는 구현에서는 실제로 그렇게 합니다. 그 감각을 이
코드에 그대로 적용해 보겠습니다.

```ts
// 오해 — 구간을 옮길 때마다 목표를 상대 번호로 다시 센다
lo = p + 1;
target = target - (p + 1); // ← 왼쪽에서 버린 칸 수만큼 당긴다
```

전개 입력에 걸어 보면 첫 갈림에서 이렇게 됩니다.

```text
바른 코드            p = 1 < target = 3  →  구간 [2,5],  target 그대로 3
오해대로 하면        p = 1 < target = 3  →  구간 [2,5],  target 3 − 2 = 1

  구간 [2,5] 를 분할하면 p = 2 이고 배열은 [3 4 7 10 20 15] 다
    바른 코드     2 < 3 이라 오른쪽 [3,5] 로 간다   →  두 번 더 갈라 10 을 돌려준다
    오해대로 하면 2 > 1 이라 hi ← p − 1 = 1 이 되어 lo = 2 를 넘어선다
                  반복문이 그대로 끝나고 A[2] = 7 을 돌려준다
                       └ 답은 10 인데 7 이 나온다
```

**두 셈법을 섞으면 안 된다는 것이 요점입니다.** 구간을 부분 배열로 잘라 넘기면 그 안에서 순번도
0 부터 다시 시작하니 당기는 것이 맞고, 이 코드처럼 **원본 배열 위에서 `lo`·`hi` 만 옮기면**
자리 번호가 원본 기준으로 남아 있으니 당기면 안 됩니다. 이 글은 뒤쪽을 골랐고, 그래서 `target`
은 처음 한 번만 정해집니다.

#### 4. 확정된 자리와 목표 자리를 견주어 한쪽만 남긴다

분할이 끝나면 자리 하나가 확정됩니다. 그 자리와 `target` 의 대소가 다음에 볼 구간을 정해요.
세 갈래는 서로 겹치지 않고 `p` 가 가질 수 있는 값을 빠짐없이 덮습니다.

```ts
if (i === target) return A[i] as number; // ③ 확정된 자리가 곧 목표 자리다
if (i > target) hi = i - 1; //              ④ 목표가 더 앞이다 — 왼쪽만 남긴다
else lo = i + 1; //                         ⑤ 목표가 더 뒤다 — 오른쪽만 남긴다
```

T8 이 이 조각입니다. `p = 1` 이고 `target = 3` 이라 ⑤ 로 갈라지고, 구간이 여섯 칸에서 네 칸이
됩니다.

```text
[3 4 15 7 20 10]   p = 1,  target = 3

  버린다  인덱스 0 1   값 3 4        ← 이 두 칸이 정렬된 줄의 앞 두 자리를 차지한다
  남긴다  인덱스 2..5  값 15 7 20 10
          └ 다음 바퀴가 받는 구간은 네 칸이다. 여섯 칸이 아니다
```

#### 5. 여섯 칸을 네 번 갈라 답 하나를 고른다

앞의 네 조각을 이어 `kthSmallest([7, 10, 4, 3, 20, 15], 4)` 를 끝까지 실행하면 아래 스물세
단계가 나옵니다. 어느 갈래가 언제 실행되는지를 함께 적었어요.

<!--viz:select-->

```text

T8   [3 4 15 7 20 10]   p = 1   ⑤  다음 구간 [2,5]
T14  [3 4 7 10 20 15]   p = 2   ⑤  다음 구간 [3,5]
T19  [3 4 7 10 15 20]   p = 5   ④  다음 구간 [3,4]
```


T15 부터 T18 이 눈여겨볼 자리입니다. 기준값 `20` 이 구간 `[3,5]` 의 최댓값이라 오른쪽 구역이
비었고, 확정된 자리가 `hi` 인 `5` 로 갔어요. 구간이 세 칸에서 두 칸으로 한 칸밖에 안 줄었고,
이 모양이 되풀이되는 것이 이 절차의 최악입니다.

#### 멈춤 — 같은 값이 여럿이어도 답은 안 틀린다

`A[j] < pivot` 은 **작을 때만** 참이므로 기준값과 같은 값들은 전부 오른쪽 구역으로 갑니다.
그러면 `p` 는 「기준값과 같은 값들 중 맨 앞자리」가 되는데, 이게 진짜 순위가 맞을까요? 같은 값이
셋 있는 입력으로 확인해 봅시다.

```text
[2 1 2 1 3 1]  k = 4  → 정렬하면 [1 1 1 2 2 3] 이라 답은 2

  구간 [0,5]  중앙은 인덱스 2, 값 2 를 끝으로 → [2 1 1 1 3 2]
    1 < 2 가 세 번 참 → i 가 0→3,  p = 3
    같은 값 2 가 하나 오른쪽에 남았는데도 p = 3
  target = 3 이라 p = target → A[3] = 2 를 돌려준다   ✓ 답이 맞다
```

**답은 실제로 맞게 나옵니다.** 그래서 이 자리가 함정이에요 — 테스트가 통과하니 문제가 있는 줄
모르고 넘어갑니다. `p` 가 「기준값보다 **작은** 값의 개수」라는 뜻은 그대로이고, 같은 값이 여럿일
때 그 값이 차지하는 자리는 여러 칸이므로 그중 맨 앞자리에 놓는 것이 정렬 결과와 어긋나지 않아요.

문제는 답이 아니라 **비용**입니다. 값이 전부 같으면 `A[j] < pivot` 이 한 번도 참이 아니라 `i` 가
`lo` 에 머무르고, 기준값이 구간 맨 앞으로 가서 오른쪽이 `n−1` 칸이 됩니다.

```text
[2 2 2 2 2 2 2 2]  k = 8 을 물으면
  ① 이 한 번도 실행되지 않는다  → p = lo
  target = 7 이라 매번 ⑤ 로 갈라지고 구간이 한 칸씩만 준다
  견주기 7 + 6 + 5 + … + 1 = 28 = 8·7/2
       └ 답 2 는 맞다. 견주기만 상한과 같아졌다
```

`<` 를 `≤` 로 바꾸면 같은 값이 전부 왼쪽으로 가서 이번에는 `k = 1` 을 물을 때 같은 일이
생깁니다. 두 갈래 분할로는 이 입력이 최악으로 남고, 실제 해법은 구간을 셋(작음·같음·큼)으로
가르는 것이에요.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 **구간에 칸이 하나 남았을 때
그대로 돌려주는 마지막 줄**뿐이에요 — 칸이 하나면 그 칸이 곧 목표 자리입니다.

```ts
export function kthSmallest(A: number[], k: number): number {
  // 1부터 세는 순번 k 를 0부터 세는 자리 target 으로 한 번만 옮긴다.
  const target = k - 1;

  let lo = 0;
  let hi = A.length - 1;

  while (lo < hi) {
    // 중앙을 기준값으로 골라 끝으로 옮긴다. 그래야 분할 루프가 끝 한 칸만 비켜 두면 된다.
    const m = lo + Math.floor((hi - lo) / 2);
    [A[m], A[hi]] = [A[hi] as number, A[m] as number];
    const pivot = A[hi] as number;

    // i 는 "기준값보다 작은 값이 놓일 다음 자리". j 는 읽는 자리.
    let i = lo;
    for (let j = lo; j < hi; j++) {
      if ((A[j] as number) < pivot) {
        // ① 기준값보다 작다 — 작은 쪽 구역으로 보내고 그 구역을 한 칸 넓힌다.
        [A[i], A[j]] = [A[j] as number, A[i] as number];
        i++;
      }
      // ② 기준값보다 크거나 같다 — 그대로 둔다. j 만 나아간다.
    }

    // 기준값을 두 구역 사이(i)에 놓는다. 이 자리가 기준값의 최종 위치다.
    [A[i], A[hi]] = [A[hi] as number, A[i] as number];

    // ③ 확정된 자리가 곧 목표 자리다.
    if (i === target) return A[i] as number;
    // ④ 목표가 더 앞이다 — 왼쪽만 남긴다.
    if (i > target) hi = i - 1;
    // ⑤ 목표가 더 뒤다 — 오른쪽만 남긴다.
    else lo = i + 1;
  }

  // 구간에 칸이 하나 남았다 — 그 칸이 목표 자리다.
  return A[lo] as number;
}
```

```text
kthSmallest([7, 10, 4, 3, 20, 15], 4)   →  10
kthSmallest([42], 1)                    →  42
kthSmallest([5, 5, 5, 5], 3)            →  5
kthSmallest([-5, 0, 5, -10, 10], 1)     →  -10
```

### 알아 두면 좋은 개념 — 감소 정복

파트 1 이 값으로 보인 것이 하나 있습니다. 구간이 `6 → 4 → 3 → 2` 로 줄었고, 줄어들 때마다
**버린 쪽은 다시 안 봤어요.** 이렇게 한 걸음마다 문제를 작은 조각들로 가른 뒤 **그중 하나만
이어서 푸는** 틀을 **감소 정복**(decrease and conquer)이라고 합니다.

| 절차 | 한 걸음이 하는 일 | 이어서 보는 것 | 걸음당 비용 |
| --- | --- | --- | --- |
| 이 글의 선택 | 기준값 하나의 자리를 확정한다 | 목표가 든 한쪽 구간 | 구간 크기 |
| 이분 탐색 | 가운데 칸과 찾는 값을 견준다 | 절반 하나 | 1 |
| 유클리드 호제법 | `a mod b` 를 구한다 | 짝 `(b, a mod b)` 하나 | 나눗셈 1 |
| 퀵 정렬 | 기준값 하나의 자리를 확정한다 | **양쪽 다** | 구간 크기 |

마지막 줄이 갈림입니다. 퀵 정렬은 갈라 놓은 조각을 **전부** 이어서 풀기 때문에 분할 정복이고,
같은 분할을 쓰면서 한 조각만 남기면 감소 정복이 돼요. 그 차이가 비용의 층을 이렇게 바꿉니다.

```text
여덟 칸을 가장 고르게 갈랐을 때

  층   분할 정복 (전부 이어서 푼다)   감소 정복 (하나만 이어서 푼다)
   0   구간 8        견주기 7        구간 8   견주기 7
   1   구간 3 과 4   견주기 2 + 3    구간 4   견주기 3
   2   구간 2 하나   견주기 1        구간 2   견주기 1
       합 13                         합 11

  같은 차이를 n = 1,024 에서 실제로 세면 11,091 대 2,979 다
```

같은 이름을 다시 만나는 자리가 몇 있어요. 이분 탐색은 걸음당 비용이 1 이라 총합이 `log₂ n` 이
되고, 유클리드 호제법은 줄어드는 비율이 고정이 아니라 라메 상한으로 걸음 수를 묶습니다. 「한
걸음이 얼마나 줄이는가」와 「걸음당 얼마가 드는가」 둘을 따로 보는 습관이 감소 정복을 만났을 때
쓰는 도구입니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 견주기의 점화식이 어떻게 풀리는지,
무엇이 매 순간 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **순위 하나만 필요합니다.** 줄 전체의 순서가 필요하면 정렬이 답이에요. 15 배의 낭비를 아끼는
  것이 이 절차가 사는 자리인데, 그 순서를 어차피 쓸 것이라면 아낀 것이 없습니다.
- **질의가 한 번이거나 배열이 매번 바뀝니다.** 같은 배열에 순위를 여러 번 물으면 한 번 정렬해
  두고 인덱싱하는 쪽이 금방 앞섭니다.
- **추가 메모리를 쓰기 어렵습니다.** 이 절차는 맞바꾸기만 하고 새 배열을 잡지 않아요.
- **평균이 중요하고 드문 최악을 감당할 수 있습니다.** 응답 시간에 상한을 약속해야 하는
  자리라면 이 절차가 아닙니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  순위 하나만        → 이어서 볼 구간을 하나만 남긴다
  질의가 한 번        → 입력을 제자리에서 헝클어도 된다
  추가 메모리 없음    → 맞바꾸기만 하고 새 배열을 잡지 않는다
  평균이 중요         → 최악 n²/2 를 코드가 막지 않는다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "k 번째로 작은/큰 값"   "중앙값을 구하라"   "상위 k 번째 점수"
  "정렬하지 말고"         "입력을 고쳐도 된다"

제약에 이런 모양이 보이면
  배열이 수만~수십만이고 답이 값 하나다
  k 가 입력으로 주어지고 1 부터 n 까지 아무 값이나 될 수 있다
  질의가 한 번뿐이다   ← 여러 번이면 정렬해 두는 쪽으로 기운다
```

반대로 **「최악에도 몇 밀리초 안에」** 같은 문구가 있으면 이 단서는 해당하지 않습니다. 그때는
최악까지 선형을 보장하는 절차를 골라야 해요.

#### 실제로 쓰이는 곳

- **러스트 표준 라이브러리의 `slice::select_nth_unstable`** — 모듈 머리 주석이 절차와 대비책을
  함께 적어 뒀습니다. *"It uses an introselect algorithm based on ipnsort … The fallback
  algorithm used for introselect is Median of Medians using Tukey's Ninther for pivot
  selection. Using this as a fallback ensures O(n) worst case running time with better
  performance than one would get using heapsort as fallback."* 평소에는 이 글과 같은 분할을
  쓰고, 갈림이 치우치면 중앙값의 중앙값으로 갈아탑니다.
  ([`library/core/src/slice/sort/select.rs`](https://github.com/rust-lang/rust/blob/master/library/core/src/slice/sort/select.rs),
  조회 2026-09-03)
- **넘파이의 `np.partition`** — 소스 머리 주석이 최악을 만드는 입력을 **식으로** 적어 뒀어요.
  *"Quick select with median of 3 pivot is usually the fastest, but the worst case scenario
  can be quadratic complexity, e.g. np.roll(np.arange(x), x / 2). To avoid this if it recurses
  too much it falls back to the worst case linear median of median of group 5 pivot strategy."*
  기준값을 세 값의 중앙으로 고르는 구현을 겨냥한 입력이라 이 글의 규칙과는 어긋나는데, 그
  차이는 「최악을 만드는 입력」에서 값으로 확인합니다.
  ([`numpy/_core/src/npysort/selection.hpp`](https://github.com/numpy/numpy/blob/main/numpy/_core/src/npysort/selection.hpp),
  조회 2026-09-03)
- **C++ 표준 라이브러리의 `std::nth_element`** — libstdc++ 는 `__introselect` 로 넘기면서
  깊이 한도를 `std::__lg(__last - __first) * 2` 로 함께 넘기고, `__depth_limit == 0` 이 되면
  `std::__heap_select` 로 갈아탑니다. 갈아타는 조건이 **재귀 깊이 하나**로 코드에 박혀 있는
  자리예요.
  ([`libstdc++-v3/include/bits/stl_algo.h`](https://github.com/gcc-mirror/gcc/blob/master/libstdc%2B%2B-v3/include/bits/stl_algo.h),
  조회 2026-09-03)

```text
세 자리가 똑같이 하는 일
  평소       이 글과 같은 분할로 한쪽만 남긴다
  치우치면   다른 절차로 갈아탄다
             러스트·넘파이 → 중앙값의 중앙값     C++ → 힙 선택
```

#### 경쟁 설계와의 대조

같은 목표를 노리는 **다른 절차**가 있어요 — **중앙값의 중앙값**(median of medians)입니다.
다섯 칸씩 묶어 각 묶음의 중앙값을 모으고, 그 모임의 중앙값을 같은 절차로 다시 골라 기준값으로
씁니다. 그렇게 고른 기준값은 양쪽에 최소 30 % 씩을 남기므로 **최악에도 선형**이에요. 이 글의
절차에는 없는 약속입니다.

`n = 1,024` 를 고정하고 입력 두 벌에 둘을 걸어 **견주기 횟수와 새로 잡는 칸 수**를 셌습니다.
한 벌은 생성식 `A[i] = (i × 7919) mod 10,007` 로 만든 뒤섞인 배열에 `k = 512` 를 물은 것이고,
다른 한 벌은 **이 글의 기준값 규칙을 겨냥해 역산한 배열**에 `k = 1,024` 를 물은 것입니다.
전개에 쓰는 여섯 칸짜리 입력을 그대로 쓰지 않은 이유는 하나예요 — 그 크기에서는 역산한 입력을
넣어도 견주기가 15 대 26 으로 이쪽이 적어 **이 대조가 재려는 뒤집힘 자체가 안 일어납니다.**
뒤집히는 첫 칸 수를 재 보면 12 이고, 그래서 대조는 그보다 훨씬 큰 규모를 씁니다.

| 설계 | 뒤섞인 입력 견주기 | 최악 입력 견주기 | 뒤섞인 입력 새 칸 | 최악 입력 새 칸 |
| --- | --- | --- | --- | --- |
| 이 가이드의 절차 | **2,979** | 523,776 | **0** | **0** |
| 중앙값의 중앙값 | 4,649 | **8,445** | 317 | 624 |

**입력 모양 하나로 순서가 뒤집힙니다.** 뒤섞인 입력에서는 이쪽이 2,979 대 4,649 로 1.56 배
적은데, 역산한 입력에서는 523,776 대 8,445 로 **62 배 많아져요.** 뒤집히는 자리를 칸 수로도
잴 수 있습니다 — 역산한 입력에서 `n` 을 키우면 `n = 11` 까지는 이쪽이 55 대 60 으로 적고
`n = 12` 부터 66 대 52 로 저쪽이 적습니다.

```text
축을 넷으로 갈라 적으면
                      이 가이드         중앙값의 중앙값
  뒤섞인 입력 견주기   2,979             4,649        ← 이쪽이 적다
  최악 입력 견주기     523,776           8,445        ← 저쪽이 적다
  새로 잡는 칸         0                 317 · 624    ← 이쪽이 적다
  최악 보장            없다              선형         ← 저쪽에 있다
```

**우열이 반대가 되는 조건이 분명합니다.** 입력을 만드는 쪽이 절차를 알고 있거나(경쟁 제출 ·
외부에서 들어오는 요청) 최악 응답 시간에 상한이 필요하면 중앙값의 중앙값이 답이에요. 입력이
그런 식으로 만들어질 일이 없고 평균만 요구하면 이 글의 절차입니다. 뒤섞인 입력에서 이쪽이
내주는 것은 최악 보장 하나이고, 받는 것이 견주기 1,670 번과 317 칸입니다.

### 수식 정의와 유도

파트 1 에서는 전개 입력 여섯 칸에서 견주기를 11 번으로 셌습니다. 그런데 그건 입력 하나에서 나온
값이에요. 임의의 `n` 에서 구간의 줄어드는 모양이 비용을 어떻게 정하는지는 식으로 확인해야
합니다.

```text
정의   한 번의 분할이 남기는 구간의 크기로 점화식을 적는다
  ↓
검산   그 점화식을 전개 입력 n = 6 에 넣어 손으로 계산한다
  ↓
유도   두 극단의 줄어듦에 대해 닫힌 형태를 푼다
  ↓
계수   그 식에 제약 규모를 넣어 수치를 낸다
```

**먼저 점화식입니다.** 크기 `n` 인 구간 하나를 처리하는 견주기 횟수를 $C(n)$ 이라 하고, 분할이
끝난 뒤 목표가 속한 쪽의 크기를 $s$ 라 둡니다. 분할 자체는 구간을 한 번 순회하므로 $n-1$ 번
견주고, 그다음에는 그 한쪽만 이어서 처리해요.

$$C(n) = (n-1) + C(s), \qquad C(1) = 0, \qquad 0 \le s \le n-1$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $n$ | 그 순회가 받은 구간의 크기 | $1 \le n$ |
| $s$ | 목표가 속한 쪽의 크기 | $0 \le s \le n-1$ |
| $n-1-s$ | 버리는 쪽의 크기. 가운데 한 칸은 기준값이라 양쪽 어디에도 안 들어간다 | $0 \le n-1-s$ |

```text
n 칸을 세 덩어리로 가른다

  |---- s 칸 ----|- 1 칸 -|---- n−1−s 칸 ----|
     목표가 든 쪽   기준값      버리는 쪽
     └ C 로 이어진다  └ 확정    └ 다시 안 본다
```

**정의를 값에 넣어 검산해 봅시다.** 전개 입력은 구간이 `6 → 4 → 3 → 2` 로 줄었으니 $s$ 가
차례로 4 · 3 · 2 · 1 이었어요.

```text
C(6) = 5 + C(4) = 5 + 3 + C(3) = 5 + 3 + 2 + C(2) = 5 + 3 + 2 + 1 + C(1) = 11
       └ 전개에서 센 11 번과 같다

같은 식에 두 극단을 넣으면
  가장 고른 갈림 s = ⌊n/2⌋   C(6) = 5 + C(3) = 5 + 2 + C(1) = 7
  한쪽이 빈다   s = n − 1    C(6) = 5 + 4 + 3 + 2 + 1 = 15
       └ 실제 11 은 그 사이에 있다
```

점화식을 그대로 코드로 옮기면 위 수들이 손 계산 없이 나옵니다. **식의 $s$ 를 코드에서는
`side` 라는 함수로 넘기고, 그 함수가 줄어드는 모양을 정해요.**

```ts
const C = (n: number, side: (n: number) => number): number =>
  n <= 1 ? 0 : n - 1 + C(side(n), side);

C(6, (n) => Math.floor(n / 2)); // 가장 고른 갈림 →  7
C(6, (n) => n - 1); //            한쪽이 빈다     → 15
C(8, (n) => Math.floor(n / 2)); // 가장 고른 갈림 → 11
```

**이제 닫힌 형태를 유도합니다.** 한쪽이 비는 경우부터 풀면 항이 하나씩 줄어드는 단순한 합이에요.

```text
C(n) = C(n-1) + (n-1)
     = C(n-2) + (n-2) + (n-1)          C(n-1) 을 같은 식으로 한 번 더 편다
     = C(n-3) + (n-3) + (n-2) + (n-1)
     …
     = C(1) + 1 + 2 + … + (n-1)        C(1) = 0 이라 여기서 멈춘다
```

$$C(n) = \sum_{j=1}^{n-1} j = \frac{n(n-1)}{2}$$

```text
검산   n = 6  →  6·5/2 = 15    전개 입력에서 한쪽이 비었다면 나올 값
       n = 8  →  8·7/2 = 28    「최악을 만드는 입력」이 실제로 내는 값
```

가장 고른 갈림은 $n = 2^t$ 에서 정확히 풀립니다. 귀납으로 갑시다. 기저는 $t = 0$ 이고
$C(1) = 0 = 2^{1} - 0 - 2$ 예요. $C(2^t) = 2^{t+1} - t - 2$ 를 가정하면 다음 단계가 이렇게
됩니다.

$$C(2^{t+1}) = (2^{t+1} - 1) + C(2^t) = 2^{t+2} - (t+1) - 2 \;\Longrightarrow\; C(2^t) = 2^{t+1} - t - 2$$

```text
 t    n = 2^t   2^(t+1) − t − 2   점화식으로 센 값
 0          1                 0                 0
 1          2                 1                 1
 2          4                 4                 4
 3          8                11                11
10      1,024             2,036             2,036
```

`n` 이 2 의 거듭제곱이 아닐 때는 정확한 값 대신 상한을 얻습니다. $C(n) \le 2n - 2$ 를 같은
방식으로 확인해요 — 기저 $C(1) = 0 = 2 \cdot 1 - 2$ 이고, 가정에서
$C(n) = (n-1) + C(\lfloor n/2 \rfloor) \le (n-1) + 2\lfloor n/2 \rfloor - 2 \le 2n - 3$
이라 상한 안에 들어갑니다.

```text
왜 로그가 사라지는가
  양쪽을 다 이어서 풀면   층마다 구간 크기의 합이 n 이고 층이 log₂ n 개  →  n log₂ n
  한쪽만 이어서 풀면      층마다 크기가 절반이라 n + n/2 + n/4 + …       →  2n 미만
                          └ 등비급수의 합이 유한해서 층 수가 곱해지지 않는다
```

**마지막으로 계수입니다.** 두 닫힌 형태에 제약 규모를 넣어 계산해요.

<!--proof:cost-extremes-->

```text
칸 수 n   가장 고른 갈림   상한 2n − 2   한쪽이 비는 갈림          차이
8                     11            14                 28        2.5 배
16                    26            30                120        4.6 배
1,024              2,036         2,046            523,776      257.3 배
100,000          199,977       199,998      4,999,950,000   25,002.6 배
```

제약 상한 `n = 100,000` 에서 199,977 번과 4,999,950,000 번이 갈리고, 그 차이가 2 만 5 천
배입니다. 아래쪽 값은 파트 1 이 「아무 기법 없이 푸는 법」으로 센 5,000,000,000 번과 5 만 번
차이로 사실상 같은 수예요 — 갈림이 한쪽으로만 치우치면 이 절차는 그 방법으로 되돌아갑니다.

### 불변식 — 매 바퀴가 시작될 때 목표 자리는 남은 구간 안에 있다

파트 1 에서 코드가 동작하는 것을 스물세 단계로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지, 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 문장으로 세우고, 그것이
실제로 유지되는지 확인해 봅시다.

> `while` 이 한 바퀴를 시작할 때마다 `lo ≤ target ≤ hi` 이고, 정렬된 줄의 `target` 번 자리에
> 오는 값은 `A[lo..hi]` 안에 있습니다.

```text
       lo                target                hi
        |-------------------|-------------------|
        └ 이 구간 밖의 칸은 답이 아니다 — 왼쪽 칸은 전부 target 보다 앞자리를,
          오른쪽 칸은 전부 뒷자리를 차지한다. 답은 구간 안에 있다
```

「한 바퀴를 시작할 때마다」가 중요합니다. 루프가 끝난 뒤 한 번만 참인 것이 아니라 **구간을 옮길
때마다** 참이라는 뜻이에요. 그래야 다음 바퀴가 그 성질을 그대로 물려받습니다.

**출발점부터 봅시다.** 첫 바퀴 전에 `lo = 0` 이고 `hi = n−1` 이라 구간이 배열 전체이고,
`target = k − 1` 은 제약 `1 ≤ k ≤ n` 때문에 `0` 과 `n−1` 사이에 있습니다. 그 뒤 한 바퀴마다
갈래 셋 중 하나가 실행돼요.

| 갈래 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| `p = target` | `A[p]` 를 돌려준다 | 분할 뒤 `A[lo..p−1]` 은 전부 `A[p]` 미만이고 그 칸이 `p − lo` 개다. 앞쪽 `lo` 칸은 불변식에 따라 전체에서 가장 작은 `lo` 개를 담고 있으므로 `A[p]` 보다 작은 값이 정확히 `p` 개다 — 그 값이 곧 `target` 번 자리의 값이다 |
| `p > target` | `hi ← p − 1` | 답의 자리 번호가 `p` 보다 작으므로 `A[p]` 와 그 오른쪽은 답이 아니다. 새 구간이 `[lo, p−1]` 이고 `lo ≤ target ≤ p−1` 이 그대로 참이다 |
| `p < target` | `lo ← p + 1` | 답의 자리 번호가 `p` 보다 크므로 `A[p]` 와 그 왼쪽은 답이 아니다. 버린 칸의 번호가 전부 `target` 미만이라 남은 칸의 번호가 밀리지 않는다 |

`while` 을 나오는 길은 하나뿐입니다 — `lo = hi` 예요. 그 시점에도 `lo ≤ target ≤ hi` 가
참이니 `target = lo` 이고, 그래서 `A[lo]` 가 답입니다. 구간이 매 바퀴 최소 한 칸씩 줄어드니
이 시점은 반드시 옵니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 칸 하나 `[42]`, `k=1` | `lo = hi = 0` 이라 `while` 에 안 들어간다 | `42` |
| 칸 둘 `[10 5]`, `k=1` | `m = 0 + ⌊1/2⌋ = 0` 이라 분할 한 번 | `5` |
| `k = 1` | `target = 0` — `p > 0` 인 동안 왼쪽으로만 간다 | 최솟값 |
| `k = n` | `target = n−1` — `p < n−1` 인 동안 오른쪽으로만 간다 | 최댓값 |
| 전부 같음 `[5 5 5 5]` | `A[j] < pivot` 이 한 번도 참이 아니다 | 어떤 `k` 든 `5` |
| 중복 경계 `[1 1 2]`, `k=2` | 같은 값이 오른쪽 구역에 남아도 `p` 는 작은 값의 개수다 | `1` |
| 값 범위 끝 `[10⁹ −10⁹ 0]`, `k=2` | 견주기만 쓰므로 부호·크기와 무관 | `0` |
| 빈 배열 `[]` | 제약 `1 ≤ n` 이 막는다 | 이 절차가 정의하지 않는다 |

마지막 줄이 예외입니다. `A.length` 가 0 이면 `hi = −1` 이라 `while` 에 안 들어가고 `A[0]` 을
읽으므로 값이 없어요. 제약이 그 입력을 막고 있으니 코드가 따로 막지 않는 것이고, 제약이 없는
자리에 이 코드를 옮긴다면 그 검사를 함께 옮겨야 합니다.

**이제 깨뜨려 봅시다.** 불변식을 세우던 줄이 어느 것인지는 바꿔 보면 확인됩니다. 다른 곳은 그대로
두고 **첫 줄의 `k - 1` 을 `k` 로만** 바꿉니다. 그러면 `k = n` 일 때 `target = n` 이 되어 첫
바퀴부터 `target ≤ hi` 가 성립하지 않아요.

```ts
const target = k; // ← k - 1 이어야 하는 자리
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-target-->

```text
입력                    바른 코드   target = k 로 바꾼 코드
[7 10 4 3 20 15]  k=4          10                        15
[3 1 2]  k=1                    1                         2
[-5 0 5 -10 10]  k=1          -10                        -5
```

세 줄 다 **한 칸씩 뒤로 밀린 값**입니다. 예외가 나거나 프로그램이 멈추는 것이 아니라 조용히 다른
값이 나오는 것이 이 자리의 성질이에요.

```text
[3 1 2]  k = 1  을 두 코드로

  두 코드의 첫 분할은 같다. 기준값 1 이 끝으로 가고 [1 2 3] 이 되어 p = 0 이다

  바른 코드      target = 0    p = 0 이 곧 목표 자리라 A[0] = 1 을 돌려준다
  바꾼 코드      target = 1    p = 0 < 1 이라 오른쪽 [1,2] 로 가고
                               거기서 p = 1 이 되어 A[1] = 2 를 돌려준다
                 └ 정렬 [1 2 3] 의 자리 1 은 2 다. k = 2 의 답을 낸 것이다
```

### 비용 계산

#### 비용을 세는 과정

한 바퀴가 하는 견주기는 분할 루프뿐이고, 그 횟수는 `hi − lo` 입니다. 전개의 값으로 확인하면
T2 부터 T6 까지가 구간 여섯 칸에서 **5 번**, T10 부터 T12 까지가 네 칸에서 **3 번**, T16 과
T17 이 세 칸에서 **2 번**, T21 이 두 칸에서 **1 번**이었어요.

```text
구간 [0,5] 크기 6   견주기 5 번    T2 · T3 · T4 · T5 · T6
구간 [2,5] 크기 4   견주기 3 번    T10 · T11 · T12
구간 [3,5] 크기 3   견주기 2 번    T16 · T17
구간 [3,4] 크기 2   견주기 1 번    T21
                    └ 합 11 번. 표에서 센 것과 같다
```

그러니 전체 견주기는 **바퀴마다의 구간 크기에서 1 을 뺀 값을 다 더한 것**입니다. 그 합이 구간의
줄어드는 모양에 따라 어떻게 달라지는지가 「수식 정의와 유도」의 두 극단이에요.

```text
총식 = Σ (그 바퀴의 구간 크기 − 1)     ← 지배항
     + 맞바꾸기                        ← 견주기 이하
     + 기준값 옮기기                   ← 바퀴당 2 회
     + 갈래 판정                       ← 바퀴당 2 회

좋은 갈림   구간이 절반씩 줄면  n + n/2 + n/4 + …      → 2n 미만
나쁜 갈림   구간이 1 씩 줄면    n + (n−1) + (n−2) + …  → n²/2
```

여기서 센 것은 **견주기 횟수만**입니다. 맞바꾸기는 견주기보다 많을 수 없고 기준값 옮기기와 갈래
판정은 바퀴당 상수라, 바퀴 수가 `n` 이하인 이상 지배항이 바뀌지 않아요. 추가로 잡는 메모리는
**0 칸**입니다 — 재귀가 아니라 반복문이라 호출 스택도 안 쌓입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안
돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (첫 분할에서 자리가 맞는다) | `O(n)` | `Θ(n)` — 견주기 정확히 `n−1` 번 |
| **평균적인 경우** (입력 순열이 고르게 분포) | `O(n)` | `Θ(n)` |
| **최악의 경우** (매번 버리는 쪽이 비어 구간이 한 칸씩 준다) | `O(n²)` | `Θ(n²)` — 실제로 도달한다 |

최악에서 `Θ(n²)` 라고 쓸 수 있는 것은 그 값을 **실제로 내는 입력이 있기** 때문입니다. `n = 8`
에서 `[2 6 4 0 1 3 5 7]` 에 `k = 8` 을 물으면 정확히 `28 = 8 · 7 / 2` 번 견줘요.

**총식을 한 번은 정확히 적습니다.** 견주기에 맞바꾸기와 바퀴당 상수가 붙고, 앞뒤로 붙는 전처리는
없습니다.

```text
총식 = Θ(견주기) + O(맞바꾸기) + O(바퀴 수) + Θ(추가 메모리)
       └ 평균 n      └ 견주기 이하   └ n 이하    └ 0 칸

n = 100,000 이면 k = 1 의 평균이 20 만 번, 가운데 k 의 평균이 34 만 번, 최악이 50 억 번이다
```

**두 줄의 보장이 종류가 다릅니다.** 최악은 최악 보장이지만 평균은 기댓값이고, 그 기댓값이
**무엇에 대한 것인지**가 이 구현에서 특별해요. 코드에 난수가 하나도 없고 기준값을 구간의 중앙에서
결정적으로 고르므로, 같은 입력을 두 번 넣으면 견주기 횟수가 언제나 같습니다. 그러니 여기서
말하는 평균은 **입력 순열이 고르게 분포한다는 가정 아래의 평균**이고, 구현이 만드는 무작위성에
대한 기댓값이 아니에요.

```text
난수가 없다는 것이 재는 대상을 바꾼다
  같은 A 를 두 번 넣으면   견주기 횟수가 언제나 같은 수다
  그래서 평균은            "이 코드가 A 하나에 몇 번 견주는가" 를 A 전체에 걸쳐 평균한 값
  그래서 최악은            그 평균과 무관하게, 계산해서 넣을 수 있는 입력 하나가 정한다
```

가정 아래의 값을 실제로 세어 봅시다. `n = 8` 의 모든 순열 40,320 개를 `k = 1` 부터 `8` 까지
전부 실행한 결과입니다.

<!--proof:average-by-k-->

```text
묻는 순번   평균 견주기   가장 적을 때   가장 많을 때   28 을 내는 순열
k = 1             10.56              7             28                 2
k = 2             12.25              7             28                14
k = 3             13.39              7             28                42
k = 4             13.95              7             28                70
k = 5             13.95              7             28                70
k = 6             13.39              7             28                42
k = 7             12.25              7             28                14
k = 8             10.56              7             28                 2
```

**`k` 가 가운데일수록 평균이 큽니다.** 양 끝은 10.56 이고 가운데는 13.95 로, 가장 고른 갈림이
내는 11 번의 1.3 배 안쪽이에요. 「가장 적을 때」가 `k` 와 무관하게 7 인 것은 `n−1 = 7` 이 첫 분할의
견주기이자 하한이기 때문이고, `28` 을 내는 순열이 `k` 가 가운데로 갈수록 2 → 70 으로 느는 것이
최악에 걸릴 확률이 가운데에서 가장 크다는 뜻입니다.

```text
n = 8 의 전수 평균이 말하는 것
  k 가 양 끝     10.56   가장 고른 갈림의 11 번보다도 적다
  k 가 가운데    13.95   11 번의 1.27 배
  가장 많을 때   28      어느 k 에서도 상한과 같은 값을 내는 순열이 있다
```

**규모를 키우면 상수가 자리를 잡습니다.** 고정 씨앗으로 만든 순열 500 벌씩을 세 크기에서
실행해 `n` 의 몇 배인지 셌어요.

<!--proof:average-large-->

```text
칸 수 n    k = 1   k = n/2 + 1    k = n
64        1.87 n        2.87 n   1.88 n
1,024     1.96 n        3.34 n   2.01 n
4,096     2.02 n        3.39 n   1.97 n
```

양 끝을 물으면 `2n` 에, 가운데를 물으면 `3.4n` 에 가까워집니다. `n = 8` 의 전수 평균이 `k` 에
따라 10.56 과 13.95 로 갈렸던 것이 규모를 키우면 이 두 상수로 굳어요. **이 구분이 갈리는
자리는 공격입니다** — 결정적 기준값은 절차를 아는 사람이 최악 입력을 계산해 넣을 수 있고,
그 계산이 다음 절입니다.

#### 최악을 만드는 입력

절차가 어느 자리를 고르는지 알고 있으므로, **그 자리에 놓일 값을 매 단계 그 구간의 최솟값으로**
정해 두면 분할이 매번 한쪽으로 완전히 치우칩니다. 값을 직접 적는 대신 절차를 거꾸로 실행해
순위를 배정하면 임의의 `n` 에서 그런 배열이 나와요.

```ts
export function worstInput(n: number): number[] {
  const pos = Array.from({ length: n }, (_, i) => i);
  const rank = new Array<number>(n).fill(-1);
  for (let round = 0; round < n - 1; round++) {
    const lo = round;
    const hi = n - 1;
    // 이 바퀴의 기준값 자리를 그대로 흉내 내고 (swap 은 두 칸을 맞바꾸는 함수다)
    swap(pos, lo + Math.floor((hi - lo) / 2), hi);
    // 그 값이 구간의 최솟값이었던 것처럼 lo 에 놓는다
    swap(pos, lo, hi);
    rank[pos[lo] as number] = round; // ← 그 칸이 round 번째로 작은 값이 된다
  }
  rank[pos[n - 1] as number] = n - 1;
  return rank;
}
```

구간이 왼쪽부터 한 칸씩 줄어드니 목표는 오른쪽 끝에 두어야 합니다 — `k = n` 이에요. 실제로
실행하면 상한과 정확히 같은 값이 나옵니다.


표의 아래 두 줄이 갈라지는 자리입니다. **최악 입력은 기준값 규칙마다 다릅니다** — 넘파이 주석이
최악의 예로 드는 `np.roll(np.arange(x), x/2)` 는 기준값을 **세 값의 중앙**으로 고르는 구현을
겨냥한 것이라 이 글의 중앙 규칙에는 통하지 않아요. `n = 1,024` 에서 그 입력은 3,057 번이고,
상한 523,776 의 0.6 % 입니다. 반대로 **값이 전부 같은 배열**은 규칙과 무관하게 523,776 번을
내는데 그쪽은 의도하지 않아도 실무에서 흔히 들어옵니다.

러스트와 넘파이가 갈림이 치우치는 것을 감지해 중앙값의 중앙값으로 갈아타는 것이 이 자리를 막는
방법이에요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 값 하나의 자리는 「그보다 작은 값의 개수」와
같아서 한 번의 순회로 확정되고, 그 자리와 목표 자리를 견주면 한쪽 구간을 통째로 버릴 수 있으며,
버리는 덕분에 층마다의 비용이 등비급수가 되어 합이 `2n` 아래로 멈춥니다.

```text
target = k − 1 로 목표 자리를 고정한다
   → 구간의 중앙을 기준값으로 골라 끝으로 옮긴다
   → 한 번 순회하며 작은 값을 왼쪽으로 맞바꾼다
   → 기준값을 경계에 놓아 자리 p 를 확정한다
   → p 와 target 을 견주어 한쪽 구간만 남긴다
       └ 갈림이 고르면 2n 미만, 한쪽이 비면 n²/2
```

먼저 답이 붙는 문제 하나입니다. 전개의 T15 부터 T18 에서 기준값 `20` 이 구간 `[3,5]` 의
최댓값이라 `p = 5` 가 됐어요. 만약 그 구간의 중앙에 `10` 이 있어서 `p = 3` 이 나왔다면, 그 뒤
몇 번을 더 견주고 끝났을까요?

```text
실제로 일어난 일   구간 [3,5] 에서 p = 5 → 왼쪽 [3,4] → 다시 분할 → 끝
가정               구간 [3,5] 에서 p = 3 → ?
```

<!--check:earlyexit-->
`target = 3` 이므로 `p = 3` 이면 그 자리에서 반환입니다. T16·T17 의 견주기 2 번까지만 하고
끝나므로, 실제로 든 11 번 중 T20~T22 에 해당하는 **1 번을 덜 견줍니다** — 총 10 번이에요.

```text
실제   5 + 3 + 2 + 1 = 11 번   (네 번 분할)
가정   5 + 3 + 2     = 10 번   (세 번 분할, 세 번째에서 p = target)
       └ 구간 [3,5] 의 견주기 2 번은 어차피 해야 한다. 줄어드는 것은 마지막 두 칸 분할뿐이다
```

여기서 한 번 잘 고른 것이 준 양은 1 번뿐인데, 남은 구간이 이미 두 칸이었기 때문입니다. 같은
일이 큰 구간에서 일어나면 **그 뒤의 바퀴가 통째로 없어져요.**
