# 퀵 정렬 — 값 하나를 제자리에 놓으면 남은 일이 둘로 갈라진다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 가장 작은 값을
하나씩 골라내는 방법에서 출발해 배열 안에서 값을 둘로 가르는 방법까지 가고, 그 방법을 단계마다 값으로 푼
뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열에서 값 하나를 골라 **그 값보다 작은 값은 전부 왼쪽, 크거나 같은 값은 전부 오른쪽**으로 옮기면, 고른
값은 정렬이 끝난 뒤에 있을 자리에 이미 도착해 있습니다. 왼쪽에 있는 값의 개수가 곧 그 값의 순위이기
때문이에요. 이렇게 고른 값을 **기준값**(pivot)이라 부르고, 기준값으로 배열을 두 쪽으로 나누는 일을
**분할**(partition)이라고 부르겠습니다. `[5 2 3 1]` 에서 가운데 칸의 값 2 를 기준값으로 한 번 분할하면
이렇게 됩니다.

<!--fig:concept-partition-->
![[5 2 3 1] 을 기준값 2 로 한 번 가른 뒤 — 작은 값, 기준값, 큰 값](./figs/concept-partition.svg)

그림의 한 줄이 분할을 마친 배열이고, 아래 괄호 셋이 기준값보다 작은 쪽, 기준값, 기준값 이상인 쪽입니다.
기준값의 자리가 정말 정렬 뒤의 자리인지 정렬을 마친 배열과 맞춰 보면 이렇습니다.

<!--proof:concept-partition-->

| 입력 | 기준값 | 한 번 가른 뒤 | 기준값의 자리 | 정렬을 마친 배열에서 그 값의 자리 |
| --- | --- | --- | --- | --- |
| [5 2 3 1] | 2 | [1 2 3 5] | 인덱스 1 | 인덱스 1 |

기준값 2 가 한 번 가른 뒤 놓인 자리와 정렬을 마친 배열 [1 2 3 5] 에서의 자리가 같습니다.

<!--/proof-->

기준값의 자리는 다시 건드리지 않아요. 남은 것은 왼쪽 `[1]` 과 오른쪽 `[3 5]` 인데, 둘 다 처음과 **같은
모양의 더 작은 과제**입니다. 그래서 같은 분할을 양쪽에 다시 적용하고, 칸이 하나 이하인 쪽에서 멈춥니다. 이
절차가 **퀵 정렬**(quick sort)입니다. 새 배열을 잡지 않고 한 배열 안에서 두 칸을 맞바꾸기만 해서 분할하는
것이 이 절차의 또 다른 성질이에요.

다만 분할이 두 쪽을 **반씩 가른다는 보장은 없습니다.** 기준값이 구간의 가장 작은 값이면 왼쪽이 비고
오른쪽이 한 칸만 줄어요. 칸 50,000 개에서 두 경우를 세어 보면 이렇습니다.

<!--proof:concept-cost-->

| 갈림 | 칸 50,000 개의 입력 | 비교 | 시간(초당 1 억 번) | 가장 깊은 부름 |
| --- | --- | ---: | ---: | --- |
| 반씩 갈린다 | 정렬된 0 … 49,999 | 684,481 | 0.01 초 | 깊이 15 |
| 한쪽이 매번 빈다 | 최악으로 만든 입력 | 1,249,975,000 | 12.50 초 | 깊이 49,999 |

반씩 갈리는 줄은 정본으로 실제로 세었습니다. 한쪽이 비는 줄은 식 n(n−1)/2 로 냈고, 이 식은 칸 1 개부터 400 개까지와 1,000 개 · 2,000 개에서 만든 최악 입력을 정본에 넣어 센 값과 일치합니다.

<!--/proof-->

같은 코드가 입력에 따라 68 만 번도 되고 12 억 번도 됩니다. 비용을 결과만 적으면 흔한 입력에서
`O(n log n)`, 최악에서 `O(n²)` 이에요. 어느 쪽이 되는지는 **기준값을 어느 칸에서 고르느냐**와 입력의
모양이 함께 정합니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **오름차순 정렬의 뜻** — 모든 이웃 쌍에서 `A[k] ≤ A[k+1]` 입니다. 이 뜻이 흐릿하면 「기준값이
  제자리를 찾았다」가 무엇을 보장하는지 확인할 수 없어요. 비교만으로 정렬하는 일 자체와 선택 정렬의 비용은
  [병합 정렬 가이드](../sortArray/sortArray-guide.md)가 먼저 다룹니다.
- **배열에서 두 칸을 맞바꾸는 비용이 `O(1)`** 이라는 것. `a[i]` 와 `a[j]` 를 맞바꾸는 데 배열 길이는
  상관없어요.
- **재귀** — 함수가 자기와 같은 모양의 더 작은 과제를 부르는 것과, 그것을 멈추는 기저 조건. 같은 모양의
  재귀가 [병합 정렬 가이드](../sortArray/sortArray-guide.md)에도 나옵니다.
- **밑이 2 인 로그** — `log₂ n` 은 `n` 을 2 로 몇 번 나눠야 1 이하가 되는가입니다. 절반씩 줄이는
  절차에서 로그가 왜 나오는지는 [이진 탐색 가이드](../../binary-search/binarySearch/binarySearch-guide.md)가
  같은 자리를 다룹니다.

세 번째가 흐릿하면 이 글의 절반이 어긋납니다. 재귀를 「어떻게든 스스로 풀리는 것」으로 잡고 있으면 칸이
하나 이하인 구간에서 멈추는 자리가 왜 필요한지 확인할 수 없어요.

### 아이디어를 떠올리는 과정 — 선택 정렬에서 제자리 분할까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열을 받아, 그 배열 안에서
값을 오름차순으로 다시 늘어놓고 같은 배열을 돌려줍니다.

```ts
function quickSort(nums: number[]): number[];
```

- 입력: 정수 배열 `nums`. 칸 수 `n` 은 0 이상이고, 값이 어떤 규칙으로 놓였는지는 모릅니다.
- 출력: `nums` 의 모든 값을 오름차순으로 담은 배열. **입력 배열 자체를 고쳐서** 돌려주고, 같은 값이
  여럿이면 그 개수 그대로 담깁니다.
- 조건: **새 배열을 잡지 않습니다.** 값을 옮기는 일은 배열 안의 두 칸을 맞바꾸는 것으로만 합니다.
- 규모: 수치 반박에는 `n = 50,000` 을 씁니다. 비용은 흔한 채점 환경의 예산인 1 초에 대어 잽니다.

쓸 수 있는 연산은 둘입니다.

| 연산 | 알려 주는 것 · 하는 일 |
| --- | --- |
| 두 값의 크기 비교 | `a[p]` 와 `a[q]` 중 어느 쪽이 작은가 |
| 두 칸 맞바꾸기 | `a[p]` 와 `a[q]` 에 든 값을 서로 바꾼다 |

값의 범위를 이용하는 방법(계수 정렬)은 쓰지 않습니다. 비교만 되는 값에도 그대로 통하는 절차를 만드는 것이
목표예요. 이 글이 끝까지 쓰는 기호는 아래와 같고, 여기서 정한 뜻을 바꾸지 않습니다.

| 기호 | 무엇인가 | 범위 |
| --- | --- | --- |
| `n` | 배열의 칸 수 | `0 ≤ n` |
| `lo` · `hi` | 지금 정렬하는 구간의 왼쪽 끝 · 오른쪽 끝. 양 끝을 포함한다 | 구간이 비면 `hi < lo` |
| `pivot` | 그 구간에서 고른 **기준값**. 글에서는 「기준값」, 코드에서는 `pivot` | 구간마다 새로 고른다 |
| `pivotIdx` | 기준값을 고른 칸의 인덱스 | `lo ≤ pivotIdx ≤ hi` |
| `i` | 기준값보다 작은 값이 놓일 다음 자리 | `lo ≤ i ≤ hi` |
| `j` | 지금 읽고 있는 자리 | `lo` 부터 `hi − 1` 까지 |
| `T(n)` | 칸이 `n` 개인 구간을 정렬하는 데 드는 비교 횟수 | `T(0) = T(1) = 0` |

가장 먼저 떠오르는 방법은 **선택 정렬**입니다. 남은 칸 중 가장 작은 값을 찾아 맨 앞 칸과 맞바꾸는 일을
되풀이해요. 새 배열이 필요 없고 기법이 하나도 안 들어갑니다.

```ts
function quickSortNaive(nums: number[]): number[] {
  for (let k = 0; k < nums.length; k++) {
    let min = k;
    for (let t = k + 1; t < nums.length; t++) {
      if ((nums[t] as number) < (nums[min] as number)) min = t;
    }
    [nums[k], nums[min]] = [nums[min] as number, nums[k] as number];
  }
  return nums;
}
```

이 방법은 답을 틀리지 않습니다. 비용은 **값을 비교한 횟수**로 세는데, `k` 번째 바퀴가 남은 칸을 전부
비교하므로 입력과 상관없이 합이 `n(n−1)/2` 입니다.

<!--proof:origin-cost-->

| 방법 | 칸 50,000 개의 비교 | 시간(초당 1 억 번) | 새로 잡는 칸 |
| --- | ---: | ---: | ---: |
| 선택 정렬 | 1,249,975,000 | 12.50 초 | 0 |

선택 정렬은 바퀴마다 남은 칸을 전부 비교하므로 비교 횟수가 입력과 무관하게 n(n−1)/2 이고, 칸 1 개부터 200 개까지 실제로 세어 이 식과 대조했습니다.

<!--/proof-->

새 칸은 하나도 안 쓰지만 예산 1 초의 열두 배가 넘습니다. 네 칸짜리 `[5 2 3 1]` 에서 바퀴마다 무엇을 알아내는지
세어 보겠습니다.

<!--proof:origin-selection-->

| 바퀴 | 비교 | 그 자리에 놓은 값 | 바퀴가 끝난 배열 |
| ---: | ---: | ---: | --- |
| 1 | 3 | 1 | [1 2 3 5] |
| 2 | 2 | 2 | [1 2 3 5] |
| 3 | 1 | 3 | [1 2 3 5] |
| 4 | 0 | 5 | [1 2 3 5] |

비교는 3 + 2 + 1 + 0 = 6 번이고, 바퀴 하나가 자리 하나를 정합니다.

<!--/proof-->

바퀴 1 은 이미 배열을 다 정렬했는데도 바퀴 2 와 3 이 비교를 이어 갑니다. 바퀴 1 의 세 번 비교에는 「3 이
5 보다 작다」도 들어 있었지만, 그 비교가 정한 것은 맨 앞 칸 하나뿐이에요. 바퀴 하나가 **자리 하나**만
정하는 것이 이 방법이 느린 이유입니다.

한 번에 여러 자리를 좁히는 방법은 앞 편에서 이미 보았습니다. 배열을 자리로 반씩 갈라 따로 정렬한 뒤 둘을
합치는 **병합 정렬**이에요. 비교는 줄지만, 합치기가 결과를 담을 새 배열을 잡습니다. 정렬된 입력 50,000
칸으로 세어 보면 이렇습니다.

<!--proof:origin-merge-->

| 방법 | 정렬된 0 … 49,999 의 비교 | 새로 잡는 칸(누적) | 가장 큰 합치기 한 번의 새 칸 |
| --- | ---: | ---: | ---: |
| 선택 정렬 | 1,249,975,000 | 0 | 없음 |
| 병합 정렬 | 382,512 | 784,464 | 50,000 |

병합 정렬은 합치기마다 두 조각의 칸 수만큼 새 배열을 잡고, 그 칸 수를 모두 더했습니다. 두 방법 모두 답은 정본과 같습니다.

<!--/proof-->

병합 정렬은 마지막 합치기 한 번만으로 배열 전체만큼 새 칸을 잡습니다. 이 과제는 새 배열을 잡지 않는 것이
조건이라 여기서 멈춰요. 그러면 병합 정렬이 왜 합쳐야 했는지를 봅시다. **자리로** 갈랐기 때문입니다. 왼쪽
절반과 오른쪽 절반의 값이 서로 섞여 있어서, 각각 정렬해도 둘을 이어 붙이면 정렬이 안 돼요. **값으로**
갈라 두면 어떨까요. 작은 값을 전부 왼쪽, 큰 값을 전부 오른쪽에 모아 두면 양쪽을 각각 정렬한 것이 그대로
전체의 정렬이라 합칠 일이 없습니다.

해 봅시다. `[5 2 3 1]` 에서 값 2 하나를 정하고, 배열을 한 번만 읽으면서 「2 보다 작은가」만 묻습니다. 작은
값을 만나면 왼쪽 끝부터 차곡차곡 맞바꿔 넣고, 그 경계를 `i` 로 기억합니다. 2 는 읽는 동안 비켜 있도록 먼저
끝 칸으로 옮겨 둬요.

<!--proof:origin-one-pass-->

| j | 읽은 값 | 2 와의 비교 | 한 일 | 배열 | i |
| ---: | ---: | --- | --- | --- | ---: |
|  |  |  | 기준값 2 를 끝 칸으로 옮긴다 | [5 1 3 2] | 0 |
| 0 | 5 | 5 ≥ 2 | 그대로 둔다 | [5 1 3 2] | 0 |
| 1 | 1 | 1 < 2 | arr[0] 과 맞바꾸고 i 를 늘린다 | [1 5 3 2] | 1 |
| 2 | 3 | 3 ≥ 2 | 그대로 둔다 | [1 5 3 2] | 1 |
|  |  |  | 기준값을 인덱스 1 에 놓는다 | [1 2 3 5] | 1 |

새로 잡은 칸은 0 개이고, 2 가 인덱스 1 에 놓였습니다. 남은 일은 [1] 과 [3 5] 입니다.

<!--/proof-->

한 번 읽는 데 비교가 세 번 들었고, 2 의 자리가 정해졌으며, 남은 일이 둘로 나뉘었습니다. 새 칸은 쓰지
않았어요. 이 분할을 남은 두 쪽에 다시 적용하면 정렬이 끝나는데, 그때 드는 비교를 세면 규칙이 하나 보입니다.
분할 한 번은 구간의 기준값을 뺀 나머지를 한 번씩 읽으므로 **(구간 크기 − 1)** 번 비교해요.

<!--proof:origin-sum-->

| 원소가 둘 이상인 부름 | 구간 크기 | 비교 |
| --- | ---: | ---: |
| sort(0,3) | 4 | 3 |
| sort(2,3) | 2 | 1 |

(구간 크기 − 1) 을 더하면 3 + 1 = 4 이고, 정본이 센 비교 4 번과 같습니다. 원소가 하나 이하인 부름은 비교가 없습니다.

<!--/proof-->

이 합에는 배열의 값이 들어 있지 않습니다. 남은 변수는 **구간이 어떤 크기로 갈리는가** 하나예요. 그러면
기준값을 어느 칸에서 고를지부터 정해야 합니다. 가장 단순한 후보는 구간의 **첫 원소**입니다. 이미 정렬된
여덟 칸 `[0 1 2 3 4 5 6 7]` 에 첫 원소와 가운데 칸을 각각 기준값으로 삼고, 부름마다 구간이 어떻게 갈리는지
적어 보겠습니다.

<!--proof:origin-two-ways-->

| 부름 | (가) 첫 원소 기준값 | 비교 | (나) 가운데 칸 기준값 | 비교 |
| ---: | --- | ---: | --- | ---: |
| 1 | 구간 8 → 왼 0 · 오 7 | 7 | 구간 8 → 왼 3 · 오 4 | 7 |
| 2 | 구간 7 → 왼 0 · 오 6 | 6 | 구간 3 → 왼 1 · 오 1 | 2 |
| 3 | 구간 6 → 왼 0 · 오 5 | 5 | 구간 4 → 왼 1 · 오 2 | 3 |
| 4 | 구간 5 → 왼 0 · 오 4 | 4 | 구간 2 → 왼 0 · 오 1 | 1 |
| 5 | 구간 4 → 왼 0 · 오 3 | 3 |  |  |
| 6 | 구간 3 → 왼 0 · 오 2 | 2 |  |  |
| 7 | 구간 2 → 왼 0 · 오 1 | 1 |  |  |

(가) 는 비교 28 번, (나) 는 13 번이고, 답은 둘 다 [0 1 2 3 4 5 6 7] 입니다.

<!--/proof-->

답도 같고 맞바꾸는 규칙도 같은데 비교가 28 과 13 으로 갈립니다. (가) 는 첫 원소가 늘 구간의 가장 작은
값이라 왼쪽이 매번 비고, 구간이 한 칸씩만 줄어요. 여기서 관찰한 것은 하나입니다. **두 쪽이 고르게 갈릴수록
비교가 적습니다.** 그리고 (가) 의 28 은 여덟 칸 선택 정렬의 비교 `8 · 7 / 2` 와 같은 값이에요. 칸 수를 키워
보면 그대로 겹칩니다.

<!--proof:origin-first-pivot-->

| 칸 수 n | 첫 원소 기준값 · 정렬된 입력의 비교 | 선택 정렬의 비교 |
| ---: | ---: | ---: |
| 8 | 28 | 28 |
| 64 | 2,016 | 2,016 |
| 50,000 | 1,249,975,000 | 1,249,975,000 |

칸 400 개까지는 첫 원소를 기준값으로 고르는 절차를 정렬된 입력에 실제로 실행해 n(n−1)/2 와 대조했고, 그보다 큰 칸 수는 그 식으로 냈습니다.

<!--/proof-->

첫 원소를 고르면 이미 정렬된 입력이라는 흔한 모양에서 선택 정렬로 되돌아갑니다. 가운데 칸을 고르면 같은
입력이 고르게 갈려요. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **제자리 분할**입니다. 구간의 가운데 칸 값을 기준값으로 골라, 한 번 읽으며 그보다
작은 값을 왼쪽으로 맞바꿔 모으고, 기준값을 두 쪽 사이에 놓은 다음, 양쪽에 같은 일을 되풀이해요. 이 절차가
퀵 정렬입니다. 그림의 마지막 칸이 적은 대로 최악은 남아 있는데, 그 입력이 어떻게 생겼는지는 파트 2 에서
직접 만들어 봅니다. 분할이 도중에 어떤 모양을 하는지, 기준값을 왜 끝으로 옮기는지, 가운데 칸이 왜 나은지는
다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 제자리 분할

이 아이디어를 한 문장으로 줄이면 이렇습니다. **구간의 가운데 칸 값을 기준값으로 끝에 빼 두고, 구간을 한
번 읽으며 기준값보다 작은 값을 왼쪽 끝부터 맞바꿔 모은 다음, 기준값을 두 쪽 사이에 놓고 양쪽에 같은 일을
되풀이합니다.** 이 분할 방식에는 로무토 분할(Lomuto partition)이라는 이름이 붙어 있어요. 실현하는 순서대로
세 단계로 나누면 이렇습니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 기준값을 고르고 끝으로 빼 두기 | 가운데 칸을 골라 끝 칸과 맞바꾼다 | — |
| 2단계 한 번 읽으며 두 구역 넓히기 | `j` 로 한 칸씩 읽고, 기준값보다 작으면 `i` 자리와 맞바꾼다 | 1단계가 끝 칸에 빼 둔 기준값 |
| 3단계 기준값을 경계에 놓고 양쪽 되풀이하기 | `i` 자리와 끝 칸을 맞바꾸고 양쪽 구간을 다시 부른다 | 2단계가 남긴 경계 `i` |

2단계가 이 방법의 중심이고, 그 도중의 배열은 처음 보면 낯선 모양을 합니다. 단계로 들어가기 전에 그
모양부터 보겠습니다.

#### 먼저 알아 둘 개념 — 분할 도중의 네 구역

##### 쉬운 말 정의

분할하는 동안 구간 `[lo, hi]` 는 네 덩어리로 나뉩니다. 이미 읽었고 기준값보다 작은 값들(**작음**), 이미
읽었고 기준값 이상인 값들(**큼**), 아직 읽지 않은 값들(**아직**), 그리고 끝 칸의 **기준값**이에요. 인덱스로
적으면 작음이 `[lo, i−1]`, 큼이 `[i, j]`, 아직이 `[j+1, hi−1]`, 기준값이 `hi` 입니다.

##### 입력 위에 놓은 그림

`[5 2 3 1]` 을 분할하면서 인덱스 1 까지 읽은 순간을 그리면 이렇습니다. 괄호 넷이 네 구역이에요.

<!--fig:build-regions-->
![분할 도중의 네 구역 — 작음, 큼, 아직, 기준값](./figs/build-regions.svg)

##### 한 칸을 읽는 법

칸 하나가 어느 구역인지는 그 칸의 인덱스를 `i` · `j` · `hi` 와 비교하면 정해지고, 구역이 정해지면 그 값과
기준값의 관계도 정해집니다. 위 그림의 네 칸을 하나씩 읽으면 이렇습니다.

<!--proof:build-regions-read-->

| 인덱스 | 값 | 구역 | 기준값 2 와의 관계 |
| ---: | ---: | --- | --- |
| 0 | 1 | 작음 | 1 < 2 |
| 1 | 5 | 큼 | 5 ≥ 2 |
| 2 | 3 | 아직 | 아직 비교하지 않았다 |
| 3 | 2 | 기준값 | 기준값 그 자체 |

i = 1, j = 1 인 순간입니다. 작음 구역은 인덱스 [0,0], 큼 구역은 [1,1], 아직 구역은 [2,2] 입니다.

<!--/proof-->

인덱스 1 의 5 를 예로 들면, `i = 1 ≤ 1 ≤ j = 1` 이라 큼 구역이고, 그래서 5 가 기준값 2 이상이라는 것을 값을
다시 보지 않고도 압니다.

##### 구역끼리의 관계

네 구역은 늘 이 순서로 붙어 있고, 경계는 `i` 와 `j` 둘이 정합니다. `j` 가 한 칸 나아갈 때마다 아직 구역의
첫 칸이 작음이나 큼으로 옮겨 가요. 한 번 분할하는 동안 칸 수가 어떻게 바뀌는지 세면 이렇습니다.

<!--proof:build-regions-grow-->

| 시점 | 갈래 | 작음 칸 수 | 큼 칸 수 | 아직 칸 수 |
| --- | --- | ---: | ---: | ---: |
| 읽기 전 |  | 0 | 0 | 3 |
| j = 0 을 읽은 뒤 | ② | 0 | 1 | 2 |
| j = 1 을 읽은 뒤 | ① | 1 | 1 | 1 |
| j = 2 를 읽은 뒤 | ② | 1 | 2 | 0 |

한 칸을 읽을 때마다 아직 구역이 한 칸 줄고, 작음과 큼 중 한 구역이 한 칸 늡니다.

<!--/proof-->

① 은 읽은 값이 기준값보다 작은 갈래, ② 는 크거나 같은 갈래입니다. 아직 구역이 0 칸이 되면 분할이 끝나고,
그때 남는 것은 작음 · 큼 · 기준값 셋이에요.

##### 헷갈리기 쉬운 모양과의 대조

처음 떠올리기 쉬운 모양은 작은 값과 큰 값을 **새 배열 둘에 나눠 담는** 가르기입니다. 같은 `[5 1 3 2]` 에
두 모양을 적용해 보았습니다.

<!--proof:build-regions-copy-->

| 가르는 모양 | 가른 결과 | 새로 잡는 칸 | 큰 쪽의 순서 |
| --- | --- | ---: | --- |
| 새 배열 둘에 나눠 담는다 | [1 2 5 3] | 3 | [5 3] |
| 한 배열 안에서 맞바꾼다 | [1 2 3 5] | 0 | [3 5] |

두 모양 모두 기준값 2 가 인덱스 1 에 오고 작은 쪽도 같습니다. 큰 쪽은 값은 같지만 순서가 다릅니다.

<!--/proof-->

두 모양이 기준값의 자리와 양쪽에 든 값은 같게 만듭니다. 다른 것은 둘이에요. 새 배열 쪽은 칸을 더 쓰고,
제자리 쪽은 맞바꾸면서 큰 쪽 값들의 순서를 바꿉니다. 큰 쪽의 순서는 어차피 다음 분할이 다시 정렬하므로
답에는 영향이 없어요.

##### 왜 이렇게 생겼는가

새 칸 없이 한 번 읽으며 값을 둘로 나누려면, 읽은 칸과 아직 안 읽은 칸이 **한 배열 안에 함께** 있어야
합니다. 작은 값을 왼쪽 끝부터 모으려면 다음에 넣을 자리를 기억할 `i` 가 필요하고, 읽는 자리 `j` 가 늘 `i`
이상이라 작은 값을 `i` 자리로 옮겨도 아직 안 읽은 칸을 덮지 않아요. 기준값을 끝에 빼 두는 것은 읽는 범위를
`[lo, hi−1]` 한 덩어리로 만들기 위해서입니다. 그래서 네 구역이 작음 · 큼 · 아직 · 기준값 순서로 붙습니다.

#### 1단계 — 기준값을 고르고 끝으로 빼 두기

구간 `[lo, hi]` 의 가운데 칸을 `pivotIdx = lo + ⌊(hi − lo) / 2⌋` 로 고릅니다. 이 글의 입력과 정렬된 여덟 칸에서
실제로 나온 구간들을 적으면 이렇습니다.

<!--proof:build-pivot-->

| 구간 | 칸 수 | pivotIdx |
| --- | ---: | --- |
| [0,7] | 8 | 0 + ⌊7/2⌋ = 3 |
| [0,3] | 4 | 0 + ⌊3/2⌋ = 1 |
| [4,7] | 4 | 4 + ⌊3/2⌋ = 5 |
| [0,2] | 3 | 0 + ⌊2/2⌋ = 1 |
| [2,3] | 2 | 2 + ⌊1/2⌋ = 2 |
| [6,7] | 2 | 6 + ⌊1/2⌋ = 6 |

칸 수가 짝수이면 가운데 두 칸 중 왼쪽 칸을 고릅니다. 칸이 둘이면 그 칸이 lo 입니다.

<!--/proof-->

`(lo + hi) / 2` 대신 `lo + (hi − lo) / 2` 로 적는 것은 두 식이 같은 값을 내면서도 뒤쪽이 `lo + hi` 라는 큰
수를 만들지 않기 때문이에요. 고른 칸은 끝 칸 `hi` 와 맞바꿉니다. 그러면 2단계가 읽을 범위가 `[lo, hi−1]` 한
덩어리가 되어, 읽는 도중에 기준값 칸을 비켜 갈 필요가 없습니다. 칸이 둘인 구간은 `pivotIdx = lo` 라 맞바꾸기가
두 칸의 순서를 뒤집기만 해요.

#### 2단계 — 한 번 읽으며 두 구역 넓히기

`i` 와 `j` 를 둘 다 `lo` 에서 출발시킵니다. 처음에는 작음과 큼이 비어 있고 `[lo, hi−1]` 전체가 아직
구역이에요. `j` 를 한 칸씩 늘리며 `arr[j]` 를 기준값과 비교합니다. 쉬운 경우는 읽은 값이 기준값 이상일
때입니다.

<!--proof:build-scan-easy-->

| 시점 | 배열 | 작음 구역의 값 | 큼 구역의 값 | i |
| --- | --- | --- | --- | ---: |
| arr[0] = 5 를 읽기 전 | [5 1 3 2] | [ ] | [ ] | 0 |
| 5 < 2 거짓 → ② | [5 1 3 2] | [ ] | [5] | 0 |

맞바꾸지 않고 j 만 나아가서, 읽은 5 가 그 자리에서 큼 구역의 끝이 됩니다.

<!--/proof-->

아무것도 옮기지 않아도 큼 구역이 오른쪽으로 한 칸 자랍니다. 불안한 경우는 작은 값을 만나 맞바꿀 때예요.
`arr[i]` 에 있던 값이 `arr[j]` 자리로 옮겨지는데, 그 값이 어느 구역에 들어가도 되는지 확인해야 합니다.

<!--proof:build-scan-swap-->

| 시점 | 배열 | 작음 구역의 값 | 큼 구역의 값 | i |
| --- | --- | --- | --- | ---: |
| arr[1] = 1 을 읽기 전 | [5 1 3 2] | [ ] | [5] | 0 |
| 1 < 2 참 → ① | [1 5 3 2] | [1] | [5] | 1 |

1 이 작음 구역 끝(인덱스 0)으로 가고, 그 자리에 있던 5 가 인덱스 1 로 옮겨져 큼 구역의 끝이 됩니다. 5 는 직전까지 큼 구역의 첫 값이었으므로 기준값 2 이상입니다.

<!--/proof-->

옮겨진 값은 늘 **큼 구역의 첫 값**이었습니다. `i` 가 큼 구역의 첫 자리이기 때문이에요. 그 값을 큼 구역의
끝 `j` 로 옮기면 큼 구역은 한 칸 오른쪽으로 옮겨 갈 뿐 여전히 기준값 이상인 값만 담고, 작음 구역은 새로 들어온
작은 값 하나만큼 자랍니다. 큼 구역이 비어 있을 때는 `i = j` 라 제자리와 맞바꾸는 셈이 되어 배열이 그대로예요.

반복은 `j` 가 `hi − 1` 을 읽고 `hi` 에 이르면 끝납니다. 그때까지 `[lo, hi−1]` 의 칸을 정확히 한 번씩
읽었으므로, 어느 칸도 분류되지 않은 채 남지 않아요. 이 구간의 비교는 `hi − lo` 번, 곧 (구간 크기 − 1) 번입니다.

#### 3단계 — 기준값을 경계에 놓고 양쪽 되풀이하기

반복이 끝나면 아직 구역이 비고 `[작음][큼][기준값]` 이 남습니다. `i` 가 큼 구역의 첫 자리이니 `arr[i]` 와
`arr[hi]` 를 맞바꾸면 기준값이 두 구역 사이에 들어가요. 왼쪽은 전부 기준값보다 작고 오른쪽은 전부 기준값
이상이라, 이 자리가 곧 정렬 뒤의 자리입니다. 그다음 왼쪽 `[lo, i−1]` 과 오른쪽 `[i+1, hi]` 를 같은 절차로
부릅니다. `[5 2 3 1]` 에서 부름마다 이렇게 됩니다.

<!--proof:build-place-->

| 부름 | 기준값 | 놓인 자리 | 놓은 뒤의 배열 | 왼쪽 구간 | 오른쪽 구간 |
| --- | --- | --- | --- | --- | --- |
| sort(0,3) | 2 | 인덱스 1 | [1 2 3 5] | [0,0] | [2,3] |
| sort(2,3) | 3 | 인덱스 2 | [1 2 3 5] | 비었다 | [3,3] |

원소가 둘 이상인 부름은 두 번이고, 부름마다 기준값 하나가 최종 자리에 놓였습니다. 나머지 두 칸은 원소가 하나인 부름에서 그대로 남았습니다.

<!--/proof-->

되풀이는 칸이 하나 이하인 구간에서 멈춥니다. `hi − lo < 1` 이면 비교할 것이 없어 그대로 정렬돼 있어요.
두 구간은 기준값 칸을 빼고 나누므로 합쳐서 원래보다 한 칸 작고, 그래서 되풀이는 반드시 끝납니다. `sort(2,1)`
처럼 `hi < lo` 인 부름도 나오는데, 기준값이 구간 왼쪽 끝에 놓여 왼쪽 구간이 빈 경우예요.

같은 깊이에서 부른 구간들은 서로 겹치지 않으므로, 한 깊이의 비교를 모두 더해도 칸 수를 넘지 않습니다.
그러니 비교 총합은 **몇 깊이까지 내려가는가**가 정해요. 정렬된 여덟 칸을 두 방식으로 부른 구간을 깊이마다
그리면 이렇습니다.

<!--fig:build-calls-middle-->
![정렬된 여덟 칸 — 가운데 칸을 기준값으로 고른 부름](./figs/build-calls-middle.svg)

<!--fig:build-calls-first-->
![정렬된 여덟 칸 — 첫 칸을 기준값으로 고른 부름](./figs/build-calls-first.svg)

두 그림의 줄마다 한 부름이고, 줄 끝이 그 부름의 기준값과 비교 횟수입니다. 깊이마다 비교를 더하면
이렇습니다.

<!--proof:build-depth-->

| 기준값 | 깊이마다 비교의 합 | 비교가 있는 깊이 수 | 비교 합 |
| --- | --- | ---: | ---: |
| 가운데 칸 | 7 · 5 · 1 | 3 | 13 |
| 첫 칸 | 7 · 6 · 5 · 4 · 3 · 2 · 1 | 7 | 28 |

어느 깊이에서도 비교의 합이 칸 수 8 을 넘지 않습니다.

<!--/proof-->

가운데 칸은 구간을 반씩 갈라 세 깊이로 끝나고, 첫 칸은 한쪽만 한 칸씩 줄여 일곱 깊이까지 내려갑니다. 반씩
갈리면 깊이가 `log₂ n` 규모, 한쪽이 비면 `n` 규모예요.

#### 이 방법이 기대는 전제

제자리 분할은 아래 세 전제에 기대고 있습니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 두 값의 크기를 비교할 수 있다 | 2단계의 비교 한 줄 | 작음과 큼을 가르지 못한다 |
| 아무 두 칸이나 바로 맞바꿀 수 있다 | 1 · 2 · 3단계의 맞바꾸기 | 연결 리스트처럼 가운데 칸까지 가는 데만 칸 수만큼 걸린다 |
| 기준값이 구간을 고르게 가른다 | 3단계 뒤 두 구간의 크기 | 답은 맞고 비교가 `n(n−1)/2` 까지 는다 |

앞의 두 전제는 절차가 성립하는 조건이고, 마지막 전제는 비용의 조건입니다. 마지막 전제가 깨지면 오류 없이 느려져요.
가운데 칸이 매번 구간의 가장 작은 값이 되도록 만든 여덟 칸을 정렬된 입력과 나란히 넣었습니다.

<!--proof:premise-balance-->

| 입력 | 결과 | 비교 | 가장 깊은 부름 |
| --- | --- | ---: | ---: |
| 정렬된 입력 [0 1 2 3 4 5 6 7] | [0 1 2 3 4 5 6 7] | 13 | 3 |
| 최악으로 만든 입력 [2 6 4 0 1 3 5 7] | [0 1 2 3 4 5 6 7] | 28 | 7 |

두 입력 모두 답은 오름차순으로 맞게 나옵니다. 갈림이 고르지 않으면 틀리지 않고 느려집니다.

<!--/proof-->

그래서 이 방법은 입력이 대체로 고르게 갈린다는 기대 위에 서 있고, 그 기대가 깨지는 입력을 막는 장치는
기준값을 고르는 자리 하나뿐입니다. 그 선택이 다음 절이에요.

#### 가운데 칸을 기준값으로 고르는 까닭

「아이디어를 떠올리는 과정」에서는 정렬된 입력 하나로 첫 원소와 가운데 칸을 비교했습니다. 이제 고르는 자리를
넷으로 두고 여덟 칸 입력 다섯에 실제로 실행합니다. 분할 규칙은 그대로 두고 1단계의 `pivotIdx` 만 바꿔요. 세
값의 중앙값은 첫 칸 · 가운데 칸 · 끝 칸의 값 중 가운데 값이 있는 칸을 고르는 방법입니다.

<!--proof:pivot-choice-->

| 입력 (n = 8) | 첫 원소 | 중앙 | 마지막 | 세 값의 중앙값 |
| --- | --- | --- | --- | --- |
| 정렬된 `[0 1 2 3 4 5 6 7]` | 28 (7) | 13 (3) | 28 (7) | 13 (3) |
| 역순 `[7 6 5 4 3 2 1 0]` | 28 (7) | 15 (3) | 28 (7) | 13 (3) |
| 가운데 칸 최악 `[2 6 4 0 1 3 5 7]` | 16 (4) | 28 (7) | 19 (4) | 14 (3) |
| 섞인 `[5 2 8 1 9 3 7 4]` | 15 (4) | 22 (5) | 16 (4) | 13 (3) |
| 전부 같음 `[2 2 2 2 2 2 2 2]` | 28 (7) | 28 (7) | 28 (7) | 28 (7) |

칸마다 비교 횟수이고, 괄호 안은 맨 바깥 부름을 0 으로 센 가장 깊은 부름의 깊이입니다. 중앙 열은 정본으로 센 값과 같습니다.

<!--/proof-->

첫 원소와 마지막은 정렬된 입력과 역순 입력에서 둘 다 28 번입니다. 가운데 칸은 그 둘을 13 번과 15 번으로
막아요. 그 대신 가운데 칸을 노린 입력에서는 가운데 칸이 28 번이 됩니다. 어느 자리든 28 을 내는 입력이 있다는
뜻이에요. 그러면 모든 입력을 고르게 넣으면 어떨까요. 순열 전부로 세어 봅니다.

<!--proof:pivot-choice-perm-->

| 기준값 자리 | 가장 적을 때 | 평균 | 가장 많을 때 | 가장 많은 순열 수 |
| --- | ---: | ---: | ---: | ---: |
| 첫 원소 | 13 | 16.92 | 28 | 128 |
| 중앙 | 13 | 16.92 | 28 | 128 |
| 마지막 | 13 | 16.92 | 28 | 128 |
| 세 값의 중앙값 | 13 | 13.87 | 16 | 3,456 |

값 0 … 7 의 순열 40,320 개를 전부 넣어 센 비교 횟수입니다.

<!--/proof-->

순열을 고르게 넣으면 첫 원소 · 중앙 · 마지막 세 자리가 모든 칸에서 같습니다. 어느 한 칸을 고정해서 고르는
한, 순열 전체로 보면 그 칸에 어떤 값이 오는지가 고르게 퍼지기 때문이에요. 그러니 가운데 칸의 이점은
**정렬됐거나 거꾸로 정렬된 입력처럼 실제로 자주 들어오는 모양**에서만 생깁니다. 세 값의 중앙값은 평균도
최악도 더 적지만, 부름마다 세 값을 비교하는 일이 따로 더해지고(위 표는 그 비교를 세지 않았습니다) 코드가
길어져요. 값이 전부 같은 입력은 네 방법 모두 막지 못합니다. 이 글은 **가운데 칸**을 고릅니다. 한 줄로 끝나고,
흔한 두 모양을 막기 때문이에요.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 다섯 걸음이 됩니다. 칸 50,000 개의 정렬된 입력이면 선택 정렬로
1,249,975,000 번이던 비교가 684,481 번이 되고, 새 칸은 여전히 쓰지 않아요.

1. 구간의 칸이 하나 이하면 그대로 돌아간다
2. 가운데 칸을 기준값으로 골라 끝 칸과 맞바꾼다
3. `j` 로 `[lo, hi−1]` 을 한 번 읽으며, 기준값보다 작은 값을 `i` 자리와 맞바꾸고 `i` 를 늘린다
4. `arr[i]` 와 끝 칸을 맞바꿔 기준값을 제자리에 놓는다
5. 왼쪽 `[lo, i−1]` 과 오른쪽 `[i+1, hi]` 에 같은 절차를 부른다

### 수행으로 알아보는 알고리즘 — 네 칸을 두 번 갈라 오름차순으로 만든다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다
그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const nums = [5, 2, 3, 1];
// 이 절이 끝나면 [1, 2, 3, 5] 가 나와야 한다
```

`nums` 를 왜 하필 이 네 칸으로 뒀을까요? 분할 루프의 두 갈래를 **모두 실행하게** 하면서, 재귀가 원소 하나인
구간과 빈 구간까지 내려가는 것을 보이려는 것입니다. 이 입력은 첫 분할 뒤에도 원소가 둘인 구간이 남아 분할이 두
번 일어나고, 두 번째 분할에서 빈 구간을 부르는 경우까지 나와요.

```text
sort(arr, lo, hi):
    원소가 1개 이하면 반환
    가운데 칸을 기준값으로 골라 끝 칸과 맞바꾼다
    i ← lo
    j 를 lo 부터 hi-1 까지:
        arr[j] < pivot 이면 arr[i] 와 맞바꾸고 i 를 늘린다   ① 작다
        아니면 그대로 둔다                                    ② 크거나 같다
    arr[i] 와 arr[hi] 를 맞바꿔 기준값을 i 에 놓는다
    sort(arr, lo, i-1)
    sort(arr, i+1, hi)
```

#### 1. 기준값을 끝으로 빼 둔다

분할 루프는 작음과 큼 두 구역만 관리하면 됩니다. 기준값이 구간 가운데 있으면 읽는 도중에 그 칸을 비켜 가야
하므로, **먼저 끝으로 옮겨** 루프가 `hi` 앞까지만 읽게 만들어요.

```ts
const pivotIdx = lo + Math.floor((hi - lo) / 2);
[arr[pivotIdx], arr[hi]] = [arr[hi] as number, arr[pivotIdx] as number];
const pivot = arr[hi] as number;
```

`nums` 에 이 조각만 실행하면 이렇게 나옵니다.

<!--proof:walk-pivot-->

```text
처음        [5 2 3 1]   lo=0 hi=3 · pivotIdx = 0 + ⌊3/2⌋ = 1
맞바꾼 뒤   [5 1 3 2]   인덱스 1 과 3 을 맞바꿔 pivot = 2 가 hi=3 에 있다
```

값 2 가 끝으로 갔고, 원래 끝에 있던 1 이 인덱스 1 로 들어왔습니다.

#### 2. 한 번 읽으며 두 구역을 넓힌다

`i` 는 「작은 값이 놓일 다음 자리」이고 `j` 는 읽는 자리입니다. 둘 사이가 큼 구역이에요.

```ts
let i = lo;
for (let j = lo; j < hi; j++) {
  if ((arr[j] as number) < pivot) {
    // ① 기준값보다 작다 — 작은 쪽 구역으로 보내고 그 구역을 한 칸 넓힌다.
    [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
    i++;
  }
  // ② 기준값보다 크거나 같다 — 그대로 둔다. j 만 나아간다.
}
```

앞 조각이 만든 `[5 1 3 2]` 에서 이 루프를 실행하면 이렇게 나옵니다.

<!--proof:walk-loop-->

```text
j=0   5 < 2 거짓   ②   [5 1 3 2]   i 0
j=1   1 < 2 참     ①   [1 5 3 2]   i 0→1
j=2   3 < 2 거짓   ②   [1 5 3 2]   i 1
루프 끝 i = 1
```

여기서 가장 중요한 줄은 `i++` 입니다. 이 줄이 **작음 구역의 오른쪽 끝을 한 칸 옮겨서**, 다음에 만나는 작은
값이 앞서 넣은 값을 덮지 않게 해요. 이 줄 하나를 지우면 무엇이 나오는지는 파트 2 의 불변식 절에서 값으로
봅니다.

#### 짚고 가기 — 정렬된 배열이 최악이라는 말은 이 구현에서 거짓이다

「이미 정렬된 배열이 퀵 정렬의 최악」이라는 말을 들어 보셨을 텐데, 그 말은 **첫 원소나 마지막 칸을
기준값으로 고르는 구현**에서만 참입니다. 1 번 걸음에서 가운데 칸을 골랐으니, 정렬된 입력을 그대로 넣고
세어 봅시다.

<!--proof:pause-sorted-->

| 입력 (n = 8) | 비교 | 가장 깊은 부름 |
| --- | ---: | ---: |
| 정렬된 [0 1 2 3 4 5 6 7] | 13 | 3 |
| 역순 [7 6 5 4 3 2 1 0] | 15 | 3 |
| 가운데 칸 최악 [2 6 4 0 1 3 5 7] | 28 | 7 |

순열 40,320 개를 전부 넣으면 비교는 가장 적을 때 13 번, 가장 많을 때 28 번입니다.

<!--/proof-->

정렬된 입력은 순열 전체에서 가장 적은 13 번과 같습니다. 정렬된 구간에서는 가운데 칸의 값이 곧 그 구간의
중앙값이라, 오히려 **가장 고른** 갈림이 나와요.

<!--proof:pause-sorted-split-->

```text
구간 [0,7]   가운데 칸의 값 3   → [0 1 2] 3 [4 5 6 7]
구간 [0,2]   가운데 칸의 값 1   → [0] 1 [2]
```

여기서 한 걸음 더 가면 두 번째 오해가 나옵니다. 「가운데 칸을 고르니 최악이 없어졌다」는 것이에요. 그것도
거짓입니다. 가운데 칸 최악으로 만든 입력이 28 번이고, 그 입력을 어떻게 만드는지는 파트 2 의 「최악을 만드는 입력」에서
부름마다 확인합니다.

#### 3. 기준값을 두 구역 사이에 놓고 양쪽을 되풀이한다

루프가 끝나면 `i` 가 큼 구역의 첫 자리이고, 그 자리가 기준값의 최종 위치입니다.

```ts
[arr[i], arr[hi]] = [arr[hi] as number, arr[i] as number];

sort(arr, lo, i - 1);
sort(arr, i + 1, hi);
```

앞 조각이 남긴 `[1 5 3 2]` 와 `i = 1` 에서 이 조각을 실행하면 이렇게 나옵니다.

<!--proof:walk-place-->

```text
루프 끝     [1 5 3 2]               i = 1
맞바꾼 뒤   [1 2 3 5]               arr[1] 과 arr[3] 을 맞바꿔 기준값 2 가 인덱스 1 에 놓였다
다음 부름   sort(0,0) · sort(2,3)
```

`i` 를 양쪽 어디에도 넣지 않는 것이 이 조각의 핵심이에요. 기준값은 확정됐으므로 다시 볼 필요가 없고, 넣으면
구간이 줄지 않아 되풀이가 끝나지 않을 수 있습니다.

#### 4. 네 칸을 실제로 갈라 본다

앞의 세 조각을 이어 `quickSort([5, 2, 3, 1])` 을 끝까지 실행합니다. 무대는 배열 `arr` 이고, 위 괄호가 지금
부른 구간, 그 아래 괄호가 분할 도중의 작음 · 큼 구역이나 기준값을 놓은 뒤의 왼쪽 · 오른쪽 구간이에요. 강조한
칸이 맞바꾼 칸이고, ▲ 는 이번에 비교한 두 칸입니다. 맨 아래 「확정」 줄에는 최종 자리가 정해진 값이 하나씩
채워집니다.

<!--viz:partition-->
<!--fig:walk-partition-->
![quickSort([5, 2, 3, 1]) 의 열세 걸음 T1~T13](./figs/walk-partition.svg)

<!--result:partition=[1, 2, 3, 5]-->

한 걸음마다 조건이 어떻게 판정되는지 전부 적으면 아래 열세 단계입니다.

<!--proof:walk-trace-->

| 단계 | 무슨 일 | 조건 판정 | 배열 | `i` |
| --- | --- | --- | --- | --- |
| T1 | `sort(0,3)` 시작 | `hi-lo = 3 ≥ 1` 이라 계속, `pivotIdx = 1` | `[5 2 3 1]` |  |
| T2 | 기준값 2 를 끝으로 | 인덱스 1 과 3 을 맞바꾼다 | `[5 1 3 2]` | 0 |
| T3 | `j=0` | `5 < 2` **거짓** → ② | `[5 1 3 2]` | 0 |
| T4 | `j=1` | `1 < 2` **참** → ① | `[1 5 3 2]` | 0→1 |
| T5 | `j=2` | `3 < 2` **거짓** → ② | `[1 5 3 2]` | 1 |
| T6 | 기준값을 경계 자리로 | `i = 1` 이 값 2 의 최종 자리 | `[1 2 3 5]` | 1 |
| T7 | `sort(0,0)` | `hi-lo = 0 < 1` 이라 즉시 반환 | `[1 2 3 5]` |  |
| T8 | `sort(2,3)` 시작 | `hi-lo = 1 ≥ 1` 이라 계속, `pivotIdx = 2` | `[1 2 3 5]` |  |
| T9 | 기준값 3 을 끝으로 | 인덱스 2 와 3 을 맞바꾼다 | `[1 2 5 3]` | 2 |
| T10 | `j=2` | `5 < 3` **거짓** → ② | `[1 2 5 3]` | 2 |
| T11 | 기준값을 경계 자리로 | `i = 2` 가 값 3 의 최종 자리 | `[1 2 3 5]` | 2 |
| T12 | `sort(2,1)` | `hi-lo = -1 < 1` 이라 즉시 반환 | `[1 2 3 5]` |  |
| T13 | `sort(3,3)` | `hi-lo = 0 < 1` 이라 즉시 반환 | `[1 2 3 5]` |  |

<!--/proof-->

**두 갈래가 모두 나왔습니다.** 반환값은 `[1, 2, 3, 5]` 예요.

<!--proof:walk-branches-->

```text
①  작다          T4
②  크거나 같다   T3 · T5 · T10

비교 4 번 = (구간 4 − 1) + (구간 2 − 1) = 3 + 1
```

여기서 헷갈리기 쉬운 포인트는 T7 과 T12 입니다. 둘 다 즉시 반환인데 `hi-lo` 가 각각 `0` 과 `-1` 이에요.
`sort(2,1)` 처럼 `hi` 가 `lo` 보다 작은 부름이 나오는 것은 T11 에서 기준값이 구간의 왼쪽 끝에 놓였기
때문이고, 왼쪽 구간이 비어 있다는 뜻입니다. 조건을 `hi - lo < 1` 로 적었기 때문에 이 두 경우를 한 줄이
함께 받아요.

#### 짚고 가기 — 값이 전부 같으면 답은 맞는데 가장 느리다

값이 전부 같은 배열은 이미 정렬된 것이니 가장 빨리 끝날 것 같지 않나요? **답은 실제로 맞게 나옵니다.**
그래서 이 자리가 함정이에요. 테스트가 통과하니 문제가 있는 줄 모르고 넘어갑니다. 비교를 `<=` 로 바꾸면 되지
않을까 싶은 것까지 함께 넣어 보았습니다.

<!--proof:pause-equal-->

| 코드 | 입력 | 결과 | 비교 |
| --- | --- | --- | ---: |
| 바른 코드 `<` | [2 2 2 2 2 2 2 2] | [2 2 2 2 2 2 2 2] | 28 |
| `<=` 로 적은 코드 | [2 2 2 2 2 2 2 2] | [2 2 2 2 2 2 2 2] | 28 |
| 바른 코드 `<` | [0 1 2 3 4 5 6 7] | [0 1 2 3 4 5 6 7] | 13 |

값이 전부 같은 입력은 두 코드 모두 답이 맞고, 비교는 28 번 = 8 · 7 / 2 입니다.

<!--/proof-->

`arr[j] < pivot` 이 한 번도 참이 되지 않으니 ① 이 한 번도 실행되지 않고, `i` 가 `lo` 에 머뭅니다. 그래서
기준값이 매번 구간 맨 앞으로 가고 오른쪽 구간이 한 칸만 줄어요.

<!--proof:pause-equal-calls-->

```text
구간 8 → 왼 0 · 오 7   비교 7   기준값이 놓인 자리 0 = lo
구간 7 → 왼 0 · 오 6   비교 6   기준값이 놓인 자리 1 = lo
구간 6 → 왼 0 · 오 5   비교 5   기준값이 놓인 자리 2 = lo
구간 5 → 왼 0 · 오 4   비교 4   기준값이 놓인 자리 3 = lo
구간 4 → 왼 0 · 오 3   비교 3   기준값이 놓인 자리 4 = lo
구간 3 → 왼 0 · 오 2   비교 2   기준값이 놓인 자리 5 = lo
구간 2 → 왼 0 · 오 1   비교 1   기준값이 놓인 자리 6 = lo
```

`<=` 로 바꾸면 같은 값이 전부 작음 구역으로 가서 이번에는 오른쪽이 비고, 비교는 똑같이 28 번입니다. 그런데도
고치고 싶다면 구간을 셋(작음 · 같음 · 큼)으로 가르는 분할이 필요해요. 이 글의 두 구역 분할로는 이 입력이
최악으로 남습니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 **원소가 0 개나 1 개인 구간에서 즉시
반환**하는 첫 줄과, 배열 전체로 첫 부름을 하는 `quickSort` 뿐이에요. 빈 배열이면 `hi` 가 `-1` 이라 그 첫 줄이
받습니다.

```ts
export function quickSort(nums: number[]): number[] {
  sort(nums, 0, nums.length - 1);
  return nums;
}

function sort(arr: number[], lo: number, hi: number): void {
  // 원소가 0개 또는 1개면 이미 정렬이다.
  if (hi - lo < 1) return;

  // 중앙을 기준값으로 고르고 끝으로 옮긴다. 그래야 분할 루프가 끝 한 칸만 비켜 두면 된다.
  const pivotIdx = lo + Math.floor((hi - lo) / 2);
  [arr[pivotIdx], arr[hi]] = [arr[hi] as number, arr[pivotIdx] as number];
  const pivot = arr[hi] as number;

  // i 는 "작은 값이 놓일 다음 자리". j 는 읽는 자리.
  let i = lo;
  for (let j = lo; j < hi; j++) {
    if ((arr[j] as number) < pivot) {
      // ① 기준값보다 작다 — 작은 쪽 구역으로 보내고 그 구역을 한 칸 넓힌다.
      [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
      i++;
    }
    // ② 기준값보다 크거나 같다 — 그대로 둔다. j 만 나아간다.
  }

  // 기준값을 두 구역 사이(i)에 놓는다. 이 자리가 기준값의 최종 위치다.
  [arr[i], arr[hi]] = [arr[hi] as number, arr[i] as number];

  sort(arr, lo, i - 1);
  sort(arr, i + 1, hi);
}
```

<!--proof:final-calls-->

```text
quickSort([5, 2, 3, 1])             →  [1, 2, 3, 5]
quickSort([])                       →  []
quickSort([7])                      →  [7]
quickSort([2, 2, 2])                →  [2, 2, 2]
quickSort([-10, 5, -3, 0, 8, -1])   →  [-10, -3, -1, 0, 5, 8]
```

### 알아 두면 좋은 개념 — 선택 알고리즘 (quickselect)

전개의 T6 에서 분할이 끝나자 값 2 의 최종 자리가 인덱스 1 로 정해졌습니다. 그 뒤 코드는 양쪽 구간을 모두
부르는데, **`k` 번째로 작은 값 하나만** 필요하다면 어떨까요. 기준값의 자리가 `k` 와 같으면 이미 찾은
것이고, `k` 보다 크면 왼쪽만, 작으면 오른쪽만 따라가면 됩니다.

<!--proof:related-select-->

| k | k 번째로 작은 값 | 첫 분할 뒤 [1 2 3 5] 에서 할 일 |
| ---: | ---: | --- |
| 0 | 1 | 왼쪽 [1] 만 따라간다 |
| 1 | 2 | 이미 찾았다 — 더 가르지 않는다 |
| 2 | 3 | 오른쪽 [3 5] 만 따라간다 |
| 3 | 5 | 오른쪽 [3 5] 만 따라간다 |

<!--/proof-->

분할 뒤 한쪽을 버리는 이 절차를 **선택 알고리즘**(quickselect)이라고 해요. 정렬을 끝까지 하지 않고 자리
하나만 확정합니다. 정렬은 한 깊이에서 모든 구간을 보고 선택은 한 구간만 보므로, 반씩 갈리면 깊이마다
읽는 칸이 `n`, `n/2`, `n/4` … 로 줄어 합이 `2n` 을 넘지 않아요. 실제로 세어 보면 이렇습니다.

<!--proof:related-cost-->

| 입력 | n | k | 정렬 전체의 비교 | k 번째 하나만의 비교 | 2n |
| --- | ---: | ---: | ---: | ---: | ---: |
| 정렬된 0 … 49,999 | 50,000 | 25,000 | 684,481 | 99,965 | 100,000 |
| 가운데 칸 최악으로 만든 입력 | 2,000 | 1,999 | 1,999,000 | 1,999,000 | 4,000 |

반씩 갈리는 입력에서는 한쪽만 따라가는 비교가 2n 아래이고, 한쪽이 매번 비는 입력에서는 정렬 전체와 같은 n(n−1)/2 = 1,999,000 번입니다.

<!--/proof-->

한쪽이 매번 비면 버리는 쪽이 비어서 아무것도 줄지 않으므로, 선택도 퀵 정렬과 같은 최악을 가집니다. 이 이름을
다시 만나는 자리는 둘이에요. 「배열에서 k 번째로 큰 값」처럼 순위 하나만 묻는 문제, 그리고 중앙값을 기준값으로
써서 최악까지 선형으로 막는 median of medians 입니다. 후자는 기준값을 고르는 데 다시 선택을 씁니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 비교 횟수의 점화식이 어떻게 풀리는지, 무엇이
매 순간 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 비교만 되는 값 | 두 값 중 어느 쪽이 작은지만 정해지면 되고, 값의 범위를 요구하지 않는다 | 값에 하는 연산이 `<` 하나뿐이다 |
| 새 배열을 잡기 어렵다 | 입력이 메모리를 거의 다 쓰고 있거나 할당 자체의 비용이 크다 | 맞바꾸기만 하고 새 배열이 없다 |
| 평균이 중요하고 최악 한 번을 감당할 수 있다 | 응답 시간에 엄격한 상한이 필요하지 않다 | 최악 `n(n−1)/2` 를 코드가 막지 않는다 |
| 같은 값의 입력 순서를 지킬 필요가 없다 | 값에 딸린 다른 정보가 없거나, 있어도 순서가 상관없다 | 맞바꾸기가 같은 값의 앞뒤를 바꿀 수 있다 |

#### 문제에서 이것을 떠올리게 하는 단서

- 지문에 **「제자리에서 정렬하라」**, **「추가 배열을 쓰지 말라」**, 「메모리 제한이 입력 크기와 비슷하다」가
  보입니다.
- 입력이 수만에서 수백만 규모이고 **평균 성능만** 요구합니다.
- **「k 번째로 작은 값」** 하나만 필요합니다. 분할을 한쪽만 따라가면 선택 알고리즘이 됩니다.

반대로 **「최악에도 몇 초 안에」**, 「동점이면 입력 순서대로」 같은 문구가 있으면 이 단서는 해당하지 않습니다.
그때는 최악까지 `Θ(n log n)` 을 보장하고 같은 값의 순서를 지키는 병합 정렬을 골라야 해요.

#### 실제로 쓰이는 곳

- **Go 표준 라이브러리 `sort`** — pdqsort(pattern-defeating quicksort)를 씁니다. 분할이 치우치는 것을
  감지하면 힙 정렬로 바꿔 최악을 `Θ(n log n)` 으로 막아요.
  ([`src/sort/zsortfunc.go`](https://cs.opensource.google/go/go/+/master:src/sort/zsortfunc.go), 조회 2026-08-19)
- **C 표준 라이브러리 `qsort`** — 이름은 퀵 정렬에서 왔지만, 이름만 보고 퀵 정렬이라 여기면 안 됩니다. 지금의
  glibc 구현은 퀵 정렬을 쓰지 않아요. 병합 정렬(`qsort_r_mergesort`)로 정렬하고, 보조 버퍼를 잡지 못하면
  재귀 없는 힙 정렬(`heapsort_r`)로 바꿔 정렬합니다.
  ([glibc `stdlib/qsort.c`](https://sourceware.org/git/?p=glibc.git;a=blob;f=stdlib/qsort.c), 조회 2026-10-01)

`Array.prototype.sort` 는 V8 에서 **TimSort**(병합 정렬 계열)라 여기 들지 않아요. 명세가 안정성을 요구하기
때문입니다.

#### 경쟁 설계와의 대조

같은 목표를 노리는 **다른 절차**가 있어요. **병합 정렬**입니다. 구간을 자리로 반씩 나눠 각각 정렬한 다음 둘을
합치고, 합칠 때 새 배열을 잡습니다. 최악에도 `Θ(n log n)` 이고 같은 값의 입력 순서를 지켜서 오히려 더 강한
약속을 해요.

같은 입력 `[23 4 91 8 15 42 7 66 30 1 58 12 77 25 3 49]`(`n = 16`, 손으로 고른 고정 배열)에 둘을 실행하고 **비교
횟수와 새로 잡는 칸 수**를 셌습니다. 전개에 쓰는 `[5 2 3 1]`(`n = 4`)을 그대로 쓰지 않은 이유는 하나예요.
그 크기에서는 비교가 **4 대 5** 라 한 번밖에 안 갈려 계수가 상수에 묻힙니다.

| 설계 | 비교 횟수 | 새로 잡는 칸 |
| --- | --- | --- |
| 퀵 정렬 (이 가이드) | 52 | **0** |
| 병합 정렬 | **49** | 64 |

**비교는 병합 정렬이 적습니다.** 49 대 52 예요. 퀵 정렬이 내주는 것이 그 비교 세 번이고, 받는 것이 새 칸을
안 쓰는 것입니다. 병합 정렬은 합치는 단계마다 새 배열을 잡아 **64 칸**을 쓰고, 퀵 정렬은 **0 칸**으로
끝나요. 항목 넷으로 나눠 적으면 이렇습니다.

| 항목 | 퀵 정렬 | 병합 정렬 | 유리한 쪽 |
| --- | --- | --- | --- |
| 비교 횟수 | 52 | 49 | 병합 정렬 |
| 새로 잡는 칸 | 0 | 64 | 퀵 정렬 |
| 최악 보장 | `n(n−1)/2` | `n⌈log₂ n⌉` 규모 | 병합 정렬 |
| 같은 값의 입력 순서 | 안 지킨다 | 지킨다 | 병합 정렬 |

**우열이 반대가 되는 조건이 분명합니다.** 메모리가 넉넉하고 최악 응답 시간에 상한이 필요하거나 같은 값의
순서를 지켜야 하면 병합 정렬이 답이에요. 새 배열을 쓸 수 없고 평균만 요구하면 퀵 정렬입니다. 어느 쪽이
우월한지가 아니라 **무엇을 내줄 수 있는가**가 선택을 정해요.

### 수식 정의와 유도

칸이 `n` 개인 구간을 정렬하는 비교 횟수를 $T(n)$ 이라 하고, 그 구간의 분할이 기준값을 뺀 나머지를 크기 $k$
와 $n-k-1$ 인 두 구간으로 나눈다고 둡니다. 분할 자체는 기준값을 뺀 $n-1$ 칸을 한 번씩 읽으므로 $n-1$ 번
비교해요.

$$T(n) = T(k) + T(n-k-1) + (n-1), \qquad T(0) = T(1) = 0$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $n$ | 그 부름이 받은 구간의 칸 수 | $0 \le n$ |
| $k$ | 분할 뒤 왼쪽 구간의 칸 수 | $0 \le k \le n-1$ |
| $n-k-1$ | 오른쪽 구간의 칸 수. 가운데 한 칸은 기준값이라 빠진다 | $0 \le n-k-1$ |

```text
n 칸을 세 덩어리로 나눈다

  |---- k 칸 ----|- 1 칸 -|---- n-k-1 칸 ----|
     왼쪽 구간     기준값     오른쪽 구간
```

**정의를 작은 값에 넣어 검산해 봅시다.** $n = 8$ 에 두 극단을 넣습니다. 절반씩은 $k = \lfloor (n-1)/2
\rfloor$, 한쪽이 빔은 $k = 0$ 이에요. 식을 한 번씩 펴 나가며 분할마다 비교 $n-1$ 을 더합니다.

<!--proof:math-check-->

| 갈림 | 펴 나간 분할 (n → k · n−k−1) | 분할마다 n−1 의 합 |
| --- | --- | --- |
| 절반씩 | 8 → 3 · 4 · 3 → 1 · 1 · 4 → 1 · 2 · 2 → 0 · 1 | 7 + 2 + 3 + 1 = 13 |
| 한쪽이 빔 | 8 → 0 · 7 · 7 → 0 · 6 · 6 → 0 · 5 · 5 → 0 · 4 · 4 → 0 · 3 · 3 → 0 · 2 · 2 → 0 · 1 | 7 + 6 + 5 + 4 + 3 + 2 + 1 = 28 |

두 합은 정렬된 여덟 칸을 가운데 칸으로 실행해 센 13 번, 첫 칸으로 실행해 센 28 번과 같습니다.

<!--/proof-->

점화식을 그대로 코드로 옮기면 같은 두 수가 나옵니다. 식의 $k$ 는 코드에서 `k` 라는 함수로 넘기고, 그 함수가
갈림의 모양을 정해요.

<!--proof:math-code-->

```ts
const T = (n: number, k: (n: number) => number): number =>
  n <= 1 ? 0 : T(k(n), k) + T(n - k(n) - 1, k) + (n - 1);

T(8, (n) => Math.floor((n - 1) / 2)); // 절반씩    → 13
T(8, () => 0); //                        한쪽이 빔 → 28
```

**이제 닫힌 형태를 유도합니다.** 한쪽이 비는 경우부터 풀면 항이 하나씩 줄어드는 단순한 합이에요.

```text
T(n) = T(n-1) + (n-1)
     = T(n-2) + (n-2) + (n-1)          T(n-1) 을 같은 식으로 한 번 더 편다
     = T(n-3) + (n-3) + (n-2) + (n-1)
     …
     = T(1) + 1 + 2 + … + (n-1)        T(1) = 0 이라 여기서 멈춘다
```

$$T(n) = \sum_{m=1}^{n-1} m = \frac{n(n-1)}{2}$$

절반씩 갈리는 경우는 깊이마다 비교를 더합니다. 한 깊이의 구간들은 겹치지 않으므로 그 깊이의 비교 합은 $n$
이하이고, 구간 크기가 깊이마다 절반 이하로 줄어 깊이가 $\lceil \log_2 n \rceil$ 개를 넘지 않아요. 두 값을
곱한 것이 상한입니다.

```text
깊이 0      구간 1 개, 크기 n           비교 ≤ n
깊이 1      구간 2 개, 크기 합 ≤ n      비교 ≤ n
깊이 2      구간 4 개, 크기 합 ≤ n      비교 ≤ n
  …
깊이 ⌈log₂ n⌉ 에 이르면 구간 크기가 1 이하라 비교가 없다
```

$$T(n) \le n \lceil \log_2 n \rceil = O(n \log n)$$

아래쪽 경계도 같은 차수입니다. 깊이 $d$ 에는 구간이 많아야 $2^d$ 개 있고, 그 위 깊이들이 놓은 기준값이 많아야
$2^d - 1$ 개 빠졌어요. 절반씩 갈리면 깊이 $\log_2 n - 2$ 까지는 어느 구간도 칸이 하나 이하로 끝나지 않으므로,
그 깊이의 칸은 $n - (2^d - 1)$ 개 이상이고 비교는 구간마다 하나씩 빠져 $n - 2^{d+1} + 1$ 번 이상입니다.
$d \le \log_2 n - 2$ 이면 $2^{d+1} \le n/2$ 라 이 값이 $n/2$ 이상이고, 그런 깊이가 $\log_2 n - 1$ 개이므로
$T(n) \ge \tfrac{n}{2}(\log_2 n - 1)$ 입니다. 위아래가 같은 차수라 $T(n) = \Theta(n \log n)$ 이에요.

**마지막으로 계수입니다.** $n = 8$ 과 $n = 50{,}000$ 을 넣어 계산합니다. 절반씩 갈릴 때는 점화식을 그대로
실행했어요.

<!--proof:math-closed-->

| n | 절반씩 갈릴 때 T(n) | n log₂ n (반올림) | 한쪽이 빌 때 n(n−1)/2 |
| ---: | ---: | ---: | ---: |
| 8 | 13 | 24 | 28 |
| 50,000 | 684,481 | 780,482 | 1,249,975,000 |

n = 50,000 에서 절반씩 갈릴 때의 T(n) 은 정렬된 입력을 정본으로 센 비교와 같고, 한쪽이 빌 때는 그 약 1,826 배입니다.

<!--/proof-->

오른쪽 열이 낯익습니다. 파트 1 에서 선택 정렬의 비교로 센 값과 **정확히 같아요.** 분할이 한쪽으로만 치우치면
퀵 정렬은 그 단순한 방법으로 되돌아가고, 절반씩 갈리면 그 1,800 분의 1 쯤으로 내려갑니다. 식이 보여 주는
것은 그 차이가 전부 $k$ 하나에서 나온다는 것입니다.

### 불변식 — 분할 루프가 한 바퀴를 마칠 때마다 `i` 왼쪽은 기준값보다 작고 `i` 부터 `j` 까지는 기준값 이상이다

파트 1 에서 코드가 동작하는 것을 열세 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 문장으로 세우고, 그것이 실제로 유지되는지 확인해 봅시다.

> 분할 루프가 한 바퀴를 마친 시점마다, `arr[lo..i-1]` 의 모든 값이 `pivot` 보다 작고 `arr[i..j]` 의 모든
> 값이 `pivot` 이상입니다.

```text
lo          i            j           hi
 |-- 작음 --|--- 큼 ----|-- 아직 --| pivot |
 이 두 구역에 대한 문장이 매 바퀴 참이다
```

「한 바퀴를 마친 시점마다」가 중요합니다. 루프가 끝난 뒤 한 번만 참인 것이 아니라 **`j` 가 한 칸 나아갈
때마다** 참이라는 뜻이에요. 그래야 다음 바퀴가 그 성질을 그대로 이어받습니다.

**출발점부터 봅시다.** 루프에 들어가기 전 `i = lo` 라 작음 구역이 비어 있고, 아직 아무 칸도 읽지 않아 큼
구역도 비어 있습니다. 빈 구역에 대한 「모든 값이 …」는 참이에요. 그 뒤 한 바퀴마다 `arr[j]` 를 보고 두 갈래
중 하나를 실행합니다.

| 읽은 값 | 하는 일 | 두 문장이 유지되는 근거 |
| --- | --- | --- |
| `arr[j] < pivot` | `arr[i]` 와 맞바꾸고 `i` 를 늘린다 | 작음 구역에 새로 들어간 값은 `arr[j]` 이고 조건상 `pivot` 보다 작다. `arr[i]` 에 있던 값은 직전까지 큼 구역의 첫 값이라 `pivot` 이상이고, 그 값이 간 `j` 자리는 큼 구역의 끝이다 |
| `arr[j] ≥ pivot` | 아무것도 안 바꾼다 | 큼 구역이 오른쪽으로 한 칸 늘어날 뿐이고, 새로 들어온 값이 `pivot` 이상이다 |

둘이 전부입니다. 수 둘을 `<` 로 비교하는 데 세 번째 결과는 없어요. 전개의 입력에서 바퀴마다 두 구역을 적고,
작은 입력 전부에서도 확인했습니다.

<!--proof:invariant-steps-->

| 바퀴 | 읽은 값 | arr[lo..i-1] | arr[i..j] | 두 문장 |
| --- | --- | --- | --- | --- |
| j = 0 | 5 < 2 거짓 | [ ] | [5] | 참 |
| j = 1 | 1 < 2 참 | [1] | [5] | 참 |
| j = 2 | 3 < 2 거짓 | [1] | [5 3] | 참 |

칸 1 개부터 7 개까지 모든 순열의 모든 바퀴 76,406 번에서도 두 문장을 확인했고, 거짓인 바퀴는 0 번입니다.

<!--/proof-->

`j` 가 `hi` 에 이르면 `arr[lo..hi-1]` 전부를 읽었고 두 문장이 그 전체에 대해 참입니다. 그 시점에 `arr[i]` 와
`arr[hi]` 를 맞바꾸면 기준값이 두 구역 사이로 들어가요.

```text
루프 끝    [작음…][큼…][pivot]      i 가 두 구역의 경계
맞바꾼 뒤  [작음…][pivot][큼…]      pivot 의 최종 자리
```

왼쪽은 전부 `pivot` 미만, 오른쪽은 전부 `pivot` 이상이므로 이 자리가 정렬이 끝난 뒤의 자리와 같습니다. 전체
정렬이 옳다는 것은 구간 크기에 대한 귀납으로 이어져요. 기저는 칸이 하나 이하인 구간이고, 비교할 것이 없어
그대로 정렬돼 있습니다. 단계는 칸이 `n` 개인 구간인데, 두 구간이 각각 `n` 보다 작아 귀납 가정으로 정렬되고,
왼쪽 값은 전부 기준값보다 작고 오른쪽 값은 전부 기준값 이상이라 이어 놓은 전체가 정렬됩니다.

**경계에 있는 입력도 확인하고 갑시다.** 아래 다섯 줄이 이 함수가 받을 수 있는 모양의 끝입니다.

<!--proof:invariant-edges-->

| 입력 | 처리되는 곳 | 결과 |
| --- | --- | --- |
| 빈 배열 `[]` | `hi - lo = -1 < 1` → 즉시 반환 | `[]` |
| 원소 하나 `[7]` | `hi - lo = 0 < 1` → 즉시 반환 | `[7]` |
| 원소 둘 `[2 1]` | pivotIdx = 0 · 기준값 2 가 인덱스 1 에 · 비교 1 번 | `[1 2]` |
| 전부 같음 `[2 2 2 2 2]` | pivotIdx = 2 · 기준값 2 가 인덱스 0 에 · 비교 10 번 | `[2 2 2 2 2]` |
| 음수가 섞임 `[-10 5 -3]` | pivotIdx = 1 · 기준값 5 가 인덱스 2 에 · 비교 3 번 | `[-10 -3 5]` |

<!--/proof-->

빈 배열과 원소 하나는 첫 줄에서 끝납니다. 값이 전부 같으면 `arr[j] < pivot` 이 한 번도 참이 아니라 `i` 가
`lo` 에 머물러, 기준값이 맨 앞으로 가고 비교가 가장 많아요. 음수도 비교 연산자만 쓰므로 부호와 무관합니다.

**이제 깨뜨려 봅시다.** 불변식을 지키던 줄이 어느 것인지는 지워 보면 확인됩니다. 작은 값을 왼쪽으로 맞바꾸는
동작은 그대로 두고, **그 구역을 넓히는 `i++` 한 줄만** 없앱니다.

```ts
if ((arr[j] as number) < pivot) {
  [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
  // i++;   ← 이 줄만 지운다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-i-inc-->

| 입력 | 바른 코드 | `i++` 를 지운 코드 |
| --- | --- | --- |
| [5 2 3 1] | [1 2 3 5] | [2 3 5 1] |
| [5 1 1 2 0 0] | [0 0 1 1 2 5] | [1 2 1 0 0 5] |
| [-10 5 -3 0 8 -1] | [-10 -3 -1 0 5 8] | [-3 0 -1 8 5 -10] |

세 벌 모두 결과가 오름차순이 아닙니다.

<!--/proof-->

`i` 가 `lo` 에 머무르니 작은 값을 찾을 때마다 **같은 자리에** 맞바꿔 넣습니다. 먼저 넣어 둔 작은 값이 그
자리에서 다른 칸으로 옮겨지고, 분할이 끝났을 때 `i` 는 작음 구역의 끝이 아니게 돼요. 불변식의 앞 문장(「`arr[lo..i-1]`
의 모든 값이 `pivot` 보다 작다」)은 빈 구역이라 참으로 남지만, 뒷문장이 깨집니다. 작은 값이 `i` 자리에 있는데
`i` 부터가 큼 구역이라고 믿고 있으니까요. `[5 2 3 1]` 의 첫 분할을 따라가 봅니다.

<!--proof:invariant-mutant-step-->

```text
[5 1 3 2]   기준값 2 를 끝으로 뺀 뒤
[1 5 3 2]   j=1  1 < 2 참 → arr[0] 과 arr[1] 을 맞바꾼다 · i 는 0 그대로
[2 5 3 1]   루프 끝 i = 0 — arr[0] 과 arr[3] 을 맞바꾼다
기준값 2 가 인덱스 0 에 갔는데 오른쪽 끝의 1 이 그보다 작다
```

j=1 바퀴를 마친 시점에 `i = 0` 이라 큼 구역 `arr[i..j]` 는 `[1 5]` 인데, 1 이 기준값 2 보다 작습니다. 그
순간 뒷문장이 거짓이 되었고, 마지막 맞바꾸기가 작은 값 1 을 기준값 오른쪽 끝으로 보냈어요.

### 비용 계산

비교 횟수가 어디서 나오는지를 전개의 값으로 세고, 케이스와 경계를 갈라 적은 다음, 최악을 실제로 내는 입력을
만들어 봅니다.

#### 비용을 세는 과정

한 번의 `sort(lo, hi)` 부름이 하는 비교는 분할 루프뿐이고, 그 횟수는 `hi − lo` 입니다. 전개의 걸음으로 세면
이렇습니다.

<!--proof:perf-derive-->

```text
T1               구간 [0,3] 크기 4   비교 3 번   T3 · T4 · T5
T8               구간 [2,3] 크기 2   비교 1 번   T10
T7 · T12 · T13   즉시 반환           비교 0 번
                                     합 4 번
```

그러니 전체 비교 횟수는 **원소가 둘 이상인 부름마다 (구간 크기 − 1) 을 더한 값**입니다. 같은 깊이의 부름은
겹치지 않는 구간을 맡으므로 한 깊이의 비교 합은 `n` 이하이고, 전체는 **깊이 수 × n** 을 넘지 않아요. 깊이
수는 갈림이 정합니다. 반씩 갈리면 `⌈log₂ n⌉`, 한쪽이 매번 비면 `n − 1` 이에요.

여기서 센 것은 **비교 횟수만**입니다. 맞바꾸기는 루프 한 바퀴에 많아야 한 번이고 부름마다 두 번(기준값
옮기기 · 놓기)이 더해질 뿐이에요. 원소가 둘 이상인 부름은 기준값을 하나씩 확정하므로 `n` 번 이하이고, 즉시
반환하는 부름은 그 부름마다 많아야 둘이라 부름 수도 `n` 규모입니다. 그래서 지배항이 바뀌지 않아요. 새 배열은
잡지 않지만 **재귀 깊이**만큼 호출 스택이 따로 듭니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (매번 반씩 갈린다) | `O(n log n)` | `Θ(n log n)` |
| **평균적인 경우** (모든 순열이 같은 확률) | `O(n log n)` | `Θ(n log n)` |
| **최악의 경우** (매번 한쪽이 빈다) | `O(n²)` | `Θ(n²)` — 실제로 도달한다 |

평균은 작은 `n` 에서 순열을 전부 넣어 확인할 수 있습니다.

<!--proof:perf-perm-->

| n | 순열 수 | 가장 적을 때 | 평균 | 가장 많을 때 | 가장 많은 순열 수 | n log₂ n |
| ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 8 | 40,320 | 13 | 16.92 | 28 = 8·7/2 | 128 | 24 |

정본을 모든 순열에 실행해 센 값이고, 평균은 순열마다 같은 확률을 준 평균입니다.

<!--/proof-->

최악에서 `Θ(n²)` 이라고 쓸 수 있는 것은 그 값을 **실제로 내는 입력이 있기** 때문이고, 그 입력은 아래
「최악을 만드는 입력」에서 만듭니다.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리는 없고, 비교에 맞바꾸기와 부름 비용이 붙으며, 새
배열은 없지만 재귀 스택이 따로 듭니다.

```text
시간   Θ(비교) + Θ(맞바꾸기) + Θ(부름 수)
       비교가 지배한다 — 평균 Θ(n log n), 최악 Θ(n²)
공간   새 배열 0 칸 + 재귀 스택 Θ(깊이)
       깊이는 반씩 갈리면 Θ(log n), 한쪽이 매번 비면 Θ(n)
```

칸 50,000 개의 최악이면 재귀 깊이가 49,999 까지 내려갑니다(전체 컨셉의 표). 그 입력을 Bun 1.3.12 에서
정본에 넣어 실행하면 정렬을 끝내지 못하고 `RangeError: Maximum call stack size exceeded.` 로 멈춰요. 같은 방법으로
만든 칸 10,000 개 최악 입력은 끝까지 정렬했고, 20,000 개에서는 같은 오류로 멈췄습니다.

**보장의 종류가 하나 섞여 있습니다.** 최악은 최악 보장이지만 평균은 기댓값이고, 그 기댓값이 **무엇에 대한
것인지**가 이 구현에서 중요해요. 코드에 난수가 하나도 없고 기준값을 가운데 칸에서 정해진 대로 고릅니다. 그래서
같은 입력을 두 번 넣으면 늘 같은 횟수가 나와요. 여기서 말하는 평균은 **모든 순열이 같은 확률로 들어온다는
입력 분포 가정 아래의 평균**이고, 구현이 만드는 무작위성에 대한 기댓값이 아닙니다. 이 구분이 갈리는 자리는
**공격**입니다. 절차를 아는 사람은 최악 입력을 계산해서 넣을 수 있어요. 기준값을 무작위로 고르는 구현이면
평균이 입력이 아니라 구현의 난수에 대한 기댓값이 되어 어떤 입력에도 성립합니다.

#### 최악을 만드는 입력

「정렬된 배열이 최악」이라는 말은 이 구현에 해당하지 않습니다. 여덟 칸에 여러 입력을 넣어 실제로 세어 보면
이렇습니다.

<!--proof:worst-input-->

| 입력 (n = 8) | 배열 | 비교 |
| --- | --- | ---: |
| 가운데 칸 최악으로 만든 입력 | [2 6 4 0 1 3 5 7] | 28 |
| 순열을 사전 순으로 돌며 처음 만난 최악 | [0 3 5 7 1 4 2 6] | 28 |
| 역순 | [7 6 5 4 3 2 1 0] | 15 |
| 정렬된 | [0 1 2 3 4 5 6 7] | 13 |
| 전부 같음 | [2 2 2 2 2 2 2 2] | 28 |

최악은 8 · 7 / 2 = 28 번이고, 정렬된 입력은 최악이 아닙니다.

<!--/proof-->

첫 줄의 입력은 이렇게 만들었습니다. 절차가 어느 칸을 기준값으로 고를지 미리 알고 있으므로, **부름마다 그
가운데 칸에 남은 값 중 가장 작은 값을 줍니다.** 그러면 비교가 한 번도 참이 되지 않아 `i` 가 `lo` 에 머물고,
기준값이 구간 맨 앞으로 가서 오른쪽 구간만 한 칸 줄어 남아요. 맞바꾸기가 칸을 어디로 옮기는지도 절차가 정해
두었으니, 원래 자리 번호를 따라가면 각 원래 자리에 줄 값이 정해집니다. 그렇게 만든 입력을 정본에 넣어 부름마다
기록했습니다.

<!--proof:worst-built-->

| 부름 | 그때의 구간 | 가운데 칸 | 가운데 칸의 값 | 구간의 최솟값 |
| --- | --- | --- | ---: | ---: |
| sort(0,7) | [2 6 4 0 1 3 5 7] | 인덱스 3 | 0 | 0 |
| sort(1,7) | [6 4 7 1 3 5 2] | 인덱스 4 | 1 | 1 |
| sort(2,7) | [4 7 2 3 5 6] | 인덱스 4 | 2 | 2 |
| sort(3,7) | [7 6 3 5 4] | 인덱스 5 | 3 | 3 |
| sort(4,7) | [6 4 5 7] | 인덱스 5 | 4 | 4 |
| sort(5,7) | [7 5 6] | 인덱스 6 | 5 | 5 |
| sort(6,7) | [6 7] | 인덱스 6 | 6 | 6 |

[2 6 4 0 1 3 5 7] 을 정본에 넣어 부름마다 기록했습니다. 가운데 칸의 값이 모든 부름에서 구간의 최솟값이고, 비교는 28 번입니다.

<!--/proof-->

같은 방법이 어떤 `n` 에도 통합니다. 전체 컨셉의 칸 50,000 개 최악 입력도 이렇게 만든 것이에요. **가운데
칸을 고르는 것은 우연히 정렬된 입력을 막을 뿐, 의도적으로 만든 입력은 막지 못합니다.** 값이 전부 같은 입력도
같은 28 번을 내는데, 그쪽은 의도하지 않아도 실무에서 흔히 들어와요. Go 의 pdqsort 가 분할이 치우치는 것을
감지해 힙 정렬로 바꾸는 것이 이 자리를 막는 방법입니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 바퀴 하나가 자리 하나만 정하던 것을 **값으로 둘로 가르는
것**으로 바꿨고, 분할이 정확한 답을 주는 근거는 두 구역에 대한 불변식이며, 비용은 갈림의 균형이 정합니다.

```text
가운데 칸을 기준값으로 → 한 번 읽으며 작은 값을 왼쪽으로 → 기준값을 경계에 놓는다 → 양쪽을 되풀이
                          i 가 두 구역의 경계를 지킨다      갈림이 반씩이면 n log n, 한쪽이 비면 n(n−1)/2
```

먼저 답이 붙는 문제 하나입니다. 전개의 T3 에서 `5 < 2` 가 거짓이라 `i` 가 0 에 머물렀어요. 만약 T3 에서 5 를
작은 값으로 잘못 보고 ① 로 갔다면, 첫 분할이 끝난 배열과 기준값 2 의 자리는 무엇이 되었을까요?

제자리 맞바꿈한 뒤 `i` 가 2 가 되기 때문이에요. 불변식의 앞 문장이 깨진 것입니다. `arr[lo..i-1]` 에 5 가

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Quick Sort

풀 파일: [`quicksort.ts`](./quicksort.ts) · 테스트: [`quicksort.test.ts`](./quicksort.test.ts) · 실행: `bun test src/algorithms/sorting/quicksort/quicksort.test.ts`

#### 한 줄 요약

> 정수 배열 `nums`를 받아 **오름차순으로 정렬된 새 배열**을 반환한다.

#### 스토리

물류 창고 시스템. 오늘 입고된 **`N`개 택배 상자**의 무게(g)가 무작위 순서로 배열 하나에 담겨 들어왔다.
무게별로 선반을 정리해야 하는 작업자가 말한다. "가장 가벼운 것부터 차례로 줄 세워 주세요."

같은 무게의 상자가 여럿이어도 개수는 그대로 보존되어야 한다.
빈 배열이 들어오면 빈 배열을 돌려주면 된다.

#### 함수 인터페이스

```ts
export function quickSort(nums: number[]): number[];
```

- `nums` — 정렬할 정수 배열
- 반환 — `nums`의 모든 원소를 오름차순으로 정렬한 배열

#### 제약 조건

- $1 \leq N \leq 50{,}000$ — 여기서 $N$은 배열 `nums`의 길이다.
- $-50{,}000 \leq \text{nums}[i] \leq 50{,}000$ — 각 원소는 이 범위의 정수이며 음수일 수 있다.
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

배열 `nums`를 **오름차순(작은 값 → 큰 값)** 으로 정렬한 결과를 반환한다. 다음 규칙을 따른다.

- **결과 배열은 오름차순.** $\text{result}[0] \leq \text{result}[1] \leq \cdots \leq \text{result}[N-1]$을 만족해야 한다.
- **원소 집합 보존.** 반환 배열의 다중집합(multiset)은 입력 `nums`의 다중집합과 같아야 한다.
- **빈 배열 입력.** `nums`가 빈 배열이면 빈 배열을 반환한다.
- **중복 허용.** 같은 값이 여럿이면 그 개수 전부 결과에 포함된다.
- 함수가 입력 `nums`를 제자리에서 변경해도 된다.

#### 예시

```ts
quickSort([5, 2, 3, 1]);          // [1, 2, 3, 5] — 작은 순으로 나열
quickSort([5, 1, 1, 2, 0, 0]);    // [0, 0, 1, 1, 2, 5] — 중복은 개수 그대로 보존
quickSort([-10, 5, -3, 0, 8]);    // [-10, -3, 0, 5, 8] — 음수 포함 시 음수가 앞에
quickSort([1]);                   // [1] — 원소가 하나(경계: N=1)
quickSort([3, 3, 3]);             // [3, 3, 3] — 전부 동일(경계: 모든 값 같음)
quickSort([5, 4, 3, 2, 1]);       // [1, 2, 3, 4, 5] — 역순 입력
```
