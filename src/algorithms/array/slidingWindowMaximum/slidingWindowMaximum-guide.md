# slidingWindowMaximum — 창 밖으로 나간 자리는 앞에서, 답이 될 수 없는 자리는 뒤에서 버리면 창마다 최댓값이 맨 앞에 남는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 창마다 칸을 다시
읽는 방법에서 출발해 단조 덱에 이르고, 단조 덱을 단계마다 값으로 푼 뒤, 실제로 동작하는 코드를 한 조각씩
만듭니다.

### 전체 컨셉

정수 배열 `nums` 와 창의 칸 수 `k` 를 받아, 크기 `k` 인 창이 왼쪽에서 오른쪽으로 한 칸씩 옮겨 가며 지나는
**모든 위치의 최댓값**을 차례로 구합니다. 여기서 **창**은 배열에서 이어진 `k` 칸이에요. 창의 위치가
`N − k + 1` 개이므로 답도 그만큼 나옵니다. `nums = [1 3 -1 -3 5 3 6 7]` · `k = 3` 에서 창마다 괄호를 치고, 그
창의 최댓값이 있는 칸에 ▲ 를 달았어요.

<!--fig:concept-windows-->
![창 여섯 개와 창마다의 최댓값](./figs/concept-windows.svg)

이웃한 두 창은 `k − 1` 칸을 함께 씁니다. 창이 한 칸 옮겨 갈 때 달라지는 것은 **양 끝 둘뿐**이에요 — 오른쪽
끝에서 한 칸이 들어오고, 왼쪽 끝에서 한 칸이 나갑니다. 들어오는 칸은 다루기 쉽습니다. 들어온 값이 지금까지의
최댓값보다 크면 그것이 새 최댓값이니까요. 어려운 것은 나가는 칸이에요. **나간 칸이 그 창의 답이었으면, 남은
칸 중 누가 답을 이어받는지 그 자리에서 알 수 없습니다.**

그래서 이 글의 절차는 답 하나가 아니라 **앞으로 답이 될 수 있는 자리 전부**를 들고 다닙니다. 무엇이 답이 될
수 없는지는 규칙 하나로 정해져요. 지금 자리 `u` 를 읽었는데, 그보다 왼쪽에 있으면서 값이 더 작은 자리 `t` 가
남아 있으면 `t` 는 앞으로 어느 창에서도 답이 될 수 없습니다. 앞으로 답을 낼 창 중 `t` 를 담은 창은
`t < u` 이므로 `u` 도 함께 담고, 그 창에서는 `u` 가 `t` 보다 크기 때문이에요. 자리 4 의 값 5 를 읽은 시점에 아직
답을 안 낸 창과, 그 창이 자리 2(값 -1)와 자리 4 를 담는지 세어 봤습니다.

<!--proof:concept-dominated-->

| 아직 답을 안 낸 창 | 자리 2 포함 | 자리 4 포함 | 그 창의 최댓값 |
| --- | --- | --- | ---: |
| [2,4] | 예 | 예 | 5 |
| [3,5] | 아니오 | 예 | 5 |
| [4,6] | 아니오 | 예 | 6 |
| [5,7] | 아니오 | 아니오 | 7 |

자리 2 를 담는 창은 [2,4] 하나이고, 그 창에는 자리 4 도 들어 있어 최댓값이 5 이상입니다. 값 -1 인 자리 2 는 어느 창의 답도 되지 못합니다.

<!--/proof-->

이 규칙으로 걸러 내고 남은 자리를 읽은 차례대로 줄에 담으면, 줄의 왼쪽 끝(**앞**)에서 오른쪽 끝(**뒤**)으로 갈수록
값이 **커지지 않습니다.** 커지는 짝이 있었다면 왼쪽 것이 이미 걸러졌을 테니까요. 이 줄에 필요한 일은 셋입니다
— 창 밖으로 나간 자리를 **앞**에서 빼고, 지금 값보다 작은 자리를 **뒤**에서 빼고, 지금 자리를 **뒤**에 넣는
것. 양 끝에서 넣고 빼는 자료구조를 덱이라 부르고, 값이 한 방향으로만 가는 덱을 **단조 덱**이라고 부릅니다.
여덟 자리를 읽을 때마다 단조 덱과 답 배열 `result` 를 그렸어요.

<!--fig:concept-deque-->
![여덟 자리를 읽을 때마다의 단조 덱 — cand 의 값 줄이 앞에서 뒤로 커지지 않는다](./figs/concept-deque.svg)

`cand` 줄이 단조 덱에 든 자리 번호이고 왼쪽 끝이 앞, 오른쪽 끝이 뒤예요. 그 아래 `cand 의 값` 줄이 그 자리의
값이고, 곁말이 그 값을 앞에서 뒤로 늘어놓은 것입니다. 여덟 장 모두 곁말의 값이 커지지 않아요. 그리고 창이 다
찬 장마다 **단조 덱의 앞 자리 값이 곧 그 창의 답**입니다. 값이 앞에서 뒤로 커지지 않으니 가장 큰 것이 앞에
있고, 창 밖으로 나간 자리는 이미 앞에서 빠졌으니까요. `i=4` 장이 앞과 뒤에서 함께 빼는 장이에요.

자리마다 한 번 들어가고 많아야 한 번 나오므로 전체 비용은 배열을 한 번 지나는 것과 같은 규모인 `O(N)` 이고,
창의 칸 수 `k` 는 거기 들어가지 않습니다. 여기서 `N` 은 배열의 길이예요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **배열의 인덱스.** `nums[i]` 가 `i` 번째 값이고 `i` 는 0 부터 셉니다. 이 글은 인덱스를 「자리」라고도
  부릅니다.
- **창과 그 위치.** 이 글은 왼쪽 끝이 `a` 이고 오른쪽 끝이 `b` 인 창을 `[a,b]` 로 적습니다. 칸 수가 `k` 이면
  `b = a + k − 1` 이에요. 창을 쥐고 옮기는 다른 절차는
  [`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-guide.md) 이 다룹니다.
- **단조 스택.** 지금 값보다 작은 꼭대기를 꺼내고 나서 넣어, 쌓인 값이 한 방향으로만 가게 유지하는 스택입니다.
  이 글의 단조 덱은 그 스택에 **앞에서 빼는 일 하나**를 더한 것이에요. 흐릿하면
  [`nextGreaterElement`](../nextGreaterElement/nextGreaterElement-guide.md) 를 먼저 봅니다.
- **덱.** 양쪽 끝에서 넣고 뺄 수 있는 자료구조입니다. 앞에 넣기 · 뒤에 넣기 · 앞에서 빼기 · 뒤에서 빼기 · 양 끝
  보기가 각각 한 번에 끝나요. 흐릿하면 [`deque`](../../../data-structures/linear/deque/deque-guide.md) 를 먼저
  봅니다.
- **`O(N)` 표기.** 비용이 입력 길이에 비례한다는 뜻입니다.

「구간마다 무엇을 구한다」는 말만으로는 절차가 정해지지 않습니다. **구간의 길이가 고정인가**와 **무엇을
묻는가**가 함께 있어야 해요. 같은 배열로 비슷한 물음 넷에 답하면 이렇게 갈립니다.

<!--proof:prereq-questions-->

| 물음 | [1 3 -1 -3 5 3 6 7] 의 답 | 이 글에서 |
| --- | --- | --- |
| 길이 3 인 창마다 최댓값 | [3 3 5 5 6 7] | 다룬다 |
| 길이 3 인 창마다 최솟값 | [-1 -3 -3 -3 3 3] | 부등호만 뒤집는다 |
| 길이 3 인 창마다 합 | [3 -1 1 5 14 16] | 다루지 않는다. 모든 칸이 합에 들어간다 |
| 자리마다 오른쪽에서 처음 더 큰 값 | [3 5 5 5 6 6 7 -1] | 다루지 않는다. 창이 없다 |

합처럼 모든 칸이 값에 들어가는 물음은 누적합 쪽이고, 창 없이 자리마다 답하는 물음은
[`nextGreaterElement`](../nextGreaterElement/nextGreaterElement-guide.md) 쪽입니다. 묻는 구간의 길이가 질의마다
다르면 [`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 쪽이에요.

### 아이디어를 떠올리는 과정 — 창마다 다시 읽기에서 단조 덱까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열과 창의 칸 수를 받아, 창이
지나는 위치마다의 최댓값을 차례로 담은 배열을 돌려줍니다.

```ts
function slidingWindowMaximum(nums: number[], k: number): number[];
```

- 입력: 정수 배열 `nums` 와 창의 칸 수 `k`. `1 ≤ k ≤ N` 입니다.
- 출력: 길이가 `N − k + 1` 인 배열. `j` 번째 값은 창 `[j, j + k − 1]` 의 최댓값이에요.
- 규모: 배열 길이 `N` 은 1 이상 100,000 이하로 둡니다. 이 규모를 고른 까닭은 창이 커질 때 `N · k` 가 흔한 채점
  환경의 예산인 1 초(단순 연산 1 초에 1 억 번)를 넘기 시작하는 규모라서, 단순한 방법과 이 글의 절차가 확실히
  갈리기 때문이에요.
- 비용은 **배열 접근 수**로 셉니다. `nums` 를 읽은 횟수와 단조 덱 · 답 배열을 읽고 쓴 횟수를 모두 더한 값이고,
  이 글 끝까지 이 기준 하나만 씁니다. 덱의 앞 · 뒤 어느 쪽에서 넣고 빼도 한 번으로 세요. 메모리는 입력과 출력
  밖에 **추가로 잡는 칸 수**로 셉니다.

이 글이 끝까지 쓰는 기호를 여기서 정합니다.

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| `N` | 배열 `nums` 의 길이 | `1 ≤ N ≤ 100,000` |
| `k` | 창의 칸 수 | `1 ≤ k ≤ N` |
| `nums[i]` | 배열의 `i` 번째 값. 0 부터 셉니다 | 32 비트 정수 |
| `i` | 지금 읽고 있는 자리이자 창의 오른쪽 끝 | `0 ≤ i < N` |
| `cur` | 지금 값 `nums[i]` | — |
| `cand` | 앞으로 답이 될 수 있는 자리를 담은 단조 덱 | 값이 아니라 자리 번호를 담습니다 |
| `front` | `cand` 의 앞 자리 `cand[0]` | 단조 덱이 비면 없습니다 |
| `back` | `cand` 의 뒤 자리 `cand[cand.length − 1]` | 단조 덱이 비면 없습니다 |
| `result` | 창마다의 답을 차례로 담은 배열 | 길이가 `N − k + 1` 입니다 |
| `P` | 한 번의 실행에서 **뒤**에서 버린 자리의 수 | `0 ≤ P ≤ N − 1` |
| `F` | 창 밖으로 나가 **앞**에서 버린 자리의 수 | `0 ≤ F ≤ N − 1` |
| `B` | 뒤 자리가 남은 채로 뒤에서 버리기를 멈춘 걸음의 수 | `0 ≤ B ≤ N − 1` |

가장 먼저 떠오르는 방법은 정의를 글자 그대로 옮기는 것입니다. 창 하나마다 그 안의 `k` 칸을 처음부터 읽어 가장
큰 값을 찾아요.

```ts
function rescanEvery(nums: number[], k: number): number[] {
  const result: number[] = [];
  for (let s = 0; s + k <= nums.length; s++) {
    let best = nums[s] ?? 0;
    for (let j = s + 1; j < s + k; j++) {
      const v = nums[j] ?? 0;
      if (v > best) best = v; // 창 하나에 k 칸을 다시 읽는다
    }
    result.push(best);
  }
  return result;
}
```

답은 틀리지 않습니다. 걸리는 것은 **창의 개수와 창의 크기가 곱해진다**는 것이에요. 이 방법과 이 글이 만들
절차를 같은 기준으로 세면 이렇습니다.

<!--proof:origin-rescan-scale-->

| N | k | 창마다 다시 읽기의 배열 접근 | 이 글이 만들 절차의 배열 접근 | 다시 읽기의 시간(초당 1 억 번) |
| ---: | ---: | ---: | ---: | ---: |
| 1,000 | 100 | 91,001 | 10,644 | 0.00 초 |
| 10,000 | 1,000 | 9,010,001 | 106,921 | 0.09 초 |
| 100,000 | 10,000 | 900,100,001 | 1,069,781 | 9.00 초 |

입력은 nums[i] = (2731 i) mod 1201 입니다. 창마다 다시 읽기는 입력과 무관하게 (k + 1)(N − k + 1) 번이라, N = 1,000 · 10,000 은 실제로 세었고 N = 100,000 은 그 식에 넣은 값입니다. 이 글이 만들 절차는 세 줄 모두 실제로 세었습니다. k 를 N 의 절반인 50,000 으로 두면 다시 읽기는 2,500,100,001 번입니다.

<!--/proof-->

`N = 100,000` 에 `k = 10,000` 을 넣으면 창마다 다시 읽는 방법은 예산 1 초를 몇 배나 넘깁니다.
어디서 그만큼 늘어나는지 작은 입력에서 봅시다. 전개 입력에서 창마다 읽은 칸을 그렸어요.

<!--fig:origin-rescan-->
![창마다 k 칸을 다시 읽으면 — 이웃한 창이 함께 쓰는 칸을 창마다 다시 읽는다](./figs/origin-rescan.svg)

괄호가 그 창에서 읽은 칸이고 ▲ 가 읽은 칸 전부입니다. 같은 것을 표로 옮기면 이렇습니다.

<!--proof:origin-rescan-small-->

| 창 | 읽은 자리 | 최댓값 | 읽은 칸 수 |
| --- | --- | ---: | ---: |
| [0,2] | 0 · 1 · 2 | 3 | 3 |
| [1,3] | 1 · 2 · 3 | 3 | 3 |
| [2,4] | 2 · 3 · 4 | 5 | 3 |
| [3,5] | 3 · 4 · 5 | 5 | 3 |
| [4,6] | 4 · 5 · 6 | 6 | 3 |
| [5,7] | 5 · 6 · 7 | 7 | 3 |

창 6 개가 읽은 칸은 모두 18 칸이고, 서로 다른 칸은 8 칸입니다. 두 창 이상이 거듭 읽은 칸은 자리 1 · 2 · 3 · 4 · 5 · 6 입니다.

<!--/proof-->

이웃한 두 창이 두 칸씩 겹치고, 겹친 칸을 창마다 다시 읽습니다. 그러니 창이 한 칸 옮겨 갈 때 **바뀐 것만
반영**하면 될 것 같아요. 그 생각을 가장 단순하게 옮기면 「지금까지의 최댓값과 그 자리 하나만 기억한다」가
됩니다. 기억한 자리가 창을 벗어났을 때만 창을 다시 읽어요.

```ts
if (at <= i - k) {
  // 기억하던 자리가 창을 벗어났다 — 창의 k 칸을 다시 읽는다
  best = Number.NEGATIVE_INFINITY;
  for (let j = Math.max(0, i - k + 1); j <= i; j++) {
    if ((nums[j] ?? 0) > best) {
      best = nums[j] ?? 0;
      at = j;
    }
  }
} else if (cur >= best) {
  best = cur; // 들어온 값이 더 크면 그것으로 바꾼다
  at = i;
}
```

두 방식을 같은 입력에 적용해 배열 접근 수를 나란히 재 봅시다. 입력은 두 벌이에요 — 값이 골고루 섞인 1,024
칸과, 같은 길이의 감소 수열입니다.

<!--proof:origin-three-ways-->

| 입력 | 창마다 다시 읽기 | 최댓값 하나만 기억하기 | 그중 창을 다시 읽은 걸음 |
| --- | ---: | ---: | ---: |
| 곱셈 나머지 | 32,769 | 2,433 | 13 |
| 감소 수열 | 32,769 | 33,761 | 992 |

N = 1,024 · k = 32 이고 배열 접근 수를 셉니다. 곱셈 나머지는 nums[i] = (2731 i) mod 1201, 감소 수열은 nums[i] = N − i 이고, 두 방식의 답은 두 입력 모두 정본과 같습니다.

<!--/proof-->

**두 줄이 반대로 갈립니다.** 값이 골고루 섞인 입력에서 「하나만 기억하기」는 창을 다시 읽은 걸음이 적어 가장
적게 접근합니다. 그런데 감소 수열에서는 거의 모든 걸음에서 기억한 답이 창을 벗어나, 창마다 다시 읽는 방법보다도
많아요. 여기서 비용이 무엇에 달렸는지가 보입니다 — **기억한 답이 창을 벗어나는 횟수**예요. 그 횟수는 입력의
모양이 정하고 우리가 고를 수 없으니, 고칠 곳은 **다시 읽는 일 자체**입니다. 답이 창을 벗어나는 순간 다음 답을
이미 알고 있으면 다시 읽을 일이 없어요.

다음 답이 될 수 있는 자리는 「전체 컨셉」의 규칙이 정합니다. 자기 오른쪽에 더 큰 값이 생긴 자리는 버리고
나머지를 남기는 것이에요. 이 규칙은 [`nextGreaterElement`](../nextGreaterElement/nextGreaterElement-guide.md) 의
단조 스택이 이미 합니다 — 지금 값보다 작은 꼭대기를 꺼내고 나서 넣으니까요. 가장 단순한 후보는 **그 단조
스택을 그대로 쓰고 바닥의 값을 답으로 적는 것**입니다. `nums = [5 9 1 3 1 1]` · `k = 3` 에서 해 봤어요.

<!--proof:origin-stack-only-->

| 읽은 자리 | 뒤에서만 버린 뒤 stack | 맨 앞의 값 | 창 | 바른 답 |
| --- | --- | --- | --- | --- |
| 0 · 값 5 | [0] | — | 덜 찼다 | — |
| 1 · 값 9 | [1] | — | 덜 찼다 | — |
| 2 · 값 1 | [1 2] | 9 | [0,2] | 9 |
| 3 · 값 3 | [1 3] | 9 | [1,3] | 9 |
| 4 · 값 1 | [1 3 4] | 9 | [2,4] | 3 |
| 5 · 값 1 | [1 3 4 5] | 9 | [3,5] | 3 |

창 4 개 중 2 개에서 답이 다릅니다. 1,024 칸 곱셈 나머지 입력(k = 32)에서는 창 993 개 중 855 개가 틀립니다.

<!--/proof-->

자리 1 의 값 9 가 창 `[2,4]` 에서 이미 창 밖인데도 바닥에 남아 답 9 를 냅니다. 단조 스택은 **한쪽 끝에서만**
넣고 빼니, 가장 먼저 들어온 자리 — 가장 먼저 창 밖으로 나갈 자리 — 를 뺄 길이 없어요. 창 밖으로 나간 자리를
반대쪽 끝에서도 빼야 합니다. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **단조 덱**입니다. 답이 될 수 있는 자리를 단조 덱에 남기고, 지금 값보다 작은 자리를
뒤에서 버리고, 창 밖으로 나간 자리를 앞에서 버려요. 앞에서 한 번 보는 것으로 충분한 까닭과, 단조 덱이 어떻게
생겼고 어떻게 채워지는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 단조 덱

이 아이디어를 한 문장으로 줄이면 이렇습니다. **답이 될 수 있는 자리를 읽은 차례대로 단조 덱에 담아 두고, 새
자리를 읽을 때마다 창 밖으로 나간 앞 자리와 지금 값보다 작은 뒤 자리를 버린 뒤 새 자리를 뒤에 넣으면, 앞 자리의
값이 그 창의 답입니다.** 이 방법이 기대는 구조는 단조 덱 하나인데, 처음 보는 사람에게는 「양 끝에서 버리는
줄이 왜 저절로 정렬된 모양이 되고, 왜 앞이 곧 답인가」가 낯설어요. 그래서 단조 덱을 먼저 따로 설명하고,
그다음 실현하는 순서대로 네 단계를 설명합니다. 첫 단계는 순회 전에 한 번, 나머지 셋은 자리마다 합니다.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 순회 전에 한 번 | 1단계 빈 단조 덱과 빈 답 배열 준비 | 빈 `cand` 와 빈 `result` 를 잡는다 | — |
| 자리마다 | 2단계 창 밖으로 나간 앞 자리 버리기 | `front` 가 `i − k` 이하이면 앞에서 뺀다 | 1단계의 `cand` · 직전 자리까지 쌓인 `cand` |
| 자리마다 | 3단계 작은 뒤 자리 버리고 지금 자리 넣기 | `back` 의 값이 `cur` 보다 작은 동안 뒤에서 빼고 `i` 를 뒤에 넣는다 | 2단계가 남긴 `cand` |
| 자리마다 | 4단계 창이 다 차면 앞 자리의 값 적기 | `i ≥ k − 1` 이면 `nums[front]` 를 `result` 에 붙인다 | 3단계가 남긴 `cand` · 1단계의 `result` |

#### 먼저 알아 둘 개념 — 단조 덱

단조 덱은 **지금 창 안에서 자기 오른쪽에 자기보다 큰 값이 없는 자리를 읽은 차례대로 담은 덱으로, 담긴 자리의
값이 앞에서 뒤로 가며 커지지 않는 것**입니다. 앞에 있는 자리일수록 먼저 읽은 자리이고, 뒤가 가장 나중에 읽은
자리예요. 단조 덱의 칸 `c` 에 든 자리를 `cand[c]` 라고 쓰면 식으로는
`nums[cand[0]] ≥ nums[cand[1]] ≥ … ≥ nums[cand[cand.length − 1]]` 입니다.

##### 입력 위의 단조 덱

자리 5 까지 읽은 순간의 단조 덱을 입력 배열 위에 그렸습니다. 괄호가 지금 창이고, 대시 칸은 단조 덱에 없는 자리,
점선 칸은 아직 안 읽은 자리예요.

<!--fig:build-on-input-->
![자리 5 까지 읽은 뒤의 단조 덱 — 칸마다 창 안의 한 자리를 가리킨다](./figs/build-on-input.svg)

`nums` 줄에서 실선으로 남은 칸이 자리 4 와 자리 5 이고, 그 둘이 `cand` 줄에 앞부터 들어 있습니다. 대시 칸은
두 가지로 갈려요. 자리 0 · 1 · 2 는 창 `[3,5]` 밖이고, 자리 3 은 창 안이지만 오른쪽의 자리 4 가 더 커서 이미
뒤에서 버려졌습니다. 단조 덱은 창 안의 자리 가운데 **답이 될 수 있는 것만** 골라 차례대로 적은 목록인 셈이에요.

##### 칸 하나를 읽는 법

앞 칸 `cand[0]` 을 골라 이름에서 입력의 자리와 값, 답까지 따라가 봅시다.

<!--proof:build-read-one-->

| 차례 | 읽는 것 | 나오는 것 |
| ---: | --- | --- |
| 1 | cand[0] | 자리 4 |
| 2 | nums[4] | 값 5 |
| 3 | 자리 4 가 창 [3,5] 안인가 | 4 ≥ 3 · 창 안이다 |
| 4 | result[3] | 5 — 왼쪽 끝이 3 인 창의 답 |

단조 덱의 칸에 든 수는 자리 번호이지 값이 아닙니다. 값은 그 번호로 `nums` 를 한 번 더 읽어야 나와요. 자리
번호를 담는 까닭이 셋째 줄에 있습니다 — 창 안인지는 **자리 번호**를 창의 왼쪽 끝과 비교해야 알 수 있어요.

##### 이웃한 두 칸의 관계

단조 덱에서 바로 이웃한 두 칸을 모두 모아, 두 값의 크기와 두 자리 사이에 있던 자리가 어떻게 됐는지 쟀습니다.

<!--proof:build-neighbors-->

| 앞 칸 | 바로 뒤 칸 | 앞 칸의 값 ≥ 뒤 칸의 값 | 두 자리 사이에 있던 자리 |
| --- | --- | --- | --- |
| 자리 1 · 값 3 | 자리 2 · 값 -1 | 예 | 없음 |
| 자리 2 · 값 -1 | 자리 3 · 값 -3 | 예 | 없음 |
| 자리 4 · 값 5 | 자리 5 · 값 3 | 예 | 없음 |

전개 입력에서 이웃한 두 칸이 3 쌍 나왔습니다. 1,024 칸 곱셈 나머지 입력(k = 32)에서는 자리를 넣은 순간마다 이웃한 두 칸 1,790 쌍을 쟀고, 앞 칸의 값이 더 작거나 사이에 뒤 칸의 값 이상인 자리가 있던 쌍은 0 개입니다.

<!--/proof-->

앞 칸의 값은 늘 뒤 칸의 값 이상이고, 두 자리 사이에 있던 자리는 전부 뒤 칸보다 작은 값이라 이미 뒤에서
버려졌습니다. 사이에 뒤 칸의 값 이상인 자리가 남아 있다면 그 자리도 단조 덱에 있어야 하므로, 두 칸은 이웃일 수
없어요.

##### 창 안의 값을 정렬한 목록과의 차이

단조 덱을 처음 보면 「창 안의 값을 크기순으로 정렬해 두는 것」으로 읽기 쉽습니다. 값이 정렬된 모양이니까요.
같은 입력에서 둘을 나란히 놓았습니다.

<!--proof:build-vs-sorted-->

| 창 | 창 안의 값을 큰 것부터 정렬한 목록 | 단조 덱의 값 | 목록 칸 수 | 단조 덱 칸 수 |
| --- | --- | --- | ---: | ---: |
| [0,0] | [1] | [1] | 1 | 1 |
| [0,1] | [3 1] | [3] | 2 | 1 |
| [0,2] | [3 1 -1] | [3 -1] | 3 | 2 |
| [1,3] | [3 -1 -3] | [3 -1 -3] | 3 | 3 |
| [2,4] | [5 -1 -3] | [5] | 3 | 1 |
| [3,5] | [5 3 -3] | [5 3] | 3 | 2 |
| [4,6] | [6 5 3] | [6] | 3 | 1 |
| [5,7] | [7 6 3] | [7] | 3 | 1 |

1,024 칸 곱셈 나머지 입력(k = 32)에서 정렬한 목록은 창이 다 찬 뒤로 늘 32 칸이고, 단조 덱은 가장 길 때 4 칸입니다.

<!--/proof-->

정렬한 목록은 창 안의 값을 **전부** 들고 있어 칸 수가 창의 칸 수와 같습니다. 단조 덱은 오른쪽에 더 큰 값이
생긴 자리를 버리므로 훨씬 짧아요. 창 `[2,4]` 에서 목록에는 -1 과 -3 이 남아 있지만 단조 덱에는 5 하나뿐입니다.
값이 정렬된 모양이 되는 것은 정렬해서가 아니라 작은 뒤 자리를 버리고 나서 넣기 때문이고, 새 값을 목록 가운데
끼워 넣는 일이 없으니 넣기도 뒤에서 한 번에 끝납니다.

##### 앞 끝과 뒤 끝이 따로 있는 까닭

단조 덱이 두 끝을 쓰는 까닭은 **버리는 까닭이 둘**이기 때문입니다. 뒤에서 버리는 것은 「오른쪽에 더 큰 값이
생겼다」이고, 앞에서 버리는 것은 「창을 벗어났다」예요. 자리 번호가 앞에서 뒤로 커지니, 창을 벗어나는 자리 —
가장 먼저 읽은 자리 — 는 늘 앞에 있습니다. 창 밖으로 나간 자리가 단조 덱에 있던 걸음을 모두 세어 그 자리가 어디
있었는지 확인했어요.

<!--proof:build-two-ends-->

| 입력 | k | 창 밖으로 나간 자리가 단조 덱에 있던 걸음 | 그 자리가 하나이고 맨 앞이던 걸음 | 둘 이상이던 걸음 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 | 3 | 1 | 1 | 0 |
| 곱셈 나머지 1,024 칸 | 32 | 13 | 13 | 0 |
| 감소 수열 1,024 칸 | 32 | 992 | 992 | 0 |

세 입력 모두 창 밖으로 나간 자리는 **하나이고 늘 맨 앞**이었습니다. 그러니 앞에서 한 번만 보면 되고, 가운데를
뒤질 일이 없어요. 앞이 답인 까닭도 같은 모양에서 나옵니다 — 값이 앞에서 뒤로 커지지 않으니 창 안에 남은 자리
중 가장 큰 값이 앞에 있습니다.

#### 1단계 — 빈 단조 덱과 빈 답 배열 준비

순회를 시작하기 전에 빈 `cand` 와 빈 `result` 를 잡습니다. 답 배열의 길이를 **미리 정하지 않는** 것이 이
단계의 요점이에요. 창이 다 찬 자리마다 답을 하나씩 붙이면, 창의 수 `N − k + 1` 을 따로 계산하지 않아도 개수가
저절로 맞습니다. 전개 입력에서 `k` 를 바꿔 가며 확인했어요.

<!--proof:build-init-->

| k | 창의 수 N − k + 1 | 정본이 낸 답의 수 |
| ---: | ---: | ---: |
| 1 | 8 | 8 |
| 3 | 6 | 6 |
| 8 | 1 | 1 |

`k = N` 이면 창이 하나라 답도 하나이고, `k = 1` 이면 자리마다 창이 하나라 답이 `N` 개입니다.

#### 2단계 — 창 밖으로 나간 앞 자리 버리기

자리 `i` 를 읽으면 먼저 앞 자리가 창 안인지 봅니다. 오른쪽 끝이 `i` 인 창의 왼쪽 끝은 `i − k + 1` 이므로, 자리
번호가 `i − k` 이하인 자리는 창 밖이에요. 전개 입력의 여덟 자리에서 이 판정이 어떻게 나왔는지 모았습니다.

<!--proof:build-expire-steps-->

| 자리 i | 창 | 앞 자리 | i − k | 앞 자리 ≤ i − k | 버린 자리 |
| ---: | --- | --- | ---: | --- | --- |
| 0 | [0,0] | 없다 | -3 | 보지 않는다 | 없음 |
| 1 | [0,1] | 자리 0 | -2 | 거짓 | 없음 |
| 2 | [0,2] | 자리 1 | -1 | 거짓 | 없음 |
| 3 | [1,3] | 자리 1 | 0 | 거짓 | 없음 |
| 4 | [2,4] | 자리 1 | 1 | 참 | 자리 1 |
| 5 | [3,5] | 자리 4 | 2 | 거짓 | 없음 |
| 6 | [4,6] | 자리 4 | 3 | 거짓 | 없음 |
| 7 | [5,7] | 자리 6 | 4 | 거짓 | 없음 |

앞에서 버린 걸음은 1 번이고, 자리 4 를 읽을 때입니다.

<!--/proof-->

자리 4 에서 창이 `[2,4]` 로 옮겨 가자 자리 1 이 창 밖이 됐고, 그 자리가 마침 앞에 있어 앞에서 버렸습니다.
버리는 것이 **한 걸음에 많아야 하나**인 까닭은 이렇습니다. 직전 걸음을 마친 시점의 단조 덱에는 그 창
`[i − k, i − 1]` 안의 자리만 있어요. 이번 걸음에 창 밖이 되는 자리는 번호가 `i − k` 이하이면서 `i − k` 이상인
자리, 곧 `i − k` 하나뿐입니다.

```ts
if (cand.length > 0 && (cand[0] ?? 0) <= i - k) cand.shift(); // 앞에서 한 번만 본다
```

#### 3단계 — 지금 값보다 작은 뒤 자리 버리고 지금 자리 넣기

앞을 정리했으면 지금 값 `cur` 를 뒤 자리의 값과 비교합니다. 뒤 자리의 값이 `cur` 보다 **엄격하게 작으면** 뒤에서
버리고, 새 뒤 자리와 다시 비교해요. 버리기가 멈추는 경우는 둘뿐입니다 — 단조 덱이 비었거나, 뒤 자리의 값이
`cur` 이상이거나. 멈추면 지금 자리 `i` 를 뒤에 넣습니다. 여덟 자리에서 실제로 어떻게 됐는지 모았어요.

<!--proof:build-pop-steps-->

| 읽은 자리 | 앞 처리 뒤 cand | 뒤에서 버린 자리(차례대로) | 멈춘 까닭 | 넣은 뒤 cand |
| --- | --- | --- | --- | --- |
| 0 · 값 1 | [] | 없음 | 단조 덱이 비었다 | [0] |
| 1 · 값 3 | [0] | 0 | 단조 덱이 비었다 | [1] |
| 2 · 값 -1 | [1] | 없음 | 뒤 자리 1 의 값 3 ≥ -1 | [1 2] |
| 3 · 값 -3 | [1 2] | 없음 | 뒤 자리 2 의 값 -1 ≥ -3 | [1 2 3] |
| 4 · 값 5 | [2 3] | 3 · 2 | 단조 덱이 비었다 | [4] |
| 5 · 값 3 | [4] | 없음 | 뒤 자리 4 의 값 5 ≥ 3 | [4 5] |
| 6 · 값 6 | [4 5] | 5 · 4 | 단조 덱이 비었다 | [6] |
| 7 · 값 7 | [6] | 6 | 단조 덱이 비었다 | [7] |

가장 불안한 자리는 자리 4 입니다. 앞에서 자리 1 을 버린 뒤 뒤 자리 3 과 자리 2 를 차례로 버려 단조 덱이 비었고,
그래서 멈췄어요. 한 걸음에 **앞과 뒤를 함께** 버리는 자리입니다. 자리 6 도 뒤에서 둘을 한꺼번에 버렸고요.

```ts
while (cand.length > 0 && (nums[cand[cand.length - 1] ?? 0] ?? 0) < cur) {
  cand.pop(); // 오른쪽에 더 큰 값이 생긴 자리
}
cand.push(i); // 지금 자리는 오른쪽이 비어 있으니 늘 답이 될 수 있다
```

반복이 끝나면 `cand.length === 0` 이거나 뒤 자리의 값이 `cur` 이상입니다. 앞의 경우에는 넣은 자리 하나만
남고, 뒤의 경우에는 넣는 값이 남은 뒤 자리의 값 이하라 값이 커지지 않는 모양이 그대로 이어져요.

단조 덱이 얼마나 길어지는지도 여기서 정해집니다. 단조 덱에는 창 안의 자리만 있으니 `k` 칸을 못 넘고, 그 안에서
얼마나 차는지는 입력의 모양이 정해요. `k` 를 바꿔 가며 재 봤습니다.

<!--proof:build-k-sweep-->

| k | 곱셈 나머지 · 배열 접근 | 곱셈 나머지 · 가장 길 때 | 감소 수열 · 배열 접근 | 감소 수열 · 가장 길 때 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 7,166 | 1 | 7,166 | 1 |
| 2 | 9,208 | 2 | 9,208 | 2 |
| 8 | 10,864 | 3 | 9,184 | 8 |
| 32 | 11,012 | 4 | 9,088 | 32 |
| 128 | 10,826 | 5 | 8,704 | 128 |
| 512 | 9,689 | 8 | 7,168 | 512 |
| 1,024 | 8,153 | 8 | 5,120 | 1,024 |

N = 1,024 고정입니다. 가장 길 때의 칸 수는 곱셈 나머지에서 8 칸을 넘지 않고, 감소 수열에서는 k 까지 찹니다. 배열 접근은 14 개 값 모두 5,120 이상 11,012 이하입니다.

<!--/proof-->

값이 골고루 섞인 입력에서는 오른쪽에 더 큰 값이 금방 나타나 단조 덱이 몇 칸을 넘지 않습니다. 감소 수열에서는
어느 자리도 뒤에서 버려지지 않아 창 크기만큼 찹니다. 그리고 두 입력 모두 **배열 접근이 `k` 를 따라 늘지 않아요.**
자리마다 한 번 들어가고 많아야 한 번 나오기 때문입니다. `k` 는 시간이 아니라 단조 덱의 칸 수에만 남습니다.

#### 4단계 — 창이 다 차면 앞 자리의 값 적기

창이 처음으로 다 차는 자리는 `i = k − 1` 입니다. 그 자리부터 매번 앞 자리의 값을 답에 붙여요. 창이 다 찬 여섯
자리에서 앞 자리의 값과 정의대로 구한 창의 최댓값을 나란히 놓았습니다.

<!--proof:build-answers-->

| 창 | 앞 자리 | 그 값 | 창의 최댓값(정의) | 둘 |
| --- | --- | ---: | ---: | --- |
| [0,2] | 자리 1 | 3 | 3 | 같다 |
| [1,3] | 자리 1 | 3 | 3 | 같다 |
| [2,4] | 자리 4 | 5 | 5 | 같다 |
| [3,5] | 자리 4 | 5 | 5 | 같다 |
| [4,6] | 자리 6 | 6 | 6 | 같다 |
| [5,7] | 자리 7 | 7 | 7 | 같다 |

여섯 창 모두 둘이 같습니다. 2단계가 창 밖 자리를 앞에서 빼고, 3단계가 값이 커지지 않는 모양을 지켰기 때문에,
앞 자리는 창 안에서 가장 큰 값을 가진 자리예요. 같은 값이 여럿이면 그중 가장 왼쪽 자리가 앞에 옵니다 — 값이
같으면 뒤에서 버리지 않고 남기기 때문이에요.

#### 이 방법이 기대는 전제

단조 덱은 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 창의 값이 「하나가 나머지를 가린다」로 정해진다 | 3단계에서 더 큰 값이 생긴 자리를 버린다 | 합이나 서로 다른 값의 개수처럼 모든 칸이 값에 들어가면 버릴 근거가 없다 |
| 창의 길이가 하나로 고정이다 | 2단계에서 창 밖을 자리 번호 `i − k` 하나로 판정한다 | 길이가 질의마다 다르면 한 걸음에 여러 자리가 나갈 수 있고 앞 자리 하나로 판정이 안 끝난다 |
| 창이 한 방향으로만 옮겨 간다 | 버린 자리를 다시 보지 않는다 | 왼쪽으로 되돌아가면 이미 버린 자리가 다시 답이 될 수 있다 |

같은 값을 뒤에서 버리지 않고 남기는 것은 이 전제가 아니라 설계의 선택입니다. 같은 값도 버려 봤자 답은 안
바뀌는데, 그 차이는 「스스로 점검하기」에서 직접 세어 보게 두었어요.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇습니다. 2단계부터 4단계까지가 자리 하나의 반복 한 바퀴예요.

1. 빈 `cand` 와 빈 `result` 를 잡는다
2. 자리 `i` 를 0 부터 `N − 1` 까지 읽으며, `front` 가 `i − k` 이하이면 앞에서 뺀다
3. `back` 의 값이 `cur` 보다 작은 동안 뒤에서 빼고, 멈추면 `i` 를 뒤에 넣는다
4. `i ≥ k − 1` 이면 `nums[front]` 를 `result` 에 붙인다 — 순회가 끝나면 `result` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 창 셋짜리로 여덟 칸을 지나며 답 여섯 개를 낸다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const nums = [1, 3, -1, -3, 5, 3, 6, 7];
const k = 3;
// 이 절이 끝나면 [3, 3, 5, 5, 6, 7] 이 나와야 한다
```

이 여덟 칸을 고른 까닭은 **갈래를 전부 실행하기** 때문이에요. 단조 덱이 비어 바로 넣는 걸음과 뒤에서 여럿을
버리는 걸음이 둘 다 나오고, 앞에서 버리는 걸음이 한 번 있으며, 창이 덜 찬 자리도 둘 있고, 음수도 섞여 있습니다.

```text
slidingWindowMaximum(nums, k):
    result 를 빈 배열로, cand 를 빈 단조 덱으로 잡는다                 ①
    자리 i 를 0 부터 N-1 까지 읽으며:
        cur 는 이번 자리의 값 nums[i] 다
        앞 자리가 i - k 이하이면 앞에서 버린다                         ②
        뒤 자리의 값이 cur 보다 작은 동안 뒤에서 버린다                ③
        지금 자리 i 를 뒤에 넣는다                                     ④
        i 가 k - 1 이상이면 앞 자리의 값을 result 에 붙인다            ⑤
    result 를 돌려준다
```

#### 1. 단조 덱과 답 배열을 빈 채로 잡는다

답 배열과 단조 덱을 빈 채로 잡는 것이 이 조각의 전부입니다. 답의 개수는 창이 다 찰 때마다 하나씩 붙이며
저절로 맞춰져요.

```ts
const n = nums.length;
const result: number[] = []; // ① 창 하나에 답 하나. 길이가 n - k + 1 이 된다
const cand: number[] = [];
```

실행하면 이렇게 나옵니다.

<!--proof:walk-init-->

| nums | k | cand | result | 순회 |
| --- | ---: | --- | --- | --- |
| [1 3 -1 -3 5 3 6 7] | 3 | [] | [] | 자리 0 부터 7 까지 |

#### 2. 창 밖으로 나간 앞 자리를 버린다

오른쪽 끝이 `i` 인 창의 왼쪽 끝은 `i − k + 1` 이므로, 번호가 `i − k` 이하인 앞 자리는 창 밖입니다.

```ts
const cur = nums[i] ?? 0;
// ② 창을 벗어난 맨 앞 자리를 버린다. 한 걸음에 많아야 하나다.
if (cand.length > 0 && (cand[0] ?? 0) <= i - k) cand.shift();
```

`i = 4` 와 `i = 5` 에서 이 조각만 실행하면 이렇습니다.

<!--proof:walk-expire-at-4-->

| 걸음 | 앞 처리 전 cand | 앞 자리 | 조건 | 하는 일 | 앞 처리 뒤 cand |
| --- | --- | --- | --- | --- | --- |
| i = 4 | [1 2 3] | 자리 1 | `1 <= 1` 참 | 앞에서 버린다 | [2 3] |
| i = 5 | [4] | 자리 4 | `4 <= 2` 거짓 | 그대로 둔다 | [4] |

여기서 가장 중요한 것은 `<=` 입니다. 창의 왼쪽 끝이 `i − k + 1` 이니 자리 `i − k` 는 **방금 벗어난 자리**이고,
그 자리까지 버려야 해요. 등호를 떼면 무엇이 틀어지는지는 「불변식」 절에서 실행 결과로 봅니다.

#### 짚고 가기 — 앞에서 버리는 일은 한 걸음에 많아야 한 번이다

여기서 헷갈리기 쉬운 포인트는 `if` 입니다. 「뒤에서 버릴 때는 `while` 인데 앞에서는 왜 한 번인가, 여러 자리가
한꺼번에 창을 벗어날 수도 있지 않나」로 읽혀요. 2단계에서 본 대로 창 밖이 되는 자리는 번호 `i − k` 하나뿐이라,
되풀이해도 두 번째가 없습니다. 되풀이해서 버리는 코드를 같은 입력들로 실행해 봅시다.

```ts
while (cand.length > 0 && (cand[0] ?? 0) <= i - k) cand.shift(); // ← 되풀이해 버린다. 원래는 if 다
```

<!--proof:pause-expiry-while-->

| 입력 | k | 바른 코드 | 되풀이해 버리는 코드 | 답 |
| --- | ---: | --- | --- | --- |
| [1 3 -1 -3 5 3 6 7] | 3 | [3 3 5 5 6 7] | [3 3 5 5 6 7] | 같다 |
| [5 4 3 2 1] | 2 | [5 4 3 2] | [5 4 3 2] | 같다 |
| [1 2 3 4 5] | 3 | [3 4 5] | [3 4 5] | 같다 |
| [7 7 7 7] | 2 | [7 7 7] | [7 7 7] | 같다 |

4 벌 중 0 벌에서 답이 다릅니다. 입력 5 개의 모든 창 크기 2,065 벌을 되풀이하는 규칙으로 실행해 한 걸음에 두 번 이상 앞에서 버린 걸음을 세었고, 0 개입니다.

<!--/proof-->

**답이 안 갈립니다.** `while` 로 적어도 두 번째 반복이 한 번도 실행되지 않아요. 그래도 `if` 로 적는 까닭은 읽는
사람에게 **한 번이면 충분하다는 사실 자체를 알리기 위해서**입니다. `while` 로 적으면 「한 걸음에 여러 자리가 빠질
수 있구나」로 읽히고, 그 오해는 비용을 셀 때 곧바로 틀린 식을 만들어요. 길이가 질의마다 다른 구간에서는 이
「하나뿐」이 성립하지 않는다는 것도 함께 가려집니다.

#### 3. 지금 값보다 작은 뒤 자리를 버리고 지금 자리를 넣는다

한 걸음의 핵심이 이 조각입니다. 뒤 자리의 값을 지금 값과 비교해, 엄격하게 작을 때만 버려요.

```ts
// ③ 지금 값보다 작은 뒤 자리를 버린다. 값이 같으면 멈춘다.
while (cand.length > 0 && (nums[cand[cand.length - 1] ?? 0] ?? 0) < cur) {
  cand.pop();
}
cand.push(i); // ④ 지금 자리를 뒤에 넣는다
```

`i = 4`(값 5)에서 이 조각만 실행하면 두 번 버립니다. 앞에서 자리 1 을 이미 버린 뒤라 단조 덱은 자리 2 와 자리 3
을 담고 있어요.

<!--proof:walk-pop-at-4-->

| 차례 | 뒤 자리 | 그 값 | 조건 | 하는 일 | cand |
| ---: | --- | --- | --- | --- | --- |
| 1 | 자리 3 | -3 | `-3 < 5` 참 | 뒤에서 버린다 | [2] |
| 2 | 자리 2 | -1 | `-1 < 5` 참 | 뒤에서 버린다 | [] |
| 3 | 없다 | — | `cand.length > 0` 거짓 | 반복이 끝나고 자리 4 를 넣는다 | [4] |

버리기가 끝난 뒤 넣으므로 지금 자리는 언제나 뒤가 되고, 그 값이 단조 덱 안에서 가장 작습니다 — 같은 값이 앞에
남아 있을 수는 있어요. 순서를 뒤집어 먼저 넣고 버리기를 시작하면 자기 자신이 뒤 자리가 되는데, 자기 값이 자기
값보다 작을 수는 없어서 바로 멈춥니다. 그러면 아무것도 안 버려져 단조 덱이 창 크기만큼 늘어나요.

#### 4. 창이 다 차면 맨 앞의 값을 적는다

창이 처음으로 다 차는 자리는 `i = k − 1` 입니다. 그전까지는 창이 아직 `k` 칸을 못 채웠으니 답을 적지 않아요.

```ts
// ⑤ 창이 다 찼으면 맨 앞 자리의 값이 그 창의 답이다
if (i >= k - 1) result.push(nums[cand[0] ?? 0] ?? 0);
```

전개 입력에서 답이 적히는 자리와 안 적히는 자리가 이렇게 갈립니다.

<!--proof:walk-answer-->

| 자리 i | 조건 | 앞 자리 | 그 값 | 적는 답 | result |
| ---: | --- | --- | ---: | --- | --- |
| 0 | `0 >= 2` 거짓 | 자리 0 | 1 | 적지 않는다 | [] |
| 1 | `1 >= 2` 거짓 | 자리 1 | 3 | 적지 않는다 | [] |
| 2 | `2 >= 2` 참 | 자리 1 | 3 | 3 | [3] |
| 3 | `3 >= 2` 참 | 자리 1 | 3 | 3 | [3 3] |
| 4 | `4 >= 2` 참 | 자리 4 | 5 | 5 | [3 3 5] |
| 5 | `5 >= 2` 참 | 자리 4 | 5 | 5 | [3 3 5 5] |
| 6 | `6 >= 2` 참 | 자리 6 | 6 | 6 | [3 3 5 5 6] |
| 7 | `7 >= 2` 참 | 자리 7 | 7 | 7 | [3 3 5 5 6 7] |

참인 자리가 6 개이고, 창의 수 N − k + 1 = 8 − 3 + 1 = 6 과 같습니다.

<!--/proof-->

#### 짚고 가기 — 창이 다 차기 전에 답을 적으면 개수부터 달라진다

여기서 헷갈리기 쉬운 포인트는 `i >= k - 1` 입니다. 「어차피 앞 자리가 지금까지의 최댓값이니 자리마다 적으면
되지 않나」로 읽히는데, **창이 덜 찬 동안의 최댓값은 어느 창의 답도 아닙니다.** `i = 1` 이면 창 `[-1,1]` 의
왼쪽 끝이 배열 밖이라 그 자리에는 창이 없어요. 그 조건을 없앤 코드를 같은 입력들로 실행해 봅시다.

```ts
result.push(nums[cand[0] ?? 0] ?? 0); // ← 창이 덜 차도 적는다. 원래는 if (i >= k - 1) 이 앞에 있다
```

<!--proof:pause-no-warmup-->

| 입력 | k | 바른 코드 | 창이 덜 찼을 때도 적는 코드 | 답 |
| --- | ---: | --- | --- | --- |
| [1 3 -1 -3 5 3 6 7] | 3 | [3 3 5 5 6 7] | [1 3 3 3 5 5 6 7] | 다르다 |
| [3 1 5 2] | 4 | [5] | [3 3 5 5] | 다르다 |
| [3 1 5 2] | 1 | [3 1 5 2] | [3 1 5 2] | 같다 |
| [9 8 7 6 5] | 2 | [9 8 7 6] | [9 9 8 7 6] | 다르다 |

4 벌 중 3 벌에서 답이 다릅니다. 답의 개수가 바른 코드는 4 벌 모두 N − k + 1 개, 창이 덜 찼을 때도 적는 코드는 4 벌 모두 N 개입니다.

<!--/proof-->

**답이 같은 셋째 줄이 이 짚고 가기를 두는 이유입니다.** `k = 1` 이면 첫 자리에서 창이 이미 다 차므로 두 코드의
답이 글자 그대로 같아요. 시험 목록이 `k = 1` 인 입력으로만 채워져 있으면 이 코드는 오류 없이 통과하고, 틀린 줄
모르는 채로 남습니다.

#### 5. 여덟 칸을 열다섯 걸음으로 지난다

네 조각을 하나로 이어 고정 입력에 실행하면 열다섯 걸음이 나옵니다. 한 걸음은 「앞에서 버리기」나 「뒤에서
버리기」나 「멈추고 넣기」나 「바로 넣기」 중 하나이고, 넣는 걸음은 창이 다 찼으면 답까지 적어요. 무대의 괄호가
지금 창, ▲ 가 이번에 읽은 칸입니다. `result` 줄의 굵은 칸이 이번에 적은 답, `cand` 두 줄의 굵은 칸이 이번에
넣은 칸이에요. 앞에서 버리는 걸음(T6)은 창 밖으로 나간 그 자리에 ▲ 를 달았습니다.

① 은 T1 앞의 준비, ② 는 T6, ③ 은 T2 · T4 · T5 · T7 · T8 · T10 · T11 · T12 · T14, ④ 는 T1 · T3 · T4 · T5 · T9 · T10 · T13 · T15, ⑤ 는 T4 · T5 · T9 · T10 · T13 · T15 입니다. 앞에서 버리기가 1 번, 뒤에서 버리기가 6 번, 넣기가 8 번입니다.

<!--/proof-->

**다섯 갈래가 모두 나왔습니다.** T6 에서 자리 1 이 창 밖이 되어 앞에서 빠졌고, 이어지는 T7 · T8 에서 값 5 가
뒤 자리 둘을 버려 단조 덱이 비었어요. `result` 가 바뀐 걸음은 넣는 걸음 가운데 창이 다 찬 여섯 걸음뿐입니다.

#### 짚고 가기 — 앞에서 버리는 한 번과 배열이 실제로 옮기는 칸

여기서 헷갈리기 쉬운 포인트는 `shift` 입니다. 「덱은 앞에서 빼는 것도 한 번에 끝나니 `shift` 도 한 번이다」로
읽히는데, **자바스크립트 배열의 `shift` 는 남은 칸을 전부 한 칸씩 앞으로 옮깁니다.** 이 글의 비용은 덱의 계약대로
앞에서 빼기를 한 번으로 세지만, 배열로 적은 정본이 실제로 하는 일은 그보다 많을 수 있어요. 단조 덱이 얼마나
긴지에 따라 그 차이가 얼마나 벌어지는지 재 봤습니다.

<!--proof:pause-shift-cost-->

| 입력 | N | k | 앞에서 버린 횟수 | shift 가 옮긴 칸 |
| --- | ---: | ---: | ---: | ---: |
| 감소 수열 | 1,024 | 32 | 992 | 30,752 |
| 감소 수열 | 100,000 | 1,000 | 99,000 | 98,901,000 |
| 곱셈 나머지 | 1,024 | 32 | 13 | 26 |
| 곱셈 나머지 | 100,000 | 1,000 | 82 | 492 |

앞에서 버린 횟수는 덱의 계약대로 한 번씩 센 값이고, 옮긴 칸은 배열의 shift 가 실제로 옮긴 칸입니다. 감소 수열 100,000 칸 · k = 1,000 에서는 옮긴 칸이 앞에서 버린 횟수의 999 배입니다.

<!--/proof-->

**답은 안 틀립니다** — 갈리는 것은 옮긴 칸 수뿐이에요. 값이 골고루 섞인 입력에서는 단조 덱이 짧아 차이가
작습니다. 감소 수열에서는 단조 덱이 창 크기까지 차서, 앞에서 뺄 때마다 창 크기만큼 옮겨요. 계약대로 한 번에
끝내려면 길이 `k` 짜리 고리 버퍼를 쓰면 되고, 아래 「실제로 쓰이는 곳」의 두 구현이 실제로 그렇게 합니다.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 순회를 감싸는 `for` 와 마지막 `return result`
뿐이에요.

```ts
export function slidingWindowMaximum(nums: number[], k: number): number[] {
  const n = nums.length;
  const result: number[] = []; // ① 창 하나에 답 하나. 길이가 n - k + 1 이 된다
  // 단조 덱 — 앞으로 답이 될 수 있는 **자리**만 담는다. 앞이 창의 왼쪽에 가깝고 뒤가 오른쪽에 가깝다.
  const cand: number[] = [];

  for (let i = 0; i < n; i++) {
    const cur = nums[i] ?? 0;
    // ② 창을 벗어난 맨 앞 자리를 버린다. 한 걸음에 많아야 하나다.
    if (cand.length > 0 && (cand[0] ?? 0) <= i - k) cand.shift();
    // ③ 지금 값보다 작은 뒤 자리를 버린다. 값이 같으면 멈춘다.
    while (cand.length > 0 && (nums[cand[cand.length - 1] ?? 0] ?? 0) < cur) {
      cand.pop();
    }
    cand.push(i); // ④ 지금 자리를 뒤에 넣는다
    // ⑤ 창이 다 찼으면 맨 앞 자리의 값이 그 창의 답이다
    if (i >= k - 1) result.push(nums[cand[0] ?? 0] ?? 0);
  }

  return result;
}
```

<!--proof:final-calls-->

```text
slidingWindowMaximum([1, 3, -1, -3, 5, 3, 6, 7], 3)   →   [3, 3, 5, 5, 6, 7]
slidingWindowMaximum([3, 1, 5, 2], 1)                 →   [3, 1, 5, 2]
slidingWindowMaximum([3, 1, 5, 2], 4)                 →   [5]
slidingWindowMaximum([-3, -1, -4, -2], 2)             →   [-1, -1, -2]
```

### 알아 두면 좋은 개념 — 형태학의 팽창과 침식

이 절차가 낸 답을 원래 배열과 나란히 놓으면 모양이 하나 보입니다. 큰 값이 자기 자리에서 **왼쪽으로 `k − 1`
칸까지** 번져 나타나 있어요. 부등호를 뒤집은 창 최솟값은 작은 값이 같은 방식으로 번집니다.

<!--proof:related-dilation-->

| 줄 | 자리 0 | 자리 1 | 자리 2 | 자리 3 | 자리 4 | 자리 5 | 자리 6 | 자리 7 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 원래 값 | 1 | 3 | -1 | -3 | 5 | 3 | 6 | 7 |
| 팽창(창 3 칸의 최댓값) | 3 | 3 | 5 | 5 | 6 | 7 | — | — |
| 침식(창 3 칸의 최솟값) | -1 | -3 | -3 | -3 | 3 | 3 | — | — |

자리 4 의 값 5 가 창 `[2,4]` 와 `[3,5]` 의 답이 되어 자리 2 · 3 아래에 나옵니다. 길이 `k` 인 창의 최댓값을
자리마다 구하는 것을 영상 처리에서는 **팽창**(dilation)이라 하고, 같은 창의 최솟값을 구하는 것을
**침식**(erosion)이라 부릅니다. 창 대신 「구조 요소」라는 말을 쓰고, 이 글의 창처럼 길이만 있고 모양이 평평한
구조 요소를 평평한 구조 요소라고 해요.

| 같은 이름을 다시 만나는 자리 | 창의 모양 | 구하는 것 |
| --- | --- | --- |
| 이 글의 창 최댓값 | 길이 `k` 인 1 차원 구간 | 팽창 |
| 이 글의 부등호를 뒤집은 것 | 같은 구간 | 침식 |
| 사진의 잡티 지우기 | 가로 `a` × 세로 `b` 인 사각형 | 침식 뒤에 팽창(열림) |
| 소리 신호의 봉우리 따라가기 | 길이 `k` 인 시간 구간 | 팽창 |

**2 차원 사각형 구조 요소는 1 차원 두 번으로 갈라집니다.** 가로로 한 번 팽창하고 그 결과를 세로로 한 번 팽창하면
사각형 팽창과 같은 결과가 나와요. 그래서 영상 처리 라이브러리는 이 글의 절차나 그 변형을 줄마다 · 열마다 한
번씩 부릅니다.

어떻게 정의하는지, 무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

세 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 구간의 길이가 하나로 고정이다 | 질의마다 길이가 다르면 창의 양 끝이 따로 움직여 「앞에서 하나 빼고 뒤에 넣는다」가 성립하지 않는다 | 앞에서 빼는 조건이 자리 번호 `i − k` 하나로 적힌다 |
| 구간의 값이 「하나가 나머지를 가린다」로 정해진다 | 최댓값 · 최솟값처럼 두 값을 비교해 한쪽을 버려도 답이 안 바뀌어야 한다 | 뒤 자리를 버릴 수 있다 |
| 창이 한 방향으로만 옮겨 간다 | 왼쪽으로 되돌아가는 질의가 섞이면 이미 버린 자리가 다시 필요해진다 | 버린 자리를 다시 보지 않는다 |

두 번째 조건이 가장 자주 걸립니다. 창의 값이 무엇으로 정해지는지에 따라 이 절차가 되는 것과 안 되는 것이 갈려요.

| 창의 값 | 앞 값으로 뒤 값 가리기 | 이 절차 |
| --- | --- | --- |
| 창의 최댓값 | 더 큰 값 하나가 나머지를 가린다 | 그대로 쓴다 |
| 창의 최솟값 | 부등호만 뒤집으면 가린다 | 부등호만 바꿔 쓴다 |
| 창의 합 | 모든 칸이 합에 들어간다 | 쓸 수 없다. 누적합 한 줄로 끝난다 |
| 창 안 서로 다른 값의 개수 | 한 값이 다른 값을 못 가린다 | 쓸 수 없다. 값마다 개수를 세는 맵이 필요하다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "크기 k 인 윈도우"  "연속한 k 개"  "최근 k 개 중 최댓값"       ← 결정적인 신호다
  "모든 길이 k 부분배열에 대해 최댓값을 구하라"
  "창을 한 칸씩 옮기며"                                          ← 창이 한 방향으로만 간다는 뜻이다

제약에 이런 모양이 보이면
  N 이 10^5 이상인데 k 도 크다                                   ← N·k 가 못 들어간다는 뜻이다
  값의 범위가 넓어 값마다 칸을 잡을 수 없다                      ← 값을 인덱스로 쓰는 배열이 못 들어간다는 뜻이다

반대로 이런 말이 보이면 해당하지 않는다
  "구간 [l, r] 이 질의로 주어진다"                               ← 길이가 고정이 아니다
  "중간에 값이 바뀐다"                                           ← 답을 처음부터 다시 만들어야 한다
  "합이 s 이하인 가장 긴 구간"                                   ← 양 끝이 따로 움직인다
```

마지막 무리가 보이면 다른 절차로 갑니다. 길이가 질의마다 다르면
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 쪽이고, 양 끝이 따로 움직이는
과제는 [`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **pandas 의 `roll_max` · `roll_min`** — `Series.rolling(k).max()` 가 부르는 함수입니다. 뒤에서 버리는 반복이
  `while (not candidates.empty() and values[k] >= values[candidates.back()]): candidates.pop_back()` 이고, 앞에서
  버리는 반복이 `while not candidates.empty() and candidates.front() < stash_start: candidates.pop_front()` 이며,
  답을 `output[i] = values[candidates.front()]` 로 적어요. **부등호가 `>=` 라 값이 같은 옛 자리도 버립니다** —
  이 글은 `<` 로 두어 남기는 쪽이고, 둘 다 답은 같습니다.
  ([`pandas/_libs/window/aggregations.pyx`](https://github.com/pandas-dev/pandas/blob/main/pandas/_libs/window/aggregations.pyx),
  조회 2026-09-03)
- **SciPy 의 `ndimage` 1 차원 최소 · 최대 필터 `NI_MinOrMaxFilter1D`** — `scipy.ndimage.maximum_filter1d` 가 부르는
  C 함수입니다. 후보마다 **값과 「창을 벗어나는 시점」을 함께** 담아 두고
  `if (minpair->death == ll) { INCREASE_RING_PTR(minpair) }` 로 앞을 버려요. 담는 곳이 배열이 아니라
  **고리 버퍼**(`ring`)라 앞에서 뺄 때 칸을 옮기지 않습니다 — 위 짚고 가기가 말한 자리를 그렇게 처리한
  실물이에요. 주석이 원저자를 밝혀 뒀습니다 — *"Original code by Richard Harter, adapted from:
  http://www.richardhartersworld.com/cri/2001/slidingmin.html"*.
  ([`scipy/ndimage/src/ni_filters.c`](https://github.com/scipy/scipy/blob/main/scipy/ndimage/src/ni_filters.c),
  조회 2026-09-03)
- **Bottleneck 의 `move_max` · `move_min`** — 넘파이 배열용 이동 집계 패키지입니다. 주석이 *"move_min, move_max,
  move_argmin, and move_argmax are based on the minimum on a sliding window algorithm by Richard Harter"* 이고,
  뒤에서 버리는 반복이 `while (last->value FLIP ai) { if (last == ring) last = end; last--; }` 로 **고리 버퍼를
  거꾸로** 지납니다. pandas 의 주석이 이 구현을 출처로 밝히고 있어요 — *"Prior version of moving maximum /
  minimum code taken from Bottleneck"*.
  ([`bottleneck/src/move_template.c`](https://github.com/pydata/bottleneck/blob/master/bottleneck/src/move_template.c),
  조회 2026-09-03)

네 구현이 단조 덱에 담는 것과 앞에서 빼는 방법을 나란히 두면 이렇습니다.

| 쓰는 곳 | 담는 것 | 앞에서 뺄 때 | 그때 옮기는 칸 |
| --- | --- | --- | --- |
| 이 글 | 자리 번호 | 배열의 `shift` | 남은 칸을 옮긴다 |
| pandas | 자리 번호 | 덱의 `pop_front` | C++ 의 `deque` 가 맡는다 |
| SciPy | 값과 창을 벗어나는 시점의 쌍 | 고리 버퍼의 시작을 옮긴다 | 안 옮긴다 |
| Bottleneck | 값과 창을 벗어나는 시점의 쌍 | 고리 버퍼의 시작을 옮긴다 | 안 옮긴다 |

넷 다 자리 번호든 시점이든 **창을 벗어났는지 가릴 수 있는 것**을 함께 담습니다. 값만으로는 창 밖인지 알 수
없어요.

#### 경쟁 설계와의 대조

같은 목표(길이 `k` 인 창마다 최댓값)를 노리는 다른 절차로 **조각마다 접두 · 접미 최댓값 표를 미리 적어 두는
방법**이 있습니다. 배열을 `k` 칸씩 조각으로 끊고, 조각 안에서 왼쪽부터의 최댓값과 오른쪽부터의 최댓값을 각각 한
벌씩 만들어 두는 방식이에요. van Herk(1992)와 Gil–Werman(1993)이 낸 방법이고, 영상 처리의 사각형 구조 요소
필터가 이것을 씁니다. 길이 `k` 인 창은 이어진 `k` 칸이므로 조각의 마지막 칸을 정확히 하나 담고, 그 칸에서 창이
둘로 갈리니 창의 최댓값은 「왼쪽 끝의 접미 최대」와 「오른쪽 끝의 접두 최대」 중 큰 쪽이에요.

| 설계 | 미리 만드는 것 | 창 하나의 답 | 답을 내기 시작하는 때 |
| --- | --- | --- | --- |
| 단조 덱 | 없다 | 앞 자리의 값을 읽는다 | 값이 들어오는 대로 |
| 조각 접두 · 접미 표 | 길이 `N` 인 표 두 벌 | 두 표에서 한 칸씩 읽어 큰 쪽 | 배열 전체를 두 번 지난 뒤 |

같은 입력 · 같은 창 크기로 두 설계를 실행하고 **배열 접근 수**를 셌습니다. 입력은 「아이디어를 떠올리는 과정」과
같은 생성식의 두 벌이에요 — `nums[i] = (2731 i) mod 1201` 인 1,024 칸과 같은 길이의 감소 수열
`nums[i] = N − i` 이고, 난수가 없으니 시드도 없습니다. 전개의 여덟 칸으로는 표 두 벌이 열 몇 번짜리 상수에 묻혀 두
설계의 순서가 안 갈리므로 1,024 칸을 쓰고 창 크기만 바꿉니다.

**감소 수열을 고정하고 창 크기만 바꾸면 순서가 뒤집힙니다.**

<!--proof:alt-k-->

| 감소 수열 1,024 칸 | 단조 덱 | 조각 접두·접미 표 | 적은 쪽 |
| --- | ---: | ---: | --- |
| k = 2 | 9,208 | 8,189 | 조각 표 · 1,019 번 적다 |
| k = 44 | 9,040 | 9,039 | 조각 표 · 1 번 적다 |
| k = 45 | 9,036 | 9,038 | 단조 덱 · 2 번 적다 |
| k = 1,024 | 5,120 | 6,145 | 단조 덱 · 1.20 배 적다 |

**같은 창 크기에서 입력의 모양만 바꿔도 순서가 뒤집힙니다.** 조각 표의 접근 수는 배열의 값에 안 매이고 길이와
창 크기만으로 정해지는데, 단조 덱 쪽은 값의 순서를 따라 움직이기 때문이에요.

| 1,024 칸 | 단조 덱 | 조각 접두·접미 표 | 적은 쪽 |
| --- | ---: | ---: | --- |
| 감소 수열 · k = 45 | 9,036 | 9,038 | 단조 덱 · 2 번 적다 |
| 곱셈 나머지 · k = 45 | 10,999 | 9,038 | 조각 표 · 1.22 배 적다 |
| 감소 수열 · k = 1,024 | 5,120 | 6,145 | 단조 덱 · 1.20 배 적다 |
| 곱셈 나머지 · k = 1,024 | 8,153 | 6,145 | 조각 표 · 1.33 배 적다 |

추가로 잡는 칸은 단조 덱이 감소 수열에서 k = 45 에 45 칸, k = 1,024 에 1,024 칸이고, 조각 표는 두 경우 모두 2,048 칸입니다.

<!--/proof-->

경계가 왜 그 자리인지는 감소 수열에서 두 계수가 닫힌 식으로 나와 풀립니다. 단조 덱은 뒤에서 버리는 일이 한 번도
없고 자리마다 멈추며, 조각 표는 조각 수가 `⌈N/k⌉` 이고 조각마다 두 칸을 그대로 적어요.

<!--proof:alt-boundary-->

| 설계 | 감소 수열의 배열 접근 | k = 44 | k = 45 |
| --- | --- | ---: | ---: |
| 단조 덱 | 9N − 4k | 9,040 | 9,036 |
| 조각 접두·접미 표 | 9N − 3k + 3 − 2⌈N/k⌉ | 9,039 | 9,038 |

단조 덱에서 조각 표를 뺀 차이는 2⌈N/k⌉ − (k + 3) 이고, k = 44 에서 1, k = 45 에서 -2 입니다. 단조 덱이 적어지는 첫 k 가 45 이고, √(2N) = 45.25 입니다.

<!--/proof-->

**이 절차가 내주는 것은 값이 골고루 섞인 입력에서의 접근 수입니다.** 뒤에서 버리는 일과 멈추는 걸음이 둘 다
많아지면 걸음마다 비교가 늘어나는데, 조각 표는 입력이 무엇이든 같은 횟수라 그 자리에서 앞섭니다. 그 대신 얻는 것이
둘이에요 — **추가로 잡는 칸이 창 크기까지만**이고, **값이 들어오는 대로 답을 낼 수 있습니다.** 조각 표는 배열
전체를 두 번 지나야 표가 완성되므로 마지막 값이 들어오기 전에는 첫 창의 답도 못 냅니다. 우열이 반대가 되는
조건도 분명해요 — 값이 한 방향으로 줄어드는 입력에서 창이 `√(2N)` 을 넘으면 단조 덱이, 값이 골고루 섞인 입력이나
창이 작은 입력에서는 조각 표가 적습니다.

### 수식 정의와 유도

창과 답과 후보 집합을 정의합니다. 기호표의 `i` 를 그대로 써요 — 창의 오른쪽 끝이고 지금 읽고 있는 자리입니다.

$$W(i) = [\,i-k+1,\; i\,], \qquad M(i) = \max_{i-k+1 \le t \le i} \mathit{nums}[t]$$

$$C(i) = \{\, t \mid i-k+1 \le t \le i,\ \ \mathit{nums}[t] \ge \mathit{nums}[u] \ \text{ for all } u \text{ with } t < u \le i \,\}$$

`W(i)` 는 오른쪽 끝이 `i` 인 창이고, 창이 다 찬 `k − 1 ≤ i ≤ N − 1` 에서 `M(i)` 가 `result[i − k + 1]` 입니다.
`C(i)` 는 자리 `i` 까지 읽은 시점의 **후보 집합**이에요. 조건이 둘입니다 — 창 `W(i)` 안에 있는 것, 그리고 자기
오른쪽에 자기보다 큰 값이 없는 것이에요. 이 집합을 코드에서는 `cand` 가 담습니다. 후보를 가려내는 조건을 코드로 그대로 옮기면
이렇습니다.

```ts
// 정의를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const isCandidate = (nums: number[], k: number, i: number, t: number): boolean =>
  t >= i - k + 1 && t <= i && nums.slice(t + 1, i + 1).every((v) => v <= (nums[t] ?? 0));
```

**정의를 값에 넣어 검산해 봅시다.** 전개 입력의 여덟 자리마다 정의로 구한 `C(i)` 와 정본이 그 자리를 끝낸 뒤의
`cand` 입니다.

<!--proof:candidates-check-->

| 자리 i | 정의로 구한 C(i) | 정본의 cand | 둘 | 맨 앞의 값 |
| ---: | --- | --- | --- | --- |
| 0 | [0] | [0] | 같다 | — |
| 1 | [1] | [1] | 같다 | — |
| 2 | [1 2] | [1 2] | 같다 | 3 |
| 3 | [1 2 3] | [1 2 3] | 같다 | 3 |
| 4 | [4] | [4] | 같다 | 5 |
| 5 | [4 5] | [4 5] | 같다 | 5 |
| 6 | [6] | [6] | 같다 | 6 |
| 7 | [7] | [7] | 같다 | 7 |

여덟 자리에서 두 열이 어긋난 자리는 0 개이고, 1,024 칸 곱셈 나머지 입력(k = 32)에서도 1,024 자리 중 0 개입니다.

<!--/proof-->

**이제 그 일치가 우연이 아님을 유도합니다.** 자리 `i` 를 끝낸 시점의 `cand` 는 정확히 `C(i)` 예요. 두 방향으로
보입니다.

| 방향 | 출발 | 근거 | 도착 |
| --- | --- | --- | --- |
| 남은 자리는 후보 | 자리 `t` 가 `cand` 에 남아 있다 | 앞에서 안 버려졌으니 `t ≥ i − k + 1` 이다. 뒤에서 안 버려졌으니, 뒤에서 버리는 조건 `nums[t] < nums[u]` 가 `t < u ≤ i` 인 어느 `u` 에서도 거짓이었다 | 모든 `u` 에서 `nums[t] ≥ nums[u]` 라 `t ∈ C(i)` 다 |
| 후보는 남는 자리 | `t ∈ C(i)` 다 | `t ≥ i − k + 1` 이라 앞에서 버려지지 않는다. `t` 뒤에 쌓인 자리는 값이 `nums[t]` 이하라 `t` 보다 먼저 버려질 수는 있어도, `t` 가 뒤 자리가 된 순간에도 조건 `nums[t] < nums[u]` 가 거짓이다 | 자리 `t` 는 `cand` 에 남는다 |

`C(i)` 의 가장 작은 원소가 창의 최댓값 자리입니다. 창 안의 자리 `s` 가 후보가 아니면 오른쪽에 자기보다 큰 값이
있고, 그 자리를 따라가면 결국 후보에 이르러요. 후보들의 값은 앞에서 뒤로 커지지 않으므로 가장 큰 것이 맨
앞입니다. 크기와 버린 횟수는 이렇게 닫힙니다.

$$|C(i)| \le \min(k,\; i+1), \qquad P + F = N - |C(N-1)|$$

세 식이 성립하는 까닭은 각각 이렇습니다.

| 식 | 성립하는 까닭 |
| --- | --- |
| `\|C(i)\| ≤ k` | 창 안의 자리만 담는다. 등호는 창 안의 값이 커지지 않을 때 성립한다 |
| `\|C(i)\| ≤ i + 1` | 아직 `i + 1` 칸밖에 안 읽었다 |
| `P + F = N − \|C(N−1)\|` | 넣은 것이 `N` 개이고, 끝에 남은 것이 `\|C(N−1)\|` 개다. 나머지는 앞이나 뒤에서 한 번씩 버려졌다 |

여기서 배열 접근의 총식이 닫힙니다. 자리마다 값을 한 번 읽고, 단조 덱이 비지 않았으면 앞 자리를 한 번 읽고,
비교 한 번에 두 번 읽고, 버릴 때마다 한 번 쓰고, 넣을 때 한 번 쓰고, 답을 적는 자리마다 세 번 접근합니다. 넣은
직후의 단조 덱은 비지 않으니 앞 자리를 못 보는 것은 첫 자리뿐이고, 비교한 횟수가 `P + B` 이므로 이렇게 돼요.

$$T(N,k) = 3N - 1 + F + 3P + 2B + 3(N-k+1)$$

`3N − 1` 은 값 읽기 `N` · 넣기 `N` · 앞 자리 보기 `N − 1` 을 더한 것이고, `3P` 는 버린 비교 하나의 두 번과 버리기
한 번, `2B` 는 멈춘 비교의 두 번, `3(N − k + 1)` 은 창마다 앞 자리 읽기 · 그 값 읽기 · 답 쓰기 셋입니다. 입력과
창 크기를 바꿔 실측과 맞대 봤어요.

<!--proof:cost-formula-->

| 입력 | N | k | P | F | B | 3N − 1 + F + 3P + 2B + 3(N − k + 1) | 실측 배열 접근 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 전개 입력 | 8 | 3 | 6 | 1 | 3 | 66 | 66 |
| 곱셈 나머지 | 1,024 | 2 | 743 | 279 | 280 | 9,208 | 9,208 |
| 곱셈 나머지 | 1,024 | 45 | 1,009 | 13 | 974 | 10,999 | 10,999 |
| 곱셈 나머지 | 1,024 | 1,024 | 1,019 | 0 | 1,011 | 8,153 | 8,153 |
| 감소 수열 | 1,024 | 2 | 0 | 1,022 | 1,023 | 9,208 | 9,208 |
| 감소 수열 | 1,024 | 45 | 0 | 979 | 1,023 | 9,036 | 9,036 |
| 감소 수열 | 1,024 | 1,024 | 0 | 0 | 1,023 | 5,120 | 5,120 |

7 줄 중 총식과 실측이 어긋난 줄은 0 개입니다.

<!--/proof-->

**여기부터가 본문의 값만으로는 안 나오는 자리입니다.** 파트 1 은 여덟 칸에서 한 점을 보였을 뿐인데, 총식에 상한을
넣으면 임의의 `N` 과 `k` 에서 접근 수가 닫혀요. 세 항의 상한을 하나씩 봅니다. `F + 3P` 는 `P` 가 클수록 커서
`F = 0` 일 때 가장 큽니다. `B` 는 첫 자리에서 단조 덱이 비어 멈출 수 없으니 `N − 1` 을 못 넘어요. 그리고 마지막
자리가 멈췄다면 그 자리와 그 앞 자리가 둘 다 남아 `|C(N−1)| ≥ 2` 이고, `P ≤ N − 2` 입니다.

$$T(N,k) \le 3N-1+3(N-2)+2(N-1)+3(N-k+1) = 11N - 3k - 6$$

`B = N − 1` 이면 위 식이 그 경우이고, `B = N − 2` 로 한 걸음 양보하면 `P ≤ N − 1` 이 되어 `11N − 3k − 5` 가
됩니다. 둘 중 큰 쪽이 상한이므로 `T(N,k) ≤ 11N − 3k − 5` 예요. 과제 규모에 넣으면 이렇습니다.

<!--proof:math-bound-->

| 방법 | N = 100,000 · k = 1,000 의 배열 접근 |
| --- | ---: |
| 창마다 다시 읽기 (k + 1)(N − k + 1) | 99,100,001 |
| 단조 덱의 상한 11N − 3k − 5 | 1,096,995 |
| 단조 덱 실측(곱셈 나머지 입력) | 1,096,624 |

다시 읽기는 단조 덱의 상한보다 90.3 배 많습니다.

<!--/proof-->

**이 상한은 타이트하지 않습니다.** 두 상한을 동시에 달성하는 입력은 없고, 여러 모양을 전부 재서 얻은 최댓값이
상한보다 작아요 — 그 값은 아래 「케이스별 비용과 그 경계」가 냅니다. 그래도 이 식이 주는 것이 하나 있습니다. `k`
가 **음의 계수로만** 들어간다는 것이에요. 창을 키우면 창의 개수가 줄어 접근이 줄고, 늘어나는 항은 없습니다.

### 불변식 — 자리를 끝낼 때마다 단조 덱은 창 안에서 오른쪽에 더 큰 값이 없는 자리 전부다

파트 1 에서 코드가 동작하는 것을 열다섯 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매번 참으로 남는지**를 아래 문장으로 세우고, 전개의 걸음마다 `cand` 를 정의의 `C(i)` 와
맞대 실제로 그런지 확인해 봅시다.

> **자리 `i` 를 끝낼 때마다**(지금 자리를 넣고 나면), `cand` 는 자리 `i − k + 1` 부터 `i` 까지 중 **오른쪽에
> 자기보다 큰 값이 없는 자리 전부**를 담고 있고, 앞에서 뒤로 자리 번호가 커지며 그 자리의 값은 커지지
> 않습니다. 그리고 창이 다 찬 자리에서는 앞 자리의 값이 그 창의 최댓값입니다.

<!--proof:invariant-states-->

| 걸음 | 자리 i | 걸음 뒤 cand | 자리 i 를 끝낸 걸음 | 정의로 구한 C(i) | 둘 | cand 의 값이 커지지 않음 |
| --- | ---: | --- | --- | --- | --- | --- |
| T1 | 0 | [0] | 예 | [0] | 같다 | 예 |
| T2 | 1 | [] | 아니오 | [1] | 다르다 | 예 |
| T3 | 1 | [1] | 예 | [1] | 같다 | 예 |
| T4 | 2 | [1 2] | 예 | [1 2] | 같다 | 예 |
| T5 | 3 | [1 2 3] | 예 | [1 2 3] | 같다 | 예 |
| T6 | 4 | [2 3] | 아니오 | [4] | 다르다 | 예 |
| T7 | 4 | [2] | 아니오 | [4] | 다르다 | 예 |
| T8 | 4 | [] | 아니오 | [4] | 다르다 | 예 |
| T9 | 4 | [4] | 예 | [4] | 같다 | 예 |
| T10 | 5 | [4 5] | 예 | [4 5] | 같다 | 예 |
| T11 | 6 | [4] | 아니오 | [6] | 다르다 | 예 |
| T12 | 6 | [] | 아니오 | [6] | 다르다 | 예 |
| T13 | 6 | [6] | 예 | [6] | 같다 | 예 |
| T14 | 7 | [] | 아니오 | [7] | 다르다 | 예 |
| T15 | 7 | [7] | 예 | [7] | 같다 | 예 |

자리를 끝낸 8 걸음 중 8 걸음에서 cand 와 C(i) 가 같습니다. 자리를 끝내기 전인 T2 · T6 · T7 · T8 · T11 · T12 · T14 에서는 둘이 다릅니다.

<!--/proof-->

「자리를 끝낼 때마다」가 중요합니다. 자리를 끝내기 전의 걸음에서는 지금 자리 `i` 가 아직 넣어지지 않았고,
T6 처럼 앞에서만 버린 순간에는 오른쪽에 더 큰 값이 생긴 자리도 아직 남아 있어요. 그래서 불변식을 「걸음마다」가
아니라 「자리를 끝낼 때마다」로 세웠고, 값이 커지지 않는다는 것은 한가운데 걸음에서도 참입니다.

**갈래마다 확인합시다.** 초기화 말고 `cand` 를 바꾸는 자리가 셋이고, 답 적기는 `cand` 를 안 건드립니다.

| 지나는 자리 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| 초기화 | 빈 `cand` 와 빈 `result` 를 잡는다 | 아직 아무 자리도 안 읽었으니 담긴 자리가 없다 |
| 앞에서 버리기 | 번호가 `i − k` 이하인 앞 자리를 뺀다 | 뺀 자리는 창 밖이고, 남은 자리의 순서와 값 관계는 안 바뀐다 |
| 뒤에서 버리기 | 값이 `cur` 보다 작은 뒤 자리를 뺀다 | 뺀 자리는 오른쪽에 더 큰 값(`cur`)이 생겨 후보가 아니다 |
| 넣기 | 자리 `i` 를 뒤에 넣는다 | 자리 `i` 는 오른쪽이 비어 후보이고, 남은 뒤 자리의 값이 `cur` 이상이라 순서도 유지된다 |
| 답 적기 | 앞 자리의 값을 적는다 | `cand` 를 안 건드린다 |

**경계에 있는 입력도 확인하고 갑시다.**

<!--proof:invariant-edges-->

| 입력 | k | 결과 | 앞에서 버린 횟수 F | 뒤에서 버린 횟수 P |
| --- | ---: | --- | ---: | ---: |
| [7] | 1 | [7] | 0 | 0 |
| [3 1 5 2] | 1 | [3 1 5 2] | 3 | 0 |
| [3 1 5 2] | 4 | [5] | 0 | 2 |
| [5 5 5 5] | 2 | [5 5 5] | 2 | 0 |
| [9 8 7 6 5] | 2 | [9 8 7 6] | 3 | 0 |
| [1 2 3 4 5] | 3 | [3 4 5] | 0 | 4 |
| [-3 -1 -4 -2] | 2 | [-1 -1 -2] | 1 | 2 |

`k = 1` 과 `k = N` 이 이 절차의 두 끝입니다. `k = 1` 이면 단조 덱에 자리가 하나뿐이라 둘째 자리부터 앞에서 버리기가
자리마다 일어나고, `k = N` 이면 앞에서 버리기가 한 번도 안 일어나요. 값이 전부 같은 줄은 같은 값을 뒤에서 버리지
않으므로 앞에서만 버리고, 음수만 있는 줄은 값의 부호가 비교에 쓰이지 않는다는 것을 보입니다.

**이제 깨뜨려 봅시다.** 「창 안의 자리만 담는다」를 지키던 줄은 앞에서 버리는 조건의 부등호 한 줄입니다. 「자리
번호가 창의 왼쪽 끝보다 작을 때 버리면 되니 등호는 없어도 되지 않나」라는 생각으로 그 등호를 떼어 봅니다.

```ts
if (cand.length > 0 && (cand[0] ?? 0) < i - k) cand.shift(); // ← 등호를 뗐다. 원래는 <= 다
```

<!--proof:mutant-expiry-strict-->

| 입력 | k | 바른 코드 | 등호를 뗀 코드 | 답 |
| --- | ---: | --- | --- | --- |
| [1 3 -1 -3 5 3 6 7] | 3 | [3 3 5 5 6 7] | [3 3 5 5 6 7] | 같다 |
| [9 1 1 1 1] | 2 | [9 1 1 1] | [9 9 1 1] | 다르다 |
| [1 2 3 4 5] | 3 | [3 4 5] | [3 4 5] | 같다 |
| [5 4 3 2 1] | 2 | [5 4 3 2] | [5 5 4 3] | 다르다 |

4 벌 중 2 벌에서 답이 다릅니다.

<!--/proof-->

`[9 1 1 1 1]` · `k = 2` 에서 두 번째 답이 1 대신 9 가 됩니다. 창 `[1,2]` 의 값은 1 과 1 이라 최댓값이 1 인데,
그 답을 적을 때 어느 앞 자리를 읽었는지 두 코드를 나란히 놓으면 까닭이 보여요.

<!--proof:mutant-expiry-trace-->

| 코드 | 창 [1,2] 의 답을 적을 때 읽은 앞 자리 | 그 자리가 창 안 | 창 [1,2] 의 답 |
| --- | --- | --- | ---: |
| 바른 조건 — cand[0] <= i - k | 자리 1 | 예 | 1 |
| 등호를 뗀 조건 — cand[0] < i - k | 자리 0 | 아니오 | 9 |

등호를 뗀 코드에서는 자리 2 를 읽을 때 `0 < 0` 이 거짓이라 자리 0 이 한 걸음 더 남고, 창 밖인 그 자리의 값 9 를
답으로 냅니다. 불변식의 「창 안의 자리만 담는다」가 그 걸음에서 깨진 것이에요. 값이 계속 커지는 입력에서는 앞
자리가 언제나 방금 넣은 자리라 답이 안 갈리고, 그래서 표의 셋째 줄이 같게 나옵니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 일곱뿐입니다 — 지금 값을 읽고, 앞 자리가 창 안인지 보고, 창 밖 앞 자리를 버리고, 뒤
자리와 비교하고, 뒤 자리를 버리고, 지금 자리를 넣고, 답을 적는 것. 비교 한 번이 접근 둘인 것은 뒤 자리를 읽고 그
자리의 값을 또 읽기 때문이고, 답 적기가 셋인 것도 같은 까닭이에요 — 앞 자리를 읽고, 그 값을 읽고, 답 배열에
씁니다. 전개의 걸음으로 세면 이렇습니다.

<!--proof:walk-cost-->

| 갈래 | 걸음 | 식 | 배열 접근 |
| --- | --- | --- | ---: |
| 지금 값을 읽는다 | T1 · T2 · T4 · T5 · T6 · T10 · T11 · T14 | N | 8 |
| 앞 자리가 창 안인지 본다 ② | T2 · T4 · T5 · T6 · T10 · T11 · T14 | N − 1 | 7 |
| 창 밖 앞 자리를 버린다 ② | T6 | F | 1 |
| 뒤 자리와 비교한다 ③ | T2 · T4 · T5 · T7 · T8 · T10 · T11 · T12 · T14 | 2(P + B) | 18 |
| 뒤 자리를 버린다 ③ | T2 · T7 · T8 · T11 · T12 · T14 | P | 6 |
| 지금 자리를 넣는다 ④ | T1 · T3 · T4 · T5 · T9 · T10 · T13 · T15 | N | 8 |
| 답을 적는다 ⑤ | T4 · T5 · T9 · T10 · T13 · T15 | 3(N − k + 1) | 18 |
| 합 |  | 3N − 1 + F + 3P + 2B + 3(N − k + 1) | 66 |

전개는 N = 8 · k = 3 · P = 6 · F = 1 · B = 3 이라 식에 넣으면 66 번입니다. 같은 입력을 창마다 다시 읽으면 24 번입니다.

<!--/proof-->

여덟 칸에서는 앞 자리를 보고 답을 적는 몫이 커서 창마다 다시 읽는 방법보다 많습니다. 칸이 늘면 이 몫들은 `N`
에 비례하는 그대로이고, 다시 읽는 쪽만 `N · k` 로 커져요. 과제 규모에 넣으면 이렇습니다.

<!--proof:perf-scale-->

| 입력 | P | F | B | 배열 접근 |
| --- | ---: | ---: | ---: | ---: |
| 감소 수열 | 0 | 99,000 | 99,999 | 896,000 |
| 곱셈 나머지 | 99,910 | 82 | 99,905 | 1,096,624 |
| 창마다 큰 값 하나 · 나머지 증가 | 99,899 | 99 | 99,900 | 1,096,598 |

N = 100,000 · k = 1,000 에서 세 줄 모두 실제로 세었고, 총식과 같습니다. 상한 11N − 3k − 5 는 1,096,995 이고, 단순 연산 1 초에 1 억 번으로 잡으면 가장 많은 줄도 0.011 초입니다.

<!--/proof-->

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (`k = N` 인 감소 수열) | `O(N)` | `Θ(N)` — 접근 `5N`, 실제로 도달합니다 |
| **평균적인 경우** (값의 순서에 분포를 정해야 한다) | `O(N)` | 분포를 정해야 값이 나옵니다 |
| **최악의 경우** (아래 절이 구성하는 입력) | `O(N)` | `Θ(N)` — 차수는 타이트하고, 상수는 `11N − 3k − 5` 이하까지만 압니다 |

세 케이스가 **경계의 종류에서는 갈리지 않습니다.** 셋 다 `Θ(N)` 이고 갈리는 것은 상수예요. 다만 세 줄에 적힌
값의 종류는 서로 다릅니다.

<!--proof:perf-range-->

| 경계 | N = 1,024 에서의 값 | 그 값에 이르는 입력 |
| --- | ---: | --- |
| 최선 5N | 5,120 | 감소 수열 · k = 1,024 |
| 실측 최대 | 11,040 | 창마다 큰 값 하나 · 나머지 증가 · k = 38 |
| 그 k 의 상한 11N − 3k − 5 | 11,145 | 이르는 입력을 못 찾았다 |

여섯 모양 × 창 크기 1,024 벌, 모두 6,144 번을 실행해 얻은 값입니다. 가장 적은 것은 5,120 번으로 5N 과 같고, 실측 최대는 그 2.2 배이며 상한과 105 번 차이입니다.

<!--/proof-->

최선은 그 값에 이르는 입력이 있는 **타이트한 값**이고, 상한 `11N − 3k − 5` 는 그 값에 이르는 입력을 못 찾은
**상한**입니다. 그래서 상한과 실측 최대를 같은 줄에 적지 않았어요. 이 절차에서 「최악이 느리다」는 말은 상수가
두 배 남짓이라는 뜻이지 차수가 다르다는 뜻이 아닙니다.

평균이 비어 있는 까닭도 적어 둡니다. 이 과제는 값이 **어떤 순서로 오는지 정하지 않아요.** 순서에 분포를 하나
놓으면(값이 전부 다르고 모든 나열이 같은 확률이라고 두면) `P` 와 `B` 의 기댓값이 나오지만, 그 분포는 과제가 준
조건이 아니라 이 글이 놓은 가정입니다. 총식을 한 번 정확히 적으면 이렇습니다.

```text
총식 = 배열 접근 3N − 1 + F + 3P + 2B + 3(N − k + 1),  5N ≤ 접근 ≤ 11N − 3k − 5   →   Θ(N) 시간
       추가로 잡는 칸 = 단조 덱 최대 min(k, N) 칸 (답 배열 N − k + 1 칸은 출력이라 안 센다)   →   Θ(k) 공간
       앞뒤로 붙는 전처리가 없다. 정렬도 좌표 압축도 쓰지 않는다
```

**약속으로 내놓는 것은 최악 보장 하나입니다.** 코드에 난수가 없으니 같은 배열과 같은 창 크기를 두 번 넣으면 같은
횟수가 나오고, 어떤 입력을 넣어도 `11N − 3k − 5` 아래라는 것이 조건 없이 성립합니다. 평균 쪽은 그 약속에 안
들어가요 — 구현이 만드는 무작위성이 아니라 **입력 분포를 하나 놓았을 때의 기댓값**이고, 실제 입력이 그 분포를
따르지 않으면 성립하지 않습니다.

#### 최악을 만드는 입력

「값이 큰 순서대로 늘어놓으면 느리다」가 이 절차에서는 반대입니다. 감소 수열은 뒤에서 버리는 일이 한 번도 없어
`P = 0` 이고, 접근이 적은 쪽이에요. 접근을 크게 하려면 **뒤에서 버리는 일과 멈추는 일을 동시에 많이** 만들어야
합니다. 모양이 다른 입력 여섯을 같은 길이 · 같은 창 크기로 재 봤어요.

<!--proof:worst-shape-->

| 입력의 모양 | 뒤에서 버림 P | 앞에서 버림 F | 멈춘 걸음 B | 가장 길 때 | 총식 | 실측 배열 접근 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 감소 수열 | 0 | 979 | 1,023 | 45 | 9,036 | 9,036 |
| 전부 같은 값 | 0 | 979 | 1,023 | 45 | 9,036 | 9,036 |
| 증가 수열 | 1,023 | 0 | 0 | 1 | 9,080 | 9,080 |
| 곱셈 나머지 | 1,009 | 13 | 974 | 4 | 10,999 | 10,999 |
| 창마다 큰 값 하나 · 나머지 증가 | 1,000 | 22 | 1,001 | 2 | 11,035 | 11,035 |
| 이웃 둘씩 자리를 바꾼 증가 수열 | 1,022 | 0 | 512 | 2 | 10,101 | 10,101 |

N = 1,024 · k = 45 입니다. 총식과 실측이 어긋난 줄은 0 개입니다.

<!--/proof-->

가장 많은 것은 **창마다 큰 값을 하나씩 심고 그 사이를 증가시킨 입력**입니다. 심어 둔 큰 값이 앞에 남아 걸음을
멈추게 하고, 그 사이의 증가하는 값들이 바로 앞 자리를 뒤에서 버리게 만들어요 — 총식의 `2B` 와 `3P` 가 함께 커지는
것이 이 모양입니다. 같은 모양을 `k = 3` · `N = 9` 로 적어 자리마다 따라가면 이렇습니다.

<!--proof:worst-n9-->

| 읽은 자리 | 앞에서 버린 자리 | 뒤에서 버린 자리 | 멈춘 뒤 자리 | 넣은 뒤 cand |
| --- | --- | --- | --- | --- |
| 0 · 값 100 | 없음 | 없음 | 없음 | [0] |
| 1 · 값 1 | 없음 | 없음 | 자리 0 | [0 1] |
| 2 · 값 2 | 없음 | 1 | 자리 0 | [0 2] |
| 3 · 값 99 | 0 | 2 | 없음 | [3] |
| 4 · 값 1 | 없음 | 없음 | 자리 3 | [3 4] |
| 5 · 값 2 | 없음 | 4 | 자리 3 | [3 5] |
| 6 · 값 98 | 3 | 5 | 없음 | [6] |
| 7 · 값 1 | 없음 | 없음 | 자리 6 | [6 7] |
| 8 · 값 2 | 없음 | 7 | 자리 6 | [6 8] |

입력은 [100 1 2 99 1 2 98 1 2] · k = 3 입니다. P = 5 · F = 2 · B = 6 이고, 배열 접근은 76 번입니다.

<!--/proof-->

심어 둔 큰 값이 앞에 남아 사이의 자리를 전부 멈추게 하고, 그 사이의 1 과 2 가 바로 앞 자리를 뒤에서 버립니다. 큰
값은 창 하나를 지나면 창 밖이 되어 앞에서 빠져요. 그러니 최악은 **값의 크기가 아니라 놓인 순서**가 만듭니다. 같은
값들을 다르게 늘어놓기만 해도 접근이 달라지고, 그 폭이 두 배 남짓이라 이 절차는 최악을 따로 걱정할 일이 없습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 창이 옮겨 갈 때 왼쪽 끝이 빠지는 것이 어려운 자리였고, 그래서
**지금의 답 하나가 아니라 앞으로 답이 될 자리 전부**를 자리 번호로 단조 덱에 담아 두었습니다. 오른쪽에 더 큰 값이
생긴 자리는 뒤에서, 창 밖으로 나간 자리는 앞에서 버렸고, 창이 다 찰 때마다 앞 자리의 값을 적었어요.

```text
빈 cand · 빈 result → 창 밖 앞 자리를 버린다 → cur 보다 작은 뒤 자리를 버린다 → i 를 넣는다 → 창이 찼으면 앞의 값을 적는다
                      └ 한 걸음에 많아야 한 번      └ 같은 값에서는 멈춘다
```

먼저 답이 붙는 문제 하나입니다. T5 를 마친 시점의 단조 덱은 `[1 2 3]` 이고 그 값이 3 · -1 · -3 이에요. 그런데
자리 2 와 자리 3 의 값은 창 `[1,3]` 의 답 3 에 한참 못 미칩니다. 지금 답에 아무 보탬도 안 되는 이 둘을 왜 담아
두었을까요?

<!--check:whyKeepSmallOnes-->
**자리 1 이 빠진 뒤에 답이 될 수 있는 자리**이기 때문입니다. 다음 창 `[2,4]` 에서 자리 1 은 밖이고, 그때 답이 될
수 있는 것은 자리 2 · 3 · 4 뿐이에요. 그 셋을 그 자리에서 찾으려면 창을 다시 읽어야 하는데, 미리 담아 두었으므로
앞에서 하나 빼는 것으로 끝납니다. 전개 입력에서는 T7 · T8 에서 값 5 가 둘을 함께 버려서 결과적으로 둘이 안
쓰였어요. 쓰이는 경우를 보려면 자리 4 의 값만 바꿔 보면 됩니다.

<!--proof:selfcheck-keep-small-->

| 입력 | nums | 창 [2,4] 의 답 | 그 답의 자리 | 자리 4 를 끝낸 뒤 cand |
| --- | --- | --- | --- | --- |
| 전개 입력 | [1 3 -1 -3 5 3 6 7] | 5 | 자리 4 | [4] |
| 자리 4 만 -2 로 바꾼 입력 | [1 3 -1 -3 -2 3 6 7] | -1 | 자리 2 | [2 4] |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「수식 정의와 유도」의 후보 집합 정의, 「비용을 세는 과정」의
T# 별 표와 「최악을 만드는 입력」, 「알아 두면 좋은 개념」의 팽창과 침식을 다시 보세요.

- 이 절차로 **창마다 최솟값**을 구하려면 어디를 고쳐야 할까요? 고칠 곳은 한 줄이고, 그 줄이 어느 갈래인지도 함께
  적어 보세요. `[1 3 -1 -3 5 3 6 7]` 에 `k = 3` 으로 답이 「시작하기 전에」 표의 둘째 줄과 같은지 확인해 보세요.
- 뒤에서 버리는 조건을 `<` 에서 `<=` 로 바꾸면 답은 안 갈리는데 단조 덱의 내용은 달라집니다. `[7 7 7 7]` 에
  `k = 2` 로 두 판본의 `cand` 를 자리마다 적어 보고, 단조 덱이 가장 길 때의 칸 수가 어느 쪽이 작은지, 그때 T# 로
  센 배열 접근이 어떻게 달라지는지 세어 보세요.
- 창이 오른쪽 끝이 아니라 **왼쪽 끝을 한 칸씩 줄이며** 왼쪽으로 옮겨 가는 과제라면 이 절차를 그대로 쓸 수
  있을까요? 못 쓴다면 어느 갈래가 성립하지 않는지 적고, 배열을 뒤집어 푸는 방법이 왜 되는지도 함께 적어 보세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Sliding Window Maximum

풀 파일: [`slidingWindowMaximum.ts`](./slidingWindowMaximum.ts) · 테스트: [`slidingWindowMaximum.test.ts`](./slidingWindowMaximum.test.ts) · 실행: `bun test src/algorithms/array/slidingWindowMaximum/slidingWindowMaximum.test.ts`

#### 한 줄 요약

> 정수 배열과 윈도우 크기 $k$를 받아, **크기 $k$의 윈도우가 왼쪽에서 오른쪽으로 이동하며 방문하는 각 위치의 최댓값**을 담은 배열을 반환한다.

#### 스토리

공기 질 모니터링 센터의 담당자 수빈은 연속된 $k$일의 오염 수치 중 최댓값을 각 일자별로 기록해야 한다.

센서 데이터는 날마다 들어온다. 수빈은 오늘 포함 직전 $k$일($k$일 구간)의 수치 중 가장 높은 값을 해당 일자의 대표값으로 기록한다.

윈도우가 배열 끝에 닿을 때까지 이 작업을 반복한 결과 배열을 반환해야 한다.

#### 함수 인터페이스

```ts
export function slidingWindowMaximum(nums: number[], k: number): number[];
```

- `nums` — 정수 배열.
- `k` — 윈도우의 크기 (연속된 원소의 개수).
- 반환 — 각 윈도우 위치의 최댓값을 순서대로 담은 배열. 길이는 $N - k + 1$.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `nums`의 길이)
- $1 \leq k \leq N$
- $-10{,}000 \leq nums[i] \leq 10{,}000$ (정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

윈도우 시작 인덱스 $i$는 $0, 1, \ldots, N - k$의 값을 가진다. 결과 배열의 $i$번째 원소는

$$\text{result}[i] = \max_{i \leq j < i + k}\, nums[j]$$

이다. 결과 배열의 길이는 정확히 $N - k + 1$이다. $k = 1$이면 배열 자체가 결과이고, $k = N$이면 원소 하나인 배열이 반환된다.

#### 예시

```ts
slidingWindowMaximum([1, 3, -1, -3, 5, 3, 6, 7], 3);
// [3, 3, 5, 5, 6, 7]

slidingWindowMaximum([5, 5, 5, 5], 2);    // [5, 5, 5]  — 모두 같은 값

slidingWindowMaximum([3, 1, 5, 2], 4);    // [5]  — k=N, 전체 최댓값 하나

slidingWindowMaximum([7], 1);             // [7]  — 단일 원소
```
