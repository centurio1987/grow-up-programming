# twoSum — 짝을 찾지 않고 보수를 해시 맵에서 조회하면 한 번만 지나가도 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 두 원소의
짝을 모두 맞춰 보는 방법에서 출발해, 앞에서 지나온 원소를 해시 맵에 적어 두고 조회 한 번으로 짝을
찾는 방법까지 갑니다. 마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

정수 배열에서 **합이 `target` 인 두 원소**를 찾아 그 인덱스를 돌려주는 과제를 다룹니다. 가장 먼저
떠오르는 방법은 두 원소를 골라 더해 보는 것이에요. 그런데 원소 하나를 정하고 나면, 짝이 될 원소의
값은 이미 정해져 있습니다. 원소 `x` 의 짝은 반드시 값이 `target − x` 여야 하니까요. 이 값을 `x` 의
**보수**라고 부르겠습니다. 짝을 찾는 대신 값 하나를 찾으면 됩니다. 배열 `[5 8 3 8 12 2]` 와 `target = 10` 으로 원소마다 보수를 적어 보면
이렇습니다.

<!--fig:concept-complement-->
![원소마다 보수가 하나로 정해진다 — 인덱스 5 의 보수 8 은 앞의 칸 1 · 3 에 있다](./figs/concept-complement.svg)

보수가 정해져 있으니, 짝을 찾는 일은 **「보수와 같은 값이 앞에 있었는가」를 묻는 일**로 바뀝니다.
인덱스 5 의 원소 2 는 보수가 8 이고, 앞에 8 이 두 번 있었어요. 그러면 둘 중 하나와 짝이 됩니다.
그 물음에 빨리 답하려고, 앞에서부터 지나가며 본 원소의 값과 인덱스를 적어 두는 자료구조를
씁니다. 값을 주면 그 값에 적어 둔 인덱스를 바로 꺼내 주는 자료구조이고, 이 글에서는 이것을
**해시 맵**이라고 부릅니다. JavaScript 의 `Map` 이 해시 맵이에요.

아래는 원소를 하나씩 지나가며, 그 원소를 보기 직전에 해시 맵에 무엇이 적혀 있는지 그린 것입니다.
`5→0` 은 「값 5 가 인덱스 0 에 있었다」라는 뜻이에요.

<!--proof:concept-states-->

| 지금 원소 | 보수 | 그 직전 해시 맵 | 보수 조회 결과 |
| --- | ---: | --- | --- |
| 인덱스 0 · 값 5 | 5 | 비어 있음 | 없다. 5→0 을 적는다 |
| 인덱스 1 · 값 8 | 2 | 5→0 | 없다. 8→1 을 적는다 |
| 인덱스 2 · 값 3 | 7 | 5→0 · 8→1 | 없다. 3→2 를 적는다 |
| 인덱스 3 · 값 8 | 2 | 5→0 · 8→1 · 3→2 | 없다. 8 의 인덱스를 3 으로 바꾼다 |
| 인덱스 4 · 값 12 | -2 | 5→0 · 8→3 · 3→2 | 없다. 12→4 를 적는다 |
| 인덱스 5 · 값 2 | 8 | 5→0 · 8→3 · 3→2 · 12→4 | 있다. 인덱스 3 과 짝이다 |

마지막 줄을 배열과 해시 맵 위에 놓으면 이렇습니다. 괄호가 해시 맵에 적어 둔 원소이고, 아래 두 줄이 그
해시 맵의 키와 인덱스예요.

<!--fig:concept-lookup-->
![인덱스 5 에서 보수 8 을 조회한다 — 해시 맵에는 앞 원소만 들어 있다](./figs/concept-lookup.svg)

원소마다 하는 일은 **보수를 해시 맵에서 한 번 조회하고, 없으면 지금 원소를 적는 것**뿐입니다. 앞
원소를 하나하나 다시 읽지 않아요. 그래서 배열을 앞에서 뒤로 **한 번만** 지나가면 짝이 나오고, 답은
`[3, 5]` 입니다. 조회를 먼저 하고 적기를 뒤에 하므로, 해시 맵에는 늘 지금 원소보다 앞에 있는
원소만 들어 있어요. 그래서 원소가 자기 자신과 짝이 되는 일이 없습니다.

| 방법 | 원소 하나에 하는 일 | 원소 `n` 개에 드는 일(최악) |
| --- | --- | --- |
| 두 원소를 모두 맞춰 보기 | 앞 원소를 전부 읽는다 | `n(n−1)/2` 번의 비교 |
| 보수를 해시 맵에서 조회하기 | 조회 1 번, 기록 1 번 | 조회 `n` 번 + 기록 `n−1` 번 |

해시 맵 조회 한 번에 드는 시간은 평균적으로 원소 수와 상관없이 일정하다고 봅니다. 그래서 전체 시간은
`O(n)` 이고, 대신 해시 맵이 원소를 최대 `n − 1` 개까지 담으므로 추가 메모리도 `O(n)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **해시 맵**(JavaScript `Map`)의 세 연산. `get(key)` 는 적어 둔 값을, 없으면 `undefined` 를 돌려주고,
  `set(key, value)` 는 적거나 이미 있는 키의 값을 바꾸며, 같은 키를 다시 `set` 하면 앞의 값이
  사라집니다. 해시 맵이 어떻게 평균 상수 시간에 조회하는지가 궁금하면
  [`hashMapChaining`](../../../data-structures/hash/hashMapChaining/hashMapChaining-guide.mdx) 을 먼저
  읽어 보세요.
- **배열을 앞에서부터 한 번 지나가는 반복문.** `for (let j = 0; j < nums.length; j++)` 로 원소를
  하나씩 봅니다.
- JavaScript 에서 **`0` 은 조건식에서 거짓으로 읽힌다**는 것. `if (0)` 은 실행되지 않습니다.

두 원소의 합을 묻는 물음 가운데 이 글이 다루는 범위를 배열 `[5 8 3 8 12 2]` 로 나눠 보면 이렇습니다.

| 물음 | 답 | 이 글에서 |
| --- | --- | --- |
| 합이 10 인 두 원소의 인덱스 하나 | `[3, 5]` | 다룬다 |
| 합이 10 인 짝이 몇 개인가 | 2 | 다루지 않는다. 짝을 하나 찾으면 멈추는 절차다 |
| 합이 10 인 연속 부분 배열 | — | 다루지 않는다. [`subarraySumEqualsK`](../subarraySumEqualsK/subarraySumEqualsK-guide.md) 에서 다룬다 |

### 아이디어를 떠올리는 과정 — 모든 짝 맞춰 보기에서 보수 조회까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 배열과 목표 합을 받아서
인덱스 두 개를 돌려줍니다.

```ts
function twoSum(nums: number[], target: number): [number, number];
```

- 입력: 정수 배열 `nums` 와 정수 `target` 을 받습니다.
- 출력: `nums[i] + nums[j] === target` 이고 `i < j` 인 인덱스 쌍 `[i, j]` 를 돌려줍니다. 같은 인덱스를
  두 번 쓰지 않아요. 그런 짝이 여럿이면 어느 것을 돌려줘도 됩니다. 짝이 하나도 없으면 오류를 던집니다.
- 규모: `2 ≤ n ≤ 100,000`, `−10^9 ≤ nums[k] ≤ 10^9`, `−2·10^9 ≤ target ≤ 2·10^9` 로 잡습니다. 비용은
  컴퓨터가 단순한 연산을 1 초에 1 억 번쯤 한다는 기준에 대어 잽니다.

이 글에서 쓰는 기호는 여섯 개입니다. 여기서 정한 뜻을 글 끝까지 그대로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 배열 `nums` 의 길이 | `n ≤ 100,000` |
| `target` | 두 원소의 합이 되어야 하는 값 | 전개 입력에서는 10 |
| `j` | 지금 보는 원소의 인덱스. 짝의 뒤쪽 인덱스가 됩니다 | `0 ≤ j ≤ n−1` |
| `i` | 짝의 앞쪽 인덱스 | `0 ≤ i < j` |
| `x` | 지금 원소의 값 `nums[j]`. 그 보수는 `target − x` 입니다 | `−10^9` 이상 `10^9` 이하 |
| `seen` | 해시 맵. 키는 앞에서 지나온 원소의 값, 값은 그 값의 인덱스입니다 | 항목이 `n − 1` 개 이하 |

출발점은 아무 기법도 쓰지 않는 방법이에요. 뒤 원소 `j` 마다 그 앞의 원소 `i` 를 처음부터 하나씩
더해 보고, 합이 `target` 이면 멈춥니다.

```ts
for (let j = 0; j < nums.length; j++) {
  for (let i = 0; i < j; i++) {
    if (nums[i] + nums[j] === target) return [i, j];
  }
}
```

이 방법이 얼마나 오래 걸리는지는 **두 원소의 합을 `target` 과 비교한 횟수**로 셉니다. 가장 오래
걸리는 것은 짝이 맨 끝 두 자리에만 있는 입력이고, 그때는 모든 짝 `n(n−1)/2` 개를 다 맞춰 봅니다.
그런 입력을 만들어 실제로 세었어요.

<!--proof:cost-scan-->

| n | 비교 횟수(실측) | n(n−1)/2 | 초당 1억 번 기준 |
| ---: | ---: | ---: | ---: |
| 6 | 15 | 15 | 0.01 초 미만 |
| 100 | 4,950 | 4,950 | 0.01 초 미만 |
| 1,000 | 499,500 | 499,500 | 0.01 초 미만 |
| 10,000 | 49,995,000 | 49,995,000 | 0.50 초 |
| 100,000 | (실행하지 않음) | 4,999,950,000 | 50.00 초 |

`n = 10,000` 이면 비교가 약 5 천만 번이라 0.5 초쯤 걸립니다. `n` 이 열 배인 100,000 이 되면 비교가 백
배인 약 50 억 번이 되어 50 초가 걸려요. 원소 수가 열 배가 될 때 일이 백 배가 되니, 규모를 조금만 키워도
쓸 수 없습니다.

느린 까닭을 찾으려고 안쪽 반복문이 하는 일을 한 줄씩 봅시다. 전개 입력 `[5 8 3 8 12 2]` · `target =
10` 에서 뒤 원소마다 안쪽 반복문이 몇 번 비교했는지 적었습니다.

<!--proof:origin-scan-walk-->

| j | x | 찾는 값 target − x | 앞 원소들의 값 | 비교 | 찾은 짝 |
| ---: | ---: | ---: | --- | ---: | --- |
| 0 | 5 | 5 | 없음 | 0 | 없음 |
| 1 | 8 | 2 | [5] | 1 | 없음 |
| 2 | 3 | 7 | [5 8] | 2 | 없음 |
| 3 | 8 | 2 | [5 8 3] | 3 | 없음 |
| 4 | 12 | -2 | [5 8 3 8] | 4 | 없음 |
| 5 | 2 | 8 | [5 8 3 8 12] | 2 | i = 1 |

비교는 모두 12 번이고 돌려준 답은 [1, 5] 입니다.

<!--/proof-->

「찾는 값」 열을 보면 안쪽 반복문이 사실은 **값 하나를 찾고 있다**는 것을 확인할 수 있습니다. `j = 4`
에서는 앞 원소 넷을 모두 읽었지만, 찾던 것은 −2 라는 값 하나였어요. 합을 매번 새로 더할 필요 없이
「앞 원소 가운데 −2 가 있는가」만 알면 됩니다. 그리고 `j` 가 하나 늘 때마다 앞 원소 목록은 원소
하나만 늘어나는데, 안쪽 반복문은 그 목록을 매번 처음부터 다시 읽습니다. 같은 일을 되풀이하는 셈이에요.

그렇다면 앞 원소를 **값으로 바로 찾을 수 있게 적어 두면** 어떨까요. 같은 입력을 두 방식으로 처리해
세었습니다. 방식 A 는 앞의 이중 반복이고, 방식 B 는 앞 원소의 값과 인덱스를 적어 두고 보수를 한 번
조회하는 방법입니다.

<!--proof:origin-two-ways-->

| j | x | 방식 A 의 비교 | 방식 B 의 조회 |
| ---: | ---: | ---: | ---: |
| 0 | 5 | 0 | 1 |
| 1 | 8 | 1 | 1 |
| 2 | 3 | 2 | 1 |
| 3 | 8 | 3 | 1 |
| 4 | 12 | 4 | 1 |
| 5 | 2 | 2 | 1 |

방식 A 는 비교 12 번으로 [1, 5] 를, 방식 B 는 조회 6 번과 기록 5 번으로 [3, 5] 를 냈습니다.

<!--/proof-->

방식 A 의 비교 횟수는 `j` 를 따라 0, 1, 2, 3, 4 로 늘어나고, 방식 B 의 조회는 줄마다 1 번입니다. 방식
B 는 짝이 없던 원소를 하나씩 적어 두는 데 기록 5 번을 더 썼어요. 두 방식이 낸 답이 다른 것은
`[1, 5]` 와 `[3, 5]` 가 둘 다 합이 10 인 짝이기 때문이고, 어느 쪽이 나오는지는 뒤의 「짚고 가기」에서
실행으로 확인합니다. 여기서 관찰할 것은 **방식 B 의 원소 하나당 일이 앞 원소 수와 상관없이 한 번**이라는
점입니다.

남은 질문은 「값으로 바로 찾을 수 있게 적어 두는」 자료구조를 무엇으로 하느냐입니다. 가장 단순한
후보부터 시험해 봅시다. 원소의 값을 **배열의 칸 번호**로 쓰면, `pos[v]` 한 칸만 읽어 값 `v` 의 인덱스를
바로 꺼낼 수 있어요. 문제는 칸 수가 원소 수가 아니라 **값의 범위**로 정해진다는 것입니다.

<!--proof:origin-direct-address-->

| 값의 범위 | 배열의 칸 수 | 8 바이트 기준 | 해시 맵의 항목 수 |
| --- | ---: | ---: | --- |
| 전개 입력(2 이상 12 이하) | 11 | 88 바이트 | 4 |
| 0 이상 1,000 이하 | 1,001 | 8,008 바이트 | n − 1 이하 |
| −10^9 이상 10^9 이하 | 2,000,000,001 | 14.90 GiB | n − 1 이하(n = 100,000 이면 99,999) |

전개 입력처럼 값이 2 부터 12 까지면 11 칸이면 됩니다. 하지만 값이 `−10^9` 부터 `10^9` 까지 올 수
있으면 칸이 약 20 억 개, 메모리로 14.90 GiB 가 필요해요. 원소가 10 만 개뿐이어도 적어 둘 것은 많아야
99,999 개인데, 값의 범위 전체에 칸을 잡느라 거의 모든 칸이 빈 칸으로 남습니다.

그래서 칸을 값의 범위만큼이 아니라 **적어 둔 원소 수만큼만** 쓰면서, 값으로 바로 찾는 자료구조가
필요합니다. 그것이 해시 맵이에요. 해시 맵은 키를 정해진 규칙으로 작은 칸 번호로 바꿔 그 칸에 적어
두므로, 항목 수에 비례하는 메모리로 값을 평균 상수 시간에 조회합니다. 지금까지 시험한 방법을
차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

아직 확인하지 않은 것이 남아 있습니다. 해시 맵에 정확히 무엇을 적는지, 보수를 언제 조회하는지,
조회와 기록의 순서가 왜 그래야 하는지예요. 다음 절에서 이 방법을 실현하는 순서대로 하나씩
확인합니다.

### 아이디어 상세 — 지나온 원소를 담은 해시 맵에서 보수 조회하기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **배열을 앞에서부터 지나가며, 원소마다 보수가 해시 맵에
있는지 조회하고, 없으면 그 원소의 값과 인덱스를 해시 맵에 적습니다.** 실현하는 순서대로 세 단계로
나누면 아래와 같고, 세 단계 모두 원소마다 한 번씩 합니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 해시 맵에 적을 것 정하기 | 키와 값을 무엇으로 둘지 정한다 | — |
| 2단계 보수를 계산해 조회하기 | `target − x` 를 키로 조회한다 | 1단계의 키(원소의 값) |
| 3단계 조회한 뒤에 지금 원소 적기 | 짝이 없으면 `x → j` 를 적는다 | 1단계의 키와 값 · 2단계의 조회 결과 |

#### 1단계 — 해시 맵에 적을 것 정하기

해시 맵에는 키 하나에 값 하나를 적습니다. 무엇을 키로 둘지는 무엇으로 찾을지가 정해요. 2단계에서
조회할 것은 보수, 곧 원소의 **값**이므로 키는 원소의 값입니다. 찾은 뒤에 돌려줘야 하는 것은 그 원소의
**인덱스**이므로, 해시 맵의 값에는 인덱스를 적어요. 전개 입력으로 짝을 찾은 순간의 해시 맵 전체를
펼치면 아래와 같습니다.

<!--fig:build-map-final-->
![짝을 찾은 순간의 해시 맵 — 키는 원소의 값, 값은 그 값이 마지막으로 나온 인덱스](./figs/build-map-final.svg)

키마다 그 키를 적은 걸음을 함께 적으면 이렇습니다.

<!--proof:build-map-final-->

| 키(원소의 값) | 값(인덱스) | 이 키를 적은 걸음 |
| ---: | ---: | --- |
| 5 | 0 | j = 0 |
| 8 | 3 | j = 1 · j = 3 |
| 3 | 2 | j = 2 |
| 12 | 4 | j = 4 |

원소 6 개 가운데 앞의 5 개를 적었고, 값이 같은 원소가 둘이라 항목은 4 개입니다.

<!--/proof-->

키 8 은 두 걸음이 적었습니다. `j = 1` 에서 `8 → 1` 을 적었고, `j = 3` 에서 같은 키에 3 을 적어 1 이
사라졌어요. 해시 맵은 키 하나에 값을 하나만 두므로, 같은 값이 다시 나오면 **나중 인덱스**가 남습니다.
그래도 키 8 이 있다는 사실은 그대로라서 「보수 8 이 앞에 있었는가」라는 물음의 답은 바뀌지 않아요.
이 점이 답을 틀리게 하지 않는지는 「수행으로 알아보는 알고리즘」의 「짚고 가기」에서 여러 입력으로
확인합니다.

해시 맵의 크기도 여기서 정해집니다. 짝을 찾는 걸음에서는 적지 않으므로 기록은 많아야 `n − 1` 번이고,
같은 값이 겹치면 항목은 그보다 적어요. 전개 입력에서는 기록이 5 번, 항목이 4 개였습니다.

#### 2단계 — 보수를 계산해 조회하기

원소 `x = nums[j]` 를 보면 먼저 보수 `target − x` 를 계산하고, 그 값을 키로 해시 맵을 조회합니다.
조회는 「그 키가 있으면 적힌 인덱스, 없으면 `undefined`」를 돌려줘요. 걸음마다 보수와 조회 결과를
적으면 이렇습니다.

<!--proof:build-lookup-->

| j | x | 보수 | 해시 맵에 있는 키 | 조회 결과 |
| ---: | ---: | --- | --- | --- |
| 0 | 5 | 10 − 5 = 5 | 없음 | 없음 |
| 1 | 8 | 10 − 8 = 2 | 5 | 없음 |
| 2 | 3 | 10 − 3 = 7 | 5 8 | 없음 |
| 3 | 8 | 10 − 8 = 2 | 5 8 3 | 없음 |
| 4 | 12 | 10 − 12 = -2 | 5 8 3 | 없음 |
| 5 | 2 | 10 − 2 = 8 | 5 8 3 12 | 있음, 인덱스 3 |

여섯 걸음 가운데 조회가 성공한 것은 `j = 5` 하나이고, 보수 8 이 키로 있어 인덱스 3 이 나왔습니다. 짝은
`i = 3`, `j = 5` 예요. 눈여겨볼 걸음이 둘 있습니다. `j = 4` 의 보수는 −2 인데, 배열에 음수가 하나도
없어도 보수는 음수가 될 수 있고 그대로 조회하면 됩니다. `j = 1` 과 `j = 3` 은 보수가 둘 다 2 이지만,
2 가 배열의 맨 끝에 있어서 두 걸음 모두 조회에 실패해요. 짝은 **뒤 원소 쪽에서** 찾아지므로, 앞 원소
8 과 뒤 원소 2 의 짝은 2 를 볼 때 발견됩니다.

| 짝 `(i, j)` | 앞 원소를 볼 때 | 뒤 원소를 볼 때 |
| --- | --- | --- |
| (3, 5) · 값 8 과 2 | `j = 3` · 보수 2 가 아직 해시 맵에 없다 | `j = 5` · 보수 8 이 해시 맵에 있다 |

어느 짝이든 뒤 원소를 볼 때에는 앞 원소가 이미 해시 맵에 적혀 있습니다. 그래서 짝이 하나라도 있으면
배열을 끝까지 가기 전에 반드시 찾아요.

#### 3단계 — 조회한 뒤에 지금 원소 적기

조회에 실패하면 지금 원소를 `x → j` 로 해시 맵에 적고 다음 원소로 갑니다. 여기서 순서가 중요합니다.
**조회를 먼저 하고 적기를 뒤에 해야** 해시 맵에 지금 원소가 들어 있지 않은 채로 조회해요. 전개 입력의
첫 원소 5 는 보수도 5 라서, 순서를 바꾸면 결과가 달라집니다.

<!--proof:build-order-->

| 순서 | 조회할 때의 해시 맵 | 보수 5 조회 | 그 걸음의 결과 |
| --- | --- | --- | --- |
| 조회하고 적는다 | 비어 있음 | 없음 | 5→0 을 적고 다음 원소로 간다 |
| 적고 조회한다 | 5→0 | 인덱스 0 | [0, 0] 을 돌려준다 |

적고 나서 조회하면 방금 적은 자기 자신이 보수로 나와 `[0, 0]` 을 돌려줍니다. 같은 인덱스를 두 번 쓴
답이라 틀린 답이에요. 조회를 먼저 하면 해시 맵이 비어 있어 짝이 없다고 판단하고, 5 를 적은 뒤 다음
원소로 갑니다. 반대로 `[3 3]` · `target = 6` 처럼 값이 같은 **두** 원소가 짝이면, 뒤의 3 을 볼 때 앞의
3 이 이미 적혀 있으므로 조회를 먼저 해도 `[0, 1]` 을 찾습니다. 이 순서를 코드로 바꿔 실행한 결과는
「불변식」 절에서 봅니다.

#### 이 방법이 기대는 전제

보수 조회는 아래 전제에 기대고 있어서, 하나라도 빠지면 답이 틀리거나 비용이 달라집니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 합이 `target` 인지가 값의 **같음**으로 판정된다 | 2단계 보수를 키로 조회한다 | 「합이 `target` 에 가장 가까운 짝」처럼 같음이 아닌 조건이면 조회로 찾을 수 없다 |
| 키를 정확히 비교할 수 있다 | 1단계 원소의 값을 키로 둔다 | 부동소수 `0.1 + 0.2` 는 `0.3` 과 다른 키라 조회에 실패한다 |
| 해시 맵 조회가 평균 상수 시간이다 | 2·3단계를 원소마다 한 번씩 한다 | 조회가 느린 구조를 쓰면 원소 하나의 일이 커진다 |
| 짝을 하나만 찾으면 된다 | 짝을 찾는 걸음에서 바로 돌려준다 | 짝을 모두 세려면 멈추지 않고 인덱스 목록을 적어야 한다 |

부동소수 줄은 실제 값으로 확인할 수 있습니다. 배열 `[0.1 0.2]` 와 `target = 0.3` 을 정본에 넣었어요.

<!--proof:build-float-->

| 배열 | target | 0.1 + 0.2 | j = 1 의 보수 | 키 0.1 과의 비교 | 정본의 답 |
| --- | ---: | --- | --- | --- | --- |
| [0.1 0.2] | 0.3 | 0.30000000000000004 | 0.09999999999999998 | 다르다 | 오류(짝 없음) |

두 원소를 더하면 `0.3` 이 아니라 `0.30000000000000004` 이고, 보수도 `0.1` 이 아닌 값이 나와 조회에
실패합니다. 사람이 보기에는 짝인데 정본은 짝이 없다고 답해요. 이 글의 과제는 정수 배열이라 이 전제가
성립합니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 원소 하나마다 세 걸음이 됩니다. 이렇게 하면 `n = 100,000` 에서 약
50 억 번이던 비교가 조회 10 만 번과 기록 10 만 번 미만으로 줄어요.

1. 빈 해시 맵을 만들고 원소를 앞에서부터 하나씩 본다
2. 지금 원소의 보수를 해시 맵에서 조회해, 있으면 두 인덱스를 돌려준다
3. 없으면 지금 원소의 값과 인덱스를 해시 맵에 적는다

### 수행으로 알아보는 알고리즘 — 여섯 원소를 지나며 해시 맵에서 짝을 찾는다

아이디어를 확인했으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 정해 끝까지
가져가되, 코드 조각을 하나 만들 때마다 그 조각만 실행한 결과를 확인하고 다음으로 넘어갑니다.

```ts
const nums = [5, 8, 3, 8, 12, 2];
const target = 10;
// 이 절이 끝나면 [3, 5] 가 나와야 한다
```

이 입력을 고른 까닭은 두 갈래와 걸리기 쉬운 자리가 모두 들어 있기 때문입니다. 짝이 없는 걸음이
다섯 번, 짝을 찾는 걸음이 한 번 나와요. 8 이 두 번 나와 해시 맵의 인덱스가 바뀌고, 12 의 보수는 음수
−2 이며, 첫 원소 5 는 보수가 자기 자신입니다.

```text
절차 전체를 한 장으로

    빈 해시 맵 seen 을 만든다
    j 를 0 부터 n−1 까지 올리며:
        x = nums[j], 보수 target − x 를 seen 에서 조회한다
        있으면 [그 인덱스, j] 를 돌려준다                ① 짝을 찾음
        없으면 seen 에 x → j 를 적는다                   ② 짝이 없음
    끝까지 없으면 오류를 던진다
```

#### 1. 빈 해시 맵을 만들고 원소를 하나씩 읽는다

해시 맵은 비어 있는 채로 시작합니다. 아직 지나온 원소가 없기 때문이에요. 반복문은 인덱스 `j` 를
0 부터 올리며 원소 `x` 를 하나씩 꺼냅니다.

```ts
const seen = new Map<number, number>();
for (let j = 0; j < nums.length; j++) {
  const x = nums[j] as number;
  // 2 와 3 의 조각이 여기에 들어간다
}
```

이 조각만 실행하면 `j` 와 `x` 가 이렇게 나옵니다. 걸음마다 `T1` 부터 `T6` 까지 이름을 붙여 두고 끝까지
그 이름으로 부릅니다.

<!--fig:walk-loop-->
![원소마다 걸음 하나 — T1~T6](./figs/walk-loop.svg)

아직 아무것도 적지 않았으므로 `seen` 은 여섯 걸음 내내 비어 있습니다.

`nums[j] as number` 는 타입만 좁히는 표기입니다. `j` 가 배열 안이므로 값이 `undefined` 일 수 없다는 것을
TypeScript 에 알리는 것이고, 실행에는 아무 영향이 없어요.

#### 2. 보수를 계산해 해시 맵에서 조회한다

원소마다 보수를 계산해 조회하고, 결과가 있으면 바로 돌려줍니다.

```ts
const i = seen.get(target - x);
if (i !== undefined) {
  // ① 짝을 찾음 — 앞에서 지나온 원소 가운데 보수가 있다.
  return [i, j];
}
```

첫 걸음 `T1` 과 마지막 걸음 `T6` 에서 이 조각이 어떻게 판단하는지 보겠습니다.

<!--proof:walk-lookup-->

| 걸음 | j | x | target - x | 조회할 때의 해시 맵 | i | i !== undefined |
| --- | ---: | ---: | ---: | --- | --- | --- |
| T1 | 0 | 5 | 5 | 비어 있음 | undefined | 거짓 |
| T6 | 5 | 2 | 8 | 5→0 · 8→3 · 3→2 · 12→4 | 3 | 참 |

`T1` 에서는 해시 맵이 비어 있어 `i` 가 `undefined` 이고, 조건이 거짓이라 돌려주지 않습니다. `T6` 에서는
보수 8 이 키로 있어 `i = 3` 이 나오고, 조건이 참이라 `[3, 5]` 를 돌려줘요. 여기서 가장 중요한 부분은
조건식 `i !== undefined` 입니다. 「조회 결과가 있는가」를 묻는 조건인데, 짧게 줄여 쓰고 싶어지는
자리이기도 해요.

#### 짚고 가기 — `if (i)` 로 검사하면 인덱스 0 인 짝을 놓친다

여기서 헷갈리기 쉬운 부분은 조건식입니다. 「`get` 이 없으면 `undefined` 를 돌려주니, `if (i)` 로 써도
같지 않나」라고 생각하기 쉬워요. 그렇게 바꾼 줄은 이렇습니다.

```ts
if (i) { // ← i !== undefined 대신
```

정본과 이렇게 바꾼 코드를 여덟 입력에 함께 실행해 보았습니다.

<!--proof:pause-truthy-->

| 입력 | 인덱스 0 이 나온 조회 | 정본 | if (i) 로 검사한 판 | 판정 |
| --- | ---: | --- | --- | --- |
| 전개 입력 [5 8 3 8 12 2] · target 10 | 0 | [3, 5] | [3, 5] | 같다 |
| [2 7 11 15] · target 9 | 1 | [0, 1] | 오류(짝 없음) | 어긋난다 |
| [3 2 4] · target 6 | 0 | [1, 2] | [1, 2] | 같다 |
| [3 3] · target 6 | 1 | [0, 1] | 오류(짝 없음) | 어긋난다 |
| [-1 -2 3] · target 1 | 0 | [1, 2] | [1, 2] | 같다 |
| [-3 4 -7] · target -10 | 1 | [0, 2] | 오류(짝 없음) | 어긋난다 |
| [0 5 0] · target 0 | 1 | [0, 2] | 오류(짝 없음) | 어긋난다 |
| [1 2] · target 3 | 1 | [0, 1] | 오류(짝 없음) | 어긋난다 |

「인덱스 0 이 나온 조회」 열이 1 인 다섯 줄이 모두 틀렸고, 0 인 세 줄은 답이 같습니다. JavaScript 에서
`0` 은 조건식에서 거짓으로 읽히므로, 짝의 앞 원소가 **인덱스 0** 에 있으면 조회가 성공해도 `if (i)` 가
그것을 「없음」으로 처리해요. 그러면 지금 원소를 적고 지나가고, 짝이 그 하나뿐이면 끝까지 못 찾아 오류가
납니다.

| 조회 결과 `i` | `i !== undefined` | `if (i)` |
| --- | --- | --- |
| `undefined` | 거짓 | 거짓 |
| `0` | 참 | **거짓** |
| `3` | 참 | 참 |

전개 입력은 짝이 `[3, 5]` 라서 이 차이가 나타나지 않습니다. 이렇게 **짝이 인덱스 0 을 쓰지 않는
입력에서는 답이 틀리지 않으므로**, 몇몇 예시만 확인하면 틀린 줄 모르고 넘어가기 쉬워요. 그래도 고쳐야
하는 까닭은 위 표의 가운데 줄입니다. 짝의 앞 원소가 배열의 첫 원소인 입력은 흔하고, 그때마다 답이
사라집니다.

#### 3. 짝이 없으면 지금 원소를 해시 맵에 적는다

조회에 실패한 걸음에서만 이 줄에 옵니다. 지금 원소를 적어 두어야 뒤 원소가 그것을 보수로 찾을 수
있어요.

```ts
// ② 짝이 없음 — 지금 원소를 적어 두고 다음 원소로 간다.
seen.set(x, j);
```

짝이 없던 다섯 걸음 `T1` 부터 `T5` 까지 이 줄이 해시 맵을 어떻게 바꾸는지 적었습니다.

<!--proof:walk-map-growth-->

| 걸음 | j | 실행한 줄 | 해시 맵에 일어난 일 | 걸음 뒤 해시 맵 |
| --- | ---: | --- | --- | --- |
| T1 | 0 | seen.set(5, 0) | 새 키 | 5→0 |
| T2 | 1 | seen.set(8, 1) | 새 키 | 5→0 · 8→1 |
| T3 | 2 | seen.set(3, 2) | 새 키 | 5→0 · 8→1 · 3→2 |
| T4 | 3 | seen.set(8, 3) | 키 8 의 값 1 을 3 으로 바꾼다 | 5→0 · 8→3 · 3→2 |
| T5 | 4 | seen.set(12, 4) | 새 키 | 5→0 · 8→3 · 3→2 · 12→4 |

`T4` 에서 같은 키 8 을 다시 적어, 값이 1 에서 3 으로 바뀌었습니다. 해시 맵의 항목 수는 3 개 그대로예요.
여기서 가장 중요한 것은 이 줄이 **조회보다 뒤에** 있다는 점입니다. 그래서 조회하는 순간의 해시 맵에는
지금 원소가 없어요.

#### 짚고 가기 — 같은 값이 다시 나오면 앞 인덱스를 덮어써도 짝을 잃지 않는다

여기서 헷갈리기 쉬운 부분은 `T4` 의 덮어쓰기입니다. 「인덱스 1 을 지웠으니, 인덱스 1 과 짝이 되는 원소가
뒤에 오면 못 찾지 않나」라고 걱정하기 쉬워요. 처음 인덱스를 지키도록 바꾼 코드와 정본을 함께 실행해
봅시다.

```ts
if (!seen.has(x)) seen.set(x, j); // ← 처음 나온 인덱스만 적는다
```

| --- | ---: | --- | --- | --- |
| 전개 입력 [5 8 3 8 12 2] · target 10 | 1 | [3, 5] | [1, 5] | 어긋난다 |
| [2 7 11 15] · target 9 | 0 | [0, 1] | [0, 1] | 같다 |
| [3 2 4] · target 6 | 0 | [1, 2] | [1, 2] | 같다 |

| [-3 4 -7] · target -10 | 0 | [0, 2] | [0, 2] | 같다 |

| [1 2] · target 3 | 0 | [0, 1] | [0, 1] | 같다 |

전개 입력에서 두 판의 답이 갈립니다. 정본은 `[3, 5]`, 처음 인덱스를 지키는 판은 `[1, 5]` 를 냈어요.
그러면 한쪽이 틀린 것일까요? 두 답이 모두 짝인지, 짝을 찾은 걸음 `j` 가 같은지를 확인해 보았습니다.

**두 판 모두 여덟 입력에서 합이 `target` 인 짝을 냈고, 짝을 찾은 걸음 `j` 도 모두 같습니다.** 덮어쓰기가
바꾸는 것은 키에 적힌 인덱스뿐이고, 키가 해시 맵에 **있는지**는 바꾸지 않기 때문이에요. 조회가
성공하는지는 키가 있는지만으로 정해지므로, 두 판은 같은 걸음에서 조회에 성공하고 앞 인덱스만 다르게
꺼냅니다.

| 비교할 것 | 정본(나중 인덱스) | 처음 인덱스를 지키는 판 |
| --- | --- | --- |
| 짝을 찾는 걸음 `j` | 같다 | 같다 |
| 꺼내는 앞 인덱스 `i` | 그 값이 마지막으로 나온 자리 | 그 값이 처음 나온 자리 |
| 원소 하나에 드는 일 | 조회 1 번 + 기록 1 번 | 조회 1 번 + 존재 확인 1 번 + 기록 0~1 번 |

그래서 이 과제처럼 「짝 하나면 된다」면 덮어써도 됩니다. 반대로 「그런 짝 가운데 `i` 가 가장 작은
것」을 요구하면 처음 인덱스를 지켜야 하고, 그때는 위 판처럼 `has` 로 한 번 더 확인합니다.

#### 4. 여섯 원소를 끝까지 따라가며 짝을 찾는다

지금까지 만든 조각을 하나로 이어 고정 입력에 실행하면 걸음이 여섯 개 나옵니다. 걸음마다 무대의 괄호
「본 원소」는 지금까지 본 원소이고, ▲ 는 이번에 보는 원소예요. 맨 아래 두 줄이 해시 맵이고, 점선 칸은
아직 안 적은 자리, 강조 칸은 이번에 적거나 인덱스를 바꾼 키, 키 아래 ▲ 는 조회해서 찾은 키입니다.

| 걸음 | j | x | target - x | i | i !== undefined | 갈래 | 걸음 뒤 해시 맵 또는 반환 |
| --- | ---: | ---: | ---: | --- | --- | --- | --- |
| T1 | 0 | 5 | 5 | undefined | 거짓 | ② | 5→0 |
| T2 | 1 | 8 | 2 | undefined | 거짓 | ② | 5→0 · 8→1 |
| T3 | 2 | 3 | 7 | undefined | 거짓 | ② | 5→0 · 8→1 · 3→2 |
| T4 | 3 | 8 | 2 | undefined | 거짓 | ② | 5→0 · 8→3 · 3→2 |
| T5 | 4 | 12 | -2 | undefined | 거짓 | ② | 5→0 · 8→3 · 3→2 · 12→4 |

**두 갈래가 모두 실행됐습니다.** ② 는 `T1` 부터 `T5` 까지 다섯 번, ① 은 `T6` 에서 한 번이에요. `T5` 의
보수 −2 는 해시 맵에 없어 ② 로 갔고, `T6` 의 보수 8 은 `T4` 가 적은 `8→3` 에서 찾았습니다.

| 갈래 | 하는 일 | 걸음 | 해시 맵 연산 |
| --- | --- | --- | --- |
| ① | 짝을 돌려준다 | T6 | 조회 1 번 |
| ② | 지금 원소를 적는다 | T1 T2 T3 T4 T5 | 조회 5 번 + 기록 5 번 |

해시 맵 연산은 모두 11 번이고, 「아이디어를 떠올리는 과정」의 방식 B 와 같습니다.

#### 5. 전체 코드

조각을 하나로 이어 붙입니다. 앞에서 확인한 것 말고 새로 들어간 것은 반복문이 끝까지 짝을 못 찾았을
때 오류를 던지는 마지막 줄뿐이에요. 짝이 있는 입력에서는 그 줄에 오지 않습니다.

```ts
export function twoSum(nums: number[], target: number): [number, number] {
  // 해시 맵에는 지금 원소보다 앞에 있는 원소만 들어 있다. 키는 원소의 값, 값은 그 값이
  // 마지막으로 나온 인덱스다.
  const seen = new Map<number, number>();
  for (let j = 0; j < nums.length; j++) {
    const x = nums[j] as number;
    const i = seen.get(target - x);
    if (i !== undefined) {
      // ① 짝을 찾음 — 앞에서 지나온 원소 가운데 보수가 있다.
      return [i, j];
    }
    // ② 짝이 없음 — 지금 원소를 적어 두고 다음 원소로 간다.
    seen.set(x, j);
  }
  throw new Error("합이 target 인 두 원소가 없다");
}
```

여러 입력에 실행한 결과입니다.

<!--proof:final-examples-->

| 호출 | 결과 |
| --- | --- |
| twoSum([5, 8, 3, 8, 12, 2], 10) | [3, 5] |
| twoSum([2, 7, 11, 15], 9) | [0, 1] |
| twoSum([3, 3], 6) | [0, 1] |
| twoSum([-3, 4, -7], -10) | [0, 2] |
| twoSum([1, 2, 3], 100) | 오류(짝 없음) |

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 절차를 따져 봅니다. 어떤 과제에 이 절차가 맞는지, 해시 맵이 무엇을 늘 참으로 유지하는지,
비용이 얼마인지를 차례로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때 보수 조회가 가장 알맞습니다.

- 두 원소의 관계가 **한쪽 값을 정하면 다른 쪽 값이 하나로 정해지는** 꼴입니다. 합이 `target` 이면 보수
  `target − x`, 차가 `d` 이면 `x − d` 와 `x + d` 처럼 찾을 값이 식으로 나와야 조회할 수 있어요.
- 찾을 값을 **같음으로** 비교할 수 있습니다. 정수·문자열은 되고, 오차를 허용하는 부동소수 비교는 안 됩니다.
- 입력이 **정렬되어 있지 않고**, 돌려줄 것이 원래 **인덱스**입니다. 정렬하면 인덱스를 따로 기억해야 해요.
- 원소 수만큼의 **추가 메모리**를 쓸 수 있습니다.

| 조건 | 코드에 나타나는 모양 |
| --- | --- |
| 찾을 값이 식으로 정해진다 | `seen.get(target - x)` 한 줄로 찾는다 |
| 같음으로 비교한다 | 해시 맵의 키로 쓴다 |
| 정렬 안 된 입력 · 인덱스를 돌려준다 | 해시 맵의 값에 인덱스를 적는다 |
| 추가 메모리 `O(n)` | 해시 맵이 항목을 `n − 1` 개까지 담는다 |

#### 문제에서 이것을 떠올리게 하는 단서

| 보이는 곳 | 이런 말이나 모양 | 뜻 | 보수 조회 |
| --- | --- | --- | --- |
| 지문 | "합이 target 인 두 원소" "두 수의 합" | 한쪽을 정하면 다른 쪽 값이 정해진다 | 쓴다 |
| 지문 | "차이가 k 인 쌍" "짝을 이루는 값" | 찾을 값이 `x ± k` 로 정해진다 | 쓴다 |
| 지문 | "인덱스를 반환" "위치를 출력" | 정렬하면 원래 자리를 잃는다 | 쓴다 |
| 제약 | N 이 10^5 이상이고 시간 제한이 1 초 | 모든 짝을 맞춰 보면 시간 안에 못 든다 | 쓴다 |
| 지문 | "정렬된 배열이 주어진다" | 두 포인터가 추가 메모리 없이 푼다 | 따져 본다 |
| 지문 | "합이 target 에 가장 가까운 두 수" | 같음이 아니라 조회로 못 찾는다 | 못 쓴다 |
| 지문 | "합이 k 인 연속 부분 배열의 개수" | 원소가 아니라 접두 합의 짝이다 | 접두 합에 적용한다 |

마지막 줄은 같은 생각을 접두 합에 적용한 것입니다. 구간의 합을 접두 합 두 개의 차로 바꾸면 「차가 `k` 인
접두 합의 짝」이 되고, 그 짝을 해시 맵에서 조회해요.
[`subarraySumEqualsK`](../subarraySumEqualsK/subarraySumEqualsK-guide.md) 가 그 과제를 다룹니다.

#### 실제로 쓰이는 곳

- **PostgreSQL 의 해시 조인** — `src/backend/executor/nodeHashjoin.c` 는 파일 머리에서 자기 일을
  `"Routines to handle hash join nodes"` 로 적고, `"Note: the relation we build hash table on is the
  'inner' the other one is 'outer'."` 라고 설명합니다. 한쪽 테이블의 행을 조인 키로 해시 테이블에 적어
  두고, 다른 쪽 행마다 같은 키가 있는 칸을 조회하는 구조예요. 조회를 맡는 `nodeHash.c` 의
  `ExecScanHashBucket` 은 주석이 `"scan a hash bucket for matches to the current outer tuple"` 입니다.
  이 글과 다른 점은 한쪽 테이블을 **먼저 다 적어 두고** 조회한다는 것이에요. 두 입력이 서로 다른
  테이블이라 같은 원소를 두 번 쓸 걱정이 없기 때문입니다.
  ([nodeHashjoin.c](https://github.com/postgres/postgres/blob/master/src/backend/executor/nodeHashjoin.c) ·
  [nodeHash.c](https://github.com/postgres/postgres/blob/master/src/backend/executor/nodeHash.c), 조회
  2026-09-29)
- **ECMAScript 명세의 `Map`** — 이 글의 코드가 쓰는 `Map` 의 비용 근거입니다. 명세의 Map Objects 절은
  `"Maps must be implemented using either hash tables or other mechanisms that, on average, provide
  access times that are sublinear on the number of elements in the collection."` 라고 적어요. 명세가
  약속하는 것은 **평균** 접근 시간이 원소 수보다 느리게 늘어난다는 것까지입니다.
  ([ECMA-262 Keyed Collections](https://tc39.es/ecma262/multipage/keyed-collections.html), 조회
  2026-09-29)

| 출처 | 해시 테이블에 적는 것 | 조회하는 것 | 적기와 조회의 순서 |
| --- | --- | --- | --- |
| PostgreSQL 해시 조인 | 안쪽 테이블의 행 | 바깥쪽 행의 조인 키 | 다 적은 뒤 조회한다 |
| 이 글 | 지나온 원소의 값 → 인덱스 | 지금 원소의 보수 | 원소마다 조회한 뒤 적는다 |

두 출처 모두 「찾을 키를 해시 테이블에서 조회한다」는 같고, 무엇을 적어 두는지와 적는 시점만 다릅니다.

#### 경쟁 설계와의 대조

같은 목표를 이루는 다른 절차로 **정렬 후 두 포인터**가 있습니다. 값을 오름차순으로 정렬한 뒤 왼쪽 끝과
오른쪽 끝에 포인터를 하나씩 두고, 두 값의 합이 `target` 보다 작으면 왼쪽 포인터를, 크면 오른쪽 포인터를
한 칸 옮겨요. 정렬 안 된 입력이면 원래 인덱스를 돌려주려고 인덱스 배열을 만들어 값 기준으로 정렬합니다.

| 설계 | 원소를 찾는 법 | 정렬 안 된 입력에서 드는 일 | 추가 칸 |
| --- | --- | --- | --- |
| 해시 맵 | 보수를 조회한다 | 조회·기록 `2n − 1` 번 이하 | 해시 맵 항목 `n − 1` 개 이하 |
| 정렬 후 두 포인터 | 합의 크기로 포인터를 옮긴다 | 정렬 비교 `n log n` 규모 + 포인터 비교 `n − 1` 번 이하 | 인덱스 배열 `n` 칸(입력이 정렬돼 있으면 0) |

두 설계에 같은 입력을 주고 **기본 연산**과 **추가 칸**을 세었습니다. 기본 연산은 해시 맵 조회·기록 한 번과
값 비교 한 번을 각각 1 로 셉니다. 해시 맵 쪽은 조회·기록 호출 수이고, 두 포인터 쪽은 값 비교 수(병합 정렬의
비교 + 두 합을 `target` 과 비교한 수)예요. 두 설계 모두 보수 계산의 뺄셈, 합을 만드는 덧셈, 포인터 이동은 세지
않습니다. 추가 칸은 해시 맵의 항목 수와 인덱스 배열의 길이이고, 병합 정렬이 잠시 잡는 배열과 재귀 스택은 넣지
않았어요. 배열은
`n = 2,048` 이고 `nums[k] = (733k) mod 4099` 이며, 4099 가 소수라 값이 모두 다릅니다. `target` 은 이 배열의
마지막 두 원소의 합 3,800 이에요. 정렬된 입력은 같은 값을 오름차순으로 놓은 것이고 `target` 도 같습니다.
전개에서 쓰는 여섯 칸짜리 입력은 정렬의 비교가 열 번 남짓이라 차이가 상수에 가려지므로, 여기서는 규모를
키운 입력을 따로 씁니다.

| 입력 | 해시 맵 기본 연산 | 두 포인터 기본 연산 | 해시 맵 추가 칸 | 두 포인터 추가 칸 |
| --- | ---: | ---: | ---: | ---: |
| 정렬 안 된 입력 | **4095** | 20379 | 2047 | 2048 |
| 정렬된 입력 | 3585 | **367** | 1792 | **0** |

<!--proof:alt-ratio-->

**입력이 정렬돼 있는가가 순서를 뒤집습니다.** 정렬 안 된 입력에서는 해시 맵이 기본 연산 4,095 로 두 포인터의 20,379 보다 약 5 배 적어요.

<!--/proof-->

두 포인터가 정렬에만 비교를 약 2 만 번 쓰기 때문입니다. 같은 값이 정렬된
채로 오면 두 포인터는 정렬을 건너뛰어 367 번이면 되고, 추가 칸도 0 입니다. 해시 맵은 입력이 정렬됐는지를
쓰지 못해 3,585 번과 1,792 칸을 그대로 씁니다.

**이 절차가 내주는 것은 추가 메모리입니다.** 해시 맵은 입력 모양과 상관없이 지나온 원소를 모두 적어
두므로, 정렬된 입력이 주어져도 메모리를 아끼지 못해요. 그 대가로 얻는 것은 정렬하지 않아도 된다는 점과,
원래 인덱스를 따로 기억할 필요가 없다는 점입니다.

| 조건 | 고를 설계 | 까닭 |
| --- | --- | --- |
| 정렬 안 된 입력 · 인덱스를 돌려준다 | 해시 맵 | 정렬 비교 `n log n` 을 쓰지 않는다 |
| 입력이 이미 정렬돼 있다 | 두 포인터 | 기본 연산과 추가 칸이 모두 적다 |
| 추가 메모리를 쓸 수 없다 | 정렬 후 두 포인터(제자리 정렬) | 해시 맵은 항목을 `n − 1` 개까지 담는다 |
| 값을 같음으로 비교할 수 없다 | 정렬 후 두 포인터 | 크기 비교만으로 포인터를 옮긴다 |

### 불변식 — j 번째 원소를 조회하기 직전 해시 맵의 키는 앞 원소의 값 전부이고 앞부분에는 짝이 없다

파트 1 에서 코드가 동작하는 모습을 여섯 걸음으로 확인했습니다. 하지만 그것은 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. **매 걸음 참으로 남는 것**이 무엇인지 문장으로 세우고, 그것이
실제로 유지되는지 확인해 봅시다.

> 원소 `j` 의 보수를 조회하기 직전마다, 해시 맵의 키는 `nums[0..j−1]` 에 나온 값 전부이고, 키마다
> 그 값이 `j` 앞에서 마지막으로 나온 인덱스가 적혀 있습니다. 그리고 `nums[0..j−1]` 안에는 합이
> `target` 인 짝이 없습니다.

<!--fig:invariant-prefix-->
![j = 4 를 조회하기 직전 — 키는 nums[0..3] 의 값 전부, 값은 그 값의 마지막 인덱스](./figs/invariant-prefix.svg)

| 문장 | 참인 것 | 지키는 코드 |
| --- | --- | --- |
| 앞 문장 | 해시 맵에 앞 원소만, 빠짐없이 들어 있다 | 조회 뒤에 오는 기록 줄 `seen.set(x, j)` |
| 뒤 문장 | 앞부분에 짝이 있었다면 이미 돌려줬다 | 짝을 찾으면 바로 돌려주는 조건문 |

앞 문장이 조회를 정확하게 만들고, 뒤 문장이 **처음 찾은 짝에서 멈춰도 되는** 근거가 됩니다. 두 문장이
합쳐지면 답에 대한 결론이 나와요. 원소 `j` 의 보수가 앞 원소 가운데 있으면 앞 문장 때문에 조회가
성공하고, 그 인덱스는 `j` 보다 작습니다. 짝이 하나라도 있으면 그 짝의 뒤 원소에 이르렀을 때 조회가
성공하므로 반드시 돌려줘요.

**출발점부터 봅시다.** `j = 0` 에서는 앞 원소가 없고 해시 맵도 비어 있어, 두 문장이 모두 참입니다. 그
뒤로는 걸음마다 둘 중 하나가 일어나요.

| 걸음에서 일어난 일 | 앞 문장이 다음 걸음에도 참인 근거 | 뒤 문장이 다음 걸음에도 참인 근거 |
| --- | --- | --- |
| 조회 성공 | 돌려주고 끝나므로 다음 걸음이 없다 | 다음 걸음이 없다 |
| 조회 실패 · 새 키 | `x → j` 를 더해 키가 `nums[0..j]` 의 값 전부가 된다 | `x` 의 짝이 앞에 없었으므로 `nums[0..j]` 에도 짝이 없다 |
| 조회 실패 · 있던 키 | 키 목록은 그대로이고 그 키의 인덱스가 `j` 로 바뀐다 | 위와 같다 |

이것을 전개 입력의 걸음마다 실제 값으로 확인합니다. 조회 직전 해시 맵을 앞 원소 목록과 비교하고, 앞부분의
짝 수를 이중 반복으로 직접 세었어요.

<!--proof:invariant-states-->

| 걸음 | 앞 원소 nums[0..j−1] | 조회 직전 해시 맵 | 키마다 적힌 인덱스 | 앞부분의 짝 수 |
| --- | --- | --- | --- | ---: |
| T1 | 없음 | 비어 있음 | 마지막 인덱스 | 0 |
| T2 | [5] | 5→0 | 마지막 인덱스 | 0 |
| T3 | [5 8] | 5→0 · 8→1 | 마지막 인덱스 | 0 |
| T4 | [5 8 3] | 5→0 · 8→1 · 3→2 | 마지막 인덱스 | 0 |
| T5 | [5 8 3 8] | 5→0 · 8→3 · 3→2 | 마지막 인덱스 | 0 |
| T6 | [5 8 3 8 12] | 5→0 · 8→3 · 3→2 · 12→4 | 마지막 인덱스 | 0 |

6 걸음 모두에서 키 목록이 앞 원소의 값 목록과 같았고, 불변식이 깨진 걸음은 0 개입니다.

<!--/proof-->

경계에 있는 입력도 확인하고 넘어갑시다. 「이중 반복과 비교」 열은 정본의 답이 합이 `target` 인 짝이고
`i < j` 이며, 짝을 찾은 걸음 `j` 가 이중 반복과 같은지를 본 것입니다.

<!--proof:invariant-edges-->

| 경계 | 배열 | target | 답 | 이중 반복과 비교 |
| --- | --- | ---: | --- | --- |
| 원소 둘 | [1 2] | 3 | [0, 1] | 같다 |
| 같은 값 둘 | [3 3] | 6 | [0, 1] | 같다 |
| 0 이 둘 | [0 5 0] | 0 | [0, 2] | 같다 |
| 음수 목표 | [-3 4 -7] | -10 | [0, 2] | 같다 |
| 음수가 섞임 | [-1 -2 3] | 1 | [1, 2] | 같다 |
| 짝이 맨 끝(n = 10,000) | 0 이 9,998 개 · 99 · 1 | 100 | [9998, 9999] | 같다 |
| 원소 하나 | [5] | 10 | 오류(짝 없음) | 둘 다 짝이 없다 |

원소가 둘뿐이면 `j = 1` 에서 바로 찾고, 같은 값 3 이 둘이면 뒤의 3 을 볼 때 앞의 3 이 키로 있어
`[0, 1]` 이 나옵니다. 0 이 둘인 `[0 5 0]` 도 같은 까닭으로 `[0, 2]` 예요. 원소가 하나뿐이면 조회가 한 번
실패하고 반복문이 끝나 오류를 던집니다.

**이제 코드 한 곳을 바꿔 확인해 봅시다.** 앞 문장을 지키는 것은 기록 줄이 조회 **뒤에** 있다는 순서예요.
조회하는 줄에서 지금 원소를 먼저 적도록 바꾸면, 조회하는 순간의 해시 맵에 `nums[j]` 까지 들어가서 「키는
`nums[0..j−1]` 의 값」이라는 문장이 깨집니다.

```ts
const i = seen.set(x, j).get(target - x); // ← 조회하기 전에 지금 원소를 먼저 적는다
```

<!--proof:mutant-write-first-->

| 입력 | 보수가 자기 자신인 걸음 | 정본 | 먼저 적는 판 | 판정 |
| --- | ---: | --- | --- | --- |
| 전개 입력 [5 8 3 8 12 2] · target 10 | 1 | [3, 5] | [0, 0] | 어긋난다 |
| [2 7 11 15] · target 9 | 0 | [0, 1] | [0, 1] | 같다 |
| [3 2 4] · target 6 | 1 | [1, 2] | [0, 0] | 어긋난다 |
| [3 3] · target 6 | 2 | [0, 1] | [0, 0] | 어긋난다 |
| [-1 -2 3] · target 1 | 0 | [1, 2] | [1, 2] | 같다 |
| [-3 4 -7] · target -10 | 0 | [0, 2] | [0, 2] | 같다 |
| [0 5 0] · target 0 | 2 | [0, 2] | [0, 0] | 어긋난다 |
| [1 2] · target 3 | 0 | [0, 1] | [0, 1] | 같다 |

보수가 자기 자신인 걸음이 있는 네 입력에서 모두 `[0, 0]` 이 나왔습니다. 전개 입력은 첫 원소 5 의 보수가
5 라서, 방금 적은 `5→0` 을 찾아 `i = j = 0` 을 돌려줬어요.

| 코드 | `T1` 에서 조회하는 순간의 해시 맵 | 보수 5 조회 | 결과 |
| --- | --- | --- | --- |
| 바른 코드 | 비어 있음 | `undefined` | 5→0 을 적고 다음 걸음 |
| 바꾼 코드 | 5→0 | 0 | `[0, 0]` — 같은 인덱스를 두 번 썼다 |

「보수가 자기 자신인 걸음」 열이 0 인 네 줄은 답이 같습니다. 그 입력들에서는 먼저 적은 자기 자신이 조회에
걸릴 일이 없었을 뿐이에요. 답이 같은 것은 우연입니다. **답이 같다고 해서 해가 없다는 뜻은 아니라는 것**을
보이려고 이 열을 두었어요.

### 비용 계산

#### 비용을 세는 과정

원소 하나에 하는 일은 조회 한 번이고, 짝이 없으면 기록 한 번이 더해집니다. 전개 입력의 걸음으로 보면 조회가
`T1` 부터 `T6` 까지 여섯 번, 기록이 `T1` 부터 `T5` 까지 다섯 번이었어요. 정본을 실행하며 해시 맵 연산을
세면 이렇습니다.

<!--proof:perf-walk-->

| 하는 일 | 걸음 | 횟수 |
| --- | --- | ---: |
| 조회 seen.get | T1 T2 T3 T4 T5 T6 | 6 |
| 기록 seen.set | T1 T2 T3 T4 T5 | 5 |
| 합 |  | 11 |

짝을 `j` 번째 원소에서 찾으면 조회는 `j + 1` 번, 기록은 `j` 번입니다. 가장 늦게 찾는 것은 `j = n − 1` 일
때이므로 조회 `n` 번과 기록 `n − 1` 번, 합해서 `2n − 1` 번이 해시 맵 연산의 최댓값이에요. 짝이 맨 끝에만
있는 입력으로 규모를 늘려 실제로 세었습니다.

<!--proof:perf-scale-->

| n | 조회(실측) | 기록(실측) | 합 | 2n − 1 | 이중 반복의 비교 n(n−1)/2 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 6 | 6 | 5 | 11 | 11 | 15 |
| 1,000 | 1,000 | 999 | 1,999 | 1,999 | 499,500 |
| 10,000 | 10,000 | 9,999 | 19,999 | 19,999 | 49,995,000 |
| 100,000 | 100,000 | 99,999 | 199,999 | 199,999 | 4,999,950,000 |

네 규모 모두 실측이 `2n − 1` 과 같습니다. `n = 100,000` 에서 해시 맵 연산은 약 20 만 번이고, 이중 반복의
비교 약 50 억 번의 2 만 5 천분의 1 이에요. 여기서 센 것은 **해시 맵 연산 수**이고, 연산 하나에 드는 시간은
해시 맵 구현이 정합니다.

| 항목 | 횟수 | `n = 100,000` 일 때(최악) |
| --- | --- | ---: |
| 보수 계산(뺄셈) | 조회와 같은 수 | 100,000 |
| 해시 맵 조회 | `j + 1` 번, 최대 `n` 번 | 100,000 |
| 해시 맵 기록 | `j` 번, 최대 `n − 1` 번 | 99,999 |
| 추가 칸 | 해시 맵 항목 최대 `n − 1` 개 | 99,999 |

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 서로 다른 축입니다. 「최악은 `O`, 평균은 `Θ`」처럼
한쪽을 다른 쪽에 짝지으면 안 돼요. 아래 표는 해시 맵 연산 하나를 상수 시간으로 볼 때의 시간입니다.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (짝이 `[0, 1]`) | `O(1)` | `Θ(1)` — 조회 2 번 + 기록 1 번 |
| **평균적인 경우** | 정의되지 않는다 — 짝의 자리가 입력마다 정해지고 그 분포가 과제에 없다 | — |
| **최악의 경우** (짝의 뒤 원소가 맨 끝) | `O(n)` | `Θ(n)` — 조회 `n` 번 + 기록 `n − 1` 번 |

평균을 정의하지 않은 까닭은 비용이 **짝의 뒤 원소가 놓인 자리 하나로** 정해지기 때문입니다. 그 자리가
어떤 분포를 따르는지 과제가 말하지 않으므로, 평균을 적으면 분포를 지어내는 셈이에요.

**총식을 한 번은 정확히 적어 둡니다.** 짝의 뒤 원소가 인덱스 `j` 에 있을 때입니다.

| 자원 | 총식 | 이루는 것 | 최악 `n = 100,000` 일 때 |
| --- | --- | --- | --- |
| 해시 맵 연산 | `(j + 1) + j = 2j + 1` | 조회 `j + 1` 번 + 기록 `j` 번 | 199,999 번 |
| 시간 | `Θ(j + 1)` 번의 해시 맵 연산, 최악 `Θ(n)` | 연산마다 해시 맵의 평균 접근 시간 | — |
| 추가 메모리 | 항목 `j` 개 이하, 최악 `Θ(n)` | 해시 맵 | 99,999 항목 |

**보장의 종류는 둘로 갈립니다.** 해시 맵 연산 수 `2j + 1` 은 입력이 정해지면 정확히 정해지는 값이라
최악 보장이에요. 반면 연산 하나의 시간은 해시 맵이 약속하는 평균입니다. 그 평균은 입력 분포에 대한
것이 아니라, 해시 맵이 키를 칸 번호로 바꿀 때 서로 다른 키가 같은 칸에 몰리는 정도에 대한 것이에요.

| 대상 | 보장의 종류 | 기댓값의 근거 |
| --- | --- | --- |
| 해시 맵 연산 수 | 최악 보장 — 입력마다 정확히 `2j + 1` 번 | — |
| 연산 하나의 시간 | 평균 — 명세는 「원소 수보다 느리게 늘어난다」까지만 약속한다 | 해시 맵 구현이 키를 칸에 나누는 방식 |

그래서 「`O(n)` 시간」은 **해시 맵 조회가 평균 상수 시간이라는 가정 아래의 값**입니다. 키가 한 칸에
몰리는 입력이 오면 연산 하나가 느려질 수 있고, 그 정도는 엔진의 해시 맵 구현에 달려 있어요.

#### 최악을 만드는 입력

해시 맵 연산 수를 가장 많이 만드는 방법은 **짝의 뒤 원소를 맨 끝에 두는 것**입니다. 값이 정렬됐는지나
짝의 앞 원소가 어디 있는지는 상관없어요. 「정렬된 배열이면 빠르다」나 「느리다」 같은 생각이 여기서도
맞는지 `n = 10,000` 에서 짝의 자리와 값의 순서를 바꿔 가며 세었습니다.

<!--proof:worst-position-->

| 입력의 모양 | 답 | 조회 | 기록 | 합 |
| --- | --- | ---: | ---: | ---: |
| 짝이 맨 앞 | [0, 1] | 2 | 1 | 3 |
| 짝이 가운데 | [4999, 5000] | 5,001 | 5,000 | 10,001 |
| 짝이 맨 끝 | [9998, 9999] | 10,000 | 9,999 | 19,999 |
| 짝이 맨 앞과 맨 끝 | [0, 9999] | 10,000 | 9,999 | 19,999 |
| 오름차순 · 짝이 맨 끝 | [9998, 9999] | 10,000 | 9,999 | 19,999 |
| 내림차순 · 짝이 맨 앞 | [0, 1] | 2 | 1 | 3 |

**연산 수를 정하는 것은 답의 뒤 인덱스 하나뿐입니다.** 답이 `[9998, 9999]` 인 두 줄과 `[0, 9999]` 인 줄은
모두 19,999 번이에요. 짝의 앞 원소가 맨 앞이든 끝에서 두 번째 자리든 같고, 값이 오름차순이어도 같습니다. 같은
오름차순 배열을 뒤집어 짝이 맨 앞에 오면 3 번으로 끝나요. 그래서 최악은 값의 모양이 아니라 **짝의 뒤
원소가 끝에 있는** 입력이고, 그때 해시 맵 연산은 `2n − 1` 번입니다.

| 규모 | 해시 맵 연산 | 해시 맵 항목 | 기준 |
| --- | ---: | ---: | --- |
| `n = 100,000` | 199,999 번 | 99,999 개 | 초당 1 억 번 기준으로 0.01 초 미만 |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하겠습니다. 원소 하나를 정하면 짝의 값은 보수 `target − x` 로 정해지므로,
앞에서 지나온 원소를 해시 맵에 적어 두고 **보수를 한 번 조회**하면 짝을 찾습니다. 조회를 적기보다 먼저
하는 것이 같은 원소를 두 번 쓰지 않게 하는 근거예요.

| 순서 | 하는 일 | 규모 |
| ---: | --- | --- |

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Two Sum

풀 파일: [`twoSum.ts`](./twoSum.ts) · 테스트: [`twoSum.test.ts`](./twoSum.test.ts) · 실행: `bun test src/algorithms/array/twoSum/twoSum.test.ts`

#### 한 줄 요약

> 함수는 정수 배열과 목표값을 받아, 합이 목표값이 되는 두 원소의 인덱스를 반환한다.

#### 스토리

쇼핑몰 계산대에서 직원이 정확히 목표 금액을 만들기 위해 선반에서 두 상품을 골라야 한다. 선반에는 다양한 가격의 상품들이 순서대로 놓여 있고, 두 상품의 가격 합이 정확히 목표 금액이 되어야 한다.

같은 상품을 두 번 가져갈 수는 없다. 문제에서는 합이 목표값이 되는 두 상품의 쌍이 반드시 존재한다고 보장한다.

두 상품이 선반 위 몇 번째에 있는지 인덱스 쌍으로 반환하라.

#### 함수 인터페이스

```ts
export function twoSum(nums: number[], target: number): [number, number];
```

- `nums` — 길이 $N$인 정수 배열
- `target` — 두 원소의 합이 되어야 하는 목표값
- 반환 — `nums[i] + nums[j] === target`을 만족하는 인덱스 쌍 `[i, j]` ($i < j$)

#### 제약 조건

- $2 \leq N \leq 10{,}000$ ($N$은 `nums`의 길이)
- `nums`의 원소는 정수 (음수 포함 가능)
- 합이 `target`이 되는 두 인덱스는 반드시 존재한다
- 같은 인덱스를 두 번 사용하지 않는다
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

배열 `nums`와 정수 `target`이 주어질 때, `nums[i] + nums[j] === target`이고 $i \neq j$인 두 인덱스 $(i, j)$를 찾아 `[i, j]` 형태로 반환한다. $i < j$가 되도록 작은 인덱스를 먼저 반환한다.

#### 예시

```ts
twoSum([2, 7, 11, 15], 9);
// [0, 1] — nums[0]=2, nums[1]=7, 2+7=9

twoSum([3, 2, 4], 6);
// [1, 2] — nums[1]=2, nums[2]=4, 2+4=6

twoSum([3, 3], 6);
// [0, 1] — 같은 값이지만 서로 다른 인덱스

twoSum([-1, -2, 3], 1);
// [1, 2] — nums[1]=-2, nums[2]=3, -2+3=1

twoSum([0, 5, 0], 0);
// [0, 2] — nums[0]=0, nums[2]=0, 0+0=0

twoSum([-3, 4, -7], -10);
// [0, 2] — nums[0]=-3, nums[2]=-7, -3+(-7)=-10
```
