# 합이 k 인 구간 세기 — 구간을 하나씩 재지 않고 지나온 누적합의 개수만 묻는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 모든 구간을
하나씩 더하는 방법에서 출발해 누적합의 짝을 개수 맵으로 세는 방법까지 가고, 그 방법을 단계마다 값으로
푼 뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

정수 배열에서 **합이 정확히 `k` 인 연속 부분 배열이 몇 개인지** 세는 과제입니다. 시작과 끝이 다르면 합이
같아도 따로 세고, 원소에는 음수가 섞일 수 있어요. `nums = [3 4 7 2 -3 1 4 2]`, `k = 7` 에서 합이 7 인
구간을 모두 찾으면 이렇습니다.

<!--proof:concept-ranges-->

| 구간 | 더한 값 | 누적합 두 칸의 차 |
| --- | --- | --- |
| [0,1] | 3 + 4 = 7 | P[2] − P[0] = 7 − 0 = 7 |
| [2,2] | 7 = 7 | P[3] − P[2] = 14 − 7 = 7 |
| [2,5] | 7 + 2 + (-3) + 1 = 7 | P[6] − P[2] = 14 − 7 = 7 |
| [5,7] | 1 + 4 + 2 = 7 | P[8] − P[5] = 20 − 13 = 7 |

구간 36 개를 모두 직접 더해 보면 합이 7 인 것이 4 개이고, 4 개 모두 두 칸의 차가 더한 값과 같습니다.

<!--/proof-->

셋째 열의 `P` 는 **누적합**입니다. `P[j]` 는 `nums` 의 앞 `j` 개를 더한 값이고, `P[0]` 은 아무것도 더하지
않은 0 이에요. 구간 `[l, r]` 의 합은 앞 `r + 1` 개의 합에서 앞 `l` 개의 합을 뺀 `P[r+1] − P[l]` 이라, 합이
`k` 인 구간을 세는 일은 **차이가 `k` 인 누적합의 짝 `(i, j)`(단 `i < j`)를 세는 일**과 같아집니다.

짝을 셀 때 오른쪽 칸 `j` 를 하나로 정하면, 짝이 될 왼쪽 칸의 값은 `P[j] − k` 하나로 정해져요. 그러니
「`j` 보다 앞 칸 중에 값이 `P[j] − k` 인 칸이 몇 개인가」만 물으면 됩니다. 이 물음에 한 번에 답하려고
**지금까지 지나온 누적합을 키로, 그 값이 나온 횟수를 값으로 담은 해시 맵**을 둡니다. 이 글은 이 해시 맵을
**개수 맵**이라고 부르고, 코드에서는 `seen` 이에요. 칸 6 에서 개수 맵에 묻는 모습을 그리면 이렇습니다.

<!--fig:concept-lookup-->
![칸 6 에서 개수 맵에 7 을 묻는다 — 찾은 개수 1 이 곧 합이 7 인 구간 [2,5] 하나](./figs/concept-lookup.svg)

`P[6] = 14` 에서 7 을 빼면 찾는 키는 7 이고, 개수 맵에 키 7 이 한 번 들어 있습니다. 그 한 번이 `P[2]` 이고,
짝 `(2, 6)` 이 곧 맨 위 괄호의 구간 `[2,5]` 예요. 개수 맵에는 칸 6 보다 **앞의 누적합만** 들어 있어서,
찾은 개수를 그대로 답에 더하면 됩니다. 칸을 왼쪽부터 하나씩 옮기며 「묻고, 적고」를 되풀이하면 원소마다
개수 맵 연산 몇 번으로 끝나요. 결과만 적으면 `O(n)` 입니다.

<!--proof:concept-scale-->

```text
n = 100,000  구간 5,000,050,000 개  구간을 하나씩 재면 이만큼 본다
             맵 연산 300,001 번     원소마다 개수 맵에 묻고 적는다
```

원소에 음수가 섞인다는 조건이 이 방법을 고르게 합니다. 누적합이 한 방향으로만 커지지 않고 줄었다 늘었다
하기 때문에, 오래된 누적합을 버리지 못하고 **지나온 것을 전부** 개수 맵에 남겨야 해요.

<!--proof:concept-negative-->

```text
누적합  0 → 3 → 7 → 14 → 16 → 13 → 14 → 18 → 20
    └ 칸 5 에서 값이 줄었다. nums[4] = -3 을 더한 칸이다
```

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **연속 부분 배열**이 무엇인지. 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 것이고, 원소를
  골라 담는 부분집합과 다릅니다.
- **누적합 배열**이 무엇인지. 칸 `j` 에 앞 `j` 개의 합을 담고, 구간 합을 두 칸의 차로 만드는 배열이에요.
  흐릿하면 [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 를 먼저 봅니다.
  이 글은 그 배열을 만들지 않고 값 하나만 가지고 지나가지만, 칸 번호를 붙이는 방식은 같습니다.
- **해시 맵**(자바스크립트의 `Map`)에서 키로 값을 찾고 넣는 일. 키 하나를 찾거나 넣는 데 드는 시간이 맵의
  크기와 상관없이 평균적으로 상수라는 것도 씁니다.
- 배열을 한 번 지나가는 `for` 루프와, 배열 인덱스가 `0` 부터 시작한다는 것.

「합이 `k` 인 구간이 몇 개인가」와 「합이 조건을 만족하는 구간 중 가장 긴 것」은 다른 과제입니다. 뒤쪽은
[`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-guide.md) 이 다루는
것이고, 이 글은 **개수**를 셉니다. 같은 배열에서 두 과제를 나란히 놓으면 이렇습니다.

<!--proof:prereq-two-tasks-->

| 과제 | 답의 모양 | [3 4 7 2 -3 1 4 2] 에서의 답 |
| --- | --- | --- |
| 합이 7 인 구간 세기 — 이 글이 하는 것 | 개수 | 4 |
| 합이 7 이하인 가장 긴 구간 | 길이 | 5 |

### 아이디어를 떠올리는 과정 — 모든 구간 더하기에서 누적합 짝 세기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열과 찾을 합을 받아서,
합이 그 값인 연속 부분 배열의 개수를 돌려줍니다.

```ts
function subarraySumEqualsK(nums: number[], k: number): number;
```

- 입력: 정수 배열 `nums` 와 찾을 합 `k`. 원소와 `k` 모두 음수일 수 있습니다.
- 출력: 합이 정확히 `k` 인 연속 부분 배열의 개수. 시작이나 끝이 다르면 따로 셉니다. 없으면 `0`.
- 규모: 배열 길이 `n` 이 100,000 까지, 원소는 −10,000 이상 10,000 이하, `k` 는 `−10^9` 이상 `10^9`
  이하입니다. 비용은 흔한 채점 환경의 예산인 1 초 · 256 MB 에 대어 잽니다.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 배열 `nums` 의 길이 | `n ≤ 100,000` |
| `k` | 찾을 구간 합 | `−10^9` 이상 `10^9` 이하 |
| `nums[i]` | 배열의 `i` 번째 값 | `−10,000` 이상 `10,000` 이하 |
| `l` · `r` | 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ n−1` |
| `P[j]` | 누적합 — `nums` 의 앞 `j` 개 원소의 합. 코드에서는 지금 칸의 값 하나를 변수 `prefix` 로 가집니다 | 칸이 `n+1` 개 |
| `seen` | 개수 맵 — 지나온 누적합을 키로, 그 값이 나온 횟수를 값으로 담는 해시 맵 | 키가 많아야 `n+1` 개 |
| `answer` | 지금까지 센 구간의 개수. 끝나면 이 값이 답입니다 | `0 ≤ answer ≤ n(n+1)/2` |

가장 먼저 떠오르는 방법은 왼쪽 끝 `l` 을 하나 정하고 오른쪽 끝 `r` 을 늘려 가며 합을 재는 것을, 모든 왼쪽
끝에 대해 되풀이하는 것이에요.

```ts
let answer = 0;
for (let l = 0; l < n; l++) {
  let sum = 0;
  for (let r = l; r < n; r++) {
    sum += nums[r] as number; // 오른쪽 끝을 한 칸 넓히고 값을 더한다
    if (sum === k) answer++;
  }
}
```

이 방법은 답을 틀리지 않습니다. 다만 원소에 음수가 있어 합이 커졌다 작아졌다 하니 중간에 멈출 근거가
없고, 어떤 입력에서도 구간을 **전부** 봐야 해요. 구간 하나에 덧셈 하나로 세면 이렇습니다.

<!--proof:origin-cost-->

| n | 구간의 수 | 초당 1 억 번 기준 | 구한 방법 |
| ---: | ---: | ---: | --- |
| 1,000 | 500,500 | 0.00501 초 | 실행해서 셌다 |
| 10,000 | 50,005,000 | 0.5 초 | 실행해서 셌다 |
| 100,000 | 5,000,050,000 | 50 초 | n(n+1)/2 로 냈다 |

실행해서 센 n = 1,000 · 10,000 에서 덧셈 수가 n(n+1)/2 와 정확히 같았습니다.

<!--/proof-->

`n` 이 상한 100,000 이면 구간이 50 억 개이고, 초당 1 억 번으로 잡아도 50 초입니다. 예산 1 초의 쉰
배예요. 이 50 억 안에서 같은 덧셈을 몇 번이나 되풀이하는지 보려고, 원소 여덟 개짜리 전개 입력에서 왼쪽 끝
셋이 더한 합을 적었습니다.

<!--proof:origin-repeat-->

```text
nums 의 값        3 4 7 2 -3 1 4 2
l = 0 이 더한 합  3 → 7 → 14 → 16 → 13 → 14 → 18 → 20
l = 1 이 더한 합  4 → 11 → 13 → 10 → 11 → 15 → 17
l = 2 이 더한 합  7 → 9 → 6 → 7 → 11 → 13
    └ 세 줄이 인덱스 2 부터 뒤쪽을 모두 다시 더했다
```

첫 줄은 앞에서부터의 합, 곧 누적합을 이미 다 가지고 있는데 아래 줄들이 뒷부분을 처음부터 다시 더합니다.
누적합을 한 번만 만들어 두면 어떤 구간이든 뺄셈 하나로 나와요.

<!--proof:origin-reuse-->

```text
앞 6 개의 합  3 + 4 + 7 + 2 + (-3) + 1 = 14  P[6]
앞 2 개의 합  3 + 4 = 7                      P[2]
두 합의 차    14 − 7 = 7                     구간 [2,5] 의 합이 뺄셈 하나로 나온다
```

이제 두 방식을 같은 입력에 실제로 실행해 **기본 연산**(덧셈·뺄셈 한 번, 뒤에 나올 개수 맵의
조회·읽기·쓰기 한 번을 각각 1)을 셉니다. 한쪽은 구간마다 처음부터 더하는 것이고,
다른 쪽은 누적합을 한 번 만들어 두고 오른쪽 끝마다 앞 칸 전부와 한 번씩 빼 보는 것이에요.

<!--proof:origin-two-ways-->

| 오른쪽 끝 r | 구간마다 직접 더하기의 덧셈 | 누적합 두 칸의 뺄셈 |
| ---: | ---: | ---: |
| 0 | 1 | 1 |
| 1 | 3 | 2 |
| 2 | 6 | 3 |
| 3 | 10 | 4 |
| 4 | 15 | 5 |
| 5 | 21 | 6 |
| 6 | 28 | 7 |
| 7 | 36 | 8 |

직접 더하기는 덧셈 120 번이고, 누적합은 만드는 덧셈 8 번과 뺄셈 36 번입니다. 답은 둘 다 4 입니다.

<!--/proof-->

누적합이 120 을 36 으로 줄였지만, 36 은 여전히 구간의 수 그대로입니다. 오른쪽 열은 오른쪽 끝마다 **앞 칸
수만큼** 늘어나요. 여기서 관찰할 것은 그 뺄셈들이 무엇을 묻고 있는가입니다. 오른쪽 끝이 `r` 이면 뺄셈
`r + 1` 번이 모두 「앞 칸 중에 값이 `P[r+1] − k` 인 칸이 있는가」라는 **한 가지 물음**을 칸마다 따로 묻고
있어요. 물음이 하나인데 칸 수만큼 읽는 것이 비용입니다.

그 물음을 한 번에 답하는 방법을 꺼내기 전에, 더 단순한 후보부터 시험해 봅시다. 첫 후보는 원소가 음수가
아닐 때 쓰는 방법 — 창의 두 끝을 오른쪽으로만 옮기면서, 합이 `k` 를 넘으면 왼쪽 끝을 당겨 창을 줄이는
것이에요. 칸마다 한 번씩만 들어가고 나오니 연산이 `n` 에 비례합니다. 네 입력에 실행했습니다.

<!--proof:origin-window-->

| 입력 | k | 음수 | 정답 | 창으로 센 값 | 판정 |
| --- | ---: | --- | ---: | ---: | --- |
| [3 4 7 2 -3 1 4 2] | 7 | 있다 | 4 | 2 | 다르다 |
| [5 -5 5] | 5 | 있다 | 3 | 2 | 다르다 |
| [1 2 3] | 3 | 없다 | 2 | 2 | 같다 |
| [1 1 1] | 2 | 없다 | 2 | 2 | 같다 |

음수가 없는 두 줄은 맞고, 음수가 있는 두 줄은 틀립니다. 창을 줄이는 근거가 「합이 `k` 를 넘었으니 왼쪽
끝을 더 붙여도 `k` 로 돌아오지 않는다」인데, 음수가 있으면 뒤에서 더한 음수가 합을 다시 `k` 로 내려요.
줄인 창의 앞부분이 나중에 다시 답이 될 수 있어서 버리면 안 됩니다.

둘째 후보는 누적합을 한꺼번에 세는 것입니다. 누적합을 정렬해 두고 차이가 `k` 인 값의 짝을 세면, 창을 줄이지
않으니 버리는 것이 없어요. 다섯 입력에 실행했습니다.

<!--proof:origin-ignore-order-->

| 입력 | k | 정답 | 순서 없이 센 값 | 판정 |
| --- | ---: | ---: | ---: | --- |
| [3 4 7 2 -3 1 4 2] | 7 | 4 | 4 | 같다 |
| [5 -5 5] | 5 | 3 | 4 | 다르다 |
| [2 -2 2 -2] | 2 | 3 | 6 | 다르다 |
| [1 -1 1 -1] | 0 | 4 | 4 | 같다 |
| [1 2 3] | 3 | 2 | 2 | 같다 |

전개 입력에서는 4 로 맞았는데 `[5 -5 5]` 는 3 대신 4 를 냈습니다. 정렬하면 **어느 칸이 앞이었는지가
사라져서**, 뒤 칸의 누적합이 앞 칸보다 `k` 만큼 **작은** 짝까지 함께 세어져요. `[5 -5 5]` 의 짝을 전부
펼치면 이렇습니다.

<!--proof:origin-ignore-pairs-->

| 누적합의 짝 | 앞 칸 → 뒤 칸 | 뒤 − 앞 | 뜻 |
| --- | --- | ---: | --- |
| (칸 0, 칸 1) | 0 → 5 | 5 | 구간 [0,0] |
| (칸 0, 칸 3) | 0 → 5 | 5 | 구간 [0,2] |
| (칸 1, 칸 2) | 5 → 0 | -5 | 구간이 아니다 |
| (칸 2, 칸 3) | 0 → 5 | 5 | 구간 [2,2] |

차이가 5 인 짝 4 개 중 3 개만 구간입니다. 나머지는 뒤 칸의 누적합이 더 작아서, 그 사이 구간의 합이 -5 입니다.

<!--/proof-->

그러니 왼쪽 칸이 **오른쪽 칸보다 앞**이어야 한다는 조건을 절차가 지켜야 합니다. 지금까지 해 본 방법을
차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법은 두 후보가 놓친 것을 함께 채웁니다. 오른쪽 칸을 왼쪽부터 하나씩 옮기되, 그 시점까지 **지나온
누적합만** 개수 맵에 담아 두고 거기에 `P[j] − k` 를 묻는 것이에요. 개수 맵에 든 것이 전부 앞 칸이라 순서
조건이 저절로 지켜지고, 아무것도 버리지 않으니 음수가 있어도 틀리지 않습니다. 이 방법에 이름을 붙이면
**누적합 짝 세기**입니다. 개수 맵을 어떻게 준비하고, 어떻게 묻고, 어떻게 적는지는 다음 절에서 실현하는
순서대로 확인합니다.

### 아이디어 상세 — 개수 맵으로 누적합 짝 세기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **원소를 왼쪽부터 하나씩 더해 누적합 `P[j]` 를 만들고, 그때마다
개수 맵에서 `P[j] − k` 가 나온 횟수를 받아 답에 더한 뒤, `P[j]` 를 개수 맵에 한 번 적습니다.** 실현 순서대로
나누면 단계가 셋이고, 첫 단계는 루프에 들어가기 전에 한 번, 뒤의 둘은 원소마다 합니다.

| 단계 | 언제 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 1단계 개수 맵 준비하기 | 루프 전에 한 번 | 빈 개수 맵에 빈 누적합 `P[0] = 0` 을 한 번 적는다 | — |
| 2단계 필요한 누적합의 개수 찾기 | 원소마다 | `prefix` 에 원소를 더하고, 개수 맵에서 `prefix − k` 의 개수를 받아 `answer` 에 더한다 | 1단계의 개수 맵 · 3단계가 앞 걸음에서 적은 키 |
| 3단계 이번 누적합 적기 | 원소마다 | 개수 맵에서 `prefix` 의 개수를 하나 늘린다 | 2단계가 만든 `prefix` |

#### 먼저 알아 둘 개념 — 개수 맵

단계로 들어가기 전에, 개수 맵이 어떻게 생겼고 어떻게 읽는지를 먼저 잡고 갑니다. 키가 칸 번호가 아니라
**누적합의 값**이라서, 누적합 배열을 먼저 배운 독자에게는 방향이 거꾸로 된 구조로 보이기 쉽기 때문이에요.

##### 쉬운 말 정의

개수 맵은 **지금까지 지나온 누적합의 값마다, 그 값이 몇 번 나왔는지를 적어 둔 해시 맵**입니다. 키는
누적합의 값이고, 값은 그 키와 같은 누적합을 가진 칸의 수예요. 식으로 적으면 칸 `j` 까지 지났을 때
`seen[v] = |{ i : 0 ≤ i ≤ j, P[i] = v }|` 입니다.

##### 입력 위에 놓은 그림

전개 입력의 누적합 아홉 칸을 모두 지난 뒤의 개수 맵을 누적합 아래에 놓으면 이렇습니다. 누적합 줄의 ▲ 두
칸과 개수 맵의 키 14 가 같은 값을 가리켜요.

<!--fig:build-map-whole-->
![누적합 9 칸과, 그 값을 센 개수 맵 — 키 14 는 P[3] 과 P[6] 두 칸](./figs/build-map-whole.svg)

누적합은 아홉 칸인데 개수 맵의 키는 여덟 개입니다. `P[3]` 과 `P[6]` 이 모두 14 라서 한 키로 모였고, 그 키의
개수가 2 가 됐어요.

##### 키 하나를 읽는 법

키 하나를 골라 이름에서 칸까지 따라가 봅시다. 개수가 2 인 키 14 입니다.

<!--proof:build-read-one-->

```text
seen.get(14) = 2
  → 누적합이 14 인 칸이 P[3] · P[6] 로 2 개
  → 그 칸을 왼쪽 칸으로 쓰는 구간은 왼쪽 끝이 3 또는 6
```

개수 하나가 왼쪽 칸 후보 하나입니다. 뒤에 오는 칸 `j` 에서 `P[j] − k` 가 14 이면, 이 두 칸이 모두 짝이
되어 구간 둘이 한꺼번에 세어져요.

##### 키끼리의 관계

키마다 어느 칸이 모였는지 펼치면 이렇습니다.

<!--proof:build-map-partition-->

| 키 | 개수 | 누적합이 그 값인 칸 |
| ---: | ---: | --- |
| 0 | 1 | 0 |
| 3 | 1 | 1 |
| 7 | 1 | 2 |
| 14 | 2 | 3 · 6 |
| 16 | 1 | 4 |
| 13 | 1 | 5 |
| 18 | 1 | 7 |
| 20 | 1 | 8 |

키 8 개의 개수를 더하면 9 이고, 누적합의 칸 수 n + 1 = 9 와 같습니다. 칸 하나는 키 하나에만 들어갑니다.

<!--/proof-->

키들은 누적합의 칸을 **값에 따라 나눈 묶음**입니다. 서로 다른 키는 칸을 나눠 갖지 않고, 모든 칸이 어느 한
키에 들어가요. 그래서 개수의 합은 언제나 지나온 칸의 수이고, 키의 수는 그보다 많을 수 없습니다. 열의
순서는 키를 처음 넣은 순서일 뿐이라, 키 13 이 키 16 뒤에 온 것에는 뜻이 없어요.

##### 헷갈리기 쉬운 모양 — 누적합 배열

개수 맵과 가장 헷갈리기 쉬운 것은 누적합 배열입니다. 누적합 배열은 **칸 번호 → 값**이고, 개수 맵은
**값 → 개수**예요. 둘 다 같은 물음 「앞 칸 중 값이 `P[j] − k` 인 칸은 몇 개인가」에 답할 수 있는데, 전개
입력의 모든 칸 `j` 에서 두 구조로 실제로 답해 보았습니다.

<!--proof:build-array-vs-map-->

| 칸 j | P[j] | 찾는 값 | 누적합 배열에서 읽은 칸 | 개수 맵 조회 | 찾은 개수 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 3 | -4 | 1 | 1 | 0 |
| 2 | 7 | 0 | 2 | 1 | 1 |
| 3 | 14 | 7 | 3 | 1 | 1 |
| 4 | 16 | 9 | 4 | 1 | 0 |
| 5 | 13 | 6 | 5 | 1 | 0 |
| 6 | 14 | 7 | 6 | 1 | 1 |
| 7 | 18 | 11 | 7 | 1 | 0 |
| 8 | 20 | 13 | 8 | 1 | 1 |

찾은 개수는 모든 줄에서 두 방법이 같습니다. 누적합 배열은 모두 36 칸을 읽었고, 개수 맵은 8 번 조회했습니다.

<!--/proof-->

누적합 배열은 칸 번호로 찾는 구조라 「값이 얼마인 칸」을 알려면 앞 칸을 전부 읽어야 합니다. 개수 맵은 값을
키로 두었으니 그 값을 한 번 찾으면 끝나요. 36 과 8 의 차이가 「아이디어를 떠올리는 과정」에서 본 뺄셈 36
번과 조회 한 번의 차이입니다.

##### 왜 이렇게 생겼는가

모양의 세 가지가 모두 과제의 요구에서 나옵니다.

| 모양 | 채우는 요구 | 없으면 |
| --- | --- | --- |
| 키가 누적합의 **값** | 물음이 「값이 `P[j] − k` 인 칸」이다 | 칸을 전부 읽어야 한다 — 위 표의 누적합 배열 |
| 값이 **개수** | 같은 누적합이 여러 칸에 나오면 구간도 여럿이다 | 「불변식」 절의 깨뜨리기에서 답이 준다 |
| **지나온** 누적합만 담는다 | 왼쪽 칸은 오른쪽 칸보다 앞이어야 한다 | 「아이디어를 떠올리는 과정」의 순서 없이 세기처럼 구간이 아닌 짝을 센다 |

#### 1단계 — 개수 맵 준비하기

빈 개수 맵을 만들고, 루프에 들어가기 전에 **빈 누적합 `P[0] = 0` 을 한 번** 적습니다. 원소를 하나도
더하지 않았을 때의 누적합이에요. 이 한 번이 왼쪽 끝이 0 인 구간의 왼쪽 칸입니다. 전개 입력의 답 넷이 각각
어느 칸을 왼쪽 칸으로 쓰는지 보면 이렇습니다.

<!--proof:build-seed-->

| 구간 | 왼쪽 칸 | 오른쪽 칸 | 왼쪽 칸의 정체 |
| --- | --- | --- | --- |
| [0,1] | P[0] = 0 | P[2] = 7 | 빈 누적합 |
| [2,2] | P[2] = 7 | P[3] = 14 | 앞 칸의 누적합 |
| [2,5] | P[2] = 7 | P[6] = 14 | 앞 칸의 누적합 |
| [5,7] | P[5] = 13 | P[8] = 20 | 앞 칸의 누적합 |

`[0,1]` 의 왼쪽 칸은 원소를 하나도 지나기 전의 누적합이라, 루프 안에서는 적힐 기회가 없어요. 그래서 루프
밖에서 미리 적습니다. 준비가 끝나면 상태가 셋이고, 각 상태의 크기와 범위는 이렇습니다.

<!--proof:build-size-->

```text
개수 맵의 키  많아야 n + 1 개        전개 입력 n = 8 에서 8 개 · n = 100,000 이면 많아야 100,001 개
prefix        |prefix| ≤ n × 10,000  n = 100,000 이면 1,000,000,000 이하 — 2^31 − 1 = 2,147,483,647 보다 작다
answer        많아야 n(n+1)/2        n = 100,000 이면 5,000,050,000 — 2^31 − 1 = 2,147,483,647 보다 크다
```

키가 `n + 1` 개를 넘지 않는 까닭은 「키끼리의 관계」에서 본 대로 칸 하나가 키 하나에만 들어가기 때문입니다.
`answer` 는 32 비트 정수를 넘을 수 있어요. 자바스크립트의 `number` 는 2^53 까지 정수를 정확히 담으므로 이
글의 코드는 그대로 두지만, 32 비트 정수를 쓰는 언어로 옮기면 64 비트 정수로 잡아야 합니다.

#### 2단계 — 필요한 누적합의 개수 찾기

원소 하나를 받으면 `prefix` 에 더해 이번 누적합 `P[j]` 를 만들고, 개수 맵에서 키 `prefix − k` 의 개수를
받아 `answer` 에 더합니다. 키가 없으면 개수가 0 이에요. 가장 불안한 자리는 세 갈래입니다 — 찾는 키가 아예
없을 때, 찾는 키가 1단계에서 넣은 빈 누적합일 때, 그리고 찾는 키가 루프 안에서 적힌 앞 칸의 누적합일 때예요.
전개 입력에서 세 경우를 조회할 때의 개수 맵과 함께 적었습니다.

<!--proof:build-lookup-cases-->

| 경우 | r | 누적합 | 찾는 키 | 조회할 때의 개수 맵 | 찾은 개수 |
| --- | ---: | ---: | --- | --- | --- |
| 찾는 키가 없다 | 0 | 3 | 3 − 7 = -4 | {0: 1} | 없음 → 0 |
| 빈 누적합을 찾는다 | 1 | 7 | 7 − 7 = 0 | {0: 1, 3: 1} | 1 |
| 앞 칸의 누적합을 찾는다 | 5 | 14 | 14 − 7 = 7 | {0: 1, 3: 1, 7: 1, 14: 1, 16: 1, 13: 1} | 1 |

셋째 줄의 개수 맵에는 이번 누적합 14 가 이미 한 번 들어 있습니다. 칸 3 에서 적힌 것이에요. 그래도 찾는 키는
7 이라 답에 더해지는 것은 키 7 의 개수 1 뿐입니다. 조회는 개수 맵을 읽기만 하고 바꾸지 않습니다. 이번 누적합을
적는 일은 다음 단계예요.

#### 3단계 — 이번 누적합 적기

조회가 끝난 뒤, 개수 맵에서 키 `prefix` 의 개수를 하나 늘립니다. 쉬운 경우는 처음 나온 누적합이라 키가 새로
생기는 것이고, 불안한 경우는 **같은 누적합이 두 번째로 나와서** 이미 있는 키의 개수를 고치는 것이에요. 전개
입력에서 누적합 14 가 처음 나온 걸음과 두 번째로 나온 걸음을 나란히 적었습니다.

<!--proof:build-record-->

| r | 누적합 | 나온 차례 | 기록 전 개수 맵 | 기록 뒤 개수 맵 |
| ---: | ---: | --- | --- | --- |
| 2 | 14 | 처음 | {0: 1, 3: 1, 7: 1} | {0: 1, 3: 1, 7: 1, 14: 1} |
| 5 | 14 | 2 번째 | {0: 1, 3: 1, 7: 1, 14: 1, 16: 1, 13: 1} | {0: 1, 3: 1, 7: 1, 14: 2, 16: 1, 13: 1} |

두 번째 줄에서 키는 늘지 않고 키 14 의 개수만 1 에서 2 가 됐습니다. 값을 덮어쓰지 않고 개수를 늘리기
때문에, 뒤에서 누군가 14 를 찾으면 두 칸이 모두 짝으로 세어져요. 루프는 `nums` 의 원소를 왼쪽부터 마지막
원소까지 하나씩 받고, 받을 때마다 누적합 하나를 **정확히 한 번** 적습니다. 그러니 루프가 끝나면 `P[1]` 부터
`P[n]` 까지 `n` 칸이 한 번씩 적혀 있고, `P[0]` 은 1단계가 적었어요. 빠지거나 두 번 적힌 칸이 없습니다.

적는 일을 조회 **뒤**에 두는 것도 이 단계의 규칙입니다. 이번 칸을 먼저 적으면 이번 칸이 자기 자신의 짝이
되는데, 그 모습은 「수행으로 알아보는 알고리즘」의 두 번째 「짚고 가기」에서 실행 결과로 봅니다.

#### 이 방법이 기대는 전제

누적합 짝 세기는 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 뺄셈이 덧셈을 되돌린다 | 구간 합이 두 누적합의 차 `P[r+1] − P[l]` 이다 | 최댓값처럼 되돌리는 연산이 없으면 두 칸으로 구간 값을 만들 수 없다 |
| 조건이 값 하나다 (`= k`) | 2단계가 키 `P[j] − k` 하나를 찾는다 | 합이 `k` 이하인 구간처럼 조건이 범위면 키 하나로 셀 수 없다 |
| 해시 맵의 조회 · 기록이 평균 상수 시간이다 | 원소마다 조회 하나 · 기록 하나 | 키가 한 자리에 몰리면 조회 하나가 길어진다 — 「비용 계산」에서 다룬다 |

두 번째 전제가 깨지는 모습을 값으로 확인합니다. 같은 입력에서 「합이 7 인 구간」과 「합이 7 이하인 구간」을
모든 구간을 직접 더해 센 값과, 개수 맵으로 센 값을 비교했어요.

<!--proof:premise-at-most-->

| 세는 것 | 모든 구간을 직접 더해 센 값 | 개수 맵으로 센 값 |
| --- | ---: | ---: |
| 합이 7 인 구간 | 4 | 4 |
| 합이 7 이하인 구간 | 21 | 4 |

개수 맵은 키 P[j] − 7 하나만 찾으므로 두 줄에서 같은 4 를 냅니다. 합이 7 이하인 구간은 21 개입니다.

<!--/proof-->

합이 7 이하인 구간을 세려면 「`P[j] − 7` **이상**인 키가 모두 몇 번 나왔나」를 물어야 합니다. 해시 맵은 키의
순서를 모르니 그 물음에 한 번에 답하지 못해요. 순서를 유지하는 구조가 따로 필요합니다.

#### 지나온 누적합을 모두 남기는 까닭

개수 맵은 지나온 누적합을 **전부** 남깁니다. 정말 전부가 필요한지, 직전 `W` 개의 누적합만 남기고 오래된
것은 지우는 절차를 따로 만들어 `W` 를 바꿔 가며 같은 입력에서 세었어요.

<!--proof:cost-window-->

| 남기는 누적합 W | 조회 수 | 답 | 놓친 답 |
| --- | ---: | ---: | ---: |
| 1 | 8 | 1 | 3 |
| 2 | 8 | 2 | 2 |
| 3 | 8 | 3 | 1 |
| 4 | 8 | 4 | 0 |
| 9 (전부) | 8 | 4 | 0 |

W 를 줄여도 조회 수는 8 번 그대로이고 답만 줄어듭니다. 놓친 답이 0 이 되는 것은 W 가 4 이상일 때이고, 전개 입력에서 가장 긴 답 구간이 4 칸입니다.

<!--/proof-->

`W` 를 줄여서 아끼는 것은 개수 맵의 크기뿐이고 조회 수는 하나도 줄지 않습니다. 그런데 `W` 가 가장 긴 답
구간보다 작으면 그 구간을 놓치고, 가장 긴 답 구간이 얼마인지는 입력을 끝까지 보기 전에는 모릅니다. 1단계에서
본 대로 개수 맵의 키가 많아야 `n + 1` 개라 메모리 예산에도 여유가 크니, **지나온 누적합은 모두 남깁니다.**

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 이렇습니다. 첫 줄이 루프 전에 한 번이고 나머지가 원소마다예요. 이렇게
하면 `n` 이 100,000 일 때 50 억 개이던 구간을 하나도 직접 보지 않고, 맵 연산 300,001 번으로 셉니다.

1. 빈 개수 맵에 키 0 을 개수 1 로 넣고, `prefix` 와 `answer` 를 0 으로 둔다
2. 원소를 왼쪽부터 하나씩 받아 `prefix` 에 더한다
3. 개수 맵에서 `prefix − k` 의 개수를 받아 `answer` 에 더한다
4. 개수 맵에서 `prefix` 의 개수를 하나 늘린다
5. 원소를 다 받으면 `answer` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 여덟 칸을 지나며 합이 7 인 구간 넷을 센다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const nums = [3, 4, 7, 2, -3, 1, 4, 2];
const k = 7;
// 이 절이 끝나면 4 가 나와야 한다
```

왜 하필 이 여덟 칸일까요? 갈래를 **모두 실행하게** 하려는 것입니다. 음수가 하나 있어 누적합이 한 번 줄고,
누적합 14 가 두 번 나와 **이미 있는 키의 개수를 늘리는 걸음**이 실행돼요. 찾는 키가 없는 걸음과 있는
걸음이 둘 다 나오고, 답 넷 중 하나는 왼쪽 끝이 0 이라 빈 누적합을 찾는 걸음도 나옵니다.

```text
subarraySumEqualsK(nums, k):
    개수 맵 seen 을 만들고 키 0 을 개수 1 로 넣는다
    prefix 를 0 으로, answer 를 0 으로 둔다
    nums 의 원소를 왼쪽부터 하나씩 받으며:
        prefix 에 그 값을 더한다
        seen 에서 prefix − k 의 개수를 받아 answer 에 더한다      ① 조회
        seen 에서 prefix 의 개수를 하나 늘린다                    ② 기록
    answer 를 반환한다
```

#### 1. 개수 맵에 빈 누적합을 한 번 적는다

시작 상태가 이 조각의 전부입니다. 네 줄이지만 그중 한 줄이 뒤의 모든 분기를 없애요.

```ts
const seen = new Map<number, number>();
seen.set(0, 1);

let prefix = 0;
let answer = 0;
```

이 조각만 실행하면 상태가 이렇게 잡힙니다.

<!--proof:walk-init-->

```text
seen = {0: 1}   prefix = 0   answer = 0
    └ 원소를 하나도 더하지 않은 누적합 P[0] = 0 이 한 번 들어 있다
```

여기서 가장 중요한 줄은 `seen.set(0, 1)` 입니다. 왼쪽 끝이 인덱스 0 인 구간은 이 키를 왼쪽 칸으로 쓰는데,
루프 안에서는 이 키가 적힐 기회가 없어요.

#### 2. 누적합을 갱신하고 필요한 누적합의 개수를 찾는다

걸음마다 하는 일의 앞쪽 절반입니다. 값을 더해 누적합을 갱신하고, 그 누적합에 맞는 왼쪽 칸이 개수 맵에 몇 개
있는지 물어요.

```ts
for (const value of nums) {
  prefix += value;
  // ① 조회 — 지금 누적합에서 k 를 뺀 값이 앞에 몇 번 나왔는지 그대로 더한다.
  answer += seen.get(prefix - k) ?? 0;
}
```

1 번 조각 뒤에 이 조각을 두 걸음만 실행하면 이렇게 나옵니다.

<!--proof:walk-lookup-two-->

| 걸음 | 값 | prefix | 찾는 키 | 개수 맵 | 찾은 개수 | answer |
| --- | ---: | ---: | ---: | --- | --- | ---: |
| T2 | 3 | 3 | -4 | {0: 1} | 없음 → 0 | 0 |
| T3 | 4 | 7 | 0 | {0: 1, 3: 1} | 1 | 1 |

T3 에서 찾은 키 0 이 빈 누적합이고, 그 짝이 구간 `[0,1]` 입니다. 표의 개수 맵에 3 이 들어 있는 것은 T2 의 기록
때문인데, 기록하는 줄은 3 번 조각에서 붙어요. `?? 0` 은 키가 한 번도 안 나왔을 때를 맡습니다. `get` 이
`undefined` 를 돌려주면 0 이 되고, 0 을 더하는 것은 아무것도 안 더하는 것과 같아서 **따로 분기를 두지
않아요.**

#### 짚고 가기 — 빈 누적합을 적지 않으면 왼쪽 끝이 0 인 구간만 빠진다

여기서 헷갈리기 쉬운 포인트는 개수 맵의 시작 상태입니다. 「아직 아무 칸도 안 지나왔으니 개수 맵은 비어 있는
것이 자연스럽지 않나」로 읽기 쉬워요. 그 생각대로 `seen.set(0, 1)` 한 줄을 빼 봅시다.

```ts
const seen = new Map<number, number>();
// seen.set(0, 1) 을 두지 않았다
```

이렇게 하면 개수 맵은 첫 걸음의 기록부터 채워지고, 빈 누적합은 끝까지 없습니다. 정본에서 그 한 줄만 지운
코드를 만들어 네 입력에 두 코드를 각각 실행했어요.

<!--proof:pause-no-seed-->

| 입력 | k | 정본 | 빈 누적합을 안 센 코드 | 판정 |
| --- | ---: | ---: | ---: | --- |
| [3 4 7 2 -3 1 4 2] | 7 | 4 | 3 | 다르다 |
| [1 1 1] | 2 | 2 | 1 | 다르다 |
| [1 2 3] | 5 | 1 | 1 | 같다 |
| [1 2 3] | 100 | 0 | 0 | 같다 |

위 두 줄에서 답이 하나씩 줄었고, 아래 두 줄은 **답이 안 틀립니다.** 어느 답이 빠졌는지 입력마다 답 구간을
펼쳐 보면 이렇습니다.

<!--proof:pause-no-seed-left-->

| 입력 | k | 답 구간 | 왼쪽 끝이 0 인 구간 |
| --- | ---: | --- | --- |
| [3 4 7 2 -3 1 4 2] | 7 | [0,1] · [2,2] · [2,5] · [5,7] | [0,1] |
| [1 1 1] | 2 | [0,1] · [1,2] | [0,1] |
| [1 2 3] | 5 | [1,2] | 없음 |
| [1 2 3] | 100 | 없음 | 없음 |

빠진 것은 정확히 왼쪽 끝이 0 인 구간입니다. 아래 두 입력에는 그런 구간이 아예 없어서 답이 그대로예요.
**시험 입력에 왼쪽 끝이 0 인 답이 없으면 이 코드는 통과합니다** — 그래서 알아채지 못한 채로 남아요. 고치는
길은 둘입니다.

| 고치는 길 | 걸음마다 드는 것 |
| --- | --- |
| 왼쪽 끝이 0 인 구간을 따로 검사한다 — `prefix === k` 면 하나를 더 센다 | 조건 검사 하나가 는다 |
| 개수 맵에 빈 누적합 0 을 한 번 미리 적는다 | 분기가 아예 없어진다 |

아래 길은 「없는 칸」을 따로 처리하는 대신 「빈 누적합」이라는 뜻 있는 값을 그 자리에 둡니다. 누적합 배열이
`P[0] = 0` 칸을 두는 것과 같은 이유예요.

#### 3. 조회를 마친 뒤 이번 누적합을 개수 맵에 적는다

걸음의 뒤쪽 절반입니다. 조회를 마친 다음에 이번 누적합의 개수를 하나 늘려요. 키가 이미 있으면 개수에 1 을
더하고, 없으면 `?? 0` 이 0 을 내어 1 로 시작합니다.

```ts
for (const value of nums) {
  prefix += value;
  // ① 조회 — 지금 누적합에서 k 를 뺀 값이 앞에 몇 번 나왔는지 그대로 더한다.
  answer += seen.get(prefix - k) ?? 0;
  // ② 기록 — 이번 누적합의 개수를 하나 늘린다.
  seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
}
```

누적합 14 가 처음 나온 걸음과 두 번째로 나온 걸음에서 이 줄이 한 일은 이렇습니다.

<!--proof:walk-record-->

| 걸음 | prefix | 기록 전 개수 맵 | 기록 뒤 개수 맵 | 키의 수 |
| --- | ---: | --- | --- | --- |
| T4 | 14 | {0: 1, 3: 1, 7: 1} | {0: 1, 3: 1, 7: 1, 14: 1} | 3 개 → 4 개 |
| T7 | 14 | {0: 1, 3: 1, 7: 1, 14: 1, 16: 1, 13: 1} | {0: 1, 3: 1, 7: 1, 14: 2, 16: 1, 13: 1} | 6 개 → 6 개 |

T4 는 키를 하나 늘렸고, T7 은 키의 수는 그대로 두고 키 14 의 개수만 2 로 늘렸습니다.

#### 짚고 가기 — 기록을 조회보다 먼저 하면 k 가 0 일 때만 답이 늘어난다

여기서 헷갈리기 쉬운 포인트는 ① 과 ② 의 순서입니다. 「어차피 둘 다 이번 걸음에서 하는 일인데 순서가
중요할까」로 읽기 쉬워요. 순서를 바꿔 봅시다.

```ts
for (const value of nums) {
  prefix += value;
  seen.set(prefix, (seen.get(prefix) ?? 0) + 1); // 기록을 먼저 했다
  answer += seen.get(prefix - k) ?? 0;
}
```

기록을 먼저 하면 이번 칸 자신이 개수 맵에 들어간 채로 조회합니다. 이번 칸이 자기 자신과 짝이 되면 차이가
`P[j] − P[j] = 0` 이라, `k` 가 0 일 때만 조회에서 찾아져요. 다섯 입력으로 확인합니다.

<!--proof:pause-record-first-->

| 입력 | k | n | 정본 | 기록을 먼저 한 코드 | 늘어난 수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| [3 4 7 2 -3 1 4 2] | 7 | 8 | 4 | 4 | 0 |
| [1 2 3] | 3 | 3 | 2 | 2 | 0 |
| [1 -1 1 -1] | 0 | 4 | 4 | 8 | 4 |
| [0 0 0] | 0 | 3 | 6 | 9 | 3 |
| [5] | 0 | 1 | 0 | 1 | 1 |

위 두 줄은 **답이 안 틀립니다.** `k` 가 0 이 아니면 자기 자신과의 짝이 조회에서 찾아지지 않기 때문이에요.
그래서 `k` 가 0 인 시험이 없으면 이 순서 바꾸기는 그대로 통과합니다. 아래 세 줄에서는 늘어난 수가 셋째 열의
`n` 과 같아요. 걸음마다 자기 자신과의 짝이 하나씩 더 세어지고, 걸음이 `n` 개이기 때문입니다. 그 짝이 뜻하는
구간은 원소를 하나도 고르지 않은 길이 0 짜리라, 원소가 하나 이상인 구간을 세는 이 과제의 답에 들어가면 안
됩니다.

#### 4. 여덟 칸을 끝까지 지나며 짝을 센다

세 조각을 이어 고정 입력에 실행하면 아홉 걸음이 나옵니다. T1 은 루프에 들어가기 전 준비이고, T2 부터 T9
까지 여덟 걸음이 원소 하나씩을 처리해요. 걸음마다 무대의 괄호 「앞부분」은 지금까지 더한 원소이고, 그
아래 괄호 「찾은 구간」은 이번 조회가 찾은 구간입니다. 맨 아래 두 줄이 개수 맵이고, 점선 칸은 아직 안 넣은
자리, 강조 칸은 이번에 넣거나 늘린 키, ▲ 는 이번에 찾은 키예요.

<!--viz:scan-->

걸음마다 두 갈래의 조건을 실제 값으로 판정하면 아래 아홉 단계입니다.

| 걸음 | r | 값 | prefix | 찾는 키 | ① 조회 | ② 기록 | answer |
| --- | ---: | ---: | ---: | ---: | --- | --- | ---: |
| T1 | — | — | 0 | — | 루프 전 | seen.set(0, 1) | 0 |
| T2 | 0 | 3 | 3 | -4 | seen.get(-4) 이 undefined — ?? 0 으로 0 | 키 3 이 처음 — 1 로 넣는다 | 0 |
| T3 | 1 | 4 | 7 | 0 | seen.get(0) = 1 — 있다 | 키 7 이 처음 — 1 로 넣는다 | 1 |
| T4 | 2 | 7 | 14 | 7 | seen.get(7) = 1 — 있다 | 키 14 가 처음 — 1 로 넣는다 | 2 |

<!--proof:walk-branches-->

```text
① 조회 · 키가 있다  T3 T4 T7 T9           4 번
① 조회 · 키가 없다  T2 T5 T6 T8           4 번
② 기록 · 새 키      T2 T3 T4 T5 T6 T8 T9  7 번
② 기록 · 개수 +1    T7                    1 번
    └ 조회와 기록이 각각 8 번 = n. 키가 있던 4 걸음이 답 4 를 만든다
```

키가 있던 네 걸음이 어느 구간을 찾았는지 확인하고 갑니다. 찾은 키가 왼쪽 칸의 누적합이고, 이번 누적합이
오른쪽 칸이에요.

<!--proof:walk-found-ranges-->

| 걸음 | 왼쪽 칸 | 오른쪽 칸 | 구간 | 구간의 합 |
| --- | --- | --- | --- | --- |
| T3 | P[0] = 0 | P[2] = 7 | [0,1] | 3 + 4 = 7 |
| T4 | P[2] = 7 | P[3] = 14 | [2,2] | 7 = 7 |
| T7 | P[2] = 7 | P[6] = 14 | [2,5] | 7 + 2 + (-3) + 1 = 7 |
| T9 | P[5] = 13 | P[8] = 20 | [5,7] | 1 + 4 + 2 = 7 |

「전체 컨셉」에서 모든 구간을 직접 더해 찾은 네 구간과 같습니다. T7 에서 키 14 의 개수가 2 가 됐지만, 이
입력에서는 그 뒤에 14 를 찾는 걸음이 없어서 개수 2 가 답에 쓰이지는 않았어요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `answer` 를 돌려주는 마지막 줄뿐이에요 —
배열이 비면 루프가 한 번도 실행되지 않아 0 이 그대로 답이 됩니다.

```ts
export function subarraySumEqualsK(nums: number[], k: number): number {
  // 개수 맵 — 지금까지 지나온 누적합을 키로, 그 값이 나온 횟수를 값으로 담는다.
  const seen = new Map<number, number>();
  // 원소를 하나도 더하지 않은 누적합 P[0] 은 0 이다. 그 한 번을 미리 세어 둔다.
  seen.set(0, 1);

  let prefix = 0;
  let answer = 0;
  for (const value of nums) {
    prefix += value;
    // ① 조회 — 지금 누적합에서 k 를 뺀 값이 앞에 몇 번 나왔는지 그대로 더한다.
    answer += seen.get(prefix - k) ?? 0;
    // ② 기록 — 이번 누적합의 개수를 하나 늘린다.
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }

  return answer;
}
```

<!--proof:final-calls-->

```text
subarraySumEqualsK([3, 4, 7, 2, -3, 1, 4, 2], 7)  →  4
subarraySumEqualsK([1, 1, 1], 2)                  →  2
subarraySumEqualsK([1, -1, 1, -1], 0)             →  4
subarraySumEqualsK([1, 2, 3], 100)                →  0
subarraySumEqualsK([], 7)                         →  0
```

### 알아 두면 좋은 개념 — 여집합 조회

이 절차가 걸음마다 한 일을 한 문장으로 줄이면 **「지금 가진 값에서 목표를 빼 필요한 나머지를 만들고, 그
나머지가 앞에 있었는지 해시 맵에 묻는다」** 입니다. 그 「필요한 나머지」를 **여집합**이라고 부르고, 이렇게
묻는 방식을 여집합 조회라고 해요. 전개에서 키를 찾은 네 걸음이 그 모양입니다.

<!--proof:related-lookups-->

| 걸음 | 지금 가진 값 prefix | 목표 k | 필요한 나머지 | 받은 개수 |
| --- | ---: | ---: | --- | ---: |
| T3 | 7 | 7 | 7 − 7 = 0 | 1 |
| T4 | 14 | 7 | 14 − 7 = 7 | 1 |
| T7 | 14 | 7 | 14 − 7 = 7 | 1 |
| T9 | 20 | 7 | 20 − 7 = 13 | 1 |

같은 모양이 다른 과제에서도 같은 이름으로 나옵니다. 바뀌는 것은 **해시 맵에 무엇을 담는가** 하나예요.

| 과제 | 해시 맵에 담는 것 | 필요한 나머지 |
| --- | --- | --- |
| [`twoSum`](../twoSum/twoSum-guide.md) — 합이 `target` 인 두 원소 | 지나온 원소의 값 → 인덱스 | `target − nums[i]` |
| 이 글 — 합이 `k` 인 구간 세기 | 지나온 누적합 → 개수 | `prefix − k` |
| 합이 `M` 의 배수인 구간 세기 | 누적합을 `M` 으로 나눈 나머지 → 개수 | 같은 나머지 |

차이는 **값 자리**입니다. 답이 「어느 것인가」면 인덱스를 담고, 답이 「몇 개인가」면 개수를 담아요. 이 글이
개수를 담는 이유가 그것입니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 세는 일을 식으로 어떻게 적는지, 무엇이 매
걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때이고, 네 조건이 코드의 모양을 그대로 정합니다.

| 조건 | 없으면 | 코드에 생기는 모양 |
| --- | --- | --- |
| 세는 대상이 **연속 구간**이다 | 원소를 골라 담는 부분집합은 누적합의 차로 만들 수 없다 | 구간 하나가 누적합 두 칸의 차가 된다 |
| 구간의 값이 **덧셈으로 쌓이고 뺄셈으로 되돌려진다** — 합 · 개수 · 배타적 논리합 | 최댓값은 두 칸으로 구간 값을 만들 수 없다 | 두 누적합이 함께 가진 앞부분이 뺄셈에서 지워진다 |
| 조건이 **정확히 하나의 값**이다 (`= k`) | 범위 조건은 키 하나로 셀 수 없다 | 개수 맵에 묻는 것이 원소마다 한 번이다 |
| 원소에 **음수가 섞일 수 있다** | 음수가 없으면 창의 두 끝을 옮기는 방법으로도 된다 | 지나온 누적합을 버리지 않고 전부 개수 맵에 남긴다 |

조건이 바뀌면 고를 방법도 바뀝니다.

| 조건 | 개수 맵에 묻는 것 | 고를 방법 |
| --- | --- | --- |
| 합이 정확히 `k` | 키 `P[j] − k` 하나 | 이 글의 누적합 짝 세기 |
| 합이 `k` 이하 | `P[j] − k` 이상인 키 전부 | 순서를 유지하는 구조가 따로 필요하다 |
| 원소가 모두 음이 아니다 | 묻지 않아도 된다 | 창의 두 끝을 오른쪽으로만 옮겨도 된다 — 개수 맵이 없어도 된다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "합이 정확히 k 인"  "합이 k 가 되는"                ← 찾을 값이 하나로 정해진다
  "연속된"  "부분 배열"  "구간"                        ← 골라 담는 것이 아니다
  "개수를 구하라"  "몇 개인가"                         ← 하나만 찾는 것이 아니다
  "음수가 포함될 수 있다"                              ← 결정적인 신호다

제약에 이런 모양이 보이면
  N 이 10^5 이상이라 N² 이 못 들어간다
  값의 범위가 좁아 누적합이 정수 범위를 안 넘는다

반대로 이런 말이 보이면 해당하지 않는다
  "합이 k 이하인"  "합이 최대인"                       ← 찾을 값이 하나가 아니다
  "구간의 최솟값"  "구간의 최댓값"                     ← 뺄셈으로 되돌려지지 않는다
  "원소는 모두 양수"                                   ← 창의 두 끝을 옮기는 방법이 열린다
```

마지막 무리가 보이면 다른 절차로 갑니다. 합이 최대인 구간이면 [`kadane`](../kadane/kadane-guide.md) 쪽이고,
원소가 전부 음이 아니고 상한이 주어진 과제면
[`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **CPython 의 `collections.Counter`** — 이 절차의 개수 맵 그 자체입니다. 없는 키를 물으면 예외 대신 0 을
  돌려주는 것이 `?? 0` 과 같은 자리이고, 공식 문서가 그 동작을 *"returns a zero count for missing items
  instead of raising a KeyError"* 로 적고 있어요.
  ([`collections.Counter`](https://docs.python.org/3/library/collections.html#collections.Counter),
  조회 2026-08-29)
- **NumPy 의 `numpy.cumsum`** — 배열 하나를 받아 누적합 배열을 돌려줍니다. 이 글의 `P` 와 다른 점은 **앞에
  0 칸을 두지 않는다**는 것이라, 왼쪽 끝이 인덱스 0 인 구간을 따로 다뤄야 해요 — 첫 「짚고 가기」에서 값으로
  확인한 그 자리입니다.
  ([`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-29)
- **SQL 의 윈도 함수** — `sum(v) over (order by i)` 가 누적합을 만들고, 그 결과를 값으로 묶어 세면 이 글의
  개수 맵이 됩니다. PostgreSQL 공식 문서의 윈도 함수 장이 누적 집계를 그 꼴로 적어요.
  ([PostgreSQL — Window Functions](https://www.postgresql.org/docs/current/tutorial-window.html),
  조회 2026-08-29)

```text
세 사례와 이 글의 절차의 관계

  앞의 둘   조각을 하나씩 제공한다. 누적합과 개수 맵을 잇는 것은 쓰는 쪽의 몫이다
  SQL       두 조각을 한 질의에 적을 수 있지만 누적합 열을 통째로 만든다
            └ 이 글의 절차는 그 열을 만들지 않고 값 하나만 가지고 지나간다
```

**이 절차 전체를 하나의 이름으로 제공하는 시스템은 찾지 못했습니다.** 표준 라이브러리가 주는 것은 두
조각이고, 「지나온 누적합의 개수를 세면서 여집합을 묻는다」는 그 둘을 잇는 쪽의 코드로 남아 있어요.

### 수식 정의와 유도

누적합을 기호로 정의합니다. 칸 0 은 원소를 하나도 더하지 않은 누적합이고, 그다음부터는 직전 칸에 값 하나를
더한 것입니다.

$$P[0] = 0, \qquad P[j] = P[j-1] + nums[j-1] \quad (1 \le j \le n)$$

<!--proof:math-check-->

```text
nums 의 값 3 4 7 2 -3 1 4 2

  P[0] = 0
  P[1] = P[0] + nums[0] = 0 + 3 = 3
  P[2] = P[1] + nums[1] = 3 + 4 = 7
  P[3] = P[2] + nums[2] = 7 + 7 = 14
```

정의 하나가 칸 하나를 정하고, 정의가 두 항만 봅니다. 구간 합을 이 기호로 적으면 이렇게 됩니다. 앞 `r+1` 개의
합에서 앞 `l` 개의 합을 덜어 낸 것이 가운데 구간이에요.

$$\sum_{t=l}^{r} nums[t] = P[r+1] - P[l] \qquad (0 \le l \le r \le n-1)$$

<!--proof:math-split-->

```text
l = 2, r = 5

  t = 0 … 5 의 합  3 + 4 + 7 + 2 + (-3) + 1 = 14  P[6]
  t = 0 … 1 의 합  3 + 4 = 7                      P[2]
  t = 2 … 5 의 합  7 + 2 + (-3) + 1 = 7
    └ 앞의 둘이 겹치는 항이 없고 14 = 7 + 7 이다
```

더하는 자리를 `t` 로 적어 누적합의 칸 번호와 갈라 두었습니다. 이제 답을 집합으로 정의해요. 세는 것은 구간이지만,
위 식이 구간 하나에 누적합의 짝 하나를 붙여 주므로 **짝의 개수**로 옮겨 적을 수 있습니다.

$$A = \{(l, r) : 0 \le l \le r \le n-1,\ P[r+1] - P[l] = k\}$$

<!--proof:math-set-->

```text
  (0, 1)  P[2] − P[0] = 7 − 0 = 7
  (2, 2)  P[3] − P[2] = 14 − 7 = 7
  (2, 5)  P[6] − P[2] = 14 − 7 = 7
  (5, 7)  P[8] − P[5] = 20 − 13 = 7
    └ |A| = 4 이고, 정본의 답 4 와 같다
```

같은 것을 누적합의 칸으로만 적으면 이렇게 됩니다.

$$B = \{(i, j) : 0 \le i < j \le n,\ P[j] - P[i] = k\}$$

두 집합의 크기가 같은 이유는 짝을 서로 옮겨 보면 확인됩니다.

| 방향 | 옮기는 식 | 조건이 지켜지는 까닭 |
| --- | --- | --- |
| `A` 에서 `B` 로 | `(l, r)` → `(i, j) = (l, r+1)` | `l ≤ r` 이므로 `i < j` 다 |
| `B` 에서 `A` 로 | `(i, j)` → `(l, r) = (i, j−1)` | `i < j` 이므로 `l ≤ r` 다 |

두 방향을 이어 적용하면 처음 짝이 그대로 나오니, 두 집합의 원소가 하나씩 짝지어져 개수가 같아요.

`B` 를 오른쪽 칸 `j` 로 갈라 셉니다. 짝 하나에는 `j` 가 하나뿐이므로, `j` 마다 세어 더하면 겹치지도 빠지지도
않아요.

$$|B| = \sum_{j=1}^{n} \bigl| \{ i : 0 \le i < j,\ P[i] = P[j] - k \} \bigr|$$

<!--proof:math-by-j-->

| j | P[j] | P[j] − k | 앞 칸 중 그 값인 칸 |
| ---: | ---: | ---: | ---: |
| 1 | 3 | -4 | 0 |
| 2 | 7 | 0 | 1 |
| 3 | 14 | 7 | 1 |
| 4 | 16 | 9 | 0 |
| 5 | 13 | 6 | 0 |
| 6 | 14 | 7 | 1 |
| 7 | 18 | 11 | 0 |
| 8 | 20 | 13 | 1 |

넷째 열을 더하면 4 이고, |A| 와 같습니다.

<!--/proof-->

합의 안쪽 항은 **`j` 보다 앞 칸 중 값이 `P[j] − k` 인 칸의 수**이고, 그것이 칸 `j` 를 지나기 직전의
`seen[P[j] − k]` 입니다. 개수 맵이 그 수를 들고 있으니 항 하나가 조회 한 번이 돼요. 식을 그대로 옮긴 조각이
이것입니다.

```ts
// 위 합의 항 하나를 그대로 적은 것. 실제 절차는 이 세기를 개수 맵 조회로 대신한다.
const term = (P: number[], j: number, k: number): number =>
  P.slice(0, j).filter((v) => v === (P[j] as number) - k).length;
```

이 조각은 항 하나를 세는 데 `j` 칸을 읽으므로 전부 더하면 `n(n+1)/2` 번입니다. 개수 맵을 쓰면 항 하나가 조회
한 번이라 `n` 번이에요. 답이 가장 커지는 것은 모든 짝이 조건을 만족할 때이고, 칸이 `n + 1` 개이므로 짝의 수가
상한입니다.

$$|B| \le \binom{n+1}{2} = \frac{n(n+1)}{2}$$

등호는 누적합의 모든 칸이 같은 값이고 `k = 0` 일 때 성립합니다 — 원소가 전부 0 이고 `k = 0` 인 입력이에요. 그
입력에서 닫힌 형태에 규모를 넣고 실제 실행과 대조했습니다.

<!--proof:math-scale-->

| n | 답(실측) | n(n+1)/2 | 맵 연산(실측) | 3n + 1 |
| ---: | ---: | ---: | ---: | ---: |
| 3 | 6 | 6 | 10 | 10 |
| 8 | 36 | 36 | 25 | 25 |
| 1,000 | 500,500 | 500,500 | 3,001 | 3,001 |
| 100,000 | 5,000,050,000 | 5,000,050,000 | 300,001 | 300,001 |

원소가 전부 0 이고 k = 0 인 입력입니다. 실측값이 닫힌 형태와 4 규모에서 모두 같습니다.

<!--/proof-->

마지막 줄이 과제 규모의 끝입니다. 답은 50 억을 넘을 수 있는데 그 답을 만드는 연산은 30 만 번이에요.

<!--proof:math-max-->

```text
n = 100,000 에서
  답의 최댓값  n(n+1)/2 = 5,000,050,000          32 비트 정수의 범위를 넘는다
  맵 연산      3n + 1 = 300,001
  둘의 비      5,000,050,000 ÷ 300,001 ≈ 16,667
```

답이 기본 연산보다 훨씬 클 수 있는 것은 답을 하나씩 만들지 않고 **개수를 한 번에 더하기** 때문입니다.

### 불변식 — 개수 맵은 지나온 누적합이 나온 횟수를 그대로 담는다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해
봅시다. 문장을 세운 뒤 전개의 T4 직후에 먼저 대어 봅니다.

> 루프가 `r` 번째 원소를 처리한 직후마다, 개수 맵은 `P[0]` 부터 `P[r+1]` 까지가 각각 몇 번 나왔는지를 담고
> 있고, `answer` 는 오른쪽 끝이 `r` 이하인 구간 중 합이 `k` 인 것의 개수입니다.

<!--proof:invariant-at-t4-->

```text
T4 직후  개수 맵에 든 칸  P[0] P[1] P[2] P[3]       {0: 1, 3: 1, 7: 1, 14: 1}
         아직 안 든 칸    P[4] P[5] P[6] P[7] P[8]
         answer = 2       오른쪽 끝이 2 이하인 답   [0,1] · [2,2]
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 개수 맵이 **지나온 칸만, 빠짐없이** 담는다는 것이고, 뒤 문장이
**답을 두 번 세거나 빠뜨리지 않는다**는 것을 말해요. 둘 중 하나만 빠져도 조회 결과를 그대로 더해도 된다는
근거가 사라집니다. 출발점과 각 걸음에서 두 문장이 어떻게 유지되는지 적으면 이렇습니다.

| 시점 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 루프 전 | 개수 맵에 `P[0]` 을 한 번 적는다 | 지나온 칸이 `P[0]` 하나뿐이다 | 처리한 원소가 없으니 센 것도 없다 |
| 원소 `r` | 조회한 뒤 `P[r+1]` 을 적는다 | 직전 걸음이 `P[0]` … `P[r]` 을 담아 두었고, 이번에 `P[r+1]` 하나를 더했다 | 조회가 오른쪽 끝이 `r` 인 답을 정확히 센다 — 아래 설명 |
| 루프 끝 | `r = n − 1` 까지 처리했다 | `P[0]` 부터 `P[n]` 까지 전부 | 오른쪽 끝이 `n − 1` 이하인 답, 곧 전부 |

둘째 줄의 뒤 문장이 핵심입니다. 조회할 때의 개수 맵은 `P[0]` … `P[r]` 만 담고 있고 이번 칸 `P[r+1]` 은 아직
안 들어갔어요. 그중 값이 `P[r+1] − k` 인 칸 `P[i]` 하나가 오른쪽 끝이 `r` 인 답 `[i, r]` 하나이고, 서로 다른
칸은 서로 다른 구간을 줍니다. 기록을 조회 뒤로 미룬 이유가 이것이에요. 전개 입력에서 걸음마다 두 문장을 직접
대조했습니다.

<!--proof:invariant-hold-->

| 걸음 | 지나온 누적합 | 개수 맵의 키 | answer | 오른쪽 끝이 r 이하인 답 |
| --- | --- | ---: | ---: | ---: |
| T2 | P[0] … P[1] | 2 | 0 | 0 |
| T3 | P[0] … P[2] | 3 | 1 | 1 |
| T4 | P[0] … P[3] | 4 | 2 | 2 |
| T5 | P[0] … P[4] | 5 | 2 | 2 |
| T6 | P[0] … P[5] | 6 | 2 | 2 |
| T7 | P[0] … P[6] | 6 | 3 | 3 |
| T8 | P[0] … P[7] | 7 | 3 | 3 |
| T9 | P[0] … P[8] | 8 | 4 | 4 |

걸음마다 개수 맵을 지나온 누적합을 직접 센 값과 대조했습니다. 키 41 개를 대조했고 어긋난 키는 0 개이며, answer 는 8 걸음 모두 오른쪽 끝이 r 이하인 답의 수와 같습니다.

<!--/proof-->

경계에 있는 입력들도 확인하고 갑시다.

<!--proof:invariant-edges-->

| 경우 | 입력 | k | 결과 |
| --- | --- | ---: | ---: |
| 배열이 빔 | [] | 7 | 0 |
| 원소 하나가 k 와 같음 | [5] | 5 | 1 |
| 원소 하나가 k 와 다름 | [5] | 1 | 0 |
| k 가 0 이고 원소도 0 | [0] | 0 | 1 |
| 원소가 전부 0 · k = 0 | [0 0 0 0] | 0 | 10 |
| k 가 음수 | [-1 -1 1] | -2 | 1 |
| 답이 하나도 없음 | [1 2 3] | 100 | 0 |

배열이 비면 루프가 한 번도 실행되지 않아 불변식의 「루프 끝」이 곧 「루프 전」이고, 센 것이 없으니 0 입니다.
원소 하나가 `k` 와 같으면 조회가 빈 누적합 0 을 찾아요. `k` 가 음수여도 찾는 키 `P[j] − k` 가 커질 뿐 절차는
같습니다.

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 개수 맵에 개수를 더하는 그 한 줄이에요. 「어차피 값이 있었는지만
알면 되지 않나」라는 생각으로 개수 대신 1 을 적어 봅니다. 한 줄만 바뀝니다.

```ts
for (const value of nums) {
  prefix += value;
  answer += seen.get(prefix - k) ?? 0;
  seen.set(prefix, 1); // 개수를 더하지 않고 1 을 적는다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-count-once-->

| 입력 | k | 정본 | 개수 대신 1 을 적은 코드 | 판정 |
| --- | ---: | ---: | ---: | --- |
| [3 4 7 2 -3 1 4 2] | 7 | 4 | 4 | 같다 |
| [1 -1 1 -1] | 0 | 4 | 3 | 다르다 |
| [0 0 0] | 0 | 6 | 3 | 다르다 |
| [1 1 1] | 2 | 2 | 2 | 같다 |

첫 줄과 마지막 줄은 답이 그대로입니다. 전개 입력에서는 T7 에서 키 14 가 두 번째로 나왔지만, 그 뒤에 14 를
찾는 걸음이 없었어요. 개수가 틀려도 그 개수를 읽는 자리가 없으면 답은 그대로입니다. `[0 0 0]` 의 앞부분마다
두 코드의 `answer` 를 보면 걸음마다 조회가 몇을 냈는지 알 수 있어요.

<!--proof:mutant-growth-->

| 앞부분 | 정본 answer | 정본이 늘어난 수 | 깨진 코드 answer | 깨진 코드가 늘어난 수 |
| --- | ---: | --- | ---: | --- |
| [0] | 1 | +1 | 1 | +1 |
| [0 0] | 3 | +2 | 2 | +1 |
| [0 0 0] | 6 | +3 | 3 | +1 |

정본은 조회가 1, 2, 3 을 내는데 깨진 코드는 1, 1, 1 을 냅니다. 개수 맵의 키 0 이 매번 1 로 덮여서, 앞에 나온
누적합 0 이 몇 칸이든 한 칸으로만 세어졌어요. 「값이 있었는가」만 담는 해시 맵으로는 **같은 값이 여럿일 때
답이 몇 개인지**를 낼 수 없습니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 종류뿐입니다 — `prefix` 에 값을 더하는 것, 개수 맵에 묻는 것, 개수 맵에 적는
것이에요. 전개의 걸음으로 세면 이렇습니다.

<!--proof:perf-derive-->

```text
더하기  T2 T3 T4 T5 T6 T7 T8 T9  걸음마다 한 번 → 정확히 8 번 = n
조회    T2 T3 T4 T5 T6 T7 T8 T9  걸음마다 한 번 → 정확히 8 번 = n
기록    T2 T3 T4 T5 T6 T7 T8 T9  걸음마다 한 번 → 정확히 8 번 = n
    └ T1 은 루프 밖이고 개수 맵에 한 번 적는 것이 전부다
```

셋 다 걸음마다 정확히 하나이므로 각각 `n` 번이고, 시작할 때의 기록 하나가 더 붙습니다. 개수는 **입력의
내용과 상관없이 정해져요** — 값이 크든 작든, 답이 많든 적든 같습니다. 개수 맵 연산만 따로 세면, 기록 한 번이
읽기(`get`) 하나와 쓰기(`set`) 하나로 나뉘므로 이렇게 됩니다.

$$\text{맵 연산} = \underbrace{n}_{\text{조회}} + \underbrace{n}_{\text{기록의 읽기}} + \underbrace{(n + 1)}_{\text{기록의 쓰기와 첫 쓰기}} = 3n + 1$$

<!--proof:perf-total-->

```text
n = 8        맵 연산 25 번       실측 — 3 × 8 + 1 과 같다
n = 100,000  맵 연산 300,001 번  개수 맵의 키는 많아야 100,001 개
```

여기에 덧셈 `n` 번이 더해집니다. 추가로 잡는 메모리는 개수 맵 하나뿐이라 키가 많아야 `n + 1` 개이고, 입력
배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (답이 하나도 없다) | `O(n)` | `Θ(n)` |
| **평균적인 경우** (입력 분포와 상관없다) | `O(n)` | `Θ(n)` |
| **최악의 경우** (모든 구간이 답이다) | `O(n)` | `Θ(n)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 연산의 **횟수**가 `3n + 1` 로 고정이라 입력의 모양을 어떻게 바꿔도
같아요. 총식을 정확히 적으면 이렇습니다. 앞뒤로 붙는 전처리가 없어요 — 정렬도 좌표압축도 하지 않습니다.

$$T(n) = \underbrace{n}_{\text{덧셈}} + \underbrace{3n + 1}_{\text{맵 연산}} \cdot c_{\text{맵}}, \qquad \text{추가 메모리} = \Theta(n)$$

**보장의 종류를 나눠 적어야 하는 자리가 하나 있습니다.** 연산의 횟수는 최악 보장이에요 — 어떤 입력을 넣어도
`3n + 1` 번입니다. 그런데 맵 연산 **하나**의 비용 `c_맵` 이 상수라는 것은 해시 맵의 구현에 달린 값이고,
해시가 키를 고르게 나눈다는 전제 위의 기댓값입니다.

| 층 | 값 | 보장의 종류 |
| --- | --- | --- |
| 맵 연산의 횟수 | `3n + 1` | 최악 보장. 입력이 무엇이든 이 수다 |
| 맵 연산 하나의 비용 `c_맵` | 평균 상수 | 기댓값. 무작위성은 입력 분포가 아니라 해시 맵의 해시 함수가 만든다 |

충돌이 많은 키 집합을 일부러 만들면 조회 하나가 길어질 수 있습니다. 최악 보장까지 필요하면 누적합을 정렬해
좌표압축한 뒤 배열로 세는 길이 있고, 그때는 정렬 때문에 `Θ(n log n)` 이 됩니다.

#### 최악을 만드는 입력

기본 연산을 최대로 만드는 방법은 하나뿐입니다 — **`n` 을 규모의 최댓값으로 두는 것**이에요. 입력의 모양은
걸음 수를 바꾸지 못합니다. 같은 `n` 에서 모양만 셋으로 바꿔 실제로 셌습니다.

<!--proof:worst-shape-->

| 입력의 모양 (n = 1,000) | 조회 수 | 개수 맵의 키 | 답 |
| --- | ---: | ---: | ---: |
| 전부 0 · k = 0 | 1,000 | 1 | 500,500 |
| 전부 1 · k = 5 | 1,000 | 1,001 | 996 |
| 1 2 3 … n · k = 0 | 1,000 | 1,001 | 0 |

조회 수는 세 줄이 모두 같습니다. 답이 가장 많은 첫 줄은 키가 가장 적고, 답이 없는 셋째 줄은 키가 가장 많습니다.

<!--/proof-->

**「답이 많은 입력이 느리다」는 이 절차에서 거짓입니다.** 첫 줄과 셋째 줄에서 답은 500,500 대 0 인데 조회
수는 둘 다 1,000 이에요. 답을 하나씩 만들지 않고 개수를 한 번에 더하기 때문입니다. 최악은 축마다 다른
입력이 만듭니다. 시간의 최악은 `n` 이 가장 클 때이고, 메모리의 최악은 누적합이 한 번도 겹치지 않아 키가
`n + 1` 개가 될 때이며, 반환값 크기의 최악은 원소가 전부 0 이고 `k = 0` 일 때예요. 위 표에서 메모리가 가장
많이 드는 입력과 답이 가장 많은 입력이 서로 반대인 것을 확인할 수 있습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 구간을 하나씩 재던 것을 **누적합 짝 세기**로 바꿨고, 오른쪽
칸을 정하면 찾을 누적합이 `P[j] − k` 하나로 정해지며, 지나온 누적합의 **개수**를 개수 맵에 두면 그 물음이
조회 한 번이 됩니다.

```text
개수 맵에 0 을 한 번 적는다 → 원소마다 prefix 를 갱신한다 → prefix − k 의 개수를 더한다 → prefix 를 적는다
      └ 왼쪽 끝이 0 인 답을 맡는다        └ 덧셈 n 번              └ 조회 n 번              └ 기록 n 번
```

먼저 답이 붙는 문제 하나입니다. 전개의 T7 은 누적합이 두 번째로 14 가 된 걸음이었어요. 그때 개수 맵에서 찾은
개수가 1 이었는데, 만약 그 자리에서 2 가 나왔다면 무슨 뜻일까요?

<!--proof:selfcheck-t7-->

```text
T7  prefix = 14  찾는 키 7  찾은 개수 1  answer 3
    └ 개수 맵에 키 7 이 1 번 들어 있었다
```

<!--check:found-two-->
누적합 7 이 그 시점까지 **두 번** 나왔다는 뜻이고, 그러면 오른쪽 끝이 인덱스 5 인 답이 둘이 됩니다. 왼쪽 칸
후보가 둘이니 구간도 둘이에요. 조회 한 번이 답 둘을 한꺼번에 내는 자리이고, 개수 맵이 「있다 / 없다」가 아니라
**개수**를 담아야 하는 까닭이 여기에 있습니다. 「불변식」 절의 깨뜨리기가 그 개수를 1 로 덮었을 때의 답을 값으로
보였어요. 두 경우를 나란히 놓으면 이렇습니다.

| 키 7 의 개수 | 왼쪽 칸 후보 | 오른쪽 끝이 5 인 답 |
| --- | --- | --- |
| 1 — 실제 | `P[2]` | `[2,5]` 하나 |
| 2 — 가정 | `P[2]` 와, 값이 7 인 다른 앞 칸 `P[x]` | `[2,5]` 와 `[x,5]` 둘 |

<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「알아 두면 좋은 개념」, 두 번째 「짚고 가기」, 「최악을
만드는 입력」을 다시 보세요.

- 합이 `M` 의 배수인 연속 부분 배열의 개수를 세려면 개수 맵의 키에 무엇을 담아야 할까요? `nums` 의 값
  3 4 7 2 로 `M = 5` 일 때 개수 맵이 어떻게 변하는지 손으로 적어 보세요.
- 전개의 T2 는 조회가 0 을 냈습니다. 만약 `k` 를 −4 로 바꾸면 T2 의 조회 결과가 어떻게 되고, 답 전체는 몇이
  될까요? 개수 맵의 첫 키가 어느 걸음에서 쓰이는지까지 확인해 보세요.
- 반환값이 `n(n+1)/2` 까지 커질 수 있다는 것을 위에서 확인했습니다. 32 비트 정수만 쓰는 언어라면 어느 입력에서
  값이 넘치는지, 그리고 그것을 어떻게 알아챌 수 있을지 생각해 보세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Subarray Sum Equals K

풀 파일: [`subarraySumEqualsK.ts`](./subarraySumEqualsK.ts) · 테스트: [`subarraySumEqualsK.test.ts`](./subarraySumEqualsK.test.ts) · 실행: `bun test src/algorithms/array/subarraySumEqualsK/subarraySumEqualsK.test.ts`

#### 한 줄 요약

> 정수 배열과 목표값 $k$를 받아, **합이 정확히 $k$인 연속 부분 배열의 개수**를 반환한다.

#### 스토리

출납 감사관 혜린은 수천 건의 거래 기록을 검토하고 있다. 각 거래는 입금(양수) 또는 출금(음수)이다.

감사 규정상 연속된 거래들의 합이 정확히 $k$인 구간이 몇 개인지 파악해야 한다. 같은 합을 가진 구간이라도 시작·끝 인덱스가 다르면 별개로 센다.

혜린은 조건을 만족하는 구간의 총 개수를 계산해야 한다.

#### 함수 인터페이스

```ts
export function subarraySumEqualsK(nums: number[], k: number): number;
```

- `nums` — 정수 배열. 음수 포함 가능.
- `k` — 찾을 목표 합.
- 반환 — 합이 정확히 $k$인 연속 부분 배열의 개수.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `nums`의 길이)
- $-10{,}000 \leq nums[i] \leq 10{,}000$ (정수, 음수 가능)
- $-10^9 \leq k \leq 10^9$ (정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

인덱스 쌍 $(l, r)$ ($0 \leq l \leq r < N$)로 표현된 구간 중

$$\sum_{i=l}^{r} nums[i] = k$$

를 만족하는 쌍의 개수를 반환한다. 같은 합을 가진 서로 다른 인덱스 쌍은 각각 개별적으로 센다. 결과가 $0$인 것도 합법적인 목표값이다. 만족하는 구간이 없으면 $0$을 반환한다.

#### 예시

```ts
subarraySumEqualsK([1, 1, 1], 2);    // 2  — [1,1](0..1), [1,1](1..2)
subarraySumEqualsK([1, 2, 3], 3);    // 2  — [1,2](0..1), [3](2..2)
subarraySumEqualsK([3, 4, 7, 2, -3, 1, 4, 2], 7); // 4

subarraySumEqualsK([1, -1, 1, -1], 0); // 4  — 합 0인 구간이 4개
subarraySumEqualsK([0, 0, 0], 0);      // 6  — 길이 1, 2, 3짜리 구간이 각각 3, 2, 1개

subarraySumEqualsK([1, 2, 3], 100);  // 0  — 만족하는 구간 없음
subarraySumEqualsK([5], 5);          // 1  — 단일 원소 일치
subarraySumEqualsK([5], 1);          // 0  — 단일 원소 불일치
```
