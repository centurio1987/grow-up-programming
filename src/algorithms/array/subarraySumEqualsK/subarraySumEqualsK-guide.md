# subarraySumEqualsK — 구간을 하나씩 재지 않고 접두 합의 짝을 세는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 모든 구간의 합을 하나씩
재는 방법에서 걸음마다 표를 한 번 조회하는 방법까지 가는 경로를 따라갑니다. 마지막에는
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

정수 배열에서 **합이 정확히 `k` 인 연속 부분 배열이 몇 개인지** 세는 문제예요. 시작과 끝이
다르면 합이 같아도 따로 셉니다. 원소에 음수가 섞일 수 있다는 것이 이 문제의 성격을 정합니다.

```text
nums 의 값   3  4  7  2 -3  1  4  2        k = 7
인덱스       0  1  2  3  4  5  6  7
             └──┘                          3 + 4 = 7
                   ●                       7
                   └────────┘              7 + 2 + (−3) + 1 = 7
                            └─────┘        1 + 4 + 2 = 7
                                           └ 네 개다
```

구간마다 합을 직접 더하면 구간의 개수만큼 일이 생깁니다. 길이 `n` 인 배열의 연속 부분 배열은
`n(n+1)/2` 개라, `n` 이 10 만이면 구간만 50 억 개예요. 그래서 구간을 하나씩 보지 않는 방법이
필요합니다.

```text
n = 8    구간이 8 × 9 / 2 = 36 개
n = 10 만  구간이 100,000 × 100,001 / 2 = 5,000,050,000 개
           └ 구간 하나를 한 번만 봐도 50 억 번이다
```

여기서 **접두 합**을 씁니다. `P[j]` 를 배열의 앞 `j` 개 원소의 합으로 두면, 구간 하나의 합이
접두 합 두 개의 뺄셈으로 나와요.

```text
nums 의 값       3   4   7   2  -3   1   4   2
인덱스           0   1   2   3   4   5   6   7

P 의 값      0   3   7  14  16  13  14  18  20     앞 j 개의 합, 칸이 아홉 개다
칸 j         0   1   2   3   4   5   6   7   8
             └ 앞 0 개의 합, 그러니까 아무것도 더하지 않은 0 이다

구간 [2,5] 의 합 = P[6] − P[2] = 14 − 7 = 7
```

그러면 「합이 `k` 인 구간」이 「차이가 `k` 인 접두 합의 짝」으로 바뀝니다. 구간의 왼쪽 끝이
칸 `i` 에, 오른쪽 끝의 바로 다음이 칸 `j` 에 대응해요.

```text
구간 [l, r]  ↔  접두 합의 짝 (i, j) = (l, r+1)      i < j 다

  구간 [0,1]  ↔  (0, 2)   P[2] − P[0] = 7 − 0 = 7
  구간 [2,2]  ↔  (2, 3)   P[3] − P[2] = 14 − 7 = 7
  구간 [2,5]  ↔  (2, 6)   P[6] − P[2] = 14 − 7 = 7
  구간 [5,7]  ↔  (5, 8)   P[8] − P[5] = 20 − 13 = 7
                 └ 구간을 세는 일이 짝을 세는 일과 같은 일이 된다
```

짝도 그냥 세면 여전히 개수가 같습니다. 그래서 한 걸음 더 갑니다 — **오른쪽 칸 `j` 를 하나로
고정해 두고**, 그 칸에 맞는 왼쪽 칸이 앞에 몇 개 있는지만 물어요. 물어야 할 값은 하나뿐입니다.

```text
칸 j 를 고정하면 필요한 왼쪽 값이 하나로 정해진다

  P[j] − P[i] = k        →      P[i] = P[j] − k
                                └ 「이 값이 앞에 몇 번 나왔나」 한 가지만 물으면 된다
```

그 질문에 한 번에 답하려면 **지금까지 지나온 접두 합이 각각 몇 번 나왔는지**를 표로 들고
있으면 됩니다. 칸을 왼쪽에서 오른쪽으로 옮기면서, 표에 묻고 표에 적는 것을 되풀이해요.

```text
칸 j   접두 합 P[j]   묻는 값 P[j] − 7   표에서 찾은 개수   표의 내용
0                 0                  —                  —   {0:1}
1                 3                 −4                  0   {0:1, 3:1}
2                 7                  0                  1   {0:1, 3:1, 7:1}
3                14                  7                  1   {…, 14:1}
                                                        └ 찾은 개수를 그대로 더한 것이 답이다
```

표에 묻는 일과 적는 일이 걸음마다 한 번씩이라, 전체 연산이 배열 길이에 비례합니다 — `O(n)`
이에요. 구간을 하나씩 보던 `n(n+1)/2` 가 `n` 이 됩니다.

```text
구간을 하나씩 본다      50 억 번        n = 10 만
접두 합의 짝을 센다     10 만 걸음      걸음마다 표에 한 번 묻고 한 번 적는다
```

원소가 음수일 수 있다는 조건이 여기서 값을 합니다. 접두 합이 오르내리기 때문에 두 끝을 한
방향으로만 옮기는 방법을 쓸 수 없고, **지나온 값을 전부 표에 남겨 두는 것**이 그 자리를 대신해요.

```text
접두 합의 움직임   0 → 3 → 7 → 14 → 16 → 13 → 14 → 18 → 20
                                          └ 음수 −3 에서 값이 줄었다
                                            줄었다 늘었다 하므로 앞의 값을 버릴 수 없다
```

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **연속 부분 배열**이 무엇인지. 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 것이고,
  원소를 골라 담는 부분집합과 다릅니다.
- **접두 합**이 무엇인지. 배열의 앞에서부터 `j` 개를 더한 값이고, 구간 합을 두 칸의 뺄셈으로
  만들 때 씁니다. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 를 먼저 봅니다.
- **키-값 표**(자바스크립트의 `Map`)에서 값을 찾고 넣는 일. 여기서는 「이 수가 몇 번
  나왔는가」를 담는 데 씁니다.
- 배열을 한 번 지나가는 `for` 루프와, 배열 인덱스가 `0` 부터 시작한다는 것.

「합이 `k` 인 구간이 몇 개인가」와 「합이 조건을 만족하는 구간 중 가장 긴 것」은 다른
문제입니다. 뒤쪽은
[`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-problem.md)
이 다루는 것이고, 이 글은 **개수**를 셉니다.

```text
[3 4 7 2 -3 1 4 2] 에서
  합이 7 인 구간의 개수         4        ← 이 글이 하는 것. 몇 개인지가 답이다
  합이 7 이하인 가장 긴 구간    길이 4   ← 어느 구간인지가 답이다. 다른 문제다
```

### 아이디어 상세 — 접두 합의 짝 세기를 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function subarraySumEqualsK(nums: number[], k: number): number;
```

- 입력: 정수 배열 `nums` 와 찾을 합 `k`. 원소와 `k` 모두 음수일 수 있습니다.
- 출력: 합이 정확히 `k` 인 연속 부분 배열의 개수. 없으면 `0`.
- 제약: `1 ≤ n ≤ 100,000`, `−10,000 ≤ nums[i] ≤ 10,000`, `−10^9 ≤ k ≤ 10^9`.
  시간 1초, 메모리 256 MB.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 배열 `nums` 의 길이 | `n ≤ 100,000` |
| `k` | 찾을 구간 합 | `−10^9` 이상 `10^9` 이하 |
| `nums[i]` | 배열의 `i` 번째 값 | `−10,000` 이상 `10,000` 이하 |
| `l` · `r` | 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ n−1` |
| `P[j]` | `nums` 의 앞 `j` 개 원소의 합 | 칸이 `n+1` 개 |
| `seen` | 지금까지 지나온 접두 합이 각각 몇 번 나왔는지 담는 표 | 칸이 많아야 `n+1` 개 |
| `answer` | 지금까지 센 구간의 개수. 이 값이 답이 됩니다 | `0 ≤ answer ≤ n(n+1)/2` |

글에서 `P[j]` 로 적는 값은 코드에서 하나씩 갱신되는 변수 `prefix` 입니다. 표 전체를 배열로
만들지 않고 지금 값 하나만 들고 가는 것이라 이름을 따로 두었어요.

가장 먼저 떠오르는 방법으로 시작합시다. 왼쪽 끝 `l` 을 하나 정하고 오른쪽 끝 `r` 을 늘려
가며 합을 재는 것을, 모든 왼쪽 끝에 대해 되풀이하는 것이에요.

```ts
let answer = 0;
for (let l = 0; l < n; l++) {
  let sum = 0;
  for (let r = l; r < n; r++) {
    sum += nums[r] as number;      // 오른쪽 끝을 한 칸 넓히고 값을 더한다
    if (sum === k) answer++;
  }
}
```

이 방법이 보는 것은 **구간 전부**입니다. 원소가 음수일 수 있어서 합이 커졌다 작아졌다 하니,
중간에 멈출 근거가 없어 어떤 입력에서도 구간을 다 봐야 해요.

| `n` | 구간의 개수 `n(n+1)/2` | 초당 1억 번 기준 |
| --- | --- | --- |
| 1,000 | 500,500 | 0.005초 |
| 10,000 | 50,005,000 | 0.5초 |
| **100,000** | **5,000,050,000** | **50초** |

50 억 번입니다. 구간 하나를 한 번만 보는 것으로 잡아도 50 초가 넘어요. 제약이 10 만인데 이
방법으로는 1 초 안에 못 끝냅니다. 그러면 이 50 억 안에서 같은 덧셈을 몇 번이나 되풀이하는지
봅시다.

```text
nums 의 값   3  4  7  2 -3  1  4  2

l=0 이 더한 것   3 → 7 → 14 → 16 → 13 → 14 → 18 → 20
l=1 이 더한 것      4 → 11 → 13 → 10 → 11 → 15 → 17
l=2 이 더한 것          7 → 9 → 6 → 7 → 11 → 13
                        └ 인덱스 2 부터 뒤쪽을 세 번 다시 더했다
```

첫 줄이 이미 앞에서부터의 합을 전부 갖고 있는데, 아래 줄들이 그 뒷부분을 처음부터 다시
더합니다. 첫 줄을 한 번만 만들어 두면 어떤 구간이든 뺄셈 하나로 나와요.

```text
앞 여섯 개의 합   3 + 4 + 7 + 2 + (−3) + 1 = 14     P[6]
앞 두 개의 합     3 + 4                    = 7      P[2]
──────────────────────────────────────────────
14 − 7 = 7                                          구간 [2,5] 의 합이 뺄셈 하나로 나온다
```

이제 세 방식을 같은 입력에 실제로 실행해 **연산 수**를 셉니다. 방식 A 는 구간마다 직접
더하는 것, 방식 B 는 접두 합 표를 한 번 만들고 모든 쌍을 빼 보는 것, 방식 C 는 접두 합의
개수 표를 조회하는 것이에요.

<!--proof:cost-three-ways-->

```text
오른쪽 끝 r  직접 더하기  접두 합의 차이  개수 표
          0            1               1        1
          1            3               2        1
          2            6               3        1
          3           10               4        1
          4           15               5        1
          5           21               6        1
          6           28               7        1
          7           36               8        1

방식 A  모든 구간을 직접 더한다            덧셈 120 번
방식 B  접두 합 표를 만들고 쌍마다 뺀다    덧셈 8 번 · 뺄셈 36 번
방식 C  접두 합의 개수 표를 조회한다       덧셈 8 번 · 조회 8 번
        └ 답은 셋 다 4 로 같고, 오른쪽 열만 r 을 따라 늘지 않는다
```

방식 B 가 방식 A 의 120 을 36 으로 줄였지만 그 36 은 구간의 개수 그대로입니다. 여기서 관찰할
것은 **오른쪽 열이 전부 1** 이라는 것 하나예요 — 방식 C 에서 오른쪽 끝 하나를 처리하는 비용이
그 앞에 칸이 몇 개 있는지와 상관이 없습니다.

```text
오른쪽 끝 r      0  1  2  3  4  5  6  7
방식 B 의 비용   1  2  3  4  5  6  7  8      앞에 있는 칸 수를 그대로 따라간다
방식 C 의 비용   1  1  1  1  1  1  1  1      앞에 몇 칸이 있든 한 번이다
                 └ 이 줄이 50 억을 10 만으로 바꾸는 자리다
```

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「접두 합을 정렬해서 차이가
`k` 인 값끼리 짝지어 세면 되지 않나」가 그것이에요. 그러면 표를 유지할 필요도 없습니다.

<!--proof:cost-ignore-order-->

```text
입력                k  정본  순서를 무시하고 센 값
[3 4 7 2 -3 1 4 2]  7     4                      4  같다
[5 -5 5]            5     3                      4  다르다
[2 -2 2 -2]         2     3                      6  다르다
[1 -1 1 -1]         0     4                      4  같다
[1 2 3]             3     2                      2  같다

└ 뒤에 나온 접두 합이 더 작은 짝까지 세는 줄에서만 값이 커진다
```

첫 줄이 4 로 맞았는데 둘째 줄이 3 대신 4 를 냈습니다. 정렬하면 **어느 값이 먼저 나왔는지가
사라져서**, 뒤에 나온 값에서 앞에 나온 값을 빼는 짝까지 함께 세는 것이 원인이에요.

```text
[5 -5 5] 의 접두 합    0  5  0  5      칸 0 1 2 3
                       └ 차이가 5 인 짝을 순서 없이 세면 넷이다

  (칸 0, 칸 1)   0 → 5    구간 [0,0] 이다        ✓
  (칸 0, 칸 3)   0 → 5    구간 [0,2] 다          ✓
  (칸 2, 칸 3)   0 → 5    구간 [2,2] 다          ✓
  (칸 1, 칸 2)   5 → 0    앞이 크고 뒤가 작다    ✗ 이 짝의 구간 합은 −5 다
```

그러니 왼쪽 칸이 **오른쪽 칸보다 앞이어야 한다**는 조건을 절차가 지켜야 합니다. 여기서 진짜
개념이 나와요. **오른쪽 칸을 하나씩 옮기면서, 그 시점까지 지나온 접두 합만 담긴 표에 묻는
것**입니다. 표에 든 것이 전부 「앞」이라 조건이 저절로 지켜집니다.

```text
칸 j 를 처리할 때 표에 든 것    P[0] P[1] … P[j−1]     전부 j 보다 앞이다
묻는 값                         P[j] − k
받는 값                         그 값이 표에 있는 횟수
                                └ 그 횟수가 오른쪽 끝을 j−1 로 하는 답의 개수다
```

개념이 정하는 것은 **각 걸음이 하는 일의 개수**입니다. 걸음 하나에서 표에 묻는 것이 한 번,
표에 적는 것이 한 번이에요. 앞에 칸이 몇 개 쌓였든 이 둘은 변하지 않습니다.

```text
걸음 하나의 일

  더하기   prefix 에 값 하나를 더한다               1 번
  묻기     표에서 prefix − k 의 개수를 받는다       1 번
  적기     표에서 prefix 의 개수를 하나 늘린다      1 번
           └ 걸음이 n 개이므로 전체가 3n 번 언저리에서 끝난다
```

**쉬운 경우와 불안한 경우를 나눠서 값으로 확인합시다.** 쉬운 경우는 접두 합이 처음 나오는
칸이에요. 표에 그 값이 없으니 개수가 하나 늘어나기만 합니다.

```text
칸 3 을 처리하기 직전의 표    {0:1, 3:1, 7:1}
  접두 합                     14
  묻는 값 14 − 7 = 7          표에 1 번 있다 → 답에 1 을 더한다
  적기                        {0:1, 3:1, 7:1, 14:1}
                              └ 14 가 처음 나왔으므로 칸이 하나 늘었다
```

불안한 경우는 **같은 접두 합이 두 번째로 나오는 칸**입니다. 이 문제의 답이 겹쳐 세어지거나
빠지는 자리가 여기예요. 칸 6 에서 접두 합이 다시 14 가 됩니다.

```text
칸 6 을 처리하기 직전의 표    {0:1, 3:1, 7:1, 14:1, 16:1, 13:1}
  접두 합                     14   (칸 3 에 이어 두 번째다)
  묻는 값 14 − 7 = 7          표에 1 번 있다 → 답에 1 을 더한다
  적기                        14 의 개수가 1 에서 2 가 된다 → {…, 14:2}
                              └ 값을 덮어쓰지 않고 개수를 늘린다. 둘 다 왼쪽 칸 후보다
```

칸 6 이후에 「14 를 왼쪽 칸으로 쓰는 구간」을 묻는 걸음이 오면 답이 **둘** 나와야 합니다.
표가 개수를 담고 있어야 그 둘이 한 번의 조회로 나와요.

```text
표가 담는 것이 「있다/없다」라면    14 를 물었을 때 1 만 나온다   →  하나를 빠뜨린다
표가 담는 것이 「몇 번」이라면      14 를 물었을 때 2 가 나온다   →  둘 다 센다
```

빠뜨리는 칸이 없다는 것은 루프의 종료 조건으로 말할 수 있습니다. 루프는 `nums` 의 원소를
왼쪽부터 하나씩 받아 마지막 원소까지 실행되고, 한 번 실행할 때마다 칸 하나를 **정확히 한 번**
표에 적어요.

```text
루프가 끝난 시점에 처리한 원소가 n 개다
  적은 칸        P[1] P[2] … P[n]      n 개, 각각 정확히 한 번
  미리 적은 칸   P[0]                  루프에 들어가기 전에 개수 1 로 넣었다
                 └ 칸 n+1 개가 빠짐없이 한 번씩 표에 들어간다
```

이제 「지나온 접두 합을 **전부** 표에 남긴다」가 정말 필요한지 값으로 확인합니다. 직전 `W` 개만
남기고 오래된 것을 버리는 절차를 따로 만들어 `W` 를 다섯으로 두고 같은 입력에서 세었어요.

<!--proof:cost-window-->

```text
표에 남기는 개수  표 칸 수  조회 수  답  놓친 답
W=1                      1        8   1        3
W=2                      2        8   2        2
W=3                      3        8   3        1
W=4                      4        8   4        0
W=8                      8        8   4        0

└ 표를 줄여도 조회 수는 그대로이고 답만 줄어든다
  제약 규모 n = 100,000 에서 표는 많아야 100,001 칸이다
```

`W` 를 줄이면 **조회 수는 하나도 안 줄고 답만 빠집니다.** 표를 아껴서 얻는 것이 없다는 뜻이고,
그래서 답은 「전부 남긴다」예요. 표가 많아야 `n+1` 칸이라 메모리 제한에도 여유가 큽니다.

```text
얻은 절차 한 벌
  1. 표에 「접두 합 0 이 한 번 나왔다」를 미리 적는다
  2. 원소를 왼쪽부터 하나씩 받아 prefix 에 더한다
  3. 표에서 prefix − k 의 개수를 받아 답에 더한다
  4. 표에서 prefix 의 개수를 하나 늘린다
       └ 10 만 칸에서 50 억 번이던 것이 걸음 10 만 개가 된다
```

### 수행으로 알아보는 알고리즘 — 여덟 칸을 지나며 네 개의 답을 센다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const nums = [3, 4, 7, 2, -3, 1, 4, 2];
const k = 7;
// 이 절이 끝나면 4 가 나와야 한다
```

왜 하필 이 여덟 칸일까요? 음수가 하나 들어 있어 접두 합이 한 번 줄어들고, 접두 합 14 가 두
번 나와 **같은 값이 두 번째로 나오는 걸음**이 실제로 실행되며, 조회가 0 을 내는 걸음과 1 을
내는 걸음이 둘 다 나오기 때문이에요. 답 넷 중 하나는 왼쪽 끝이 인덱스 0 입니다.

```text
절차 전체를 한 장으로

    표를 만들고 「접두 합 0 이 한 번」을 적는다
    prefix 를 0 으로, answer 를 0 으로 둔다
    nums 의 원소를 왼쪽부터 하나씩 받으며:
        prefix 에 그 값을 더한다
        표에서 prefix − k 의 개수를 받아 answer 에 더한다      ① 조회
        표에서 prefix 의 개수를 하나 늘린다                    ② 기록
    answer 를 돌려준다
```

#### 1. 접두 합과 개수 표를 준비한다

시작 상태가 이 조각의 전부입니다. 세 줄이지만 그중 한 줄이 뒤의 모든 분기를 없애요.

```ts
const seen = new Map<number, number>();
seen.set(0, 1);

let prefix = 0;
let answer = 0;
```

`seen.set(0, 1)` 은 **원소를 하나도 안 고른 접두의 합이 0 이고, 그것이 한 번 있다**는 뜻입니다.
왼쪽 끝이 인덱스 0 인 구간은 이 칸을 왼쪽 칸으로 씁니다.

```text
구간 [0, r] 의 합 = P[r+1] − P[0] = P[r+1] − 0

  왼쪽 칸이 P[0] 이다        표에 0 이 들어 있어야 조회에 걸린다
  표가 비어 있으면           P[r+1] − k 가 0 이어도 못 찾는다
                             └ 왼쪽 끝이 0 인 답이 전부 여기서 빠진다
```

#### 2. 지금 필요한 접두 합을 표에서 조회한다

걸음마다 하는 일의 앞쪽 절반입니다. 값을 더해 접두 합을 갱신하고, 그 접두 합에 맞는 왼쪽 칸이
표에 몇 개 있는지 물어요.

```ts
for (const value of nums) {
  prefix += value;
  // ① 조회 — 지금 접두 합에서 k 를 뺀 값이 앞에 몇 번 나왔는지 그대로 더한다.
  answer += seen.get(prefix - k) ?? 0;
}
```

표가 `{0:1}` 인 상태에서 이 조각을 두 걸음만 실행하면 이렇게 나옵니다.

```text
걸음   값   prefix   묻는 값 prefix − 7   표에서 받은 개수   answer
T2      3        3                   −4                  0        0
T3      4        7                    0                  1        1
        └ T3 에서 찾은 것이 P[0] 이고, 그 짝이 구간 [0,1] 이다
```

`?? 0` 은 표에 그 값이 한 번도 안 나왔을 때를 맡습니다. 없으면 개수가 0 이고, 0 을 더하는
것은 아무것도 안 더하는 것과 같아서 **따로 분기를 두지 않아요.**

#### 짚고 가기 — 빈 접두를 세어 두지 않으면 왼쪽 끝이 0 인 답만 빠진다

여기서 헷갈리기 쉬운 포인트는 표의 시작 상태입니다. 「아직 아무 칸도 안 지나왔으니 표는 비어
있는 것이 자연스럽지 않나」로 읽기 쉬워요. 그 생각대로 첫 줄을 빼 봅시다.

```ts
const seen = new Map<number, number>();
// seen.set(0, 1) 을 두지 않았다
```

이렇게 하면 표는 첫 걸음의 기록부터 채워집니다. 그런데 왼쪽 끝이 인덱스 0 인 구간은 왼쪽 칸이
`P[0]` 이라, 그 칸이 표에 없으면 조회에 안 걸려요. 네 입력에 두 코드를 각각 실행해 봅니다.

<!--proof:pause-no-seed-->

```text
입력                  k  정본  빈 접두를 안 센 코드
[3 4 7 2 -3 1 4 2]    7     4                     3  답이 다르다
[1 1 1]               2     2                     1  답이 다르다
[1 2 3]               5     1                     1  답이 같다
[1 2 3]             100     0                     0  답이 같다

└ 아래 둘은 왼쪽 끝이 0 인 답이 없어서 그대로다. 그래서 이 변경이 남는다
```

첫 줄에서 4 가 3 이 됐습니다. 빠진 하나가 구간 `[0,1]`, 그러니까 값 3 과 4 를 더한 자리예요.
아래 두 줄은 **답이 안 틀립니다** — 그 입력에는 왼쪽 끝이 인덱스 0 인 답이 아예 없어서요.

```text
[1 2 3] · k=5 의 답    구간 [1,2] 하나다      왼쪽 끝이 1 이라 P[1] 을 왼쪽 칸으로 쓴다
                       P[1] 은 첫 걸음이 표에 적었다  →  빈 접두가 없어도 찾는다

[1 1 1] · k=2 의 답    구간 [0,1] 과 [1,2]    앞의 것이 P[0] 을 왼쪽 칸으로 쓴다
                       P[0] 이 표에 없다      →  그 하나가 빠진다
```

테스트에 왼쪽 끝이 인덱스 0 인 답이 없으면 이 코드는 그대로 통과합니다. 그래서 알아채지 못한
채로 남아요. 고치는 방법은 `P[0] = 0` 을 표에 미리 한 번 적는 것 하나입니다.

```text
고치는 길이 둘이다
  (가) 왼쪽 끝이 0 인 구간을 따로 검사한다   걸음마다 조건 하나가 는다
  (나) 표에 「0 이 한 번」을 미리 적는다     분기가 아예 없어진다
       └ (나)는 「없는 칸」 대신 「빈 접두의 합」이라는 뜻 있는 값을 그 자리에 둔다
```

#### 3. 조회를 먼저 하고 표에 기록한다

걸음의 뒤쪽 절반입니다. 조회를 마친 다음에 이번 접두 합을 표에 적어요. 값이 이미 있으면 개수를
하나 늘리고, 없으면 1 로 시작합니다.

```ts
for (const value of nums) {
  prefix += value;
  // ① 조회
  answer += seen.get(prefix - k) ?? 0;
  // ② 기록 — 이번 접두 합을 표에 한 번 더 적는다.
  seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
}
```

같은 값이 두 번째로 나오는 걸음에서 이 줄이 무엇을 하는지 보입니다. 칸 6 에서 접두 합이 다시
14 가 되는 자리예요.

```text
걸음   prefix   기록 전의 표                        기록 후의 표
T4         14   {0:1, 3:1, 7:1}                     {0:1, 3:1, 7:1, 14:1}
T7         14   {0:1, 3:1, 7:1, 14:1, 16:1, 13:1}   {…, 14:2}
                └ 개수가 1 에서 2 가 된다. 칸 수는 그대로 여섯이다
```

`?? 0` 이 여기서도 「처음 나온 값」을 맡습니다. 없으면 0 에서 시작해 1 이 되고, 있으면 그
개수에 1 을 더해요.

#### 짚고 가기 — 기록을 먼저 하면 k 가 0 일 때만 답이 늘어난다

여기서 헷갈리기 쉬운 포인트는 ① 과 ② 의 순서입니다. 「어차피 둘 다 이번 걸음에서 하는
일인데 순서가 중요할까」로 읽기 쉬워요. 순서를 바꿔 봅시다.

```ts
for (const value of nums) {
  prefix += value;
  seen.set(prefix, (seen.get(prefix) ?? 0) + 1);   // 기록을 먼저 했다
  answer += seen.get(prefix - k) ?? 0;
}
```

기록을 먼저 하면 표에 **이번 칸 자신**이 들어간 상태로 조회합니다. 이번 칸을 왼쪽 칸으로 쓰는
짝은 `P[j] − P[j] = 0` 이라, `k` 가 0 일 때만 조회에 걸려요. 다섯 입력으로 확인합니다.

<!--proof:pause-record-first-->

```text
입력                k  n  정본  기록을 먼저 한 코드  차이
[3 4 7 2 -3 1 4 2]  7  8     4                    4     0
[1 2 3]             3  3     2                    2     0
[1 -1 1 -1]         0  4     4                    8     4
[0 0 0]             0  3     6                    9     3
[5]                 0  1     0                    1     1

└ k 가 0 인 줄에서만 답이 늘고, 늘어난 양이 정확히 n 이다
```

위 두 줄은 **답이 안 틀립니다.** `k` 가 0 이 아니면 자기 자신과의 짝이 조회에 안 걸리기
때문이에요. 그래서 `k` 가 0 인 테스트가 없으면 이 순서 바꾸기는 그대로 통과합니다.

```text
늘어난 양이 정확히 n 인 이유
  걸음마다 자기 자신 하나가 더 세어진다        걸음이 n 개다
  그 짝이 뜻하는 구간은 길이 0 짜리다          원소를 하나도 안 고른 것이라 구간이 아니다
       └ 문제가 세라고 한 것은 원소가 하나 이상인 구간이다
```

#### 4. 여덟 칸을 끝까지 지나며 짝을 센다

두 조각을 하나로 이어 고정 입력에 실행하면 아홉 걸음이 나옵니다. T1 은 루프에 들어가기 전
준비이고, T2 부터 T9 까지 여덟 걸음이 원소 하나씩을 처리해요.

```text
걸음  r  값  접두 합  찾는 값  표에서 찾은 개수  답 누적  표 칸 수
T2    0   3        3       -4                 0        0         2
T3    1   4        7        0                 1        1         3
T4    2   7       14        7                 1        2         4

T9    7   2       20       13                 1        4         8
```

**두 갈래가 모두 실행됐습니다.** ① 은 T2 부터 T9 까지 여덟 번 실행돼 「표에서 찾은 개수」 열을
만들었고, ② 도 같은 여덟 걸음에서 실행돼 「표 칸 수」 열을 움직였어요. T6 과 T7 사이에서 표
칸 수가 6 에서 6 으로 그대로인 것이 ② 가 **개수만 늘린** 자리입니다.

```text
①  표에 묻는다     T2 T3 T4 T5 T6 T7 T8 T9      조회 8 번 = n
②  표에 적는다     T2 T3 T4 T5 T6 T7 T8 T9      기록 8 번 = n
                                                 └ 답이 몇 개든 걸음 수는 여덟이다
```

조회가 1 을 낸 네 걸음이 어느 구간을 가리키는지 확인하고 갑니다. 찾은 값이 왼쪽 칸이고, 지금
칸이 오른쪽 칸이에요.

```text
걸음   왼쪽 칸        오른쪽 칸   구간        구간의 값
T3     P[0] = 0       P[2] = 7    [0,1]       3 4
T4     P[2] = 7       P[3] = 14   [2,2]       7
T7     P[2] = 7       P[6] = 14   [2,5]       7 2 -3 1
T9     P[5] = 13      P[8] = 20   [5,7]       1 4 2
                                              └ 네 줄 다 더하면 7 이다
```

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `answer` 를 그대로 돌려주는
마지막 한 줄뿐이에요 — 배열이 비면 루프가 한 번도 실행되지 않아 0 이 그대로 답이 됩니다.

```ts
export function subarraySumEqualsK(nums: number[], k: number): number {
  // 지금까지 지나온 접두 합이 각각 몇 번 나왔는지 담는 표.
  const seen = new Map<number, number>();
  // 원소를 하나도 안 고른 접두의 합은 0 이다. 그 한 번을 미리 세어 둔다.
  seen.set(0, 1);

  let prefix = 0;
  let answer = 0;
  for (const value of nums) {
    prefix += value;
    // ① 조회 — 지금 접두 합에서 k 를 뺀 값이 앞에 몇 번 나왔는지 그대로 더한다.
    answer += seen.get(prefix - k) ?? 0;
    // ② 기록 — 이번 접두 합을 표에 한 번 더 적는다.
    seen.set(prefix, (seen.get(prefix) ?? 0) + 1);
  }

  return answer;
}
```

```text
subarraySumEqualsK([3, 4, 7, 2, -3, 1, 4, 2], 7)   →  4
subarraySumEqualsK([1, 1, 1], 2)                   →  2
subarraySumEqualsK([1, -1, 1, -1], 0)              →  4
subarraySumEqualsK([1, 2, 3], 100)                 →  0
subarraySumEqualsK([], 7)                          →  0
```

### 알아 두면 좋은 개념 — 여집합 조회

이 절차가 걸음마다 한 일을 한 문장으로 줄이면 **「지금 가진 값에서 목표를 빼 필요한 나머지를
만들고, 그것이 앞에 있었는지 표에 묻는다」** 입니다. 그 「필요한 나머지」를 **여집합**이라고
부르고, 이렇게 묻는 방식을 여집합 조회라고 합니다.

```text
                  목표 k
                    │
   지금 가진 값 ─── 빼기 ───→ 필요한 나머지 ───→ 표에 묻는다 ───→ 개수
   prefix                     prefix − k          seen

   T3 에서    prefix = 7,  k = 7   →  필요한 나머지 0  →  표에 1 번 있다
   T9 에서    prefix = 20, k = 7   →  필요한 나머지 13 →  표에 1 번 있다
```

같은 모양이 다른 문제에서도 같은 이름으로 나옵니다. 바뀌는 것은 **표에 무엇을 담는가** 하나예요.

| 문제 | 표에 담는 것 | 필요한 나머지 |
| --- | --- | --- |
| [`twoSum`](../twoSum/twoSum-problem.md) | 지나온 원소의 값 → 인덱스 | `target − nums[i]` |
| 이 문제 | 지나온 접두 합 → 개수 | `prefix − k` |
| 합이 `M` 의 배수인 구간 세기 | 접두 합을 `M` 으로 나눈 나머지 → 개수 | 같은 나머지 |

세 줄의 차이는 **표의 값 자리**입니다. 답이 「어느 것인가」면 인덱스를 담고, 답이 「몇
개인가」면 개수를 담아요. 이 문제가 개수를 담는 이유가 그것입니다.

```text
표의 값 자리가 정하는 것
  인덱스를 담는다   짝을 하나 찾으면 끝난다        twoSum 은 하나만 있으면 된다
  개수를 담는다     같은 값이 여럿이면 다 센다     이 문제는 전부 세어야 한다
```

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 세는 일을 식으로 어떻게 적는지,
무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 세는 대상이 **연속 구간**입니다. 원소를 골라 담는 부분집합이면 접두 합의 차이로 만들 수
  없어요.
- 구간에 매기는 값이 **덧셈으로 쌓이고 뺄셈으로 취소됩니다.** 합·개수·배타적 논리합이
  그렇고, 최댓값은 아닙니다.
- 조건이 **정확히 하나의 값**입니다. `= k` 라서 물을 값이 하나로 정해져요. `≤ k` 였다면
  표에 「그 값 하나」가 아니라 「그 값 이하 전부」를 물어야 합니다.
- 원소에 **음수가 섞일 수 있습니다.** 이 조건이 두 끝을 한 방향으로만 옮기는 방법을 막고, 그
  자리를 표가 대신합니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  연속 구간        → 접두 합 두 개의 뺄셈으로 구간이 만들어진다
  덧셈과 뺄셈      → 앞부분이 서로 지워진다
  값이 하나        → 표에 묻는 것이 한 번이다
  음수가 있다      → 지나온 값을 버리지 않고 전부 표에 남긴다
```

마지막 두 줄이 이 절차의 경계입니다. 조건이 `≤ k` 로 바뀌면 표 하나를 묻는 것으로 끝나지
않고, 원소가 전부 비음이면 표 없이도 두 끝을 옮겨 풀 수 있어요.

```text
조건이 "= k"          표에서 값 하나를 묻는다               이 글의 절차
조건이 "≤ k"          그 값 이하의 개수를 묻는다            순서를 유지하는 다른 표가 필요하다
원소가 전부 비음      두 끝을 오른쪽으로만 옮겨도 된다      표가 아예 없어도 된다
                      └ 이 문제는 음수를 허용하므로 셋째 줄이 아니다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "합이 정확히 k 인"  "합이 k 가 되는"                ← 값이 하나로 정해진다
  "연속된"  "부분 배열"  "구간"                        ← 골라 담는 것이 아니다
  "개수를 구하라"  "몇 개인가"                         ← 하나만 찾는 문제가 아니다
  "음수가 포함될 수 있다"                              ← 결정적인 신호다

제약에 이런 모양이 보이면
  N 이 10^5 이상이라 N² 이 못 들어간다
  값의 범위가 좁아 접두 합이 정수 범위를 안 넘는다

반대로 이런 말이 보이면 해당하지 않는다
  "합이 k 이하인"  "합이 최대인"                       ← 물을 값이 하나가 아니다
  "구간의 최솟값"  "구간의 최댓값"                     ← 뺄셈으로 취소되지 않는다
  "원소는 모두 양수"                                   ← 두 끝을 옮기는 방법이 열린다
```

두 번째 무리가 보이면 다른 절차로 갑니다. 합이 최대인 구간이면
[`kadane`](../kadane/kadane-problem.md) 쪽이고, 원소가 전부 비음이고 상한이 걸린 문제면
[`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-problem.md)
쪽이에요.

#### 실제로 쓰이는 곳

- **CPython 의 `collections.Counter`** — 이 절차의 「개수 표」 그 자체입니다. 없는 키를 물으면
  예외 대신 0 을 돌려주는 것이 `?? 0` 과 같은 자리이고, 공식 문서가 그 동작을 *"returns a zero
  count for missing items instead of raising a KeyError"* 로 적고 있어요.
  ([`collections.Counter`](https://docs.python.org/3/library/collections.html#collections.Counter),
  조회 2026-08-29)
- **NumPy 의 `numpy.cumsum`** — 배열 하나를 받아 접두 합 배열을 돌려줍니다. 이 글의 `P` 와
  다른 점은 **앞에 0 칸을 두지 않는다**는 것이라, 왼쪽 끝이 인덱스 0 인 구간을 따로 다뤄야
  해요 — 첫 「짚고 가기」에서 값으로 확인한 그 자리입니다.
  ([`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-29)
- **SQL 의 윈도 함수** — `sum(v) over (order by i)` 가 접두 합을 만들고, 그 결과를 값으로 묶어
  세면 이 글의 표가 됩니다. PostgreSQL 공식 문서의 윈도 함수 장이 누적 집계를 그 꼴로 적어요.
  ([PostgreSQL — Window Functions](https://www.postgresql.org/docs/current/tutorial-window.html),
  조회 2026-08-29)

```text
세 사례와 이 문제의 관계

  앞의 둘   조각을 하나씩 제공한다. 접두 합과 개수 표를 잇는 것은 쓰는 쪽의 몫이다
  SQL       두 조각을 한 질의에 적을 수 있지만 접두 합 열을 통째로 만든다
            └ 이 글의 절차는 그 열을 만들지 않고 값 하나만 들고 지나간다
```

**이 절차 전체를 하나의 이름으로 제공하는 시스템은 찾지 못했습니다.** 표준 라이브러리가 주는
것은 두 조각이고, 「지나온 접두 합의 개수를 세면서 여집합을 묻는다」는 그 둘을 잇는 쪽의
코드로 남아 있어요.

### 수식 정의와 유도

접두 합을 기호로 정의합니다. 칸 0 은 원소를 하나도 안 고른 접두의 합이고, 그다음부터는 직전
칸에 값 하나를 더한 것입니다.

$$P[0] = 0, \qquad P[j] = P[j-1] + nums[j-1] \quad (1 \le j \le n)$$

```text
정의를 값에 넣어 봅니다 — nums 의 값 3 4 7 2 -3 1 4 2

  P[0] = 0
  P[1] = P[0] + nums[0] = 0 + 3 = 3
  P[2] = P[1] + nums[1] = 3 + 4 = 7
  P[3] = P[2] + nums[2] = 7 + 7 = 14
       └ 정의 하나가 칸 하나를 정하고, 정의가 두 항만 본다
```

구간 합을 이 기호로 적으면 이렇게 됩니다. 앞 `r+1` 개의 합에서 앞 `l` 개의 합을 덜어 낸 것이
가운데 구간이에요.

$$\sum_{t=l}^{r} nums[t] = P[r+1] - P[l] \qquad (0 \le l \le r \le n-1)$$

```text
값으로 확인합니다 — l = 2, r = 5. 더하는 자리를 t 로 적어 접두 합의 칸 번호와 갈라 둡니다

  t = 0 … 5 의 합   3 + 4 + 7 + 2 + (−3) + 1 = 14      P[6]
  t = 0 … 1 의 합   3 + 4                    = 7       P[2]
  t = 2 … 5 의 합           7 + 2 + (−3) + 1 = 7
                    └ 앞의 둘이 겹치는 항이 없고, 셋을 합치면 14 = 7 + 7 이다
```

이제 답을 집합으로 정의합니다. 세는 것은 구간이지만, 위 식이 구간 하나에 접두 합의 짝 하나를
붙여 주므로 **짝의 개수**로 옮겨 적을 수 있어요.

$$A = \{(l, r) : 0 \le l \le r \le n-1,\ P[r+1] - P[l] = k\}$$

```text
A 를 값으로 폅니다 — k = 7 일 때 조건을 만족하는 (l, r)

  (0, 1)   P[2] − P[0] = 7 − 0  = 7
  (2, 2)   P[3] − P[2] = 14 − 7 = 7
  (2, 5)   P[6] − P[2] = 14 − 7 = 7
  (5, 7)   P[8] − P[5] = 20 − 13 = 7
           └ |A| = 4 이고, 그것이 이 입력의 답이다
```

같은 것을 접두 합의 칸으로만 적으면 이렇게 됩니다.

$$B = \{(i, j) : 0 \le i < j \le n,\ P[j] - P[i] = k\}$$

```text
두 집합이 같은 크기인 이유 — 짝을 서로 옮겨 보면 됩니다

  (l, r)  →  (i, j) = (l, r+1)      l ≤ r 이므로 i < j 다
  (i, j)  →  (l, r) = (i, j−1)      i < j 이므로 l ≤ r 이다
       └ 두 방향을 이어 적용하면 처음 짝이 그대로 나온다. 그래서 개수가 같다
```

`B` 를 오른쪽 칸 `j` 로 갈라 셉니다. 짝 하나에는 `j` 가 하나뿐이므로, `j` 마다 세어 더하면
겹치지도 빠지지도 않아요.

$$|B| = \sum_{j=1}^{n} \bigl| \{ i : 0 \le i < j,\ P[i] = P[j] - k \} \bigr|$$

```text
이 합을 값으로 폅니다 — k = 7

  j=1   P[1]=3    3−7=−4    앞에 −4 가 0 개    0
  j=2   P[2]=7    7−7=0     앞에 0 이 1 개     1
  j=3   P[3]=14   14−7=7    앞에 7 이 1 개     1
  j=4   P[4]=16   16−7=9    앞에 9 가 0 개     0
  j=5   P[5]=13   13−7=6    앞에 6 이 0 개     0
  j=6   P[6]=14   14−7=7    앞에 7 이 1 개     1
  j=7   P[7]=18   18−7=11   앞에 11 이 0 개    0
  j=8   P[8]=20   20−7=13   앞에 13 이 1 개    1
                                               └ 합이 4 다
```

합의 안쪽 항은 **`j` 보다 앞에 있는 칸 중 값이 `P[j] − k` 인 것의 개수**입니다. 그 개수를
왼쪽부터 누적해 두면 항 하나가 조회 한 번이 돼요. 식을 그대로 옮긴 조각이 이것입니다.

```ts
// 위 합의 항 하나를 그대로 적은 것. 실제 절차는 이 세기를 표로 대신한다.
const term = (P: number[], j: number, k: number): number =>
  P.slice(0, j).filter((v) => v === (P[j] as number) - k).length;
```

이 조각은 항 하나를 세는 데 `j` 번을 보므로 전부 더하면 `n(n+1)/2` 번입니다. 표를 쓰면 항
하나가 조회 한 번이라 `n` 번이에요 — 같은 합을 구하는 두 방법의 차이가 그것입니다.

$$|B| \le \binom{n+1}{2} = \frac{n(n+1)}{2}$$

```text
등호가 성립하는 자리
  P 의 모든 칸이 같은 값이고 k = 0 이면 짝이 전부 조건을 만족한다
  칸이 n+1 개이므로 짝이 (n+1)n/2 개다
       └ 원소가 전부 0 이고 k = 0 인 입력이 그것이다
```

닫힌 형태에 규모를 넣고 실제 실행과 대조했어요. 왼쪽 두 열이 답의 최댓값이고, 오른쪽 두 열이
표를 쓰는 절차의 맵 연산 수입니다.

<!--proof:math-scale-->

```text
      n  구간의 개수(실측)       n(n+1)/2  맵 연산(실측)   3n + 1
      3                  6              6             10       10
      8                 36             36             25       25
  1,000            500,500        500,500          3,001    3,001
100,000      5,000,050,000  5,000,050,000        300,001  300,001
```

실측값이 닫힌 형태와 네 규모에서 정확히 같습니다. 마지막 줄이 이 문제의 제약 규모예요 — 답이
50 억을 넘을 수 있는데 그 답을 만드는 연산은 30 만 번입니다.

```text
n = 100,000 에서
  답의 최댓값        n(n+1)/2 = 5,000,050,000     32 비트 정수의 범위를 넘는다
  맵 연산            3n + 1   =       300,001
  5,000,050,000 ÷ 300,001 ≈ 16,667 배
       └ 답이 연산 수보다 훨씬 클 수 있다는 것이 이 절차의 성질이다
```

### 불변식 — 표는 지금까지 지나온 접두 합의 개수를 그대로 담는다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> 루프가 `j` 번째 원소를 처리한 직후, 표는 `P[0]` 부터 `P[j]` 까지가 각각 몇 번 나왔는지를
> 담고 있고, `answer` 는 오른쪽 끝이 인덱스 `j−1` 이하인 구간 중 합이 `k` 인 것의 개수입니다.

```text
       P[0]  P[1]  …  P[j]        P[j+1] … P[n]
 표      ●     ●    …    ●            아직 없다
         └ 여기까지가 표에 든 것이다        ← 앞 문장

 answer  오른쪽 끝이 j−1 이하인 답을 전부 셌다   ← 뒤 문장
         그보다 오른쪽에서 끝나는 답은 아직 안 셌다
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 표가 「지나온 것」만 담는다는 것이고, 뒤 문장이
**답을 두 번 세거나 빠뜨리지 않는다**는 것을 말해요. 둘 중 하나만 빠져도 조회 결과를 그대로
더해도 된다는 근거가 사라집니다.

**출발점부터 봅시다.** 루프에 들어가기 전 표는 `{0:1}` 이고 `answer` 는 0 입니다. 원소를 하나도
처리하지 않았으니 「`P[0]` 이 한 번」이 맞고, 센 답도 0 개가 맞아요.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | 표에 `0` 을 한 번 적는다 | `P[0]` 하나만 지나왔다 | 센 것이 없다 |
| `j = 1` | 조회하고 `P[1]` 을 적는다 | 표에 `P[1]` 이 더해진다 | 오른쪽 끝 0 인 답을 전부 셌다 |
| 임의의 `j` | 조회하고 `P[j]` 를 적는다 | 직전 걸음이 `P[j−1]` 까지 만들어 뒀다 | 오른쪽 끝 `j−1` 인 답이 조회 결과다 |
| 종료 | `j = n` | `P[0]` 부터 `P[n]` 까지 전부 | 오른쪽 끝 `n−1` 이하가 전부다 |

조회가 오른쪽 끝 `j−1` 인 답의 개수와 같다는 것이 셋째 줄의 핵심입니다. 조회 시점의 표는
`P[0]` 부터 `P[j−1]` 까지만 담고 있고, 그중 값이 `P[j] − k` 인 칸 하나가 답 하나예요.

```text
조회 시점의 표      P[0] … P[j−1]        이번 칸 P[j] 는 아직 안 들어갔다
찾은 개수 c         값이 P[j] − k 인 칸이 c 개
뜻하는 것           왼쪽 칸 후보가 c 개  →  오른쪽 끝이 j−1 인 답이 c 개
                    └ 기록을 조회 뒤로 미룬 이유가 이 줄이다
```

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 배열이 빔 | 루프가 한 번도 실행되지 않는다 | `0` |
| 원소 하나 `[5]`, `k = 5` | 표가 `{0:1}`, 조회가 `5−5=0` 을 찾는다 | `1` |
| 원소 하나 `[5]`, `k = 1` | 조회가 `4` 를 찾고 표에 없다 | `0` |
| `k = 0` 이고 원소도 `[0]` | 조회가 `0` 을 찾아 표의 첫 칸에 걸린다 | `1` |
| 원소가 전부 `0`, `k = 0` | 걸음마다 표의 `0` 개수가 하나씩 는다 | `n(n+1)/2` |
| 음수만 섞인 `[-1 -1 1]`, `k = -2` | 접두 합이 줄어드는 방향으로 간다 | `1` |
| 답이 하나도 없음 | 조회가 늘 0 을 낸다 | `0` |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 표에 개수를 더하는 그 한 줄이에요. 「어차피 값이
있었는지만 알면 되지 않나」라는 생각으로 개수 대신 1 을 적어 봅니다. 한 줄만 바뀝니다.

```ts
for (const value of nums) {
  prefix += value;
  answer += seen.get(prefix - k) ?? 0;
  seen.set(prefix, 1);   // 개수를 더하지 않고 1 을 적는다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-count-once-->

```text
입력                k  정본  개수 대신 1 을 적은 코드  차이
[3 4 7 2 -3 1 4 2]  7     4                         4     0
[1 -1 1 -1]         0     4                         3    -1
[0 0 0]             0     6                         3    -3
[1 1 1]             2     2                         2     0

└ 같은 접두 합이 두 번 이상 나오는 입력에서만 답이 줄어든다
```

첫 줄과 마지막 줄은 답이 그대로입니다. 그 두 입력에서는 **같은 접두 합이 두 번 나온 뒤 그
값을 다시 묻는 걸음이 없었어요.** 아래 두 줄에서 답이 줄어든 것이 이 줄이 하던 일입니다.

```text
[0 0 0] · k=0 의 표 변화

  정본      {0:1} → {0:2} → {0:3} → {0:4}      조회가 1, 2, 3 을 내어 합이 6
  깨진 판   {0:1} → {0:1} → {0:1} → {0:1}      조회가 1, 1, 1 을 내어 합이 3
                    └ 개수를 덮어써서 두 번째·세 번째 칸이 사라졌다
```

세 번째 줄이 6 에서 3 으로 준 것이 정확히 그 자리입니다. 「값이 있었는가」만 담는 표로는
**같은 값이 여럿일 때 답이 몇 개인지**를 낼 수 없어요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 종류뿐입니다 — 값을 더하는 것, 표에 묻는 것, 표에 적는 것이에요.
전개의 값으로 확인하면 T2 부터 T9 까지 여덟 걸음이 셋을 각각 한 번씩 실행했습니다.

```text
더하기   T2 T3 T4 T5 T6 T7 T8 T9      걸음마다 한 번  →  정확히 8 번 = n
묻기     T2 T3 T4 T5 T6 T7 T8 T9      걸음마다 한 번  →  정확히 8 번 = n
적기     T2 T3 T4 T5 T6 T7 T8 T9      걸음마다 한 번  →  정확히 8 번 = n
         └ T1 은 루프 밖이고 표에 한 번 적는 것이 전부다
```

셋 다 반복마다 정확히 하나이므로 각각 `n` 번이고, 시작할 때의 기록 하나가 더 붙습니다.
개수는 **입력의 내용과 무관하게 정해져요** — 값이 크든 작든, 답이 많든 적든 같습니다.

```text
총식 = 더하기 + 조회 + 표 읽기 + 표 쓰기
       └ n     └ n    └ n       └ n + 1
                  └ 적기 한 번이 읽기 하나와 쓰기 하나로 나뉜다

       맵 연산 = n + n + (n + 1) = 3n + 1
       산술 연산(덧셈·뺄셈)만 보면 걸음마다 둘이라 2n 이다
```

여기서 센 것은 **표를 만들고 묻는 연산 전부**입니다. 추가로 잡는 메모리는 표 하나뿐이라 많아야
`n + 1` 칸이고, 입력 배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (답이 하나도 없다) | `O(n)` | `Θ(n)` |
| **평균적인 경우** (입력 분포와 무관하다) | `O(n)` | `Θ(n)` |
| **최악의 경우** (모든 구간이 답이다) | `O(n)` | `Θ(n)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 걸음 수가 `n` 으로 딱 고정이라 입력의 모양을 어떻게
바꿔도 값이 같아요.

```text
비교 대상과 나란히 놓으면 이 성질이 확인된다
  구간을 하나씩 본다   최선 n(n+1)/2 번   최악 n(n+1)/2 번
  접두 합의 짝을 센다  최선 3n+1 번       최악 3n+1 번
                       └ 앞쪽은 답을 안 찾아도 구간을 다 봐야 한다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 표를 만드는 것 하나뿐이라는 것이 이
절차의 특징이에요 — 정렬도 좌표압축도 하지 않습니다.

```text
총식 = Θ(n) 시간 + Θ(n) 추가 메모리
       └ 걸음 n 개 × 걸음당 세 연산    └ 표가 많아야 n+1 칸

n = 100,000 이면 맵 연산이 정확히 300,001 번, 표는 많아야 100,001 칸이다
```

**보장의 종류를 나눠 적어야 하는 자리가 하나 있습니다.** 연산의 **횟수**는 최악 보장이에요 —
어떤 입력을 넣어도 `3n + 1` 번입니다. 그런데 그 연산 **하나가 상수 시간**이라는 것은 표의
구현에 달린 값이고, 해시 충돌이 드물다는 전제 위의 기댓값입니다.

```text
두 층을 갈라 적는다
  연산의 횟수      3n + 1        최악 보장. 입력이 무엇이든 이 수다
  연산 하나의 비용 상수          기댓값. 해시가 키를 고르게 나눈다는 전제 위다
                                 └ 무작위성은 입력 분포가 아니라 표의 해시가 만든다

  충돌이 많은 키 집합을 일부러 만들면 조회 하나가 길어질 수 있다
  최악 보장까지 필요하면 접두 합을 정렬해 좌표압축하고 배열로 세면 Θ(n log n) 이 된다
```

#### 최악을 만드는 입력

연산 수를 최대로 만드는 방법은 하나뿐입니다 — **`n` 을 제약의 최댓값으로 두는 것**이에요.
입력의 모양은 걸음 수를 바꾸지 못합니다. 그것을 값으로 확인해 봅시다.

```text
n = 1,000 에서 입력의 모양만 바꿔 본다

  전부 0 · k=0        모든 구간이 답이다        답이 가장 많은 입력이다
  전부 1 · k=5        길이 5 짜리만 답이다      답이 n−4 개다
  1 2 3 … n · k=0     답이 하나도 없다          접두 합이 전부 다르다
                      └ 답의 개수가 세 자리에서 크게 갈린다. 걸음 수는 어떨까
```

세 모양의 연산 수를 실제로 셌습니다.

<!--proof:worst-shape-->

```text
입력의 모양 (n=1,000)          조회 수  표 칸 수       답
전부 0 · k=0 — 답이 가장 많다    1,000         1  500,500
전부 1 · k=5                     1,000     1,001      996
1 2 3 … n · k=0 — 답이 없다      1,000     1,001        0

└ 조회 수가 세 줄 다 같다. 답이 몇 개든 걸음 수는 n 이다
```

**「답이 많은 입력이 느리다」는 이 절차에서 거짓입니다.** 물려받은 통념이 여기서는 성립하지
않아요 — 첫 줄과 셋째 줄에서 답은 500,500 대 0 인데 조회 수는 둘 다 1,000 입니다. 답을
하나씩 만들어 내지 않고 **개수를 한 번에 더하기** 때문이에요.

```text
최악은 축마다 다른 입력이 만든다
  걸음 수의 최악    n = 100,000       입력의 모양과 무관하다. 맵 연산 300,001 번
  표 칸 수의 최악   접두 합이 전부 다른 입력   칸이 n+1 = 100,001 개다
  답 크기의 최악    전부 0 이고 k = 0          5,000,050,000
       └ 첫 줄이 시간을, 둘째 줄이 메모리를, 셋째 줄이 반환값의 크기를 정한다
```

표 칸 수의 최악은 둘째 줄과 셋째 줄이 함께 보입니다. 접두 합이 한 번도 겹치지 않으면 칸이
`n+1` 개가 되고, 전부 겹치면 한 칸으로 끝나요.

```text
전부 0 · k=0        표가 {0: 1001} 한 칸이다        답은 가장 많다
1 2 3 … n · k=0     표가 1,001 칸이다               답은 하나도 없다
                    └ 메모리가 많이 드는 입력과 답이 많은 입력이 서로 반대다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 구간을 하나씩 재던 것을 **접두 합 짝 세기**로
바꿨고, 오른쪽 칸을 고정하면 물을 값이 하나로 정해지며, 지나온 접두 합의 **개수**를 표에
들고 있으면 그 질문이 조회 한 번이 됩니다.

```text
표에 「0 이 한 번」을 적는다 → 걸음마다 prefix 를 갱신한다 → prefix − k 의 개수를 더한다 → prefix 를 적는다
      └ 왼쪽 끝이 0 인 답을 맡는다        └ 덧셈 n 번          └ 조회 n 번        └ 기록 n 번
```

먼저 답이 붙는 문제 하나입니다. 전개의 T7 은 접두 합이 두 번째로 14 가 된 걸음이었어요.
그때 표에서 찾은 개수가 1 이었는데, 만약 그 자리에서 2 가 나왔다면 무슨 뜻일까요?

```text
T7   prefix = 14   찾는 값 7   표에서 찾은 개수 1   답 누적 3
                   └ 표에 7 이 한 번 들어 있었다
```

<!--check:found-two-->
접두 합 7 이 그 시점까지 **두 번** 나왔다는 뜻이고, 그러면 오른쪽 끝이 인덱스 5 인 답이 둘이
됩니다. 왼쪽 칸 후보가 둘이니 구간도 둘이에요.

```text
표에 7 이 두 번 있었다면
  왼쪽 칸 후보   P[2] = 7 과 P[x] = 7      x 는 2 와 6 사이의 어떤 칸이다
  나오는 구간    [2,5] 와 [x,5]            둘 다 합이 7 이다
                 └ 조회 한 번이 답 두 개를 한꺼번에 낸다
```

같은 이유로 「표에 개수를 담는다」가 「표에 있다/없다를 담는다」로 바뀌면 이 자리에서 답이
빠집니다. 불변식 절의 깨뜨리기가 그것을 값으로 보인 자리예요.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「알아 두면 좋은 개념」           3 → 「비용 계산」의 최악을 만드는 입력
  2 → 두 번째 「짚고 가기」
```

- 합이 `M` 의 배수인 연속 부분 배열의 개수를 세려면 표에 무엇을 담아야 할까요?
  `nums` 의 값 3 4 7 2 로 `M = 5` 일 때 표가 어떻게 변하는지 손으로 적어 보세요.
- 전개의 T2 는 조회가 0 을 냈습니다. 만약 `k` 를 `−4` 로 바꾸면 T2 의 조회 결과가 어떻게
  되고, 답 전체는 몇이 될까요? 표의 첫 칸이 어디에 걸리는지까지 확인해 보세요.
- 반환값이 `n(n+1)/2` 까지 커질 수 있다는 것을 위에서 확인했습니다. 언어가 32 비트 정수만
  쓴다면 어느 입력에서 값이 넘치는지, 그리고 그것을 어떻게 알아챌 수 있을지 생각해 보세요.
