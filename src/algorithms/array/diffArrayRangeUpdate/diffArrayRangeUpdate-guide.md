# diffArrayRangeUpdate — 구간 전체를 고치지 않고 경계 두 칸만 적어 두는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 구간을 통째로 고치는
방법에서 갱신 하나를 칸 두 개로 줄이는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

길이 `N` 인 배열이 있고 처음에는 모든 칸이 `0` 입니다. 「인덱스 `l` 부터 `r` 까지 `v` 를
더하라」는 갱신이 `Q` 개 들어오고, **전부 적용한 뒤의 배열 하나**를 돌려주는 문제예요.
갱신 도중에는 아무것도 묻지 않는다는 것이 이 문제의 성격을 정합니다.

```text
N = 7 · 갱신 셋

  인덱스      0    1    2    3    4    5    6
  (1,3,2)         +2   +2   +2
  (0,2,-1)   -1   -1   -1
  (5,6,3)                             +3   +3
  -------------------------------------------
  결과       -1    1    1    2    0    3    3
```

갱신마다 구간을 통째로 고치면 일이 구간의 길이만큼 생깁니다. 제약이 `N ≤ 100,000` 이고
`Q ≤ 100,000` 이라, 모든 갱신이 배열 전체를 덮으면 칸을 고치는 횟수가 100 억 번이에요.

```text
갱신 하나가 덮는 칸    최대 N = 100,000
갱신 개수              최대 Q = 100,000
칸을 고치는 횟수       100,000 × 100,000 = 10,000,000,000
                       └ 1 초 제한 안에 못 끝낸다
```

여기서 **차이만 적어 두는 배열 `D`** 를 씁니다. 갱신 하나를 「인덱스 `l` 에서 `v` 가 시작된다」와
「인덱스 `r+1` 에서 그 `v` 가 없어진다」 두 사건으로 바꾸고, 그 두 칸에만 값을 적어요.

```text
갱신 (1,3,2) 를 두 사건으로

  D 의 칸 번호    0    1    2    3    4    5    6    7
  적는 값             +2             -2
                       ↑
                       └ 인덱스 1 부터 2 가 있다
                                      ↑
                                      └ 인덱스 4 부터 그 2 가 없다
```

갱신 셋을 같은 방법으로 다 적은 다음 **앞에서부터 누적**하면 원래 배열이 나옵니다. 결과 배열의
칸 번호를 `i` 라 하면, `D` 의 칸 `0` 부터 `i` 까지 더한 값이 곧 인덱스 `i` 를 덮은 모든 갱신의
`v` 합이에요.

| `D` 의 칸 번호 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `D` 에 적힌 값 | -1 | 2 | 0 | 1 | -2 | 3 | 0 | -3 |
| 앞에서부터 누적 | -1 | 1 | 1 | 2 | 0 | 3 | 3 | 읽지 않는다 |

갱신 하나가 건드리는 칸이 구간 길이와 상관없이 **둘로 고정**됩니다. 그래서 전체 연산 수가
`O(N + Q)` 가 되고, 100 억이 30 만 언저리로 줄어들어요.

```text
구간을 통째로 고친다    갱신마다 최대 100,000 칸    합쳐서 100 억 번
경계 두 칸만 적는다     갱신마다 2 칸               기록 20 만 번 + 복원 10 만 번
```

더하는 값이 음수여도 같은 절차가 그대로 성립합니다. 시작 칸에 음수를 적고 취소 칸에서 그
음수를 빼면 되는데, 음수를 빼는 것은 결국 양수를 더하는 것이에요.

```text
갱신 (0,2,-1)     D[0] 에 -1 을 적는다         D[3] 에서 -1 을 뺀다 → +1 이 적힌다
누적이 지나가면   인덱스 0,1,2 가 -1 을 받고   인덱스 3 부터 그 -1 이 없어진다
```

갱신을 적용하는 순서도 결과를 바꾸지 않습니다. 칸마다 값을 더하기만 하니 순서를 바꿔 더해도
합이 같아요.

```text
(1,3,2)  의 D    [ 0   2   0   0  -2   0   0   0]
(0,2,-1) 의 D    [-1   0   0   1   0   0   0   0]
(5,6,3)  의 D    [ 0   0   0   0   0   3   0  -3]
----------------------------------------------------  칸마다 그냥 더한다
합               [-1   2   0   1  -2   3   0  -3]
```

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **누적합**이 무엇인지. 배열의 앞에서부터 `i` 개를 더한 값이고, 이 글에서는 차이를 적어 둔
  차이를 적어 둔 배열에서 원래 배열을 다시 만드는 데 씁니다. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 를 먼저 봅니다.
- **구간이 무엇인지.** 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 자리이고,
  양끝을 포함합니다.
- **배열의 칸을 읽고 쓰는 일이 한 번에 얼마나 드는지.** 인덱스로 바로 찾아가므로 칸 하나를
  읽거나 쓰는 데 드는 일이 배열 길이와 상관없습니다.
- 배열 인덱스가 `0` 부터 시작한다는 것과, 배열을 한 번 지나가는 `for` 루프.

「갱신을 전부 받은 뒤 배열을 한 번 본다」와 「갱신 사이사이에 값을 묻는다」는 다른 문제입니다.
뒤쪽은 [`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-problem.md) 이나
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-problem.md) 이 다루는 것이고,
이 글은 **마지막에 배열 전체를 한 번** 냅니다.

```text
갱신 Q 개 → (전부 끝난 뒤) 배열 전체를 한 번    ← 이 글이 다루는 것
갱신 → 조회 → 갱신 → 조회 → …                   ← 다른 자료구조가 다루는 것
```

### 아이디어 상세 — 경계 두 칸 기록을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[];
```

- 입력: 배열의 길이 `N` 과 갱신 목록 `updates`. 갱신 하나는 `[l, r, v]` 세 값입니다.
- 출력: 모든 갱신을 적용한 뒤의 길이 `N` 배열. 갱신이 없으면 모든 칸이 `0` 입니다.
- 제약: `1 ≤ N ≤ 100,000`, `0 ≤ Q ≤ 100,000`, `0 ≤ l ≤ r ≤ N−1`,
  `−10,000 ≤ v ≤ 10,000`. 시간 1 초, 메모리 256 MB.

이 글이 쓰는 기호는 아홉이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `N` | 결과 배열의 길이 | `1 ≤ N ≤ 100,000` |
| `Q` | 갱신의 개수 | `0 ≤ Q ≤ 100,000` |
| `l` · `r` | 한 갱신이 덮는 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ N−1` |
| `v` | 그 구간의 모든 칸에 더하는 값 | `−10,000` 이상 `10,000` 이하 |
| `i` | 결과 배열의 칸 번호 | `0 ≤ i ≤ N−1` |
| `j` | 차분 배열의 칸 번호 | `0 ≤ j ≤ N` |
| `A` | 결과 배열. 이 배열이 답이 됩니다 | 칸이 `N` 개 |
| `D` | 갱신을 경계 두 칸에만 적어 두는 차분 배열 | 칸이 `N+1` 개 |
| `running` | 복원 도중 `D[0]` 부터 `D[i]` 까지 더한 값 | 그 값이 곧 `A[i]` 입니다 |

기호 이름을 코드에서도 그대로 씁니다 — 결과 배열은 `A`, 차분 배열은 `D`, 누적 중인 값은
`running` 입니다.

가장 먼저 떠오르는 방법으로 시작합시다. 갱신을 받을 때마다 그 구간을 왼쪽에서 오른쪽으로
차례로 읽으며 칸마다 `v` 를 더하는 것이에요.

```ts
const A = new Array<number>(N).fill(0);
for (const [l, r, v] of updates) {
  for (let i = l; i <= r; i++) {
    A[i] = (A[i] as number) + v;   // 구간 안의 칸을 하나씩 고친다
  }
}
```

이 방법이 하는 일의 양은 **구간 길이의 합**입니다. 갱신 하나가 배열 전체를 덮으면 그 하나에
`N` 칸이 들고, 그런 갱신이 `Q` 개면 `N × Q` 가 돼요.

| `N = Q` | 칸을 고치는 횟수 `N × Q` | 초당 1 억 번 기준 |
| --- | --- | --- |
| 1,000 | 1,000,000 | 0.01 초 |
| 10,000 | 100,000,000 | 1 초 |
| **100,000** | **10,000,000,000** | **100 초** |

100 억 번입니다. 제약이 10 만인데 이 방법으로는 1 초 안에 못 끝냅니다. 그러면 이 100 억 안에서
무엇이 되풀이되는지 봅시다.

```text
N = 7 · 갱신 셋을 차례로 적용

  (1,3,2)  뒤    [ 0   2   2   2   0   0   0]    3 칸을 고쳤다
  (0,2,-1) 뒤    [-1   1   1   2   0   0   0]    3 칸을 고쳤다. 그중 둘은 방금 고친 칸이다
  (5,6,3)  뒤    [-1   1   1   2   0   3   3]    2 칸을 고쳤다
                  └ 인덱스 1 과 2 는 값이 두 번씩 바뀌었다
```

같은 칸을 여러 갱신이 다시 고치는 것이 확인됩니다. 그런데 칸 하나의 최종 값은 그 칸을 덮은
`v` 들의 합이라, 중간 값이 몇 번 바뀌었는지는 답과 상관이 없어요.

```text
인덱스 1 의 최종 값    (1,3,2) 의 +2 와 (0,2,-1) 의 -1 을 더한 것    2 + (-1) = 1
인덱스 5 의 최종 값    (5,6,3) 의 +3 하나                            3
인덱스 4 의 최종 값    덮은 갱신이 없다                              0
                       └ 중간 값을 만들지 않고 합만 알면 된다
```

이제 갱신 하나를 처리하는 데 실제로 몇 칸을 건드리는지 두 방식으로 세어 봅시다. 왼쪽은 구간을
차례로 읽는 방식이고, 오른쪽은 구간의 두 끝에만 값을 적는 방식이에요.

<!--proof:cost-two-ways-->

```text
갱신      덮는 칸 수  구간 순회가 건드린 칸  경계만 적을 때 건드린 칸
(1,3,2)            3                      3                         2
(0,2,-1)           3                      3                         2
(5,6,3)            2                      2                         2
합계               8                      8                         6

제약 규모 N = Q = 100,000 이고 모든 갱신이 배열 전체를 덮으면
  구간 순회      10,000,000,000 칸
  경계만 적기    200,000 칸
  └ 왼쪽은 구간 길이를 따라 늘고, 오른쪽은 갱신 개수만 따라 늘어난다
```

두 방식이 내는 배열은 같고 **오른쪽 열만 전부 2** 입니다. 여기서 관찰할 것은 그 하나예요 —
구간이 몇 칸이든 갱신 하나가 건드리는 칸이 2 로 고정됩니다.

| 갱신 | (1,3,2) | (0,2,-1) | (5,6,3) | 무엇을 따라가는가 |
| --- | --- | --- | --- | --- |
| 덮는 칸 수 | 3 | 3 | 2 | 구간 길이를 그대로 따라간다 |
| 경계만 적기 | 2 | 2 | 2 | 구간 길이와 상관없이 같다 |

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「구간의 시작 칸에만 `+v` 를
적어 두면 되지 않나」가 그것이에요. 그러면 갱신 하나가 칸 하나로 끝납니다.

<!--proof:cost-start-only-->

```text
입력                  정본이 낸 배열    시작 칸에만 적은 배열  어긋난 칸
N=7 · 전개 입력       [-1 1 1 2 0 3 3]  [-1 1 1 1 1 4 4]               4
N=5 · (0,2,3)         [3 3 3 0 0]       [3 3 3 3 3]                    2
N=4 · (0,3,5)         [5 5 5 5]         [5 5 5 5]                      0
N=6 · (1,2,4)(4,5,1)  [0 4 4 0 1 1]     [0 4 4 4 5 5]                  3

└ 셋째 줄은 구간이 배열의 마지막 칸까지 덮어서 어긋날 자리가 없다
```

첫 줄에서 네 칸이 어긋났습니다. 시작만 적으면 **구간이 끝나는 자리를 아무도 적어 두지
않아서**, 더한 값이 배열의 마지막 칸까지 그대로 이어지는 것이 원인이에요.

```text
(1,3,2) 를 시작 칸에만 적으면

  인덱스          0    1    2    3    4    5    6
  D 에 적힌 값    0   +2    0    0    0    0    0
  누적한 값       0    2    2    2    2    2    2
  원하는 값       0    2    2    2    0    0    0
                                      └ 인덱스 4 부터 어긋난다. 여기서 2 를 끝냈어야 한다
```

그러니 **구간이 끝난 다음 칸에서 그 값을 취소한다**는 것이 절차에 있어야 합니다. 여기서 진짜
개념이 나와요. **갱신 하나를 두 사건으로 바꿔 `D` 의 두 칸에만 적는 것**입니다.

```text
갱신 (l, r, v) 를 D 에 적는 규칙

  D[l]     에 v 를 더한다      인덱스 l 부터 v 가 있다
  D[r+1]   에서 v 를 뺀다      인덱스 r+1 부터 v 가 없다
           └ 칸이 둘뿐이고, l 과 r 이 얼마나 떨어져 있든 그대로 둘이다
```

개념이 정하는 것은 **각 값이 움직이는 범위**입니다. 기록 걸음이 건드리는 칸 번호는 `l` 과
`r+1` 둘이고, `r` 의 최댓값이 `N−1` 이라 `r+1` 의 최댓값이 `N` 이에요.

```text
갱신 하나가 건드리는 칸 수    2                구간 길이와 상관없다
건드리는 칸 번호 j 의 범위    0 부터 N 까지    r+1 의 최댓값이 (N−1)+1 = N 이다
복원이 읽는 칸 번호 j         0 부터 N−1 까지  마지막 칸 D[N] 은 읽지 않는다
                              └ D 의 칸이 N+1 개인 이유가 이 세 줄이다
```

**쉬운 경우와 불안한 경우를 나눠서 값으로 확인합시다.** 쉬운 경우는 갱신들이 서로 겹치지 않을
때예요. 각 칸이 갱신 하나에만 덮여서 누적이 한 번 올라갔다 한 번 내려옵니다.

```text
겹치지 않는 갱신 둘 — N = 6, (1,2,4) 와 (4,5,1)

  D 의 칸 번호    0    1    2    3    4    5    6
  D 에 적힌 값    0   +4    0   -4   +1    0   -1
  누적한 값       0    4    4    0    1    1
                                 └ 두 구간 사이의 칸에서 값이 0 으로 되돌아온다
                                                └ 칸 6 은 여분 칸이라 누적이 읽지 않는다
```

불안한 경우는 **구간이 서로 겹칠 때**입니다. 한 칸에 여러 갱신의 사건이 함께 걸리는 자리가
여기예요. 전개 입력의 `D` 를 갱신마다 나눠서 보면 겹침이 어디서 생기는지 확인됩니다.

```text
(1,3,2)  의 D    [ 0   2   0   0  -2   0   0   0]
(0,2,-1) 의 D    [-1   0   0   1   0   0   0   0]
(5,6,3)  의 D    [ 0   0   0   0   0   3   0  -3]
----------------------------------------------------  칸마다 그냥 더한다
합               [-1   2   0   1  -2   3   0  -3]
                              └ 칸 3 은 취소가 +1 로 적히고, 칸 4 는 취소만 걸린다
```

칸 하나에 여러 사건이 겹쳐도 **더하기만 하므로** 서로를 지우지 않습니다. 그래서 갱신을 적용한
순서가 결과를 바꾸지 않아요.

```text
순서를 바꿔 더해도 합이 같다
  (1,3,2) → (0,2,-1) → (5,6,3)      합 [-1   2   0   1  -2   3   0  -3]
  (5,6,3) → (0,2,-1) → (1,3,2)      합 [-1   2   0   1  -2   3   0  -3]
                                      └ 덧셈의 순서를 바꾼 것뿐이다
```

빠뜨리는 칸이 없다는 것은 복원 루프의 종료 조건으로 말할 수 있습니다. 루프는 `i` 를 `0` 부터
`N−1` 까지 하나씩 올리며 실행되고, 한 번 실행할 때마다 `D[i]` 를 **정확히 한 번** 더해요.

```text
루프가 끝난 시점
  더한 칸       D[0] D[1] … D[N−1]     N 개, 각각 정확히 한 번
  안 더한 칸    D[N]                   인덱스 N−1 보다 뒤의 이야기라 결과에 안 들어간다
                └ 결과 배열의 칸 N 개가 빠짐없이 한 번씩 정해진다
```

이제 「취소를 `r+1` 에 적는다」의 그 `+1` 이 정말 필요한지 값으로 확인합니다. 취소를 적는
자리를 `r + 0` · `r + 1` · `r + 2` 세 값으로 두고 같은 입력에서 결과를 냈어요.

<!--proof:cost-cancel-offset-->

```text
취소를 적는 칸  필요한 D 칸 수  낸 배열           어긋난 칸
r + 0                        7  [-1 1 2 0 0 3 0]          3
r + 1                        8  [-1 1 1 2 0 3 3]          0
r + 2                        9  [-1 1 1 1 2 3 3]          2

정본이 낸 배열   [-1 1 1 2 0 3 3]
└ 어긋난 칸이 0 인 것은 r + 1 하나다. r + 0 은 오른쪽 끝 칸을 빼먹고, r + 2 는 한 칸을 더 덮는다
```

`r + 0` 은 구간의 오른쪽 끝 칸이 자기 갱신을 못 받고, `r + 2` 는 구간 밖의 칸 하나가 값을 더
받습니다. 어긋난 칸이 0 인 것은 가운데 하나뿐이에요.

```text
얻은 절차 한 벌
  1. 칸이 N+1 개인 D 를 0 으로 채운다
  2. 갱신마다 D[l] 에 v 를 더하고 D[r+1] 에서 v 를 뺀다
  3. running 을 0 으로 두고 i 를 0 부터 N−1 까지 올리며 D[i] 를 더한다
  4. 그때그때의 running 을 A[i] 에 적는다
       └ 100 억 번이던 것이 기록 20 만 번과 복원 10 만 번이 된다
```

### 수행으로 알아보는 알고리즘 — 갱신 셋을 경계 여섯 칸에 적고 일곱 칸을 복원한다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const N = 7;
const updates: Array<[number, number, number]> = [
  [1, 3, 2],
  [0, 2, -1],
  [5, 6, 3],
];
// 이 절이 끝나면 [-1, 1, 1, 2, 0, 3, 3] 이 나와야 한다
```

왜 하필 이 갱신 셋일까요? 세 구간이 서로 겹쳐 한 칸에 사건이 여럿 걸리고, 더하는 값 하나가
음수라 취소가 덧셈이 되며, 마지막 갱신의 오른쪽 끝이 `N−1` 이라 **여분 칸 `D[7]` 에 적는
자리**가 실제로 실행되기 때문이에요. 어느 갱신도 덮지 않는 칸도 하나 있습니다.

```text
절차 전체를 한 장으로

  T1        칸이 N+1 개인 D 를 0 으로 채우고 running 을 0 으로 둔다
            갱신 목록을 왼쪽부터 하나씩 받으며:            ① 남은 갱신이 있는가
  T2~T4         D[l] 에 v 를 더한다                        ② 시작 이벤트
                D[r+1] 에서 v 를 뺀다                      ③ 취소 이벤트
  T5        남은 갱신이 없어 기록 루프를 벗어난다
            i 를 0 부터 N−1 까지 올리며:                   ④ 복원할 칸이 남았는가
  T6~T12        running 에 D[i] 를 더하고 A[i] 에 적는다
  T13       A 를 돌려준다
```

#### 1. 차분 배열을 만들고 갱신을 경계 두 칸에 적는다

첫 조각은 기록 루프입니다. 갱신을 받아 `D` 의 두 칸만 고치고, 결과 배열은 아직 만들지 않아요.

```ts
const D = new Array<number>(N + 1).fill(0);

for (const [l, r, v] of updates) {      // ① 남은 갱신이 있는가
  D[l] = (D[l] as number) + v;          // ② 시작 이벤트
  D[r + 1] = (D[r + 1] as number) - v;  // ③ 취소 이벤트
}
```

이 조각만 실행하면 갱신 셋이 `D` 를 이렇게 바꿉니다.

<!--proof:walk-record-->

```text
걸음  갱신      시작 이벤트  취소 이벤트  기록 뒤의 D
T2    (1,3,2)   D[1] += 2    D[4] -= 2    [0 2 0 0 -2 0 0 0]
T3    (0,2,-1)  D[0] += -1   D[3] -= -1   [-1 2 0 1 -2 0 0 0]
T4    (5,6,3)   D[5] += 3    D[7] -= 3    [-1 2 0 1 -2 3 0 -3]

└ 갱신 3 개가 경계 6 칸으로 압축됐고, 결과 배열은 아직 한 칸도 만들지 않았다
```

`①` 은 T2·T3·T4 에서 참이었고 T5 에서 처음 거짓이 됩니다. `②` 와 `③` 은 그 세 걸음에서 각각
한 번씩 실행돼 경계 여섯 칸을 채웠어요.

| `D` 의 칸 번호 | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 적힌 값 | -1 | 2 | 0 | 1 | -2 | 3 | 0 | -3 |
| 적은 걸음 | T3 | T2 | 없음 | T3 | T2 | T4 | 없음 | T4 |
| 어느 이벤트인가 | 시작 | 시작 | 없음 | 취소 | 취소 | 시작 | 없음 | 취소 |

`D[3]` 이 `+1` 인 것이 음수 갱신의 취소입니다. `(0,2,-1)` 의 취소는 `-1` 을 빼는 것이라 부호가
뒤집혀 `+1` 이 적혀요.

```text
v 가 양수일 때    D[r+1] -= 2     칸에 -2 가 쌓인다
v 가 음수일 때    D[r+1] -= -1    칸에 +1 이 쌓인다
                  └ 취소는 "그 값을 없앤다" 이지 "빼기" 가 아니다
```

#### 멈춤 — 취소를 r 에 적으면 구간의 오른쪽 끝 한 칸이 빠진다

여기서 헷갈리기 쉬운 포인트는 취소를 적는 칸 번호입니다. 「구간이 `r` 까지니까 `r` 에서
끝내면 되지 않나」로 읽기 쉬워요. 그 생각대로 한 글자만 바꿔 봅시다.

```ts
for (const [l, r, v] of updates) {
  D[l] = (D[l] as number) + v;
  D[r] = (D[r] as number) - v;   // r+1 이 아니라 r 에 적었다
}
```

이렇게 하면 누적이 인덱스 `r` 에 **도착하는 그 순간** `v` 가 취소됩니다. 정작 갱신 대상이어야
할 `r` 자신이 값을 못 받는 것이고, 다섯 입력으로 확인해 봅니다.

<!--proof:pause-cancel-at-r-->

```text
입력             정본이 낸 배열    취소를 r 에 적은 배열  어긋난 칸
N=7 · 전개 입력  [-1 1 1 2 0 3 3]  [-1 1 2 0 0 3 0]               3
N=5 · (2,2,7)    [0 0 7 0 0]       [0 0 0 0 0]                    1
N=4 · (0,3,5)    [5 5 5 5]         [5 5 5 0]                      1
N=3 · 갱신 없음  [0 0 0]           [0 0 0]                        0
N=3 · (0,2,0)    [0 0 0]           [0 0 0]                        0

└ 아래 두 줄은 더한 값이 없어서 어긋날 자리도 없다. 값을 더하는 갱신이 하나라도 있으면 오른쪽 끝 칸이 어긋난다
```

둘째 줄이 이 실수를 가장 짧게 보입니다. `(2,2,7)` 은 칸 하나짜리 갱신이라 시작과 취소가 같은
칸에 적히고, 그 자리에서 서로 지워져 갱신이 통째로 사라져요.

```text
(2,2,7) 을 D 에 적으면

  올바른 자리    D[2] += 7   D[3] -= 7    누적 0 0 7 0 0
  r 에 적으면    D[2] += 7   D[2] -= 7    누적 0 0 0 0 0
                             └ 같은 칸에서 서로 지워져 D 가 전부 0 이 된다
```

예외도 안 던져지고 배열 길이도 그대로라, 값을 대조하지 않으면 알아채기 어렵습니다. 고치는
방법은 취소를 **구간이 끝난 다음 칸**에 적는 것 하나예요.

```text
취소를 적는 칸이 정하는 것
  r    에 적는다    인덱스 r 이 값을 받기 전에 취소된다      구간의 마지막 칸이 빠진다
  r+1  에 적는다    인덱스 r 까지 받고 그다음부터 없어진다   구간의 칸만 정확히 받는다
       └ D 의 칸을 N+1 개로 잡는 이유도 여기에 있다
```

#### 2. 앞에서부터 누적해 결과 배열을 만든다

둘째 조각은 복원 루프입니다. `running` 에 `D[i]` 를 더하고, 그 값을 그대로 `A[i]` 에 적어요.

```ts
const A = new Array<number>(N);
let running = 0;
for (let i = 0; i < N; i++) {   // ④ 복원할 칸이 남았는가
  running += D[i] as number;
  A[i] = running;
}
```

`④` 는 `i` 가 `0` 부터 `6` 까지일 때 참이고 `7` 에서 처음 거짓이 됩니다. 이 조각을 앞 두 걸음만
실행하면 이렇게 나와요.

| 걸음 | `i` | `D[i]` | 더한 뒤의 `running` | `A[i]` |
| --- | --- | --- | --- | --- |
| T6 | 0 | -1 | -1 | -1 |
| T7 | 1 | 2 | 1 | 1 |

`running` 이 곧 `A[i]` 라는 것이 이 두 줄의 전부입니다. 앞 칸까지의 누적을 들고 있다가 이번
칸의 차이를 더하면 이번 칸의 값이 되는 것이에요.

```text
T7 이 하는 일
  들고 있던 값   running = -1     인덱스 0 까지의 누적이다
  더하는 값      D[1] = 2         인덱스 1 에서 시작하는 갱신의 값이다
  나오는 값      running = 1      A[1] 에 그대로 적는다
                 └ D[1] 이 "인덱스 0 과 1 의 값 차이" 라는 뜻이 여기서 확인된다
```

#### 멈춤 — 복원 루프의 두 줄 순서를 바꾸면 값이 한 칸씩 뒤로 옮겨진다

여기서 헷갈리기 쉬운 포인트는 루프 안 두 줄의 순서입니다. 「어차피 둘 다 이번 걸음에서 하는
일인데 순서가 중요할까」로 읽기 쉬워요. 순서를 바꿔 봅시다.

```ts
for (let i = 0; i < N; i++) {
  A[i] = running;               // 적기를 먼저 했다
  running += D[i] as number;
}
```

이렇게 하면 `A[i]` 에 **인덱스 `i−1` 까지의 누적**이 실립니다. 이번 칸의 차이를 아직 안 더한
값이라, 결과가 한 칸씩 뒤로 옮겨져요.

<!--proof:pause-write-first-->

```text
입력             길이    정본이 낸 배열    순서를 바꾼 배열  어긋난 칸
N=7 · 전개 입력  7 대 7  [-1 1 1 2 0 3 3]  [0 -1 1 1 2 0 3]          5
N=1 · (0,0,5)    1 대 1  [5]               [0]                       1
N=4 · (0,3,5)    4 대 4  [5 5 5 5]         [0 5 5 5]                 1
N=3 · 갱신 없음  3 대 3  [0 0 0]           [0 0 0]                   0

└ 길이는 네 줄 다 같다. 값이 한 칸씩 뒤로 옮겨지고 앞에 0 이 하나 들어간다
```

**길이가 네 줄 다 같다는 것**이 이 실수의 성격입니다. 배열 길이를 검사하는 테스트는 전부
통과하고, 값도 「본 적 있는 수」뿐이라 눈으로 대조해도 넘어가기 쉬워요.

```text
정본        -1    1    1    2    0    3    3
순서 바꿈    0   -1    1    1    2    0    3
             ↑    └ 정본의 값들이 한 칸씩 오른쪽으로 옮겨졌다
             └ 앞에 0 이 하나 들어가고, 정본의 마지막 3 이 잘린다
```

#### 3. 일곱 칸을 끝까지 복원해 결과를 낸다

두 조각을 하나로 이어 고정 입력에 실행하면 열세 걸음이 나옵니다. T1 은 준비, T2 부터 T4 까지가
기록, T5 는 기록 루프를 벗어나는 자리, T6 부터 T12 까지가 복원, T13 이 반환이에요.

<!--viz:restore-->

```text
기록이 끝난 D    [-1   2   0   1  -2   3   0  -3]
복원이 만든 A    [-1   1   1   2   0   3   3]
                  └ 위 줄의 앞 일곱 칸을 왼쪽부터 누적한 것이 아래 줄이다
```

걸음마다의 상태값을 펼치면 이렇게 나옵니다.

<!--proof:walk-trace-->

```text
걸음  i  D[i]  running  A 지금까지
T6    0    -1       -1  [-1]
T7    1     2        1  [-1 1]
T8    2     0        1  [-1 1 1]
T9    3     1        2  [-1 1 1 2]
T10   4    -2        0  [-1 1 1 2 0]
T11   5     3        3  [-1 1 1 2 0 3]
T12   6     0        3  [-1 1 1 2 0 3 3]

└ running 이 그대로 A[i] 이고, 마지막 줄 [-1 1 1 2 0 3 3] 가 반환값이다
```

<!--result:restore=[-1, 1, 1, 2, 0, 3, 3]-->

**네 갈래가 모두 실행됐습니다.** `①` 은 T2·T3·T4 에서 참이고 T5 에서 거짓이며, `②` 와 `③` 은
그 세 걸음에서 실행됐어요. `④` 는 T6 부터 T12 까지 참이고 T13 에서 거짓이 됩니다.

```text
①  남은 갱신이 있는가    T2 T3 T4 에서 참 · T5 에서 거짓
②  시작 이벤트          T2 T3 T4 에서 세 번
③  취소 이벤트          T2 T3 T4 에서 세 번
④  복원할 칸이 남았는가  T6~T12 에서 참 · T13 에서 거짓
                         └ 참과 거짓 양쪽이 다 실행됐다
```

각 칸의 값이 정말 그 칸을 덮은 갱신의 합인지 확인하고 갑니다. 왼쪽이 복원이 낸 값이고
오른쪽이 갱신 목록을 직접 읽어 더한 값이에요.

| 인덱스 | 복원이 낸 값 | 덮은 갱신 | 갱신의 `v` 합 |
| --- | --- | --- | --- |
| 0 | -1 | (0,2,-1) | -1 |
| 1 | 1 | (1,3,2) · (0,2,-1) | 2 + (-1) = 1 |
| 2 | 1 | (1,3,2) · (0,2,-1) | 2 + (-1) = 1 |
| 3 | 2 | (1,3,2) | 2 |
| 4 | 0 | 없음 | 0 |
| 5 | 3 | (5,6,3) | 3 |
| 6 | 3 | (5,6,3) | 3 |

#### 4. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `A` 를 그대로 돌려주는 마지막
한 줄뿐이에요 — 갱신 목록이 비면 기록 루프가 한 번도 실행되지 않아 `D` 가 전부 `0` 이고,
복원이 `0` 만 쌓아 모든 칸이 `0` 인 배열이 나옵니다.

```ts
export function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[] {
  // 갱신을 결과 배열에 바로 반영하지 않고 경계 두 칸에만 적어 두는 차분 배열.
  // 칸이 N+1 개인 것은 오른쪽 끝이 N−1 인 갱신이 마지막 칸에 취소를 적기 때문이다.
  const D = new Array<number>(N + 1).fill(0);

  for (const [l, r, v] of updates) {
    // ① 처리할 갱신이 남았는가 — 남아 있으면 아래 두 줄을 한 번 실행한다.
    // ② 시작 이벤트 — 인덱스 l 부터 v 가 더해진다.
    D[l] = (D[l] as number) + v;
    // ③ 취소 이벤트 — 인덱스 r+1 부터 그 v 가 없어진다.
    D[r + 1] = (D[r + 1] as number) - v;
  }

  const A = new Array<number>(N);
  let running = 0;
  for (let i = 0; i < N; i++) {
    // ④ 복원할 칸이 남았는가 — 앞에서부터 누적한 값이 인덱스 i 의 최종 값이다.
    running += D[i] as number;
    A[i] = running;
  }

  return A;
}
```

```text
diffArrayRangeUpdate(7, [[1,3,2], [0,2,-1], [5,6,3]])   →  [-1, 1, 1, 2, 0, 3, 3]
diffArrayRangeUpdate(5, [[0,2,3]])                      →  [3, 3, 3, 0, 0]
diffArrayRangeUpdate(4, [[0,3,5]])                      →  [5, 5, 5, 5]
diffArrayRangeUpdate(5, [[2,2,7]])                      →  [0, 0, 7, 0, 0]
diffArrayRangeUpdate(3, [])                             →  [0, 0, 0]
```

### 알아 두면 좋은 개념 — 이벤트 스위핑

이 절차가 갱신 하나에 한 일을 한 문장으로 줄이면 **「구간을 시작 사건과 끝 사건 두 개로
바꾸고, 좌표축을 한 번 지나가며 그 사건들을 누적한다」** 입니다. 이렇게 구간을 사건으로 바꿔
좌표축을 한 번에 처리하는 방식을 **이벤트 스위핑**이라고 부릅니다.

```text
구간 하나가 사건 둘이 된다

  [1,3] 에 2 를 더한다   →   인덱스 1 에서 시작   인덱스 4 에서 끝
                             └ T2 가 D[1] 과 D[4] 에 적은 것이 이 두 사건이다

좌표축을 왼쪽에서 오른쪽으로 한 번 지나가며 누적한다

  인덱스       0    1    2    3    4    5    6
  사건             +2             -2
  누적한 값    0    2    2    2    0    0    0
                    └ T7 부터 T10 까지가 이 줄을 만든 걸음이다
```

같은 모양이 다른 문제에서도 같은 이름으로 나옵니다. 바뀌는 것은 **사건에 무엇을 적는가**
하나예요.

| 문제 | 사건에 적는 것 | 좌표축을 지나며 하는 일 |
| --- | --- | --- |
| 이 문제 | 시작에 `+v`, 끝난 다음 칸에 `−v` | 누적한 값을 그대로 배열에 적는다 |
| 회의가 가장 많이 겹치는 시각 | 시작에 `+1`, 끝난 다음에 `−1` | 누적한 값의 최댓값을 찾는다 |
| 2 차원 구간 갱신 | 네 꼭짓점에 `+v` 와 `−v` 를 적는다 | 행으로 한 번, 열로 한 번 누적한다 |

세 줄의 차이는 **누적한 값을 무엇에 쓰는가**입니다. 배열을 그대로 돌려주면 이 문제가 되고,
최댓값만 보면 겹침을 세는 문제가 돼요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 두 배열의 관계를 식으로 어떻게
적는지, 무엇이 매 걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 갱신 대상이 **연속 구간**입니다. 인덱스를 골라 담는 집합이면 두 칸으로 줄일 수 없어요.
- 구간에 하는 일이 **덧셈으로 쌓이고 뺄셈으로 취소됩니다.** 더하기·빼기·배타적 논리합이
  그렇고, 「구간을 전부 5 로 덮어쓰기」는 아닙니다.
- 조회가 **갱신이 다 끝난 뒤에** 옵니다. 이 문제는 마지막에 배열 전체를 한 번 냅니다.
- 인덱스의 범위가 **배열로 잡을 수 있는 크기**입니다. `N ≤ 100,000` 이라 칸을 그대로 잡아요.

```text
네 조건이 코드의 모양을 그대로 정한다
  연속 구간          → 시작과 끝 두 칸으로 갱신이 표현된다
  덧셈과 뺄셈        → 여러 갱신의 사건이 한 칸에서 그냥 더해진다
  조회가 맨 끝에     → 누적을 한 번만 하면 된다
  인덱스가 배열 크기 → 사건을 그 자리에 바로 적는다. 정렬이 필요 없다
```

마지막 두 줄이 이 절차의 경계입니다. 조회가 갱신 사이에 섞이면 누적을 매번 다시 해야 하고,
인덱스 범위가 `10^9` 처럼 크면 배열을 잡을 수 없어요.

```text
조회가 맨 끝에 한 번        누적 한 번으로 끝난다              이 글의 절차
조회가 갱신 사이에 섞인다   조회마다 누적을 다시 해야 한다     펜윅 트리 쪽이 낫다
인덱스가 10^9 까지          배열을 못 잡는다                   좌표를 압축하고 정렬한다
                            └ 이 문제는 N ≤ 100,000 이라 첫 줄이다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "구간 [l, r] 에 v 를 더한다"  "범위에 일괄 적용"       ← 갱신이 구간 단위다
  "모든 갱신을 적용한 뒤"  "최종 상태를 출력하라"        ← 조회가 맨 끝에 한 번이다
  "갱신 순서는 결과에 영향을 주지 않는다"                ← 덧셈으로 쌓인다는 신호다
  "예약된 좌석 수"  "구간별 인원 증감"                   ← 시작과 끝이 있는 사건이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N × Q 가 못 들어간다
  인덱스가 배열로 잡을 수 있는 크기다

반대로 이런 말이 보이면 해당하지 않는다
  "갱신 중간에 값을 물어본다"  "질의가 섞여 들어온다"     ← 누적을 매번 다시 해야 한다
  "구간의 최댓값을 갱신한다"  "구간을 v 로 덮어쓴다"      ← 뺄셈으로 취소되지 않는다
  "인덱스가 10^9 까지"                                    ← 배열을 못 잡는다
```

두 번째 무리가 보이면 다른 절차로 갑니다. 갱신과 조회가 섞이면
[`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-problem.md) 쪽이고, 구간의 최솟값이나
최댓값을 다루면 [`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-problem.md)
쪽이에요.

#### 실제로 쓰이는 곳

- **NumPy 의 `numpy.diff` 와 `numpy.cumsum`** — 이 글이 쓰는 두 연산을 각각 함수 하나로
  제공합니다. 앞은 공식 문서가 *"Calculate the n-th discrete difference along the given axis"*
  로 적고, 뒤는 *"Return the cumulative sum of the elements along a given axis"* 로 적어요.
  두 페이지가 서로를 「See also」로 서로를 가리키고 있습니다.
  ([`numpy.diff`](https://numpy.org/doc/stable/reference/generated/numpy.diff.html) ·
  [`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-30)
- **LLVM libc++ 의 `std::partial_sum`** — 복원 루프와 글자 그대로 같은 모양입니다. 소스의
  중심 두 줄이 `__t = __t + *__first;` 와 `*__result = __t;` 인데, 이 글의
  `running += D[i]` 와 `A[i] = running` 이 그 둘이에요. 짝이 되는
  `std::adjacent_difference` 는 반대로 `*__result = __val - __acc;` 를 적습니다.
  ([`partial_sum.h`](https://github.com/llvm/llvm-project/blob/main/libcxx/include/__numeric/partial_sum.h) ·
  [`adjacent_difference.h`](https://github.com/llvm/llvm-project/blob/main/libcxx/include/__numeric/adjacent_difference.h),
  조회 2026-08-30)
- **Prometheus 의 카운터** — 공식 문서가 카운터를 *"a cumulative metric that represents a
  single monotonically increasing counter whose value can only increase or be reset to zero on
  restart"* 로 정의합니다. 저장되는 것은 누적값이고 구간의 증가량은 뒤에서 두 시점의 차이로
  만드는데, 이 글이 `D` 를 적어 두었다가 누적하는 것과 방향만 반대예요.
  ([Prometheus — Metric types](https://prometheus.io/docs/concepts/metric_types/),
  조회 2026-08-30)

```text
세 사례와 이 문제의 관계

  앞의 둘      차이와 누적을 각각 하나씩 제공한다. 구간 갱신을 두 사건으로 바꾸는 것은 쓰는 쪽의 몫이다
  Prometheus   누적을 먼저 저장하고 차이를 나중에 만든다. 이 글은 차이를 먼저 적고 누적을 나중에 한다
               └ 두 연산이 서로의 역이라는 것을 양쪽이 같이 보인다
```

**구간 갱신 전체를 하나의 이름으로 제공하는 표준 라이브러리는 찾지 못했습니다.** 주어지는 것은
차이와 누적 두 조각이고, 「구간을 두 사건으로 바꿔 그 자리에 적는다」는 그 둘을 잇는 쪽의
코드로 남아 있어요.

#### 경쟁 설계와의 대조

같은 목표(구간 갱신을 모아 두었다가 값을 읽기)를 노리는 다른 절차로 **펜윅 트리**(이진 인덱스
트리)에 같은 차이 값을 담는 방법이 있습니다. 칸 `j` 가 자기 아래 여러 칸의 차이 합을 들고
있어서, 갱신 하나가 `log N` 개의 칸을 고치고 값 하나를 묻는 것도 `log N` 개의 칸을 읽어요.

```text
같은 일에 두 설계가 드는 칸

  차분 배열   갱신은 칸 2 개, 값 하나를 묻는 것은 칸 0 부터 그 칸까지 전부
  펜윅 트리   갱신은 칸 log N 개, 값 하나를 묻는 것도 칸 log N 개
              └ 갱신은 차분 배열이 적고, 중간 조회는 펜윅 트리가 적다
                섞인 비율이 어느 쪽의 접근 수가 적은지를 정한다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은
`N = 1,024` 이고 갱신은 `Q = 1,024` 개인데, `k` 번째 갱신이 `l = (37k) mod N` 에서 시작해
`r = min(N−1, l + (k mod 64))` 에서 끝나고 `v = (k mod 7) + 1` 을 더합니다. `t` 번째 점 조회는
인덱스 `x = (91(t+1)) mod N` 의 지금 값을 묻고, 조회는 갱신 사이에 고르게 끼웠어요. 마지막에는
두 설계가 다 배열 전체를 만듭니다. **전개 입력을 그대로 쓰지 않은 이유**는 일곱
칸에서는 펜윅 트리가 한 번에 지나는 칸이 두세 개뿐이라 두 설계의 접근 수가 상수에 묻히기
때문입니다.

| 섞인 점 조회 | 차분 배열 | 펜윅 트리 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 0 회 | **7,169** | 30,214 | 차분 배열이 4.2 배 적습니다 |
| 44 회 | **29,719** | 30,437 | 차분 배열이 근소하게 적습니다 |
| 45 회 | 30,743 | **30,438** | **여기서 순서가 뒤집힙니다** |
| 1,024 회 | 531,969 | **35,335** | 펜윅 트리가 15 배 적습니다 |

**저장 칸은 둘 다 1,025 개로 같습니다.** 메모리에서는 갈리지 않아요 — 갈리는 것은 접근 수이고,
그 경계가 이 입력에서 **점 조회 45 회**입니다.

```text
경계가 그 자리인 이유

  점 조회 1,024 회를 더했을 때 늘어난 접근 수
    차분 배열   531,969 − 7,169 = 524,800     조회 하나당 평균 512.5
    펜윅 트리    35,335 − 30,214 = 5,121      조회 하나당 평균 5.0
  시작점의 차이  30,214 − 7,169 = 23,045
  23,045 ÷ (512.5 − 5.0) ≈ 45.4    → 실측에서 뒤집히는 자리가 45 회다
```

**이 절차가 내주는 것은 중간 조회입니다.** 갱신 도중에 값 하나를 물으면 칸 0 부터 그 칸까지
다시 더해야 해서, 조회 하나가 평균 512.5 번의 접근이 돼요. 그 대신 얻는 것이 셋입니다.

```text
차분 배열이 얻는 것
  갱신 비용   경계 두 칸만 고친다          펜윅은 갱신 하나에 칸 log N 개를 고친다
  전처리      0 으로 채우는 것뿐이다       7,169 대 30,214 로 접근 수가 4.2 배 적다
  구현        루프 두 개, 비트 연산 없음   펜윅은 j & -j 로 칸을 골라 다닌다
              └ 조회가 맨 끝에 한 번이라는 것이 이 문제의 제약이므로 첫 열이 이 문제의 답이다
```

문제가 「모든 갱신을 적용한 뒤의 배열」을 요구하니 이 문제에서는 차분 배열이 답입니다. 같은
지문에서 **갱신 사이에 값을 묻는 조회가 45 회 넘게 섞이는 순간** 이 판정은 다시 해야 해요.

### 수식 정의와 유도

갱신 목록을 집합으로 두고 차분 배열을 정의합니다. `U` 는 주어진 갱신 `(l, r, v)` 들의 모음이고,
`D` 의 칸 `j` 에는 그 칸에서 시작하는 갱신의 값을 더하고 그 칸에서 끝나는 갱신의 값을 뺍니다.

$$D[j] \;=\; \sum_{(l,r,v)\in U,\; l = j} v \;-\; \sum_{(l,r,v)\in U,\; r+1 = j} v \qquad (0 \le j \le N)$$

```text
정의를 값에 넣어 봅니다 — N = 7, U = {(1,3,2), (0,2,-1), (5,6,3)}

  D[0] =  (l = 0 인 갱신의 값 -1)  − (r+1 = 0 인 갱신 없음)     = -1
  D[3] =  (l = 3 인 갱신 없음)     − (r+1 = 3 인 갱신의 값 -1)  = +1
  D[4] =  (l = 4 인 갱신 없음)     − (r+1 = 4 인 갱신의 값 2)   = -2
  D[7] =  (l = 7 인 갱신 없음)     − (r+1 = 7 인 갱신의 값 3)   = -3
          └ 정의 하나가 칸 하나를 정하고, 그 칸에 걸린 갱신만 본다
```

결과 배열은 그 칸까지의 합으로 정의합니다. 앞에서부터 `i` 번 칸까지 더한 값이에요.

$$A[i] \;=\; \sum_{j=0}^{i} D[j] \qquad (0 \le i \le N-1)$$

```text
값으로 확인합니다 — 같은 입력의 D 는 [-1 2 0 1 -2 3 0 -3] 입니다

  A[0] = D[0]                             = -1
  A[3] = D[0] + D[1] + D[2] + D[3]        = -1 + 2 + 0 + 1 = 2
  A[4] = A[3] + D[4]                      = 2 + (-2) = 0
         └ 정의를 그대로 쓰면 매번 앞 칸을 다시 더하고, 직전 값에 한 칸만 더하면 한 번이다
```

두 정의를 이으면 `A[i]` 가 무엇인지 임의의 `N` 과 임의의 갱신 목록에서 나옵니다. 합의 순서를
바꿔 갱신 하나씩으로 묶는 것이 유도의 전부예요.

$$A[i] \;=\; \sum_{j=0}^{i}\left(\sum_{l=j} v - \sum_{r+1=j} v\right) \;=\; \sum_{(l,r,v)\in U} v\Bigl([\,l \le i\,] - [\,r+1 \le i\,]\Bigr)$$

```text
대괄호는 조건이 참이면 1, 거짓이면 0 을 뜻합니다

  왼쪽 항 [l ≤ i]      갱신의 시작 사건이 칸 0..i 안에 들어왔는가
  오른쪽 항 [r+1 ≤ i]  그 갱신의 취소 사건도 칸 0..i 안에 들어왔는가
                       └ 갱신 하나가 두 항으로 갈려 서로 지운다
```

두 항의 차이를 `i` 의 위치로 갈라 봅니다. `l ≤ r` 이 제약이므로 `l ≤ i` 이면서 `r+1 ≤ i` 가
아닌 자리가 정확히 구간 안이에요.

| `i` 의 위치 | `[l ≤ i]` | `[r+1 ≤ i]` | 두 항의 차이 |
| --- | --- | --- | --- |
| `i < l` | 0 | 0 | 0 |
| `l ≤ i ≤ r` | 1 | 0 | 1 |
| `i > r` | 1 | 1 | 0 |

세 줄이 겹치지도 빠지지도 않으므로 차이가 `[l ≤ i ≤ r]` 과 같습니다. 그래서 유도가 문제의
정의로 닫혀요.

$$A[i] \;=\; \sum_{(l,r,v)\in U} v\,[\,l \le i \le r\,] \;=\; \sum_{(l,r,v)\in U,\; l \le i \le r} v$$

```ts
// 위 정의를 그대로 옮긴 조각. 실제 절차는 이 합을 누적 하나로 대신한다.
const cellFromDefinition = (D: number[], i: number): number =>
  D.slice(0, i + 1).reduce((s, x) => s + x, 0);
```

이 조각은 칸 하나를 만드는 데 `i+1` 번을 더하므로 전부 더하면 `N(N+1)/2` 번입니다. 누적을 들고
가면 칸 하나가 덧셈 한 번이라 `N` 번이에요 — 같은 값을 만드는 두 방법의 차이가 그것입니다.

```text
칸 하나를 만드는 데 드는 덧셈
  정의를 그대로 쓴다    i+1 번    전부 더하면 N(N+1)/2 번
  누적을 들고 간다      1 번      전부 더하면 N 번
                        └ N = 100,000 이면 50 억 대 10 만이다
```

배열 접근 수도 두 절차에서 닫힌 형태로 나옵니다. 차분 배열은 초기화 `N+1` 번, 갱신마다 네 번,
복원마다 두 번이라 `3N + 4Q + 1` 이고, 구간 순회는 초기화 `N` 번에 덮는 칸마다 두 번이라 모든
갱신이 배열 전체를 덮을 때 `N + 2NQ` 예요.

<!--proof:math-scale-->


### 불변식 — running 은 D 의 앞 칸을 모두 더한 값이고 그것이 그 칸의 답이다

파트 1 에서 코드가 동작하는 것을 열세 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이
실제로 유지되는지 확인해 봅시다.

> 복원 루프가 칸 `i` 를 처리한 직후, `running` 은 `D[0]` 부터 `D[i]` 까지의 합이고, 그 값은
> 인덱스 `i` 를 덮은 모든 갱신의 `v` 를 더한 것과 같습니다.

```text
  running 이 더한 칸   D[0]  D[1]  …  D[i]
  아직 안 더한 칸      D[i+1]  …  D[N]

  running = D[0] + D[1] + … + D[i]                        ← 앞 문장
  그 합이 인덱스 i 를 덮은 모든 갱신의 v 를 더한 값이다   ← 뒤 문장
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 `running` 이 무엇인지 정하고, 뒤 문장이 **그 값을
그대로 `A[i]` 에 적어도 된다**는 것을 말해요. 둘 중 하나만 빠져도 복원 루프의 두 줄이 왜 그
모양인지 근거가 사라집니다.

**출발점부터 봅시다.** 루프에 들어가기 전 `running` 은 `0` 이고 더한 칸이 하나도 없습니다.
앞 문장의 「`D[0]` 부터 `D[i]` 까지」가 빈 범위라 합이 `0` 인 것이 맞아요.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | `running` 을 0 으로 둔다 | 더한 칸이 없어 합이 0 이다 | 아직 적은 칸이 없다 |
| `i = 0` | `D[0]` 을 더한다 | 합이 `D[0]` 하나가 된다 | 인덱스 0 에서 시작한 갱신만 들어 있다 |
| 임의의 `i` | `D[i]` 를 더한다 | 직전 걸음이 `D[i−1]` 까지 만들어 뒀다 | 인덱스 `i` 에서 시작·취소된 갱신이 반영된다 |
| 종료 | `i = N−1` 을 마친다 | `D[0]` 부터 `D[N−1]` 까지 전부 | 결과 배열의 칸이 전부 정해졌다 |

셋째 줄이 이 논증의 핵심입니다. `D[i]` 에 적힌 것은 「인덱스 `i` 에서 시작하는 갱신의 값」에서
「인덱스 `i` 에서 취소되는 갱신의 값」을 뺀 것이라, 그것을 더하면 덮는 갱신의 집합이 정확히
갱신됩니다.

| 갱신 `(l, r, v)` 와 칸 `i` 의 관계 | `D[i]` 에 걸리는 것 | `running` 에 미치는 영향 |
| --- | --- | --- |
| `i = l` (구간이 여기서 시작한다) | `+v` | 이 갱신이 합에 들어온다 |
| `l < i ≤ r` (구간 안쪽이다) | 없음 | 이미 들어와 있고 그대로 남는다 |
| `i = r + 1` (구간이 끝난 다음 칸이다) | `−v` | 이 갱신이 합에서 빠진다 |
| `i < l` 또는 `i > r + 1` | 없음 | 관계가 없다 |

`l ≤ r` 이 제약이므로 시작이 취소보다 반드시 먼저 옵니다. 그래서 「들어왔다가 빠진다」의 순서가
뒤집히는 입력이 없어요.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 갱신 목록이 빔 | 기록 루프가 한 번도 실행되지 않는다 | 모든 칸이 `0` |
| `N = 1`, 갱신 `(0,0,5)` | `D[0]` 에 `+5`, `D[1]` 에 `−5` | `[5]` |
| `l = r` 인 갱신 | 시작과 취소가 이웃한 두 칸에 적힌다 | 그 칸 하나만 값을 받는다 |
| `r = N−1` 인 갱신 | 취소가 `D[N]` 에 적히고 복원이 읽지 않는다 | 끝까지 값이 남는다 |
| 같은 구간을 여러 번 갱신 | 같은 두 칸에 값이 계속 더해진다 | `v` 들의 합이 실린다 |
| `v` 가 음수 | 취소 칸에서 음수를 빼 양수가 적힌다 | 음수가 그대로 반영된다 |
| `v = 0` 인 갱신 | 두 칸에 `0` 을 더한다 | 아무것도 바뀌지 않는다 |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 `running` 에 `D[i]` 를 **더하는** 그 한 줄이에요.
「어차피 `A[i]` 에 적을 값을 만드는 것이니 그 칸의 값을 옮기면 되지 않나」라는 생각으로 더하기를
대입으로 바꿔 봅니다.

```ts
for (let i = 0; i < N; i++) {
  running = D[i] as number;   // 더하지 않고 그 칸의 값을 그대로 옮겼다
  A[i] = running;
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-no-accumulate-->

```text
입력             정본이 낸 배열    누적하지 않은 배열  어긋난 칸
N=7 · 전개 입력  [-1 1 1 2 0 3 3]  [-1 2 0 1 -2 3 0]           5
N=5 · (2,2,7)    [0 0 7 0 0]       [0 0 7 -7 0]                1
N=1 · (0,0,5)    [5]               [5]                         0
N=3 · 갱신 없음  [0 0 0]           [0 0 0]                     0

└ 칸이 하나뿐이거나 갱신이 없으면 누적할 것이 없어서 답이 같다
```

첫 줄에서 결과가 `D` 그 자체가 됐습니다. 앞 문장이 깨지면 `running` 은 「앞 칸들의 합」이 아니라
「이번 칸의 차이」가 되고, 뒤 문장의 근거가 함께 사라져요.

```text
[0 0 7 -7 0] 이 뜻하는 것

  인덱스 3 의 값이 -7 이다                D[3] 에 적힌 취소 사건이 그대로 답으로 나왔다
  취소는 앞에서 더한 7 을 없애는 것인데   더할 7 이 없으니 -7 이 그대로 남는다
                                          └ 차이는 앞의 합이 있을 때만 뜻이 있다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — `D` 를 `0` 으로 채우는 것, 갱신을 경계 두 칸에 적는
것, 앞에서부터 누적해 `A` 를 채우는 것이에요. 전개의 값으로 확인하면 이렇게 나뉩니다.

| 무리 | 어느 걸음인가 | 걸음마다 배열 접근 | 이 입력에서 |
| --- | --- | --- | --- |
| 초기화 | T1 | `N+1` 번 쓰기 | 8 |
| 기록 | T2 · T3 · T4 | 4 번 (경계 두 칸을 읽고 쓴다) | 3 × 4 = 12 |
| 복원 | T6 부터 T12 | 2 번 (`D[i]` 읽기 · `A[i]` 쓰기) | 7 × 2 = 14 |

T5 와 T13 은 루프 조건이 거짓이 되는 자리라 배열을 건드리지 않습니다. 그래서 이 입력의 접근
수가 8 + 12 + 14 로 34 번이에요.

```text
총식 = 초기화 + 기록 + 복원
       └ N+1   └ 4Q   └ 2N

       배열 접근 = (N + 1) + 4Q + 2N = 3N + 4Q + 1
       N = 7, Q = 3 이면 21 + 12 + 1 = 34 로 위 표와 같다
```

**개수가 입력의 내용과 무관하게 정해집니다.** 구간이 길든 짧든, 갱신이 겹치든 안 겹치든 걸음
수가 같아요 — 갱신 하나가 항상 칸 두 개이고 복원이 항상 `N` 걸음이기 때문입니다.

```text
여기서 센 것은 배열의 읽기와 쓰기 전부다
  추가로 잡는 메모리   D 가 N+1 칸, A 가 N 칸
  줄이려면             A 를 따로 만들지 않고 D 자리에 덮어써도 된다
                       읽은 D[i] 는 그 뒤로 다시 안 읽으므로 안전하다
                       └ 접근 수는 그대로이고 칸 수만 2N+1 에서 N+1 로 준다
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (갱신이 없다) | `O(N + Q)` | `Θ(N)` — `Q = 0` 이라 `N` 만 남는다 |
| **평균적인 경우** (입력 분포와 무관하다) | `O(N + Q)` | `Θ(N + Q)` |
| **최악의 경우** (모든 갱신이 배열 전체를 덮는다) | `O(N + Q)` | `Θ(N + Q)` — 실제로 도달한다 |

가운데와 아래 줄이 같은 것이 이 절차의 성질입니다. 걸음 수가 `N` 과 `Q` 로 딱 고정이라 입력의
모양을 어떻게 바꿔도 값이 같아요.

```text
비교 대상과 나란히 놓으면 이 성질이 확인된다
  구간을 통째로 고친다   최선 N + 2Q 번         최악 N + 2NQ 번
  경계 두 칸만 적는다    최선 3N + 4Q + 1 번    최악 3N + 4Q + 1 번
                         └ 위쪽은 구간 길이에 달렸고 아래쪽은 아니다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 `D` 를 `0` 으로 채우는 것 하나뿐이라는
것이 이 절차의 특징이에요 — 정렬도, 좌표압축도, 트리 만들기도 하지 않습니다.

```text
총식 = Θ(N + Q) 시간 + Θ(N) 추가 메모리
       └ 초기화 N+1 · 기록 4Q · 복원 2N   └ D 가 N+1 칸, A 가 N 칸

N = Q = 100,000 이면 배열 접근이 정확히 700,001 번, 잡는 칸이 200,001 개다
```

**보장의 종류는 전부 최악 보장입니다.** 해시도, 무작위성도, 분할 상환도 쓰지 않아요 — 어떤
입력을 넣어도 접근 수가 `3N + 4Q + 1` 로 같습니다.

```text
기댓값이 끼어들 자리가 없다
  칸을 찾는 방법   인덱스로 바로 간다        해시 충돌이라는 개념이 없다
  걸음 수          입력을 안 보고 정해진다   분포를 가정할 필요가 없다
  갱신 하나의 값   항상 칸 2 개              평균이 아니라 상수다
                   └ 최악 보장과 평균 비용이 같은 수다
```

#### 최악을 만드는 입력

접근 수를 최대로 만드는 방법은 하나뿐입니다 — **`N` 과 `Q` 를 제약의 최댓값으로 두는 것**이에요.
구간의 길이는 접근 수를 바꾸지 못합니다. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->

```text
입력의 모양 (N = Q = 1,000)        덮는 칸의 합  구간 순회 접근 수  차분 배열 접근 수
갱신이 전부 배열 전체를 덮는다        1,000,000          2,001,000              7,001
갱신이 전부 칸 하나짜리다                 1,000              3,000              7,001
구간 길이가 1 부터 64 까지 섞인다        31,330             63,660              7,001

└ 왼쪽 두 열은 세 줄이 다 다르고, 오른쪽 열은 세 줄이 같다
```

**「구간이 길수록 비용이 크다」는 이 절차에서 거짓입니다.** 물려받은 통념이 여기서는 성립하지
않아요 — 첫 줄과 둘째 줄에서 덮는 칸이 100 만 대 1,000 인데 접근 수는 둘 다 7,001 입니다.
구간을 읽지 않고 두 끝만 적기 때문이에요.

```text
최악은 축마다 다른 입력이 만든다
  접근 수의 최악       N = Q = 100,000             입력의 모양과 무관하다. 700,001 번
  잡는 칸의 최악       N = 100,000                 D 가 100,001 칸, A 가 100,000 칸
  결과값 크기의 최악   (0,0,10000) 을 100,000 번   한 칸의 값이 1,000,000,000 이 된다
                       └ 앞의 둘은 N 과 Q 만 보고, 셋째만 v 를 본다
```

값의 크기가 최악이 되는 입력은 따로 만들어야 합니다. 모든 갱신이 같은 칸 하나를 덮고 `v` 가
최댓값이면 그 칸의 값이 제약 안에서 가장 커져요.

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 접근 수 | `N = Q = 100,000`, 구간 길이는 무엇이든 | 700,001 |
| 잡는 칸 | `N = 100,000` | 200,001 |
| 한 칸의 값 | `(0, 0, 10000)` 을 100,000 번 | 1,000,000,000 |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 구간을 통째로 고치던 것을 **시작과 취소 두
사건**으로 바꿨고, 취소를 `r+1` 에 적어야 구간의 오른쪽 끝이 값을 받으며, 앞에서부터 누적하면
각 칸이 자기를 덮은 갱신의 합이 됩니다.

```text
D 를 0 으로 채운다 → 갱신마다 D[l] 에 v 를 더하고 D[r+1] 에서 v 를 뺀다 → 앞에서부터 누적해 A 를 만든다
     └ 칸 N+1 개          └ 갱신 하나에 칸 2 개                              └ 칸마다 덧셈 한 번
```

먼저 답이 붙는 문제 하나입니다. 전개의 T4 는 `(5,6,3)` 을 기록한 걸음이었고, 오른쪽 끝이
`N−1 = 6` 이라 취소가 `D[7]` 에 적혔어요. 그런데 복원 루프는 `D[7]` 을 읽지 않습니다. 그러면
`D` 를 굳이 `N+1` 칸으로 잡을 이유가 있을까요?

```text
T4   (5,6,3)   D[5] += 3   D[7] -= 3   기록 뒤의 D  [-1 2 0 1 -2 3 0 -3]
                                                                      └ 이 칸을 아무도 읽지 않는다
```

<!--check:bufferCell-->
읽지 않아도 **적을 자리는 있어야 하기** 때문입니다. `D` 를 `N` 칸으로 잡으면 `r = N−1` 인 갱신이
`D[N]` 에 취소를 적으려다 배열 밖으로 나가요. 자바스크립트는 그 자리에서 예외를 던지지 않고
배열을 늘리지만, 그런 언어에서도 「없는 칸에 적었다」는 사실이 남습니다.

```text
D 의 칸 수를 N 으로 잡으면
  r = 6 인 갱신   D[7] 에 적으려 한다      칸 번호 7 은 길이 7 짜리 배열에 없다
  파이썬·자바     범위를 벗어난 접근이다   그 자리에서 예외가 난다
  자바스크립트    배열이 조용히 길어진다   버그가 다른 자리에서 나온다
                  └ 여분 칸 하나가 이 분기를 통째로 없앤다
```

값 자체는 버려도 됩니다. `D[N]` 이 뜻하는 것은 「인덱스 `N−1` 보다 뒤에서 일어날 일」이고, 결과
배열에는 그런 칸이 없어요.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「알아 두면 좋은 개념」            3 → 「경쟁 설계와의 대조」
  2 → 두 번째 「멈춤」
```
