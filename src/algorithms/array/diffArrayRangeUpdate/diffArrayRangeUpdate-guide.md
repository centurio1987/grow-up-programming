# 차분 배열 — 구간 전체를 고치지 않고 경계 두 칸만 적어 두는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 갱신마다 구간을
직접 고치는 방법에서 출발해 차분 배열의 두 칸만 적는 방법까지 가고, 그 방법을 단계마다 값으로 푼 뒤, 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

길이 `N` 인 배열이 처음에 모두 `0` 이고, 「인덱스 `l` 부터 `r` 까지 `v` 를 더하라」는 **구간 갱신**이 여러 개
들어옵니다. 갱신을 다 받은 뒤에 **최종 배열 하나**를 돌려주면 되고, 갱신 도중에는 아무도 값을 묻지 않아요.
이 조건 하나가 방법을 정합니다. 갱신마다 구간의 칸을 전부 고치면 일이 구간 길이만큼 생깁니다. 그런데 구간 갱신은 구간 안에서 **이웃한 두
칸의 차이**를 바꾸지 않아요. 차이가 바뀌는 곳은 구간이 시작하는 자리와 끝난 바로 다음 자리, 두 경계뿐입니다.
그래서 배열의 값 대신 **이웃한 두 칸의 차이**를 칸마다 적어 두면, 갱신 하나가 두 칸만 고치고 끝나요. 이
배열을 **차분 배열**(difference array)이라고 부르고 `D` 로 적습니다. 이 글은 끝까지 그 이름 하나로 부릅니다.

차분 배열의 칸 `j` 에는 **결과 배열 `A` 의 칸 `j` 가 바로 앞 칸보다 얼마나 큰지**가 들어 있습니다. 배열의 앞과
뒤에는 값 `0` 인 칸이 하나씩 있다고 보고 세기 때문에, 칸이 `A` 보다 하나 많아요. 일곱 칸짜리 `A` 위에서
갱신 하나와 갱신 셋을 차례로 그리면 이렇습니다.

<!--fig:concept-diff-->
![구간 갱신 하나가 결과 배열 A 의 세 칸을 바꾸는 동안 차분 배열 D 는 두 칸만 바뀌고, 갱신 셋을 적은 D 를 누적하면 A 가 된다](./figs/concept-diff.svg)

첫 장에서 괄호가 갱신이 덮는 구간이고, 진하게 칠한 두 칸이 차분 배열에서 바뀐 칸이에요. 구간 안의 칸
`A[2]` 와 `A[1]` 은 같이 올라가서 차이가 그대로이고, 차이가 바뀌는 곳은 구간이 시작하는 칸과 끝난 다음
칸뿐입니다. 둘째 장은 갱신 셋을 모두 적은 차분 배열이고, 그 칸을 **앞에서부터 누적**하면 윗줄의 `A` 가
다시 나와요.

그래서 절차는 둘로 나뉩니다. 갱신이 올 때마다 차분 배열의 두 칸만 고치고, 갱신이 끝나면 차분 배열을 한 번
앞에서부터 누적해 `A` 를 만들어요. 갱신 하나가 구간 길이와 상관없이 칸 두 개이고, 누적은 칸마다 덧셈 한
번입니다. 갱신이 `Q` 개면 연산이 `N + Q` 에 비례하고, 결과만 적으면 `O(N + Q)` 예요. 규모의 끝에서 두 방법이
건드리는 칸을 세면 이렇습니다.

<!--proof:concept-scale-->

```text
갱신마다 구간을 고친다  N = Q = 100,000 최악 10,000,000,000 칸  갱신 하나가 구간의 칸 수만큼
경계 두 칸만 적는다     기록 200,000 칸 + 누적 100,000 번       갱신 하나가 칸 2 개
```

여기에 조건 하나가 붙습니다. **갱신 도중에 값을 읽으면 이 방법의 이점이 사라져요.** 차분 배열에는 차이만
있어서, 칸 하나의 지금 값을 알려면 그 칸까지의 차이를 앞에서부터 다 더해야 합니다. 이 방법은 갱신을 다 받은
뒤에 배열을 한 번 읽는다는 조건에 기대고 있어요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **누적합 배열**이 무엇이고 어떻게 채우는지. 칸 `i` 에 앞 `i` 칸의 합을 담는 배열이고, 직전 칸에 원소 하나를
  더해 한 번에 채웁니다. 이 글은 차분 배열에서 결과 배열을 다시 만들 때 그 채우기를 그대로 씁니다. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 를 먼저 봅니다.
- **구간**이 무엇인지. 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 자리이고, 양끝을 포함합니다.
- **배열의 칸을 읽고 쓰는 일이 한 번에 얼마나 드는지.** 인덱스로 바로 찾아가므로 칸 하나를 읽거나 쓰는 데
  드는 일이 배열 길이와 상관없습니다.
- 배열 인덱스가 `0` 부터 시작한다는 것과, 배열을 한 번 지나가는 `for` 루프.

「갱신을 전부 받은 뒤 배열을 한 번 읽는다」와 「갱신 사이사이에 값을 묻는다」는 다른 과제입니다. 뒤쪽은
[`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-guide.md) 이나
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 이 다루는 것이고, 이 글은
**갱신이 모두 끝난 뒤 배열 전체를 한 번** 냅니다. 두 과제를 나란히 놓으면 이렇습니다.

| 과제 | 갱신과 읽기의 순서 | 다루는 글 |
| --- | --- | --- |
| 구간 갱신을 모두 적용한 최종 배열 | 갱신을 전부 받고 끝에 한 번 읽는다 | 이 글 |
| 구간 갱신과 값 조회가 섞인 과제 | 갱신 · 조회 · 갱신 · 조회가 번갈아 온다 | 펜윅 트리 · 세그먼트 트리 |

### 아이디어를 떠올리는 과정 — 갱신마다 구간 고치기에서 차분 배열까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 배열의 길이와 갱신 목록을 받아서,
갱신을 모두 적용한 최종 배열을 돌려줍니다.

```ts
function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[];
```

- 입력: 배열의 길이 `N` 과 갱신 목록 `updates`. 갱신 하나는 `[l, r, v]` 세 값이고, 인덱스 `l` 부터 `r` 까지
  **양끝을 포함해** `v` 를 더하라는 뜻입니다.
- 출력: 모든 칸이 `0` 인 배열에 갱신을 모두 적용한 길이 `N` 배열. 갱신이 없으면 모든 칸이 `0` 입니다.
- 규모: `N` 과 갱신 수 `Q` 가 각각 100,000 까지, 갱신은 `0 ≤ l ≤ r ≤ N−1`, 더하는 값은 −10,000 이상 10,000
  이하입니다. 비용은 흔한 채점 환경의 예산인 1 초 · 256 MB 에 대어 잽니다.

이 글이 쓰는 기호는 아홉이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 결과 배열의 길이 | `1 ≤ N ≤ 100,000` |
| `Q` | 갱신의 개수 | `0 ≤ Q ≤ 100,000` |
| `l` · `r` | 한 갱신이 덮는 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ N−1` |
| `v` | 그 구간의 모든 칸에 더하는 값 | `−10,000` 이상 `10,000` 이하 |
| `i` | 결과 배열의 칸 번호 | `0 ≤ i ≤ N−1` |
| `j` | 차분 배열의 칸 번호 | `0 ≤ j ≤ N` |
| `A` | 결과 배열. 이 배열이 답이 됩니다 | 칸이 `N` 개 |
| `D` | 차분 배열 — 칸 `j` 에 `A[j]` 가 앞 칸보다 얼마나 큰지를 담습니다 | 칸이 `N+1` 개 |
| `running` | 복원 도중 `D[0]` 부터 `D[i]` 까지 더한 값 | 그 값이 곧 `A[i]` 입니다 |

가장 먼저 떠오르는 방법은 갱신이 올 때마다 그 구간을 왼쪽부터 차례로 읽으며 칸마다 `v` 를 더하는 것이에요.

```ts
const A = new Array<number>(N).fill(0);
for (const [l, r, v] of updates) {
  for (let i = l; i <= r; i++) {
    A[i] = (A[i] as number) + v; // 구간 안의 칸을 하나씩 고친다
  }
}
```

이 방법은 답을 틀리지 않습니다. 비용은 **갱신마다 고치는 칸 수의 합**이고, 모든 갱신이 배열 전체를 덮는
입력을 넣으면 갱신마다 `N` 칸을 고쳐요.

<!--proof:origin-cost-->

| N = Q | 고친 칸 수의 합 | 초당 1 억 번 기준 | 구한 방법 |
| ---: | ---: | ---: | --- |
| 1,000 | 1,000,000 | 0.01 초 | 실행해서 셌다 |
| 10,000 | 100,000,000 | 1 초 | 실행해서 셌다 |
| 100,000 | 10,000,000,000 | 100 초 | N·Q 로 냈다 |

모든 갱신이 배열 전체를 덮는 입력입니다. 실행해서 센 N = 1,000 · 10,000 에서 고친 칸 수가 N·Q 와 정확히 같았습니다.
<!--/proof-->

`N` 과 `Q` 가 상한 100,000 이면 칸을 100 억 번 고치고, 초당 1 억 번으로 잡아도 100 초입니다. 예산 1 초의
백 배예요. 그 100 억 안에 같은 일을 몇 번이나 되풀이하는지 보려고, 일곱 칸짜리 배열에 갱신 셋
`(1,3,2) · (0,2,-1) · (5,6,3)` 을 차례로 걸고 갱신마다 고친 뒤의 배열을 적었습니다.

<!--proof:origin-repeat-->

| 갱신 | 고친 칸 | 고친 뒤의 배열 | 다시 고친 칸 |
| --- | ---: | --- | ---: |
| (1,3,2) | 3 | [0 2 2 2 0 0 0] | 0 |
| (0,2,-1) | 3 | [-1 1 1 2 0 0 0] | 2 |
| (5,6,3) | 2 | [-1 1 1 2 0 3 3] | 0 |

둘째 갱신이 고친 세 칸 중 두 칸은 첫 갱신이 이미 고친 칸입니다. 그런데 칸 하나의 **최종 값**은 그 칸을
덮은 갱신의 `v` 를 더한 것뿐이라, 중간에 몇 번 바뀌었는지는 답과 상관이 없어요. 칸마다 확인하면 이렇습니다.

<!--proof:origin-final-->

| 인덱스 | 고친 횟수 | 덮은 갱신 | 최종 값 |
| ---: | ---: | --- | --- |
| 0 | 1 | (0,2,-1) | -1 |
| 1 | 2 | (1,3,2) · (0,2,-1) | 2 + (-1) = 1 |
| 2 | 2 | (1,3,2) · (0,2,-1) | 2 + (-1) = 1 |
| 3 | 1 | (1,3,2) | 2 |
| 4 | 0 | 없음 | 0 |
| 5 | 1 | (5,6,3) | 3 |
| 6 | 1 | (5,6,3) | 3 |

7 칸 모두 최종 값이 덮은 갱신의 v 를 더한 값과 같습니다. 가장 많이 고친 칸은 2 번 고쳤습니다.
<!--/proof-->

중간 값을 만들 필요가 없다면, 갱신 하나를 처리할 때 **정말 건드려야 하는 칸**이 몇 개인지가 문제입니다. 같은
갱신 셋을 두 방식으로 처리해 건드린 칸을 셌어요. 하나는 구간을 차례로 고치는 방식이고, 다른 하나는 구간의
두 경계에만 값을 적어 두고 끝에 한 번 누적하는 방식입니다.

<!--proof:cost-two-ways-->

| 갱신 | 덮는 칸 수 | 구간을 고칠 때 건드린 칸 | 경계만 적을 때 건드린 칸 |
| --- | ---: | ---: | ---: |
| (1,3,2) | 3 | 3 | 2 |
| (0,2,-1) | 3 | 3 | 2 |
| (5,6,3) | 2 | 2 | 2 |

구간을 고치면 8 칸, 경계만 적으면 6 칸입니다. 두 방식이 낸 배열은 같습니다.
<!--/proof-->

여기서 관찰할 것은 **오른쪽 열이 전부 2** 라는 것 하나예요. 경계만 적는 방식에서 갱신 하나의 비용은 구간
길이와 상관이 없습니다. 그 관찰을 이름으로 세우기 전에 더 단순한 후보부터 시험해 봅시다. 「구간의 시작 칸에만
`+v` 를 적어 두고 끝에 누적하면 되지 않나」가 그것이에요. 그러면 갱신 하나가 칸 하나로 끝납니다. 정본에서
취소를 적는 줄 하나를 지운 코드를 만들어 네 입력에 걸었습니다.

<!--proof:cost-start-only-->

| 입력 | 정본이 낸 배열 | 시작 칸에만 적은 배열 | 어긋난 칸 |
| --- | --- | --- | ---: |
| N=7 · 전개 입력 | [-1 1 1 2 0 3 3] | [-1 1 1 1 1 4 4] | 4 |
| N=5 · (0,2,3) | [3 3 3 0 0] | [3 3 3 3 3] | 2 |
| N=4 · (0,3,5) | [5 5 5 5] | [5 5 5 5] | 0 |
| N=6 · (1,2,4)(4,5,1) | [0 4 4 0 1 1] | [0 4 4 4 5 5] | 3 |

어긋난 칸이 0 인 입력은 N=4 · (0,3,5) 하나입니다. 구간이 배열의 마지막 칸까지 덮어서 어긋날 자리가 없습니다.
<!--/proof-->

전개 입력에서 네 칸이 어긋났습니다. 갱신 `(1,3,2)` 하나만 걸어서 어디서부터 어긋나는지 확인해 봅시다.

<!--proof:origin-start-trace-->

```text
인덱스                      0  1  2  3  4  5  6
시작 칸에만 적고 누적한 값  0  2  2  2  2  2  2
정본이 낸 값                0  2  2  2  0  0  0
└ 인덱스 4 부터 어긋난다. 구간이 끝난 칸 3 다음에서 2 를 끝냈어야 한다
```

시작만 적으면 **구간이 끝나는 자리를 아무도 적어 두지 않아서**, 더한 값이 배열의 마지막 칸까지 그대로
이어집니다. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

구간을 고치는 방법은 시간이 모자랐고, 시작 칸에만 적는 방법은 끝을 적지 않아 답이 틀렸습니다. 끝난 다음 칸에
그 값을 **취소하는 기록**을 하나 더 두면 갱신 하나가 칸 두 개로 끝나고 답도 맞아요. 이렇게 경계 두 칸에 적힌
값을 모은 배열에 붙은 이름이 **차분 배열**입니다. 차분 배열이 무엇을 담고, 어떻게 채우고, 어떻게 다시 결과
배열이 되는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 차분 배열

이 아이디어를 한 문장으로 줄이면 이렇습니다. **갱신 `(l, r, v)` 마다 차분 배열 `D` 의 칸 `l` 에 `v` 를 더하고
칸 `r+1` 에서 `v` 를 뺀 뒤, 갱신이 끝나면 `D` 를 앞에서부터 누적해 결과 배열 `A` 를 만듭니다.** 실현 순서대로
나누면 단계가 셋이고, 첫 단계는 갱신 전에 한 번, 둘째는 갱신마다, 셋째는 갱신이 끝난 뒤 한 번 합니다.

| 단계 | 언제 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 1단계 차분 배열 잡기 | 갱신 전에 한 번 | `N + 1` 칸을 잡고 모두 `0` 으로 채운다 | — |
| 2단계 경계 두 칸에 적기 | 갱신마다 | `D[l]` 에 `v` 를 더하고 `D[r+1]` 에서 `v` 를 뺀다 | 1단계가 잡은 `N + 1` 칸 |
| 3단계 누적해 결과 배열 만들기 | 갱신이 끝난 뒤 한 번 | `running` 에 `D[i]` 를 더해 `A[i]` 에 적는다 | 2단계가 적은 차분 배열 |

#### 먼저 알아 둘 개념 — 차분 배열

단계로 들어가기 전에, 차분 배열이 어떻게 생겼고 어떻게 읽는지를 먼저 잡고 갑니다. 차분 배열의 칸에는 값이
아니라 **값의 차이**가 들어 있어서, 칸 하나를 보고 그것이 결과 배열의 어느 칸에 어떻게 작용하는지 떠올리지
못하면 뒤의 `r + 1` 이 왜 그 자리인지 따라가기 어렵기 때문이에요.

##### 쉬운 말 정의

차분 배열은 **결과 배열의 이웃한 두 칸이 얼마나 차이 나는지를 칸마다 적은 배열**입니다. 칸 `j` 는 칸 `j−1`
에서 칸 `j` 로 넘어갈 때 값이 얼마나 오르거나 내리는지를 맡아요. `A` 의 앞과 뒤에 값 `0` 인 칸이 하나씩 있다고
보고, 식으로 적으면 `D[0] = A[0]`, `D[j] = A[j] − A[j−1]`(`1 ≤ j ≤ N−1`), `D[N] = 0 − A[N−1]` 입니다.

##### 입력 위에 놓은 그림

칸 `D[j]` 의 값은 결과 배열의 칸 `j` 에서 오른쪽 끝까지 **모든 칸에** 더해집니다. 칸 `j` 에서 값이 오르면 그
뒤의 칸도 모두 그만큼 오른 자리에서 출발하기 때문이에요. 0 이 아닌 칸마다 그 값이 더해지는 자리를 괄호로
그리면 이렇습니다.

<!--fig:build-cover-->
![차분 배열의 칸마다 값이 더해지는 자리 — D[j] 는 칸 j 부터 끝까지](./figs/build-cover.svg)

실선 괄호는 값이 오르는 칸, 대시 괄호는 내리는 칸입니다. 결과 배열의 칸 하나에는 **그 칸 위에 걸친 괄호의
값이 모두 더해져요.** 칸 4 에는 `D[0]` · `D[1]` · `D[3]` · `D[4]` 네 괄호가 걸쳐 있고, 그 넷을 더한 것이 윗줄의
`A[4]` 입니다.

##### 칸 하나를 읽는 법

칸 하나를 골라 이름에서 뜻까지 따라가 봅시다. `D[4]` 는 칸 3 에서 칸 4 로 넘어갈 때의 변화입니다.

<!--proof:build-read-one-->

```text
D[4]  →  A[4] − A[3]  →  0 − 2  →  -2  →  인덱스 4 에서 값이 2 내려간다
```

##### 이웃한 칸끼리의 관계

차분 배열을 앞에서부터 더하면 결과 배열이 다시 나옵니다. 칸 `j` 까지 더하면 칸 0 에서 칸 `j` 까지의 변화가
모두 쌓여 `A[j]` 가 되기 때문이에요. 여덟 칸을 모두 확인했습니다.

<!--proof:build-neighbors-->

| j | A[j−1] | A[j] | D[j] = A[j] − A[j−1] | D[0] 부터 D[j] 까지의 합 |
| ---: | --- | --- | ---: | ---: |
| 0 | 0 (앞 칸 없음) | -1 | -1 | -1 |
| 1 | -1 | 1 | 2 | 1 |
| 2 | 1 | 1 | 0 | 1 |
| 3 | 1 | 2 | 1 | 2 |
| 4 | 2 | 0 | -2 | 0 |
| 5 | 0 | 3 | 3 | 3 |
| 6 | 3 | 3 | 0 | 3 |
| 7 | 3 | 0 (뒤 칸 없음) | -3 | 0 |

8 칸 모두 앞에서부터의 합이 A[j] 와 같고, 마지막 칸 j = 7 에서 합이 0 으로 돌아옵니다.
<!--/proof-->

마지막 칸 `D[N]` 은 결과 배열의 끝에서 뒤의 `0` 칸으로 내려오는 변화라, 모든 칸을 더하면 늘 0 으로 돌아옵니다.
이 관계를 거꾸로 읽으면 결과 배열을 다시 만드는 규칙이 돼요. `A[i]` 는 `A[i−1]` 에 `D[i]` 하나를 더한
값입니다. 누적합 배열을 채울 때와 같은 규칙이에요.

##### 헷갈리기 쉬운 모양 — 누적합 배열

누적합 배열을 알고 이 글에 온 독자는 「앞에서부터의 합을 적어 두면 되지 않나」를 먼저 떠올리기 쉽습니다. 누적합
배열은 **앞 칸들의 합**을, 차분 배열은 **이웃 칸의 차이**를 담으니 방향이 반대예요. 전개 입력 위에 갱신
하나를 더 걸고, 결과 배열 · 누적합 배열 · 차분 배열에서 각각 몇 칸이 바뀌는지 셌습니다.

<!--proof:build-vs-prefix-->

| 배열 | 칸 수 | 갱신 전 | 갱신 뒤 | 바뀐 칸 수 | 바뀐 칸 |
| --- | ---: | --- | --- | ---: | --- |
| 결과 배열 A | 7 | [-1 1 1 2 0 3 3] | [-1 1 6 7 5 3 3] | 3 | 2 3 4 |
| 누적합 배열 P | 8 | [0 -1 0 1 3 3 6 9] | [0 -1 0 6 13 18 21 24] | 5 | 3 4 5 6 7 |
| 차분 배열 D | 8 | [-1 2 0 1 -2 3 0 -3] | [-1 2 5 1 -2 -2 0 -3] | 2 | 2 5 |

전개 입력 위에 갱신 (2,4,5) 하나를 더 걸었습니다. 이 갱신이 덮는 칸은 3 개입니다.
<!--/proof-->

누적합 배열은 구간이 시작하는 자리부터 **뒤쪽 칸이 전부** 바뀌고, 차분 배열은 두 칸만 바뀝니다. 누적합 배열은
구간 **합을 묻는 질의**를 두 칸으로 줄이고, 차분 배열은 구간 **갱신**을 두 칸으로 줄여요. 하려는 일이 다르니
담는 것도 다릅니다.

##### 이렇게 생긴 까닭

구간 갱신은 구간 안의 칸을 **모두 같은 만큼** 올립니다. 그래서 구간 안에서 이웃한 두 칸의 차이는 그대로이고,
차이가 바뀌는 곳은 구간 밖에서 구간 안으로 들어가는 경계와 구간 안에서 밖으로 나오는 경계, 둘뿐이에요. 차이를
저장하면 갱신이 그 두 경계만 건드립니다.

칸이 `N + 1` 개인 것은 경계가 올 수 있는 자리가 그만큼이기 때문입니다. 들어가는 경계 `l` 은 0 부터 `N−1` 까지,
나오는 경계 `r+1` 은 1 부터 `N` 까지 올 수 있어요.

```text
적는 칸     l 은 0 … N−1       r+1 은 1 … N
합치면      0 … N              N + 1 칸
            └ 구간의 두 끝이 배열 어디든 올 수 있어서, 모든 경계 자리에 칸이 하나씩 있어야 한다
```

#### 1단계 — 차분 배열의 크기와 처음 값 정하기

앞 절의 모양 그대로 `N + 1` 칸을 잡고 모두 `0` 으로 채웁니다. 처음의 결과 배열은 모든 칸이 `0` 이라 이웃한 두
칸의 차이도 모두 `0` 이에요. 그러니 `0` 으로 채운 차분 배열이 곧 **처음 상태의 차분 배열**이고, 이 단계는
따로 계산할 것이 없습니다. 각 상태의 크기와 범위를 적으면 이렇습니다.

<!--proof:build-size-->

```text
칸 수           N + 1                전개 입력은 N = 7 이라 칸 8 개 · N = 100,000 이면 칸 100,001 개
메모리          (N + 1) × 8 바이트   N = 100,000 이면 800,008 바이트 — 256 MB 의 0.30 %
칸 하나의 범위  |D[j]| ≤ Q × 10,000  Q = 100,000 이면 1,000,000,000 이하 — 2^31 − 1 = 2,147,483,647 보다 작다
```

칸 하나에는 갱신마다 `v` 가 더해지거나 빠지므로, 절댓값이 `Q × 10,000` 을 넘지 않아요. 과제 규모의 끝에서도
32 비트 정수 범위 안이고, 메모리는 예산의 1 % 도 쓰지 않습니다. 결과 배열의 칸도 덮은 갱신의 `v` 를 더한
것이라 같은 범위 안에 있어요.

#### 2단계 — 갱신마다 경계 두 칸에 적기

갱신 `(l, r, v)` 가 오면 `D[l]` 에 `v` 를 더하고 `D[r+1]` 에서 `v` 를 뺍니다. 앞은 「칸 `l` 부터 값이 `v` 만큼
오른다」이고 뒤는 「칸 `r+1` 부터 그 `v` 가 없어진다」예요. 이 글은 앞을 **시작 이벤트**, 뒤를 **취소
이벤트**라고 부릅니다.

가장 쉬운 경우는 갱신들이 서로 겹치지 않을 때예요. 각 칸이 갱신 하나에만 덮여서, 누적이 한 번 올라갔다가 한 번
내려옵니다.

<!--proof:build-easy-->

```text
D 의 칸 번호  0  1  2  3   4  5  6
D 에 적힌 값  0  4  0  -4  1  0  -1
누적한 값     0  4  4  0   1  1  읽지 않음
└ 두 구간 사이의 칸 3 에서 값이 0 으로 되돌아온다. 칸 6 은 여분 칸이라 누적이 읽지 않는다
```

불안한 경우는 **구간이 서로 겹칠 때**입니다. 한 칸에 여러 갱신의 사건이 함께 걸리는 자리가 여기예요. 전개
입력의 갱신 셋이 저마다 적는 두 칸을 따로 그리고, 칸마다 더한 차분 배열을 맨 아래에 놓으면 이렇습니다.

<!--fig:build-overlap-->
![갱신 셋이 저마다 적은 두 칸과, 그것을 칸마다 더한 차분 배열](./figs/build-overlap.svg)

둘째 갱신 `(0,2,-1)` 은 `v` 가 음수라 취소 이벤트가 `−(−1)`, 곧 `+1` 로 적힙니다. 셋째 갱신은 오른쪽 끝이
`N−1` 이라 취소가 여분 칸 `D[7]` 에 적혀요. 한 칸에 여러 사건이 걸려도 **더하기만 하므로** 서로를 지우지
않고, 그래서 갱신을 적는 순서가 결과를 바꾸지 않습니다. 순서를 셋으로 바꿔 적어 보았습니다.

<!--proof:build-order-->

```text
(1,3,2) → (0,2,-1) → (5,6,3)  D [-1 2 0 1 -2 3 0 -3]
(5,6,3) → (0,2,-1) → (1,3,2)  D [-1 2 0 1 -2 3 0 -3]
(0,2,-1) → (5,6,3) → (1,3,2)  D [-1 2 0 1 -2 3 0 -3]
└ 세 순서의 D 가 모두 같다. 칸마다 더하기만 하므로 더하는 순서가 합을 바꾸지 않는다
```

빠뜨리는 갱신이 없다는 것은 기록 반복의 모양으로 말할 수 있습니다. 반복은 갱신 목록을 앞에서부터 하나씩 받고,
받을 때마다 두 줄을 **정확히 한 번** 실행해요. 목록이 끝나면 반복이 끝나므로, 갱신 `Q` 개가 모두 한 번씩 두
칸을 남깁니다.

#### 3단계 — 앞에서부터 누적해 결과 배열 만들기

갱신이 끝나면 `running` 을 `0` 으로 두고, `i` 를 `0` 부터 `N−1` 까지 올리며 `D[i]` 를 더해 그 값을 `A[i]` 에
적습니다. 「이웃한 칸끼리의 관계」에서 본 대로 `D[0]` 부터 `D[i]` 까지의 합이 `A[i]` 이기 때문이에요. 이 누적이
정말 **그 칸을 덮은 갱신의 `v` 합**인지, 전개 입력의 일곱 칸을 갱신 목록과 직접 대조했습니다.

<!--proof:build-restore-->

| i | D[i] | running | 덮은 갱신 | 덮은 갱신의 v 합 |
| ---: | ---: | ---: | --- | ---: |
| 0 | -1 | -1 | (0,2,-1) | -1 |
| 1 | 2 | 1 | (1,3,2) · (0,2,-1) | 1 |
| 2 | 0 | 1 | (1,3,2) · (0,2,-1) | 1 |
| 3 | 1 | 2 | (1,3,2) | 2 |
| 4 | -2 | 0 | 없음 | 0 |
| 5 | 3 | 3 | (5,6,3) | 3 |
| 6 | 0 | 3 | (5,6,3) | 3 |

7 칸 중 7 칸에서 running 이 그 칸을 덮은 갱신의 v 합과 같습니다.
<!--/proof-->

빠뜨리는 칸이 없는 근거는 복원 반복의 종료 조건이에요. 반복은 `i` 를 `0` 부터 `N−1` 까지 하나씩 올리고, 한
번마다 `D[i]` 를 **정확히 한 번** 더한 뒤 `A[i]` 를 **정확히 한 번** 씁니다. 그러니 결과 배열의 칸 `N` 개가
빠짐없이 한 번씩 정해져요. 마지막 칸 `D[N]` 은 더하지 않는데, 그 칸이 맡는 것은 결과 배열 뒤의 `0` 칸으로
내려오는 변화라 결과 배열에 들어갈 자리가 없습니다.

#### 이 방법이 기대는 전제

차분 배열은 아래 두 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 갱신이 덧셈으로 쌓이고 뺄셈으로 취소된다 | 2단계가 두 칸에 `+v` 와 `−v` 를 적고, 3단계가 그것을 더한다 | 구간을 한 값으로 덮어쓰는 갱신은 두 칸으로 적을 수 없다 |
| 값을 읽는 것은 갱신이 끝난 뒤 한 번이다 | 3단계의 누적을 한 번만 한다 | 갱신 도중 값을 읽을 때마다 그 칸까지 다시 더해야 한다 |

덮어쓰기가 안 되는 이유를 값으로 확인해요. 「구간을 `v` 로 덮어쓴다」를 두 번 한 결과와, 같은 두 갱신을 차분
배열에 더하기로 적은 결과를 나란히 놓았습니다.

<!--proof:premise-assign-->

```text
덮어쓴 결과                     [5 2 2 5]
차분 배열에 더하기로 적은 결과  [5 7 7 5]
└ 2 칸이 어긋난다. 앞 갱신의 5 를 지우는 일이 D 의 두 칸으로는 적히지 않는다
```

덮어쓰기는 앞 값을 **지우고** 새 값을 두는데, 지울 값이 칸마다 다르니 경계 두 칸의 고정된 수로는 적을 수
없어요. 둘째 전제는 비용의 문제입니다. 갱신 도중 칸 하나를 읽으면 그 칸까지의 차이를 다 더해야 해요.

<!--proof:premise-midquery-->

```text
A[6] 하나를 지금 읽는다            D[0] 부터 D[6] 까지 7 칸을 더한다
N = 100,000 에서 칸 하나를 읽는다  평균 50,000.5 칸을 더한다
```

#### 취소를 r + 1 에 적는 까닭

취소 이벤트를 적는 자리는 구간의 **끝난 다음 칸** `r + 1` 입니다. 구간의 끝 `r` 이나 두 칸 뒤 `r + 2` 가 아닌
까닭을 값으로 확인해요. 정본에서 취소를 적는 줄의 자리만 바꾼 코드를 만들어 `r + 0` · `r + 1` · `r + 2` 셋을
같은 입력에 걸었습니다.

<!--proof:cost-cancel-offset-->

| 취소를 적는 칸 | 필요한 D 칸 수 | 낸 배열 | 어긋난 칸 |
| --- | ---: | --- | ---: |
| r + 0 | 7 | [-1 1 2 0 0 3 0] | 3 |
| r + 1 | 8 | [-1 1 1 2 0 3 3] | 0 |
| r + 2 | 9 | [-1 1 1 1 2 3 3] | 2 |

정본이 낸 배열은 [-1 1 1 2 0 3 3] 입니다.
<!--/proof-->

`r + 0` 은 구간의 오른쪽 끝 칸이 자기 갱신을 못 받고, `r + 2` 는 구간 밖의 칸 하나가 값을 더 받습니다. 어긋난
칸이 0 인 것은 가운데 하나뿐이에요. 칸 `r` 까지는 값이 있어야 하고 칸 `r+1` 부터는 없어야 하니, 없어지기
시작하는 칸이 곧 취소를 적을 칸입니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 이렇습니다. 첫 줄이 갱신 전에 한 번, 둘째 줄이 갱신마다, 나머지가 갱신이
끝난 뒤 한 번이에요.

1. 차분 배열 `D` 를 `N + 1` 칸의 `0` 으로 잡는다
2. 갱신 `(l, r, v)` 마다 `D[l]` 에 `v` 를 더하고 `D[r+1]` 에서 `v` 를 뺀다
3. `running` 을 `0` 으로 두고 `i` 를 `0` 부터 `N−1` 까지 올리며 `D[i]` 를 더한다
4. 그때그때의 `running` 을 `A[i]` 에 적고, 끝나면 `A` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 갱신 셋을 경계 여섯 칸에 적고 일곱 칸을 복원한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const N = 7;
const updates: Array<[number, number, number]> = [
  [1, 3, 2],
  [0, 2, -1],
  [5, 6, 3],
];
// 이 절이 끝나면 [-1, 1, 1, 2, 0, 3, 3] 이 나와야 한다
```

왜 하필 이 갱신 셋일까요? 세 구간이 서로 겹쳐 한 칸에 사건이 여럿 걸리고, 더하는 값 하나가 음수라 취소가
덧셈이 되며, 마지막 갱신의 오른쪽 끝이 `N−1` 이라 **여분 칸 `D[N]` 에 적는 자리**가 실제로 실행되기 때문이에요.
어느 갱신도 덮지 않는 칸도 하나 있습니다.

```text
diffArrayRangeUpdate(N, updates):
    D 를 N+1 칸의 0 으로 잡는다
    갱신 (l, r, v) 를 목록에서 하나씩 받으며:          ① 처리할 갱신이 남았는가
        D[l] 에 v 를 더한다                            ② 시작 이벤트
        D[r+1] 에서 v 를 뺀다                          ③ 취소 이벤트
    running 을 0 으로 두고 i 를 0 부터 N−1 까지 올리며:  ④ 복원할 칸이 남았는가
        running 에 D[i] 를 더하고 A[i] 에 적는다
    A 를 반환한다
```

#### 1. 차분 배열을 N + 1 칸의 0 으로 잡는다

크기와 처음 값이 이 조각의 전부입니다. 한 줄이지만 칸 수 `N + 1` 이 뒤의 취소 이벤트가 쓸 자리를 미리 마련해요.

```ts
const D = new Array<number>(N + 1).fill(0);
```

이 조각만 실행하면 차분 배열이 이렇게 잡힙니다.

<!--proof:walk-init-->

```text
N = 7                  칸 8 개 (0 … 7)
D = [0 0 0 0 0 0 0 0]  모든 칸이 0 인 결과 배열의 차분 배열이다
```

#### 2. 갱신마다 시작 칸과 취소 칸을 적는다

기록 반복이 이 조각입니다. 갱신을 받아 `D` 의 두 칸만 고치고, 결과 배열은 아직 만들지 않아요.

```ts
for (const [l, r, v] of updates) {
  // ① 처리할 갱신이 남았는가 — 남아 있으면 아래 두 줄을 한 번 실행한다.
  // ② 시작 이벤트 — 인덱스 l 부터 v 가 더해진다.
  D[l] = (D[l] as number) + v;
  // ③ 취소 이벤트 — 인덱스 r+1 부터 그 v 가 없어진다.
  D[r + 1] = (D[r + 1] as number) - v;
}
```

이 조각까지 실행하면 갱신 셋이 `D` 를 이렇게 바꿉니다.

<!--proof:walk-record-->

| 걸음 | 갱신 | 시작 이벤트 | 취소 이벤트 | 기록 뒤의 D |
| --- | --- | --- | --- | --- |
| T2 | (1,3,2) | D[1] += 2 | D[4] −= 2 | [0 2 0 0 -2 0 0 0] |
| T3 | (0,2,-1) | D[0] += -1 | D[3] −= -1 | [-1 2 0 1 -2 0 0 0] |
| T4 | (5,6,3) | D[5] += 3 | D[7] −= 3 | [-1 2 0 1 -2 3 0 -3] |

갱신 3 개가 경계 6 칸에 적혔고, 결과 배열은 아직 한 칸도 만들지 않았습니다.
<!--/proof-->

`①` 은 T2 · T3 · T4 에서 참이었고, 갱신이 더 없어 그다음에 처음 거짓이 됩니다. `②` 와 `③` 은 그 세 걸음에서
각각 한 번씩 실행돼 경계 여섯 칸을 채웠어요. T3 의 취소 이벤트는 `−1` 을 빼는 것이라 `D[3]` 에 `+1` 이 적힙니다.
취소는 「빼기」가 아니라 「그 값을 없앤다」이고, 음수를 없애는 것은 양수를 더하는 것이에요.

여기서 가장 중요한 줄은 `D[r + 1] = (D[r + 1] as number) - v;` 입니다. 앞의 줄은 `l` 에 쓰고 이 줄은 `r + 1` 에
써요. **값이 있는 마지막 칸이 아니라 값이 없어지는 첫 칸**에 적는다는 것이 이 줄의 전부입니다.

#### 짚고 가기 — D 를 N 칸으로 잡아도 자바스크립트에서는 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 차분 배열의 칸 수입니다. 「결과 배열이 `N` 칸이니 차분 배열도 `N` 칸이면 되지
않나」로 읽기 쉬워요. 그 생각대로 한 곳만 바꿔 봅시다.

```ts
const D = new Array<number>(N).fill(0); // N + 1 이 아니라 N 칸으로 잡았다
```

그러면 오른쪽 끝이 `N−1` 인 갱신이 `D[N]` 에 취소를 적을 때 배열 밖으로 나갑니다. 그런데 **이 변경을 넣어도
답이 안 틀려요.** 네 입력에 두 코드를 각각 실행했습니다.

<!--proof:pause-short-d-->

```text
입력             정본              D 를 N 칸으로 잡은 코드
N=7 · 전개 입력  [-1 1 1 2 0 3 3]  [-1 1 1 2 0 3 3]         답이 같다
N=4 · (0,3,5)    [5 5 5 5]         [5 5 5 5]                답이 같다
N=5 · (2,2,7)    [0 0 7 0 0]       [0 0 7 0 0]              답이 같다
N=3 · 갱신 없음  [0 0 0]           [0 0 0]                  답이 같다

└ 입력 4 개 중 4 개에서 답이 같다. 오른쪽 끝이 N−1 인 갱신이 있는 입력도 그렇다
```

오른쪽 끝이 `N−1` 인 갱신이 있는 첫 두 줄도 답이 같습니다. 왜 그런지는 기록이 끝난 뒤의 차분 배열을 꺼내 보면
보여요.

<!--proof:pause-short-d-state-->

```text
잡은 칸 수              7
기록이 끝난 뒤의 칸 수  8
기록이 끝난 뒤의 D      [-1 2 0 1 -2 3 0 NaN]
정본의 D                [-1 2 0 1 -2 3 0 -3]
└ 없던 칸 D[7] 에서 3 을 빼서 NaN 이 적혔다. 배열은 조용히 한 칸 늘었고, 복원은 그 칸을 읽지 않는다
```

자바스크립트는 없는 칸 `D[N]` 을 읽으면 `undefined` 를 내고, 거기서 `v` 를 빼면 `NaN` 이 됩니다. 그 값을
`D[N]` 에 쓰면 배열이 **예외 없이 한 칸 늘어나요.** 복원은 `D[N−1]` 까지만 읽으니 그 `NaN` 이 답에 섞이지
않습니다. 답이 안 틀리는 것은 이 두 우연이 겹친 결과예요.

```text
같은 실수가 환경마다 내는 결과
  자바스크립트 배열     배열이 조용히 길어진다         답은 맞고 D 의 길이가 바뀐다
  파이썬 리스트 · 자바  범위를 벗어난 쓰기다           그 자리에서 예외가 난다
  D[N] 을 읽는 코드     NaN 을 더하게 된다             그 뒤의 값이 모두 NaN 이 된다
                        └ 칸을 N + 1 개로 잡으면 이 세 갈래가 다 사라진다
```

그래서 답이 맞더라도 고칩니다. 차분 배열의 칸 수는 경계가 올 수 있는 자리의 수이고, 그 자리는 0 부터 `N` 까지
`N + 1` 개예요.

#### 3. 앞에서부터 누적해 결과 배열을 채운다

복원 반복이 이 조각입니다. `running` 에 `D[i]` 를 더하고, 그 값을 그대로 `A[i]` 에 적어요.

```ts
const A = new Array<number>(N);
let running = 0;
for (let i = 0; i < N; i++) {
  // ④ 복원할 칸이 남았는가 — 앞에서부터 누적한 값이 인덱스 i 의 최종 값이다.
  running += D[i] as number;
  A[i] = running;
}
```

`④` 는 `i` 가 `0` 부터 `N−1` 까지일 때 참이고 `N` 에서 처음 거짓이 됩니다. 이 조각의 앞 두 걸음만 실행하면
이렇게 나와요.

<!--proof:walk-restore-two-->

| 걸음 | i | D[i] | 더한 뒤의 running | A[i] |
| --- | ---: | ---: | ---: | ---: |
| T5 | 0 | -1 | -1 | -1 |
| T6 | 1 | 2 | 1 | 1 |

`running` 이 곧 `A[i]` 라는 것이 이 두 줄의 전부입니다. 앞 칸까지의 누적을 들고 있다가 이번 칸의 차이를 더하면
이번 칸의 값이 돼요. T6 에서 `−1` 을 들고 있다가 `D[1] = 2` 를 더해 `1` 이 된 것이 「칸 0 에서 칸 1 로 넘어가며
2 가 오른다」를 그대로 따른 것입니다.

#### 짚고 가기 — 복원 루프의 두 줄 순서를 바꾸면 값이 한 칸씩 뒤로 옮겨진다

여기서 헷갈리기 쉬운 포인트는 반복 안 두 줄의 순서입니다. 「어차피 둘 다 이번 바퀴에서 하는 일인데 순서가
중요할까」로 읽기 쉬워요. 순서를 바꿔 봅시다.

```ts
for (let i = 0; i < N; i++) {
  A[i] = running; // 적기를 먼저 했다
  running += D[i] as number;
}
```

이렇게 하면 `A[i]` 에 **칸 `i−1` 까지의 누적**이 실립니다. 이번 칸의 차이를 아직 안 더한 값이에요. 정본에서
두 줄의 순서만 바꾼 코드를 만들어 네 입력에 걸었습니다.

<!--proof:pause-write-first-->

```text
입력             정본              순서를 바꾼 코드  어긋난 칸
N=7 · 전개 입력  [-1 1 1 2 0 3 3]  [0 -1 1 1 2 0 3]  5          답이 다르다
N=1 · (0,0,5)    [5]               [0]               1          답이 다르다
N=4 · (0,3,5)    [5 5 5 5]         [0 5 5 5]         1          답이 다르다
N=3 · 갱신 없음  [0 0 0]           [0 0 0]           0          답이 같다

└ 배열 길이는 네 입력 모두 정본과 같다
```

**배열 길이가 네 입력 모두 같다는 것**이 이 실수의 성격입니다. 길이를 검사하는 테스트는 전부 통과하고, 갱신이
없는 입력에서는 답까지 같아요. 전개 입력의 두 배열을 칸마다 맞대면 무엇이 일어났는지 보입니다.

<!--proof:pause-shift-->

```text
정본              -1  1   1  2  0  3  3
순서를 바꾼 코드  0   -1  1  1  2  0  3
└ 아래 줄의 칸 i 가 위 줄의 칸 i−1 이다. 앞에는 0 이 들어가고 정본의 마지막 3 은 잘린다
```

값이 모두 「본 적 있는 수」라 눈으로 대조해도 넘어가기 쉽습니다. 고치는 방법은 **더하고 나서 적는** 순서 하나예요.
`A[i]` 는 칸 `i` 의 변화까지 들어간 값이어야 합니다.

#### 4. 일곱 칸을 끝까지 복원해 결과를 낸다

조각을 이어 고정 입력에 실행하면 열한 걸음이 나옵니다. T1 이 차분 배열을 잡고, T2 부터 T4 까지가 기록, T5
부터 T11 까지가 복원이에요. 맨 윗줄이 결과 배열 `A`, 그 아래가 차분 배열 `D` 입니다. 괄호는 이번 걸음이 다루는
`A` 의 구간이에요. 기록에서는 갱신이 덮는 구간이고, 복원에서는 지금까지 누적한 앞부분입니다. 점선 칸은 아직
안 쓴 칸, 진한 칸은 이번 걸음에 쓴 칸, ▲ 는 이번 걸음에 읽은 칸이에요.

기록 걸음에서 괄호는 세 칸을 덮는데 차분 배열에서 진해지는 칸은 두 칸뿐이고, 결과 배열은 기록이 끝날 때까지
한 칸도 채워지지 않습니다. 걸음마다 읽고 쓴 칸을 전부 적으면 아래 열한 단계예요.

<!--proof:walk-trace-->

| 걸음 | 하는 일 | 갱신 또는 i | 읽은 칸 | 쓴 칸 | 갈래 |
| --- | --- | --- | --- | --- | --- |

| T3 | 갱신을 경계 두 칸에 적는다 | (0,2,-1) | — | D[0] = -1, D[3] = 1 | ①②③ |
| T4 | 갱신을 경계 두 칸에 적는다 | (5,6,3) | — | D[5] = 3, D[7] = -3 | ①②③ |
| T5 | 누적해 A[i] 에 적는다 | i = 0 | D[0]=-1 | A[0] = -1 | ④ |
| T6 | 누적해 A[i] 에 적는다 | i = 1 | D[1]=2 | A[1] = 1 | ④ |
| T7 | 누적해 A[i] 에 적는다 | i = 2 | D[2]=0 | A[2] = 1 | ④ |
| T8 | 누적해 A[i] 에 적는다 | i = 3 | D[3]=1 | A[3] = 2 | ④ |
| T9 | 누적해 A[i] 에 적는다 | i = 4 | D[4]=-2 | A[4] = 0 | ④ |
| T10 | 누적해 A[i] 에 적는다 | i = 5 | D[5]=3 | A[5] = 3 | ④ |
| T11 | 누적해 A[i] 에 적는다 | i = 6 | D[6]=0 | A[6] = 3 | ④ |

**네 갈래가 모두 실행됐습니다.** 반환값은 결과 배열의 최종 상태인 `[-1, 1, 1, 2, 0, 3, 3]` 이고, 갈래마다
실행된 걸음과 연산 수를 세면 이렇습니다.

<!--proof:walk-branches-->

```text
갱신을 적는다  T2 T3 T4  갱신 3 개에 경계 6 칸  ①②③
누적해 적는다  T5~T11    칸 7 개에 덧셈 7 번    ④
```

`①` 과 `④` 는 반복의 조건이라 참인 걸음은 위와 같고, 목록이 끝났을 때와 `i` 가 `N` 이 됐을 때 한 번씩 거짓이
되어 반복을 벗어납니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `A` 를 그대로 돌려주는 마지막 한 줄뿐이에요 —
갱신 목록이 비면 기록 반복이 한 번도 실행되지 않아 `D` 가 전부 `0` 이고, 복원이 `0` 만 쌓아 모든 칸이 `0` 인
배열이 나옵니다.

```ts
export function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[] {
  // 갱신을 결과 배열에 바로 반영하지 않고 경계 두 칸에만 적어 두는 차분 배열.
  // 칸이 N+1 개인 것은 오른쪽 끝이 N−1 인 갱신이 마지막 칸에 취소를 적기 때문이다.
  const D = new Array<number>(N + 1).fill(0);

  for (const [l, r, v] of updates) {
    // ① 처리할 갱신이 남았는가 — 남아 있으면 아래 두 줄을 한 번 실행한다.
    // ② 시작 이벤트 — 인덱스 l 부터 v 가 더해진다.
    D[l] = (D[l] as number) + v;
    // ③ 취소 이벤트 — 인덱스 r+1 부터 그 v 가 없어진다.
    D[r + 1] = (D[r + 1] as number) - v;
  }

  const A = new Array<number>(N);
  let running = 0;
  for (let i = 0; i < N; i++) {
    // ④ 복원할 칸이 남았는가 — 앞에서부터 누적한 값이 인덱스 i 의 최종 값이다.
    running += D[i] as number;
    A[i] = running;
  }

  return A;
}
```

<!--proof:final-calls-->

```text
diffArrayRangeUpdate(7, [[1,3,2], [0,2,-1], [5,6,3]])  →  [-1, 1, 1, 2, 0, 3, 3]
diffArrayRangeUpdate(5, [[0,2,3]])                     →  [3, 3, 3, 0, 0]
diffArrayRangeUpdate(4, [[0,3,5]])                     →  [5, 5, 5, 5]
diffArrayRangeUpdate(5, [[2,2,7]])                     →  [0, 0, 7, 0, 0]
diffArrayRangeUpdate(3, [])                            →  [0, 0, 0]
```

### 알아 두면 좋은 개념 — 이벤트 스위핑

이 절차가 갱신 하나에 한 일을 한 문장으로 줄이면 **「구간을 시작 사건과 끝 사건 두 개로 바꾸고, 좌표축을 한 번
지나가며 그 사건들을 누적한다」** 입니다. 이렇게 구간을 사건으로 바꿔 좌표축을 한 번에 처리하는 방식을
**이벤트 스위핑**이라고 부릅니다.

<!--proof:related-sweep-->

```text
[1,3] 에 2 를 더한다  →  인덱스 1 에서 시작 · 인덱스 4 에서 끝
  └ T2 가 D[1] 과 D[4] 에 적은 것이 이 두 사건이다

인덱스     0  1   2  3  4   5  6
사건       ·  +2  ·  ·  -2  ·  ·
누적한 값  0  2   2  2  0   0  0
```

같은 모양이 다른 과제에서도 같은 이름으로 나옵니다. 바뀌는 것은 **사건에 무엇을 적는가**와 **누적한 값을 어디에
쓰는가**예요.

| 과제 | 사건에 적는 것 | 좌표축을 지나며 하는 일 |
| --- | --- | --- |
| 구간 덧셈 갱신 — 이 글 | 시작에 `+v`, 끝난 다음 칸에 `−v` | 누적한 값을 그대로 배열에 적는다 |
| 회의가 가장 많이 겹치는 시각 | 시작에 `+1`, 끝난 다음에 `−1` | 누적한 값의 최댓값을 찾는다 |
| 2 차원 구간 갱신 | 네 꼭짓점에 `+v` 와 `−v` 를 적는다 | 행으로 한 번, 열로 한 번 누적한다 |

첫 줄과 둘째 줄의 차이는 누적한 값을 배열로 돌려주는가, 최댓값만 보는가 하나입니다. 셋째 줄은 좌표축이 둘이라
사건이 네 개가 되고 누적도 두 번이 돼요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 두 배열의 관계를 식으로 어떻게 적는지, 무엇이
매 걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 갱신 대상이 **연속 구간**입니다. 인덱스를 골라 담는 집합이면 두 칸으로 줄일 수 없어요.
- 구간에 하는 일이 **덧셈으로 쌓이고 뺄셈으로 취소됩니다.** 더하기 · 빼기 · 배타적 논리합이 그렇고, 「구간을
  전부 5 로 덮어쓰기」는 아닙니다.
- 값을 읽는 것이 **갱신이 다 끝난 뒤**입니다. 차분 배열은 마지막에 배열 전체를 한 번 냅니다.
- 인덱스의 범위가 **배열로 잡을 수 있는 크기**입니다. 경계를 인덱스 자리에 바로 적기 때문이에요.

```text
네 조건이 코드의 모양을 그대로 정한다
  연속 구간          → 시작과 끝 두 칸으로 갱신이 표현된다
  덧셈과 뺄셈        → 여러 갱신의 사건이 한 칸에서 그냥 더해진다
  읽기가 맨 끝에     → 누적을 한 번만 하면 된다
  인덱스가 배열 크기 → 사건을 그 자리에 바로 적는다. 정렬이 필요 없다
```

마지막 두 줄이 이 절차의 경계입니다. 읽기가 갱신 사이에 섞이면 누적을 매번 다시 해야 하고, 인덱스 범위가
`10^9` 처럼 크면 배열을 잡을 수 없어요.

| 조건 | 차분 배열에서 일어나는 일 | 갈 곳 |
| --- | --- | --- |
| 읽기가 맨 끝에 한 번 | 누적 한 번으로 끝난다 | 이 글의 절차 |
| 읽기가 갱신 사이에 섞인다 | 읽을 때마다 그 칸까지 다시 더한다 | 펜윅 트리 |
| 인덱스가 `10^9` 까지 | 배열을 잡지 못한다 | 좌표를 압축하고 사건을 정렬한다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "구간 [l, r] 에 v 를 더한다"  "범위에 일괄 적용"       ← 갱신이 구간 단위다
  "모든 갱신을 적용한 뒤"  "최종 상태를 출력하라"        ← 읽기가 맨 끝에 한 번이다
  "갱신 순서는 결과에 영향을 주지 않는다"                ← 덧셈으로 쌓인다는 신호다
  "예약된 좌석 수"  "구간별 인원 증감"                   ← 시작과 끝이 있는 사건이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N × Q 가 못 들어간다
  인덱스가 배열로 잡을 수 있는 크기다

반대로 이런 말이 보이면 해당하지 않는다
  "갱신 중간에 값을 물어본다"  "질의가 섞여 들어온다"     ← 누적을 매번 다시 해야 한다
  "구간의 최댓값을 갱신한다"  "구간을 v 로 덮어쓴다"      ← 뺄셈으로 취소되지 않는다
  "인덱스가 10^9 까지"                                    ← 배열을 못 잡는다
```

마지막 무리가 보이면 다른 절차로 갑니다. 갱신과 조회가 섞이면
[`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-guide.md) 쪽이고, 구간의 최솟값이나 최댓값을 다루면
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **NumPy 의 `numpy.diff` 와 `numpy.cumsum`** — 이 글이 쓰는 두 연산을 각각 함수 하나로 제공합니다. 앞은 공식
  문서가 *"Calculate the n-th discrete difference along the given axis"* 로 적고, 뒤는 *"Return the cumulative
  sum of the elements along a given axis"* 로 적어요. 두 페이지가 「See also」로 서로를 가리키고 있습니다.
  ([`numpy.diff`](https://numpy.org/doc/stable/reference/generated/numpy.diff.html) ·
  [`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-30)
- **LLVM libc++ 의 `std::partial_sum`** — 복원 반복과 같은 모양입니다. 소스의 중심 두 줄이
  `__t = __t + *__first;` 와 `*__result = __t;` 인데, 이 글의 `running += D[i]` 와 `A[i] = running` 이 그
  둘이에요. 짝이 되는 `std::adjacent_difference` 는 반대로 `*__result = __val - __acc;` 를 적습니다.
  ([`partial_sum.h`](https://github.com/llvm/llvm-project/blob/main/libcxx/include/__numeric/partial_sum.h) ·
  [`adjacent_difference.h`](https://github.com/llvm/llvm-project/blob/main/libcxx/include/__numeric/adjacent_difference.h),
  조회 2026-08-30)
- **Prometheus 의 카운터** — 공식 문서가 카운터를 *"a cumulative metric that represents a single
  monotonically increasing counter whose value can only increase or be reset to zero on restart"* 로
  정의합니다. 저장되는 것은 누적값이고 구간의 증가량은 뒤에서 두 시점의 차이로 만드는데, 이 글이 `D` 를 적어
  두었다가 누적하는 것과 방향만 반대예요.
  ([Prometheus — Metric types](https://prometheus.io/docs/concepts/metric_types/),
  조회 2026-08-30)

```text
세 사례와 이 과제의 관계

  앞의 둘      차이와 누적을 각각 하나씩 제공한다. 구간 갱신을 두 사건으로 바꾸는 것은 쓰는 쪽의 몫이다
  Prometheus   누적을 먼저 저장하고 차이를 나중에 만든다. 이 글은 차이를 먼저 적고 누적을 나중에 한다
               └ 두 연산이 서로의 역이라는 것을 양쪽이 같이 보인다
```

**구간 갱신 전체를 하나의 이름으로 제공하는 표준 라이브러리는 찾지 못했습니다.** 주어지는 것은 차이와 누적 두
조각이고, 「구간을 두 사건으로 바꿔 그 자리에 적는다」는 그 둘을 잇는 쪽의 코드로 남아 있어요.

#### 경쟁 설계와의 대조

같은 목표(구간 갱신을 모아 두었다가 값을 읽기)를 노리는 다른 절차로 **펜윅 트리**(이진 인덱스 트리)에 같은
차이 값을 담는 방법이 있습니다. 칸 `j` 가 자기 아래 여러 칸의 차이 합을 들고 있어서, 갱신 하나가 `log N` 개의
칸을 고치고 값 하나를 묻는 것도 `log N` 개의 칸을 읽어요.

| 설계 | 갱신 때 고치는 칸 | 값 하나를 물을 때 읽는 칸 |
| --- | --- | --- |
| 차분 배열 | 2 개 | 칸 0 부터 그 칸까지 전부 |
| 펜윅 트리 | `log N` 개 | `log N` 개 |

갱신은 차분 배열이 적게 고치고, 중간 조회는 펜윅 트리가 적게 읽습니다. 그래서 섞인 비율이 어느 쪽의 접근 수가
적은지를 정해요.

같은 입력·같은 작업 목록에 두 설계를 걸고 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은 `N = 1,024` 이고
갱신은 `Q = 1,024` 개인데, `k` 번째 갱신이 `l = (37k) mod N` 에서 시작해 `r = min(N−1, l + (k mod 64))` 에서
끝나고 `v = (k mod 7) + 1` 을 더합니다. `t` 번째 점 조회는 인덱스 `x = (91(t+1)) mod N` 의 지금 값을 묻고,
조회는 갱신 사이에 고르게 끼웠어요. 마지막에는 두 설계가 다 배열 전체를 만듭니다. 난수를 쓰지 않아 시드가 없고,
위 식이 입력의 전부예요. 전개의 일곱 칸을 쓰지 않은 까닭은 일곱 칸에서는 펜윅 트리가 한 번에 지나는 칸이
두세 개뿐이라 두 설계의 접근 수가 상수에 묻히기 때문입니다.

| 섞인 점 조회 | 차분 배열 | 펜윅 트리 | 적은 쪽 |
| --- | --- | --- | --- |
| 0 회 | **7,169** | 30,214 | 차분 배열 |
| 44 회 | **29,719** | 30,437 | 차분 배열 |
| 45 회 | 30,743 | **30,438** | **펜윅 트리 — 여기서 순서가 뒤집힙니다** |
| 1,024 회 | 531,969 | **35,335** | 펜윅 트리 |

**저장 칸은 둘 다 1,025 개로 같습니다.** 메모리에서는 갈리지 않아요 — 갈리는 것은 접근 수이고, 그 경계가 이
입력에서 **점 조회 45 회**입니다. 경계가 그 자리에 오는 까닭을 표의 값으로 풀면 이렇습니다.

<!--proof:alt-crossing-->

```text
차분 배열의 점 조회 하나  (531,969 − 7,169) ÷ 1,024 = 512.5  칸 0 부터 그 칸까지 다시 더한다
펜윅 트리의 점 조회 하나  (35,335 − 30,214) ÷ 1,024 = 5.0    칸 log N 개를 읽는다
점 조회 0 회의 차이       30,214 − 7,169 = 23,045            차분 배열이 적은 만큼
뒤집히는 자리             23,045 ÷ (512.5 − 5.0) ≈ 45.4      실측으로는 점 조회 45 회에서 뒤집힌다
```

평균으로 낸 자리와 실측이 뒤집히는 자리가 같은 곳을 가리킵니다. **이 절차가 내주는 것은 중간 조회입니다.**
갱신 도중에 값 하나를 물으면 칸 0 부터 그 칸까지 다시 더해야 해서, 조회 하나가 평균 수백 번의 접근이 돼요.
그 대신 얻는 것이 셋입니다.

| 축 | 차분 배열 | 펜윅 트리 |
| --- | --- | --- |
| 갱신 비용 | 경계 두 칸만 고친다 | 갱신 하나에 칸 `log N` 개를 고친다 |
| 구현 | 루프 두 개, 비트 연산 없음 | `j & -j` 로 칸을 골라 다닌다 |
| 점 조회 0 회의 접근 수 | 7,169 | 30,214 |

**우열이 반대가 되는 조건이 분명합니다.** 값을 읽는 것이 갱신이 다 끝난 뒤 한 번이면 차분 배열이 답이고, 이
입력에서 점 조회가 45 회 이상 섞이면 펜윅 트리가 적어요. 지문에 **갱신 사이의 조회가 섞이는 순간** 이 판정을
다시 해야 합니다.

### 수식 정의와 유도

갱신 목록을 집합으로 두고 차분 배열을 정의합니다. `U` 는 주어진 갱신 `(l, r, v)` 들의 모음이고, `D` 의 칸 `j`
에는 그 칸에서 시작하는 갱신의 값을 더하고 그 칸에서 끝나는 갱신의 값을 뺍니다.

$$D[j] \;=\; \sum_{(l,r,v)\in U,\; l = j} v \;-\; \sum_{(l,r,v)\in U,\; r+1 = j} v \qquad (0 \le j \le N)$$

정의를 전개 입력 `U = {(1,3,2), (0,2,-1), (5,6,3)}` 에 넣어 칸 넷을 계산하면 이렇습니다.

<!--proof:math-check-d-->

```text
D[0]  = (l = 0 인 갱신의 v -1)    − (r+1 = 0 인 갱신의 v 없음)  = -1
D[3]  = (l = 3 인 갱신의 v 없음)  − (r+1 = 3 인 갱신의 v -1)    = 1
D[4]  = (l = 4 인 갱신의 v 없음)  − (r+1 = 4 인 갱신의 v 2)     = -2
D[7]  = (l = 7 인 갱신의 v 없음)  − (r+1 = 7 인 갱신의 v 3)     = -3
```

정의 하나가 칸 하나를 정하고, 그 칸에 걸린 갱신만 봅니다. 결과 배열은 그 칸까지의 합으로 정의해요.

$$A[i] \;=\; \sum_{j=0}^{i} D[j] \qquad (0 \le i \le N-1)$$

<!--proof:math-check-a-->

```text
D = [-1 2 0 1 -2 3 0 -3]

A[0]  = D[0]                              = (-1) = -1
A[3]  = D[0] + D[1] + D[2] + D[3]         = (-1) + 2 + 0 + 1 = 2
A[4]  = D[0] + D[1] + D[2] + D[3] + D[4]  = (-1) + 2 + 0 + 1 + (-2) = 0
```

두 정의를 이으면 `A[i]` 가 무엇인지 임의의 `N` 과 임의의 갱신 목록에서 나옵니다. 합의 순서를 바꿔 갱신 하나씩으로
묶는 것이 유도의 전부예요.

$$A[i] \;=\; \sum_{j=0}^{i}\left(\sum_{l=j} v - \sum_{r+1=j} v\right) \;=\; \sum_{(l,r,v)\in U} v\Bigl([\,l \le i\,] - [\,r+1 \le i\,]\Bigr)$$

```text
대괄호는 조건이 참이면 1, 거짓이면 0 을 뜻합니다

  왼쪽 항 [l ≤ i]      갱신의 시작 사건이 칸 0..i 안에 들어왔는가
  오른쪽 항 [r+1 ≤ i]  그 갱신의 취소 사건도 칸 0..i 안에 들어왔는가
                       └ 갱신 하나가 두 항으로 갈려 서로 지운다
```

두 항의 차이를 `i` 의 위치로 갈라 봅니다. `l ≤ r` 이 조건이므로 `l ≤ i` 이면서 `r+1 ≤ i` 가 아닌 자리가 정확히
구간 안이에요.

| `i` 의 위치 | `[l ≤ i]` | `[r+1 ≤ i]` | 두 항의 차이 |
| --- | --- | --- | --- |
| `i < l` | 0 | 0 | 0 |
| `l ≤ i ≤ r` | 1 | 0 | 1 |
| `i > r` | 1 | 1 | 0 |

세 줄이 겹치지도 빠지지도 않으므로 차이가 `[l ≤ i ≤ r]` 과 같습니다. 그래서 유도가 과제의 정의로 닫혀요.

$$A[i] \;=\; \sum_{(l,r,v)\in U} v\,[\,l \le i \le r\,] \;=\; \sum_{(l,r,v)\in U,\; l \le i \le r} v$$

```ts
// 위 정의를 그대로 옮긴 조각. 실제 절차는 이 합을 누적 하나로 대신한다.
const cellFromDefinition = (D: number[], i: number): number =>
  D.slice(0, i + 1).reduce((s, x) => s + x, 0);
```

이 조각은 칸 하나를 만드는 데 `i+1` 번을 더하므로 전부 더하면 `N(N+1)/2` 번입니다. 누적을 들고 가면 칸 하나가
덧셈 한 번이라 `N` 번이에요 — 같은 값을 만드는 두 방법의 차이가 그것입니다.

<!--proof:math-count-->

```text
정의를 그대로 쓴다  칸 i 에 i+1 번  전부 N(N+1)/2 = 5,000,050,000 번
누적을 들고 간다    칸 i 에 1 번    전부 N = 100,000 번
└ N = 100,000 일 때의 값이다
```

배열 접근 수도 두 절차에서 닫힌 형태로 나옵니다. 차분 배열은 초기화 `N+1` 번, 갱신마다 네 번, 복원마다 두 번이라
`3N + 4Q + 1` 이고, 구간 순회는 초기화 `N` 번에 덮는 칸마다 두 번이라 모든 갱신이 배열 전체를 덮을 때
`N + 2NQ` 예요. 두 식을 네 규모의 실측과 대조했습니다.

<!--proof:math-scale-->

| N = Q | 구간 순회(실측) | N + 2NQ | 차분 배열(실측) | 3N + 4Q + 1 |
| ---: | ---: | ---: | ---: | ---: |
| 4 | 36 | 36 | 29 | 29 |
| 64 | 8,256 | 8,256 | 449 | 449 |
| 1,000 | 2,001,000 | 2,001,000 | 7,001 | 7,001 |
| 4,000 | 32,004,000 | 32,004,000 | 28,001 | 28,001 |

실측값이 닫힌 형태와 4 규모에서 정확히 같습니다. 규모 N = Q = 100,000 을 두 식에 넣으면 20,000,100,000 대 700,001 이고, 28,572 배입니다.
<!--/proof-->

### 불변식 — running 은 D 의 앞 칸을 모두 더한 값이고 그것이 그 칸의 답이다

파트 1 에서 코드가 동작하는 것을 열한 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해
봅시다.

> 복원 반복이 칸 `i` 를 처리한 직후, `running` 은 `D[0]` 부터 `D[i]` 까지의 합이고, 그 값은 인덱스 `i` 를 덮은
> 모든 갱신의 `v` 를 더한 것과 같습니다.

```text
  running 이 더한 칸   D[0]  D[1]  …  D[i]
  아직 안 더한 칸      D[i+1]  …  D[N]

  running = D[0] + D[1] + … + D[i]                        ← 앞 문장
  그 합이 인덱스 i 를 덮은 모든 갱신의 v 를 더한 값이다   ← 뒤 문장
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 `running` 이 무엇인지 정하고, 뒤 문장이 **그 값을 그대로 `A[i]` 에
적어도 된다**는 것을 말해요. 둘 중 하나만 빠져도 복원 반복의 두 줄이 왜 그 모양인지 근거가 사라집니다.

**출발점부터 봅시다.** 반복에 들어가기 전 `running` 은 `0` 이고 더한 칸이 하나도 없습니다. 앞 문장의
「`D[0]` 부터 `D[i]` 까지」가 빈 범위라 합이 `0` 인 것이 맞아요.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | `running` 을 0 으로 둔다 | 더한 칸이 없어 합이 0 이다 | 아직 적은 칸이 없다 |
| `i = 0` | `D[0]` 을 더한다 | 합이 `D[0]` 하나가 된다 | 인덱스 0 에서 시작한 갱신만 들어 있다 |
| 임의의 `i` | `D[i]` 를 더한다 | 직전 바퀴가 `D[i−1]` 까지 만들어 뒀다 | 인덱스 `i` 에서 시작·취소된 갱신이 반영된다 |
| 종료 | `i = N−1` 을 마친다 | `D[0]` 부터 `D[N−1]` 까지 전부 | 결과 배열의 칸이 전부 정해졌다 |

셋째 줄이 이 논증의 핵심입니다. `D[i]` 에 적힌 것은 「인덱스 `i` 에서 시작하는 갱신의 값」에서 「인덱스 `i` 에서
취소되는 갱신의 값」을 뺀 것이라, 그것을 더하면 덮는 갱신의 집합이 정확히 갱신됩니다.

| 갱신 `(l, r, v)` 와 칸 `i` 의 관계 | `D[i]` 에 걸리는 것 | `running` 에 미치는 영향 |
| --- | --- | --- |
| `i = l` (구간이 여기서 시작한다) | `+v` | 이 갱신이 합에 들어온다 |
| `l < i ≤ r` (구간 안쪽이다) | 없음 | 이미 들어와 있고 그대로 남는다 |
| `i = r + 1` (구간이 끝난 다음 칸이다) | `−v` | 이 갱신이 합에서 빠진다 |
| `i < l` 또는 `i > r + 1` | 없음 | 관계가 없다 |

`l ≤ r` 이 조건이므로 시작이 취소보다 반드시 먼저 옵니다. 그래서 「들어왔다가 빠진다」의 순서가 뒤집히는 입력이
없어요. 전개 입력의 복원 걸음마다 두 문장을 따로 대조했습니다.

<!--proof:invariant-hold-->

| 걸음 | i | running | D[0] 부터 D[i] 까지의 합 | i 를 덮은 갱신의 v 합 |
| --- | ---: | ---: | ---: | ---: |
| T5 | 0 | -1 | -1 | -1 |
| T6 | 1 | 1 | 1 | 1 |
| T7 | 2 | 1 | 1 | 1 |
| T8 | 3 | 2 | 2 | 2 |
| T9 | 4 | 0 | 0 | 0 |
| T10 | 5 | 3 | 3 | 3 |
| T11 | 6 | 3 | 3 | 3 |

걸음마다 두 문장을 따로 대조해 모두 14 번 대조했고, 어긋난 것은 0 번입니다.
<!--/proof-->

경계에 있는 입력들도 확인하고 갑시다.

<!--proof:invariant-edges-->

| 경우 | 입력 | 처리되는 자리 | 기록 뒤의 D | 결과 |
| --- | --- | --- | --- | --- |
| 갱신 목록이 빔 | N = 3 · 없음 | 기록 루프가 한 번도 실행되지 않는다 | [0 0 0 0] | [0 0 0] |
| N = 1 | N = 1 · (0,0,5) | D[0] 과 D[1] 에 적는다 | [5 -5] | [5] |
| l = r 인 갱신 | N = 5 · (2,2,7) | 이웃한 두 칸에 적힌다 | [0 0 7 -7 0 0] | [0 0 7 0 0] |
| r = N−1 인 갱신 | N = 4 · (1,3,4) | 취소가 D[N] 에 적히고 복원이 읽지 않는다 | [0 4 0 0 -4] | [0 4 4 4] |
| 같은 구간을 세 번 | N = 3 · (0,2,1) (0,2,1) (0,2,1) | 같은 두 칸에 값이 쌓인다 | [3 0 0 -3] | [3 3 3] |
| v 가 음수 | N = 4 · (0,2,5) (1,3,-3) | 취소 칸에 양수가 적힌다 | [5 -3 0 -5 3] | [5 2 2 -3] |
| v = 0 | N = 3 · (0,2,0) | 두 칸에 0 을 더한다 | [0 0 0 0] | [0 0 0] |

7 경우 모두 결과가 정의(칸마다 덮은 갱신의 v 합)와 같습니다.
<!--/proof-->

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 `running` 에 `D[i]` 를 **더하는** 그 한 줄이에요. 「어차피 `A[i]`
에 적을 값을 만드는 것이니 그 칸의 값을 옮기면 되지 않나」라는 생각으로 더하기를 대입으로 바꿔 봅니다.

```ts
for (let i = 0; i < N; i++) {
  running = D[i] as number; // 더하지 않고 그 칸의 값을 그대로 옮겼다
  A[i] = running;
}
```

정본에서 그 한 줄만 바꾼 코드를 네 입력에 걸었습니다.

<!--proof:mutant-no-accumulate-->

```text
입력             정본              누적하지 않은 코드  어긋난 칸
N=7 · 전개 입력  [-1 1 1 2 0 3 3]  [-1 2 0 1 -2 3 0]   5          답이 다르다
N=5 · (2,2,7)    [0 0 7 0 0]       [0 0 7 -7 0]        1          답이 다르다
N=1 · (0,0,5)    [5]               [5]                 0          답이 같다
N=3 · 갱신 없음  [0 0 0]           [0 0 0]             0          답이 같다

└ 칸이 하나뿐이거나 갱신이 없으면 누적할 것이 없어서 답이 같다
```

첫 줄에서 결과가 `D` 의 앞 일곱 칸 그 자체가 됐습니다. 앞 문장이 깨지면 `running` 은 「앞 칸들의 합」이 아니라
「이번 칸의 차이」가 되고, 뒤 문장의 근거가 함께 사라져요. 둘째 줄의 음수 한 칸이 그것을 가장 짧게 보입니다.

<!--proof:mutant-meaning-->

```text
누적하지 않은 코드의 결과  [0 0 7 -7 0]
같은 입력의 D              [0 0 7 -7 0 0]
└ 칸 3 의 -7 은 D[3] 에 적힌 취소 사건 그대로다. 없앨 7 이 앞에서 더해지지 않았으니 취소만 남았다
```

차이는 앞의 합이 있을 때만 뜻이 있습니다. 취소 사건은 앞에서 더한 값을 없애라는 기록이라, 앞의 합 없이 혼자 읽으면
없는 값을 없애는 음수가 답으로 나와요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — `D` 를 `0` 으로 채우는 것, 갱신을 경계 두 칸에 적는 것, 앞에서부터
누적해 `A` 를 채우는 것이에요. 전개의 걸음으로 세면 이렇게 나뉩니다.

<!--proof:perf-derive-->

| 무리 | 걸음 | 걸음마다 배열 접근 | 이 입력에서 |
| --- | --- | --- | --- |
| 초기화 | T1 | N+1 번 쓰기 | 8 |
| 기록 | T2 · T3 · T4 | 4 번 (경계 두 칸을 읽고 쓴다) | 3 × 4 = 12 |
| 복원 | T5~T11 | 2 번 (D[i] 읽기 · A[i] 쓰기) | 7 × 2 = 14 |

모두 8 + 12 + 14 = 34 번이고, 3N + 4Q + 1 에 N = 7, Q = 3 을 넣은 34 와 같습니다.
<!--/proof-->

T1 은 칸마다 한 번 쓰고, T2 부터 T4 까지의 기록 걸음은 경계 두 칸을 각각 읽고 써서 네 번이며, T5 부터 T11 까지의
복원 걸음은 `D[i]` 를 읽고 `A[i]` 를 써서 두 번입니다. 세 무리를 일반식으로 적으면 이렇습니다.

```text
총식 = 초기화 + 기록 + 복원
       └ N+1   └ 4Q   └ 2N

       배열 접근 = (N + 1) + 4Q + 2N = 3N + 4Q + 1
```

**개수가 입력의 내용과 무관하게 정해집니다.** 구간이 길든 짧든, 갱신이 겹치든 안 겹치든 걸음 수가 같아요 —
갱신 하나가 항상 칸 두 개이고 복원이 항상 `N` 걸음이기 때문입니다.

```text
여기서 센 것은 배열의 읽기와 쓰기 전부다
  추가로 잡는 메모리   D 가 N+1 칸, A 가 N 칸
  줄이려면             A 를 따로 만들지 않고 D 자리에 덮어써도 된다
                       읽은 D[i] 는 그 뒤로 다시 안 읽으므로 안전하다
                       └ 접근 수는 그대로이고 칸 수만 2N+1 에서 N+1 로 준다
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (갱신이 없다) | `O(N + Q)` | `Θ(N)` — `Q = 0` 이라 `N` 만 남는다 |
| **평균적인 경우** (입력 분포와 무관하다) | `O(N + Q)` | `Θ(N + Q)` |
| **최악의 경우** (모든 갱신이 배열 전체를 덮는다) | `O(N + Q)` | `Θ(N + Q)` — 실제로 도달한다 |

가운데와 아래 줄이 같은 것이 이 절차의 성질입니다. 걸음 수가 `N` 과 `Q` 로 딱 고정이라 입력의 모양을 어떻게
바꿔도 값이 같아요.

```text
비교 대상과 나란히 놓으면 이 성질이 확인된다
  구간을 통째로 고친다   최선 N + 2Q 번         최악 N + 2NQ 번
  경계 두 칸만 적는다    최선 3N + 4Q + 1 번    최악 3N + 4Q + 1 번
                         └ 위쪽은 구간 길이에 달렸고 아래쪽은 아니다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 `D` 를 `0` 으로 채우는 것 하나뿐이라는 것이 이 절차의
특징이에요 — 정렬도, 좌표압축도, 트리 만들기도 하지 않습니다.

```text
총식 = Θ(N + Q) 시간 + Θ(N) 추가 메모리
       └ 초기화 N+1 · 기록 4Q · 복원 2N   └ D 가 N+1 칸, A 가 N 칸
```

<!--proof:perf-total-->

```text
N = Q = 100,000 이면 배열 접근이 정확히 700,001 번, 잡는 칸이 200,001 개다
```

**보장의 종류는 전부 최악 보장입니다.** 해시도, 무작위성도, 분할 상환도 쓰지 않아요 — 어떤 입력을 넣어도 접근
수가 `3N + 4Q + 1` 로 같습니다.

```text
기댓값이 끼어들 자리가 없다
  칸을 찾는 방법   인덱스로 바로 간다        해시 충돌이라는 개념이 없다
  걸음 수          입력을 안 보고 정해진다   분포를 가정할 필요가 없다
  갱신 하나의 값   항상 칸 2 개              평균이 아니라 상수다
                   └ 최악 보장과 평균 비용이 같은 수다
```

#### 최악을 만드는 입력

접근 수를 최대로 만드는 방법은 하나뿐입니다 — **`N` 과 `Q` 를 과제 규모의 최댓값으로 두는 것**이에요. 구간의
길이는 접근 수를 바꾸지 못합니다. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->

| 입력의 모양 (N = Q = 1,000) | 덮는 칸의 합 | 구간 순회 접근 수 | 차분 배열 접근 수 |
| --- | ---: | ---: | ---: |
| 갱신이 전부 배열 전체를 덮는다 | 1,000,000 | 2,001,000 | 7,001 |
| 갱신이 전부 칸 하나짜리다 | 1,000 | 3,000 | 7,001 |
| 구간 길이가 1 부터 64 까지 섞인다 | 31,330 | 63,660 | 7,001 |

구간 순회의 접근 수는 세 줄이 다 다르고, 차분 배열의 접근 수는 세 줄이 같습니다.
<!--/proof-->

**「구간이 길수록 비용이 크다」는 이 절차에서 거짓입니다.** 물려받은 통념이 여기서는 성립하지 않아요 — 첫 줄과
둘째 줄은 덮는 칸의 합이 크게 다른데 차분 배열의 접근 수는 같습니다. 구간을 읽지 않고 두 끝만 적기 때문이에요.

최악은 축마다 다른 입력이 만듭니다. 접근 수와 잡는 칸은 `N` 과 `Q` 만 보고, 한 칸의 값은 `v` 를 봐요. 모든
갱신이 같은 칸 하나를 덮고 `v` 가 최댓값이면 그 칸의 값이 과제 규모 안에서 가장 커집니다.

<!--proof:worst-axes-->

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 배열 접근 수 | N = Q = 100,000, 구간 길이는 무엇이든 | 700,001 번 |
| 잡는 칸 | N = 100,000 | D 100,001 칸 + A 100,000 칸 = 200,001 칸 |
| 한 칸의 값 | (0,0,10000) 을 100,000 번 | 1,000,000,000 |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 구간을 통째로 고치던 것을 **시작과 취소 두 사건**으로 바꿨고,
취소를 `r+1` 에 적어야 구간의 오른쪽 끝이 값을 받으며, 앞에서부터 누적하면 각 칸이 자기를 덮은 갱신의 합이
됩니다.

```text
D 를 0 으로 채운다 → 갱신마다 D[l] 에 v 를 더하고 D[r+1] 에서 v 를 뺀다 → 앞에서부터 누적해 A 를 만든다
     └ 칸 N+1 개          └ 갱신 하나에 칸 2 개                              └ 칸마다 덧셈 한 번
```

먼저 답이 붙는 문제 하나입니다. 전개의 T4 는 `(5,6,3)` 을 기록한 걸음이었고, 오른쪽 끝이 `N−1` 이라 취소가
`D[N]` 에 적혔어요. 복원 반복은 그 칸을 읽지 않습니다. 그렇다면 기록이 끝난 `D[N]` 의 값을 보고 결과 배열에
대해 무엇을 알 수 있을까요?

<!--check:lastCell-->
답: **결과 배열의 마지막 칸 `A[N−1]` 을 알 수 있습니다.** `D[N]` 은 결과 배열의 끝에서 뒤의 `0` 칸으로 내려오는
변화라 `0 − A[N−1]` 이에요. 전개 입력에서 확인하면 이렇습니다.

<!--proof:selfcheck-dn-->

```text
D[7]               -3
A[6]               3
D 의 모든 칸의 합  0
└ D[7] 은 A[6] 의 부호를 바꾼 값이고, D 전체의 합은 0 이다
```

갱신 하나마다 `+v` 와 `−v` 를 한 번씩 적으니 `D` 의 모든 칸을 더하면 언제나 0 이고, 앞 `N` 칸의 합이 `A[N−1]`
이므로 남은 `D[N]` 이 그 부호를 바꾼 값이 됩니다.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「알아 두면 좋은 개념」            3 → 「경쟁 설계와의 대조」
  2 → 「취소를 r + 1 에 적는 까닭」
```

- 2 차원 구간 갱신(직사각형 `(r1,c1)` 부터 `(r2,c2)` 까지 `v` 를 더하기)에서는 사건을 몇 개 적어야 할까요?

### 구간 갱신 + 배열 반환 (Difference Array Range Update)

풀 파일: [`diffArrayRangeUpdate.ts`](./diffArrayRangeUpdate.ts) · 테스트: [`diffArrayRangeUpdate.test.ts`](./diffArrayRangeUpdate.test.ts) · 실행: `bun test src/algorithms/array/diffArrayRangeUpdate/diffArrayRangeUpdate.test.ts`

#### 한 줄 요약

> 길이 $N$의 제로 배열에 구간 덧셈 연산들을 적용한 뒤 **최종 배열**을 반환한다.

#### 스토리

물류 창고 관리자 민준은 창고 $N$칸의 재고를 관리한다. 처음에는 모든 칸의 재고가 $0$이다.

하루에 여러 번 입출고 지시가 들어온다. 각 지시는 "칸 $l$부터 칸 $r$까지 $v$만큼 더하라"는 형태다. $v$가 양수이면 입고, 음수이면 출고다.

하루 업무가 끝났을 때, 모든 칸의 최종 재고 상태를 배열로 출력해야 한다.

#### 함수 인터페이스

```ts
export function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[];
```

- `N` — 배열의 길이. 초기 값은 모두 `0`.
- `updates` — 갱신 연산 목록. 각 원소 `[l, r, v]`는 인덱스 $[l, r]$ 범위에 $v$를 더하는 연산이다.
- 반환 — 모든 갱신을 적용한 뒤의 길이 $N$ 배열.

#### 제약 조건

- $1 \leq N \leq 100{,}000$
- $0 \leq Q \leq 100{,}000$ (여기서 $Q$는 `updates`의 길이)
- 각 갱신 $[l, r, v]$는 $0 \leq l \leq r \leq N - 1$, $-10{,}000 \leq v \leq 10{,}000$ (정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

길이 $N$의 배열 $A$는 모든 원소가 $0$으로 초기화된다. 각 갱신 $[l, r, v]$는 다음을 의미한다.

$$\forall\, i \in [l, r],\quad A[i] \mathrel{+}= v$$

모든 갱신을 순서대로 적용한 뒤의 배열 $A$를 반환한다. 갱신 순서는 결과에 영향을 주지 않는다(덧셈은 교환·결합 법칙이 성립하므로). 갱신이 없으면 모든 원소가 $0$인 배열을 반환한다.

#### 예시

```ts
diffArrayRangeUpdate(5, [[0, 2, 3]]);
// [3, 3, 3, 0, 0]  — 인덱스 0~2에 3을 더함

diffArrayRangeUpdate(5, [
  [0, 2, 3],
  [1, 4, 2],
  [2, 2, -10],
]);
// [3, 5, -5, 2, 2]
// A[0]+=3 → 3, A[1]+=3+2=5, A[2]+=3+2-10=-5, A[3]+=2, A[4]+=2

diffArrayRangeUpdate(3, []);
// [0, 0, 0]  — 갱신 없음, 초기 상태 그대로

diffArrayRangeUpdate(1, [[0, 0, 5]]);
// [5]  — 단일 원소에 대한 갱신

diffArrayRangeUpdate(4, [[0, 3, 5]]);
// [5, 5, 5, 5]  — 전체 구간에 동일한 값 적용
```
