# diffArrayRangeUpdate — 구간을 통째로 손대지 않고 경계 두 점만 기록하는 이유

## 한눈에 보는 컨셉

길이 `N`인 배열에 구간 `[l, r]`마다 값 `v`를 더하는 갱신을 `Q`번 수행한 뒤, 마지막에 전체 배열 상태를 한 번만 돌려주면 되는 문제예요. 매 갱신을 배열에 직접 반영하는 대신, 구간이 **시작되는 지점**과 **끝난 직후 지점** 두 곳에만 흔적을 남기고, 모든 갱신이 끝난 뒤 누적합 한 번으로 실제 배열을 복원합니다.

```text
갱신 하나:  구간 전체를 순회        →  경계 두 칸만 건드림      O(r-l+1) → O(1)
전부 끝난 뒤: (할 일 없음)           →  누적합 한 번으로 복원    O(N)
합계:       O(N·Q)                  →  O(N + Q)               전부 최악 보장
```

이 문제는 **조회가 맨 끝에 딱 한 번**이라는 점이 전부입니다. 그 조건이 없으면 뒤에서 볼 세그먼트 트리 쪽이 이겨요 — 조건이 설계를 고른다는 것을 이 글에서 수치로 보게 됩니다.

## 출발점: 가장 순진한 방법부터

문제를 먼저 정확히 잡을게요.

```ts
function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[]
```

| 파라미터 | 의미 | 제약 |
|----------|------|------|
| `N` | 배열 길이(초기값은 모두 `0`) | $1 \leq N \leq 100{,}000$ |
| `updates` | 구간 갱신 목록 $[(l, r, v), \ldots]$ | $0 \leq l \leq r \leq N-1$, $-10{,}000 \leq v \leq 10{,}000$, 갱신 개수 $Q \leq 100{,}000$ |

**반환값**: 모든 갱신 `[l, r, v]`(각 인덱스 `i`에서 `l ≤ i ≤ r`일 때 `A[i] += v`)를 순서대로 적용한 뒤의 길이 `N` 배열입니다.

"구간에 값을 더하라"는 요청을 있는 그대로 읽으면, 가장 정직한 구현은 **그 구간을 순회하며 하나씩 더하는 것**입니다. 문제 정의 자체가 순회를 지시하는 형태라 이게 자연스러운 첫 시도예요.

```ts
function diffArrayRangeUpdateNaive(
  N: number,
  updates: Array<[number, number, number]>,
): number[] {
  const A = new Array<number>(N).fill(0);
  for (const [l, r, v] of updates) {
    for (let i = l; i <= r; i++) A[i] += v; // 구간을 매번 통째로 순회
  }
  return A;
}
```

작은 예로 비용을 세어 봅시다. `N=5`, `updates=[[1,3,2],[0,2,-1]]`이면 이렇습니다.

```text
갱신 (1,3,2):  i=1,2,3 방문 → 3칸
갱신 (0,2,-1): i=0,1,2 방문 → 3칸
총 방문 칸 수 = 3 + 3 = 6칸
```

이 정도는 아무렇지 않아 보이지만, 제약을 그대로 대입하면 얘기가 달라집니다. `N`과 `Q`가 각각 최대 `100,000`이고 각 갱신이 구간 전체(`l=0, r=N-1`)를 덮는 최악의 경우예요.

```text
갱신 1개당 최대 방문 = N = 100,000
갱신 개수            = Q = 100,000
총 방문 칸 수         = N × Q = 10,000,000,000  (10^10)
```

1초에 대략 `10^8`~`10^9`번 수준의 단순 연산을 처리할 수 있다고 잡아도 `10^10`은 시간 제한을 크게 넘깁니다. **목표 복잡도는 갱신 전체를 합쳐 `O(N+Q)`** 정도까지 낮춰야 해요.

낭비의 정체는 "같은 칸을 여러 갱신이 겹쳐서 방문할 때마다 매번 다시 써넣는다"는 점입니다. 겹치는 구간을 인덱스별로 다시 훑지 않고, **이 구간이 어디서 시작해서 어디서 끝나는지만 기억해 둘 수는 없을까** — 이게 다음 절의 출발점입니다.

### 같은 목표를 노리는 설계가 셋 더 있다 — 왜 하필 차분 배열인가

"구간 갱신을 모아 두었다가 마지막에 배열 전체를 돌려준다"는 목표를 노리는 설계는 여럿입니다. 실명으로 셋을 세우고, **같은 입력에서 배열 접근·비교 횟수를 실제로 세어** 대조했어요.

```text
순진한 순회         갱신마다 구간 [l, r] 을 통째로 훑으며 A[i] += v

이벤트 정렬 스윕     갱신 하나를 (l, +v)·(r+1, -v) 두 이벤트로 만들고,
                    이벤트를 인덱스 기준으로 정렬한 뒤 왼쪽부터 한 번 훑는다

세그먼트 트리 lazy   구간 갱신을 O(log N) 개의 노드에 "지연 표시"로 걸어 두고,
                    마지막에 루트부터 내려가며 잎마다 표시를 합산한다

차분 배열           이벤트를 정렬하지 않고 배열의 그 자리에 바로 꽂는다
```

`N = Q`로 두고 무작위 갱신을 준 실측입니다. 네 설계가 **같은 배열을 돌려준다는 것은 매번 대조해 확인**했고, 갈리는 것은 비용뿐이에요.

```text
N = Q          순진한 순회      차분 배열   이벤트 정렬 스윕   세그먼트 트리 lazy
 1,000          656,442         6,000         24,361            75,588
 4,000       10,678,202        24,000        113,389           373,023
16,000      171,460,060        96,000        517,399         1,788,591

성장률 r = C(4N)/C(N)   ← N을 4배로 키우면 비용이 몇 배가 되는가
 순진한 순회        16.27, 16.06     r ≈ 16 = 4²    →  O(N²)
 차분 배열           4.00,  4.00     r = 4 정확히    →  O(N)
 이벤트 정렬 스윕     4.65,  4.56     r > 4          →  O(N log N)
 세그먼트 트리 lazy   4.93,  4.79     r > 4          →  O(N log N)
```

**스윕이 지는 이유는 정렬 하나입니다.** 정렬 키가 무엇인지 보면 답이 나와요 — `0`부터 `N`까지의 정수 인덱스입니다.

```text
이벤트 정렬 스윕:  (1,+2) (4,-2) (0,-1) (3,+1)  → 비교 정렬 → 인덱스 순으로 훑기
차분 배열:         D[1]+=2  D[4]-=2  D[0]-=1  D[3]+=1   ← 그 자리에 바로 꽂는다
                       ↑ 키가 곧 배열 인덱스라 "어디 놓을지"를 비교로 찾을 필요가 없다
```

키가 그대로 자리 번호이면 비교로 순서를 알아낼 이유가 없습니다. 계수 정렬이 비교 정렬을 이기는 것과 같은 자리예요 — **차분 배열은 이벤트 스윕에서 정렬을 걷어낸 것**입니다.

**세그먼트 트리가 지는 이유는 다른 데 있습니다.** 구간 갱신 하나를 `O(log N)`개 노드로 쪼개 표시하는 그 일이, 이 문제에서는 값을 하나도 벌어 주지 못해요.

```text
세그먼트 트리가 쪼개는 값어치:  갱신 중간에 "지금 A[i] 얼마?" 조회가 끼어들 때
                              쪼개 둔 덕에 조회 하나를 O(log N)에 답한다

이 문제의 조회 패턴:           갱신 Q개를 다 받은 뒤 전체를 한 번 본다
                              → 쪼갠 것을 도로 합치기만 한다. 쪼갤 이유가 없다
```

그러니 세그먼트 트리는 **틀린 설계가 아니라 다른 문제의 설계**입니다. 갱신과 조회가 실시간으로 섞여 들어오는 패턴이면 위 표가 그대로 뒤집혀요.

**그리고 작은 입력에서는 순진한 순회가 이깁니다.** 차분 배열은 갱신이 몇 개든 복원에 `O(N)`을 무조건 내기 때문이에요. `N = 1,000`을 고정하고 갱신 개수만 늘려 보면 갈리는 지점이 보입니다.

```text
   Q       순진한 순회      차분 배열   싼 쪽
   1             102         2,004   순진한 순회
   2             460         2,008   순진한 순회
   4           1,862         2,016   순진한 순회
   8           5,246         2,032   차분 배열      ← 여기서 뒤집힌다
  16          10,884         2,064   차분 배열
  64          37,752         2,256   차분 배열
```

`Q`가 4에서 8 사이 어딘가에서 뒤집혀요. 제약이 `Q ≤ 100,000`이라 최악을 기준으로 고르면 차분 배열이지만, **"항상 더 빠르다"가 아니라 "이 제약에서 더 빠르다"** 라는 것이 정확한 진술입니다.

## 아이디어 자세히 들여다보기

### 구간을 경계 이벤트로 압축하기 — 수식과 그림

길이 `N+1`짜리 **차분 배열(difference array)** `D`를 하나 둡니다(끝에 여분 칸 하나를 더 두는 이유는 잠시 뒤에 나와요). 구간 갱신 `update(l, r, v)`를 배열 전체에 즉시 반영하는 대신, `D`에 딱 두 자리만 건드립니다.

$$D[l] \mathrel{+}= v, \qquad D[r+1] \mathrel{-}= v$$

그림으로 보면, 구간 `[1,3]`에 `+2`를 적용하는 갱신 하나가 이렇게 압축됩니다.

```text
목표: A = [0, 2, 2, 2, 0]   (인덱스 1,2,3에 +2)

D 이전: [0, 0, 0, 0, 0, 0]
         D[1] += 2 ─┐          D[4] -= 2 ─┐
                     ▼                     ▼
D 이후: [0, 2, 0, 0, -2, 0]
         ↑ "여기서부터 +2 시작"   ↑ "여기서부터 +2 취소"
```

잠깐, 확인 하나만 해 볼까요? 구간 `[2,4]`에 `+7`을 기록하려면 `D`의 어느 인덱스에 무엇을 더해야 할까요? — 정답은 `D[2] += 7`, `D[5] -= 7`입니다. 시작 인덱스에는 그대로 더하고, **끝난 다음 칸**에서 되돌려 놓는다는 규칙만 지키면 돼요.

**왜 하필 `D[r+1]`이어야 할까요?** `D[r]`에 `-v`를 기록하면 어떻게 되는지 같은 예로 대비해 봅시다.

```text
올바른 버전  D[r+1] -= v:  D = [0, 2, 0,  0, -2, 0]  →  A = [0, 2, 2, 2, 0]
잘못된 버전  D[r]   -= v:  D = [0, 2, 0, -2,  0, 0]  →  A = [0, 2, 2, 0, 0]
                                                                     ↑
                                                     인덱스 3(=r)이 잘려나감
```

`D[r]`에서 빼면 누적합이 인덱스 `r`에 도달하는 **바로 그 순간** `+v`가 취소되어 버려서, 정작 갱신 대상이어야 할 `r` 자신이 효과를 못 받습니다. "구간이 끝난 **다음** 칸에서 취소한다"는 `+1`이 반드시 필요한 이유가 이거예요.

이제 두 개의 갱신을 순서대로 적용해 실제 예시로 채워 봅시다. `N=5`, `updates=[[1,3,2],[0,2,-1]]`입니다.

| 단계 | 연산 | D |
|------|------|---|
| 초기 | — | `[0, 0, 0, 0, 0, 0]` |
| 갱신 (1,3,2) | `D[1]+=2`, `D[4]-=2` | `[0, 2, 0, 0, -2, 0]` |
| 갱신 (0,2,-1) | `D[0]+=-1`, `D[3]-=-1` | `[-1, 2, 0, 1, -2, 0]` |

두 갱신 모두 `D`에서 딱 두 자리씩만 건드렸을 뿐, 배열 전체를 순회하지 않았다는 점을 확인하세요.

### 단서를 설명해 주는 이론 — 이산 미분·적분과 선형성(linearity)

방금 만든 `D`가 왜 하필 "시작에서 `+v`, 끝+1에서 `-v`" 형태인지, 그리고 여러 갱신을 왜 그냥 더하기만 해도 되는지를 일반적인 언어로 승격해 봅시다. 배열 `A`에 대해 **이산 미분(discrete derivative)**과 그 역연산인 **이산 적분(prefix sum)**을 정의합니다.

$$\Delta A[i] = A[i] - A[i-1] \quad (A[-1] \equiv 0), \qquad A[i] = \sum_{k=0}^{i} \Delta A[k]$$

구간 `[l,r]`에 `v`를 더하는 갱신 하나는, 결과적으로 "`l`부터 `r`까지는 `v`, 그 외에는 `0`"인 계단 함수를 `A`에 더하는 일입니다. 이 계단 함수를 직접 미분해 보면 값이 바뀌는 지점 딱 두 곳에서만 `0`이 아닌 값이 나와요.

```text
계단 함수 (구간 [1,3] 에 +2):     0   2   2   2   0
                                  ↑           ↑
Δ(계단 함수):                  0  +2   0   0  -2      ← i=1 에서 뛰어오르고
                                  ↑           ↑         i=4 에서 떨어진다
                              D[1]=+2      D[4]=-2

즉 D 는 우리가 원하는 결과 배열의 이산 미분 그 자체다
```

`Δ`와 그 역연산인 누적합은 **선형(linear) 연산자**입니다.

$$\Delta(A_1 + A_2) = \Delta A_1 + \Delta A_2$$

즉 여러 갱신이 만드는 각각의 "이상적인 결과 배열"을 다 더한 게 최종 `A`라면, 그 미분인 `D`도 각 갱신의 `D`를 그냥 더한 것과 같습니다.

```text
갱신 (1,3,+2) 의 D :  [ 0,  2, 0, 0, -2, 0]
갱신 (0,2,-1) 의 D :  [-1,  0, 0, 1,  0, 0]
                       ─────────────────────  칸마다 그냥 더한다
합                  :  [-1,  2, 0, 1, -2, 0]   ← 순서를 바꿔 더해도 같다
```

이것이 `Q`개의 갱신을 처리할 때 순서와 상관없이 `D[l] += v`, `D[r+1] -= v`를 그때그때 누적해도 되는 이유예요 — **선형성에 의한 중첩(superposition)**이 갱신 순서 교환을 정당화합니다. 이 성질은 바로 다음 절의 귀납 증명에서 다시 씁니다.

### 왜 모순 없이 작동하는가

갱신을 하나씩 적용해 가는 과정을 갱신 개수 `k`에 대한 귀납법으로 증명합니다.

**기저(k=0)**: 갱신이 없으면 `D`는 전부 `0`이고, 복원한 `A`도 전부 `0`입니다. 문제 정의상 "갱신 없음 → 전부 0"과 정확히 일치해요.

**귀납 가정**: `k`개의 갱신을 처리한 뒤 `D`의 누적합이 정확한 `A_k`(그 `k`개 갱신만 반영된 배열)를 만든다고 합시다.

**귀납 단계**: `(k+1)`번째 갱신 `(l,r,v)`를 처리하면 `D[l] += v`, `D[r+1] -= v`가 추가됩니다. 앞 절의 선형성에 의해 새 누적합은 "기존 누적합" + "이 갱신 하나만 있었을 때의 누적합"이고, 뒤쪽은 인덱스 `i`에 대해 아래 세 경우로 갈려요.

| 인덱스 `i` | `D[l]`의 `+v` | `D[r+1]`의 `-v` | 이 갱신의 효과 | 원하는 값 |
| --- | --- | --- | --- | --- |
| $i < l$ | 아직 안 포함 | 아직 안 포함 | $0$ | $0$ (구간 밖) |
| $l \leq i \leq r$ | 포함됨 | 아직 안 포함 | $+v$ | $+v$ (구간 안) |
| $i > r$ | 포함됨 | 포함됨 | $0$ | $0$ (구간 밖) |

`l ≤ r`이 항상 성립하므로(제약 조건), 임의의 인덱스 `i`는 이 세 경우 중 정확히 하나에만 속합니다 — 빠지는 경우가 없어요. 따라서 `A_{k+1}[i] = A_k[i] + v·1[l≤i≤r]`이 정확히 성립하고, 귀납이 닫히므로 `Q`개 갱신 후 최종 `A[i] = Σ(l≤i≤r인 갱신들의 v)`가 성립합니다.

**여기서 헷갈리기 쉬운 포인트는 `D[r+1] -= v`를 깜빡 빠뜨리는 것입니다.** 대표 예시 `N=5, updates=[[1,3,2],[0,2,-1]]`에서 첫 번째 갱신만 이 이벤트를 빠뜨렸다고 해 봅시다.

```text
빠뜨린 D: D[1]+=2 (O), D[4]-=2 (누락!)
          D[0]+=-1, D[3]+=1 은 정상 기록
        → D = [-1, 2, 0, 1, 0, 0]

복원하면: A = [-1, 1, 1, 2, 2]
                            ↑
             원래는 0이어야 할 인덱스 4가 2로 "새어나감"

올바른 A: [-1, 1, 1, 2, 0]
```

`+2`라는 효과가 `r=3`을 넘어서도 계속 살아남아 인덱스 4까지 오염시킵니다. `D[r+1] -= v`는 장식이 아니라 "여기서부터는 효과가 끝난다"는 취소 신호 그 자체예요.

엣지 케이스도 불변식 위에서 짚어 둡니다.

```text
updates = []                   → D 전부 0 → A 전부 0                          (정상)
N = 1, updates=[[0,0,10000]]   → D=[10000, -10000], A=[10000]                  (경계 최대값)
r = N-1인 갱신(전체 구간 갱신)  → D[N]에 -v가 기록되지만 복원 루프는 i<N까지만  (D[N]은 안전 버퍼)
같은 구간을 겹쳐 갱신          → 여러 갱신의 D 이벤트가 선형적으로 합산됨      (교환법칙)
```

## 아이디어를 코드로 옮기기

```ts
function diffArrayRangeUpdate(
  N: number,
  updates: Array<[number, number, number]>,
): number[] {
  const D = new Array<number>(N + 1).fill(0);
  for (const [l, r, v] of updates) { // ① 처리할 갱신이 남았는가
    D[l] += v;                       // ② 시작 이벤트
    D[r + 1] -= v;                   // ③ 취소 이벤트
  }

  const A = new Array<number>(N);
  let running = 0;
  for (let i = 0; i < N; i++) {      // ④ 복원할 칸이 남았는가
    running += D[i];
    A[i] = running;
  }
  return A;
}
```

이 절은 코드를 **정적으로** 읽습니다 — 초기값, 배열 크기, 두 줄의 순서. 실제로 무슨 값이 만들어지는지는 다음 절이 끝까지 보여 줄게요.

```text
D 의 크기 = N + 1     N 으로 잡으면 r = N-1 인 갱신에서 D[N] 접근이 범위를 벗어난다
                      ③ 이 쓰는 최대 인덱스가 (N-1)+1 = N 이기 때문이다

②③ 은 짝이다         ② 만 있으면 효과가 배열 끝까지 새어 나간다(앞 절 실측 참조)

④ 안의 두 줄 순서     running += D[i] 가 A[i] = running 보다 먼저다.
                      뒤집으면 인덱스 i 자신의 경계 이벤트가 A[i] 에 안 실린다
```

**가장 실수가 잦은 줄은 `D[r + 1] -= v;`입니다.** 이 줄을 빠뜨려도 예외가 던져지지 않고 배열 길이도 그대로라, 눈으로 결과를 대조하지 않으면 알아채기 어려워요.

두 번째로 잦은 것이 ④ 안의 두 줄 순서입니다. 뒤집으면 실제로 이런 값이 나와요.

```text
N = 5, updates = [[1,3,2], [0,2,-1]]      D = [-1, 2, 0, 1, -2, 0]

올바른 순서  running += D[i];  A[i] = running;   →  A = [-1,  1, 1, 2, 0]
뒤집은 순서  A[i] = running;   running += D[i];  →  A = [ 0, -1, 1, 1, 2]
                                                        ↑ 올바른 답을 한 칸 오른쪽으로
                                                          밀고 앞에 0 을 끼운 배열이다
```

패턴이 정확한 것이 이 실수의 함정이에요. `A[i]`에 `i-1`까지의 누적합이 실려서 배열 전체가 한 칸씩 밀리는데, 길이도 맞고 값도 전부 "본 적 있는 숫자"라 눈으로는 안 걸립니다.

## 코드를 한 번 끝까지 굴려 보기

위 코드를 고정 입력 `N = 5`, `updates = [[1,3,2], [0,2,-1]]`에 넣고 처음부터 끝까지 굴려 봅니다. 아래 `실행 시각화` 절의 시뮬레이션과 **같은 입력**이라 프레임과 단계가 대응해요.

```text
D 의 인덱스:  0  1  2  3  4  5      ← 길이 N+1 = 6, 마지막 칸은 안전 버퍼
A 의 인덱스:  0  1  2  3  4         ← 길이 N = 5
```

**T1 — 초기화.** 아직 어떤 루프에도 들어가기 전입니다.

```text
T1   D = [0, 0, 0, 0, 0, 0]   A = (미할당)   running = 0
```

**T2 — 첫 갱신 `(1, 3, +2)`.** ① 갱신이 남아 있어 참이므로 루프에 들어가고, ②③이 한 번씩 실행됩니다.

```text
T2   ① 남은 갱신 있음 → 참, 진입
     ② D[1] += 2    → D[1]: 0 → 2      "인덱스 1부터 +2 시작"
     ③ D[4] -= 2    → D[4]: 0 → -2     r+1 = 3+1 = 4, "인덱스 4부터 취소"
     D = [0, 2, 0, 0, -2, 0]
```

**T3 — 둘째 갱신 `(0, 2, -1)`.** ①이 다시 참이라 같은 자리를 한 번 더 밟아요. `v`가 음수라 ③은 **빼기가 아니라 더하기**가 됩니다.

```text
T3   ① 남은 갱신 있음 → 참, 진입
     ② D[0] += (-1)  → D[0]:  0 → -1
     ③ D[3] -= (-1)  → D[3]:  0 →  1    r+1 = 2+1 = 3, 부호가 뒤집혀 +1 이 된다
     D = [-1, 2, 0, 1, -2, 0]
```

`D`의 0이 아닌 칸이 넷입니다. 갱신 두 개가 경계 이벤트 네 개로 압축된 것이고, 배열 전체를 한 번도 훑지 않았어요.

**T4 — ① 거짓, 기록 루프 탈출.** 남은 갱신이 없어 조건이 처음으로 거짓이 됩니다.

```text
T4   ① 남은 갱신 있음 → 거짓, 탈출
     D = [-1, 2, 0, 1, -2, 0]    ← 이 상태가 곧 결과 배열의 이산 미분이다
     A = new Array(5), running = 0 으로 복원 준비
```

**T5 — ④ 복원 시작, `i = 0`.** ④ `0 < 5`가 참이라 진입하고, `running`이 `D`의 접두사합을 들고 전진합니다.

```text
T5   ④ 0 < 5 → 참
     running += D[0](-1)  →  running = -1      A[0] = -1
     A = [-1]
```

**T6 — `i = 1`. 시작 이벤트가 실리는 자리입니다.**

```text
T6   ④ 1 < 5 → 참
     running += D[1](2)   →  running = 1       A[1] = 1
     A = [-1, 1]          ← T2의 "+2 시작"이 여기서 반영된다
```

**T7 — `i = 2`. 아무 이벤트도 없는 칸입니다.**

```text
T7   ④ 2 < 5 → 참
     running += D[2](0)   →  running = 1       A[2] = 1
     A = [-1, 1, 1]       ← 경계가 아닌 칸은 앞 값을 그대로 물려받는다
```

**T8 — `i = 3`. T3이 기록한 `+1`이 실립니다.**

```text
T8   ④ 3 < 5 → 참
     running += D[3](1)   →  running = 2       A[3] = 2
     A = [-1, 1, 1, 2]    ← 둘째 갱신의 구간 [0,2]가 여기서 끝난다
```

**T9 — `i = 4`. 첫 갱신의 취소 이벤트가 실려 값이 0으로 돌아옵니다.**

```text
T9   ④ 4 < 5 → 참
     running += D[4](-2)  →  running = 0       A[4] = 0
     A = [-1, 1, 1, 2, 0] ← T2의 "+2 취소"가 여기서 발동한다
```

**T10 — ④ 거짓, 반환.**

```text
T10  ④ 5 < 5 → 거짓, 탈출
     반환 A = [-1, 1, 1, 2, 0]

     검산  인덱스 0: 갱신(0,2,-1)만 덮음 → -1        인덱스 1,2: 둘 다 덮음 → 2-1 = 1
           인덱스 3: 갱신(1,3,2)만 덮음 → 2          인덱스 4: 어느 갱신도 안 덮음 → 0  ✓
```

네 자리 ①②③④를 참·거짓 양쪽으로 모두 밟았습니다 — ①은 T2·T3에서 참이고 T4에서 거짓, ②③은 T2·T3에서 실행됐고, ④는 T5~T9에서 참이고 T10에서 거짓입니다. 반환값 `[-1, 1, 1, 2, 0]`은 아래 시뮬레이션의 마지막 프레임과 같아요.

## 더 빠르게 만들 단서 찾기

복원 구간 **T5부터 T9까지**를 나란히 놓고 보면, 배열 두 개가 같은 걸음으로 움직입니다.

```text
      D 에서 읽기        A 에 쓰기        D[i] 를 다시 읽는가?
T5    D[0] = -1          A[0] = -1        아니오
T6    D[1] =  2          A[1] =  1        아니오
T7    D[2] =  0          A[2] =  1        아니오
T8    D[3] =  1          A[3] =  2        아니오
T9    D[4] = -2          A[4] =  0        아니오
                          ↑ 읽고 나면 D[i] 는 두 번 다시 안 쓰인다
```

**칸 하나를 두 배열에 나눠 들고 있어요.** `D[i]`는 `running`에 합쳐지는 순간 임무가 끝나는데, 그 자리를 계속 붙들고 있고 옆에 `A`를 새로 하나 더 만듭니다.

여기서 짚어 둘 것이 하나 있습니다 — **이 단서가 가리키는 것은 시간이 아니라 공간입니다.** 기록이 `2Q`번, 복원이 `N`번이고 그 아래로는 내려갈 수 없거든요(그 논증은 최적화 절 끝에서 합니다). 줄일 수 있는 것은 들고 있는 배열의 개수예요.

## 단서를 최적화로 연결하기

`A`를 없애고 `D` 자리에 결과를 덮어쓰면 됩니다. T5~T9에서 확인한 *"읽고 나면 다시 안 읽는다"* 가 덮어쓰기를 안전하게 만들어요 — `D[i]`를 `A[i]` 값으로 갈아 끼워도 뒤 단계가 원래 `D[i]`를 찾지 않습니다.

```text
before                          after

T5   D[0] = -1  →  A[0] = -1    T5   running += D[0](-1) → D[0] = -1
T6   D[1] =  2  →  A[1] =  1    T6   running += D[1]( 2) → D[1] =  1
     ...                             ...
                                     ↑ 읽은 값을 running 에 합친 직후 그 자리에 덮어쓴다

배열 둘: D(N+1칸) + A(N칸)       배열 하나: D(N+1칸)
```

**순서가 이 최적화의 전부입니다.** `running += D[i]`를 먼저 하고 `D[i] = running`을 나중에 해야 해요. 뒤집으면 아직 안 읽은 값을 지워 버립니다.

## 최적화 코드

바뀌는 곳은 **복원 루프 하나**입니다.

```ts
  const D = new Array<number>(N + 1).fill(0);
  for (const [l, r, v] of updates) { // ① 처리할 갱신이 남았는가
    D[l] += v;                       // ② 시작 이벤트
    D[r + 1] -= v;                   // ③ 취소 이벤트
  }

  let running = 0;
  for (let i = 0; i < N; i++) {      // ④ 복원할 칸이 남았는가
    running += D[i];                 // 먼저 읽어서 합치고
    D[i] = running;                  // 그 자리에 덮어쓴다
  }
  D.pop();                           // 여분 칸 하나를 버려 길이를 N 으로
  return D;
```

트레이스로 대조하면 **T5~T9의 오른쪽 열이 `A[i] = …`에서 `D[i] = …`로 바뀌고, T4에서 하던 `A` 할당이 통째로 사라집니다.** 단계 수도 값도 그대로예요.

| 항목 | 보조 배열 판 | 제자리 판 |
| --- | --- | --- |
| 트레이스 단계 | T1 ~ T10 | 같음 |
| 배열 접근 (N=Q=16,000) | 96,000회 | **96,000회 — 한 톨도 안 줄었다** |
| 할당 칸 (N=Q=16,000) | 32,001칸 | **16,001칸 — 절반** |
| 반환값 | `[-1, 1, 1, 2, 0]` | 같음 |

시간은 그대로고 공간만 절반입니다. 실측 표의 접근 횟수가 정확히 같다는 것이 그 증거예요 — `A[i] = running`이 `D[i] = running`으로 이름만 바뀐 쓰기라서 그렇습니다.

**가장 중요한 줄은 `D.pop()`입니다.** 이 줄을 빠뜨리면 예외도 안 나고 값도 전부 맞는데, 반환 배열의 길이가 `N+1`이 돼요.

```text
D.pop() 있음:  [-1, 1, 1, 2, 0]        길이 5 = N     ✓
D.pop() 없음:  [-1, 1, 1, 2, 0, 0]     길이 6 = N+1   ← 마지막 0 은 안전 버퍼의 잔해다
```

값이 `0`이라 눈으로는 "맞는 답에 0 하나 붙은 것"처럼 보이지만, 길이를 검사하는 테스트에서만 걸립니다.

> **여분 칸은 쓰기용이지 결과가 아니다.**

**더 최적화할 여지가 있을까요? 없습니다** — 시간 쪽은 이미 하한에 닿아 있어요.

```text
하한 논증
  갱신 Q개를 읽기라도 해야 한다            →  Ω(Q)
  길이 N 배열을 출력이라도 해야 한다        →  Ω(N)
  합                                       →  Ω(N + Q)

달성한 것
  기록 2Q회 + 복원 N회 + 할당·초기화 N+1칸  →  O(N + Q)      ← 하한에 맞닿음
  보장 종류는 전부 최악(worst case)이다 — 해시도 상환 분석도 확률도 쓰지 않는다
```

다만 **문제 패턴이 달라지면 얘기가 다릅니다.** 앞의 경쟁 설계 절에서 세그먼트 트리가 `O(N log N)`으로 진 이유가 "조회가 맨 끝에 한 번뿐"이었는데, 갱신과 조회가 실시간으로 섞이면 그 전제가 깨져요.

```text
이 문제:        갱신 Q개 → (전부 끝난 뒤) 전체 조회 1회      차분 배열이 이긴다
섞이는 패턴:    갱신 → 조회 → 갱신 → 조회 → …               차분 배열은 조회마다 O(N)
                                                            Fenwick Tree / 세그먼트 트리가 이긴다
```

차분 배열이 이기는 조건은 **"갱신을 다 모은 뒤 한 번만 본다"** 하나입니다. 그 조건이 이 문제의 정의에 박혀 있어서 이 설계를 고른 것이고, 조건이 바뀌면 고르는 것도 바뀌어요.

## 흐름 한눈에 보기

```mermaid
flowchart TD
    A(["시작"]) --> B["D = [0 x (N+1)]"]
    B --> C{"다음 갱신 l,r,v 있음?"}
    C -- Yes --> D["D[l] += v / D[r+1] -= v"]
    D --> C
    C -- No --> E["running = 0 / i = 0"]
    E --> F{"i < N?"}

    F -- No --> I(["return A"])
```

**핵심 불변식**: 복원 루프 진입 시점에 `running` $= \sum_{k=0}^{i-1} D[k]$, 즉 인덱스 `i-1`까지의 모든 갱신 효과가 이미 합산된 값이며, 루프가 끝난 뒤 `A[i]` $= \sum_{\text{갱신}(l,r,v):\, l \leq i \leq r} v$가 정확히 성립합니다.
