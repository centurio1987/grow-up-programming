# 이웃하지 않은 칸의 최대 합 — 칸 i 를 고른 답이 두 칸 앞의 답에서 나오는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 칸을 고르는 방법을
전부 만들어 보는 데서 출발해 앞의 두 답만 들고 가는 방법까지 가고, 그 방법을 단계마다 값으로 푼 뒤, 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

음이 아닌 정수 배열에서 칸을 몇 개 골라 그 값을 더하되, **이웃한 두 칸은 함께 고르지 않는** 과제입니다.
고른 합 가운데 가장 큰 것이 답이에요. 한 칸도 안 고르는 **빈 선택도 후보**라서 답은 언제나 0 이상이고,
배열이 비어 있으면 답이 0 입니다. 배열 `A = [2 7 9 3 1 5]` 에서 고를 수 있는 선택 몇 가지를 적어 보면
이렇습니다.

<!--proof:concept-examples-->
| 고른 칸 | 그 칸의 값 | 합 | 비고 |
| --- | --- | ---: | --- |
| {0, 2, 5} | 2 · 9 · 5 | 16 | 가장 크다 |
| {1, 3, 5} | 7 · 3 · 5 | 15 |  |
| {2, 5} | 9 · 5 | 14 |  |
| {} | — | 0 |  |
| {2, 3} | 9 · 3 | — | 칸 2 와 칸 3 이 이웃이라 고를 수 없다 |

이웃한 두 칸을 함께 담지 않는 선택은 빈 선택까지 21 가지이고, 그 가운데 가장 큰 합은 16 입니다. 정본 houseRobber([2 7 9 3 1 5]) 가 낸 값도 16 입니다.

<!--/proof-->

선택을 하나씩 만들어 보는 것으로는 끝나지 않습니다. 칸마다 「고른다」와 「안 고른다」 둘이라, 칸을 고르는
방법이 배열 길이에 대해 2 의 거듭제곱으로 늘어나요. 이웃한 두 칸을 걸러 내도 크게 줄지 않습니다.

<!--proof:concept-count-->
| 배열 길이 N | 칸을 고르는 방법 | 이웃하지 않게 고르는 방법 | 구한 방법 |
| --- | ---: | ---: | --- |
| 6 | 64 | 21 | 선택을 모두 만들어 셌다 |
| 100,000 | 30,103 자리 수 | 20,899 자리 수 | 2^N 과 F(N+2) 로 냈다 |

N = 6 에서 센 21 이 F(8) = 21 과 같았습니다.

<!--/proof-->

그래서 선택을 만들지 않고 **앞부분마다 답 하나씩**을 적어 갑니다. 칸 0 부터 칸 `i` 까지만 놓고 본 답을
**칸 `i` 까지의 최대 합**이라고 부르고 `dp[i]` 로 적어요. 이 글은 끝까지 이 이름 하나로 부릅니다. `A` 아래에
칸마다의 `dp` 를 적으면 이렇습니다.

<!--fig:concept-rows-->
![A 아래에 놓은 dp 줄 — 마지막 칸 dp[5] = 16 이 답](./figs/concept-rows.svg)

진하게 그린 `A` 의 세 칸이 답이 고른 칸이고, 강조한 `dp[5] = 16` 이 답입니다. `dp[5]` 는 배열 전체를 놓고 본
답이라, 따로 최댓값을 모을 필요 없이 **마지막 칸의 `dp` 가 곧 답**이에요. `dp` 줄은 왼쪽에서 오른쪽으로 한
번도 작아지지 않는다는 것도 봐 주세요. 놓고 보는 칸이 늘면 고를 수 있는 선택도 늘기 때문입니다.

칸 `i` 까지의 선택은 칸 `i` 를 고르는지로 둘로 갈립니다. 칸 `i` 를 고르면 이웃인 칸 `i−1` 이 빠지므로, 이어받을
답이 한 칸 앞이 아니라 **두 칸 앞**이 돼요.

| 갈래 | 칸 `i` 를 | 그 갈래에서 가장 큰 합 |
| --- | --- | --- |
| 건너뛴다 | 안 고른다 | `dp[i−1]` |
| 고른다 | 고르고, 칸 `i−1` 은 뺀다 | `dp[i−2] + A[i]` |

둘 중 큰 쪽이 `dp[i]` 입니다. 칸 2 에서 두 갈래가 어떻게 갈리는지 값으로 보면 두 칸 앞이어야 하는 까닭이
보여요.

<!--proof:concept-two-back-->
| 이어받는 답 | 그 답의 선택 | 칸 2 를 더한 합 | 이웃 |
| --- | --- | --- | --- |
| dp[1] = 7 | {1} | 7 + 9 = 16 | 칸 1 과 칸 2 가 이웃이라 어긋난다 |
| dp[0] = 2 | {0} | 2 + 9 = 11 | 칸 0 과 칸 2 라 지킨다 |

정본의 dp[2] 는 11 이고, 그 선택은 {0, 2} 입니다.

<!--/proof-->

`dp[i]` 하나를 정하는 데 필요한 과거가 `dp[i−1]` 과 `dp[i−2]` 둘뿐이라, 배열을 한 번 지나가며 **마지막 두
칸의 값만** 들고 가면 됩니다. 비용을 결과만 적으면 시간 `O(N)`, 추가 메모리 `O(1)` 이에요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **부분집합이 무엇인지.** 배열의 칸 중 일부를 골라 담은 것이고, **칸이 이어져 있을 필요가 없습니다.** 칸을
  건너뛰지 않고 이어서 고르는 부분 배열과는 다른 것이에요.
- **이웃이라는 말이 무엇을 막는지.** 고른 두 번호 `a` 와 `b` 는 `|a − b| ≥ 2` 여야 합니다. 한 칸 떨어진 둘은
  안 되고 두 칸 떨어진 둘은 됩니다.
- **배열의 칸을 인덱스로 읽는 비용이 `O(1)`** 이라는 것. 칸 하나를 읽는 데 드는 일이 배열 길이와 상관없습니다.
- **칸마다 직전 결과를 이어받아 답을 정하는 방법.** 흐릿하면 [`kadane`](../kadane/kadane-guide.md) 을 먼저
  봅니다 — 거기서는 이어받는 값이 한 칸 앞 하나인데, 이 글에서는 두 칸 앞까지 둘이에요.
- **작은 입력의 답을 칸에 적어 두고 큰 입력의 답을 그 칸들에서 만드는 방법(동적 계획법).** 칸을 모은 것을 DP
  테이블이라고 부르고, [`coinChangeWays`](../../dp/coinChangeWays/coinChangeWays-guide.md) 가 그 구조를 처음부터
  다룹니다. 이 글의 `dp` 는 칸이 한 줄뿐인 DP 테이블이에요.

고른 칸의 합을 최대로 하는 과제는 여럿이고, 이 글은 그중 **이웃한 두 칸을 함께 못 고르는** 경우를 다룹니다.

| 과제 | 고르는 것 | 다루는 글 |
| --- | --- | --- |
| 이웃하지 않은 칸의 최대 합 | 이웃하지 않은 칸 여럿 | 이 글 |
| 최대 부분 배열 합 | 이어진 구간 하나 | [`kadane`](../kadane/kadane-guide.md) |
| 나무 모양으로 놓인 칸의 최대 합 | 부모와 자식을 함께 안 고른 칸 여럿 | [`treeMaxIndependentSet`](../../dp/treeMaxIndependentSet/treeMaxIndependentSet-guide.md) |

### 아이디어를 떠올리는 과정 — 부분집합 다 만들기에서 두 값 이어받기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 칸마다의 값을 받아서, 이웃한 두 칸을
함께 고르지 않은 선택의 합 가운데 최댓값을 돌려줍니다.

```ts
function houseRobber(nums: number[]): number;
```

- 입력: 음이 아닌 정수 배열 `nums`. 길이는 0 일 수도 있습니다.
- 출력: 이웃한 두 칸을 함께 고르지 않고 고른 값의 합 가운데 최댓값. 한 칸도 안 골라도 되므로 0 이상입니다.
- 규모: 배열 길이 `N` 이 100,000 까지, 값은 0 이상 10,000 이하입니다. 비용은 흔한 채점 환경의 예산인 1 초에
  대어 잽니다.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 배열의 길이 | `0 ≤ N ≤ 100,000` |
| `A` | 입력 배열. `A[i]` 가 칸 `i` 의 값 | `0 ≤ A[i] ≤ 10,000` |
| `i` | 지금 보고 있는 칸 번호 | `0 ≤ i ≤ N−1` |
| `S` | 고른 칸의 번호를 담은 집합 하나 | 어느 두 번호도 이웃이 아니다 |
| `dp[i]` | 칸 `i` 까지의 최대 합 — 칸 0 부터 칸 `i` 까지에서 고른 선택의 합 가운데 최댓값 | 칸마다 하나. 칸이 없을 때의 답 `dp[−1]` 은 0 |
| `prev` | 코드가 들고 있는 `dp[i−1]` | 값 하나 |
| `cur` | 코드가 들고 있는 `dp[i]` | 끝나면 이 값이 답이다 |

`dp` 는 칸마다 하나씩이지만, 절차가 실제로 드는 것은 마지막 두 칸뿐이라 그 둘을 `prev` 와 `cur` 로 적어요.
식의 `A` 는 코드에서는 `nums` 로 적습니다.

가장 먼저 떠오르는 방법은 선택을 전부 만들어 보는 것입니다. 선택 하나가 부분집합 하나로 정해지니, 부분집합을
전부 만들어 이웃이 섞였는지 보고 합의 최댓값을 갱신해요.

```ts
let best = 0;
for (let mask = 0; mask < 1 << nums.length; mask++) {
  let sum = 0;
  let ok = true;
  for (let i = 0; i < nums.length; i++) {
    if ((mask & (1 << i)) === 0) continue; // 이 칸을 안 골랐다
    if (i > 0 && (mask & (1 << (i - 1))) !== 0) ok = false; // 옆 칸도 골랐다
    sum += nums[i] as number;
  }
  if (ok) best = Math.max(best, sum);
}
```

이 방법은 답을 틀리지 않습니다. 하는 일의 양은 부분집합의 개수를 따라가는데, 부분집합 하나마다 칸을 `N` 번
검사하므로 검사 횟수가 `N × 2^N` 이에요. 규칙으로 만든 배열에서 실제로 세어 보면 이렇습니다.

<!--proof:origin-cost-->
| N | 부분집합의 개수 | 칸을 검사한 횟수 | N × 2^N | 구한 방법 |
| ---: | ---: | ---: | ---: | --- |
| 6 | 64 | 384 | 384 | 실행해서 셌다 |
| 12 | 4,096 | 49,152 | 49,152 | 실행해서 셌다 |
| 18 | 262,144 | 4,718,592 | 4,718,592 | 실행해서 셌다 |
| 100,000 | 30,103 자리 수 | 30,108 자리 수 | 30,108 자리 수 | N × 2^N 으로 냈다 |

실행해서 센 3 규모에서 검사 횟수가 N × 2^N 과 정확히 같았습니다. 초당 1 억 번으로 잡으면 N = 100,000 에서 걸리는 초가 30,100 자리 수입니다.

<!--/proof-->

`N` 이 100,000 이면 걸리는 초의 자릿수가 3 만입니다. 예산 1 초와는 비교할 수도 없어요. 그러면 이 안에서
무엇이 되풀이되는지 봅시다. 마지막 칸을 고르는지로 선택을 가르면, 갈래마다 **더 짧은 앞부분의 같은 물음**이
나옵니다. 앞 네 칸 `[2 7 9 3]` 에서 물음을 차례로 펴면 이렇습니다.

<!--proof:origin-split-->
| 물음 | 건너뛴 갈래 | 고른 갈래 |
| --- | --- | --- |
| 칸 3 까지의 답 | 칸 2 까지의 답 | 칸 1 까지의 답 + 3 |
| 칸 2 까지의 답 | 칸 1 까지의 답 | 칸 0 까지의 답 + 9 |
| 칸 1 까지의 답 | 칸 0 까지의 답 | 칸이 없을 때의 답 + 7 |
| 칸 0 까지의 답 | 칸이 없을 때의 답 | 칸이 없을 때의 답 + 2 |

오른쪽 두 열에 나오는 물음이 모두 왼쪽 열의 물음 가운데 하나입니다. 물음의 종류는 칸 수보다 하나 많을 뿐인데,
갈래를 끝까지 다 펴면 같은 물음을 여러 번 부르게 돼요. 몇 번씩 부르는지 세었습니다.

<!--proof:origin-repeat-->
| 물음 | 부른 횟수 |
| --- | ---: |
| 칸 0 까지의 답 | 3 |
| 칸 1 까지의 답 | 2 |
| 칸 2 까지의 답 | 1 |
| 칸 3 까지의 답 | 1 |
| 칸이 없을 때의 답 | 8 |

[2 7 9 3] 에서 물음의 종류 5 개를 15 번 불렀습니다. 규모를 키우며 같은 방식으로 세면 이렇습니다.

| N | 물음의 종류 | 부른 횟수 |
| ---: | ---: | ---: |
| 6 | 7 | 41 |
| 12 | 13 | 753 |
| 18 | 19 | 13,529 |
| 24 | 25 | 242,785 |

물음의 종류는 칸 수보다 하나 많을 뿐인데, 부른 횟수는 그보다 훨씬 빨리 늘어납니다.

<!--/proof-->

그래서 두 번째 방식을 세웁니다. 물음마다 답을 **한 번씩만** 정해 적어 두고, 칸 0 부터 차례로 채우는 것이에요.
칸 `i` 의 답은 앞의 두 답만 쓰므로, 앞의 두 답을 이어받아 덧셈 한 번과 비교 한 번으로 정합니다. 같은 배열을 두
방식으로 처리하고 기본 연산(덧셈과 비교)을 나란히 세었습니다.

<!--proof:cost-two-ways-->
| 방식 | 덧셈 (N = 6) | 비교 (N = 6) | 기본 연산 (N = 6) | 기본 연산 (N = 100,000) |
| --- | ---: | ---: | ---: | ---: |
| 부분집합을 다 만들어 이웃이 섞인 것을 버린다 | 192 | 608 | 800 | 30,108 자리 수 |
| 칸마다 앞의 두 답을 이어받는다 | 5 | 5 | 10 | 199,998 |

두 방식 모두 답은 16 입니다. 아래 방식은 칸 하나에 덧셈 1 번과 비교 1 번을 씁니다.

<!--/proof-->

800 대 10 입니다. 여기서 관찰할 것은 하나예요. 아래 방식은 **칸 하나를 처리하는 비용이 고정**이라, 배열이
길어져도 칸 수만큼만 늘어납니다. 위 방식은 부분집합의 개수를 따라 늘어나요.

그 관찰을 이름으로 세우기 전에, 더 단순한 후보부터 시험해 봅시다. 첫째는 「짝수 번째 칸만 고른 합과 홀수 번째
칸만 고른 합 중 큰 쪽」이에요. 한 칸 걸러 고르면 이웃이 절대 생기지 않으니까요.

```ts
let even = 0;
let odd = 0;
for (let i = 0; i < nums.length; i++) {
  if (i % 2 === 0) even += nums[i] as number;
  else odd += nums[i] as number;
}
const answer = Math.max(even, odd);
```

이 후보를 네 입력에 실제로 실행하면 두 줄이 틀립니다.

<!--proof:origin-alternating-->
| 입력 | 정본이 낸 답 | 한 칸 걸러 고른 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 [2 7 9 3 1 5] | 16 | 15 | 틀리다 |
| [2 1 1 2] | 4 | 3 | 틀리다 |
| [1 3 1 3 1 3] | 9 | 9 | 같다 |
| [1 2 3 1] | 4 | 4 | 같다 |

틀린 두 줄은 답이 고른 칸의 번호가 짝수와 홀수에 섞인 입력입니다.

<!--/proof-->

`[2 1 1 2]` 가 이 후보의 문제를 가장 짧게 보입니다. 답이 고른 칸은 0 과 3 인데, 하나는 짝수 번호이고 하나는
홀수 번호라 한쪽 무리만 골라서는 만들 수 없어요. **두 칸 넘게 걸러 고르는 선택**을 이 후보가 버린 것입니다.
둘째 후보는 「값이 큰 칸부터 보면서 양옆이 비어 있을 때만 고른다」예요.

```ts
const order = [...nums.keys()].sort((a, b) => (nums[b] as number) - (nums[a] as number));
const taken = new Array<boolean>(nums.length).fill(false);
let sum = 0;
for (const i of order) {
  if (taken[i - 1] === true || taken[i + 1] === true) continue; // 옆 칸이 이미 골라졌다
  taken[i] = true;
  sum += nums[i] as number;
}
```

<!--proof:origin-greedy-->
| 입력 | 정본이 낸 답 | 큰 값부터 고른 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 [2 7 9 3 1 5] | 16 | 16 | 같다 |
| [4 5 4] | 8 | 5 | 틀리다 |
| [5 6 5 6 5] | 15 | 12 | 틀리다 |
| [1 2 3 1] | 4 | 4 | 같다 |

틀린 두 줄은 값이 가장 큰 칸 하나가 답이 고르는 칸 둘 사이에 낀 입력입니다.

<!--/proof-->

`[4 5 4]` 에서 가운데 5 를 먼저 고르면 양옆의 4 둘이 함께 빠지고, 합이 5 로 끝납니다. 한 번 고른 칸을 되돌릴
수 없어서, 고르지 않는 편이 나았던 칸을 끝까지 들고 가요. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

부분집합을 다 만드는 방법은 같은 물음을 되풀이해서 느렸고, 두 후보는 고를 칸을 미리 정해 버려서 틀렸습니다.
칸마다 **고른 경우와 건너뛴 경우를 둘 다** 따지고, 그 답을 앞의 두 답에서 이어받으면 둘 다 풀려요. 남은 방법에
이름을 붙이면 **두 값 이어받기**입니다. 무엇을 이어받고, 어떻게 고르고, 답을 어디서 읽는지는 다음 절에서
실현하는 순서대로 확인합니다.

### 아이디어 상세 — 두 값 이어받기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **칸 `i` 까지의 최대 합 `dp[i]` 를 건너뛴 답 `dp[i−1]` 과 고른 답
`dp[i−2] + A[i]` 가운데 큰 쪽으로 정하고, 마지막 두 칸의 값만 한 칸씩 옮기며 들고 가다가 마지막 칸의 값을
돌려줍니다.** 이 방법은 「칸 `i` 까지의 최대 합」이라는 값 위에서 동작하는데, 이름이 비슷한 다른 값과 헷갈리기
쉬워요. 그래서 그 값을 먼저 따로 설명하고, 그다음 실현하는 순서대로 네 단계를 설명합니다. 1단계는 반복에
들어가기 전에 한 번, 2단계와 3단계는 칸마다, 4단계는 반복이 끝난 뒤 한 번 합니다.

| 단계 | 언제 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 1단계 시작값 두 개 정하기 | 반복 전에 한 번 | `prev = dp[−1] = 0`, `cur = dp[0] = A[0]` | — |
| 2단계 두 갈래 중 큰 쪽으로 다음 칸 정하기 | 칸 1 부터 칸마다 | `dp[i] = max(dp[i−1], dp[i−2] + A[i])` | 직전 칸의 `prev` · `cur` — 처음에는 1단계의 두 값 |
| 3단계 두 값을 한 칸씩 옮기기 | 칸 1 부터 칸마다 | `prev` 에 옛 `cur`, `cur` 에 `dp[i]` | 2단계가 정한 `dp[i]` |
| 4단계 마지막 칸의 최대 합 읽기 | 반복 뒤에 한 번 | `cur` 를 돌려준다 | 3단계가 마지막으로 옮긴 `cur` |

#### 먼저 알아 둘 개념 — 칸 i 까지의 최대 합

단계로 들어가기 전에, 칸 `i` 까지의 최대 합이 어떻게 생겼고 어떻게 읽는지를 먼저 잡고 갑니다. 「칸 `i` 를 고른
최대 합」과 이름이 비슷해서 둘을 한 값으로 읽기 쉬운데, 그러면 2단계의 규칙이 왜 맞는지를 따라갈 수 없기
때문이에요.

##### 쉬운 말 정의

칸 `i` 까지의 최대 합은 **칸 0 부터 칸 `i` 까지만 놓고, 이웃한 두 칸을 함께 고르지 않은 선택 가운데 합이 가장
큰 것의 합**입니다. 칸 `i` 를 고른 선택도, 안 고른 선택도, 빈 선택도 모두 후보예요. 식으로 적으면
`dp[i] = max { S 의 합 | S ⊆ {0, 1, …, i}, S 의 어느 두 번호도 이웃이 아니다 }` 이고, 칸이 하나도 없을 때의
답 `dp[−1]` 은 빈 선택 하나뿐이라 0 입니다.

##### 입력 위에 놓은 그림

칸 3 을 골라 칸 0 부터 칸 3 까지에서 고를 수 있는 선택을 한 줄씩 그리면 이렇습니다. 줄마다 고른 칸의 값만
진하게, 안 고른 칸은 흐리게 그렸어요.

<!--fig:build-candidates-->
![칸 3 까지의 선택 8 가지 — 가장 큰 합이 dp[3]](./figs/build-candidates.svg)

강조한 줄이 합이 가장 큰 선택이고, 그 합이 `dp[3]` 입니다. 빈 선택 `{}` 도 한 줄을 차지하고, 칸 3 을 고르지
않은 선택 `{0, 2}` 가 가장 큰 줄이라는 것을 봐 주세요.

##### 하나를 읽는 법

`dp[3]` 하나를 골라 이름에서 값까지 따라가 봅시다.

<!--proof:build-read-one-->
```text
dp[3]  →  칸 0 부터 칸 3 까지  →  이웃하지 않는 선택 8 가지
       →  합 0 2 7 9 11 3 5 10  →  가장 큰 합 11, 선택 {0, 2}
```

`dp[3]` 은 값 하나지만 그 뒤에 선택 하나가 있습니다. 이 입력에서는 `{0, 2}` 예요. 선택을 따로 저장하지 않아도
합은 정해지고, 코드는 합만 들고 갑니다.

##### 이웃한 칸끼리의 관계

이웃한 칸의 최대 합이 어떻게 이어지는지 세 칸에서 그렸습니다. 칸 2 와 칸 5 는 두 칸 앞의 선택에 칸 `i` 를 더했고,
칸 3 은 한 칸 앞의 선택을 그대로 썼어요.

<!--fig:build-neighbors-->
![이웃한 칸의 최대 합 — dp[i] 의 선택은 dp[i−1] 의 선택이거나 dp[i−2] 의 선택에 칸 i 를 더한 것](./figs/build-neighbors.svg)

반복하는 다섯 칸을 모두 대조했습니다. 선택은 정본이 고른 갈래에서 이어 붙였고, 합은 정의대로 센 값과 맞춰 본
것이에요.

<!--proof:build-neighbors-->
| i | dp[i−2] 의 선택 | dp[i−1] 의 선택 | dp[i] 의 선택 | 두 선택의 관계 |
| ---: | --- | --- | --- | --- |
| 1 | {} = 0 | {0} = 2 | {1} = 7 | dp[−1] 의 선택에 칸 1 을 더했다 |
| 2 | {0} = 2 | {1} = 7 | {0, 2} = 11 | dp[0] 의 선택에 칸 2 를 더했다 |
| 3 | {1} = 7 | {0, 2} = 11 | {0, 2} = 11 | dp[2] 의 선택 그대로 |
| 4 | {0, 2} = 11 | {0, 2} = 11 | {0, 2, 4} = 12 | dp[2] 의 선택에 칸 4 를 더했다 |
| 5 | {0, 2} = 11 | {0, 2, 4} = 12 | {0, 2, 5} = 16 | dp[3] 의 선택에 칸 5 를 더했다 |

5 칸 모두 dp[i] 의 선택이 dp[i−1] 의 선택 그대로이거나 dp[i−2] 의 선택에 칸 i 를 더한 것입니다. 칸 i 를 더한 칸이 4 개, 그대로 쓴 칸이 1 개입니다. 칸 1 의 dp[−1] 은 칸이 없을 때의 답 0 입니다.

<!--/proof-->

`dp[i]` 의 선택은 늘 둘 중 하나입니다. 칸 `i` 를 안 고른 선택은 칸 `i−1` 까지의 선택과 같은 것이라 그 가운데
가장 큰 합이 `dp[i−1]` 이고, 칸 `i` 를 고른 선택은 칸 `i−1` 을 못 담으니 나머지가 칸 `i−2` 까지의 선택이라 가장
큰 합이 `dp[i−2] + A[i]` 예요. 칸 5 의 줄을 보면 `dp[3]` 의 선택 `{0, 2}` 에 칸 5 를 더했고, 칸 4 를 고른
`dp[4]` 의 선택 `{0, 2, 4}` 는 버려졌습니다.

##### 헷갈리기 쉬운 모양 — 칸 i 를 반드시 고른 최대 합

먼저 떠오르기 쉬운 모양은 **칸 `i` 를 반드시 고른 선택 가운데 가장 큰 합**입니다. 이것도 칸마다 하나씩이고
왼쪽부터 채울 수 있어 보이는데, 값이 다르게 움직여요. 전개 입력에서 두 줄을 나란히 세었습니다.

<!--proof:build-confuse-->
| 칸 i | A[i] | 칸 i 를 반드시 고른 최대 합 | dp[i] |
| ---: | ---: | ---: | ---: |
| 0 | 2 | 2 | 2 |
| 1 | 7 | 7 | 7 |
| 2 | 9 | 11 | 11 |
| 3 | 3 | 10 | 11 |
| 4 | 1 | 12 | 12 |
| 5 | 5 | 16 | 16 |

칸 i 를 반드시 고른 최대 합은 칸 3 에서 앞 칸보다 작아지고, dp[i] 는 한 번도 작아지지 않습니다. 입력 [1 5 1] 에서는 두 줄이 각각 [1 5 2] · [1 5 5] 이고, 마지막 칸만 읽으면 칸 i 를 반드시 고른 쪽은 2 이고 답은 5 입니다.

<!--/proof-->

칸 `i` 를 반드시 고른 값은 **마지막 칸이 답이 아닙니다.** 답이 마지막 칸을 안 고르면 그 값을 못 보기 때문이에요.
다음 칸을 정할 때도 칸 `i−2` 를 골랐는지 칸 `i−3` 을 골랐는지 둘 다 봐야 해서 들고 갈 값이 늘어납니다. 칸 `i`
까지의 최대 합은 칸 `i` 를 골랐든 안 골랐든 앞부분 전체의 답이라, 이런 갈래를 한 값 안에 이미 담고 있어요.

##### 앞부분 전체의 답으로 잡는 까닭

칸 `i` 를 고를 때 막히는 것은 **칸 `i−1` 하나뿐**이기 때문입니다. 칸 `i−2` 까지는 어떻게 골랐든 칸 `i` 와
부딪히지 않으니, 칸 `i` 가 알아야 할 과거는 「칸 `i−2` 까지 어떻게 골랐든 가장 큰 합」 하나예요. 그 값이 바로
`dp[i−2]` 입니다.

```text
칸 i 를 고를 때   칸 i−1 은 못 고른다   칸 i−2 까지는 무엇을 골랐든 괜찮다   →  dp[i−2] 하나면 된다
칸 i 를 건너뛸 때  칸 i−1 까지 무엇을 골랐든 괜찮다                       →  dp[i−1] 하나면 된다
                   └ 앞부분 전체의 답이라 「어떻게 골랐든」을 한 값에 담는다
```

#### 1단계 — 시작값 두 개 정하기

반복에 들어가기 전에 두 값을 정합니다. `prev` 는 칸이 없을 때의 답 `dp[−1]` 이고, 고를 칸이 없으니 빈 선택
하나뿐이라 0 이에요. `cur` 는 칸 0 까지의 최대 합 `dp[0]` 이고, 선택이 `{}` 와 `{0}` 둘뿐이라 큰 쪽이 `A[0]`
입니다. 전개 입력에서는 이렇습니다.

<!--proof:build-first-->
| 상태 | 놓고 본 칸 | 고를 수 있는 선택 | 값 |
| --- | --- | --- | ---: |
| 칸이 없을 때의 답 dp[−1] | 없다 | {} | 0 |
| 칸 0 까지의 최대 합 dp[0] | 칸 0 | {} · {0} | 2 |

`cur` 를 `A[0]` 으로 둘 수 있는 것은 값이 음수가 아니라서 `{0}` 의 합이 `{}` 의 합 0 보다 작지 않기
때문입니다. 배열이 비어 있으면 `A[0]` 이 없으니, 이 단계보다 먼저 0 을 돌려줘야 해요. 이 단계가 잡는 상태는 값
두 개이고, 배열 길이와 상관없이 그대로입니다.

#### 2단계 — 두 갈래 중 큰 쪽으로 다음 칸 정하기

칸 `i` 까지의 최대 합은 건너뛴 답 `dp[i−1]` 과 고른 답 `dp[i−2] + A[i]` 가운데 큰 쪽입니다. 코드에서는 건너뛴
답이 `cur` 이고 고른 답이 `prev + A[i]` 예요. 쉬운 경우는 고른 쪽이 클 때이고, 불안한 경우는 **건너뛴 쪽이 클
때**입니다. 전개 입력의 반복 다섯 칸을 두 경우로 나누면 이렇습니다.

<!--proof:build-cases-->
| 경우 | i | dp[i−2] | dp[i−1] | A[i] | 건너뛴 답 | 고른 답 | dp[i] |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 고른 쪽이 크다 | 1 | 0 | 2 | 7 | 2 | 0 + 7 = 7 | 7 |
| 고른 쪽이 크다 | 2 | 2 | 7 | 9 | 7 | 2 + 9 = 11 | 11 |
| 고른 쪽이 크다 | 4 | 11 | 11 | 1 | 11 | 11 + 1 = 12 | 12 |
| 고른 쪽이 크다 | 5 | 11 | 12 | 5 | 12 | 11 + 5 = 16 | 16 |
| 건너뛴 쪽이 크다 | 3 | 7 | 11 | 3 | 11 | 7 + 3 = 10 | 11 |

반복의 5 칸이 두 경우에 빠짐없이 들어갑니다. 고른 쪽이 큰 칸은 1 · 2 · 4 · 5 이고, 건너뛴 쪽이 큰 칸은 3 입니다.

<!--/proof-->

칸 4 는 값이 1 로 작은데도 골랐습니다. 칸 3 을 건너뛴 덕분에 `dp[2]` 와 `dp[3]` 이 같은 11 이 되었고, 칸 4 를
고른 답이 두 칸 앞의 11 에서 이어지기 때문이에요. 두 답이 같으면 어느 쪽을 골라도 `dp[i]` 가 같습니다.

빠뜨리는 칸이 없다는 것은 반복의 종료 조건으로 말할 수 있습니다. 반복은 `i` 를 1 부터 `N−1` 까지 하나씩 올리며
실행되고, 한 번 실행할 때마다 `dp[i]` 를 **정확히 한 번** 정해요. `dp[−1]` 과 `dp[0]` 은 1단계가 반복 전에
정했으니, 반복이 끝나면 `dp[0]` 부터 `dp[N−1]` 까지 `N` 개가 빠짐없이 한 번씩 정해집니다.

```text
반복이 끝난 시점
  정해진 값   dp[0] dp[1] … dp[N−1]   칸마다 하나씩, 각각 정확히 한 번
  안 본 칸    없다                     칸 0 은 반복에 들어가기 전에 정해진다
```

#### 3단계 — 두 값을 한 칸씩 옮기기

`dp[i]` 를 정했으면 다음 칸을 위해 두 값을 한 칸씩 옮깁니다. `prev` 에 옛 `cur`(`dp[i−1]`)를 적고, `cur` 에 새
`dp[i]` 를 적어요. 불안한 경우는 여기서도 **건너뛴 쪽이 클 때**입니다. `cur` 가 안 바뀌니 아무 일도 없는 것처럼
보이는데, `prev` 는 그때도 바뀌어요.

<!--proof:build-shift-->
| i | 옮기기 전 prev · cur | 옮긴 뒤 prev · cur | 무엇이 바뀌었나 |
| ---: | --- | --- | --- |
| 1 | 0 · 2 | 2 · 7 | 둘 다 바뀜 |
| 2 | 2 · 7 | 7 · 11 | 둘 다 바뀜 |
| 3 | 7 · 11 | 11 · 11 | cur 는 그대로 · prev 는 바뀜 |
| 4 | 11 · 11 | 11 · 12 | 둘 다 바뀜 |
| 5 | 11 · 12 | 12 · 16 | 둘 다 바뀜 |

cur 가 그대로인 칸은 3 이고, 그 칸에서도 prev 는 7 에서 11 로 바뀌었습니다.

<!--/proof-->

칸 3 을 마친 뒤의 두 값이 둘 다 11 이지만 뜻이 다릅니다. `prev` 의 11 은 칸 2 까지의 답이고 `cur` 의 11 은 칸 3
까지의 답이에요. 칸 4 가 고른 답을 만들 때 쓰는 것이 이 `prev` 의 11 이라, 여기서 `prev` 를 옮기지 않으면 칸 4
의 답이 어긋납니다. 옮기는 순서도 정해져 있어요 — `prev` 가 옛 `cur` 를 먼저 받아야 합니다. `cur` 를 먼저 고친 뒤
`prev = cur` 를 하면 `prev` 가 새 `cur` 를 받아 두 값이 같은 칸의 답이 돼요.

#### 4단계 — 마지막 칸의 최대 합 읽기

반복이 끝나면 `cur` 가 `dp[N−1]` 입니다. `dp[N−1]` 은 배열 전체를 놓고 본 답이라 **정의 그대로 과제의 답**이에요.
칸마다의 최댓값을 따로 모을 필요가 없습니다.

<!--proof:build-last-->
| 줄 | 칸 0 부터 칸 5 까지 |
| --- | --- |
| dp | [2 7 11 11 12 16] |
| 앞 칸보다 커진 칸 | 0 · 1 · 2 · 4 · 5 |

dp 는 한 번도 작아지지 않았습니다. 마지막 칸 dp[5] = 16 이고, 선택 21 가지를 모두 더해 본 가장 큰 합도 16 입니다.

<!--/proof-->

`dp` 가 한 번도 작아지지 않는 것은 2단계의 규칙에서 나옵니다. `dp[i]` 가 `dp[i−1]` 과 다른 값 중 큰 쪽이니
`dp[i]` 는 `dp[i−1]` 보다 작을 수 없어요. 그래서 마지막 칸의 값이 지나온 어느 칸의 값보다도 작지 않습니다.

#### 이 방법이 기대는 전제

두 값 이어받기는 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 칸이 일렬로 놓여 막히는 것이 바로 옆 하나다 | 2단계에서 칸 `i` 를 고르면 칸 `i−1` 만 빠진다 | 두 칸 떨어진 것까지 막히면 `dp[i−3]` 이 필요하고, 나무 모양이면 이웃이 여럿이라 갈래가 둘로 줄지 않는다 |
| 선택의 값이 덧셈으로 이어진다 | 2단계에서 가장 큰 앞부분에 `A[i]` 를 더한 것이 가장 크다 | 곱처럼 순서가 뒤집힐 수 있는 값은 가장 큰 앞부분이 가장 큰 결과를 내지 않는다 |
| 값이 음수가 아니다 | 1단계에서 `cur` 를 `A[0]` 으로 둔다 | 첫 칸이 음수면 빈 선택 0 이 더 커서 `dp[0]` 이 `A[0]` 이 아니다 |

세 번째 전제가 깨지는 모습을 값으로 확인합니다. 정본을 그대로 두고 음수가 섞인 입력을 넣어, 빈 선택까지 센 답과
나란히 놓았어요.

<!--proof:premise-negative-->
| 입력 | 빈 선택까지 센 답 | 정본이 낸 값 | 판정 |
| --- | ---: | ---: | --- |
| [-5] | 0 | -5 | 틀리다 |
| [-2 -1 -3] | 0 | -1 | 틀리다 |
| [3 -1 4] | 7 | 7 | 같다 |
| [-4 6] | 6 | 6 | 같다 |

틀린 2 줄은 빈 선택이 답인 입력이고, 정본은 빈 선택 대신 첫 칸의 음수에서 시작한 값을 냈습니다. [3 -1 4] · [-4 6] 처럼 음수가 섞여도 답이 양수인 입력에서는 값이 같습니다.

<!--/proof-->

음수가 들어와도 2단계와 3단계는 그대로 맞습니다. 틀리는 곳은 1단계의 `dp[0] = A[0]` 한 곳뿐이에요. 음수를
받는 과제라면 1단계를 `cur = max(0, A[0])` 으로 바꾸면 되고, 이 글의 과제는 값이 0 이상이라 그 비교가 필요
없습니다.

#### 두 칸 앞까지 드는 까닭

고른 답을 몇 칸 앞에서 이어받을지를 1 칸 · 2 칸 · 3 칸 앞과 `dp` 전체 네 가지로 두고 같은 입력 넷에
실행했습니다. `dp` 전체는 칸마다 값을 저장해 두고 두 칸 앞을 읽는 방식이에요.

<!--proof:state-span-->
| 입력 | 정답 | 1 칸 앞 | 2 칸 앞 | 3 칸 앞 | dp 전체 |
| --- | ---: | ---: | ---: | ---: | ---: |
| [2 7 9 3 1 5] | 16 | 27 | 16 | 14 | 16 |
| [1 2 3 1] | 4 | 7 | 4 | 3 | 4 |
| [2 1 1 2] | 4 | 6 | 4 | 4 | 4 |
| [5 5 5 5 5] | 15 | 25 | 15 | 10 | 15 |
| 어긋난 입력 수 |  | 4 | 0 | 3 | 0 |
| N = 100,000 에서 들고 가는 칸 |  | 1 | 2 | 3 | 100,000 |

어긋난 입력이 0 개인 것은 2 칸 앞과 dp 전체이고, 둘 중 들고 가는 칸이 적은 쪽은 2 칸 앞입니다.

<!--/proof-->

1 칸 앞은 이웃한 칸을 함께 고르므로 답이 전부 더한 값으로 커지고, 3 칸 앞은 이웃이 아닌데도 못 고르는 칸이 생겨
답이 작아집니다. `dp` 전체는 답은 맞지만 두 칸 앞과 같은 답을 내려고 100,000 칸을 써요. 그래서 **들고 가는 값은
둘**입니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇습니다. 앞의 둘이 반복 전에 한 번, 가운데 둘이 칸마다, 마지막이 반복
뒤에 한 번이에요. 이렇게 하면 `N` 이 100,000 일 때 30,108 자리 수이던 기본 연산이 199,998 번이 됩니다.

1. 칸이 하나도 없으면 0 을 돌려준다
2. `prev` 를 0 으로, `cur` 를 `A[0]` 으로 둔다
3. `i` 를 1 부터 `N − 1` 까지 옮기며 건너뛴 답 `cur` 와 고른 답 `prev + A[i]` 를 만든다
4. 같은 칸에서 `prev` 에 옛 `cur` 를, `cur` 에 두 답 중 큰 쪽을 적는다
5. 반복이 끝나면 `cur` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 여섯 칸을 한 번 지나가며 최대 합을 낸다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->
```ts
const nums = [2, 7, 9, 3, 1, 5];
// 이 절이 끝나면 16 이 나와야 한다
```

왜 하필 이 여섯 칸일까요? 두 갈래가 다 실행되고(칸 3 에서 건너뛰고, 나머지에서 고르고), 답이 고른 칸이 이어지지
않은 셋이며, **건너뛰는 걸음에서 `cur` 는 그대로인데 `prev` 는 바뀌는 장면**이 실제로 나오기 때문이에요. 그
자리가 이 절차에서 가장 헷갈리는 곳이고, 건너뛰는 걸음이 하나뿐이라 그 걸음이 하는 일도 또렷합니다.

```text
houseRobber(nums):
    nums 가 비었으면 0 을 반환한다                       ① 빈 입력 막기
    prev ← 0, cur ← nums[0]                               ② 두 값 시작
    i 를 1 부터 N−1 까지 옮기며:                          ③ 반복 조건 i < N
        skip ← cur, take ← prev + nums[i]                 ④ 두 답 만들기
        prev ← cur, cur ← max(skip, take)                 ⑤ 두 값 옮기기
    cur 를 반환한다
```

#### 1. 빈 입력을 막고 두 값을 시작한다

첫 조각은 준비입니다. 빈 입력을 먼저 막고 두 값을 적어 두며, 아직 반복에는 들어가지 않아요.

```ts
if (nums.length === 0) return 0; // ① 칸이 하나도 없으면 답이 0 이다
let prev = 0; // ② 칸이 없을 때의 답
let cur = nums[0] as number; // ② 칸 0 까지의 최대 합
```

이 세 줄만 실행하면 두 값이 이렇게 잡힙니다.

<!--proof:walk-init-->
| 상태 | 값 | 뜻 |
| --- | ---: | --- |
| prev | 0 | 칸이 없을 때의 답 dp[−1] |
| cur | 2 | 칸 0 까지의 최대 합 dp[0] |

`①` 이 먼저 오는 것이 이 조각의 요점입니다. 빈 배열에서 `nums[0]` 을 읽으면 값이 없어서 그 뒤가 전부 어긋나요.
`②` 는 같은 자리를 두 뜻으로 갈라 시작합니다. `prev` 는 칸이 없을 때의 답이고 `cur` 는 칸 0 까지의 답이라, 다음
걸음부터 둘이 함께 한 칸씩 옮겨 갑니다.

#### 2. 칸마다 건너뛴 답과 고른 답 중 큰 쪽을 고른다

둘째 조각은 반복입니다. 칸 하나마다 두 갈래를 값으로 만들고, 두 값을 한 칸씩 옮기면서 큰 쪽을 `cur` 에 적어요.

```ts
for (let i = 1; i < nums.length; i++) {
  // ③ 반복 조건 i < N
  const skip = cur; // ④ 칸 i 를 건너뛴 답
  const take = prev + (nums[i] as number); // ④ 칸 i 를 고른 답
  prev = cur; // ⑤ prev 가 옛 cur 를 받는다
  cur = Math.max(skip, take); // ⑤ cur 는 두 답 중 큰 쪽이 된다
}
```

`③` 은 `i` 가 1 부터 5 까지일 때 참이고 6 에서 처음 거짓이 됩니다. `④` 와 `⑤` 는 그 다섯 걸음에서 각각 한 번씩
실행돼요. 앞 두 걸음만 실행하면 이렇게 나옵니다.

<!--proof:walk-first-two-->
| 걸음 | i | A[i] | 건너뛴 답 | 고른 답 | prev | cur |
| --- | ---: | ---: | ---: | --- | ---: | ---: |
| T2 | 1 | 7 | 2 | 0 + 7 = 7 | 2 | 7 |
| T3 | 2 | 9 | 7 | 2 + 9 = 11 | 7 | 11 |

T3 의 고른 답 11 은 직전 답 7 이 아니라 두 칸 앞의 답 2 에서 나왔습니다.

<!--/proof-->

T3 이 이 두 줄의 핵심입니다. `cur` 가 11 이 됐는데 그 재료는 직전 답이 아니라 **두 칸 앞의 답**이에요. 두 칸
앞의 답을 `prev` 로 들고 있지 않으면 11 을 만들 재료가 없습니다.

#### 짚고 가기 — 고른 답을 cur 에서 이어받으면 이웃한 두 칸을 함께 고른다

여기서 헷갈리기 쉬운 포인트는 `take` 가 보는 값입니다. 「어차피 지금까지의 답이 `cur` 인데 거기에 `A[i]` 를
더하면 되지 않나」로 읽기 쉬워요. 그 생각대로 한 곳만 바꿔 봅시다.

```ts
const take = cur + (nums[i] as number); // ← prev 가 아니라 cur 에서 이어받았다
```

이렇게 하면 칸 `i−1` 을 이미 고른 답 위에 칸 `i` 를 더하게 됩니다. 다섯 입력으로 확인해 봅니다.

<!--proof:pause-adjacent-->
| 입력 | 정본이 낸 답 | cur 에서 이어받은 값 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 [2 7 9 3 1 5] | 16 | 27 | 틀리다 |
| [1 2 3 1] | 4 | 7 | 틀리다 |
| [2 7] | 7 | 9 | 틀리다 |
| [5] | 5 | 5 | 같다 |
| [0 0 0] | 0 | 0 | 같다 |

전개 입력의 변이 값은 여섯 칸을 전부 더한 합 27 과 같은 크기입니다. 칸이 하나이거나 값이 전부 0 이면 답이 그대로입니다.

<!--/proof-->

값이 음수가 아니라서 「더하는 쪽」이 언제나 커집니다. 그래서 이 변이는 **모든 칸을 다 고른 합**을 내요. 칸이
하나이거나 값이 전부 0 이면 더해도 달라지는 것이 없어 답이 같으니, 그런 입력만 시험에 넣으면 끝까지 모르고
넘어갑니다. 두 칸짜리 입력 `[2 7]` 에서 가장 짧게 보여요.

<!--proof:pause-adjacent-two-->
| 방식 | 고른 답 | 그 답의 선택 |
| --- | --- | --- |
| 정본 | prev + 7 = 0 + 7 = 7 | {1} |
| cur 에서 이어받기 | cur + 7 = 2 + 7 = 9 | {0, 1} — 이웃 |

`cur` 의 2 는 칸 0 을 고른 합이라, 거기에 칸 1 을 더하면 이웃한 두 칸을 함께 고른 선택이 후보로 들어갑니다.
`prev` 가 칸 `i−1` 을 빼고 본 답이어야 하는 까닭이 이것이에요.

#### 3. 여섯 칸을 끝까지 지나가며 답을 낸다

두 조각을 이어 고정 입력에 실행하면 일곱 걸음이 나옵니다. T1 은 준비, T2 부터 T6 까지가 반복, T7 이 반복 조건이
거짓이 되어 답을 돌려주는 걸음이에요. 괄호는 지금까지 놓고 본 칸이고, ▲ 는 이번 걸음에 읽은 칸입니다. `dp` 줄은
칸마다의 최대 합이고, 「고른 칸」 줄은 지금 `cur` 를 만든 선택의 칸에만 값을 적고 안 고른 칸을 `·` 로 둔 것이에요. 코드가 실제로 드는 것은
`dp` 줄의 마지막 두 칸뿐입니다.

<!--viz:rob-->
<!--fig:walk-carry-->
![houseRobber([2, 7, 9, 3, 1, 5]) 의 일곱 걸음 T1~T7](./figs/walk-carry.svg)

<!--result:rob=16-->

걸음마다의 상태값과 조건 판정을 전부 적으면 아래 일곱 단계입니다.

<!--proof:walk-trace-->
| 걸음 | i | 조건 | A[i] | 건너뛴 답 | 고른 답 | 고른 갈래 | prev | cur |
| --- | ---: | --- | ---: | ---: | ---: | --- | ---: | ---: |
| T1 | 0 | `6 === 0` 거짓 | 2 | — | — | — | 0 | 2 |
| T2 | 1 | `1 < 6` 참 | 7 | 2 | 7 | 고른다 | 2 | 7 |
| T3 | 2 | `2 < 6` 참 | 9 | 7 | 11 | 고른다 | 7 | 11 |
| T4 | 3 | `3 < 6` 참 | 3 | 11 | 10 | 건너뛴다 | 11 | 11 |
| T5 | 4 | `4 < 6` 참 | 1 | 11 | 12 | 고른다 | 11 | 12 |
| T6 | 5 | `5 < 6` 참 | 5 | 12 | 16 | 고른다 | 12 | 16 |
| T7 | 6 | `6 < 6` 거짓 | — | — | — | — | 12 | 16 |

cur 는 한 번도 작아지지 않았고, T7 에서 16 을 돌려줍니다.

<!--/proof-->

T4 에서 `cur` 는 11 그대로인데 `prev` 는 7 에서 11 로 바뀌었고, T5 가 그 11 에 1 을 더해 12 를 만들었어요.
**다섯 라벨이 모두 실행됐습니다.** 라벨마다 실행된 걸음을 모으면 이렇습니다.

<!--proof:walk-branches-->
| 갈래 | 실행된 걸음 |
| --- | --- |
| ① 빈 입력 막기 | T1 에서 거짓 |
| ② 두 값 시작 | T1 |
| ③ 반복 조건 i < 6 | T2~T6 에서 참 · T7 에서 거짓 |
| ④ 두 답 만들기 | T2~T6 |
| ⑤ 두 값 옮기기 | 칸을 고른 걸음 T2 T3 T5 T6 · 건너뛴 걸음 T4 |

두 답이 같아지는 걸음은 이 입력에 없습니다.

<!--/proof-->

`③` 은 참과 거짓이 다 나왔고, `⑤` 는 고른 걸음과 건너뛴 걸음이 다 있어요. 답이 정말 그 칸들의 합인지도 확인하고
갑니다.

<!--proof:walk-check-sum-->
| cur 를 만든 선택 | 그 칸들의 값 | 직접 더한 합 | 번호 차이 | T7 이 돌려준 값 |
| --- | --- | --- | --- | ---: |
| {0, 2, 5} | 2 · 9 · 5 | 2 + 9 + 5 = 16 | 2 · 3 | 16 |

번호 차이가 모두 2 이상이라 이웃한 쌍이 없고, 직접 더한 합이 T7 이 돌려준 값과 같습니다.

#### 짚고 가기 — 점화식을 재귀로 옮기면 과제 규모에서 실행되지 않는다

여기서 헷갈리기 쉬운 포인트는 점화식과 재귀의 관계입니다. 「식이 자기 자신을 부르는 모양이니 재귀로 적는 것이
가장 곧은 옮김 아닌가」로 읽기 쉬워요. 그렇게 적어 봅시다.

```ts
function robFrom(i: number): number {
  // 점화식을 그대로 옮긴 재귀
  if (i < 0) return 0;
  return Math.max(robFrom(i - 1), robFrom(i - 2) + (nums[i] as number));
}
robFrom(nums.length - 1);
```

메모를 붙이면 물음마다 답을 한 번씩만 정하니 호출 수는 잡힙니다. 그래도 남는 것이 있어요.

<!--proof:pause-recursion-->
| 입력 | 정본이 낸 답 | 메모를 붙인 재귀의 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 [2 7 9 3 1 5] | 16 | 16 | 같다 |
| [1 2 3 1] | 4 | 4 | 같다 |
| [5 5 5 5 5] | 15 | 15 | 같다 |

메모를 안 붙이면 부르는 횟수가 이렇게 늘어납니다.

| N | 재귀 호출 | 두 값 이어받기의 기본 연산 |
| ---: | ---: | ---: |
| 6 | 41 | 10 |
| 12 | 753 | 22 |
| 18 | 13,529 | 34 |
| 24 | 242,785 | 46 |

메모를 붙였을 때 과제 규모까지 실행되는지 보면 이렇습니다.

| N | 메모를 붙인 재귀 |
| ---: | --- |
| 1,000 | 답 500 이 나온다 |
| 100,000 | 재귀 깊이를 넘어 답이 안 나온다 |

<!--/proof-->

**작은 입력에서는 답이 똑같습니다.** 갈리는 것은 과제 규모예요. 메모를 붙여도 `robFrom(99999)` 가 `robFrom(0)`
까지 내려가는 동안 부른 자리가 전부 쌓이고, 그 깊이에서 실행이 멈춥니다. 위 표는 Bun 1.3.12 에서 실행한
결과이고, 멈춘 오류는 `RangeError: Maximum call stack size exceeded.` 입니다. 몇 칸에서 멈추는지는 실행 환경의
호출 스택 한도가 정해요. 반복으로 적으면 칸 0 부터 차례로 정해
두 값만 이어받으니 쌓이는 것이 없어요.

#### 4. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `cur` 를 돌려주는 마지막 한 줄뿐이에요. 칸이
하나면 반복이 한 번도 실행되지 않아 `A[0]` 이 그대로 답이 됩니다.

```ts
export function houseRobber(nums: number[]): number {
  // ① 칸이 하나도 없으면 답이 0 이다 — 아래에서 첫 칸을 읽기 전에 막는다.
  if (nums.length === 0) return 0;

  // ② 두 값을 시작값으로 둔다. prev 는 칸이 없을 때의 답이라 0 이고, cur 는 칸 0
  //    까지의 최대 합이라 첫 칸의 값이다.
  let prev = 0;
  let cur = nums[0] as number;

  for (let i = 1; i < nums.length; i++) {
    // ③ 순회할 칸이 남았는가 — 남아 있으면 아래를 한 번 실행한다.
    // ④ 칸 i 를 건너뛴 답과 칸 i 를 고른 답을 각각 만든다. 고른 쪽은 옆 칸을 뺀 답에서
    //    이어받으므로 cur 가 아니라 prev 를 쓴다.
    const skip = cur;
    const take = prev + (nums[i] as number);
    // ⑤ 두 값을 한 칸씩 옮긴다. prev 가 먼저 옛 cur 를 받아야 다음 걸음에서 두 칸 앞이 된다.
    prev = cur;
    cur = Math.max(skip, take);
  }

  return cur;
}
```

```text
houseRobber([2, 7, 9, 3, 1, 5])   →      16
houseRobber([1, 2, 3, 1])         →       4
houseRobber([2, 1, 1, 2])         →       4
houseRobber([10000, 1, 10000])    →  20,000
houseRobber([])                   →       0
```

### 알아 두면 좋은 개념 — 가중치가 있는 최대 독립 집합

칸을 점으로, 「함께 고를 수 없다」를 선으로 그리면 이 과제가 그래프 하나가 됩니다. 답이 고른 칸들은 **어느 둘도
선으로 이어져 있지 않은 점의 모임**이고, 그런 모임을 독립 집합이라고 불러요. 점마다 값이 붙어 있고 그 합을
최대로 하는 것이라 **가중치가 있는 최대 독립 집합**입니다.

<!--fig:related-path-->
![칸 여섯을 점으로, 이웃한 두 칸을 선으로 — 강조한 점 셋이 답의 선택](./figs/related-path.svg)

강조한 세 점은 「고른 칸」 줄이 T7 에서 찍은 선택과 같고, 어느 둘도 선 하나로 이어져 있지 않습니다. 이 이름이
쓸모 있는 것은 **선을 다르게 그으면 다른 과제가 되기** 때문이에요. 점과 선의 모양만 바꾸면 같은 물음이 여러
자리에서 다시 나옵니다.

| 다시 나오는 자리 | 선이 잇는 것 | 막히는 선택 |
| --- | --- | --- |
| 이 글의 과제(경로) | 이웃한 두 칸 | 이웃한 둘을 함께 고르기 |
| 나무([`treeMaxIndependentSet`](../../dp/treeMaxIndependentSet/treeMaxIndependentSet-guide.md)) | 부모와 자식 | 부모와 자식을 함께 고르기 |
| 구간 겹침 | 겹치는 두 구간 | 겹치는 둘을 함께 고르기 |

셋 다 고른 것끼리 선으로 이어져 있지 않아야 한다는 조건입니다. 선이 일렬이면 이 글의 두 값 이어받기로 끝나고,
나무면 자식마다 값 둘을 모아 올리는 절차가 되고, 일반 그래프면 다항 시간 절차가 알려져 있지 않아요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 두 갈래 규칙을 식으로 어떻게 적는지, 무엇이 매
걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 고를 것이 **일렬로 놓여** 있습니다. 놓인 모양이 나무나 일반 그래프면 갈래가 둘로 안 줄어요.
- 막히는 것이 **바로 옆 하나**입니다. 두 칸 떨어진 것까지 막히면 이어받을 답이 하나 더 늘어요.
- 답이 **한 번만** 필요합니다. 값이 바뀌면 처음부터 다시 지나가야 해요.
- 값이 **음수가 아닙니다.** 그래서 첫 칸의 답을 `A[0]` 으로 바로 둘 수 있어요.

```text
네 조건이 코드의 모양을 그대로 정한다
  일렬로 놓임        → 칸 i 의 갈래가 둘로 줄어든다
  이웃만 막힘        → 두 칸 앞의 답 하나만 더 들고 있으면 된다
  답이 한 번         → 한 번 지나가면 끝난다
  값이 음수가 아님   → 첫 칸의 답이 A[0] 이다
```

네 번째 줄은 코드 한 줄만 정합니다. 값에 음수가 섞이면 1단계를 `max(0, A[0])` 으로 바꾸면 되고, 나머지는 그대로예요.
과제의 모양에 따라 들고 가는 것이 달라집니다.

| 과제 | 칸마다 들고 가는 것 | 다루는 글 |
| --- | --- | --- |
| 이어진 구간의 합을 최대로 한다 | 값 하나 | [`kadane`](../kadane/kadane-guide.md) |
| 이웃한 둘을 함께 못 고른다 | 값 둘 | 이 글 |
| 나무 모양으로 놓여 있다 | 자식마다 값 둘을 모아 올린다 | [`treeMaxIndependentSet`](../../dp/treeMaxIndependentSet/treeMaxIndependentSet-guide.md) |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "인접한 두 개를 함께 고를 수 없다"  "연달아 고를 수 없다"   ← 이웃만 막히는 조건이다
  "일렬로 늘어선"  "한 줄로 놓인"                             ← 경로 모양이다
  "합을 최대로"  "가장 많이"                                  ← 답이 합의 최댓값 하나다
  "하나도 안 골라도 된다"                                     ← 빈 선택이 후보라 답이 0 이상이다

입력 규모에 이런 모양이 보이면
  N 이 10^5 이상이라 부분집합을 다 만들 수 없다
  값이 음수가 아니다

반대로 이런 말이 보이면 해당하지 않는다
  "이어진 구간"                        ← 고르는 것이 구간이라 kadane 쪽이다
  "두 칸 이상 떨어져야 한다"           ← 막히는 범위가 이웃 하나가 아니다
  "고를 수 있는 개수가 K 개다"         ← 상태에 개수가 하나 더 붙는다
  "첫 칸과 마지막 칸이 이웃이다"       ← 원형이라 두 경우로 갈라 두 번 지나가야 한다
  "나무 모양으로 이어져 있다"          ← 트리 최대 독립 집합 쪽이다
```

세 번째 무리가 보이면 다른 절차로 갑니다. 구간을 다루면 [`kadane`](../kadane/kadane-guide.md) 쪽이고, 놓인
모양이 나무면 [`treeMaxIndependentSet`](../../dp/treeMaxIndependentSet/treeMaxIndependentSet-guide.md) 쪽이에요.

  the goal of the maximum independent set problem is to compute a maximum cardinality set of

  v3.0 항목이 *"mmwis (Memetic Maxmimum Weight Independent Set): Our iterative reduce and
  evolution algorithm to solve the maximum weight independent set problem"* 로 **가중치가 붙은
  쪽**을 함께 다룬다고 적습니다. 이 글의 과제는 그 일반형에서 점들이 일렬로 놓인 경우예요.
  ([`KaMIS` README](https://github.com/KarlsruheMIS/KaMIS), 조회 2026-08-30)
- **Lamm 외 5인, *Exactly Solving the Maximum Weight Independent Set Problem on Large Real-World
  Graphs* (ALENEX 2019)** — 초록이 *"we develop a full suite of new reductions for the maximum
  weight independent set problem and provide extensive experiments to show their effectiveness in
  practice on real-world graphs of up to millions of vertices and edges"* 라고 적습니다. 일반
  그래프에서는 축소 규칙을 쌓아야 겨우 정확히 푼다는 뜻이에요.

같은 과제가 점과 선의 모양에 따라 세 자리에 놓입니다.

| 놓인 모양 | 알려진 절차 | 드는 것 |
| --- | --- | --- |
| 일반 그래프 | 축소 규칙과 분기 탐색 | 다항 시간 절차가 알려져 있지 않다 |

**이 절차를 그 이름으로 제공하는 표준 라이브러리는 1 차 출처로 확인하지 못했습니다.** 경로에서는 위 코드 한
벌로 끝나서 라이브러리가 따로 이름을 붙일 일이 없어요. 확인한 것은 이 과제가 실제로 풀리고 있는 더 큰 과제의
가장 쉬운 경우라는 것과, 그 큰 과제를 푸는 도구가 실재한다는 것 둘입니다.

#### 경쟁 설계와의 대조

같은 목표(이웃하지 않은 칸의 최대 합을 아는 것)를 노리는 다른 절차로 **세그먼트 트리**가 있습니다. 마디마다 그
구간의 네 값(첫 칸을 골랐는가 × 마지막 칸을 골랐는가의 조합마다 그 조건에서의 최댓값)을 들고, 두 마디를 합칠 때
왼쪽의 마지막 칸과 오른쪽의 첫 칸이 함께 골라지지 않는 조합 셋만 더하는 방식이에요.

```text
두 설계가 값 하나를 바꿀 때 하는 일
  두 값 이어받기   칸 하나를 고쳐 두고, 답을 물으면 배열을 처음부터 다시 지나간다
  세그먼트 트리    잎 하나를 고치고 뿌리까지 log N 번 합친다. 답은 뿌리에 이미 적혀 있다
                   └ 갱신은 두 값 이어받기가 적고, 반복 질의는 세그먼트 트리가 적다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **기본 연산 수**(덧셈 + 비교)를 셌습니다. 배열은 `N = 1,024` 이고 칸
번호 `k` 마다 `A[k] = (37k mod 97) + 1` 로 만들었어요. 갱신은 1,024 개인데 `k` 번째 갱신이 칸 `91k mod N` 의
값을 `(53k mod 97) + 1` 로 바꿉니다. 질의는 「지금 배열의 답」을 묻는 것이고 갱신 사이에 고르게 끼웠으며, 목록의
끝에서 두 설계가 다 한 번 답해요. **전개 입력을 그대로 쓰지 않은 이유**는 여섯 칸에서는 세그먼트 트리가 한 번
갱신할 때 합치는 마디가 셋뿐이라 두 설계의 계수가 상수에 묻히기 때문이에요.

<!--proof:alt-table-->
| 섞인 질의 | 두 값 이어받기 | 세그먼트 트리 | 적은 쪽 |
| --- | ---: | ---: | --- |
| 0 회 | **2,046** | 225,263 | 두 값 이어받기가 110 배 적음 |
| 109 회 | **225,060** | 225,590 | 두 값 이어받기가 근소하게 적음 |
| 110 회 | 227,106 | **225,593** | 세그먼트 트리가 근소하게 적음 |
| 1,024 회 | 2,097,150 | **228,335** | 세그먼트 트리가 9 배 적음 |

저장 칸은 2 개 대 8,192 개입니다.

<!--/proof-->

메모리에서는 갈리지 않고 한쪽이 계속 적어요 — 갈리는 것은 연산 수이고, 그 경계가 이 입력에서 **질의 110 회**
입니다. 경계가 그 자리인 이유는 두 설계가 연산을 쓰는 방식에서 나옵니다.

<!--proof:alt-boundary-->
| 무엇 | 값 |
| --- | --- |
| 질의 하나에 드는 두 값 이어받기의 연산 | 2,046 |
| 질의 하나에 드는 세그먼트 트리의 연산 | 3 |
| 세그먼트 트리가 먼저 쓰는 연산 | 225,260 = 트리 세우기 20,460 + 갱신 204,800 |
| 뒤집히는 질의 수 | 225,260 ÷ (2,046 − 3) ≈ 110.3 |

**이 절차가 내주는 것은 반복 질의입니다.** 값 하나가 바뀔 때마다 답을 다시 물으면 그때마다 배열 전체를 지나가서,
질의 하나가 2,046 번의 연산이 돼요. 그 대신 얻는 것이 셋입니다.

| 축 | 두 값 이어받기 | 세그먼트 트리 |
| --- | --- | --- |
| 저장 칸 | 값 두 개 | 마디마다 값 넷 |
| 전처리 | 없다 | 트리를 세우는 합치기가 먼저 든다 |
| 구현 | 반복 하나 | 합치기 규칙 넷을 따로 맞춰야 한다 |

답을 한 번 구하는 과제에서는 두 값 이어받기가 답입니다. 같은 배열에서 **값이 바뀌며 답을 110 회 넘게 다시 묻는
순간** 이 판정은 다시 해야 해요.

### 수식 정의와 유도

고를 수 있는 선택과 답을 기호로 정의합니다. `𝒮_i` 는 칸 `0` 부터 칸 `i` 까지에서 이웃한 두 번호를 함께 담지 않는
부분집합을 전부 모은 것이고, `dp[i]` 는 그중 합이 가장 큰 것의 합이에요. `𝒮_{−1}` 은 빈 집합 하나만 담습니다.

$$\mathcal{S}_i = \bigl\{\, S \subseteq \{0, 1, \dots, i\} \;\bigm|\; a, b \in S,\ a \ne b \implies |a - b| \ge 2 \,\bigr\} \qquad dp[i] = \max_{S \in \mathcal{S}_i} \sum_{k \in S} A[k]$$

정의를 작은 값에 넣어 확인하고 갑시다. 칸 2 까지의 선택을 정의대로 모두 만들고, 여섯 칸 전부에서 정의로 센 값과
정본의 `cur` 를 맞춰 보았어요.

<!--proof:math-check-->
| 𝒮_2 의 선택 | 더한 값 | 합 |
| --- | --- | ---: |
| {} | 0 | 0 |
| {0} | 2 | 2 |
| {1} | 7 | 7 |
| {2} | 9 | 9 |
| {0, 2} | 2 + 9 | 11 |

여섯 칸 전부에서 정의로 센 값과 정본의 cur 를 나란히 놓으면 이렇습니다.

| i | 𝒮_i 의 크기 | 정의로 센 dp[i] | 정본의 cur |
| ---: | ---: | ---: | ---: |
| 0 | 2 | 2 | 2 |
| 1 | 3 | 7 | 7 |
| 2 | 5 | 11 | 11 |
| 3 | 8 | 11 | 11 |
| 4 | 13 | 12 | 12 |
| 5 | 21 | 16 | 16 |

두 열이 6 칸 모두 같습니다.

<!--/proof-->

이제 유도합니다. `𝒮_i` 를 **칸 `i` 를 담은 것**과 **안 담은 것** 둘로 가르면, 두 무리가 각각 앞의 집합에서 한
걸음으로 나와요.

```text
칸 i 까지의 선택을 두 무리로 가른다
  i 를 안 담은 것   칸 i−1 까지의 선택 그대로           합의 최댓값이 dp[i−1] 이다
  i 를 담은 것      칸 i−2 까지의 선택에 i 를 더한 것   i−1 은 이웃이라 못 담는다
                                                        └ 두 무리가 겹치지도 빠지지도 않는다
```

두 무리가 겹치지도 빠지지도 않으므로 집합 자체가 이렇게 갈리고, 합의 최댓값도 두 무리의 최댓값 중 큰 쪽이 됩니다.
임의의 `N` 과 임의의 배열에 대해 얻은 것이에요.

$$\mathcal{S}_i = \mathcal{S}_{i-1} \;\cup\; \bigl\{\, S \cup \{i\} \;\bigm|\; S \in \mathcal{S}_{i-2} \,\bigr\} \quad\Longrightarrow\quad dp[i] = \max\bigl(dp[i-1],\; dp[i-2] + A[i]\bigr) \quad (i \ge 1), \qquad dp[-1] = 0, \quad dp[0] = A[0]$$

```ts
// 정의를 그대로 옮긴 조각. 실제 절차는 이 목록을 만들지 않고 두 값만 이어받는다.
const admissible = (i: number): number[][] => {
  if (i < 0) return [[]];
  if (i === 0) return [[], [0]];
  return [...admissible(i - 1), ...admissible(i - 2).map((s) => [...s, i])];
};
```

같은 갈림이 **개수**에도 그대로 적용됩니다. 두 무리의 크기를 더하면 개수의 점화식이 나오고, 그 점화식이 피보나치
수(`F(1) = F(2) = 1`, `F(k) = F(k−1) + F(k−2)`)라서 닫힌 형태가 붙어요.

$$|\mathcal{S}_i| = |\mathcal{S}_{i-1}| + |\mathcal{S}_{i-2}| \qquad |\mathcal{S}_0| = 2,\ \ |\mathcal{S}_1| = 3 \qquad\Longrightarrow\qquad |\mathcal{S}_{N-1}| = F(N+2)$$

```text
두 점화식이 같은 모양인 이유
  dp[i]    두 무리의 최댓값 중 큰 것을 고른다   max 로 합친다
  |𝒮_i|    두 무리의 크기를 더한다              + 로 합친다
                                               └ 같은 갈림에서 나왔고, 합치는 연산만 다르다
```

마지막으로 과제 규모를 넣습니다. 이 식이 말하는 것은 **이웃 조건이 후보를 얼마나 걷어내는가**예요.

<!--proof:math-count-->
| i | 𝒮_i 의 크기(실측) | 피보나치 |
| ---: | ---: | --- |
| 0 | 2 | F(3) = 2 |
| 1 | 3 | F(4) = 3 |
| 2 | 5 | F(5) = 5 |
| 3 | 8 | F(6) = 8 |
| 4 | 13 | F(7) = 13 |
| 5 | 21 | F(8) = 21 |

과제 규모 N = 100,000 을 넣으면 이렇습니다.

| 무엇 | 값 |
| --- | --- |
| 이웃하지 않는 선택 𝒮_{N−1} 의 크기 | F(100,002) — 20,899 자리 수 |
| 모든 부분집합 | 2^100,000 — 30,103 자리 수 |
| 고를 수 있는 칸의 최대 개수 | 50,000 |
| 답의 상한 | 500,000,000 |
| 두 값 이어받기의 기본 연산 | 199,998 |

<!--/proof-->

식이 말하는 것은 **후보를 거르는 것으로는 안 된다**는 것입니다. 이웃 조건이 후보의 자릿수를 3 분의 1 쯤 걷어내는데도
세는 것 자체가 불가능해요. 답의 상한 5 억은 고를 수 있는 칸이 최대 5 만 개라는 데서 나오고, `number` 가 정확히
담을 수 있는 정수 안에 넉넉히 듭니다.

### 불변식 — prev 는 칸 i−1 까지의, cur 는 칸 i 까지의 최대 합이다

파트 1 에서 코드가 동작하는 것을 일곱 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해 봅시다.

> 반복이 칸 `i` 를 처리한 직후, `cur` 는 `dp[i]` 와 같고 `prev` 는 `dp[i−1]` 과 같습니다.

```text
  prev 가 뜻하는 것   칸 0 부터 칸 i−1 까지만 놓고 본 최대 합
  cur 가 뜻하는 것    칸 0 부터 칸 i 까지만 놓고 본 최대 합

  둘 다 「칸 i 를 막 처리한 직후」에 참이다   걸음 도중에는 두 줄 사이에서 잠깐 어긋난다
```

문장이 둘인 것에 이유가 있습니다. 앞의 것은 **반복이 끝났을 때 `cur` 를 그대로 돌려줘도 된다**는 것을 말하고, 뒤의
것은 **다음 걸음이 두 칸 앞의 답으로 쓸 값**을 준비합니다. 둘 중 하나만 빠져도 반복의 네 줄이 왜 그 모양인지 근거가
사라져요.

**출발점부터 봅시다.** 반복에 들어가기 전 `cur` 는 `A[0]` 이고 `prev` 는 0 입니다. 칸 0 까지의 선택이 `{}` 와
`{0}` 둘뿐이라 큰 쪽이 `A[0]` 이고, 칸이 없을 때의 답은 0 이라 뒤 문장도 참이에요.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | `prev` 를 0, `cur` 를 `A[0]` 으로 둔다 | 선택이 둘뿐이고 값이 음수가 아니라 큰 쪽이 `A[0]` 이다 | 빈 선택의 합이 0 이다 |
| 임의의 `i` | 같은 네 줄을 실행한다 | 직전 걸음이 `dp[i−1]` 과 `dp[i−2]` 를 만들어 뒀다 | `prev` 가 옛 `cur` 를 받는다 |
| 종료 | `i = N−1` 을 마친다 | `cur` 가 `dp[N−1]` 이다 | 더 쓸 곳이 없다 |

가운데 줄이 이 논증의 핵심입니다. 칸 `i` 까지의 선택은 **칸 `i` 를 담은 것**과 **안 담은 것** 둘로 완전히 갈리고,
앞쪽 무리는 칸 `i−1` 을 못 담으므로 그 무리의 최댓값이 `dp[i−2] + A[i]` 예요.

| 선택의 모양 | 그 무리의 최댓값 | 근거 |
| --- | --- | --- |
| 칸 `i` 를 안 담았다 | `dp[i−1]` | 칸 `i−1` 까지의 선택과 글자 그대로 같은 모임이다 |
| 칸 `i` 를 담았다 | `dp[i−2] + A[i]` | 칸 `i−1` 이 이웃이라 빠지고, 나머지는 칸 `i−2` 까지의 선택이다 |
| 두 무리를 합치면 | 둘 중 큰 것 | 두 무리가 겹치지도 빠지지도 않는다 |

둘째 줄의 `dp[i−2]` 가 직전 걸음의 뒤 문장에서 옵니다. 그 문장이 참이라 `prev` 를 그 자리에 쓸 수 있는 것이고,
그래서 두 문장이 서로를 떠받쳐요. 전개 입력의 걸음마다 두 문장을 정의로 센 값과 대조했습니다.

<!--proof:invariant-hold-->
| 걸음 | 칸 i | prev | 정의로 센 dp[i−1] | cur | 정의로 센 dp[i] |
| --- | ---: | ---: | ---: | ---: | ---: |
| T1 | 0 | 0 | 0 | 2 | 2 |
| T2 | 1 | 2 | 2 | 7 | 7 |
| T3 | 2 | 7 | 7 | 11 | 11 |
| T4 | 3 | 11 | 11 | 11 | 11 |
| T5 | 4 | 11 | 11 | 12 | 12 |
| T6 | 5 | 12 | 12 | 16 | 16 |

6 걸음 모두 prev 가 정의로 센 dp[i−1] 과, cur 가 정의로 센 dp[i] 와 값이 같습니다.

<!--/proof-->

경계에 있는 입력들도 확인하고 갑시다. 반복 횟수와 끝난 뒤의 두 값은 정본을 실행해 센 것이에요.

<!--proof:invariant-edges-->
| 경계 | 입력 | 반복 횟수 | 끝난 뒤 prev | 끝난 뒤 cur | 정본의 답 | 정의로 센 답 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 칸이 하나도 없다 | [] | — | — | — | 0 | 0 |
| 칸이 하나다 | [7] | 0 | 0 | 7 | 7 | 7 |
| 칸이 둘이다 | [2 7] | 1 | 2 | 7 | 7 | 7 |
| 값이 전부 0 이다 | [0 0 0] | 2 | 0 | 0 | 0 | 0 |
| 값이 전부 같다 | [5 5 5 5 5] | 4 | 10 | 15 | 15 | 15 |
| 가운데 하나만 크다 | [1 3 1] | 2 | 3 | 3 | 3 | 3 |
| 최댓값 둘이 이어져 있다 | [10000 10000] | 1 | 10,000 | 10,000 | 10,000 | 10,000 |
| 최댓값 둘이 떨어져 있다 | [10000 1 10000] | 2 | 10,000 | 20,000 | 20,000 | 20,000 |
| 답이 마지막 칸을 안 고른다 | [1 10 1 1] | 3 | 10 | 11 | 11 | 11 |

9 입력 모두 정본의 답이 정의로 센 답과 값이 같습니다.

<!--/proof-->

칸이 없으면 반복에 들어가기 전에 0 이 나가고, 칸이 하나면 반복이 한 번도 실행되지 않아 두 값이 시작값 그대로
남습니다. 최댓값 둘이 이어진 입력에서는 둘 중 하나만 골라지고, `[1 3 1]` 은 가운데 하나를 고르는 것이 양옆
둘보다 큰 자리, `[1 10 1 1]` 은 답이 마지막 칸을 안 고르는 자리예요.

**이제 깨뜨려 봅시다.** 뒤 문장을 지키던 줄은 `prev` 에 옛 `cur` 를 적는 그 한 줄이에요. 「`cur` 만 제대로
정하면 되지 `prev` 를 매번 손볼 필요가 있나」라는 생각으로 그 줄을 지워 봅니다.

```ts
const skip = cur;
const take = prev + (nums[i] as number);
// prev = cur;   ← prev 에 옛 cur 를 적는 이 줄을 지웠다
cur = Math.max(skip, take);
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-prev-frozen-->
| 입력 | 정본이 낸 답 | 옮기기를 뺀 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 [2 7 9 3 1 5] | 16 | 9 | 틀리다 |
| [2 1 1 2] | 4 | 2 | 틀리다 |
| [5 5 5 5 5] | 15 | 5 | 틀리다 |
| [1 3 1] | 3 | 3 | 같다 |
| [2 7] | 7 | 7 | 같다 |

틀린 세 줄은 답이 칸 둘 이상을 고르는 입력입니다.

<!--/proof-->

뒤 문장이 깨지면 `prev` 의 뜻이 바뀌고, 그러면 앞 문장의 근거도 함께 사라집니다. 전개 입력에서 칸마다의 `prev`
를 두 코드로 펼치면 이렇습니다.

<!--proof:mutant-prev-trace-->
| 칸 i | 0 | 1 | 2 | 3 | 4 | 5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 정본의 prev | 0 | 2 | 7 | 11 | 11 | 12 |
| 옮기기를 뺀 prev | 0 | 0 | 0 | 0 | 0 | 0 |

옮기기를 뺀 prev 는 끝까지 0 이라, 고른 답이 A[i] 하나가 됩니다. 그래서 답이 가장 큰 칸 하나의 값 9 가 됩니다.

<!--/proof-->

`prev` 가 「칸 `i−1` 까지의 최대 합」이 아니라 「언제나 0」이 되면, 고른 답은 칸 하나짜리 선택으로 줄어듭니다.
가장 큰 칸 하나가 곧 답인 입력에서는 그것이 우연히 정답과 같아서 `[1 3 1]` 과 `[2 7]` 이 안 틀려요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — 두 값을 시작값으로 두는 것, 칸마다 두 갈래를 만들어 큰 쪽을 고르는 것,
답을 돌려주는 것이에요. 전개의 걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perf-count-->
| 무리 | 걸음 | 걸음 수 | 걸음마다 덧셈 | 걸음마다 비교 | 이 입력에서 |
| --- | --- | ---: | ---: | ---: | ---: |
| 초기화 | T1 | 1 | 0 | 0 | 0 |
| 순회 | T2~T6 | 5 | 1 | 1 | 10 |
| 반환 | T7 | 1 | 0 | 0 | 0 |
| 합계 |  |  |  |  | 10 |

덧셈 5 번과 비교 5 번이고, 둘 다 칸 수 6 에서만 나온 수입니다.

<!--/proof-->

T1 과 T7 은 값을 옮기기만 하는 자리라 덧셈도 비교도 없습니다. T2 부터 T6 까지 다섯 걸음이 걸음마다 덧셈 하나와
비교 하나라, 칸이 `N` 개면 기본 연산이 `2(N − 1)` 이에요. 두 규모에서 실행과 대조했습니다.

<!--proof:perf-total-->
| N | 센 기본 연산 | 2(N − 1) |
| ---: | ---: | ---: |
| 6 | 10 | 10 |
| 100,000 | 199,998 | 199,998 |

두 규모 모두 센 값이 2(N − 1) 과 같습니다.

<!--/proof-->

**연산 수가 입력의 내용과 무관하게 정해집니다.** 값이 크든 0 이든, 답이 어느 칸을 고르든 걸음 수가 같아요 —
칸마다 하는 일이 덧셈 하나와 비교 하나로 고정이기 때문입니다.

```text
여기서 센 것은 덧셈과 비교 전부다
  추가로 잡는 메모리   값 두 개 (prev · cur)
  안 센 것             빈 입력 검사 1 번 · 배열 읽기 N 번 · 반복 변수 증가 N−1 번
                       앞의 하나는 상수이고 뒤의 둘은 칸 수에 비례하므로 총식의 차수는 그대로다
                       └ dp 를 칸마다 저장하는 방식이면 여기에 칸 N 개가 더 붙는다
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (칸이 0 개나 1 개다) | `O(N)` | `Θ(1)` — 반복이 한 번도 실행되지 않는다 |
| **평균적인 경우** (입력 분포와 무관하다) | `O(N)` | `Θ(N)` |
| **최악의 경우** (칸이 `N` 개다) | `O(N)` | `Θ(N)` — 실제로 도달한다 |

가운데와 아래 줄이 같은 것이 이 절차의 성질입니다. 걸음 수가 칸 수 하나로 고정이라 입력의 값을 어떻게 바꿔도
연산 수가 같아요.

```text
상한과 타이트한 값을 가르는 자리
  O(N)   이 절차의 연산 수가 그보다 크지 않다는 것만 말한다      상한이다
  Θ(N)   위아래로 같은 차수라 실제로 그만큼 든다는 것도 말한다   타이트한 값이다
         └ 이 절차는 칸마다 반드시 두 번을 세므로 Θ 로 적을 수 있다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 절차의 특징이에요 — 정렬도, 누적합
배열도, 트리 만들기도 하지 않습니다.

$$\text{시간} = \Theta(N) \;\bigl(\text{덧셈 } N-1 \,+\, \text{비교 } N-1 \,+\, \text{읽기 } N\bigr), \qquad \text{추가 메모리} = \Theta(1) \;(\text{값 두 개})$$

**보장의 종류는 전부 최악 보장입니다.** 해시도, 무작위성도, 분할 상환도 쓰지 않아요 — 어떤 입력을 넣어도 연산 수가
`2N − 2` 로 같습니다.

```text
기댓값이 끼어들 자리가 없다
  칸을 찾는 방법   칸 번호로 바로 간다       해시 충돌이라는 개념이 없다
  걸음 수          입력을 안 보고 정해진다   분포를 가정할 필요가 없다
  칸 하나의 비용   항상 덧셈 1 · 비교 1      평균이 아니라 상수다
                   └ 최악 보장과 평균 비용이 같은 수다
```

#### 최악을 만드는 입력

연산 수를 최대로 만드는 방법은 하나뿐입니다 — **`N` 을 과제 규모의 최댓값으로 두는 것**이에요. 값의 모양은 연산
수를 바꾸지 못합니다. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->
| 입력의 모양 (N = 1,000) | 덧셈 | 비교 | 기본 연산 | 답 |
| --- | ---: | ---: | ---: | ---: |
| 값이 전부 0 | 999 | 999 | 1,998 | 0 |
| 값이 전부 10,000 | 999 | 999 | 1,998 | 5,000,000 |
| 1 과 0 이 번갈아 | 999 | 999 | 1,998 | 500 |
| 마지막 한 칸만 10,000 · 나머지는 0 | 999 | 999 | 1,998 | 10,000 |
| 1 부터 차례로 커진다 | 999 | 999 | 1,998 | 250,500 |

가운데 세 열은 5 줄 모두 값이 같고, 오른쪽 열만 다릅니다.

<!--/proof-->

**「값이 들쭉날쭉하면 갈래를 더 자주 갈아 느리다」는 이 절차에서 거짓입니다.** 셋째 줄은 고르는 갈래와 건너뛰는
갈래가 매 칸 바뀌고 첫째 줄은 한 번도 안 바뀌는데 연산 수가 같아요. 두 답 중 큰 쪽을 고르는 비교가 어느 쪽이
골라지든 한 번이기 때문입니다. 최악은 무엇을 재느냐에 따라 다른 입력이 만듭니다.

<!--proof:worst-axes-->
| 최악으로 만들 것 | 입력 | 값 |
| --- | --- | ---: |
| 기본 연산 수 | N = 100,000, 값은 무엇이든 | 199,998 |
| 들고 가는 칸 | 어떤 입력이든 | 2 |
| 답의 크기 | 10,000 이 100,000 칸 | 500,000,000 |

앞의 둘은 `N` 만 보고, 셋째만 값을 봅니다. 모든 칸이 최댓값이면 한 칸 걸러 고른 5 만 칸이 답이 되고, 그 값은
과제 규모 안에서 가장 크되 `number` 가 정확히 담는 범위 안에 들어요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 칸 `i` 를 고르는지로 선택을 **두 갈래**로 갈랐고, 칸 하나를 고르면
이웃이 빠지므로 고른 답은 **두 칸 앞의 답**에서 이어받으며, 칸 `i` 까지의 최대 합은 앞부분 전체의 답이라 **마지막
칸의 값이 곧 답**입니다.

```text
prev ← 0, cur ← A[0] → 칸마다 skip = cur · take = prev + A[i] → prev ← cur, cur ← max → cur 를 돌려준다
└ 값 두 개             └ 덧셈 1                                 └ 비교 1
```

먼저 답이 붙는 문제 하나입니다. 전개의 T4 는 `A[3] = 3` 을 처리한 걸음이었고, 건너뛴 쪽이 커서 `cur` 가 그대로였어요.
그런데 이 걸음에서도 `prev` 는 바뀝니다. `cur` 가 안 바뀌었는데 `prev` 는 왜 바뀌어야 할까요?

<!--proof:selfcheck-t4-->
```text
T4   A[3] = 3   건너뛴 답 11 · 고른 답 10   cur = 11 그대로   prev = 7 → 11
T5   A[4] = 1   건너뛴 답 11 · 고른 답 prev + 1 = 11 + 1 = 12
```

<!--check:whyPrevMoves-->
두 값이 **가리키는 범위가 다르기** 때문입니다. `cur` 는 「칸 `i` 까지의 최대 합」이고 `prev` 는 「칸 `i−1` 까지의
최대 합」이라, 걸음이 하나 지나면 두 범위가 함께 한 칸 오른쪽으로 가야 해요. T4 를 마친 시점에서 `cur` 는 칸 3
까지의 답이고 `prev` 는 칸 2 까지의 답이어야 하는데, 칸 2 까지의 답이 곧 T3 이 남긴 `cur` 입니다.

T5 가 그 값을 바로 씁니다. 칸 4 를 고른 답이 T4 에서 옮겨진 `prev` 에 1 을 더한 값이에요. `prev` 를 안 옮겼으면
칸 1 까지의 답에 1 을 더하게 되어 칸 4 의 답이 어긋납니다.

| 값 | 보는 범위 | 쓰이는 곳 |
| --- | --- | --- |
| `prev` | 칸 `i−1` 까지 | 다음 걸음의 고른 답 |
| `cur` | 칸 `i` 까지 | 다음 걸음의 건너뛴 답 · 마지막에 돌려주는 답 |

<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 첫째는 「아이디어 상세」의 「이웃한 칸끼리의 관계」, 둘째는 「수행으로 알아보는
알고리즘」의 걸음 표, 셋째는 「이 방법이 기대는 전제」와 「비용 계산」을 다시 보세요.

- 답이 고른 **칸의 번호 목록**까지 함께 돌려주려면 무엇을 더 들고 가야 할까요? 칸마다 두 갈래 중 어느 것이 골라졌는지
  적어 두면 되는데, 그때 잡는 칸이 몇 개가 되는지와 그 칸을 안 쓰고 목록을 얻는 방법이 있는지를 따져 보세요.
- 전개의 T3 은 `cur` 가 7 에서 11 로 바뀐 걸음이었습니다. 만약 칸 1 의 값이 7 이 아니라 20 이었다면 T3 이후의
  `prev` · `cur` 는 어떻게 달라지고, 최종 답은 얼마가 될까요? 걸음 표를 손으로 다시 채워 보세요.
- 첫 칸과 마지막 칸이 이웃인 원형 배열로 바꾸면 이 절차를 어떻게 고쳐야 할까요? 칸 0 을 고르는 경우와 안 고르는
  경우로 갈라 각각 한 번씩 지나가는 방법을 세우고, 그때 기본 연산 수가 몇 번이 되는지 `N` 으로 적어 보세요.

### House Robber

풀 파일: [`houseRobber.ts`](./houseRobber.ts) · 테스트: [`houseRobber.test.ts`](./houseRobber.test.ts) · 실행: `bun test src/algorithms/array/houseRobber/houseRobber.test.ts`

#### 한 줄 요약

> 일렬로 늘어선 집들의 현금 배열을 받아, **인접한 두 집을 동시에 선택하지 않는 조건** 아래 선택 합의 최댓값을 반환한다.

#### 스토리

도둑 기민은 일렬로 늘어선 주택가를 훑어보고 있다. 각 집에는 훔칠 수 있는 현금이 있다.

경보 시스템이 연결되어 있어, 같은 밤에 바로 이웃한 두 집을 연달아 털면 경보가 울린다. 기민은 경보 없이 최대한 많은 돈을 챙기고 싶다.

어떤 집들을 골라야 경보 없이 가장 많은 돈을 가져갈 수 있을까? 집을 한 채도 고르지 않아도 되며 그 경우 수확은 $0$이다.

#### 함수 인터페이스

```ts
export function houseRobber(nums: number[]): number;
```

- `nums` — 각 집의 현금 금액. `nums[i]`는 $i$번째 집의 현금이다.
- 반환 — 인접하지 않은 집들을 선택해 얻을 수 있는 현금 합의 최댓값.

#### 제약 조건

- $0 \leq N \leq 100{,}000$ (여기서 $N$은 `nums`의 길이, 집의 수)
- $0 \leq nums[i] \leq 10{,}000$ (각 집의 현금, 정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

선택한 집의 인덱스 집합 $S$에 대해, 임의의 두 인덱스 $i, j \in S$에 대해 $|i - j| \geq 2$를 만족해야 한다. 즉, 인접한 두 인덱스를 동시에 선택할 수 없다.

답은 $\displaystyle\max_{S}\sum_{i \in S} nums[i]$이다. 집이 없거나($N = 0$), 모든 집의 현금이 $0$이면 답은 $0$이다.

#### 예시

```ts
houseRobber([1, 2, 3, 1]);    // 4  — 인덱스 0, 2 선택: 1+3=4
houseRobber([2, 7, 9, 3, 1]); // 12 — 인덱스 0, 2, 4 선택: 2+9+1=12
houseRobber([2, 1, 1, 2]);    // 4  — 인덱스 0, 3 선택: 2+2=4

houseRobber([]);              // 0  — 집 없음
houseRobber([0, 0, 0]);       // 0  — 현금 없음

houseRobber([5]);             // 5  — 집 하나, 무조건 선택
houseRobber([2, 7]);          // 7  — 둘 중 큰 값만 선택 가능
houseRobber([10000, 1, 10000]); // 20000  — 최댓값 원소 두 개 비인접
```
