# nextGreaterElement — 답을 기다리는 자리를 쌓아 두면 큰 값 하나가 여러 자리의 답을 한꺼번에 정하는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 자리마다
오른쪽을 차례로 읽는 방법에서 출발해 단조 스택에 이르고, 단조 스택을 단계마다 값으로 푼 뒤, 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열의 자리마다 **오른쪽에서 처음 만나는 더 큰 값**을 구합니다. 「더 크다」는 엄격한 부등호라서 같은
값은 답이 되지 않고, 오른쪽에 더 큰 값이 하나도 없으면 그 자리의 답은 `-1` 이에요. 이 과제를 한 번의
순회로 푸는 관찰은 하나입니다. **값 하나를 읽는 순간, 그 값을 답으로 받을 자리가 여럿일 수 있습니다.**
배열 `nums = [2 1 2 4 3]` 에서 자리 3 의 값 4 를 읽기 전과 뒤를 나란히 그렸어요.

<!--fig:concept-one-read-->
![값 4 하나를 읽는 순간 자리 0 과 자리 2 의 답이 함께 정해진다](./figs/concept-one-read.svg)

위 장면에서 `result` 는 자리마다 답을 적는 배열이고, 아직 답이 없는 칸에는 `-1` 이 들어 있습니다. 자리 3
을 읽기 전에는 자리 0 과 자리 2 가 답을 기다리고 있었어요. 값 4 를 읽자 두 자리의 답이 함께 4 로
정해졌습니다. 자리 1 은 그전에 자리 2 의 값 2 를 만나 답을 이미 받았고요.

그러니 **답을 아직 못 받은 자리를 모아 두었다가, 큰 값을 만나는 순간 한꺼번에 답을 적으면** 됩니다.
모아 두는 곳은 스택이고, 담는 것은 값이 아니라 **자리 번호**예요. 이 스택에는 성질이 하나 붙습니다 —
바닥에서 꼭대기로 갈수록 그 자리의 값이 **커지지 않아요.** 이 성질이 붙은 단조 스택을 **단조 스택**이라고
부릅니다. 다섯 자리를 읽을 때마다 단조 스택을 그리면 이렇습니다.

<!--fig:concept-stack-->
![다섯 자리를 읽을 때마다의 단조 스택 — stack 의 값 줄이 늘 커지지 않는다](./figs/concept-stack.svg)

`stack` 줄은 단조 스택이 담은 자리 번호이고, 왼쪽 끝이 바닥, 오른쪽 끝이 꼭대기예요. 그 아래 `stack 의 값`
줄이 그 자리의 값이고, 오른쪽 곁말이 그 값을 바닥에서 꼭대기로 늘어놓은 것입니다. 다섯 장 모두 곁말의
값이 왼쪽에서 오른쪽으로 커지지 않아요. 지금 값보다 작은 꼭대기는 넣기 전에 꺼내고 그 자리의 답을 지금
값으로 적기 때문입니다.

자리마다 한 번 들어가고 많아야 한 번 나오므로 전체 비용은 배열을 한 번 지나는 것과 같은 규모인 `O(N)`
이에요. 여기서 `N` 은 배열의 길이입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **배열의 인덱스.** `nums[i]` 가 `i` 번째 값이고 `i` 는 0 부터 셉니다. 이 글은 인덱스를 「자리」라고도
  부릅니다.
- **스택.** 마지막에 넣은 것이 가장 먼저 나오는 자료구조예요. 넣기 · 꺼내기 · 꼭대기 보기가 각각 한 번에
  끝납니다. 흐릿하면 [`monotonicStack`](../../../data-structures/linear/monotonicStack/monotonicStack.ts)
  을 먼저 봅니다.
- **엄격한 부등호와 느슨한 부등호의 차이.** `a < b` 와 `a ≤ b` 는 `a = b` 인 자리에서 갈립니다. 이 글이
  구하는 답은 「엄격하게 큰 값」이라 그 자리가 답을 바꿉니다.
- **`O(N)` 표기.** 비용이 입력 길이에 비례한다는 뜻입니다.

「오른쪽에서 처음 만나는 어떤 값」이라는 말만으로는 절차가 정해지지 않습니다. **무엇을 묻는가**와 **어느
쪽을 보는가**가 함께 있어야 해요. 같은 배열로 비슷한 물음 넷에 답하면 이렇게 갈립니다.

<!--proof:prereq-four-questions-->

| 물음 | [2 1 2 4 3] 의 답 | 이 글에서 |
| --- | --- | --- |
| 자리마다 오른쪽에서 처음 더 큰 값 | [4 2 4 -1 -1] | 다룬다 |
| 자리마다 왼쪽에서 처음 더 큰 값 | [-1 2 -1 -1 4] | 읽는 방향만 뒤집는다 |
| 자리마다 오른쪽에서 처음 더 작은 값 | [1 -1 -1 3 -1] | 부등호만 뒤집는다 |
| 길이 3 인 창마다 최댓값 | [2 4 4] | 다루지 않는다. 넣고 빼는 쪽이 둘이다 |

창이 움직이는 물음은 양 끝에서 넣고 빼는 자료구조가 필요해
[`slidingWindowMaximum`](../slidingWindowMaximum/slidingWindowMaximum-guide.md) 쪽이고, 답을 값이 아니라
넓이로 묶는 물음은 [`largestRectangleInHistogram`](../largestRectangleInHistogram/largestRectangleInHistogram-guide.md)
쪽입니다.

### 아이디어를 떠올리는 과정 — 자리마다 오른쪽을 차례로 읽기에서 단조 스택까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열을 받아, 자리마다
오른쪽에서 처음 만나는 더 큰 값을 담은 배열을 돌려줍니다.

```ts
function nextGreaterElement(nums: number[]): number[];
```

- 입력: 정수 배열 `nums`. 값은 32 비트 정수 범위입니다.
- 출력: 길이가 같은 배열. `i` 번째 값은 `nums[i]` 보다 **오른쪽**에 있는 값 중 처음으로 **엄격하게** 큰
  값이고, 그런 값이 없으면 `-1` 입니다. 마지막 자리는 언제나 `-1` 이에요.
- 규모: 배열 길이 `N` 은 1 이상 100,000 이하로 둡니다. 이 규모를 고른 까닭은 `N²` 이 흔한 채점 환경의
  예산인 1 초(단순 연산 1 초에 1 억 번)를 넘기 시작하는 규모라서, 단순한 방법과 이 글의 절차가 확실히
  갈리기 때문이에요.
- 비용은 **배열 접근 수**로 셉니다. `nums` 를 읽은 횟수와 답 배열 · 단조 스택을 읽고 쓴 횟수를 모두 더한
  값이고, 이 글 끝까지 이 기준 하나만 씁니다. 메모리는 입력 밖에 **추가로 잡는 칸 수**로 셉니다.

이 글이 끝까지 쓰는 기호를 여기서 정합니다.

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| `N` | 배열 `nums` 의 길이 | `1 ≤ N ≤ 100,000` |
| `nums[i]` | 배열의 `i` 번째 값. 0 부터 셉니다 | 32 비트 정수 |
| `i` | 지금 읽고 있는 자리 | `0 ≤ i < N` |
| `cur` | 지금 값 `nums[i]` | — |
| `result[i]` | 자리 `i` 의 답. 없으면 `-1` | 길이가 `N` 입니다 |
| `stack` | 답을 아직 못 받은 자리를 담은 단조 스택 | 값이 아니라 자리 번호를 담습니다 |
| `top` | `stack` 꼭대기에 있는 자리 | 단조 스택이 비면 없습니다 |
| `P` | 한 번의 실행에서 자리를 꺼낸 횟수 | `0 ≤ P ≤ N − 1` |
| `B` | 꼭대기가 남은 채로 꺼내기를 멈춘 걸음의 수 | `0 ≤ B ≤ N − 1` |
| `S` | 순회가 끝났을 때 `stack` 에 남은 자리의 수 | `1 ≤ S ≤ N` |

가장 먼저 떠오르는 방법은 정의를 글자 그대로 옮기는 것입니다. 자리마다 자기 오른쪽을 차례로 읽고, 처음
만나는 더 큰 값에서 멈춰요.

```ts
function scanRight(nums: number[]): number[] {
  const result = new Array<number>(nums.length).fill(-1);
  for (let i = 0; i < nums.length; i++) {
    const cur = nums[i] ?? 0;
    for (let j = i + 1; j < nums.length; j++) {
      const v = nums[j] ?? 0;
      if (v > cur) {
        result[i] = v; // 처음 만난 더 큰 값에서 멈춘다
        break;
      }
    }
  }
  return result;
}
```

이 방법은 답을 틀리지 않습니다. 문제는 **오른쪽에 더 큰 값이 없을 때**예요 — 그때는 배열 끝까지 읽고도
아무것도 못 얻습니다. 감소 수열이면 모든 자리가 그렇고, 이 방법의 최악이 됩니다. 이 방법과 이 글이 만들
절차를 같은 기준으로 세면 이렇습니다.

<!--proof:origin-naive-scale-->

| N | 차례로 읽기의 배열 접근 | 이 글이 만들 절차의 배열 접근 | 차례로 읽기의 시간(초당 1 억 번) |
| ---: | ---: | ---: | ---: |
| 1,000 | 501,500 | 4,998 | 0.01 초 |
| 10,000 | 50,015,000 | 49,998 | 0.50 초 |
| 100,000 | 5,000,150,000 | 499,998 | 50.00 초 |

입력은 감소 수열입니다. N = 1,000 · 10,000 은 실제로 세었고, N = 100,000 은 두 실측과 맞는 식 2N + N(N−1)/2 와 5N − 2 에 넣은 값입니다.

<!--/proof-->

`N = 100,000` 에서 차례로 읽는 방법은 50 억 번을 넘게 접근해 예산 1 초의 오십 배가 걸립니다. 어디서
그만큼 늘어나는지 작은 입력에서 봅시다. `nums = [2 1 2 4 3]` 에서 자리마다 읽은 칸을 그렸어요.

<!--fig:origin-scan-->
![자리마다 오른쪽을 차례로 읽으면 — 자리 3 을 자리 0 과 자리 2 가 따로 읽는다](./figs/origin-scan.svg)

괄호가 그 자리에서 읽은 칸이고 ▲ 가 멈춘 칸입니다. 같은 것을 표로 옮기면 이렇습니다.

<!--proof:origin-scan-small-->

| 자리 i | nums[i] | 읽은 자리 | 멈춘 값 | 읽은 칸 수 |
| ---: | ---: | --- | --- | ---: |
| 0 | 2 | 1 · 2 · 3 | 4 | 3 |
| 1 | 1 | 2 | 2 | 1 |
| 2 | 2 | 3 | 4 | 1 |
| 3 | 4 | 4 | 못 찾았다 | 1 |
| 4 | 3 | 없음 | 못 찾았다 | 0 |

다섯 자리가 읽은 칸은 모두 6 칸이고, 두 자리 이상이 거듭 읽은 칸은 자리 2 · 3 입니다. 자리 3 의 값 4 를 자리 0 · 2 가 따로 읽었습니다.

<!--/proof-->

값 4 하나가 자리 0 과 자리 2 **둘의 답**인데, 이 방법은 그 값을 자리마다 따로 읽습니다. 여기서 물음의
방향을 뒤집어 봅시다. 「자리 `i` 의 답이 무엇인가」가 아니라 **「지금 읽은 값이 누구의 답인가」** 로요.
자리 3 의 값 4 를 읽었을 때, 그 왼쪽 자리들이 4 를 답으로 받는지 따져 봤습니다.

<!--proof:origin-who-receives-->

| 자리 | 그 값 | 4 > 그 값 | 자리 3 을 읽기 전에 정해진 답 | 답 4 |
| --- | ---: | --- | --- | --- |
| 자리 0 | 2 | 참 | 아니다 | 받는다 |
| 자리 1 | 1 | 참 | 예 · 답 2 | 못 받는다 |
| 자리 2 | 2 | 참 | 아니다 | 받는다 |

자리 1 도 4 보다 작지만 4 를 받지 않습니다. 자리 2 의 값 2 가 먼저 1 을 넘어서 답이 이미 정해졌기
때문이에요. 그러니 **4 를 받을 자리는 답을 아직 못 받은 자리 중에서만** 나옵니다. 답을 못 받은 자리를
어딘가에 남겨 두면, 값 하나를 읽을 때 그 자리들만 보면 돼요.

답을 기다리는 자리를 남겨 두고 지금 값을 가장 나중에 남긴 자리부터 보는 방식을, 차례로 읽는 방식과 같은
입력에서 세어 봅시다. 뒤엣것이 무엇인지는 아래에서 차례로 세우고, 여기서는 비용만 봅니다.

<!--proof:origin-two-ways-->

| 입력 | 차례로 읽기 | 기다리는 자리를 남겨 두고 꼭대기부터 보기 |
| --- | ---: | ---: |
| 전개 입력 [2 1 2 4 3] | 19 | 30 |
| nums[i] = (7919 i) mod 1009 인 1,024 칸 | 11,316 | 8,146 |
| 감소 수열 1,024 칸 | 525,824 | 5,118 |

다섯 칸에서는 뒤엣것이 11 번 더 많고, 1,024 칸 두 입력에서는 적습니다. 두 방식이 낸 답은 세 입력 모두 서로 일치합니다.

<!--/proof-->

다섯 칸에서는 남겨 두는 쪽이 오히려 많습니다. 답 배열을 깔고 자리를 넣는 몫이 다섯 칸에서는 크게
보이기 때문이에요. 칸이 1,024 개로 늘면 순서가 바뀝니다. 여기서 관찰할 것은 **답을 기다리는 자리를
남겨 두면 오른쪽을 다시 읽을 필요가 없어진다**는 것 하나입니다. 남은 물음은 「무엇을 얼마나 남기고,
어디서 멈추는가」예요.

가장 단순한 후보부터 시험해 봅시다. **기다리는 자리를 몇 개까지만 남기는 것**이에요. 남길 자리 수에
상한을 두고, 넘치면 가장 오래된 자리를 버립니다. 버린 자리는 답을 못 받고 `-1` 로 남아요. 상한을 바꿔
가며 틀린 자리를 셌고, 마지막 줄에는 전부 남기되 꼭대기에서 멈추지 않고 아래까지 비교한 방식을 넣었습니다.

<!--proof:origin-keep-how-many-->

| 남기는 자리 수 | 배열 접근 | 틀린 자리 |
| --- | ---: | ---: |
| 1 | 5,274 | 858 |
| 2 | 5,739 | 703 |
| 4 | 6,669 | 393 |
| 8 | 8,092 | 18 |
| 12 | 8,128 | 6 |
| 13 | 8,137 | 3 |
| 14 | 8,146 | 0 |
| 전부(1,024) | 8,146 | 0 |
| 전부 · 아래까지 비교 | 20,594 | 0 |

입력은 nums[i] = (7919 i) mod 1009 인 1,024 칸이고, 틀린 자리가 0 이 되는 것은 14 부터입니다. 감소 수열 1,023 칸 뒤에 가장 큰 값 하나를 둔 입력에서는 1,023 부터입니다.

<!--/proof-->

두 가지가 나왔습니다. 첫째, **남기는 자리 수에 상한을 둘 수 없습니다.** 이 입력에서는 14 개면 됐지만,
감소 수열 뒤에 큰 값 하나를 붙이면 1,023 개를 남겨야 해요. 버린 자리는 답을 영영 못 받으니, 기다리는
자리는 전부 남겨야 합니다. 둘째, **전부 남기고 아래까지 비교하면 차례로 읽는 방법보다 비용이 많아집니다.**
꼭대기에서 멈춘 줄은 같은 답을 훨씬 적게 접근해 냈어요. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **단조 스택**입니다. 답을 기다리는 자리를 전부 단조 스택에 남기고, 지금 값보다 작은
꼭대기를 꺼내 답을 적다가, 꼭대기가 지금 값보다 작지 않으면 멈춰요. 꼭대기에서 멈춰도 답이 틀리지 않는
까닭과, 단조 스택이 어떻게 생겼고 어떻게 채워지는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 단조 스택

이 아이디어를 한 문장으로 줄이면 이렇습니다. **답을 아직 못 받은 자리를 읽은 차례대로 단조 스택에 쌓아 두고,
새 값을 읽을 때마다 그 값보다 작은 꼭대기를 꺼내 답을 적은 뒤 새 자리를 넣습니다.** 이 방법이 기대는
구조는 단조 스택 하나인데, 처음 보는 사람에게는 「단조 스택이 왜 저절로 정렬된 모양이 되는가」가 낯설어요.
그래서 단조 스택을 먼저 따로 설명하고, 그다음 실현하는 순서대로 세 단계를 설명합니다. 첫 단계는 순회 전에
한 번, 나머지 둘은 자리마다 합니다.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 순회 전에 한 번 | 1단계 답 배열 준비 | `result` 를 `-1` 로 채우고 빈 `stack` 을 잡는다 | — |
| 자리마다 | 2단계 꺼내고 답 적기 | 꼭대기가 `cur` 보다 작은 동안 꺼내고 `result` 에 `cur` 를 적는다 | 1단계의 `result` · `stack` |
| 자리마다 | 3단계 지금 자리 넣기 | 꺼내기가 멈추면 `i` 를 넣는다 | 2단계가 남긴 `stack` |

#### 먼저 알아 둘 개념 — 단조 스택

단조 스택은 **답을 아직 못 받은 자리를 읽은 차례대로 쌓은 단조 스택으로, 쌓인 자리의 값이 바닥에서 꼭대기로
가며 커지지 않는 것**입니다. 바닥에 있는 자리일수록 먼저 읽은 자리이고, 꼭대기가 가장 나중에 읽은
자리예요. 단조 스택의 칸 `k` 에 든 자리를 `stack[k]` 라고 쓰면 식으로는
`nums[stack[0]] ≥ nums[stack[1]] ≥ … ≥ nums[stack[top]]` 입니다.

##### 입력 위의 단조 스택

자리 2 까지 읽은 순간의 단조 스택을 입력 배열 위에 그렸습니다. 대시 칸은 이미 답을 받아 단조 스택에서 빠진
자리, 점선 칸은 아직 안 읽은 자리예요.

<!--fig:build-on-input-->
![자리 2 까지 읽은 뒤의 단조 스택 — 칸마다 nums 의 한 자리를 가리킨다](./figs/build-on-input.svg)

`nums` 줄에서 실선으로 남은 칸이 자리 0 과 자리 2 이고, 그 둘이 `stack` 줄에 바닥부터 들어 있습니다. 자리
1 은 자리 2 의 값 2 를 만나 답을 받았으므로 단조 스택에 없어요. 단조 스택은 읽은 자리 가운데 **답을 기다리는 것만**
골라 순서대로 적은 목록인 셈입니다.

##### 칸 하나를 읽는 법

꼭대기 칸 `stack[1]` 을 골라 이름에서 입력의 자리와 값, 답까지 따라가 봅시다.

<!--proof:build-read-one-->

| 차례 | 읽는 것 | 나오는 것 |
| ---: | --- | --- |
| 1 | stack[1] | 자리 2 |
| 2 | nums[2] | 값 2 |
| 3 | result[2] | -1 — 아직 답이 없다 |
| 4 | 답을 받는 때 | 자리 3 의 4 를 읽을 때 4 를 받는다 |

단조 스택의 칸에 든 수는 자리 번호이지 값이 아닙니다. 값은 그 번호로 `nums` 를 한 번 더 읽어야 나오고, 답을
적을 곳도 그 번호로 정해져요.

##### 이웃한 두 칸의 관계

단조 스택에서 바로 이웃한 두 칸을 모두 모아, 두 값의 크기와 두 자리 사이에 있던 자리가 어떻게 됐는지 쟀습니다.

<!--proof:build-neighbors-->

| 아래 칸 | 바로 위 칸 | 아래 칸의 값 ≥ 위 칸의 값 | 두 자리 사이에 있던 자리 |
| --- | --- | --- | --- |
| 자리 0 · 값 2 | 자리 1 · 값 1 | 예 | 없음 |
| 자리 0 · 값 2 | 자리 2 · 값 2 | 예 | 자리 1 · 답 2 |
| 자리 3 · 값 4 | 자리 4 · 값 3 | 예 | 없음 |

전개 입력에서 이웃한 두 칸이 3 쌍 나왔습니다. 1,024 칸 입력에서는 자리를 넣은 순간마다 이웃한 두 칸 7,240 쌍을 쟀고, 아래 칸의 값이 더 작거나 사이에 답을 못 받은 자리가 남은 쌍은 0 개입니다.

<!--/proof-->

아래 칸의 값은 늘 위 칸의 값 이상이고, 두 자리 사이에 있던 자리는 전부 이미 답을 받았습니다. 둘째 줄의
자리 1 이 그 예예요. 이웃한 두 칸 사이에 답을 기다리는 자리가 남아 있다면 그 자리도 단조 스택에 있어야 하므로,
두 칸은 이웃일 수 없습니다.

##### 읽은 값을 정렬한 목록과의 차이

단조 스택을 처음 보면 「읽은 값을 크기순으로 정렬해 두는 것」으로 읽기 쉽습니다. 값이 정렬된 모양이니까요.
같은 입력에서 둘을 나란히 놓았습니다.

<!--proof:build-vs-sorted-->

| 읽은 마지막 자리 | 읽은 값을 큰 것부터 정렬한 목록 | 단조 스택의 값 | 목록 칸 수 | 단조 스택 칸 수 |
| ---: | --- | --- | ---: | ---: |
| 0 | [2] | [2] | 1 | 1 |
| 1 | [2 1] | [2 1] | 2 | 2 |
| 2 | [2 2 1] | [2 2] | 3 | 2 |
| 3 | [4 2 2 1] | [4] | 4 | 1 |
| 4 | [4 3 2 2 1] | [4 3] | 5 | 2 |

1,024 칸 입력을 끝까지 읽으면 정렬한 목록은 1,024 칸이 되고, 단조 스택은 가장 깊을 때가 15 칸, 끝났을 때가 10 칸입니다.

<!--/proof-->

정렬한 목록은 읽은 값을 **전부** 들고 있어 칸 수가 읽은 자리 수와 같습니다. 단조 스택은 답을 받은 자리를
버리므로 훨씬 짧아요. 자리 2 까지 읽은 줄에서 목록에는 1 이 남아 있지만 단조 스택에는 없습니다. 값이 정렬된
모양이 되는 것은 정렬해서가 아니라, 작은 꼭대기를 꺼내고 나서 넣기 때문이에요. 새 값을 목록 가운데
끼워 넣는 일이 없으니 넣기도 꼭대기에서 한 번에 끝납니다.

##### 꼭대기에서 멈춰도 되는 까닭

이 모양이 필요한 까닭은 「아이디어를 떠올리는 과정」에서 남긴 물음 — **어디서 멈추는가** — 에 있습니다.
값이 바닥에서 꼭대기로 커지지 않으면, 꼭대기가 지금 값 이상일 때 그 아래 칸은 전부 꼭대기 이상이라 더더욱
지금 값 이상입니다. 그러니 아래를 볼 필요가 없어요. 멈춘 걸음마다 아래 칸까지 실제로 확인해 봤습니다.

<!--proof:build-why-stop-->

| 입력 | 꼭대기에서 멈춘 걸음 | 그 아래 칸까지 전부 지금 값 이상이던 걸음 |
| --- | ---: | ---: |
| 전개 입력 | 3 | 3 |
| 1,024 칸 입력 | 1,016 | 1,016 |
| 감소 수열 1,024 칸 | 1,023 | 1,023 |

세 입력 모두 두 열이 같습니다. 꼭대기에서 멈춘 모든 걸음에서 아래 칸도 전부 지금 값 이상이었어요. 값이
커지지 않는 모양이 왜 늘 유지되는지는 아래 두 줄로 닫힙니다.

```text
자리 j 와 자리 k 가 둘 다 스택에 있고 j < k 라면
    nums[j] < nums[k] 일 수 없다 — 그랬다면 자리 k 를 읽을 때 자리 j 가 꺼내져 답을 받았다
    그러니 nums[j] ≥ nums[k] 다. 스택에서 바닥 쪽 자리의 값이 꼭대기 쪽 자리의 값 이상이다
```

#### 1단계 — 답 없음으로 채운 답 배열 준비

순회를 시작하기 전에 `result` 를 길이 `N` 으로 잡아 모든 칸에 `-1` 을 채우고, 빈 `stack` 을 잡습니다.
`-1` 을 미리 까는 까닭은 **끝까지 한 번도 꺼내지지 않는 자리가 늘 있기** 때문이에요. 그 자리는 오른쪽에
더 큰 값이 없었다는 뜻이고, 답이 바로 `-1` 입니다. 입력 셋에서 끝까지 남은 자리를 확인했습니다.

<!--proof:build-leftover-->

| 입력 | 끝까지 단조 스택에 남은 자리 | 그 자리의 답 |
| --- | --- | --- |
| [2 1 2 4 3] | 3 · 4 | -1 · -1 |
| [1 2 3 4] | 3 | -1 |
| [4 3 2 1] | 0 · 1 · 2 · 3 | -1 · -1 · -1 · -1 |

마지막 자리는 오른쪽이 비어 있으니 언제나 남습니다. 남은 자리의 답이 모두 `-1` 인 것은 1단계가 깔아 둔
값이 그대로 남은 것이에요. 그래서 순회가 끝난 뒤에 단조 스택을 비우며 뒷정리하는 코드가 따로 필요 없습니다.

#### 2단계 — 꼭대기부터 비교해 꺼내고 답 적기

자리 `i` 를 읽으면 지금 값 `cur` 를 꼭대기 자리의 값과 비교합니다. 꼭대기의 값이 `cur` 보다 **엄격하게
작으면** 꺼내고 그 자리의 답에 `cur` 를 적은 뒤, 새 꼭대기와 다시 비교해요. 꺼내기가 멈추는 경우는
둘뿐입니다 — 단조 스택이 비었거나, 꼭대기의 값이 `cur` 이상이거나. 다섯 자리에서 실제로 어떻게 됐는지
모았습니다.

<!--proof:build-pop-steps-->

| 읽은 자리 | 읽기 전 stack | 꺼낸 자리(차례대로) | 꺼내기가 멈춘 까닭 |
| --- | --- | --- | --- |
| 0 · 값 2 | 비었다 | 없음 | 단조 스택이 비었다 |
| 1 · 값 1 | [0] | 없음 | 꼭대기 자리 0 의 값 2 ≥ 1 |
| 2 · 값 2 | [0 1] | 1 | 꼭대기 자리 0 의 값 2 ≥ 2 |
| 3 · 값 4 | [0 2] | 2 · 0 | 단조 스택이 비었다 |
| 4 · 값 3 | [3] | 없음 | 꼭대기 자리 3 의 값 4 ≥ 3 |

가장 불안한 자리는 둘입니다. 하나는 자리 3 처럼 **한 번에 여럿을 꺼내는** 자리예요. 꼭대기 자리 2 를
꺼내고 새 꼭대기 자리 0 도 4 보다 작아 이어서 꺼냈고, 단조 스택이 비어서 멈췄습니다. 다른 하나는 자리 2 처럼
**같은 값에서 멈추는** 자리예요. 자리 1 을 꺼낸 뒤 꼭대기 자리 0 의 값이 2 로 지금 값과 같았고, 같은 값은
답이 아니므로 멈췄습니다. 자리 0 은 남아서 나중에 4 를 받아요.

이 단계를 코드로 적으면 조건 하나와 반복 하나입니다.

```ts
while (stack.length > 0) {
  const top = stack[stack.length - 1] ?? 0;
  if ((nums[top] ?? 0) >= cur) break; // 꼭대기가 cur 이상이면 멈춘다
  stack.pop();
  result[top] = cur;
}
```

반복이 끝나면 `stack.length === 0` 이거나 꼭대기의 값이 `cur` 이상입니다. 앞의 경우에는 꺼낼 것이 없고,
뒤의 경우에는 「꼭대기에서 멈춰도 되는 까닭」에서 본 대로 아래 칸도 전부 `cur` 이상이에요. 그래서 `cur`
를 답으로 받아야 하는 자리 가운데 빠진 것이 없습니다.

#### 3단계 — 지금 자리 넣기

꺼내기가 멈추면 지금 자리 `i` 를 넣습니다. 자리 `i` 는 방금 읽혔고 오른쪽을 아직 하나도 못 봤으니 답이
없는 자리이고, 넣는 것이 정의 그대로예요. 넣는 순간 `nums[i]` 는 남은 꼭대기의 값 이하이므로 값이 커지지
않는 모양이 그대로 이어집니다. 자리마다 언제 들어가고 언제 나왔는지 모았습니다.

<!--proof:build-once-->

| 자리 | 넣은 때 | 꺼낸 때 |
| --- | --- | --- |
| 자리 0 | 자리 0 을 읽을 때 | 자리 3 을 읽을 때 |
| 자리 1 | 자리 1 을 읽을 때 | 자리 2 를 읽을 때 |
| 자리 2 | 자리 2 를 읽을 때 | 자리 3 을 읽을 때 |
| 자리 3 | 자리 3 을 읽을 때 | 끝까지 남았다 |
| 자리 4 | 자리 4 를 읽을 때 | 끝까지 남았다 |

1,024 칸 입력에서는 넣기가 1,024 자리에 1,024 번, 꺼내기가 1,014 자리에 1,014 번이었습니다. 한 자리를 넣은 횟수는 많아야 1 번, 꺼낸 횟수도 많아야 1 번입니다.

<!--/proof-->

자리마다 **한 번 들어가고 많아야 한 번 나옵니다.** 넣기는 자리마다 정확히 한 번이라 모두 `N` 번이고,
꺼내기는 들어간 자리만 할 수 있으니 `P ≤ N` 이에요. 마지막 자리는 늘 남으므로 `P ≤ N − 1` 입니다. 단조 스택의
크기는 비었을 때 0 칸, 가장 깊을 때 많아야 `N` 칸이에요.

#### 이 방법이 기대는 전제

단조 스택은 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 답의 기준이 두 값의 크기 비교다 | 2단계에서 꼭대기 하나로 아래 칸 전부를 판정한다 | 「오른쪽에서 처음 나오는 짝수」처럼 비교가 아닌 기준이면 앞 값이 뒤 값을 가리지 못해 멈출 근거가 없다 |
| 한쪽 방향으로 처음 만나는 값을 묻는다 | 3단계가 넣은 자리는 오른쪽에서 오는 값만 기다린다 | 양쪽을 다 보거나 창이 움직이면 단조 스택 한쪽 끝으로는 넣고 빼기가 모자라다 |
| 답을 만드는 동안 배열이 바뀌지 않는다 | 꺼내며 적은 답을 다시 보지 않는다 | 값 하나가 바뀌면 이미 적은 답이 통째로 낡는다 |

부등호가 같은 값에서 어떻게 갈리는지는 이 전제가 아니라 설계 그 자체입니다. 같은 값에서 멈추지 않으면 답이
어떻게 틀리는지는 「불변식」 절에서 실행 결과로 보고, 배열이 바뀔 때의 비용은 「경쟁 설계와의 대조」에서
잽니다.

#### 단조 스택에 자리 번호를 담는 까닭

단조 스택에 값을 담아도 비교는 똑같이 됩니다. 그런데 꺼낸 값의 답을 **어느 칸에 적을지**를 알 수 없어요. 값을
담고, 꺼낸 값이 처음 나오는 자리를 찾아 답을 적는 코드를 같은 입력들로 실행했습니다.

<!--proof:build-store-value-->

| 입력 | 자리를 담는 코드 | 값을 담는 코드 | 답 |
| --- | --- | --- | --- |
| [2 1 2 4 3] | [4 2 4 -1 -1] | [4 2 -1 -1 -1] | 다르다 |
| [1 2 3 4] | [2 3 4 -1] | [2 3 4 -1] | 같다 |
| [3 1 3 2] | [-1 3 -1 -1] | [-1 3 -1 -1] | 같다 |
| [2 7 3 5 1 6] | [7 -1 5 6 6 -1] | [7 -1 5 6 6 -1] | 같다 |

4 벌 중 1 벌에서 답이 다릅니다. 답이 갈린 벌은 모두 같은 값이 두 번 이상 나오는 입력입니다.

<!--/proof-->

값이 모두 다른 입력에서는 값이 곧 자리를 가리키니 답이 맞습니다. 같은 값이 두 번 나오면, 두 번째 2 의 답
4 가 첫 번째 2 의 칸에 겹쳐 적히고 두 번째 2 의 칸은 `-1` 로 남아요. 자리 번호를 담으면 이런 찾기가 필요
없고, 같은 값이 몇 번 나와도 칸이 섞이지 않습니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 네 걸음입니다. 2단계와 3단계가 자리 하나의 반복 한 바퀴예요.

1. `result` 를 `-1` 로 채우고 빈 `stack` 을 잡는다
2. 자리 `i` 를 0 부터 `N − 1` 까지 읽으며, 꼭대기의 값이 `cur` 보다 작은 동안 꺼내고 `result[top] = cur` 를 적는다
3. 꺼내기가 멈추면 `i` 를 넣는다
4. 순회가 끝나면 `result` 를 돌려준다 — 단조 스택에 남은 자리는 1 이 깐 `-1` 을 그대로 쓴다

### 수행으로 알아보는 알고리즘 — 다섯 칸을 아홉 걸음으로 지난다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const nums = [2, 1, 2, 4, 3];
// 이 절이 끝나면 [4, 2, 4, -1, -1] 이 나와야 한다
```

이 다섯 칸을 고른 까닭은 **갈래를 전부 실행하기** 때문이에요. 같은 값 2 가 두 번 나와서 엄격한 부등호가
실제로 쓰이고, 값 4 하나가 두 자리를 한꺼번에 꺼내며, 마지막 두 자리는 답을 못 받고 남습니다.

```text
nextGreaterElement(nums):
    result 를 -1 로 채운다 (길이 N)                                  ①
    stack 을 빈 스택으로 잡는다
    자리 i 를 0 부터 N-1 까지 읽으며:
        꼭대기가 있고 그 값이 nums[i] 보다 엄격하게 작은 동안         ②
            꺼내고 그 자리의 답에 nums[i] 를 적는다                   ③
        지금 자리 i 를 넣는다                                         ④
    result 를 돌려준다 — 남은 자리는 ① 이 깐 -1 그대로다              ⑤
```

#### 1. 답 배열을 -1 로 깔고 빈 stack 을 잡는다

답이 없다는 표시를 미리 깔아 두면 순회 뒤의 뒷정리가 사라집니다. 이 조각이 그 일을 해요.

```ts
const n = nums.length;
const result = new Array<number>(n).fill(-1); // ① 답 없음을 초기값으로 깐다
const stack: number[] = [];
```

실행하면 이렇게 나옵니다. 빈 배열이 여기서 이미 처리된다는 것이 이 세 줄의 두 번째 일이에요.

<!--proof:walk-init-->

| nums | result | stack | 순회 |
| --- | --- | --- | --- |
| [2 1 2 4 3] | [-1 -1 -1 -1 -1] | [] | 자리 0 부터 4 까지 |
| [] | [] | [] | 들어가지 않는다 |

#### 2. 꼭대기와 비교해 엄격하게 작을 때만 꺼낸다

한 걸음의 핵심이 이 조각입니다. 꼭대기가 가리키는 값을 지금 값과 비교해, 엄격하게 작을 때만 꺼내 답을
적어요.

```ts
const cur = nums[i] ?? 0;
while (stack.length > 0) {
  const top = stack[stack.length - 1] ?? 0;
  // ② 꼭대기의 값이 지금 값보다 **엄격하게** 작을 때만 꺼낸다.
  if ((nums[top] ?? 0) >= cur) break;
  stack.pop();
  result[top] = cur; // ③ 꺼낸 자리의 답이 지금 값으로 정해진다
}
```

`i = 3`(값 4)에서 이 조각만 실행하면 두 번 꺼냅니다. 그 앞의 `stack` 은 자리 0 과 자리 2 를 담고 있어요.

<!--proof:walk-pop-at-3-->

| 차례 | 꼭대기 | 그 값 | 조건 | 하는 일 | stack | result |
| ---: | --- | ---: | --- | --- | --- | --- |
| 1 | 자리 2 | 2 | `2 >= 4` 거짓 | 꺼낸다 | [0] | [-1 2 4 -1 -1] |
| 2 | 자리 0 | 2 | `2 >= 4` 거짓 | 꺼낸다 | [] | [4 2 4 -1 -1] |
| 3 | 없다 | — | `stack.length > 0` 거짓 | 반복이 끝난다 | [] | [4 2 4 -1 -1] |

여기서 가장 중요한 줄은 `if ((nums[top] ?? 0) >= cur) break;` 입니다. `>=` 로 적힌 조건이 「엄격하게 작을
때만 꺼낸다」의 다른 표현이에요. 꼭대기의 값이 지금 값과 **같을 때도 멈춰야** 합니다 — 같은 값은 답이
되지 않으니까요.

#### 짚고 가기 — 꺼내기를 한 번만 하면 왼쪽에 남은 자리가 답을 못 받는다

여기서 헷갈리기 쉬운 포인트는 `while` 입니다. 「한 걸음에 한 자리씩만 꺼내도 결국 다 꺼내지지 않나」로
읽히는데, **꺼낼 자리가 여럿인 걸음이 실제로 있습니다.** `while` 을 한 번만 실행되는 반복으로 바꾼 코드가
자리마다 무엇을 꺼내는지 따라가 봤어요.

<!--proof:pause-once-trace-->

| 읽은 자리 | 바른 코드가 꺼낸 자리 | 한 번만 꺼내는 코드가 꺼낸 자리 |
| --- | --- | --- |
| 0 · 값 2 | 없음 | 없음 |
| 1 · 값 1 | 없음 | 없음 |
| 2 · 값 2 | 1 | 1 |
| 3 · 값 4 | 2 · 0 | 2 |
| 4 · 값 3 | 없음 | 없음 |

자리 3 을 읽을 때 바른 코드는 자리 2 와 자리 0 을 꺼내는데, 한 번만 꺼내는 코드는 자리 2 에서 멈춥니다.
자리 0 은 단조 스택에 남고, 자리 4 의 값 3 은 꼭대기 자리 3 의 값 4 보다 작아 아무것도 못 꺼내요. 자리 0 의
답은 `-1` 로 끝납니다. 여러 입력으로 실행하면 이렇습니다.

<!--proof:pause-once-only-->

| 입력 | 바른 코드 | 한 번만 꺼내는 코드 | 답 |
| --- | --- | --- | --- |
| [2 1 2 4 3] | [4 2 4 -1 -1] | [-1 2 4 -1 -1] | 다르다 |
| [1 2 3 4] | [2 3 4 -1] | [2 3 4 -1] | 같다 |
| [4 3 2 1] | [-1 -1 -1 -1] | [-1 -1 -1 -1] | 같다 |
| [1 5 2 6] | [5 6 6 -1] | [5 -1 6 -1] | 다르다 |

4 벌 중 2 벌에서 답이 다릅니다.

<!--/proof-->

**답이 같은 두 줄이 이 짚고 가기를 두는 이유입니다.** 증가 수열은 걸음마다 한 자리씩만 꺼내고 감소 수열은
아무것도 안 꺼내므로, 한 번만 꺼내도 답이 안 틀려요. 한 걸음에 두 자리 이상을 꺼내야 하는 입력이 시험에
하나라도 있어야 이 줄이 검사되고, 그런 입력이 없는 시험은 이 코드를 통과시킵니다.

#### 3. 더 꺼낼 것이 없으면 지금 자리를 넣는다

꺼내기가 끝나면 지금 자리를 넣습니다. 지금 자리는 자기 답을 아직 못 받은 자리이므로 넣는 것이 단조 스택의
정의 그대로예요.

```ts
stack.push(i); // ④ 답이 아직 없는 자리로 넣는다
```

넣는 자리가 언제나 꼭대기가 되고, 꺼내기가 먼저 끝났으므로 그 값이 단조 스택 안에서 가장 작습니다.

<!--proof:walk-push-->

| 읽은 자리 | 꺼내기가 끝난 뒤 stack | 넣은 뒤 stack | 넣은 뒤 그 값(바닥 → 꼭대기) |
| ---: | --- | --- | --- |
| 0 | [] | [0] | 2 |
| 1 | [0] | [0 1] | 2 ≥ 1 |
| 2 | [0] | [0 2] | 2 ≥ 2 |
| 3 | [] | [3] | 4 |
| 4 | [3] | [3 4] | 4 ≥ 3 |

넣은 뒤의 값이 바닥에서 꼭대기로 커지지 않습니다. 같은 값 2 2 가 나란히 있는 것도 허용돼요. 순서를 뒤집어
먼저 넣고 꺼내기를 시작하면 자기 자신이 꼭대기가 되는데, `nums[i]` 가 `nums[i]` 보다 작을 수는 없어서
그 자리에서 바로 멈춥니다. 그러면 아무것도 안 꺼내져 답이 전부 `-1` 로 남아요.

#### 짚고 가기 — 순회가 끝나도 한 번도 안 꺼내지는 자리가 있다

여기서 헷갈리기 쉬운 포인트는 초기값 `-1` 입니다. 「어차피 모든 자리가 언젠가 꺼내지니 초기값은 아무것이나
되지 않나」로 읽히는데, **꺼내지지 않고 끝나는 자리가 늘 있습니다.** 마지막 자리가 그렇고, 감소 수열이면
전부 그래요. 초기값을 `0` 으로 깔아 둔 코드를 같은 입력들로 실행해 봅시다.

<!--proof:pause-fill-zero-->

| 입력 | 바른 코드 | 0 을 깔아 둔 코드 | 답 |
| --- | --- | --- | --- |
| [2 1 2 4 3] | [4 2 4 -1 -1] | [4 2 4 0 0] | 다르다 |
| [1 2 3 4] | [2 3 4 -1] | [2 3 4 0] | 다르다 |
| [4 3 2 1] | [-1 -1 -1 -1] | [0 0 0 0] | 다르다 |

3 벌 중 3 벌에서 답이 다릅니다.

<!--/proof-->

세 입력 모두 답이 갈립니다. 증가 수열에서도 마지막 한 자리는 남고, 감소 수열에서는 네 자리가 전부 남아요.
`0` 은 배열에 실제로 나올 수 있는 값이라, 답이 없는 자리와 답이 `0` 인 자리를 구별할 수도 없습니다.

#### 4. 다섯 칸을 아홉 걸음으로 지난다

세 조각을 하나로 이어 고정 입력에 실행하면 아홉 걸음이 나옵니다. 한 걸음은 「꼭대기와 비교해 꺼내기」나
「멈추고 넣기」나 「바로 넣기」 중 하나예요. 무대의 괄호가 이미 읽은 자리, ▲ 가 이번에 읽은 칸이고,
`result` 줄의 굵은 칸이 이번에 적은 답, `stack` 두 줄의 굵은 칸이 이번에 넣은 칸입니다.

<!--viz:walk-->
<!--fig:walk-film-->
![nextGreaterElement([2, 1, 2, 4, 3]) 의 아홉 걸음 T1~T9](./figs/walk-film.svg)

한 걸음마다 조건이 어떻게 판정되는지 전부 적으면 이렇습니다.

<!--proof:walk-trace-->

| 걸음 | 자리 i | 비교한 꼭대기 | 조건 판정 | 걸음 뒤 stack | 걸음 뒤 result | 갈래 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 | 0 | — | `stack.length > 0` 이 **거짓** | [0] | [-1 -1 -1 -1 -1] | ④ |
| T2 | 1 | 자리 0 | `2 >= 1` 이 **참** → 멈춘다 | [0 1] | [-1 -1 -1 -1 -1] | ② ④ |
| T3 | 2 | 자리 1 | `1 >= 2` 가 **거짓** → 꺼낸다 | [0] | [-1 2 -1 -1 -1] | ② ③ |
| T4 | 2 | 자리 0 | `2 >= 2` 가 **참** → 멈춘다 | [0 2] | [-1 2 -1 -1 -1] | ② ④ |
| T5 | 3 | 자리 2 | `2 >= 4` 가 **거짓** → 꺼낸다 | [0] | [-1 2 4 -1 -1] | ② ③ |
| T6 | 3 | 자리 0 | `2 >= 4` 가 **거짓** → 꺼낸다 | [] | [4 2 4 -1 -1] | ② ③ |
| T7 | 3 | — | `stack.length > 0` 이 **거짓** | [3] | [4 2 4 -1 -1] | ④ |
| T8 | 4 | 자리 3 | `4 >= 3` 이 **참** → 멈춘다 | [3 4] | [4 2 4 -1 -1] | ② ④ |
| T9 | — | — | `i < 5` 가 **거짓** → 반환 | [3 4] | [4 2 4 -1 -1] | ⑤ |

① 은 T1 앞의 준비, ② 는 T2 · T3 · T4 · T5 · T6 · T8, ③ 은 T3 · T5 · T6, ④ 는 T1 · T2 · T4 · T7 · T8, ⑤ 는 T9 입니다. 넣기가 5 번, 꺼내기가 3 번입니다.

<!--/proof-->

**다섯 갈래가 모두 나왔습니다.** 값 4 하나가 T5 와 T6 에서 두 자리의 답을 한꺼번에 정했고, T4 에서는 같은
값 2 에서 멈춰 자리 0 을 남겼어요. `result` 가 바뀐 걸음은 꺼낸 세 걸음뿐입니다.

#### 짚고 가기 — 답 칸에 적는 것은 자리 번호가 아니라 값이다

여기서 헷갈리기 쉬운 포인트는 `result[top]` 에 무엇을 적는가입니다. 꺼내는 걸음에서 손에 든 것이 둘이라 —
지금 자리 `i` 와 지금 값 `cur` — 어느 쪽을 적는지가 갈려요. 이 글의 과제는 값을 묻지만, 「다음 큰 원소의
자리」나 「며칠을 기다리는가」를 묻는 과제는 `i` 나 `i − top` 을 적습니다. 코드가 이 한 줄에서만 갈리니
헷갈리기 쉬워요. 자리 번호를 적은 코드를 같은 입력들로 실행해 봅시다.

<!--proof:pause-write-index-->

| 입력 | 바른 코드 | 자리 번호를 적은 코드 | 답 |
| --- | --- | --- | --- |
| [2 1 2 4 3] | [4 2 4 -1 -1] | [3 2 3 -1 -1] | 다르다 |
| [0 1 2 3] | [1 2 3 -1] | [1 2 3 -1] | 같다 |
| [0 1 2 3 4] | [1 2 3 4 -1] | [1 2 3 4 -1] | 같다 |
| [1 2 3 4] | [2 3 4 -1] | [1 2 3 -1] | 다르다 |

4 벌 중 2 벌에서 답이 다릅니다.

<!--/proof-->

**답이 같은 두 줄이 이 짚고 가기를 두는 이유입니다.** `nums[i] = i` 인 배열은 값과 자리 번호가 같아 두
코드의 답이 글자 그대로 같아요. 시험 목록이 `[0 1 2 3]` 같은 배열로만 채워져 있으면 이 코드는 오류 없이
통과하고, 틀린 줄 모르는 채로 남습니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 순회를 감싸는 `for` 와 마지막
`return result` 뿐이에요. `n` 이 0 이면 `for` 가 한 번도 실행되지 않아 빈 배열이 그대로 나옵니다.

```ts
export function nextGreaterElement(nums: number[]): number[] {
  const n = nums.length;
  // 답이 없는 자리의 값을 미리 깔아 둔다. 순회가 끝나고 스택에 남은 자리가 이 값을 그대로 쓴다.
  const result = new Array<number>(n).fill(-1); // ① 답 없음을 초기값으로 깐다
  // 답이 아직 정해지지 않은 **자리**만 담는다. 값이 아니라 자리다 — 답을 적을 칸을 알아야 한다.
  const stack: number[] = [];

  for (let i = 0; i < n; i++) {
    const cur = nums[i] ?? 0;
    while (stack.length > 0) {
      const top = stack[stack.length - 1] ?? 0;
      // ② 꼭대기의 값이 지금 값보다 **엄격하게** 작을 때만 꺼낸다.
      if ((nums[top] ?? 0) >= cur) break;
      stack.pop();
      result[top] = cur; // ③ 꺼낸 자리의 답이 지금 값으로 정해진다
    }
    stack.push(i); // ④ 답이 아직 없는 자리로 넣는다
  }

  return result; // ⑤ 스택에 남은 자리는 ① 이 깔아 둔 -1 을 그대로 쓴다
}
```

<!--proof:final-calls-->

```text
nextGreaterElement([2, 1, 2, 4, 3])      →   [4, 2, 4, -1, -1]
nextGreaterElement([5])                  →   [-1]
nextGreaterElement([5, 5, 5])            →   [-1, -1, -1]
nextGreaterElement([2, 7, 3, 5, 1, 6])   →   [7, -1, 5, 6, 6, -1]
```

### 알아 두면 좋은 개념 — 괄호 구조

자리 `i` 는 자기가 들어간 걸음부터 꺼내지는 걸음까지 답을 기다립니다. 그 **기다린 구간**을 전개의 아홉
걸음 위에 나란히 그렸어요.

<!--fig:related-intervals-->
![자리마다 답을 기다린 구간 — 포개지거나 떨어져 있고, 절반만 걸치는 짝이 없다](./figs/related-intervals.svg)

자리 1 과 자리 2 의 구간은 자리 0 의 구간 안에 온전히 들어가고, 자리 1 과 자리 2 끼리는 겹치지 않습니다.
어느 두 구간도 **절반만 걸치지 않아요.** 포개지거나 떨어져 있거나 둘 중 하나입니다. 큰 입력에서도 세어
봤습니다.

<!--proof:related-nesting-->

| 입력 | 기다린 구간 | 포개진 짝 | 떨어진 짝 | 절반만 걸친 짝 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 | 5 | 3 | 7 | 0 |
| 1,024 칸 입력 | 1,024 | 7,240 | 516,536 | 0 |

이런 모양을 **괄호 구조**라고 부릅니다. 들어간 걸음을 여는 괄호, 꺼내진 걸음을 닫는 괄호로 적으면
`0( 1( 1) 2( 2) 0)` 처럼 짝이 맞는 괄호열이 돼요. 절반만 걸치는 `0( 1( 0) 1)` 은 나올 수 없습니다. 자리 0 을
먼저 꺼내려면 꼭대기가 자리 0 이어야 하는데, 자리 1 이 나중에 들어갔으니 꼭대기는 자리 1 이기 때문이에요.

| 같은 이름을 다시 만나는 자리 | 구간의 양 끝 | 짝을 맞추는 구조 |
| --- | --- | --- |
| 괄호 짝 맞추기 · 식 파싱 | 여는 괄호 · 닫는 괄호 | 스택 하나 |
| 깊이 우선 탐색의 방문 시각과 종료 시각 | 정점에 들어간 때 · 나온 때 | 재귀 호출 스택 |
| 이 글의 기다린 구간 | 자리를 넣은 걸음 · 꺼낸 걸음 | 단조 스택 |

깊이 우선 탐색 쪽은 이 성질을 **괄호 정리**라는 이름으로 부르고,
[`dfsTraversal`](../../graph/dfsTraversal/dfsTraversal-guide.md) 이 같은 구조를 다룹니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 무엇과 대신 쓸 수 있는지, 남는 자리의 수를
식으로 어떻게 내는지, 무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

세 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 자리마다 답이 다 필요하다 | 몇 자리만 궁금하면 그 자리에서 오른쪽을 읽는 쪽이 배열 전체를 지나는 것보다 적을 수 있다 | 배열을 한 번 지나며 모든 답을 정한다 |
| 답을 만드는 동안 배열이 안 바뀐다 | 값 하나가 바뀌면 답 배열이 통째로 낡는다 | 답을 한 벌 만들어 두고 다시 만들지 않는다 |
| 기준이 「한쪽 방향으로 처음 만나는, 크기 비교」다 | 크다 · 작다로 한쪽을 버릴 수 있어야 한다 | 꼭대기 하나만 보고 멈춘다 |

마지막 조건이 가장 자주 걸립니다. 기준을 바꿔 보면 이 절차가 되는 것과 안 되는 것이 갈려요.

| 기준 | 앞 값으로 뒤 값 가리기 | 이 절차 |
| --- | --- | --- |
| 오른쪽에서 처음 더 큰 값 | 크다 · 작다로 가린다 | 그대로 쓴다 |
| 오른쪽에서 처음 더 작은 값 | 부등호만 뒤집으면 가린다 | 부등호만 바꿔 쓴다 |
| 오른쪽에서 처음 나오는 짝수 | 앞의 값이 뒤의 값을 못 가린다 | 쓸 수 없다. 짝수 여부는 자리마다 따로 본다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "오른쪽에서 처음으로 더 큰"  "다음으로 큰"  "며칠을 기다려야"      ← 결정적인 신호다
  "왼쪽에서 가장 가까운 더 작은"  "양쪽으로 뻗을 수 있는 최대 길이"
  "각 원소에 대해 …를 구하라"                                       ← 자리마다 답이 필요하다는 뜻이다

제약에 이런 모양이 보이면
  N 이 10^5 이상이라 N² 이 못 들어간다
  값의 범위가 넓어 값을 인덱스로 못 쓴다                            ← 세는 배열로는 안 된다는 뜻이다

반대로 이런 말이 보이면 해당하지 않는다
  "구간 [l, r] 에서"  "질의가 주어진다"                             ← 구간 자료구조 쪽이다
  "i 번째 값을 v 로 바꾼다"                                         ← 답 배열이 통째로 낡는다
  "창을 한 칸씩 옮기며"                                             ← 양 끝에서 넣고 빼는 자료구조가 필요하다
```

마지막 무리가 보이면 다른 절차로 갑니다. 창이 움직이면
[`monotonicQueue`](../../../data-structures/linear/monotonicQueue/monotonicQueue.ts) ·
[`slidingWindowMaximum`](../slidingWindowMaximum/slidingWindowMaximum-guide.md) 쪽이고, 구간 질의가 붙으면
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **`sdsl-lite` 의 `construct_supercartesian_tree_bp`** — 구간 최솟값 질의를 상수 시간에 답하는
  자료구조를 세울 때 쓰는 함수입니다. 머리 주석이 *"Calculate the balanced parentheses of the
  Super-Cartesian tree, described in Ohlebusch and Gog (SPIRE 2009)"* 이고, 본문의 반복이
  `while (vec_stack.size() > 0 and l < vec_stack.top()) { vec_stack.pop(); ++k; }` 입니다. **부등호 방향만
  반대**예요 — 이 글은 「더 큰 값」을 찾느라 작은 것을 꺼내고, 저쪽은 최솟값을 다루느라 큰 것을 꺼냅니다.
  ([`include/sdsl/suffix_tree_helper.hpp`](https://github.com/simongog/sdsl-lite/blob/master/include/sdsl/suffix_tree_helper.hpp),
  조회 2026-09-03)
- **CPython 의 어휘 분석기 `Parser/lexer/lexer.c`** — 들여쓰기 칸 수를 스택에 쌓아 두었다가, 줄의
  들여쓰기가 꼭대기보다 작으면 꺼내면서 `DEDENT` 토큰을 냅니다. 반복이
  `while (tok->indent > 0 && col < tok->indstack[tok->indent]) { tok->pendin--; tok->indent--; }` 이고,
  주석이 `/* Dedent -- any number, must be consistent */` 로 **한 걸음에 여러 개를 꺼낸다**는 것을 그 자리에
  적어 뒀어요.
  ([`Parser/lexer/lexer.c`](https://github.com/python/cpython/blob/main/Parser/lexer/lexer.c), 조회 2026-09-03)
- **파이썬 언어 레퍼런스 2.1.8 Indentation** — 그 스택의 규칙을 명세가 직접 적어 둔 자리입니다. *"The
  numbers pushed on the stack will always be strictly increasing from bottom to top … If it is smaller, it
  must be one of the numbers occurring on the stack; all numbers on the stack that are larger are popped
  off"* — **바닥에서 꼭대기로 커진다**는 성질과 **큰 것을 전부 꺼낸다**는 규칙이 문장으로 나와 있어요.
  ([Lexical analysis — Indentation](https://docs.python.org/3/reference/lexical_analysis.html), 조회 2026-09-03)

세 자리가 스택에 담는 것과 그 순서를 나란히 두면 이렇습니다.

| 쓰는 곳 | 스택에 담는 것 | 바닥에서 꼭대기로 가는 값의 순서 |
| --- | --- | --- |
| 이 글 | 답을 아직 못 받은 자리 번호 | 값이 커지지 않는다 |
| sdsl-lite | 아직 짝을 못 찾은 값 | 값이 작아지지 않는다 |
| CPython | 아직 안 닫힌 들여쓰기 칸 수 | 값이 커진다 |

셋 다 「꼭대기 하나만 보고 멈춰도 되는가」가 성립하는 순서로 담습니다.

#### 경쟁 설계와의 대조

같은 목표(자리마다 오른쪽에서 처음 만나는 더 큰 값 답하기)를 노리는 다른 절차로 **구간 최댓값 트리**가
있습니다. 마디마다 그 구간의 최댓값을 들고 있다가, `nums[i]` 보다 큰 값이 든 가장 왼쪽 잎을 위에서
내려가며 찾는 방식이에요. 단조 스택은 배열을 한 번 지나며 모든 답을 한꺼번에 정하고, 구간 최댓값 트리는
물어본 자리마다 위에서 내려가며 찾습니다.

| 설계 | 미리 만드는 것 | 질의 하나 | 갱신 하나 |
| --- | --- | --- | --- |
| 단조 스택 | 답 배열 한 벌 | 답 배열을 읽는다 | 답 배열을 다시 만든다 |
| 구간 최댓값 트리 | 마디마다 구간 최댓값 | 뿌리에서 잎으로 내려간다 | 잎에서 뿌리까지 마디만 고친다 |

그래서 「몇 자리를 묻는가」와 「배열이 바뀌는가」 둘이 갈림점이에요. 같은 입력 · 같은 작업 목록으로 두 설계를 실행하고 **배열 접근 수**를 셌습니다. 배열은 `N = 1,024` 이고
`nums[i] = (7919 i) mod 1009`, 질의 `t` 번째는 자리 `(23 t) mod N` 을 묻고, 갱신 `k` 번째는
`nums[(59 k) mod N]` 를 `(31 k) mod 1009` 로 덮어씁니다. 난수가 없으니 시드도 없고, 갱신은 질의 사이에
고르게 끼웠어요. 전개의 다섯 칸에서는 트리의 깊이가 셋뿐이라 두 설계의 계수가 열 몇 번짜리 상수에 묻히므로,
「아이디어를 떠올리는 과정」과 **같은 생성식**의 1,024 칸 입력을 쓰고 질의 수와 갱신 수만 바꿉니다.

**배열이 안 바뀐다고 두면 「몇 자리를 묻는가」 하나가 순서를 정합니다.**

<!--proof:alt-queries-->

| 갱신 0 회 | 단조 스택 | 구간 최댓값 트리 | 적은 쪽 |
| --- | ---: | ---: | --- |
| 질의 53 개 | 8,199 | 8,194 | 구간 최댓값 트리 · 5 번 적다 |
| 질의 54 개 | 8,200 | 8,211 | 단조 스택 · 11 번 적다 |
| 질의 4,096 개 | 12,242 | 88,129 | 단조 스택 · 7.2 배 적다 |

**묻는 자리를 1,024 개로 묶어 두면 「배열이 몇 번 바뀌는가」가 순서를 다시 뒤집습니다.**

<!--proof:alt-updates-->

| 질의 1,024 개 | 단조 스택 | 구간 최댓값 트리 | 적은 쪽 |
| --- | ---: | ---: | --- |
| 갱신 0 회 | 9,170 | 27,406 | 단조 스택 · 3.0 배 적다 |
| 갱신 2 회 | 25,464 | 27,470 | 단조 스택 · 2,006 번 적다 |
| 갱신 3 회 | 33,611 | 27,502 | 구간 최댓값 트리 · 6,109 번 적다 |
| 갱신 1,024 회 | 8,355,655 | 59,569 | 구간 최댓값 트리 · 140.3 배 적다 |

추가로 잡는 칸은 단조 스택이 1,039 칸(답 배열 1,024 칸 + 단조 스택이 가장 깊었을 때 15 칸), 구간 최댓값 트리가 2,048 칸입니다.

<!--/proof-->

경계가 왜 그 자리인지는 한 벌 만들기 · 질의 하나 · 갱신 하나의 비용으로 풀립니다.

<!--proof:alt-boundary-->

| 설계 | 한 벌 만들기 | 질의 하나 | 갱신 하나 |
| --- | ---: | ---: | ---: |
| 단조 스택 | 8,146 | 1 | 8,147 |
| 구간 최댓값 트리 | 7,165 | 평균 19.4 | 32 |

한 벌 만들기의 차이 981 번을 질의 하나의 차이 18.4 번으로 나누면 53.3 이고, 실측은 질의 53 개에서 54 개로 넘어가는 자리에서 순서가 뒤집힙니다. 질의 1,024 개에서 벌어진 차이 18,236 번을 갱신 하나의 차이 8,115 번으로 나누면 2.25 이고, 실측은 갱신 2 회에서 3 회로 넘어가는 자리입니다.

<!--/proof-->

**이 절차가 내주는 것은 갱신 하나의 비용입니다.** 값 하나가 바뀌면 답 배열이 통째로 낡아 다시 만들어야
하는데, 트리는 잎에서 뿌리까지 몇 마디만 고치면 끝나요. 그 대신 얻는 것이 자리마다 답을 다 필요로 할 때의
비용과 추가 칸입니다. 우열이 반대가 되는 조건도 분명해요 — **자리를 54 개 이상 묻고 배열이 안 바뀌면**
단조 스택이, **갱신이 세 번만 섞여 들어와도** 구간 최댓값 트리가 적습니다.

### 수식 정의와 유도

답과 **기록**을 정의합니다. 기록은 오른쪽에 자기보다 큰 값이 하나도 없는 자리예요.

$$g(i) = \min\{\, j \mid i < j < N,\ \mathit{nums}[j] > \mathit{nums}[i] \,\}$$

$$R[i] = \begin{cases} \mathit{nums}[g(i)] & g(i) \text{ 가 있을 때} \\ -1 & \text{없을 때} \end{cases}$$

$$\mathit{rec} = \{\, i \mid \mathit{nums}[j] \le \mathit{nums}[i] \ \text{ for all } j > i \,\}, \qquad S = |\mathit{rec}|$$

`g(i)` 는 조건을 만족하는 자리 중 **가장 작은** 것이고, 「처음 만나는」이 그 뜻입니다. `R[i]` 는 코드의
`result[i]` 이고, `g(i)` 가 없는 자리에만 `-1` 이 들어가요. `i` 가 기록이라는 것은 `g(i)` 가 없다는 것과 같은
말이고, 마지막 자리는 언제나 기록이라 `S ≥ 1` 입니다. 기록을 가려내는 조건을 코드로 그대로 옮기면
이렇습니다.

```ts
// 정의를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const isRecord = (nums: number[], i: number): boolean =>
  nums.slice(i + 1).every((v) => v <= (nums[i] ?? 0));
```

**정의를 값에 넣어 검산해 봅시다.** 전개 입력의 다섯 자리입니다.

<!--proof:records-check-->

| 자리 i | nums[i] | 오른쪽에서 처음 더 큰 값 | 기록 |
| ---: | ---: | --- | --- |
| 0 | 2 | 자리 3 의 4 | 아니오 |
| 1 | 1 | 자리 2 의 2 | 아니오 |
| 2 | 2 | 자리 3 의 4 | 아니오 |
| 3 | 4 | 없다 | 예 |
| 4 | 3 | 없다 | 예 |

기록이 2 개(자리 3 · 4)이고, 정본이 끝났을 때 단조 스택에 남은 자리도 2 개입니다. 꺼낸 횟수 P 는 3 번이고 N − S = 5 − 2 = 3 과 같습니다.

<!--/proof-->

**이제 그 일치가 우연이 아님을 유도합니다.** 순회가 끝난 시점의 `stack` 은 정확히 기록의 집합이에요. 두
방향으로 보입니다.

| 방향 | 출발 | 근거 | 도착 |
| --- | --- | --- | --- |
| 남은 자리는 기록 | 자리 `i` 가 끝까지 남았다 | `nums[j] > nums[i]` 인 `j > i` 가 있었다면, 걸음 `j` 에서 자리 `i` 위의 자리들은 값이 `nums[i]` 이하라 전부 `nums[j]` 보다 작아 먼저 꺼내지고, 이어서 꼭대기가 된 자리 `i` 도 꺼내졌다 | 그런 `j` 가 없다. 모든 `j > i` 에서 `nums[j] ≤ nums[i]` 다 |
| 기록은 남는 자리 | 모든 `j > i` 에서 `nums[j] ≤ nums[i]` 다 | 꺼내는 조건 `nums[i] < nums[j]` 가 한 번도 참이 안 된다 | 자리 `i` 는 끝까지 남는다 |

자리는 한 번 들어가고 많아야 한 번 나오므로 **꺼낸 횟수는 `P = N − S`** 입니다. 멈춘 걸음의 수 `B` 도 같은
방식으로 닫혀요. 걸음 `i` 가 멈추려면 꺼내기가 끝난 뒤 꼭대기가 남아 있어야 하는데, `stack` 의 맨 아래는
언제나 `nums[0..i−1]` 의 최댓값이 있는 자리입니다. 그래서 `B` 는 「지금 값이 왼쪽 최댓값을 못 넘은 걸음」의
수이고, `i = 0` 은 왼쪽이 비어 있어 들어가지 않으므로 `B ≤ N − 1` 이에요.

$$P = N - S, \qquad B = \bigl|\{\, i \mid \max(\mathit{nums}[0..i-1]) \ge \mathit{nums}[i] \,\}\bigr|$$

두 식을 전개 입력과 큰 입력에서 실측과 나란히 놓았습니다.

<!--proof:records-pb-->

| 입력 | 꺼낸 횟수 P | N − S | 멈춘 걸음 B | 왼쪽 최댓값을 못 넘은 자리 수 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 | 3 | 3 | 3 | 3 |
| 1,024 칸 입력 | 1,014 | 1,014 | 1,016 | 1,016 |
| 감소 수열 1,024 칸 | 0 | 0 | 1,023 | 1,023 |

**여기부터가 본문의 값만으로는 안 나오는 자리입니다.** 파트 1 은 다섯 칸에서 `S` 하나를 보였을 뿐인데, `S`
가 평균 얼마인지는 그 한 점으로 알 수 없어요. 값이 전부 다른 배열이 **어떤 순서로 와도 같은 확률**이라고
두면 두 기댓값이 닫힌 형태로 나옵니다. 자리 `i` 가 기록이려면 `nums[i]` 가 `nums[i..N−1]` 의 최댓값이어야
하고, 그 구간의 칸이 `N − i` 개이며 어느 칸이 최댓값이든 확률이 같으니 `1/(N−i)` 입니다. 걸음 `i` 가
멈추려면 `nums[i]` 가 `nums[0..i]` 의 최댓값이 아니어야 하고, 그 확률은 `1 − 1/(i+1)` 이에요.

$$\Pr[\,i \in \mathit{rec}\,] = \frac{1}{N-i} \;\Longrightarrow\; \mathbb{E}[S] = \sum_{i=0}^{N-1}\frac{1}{N-i} = \sum_{k=1}^{N}\frac{1}{k} = H_N$$

$$\Pr[\,\text{걸음 } i \text{ 가 멈춘다}\,] = 1 - \frac{1}{i+1} \;\Longrightarrow\; \mathbb{E}[B] = N - H_N$$

여기서 `H_N = 1 + 1/2 + … + 1/N` 은 조화수입니다. 식이 맞는지 순열을 전부 만들어 정본으로 실행하고, 끝났을 때
단조 스택에 남은 자리 수를 평균 냈습니다.

<!--proof:records-average-->

| N | 순열 수 | 정본이 남긴 자리 수의 평균 | H_N | 차이 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 1.000000 | 1.000000 | 0 |
| 2 | 2 | 1.500000 | 1.500000 | 0 |
| 3 | 6 | 1.833333 | 1.833333 | 0 |
| 4 | 24 | 2.083333 | 2.083333 | 0 |
| 5 | 120 | 2.283333 | 2.283333 | 0 |
| 6 | 720 | 2.450000 | 2.450000 | 0 |
| 7 | 5,040 | 2.592857 | 2.592857 | 0 |
| 8 | 40,320 | 2.717857 | 2.717857 | 0 |

여덟 줄 모두 차이가 0 입니다. N = 100,000 이면 H_N = 12.0901 이고, 평균 배열 접근 8N − 5·H_N 은 799,939.5 번, 최악 8N − 7 은 799,993 번으로 둘의 차이가 53.5 번입니다.

<!--/proof-->

10 만 칸을 지나도 끝에 남는 자리는 평균 열두 개 남짓이고, 그래서 꺼낸 횟수가 평균 `N − H_N` 으로 거의
`N` 입니다. 이 절차는 평균과 최악이 거의 같아요.

### 불변식 — 자리를 넣은 직후마다 단조 스택은 답을 기다리는 자리 전부이고 그 값이 커지지 않는다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 아래 문장으로 세우고, 전개의 걸음마다 읽은 자리가
단조 스택과 답 배열 중 어디에 있는지 세어 실제로 그런지 확인해 봅시다.

> **자리 `i` 를 넣은 직후마다**, `stack` 은 자리 `0` 부터 `i` 까지 중 **답을 아직 못 받은 자리 전부**를
> 담고 있고, 바닥에서 꼭대기로 자리 번호가 커지며 그 자리의 값은 커지지 않습니다. 이미 답을 받은 자리는
> `stack` 에 없고 `result` 에 값이 적혀 있습니다.

<!--proof:invariant-states-->

| 걸음 | 읽은 자리 | stack 에 있는 자리 | 답을 받은 자리 | 두 곳에 다 있는 자리 | 어디에도 없는 자리 | stack 의 값이 커지지 않음 |
| --- | --- | --- | --- | --- | --- | --- |
| T1 | 0 | 0 | 없음 | 없음 | 없음 | 예 |
| T2 | 0 · 1 | 0 · 1 | 없음 | 없음 | 없음 | 예 |
| T3 | 0 · 1 · 2 | 0 | 1 | 없음 | 2 | 예 |
| T4 | 0 · 1 · 2 | 0 · 2 | 1 | 없음 | 없음 | 예 |
| T5 | 0 · 1 · 2 · 3 | 0 | 1 · 2 | 없음 | 3 | 예 |
| T6 | 0 · 1 · 2 · 3 | 없음 | 0 · 1 · 2 | 없음 | 3 | 예 |
| T7 | 0 · 1 · 2 · 3 | 3 | 0 · 1 · 2 | 없음 | 없음 | 예 |
| T8 | 0 · 1 · 2 · 3 · 4 | 3 · 4 | 0 · 1 · 2 | 없음 | 없음 | 예 |
| T9 | 0 · 1 · 2 · 3 · 4 | 3 · 4 | 0 · 1 · 2 | 없음 | 없음 | 예 |

T1 · T2 · T4 · T7 · T8 · T9 에서는 두 곳에 다 있는 자리도 어디에도 없는 자리도 없습니다. 꺼내는 걸음 T3 · T5 · T6 에서는 지금 읽고 있는 자리 하나만 아직 어디에도 없습니다.

<!--/proof-->

「넣은 직후마다」가 중요합니다. 꺼내는 걸음에서는 지금 자리 `i` 가 아직 넣어지지 않아 어디에도 없어요.
그래서 불변식을 「걸음마다」가 아니라 「넣은 직후마다」로 세웠고, 넣기를 마치면 지금 자리까지 두 곳 중
정확히 한 곳에 있습니다.

**갈래마다 확인합시다.** 상태를 바꾸는 자리가 넷이고, 나머지는 상태를 안 건드립니다.

| 지나는 자리 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| 초기화 | `result` 를 `-1` 로 채운다 | 아직 아무 자리도 안 읽었으니 `stack` 이 비어 있고 답도 없다 |
| 꺼내기 — 꼭대기의 값이 `cur` 보다 작다 | `stack` 에서 빼고 `result` 에 적는다 | 빠진 자리가 그 걸음에서 답을 받으므로 「답을 못 받은 자리 전부」가 유지된다 |
| 멈춤 — 꼭대기의 값이 `cur` 이상이다 | 아무것도 안 한다 | 꼭대기 아래는 값이 더 커서 더더욱 꺼낼 조건을 못 만족한다 |
| 넣기 | `stack` 에 자리 `i` 를 넣는다 | 자리 `i` 는 방금 읽혔고 답이 없다. 값이 단조 스택 안에서 가장 작아 순서도 유지된다 |
| 반환 | 아무것도 안 한다 | `stack` 에 남은 자리는 답이 없는 자리이고 `-1` 이 이미 적혀 있다 |

**경계에 있는 입력도 확인하고 갑시다.**

<!--proof:invariant-edges-->

| 입력 | 배열 | 처리되는 자리 | 결과 |
| --- | --- | --- | --- |
| N = 1 | [5] | 넣기만 하고 순회가 끝난다 | [-1] |
| N = 2 증가 | [1 2] | 두 번째 자리를 읽을 때 첫 자리를 꺼낸다 | [2 -1] |
| N = 2 감소 | [2 1] | 아무것도 안 꺼낸다 | [-1 -1] |
| 값이 전부 같다 | [5 5 5] | 조건 `>=` 가 늘 참이라 한 번도 안 꺼낸다 | [-1 -1 -1] |
| 감소 수열 | [4 3 2 1] | 위와 같은 갈래로 전부 남는다 | [-1 -1 -1 -1] |
| 음수만 있다 | [-3 -2 -1] | 값의 부호는 비교에 쓰이지 않는다 | [-2 -1 -1] |
| 최댓값이 맨 앞 | [9 1 5 2] | 첫 자리가 끝까지 남는다 | [-1 5 -1 -1] |

마지막 줄이 「답이 `-1` 인 자리는 마지막 자리뿐」이라는 오해를 막는 자리입니다. 가장 큰 값이 어디에 있든 그
자리의 답은 `-1` 이에요.

**이제 깨뜨려 봅시다.** 불변식을 지키던 줄은 꺼내는 조건의 부등호 한 줄입니다. 「같은 값도 어차피 순서상
뒤엣것이 늦게 오니 꺼내도 되지 않나」라는 생각으로 그 조건을 느슨하게 바꿔 봅니다.

```ts
if ((nums[top] ?? 0) > cur) break; // ← 같은 값에서 멈추지 않는다. 원래는 >= 다
```

<!--proof:mutant-loose-compare-->

| 입력 | 바른 코드 | 같은 값도 꺼내는 코드 | 답 |
| --- | --- | --- | --- |
| [5 5 5] | [-1 -1 -1] | [5 5 -1] | 다르다 |
| [2 1 2 4 3] | [4 2 4 -1 -1] | [2 2 4 -1 -1] | 다르다 |
| [1 2 3 4] | [2 3 4 -1] | [2 3 4 -1] | 같다 |
| [4 3 2 1] | [-1 -1 -1 -1] | [-1 -1 -1 -1] | 같다 |

4 벌 중 2 벌에서 답이 다릅니다.

<!--/proof-->

`[5 5 5]` 에서 답이 `[5 5 -1]` 이 됩니다. 5 는 5 보다 크지 않으니 답이 될 수 없는데도 적혔어요. 전개
입력에서는 자리 0 의 답이 4 대신 2 가 됩니다. 자리 0 이 언제 꺼내졌는지 두 코드를 나란히 놓으면 까닭이
보여요.

<!--proof:mutant-loose-trace-->

| 코드 | 자리 0 을 꺼낸 때 | 자리 0 의 답 |
| --- | --- | --- |
| 바른 조건 — 같으면 멈춘다 | 자리 3 의 4 를 읽을 때 | 4 |
| 느슨한 조건 — 같아도 꺼낸다 | 자리 2 의 2 를 읽을 때 | 2 |

느슨한 조건에서는 자리 0 이 같은 값 2 에게 너무 일찍 꺼내져, 진짜 답인 4 를 못 만났습니다. 답을 받지 말아야
할 자리가 단조 스택에서 빠졌으니 「답을 못 받은 자리 전부」가 깨진 것이고, 그 순간부터 자리 0 에는 틀린 답이
남아요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 다섯뿐입니다 — 답 배열을 깔고, 지금 값을 읽고, 꼭대기와 비교하고, 답을 적고,
자리를 넣는 것. 비교 한 번이 접근 둘인 것은 꼭대기 자리를 읽고 그 자리의 값을 또 읽기 때문이에요. 전개의
걸음으로 세면 이렇습니다.

<!--proof:walk-cost-->

| 갈래 | 걸음 | 식 | 배열 접근 |
| --- | --- | --- | ---: |
| 답 없음을 깐다 ① | T1 앞 | N | 5 |
| 지금 값을 읽는다 | T1 · T2 · T3 · T5 · T8 | N | 5 |
| 꼭대기와 비교한다 ② | T2 · T3 · T4 · T5 · T6 · T8 | 2(P + B) | 12 |
| 답을 적는다 ③ | T3 · T5 · T6 | P | 3 |
| 자리를 넣는다 ④ | T1 · T2 · T4 · T7 · T8 | N | 5 |
| 남은 자리를 그대로 둔다 ⑤ | T9 | 0 | 0 |
| 합 |  | 3N + 3P + 2B | 30 |

전개는 N = 5 · P = 3 · B = 3 이라 식에 넣으면 15 + 9 + 6 = 30 번입니다. 같은 입력을 자리마다 오른쪽을 차례로 읽어 처리하면 19 번입니다.

<!--/proof-->

다섯 칸에서는 답 배열을 까는 몫과 자리를 넣는 몫이 커서 차례로 읽는 방법보다 많습니다. 칸이 늘면 이 두
몫은 `N` 에 비례하는 그대로이고, 차례로 읽는 쪽만 `N²` 으로 커져요. 다 더하면 `3N + 3P + 2B` 이고, `P ≤ N −
1` · `B ≤ N − 1` 이므로 접근이 `8N − 5` 아래입니다. 다만 두 상한이 **동시에** 달성되지는 않아요 — `P = N − 1`
이면 마지막 걸음이 단조 스택을 비우고 끝나므로 그 걸음은 멈춘 걸음이 아닙니다. 과제 규모에 넣으면 이렇습니다.

<!--proof:perf-scale-->

| 입력 | P | B | 배열 접근 |
| --- | ---: | ---: | ---: |
| 감소 수열 | 0 | 99,999 | 499,998 |
| 두 번째로 큰 값이 맨 앞 · 가운데 증가 · 가장 큰 값이 맨 뒤 | 99,999 | 99,998 | 799,993 |
| 값이 모두 다르고 모든 순서가 같은 확률(평균) | N − H_N | N − H_N | 799,939.5 |

N = 100,000 에서 위 두 줄은 실제로 세었고, 셋째 줄은 식 8N − 5·H_N 에 넣은 값입니다. 첫 줄의 실측은 5N − 2 = 499,998 과 같고, 둘째 줄의 실측은 8N − 7 = 799,993 과 같습니다. 단순 연산 1 초에 1 억 번으로 잡으면 가장 많은 줄도 0.008 초입니다.

<!--/proof-->

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (감소 수열 · 값이 전부 같음) | `O(N)` | `Θ(N)` — 접근 `5N − 2` |
| **평균적인 경우** (순서의 분포를 정해야 한다) | `O(N)` | 분포를 정하면 `Θ(N)` — 접근 `8N − 5H_N` |
| **최악의 경우** (아래 절이 구성하는 입력) | `O(N)` | `Θ(N)` — 접근 `8N − 7`, 실제로 도달합니다 |

세 케이스가 **경계의 종류에서는 갈리지 않습니다.** 셋 다 타이트하게 `Θ(N)` 이고, 갈리는 것은 상수예요 — 5
와 8 사이입니다. 이 절차에서 「최악이 느리다」는 말은 상수가 조금 크다는 뜻이지 차수가 다르다는 뜻이
아닙니다.

평균이 정해지지 않는 이유도 적어 둡니다. 이 과제는 값이 **어떤 순서로 오는지 말하지 않아요.** 순서의 분포를
하나 정하면(모든 순열이 같은 확률이라고 두면) 평균이 `8N − 5H_N` 이 되지만, 그것은 과제가 준 조건이 아니라 이
글이 놓은 가정입니다. 총식을 한 번 정확히 적으면 이렇습니다.

```text
총식 = 배열 접근 3N + 3P + 2B,  5N − 2 ≤ 접근 ≤ 8N − 7   →   Θ(N) 시간
       추가로 잡는 칸 = 답 배열 N 칸 + 스택 최대 N 칸       →   Θ(N) 공간
       앞뒤로 붙는 전처리가 없다. 정렬도 좌표 압축도 쓰지 않는다
```

**약속으로 내놓는 것은 최악 보장 하나입니다.** 코드에 난수가 없으니 같은 배열을 두 번 넣으면 같은 횟수가
나오고, 어떤 배열을 넣어도 `8N − 7` 아래라는 것이 조건 없이 성립합니다. `8N − 5H_N` 은 그 약속의 일부가
아니라 **입력 분포를 하나 놓았을 때의 기댓값**이에요 — 구현이 만드는 무작위성이 아니라 **모든 순서가 같은
확률**이라는 가정에서 나온 값이고, 실제 입력이 그 분포를 따르지 않으면 성립하지 않습니다.

#### 최악을 만드는 입력

「정렬된 배열이면 느리다」가 이 절차에서는 절반만 맞습니다. 증가 수열은 자리마다 답을 받으니 꺼내기가
최대인데, **멈추는 걸음이 하나도 없어** 접근이 `6N − 3` 에 그쳐요. 모양이 다른 입력 다섯을 같은 길이로 재
봤습니다.

<!--proof:worst-shape-->

| 입력의 모양 | 꺼낸 횟수 P | 멈춘 걸음 B | 남은 자리 S | 3N + 3P + 2B | 실측 배열 접근 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 감소 수열 | 0 | 1,023 | 1,024 | 5,118 | 5,118 |
| 전부 같은 값 | 0 | 1,023 | 1,024 | 5,118 | 5,118 |
| nums[i] = (7919 i) mod 1009 | 1,014 | 1,016 | 10 | 8,146 | 8,146 |
| 증가 수열 | 1,023 | 0 | 1 | 6,141 | 6,141 |
| 두 번째로 큰 값이 맨 앞 · 가운데 증가 · 가장 큰 값이 맨 뒤 | 1,023 | 1,022 | 1 | 8,185 | 8,185 |

N = 1,024 에서 가장 많은 것은 8,185 번이고 8N − 7 = 8,185 와 같습니다. 길이 2~8 순열을 전부 넣어 8N − 7 을 넘는 입력을 찾았고, 찾은 입력은 0 개입니다. 길이 8 의 최댓값은 57 = 8·8 − 7 입니다.

<!--/proof-->

최악은 **꺼내기와 멈춤을 동시에 최대로 만드는 입력**입니다. 두 번째로 큰 값을 맨 앞에 두면 가운데 걸음이
전부 그 값에서 멈추고, 가장 큰 값을 맨 뒤에 두면 마지막 걸음이 단조 스택을 통째로 비웁니다. 같은 모양을 `N = 8`
로 적어 자리마다 따라가면 이렇습니다.

<!--proof:worst-n8-->

| 읽은 자리 | 꺼낸 자리 | 멈춘 꼭대기 |
| --- | --- | --- |
| 0 · 값 7 | 없음 | 없음 |
| 1 · 값 0 | 없음 | 자리 0 · 값 7 |
| 2 · 값 1 | 1 | 자리 0 · 값 7 |
| 3 · 값 2 | 2 | 자리 0 · 값 7 |
| 4 · 값 3 | 3 | 자리 0 · 값 7 |
| 5 · 값 4 | 4 | 자리 0 · 값 7 |
| 6 · 값 5 | 5 | 자리 0 · 값 7 |
| 7 · 값 8 | 6 · 0 | 없음 |

입력은 [7 0 1 2 3 4 5 8] 입니다. 꺼낸 횟수 P = 7 = N − 1 이고, 멈춘 걸음 B = 6 = N − 2 입니다. 배열 접근은 57 = 8·8 − 7 번입니다.

<!--/proof-->

그러니 최악은 **값의 크기가 아니라 놓인 순서**가 만듭니다. 같은 값들을 다르게 늘어놓기만 해도 접근이 `5N −
2` 에서 `8N − 7` 까지 갈려요. `B` 가 `N − 1` 까지 못 가는 까닭은 아래와 같습니다.

```text
걸음 N−1 이 멈춘다   → 꺼내기가 끝난 뒤에도 꼭대기가 남아 있다
                     → 그 자리와 자리 N−1 이 둘 다 끝까지 남아 S ≥ 2 다
                     → P = N − S ≤ N − 2 가 되어 3P 쪽에서 3 을 잃는다
                     └ 3P 로 3 을 잃고 2B 로 2 를 얻으므로 합이 줄어든다. 그래서 8N − 7 이 상한이다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 답을 아직 못 받은 자리만 단조 스택에 담아 두고, 값이
바닥에서 꼭대기로 커지지 않게 유지했으며, 큰 값을 만나는 순간 꼭대기부터 꺼내 답을 한꺼번에 적었습니다.
자리마다 한 번 들어가고 많아야 한 번 나오므로 배열 접근이 `8N − 7` 을 넘지 않아요.

```text
result 를 -1 로 → 자리 i 를 읽는다 → cur 보다 작은 꼭대기를 꺼내 답을 적는다 → i 를 넣는다
                                      └ 같은 값에서는 멈춘다. 같은 값은 답이 아니다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T6 에서 자리 0 이 꺼내지면서 답 4 를 받았어요. 그런데 자리 0 과

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Next Greater Element

풀 파일: [`nextGreaterElement.ts`](./nextGreaterElement.ts) · 테스트: [`nextGreaterElement.test.ts`](./nextGreaterElement.test.ts) · 실행: `bun test src/algorithms/array/nextGreaterElement/nextGreaterElement.test.ts`

#### 한 줄 요약

> 정수 배열을 받아, 각 원소에 대해 **오른쪽에서 처음으로 자신보다 엄격하게 큰 값**을 담은 배열을 반환한다.

#### 스토리

기상 예보 팀의 분석가 나연은 일별 기온 기록을 들여다보고 있다. 각 날짜에 대해, 이후 날들 중 처음으로 오늘보다 더 더웠던 날의 기온을 알고 싶다.

단, "더 덥다"는 기준은 엄격하다. 같은 온도는 해당되지 않는다. 나연이 보는 날짜 이후로 더 더운 날이 없으면 특별 표시 $-1$을 기록한다.

배열의 끝에 위치한 원소들은 오른쪽에 다음 날이 없으므로 항상 $-1$을 가진다.

#### 함수 인터페이스

```ts
export function nextGreaterElement(nums: number[]): number[];
```

- `nums` — 정수 배열.
- 반환 — 길이 $N$의 배열. `result[i]`는 `nums[i]`보다 오른쪽에 있는 원소 중 처음으로 엄격하게 큰 값. 없으면 `-1`.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `nums`의 길이)
- $-10^9 \leq nums[i] \leq 10^9$ (정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

결과 배열 $R$의 정의:

$$R[i] = \begin{cases} nums[j] & j = \min\{\, j > i \mid nums[j] > nums[i] \,\} \\ -1 & \text{그런 } j \text{가 없는 경우} \end{cases}$$

"엄격하게 크다"는 $nums[j] > nums[i]$를 의미한다. 같은 값은 포함하지 않는다. 마지막 원소(`i = N-1`)는 오른쪽에 아무것도 없으므로 항상 $-1$이다.

#### 예시

```ts
nextGreaterElement([2, 1, 2, 4, 3]);    // [4, 2, 4, -1, -1]  — 각 원소의 다음 큰 값
nextGreaterElement([1, 2, 3, 4]);       // [2, 3, 4, -1]  — 엄격 증가, 마지막은 -1
nextGreaterElement([2, 7, 3, 5, 1, 6]); // [7, -1, 5, 6, 6, -1]

nextGreaterElement([4, 3, 2, 1]);       // [-1, -1, -1, -1]  — 엄격 감소, 모두 -1
nextGreaterElement([5, 5, 5]);          // [-1, -1, -1]  — 같은 값은 포함 안 됨

nextGreaterElement([5]);                // [-1]  — 단일 원소, 오른쪽 없음
nextGreaterElement([1, 2]);             // [2, -1]  — 두 원소, 첫 것만 다음 큰 값 존재
```
