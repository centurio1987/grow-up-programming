# 편집 거리 — 마지막 한 번의 편집만 정하면 과제가 한 칸 작아지는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 편집을 한 번씩 해 보는
방법에서 출발해 접두어 쌍마다 답을 적는 DP 테이블까지 가고, 그 DP 테이블을 단계마다 값으로 푼 뒤, 실제로 동작하는
코드를 한 조각씩 만듭니다.

### 전체 컨셉

문자열 하나를 고치는 편집은 세 가지입니다. 글자 하나를 끼워 넣는 **삽입**, 글자 하나를 지우는 **삭제**, 글자 하나를
다른 글자로 바꾸는 **교체**예요. 세 편집의 비용은 모두 1 입니다. 문자열 `s` 를 문자열 `t` 로 바꾸는 데 필요한 **편집
횟수의 최솟값**을 두 문자열의 편집 거리라고 부르고, 그 값을 구하는 것이 목표입니다. `s = "horse"` 를 `t = "ros"` 로
바꾸는 편집을 한 번에 한 장씩 그리면 이렇습니다.

<!--fig:concept-edits-->
![s = "horse" 를 t = "ros" 로 바꾸는 편집 — 편집 한 번에 한 장](./figs/concept-edits.svg)

강조색 칸이 그 편집이 손대는 자리입니다. 세 편집을 차례로 적으면 이렇게 돼요.

<!--proof:concept-edits-->

| 번째 | 편집 | 편집 전 | 편집 후 |
| ---: | --- | --- | --- |
| 1 | h 를 r 로 교체 | "horse" | "rorse" |
| 2 | r 을 삭제 | "rorse" | "rose" |
| 3 | e 를 삭제 | "rose" | "ros" |

편집은 모두 3 번입니다. 편집을 한 번씩 해 보며 만들 수 있는 문자열을 전부 만들어 보면 2 번 안에는 "ros" 가 나오지 않고, 정본이 editDistance("horse", "ros") 로 낸 값도 3 입니다.

<!--/proof-->

편집을 실제로 해 보며 찾으면 답은 맞지만, 편집 횟수가 하나 늘 때마다 만들어 볼 문자열의 가짓수가 곱해져 늘어납니다.
길이 1,000 짜리 두 문자열이면 끝나지 않아요.

그래서 편집을 해 보지 않고 **두 문자열의 앞부분 한 쌍마다 답을 적어 두는 표**를 씁니다. 줄 `i` 는 `s` 를 앞에서 몇
글자 보았는가, 열 `j` 는 `t` 를 앞에서 몇 글자 보았는가예요. `i` 번째 줄의 `j` 번째 칸 `dp[i][j]` 에는 「`s` 의 앞 `i`
글자를 `t` 의 앞 `j` 글자로 바꾸는 최소 편집 횟수」를 적습니다. 작은 입력의 답을 칸에 적어 두고 큰 입력의 답을 그
칸들에서 만드는 이런 표를 **DP 테이블**이라고 부릅니다. DP 는 동적 계획법(dynamic programming)의 줄임말이에요.
`s = "horse"`, `t = "ros"` 의 DP 테이블 전체를 그리면 이렇습니다.

<!--fig:concept-table-->
![editDistance("horse", "ros") 의 DP 테이블 — 줄은 s 의 글자, 열은 t 의 글자](./figs/concept-table.svg)

줄 머리는 그 줄에서 새로 보는 `s` 의 글자이고, 열 머리는 그 열에서 새로 보는 `t` 의 글자입니다. `∅` 는 한 글자도 안
본 자리, 곧 빈 문자열이에요. 맨 왼쪽 열은 `t` 가 빈 문자열이라 `s` 의 앞 `i` 글자를 전부 지워야 하니 값이 `i` 이고,
맨 위 줄은 `s` 가 빈 문자열이라 `t` 의 앞 `j` 글자를 전부 넣어야 하니 값이 `j` 입니다. 답은 오른쪽 아래 칸
`dp[5][3] = 3` 이에요. 나머지 칸 하나를 정하는 규칙은 그 칸이 새로 보는 두 글자 `s[i-1]` 과 `t[j-1]` 로 갈립니다.

| 경우 | 그 칸에 적는 값 |
| --- | --- |
| 두 글자가 같다 | 왼쪽 위 칸 `dp[i-1][j-1]` 을 그대로 |
| 두 글자가 다르다 | 왼쪽 위 `dp[i-1][j-1]` · 위 `dp[i-1][j]` · 왼쪽 `dp[i][j-1]` 중 가장 작은 값에 1 을 더한 값 |

두 글자가 같으면 그 글자는 손대지 않고 양쪽에서 한 글자씩 떼면 됩니다. 다르면 마지막 한 번의 편집이 셋 중 하나예요.
`s[i-1]` 을 `t[j-1]` 로 교체하면 양쪽에서 한 글자씩 떼어 왼쪽 위, `s[i-1]` 을 삭제하면 `s` 에서만 떼어 위, `t[j-1]` 을
삽입하면 `t` 에서만 떼어 왼쪽 칸이 남은 일의 답입니다. 어느 갈래든 남는 것은 **더 짧은 앞부분 한 쌍**이라, 이
알고리즘의 핵심이 여기 있어요. 두 경우가 읽는 칸을 그리면 이렇습니다. 강조색 굵은 테가 새로 정하는 칸이고, 진한 테를
두른 칸이 그 칸이 읽는 칸이에요.

<!--fig:concept-rule-->
![칸 하나가 읽는 자리 — 글자가 같으면 왼쪽 위, 다르면 왼쪽 위 · 위 · 왼쪽](./figs/concept-rule.svg)

칸은 `(n+1) × (m+1)` 개이고(`n` 은 `s` 의 길이, `m` 은 `t` 의 길이), 칸 하나에 문자 비교 한 번과 값 비교 두 번 이하면
됩니다. 비용은 결과만 적어 `O(nm)` 이고, 칸 수를 세면 이렇습니다.

<!--proof:concept-size-->

```text
s 의 길이 n  t 의 길이 m  칸 (n+1)(m+1)
          5            3             24
      1,000        1,000      1,002,001
```

입력이 무엇이든 모든 칸을 한 번씩 채우니, 답이 크다고 칸이 늘거나 답이 작다고 칸이 줄지 않습니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **삽입과 삭제가 뒤의 자리를 한 칸씩 옮긴다는 것.** 앞에서 글자 하나를 지우면 그 뒤 글자들의 자리 번호가 전부 하나씩
  줄어듭니다. 이 사실 하나가 「같은 자리끼리 비교하기」를 틀리게 만들어요.
- **2 차원 배열의 첨자 읽기.** `dp[i][j]` 는 `i` 번째 줄의 `j` 번째 칸입니다. 앞 첨자가 줄, 뒤 첨자가 열이에요.
- **문자열의 첨자가 0 부터라는 것.** DP 테이블의 줄 `i` 는 「본 글자 수」라 1 부터 세고, 그 줄이 새로 보는 글자는
  `s[i-1]` 입니다. 이 `1` 이 어긋나기 쉬워요.
- **DP 테이블.** 칸마다 작은 입력의 답을 적어 두는 표입니다. 칸 하나를 읽는 법과 이웃한 칸끼리의 관계는
  [동전 조합의 경우의 수](../../dp/coinChangeWays/coinChangeWays-guide.md) 의 「먼저 알아 둘 개념 — DP 테이블」 절이
  풀어 둡니다. 이 글은 그 설명을 되풀이하지 않고, 필요한 만큼만 그 자리에서 다시 적어요.

| 이미 아는 것 | 이 글에서 쓰이는 자리 |
| --- | --- |
| 삽입과 삭제가 자리를 옮긴다 | 같은 자리끼리 비교하는 방법이 틀리는 까닭 |
| 2 차원 첨자 | DP 테이블의 칸 `dp[i][j]` |
| 0 부터 세는 첨자 | 칸 `(i, j)` 가 비교하는 두 글자 `s[i-1]` · `t[j-1]` |
| DP 테이블 | 줄마다 `s` 의 글자 하나를 더 보는 표 |

재귀 · 메모이제이션은 몰라도 됩니다. DP 테이블을 왼쪽 위에서 오른쪽 아래로 채우는 반복문만 써요. 두 문자열에 공통으로
남는 가장 긴 부분 수열의 길이는 [최장 공통 부분 수열](../longestCommonSubsequence/longestCommonSubsequence-guide.md) 이
같은 모양의 DP 테이블로 구합니다. 그 글을 먼저 읽었다면 칸을 채우는 순서와 테두리의 뜻이 그대로 이어져요.

### 아이디어를 떠올리는 과정 — 편집을 한 번씩 해 보기에서 접두어 쌍 DP 테이블까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 두 문자열을 받아서, 편집 거리를 돌려줍니다.

```ts
function editDistance(s: string, t: string): number;
```

- 입력: 두 문자열 `s` 와 `t`. 글자는 ASCII 범위이고 빈 문자열일 수 있습니다.
- 출력: **횟수 하나.** 편집 목록 자체는 돌려주지 않아요. 한쪽이 빈 문자열이면 다른 쪽의 길이가 답입니다.
- 규모: 두 문자열의 길이가 각각 1,000 이하입니다. 비용은 흔한 채점 환경의 예산인 1 초에 대어 잽니다.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| `s` | 바꿀 문자열 | 길이가 `n` |
| `t` | 목표 문자열 | 길이가 `m` |
| `n` | `s` 의 길이 | `0 ≤ n ≤ 1,000` |
| `m` | `t` 의 길이 | `0 ≤ m ≤ 1,000` |
| `i` | `s` 를 앞에서 몇 글자 보았는가. DP 테이블의 줄 | `0 ≤ i ≤ n` |
| `j` | `t` 를 앞에서 몇 글자 보았는가. DP 테이블의 열 | `0 ≤ j ≤ m` |
| `dp[i][j]` | `s` 의 앞 `i` 글자를 `t` 의 앞 `j` 글자로 바꾸는 최소 편집 횟수 | DP 테이블의 칸 하나 |

`i` 와 `j` 는 **본 글자의 개수**이지 자리 번호가 아닙니다. 그래서 칸 `(i, j)` 가 비교하는 두 글자는 `s[i-1]` 과
`t[j-1]` 이에요.

가장 먼저 떠오르는 방법으로 시작합시다. 편집 거리의 정의를 그대로 옮기면, `s` 에 편집 한 번을 한 결과를 전부 만들어
그중에 `t` 가 있는지 보고, 없으면 그 결과들에 다시 한 번씩 편집하면 됩니다.

```ts
let frontier = new Set([s]);
for (let depth = 1; ; depth++) {
  const next = new Set<string>();
  for (const x of frontier) {
    for (const y of oneEditAway(x)) { // 편집 한 번으로 만들 수 있는 문자열 전부
      if (y === t) return depth;
      next.add(y);
    }
  }
  frontier = next;
}
```

이 방법이 하는 일의 양은 **만나는 문자열의 개수**입니다. 전개 입력에 실행하고 과제 규모에 넣어 보면 이렇습니다.

<!--proof:origin-breadth-first-->

```text
편집 횟수  새로 만난 문자열 수    누적
        1                   50      50
        2                1,040   1,090
        3               12,688  13,778

└ 3 번째에 "ros" 가 나온다

과제 규모 n = m = 1,000 · 글자 종류 26 이면
  편집 한 번으로 만드는 후보 수(겹침 포함)         52,026
  답이 1,000 일 때 확인할 문자열 수의 상한  4,717 자리 수
  └ 편집 한 번마다 가짓수가 그만큼 곱해지므로 답이 곧 지수가 된다
```

편집 한 번으로 만드는 후보가 수만 가지이고, 편집 횟수만큼 그 수가 곱해집니다. 답이 1,000 이면 확인할 문자열이
4,717 자리 수라 1 초에 `10^9` 개를 본다 해도 끝나지 않아요. **문자열을 통째로 들고 편집해 보는 길은 여기서 막힙니다.**

편집을 해 보지 않는 가장 단순한 방법은 **같은 자리끼리 비교하는 것**입니다. 두 문자열을 앞에서부터 같은 자리끼리
비교해 다른 자리를 세고, 길이 차이만큼 더하면 교체와 끝의 삽입 · 삭제로 바꾸는 횟수가 나와요. 몇 입력에 실행해 봅시다.

<!--proof:origin-slot-->

```text
입력                        정본이 낸 답  자리마다 비교한 값  판정
전개 입력 "horse" 와 "ros"             3                   4  틀리다
"abcd" 와 "bcda"                       2                   4  틀리다
"flaw" 와 "lawn"                       2                   4  틀리다
"ab" 와 "ba"                           2                   2  같다
"horse" 와 "house"                     1                   1  같다

"abcd" 와 "bcda" 에서 두 방식이 갈리는 자리
  자리마다 비교한다        a-b  b-c  c-d  d-a  다른 자리 4
  앞 글자 하나를 지운다    "bcd" 와 "bcda"     뒤가 한 칸씩 당겨진다
  끝에 글자 하나를 넣는다  "bcda" 와 "bcda"    편집 2 번에 같아진다
```

전개 입력에서부터 틀립니다. 삽입과 삭제는 **뒤의 글자를 통째로 한 칸씩 옮기는** 편집인데, 같은 자리끼리 비교하는
방법은 자리 번호를 고정해 두고 봐요. `"abcd"` 와 `"bcda"` 는 앞 글자 하나를 지우고 끝에 하나를 넣으면 같아지는데, 자리를
고정하면 네 자리가 전부 다르게 보입니다. 그러니 **어느 자리를 고쳤는지가 아니라 양쪽을 어디까지 보았는지**를 들고
가야 해요.

양쪽을 어디까지 보았는지로 나누는 자리를 **마지막 편집**으로 잡으면 경우가 깔끔하게 갈립니다. 편집 목록은 순서를 바꿔도
비용이 같으니, 뒤에서부터 정해도 손해가 없어요. 두 문자열의 마지막 글자가 같으면 편집 없이 양쪽에서 한 글자씩 떼고,
다르면 마지막 편집이 교체 · 삭제 · 삽입 중 하나입니다. 어느 쪽이든 남는 것은 두 문자열의 앞부분 한 쌍이라, 앞 `i`
글자와 앞 `j` 글자의 답을 `f(i, j)` 로 적는 재귀가 됩니다.

```ts
function f(i: number, j: number): number {
  if (i === 0) return j; // s 가 비었다 — t 의 남은 j 글자를 넣는다
  if (j === 0) return i; // t 가 비었다 — s 의 남은 i 글자를 지운다
  if (s[i - 1] === t[j - 1]) return f(i - 1, j - 1);
  return 1 + Math.min(f(i - 1, j - 1), f(i - 1, j), f(i, j - 1));
}
```

이 재귀는 답이 맞습니다. 비용이 무엇에 달렸는지 보려고 **두 길이가 같고 글자만 다른 두 입력**으로 실행해, 몇 번
불리는지와 서로 다른 `(i, j)` 가 몇 개인지를 나란히 세었어요.

<!--proof:origin-recursion-->

```text
입력                      두 길이  기억 없이 부른 횟수  서로 다른 (i, j)  DP 테이블 칸
"horse" 와 "ros"          5 x 3                     77                18            24
"horse" 와 "vwx"          5 x 3                    346                24            24
"abcdefgh" 와 "ijklmnop"  8 x 8                398,593                81            81

└ 첫 두 줄은 두 길이가 같은데 부른 횟수가 4.5 배로 갈린다
└ 서로 다른 (i, j) 는 DP 테이블 칸 수를 넘지 않는다. 그 칸 수는 글자를 안 보고 두 길이로 정해진다

과제 규모 n = m = 1,000 이고 공통 글자가 없으면
  기억 없이 부르는 횟수  764 자리 수
  DP 테이블 칸             1,002,001
```

같은 `5 x 3` 인데 부른 횟수가 77 과 346 으로 갈립니다. 마지막 글자가 같으면 한 갈래로만 내려가고, 다르면 세 갈래로
벌어지기 때문이에요. 여기서 눈여겨볼 것은 넷째 열입니다. 346 번을 불렀는데 **서로 다른 `(i, j)` 는 DP 테이블 칸 수를
넘지 않아요.** 같은 앞부분 한 쌍을 여러 갈래에서 거듭 계산하고 있다는 뜻입니다. 한 번 낸 `f(i, j)` 를 칸에 적어 두고
다시 읽으면 비용은 칸 수가 되고, 칸 수는 글자를 안 보고 두 길이로 정해져요. 지금까지 해 본 방법을 차례로 놓으면
이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **접두어 쌍 DP 테이블**입니다. 두 문자열의 앞부분을 접두어라고 하고, 줄은 `s` 의 접두어
길이 `i`, 열은 `t` 의 접두어 길이 `j` 예요. 테두리에 무엇을 적는지, 칸 하나가 어느 칸을 읽는지, 왜 그 갈래로
충분한지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 접두어 쌍 DP 테이블

이 아이디어를 한 문장으로 줄이면 이렇습니다. **`s` 의 글자를 한 줄에 하나씩 보며 DP 테이블의 칸 `dp[i][j]` 에 「`s` 의
앞 `i` 글자를 `t` 의 앞 `j` 글자로 바꾸는 최소 편집 횟수」를 적고, 오른쪽 아래 칸을 답으로 읽습니다.** 이 방법을
실현하는 순서대로 세 단계를 설명합니다. 앞 단계에서 만든 것을 뒤 단계에서 씁니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 크기와 테두리 정하기 | 줄 `n+1` 개 · 줄마다 칸 `m+1` 개를 만들고, 0 번째 열에 `i` 를, 0 번째 줄에 `j` 를 적는다 | — |
| 2단계 칸 하나를 네 갈래로 정하기 | 두 글자가 같으면 왼쪽 위를 그대로, 다르면 교체 · 삭제 · 삽입 세 후보 중 가장 작은 값에 1 을 더한다 | 1단계의 테두리 · 앞 줄 · 같은 줄의 왼쪽 칸 |
| 3단계 오른쪽 아래 칸 읽기 | `dp[n][m]` 을 답으로 돌려준다 | 2단계가 채운 마지막 줄 |

#### 1단계 — DP 테이블의 크기와 테두리 정하기

DP 테이블에는 줄이 `n+1` 개, 줄마다 칸이 `m+1` 개 있습니다. `+1` 은 둘 다 「한 글자도 안 본 상태」를 칸으로 두는
자리예요. `s` 를 안 본 줄 `i=0` 과 `t` 를 안 본 열 `j=0` 입니다. 전개 입력과 규모의 끝에서 크기를 세면 이렇습니다.

<!--proof:build-size-->

| n | m | 줄 수 n+1 | 줄마다 칸 수 m+1 | 모든 칸 |
| ---: | ---: | ---: | ---: | ---: |
| 5 | 3 | 6 | 4 | 24 |
| 1,000 | 1,000 | 1,001 | 1,001 | 1,002,001 |

전개 입력에서 정본이 깐 DP 테이블은 6 줄 × 4 칸, 모두 24 칸입니다.

<!--/proof-->

0 번째 줄과 0 번째 열은 계산하지 않고 바로 정합니다. 한쪽이 빈 문자열이면 할 수 있는 일이 하나뿐이에요. `t` 가 비어
있으면 `s` 의 글자를 전부 지워야 하고, `s` 가 비어 있으면 `t` 의 글자를 전부 넣어야 합니다. 곁말은 그 칸이 뜻하는
일이에요.

<!--fig:build-border-->
![테두리 — 0 번째 열은 지우는 횟수, 0 번째 줄은 넣는 횟수](./figs/build-border.svg)

테두리 몇 칸이 뜻하는 일과 값을 적고, 편집을 한 번씩 해 보며 센 값과 맞대 봤습니다.

<!--proof:build-border-->

| 칸 | s 의 앞부분 | t 의 앞부분 | 하는 일 | 값 |
| --- | --- | --- | --- | ---: |
| dp[0][0] | "" | "" | 할 일이 없다 | 0 |
| dp[3][0] | "hor" | "" | 3 글자를 지운다 | 3 |
| dp[5][0] | "horse" | "" | 5 글자를 지운다 | 5 |
| dp[0][2] | "" | "ro" | 2 글자를 넣는다 | 2 |
| dp[0][3] | "" | "ros" | 3 글자를 넣는다 | 3 |

테두리 9 칸 가운데 9 칸에서, 편집을 한 번씩 해 보며 센 최소 횟수가 적어 둔 값과 같습니다.

<!--/proof-->

이 테두리가 최장 공통 부분 수열의 DP 테이블과 갈리는 자리입니다. 그쪽은 한쪽이 비면 공통으로 남는 것이 없어 테두리가
전부 0 이지만, 여기서는 한쪽이 비면 다른 쪽을 전부 지우거나 넣어야 해서 테두리가 `0 1 2 3 …` 으로 늘어나요.
이제 칸 하나가 무엇을 뜻하는지 `dp[3][2]` 로 확인해 봅시다. 3 번째 줄 · 2 번째 열이라 `s` 의 앞 `"hor"` 를 `t` 의 앞
`"ro"` 로 바꾸는 답이에요. 그림에서 대시로 그린 칸은 이번에 보지 않는 칸입니다.

<!--fig:build-read-cell-->
![dp[3][2] — s 의 앞 "hor" 를 t 의 앞 "ro" 로 바꾸는 최소 편집 횟수](./figs/build-read-cell.svg)

두 앞부분만 놓고 편집을 찾으면 이렇습니다.

<!--proof:build-read-one-->

| 번째 | 편집 | 편집 전 | 편집 후 |
| ---: | --- | --- | --- |
| 1 | h 를 r 로 교체 | "hor" | "ror" |
| 2 | r 을 삭제 | "ror" | "ro" |

"hor" 를 "ro" 로 바꾸는 편집은 이 2 번이고, 편집을 한 번씩 해 보며 찾아가도 2 번보다 적게는 안 됩니다. DP 테이블의 dp[3][2] 도 2 입니다.

<!--/proof-->

칸 하나는 두 문자열 전체가 아니라 **앞부분 한 쌍**의 답입니다. 같은 줄의 칸은 `s` 의 같은 앞부분을 `t` 의 한 글자씩
더 긴 앞부분으로 바꾸고, 같은 열의 칸은 `s` 를 한 글자씩 더 보며 `t` 의 같은 앞부분으로 바꿔요. 오른쪽 아래 칸이 두
문자열 전체의 답이 되는 까닭이 이것입니다.

#### 2단계 — 칸 하나를 네 갈래로 정하기

칸 `dp[i][j]` 는 새로 보는 두 글자 `s[i-1]` 과 `t[j-1]` 로 갈립니다. 같으면 ④ 왼쪽 위를 그대로 적고, 다르면 ⑤
세 후보 중 가장 작은 값에 1 을 더해요. 세 후보가 곧 마지막 편집 셋입니다.

| 후보 | 읽는 칸 | 마지막 편집 | 남는 일 |
| --- | --- | --- | --- |
| 왼쪽 위 | `dp[i-1][j-1]` | `s[i-1]` 을 `t[j-1]` 로 교체한다 | 양쪽에서 한 글자씩 뗀 앞부분 |
| 위 | `dp[i-1][j]` | `s[i-1]` 을 삭제한다 | `s` 에서만 한 글자 뗀 앞부분 |
| 왼쪽 | `dp[i][j-1]` | `t[j-1]` 을 삽입한다 | `t` 에서만 한 글자 뗀 앞부분 |

같은 글자 칸 하나와, 다른 글자 칸 가운데 교체 · 삭제 · 삽입이 저마다 가장 작은 칸을 하나씩 그렸습니다.

<!--fig:build-reads-->
![칸 하나를 정하는 네 모양 — 같은 글자 · 교체가 가장 작은 칸 · 삭제가 가장 작은 칸 · 삽입이 가장 작은 칸](./figs/build-reads.svg)

가장 쉬운 경우는 윗 줄이 이미 다 차 있는 자리입니다. 읽을 칸이 준비돼 있어 읽기만 하면 돼요. 불안한 경우는 **줄의
첫 칸**입니다. 왼쪽에 이 줄의 칸이 아직 하나도 없어서, 읽을 왼쪽 칸이 없어 보이는 자리예요. `i=3` 줄을 왼쪽부터
채우며 읽은 값을 모두 적었습니다.

<!--proof:build-fill-row-->

| j | 두 글자 | 갈래 | 읽은 값 | 가장 작은 후보 | dp[3][j] |
| ---: | --- | --- | --- | --- | ---: |
| 1 | 'r' · 'r' | ④ | dp[2][0] = 2 | — | 2 |
| 2 | 'r' · 'o' | ⑤ | min(2, 1, 2) + 1 | 삭제 | 2 |
| 3 | 'r' · 's' | ⑤ | min(1, 2, 2) + 1 | 교체 | 2 |

이 줄에서 읽은 칸 7 개 가운데 5 개가 윗 줄 i=2 이고, 나머지 2 개는 같은 줄의 왼쪽 칸입니다. 읽은 칸 가운데 1 개는 테두리입니다.

<!--/proof-->

첫 칸 `j=1` 이 읽은 왼쪽 위 칸은 테두리 `dp[2][0]` 이고, 1단계에서 이미 2 로 정한 칸입니다. 테두리를 칸으로 깔아 둔
덕분에 줄의 첫 칸에도 특별한 분기가 없어요. 나머지 읽기는 왜 늘 준비돼 있는지 반복의 차례로 말할 수 있습니다. 바깥
반복이 `i` 를 하나 올리기 전에 안쪽 반복이 그 줄의 `j = 1 … m` 을 한 번씩 모두 정하므로, `i` 번째 줄을 채울 때 `i-1`
번째 줄은 이미 끝나 있습니다. 같은 줄의 왼쪽 칸 `dp[i][j-1]` 은 `j` 보다 작은 자리라 이 줄에서 먼저 정해졌고요. 한 줄의
칸은 `j = 1` 부터 `m` 까지 한 번씩만 정해지니 건너뛰는 칸도 없습니다.

두 글자가 같은 칸에서 왼쪽 위만 보는 것이 안전한지도 값으로 확인해 둡시다. 같은 글자 칸에서도 위를 거쳐 삭제하거나
왼쪽을 거쳐 삽입하는 길이 있는데, 그 길의 비용이 더 작으면 놓치는 셈이에요. 전개 입력에서 두 글자가 같은 칸의 세 후보를 모두
적으면 이렇습니다.

<!--proof:build-same-bound-->

| 칸 | 두 글자 | 왼쪽 위 | 위 + 1 | 왼쪽 + 1 |
| --- | --- | ---: | ---: | ---: |
| dp[2][2] | 'o' · 'o' | 1 | 3 | 3 |
| dp[3][1] | 'r' · 'r' | 2 | 3 | 4 |
| dp[4][3] | 's' · 's' | 2 | 3 | 4 |

두 글자가 같은 칸 3 개 가운데 3 개에서 왼쪽 위가 위 + 1 과 왼쪽 + 1 보다 크지 않습니다.

<!--/proof-->

세 칸 모두 왼쪽 위가 가장 작습니다. 이것은 이 입력의 우연이 아니라 늘 성립하는 성질이에요.

```text
위를 거친 길의 비용이 왼쪽 위보다 작을 수 없는 이유
  1. 이웃한 두 칸 dp[i-1][j] 와 dp[i-1][j-1] 은 t 의 앞부분이 한 글자 차이다
  2. dp[i-1][j-1] 짜리 편집 목록 끝에 t[j-1] 을 넣는 편집 하나를 붙이면 dp[i-1][j] 의 목록이 된다
  3. 그래서 dp[i-1][j] ≤ dp[i-1][j-1] + 1 이고, 같은 까닭으로 dp[i-1][j-1] ≤ dp[i-1][j] + 1 이다
  4. 뒤의 부등식이 곧 「왼쪽 위 ≤ 위 + 1」이다. 위를 거친 길의 값이 dp[i-1][j] + 1 이다
  └ 왼쪽을 거친 길도 s 쪽에서 같은 논리로 왼쪽 위보다 작아지지 않는다
```

두 글자가 다른 칸에서는 마지막 편집이 반드시 있습니다. 마지막 자리에서 `s` 의 글자를 `t` 의 글자로 바꾸거나, `s` 의
글자를 지우거나, `t` 의 글자를 넣는 셋이 전부라 가장 작은 쪽에 1 을 더한 값이 이 칸의 답이에요.

#### 3단계 — 오른쪽 아래 칸 읽기

마지막 줄 `i = n` 을 다 채우면 `s` 전체를 본 줄이 완성됩니다. 그 줄의 칸 `dp[n][j]` 는 `s` 전체를 `t` 의 앞 `j`
글자로 바꾸는 답이고, 돌려주는 것은 그중 오른쪽 끝 `dp[n][m]` 이에요. 마지막 줄을 `t` 의 앞부분마다 따로 호출한 답과
나란히 놓았습니다.

<!--proof:build-answer-->

| j | t 의 앞 j 글자 | dp[5][j] | editDistance("horse", t 의 앞 j 글자) |
| ---: | --- | ---: | ---: |
| 0 | "" | 5 | 5 |
| 1 | "r" | 4 | 4 |
| 2 | "ro" | 4 | 4 |
| 3 | "ros" | 3 | 3 |

4 열 가운데 4 열에서 두 값이 같습니다. 정본이 돌려주는 것은 오른쪽 끝 dp[5][3] = 3 하나입니다.

<!--/proof-->

횟수만 돌려주지만, 다 채운 DP 테이블에는 **어느 편집을 했는지**도 남아 있습니다. 오른쪽 아래에서 출발해 칸마다 그
값을 만든 이웃으로 거슬러 가면 돼요. 두 글자가 같고 왼쪽 위와 값이 같으면 왼쪽 위로, 아니면 교체 · 삭제 · 삽입 차례로
값이 1 작은 이웃을 찾아 갑니다. 곁말의 「지나온 칸」이 거슬러 온 칸 수입니다.

<!--fig:build-trace-back-->
![dp[5][3] 에서 거슬러 따라가기 — 걸음 하나가 편집 하나다](./figs/build-trace-back.svg)

<!--proof:build-trace-back-path-->

| 걸음 | 선 칸 | 가는 쪽 | 편집 | 비용 | 지나온 비용 |
| ---: | --- | --- | --- | ---: | ---: |
| 1 | dp[5][3] = 3 | 위로 → dp[4][3] | 삭제 e | 1 | 1 |
| 2 | dp[4][3] = 2 | 왼쪽 위로 → dp[3][2] | 그대로 s | 0 | 1 |
| 3 | dp[3][2] = 2 | 위로 → dp[2][2] | 삭제 r | 1 | 2 |
| 4 | dp[2][2] = 1 | 왼쪽 위로 → dp[1][1] | 그대로 o | 0 | 2 |
| 5 | dp[1][1] = 1 | 왼쪽 위로 → dp[0][0] | 교체 r | 1 | 3 |

테두리의 dp[0][0] 에 이르기까지 5 걸음이고, 비용 합 3 이 dp[5][3] = 3 과 같습니다. 이 편집을 "horse" 에 앞에서부터 적용하면 "ros" 가 됩니다.

<!--/proof-->

왼쪽 위로 간 걸음은 2단계의 ④ 로 정한 칸이면 「그대로」, ⑤ 로 정한 칸이면 교체입니다. 위로 간 걸음은 `s` 의 글자를
지운 삭제, 왼쪽으로 간 걸음은 `t` 의 글자를 넣은 삽입이에요. 걸음 하나가 편집 하나라, 지나온 비용의 합이 곧 오른쪽 아래
칸의 값이 됩니다.

#### 이 방법이 기대는 전제

이 방법은 전제 셋 위에서 성립합니다. 하나라도 빠지면 테두리나 칸 하나가 읽는 이웃이 바뀌어요.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 한쪽이 비면 다른 쪽을 전부 지우거나 넣어야 한다 | 1단계의 테두리 `i` · `j` | 테두리가 0 이면 앞부분을 비용 없이 버리는 다른 과제가 된다 |
| 교체가 한 번의 편집이다 | 2단계의 왼쪽 위 후보 | 교체가 없으면 삭제와 삽입 두 번이 들어 값이 커진다 |
| 세 편집의 비용이 같다 | 모든 후보에 똑같이 1 을 더한다 | 비용이 다르면 후보마다 다른 값을 더해야 하고, 바꾸는 방향에 따라 답이 갈린다 |

세 경우가 실제로 어떤 값을 내는지는 「불변식」의 깨뜨려 보기와, 「수행으로 알아보는 알고리즘」의 「짚고 가기 — 교체를
삭제와 삽입으로 대신하면 답이 커진다」 · 「짚고 가기 — 비용이 셋 다 1 이 아니면 바꾸는 방향에 따라 답이 달라진다」에서
실행 결과로 봅니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 네 걸음이 됩니다.

1. DP 테이블을 `(n+1) × (m+1)` 로 만들고, 0 번째 열에 `i` 를, 0 번째 줄에 `j` 를 적는다
2. `i` 를 1 부터 `n` 까지 올리며 줄마다 `s[i-1]` 을 본다
3. 그 줄에서 `j` 를 1 부터 `m` 까지 올리며, `s[i-1]` 과 `t[j-1]` 이 같으면 왼쪽 위를 그대로, 다르면 왼쪽 위 · 위 · 왼쪽 중 가장 작은 값에 1 을 더해 적는다
4. `dp[n][m]` 을 돌려준다

### 수행으로 알아보는 알고리즘 — DP 테이블 여섯 줄을 열일곱 걸음으로 채운다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그 조각만
실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const s = "horse";
const t = "ros";
// 이 절이 끝나면 3 이 나와야 한다
```

왜 하필 이 둘일까요? 두 글자가 같은 칸이 있고, 다른 글자 칸에서도 교체 · 삭제 · 삽입이 저마다 **혼자 가장 작아지는
칸**이 있어서 모든 갈래가 실행되기 때문이에요.

<!--proof:walk-branches-->

```text
두 글자가 같은 칸         (2, 2) (3, 1) (4, 3)         ④
교체가 혼자 가장 작은 칸  (1, 1) (3, 3)                ⑤ 의 왼쪽 위
삭제가 혼자 가장 작은 칸  (3, 2) (4, 1) (5, 1) (5, 3)  ⑤ 의 위
삽입이 혼자 가장 작은 칸  (2, 3)                       ⑤ 의 왼쪽
```

절차 전체를 한 장으로 적으면 이렇습니다. 원문자는 아래 코드 조각에 그대로 달려 있어요.

```text
DP 테이블 dp 를 (n+1) × (m+1) 로 만든다
첫 열에 i 를 적는다                                             ① 지우기 비용
첫 줄에 j 를 적는다                                             ② 넣기 비용

i 를 1 부터 n 까지:
    j 를 1 부터 m 까지:                                         ③ 채울 칸이 남았는가
        만약 s[i-1] = t[j-1] 이면:
            dp[i][j] ← dp[i-1][j-1]                             ④ 같다
        아니면:
            dp[i][j] ← min(dp[i-1][j-1], dp[i-1][j], dp[i][j-1]) + 1   ⑤ 다르다

dp[n][m] 을 돌려준다
```

#### 1. DP 테이블을 깔고 테두리에 지우기 · 넣기 비용을 적는다

1단계에서 정한 크기대로 DP 테이블을 만들고, 첫 열과 첫 줄에 한쪽이 빈 문자열일 때의 비용을 적습니다.

```ts
const n = s.length;
const m = t.length;
const dp: number[][] = Array.from({ length: n + 1 }, () =>
  new Array<number>(m + 1).fill(0),
);

for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = i; // ① 지우기 비용
for (let j = 0; j <= m; j++) (dp[0] as number[])[j] = j; // ② 넣기 비용
```

실행하면 이렇게 나옵니다. 한쪽이 빈 입력도 함께 넣었어요.

<!--proof:walk-init-->

```text
       j=0  j=1 r  j=2 o  j=3 s
i=0 -    0      1      2      3
i=1 h    1      ·      ·      ·
i=2 o    2      ·      ·      ·
i=3 r    3      ·      ·      ·
i=4 s    4      ·      ·      ·
i=5 e    5      ·      ·      ·
  └ · 은 fill(0) 이 둔 0 이다. 아직 안 정한 칸이라 값에 뜻이 없다

s = "", t = "abc"     →  1 줄 × 4 칸, 칸을 0 개 정하고 dp[0][3] = 3 반환
s = "abc", t = ""     →  4 줄 × 1 칸, 칸을 0 개 정하고 dp[3][0] = 3 반환
s = "", t = ""        →  1 줄 × 1 칸, 칸을 0 개 정하고 dp[0][0] = 0 반환
```

`fill(0)` 이 깔아 둔 0 은 아직 정하지 않은 칸이라 값에 뜻이 없고, 다음 조각이 한 칸씩 덮어써요. 한쪽이 빈 문자열이면
다음 조각의 안쪽 반복에 한 번도 들어가지 않아 테두리에 적어 둔 값이 그대로 답이 됩니다. 빈 입력을 위한 분기를 따로
두지 않아도 되는 까닭이 이 테두리예요.

#### 2. 줄마다 윗 줄과 이번 줄에 이름을 붙인다

바깥 반복이 `s` 의 글자, 안쪽 반복이 `t` 의 글자입니다. 2단계의 칸 규칙이 읽는 줄이 윗 줄과 이번 줄 둘뿐이라, 두 줄에
이름을 붙여 둡니다.

```ts
for (let i = 1; i <= n; i++) {
  const prev = dp[i - 1] as number[]; // 윗 줄 — s 의 앞 i-1 글자까지만 본 줄
  const cur = dp[i] as number[]; // 이번 줄 — s 의 앞 i 글자까지 본 줄

  for (let j = 1; j <= m; j++) {
    // ③ 채울 칸이 남았는가 — 여기서 칸 하나가 정해진다
  }
}
```

두 반복이 칸을 정하는 차례는 이렇습니다.

<!--proof:walk-order-->

```text
i=1 ('h')   j = 1 → 2 → 3
i=2 ('o')   j = 1 → 2 → 3
i=3 ('r')   j = 1 → 2 → 3
i=4 ('s')   j = 1 → 2 → 3
i=5 ('e')   j = 1 → 2 → 3
  └ 한 줄을 왼쪽 끝부터 오른쪽 끝까지 다 정한 뒤 다음 줄로 간다
```

#### 3. 칸 하나를 두 갈래로 정한다

안쪽 반복의 몸통입니다. ⑤ 의 세 후보에는 그 후보가 뜻하는 편집의 이름을 붙여 둡니다.

```ts
if (s[i - 1] === t[j - 1]) {
  // ④ 두 글자가 같다 — 편집을 하나도 쓰지 않고 대각선 칸의 비용을 그대로 받는다.
  cur[j] = prev[j - 1] as number;
} else {
  // ⑤ 다르다 — 세 후보 중 가장 작은 비용에 편집 한 번을 더한다.
  const sub = prev[j - 1] as number; // 교체 — 양쪽에서 한 글자씩 지나간다
  const del = prev[j] as number; // 삭제 — s 의 글자 하나를 버린다
  const ins = cur[j - 1] as number; // 삽입 — t 의 글자 하나를 넣는다
  cur[j] = Math.min(sub, del, ins) + 1;
}
```

세 후보에 이름을 붙여 둔 것은 편의가 아닙니다. 세 첨자가 각각 어느 편집인지가 이 알고리즘의 전부인데, `prev[j - 1]`
처럼 첨자로만 적으면 그 뜻이 수 뒤에 숨어요. **`sub` 는 왼쪽 위, `del` 은 윗 줄의 같은 열, `ins` 는 같은 줄의 왼쪽
칸입니다.** 앞 두 줄만 실행하면 이렇게 나옵니다.

<!--proof:walk-two-rows-->

```text
걸음   줄   s 의 글자  j=0  j=1 r  j=2 o  j=3 s  갈래
T2~T4  i=1  h            1      1      2      3  ⑤⑤⑤
T5~T7  i=2  o            2      2      1      2  ⑤④⑤

③ j <= m 은 j = 1 … 3 에서 참이고 j = 4 에서 처음 거짓이 되어 줄이 끝난다
```

`i=2` 줄의 `j=2` 가 처음으로 ④ 가 나오는 칸입니다. `'o'` 가 같아 왼쪽 위 `dp[1][1] = 1` 을 **그대로** 가져왔어요.
값이 커지지 않는 유일한 갈래이고, 그 1 이 오른쪽 칸 `dp[2][3]` 의 삽입 후보로 이어졌습니다.

#### 짚고 가기 — 위 칸은 삭제이고 왼쪽 칸은 삽입이다

여기서 헷갈리기 쉬운 포인트는 `del` 과 `ins` 의 방향입니다. 「위 칸에서 왔으면 `t` 의 글자를 넣은 것」으로 뒤집어
외우기 쉬워요. 3단계에서 거슬러 찾은 편집 목록을 그 생각대로 읽어 봅시다.

<!--proof:pause-direction-->

```text
칸        옳게 읽으면  뒤바꿔 읽으면  비용
dp[1][1]  교체 r       교체 r            1
dp[2][2]  그대로 o     그대로 o          0
dp[3][2]  삭제 r       삽입 o            1
dp[4][3]  그대로 s     그대로 s          0
dp[5][3]  삭제 e       삽입 s            1

옳게 읽은 목록을 적용한 결과    "ros"      길이 3
뒤바꿔 읽은 목록을 적용한 결과  "roorsse"  길이 7
└ 뒤바꿔 읽으면 지울 글자 2 개를 지우지 않고 오히려 2 개를 넣어, 길이가 5 + 2 = 7 이 된다
```

**DP 테이블의 값 3 은 안 틀립니다.** 뒤바꿔 읽어도 `dp[5][3]` 은 그대로 3 이에요 — 세 후보가 전부 `Math.min` 안에
들어 있어서 이름을 바꿔도 고르는 값이 안 바뀝니다. 틀리는 것은 그 값을 편집 목록으로 되읽을 때이고, 위 결과의
`"roorsse"` 가 그 모습이에요. 어느 쪽이 삭제인지는 테두리가 정합니다.

```text
어느 쪽이 삭제인지는 테두리가 정한다
  dp[i][0] = i    t 가 비었다. s 를 i 번 지운다   첫 열을 따라 아래로 가는 것이 삭제다
  dp[0][j] = j    s 가 비었다. t 를 j 번 넣는다   첫 줄을 따라 오른쪽으로 가는 것이 삽입이다
  └ 아래로 한 칸은 s 를 한 글자 더 본 것이고, 그 글자를 t 와 짝짓지 않았으니 지운 것이다
```

> 위는 `s` 를 한 글자 덜 본 칸이다 — 그래서 삭제다.

#### 짚고 가기 — 교체를 삭제와 삽입으로 대신하면 답이 커진다

⑤ 에서도 헷갈리기 쉬운 포인트가 있습니다. 「교체 한 번은 삭제 한 번과 삽입 한 번으로도 되니까, 왼쪽 위 후보는 없어도
되지 않나」로 읽기 쉬워요. 그 생각대로 한 줄만 바꿔 봅시다.

```ts
cur[j] = Math.min(del, ins) + 1; // 교체 후보를 뺐다
```

다섯 입력으로 확인해 봅니다. 오른쪽에 `n + m − 2 × LCS` 를 함께 적었어요. `LCS` 는 두 문자열의 최장 공통 부분 수열의
길이입니다.

<!--proof:pause-no-sub-->

```text
입력                        정본이 낸 답  교체를 뺀 답  n + m - 2 x LCS  판정
전개 입력 "horse" 와 "ros"             3             4                4  틀리다
"a" 와 "b"                             1             2                2  틀리다
"kitten" 과 "sitting"                  3             5                5  틀리다
"abcd" 와 "bcda"                       2             2                2  같다
"flaw" 와 "lawn"                       2             2                2  같다

└ 교체를 뺀 답이 5 줄 가운데 5 줄에서 n + m - 2 x LCS 와 같다
```

**교체를 빼면 값이 커집니다.** `"a"` 를 `"b"` 로 바꾸는 데 교체는 한 번이지만, 삭제와 삽입으로는 두 번이에요. 그런데
다섯 입력 중 둘은 답이 같습니다. 그 둘은 교체를 안 쓰고도 같은 횟수로 끝나는 편집 목록이 있다는 뜻이고, 「교체가 필요
없는 입력」과 「교체가 없어도 되는 규칙」은 다른 이야기예요. 넷째 열이 교체를 뺀 답과 모든 입력에서 같은 것도
우연이 아닙니다. 삭제와 삽입만 쓰면 **양쪽에 공통으로 남는 부분 수열**을 빼고 나머지를 전부 지우고 넣는 셈이라, 그
비용이 `n + m − 2 × LCS` 가 돼요.

#### 4. DP 테이블 여섯 줄을 열일곱 걸음으로 채운다

앞의 세 조각을 이어 `editDistance("horse", "ros")` 를 실행하면 열일곱 걸음이 됩니다. 테두리를 적는 한 걸음, 칸 열다섯을
한 걸음에 하나씩, 답을 읽는 한 걸음이에요. 걸음마다 무대의 점선 칸은 아직 안 정한 칸, 강조색 굵은 테가 이번에 정한
칸, 진한 테를 두른 칸이 그 칸이 읽은 칸입니다. 먼저 테두리와 `i=1` · `i=2` 줄이에요.

#### 짚고 가기 — 비용이 셋 다 1 이 아니면 바꾸는 방향에 따라 답이 달라진다

이 글의 과제는 세 편집의 비용이 모두 1 입니다. 이 조건이 어디에 쓰이는지 모르고 지나가면 「편집 거리는 두 문자열의
순서를 바꿔도 같다」를 늘 참인 성질로 외우게 돼요. 실제 도구가 쓰는 비용을 넣어 확인해 봅시다. 세 비용을 따로 받는
사본은 테두리에 `i × 삭제 비용` · `j × 삽입 비용` 을 적고, 후보마다 자기 비용을 더합니다.

<!--proof:pause-cost-->

```text
바꾸는 방향       비용이 셋 다 1  교체 2 · 삭제 3 · 삽입 1
"ab" -> "abc"                  1                         1
"abc" -> "ab"                  1                         3
"horse" -> "ros"               3                         8
"ros" -> "horse"               3                         4

└ 가운데 열은 방향을 바꿔도 값이 같고, 오른쪽 열은 "abc" -> "ab" 가 3, "ab" -> "abc" 가 1 로 갈린다
```

오른쪽 열의 비용은 지어낸 값이 아닙니다. git 이 명령어 오타를 고쳐 줄 때 부르는 함수가 그 값을 씁니다 —
`levenshtein(cmd, candidate, 0, 2, 1, 3)` 이고, 인자 순서가 맞바꾸기 · 교체 · 넣기 · 지우기예요
([git 저장소의 `help.c`](https://github.com/git/git/blob/master/help.c), 조회 2026-08-30).
같은 저장소의 구현 파일이 *"Note that this algorithm calculates a distance _iff_ d == a"* 라고
적어 둡니다 — 지우기와 넣기의 비용이 같아야 거리가 된다는 뜻인데, git 이 넘기는 값은 그
조건을 안 지킵니다
([`levenshtein.c`](https://github.com/git/git/blob/master/levenshtein.c), 조회 2026-08-30).

```text
비용이 갈리면 무엇이 성립하지 않는가
  d(x, y) = d(y, x)      셋 다 1 이면 참이다. 삭제와 삽입이 서로를 되돌리는 편집이라 맞바뀐다
  d(x, y) = d(y, x)      삭제와 삽입의 비용이 다르면 거짓이다. 두 문자열을 맞바꾸면 삭제와 삽입도 맞바뀐다
  └ 이 글의 DP 테이블은 세 비용이 같다는 조건에서만 방향을 안 가린다
```

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 오른쪽 아래 칸을 돌려주는 마지막 한 줄뿐이에요.

```ts
export function editDistance(s: string, t: string): number {
  const n = s.length;
  const m = t.length;

  const dp: number[][] = Array.from({ length: n + 1 }, () =>
    new Array<number>(m + 1).fill(0),
  );

  // ① 첫 열 — t 가 빈 문자열인 자리다. s 의 앞 i 글자를 전부 지워야 하므로 비용이 i 다.
  for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = i;

  // ② 첫 줄 — s 가 빈 문자열인 자리다. t 의 앞 j 글자를 전부 넣어야 하므로 비용이 j 다.
  for (let j = 0; j <= m; j++) (dp[0] as number[])[j] = j;

  for (let i = 1; i <= n; i++) {
    const prev = dp[i - 1] as number[]; // 윗 줄 — s 의 앞 i-1 글자까지만 본 줄
    const cur = dp[i] as number[]; // 이번 줄 — s 의 앞 i 글자까지 본 줄

    for (let j = 1; j <= m; j++) {
      // ③ 채울 칸이 남았는가 — 남아 있으면 아래 두 갈래 중 하나로 이 칸을 정한다.
      if (s[i - 1] === t[j - 1]) {
        // ④ 두 글자가 같다 — 편집을 하나도 쓰지 않고 대각선 칸의 비용을 그대로 받는다.
        cur[j] = prev[j - 1] as number;
      } else {
        // ⑤ 다르다 — 세 후보 중 가장 작은 비용에 편집 한 번을 더한다.
        const sub = prev[j - 1] as number; // 교체 — 양쪽에서 한 글자씩 지나간다
        const del = prev[j] as number; // 삭제 — s 의 글자 하나를 버린다
        const ins = cur[j - 1] as number; // 삽입 — t 의 글자 하나를 넣는다
        cur[j] = Math.min(sub, del, ins) + 1;
      }
    }
  }

  return (dp[n] as number[])[m] as number;
}
```

실행하면 이렇게 나옵니다.

<!--proof:final-run-->

```text
editDistance("horse", "ros")            →  3
editDistance("intention", "execution")  →  5
editDistance("kitten", "sitting")       →  3
editDistance("", "abc")                 →  3
editDistance("abc", "")                 →  3
editDistance("", "")                    →  0
```

### 알아 두면 좋은 개념 — 격자 위의 최단 경로

3단계에서 DP 테이블을 거슬러 얻은 걸음에는 이름이 붙어 있습니다. DP 테이블의 칸을 점으로 보고 네 갈래를 그 점에서
나가는 길로 보면, `dp[n][m]` 은 **왼쪽 위에서 오른쪽 아래까지 가는 경로 가운데 비용이 가장 작은 것의 값**이에요.
아래로 한 칸이 삭제, 오른쪽으로 한 칸이 삽입, 대각선 한 칸이 교체이거나 두 글자가 같은 「그대로」입니다. 전개 입력에서
거슬러 찾은 경로를 DP 테이블 위에 그리면 이렇습니다.

<!--fig:related-path-->
![격자 위의 경로 — (0, 0) 에서 (5, 3) 까지 비용 3 인 길](./figs/related-path.svg)

경로를 따라가며 비용을 쌓으면 걸음마다 그 칸의 값과 같아요.

<!--proof:related-path-->

```text
걸음              방향    편집      비용  누적  그 칸의 값
(0, 0) -> (1, 1)  대각선  교체 r       1     1           1
(1, 1) -> (2, 2)  대각선  그대로 o     0     1           1
(2, 2) -> (3, 2)  아래    삭제 r       1     2           2
(3, 2) -> (4, 3)  대각선  그대로 s     0     2           2
(4, 3) -> (5, 3)  아래    삭제 e       1     3           3

└ 누적과 칸의 값이 5 걸음 가운데 5 걸음에서 같다. 경로의 비용 합 3 이 오른쪽 아래 칸의 값이다
```

길에 방향이 있고 되돌아오는 길이 없는 격자에서는 **왼쪽 위부터 차례로 한 번씩 보는 것만으로** 비용이 가장 작은 경로가
나옵니다. 칸 하나를 정할 때 그 칸으로 들어오는 길이 전부 이미 정해진 칸에서 오기 때문이에요. 같은 이름을 다른 자리에서도
만납니다. [최장 공통 부분 수열](../longestCommonSubsequence/longestCommonSubsequence-guide.md) 은 같은 격자에서 비용이 가장
작은 경로 대신 대각선 걸음이 가장 많은 경로를 찾고, 생물 서열의 전역 정렬은 같은 격자에서 길의 비용만 점수로 바꾼 것이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 전이식을 어떻게 세우는지, 무엇이 매 칸 참으로 남는지,
그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **한 자리를 고치면 그 뒤가 통째로 옮겨집니다.** 같은 자리끼리 따로 비교해도 되는 과제라면 DP 테이블이 필요 없고
  자리를 한 번씩 보면 끝나요.
- **마지막 한 자리를 보는 것만으로 갈래가 유한하게 갈립니다.** 여기서는 넷이고, 그래서 칸 하나가 이웃 셋만 읽습니다.
- **두 길이의 곱이 감당할 만합니다.** DP 테이블의 칸이 두 길이의 곱이라, 곱이 너무 크면 DP 테이블을 못 깝니다.
- **답이 얼마나 클지 미리 모릅니다.** 답이 작다는 것을 알면 DP 테이블을 통째로 안 채워도 되고, 그 경우는 아래 「경쟁
  설계와의 대조」가 값으로 잽니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  뒤가 옮겨진다               → 상태가 접두어 쌍이다
  갈래가 넷이다               → 칸 하나가 이웃 셋만 읽는다
  두 길이의 곱이 감당된다     → DP 테이블을 통째로 깔 수 있다
  답의 크기를 모른다          → 문턱 없이 한 번에 채운다
```

세 번째 줄이 이 절차의 경계입니다. 글자가 아니라 파일의 줄이나 유전자 서열을 비교하느라 두 길이가 수십만이 되면 칸
수와 메모리가 이렇게 불어나요.

<!--proof:fit-scale-->

```text
      n        m   칸 (n+1)(m+1)  칸마다 4 바이트
  1,000    1,000       1,002,001          약 4 MB
100,000  100,000  10,000,200,001         약 40 GB
```

앞은 이 글의 절차가 그대로 쓰이는 규모이고, 뒤는 다른 절차를 찾아야 하는 규모입니다.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "최소 편집"  "삽입 삭제 교체"  "몇 번 고치면"        ← 편집 셋이 이웃 셋이 된다
  "두 문자열이 얼마나 비슷한가"  "오타 교정"           ← 자리가 옮겨지는 비교다
  "가장 가까운 단어"  "유사도"                        ← 거리를 값으로 요구한다
  "두 서열을 정렬"                                    ← 같은 격자에 점수를 붙인 것이다

제약에 이런 모양이 보이면
  두 길이의 곱은 DP 테이블을 깔 만한데, 편집을 해 보며 찾기에는 답이 크다
  답이 얼마나 될지 아무 말도 없다

반대로 이런 말이 보이면 해당하지 않는다
  "자리를 그대로 두고"  "같은 길이"만 다룬다   ← 같은 자리끼리 비교하면 끝난다
  "두 길이가 10^5 이다"                        ← DP 테이블을 통째로 깔 수 없다
  "거리가 2 이하인 것만"                       ← 문턱이 있으면 띠만 채우면 된다
```

마지막 줄이 「경쟁 설계와의 대조」로 이어집니다. 답의 상한이 주어지면 DP 테이블 전체를 채울 이유가 없어져요.

#### 실제로 쓰이는 곳

- **PostgreSQL `fuzzystrmatch` 확장의 `levenshtein()`.** 공식 문서가
  *"This function calculates the Levenshtein distance between two strings"* 라 적고, 시그니처를
  `levenshtein(source text, target text, ins_cost int, del_cost int, sub_cost int) returns int`
  로 둡니다. 비용을 생략하면 *"they all default to 1"* 이라 이 글이 푸는 과제와 같아져요. 같은
  문서에 문턱을 받는 변형이 함께 있습니다 — `levenshtein_less_equal` 은
  *"an accelerated version of the Levenshtein function for use when only small distances are of
  interest"* 이고, *"If the actual distance is less than or equal to `max_d`, then
  `levenshtein_less_equal` returns the correct distance; otherwise it returns some value greater
  than `max_d`"* 입니다.
  ([PostgreSQL 공식 문서 — `fuzzystrmatch`](https://www.postgresql.org/docs/current/fuzzystrmatch.html),
  조회 2026-08-30)
- **git 의 명령어 오타 교정.** `help.c` 의 `help_unknown_cmd` 가 후보 명령어마다
  `levenshtein(cmd, candidate, 0, 2, 1, 3) + 1` 을 계산하고, 가장 가까운 것을
  *"The most similar command is"* 로 보여 줍니다. 인자 넷이 맞바꾸기 0 · 교체 2 · 넣기 1 ·
  지우기 3 이라 **이 글의 비용과 다른 값**이에요.
  ([git 저장소의 `help.c`](https://github.com/git/git/blob/master/help.c), 조회 2026-08-30)
- **Elasticsearch 의 `fuzziness`.** 공식 문서가 *"`fuzziness` is interpreted as a Levenshtein
  Edit Distance — the number of one character changes that need to be made to one string to make
  it the same as another string"* 이라 적고, 받는 값을 *"The maximum allowed Levenshtein Edit
  Distance (or number of edits)"* 로 `0`·`1`·`2` 로 제한합니다. 기본값 `AUTO:3,6` 은 글자
  수 0\~2 면 정확히 일치, 3\~5 면 편집 한 번, 그보다 길면 편집 두 번까지 허용해요.
  ([Elasticsearch 공식 문서 — Common options](https://www.elastic.co/guide/en/elasticsearch/reference/current/common-options.html),
  조회 2026-08-30)

```text
세 자리가 서로 다른 것을 요구한다
  PostgreSQL     비용을 인자로 받는다                 세 비용이 같지 않을 수 있다
  git            교체 · 넣기 · 지우기 비용이 다르다   방향을 가리는 값이다
  Elasticsearch  편집 두 번까지만 본다                답의 상한이 미리 주어진다
  └ 셋째 줄이 DP 테이블을 통째로 안 채워도 되는 자리이고, 그것이 다음 절의 경쟁 설계다
```

#### 경쟁 설계와의 대조

최소 편집 횟수라는 같은 값을 내는 다른 절차가 있습니다 — **띠 계산과 문턱 배가**예요(Ukkonen, 1985). 문턱을 `k` 라
하면, 비용이 `k` 이하인 편집 목록은 DP 테이블의 대각선에서 `k` 칸 넘게 벗어날 수 없다는 성질(「수식 정의와 유도」가
유도합니다)을 써서 그 띠만 채우고, 나온 값이 `k` 를 넘으면 `k` 를 배로 늘려 다시 채웁니다. PostgreSQL 의
`levenshtein_less_equal` 이 문턱을 받는 것과 같은 자리예요.

```text
두 설계가 하는 일
  DP 테이블 채우기   (n+1)(m+1) 칸을 한 번씩 채운다. 답이 크든 작든 채우는 칸이 같다
  띠 계산            대각선에서 k 칸 안쪽만 채우고, 모자라면 k 를 배로 늘려 다시 채운다
  └ 답이 작으면 띠가 좁아 적게 채우고, 답이 크면 배가 때문에 같은 자리를 여러 번 채운다
```

두 설계에 같은 생성식 · 같은 길이의 입력을 주고 **값을 정한 칸**이 몇 개인지 셌습니다(테두리에
값을 적은 칸도 넣고, 띠 계산이 문턱을 늘려 다시 채운 칸은 다시 셉니다). **추가 칸**은 입력 두 문자열 밖에 동시에 들고 있는 칸의 최댓값이에요. 두 문자열의 길이는 둘 다 200
이고, `s` 의 `q` 번째 글자를 알파벳 26 개 중 `(37q) mod 26` 번째 것으로 만든 다음, `t` 는 자리 `floor(200q/c)` 의
글자만 알파벳에서 13 칸 옮긴 것이에요. 여기서 `c` 는 아래 첫 열의 「바꾼 글자 수」이고 `q` 는 0 부터 `c−1` 까지입니다.
**전개 입력을 그대로 쓰지 않은 이유**는 `"horse"` 와 `"ros"` 에서는 답 3 이 `t` 의 길이 3 과 같아 띠가 좁아질 여지가
없고, 문턱만 한 번 늘어나기 때문이에요. 그 크기에서는 경쟁 설계가 앞서는 쪽을 아예 못 봅니다.

<!--proof:alt-bench-->

| 바꾼 글자 수 | 답 | DP 테이블 채우기 | 띠 계산 | 적은 쪽 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 1 | 40,401 | **601** | 띠 계산 쪽이 67.2 배 적다 |
| 2 | 2 | 40,401 | **1,600** | 띠 계산 쪽이 25.3 배 적다 |
| 4 | 4 | 40,401 | **3,389** | 띠 계산 쪽이 11.9 배 적다 |
| 8 | 8 | 40,401 | **6,734** | 띠 계산 쪽이 6.0 배 적다 |
| 16 | 16 | 40,401 | **13,095** | 띠 계산 쪽이 3.1 배 적다 |
| 32 | 32 | 40,401 | **25,104** | 띠 계산 쪽이 1.6 배 적다 |
| 64 | 64 | **40,401** | 46,873 | DP 테이블 채우기 쪽이 1.2 배 적다 |
| 128 | 92 | **40,401** | 82,018 | DP 테이블 채우기 쪽이 2.0 배 적다 |

DP 테이블 채우기는 모든 줄에서 40,401 칸입니다. 전개 입력 "horse" 와 "ros" 에서는 DP 테이블 채우기 24 칸, 띠 계산 40 칸입니다.

<!--/proof-->

**경계는 답의 크기입니다.** DP 테이블 채우기는 답이 무엇이든 같고, 띠 계산만 답을 따라 움직여요. 바꾼 글자를 1 부터
하나씩 늘리며 재 보면 우열이 뒤집히는 자리가 이렇습니다.

<!--proof:alt-flip-->

```text
DP 테이블 채우기  (200+1)(200+1) = 40,401         답을 안 본다
띠 계산           문턱을 1 · 2 · 4 · … 로 늘린다  답이 32 면 32 에서 멈추고, 33 이면 64 까지 간다
뒤집히는 답       33                              25,104 에서 46,873 으로 뛰는 자리다
```

문턱이 배로 늘어나는 순간 띠 하나가 통째로 더 붙어서, 답이 1 커지는 것만으로 채우는 칸이 뛰어요. 추가 칸은 어느
쪽으로도 안 갈립니다. DP 테이블 채우기는 칸을 끝까지 들고 있고 띠 계산은 줄 두 개만 들고 있어, 추가 칸만 보면 답이
무엇이든 띠 쪽이 적습니다. 내주는 것과 얻는 것을 모으면 이렇습니다.

<!--proof:alt-trade-->

```text
내주는 것  추가 칸       40,401 대 402. DP 테이블을 통째로 들고 있다
내주는 것  작은 답       답이 1 이면 채우는 칸이 67.2 배 많다
얻는 것    큰 답         답이 92 이면 82,018 대 40,401 로 이쪽이 적다
얻는 것    한 번에 끝남  문턱을 몰라도 되고 같은 칸을 두 번 채우지 않는다
얻는 것    편집 목록     DP 테이블이 남아 있어 편집 목록을 거슬러 찾을 수 있다
```

이 글의 규모는 두 길이 1,000 이하에서 답의 상한 없이 한 번 구하는 것이라 DP 테이블 채우기를 씁니다. **문턱이 주어지는
순간** 이 선택은 다시 해야 해요 — 바꾼 글자 1 에서는 띠 계산이 몇십 배 적게 채웠습니다.

### 수식 정의와 유도

정의부터 적습니다. 편집 목록 하나를 $\sigma$ 라 부르고, 그 안에 담긴 편집의 개수를 $|\sigma|$ 로 적어요. 문자열
$x$ 에 $\sigma$ 를 차례로 적용해 $y$ 가 되는 목록 전체를 $\mathrm{Script}(x, y)$ 라 두면 이렇게 됩니다.

$$dp[i][j] = \min_{\sigma \in \mathrm{Script}(s[1..i],\; t[1..j])} |\sigma|$$

```text
정의를 말로 펴면
  sigma        삽입 · 삭제 · 교체를 차례로 적은 목록 하나
  |sigma|      그 목록에 담긴 편집의 개수. 비용이 셋 다 1 이라 개수가 곧 비용이다
  s[1..i]      s 의 앞 i 글자. i = 0 이면 빈 문자열이다
  Script(x,y)  x 를 y 로 만드는 편집 목록 전부
  └ 어떤 문자열도 글자를 전부 지우고 다시 넣으면 다른 문자열이 되므로 Script 는 결코 비지 않는다
```

정의를 작은 값에 넣어 확인하고 갑시다. `s = "ho"` 와 `t = "or"` 의 접두어 쌍마다 편집을 한 번씩 해 보며 센 값과 DP
테이블의 값을 나란히 적었어요.

<!--proof:math-check-->

```text
i  j  s 의 앞 i 글자  t 의 앞 j 글자  한 번씩 편집해 센 최소 횟수  dp[i][j]
0  0  ""              ""                                        0         0
0  1  ""              "o"                                       1         1
0  2  ""              "or"                                      2         2
1  0  "h"             ""                                        1         1
1  1  "h"             "o"                                       1         1
1  2  "h"             "or"                                      2         2
2  0  "ho"            ""                                        2         2
2  1  "ho"            "o"                                       1         1
2  2  "ho"            "or"                                      2         2

└ 오른쪽 두 열이 9 줄 가운데 9 줄에서 같다
```

정의대로 센 값과 DP 테이블의 값이 모든 칸에서 같습니다. 이제 유도합니다. 먼저 **하한** 하나가 나와요. 편집 하나는
두 문자열의 길이 차이를 많아야 1 바꿉니다 — 삭제와 삽입은 한쪽 길이만 1 바꾸고, 교체는 양쪽을 그대로 둡니다.

$$dp[i][j] \ge |i - j|$$

```text
왜 길이 차이보다 작을 수 없는가
  삭제        s 쪽 길이가 1 준다          차이가 많아야 1 바뀐다
  삽입        s 쪽 길이가 1 는다          차이가 많아야 1 바뀐다
  교체        길이가 그대로다             차이가 안 바뀐다
  시작과 끝   차이가 |i - j| 에서 0 으로  그러려면 편집이 적어도 |i - j| 개 필요하다
```

다음은 점화식입니다. 마지막 편집이 무엇이었는지로 경우를 가르는데, 두 글자가 같으면 아무것도 안 하는 갈래가 하나 더
있어요. 갈래가 이 넷으로 전부인 것은 마지막 자리에서 `s` 의 글자를 쓰거나 안 쓰고 `t` 의 글자를 쓰거나 안 쓰는 조합이
그것뿐이기 때문입니다.

$$dp[i][j] = \begin{cases} dp[i-1][j-1] & (s[i-1] = t[j-1]) \\ 1 + \min\bigl(dp[i-1][j-1],\; dp[i-1][j],\; dp[i][j-1]\bigr) & (s[i-1] \ne t[j-1]) \end{cases}$$

```text
두 방향으로 확인한다
  상한   네 갈래 각각이 실제로 가능한 편집 목록을 하나씩 준다   dp[i][j] 는 그 최솟값을 넘지 못한다
  하한   어떤 최소 목록이든 마지막 편집이 넷 중 하나다          그 목록의 앞부분이 그 갈래의 값 이상이다
  └ 두 방향이 만나 등호가 된다

같은 글자에서 왼쪽 위를 그냥 쓰는 것이 왜 안전한가
  이웃 칸의 성질   |dp[i-1][j] - dp[i-1][j-1]| <= 1   접두어를 한 글자 늘린 답은 넣기나 지우기 한 번 차이다
  왼쪽 위를 쓴 값  dp[i-1][j-1]                       비용 0 을 더한다
  위를 쓴 값       dp[i-1][j] + 1                     위 성질에서 dp[i-1][j-1] 이상이다
  왼쪽을 쓴 값     dp[i][j-1] + 1                     같은 성질을 j 쪽에 쓰면 마찬가지다
  └ 그래서 같은 글자 칸에서는 최솟값을 다시 고를 필요가 없다
```

식을 그대로 옮기면 이런 조각이 됩니다. DP 테이블을 안 쓰고 정의만 따라간 형태예요.

```ts
const f = (i: number, j: number): number =>
  i === 0
    ? j
    : j === 0
      ? i
      : s[i - 1] === t[j - 1]
        ? f(i - 1, j - 1)
        : 1 + Math.min(f(i - 1, j - 1), f(i - 1, j), f(i, j - 1));
```

식의 `dp` 는 코드에서 `cur` 과 `prev` 두 이름으로 나뉩니다.

| 식 | 코드 | 자리 |
| --- | --- | --- |
| `dp[i][j]` | `cur[j]` | 지금 정하는 칸 |
| `dp[i-1][j-1]` | `prev[j-1]` | 윗 줄의 왼쪽 열 — 교체 후보 `sub` |
| `dp[i-1][j]` | `prev[j]` | 윗 줄의 같은 열 — 삭제 후보 `del` |
| `dp[i][j-1]` | `cur[j-1]` | 같은 줄의 바로 앞 칸 — 삽입 후보 `ins` |

여기서 본문의 값만으로는 안 나오는 것이 나옵니다. **갈래를 끝까지 펼쳤을 때 편집 목록의 뼈대가 몇 가지인가**를 임의의
`i` · `j` 로 닫을 수 있어요. 뼈대 하나는 격자에서 대각선 · 아래 · 오른쪽 세 걸음으로 `(0, 0)` 에서 `(i, j)` 까지 가는
경로 하나이고, 그 수를 $P(i, j)$ 라 적으면 점화식이 이렇게 됩니다.

$$P(i, 0) = P(0, j) = 1, \qquad P(i, j) = P(i-1, j) + P(i, j-1) + P(i-1, j-1)$$

점화식을 작은 값에 넣어 봅니다.

<!--proof:math-p-small-->

```text
P(1,1)  P(0,1) + P(1,0) + P(0,0)  = 1 + 1 + 1  = 3
P(1,2)  P(0,2) + P(1,1) + P(0,1)  = 1 + 3 + 1  = 5
P(2,2)  P(1,2) + P(2,1) + P(1,1)  = 5 + 5 + 3  = 13
```

닫힌 형태는 **대각선 걸음의 수로 갈라서** 나옵니다. 대각선을 `p` 번 쓰면 아래로 `i − p` 번, 오른쪽으로 `j − p` 번
가야 하고, 걸음이 모두 `i + j − p` 개예요. 그 걸음들을 늘어놓는 방법의 수가 곧 경로의 수입니다.

$$P(i, j) = \sum_{p=0}^{\min(i,j)} \frac{(i+j-p)!}{p!\,(i-p)!\,(j-p)!}$$

`i = j = 2` 에 넣어 항마다 세면 이렇습니다.

<!--proof:math-p-terms-->

```text
p = 0  대각선 0 번 · 아래 2 번 · 오른쪽 2 번  4! / (0! 2! 2!)  = 6
p = 1  대각선 1 번 · 아래 1 번 · 오른쪽 1 번  3! / (1! 1! 1!)  = 6
p = 2  대각선 2 번 · 아래 0 번 · 오른쪽 0 번  2! / (2! 0! 0!)  = 1
합                                                             = 13
└ 점화식으로 센 P(2,2) 와 같다
```

점화식으로 센 값과 대조하고 과제 규모를 넣습니다.

<!--proof:math-path-count-->

```text
i = j  경로 수(점화식)  sum_p (i+j-p)! / (p! (i-p)! (j-p)!)
    1                3                                    3
    2               13                                   13
    3               63                                   63
    4              321                                  321
    5            1,683                                1,683
    6            8,989                                8,989

과제 규모 i = j = 1,000 을 두 식에 넣으면
  경로 수     764 자리 수
  (i+1)(j+1)    1,002,001
```

여섯 규모에서 점화식으로 센 값이 닫힌 형태와 정확히 같습니다. 마지막 두 줄이 과제 규모예요 — 같은 답 하나를 얻는 데
뼈대를 전부 보면 764 자리 수이고, DP 테이블로는 칸 1,002,001 개입니다.

하한 하나가 더 나옵니다. 경로 위의 어느 칸 `(i, j)` 에서든 거기까지의 비용이 `|i − j|` 이상이므로, **비용이 문턱 `k`
이하인 경로는 대각선에서 `k` 칸을 벗어날 수 없습니다.**

```text
비용이 문턱 k 이하인 경로는 어디에 있는가
  칸 (i, j) 까지의 비용   |i - j| 이상이다   위에서 유도한 하한이다
  경로 전체의 비용         그 이상이다        앞부분의 비용이 전체를 넘지 못하니까
  전체가 k 이하라면        |i - j| <= k      대각선에서 k 칸 안쪽 칸만 지난다
  └ 답이 작다는 것을 미리 알면 DP 테이블의 이 띠만 채워도 된다는 뜻이고, 그것이 경쟁 설계가 쓰는 성질이다
```

### 불변식 — `dp[i][j]` 는 `s` 의 앞 `i` 글자를 `t` 의 앞 `j` 글자로 바꾸는 최소 편집 횟수다

파트 1 에서 코드가 동작하는 것을 열일곱 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지, 언제나 맞는다는 뜻은
아니에요. 무엇이 **매 칸 참으로 남는지**를 문장으로 세우고, 그것이 실제로 유지되는지 확인해 봅시다.

> 안쪽 반복이 칸 `(i, j)` 를 정한 직후, `dp[i][j]` 는 `s` 의 앞 `i` 글자를 `t` 의 앞 `j` 글자로 바꾸는 데 필요한
> 최소 편집 횟수와 같습니다.

```text
  무엇이   dp[i][j] 한 칸
  언제     그 칸을 정한 직후다. 그 전에는 fill(0) 이 깔아 둔 0 이 들어 있다
  왜       칸을 정하는 순간 읽는 이웃이 이미 참이어야 하기 때문이다
```

「언제」를 빠뜨리면 안 됩니다. DP 테이블을 깐 직후에는 안쪽 칸이 전부 0 인데 그 0 은 답이 아니라 아직 안 정한 자리이고,
그 시점에 참인 것은 테두리뿐이에요.

**출발점부터 봅시다.** 반복에 들어가기 전 첫 열과 첫 줄은 한쪽이 빈 문자열인 자리입니다. 빈 문자열로 만들려면 남은 글자를
전부 지우는 수밖에 없고, 빈 문자열에서 만들려면 전부 넣는 수밖에 없어요. 그 뒤로 칸 하나가 두 갈래 중 하나로 정해지고,
각 갈래가 문장을 지키는 근거는 이렇습니다.

| 자리 | 하는 일 | 문장이 유지되는 근거 |
| --- | --- | --- |
| 첫 열 `dp[i][0]` | `i` 를 적는다 | `t` 가 비어 있어 `s` 의 `i` 글자를 지우는 것 말고 할 일이 없다 |
| 첫 줄 `dp[0][j]` | `j` 를 적는다 | `s` 가 비어 있어 `t` 의 `j` 글자를 넣는 것 말고 할 일이 없다 |
| 두 글자가 같은 칸 | 왼쪽 위를 그대로 | 그 글자를 안 건드리는 것이 최선이고, 남는 것이 왼쪽 위 칸이다 |
| 두 글자가 다른 칸 | 세 후보 중 최솟값에 1 | 마지막 편집이 셋 중 하나이고, 그 셋이 후보의 전부다 |
| 종료 | `(n, m)` 을 정한다 | 두 문자열 전체를 놓고 본 답이다 |

가운데 두 줄이 이 논증의 핵심입니다. 각각이 읽는 이웃은 **앞 줄이거나 같은 줄의 왼쪽**이라, 두 반복이 위에서 아래로
그리고 왼쪽에서 오른쪽으로 나아가는 동안 이미 정해져 있어요.

| 읽는 이웃 | 자리 | 정해진 때 |
| --- | --- | --- |
| `dp[i-1][j-1]` | 앞 줄의 왼쪽 열 | 앞 줄을 채울 때 |
| `dp[i-1][j]` | 앞 줄의 같은 열 | 앞 줄을 채울 때 |
| `dp[i][j-1]` | 같은 줄의 바로 앞 칸 | 이 줄에서 방금 |

모든 칸을 정의대로 직접 구한 값과 맞대 보면 이렇습니다. 정의대로 구하는 쪽은 편집을 한 번씩 해 보며 두 문자열에서
동시에 넓혀 가다가 양쪽이 처음 만나는 곳을 찾아요.

<!--proof:invariant-cells-->

| 줄 | DP 테이블의 값 | 정의대로 직접 구한 값 | 어긋난 칸 |
| --- | --- | --- | ---: |
| i=0 | [0 1 2 3] | [0 1 2 3] | 0 |
| i=1 | [1 1 2 3] | [1 1 2 3] | 0 |
| i=2 | [2 2 1 2] | [2 2 1 2] | 0 |
| i=3 | [3 2 2 2] | [3 2 2 2] | 0 |
| i=4 | [4 3 3 2] | [4 3 3 2] | 0 |
| i=5 | [5 4 4 3] | [5 4 4 3] | 0 |

정의대로 직접 구한 값과 DP 테이블의 값을 24 칸에서 대조했고, 어긋난 칸은 0 개입니다.

<!--/proof-->

경계에 있는 입력들도 확인하고 갑시다. 칸을 어느 갈래로 정했는지 세고, 반환값을 정의대로 센 값과 맞댔습니다.

<!--proof:invariant-edges-->

| 입력 | 줄 × 칸 | 같은 글자 칸 | 다른 글자 칸 | 반환 | 정의대로 센 값 |
| --- | --- | ---: | ---: | ---: | ---: |
| "" 과 "" | 1 × 1 | 0 | 0 | 0 | 0 |
| "" 과 "abc" | 1 × 4 | 0 | 0 | 3 | 3 |
| "abc" 와 "" | 4 × 1 | 0 | 0 | 3 | 3 |
| "a" 와 "a" | 2 × 2 | 1 | 0 | 0 | 0 |
| "a" 와 "b" | 2 × 2 | 0 | 1 | 1 | 1 |
| "abc" 와 "abc" | 4 × 4 | 3 | 6 | 0 | 0 |
| "abc" 와 "def" | 4 × 4 | 0 | 9 | 3 | 3 |

7 입력 가운데 7 입력에서 반환값이 정의대로 센 값과 같습니다.

<!--/proof-->

한쪽이라도 빈 문자열이면 테두리만 있고 칸을 하나도 정하지 않아 테두리의 값이 그대로 답입니다. 한 글자씩이면 칸 하나를
정하고, 같으면 왼쪽 위 `dp[0][0] = 0` 을 그대로, 다르면 세 후보 `0` · `1` · `1` 중 가장 작은 0 에 1 을 더해 1 이에요.
두 문자열이 같으면 대각선 칸이 전부 같은 글자 칸이라 0 이 끝까지 이어지고, 공통 글자가 없으면 모든 칸이 다른 글자
칸이라 긴 쪽의 길이가 답이 됩니다. 모두 특별 분기 없이 같은 전이식으로 처리돼요.

**이제 깨뜨려 봅시다.** 출발점을 지키던 줄은 **첫 열을 채우는 줄**이에요. 「테두리는 어차피 빈 문자열 자리이니 전부
0 이면 되지 않나」라는 생각으로 그 한 줄만 바꿔 봅니다.

```ts
for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = 0; // i 대신 0 을 적었다
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-first-column-->

```text
입력                        정본이 낸 답  첫 열을 0 으로 둔 답  판정
전개 입력 "horse" 와 "ros"             3                     2  틀리다
"abc" 와 ""                            3                     0  틀리다
"" 과 "abc"                            3                     3  같다
"kitten" 과 "sitting"                  3                     3  같다
"horse" 와 "house"                     1                     1  같다

전개 입력의 마지막 줄  정본 [5 4 4 3]  변이 [0 1 2 2]
```

문장이 깨지는 자리가 보입니다. `dp[3][0] = 0` 은 「`"hor"` 를 빈 문자열로 만드는 데 편집이 필요 없다」는 뜻인데,
지우기도 편집 한 번이라 그 자리의 참값은 3 이에요. 첫 열을 0 으로 두면 `s` 의 앞부분을 비용 없이 버릴 수 있게 되어,
「`t` 가 `s` 의 어느 뒷부분과 얼마나 가까운가」를 재는 다른 과제가 됩니다. 전개 입력의 마지막 줄에서 변이는
`"horse"` 의 앞 두 글자를 공짜로 버리고 `"rse"` 만 고친 값을 냅니다. 다섯 입력 중 셋에서 답이 같은 것도 이 실수의
성격입니다 — `s` 의 앞부분을 버리는 것이 이득이 아닌 입력에서는 티가 안 나요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — 테두리를 적는 것, 칸을 하나씩 정하는 것, 오른쪽 아래를 읽는 것이에요. 전개의
걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perf-count-->

```text
무리         걸음    문자 비교  값 비교  기본 연산
테두리 적기  T1              0        0          0
칸 채우기    T2~T16         15       24         39
읽기         T17             0        0          0
합계                        15       24         39

└ 채운 칸이 5 x 3 = 15 개이고 그중 두 글자가 같은 칸이 3 개다
└ 두 글자가 다른 칸 12 개에서만 세 후보를 비교하느라 값 비교가 두 번씩 든다. 12 x 2 = 24
```

T1 은 테두리에 값을 적기만 하고 T17 은 값을 읽기만 하는 자리라 문자 비교도 값 비교도 없습니다. T2~T16 의 칸마다 문자
비교 하나가 들고, 두 글자가 다른 칸에서만 `Math.min` 이 세 후보를 비교하느라 값 비교가 두 번 더 들어요. 셋을 다 더해야
총식이 됩니다.

```text
총식 = 테두리 적기 + 칸 채우기 + 읽기

  테두리 적기   칸 n + m + 1 개에 값을 적는다
  칸 채우기     문자 비교 nm 번과 값 비교 2 x (nm - 같은 칸 수) 번
  읽기          0
  기본 연산     nm + 2 x (nm - 같은 칸 수)
  추가 칸       (n+1)(m+1)
```

전개 입력과 과제 규모를 이 총식에 넣고 실측과 맞대면 이렇습니다.

<!--proof:perf-total-->

```text
n = 5 · m = 3 · 같은 칸 3  15 + 2 x (15 - 3) = 39                 위 표의 합계와 같다
n = m = 1,000 · 같은 칸 0  1,000,000 + 2 x 1,000,000 = 3,000,000  공통 글자가 없는 두 문자열의 실측과 같다
```

**연산 수가 입력의 내용에 조금 달려 있습니다.** 두 글자가 같은 칸에서는 왼쪽 위 하나를 읽고 끝나지만, 다른 칸에서는
후보 셋을 비교하느라 값 비교가 두 번 더 들어요.

```text
같은 칸 수가 정하는 범위
  같은 칸이 nm 개   두 문자열이 한 글자를 되풀이한다   기본 연산 nm
  같은 칸이 0 개    공통 글자가 하나도 없다            기본 연산 3nm
  └ 같은 칸 수만 이 범위를 정한다. 3 배 안쪽이라 차수는 안 바뀐다
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (한쪽이 빈 문자열이다) | `O(nm)` | `Θ(n + m)` — 안쪽 반복이 한 번도 실행되지 않는다 |
| **평균적인 경우** (입력 분포를 가정하지 않는다) | `O(nm)` | `Θ(nm)` |
| **최악의 경우** (두 길이가 규모의 끝이고 공통 글자가 없다) | `O(nm)` | `Θ(nm)` — 실제로 도달한다 |

평균과 최악이 같은 차수인 것이 이 절차의 성질입니다. 기본 연산이 `nm` 과 `3nm` 사이를 벗어나지 못하니, 글자를 어떻게
바꿔도 차수가 안 바뀌어요. 최선의 줄이 `Θ(n + m)` 인 것은 칸 채우기가 0 이어도 테두리를 적는 일이 남기 때문입니다.

```text
상한과 타이트한 값을 가르는 자리
  기본 연산이 그보다 크지 않다는 것만 말한다           상한이다          O(nm)
  위아래로 같은 차수라 실제로 그만큼 든다고도 말한다   타이트한 값이다   Θ(nm)
  └ 칸마다 문자 비교를 적어도 하나는 하므로 아래로도 nm 이다. 그래서 Θ 로 적을 수 있다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 절차의 특징이에요 — 정렬도, 위치
목록도, 해시도 만들지 않습니다.

```text
총식 = Θ(nm) 시간 + Θ(nm) 추가 메모리

  시간     테두리 n + m + 1 칸 · 문자 비교 nm · 값 비교 2 x (nm - 같은 칸 수) · DP 테이블을 0 으로 까는 일 (n+1)(m+1)
  메모리   칸 (n+1)(m+1) 개
```

**보장의 종류는 전부 최악 보장입니다.** 해시도, 무작위성도, 분할 상환도 쓰지 않아요 — 어떤 입력을 넣어도 기본 연산이
`3nm` 이하입니다.

```text
기댓값이 끼어들 자리가 없다
  칸을 찾는 방법   첨자 둘로 바로 간다          해시 충돌이라는 개념이 없다
  칸 수            글자를 안 보고 정해진다      분포를 가정할 필요가 없다
  칸 하나의 비용   많아야 문자 비교 1 과 값 2   평균이 아니라 상수다
  └ 최악에서 잰 값과 아무 입력에서나 잰 값이 같은 차수다
```

#### 최악을 만드는 입력

기본 연산을 최대로 만들려면 둘이 함께 필요합니다 — **두 길이를 규모의 끝으로 두는 것**과 **두 글자가 같은 칸을 하나도
안 만드는 것**이에요. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->

```text
입력의 모양 (n = m = 1,000)     두 글자가 같은 칸  문자 비교    값 비교  기본 연산     답
두 문자열이 같다                        1,000,000  1,000,000          0  1,000,000      0
글자가 둘씩 번갈아 나온다                 500,000  1,000,000  1,000,000  2,000,000      2
알파벳 26 을 차례로 되풀이한다             38,467  1,000,000  1,923,066  2,923,066      2
공통 글자가 하나도 없다                         0  1,000,000  2,000,000  3,000,000  1,000

└ 문자 비교는 네 줄 다 1,000,000 으로 같고, 값 비교만 0 에서 2,000,000 까지 갈린다
```

**「비슷한 문자열일수록 오래 걸린다」는 이 결과에서 거꾸로입니다.** 첫 줄은 모든 칸이 같은 갈래라 값 비교가 0 이고,
마지막 줄은 모든 칸이 다른 갈래라 값 비교가 가장 많아요. 겹치는 글자가 많을수록 비교할 후보가 줄어 오히려 적게 듭니다.
축마다 최악을 모으면 이렇습니다.

<!--proof:worst-axes-->

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | ---: |
| 기본 연산 | n = m = 1,000 · 공통 글자 없음 | 3,000,000 |
| 추가 칸 | n = m = 1,000 · 글자는 무엇이든 | 1,002,001 |
| 답의 크기 | 공통 글자가 없는 길이 1,000 짜리 둘 | 1,000 |

공통 글자가 없는 길이 1,000 짜리 두 문자열에서 기본 연산과 답이 함께 가장 커지고, 답 1,000 은 긴 쪽의 길이 1,000 과 같습니다.

<!--/proof-->

**답 크기의 최악은 긴 쪽의 길이입니다.** 어떤 두 문자열이든 `s` 를 전부 지우고 `t` 를 전부 넣으면 `n + m` 번에 끝나지만,
앞에서부터 `min(n, m)` 자리는 교체 한 번씩으로 처리할 수 있어 `max(n, m)` 을 넘지 않아요. 추가 칸은 글자를 아예 안 보고
두 길이로만 정해집니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 두 문자열의 **마지막 편집 하나만** 정하면 과제가 한 칸 작아지고, 남는
것이 접두어 한 쌍이라 상태가 `(n+1)(m+1)` 개로 닫히며, 테두리에 지우기 · 넣기 비용을 적고 나머지 칸을 이웃 셋에서
채우면 오른쪽 아래 칸이 답입니다.

```text
테두리에 i · j 를 적는다 → 같으면 왼쪽 위 그대로 · 다르면 세 후보 중 가장 작은 값에 1 → dp[n][m] 을 읽는다
       └ 한쪽이 비면 전부 지우거나 넣는다      └ 왼쪽 위는 교체, 위는 삭제, 왼쪽은 삽입이다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T11~T13 은 `s` 의 `'s'` 를 처리한 줄이었어요. 윗 줄과 나란히 놓으면 이렇습니다.

<!--proof:selfcheck-row-->

```text
걸음     줄   s 의 글자  다 채운 줄
T8~T10   i=3  'r'        [3 2 2 2]
T11~T13  i=4  's'        [4 3 3 2]
```

같은 줄에서 `j=1` · `j=2` 칸은 윗 줄보다 값이 커졌는데 `j=3` 칸은 그대로입니다. 한 줄 안에서 이렇게 갈리는 이유는
무엇일까요?

<!--check:whyRowMixes-->
`s` 의 글자 `'s'` 가 `t` 의 세 글자 중 마지막 것과만 같기 때문입니다. `j=3` 은 `t[2] = 's'` 라 두 글자가 같은 갈래이고,
왼쪽 위를 편집 없이 그대로 받아요. `j=1` 과 `j=2` 는 `'r'` · `'o'` 와 비교하므로 다른 갈래이고, 세 후보 중 가장 작은 값에
1 을 더합니다.

<!--proof:selfcheck-mix-->

```text
j=1  's' 와 'r'  다르다  min(3, 2, 4) + 1 = 3    윗 줄 2 → 3
j=2  's' 와 'o'  다르다  min(2, 2, 3) + 1 = 3    윗 줄 2 → 3
j=3  's' 와 's'  같다    dp[3][2] = 2 를 그대로  윗 줄 2 → 2
```

한 줄 안에서도 칸마다 갈래가 다릅니다. 줄 단위로 값이 커지는 것이 아니라, 칸마다 두 글자를 비교한 결과가 정해요.
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요.

```text
1 → 짚고 가기 — 위 칸은 삭제이고 왼쪽 칸은 삽입이다
2 → 수식 정의와 유도
3 → 경쟁 설계와의 대조
```

- DP 테이블을 다 채우고 나면 마지막 칸만 쓰니 줄 둘만 들고도 답을 낼 수 있습니다. 그때 왼쪽 위 값을 어떻게 챙겨야 하는지
  손으로 적어 보세요. 3단계에서 편집 목록을 거슬러 찾는 일이 그때 왜 안 되는지도 함께 생각해 보세요.
- 세 편집의 비용이 `1` · `1` · `1` 이 아니라 교체 `2` · 삭제 `3` · 삽입 `1` 이면 DP 테이블의 어느 칸이 바뀔까요? 전개의 T2
  에서 교체가 혼자 가장 작았는데, 이 비용에서도 그 칸에서 교체가 가장 작은지 따져 보고, 첫 줄과 첫 열이 어떻게
  달라지는지도 적어 보세요.
- 두 문자열의 길이가 각각 100,000 이면 이 DP 테이블을 못 깝니다. 띠 계산이 문턱 `k` 로 한 바퀴 채울 때 몇 칸을
  채우는지 `k` 와 두 길이로 식을 세우고, 문턱을 배로 늘리는 바퀴까지 더하면 답이 얼마 이하일 때 1 초 안에 끝나는지 따져
  보세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Edit Distance

풀 파일: [`editDistance.ts`](./editDistance.ts) · 테스트: [`editDistance.test.ts`](./editDistance.test.ts) · 실행: `bun test src/algorithms/array/editDistance/editDistance.test.ts`

#### 한 줄 요약

> 두 문자열 `s`와 `t`를 받아, `s`를 `t`로 변환하는 데 필요한 **최소 편집 횟수**를 반환한다.

#### 스토리

철자 교정 엔진을 만드는 개발자 하린은 사용자가 입력한 단어가 사전에 없을 때 가장 가까운 단어를 찾아야 한다.

"가까운"의 기준은 변환 비용이다. 문자 하나를 삽입하거나, 문자 하나를 삭제하거나, 문자 하나를 다른 문자로 교체할 수 있다. 세 연산 각각의 비용은 동일하다.

두 단어 사이의 거리가 작을수록 더 비슷한 단어다. 하린은 이 최소 변환 비용을 계산하는 함수를 작성해야 한다.

#### 함수 인터페이스

```ts
export function editDistance(s: string, t: string): number;
```

- `s` — 변환 대상 문자열 (원본).
- `t` — 목표 문자열.
- 반환 — `s`를 `t`로 변환하는 데 필요한 최소 편집 횟수.

#### 제약 조건

- $0 \leq |s| \leq 1{,}000$
- $0 \leq |t| \leq 1{,}000$
- 문자열의 문자는 ASCII 범위로 가정한다
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

허용되는 편집 연산은 세 가지이며 각각의 비용은 $1$이다.

- **삽입**: `s`의 임의 위치에 문자 하나를 끼워 넣는다.
- **삭제**: `s`의 임의 위치에서 문자 하나를 제거한다.
- **교체**: `s`의 임의 위치에 있는 문자 하나를 다른 문자로 바꾼다.

`s`와 `t`가 같으면 비용은 $0$이다. 한쪽이 빈 문자열이면 다른 쪽의 길이가 곧 비용이다. 연산 순서는 비용에 영향을 주지 않으며, 최소 비용만 구하면 된다(변환 경로 자체는 반환하지 않는다).

#### 예시

```ts
editDistance("kitten", "sitting"); // 3  — k→s, e→i, 끝에 g 삽입
editDistance("flaw", "lawn");      // 2  — f 삭제, 끝에 n 삽입
editDistance("horse", "ros");      // 3  — h→r, r 삭제, e 삭제

editDistance("same", "same");      // 0  — 동일 문자열, 변환 불필요
editDistance("", "abc");           // 3  — 문자 3개 삽입
editDistance("abc", "");           // 3  — 문자 3개 삭제
editDistance("", "");              // 0  — 둘 다 빈 문자열

editDistance("a", "b");            // 1  — 문자 하나 교체
```
