# editDistance — 세 가지 편집이 표의 이웃 세 칸이 되는 이유

## 파트 1 — 세 연산에서 표 한 장까지

편집 한 번이 무엇을 하는지부터 보고, 그 한 번을 표의 이웃 칸 하나로 바꾸는 경로를 따라
갑니다. 마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

문자열 `s` 를 문자열 `t` 로 바꾸는 데 필요한 **최소 편집 횟수**를 돌려주는 문제예요. 쓸 수
있는 편집은 셋이고 비용이 각각 1 입니다 — 글자 하나를 넣는 삽입, 글자 하나를 지우는 삭제,
글자 하나를 다른 글자로 바꾸는 교체입니다.

```text
"horse" 를 "ros" 로 바꾸기

  horse   h 를 r 로 교체    →  rorse
  rorse   r 을 삭제         →  rose
  rose    e 를 삭제         →  ros

  편집 세 번. 두 번으로는 안 되므로 이 두 문자열의 답은 3 이다
```

가장 먼저 떠오르는 방법은 편집을 한 번씩 해 보는 것입니다. `s` 에 편집 한 번을 적용한
결과를 전부 만들어 그중에 `t` 가 있는지 보고, 없으면 그 결과들에 다시 한 번씩 적용해요.

```text
편집 한 번으로 갈 수 있는 문자열 수

  교체    글자마다 다른 글자로       길이 x (글자 종류 - 1) 가지
  삭제    글자마다 하나씩 지우기     길이 가지
  삽입    자리마다 글자 하나 넣기    (길이 + 1) x 글자 종류 가지
  └ 길이 1,000 에 글자 종류 26 이면 한 번에 52,026 가지이고, 답이 1,000 이면 그것이 1,000 번 겹친다
```

그러니 편집을 실제로 해 보는 대신 **마지막 한 번의 편집이 무엇이었는지**만 봅시다. 두
문자열의 마지막 글자를 견주면 갈래가 넷이고, 어느 갈래든 남는 것은 **두 문자열의 앞부분,
곧 접두어 한 쌍**입니다.

```text
마지막 한 번의 편집을 정하면

  같다     s = ...e 와 t = ...e   편집 없이 양쪽에서 하나씩 뗀다   비용 + 0
  교체     s = ...h 와 t = ...r   h 를 r 로 바꾸고 하나씩 뗀다     비용 + 1
  삭제     s = ...e 를 버린다     s 에서만 하나 뗀다               비용 + 1
  삽입     t = ...s 를 넣는다     t 에서만 하나 뗀다               비용 + 1
  └ 넷 다 남는 것이 s 의 앞부분과 t 의 앞부분이다
```

그래서 표에 담을 것이 **접두어 쌍마다의 최소 편집 횟수**입니다. `s` 의 앞 `i` 글자를 `t` 의 앞 `j`
글자로 바꾸는 최소 편집 횟수를 `dp[i][j]` 라 적으면, 위 네 갈래가 그대로 이웃 칸을 읽는
규칙이 됩니다. `s` 의 길이를 `n`, `t` 의 길이를 `m` 이라 적고, 표의 `∅` 는 한 글자도 안 본
자리, 곧 빈 문자열이에요.

| | `j=0` ∅ | `j=1` r | `j=2` o | `j=3` s |
| --- | --- | --- | --- | --- |
| `i=0` ∅ | 0 | 1 | 2 | 3 |
| `i=1` h | 1 | 1 | 2 | 3 |
| `i=2` o | 2 | 2 | 1 | 2 |
| `i=3` r | 3 | 2 | 2 | 2 |
| `i=4` s | 4 | 3 | 3 | 2 |
| `i=5` e | 5 | 4 | 4 | 3 |

**첫 줄과 첫 열은 계산해서 얻은 값이 아닙니다.** 한쪽이 빈 문자열이면 할 수 있는 일이 하나뿐
이에요 — `t` 가 비어 있으면 `s` 의 글자를 전부 지워야 하니 비용이 `i` 이고, `s` 가 비어
있으면 `t` 의 글자를 전부 넣어야 하니 비용이 `j` 입니다. 나머지 칸은 대각선·위·왼쪽 세
이웃만 읽어요.

```text
칸 하나가 읽는 자리

  dp[i-1][j-1]  dp[i-1][j]      두 글자가 같으면   대각선 값 그대로
  dp[i][j-1]    dp[i][j]        다르면             셋 중 가장 작은 값에 1
  └ 세 이웃이 전부 이 칸의 위나 왼쪽에 있다. 왼쪽 위 구석에서 시작해 줄 단위로 채우면 읽을 때 이미 값이 있다
```

칸이 `(n+1)(m+1)` 개이고 칸 하나에 드는 일이 문자 비교 한 번과 값 비교 두 번 이하라, 시간이
`O(nm)` 이고 표에 쓰는 칸도 `O(nm)` 입니다. 편집을 실제로 해 보는 방법이 답의 크기를 지수로
올리던 것과 견주면, `n = m = 1,000` 에서 100 만 칸 언저리예요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **삽입과 삭제가 뒤의 자리를 한 칸씩 옮긴다는 것.** 앞에서 글자 하나를 지우면 그 뒤
  글자들의 자리 번호가 전부 하나씩 줄어듭니다. 이 사실 하나가 「자리마다 견주기」를 성립하지
  않게 만드는 자리예요.
- **첨자 둘로 2 차원 배열의 칸을 지정하는 일.** 표가 아무리 커도 칸 하나를 읽는 값이 같다는
  것까지 알고 있어야 합니다.
- **작은 문제의 답을 모아 큰 문제의 답을 만드는 방식.** 이 글에서 작은 문제는 두 문자열을
  앞에서 얼마씩만 잘라 본 것이고, 큰 문제는 그 자른 길이를 하나씩 늘린 것입니다.
- **문자열 첨자와 개수의 어긋남.** `s` 의 `i` 번째 글자는 `s[i−1]` 이라, 「몇 글자 보았는가」를
  세는 수와 「몇 번 자리인가」를 가리키는 수가 늘 1 만큼 차이 납니다.

이 글이 다루는 것은 **삽입·삭제·교체 세 연산의 비용이 모두 1** 인 경우입니다. 같은 격자 표를
쓰되 두 문자열이 공유하는 가장 긴 부분 수열의 길이를 재는 문제는
[`longestCommonSubsequence`](../longestCommonSubsequence/longestCommonSubsequence-guide.md)
가 다루고, 문제 지문과 제약은
[`editDistance-problem.md`](./editDistance-problem.md) 에 있어요.

```text
두 문자열을 같게 만드는 최소 편집 횟수   ← 이 글이 다루는 것
두 문자열의 공통 부분 수열 길이          ← 다른 글이 다루는 것
└ 표의 모양은 같고 칸에 적는 값의 뜻이 다르다
```

### 아이디어 상세 — 세 연산을 이웃 세 칸으로 바꾸는 방법을 떠올리는 과정

무엇을 만들어야 하는지부터 못박겠습니다.

```ts
function editDistance(s: string, t: string): number;
```

- 입력: 두 문자열 `s` 와 `t`. 글자는 ASCII 범위이고 빈 문자열일 수 있습니다.
- 출력: `s` 를 `t` 로 바꾸는 데 필요한 **최소 편집 횟수**. 편집 목록 자체가 아니라 횟수만
  돌려줍니다.
- 제약: `0 ≤ n ≤ 1,000`, `0 ≤ m ≤ 1,000`. 시간 1 초, 메모리 256 MB.

뒤에서 계속 나올 기호는 여덟이에요. 여기 적은 뜻이 마지막 절까지 그대로 갑니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `s` | 바꿀 문자열 | 길이가 `n` 이다 |
| `t` | 목표 문자열 | 길이가 `m` 이다 |
| `n` | `s` 의 길이 | `0 ≤ n ≤ 1,000` |
| `m` | `t` 의 길이 | `0 ≤ m ≤ 1,000` |
| `i` | `s` 를 앞에서부터 몇 글자 보았는가 | `0 ≤ i ≤ n` |
| `j` | `t` 를 앞에서부터 몇 글자 보았는가 | `0 ≤ j ≤ m` |
| `dp[i][j]` | `s` 의 앞 `i` 글자를 `t` 의 앞 `j` 글자로 바꾸는 최소 편집 횟수 | 표의 칸 하나 |
| `k` | 대각선에서 몇 칸까지 벗어나는 것을 허용하는가 | 경쟁 설계가 쓰는 문턱 |

`i` 와 `j` 를 자리 번호로 읽으면 뒤가 전부 하나씩 어긋납니다. 둘은 **몇 글자까지 보았는가**를
세는 수이고, 그래서 칸 `(i, j)` 에서 견주는 글자가 `s[i−1]` 과 `t[j−1]` 이에요.

가장 단순한 방법부터 세워 봅시다. 문제가 「최소 편집 횟수」를 물으니, 편집을 한 번 한 결과를
전부 만들고 그중에 `t` 가 있는지 보는 것이 지문을 그대로 옮긴 방법이에요. 없으면 그 결과들에
다시 한 번씩 편집합니다.

```ts
let frontier = new Set([s]);
for (let depth = 1; ; depth++) {
  const next = new Set<string>();
  for (const x of frontier) {
    for (const y of oneEditAway(x)) {   // 한 번 편집한 결과 전부
      if (y === t) return depth;
      next.add(y);
    }
  }
  frontier = next;
}
```

이 방법이 하는 일의 양은 **만나는 문자열의 개수**입니다. `"horse"` 를 `"ros"` 로 바꾸는 데
답이 3 이니 편집 횟수 3 까지 만들어 봐야 해요.

```text
편집 횟수  새로 만난 문자열 수    누적
        1                   50      50
        2                1,040   1,090
        3               12,688  13,778

└ 3 번째에 "ros" 가 나온다. 답이 3 이라는 뜻이다

제약 규모 |s| = |t| = 1,000 · 글자 종류 26 이면
  한 번 편집해 만들 수 있는 문자열 수         52,026
  답이 1,000 일 때 확인할 문자열 수 상한  4,717 자리
  └ 편집 한 번마다 만들 수 있는 문자열이 그만큼이라, 답이 곧 지수가 된다
```

4,717 자리입니다. 제약이 1,000 인데 이 방법으로는 답이 커질수록 확인할 문자열이 지수로
늘어나요. 그러면 이 안에서 무엇이 되풀이되는지 봅시다.

편집 목록의 **순서를 바꿔도 비용이 같다**는 것이 지문에 있습니다. 그러면 편집을 아무 자리에서나
하는 대신 **뒤에서부터 하나씩 정해도** 손해가 없어요. 마지막 한 번을 정하면 남는 것이 접두어
한 쌍이니, 그것을 그대로 재귀로 옮기면 이렇게 됩니다.

```ts
function f(i: number, j: number): number {
  if (i === 0) return j;   // s 가 비었다 — t 의 남은 j 글자를 넣는다
  if (j === 0) return i;   // t 가 비었다 — s 의 남은 i 글자를 지운다
  if (s[i - 1] === t[j - 1]) return f(i - 1, j - 1);
  return 1 + Math.min(f(i - 1, j - 1), f(i - 1, j), f(i, j - 1));
}
```

이제 **길이는 같고 글자만 다른 세 입력**에 두 방식을 나란히 걸어 봅시다. 왼쪽은 문자열을
통째로 들고 한 번씩 편집해 찾아가는 방식이고, 오른쪽은 접두어 쌍마다 칸 하나를 두는
방식이에요.

<!--proof:costTwoWays-->

```text
입력              두 길이  답  만난 문자열 수  표에서 채운 칸
"horse" 와 "hos"  5 x 3     2           1,090              24
"horse" 와 "ros"  5 x 3     3          13,778              24
"horse" 와 "xor"  5 x 3     3          26,019              24

└ 답이 1 커지는 것만으로 왼쪽 열이 12.6 배가 되고, 글자 종류가 늘어도 함께 커진다
└ 오른쪽 열은 답도 글자도 안 보고 두 길이의 곱으로 정해진다
```

같은 `5 x 3` 인데 왼쪽 열이 1,090 과 26,019 로 갈립니다. 여기서 관찰할 것은 하나예요 —
**오른쪽 열은 답의 크기도 글자 종류도 아예 안 보고 두 길이의 곱으로 정해집니다.**

| 방식 | 하는 일의 양 | 무엇을 따라가는가 |
| --- | --- | --- |
| 문자열을 통째로 들고 편집하기 | 답의 크기가 지수가 된다 | 답과 글자 종류 수를 따라간다 |
| 접두어 쌍마다 칸 하나 | 두 길이의 곱 | 답도 글자도 안 본다 |

상태를 무엇으로 잡을지 정하기 전에 더 만만한 후보를 하나 처리하고 갑시다. 「앞에서부터 같은
자리끼리 견주어 다른 자리를 세고, 길이 차이만큼 더한다」가 그 후보예요.

<!--proof:costSlot-->

```text
입력                        정본이 낸 답  자리마다 견주기  판정
전개 입력 "horse" 와 "ros"             3                4  틀리다
"abcd" 와 "bcda"                       2                4  틀리다
"flaw" 와 "lawn"                       2                4  틀리다
"ab" 와 "ba"                           2                2  같다
"horse" 와 "house"                     1                1  같다

└ 앞에서 글자 하나를 지우거나 넣으면 뒤가 통째로 한 칸씩 밀리는데, 자리마다 견주는 방식은 그 자리를 전부 다른 글자로 센다
```

이 후보가 어긋나는 이유는 하나입니다. 삽입과 삭제는 **뒤의 글자를 통째로 한 칸씩 옮기는**
연산인데, 자리마다 견주는 방식은 자리 번호를 고정해 두고 봐요.

```text
"abcd" 와 "bcda" 에서 두 방식이 갈리는 자리
  자리마다 견준다   a-b  b-c  c-d  d-a   네 자리가 다 다르다        4
  앞을 하나 지운다  "bcd" 와 "bcda"       뒤가 한 칸씩 당겨진다
  끝에 하나 넣는다  "bcda" 와 "bcda"      같아진다                   2
  └ 지우기 한 번과 넣기 한 번으로 끝나는 자리를, 자리마다 견주면 네 번으로 센다
```

그러니 **어느 자리를 고쳤는지가 아니라 양쪽을 어디까지 보았는지**를 들고 가야 합니다. 여기서
진짜 개념이 나와요. 두 문자열을 각각 앞에서부터 몇 글자 보았는지, 그 **접두어 쌍 `(i, j)`**
하나가 상태입니다.

```text
접두어 쌍 (i, j) 가 정하는 것

  i    s 를 앞에서부터 i 글자 보았다   i 는 0 부터 n 까지   n+1 가지
  j    t 를 앞에서부터 j 글자 보았다   j 는 0 부터 m 까지   m+1 가지
  상태 수                              (n+1)(m+1) 가지
  └ 어떤 편집을 어떤 순서로 했는지는 상태에 안 들어간다. 앞으로 할 수 있는 일이 같기 때문이다
```

이 상태가 한 걸음에 얼마나 움직이는지도 정해집니다. 네 갈래 어느 쪽이든 `i` 와 `j` 의 합이
적어도 1 줄어들어요.

```text
상태의 이동 범위
  같은 갈래   i 가 1 줄고 j 도 1 준다   대각선으로 한 칸, 비용 0
  교체        i 가 1 줄고 j 도 1 준다   대각선으로 한 칸, 비용 1
  삭제        i 만 1 준다               위로 한 칸, 비용 1
  삽입        j 만 1 준다               왼쪽으로 한 칸, 비용 1
  걸음 수     i + j 가 매번 최소 1 준다   많아야 n + m 걸음
```

**규칙이 그대로 적용되는 자리와 불안한 자리를 갈라 값으로 확인합시다.** 편한 자리는 윗줄이 이미
채워져 있을 때입니다. 읽어야 할 이웃 셋이 전부 값을 갖고 있어요.

```text
이미 채운 줄이 있는 자리 — 칸 (3, 2)
  대각선 dp[2][1] = 2   앞 줄에서 채웠다
  위     dp[2][2] = 1   앞 줄에서 채웠다
  왼쪽   dp[3][1] = 2   같은 줄에서 방금 채웠다
  s 의 'r' 과 t 의 'o' 가 다르니 셋 중 가장 작은 1 에 1 을 더해 2 다
```

불안한 경우는 **첫 줄과 첫 열**입니다. 위에도 왼쪽에도 읽을 칸이 없는 자리라, 규칙을 그대로
쓸 수 없어 보이는 자리예요.

```text
첫 줄과 첫 열 — 값이 계산이 아니라 정의에서 나온다
  dp[0][0]   빈 문자열을 빈 문자열로   할 일이 없다        0
  dp[3][0]   "hor" 를 빈 문자열로      세 글자를 지운다    3
  dp[0][2]   빈 문자열을 "ro" 로       두 글자를 넣는다    2
  └ 이 아홉 칸을 표 안에 실제로 깔아 두면, 안쪽 칸에는 특별한 분기가 안 생긴다
```

**여기가 이 문제에서 가장 자주 어긋나는 자리입니다.** 첫 줄과 첫 열을 0 으로 두면 「빈
문자열로 만드는 데 비용이 안 든다」는 뜻이 되어 버려요. 그러면 표는 채워지지만 다른 문제의
답이 나옵니다.

```text
첫 열을 어떻게 두느냐
  dp[i][0] = i   s 의 앞 i 글자를 지운다        이 문제의 정의다
  dp[i][0] = 0   s 의 앞부분을 비용 없이 버린다  t 가 s 안에 얼마나 가깝게 있는지를 재는 다른 문제다
  └ 표를 채우는 규칙은 한 글자도 안 바뀌는데 답이 갈린다
```

건너뛰는 칸이 하나도 없다는 것은 두 루프의 범위가 말해 줍니다. `i` 가 `1` 에서 `n` 까지,
`j` 가 `1` 에서 `m` 까지 올라가는 동안 안쪽 칸마다 대입이 **정확히 한 번씩** 일어나요.

```text
두 루프가 끝난 시점
  대입이 일어난 칸  dp[1][1] 부터 dp[n][m] 까지   nm 개, 칸마다 한 번씩
  대입이 없는 칸    첫 줄과 첫 열                 루프 앞에서 이미 값을 적었다
  └ 답이 되는 dp[n][m] 은 두 루프의 마지막 바퀴에서 정해진다
```

이제 상태를 접두어 쌍으로 잡는 것이 정말 필요한지 값으로 확인합니다. 무엇을 들고 갈지를 세
가지로 두고 같은 입력 다섯에 실행했어요.

<!--proof:stateChoice-->

```text
입력                                정답  문자열 통째  자리마다 견주기  접두어 쌍 (i, j)
전개 입력 "horse" 와 "ros"             3            3                4                 3
"abcd" 와 "bcda"                       2            2                4                 2
"flaw" 와 "lawn"                       2            2                4                 2
"ab" 와 "ba"                           2            2                2                 2
"horse" 와 "house"                     1            1                1                 1
어긋난 입력 수                                      0                3                 0
|s| = |t| = 1,000 에서 확인할 개수         4,717 자리            1,000         1,002,001

└ 마지막 줄은 왼쪽부터 문자열 · 자리 · 칸의 개수다
└ 어긋나지 않는 것 중 개수가 감당되는 것이 오른쪽 열이다. 왼쪽 열은 답은 맞지만 확인할 것이 지수로 늘어난다
```

가운데 열은 답이 다섯 중 셋에서 어긋나고, 왼쪽 열은 답은 맞지만 확인할 문자열이 4,717 자리
입니다. 오른쪽 열만 둘 다 만족해요 — 답이 한 번도 안 어긋나고 확인할 칸이 1,002,001 개입니다.

```text
지금까지 세운 것을 절차로 적으면
  1. (n+1) x (m+1) 짜리 표를 깐다
  2. 첫 열 dp[i][0] 에 i 를, 첫 줄 dp[0][j] 에 j 를 적는다
  3. i 를 1 부터 n 까지, j 를 1 부터 m 까지 차례로 보며
  4.   s[i-1] 과 t[j-1] 이 같으면 대각선 값을 그대로 적는다
  5.   다르면 대각선·위·왼쪽 중 가장 작은 값에 1 을 더해 적는다
  6. 오른쪽 아래 칸 dp[n][m] 을 돌려준다
     └ 4,717 자리이던 것이 100 만 칸 언저리가 된다
```

### 수행으로 알아보는 알고리즘 — 테두리부터 오른쪽 아래까지 한 줄씩 채운다

여기서부터는 **실제로 동작하는 코드**를 만듭니다. 입력 하나를 고정해 두고 조각을 하나씩
늘려 가되, 조각마다 그것만 실행한 결과를 보고 넘어가요.

```ts
const s = "horse";
const t = "ros";
// 이 절이 끝나면 3 이 나와야 한다
```

왜 하필 이 둘일까요? 세 후보(교체·삭제·삽입)가 각각 **혼자 가장 작아지는 칸**이 있고, 두
글자가 같은 칸도 셋 있어서 네 갈래가 전부 실행되기 때문이에요. 문제 지문이 예시로 든 셋 중
하나이자 `editDistance.test.ts` 의 첫 케이스이기도 합니다.

<!--proof:walkInput-->

```text
두 글자가 같은 칸         (2, 2) (3, 1) (4, 3)         ④ 가 그만큼 실행된다
교체가 혼자 가장 작은 칸  (1, 1) (3, 3)                ⑤ 의 첫째 후보
삭제가 혼자 가장 작은 칸  (3, 2) (4, 1) (5, 1) (5, 3)  ⑤ 의 둘째 후보
삽입이 혼자 가장 작은 칸  (2, 3)                       ⑤ 의 셋째 후보
오른쪽 아래 칸의 값       3                            이 입력의 답
```

절차 전체를 한 장으로 보이면 이렇습니다. 원문자는 아래 코드 조각에 그대로 달려 있어요.

```text
  T1       (n+1) x (m+1) 짜리 표를 깐다
           첫 열에 i 를 적는다                        ① 지우기 비용
           첫 줄에 j 를 적는다                        ② 넣기 비용
           i 를 1 부터 n 까지:
  T2~T6      j 를 1 부터 m 까지:                      ③ 채울 칸이 남았는가
               두 글자가 같으면 대각선 그대로         ④ 같다
               다르면 세 후보 중 가장 작은 값에 1     ⑤ 다르다
  T7       dp[n][m] 을 돌려준다
```

#### 1. 표를 깔고 테두리에 지우기·넣기 비용을 적는다

첫 조각은 준비입니다. 줄을 `n + 1` 개, 열을 `m + 1` 개로 잡고, 첫 열과 첫 줄에 한쪽이 빈
문자열일 때의 비용을 적어요.

```ts
const n = s.length;
const m = t.length;
const dp: number[][] = Array.from({ length: n + 1 }, () =>
  new Array<number>(m + 1).fill(0),
);

for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = i;   // ① 지우기 비용
for (let j = 0; j <= m; j++) (dp[0] as number[])[j] = j;   // ② 넣기 비용
```

`①` 과 `②` 가 이 조각의 요점입니다. `fill(0)` 이 깔아 둔 `0` 은 아직 아무 뜻이 없는 값이고,
테두리의 값은 그 위에 덮어써요 — 첫 열의 `i` 는 지우는 횟수, 첫 줄의 `j` 는 넣는 횟수입니다.

```text
T1 이 끝난 시점 — 줄 6 개 · 열 4 개
  첫 줄     값 0 1 2 3       s 가 빈 문자열이라 t 를 j 글자 넣는다
  첫 열     값 0 1 2 3 4 5   t 가 빈 문자열이라 s 를 i 글자 지운다
  나머지 칸  값 0            아직 안 채운 칸이다. fill(0) 이 남긴 값일 뿐 뜻이 없다
  └ 두 테두리가 만나는 dp[0][0] 은 0 이다. 빈 문자열을 빈 문자열로 바꾸는 데 할 일이 없다
```

#### 2. 두 글자를 견주어 칸 하나를 정한다

둘째 조각은 칸 하나를 정하는 규칙입니다. 두 루프로 칸을 왼쪽 위부터 차례로 채우고, 칸마다
`s[i−1]` 과 `t[j−1]` 을 견주어 갈래를 골라요.

```ts
for (let i = 1; i <= n; i++) {
  const prev = dp[i - 1] as number[];   // 윗줄 — s 를 앞에서 i-1 글자까지만 본 층
  const cur = dp[i] as number[];        // 이번 줄 — s 를 앞에서 i 글자까지 본 층

  for (let j = 1; j <= m; j++) {                    // ③ 채울 칸이 남았는가
    if (s[i - 1] === t[j - 1]) {
      cur[j] = prev[j - 1] as number;               // ④ 같다
    } else {
      const sub = prev[j - 1] as number;            // 교체
      const del = prev[j] as number;                // 삭제
      const ins = cur[j - 1] as number;             // 삽입
      cur[j] = Math.min(sub, del, ins) + 1;         // ⑤ 다르다
    }
  }
}
```

세 후보에 이름을 붙여 둔 것은 편의가 아닙니다. 세 첨자가 각각 어느 편집인지가 이 알고리즘의
전부인데, `prev[j - 1]` 처럼 첨자로만 적으면 그 뜻이 수 뒤에 숨어요. **코드에서 `sub` 는
대각선 칸, `del` 은 윗칸, `ins` 는 왼쪽 칸입니다.**

| 갈래 | 읽는 칸 | 무엇을 한 것인가 | 비용 |
| --- | --- | --- | --- |
| `④` | `prev[j-1]` | 두 글자가 같아 아무것도 안 한다 | + 0 |
| `⑤` `sub` | `prev[j-1]` | `s[i−1]` 을 `t[j−1]` 로 교체한다 | + 1 |
| `⑤` `del` | `prev[j]` | `s[i−1]` 을 지운다 | + 1 |
| `⑤` `ins` | `cur[j-1]` | `t[j−1]` 을 넣는다 | + 1 |

앞 두 줄만 실행하면 이렇게 나옵니다. `③` 은 `j` 가 `1` 부터 `3` 까지일 때 참이고 `4` 에서
처음 거짓이 돼요.

| 걸음 | 줄 | `s` 의 글자 | `j=0` | `j=1` r | `j=2` o | `j=3` s | 갈래 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| T2 | `i=1` | h | 1 | 1 | 2 | 3 | `⑤⑤⑤` |
| T3 | `i=2` | o | 2 | 2 | 1 | 2 | `⑤④⑤` |

T3 의 `j=2` 가 이 두 줄의 핵심입니다. `'o'` 가 같아 대각선 `dp[1][1] = 1` 을 **그대로**
가져와요 — 값이 안 커지는 유일한 갈래입니다.

```text
T3 의 j=2 가 하는 일
  견주는 두 글자   s[1] = 'o' 와 t[1] = 'o'   같다 — ④ 다
  읽는 칸          dp[1][1] = 1               대각선, 곧 윗줄의 왼쪽 칸이다
  적는 값          1                          편집을 하나도 안 썼으므로 그대로다
  └ 값이 안 커진 칸이 표에 남아 있어야 답이 3 으로 끝난다
```

#### 멈춤 — 교체를 삭제와 삽입으로 대신하면 답이 커진다

여기서 헷갈리기 쉬운 포인트는 `⑤` 의 후보가 셋이라는 것입니다. 「교체 한 번은 삭제 한 번과
삽입 한 번으로도 되니까, 대각선 후보는 없어도 되지 않나」로 읽기 쉬워요. 그 생각대로 한 줄만
바꿔 봅시다.

```ts
cur[j] = Math.min(del, ins) + 1;   // 교체 후보를 뺐다
```

다섯 입력으로 확인해 봅니다. 오른쪽에 `n + m − 2 × LCS` 를 함께 적었어요 — `LCS` 는 두
문자열의 가장 긴 공통 부분 수열의 길이입니다.

<!--proof:pauseNoSub-->

```text
입력                        정본이 낸 답  교체를 뺀 사본  n + m - 2 x LCS  판정
전개 입력 "horse" 와 "ros"             3               4                4  틀리다
"a" 와 "b"                             1               2                2  틀리다
"kitten" 와 "sitting"                  3               5                5  틀리다
"abcd" 와 "bcda"                       2               2                2  같다
"flaw" 와 "lawn"                       2               2                2  같다

└ 교체를 뺀 사본의 답이 다섯 줄 다 n + m - 2 x LCS 와 같다. 그 값이 곧 삭제와 삽입만으로 두 문자열을 같게 만드는 비용이다
```

**교체를 빼면 값이 커집니다.** `"a"` 를 `"b"` 로 바꾸는 데 교체는 한 번이지만 삭제와 삽입은
두 번이에요. 그런데 다섯 줄 중 둘은 답이 같습니다 — 그 둘은 교체를 안 쓰고도 같은 횟수로 끝나는 편집
목록이 있다는 뜻이고, 「교체가 필요 없는 입력」과 「교체가 없어도 되는 규칙」은 다른 이야기예요.

```text
"a" 와 "b" 에서 두 규칙
  교체를 쓴다   a 를 b 로 바꾼다                 편집 1 번
  교체를 뺀다   a 를 지우고 b 를 넣는다          편집 2 번
  └ 두 문자열의 길이가 같은데도 답이 갈린다. 교체는 삭제와 삽입을 한 번에 하는 연산이다
```

오른쪽 열이 우연이 아닙니다. 삭제와 삽입만 쓰면 **양쪽에 공통으로 남는 부분 수열**을 빼고
나머지를 전부 지우고 넣는 셈이라, 그 비용이 `n + m − 2 × LCS` 가 돼요. 공통 부분 수열의
길이를 구하는 절차는
[`longestCommonSubsequence`](../longestCommonSubsequence/longestCommonSubsequence-guide.md)
가 다룹니다.

#### 멈춤 — 위 칸은 삭제이고 왼쪽 칸은 삽입이다

방금 표를 거꾸로 확인하면서 「아래로 한 칸」을 삭제라고 읽었습니다. 여기가 뒤집어 외우기
쉬운 자리예요 — 「위 칸에서 왔으면 `t` 의 글자를 넣은 것」으로 읽으면 어떻게 되는지 봅시다.

<!--proof:pauseDirection-->

```text
칸      옳게 읽으면  뒤바꿔 읽으면  비용
(1, 1)  교체 r       교체 r            1
(2, 2)  그대로 o     그대로 o          0
(3, 2)  삭제 r       삽입 o            1
(4, 3)  그대로 s     그대로 s          0
(5, 3)  삭제 e       삽입 s            1

옳게 읽은 목록을 실행한 결과    "ros"      길이 3
뒤바꿔 읽은 목록을 실행한 결과  "roorsse"  길이 7
└ 아래쪽은 s 의 글자를 하나도 지우지 않아 길이가 5 + 2 = 7 이 된다. 길이 3 인 "ros" 가 될 수 없다
```

**표의 값 3 은 안 틀립니다.** 뒤바꿔 읽어도 `dp[5][3]` 은 그대로 3 이에요 — 세 후보가 전부
`Math.min` 안에 들어 있어서 이름을 바꿔도 고르는 값이 안 바뀝니다. 틀리는 것은 그 값을 편집
목록으로 되읽을 때이고, 위에서 나온 `"roorsse"` 가 그 결과예요.

```text
어느 쪽이 삭제인지는 테두리가 정한다
  dp[i][0] = i    t 가 비었다. s 를 i 번 지운다   첫 열로 내려가는 것이 삭제다
  dp[0][j] = j    s 가 비었다. t 를 j 번 넣는다   첫 줄로 가는 것이 삽입이다
  └ 아래로 한 칸은 s 를 한 글자 더 쓴 것이고, 그 글자를 t 와 안 맞췄으니 지운 것이다
```

#### 멈춤 — 비용이 셋 다 1 이 아니면 바꾸는 방향에 따라 답이 달라진다

지문은 세 연산의 비용이 모두 1 이라고 했습니다. 이 조건이 어디에 쓰이는지 모르고 지나가면
「편집 거리는 두 문자열의 순서를 바꿔도 같다」를 늘 참인 성질로 외우게 돼요. 실제 도구가
쓰는 비용을 넣어 확인해 봅시다.

<!--proof:pauseCost-->

```text
바꾸는 방향       비용이 셋 다 1  교체 2 · 삭제 3 · 삽입 1
"ab" -> "abc"                  1                         1
"abc" -> "ab"                  1                         3
"horse" -> "ros"               3                         8
"ros" -> "horse"               3                         4

└ 왼쪽 열은 방향을 바꿔도 값이 같고 오른쪽 열은 달라진다. 삭제와 삽입의 비용이 다르면 두 문자열을 맞바꿀 때 그 둘도 맞바뀌기 때문이다
```

오른쪽 열의 비용은 지어낸 값이 아닙니다. git 이 명령어 오타를 고쳐 줄 때 부르는 함수가 그
값을 씁니다 — `levenshtein(cmd, candidate, 0, 2, 1, 3)` 이고, 인자 순서가 맞바꾸기 · 교체 ·
넣기 · 지우기예요
([git 저장소의 `help.c`](https://github.com/git/git/blob/master/help.c), 조회 2026-08-30).
같은 저장소의 구현 파일이 *"Note that this algorithm calculates a distance _iff_ d == a"* 라고
적어 둡니다 — 지우기와 넣기의 비용이 같아야 거리가 된다는 뜻인데, git 이 넘기는 값은 그
조건을 안 지킵니다
([`levenshtein.c`](https://github.com/git/git/blob/master/levenshtein.c), 조회 2026-08-30).

```text
비용이 갈리면 무엇이 성립하지 않는가
  d(x, y) = d(y, x)      셋 다 1 이면 참. 삭제와 삽입이 서로의 반대 연산이라 맞바뀐다
  d(x, y) = d(y, x)      삭제 3 · 삽입 1 이면 거짓. "abc" 와 "ab" 에서 3 대 1 이다
  └ 이 글의 표는 세 비용이 같다는 조건에서만 방향을 안 가린다
```

#### 4. 전체 코드

세 조각을 한 함수로 모읍니다. 앞에서 안 나온 것은 마지막 `return` 한 줄뿐이에요. 한쪽이 빈
문자열이면 안쪽 루프가 한 번도 실행되지 않으므로, 그때는 테두리에 적어 둔 값이 그대로 반환
됩니다.

```ts
export function editDistance(s: string, t: string): number {
  const n = s.length;
  const m = t.length;

  const dp: number[][] = Array.from({ length: n + 1 }, () =>
    new Array<number>(m + 1).fill(0),
  );

  // ① 첫 열 — t 가 빈 문자열인 자리다. s 의 앞 i 글자를 전부 지워야 하므로 비용이 i 다.
  for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = i;

  // ② 첫 줄 — s 가 빈 문자열인 자리다. t 의 앞 j 글자를 전부 넣어야 하므로 비용이 j 다.
  for (let j = 0; j <= m; j++) (dp[0] as number[])[j] = j;

  for (let i = 1; i <= n; i++) {
    const prev = dp[i - 1] as number[]; // 윗줄 — s 를 앞에서 i-1 글자까지만 본 층
    const cur = dp[i] as number[]; // 이번 줄 — s 를 앞에서 i 글자까지 본 층

    for (let j = 1; j <= m; j++) {
      // ③ 채울 칸이 남았는가 — 남아 있으면 아래 두 갈래 중 하나로 이 칸을 정한다.
      if (s[i - 1] === t[j - 1]) {
        // ④ 두 글자가 같다 — 편집을 하나도 쓰지 않고 대각선 칸의 비용을 그대로 받는다.
        cur[j] = prev[j - 1] as number;
      } else {
        // ⑤ 다르다 — 세 후보 중 가장 작은 비용에 편집 한 번을 더한다.
        const sub = prev[j - 1] as number; // 교체 — 양쪽에서 한 글자씩 지나간다
        const del = prev[j] as number; // 삭제 — s 의 글자 하나를 버린다
        const ins = cur[j - 1] as number; // 삽입 — t 의 글자 하나를 넣는다
        cur[j] = Math.min(sub, del, ins) + 1;
      }
    }
  }

  return (dp[n] as number[])[m] as number;
}
```

```text
editDistance("horse", "ros")           → 3
editDistance("intention", "execution") → 5
editDistance("kitten", "sitting")      → 3
editDistance("", "abc")                → 3
editDistance("abc", "")                → 3
editDistance("", "")                   → 0
```

### 알아 두면 좋은 개념 — 격자 위의 최단 경로

방금 표를 거꾸로 확인해 얻은 걸음 다섯에는 이름이 붙어 있습니다. 표의 칸을 점으로 보고 세
갈래를 그 점에서 나가는 길로 보면, `dp[n][m]` 은 **왼쪽 위에서 오른쪽 아래까지 가는 경로
중 비용이 가장 작은 것의 값**이에요.

```text
"horse" 와 "ros" 의 격자 — 대괄호가 고른 경로의 칸이다

         j=0    j=1 r  j=2 o  j=3 s
  i=0 -  [0]     1      2      3
            \
  i=1 h   1     [1]     2      3
                   \
  i=2 o   2      2     [1]     2
                        |
  i=3 r   3      2     [2]     2
                          \
  i=4 s   4      3      3     [2]
                               |
  i=5 e   5      4      4     [3]

  아래로 한 칸 = 삭제(비용 1) · 오른쪽으로 한 칸 = 삽입(비용 1)
  대각선 한 칸 = 두 글자가 같으면 0, 다르면 교체(비용 1)
  └ 대괄호 밖의 칸에도 값이 있다. 경로에 안 든 칸일 뿐이다
```

경로의 비용 합이 곧 칸의 값이라는 것은 앞의 표에서 이미 값으로 확인했습니다 — 걸음 다섯의
누적이 `1 · 1 · 2 · 2 · 3` 이고 그 자리 칸의 값과 하나씩 같았어요.

| 무엇 | 격자에서 | 이 문제에서 |
| --- | --- | --- |
| 점 | 칸 `(i, j)` | 접두어 쌍 |
| 길 | 아래 · 오른쪽 · 대각선 | 삭제 · 삽입 · 교체 |
| 길의 비용 | 0 또는 1 | 편집 한 번 |
| 비용이 가장 작은 경로 | 왼쪽 위에서 오른쪽 아래까지 | 최소 편집 횟수 |

이 모양은 이 문제 밖에서도 만납니다. 격자에서 오른쪽과 아래로만 가는 경로의 수를 세는 문제가
같은 점과 같은 길을 쓰고, 생물 서열을 견주는 전역 정렬은 같은 격자에서 길의 비용만 점수로
바꾼 것이에요. 길에 방향이 있고 되돌아오는 길이 없는 격자에서는 **왼쪽 위부터 차례로 한 번씩
보는 것만으로** 비용이 가장 작은 경로가 나옵니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 규칙을 식으로 어떻게 세우는지,
무엇이 매 칸 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

아래 넷이 한꺼번에 맞는 자리입니다.

- **한 자리를 고치면 그 뒤가 통째로 밀립니다.** 자리마다 따로 견주어도 되는 문제라면 표가
  필요 없고 자리를 한 번씩 보면 끝나요.
- **마지막 한 자리를 보는 것만으로 갈래가 유한하게 갈립니다.** 여기서는 넷이고, 그래서 칸
  하나가 이웃 셋만 읽습니다.
- **두 길이의 곱이 감당할 만합니다.** `nm` 이 100 만이면 되지만 `10^9` 이면 표를 못 깝니다.
- **답이 얼마나 클지 미리 모릅니다.** 답이 작다는 것을 알면 표를 통째로 안 채워도 되고, 그
  경우는 아래 「경쟁 설계와의 대조」가 값으로 잽니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  뒤가 밀린다               → 상태가 접두어 쌍이다
  갈래가 넷이다             → 칸 하나가 이웃 셋만 읽는다
  두 길이의 곱이 감당된다   → 표를 통째로 깔 수 있다
  답의 크기를 모른다        → 문턱 없이 한 번에 채운다
```

셋째 줄에서 이 절차가 끊깁니다. 글자가 아니라 파일의 줄이나 유전자 서열을 견주느라 두 길이가
수십만이 되면 `nm` 이 `10^10` 을 넘고, 그때는 표를 만드는 일 자체가 안 됩니다.

```text
두 길이의 곱이 정하는 것
  n = m = 1,000      칸 1,002,001         4 바이트씩 잡아도 4 MB 다
  n = m = 100,000    칸 10,000,200,001    같은 계산으로 40 GB 다
  └ 위는 이 글의 절차로 되는 규모, 아래는 다른 절차를 찾아야 하는 규모다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "최소 편집"  "삽입 삭제 교체"  "몇 번 고치면"        ← 연산 셋이 이웃 셋이 된다
  "두 문자열이 얼마나 비슷한가"  "오타 교정"           ← 자리가 밀리는 견주기다
  "가장 가까운 단어"  "유사도"                        ← 거리를 값으로 요구한다
  "두 서열을 정렬"                                    ← 같은 격자에 점수를 붙인 것이다

제약에 이런 모양이 보이면
  두 길이가 1,000 언저리라 곱이 100 만이다
  답이 얼마나 될지 지문이 아무 말도 안 한다

이런 말이 보이면 이 절차의 자리가 아니다
  "자리를 그대로 두고"  "같은 길이"만 다룬다   ← 자리마다 견주면 끝난다
  "두 길이가 10^5 이다"                        ← 표를 통째로 깔 수 없다
  "거리가 2 이하인 것만"                       ← 문턱이 있으면 띠만 채우면 된다
```

마지막 줄이 다음 절로 이어집니다. 답의 상한을 지문이 주면 표 전체를 채울 이유가 없어져요.

#### 실제로 쓰이는 곳

- **PostgreSQL `fuzzystrmatch` 확장의 `levenshtein()`.** 공식 문서가
  *"This function calculates the Levenshtein distance between two strings"* 라 적고, 시그니처를
  `levenshtein(source text, target text, ins_cost int, del_cost int, sub_cost int) returns int`
  로 둡니다. 비용을 생략하면 *"they all default to 1"* 이라 이 글이 푸는 문제와 같아져요. 같은
  문서에 문턱을 받는 변형이 함께 있습니다 — `levenshtein_less_equal` 은
  *"an accelerated version of the Levenshtein function for use when only small distances are of
  interest"* 이고, *"If the actual distance is less than or equal to `max_d`, then
  `levenshtein_less_equal` returns the correct distance; otherwise it returns some value greater
  than `max_d`"* 입니다.
  ([PostgreSQL 공식 문서 — `fuzzystrmatch`](https://www.postgresql.org/docs/current/fuzzystrmatch.html),
  조회 2026-08-30)
- **git 의 명령어 오타 교정.** `help.c` 의 `help_unknown_cmd` 가 후보 명령어마다
  `levenshtein(cmd, candidate, 0, 2, 1, 3) + 1` 을 계산하고, 가장 가까운 것을
  *"The most similar command is"* 로 보여 줍니다. 인자 넷이 맞바꾸기 0 · 교체 2 · 넣기 1 ·
  지우기 3 이라 **이 글의 비용과 다른 값**이에요.
  ([git 저장소의 `help.c`](https://github.com/git/git/blob/master/help.c), 조회 2026-08-30)
- **Elasticsearch 의 `fuzziness`.** 공식 문서가 *"`fuzziness` is interpreted as a Levenshtein
  Edit Distance — the number of one character changes that need to be made to one string to make
  it the same as another string"* 이라 적고, 받는 값을 *"The maximum allowed Levenshtein Edit
  Distance (or number of edits)"* 로 `0`·`1`·`2` 로 제한합니다. 기본값 `AUTO:3,6` 은 글자
  수 0~2 면 정확히 일치, 3~5 면 편집 한 번, 그보다 길면 편집 두 번까지 허용해요.
  ([Elasticsearch 공식 문서 — Common options](https://www.elastic.co/guide/en/elasticsearch/reference/current/common-options.html),
  조회 2026-08-30)

```text
세 자리가 서로 다른 것을 요구한다
  PostgreSQL     비용을 인자로 받는다              세 비용이 같지 않을 수 있다
  git            교체 2 · 넣기 1 · 지우기 3        방향을 가리는 값이다
  Elasticsearch  편집 두 번까지만 본다             답의 상한이 미리 주어진다
  └ 셋째 줄이 표를 통째로 안 채워도 되는 자리이고, 그것이 다음 절의 경쟁 설계다
```

#### 경쟁 설계와의 대조

최소 편집 횟수라는 같은 값을 내는 다른 절차가 있습니다 — **띠 계산과 문턱 배가**예요. 비용이
문턱 `k` 이하인 편집 목록은 대각선에서 `k` 칸 넘게 벗어날 수 없다는 성질을 써서, 그 띠만
채우고 나온 값이 `k` 를 넘으면 `k` 를 배로 늘려 다시 채웁니다. PostgreSQL 의
`levenshtein_less_equal` 이 문턱을 받는 것과 같은 자리예요.

```text
두 설계가 하는 일
  표 채우기   (n+1)(m+1) 칸을 한 번씩 채운다. 답이 크든 작든 채우는 칸이 같다
  띠 계산     대각선에서 k 칸 안쪽만 채우고, 모자라면 k 를 배로 늘려 다시 채운다
  └ 답이 작으면 띠가 좁아 적게 채우고, 답이 크면 배가 때문에 같은 자리를 여러 번 채운다
```

두 설계에 같은 생성식·같은 길이의 입력을 주고 **값을 정한 칸이 몇 개인지** 셌습니다. 두
문자열의 길이는 둘 다 200 이고, `s` 의 `q` 번째 글자를 알파벳 26 개 중 `(37q) mod 26` 번째
것으로 만든 다음, `t` 는 자리 `floor(200q/c)` 의 글자만 알파벳에서 13 칸 옮긴 것이에요.
여기서 `c` 는 아래 표의 첫 열에 있는 「바꾼 글자 수」이고 `q` 는 0 부터 `c−1` 까지입니다.

**전개 입력을 그대로 쓰지 않은 이유는 그 크기에서 대조가 성립하지 않기 때문이에요.**
`"horse"` 와 `"ros"` 에서는 답 3 이 `t` 의 길이 3 과 같아 띠가 좁아질 여지가 없고, 문턱만
2 에서 4 로 한 번 늘어납니다. 그래서 실측이 표 24 칸 대 띠 40 칸이라 경쟁 설계가 앞서는
쪽을 아예 못 봅니다.

| 바꾼 글자 수 | 답 | 표 채우기 | 띠 계산 | 어느 쪽이 적은가 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 40,401 | **601** | 띠 쪽이 67.2 배 적습니다 |
| 2 | 2 | 40,401 | **1,600** | 띠 쪽이 25.3 배 적습니다 |
| 4 | 4 | 40,401 | **3,389** | 띠 쪽이 11.9 배 적습니다 |

해야 해요 — 바꾼 글자 1 에서는 상대가 601 칸으로 끝냈습니다.

### 수식 정의와 유도

정의부터 적습니다. 편집 목록 하나를 $\sigma$ 라 부르고, 그 안에 담긴 연산의 개수를
$|\sigma|$ 로 적어요. 문자열 $x$ 에 $\sigma$ 를 차례로 적용해 $y$ 가 되는 목록 전체를
$\mathrm{Script}(x, y)$ 라 두면 이렇게 됩니다.

$$dp[i][j] = \min_{\sigma \in \mathrm{Script}(s[1..i],\; t[1..j])} |\sigma|$$

```text
정의를 말로 펴면
  sigma       삽입 · 삭제 · 교체를 차례로 적은 목록 하나
  |sigma|     그 목록에 담긴 연산의 개수. 비용이 셋 다 1 이라 개수가 곧 비용이다
  s[1..i]     s 의 앞 i 글자. i = 0 이면 빈 문자열이다
  Script(x,y) x 를 y 로 만드는 편집 목록 전부
  └ 어떤 문자열도 글자를 전부 지우고 다시 넣으면 다른 문자열이 되므로 Script 는 결코 비지 않는다
```

이 정의가 표와 같은 값을 내는지 작은 입력에서 확인합니다. `s = "ho"` 와 `t = "or"` 의 접두어
쌍은 아홉 개이고, 각각을 한 번씩 편집해 찾아가는 방식으로 센 값과 표의 값을 나란히 적었어요.

<!--proof:mathCheck-->

```text
i  j  s 의 앞 i 글자  t 의 앞 j 글자  한 번씩 편집해 센 최소 횟수  dp[i][j]
0  0  ""              ""                                        0         0
0  1  ""              "o"                                       1         1
0  2  ""              "or"                                      2         2
1  0  "h"             ""                                        1         1
1  1  "h"             "o"                                       1         1
1  2  "h"             "or"                                      2         2
2  0  "ho"            ""                                        2         2
2  1  "ho"            "o"                                       1         1
2  2  "ho"            "or"                                      2         2

└ 오른쪽 두 열이 아홉 줄 다 같다. 정의대로 센 값과 표의 값이 같다는 뜻이다
```

이제 유도합니다. 먼저 **하한** 하나가 나와요. 편집 하나는 두 문자열의 길이 차이를 많아야 1
바꿉니다 — 삭제와 삽입은 한쪽 길이만 1 바꾸고, 교체는 양쪽을 그대로 둡니다.

$$dp[i][j] \ge |i - j|$$

```text
왜 길이 차이보다 작을 수 없는가
  삭제      s 쪽 길이가 1 준다        차이가 많아야 1 바뀐다
  삽입      t 쪽을 하나 맞춘다        차이가 많아야 1 바뀐다
  교체      양쪽 길이가 그대로다      차이가 안 바뀐다
  시작과 끝  차이가 |i - j| 에서 0 으로   그러려면 연산이 적어도 |i - j| 개 필요하다
```

다음은 점화식입니다. 마지막 연산이 무엇이었는지로 경우를 가르는데, 두 글자가 같으면 아무것도
안 하는 갈래가 하나 더 있어요. 갈래가 이 넷으로 전부인 것은 마지막 자리에서 `s` 의 글자를
쓰거나 안 쓰고 `t` 의 글자를 쓰거나 안 쓰는 네 조합이 그것뿐이기 때문입니다.

$$dp[i][j] = \begin{cases} dp[i-1][j-1] & (s[i-1] = t[j-1]) \\ 1 + \min\bigl(dp[i-1][j-1],\; dp[i-1][j],\; dp[i][j-1]\bigr) & (s[i-1] \ne t[j-1]) \end{cases}$$

```text
두 방향으로 확인한다
  상한   네 갈래 각각이 실제로 가능한 편집 목록을 하나씩 준다   dp[i][j] 는 그 최솟값을 넘지 못한다
  하한   어떤 최소 목록이든 마지막 연산이 넷 중 하나다          그 목록의 앞부분이 그 갈래의 값 이상이다
  └ 두 방향이 만나 등호가 된다

같은 글자에서 대각선을 그냥 쓰는 것이 왜 안전한가
  이웃 칸의 성질     |dp[i-1][j] - dp[i-1][j-1]| <= 1   접두어를 한 글자 늘린 답은 넣기나 지우기 한 번 차이다
  대각선을 쓴 값     dp[i-1][j-1]                       비용 0 을 더한다
  위를 쓴 값         dp[i-1][j] + 1                     위 성질에서 dp[i-1][j-1] - 1 이상이므로 합이 대각선 값 이상이다
  왼쪽을 쓴 값       dp[i][j-1] + 1                     같은 성질을 j 쪽에 쓰면 마찬가지다
  └ 그래서 같은 글자 칸에서는 최솟값을 다시 고를 필요가 없다
```

식을 그대로 옮기면 이런 조각이 됩니다. 표를 안 쓰고 정의만 따라간 형태예요.

```ts
const f = (i: number, j: number): number =>
  i === 0
    ? j
    : j === 0
      ? i
      : s[i - 1] === t[j - 1]
        ? f(i - 1, j - 1)
        : 1 + Math.min(f(i - 1, j - 1), f(i - 1, j), f(i, j - 1));
```

지금까지는 표가 이미 보인 것을 기호로 옮긴 것입니다. 식이 새로 주는 것은 여기부터예요 —
**갈래를 끝까지 펼쳤을 때 편집 목록의 뼈대가 몇 가지인가**를 임의의 `i`·`j` 로 닫을 수 있습니다. 뼈대 하나는 격자에서 대각선·아래·
오른쪽 세 걸음으로 `(0, 0)` 에서 `(i, j)` 까지 가는 경로 하나이고, 그 수를 $P(i, j)$ 라 적으면
점화식이 이렇게 됩니다.

$$P(i, 0) = P(0, j) = 1, \qquad P(i, j) = P(i-1, j) + P(i, j-1) + P(i-1, j-1)$$

```text
점화식을 작은 값에 넣어 봅니다
  P(1,1)   P(0,1) + P(1,0) + P(0,0)   = 1 + 1 + 1   = 3
  P(1,2)   P(0,2) + P(1,1) + P(0,1)   = 1 + 3 + 1   = 5
  P(2,2)   P(1,2) + P(2,1) + P(1,1)   = 5 + 5 + 3   = 13
```

닫힌 형태는 **대각선 걸음의 수로 갈라서** 나옵니다. 대각선을 `p` 번 쓰면 아래로 `i − p` 번,
오른쪽으로 `j − p` 번 가야 하고, 걸음이 모두 `i + j − p` 개예요. 그 걸음들을 늘어놓는 방법의
수가 곧 경로의 수입니다.

$$P(i, j) = \sum_{p=0}^{\min(i,j)} \frac{(i+j-p)!}{p!\,(i-p)!\,(j-p)!}$$

```text
i = j = 2 에 손으로 넣어 보면
  p = 0   대각선 0 번 · 아래 2 번 · 오른쪽 2 번   4! / (0! 2! 2!) = 24 / 4 = 6
  p = 1   대각선 1 번 · 아래 1 번 · 오른쪽 1 번   3! / (1! 1! 1!) = 6 / 1  = 6
  p = 2   대각선 2 번 · 아래 0 번 · 오른쪽 0 번   2! / (2! 0! 0!) = 2 / 2  = 1
  합                                                                        13
  └ 위 점화식으로 센 P(2,2) 와 같다
```

<!--proof:mathPathCount-->

```text
i = j  경로 수(실측)  sum_p (i+j-p)! / (p! (i-p)! (j-p)!)
    1              3                                    3
    2             13                                   13
    3             63                                   63
    4            321                                  321
    5          1,683                                1,683
    6          8,989                                8,989

제약 규모 i = j = 1,000 을 두 식에 넣으면
  경로 수      764 자리
  (i+1)(j+1)  1,002,001
```

여섯 규모 전부에서 세어 본 값과 닫힌 형태가 한 자리도 안 틀립니다. 마지막 두 줄이 제약
규모에서의 대조예요 — 같은 답 하나를 얻는 데 764 자리와 1,002,001 이 갈립니다.

하한 하나가 더 나옵니다. 경로 위의 어느 칸 `(i, j)` 에서든 거기까지의 비용이 `|i − j|` 이상
이므로, **비용이 문턱 `k` 이하인 경로는 대각선에서 `k` 칸을 벗어날 수 없습니다.**

```text
비용이 문턱 k 이하인 경로는 어디에 있는가
  칸 (i, j) 까지의 비용   |i - j| 이상이다   위에서 유도한 하한이다
  경로 전체의 비용         그 이상이다        앞부분의 비용이 전체를 넘지 못하니까
  전체가 k 이하라면        |i - j| <= k      대각선에서 k 칸 안쪽 칸만 지난다
  └ 답이 작다는 것을 미리 알면 표의 이 띠만 채워도 된다는 뜻이고, 그것이 경쟁 설계가 쓰는 성질이다
```

### 불변식 — 칸을 정한 직후 그 칸은 두 접두어를 같게 만드는 최소 비용이다

파트 1 이 보인 것은 `"horse"` 와 `"ros"` 라는 입력 하나에서 답이 맞았다는 사실입니다. 그것과
「어떤 입력에서도 맞는다」 사이에는 아직 거리가 있어요. 그 거리를 메우는 것이 **칸마다 늘 참인
문장** 하나이고, 이 절에서 그것을 세운 다음 유지되는지 확인합니다.

> 안쪽 루프가 칸 `(i, j)` 를 정한 직후, `dp[i][j]` 는 `s` 의 앞 `i` 글자를 `t` 의 앞 `j`
> 글자로 바꾸는 데 필요한 최소 편집 횟수와 같습니다.

```text
  무엇이   dp[i][j] 한 칸
  언제     그 칸을 정한 직후다. 그 전에는 fill(0) 이 깔아 둔 0 이 들어 있다
  왜       칸을 정하는 순간 세 이웃이 이미 참이어야 하기 때문이다
```

「언제」가 빠지면 이 문장은 거짓이 됩니다. `fill(0)` 직후의 안쪽 칸도 `0` 을 들고 있지만 그
`0` 은 답이 아니라 아직 아무도 안 건드린 자리예요. 그 시점에 참인 것은 테두리뿐입니다.

**출발점부터 봅시다.** 루프에 들어가기 전 첫 열과 첫 줄은 한쪽이 빈 문자열인 자리입니다. 빈
문자열로 만들려면 남은 글자를 전부 지우는 수밖에 없고, 빈 문자열에서 만들려면 전부 넣는
수밖에 없어요.

| 자리 | 하는 일 | 문장이 유지되는 근거 |
| --- | --- | --- |
| 첫 열 `dp[i][0]` | `i` 를 적는다 | `t` 가 비어 있어 `s` 의 `i` 글자를 지우는 것 말고 할 일이 없다 |
| 첫 줄 `dp[0][j]` | `j` 를 적는다 | `s` 가 비어 있어 `t` 의 `j` 글자를 넣는 것 말고 할 일이 없다 |
| 두 글자가 같은 칸 | 대각선을 그대로 | 그 글자를 안 건드리는 것이 최선이고, 남는 것이 대각선 칸이다 |
| 두 글자가 다른 칸 | 세 후보 중 최솟값에 1 | 마지막 연산이 셋 중 하나이고, 그 셋이 후보의 전부다 |
| 종료 | `(n, m)` 을 정한다 | 두 문자열 전체를 놓고 본 답이다 |

표의 가운데 두 줄이 논증의 무게를 집니다. 그 둘이 읽는 이웃은 셋 다 **윗줄이거나 같은 줄의
왼쪽**이고, 루프가 위에서 아래로 · 왼쪽에서 오른쪽으로 나아가므로 읽는 시점에 이미 값이
정해져 있어요.

| 읽는 이웃 | 어디인가 | 언제 정해졌는가 |
| --- | --- | --- |
| `dp[i-1][j-1]` | 앞 줄의 왼쪽 열 | 앞 줄을 채울 때 |
| `dp[i-1][j]` | 앞 줄의 같은 열 | 앞 줄을 채울 때 |
| `dp[i][j-1]` | 같은 줄의 바로 앞 칸 | 이 줄에서 방금 |

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 둘 다 빈 문자열 | 두 루프가 한 번도 실행되지 않는다 | `dp[0][0]` 인 `0` 이 답이다 |
| `s` 만 빈 문자열 | 안쪽 루프가 한 번도 실행되지 않는다 | 첫 줄에 적어 둔 `m` 이 답이다 |
| `t` 만 빈 문자열 | 안쪽 루프가 한 번도 실행되지 않는다 | 첫 열에 적어 둔 `n` 이 답이다 |
| 한 글자씩이고 같다 | 칸 하나를 정한다 | 대각선 `dp[0][0]` 이 그대로 `0` 이다 |
| 한 글자씩이고 다르다 | 칸 하나를 정한다 | 세 후보가 `0`·`1`·`1` 이라 `0 + 1 = 1` 이다 |
| 두 문자열이 같다 | 대각선 칸이 전부 같은 갈래다 | `0` 이 대각선을 따라 끝까지 이어진다 |

**이번에는 문장을 일부러 깨뜨려 봅니다.** 출발점을 지키고 있던 줄은 **첫 열을 채우는 줄**
이에요. 「테두리는 어차피 빈 문자열 자리이니 전부 0 이면 되지 않나」라는 생각으로 그 한 줄만
바꾸겠습니다.

```ts
for (let i = 0; i <= n; i++) (dp[i] as number[])[0] = 0;   // i 대신 0 을 적었다
```

실행하면 이렇게 나옵니다.

```text
입력                        정본이 낸 답  첫 열을 0 으로 둔 답  판정
전개 입력 "horse" 와 "ros"             3                     2  틀리다
"abc" 와 ""                            3                     0  틀리다
"" 와 "abc"                            3                     3  같다

└ 첫 열의 i 는 s 의 앞 i 글자를 지우는 비용이다. 그것을 0 으로 두면 s 의 앞부분을 비용 없이 버릴 수 있게 되어, t 가 s 어딘가에 얼마나 가깝게 들어 있는지를 재는 다른 문제가 된다
```

문장이 어디서 거짓이 되는지가 값으로 확인됩니다. `dp[3][0] = 0` 은 「`"hor"` 를 빈 문자열로
만드는 데 편집이 필요 없다」는 뜻인데, 지우기도 편집 한 번이라 그 자리의 참값은 3 이에요. 다섯 줄 중 셋에서 답이
같은 것도 이 실수의 성격입니다 — `s` 의 앞부분을 버리는 것이 이득이 아닌 입력에서는 티가 안
납니다.

```text
"horse" 와 "ros" 에서 두 값이 갈리는 자리
  정본의 마지막 줄   5 4 4 3   h 를 바꾸고 r 과 e 를 지운다
  변이의 마지막 줄   0 1 2 2   "horse" 의 앞 두 글자를 공짜로 버리고 "rse" 만 고친다
  변이가 세는 것               t 가 s 안에 얼마나 가깝게 들어 있는가
  └ 그것은 시작 자리를 골라도 되는 문제라, 두 문자열 전체를 견주는 이 문제의 답이 아니다
```

### 비용 계산

#### 비용을 세는 과정

실행 한 번이 하는 일을 셋으로 나눠 셉니다 — 테두리를 채우는 일, 안쪽 칸을 정하는 일, 마지막
칸을 읽는 일이에요. 전개의 걸음에 그대로 대응시키면 이렇게 나뉩니다.

<!--proof:perfCount-->

```text
무리           어느 걸음인가    문자 비교  값 비교  기본 연산
테두리 채우기  T1                       0        0          0
칸 채우기      T2 부터 T6 까지         15       24         39
읽기           T7                       0        0          0
합계                                   15       24         39

└ 채운 칸이 5 x 3 = 15 개이고 그중 두 글자가 같은 칸이 3 개다
└ 두 글자가 다른 칸에서만 세 후보를 견주느라 값 비교가 두 번씩 든다 — 12 x 2 = 24
└ 제약 규모 |s| = |t| = 1,000 이고 두 글자가 같은 칸이 하나도 없으면 기본 연산이 3,000,000 번이다
```

T1 과 T7 의 줄이 전부 0 인 것은 두 걸음이 값을 적거나 읽기만 하기 때문입니다. 견주는 일이
없으니 이 입력의 기본 연산은 T2 부터 T6 까지의 39 번이 전부예요.

```text
총식 = 테두리 채우기 + 칸 채우기 + 읽기

  테두리 채우기   칸 n + m + 1 개에 값을 적는다
  칸 채우기       문자 비교 nm 번과 값 비교 2 x (nm - 같은 칸 수) 번
  읽기            0
  기본 연산       nm + 2 x (nm - 같은 칸 수)
  잡는 칸         (n+1)(m+1)
  n = 5 이고 m = 3 이면 15 + 2 x (15 - 3) = 39 로 위 표와 같다
```

**연산 수가 입력의 내용에 조금 달려 있습니다.** 두 글자가 같은 칸에서는 대각선 하나를 읽고
끝나지만, 다른 칸에서는 후보 셋을 견주느라 값 비교가 두 번 더 들어요.

```text
같은 칸 수가 정하는 범위
  같은 칸이 nm 개   두 문자열이 한 글자를 되풀이한다   기본 연산 nm
  같은 칸이 0 개    공통 글자가 하나도 없다            기본 연산 3nm
  └ 같은 칸 수만 이 범위를 정한다. 3 배 안쪽이라 차수는 안 바뀐다
```

#### 케이스별 비용과 그 경계

「어떤 입력인가」와 「어떤 종류의 값인가」는 서로 다른 축이에요. 앞을 **케이스**, 뒤를
**경계**라 부르고 둘을 짝지어 적지 않습니다.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (한쪽이 빈 문자열이다) | `O(nm)` | `Θ(n + m)` — 안쪽 루프가 한 번도 실행되지 않는다 |
| **평균적인 경우** (입력 분포를 가정하지 않는다) | `O(nm)` | `Θ(nm)` |
| **최악의 경우** (둘 다 제약의 최댓값이고 공통 글자가 없다) | `O(nm)` | `Θ(nm)` — 실제로 도달한다 |

평균과 최악이 같은 차수인 것이 이 절차의 성질입니다. 기본 연산이 `nm` 과 `3nm` 사이를 벗어나지
못하니, 글자를 어떻게 바꿔도 차수가 안 바뀌어요.

```text
두 경계가 무엇을 말하는가
  O(nm)   연산 수가 그보다 크지 않다             위쪽만 막은 값이다
  Θ(nm)   위아래가 같은 차수라 실제로 그만큼 든다   아래쪽까지 막은 값이다
  └ 칸마다 문자 비교를 적어도 하나는 하므로 아래로도 nm 이다. 그래서 Θ 를 쓸 수 있다
```

**총식은 앞뒤로 붙는 항까지 한 번은 적어 둡니다.** 이 절차에는 그 항이 없다는 것이 특징이에요 —
정렬도, 위치 목록도, 해시표도 만들지 않습니다.

```text
총식 = Θ(nm) 시간 + Θ(nm) 추가 메모리

  시간     테두리 n + m + 1 칸 · 문자 비교 nm · 값 비교 2 x (nm - 같은 칸 수)
  메모리   칸 (n+1)(m+1) 개

n = m = 1,000 이고 공통 글자가 없으면 기본 연산이 정확히 3,000,000 번, 잡는 칸이 1,002,001 개다
```

**여기서 말한 보장은 전부 최악 보장입니다.** 기댓값이 아니에요 — 무작위성도, 해시도, 분할
상환도 안 쓰고, 어떤 입력을 넣어도 기본 연산이 `3nm` 이하입니다.

```text
기댓값을 말할 자리가 없는 이유
  칸을 찾는 일     첨자 둘로 바로 간다          충돌이라는 개념이 없다
  칸의 개수        두 길이만으로 정해진다       입력 분포를 가정할 필요가 없다
  칸 하나의 비용   많아야 문자 비교 1 값 2      평균이 아니라 상수다
  └ 최악에서 잰 값과 아무 입력에서나 잰 값이 같은 차수다
```

#### 최악을 만드는 입력

연산 수를 최대로 만들려면 둘이 함께 필요합니다 — **두 길이를 제약의 최댓값으로 두는 것**과
**두 글자가 같은 칸을 하나도 안 만드는 것**이에요. 그것을 값으로 확인해 봅시다.

<!--proof:worstShape-->

```text
입력의 모양 (|s| = |t| = 1,000)  두 글자가 같은 칸  문자 비교    값 비교  기본 연산     답
두 문자열이 같다                         1,000,000  1,000,000          0  1,000,000      0
글자가 둘씩 번갈아 나온다                  500,000  1,000,000  1,000,000  2,000,000      2
알파벳 26 을 차례로 되풀이한다              38,467  1,000,000  1,923,066  2,923,066      2
공통 글자가 하나도 없다                          0  1,000,000  2,000,000  3,000,000  1,000

가운데 왼쪽 열이 0 이 되는 마지막 줄에서 기본 연산이 가장 많다
└ 문자 비교는 네 줄 다 1,000,000 으로 같고, 값 비교만 0 에서 2,000,000 까지 갈린다
```

**「비슷한 문자열일수록 오래 걸린다」는 이 표에서 거꾸로입니다.** 첫 줄은 모든 칸이 같은
갈래라 값 비교가 0 이고, 마지막 줄은 모든 칸이 다른 갈래라 2,000,000 이에요. 겹치는 글자가
많을수록 견줄 후보가 줄어 오히려 적게 듭니다.

```text
축마다 최악을 만드는 입력이 다르다
  기본 연산   n = m = 1,000 이고 공통 글자가 없다   3,000,000 번
  잡는 칸     n = m = 1,000                        1,002,001 칸. 글자는 안 본다
  답의 크기   공통 글자가 없는 길이 1,000 짜리 둘   답이 긴 쪽의 길이 1,000 이 된다
  └ 첫째와 셋째는 같은 입력에서 함께 최악이 되고, 둘째만 글자를 아예 안 본다
```

**답 크기의 최악은 긴 쪽의 길이입니다.** 어떤 두 문자열이든 `s` 를 전부 지우고 `t` 를 전부
넣으면 `n + m` 번에 끝나지만, 앞에서부터 `min(n, m)` 자리는 교체 한 번으로 처리할 수 있어
`max(n, m)` 을 넘지 않아요.

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 기본 연산 | `n = m = 1,000`, 공통 글자 없음 | 3,000,000 |
| 잡는 칸 | `n = m = 1,000`, 글자는 무엇이든 | 1,002,001 |
| 답의 크기 | 공통 글자가 없는 길이 1,000 짜리 둘 | 1,000 |

### 스스로 점검하기

여기까지를 한 문장으로 줄이면 이렇습니다. 두 문자열의 **마지막 한 번의 편집**을 정하면
남는 것이 접두어 한 쌍이라 상태가 `(n+1)(m+1)` 개로 닫히고, 첫 줄과 첫 열은 한쪽이 빈
문자열이라 값이 정의에서 바로 나오며, 나머지 칸은 이웃 셋만 읽어 채우면 오른쪽 아래가 답입니다.

```text
1.   테두리에 지우기 · 넣기 비용을 적는다   첫 열은 i, 첫 줄은 j
2.   두 글자를 견준다                        갈래가 같다와 다르다로 갈린다
3.   같으면 대각선을 그대로                  편집을 안 쓴다
4.   다르면 세 후보 중 가장 작은 값에 1      교체 · 삭제 · 삽입
5.   오른쪽 아래 칸을 돌려준다               마지막으로 정해지는 칸이다
```

답을 이어 붙인 문제부터 하나 봅시다. 전개의 T5 는 `s` 의 `'s'` 를 처리한 줄이었고 `4 3 3 2` 로
나왔어요. 그 줄에서 `j=3` 칸이 2 인데, 그 값은 윗줄 T4 의 `j=2` 칸에서 그대로 온 것입니다.
그런데 T5 의 `j=1` 과 `j=2` 는 윗줄보다 값이 커졌어요. 같은 줄에서 어떤 칸은 값이 커지고
어떤 칸은 그대로인 이유가 무엇일까요?

```text
T4   i=3   s 의 글자 'r'   줄 = 3 2 2 2
T5   i=4   s 의 글자 's'   줄 = 4 3 3 2
```

<!--check:whyRowMixes-->
`s` 의 글자 `'s'` 가 `t` 의 세 글자 중 마지막 것과만 같기 때문입니다. `j=3` 은 `t[2] = 's'`
라 두 글자가 같은 갈래이고, 대각선 `dp[3][2] = 2` 를 편집 없이 그대로 받아요. `j=1` 과 `j=2`
는 `'r'`·`'o'` 와 견주므로 다른 갈래이고, 세 후보 중 가장 작은 값에 1 을 더하니 반드시 이웃
보다 커집니다.

```text
T5 의 세 칸이 갈리는 자리
  j=1   's' 와 'r'   다르다   min(3, 2, 4) + 1 = 3
  j=2   's' 와 'o'   다르다   min(2, 2, 3) + 1 = 3
  j=3   's' 와 's'   같다     dp[3][2] = 2 를 그대로
  └ 한 줄 안에서도 칸마다 갈래가 다르다. 줄 단위로 값이 커지는 것이 아니다
```
<!--/check-->

```text
아래 셋에는 답을 안 달았습니다. 막히면 괄호 안의 절로 돌아가 보세요
  1 번 문제   두 번째 「멈춤」
  2 번 문제   「수식 정의와 유도」
  3 번 문제   「경쟁 설계와의 대조」
```

- 표를 다 채우고 나면 마지막 칸만 쓰니 줄 하나만 유지해도 될 것 같습니다. 실제로 줄 둘만
  들고도 답을 낼 수 있는데, 그때 대각선 값을 어떻게 챙겨야 하는지 손으로 적어 보세요. 두 번째
  「멈춤」에서 본 편집 목록을 거슬러 확인하는 일이 그때 왜 안 되는지도 함께 생각해 보세요.
- 세 연산의 비용이 `1`·`1`·`1` 이 아니라 `2`·`3`·`1` 이면 표의 어느 줄이 바뀔까요? 「수식
  정의와 유도」의 점화식에서 `+1` 이 붙는 자리를 각각 어떤 값으로 바꿔야 하는지 적고, 첫 줄과
  첫 열이 어떻게 달라지는지도 함께 적어 보세요.
- 두 문자열의 길이가 각각 100,000 이면 이 표를 못 깝니다. 「경쟁 설계와의 대조」의 띠 계산이
  문턱 `k` 로 한 바퀴 채울 때 몇 칸을 채우는지 `k` 와 두 길이로 식을 세우고, 문턱을 배로
  늘리는 바퀴까지 더하면 답이 얼마 이하일 때 1 초 안에 끝나는지 따져 보세요.
