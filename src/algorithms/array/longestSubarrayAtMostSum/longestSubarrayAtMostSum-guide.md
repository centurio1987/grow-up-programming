# 슬라이딩 윈도 — 합이 S 이하인 가장 긴 구간에서 왼쪽 끝을 되돌리지 않아도 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 모든 구간을
하나씩 재는 방법에서 출발해 두 끝을 한 방향으로만 옮기는 방법까지 가고, 그 방법을 단계마다 값으로 푼
뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열에서 **연속된 한 토막**을 고르되, 그 토막에 든 값의 합이 상한 `S` 를 넘지 않으면서 가장 길게
고르는 과제입니다. 고른 토막을 **창**이라고 부르고, 창의 왼쪽 끝을 `l`, 오른쪽 끝을 `r` 로 적어요. 창은
두 끝을 포함하는 인덱스 구간 `[l, r]` 입니다. 배열 `[1 2 1 0 1 1 0]` 에 `S = 4` 를 두고 합이 4 이하인 창
둘을 그리면 이렇습니다.

<!--fig:concept-window-->
![합이 4 이하인 창 둘 — [0,3] 과 더 긴 [2,6]](./figs/concept-window.svg)

괄호가 창이고, 대시로 그린 칸은 창 밖입니다. 두 창 모두 합이 4 이하인데 `[2,6]` 이 한 칸 더 길어서
이쪽이 답이에요. 창을 배열 위에서 오른쪽으로 옮겨 가며 답을 찾는 방법을 **슬라이딩 윈도**라고 부르고, 이
글은 끝까지 그 이름으로 부릅니다.

이 과제 전체를 정하는 것은 **원소가 전부 비음의 정수**라는 조건입니다. 그 덕분에 창의 합이 한 방향으로만
움직여요. 오른쪽 끝을 넓히면 합이 줄지 않고, 왼쪽 끝을 오른쪽으로 옮겨 값을 빼면 합이 늘지 않습니다.

```text
r 을 한 칸 넓힌다   [l, r] → [l, r+1]    합에 nums[r+1] 을 더한다   합은 줄지 않는다
l 을 한 칸 옮긴다   [l, r] → [l+1, r]    합에서 nums[l] 을 뺀다     합은 늘지 않는다
```

여기서 결론 하나가 따라옵니다. 오른쪽 끝을 한 칸 넓혔을 때 **왼쪽 끝을 왼쪽으로 되돌릴 이유가
없어요.** 되돌리면 창은 길어지지만 합도 함께 늘어서, 방금 상한을 넘겨 줄여 둔 자리를 다시 넘기 때문입니다.
위 배열에서 오른쪽 끝을 한 칸씩 넓혀 보면 왼쪽 끝은 이렇게만 움직입니다.

<!--proof:concept-left-path-->

```text
r = 4 로 넓히면  창의 합이 5 가 되어  l 을 0 에서 1 로 옮긴다
r = 5 로 넓히면  창의 합이 5 가 되어  l 을 1 에서 2 로 옮긴다
      └ l 은 0 → 1 → 2 로만 갔다. 왼쪽으로 되돌아간 적이 없다
```

그래서 오른쪽 끝은 `n` 칸을 한 번 지나가고 왼쪽 끝도 많아야 `n` 칸을 한 번 지나갑니다. 두 끝을 합쳐
최대 `2n` 번만 움직이니 전체 연산이 배열 길이에 비례해요. 결과만 적으면 `O(n)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **연속 부분 배열**이 무엇인지. 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 것이고,
  원소를 골라 담는 부분집합과 다릅니다.
- **구간 합**이 무엇인지. 그 구간에 든 값을 전부 더한 수예요. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 를 먼저 봅니다.
- **비음의 정수**라는 말의 뜻 — `0` 이거나 `0` 보다 큰 정수입니다. 이 조건 하나가 이 글의
  전부를 떠받치므로 여기서 확인하고 갑니다.
- 배열을 한 번 지나가는 `for` 루프와, 조건이 참인 동안 반복하는 `while` 루프.

「가장 긴 구간을 찾는다」와 「가장 큰 합을 찾는다」는 다른 과제입니다. 뒤쪽은
[`kadane`](../kadane/kadane-guide.md) 이 다루는 것이고, 이 글은 **길이**를 최대로 만듭니다. 같은 배열에서
두 과제의 답을 나란히 놓으면 이렇습니다.

<!--proof:prereq-max-vs-long-->

| 찾는 것 | 구간 | 합 | 길이 |
| --- | --- | ---: | ---: |
| 합이 가장 큰 구간(같으면 긴 쪽) | [0,6] | 6 | 7 |
| 합이 4 이하인 가장 긴 구간 | [2,6] | 3 | 5 |

상한이 없으면 합이 가장 큰 구간은 배열 전체이고, 상한 4 가 붙으면 합보다 길이를 보는 다른 구간이 답이
됩니다.

### 아이디어를 떠올리는 과정 — 모든 구간 재기에서 슬라이딩 윈도까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 비음의 정수 배열과 상한을
받아서, 합이 상한 이하인 가장 긴 연속 구간의 길이를 돌려줍니다.

```ts
function longestSubarrayAtMostSum(nums: number[], S: number): number;
```

- 입력: 비음의 정수 배열 `nums` 와 합의 상한 `S`.
- 출력: 합이 `S` 이하인 연속 부분 배열 중 가장 긴 것의 길이. 그런 것이 없으면 `0`.
- 규모: 배열 길이 `n` 은 1 이상 100,000 이하, 원소는 0 이상 10,000 이하, `S` 는 0 이상 `10^9`
  이하입니다. 비용은 흔한 채점 환경의 예산인 1 초에 대어 잽니다.

이 글이 쓰는 기호는 여섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 배열 `nums` 의 길이 | `1 ≤ n ≤ 100,000` |
| `nums` | 입력 배열. `nums[i]` 가 `i` 번째 값 | `0 ≤ nums[i] ≤ 10,000` |
| `S` | 창의 합에 걸린 상한 | `0 ≤ S ≤ 10^9` |
| `l` · `r` | 창의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `l = r + 1` 이면 창이 비었다 |
| `windowSum` | 창 안의 값을 더한 수. 글에서는 「창의 합」, 코드에서는 `windowSum` 으로 씁니다 | `0` 이상 |
| `best` | 지금까지 찾은 가장 긴 창의 길이. 이 값이 답이 됩니다 | `0 ≤ best ≤ n` |

가장 먼저 떠오르는 방법은 모든 구간을 재는 것입니다. 시작점 `l` 을 하나 정하고 끝점 `r` 을 오른쪽으로
늘려 가며 합을 재는 일을, 모든 시작점에 대해 되풀이해요.

```ts
let best = 0;
for (let l = 0; l < n; l++) {
  let sum = 0;
  for (let r = l; r < n; r++) {
    sum += nums[r];
    if (sum > S) break; // 비음의 정수라 더 늘려도 합이 줄지 않는다
    best = Math.max(best, r - l + 1);
  }
}
```

이 방법은 답을 틀리지 않습니다. 비용은 **창의 합을 고친 횟수**, 여기서는 덧셈 수로 셉니다. `break` 가 한
번도 실행되지 않는 입력 — 모든 원소가 `0` 이고 `S = 0` 인 경우 — 을 넣으면 시작점·끝점 쌍이 전부
나옵니다.

<!--proof:origin-cost-->

| n | 덧셈 수 | 초당 1 억 번 기준 | 구한 방법 |
| ---: | ---: | ---: | --- |
| 1,000 | 500,500 | 0.005 초 | 실행해서 셌다 |
| 10,000 | 50,005,000 | 0.5 초 | 실행해서 셌다 |
| 100,000 | 5,000,050,000 | 50 초 | n(n+1)/2 로 냈다 |

모든 원소가 0 이고 S = 0 인 입력이라 한 번도 멈추지 않습니다. 실행해서 센 n = 1,000 · 10,000 에서 덧셈 수가 n(n+1)/2 와 정확히 같았습니다.

<!--/proof-->

`n` 이 상한 100,000 이면 덧셈이 50 억 번이고, 초당 1 억 번으로 잡아도 50 초예요. 예산 1 초의 쉰
배입니다. 그 50 억 안에 같은 일을 몇 번이나 되풀이하는지 보려고, 원소 일곱 개짜리 입력 `[1 2 1 0 1 1 0]`,
`S = 4` 에서 시작점마다 쌓인 합을 적었습니다.

<!--proof:origin-restart-->

| 시작점 | 차례로 쌓인 합 | 더한 횟수 | 멈춘 까닭 |
| --- | --- | ---: | --- |
| l = 0 | 1 → 3 → 4 → 4 → 5 | 5 | 합이 4 를 넘었다 |
| l = 1 | 2 → 3 → 3 → 4 → 5 | 5 | 합이 4 를 넘었다 |
| l = 2 | 1 → 1 → 2 → 3 → 3 | 5 | 배열 끝까지 갔다 |
| l = 3 | 0 → 1 → 2 → 2 | 4 | 배열 끝까지 갔다 |
| l = 4 | 1 → 2 → 2 | 3 | 배열 끝까지 갔다 |
| l = 5 | 1 → 1 | 2 | 배열 끝까지 갔다 |
| l = 6 | 0 | 1 | 배열 끝까지 갔다 |

더한 횟수를 모두 합하면 25 번이고, 답은 5 입니다.

<!--/proof-->

`l = 1` 의 줄은 인덱스 1 부터 4 까지를 새로 더했는데, `l = 0` 의 줄이 그 구간을 이미 더해 뒀어요. 직전
줄의 합에서 `nums[0]` 하나만 빼면 같은 값이 나옵니다.

<!--proof:origin-reuse-->

```text
l = 0, r = 4 까지의 합  5
− nums[0]               1
l = 1, r = 4 까지의 합  4  덧셈 4 번 대신 뺄셈 한 번
```

이제 두 방식을 같은 입력에 실제로 실행해 **창의 합을 고친 횟수**를 셉니다. 방식 A 는 시작점마다
처음부터 다시 더하는 것이고, 방식 B 는 이 글이 만들 절차로, 직전 합에 새 칸을 더하고 빠진 칸만 빼요.

<!--proof:origin-two-ways-->

| 방식 | 창의 합을 고친 횟수 | 답 |
| --- | ---: | ---: |
| A 시작점마다 처음부터 다시 더한다 | 25 | 5 |
| B 직전 합에서 빠진 칸만 뺀다 | 9 | 5 |

답은 둘 다 5 이고, 연산은 16 번 줄었습니다. 방식 B 에서 왼쪽 끝은 0 → 1 → 2 로만 움직였습니다.

<!--/proof-->

25 대 9 입니다. 여기서 관찰할 것은 **왼쪽 끝의 자취** 하나예요. 방식 B 에서 왼쪽 끝은 한 번도 왼쪽으로
되돌아가지 않았습니다. 그렇다면 합은 이어 쓰되 왼쪽 끝을 매번 0 으로 되돌려 다시 줄이는 가장 단순한
후보는 어떨까요. 그것까지 시험해 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

왼쪽 끝을 되돌리는 후보는 답은 맞지만 되돌린 칸을 다시 빼느라 연산이 늘었습니다. 되돌아갈 자리가
실제로 한 번도 없었으니 되돌리는 일 자체가 낭비예요. 남은 방법에 이름을 붙이면 **슬라이딩 윈도**입니다.
오른쪽 끝을 한 칸씩 넓히고, 창의 합이 `S` 를 넘는 동안만 왼쪽 끝을 오른쪽으로 옮기며, 왼쪽 끝은 절대
되돌리지 않아요. 창을 어떻게 적고, 넓히고, 줄이고, 답을 어떻게 고치는지는 다음 절에서 실현하는 순서대로
확인합니다.

### 아이디어 상세 — 슬라이딩 윈도

이 아이디어를 한 문장으로 줄이면 이렇습니다. **창 `[l, r]` 과 그 합을 들고 오른쪽 끝을 한 칸씩 넓히다가,
합이 `S` 를 넘으면 넘지 않을 때까지 왼쪽 끝을 오른쪽으로 옮기고, 그때마다 창의 길이로 답을 고칩니다.**
미리 만들어 두는 구조가 없어서 네 단계가 모두 오른쪽 끝 한 칸마다 되풀이돼요.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 창을 두 끝과 합으로 적기 | 창을 `l` · `r` 과 `windowSum` 으로 나타내고 빈 창에서 시작한다 | — |
| 2단계 오른쪽 끝 넓히기 | `r` 을 한 칸 옮기고 새 칸의 값을 창의 합에 더한다 | 1단계의 `windowSum` |
| 3단계 왼쪽 끝 옮기기 | 창의 합이 `S` 를 넘는 동안 `nums[l]` 을 빼고 `l` 을 한 칸 옮긴다 | 2단계에서 늘어난 창의 합 |
| 4단계 창의 길이로 답 고치기 | `r − l + 1` 이 `best` 보다 길면 `best` 를 바꾼다 | 3단계가 남긴 창 |

#### 1단계 — 창을 두 끝과 합으로 적기

창은 늘 이어진 한 구간이라 양 끝 두 인덱스로 적습니다. 창의 칸 수는 `r − l + 1` 이고, 창 안의 값을 더한
수를 `windowSum` 에 따로 들고 있어요. 합을 칸마다 다시 더하지 않으려고 두는 값입니다. 창이 칸을 담은
경우와 통째로 빈 경우를 하나씩 적으면 이렇습니다.

<!--proof:build-window-->

```text
창 [2,6]  l = 2, r = 6  칸 수 6 − 2 + 1 = 5  windowSum = 3    [1 2 1 0 1 1 0], S = 4 의 마지막 바퀴
빈 창     l = 1, r = 0  칸 수 0 − 1 + 1 = 0  windowSum = 0    [10 20 30], S = 5 의 첫 바퀴
```

빈 창은 `l = r + 1` 이고 칸 수가 정확히 `0` 으로 나와요. 그래서 빈 창을 따로 다루지 않아도 이 표기 하나로
「담은 칸 0 개」가 적힙니다. 처음에는 아직 아무 칸도 넣지 않았으니 `l = 0`, `windowSum = 0`, `best = 0`
에서 시작합니다. 창의 칸 수는 0 이상 `n` 이하이고, `windowSum` 은 비음의 정수의 합이라 0 이상이에요.

#### 2단계 — 오른쪽 끝 넓히기

오른쪽 끝을 한 칸 옮기면 창에 칸 하나가 들어오므로, 1단계의 `windowSum` 에 그 칸의 값 `nums[r]` 만
더합니다. 가장 쉬운 경우는 넓혔는데도 상한을 넘지 않을 때예요. 0 을 더하는 자리를 보겠습니다.

<!--proof:build-extend-->

```text
r = 2 → 3   창의 합 4 에 nums[3] = 0 을 더해 4
            4 > 4 가 거짓이라 줄이지 않는다
            l 은 0 그대로, 창의 값 1 2 1 0, 길이 3 → 4
            └ 합이 그대로인데 길이만 늘었다. 0 이 섞이면 이런 자리가 나온다
```

넓힌 창의 합이 `S` 이하면 창을 그대로 두고 4단계로 갑니다. 합이 `S` 를 넘었을 때가 다음 단계의 일이에요.

#### 3단계 — 왼쪽 끝 옮기기

2단계에서 합이 `S` 를 넘었다면 창이 조건을 어긴 것입니다. 조건이 다시 참이 될 때까지 `nums[l]` 을 빼고
`l` 을 한 칸 오른쪽으로 옮겨요. 합이 처음 넘는 자리에서 넓힌 직후와 줄인 뒤를 나란히 그리면 이렇습니다.

<!--fig:build-shrink-->
![r = 4 에서 넓힌 직후와 줄인 뒤 — nums[0] 을 빼고 l 이 1 로 간다](./figs/build-shrink.svg)

왼쪽에서 빠져나가는 값이 합에서 **정확히 한 번만** 빠지는지가 여기서 확인할 것입니다. 전개 입력에서 줄이기가
일어나는 자리는 둘이고, 둘 다 창의 값을 직접 더해 합과 대조했어요.

<!--proof:build-shrink-->

```text
r = 3 → 4  창의 합 4 에 nums[4] = 1 을 더해 5  5 > 4 가 참
           nums[0] = 1 을 빼서 4, l 을 0 → 1   4 > 4 가 거짓
           창의 값 2 1 0 1, 길이 4             합 4 는 실제로 2+1+0+1 이다

r = 4 → 5  창의 합 4 에 nums[5] = 1 을 더해 5  5 > 4 가 참
           nums[1] = 2 를 빼서 3, l 을 1 → 2   3 > 4 가 거짓
           창의 값 1 0 1 1, 길이 4             합 3 은 실제로 1+0+1+1 이다
```

빠뜨리는 칸이 없는 근거는 반복의 종료 조건입니다. 줄이기 반복은 합이 상한 이하가 될 때까지만 실행되고,
한 번 반복할 때마다 `nums[l]` 을 빼고 `l` 을 정확히 한 칸 늘려요. 그러니 `l` 이 지나온 칸은 전부 정확히 한
번씩 합에서 빠지고, 지나온 칸은 다시 창에 들어오지 않으므로 두 번 빠질 자리가 없습니다.

이 단계가 기대는 핵심 성질이 **왼쪽 끝은 되돌아가지 않는다**입니다. 오른쪽 끝을 `r` 로 고정했을 때 합이
`S` 이하가 되는 가장 왼쪽 자리를 `lo(r)` 이라고 부를게요. 창의 왼쪽 끝이 이 자리에 있을 때 창이 가장
깁니다. 모든 구간을 직접 재서 `lo(r)` 을 구하고, 정본이 3단계를 마친 뒤의 `l` 과 나란히 놓았습니다.

<!--proof:build-lo-->

| r | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| nums[r] | 1 | 2 | 1 | 0 | 1 | 1 | 0 |
| 정의로 구한 lo(r) | 0 | 0 | 0 | 0 | 1 | 2 | 2 |
| 정본의 l | 0 | 0 | 0 | 0 | 1 | 2 | 2 |
| 창의 합 | 1 | 3 | 4 | 4 | 4 | 3 | 3 |

lo(r) 의 줄은 한 번도 줄지 않고, 정본이 줄인 뒤의 l 과 7 칸 중 7 칸이 일치합니다.

<!--/proof-->

`lo(r)` 이 줄지 않으니 3단계는 직전 `l` 에서 이어서 오른쪽으로만 움직이면 됩니다. 되돌려서 더 왼쪽을
찾을 필요가 없어요. 이 성질이 모든 비음의 정수 배열에서 성립하는 까닭은 「수식 정의와 유도」에서 식으로
풉니다.

#### 4단계 — 창의 길이로 답 고치기

3단계를 마친 창은 합이 `S` 이하이고, 그 `r` 에서 가장 긴 창입니다. 그 길이 `r − l + 1` 이 `best` 보다
길면 `best` 를 바꿔요. 전개 입력에서 바퀴마다 창과 `best` 를 적으면 이렇습니다.

<!--proof:build-best-->

| r | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 창 [l, r] | [0,0] | [0,1] | [0,2] | [0,3] | [1,4] | [2,5] | [2,6] |
| 길이 r − l + 1 | 1 | 2 | 3 | 4 | 4 | 4 | 5 |
| best | 1 | 2 | 3 | 4 | 4 | 4 | 5 |

best 는 길이가 지금까지보다 길 때만 바뀌고, 마지막 값 5 가 답입니다.

<!--/proof-->

창이 빈 바퀴에서는 길이가 `0` 으로 나오고, `best` 가 `0` 에서 시작하므로 그 값은 답을 바꾸지 않아요.
조건을 만족하는 창이 하나도 없으면 `best` 가 끝까지 `0` 이고 그것이 답입니다.

#### 이 방법이 기대는 전제

슬라이딩 윈도는 아래 두 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 원소가 전부 비음의 정수다 | 3단계에서 왼쪽 끝을 되돌리지 않는다 | 오른쪽 끝을 넓혔는데 합이 줄 수 있어, 앞서 옮겨 둔 왼쪽 끝을 되돌려야 하는 자리가 생긴다 |
| 창의 값을 칸 하나씩 더하고 뺄 수 있다 | 2단계와 3단계가 `windowSum` 을 고친다 | 칸이 들고 날 때마다 창 전체를 다시 계산해야 해서, 모든 구간을 재는 방법의 비용으로 돌아간다 |

음수가 섞였을 때 이 절차가 다른 답을 내는 모습은 「수행으로 알아보는 알고리즘」의 「짚고 가기 — 음수가
하나 섞이면 이 절차가 다른 답을 낸다」에서 실행 결과로 볼 수 있습니다.

#### 왼쪽 끝을 되돌리지 않는 까닭

「아이디어를 떠올리는 과정」에서는 늘 처음으로 되돌리는 후보 하나만 보았습니다. 이제 왼쪽 끝을 오른쪽
끝을 넓힐 때마다 `K` 칸까지 되돌려 보는 절차를 만들고, `K` 를 넷으로 놓아 같은 입력에서 **기본 연산**(창의 합을
고치는 덧셈 한 번 · 뺄셈 한 번을 각각 1 로, 비교는 넣지 않습니다)을 셉니다. 되돌린 뒤의 줄이기 규칙은 3단계와 같아요.

<!--proof:cost-rewind-->

| 되돌림 폭 | 덧셈·뺄셈 | 답 |
| --- | ---: | ---: |
| K = 7 (늘 처음으로) | 15 | 5 |
| K = 2 | 15 | 5 |
| K = 1 | 13 | 5 |
| K = 0 | 9 | 5 |

답은 넷 모두 5 이고, 연산이 가장 적은 것은 K = 0 입니다.

<!--/proof-->

`K` 를 키울수록 연산이 늘고 답은 그대로입니다. `K = 2` 와 `K = 7` 이 같은 것은 이 입력에서 왼쪽 끝이
인덱스 2 를 넘어가지 않아 더 되돌릴 자리가 없기 때문이에요. 되돌린 칸은 3단계가 곧바로 다시 빼므로 더한
만큼 연산만 늘고, 답은 3단계의 종료 조건이 정하니 바뀌지 않습니다. 그래서 되돌림 폭은 0 입니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇습니다. 2단계부터 4단계가 반복 한 바퀴예요. 이렇게 하면 길이
100,000 배열에서 최악 50 억 번이던 덧셈이 창의 합을 고치는 연산 200,000 번 이하로 줄어듭니다.

1. `l = 0`, `windowSum = 0`, `best = 0` 으로 시작한다
2. `r` 을 0 부터 `n − 1` 까지 옮기며 `windowSum` 에 `nums[r]` 을 더한다
3. `windowSum > S` 인 동안 `nums[l]` 을 빼고 `l` 을 한 칸 옮긴다
4. `r − l + 1` 이 `best` 보다 길면 `best` 를 바꾸고, 배열 끝에서 `best` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 일곱 칸을 한 번씩 지나 답 5 를 만든다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다
그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const nums = [1, 2, 1, 0, 1, 1, 0];
const S = 4;
// 이 절이 끝나면 5 가 나와야 한다
```

왜 하필 이 입력일까요? 창을 줄이는 갈래와 줄이지 않는 갈래를 **둘 다 실행**하면서, `0` 이 섞여 있어
「합은 그대로인데 길이만 느는」 자리까지 지나가기 때문이에요. 답이 배열의 마지막 칸에서 바뀌는 것도 함께
확인됩니다. 창이 통째로 비는 자리는 이 입력으로는 안 나오므로, 3 번 걸음에서 다른 입력을 한 번 더 넣습니다.

```text
longestSubarrayAtMostSum(nums, S):
    l ← 0, windowSum ← 0, best ← 0
    r 을 0 부터 n-1 까지 옮기며:
        windowSum 에 nums[r] 을 더한다
        windowSum > S 인 동안:
            windowSum 에서 nums[l] 을 빼고 l 을 한 칸 옮긴다    ① 상한을 넘는다
        best ← max(best, r - l + 1)                            ② 상한 이하다
    best 를 반환한다
```

#### 1. 오른쪽 끝을 한 칸 넓힌다

창의 합을 매번 다시 더하지 않는 것이 이 조각의 전부입니다. 직전 값에 새로 들어온 칸의 값만 더해요.

```ts
let windowSum = 0;
let l = 0;
for (let r = 0; r < nums.length; r++) {
  windowSum += nums[r] as number;
}
```

이 조각만 실행하면 창의 합이 이렇게 쌓입니다. 아직 줄이는 부분이 없어서 왼쪽 끝은 0 에 그대로 있어요.

<!--proof:walk-extend-->

| r | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| nums[r] | 1 | 2 | 1 | 0 | 1 | 1 | 0 |
| windowSum | 1 | 3 | 4 | 4 | 5 | 6 | 6 |

r = 4 에서 처음으로 4 를 넘고, 그 뒤로는 줄지 않습니다.

<!--/proof-->

#### 2. 합이 상한을 넘으면 왼쪽 끝을 옮긴다

넘긴 자리를 그대로 두면 창이 조건을 어깁니다. 조건이 다시 참이 될 때까지 왼쪽 끝의 값을 빼면서 `l` 을
오른쪽으로 옮겨요.

```ts
while (windowSum > S) {
  // ① 상한을 넘는다 — 왼쪽 끝의 값을 빼고 l 을 한 칸 옮긴다
  windowSum -= nums[l] as number;
  l++;
}
```

합이 처음 넘는 자리에서 이 조각만 실행한 결과입니다. 한 번 빼자마자 조건이 거짓이 되어 반복이 끝나요.

<!--proof:walk-shrink-->

```text
들어올 때  windowSum = 5  l = 0  5 > 4 가 참이라 ① 을 실행한다
① 1 번째   windowSum = 4  l = 1  5 − nums[0] = 5 − 1 = 4
다시 검사  4 > 4 가 거짓         반복이 끝난다
            창의 값 2 1 0 1, 합 4
```

여기서 가장 중요한 줄은 `l++` 입니다. 이 줄이 없으면 같은 칸의 값을 몇 번이고 다시 빼서 창의 합이 창의
내용과 어긋나요. 값을 뺀 칸은 이미 창 밖으로 나간 칸입니다.

#### 짚고 가기 — 합이 상한과 같을 때 줄이면 전개 입력에서는 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 조건을 `>` 로 쓸지 `>=` 로 쓸지입니다. 「합이 상한과 같아지면 꽉 찼으니
줄여야 한다」로 읽기 쉬운데, 과제가 요구한 것은 **합이 `S` 이하**인 구간이에요. 같을 때는 조건을 지키고
있으므로 줄일 이유가 없습니다.

<!--proof:pause-equal-r2-->

```text
r = 2 에서 창의 합이 정확히 4 다

  > 로 비교하면   4 > 4 가 거짓  → 줄이지 않는다        → 창의 값 1 2 1, 길이 3
  >= 로 비교하면  4 >= 4 가 참   → nums[0] = 1 을 뺀다  → 창의 값 2 1, 길이 2
```

이 오해가 위험한 것은 **전개에 쓰는 입력에서 답이 안 틀리기 때문**입니다. 비교 연산자 한 글자만 바꾼
코드를 정본에서 만들어 두 코드를 각각 실행해 보면 이렇게 나와요.

<!--proof:pause-shrink-on-equal-->

| 입력 | S | > 로 비교 | >= 로 비교 | 두 답 |
| --- | ---: | ---: | ---: | --- |
| [1 2 1 0 1 1 0] | 4 | 5 | 5 | 같다 |
| [1 2 3 4 5] | 8 | 3 | 3 | 같다 |
| [1 2 1] | 4 | 3 | 2 | 다르다 |
| [4 4] | 4 | 1 | 0 | 다르다 |

네 입력 중 2 개에서는 이 변경을 넣어도 답이 그대로라 알아챌 수 없습니다.

<!--/proof-->

`[1 2 1]` 에서 정답은 3 인데 `>=` 는 2 를 냅니다. 전체 합이 정확히 4 라 배열 전체가 답인데, 그 창을
스스로 줄여 버린 것이에요. `[4 4]` 에서는 1 이 0 이 됩니다. 원소 하나짜리 창조차 남기지 못해서 「그런
구간이 없다」는 답이 나와요. 답이 같은 두 줄 때문에 테스트 몇 개로는 이 자리를 못 알아챌 수 있으니, 비교는
`>` 로 적습니다.

#### 3. 창의 길이를 답 후보로 삼는다

반복이 끝난 시점의 창은 조건을 지키고 있으므로 그 길이를 답 후보로 쓸 수 있습니다. 길이는 두 끝의
인덱스로 계산해요.

```ts
// ② 상한 이하다 — 줄일 것이 없다. 지금 창의 길이가 답 후보다
best = Math.max(best, r - l + 1);
```

창이 통째로 비는 자리에서 이 식이 무엇을 내는지 확인하고 갑시다. 모든 원소가 상한보다 큰 입력을 넣습니다.

<!--proof:walk-empty-->

```text
nums 의 값 10 20 30, S = 5 일 때 r = 0

  windowSum = 10, 10 > 5 가 참이라 ① 을 실행한다  nums[0] 을 빼서 0, l = 1
  창은 비었다                                     l = 1 이라 r = 0 보다 한 칸 크다
  r − l + 1 = 0 − 1 + 1 = 0                       길이가 0 으로 나온다. best 는 0 그대로다
```

왼쪽 끝이 오른쪽 끝을 한 칸 지나가면 창이 비고, 그때 길이가 **정확히 `0`** 으로 나옵니다. 창이 빈 뒤로는
합이 `0` 이라 `l` 이 더 갈 곳이 없어서 길이가 음수가 되지는 않아요.

#### 4. 배열 전체를 한 번 지나간다

세 조각을 하나로 이어 고정 입력에 실행하면 두 끝이 어떻게 움직이는지 값으로 확인됩니다. 걸음마다 괄호가
창이고, 대시 칸은 창 밖, ▲ 가 이번 걸음에 읽은 칸이에요. 뺀 칸과 더한 칸을 모두 읽은 칸으로 그렸습니다.

한 걸음마다 조건이 어떻게 판정되는지 전부 적으면 아래 여덟 단계입니다. 「더한 뒤 합」은 오른쪽 끝을 넓힌
직후의 값이고, 「줄인 뒤」는 왼쪽 끝을 옮긴 다음의 값이에요.

<!--proof:walk-trace-->

| 단계 | r | 더한 뒤 합 | 조건 판정 | 뺀 값 | 줄인 뒤 l | 줄인 뒤 합 | 길이 | best |
| --- | ---: | ---: | --- | --- | ---: | ---: | ---: | ---: |
| T1 | — | — | 루프 진입 전 | — | 0 | 0 | 0 | 0 |
| T2 | 0 | 1 | `1 > 4` **거짓** → ② | — | 0 | 1 | 1 | 1 |
| T3 | 1 | 3 | `3 > 4` **거짓** → ② | — | 0 | 3 | 2 | 2 |
| T4 | 2 | 4 | `4 > 4` **거짓** → ② | — | 0 | 4 | 3 | 3 |
| T5 | 3 | 4 | `4 > 4` **거짓** → ② | — | 0 | 4 | 4 | 4 |
| T6 | 4 | 5 | `5 > 4` **참** → ① | nums[0]=1 | 1 | 4 | 4 | 4 |
| T7 | 5 | 5 | `5 > 4` **참** → ① | nums[1]=2 | 2 | 3 | 4 | 4 |
| T8 | 6 | 3 | `3 > 4` **거짓** → ② | — | 2 | 3 | 5 | 5 |

**두 갈래가 모두 나왔습니다.** 반환값은 `best` 의 마지막 값인 5 이고, 갈래마다 실행된 자리와 기본 연산을
세면 이렇습니다.

<!--proof:walk-branches-->

```text
①  상한을 넘는다  T6 · T7               왼쪽 끝이 0 → 1 → 2 로 2 칸 움직였다
②  상한 이하다    T2 T3 T4 T5 T6 T7 T8  7 번 전부 길이를 재 봤다

연산 = 덧셈 7 (T2~T8) + 뺄셈 2 (T6 · T7) = 9
```

연산 9 는 「아이디어를 떠올리는 과정」의 방식 B 에서 센 값과 같습니다. 그 표가 센 것이 바로 이 여덟 걸음이에요.

#### 짚고 가기 — 음수가 하나 섞이면 이 절차가 다른 답을 낸다

여기서 헷갈리기 쉬운 포인트는 「연속 구간의 합이니 음수가 있어도 되겠지」입니다. 이 절차는 비음의 정수라는
조건에 **정면으로 기대고 있어요.** 음수가 있으면 오른쪽 끝을 넓혔을 때 합이 줄어들 수 있고, 그러면 앞서
옮겨 둔 왼쪽 끝을 되돌려야 하는 자리가 생깁니다.

<!--proof:pause-negative-trace-->

```text
nums 의 값 5 1 -5 1, S = 2

  이 절차           r = 0 에서 합 5 > 2 가 참이라 5 를 빼고 l 을 1 로 옮긴다
                    그 뒤로 l 은 1 에 머문다 → 가장 긴 창은 값 1 -5 1, 길이 3
  모든 구간을 재면  [0,3] 의 합은 5+1−5+1 = 2 ≤ 2 → 길이 4
                    └ 왼쪽 끝을 0 으로 되돌려야 찾을 수 있는 답이다
```

세 입력에 두 방식을 각각 실행해 확인합니다. 「모든 구간을 잰 답」은 모든 구간의 합을 직접 재서 가장 긴
것을 고른 값이에요.

<!--proof:pause-negative-->

| 입력 | S | 슬라이딩 윈도의 답 | 모든 구간을 잰 답 | 두 답 |
| --- | ---: | ---: | ---: | --- |
| [5 1 -5 1] | 2 | 3 | 4 | 다르다 |
| [3 -2 4] | 4 | 2 | 2 | 같다 |
| [1 2 1 0 1 1 0] | 4 | 5 | 5 | 같다 |

음수가 섞인 첫 줄에서만 답이 갈립니다. 둘째 줄이 이 오해가 오래 남는 이유예요. `[3 -2 4]` 는 음수가
있어도 왼쪽 끝을 되돌릴 필요가 없는 배치라 우연히 같은 답이 나옵니다. 그러니 「음수를 넣어 봤는데
맞더라」는 근거가 되지 않아요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `best` 를 `0` 으로 시작하는 한 줄과 마지막의
반환뿐이에요. 조건을 만족하는 구간이 하나도 없을 때 그 `0` 이 그대로 답이 됩니다.

```ts
export function longestSubarrayAtMostSum(nums: number[], S: number): number {
  let best = 0;
  // 창 [l, r] 안의 값을 더한 것. 매번 다시 더하지 않고 증분으로 유지한다.
  let windowSum = 0;
  let l = 0;

  for (let r = 0; r < nums.length; r++) {
    // 오른쪽 끝을 한 칸 넓히고 새로 들어온 값을 창의 합에 더한다.
    windowSum += nums[r] as number;

    while (windowSum > S) {
      // ① 합이 상한을 넘는다 — 왼쪽 끝의 값을 빼고 l 을 한 칸 오른쪽으로 옮긴다.
      windowSum -= nums[l] as number;
      l++;
    }

    // ② 합이 상한 이하다 — 줄일 것이 없다. 지금 창의 길이가 답 후보다.
    best = Math.max(best, r - l + 1);
  }

  return best;
}
```

<!--proof:final-calls-->

```text
longestSubarrayAtMostSum([1, 2, 1, 0, 1, 1, 0], 4)  →  5
longestSubarrayAtMostSum([10, 20, 30], 5)           →  0
longestSubarrayAtMostSum([0, 0, 0, 0], 0)           →  4
longestSubarrayAtMostSum([5], 10)                   →  1
```

### 알아 두면 좋은 개념 — 분할 상환 분석

전개의 T6 · T7 에서 왼쪽 끝이 한 칸씩 움직였습니다. 그런데 한 단계에서 여러 칸을 움직이는 일도 있어요.
큰 값 하나가 들어오면 창이 통째로 비워질 때까지 반복이 이어집니다. 단계 하나만 떼어 보면 최악이 `n` 칸인데,
**전체 합은 `n` 칸을 넘지 못합니다.** 전개의 걸음마다 뺄셈을 세면 이렇습니다.

<!--proof:related-amortized-->

| 단계 | T2 | T3 | T4 | T5 | T6 | T7 | T8 | 합 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 그 단계의 뺄셈 | 0 | 0 | 0 | 0 | 1 | 1 | 0 | 2 |
| 누적 뺄셈 | 0 | 0 | 0 | 0 | 1 | 2 | 2 | — |
| 단계별 최악 | 7 | 7 | 7 | 7 | 7 | 7 | 7 | 49 |

단계마다 최악 7 칸을 잡아 더하면 49 인데, 실제 뺄셈은 2 번입니다.

<!--/proof-->

이렇게 **단계별 최악을 곱하지 않고 전체 합으로 비용을 세는 방법**을 분할 상환 분석이라고 해요. 왼쪽 끝이
한 방향으로만 움직인다는 사실이 그 합의 상한을 `n` 으로 묶습니다.

```text
단계별 최악을 곱한다   한 단계 최대 n 칸 × n 단계 = n²      실제 값과 크게 벌어진다
전체 합으로 센다       l 은 0 에서 시작해 n 을 못 넘는다     합이 n 칸 이하다
                       └ 「비싼 단계」의 비용을 앞뒤 단계가 나눠 진 것으로 본다
```

같은 세는 법이 다른 곳에서도 나옵니다. 배열이 꽉 찼을 때 두 배로 늘리는 동적 배열은 한 번의 추가가 최악
`n` 이지만 `n` 번 추가의 총비용이 `2n` 이하이고, 유니온 파인드의 경로 압축도 한 번의 탐색이 아니라 연산
전체의 합으로 비용을 잽니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 왼쪽 끝이 되돌아가지 않는다는 것을 식으로
어떻게 적는지, 무엇이 매 단계 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **연속 구간**을 고르는 과제입니다. 원소를 골라 담는 과제라면 순서를 바꿀 수 있어서 이 절차가 성립하지
  않아요.
- 구간에 매기는 값이 **한 방향으로만 움직입니다.** 오른쪽 끝을 넓히면 늘기만 하고 왼쪽 끝을 옮기면 줄기만
  하는 것 — 비음의 정수 합이 그런 값입니다.
- **조건이 상한이나 하한 한쪽**입니다. 「합이 `S` 이하」처럼 한 방향이라야 왼쪽 끝을 어느 쪽으로 옮길지가
  정해져요.
- 답이 **구간의 길이나 개수**입니다. 구간 안의 순서나 배치가 답이면 창을 옮기는 것만으로는 답을 못
  만듭니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  연속 구간         → 인덱스 두 개 l 과 r 로 상태가 끝난다
  값이 한 방향      → l 을 되돌리는 코드가 아예 없다
  조건이 상한 한쪽  → while 의 조건이 windowSum > S 하나다
  답이 길이         → best 가 r − l + 1 만 본다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "연속된"  "부분 배열"  "구간"       ← 부분집합이 아니라 연속이라는 신호다
  "합이 K 이하"  "예산 안에서"  "가장 많이"
  "모든 값은 양의 정수"  "0 이상"      ← 한 방향으로만 움직인다는 조건이다

제약에 이런 모양이 보이면
  n 이 10^5 이상이라 O(n²) 이 못 들어간다
  값의 범위가 좁아 합이 정수 범위를 안 넘는다
```

반대로 **「음수가 포함될 수 있다」** 가 보이면 이 단서는 해당하지 않습니다. 그때는 접두사 합을 정렬하거나
자료구조에 넣어 푸는 다른 절차가 필요해요. 파트 1 의 두 번째 「짚고 가기」에서 값으로 확인한 자리입니다.

#### 실제로 쓰이는 곳

- **CPython 의 `textwrap`** — 폭 상한 안에서 연속된 조각을 최대한 많이 한 줄에 담습니다.
  `_wrap_chunks` 의 누적 검사가 `if cur_len + l <= width:` 한 줄이고, 넘으면 그 줄을 끊고
  다음 줄이 **그 뒤에서** 시작해요 — 왼쪽 끝이 되돌아가지 않는 것과 같은 자리입니다.
  ([`Lib/textwrap.py`](https://github.com/python/cpython/blob/main/Lib/textwrap.py), 조회 2026-08-29)
- **리눅스 커널 블록 계층의 `bio_add_page`** — 하나의 입출력 요청에 페이지를 이어 붙일 때
  누적 크기가 상한을 넘으면 더 붙이지 않고 거기서 끊습니다. 검사가
  `if (bio->bi_iter.bi_size > BIO_MAX_SIZE - len) return 0;` 한 줄이에요.
  ([`block/bio.c`](https://github.com/torvalds/linux/blob/master/block/bio.c), 조회 2026-08-29)

```text
두 사례와 이 과제의 차이

  두 사례   왼쪽 끝이 직전에 끊은 자리에 고정된다 → 오른쪽으로만 채운다
  이 과제   왼쪽 끝도 움직여 가장 긴 창 하나를 찾는다
            └ 그래도 왼쪽 끝이 되돌아가지 않는다는 성질은 같다
```

두 사례 모두 **한 줄·한 요청을 최대로 채우는** 자리이고, 배열 전체에서 가장 긴 구간 하나를 고르는 이
과제와는 목표가 다릅니다. **이 과제의 형태 그대로**를 쓰는 도입 사례는 1차 출처로 확인하지 못했어요.
확인한 것은 창을 오른쪽으로만 채우는 위 둘입니다.

### 수식 정의와 유도

구간의 합을 기호로 정의합니다.

$$\operatorname{sum}(l, r) = \sum_{k=l}^{r} nums[k]$$

<!--proof:math-sum-check-->

```text
정의를 값에 넣어 봅니다 — nums 의 값 1 2 1 0 1 1 0

  sum(0, 2)  = 1 + 2 + 1         = 4
  sum(1, 4)  = 2 + 1 + 0 + 1     = 4
  sum(5, 4)  = (더할 것이 없다)  = 0     l 이 r 보다 크면 빈 구간이다
```

다음은 창의 왼쪽 끝이 어디까지 갈 수 있는지입니다. 오른쪽 끝을 `r` 로 고정했을 때 조건을 만족하는 왼쪽
자리 중 가장 작은 것을 `lo(r)` 로 적어요.

$$\operatorname{lo}(r) = \min \{\, l \mid 0 \le l \le r+1,\ \operatorname{sum}(l, r) \le S \,\}$$

<!--proof:math-lo-candidates-->

```text
S = 4 이고 r = 4 일 때 후보가 되는 왼쪽 자리

  l = 0  sum(0,4) = 5  4 이하가 아니다   후보 아님
  l = 1  sum(1,4) = 4  4 이하다          후보. 이 중 가장 작으므로 lo(4) = 1
  l = 2  sum(2,4) = 2  4 이하다          후보
  l = 3  sum(3,4) = 1  4 이하다          후보
  l = 4  sum(4,4) = 1  4 이하다          후보
  l = 5  sum(5,4) = 0  빈 구간이라 언제나 후보
```

`l = r+1` 을 후보에 넣은 것이 이 정의의 요점이에요. 그때 구간이 비어 있어 합이 `0` 이므로, `S` 가 `0`
이상인 한 후보가 **항상 하나는 있습니다.** 정의를 그대로 코드로 옮기면 이렇습니다.

```ts
const lo = (nums: number[], S: number, r: number): number => {
  for (let l = 0; l <= r + 1; l++) {
    let sum = 0;
    for (let k = l; k <= r; k++) sum += nums[k] as number;
    if (sum <= S) return l;
  }
  return r + 1;
};
```

위 검산의 `lo(4) = 1` 은 「아이디어 상세」 3단계의 표에서 `r = 4` 칸에 나온 값과 같습니다. 그 표에서
`lo(r)` 의 줄이 한 번도 줄지 않았는데, 그것이 모든 비음의 정수 배열에서 참이라는 것이 이제 유도할
명제예요.

$$\operatorname{sum}(l, r+1) = \operatorname{sum}(l, r) + nums[r+1]$$

```text
nums[r+1] 이 0 이상이므로 sum(l, r+1) 은 sum(l, r) 이상이다

  sum(l, r) > S 였다면   →   sum(l, r+1) > S 도 참이다
                             └ S 보다 큰 수에 0 이상을 더해도 S 보다 크다
```

조건을 만족하는 왼쪽 자리를 모은 집합을 `A(r)` 이라고 두면, 방금 확인한 것은 「`r` 에서 탈락한 자리는
`r+1` 에서도 탈락한다」입니다. 집합이 줄기만 하니 그 최솟값은 늘기만 해요.

```text
A(r+1) ⊆ A(r)                 탈락한 자리는 되돌아오지 않는다
A(r) 은 비어 있지 않다         l = r+1 이 언제나 들어 있다
                              └ 두 집합 다 최솟값이 있고, 부분집합 쪽의 최솟값이
                                더 크거나 같다 → lo(r+1) ≥ lo(r)
```

$$\operatorname{lo}(0) \le \operatorname{lo}(1) \le \dots \le \operatorname{lo}(n-1)$$

왼쪽 끝의 이동 칸 수를 전부 더하면 중간 항이 서로 지워져 마지막 값에서 첫 값을 뺀 것만 남습니다.
`lo(0)` 은 `0` 이상이고 `lo(n-1)` 은 `n` 이하이므로 그 차이가 `n` 을 넘지 못해요.

```text
이동 칸 수의 합
  (lo(1) − lo(0)) + (lo(2) − lo(1)) + … + (lo(n−1) − lo(n−2))
= lo(n−1) − lo(0)                    중간 항이 전부 지워진다
≤ n − 0 = n
```

$$\text{기본 연산} = \underbrace{n}_{\text{덧셈}} + \underbrace{\operatorname{lo}(n-1) - \operatorname{lo}(0)}_{\text{뺄셈}} \le 2n$$

제약 규모를 넣으면 `n = 100,000` 에서 연산이 최대 200,000 번입니다. 시작점마다 다시 더하는 방법의 닫힌
형태 `n(n+1)/2` 와 나란히 놓고, 두 값을 모든 원소가 0 이고 `S = 0` 인 입력에서 실제 실행으로 확인했어요.

<!--proof:cost-scale-->

| n | 시작점마다 다시(실측) | n(n+1)/2 | 슬라이딩 윈도(실측) | n |
| ---: | ---: | ---: | ---: | ---: |
| 7 | 28 | 28 | 7 | 7 |
| 100 | 5,050 | 5,050 | 100 | 100 |
| 1,000 | 500,500 | 500,500 | 1,000 | 1,000 |
| 10,000 | 50,005,000 | 50,005,000 | 10,000 | 10,000 |
| 100,000 | (실행하지 않음) | 5,000,050,000 | 100,000 | 100,000 |

실측값이 닫힌 형태와 네 규모에서 정확히 같습니다. 오른쪽 두 열도 마찬가지예요. 모든 원소가 `0` 이면 왼쪽
끝이 한 번도 안 움직이므로 연산이 정확히 `n` 이고, 그것이 `2n` 상한의 아래쪽 끝입니다. 10 만에서 50 억과
10 만의 차이가 5 만 배예요.

### 불변식 — 바퀴가 끝날 때마다 windowSum 은 창의 합이고 S 이하다

파트 1 에서 코드가 동작하는 것을 여덟 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지
확인해 봅시다.

> **`r` 한 바퀴를 마친 시점마다**, `windowSum` 은 인덱스 `l` 부터 `r` 까지의 값을 더한 것과 같고 그 값이
> `S` 이하입니다. 그리고 `l` 은 그 시점에 조건을 만족하는 가장 왼쪽 자리입니다.

```text
       l                r
 ...   |──── 창 ────|   ...
       └ windowSum 이 이 구간의 합과 같다   ← 앞 문장
         그 값이 S 이하다                   ← 가운데 문장
         l−1 을 포함하면 S 를 넘는다        ← 뒤 문장
```

문장이 셋인 것에 이유가 있습니다. 앞 문장은 상태가 서로 어긋나지 않는다는 것이고, 가운데 문장은 답 후보가
조건을 지킨다는 것이며, 뒤 문장이 그 후보가 **가장 긴** 것임을 말해요. 셋 중 하나만 빠져도 답이 최댓값이라는
근거가 사라집니다.

**출발점부터 봅시다.** 루프에 들어가기 전 `l = 0` 이고 `windowSum = 0` 이라 창이 비어 있고, 「비어 있는
구간의 합은 `0`」 과 「`0 ≤ S`」 가 둘 다 참입니다. 그 뒤 한 바퀴마다 아래 일이 차례로 실행돼요.

| 하는 일 | 앞 문장이 유지되는 근거 | 가운데 문장이 유지되는 근거 |
| --- | --- | --- |
| `windowSum += nums[r]` | 창이 오른쪽으로 한 칸 늘었고 그 칸의 값을 정확히 한 번 더했다 | 아직 성립하지 않을 수 있다. 다음 갈래가 받는다 |
| 줄이기 반복이 실행된다 — `windowSum -= nums[l]` 뒤 `l++` | 창이 왼쪽에서 한 칸 줄었고 그 칸의 값을 정확히 한 번 뺐다 | 반복 조건이 거짓이 될 때까지 실행되므로 끝나면 `S` 이하다 |
| 줄이기 반복을 건너뛴다 | 상태를 안 바꾼다 | 조건이 이미 거짓이라 `S` 이하다 |

뒤 문장은 줄이기 반복의 종료 조건이 지킵니다. 반복이 끝난 순간 `windowSum` 은 `S` 이하인데, 직전 반복에서
나온 값 — 즉 `l-1` 을 포함한 창의 합 — 은 `S` 를 넘었어요. 반복이 한 번도 실행되지 않았다면 `l` 이
그대로이고, 「수식 정의와 유도」의 `lo(r+1) ≥ lo(r)` 에 따라 직전 바퀴의 가장 왼쪽 자리보다 왼쪽에는 후보가
없으므로 뒤 문장이 그대로 이어집니다.

경계에 있는 입력들도 확인하고 갑시다.

<!--proof:invariant-edges-->

| 입력 | 처리되는 자리 | 결과 |
| --- | --- | ---: |
| 원소 하나 [5], S = 10 | 줄이기 반복이 한 번도 실행되지 않는다 | 1 |
| 원소 하나 [5], S = 1 | 매 바퀴 창이 통째로 비워진다(뺄셈 1 번) | 0 |
| 전부 상한 초과 [10 20 30], S = 5 | 매 바퀴 창이 통째로 비워진다(뺄셈 3 번) | 0 |
| 전부 0 [0 0 0 0], S = 0 | 줄이기 반복이 한 번도 실행되지 않는다 | 4 |
| S 가 아주 큼 [100 100 100], S = 1,000,000,000 | 줄이기 반복이 한 번도 실행되지 않는다 | 3 |

**이제 깨뜨려 봅시다.** 가운데 문장을 지키던 줄은 줄이기 반복의 조건 `windowSum > S` 입니다. 「왼쪽 끝이
오른쪽 끝을 지나가면 안 된다」는 생각으로 그 조건에 `l < r` 을 더해 봅니다. 한 줄만 바뀝니다.

```ts
while (windowSum > S && l < r) { // ← 여기에 l < r 을 더했다
  windowSum -= nums[l] as number;
  l++;
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-left-guard-->

| 입력 | S | 바른 코드 | l < r 을 더한 코드 | 두 답 |
| --- | ---: | ---: | ---: | --- |
| [10 20 30] | 5 | 0 | 1 | 다르다 |
| [1 2 3] | 0 | 0 | 1 | 다르다 |
| [5] | 1 | 0 | 1 | 다르다 |
| [1 2 1 0 1 1 0] | 4 | 5 | 5 | 같다 |

네 입력 중 3 개에서 조건을 어기는 창의 길이가 답으로 나왔습니다.

<!--/proof-->

`l < r` 이 거짓이 되는 순간 반복이 멈추므로 `windowSum` 이 `S` 를 넘은 채로 남습니다. 가운데 문장이 성립하지
않는 상태에서 그 창의 길이를 답 후보로 삼은 것이고, 그래서 조건을 어기는 구간의 길이 `1` 이 답으로 나와요.

<!--proof:mutant-left-guard-trace-->

```text
nums 의 값 5, S = 1 에서 l < r 을 더하면

  r = 0  windowSum = 5                 5 > 1 은 참인데 l < r 이 0 < 0 이라 거짓
         반복이 아예 실행되지 않는다   windowSum = 5 가 남는다
         best = max(0, 0 − 0 + 1) = 1  합 5 인 창을 길이 1 로 세었다
         └ 바른 코드의 답은 0 이다. S = 1 인데 유일한 원소가 5 다
```

창이 비는 것은 막아야 할 일이 아니라 **답이 `0` 이라는 뜻**입니다. 왼쪽 끝이 오른쪽 끝을 한 칸 지나가면
길이가 `0` 으로 계산되고, `best` 가 그 값을 그냥 무시해요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 창의 합을 고치는 일은 두 종류뿐입니다. 오른쪽 끝을 넓히며 더하는 것과, 왼쪽 끝을 옮기며
빼는 것이에요. 전개의 걸음으로 세면 이렇습니다.

<!--proof:perf-derive-->

```text
덧셈  T2 T3 T4 T5 T6 T7 T8  r 이 0 부터 6 까지 한 칸씩 → 정확히 7 번
뺄셈  T6 · T7               l 이 0 → 1 → 2 로 → 2 번
      └ 합 9 번. 「아이디어를 떠올리는 과정」의 방식 B 와 같다
```

덧셈은 바퀴마다 정확히 하나이므로 `n` 번입니다. 뺄셈은 바퀴마다 몇 번일지 정해지지 않지만 전체 합이 왼쪽
끝의 총이동 칸 수와 같고, 그 값이 `n` 을 넘지 못해요.

```text
총식 = 덧셈 + 뺄셈 + 비교 + Math.max 호출
       └ n   └ l 의 총이동  └ 뺄셈 수 + n   └ n
             └ 0 이상 n 이하  └ n 이상 2n 이하

       총연산 ≤ n + n + 2n + n = 5n            전부 n 에 비례한다
       창의 합을 고치는 연산(덧셈 + 뺄셈)만 보면 n 이상 2n 이하다
```

여기서 센 것은 **창의 합을 고치는 연산과 그에 딸린 비교**입니다. 추가로 잡는 배열이 없어서 메모리는 변수
셋(`l`·`windowSum`·`best`)뿐이고, 입력 배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (왼쪽 끝이 한 번도 안 움직인다) | `O(n)` | `Θ(n)` |
| **평균적인 경우** (입력 분포와 무관하다) | `O(n)` | `Θ(n)` |
| **최악의 경우** (왼쪽 끝이 `n` 칸을 다 움직인다) | `O(n)` | `Θ(n)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 최선과 최악의 차이가 **상수 계수**에만 나타나요. 창의 합을 고치는
연산이 `n` 번이냐 `2n` 번이냐이고, `Θ` 는 그 상수를 보지 않습니다.

```text
기본 연산만 따로 보면 경계가 갈린다
  최선   n 번     원소가 전부 0 이라 왼쪽 끝이 한 번도 안 움직인다
  최악   2n 번    매 바퀴 왼쪽 끝이 한 칸씩 움직인다
         └ 둘 다 Θ(n) 이지만 실제 연산은 두 배 차이다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 없다는 것이 이 절차의 특징이에요. 정렬도
좌표압축도 접두사 합 배열도 만들지 않습니다.

```text
총식 = Θ(n) 시간 + Θ(1) 추가 메모리
       └ 전처리 0     └ 변수 세 개. 입력 배열은 읽기만 한다
```

<!--proof:perf-total-->

```text
n = 100,000 이면 창의 합을 고치는 연산이 최대 200,000 번, 추가 메모리는 입력 크기와 무관하게 일정하다
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에 대한 가정도
하지 않으니, 어떤 입력을 넣어도 창의 합을 고치는 연산이 `2n` 번을 넘지 않는다는 것이 그대로 약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
```

#### 최악을 만드는 입력

연산을 최대로 만들려면 **매 바퀴 왼쪽 끝이 움직이게** 하면 됩니다. 새로 들어오는 값이 늘 상한을 넘게 하면
그렇게 돼요. 모든 원소를 `1` 로 두고 `S = 0` 으로 잡는 것이 가장 짧은 구성입니다.

<!--proof:worst-trace-->

```text
nums 의 값 1 1 1 1 1 1, S = 0

  r = 0  더해서 1  1 > 0 이라 빼서 0, l = 1  길이 0 − 1 + 1 = 0
  r = 1  더해서 1  1 > 0 이라 빼서 0, l = 2  길이 1 − 2 + 1 = 0
  …     바퀴마다 덧셈 1 + 뺄셈 1
        └ 답은 0 이고, 답이 0 인 채로 배열 끝까지 간다
```

`n = 1,000` 에서 세 입력의 기본 연산을 실제로 셌습니다.

<!--proof:worst-counts-->

| 입력(n = 1,000) | 덧셈·뺄셈 | n 의 배수 | 답 |
| --- | ---: | ---: | ---: |
| 전부 0 · S = 0 | 1,000 | 1.0n | 1,000 |
| 전부 1 · S = n | 1,000 | 1.0n | 1,000 |
| 전부 1 · S = 0 | 2,000 | 2.0n | 0 |

가장 많은 것은 「전부 1 · S = 0」의 2,000 번입니다.

<!--/proof-->

**「값이 크면 느리다」는 이 절차에서 거짓입니다.** 둘째 줄이 그것을 말해요. 원소가 전부 `1` 이어도 `S` 가
넉넉하면 왼쪽 끝이 한 번도 안 움직여 `1.0n` 입니다. 기본 연산을 정하는 것은 값의 크기가 아니라 **왼쪽 끝이
몇 칸 움직이는가**예요. 제약 규모의 최악에서도 연산이 200,000 번이라 예산 1 초보다 한참 적습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 모든 구간을 하나씩 재던 것을 **창 하나를 오른쪽으로 옮기는
것**으로 바꿨고, 원소가 비음의 정수라 왼쪽 끝이 되돌아가지 않으며, 답이 최댓값인 근거는 세 문장짜리
불변식입니다.

```text
오른쪽 끝을 넓혀 더한다 → 상한을 넘는 동안 왼쪽 끝을 옮겨 뺀다 → 길이를 답 후보로 삼는다
        └ 덧셈 n 번          └ 뺄셈 합쳐서 n 번 이하        └ best 가 최댓값을 들고 있다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 에서 `nums[3] = 0` 을 더했는데 창의 합이 그대로였어요. 그러면
이 걸음에서 `best` 는 왜 바뀌었을까요?

<!--proof:selfcheck-t4-t5-->

```text
T4  값 1 2 1    windowSum = 4  길이 3  best = 3
T5  값 1 2 1 0  windowSum = 4  길이 4  best = 4    ← 합은 같은데 best 가 늘었다
```

<!--check:zero-extends-->
`best` 가 보는 것은 합이 아니라 **길이**이기 때문입니다. `0` 을 더하면 합은 그대로인데 오른쪽 끝이 한 칸
오른쪽으로 갔으므로 `r - l + 1` 이 하나 늘어요. `0` 이 섞인 입력에서 답이 길어지는 이유가 이것이고, 원소가
전부 `0` 이면 `S = 0` 에서도 답이 배열 전체 길이가 되는 이유이기도 합니다.

<!--proof:selfcheck-length-->

```text
T4  r = 2  l = 0  r − l + 1 = 2 − 0 + 1 = 3
T5  r = 3  l = 0  r − l + 1 = 3 − 0 + 1 = 4
        └ l 이 그대로이고 r 만 늘었으니 길이가 정확히 1 늘어난다
```
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「수행으로 알아보는 알고리즘」의 T6 · T7, 「최악을 만드는
입력」, 「불변식」을 다시 보세요.

- T6 과 T7 에서 뺄셈이 각각 한 번씩이었습니다. 한 걸음에서 뺄셈이 세 번 일어나는 입력을 원소 다섯 개
  이내로 만들어 보세요.
- 원소가 전부 `1` 이고 `S = 0` 인 입력이 연산 `2n` 번을 쓰는데, 답은 `0` 입니다. 답이 `0` 이 아니면서
  연산이 `2n` 에 가까운 입력을 만들 수 있을까요?
- 불변식의 뒤 문장(「`l-1` 을 포함하면 `S` 를 넘는다」)이 없어도 답이 최댓값이라고 말할 수 있는지 확인해
  보세요. 없으면 무엇을 못 말하게 되는지가 답입니다.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### Longest Subarray with Sum at Most S

풀 파일: [`longestSubarrayAtMostSum.ts`](./longestSubarrayAtMostSum.ts) · 테스트: [`longestSubarrayAtMostSum.test.ts`](./longestSubarrayAtMostSum.test.ts) · 실행: `bun test src/algorithms/array/longestSubarrayAtMostSum/longestSubarrayAtMostSum.test.ts`

#### 한 줄 요약

> 비음의 정수 배열과 상한 $S$를 받아, **합이 $S$ 이하인 연속 부분 배열 중 가장 긴 것의 길이**를 반환한다.

#### 스토리

영양사 소연은 하루 칼로리 예산 $S$ 킬로칼로리 안에서 연속된 음식 메뉴를 최대한 많이 골라야 한다. 메뉴 목록은 순서가 고정되어 있고, 건너뛸 수 없다.

소연은 어느 위치에서 시작해 어느 위치에서 멈출지를 정해, 그 구간의 메뉴를 모두 고를 때 칼로리 합이 $S$를 넘지 않으면서 가장 많은 메뉴를 포함하려 한다.

이 조건을 만족하는 최대 메뉴 수를 구하는 함수를 작성해야 한다.

#### 함수 인터페이스

```ts
export function longestSubarrayAtMostSum(nums: number[], S: number): number;
```

- `nums` — 비음의 정수 배열. `nums[i]`는 $i$번째 메뉴의 칼로리.
- `S` — 합의 상한 (비음의 정수).
- 반환 — 합이 $S$ 이하인 연속 부분 배열의 최대 길이. 그러한 부분 배열이 없으면 `0`.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `nums`의 길이)
- $0 \leq nums[i] \leq 10{,}000$ (비음의 정수)
- $0 \leq S \leq 10^9$ (비음의 정수)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

인덱스 구간 $[l, r]$ ($0 \leq l \leq r < N$)의 합을

$$\text{sum}(l, r) = \sum_{k=l}^{r} nums[k]$$

로 정의하면, 답은

$$\max\{\, r - l + 1 \mid 0 \leq l \leq r < N,\; \text{sum}(l, r) \leq S \,\}$$

이다.

모든 단일 원소가 $S$를 초과하면 합 조건을 만족하는 부분 배열이 없으므로 $0$을 반환한다. `nums`의 모든 원소가 $0$이면 전체 길이가 답이 된다.

#### 예시

```ts
longestSubarrayAtMostSum([1, 2, 1, 0, 1, 1, 0], 4); // 5  — 인덱스 [1,5] 합=1+0+1+1+0=3
longestSubarrayAtMostSum([1, 1, 1, 1, 1], 3);       // 3  — 어느 연속 세 원소든 합=3
longestSubarrayAtMostSum([1, 2, 3], 10);            // 3  — 전체 합 6 ≤ 10

longestSubarrayAtMostSum([5, 6, 7], 4);             // 0  — 단일 원소도 S 초과
longestSubarrayAtMostSum([1, 2, 3], 0);             // 0  — S=0이고 모든 원소 양수

longestSubarrayAtMostSum([0, 0, 0, 0], 0);          // 4  — 모든 원소 0, 전체 길이
longestSubarrayAtMostSum([5], 10);                  // 1  — 단일 원소, 조건 충족
longestSubarrayAtMostSum([5], 1);                   // 0  — 단일 원소, 조건 초과
```
