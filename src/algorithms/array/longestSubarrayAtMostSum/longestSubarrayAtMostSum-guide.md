# longestSubarrayAtMostSum — 왼쪽 끝을 한 번도 되돌리지 않아도 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 모든 구간을 하나씩 재는
방법에서 두 끝을 한 번씩만 옮기는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열에서 **연속된 한 토막**을 고르되, 그 토막에 든 값의 합이 상한 `S` 를 넘지 않으면서 가장
길게 고르는 문제예요. 고른 토막을 **창**이라고 부르고, 창의 두 끝을 `l`(왼쪽 끝) 과
`r`(오른쪽 끝) 로 적습니다.

```text
nums 의 값   1  2  1  0  1  1  0        S = 4
인덱스       0  1  2  3  4  5  6
             └───── [0,3] ─────┘        합 4 ≤ 4, 길이 4
                   └────── [2,6] ──────┘  합 3 ≤ 4, 길이 5   ← 이쪽이 더 길다
```

이 문제 전체를 정하는 것은 **원소가 전부 비음의 정수**라는 조건입니다. 그 덕분에 창의 합이
한 방향으로만 움직여요 — 오른쪽 끝을 넓히면 합이 줄지 않고, 왼쪽 끝을 오른쪽으로 옮겨 값을
빼면 합이 늘지 않습니다.

```text
r 을 한 칸 넓힌다   [l, r] → [l, r+1]    합에 nums[r+1] 을 더한다   합은 줄지 않는다
l 을 한 칸 옮긴다   [l, r] → [l+1, r]    합에서 nums[l] 을 뺀다     합은 늘지 않는다
```

여기서 결론 하나가 따라옵니다. 오른쪽 끝을 한 칸 넓혔을 때 **왼쪽 끝을 왼쪽으로 되돌릴
이유가 없어요.** 왼쪽으로 다시 옮기면 창은 길어지지만 합도 함께 늘어서, 방금 상한을 넘겨
줄여 둔 자리를 다시 넘기기 때문입니다.

```text
r=3 에서 합이 4 이하가 되는 가장 왼쪽 자리는 l=0
r=4 로 넓히면 합이 5 가 되어 l 을 1 로 옮긴다
r=5 로 넓히면 합이 다시 5 가 되어 l 을 2 로 옮긴다
      └ l 은 한 번도 왼쪽으로 되돌아가지 않는다. 0 → 1 → 2 로만 간다
```

그래서 오른쪽 끝은 `n` 칸을 한 번 지나가고 왼쪽 끝도 많아야 `n` 칸을 한 번 지나갑니다. 두 끝을
합쳐 최대 `2n` 번만 움직이니 전체 연산이 배열 길이에 비례해요 — `O(n)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **연속 부분 배열**이 무엇인지. 인덱스 `l` 부터 `r` 까지를 **건너뛰지 않고** 전부 고른 것이고,
  원소를 골라 담는 부분집합과 다릅니다.
- **구간 합**이 무엇인지. 그 구간에 든 값을 전부 더한 수예요. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 를 먼저 봅니다.
- **비음의 정수**라는 말의 뜻 — `0` 이거나 `0` 보다 큰 정수입니다. 이 조건 하나가 이 글의
  전부를 떠받치므로 여기서 확인하고 갑니다.
- 배열을 한 번 지나가는 `for` 루프와, 조건이 참인 동안 반복하는 `while` 루프.

「가장 긴 구간을 찾는다」와 「가장 큰 합을 찾는다」는 다른 문제입니다. 뒤쪽은
[`kadane`](../kadane/kadane-problem.md) 이 다루는 것이고, 이 글은 **길이**를 최대로 만듭니다.

```text
[1 2 1 0 1 1 0] 에서
  합이 가장 큰 구간          [0,6] 합 6   길이 7    ← 상한이 없으면 배열 전체다
  합 4 이하인 가장 긴 구간   [2,6] 합 3   길이 5    ← 이 글이 찾는 것
       └ 합이 4 인 구간도 있지만([0,3]) 길이가 4 라 답이 아니다
```

### 아이디어 상세 — 왼쪽 끝을 되돌리지 않는 방법을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function longestSubarrayAtMostSum(nums: number[], S: number): number;
```

- 입력: 비음의 정수 배열 `nums` 와 합의 상한 `S`.
- 출력: 합이 `S` 이하인 연속 부분 배열 중 가장 긴 것의 길이. 그런 것이 없으면 `0`.
- 제약: `1 ≤ n ≤ 100,000`, `0 ≤ nums[i] ≤ 10,000`, `0 ≤ S ≤ 10^9`. 시간 1초.

이 글이 쓰는 기호는 다섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 배열 `nums` 의 길이 | `n ≤ 100,000` |
| `S` | 창의 합에 걸린 상한 | `0 ≤ S ≤ 10^9` |
| `l` · `r` | 창의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함하는 구간입니다 | `0 ≤ l ≤ r+1`, `0 ≤ r < n` |
| `windowSum` | 창 안의 값을 더한 수. 글에서는 「창의 합」, 코드에서는 `windowSum` 으로 씁니다 | `0` 이상 |
| `best` | 지금까지 찾은 가장 긴 창의 길이. 이 값이 답이 됩니다 | `0 ≤ best ≤ n` |

가장 먼저 떠오르는 방법으로 시작합시다. 시작점 `l` 을 하나 정하고 끝점 `r` 을 오른쪽으로
늘려 가며 합을 재는 것을, 모든 시작점에 대해 되풀이하는 것이에요.

```ts
let best = 0;
for (let l = 0; l < n; l++) {
  let sum = 0;
  for (let r = l; r < n; r++) {
    sum += nums[r];
    if (sum > S) break;    // 비음의 정수라 더 늘려도 합이 줄지 않는다
    best = Math.max(best, r - l + 1);
  }
}
```

이 방법의 비용은 시작점·끝점 쌍의 수입니다. `break` 가 한 번도 실행되지 않는 입력 — 모든
원소가 `0` 이고 `S = 0` 인 경우 — 을 넣으면 쌍이 전부 나와요.

| `n` | 시작점·끝점 쌍의 수 | 초당 1억 번 기준 |
| --- | --- | --- |
| 1,000 | 500,500 | 0.005초 |
| 10,000 | 50,005,000 | 0.5초 |
| **100,000** | **5,000,050,000** | **50초** |

50억 번입니다. 단순 연산을 초당 1억 번으로 잡아도 50초가 넘어요. 제약이 10만인데 이 방법으로는
1초 안에 못 끝냅니다. 그러면 이 50억 안에 같은 일을 몇 번이나 되풀이하는지 봅시다. 원소 일곱
개짜리 입력을 하나 잡고 시작점을 옮겨 가며 무엇을 다시 더하는지 적습니다.

```text
nums 의 값   1  2  1  0  1  1  0      S = 4
인덱스       0  1  2  3  4  5  6

l=0 이 더한 것   1 → 3 → 4 → 4 → 5    합이 4 를 넘어 여기서 멈춘다
l=1 이 더한 것   2 → 3 → 3 → 4 → 5    인덱스 1~5 를 처음부터 다시 더했다
l=2 가 더한 것   1 → 1 → 2 → 3 → 3    인덱스 2~6 을 또 처음부터 다시 더했다
```

`l=1` 의 줄은 인덱스 1부터 5까지를 새로 더했는데, `l=0` 의 줄이 그 구간을 이미 더해 뒀어요.
직전 줄의 합에서 `nums[0]` 하나만 빼면 같은 값이 나옵니다.

```text
l=0, r=4 까지의 합   5
          − nums[0]  1
l=1, r=4 까지의 합   4        덧셈 다섯 번 대신 뺄셈 한 번
```

이제 두 방식을 같은 입력에 실제로 실행해 **창의 합을 고치는 연산 수**를 셉니다. 방식 A 는
시작점마다 처음부터 다시 더하는 것이고, 방식 B 는 직전 결과에서 값 하나를 빼는 것이에요.

<!--proof:cost-two-ways-->

```text
시작점  더한 횟수  멈춘 이유
l=0             5  합이 4 를 넘었다
l=1             5  합이 4 를 넘었다
l=2             5  배열 끝에 도착했다
l=3             4  배열 끝에 도착했다
l=4             3  배열 끝에 도착했다
l=5             2  배열 끝에 도착했다
l=6             1  배열 끝에 도착했다

방식 A  시작점마다 다시 더한다   덧셈 25 번   답 5
방식 B  왼쪽 끝을 되돌리지 않는다  덧셈·뺄셈 9 번   답 5
        └ 답은 같고 연산만 16 번 줄었다
```

25 대 9 입니다. 답은 둘 다 5 로 같은데 연산이 16 번 줄었어요. 여기서 관찰할 것은 **왼쪽 끝의
자취** 하나입니다 — 방식 B 에서 왼쪽 끝은 0 · 1 · 2 로만 갔고 한 번도 되돌아가지 않았어요.

그 관찰을 개념으로 세웁니다. 오른쪽 끝을 `r` 로 고정했을 때 **합이 `S` 이하가 되는 가장 왼쪽
자리**를 `lo(r)` 이라고 부를게요. 창의 왼쪽 끝은 이 자리에 있을 때 가장 길어집니다.

```text
가장 단순한 후보부터 시험합니다 — "r 을 옮길 때마다 lo(r) 을 0 부터 다시 찾는다"

  그러면 r 마다 배열의 앞쪽을 다시 읽는다 → 방식 A 와 같은 25 번이다
  그런데 방식 B 의 자취가 말하는 것은 다르다 → lo 는 되돌아가지 않았다
```

`lo(r)` 을 이 입력의 일곱 자리에 걸음마다 실제로 계산해 봅시다. 각 `r` 에 대해 합이 4 이하가
되는 가장 왼쪽 자리를 찾고, 그때의 창 길이 `r - lo(r) + 1` 을 함께 적습니다.

| `r` | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `nums[r]` | 1 | 2 | 1 | 0 | 1 | 1 | 0 |
| `lo(r)` | 0 | 0 | 0 | 0 | 1 | 2 | 2 |
| 창의 합 | 1 | 3 | 4 | 4 | 4 | 3 | 3 |
| `r - lo(r) + 1` | 1 | 2 | 3 | 4 | 4 | 4 | **5** |

`lo` 의 줄이 `0 0 0 0 1 2 2` 로 **한 번도 줄지 않습니다.** 그래서 왼쪽 끝은 직전 자리에서
이어서 오른쪽으로만 움직이면 되고, 각 상태 변수의 이동 범위가 그 자리에서 정해져요.

```text
r    0 부터 n−1 까지 한 방향으로만 이동한다        → 정확히 n 칸
l    lo(0)=0 에서 lo(n−1) 까지 한 방향으로만       → 0 칸 이상 n 칸 이하
     └ 위 표에서 실제로 0 → 1 → 2 로 2 칸 움직였다. n=7 이므로 7 칸 이하다
```

창의 합도 매번 다시 더하지 않고 **직전 값에서 고치기만** 합니다. 쉬운 경우와 불안한 경우를
나눠서 값으로 확인해 봅시다. 쉬운 경우는 넓혔는데도 상한을 안 넘을 때예요.

```text
r=2 → r=3   창의 합 4 에 nums[3]=0 을 더해 4        상한 4 를 안 넘는다
            l 은 0 그대로, 창의 값 1 2 1 0, 길이 3 → 4
            └ 합이 그대로인데 길이만 늘었다. 0 이 섞이면 이런 자리가 나온다
```

불안한 경우는 넓혔더니 상한을 넘어서 왼쪽 끝을 옮겨야 할 때입니다. 왼쪽에서 빠져나가는 값이
합에서 정확히 한 번만 빠지는지가 여기서 확인할 것이에요.

```text
r=3 → r=4   창의 합 4 에 nums[4]=1 을 더해 5        상한 4 를 넘었다
            nums[0]=1 을 빼서 4, l 을 0 → 1        더 뺄 것이 없다
            창의 값 2 1 0 1, 길이 4                합 4 는 실제로 2+1+0+1 이다

r=4 → r=5   창의 합 4 에 nums[5]=1 을 더해 5        또 넘었다
            nums[1]=2 를 빼서 3, l 을 1 → 2
            창의 값 1 0 1 1, 길이 4                합 3 은 실제로 1+0+1+1 이다
```

왜 빠뜨리는 칸이 없는지는 루프의 종료 조건으로 말할 수 있습니다. 왼쪽 끝을 옮기는 반복은
합이 상한 이하가 될 때까지만 실행되고, 한 번 반복할 때마다 `nums[l]` 을 빼고 `l` 을 정확히
한 칸 늘려요. 그러니 `l` 이 지나온 칸은 전부 정확히 한 번씩 합에서 빠집니다.

```text
l 이 0 → 1 → 2 로 갈 때 합에서 빠진 값
  l=0 → 1   nums[0] = 1 을 한 번
  l=1 → 2   nums[1] = 2 를 한 번
       └ 인덱스 0 과 1 은 다시 창에 들어오지 않으므로 두 번 빠질 자리가 없다
```

이제 「되돌리지 않는다」가 정말 가장 적은 연산인지 값으로 확인합니다. 왼쪽 끝을 `K` 칸까지
되돌리는 절차를 따로 만들어 `K` 를 넷으로 두고 같은 입력에서 연산 수를 셌어요.

<!--proof:cost-rewind-->

```text
되돌림 폭            덧셈·뺄셈  답
K=7 (항상 처음으로)         15   5
K=2                         15   5
K=1                         13   5
K=0                          9   5

└ 답은 넷 다 같고 연산 수만 다르다. 가장 적은 것은 되돌리지 않는 K=0 이다
```

`K` 를 키울수록 연산이 늘고 답은 그대로입니다. `K=2` 와 `K=7` 이 같은 것은 이 입력에서 왼쪽
끝이 인덱스 2 를 넘어가지 않아 더 되돌릴 자리가 없기 때문이에요. **되돌림 폭 0 이 답입니다.**

```text
얻은 절차 한 벌
  1. 오른쪽 끝을 한 칸 넓히고 그 값을 창의 합에 더한다
  2. 창의 합이 S 를 넘는 동안, 왼쪽 끝의 값을 빼고 왼쪽 끝을 한 칸 옮긴다
  3. 지금 창의 길이를 답 후보로 삼는다
       └ 10만 개 입력에서 50억 번이던 연산이 20만 번 이하가 된다
```

### 수행으로 알아보는 알고리즘 — 일곱 칸을 한 번씩만 지나 답 5를 만든다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const nums = [1, 2, 1, 0, 1, 1, 0];
const S = 4;
// 이 절이 끝나면 5 가 나와야 한다
```

왜 하필 이 입력일까요? 창을 줄이는 갈래와 줄이지 않는 갈래를 **둘 다 실행**하면서, `0` 이
섞여 있어 「합은 그대로인데 길이만 느는」 자리까지 지나가기 때문이에요. 답이 배열의 마지막
칸에서 갱신되는 것도 함께 확인됩니다.

```text
반복 한 바퀴가 하는 일

    r 을 한 칸 오른쪽으로 옮긴다
    창의 합에 nums[r] 을 더한다
    창의 합이 S 를 넘는 동안:
        창의 합에서 nums[l] 을 빼고 l 을 한 칸 오른쪽으로 옮긴다   ① 넘는다
    창의 길이 r − l + 1 이 지금까지보다 길면 best 를 갱신한다      ② 넘지 않는다
```

#### 1. 오른쪽 끝을 한 칸 넓힌다

창의 합을 매번 다시 더하지 않는 것이 이 조각의 전부입니다. 직전 값에 새로 들어온 칸의 값만
더해요.

```ts
let windowSum = 0;
let l = 0;
for (let r = 0; r < nums.length; r++) {
  windowSum += nums[r] as number;
}
```

이 조각만 실행하면 창의 합이 이렇게 쌓입니다. 아직 줄이는 부분이 없어서 왼쪽 끝은 0 에
그대로 있어요.

```text
r          0   1   2   3   4   5   6
nums[r]    1   2   1   0   1   1   0
windowSum  1   3   4   4   5   6   6
                           ↑ 여기서 처음으로 S=4 를 넘는다
```

#### 2. 합이 상한을 넘으면 왼쪽 끝을 옮긴다

넘긴 자리를 그대로 두면 창이 조건을 어깁니다. 조건이 다시 참이 될 때까지 왼쪽 끝의 값을
빼면서 `l` 을 오른쪽으로 옮겨요.

```ts
while (windowSum > S) {
  // ① 상한을 넘는다 — 왼쪽 끝의 값을 빼고 l 을 한 칸 옮긴다
  windowSum -= nums[l] as number;
  l++;
}
```

`r=4` 에서 이 조각만 실행한 결과입니다. 한 번 빼자마자 조건이 거짓이 되어 반복이 끝나요.

```text
들어올 때   windowSum=5  l=0        5 > 4 가 참이라 ① 을 실행한다
① 한 번     windowSum=4  l=1        5 − nums[0] = 5 − 1 = 4
다시 검사   4 > 4 가 거짓            반복이 끝난다
            창의 값 2 1 0 1, 합 4
```

여기서 가장 중요한 줄은 `l++` 입니다. 이 줄이 없으면 같은 칸의 값을 몇 번이고 다시 빼서 창의
합이 창의 내용과 어긋나요. 값을 뺀 칸은 이미 창 밖으로 나간 칸입니다.

#### 짚고 가기 — 합이 상한과 같을 때 줄이면 이 입력에서는 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 조건을 `>` 로 쓸지 `>=` 로 쓸지입니다. 「합이 상한과 같아지면
꽉 찼으니 줄여야 한다」로 읽기 쉬운데, 문제가 요구한 것은 **합이 `S` 이하**인 구간이에요.
같을 때는 조건을 지키고 있으므로 줄일 이유가 없습니다.

```text
r=2 에서 창의 합이 정확히 4 다

  > 로 비교하면   4 > 4 가 거짓 → 줄이지 않는다 → 창의 값 1 2 1, 길이 3
  >= 로 비교하면  4 >= 4 가 참  → nums[0] 을 뺀다 → 창의 값 2 1, 길이 2
```

이 오해가 위험한 것은 **전개에 쓰는 입력에서 답이 안 틀리기 때문**입니다. 두 비교 연산자로
각각 실행해 보면 이렇게 나와요.

<!--proof:pause-shrink-on-equal-->

```text
입력             S  > 로 비교  >= 로 비교
[1 2 1 0 1 1 0]  4          5           5  답이 같다
[1 2 3 4 5]      8          3           3  답이 같다
[1 2 1]          4          3           2  답이 다르다
[4 4]            4          1           0  답이 다르다

└ 위의 둘은 답이 같아서 이 변경을 넣어도 알아채지 못한다
```

`[1 2 1]` 에서 정답은 3 인데 `>=` 는 2 를 냅니다. 전체 합이 정확히 4 라 배열 전체가 답인데,
그 창을 스스로 줄여 버린 것이에요. `[4 4]` 에서는 1 이 0 이 됩니다 — 원소 하나짜리 창조차
남기지 못해서 「그런 구간이 없다」는 답이 나와요.

#### 3. 창의 길이를 답 후보로 삼는다

반복이 끝난 시점의 창은 조건을 지키고 있으므로 그 길이를 답 후보로 쓸 수 있습니다. 길이는
두 끝의 인덱스로 계산해요.

```ts
// ② 상한 이하다 — 줄일 것이 없다. 지금 창의 길이가 답 후보다
best = Math.max(best, r - l + 1);
```

창이 통째로 비는 자리에서 이 식이 무엇을 내는지 확인하고 갑시다. 왼쪽 끝이 오른쪽 끝을 한
칸 지나가면 창이 비는데, 그때 길이가 **정확히 `0`** 으로 나옵니다.

```text
nums 의 값 10 20 30, S = 5 일 때 r=0

  windowSum=10, 10 > 5 라 ① 을 실행한다   nums[0] 을 빼서 0, l=1
  창은 비었다                              l=1 이라 r 보다 한 칸 크다
  r − l + 1 = 0 − 1 + 1 = 0               길이가 0 으로 나온다
       └ 창이 빈 뒤로는 l 이 더 갈 곳이 없어 길이가 음수가 되지는 않는다
         best 는 0 에서 시작하므로 Math.max 가 이 값을 그대로 무시한다
```

#### 4. 배열 전체를 한 번 지나간다

세 조각을 하나로 이어 고정 입력에 실행하면 두 끝이 어떻게 움직이는지 값으로 확인됩니다.
분기 `①`·`②` 가 각각 어디서 실행되는지도 함께 적었어요.

<!--viz:slide-->
```text
T1  창 없음        l=0 r=−   windowSum=0  best=0   루프에 들어가기 전
T2  값 1           l=0 r=0   windowSum=1  best=1   1>4 거짓 → ②
T3  값 1 2         l=0 r=1   windowSum=3  best=2   3>4 거짓 → ②
T4  값 1 2 1       l=0 r=2   windowSum=4  best=3   4>4 거짓 → ②
T5  값 1 2 1 0     l=0 r=3   windowSum=4  best=4   4>4 거짓 → ②
T6  값 2 1 0 1     l=1 r=4   windowSum=4  best=4   5>4 참 → ① 뒤 ②
T7  값 1 0 1 1     l=2 r=5   windowSum=3  best=4   5>4 참 → ① 뒤 ②
T8  값 1 0 1 1 0   l=2 r=6   windowSum=3  best=5   3>4 거짓 → ②
```

<!--result:slide=5-->

한 걸음마다 조건이 어떻게 판정되는지 전부 적으면 아래 여덟 단계입니다. 「더한 뒤」는 오른쪽
끝을 넓힌 직후의 값이고, 「줄인 뒤」는 왼쪽 끝을 옮긴 다음의 값이에요.

| 단계 | `r` | 더한 뒤 | 조건 판정 | 뺀 값 | 줄인 뒤 `l` | 줄인 뒤 합 | 길이 | `best` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| T1 | — | — | 루프 진입 전 | — | `0` | `0` | `0` | `0` |
| T2 | 0 | `1` | `1 > 4` **거짓** → ② | — | `0` | `1` | `1` | `1` |
| T3 | 1 | `3` | `3 > 4` **거짓** → ② | — | `0` | `3` | `2` | `2` |
| T4 | 2 | `4` | `4 > 4` **거짓** → ② | — | `0` | `4` | `3` | `3` |
| T5 | 3 | `4` | `4 > 4` **거짓** → ② | — | `0` | `4` | `4` | `4` |
| T6 | 4 | `5` | `5 > 4` **참** → ① | `nums[0]=1` | `1` | `4` | `4` | `4` |
| T7 | 5 | `5` | `5 > 4` **참** → ① | `nums[1]=2` | `2` | `3` | `4` | `4` |
| T8 | 6 | `3` | `3 > 4` **거짓** → ② | — | `2` | `3` | `5` | **`5`** |

**두 갈래가 모두 나왔습니다.** ① 은 T6·T7 에서 한 번씩 실행됐고 ② 는 T2부터 T8까지 일곱 번
실행됐어요. 반환값은 `best` 의 마지막 값인 5 입니다.

```text
①  상한을 넘는다      T6 · T7               왼쪽 끝이 0 → 1 → 2 로 두 칸 움직였다
②  상한 이하다        T2 T3 T4 T5 T6 T7 T8  일곱 번 전부 길이를 재 봤다

연산 = 덧셈 7 (T2~T8) + 뺄셈 2 (T6·T7) = 9
       └ 「아이디어 상세」의 방식 B 에서 센 9 와 같은 값이다
```

#### 짚고 가기 — 음수가 하나 섞이면 이 절차가 다른 답을 낸다

여기서 헷갈리기 쉬운 포인트는 「연속 구간의 합이니 음수가 있어도 되겠지」입니다. 이 절차는
비음의 정수라는 조건에 **정면으로 기대고 있어요.** 음수가 있으면 오른쪽 끝을 넓혔을 때 합이
줄어들 수 있고, 그러면 앞서 옮겨 둔 왼쪽 끝을 되돌려야 하는 자리가 생깁니다.

```text
nums 의 값 5 1 −5 1, S = 2

  이 절차     r=0 에서 합 5 > 2 라 5 를 빼고 l 을 1 로 옮긴다
              그 뒤로 l 은 1 에 머문다 → 가장 긴 창은 값 1 −5 1, 길이 3
  정의 그대로 [0,3] 의 합은 5+1−5+1 = 2 ≤ 2 → 길이 4
              └ 왼쪽 끝을 0 으로 되돌려야 찾을 수 있는 답이다
```

세 입력에 두 방식을 각각 실행해 확인합니다.

<!--proof:pause-negative-->

```text
입력             S  두 포인터  정의 그대로
[5 1 -5 1]       2          3            4  다르다
[3 -2 4]         4          2            2  같다
[1 2 1 0 1 1 0]  4          5            5  같다

└ 음수가 섞인 첫 줄에서만 갈린다. 나머지 둘은 전부 비음의 정수다
```

둘째 줄이 이 오해가 오래 남는 이유입니다 — 음수가 있어도 답이 맞는 입력이 있어요. `[3 -2 4]`
는 왼쪽 끝을 되돌릴 필요가 없는 배치라 우연히 같은 답이 나옵니다. 그러니 「음수를 넣어 봤는데
맞더라」는 근거가 되지 않아요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `best` 를 `0` 으로 시작하는
한 줄뿐이에요 — 조건을 만족하는 구간이 하나도 없을 때 그 값이 그대로 답이 됩니다.

```ts
export function longestSubarrayAtMostSum(nums: number[], S: number): number {
  let best = 0;
  // 창 [l, r] 안의 값을 더한 것. 매번 다시 더하지 않고 증분으로 유지한다.
  let windowSum = 0;
  let l = 0;

  for (let r = 0; r < nums.length; r++) {
    // 오른쪽 끝을 한 칸 넓히고 새로 들어온 값을 창의 합에 더한다.
    windowSum += nums[r] as number;

    while (windowSum > S) {
      // ① 합이 상한을 넘는다 — 왼쪽 끝의 값을 빼고 l 을 한 칸 오른쪽으로 옮긴다.
      windowSum -= nums[l] as number;
      l++;
    }

    // ② 합이 상한 이하다 — 줄일 것이 없다. 지금 창의 길이가 답 후보다.
    best = Math.max(best, r - l + 1);
  }

  return best;
}
```

```text
longestSubarrayAtMostSum([1, 2, 1, 0, 1, 1, 0], 4)  →  5
longestSubarrayAtMostSum([10, 20, 30], 5)           →  0
longestSubarrayAtMostSum([0, 0, 0, 0], 0)           →  4
longestSubarrayAtMostSum([5], 10)                   →  1
```

### 알아 두면 좋은 개념 — 분할 상환 분석

전개의 T6·T7 에서 왼쪽 끝이 한 칸씩 움직였습니다. 그런데 한 단계에서 여러 칸을 움직이는 일도
있어요 — 큰 값 하나가 들어오면 창이 통째로 비워질 때까지 반복이 이어집니다. 단계 하나만
떼어 보면 최악이 `n` 칸인데, **전체 합은 `n` 칸을 넘지 못합니다.**

| 단계 | T2 | T3 | T4 | T5 | T6 | T7 | T8 | 합 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 그 단계의 뺄셈 | 0 | 0 | 0 | 0 | 1 | 1 | 0 | **2** |
| 누적 뺄셈 | 0 | 0 | 0 | 0 | 1 | 2 | 2 | — |
| 단계별 최악을 곱하면 | 7 | 7 | 7 | 7 | 7 | 7 | 7 | 49 |

단계마다 최악을 잡아 곱하면 49 가 나오는데 실제 값은 2 입니다. 이렇게 **단계별 최악을 곱하지
않고 전체 합으로 비용을 세는 방법**을 분할 상환 분석이라고 해요. 왼쪽 끝이 한 방향으로만
움직인다는 사실이 그 합의 상한을 `n` 으로 묶습니다.

```text
단계별 최악을 곱한다   한 단계 최대 n 칸 × n 단계 = n²      실제 값과 크게 벌어진다
전체 합으로 센다       l 은 0 에서 시작해 n 을 못 넘는다     합이 n 칸 이하다
                       └ 「비싼 단계」의 비용을 앞뒤 단계가 나눠 진 것으로 본다
```

같은 세는 법이 다른 곳에서도 나옵니다. 배열이 꽉 찼을 때 두 배로 늘리는 동적 배열은 한 번의
추가가 최악 `n` 이지만 `n` 번 추가의 총비용이 `2n` 이하이고, 유니온 파인드의 경로 압축도 한
번의 탐색이 아니라 연산 전체의 합으로 비용을 잽니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 왼쪽 끝이 되돌아가지 않는다는
것을 식으로 어떻게 적는지, 무엇이 매 단계 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **연속 구간**을 고르는 문제입니다. 원소를 골라 담는 문제라면 순서를 바꿀 수 있어서 이
  절차가 성립하지 않아요.
- 구간에 매기는 값이 **한 방향으로만 움직입니다.** 오른쪽 끝을 넓히면 늘기만 하고 왼쪽 끝을
  옮기면 줄기만 하는 것 — 비음의 정수 합이 그런 값입니다.
- **조건이 상한이나 하한 한쪽**입니다. 「합이 `S` 이하」처럼 한 방향이라야 왼쪽 끝을 어느
  쪽으로 옮길지가 정해져요.
- 답이 **구간의 길이나 개수**입니다. 구간 안의 순서나 배치가 답이면 창을 옮기는 것만으로는
  답을 못 만듭니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  연속 구간          → 인덱스 두 개 l 과 r 로 상태가 끝난다
  값이 한 방향        → l 을 되돌리는 코드가 아예 없다
  조건이 상한 한쪽    → while 의 조건이 windowSum > S 하나다
  답이 길이           → best 가 r − l + 1 만 본다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "연속된"  "부분 배열"  "구간"       ← 부분집합이 아니라 연속이라는 신호다
  "합이 K 이하"  "예산 안에서"  "가장 많이"
  "모든 값은 양의 정수"  "0 이상"      ← 한 방향으로만 움직인다는 조건이다

제약에 이런 모양이 보이면
  n 이 10^5 이상이라 O(n²) 이 못 들어간다
  값의 범위가 좁아 합이 정수 범위를 안 넘는다
```

반대로 **「음수가 포함될 수 있다」** 가 보이면 이 단서는 해당하지 않습니다. 그때는 접두사 합을
정렬하거나 자료구조에 넣어 푸는 다른 절차가 필요해요. 파트 1 의 두 번째 멈춤에서 값으로
확인한 자리입니다.

#### 실제로 쓰이는 곳

- **CPython 의 `textwrap`** — 폭 상한 안에서 연속된 조각을 최대한 많이 한 줄에 담습니다.
  `_wrap_chunks` 의 누적 검사가 `if cur_len + l <= width:` 한 줄이고, 넘으면 그 줄을 끊고
  다음 줄이 **그 뒤에서** 시작해요 — 왼쪽 끝이 되돌아가지 않는 것과 같은 자리입니다.
  ([`Lib/textwrap.py`](https://github.com/python/cpython/blob/main/Lib/textwrap.py), 조회 2026-08-29)
- **리눅스 커널 블록 계층의 `bio_add_page`** — 하나의 입출력 요청에 페이지를 이어 붙일 때
  누적 크기가 상한을 넘으면 더 붙이지 않고 거기서 끊습니다. 검사가
  `if (bio->bi_iter.bi_size > BIO_MAX_SIZE - len) return 0;` 한 줄이에요.
  ([`block/bio.c`](https://github.com/torvalds/linux/blob/master/block/bio.c), 조회 2026-08-29)

```text
두 사례와 이 문제의 차이

  두 사례   왼쪽 끝이 직전에 끊은 자리에 고정된다 → 오른쪽으로만 채운다
  이 문제   왼쪽 끝도 움직여 가장 긴 창 하나를 찾는다
            └ 그래도 왼쪽 끝이 되돌아가지 않는다는 성질은 같다
```

두 사례 모두 **한 줄·한 요청을 최대로 채우는** 자리이고, 배열 전체에서 가장 긴 구간 하나를
고르는 이 문제와는 목표가 다릅니다. **이 문제의 형태 그대로**를 쓰는 도입 사례는 1차 출처로
확인하지 못했어요. 확인한 것은 창을 오른쪽으로만 채우는 위 둘입니다.

### 수식 정의와 유도

구간의 합을 기호로 정의합니다.

$$\operatorname{sum}(l, r) = \sum_{k=l}^{r} nums[k]$$

```text
정의를 값에 넣어 봅니다 — nums 의 값 1 2 1 0 1 1 0

  sum(0, 2) = 1 + 2 + 1         = 4
  sum(1, 4) = 2 + 1 + 0 + 1     = 4
  sum(5, 4) = (더할 것이 없다)  = 0     l 이 r 보다 크면 빈 구간이다
```

다음은 창의 왼쪽 끝이 어디까지 갈 수 있는지입니다. 오른쪽 끝을 `r` 로 고정했을 때 조건을
만족하는 왼쪽 자리 중 가장 작은 것을 `lo(r)` 로 적어요.

$$\operatorname{lo}(r) = \min \{\, l \mid 0 \le l \le r+1,\ \operatorname{sum}(l, r) \le S \,\}$$

```text
S = 4 이고 r = 4 일 때 후보가 되는 왼쪽 자리

  l = 0   sum(0,4) = 5   4 이하가 아니다   후보 아님
  l = 1   sum(1,4) = 4   4 이하다          후보. 이 중 가장 작으므로 lo(4) = 1
  l = 2   sum(2,4) = 2   4 이하다          후보
  l = 3   sum(3,4) = 1   4 이하다          후보
  l = 4   sum(4,4) = 1   4 이하다          후보
  l = 5   sum(5,4) = 0   빈 구간이라 언제나 후보
```

`l = r+1` 을 후보에 넣은 것이 이 정의의 요점이에요. 그때 구간이 비어 있어 합이 `0` 이므로,
`S` 가 `0` 이상인 한 후보가 **항상 하나는 있습니다.** 식의 `lo` 를 코드에서는 `lo` 로 그대로
쓰고, 정의를 그대로 옮기면 이렇습니다.

```ts
const lo = (nums: number[], S: number, r: number): number => {
  for (let l = 0; l <= r + 1; l++) {
    let sum = 0;
    for (let k = l; k <= r; k++) sum += nums[k] as number;
    if (sum <= S) return l;
  }
  return r + 1;
};
```

위 검산의 `lo(4) = 1` 은 파트 1 의 표에서 `r=4` 칸에 적은 값과 같습니다. `r` 을 0 부터 6 까지
넣으면 `0 0 0 0 1 2 2` 가 나오고, **그 줄이 한 번도 줄지 않는다**는 것이 이제 유도할 명제예요.

$$\operatorname{sum}(l, r+1) = \operatorname{sum}(l, r) + nums[r+1]$$

```text
nums[r+1] 이 0 이상이므로 sum(l, r+1) 은 sum(l, r) 이상이다

  sum(l, r) > S 였다면   →   sum(l, r+1) > S 도 참이다
                             └ S 보다 큰 수에 0 이상을 더해도 S 보다 크다
```

조건을 만족하는 왼쪽 자리를 모은 집합을 `A(r)` 이라고 두면, 방금 확인한 것은 「`r` 에서
탈락한 자리는 `r+1` 에서도 탈락한다」입니다. 집합이 줄기만 하니 그 최솟값은 늘기만 해요.

```text
A(r+1) ⊆ A(r)                 탈락한 자리는 되돌아오지 않는다
A(r) 은 비어 있지 않다         l = r+1 이 언제나 들어 있다
                              └ 두 집합 다 최솟값이 있고, 부분집합 쪽의 최솟값이
                                더 크거나 같다 → lo(r+1) ≥ lo(r)
```

$$\operatorname{lo}(0) \le \operatorname{lo}(1) \le \dots \le \operatorname{lo}(n-1)$$

왼쪽 끝의 이동 칸 수를 전부 더하면 중간 항이 서로 지워져 마지막 값에서 첫 값을 뺀 것만
남습니다. `lo(0)` 은 `0` 이상이고 `lo(n-1)` 은 `n` 이하이므로 그 차이가 `n` 을 넘지 못해요.

```text
이동 칸 수의 합
  (lo(1) − lo(0)) + (lo(2) − lo(1)) + … + (lo(n−1) − lo(n−2))
= lo(n−1) − lo(0)                    중간 항이 전부 지워진다
≤ n − 0 = n
```

$$\text{연산 수} = \underbrace{n}_{\text{덧셈}} + \underbrace{\operatorname{lo}(n-1) - \operatorname{lo}(0)}_{\text{뺄셈}} \le 2n$$

제약 규모를 넣으면 `n = 100,000` 에서 연산이 최대 200,000 번입니다. 시작점마다 다시 더하는
방법의 닫힌 형태 `n(n+1)/2` 와 나란히 놓고, 두 값을 실제 실행으로 확인했어요.
<!--proof:cost-scale-->

```text
      n  시작점마다 다시(실측)       n(n+1)/2  두 포인터(실측)        n
      7                     28             28                7        7
    100                  5,050          5,050              100      100
  1,000                500,500        500,500            1,000    1,000
 10,000             50,005,000     50,005,000           10,000   10,000
100,000        (실행하지 않음)  5,000,050,000          100,000  100,000
```

실측값이 닫힌 형태와 네 규모에서 정확히 같습니다. 오른쪽 두 열도 마찬가지예요 — 모든 원소가
`0` 이면 왼쪽 끝이 한 번도 안 움직이므로 연산이 정확히 `n` 이고, 그것이 `2n` 상한의 아래쪽
끝입니다. 10만에서 50억과 10만의 차이가 5만 배예요.

### 불변식 — 단계가 끝날 때마다 windowSum 은 창의 합이고 S 이하다

파트 1 에서 코드가 동작하는 것을 여덟 단계로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 단계 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> `r` 한 바퀴를 마친 시점마다, `windowSum` 은 인덱스 `l` 부터 `r` 까지의 값을 더한 것과 같고
> 그 값이 `S` 이하입니다. 그리고 `l` 은 그 시점에 조건을 만족하는 가장 왼쪽 자리입니다.

```text
       l                r
 ...   |──── 창 ────|   ...
       └ windowSum 이 이 구간의 합과 같다   ← 앞 문장
         그 값이 S 이하다                   ← 가운데 문장
         l−1 을 포함하면 S 를 넘는다        ← 뒤 문장
```

문장이 셋인 것에 이유가 있습니다. 앞 문장은 상태가 서로 어긋나지 않는다는 것이고, 가운데
문장은 답 후보가 조건을 지킨다는 것이며, 뒤 문장이 그 후보가 **가장 긴** 것임을 말해요.
셋 중 하나만 빠져도 답이 최댓값이라는 근거가 사라집니다.

**출발점부터 봅시다.** 루프에 들어가기 전 `l = 0` 이고 `windowSum = 0` 이라 창이 비어 있고,
「비어 있는 구간의 합은 `0`」 과 「`0 ≤ S`」 가 둘 다 참입니다. 그 뒤 한 바퀴마다 두 갈래 중
하나가 실행돼요.

| 하는 일 | 앞 문장이 유지되는 근거 | 가운데 문장이 유지되는 근거 |
| --- | --- | --- |
| `windowSum += nums[r]` | 창이 오른쪽으로 한 칸 늘었고 그 칸의 값을 정확히 한 번 더했다 | 아직 성립하지 않을 수 있다. 다음 갈래가 받는다 |
| 줄이기 반복이 실행된다 — `windowSum -= nums[l]` 뒤 `l++` | 창이 왼쪽에서 한 칸 줄었고 그 칸의 값을 정확히 한 번 뺐다 | 반복 조건이 거짓이 될 때까지 실행되므로 끝나면 `S` 이하다 |
| 줄이기 반복을 건너뛴다 | 상태를 안 바꾼다 | 조건이 이미 거짓이라 `S` 이하다 |

뒤 문장은 줄이기 반복의 종료 조건이 지킵니다. 반복이 끝난 순간 `windowSum` 은 `S` 이하인데, 직전
반복에서 나온 값 — 즉 `l-1` 을 포함한 창의 합 — 은 `S` 를 넘었어요. 반복이 한 번도 실행되지
않았다면 `l` 이 그대로이므로 직전 단계의 뒤 문장이 그대로 이어집니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 원소 하나 `[5]`, `S=10` | 줄이기 반복이 한 번도 실행되지 않는다 | `1` |
| 원소 하나 `[5]`, `S=1` | 줄이기 반복이 한 번 실행되어 `l=1`, 길이 `0` | `0` |
| 전부 상한 초과 `[10 20 30]`, `S=5` | 매 단계 창이 통째로 비워진다 | `0` |
| 전부 `0` 인 `[0 0 0 0]`, `S=0` | 줄이기 반복이 한 번도 실행되지 않는다 | `4` |
| `S` 가 아주 큼 | 줄이기 반복이 한 번도 실행되지 않아 창이 배열 전체가 된다 | `n` |

**이제 깨뜨려 봅시다.** 가운데 문장을 지키던 줄은 줄이기 반복의 조건 `windowSum > S` 입니다. 「왼쪽 끝이 오른쪽
끝을 지나가면 안 된다」는 생각으로 그 조건에 `l < r` 을 더해 봅니다. 한 줄만 바뀝니다.

```ts
while (windowSum > S && l < r) {
  windowSum -= nums[l] as number;
  l++;
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-left-guard-->

```text
입력             S  바른 코드  l < r 을 더한 코드
[10 20 30]       5          0                   1
[1 2 3]          0          0                   1
[5]              1          0                   1
[1 2 1 0 1 1 0]  4          5                   5

└ 앞의 셋은 답이 될 수 없는 창의 길이를 답으로 냈다. 마지막 줄만 우연히 같다
```

`l < r` 이 거짓이 되는 순간 반복이 멈추므로 `windowSum` 이 `S` 를 넘은 채로 남습니다. 가운데
문장이 성립하지 않는 상태에서 그 창의 길이를 답 후보로 삼은 것이고, 그래서 조건을 어기는
구간의 길이 `1` 이 답으로 나와요.

```text
nums 의 값 5, S = 1 에서 l < r 을 더하면

  r=0  windowSum=5   5 > 1 은 참인데 l < r 이 0 < 0 이라 거짓
       반복이 아예 실행되지 않는다        windowSum=5 가 남는다
       best = max(0, 0 − 0 + 1) = 1      합 5 인 창을 길이 1 로 세었다
            └ 정답은 0 이다. S=1 인데 유일한 원소가 5 다
```

창이 비는 것은 막아야 할 일이 아니라 **답이 `0` 이라는 뜻**입니다. 왼쪽 끝이 오른쪽 끝을
한 칸 지나가면 길이가 `0` 으로 계산되고, `best` 가 그 값을 그냥 무시해요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 두 종류뿐입니다 — 오른쪽 끝을 넓히며 더하는 것과, 왼쪽 끝을 옮기며
빼는 것이에요. 전개의 값으로 확인하면 덧셈은 T2부터 T8까지 일곱 번이고 뺄셈은 T6·T7 두
번이었습니다.

```text
덧셈   T2 T3 T4 T5 T6 T7 T8    r 이 0 부터 6 까지 한 칸씩 → 정확히 7 번
뺄셈   T6 · T7                 l 이 0 → 1 → 2 로          → 2 번
                               └ 합 9 번. 「아이디어 상세」의 방식 B 와 같다
```

덧셈은 단계마다 정확히 하나이므로 `n` 번입니다. 뺄셈은 단계마다 몇 번일지 정해지지 않지만
전체 합이 왼쪽 끝의 총이동 칸 수와 같고, 그 값이 `n` 을 넘지 못해요.

```text
총식 = 덧셈 + 뺄셈 + 비교 + Math.max 호출
       └ n   └ l 의 총이동  └ 뺄셈 수 + n   └ n
             └ 0 이상 n 이하  └ n 이상 2n 이하

       총연산 ≤ n + n + 2n + n = 5n            전부 n 에 비례한다
       창의 합을 고치는 연산(덧셈 + 뺄셈)만 보면 n 이상 2n 이하다
```

여기서 센 것은 **창의 합을 고치는 연산과 그에 딸린 비교**입니다. 추가로 잡는 배열이 없어서
메모리는 변수 셋(`l`·`windowSum`·`best`)뿐이고, 입력 배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (왼쪽 끝이 한 번도 안 움직인다) | `O(n)` | `Θ(n)` |
| **평균적인 경우** (입력 분포와 무관하다) | `O(n)` | `Θ(n)` |
| **최악의 경우** (왼쪽 끝이 `n` 칸을 다 움직인다) | `O(n)` | `Θ(n)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 최선과 최악의 차이가 **상수 계수**에만 나타나요 —
연산이 `n` 번이냐 `2n` 번이냐이고, `Θ` 는 그 상수를 보지 않습니다.

```text
연산 수만 따로 보면 경계가 갈린다
  최선   n 번     원소가 전부 0 이라 왼쪽 끝이 한 번도 안 움직인다
  최악   2n 번    매 단계 왼쪽 끝이 한 칸씩 움직인다
         └ 둘 다 Θ(n) 이지만 실제 연산은 두 배 차이다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 없다는 것이 이 절차의 특징이에요 —
정렬도 좌표압축도 접두사 합 배열도 만들지 않습니다.

```text
총식 = Θ(n) 시간 + Θ(1) 추가 메모리
       └ 전처리 0     └ 변수 세 개. 입력 배열은 읽기만 한다

n = 100,000 이면 연산이 최대 200,000 번, 추가 메모리는 입력 크기와 무관하게 일정하다
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에
대한 가정도 하지 않으니, 어떤 입력을 넣어도 연산이 `2n` 번을 넘지 않는다는 것이 그대로
약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
```

#### 최악을 만드는 입력

연산을 최대로 만들려면 **매 단계 왼쪽 끝이 움직이게** 하면 됩니다. 새로 들어오는 값이 늘
상한을 넘게 하면 그렇게 돼요 — 모든 원소를 `1` 로 두고 `S = 0` 으로 잡는 것이 가장 짧은
구성입니다.

```text
nums 의 값 1 1 1 … 1, S = 0

  r=0   더해서 1   1 > 0 이라 빼서 0, l=1     길이 0 − 1 + 1 = 0
  r=1   더해서 1   1 > 0 이라 빼서 0, l=2     길이 0
  …                                           매 단계 덧셈 1 + 뺄셈 1
        └ 답은 0 이고, 답이 0 인 채로 배열 끝까지 간다
```

`n = 1,000` 에서 세 입력의 연산 수를 실제로 셌습니다.

<!--proof:worst-counts-->

```text
입력 (n=1,000)  덧셈·뺄셈  n 으로 나누면     답
전부 0 · S=0        1,000           1.0n  1,000
전부 1 · S=n        1,000           1.0n  1,000
전부 1 · S=0        2,000           2.0n      0

└ 마지막 줄이 최대다. 매 단계 왼쪽 끝이 한 칸씩 움직여 l 의 이동이 n 칸을 채운다
```

**「값이 크면 느리다」는 이 절차에서 거짓입니다.** 둘째 줄이 그것을 말해요 — 원소가 전부 `1`
이어도 `S` 가 넉넉하면 왼쪽 끝이 한 번도 안 움직여 `1.0n` 입니다. 연산 수를 정하는 것은 값의
크기가 아니라 **왼쪽 끝이 몇 칸 움직이는가**예요.

```text
n = 100,000 의 최악이면 연산 200,000 번
  1 초 제한에 견주면 여유가 크다. 이 절차에서 시간 초과가 나면 원인은 다른 곳이다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 모든 구간을 하나씩 재던 것을 **창 하나를
오른쪽으로 옮기는 것**으로 바꿨고, 원소가 비음의 정수라 왼쪽 끝이 되돌아가지 않으며, 답이
최댓값인 근거는 세 문장짜리 불변식입니다.

```text
오른쪽 끝을 넓혀 더한다 → 상한을 넘는 동안 왼쪽 끝을 옮겨 뺀다 → 길이를 답 후보로 삼는다
        └ 덧셈 n 번          └ 뺄셈 합쳐서 n 번 이하        └ best 가 최댓값을 들고 있다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 에서 `nums[3] = 0` 을 더했는데 창의 합이 4 그대로
였어요. 그러면 이 단계에서 `best` 는 왜 바뀌었을까요?

```text
T4  값 1 2 1     windowSum=4  길이 3  best=3
T5  값 1 2 1 0   windowSum=4  길이 4  best=4    ← 합은 같은데 best 가 늘었다
```

<!--check:zero-extends-->
`best` 가 보는 것은 합이 아니라 **길이**이기 때문입니다. `0` 을 더하면 합은 그대로인데 오른쪽
끝이 한 칸 오른쪽으로 갔으므로 `r - l + 1` 이 하나 늘어요.

```text
T4   r=2  l=0   r − l + 1 = 2 − 0 + 1 = 3
T5   r=3  l=0   r − l + 1 = 3 − 0 + 1 = 4
        └ l 이 그대로이고 r 만 늘었으니 길이가 정확히 1 늘어난다
```

이것이 `0` 이 섞인 입력에서 답이 길어지는 이유이고, 원소가 전부 `0` 이면 `S = 0` 에서도 답이
배열 전체 길이가 되는 이유이기도 합니다.
