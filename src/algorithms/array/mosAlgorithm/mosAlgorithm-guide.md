# Mo's 알고리즘 — 질의를 다시 정렬하면 창이 √n배 덜 움직인다

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 순진한 방법에서
Mo's 알고리즘까지 가는 경로를 따라갑니다. 마지막에는 실제로 동작하는 코드를 한 줄씩 만듭니다.

### 전체 컨셉

구간 `[l, r]` 을 읽는 **창** 하나를 그대로 유지합니다. 창 안에 무엇이 몇 개 있는지 세어
두면 「서로 다른 값의 개수」는 그 셈에서 바로 나와요. 다음 질의로 갈 때는 창을 처음부터
다시 만들지 않고 양 끝만 이동시킵니다.

```text
arr        1 1 2 1 3
인덱스     0 1 2 3 4

지금 창    [0,2]  값 1 1 2
다음 질의 [1,3] 로 가려면
  R+ →     [0,3]  값 1 1 2 1     오른쪽 한 칸 넓히고
  L− →     [1,3]  값 1 2 1       왼쪽 한 칸 좁힌다   → 두 칸만 이동했다
```

두 칸만 이동해서 다음 답을 얻었습니다. 질의가 여럿이면 총비용은 창이 이동한 칸의 합이
되고, 그 합은 **질의를 어떤 순서로 처리하느냐**에 달립니다. 받은 순서 그대로 처리하면 창이
배열의 앞뒤로 왕복하면서 쓸모없이 이동해요. 그래서 질의를 먼저 **다시 정렬합니다.** 왼쪽 끝을 크기
`√n` 짜리 구역으로 묶고, 같은 구역 안에서는 오른쪽 끝 순으로 놓습니다.

```text
정렬 전       Q0[0,4]  Q1[0,2]  Q2[2,4]  Q3[1,3]  Q4[2,3]
정렬 후       Q1[0,2]  Q3[1,3]  Q0[0,4]  Q4[2,3]  Q2[2,4]
               └───── 왼쪽 끝이 같은 구역 ─────┘  └── 다음 구역 ──┘
```

답은 원래 질의 자리에 넣어 돌려주니, 처리 순서를 바꿔도 호출한 쪽이 받는 결과는 달라지지
않습니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **해시 맵의 넣기·빼기가 평균 `O(1)`** 이라는 것. 값마다 몇 개 있는지 세는 데 씁니다.
- **정렬이 `O(q log q)`** 라는 것. 질의를 다시 정렬할 때 그 비용이 붙어요.
- **오프라인 질의**의 뜻 — 질의를 **전부 미리 받아** 두고 아무 순서로나 처리해도 되는
  상황입니다. 답만 원래 순서로 돌려주면 됩니다.

세 번째가 이 알고리즘의 전제예요. 질의가 하나씩 도착해서 그때그때 답해야 하는 상황이라면
방금 본 재정렬은 아예 할 수가 없습니다.

### 아이디어 상세 — 질의 재정렬을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function mosAlgorithm(arr: number[], queries: [number, number][]): number[];
```

- 입력: 정수 배열 `arr`, 폐구간 질의 목록 `queries`.
- 출력: 각 구간의 **서로 다른 원소 수**. 답이 놓이는 자리는 입력 질의의 자리 그대로예요.
- 제약: 배열 길이도 질의 수도 최대 `10,000`. 시간 1초.

여기서 한 가지 눈여겨볼 것이 있어요. 질의가 배열 하나로 한꺼번에 들어옵니다. 하나 묻고
답한 뒤에 다음을 받는 형태가 아니에요.

```text
queries 가 배열 하나다
  ┗ 어느 질의부터 답할지는 이쪽에서 정한다
  ┗ 답을 원래 자리 i 에 넣어 돌려주면 호출한 쪽이 받는 결과는 처리 순서와 무관하다
```

지금은 그냥 지나가도 됩니다. 이 성질이 필요해지는 자리가 뒤에 옵니다.

이 글이 쓰는 기호는 여섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 배열 `arr` 의 길이 | `n ≤ 10^4` |
| `q` | 질의의 개수. `queries` 의 길이 | `q ≤ 10^4` |
| `l` · `r` | 질의 하나의 왼쪽 끝 · 오른쪽 끝. 구간은 폐구간 `[l, r]` | `0 ≤ l ≤ r < n` |
| `curL` · `curR` | 지금 창의 왼쪽 끝 · 오른쪽 끝 | 처리하는 동안 이동한다 |
| `count[v]` | 지금 창 안에 값 `v` 가 몇 개 있는가 | 해시 맵 |
| `distinct` | 지금 창 안의 서로 다른 값의 수 | 이것이 곧 답 |

가장 먼저 떠오르는 방법으로 시작합시다. 질의마다 그 구간을 처음부터 다시 읽어 집합에
담는 것이에요. 구간 하나가 최대 `n` 칸이고 질의가 `q` 개입니다.

```text
질의 하나에 최대 n 칸  →  q × n = 10^4 × 10^4 = 100,000,000 칸
```

칸마다 해시 맵을 한 번씩 조회하니까 실제 상수는 1보다 큽니다. 1초 안에 끝난다고 보기
어려워요. 그러면 이 1억 칸 안에 헛일이 얼마나 섞여 있는지 봅시다. `[0,4]` 를 센 다음
`[1,3]` 을 처음부터 다시 세는 경우예요.

```text
arr        1 1 2 1 3
인덱스     0 1 2 3 4

[0,4]      ■ ■ ■ ■ ■
[1,3]        ■ ■ ■        ← 이 셋은 방금 읽은 칸입니다
```

인덱스 1·2·3 을 두 번씩 읽었습니다. 두 구간이 다른 자리는 양 끝 두 칸뿐인데 세 칸을
통째로 다시 읽은 셈이에요. 그러면 이런 생각을 해 볼 수 있습니다. 방금 센 결과를 버리지
않고, 달라진 양 끝만 이동시켜서 다음 질의로 넘어갈 수는 없을까요?

해 봅시다. 구간 `[l, r]` 을 읽는 창 하나를 계속 유지하고, 다음 질의로 갈 때 창을 새로
만들지 않고 양 끝을 차이만큼만 이동시킵니다. 창이 한 칸 이동하면 값 하나가 들어오거나
나가고, 그 일을 `add` 와 `remove` 가 합니다.

```text
add(v)     count[v] 를 1 늘린다.  0 → 1 이 되면 distinct 를 1 늘린다
remove(v)  count[v] 를 1 줄인다.  1 → 0 이 되면 distinct 를 1 줄인다

L+  curL 을 왼쪽으로   창이 넓어짐 → add        L−  curL 을 오른쪽으로  창이 좁아짐 → remove
R+  curR 을 오른쪽으로  창이 넓어짐 → add        R−  curR 을 왼쪽으로    창이 좁아짐 → remove
```

창을 이동시키는 코드는 이 네 갈래가 전부예요. 잠깐, 확인 하나만 해 볼까요? `[0,4]` 에서
`[1,3]` 으로 갈 때 창이 몇 칸 이동할까요? 왼쪽 끝이 0 에서 1 로 한 칸, 오른쪽 끝이 4 에서
3 으로 한 칸이니 두 칸입니다. 처음부터 다시 세면 세 칸을 읽던 자리가 두 번 이동으로 끝나요.

그러면 총비용은 창이 이동한 칸 수의 합이 되고, 그 값은 식 하나로 적힙니다.

```text
비용 = Σ ( |다음 l − curL| + |다음 r − curR| )       질의를 처리하는 순서대로 더한다
       └ 이 식에 arr 의 값이 없다. 배열이 무엇이든 비용은 같다
```

이 식을 한 번 더 봅시다. `arr` 이 없어요. 배열에 무슨 값이 들어 있든 비용은 같다는
뜻입니다. 남은 변수는 **질의를 늘어놓은 순서** 하나뿐이에요. 그러면 순서를 바꿨을 때 값이
정말로 달라지는지부터 확인해야겠죠.

`arr = [1, 1, 2, 1, 3]` 에 질의 다섯을 두고 세어 봅니다. 창은 빈 상태(`curL = 0`,
`curR = −1`)에서 출발해요.

```text
Q0[0,4]   Q1[0,2]   Q2[2,4]   Q3[1,3]   Q4[2,3]
```

같은 다섯을 두 순서로 처리하고 이동 칸을 셉니다. 오른쪽은 오른쪽 끝 `r` 의 오름차순이에요.

```text
입력 순서 — 14칸                      r 오름차순 — 11칸
  Q0[0,4]  curR −1→4        5칸        Q1[0,2]  curR −1→2        3칸
  Q1[0,2]  curR  4→2        2칸        Q3[1,3]  curL 0→1 curR 2→3  2칸
  Q2[2,4]  curL 0→2 curR 2→4  4칸      Q4[2,3]  curL 1→2          1칸
  Q3[1,3]  curL 2→1 curR 4→3  2칸      Q0[0,4]  curL 2→0 curR 3→4  3칸
  Q4[2,3]  curL 1→2          1칸        Q2[2,4]  curL 0→2          2칸
```

답 다섯 개는 어느 쪽이든 같고 창을 이동시키는 코드도 같은데, 14칸이 11칸이 됐습니다.
순서가 비용을 정한다는 것이 값으로 확인됐어요. 그러면 다음 질문은 이것입니다. 어떤 순서가
좋은 순서일까요? 질의를 받아서 늘어놓는 규칙, 곧 정렬 기준을 만들어야 합니다.

기준을 지어내기 전에 비용 식을 다시 봅시다. 두 항이 각각 커서 하나에 붙어 있어요. `curL`
이 되돌아가지 않으면 앞 항이 작아지고, `curR` 이 되돌아가지 않으면 뒤 항이 작아집니다.

```text
비용 = Σ ( |다음 l − curL|  +  |다음 r − curR| )
           └ l 오름차순이     └ r 오름차순이
             줄이는 항          줄이는 항
```

후보가 둘 나왔습니다. 다섯 질의는 둘을 가르기에 너무 작으니 배열을 열여섯 칸으로 늘리고
질의를 여덟 개 둡니다. 앞의 다섯과 섞이지 않게 이름을 `P` 로 구분해요.

```text
P0[0,15]   P1[1,4]    P2[8,12]   P3[2,9]    P4[9,14]   P5[3,6]    P6[10,11]  P7[5,13]
```

두 후보로 각각 늘어놓고 커서 자취를 나란히 적습니다.

```text
l 오름차순 — 58칸                        r 오름차순 — 46칸
  P0 P1 P3 P5 P7 P2 P4 P6                  P1 P5 P3 P6 P2 P7 P4 P0
  curL 0→1→2→3→5→8→9→10   한 방향         curL 1→3→2→10→8→5→9→0   오르내린다
  curR 15→4→9→6→13→12→14→11 오르내린다     curR 4→6→9→11→12→13→14→15 한 방향
  16+12+6+4+9+4+3+4                        6+4+4+10+3+4+5+10
```

자취를 보면 두 후보가 같은 모양으로 막혀 있습니다. 한쪽 커서를 한 방향으로 만들면 다른
쪽이 오르내려요. 왜 그럴까요? 사전식 비교의 성질 하나 때문입니다. 앞자리 값이 다르면
거기서 순서가 확정되고 뒷자리 값은 순서에 관여하지 못해요.

```text
l 을 앞자리에 두면      l 이 1만 달라도 순서가 정해진다 → r 은 아무 값이나 올 수 있다
  P0[0,15] 다음에 P1[1,4]    l 은 0 → 1 로 한 칸인데 r 이 15 → 4 로 11칸 이동한다

r 을 앞자리에 두면      r 이 1만 달라도 순서가 정해진다 → l 은 아무 값이나 올 수 있다
  P3[2,9] 다음에 P6[10,11]   r 은 9 → 11 로 두 칸인데 l 이 2 → 10 으로 8칸 이동한다
```

여기가 갈림길입니다. 뒷자리가 순서를 정하려면 앞자리 값이 **같아야** 하는데, `l` 을 그대로
앞자리에 쓰면 `l` 이 정확히 똑같은 질의들 사이에서만 그렇게 돼요. 그런 질의는 많지 않습니다.

그러면 앞자리를 이렇게 바꿔 보면 어떨까요? `l` 이 조금 달라도 **같은 값이 나오는 것**으로요.
앞자리가 같은 질의가 많아지고, 그 안에서 뒷자리 `r` 이 순서를 정하게 됩니다.

```text
여덟 질의의 왼쪽 끝   l =  0  1  8  2  9  3  10  5     (P0 P1 P2 P3 P4 P5 P6 P7)

앞자리가 l 그대로        0  1  8  2  9  3  10  5     여덟 값이 전부 다르다 → 묶이는 것이 없다
앞자리가 네 칸 단위      0  0  2  0  2  0   2  1     l 이 달라도 같아진다 → 묶음 셋이 생긴다
                         └ 묶음 0: P0 P1 P3 P5   묶음 1: P7   묶음 2: P2 P4 P6
                         └ 같은 묶음 안에서만 뒷자리 r 이 순서를 정하게 된다
```

왼쪽 끝이 놓이는 좌표축 `0 … n−1` 을 `B` 칸씩 끊읍시다. 끊은 토막을 구역이라 부르고,
왼쪽 끝이 `l` 인 질의가 몇 번 구역에 드는지를 `blk(l) = ⌊l / B⌋` 로 씁니다. `l` 이 달라도
같은 토막 안이면 `blk(l)` 이 같은 값이 돼요.

```text
n = 5, B = 2 로 끊은 왼쪽 끝 좌표축과, 그 위에 놓인 다섯 질의의 왼쪽 끝

  l         0    1  │  2    3  │  4
  blk(l)    0    0  │  1    1  │  2
  질의      Q0   Q3 │  Q2      │
            Q1      │  Q4      │
            └─ 2칸 ─┘  └─ 2칸 ─┘  └ 1칸 ┘
```

정렬 키는 `(blk(l), r)` 이고 사전식으로 비교합니다. 앞 값 `blk(l)` 이 같은 질의들이
생기고, 그 질의들 사이에서는 뒤 값 `r` 이 순서를 정해요.

```text
앞 값  blk(l)   같은 구역의 질의를 한데 모은다        앞 값이 다르면 거기서 끝난다
뒤 값  r        모인 것끼리 r 오름차순으로 놓는다      앞 값이 같을 때만 본다
```

> 앞자리는 모으는 일을, 뒷자리는 모인 것의 순서를 정하는 일을 합니다.

다섯 질의에 이 키를 적용해 봅시다. `n = 5` 이므로 `B = 2` 예요.

```text
1단계  앞 값을 계산한다              2단계  구역별로 모아 r 오름차순      3단계  이어 붙인다
  Q0[0,4]  blk = ⌊0/2⌋ = 0  r = 4     구역 0   Q1(r=2) Q3(r=3) Q0(r=4)     Q1 → Q3 → Q0
  Q1[0,2]  blk = ⌊0/2⌋ = 0  r = 2     구역 1   Q4(r=3) Q2(r=4)                 → Q4 → Q2
  Q2[2,4]  blk = ⌊2/2⌋ = 1  r = 4
  Q3[1,3]  blk = ⌊1/2⌋ = 0  r = 3
  Q4[2,3]  blk = ⌊2/2⌋ = 1  r = 3
```

나온 순서는 `Q1 → Q3 → Q0 → Q4 → Q2` 입니다. 같은 키를 열여섯 칸 쪽 여덟 질의에 `B = 4`
로 적용하면 이렇게 돼요.

```text
B = 4    P1 P5 P3 P0 P7 P6 P2 P4        6+4+4+8+7+7+3+3 = 42칸
         구역   0  0  0  0 │ 1 │ 2  2  2
         curL   1→3→2→0   │ 5 │ 10→8→9
         curR   4→6→9→15  │13 │ 11→12→14
```

42칸입니다. 후보 둘의 58칸·46칸보다 적어요. 한 커서만 한 방향으로 만드는 것보다, 두 커서의
이동을 나누어 줄이는 쪽의 총합이 더 적습니다.

여기서 헷갈리기 쉬운 포인트는 `blk(l)` 이 창의 위치를 정한다고 읽는 것이에요. 구역으로
묶었으니 같은 구역의 질의들 사이에서는 창의 왼쪽 끝이 그대로 있겠다고 생각하기 쉬운데,
그렇지 않습니다. `blk(l)` 은 어느 질의를 먼저 놓을지 **비교할 때만** 쓰고, 창을 이동시키는
코드에는 `l` 과 `r` 이 그대로 들어가요.

```text
blk(l)   정렬에서 어느 질의를 먼저 놓을지 비교할 때만 쓴다
l · r    창을 이동시키는 코드가 그대로 쓴다 — while (curL < l) · while (curR < r) …
```

위에서 얻은 순서로 다섯 질의를 처리하면서 값이 어떻게 변하는지 전부 적어 봅시다.

```text
Q1[0,2]  R+ curR −1→0  add(1)     [0,0]  count 1:1              distinct 1
         R+ curR  0→1  add(1)     [0,1]  count 1:2              distinct 1
         R+ curR  1→2  add(2)     [0,2]  count 1:2, 2:1         distinct 2   답 2
Q3[1,3]  R+ curR  2→3  add(1)     [0,3]  count 1:3, 2:1         distinct 2
         L− curL  0→1  remove(1)  [1,3]  count 1:2, 2:1         distinct 2   답 2
Q0[0,4]  L+ curL  1→0  add(1)     [0,3]  count 1:3, 2:1         distinct 2
         R+ curR  3→4  add(3)     [0,4]  count 1:3, 2:1, 3:1    distinct 3   답 3
Q4[2,3]  L− curL  0→1  remove(1)  [1,4]  count 1:2, 2:1, 3:1    distinct 3
         L− curL  1→2  remove(1)  [2,4]  count 1:1, 2:1, 3:1    distinct 3
         R− curR  4→3  remove(3)  [2,3]  count 1:1, 2:1         distinct 2   답 2
Q2[2,4]  R+ curR  3→4  add(3)     [2,4]  count 1:1, 2:1, 3:1    distinct 3   답 3

         이동한 칸을 세면 3 + 2 + 2 + 3 + 1 = 11칸이다
```

답 다섯은 `Q0` 부터 `Q4` 까지 차례로 3 · 2 · 3 · 2 · 2 예요. 그리고 방금 말한 오해의
반례가 이 안에 있습니다. `Q3` 와 `Q0` 은 둘 다 구역 0 인데 `curL` 이 1 에서 0 으로
이동했어요. 구역이 같다는 것은 두 질의가 정렬에서 이웃한다는 뜻이지 `l` 이 같다는 뜻이
아닙니다.

그러면 걱정이 하나 남아요. 두 질의가 아예 겹치지 않으면 어떻게 될까요? 이전 창에서 센 값이
`count` 에 남아 답을 틀리게 하지는 않을까요? 겹치는 칸이 하나도 없는 경우를 단계마다
적어 봅니다.

```text
[0,1] → [3,4]  겹치는 칸이 없다
  시작                       [0,1]  count 1:2              distinct 1
  R+ curR 1→2  add(2)        [0,2]  count 1:2, 2:1         distinct 2
  R+ curR 2→3  add(1)        [0,3]  count 1:3, 2:1         distinct 2
  R+ curR 3→4  add(3)        [0,4]  count 1:3, 2:1, 3:1    distinct 3   ← 가장 커진 지점
  L− curL 0→1  remove(1)     [1,4]  count 1:2, 2:1, 3:1    distinct 3
  L− curL 1→2  remove(1)     [2,4]  count 1:1, 2:1, 3:1    distinct 3
  L− curL 2→3  remove(2)     [3,4]  count 1:1, 3:1         distinct 2   답 2
```

창이 잠깐 커졌다가 줄어들고, 넣었다 곧바로 빼는 칸이 생깁니다. 그래도 답은 맞아요. 앞 창의
값이 남지 않는 근거는 `L−` 루프의 종료 조건입니다. `while (curL < l)` 은 `curL` 이 새
질의의 `l` 과 같아질 때까지 반복하니까, `[이전 curL, 새 l)` 의 모든 칸이 정확히 한 번씩
`remove` 를 거쳐요. 위에서는 인덱스 0·1·2 가 전부 걸렸고 건너뛴 칸이 없습니다.

이 키가 두 커서의 이동 범위를 각각 정합니다. 방금 실제로 이동한 자취가 그대로 범위가 돼요.

```text
curL   같은 구역의 두 질의는 l 이 최대 B−1 칸 차이다(구역 폭이 B 이므로)
       → 질의 하나당 최대 B 칸        (위에서 본 1→3, 3→2, 2→0 이 그것이다)
curR   같은 구역 안에서는 r 오름차순이라 한 방향으로만 이동한다
       → 한 구역을 처리하는 동안 최대 n 칸, 구역이 바뀔 때 한 번 되돌아간다
       → 구역 수가 n/B 이므로 되돌아감도 n/B 번
```

이제 `B` 를 얼마로 둘지가 남았습니다. `B` 는 구역 하나를 몇 칸으로 잡느냐예요. 크게 잡으면
구역 수가 적어져 `curR` 의 되돌아감이 줄지만, 한 구역이 넓어져 `curL` 이 질의마다 멀리
이동합니다. 작게 잡으면 반대예요.

잠깐, 양 끝부터 확인해 볼까요? `B = 1` 이면 구역 하나에 질의가 하나씩 드니까 `blk(l)` 은
`l` 을 그대로 앞자리에 쓴 것과 같아지고, `B = n` 이면 구역이 하나뿐이라 모든 질의의 앞
값이 같아져서 `r` 로만 정렬한 것과 같아집니다. 앞에서 센 두 후보가 바로 그 둘이에요.
그러니 더 적은 자리가 있다면 양 끝이 아니라 그 사이입니다. 여덟 질의로 다섯 값을 실제로
세 봅시다.

```text
B =  1   P0 P1 P3 P5 P7 P2 P4 P6    58칸    구역 16개 — l 을 정확히 정렬한 것과 같다
B =  2   P1 P0 P5 P3 P7 P2 P4 P6    52칸    구역 8개
B =  4   P1 P5 P3 P0 P7 P6 P2 P4    42칸    구역 4개                    ← 가장 적다
B =  8   P1 P5 P3 P7 P0 P6 P2 P4    48칸    구역 2개
B = 16   P1 P5 P3 P6 P2 P7 P4 P0    46칸    구역 1개 — r 로만 정렬한 것과 같다
```

| `B` | 1 | 2 | **4** | 8 | 16 |
| --- | --- | --- | --- | --- | --- |
| 총 이동 칸 | 58 | 52 | **42** | 48 | 46 |

확인한 대로 양 끝의 58칸·46칸이 앞에서 센 두 후보와 같은 값으로 나왔습니다. 가장 적은
42칸은 그 사이의 `B = 4` 에서 나왔고, 4 는 `√16` 이에요.

### 수행으로 알아보는 알고리즘 — 창 하나로 다섯 질의를 답한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const arr = [1, 1, 2, 1, 3];
const queries: [number, number][] = [[0, 4], [0, 2], [2, 4], [1, 3], [2, 3]];
// 이 절이 끝나면 [3, 2, 3, 2, 2] 가 나와야 한다
```

질의를 왜 하필 다섯으로 뒀을까요? 창을 이동시키는 네 갈래를 **모두 실행하게** 하려는
것입니다. 마지막 `Q4[2,3]` 이 없으면 오른쪽 끝이 줄어드는 일이 없어 `R−` 가 한 번도 나오지
않아요.

#### 1. 질의에 원래 자리를 붙인다

질의를 재배열하면 답이 나오는 순서도 뒤섞입니다. 그러니 정렬 **전에** 각 질의에 원래 자리
`i` 를 달아 두고, 답을 그 자리에 넣습니다.

```ts
const order = queries.map(([l, r], i) => ({ l, r, i }));
```

실행하면 이렇게 나와요. 아직 순서는 그대로이고 꼬리표만 붙었습니다.

```text
[ {l:0, r:4, i:0}   {l:0, r:2, i:1}   {l:2, r:4, i:2}
  {l:1, r:3, i:3}   {l:2, r:3, i:4} ]
                ↑ i 가 원래 자리다. 답은 out[i] 에 넣는다
```

#### 2. 구역 크기를 정한다

「아이디어 상세」에서 여덟 질의로 재 봤을 때 `B = 4` 가 가장 적었고, 4 는 `√16` 이었습니다.
그 `B` 를 코드에서는 `block` 이라 씁니다.

```ts
const block = Math.max(1, Math.floor(Math.sqrt(arr.length)));
```

```text
arr.length = 5  →  √5 = 2.2360…  →  ⌊2.2360…⌋ = 2  →  block = 2
```

#### 짚고 가기 — `Math.max(1, …)` 을 빼면 정렬이 잘못된다

`⌊√n⌋` 만 써도 될 것 같지 않나요? `n` 이 4 이상이면 실제로 아무 문제가 없습니다. 그런데
**`n` 이 0일 때 `block` 이 0이 됩니다.**

```text
n = 1 일 때   ⌊√1⌋ = 1        → block = 1     괜찮다
n = 0 일 때   ⌊√0⌋ = 0        → block = 0     여기서 문제가 생긴다
  정렬 키의 앞 값 blk(l) = ⌊l / 0⌋ 이 Infinity 가 되고
  Infinity - Infinity = NaN 이라 비교 함수가 NaN 을 돌려준다
  → sort 가 "순서를 정할 수 없다" 로 받아 배열을 그대로 두거나 엔진마다 다르게 뒤섞는다
```

빈 배열은 질의도 없어서 첫 줄에서 빠져나가지만, **`arr` 만 비고 질의가 들어오는 입력**이
막지 않으면 여기로 옵니다. 한 줄이 그 전부를 막아요.

```ts
const block = Math.max(1, Math.floor(Math.sqrt(arr.length)));
//            ~~~~~~~~~~ 0 이 되는 길을 끊는다
```

#### 3. 두 키로 순서를 정한다

「아이디어 상세」에서 얻은 키 `(blk(l), r)` 을 그대로 옮깁니다. 앞 값이 같을 때만 뒤 값을
봅니다.

```ts
const blk = (l: number): number => Math.floor(l / block); // 식의 blk(l) 그대로

order.sort((x, y) => {
  if (blk(x.l) !== blk(y.l)) return blk(x.l) - blk(y.l); // 구역이 다르면 여기서 끝
  return x.r - y.r; //                                     같은 구역 안에서만 오른쪽 끝을 본다
});
```

여기서 가장 중요한 줄은 첫 번째 `if` 입니다. 이 줄이 **앞 값이 다르면 거기서 반환**하기
때문에 뒤 값 `r` 은 같은 구역 안에서만 순서를 정하게 돼요. 이 줄을 빼고 `x.r - y.r` 만
남기면 구역이 사라지고 오른쪽 끝만으로 정렬한 것이 됩니다.

실행한 결과입니다. 「아이디어 상세」에서 손으로 만든 순서와 같아요.

```text
정렬 전   Q0[0,4]   Q1[0,2]   Q2[2,4]   Q3[1,3]   Q4[2,3]
정렬 후   Q1[0,2]   Q3[1,3]   Q0[0,4]  │ Q4[2,3]   Q2[2,4]
          blk 0     blk 0     blk 0    │ blk 1     blk 1
          └──── r 이 2 → 3 → 4 ────┘   │ └── r 이 3 → 4 ──┘
```

#### 4. 셈 도구를 만든다 — `add` 와 `remove`

창이 한 칸 이동할 때 부를 두 함수입니다. **가짓수는 `0 ↔ 1` 경계에서만 바뀌어요** — 그
조건이 이 알고리즘의 전부입니다.

```ts
const count = new Map<number, number>();
let distinct = 0;

const add = (value: number): void => {
  const next = (count.get(value) ?? 0) + 1;
  count.set(value, next);
  if (next === 1) distinct++; // 없던 값이 처음 들어왔다
};

const remove = (value: number): void => {
  const next = (count.get(value) as number) - 1;
  count.set(value, next);
  if (next === 0) distinct--; // 마지막 하나가 빠졌다
};
```

여기서 가장 중요한 줄은 `if (next === 1)` 과 `if (next === 0)` 입니다. 이 두 줄이 없으면
같은 값을 넣을 때마다 가짓수가 늘어나요. 값 `1` 을 두 번 넣었다 두 번 빼면서 `distinct` 가
언제 움직이는지 보면 조건의 뜻이 분명해집니다.

```text
add(1)      count{1:1}          distinct 0 → 1   ← 0→1 경계를 지났다
add(1)      count{1:2}          distinct 1       ← 안 는다
add(2)      count{1:2, 2:1}     distinct 1 → 2
remove(1)   count{1:1, 2:1}     distinct 2       ← 안 준다 (1 이 아직 남았다)
remove(1)   count{1:0, 2:1}     distinct 2 → 1   ← 1→0 경계를 지났다
```

#### 짚고 가기 — `Set` 하나로 바꾸고 싶어지는 자리

`count` 맵과 `distinct` 를 따로 유지하는 것이 번거로워 보이지 않나요? 창에 든 값의 집합만
유지하면 크기가 곧 답이니 `Set` 하나면 될 것 같습니다.

```ts
const seen = new Set<number>();
// 넓힐 때 seen.add(v), 좁힐 때 seen.delete(v), 답은 seen.size
```

넓히는 쪽은 실제로 맞아요 — `Set.add` 는 이미 있는 값을 넣어도 아무 일도 하지 않으므로
중복이 알아서 처리됩니다. **좁히는 쪽에서 잘못됩니다.** `Set.delete(v)` 는 창에 `v` 가
**아직 남아 있는지**를 모르기 때문이에요.

```text
창 [0,2] 의 값 1 1 2    Set = {1, 2}        size 2  ✓
curL 을 1 로 좁힌다 → arr[0] = 1 을 delete
창 [1,2] 의 값 1 2      Set = {2}           size 1  ✗  (답은 2)
                        └ 창에 1 이 아직 있는데 지웠다
```

다섯 질의를 끝까지 실행하면 결과가 이렇게 달라집니다. **뒤 세 개가 틀렸어요.**

```text
count 맵   [3, 2, 3, 2, 2]      ← 정답
Set        [3, 2, 2, 1, 1]      ← 좁히기가 시작되는 지점부터 어긋난다
```

`count[v]` 가 `1 → 0` 이 될 때만 가짓수를 줄이면 「마지막 하나가 빠졌는가」를 정확히 알 수
있습니다. `Set` 은 그 정보를 애초에 유지하지 않아요 — **개수를 세야 하는 이유가 이것입니다.**

#### 5. 창을 옮기며 답을 채운다

정렬된 순서대로 질의를 꺼내 네 갈래를 실행합니다. 넓히기 둘을 먼저, 좁히기 둘을 나중에 둡니다.

```ts
const out = new Array<number>(queries.length);
let curL = 0;
let curR = -1; // 빈 창

for (const q of order) {
  while (curL > q.l) add(arr[--curL] as number); //    L+ 왼쪽으로 넓힌다
  while (curR < q.r) add(arr[++curR] as number); //    R+ 오른쪽으로 넓힌다
  while (curL < q.l) remove(arr[curL++] as number); // L− 왼쪽에서 좁힌다
  while (curR > q.r) remove(arr[curR--] as number); // R− 오른쪽에서 좁힌다
  out[q.i] = distinct;
}
```

네 `while` 이 각각 따로 실행되는데도 `count` 가 맞는 이유가 궁금하지 않나요? 종료 조건에
있습니다. 네 루프가 끝나면 `curL` 은 정확히 `q.l`, `curR` 은 정확히 `q.r` 이 되고, 그 사이
모든 칸이 `add` 나 `remove` 를 정확히 한 번씩 거칩니다. 「아이디어 상세」에서 겹치지 않는
구간으로 이동하며 확인한 그대로예요.

```text
루프 하나가 끝날 때 보장되는 것
  L+ 뒤   curL ≤ q.l          L− 뒤   curL = q.l
  R+ 뒤   curR ≥ q.r          R− 뒤   curR = q.r
  ┗ 넷을 다 실행하면 창이 정확히 [q.l, q.r] 이고, count 는 그 창의 내용과 같다
```

정렬 후  Q1[0,2]  →  Q3[1,3]  →  Q0[0,4]  |  Q4[2,3]  →  Q2[2,4]

| T10 | 기록 | — | `[0,4]` | `1 1 2 1 3` | `{1:3, 2:1, 3:1}` | `out[0] = 3` |
| T11 | Q4[2,3] 로 — 왼쪽 좁힘 | `curL = 0 < 2` 참 → L− | `[1,4]` | `1 2 1 3` | `{1:2, 2:1, 3:1}` | 3 |
| T12 | 왼쪽 좁힘 | `curL = 1 < 2` 참 → L− | `[2,4]` | `2 1 3` | `{1:1, 2:1, 3:1}` | 3 |
| T13 | 오른쪽 좁힘 | `curR = 4 > 3` 참 → R− | `[2,3]` | `2 1` | `{1:1, 2:1}` | 2 (3이 1→0) |
| T14 | 기록 | — | `[2,3]` | `2 1` | `{1:1, 2:1}` | `out[4] = 2` |
| T15 | Q2[2,4] 로 — 오른쪽 넓힘 | `curR = 3 < 4` 참 → R+ | `[2,4]` | `2 1 3` | `{1:1, 2:1, 3:1}` | 3 |
| T16 | 기록 | — | `[2,4]` | `2 1 3` | `{1:1, 2:1, 3:1}` | `out[2] = 3` |

**`count` 열이 매 단계 창의 내용과 일치합니다.** T6 에서 창이 `[0,3]` 에서 `[1,3]` 으로
좁아졌는데 `count[1]` 이 2 로 남는 것이 그 증거예요 — 창 `[1,3]` 의 값 `1 2 1` 에 1 이 실제로
둘 있습니다. `distinct` 는 이 맵에서 개수가 1 이상인 키의 수이므로, 맵이 맞으면 답도 맞아요.

**네 갈래가 모두 나왔습니다.** 창이 이동한 칸은 모두 **11칸**이고, 반환값은 `[3, 2, 3, 2, 2]`
로 원래 질의 순서 그대로입니다.

```text
L+  T8                            L−  T6 · T11 · T12
R+  T1 · T2 · T3 · T5 · T9 · T15  R−  T13
```

여기서 헷갈리기 쉬운 포인트는 T2와 T6 입니다. 둘 다 값 `1` 을 건드리는데 `distinct` 가
바뀌지 않아요. 값을 넣거나 뺐으니 가짓수도 움직여야 할 것 같은데, 개수가 `1→2` 이거나
`2→1` 이라 `0↔1` 경계를 넘지 않기 때문입니다.

#### 짚고 가기 — 네 갈래의 차례를 바꿔도 답은 맞게 나온다

네 `while` 이 어차피 다 실행되니까 차례는 아무래도 될 것 같지 않나요? **이 문제에서는 실제로
답이 틀리지 않습니다.** 그래서 이 자리가 함정이에요 — 테스트가 통과하니 틀린 줄 모르고
넘어갑니다.

좁히기를 먼저 실행하면 `curL` 이 `curR` 을 지나쳐, **창에 담은 적도 없는 값을 빼는** 순간이
생깁니다.

```text
arr = [1, 2, 3, 1, 2, 3]   queries = [[0,1], [4,5]]   block = 2
창 [0,1] 에서 [4,5] 로 갈 때 좁히기(L−)를 먼저 하면
  curL=2 에서 값 3 을 뺀다 → count[3] = -1     (창 [0,1] 밖의 값이다)
  curL=3 에서 값 1 을 뺀다 → count[1] = -1
        └ curR 은 아직 1 인데 curL 이 3 까지 갔다. 두 끝의 앞뒤가 바뀌었다
```

무작위 입력 30,000회로 두 차례를 대조했더니 **답이 달라진 경우는 0건**이었고, 카운트가
음수가 된 경우만 4,200건이었습니다. `distinct` 는 `0 ↔ 1` 경계만 보는데, 음수로 내려간 값이
나중에 다시 0을 지나며 상쇄되기 때문이에요.

```text
count[3]:  0 → -1 → 0 → 1      경계 0→1 을 한 번만 지난다 → distinct 는 맞게 는다
                └ 잘못된 -1 을 지나갔는데도 결과가 같다
```

**같은 구조를 다른 양에 적용하는 순간 틀린 답이 나옵니다.** 창의 합·최댓값·구간 내 쌍의
수는 경계가 아니라 **값 자체**를 쓰므로 `-1` 이 그대로 답에 섞여요. 넓히기를 먼저 두는 것은
취향이 아니라, 뒤에서 세울 불변식을 지키기 위한 순서입니다.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 **질의가 없을 때 즉시
반환**하는 첫 줄뿐이에요.

```ts
export function mosAlgorithm(
  arr: number[],
  queries: [number, number][],
): number[] {
  if (queries.length === 0) return [];

  const block = Math.max(1, Math.floor(Math.sqrt(arr.length)));
  const blk = (l: number): number => Math.floor(l / block);

  const order = queries.map((q, i) => ({ l: q[0], r: q[1], i }));
  order.sort((x, y) => {
    if (blk(x.l) !== blk(y.l)) return blk(x.l) - blk(y.l);
    return x.r - y.r;
  });

  const count = new Map<number, number>();
  let distinct = 0;
  const add = (value: number): void => {
    const next = (count.get(value) ?? 0) + 1;
    count.set(value, next);
    if (next === 1) distinct++;
  };
  const remove = (value: number): void => {
    const next = (count.get(value) as number) - 1;
    count.set(value, next);
    if (next === 0) distinct--;
  };

  const out = new Array<number>(queries.length);
  let curL = 0;
  let curR = -1;

  for (const q of order) {
    while (curL > q.l) add(arr[--curL] as number); // L+ 왼쪽 넓힘
    while (curR < q.r) add(arr[++curR] as number); // R+ 오른쪽 넓힘
    while (curL < q.l) remove(arr[curL++] as number); // L− 왼쪽 좁힘
    while (curR > q.r) remove(arr[curR--] as number); // R− 오른쪽 좁힘
    out[q.i] = distinct;
  }

  return out;
}
```

```text
mosAlgorithm([1,1,2,1,3], [[0,4],[0,2],[2,4],[1,3],[2,3]])  →  [3, 2, 3, 2, 2]
mosAlgorithm([1,1,2,1,3], [])                               →  []
mosAlgorithm([7],         [[0,0]])                          →  [1]
```

### 알아 두면 좋은 개념 — 제곱근 분할

「아이디어 상세」에서 `B` 를 정할 때 두 항이 반대로 움직이는 것을 값으로 봤습니다. 한쪽을
줄이면 다른 쪽이 늘어나서, 합이 가장 작은 자리가 가운데였어요. 이 모양에는 이름이 있습니다 —
**제곱근 분할**입니다.

```text
비용이 두 항의 합이고  →  한 항은 B 에 비례하고  →  합이 가장 작은 곳은
                          다른 항은 B 에 반비례한다     두 항이 같아지는 B = √(상수)

  qB + n²/B      →   B = n/√q   →   n = q 이면 B = √n
```

좌표축을 `√n` 칸씩 끊는 것 자체가 답인 것이 아니라, **두 비용이 반대로 움직일 때 그 균형점이
제곱근에 있다**는 것이 이 개념입니다. 끊는 대상도 `B` 의 값도 문제마다 달라져요.

| 문제 | 무엇을 `√n` 으로 끊는가 | 맞바꾸는 두 비용 |
| --- | --- | --- |
| 이 글 | 질의의 왼쪽 끝이 놓이는 좌표축 | `curL` 의 질의당 이동 ↔ `curR` 의 되돌아감 |
| 구간 합 질의 | 배열을 `√n` 칸 블록으로 | 갱신 한 번의 비용 ↔ 질의 한 번의 비용 |
| 그래프의 무거운 정점 | 차수 `√m` 을 경계로 정점을 둘로 | 무거운 쪽 처리 ↔ 가벼운 쪽 처리 |

세 줄이 다른 문제인데 균형점이 같은 자리에 있습니다. **두 비용이 `x` 와 `C/x` 꼴이면 합의
최솟값이 `x = √C` 에서 나오기 때문**이고, 「수식 정의와 유도」에서 `qB = n²/B` 를 푼 것이
바로 그 계산이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 상한이 어떻게 나오는지,
무엇이 매 순간 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 질의가 **오프라인**입니다 — 전부 미리 받아 두고 순서를 이쪽에서 정할 수 있어요.
- 답이 **구간에서 정의되고**, 창을 **한 칸 늘리거나 줄일 때 `O(1)` 로 갱신**됩니다.
- 배열이 **바뀌지 않습니다.** 중간에 값이 갱신되면 창을 이어받는 전제가 성립하지 않아요.
- `n` 과 `q` 가 비슷한 규모이고 `n\sqrt{n}` 이 제한에 들어갑니다.

#### 문제에서 이것을 떠올리게 하는 단서

- "질의를 **모두 입력받은 뒤**" · "질의 순서와 같은 순서로 출력"
- 구간에 대해 묻는데 **누적합으로는 안 되는** 양 — 서로 다른 개수, 최빈값, 구간 내 쌍의 수
- 갱신이 없고 질의만 많다
- 반대로 **"질의가 온라인으로 들어온다"** 거나 **"중간에 값을 바꾼다"** 는 문구가 있으면
  이 단서는 해당하지 않습니다

#### 실제로 쓰이는 곳

이 이름 그대로 표준 라이브러리에 들어간 사례는 **찾지 못했습니다.** 지어내지 않고 그대로
적어요. 쓰이는 자리는 경쟁 프로그래밍과 오프라인 분석 배치 쪽입니다.

- 원 출처는 Mo Tao 가 소개한 것으로 알려져 있으나 **1차 문헌을 확인하지 못했습니다.**
  널리 인용되는 정리는 Codeforces 블로그다
  ([Codeforces #340134](https://codeforces.com/blog/entry/340134), 조회 2026-08-19).

#### 경쟁 설계와의 대조

같은 목표를 노리는 **완전히 다른 절차**가 있어요 — **오프라인 + 펜윅 트리(BIT)** 입니다.
창을 이동시키는 대신 배열을 왼쪽부터 **한 번만** 읽습니다. 값 `v` 를 만나면 그 값의 직전
등장 자리를 지우고 지금 자리에 1을 더해요. 그러면 각 값이 **가장 오른쪽 등장에서만**
세지므로, 시점 `i` 에서 구간합 `[l, i]` 이 곧 그 구간의 서로 다른 값 수가 됩니다. 질의를
`r` 로만 정렬하면 한 번 순회로 전부 답할 수 있어요.

같은 입력(`n = 400`, `q = 200`, 고정 시드)에 둘을 걸고 **기본 연산 횟수**를 셌습니다.
Mo 는 포인터가 이동한 칸 수(칸마다 맵을 한 번 조회합니다), 펜윅은 트리 노드 방문 수입니다.

| 입력 | Mo · 포인터 이동 칸 | 펜윅 · 트리 노드 방문 |
| --- | --- | --- |
| 전개용 `n = 5`, `q = 5` | **11** | 25 |
| 대조용 `n = 400`, `q = 200` | 6,895 | **4,850** |

**크기를 키우면 순서가 뒤집힙니다.** 작은 입력에서는 펜윅의 트리 높이 상수가 그대로 나와
Mo 쪽이 적고, `n = 400` 에서는 증가 차수 차이(`O((n+q)\log n)` 대 `O((n+q)\sqrt{n})`)가 그
상수를 덮어 펜윅이 1.4배 적어요. **대조에 큰 쪽을 쓰는 이유가 이것입니다** — 전개 입력을
그대로 쓰면 Mo 가 적게 나오지만, 그건 측정한 것이 아니라 유리한 자리를 고른 것이니까요.

그러면 왜 Mo 를 쓸까요? **일반성 때문입니다.** 펜윅 쪽 방법은 「각 값을 가장 오른쪽 등장에서만
센다」는 성질에 통째로 기대고 있어서, 그 성질이 없는 양으로는 **옮겨지지 않습니다.**

| 묻는 양 | 펜윅 트릭 | Mo |
| --- | --- | --- |
| 서로 다른 개수 | 된다 (가장 오른쪽 등장) | 된다 |
| 구간의 최빈값 | 안 된다 | 된다 |
| 구간 내 같은 값 쌍의 수 | 안 된다 | 된다 |
| 구간 내 값의 제곱합 | 누적합이 더 쉽다 | 된다 |

Mo 가 요구하는 것은 **「창을 한 칸 늘리거나 줄일 때 `O(1)` 로 갱신되는가」** 하나뿐이에요.
그 조건만 맞으면 답이 무엇이든 같은 구조가 그대로 동작합니다. 문제마다 새 자료구조를
설계하는 대신 `add`·`remove` 두 함수만 바꿔 끼우면 된다는 것, 그것이 이 알고리즘이 주는
값입니다.

### 수식 정의와 유도

파트 1 에서는 값을 세어 `B = 4` 가 가장 적다는 것을 확인했습니다. 그런데 그건 `n = 16` 짜리
입력 하나에서 나온 값이에요. 임의의 `n` 과 `q` 에서도 그런지는 식으로 확인해야 합니다.
정렬 키를 기호로 정의하고, 그 정의를 실제 값에 넣어 검산하고, 창이 이동한 칸 수의 상한식을
세운 다음, 그 상한을 가장 작게 만드는 `B` 를 풉니다.

```text
정의   구역 번호 blk 와 정렬 키 ≺ 를 기호로 적는다
  ↓
검산   그 정의를 다섯 질의에 넣어 손으로 계산한다
  ↓
유도   두 끝의 이동 범위에서 상한식을 세운다
  ↓
계수   그 식을 가장 작게 만드는 B 를 풀고 제약 규모를 넣는다
```

**먼저 구역 크기 `B` 와 구역 번호 `blk` 입니다.** 왼쪽 끝이 놓이는 좌표축 `0 … n−1` 을 `B`
칸씩 끊고, 그렇게 끊은 토막을 **구역**이라 부릅니다. `blk(l)` 은 왼쪽 끝이 `l` 인 질의가
**몇 번 구역에 속하는가**이고, 나눗셈 한 번이 전부예요 — 배열을 자르지도, 질의를 구역별로
옮겨 담지도 않습니다.

$$
B \in \{1, 2, \dots, n\}, \qquad \operatorname{blk}(l) \;=\; \left\lfloor \frac{l}{B} \right\rfloor
$$

```text
n = 5, B = 2 로 끊은 왼쪽 끝 좌표축

  l         0    1  │  2    3  │  4
  blk(l)    0    0  │  1    1  │  2
            └─ 2칸 ─┘  └─ 2칸 ─┘  └ 1칸 ┘
                                    ↑ 마지막 구역은 남는 만큼만이라 B 보다 작다
```

끊고 남는 것이 있으면 마지막 구역이 `B` 칸에 못 미칩니다. 그러면 뒤에서 세울 상한이 깨질까요?
깨지지 않습니다 — 상한은 **구역 폭이 `B` 이하**라는 것만 쓰므로, 잘린 구역이 있어도 그대로
성립해요.

```text
Q3[1,3]  →  두 값을 뽑는다  →  (blk(1), 3) = (0, 3)
              질의 자체는 [1,3] 그대로 두고, 비교에 쓸 쌍만 따로 만든다
```

**정렬 키 `≺` 는 이렇게 정의합니다.** 질의 하나에서 `(blk(l), r)` 두 값을 **뽑아** 그 쌍을
**사전식**으로 비교합니다. 앞 값이 다르면 거기서 끝이고, 같을 때만 뒤 값을 봐요. 질의 자체는
`[l, r]` 그대로입니다 — 이 쌍은 비교에만 씁니다.

$$
Q_i \prec Q_j \iff \bigl(\operatorname{blk}(l_i),\; r_i\bigr) \;<_{\text{lex}}\; \bigl(\operatorname{blk}(l_j),\; r_j\bigr)
$$

```text
앞 값  blk(l)  같은 구역끼리 모은다   → 그 순서에서 curL 이 구역 폭 B 안에서만 이동한다
뒤 값  r       그 안에서 오름차순     → 그 순서에서 curR 이 한 방향으로만 이동한다
```

두 값을 쓰는 이유는 **각 값이 줄이는 이동이 다르기 때문**이에요. 앞 값이 만든 순서가 `curL`
의 이동을, 뒤 값이 만든 순서가 `curR` 의 이동을 줄입니다. 식을 그대로 코드로 옮기면 이만큼
입니다. **식의 `B` 를 코드에서는 `block` 이라 쓰고, `blk` 는 이름 그대로 둡니다** — 이 대응은
이 글 끝까지 같아요.

```ts
const blk = (l: number) => Math.floor(l / block);
order.sort((x, y) => blk(x.l) - blk(y.l) || x.r - y.r); // 앞 값이 같을 때만 뒤 값
```

**정의를 값에 넣어 검산해 봅시다.** `n = 5` 라 `B = 2` 이고, 이때 `blk` 는 `Q0`·`Q1`·`Q3` 이
0, `Q2`·`Q4` 가 1 입니다. 그 값으로 사전식 비교 세 쌍을 계산합니다.

```text
사전식 비교 — 앞 값(blk)을 먼저, 같을 때만 뒤 값(r)
  Q1 vs Q0   blk 0 = 0 → r 을 본다 → 2 < 4   ⇒ Q1 ≺ Q0
  Q0 vs Q2   blk 0 < 1 → 거기서 끝            ⇒ Q0 ≺ Q2   (r 은 4 > 3 인데도)
  Q4 vs Q2   blk 1 = 1 → r 을 본다 → 3 < 4   ⇒ Q4 ≺ Q2
```

두 번째 비교가 이 키의 성격을 그대로 보여줍니다. `Q0` 의 오른쪽 끝은 4 이고 `Q2` 는 3 인데도
`Q0` 이 앞이에요 — **구역 번호가 먼저 갈리면 오른쪽 끝은 보지도 않습니다.** 세 비교가 정하는
전체 순서는 `Q1 ≺ Q3 ≺ Q0 ≺ Q4 ≺ Q2` 이고, 「아이디어 상세」에서 구역별로 모아 얻은 순서와
같습니다.

**이제 상한식을 세웁니다.** 「아이디어 상세」가 정한 두 범위가 그대로 두 항이 돼요. 왼쪽 끝은
**질의마다** 최대 `B` 칸이니 `q` 개를 더해 `qB`, 오른쪽 끝은 **구역마다** 최대 `n` 칸이니 구역
수 `n/B` 를 곱해 `n²/B` 입니다.

```text
왼쪽 끝   같은 구역 안의 두 질의는 l 이 최대 B−1 칸 차이   → 질의당 B 칸,  질의가 q 개
오른쪽 끝  한 구역 안에서는 r 오름차순이라 한 방향          → 구역당 n 칸,  구역이 n/B 개
```

$$
\text{이동} \;\le\; \underbrace{q \cdot B}_{\text{왼쪽 끝}} \;+\; \underbrace{\frac{n}{B} \cdot n}_{\text{오른쪽 끝}}
$$

```text
다섯 질의(n = 5, q = 5, B = 2)로 두 항을 계산하면
  왼쪽 끝   qB   = 5 × 2  = 10
  오른쪽 끝  n²/B = 25 / 2 = 12.5
  합 22.5   └ 앞에서 실제로 센 11칸이 이 상한 안에 든다
```

구역이 바뀌는 자리에서 `curL` 이 `B` 칸을 넘게 이동할 수 있습니다. 그 자리는 `n/B` 번뿐이라
합쳐도 `2n` 이하이고, 증가 차수를 바꾸지 않으므로 위 식에 따로 적지 않았어요.

**남은 것은 `B` 를 정하는 일입니다.** 두 항은 `B` 에 대해 반대로 움직입니다.

```text
B 가 커지면    qB 는 비례해 늘어나고     n²/B 는 반비례해 줄어든다
B 가 작아지면  qB 가 줄어들고            n²/B 가 늘어난다
               └ 한쪽이 늘 때 다른 쪽이 주니, 합이 가장 작은 곳은 두 항이 같아지는 자리다
```

$$q B = \frac{n^2}{B} \;\Longrightarrow\; B^2 = \frac{n^2}{q} \;\Longrightarrow\; B = \frac{n}{\sqrt{q}} \;\xrightarrow{\;n = q\;}\; B = \sqrt{n}$$

제약 규모 `n = q = 10^4` 를 넣고 `B` 를 세 가지로 계산해 봅시다.

| `B` | 왼쪽 끝 `qB` | 오른쪽 끝 `n²/B` | 합 |
| --- | --- | --- | --- |
| 10 | 100,000 | 10,000,000 | 10,100,000 |
| **100** = √n | **1,000,000** | **1,000,000** | **2,000,000** |
| 1,000 | 10,000,000 | 100,000 | 10,100,000 |

`B = √n` 에서 총 이동이 `O((n + q)\sqrt{n})` 이 되고, 「아이디어 상세」에서 센 1억 칸이 200만
규모가 됩니다. 그리고 처음의 의문에 답이 나왔어요 — `n = 16` 에서 값으로 본 「가운데가 가장
적다」는 이 식의 특수한 경우입니다. `n = q = 16` 이면 `B = √16 = 4` 이고, 실제로 42칸으로
가장 적었습니다.

### 불변식 — `count` 는 창 안의 개수이고 `distinct` 는 그중 0 이 아닌 것의 수다

파트 1 에서 코드가 동작하는 것을 열여섯 단계로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지, 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 문장으로 세우고,
그것이 실제로 유지되는지 확인해 봅시다.

> 어느 시점에나 `count[v]` 는 창 `[curL, curR]` 안에 값 `v` 가 몇 개 있는지이고,
> `distinct` 는 그중 개수가 1 이상인 `v` 의 가짓수입니다.

```text
넓히기   add(v)     count[v] 0→1 이면 distinct++     (없던 값이 처음 들어왔다)
좁히기   remove(v)  count[v] 1→0 이면 distinct--     (마지막 하나가 빠졌다)
```

「어느 시점에나」가 중요합니다. 질의를 끝낸 시점만이 아니라 **창이 한 칸 이동한 직후마다**
참이라는 뜻이에요. 그래야 답을 아무 때나 읽어도 맞습니다.

**출발점부터 봅시다.** 창이 비어 있을 때(`curL = 0`, `curR = −1`) 맵도 비어 있고
`distinct = 0` 이므로 두 문장이 참입니다. 그 뒤로 창은 **한 칸씩만** 바뀌고, 한 칸이 바뀔
때 `add` 나 `remove` 가 정확히 한 번 불려요. `add` 는 개수를 1 늘리고 그 값이 0에서 1이
될 때만 가짓수를 늘립니다. `remove` 는 개수를 1 줄이고 1에서 0이 될 때만 가짓수를 줄여요.
개수가 정확하면 「0 이 아닌 키의 수」도 정확하니, 매 칸 이동 뒤에도 두 문장이 함께 유지
됩니다.

```text
빈 창 [0,−1]     count {}          distinct 0        ← 두 문장이 참이다
  ↓ add(v)       count[v] 를 +1    0→1 일 때만 distinct +1
  ↓ remove(v)    count[v] 를 −1    1→0 일 때만 distinct −1
한 칸 이동 뒤    count 가 맞으면 「0 이 아닌 키의 수」도 맞다   ← 두 문장이 다시 참이다
```

그러면 여기서 질문 하나. 같은 창에 **다른 경로로** 도착하면 답이 달라질까요?

```text
arr = [1, 1, 2, 1, 3] 에서 같은 창 [1,3] 에 도착하는 두 경로
  경로 A   [0,2] → [1,3]    L− 1번, R+ 1번
  경로 B   [0,4] → [1,3]    L− 1번, R− 1번
둘 다 창 [1,3] 의 값은 1 2 1  →  count{1:2, 2:1}  →  distinct = 2
```

달라지지 않습니다. 불변식이 창 `[curL, curR]` 의 **내용**만 말하고 도착 경로를 말하지 않기
때문이에요. **질의를 재정렬해도 되는 근거가 바로 이것입니다** — 순서를 어떻게 바꿔도 각
질의를 읽는 시점의 창 내용은 같고, 답을 원래 자리 `i` 에 넣어 돌려주므로 호출한 쪽이 받는
결과도 같습니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 질의 0개 | 첫 줄에서 바로 반환 | `[]` |
| `l = r` | 창이 한 칸. `add` 한 번 | 항상 `1` |
| 모든 값이 같음 | `count` 에 키가 하나뿐 | 항상 `1` |
| `n = 1` | `B = max(1, ⌊√1⌋) = 1` | 0으로 나누는 일이 없다 |

마지막 줄이 파트 1 의 `Math.max(1, …)` 가 있는 이유입니다. 거기서 `block` 이 0이 되면
`blk(l)` 이 `Infinity` 가 되고 비교 함수가 `NaN` 을 돌려주는 것을 값으로 확인했어요.

**이제 깨뜨려 봅시다.** 불변식을 지키던 줄이 어느 것인지는 지워 보면 바로 알 수 있습니다.
`add` 에서 가짓수를 **0↔1 경계에서만** 늘리던 조건 한 줄을 없앱니다. 개수를 늘리는 것은
그대로 둡니다.

```ts
const add = (value: number): void => {
  const next = (count.get(value) ?? 0) + 1;
  count.set(value, next);
  distinct++;            // ← `if (next === 1)` 을 지웠다
};
```

`mosAlgorithm([1,1,2,1,3], [[0,4],[0,2],[2,4],[1,3],[2,3]])` 을 실행하면 이렇게 나옵니다.

```text
바른 코드   [3, 2, 3, 2, 2]
조건 지움   [6, 3, 6, 4, 5]      ← 전부 부풀었다
```

`[0,4]` 의 답이 3 이 아니라 6 입니다. 배열 `[1, 1, 2, 1, 3]` 에 값은 세 가지뿐인데 6이 나온
것은 **같은 값을 넣을 때마다 가짓수를 늘렸기** 때문이에요 — `1` 이 세 번 들어가며 3을
더했습니다. 불변식의 뒷문장(「`distinct` 는 개수가 1 이상인 `v` 의 가짓수」)이 깨진 것이고,
`count` 는 여전히 맞으므로 **앞문장만 남고 뒷문장이 성립하지 않는 상태**입니다.

`remove` 쪽 조건(`next === 0`)은 그대로라 빼는 쪽만 정상이고, 그래서 값이 일관되게 부풀지도
않아요. 「수행으로 알아보는 알고리즘」의 T2와 T6이 정확히 이 조건이 작동하는 자리였습니다 —
둘 다 값 `1` 을 건드렸는데 `distinct` 가 바뀌지 않았죠.

### 비용 계산

#### 비용을 세는 과정

한 번의 호출이 하는 일은 셋이고, 셋을 다 더해야 총식이 됩니다.

- **질의 정렬** — `q` 개를 정렬합니다. `O(q \log q)`.
- **창 이동** — T1\~T16 에서 실제로 이동한 칸이 11칸이었어요. 일반의 상한은 「수식 정의와
  유도」의 `qB + (n/B)n` 이고, `B = √n` 에서 `O((n + q)\sqrt{n})` 입니다.
- **셈 갱신** — 창이 한 칸 이동할 때마다 해시 맵을 한 번 조회합니다. 이동 칸 수에 비례해요.

```text
총식 = O(q log q)  +  O((n + q)√n)  +  O(이동 칸 수 × 맵 1회)
                ↑ 전처리        ↑ 지배항
n = q = 10^4 이면   10^4·14 ≈ 1.4×10^5   +   2×10^4·100 = 2×10^6
```

정렬 항은 지배항의 1/14 쯤이라 흔히 생략됩니다. 그래도 **총식에는 한 번 정확히 적어요** —
`q` 가 `n` 보다 훨씬 크면 `q \log q` 가 앞설 수도 있기 때문입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최악의 경우** | `O((n+q)\sqrt{n})` | `Θ((n+q)\sqrt{n})` — 이동 상한을 실제로 채우는 질의 집합이 있다 |
| **평균적인 경우** | `O((n+q)\sqrt{n})` | 같다 — **분포와 무관하게 같은 증가 차수**다 |

퀵 정렬 같은 알고리즘과 달리 여기서는 최악과 평균이 **갈리지 않습니다.** 블록 정렬이 이동
상한을 입력과 무관하게 제한하기 때문이에요. 평균이 더 좋아 보이는 것은 상수뿐입니다.

**보장의 종류가 하나 섞여 있습니다.** 창 이동 상한은 **최악 보장**이지만, 셈 갱신에 쓰는
해시 맵의 한 번 조회는 **평균 `O(1)`** 이에요. 그러니 위 표의 값은 엄밀히 말해 「해시가
평균대로 동작한다는 가정 아래의 최악」입니다. 최악까지 확정하고 싶으면 값을 좌표압축해
배열로 세면 되고, 그때는 전처리에 `O(n \log n)` 이 더 붙어요.

#### 최악을 만드는 입력

상한을 실제로 채우는 입력이 정말 있을까요? 만들어 봅시다. **왼쪽 끝은 한 구역 안에 모아
두고 오른쪽 끝을 양극단으로** 흔들면 됩니다. 같은 구역 안이라 `r` 로 정렬되지만, 구역이
바뀌는 순간 `curR` 이 되돌아가요.

```text
n=400, block=20 일 때
  구역 0 의 질의들:  [0,399] [1,398] [2,397] …   r 이 큰 값에 몰려 있다
  구역 1 로 넘어가며  curR 이 399 → 작은 값으로 되돌아간다
  구역이 n/B = 20 개  →  되돌아감이 20번, 매번 최대 n=400 칸
```

`n`·`q` 를 최대(`10^4`)로 잡고 이 모양을 만들면 이동이 `2 \times 10^6` 칸 규모가 됩니다.
1초 제한에는 들어가지만 **여유가 크지 않아요** — `n` 이 한 자릿수만 더 커져도 위험합니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 질의를 **다시 정렬해서** 창의 총 이동을 줄였고,
그 정렬 키는 `(blk(l), r)` 이며, 창이 정확한 답을 주는 근거는 `count` 와 `distinct` 의
불변식입니다.

```text
질의를 받는다 → (blk(l), r) 로 정렬 → 창을 이동시키며 add·remove → 답을 원래 자리 i 에
                     └ B = √n 에서 이동이 가장 적다      └ 0↔1 경계에서만 distinct 가 움직인다
```

먼저 답이 붙는 문제 하나입니다. 구역 크기 `B` 를 `√n` 이 아니라 **1로** 두면 이동 상한이
얼마가 될까요? `n = q = 10^4` 를 상한식 `qB + (n/B)·n` 에 넣어 계산해 보세요.

```text
B = √n = 100   →   10^6 + 10^6 = 2 × 10^6      (앞에서 계산한 값)
B = 1          →   ?                            ← 이 자리를 직접 채워 봅시다
```

<!--check:blockone-->
`B = 1` 을 넣으면 `10^4 · 1 + 10^4 · 10^4 = 10^4 + 10^8 ≈ 10^8` 입니다.

```text
B = 1     qB = 10^4 · 1 = 10^4      (n/B)·n = 10^4 · 10^4 = 10^8      합 ≈ 10^8
B = 100   qB = 10^4 · 100 = 10^6    (n/B)·n = 10^2 · 10^4 = 10^6      합 = 2 × 10^6
                                                                       └ 50배 차이
```

「아이디어 상세」에서 본 순진한 방법(1억 칸)과 같은 자리로 되돌아갔습니다. `B` 를 1로 두면
구역이 `n` 개가 되어 `curR` 이 `n` 번 되돌아가기 때문이에요.
<!--/check-->

```text
아래 넷은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 수행으로 알아보는 알고리즘 의 T2·T6      3 → 비용 계산
  2 → 아이디어 상세                            4 → 불변식
```

- `l` 만 정렬해도 `curL` 은 한 방향으로만 이동하는데, 왜 그것으로는 부족할까요?
- 총식에서 정렬 항 `O(q log q)` 이 흔히 생략되는데, 생략하면 안 되는 상황은 언제일까요?
- 배열이 중간에 바뀌는 문제라면 이 알고리즘의 어느 전제가 깨질까요?
