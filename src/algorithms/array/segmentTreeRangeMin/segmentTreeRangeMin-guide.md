# segmentTreeRangeMin — 반씩 갈라 적어 둔 구간으로 질의는 깊이마다 둘, 갱신은 깊이마다 하나만 만지는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 질의마다 구간을
처음부터 읽는 방법에서 출발해, 반씩 갈라 적어 둔 구간 몇 개로 질의를 덮는 방법까지 갑니다. 그 방법을
단계마다 값으로 풀고, 마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

이 글이 다루는 것은 **원소가 중간중간 바뀌는 배열**에서 구간 최솟값 질의에 답하는 일입니다. 배열이
안 바뀐다면 [Sparse Table](../sparseTableRangeMin/sparseTableRangeMin-guide.md) 이 질의마다 칸 두 개로
답해요. 그런데 Sparse Table 의 칸은 서로 겹쳐 놓여 있어서, 원소 하나를 여러 칸이 함께 덮습니다. 원소
하나가 바뀌면 그 칸들을 모두 고쳐야 해요. 그래서 여기서는 **서로 겹치지 않게 나눈 구간**의 최솟값을
적어 둡니다. 배열 전체를 반으로 가르고, 그 반쪽을 또 반으로 가르는 일을 한 칸이 남을 때까지
되풀이해요. 그렇게 생긴 구간마다 자리를 하나씩 두고 그 자리를 **노드**라고 부르겠습니다. 노드는 자기가
맡은 구간, 곧 **담당 구간**의 최솟값을 하나 적어 둡니다. 노드를 가른 차례대로 이으면 이진 트리가 되고,
이 트리를 **세그먼트 트리**(segment tree)라고 부릅니다. 배열 `[5 2 4 1 3]` 의 세그먼트 트리를 그리면
이렇습니다. 노드 안의 두 줄은 노드의 이름과 「담당 구간=최솟값」이에요.

<!--fig:concept-tree-->
![세그먼트 트리 — 노드마다 담당 구간과 그 최솟값](./figs/concept-tree.svg)

맨 위의 노드1 이 배열 전체 `[0,4]` 를 맡고, 그 아래 노드2 와 노드3 이 `[0,2]` 와 `[3,4]` 로 반씩
나눠 맡습니다. 한 칸짜리 구간을 맡는 노드를 **리프**라고 해요. 리프는 원소를 그대로 적어 두고, 왼쪽부터
인덱스 0 · 1 · 2 · 3 · 4 의 차례로 놓입니다. 리프가 아닌 노드는 자식 둘의 값 가운데 작은 쪽을 적어요.
노드2 는 자식 `[0,1]=2` 와 `[2,2]=4` 가운데 2 를 적었습니다.

이 세그먼트 트리만으로 아무 구간이나 답할 수 있을까요? 구간 `[1,3]` 을 봅시다. 담당 구간이 `[1,3]` 과
똑같은 노드는 없어요. 그래서 담당 구간이 `[1,3]` 안에 **통째로 들어가는** 노드를 골라 이어 붙입니다.

<!--fig:concept-cover-->
![구간 [1,3] 을 겹치지 않는 노드 셋으로 덮기](./figs/concept-cover.svg)

노드9 `[1,1]` · 노드5 `[2,2]` · 노드6 `[3,3]` 을 이어 붙이면 `[1,3]` 이 한 칸도 빠지거나 겹치지 않고
덮입니다. 답은 세 값 2 · 4 · 1 가운데 가장 작은 1 이에요. 같은 배열에 질의 넷을 걸고, 세그먼트 트리가
읽는 조각과 Sparse Table 이 읽는 조각을 나란히 놓았습니다.

<!--proof:concept-compare-->

| 질의 | 세그먼트 트리의 조각 | 조각 수 | Sparse Table 의 조각 | 겹친 칸 | 답 |
| --- | --- | ---: | --- | ---: | ---: |
| [0,4] | [0,4] | 1 | [0,3] [1,4] | 3 | 1 |
| [0,2] | [0,2] | 1 | [0,1] [1,2] | 1 | 2 |
| [1,3] | [1,1] [2,2] [3,3] | 3 | [1,2] [2,3] | 1 | 1 |
| [3,4] | [3,4] | 1 | [3,4] [3,4] | 2 | 1 |

두 구조가 구간을 덮는 방식이 반대입니다. Sparse Table 은 언제나 조각 **둘**로 덮고 그 둘이 겹쳐요.
세그먼트 트리는 조각이 하나일 때도 셋일 때도 있지만 **조각끼리 겹치지 않습니다.** 조각이 몇 개가
되든, 조각마다 노드를 하나씩 정하는 규칙은 셋뿐이에요.

| 노드의 담당 구간과 질의 구간 | 하는 일 |
| --- | --- |
| 한 칸도 안 겹친다 | 이 노드 아래는 보지 않는다 |
| 질의 구간 안에 통째로 들어간다 | 적어 둔 값을 그대로 조각으로 쓴다 |
| 걸쳐 있다 | 자식 둘에게 나눠 묻는다 |

겹치지 않게 나눈 덕을 보는 것은 갱신입니다. 뿌리에서 몇 번 내려온 노드인지를 그 노드의 **깊이**라고
하겠습니다. 원소 하나가 바뀌면 값이 달라질 수 있는 노드는 **그 원소를
담당 구간에 품은 노드**뿐이고, 같은 깊이의 노드는 서로 겹치지 않으니 그런 노드는 깊이마다 하나예요.
`A[3]` 을 1 에서 10 으로 고친 뒤의 세그먼트 트리입니다. 굵은 강조 테가 값이 바뀐 노드예요.

<!--fig:concept-update-->
![A[3] 을 10 으로 고친 뒤 — 값이 바뀐 노드](./figs/concept-update.svg)

같은 갱신에서 두 구조가 고친 칸을 세면 이렇습니다.

<!--proof:concept-update-->

| 구조 | 칸 수 | 인덱스 3 을 덮는 칸 | 값이 바뀐 칸 |
| --- | ---: | ---: | ---: |
| 세그먼트 트리 | 9 | 3 | 3 |
| Sparse Table | 11 | 5 | 5 |

A[3] 을 1 에서 10 으로 고쳤습니다. 세그먼트 트리에서 값이 바뀐 노드는 노드1 · 노드3 · 노드6 입니다.

<!--/proof-->

세그먼트 트리에서는 리프 노드6 에서 뿌리 노드1 까지 이어진 **한 줄기**만 바뀌었습니다. 가르는 일을 한
칸이 남을 때까지 되풀이했으니 그 줄기의 길이는 배열 길이의 로그 규모예요. 그래서 세그먼트 트리를 만드는
데 `O(N)`, 질의 하나와 갱신 하나에 각각 `O(log N)` 이 듭니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 최솟값**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값을 하나도 빼지 않고 볼 때 가장 작은 수입니다.
- **이진 트리**와 **깊이**. 노드마다 자식이 최대 둘이고, 맨 위 노드(뿌리)에서 몇 번 내려왔는지가
  깊이예요.
- **재귀 함수와 종료 조건**. 이 글의 절차는 자기 자신을 두 번 부르고, 구간이 한 칸이 되면 멈춥니다.
- **미리 계산해 두고 질의에 답하는 방식**이 왜 이득인지. 잘 떠오르지 않으면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 를 먼저 읽어 보세요.

같은 과제에서 원소가 안 바뀌는 쪽은
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-guide.md) 이 다룹니다. 그 글을
몰라도 이 글을 읽는 데 지장은 없어요. 두 글이 갈리는 자리는 배열 `[5 2 4 1 3]` 에 물음 둘을 대 보면
확인할 수 있습니다.

<!--proof:prereq-scope-->

| 물음 | 답 | 세그먼트 트리 | Sparse Table |
| --- | ---: | --- | --- |
| 구간 [0,2] 의 최솟값 | 2 | 답한다 | 답한다 |
| A[3] 을 10 으로 고친 뒤 [0,4] 의 최솟값 | 2 | 답한다 | 층을 다시 계산해야 답한다 |

둘째 물음처럼 **갱신이 섞여 들어오는 쪽**이 이 글의 범위입니다.

### 아이디어를 떠올리는 과정 — 질의마다 차례로 읽기에서 반씩 가른 구간으로 덮기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 배열과 연산 목록을 받아서
질의의 답 목록을 돌려줍니다.

```ts
type SegOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

function segmentTreeRangeMin(A: number[], ops: SegOp[]): number[];
```

- 입력: 정수 배열 `A` 와 연산 목록 `ops`. `update` 는 `A[i]` 를 `v` 로 덮어쓰고(더하는 것이 아닙니다),
  `query` 는 **양끝을 포함하는** 구간 `[l, r]` 의 최솟값을 묻습니다. 연산은 목록 순서대로 처리하고,
  갱신은 그 뒤의 모든 질의에 반영돼요.
- 출력: `query` 의 답만 **입력 순서 그대로** 담은 배열입니다. 질의가 하나도 없으면 빈 배열이에요.
- 규모: `1 ≤ N ≤ 100,000`, `0 ≤ Q ≤ 100,000`, `−10^9 ≤ A[i], v ≤ 10^9`, `0 ≤ i < N`,
  `0 ≤ l ≤ r < N`. 비용은 흔한 채점 환경의 예산인 시간 1 초, 메모리 256 MB 에 대어 잽니다.

이 글이 쓰는 기호는 아홉이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 배열 `A` 의 길이 | `N ≤ 100,000` |
| `Q` | 연산 목록 `ops` 의 길이 | `Q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값 | `−10^9` 이상 `10^9` 이하 |
| `i` · `v` | `update` 가 바꿀 자리와 새 값 | `0 ≤ i < N` |
| `l` · `r` | `query` 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r < N` |
| `node` | 트리 배열에서 노드 하나를 가리키는 번호. 뿌리가 `1` 입니다 | `1` 이상 |
| `s` · `e` | 노드 `node` 의 담당 구간의 왼쪽 끝 · 오른쪽 끝 | `0 ≤ s ≤ e < N` |
| `tree[node]` | 노드 `node` 의 담당 구간의 최솟값 | 칸이 `4N` 개 |
| `INF` | 한 칸도 안 겹치는 노드가 돌려주는 값 | `Number.MAX_SAFE_INTEGER` |

출발점은 아무 기법도 쓰지 않는 방법입니다. 질의가 오면 구간을 왼쪽 끝부터 오른쪽 끝까지 한 칸씩
읽으면서 가장 작은 값을 기억하고, 갱신은 배열 칸 하나를 고쳐요.

```ts
for (const op of ops) {
  if (op.type === "update") {
    A[op.i] = op.v; // 칸 하나를 쓴다
  } else {
    let m = INF;
    for (let k = op.l; k <= op.r; k++) m = Math.min(m, A[k] as number);
    result.push(m); // 구간을 처음부터 끝까지 읽는다
  }
}
```

이 글은 비용을 **칸 접근 수**, 곧 배열 칸을 읽거나 쓴 횟수로 셉니다. 이 방법은 갱신 하나에 1 번,
질의 하나에 구간의 칸 수만큼 접근해요. 방법마다 같은 작업 목록으로 재려고 목록 하나를 정했습니다.
갱신과 질의를 번갈아 두고, 질의는 전부 양 끝을 한 칸씩 안으로 당긴 `[1, N−2]` 예요. 거의 배열
전체를 읽는 모양이라 이 방법에는 최악에 가깝습니다.

<!--proof:cost-scan-->

| N = Q | 칸 접근(실측) | (Q/2)(N−2) + Q/2 | 초당 1 억 번 기준 |
| ---: | ---: | ---: | ---: |
| 1,000 | 499,500 | 499,500 | 0.01 초 미만 |
| 10,000 | 49,995,000 | 49,995,000 | 0.50 초 |
| 100,000 | (실행하지 않음) | 4,999,950,000 | 50.00 초 |

실측이 식과 두 규모에서 같으니, 제약의 최대 크기에서는 식이 곧 접근 수입니다. 약 50 억 번이고,
단순한 연산을 1 초에 1 억 번 한다고 잡아도 50 초가 걸려요. 예산이 1 초이니 이 방법으로는 안 됩니다.
질의 하나가 구간 길이만큼 읽는 것이 원인이니, 최솟값을 **미리 적어 두고** 질의가 적어 둔 값을 읽게
해야 합니다.

구간 합이었다면 이미 답이 있어요. 앞에서부터 누적한 합을 적어 두면 구간의 합이 두 칸의 차이로 바로
나옵니다. 최솟값에 같은 방법을 옮겨 봅시다. 칸 `i` 에 `A[0]` 부터 `A[i]` 까지의 최솟값을 적은 표를
**접두 최솟값 표** `m` 이라고 하고, 질의 `[l, r]` 에 `m[r]` 을 답으로 내밀어 봅니다.

<!--proof:prefix-min-fails-->

| 질의 | 정본의 답 | 접두 최솟값 표의 답 | 판정 |
| --- | ---: | --- | --- |
| [0,4] | 1 | m[4] = 1 | 같다 |
| [0,2] | 2 | m[2] = 2 | 같다 |
| [1,3] | 1 | m[3] = 1 | 같다 |
| [2,2] | 4 | m[2] = 2 | 다르다 |
| [4,4] | 3 | m[4] = 1 | 다르다 |

배열 [5 2 4 1 3] 의 접두 최솟값 표는 m = [5 2 2 1 1] 입니다.

<!--/proof-->

왼쪽 끝이 0 인 질의 둘은 정의상 맞고, 나머지 셋은 우연에 달렸습니다. `[1,3]` 은 맞고 `[2,2]` 와
`[4,4]` 는 틀려요. 여기서 헷갈리기 쉬운 부분은 「합은 되는데 왜 최솟값은 안 되나」입니다. 합은 뺄셈으로
앞부분을 덜어 낼 수 있는데, 최솟값에는 덜어 내는 연산이 없어요.

| 연산 | 앞의 3 과 뒤의 5 를 합친 결과 | 앞의 3 을 덜어 낸 결과 |
| --- | --- | --- |
| 덧셈 | 3 + 5 = 8 | 8 − 3 = 5. 뒤의 값을 되찾는다 |
| 최솟값 | min(3, 5) = 3 | 덜어 낼 방법이 없어 5 를 되찾지 못한다 |

왼쪽 끝이 0 이 아닌 구간의 최솟값도 따로 적어 두어야 합니다. 그렇게 적어 두는 구조가 이미 하나
있어요. 칸 수가 2 의 거듭제곱인 구간을 **모든 시작 자리에** 적어 두고 질의를 겹치는 두 조각으로 덮는
Sparse Table 입니다. 질의는 칸 두 개로 끝나니 이 과제의 질의 쪽은 해결돼요. 걸리는 것은 갱신입니다.
칸들이 겹쳐 놓여 있어서 원소 하나를 덮는 칸이 층마다 여럿이고, 갱신 하나가 그 칸을 모두 다시 계산해야
해요. 가운데 원소를 고칠 때 다시 계산할 칸을 배열 크기별로 세었습니다.

<!--proof:origin-sparse-update-->

| N | 고치는 자리 i | Sparse Table 칸 수 | i 를 덮는 칸 | 세그먼트 트리에서 i 를 품는 노드 |
| ---: | ---: | ---: | ---: | ---: |
| 5 | 2 | 11 | 5 | 3 |
| 1,000 | 500 | 8,987 | 1,000 | 11 |
| 100,000 | 50,000 | 1,568,946 | 100,000 | 18 |

고치는 자리는 가운데 인덱스 ⌊N/2⌋ 입니다.

<!--/proof-->

`N = 100,000` 이면 원소 하나를 덮는 칸이 100,000 개입니다. 칸마다 아래층 두 칸을 다시 읽어야 하니,
칸 두 개로 끝나는 질의와 달리 갱신 하나가 배열 길이 규모의 일을 합니다. 오른쪽 끝 열은 겹치지 않게 반씩 가른 구간(세그먼트 트리)에서
같은 원소를 품은 노드의 수이고, 18 개뿐입니다. 갱신이 커지는 까닭이 겹침이니, 이번에는 **겹치지 않게 나눈 묶음**을
시험해 봅시다. 배열을 `B` 칸씩 끊어 묶음마다 최솟값 하나를 적어 두는 방법이에요. 질의는 통째로 들어가는
묶음의 값을 읽고 양 끝의 남는 칸만 배열에서 읽습니다. 갱신은 그 칸이 든 묶음 하나를 다시 읽어요.
다섯 칸짜리 배열로는 묶음 크기를 갈라 보기에 너무 작아서, 같은 생성식으로 만든 1,024 칸 배열에 갱신과
질의를 512 개씩 번갈아 건 목록으로 셌습니다.

<!--proof:cost-two-ways-->

| 묶음 크기 | 미리 만들기 | 질의 | 갱신 | 합 | 추가 칸 |
| --- | ---: | ---: | ---: | ---: | ---: |
| B=1 | 2,048 | 172,544 | 1,536 | 176,128 | 1,024 |
| B=32 | 1,056 | 20,768 | 17,408 | 39,232 | 32 |

두 묶음 크기의 답은 정본과 같습니다. 질의는 172,544 에서 20,768 로 줄고, 갱신은 1,536 에서 17,408 로 늘었습니다.

<!--/proof-->

여기서 관찰할 것은 **두 비용이 반대 방향으로 움직인다**는 것 하나입니다. 묶음을 키우면 질의가 읽는
칸이 줄고, 갱신이 다시 읽는 칸이 늘어요. 크기가 하나뿐인 묶음으로는 두 비용을 함께 줄일 수 없습니다.
그렇다면 **크기가 다른 묶음을 층층이** 두면 어떨까요. 배열 전체를 반으로, 반쪽을 다시 반으로 가르면
큰 묶음과 작은 묶음이 모두 생깁니다. 질의는 큰 묶음을 먼저 쓰고 모자란 자리만 작은 묶음으로 채우고,
갱신은 원소를 품은 묶음만 층마다 하나씩 고치면 돼요. 지금까지의 방법을 과제 규모에서 같은 작업 목록으로
세었습니다. 한 층 묶음의 크기는 `B = ⌊√N⌋` 으로 두었어요.

<!--proof:origin-scale-->

| 방법 | 미리 만들기 | 질의 | 갱신 | 합 | 초당 1 억 번 기준 | 센 방법 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 차례로 읽기 | 0 | 4,999,900,000 | 50,000 | 4,999,950,000 | 50.00 초 | 식 |
| Sparse Table | 4,606,838 | 100,000 | 11,070,812,015 | 11,075,518,853 | 110.76 초 | 식 |
| 한 층 묶음 B=316 | 100,317 | 38,650,000 | 15,887,616 | 54,637,933 | 0.55 초 | 실행 |
| 세그먼트 트리 | 499,997 | 1,550,000 | 2,553,392 | 4,603,389 | 0.05 초 | 실행 |

N = Q = 100,000 이고 갱신과 질의가 50,000 개씩입니다. 「식」 줄은 같은 식이 N = Q = 1,000 에서 실행한 값과 같은 것을 확인하고 식으로 셌습니다.

<!--/proof-->

Sparse Table 은 질의 5 만 개를 100,000 번에 끝내지만 갱신에 110 억 번 넘게 씁니다. 한 층 묶음은 0.55
초로 예산 안에 들지만, 반씩 가른 구간은 그보다 열 배 넘게 적은 4,603,389 번이에요. 지금까지 해 본 방법
다섯을 차례로 놓으면 이렇습니다. 앞 방법이 막힌 자리에서 다음 방법이 나왔고, 넷은 버리고 하나가
남았어요.

<!--fig:origin-approaches-->
![시도한 방법 다섯 — 넷은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **반씩 가른 구간으로 덮기**입니다. 배열을 반씩 갈라 생긴 구간마다
최솟값을 적어 두고, 질의 구간은 그런 구간 가운데 겹치지 않는 몇 개로 덮어 답해요. 무엇을 어떤 번호로
적어 두는지, 어떻게 채우는지, 질의가 어느 구간을 고르는지, 갱신이 어디까지 고치는지는 다음 절에서
실현하는 순서대로 확인합니다.

### 아이디어 상세 — 반씩 가른 구간으로 덮기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **배열을 반씩 갈라 생긴 구간마다 최솟값을 노드에 적어
두고, 질의는 담당 구간이 질의 안에 통째로 드는 노드 몇 개로 덮어 그 값의 최솟값을 답하며, 갱신은 그
원소를 품은 노드만 고칩니다.** 이 방법은 세그먼트 트리라는 구조 위에서 동작하는데, 처음 보는 사람에게는
그 구조부터 낯설어요. 그래서 세그먼트 트리를 먼저 따로 설명하고, 그다음 실현하는 순서대로 다섯 단계를
설명합니다. 앞 단계에서 만든 것을 뒤 단계에서 쓰는 순서예요.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 연산 전에 한 번 | 1단계 노드 번호와 담당 구간 정하기 | 노드마다 번호와 담당 구간을 정하고 트리 배열을 잡는다 | — |
| 연산 전에 한 번 | 2단계 리프부터 위로 값 채우기 | 노드마다 담당 구간의 최솟값을 적는다 | 1단계의 번호와 담당 구간 |
| 질의마다 | 3단계 노드마다 세 갈래로 판정하기 | 담당 구간과 질의 구간을 비교해 버리거나 읽거나 나눈다 | 1단계의 담당 구간 |
| 질의마다 | 4단계 조각의 최솟값 모으기 | 읽은 값을 하나로 합친다 | 2단계의 값 · 3단계의 조각 |
| 갱신마다 | 5단계 리프를 고치고 그 줄기만 다시 계산하기 | 원소를 품은 노드만 새 값으로 고친다 | 1단계의 번호 · 2단계의 채우는 규칙 |

#### 먼저 알아 둘 개념 — 세그먼트 트리

세그먼트 트리는 **배열을 반씩 가르는 일을 한 칸이 남을 때까지 되풀이해 생긴 구간마다 노드를 하나씩 두고,
노드에 그 구간의 최솟값을 적은 이진 트리**입니다. 노드의 자식 둘은 그 노드의 담당 구간을 반으로 가른
두 조각을 맡아요. 여기서 헷갈리기 쉬운 부분이 하나 있습니다. 이 글에서 「칸」과 「노드」는 다른 것을
가리켜요.

| 이름 | 맡는 자리 | 담는 값 | 이 글에서 쓰는 곳 |
| --- | --- | --- | --- |
| 배열의 칸 | 인덱스 하나 | 그 자리의 값 하나 | `A[i]`, 「구간의 칸 수」라고 할 때 |
| 노드 | 담당 구간의 칸 여러 개 | 담당 구간의 최솟값 하나 | `tree[node]` 가 가리킬 때 |

##### 노드가 맡는 자리

노드 아홉 개를 배열 아래에 한 줄씩 그려 보겠습니다. 줄마다 그 노드가 맡는 자리에만 배열 값을 남겼고,
오른쪽 끝에 노드에 적힌 값을 적었어요. 같은 깊이의 노드를 한 묶음으로 모았습니다.

<!--fig:build-bars-->
![노드마다 맡는 자리 — 깊이마다 한 묶음](./figs/build-bars.svg)

그림을 위에서 아래로 읽으면 세그먼트 트리를 이렇게 떠올릴 수 있습니다. 깊이 0 의 노드 하나가 배열
전체를 맡고, 깊이가 하나 내려갈 때마다 노드가 맡는 자리가 반으로 줄어요. 한 묶음 안의 노드는 **서로
다른 자리**를 맡고, 왼쪽부터 빈틈없이 이어집니다. 깊이 3 에 노드가 둘뿐인 까닭은 깊이 2 의 노드 가운데
`[0,1]` 만 두 칸이라 더 갈릴 수 있기 때문이에요. 나머지 셋은 이미 한 칸이라 리프입니다.

##### 노드 하나를 읽는 법

노드는 번호 하나로 부릅니다. 뿌리가 1 이고, 노드 `node` 의 왼쪽 자식은 `2·node`, 오른쪽 자식은
`2·node+1` 이에요. 담당 구간 `[s, e]` 는 가운데 `mid = ⌊(s+e)/2⌋` 에서 `[s, mid]` 와 `[mid+1, e]` 로
갈립니다. 노드5 를 골라 뿌리에서부터 따라가 보겠습니다.

<!--proof:node-read-->

| 노드 | 담당 구간 | 다음 |
| --- | --- | --- |
| 노드1 | [0,4] | mid = 2, 왼쪽 자식 2·1 = 2 가 [0,2] 를 맡는다 |
| 노드2 | [0,2] | mid = 1, 오른쪽 자식 2·2+1 = 5 가 [2,2] 를 맡는다 |
| 노드5 | [2,2] | s = e 라 리프, 값은 A[2] = 4 |

번호 5 는 `2·2+1` 이니 노드2 의 오른쪽 자식이고, 노드2 는 `2·1` 이니 뿌리의 왼쪽 자식입니다. 그래서
노드5 는 뿌리의 담당 구간 `[0,4]` 에서 왼쪽 반 `[0,2]`, 그 오른쪽 반 `[2,2]` 로 두 번 갈라 들어간
자리이고, 적힌 값은 `A[2] = 4` 예요. 조심할 점이 하나 있습니다. 번호는 **담당 구간의 크기가 아니라 가른
차례**를 적은 것이에요. 노드5 와 노드8 은 둘 다 한 칸짜리 리프지만 깊이가 다릅니다.

##### 부모와 자식, 같은 깊이의 노드

같은 깊이의 노드들이 배열을 어떻게 나눠 갖는지 세어 보겠습니다.

<!--proof:node-depths-->

| 깊이 | 노드와 담당 구간 | 맡은 인덱스 수 | 두 번 맡은 인덱스 |
| --- | --- | ---: | ---: |
| 깊이 0 | 노드1 [0,4] | 5 | 0 |
| 깊이 1 | 노드2 [0,2] · 노드3 [3,4] | 5 | 0 |
| 깊이 2 | 노드4 [0,1] · 노드5 [2,2] · 노드6 [3,3] · 노드7 [4,4] | 5 | 0 |
| 깊이 3 | 노드8 [0,0] · 노드9 [1,1] | 2 | 0 |

자식이 있는 노드 4 개 가운데 4 개에서, 왼쪽 자식의 구간 바로 뒤에 오른쪽 자식의 구간이 이어지고 둘을 합치면 부모의 구간입니다.

<!--/proof-->

두 가지 관계가 보입니다. 하나는 **같은 깊이의 노드는 한 인덱스를 두 번 맡지 않는다**는 것이에요. 마지막
열이 네 줄 모두 0 입니다. 다른 하나는 **부모의 담당 구간은 자식 둘의 구간을 이어 붙인 것**이라는
거예요. 그래서 부모의 최솟값은 자식 둘의 최솟값 가운데 작은 쪽이고, 인덱스 하나를 품은 노드는 깊이마다
많아야 하나입니다.

##### Sparse Table 의 층과의 차이

「구간마다 최솟값을 적어 둔다」까지는 Sparse Table 과 같아서 둘을 섞어 떠올리기 쉽습니다. Sparse Table
은 칸 수가 같은 구간을 **모든 시작 자리에** 두어 칸끼리 겹치고, 세그먼트 트리는 한 번 가른 조각만 두어
노드끼리 겹치지 않아요. 같은 배열 크기에서 세면 이렇습니다.

<!--proof:node-vs-layers-->

| N | 세그먼트 트리 노드 | Sparse Table 칸 | 가운데 원소를 품는 노드 | 가운데 원소를 덮는 칸 | 질의 하나가 읽는 노드(최대) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 9 | 11 | 3 | 5 | 3 |
| 1,000 | 1,999 | 8,987 | 11 | 1,000 | 17 |

가운데 원소는 인덱스 ⌊N/2⌋ 이고, 「최대」는 모든 (l, r) 짝을 다 넣어 잰 값입니다. Sparse Table 이 질의 하나에 읽는 칸은 늘 2 개입니다.

<!--/proof-->

`N = 1,000` 에서 세그먼트 트리는 노드가 1,999 개로 Sparse Table 의 칸 8,987 개보다 적고, 원소 하나를
품은 노드도 11 개뿐입니다. 그 대신 질의 하나가 노드를 17 개까지 읽어요. Sparse Table 은 겹쳐 놓은 칸
덕에 질의가 칸 둘로 끝나고, 같은 겹침 때문에 원소 하나를 1,000 칸이 덮습니다.

##### 겹치지 않게 반씩 가르는 까닭

이 모양은 갱신과 질의를 **둘 다** 깊이 수에 묶으려고 이렇게 생겼습니다. 두 요구가 모양의 서로 다른
성질에 기대요.

| 요구 | 기대는 성질 | 그래서 |
| --- | --- | --- |
| 갱신이 적게 고친다 | 같은 깊이의 노드가 겹치지 않는다 | 원소를 품은 노드가 깊이마다 많아야 하나다 |
| 질의가 적게 읽는다 | 부모가 자식 둘로 반씩 갈린다 | 질의의 양 끝 경계가 지나는 노드가 깊이마다 많아야 하나씩이다 |
| 깊이가 얕다 | 가를 때마다 담당 구간이 반이 된다 | 깊이가 배열 길이의 로그 규모다 |

겹치지 않게만 나누고 반씩 가르지 않으면 앞 절의 한 층 묶음이 되어 질의와 갱신 중 한쪽이 커지고, 반씩
가르되 모든 시작 자리에 두면 Sparse Table 이 되어 갱신이 커집니다.

#### 1단계 — 노드 번호와 담당 구간 정하기

세그먼트 트리를 만들려면 먼저 노드를 몇 개 두고, 노드마다 어떤 번호와 담당 구간을 줄지 정해야 합니다.
규칙은 넷이에요.

| 노드 | 담당 구간 | 뜻 |
| --- | --- | --- |
| `node = 1` | `[0, N−1]` | 뿌리가 배열 전체를 맡는다 |
| `2·node` | `[s, mid]` | 왼쪽 자식이 왼쪽 반을 맡는다 |
| `2·node + 1` | `[mid+1, e]` | 오른쪽 자식이 오른쪽 반을 맡는다 |
| `s = e` 인 노드 | 한 칸 | 더 가르지 않는다. 리프다 |

번호를 이렇게 매기면 포인터 없이 배열 하나 `tree` 에 노드를 담고, 곱셈 하나로 자식을 찾을 수 있어요.
배열 `[5 2 4 1 3]` 의 노드 아홉에 적용한 결과입니다.

<!--proof:tree-build-->

| 노드 | 담당 구간 | 깊이 | 자식 | 값 |
| --- | --- | ---: | --- | ---: |
| 노드1 | [0,4] | 0 | 노드2 · 노드3 | 1 |
| 노드2 | [0,2] | 1 | 노드4 · 노드5 | 2 |
| 노드3 | [3,4] | 1 | 노드6 · 노드7 | 1 |
| 노드4 | [0,1] | 2 | 노드8 · 노드9 | 2 |
| 노드5 | [2,2] | 2 | 없음 (리프) | 4 |
| 노드6 | [3,3] | 2 | 없음 (리프) | 1 |
| 노드7 | [4,4] | 2 | 없음 (리프) | 3 |
| 노드8 | [0,0] | 3 | 없음 (리프) | 5 |
| 노드9 | [1,1] | 3 | 없음 (리프) | 2 |

번호가 1 부터 9 까지 빈 자리 없이 이어진 것은 이 입력에서 그렇게 된 것뿐입니다. 번호는 가른 차례를
적은 것이라, 배열 길이에 따라 중간 번호가 비고 가장 큰 번호가 `2N` 을 넘기도 해요. 그래서 `tree` 는
넉넉히 `4N` 칸으로 잡습니다. `4N` 이면 늘 충분한 까닭과 `2N` 이 모자란 길이는 「수식 정의와 유도」에서
값으로 확인해요. 칸 수는 `N` 에만 달렸고 값에는 안 달렸습니다.

#### 2단계 — 리프부터 위로 값 채우기

노드의 값은 자식 둘의 값에서 나오므로 **자식을 먼저** 채워야 합니다. 뿌리에서 재귀로 내려가 리프에
이르면 `A[s]` 를 그대로 적고, 돌아오면서 부모에 자식 둘의 작은 쪽을 적어요. 그래서 채우는 차례는 번호
순도 깊이 순도 아니라 **재귀가 돌아오는 순서**입니다.

<!--proof:build-order-->

| 차례 | 채우는 노드 | 읽은 값 | 쓴 값 |
| ---: | --- | --- | ---: |
| 1 | 노드8 [0,0] | A[0] = 5 | 5 |
| 2 | 노드9 [1,1] | A[1] = 2 | 2 |
| 3 | 노드4 [0,1] | min(노드8, 노드9) = min(5, 2) | 2 |
| 4 | 노드5 [2,2] | A[2] = 4 | 4 |
| 5 | 노드2 [0,2] | min(노드4, 노드5) = min(2, 4) | 2 |
| 6 | 노드6 [3,3] | A[3] = 1 | 1 |
| 7 | 노드7 [4,4] | A[4] = 3 | 3 |
| 8 | 노드3 [3,4] | min(노드6, 노드7) = min(1, 3) | 1 |
| 9 | 노드1 [0,4] | min(노드2, 노드3) = min(2, 1) | 1 |

믿기 전에 확인해 둘 자리가 두 곳 있습니다. 하나는 **리프의 깊이가 다른 자리**예요. 노드5 는 깊이 2 에서
리프가 되고 노드8 · 노드9 는 깊이 3 에서 리프가 되는데, 차례 4 의 노드5 는 자기 담당 구간이 한 칸이라
그 자리에서 `A[2]` 를 적고 돌아갑니다. 깊이가 달라도 「담당 구간이 한 칸이면 리프」라는 조건 하나로
멈춰요. 다른 하나는 **부모를 적는 순간 자식이 이미 차 있는가**입니다. 표에서 부모 줄은 언제나 두 자식
줄보다 아래에 있어요. 재귀가 두 자식을 다 부르고 돌아온 뒤에야 부모 줄을 실행하기 때문입니다. 아홉
줄이 노드 아홉에 하나씩이니, 채우지 않고 남는 노드도 두 번 채우는 노드도 없어요.

#### 3단계 — 노드마다 세 갈래로 판정하기

여기부터는 질의가 올 때마다 하는 일입니다. 질의 `[l, r]` 이 오면 뿌리에서 시작해, 방문한 노드마다 담당
구간 `[s, e]` 와 질의 구간을 비교해 셋 중 하나로 판정해요.

| 판정 | 조건 | 하는 일 |
| --- | --- | --- |
| 겹치지 않는다 | `r < s` 또는 `e < l` | 이 노드 아래는 보지 않고 `INF` 를 돌려준다 |
| 통째로 들어간다 | `l ≤ s` 이고 `e ≤ r` | 적어 둔 `tree[node]` 를 돌려준다 |
| 걸쳐 있다 | 위의 둘이 모두 아니다 | 자식 둘에게 같은 질의를 묻는다 |

셋째 갈래만 아래로 내려갑니다. 질의가 노드의 담당 구간과 맞을 때와 안 맞을 때를 세 질의로 비교해 봅시다.

<!--proof:range-split-->

| 질의 | 방문 노드 | 읽은 노드 | 읽은 자리 | 답 |
| --- | ---: | ---: | --- | ---: |
| [0,4] | 1 | 1 | 노드1 [0,4] | 1 |
| [0,2] | 3 | 1 | 노드2 [0,2] | 2 |
| [1,3] | 9 | 3 | 노드9 [1,1] · 노드5 [2,2] · 노드6 [3,3] | 1 |

`[0,4]` 는 뿌리와 담당 구간이 같아 한 번에 끝나고, `[0,2]` 는 노드2 와 같아 뿌리를 거쳐 셋만
들어갑니다. 불안한 경우는 `[1,3]` 이에요. 담당 구간이 같은 노드가 없어서 노드 아홉에 모두 들어갑니다.
들어간 차례대로 판정을 적으면 이렇습니다.

<!--proof:split-13-->

| 차례 | 노드 | 판정 | 하는 일 |
| ---: | --- | --- | --- |
| 1 | 노드1 [0,4] | 걸쳐 있다 ③ | 자식 둘에게 묻는다 |
| 2 | 노드2 [0,2] | 걸쳐 있다 ③ | 자식 둘에게 묻는다 |
| 3 | 노드4 [0,1] | 걸쳐 있다 ③ | 자식 둘에게 묻는다 |
| 4 | 노드8 [0,0] | 겹치지 않는다 ① | INF 를 돌려준다 |
| 5 | 노드9 [1,1] | 통째로 들어간다 ② | 2 를 돌려준다 |
| 6 | 노드5 [2,2] | 통째로 들어간다 ② | 4 를 돌려준다 |
| 7 | 노드3 [3,4] | 걸쳐 있다 ③ | 자식 둘에게 묻는다 |
| 8 | 노드6 [3,3] | 통째로 들어간다 ② | 1 을 돌려준다 |
| 9 | 노드7 [4,4] | 겹치지 않는다 ① | INF 를 돌려준다 |

노드 9 개에 들어갔고 그중 3 개를 읽었습니다. 답은 1 입니다.

<!--/proof-->

걸쳐 있는 노드가 넷이고, 그 넷은 모두 질의의 왼쪽 끝 1 이나 오른쪽 끝 3 이 담당 구간 안쪽을 지나는
노드예요. 노드4 `[0,1]` 에서는 인덱스 0 과 1 사이로 왼쪽 경계가 지나고, 노드3 `[3,4]` 에서는 3 과 4 사이로
오른쪽 경계가 지납니다. 경계가 안 지나는 노드는 겹치지 않거나 통째로 들어가서 거기서 멈춰요. 판정에 붙인
원문자 ①②③ 은 뒤의 코드에서 같은 갈래에 붙는 이름입니다.

#### 4단계 — 조각의 최솟값 모으기

읽은 값은 걸쳐 있는 노드로 돌아가며 하나로 합쳐집니다. 걸쳐 있는 노드는 두 자식이 돌려준 값 가운데
작은 쪽을 자기 부모에게 돌려줘요. 질의 `[1,3]` 이라면 노드4 가 `min(INF, 2) = 2`, 노드2 가
`min(2, 4) = 2`, 노드3 이 `min(1, INF) = 1`, 뿌리가 `min(2, 1) = 1` 을 돌려줍니다. 겹치지 않는 노드가
`INF` 를 돌려주는 까닭이 여기 있어요. 그 가지는 답에 **아무것도 보태지 않아야** 하는데, 최솟값에서
아무것도 안 보태는 값이 「어떤 원소보다도 큰 수」이기 때문입니다.

이 합이 질의 구간의 최솟값과 같다는 것은 조각이 **빠짐없이, 겹침 없이** 덮는다는 데서 나옵니다. 근거는
판정이 칸을 어디로 보내는가예요.

| 판정 | 그 담당 구간의 칸 | 빠지는 칸이 없는 까닭 |
| --- | --- | --- |
| 겹치지 않는다 | 전부 `[l, r]` 밖이다 | 버리는 칸이 질의 밖의 칸뿐이다 |
| 통째로 들어간다 | 전부 `[l, r]` 안이다 | 적어 둔 값이 그 칸들의 최솟값이다 |
| 걸쳐 있다 | 안과 밖이 섞여 있다 | 자식 둘의 구간을 합치면 이 노드의 구간이라, 두 자식에게 모든 칸이 넘어간다 |

질의 구간의 칸은 뿌리의 담당 구간에서 출발해 셋째 갈래를 따라 계속 자식에게 넘어가다가, 결국 둘째
갈래에서 읽힙니다. 첫째 갈래는 질의 밖의 칸만 버리니 질의 안의 칸은 한 번도 버려지지 않아요. 같은
깊이의 노드가 겹치지 않으니 한 칸을 두 조각이 읽는 일도 없습니다. 앞 그림의 세 조각 `[1,1]` · `[2,2]`
· `[3,3]` 이 그 결과예요.

#### 5단계 — 리프를 고치고 그 줄기만 다시 계산하기

갱신 `A[i] = v` 는 `i` 를 품은 노드만 고칩니다. 뿌리에서 `i ≤ mid` 면 왼쪽, 아니면 오른쪽 자식으로 내려가
리프에 `v` 를 쓰고, 돌아오면서 지나온 노드마다 자식 둘의 작은 쪽을 다시 적어요. 2단계의 채우는 규칙을
그 줄기에만 한 번 더 적용하는 셈입니다. `A[3]` 을 1 에서 10 으로 고치면 이렇게 됩니다.

<!--proof:update-path-->

| 노드 | 옛 값 | 다시 계산 | 새 값 |
| --- | ---: | --- | ---: |
| 노드6 [3,3] | 1 | 새 값을 그대로 쓴다 | 10 |
| 노드3 [3,4] | 1 | min(노드6, 노드7) = min(10, 3) | 3 |
| 노드1 [0,4] | 1 | min(노드2, 노드3) = min(2, 3) | 2 |

고친 노드가 셋이고, 나머지 여섯은 손대지 않았습니다. 담당 구간에 인덱스 3 이 없으면 최솟값이 바뀔 수
없어요. 여기서 불안한 경우는 **값이 커지는 갱신**입니다. 값이 작아지는 갱신이라면 조상마다 옛 값과 새
값 가운데 작은 쪽만 적어도 맞아요. 커지는 갱신에서도 그렇게 하면 어떻게 되는지 두 판을 나란히
실행했습니다.

<!--proof:update-grow-->

| 갱신 뒤 질의 [0,4] | 형제까지 다시 읽는 정본 | 옛 값과 새 값만 비교한 판 | 판정 |
| --- | ---: | ---: | --- |
| A[3] 을 1 에서 0 으로 — 작아진다 | 0 | 0 | 같다 |
| A[3] 을 1 에서 10 으로 — 커진다 | 2 | 1 | 다르다 |

옛 값과 새 값만 비교한 판은 조상마다 min(옛 값, 새 값) 을 적습니다.

<!--/proof-->

값이 커지면 옛 최솟값 1 이 더는 배열에 없는데, 옛 값과 비교하면 그 1 이 조상에 그대로 남아요. 올바른
새 최솟값은 **형제 쪽에 있을 수 있어서** 자식 둘을 다시 읽어야 합니다. 노드3 이 형제 노드7 의 3 을 읽어
3 이 되고, 뿌리가 노드2 의 2 를 읽어 2 가 된 것이 그 모습이에요. 줄기의 길이는 뿌리에서 리프까지의
노드 수이니 깊이 수를 넘지 않습니다.

#### 이 방법이 기대는 전제

반씩 가른 구간으로 덮기는 아래 네 전제에 기대고 있어서, 하나라도 빠지면 답이 틀리거나 방법 자체를 쓸
수 없어요.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| `min(min(a, b), c) = min(a, min(b, c))` | 2 · 4단계 조각의 최솟값을 따로 구해 합친다 | 반씩 나눠 채운 값이 구간의 값과 달라진다 |
| 어떤 값 `x` 에도 `min(x, INF) = x` | 4단계 겹치지 않는 가지를 `INF` 로 돌려준다 | 버린 가지가 답을 바꾼다 |
| 질의가 연속 구간을 묻는다 | 3단계 담당 구간과 질의 구간을 두 끝으로 비교한다 | 조각이 구간이 아니라 칸의 집합이 되어 노드와 맞지 않는다 |
| 갱신이 원소 하나를 바꾼다 | 5단계 한 줄기만 고친다 | 구간 전체를 바꾸면 그 구간의 리프를 모두 고쳐야 한다 |

첫째와 둘째 전제를 갖춘 연산은 최솟값 말고도 여럿이고, 그 이름은 파트 1 의 마지막에서 붙입니다. 같은
Sparse Table 이 기대던 「같은 값을 두 번 넣어도 그대로」는 여기에 없어요. 조각이 겹치지 않으니
필요하지 않습니다.

#### 한 층 묶음이 아니라 반씩 가르는 까닭

「아이디어를 떠올리는 과정」에서 한 층 묶음을 크기 둘로만 비교했습니다. 이번에는 묶음 크기를 아홉
가지로 놓고, 같은 1,024 칸 목록에서 반씩 가른 세그먼트 트리와 함께 세었어요.

<!--proof:cost-block-->

| 방법 | 미리 만들기 | 질의 | 갱신 | 합 | 추가 칸 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 한 층 묶음 B=1 | 2,048 | 172,544 | 1,536 | 176,128 | 1,024 |
| 한 층 묶음 B=2 | 1,536 | 86,528 | 2,048 | 90,112 | 512 |
| 한 층 묶음 B=4 | 1,280 | 44,288 | 3,072 | 48,640 | 256 |
| 한 층 묶음 B=8 | 1,152 | 24,704 | 5,120 | 30,976 | 128 |
| 한 층 묶음 B=16 | 1,088 | 17,984 | 9,216 | 28,288 | 64 |
| 한 층 묶음 B=32 | 1,056 | 20,768 | 17,408 | 39,232 | 32 |
| 한 층 묶음 B=64 | 1,040 | 34,448 | 33,792 | 69,280 | 16 |
| 한 층 묶음 B=256 | 1,028 | 106,499 | 132,096 | 239,623 | 4 |
| 한 층 묶음 B=1024 | 1,025 | 172,544 | 525,312 | 698,881 | 1 |
| 세그먼트 트리 | 5,117 | 4,102 | 15,872 | 25,091 | 4,096 |

한 층 묶음은 B=16 에서 합이 28,288 로 가장 적고, 세그먼트 트리는 25,091 입니다.

<!--/proof-->

한 층 묶음의 합은 `B` 를 키울수록 줄다가 `B = 16` 을 지나 다시 늘어요. 질의가 줄고 갱신이 늘기
때문입니다. 1,024 칸에서는 가장 좋은 `B` 와 세그먼트 트리의 차이가 크지 않아요. 차이는 규모가 벌립니다.
「아이디어를 떠올리는 과정」의 과제 규모 표에서 한 층 묶음은 54,637,933 번, 세그먼트 트리는 4,603,389
번이었어요. 한 층 묶음은 질의 하나가 `√N` 규모를 읽고, 세그먼트 트리는 깊이 수 규모를 읽기 때문입니다.
추가 칸은 세그먼트 트리가 4,096 칸으로 가장 많아요. **추가 칸을 더 쓰고 접근 수를 덜 쓰는 맞바꿈**이고,
과제 규모에서도 400,000 칸이라 메모리 예산에 넉넉히 들어갑니다.

#### 다섯 단계를 이은 절차

다섯 단계를 코드의 순서로 다시 적으면 네 걸음이 됩니다. 3 · 4단계는 질의 하나를 답하는 재귀 함수
하나로 묶여요.

1. `tree` 를 `4N` 칸으로 잡는다
2. 뿌리부터 반씩 갈라 내려가고, 돌아오면서 노드마다 담당 구간의 최솟값을 채운다
3. 질의 `[l, r]` 은 뿌리부터 노드마다 겹치지 않으면 `INF`, 통째로 들어가면 적어 둔 값, 걸쳐 있으면 두
   자식의 답 가운데 작은 쪽을 돌려준다
4. 갱신 `(i, v)` 는 리프까지 내려가 `v` 를 쓰고, 돌아오면서 지나온 노드를 다시 계산한다

### 수행으로 알아보는 알고리즘 — 다섯 칸짜리 배열에 연산 다섯을 처리한다

아이디어를 확인했으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 정해 끝까지 가져가되,
코드 조각을 하나 만들 때마다 그 조각만 실행한 결과를 확인하고 다음으로 넘어갑니다.

<!--proof:walk-input-->

```ts
const A = [5, 2, 4, 1, 3];
const ops: SegOp[] = [
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 0, r: 2 },
  { type: "update", i: 3, v: 10 },
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 3, r: 4 },
];
// 이 절이 끝나면 [1, 2, 2, 3] 이 나와야 한다
```

왜 이 다섯 연산일까요? 판정 세 갈래와 갱신의 두 갈래를 **모두 실행하게** 하려는 것입니다. `[0,4]` 는
뿌리에서 통째로 들어가고, `[0,2]` 와 `[3,4]` 는 뿌리에서 걸친 뒤 한쪽 자식은 통째로, 다른 쪽은 겹치지
않아요. 갱신이 가운데 있어서 같은 질의 `[0,4]` 의 답이 앞뒤로 갈리고, 값이 커지는 갱신이라 형제를 다시
읽는 자리도 나옵니다. `N = 5` 라 리프의 깊이가 2 와 3 으로 갈리는 것도 이 입력에서 보여요.

```text
절차 전체를 한 장으로

  tree 를 4N 칸으로 잡고 INF 로 채운다
  build(node, s, e):
      s = e 이면            tree[node] ← A[s]
      아니면                자식 둘을 먼저 채우고 tree[node] ← min(자식 둘)

  연산을 순서대로 받으며:
      update(i, v)   리프까지 내려가 값을 쓴다                      ④
                     올라오면서 지나온 노드를 다시 계산한다          ⑤
      query(l, r)    겹치지 않으면 INF 를 답한다                    ①
                     통째로 들어가면 적어 둔 값을 답한다             ②
                     걸쳐 있으면 자식 둘에게 나눠 묻는다             ③
```

#### 1. 배열 하나에 트리를 담는다

포인터도 객체도 쓰지 않고 배열 한 개로 트리를 담습니다. 칸은 `4N` 개이고, 아직 안 채운 칸은 `INF` 로
둡니다.

```ts
const N = A.length;
const INF = Number.MAX_SAFE_INTEGER;
const tree = new Array<number>(4 * N).fill(INF);
```

여기서 가장 중요한 것은 뿌리를 `0` 이 아니라 `1` 로 두는 약속이에요. 자식을 `2·node` 와 `2·node+1` 로
찾는데, 뿌리가 `0` 이면 그 식이 자기 자신을 가리킵니다.

<!--proof:walk-root-->

| 뿌리 번호 | 자식 번호 2·node · 2·node+1 | 결과 |
| ---: | --- | --- |
| 0 | 0 · 1 | 왼쪽 자식이 자기 자신이다 |
| 1 | 2 · 3 | 번호가 겹치는 자리가 없다 |

뿌리가 `1` 이면 깊이 `d` 의 노드 번호가 `2^d` 이상 `2^(d+1)` 미만으로 갈려서, 깊이가 다른 두 노드가
같은 번호를 받는 일이 없어요.

#### 2. 아래에서 위로 값을 채운다

채우는 순서가 이 조각의 전부입니다. 부모의 값은 자식 둘의 값에서 나오므로 **자식을 먼저** 채워요.

```ts
const merge = (node: number): number =>
  Math.min(tree[2 * node] ?? INF, tree[2 * node + 1] ?? INF);

function build(node: number, s: number, e: number): void {
  if (s === e) {
    tree[node] = A[s] ?? INF;
    return;
  }
  const mid = (s + e) >> 1;
  build(2 * node, s, mid);
  build(2 * node + 1, mid + 1, e);
  tree[node] = merge(node);
}
```

`build(1, 0, 4)` 를 실행하면 걸음이 아홉 개 나옵니다. 걸음마다 노드 하나를 채우고, 점선 테가 아직 안 채운
노드, 굵은 강조 테가 이번에 채운 노드, 굵은 잉크 테가 이번에 읽은 자식이에요. 리프를 채우는 걸음에서는
무대 아래 `A` 의 읽은 칸이 굵어집니다.

나서 T5 에서 노드2 가 정해지고, 오른쪽 반은 T6 · T7 의 리프 둘과 T8 의 노드3 순서예요. 뿌리 노드1 은
마지막 T9 에 채워집니다.
`merge` 는 자식 두 칸만 읽고, 아직 안 채운 칸이 있다면 `INF` 로 읽어 답을 바꾸지 않아요.

#### 3. 세 갈래로 갈라 질의에 답한다

질의 하나는 판정 세 갈래로 끝납니다. 세 갈래가 **서로 겹치지 않고 빠짐없이** 모든 경우를 나눈다는 것이
이 조각의 전부예요.

```ts
function query(node: number, s: number, e: number, l: number, r: number): number {
  if (r < s || e < l) return INF; // ① 겹치지 않는다
  if (l <= s && e <= r) return tree[node] ?? INF; // ② 통째로 들어간다
  const mid = (s + e) >> 1;
  // ③ 걸쳐 있다 — 두 자식에게 나눠 묻고 작은 쪽을 고른다
  return Math.min(
    query(2 * node, s, mid, l, r),
    query(2 * node + 1, mid + 1, e, l, r),
  );
}
```

질의 `[0,2]` 에 이 조각만 실행한 결과입니다. 걸음 번호는 채우는 아홉 걸음 뒤로 이어 붙였어요.

<!--proof:walk-query-02-->

| 걸음 | 노드 | 판정 | 돌려준 값 |
| --- | --- | --- | --- |
| T11 | 노드1 [0,4] | 걸쳐 있다 ③ | 자식 둘에게 묻는다 |
| T12 | 노드2 [0,2] | 통째로 들어간다 ② | 2 |
| T13 | 노드3 [3,4] | 겹치지 않는다 ① | INF |
| T14 | 노드1 [0,4] | 두 답을 합친다 ③ | min(2, INF) = 2 |

노드 셋에 들어가 하나만 읽었습니다. T14 의 `min(2, INF) = 2` 에서 `INF` 가 답을 바꾸지 않는 것을 볼 수
있어요.

#### 짚고 가기 — 통째로 들어가는지 재는 조건을 어느 방향으로 적는가

여기서 헷갈리기 쉬운 부분은 ② 의 부등호 방향입니다. 「질의가 노드를 품는다」와 「노드가 질의에
들어간다」가 같은 말처럼 읽히는데, 코드로는 정반대예요. 바른 조건은 `l <= s && e <= r`, 곧 노드의 담당
구간이 질의 안에 있다는 뜻입니다. 뒤집으면 `s <= l && r <= e` 가 되고, 질의가 노드 안에 있다는 뜻이
돼요. 뒤집은 조건으로 다섯 연산을 실행해 봤습니다.

<!--proof:pause-contain-flip-->

| 질의 | 바른 코드 | 조건을 뒤집은 코드 | 판정 |
| --- | ---: | ---: | --- |
| 질의 [0,4] | 1 | 1 | 같다 |
| 질의 [0,2] | 2 | 1 | 어긋난다 |
| 질의 [0,4] | 2 | 2 | 같다 |
| 질의 [3,4] | 3 | 2 | 어긋난다 |

**질의가 배열 전체일 때는 답이 같습니다.** 테스트에 전체 구간 질의만 있으면 이 코드는 통과해요. 뿌리에서
두 조건을 실제 값으로 판정하면 까닭이 보입니다.

<!--proof:pause-contain-cond-->

| 질의 | 조건 | 뿌리 [0,4] 에서 | 결과 |
| --- | --- | --- | --- |
| [0,4] | l <= s && e <= r | 0 <= 0 && 4 <= 4 | 참 |
| [0,4] | s <= l && r <= e | 0 <= 0 && 4 <= 4 | 참 |
| [0,2] | l <= s && e <= r | 0 <= 0 && 4 <= 2 | 거짓 |
| [0,2] | s <= l && r <= e | 0 <= 0 && 2 <= 4 | 참 |

`[0,4]` 는 뿌리의 담당 구간과 같아서 두 조건이 모두 참이에요. `[0,2]` 에서는 뒤집은 조건이 뿌리에서 참이
되어 뿌리의 값 1 을 답으로 냅니다. 모든 질의는 배열 안에 있으니, 뒤집은 조건은 **뿌리에서 언제나 참**이고
어떤 질의든 `tree[1]` 을 답해요.

#### 4. 리프를 고치고 조상만 다시 계산한다

갱신은 내려가면서 자리를 찾고 올라오면서 값을 고칩니다. 내려가는 길과 올라오는 길이 **같은 한 줄기**라는
것이 이 조각의 전부예요.

```ts
function update(node: number, s: number, e: number, i: number, v: number): void {
  if (s === e) {
    tree[node] = v; // ④ 리프 도달 — 새 값을 그대로 쓴다
    return;
  }
  const mid = (s + e) >> 1;
  if (i <= mid) update(2 * node, s, mid, i, v);
  else update(2 * node + 1, mid + 1, e, i, v);
  tree[node] = merge(node); // ⑤ 상향 재계산
}
```

`update(1, 0, 4, 3, 10)` 에 이 조각만 실행한 결과입니다.

| --- | --- | --- | --- |
| 내려가는 길 | 노드1 [0,4] | mid = 2, i = 3 > 2 | 오른쪽 자식으로 |
| 내려가는 길 | 노드3 [3,4] | mid = 3, i = 3 <= 3 | 왼쪽 자식으로 |
| T15 | 노드6 [3,3] | s = e 라 리프 ④ | tree[6] = 10, 옛 값 1 |

부모를 정하는** 같은 일을 해요. T16 이 형제 노드7 의 3 을 다시 읽은 것이 값이 커지는 갱신을 바르게 만든
자리입니다.

#### 짚고 가기 — 오른쪽 끝을 하나 빼고 물어도 답이 안 틀리는 질의가 있다

여기서 헷갈리기 쉬운 부분은 질의 구간의 오른쪽 끝입니다. 구간을 오른쪽 끝을 뺀 반개구간 `[l, r)` 로
다루는 구현이 흔해서, 그 습관대로 `op.r − 1` 을 넘기면 오른쪽 끝 한 칸이 빠져요. 이 과제의 구간은
양끝을 포함하니 `r` 번째 칸이 답에 들어가야 합니다. 오른쪽 끝을 하나 뺀 코드로 같은 다섯 연산과 한 칸짜리
질의 `[2,2]` 를 실행했습니다.

<!--proof:pause-half-open-->

| 질의 | 바른 코드 | 오른쪽 끝을 뺀 코드 | 판정 |
| --- | ---: | ---: | --- |
| 질의 [0,4] | 1 | 1 | 같다 |
| 질의 [0,2] | 2 | 2 | 같다 |
| 질의 [0,4] | 2 | 2 | 같다 |
| 질의 [3,4] | 3 | 10 | 어긋난다 |
| 질의 [2,2] | 4 | INF | 어긋난다 |

**앞의 질의 셋은 답이 같습니다.** 첫 `[0,4]` 의 최솟값은 인덱스 3 에, `[0,2]` 의 최솟값은 인덱스 1 에,
갱신 뒤 `[0,4]` 의 최솟값은 인덱스 1 에 있어서, 오른쪽 끝을 빼도 그 값이 남아요. 빠진 칸이 그 구간의
최솟값일 때만 답이 틀리니, 무작위로 만든 테스트 몇 개로는 틀린 답이 잘 나오지 않습니다. 마지막 줄은 구간이
`[2,1]` 이 되어 어느 노드에도 안 들어가고 `INF` 가 그대로 답이 된 자리예요. 고치는 길은 둘입니다.

| 고치는 길 | 하는 일 | 이 글 |
| --- | --- | --- |
| 호출부에서 맞춘다 | 반개구간 트리에 `[l, r+1)` 을 넘긴다 | 쓰지 않는다 |
| 판정을 양끝 포함으로 적는다 | ① · ② 두 줄의 조건을 양끝을 포함하는 비교로 쓴다 | 이쪽이다. 과제의 구간과 코드의 구간이 같은 뜻이 된다 |

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `ops` 를 순서대로 받는 루프와 결과 목록을
빈 배열로 시작하는 한 줄뿐이에요. 질의가 하나도 없으면 그 빈 배열이 그대로 답이 됩니다.

```ts
export type SegOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function segmentTreeRangeMin(A: number[], ops: SegOp[]): number[] {
  const N = A.length;
  // 겹치지 않는 가지가 돌려줄 값. 어떤 원소보다도 커야 최솟값 계산을 바꾸지 않는다.
  const INF = Number.MAX_SAFE_INTEGER;
  // 노드 번호가 이 칸 수를 넘지 않는다 — 근거는 「수식 정의와 유도」에 있다.
  const tree = new Array<number>(4 * N).fill(INF);

  /** 자식 둘의 값을 합쳐 부모 값을 만든다. 아직 안 채운 칸은 INF 로 읽는다. */
  const merge = (node: number): number =>
    Math.min(tree[2 * node] ?? INF, tree[2 * node + 1] ?? INF);

  /** 노드 `node` 가 구간 `[s, e]` 를 담당하도록 아래에서 위로 값을 채운다. */
  function build(node: number, s: number, e: number): void {
    if (s === e) {
      tree[node] = A[s] ?? INF;
      return;
    }
    const mid = (s + e) >> 1;
    build(2 * node, s, mid);
    build(2 * node + 1, mid + 1, e);
    tree[node] = merge(node);
  }

  /** `A[i]` 를 `v` 로 바꾸고 그 리프에서 뿌리까지의 노드만 다시 계산한다. */
  function update(
    node: number,
    s: number,
    e: number,
    i: number,
    v: number,
  ): void {
    if (s === e) {
      tree[node] = v; // ④ 리프 도달 — 새 값을 그대로 쓴다
      return;
    }
    const mid = (s + e) >> 1;
    if (i <= mid) update(2 * node, s, mid, i, v);
    else update(2 * node + 1, mid + 1, e, i, v);
    tree[node] = merge(node); // ⑤ 상향 재계산
  }

  /** 노드 `node`(담당 `[s, e]`)에서 질의 `[l, r]` 의 최솟값을 답한다. */
  function query(
    node: number,
    s: number,
    e: number,
    l: number,
    r: number,
  ): number {
    if (r < s || e < l) return INF; // ① 겹치지 않는다
    if (l <= s && e <= r) return tree[node] ?? INF; // ② 통째로 들어간다
    const mid = (s + e) >> 1;
    // ③ 걸쳐 있다 — 두 자식에게 나눠 묻고 작은 쪽을 고른다
    return Math.min(
      query(2 * node, s, mid, l, r),
      query(2 * node + 1, mid + 1, e, l, r),
    );
  }

  build(1, 0, N - 1);

  const result: number[] = [];
  for (const op of ops) {
    if (op.type === "update") update(1, 0, N - 1, op.i, op.v);
    else result.push(query(1, 0, N - 1, op.l, op.r));
  }
  return result;
}
```

```text
segmentTreeRangeMin([1, 2, 3], [])                                  →  []
segmentTreeRangeMin([5], 질의 [0,0] · 갱신 i=0 v=99 · 질의 [0,0])   →  [5, 99]
```

### 알아 두면 좋은 개념 — 모노이드(항등원이 있는 결합 연산)

이 절차가 `min` 에 요구한 성질은 둘뿐입니다. 하나는 **결합 법칙**이에요. 묶는 순서를 바꿔도 결과가
같아야 자식 둘의 최솟값을 노드에 미리 적어 둘 수 있습니다. 다른 하나는 **항등원**이에요. 겹치지 않는
가지가 답을 바꾸지 않으려면 「합쳐도 아무 일이 없는 값」이 있어야 합니다. 두 성질이 이 글에서 쓰인 자리를
값으로 짚으면 이렇습니다.

<!--proof:related-monoid-->

| 성질 | 쓰인 자리 | 값 |
| --- | --- | --- |
| 결합 법칙 | 노드2 = min(노드4, 노드5) 이고 노드4 = min(A[0], A[1]) | min(min(5, 2), 4) = 2 · min(5, min(2, 4)) = 2 |
| 항등원 | T14 노드1 에서 두 답을 합친다 | min(2, INF) = 2 |
| 항등원 | T22 노드1 에서 두 답을 합친다 | min(INF, 3) = 3 |

이 두 성질을 갖춘 연산을 **모노이드**라고 부릅니다. 이름을 붙이고 나면 이 트리가 `min` 전용이 아니라는
것이 곧바로 보여요. 연산과 항등원만 갈아 끼우면 같은 코드가 다른 질의를 답합니다.

| 연산 | 항등원 | 세그먼트 트리 | 접두 표 |
| --- | --- | --- | --- |
| 최솟값 | `+∞` — 코드의 `INF` 가 그 자리다 | 쓸 수 있다. 이 글이 그것이다 | 쓸 수 없다. 덜어 내는 연산이 없다 |
| 최댓값 | `−∞` | 쓸 수 있다 | 쓸 수 없다 |
| 덧셈 | `0` | 쓸 수 있다 | 쓸 수 있다. 뺄셈이 앞부분을 덜어 낸다 |
| 최대공약수 | `0` | 쓸 수 있다 | 쓸 수 없다 |
| 행렬 곱 | 단위행렬 | 쓸 수 있다. 왼쪽 자식을 앞에 두고 합친다 | 쓸 수 없다 |

마지막 줄이 결합 법칙만 요구한다는 말의 뜻입니다. 행렬 곱은 순서를 바꾸면 결과가 달라지는데도 됩니다.
[`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 가 쓰는 접두 표는 그보다
강한 조건(덜어 내는 연산)을 요구하고, 그 대신 질의가 뺄셈 한 번으로 끝나요. 같은 이름을 다시 만나는
자리가 둘 더 있습니다.

| 같은 이름을 다시 만나는 자리 | 하는 일 | 요구하는 조건 |
| --- | --- | --- |
| 거듭제곱 | `x^n` 을 절반씩 접어 계산한다 | 결합 법칙 |
| Sparse Table | 겹치는 두 조각으로 덮는다 | 결합 법칙 + 같은 값을 두 번 넣어도 그대로 |

거듭제곱 쪽은 [`fastPower`](../../number-theory/fastPower/fastPower-guide.md) 가 같은 조건을 다뤄요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 세그먼트 트리가 맞는지, 노드 수와 질의가 읽는 노드 수를
식으로 어떻게 닫는지, 무엇이 매번 참으로 남는지, 비용이 얼마인지를 차례로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 배열이 질의 사이에 바뀐다 | 안 바뀌면 질의가 더 적은 Sparse Table 이 있다 | 리프에서 뿌리까지 다시 계산하는 `update` |
| 질의가 연속 구간을 묻는다 | 띄엄띄엄 고른 인덱스는 담당 구간에 안 맞는다 | 두 끝 `l` · `r` 만 받는 `query` |
| 합치는 연산이 모노이드다 | 결합 법칙과 항등원이 있다 | `merge` 한 줄과 `INF` 하나 |
| 연산이 많다 | 만드는 비용을 연산들이 나눠 진다 | 한 번 부르는 `build` |

마지막 조건에 경계가 있습니다. 세그먼트 트리를 만드는 데 드는 비용이 연산 하나의 비용보다 훨씬 커서,
연산이 한둘뿐이면 구간을 그냥 읽는 편이 적어요.

<!--proof:fit-boundary-->

| 경우 | 차례로 읽기 | 세그먼트 트리(만들기 + 연산의 상한) |
| --- | ---: | ---: |
| 질의 1 개, 구간 10 칸 | 10 | 500,031 |
| 연산 100,000 개 | 최악 10,000,000,000 | 5,699,997 |

N = 100,000 에서 트리를 만드는 데 499,997 번(5N − 3, 실측과 같다)이고, 연산 하나는 최악 52 번(3⌈log₂N⌉ + 1)으로 셌습니다.

<!--/proof-->

경계는 「연산이 몇 개인가」입니다. 질의 하나에 50 만 번을 쓰는 것은 손해이고, 연산이 10 만 개면 100 억
번이 570 만 번이 돼요.

#### 문제에서 이것을 떠올리게 하는 단서

| 보이는 곳 | 이런 말이나 모양 | 뜻 | 세그먼트 트리 |
| --- | --- | --- | --- |
| 지문 | "i 번째 원소를 v 로 바꾼다" "갱신 질의" "실시간으로 반영" | 배열이 바뀐다. 결정적인 신호다 | 쓴다 |
| 지문 | "구간 [l, r] 의 최솟값" "최댓값" "합" "최대공약수" | 모노이드 연산을 묻는다 | 쓴다 |
| 지문 | "연산이 순서대로 주어진다" "각 질의에 대해 답하라" | 연산이 많다 | 쓴다 |
| 제약 | N 과 Q 가 둘 다 10^5 규모 | N × Q 가 시간 안에 못 든다 | 쓴다 |
| 제약 | 갱신과 질의의 비율이 안 적혀 있다 | 둘 다 빨라야 한다 | 쓴다 |
| 지문 | "배열은 변경되지 않는다" "정적" | 갱신이 없다 | Sparse Table 이 질의가 더 적다 |
| 지문 | "구간 [l, r] 의 모든 값에 x 를 더한다" | 한 번에 여러 원소가 바뀐다 | 이 글의 갱신으로는 못 쓴다 |

마지막 두 줄에 해당하면 다른 절차로 갑니다. 배열이 안 바뀌면
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-guide.md) 이고, 구간 합에 원소 갱신이
붙으면 [`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-guide.md) 도 후보예요. 구간 전체를 바꾸는
갱신은 이 트리에 「나중에 자식에게 넘길 갱신」을 노드마다 적어 두는 확장이 필요합니다.

#### 실제로 쓰이는 곳

- **AtCoder Library 의 `atcoder::segtree`** — 이 절차를 담은 공개 라이브러리입니다. 선언이
  `template <class S, auto op, auto e> struct segtree` 라 **합치는 연산 `op` 와 항등원 `e` 를 타입 인자로
  받아요**. 파트 1 의 마지막에서 이름 붙인 조건 둘이 그대로 인터페이스가 된 자리입니다.
  ([`atcoder/segtree.hpp`](https://github.com/atcoder/ac-library/blob/master/atcoder/segtree.hpp),
  조회 2026-09-02)
- **KACTL 의 `SegmentTree.h`** — 머리 주석이 *"Zero-indexed max-tree"* 로 최댓값 트리임을 밝히고,
  합치는 함수 `f` 와 항등원 `unit`(여기서는 `INT_MIN`)을 바꾸면 다른 연산이 된다고 적혀 있습니다. 이
  글의 `INF` 가 그 `unit` 과 같은 자리예요.
  ([`content/data-structures/SegmentTree.h`](https://github.com/kth-competitive-programming/kactl/blob/main/content/data-structures/SegmentTree.h),
  조회 2026-09-02)
- **Rust 의 `segment-tree` 크레이트 2.0.0** — `SegmentPoint` 가 구간 질의와 점 갱신을 맡고, 같은
  크레이트의 `PrefixPoint`(펜윅 트리)는 **교환 법칙을 추가로 요구**한다고 문서가 밝힙니다. 같은 라이브러리
  안에 두 조건이 갈려 있는 자리예요.
  ([`segment_tree`](https://docs.rs/segment-tree/latest/segment_tree/), 조회 2026-09-02)

| 출처 | 합치는 연산 | 항등원 | 이 글에서 |
| --- | --- | --- | --- |
| AtCoder Library | `op` | `e` | `merge` · `INF` |
| KACTL | `f` | `unit` | `merge` · `INF` |
| segment-tree 크레이트 | `Operation` 트레이트 | 트레이트가 정한다 | `merge` · `INF` |

세 라이브러리 모두 `min` 을 박아 두지 않고 바깥에서 받습니다.

#### 경쟁 설계와의 대조

같은 목표, 곧 구간 최솟값 질의에 답하는 다른 절차로 **Sparse Table** 이 있습니다. 칸 수가 `2^k` 인
구간을 모든 시작 자리에 적어 두고, 질의는 그런 구간 둘로 **겹쳐 덮어** 칸 두 개로 답해요. 대신 갱신을
받으려면 원소를 덮는 칸을 층마다 다시 계산해야 합니다.

| 설계 | 구간을 덮는 법 | 질의 하나가 읽는 칸 | 갱신 |
| --- | --- | --- | --- |
| 세그먼트 트리 | 겹치지 않는 노드 여러 개 | 최대 `2⌈log₂N⌉` 개 | 한 줄기만 고친다 |
| Sparse Table | 겹치는 두 조각 | 언제나 2 개 | 표를 다시 만든다 |

두 설계에 같은 입력과 같은 작업 목록을 주고 **칸 접근 수**(읽기 + 쓰기)를 셌습니다. 트리를 `INF` 로 채우는 초기화 쓰기는 뺐어요. 배열은 `N = 1,024` 이고
`A[i] = (37i) mod 101` 이에요. 질의 `t` 번째는 `a = (37t) mod N` 과 `b = (91t) mod N` 을 만들어 작은
쪽을 왼쪽 끝으로 두고, 갱신 `k` 번째는 `A[(53k) mod N]` 을 `((29k) mod 1000) − 500` 으로 덮어써요.
갱신은 질의 사이에 고르게 끼웠고, 이 대조의 Sparse Table 은 갱신마다 표를 통째로 다시 만듭니다. 난수가
없어 시드도 없어요. 전개가 쓰는 다섯 칸짜리 입력으로는 Sparse Table 의 층이 셋뿐이라 두 설계의 계수가
상수에 묻혀서, 규모를 키운 입력을 따로 씁니다.

**갱신이 하나도 없으면 질의 수가 순서를 정합니다.**

<!--proof:alt-counts-->

| 갱신 0 회 | 세그먼트 트리 | Sparse Table | 적은 쪽 |
| --- | --- | --- | --- |
| 질의 3,515 개 | **33,685** | 33,690 | 세그먼트 트리가 5 번 적습니다 |
| 질의 3,516 개 | 33,696 | **33,692** | **여기서 순서가 뒤집힙니다** |
| 질의 4,096 개 | 38,421 | **34,852** | Sparse Table 이 1.1 배 적습니다 |
| 질의 10,000 개 | 86,424 | **46,660** | Sparse Table 이 1.9 배 적습니다 |

**갱신이 하나라도 섞이면 순서가 반대로 갑니다.**

| 질의 4,096 개 | 세그먼트 트리 | Sparse Table | 적은 쪽 |
| --- | --- | --- | --- |
| 갱신 0 회 | 38,421 | **34,852** | Sparse Table 이 앞섭니다 |
| 갱신 1 회 | **38,453** | 61,513 | **여기서 순서가 뒤집힙니다** |
| 갱신 1,024 회 | **71,189** | 27,335,716 | 세그먼트 트리가 384 배 적습니다 |

<!--/proof-->

추가 칸은 세그먼트 트리가 **4,096** 이고 Sparse Table 이 **9,228** 입니다. 트리 배열과 표의 층 길이 합이고, 두 설계가 똑같이 잡는 입력 사본은 뺐어요. 트리는 `4N` 을 넉넉히 잡고도
적은데, Sparse Table 은 층이 `⌊log₂N⌋ + 1` 개라 칸이 층마다 붙어요. 순서가 뒤집히는 자리를 비용 항으로
가르면 이렇습니다.

<!--proof:alt-boundary-->

| 비용(칸 접근 수) | 세그먼트 트리 | Sparse Table | Sparse Table − 세그먼트 트리 |
| --- | ---: | ---: | ---: |
| 만들기 | 5,117 | 26,660 | 21,543 |
| 질의 하나 평균(질의 3,515 개) | 8.1275 | 2.0000 | -6.1275 |
| 질의 하나 평균(질의 4,096 개) | 8.1309 | 2.0000 | -6.1309 |
| 갱신 하나 | 32 | 26,661 | 26,629 |

Sparse Table 은 만들기에서 21,543 번을 더 쓰고 질의 하나에서 평균 6.1309 번(질의 4,096 개) 또는 6.1275 번(질의 3,515 개)을 덜 씁니다. 만들기의 차이를 그 둘로 나누면 3,513.86 과 3,515.82 입니다.

<!--/proof-->

질의 하나의 비용은 질의마다 달라서, 평균을 몇 개까지 잡느냐에 따라 나눈 값이 조금 움직입니다. 뒤집히는
자리 바로 앞인 3,515 개의 평균으로 나누면 3,515.82 가 나와 실측 경계 3,516 과 맞아요. 갱신 하나의 차이는 26,629 번이라 갱신
한 번으로 순서가 뒤집힙니다.

**이 절차가 내주는 것은 질의 하나의 비용입니다.** Sparse Table 은 칸 두 개로 끝내는데 이쪽은
`2⌈log₂N⌉` 개까지 읽어요. 그 대신 얻는 것이 둘입니다. 갱신을 `O(log N)` 에 받는 것과 추가 칸이 절반
이하인 것이에요.

| 조건 | 고를 설계 | 까닭 |
| --- | --- | --- |
| 갱신이 섞여 들어온다 | 세그먼트 트리 | 갱신 한 번으로 순서가 뒤집힌다 |
| 갱신이 없고 질의가 3,516 개 이상 | Sparse Table | 질의에서 아낀 접근이 만들기의 차이보다 많다 |
| 갱신이 없고 질의가 적다 | 세그먼트 트리 | Sparse Table 을 더 만드는 접근이 질의에서 아낀 접근보다 많다 |
| 메모리가 빠듯하다 | 세그먼트 트리 | 추가 칸이 절반 이하다 |

갱신이 섞여 들어오는 과제라면 세그먼트 트리가 알맞습니다. 같은 과제라도 **갱신이 사라지는 순간** 이
결론을 다시 따져야 해요.

### 수식 정의와 유도

노드가 담당하는 구간과 그 노드에 적는 값을 정의합니다. 뿌리 `node = 1` 이 `[0, N−1]` 을 맡고, 담당 구간이
두 칸 이상이면 가운데를 경계로 자식 둘에게 갈립니다.

$$\mathrm{tree}[node] = \min\bigl(A[s],\ A[s+1],\ \ldots,\ A[e]\bigr)$$

| 기호 | 뜻 |
| --- | --- |
| `node` | 노드 번호. 뿌리가 1, 자식이 `2·node` · `2·node+1` |
| `[s, e]` | 노드 `node` 의 담당 구간 |
| `mid` | 담당 구간을 가르는 가운데 인덱스 |

$$mid = \left\lfloor \frac{s+e}{2} \right\rfloor, \qquad [s, e] \longrightarrow [s,\ mid] \cup [mid+1,\ e] \quad (s < e)$$

정의를 전개 입력 `[5 2 4 1 3]` 에 넣어 봅시다.

<!--proof:math-check-->

| 노드 | [s, e] | mid | 자식의 구간 | tree[node] |
| --- | --- | --- | --- | --- |
| node = 1 | [0,4] | ⌊(0+4)/2⌋ = 2 | [0,2] · [3,4] | min(5, 2, 4, 1, 3) = 1 |
| node = 2 | [0,2] | ⌊(0+2)/2⌋ = 1 | [0,1] · [2,2] | min(5, 2, 4) = 2 |
| node = 4 | [0,1] | ⌊(0+1)/2⌋ = 0 | [0,0] · [1,1] | min(5, 2) = 2 |
| node = 8 | [0,0] | s = e | 없음 (리프) | A[0] = 5 |

가운데가 내림이라 왼쪽 조각이 오른쪽보다 한 칸 크거나 같아요. 식의 `mid` 는 코드에서도 `mid` 이고,
나눗셈은 정수 나눗셈 `(s + e) >> 1` 입니다.

```ts
// 정의의 자식 관계를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const children = (node: number, s: number, e: number) => {
  const mid = (s + e) >> 1;
  return [
    { node: 2 * node, s, e: mid },
    { node: 2 * node + 1, s: mid + 1, e },
  ];
};
```

이제 질의 하나가 들어가는 노드 수의 상한을 유도합니다. 깊이 `d` 를 「뿌리에서 몇 번 내려왔는가」로 두면,
같은 깊이의 노드들이 담당하는 구간은 **서로 겹치지 않습니다.** 부모의 구간을 두 조각으로 가른 것이 자식이라,
다른 갈래로 내려간 구간끼리는 만나지 않아요.

<!--proof:math-depth-->

| 깊이 | 노드의 담당 구간 | 맡는 인덱스 |
| --- | --- | --- |
| 깊이 1 | [0,2] · [3,4] | 0 1 2 · 3 4 |
| 깊이 2 | [0,1] · [2,2] · [3,3] · [4,4] | 0 1 · 2 · 3 · 4 |
| 깊이 3 | [0,0] · [1,1] | 0 · 1 |

노드 `[s, e]` 가 「걸쳐 있다」로 판정되는 것은 질의 `[l, r]` 과 겹치면서 통째로 들어가지는 않을 때입니다.
그것을 부등식으로 펴면 둘 중 하나예요.

$$s < l \le e \qquad \text{또는} \qquad s \le r < e$$

| 조건 | 뜻 |
| --- | --- |
| `s < l ≤ e` | 인덱스 `l−1` 과 `l` 사이의 경계가 이 노드 안을 지난다 |
| `s ≤ r < e` | 인덱스 `r` 과 `r+1` 사이의 경계가 이 노드 안을 지난다 |

같은 깊이의 노드는 겹치지 않으니 경계 하나는 깊이마다 노드 하나 안에만 있습니다. 경계가 둘이므로 깊이마다
걸쳐 있는 노드는 **최대 둘**이에요. 자식을 부르는 것은 걸쳐 있는 노드뿐이라, 깊이 `d+1` 에 들어가는 노드는
최대 넷입니다. 최대 깊이를 `D` 로 두고 깊이별로 더하면 방문 노드의 총수 `V` 가 나와요.

$$V \le 1 + 2 + \underbrace{4 + 4 + \cdots + 4}_{D-1\ \text{개}} = 4D - 1, \qquad D = \lceil \log_2 N \rceil$$

값을 읽은 노드의 수 `R` 은 더 작습니다. 걸쳐 있는 노드의 자식 둘이 **둘 다** 통째로 들어가면 부모의 구간도
통째로 들어가서 부모가 걸쳐 있다는 것과 어긋나요. 그래서 걸친 노드 하나에 통째로 들어가는 자식은 최대
하나이고, 깊이 `1` 부터 `D` 까지 깊이마다 최대 둘이라 `R ≤ 2D` 입니다. 두 상한을 모든 `(l, r)` 짝에서
실제로 잰 최댓값과 대조합니다.

<!--proof:visit-bound-->

| N | D | 상한 4D−1 | 실측 최대 진입 | 그 짝 | 상한 2D | 실측 최대 읽기 |
| ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 5 | 3 | 11 | 9 | [1,3] | 6 | 3 |
| 8 | 3 | 11 | 11 | [1,4] | 6 | 4 |
| 16 | 4 | 15 | 15 | [1,8] | 8 | 6 |
| 64 | 6 | 23 | 23 | [1,32] | 12 | 10 |
| 256 | 8 | 31 | 31 | [1,128] | 16 | 14 |
| 1,024 | 10 | 39 | 39 | [1,512] | 20 | 18 |

진입 상한 `4D − 1` 은 `N = 8` 부터 실측 최댓값과 같아서 더 줄일 수 없는 값이에요. 읽기 상한 `2D` 는
`N = 1,024` 에서 20 에 실측 18 이라 2 만큼 헐겁습니다. 최대를 만드는 짝이 배열 전체가 아니라는 것도 함께
보여요. 과제 규모에 넣으면
이렇습니다.

<!--proof:math-scale-->

| 방법 | 질의 하나의 읽기 | 질의 100,000 개 |
| --- | ---: | ---: |
| 구간을 직접 읽기(최악) | 100,000 | 10,000,000,000 |
| 세그먼트 트리(상한 2D) | 34 | 3,400,000 |

N = 100,000 이면 D = 17 이고, 두 합의 비는 약 2,941 배입니다.

<!--/proof-->

같은 정의에서 **트리 배열의 칸 수**도 나옵니다. 뿌리가 `1` 이고 자식이 `2·node` · `2·node+1` 이므로 깊이
`d` 의 노드 번호는 `2^d` 이상 `2^(d+1)` 미만이고, 최대 깊이가 `D` 이므로 번호는 `2^(D+1)` 보다 작아요.

$$node < 2^{D+1} = 2 \cdot 2^{\lceil \log_2 N \rceil} < 2 \cdot 2N = 4N$$

| 부등식 | 까닭 |
| --- | --- |
| `2^⌈log₂N⌉ ≥ N` | `2^⌈log₂N⌉` 은 `N` 이상인 2 의 거듭제곱 가운데 가장 작은 것이다 |
| `2^⌈log₂N⌉ < 2N` | 그보다 한 단계 작은 `2^(⌈log₂N⌉−1)` 은 `N` 보다 작다 |
| `node < 4N` | 위 둘을 합치면 `2^(D+1) < 4N` 이다. `2N` 보다 작다는 보장은 없다 |

`2N` 으로 잡으면 어디서 모자란지 값으로 확인합니다.

<!--proof:node-index-->

| N | D | 실측 최대 깊이 | 실측 최대 번호 | 2^(D+1) | 2N | 4N | 2N 칸 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 5 | 3 | 3 | 9 | 16 | 10 | 20 | 충분 |
| 6 | 3 | 3 | 13 | 16 | 12 | 24 | 모자람 |
| 10 | 4 | 4 | 25 | 32 | 20 | 40 | 모자람 |
| 16 | 4 | 4 | 31 | 32 | 32 | 64 | 충분 |
| 100 | 7 | 7 | 253 | 256 | 200 | 400 | 모자람 |
| 1,000 | 10 | 10 | 2,045 | 2,048 | 2,000 | 4,000 | 모자람 |
| 100,000 | 17 | 17 | 262,141 | 262,144 | 200,000 | 400,000 | 모자람 |

N 이 1 부터 200 까지인 경우 가운데 2N 칸으로 모자란 것이 180 개입니다.

<!--/proof-->

`N = 6` 이 첫 자리예요. 노드 번호가 13 까지 가는데 `2N` 은 12 입니다. 200 까지 가운데 180 개가 그
상태이니 `2N` 이 모자란 것은 예외가 아니라 기본이고, 실측 최대 깊이가 언제나 `D` 와 같아서 `4N` 이면
늘 충분해요.

### 불변식 — 연산이 끝날 때마다 노드의 값은 그 노드가 담당하는 구간의 최솟값이다

파트 1 에서 코드가 동작하는 모습을 스물두 걸음으로 확인했습니다. 하지만 그것은 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. **무엇이 매번 참으로 남는지**를 문장으로 세우고, 그것이 실제로
유지되는지 확인해 봅시다.

> `build` 가 끝난 시점과 `update` 하나가 끝난 시점마다, 모든 노드 `node` 에 대해 `tree[node]` 는 그 노드가
> 담당하는 구간 `[s, e]` 의 최솟값입니다. `query` 는 `tree` 를 읽기만 하므로 이 성질을 바꾸지 않습니다.

<!--fig:invariant-moment-->
![T15 직후 — 리프만 바뀌고 조상 둘이 옛 값](./figs/invariant-moment.svg)

「끝난 시점」을 빠뜨리면 이 문장이 거짓이 됩니다. `update` 가 **진행 중인** 동안은 리프만 바뀌고 조상은 옛
값이라, 그 순간에는 조상이 성질을 만족하지 않아요. 그림의 전개 T15 직후가 바로 그 순간입니다.

전개의 스물두 걸음 가운데 연산이 끝난 시점과 T15 에서, 노드마다 적힌 값을 그 시점 배열로 정의대로 직접
계산한 최솟값과 대조했습니다.

<!--proof:invariant-check-->

| 걸음 | 시점 | 확인한 노드 | 어긋난 노드 | 어긋난 자리 |
| --- | --- | ---: | ---: | --- |
| T9 | 트리를 다 채운 뒤 | 9 | 0 | 없음 |
| T10 | 질의 [0,4] 가 끝난 뒤 | 9 | 0 | 없음 |
| T14 | 질의 [0,2] 가 끝난 뒤 | 9 | 0 | 없음 |
| T15 | 갱신 i=3 v=10 에서 리프만 쓴 순간 | 9 | 2 | 노드1 · 노드3 |
| T17 | 갱신 i=3 v=10 이 끝난 뒤 | 9 | 0 | 없음 |
| T18 | 질의 [0,4] 가 끝난 뒤 | 9 | 0 | 없음 |
| T22 | 질의 [3,4] 가 끝난 뒤 | 9 | 0 | 없음 |

T15 에서만 두 노드가 어긋나고, 그 두 노드는 T16 · T17 이 다시 계산해 T17 에서 0 이 됩니다. 상태를 바꾸는
갈래마다 성질이 유지되는 근거는 이렇습니다.

| 갈래 | 하는 일 | 성질이 유지되는 근거 |
| --- | --- | --- |
| `build` 리프 | `tree[node] = A[s]` | 원소 하나짜리 구간의 최솟값은 그 원소다 |
| `build` 내부 | `tree[node] = merge(node)` | 자식 둘의 구간을 합치면 부모의 구간이고, 두 자식이 이미 참이다 |
| `update` 리프 | `tree[node] = v` | 그 구간의 유일한 원소가 `v` 로 바뀌었다 |
| `update` 내부 | `tree[node] = merge(node)` | 바뀐 자식이 먼저 참이 됐고, 다른 자식은 원래 참이다 |
| `update` 줄기 밖 | 아무것도 안 한다 | 담당 구간에 `i` 가 없으니 최솟값이 바뀔 수 없다 |
| `query` | `tree` 를 읽기만 한다 | 상태를 바꾸는 코드가 없다 |

경계에 있는 입력도 확인하고 갑시다. 정본의 답과, 연산을 차례로 적용한 배열에서 정의대로 직접 계산한 값을
대조했어요.

<!--proof:invariant-edges-->

| 경계 | 배열 | 연산 | 답 | 정의로 직접 계산한 값과 |
| --- | --- | --- | --- | --- |
| 연산 목록이 빔 | [1 2 3] | 없음 | [] | 같다 |
| 갱신만 있음 | [1 2 3] | 갱신 i=0 v=999 | [] | 같다 |
| 원소 하나 | [5] | 질의 [0,0] · 갱신 i=0 v=99 · 질의 [0,0] | [5 99] | 같다 |
| 한 칸짜리 질의 | [5 3 7 1 9] | 질의 [2,2] | [7] | 같다 |
| 음수로 갱신 | [1 2 3] | 갱신 i=1 v=-1000 · 질의 [0,2] | [-1000] | 같다 |
| 전부 같은 값으로 갱신 | [10 20 30] | 갱신 i=0 v=7 · 갱신 i=1 v=7 · 갱신 i=2 v=7 · 질의 [0,2] | [7] | 같다 |
| 값이 커지는 갱신 | [5 3 7 1 9] | 질의 [0,4] · 갱신 i=3 v=100 · 질의 [0,4] | [1 3] | 같다 |

원소가 하나면 뿌리가 곧 리프라 `build` · `update` · `query` 가 모두 `s = e` 갈래만 탑니다. 음수가 섞여도
`INF` 가 어떤 원소보다 크니 `min` 이 그대로 음수를 골라요. 마지막 줄이 가장 미끄러운 자리입니다. 값이
커지는 갱신은 형제를 다시 봐야 맞고, `merge` 가 자식 둘을 함께 읽는 까닭이 그것이에요.

**이제 코드 한 곳을 바꿔 확인해 봅시다.** 성질을 지키던 줄은 `update` 의 상향 재계산 한 줄입니다.
「리프만 고치면 되지 않나」라는 생각으로 그 줄을 지워 봅니다.

```ts
if (i <= mid) update(2 * node, s, mid, i, v);
else update(2 * node + 1, mid + 1, e, i, v);
// tree[node] = merge(node);   ← 이 줄을 지운다
```

<!--proof:mutant-no-pullup-->

| 질의 | 바른 코드 | 상향 재계산을 지운 코드 | 판정 |
| --- | ---: | ---: | --- |
| 질의 [0,4] | 1 | 1 | 같다 |
| 질의 [0,2] | 2 | 2 | 같다 |
| 질의 [0,4] | 2 | 1 | 어긋난다 |
| 질의 [3,4] | 3 | 1 | 어긋난다 |

갱신 앞의 질의 둘은 그대로이고 갱신 뒤의 질의 둘이 옛 값 1 을 답합니다. 리프 노드6 은 10 으로 바뀌었는데
노드3 과 노드1 이 T15 의 그림처럼 1 을 들고 남아서, 배열에서 이미 지워진 1 이 계속 답으로 나와요. 불변식
문장의 「`update` 하나가 끝난 시점마다」를 지키는 것이 바로 그 한 줄이고, 그 줄이 빠지면 T15 의 어긋난
상태가 연산이 끝난 뒤에도 남습니다.

### 비용 계산

#### 비용을 세는 과정

한 번 실행할 때 하는 일은 셋뿐입니다. 트리를 채우는 일, 질의에 답하는 일, 갱신을 반영하는 일이에요.
전개의 걸음으로 보면 T1 부터 T9 까지가 채우기, T10 · T11\~T14 · T18 · T19\~T22 가 질의 넷, T15\~T17 이
갱신 하나였습니다. 그 걸음들의 칸 접근을 세면 이렇습니다.

<!--proof:walk-cost-->

| 갈래 | 걸음 | 칸 접근 |
| --- | --- | ---: |
| 트리를 채운다 | T1\~T9 | 22 |
| 질의 4 개 | T10 · T11\~T14 · T18 · T19\~T22 | 4 |
| 갱신 1 개 | T15\~T17 | 7 |
| 합 |  | 33 |

같은 연산 목록을 차례로 읽기로 처리하면 16 번입니다.

<!--/proof-->

다섯 칸짜리 입력에서는 미리 만드는 접근이 연산에서 아낀 접근보다 많아서 차례로 읽기가 더 적어요. 세는 것은 **배열
접근 전부**입니다. 채울 때 `A` 를 읽는 것, `tree` 를 읽는 것과 쓰는 것이에요. 세 갈래의 개수를 `N` 과
`D = ⌈log₂N⌉` 으로 적고 전개 입력에 넣으면 이렇습니다.

<!--proof:perf-formula-->

| 갈래 | 식 | N = 5, D = 3 을 넣은 값 | 전개에서 잰 값 |
| --- | --- | ---: | --- |
| 트리 채우기 | 리프 N 개 × 2 + 내부 N−1 개 × 3 = 5N − 3 | 22 | 22 |
| 질의 하나 | 읽은 노드 수 ≤ 2D | 6 이하 | 질의 4 개에 1 · 1 · 1 · 1 |
| 갱신 하나 | 리프 쓰기 1 + 조상 D 개 × 3 = 3D + 1 이하 | 10 이하 | 7 |

리프는 `A[s]` 읽기와 `tree` 쓰기로 2 번, 내부 노드는 자식 둘 읽기와 자기 쓰기로 3 번이에요. 갱신의 실측
7 이 상한 10 보다 적은 것은 인덱스 3 의 리프가 깊이 3 이 아니라 깊이 2 에 있기 때문입니다. 셋을 더하면
총식이 됩니다.

$$\text{총 접근 수} = (5N - 3) + \sum_{\text{질의}} R + \sum_{\text{갱신}} (\text{줄기 길이} \times 3 - 2) \le (5N - 3) + Q\,(3\lceil \log_2 N \rceil + 1)$$

`N = Q = 100,000` 을 넣으면 `D = 17` 이라 `499,997 + 100,000 × 52 = 5,699,997` 번이고, 「최적인 문제의
모양」의 경계 표에 적은 값과 같습니다. 추가로 잡는 메모리는 트리 배열 하나, `4N` 칸이에요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 서로 다른 축입니다. 「최악은 `O`, 평균은
`Θ`」처럼 한쪽을 다른 쪽에 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (질의가 전부 배열 전체) | `O(N + Q)` | `Θ(N + Q)` — 질의 하나에 노드 하나 |
| **평균적인 경우** (질의 구간의 분포가 필요하다) | `O(N + Q log N)` | 분포를 정하기 전에는 정의되지 않는다 |
| **최악의 경우** (질의의 양 끝이 노드 안쪽을 지난다) | `O(N + Q log N)` | `Θ(N + Q log N)` — 실제로 도달한다 |

가운데 줄이 정의되지 않는 까닭은 이 과제가 질의 구간이 **어떤 분포로 오는지 말하지 않기** 때문입니다.
분포를 하나 정하면(두 끝을 고르게 뽑는다든지) 평균도 나오지만, 그것은 과제가 준 조건이 아니라 이 글이
놓는 가정이에요. 최선과 최악의 차이는 상수가 아니라 `log N` 배입니다. 같은 배열에서 질의의 모양만 바꿔
보았어요.

<!--proof:perf-best-worst-->

| 질의 | 구간의 칸 수 | 읽은 노드 |
| --- | ---: | ---: |
| [0,1023] | 1,024 | 1 |
| [1,1022] | 1,022 | 18 |

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 트리 채우기 하나뿐이라 더할 항이 없어요. 질의를
미리 모으지도, 좌표를 다시 매기지도 않습니다.

| 자원 | 총식 | 이루는 것 |
| --- | --- | --- |
| 시간 | `Θ(N + Q log N)` (최악) | 채우기 `Θ(N)` + 연산 `Q` 개 × `O(log N)` |
| 추가 메모리 | `Θ(N)` | 트리 배열 `4N` 칸. 입력 배열은 채울 때 한 번만 읽는다 |

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에 대한 가정도
없으니, 어떤 배열과 어떤 연산 목록을 넣어도 위 상한 아래입니다. 다만 질의 하나의 상한 `2D` 는 타이트하지
않아요. 「수식 정의와 유도」의 표에서 `N = 1,024` 일 때 상한 20 에 실측 18 이었습니다.

| 보장의 종류 | 뜻 | 이 절차 |
| --- | --- | --- |
| 기댓값이면 | 같은 입력을 두 번 넣었을 때 값이 다를 수 있다 | 해당하지 않는다 |
| 최악 보장이면 | 어떤 입력이든 상한 아래다 | 이쪽이다 |

#### 최악을 만드는 입력

「긴 구간을 묻는 질의가 느리다」는 이 절차에서는 틀린 말입니다. 배열 전체를 묻는 질의는 뿌리 하나로
끝나요. `N = 1,024` 에서 질의의 모양을 바꿔 가며 세었습니다.

<!--proof:worst-shape-->

| 질의의 모양 | 구간 | 구간의 칸 수 | 방문 노드 | 읽은 노드 |
| --- | --- | ---: | ---: | ---: |
| 배열 전체 | [0,1023] | 1,024 | 1 | 1 |
| 왼쪽 절반 | [0,511] | 512 | 3 | 1 |
| 한 칸 | [500,500] | 1 | 21 | 1 |
| 방문 노드가 최대인 짝 | [1,512] | 512 | 39 | 10 |
| 읽은 노드가 최대인 짝 | [1,1022] | 1,022 | 39 | 18 |

가장 긴 구간이 가장 적게 읽고, 가장 많이 읽는 질의는 배열 전체에서 **양 끝을 한 칸씩만 안으로 당긴**
`[1,1022]` 입니다. 그 한 칸 때문에 뿌리가 걸쳐 있게 되고, 그 뒤로 왼쪽 경계와 오른쪽 경계가 깊이마다 노드
하나씩의 안쪽을 지나며 조각을 둘씩 만들어요. 그러니 최악은 **규모와 질의의 모양이 함께** 만듭니다. `N` 과
`Q` 를 제약의 최댓값으로 두고 질의를 전부 `[1, N−2]` 로 채운 작업 목록을 실행했습니다.

<!--proof:worst-scale-->

| 항목 | 칸 접근 또는 방문 노드 |
| --- | ---: |
| 질의 하나가 방문 노드 | 65 |
| 질의 하나가 읽은 노드 | 31 |
| 미리 만들기 | 499,997 |
| 질의 50,000 개 | 1,550,000 |
| 갱신 50,000 개 | 2,553,392 |
| 합 | 4,603,389 |

N = Q = 100,000 에 질의를 전부 [1, N−2] 로 둔 작업 목록입니다. 합 4,603,389 번은 초당 1 억 번 기준으로 0.05 초 입니다.

<!--/proof-->

질의 하나가 읽은 31 개는 상한 `2D = 34` 아래이고, 방문 노드 65 개도 상한 `4D − 1 = 67` 아래입니다. 재귀
호출도 방문 노드 수만큼이라 같은 규모예요. 최악을 넣어도 예산 1 초에 여유가 큽니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하겠습니다. 배열을 반씩 갈라 생긴 구간마다 노드를 두고 담당 구간의
최솟값을 적어 두었고, 질의는 세 갈래 판정으로 겹치지 않는 노드 몇 개만 읽으며, 갱신은 리프에서 뿌리까지
한 줄기만 다시 계산합니다.

| 순서 | 하는 일 | 규모 |
| ---: | --- | --- |
| 1 | `tree` 를 `4N` 칸으로 잡고 아래에서 위로 채운다 | 접근 `5N − 3` 번 |
| 2 | 질의는 세 갈래로 판정한다 | 읽는 노드 `2⌈log₂N⌉` 개 이하 |
| 3 | 갱신은 한 줄기만 다시 계산한다 | 고치는 노드 `⌈log₂N⌉ + 1` 개 이하 |

먼저 답이 붙는 문제 하나입니다. 전개의 T10 은 질의 `[0,4]` 를 노드 **하나**에 들어가서 답했는데, T19 부터
T22 까지는 질의 `[3,4]` 를 노드 **셋**에 들어가서 답했어요. 구간이 더 짧은 쪽이 더 많이 만진 까닭이
무엇일까요?

<!--proof:check-short-->

| 걸음 | 질의 | 구간의 칸 수 | 방문 노드 |
| --- | --- | ---: | ---: |
| T10 | [0,4] | 5 | 1 |
| T19\~T22 | [3,4] | 2 | 3 |

<!--check:whyShortCostsMore-->
비용을 정하는 것이 구간의 칸 수가 아니라 **질의 구간이 어느 노드의 담당 구간과 같은가**이기 때문입니다.
`[0,4]` 는 뿌리의 담당 구간과 같아서 판정 ② 가 뿌리에서 곧바로 참이 되고 거기서 끝나요. `[3,4]` 는 뿌리와
다르므로 판정 ③ 으로 갈라지고, 왼쪽 자식에서 ① 을, 오른쪽 자식에서 ② 를 만나 노드 셋에 들어갑니다.

<!--proof:check-match-->

| 질의 | 담당 구간이 같은 노드 | 그 노드의 깊이 | 방문 노드 |
| --- | --- | ---: | ---: |
| [0,4] | 노드1 | 0 | 1 |
| [0,2] | 노드2 | 1 | 3 |
| [3,4] | 노드3 | 1 | 3 |
| [1,3] | 없음 | — | 9 |

담당 구간이 같은 노드가 깊을수록 내려오는 길이 길어지고, 같은 노드가 아예 없으면 조각으로 갈려 더 많이
들어갑니다. 「최악을 만드는 입력」의 `[1,1022]` 가 노드 열여덟 개를 읽는 것도 같은 까닭이에요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### 구간 최솟값 질의 (동적 갱신)

풀 파일: [`segmentTreeRangeMin.ts`](./segmentTreeRangeMin.ts) · 테스트: [`segmentTreeRangeMin.test.ts`](./segmentTreeRangeMin.test.ts) · 실행: `bun test src/algorithms/array/segmentTreeRangeMin/segmentTreeRangeMin.test.ts`

#### 한 줄 요약

> 정수 배열과 갱신·질의 연산 목록을 받아, **각 질의(구간 최솟값)의 결과**를 순서대로 담은 배열을 반환한다.

#### 스토리

물류 창고 모니터링 시스템을 담당하는 진수는 창고 구역별 재고 최솟값을 실시간으로 추적한다.

시스템에는 두 종류의 명령이 들어온다. 하나는 특정 구역의 재고를 새 값으로 교체하는 갱신이고, 다른 하나는 구간 $[l, r]$에 속한 구역들의 재고 중 가장 적은 양을 묻는 질의다.

명령이 섞여 들어오므로, 갱신 결과가 이후 질의에 즉시 반영되어야 한다. 진수는 모든 질의의 결과를 순서대로 모아 반환해야 한다.

#### 함수 인터페이스

```ts
export type SegOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function segmentTreeRangeMin(A: number[], ops: SegOp[]): number[];
```

- `A` — 초기 정수 배열.
- `ops` — 순서대로 처리할 연산 목록. `update`는 점 갱신, `query`는 구간 최솟값 요청이다.
- 반환 — `query` 연산의 결과만 등장 순서대로 담은 배열.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `A`의 길이)
- $0 \leq Q \leq 100{,}000$ (여기서 $Q$는 `ops`의 길이)
- $-10^9 \leq A[i],\, v \leq 10^9$ (정수)
- `update` 연산: $0 \leq i < N$
- `query` 연산: $0 \leq l \leq r < N$
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

연산은 두 종류다.

- **update** $(i, v)$: $A[i] \leftarrow v$ (덮어쓰기, 누적이 아님).
- **query** $(l, r)$: $\min(A[l], A[l+1], \ldots, A[r])$를 계산한다.

연산은 입력 순서대로 처리된다. `update`는 이후 모든 연산에 즉시 반영된다. `query` 결과만 모아 반환하며, `update`는 결과 배열에 포함되지 않는다. `query`가 하나도 없으면 빈 배열을 반환한다.

#### 예시

```ts
segmentTreeRangeMin(
  [5, 2, 4, 1, 3],
  [
    { type: "query",  l: 0, r: 4 },   // 1  — 초기 전체 최솟값
    { type: "query",  l: 0, r: 2 },   // 2  — A[0..2] 중 최솟값
    { type: "update", i: 3, v: 10 },  // A는 이제 [5,2,4,10,3]
    { type: "query",  l: 0, r: 4 },   // 2  — 갱신 후 전체 최솟값
    { type: "query",  l: 3, r: 4 },   // 3  — A[3..4] 중 최솟값
  ],
); // [1, 2, 2, 3]

segmentTreeRangeMin([5], [
  { type: "query",  l: 0, r: 0 },
  { type: "update", i: 0, v: 99 },
  { type: "query",  l: 0, r: 0 },
]); // [5, 99]  — 단일 원소, 갱신 전후

segmentTreeRangeMin([1, 2, 3], []);
// []  — 연산 없음

segmentTreeRangeMin(
  [1, 2, 3],
  [{ type: "update", i: 1, v: -1000 }, { type: "query", l: 0, r: 2 }],
); // [-1000]  — 음수 갱신 후 최솟값
```
