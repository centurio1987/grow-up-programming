# segmentTreeRangeMin — 어떤 구간이든 미리 저장해 둔 노드 열몇 개로 갈리는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 질의마다 구간을 직접 읽는
방법에서 구간을 반씩 갈라 저장하는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열의 원소가 중간에 바뀌는데도 구간 최솟값을 빠르게 답해야 합니다. 그러려면 미리 계산해 둔
값이 갱신 하나에 통째로 거짓이 되면 안 되고, 그 조건이 **저장하는 값을 배열 전체가 아니라
작은 구간마다 붙여 두라**고 말합니다.

배열 `[0, N-1]` 을 반으로 가르고, 그 반쪽을 또 반으로 가르는 일을 한 칸이 남을 때까지
되풀이합니다. 그렇게 생긴 구간마다 자리를 하나씩 두고 그 자리를 **노드**라고 부를게요.
노드는 자기가 담당하는 구간의 최솟값을 저장합니다. 다섯 칸짜리 배열이면 노드가 아홉 개예요.

```text
A 의 값    5  2  4  1  3          인덱스 0 1 2 3 4

노드1 [0,4] = 1                   담당 구간 전체의 최솟값
├─ 노드2 [0,2] = 2
│  ├─ 노드4 [0,1] = 2
│  │  ├─ 노드8 [0,0] = 5          원소 하나짜리 구간이라 A[0] 을 그대로 든다
│  │  └─ 노드9 [1,1] = 2
│  └─ 노드5 [2,2] = 4
└─ 노드3 [3,4] = 1
   ├─ 노드6 [3,3] = 1
   └─ 노드7 [4,4] = 3
```

원소 하나짜리 구간을 담당하는 노드를 **리프**라고 부릅니다. 리프는 원소를 그대로 들고 있고,
그 위의 노드는 자식 둘의 값 중 작은 쪽을 들고 있어요.

질의 `[l, r]` 이 오면 뿌리에서 시작해 노드마다 셋 중 하나로 판정합니다.

```text
노드의 담당 구간과 질의 구간의 관계   그때 하는 일

  한 칸도 안 겹친다                  이 가지를 통째로 버린다
  질의 구간에 통째로 들어간다        저장해 둔 값을 그대로 답한다
  걸쳐 있다                          자식 둘에게 나눠 묻고 작은 쪽을 고른다
```

세 번째 갈래만 아래로 내려가므로, 어떤 질의든 노드 몇 개만 만지고 끝납니다. 갱신도 같습니다 —
`A[i]` 가 바뀌면 값이 달라지는 노드는 **그 원소를 담당 구간에 품은 노드**뿐이고, 그것은 리프
하나에서 뿌리까지 이어진 한 줄기예요.

```text
A[3] 을 1 에서 10 으로 바꾸면

  값이 달라질 수 있는 노드   노드6 [3,3] → 노드3 [3,4] → 노드1 [0,4]     세 개
  그대로인 노드              노드2 노드4 노드5 노드7 노드8 노드9         여섯 개
                             └ 담당 구간에 인덱스 3 이 없으면 값이 안 바뀐다
```

가르는 일을 한 칸이 남을 때까지 되풀이했으니 줄기의 길이는 배열 길이의 로그입니다. 그래서
미리 만드는 데 `O(N)`, 질의 하나와 갱신 하나가 각각 `O(log N)` 이에요. `N = 100,000` 이면
그 줄기가 노드 열여덟 개를 넘지 않습니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 최솟값**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값 중 가장 작은 수이고, 건너뛰는 칸
  없이 그 구간 전부를 봅니다.
- **이진 트리**와 **깊이**. 노드마다 자식이 최대 둘이고, 뿌리에서 몇 번 내려왔는지가 깊이예요.
- **재귀 함수와 종료 조건**. 이 글의 절차는 자기 자신을 두 번 부르고, 구간이 한 칸이 되면
  멈춥니다.
- **미리 계산해 두고 질의에 답하는 방식**이 무엇인지. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 를 먼저 봅니다.

「구간의 값을 묻는다」와 「구간이 안 바뀐다」는 다른 조건입니다. 배열이 안 바뀌는 문제는
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-problem.md) 이 다루고, 이
글은 **갱신이 섞여 들어오는 쪽**만 합니다.

```text
[5 2 4 1 3] 에서
  구간 [0,2] 의 최솟값을 답하라        2        ← 이 글도 하고 저 글도 한다
  A[3] 을 10 으로 바꿔라               —        ← 이 글만 한다. 저 글은 표를 다시 만들어야 한다
```

### 아이디어 상세 — 구간을 반씩 갈라 저장하는 방법을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
export type SegOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function segmentTreeRangeMin(A: number[], ops: SegOp[]): number[];
```

- 입력: 정수 배열 `A` 와 연산 목록 `ops`. `update` 는 `A[i]` 를 `v` 로 덮어쓰고(누적이
  아닙니다), `query` 는 **양끝을 포함하는** 구간 `[l, r]` 의 최솟값을 묻습니다.
- 출력: `query` 의 답만 **입력 순서 그대로** 담은 배열. 질의가 없으면 빈 배열.
- 제약: `1 ≤ N ≤ 100,000`, `0 ≤ Q ≤ 100,000`, `−10^9 ≤ A[i], v ≤ 10^9`, `0 ≤ i < N`,
  `0 ≤ l ≤ r < N`. 시간 1초, 메모리 256 MB.

이 글이 쓰는 기호는 아홉이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `N` | 배열 `A` 의 길이 | `N ≤ 100,000` |
| `Q` | 연산 목록 `ops` 의 길이 | `Q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값 | `−10^9` 이상 `10^9` 이하 |
| `i` · `v` | `update` 가 바꿀 자리와 새 값 | `0 ≤ i < N` |
| `l` · `r` | `query` 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r < N` |
| `node` | 트리 배열에서 노드 하나를 가리키는 번호. 뿌리가 `1` 입니다 | `1` 이상 |
| `s` · `e` | 노드 `node` 가 담당하는 구간의 왼쪽 끝 · 오른쪽 끝 | `0 ≤ s ≤ e < N` |
| `tree[node]` | 노드 `node` 가 담당하는 구간의 최솟값 | 칸이 `4N` 개 |
| `INF` | 겹치지 않는 가지가 돌려주는 값 | `Number.MAX_SAFE_INTEGER` |

가장 먼저 떠오르는 방법으로 시작합시다. 질의가 오면 그 구간을 왼쪽부터 오른쪽까지 직접 읽어
가장 작은 값을 찾고, 갱신은 배열 칸 하나를 고치는 것이에요.

```ts
for (const op of ops) {
  if (op.type === "update") {
    A[op.i] = op.v;                                    // 칸 하나를 쓴다
  } else {
    let m = INF;
    for (let k = op.l; k <= op.r; k++) m = Math.min(m, A[k] as number);
    result.push(m);                                    // 구간을 직접 읽는다
  }
}
```

갱신은 한 번에 끝나는데 질의가 구간의 칸 수만큼 읽습니다. 모든 질의가 배열 전체를 묻는 목록을
넣어 제약 규모에서 재 봅시다.

<!--proof:naive-scale-->

```text
  N = Q    읽은 칸(실측)             Q·N  1억 번/초 기준
  1,000        1,000,000       1,000,000         0.01 초
 10,000      100,000,000     100,000,000            1 초
100,000  (실행하지 않음)  10,000,000,000          100 초

└ 질의가 전부 배열 전체를 묻는 목록이다. 읽은 칸이 정확히 Q·N 이다
```

100억 번입니다. 단순 연산을 초당 1억 번으로 잡아도 100초가 걸려요. 제약이 10만인데 이
방법으로는 1초 안에 못 끝냅니다.

```text
누적합이 구간 합에서 하던 일
  P[i] 에 앞 i 개의 합을 담아 두면       구간의 합 = P[r+1] − P[l]
같은 모양을 최솟값에 옮기면
  M[i] 에 앞 i+1 개의 최솟값을 담으면    구간의 최솟값 = ?
                                         └ 이 물음표가 이 절의 갈림점이다
```

위 그림의 `M` 이 접두 최솟값 표입니다. 칸 `i` 에 `A[0..i]` 의 최솟값을 담아 두는 것이고,
질의 `[l,r]` 의 답으로 `M[r]` 을 내미는 것이 이 표가 할 수 있는 전부예요. 다섯 질의에 실제로
적용해 봅시다.

<!--proof:prefix-min-fails-->

```text
A 의 값        [5 2 4 1 3]
접두 최솟값 표 [5 2 2 1 1]   칸 i 에 A[0..i] 의 최솟값을 담았다

질의   정본  접두 최솟값 표
[0,4]     1               1  답이 같다
[0,2]     2               2  답이 같다
[1,3]     1               1  답이 같다
[2,2]     4               2  답이 다르다
[4,4]     3               1  답이 다르다

└ 왼쪽 끝이 0 인 질의는 정의상 맞고, 나머지는 맞기도 하고 틀리기도 한다
```

왼쪽 끝이 `0` 인 질의 둘은 정의상 맞고 나머지 셋은 우연에 달렸습니다 — `[1,3]` 은 맞고
`[2,2]`·`[4,4]` 는 틀려요. 누적합은 `P[r+1] − P[l]` 로 앞부분을 덜어 냈는데, 최솟값에는
**덜어 내는 연산이 없기** 때문입니다.

```text
합       앞 r+1 개의 합 − 앞 l 개의 합 = 구간의 합        뺄셈이 앞부분을 지운다
최솟값   앞 r+1 개의 최솟값 ? 앞 l 개의 최솟값 = ?         지우는 연산이 없다
         └ 그래서 왼쪽 끝을 0 으로 고정한 표 하나로는 안 된다
```

왼쪽 끝을 고정할 수 없다면, 저장하는 구간을 **여러 개** 두는 수밖에 없습니다. 가장 단순한
형태는 배열을 `B` 칸씩 끊어 묶음마다 최솟값 하나를 저장하는 것이에요. 질의는 온전히 들어가는
묶음은 저장값을 읽고 양 끝의 남는 칸만 직접 읽습니다.

```text
B = 2 로 [5 2 4 1 3] 을 끊으면

  묶음        [0,1]  [2,3]  [4,4]
  저장값          2      1      3
  질의 [1,3]  칸 1 은 묶음 [0,1] 의 절반이라 A[1] = 2 를 직접 읽고,
              묶음 [2,3] 은 통째로 들어가 저장값 1 을 읽는다   →  min(2, 1) = 1
```

이 방법은 질의를 줄이는 대신 갱신을 늘립니다 — `A[i]` 가 바뀌면 그 묶음의 최솟값을 다시
만들어야 하고, 최솟값은 값이 커지는 갱신에서 묶음 전체를 다시 읽어야 알 수 있어요. 두 방식을
같은 작업 목록에 적용해 실제 계수를 봅시다. 전개가 쓰는 다섯 칸짜리 입력은 묶음 크기를 갈라
보기에 너무 작아서, 같은 규칙으로 만든 1,024 칸 입력에 질의 512 개와 갱신 512 개를 섞은
목록을 씁니다.

<!--proof:cost-two-ways-->

```text
방식             미리 만들기     질의    갱신       합  저장 칸
묶음 없음                  0  172,544     512  173,056        0
한 층 묶음 B=32        1,056   20,768  17,408   39,232       32

└ 답은 둘 다 같다. 질의가 크게 줄고 갱신이 크게 늘었다
```

질의가 172,544 에서 20,768 로 줄고 갱신이 512 에서 17,408 로 늘었습니다. 여기서 관찰할 것은
**두 비용이 반대 방향으로 움직인다**는 것 하나예요 — 묶음을 키우면 질의가 유리해지고 갱신이
불리해집니다.

```text
묶음 크기 B 를 키우면
  질의   온전히 들어가는 묶음이 늘어 읽는 횟수가 준다
  갱신   다시 만들 묶음이 커져 읽는 횟수가 는다
         └ 둘을 동시에 줄이는 B 는 없다. 한 층으로는 여기가 끝이다
```

그 관찰을 개념으로 세워 봅시다. 한 층으로 안 되는 이유는 **묶음의 크기가 하나로 고정**돼
있기 때문이에요. 질의마다 알맞은 크기가 다른데 표는 한 가지 크기만 갖고 있습니다. 그러면
크기를 여럿 두면 됩니다 — 전체 구간을 반으로, 그 반쪽을 다시 반으로 가르며 **크기가 다른
구간을 층층이** 저장하는 것이에요.

```text
[0,4] 를 반씩 가르면

  층 0    [0,4]                      한 개
  층 1    [0,2]  [3,4]               두 개
  층 2    [0,1]  [2,2]  [3,3]  [4,4] 네 개
  층 3    [0,0]  [1,1]               두 개
          └ 층마다 크기가 다르고, 층 수는 N 의 로그다
```

이 구간들에 번호를 붙여 배열 하나에 담습니다. 뿌리를 `1` 로 두고 노드 `node` 의 자식을
`2·node` 와 `2·node + 1` 로 두면 번호만으로 부모와 자식을 오갈 수 있어요. 담당 구간은
`mid = ⌊(s+e)/2⌋` 를 경계로 `[s, mid]` 와 `[mid+1, e]` 로 갈립니다.

```text
번호와 담당 구간
  node = 1        [0, N-1]        뿌리가 배열 전체를 담당한다
  2·node          [s, mid]        왼쪽 자식
  2·node + 1      [mid+1, e]      오른쪽 자식
  s = e 이면      더 갈리지 않는다  리프다
```

이 정의를 실제 입력의 아홉 노드에 걸음마다 적용해 봅시다.

<!--proof:tree-build-->

```text
A 의 값   [5 2 4 1 3]
인덱스     0 1 2 3 4

노드   담당 구간  깊이  값  어디서 왔는가
노드1  [0,4]         0   1  min(노드2, 노드3)
노드2  [0,2]         1   2  min(노드4, 노드5)
노드3  [3,4]         1   1  min(노드6, 노드7)
노드4  [0,1]         2   2  min(노드8, 노드9)
노드5  [2,2]         2   4  A[2]
노드6  [3,3]         2   1  A[3]
노드7  [4,4]         2   3  A[4]
노드8  [0,0]         3   5  A[0]
노드9  [1,1]         3   2  A[1]

└ 리프는 원소 하나를 그대로 들고, 나머지는 자식 둘의 작은 쪽을 들고 있다
```

각 상태가 움직이는 범위가 여기서 정해집니다. 갱신 하나가 고치는 노드는 리프에서 뿌리까지
**깊이 + 1 개**이고, 질의 하나가 읽는 노드는 층마다 최대 두 개예요. 왜 층마다 두 개인지는
「수식 정의와 유도」가 값으로 냅니다.

```text
움직이는 범위
  갱신 하나가 고치는 노드   리프에서 뿌리까지 한 줄기      깊이 + 1 개
  질의 하나가 읽는 노드     층마다 최대 두 개              2 × 층 수 이하
                            └ 둘 다 배열 길이가 아니라 층 수를 따라간다
```

이 정의가 쓸모 있으려면 **모든 질의를 같은 절차 하나로** 답해야 합니다. 쉬운 경우와 불안한
경우를 나눠서 값으로 확인해 봅시다. 쉬운 경우는 질의 구간이 노드 하나와 정확히 맞을 때예요.

<!--proof:range-split-->

```text
질의   들어간 노드  읽은 노드  읽은 자리          답
[0,4]            1          1  노드1               1
[0,2]            3          1  노드2               2
[1,3]            9          3  노드9 노드5 노드6   1

└ 구간이 노드 하나와 맞으면 읽기 한 번이고, 안 맞으면 조각으로 갈린다
```

불안한 경우가 세 번째 줄입니다. 질의 `[1,3]` 과 담당 구간이 같은 노드는 없어요 — 그래서 노드
아홉 개 중 아홉 개에 전부 들어가 보고 그중 셋을 읽습니다. **읽은 세 노드의 담당 구간을 이어
붙이면 질의 구간이 정확히 한 번씩 덮입니다.**

```text
질의 [1,3] 이 갈린 조각

  노드9 [1,1]  노드5 [2,2]  노드6 [3,3]
    └ 이어 붙이면 [1,3] 이고, 겹치는 칸도 빠진 칸도 없다
      min(2, 4, 1) = 1 이 답이다
```

빠뜨리는 칸이 없는 이유는 종료 조건으로 말할 수 있습니다. 걸쳐 있는 노드는 **자식 둘 모두에게**
묻고, 자식 둘의 담당 구간을 합치면 부모의 담당 구간이에요. 그러니 버려지는 칸은 「한 칸도 안
겹친다」로 판정된 칸뿐이고, 그 칸은 질의 구간 밖입니다.

```text
판정 셋과 그 칸의 운명
  겹치지 않는다      버린다      그 구간은 [l,r] 밖이다
  통째로 들어간다    읽는다      그 구간은 [l,r] 안이고 저장값이 곧 답이다
  걸쳐 있다          나눈다      자식 둘의 구간을 합치면 이 노드의 구간이라 빠지는 칸이 없다
```

이제 층을 쌓는 것이 정말 가장 적은지 값으로 확인합니다. 한 층짜리 묶음의 `B` 를 아홉 가지로
두고 같은 작업 목록에서 세었어요.

```text
묶음 크기       미리 만들기     질의     갱신       합  저장 칸
B=1                   2,048  172,544    1,536  176,128    1,024
B=2                   1,536   86,528    2,048   90,112      512
```

한 층짜리 묶음은 `B = 16` 에서 28,288 로 가장 적고, 층을 끝까지 쌓으면 25,091 입니다. 저장
칸은 트리가 4,096 으로 가장 많아요 — **저장을 더 쓰고 연산을 덜 쓰는 맞바꿈**입니다.

```text
얻은 절차 한 벌
  1. tree 를 4N 칸으로 잡고, 뿌리부터 반씩 갈라 노드마다 담당 구간의 최솟값을 채운다
  2. update(i, v) 는 리프까지 내려가 값을 쓰고, 올라오면서 지나온 노드를 다시 계산한다
  3. query(l, r) 은 겹치지 않으면 버리고, 통째로 들어가면 저장값을 읽고, 걸쳐 있으면 나눈다
       └ 10만 칸 · 10만 질의에서 100억 번이던 읽기가 570만 번이 된다
```

### 수행으로 알아보는 알고리즘 — 다섯 칸짜리 배열에 연산 다섯을 처리한다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const A = [5, 2, 4, 1, 3];
const ops: SegOp[] = [
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 0, r: 2 },
  { type: "update", i: 3, v: 10 },
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 3, r: 4 },
];
// 이 절이 끝나면 [1, 2, 2, 3] 이 나와야 한다
```

왜 하필 이 다섯 연산일까요? 문제 문서의 예시를 그대로 가져온 것이고, 이 다섯이 **판정 세
갈래를 전부 실행**하기 때문이에요. 갱신이 가운데 있어서 같은 질의 `[0,4]` 의 답이 앞뒤로
갈리고, `N = 5` 라 좌우 자식의 크기가 3 과 2 로 다릅니다.

```text
절차 전체를 한 장으로

  tree 를 4N 칸으로 잡고 INF 로 채운다
  build(node, s, e):
      s = e 이면            tree[node] ← A[s]
      아니면                자식 둘을 먼저 채우고 tree[node] ← min(자식 둘)

  연산을 순서대로 받으며:
      update(i, v)   리프까지 내려가 값을 쓴다                      ④
                     올라오면서 지나온 노드를 다시 계산한다          ⑤
      query(l, r)    겹치지 않으면 INF 를 답한다                    ①
                     통째로 들어가면 저장값을 답한다                 ②
                     걸쳐 있으면 자식 둘에게 나눠 묻는다             ③
```

#### 1. 배열 하나에 트리를 담는다

포인터도 객체도 쓰지 않고 배열 한 개로 트리를 담습니다. 뿌리를 `1` 로 두는 것이 이 조각의
전부인데, 그 한 줄이 부모·자식 계산을 곱셈 하나로 만들어요.

```ts
const N = A.length;
const INF = Number.MAX_SAFE_INTEGER;
const tree = new Array<number>(4 * N).fill(INF);
```

뿌리를 `0` 으로 두면 자식이 `2·0 = 0` 과 `2·0 + 1 = 1` 이 되어 자기 자신을 가리킵니다. `1` 로
두면 그런 자리가 없어요.

```text
뿌리 번호   자식 번호        결과
        0   0 과 1           왼쪽 자식이 자기 자신이다
        1   2 와 3           번호가 겹치는 자리가 없다
            └ 깊이 d 의 노드 번호가 2^d 이상 2^(d+1) 미만으로 정확히 갈린다
```

칸 수를 `4N` 으로 잡은 것은 `N` 이 2 의 거듭제곱이 아닐 때 노드 번호가 `2N` 을 넘기 때문이고,
그 근거는 「수식 정의와 유도」에 있습니다. 지금은 넉넉히 잡아 두고 갑시다.

#### 2. 아래에서 위로 값을 채운다

채우는 순서가 이 조각의 전부입니다. 부모의 값은 자식 둘의 값에서 나오므로 **자식을 먼저**
채워야 해요.

```ts
const merge = (node: number): number =>
  Math.min(tree[2 * node] ?? INF, tree[2 * node + 1] ?? INF);

function build(node: number, s: number, e: number): void {
  if (s === e) {
    tree[node] = A[s] ?? INF;
    return;
  }
  const mid = (s + e) >> 1;
  build(2 * node, s, mid);
  build(2 * node + 1, mid + 1, e);
  tree[node] = merge(node);
}
```

이 조각만 실행하면 노드 아홉 개가 이렇게 채워집니다. 위에서 이미 값으로 본 표와 같은 것이고,
여기서는 채워지는 **차례**가 다릅니다 — 번호 순도 깊이 순도 아니라 **재귀가 돌아오는 순서**
예요. 노드2 가 노드6·노드7 보다 먼저 정해지는 것이 그 증거입니다.

```text
채워지는 차례 (재귀가 돌아오는 순서)

  노드8 [0,0] ← 5      노드9 [1,1] ← 2      노드4 [0,1] ← min(5, 2) = 2
  노드5 [2,2] ← 4      노드2 [0,2] ← min(2, 4) = 2
  노드6 [3,3] ← 1      노드7 [4,4] ← 3      노드3 [3,4] ← min(1, 3) = 1
  노드1 [0,4] ← min(2, 1) = 1
                        └ 노드 아홉 개, min 이 노드마다 정확히 한 번
```

#### 3. 세 갈래로 갈라 질의에 답한다

질의 하나는 판정 세 갈래로 끝납니다. 세 갈래가 **서로 겹치지 않고 빠짐없이** 모든 경우를
덮는다는 것이 이 조각의 전부예요.

```ts
function query(node: number, s: number, e: number, l: number, r: number): number {
  if (r < s || e < l) return INF;                 // ① 겹치지 않는다
  if (l <= s && e <= r) return tree[node] ?? INF; // ② 통째로 들어간다
  const mid = (s + e) >> 1;
  // ③ 걸쳐 있다 — 두 자식에게 나눠 묻고 작은 쪽을 고른다
  return Math.min(
    query(2 * node, s, mid, l, r),
    query(2 * node + 1, mid + 1, e, l, r),
  );
}
```

질의 `[0,2]` 에 이 조각만 실행한 결과입니다.

```text
들어간 노드   판정                     돌려준 값
노드1 [0,4]   걸쳐 있다 ③              자식 둘에게 묻는다
노드2 [0,2]   통째로 들어간다 ②        2
노드3 [3,4]   겹치지 않는다 ①          INF
              └ min(2, INF) = 2 가 답이다. 노드 셋에 들어가 하나만 읽었다
```

`INF` 가 ① 의 답인 이유가 여기서 확인됩니다. 겹치지 않는 가지는 답에 **아무것도 보태지 않아야**
하는데, `min` 에서 아무것도 안 보태는 값이 「그 어떤 원소보다도 큰 수」예요.

#### 멈춤 — 통째로 들어가는지 재는 조건을 어느 방향으로 적을 것인가

여기서 헷갈리기 쉬운 포인트는 ② 의 부등호 방향입니다. 「질의가 노드를 품으면」과 「노드가
질의에 들어가면」이 같은 말처럼 읽히는데, 코드로는 정반대예요.

```text
바른 조건    l <= s && e <= r     노드의 담당 구간이 질의 구간 안에 있다
뒤집은 조건  s <= l && r <= e     질의 구간이 노드의 담당 구간 안에 있다
             └ 뒤집으면 뿌리에서 언제나 참이라 어떤 질의든 tree[1] 을 그대로 답한다
```

뒤집은 조건으로 다섯 연산을 실행해 봅시다.

<!--proof:pause-contain-flip-->

```text
질의         바른 코드  조건을 뒤집은 코드
query [0,4]          1                   1  답이 같다
query [0,2]          2                   1  답이 다르다
query [0,4]          2                   2  답이 같다
query [3,4]          3                   2  답이 다르다

└ 질의가 배열 전체일 때만 답이 같다. 뿌리가 곧 답이라 조건의 방향이 답에 안 나타난다
```

**질의가 배열 전체일 때는 답이 같습니다.** 그때는 뿌리의 담당 구간과 질의 구간이 같아서 어느
방향으로 적어도 뿌리에서 끝나기 때문이에요. 테스트에 전체 구간 질의만 있으면 이 코드는
통과합니다.

```text
질의 [0,4] 에서   l <= s && e <= r  →  0 <= 0 && 4 <= 4  →  참
                  s <= l && r <= e  →  0 <= 0 && 4 <= 4  →  참
질의 [0,2] 에서   l <= s && e <= r  →  0 <= 0 && 4 <= 2  →  거짓, 자식으로 내려간다
                  s <= l && r <= e  →  0 <= 0 && 2 <= 4  →  참, 뿌리 값 1 을 답한다
```

#### 4. 리프를 고치고 조상만 다시 계산한다

갱신은 내려가면서 자리를 찾고 올라오면서 값을 고칩니다. 내려가는 길과 올라오는 길이 **같은 한
줄기**라는 것이 이 조각의 전부예요.

```ts
function update(node: number, s: number, e: number, i: number, v: number): void {
  if (s === e) {
    tree[node] = v; // ④ 리프 도달 — 새 값을 그대로 쓴다
    return;
  }
  const mid = (s + e) >> 1;
  if (i <= mid) update(2 * node, s, mid, i, v);
  else update(2 * node + 1, mid + 1, e, i, v);
  tree[node] = merge(node); // ⑤ 상향 재계산
}
```

`update(1, 0, 4, 3, 10)` 에 이 조각만 실행한 결과입니다.

```text
내려가는 길   노드1 [0,4]  mid=2, i=3 > 2 라 오른쪽    노드3 [3,4]  mid=3, i=3 <= 3 이라 왼쪽
              노드6 [3,3]  s = e 라 리프 ④            tree[6] ← 10

올라오는 길   노드3 [3,4] ⑤   min(10, 3) = 3      옛 값 1 이 3 으로 바뀐다
              노드1 [0,4] ⑤   min(2, 3) = 2       옛 값 1 이 2 로 바뀐다
                              └ 고친 노드가 셋. 나머지 여섯은 손대지 않았다
```

`merge` 를 부르는 자리가 `build` 와 `update` 두 곳인 것이 우연이 아닙니다. 둘 다 **자식이
정해진 뒤에 부모를 정하는** 같은 일을 해요.

#### 멈춤 — 오른쪽 끝을 하나 빼고 물어도 답이 안 틀리는 질의가 있다

여기서 헷갈리기 쉬운 포인트는 질의 구간의 오른쪽 끝입니다. 트리를 반개구간 `[l, r)` 으로 다루는
구현이 흔해서, 그 습관대로 `op.r` 을 그대로 넘기면 오른쪽 끝 한 칸이 빠져요.

```text
문제가 주는 것       [l, r]     양끝을 포함한다. r 번째 칸이 답에 들어간다
반개구간으로 읽으면  [l, r)     r 번째 칸이 빠진다
                     └ 빠진 칸이 그 구간의 최솟값이 아니면 답이 그대로다
```

오른쪽 끝을 하나 뺀 코드로 같은 다섯 연산을 실행해 봅시다.

<!--proof:pause-half-open-->

```text
질의         바른 코드  오른쪽 끝을 뺀 코드
query [0,4]          1                    1  답이 같다
query [0,2]          2                    2  답이 같다
query [0,4]          2                    2  답이 같다
query [3,4]          3                   10  답이 다르다
query [2,2]          4                  INF  답이 다르다

└ 오른쪽 끝의 값이 그 구간의 최솟값이 아니면 답이 같다. 마지막 줄은 구간이 사라져 INF 다
```

앞의 네 줄이 전개의 질의 넷이고 그중 셋이 답이 같습니다. 첫 `[0,4]` 는 최솟값이 인덱스 3 에,
`[0,2]` 는 인덱스 1 에, 갱신 뒤의 `[0,4]` 는 인덱스 1 에 있어서 오른쪽 끝을 빼도 그 값이 남아
있어요. 마지막 줄은 따로 건 한 칸짜리 질의라 구간이 `[2,1]` 이 되고, 어느 노드에도 안 들어가
`INF` 가 그대로 답이 됩니다.

```text
고치는 길이 둘이다
  (가) 질의를 [l, r+1) 로 바꿔 넘긴다        호출부에서 한 번 더한다
  (나) 판정을 양끝 포함으로 적는다           r < s || e < l 과 l <= s && e <= r 이 그것이다
       └ 이 글은 (나)다. 문제가 주는 구간과 코드가 다루는 구간이 같은 뜻이 된다
```

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `ops` 를 순서대로 받는 루프와
결과 목록을 빈 배열로 시작하는 한 줄뿐이에요 — 질의가 하나도 없으면 그 값이 그대로 답이 됩니다.

```ts
export type SegOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function segmentTreeRangeMin(A: number[], ops: SegOp[]): number[] {
  const N = A.length;
  // 겹치지 않는 가지가 돌려줄 값. 어떤 원소보다도 커야 최솟값 계산을 바꾸지 않는다.
  const INF = Number.MAX_SAFE_INTEGER;
  // 노드 번호가 이 칸 수를 넘지 않는다 — 근거는 「수식 정의와 유도」에 있다.
  const tree = new Array<number>(4 * N).fill(INF);

  /** 자식 둘의 값을 합쳐 부모 값을 만든다. 아직 안 채운 칸은 INF 로 읽는다. */
  const merge = (node: number): number =>
    Math.min(tree[2 * node] ?? INF, tree[2 * node + 1] ?? INF);

  /** 노드 `node` 가 구간 `[s, e]` 를 담당하도록 아래에서 위로 값을 채운다. */
  function build(node: number, s: number, e: number): void {
    if (s === e) {
      tree[node] = A[s] ?? INF;
      return;
    }
    const mid = (s + e) >> 1;
    build(2 * node, s, mid);
    build(2 * node + 1, mid + 1, e);
    tree[node] = merge(node);
  }

  /** `A[i]` 를 `v` 로 바꾸고 그 리프에서 뿌리까지의 노드만 다시 계산한다. */
  function update(
    node: number,
    s: number,
    e: number,
    i: number,
    v: number,
  ): void {
    if (s === e) {
      tree[node] = v; // ④ 리프 도달 — 새 값을 그대로 쓴다
      return;
    }
    const mid = (s + e) >> 1;
    if (i <= mid) update(2 * node, s, mid, i, v);
    else update(2 * node + 1, mid + 1, e, i, v);
    tree[node] = merge(node); // ⑤ 상향 재계산
  }

  /** 노드 `node`(담당 `[s, e]`)에서 질의 `[l, r]` 의 최솟값을 답한다. */
  function query(
    node: number,
    s: number,
    e: number,
    l: number,
    r: number,
  ): number {
    if (r < s || e < l) return INF; // ① 겹치지 않는다
    if (l <= s && e <= r) return tree[node] ?? INF; // ② 통째로 들어간다
    const mid = (s + e) >> 1;
    // ③ 걸쳐 있다 — 두 자식에게 나눠 묻고 작은 쪽을 고른다
    return Math.min(
      query(2 * node, s, mid, l, r),
      query(2 * node + 1, mid + 1, e, l, r),
    );
  }

  build(1, 0, N - 1);

  const result: number[] = [];
  for (const op of ops) {
    if (op.type === "update") update(1, 0, N - 1, op.i, op.v);
    else result.push(query(1, 0, N - 1, op.l, op.r));
  }
  return result;
}
```

```text
segmentTreeRangeMin([5, 2, 4, 1, 3], 위 다섯 연산)                 →  [1, 2, 2, 3]
segmentTreeRangeMin([1, 2, 3], [])                                 →  []
segmentTreeRangeMin([5], 질의 [0,0] · 갱신 i=0 v=99 · 질의 [0,0])   →  [5, 99]
```

### 알아 두면 좋은 개념 — 모노이드(항등원이 있는 결합 연산)

이 절차가 `min` 에 대해 요구한 성질은 둘뿐입니다. 하나는 **결합 법칙** — 자식 둘을 합친 값이
어느 순서로 합쳐도 같아야 노드에 미리 저장해 둘 수 있어요. 다른 하나는 **항등원** — 겹치지
않는 가지가 답을 바꾸지 않으려면 「합쳐도 아무 일이 없는 값」이 있어야 합니다.

```text
이 글에서 그 둘이 나온 자리

  결합 법칙   노드1 = min(노드2, 노드3) 이고 노드2 = min(노드4, 노드5) 였다
              min(min(A[0], A[1]), A[2]) 와 min(A[0], min(A[1], A[2])) 가 같아야 성립한다
  항등원      T5 와 T12 의 INF. min(2, INF) = 2 라 답이 안 바뀌었다
              └ 이 둘을 갖춘 연산을 모노이드라고 부른다
```

이름을 붙이고 나면 이 트리가 `min` 전용이 아니라는 것이 곧바로 확인됩니다. 연산과 항등원만
갈아 끼우면 같은 코드가 그대로 다른 질의를 답해요.

| 연산 | 항등원 | 세그먼트 트리로 되는가 | 접두 표만으로 되는가 |
| --- | --- | --- | --- |
| 최솟값 | `+∞` — 코드의 `INF` 가 그 자리다 | 됩니다. 이 글이 그것입니다 | 안 됩니다. 덜어 내는 연산이 없습니다 |
| 최댓값 | `−∞` | 됩니다 | 안 됩니다 |
| 덧셈 | `0` | 됩니다 | 됩니다. 뺄셈이 앞부분을 덜어 냅니다 |
| 최대공약수 | `0` | 됩니다 | 안 됩니다 |
| 행렬 곱 | 단위행렬 | 됩니다. 순서를 지켜 합치면 됩니다 | 안 됩니다 |

마지막 줄이 결합 법칙만 요구한다는 말의 뜻입니다 — 행렬 곱은 교환 법칙이 성립하지 않는데도
됩니다. [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 가 쓰는
접두 표는 그보다 강한 조건(역원)을 요구하고, 그 대신 질의가 뺄셈 한 번으로 끝나요.

| 같은 이름을 다시 만나는 자리 | 무엇을 하는가 | 요구하는 조건 |
| --- | --- | --- |
| 거듭제곱 | `x^n` 을 절반씩 접어 계산한다 | 결합 법칙 |
| 접두 표 | 구간의 값을 두 칸의 차이로 만든다 | 결합 법칙 + 역원 |
| 스파스 테이블 | 겹치는 두 칸으로 덮는다 | 결합 법칙 + 멱등성 |

셋이 요구하는 조건이 다 다르고, 이 트리가 그중 가장 약한 것만 씁니다. 거듭제곱 쪽은
[`fastPower`](../../number-theory/fastPower/fastPower-problem.md) 가 같은 조건을 같은 이름으로
다뤄요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 노드 값과 질의를 식으로 어떻게
적는지, 무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 배열이 **질의를 처리하는 동안 바뀝니다.** 안 바뀌면 미리 만드는 비용을 더 줄이는 설계가
  있어요.
- 질의가 **연속 구간**에 매기는 값을 묻습니다. 인덱스를 골라 담는 질의라면 노드의 담당 구간에
  안 맞습니다.
- 합치는 연산에 **결합 법칙과 항등원이 있습니다.** 최솟값·최댓값·합·최대공약수가 그렇습니다.
- 갱신과 질의를 합친 개수 `Q` 가 **미리 만드는 비용을 갚을 만큼** 많습니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  갱신이 섞인다      → 리프에서 뿌리까지 다시 계산하는 코드가 필요하다
  연속 구간          → 두 끝 l 과 r 만 받으면 상태가 끝난다
  결합 법칙과 항등원 → merge 한 줄과 INF 하나로 모든 갈래가 닫힌다
  연산이 많다        → 미리 만드는 5N 을 Q 개가 나눠 진다
```

마지막 줄에 경계가 있습니다. 미리 만드는 데 `5N − 3` 번을 쓰고 연산 하나가 `3⌈log₂N⌉ + 1`
번 이하이니, 연산이 한둘뿐이면 그냥 구간을 직접 읽는 편이 적어요.

```text
N = 100,000 일 때 (배열 접근만 센다)
  연산 1 개, 구간 10 칸    직접 10 번          트리를 만들면 499,997 번
  연산 100,000 개          직접 최악 100억     트리를 만들면 5,699,997 번
                           └ 경계는 「연산이 몇 개인가」다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "i 번째 원소를 v 로 바꾼다"  "갱신 질의"  "실시간으로 반영"   ← 결정적인 신호다
  "구간 [l, r] 의 최솟값"  "최댓값"  "합"  "최대공약수"
  "연산이 순서대로 주어진다"  "각 질의에 대해 답하라"          ← 질의가 많다는 뜻이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N×Q 가 못 들어간다
  갱신과 질의의 비율이 지문에 안 적혀 있다                     ← 둘 다 빨라야 한다는 뜻이다

반대로 이런 말이 보이면 해당하지 않는다
  "배열은 변경되지 않는다"  "정적"                             ← 질의가 아주 많으면 다른 표가 적다
  "구간에 값을 더한다"  "구간 갱신"                            ← 지연 전파가 따로 필요하다
```

두 번째 무리가 보이면 다른 절차로 갑니다. 배열이 안 바뀌면
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-problem.md) 쪽이고, 구간
합에 갱신이 붙으면 [`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-problem.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **AtCoder Library 의 `atcoder::segtree`** — 이 절차를 그대로 담은 공개 라이브러리입니다.
  선언이 `template <class S, auto op, auto e> struct segtree` 라 **합치는 연산 `op` 와 항등원
  `e` 를 타입 인자로 받아요** — 「알아 두면 좋은 개념」이 이름 붙인 조건 둘이 그대로 인터페이스가
  된 자리입니다.
  ([`atcoder/segtree.hpp`](https://github.com/atcoder/ac-library/blob/master/atcoder/segtree.hpp),
  조회 2026-09-02)
- **KACTL 의 `SegmentTree.h`** — 머리 주석이 *"Zero-indexed max-tree"* 로 최댓값 트리임을
  밝히고, 합치는 함수 `f` 와 항등원 `unit`(여기서는 `INT_MIN`)을 바꾸면 다른 연산이 된다고
  적혀 있습니다. 이 글의 `INF` 가 그 `unit` 과 같은 자리예요.
  ([`content/data-structures/SegmentTree.h`](https://github.com/kth-competitive-programming/kactl/blob/main/content/data-structures/SegmentTree.h),
  조회 2026-09-02)
- **Rust 의 `segment-tree` 크레이트 2.0.0** — `SegmentPoint` 가 구간 질의와 점 갱신을 맡고,
  같은 크레이트의 `PrefixPoint`(펜윅 트리)는 **교환 법칙을 추가로 요구**한다고 문서가 밝힙니다.
  같은 라이브러리 안에 두 조건이 갈려 있는 자리입니다.
  ([`segment_tree`](https://docs.rs/segment-tree/latest/segment_tree/), 조회 2026-09-02)

```text
세 사례가 공통으로 노출하는 것

  합치는 연산   op · f · Op 트레이트      이 글의 merge 다
  항등원        e · unit                  이 글의 INF 다
                └ 세 라이브러리 다 min 을 박아 두지 않고 바깥에서 받는다
```

#### 경쟁 설계와의 대조

같은 목표(구간 최솟값 질의에 답하기)를 노리는 다른 절차로 **스파스 테이블**이 있습니다. 층
`j` 의 칸 `i` 에 `A[i .. i+2^j−1]` 의 최솟값을 저장해 두고, 질의는 길이 `2^j` 짜리 구간 **둘로
겹쳐 덮어** 답해요. 겹쳐도 되는 것은 최솟값이 같은 값을 두 번 넣어도 답이 안 바뀌기 때문입니다.

```text
같은 질문에 두 설계가 답하는 방식

  세그먼트 트리   겹치지 않는 노드 여러 개로 갈라 합친다     읽는 칸이 최대 2⌈log₂N⌉ 개
  스파스 테이블   겹치는 두 칸으로 덮는다                    읽는 칸이 언제나 2 개
                  └ 스파스 테이블은 질의가 더 적고, 갱신을 받지 못한다
                    원소 하나가 바뀌면 그 원소를 덮는 칸이 층마다 흩어져 있어 표를 다시 만든다
```

같은 입력·같은 작업 목록에 두 설계를 나란히 두고 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은
`N = 1,024` 이고 `A[i] = (37i) mod 101`, 질의 `t` 번째는 `a = (37t) mod N` 과 `b = (91t) mod N`
을 만들어 작은 쪽을 왼쪽 끝으로 뒀어요. 갱신 `k` 번째는 `A[(53k) mod N]` 를
`((29k) mod 1000) − 500` 으로 덮어쓰고, 갱신은 질의 사이에 고르게 끼웠습니다. 전개가 쓰는 다섯
칸짜리 입력으로는 스파스 테이블의 층이 셋뿐이라 두 설계의 계수가 상수에 묻혀서, 규모를 키운
입력을 따로 씁니다.

**갱신이 하나도 없으면 질의 수가 순서를 정합니다.**

| 갱신 0 회 | 세그먼트 트리 | 스파스 테이블 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 질의 3,515 개 | **33,685** | 33,690 | 세그먼트 트리가 5 번 적습니다 |
| 질의 3,516 개 | 33,696 | **33,692** | **여기서 순서가 뒤집힙니다** |
| 질의 4,096 개 | 38,421 | **34,852** | 스파스 테이블이 1.1 배 적습니다 |
| 질의 10,000 개 | 86,424 | **46,660** | 스파스 테이블이 1.8 배 적습니다 |

**갱신이 하나라도 섞이면 순서가 반대로 갑니다.**

| 질의 4,096 개 | 세그먼트 트리 | 스파스 테이블 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 갱신 0 회 | 38,421 | **34,852** | 스파스 테이블이 앞섭니다 |
| 갱신 1 회 | **38,453** | 61,513 | **여기서 순서가 뒤집힙니다** |
| 갱신 1,024 회 | **71,189** | 27,335,716 | 세그먼트 트리가 384 배 적습니다 |

저장 칸은 세그먼트 트리가 **4,096** 이고 스파스 테이블이 **9,228** 입니다. 트리는 `4N` 을
넉넉히 잡고도 적은데, 스파스 테이블은 층이 `⌊log₂N⌋ + 1` 개라 칸이 층마다 붙어요.

```text
경계가 그 자리인 이유

  미리 만들기      세그먼트 트리 5,117 번        스파스 테이블 26,660 번
  질의 하나        세그먼트 트리 평균 8.1 번     스파스 테이블 2 번
                   (38,421 − 5,117) ÷ 4,096 = 8.13
  차이 21,543 를 질의당 차이 6.13 으로 나누면 3,514.4 가 나오고, 실측으로 뒤집히는 자리는
  3,516 이다 — 질의당 8.13 은 평균이라 한둘 어긋난다
  갱신 하나        세그먼트 트리 32 번           스파스 테이블 26,661 번(표를 통째로 다시 만든다)
                   └ 갱신 하나의 차이가 26,629 라 갱신 한 번으로 뒤집힌다
```

**이 절차가 내주는 것은 질의 하나의 비용입니다.** 스파스 테이블은 칸 두 개로 끝내는데 이쪽은
`2⌈log₂N⌉` 개까지 읽어요. 그 대신 얻는 것이 둘입니다 — 갱신을 `O(log N)` 에 받는 것과 저장
칸이 절반 이하인 것. 이 문제는 갱신이 섞여 들어오므로 여기서는 세그먼트 트리가 답이고, 같은
지문에서 **갱신이 사라지는 순간** 이 판정은 다시 해야 합니다.

### 수식 정의와 유도

노드가 담당하는 구간과 그 노드에 저장하는 값을 정의합니다. 뿌리가 배열 전체를 담당하고,
담당 구간이 두 칸 이상이면 가운데를 경계로 갈립니다.

$$\mathrm{tree}[node] = \min\bigl(A[s],\ A[s+1],\ \ldots,\ A[e]\bigr)$$

```text
담당 구간이 갈리는 모습 (N = 5)
  [0,4] → [0,2] · [3,4]
  [0,2] → [0,1] · [2,2]
  [0,1] → [0,0] · [1,1]
        └ 가운데가 내림이라 왼쪽이 한 칸 더 크거나 같다
```

$$mid = \left\lfloor \frac{s+e}{2} \right\rfloor, \qquad [s, e] \longrightarrow [s,\ mid] \cup [mid+1,\ e] \quad (s < e)$$

정의를 작은 값에 넣어 봅시다. `A` 의 값이 `[5 2 4 1 3]` 이고 `N = 5` 입니다.

```text
뿌리        node = 1,  [s,e] = [0,4],  mid = ⌊4/2⌋ = 2   →  [0,2] 와 [3,4]
왼쪽 자식   node = 2,  [s,e] = [0,2],  mid = ⌊2/2⌋ = 1   →  [0,1] 와 [2,2]
리프        node = 8,  [s,e] = [0,0],  s = e             →  tree[8] = A[0] = 5

  tree[4] = min(A[0], A[1]) = min(5, 2) = 2
  tree[2] = min(tree[4], tree[5]) = min(2, 4) = 2
  tree[1] = min(tree[2], tree[3]) = min(2, 1) = 1
```

식의 `mid` 는 코드에서도 `mid` 이고, 나눗셈은 정수 나눗셈입니다.

```ts
// 정의의 자식 관계를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const children = (node: number, s: number, e: number) => {
  const mid = (s + e) >> 1;
  return [
    { node: 2 * node, s, e: mid },
    { node: 2 * node + 1, s: mid + 1, e },
  ];
};
```

이제 질의 하나가 만지는 노드 수의 상한을 유도합니다. 깊이 `d` 를 「뿌리에서 몇 번 내려왔는가」로
두면, 같은 깊이의 노드들이 담당하는 구간은 **서로 겹치지 않습니다** — 부모의 구간을 두 조각으로
가른 것이 자식이므로, 갈래를 따라 내려간 구간끼리는 만나지 않아요.

```text
같은 깊이의 노드가 배열을 나누는 모습 (N = 5)

  깊이 1   [0,2] 가 인덱스 0·1·2 를, [3,4] 가 3·4 를 담당한다
  깊이 2   [0,1] 이 0·1 을, [2,2] 가 2 를, [3,3] 이 3 을, [4,4] 가 4 를 담당한다
  깊이 3   [0,0] 이 0 을, [1,1] 이 1 을 담당한다
           └ 한 줄 안에서 같은 인덱스를 두 노드가 담당하는 자리가 없다
```

노드 `[s,e]` 가 「걸쳐 있다」로 판정되는 것은 질의 `[l,r]` 과 겹치면서 통째로 들어가지는 않을
때입니다. 그것을 부등식으로 펴면 이렇게 됩니다.

$$s < l \le e \qquad \text{또는} \qquad s \le r < e$$

```text
왼쪽 조건    s < l <= e     인덱스 l−1 과 l 사이의 경계가 이 노드 안을 지난다
오른쪽 조건  s <= r < e     인덱스 r 과 r+1 사이의 경계가 이 노드 안을 지난다
             └ 같은 깊이의 노드는 겹치지 않으므로 경계 하나는 노드 하나 안에만 있다
               그래서 깊이마다 걸쳐 있는 노드는 최대 두 개다
```

자식을 부르는 것은 걸쳐 있는 노드뿐입니다. 그러니 깊이 `d+1` 에 들어가는 노드는 깊이 `d` 의
걸친 노드 둘이 각각 자식 둘을 부른 것이라 최대 넷이에요. 최대 깊이를 `D` 로 두면 진입한 노드의
총수 `V` 와 값을 읽은 노드의 수 `R` 이 이렇게 닫힙니다.

$$V \le 1 + 4D, \qquad R \le 2D, \qquad D = \lceil \log_2 N \rceil$$

```text
깊이별로 세면
  깊이 0       진입 1 개      걸쳐 있는 노드 ≤ 1 개
  깊이 1       진입 ≤ 2 개    걸쳐 있는 노드 ≤ 2 개
  깊이 d ≥ 2   진입 ≤ 4 개    걸쳐 있는 노드 ≤ 2 개
               └ 깊이가 D 까지이므로 다 더하면 1 + 4D 아래다
```

`R` 의 상한이 `4D` 가 아니라 `2D` 인 이유가 하나 더 있습니다. 걸쳐 있는 노드의 자식 둘이 **둘
다** 통째로 들어가면 부모의 구간도 통째로 들어가므로 부모가 걸쳐 있다는 것과 어긋나요. 그래서
걸친 노드마다 통째로 들어가는 자식은 최대 하나이고, 깊이마다 최대 둘입니다. 두 상한을 모든
`(l, r)` 짝에서 실제로 재 본 값과 대조합니다.

<!--proof:visit-bound-->

```text
    N   D  상한 1+4D  실측 최대 진입  그 짝    상한 2D  실측 최대 읽기
    5   3         13               9  [1,3]          6               3
    8   3         13              11  [1,4]          6               4
   16   4         17              15  [1,8]          8               6
   64   6         25              23  [1,32]        12              10
  256   8         33              31  [1,128]       16              14
1,024  10         41              39  [1,512]       20              18

└ 두 상한 다 실측을 웃돈다. 최대를 만드는 짝이 배열 전체가 아니라는 것도 함께 나온다
```

상한 둘 다 실측을 웃돕니다. `N = 1,024` 에서 진입 상한 41 에 실측 39, 읽기 상한 20 에 실측
18 이라 각각 2 만큼 헐거워요.

$$N = Q = 100{,}000 \Rightarrow D = 17, \quad R \le 34, \quad Q \cdot R \le 3{,}400{,}000$$

```text
제약 규모에서 견주면
  구간을 직접 읽기   10,000,000,000 번
  트리로 읽기             3,400,000 번
  10,000,000,000 ÷ 3,400,000 ≈ 2,941 배
```

같은 정의에서 **트리 배열의 칸 수**도 나옵니다. 뿌리가 `1` 이고 자식이 `2·node`, `2·node+1`
이므로 깊이 `d` 의 노드 번호는 `2^d` 이상 `2^(d+1)` 미만이고, 최대 깊이가 `D` 이므로 번호는
`2^(D+1)` 보다 작습니다.

$$node < 2^{D+1} = 2 \cdot 2^{\lceil \log_2 N \rceil} < 2 \cdot 2N = 4N$$

```text
가운데 부등식이 성립하는 근거
  2^⌈log₂ N⌉ 은 N 이상인 2 의 거듭제곱 중 가장 작은 것이다
  N 이 2 의 거듭제곱이면 정확히 N 이고, 아니면 N 보다 크되 2N 보다는 작다
  └ 그래서 2^(D+1) 이 4N 보다 작다. 2N 보다 작다는 보장은 없다
```

`2N` 으로 잡으면 왜 모자란지를 값으로 확인합니다.

<!--proof:node-index-->

```text
      N   D  실측 최대 깊이  실측 최대 번호  2^(D+1)       2N       4N  2N 이면
      5   3               3               9       16       10       20  충분
      6   3               3              13       16       12       24  모자람
     10   4               4              25       32       20       40  모자람
     16   4               4              31       32       32       64  충분
    100   7               7             253      256      200      400  모자람
  1,000  10              10           2,045    2,048    2,000    4,000  모자람
100,000  17              17         262,141  262,144  200,000  400,000  모자람

└ 실측 최대 깊이가 D 와 늘 같고, 최대 번호가 2^(D+1) 아래다
  N 이 1 부터 200 까지 중 2N 칸으로 모자란 것이 180 개다
```

`N = 6` 이 첫 자리입니다. 노드 번호가 13 까지 가는데 `2N` 은 12 예요. 200 까지 중 180 개가
그 상태이므로 `2N` 은 예외가 아니라 기본입니다.

### 불변식 — 노드의 값은 언제나 그 노드가 담당하는 구간의 최솟값이다

파트 1 에서 코드가 동작하는 것을 열세 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> `build` 가 끝난 시점과 `update` 하나가 끝난 시점마다, 모든 노드 `node` 에 대해
> `tree[node]` 는 그 노드가 담당하는 구간 `[s, e]` 의 최솟값입니다. `query` 는 `tree` 를 읽기만
> 하므로 이 성질을 바꾸지 않습니다.

```text
   깊이 0        노드1                   ●
   깊이 1        노드2 노드3             ● ●
   깊이 2        노드4 노드5 노드6 노드7  ● ● ● ●
   깊이 3        노드8 노드9             ● ●
                 └ ● 는 「담당 구간의 최솟값이 들어 있다」는 뜻이다
                   연산이 끝난 시점에는 아홉 개가 전부 ● 다
```

「끝난 시점」을 빠뜨리면 이 문장이 거짓이 됩니다. `update` 가 **진행 중인** 동안은 리프만
바뀌고 조상은 옛 값이라, 그 순간에는 조상 노드가 성질을 만족하지 않아요. T7 이 바로 그
시점입니다.

**출발점부터 봅시다.** `build` 는 리프에서 성질을 그대로 만들고, 위 노드는 자식이 정해진 뒤에
정합니다.

| 갈래 | 하는 일 | 성질이 유지되는 근거 |
| --- | --- | --- |
| `build` 리프 | `tree[node] = A[s]` | 원소 하나짜리 구간의 최솟값은 그 원소다 |
| `build` 내부 | `tree[node] = merge(node)` | 자식 둘의 구간을 합치면 부모의 구간이고, 두 자식이 이미 참이다 |
| `update` 리프 | `tree[node] = v` | 그 구간의 유일한 원소가 `v` 로 바뀌었다 |
| `update` 내부 | `tree[node] = merge(node)` | 자식 하나만 바뀌었고 그 자식이 먼저 참이 됐다 |
| `update` 경로 밖 | 아무것도 안 한다 | 담당 구간에 `i` 가 없으니 최솟값이 바뀔 수 없다 |
| `query` | `tree` 를 읽기만 한다 | 상태를 바꾸는 코드가 없다 |

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| `ops` 가 빔 | 연산 루프가 한 번도 실행되지 않는다 | `[]` |
| `update` 만 있음 | 트리는 바뀌지만 결과 목록에 아무것도 안 넣는다 | `[]` |
| `N = 1` | 뿌리가 곧 리프다. `build`·`update`·`query` 모두 `s = e` 갈래만 탄다 | `A[0]` 또는 `v` |
| `l = r` | 내려가다 리프에서 통째로 들어간다 | `A[l]` |
| 음수 값 `−1000` | `INF` 가 어떤 원소보다도 크므로 `min` 이 그대로 고른다 | `−1000` |
| 전부 같은 값 `7` | 노드마다 `min(7, 7) = 7` | `7` |
| 값이 커지는 갱신 | 리프가 커지면 조상도 다시 계산되어 옛 최솟값이 남지 않는다 | T7~T9 가 그 자리 |

마지막 줄이 이 문제에서 가장 미끄러운 자리입니다. 값이 작아지는 갱신은 조상만 비교해도 답이
맞는데, **값이 커지는 갱신은 형제의 값을 다시 봐야** 맞아요. `merge` 가 형제를 함께 읽는 이유가
그것입니다.

**이제 깨뜨려 봅시다.** 성질을 지키던 줄은 `update` 의 상향 재계산 한 줄이에요. 「리프만 고치면
되지 않나」라는 생각으로 그 줄을 지워 봅니다.

```ts
if (i <= mid) update(2 * node, s, mid, i, v);
else update(2 * node + 1, mid + 1, e, i, v);
// tree[node] = merge(node);   ← 이 줄을 지운다
```

<!--proof:mutant-no-pullup-->

```text
질의         바른 코드  상향 재계산을 지운 코드  차이
query [0,4]          1                        1     0
query [0,2]          2                        2     0
query [0,4]          2                        1    -1
query [3,4]          3                        1    -2

└ 갱신 앞의 질의 둘은 그대로이고, 갱신 뒤의 질의 둘이 옛 값을 답한다
```

갱신 앞의 질의 둘은 그대로이고 갱신 뒤의 질의 둘이 옛 값을 답합니다. 리프는 10 으로 바뀌었는데
노드3 과 노드1 이 1 을 들고 있어서, 지워진 값 1 이 계속 답으로 나와요.

```text
바른 트리    노드1 = 2   노드3 = 3   노드6 = 10     리프와 조상이 맞는다
깨진 트리    노드1 = 1   노드3 = 1   노드6 = 10     조상이 리프에 없는 값을 들고 있다
             └ 이 성질 하나로 트리가 성립하지 않는 것을 확인할 수 있다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 셋뿐입니다 — 트리를 채우는 것, 질의에 답하는 것, 갱신을 반영하는 것.
전개의 값으로 확인하면 T1 이 트리를 채우고, T2·T3~T6·T10·T11~T13 이 질의 넷을 답하고,
T7~T9 가 갱신 하나를 반영했습니다.

<!--proof:walk-cost-->

```text
갈래           걸음                        배열 접근
트리를 채운다  T1                                 22
질의 넷        T2 · T3~T6 · T10 · T11~T13          4
갱신 하나      T7~T9                               7
합                                                33

└ 같은 연산 목록을 묶음 없이 처리하면 16 번이다.
  다섯 칸짜리 입력에서는 미리 만드는 값이 아직 비용을 못 갚는다
```

세 갈래의 개수를 `N` 과 `D` 로 적으면 이렇게 됩니다. `D = ⌈log₂ N⌉` 이고 트리를 채우는 데
리프 `N` 개와 내부 노드 `N − 1` 개를 씁니다.

```text
트리 채우기   리프 N 개 × 2 + 내부 N−1 개 × 3 = 5N − 3       N=5 이면 22, 실측과 같다
질의 하나     읽은 노드 수 ≤ 2D                              N=5, D=3 이면 6 이하
갱신 하나     리프 쓰기 1 + 조상 D 개 × 3 = 3D + 1 이하      N=5, D=3 이면 10 이하, 실측 7
              └ 갱신의 실측이 상한보다 적은 것은 리프가 깊이 2 에 있기 때문이다
```

세는 것은 **배열 접근 전부**입니다 — 트리 배열의 읽기와 쓰기, 그리고 채울 때 `A` 를 읽는 것.
추가로 잡는 메모리는 트리 배열 하나뿐이라 `4N` 칸이고, 입력 배열은 채울 때 한 번만 읽어요.

```text
총식 = (5N − 3) + Σ 질의 비용 + Σ 갱신 비용
       └ 최악을 넣으면  (5N − 3) + Q · (3⌈log₂ N⌉ + 1)

N = Q = 100,000 이면 D = 17 이므로  499,997 + 100,000 × 52 = 5,699,997 번
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (질의가 전부 배열 전체) | `O(N + Q)` | `Θ(N + Q)` — 질의당 노드 1 개 |
| **평균적인 경우** (질의 구간의 분포가 필요하다) | `O(N + Q log N)` | 정의되지 않습니다 |
| **최악의 경우** (질의가 노드 경계를 어긋나게 지난다) | `O(N + Q log N)` | `Θ(N + Q log N)` — 실제로 도달합니다 |

가운데 줄이 정의되지 않는 이유를 적어 둡니다. 이 문제는 질의 구간이 **어떤 분포로 오는지 말하지
않아요.** 분포를 하나 정하면(예를 들어 두 끝을 균등하게 뽑으면) 평균도 `Θ(log N)` 이 되지만,
그것은 문제가 준 조건이 아니라 이 글이 놓은 가정입니다.

```text
최선과 최악의 차이가 상수가 아니라 log N 배다
  질의 [0, N−1]     노드 1 개를 읽는다            N=1,024 에서 1 번
  질의 [1, N−2]     노드 18 개를 읽는다           N=1,024 에서 18 번
                    └ 같은 배열, 같은 개수의 질의인데 18 배다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 트리 채우기 하나뿐이라 총식에 더할
항이 없어요 — 질의를 미리 모으지도, 좌표를 다시 매기지도 않습니다.

```text
총식 = Θ(N + Q log N) 시간 + Θ(N) 추가 메모리
       └ 채우기 Θ(N) + 연산 Q 개 × Θ(log N)     └ 트리 4N 칸. 입력 배열은 한 번만 읽는다
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에
대한 가정도 하지 않으니, 어떤 배열과 어떤 연산 목록을 넣어도 위 상한 아래라는 것이 그대로
약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
                └ 다만 질의 하나의 상한 2D 는 타이트하지 않다. N=1,024 에서 20 대 실측 18 이다
```

#### 최악을 만드는 입력

「긴 구간을 묻는 질의가 느리다」가 이 절차에서는 거짓입니다. 배열 전체를 묻는 질의는 뿌리
하나로 끝나요. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->

```text
질의의 모양              구간       구간의 칸 수  들어간 노드  읽은 노드
배열 전체                [0,1023]          1,024            1          1
왼쪽 절반                [0,511]             512            3          1
한 칸                    [500,500]             1           21          1
들어간 노드가 최대인 짝  [1,512]             512           39         10
읽은 노드가 최대인 짝    [1,1022]          1,022           39         18

└ 가장 긴 구간이 가장 적다. 칸 수와 노드 수가 같은 방향으로 가지 않는다
```

`N = 1,024` 에서 가장 많은 노드를 읽는 질의는 `[1,1022]` 입니다 — 배열 전체에서 **양 끝을 한
칸씩만 안으로 당긴** 구간이에요. 그 한 칸 때문에 뿌리가 걸쳐 있게 되고, 그 뒤로 층마다 두
조각씩 갈립니다.

```text
왜 양 끝 한 칸이 최악을 만드는가

  [0,1023]   뿌리의 담당 구간과 같다               통째로 들어간다, 노드 1 개
  [1,1022]   왼쪽 경계가 노드 안쪽을 지난다        층마다 두 조각으로 갈린다, 노드 18 개
             오른쪽 경계도 노드 안쪽을 지난다
             └ 경계 둘이 노드의 가운데를 지날수록 갈리는 조각이 는다
```

그러니 최악은 **규모와 질의의 모양이 함께** 만듭니다. `N` 과 `Q` 를 제약의 최댓값으로 두고
질의를 전부 `[1, N−2]` 로 채우면 배열 접근이 위 총식의 상한 근처에 갑니다.

```text
N = 100,000 · Q = 100,000 · 질의를 전부 [1, N−2] 로
  D = 17 이므로 질의당 읽기가 최대 34 번, 총 3,400,000 번 남짓
  1 초 제한에 견주면 여유가 크다
       └ 배열 접근 밖에 남는 비용은 재귀 호출이고, 진입 노드가 질의당 69 개 아래라 같은 규모다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 구간을 반씩 갈라 노드마다 담당 구간의
최솟값을 저장해 두었고, 질의는 세 갈래 판정으로 노드 몇 개만 읽으며, 갱신은 리프에서 뿌리까지
한 줄기만 다시 계산합니다.

```text
tree 를 4N 칸으로 잡는다 → 아래에서 위로 채운다 → 질의는 세 갈래, 갱신은 한 줄기
        └ 뿌리를 1 로   └ 5N−3 번        └ 읽기 ≤ 2⌈log₂N⌉   └ 고치는 노드 ≤ ⌈log₂N⌉+1
```

먼저 답이 붙는 문제 하나입니다. 전개의 T2 는 질의 `[0,4]` 를 노드 **하나**에 들어가서
답했는데, T11 부터 T13 까지는 질의 `[3,4]` 를 노드 **셋**에 들어가서 답했어요. 구간이 더 짧은
쪽이 더 많이 만진 이유가 무엇일까요?

```text
T2    질의 [0,4]   구간의 칸 수 5   들어간 노드 1
T13   질의 [3,4]   구간의 칸 수 2   들어간 노드 3
                   └ 칸 수가 적은 쪽이 노드를 더 만졌다
```

<!--check:whyShortCostsMore-->
비용을 정하는 것이 구간의 칸 수가 아니라 **노드의 담당 구간과 맞는지**이기 때문입니다.
`[0,4]` 는 뿌리의 담당 구간과 글자 그대로 같아서 판정 ② 가 곧바로 참이 되고 거기서 끝나요.
`[3,4]` 는 뿌리와 다르므로 판정 ③ 으로 갈라지고, 왼쪽 자식에서 ① 을, 오른쪽 자식에서 ② 를
만나 노드 셋을 만집니다.

```text
질의 구간이 어느 노드의 담당 구간과 같은가

  [0,4]  =  노드1 의 담당 구간      노드 1 개
  [0,2]  =  노드2 의 담당 구간      노드 3 개 (뿌리를 거쳐야 한다)
  [3,4]  =  노드3 의 담당 구간      노드 3 개 (뿌리를 거쳐야 한다)
  [1,3]  =  어느 노드와도 다르다    노드 9 개
           └ 깊이가 깊은 노드와 맞을수록 내려오는 길이 길어진다
```
