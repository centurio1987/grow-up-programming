# fenwickRangeSum — 담당 구간의 길이를 칸마다 다르게 두면 갱신과 질의가 함께 줄어드는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 질의마다 구간을 직접 더하는
방법에서 칸마다 담당 길이를 다르게 두는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열의 원소가 중간에 바뀌는데 구간의 합을 계속 답해야 합니다. 미리 더해 둔 값이 갱신 하나에
통째로 거짓이 되면 안 되고, 그 조건이 **합을 배열 전체가 아니라 여러 조각에 나눠 담으라**고
말합니다.

조각을 어떻게 나누는지가 이 절차의 전부예요. 저장용 배열의 칸에 1 부터 번호를 매기고, 칸
번호를 이진수로 적었을 때 **가장 낮은 자리에 있는 1 비트의 크기**를 그 칸이 담당하는 구간의
길이로 삼습니다. 칸 `k` 는 오른쪽 끝이 `k` 이고 길이가 그만큼인 구간의 합을 저장해요.

```text
칸 번호   이진 표기   담당 길이   담당 구간(1 부터 센다)
   1      0001              1     [1,1]
   2      0010              2     [1,2]
   3      0011              1     [3,3]
   4      0100              4     [1,4]
   5      0101              1     [5,5]
   6      0110              2     [5,6]
   7      0111              1     [7,7]
   8      1000              8     [1,8]
        └ 길이가 1·2·4·8 로 섞여 있고, 긴 칸은 적고 짧은 칸은 많다
```

앞 `r` 개의 합은 이 조각 몇 개를 이어 붙이면 나옵니다. `r` 에서 담당 길이를 빼면 그 조각의
왼쪽 바로 앞자리가 되고, 0 이 될 때까지 되풀이하면 겹치는 칸도 빠진 칸도 없이 앞부분이
덮여요.

```text
앞 7 개의 합
  7 = 0111    칸 7 이 [7,7] 을 준다     다음 칸 번호 7 − 1 = 6
  6 = 0110    칸 6 이 [5,6] 을 준다     다음 칸 번호 6 − 2 = 4
  4 = 0100    칸 4 가 [1,4] 를 준다     다음 칸 번호 4 − 4 = 0, 끝
              └ 조각 셋이 [1,7] 을 정확히 한 번씩 덮는다
                더한 칸의 개수가 7 의 이진 표기에 있는 1 의 개수와 같다
```

갱신도 같은 모양입니다. 값 하나가 바뀌면 고쳐야 하는 칸은 **그 자리를 담당 구간에 품은
칸**뿐이고, 그 칸들은 번호에 담당 길이를 **더해 가며** 만납니다.

```text
세 번째 자리(칸 번호 3)의 값이 바뀌면
  3 = 0011    칸 3 이 [3,3] 으로 품는다     다음 칸 번호 3 + 1 = 4
  4 = 0100    칸 4 가 [1,4] 로 품는다       다음 칸 번호 4 + 4 = 8
  8 = 1000    칸 8 이 [1,8] 로 품는다       다음 칸 번호 8 + 8 = 16, 배열 밖이라 끝
              └ 여덟 칸 중 셋만 바뀐다. 나머지 다섯은 담당 구간에 세 번째 자리가 없다
```

두 이동 다 한 걸음마다 1 비트가 하나씩 지워지거나 자리가 하나씩 올라가므로, 만지는 칸의
개수가 배열 길이의 로그입니다. 그래서 칸을 처음 채우는 데 `O(N)`, 질의 하나와 갱신 하나가
각각 `O(log N)` 이에요. `N = 100,000` 이면 어느 쪽도 칸 서른두 개를 넘지 않습니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 합**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값을 건너뛰는 칸 없이 전부 더한 값입니다.
- **누적합**이 무엇인지. 앞에서부터 쌓아 둔 합 두 개의 차이로 구간의 합을 만드는 방법이고,
  흐릿하면 [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 를
  먼저 봅니다. 이 글은 그 표에 **갱신이 섞여 들어올 때**를 다룹니다.
- **정수의 이진 표기**. 어떤 자연수든 2 의 거듭제곱 몇 개의 합으로 한 가지 방법으로 적힙니다.
- **비트 연산 `&` 와 음수의 표현**. `-i` 는 `i` 의 비트를 뒤집고 1 을 더한 값이라, `i & -i` 가
  가장 낮은 자리의 1 비트만 남깁니다.

```text
i  = 6 = 0110
-i     = 1010     비트를 뒤집어 1001, 거기에 1 을 더한 값이다
──────────────
i & -i = 0010     가장 낮은 자리의 1 비트만 남는다. 값은 2 다
```

「구간의 값을 묻는다」만으로는 어느 절차를 쓸지 안 정해집니다. **무엇을 묻는가**와 **배열이
바뀌는가** 둘이 함께 있어야 갈려요. 합이 아니라 최솟값을 묻는 문제는
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-problem.md) 이 다루고,
배열이 아예 안 바뀌는 문제는
[`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 쪽입니다.

```text
[1 2 3 4 5] 에서
  구간 [0,4] 의 합을 답하라       15      ← 이 글도 하고 누적합 표도 한다
  A[2] 를 10 으로 바꿔라          —       ← 이 글만 한다. 누적합 표는 뒤쪽을 전부 고쳐야 한다
  구간 [0,4] 의 최솟값을 답하라   —       ← 이 글은 안 한다. 뺄셈으로 앞부분을 덜어낼 수 없다
```

### 아이디어 상세 — 담당 길이를 칸마다 다르게 두는 방법을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
export type FenwickOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function fenwickRangeSum(A: number[], ops: FenwickOp[]): number[];
```

- 입력: 정수 배열 `A` 와 연산 목록 `ops`. `update` 는 `A[i]` 를 `v` 로 덮어쓰고(누적이
  아닙니다), `query` 는 **양끝을 포함하는** 구간 `[l, r]` 의 합을 묻습니다.
- 출력: `query` 의 답만 **입력 순서 그대로** 담은 배열. 질의가 없으면 빈 배열.
- 제약: `1 ≤ N ≤ 100,000`, `0 ≤ Q ≤ 100,000`, `−10,000 ≤ A[i], v ≤ 10,000`, `0 ≤ i < N`,
  `0 ≤ l ≤ r < N`. 시간 1초, 메모리 256 MB.

이 글이 쓰는 기호는 11 개예요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `N` | 배열 `A` 의 길이 | `N ≤ 100,000` |
| `Q` | 연산 목록 `ops` 의 길이 | `Q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값. 0 부터 셉니다 | `−10,000` 이상 `10,000` 이하 |
| `i` | `update` 가 바꿀 자리 | `0 ≤ i < N` |
| `v` | `update` 가 써 넣을 새 값 | `−10,000` 이상 `10,000` 이하 |
| `l` | `query` 구간의 왼쪽 끝 | `0 ≤ l ≤ r` |
| `r` | `query` 구간의 오른쪽 끝. 양끝을 포함합니다 | `r < N` |
| `k` | 저장용 배열의 칸 번호. **1 부터** 셉니다 | `1 ≤ k ≤ N` |
| `lowbit(k)` | 칸 `k` 가 담당하는 구간의 길이 | 1 · 2 · 4 · 8 … |
| `tree[k]` | 칸 `k` 가 담당하는 구간의 합 | 칸이 `N + 1` 개 |
| `delta` | 갱신 하나가 만드는 변화량 | `v` 에서 옛 값을 뺀 수 |

가장 먼저 떠오르는 방법으로 시작합시다. 배열을 그대로 들고 있다가, 질의가 오면 그 구간을
왼쪽부터 오른쪽까지 직접 더하고, 갱신은 칸 하나를 고치는 것이에요.

```ts
for (const op of ops) {
  if (op.type === "update") {
    arr[op.i] = op.v;                                  // 칸 하나를 쓴다
  } else {
    let s = 0;
    for (let k = op.l; k <= op.r; k++) s += arr[k] ?? 0;
    result.push(s);                                    // 구간을 직접 더한다
  }
}
```

갱신은 한 번에 끝나는데 질의가 구간의 칸 수만큼 읽습니다. 그러면 반대로 해 보면 어떨까요.
합에는 **뺄셈**이 있으니 앞에서부터 쌓아 둔 값 두 개의 차이로 구간의 합을 만들 수 있어요.

```ts
// P[k] 에 앞 k 개의 합을 담아 두면
result.push((P[op.r + 1] ?? 0) - (P[op.l] ?? 0));      // 질의는 뺄셈 한 번이다

// 그런데 A[i] 가 바뀌면
for (let k = op.i + 1; k <= N; k++) P[k] = (P[k] ?? 0) + delta;   // 표 뒤쪽을 전부 고친다
```

두 방식을 제약 규모에 넣어 봅시다. 질의 `N` 개는 전부 배열 전체를 묻고, 갱신 `N` 개는 서로
다른 자리를 덮어씁니다.

<!--proof:two-ways-scale-->

```text
       N = Q     직접 · 질의  직접 · 갱신  누적합 · 질의   누적합 · 갱신
       1,000       1,000,000        1,000          2,000       1,003,000
      10,000     100,000,000       10,000         20,000     100,030,000
100,000 (식)  10,000,000,000      100,000        200,000  10,000,300,000

└ 질의 N 개는 전부 배열 전체를 묻고, 갱신 N 개는 인덱스 (59k) mod N 를 덮어쓴다
  미리 만드는 값은 뺀 수다. 한쪽이 작아지면 반대쪽이 그만큼 커진다
```

둘 다 100억 번입니다. 단순 연산을 초당 1억 번으로 잡아도 100초가 걸려요. **한쪽을 줄인 만큼
반대쪽이 커진** 것이지 총량이 준 것이 아닙니다.

```text
배열을 그대로 들면    질의가 구간의 칸 수만큼      갱신은 한 번
누적합 표를 들면      질의는 두 칸                 갱신이 표 뒤쪽 전부
                      └ 저장한 값 하나가 넓은 구간을 담당할수록 갱신이 그 값을 자주 건드린다
```

같은 작업 목록에 두 방식을 적용해 실제 계수를 봅시다. 전개가 쓸 다섯 칸짜리 입력은 계수를
갈라 보기에 너무 작아서, 같은 규칙으로 만든 1,024 칸 입력에 질의 512 개와 갱신 512 개를 섞은
목록을 씁니다. 세는 것은 **배열 접근 수**(읽기 + 쓰기)예요.

<!--proof:mixed-load-->

```text
방식         미리 만들기  질의 512 개  갱신 512 개       합  추가 칸
직접 더하기            0      173,944          512  174,456        0
누적합 표          3,072        1,024      530,944  535,040    1,025

└ 답은 둘 다 같다. 질의가 크게 줄고 갱신이 그보다 크게 늘었다
```

질의가 173,944 에서 1,024 로 줄고 갱신이 512 에서 530,944 로 늘었습니다. 여기서 관찰할 것은
**저장한 값 하나가 담당하는 구간의 길이가 두 비용을 동시에 정한다**는 것 하나예요 — 길면
질의가 유리해지고 갱신이 불리해집니다.

```text
담당 구간의 길이를 키우면
  질의   온전히 들어가는 조각이 늘어 읽는 횟수가 준다
  갱신   그 값을 품은 조각이 넓어져 고칠 횟수가 는다
         └ 길이를 하나로 정하는 한 둘을 동시에 줄일 수 없다
```

그 관찰을 개념으로 세워 봅시다. 가장 단순한 후보는 **길이를 하나로 고정**하는 것이에요.
배열을 `B` 칸씩 끊어 묶음마다 합 하나를 저장하면, 갱신은 그 묶음의 합에 변화량을 더하는
것으로 끝나고 질의는 온전히 들어가는 묶음만 저장값으로 읽습니다.

```text
B = 2 로 [1 2 3 4 5] 를 끊으면

  묶음 번호        0      1      2
  덮는 인덱스  [0,1]  [2,3]  [4,4]
  저장값           3      7      5

  질의 [1,3] 을 답하려면
     인덱스 1   묶음 0 이 절반만 걸쳐 A[1] = 2 를 직접 읽는다
     인덱스 2·3 묶음 1 이 통째로 들어가 저장값 7 을 읽는다
                                                      →  2 + 7 = 9
```

이 방법은 갱신을 배열 길이와 무관하게 만들지만 질의 하나의 최악이 `2(B − 1) + N / B` 입니다.
양 끝에서 남는 칸이 최대 `B − 1` 개씩이고 온전히 들어가는 묶음이 최대 `N / B` 개인데, `B` 를
어느 쪽으로 움직여도 두 항 중 하나가 커져요.

```text
질의 하나가 읽는 칸의 최악   =  2(B − 1)  +  N / B
                                └ 남는 칸    └ 묶음 수
  B 를 키우면                   남는 칸이 늘고 묶음 수가 준다
  B 를 줄이면                   남는 칸이 줄고 묶음 수가 는다
  N = 1,024 에서 가장 좋은 B    22 나 23 이고 그때가 89 번 언저리다
                                └ 자릿수를 따라가면 스무 번 아래다. 규모가 다르다
```

원인이 「길이가 하나」라면 **길이를 여럿 두면** 됩니다. 그런데 길이를 아무렇게나 섞으면 질의
하나가 어느 조각을 골라야 하는지 매번 찾아야 해요. 칸 번호만 보고 곧바로 알 수 있게 정하는
방법이 **번호의 가장 낮은 1 비트를 담당 길이로 삼는 것**입니다.

<!--proof:lowbit-cover-->

```text
칸 k  k 의 이진 표기  담당 길이  담당 구간  칸 수
   1  0001                    1  [1,1]          1
   2  0010                    2  [1,2]          2
   3  0011                    1  [3,3]          1
   4  0100                    4  [1,4]          4
   5  0101                    1  [5,5]          1
   6  0110                    2  [5,6]          2
   7  0111                    1  [7,7]          1
   8  1000                    8  [1,8]          8

└ 칸 여덟 개가 길이 1·2·4·8 짜리 구간을 함께 덮는다
  길이가 긴 칸은 적고 짧은 칸은 많다 — 이 분포가 두 비용을 함께 누른다
```

이 정의가 각 상태의 이동 범위를 정합니다. 앞부분의 합을 모으는 이동은 칸 번호에서 담당
길이를 빼므로 **1 비트가 한 걸음에 하나씩 지워지고**, 갱신이 고칠 칸을 찾는 이동은 담당
길이를 더하므로 **1 비트의 자리가 한 걸음에 하나씩 올라갑니다.**

```text
움직이는 범위
  앞부분의 합    r 에서 시작해 1 비트를 하나씩 지운다     r 의 1 비트 개수만큼
  갱신           i+1 에서 시작해 자리를 하나씩 올린다     ⌊log₂ N⌋ + 1 칸 이하
                 └ 둘 다 배열 길이가 아니라 자릿수를 따라간다
```

정의를 세웠으니 **질의도 갱신도 같은 규칙 하나로** 처리되는지 봐야 합니다. 걸리는 것 없이
되는 경우와 미덥지 않은 경우를 갈라 값으로 확인해 봅시다. 쉬운 경우는 오른쪽 끝이 어느 칸의
담당 구간과 정확히 맞을 때예요 — 앞 4 개의 합은 칸 4 하나로 끝납니다.

```text
A 의 값 [1 2 3 4 5] 에서 (칸 번호는 1 부터, 인덱스는 0 부터)

  앞 4 개의 합    칸 4 [1,4] 하나                     10          읽은 칸 1 개
  앞 5 개의 합    칸 5 [5,5] · 칸 4 [1,4]             5 + 10 = 15 읽은 칸 2 개
  앞 3 개의 합    칸 3 [3,3] · 칸 2 [1,2]             3 + 3 = 6   읽은 칸 2 개
                  └ 이어 붙인 구간이 겹치지도 빠지지도 않는다
```

불안한 경우는 **갱신이 앞부분의 합을 거짓으로 만들지 않는가**입니다. `A[2]` 를 3 에서 10 으로
바꾸면 늘어난 값이 7 이고, 그 자리를 품은 칸은 칸 3 과 칸 4 둘이에요. 두 칸에만 7 을 더하면
앞부분의 합이 어느 `r` 에서든 다시 맞습니다.

```text
A[2] 를 3 → 10 으로 바꾸면 (칸 번호 3 부터 시작한다)

  칸     담당 구간(1 부터)   그 구간의 인덱스   인덱스 2 를 품는가   갱신 뒤 값
  칸 1   [1,1]               0                  아니다               1
  칸 2   [1,2]               0 · 1              아니다               3
  칸 3   [3,3]               2                  그렇다               3 + 7 = 10
  칸 4   [1,4]               0 · 1 · 2 · 3      그렇다               10 + 7 = 17
  칸 5   [5,5]               4                  아니다               5
           └ 담당 구간은 1 부터 센 번호이고 그 옆 열이 같은 자리를 0 부터 센 것이다
             앞 5 개의 합 = 5 + 17 = 22 다. 갱신 전 15 에 7 을 더한 값과 같다
```

빠뜨리는 칸이 없는 이유는 루프의 종료 조건으로 말할 수 있습니다. 앞부분의 합을 모으는 이동은
칸 번호가 0 이 될 때 멈추고, 그때까지 지난 칸들의 담당 구간을 이어 붙이면 `[1, r]` 이 정확히
한 번씩 덮여요. 갱신 쪽 이동은 칸 번호가 `N` 을 넘을 때 멈추고, 그 사이의 칸이 **바뀐 자리를
품은 칸 전부**입니다.

```text
두 이동의 종료 조건
  앞부분의 합   칸 번호가 0 이 되면 멈춘다      지난 칸의 담당 구간을 이으면 [1,r] 이다
  갱신          칸 번호가 N 을 넘으면 멈춘다    지난 칸이 바뀐 자리를 품은 칸 전부다
                └ 둘 다 「더 갈 곳이 없다」로 끝나므로 건너뛰는 자리가 생기지 않는다
```

이제 길이를 섞는 것이 정말 가장 적은지 값으로 확인합니다. 고정 길이 `B` 를 아홉 가지로 두고
같은 작업 목록에서 셌어요.

```text
  2. update(i, v) 는 변화량을 만들고, 칸 i+1 부터 담당 길이를 더해 가며 고친다
  3. query(l, r) 은 앞 r+1 개의 합에서 앞 l 개의 합을 뺀다

```

### 수행으로 알아보는 알고리즘 — 다섯 칸을 채우고 연산 넷을 처리한다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const A = [1, 2, 3, 4, 5];
const ops: FenwickOp[] = [
  { type: "query", l: 0, r: 4 },
  { type: "update", i: 2, v: 10 },
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 2, r: 3 },
];
// 이 절이 끝나면 [15, 22, 14] 가 나와야 한다
```

왜 하필 이 넷일까요? 문제 문서의 예시를 그대로 가져온 것이고, 이 넷이 **갈래를 전부
실행**하기 때문이에요. 갱신이 가운데 있어서 같은 질의 `[0,4]` 의 답이 앞뒤로 갈리고, 마지막
질의는 왼쪽 끝이 0 이 아니라 **빼는 쪽 호출까지** 실행합니다. `N = 5` 라 담당 길이 1·2·4 가
셋 다 나와요.

```text
절차 전체를 한 장으로

  tree 를 N+1 칸으로 잡고 0 으로 채운다 (칸 0 은 쓰지 않는다)

  채우기:  칸마다 자기 몫을 넣는다                                   ③
           칸 k 가 k + 담당 길이 번 칸에 자기 값을 한 번 넘긴다      ④

  연산을 순서대로 받으며:
      update(i, v)   변화량을 만들고 논리 배열을 고친다              ⑤
                     칸 i+1 부터 담당 길이를 더해 가며 고친다        ①
      query(l, r)    앞 r+1 개의 합에서 앞 l 개의 합을 뺀다          ⑥
                     앞부분의 합은 담당 길이를 빼 가며 모은다        ②
```

#### 1. 칸 0 을 비우고 배열 하나를 잡는다

저장용 배열을 `N + 1` 칸으로 잡고 칸 번호를 1 부터 씁니다. 칸 0 을 비워 두는 것이 이 조각의
전부인데, 그 한 줄이 두 이동의 종료 조건을 만들어요.

```ts
const N = A.length;
const arr = A.slice();
const tree = new Array<number>(N + 1).fill(0);
const lowbit = (k: number): number => k & -k;
```

0 의 담당 길이는 0 입니다. 그러니 칸 0 에서는 빼도 더해도 제자리예요.

```text
칸 번호   담당 길이   빼 가는 이동   더해 가는 이동
      0           0   0 − 0 = 0      0 + 0 = 0      제자리다
      1           1   1 − 1 = 0      1 + 1 = 2      끝나거나 위로 올라간다
          └ 그래서 칸 번호를 1 부터 쓰고 칸 0 은 비워 둔다
```

논리 배열 `arr` 를 따로 두는 것도 여기서 정합니다. 이 문제의 갱신이 **덮어쓰기**라 새 값과
옛 값의 차이가 필요하고, 옛 값을 아는 자리가 `arr` 예요.

#### 2. 자기 몫을 채우고 위 칸에 한 번만 넘긴다

채우는 순서가 이 조각의 전부입니다. 칸 `k` 의 값은 자기 몫과 **자기보다 번호가 작은 칸들의
몫**으로 이루어지므로, 번호가 작은 칸부터 위로 넘기면 한 바퀴로 끝나요.

```ts
for (let i = 1; i <= N; i++) tree[i] = arr[i - 1] ?? 0; // ③ 자기 몫만 채운다
for (let i = 1; i <= N; i++) {
  const j = i + lowbit(i);
  if (j <= N) tree[j] = (tree[j] ?? 0) + (tree[i] ?? 0); // ④ 위 칸에 한 번만 넘긴다
}
```

이 조각만 실행하면 다섯 칸이 이렇게 채워집니다.

```text
걸음   하는 일                          칸 1  칸 2  칸 3  칸 4  칸 5
T1     자기 몫만 채운다                    1     2     3     4     5
T2     칸 1 이 칸 2 에 1 을 넘긴다         1     3     3     4     5
T3     칸 2 가 칸 4 에 3 을 넘긴다         1     3     3     7     5
T4     칸 3 이 칸 4 에 3 을 넘긴다         1     3     3    10     5
       └ 칸 4 와 칸 5 는 받을 칸이 5 를 넘어 아무 데도 안 넘긴다
```

채워진 값을 담당 구간과 대조하면 정의대로입니다 — 칸 2 는 `[1,2]` 라 1 + 2 = 3, 칸 4 는
`[1,4]` 라 1 + 2 + 3 + 4 = 10 이에요. 넘기는 값이 **칸 `i` 의 최종값**이라는 것이 T3 에서
확인됩니다. 칸 2 가 넘긴 값이 2 가 아니라 3 이었어요.

#### 짚고 가기 — 넘겨주는 바퀴는 오름차순이어야 한다

여기서 헷갈리기 쉬운 지점은 두 번째 바퀴의 방향입니다. 「어느 순서로 넘겨도 같은 값이
모인다」고 읽히는데, 넘기는 값이 그 칸의 **최종값**이어야 하므로 순서가 답을 정합니다.

```text
오름차순    칸 i 에 올 것이 다 온 뒤에 넘긴다     칸 2 가 3 을 넘긴다
내림차순    칸 i 가 아직 덜 받은 채로 넘긴다      칸 2 가 2 를 넘긴다
            └ 칸 1 의 몫 1 이 칸 4 에 영영 안 간다
```

내림차순으로 지나간 코드에 같은 연산 넷을 실행해 봅시다.

<!--proof:pause-build-order-->

```text
질의         바른 코드  내림차순으로 지나간 코드
query [0,4]         15                        14  답이 다르다
query [0,4]         22                        21  답이 다르다
query [2,3]         14                        13  답이 다르다

└ 세 답이 전부 1 씩 작다 — 칸 4 가 10 대신 9 를 들고 있다
```

세 답이 정확히 1 씩 작습니다. 잃어버린 1 이 칸 1 의 값이고, 세 질의가 모두 칸 4 를 읽기
때문에 같은 크기만큼 어긋나요. **받는 칸의 번호가 언제나 준 칸보다 크다**는 성질 하나가
오름차순 한 바퀴를 정당하게 만듭니다.

#### 3. 담당 구간을 이어 붙여 앞부분의 합을 낸다

질의 하나는 앞부분의 합 두 번으로 끝납니다. 칸 번호에서 담당 길이를 빼 가며 저장값을 모으는
것이 그 조각의 전부예요.

```ts
function prefix(r: number): number {
  let sum = 0;
  for (let k = r; k > 0; k -= lowbit(k)) {
    sum += tree[k] ?? 0; // ② 담당 구간을 이어 붙이며 내려간다
  }
  return sum;
}

result.push(prefix(op.r + 1) - prefix(op.l)); // ⑥ 구간 합을 접두 합 둘의 차로
```

질의 `[0,4]` 에 이 조각만 실행한 결과입니다.

```text
걸음   부르는 곳    보는 칸        더한 값   다음 칸 번호
T5     prefix(5)    칸 5 [5,5]     5         5 − 1 = 4
T6     prefix(5)    칸 4 [1,4]     5 + 10    4 − 4 = 0, 끝
T7     prefix(0)    없다           0         루프가 실행되지 않는다
                    └ 답은 15 − 0 = 15 이다
```

오른쪽 끝에 `+ 1` 이 붙는 이유가 여기서 확인됩니다. `prefix(r)` 는 **앞 `r` 개**의 합이라
인덱스 `r − 1` 까지예요. 인덱스 `r` 까지 포함하려면 앞 `r + 1` 개를 물어야 하고, 왼쪽은
인덱스 `l − 1` 까지를 덜어 내야 하므로 앞 `l` 개입니다.

#### 4. 덮어쓰기를 변화량으로 바꿔 담당 칸만 고친다

갱신은 두 걸음입니다. 덮어쓰기를 변화량으로 바꾸는 것이 첫 걸음이고, 그 변화량을 담당 칸에
더하는 것이 두 번째예요.

```ts
function add(i: number, delta: number): void {
  for (let k = i; k <= N; k += lowbit(k)) {
    tree[k] = (tree[k] ?? 0) + delta; // ① 담당 칸을 따라 올라간다
  }
}

const delta = op.v - (arr[op.i] ?? 0); // ⑤ 덮어쓰기를 변화량으로 바꾼다
arr[op.i] = op.v;
add(op.i + 1, delta);
```

`update(i=2, v=10)` 에 이 조각만 실행한 결과입니다.

```text
걸음   하는 일                        칸 번호   결과
T8     변화량 10 − 3 = 7 을 만든다    —         arr 가 [1 2 10 4 5] 가 된다
T9     칸 3 에 7 을 더한다            3         3 → 10, 다음은 3 + 1 = 4
T10    칸 4 에 7 을 더한다            4         10 → 17, 다음은 4 + 4 = 8 이라 끝
                                                └ 고친 칸이 둘. 나머지 셋은 손대지 않았다
```

채우기의 두 번째 바퀴와 `add` 가 같은 방향으로 움직인다는 것을 여기서 확인해 둡시다. 둘 다
칸 번호에 담당 길이를 더하는 이동인데, 채우기는 **한 칸만** 넘기고 `add` 는 `N` 을 넘을
때까지 계속 올라갑니다.

```text
같은 방향, 다른 거리
  채우기 두 번째 바퀴   i → i + 담당 길이 한 번만        칸마다 많아야 한 번이라 다 합쳐 N 회 아래
  add(i, delta)         i → i + 담당 길이 → … → N 초과   한 번에 ⌊log₂ N⌋ + 1 칸 이하
                        └ 채우기가 이 이동을 칸마다 한 조각씩 나눠 맡은 것이다
```

#### 짚고 가기 — 새 값을 그대로 더하면 초기값이 0 인 배열에서만 답이 맞는다

여기서 헷갈리기 쉬운 지점은 `update` 의 뜻입니다. 이 절차가 저장하는 것은 **합**이라 더하는
연산밖에 없는데, 문제가 주는 연산은 「그 자리를 `v` 로 바꿔라」예요.

```text
문제가 주는 것       A[i] ← v          덮어쓰기다. 옛 값이 사라진다
절차가 할 수 있는 것 tree[k] += d      더하기다. 옛 값 위에 쌓인다
                     └ 그래서 d = v − 옛 값 으로 바꿔서 넣는다
```

변화량을 만들지 않고 `v` 를 그대로 더한 코드에 같은 연산 넷을 실행해 봅시다.

<!--proof:pause-raw-value-->

```text
질의                       바른 코드  값을 그대로 더한 코드
query [0,4]                       15                     15  답이 같다
query [0,4]                       22                     25  답이 다르다
query [2,3]                       14                     17  답이 다르다
query [0,2] · A = [0 0 0]          7                      7  답이 같다

└ 갱신 앞의 질의와 옛 값이 0 인 자리는 답이 같다. 초기값이 0 인 배열로 시험하면 통과한다
```

**마지막 줄이 이 멈춤을 두는 이유입니다.** 초기 배열이 전부 0 이면 옛 값이 0 이라 변화량과 새
값이 같아지고, 그런 시험만 있으면 이 코드는 통과해요. 답이 어긋난 크기 3 과 3 은 각각 덮어쓴
자리의 옛 값 3 이고, 그 값이 지워지지 않고 남은 것입니다.

#### 5. 네 연산을 처음부터 끝까지 처리한다

세 조각을 하나로 이어 고정 입력에 실행하면 열세 걸음이 나옵니다. 앞의 넷이 칸을 채우는
걸음이고 나머지 아홉이 연산 넷을 처리하는 걸음이에요.

| 걸음 | 연산 | 보는 칸 | 하는 일 | 그 결과 | 갈래 |

| T2 | — | 칸 2 | 칸 1 의 1 을 받는다 | `tree[2] = 3` | ④ |
| T3 | — | 칸 4 | 칸 2 의 3 을 받는다 | `tree[4] = 7` | ④ |
| T4 | — | 칸 4 | 칸 3 의 3 을 받는다 | `tree[4] = 10` | ④ |
| T5 | `query l=0 r=4` | 칸 5 | 저장값을 더한다 | 합 `5` | ② |

| T12 | `query l=2 r=3` | 칸 4 | 앞 4 개의 합을 낸다 | `17` | ② |
| T13 | `query l=2 r=3` | 칸 2 | 앞 2 개의 합을 뺀다 | `17 − 3 = 14` | ⑥ |

질의 셋의 답과 그때 다섯 칸의 상태를 함께 보면 갱신이 어디까지 반영됐는지 확인됩니다.

갱신이 반영된 자리예요.

#### 짚고 가기 — 논리 배열을 함께 고치지 않으면 같은 자리를 두 번 갱신할 때만 답이 갈린다

여기서 헷갈리기 쉬운 지점은 `arr` 를 고치는 한 줄입니다. 변화량을 만들고 나면 그 줄이 할 일이
없어 보이는데, **다음 갱신이 그 값을 읽습니다.**

```text
같은 자리를 두 번 갱신하면 (A = [1 2 3] · 자리 0)

  arr 를 고치면      첫 번째 5 − 1 = 4     두 번째 10 − 5 = 5     합쳐서 1 + 4 + 5 = 10
  arr 를 안 고치면   첫 번째 5 − 1 = 4     두 번째 10 − 1 = 9     합쳐서 1 + 4 + 9 = 14
                     └ 옛 값이 1 에 머물러 두 번째 변화량이 커진다
```

논리 배열을 고치는 줄을 지운 코드에 두 목록을 실행해 봅시다.

<!--proof:pause-no-sync-->

```text
질의                                  바른 코드  논리 배열을 안 고친 코드
query [0,4]                                  15                        15  답이 같다
query [0,4]                                  22                        22  답이 같다
query [2,3]                                  14                        14  답이 같다
query [0,0] · 같은 자리를 두 번 갱신         10                        14  답이 다르다

└ 한 자리를 한 번만 갱신하는 목록에서는 답이 전부 같다. 마지막 줄만 다르다
```

**전개가 쓰는 목록에서는 답이 전부 같습니다.** 갱신이 하나뿐이라 옛 값을 두 번 읽을 일이
없어요. 한 자리를 두 번 갱신하는 목록이 하나라도 있어야 이 줄이 검사되고, 그런 목록이 없는
시험은 이 코드를 통과시킵니다.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `ops` 를 순서대로 받는 루프와
결과 목록을 빈 배열로 시작하는 한 줄뿐이에요 — 질의가 하나도 없으면 그 값이 그대로 답이 됩니다.

```ts
export type FenwickOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function fenwickRangeSum(A: number[], ops: FenwickOp[]): number[] {
  const N = A.length;
  // `update` 가 덮어쓰기라 옛 값이 필요하다. 논리 배열을 따로 들고 tree 와 함께 고친다.
  const arr = A.slice();
  // 칸 0 은 비워 둔다 — 0 의 담당 구간 길이가 0 이라 두 루프가 그 칸에서 멈추지 않는다.
  const tree = new Array<number>(N + 1).fill(0);

  /** 칸 `k` 가 담당하는 구간의 길이. */
  const lowbit = (k: number): number => k & -k;

  /** `arr[i-1]` 이 `delta` 만큼 달라진 것을 그 칸을 담당 구간에 품은 칸 전부에 반영한다. */
  function add(i: number, delta: number): void {
    for (let k = i; k <= N; k += lowbit(k)) {
      tree[k] = (tree[k] ?? 0) + delta; // ① 담당 칸을 따라 올라간다
    }
  }

  /** `arr[0..r-1]` 의 합. `r = 0` 이면 루프가 한 번도 실행되지 않아 0 이다. */
  function prefix(r: number): number {
    let sum = 0;
    for (let k = r; k > 0; k -= lowbit(k)) {
      sum += tree[k] ?? 0; // ② 담당 구간을 이어 붙이며 내려간다
    }
    return sum;
  }

  for (let i = 1; i <= N; i++) tree[i] = arr[i - 1] ?? 0; // ③ 자기 몫만 채운다
  for (let i = 1; i <= N; i++) {
    const j = i + lowbit(i);
    if (j <= N) tree[j] = (tree[j] ?? 0) + (tree[i] ?? 0); // ④ 위 칸에 한 번만 넘긴다
  }

  const result: number[] = [];
  for (const op of ops) {
    if (op.type === "update") {
      const delta = op.v - (arr[op.i] ?? 0); // ⑤ 덮어쓰기를 변화량으로 바꾼다
      arr[op.i] = op.v;
      add(op.i + 1, delta);
    } else {
      result.push(prefix(op.r + 1) - prefix(op.l)); // ⑥ 구간 합을 접두 합 둘의 차로
    }
  }
  return result;
}
```

```text
fenwickRangeSum([1, 2, 3, 4, 5], 위 연산 넷)            →  [15, 22, 14]
fenwickRangeSum([1, 2, 3], [])                          →  []
fenwickRangeSum([7], 질의 [0,0])                        →  [7]
fenwickRangeSum([1, 2, 3], 갱신 i=0 v=-5 · 질의 [0,2])  →  [0]
```

### 알아 두면 좋은 개념 — 이진 표현으로 분해하기

이 절차가 앞부분의 합에 대해 한 일을 한 문장으로 줄이면 **「`r` 을 2 의 거듭제곱의 합으로
쪼개고, 조각마다 저장값 하나를 읽는다」** 입니다. 어떤 자연수든 이진 표기가 한 가지뿐이므로
쪼개는 방법도 한 가지이고, 그래서 읽는 칸의 개수가 **1 비트의 개수**로 정해져요.

```text
이 글에서 그것이 나온 자리

  T5·T6   앞 5 개의 합을 칸 5 와 칸 4 로 답했다
          5 = 101₂ = 4 + 1 이라 조각이 둘이고, 각 조각이 칸 하나에 저장돼 있다
  T12·T13 앞 4 개는 칸 4 하나, 앞 2 개는 칸 2 하나였다
          4 = 100₂ · 2 = 10₂ 라 1 비트가 하나씩이다
          └ 1 비트를 하나씩 지우는 이동이 곧 이 분해다
```

이름을 붙이고 나면 같은 분해가 다른 자리에서도 확인됩니다. 지수를 이진 표기로 쪼개면 거듭제곱이
곱셈 몇 번으로 줄고, 조상 번호를 이진 표기로 쪼개면 나무를 몇 걸음으로 거슬러 올라갈 수 있어요.

| 같은 이름을 다시 만나는 자리 | 무엇을 쪼개는가 | 조각 하나가 하는 일 |
| --- | --- | --- |
| 거듭제곱 | 지수 `n` | `x^(2^j)` 를 한 번 곱한다 |
| 이진 들어올리기 | 거슬러 올라갈 걸음 수 | `2^j` 칸 위의 조상으로 건너뛴다 |
| 이 글의 앞부분 합 | 앞에서 센 개수 `r` | 길이 `2^j` 짜리 구간의 합을 읽는다 |

셋 다 조각의 개수가 **1 비트의 개수**이고, 그래서 비용이 자릿수로 정해집니다. 거듭제곱 쪽은
[`fastPower`](../../number-theory/fastPower/fastPower-problem.md) 가 같은 분해를 같은 이름으로
다뤄요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅시다. 어떤 문제에 이것을 쓰는지, 담당 구간과 앞부분의 합을 식으로
어떻게 적는지, 무엇이 매 연산 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 배열이 **질의를 처리하는 동안 바뀝니다.** 안 바뀌면 앞부분의 합을 한 번만 깔아 두는 쪽이
  질의를 두 칸으로 끝냅니다.
- 질의가 **연속 구간**의 합을 묻습니다. 인덱스를 골라 담는 질의라면 담당 구간에 안 맞습니다.
- 합치는 연산에 **역원과 교환 법칙이 있습니다.** 덧셈·배타적 논리합이 그렇고, 최솟값은
  역원이 없어서 안 됩니다.
- 갱신과 질의를 합친 개수 `Q` 가 **미리 만드는 비용을 갚을 만큼** 많습니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  갱신이 섞인다        → 담당 칸을 따라 올라가며 고치는 코드가 필요하다
  연속 구간            → 두 끝 l 과 r 만 받으면 상태가 끝난다
  역원과 교환 법칙     → 구간 합이 접두 합 둘의 뺄셈으로 닫히고, 더하는 순서를 안 따진다
  연산이 많다          → 미리 만드는 499,982 번을 Q 개가 나눠 진다
```

마지막 줄에 경계가 있습니다. 미리 만드는 데 499,982 번을 쓰고 연산 하나가 36 번 이하이니,
연산이 한둘뿐이면 그냥 구간을 직접 더하는 편이 적어요.

```text
N = 100,000 에서 두 방식을 견주면 (배열 접근만 센다)
  연산 1 개, 구간 10 칸    직접 10 번          칸을 채우면 499,982 번
  연산 100,000 개          직접 최악 100억     칸을 채우면 4,099,982 번
                           └ 갈림점은 연산의 개수 하나다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "i 번째 원소를 v 로 바꾼다"  "값을 더한다"  "실시간으로 반영"  ← 결정적인 신호다
  "구간 [l, r] 의 합"  "부분합"  "누적 점수"  "빈도 누적"
  "연산이 순서대로 주어진다"  "각 질의에 대해 답하라"            ← 질의가 많다는 뜻이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N×Q 가 못 들어간다
  갱신과 질의의 비율이 지문에 안 적혀 있다                       ← 둘 다 빨라야 한다는 뜻이다

반대로 이런 말이 보이면 해당하지 않는다
  "배열은 변경되지 않는다"  "정적"                               ← 앞부분의 합 한 벌이면 끝난다
  "구간의 최솟값"  "구간의 최댓값"                               ← 뺄셈으로 앞부분을 못 덜어 낸다
  "구간에 값을 더한다"  "구간 갱신"                              ← 차분 배열을 한 겹 더 씌운다
```

두 번째 무리가 보이면 다른 절차로 갑니다. 배열이 안 바뀌면
[`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-problem.md) 쪽이고, 최솟값을
묻거나 구간 갱신이 붙으면
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-problem.md) ·
[`diffArrayRangeUpdate`](../diffArrayRangeUpdate/diffArrayRangeUpdate-problem.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **AtCoder Library 의 `atcoder::fenwick_tree`** — 이 절차를 그대로 담은 공개
  라이브러리입니다. 공개 연산이 `void add(int p, T x)` 와 `T sum(int l, int r)` 둘인데,
  **`add` 가 누적이라 덮어쓰기를 부르는 쪽이 변화량으로 바꿔서 넣어야 해요** — 「짚고 가기」에서 본
  그 자리가 인터페이스에 그대로 있습니다. `sum` 의 본문이 `return sum(r) - sum(l);` 이라
  구간이 반개구간 `[l, r)` 이고, 내부 이동은 `p += p & -p` 와 `r -= r & -r` 입니다.
  ([`atcoder/fenwicktree.hpp`](https://github.com/atcoder/ac-library/blob/master/atcoder/fenwicktree.hpp),
  조회 2026-09-03)
- **KACTL 의 `FenwickTree.h`** — 머리 주석이 *"Computes partial sums and updates single
  elements"* 로 이 문제를 그대로 적고 있습니다. 칸 번호를 0 부터 세는 판이라 이동이
  `pos |= pos + 1` 과 `pos &= pos - 1` 인데, 뒤엣것이 **가장 낮은 1 비트를 지우는 연산**이라
  이 글의 이동과 같은 것을 다른 표기로 적은 것이에요.
  ([`content/data-structures/FenwickTree.h`](https://github.com/kth-competitive-programming/kactl/blob/main/content/data-structures/FenwickTree.h),
  조회 2026-09-03)
- **Rust 의 `segment-tree` 크레이트 `PrefixPoint`** — 문서가 *"This data structure is
  implemented using a Fenwick tree"* 라 밝히고, 타입이 `PrefixPoint<N, O> where O: Commutative<N>`
  입니다. **교환 법칙을 타입으로 요구하는 것**이 같은 크레이트의 구간 트리와 갈리는 자리예요.
  ([`segment_tree::PrefixPoint`](https://docs.rs/segment-tree/latest/segment_tree/struct.PrefixPoint.html),
  조회 2026-09-03)

```text
셋이 바깥에 내놓는 이름을 나란히 두면

  더하는 연산     add(p, x) · update(pos, dif)      이 글의 add 다
  앞부분의 합     sum(r) · query(pos)               이 글의 prefix 다
  요구하는 조건   Commutative 트레이트              더하는 순서를 안 따진다
                  └ 앞의 둘은 구간 합을 저장하지 않고 앞부분의 합 둘의 차로 만들고,
                    Rust 판은 앞부분의 합 자체만 내놓는다
```

#### 경쟁 설계와의 대조

같은 목표(갱신이 섞인 구간 합에 답하기)를 노리는 다른 절차로 **제곱근 분할**이 있습니다.
배열을 `B` 칸씩 끊어 묶음마다 합 하나를 저장하고, 갱신은 그 칸과 묶음 합 하나만 고쳐요.
「아이디어 상세」가 길이를 하나로 고정하는 한계를 보인 그 방법이고, 여기서는 **그 한계가
장점이 되는 조건**을 값으로 찾습니다.

```text
같은 질문에 두 설계가 답하는 방식

  최하위 비트 트리   담당 길이가 1·2·4·8 로 섞여 있다      질의도 갱신도 자릿수만큼
  제곱근 분할        담당 길이가 B 로 하나다               갱신은 접근 넷, 질의는 √N 언저리
                     └ 갱신이 아주 많으면 「접근 넷」이 자릿수보다 적다
```

같은 입력·같은 작업 목록에 두 설계를 적용해 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은
`N = 1,024` 이고 `A[i] = (41i) mod 97`, 질의 `t` 번째는 `a = (23t) mod N` 과 `b = (67t) mod N`
을 만들어 작은 쪽을 왼쪽 끝으로 뒀어요. 갱신 `k` 번째는 `A[(59k) mod N]` 를
`((31k) mod 1000) − 500` 으로 덮어쓰고, 갱신은 질의 사이에 고르게 끼웠습니다. 묶음 길이는
`B = 32` 입니다. 전개가 쓰는 다섯 칸짜리 입력에서는 묶음 길이가 2 나 3 이고 묶음이 두세
개뿐이라 두 설계의 계수가 열 몇 번짜리 상수에 묻히므로, 「아이디어 상세」 ④⑥ 과 **같은 생성식**의 1,024 칸 입력을 쓰고 질의 수와 갱신 수만
바꿉니다.

**갱신을 0 회로 묶어 두면 질의 수 하나가 순서를 정합니다.**

| 갱신 0 회 | 최하위 비트 트리 | 제곱근 분할 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 질의 136 개 | 6,465 | **6,458** | 제곱근 분할이 7 번 적습니다 |
| 질의 137 개 | **6,474** | 6,517 | **여기서 순서가 뒤집힙니다** |
| 질의 4,096 개 | **46,049** | 165,628 | 이쪽이 3.6 배 적습니다 |

**갱신이 아주 많아지면 순서가 다시 반대로 갑니다.**

| 질의 1,024 개 | 최하위 비트 트리 | 제곱근 분할 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 갱신 0 회 | **15,350** | 42,199 | 이쪽이 2.7 배 적습니다 |
| 갱신 2,684 회 | **52,928** | 52,935 | 7 번 차이로 아직 이쪽입니다 |
| 갱신 2,685 회 | 52,944 | **52,939** | **여기서 순서가 뒤집힙니다** |
| 갱신 16,384 회 | 244,726 | **107,735** | 제곱근 분할이 2.3 배 적습니다 |

추가로 잡는 칸은 최하위 비트 트리가 **1,025** 이고 제곱근 분할이 **32** 입니다. 이 축은 어느
비율에서도 안 갈려요 — 묶음 합은 `N / B` 개뿐인데 이쪽은 칸마다 하나씩 두기 때문입니다.

```text
경계가 그 자리인 이유

  미리 만들기   최하위 비트 트리 5,117 번      제곱근 분할 1,056 번
                차이 4,061 을 질의 쪽 이득으로 갚아야 순서가 뒤집힌다
  질의 하나     최하위 비트 트리 평균 9.9      제곱근 분할 평균 39.7
                (6,465 − 5,117) ÷ 136 = 9.9 · (6,458 − 1,056) ÷ 136 = 39.7
                4,061 을 질의당 차이 29.8 로 나누면 136.2 이고, 실측은 137 이다
  갱신 하나     최하위 비트 트리 14.0          제곱근 분할 4.0
                (244,726 − 15,350) ÷ 16,384 = 14.0 · (107,735 − 42,199) ÷ 16,384 = 4.0
                질의 1,024 개에서 벌어진 차이 42,199 − 15,350 = 26,849 를 갱신당 차이 10.0 으로
                나누면 2,684.9 이고, 실측은 2,685 이다
```

**이 절차가 내주는 것은 갱신 하나의 비용과 추가 칸입니다.** 제곱근 분할은 갱신을 접근 넷으로
끝내고 칸도 32 개만 쓰는데 이쪽은 갱신마다 자릿수만큼 고치고 칸을 1,025 개 씁니다. 그 대신
얻는 것이 질의 하나의 비용이에요 — 이 문제는 질의와 갱신의 비율을 지문이 말하지 않으므로 둘
다 자릿수로 눌러 두는 쪽이 답이고, **갱신이 질의의 2.6 배(2,685 ÷ 1,024)를 넘는다고 지문이
못 박는 순간** 이 판정은 다시 해야 합니다.

### 수식 정의와 유도

칸이 담당하는 구간과 그 칸에 저장하는 값을 정의합니다. 담당 구간은 오른쪽 끝이 칸 번호이고
길이가 칸 번호의 가장 낮은 1 비트예요.

$$\text{LSB}(k) = k \mathbin{\&} (-k), \qquad \mathrm{cover}(k) = [\,k - \text{LSB}(k) + 1,\ k\,]$$

```text
정의를 읽는 법 (1)
  칸 번호 k 는 1 부터 센다        배열 인덱스는 0 부터 세므로 t 번째 값이 A[t−1] 이다
  cover(k) 는 1 부터 센 구간      길이가 LSB(k) 이고 오른쪽 끝이 k 다
```

$$\mathrm{tree}[k] = \sum_{t \in \mathrm{cover}(k)} A[t-1], \qquad \mathrm{pre}(r) = \sum_{t=1}^{r} A[t-1]$$

```text
정의를 읽는 법 (2)
  tree[k] 는 담당 구간 안의 값을 전부 더한 수다
  pre(r) 은 앞 r 개의 합이다      r = 0 이면 빈 합이라 0 이다
```

정의를 전개 입력의 다섯 칸에 그대로 넣어 봅시다.

<!--proof:cell-check-->

```text
A 의 값   [1 2 3 4 5]
인덱스     0 1 2 3 4

칸 k  k 의 이진 표기  담당 구간(1 부터)  그 구간의 값  tree[k]
   1  001             [1,1]              [1]           1
   2  010             [1,2]              [1 2]         3
   3  011             [3,3]              [3]           3
   4  100             [1,4]              [1 2 3 4]     10
   5  101             [5,5]              [5]           5

└ 담당 구간은 오른쪽 끝이 k 이고 길이가 k 의 최하위 비트다
```

식의 $\text{LSB}$ 를 코드에서는 `lowbit` 이라는 이름으로 씁니다. 정의를 그대로 옮기면 이렇게
됩니다.

```ts
// 정의의 담당 구간을 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const cover = (k: number): [number, number] => {
  const low = k & -k;
  return [k - low + 1, k];
};
```

이제 앞부분의 합이 칸 몇 개로 갈리는지 유도합니다. $r > 0$ 이면 $\text{LSB}(r) > 0$ 이므로
$r' = r - \text{LSB}(r)$ 는 $r$ 보다 작고, 담당 구간의 정의에서 $\mathrm{cover}(r)$ 은
$[r'+1,\ r]$ 입니다. 그러니 앞 $r$ 개는 앞 $r'$ 개와 그 구간으로 정확히 갈려요.

$$\mathrm{pre}(r) = \mathrm{tree}[r] + \mathrm{pre}\bigl(r - \text{LSB}(r)\bigr), \qquad \mathrm{pre}(0) = 0$$

```text
같은 식을 r = 7 에 펴면
  pre(7) = tree[7] + pre(6)      cover(7) = [7,7]
  pre(6) = tree[6] + pre(4)      cover(6) = [5,6]
  pre(4) = tree[4] + pre(0)      cover(4) = [1,4]
  pre(0) = 0
         └ 부른 횟수가 셋이고, 7 = 111₂ 의 1 이 셋이다
```

$r$ 에서 $\text{LSB}(r)$ 을 빼는 것은 **이진 표기에서 가장 낮은 1 을 하나 지우는 것**입니다.
그러니 이 식을 펴는 횟수는 $r$ 의 1 비트 개수이고, 그 값은 $\lfloor \log_2 r \rfloor + 1$ 을
넘지 못해요. 실제로 세어 대조합니다.

<!--proof:term-count-->

```text
 r  r 의 이진 표기  prefix(r) 가 더하는 칸  칸 수  1 비트 개수
 1  1               1                           1            1
 2  10              2                           1            1
 3  11              3 2                         2            2
 4  100             4                           1            1
 5  101             5 4                         2            2
 6  110             6 4                         2            2
 7  111             7 6 4                       3            3
 8  1000            8                           1            1
15  1111            15 14 12 8                  4            4
16  10000           16                          1            1

└ 두 열이 모든 줄에서 같다. r 이 1 부터 100,000 까지일 때 칸 수의 최댓값은 16 이다
```

갱신 쪽도 같은 정의에서 나옵니다. 칸 $k$ 가 인덱스 $i$ 를 품는 조건은
$k - \text{LSB}(k) < i+1 \le k$ 이고, $i+1$ 에서 $\text{LSB}$ 를 더해 가는 이동이 그 조건을
만족하는 $k$ 를 작은 것부터 빠짐없이 지납니다. 한 걸음마다 1 비트의 자리가 하나 올라가므로
걸음 수가 $\lfloor \log_2 N \rfloor + 1$ 이하예요.

```text
인덱스 2 를 품는 칸을 조건으로 골라 보면 (칸 번호로는 i+1 = 3 이다)
  칸 3   cover(3) = [3,3]   3 − 1 = 2 < 3 ≤ 3       품는다
  칸 4   cover(4) = [1,4]   4 − 4 = 0 < 3 ≤ 4       품는다
  칸 5   cover(5) = [5,5]   5 − 1 = 4 < 3 이 거짓   안 품는다
         └ 3 → 4 로 가는 이동이 이 조건을 만족하는 칸만 지난다
```

**같은 정의에서 채우는 비용의 닫힌 형태도 나옵니다.** 칸마다 따로 올라가며 채우면 칸 $j$ 는
자기를 품는 칸의 개수만큼 쓰이는데, 그 개수가 정확히 $\text{LSB}(j)$ 입니다. 다 더하면
이렇게 닫혀요.

$$\sum_{j=1}^{N} \text{LSB}(j) = \frac{N}{2}\bigl(\log_2 N + 2\bigr) \quad (N \text{ 이 2 의 거듭제곱일 때})$$

```text
N = 8 로 손으로 세면
  LSB(1) … LSB(8) = 1 2 1 4 1 2 1 8      다 더하면 20
  (8/2)(3 + 2)    = 4 × 5                = 20, 식과 같다
```

<!--proof:build-cost-->

```text
     N  log₂ N  칸마다 올라가면  (N/2)(log₂N + 2)  한 번씩 넘기면  배수
     8       3               20                20               7   2.9
    16       4               48                48              15   3.2
 1,024      10            6,144             6,144           1,023   6.0
65,536      16          589,824           589,824          65,535   9.0

└ 셋째 열과 넷째 열이 모든 줄에서 같다. N 이 2 의 거듭제곱이면 넘기는 쪽이 N − 1 회다
```

**본문의 값만으로는 안 나오는 것이 여기 있습니다.** 파트 1 은 다섯 칸에서 넘기는 횟수 셋을
보였을 뿐인데, 이 식은 임의의 `N` 에서 두 방식의 차이가 $\log_2 N$ 에 비례한다고 말해요.
`N = 65,536` 이면 589,824 대 65,535 로 9.0 배이고, 그래서 두 바퀴짜리 채우기를 씁니다.

### 불변식 — 모든 칸은 언제나 자기가 담당하는 구간의 합을 저장한다

파트 1 에서 코드가 동작하는 것을 열세 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 연산 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> 채우기가 끝난 시점과 `add` 하나가 끝난 시점마다, 모든 칸 `k` 에 대해 `tree[k]` 는 그 칸이
> 담당하는 구간 `cover(k)` 안의 값을 전부 더한 수입니다. `prefix` 는 `tree` 를 읽기만 하므로
> 이 성질을 바꾸지 않습니다.

```text
   칸 1 [1,1]   ●
   칸 2 [1,2]   ●
   칸 3 [3,3]   ●
   칸 4 [1,4]   ●
   칸 5 [5,5]   ●
                └ ● 는 「담당 구간의 합이 들어 있다」는 뜻이다
                  연산이 끝난 시점에는 다섯 칸이 전부 ● 다
```

「끝난 시점」을 빠뜨리면 이 문장이 거짓이 됩니다. `add` 가 **진행 중인** 동안은 앞쪽 칸만
고쳐지고 뒤쪽 칸은 옛 값이라, 그 순간에는 뒤쪽 칸이 성질을 만족하지 않아요. T9 가 바로 그
시점입니다.

```text
T9 를 마친 순간의 두 칸

  칸 3   담당 [3,3]   저장값 10   그 구간의 실제 합 10   맞는다
  칸 4   담당 [1,4]   저장값 10   그 구간의 실제 합 17   어긋난다
                      └ T10 이 7 을 더해 17 이 되어야 다시 맞는다
```

**출발점부터 봅시다.** 채우기의 두 바퀴가 각각 무엇을 보장하는지 갈래마다 확인합니다.

| 갈래 | 하는 일 | 성질이 유지되는 근거 |
| --- | --- | --- |
| 첫 바퀴 | `tree[i] = arr[i-1]` | 담당 길이가 1 인 칸은 이것으로 끝나고, 나머지는 두 번째 바퀴가 마저 채운다 |
| 두 번째 바퀴 | `tree[j] += tree[i]` | `i + 담당 길이 = j` 인 칸들의 담당 구간과 `j` 자신의 한 칸을 합치면 `cover(j)` 가 빈틈없이 채워진다 |
| 두 번째 바퀴의 순서 | 작은 번호부터 | 넘기는 값이 그 칸의 최종값이다 |
| `add` 가 지나는 칸 | `tree[k] += delta` | 그 칸의 담당 구간이 바뀐 자리를 품는다 |
| `add` 가 안 지나는 칸 | 아무것도 안 한다 | 담당 구간에 바뀐 자리가 없으니 합이 바뀔 수 없다 |
| `prefix` | `tree` 를 읽기만 한다 | 상태를 바꾸는 코드가 없다 |

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| `ops` 가 빔 | 채우기만 하고 연산 루프에 들어가지 않는다 | `[]` |
| `update` 만 있음 | 칸은 바뀌지만 결과 목록에 아무것도 안 넣는다 | `[]` |
| `N = 1` | 칸이 하나뿐이고 담당 구간이 `[1,1]` 이다 | `A[0]` 또는 `v` |
| `l = r` | 앞 `r+1` 개에서 앞 `r` 개를 뺀다 | `A[r]` |
| `l = 0` | 빼는 쪽 호출이 앞 0 개라 루프가 실행되지 않는다 | 앞 `r+1` 개의 합 |
| 음수 값 `−5` | 변화량이 음수여도 더하기 하나로 처리된다 | `0`(`[−5 2 3]` 의 합) |
| 같은 자리를 두 번 갱신 | 두 번째 변화량이 **첫 번째 갱신 뒤의 값**에서 나온다 | `10` |

마지막 줄이 이 문제에서 가장 미끄러운 자리입니다. 논리 배열을 함께 고치지 않으면 옛 값이
처음 값에 머물러 두 번째 변화량이 커지고, 그때 칸에 쌓인 값은 어느 담당 구간의 합도 아니게
돼요.

**이제 깨뜨려 봅시다.** 성질을 지키던 줄은 `add` 의 걸음 한 줄입니다. 「칸을 하나씩 올라가도
어차피 위쪽 칸을 다 지나지 않나」라는 생각으로 그 걸음을 1 로 바꿔 봅니다.

```ts
for (let k = i; k <= N; k += 1) {
  tree[k] = (tree[k] ?? 0) + delta;
}
```

<!--proof:mutant-step-one-->

```text
질의         바른 코드  걸음을 1 로 바꾼 코드  차이
query [0,4]         15                     15     0
query [0,4]         22                     29     7
query [2,3]         14                     14     0

└ 갱신이 칸 5 까지 건드린다. 칸 5 를 읽는 질의만 7 만큼 커지고 나머지는 그대로다
```

칸 5 를 읽는 질의만 7 만큼 커집니다. 칸 5 의 담당 구간은 `[5,5]` 이고 바뀐 자리는 인덱스 2 —
칸 5 는 그 자리를 품지 않는데도 변화량을 받았어요. 담당 길이를 더해 가는 이동이 **품는 칸만**
지나는 이동이라는 것이 이 한 줄로 확인됩니다.

```text
바른 이동    칸 3 [3,3] → 칸 4 [1,4] → 끝          품는 칸이 정확히 둘이다
걸음 1 이동  칸 3 [3,3] → 칸 4 [1,4] → 칸 5 [5,5]  마지막 칸이 인덱스 2 를 안 품는다
             └ 담당 구간이 성질을 정하고, 걸음이 그 구간을 고른다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 셋뿐입니다 — 칸을 채우는 것, 질의에 답하는 것, 갱신을 반영하는 것.
전개의 값으로 확인하면 T1\~T4 가 칸을 채우고, T5\~T7·T11·T12\~T13 이 질의 셋을 답하고,
T8\~T10 이 갱신 하나를 반영했습니다.

<!--proof:walk-cost-->

```text
갈래         걸음                   배열 접근
칸을 채운다  T1~T4                         19
질의 셋      T5~T7 · T11 · T12~T13          6
갱신 하나    T8~T10                         6
합                                         31

└ 같은 연산 목록을 직접 더하기로 처리하면 13 번이다.
  다섯 칸에서는 칸을 채우는 19 번이 전체의 절반을 넘어 아직 손해다
```

세는 것은 **배열 접근 전부**입니다 — `tree` 의 읽기와 쓰기, 그리고 논리 배열의 읽기와 쓰기.
추가로 잡는 메모리는 `tree` 의 `N + 1` 칸과 논리 배열의 `N` 칸이에요.

```text
갱신 하나     논리 배열 2 + 지나는 칸마다 2
              └ 셋 다 배열 길이가 아니라 자릿수를 따라간다
```

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (왼쪽 끝이 0 이고 오른쪽 끝 다음이 2 의 거듭제곱) | `O(N + Q)` | `Θ(N + Q)` — 질의당 칸 1 개 |
| **평균적인 경우** (질의 구간의 분포가 필요하다) | `O(N + Q log N)` | 정의되지 않습니다 |
| **최악의 경우** (두 끝의 1 비트가 둘 다 많다) | `O(N + Q log N)` | `Θ(N + Q log N)` — 실제로 도달합니다 |

가운데 줄이 정의되지 않는 이유를 적어 둡니다. 이 문제는 질의 구간과 갱신 자리가 **어떤
분포로 오는지 말하지 않아요.** 분포를 하나 정하면(두 끝을 균등하게 뽑으면) 1 비트의 개수가
평균 `log₂N / 2` 라 평균도 `Θ(log N)` 이 되지만, 그것은 문제가 준 조건이 아니라 이 글이 놓은
가정입니다.

```text
두 끝의 1 비트가 몇 개인가로 같은 배열에서 열아홉 배가 갈린다
  질의 [0,511]      r+1 = 512 = 1000000000₂    읽은 칸 1 개
  질의 [511,1022]   l = 511 · r+1 = 1023       읽은 칸 19 개
                    └ 같은 배열, 같은 개수의 질의인데 19 배다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 칸 채우기 하나뿐이라 총식에 더할
항이 없어요. 질의를 미리 모으는 단계도, 값을 다시 매기는 단계도 두지 않습니다.

```text
총식 = Θ(N + Q log N) 시간 + Θ(N) 추가 메모리
       └ 채우기 Θ(N) + 연산 Q 개 × Θ(log N)     └ tree N+1 칸 + 논리 배열 N 칸
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에
대한 가정도 하지 않으니, 어떤 배열과 어떤 연산 목록을 넣어도 위 상한 아래라는 것이 그대로
약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
                └ 다만 질의 하나의 상한 2(⌊log₂N⌋+1) 은 타이트하지 않다. N=1,024 에서 22 대 실측 19,
                  N=100,000 에서 34 대 실측 32 다
```

#### 최악을 만드는 입력

「긴 구간을 묻는 질의가 느리다」가 이 절차에서는 거짓입니다. 배열 전체를 묻는 질의는 오히려
칸 하나로 끝나요. 그것을 값으로 확인해 봅시다.

<!--proof:worst-shape-->

```text
질의의 모양          구간        구간의 칸 수  l 의 1 비트  r+1 의 1 비트  읽은 칸
배열 전체            [0,1023]           1,024            0              1        1
왼쪽 절반            [0,511]              512            0              1        1
한 칸                [500,500]              1            6              7       13
읽은 칸이 최대인 짝  [511,1022]           512            9             10       19

└ 가장 긴 구간이 가장 적다. 칸 수와 읽은 칸이 같은 방향으로 가지 않는다
```

`N = 1,024` 에서 가장 많은 칸을 읽는 질의는 `[511,1022]` 입니다 — 왼쪽 끝이
`511 = 111111111₂` 이고 오른쪽 끝에 1 을 더한 값이 `1023 = 1111111111₂` 라, 양쪽 다 1 비트가
가득 찬 수예요. 한 칸짜리 질의 `[500,500]` 이 배열 전체보다 13 배 많이 읽는 것이 같은 이유
입니다.

```text
왜 「2 의 거듭제곱보다 1 작은 수」가 최악인가

  512 = 1000000000₂    1 비트 하나      칸 하나로 끝난다
  511 =  111111111₂    1 비트 아홉      칸 아홉 개를 이어 붙인다
                       └ 이진 표기의 1 이 곧 조각이므로 1 이 많을수록 조각이 많다
```

그러니 최악은 **규모와 두 끝의 이진 표기가 함께** 만듭니다. `N` 과 `Q` 를 제약의 최댓값으로
두고 질의를 전부 `[65535, 98302]` 로 채우면 질의 하나가 칸 32 개를 읽고, 갱신을 전부
`i = 0` 으로 채우면 갱신 하나가 칸 17 개를 고쳐요.

```text
N = 100,000 · Q = 100,000 · 갱신을 전부 i = 0 으로
  갱신 하나가 접근 36 번, 채우기가 499,982 번, 다 더해 4,099,982 번
  1 초 제한에 견주면 여유가 크다
       └ 접근 밖에 남는 비용은 루프 제어이고, 걸음 수가 접근 수를 넘지 않아 같은 규모다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 칸 번호의 가장 낮은 1 비트를 담당 길이로
삼아 합을 나눠 저장했고, 앞부분의 합은 1 비트를 지워 가며 모으며, 갱신은 1 비트의 자리를
올려 가며 품는 칸만 고칩니다.

```text
  1. 칸 배열을 N+1 칸으로 잡는다               칸 0 은 비워 둔다
  2. 자기 몫을 넣고 위 칸에 한 번씩 넘긴다     채우기가 2N + 3H 번
  3. 질의는 1 비트를 지워 가며 모은다          N = 100,000 에서 읽은 칸 32 개 이하
  4. 갱신은 1 비트의 자리를 올려 가며 고친다   N = 100,000 에서 고친 칸 17 개 이하
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 부터 T7 까지는 질의 `[0,4]` 를 칸 **둘**만 읽고
답했는데, T12 부터 T13 까지는 더 짧은 질의 `[2,3]` 을 역시 칸 **둘**로 답했어요. 그런데 「아이디어
상세」의 표는 앞 4 개의 합이 칸 하나라고 했습니다. `[2,3]` 은 왜 둘일까요?

```text
T7    질의 [0,4]   앞 5 개 − 앞 0 개    칸 5 · 칸 4 · 없음      읽은 칸 2 개
T13   질의 [2,3]   앞 4 개 − 앞 2 개    칸 4 · 칸 2             읽은 칸 2 개
                   └ 한쪽은 오른쪽에서 둘, 다른 쪽은 양쪽에서 하나씩이다
```

<!--check:whyTwoCellsEither-->
읽는 칸의 개수를 정하는 것이 **구간의 길이가 아니라 두 끝의 1 비트 개수**이기 때문입니다.
`[0,4]` 는 오른쪽이 앞 5 개(`5 = 101₂`, 1 비트 둘)라 칸 둘을 읽고 왼쪽이 앞 0 개라 아무것도
안 읽어요. `[2,3]` 은 오른쪽이 앞 4 개(`4 = 100₂`, 1 비트 하나)라 칸 하나, 왼쪽이 앞 2 개
(`2 = 10₂`, 1 비트 하나)라 칸 하나여서 합쳐 둘입니다.

```text
질의        오른쪽 호출   1 비트   왼쪽 호출   1 비트   읽은 칸
[0,4]       앞 5 개            2   앞 0 개          0        2
[2,3]       앞 4 개            1   앞 2 개          1        2
[0,2]       앞 3 개            2   앞 0 개          0        2
[1,3]       앞 4 개            1   앞 1 개          1        2
            └ 왼쪽 끝이 0 이면 빼는 쪽 루프가 한 번도 실행되지 않는다
```

같은 이유로 「최악을 만드는 입력」의 `[511,1022]` 가 칸 열아홉 개를 읽습니다. 두 끝이 모두
1 비트가 가득 찬 수라 양쪽 호출이 각각 아홉·열 개를 읽기 때문이에요.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「최적인 문제의 모양」의 세 번째 조건    3 → 「문제에서 이것을 떠올리게 하는 단서」
```
