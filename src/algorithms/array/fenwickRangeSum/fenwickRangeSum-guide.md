# 펜윅 트리 — 칸마다 최하위 1 비트만큼의 구간을 맡기면 갱신과 질의가 둘 다 자릿수만큼만 걸리는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 질의마다 구간을
직접 더하는 방법에서 출발해, 칸마다 최하위 1 비트만큼의 구간을 맡기는 방법까지 갑니다. 그 방법을 단계마다
값으로 풀고, 마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

이 글이 다루는 것은 **원소가 중간중간 바뀌는 배열**에서 구간의 합을 답하는 일입니다. 배열이 안 바뀐다면
앞에서부터 쌓은 합 두 칸의 차이로 답할 수 있어요. 그런데 그 합은 칸 하나가 배열의 앞부분 전체를 맡고
있어서, 원소 하나가 바뀌면 그 뒤의 칸을 전부 고쳐야 합니다. 그래서 여기서는 칸마다 **맡는 구간의 길이를
다르게** 둡니다.

길이를 정하는 규칙은 칸 번호의 **최하위 1 비트**입니다. 칸 번호를 이진수로 적었을 때 1 인 자리 가운데 가장
낮은 자리의 값이에요. 6 은 `110₂` 라 최하위 1 비트가 2 이고, 4 는 `100₂` 라 4 입니다. 칸을 1 부터 세고, 칸
`k` 는 **인덱스 `k − 1` 에서 끝나고 길이가 `k` 의 최하위 1 비트인 구간**의 합을 적어 둬요. 이렇게 적어 둔
배열을 **펜윅 트리**(Fenwick tree)라고 부릅니다. 배열 `[1 2 3 4 5]` 의 펜윅 트리를 칸마다 한 줄로 그리면
이렇습니다. 줄마다 그 칸이 맡는 자리에만 배열 값을 남겼어요.

<!--fig:concept-cells-->
![펜윅 트리 — 칸마다 맡는 자리](./figs/concept-cells.svg)

칸 1 · 칸 3 · 칸 5 는 한 칸씩, 칸 2 는 두 칸, 칸 4 는 네 칸을 맡습니다. 길이가 짧은 칸은 많고 긴 칸은
적어요. 앞 `r` 개의 합은 이 칸 몇 개를 이어 붙여 만듭니다. 앞 5 개라면 칸 5 가 맡는 `[4,4]` 와 칸 4 가 맡는
`[0,3]` 이 빈틈없이 이어집니다.

<!--fig:concept-prefix-->
![앞 5 개의 합을 칸 둘로 덮기](./figs/concept-prefix.svg)

구간 `[l, r]` 의 합은 앞 `r + 1` 개의 합에서 앞 `l` 개의 합을 뺀 것이에요. 질의 셋에 적용하면 이렇습니다.

<!--proof:concept-queries-->

| 질의 | 계산 | 오른쪽 호출이 읽는 칸 | 왼쪽 호출이 읽는 칸 | 뺄셈 | 답 |
| --- | --- | --- | --- | ---: | ---: |
| [0,4] | 앞 5 개 − 앞 0 개 | 칸 5 · 칸 4 | 없음 | 15 − 0 | 15 |
| [2,3] | 앞 4 개 − 앞 2 개 | 칸 4 | 칸 2 | 10 − 3 | 7 |
| [1,3] | 앞 4 개 − 앞 1 개 | 칸 4 | 칸 1 | 10 − 1 | 9 |

어느 질의도 칸을 둘보다 많이 읽지 않았습니다. 갱신도 같은 규칙 안에 있어요. 원소 하나가 바뀌면 값이 달라지는
칸은 **그 원소를 맡는 구간에 품은 칸**뿐입니다. `A[2]` 를 3 에서 10 으로 고친 모습이에요. 굵은 강조 테가 값이
바뀐 칸입니다.

<!--fig:concept-update-->
![A[2] 를 10 으로 고친 뒤 — 값이 바뀐 칸](./figs/concept-update.svg)

같은 갱신에서 앞에서부터 쌓은 합의 배열(누적합 배열)과 고친 칸을 세면 이렇습니다.

<!--proof:concept-update-->

| 구조 | 칸 수 | 인덱스 2 를 덮는 칸 | 값이 바뀐 칸 |
| --- | ---: | ---: | ---: |
| 펜윅 트리 | 5 | 2 | 2 |
| 누적합 배열 | 6 | 3 | 3 |

A[2] 를 3 에서 10 으로 고쳤습니다. 펜윅 트리의 칸 0 은 비워 두는 칸이라 세지 않았습니다.

<!--/proof-->

펜윅 트리에서 칸이 맡는 길이는 1 · 2 · 4 · 8 처럼 두 배씩 늘어나므로, 앞부분의 합 하나가 읽는 칸과 갱신 하나가
고치는 칸은 배열 길이의 로그 규모입니다. 그래서 펜윅 트리를 채우는 데 `O(N)`, 질의 하나와 갱신 하나에 각각
`O(log N)` 이 들어요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 합**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값을 하나도 빼지 않고 더한 수입니다.
- **누적합으로 구간 합을 답하는 방법**. 앞에서부터 쌓은 합 두 개의 차이로 구간의 합을 만듭니다. 흐릿하면
  [`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 를 먼저 읽어 보세요. 이 글은
  그 방법에 **갱신이 섞여 들어올 때**를 다룹니다.
- **정수의 이진 표기**. 자연수는 서로 다른 2 의 거듭제곱의 합으로 한 가지 방법으로만 적힙니다.
- **최하위 1 비트와 `x & -x`**. `-x` 는 `x` 의 비트를 뒤집고 1 을 더한 값이라, `x & -x` 가 최하위 1 비트 하나만
  남깁니다. 까닭이 궁금하면 [`lowestSetBit`](../../bit-manipulation/lowestSetBit/lowestSetBit-guide.md) 이
  자리올림으로 풀어 줍니다.

「구간의 값을 묻는다」만으로는 어느 방법을 쓸지 정해지지 않습니다. **무엇을 묻는가**와 **배열이 바뀌는가**가
함께 갈라요. 배열 `[1 2 3 4 5]` 에 물음 셋을 대 보면 이 글의 범위가 보입니다.

<!--proof:prereq-scope-->

| 물음 | 답 | 펜윅 트리 | 누적합 배열 | 세그먼트 트리 |
| --- | ---: | --- | --- | --- |
| 구간 [0,4] 의 합 | 15 | 답한다 | 답한다 | 답한다 |
| A[2] 를 10 으로 고친 뒤 [0,4] 의 합 | 22 | 답한다 | 뒤쪽 칸을 전부 고쳐야 답한다 | 답한다 |
| 구간 [0,4] 의 최솟값 | 1 | 답하지 못한다 | 답하지 못한다 | 답한다 |

둘째 물음처럼 **갱신이 섞인 구간 합**이 이 글의 범위입니다. 셋째 물음처럼 최솟값을 묻는 쪽은
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 이 다뤄요. 최솟값에는 앞부분을 덜어
내는 뺄셈이 없어서, 앞부분의 합 둘의 차로 답하는 이 글의 방법을 쓸 수 없습니다.

### 아이디어를 떠올리는 과정 — 질의마다 직접 더하기에서 최하위 1 비트 길이로 나눠 담기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 배열과 연산 목록을 받아서 질의의
답 목록을 돌려줍니다.

```ts
type FenwickOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

function fenwickRangeSum(A: number[], ops: FenwickOp[]): number[];
```

- 입력: 정수 배열 `A` 와 연산 목록 `ops`. `update` 는 `A[i]` 를 `v` 로 덮어쓰고(더하는 것이 아닙니다),
  `query` 는 **양끝을 포함하는** 구간 `[l, r]` 의 합을 묻습니다. 연산은 목록 순서대로 처리하고, 갱신은 그 뒤의
  모든 질의에 반영돼요.
- 출력: `query` 의 답만 **입력 순서 그대로** 담은 배열입니다. 질의가 하나도 없으면 빈 배열이에요.
- 규모: `1 ≤ N ≤ 100,000`, `0 ≤ Q ≤ 100,000`, `−10,000 ≤ A[i], v ≤ 10,000`, `0 ≤ i < N`, `0 ≤ l ≤ r < N`.
  비용은 흔한 채점 환경의 예산인 시간 1 초, 메모리 256 MB 에 대어 잽니다.

이 글이 쓰는 기호를 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 배열 `A` 의 길이 | `N ≤ 100,000` |
| `Q` | 연산 목록 `ops` 의 길이 | `Q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값. 인덱스는 0 부터 셉니다 | `−10,000` 이상 `10,000` 이하 |
| `i` · `v` | `update` 가 바꿀 자리와 새 값 | `0 ≤ i < N` |
| `l` · `r` | `query` 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r < N` |
| `k` | 펜윅 트리의 칸 번호. **1 부터** 셉니다 | `1 ≤ k ≤ N` |
| `lowbit(k)` | 칸 번호 `k` 의 최하위 1 비트. 칸 `k` 가 맡는 구간의 길이입니다 | `k & -k` |
| `tree[k]` | 칸 `k` 가 맡는 구간 `[k − lowbit(k), k − 1]` 의 합 | 칸이 `N + 1` 개 |
| `arr` | 갱신을 반영해 가는 배열. 옛 값을 읽으려고 따로 듭니다 | 칸이 `N` 개 |
| `delta` | 갱신 하나가 만드는 변화량 | `v` 에서 옛 값을 뺀 수 |

이 글은 비용을 **배열 접근 수**, 곧 배열 칸을 읽거나 쓴 횟수로 셉니다. 출발점은 아무 기법도 쓰지 않는
방법이에요. 배열을 그대로 들고 있다가, 질의가 오면 구간을 왼쪽 끝부터 오른쪽 끝까지 더하고, 갱신은 칸 하나를
고칩니다.

```ts
for (const op of ops) {
  if (op.type === "update") {
    arr[op.i] = op.v; // 칸 하나를 쓴다
  } else {
    let s = 0;
    for (let k = op.l; k <= op.r; k++) s += arr[k] as number;
    result.push(s); // 구간을 직접 더한다
  }
}
```

이 방법은 갱신 하나에 1 번, 질의 하나에 구간의 칸 수만큼 접근합니다. 방법마다 같은 작업 목록으로 재려고 목록
하나를 정했어요. 갱신과 질의를 번갈아 두고, 질의는 전부 양 끝을 한 칸씩 안으로 당긴 `[1, N−2]` 입니다. 갱신
`k` 번째는 `A[(59k) mod N]` 를 `((31k) mod 1000) − 500` 으로 덮어쓰고, 배열은 `A[i] = (41i) mod 97` 이에요.

<!--proof:cost-scan-->

| N = Q | 배열 접근(실측) | (Q/2)(N−2) + Q/2 | 초당 1 억 번 기준 |
| ---: | ---: | ---: | ---: |
| 1,000 | 499,500 | 499,500 | 0.01 초 미만 |
| 10,000 | 49,995,000 | 49,995,000 | 0.50 초 |
| 100,000 | (실행하지 않음) | 4,999,950,000 | 50.00 초 |

실측이 식과 두 규모에서 같으니, 과제 규모에서는 식이 곧 접근 수입니다. 약 50 억 번이고, 단순한 연산을 1 초에
1 억 번 한다고 잡아도 50 초가 걸려요. 예산이 1 초이니 이 방법으로는 안 됩니다. 질의 하나가 구간 길이만큼 읽는
것이 원인이니, 반대로 **합을 미리 적어 두면** 어떨까요. 칸 `k` 에 앞 `k` 개의 합을 적어 두는 누적합 표라면
질의는 뺄셈 한 번이에요.

```ts
// P[k] 에 앞 k 개의 합을 담아 두면
result.push((P[op.r + 1] as number) - (P[op.l] as number)); // 질의는 칸 둘을 읽는다

// 그런데 A[i] 가 바뀌면
for (let k = op.i + 1; k <= N; k++) P[k] = (P[k] as number) + delta; // 뒤쪽 칸을 전부 고친다
```

같은 작업 목록으로 셌습니다.

<!--proof:cost-prefix-->

| N = Q | 미리 만들기 | 질의 | 갱신 | 합 | 초당 1 억 번 기준 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 3,000 | 1,000 | 510,500 | 514,500 | 0.01 초 미만 |
| 10,000 | 30,000 | 10,000 | 50,505,000 | 50,545,000 | 0.51 초 |
| 100,000 (식) | 300,000 | 100,000 | 5,042,850,000 | 5,043,250,000 | 50.43 초 |

미리 만들기는 칸마다 3 번, 질의는 2 번, 갱신 i 는 2 + 2(N − i) 번입니다. 100,000 줄은 이 식이 위 두 줄의 실행과 같은 것을 확인하고 식으로 셌습니다.

<!--/proof-->

질의는 전부 합쳐도 10 만 번으로 줄었는데, 갱신이 50 억 번으로 늘었습니다. **한쪽을 줄인 만큼 반대쪽이 커진**
것이지 총량이 준 것이 아니에요. 두 방법을 규모를 줄인 한 목록에 나란히 걸어 봅시다. 다섯 칸짜리 배열은 계수를
갈라 보기에 너무 작아서, 같은 생성식으로 만든 1,024 칸 배열에 질의 512 개와 갱신 512 개를 고르게 섞었어요.
질의 `t` 번째는 `a = (23t) mod N` 과 `b = (67t) mod N` 을 만들어 작은 쪽을 왼쪽 끝으로 둡니다.

<!--proof:mixed-load-->

| 방식 | 미리 만들기 | 질의 512 개 | 갱신 512 개 | 합 | 추가 칸 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 직접 더하기 | 0 | 173,944 | 512 | 174,456 | 0 |
| 누적합 표 | 3,072 | 1,024 | 530,944 | 535,040 | 1,025 |

두 방식의 답은 같습니다. 질의는 173,944 에서 1,024 로 줄고, 갱신은 512 에서 530,944 로 늘었습니다.

<!--/proof-->

여기서 관찰할 것은 **칸 하나가 맡는 구간의 길이가 두 비용을 함께 정한다**는 것 하나입니다. 직접 더하기는 칸마다
길이 1 만 맡아서 질의가 많이 읽고, 누적합 표는 칸마다 앞부분 전체를 맡아서 갱신이 많이 고쳐요. 그 사이의 길이를
시험해 봅시다. 가장 단순한 후보는 **길이를 하나로 고정**하는 것입니다. 배열을 `B` 칸씩 끊어 묶음마다 합 하나를
적어 두는 **고정 길이 묶음**이에요. 갱신은 그 칸과 묶음 합 하나만 고치면 끝나고, 질의는 통째로 드는 묶음의 합을
읽고 양 끝에 남는 칸만 배열에서 읽습니다. `B = 2` 로 끊은 `[1 2 3 4 5]` 에서 질의 `[1,3]` 을 답하면 이렇습니다.

<!--proof:block-small-->

| 읽은 자리 | 까닭 | 읽은 값 |
| --- | --- | --- |
| 인덱스 1 | 묶음 0 에 절반만 걸친다 | A[1] = 2 |
| 인덱스 2 · 3 | 묶음 1 [2,3] 이 질의 안에 통째로 든다 | 묶음 합 7 |

B = 2 로 끊은 묶음은 묶음 0 [0,1] = 3 · 묶음 1 [2,3] = 7 · 묶음 2 [4,4] = 5 입니다. 질의 [1,3] 의 답은 2 + 7 = 9 이고, 정본의 답도 9 입니다.

<!--/proof-->

갱신은 배열 길이와 상관없이 접근 넷으로 끝나요. 걸리는 것은 질의입니다. 질의 하나는 양 끝에 남는 칸을 `B − 1`
개씩, 그 사이의 묶음을 `N / B` 개 가까이 읽어서, `B` 를 키우면 남는 칸이 늘고 줄이면 묶음 수가 늡니다. 가장
좋은 `B` 를 골라도 질의 하나의 최악이 얼마인지 세었어요.

<!--proof:block-worst-->

| N | 가장 좋은 묶음 크기 B | 고정 길이 묶음 질의 하나의 최악 | 펜윅 트리 질의 하나의 최악 |
| ---: | ---: | ---: | ---: |
| 1,024 | 21 | 86 | 19 |
| 100,000 | 216 | 890 | 32 |

고정 길이 묶음의 최악은 양 끝에 남는 칸 B − 1 개씩과 그 사이의 온전한 묶음 수를 더한 값이고, N = 1,024 에서는 모든 (l, r) 짝을 실행해 잰 최댓값과 같습니다. 펜윅 트리 쪽은 모든 (l, r) 짝에서 잰 최댓값입니다.

<!--/proof-->

묶음 크기가 하나뿐이면 가장 좋은 크기를 골라도 질의 하나가 `√N` 규모를 읽습니다. 과제 규모에서 이 넷을 모두 같은
작업 목록으로 세면 이렇습니다. 묶음 크기를 `⌊√N⌋` 으로 둔 고정 길이 묶음을 **제곱근 분할**이라고 불러요. 마지막
줄은 아래에서 이름을 붙일 방법입니다.

<!--proof:origin-scale-->

| 방법 | 미리 만들기 | 질의 | 갱신 | 합 | 초당 1 억 번 기준 | 센 방법 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 직접 더하기 | 0 | 4,999,900,000 | 50,000 | 4,999,950,000 | 50.00 초 | 식 |
| 누적합 표 | 300,000 | 100,000 | 5,042,850,000 | 5,043,250,000 | 50.43 초 | 식 |
| 제곱근 분할 B=316 | 100,317 | 38,650,000 | 200,000 | 38,950,317 | 0.39 초 | 실행 |
| 펜윅 트리 | 499,982 | 550,000 | 979,008 | 2,028,990 | 0.02 초 | 실행 |

N = Q = 100,000 이고 갱신과 질의가 50,000 개씩입니다. 「식」 줄은 같은 식이 N = Q = 1,000 · 10,000 에서 실행한 값과 같은 것을 확인하고 식으로 셌습니다.

<!--/proof-->

제곱근 분할은 0.39 초로 예산 안에 들지만, 마지막 줄은 그보다 열 배 넘게 적은 2,028,990 번이에요. 지금까지
해 본 방법 넷을 차례로 놓으면 이렇습니다. 앞 방법이 막힌 자리에서 다음 방법이 나왔고, 셋은 버리고 하나가
남았어요.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **최하위 1 비트 길이로 나눠 담기**입니다. 칸마다 맡는 길이를 칸 번호의 최하위 1
비트로 정해서, 길이 1 · 2 · 4 · 8 … 인 구간을 섞어 적어 둬요. 칸이 어느 구간을 맡는지, 어떻게 채우는지,
질의가 어느 칸을 읽는지, 갱신이 어디까지 고치는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 최하위 1 비트 길이로 나눠 담기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **칸 `k` 에 인덱스 `k − 1` 에서 끝나고 길이가 `k` 의 최하위 1
비트인 구간의 합을 적어 두고, 질의는 칸 번호에서 최하위 1 비트를 지워 가며 칸을 이어 붙이고, 갱신은 칸 번호에
최하위 1 비트를 더해 가며 그 원소를 품은 칸만 고칩니다.** 이 방법이 쓰는 펜윅 트리는 처음 보는 사람에게
낯설어서, 먼저 따로 설명하고 그다음 실현하는 순서대로 다섯 단계를 설명합니다. 앞 단계에서 만든 것을 뒤 단계에서
쓰는 순서예요.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 연산 전에 한 번 | 1단계 칸 번호와 맡는 구간 정하기 | 칸 번호를 1 부터 매기고 칸마다 맡는 구간을 정한다 | — |
| 연산 전에 한 번 | 2단계 자기 몫을 넣고 위 칸에 한 번씩 넘겨 채우기 | 칸마다 맡는 구간의 합을 적는다 | 1단계의 맡는 구간 |
| 질의마다 | 3단계 최하위 1 비트를 지워 가며 앞부분 합 모으기 | 앞 `r` 개의 합을 칸 몇 개로 이어 붙인다 | 1단계의 맡는 구간 · 2단계의 값 |
| 질의마다 | 4단계 앞부분 합 둘의 차로 구간 합 답하기 | 앞 `r + 1` 개에서 앞 `l` 개를 뺀다 | 3단계의 앞부분 합 |
| 갱신마다 | 5단계 덮어쓰기를 변화량으로 바꿔 품는 칸만 고치기 | 원소를 품은 칸에 변화량을 더한다 | 1단계의 맡는 구간 · 2단계의 값 |

#### 먼저 알아 둘 개념 — 펜윅 트리

펜윅 트리는 **칸 번호를 1 부터 매기고, 칸 `k` 에 인덱스 `k − 1` 에서 끝나며 길이가 `k` 의 최하위 1 비트인
구간의 합을 적어 둔 배열**입니다. 식으로 적으면 칸 `k` 가 맡는 구간은 `[k − lowbit(k), k − 1]` 이에요. 여기서
헷갈리기 쉬운 부분이 하나 있습니다. 이 글에서 「인덱스」와 「칸」은 다른 것을 가리켜요.

| 이름 | 세는 법 | 가리키는 것 | 이 글에서 쓰는 곳 |
| --- | --- | --- | --- |
| 인덱스 | 0 부터 | 배열 `A` 의 자리 하나 | `A[i]`, 구간 `[l, r]` |
| 칸 | 1 부터 | 펜윅 트리의 자리 하나. 구간 하나의 합을 든다 | `tree[k]`, 「칸 4」 |

##### 칸이 맡는 자리

칸이 많을 때의 모양을 보려고 길이 16 배열로 그렸습니다. 값은 인덱스에 1 을 더한 수예요. 칸 하나를 한 줄로,
그 칸이 맡는 자리에만 배열 값을 남겼고, 최하위 1 비트가 같은 칸끼리 한 묶음으로 모았습니다.

<!--fig:build-bars-->
![길이 16 배열의 펜윅 트리 — 최하위 1 비트가 같은 칸끼리 한 묶음](./figs/build-bars.svg)

위 묶음에서 아래 묶음으로 갈수록 칸이 맡는 길이가 두 배가 되고 칸의 수는 절반이 됩니다. 어느 칸이든 오른쪽
끝은 인덱스 `k − 1` 이라, 칸 번호를 보면 구간이 어디서 끝나는지 바로 알 수 있어요. 왼쪽 끝은 칸마다 다릅니다.
최하위 1 비트가 클수록 왼쪽으로 멀리 뻗어요.

##### 칸 하나를 읽는 법

칸 12 를 골라 번호에서 값까지 따라가 보겠습니다. 먼저 최하위 1 비트를 비트 그림으로 구합니다.

<!--fig:build-bits-->
![칸 12 의 최하위 1 비트](./figs/build-bits.svg)

`12 & -12` 에서 둘 다 1 인 자리는 자리 2 하나라 최하위 1 비트는 4 예요. 나머지를 차례로 적으면 이렇습니다.

<!--proof:node-read-->

| 읽는 것 | 계산 | 결과 |
| --- | --- | --- |
| 칸 번호 | — | 12 |
| 이진 표기 | — | 1100₂ |
| 최하위 1 비트 | 12 & −12 | 4 |
| 맡는 구간 | [12 − 4, 12 − 1] | [8,11] |
| 적힌 값 | 9 + 10 + 11 + 12 | 42 |

칸 12 는 인덱스 11 에서 끝나고 네 칸을 맡으니 `[8,11]` 이고, 적힌 값은 그 네 값의 합입니다. 조심할 점이 하나
있어요. 칸 번호는 구간의 **오른쪽 끝을 1 부터 센 번호**이지, 구간의 시작 자리가 아닙니다.

##### 칸끼리의 관계

같은 묶음 안의 칸, 곧 최하위 1 비트가 같은 칸끼리는 배열을 어떻게 나눠 갖는지 세어 보겠습니다.

<!--proof:cell-groups-->

| 최하위 1 비트 | 칸 | 칸 수 | 맡은 인덱스 수 | 두 번 맡은 인덱스 |
| ---: | --- | ---: | ---: | ---: |
| 1 | 칸 1 · 칸 3 · 칸 5 · 칸 7 · 칸 9 · 칸 11 · 칸 13 · 칸 15 | 8 | 8 | 0 |
| 2 | 칸 2 · 칸 6 · 칸 10 · 칸 14 | 4 | 8 | 0 |
| 4 | 칸 4 · 칸 12 | 2 | 8 | 0 |
| 8 | 칸 8 | 1 | 8 | 0 |
| 16 | 칸 16 | 1 | 16 | 0 |

마지막 열이 다섯 줄 모두 0 입니다. **최하위 1 비트가 같은 칸끼리는 한 인덱스를 두 번 맡지 않아요.** 묶음이 다른
칸끼리는 한쪽이 다른 쪽 안에 통째로 듭니다. 칸 `i` 에서 최하위 1 비트만큼 오른쪽으로 간 칸 `i + lowbit(i)` 를
칸 `i` 의 **위 칸**이라고 부르겠습니다. 위 칸이 같은 칸들을 모아 보면 이렇습니다.

<!--proof:cell-children-->

| 칸 j | 맡는 구간 | 위 칸이 칸 j 인 칸 | 그 칸들의 구간 + 자기 한 칸 |
| --- | --- | --- | --- |
| 칸 4 | [0,3] | 칸 2 · 칸 3 | [0,1] + [2,2] + [3,3] |
| 칸 8 | [0,7] | 칸 4 · 칸 6 · 칸 7 | [0,3] + [4,5] + [6,6] + [7,7] |
| 칸 12 | [8,11] | 칸 10 · 칸 11 | [8,9] + [10,10] + [11,11] |
| 칸 16 | [0,15] | 칸 8 · 칸 12 · 칸 14 · 칸 15 | [0,7] + [8,11] + [12,13] + [14,14] + [15,15] |

칸 16 개 가운데 16 개에서, 위 칸이 자기인 칸들의 구간과 자기 한 칸을 이어 붙이면 겹침도 빈칸도 없이 자기 구간이 됩니다. 칸 i 의 위 칸은 i + (i 의 최하위 1 비트) 입니다.

<!--/proof-->

칸 8 의 구간 `[0,7]` 은 칸 4 · 칸 6 · 칸 7 의 구간과 자기 한 칸 `[7,7]` 을 이어 붙인 것이에요. 그래서 칸의 값은
**위 칸이 자기인 칸들의 값과 자기 원소 하나를 더한 것**이고, 원소 하나를 품은 칸은 그 원소의 칸에서 위 칸으로,
다시 그 위 칸으로 이어집니다. 2단계와 5단계가 이 두 관계를 그대로 씁니다.

##### 헷갈리기 쉬운 두 모양과의 차이

「구간의 합을 적어 둔다」까지는 누적합 배열이나 고정 길이 묶음과 같아서 섞어 떠올리기 쉽습니다. 누적합 배열은
칸마다 **앞부분 전체**를, 고정 길이 묶음은 칸마다 **같은 길이**를 맡기고, 펜윅 트리는 칸마다 **최하위 1 비트
길이**를 맡겨요. 같은 배열 크기에서 세면 이렇습니다.

<!--proof:shape-compare-->

| 구조 | N | 적어 둔 칸 | 인덱스 하나를 덮는 칸(최대) | 앞부분 합 하나에 읽는 칸(최대) |
| --- | ---: | ---: | ---: | ---: |
| 누적합 배열 | 16 | 17 | 16 | 1 |
| 고정 길이 묶음 B=4 | 16 | 4 | 1 | 6 |
| 펜윅 트리 | 16 | 16 | 5 | 4 |
| 누적합 배열 | 1,024 | 1,025 | 1,024 | 1 |
| 고정 길이 묶음 B=32 | 1,024 | 32 | 1 | 62 |
| 펜윅 트리 | 1,024 | 1,024 | 11 | 10 |

최대는 모든 인덱스와 모든 r 을 넣어 잰 값입니다. 고정 길이 묶음의 앞부분 합은 묶음 합과 남는 칸을 함께 읽은 수이고, 펜윅 트리의 칸 수에는 비워 두는 칸 0 을 넣지 않았습니다.

<!--/proof-->

누적합 배열은 앞부분 합을 칸 하나로 읽는 대신 인덱스 하나를 1,024 칸이 덮고, 고정 길이 묶음은 인덱스 하나를
묶음 하나만 덮는 대신 앞부분 합 하나에 62 칸을 읽어요. 펜윅 트리는 두 값이 모두 11 이하입니다. 한쪽을 극단으로
몰지 않고 **둘 다 자릿수에 묶은** 모양이에요.

##### 이렇게 생긴 까닭

이 모양은 갱신과 질의를 **둘 다** 자릿수에 묶으려고 이렇게 생겼습니다. 두 요구가 모양의 서로 다른 성질에
기대요.

| 요구 | 기대는 성질 | 그래서 |
| --- | --- | --- |
| 앞부분 합이 적게 읽는다 | 칸 `k` 가 인덱스 `k − 1` 에서 끝나고 `lowbit(k)` 칸을 맡는다 | 칸 번호에서 최하위 1 비트를 빼면 바로 앞 조각의 칸이 나온다. 조각 수가 1 비트의 개수다 |
| 갱신이 적게 고친다 | 원소를 품은 칸이 위 칸으로 이어진다 | 칸 번호에 최하위 1 비트를 더하면 다음으로 품는 칸이 나온다. 칸 수가 자릿수 이하다 |
| 칸 번호만으로 계산한다 | 길이가 칸 번호의 비트에서 나온다 | 어느 칸이 어디를 맡는지 따로 적어 두지 않는다 |

길이를 하나로 고정하면 고정 길이 묶음이 되어 질의가 커지고, 모든 칸이 앞부분 전체를 맡으면 누적합 배열이 되어
갱신이 커집니다.

#### 1단계 — 칸 번호와 맡는 구간 정하기

펜윅 트리를 만들려면 먼저 칸 번호를 어떻게 매기고 칸마다 어느 구간을 맡길지 정해야 합니다. 규칙은 셋이에요.

| 칸 | 맡는 구간 | 뜻 |
| --- | --- | --- |
| `k = 0` | 없음 | 쓰지 않는 칸이다. 최하위 1 비트가 0 이라 맡을 길이가 없다 |
| `1 ≤ k ≤ N` | `[k − lowbit(k), k − 1]` | 인덱스 `k − 1` 에서 끝나고 `lowbit(k)` 칸을 맡는다 |
| 트리 배열 | 칸 `N + 1` 개 | 칸 0 을 비우고 칸 1 부터 칸 `N` 까지 쓴다 |

전개가 쓸 배열 `[1 2 3 4 5]` 에 적용한 결과입니다.

<!--proof:cell-check-->

| 칸 | 칸 번호의 이진 표기 | 최하위 1 비트 | 맡는 구간 | 구간의 값 |
| --- | --- | ---: | --- | --- |
| 칸 0 | 000₂ | 0 | 없음 | 비워 둔다 |
| 칸 1 | 001₂ | 1 | [0,0] | [1] |
| 칸 2 | 010₂ | 2 | [0,1] | [1 2] |
| 칸 3 | 011₂ | 1 | [2,2] | [3] |
| 칸 4 | 100₂ | 4 | [0,3] | [1 2 3 4] |
| 칸 5 | 101₂ | 1 | [4,4] | [5] |

칸 번호가 1 · 2 · 4 처럼 2 의 거듭제곱이면 구간이 인덱스 0 부터 시작해요. 칸 번호가 홀수면 최하위 1 비트가 1
이라 자기 한 칸만 맡습니다. 칸 수는 `N` 에만 달렸고 값에는 안 달렸어요.

#### 2단계 — 자기 몫을 넣고 위 칸에 한 번씩 넘겨 채우기

칸의 값은 위 칸이 자기인 칸들의 값과 자기 원소 하나를 더한 것이었습니다. 그래서 두 바퀴로 채웁니다. 첫 바퀴는
칸마다 자기 원소 `arr[k − 1]` 하나만 넣고, 둘째 바퀴는 칸 번호가 작은 칸부터 자기 값을 위 칸에 한 번 더해요.
위 칸이 `N` 을 넘으면 아무 데도 넘기지 않습니다.

<!--proof:build-order-->

| 차례 | 하는 일 | 칸 1 | 칸 2 | 칸 3 | 칸 4 | 칸 5 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 첫 바퀴 | 칸마다 arr[k − 1] 을 넣는다 | 1 | 2 | 3 | 4 | 5 |
| 둘째 바퀴 i = 1 | 칸 1 이 칸 2 에 1 을 넘긴다 | 1 | 3 | 3 | 4 | 5 |
| 둘째 바퀴 i = 2 | 칸 2 가 칸 4 에 3 을 넘긴다 | 1 | 3 | 3 | 7 | 5 |
| 둘째 바퀴 i = 3 | 칸 3 이 칸 4 에 3 을 넘긴다 | 1 | 3 | 3 | 10 | 5 |
| 둘째 바퀴 i = 4 | 위 칸 8 이 5 를 넘어 넘기지 않는다 | 1 | 3 | 3 | 10 | 5 |
| 둘째 바퀴 i = 5 | 위 칸 6 이 5 를 넘어 넘기지 않는다 | 1 | 3 | 3 | 10 | 5 |

채우기가 끝난 뒤 5 칸을 정의(맡는 구간의 합)와 대조했고, 어긋난 칸은 0 개입니다.

<!--/proof-->

믿기 전에 확인해 둘 자리가 두 곳 있습니다. 하나는 **넘기는 값이 그 칸의 최종값인가**예요. 칸 2 가 칸 4 에 넘긴
값은 첫 바퀴의 2 가 아니라 칸 1 을 받은 뒤의 3 입니다. 받는 칸의 번호가 언제나 주는 칸보다 크니, 번호가 작은
칸부터 지나가면 어느 칸이든 넘길 차례가 오기 전에 받을 것을 다 받아요. 다른 하나는 **위 칸이 배열 밖인
칸**입니다. 칸 4 와 칸 5 는 위 칸이 8 과 6 이라 넘기지 않고, 그래도 두 칸의 값은 정의와 같아요. 배열 밖에는 그
값을 받아야 할 칸이 없으니 빠진 몫도 없습니다.

#### 3단계 — 최하위 1 비트를 지워 가며 앞부분 합 모으기

여기부터는 질의가 올 때마다 하는 일입니다. 앞 `r` 개의 합은 칸 `r` 에서 시작해요. 칸 `r` 은 인덱스 `r − 1` 에서
끝나고 `lowbit(r)` 칸을 맡으니, 그 바로 앞 조각은 칸 `r − lowbit(r)` 이 맡습니다. 칸 번호에서 최하위 1 비트를
빼는 것은 이진 표기에서 **가장 낮은 1 하나를 지우는 것**이에요. 1 이 다 지워져 0 이 되면 멈춥니다. `r = 7` 로
따라가면 이렇습니다.

<!--fig:build-erase-->
![prefix(7) — 최하위 1 비트를 하나씩 지우며 읽는다](./figs/build-erase.svg)

전개 배열 `[1 2 3 4 5]` 에서 `r` 을 0 부터 5 까지 모두 넣어 봤습니다.

<!--proof:prefix-cases-->

| r | r 의 이진 표기 | 읽는 칸 | 이어 붙인 구간 | 합 | 앞 r 개를 직접 더한 값 |
| ---: | --- | --- | --- | --- | ---: |
| 0 | 000₂ | 없음 | 없음 | 0 | 0 |
| 1 | 001₂ | 칸 1 | [0,0] | 1 | 1 |
| 2 | 010₂ | 칸 2 | [0,1] | 3 | 3 |
| 3 | 011₂ | 칸 3 · 칸 2 | [2,2] · [0,1] | 6 | 6 |
| 4 | 100₂ | 칸 4 | [0,3] | 10 | 10 |
| 5 | 101₂ | 칸 5 · 칸 4 | [4,4] · [0,3] | 15 | 15 |

쉬운 경우는 `r = 4` 처럼 칸 하나로 끝날 때예요. 불안한 경우는 조각이 둘 이상일 때 **이어 붙인 구간이 겹치거나
비지 않는가**입니다. `r = 3` 은 칸 3 의 `[2,2]` 와 칸 2 의 `[0,1]` 을 이어 붙였고, 둘 사이에 빈 자리도 겹친 자리도
없어요. 빠지는 자리가 없는 근거는 종료 조건입니다. 칸 `k` 가 맡는 구간의 왼쪽 끝이 `k − lowbit(k)` 이고 다음 칸이
바로 그 번호에서 끝나니, 칸 번호가 0 에 이르면 이어 붙인 구간이 정확히 `[0, r − 1]` 입니다. `r = 0` 이면 루프가
한 번도 실행되지 않아 합이 0 이에요.

#### 4단계 — 앞부분 합 둘의 차로 구간 합 답하기

구간 `[l, r]` 은 앞 `r + 1` 개에서 앞 `l` 개를 덜어 낸 것입니다. 앞 `r + 1` 개가 인덱스 `r` 까지이고, 앞 `l` 개가
인덱스 `l − 1` 까지라 덜어 내면 `l` 부터 `r` 까지가 남아요. 여러 모양의 질의에 적용했습니다.

<!--proof:query-cases-->

| 질의 | 오른쪽 호출 | 왼쪽 호출 | 답 | 구간을 직접 더한 값 |
| --- | --- | --- | ---: | ---: |
| [0,4] | prefix(5) = 15 | prefix(0) = 0 | 15 | 15 |
| [2,3] | prefix(4) = 10 | prefix(2) = 3 | 7 | 7 |
| [2,2] | prefix(3) = 6 | prefix(2) = 3 | 3 | 3 |
| [4,4] | prefix(5) = 15 | prefix(4) = 10 | 5 | 5 |
| [1,3] | prefix(4) = 10 | prefix(1) = 1 | 9 | 9 |

`[0,4]` 처럼 왼쪽 끝이 0 이면 왼쪽 호출이 앞 0 개라 0 이고, `[2,2]` 처럼 한 칸짜리 질의도 같은 뺄셈으로 그 원소
하나가 남아요. 덧셈에 **뺄셈이라는 되돌리는 연산**이 있어서 이 단계가 성립합니다. 최솟값에는 그런 연산이 없다는
것이 「시작하기 전에」의 셋째 물음이었어요.

#### 5단계 — 덮어쓰기를 변화량으로 바꿔 품는 칸만 고치기

갱신은 `A[i]` 를 `v` 로 **덮어쓰는** 연산인데, 칸이 든 것은 합이라 칸에는 더하기만 할 수 있습니다. 그래서 옛 값을
`arr` 에서 읽어 **변화량** `delta = v − arr[i]` 를 만들고, 그 변화량을 인덱스 `i` 를 품은 칸에 더해요. 품은 칸은
칸 `i + 1` 에서 시작해 위 칸으로 이어지니, 칸 번호에 최하위 1 비트를 더해 가며 만납니다. 칸 번호가 `N` 을 넘으면
멈춰요. `A[2]` 를 고칠 때 칸 번호가 움직이는 모습입니다.

<!--fig:build-climb-->
![add(3, …) — 최하위 1 비트를 더하며 칸 3 · 4 를 고친다](./figs/build-climb.svg)

`A[2]` 를 3 에서 10 으로 고치면 변화량이 7 이고, 칸마다 이렇게 됩니다.

<!--proof:update-cells-->

| 칸 | 맡는 구간 | 인덱스 2 | 갱신 전 | 갱신 뒤 |
| --- | --- | ---: | ---: | ---: |
| 칸 1 | [0,0] | 품지 않는다 | 1 | 1 |
| 칸 2 | [0,1] | 품지 않는다 | 3 | 3 |
| 칸 3 | [2,2] | 품는다 | 3 | 10 |
| 칸 4 | [0,3] | 품는다 | 10 | 17 |
| 칸 5 | [4,4] | 품지 않는다 | 5 | 5 |

갱신 뒤 앞 r 개의 합을 r = 0 부터 5 까지 6 번 물었고, 6 번이 고친 배열을 직접 더한 값과 같습니다.

<!--/proof-->

고친 칸이 품는 칸과 같은지는 칸이 많을 때 더 불안합니다. 길이 16 배열에서 인덱스마다 갱신을 걸고, 지나간 칸과
맡는 구간에 그 인덱스가 든 칸을 나란히 적었어요.

<!--proof:update-contain-->

| 인덱스 i | 시작 칸 i + 1 의 이진 표기 | add 가 지나는 칸 | 맡는 구간에 i 가 든 칸 |
| ---: | --- | --- | --- |
| 0 | 00001₂ | 칸 1 · 칸 2 · 칸 4 · 칸 8 · 칸 16 | 칸 1 · 칸 2 · 칸 4 · 칸 8 · 칸 16 |
| 2 | 00011₂ | 칸 3 · 칸 4 · 칸 8 · 칸 16 | 칸 3 · 칸 4 · 칸 8 · 칸 16 |
| 5 | 00110₂ | 칸 6 · 칸 8 · 칸 16 | 칸 6 · 칸 8 · 칸 16 |
| 10 | 01011₂ | 칸 11 · 칸 12 · 칸 16 | 칸 11 · 칸 12 · 칸 16 |
| 15 | 10000₂ | 칸 16 | 칸 16 |

길이 16 배열의 인덱스 16 개 가운데 16 개에서 두 목록이 같습니다.

<!--/proof-->

두 목록이 모든 인덱스에서 같으니, 최하위 1 비트를 더해 가는 이동은 **품는 칸만, 빠짐없이** 지납니다. 품지 않는
칸은 맡는 구간에 바뀐 자리가 없어서 합이 바뀔 수 없어요.

#### 이 방법이 기대는 전제

최하위 1 비트 길이로 나눠 담기는 아래 네 전제에 기대고 있어서, 하나라도 빠지면 답이 틀리거나 방법 자체를 쓸 수
없어요.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 합치는 연산에 되돌리는 연산이 있다(덧셈 ↔ 뺄셈) | 4단계 앞 `l` 개를 덜어 낸다 | 최솟값처럼 덜어 낼 수 없으면 왼쪽 끝이 0 이 아닌 질의에 답하지 못한다 |
| 합치는 순서를 바꿔도 결과가 같다 | 2단계 넘겨받는 순서 · 5단계 변화량을 나중에 더한다 | 칸에 쌓인 값이 구간의 차례와 다르게 합쳐진다 |
| 질의가 연속 구간을 묻는다 | 3 · 4단계 앞부분 둘로 가른다 | 띄엄띄엄 고른 인덱스는 앞부분 합의 차로 나오지 않는다 |
| 갱신이 원소 하나를 바꾼다 | 5단계 품는 칸만 고친다 | 구간 전체를 바꾸면 그 구간의 원소마다 따로 고쳐야 한다 |

첫째 전제가 누적합과 같은 뿌리이고, 그 이름은 파트 1 의 마지막에서 붙입니다.

#### 고정 길이 묶음이 아니라 최하위 1 비트 길이인 까닭

「아이디어를 떠올리는 과정」에서 고정 길이 묶음은 질의 하나의 최악만 셌습니다. 이번에는 묶음 크기를 아홉 가지로
놓고, 같은 1,024 칸 목록에서 펜윅 트리와 함께 세었어요.

<!--proof:block-size-->

| 방법 | 미리 만들기 | 질의 | 갱신 | 합 | 추가 칸 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 고정 길이 묶음 B=1 | 2,048 | 173,944 | 2,048 | 178,040 | 1,024 |
| 고정 길이 묶음 B=2 | 1,536 | 87,228 | 2,048 | 90,812 | 512 |
| 고정 길이 묶음 B=4 | 1,280 | 44,638 | 2,048 | 47,966 | 256 |
| 고정 길이 묶음 B=8 | 1,152 | 24,872 | 2,048 | 28,072 | 128 |
| 고정 길이 묶음 B=16 | 1,088 | 18,049 | 2,048 | 21,185 | 64 |
| 고정 길이 묶음 B=32 | 1,056 | 20,587 | 2,048 | 23,691 | 32 |
| 고정 길이 묶음 B=64 | 1,040 | 33,202 | 2,048 | 36,290 | 16 |
| 고정 길이 묶음 B=256 | 1,028 | 109,174 | 2,048 | 112,250 | 4 |
| 고정 길이 묶음 B=1024 | 1,025 | 173,944 | 2,048 | 177,017 | 1 |
| 펜윅 트리 | 5,117 | 5,102 | 7,178 | 17,397 | 1,025 |

고정 길이 묶음은 B=16 에서 합이 21,185 로 가장 적고, 펜윅 트리는 17,397 입니다.

<!--/proof-->

고정 길이 묶음의 합은 `B` 를 키울수록 줄다가 `B = 16` 을 지나 다시 늘어요. 질의가 남는 칸과 묶음 수 두 항의
합이라서입니다. 갱신은 어느 `B` 에서도 2,048 로 펜윅 트리의 7,178 보다 적고, 추가 칸도 대부분 더 적어요.
펜윅 트리는 **갱신과 추가 칸을 더 쓰고 질의를 18,049 에서 5,102 로 줄인 맞바꿈**입니다. 1,024 칸에서는 합의
차이가 크지 않고, 차이는 규모가 벌려요. 「아이디어를 떠올리는 과정」의 과제 규모 표에서 제곱근 분할은
38,950,317 번, 펜윅 트리는 2,028,990 번이었습니다.

#### 다섯 단계를 이은 절차

다섯 단계를 코드의 순서로 다시 적으면 네 걸음이 됩니다. 3 · 4단계는 질의 하나를 답하는 두 줄로 묶여요.

1. `tree` 를 `N + 1` 칸으로 잡고 칸 0 을 비운다
2. 칸마다 자기 원소를 넣고, 번호가 작은 칸부터 위 칸 `i + lowbit(i)` 에 한 번씩 더한다
3. 질의 `[l, r]` 은 `prefix(r + 1) − prefix(l)` 로 답하고, `prefix(r)` 은 칸 `r` 부터 최하위 1 비트를 빼 가며
   칸 값을 더한다
4. 갱신 `(i, v)` 는 변화량을 만들고 `arr` 를 고친 뒤, 칸 `i + 1` 부터 최하위 1 비트를 더해 가며 변화량을 더한다

### 수행으로 알아보는 알고리즘 — 다섯 칸을 채우고 연산 넷을 처리한다

아이디어를 확인했으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 정해 끝까지 가져가되, 코드 조각을
하나 만들 때마다 그 조각만 실행한 결과를 확인하고 다음으로 넘어갑니다.

<!--proof:walk-input-->

```ts
const A = [1, 2, 3, 4, 5];
const ops: FenwickOp[] = [
  { type: "query", l: 0, r: 4 },
  { type: "update", i: 2, v: 10 },
  { type: "query", l: 0, r: 4 },
  { type: "query", l: 2, r: 3 },
];
// 이 절이 끝나면 [15, 22, 14] 가 나와야 한다
```

왜 이 넷일까요? 코드의 갈래를 **모두 실행하게** 하려는 것입니다. 갱신이 가운데 있어서 같은 질의 `[0,4]` 의 답이
앞뒤로 갈리고, 마지막 질의는 왼쪽 끝이 0 이 아니라 **빼는 쪽 호출까지** 실행해요. 1단계의 표에서 본 것처럼 이
배열에는 맡는 길이가 1 · 2 · 4 인 칸이 다 있고, 위 칸이 배열 밖인 칸도 있습니다.

```text
절차 전체를 한 장으로

  tree 를 N+1 칸으로 잡고 0 으로 채운다 (칸 0 은 쓰지 않는다)

  채우기:  칸마다 자기 몫을 넣는다                                   ③
           칸 i 가 위 칸 i + lowbit(i) 에 자기 값을 한 번 더한다     ④

  연산을 순서대로 받으며:
      update(i, v)   변화량을 만들고 arr 를 고친다                   ⑤
                     칸 i+1 부터 lowbit 을 더해 가며 변화량을 더한다 ①
      query(l, r)    앞 r+1 개의 합에서 앞 l 개의 합을 뺀다          ⑥
                     앞부분의 합은 lowbit 을 빼 가며 모은다          ②
```

#### 1. 칸 0 을 비우고 트리 배열을 잡는다

트리 배열을 `N + 1` 칸으로 잡고 칸 번호를 1 부터 씁니다. 칸 0 을 비워 두는 한 줄이 두 이동의 종료 조건을
만들어요.

```ts
const N = A.length;
const arr = A.slice();
const tree = new Array<number>(N + 1).fill(0);
const lowbit = (k: number): number => k & -k;
```

0 의 최하위 1 비트는 0 입니다. 그러니 칸 0 에서는 빼도 더해도 제자리예요.

<!--proof:walk-zero-->

| 칸 번호 | 최하위 1 비트 | 빼는 이동 | 더하는 이동 | 결과 |
| ---: | ---: | --- | --- | --- |
| 0 | 0 | 0 − 0 = 0 | 0 + 0 = 0 | 제자리다 |
| 1 | 1 | 1 − 1 = 0 | 1 + 1 = 2 | 0 에서 멈추거나 위 칸으로 간다 |

칸 번호를 0 부터 쓰면 칸 0 에서 두 루프가 멈추지 않습니다. 그래서 칸 0 은 비우고, 앞부분의 합은 칸 번호가
0 이 되면 멈추게 둡니다. `arr` 를 따로 두는 것도 여기서 정해요. 갱신이 **덮어쓰기**라 옛 값이 필요하고, 옛 값을
아는 자리가 `arr` 입니다.

#### 2. 자기 몫을 채우고 위 칸에 한 번만 넘긴다

채우는 순서가 이 조각의 전부입니다. 번호가 작은 칸부터 넘기면 한 바퀴로 끝나요.

```ts
for (let i = 1; i <= N; i++) tree[i] = arr[i - 1] ?? 0; // ③ 자기 몫만 채운다
for (let i = 1; i <= N; i++) {
  const j = i + lowbit(i);
  if (j <= N) tree[j] = (tree[j] ?? 0) + (tree[i] ?? 0); // ④ 위 칸에 한 번만 넘긴다
}
```

이 조각만 실행하면 다섯 칸이 이렇게 채워집니다.

<!--proof:walk-build-->

| 걸음 | 하는 일 | 칸 1 | 칸 2 | 칸 3 | 칸 4 | 칸 5 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| T1 | 자기 몫 채우기 · ③ | 1 | 2 | 3 | 4 | 5 |
| T2 | 칸 1 → 칸 2 · ④ | 1 | 3 | 3 | 4 | 5 |
| T3 | 칸 2 → 칸 4 · ④ | 1 | 3 | 3 | 7 | 5 |
| T4 | 칸 3 → 칸 4 · ④ | 1 | 3 | 3 | 10 | 5 |

T4 가 끝나면 다섯 칸이 모두 1단계 표의 구간 합과 같아요. T3 에서 칸 2 가 넘긴 값이 첫 바퀴의 2 가 아니라 3 인
것이 「넘기는 값이 최종값」의 자리입니다.

#### 짚고 가기 — 넘겨주는 바퀴는 오름차순이어야 한다

여기서 헷갈리기 쉬운 지점은 둘째 바퀴의 방향입니다. 「어느 순서로 넘겨도 같은 값이 모인다」고 읽히는데, 넘기는
값이 그 칸의 **최종값**이어야 하므로 순서가 답을 정해요. 둘째 바퀴를 칸 `N` 부터 거꾸로 지나가게 바꾼 코드에 같은
연산 넷과 칸 4 하나만 읽는 질의 `[0,3]` 을 실행했습니다.

<!--proof:pause-build-order-->

| 질의 | 바른 코드 | 내림차순으로 넘긴 코드 | 판정 |
| --- | ---: | ---: | --- |
| 질의 [0,4] | 15 | 14 | 어긋난다 |
| 질의 [0,4] | 22 | 21 | 어긋난다 |
| 질의 [2,3] | 14 | 13 | 어긋난다 |
| 질의 [0,3] | 17 | 16 | 어긋난다 |

마지막 줄은 칸 4 하나만 읽는 질의입니다. 네 줄에서 바른 코드의 답에서 다른 코드의 답을 빼면 1 · 1 · 1 · 1 입니다.

<!--/proof-->

네 답이 모두 같은 크기만큼 작습니다. 내림차순이면 칸 2 가 칸 1 의 몫을 받기 **전에** 칸 4 에 넘겨서, 칸 1 의
값이 칸 4 에 끝내 가지 않아요. 네 질의가 모두 칸 4 를 읽으니 같은 크기만큼 어긋납니다. **받는 칸의 번호가 언제나
주는 칸보다 크다**는 성질 하나가 오름차순 한 바퀴를 정당하게 만들어요.

#### 3. 맡는 구간을 이어 붙여 앞부분의 합을 낸다

질의 하나는 앞부분의 합 두 번으로 끝납니다. 칸 번호에서 최하위 1 비트를 빼 가며 칸 값을 모으는 것이 이 조각의
전부예요.

```ts
function prefix(r: number): number {
  let sum = 0;
  for (let k = r; k > 0; k -= lowbit(k)) {
    sum += tree[k] ?? 0; // ② 담당 구간을 이어 붙이며 내려간다
  }
  return sum;
}

result.push(prefix(op.r + 1) - prefix(op.l)); // ⑥ 구간 합을 접두 합 둘의 차로
```

첫 질의 `[0,4]` 에 이 조각만 실행한 결과입니다.

<!--proof:walk-prefix-->

| 걸음 | 부르는 곳 | 읽은 칸 | 맡는 구간 | 더한 뒤의 합 | 다음 칸 번호 |
| --- | --- | --- | ---: | ---: | --- |
| T5 | prefix(5) | 칸 5 | [4,4] | 5 | 5 − 1 = 4 |
| T5 | prefix(5) | 칸 4 | [0,3] | 15 | 4 − 4 = 0, 멈춘다 |
| T6 | prefix(0) | 없음 | — | 0 | 루프가 한 번도 실행되지 않는다 |

답은 prefix(5) − prefix(0) = 15 − 0 = 15 입니다.

<!--/proof-->

오른쪽 끝에 `+ 1` 이 붙는 까닭이 여기서 보입니다. `prefix(r)` 는 **앞 `r` 개**의 합이라 인덱스 `r − 1` 까지예요.
인덱스 `r` 까지 넣으려면 앞 `r + 1` 개를 물어야 하고, 왼쪽은 인덱스 `l − 1` 까지를 덜어 내야 하니 앞 `l` 개입니다.

#### 4. 덮어쓰기를 변화량으로 바꿔 품는 칸만 고친다

갱신은 두 걸음입니다. 덮어쓰기를 변화량으로 바꾸는 것이 첫 걸음이고, 그 변화량을 품는 칸에 더하는 것이 둘째
걸음이에요.

```ts
function add(i: number, delta: number): void {
  for (let k = i; k <= N; k += lowbit(k)) {
    tree[k] = (tree[k] ?? 0) + delta; // ① 담당 칸을 따라 올라간다
  }
}

const delta = op.v - (arr[op.i] ?? 0); // ⑤ 덮어쓰기를 변화량으로 바꾼다
arr[op.i] = op.v;
add(op.i + 1, delta);
```

`update(i=2, v=10)` 에 이 조각만 실행한 결과입니다.

<!--proof:walk-update-->

| 걸음 | 하는 일 | 계산 | 결과 |
| --- | --- | --- | ---: |
| T7 | 변화량 만들기 · ⑤ | 10 − 3 | 7 |
| T8 | 칸 3 고치기 · ① | tree[3] + delta = 3 + 7 | 10 |
| T9 | 칸 4 고치기 · ① | tree[4] + delta = 10 + 7 | 17 |

고친 칸은 2 개이고, 나머지 3 칸은 손대지 않았습니다.

<!--/proof-->

채우기의 둘째 바퀴와 `add` 는 같은 방향으로 움직입니다. 둘 다 칸 번호에 최하위 1 비트를 더하는 이동인데, 채우기는
칸마다 **위 칸 하나에만** 넘기고 `add` 는 `N` 을 넘을 때까지 계속 올라가요.

| 이동 | 한 번에 가는 거리 | 가는 횟수 |
| --- | --- | --- |
| 채우기 둘째 바퀴 | `i` → `i + lowbit(i)` 한 번 | 칸마다 많아야 한 번 |
| `add(i, delta)` | `i` → `i + lowbit(i)` → … → `N` 초과 | 한 번 부를 때 칸 번호의 자릿수 이하 |

#### 짚고 가기 — 새 값을 그대로 더하면 옛 값이 0 인 자리에서만 답이 맞는다

여기서 헷갈리기 쉬운 지점은 `update` 의 뜻입니다. 칸이 든 것은 **합**이라 칸에는 더하기밖에 못 하는데, 과제가 주는
연산은 「그 자리를 `v` 로 바꿔라」예요. 변화량을 만들지 않고 `v` 를 그대로 더한 코드에 같은 연산 넷과, 옛 값이
0 인 배열의 목록 하나를 실행했습니다.

<!--proof:pause-raw-value-->

| 질의 | 바른 코드 | 값을 그대로 더한 코드 | 판정 |
| --- | ---: | ---: | --- |
| 질의 [0,4] | 15 | 15 | 같다 |
| 질의 [0,4] | 22 | 25 | 어긋난다 |
| 질의 [2,3] | 14 | 17 | 어긋난다 |
| 질의 [0,2] · A = [0 0 0] | 7 | 7 | 같다 |

전개의 갱신은 옛 값 3 을 새 값 10 으로 덮어씁니다. 마지막 줄은 옛 값이 0 인 배열입니다.

<!--/proof-->

**갱신 앞의 질의와 마지막 줄은 답이 같습니다.** 옛 값이 0 이면 변화량과 새 값이 같아지니, 초기값이 0 인 배열로만
시험하면 이 코드는 통과해요. 갱신 뒤의 두 답이 어긋난 크기는 둘 다 덮어쓴 자리의 옛 값과 같고, 그 옛 값이 지워지지
않고 칸에 남은 것입니다.

#### 짚고 가기 — 논리 배열을 함께 고치지 않으면 같은 자리를 두 번 갱신할 때만 답이 갈린다

여기서 헷갈리기 쉬운 지점은 `arr[op.i] = op.v` 한 줄입니다. 변화량을 만들고 나면 그 줄이 할 일이 없어 보이는데,
**다음 갱신이 그 값을 읽어요.** 그 줄을 지운 코드에 같은 연산 넷과, 같은 자리를 두 번 갱신하는 목록을 실행했습니다.

옛 값이 처음 값 1 에 머물러 변화량이 `10 − 5` 가 아니라 `10 − 1` 이 되고, 그 차이만큼 칸이 커집니다. 한 자리를 두
번 갱신하는 목록이 하나라도 있어야 이 줄이 검사되고, 그런 목록이 없는 시험은 이 코드를 통과시켜요.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `ops` 를 순서대로 받는 루프와 결과 목록을 빈
배열로 시작하는 한 줄뿐이에요. 질의가 하나도 없으면 그 빈 배열이 그대로 답이 됩니다.

```ts
export type FenwickOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function fenwickRangeSum(A: number[], ops: FenwickOp[]): number[] {
  const N = A.length;
  // `update` 가 덮어쓰기라 옛 값이 필요하다. 논리 배열을 따로 들고 tree 와 함께 고친다.
  const arr = A.slice();
  // 칸 0 은 비워 둔다 — 0 의 담당 구간 길이가 0 이라 두 루프가 그 칸에서 멈추지 않는다.
  const tree = new Array<number>(N + 1).fill(0);

  /** 칸 `k` 가 담당하는 구간의 길이. */
  const lowbit = (k: number): number => k & -k;

  /** `arr[i-1]` 이 `delta` 만큼 달라진 것을 그 칸을 담당 구간에 품은 칸 전부에 반영한다. */
  function add(i: number, delta: number): void {
    for (let k = i; k <= N; k += lowbit(k)) {
      tree[k] = (tree[k] ?? 0) + delta; // ① 담당 칸을 따라 올라간다
    }
  }

  /** `arr[0..r-1]` 의 합. `r = 0` 이면 루프가 한 번도 실행되지 않아 0 이다. */
  function prefix(r: number): number {
    let sum = 0;
    for (let k = r; k > 0; k -= lowbit(k)) {
      sum += tree[k] ?? 0; // ② 담당 구간을 이어 붙이며 내려간다
    }
    return sum;
  }

  for (let i = 1; i <= N; i++) tree[i] = arr[i - 1] ?? 0; // ③ 자기 몫만 채운다
  for (let i = 1; i <= N; i++) {
    const j = i + lowbit(i);
    if (j <= N) tree[j] = (tree[j] ?? 0) + (tree[i] ?? 0); // ④ 위 칸에 한 번만 넘긴다
  }

  const result: number[] = [];
  for (const op of ops) {
    if (op.type === "update") {
      const delta = op.v - (arr[op.i] ?? 0); // ⑤ 덮어쓰기를 변화량으로 바꾼다
      arr[op.i] = op.v;
      add(op.i + 1, delta);
    } else {
      result.push(prefix(op.r + 1) - prefix(op.l)); // ⑥ 구간 합을 접두 합 둘의 차로
    }
  }
  return result;
}
```

<!--proof:final-calls-->

```text
fenwickRangeSum([1, 2, 3, 4, 5], 위 연산 넷)            →  [15, 22, 14]
fenwickRangeSum([1, 2, 3], [])                          →  []
fenwickRangeSum([7], 질의 [0,0])                        →  [7]
fenwickRangeSum([1, 2, 3], 갱신 i=0 v=-5 · 질의 [0,2])  →  [0]
```

### 알아 두면 좋은 개념 — 이진 표현으로 분해하기

이 절차가 앞부분의 합에 한 일을 한 문장으로 줄이면 **「`r` 을 2 의 거듭제곱의 합으로 쪼개고, 조각마다 칸 하나를
읽는다」** 입니다. 자연수의 이진 표기는 한 가지뿐이므로 쪼개는 방법도 한 가지이고, 그래서 읽는 칸의 개수가 `r` 의
**1 비트 개수**로 정해져요. 전개에서 그것이 나온 자리를 모으면 이렇습니다.

<!--proof:related-split-->

| 걸음 | 호출 | r 의 이진 표기 | 2 의 거듭제곱으로 쪼갠 모양 | 읽은 칸 |
| --- | --- | --- | --- | --- |
| T5 | prefix(5) | 101₂ | 1 + 4 | 칸 5 · 칸 4 |
| T12 | prefix(4) | 100₂ | 4 | 칸 4 |
| T13 | prefix(2) | 10₂ | 2 | 칸 2 |

3 줄 가운데 3 줄에서 읽은 칸의 수가 r 의 1 비트 개수와 같습니다.

<!--/proof-->

이름을 붙이고 나면 같은 분해를 다른 자리에서도 알아볼 수 있습니다. 지수를 이진 표기로 쪼개면 거듭제곱이 곱셈 몇
번으로 줄고, 거슬러 올라갈 걸음 수를 이진 표기로 쪼개면 트리의 조상을 몇 번 만에 찾아요.

| 같은 이름을 다시 만나는 자리 | 쪼개는 수 | 조각 하나가 하는 일 |
| --- | --- | --- |
| 거듭제곱 | 지수 `n` | `x^(2^j)` 를 한 번 곱한다 |
| 이진 들어올리기 | 거슬러 올라갈 걸음 수 | `2^j` 칸 위의 조상으로 건너뛴다 |
| 이 글의 앞부분 합 | 앞에서 센 개수 `r` | 길이 `2^j` 짜리 구간의 합을 읽는다 |

셋 다 조각의 개수가 **1 비트의 개수**이고, 그래서 비용이 자릿수로 정해집니다. 거듭제곱 쪽은
[`fastPower`](../../number-theory/fastPower/fastPower-guide.md) 가 같은 분해를 같은 이름으로 다뤄요.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 배열이 질의 사이에 바뀐다 | 안 바뀌면 누적합 배열이 질의를 칸 둘로 끝낸다 | 칸 번호에 최하위 1 비트를 더해 가는 `add` |
| 질의가 연속 구간의 합을 묻는다 | 띄엄띄엄 고른 인덱스는 앞부분 둘로 가르지 못한다 | 두 끝 `l` · `r` 만 받는 `prefix(r + 1) − prefix(l)` |
| 합치는 연산에 되돌리는 연산과 교환 법칙이 있다 | 덧셈 · 배타적 논리합은 되고 최솟값은 안 된다 | 뺄셈 한 번과 순서를 안 따지는 `+=` |
| 연산이 많다 | 채우는 비용을 연산들이 나눠 진다 | 처음에 한 번만 하는 두 바퀴 채우기 |

마지막 조건에 경계가 있습니다. 채우는 비용이 연산 하나의 비용보다 훨씬 커서, 연산이 한둘뿐이면 구간을 그냥
더하는 편이 적어요.

<!--proof:fit-boundary-->

| 경우 | 직접 더하기 | 펜윅 트리(만들기 + 연산의 상한) |
| --- | ---: | ---: |
| 연산 1 개, 구간 10 칸 | 10 | 500,018 |
| 연산 100,000 개 | 최악 10,000,000,000 | 4,099,982 |

N = 100,000 에서 채우기가 499,982 번(2N + 3H, H = 99,994)이고, 연산 하나는 최악 36 번으로 셌습니다.

<!--/proof-->

경계는 「연산이 몇 개인가」입니다. 질의 하나에 50 만 번을 쓰는 것은 손해이고, 연산이 10 만 개면 100 억 번이 410
만 번이 돼요.

#### 문제에서 이것을 떠올리게 하는 단서

| 보이는 곳 | 이런 말이나 모양 | 뜻 | 펜윅 트리 |
| --- | --- | --- | --- |
| 지문 | "i 번째 원소를 v 로 바꾼다" "값을 더한다" "실시간으로 반영" | 배열이 바뀐다. 결정적인 신호다 | 쓴다 |
| 지문 | "구간 [l, r] 의 합" "부분합" "누적 점수" "빈도 누적" | 되돌리는 연산이 있는 합을 묻는다 | 쓴다 |
| 지문 | "연산이 순서대로 주어진다" "각 질의에 대해 답하라" | 연산이 많다 | 쓴다 |
| 제약 | N 과 Q 가 둘 다 10^5 규모 | N × Q 가 시간 안에 못 든다 | 쓴다 |
| 제약 | 갱신과 질의의 비율이 안 적혀 있다 | 둘 다 빨라야 한다 | 쓴다 |
| 지문 | "배열은 변경되지 않는다" "정적" | 갱신이 없다 | 누적합 배열이 질의가 더 적다 |
| 지문 | "구간의 최솟값" "구간의 최댓값" | 뺄셈으로 앞부분을 덜어 내지 못한다 | 쓰지 않는다 |
| 지문 | "구간 [l, r] 의 모든 값에 x 를 더한다" | 한 번에 여러 원소가 바뀐다 | 차분 배열을 한 겹 더 씌운다 |

아래 세 줄에 해당하면 다른 절차로 갑니다. 배열이 안 바뀌면
[`prefixSumRangeQuery`](../prefixSumRangeQuery/prefixSumRangeQuery-guide.md) 이고, 최솟값을 묻거나 구간 갱신이
붙으면 [`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) ·
[`diffArrayRangeUpdate`](../diffArrayRangeUpdate/diffArrayRangeUpdate-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **AtCoder Library 의 `atcoder::fenwick_tree`** — 이 절차를 그대로 담은 공개 라이브러리입니다. 공개 연산이
  `void add(int p, T x)` 와 `T sum(int l, int r)` 둘인데, **`add` 가 누적이라 덮어쓰기를 부르는 쪽이 변화량으로
  바꿔서 넣어야 해요** — 「짚고 가기」에서 본 그 자리가 인터페이스에 그대로 있습니다. `sum` 의 본문이
  `return sum(r) - sum(l);` 이라 구간이 반개구간 `[l, r)` 이고, 내부 이동은 `p += p & -p` 와 `r -= r & -r` 입니다.
  ([`atcoder/fenwicktree.hpp`](https://github.com/atcoder/ac-library/blob/master/atcoder/fenwicktree.hpp),
  조회 2026-09-03)
- **KACTL 의 `FenwickTree.h`** — 머리 주석이 *"Computes partial sums and updates single elements"* 로 이 과제를
  그대로 적고 있습니다. 칸 번호를 0 부터 세는 판이라 이동이 `pos |= pos + 1` 과 `pos &= pos - 1` 인데, 뒤엣것이
  **최하위 1 비트를 지우는 연산**이라 이 글의 이동과 같은 것을 다른 표기로 적은 것이에요.
  ([`content/data-structures/FenwickTree.h`](https://github.com/kth-competitive-programming/kactl/blob/main/content/data-structures/FenwickTree.h),
  조회 2026-09-03)
- **Rust 의 `segment-tree` 크레이트 `PrefixPoint`** — 문서가 *"This data structure is implemented using a
  Fenwick tree"* 라 밝히고, 타입이 `PrefixPoint<N, O> where O: Commutative<N>` 입니다. **교환 법칙을 타입으로
  요구하는 것**이 같은 크레이트의 구간 트리와 갈리는 자리예요.
  ([`segment_tree::PrefixPoint`](https://docs.rs/segment-tree/latest/segment_tree/struct.PrefixPoint.html),
  조회 2026-09-03)

셋이 바깥에 내놓는 이름을 이 글의 이름과 나란히 두면 이렇습니다.

| 출처 | 더하는 연산 | 앞부분의 합 | 요구하는 조건 |
| --- | --- | --- | --- |
| AtCoder Library | `add(p, x)` | `sum(r)` | 덧셈 |
| KACTL | `update(pos, dif)` | `query(pos)` | 덧셈 |
| segment-tree 크레이트 | `modify` | `query` | `Commutative` 트레이트 |
| 이 글 | `add` | `prefix` | 되돌리는 연산과 교환 법칙 |

앞의 둘은 구간 합을 저장하지 않고 앞부분의 합 둘의 차로 만들고, Rust 판은 앞부분의 합 자체만 내놓습니다.

#### 경쟁 설계와의 대조

같은 목표, 곧 갱신이 섞인 구간 합에 답하는 다른 절차로 **제곱근 분할**이 있습니다. 배열을 `B = √N` 칸씩 끊어
묶음마다 합 하나를 적어 두고, 갱신은 그 칸과 묶음 합 하나만 고쳐요. 「아이디어를 떠올리는 과정」에서 길이를
하나로 고정하는 한계를 보인 그 방법이고, 여기서는 **그 한계가 장점이 되는 조건**을 값으로 찾습니다.

| 설계 | 칸이 맡는 길이 | 질의 하나 | 갱신 하나 |
| --- | --- | --- | --- |
| 펜윅 트리 | 칸마다 최하위 1 비트 | 두 끝의 1 비트 개수만큼 | 칸 번호의 자릿수만큼 |
| 제곱근 분할 | 모든 묶음이 `B` | 남는 칸과 묶음 수의 합 | 접근 넷 |

두 설계에 같은 입력과 같은 작업 목록을 주고 **배열 접근 수**를 셌습니다. 배열은 `N = 1,024` 이고
`A[i] = (41i) mod 97` 이에요. 질의 `t` 번째는 `a = (23t) mod N` 과 `b = (67t) mod N` 을 만들어 작은 쪽을 왼쪽
끝으로 두고, 갱신 `k` 번째는 `A[(59k) mod N]` 을 `((31k) mod 1000) − 500` 으로 덮어써요. 갱신은 질의 사이에
고르게 끼웠고, 묶음 길이는 `B = 32` 입니다. 난수가 없어 시드도 없어요. 전개가 쓰는 다섯 칸짜리 입력에서는
묶음이 두세 개뿐이라 두 설계의 계수가 상수에 묻혀서, 「아이디어를 떠올리는 과정」의 1,024 칸 표와 **같은
생성식**의 입력을 쓰고 질의 수와 갱신 수만 바꿉니다.

**갱신을 0 회로 묶어 두면 질의 수 하나가 순서를 정합니다.**

| 갱신 0 회 | 펜윅 트리 | 제곱근 분할 | 적은 쪽 |
| --- | --- | --- | --- |
| 질의 136 개 | 6,465 | **6,458** | 제곱근 분할이 7 번 적습니다 |
| 질의 137 개 | **6,474** | 6,517 | **여기서 순서가 뒤집힙니다** |
| 질의 4,096 개 | **46,049** | 165,628 | 펜윅 트리가 3.6 배 적습니다 |

**갱신이 아주 많아지면 순서가 다시 반대로 갑니다.**

| 질의 1,024 개 | 펜윅 트리 | 제곱근 분할 | 적은 쪽 |
| --- | --- | --- | --- |
| 갱신 0 회 | **15,350** | 42,199 | 펜윅 트리가 2.7 배 적습니다 |
| 갱신 2,684 회 | **52,928** | 52,935 | 7 번 차이로 아직 펜윅 트리입니다 |
| 갱신 2,685 회 | 52,944 | **52,939** | **여기서 순서가 뒤집힙니다** |
| 갱신 16,384 회 | 244,726 | **107,735** | 제곱근 분할이 2.3 배 적습니다 |

추가로 잡는 칸은 펜윅 트리가 **1,025** 이고 제곱근 분할이 **32** 입니다. 이 항목은 갱신과 질의의 비율이 어떻든 순서가 그대로예요.
묶음 합은 `N / B` 개뿐인데 펜윅 트리는 칸마다 하나씩 두기 때문입니다. 순서가 뒤집히는 자리를 비용 항으로 가르면
이렇습니다.

<!--proof:alt-boundary-->

| 비용(배열 접근 수) | 펜윅 트리 | 제곱근 분할 | 펜윅 트리 − 제곱근 분할 |
| --- | ---: | ---: | ---: |
| 만들기 | 5,117 | 1,056 | 4,061 |
| 질의 하나 평균(질의 136 개) | 9.9 | 39.7 | -29.8 |
| 갱신 하나 평균(갱신 16,384 회) | 14.0 | 4.0 | 10.0 |

만들기의 차이 4,061 을 질의 하나의 차이 29.8 로 나누면 136.2 입니다. 질의 1,024 개에서 제곱근 분할이 더 쓴 26,849 를 갱신 하나의 차이 10.0 으로 나누면 2,684.9 이고, 그 갱신 수는 질의 수 1,024 의 2.6 배입니다.

<!--/proof-->

실측 경계는 질의 137 개와 갱신 2,685 회였고, 나눈 값 136.2 와 2,684.9 가 그 바로 아래에 있어요. **이 절차가
내주는 것은 갱신 하나의 비용과 추가 칸입니다.** 제곱근 분할은 갱신을 접근 넷으로 끝내고 칸도 32 개만 쓰는데,
펜윅 트리는 갱신마다 자릿수만큼 고치고 칸을 1,025 개 써요. 그 대신 얻는 것이 질의 하나의 비용입니다.

| 조건 | 고를 설계 | 까닭 |
| --- | --- | --- |
| 갱신과 질의의 비율을 모른다 | 펜윅 트리 | 둘 다 자릿수로 눌러 둔다 |
| 갱신이 질의보다 훨씬 많다 | 제곱근 분할 | 갱신 하나의 차이가 질의에서 아낀 몫보다 커진다 |
| 연산이 아주 적다 | 제곱근 분할 | 만들기의 차이를 질의로 갚지 못한다 |
| 메모리가 빠듯하다 | 제곱근 분할 | 추가 칸이 `√N` 개다 |

갱신과 질의가 섞여 들어오는데 그 비율이 정해져 있지 않다면 펜윅 트리가 알맞습니다. 갱신이 질의의 2.6 배를 넘는다고
정해지는 순간 이 결론을 다시 따져야 해요.

### 수식 정의와 유도

칸이 맡는 구간과 그 칸에 적는 값을 정의합니다. 칸 번호 `k` 는 1 부터 세고, 인덱스는 0 부터 셉니다.

$$\text{LSB}(k) = k \mathbin{\&} (-k), \qquad \mathrm{cover}(k) = \bigl[\,k - \text{LSB}(k),\ k - 1\,\bigr]$$

$$\mathrm{tree}[k] = \sum_{t \in \mathrm{cover}(k)} A[t], \qquad \mathrm{pre}(r) = \sum_{t=0}^{r-1} A[t]$$

| 기호 | 뜻 |
| --- | --- |
| `LSB(k)` | 칸 번호 `k` 의 최하위 1 비트. 코드에서는 `lowbit(k)` 다 |
| `cover(k)` | 칸 `k` 가 맡는 인덱스 구간. 오른쪽 끝이 `k − 1` 이고 길이가 `LSB(k)` 다 |
| `pre(r)` | 앞 `r` 개의 합. `r = 0` 이면 빈 합이라 0 이다. 코드에서는 `prefix(r)` 다 |

정의를 길이 16 배열의 칸 넷에 넣어 봅시다.

<!--proof:math-check-->

| k | k 의 이진 표기 | LSB(k) | cover(k) | 그 구간의 A | tree[k] |
| ---: | --- | ---: | --- | --- | ---: |
| 6 | 110₂ | 2 | [4,5] | 5 + 6 | 11 |
| 7 | 111₂ | 1 | [6,6] | 7 | 7 |
| 8 | 1000₂ | 8 | [0,7] | 1 + 2 + 3 + 4 + 5 + 6 + 7 + 8 | 36 |
| 12 | 1100₂ | 4 | [8,11] | 9 + 10 + 11 + 12 | 42 |

배열은 길이 16 의 [1 2 3 … 16] 이고, tree[k] 열은 정본의 채우기를 실행한 값입니다.

<!--/proof-->

식의 $\text{LSB}$ 를 코드에서는 `lowbit` 이라는 이름으로 씁니다. 정의를 그대로 옮기면 이렇게 됩니다.

```ts
// 정의의 맡는 구간을 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const cover = (k: number): [number, number] => {
  const low = k & -k;
  return [k - low, k - 1];
};
```

이제 앞부분의 합이 칸 몇 개로 갈리는지 유도합니다. $r > 0$ 이면 $\text{LSB}(r) > 0$ 이므로
$r' = r - \text{LSB}(r)$ 는 $r$ 보다 작아요. 맡는 구간의 정의에서 $\mathrm{cover}(r) = [\,r',\ r-1\,]$ 이니, 앞 $r$
개는 앞 $r'$ 개와 그 구간으로 겹침 없이 갈립니다.

$$\mathrm{pre}(r) = \mathrm{tree}[r] + \mathrm{pre}\bigl(r - \text{LSB}(r)\bigr), \qquad \mathrm{pre}(0) = 0$$

같은 식을 $r = 7$ 에 펴 봅니다.

<!--proof:math-expand-->

| 식 | cover(k) | tree[k] |
| --- | --- | ---: |
| pre(7) = tree[7] + pre(6) | [6,6] | 7 |
| pre(6) = tree[6] + pre(4) | [4,5] | 11 |
| pre(4) = tree[4] + pre(0) | [0,3] | 10 |
| pre(0) = 0 | 없음 | 0 |

더하면 28 이고, 앞 7 개를 직접 더한 값도 28 입니다. 식을 편 횟수는 3 번이고 7 = 111₂ 의 1 비트도 3 개입니다.

<!--/proof-->

$r$ 에서 $\text{LSB}(r)$ 을 빼는 것은 **이진 표기에서 가장 낮은 1 을 하나 지우는 것**입니다. 그러니 이 식을 펴는
횟수는 $r$ 의 1 비트 개수이고, 그 값은 $\lfloor \log_2 r \rfloor + 1$ 을 넘지 못해요. 여러 $r$ 에서 실제로 세어
대조합니다.

<!--proof:term-count-->

| r | r 의 이진 표기 | prefix(r) 가 더하는 칸 | 칸 수 | 1 비트 개수 |
| ---: | --- | --- | ---: | ---: |
| 1 | 1₂ | 1 | 1 | 1 |
| 2 | 10₂ | 2 | 1 | 1 |
| 3 | 11₂ | 3 2 | 2 | 2 |
| 4 | 100₂ | 4 | 1 | 1 |
| 5 | 101₂ | 5 4 | 2 | 2 |
| 6 | 110₂ | 6 4 | 2 | 2 |
| 7 | 111₂ | 7 6 4 | 3 | 3 |
| 8 | 1000₂ | 8 | 1 | 1 |
| 15 | 1111₂ | 15 14 12 8 | 4 | 4 |
| 16 | 10000₂ | 16 | 1 | 1 |

두 열이 모든 줄에서 같습니다. r 이 1 부터 100,000 까지일 때 칸 수의 최댓값은 16 입니다.

<!--/proof-->

갱신 쪽도 같은 정의에서 나옵니다. 칸 $k$ 가 인덱스 $i$ 를 품는 조건은 $\mathrm{cover}(k)$ 의 정의를 그대로 편
부등식이에요.

$$k - \text{LSB}(k) \le i \le k - 1$$

$i + 1$ 에서 $\text{LSB}$ 를 더해 가는 이동이 이 조건을 만족하는 $k$ 를 작은 것부터 빠짐없이 지납니다. 한 걸음마다
최하위 1 비트의 자리가 하나 이상 올라가므로 걸음 수는 $\lfloor \log_2 N \rfloor + 1$ 이하예요. 전개의 갱신 자리
$i = 2$ 에 조건을 대 봅니다.

<!--proof:math-contain-->

| k | cover(k) | k − LSB(k) <= 2 <= k − 1 | 판정 |
| ---: | --- | --- | --- |
| 1 | [0,0] | 0 <= 2 그리고 2 <= 0 | 거짓 |
| 2 | [0,1] | 0 <= 2 그리고 2 <= 1 | 거짓 |
| 3 | [2,2] | 2 <= 2 그리고 2 <= 2 | 참 |
| 4 | [0,3] | 0 <= 2 그리고 2 <= 3 | 참 |
| 5 | [4,4] | 4 <= 2 그리고 2 <= 4 | 거짓 |

조건이 참인 칸은 칸 3 · 칸 4 이고, add(3, …) 가 지나는 칸과 같습니다.

<!--/proof-->

**같은 정의에서 채우는 비용의 닫힌 형태도 나옵니다.** 두 바퀴 채우기 대신 칸마다 `add` 를 한 번씩 불러 채우면,
칸 $j$ 는 자기가 맡는 인덱스마다 한 번씩, 곧 $\text{LSB}(j)$ 번 고쳐져요. 그러니 총 고침 수는
$\sum_{j=1}^{N} \text{LSB}(j)$ 입니다. $N = 2^m$ 이면 $\text{LSB}(j) = 2^t$ 인 $j$ 가 $t < m$ 에서
$N / 2^{t+1}$ 개이고, $t = m$ 에서는 $j = N$ 하나예요. 그 개수에 값을 곱해 더합니다.

$$\sum_{j=1}^{N} \text{LSB}(j) = \sum_{t=0}^{m-1} 2^t \cdot \frac{N}{2^{t+1}} + N = m \cdot \frac{N}{2} + N = \frac{N}{2}\bigl(\log_2 N + 2\bigr)$$

두 바퀴 채우기는 위 칸이 배열 안에 있는 칸만 한 번씩 넘기므로 $N$ 번보다 적어요. 두 값을 여러 $N$ 에서 세어
대조합니다.

<!--proof:build-cost-->

| N | log₂ N | 칸마다 add 로 채운 고침 수 | (N/2)(log₂N + 2) | 두 바퀴 채우기의 넘김 수 | 배수 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 3 | 20 | 20 | 7 | 2.9 |
| 16 | 4 | 48 | 48 | 15 | 3.2 |
| 1,024 | 10 | 6,144 | 6,144 | 1,023 | 6.0 |
| 65,536 | 16 | 589,824 | 589,824 | 65,535 | 9.0 |

N = 8 이면 LSB(1) … LSB(8) 가 1 2 1 4 1 2 1 8 이라 합이 20 이고, (8/2)(3 + 2) 도 20 입니다. 셋째 열과 넷째 열이 모든 줄에서 같습니다.

<!--/proof-->

**본문의 값만으로는 안 나오는 것이 여기 있습니다.** 파트 1 은 다섯 칸에서 넘기는 횟수 셋을 보였을 뿐인데, 이 식은
임의의 `N` 에서 두 방식의 차이가 $\log_2 N$ 에 비례한다고 말해요. `N = 65,536` 이면 589,824 대 65,535 로
9.0 배이고, 그래서 두 바퀴짜리 채우기를 씁니다.

### 불변식 — 채우기와 갱신이 끝날 때마다 모든 칸은 자기가 맡는 구간의 합을 든다

파트 1 에서 코드가 동작하는 모습을 열세 걸음으로 확인했습니다. 하지만 그것은 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. **무엇이 매번 참으로 남는지**를 문장으로 세우고, 그것이 실제로 유지되는지 확인해 봅시다.

> 채우기가 끝난 시점과 갱신 하나가 끝난 시점마다, 모든 칸 `k` 에 대해 `tree[k]` 는 그 시점의 `arr` 에서 칸 `k` 가
> 맡는 구간 `cover(k)` 의 합입니다. `prefix` 는 `tree` 를 읽기만 하므로 이 성질을 바꾸지 않습니다.

<!--fig:invariant-moment-->
![T8 직후 — 칸 3 만 고쳐졌고 칸 4 는 옛 값](./figs/invariant-moment.svg)

「끝난 시점」을 빠뜨리면 이 문장이 거짓이 됩니다. 갱신이 **진행 중인** 동안은 앞쪽 칸만 고쳐지고 위쪽 칸은 옛
값이라, 그 순간에는 위쪽 칸이 성질을 만족하지 않아요. 그림의 전개 T8 직후가 바로 그 순간입니다. 전개의 열세
걸음마다 칸 값을 그 시점 `arr` 로 정의대로 계산한 합과 대조했습니다.

<!--proof:invariant-check-->

| 걸음 | 그 걸음이 한 일 | 확인한 칸 | 어긋난 칸 | 어긋난 자리 |
| --- | --- | ---: | ---: | --- |
| T1 | 채우기 · 자기 몫 채우기 | 5 | 2 | 칸 2 · 칸 4 |
| T2 | 채우기 · 칸 1 → 칸 2 | 5 | 1 | 칸 4 |
| T3 | 채우기 · 칸 2 → 칸 4 | 5 | 1 | 칸 4 |
| T4 | 채우기 · 칸 3 → 칸 4 | 5 | 0 | 없음 |
| T5 | 질의 [0,4] · prefix(5) | 5 | 0 | 없음 |
| T6 | 질의 [0,4] · prefix(0) | 5 | 0 | 없음 |
| T7 | 갱신 i=2 v=10 · 변화량 만들기 | 5 | 2 | 칸 3 · 칸 4 |
| T8 | 갱신 i=2 v=10 · 칸 3 고치기 | 5 | 1 | 칸 4 |
| T9 | 갱신 i=2 v=10 · 칸 4 고치기 | 5 | 0 | 없음 |
| T10 | 질의 [0,4] · prefix(5) | 5 | 0 | 없음 |
| T11 | 질의 [0,4] · prefix(0) | 5 | 0 | 없음 |
| T12 | 질의 [2,3] · prefix(4) | 5 | 0 | 없음 |
| T13 | 질의 [2,3] · prefix(2) | 5 | 0 | 없음 |

정의는 그 걸음이 끝난 뒤의 arr 로 계산했습니다. T8 은 갱신이 칸 3 만 고친 순간입니다.

<!--/proof-->

어긋난 칸이 있는 걸음은 채우기 도중의 T1 ~ T3 과 갱신 도중의 T7 · T8 뿐이고, 채우기가 끝난 T4 와 갱신이 끝난
T9 에서 0 이 됩니다. 상태를 바꾸는 갈래마다 성질이 유지되는 근거는 이렇습니다.

| 갈래 | 하는 일 | 성질이 유지되는 근거 |
| --- | --- | --- |
| 채우기 첫 바퀴 | `tree[i] = arr[i-1]` | 길이가 1 인 칸은 이것으로 끝나고, 나머지는 둘째 바퀴가 마저 채운다 |
| 채우기 둘째 바퀴 | `tree[j] += tree[i]` | 위 칸이 `j` 인 칸들의 구간과 `j` 자기 한 칸을 이으면 `cover(j)` 가 빈틈없이 채워진다 |
| 둘째 바퀴의 순서 | 작은 번호부터 | 받는 칸의 번호가 주는 칸보다 커서, 넘기는 값이 그 칸의 최종값이다 |
| `add` 가 지나는 칸 | `tree[k] += delta` | 그 칸의 구간이 바뀐 자리를 품어서, 합이 정확히 `delta` 만큼 바뀐다 |
| `add` 가 안 지나는 칸 | 아무것도 안 한다 | 구간에 바뀐 자리가 없으니 합이 바뀔 수 없다 |
| `prefix` | `tree` 를 읽기만 한다 | 상태를 바꾸는 코드가 없다 |

경계에 있는 입력도 확인하고 갑시다. 정본의 답과, 연산을 차례로 적용한 배열에서 정의대로 직접 계산한 값을
대조했어요.

<!--proof:invariant-edges-->

| 경계 | 배열 | 연산 | 답 | 정의로 직접 계산한 값과 |
| --- | --- | --- | --- | --- |
| 연산 목록이 빔 | [1 2 3] | 없음 | [] | 같다 |
| 갱신만 있음 | [1 2 3] | 갱신 i=0 v=99 | [] | 같다 |
| 원소 하나 | [7] | 질의 [0,0] · 갱신 i=0 v=-3 · 질의 [0,0] | [7 -3] | 같다 |
| 한 칸짜리 질의 | [1 2 3 4 5] | 질의 [2,2] | [3] | 같다 |
| 왼쪽 끝이 0 | [1 2 3 4 5] | 질의 [0,2] | [6] | 같다 |
| 음수로 갱신 | [1 2 3] | 갱신 i=0 v=-5 · 질의 [0,2] | [0] | 같다 |
| 같은 자리를 두 번 갱신 | [1 2 3] | 갱신 i=0 v=5 · 갱신 i=0 v=10 · 질의 [0,0] | [10] | 같다 |

원소가 하나면 칸 1 하나가 인덱스 0 을 맡아 채우기 · 질의 · 갱신이 모두 그 칸만 만집니다. 음수가 섞여도 변화량이
음수일 뿐 더하기 하나로 처리돼요. 마지막 줄이 가장 미끄러운 자리입니다. 두 번째 변화량이 **첫 번째 갱신 뒤의 값**에서
나와야 맞고, `arr` 를 함께 고치는 까닭이 그것이에요.

**이제 코드 한 곳을 바꿔 확인해 봅시다.** 성질을 지키던 줄은 `add` 의 걸음 한 줄입니다. 「칸을 하나씩 올라가도
어차피 위쪽 칸을 다 지나지 않나」라는 생각으로 그 걸음을 1 로 바꿔 봅니다.

```ts
for (let k = i; k <= N; k += 1) {
  tree[k] = (tree[k] ?? 0) + delta;
}
```

<!--proof:mutant-step-one-->

| 질의 | 바른 코드 | 걸음을 1 로 바꾼 코드 | 차이 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 질의 [0,4] | 15 | 15 | 0 | 같다 |
| 질의 [0,4] | 22 | 29 | 7 | 어긋난다 |
| 질의 [2,3] | 14 | 14 | 0 | 같다 |

갱신 뒤의 `[0,4]` 만 어긋나고, 어긋난 크기가 변화량과 같습니다. 걸음을 1 로 바꾸면 `add(3, 7)` 이 칸 3 · 칸 4 에
이어 칸 5 까지 지나는데, 칸 5 의 구간은 `[4,4]` 라 인덱스 2 를 품지 않아요. 그 칸이 받지 말아야 할 변화량을 받아
불변식이 깨졌고, 칸 5 를 읽는 질의 `[0,4]` 만 그만큼 커졌습니다. 칸 5 를 읽지 않는 `[2,3]` 은 그대로예요. 최하위
1 비트를 더해 가는 걸음이 **품는 칸만 고른다**는 것이 이 한 줄로 확인됩니다.

### 비용 계산

#### 비용을 세는 과정

한 번 실행할 때 하는 일은 셋뿐입니다. 칸을 채우는 일, 질의에 답하는 일, 갱신을 반영하는 일이에요. 전개의 걸음으로
보면 T1 부터 T4 까지가 채우기, T5 \~ T6 · T10 \~ T11 · T12 \~ T13 이 질의 셋, T7 \~ T9 가 갱신 하나였습니다. 그
걸음들의 배열 접근을 세면 이렇습니다.

<!--proof:walk-cost-->

| 갈래 | 걸음 | 배열 접근 |
| --- | --- | ---: |
| 칸을 채운다 | T1\~T4 | 19 |
| 질의 셋 | T5\~T6 · T10\~T11 · T12\~T13 | 6 |
| 갱신 하나 | T7\~T9 | 6 |
| 합 |  | 31 |

같은 연산 목록을 직접 더하기로 처리하면 13 번입니다.

<!--/proof-->

다섯 칸짜리 입력에서는 채우는 접근이 연산에서 아낀 접근보다 많아서 직접 더하기가 더 적어요. 세는 것은 **배열
접근 전부**입니다. `tree` 의 읽기와 쓰기, 그리고 `arr` 의 읽기와 쓰기예요. 세 갈래의 개수를 식으로 적고 전개 입력에
넣으면 이렇습니다.

<!--proof:perf-formula-->

| 갈래 | 식 | N = 5 를 넣은 값 | 전개에서 잰 값 |
| --- | --- | --- | --- |
| 채우기 | 첫 바퀴 2N + 둘째 바퀴 3H | 2 × 5 + 3 × 3 = 19 | 19 |
| 질의 하나 | 앞 r+1 개의 1 비트 + 앞 l 개의 1 비트 | 2 + 0 · 2 + 0 · 1 + 1 | 2 · 2 · 2 |
| 갱신 하나 | 논리 배열 2 + 지나는 칸마다 2 | 2 + 2 × 2 = 6 | 6 |

채우기는 첫 바퀴가 칸마다 `arr` 읽기와 `tree` 쓰기로 2 번, 둘째 바퀴가 넘기는 칸마다 읽기 둘과 쓰기 하나로 3 번이에요.
질의 하나는 두 호출이 읽은 칸 수의 합이고, 갱신 하나는 `arr` 를 읽고 쓰는 2 번에 지나는 칸마다 읽기와 쓰기 2 번입니다.
셋을 더하면 총식이 됩니다.

$$\text{총 접근 수} = (2N + 3H) + \sum_{\text{질의}} \bigl(\mathrm{pop}(r+1) + \mathrm{pop}(l)\bigr) + \sum_{\text{갱신}} \bigl(2 + 2 \cdot \mathrm{chain}(i+1)\bigr)$$

| 기호 | 뜻 |
| --- | --- |
| `H` | 위 칸 `i + lowbit(i)` 가 `N` 이하인 칸 수 |
| `pop(x)` | `x` 의 1 비트 개수 |
| `chain(k)` | 칸 `k` 부터 최하위 1 비트를 더해 가며 `N` 이하에서 지나는 칸 수 |

과제 규모에 넣으면 이렇게 됩니다.

<!--proof:scale-cost-->

| 갈래 | 세는 것 | 값 | 그 값을 만드는 자리 |
| --- | --- | ---: | --- |
| 칸 채우기 | 2N + 3 × 99,994 | 499,982 | 한 번뿐이다 |
| 질의 하나 | 읽은 칸의 최대 | 32 | [65535,98302] |
| 갱신 하나 | 2 + 2 × 17 | 36 | i = 0 |
| 최악을 다 더하면 | 채우기 + Q × 36 | 4,099,982 | Q = 100,000 |

N = 100,000 이고, 질의와 갱신의 최대는 모든 자리를 넣어 찾은 뒤 셈하는 판으로 한 번씩 실행해 같은 값을 확인했습니다.

<!--/proof-->

추가로 잡는 메모리는 `tree` 의 `N + 1` 칸과 `arr` 의 `N` 칸이에요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 서로 다른 축입니다. 「최악은 `O`, 평균은 `Θ`」처럼
한쪽을 다른 쪽에 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (왼쪽 끝이 0 이고 `r + 1` 이 2 의 거듭제곱인 질의만) | `O(N + Q)` | `Θ(N + Q)` — 질의 하나에 칸 하나 |
| **평균적인 경우** (질의 구간과 갱신 자리의 분포가 필요하다) | `O(N + Q log N)` | 분포를 정하기 전에는 정의되지 않는다 |
| **최악의 경우** (두 끝의 1 비트가 둘 다 많은 질의 · 칸을 많이 지나는 갱신) | `O(N + Q log N)` | `Θ(N + Q log N)` — 실제로 도달한다 |

가운데 줄이 정의되지 않는 까닭은 이 과제가 질의 구간과 갱신 자리가 **어떤 분포로 오는지 말하지 않기** 때문입니다.
분포를 하나 정하면(두 끝을 고르게 뽑는다든지) 평균도 나오지만, 그것은 과제가 준 조건이 아니라 이 글이 놓는
가정이에요. 최선과 최악의 차이는 상수가 아니라 `log N` 배입니다. 같은 배열에서 질의의 모양만 바꿔 보았어요.

<!--proof:perf-best-worst-->

| 질의 | 구간의 칸 수 | r + 1 의 이진 표기 | l 의 이진 표기 | 읽은 칸 |
| --- | ---: | --- | --- | ---: |
| [0,511] | 512 | 1000000000₂ | 0₂ | 1 |
| [511,1022] | 512 | 1111111111₂ | 111111111₂ | 19 |

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 칸 채우기 하나뿐이라 더할 항이 없어요. 질의를 미리
모으지도, 좌표를 다시 매기지도 않습니다.

| 자원 | 총식 | 이루는 것 |
| --- | --- | --- |
| 시간 | `Θ(N + Q log N)` (최악) | 채우기 `Θ(N)` + 연산 `Q` 개 × `O(log N)` |
| 추가 메모리 | `Θ(N)` | `tree` `N + 1` 칸 + `arr` `N` 칸 |

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에 대한 가정도 없으니,
어떤 배열과 어떤 연산 목록을 넣어도 위 상한 아래입니다. 다만 질의 하나의 상한 `2(⌊log₂N⌋ + 1)` 은 타이트하지
않아요.

<!--proof:perf-tight-->

| N | 상한 2(⌊log₂N⌋ + 1) | 모든 짝에서 잰 최대 | 그 짝 |
| ---: | ---: | ---: | --- |
| 1,024 | 22 | 19 | [1022,1022] |
| 100,000 | 34 | 32 | [65535,98302] |

| 보장의 종류 | 뜻 | 이 절차 |
| --- | --- | --- |
| 기댓값이면 | 같은 입력을 두 번 넣었을 때 값이 다를 수 있다 | 해당하지 않는다 |
| 최악 보장이면 | 어떤 입력이든 상한 아래다 | 이쪽이다 |

#### 최악을 만드는 입력

「긴 구간을 묻는 질의가 느리다」는 이 절차에서는 틀린 말입니다. 배열 전체를 묻는 질의는 칸 하나로 끝나요.
`N = 1,024` 에서 질의의 모양을 바꿔 가며 세었습니다.

<!--proof:worst-shape-->

| 질의의 모양 | 구간 | 구간의 칸 수 | l 의 1 비트 | r+1 의 1 비트 | 읽은 칸 |
| --- | --- | ---: | ---: | ---: | ---: |
| 배열 전체 | [0,1023] | 1,024 | 0 | 1 | 1 |
| 왼쪽 절반 | [0,511] | 512 | 0 | 1 | 1 |
| 한 칸 | [500,500] | 1 | 6 | 7 | 13 |
| 읽은 칸이 최대인 짝 | [1022,1022] | 1 | 9 | 10 | 19 |

N = 1,024 에서 읽은 칸이 최대인 짝은 모든 (l, r) 짝을 넣어 찾았습니다. 1022 = 1111111110₂ 이고 1023 = 1111111111₂ 입니다.

<!--/proof-->

가장 긴 구간이 가장 적게 읽고, 가장 많이 읽는 질의는 **한 칸짜리** `[1022,1022]` 입니다. 왼쪽 끝 1022 와 오른쪽
끝 다음 자리 1023 이 둘 다 1 비트가 가득한 수라, 두 호출이 각각 아홉 칸 · 열 칸을 읽어요. 한 칸짜리 `[500,500]`
이 배열 전체보다 열세 배 많이 읽는 것도 같은 까닭입니다. 이진 표기의 1 이 곧 조각이니, 1 이 많을수록 조각이 많아요.

그러니 최악은 **규모와 두 끝의 이진 표기가 함께** 만듭니다. `N` 과 `Q` 를 과제의 최댓값으로 두고, 질의 하나가 가장
많이 읽는 짝과 갱신 하나가 가장 많이 지나는 자리로 작업 목록을 채웠어요.

<!--proof:worst-scale-->

| 작업 목록 | 미리 만들기 | 연산 | 합 | 초당 1 억 번 기준 |
| --- | ---: | ---: | ---: | ---: |
| 갱신만 100,000 개 · 전부 i = 0 | 499,982 | 3,600,000 | 4,099,982 | 0.04 초 |
| 질의만 100,000 개 · 전부 [65535,98302] | 499,982 | 3,200,000 | 3,699,982 | 0.04 초 |
| 둘을 번갈아 | 499,982 | 3,400,000 | 3,899,982 | 0.04 초 |

N = Q = 100,000 입니다. 갱신 i = 0 은 add 가 칸을 가장 많이 지나는 자리이고, 질의 [65535,98302] 는 읽는 칸이 가장 많은 짝입니다.

<!--/proof-->

갱신 하나가 접근 36 번으로 질의 하나의 32 번보다 많아서, 갱신만 채운 목록이 가장 큽니다. 그래도 합이 410 만 번
남짓이라 예산 1 초에 여유가 커요. 접근 밖에 남는 비용은 루프 제어인데, 걸음 수가 접근 수를 넘지 않아 같은
규모입니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하겠습니다. 칸 번호의 최하위 1 비트를 맡는 길이로 삼아 합을 나눠 적었고, 앞부분의
합은 1 비트를 지워 가며 모으며, 갱신은 1 비트를 더해 가며 품는 칸만 고칩니다.

| 순서 | 하는 일 | 규모 |
| ---: | --- | --- |
| 1 | `tree` 를 `N + 1` 칸으로 잡고 칸 0 을 비운다 | 칸 `N + 1` 개 |
| 2 | 자기 몫을 넣고 위 칸에 한 번씩 넘긴다 | 접근 `2N + 3H` 번 |
| 3 | 질의는 1 비트를 지워 가며 모은다 | 읽는 칸 `pop(r + 1) + pop(l)` 개 |
| 4 | 갱신은 1 비트를 더해 가며 고친다 | 고치는 칸 `⌊log₂N⌋ + 1` 개 이하 |

먼저 답이 붙는 문제 하나입니다. 전개의 T5 \~ T6 은 질의 `[0,4]` 를 칸 **둘**만 읽고 답했는데, T12 \~ T13 은 더 짧은
질의 `[2,3]` 을 역시 칸 **둘**로 답했어요. 그런데 「아이디어 상세」 3단계의 표는 앞 4 개의 합이 칸 하나라고
했습니다. `[2,3]` 은 왜 둘일까요?

<!--check:whyTwoCellsEither-->
읽는 칸의 개수를 정하는 것이 **구간의 길이가 아니라 두 끝의 1 비트 개수**이기 때문입니다. `[0,4]` 는 오른쪽이
앞 5 개(`101₂`, 1 비트 둘)라 칸 둘을 읽고 왼쪽이 앞 0 개라 아무것도 안 읽어요. `[2,3]` 은 오른쪽이 앞 4 개
(`100₂`, 1 비트 하나)라 칸 하나, 왼쪽이 앞 2 개(`10₂`, 1 비트 하나)라 칸 하나여서 합쳐 둘입니다. 같은 까닭으로 「최악을 만드는 입력」의 `[1022,1022]` 가
칸 열아홉 개를 읽어요. 두 끝이 모두 1 비트가 가득한 수라 양쪽 호출이 각각 아홉 · 열 개를 읽습니다.

<!--proof:check-two-cells-->

| 걸음 | 질의 | 오른쪽 호출 | 1 비트 | 왼쪽 호출 | 1 비트 | 읽은 칸 |
| --- | --- | --- | ---: | --- | ---: | ---: |
| T5\~T6 | [0,4] | 앞 5 개 | 2 | 앞 0 개 | 0 | 2 |
| T12\~T13 | [2,3] | 앞 4 개 | 1 | 앞 2 개 | 1 | 2 |
| — | [0,2] | 앞 3 개 | 2 | 앞 0 개 | 0 | 2 |
| — | [1,3] | 앞 4 개 | 1 | 앞 1 개 | 1 | 2 |
<!--/check-->

- 이 절차를 구간 **배타적 논리합**에 쓰려면 어느 줄을 고쳐야 할까요? 더하기를 무엇으로 바꾸고 빼기를 무엇으로
  바꿔야 하는지, 그리고 그 둘만 바꾸면 되는 까닭을 적어 보세요. (「최적인 문제의 모양」의 셋째 조건)
- `prefix(op.r + 1)` 에서 `+ 1` 을 빠뜨리면 어떤 질의가 여전히 맞는 답을 낼까요? 전개 입력 `[1 2 3 4 5]` 에서 답이
  안 틀리는 질의를 하나라도 만들 수 있는지, 만들 수 없다면 배열을 어떻게 바꿔야 하는지까지 확인해 보세요. T5 가
  읽은 칸에서 출발하면 됩니다. (「수행으로 알아보는 알고리즘」의 세 번째 조각)

  고쳐야 하는 칸의 개수부터 세어 보세요. (「문제에서 이것을 떠올리게 하는 단서」)

### 구간 합 질의 (동적 갱신)

풀 파일: [`fenwickRangeSum.ts`](./fenwickRangeSum.ts) · 테스트: [`fenwickRangeSum.test.ts`](./fenwickRangeSum.test.ts) · 실행: `bun test src/algorithms/array/fenwickRangeSum/fenwickRangeSum.test.ts`

#### 한 줄 요약

> 정수 배열과 갱신·질의 연산 목록을 받아, **각 질의(구간 합)의 결과**를 순서대로 담은 배열을 반환한다.

#### 스토리

온라인 게임의 점수 집계 서버를 담당하는 재원은 실시간으로 들어오는 두 종류의 요청을 처리해야 한다.

첫 번째는 특정 플레이어의 점수를 새 값으로 바꾸는 갱신 요청이다. 두 번째는 플레이어 구간 $[l, r]$에 속한 모든 플레이어의 점수 합계를 묻는 질의 요청이다.

요청이 섞여서 들어오기 때문에, 질의를 처리할 때마다 이미 반영된 갱신이 결과에 영향을 준다. 재원은 모든 질의의 결과를 순서대로 모아 반환해야 한다.

#### 함수 인터페이스

```ts
export type FenwickOp =
  | { type: "update"; i: number; v: number }
  | { type: "query"; l: number; r: number };

export function fenwickRangeSum(A: number[], ops: FenwickOp[]): number[];
```

- `A` — 초기 정수 배열.
- `ops` — 순서대로 처리할 연산 목록. `update`는 점 갱신, `query`는 구간 합 요청이다.
- 반환 — `query` 연산의 결과만 등장 순서대로 담은 배열.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `A`의 길이)
- $0 \leq Q \leq 100{,}000$ (여기서 $Q$는 `ops`의 길이)
- $-10{,}000 \leq A[i],\, v \leq 10{,}000$ (정수)
- `update` 연산: $0 \leq i < N$
- `query` 연산: $0 \leq l \leq r < N$
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

연산은 두 종류다.

- **update** $(i, v)$: $A[i] \leftarrow v$ (덮어쓰기, 누적이 아님).
- **query** $(l, r)$: $\displaystyle\sum_{k=l}^{r} A[k]$를 계산한다.

연산은 입력 순서대로 처리된다. `update`는 이후 모든 연산에 즉시 반영된다. `query` 결과만 모아 반환하며, `update`는 결과 배열에 포함되지 않는다. `query`가 하나도 없으면 빈 배열을 반환한다.

#### 예시

```ts
fenwickRangeSum(
  [1, 2, 3, 4, 5],
  [
    { type: "query",  l: 0, r: 4 },   // 15  — 초기 전체 합 1+2+3+4+5
    { type: "update", i: 2, v: 10 },  // A는 이제 [1,2,10,4,5]
    { type: "query",  l: 0, r: 4 },   // 22  — 갱신 후 전체 합
    { type: "query",  l: 2, r: 3 },   // 14  — A[2]+A[3]=10+4
  ],
); // [15, 22, 14]

fenwickRangeSum([7], [{ type: "query", l: 0, r: 0 }]);
// [7]  — 단일 원소, l=r=0

fenwickRangeSum([1, 2, 3], []);
// []  — 연산 없음, 빈 배열 반환

fenwickRangeSum(
  [1, 2, 3],
  [{ type: "update", i: 0, v: -5 }, { type: "query", l: 0, r: 2 }],
); // [0]  — [-5,2,3]의 합, 음수 갱신 후 질의
```
