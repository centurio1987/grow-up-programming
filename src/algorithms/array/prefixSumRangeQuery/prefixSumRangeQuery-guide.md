# prefixSumRangeQuery — 구간 합을 두 칸의 뺄셈으로 끝내는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 질의마다 구간을 직접
더하는 방법에서 표 두 칸을 빼는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로 동작하는
코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열이 질의 도중에 **한 번도 바뀌지 않는다면**, 같은 칸을 여러 질의가 몇 번이고 다시 더하는
일을 없앨 수 있어요. 왼쪽 끝을 언제나 0 으로 고정한 합만 미리 표에 적어 두고, 질의가 오면
그 표에서 두 칸을 읽어 빼는 것입니다. 표에 적는 값을 **누적합**이라고 부르고 `P` 로 적을게요.

```text
A 의 값       3  1  4  1  5  9        원래 배열, 여섯 칸
인덱스        0  1  2  3  4  5

P 의 값    0  3  4  8  9 14 23        P 의 칸 i 에 A 의 앞 i 개의 합을 담는다
칸         0  1  2  3  4  5  6        칸이 하나 더 많다
           └ 앞 0 개의 합, 그러니까 아무것도 더하지 않은 0 이다
```

`A[1] + A[2] + A[3]` 을 구해 봅시다. 앞 네 개의 합에서 앞 한 개의 합을 덜어 내면 가운데 세
개만 남아요.

```text
P[4] = 3 + 1 + 4 + 1 = 9      앞 네 개의 합
P[1] = 3                      앞 한 개의 합
────────────────────────
P[4] − P[1] = 9 − 3 = 6       남은 것이 1 + 4 + 1 = 6 이다
```

두 값이 공통으로 갖고 있던 앞부분이 뺄셈에서 지워지는 것이 전부입니다. 표를 만들 때 각 칸은
**직전 칸에 값 하나를 더한 것**이라 배열을 한 번 지나가면 끝나고, 질의 하나는 몇 칸짜리
구간이든 **읽기 두 번과 뺄셈 한 번**이에요.

```text
전처리  배열을 한 번 지나며 표를 채운다     덧셈 n 번
질의    표에서 두 칸을 읽어 뺀다            구간 길이와 무관하게 뺄셈 1 번
        └ n 칸짜리 배열과 q 개짜리 질의에서 연산이 n + q 번, 곧 O(n + q) 다
```

여기에 조건 하나가 붙습니다. **배열이 바뀌면 이 표가 그대로 거짓이 돼요.** 원소 하나를
고치면 그 자리부터 뒤의 칸이 전부 어긋나서 표를 처음부터 다시 만들어야 합니다.

```text
A[1] 을 1 에서 7 로 고쳤다면

  옛 표   0  3  4  8  9 14 23
  새 표   0  3 10 14 15 20 29
             └ 칸 2 부터 끝까지 여섯 칸이 전부 달라진다
```

문제가 「배열은 질의 중 변경되지 않는다」고 못 박은 것이 그래서 결정적입니다. 이 조건 하나가
이 절차의 전부를 떠받쳐요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 합**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값을 **건너뛰지 않고** 전부 더한 수예요.
- **연속 부분 배열**과 부분집합의 차이. 여기서 다루는 것은 연속된 한 토막입니다. 흐릿하면
  [`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-problem.md)
  를 먼저 봅니다.
- **정적 배열**과 **동적 배열**의 차이 — 여기서 정적이라는 말은 「질의를 처리하는 동안 원소가
  바뀌지 않는다」는 뜻이지 크기가 고정이라는 뜻이 아닙니다.
- 배열을 한 번 지나가는 `for` 루프와, 배열 인덱스가 `0` 부터 시작한다는 것.

「구간 합을 구한다」와 「합이 조건을 만족하는 구간을 찾는다」는 다른 문제입니다. 뒤쪽은
[`subarraySumEqualsK`](../subarraySumEqualsK/subarraySumEqualsK-problem.md) 가 다루는 것이고,
이 글은 **주어진 구간의 합을 답하는 것**만 합니다.

```text
[3 1 4 1 5 9] 에서
  구간 [1,3] 의 합을 답하라        6         ← 이 글이 하는 것. 구간은 문제가 준다
  합이 6 인 구간을 찾아라          [1,3]     ← 찾아야 할 것이 구간이다. 다른 문제다
```

### 아이디어 상세 — 누적합을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function prefixSumRangeQuery(
  A: number[],
  queries: Array<[number, number]>,
): number[];
```

- 입력: 정수 배열 `A` 와 질의 목록 `queries`. 각 질의 `[l, r]` 은 **양끝을 포함하는** 인덱스
  구간입니다.
- 출력: 각 질의의 구간 합을 **입력 순서 그대로** 담은 배열. 질의가 없으면 빈 배열.
- 제약: `1 ≤ n ≤ 100,000`, `0 ≤ q ≤ 100,000`, `−10,000 ≤ A[i] ≤ 10,000`,
  `0 ≤ l ≤ r ≤ n−1`. 시간 1초, 메모리 256 MB.

이 글이 쓰는 기호는 다섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 배열 `A` 의 길이 | `n ≤ 100,000` |
| `q` | 질의의 개수 | `q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값. 질의 도중 바뀌지 않습니다 | `−10,000` 이상 `10,000` 이하 |
| `l` · `r` | 질의 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ n−1` |
| `P[i]` | `A` 의 앞 `i` 개 원소의 합. 글과 코드에서 모두 `P` 로 씁니다 | 칸이 `n+1` 개 |

가장 먼저 떠오르는 방법으로 시작합시다. 질의가 오면 그 구간을 왼쪽부터 오른쪽까지 직접 더하는
것이에요. 질의가 하나뿐이면 이것으로 충분합니다.

```ts
const answers = queries.map(([l, r]) => {
  let s = 0;
  for (let k = l; k <= r; k++) s += A[k] as number;   // 구간을 직접 더한다
  return s;
});
```

이 방법의 비용은 **질의 하나가 지나는 칸 수의 합**입니다. 모든 질의가 배열 전체를 묻는 입력을
넣으면 질의마다 `n` 칸을 지나요.

| `n` = `q` | 지나는 칸 수의 합 | 초당 1억 번 기준 |
| --- | --- | --- |
| 1,000 | 1,000,000 | 0.01초 |
| 10,000 | 100,000,000 | 1초 |
| **100,000** | **10,000,000,000** | **100초** |

100억 번입니다. 단순 연산을 초당 1억 번으로 잡아도 100초가 걸려요. 제약이 10만인데 이
방법으로는 1초 안에 못 끝냅니다. 그러면 이 100억 안에 같은 일을 몇 번이나 되풀이하는지 봅시다.

```text
A 의 값   3  1  4  1  5  9
인덱스    0  1  2  3  4  5

질의 [1,3] 이 더한 칸        1 2 3
질의 [0,5] 가 더한 칸    0 1 2 3 4 5      칸 1·2·3 을 또 더했다
질의 [0,2] 가 더한 칸    0 1 2            칸 1·2 를 세 번째로 더했다
질의 [2,5] 가 더한 칸        2 3 4 5      칸 2 를 네 번째로 더했다
                             └ 칸 2 하나가 네 질의에 전부 들어 있다
```

질의가 겹칠 때마다 겹친 부분을 처음부터 다시 더합니다. 그런데 「앞에서부터 여기까지의 합」을
한 번만 만들어 두면, 겹친 부분은 **두 값이 공통으로 들고 있는 앞부분**이 되어 뺄셈 하나로
지워져요.

```text
앞 여섯 개의 합   3 + 1 + 4 + 1 + 5 + 9 = 23     [0,5] 의 답
앞 두 개의 합     3 + 1                 = 4
──────────────────────────────────────────
23 − 4 = 19                                     [2,5] 의 답이 뺄셈 하나로 나온다
```

이제 두 방식을 같은 입력에 실제로 실행해 **연산 수**를 셉니다. 방식 A 는 질의마다 구간을
직접 더하는 것이고, 방식 B 는 앞에서부터의 합을 한 번 만들어 두고 빼는 것이에요.

<!--proof:cost-two-ways-->

```text
질의   직접 더하기  누적합
[1,3]            3       1
[0,5]            6       1
[4,4]            1       1
[0,2]            3       1
[2,5]            4       1

방식 A  질의마다 구간을 직접 더한다      덧셈 17 번 · 전처리 0 번
방식 B  왼쪽 끝을 0 으로 고정한 합을 저장한다  덧셈 6 번 · 뺄셈 5 번
        └ 답은 [6,23,5,8,19] 로 같고, 질의 하나의 비용이 구간 길이를 따라 늘지 않는다
```

17 대 11 입니다. 답은 둘 다 같고 연산이 6 번 줄었어요. 여기서 관찰할 것은 **오른쪽 열이 전부
1** 이라는 것 하나입니다 — 방식 B 에서 질의 하나의 비용이 구간의 길이와 아무 상관이 없어요.

```text
구간의 칸 수   3  6  1  3  4        질의 다섯의 길이가 제각각이다
방식 A 의 비용  3  6  1  3  4        길이를 그대로 따라간다
방식 B 의 비용  1  1  1  1  1        길이를 안 본다
                └ 질의가 열 배로 늘어도 오른쪽 줄은 1 그대로다
```

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「질의의 답을 미리 다 계산해
표에 담아 두면 되지 않나」가 그것이에요. 그러면 어떤 질의가 와도 표를 한 번 읽고 끝납니다.

<!--proof:cost-precompute-all-->

```text
      n  모든 답을 담는 표  누적합 표
      6                 21          7
    100              5,050        101
  1,000            500,500      1,001
100,000      5,000,050,000    100,001

└ 왼쪽은 n 이 열 배가 되면 백 배가 되고, 오른쪽은 열 배가 된다
```

`n = 100,000` 이면 칸이 50억 개입니다. 정수 하나를 8 바이트로 잡아도 40 GB 라 256 MB 제한에
들어가지 않아요. **모든 `(l, r)` 짝을 담으려니 짝의 수가 `n²` 규모로 늘어난 것**이고, 그래서
후보를 하나 줄여야 합니다.

```text
왼쪽 끝과 오른쪽 끝을 둘 다 자유롭게 두면   짝이 n(n+1)/2 개다
왼쪽 끝을 0 으로 고정하면                  값이 n+1 개로 준다
                                           └ 남은 질문은 「고정하고도 답이 나오는가」다
```

여기서 진짜 개념이 나옵니다. **왼쪽 끝을 0 으로 고정한 합**만 저장하고, 임의의 구간은 그 값
둘의 차이로 만드는 것이에요. `P[i]` 를 `A` 의 앞 `i` 개 원소의 합으로 두면 이렇게 됩니다.

```text
P[0] = 0                            앞 0 개, 빈 구간의 합
P[i] = P[i−1] + A[i−1]              직전 칸에 값 하나를 더한 것

질의 [l,r] 의 답 = P[r+1] − P[l]    앞 r+1 개에서 앞 l 개를 덜어 낸다
```

이 정의를 실제 입력의 일곱 칸에 걸음마다 적용해 봅시다. 각 칸이 직전 칸에서 덧셈 한 번으로
나오는 것을 확인하고 갑니다.

| 칸 `i` | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 더하는 값 `A[i−1]` | — | 3 | 1 | 4 | 1 | 5 | 9 |
| 직전 칸 `P[i−1]` | — | 0 | 3 | 4 | 8 | 9 | 14 |
| `P[i]` | **0** | **3** | **4** | **8** | **9** | **14** | **23** |

각 상태의 크기가 여기서 정해집니다. 표는 `n+1` 칸이고, 질의 하나가 읽는 칸은 **정확히 두 개**
예요. 그 두 칸의 자리도 질의가 오는 순간 `l` 과 `r+1` 로 곧바로 정해집니다.

```text
표의 칸 수      n + 1 개                       n=6 이면 7 칸
질의당 읽기     정확히 2 칸                    구간이 1 칸이든 n 칸이든 같다
읽는 자리       왼쪽은 l, 오른쪽은 r+1         계산이 아니라 인덱스를 그대로 쓴다
```

이 표가 실제로 쓸모 있으려면 **모든 질의를 같은 식 하나로** 답해야 합니다. 쉬운 경우와 불안한
경우를 나눠서 값으로 확인해 봅시다. 쉬운 경우는 두 끝이 다 배열 안쪽에 있을 때예요.

```text
질의 [1,3]   P[4] − P[1] = 9 − 3 = 6
             표의 칸 4 와 칸 1 을 읽는다. 둘 다 표 안쪽이다
             실제 값 1 + 4 + 1 = 6 과 같다
```

불안한 경우는 둘입니다. 왼쪽 끝이 `0` 이라 **덜어 낼 앞부분이 없는** 질의와, 오른쪽 끝이
배열의 마지막이라 **표의 마지막 칸을 읽어야 하는** 질의예요.

```text
질의 [0,2]   P[3] − P[0] = 8 − 0 = 8         P[0]=0 이 「덜어 낼 것이 없다」를 맡는다
             특수한 분기가 필요 없다          실제 값 3 + 1 + 4 = 8 과 같다

질의 [2,5]   P[6] − P[2] = 23 − 4 = 19       r+1 = 6 이라 표의 마지막 칸을 읽는다
             칸이 n+1 개라 표 밖으로 안 나간다  실제 값 4 + 1 + 5 + 9 = 19 와 같다
```

왜 빠뜨리는 칸이 없는지는 루프의 종료 조건으로 말할 수 있습니다. 전처리 루프는 `i` 가 `0`
에서 시작해 `n` 이 될 때까지 실행되고, 한 번 실행할 때마다 `P[i+1]` 을 **정확히 한 번** 씁니다.

```text
루프가 끝난 시점에 i = n 이다
  쓴 칸        P[1] P[2] … P[n]      n 개, 각각 정확히 한 번
  안 쓴 칸     P[0]                  루프에 들어가기 전에 0 으로 채웠다
               └ 표의 n+1 칸이 빠짐없이 한 번씩 정해진다
```

이제 「왼쪽 끝을 0 으로 고정한 합을 **모든 칸에** 저장한다」가 정말 가장 적은 연산인지 값으로
확인합니다. 저장을 `B` 칸마다 하나씩만 하는 절차를 따로 만들어 `B` 를 넷으로 두고 같은 질의
목록에서 세었어요. `B` 칸마다 저장하면 저장점과 질의의 끝 사이에 남는 칸은 질의 때 직접
더해야 합니다.

<!--proof:cost-block-->

```text
저장 단위  저장 칸  질의 덧셈  덧셈·뺄셈 합
B=1              7          0            11
B=2              4          3            14
B=3              3          7            18
B=6              2         19            30

└ B 를 키우면 저장 칸이 줄고 연산이 는다. 답은 넷 다 같다
```

`B` 를 키울수록 저장 칸은 줄고 연산은 늡니다. 이 문제의 메모리 제한이 256 MB 이고 `n+1` 이
100,001 칸이라 저장을 아낄 이유가 없으니, **저장 단위 1 이 답입니다.**

```text
얻은 절차 한 벌
  1. 표를 n+1 칸으로 잡고 P[0] 에 0 을 넣는다
  2. i 를 0 에서 n−1 까지 옮기며 P[i+1] 에 P[i] + A[i] 를 넣는다
  3. 질의 [l,r] 이 오면 P[r+1] − P[l] 을 답한다
       └ 10만 칸 · 10만 질의에서 100억 번이던 연산이 20만 번이 된다
```

### 수행으로 알아보는 알고리즘 — 여섯 칸을 채우고 다섯 질의를 답한다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const A = [3, 1, 4, 1, 5, 9];
const queries: Array<[number, number]> = [[1, 3], [0, 5], [4, 4], [0, 2], [2, 5]];
// 이 절이 끝나면 [6, 23, 5, 8, 19] 가 나와야 한다
```

왜 하필 이 다섯 질의일까요? 앞의 셋은 흔한 모양이고, 뒤의 둘이 **표의 양 끝 칸을 각각 읽게**
하기 때문이에요. `[0,2]` 는 `P[0]` 을, `[2,5]` 는 `P[6]` 을 읽습니다. `[4,4]` 로 한 칸짜리
구간까지 넣어 두면 이 절차가 답하는 구간의 모양이 다 나와요.

```text
절차 전체를 한 장으로

    표 P 를 n+1 칸으로 잡고 P[0] 에 0 을 넣는다
    i 를 0 에서 n−1 까지 옮기며:
        P[i+1] 에 P[i] + A[i] 를 넣는다                     ① 전처리
    질의 [l,r] 을 순서대로 받으며:
        P[r+1] − P[l] 을 결과 목록에 덧붙인다               ② 질의
```

#### 1. 빈 구간의 합을 0 으로 두고 표를 잡는다

표의 크기와 첫 칸이 이 조각의 전부입니다. 두 줄이지만 이 두 줄이 뒤의 모든 분기를 없애요.

```ts
const n = A.length;
const P = new Array<number>(n + 1);
P[0] = 0;
```

`n` 이 아니라 `n + 1` 인 이유는 오른쪽 끝이 배열의 마지막인 질의 때문입니다. `r = n−1` 이면
`P[r+1] = P[n]` 을 읽어야 하는데, 칸이 `n` 개면 그 자리가 표 밖이에요.

```text
n = 6 인 배열에서 질의 [2,5] 를 답하려면

  칸이 7 개다 (0 … 6)    P[6] 이 있다      → 23 − 4 = 19
  칸이 6 개다 (0 … 5)    P[6] 이 없다      → 읽을 칸이 없다
                          └ 배열의 끝을 묻는 질의가 전부 여기서 걸린다
```

`P[0] = 0` 은 **빈 구간의 합**입니다. 아무것도 더하지 않았으니 0 이고, 이 한 칸이 왼쪽 끝
`0` 인 질의를 특수한 경우로 가르지 않게 해 줘요.

#### 2. 앞에서부터 한 번 더해 표를 채운다

표를 채우는 것이 전처리의 전부입니다. 매번 처음부터 다시 더하지 않고 **직전 칸에 값 하나만**
더해요.

```ts
for (let i = 0; i < n; i++) {
  // ① 전처리 — 직전 칸에 A[i] 를 한 번만 더해 다음 칸을 채운다
  P[i + 1] = (P[i] as number) + (A[i] as number);
}
```

이 조각만 실행하면 표가 이렇게 쌓입니다. 여섯 걸음을 `T2` 부터 `T7` 로 적었어요.

<!--viz:build-->
```text
걸음   i   P[i]   A[i]   P[i+1]   채운 칸 수
T2     0      0      3        3            2
T3     1      3      1        4            3
T4     2      4      4        8            4
T5     3      8      1        9            5
T6     4      9      5       14            6
T7     5     14      9       23            7
       └ 덧셈이 걸음마다 정확히 한 번이다. 여섯 걸음에 덧셈 여섯 번
```

<!--result:build=[0, 3, 4, 8, 9, 14, 23]-->

여기서 가장 중요한 줄은 `P[i + 1] = P[i] + A[i]` 입니다. 왼쪽이 `i+1` 이고 오른쪽이 `i` 라는
것, 그러니까 **쓰는 칸이 읽는 칸보다 하나 뒤**라는 것이 이 줄의 전부예요. 둘을 같은 인덱스로
적으면 표가 한 칸씩 밀려 뒤가 전부 어긋납니다.

#### 멈춤 — 표를 배열과 같은 길이로 잡으면 왼쪽 끝이 0 인 질의만 깨진다

여기서 헷갈리기 쉬운 포인트는 표의 길이입니다. 「누적합이면 원래 배열과 칸 수가 같아야
자연스럽지 않나」로 읽기 쉬워요. 그 정의로 가면 표는 이렇게 됩니다.

```text
같은 길이 표 T[i] = A[0..i]           칸이 여섯 개다

  A 의 값    3  1  4  1  5  9
  T 의 값    3  4  8  9 14 23
             └ 「앞 i+1 개의 합」이라 P 보다 한 칸씩 앞서 있다

  질의 [l,r] 의 답 = T[r] − T[l−1]    왼쪽에서 하나 앞의 칸을 뺀다
```

식이 `T[l−1]` 이 되는 것이 문제입니다. `l = 0` 이면 `T[−1]` 을 읽어야 하는데 그 칸이 없어요.
다섯 질의에 두 정의를 각각 실행해 보면 이렇게 나옵니다.

<!--proof:pause-same-length-->

```text
질의   정본  같은 길이 표
[1,3]     6             6  답이 같다
[0,5]    23           NaN  값이 아니다
[4,4]     5             5  답이 같다
[0,2]     8           NaN  값이 아니다
[2,5]    19            19  답이 같다

└ 왼쪽 끝이 0 인 질의 둘만 깨진다. 나머지 셋은 답이 같아서 알아채지 못한다
```

`l = 0` 인 질의 둘만 값이 아닌 것을 냈고 나머지 셋은 답이 같습니다. **테스트에 왼쪽 끝이 0 인
질의가 없으면 이 정의는 통과해요** — 그래서 알아채지 못한 채로 남습니다.

```text
고치는 길이 둘이다
  (가) if (l === 0) 분기를 더한다        질의마다 조건 검사가 하나 는다
  (나) 표를 n+1 칸으로 잡고 P[0]=0 을 넣는다   분기가 아예 없어진다
       └ (나)는 「없는 칸」 대신 「빈 구간의 합」이라는 뜻 있는 값을 그 자리에 둔다
```

#### 3. 저장한 두 칸을 빼서 질의 하나를 답한다

표가 다 채워졌으면 질의 하나는 두 줄로 끝납니다. 읽고, 빼고, 결과 목록에 덧붙여요.

```ts
const result: number[] = [];
for (const [l, r] of queries) {
  // ② 질의 — 저장해 둔 두 칸을 읽어 뺀다. 왼쪽 끝이 0 이어도 같은 식이다
  result.push((P[r + 1] as number) - (P[l] as number));
}
```

첫 질의 `[1,3]` 에 이 조각만 실행한 결과입니다.

```text
들어올 때   l=1  r=3          표는 0 3 4 8 9 14 23 로 다 채워져 있다
읽는 칸     P[r+1] = P[4] = 9
            P[l]   = P[1] = 3
빼면        9 − 3 = 6         결과 목록이 [6] 이 된다
            └ 구간이 세 칸인데 읽은 칸은 둘이다
```

#### 멈춤 — 오른쪽 끝을 한 칸 앞에서 읽으면 그 칸의 값이 0 일 때 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 오른쪽 끝의 `+1` 입니다. 「왼쪽은 `P[l]` 이니 오른쪽도 `P[r]`
이면 되겠지」로 읽기 쉬운데, 두 자리의 뜻이 서로 달라요.

```text
P[l]      앞 l 개의 합 = 인덱스 l−1 까지    구간에 안 들어가는 부분이다
P[r+1]    앞 r+1 개의 합 = 인덱스 r 까지    구간의 오른쪽 끝을 포함해야 한다
          └ 왼쪽은 「직전까지」, 오른쪽은 「끝까지」라 두 자리의 규칙이 다르다
```

`P[r]` 로 읽으면 `A[r]` 하나가 답에서 빠집니다. 그러니 **`A[r]` 이 0 인 질의에서는 답이 안
틀려요.** 다섯 입력에 두 코드를 각각 실행해 확인합니다.

<!--proof:pause-right-end-->

```text
입력           질의   바른 코드  한 칸 앞을 읽은 코드
[3 1 4 1 5 9]  [1,3]          6                     5  답이 다르다
[3 1 4 1 5 9]  [0,5]         23                    14  답이 다르다
[3 1 4 1 5 9]  [4,4]          5                     0  답이 다르다
[3 1 0 4]      [0,2]          4                     4  답이 같다
[2 0 0 7]      [1,2]          0                     0  답이 같다

└ 아래 둘은 오른쪽 끝의 값이 0 이라 답이 같다. 그래서 이 변경이 그대로 남는다
```

아래 두 줄이 이 오해가 오래 남는 이유입니다 — 0 이 섞인 입력으로 시험하면 우연히 맞아요.
문제의 제약이 `−10,000 ≤ A[i] ≤ 10,000` 이라 0 은 얼마든지 들어올 수 있습니다.

두 조각을 하나로 이어 고정 입력에 실행하면 열두 걸음이 나옵니다. 앞의 일곱이 표를 만드는
걸음이고 뒤의 다섯이 질의를 답하는 걸음이에요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 결과 목록을 빈 배열로 시작하는
한 줄뿐이에요 — 질의가 하나도 없으면 그 값이 그대로 답이 됩니다.

```ts
export function prefixSumRangeQuery(
  A: number[],
  queries: Array<[number, number]>,
): number[] {
  const n = A.length;
  // 표의 칸 `i` 에는 A 의 앞 `i` 개 원소의 합을 담는다. 칸이 n+1 개라 오른쪽 끝이
  // 배열의 마지막인 질의도 표 밖으로 나가지 않는다.
  const P = new Array<number>(n + 1);
  // 빈 구간의 합은 0 이다. 이 한 칸이 왼쪽 끝 0 을 특수한 경우로 가르지 않게 한다.
  P[0] = 0;

  for (let i = 0; i < n; i++) {
    // ① 전처리 — 직전 칸에 A[i] 를 한 번만 더해 다음 칸을 채운다.
    P[i + 1] = (P[i] as number) + (A[i] as number);
  }

  const result: number[] = [];
  for (const [l, r] of queries) {
    // ② 질의 — 저장해 둔 두 칸을 읽어 뺀다. 왼쪽 끝이 0 이어도 같은 식이다.
    result.push((P[r + 1] as number) - (P[l] as number));
  }

  return result;
}
```

```text
prefixSumRangeQuery([3, 1, 4, 1, 5, 9], [[1,3], [0,5], [4,4], [0,2], [2,5]])
  →  [6, 23, 5, 8, 19]
prefixSumRangeQuery([1, 2, 3], [])           →  []
prefixSumRangeQuery([-1, 2, -3, 4], [[0,3]]) →  [2]
prefixSumRangeQuery([7], [[0,0]])            →  [7]
```

### 알아 두면 좋은 개념 — 역원이 있는 연산

이 절차가 하는 일을 한 문장으로 줄이면 **「덧셈을 뺄셈으로 취소한다」** 입니다. 앞에서부터
쌓아 둔 두 값에서 공통 부분이 지워지는 것이 뺄셈 덕분이고, 그 뺄셈이 곧 덧셈의 **역원**이에요.
어떤 연산에 역원이 있으면 접두 표의 차이가 그대로 구간의 값이 됩니다.

```text
쌓아 둔 값 두 개                     차이를 만드는 연산      구간의 값
P[l]   = A[0] + … + A[l−1]      ─┐
                                  ├→  뺄셈                  A[l] + … + A[r]
P[r+1] = A[0] + … + A[r]        ─┘
        └ 공통으로 들어 있는 앞부분이 뺄셈에서 사라진다
```

같은 표를 다른 연산에 적용해 보면 이 성질이 어디서 끊기는지 확인됩니다.

| 연산 | 역원 | 접두 표의 차이로 구간 값이 나오는가 |
| --- | --- | --- |
| 덧셈 | 뺄셈 | 나옵니다. 이 글이 그것입니다 |
| 배타적 논리합(XOR) | 자기 자신 | 나옵니다. 두 번 하면 지워집니다 |
| 곱셈 | 나눗셈 | 값에 `0` 이 없을 때만 나옵니다 |
| 최댓값·최솟값 | 없음 | 안 나옵니다. 큰 값을 「빼는」 방법이 없습니다 |

마지막 줄이 다른 자료구조가 필요해지는 자리입니다. 구간 최솟값을 묻는 문제가
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-problem.md) 이나
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-problem.md) 으로 가는
이유가 이것이에요 — 최댓값에는 역원이 없어서 두 칸의 차이로 구간을 만들 수 없습니다.

```text
같은 이름을 다시 만나는 자리
  누적 XOR      구간의 XOR 을 두 칸의 XOR 로            역원이 자기 자신이다
  차분 배열     구간 갱신을 두 칸의 덧셈으로            누적합의 반대 방향이다
  구간 최솟값   접두 표로는 안 되어 다른 표를 만든다     역원이 없다
```

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 표와 뺄셈을 식으로 어떻게
적는지, 무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 배열이 **질의를 처리하는 동안 바뀌지 않습니다.** 원소 하나가 바뀌면 표의 뒤쪽이 통째로
  어긋나서 다시 만들어야 해요.
- 질의가 **연속 구간**을 묻습니다. 인덱스를 골라 담는 질의라면 앞에서부터의 합으로 만들 수
  없어요.
- 구간에 매기는 값의 연산에 **역원이 있습니다.** 합·XOR 이 그렇고, 최댓값은 아닙니다.
- 질의 수 `q` 가 **한 번의 전처리 비용을 갚을 만큼** 많습니다. 질의가 한두 개면 그냥 직접
  더하는 편이 적어요.

```text
네 조건이 코드의 모양을 그대로 정한다
  정적 배열        → 표를 다시 만드는 코드가 아예 없다
  연속 구간        → 두 끝 l 과 r 만 받으면 상태가 끝난다
  역원이 있는 연산 → 질의가 뺄셈 한 번이다
  질의가 많다      → 전처리 n 번을 q 개가 나눠 진다
```

마지막 줄에 경계가 있습니다. 전처리 `n` 번을 쓰고 질의당 1 번이니 총 `n + q` 이고, 직접
더하는 방법은 최악 `q·n` 이에요. 그러니 `q` 가 1 이고 구간이 짧으면 전처리가 오히려 손해입니다.

```text
n = 100,000 일 때 (덧셈·뺄셈만 센다)
  질의 1 개, 구간 10 칸    직접 10 번        표를 만들면 100,001 번
  질의 100,000 개          직접 최악 100억   표를 만들면 200,000 번
                           └ 경계는 「질의가 몇 개인가」다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "배열은 변경되지 않는다"  "정적"  "미리 주어진다"   ← 결정적인 신호다
  "구간 [l, r] 의 합"  "부분합"  "누적"
  "질의가 Q 개 주어진다"  "각 질의에 대해 답하라"     ← 질의가 많다는 뜻이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N×Q 가 못 들어간다
  값의 범위가 좁아 전체 합이 정수 범위를 안 넘는다

반대로 이런 말이 보이면 해당하지 않는다
  "i 번째 원소를 v 로 바꾼다"  "갱신 질의"           ← 배열이 바뀐다
  "구간의 최솟값"  "구간의 최댓값"                    ← 역원이 없다
```

두 번째 무리가 보이면 다른 절차로 갑니다. 갱신이 섞이면
[`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-problem.md) 쪽이고, 최솟값이면
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-problem.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **CPython 의 `itertools.accumulate`** — 표준 라이브러리가 이 전처리를 그대로 제공합니다.
  공식 문서에 실린 등가 파이썬 코드가 `total = func(total, element)` 한 줄 누적이고, 그것이
  이 글의 전처리 루프와 같은 자리예요.
  ([`itertools.accumulate`](https://docs.python.org/3/library/itertools.html#itertools.accumulate),
  조회 2026-08-29)
- **NumPy 의 `numpy.cumsum`** — 배열 하나를 받아 같은 길이의 누적합 배열을 돌려줍니다. 이
  글의 표와 다른 점은 **앞에 0 칸을 두지 않는다**는 것이라, 구간 합을 구하려면 왼쪽 끝이 0 인
  경우를 따로 다뤄야 해요 — 「멈춤」에서 값으로 확인한 그 자리입니다.
  ([`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-29)
- **OpenCV 의 `cv::integral`** — 같은 아이디어를 2차원으로 넓힌 **적분 영상**입니다. 사각형
  영역의 합을 네 칸의 덧셈·뺄셈으로 답해요. 헤더에 선언이 있습니다.
  ([`modules/imgproc/include/opencv2/imgproc.hpp`](https://github.com/opencv/opencv/blob/4.x/modules/imgproc/include/opencv2/imgproc.hpp),
  조회 2026-08-29)

```text
세 사례와 이 문제의 관계

  앞의 둘   전처리만 제공한다. 질의의 뺄셈은 쓰는 쪽이 직접 적는다
  OpenCV    2차원이라 뺄셈이 한 번이 아니라 네 항의 덧셈·뺄셈이다
            └ 1차원의 두 칸이 2차원에서 네 칸이 되는 것이 확장의 전부다
```

#### 경쟁 설계와의 대조

같은 목표(구간 합 질의에 답하기)를 노리는 다른 절차로 **펜윅 트리**(이진 인덱스 트리)가
있습니다. 칸 `j` 가 자기 아래 여러 원소의 합을 들고 있어서, 앞 `k` 개의 합을 `k` 의 1 비트
수만큼의 칸을 읽어 만들어요. 갱신은 그 원소를 덮는 칸들만 고치면 끝납니다.

```text
같은 질문에 두 설계가 답하는 방식

  누적합 표   P[r+1] − P[l]              칸 2 개를 읽는다. 갱신은 표 전체를 다시 만든다
  펜윅 트리   prefix(r+1) − prefix(l)    칸 log n 개씩 읽는다. 갱신은 칸 log n 개만 고친다
              └ 펜윅은 질의에서 칸을 더 읽고 갱신에서 훨씬 적게 고친다
                섞인 비율이 어느 쪽의 접근 수가 적은지를 정한다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은
`n = 1,024` 이고 `A[i] = (37i) mod 101`, 질의는 `q = 1,024` 개로 `a = (37i) mod n` 과
`b = (91i) mod n` 을 만들어 작은 쪽을 왼쪽 끝으로 뒀어요. 갱신 `k` 번째는 `A[(53k) mod n]` 에
`(k mod 7) + 1` 을 더하고, 갱신은 질의 사이에 고르게 끼웠습니다.

| 갱신 횟수 | 누적합 표 | 펜윅 트리 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 0 회 | **5,121** | 23,548 | 누적합 표가 4.6 배 적습니다 |
| 6 회 | **23,571** | 23,650 | 누적합 표가 근소하게 적습니다 |
| 7 회 | 26,646 | **23,662** | **여기서 순서가 뒤집힙니다** |
| 1,024 회 | 3,153,921 | **37,884** | 펜윅 트리가 83 배 적습니다 |

**저장 칸은 둘 다 1,025 개로 같습니다.** 메모리에서는 갈리지 않아요 — 갈리는 것은 시간이고,
그 경계가 이 입력에서 **갱신 7 회**입니다.

```text
경계가 그 자리인 이유

  갱신 하나의 값   누적합 표 3,075 번(표를 통째로 다시 만든다)  펜윅 트리 14 번
                   (3,153,921 − 5,121) ÷ 1,024 = 3,075
                   (37,884 − 23,548) ÷ 1,024 = 14
  시작점의 차이    누적합 표 5,121   펜윅 트리 23,548           차이 18,427
  18,427 ÷ (3,075 − 14) ≈ 6.02      → 갱신 일곱 번째에 뒤집힌다
```

**이 절차가 내주는 것은 갱신입니다.** 원소 하나가 바뀌면 표를 처음부터 다시 만들어야 해서
갱신 하나가 전처리 한 번과 같은 비용이에요. 그 대신 얻는 것이 셋입니다.

```text
누적합 표가 얻는 것
  질의 비용   읽기 2 번으로 고정      펜윅은 질의마다 log n 칸씩 읽는다
  구현        루프 두 개, 분기 없음    펜윅은 j & -j 비트 연산이 들어간다
  갱신 0 회   5,121 대 23,548          전처리 자체가 4.6 배 적다
              └ 갱신이 없다는 것이 이 문제의 제약이므로 이 열이 이 문제의 답이다
```

문제가 「배열은 질의 중 변경되지 않는다」고 못 박았으니 이 문제에서는 누적합 표가 답입니다.
같은 지문에서 **갱신 질의가 하나라도 섞이는 순간** 이 판정은 다시 해야 해요.

### 수식 정의와 유도

표를 기호로 정의합니다. 칸 `0` 은 빈 구간의 합이고, 그다음부터는 직전 칸에 값 하나를 더한
것입니다.

$$P[0] = 0, \qquad P[i] = P[i-1] + A[i-1] \quad (1 \le i \le n)$$

```text
정의를 값에 넣어 봅니다 — A 의 값 3 1 4 1 5 9

  P[0] = 0
  P[1] = P[0] + A[0] = 0 + 3 = 3
  P[2] = P[1] + A[1] = 3 + 1 = 4
  P[3] = P[2] + A[2] = 4 + 4 = 8
       └ 정의 하나가 칸 하나를 정하고, 정의가 두 항만 본다
```

이 재귀 정의에서 닫힌 형태를 유도합니다. 주장은 `P[i]` 가 앞 `i` 개 원소의 합이라는 것이에요.

$$P[i] = \sum_{k=0}^{i-1} A[k]$$

```text
기저 (i = 0)
  좌변 P[0] = 0                       정의가 그렇게 정했다
  우변 k = 0 부터 −1 까지의 합         더할 것이 없으므로 0
  둘이 같다

단계 (i−1 에서 참이면 i 에서도 참)
  P[i] = P[i−1] + A[i−1]              정의
       = (A[0] + … + A[i−2]) + A[i−1]  가정을 P[i−1] 에 넣었다
       = A[0] + … + A[i−1]            항을 하나 덧붙인 것이다
  이것이 k = 0 부터 i−1 까지의 합이다
```

다음은 뺄셈이 구간 합을 내는 이유입니다. `l ≤ r` 이므로 앞 `r+1` 개의 합은 앞 `l` 개의 합과
그 뒤의 구간으로 **겹치지 않게** 갈립니다.

$$\sum_{k=0}^{r} A[k] = \sum_{k=0}^{l-1} A[k] + \sum_{k=l}^{r} A[k]$$

```text
갈라지는 자리를 값으로 봅니다 — l = 2, r = 5

  k = 0 … 5 의 합   3 + 1 + 4 + 1 + 5 + 9 = 23      P[6]
  k = 0 … 1 의 합   3 + 1                 = 4       P[2]
  k = 2 … 5 의 합           4 + 1 + 5 + 9 = 19
                    └ 앞의 둘이 겹치는 항이 없고, 셋을 합치면 23 = 4 + 19 이다
```

왼쪽 항이 `P[r+1]` 이고 오른쪽 첫 항이 `P[l]` 이므로, 양변에서 `P[l]` 을 빼면 구간 합이
남습니다.

$$\sum_{k=l}^{r} A[k] = P[r+1] - P[l]$$

```text
이 식을 위의 값에 다시 넣어 봅니다 — l = 2, r = 5

  P[r+1] − P[l] = P[6] − P[2] = 23 − 4 = 19
  손으로 더한 값                4 + 1 + 5 + 9 = 19
                                └ 두 줄이 같다. 임의의 l ≤ r 에서 같은 이유가 위 유도다
```

식의 `P` 를 코드에서도 `P` 로 그대로 씁니다. 정의를 그대로 옮기면 이렇습니다.

```ts
// 닫힌 형태를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const P = (A: number[], i: number): number => {
  let s = 0;
  for (let k = 0; k < i; k++) s += A[k] as number;
  return s;
};
```

이 조각은 칸 하나를 만드는 데 `i` 번을 더하므로 표 전체를 만들면 `n(n+1)/2` 번입니다. 실제
절차는 직전 칸을 쓰기 때문에 `n` 번이에요 — 같은 값을 만드는 두 방법의 차이가 그것입니다.

$$\text{총 연산} = \underbrace{n}_{\text{전처리 덧셈}} + \underbrace{q}_{\text{질의 뺄셈}} = n + q$$

```text
두 항이 서로 독립이다
  n 항   배열을 한 번 지난다        질의가 몇 개든 이 항은 그대로다
  q 항   질의마다 뺄셈 하나          배열이 얼마나 크든 이 항은 그대로다
         └ 그래서 곱이 아니라 합이다. 직접 더하기는 여기가 곱이었다
```

직접 더하는 방법의 최악은 모든 질의가 배열 전체를 묻는 것이라 `q · n` 입니다. 두 닫힌
형태에 규모를 넣고 실제 실행과 대조했어요.

<!--proof:cost-scale-->

```text
  n = q  직접 더하기(실측)             q·n  누적합(실측)    n + q
      6                 36              36            12       12
    100             10,000          10,000           200      200
  1,000          1,000,000       1,000,000         2,000    2,000
100,000    (실행하지 않음)  10,000,000,000       200,000  200,000
```

실측값이 닫힌 형태와 세 규모에서 정확히 같습니다. 오른쪽 두 열도 마찬가지예요. 제약 규모인
`n = q = 100,000` 에서 100억 대 20만이니 **5만 배**입니다.

```text
n = q = 100,000 에서
  직접 더하기 최악   q·n   = 10,000,000,000
  누적합             n + q =        200,000
  10,000,000,000 ÷ 200,000 = 50,000 배
```

### 불변식 — 표의 칸 i 는 언제나 앞 i 개 원소의 합이다

파트 1 에서 코드가 동작하는 것을 열두 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> 전처리 루프가 `i` 번째 반복을 마친 시점마다, 표의 칸 `0` 부터 `i+1` 까지는 각각 `A` 의 앞
> 그 칸 수만큼의 원소를 더한 값입니다. 그리고 루프가 끝난 뒤 배열이 바뀌지 않으므로, 그
> 성질은 질의를 몇 개 처리하든 그대로 남습니다.

```text
       0    1    2   …    i+1              i+2 … n
 P     ●    ●    ●   …    ●                  ?
       └ 여기까지가 「앞 몇 개의 합」이다      ← 앞 문장
         P[0]=0 부터 시작해 한 칸씩 늘어난다
         질의는 표를 읽기만 한다              ← 뒤 문장
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 표가 정의와 어긋나지 않는다는 것이고, 뒤 문장이
**질의 순서와 개수가 답을 바꾸지 않는다**는 것을 말해요. 둘 중 하나만 빠져도 「같은 질의를
두 번 물으면 같은 답이 나온다」는 근거가 사라집니다.

**출발점부터 봅시다.** 루프에 들어가기 전 `P[0] = 0` 이고, 「앞 0 개의 합은 0」 이 참입니다.
그 뒤 한 반복마다 칸 하나가 늘어나요.

| 반복 `i` | 하는 일 | 앞 문장이 유지되는 근거 |
| --- | --- | --- |
| `i = 0` | `P[1] = P[0] + A[0]` | 앞 0 개의 합에 `A[0]` 을 더했으니 앞 1 개의 합이다 |
| `i = k` | `P[k+1] = P[k] + A[k]` | 직전 반복이 `P[k]` 를 앞 `k` 개의 합으로 만들어 뒀다 |
| 루프 종료 | `i = n` | `P[1]` 부터 `P[n]` 까지 각각 정확히 한 번씩 정해졌다 |

뒤 문장은 질의 루프가 지킵니다. 그 루프는 `P` 를 읽기만 하고 쓰지 않으며 `A` 도 건드리지
않아요. 상태를 바꾸는 코드가 없으니 첫 질의가 보는 표와 마지막 질의가 보는 표가 같습니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 질의 목록이 빔 | 질의 루프가 한 번도 실행되지 않는다 | `[]` |
| 원소 하나 `[7]`, 질의 `[0,0]` | 표가 `0 7` 두 칸, `P[1] − P[0]` | `[7]` |
| 한 칸짜리 구간 `l = r` | `P[r+1] − P[r]` 이라 `A[r]` 하나가 남는다 | `A[r]` |
| 왼쪽 끝이 `0` | `P[0] = 0` 을 빼므로 `P[r+1]` 그대로다 | 앞 `r+1` 개의 합 |
| 음수가 섞임 `[-1 2 -3 4]` | 뺄셈이 부호를 그대로 가져온다 | 정의와 같다 |
| 같은 질의 반복 | 표를 읽기만 하므로 매번 같은 값 | 같은 답이 반복 |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 표를 채우는 그 한 줄이에요. 「어차피 칸마다
값을 넣는 것이니」라는 생각으로 직전 칸을 더하는 부분을 빼 봅니다. 한 줄만 바뀝니다.

```ts
for (let i = 0; i < n; i++) {
  P[i + 1] = A[i] as number;   // 직전 칸을 더하지 않는다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-no-accumulate-->

```text
질의   바른 코드  누적을 뺀 코드  차이
[1,3]          6              -2    -8
[0,5]         23               9   -14
[4,4]          5               4    -1
[0,2]          8               4    -4
[2,5]         19               8   -11

└ 다섯 질의가 전부 다른 답을 낸다. 표의 칸이 합이 아니라 원소 하나가 됐다
```

첫 줄이 음수인 것이 이 변경의 정체를 그대로 보입니다. 표가 `0 3 1 4 1 5 9` 가 되어 칸 4 의
값 1 이 칸 1 의 값 3 보다 작아졌고, 그래서 뺄셈이 음수를 냈어요. 원소가 전부 음이 아닌 정수인
입력에서 구간 합이 음수로 나오면 표가 「앞 몇 개의 합」이 아니라는 뜻입니다.

```text
바른 표    0  3  4  8  9 14 23     칸이 오른쪽으로 갈수록 커진다(원소가 음이 아닐 때)
깨진 표    0  3  1  4  1  5  9     칸이 커졌다 작아졌다 한다 = 합이 아니다
              └ 이 성질 하나로 표가 망가진 것을 알아볼 수 있다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 두 종류뿐입니다 — 표를 채우며 더하는 것과, 표를 읽어 빼는 것이에요.
전개의 값으로 확인하면 덧셈은 T2부터 T7까지 여섯 번이고 뺄셈은 T8부터 T12까지 다섯 번이었습니다.

```text
덧셈   T2 T3 T4 T5 T6 T7      i 가 0 부터 5 까지 한 칸씩 → 정확히 6 번 = n
뺄셈   T8 T9 T10 T11 T12      질의 하나에 한 번         → 정확히 5 번 = q
                              └ 합 11 번. 「아이디어 상세」의 방식 B 와 같다
```

덧셈은 반복마다 정확히 하나이므로 `n` 번이고, 뺄셈은 질의마다 정확히 하나이므로 `q` 번입니다.
둘 다 **입력의 내용과 무관하게 개수가 정해져요** — 값이 크든 작든, 구간이 길든 짧든 같습니다.

```text
총식 = 덧셈 + 뺄셈 + 배열 읽기 + 배열 쓰기
       └ n    └ q    └ 2n + 2q   └ n + 1
                  └ 전처리에서 P[i]·A[i] 로 2n, 질의에서 두 칸씩 2q

       총연산 = n + q + (2n + 2q) + (n + 1) = 4n + 3q + 1
       표를 만들고 읽는 산술 연산(덧셈 + 뺄셈)만 보면 정확히 n + q 다
```

여기서 센 것은 **표를 만들고 읽는 연산 전부**입니다. 추가로 잡는 메모리는 표 하나뿐이라
`n + 1` 칸이고, 입력 배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (질의가 전부 한 칸짜리) | `O(n + q)` | `Θ(n + q)` |
| **평균적인 경우** (입력 분포와 무관하다) | `O(n + q)` | `Θ(n + q)` |
| **최악의 경우** (질의가 전부 배열 전체) | `O(n + q)` | `Θ(n + q)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 최선과 최악의 차이가 **상수 계수에도 나타나지
않아요** — 연산 수가 `n + q` 로 딱 고정이라, 질의의 모양을 어떻게 바꿔도 값이 같습니다.

```text
비교 대상과 나란히 놓으면 이 성질이 확인된다
  직접 더하기   최선 q 번        최악 q·n 번      질의의 모양이 비용을 정한다
  누적합        최선 n + q 번    최악 n + q 번    질의의 모양이 비용을 안 바꾼다
                └ 이 줄이 이 절차를 쓰는 이유다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 표 만들기 하나뿐이라는 것이 이
절차의 특징이에요 — 정렬도 좌표압축도 하지 않습니다.

```text
총식 = Θ(n + q) 시간 + Θ(n) 추가 메모리
       └ 전처리 Θ(n) + 질의 q 개 × Θ(1)     └ 표 n+1 칸. 입력 배열은 읽기만 한다

n = q = 100,000 이면 덧셈·뺄셈이 정확히 200,000 번, 표는 100,001 칸이다
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에
대한 가정도 하지 않으니, 어떤 배열과 어떤 질의를 넣어도 연산이 `n + q` 번이라는 것이 그대로
약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
                └ 여기서는 상한이 아니라 정확한 값이라 더 강하다
```

#### 최악을 만드는 입력

연산을 최대로 만드는 방법은 하나뿐입니다 — **`n` 과 `q` 를 제약의 최댓값으로 두는 것**이에요.
질의의 모양은 아무 상관이 없습니다. 그것을 값으로 확인해 봅시다.

```text
n = 1,000 · q = 1,000 에서 질의의 모양만 바꿔 본다

  전부 배열 전체    [0,999] 를 1,000 번      가장 긴 구간이다
  전부 한 칸짜리    [0,0] [1,1] … [999,999]  가장 짧은 구간이다
  길이가 늘어남     [0,0] [0,1] … [0,999]    평균 길이가 500.5 다
                    └ 직접 더하기는 이 셋이 크게 갈린다. 누적합은 어떨까
```

세 모양의 연산 수를 실제로 셌습니다.

<!--proof:worst-shape-->

```text
질의의 모양 (n=1,000 · q=1,000)  직접 더하기  누적합
전부 배열 전체 — 가장 긴 구간      1,000,000   2,000
전부 한 칸짜리                         1,000   2,000
길이가 하나씩 늘어나는 구간          500,500   2,000

└ 오른쪽 열이 세 줄 다 같다. 질의의 모양이 비용을 바꾸지 못한다
```

**「긴 구간을 묻는 질의가 느리다」는 이 절차에서 거짓입니다.** 물려받은 통념이 여기서는
성립하지 않아요 — 첫 줄과 둘째 줄에서 직접 더하기는 1,000 배 차이가 나는데 누적합은 같은
2,000 입니다.

```text
그래서 최악은 질의의 모양이 아니라 규모로만 만들어진다
  n = 100,000 · q = 100,000     덧셈·뺄셈 200,000 번, 표 100,001 칸
  1 초 제한에 견주면 여유가 크다. 이 절차에서 시간 초과가 나면 원인은 다른 곳이다
       └ 남는 비용은 결과 배열 q 칸을 만드는 것이고, 그것은 어떤 절차를 써도 똑같이 든다
```

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 질의마다 구간을 직접 더하던 것을 **표 두 칸의
뺄셈**으로 바꿨고, 배열이 정적이라 표를 한 번만 만들면 되며, 표의 칸이 언제나 「앞 몇 개의
합」이라는 것이 답의 근거입니다.

```text
표를 n+1 칸으로 잡는다 → 앞에서부터 한 번 더해 채운다 → 질의마다 두 칸을 빼서 답한다
        └ P[0]=0 이 분기를 없앤다   └ 덧셈 n 번        └ 뺄셈 q 번, 구간 길이와 무관
```

먼저 답이 붙는 문제 하나입니다. 전개의 T10 은 질의 `[4,4]` 를 답했는데, 구간이 한 칸뿐인데도
표에서 **두 칸**을 읽었어요. 한 칸짜리 구간이면 `A[4]` 를 그냥 읽는 편이 빠르지 않을까요?

```text
T10   l=4  r=4    P[5] = 14   P[4] = 9   답 5
                  └ 읽은 칸이 둘이다. A[4] 를 직접 읽으면 하나다
```

<!--check:single-cell-->
빠릅니다. 다만 그러려면 `l === r` 인지 검사하는 분기가 질의마다 하나 늘어요. 질의 `q` 개에
검사 `q` 번을 더해서 한 칸짜리 질의에서만 읽기 하나를 줄이는 것이라, 한 칸짜리 질의가 절반을
넘지 않으면 오히려 연산이 늡니다.

```text
분기가 없을 때    질의 하나 = 읽기 2 + 뺄셈 1              = 3
분기가 있을 때    한 칸짜리 = 검사 1 + 읽기 1              = 2
                  그 밖    = 검사 1 + 읽기 2 + 뺄셈 1      = 4
                  └ 한 칸짜리가 전체의 절반이면 평균이 3 으로 같아진다
```

더 중요한 것은 「멈춤」에서 확인한 자리와 같은 이유입니다. 분기를 하나 더하면 그 분기가 틀릴
자리가 하나 생겨요. `P[0] = 0` 을 둔 것도 분기를 없애려던 것이었습니다.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 「알아 두면 좋은 개념」          3 → 「경쟁 설계와의 대조」
  2 → 「불변식」의 깨뜨려 보기
```

- 배타적 논리합(XOR)에는 역원이 자기 자신이라 접두 표가 성립합니다. `A = [3, 1, 4, 1, 5, 9]`
  의 누적 XOR 표를 손으로 채우고, 구간 `[2,5]` 의 XOR 을 두 칸으로 구해 보세요.
- 표를 채우는 줄을 `P[i + 1] = P[i] + A[i + 1]` 로 바꾸면 어떤 답이 나올까요? 배열 끝에서
  무슨 일이 생기는지까지 확인해 보세요.
- 갱신이 섞인 문제에서 누적합 표를 쓰되 **표를 다시 만들지 않는** 방법을 하나 생각해 보세요.
  갱신을 모아 두었다가 질의 때 반영하는 길이 있습니다. 그때 질의 비용이 얼마가 되는지가
  답입니다.
