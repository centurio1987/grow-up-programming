# 누적합 — 구간 합을 두 칸의 뺄셈으로 끝내는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 질의마다 구간을
직접 더하는 방법에서 출발해 누적합 배열의 두 칸을 빼는 방법까지 가고, 그 방법을 단계마다 값으로 푼 뒤,
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열이 질의 도중에 **한 번도 바뀌지 않는다면**, 같은 칸을 여러 질의가 몇 번이고 다시 더하는 일을 없앨
수 있어요. 앞에서부터의 합을 한 번만 적어 두고, 질의가 오면 그중 두 칸을 읽어 빼는 것입니다. 앞에서부터의
합을 칸마다 적은 배열을 **누적합 배열**(prefix sum array)이라고 부르고 `P` 로 적어요. 이 글은 끝까지 그
이름 하나로 부릅니다.

누적합 배열의 칸 `i` 에는 **입력 배열 `A` 의 앞 `i` 칸을 더한 값**이 들어 있습니다. 칸 0 은 앞 0 칸,
곧 아무것도 더하지 않은 0 이고, 마지막 칸은 배열 전체의 합이에요. 그래서 칸이 `A` 보다 하나 많습니다.
`A = [3 1 4 1 5 9]` 아래에 누적합 배열을 놓고, 구간 `[1,3]` 의 합을 두 칸으로 구하는 모습을 그리면
이렇습니다.

<!--fig:concept-prefix-->
![A 아래에 놓은 누적합 배열 P 와, 구간 [1,3] 의 합을 P[4] − P[1] 로 구하는 모습](./figs/concept-prefix.svg)

아래 장에서 괄호가 질의 구간이고, ▲ 가 읽는 두 칸 `P[1]` 과 `P[4]` 예요. 앞 네 칸의 합에서 앞 한 칸의
합을 덜어 내면 가운데 세 칸만 남습니다.

<!--proof:concept-query-->

```text
P[4] = 3 + 1 + 4 + 1 = 9  앞 4 칸의 합
P[1] = 3                  앞 1 칸의 합
P[4] − P[1] = 9 − 3 = 6   남은 것이 1 + 4 + 1 = 6 이다
```

두 값이 함께 들고 있던 앞부분이 뺄셈에서 지워지는 것이 전부입니다. 누적합 배열의 칸은 **직전 칸에 값
하나를 더한 것**이라 배열을 한 번 지나가면 다 채워지고, 질의 하나는 구간이 몇 칸이든 **읽기 두 번과
뺄셈 한 번**이에요. 배열 길이가 `n` 이고 질의가 `q` 개면 연산이 `n + q` 번이고, 결과만 적으면
`O(n + q)` 입니다.

여기에 조건 하나가 붙습니다. **배열이 바뀌면 누적합 배열이 그대로 거짓이 돼요.** 원소 하나를 고치면 그
자리부터 뒤의 칸이 전부 어긋납니다.

<!--proof:concept-update-->

```text
A[1] 을 1 에서 7 로 고치면

  고치기 전 P  [0 3 4 8 9 14 23]
  고친 뒤 P    [0 3 10 14 15 20 29]
    └ 칸 2 부터 칸 6 까지 5 칸이 달라진다. 모두 A[1] 을 더한 칸이다
```

그래서 이 방법은 배열이 질의 동안 바뀌지 않는다는 조건 하나에 기대고 있습니다. 바뀌면 누적합 배열을
처음부터 다시 채워야 해요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **구간 합**이 무엇인지. 인덱스 `l` 부터 `r` 까지의 값을 **건너뛰지 않고** 전부 더한 수예요.
- **연속 부분 배열**과 부분집합의 차이. 여기서 다루는 것은 연속된 한 토막입니다. 흐릿하면
  [`longestSubarrayAtMostSum`](../longestSubarrayAtMostSum/longestSubarrayAtMostSum-guide.md)
  를 먼저 봅니다.
- **정적 배열**과 **동적 배열**의 차이 — 여기서 정적이라는 말은 「질의를 처리하는 동안 원소가
  바뀌지 않는다」는 뜻이지 크기가 고정이라는 뜻이 아닙니다.
- 배열을 한 번 지나가는 `for` 루프와, 배열 인덱스가 `0` 부터 시작한다는 것.

「구간을 받아 합을 답한다」와 「합을 받아 구간을 찾는다」는 다른 과제입니다. 뒤쪽은
[`subarraySumEqualsK`](../subarraySumEqualsK/subarraySumEqualsK-guide.md) 가 다루는 것이고, 이 글은
**주어진 구간의 합을 답하는 것**만 합니다. 같은 배열 `[3 1 4 1 5 9]` 에서 두 과제를 나란히 놓으면
이렇습니다.

<!--proof:prereq-two-tasks-->

| 과제 | 주는 것 | 답 |
| --- | --- | --- |
| 구간 합 질의 — 이 글이 하는 것 | 구간 [1,3] | 합 6 |
| 합이 6 인 구간 찾기 | 합 6 | 구간 [1,3] · [3,4] |

### 아이디어를 떠올리는 과정 — 질의마다 직접 더하기에서 누적합 배열까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열과 구간 질의 목록을
받아서, 질의마다 구간 합을 돌려줍니다.

```ts
function prefixSumRangeQuery(
  A: number[],
  queries: Array<[number, number]>,
): number[];
```

- 입력: 정수 배열 `A` 와 질의 목록 `queries`. 각 질의 `[l, r]` 은 **양끝을 포함하는** 인덱스
  구간입니다.
- 출력: 각 질의의 구간 합을 **입력 순서 그대로** 담은 배열. 질의가 없으면 빈 배열.
- 규모: 배열 길이 `n` 과 질의 수 `q` 가 각각 100,000 까지, 원소는 −10,000 이상 10,000 이하, 질의는
  `0 ≤ l ≤ r ≤ n−1` 입니다. 비용은 흔한 채점 환경의 예산인 1 초 · 256 MB 에 대어 잽니다.

이 글이 쓰는 기호는 다섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 배열 `A` 의 길이 | `1 ≤ n ≤ 100,000` |
| `q` | 질의의 개수 | `0 ≤ q ≤ 100,000` |
| `A[i]` | 배열의 `i` 번째 값. 질의 도중 바뀌지 않습니다 | `−10,000` 이상 `10,000` 이하 |
| `l` · `r` | 질의 구간의 왼쪽 끝 · 오른쪽 끝. 양끝을 포함합니다 | `0 ≤ l ≤ r ≤ n−1` |
| `P[i]` | 누적합 배열의 칸 `i` — `A` 의 앞 `i` 칸의 합. 글과 코드에서 모두 `P` 로 씁니다 | 칸이 `n+1` 개 |

가장 먼저 떠오르는 방법은 질의가 오면 그 구간을 왼쪽부터 오른쪽까지 직접 더하는 것이에요. 질의가 하나뿐이면
이것으로 충분합니다.

```ts
const answers = queries.map(([l, r]) => {
  let s = 0;
  for (let k = l; k <= r; k++) s += A[k] as number; // 구간을 직접 더한다
  return s;
});
```

이 방법은 답을 틀리지 않습니다. 비용은 **질의마다 지나는 칸 수의 합**이고, 모든 질의가 배열 전체를 묻는
입력을 넣으면 질의마다 `n` 칸을 지나요.

<!--proof:origin-cost-->

| n = q | 지나는 칸 수의 합 | 초당 1 억 번 기준 | 구한 방법 |
| ---: | ---: | ---: | --- |
| 1,000 | 1,000,000 | 0.01 초 | 실행해서 셌다 |
| 10,000 | 100,000,000 | 1 초 | 실행해서 셌다 |
| 100,000 | 10,000,000,000 | 100 초 | q·n 으로 냈다 |

모든 질의가 배열 전체를 묻는 입력입니다. 실행해서 센 n = 1,000 · 10,000 에서 지나는 칸 수가 q·n 과 정확히 같았습니다.

<!--/proof-->

`n` 과 `q` 가 상한 100,000 이면 칸을 100 억 번 지나고, 초당 1 억 번으로 잡아도 100 초입니다. 예산 1 초의
백 배예요. 그 100 억 안에 같은 일을 몇 번이나 되풀이하는지 보려고, 원소 여섯 개짜리 `A = [3 1 4 1 5 9]`
에 질의 다섯을 걸고 질의마다 더한 칸을 적었습니다.

<!--proof:origin-overlap-->

| 질의 | 더한 칸의 인덱스 | 더한 횟수 |
| --- | --- | ---: |
| [1,3] | 1 2 3 | 3 |
| [0,5] | 0 1 2 3 4 5 | 6 |
| [4,4] | 4 | 1 |
| [0,2] | 0 1 2 | 3 |
| [2,5] | 2 3 4 5 | 4 |

다섯 질의가 더한 칸은 모두 17 개인데 서로 다른 칸은 6 개뿐입니다. 칸 2 는 다섯 질의 중 4 개에 들어 있어 4 번 더했습니다.

<!--/proof-->

질의가 겹칠 때마다 겹친 칸을 처음부터 다시 더합니다. 그런데 「앞에서부터 여기까지의 합」을 한 번만 만들어
두면, 겹친 부분은 **두 합이 함께 들고 있는 앞부분**이 되어 뺄셈 하나로 지워져요.

<!--proof:origin-reuse-->

```text
앞 6 칸의 합  3 + 1 + 4 + 1 + 5 + 9 = 23  [0,5] 의 답
앞 2 칸의 합  3 + 1 = 4                   [0,1] 의 답
두 합의 차    23 − 4 = 19                 [2,5] 의 답이 뺄셈 하나로 나온다
```

이제 두 방식을 같은 입력에 실제로 실행해 **연산 수**를 셉니다. 직접 더하기는 질의마다 구간을 더하는
것이고, 누적합 배열은 앞에서부터의 합을 한 번 채워 두고 질의마다 두 칸을 빼는 것이에요.

<!--proof:origin-two-ways-->

| 질의 | 구간 칸 수 | 직접 더하기의 덧셈 | 누적합 배열의 뺄셈 |
| --- | ---: | ---: | ---: |
| [1,3] | 3 | 3 | 1 |
| [0,5] | 6 | 6 | 1 |
| [4,4] | 1 | 1 | 1 |
| [0,2] | 3 | 3 | 1 |
| [2,5] | 4 | 4 | 1 |

직접 더하기는 덧셈 17 번이고, 누적합 배열은 채우는 덧셈 6 번과 뺄셈 5 번으로 11 번입니다. 답은 둘 다 6 23 5 8 19 입니다.

<!--/proof-->

17 대 11 입니다. 여기서 관찰할 것은 **오른쪽 열이 전부 1** 이라는 것 하나예요. 누적합 배열에서 질의
하나의 비용은 구간의 길이와 상관이 없습니다. 그 관찰을 이름으로 세우기 전에 더 단순한 후보부터 시험해
봅시다. 「질의의 답을 미리 다 계산해 두면 되지 않나」가 그것이에요. 그러면 어떤 질의가 와도 한 칸을
읽고 끝납니다. 담아야 할 칸이 몇 개인지 셌습니다.

<!--proof:origin-precompute-->

| n | 모든 짝의 답을 담는 칸 | 누적합 배열의 칸 |
| ---: | ---: | ---: |
| 6 | 21 | 7 |
| 100 | 5,050 | 101 |
| 1,000 | 500,500 | 1,001 |
| 100,000 | 5,000,050,000 | 100,001 |

n = 100,000 이면 칸 하나를 8 바이트로 잡아 40,000,400,000 바이트, 약 40 GB 입니다. 예산 256 MB 의 149 배가 넘습니다.

<!--/proof-->

모든 `(l, r)` 짝을 담으려니 짝의 수가 `n²` 규모로 늘었습니다. 지금까지 해 본 방법을 차례로 놓으면
이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

모든 답을 담는 후보는 두 끝을 다 자유롭게 둔 것이 칸을 불렸습니다. 왼쪽 끝을 0 으로 고정하면 담을
값이 `n + 1` 개로 줄고, 나머지 구간은 그 값 둘의 차이로 만들 수 있어요. 남은 방법에 이름을 붙이면
**누적합 배열**입니다. 누적합 배열을 어떻게 잡고, 채우고, 질의에 쓰는지는 다음 절에서 실현하는 순서대로
확인합니다.

### 아이디어 상세 — 누적합 배열

이 아이디어를 한 문장으로 줄이면 이렇습니다. **`A` 의 앞 `i` 칸의 합을 칸 `i` 에 담은 누적합 배열을
질의 전에 한 번 채워 두고, 질의 `[l, r]` 마다 `P[r+1] − P[l]` 을 답합니다.** 실현 순서대로 나누면 단계가
셋이고, 앞의 둘은 질의 전에 한 번, 마지막 하나는 질의마다 합니다.

| 단계 | 언제 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 1단계 누적합 배열 잡기 | 질의 전에 한 번 | `n + 1` 칸을 잡고 칸 0 에 빈 구간의 합 0 을 넣는다 | — |
| 2단계 앞에서부터 채우기 | 질의 전에 한 번 | 칸 `i + 1` 에 `P[i] + A[i]` 를 넣는다 | 1단계의 칸 0 |
| 3단계 두 칸의 차로 답하기 | 질의마다 | `P[r+1] − P[l]` 을 답한다 | 2단계가 채운 누적합 배열 |

#### 먼저 알아 둘 개념 — 누적합 배열

단계로 들어가기 전에, 누적합 배열이 어떻게 생겼고 어떻게 읽는지를 먼저 잡고 갑니다. 칸 번호가 `A` 의
인덱스와 하나씩 어긋나 있어서, 이 모양을 머릿속에 그리지 못하면 뒤의 `r + 1` 과 `l` 이 왜 그 자리인지
따라가기 어렵기 때문이에요.

##### 쉬운 말 정의

누적합 배열은 **`A` 를 왼쪽 끝에서부터 잘라 낸 토막마다 그 합을 적은 배열**입니다. 칸 `i` 는 앞 `i`
칸짜리 토막을 맡아요. 식으로 적으면 `P[0] = 0`, `P[i] = A[0] + A[1] + … + A[i−1]` 입니다.

##### 입력 위에 놓은 그림

칸마다 어느 토막을 맡는지 괄호로 그리면 이렇습니다. 괄호는 모두 인덱스 0 에서 시작하고, 칸 번호가
하나 커질 때마다 오른쪽으로 한 칸씩 길어져요.

<!--fig:concept-cover-->
![누적합 배열의 칸마다 덮는 앞부분 — P[k] 의 괄호는 인덱스 0 부터 k−1 까지](./figs/concept-cover.svg)

칸 `k` 의 괄호는 인덱스 `k − 1` 에서 끝납니다. **칸 번호는 토막의 길이이고, 토막의 마지막 인덱스보다
하나 큽니다.** 칸 0 은 길이 0 인 토막이라 덮는 칸이 없어요.

##### 칸 하나를 읽는 법

칸 하나를 골라 이름에서 값까지 따라가 봅시다. `P[4]` 는 앞 4 칸이고, 앞 4 칸은 인덱스 0 부터 3 까지입니다.

<!--proof:build-read-one-->

```text
P[4]  →  앞 4 칸  →  인덱스 [0,3]  →  값 3 1 4 1  →  합 9
```

##### 이웃한 칸끼리의 관계

이웃한 두 칸은 토막이 한 칸 차이입니다. 그래서 `P[i+1]` 에서 `P[i]` 를 빼면 `A[i]` 하나가 남아요. 여섯
쌍을 모두 빼 보았습니다.

<!--proof:build-neighbors-->

| i | P[i] | P[i+1] | P[i+1] − P[i] | A[i] |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | 3 | 3 | 3 |
| 1 | 3 | 4 | 1 | 1 |
| 2 | 4 | 8 | 4 | 4 |
| 3 | 8 | 9 | 1 | 1 |
| 4 | 9 | 14 | 5 | 5 |
| 5 | 14 | 23 | 9 | 9 |

6 쌍 모두 이웃한 두 칸의 차가 A[i] 와 같습니다.

<!--/proof-->

이 관계를 거꾸로 읽으면 채우는 규칙이 됩니다. `P[i+1]` 은 `P[i]` 에 `A[i]` 하나를 더한 값이에요.
뒤 칸이 앞 칸 위에 원소 하나씩 쌓여 올라가는 모양입니다.

##### 헷갈리기 쉬운 모양 — 입력 배열과 같은 길이

누적합이라는 말을 들으면 먼저 떠오르기 쉬운 모양은 칸 수가 `A` 와 같은 배열입니다. 칸 `i` 에 앞 `i + 1`
칸, 곧 인덱스 `i` 까지의 합을 적는 것이에요. 이것을 `T` 라고 부르고, 모든 질의에 각자의 식을 실제로
적용해 보았습니다.

<!--proof:build-same-length-->

| 모양 | 칸 수 | 칸의 값 | 구간 [l,r] 의 식 | 맞게 답한 질의 |
| --- | ---: | --- | --- | --- |
| 누적합 배열 P — 칸 i 는 앞 i 칸의 합 | 7 | [0 3 4 8 9 14 23] | P[r+1] − P[l] | 21 / 21 |
| 같은 길이 T — 칸 i 는 앞 i+1 칸의 합 | 6 | [3 4 8 9 14 23] | T[r] − T[l−1] | 15 / 21 |

모든 (l, r) 짝 21 개에 식을 실제로 적용해 직접 더한 값과 대조했습니다. T 는 왼쪽 끝이 0 인 6 개에서 T[−1] 을 읽어 값이 아닌 것을 냅니다.

<!--/proof-->

`T` 로 구간 `[l, r]` 을 구하려면 인덱스 `l − 1` 까지의 합 `T[l−1]` 을 빼야 하는데, `l = 0` 이면 그 칸이
없습니다. 누적합 배열은 같은 자리에 「앞 0 칸의 합」 `P[0] = 0` 이라는 뜻 있는 칸을 하나 더 두어 이
경우를 없앴어요.

##### 칸이 n + 1 개인 까닭

질의의 왼쪽 끝 `l` 은 0 부터 `n − 1` 까지, 오른쪽 끝 바로 다음 자리 `r + 1` 은 1 부터 `n` 까지 올 수
있습니다. 둘을 합치면 읽을 수 있는 칸 번호가 0 부터 `n` 까지라 칸이 `n + 1` 개 있어야 해요.

```text
읽는 칸     l 은 0 … n−1       r+1 은 1 … n
합치면      0 … n              n + 1 칸
            └ 질의의 두 끝이 배열 어디든 올 수 있어서, 모든 경계 자리에 칸이 하나씩 있어야 한다
```

#### 1단계 — 누적합 배열의 크기와 첫 칸 정하기

앞 절의 모양 그대로 `n + 1` 칸을 잡고, 칸 0 에 빈 구간의 합 0 을 넣습니다. 칸 0 은 채우기 반복이 쓰지
않는 칸이라 여기서 따로 정해 둬요. 각 상태의 크기와 범위를 적으면 이렇습니다.

<!--proof:build-size-->

```text
칸 수           n + 1                전개 입력은 n = 6 이라 칸 7 개 · n = 100,000 이면 칸 100,001 개
메모리          (n + 1) × 8 바이트   n = 100,000 이면 800,008 바이트 — 256 MB 의 0.30 %
칸 하나의 범위  |P[i]| ≤ i × 10,000  n = 100,000 이면 1,000,000,000 이하 — 2^31 − 1 = 2,147,483,647 보다 작다
```

칸 하나의 값은 앞 `i` 칸의 합이라, 원소의 절댓값이 10,000 이하면 칸의 절댓값은 `i × 10,000` 이하예요.
과제 규모의 끝에서도 32 비트 정수 범위 안이고, 메모리는 예산의 1 % 도 쓰지 않습니다.

#### 2단계 — 앞에서부터 한 칸씩 채우기

칸 `i + 1` 은 칸 `i` 에 `A[i]` 하나를 더해 채웁니다. 매번 앞에서부터 다시 더하지 않고 **직전 칸 하나만**
읽어요. 가장 불안한 자리는 첫 칸을 채우는 `i = 0` 입니다. 읽을 직전 칸이 1단계에서 넣은 `P[0]` 뿐이기
때문이에요. 전개 입력으로 채우면 이렇습니다.

<!--proof:build-fill-->

| i | 읽는 칸 | 더하는 원소 | 쓰는 칸 |
| ---: | --- | --- | --- |
| 0 | P[0] = 0 | A[0] = 3 | P[1] = 3 |
| 1 | P[1] = 3 | A[1] = 1 | P[2] = 4 |
| 2 | P[2] = 4 | A[2] = 4 | P[3] = 8 |
| 3 | P[3] = 8 | A[3] = 1 | P[4] = 9 |
| 4 | P[4] = 9 | A[4] = 5 | P[5] = 14 |
| 5 | P[5] = 14 | A[5] = 9 | P[6] = 23 |

i 가 0 부터 5 까지 6 번 실행됐고, 칸 1 부터 칸 6 까지 한 번씩 썼습니다. 칸 0 은 반복 전에 넣은 값입니다.

<!--/proof-->

`i = 0` 에서 읽은 `P[0] = 0` 이 첫 칸을 특수한 경우로 가르지 않게 해 줍니다. 빠뜨리는 칸이 없는 근거는
반복의 종료 조건이에요. 반복은 `i` 가 0 에서 시작해 `n − 1` 까지 한 칸씩 가고, 한 번마다 칸 `i + 1` 을
**정확히 한 번** 씁니다. 그러니 칸 1 부터 칸 `n` 까지 빠짐없이 한 번씩 정해지고, 칸 0 은 반복 전에
정해졌습니다.

원소에 음수가 섞이면 칸 값이 줄기도 합니다. 누적합 배열이 오름차순이라고 기대하면 여기서 걸려요.

<!--proof:build-fill-negative-->

```text
A 의 값  -1 2 -3 4
P        [0 -1 1 -2 2]
    └ 칸 1 · 3 의 값이 직전 칸보다 작다. 음수를 더한 칸이다. 규칙은 그대로 직전 칸에 원소 하나를 더한 것이다
```

#### 3단계 — 두 칸의 차로 구간 합 답하기

질의 `[l, r]` 의 답은 `P[r+1] − P[l]` 입니다. `P[r+1]` 은 인덱스 `r` 까지의 토막, `P[l]` 은 인덱스
`l − 1` 까지의 토막이고, 두 토막이 함께 덮는 앞부분 `[0, l−1]` 이 뺄셈에서 지워져 `[l, r]` 만 남아요.
오른쪽 끝이 배열의 마지막인 질의 `[2,5]` 로 그리면 이렇습니다.

<!--fig:build-cancel-->
![질의 [2,5] — P[6] 과 P[2] 가 함께 덮는 인덱스 0 · 1 이 뺄셈에서 지워진다](./figs/build-cancel.svg)

해칭한 두 칸이 두 토막에 모두 든 칸입니다. 한쪽에서 더해지고 다른 쪽에서 빠지니 답에 남지 않아요. 이
식 하나가 모양이 다른 질의 다섯을 모두 답하는지 직접 더한 값과 대조했습니다.

<!--proof:build-query-cases-->

| 경우 | 질의 | 두 칸의 차 | 직접 더한 값 |
| --- | --- | --- | --- |
| 두 끝이 안쪽 | [1,3] | P[4] − P[1] = 9 − 3 = 6 | 1 + 4 + 1 = 6 |
| 배열 전체 | [0,5] | P[6] − P[0] = 23 − 0 = 23 | 3 + 1 + 4 + 1 + 5 + 9 = 23 |
| 한 칸짜리 | [4,4] | P[5] − P[4] = 14 − 9 = 5 | 5 = 5 |
| 왼쪽 끝이 0 — P[0] 을 읽는다 | [0,2] | P[3] − P[0] = 8 − 0 = 8 | 3 + 1 + 4 = 8 |
| 오른쪽 끝이 마지막 — P[n] 을 읽는다 | [2,5] | P[6] − P[2] = 23 − 4 = 19 | 4 + 1 + 5 + 9 = 19 |

5 경우 중 5 경우에서 두 칸의 차가 직접 더한 값과 같습니다. 분기 없이 같은 식 하나입니다.

<!--/proof-->

왼쪽 끝이 0 이면 `P[0] = 0` 을 빼므로 따로 다룰 것이 없고, 오른쪽 끝이 마지막이면 칸 `n` 을 읽는데
1단계가 그 칸까지 잡아 두었어요. 한 칸짜리 구간은 이웃한 두 칸의 차라서 `A[r]` 하나가 남습니다.

#### 이 방법이 기대는 전제

누적합 배열은 아래 두 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 배열이 질의 동안 바뀌지 않는다 | 2단계에서 한 번 채운 누적합 배열을 모든 질의가 쓴다 | 원소 하나가 바뀌면 그 뒤 칸이 전부 어긋나 다시 채워야 한다 |
| 뺄셈이 덧셈을 되돌린다 | 3단계가 두 토막이 함께 덮는 앞부분을 뺄셈으로 지운다 | 되돌리는 연산이 없는 값(최솟값 등)은 두 칸으로 구간 값을 만들 수 없다 |

배열이 바뀌는 경우는 「전체 컨셉」의 `A[1]` 을 고친 예가 값으로 보였습니다. 되돌리는 연산이 없는
경우는 앞 `i` 칸의 **최솟값**을 칸 `i` 에 담은 배열 `M` 으로 확인해요. 두 질의가 같은 두 칸에서 같은
값을 읽는데 답이 다른 짝을 찾았습니다.

<!--proof:premise-min-->

```text
앞 i 칸의 최솟값 M = [∞ 3 1 1 1 1 1]

질의 [2,2]  M[3] = 1 · M[2] = 1  실제 최솟값 4
질의 [2,3]  M[4] = 1 · M[2] = 1  실제 최솟값 1
    └ 두 질의가 같은 두 칸에서 같은 값을 읽는데 답이 다르다. 두 값만으로 답을 만드는 식은 없다
```

#### 모든 칸에 저장하는 까닭

누적합 배열은 앞에서부터의 합을 **모든** 자리에 저장합니다. 저장을 `B` 칸마다 하나씩만 하는 절차를 따로
만들어 `B` 를 넷으로 두고 같은 질의 목록에서 세었어요. `B` 칸마다 저장하면 저장한 자리와 질의의 끝 사이에
남는 칸은 질의 때 직접 더해야 합니다.

<!--proof:cost-block-->

| 저장 간격 | 저장 칸 | 질의 때 더한 수 | 덧셈·뺄셈 합 |
| --- | ---: | ---: | ---: |
| B = 1 | 7 | 0 | 11 |
| B = 2 | 4 | 3 | 14 |
| B = 3 | 3 | 7 | 18 |
| B = 6 | 2 | 19 | 30 |

넷 모두 답이 6 23 5 8 19 로 정본과 같고, 연산이 가장 적은 것은 B = 1 입니다.

<!--/proof-->

`B` 를 키울수록 저장 칸은 줄고 질의 때 더하는 수가 늡니다. 1단계에서 본 것처럼 `n + 1` 칸이 예산의
1 % 도 안 쓰니 저장을 아낄 이유가 없어서, **저장 간격은 1** 입니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 이렇습니다. 앞의 둘이 질의 전에 한 번이고 마지막이 질의마다예요.
이렇게 하면 `n` 과 `q` 가 100,000 일 때 100 억 번이던 연산이 200,000 번이 됩니다.

1. 누적합 배열을 `n + 1` 칸으로 잡고 `P[0]` 에 0 을 넣는다
2. `i` 를 0 부터 `n − 1` 까지 옮기며 `P[i+1]` 에 `P[i] + A[i]` 를 넣는다
3. 질의 `[l, r]` 마다 `P[r+1] − P[l]` 을 답 목록에 덧붙인다

### 수행으로 알아보는 알고리즘 — 여섯 칸을 채우고 다섯 질의를 답한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다
그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const A = [3, 1, 4, 1, 5, 9];
const queries: Array<[number, number]> = [[1, 3], [0, 5], [4, 4], [0, 2], [2, 5]];
// 이 절이 끝나면 [6, 23, 5, 8, 19] 가 나와야 한다
```

왜 하필 이 다섯 질의일까요? 앞의 셋은 흔한 모양이고, 뒤의 둘이 **누적합 배열의 양 끝 칸을 각각 읽게**
하기 때문이에요. `[0,2]` 는 `P[0]` 을, `[2,5]` 는 `P[6]` 을 읽습니다. `[4,4]` 로 한 칸짜리 구간까지 넣어
두면 이 절차가 답하는 구간의 모양이 다 나와요.

```text
prefixSumRangeQuery(A, queries):
    P 를 n+1 칸으로 잡고 P[0] 에 0 을 넣는다
    i 를 0 부터 n−1 까지 옮기며:
        P[i+1] 에 P[i] + A[i] 를 넣는다                     ① 전처리
    질의 [l,r] 을 순서대로 받으며:
        P[r+1] − P[l] 을 결과 목록에 덧붙인다               ② 질의
    결과 목록을 반환한다
```

#### 1. 빈 구간의 합을 0 으로 두고 누적합 배열을 잡는다

크기와 첫 칸이 이 조각의 전부입니다. 두 줄이지만 이 두 줄이 뒤의 모든 분기를 없애요.

```ts
const n = A.length;
const P = new Array<number>(n + 1);
P[0] = 0;
```

이 조각만 실행하면 누적합 배열이 이렇게 잡힙니다.

<!--proof:walk-init-->

```text
n = 6                칸 7 개 (0 … 6)
P = [0 · · · · · ·]  P[0] = 0, 나머지 6 칸은 아직 비어 있다
```

`n` 이 아니라 `n + 1` 인 이유는 오른쪽 끝이 배열의 마지막인 질의 때문입니다. `r = n−1` 이면 `P[r+1]`,
곧 `P[n]` 을 읽어야 하니 칸 `n` 까지 있어야 해요. `P[0] = 0` 은 **빈 구간의 합**이고, 이 한 칸이 왼쪽 끝
`0` 인 질의를 특수한 경우로 가르지 않게 해 줍니다.

#### 2. 앞에서부터 한 번 더해 채운다

채우기가 전처리의 전부입니다. 매번 처음부터 다시 더하지 않고 **직전 칸에 값 하나만** 더해요.

```ts
for (let i = 0; i < n; i++) {
  // ① 전처리 — 직전 칸에 A[i] 를 한 번만 더해 다음 칸을 채운다.
  P[i + 1] = (P[i] as number) + (A[i] as number);
}
```

이 조각까지 실행하면 누적합 배열이 다 찹니다.

<!--proof:walk-fill-->

```text
P = [0 3 4 8 9 14 23]    채운 칸 7 / 7 · 덧셈 6 번
```

여기서 가장 중요한 줄은 `P[i + 1] = P[i] + A[i]` 입니다. 왼쪽이 `i+1` 이고 오른쪽이 `i` 라는 것, 그러니까
**쓰는 칸이 읽는 칸보다 하나 뒤**라는 것이 이 줄의 전부예요. 둘을 같은 인덱스로 적으면 칸이 한 자리씩
옮겨져 뒤가 전부 어긋납니다.

#### 짚고 가기 — 누적합 배열을 A 와 같은 길이로 잡으면 왼쪽 끝이 0 인 질의만 깨진다

여기서 헷갈리기 쉬운 포인트는 누적합 배열의 길이입니다. 「누적합이면 원래 배열과 칸 수가 같아야
자연스럽지 않나」로 읽기 쉬워요. 그 정의로 가면 칸 `i` 에 인덱스 `i` 까지의 합이 들고, 질의의 답은
`T[r] − T[l−1]` 이 됩니다. `l = 0` 이면 `T[−1]` 을 읽어야 하는데 그 칸이 없어요. 다섯 질의에 두 정의를
각각 실행해 보면 이렇게 나옵니다.

<!--proof:pause-same-length-->

```text
질의   정본  같은 길이 T
[1,3]  6     6            답이 같다
[0,5]  23    NaN          값이 아니다
[4,4]  5     5            답이 같다
[0,2]  8     NaN          값이 아니다
[2,5]  19    19           답이 같다

└ 왼쪽 끝이 0 인 질의 2 개만 깨진다. 나머지 3 개는 답이 같아서 알아채지 못한다
```

왼쪽 끝이 0 인 질의만 값이 아닌 것을 냈고 나머지는 답이 같습니다. **시험 입력에 왼쪽 끝이 0 인 질의가
없으면 이 정의는 통과해요** — 그래서 알아채지 못한 채로 남습니다.

```text
고치는 길이 둘이다
  (가) if (l === 0) 분기를 더한다              질의마다 조건 검사가 하나 는다
  (나) n+1 칸으로 잡고 P[0] = 0 을 넣는다      분기가 아예 없어진다
       └ (나)는 「없는 칸」 대신 「빈 구간의 합」이라는 뜻 있는 값을 그 자리에 둔다
```

#### 3. 저장한 두 칸을 빼서 질의 하나를 답한다

누적합 배열이 다 채워졌으면 질의 하나는 두 줄로 끝납니다. 읽고, 빼고, 결과 목록에 덧붙여요.

```ts
const result: number[] = [];
for (const [l, r] of queries) {
  // ② 질의 — 저장해 둔 두 칸을 읽어 뺀다. 왼쪽 끝이 0 이어도 같은 식이다.
  result.push((P[r + 1] as number) - (P[l] as number));
}
```

첫 질의 `[1,3]` 에 이 조각만 실행한 결과입니다.

<!--proof:walk-query-one-->

```text
들어올 때  l = 1  r = 3       P 는 [0 3 4 8 9 14 23] 로 다 채워져 있다
오른쪽 끝  P[r+1] = P[4] = 9  앞 4 칸의 합
왼쪽 끝    P[l] = P[1] = 3    앞 1 칸의 합
빼면       9 − 3 = 6          답 목록이 [6] 이 된다
            └ 구간이 3 칸인데 읽은 칸은 둘이다
```

#### 짚고 가기 — 오른쪽 끝을 P[r] 로 읽으면 A[r] 이 0 일 때 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 오른쪽 끝의 `+1` 입니다. 「왼쪽은 `P[l]` 이니 오른쪽도 `P[r]` 이면 되겠지」로
읽기 쉬운데, 두 자리의 뜻이 서로 달라요.

```text
P[l]      앞 l 칸의 합 = 인덱스 l−1 까지    구간에 안 들어가는 부분이다
P[r+1]    앞 r+1 칸의 합 = 인덱스 r 까지    구간의 오른쪽 끝을 포함해야 한다
          └ 왼쪽은 「직전까지」, 오른쪽은 「끝까지」라 두 자리의 규칙이 다르다
```

`P[r]` 로 읽으면 `A[r]` 하나가 답에서 빠집니다. 그러니 **`A[r]` 이 0 인 질의에서는 답이 안 틀려요.**
정본에서 인덱스 하나만 바꾼 코드를 만들어 다섯 입력에 두 코드를 각각 실행했습니다.

<!--proof:pause-right-end-->

```text
입력           질의   A[r]  바른 코드  P[r] 을 읽은 코드
[3 1 4 1 5 9]  [1,3]  1     6          5                  답이 다르다
[3 1 4 1 5 9]  [0,5]  9     23         14                 답이 다르다
[3 1 4 1 5 9]  [4,4]  5     5          0                  답이 다르다
[3 1 0 4]      [0,2]  0     4          4                  답이 같다
[2 0 0 7]      [1,2]  0     0          0                  답이 같다

└ A[r] 이 0 인 입력에서는 P[r] 과 P[r+1] 이 같은 값이라 이 변경을 넣어도 답이 바뀌지 않는다
```

아래 두 줄이 이 오해가 오래 남는 이유입니다 — 0 이 섞인 입력으로 시험하면 우연히 맞아요. 이 과제의
원소는 −10,000 이상 10,000 이하라 0 은 얼마든지 들어옵니다.

#### 4. 여섯 칸을 채우고 다섯 질의를 순서대로 답한다

조각을 이어 고정 입력에 실행하면 열두 걸음이 나옵니다. 앞의 일곱이 누적합 배열을 만드는 걸음이고 뒤의
다섯이 질의를 답하는 걸음이에요. 괄호는 이번 걸음이 다루는 `A` 의 구간입니다. 채우기에서는 새 칸이 덮는
앞부분이고 답하기에서는 질의예요. 점선 칸은 아직 안 쓴 칸이고 ▲ 는 이번 걸음에 읽은 칸입니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 결과 목록을 빈 배열로 시작하는 한 줄과
마지막의 반환뿐이에요 — 질의가 하나도 없으면 그 빈 배열이 그대로 답이 됩니다.

```ts
export function prefixSumRangeQuery(
  A: number[],
  queries: Array<[number, number]>,
): number[] {
  const n = A.length;
  // 누적합 배열의 칸 `i` 에는 A 의 앞 `i` 개 원소의 합을 담는다. 칸이 n+1 개라 오른쪽
  // 끝이 배열의 마지막인 질의도 누적합 배열 밖으로 나가지 않는다.
  const P = new Array<number>(n + 1);
  // 빈 구간의 합은 0 이다. 이 한 칸이 왼쪽 끝 0 을 특수한 경우로 가르지 않게 한다.
  P[0] = 0;

  for (let i = 0; i < n; i++) {
    // ① 전처리 — 직전 칸에 A[i] 를 한 번만 더해 다음 칸을 채운다.
    P[i + 1] = (P[i] as number) + (A[i] as number);
  }

  const result: number[] = [];
  for (const [l, r] of queries) {
    // ② 질의 — 저장해 둔 두 칸을 읽어 뺀다. 왼쪽 끝이 0 이어도 같은 식이다.
    result.push((P[r + 1] as number) - (P[l] as number));
  }

  return result;
}
```

<!--proof:final-calls-->

```text
prefixSumRangeQuery([3, 1, 4, 1, 5, 9], [[1,3], [0,5], [4,4], [0,2], [2,5]])  →  [6, 23, 5, 8, 19]
prefixSumRangeQuery([1, 2, 3], [])                                            →  []
prefixSumRangeQuery([-1, 2, -3, 4], [[0,3]])                                  →  [2]
prefixSumRangeQuery([7], [[0,0]])                                             →  [7]
```

### 알아 두면 좋은 개념 — 역원이 있는 연산

이 절차가 하는 일을 한 문장으로 줄이면 **「덧셈을 뺄셈으로 되돌린다」** 입니다. 3단계에서 두 토막이 함께
덮는 앞부분이 지워진 것이 뺄셈 덕분이고, 그 뺄셈이 덧셈의 **역원**이에요. 어떤 연산에 역원이 있으면
앞에서부터 쌓아 둔 두 값의 차이가 그대로 구간의 값이 됩니다.

```text
쌓아 둔 값 두 개                     차이를 만드는 연산      구간의 값
P[l]   = A[0] + … + A[l−1]      ─┐
                                  ├→  뺄셈                  A[l] + … + A[r]
P[r+1] = A[0] + … + A[r]        ─┘
        └ 함께 들어 있는 앞부분이 뺄셈에서 사라진다
```

같은 모양을 다른 연산에 적용해 보면 이 성질이 어디서 끊기는지 확인됩니다.

| 연산 | 역원 | 앞에서부터의 값 둘로 구간 값 만들기 |
| --- | --- | --- |
| 덧셈 | 뺄셈 | 됩니다. 이 글이 그것입니다 |
| 배타적 논리합(XOR) | 자기 자신 | 됩니다. 두 번 하면 지워집니다 |
| 곱셈 | 나눗셈 | 값에 `0` 이 없을 때만 됩니다 |
| 최댓값·최솟값 | 없음 | 안 됩니다. 「이 방법이 기대는 전제」에서 값으로 보였습니다 |

마지막 줄이 다른 자료구조가 필요해지는 자리입니다. 구간 최솟값을 묻는 과제가
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-guide.md) 이나
[`segmentTreeRangeMin`](../segmentTreeRangeMin/segmentTreeRangeMin-guide.md) 으로 가는 이유가
이것이에요.

같은 이름을 다시 만나는 자리는 이렇습니다.

| 개념 | 두 칸으로 하는 일 | 역원 |
| --- | --- | --- |
| 누적 XOR | 구간의 XOR 을 두 칸의 XOR 로 | 자기 자신 |
| 차분 배열 | 구간 갱신을 두 칸의 덧셈으로 — 누적합의 반대 방향 | 뺄셈 |
| 구간 최솟값 | 두 칸으로는 안 되어 다른 구조를 만든다 | 없음 |

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 누적합 배열과 뺄셈을 식으로 어떻게 적는지,
무엇이 매 걸음 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 배열이 **질의를 처리하는 동안 바뀌지 않습니다.** 원소 하나가 바뀌면 누적합 배열의 뒤쪽이 통째로
  어긋나서 다시 채워야 해요.
- 질의가 **연속 구간**을 묻습니다. 인덱스를 골라 담는 질의라면 앞에서부터의 합으로 만들 수 없어요.
- 구간에 매기는 값의 연산에 **역원이 있습니다.** 합·XOR 이 그렇고, 최댓값은 아닙니다.
- 질의 수 `q` 가 **한 번 채우는 비용을 갚을 만큼** 많습니다. 질의가 한두 개면 그냥 직접 더하는 편이
  적어요.

```text
네 조건이 코드의 모양을 그대로 정한다
  정적 배열        → 누적합 배열을 다시 채우는 코드가 아예 없다
  연속 구간        → 두 끝 l 과 r 만 받으면 상태가 끝난다
  역원이 있는 연산 → 질의가 뺄셈 한 번이다
  질의가 많다      → 채우기 n 번을 q 개가 나눠 진다
```

마지막 줄에 경계가 있습니다. 채우기에 `n` 번을 쓰고 질의당 1 번이니 총 `n + q` 이고, 직접 더하는 방법은
최악 `q·n` 이에요. 질의가 하나이고 구간이 짧으면 채우기가 오히려 손해입니다.

<!--proof:fit-boundary-->

| 질의 (n = 100,000) | 직접 더하기 | 누적합 배열 | 구한 방법 |
| --- | ---: | ---: | --- |
| 1 개 · 구간 10 칸 | 10 | 100,001 | 실행해서 셌다 |
| 100,000 개 · 전부 배열 전체 | 10,000,000,000 | 200,000 | q·n 과 n + q 로 냈다 |

덧셈과 뺄셈만 셉니다. 질의가 하나이고 구간이 짧으면 직접 더하는 쪽이 적습니다.

<!--/proof-->

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "배열은 변경되지 않는다"  "정적"  "미리 주어진다"   ← 결정적인 신호다
  "구간 [l, r] 의 합"  "부분합"  "누적"
  "질의가 Q 개 주어진다"  "각 질의에 대해 답하라"     ← 질의가 많다는 뜻이다

제약에 이런 모양이 보이면
  N 과 Q 가 둘 다 10^5 이상이라 N×Q 가 못 들어간다
  값의 범위가 좁아 전체 합이 정수 범위를 안 넘는다

반대로 이런 말이 보이면 해당하지 않는다
  "i 번째 원소를 v 로 바꾼다"  "갱신 질의"           ← 배열이 바뀐다
  "구간의 최솟값"  "구간의 최댓값"                    ← 역원이 없다
```

마지막 무리가 보이면 다른 절차로 갑니다. 갱신이 섞이면
[`fenwickRangeSum`](../fenwickRangeSum/fenwickRangeSum-guide.md) 쪽이고, 최솟값이면
[`sparseTableRangeMin`](../sparseTableRangeMin/sparseTableRangeMin-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **CPython 의 `itertools.accumulate`** — 표준 라이브러리가 이 채우기를 그대로 제공합니다. 공식 문서에
  실린 등가 파이썬 코드가 `total = func(total, element)` 한 줄 누적이고, 그것이 이 글의 채우기 반복과
  같은 자리예요.
  ([`itertools.accumulate`](https://docs.python.org/3/library/itertools.html#itertools.accumulate),
  조회 2026-08-29)
- **NumPy 의 `numpy.cumsum`** — 배열 하나를 받아 같은 길이의 누적합을 돌려줍니다. 이 글의 누적합 배열과
  다른 점은 **앞에 0 칸을 두지 않는다**는 것이라, 구간 합을 구하려면 왼쪽 끝이 0 인 경우를 따로 다뤄야
  해요 — 「먼저 알아 둘 개념」의 같은 길이 `T` 가 그 모양입니다.
  ([`numpy.cumsum`](https://numpy.org/doc/stable/reference/generated/numpy.cumsum.html),
  조회 2026-08-29)
- **OpenCV 의 `cv::integral`** — 같은 아이디어를 2차원으로 넓힌 **적분 영상**입니다. 사각형 영역의 합을
  네 칸의 덧셈·뺄셈으로 답해요. 헤더에 선언이 있습니다.
  ([`modules/imgproc/include/opencv2/imgproc.hpp`](https://github.com/opencv/opencv/blob/4.x/modules/imgproc/include/opencv2/imgproc.hpp),
  조회 2026-08-29)

```text
세 사례와 이 과제의 관계

  앞의 둘   채우기만 제공한다. 질의의 뺄셈은 쓰는 쪽이 직접 적는다
  OpenCV    2차원이라 뺄셈이 한 번이 아니라 네 항의 덧셈·뺄셈이다
            └ 1차원의 두 칸이 2차원에서 네 칸이 되는 것이 확장의 전부다
```

#### 경쟁 설계와의 대조

같은 목표(구간 합 질의에 답하기)를 노리는 다른 절차로 **펜윅 트리**(이진 인덱스 트리)가 있습니다. 칸
`j` 가 자기 아래 여러 원소의 합을 들고 있어서, 앞 `k` 개의 합을 `k` 의 1 비트 수만큼의 칸을 읽어 만들어요.
갱신은 그 원소를 덮는 칸들만 고치면 끝납니다.

| 설계 | 구간 합의 식 | 질의 때 읽는 칸 | 갱신 때 고치는 칸 |
| --- | --- | --- | --- |
| 누적합 배열 | `P[r+1] − P[l]` | 2 개 | 배열 전체를 다시 채운다 |
| 펜윅 트리 | `prefix(r+1) − prefix(l)` | `log n` 개씩 | `log n` 개 |

펜윅 트리는 질의에서 칸을 더 읽고 갱신에서 훨씬 적게 고칩니다. 그래서 질의와 갱신이 섞인 비율이 어느 쪽의
접근 수가 적은지를 정해요.

같은 입력·같은 작업 목록에 두 설계를 걸고 **배열 접근 수**(읽기 + 쓰기)를 셌습니다. 배열은
`n = 1,024` 이고 `A[i] = (37i) mod 101`, 질의는 `q = 1,024` 개로 `a = (37i) mod n` 과
`b = (91i) mod n` 을 만들어 작은 쪽을 왼쪽 끝으로 뒀어요. 갱신 `k` 번째는 `A[(53k) mod n]` 에
`(k mod 7) + 1` 을 더하고, 갱신은 질의 사이에 고르게 끼웠습니다. 난수를 쓰지 않아 시드가 없고, 위
식이 입력의 전부예요. 전개의 여섯 칸을 쓰지 않은 까닭은 여섯 칸에서는 펜윅 트리가 한 번에 지나는 칸이
두세 개뿐이라 두 설계의 접근 수가 상수에 묻히기 때문입니다.

| 갱신 횟수 | 누적합 배열 | 펜윅 트리 | 적은 쪽 |
| --- | --- | --- | --- |
| 0 회 | **5,121** | 23,548 | 누적합 배열 |
| 6 회 | **23,571** | 23,650 | 누적합 배열 |
| 7 회 | 26,646 | **23,662** | **펜윅 트리 — 여기서 순서가 뒤집힙니다** |
| 1,024 회 | 3,153,921 | **37,884** | 펜윅 트리 |

**저장 칸은 둘 다 1,025 개로 같습니다.** 메모리에서는 갈리지 않아요 — 갈리는 것은 접근 수이고, 그
경계가 이 입력에서 **갱신 7 회**입니다. 경계가 그 자리에 오는 까닭을 표의 값으로 풀면 이렇습니다.

<!--proof:alt-crossing-->

```text
누적합 배열의 갱신 하나  (3,153,921 − 5,121) ÷ 1,024 = 3,075  배열을 통째로 다시 채운다
펜윅 트리의 갱신 하나    (37,884 − 23,548) ÷ 1,024 = 14       덮는 칸만 고친다
갱신 0 회의 차이         23,548 − 5,121 = 18,427              누적합 배열이 적은 만큼
뒤집히는 자리            18,427 ÷ (3,075 − 14) ≈ 6.02         갱신 7 번째에 뒤집힌다
```

**이 절차가 내주는 것은 갱신입니다.** 원소 하나가 바뀌면 누적합 배열을 처음부터 다시 채워야 해서 갱신
하나가 채우기 한 번과 같은 비용이에요. 그 대신 얻는 것이 셋입니다.

| 축 | 누적합 배열 | 펜윅 트리 |
| --- | --- | --- |
| 질의 비용 | 읽기 2 번으로 고정 | 질의마다 `log n` 칸씩 읽는다 |
| 구현 | 루프 두 개, 분기 없음 | `j & -j` 비트 연산이 들어간다 |
| 갱신 0 회의 접근 수 | 5,121 | 23,548 |

**우열이 반대가 되는 조건이 분명합니다.** 갱신이 없는 과제에는 누적합 배열이 답이고, 이 입력에서 갱신이
일곱 번 이상 섞이면 펜윅 트리가 적어요. 지문에 **갱신 질의가 하나라도 섞이는 순간** 이 판정을 다시
해야 합니다.

### 수식 정의와 유도

누적합 배열을 기호로 정의합니다. 칸 `0` 은 빈 구간의 합이고, 그다음부터는 직전 칸에 값 하나를 더한
것입니다.

$$P[0] = 0, \qquad P[i] = P[i-1] + A[i-1] \quad (1 \le i \le n)$$

<!--proof:math-check-->

```text
A 의 값 3 1 4 1 5 9

  P[0] = 0
  P[1] = P[0] + A[0] = 0 + 3 = 3
  P[2] = P[1] + A[1] = 3 + 1 = 4
  P[3] = P[2] + A[2] = 4 + 4 = 8
```

정의 하나가 칸 하나를 정하고, 정의가 두 항만 봅니다. 이 재귀 정의에서 닫힌 형태를 유도합니다. 주장은
`P[i]` 가 앞 `i` 개 원소의 합이라는 것이에요.

$$P[i] = \sum_{k=0}^{i-1} A[k]$$

```text
기저 (i = 0)
  좌변 P[0] = 0                       정의가 그렇게 정했다
  우변 k = 0 부터 −1 까지의 합         더할 것이 없으므로 0
  둘이 같다

단계 (i−1 에서 참이면 i 에서도 참)
  P[i] = P[i−1] + A[i−1]              정의
       = (A[0] + … + A[i−2]) + A[i−1]  가정을 P[i−1] 에 넣었다
       = A[0] + … + A[i−1]            항을 하나 덧붙인 것이다
  이것이 k = 0 부터 i−1 까지의 합이다
```

다음은 뺄셈이 구간 합을 내는 이유입니다. `l ≤ r` 이므로 앞 `r+1` 개의 합은 앞 `l` 개의 합과 그 뒤의
구간으로 **겹치지 않게** 갈립니다.

$$\sum_{k=0}^{r} A[k] = \sum_{k=0}^{l-1} A[k] + \sum_{k=l}^{r} A[k]$$

<!--proof:math-split-->

```text
l = 2, r = 5

  k = 0 … 5 의 합  3 + 1 + 4 + 1 + 5 + 9 = 23  P[6]
  k = 0 … 1 의 합  3 + 1 = 4                   P[2]
  k = 2 … 5 의 합  4 + 1 + 5 + 9 = 19
    └ 앞의 둘이 겹치는 항이 없고 23 = 4 + 19 이다
```

왼쪽 항이 `P[r+1]` 이고 오른쪽 첫 항이 `P[l]` 이므로, 양변에서 `P[l]` 을 빼면 구간 합이 남습니다.

$$\sum_{k=l}^{r} A[k] = P[r+1] - P[l]$$

<!--proof:math-apply-->

```text
P[r+1] − P[l] = P[6] − P[2] = 23 − 4 = 19
직접 더한 값    4 + 1 + 5 + 9 = 19
```

두 줄이 같고, 임의의 `l ≤ r` 에서 같은 이유가 위 유도입니다. 식의 `P` 를 코드에서도 `P` 로 그대로 씁니다.
닫힌 형태를 그대로 옮기면 이렇습니다.

```ts
// 닫힌 형태를 그대로 옮긴 조각. 정의를 확인하는 용도이고 실제 절차는 이것을 쓰지 않는다.
const prefixAt = (A: number[], i: number): number => {
  let s = 0;
  for (let k = 0; k < i; k++) s += A[k] as number;
  return s;
};
```

이 조각은 칸 하나를 만드는 데 `i` 번을 더하므로 칸 전부를 만들면 `n(n+1)/2` 번입니다. 실제 절차는 직전
칸을 쓰기 때문에 `n` 번이에요 — 같은 값을 만드는 두 방법의 차이가 그것입니다.

$$\text{총 연산} = \underbrace{n}_{\text{채우기 덧셈}} + \underbrace{q}_{\text{질의 뺄셈}} = n + q$$

```text
두 항이 서로 독립이다
  n 항   배열을 한 번 지난다        질의가 몇 개든 이 항은 그대로다
  q 항   질의마다 뺄셈 하나          배열이 얼마나 크든 이 항은 그대로다
         └ 그래서 곱이 아니라 합이다. 직접 더하기는 여기가 곱이었다
```

직접 더하는 방법의 최악은 모든 질의가 배열 전체를 묻는 것이라 `q · n` 입니다. 두 닫힌 형태에 규모를 넣고
실제 실행과 대조했어요.

<!--proof:cost-scale-->

| n = q | 직접 더하기(실측) | q·n | 누적합 배열(실측) | n + q |
| ---: | ---: | ---: | ---: | ---: |
| 6 | 36 | 36 | 12 | 12 |
| 100 | 10,000 | 10,000 | 200 | 200 |
| 1,000 | 1,000,000 | 1,000,000 | 2,000 | 2,000 |
| 100,000 | (실행하지 않음) | 10,000,000,000 | (실행하지 않음) | 200,000 |

실측값이 닫힌 형태와 3 규모에서 정확히 같습니다. n = q = 100,000 에서 10,000,000,000 대 200,000 이니 50,000 배입니다.

<!--/proof-->

### 불변식 — 누적합 배열의 칸 i 는 언제나 앞 i 개 원소의 합이다

파트 1 에서 코드가 동작하는 것을 열두 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는 뜻이지
언제나 맞는다는 뜻은 아니에요. 무엇이 **매 걸음 참으로 남는지**를 문장으로 세우고 그것이 실제로
유지되는지 확인해 봅시다.

> 채우기 반복이 `i` 번째 바퀴를 마친 시점마다, 누적합 배열의 칸 `0` 부터 `i+1` 까지는 각각 `A` 의 앞 그
> 칸 수만큼의 원소를 더한 값입니다. 그리고 반복이 끝난 뒤 배열이 바뀌지 않으므로, 그 성질은 질의를 몇 개
> 처리하든 그대로 남습니다.

```text
칸     0    1    …    i+1        i+2 … n
P      ●    ●    …    ●          아직 안 쓴 칸
       └ 여기까지가 「앞 몇 칸의 합」이다         ← 앞 문장
질의 반복은 P 를 읽기만 하고 쓰지 않는다          ← 뒤 문장
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 누적합 배열이 정의와 어긋나지 않는다는 것이고, 뒤 문장이
**질의 순서와 개수가 답을 바꾸지 않는다**는 것을 말해요. 둘 중 하나만 빠져도 「같은 질의를 두 번 물으면
같은 답이 나온다」는 근거가 사라집니다.

**출발점부터 봅시다.** 반복에 들어가기 전 `P[0] = 0` 이고, 「앞 0 개의 합은 0」 이 참입니다. 그 뒤 한
바퀴마다 칸 하나가 늘어나요.

| 바퀴 | 하는 일 | 앞 문장이 유지되는 근거 |
| --- | --- | --- |
| `i = 0` | `P[1] = P[0] + A[0]` | 앞 0 개의 합에 `A[0]` 을 더했으니 앞 1 개의 합이다 |
| `i = k` | `P[k+1] = P[k] + A[k]` | 직전 바퀴가 `P[k]` 를 앞 `k` 개의 합으로 만들어 뒀다 |
| 반복 종료 | `i = n` | `P[1]` 부터 `P[n]` 까지 각각 정확히 한 번씩 정해졌다 |

전개 입력에서 바퀴가 끝날 때마다 채워진 칸 전부를 정의와 직접 대조했습니다.

<!--proof:invariant-hold-->

| 반복 i | 채워진 칸 | 정의와 대조한 칸 | 어긋난 칸 |
| ---: | --- | ---: | ---: |
| 0 | 0 … 1 | 2 | 0 |
| 1 | 0 … 2 | 3 | 0 |
| 2 | 0 … 3 | 4 | 0 |
| 3 | 0 … 4 | 5 | 0 |
| 4 | 0 … 5 | 6 | 0 |
| 5 | 0 … 6 | 7 | 0 |

반복이 끝날 때마다 채워진 칸을 앞 칸들을 직접 더한 값과 대조했습니다. 모두 27 번 대조했고 어긋난 칸은 0 개입니다.

<!--/proof-->

뒤 문장은 질의 반복이 지킵니다. 그 반복은 `P` 를 읽기만 하고 쓰지 않으며 `A` 도 건드리지 않아요. 상태를
바꾸는 코드가 없으니 첫 질의가 보는 누적합 배열과 마지막 질의가 보는 누적합 배열이 같습니다. 경계에 있는
입력들도 확인하고 갑시다.

<!--proof:invariant-edges-->

| 경우 | 입력 | 질의 | 결과 |
| --- | --- | --- | --- |
| 질의 목록이 빔 | [1 2 3] | 없음 | [] |
| 원소 하나 | [7] | [0,0] | [7] |
| 한 칸짜리 구간 | [3 1 4 1 5 9] | [4,4] | [5] |
| 왼쪽 끝이 0 | [3 1 4 1 5 9] | [0,2] | [8] |
| 음수가 섞임 | [-1 2 -3 4] | [0,3] | [2] |
| 같은 질의 반복 | [1 2 3] | [0,2] [0,2] [0,2] | [6, 6, 6] |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 칸을 채우는 그 한 줄이에요. 「어차피 칸마다 값을 넣는
것이니」라는 생각으로 직전 칸을 더하는 부분을 빼 봅니다. 한 줄만 바뀝니다.

```ts
for (let i = 0; i < n; i++) {
  P[i + 1] = A[i] as number; // 직전 칸을 더하지 않는다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-no-accumulate-->

```text
질의   바른 코드  누적을 뺀 코드
[1,3]  6          -2              답이 다르다
[0,5]  23         9               답이 다르다
[4,4]  5          4               답이 다르다
[0,2]  8          4               답이 다르다
[2,5]  19         8               답이 다르다

└ 5 질의 중 5 개가 다른 답을 낸다
```

첫 줄이 음수인 것이 이 변경의 정체를 그대로 보입니다. 두 코드에 질의 `[0,i]` 를 물어 각자 채운 배열을
꺼내 보면 이렇습니다.

<!--proof:mutant-table-->

```text
바른 P  [0 3 4 8 9 14 23]  칸이 앞 몇 칸의 합이다
깨진 P  [0 3 1 4 1 5 9]    칸이 원소 하나다
    └ 질의 [0,i] 의 답이 P[i+1] 이라, 두 코드에 질의 [0,0] 부터 [0,5] 까지 물어 꺼냈다
```

깨진 배열은 칸 4 의 값이 칸 1 의 값보다 작아서, 원소가 전부 양수인 입력인데도 뺄셈이 음수를 냈어요.
원소가 음이 아닌 입력에서 구간 합이 음수로 나오면 칸이 「앞 몇 칸의 합」이 아니라는 뜻입니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 두 종류뿐입니다 — 누적합 배열을 채우며 더하는 것과, 두 칸을 읽어 빼는 것이에요.
전개의 걸음으로 세면 이렇습니다.

<!--proof:perf-derive-->

```text
덧셈  T2 T3 T4 T5 T6 T7  i 가 0 부터 5 까지 한 칸씩 → 정확히 6 번 = n
뺄셈  T8 T9 T10 T11 T12  질의 하나에 한 번 → 정확히 5 번 = q
    └ 합 11 번. 「아이디어를 떠올리는 과정」에서 누적합 배열로 센 값과 같다
```

덧셈은 바퀴마다 정확히 하나이므로 `n` 번이고, 뺄셈은 질의마다 정확히 하나이므로 `q` 번입니다. 둘 다
**입력의 내용과 무관하게 개수가 정해져요** — 값이 크든 작든, 구간이 길든 짧든 같습니다.

```text
총식 = 덧셈 + 뺄셈 + 배열 읽기 + 배열 쓰기
       └ n    └ q    └ 2n + 2q   └ n + 1
                  └ 채우기에서 P[i]·A[i] 로 2n, 질의에서 두 칸씩 2q

       총연산 = n + q + (2n + 2q) + (n + 1) = 4n + 3q + 1
       누적합 배열을 채우고 읽는 산술 연산(덧셈 + 뺄셈)만 보면 정확히 n + q 다
```

여기서 센 것은 **누적합 배열을 채우고 읽는 연산 전부**입니다. 추가로 잡는 메모리는 누적합 배열 하나뿐이라
`n + 1` 칸이고, 입력 배열은 읽기만 해요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (질의가 전부 한 칸짜리) | `O(n + q)` | `Θ(n + q)` |
| **평균적인 경우** (입력 분포와 무관하다) | `O(n + q)` | `Θ(n + q)` |
| **최악의 경우** (질의가 전부 배열 전체) | `O(n + q)` | `Θ(n + q)` — 실제로 도달한다 |

세 줄이 같은 것이 이 절차의 성질입니다. 최선과 최악의 차이가 **상수 계수에도 나타나지 않아요** — 산술
연산이 `n + q` 로 딱 고정이라, 질의의 모양을 어떻게 바꿔도 값이 같습니다.

```text
직접 더하기와 나란히 놓으면 이 성질이 확인된다
  직접 더하기   최선 q 번        최악 q·n 번      질의의 모양이 비용을 정한다
  누적합 배열   최선 n + q 번    최악 n + q 번    질의의 모양이 비용을 안 바꾼다
                └ 이 줄이 이 절차를 쓰는 이유다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 누적합 배열 채우기 하나뿐이라는 것이 이 절차의
특징이에요 — 정렬도 좌표압축도 하지 않습니다.

```text
총식 = Θ(n + q) 시간 + Θ(n) 추가 메모리
       └ 채우기 Θ(n) + 질의 q 개 × Θ(1)     └ 누적합 배열 n+1 칸. 입력 배열은 읽기만 한다
```

<!--proof:perf-total-->

```text
n = q = 100,000 이면 덧셈·뺄셈이 정확히 200,000 번, 누적합 배열은 100,001 칸이다
```

**보장의 종류는 최악 보장입니다.** 기댓값이 아니에요. 코드에 난수가 하나도 없고 입력 분포에 대한 가정도
하지 않으니, 어떤 배열과 어떤 질의를 넣어도 산술 연산이 `n + q` 번이라는 것이 그대로 약속입니다.

```text
기댓값이면      같은 입력을 두 번 넣었을 때 값이 다를 수 있다   ← 이 절차는 해당 없다
최악 보장이면   어떤 입력이든 상한 아래다                       ← 이쪽이다
                └ 여기서는 상한이 아니라 정확한 값이라 더 강하다
```

#### 최악을 만드는 입력

연산을 최대로 만드는 방법은 하나뿐입니다 — **`n` 과 `q` 를 규모의 최댓값으로 두는 것**이에요. 질의의
모양은 아무 상관이 없습니다. 같은 `n` 과 `q` 에서 질의의 모양만 셋으로 바꿔 연산 수를 실제로 셌습니다.

<!--proof:worst-shape-->

| 질의의 모양 (n = q = 1,000) | 평균 구간 길이 | 직접 더하기 | 누적합 배열 |
| --- | ---: | ---: | ---: |
| 전부 배열 전체 | 1,000 | 1,000,000 | 2,000 |
| 전부 한 칸짜리 | 1 | 1,000 | 2,000 |
| 길이가 하나씩 늘어남 | 500.5 | 500,500 | 2,000 |

누적합 배열의 열은 세 줄이 모두 같습니다. 직접 더하기는 가장 긴 모양과 가장 짧은 모양이 1,000 배 차이입니다.

<!--/proof-->

**「긴 구간을 묻는 질의가 느리다」는 이 절차에서 거짓입니다.** 물려받은 통념이 여기서는 성립하지 않아요.
그래서 최악은 질의의 모양이 아니라 규모로만 만들어지고, 규모의 끝에서도 산술 연산이 200,000 번이라 예산
1 초보다 한참 적습니다. 남는 비용은 결과 배열 `q` 칸을 만드는 것인데, 그것은 어떤 절차를 써도 똑같이
듭니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 질의마다 구간을 직접 더하던 것을 **누적합 배열 두 칸의
뺄셈**으로 바꿨고, 배열이 정적이라 누적합 배열을 한 번만 채우면 되며, 칸이 언제나 「앞 몇 칸의 합」이라는
것이 답의 근거입니다.

```text
n+1 칸으로 잡는다 → 앞에서부터 한 번 더해 채운다 → 질의마다 두 칸을 빼서 답한다
   └ P[0]=0 이 분기를 없앤다   └ 덧셈 n 번          └ 뺄셈 q 번, 구간 길이와 무관
```

먼저 답이 붙는 문제 하나입니다. 전개의 T10 은 질의 `[4,4]` 를 답했는데, 구간이 한 칸뿐인데도 누적합
배열에서 **두 칸**을 읽었어요. 한 칸짜리 구간이면 `A[4]` 를 그냥 읽는 편이 빠르지 않을까요?

<!--proof:selfcheck-t10-->

```text
T10  l = 4  r = 4  P[5] = 14  P[4] = 9  답 5
      └ 구간이 한 칸인데 읽은 칸이 둘이다. A[4] 하나를 직접 읽으면 한 칸이다
```

<!--check:single-cell-->
그 질의 하나만 보면 빠릅니다. 다만 그러려면 `l === r` 인지 검사하는 분기가 **모든** 질의에 하나씩 붙어요.
한 칸짜리 질의에서는 읽기 하나를 아끼지만, 나머지 질의에서는 검사 하나가 그대로 늘어납니다. 한 칸짜리
질의가 드물면 전체 연산은 오히려 늘어요. 더 중요한 것은 「짚고 가기」에서 확인한 자리와 같은 이유입니다.
분기를 하나 더하면 그 분기가 틀릴 자리가 하나 생겨요. `P[0] = 0` 을 둔 것도 분기를 없애려던 것이었습니다.

```text
분기가 없을 때    모든 질의      읽기 2 + 뺄셈 1
분기가 있을 때    한 칸짜리      검사 1 + 읽기 1
                  그 밖의 질의   검사 1 + 읽기 2 + 뺄셈 1
```
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「알아 두면 좋은 개념」, 「불변식」의 깨뜨려 보기와
전개의 T2~T7, 「경쟁 설계와의 대조」를 다시 보세요.

- 배타적 논리합(XOR)에는 역원이 자기 자신이라 앞에서부터의 값 둘로 구간 값이 나옵니다.
  `A = [3, 1, 4, 1, 5, 9]` 의 누적 XOR 배열을 손으로 채우고, 구간 `[2,5]` 의 XOR 을 두 칸으로 구해
  보세요.
- 채우는 줄을 `P[i + 1] = P[i] + A[i + 1]` 로 바꾸면 전개의 T2~T7 에서 어떤 칸이 채워질까요? 배열 끝에서
  무슨 일이 생기는지까지 확인해 보세요.
- 갱신이 섞인 과제에서 누적합 배열을 쓰되 **다시 채우지 않는** 방법을 하나 생각해 보세요. 갱신을 모아
  두었다가 질의 때 반영하는 길이 있습니다. 그때 질의 비용이 얼마가 되는지가 답입니다.

### 구간 합 질의 (정적 배열)

풀 파일: [`prefixSumRangeQuery.ts`](./prefixSumRangeQuery.ts) · 테스트: [`prefixSumRangeQuery.test.ts`](./prefixSumRangeQuery.test.ts) · 실행: `bun test src/algorithms/array/prefixSumRangeQuery/prefixSumRangeQuery.test.ts`

#### 한 줄 요약

> 정수 배열과 구간 질의 목록을 받아, **각 질의에 해당하는 구간 합**을 순서대로 담은 배열을 반환한다.

#### 스토리

도서관 사서 유진은 서가에 꽂힌 책들의 쪽수를 기록한 목록을 가지고 있다. 서가는 절대 바뀌지 않는다.

독서 클럽 회원들이 질문을 쏟아낸다. "서가 인덱스 $l$번부터 $r$번까지의 책을 모두 읽으면 총 몇 쪽이야?" 같은 질의다. 질의는 수없이 들어오지만 서가 목록 자체는 변하지 않는다.

유진은 모든 질의의 결과를 빠르게 계산해 순서대로 반환해야 한다.

#### 함수 인터페이스

```ts
export function prefixSumRangeQuery(
  A: number[],
  queries: Array<[number, number]>,
): number[];
```

- `A` — 정적 정수 배열. 질의 중 변경되지 않는다.
- `queries` — 질의 목록. 각 원소 `[l, r]`은 인덱스 $[l, r]$ 구간의 합을 요청한다.
- 반환 — 각 질의의 합을 입력 순서대로 담은 배열.

#### 제약 조건

- $1 \leq N \leq 100{,}000$ (여기서 $N$은 `A`의 길이)
- $0 \leq Q \leq 100{,}000$ (여기서 $Q$는 `queries`의 길이)
- $-10{,}000 \leq A[i] \leq 10{,}000$ (정수)
- 각 질의 $[l, r]$는 $0 \leq l \leq r \leq N - 1$
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

각 질의 $[l, r]$에 대해

$$\text{sum}(l, r) = \sum_{k=l}^{r} A[k]$$

을 계산한다. 배열 $A$는 질의 중 변하지 않는다(정적). 질의가 없으면 빈 배열을 반환한다. 동일한 질의가 여러 번 들어와도 각각 개별 결과로 반환한다.

#### 예시

```ts
prefixSumRangeQuery(
  [1, 2, 3, 4, 5],
  [[0, 4], [1, 3], [2, 2], [0, 0]],
); // [15, 9, 3, 1]
// [0,4]: 1+2+3+4+5=15, [1,3]: 2+3+4=9, [2,2]: 3, [0,0]: 1

prefixSumRangeQuery([-1, 2, -3, 4], [[0, 3], [1, 2]]);
// [2, -1]  — [0,3]: -1+2-3+4=2, [1,2]: 2+(-3)=-1

prefixSumRangeQuery([1, 2, 3], []);
// []  — 질의 없음

prefixSumRangeQuery([10, 20, 30], [[0, 0], [2, 2], [0, 2]]);
// [10, 30, 60]  — 첫 원소, 마지막 원소, 전체 합
```

### Genomic Range Query

풀 파일: [`genomicRangeQuery.ts`](./genomicRangeQuery.ts) · 테스트: [`genomicRangeQuery.test.ts`](./genomicRangeQuery.test.ts) · 실행: `bun test src/algorithms/array/prefixSumRangeQuery/genomicRangeQuery.test.ts`

#### 한 줄 요약

> 함수는 DNA 문자열과 구간 쿼리 배열을 받아, 각 구간 내 뉴클레오타이드의 최소 충격 지수를 반환한다.

#### 스토리

생물학 연구소에서 DNA 서열을 분석하는 팀이 있다. DNA는 A, C, G, T 네 종류의 뉴클레오타이드로 구성된 긴 문자열로 기록된다. 각 뉴클레오타이드는 실험 반응 강도를 나타내는 충격 지수(impact factor)를 가지며, A는 1, C는 2, G는 3, T는 4다.

연구팀은 매일 수천 건의 구간 분석 요청을 처리해야 한다. 분석 요청마다 DNA 서열의 특정 구간 $[P, Q]$를 지정하고, 그 구간에 존재하는 뉴클레오타이드 중 충격 지수가 가장 낮은 값을 알고 싶어 한다. 충격 지수가 낮은 뉴클레오타이드가 해당 구간의 반응을 지배하기 때문이다.

단 한 번의 DNA 서열 전처리로 이후의 모든 구간 쿼리를 빠르게 처리할 수 있어야 한다.

#### 함수 인터페이스

```ts
export function solution(S: string, P: number[], Q: number[]): number[];
```

- `S` — 대문자 `A`, `C`, `G`, `T`로만 구성된 DNA 문자열 (길이 $N$)
- `P` — 쿼리 구간의 시작 인덱스 배열 (길이 $M$)
- `Q` — 쿼리 구간의 종료 인덱스 배열 (길이 $M$), $P[K] \leq Q[K]$
- 반환 — 길이 $M$인 정수 배열. $K$번째 값은 구간 $[P[K], Q[K]]$에 속한 뉴클레오타이드의 최소 충격 지수

#### 제약 조건

- $1 \leq N \leq 100{,}000$ ($N$은 문자열 $S$의 길이)
- $1 \leq M \leq 50{,}000$ ($M$은 배열 $P$, $Q$의 길이)
- $0 \leq P[K] \leq Q[K] \leq N - 1$
- $S$는 대문자 영문자 `A`, `C`, `G`, `T`로만 구성
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

뉴클레오타이드의 충격 지수는 다음과 같이 정의된다.

$$\text{impact}(c) = \begin{cases} 1 & c = \text{A} \\ 2 & c = \text{C} \\ 3 & c = \text{G} \\ 4 & c = \text{T} \end{cases}$$

$M$개의 쿼리 $(P[K],\, Q[K])$에 대해, 구간 $[P[K],\, Q[K]]$ 내 최소 충격 지수를 계산한다.

$$\text{answer}[K] = \min_{P[K] \leq i \leq Q[K]} \text{impact}(S[i])$$

#### 예시

```ts
solution("CAGCCTA", [2, 5, 0], [4, 5, 6]);
// [2, 4, 1]
// 구간 [2,4] = "GCC" → impact(G)=3, impact(C)=2 → min=2
// 구간 [5,5] = "T"   → impact(T)=4 → min=4
// 구간 [0,6] = "CAGCCTA" → A 포함 → min=1

solution("ACGT", [0, 1, 2, 3], [0, 1, 2, 3]);
// [1, 2, 3, 4] — 각 단일 위치의 충격 지수 그대로

solution("AAAA", [0, 0], [3, 1]);
// [1, 1] — 모든 구간에 A만 존재

solution("T", [0], [0]);
// [4] — 단일 뉴클레오타이드, T의 충격 지수
```

### Tape Equilibrium

풀 파일: [`tapeEquilibrium.ts`](./tapeEquilibrium.ts) · 테스트: [`tapeEquilibrium.test.ts`](./tapeEquilibrium.test.ts) · 실행: `bun test src/algorithms/array/prefixSumRangeQuery/tapeEquilibrium.test.ts`

#### 한 줄 요약

> 함수는 정수 배열을 받아, 배열을 두 비어있지 않은 부분으로 나눌 때 두 부분의 합 차이 절댓값의 최솟값을 반환한다.

#### 스토리

물류 창고에서 테이프 컨베이어 위에 $N$개의 짐이 순서대로 올려져 있다. 각 짐에는 무게가 적혀 있다. 테이프를 어느 지점에서 잘라서 두 구간으로 나눌 수 있는데, 양쪽 구간은 반드시 짐이 하나 이상 있어야 한다.

균형 운반을 위해 두 구간의 무게 합 차이가 최소가 되도록 자르려 한다. 자르는 위치는 테이프 위 어디서든 가능하지만 양 끝을 잘라 한쪽이 비게 되면 안 된다.

모든 자르는 위치를 고려했을 때, 두 구간 합의 차이 절댓값이 가장 작은 경우의 값을 구하라.

#### 함수 인터페이스

```ts
export function tapeEquilibrium(A: number[]): number;
```

- `A` — 길이 $N \geq 2$인 정수 배열
- 반환 — 가능한 모든 분할에 대한 두 부분 합 차이 절댓값의 최솟값

#### 제약 조건

- $2 \leq N \leq 100{,}000$ ($N$은 `A`의 길이)
- 각 원소는 $-1{,}000 \leq A[i] \leq 1{,}000$인 정수
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

정수 $P$ ($1 \leq P \leq N-1$)로 배열을 다음 두 부분으로 나눈다.

- 왼쪽 부분: $A[0], A[1], \ldots, A[P-1]$
- 오른쪽 부분: $A[P], A[P+1], \ldots, A[N-1]$

분할 지점 $P$에서의 차이값은 다음과 같다.

$$D(P) = \left| \sum_{i=0}^{P-1} A[i] \;-\; \sum_{i=P}^{N-1} A[i] \right|$$

가능한 모든 $P$에 대해 $D(P)$의 최솟값을 반환한다.

$$\text{tapeEquilibrium}(A) = \min_{1 \leq P \leq N-1} D(P)$$

#### 예시

```ts
tapeEquilibrium([3, 1, 2, 4, 3]);
// 1
// P=1: |3 - 10| = 7
// P=2: |4 - 9|  = 5
// P=3: |6 - 7|  = 1  ← 최솟값
// P=4: |10 - 3| = 7

tapeEquilibrium([1, 2]);
// 1 — P=1만 가능: |1 - 2| = 1

tapeEquilibrium([-1000, 1000]);
// 2000 — P=1: |-1000 - 1000| = 2000

tapeEquilibrium([5, 5, 5, 5]);
// 0 — P=2: |10 - 10| = 0

tapeEquilibrium([5, 5, 5]);
// 5 — P=1: |5 - 10| = 5, P=2: |10 - 5| = 5, 최솟값 5
```
