# 행렬 체인 곱셈 최소 비용 — 마지막으로 곱하는 자리 하나가 나머지를 두 조각으로 가른다

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 괄호 배치를 전부 만들어
보는 방법에서 표 채우기까지 가는 경로를 따라갑니다. 마지막에는 그 표를 채우는 코드를
조각째로 세워 봅니다.

### 전체 컨셉

행렬 여러 개를 **주어진 순서 그대로** 곱합니다. 순서는 바꿀 수 없지만 **어느 쪽을 먼저 묶어
곱할지**는 자유롭고, 묶는 방식에 따라 실제 곱셈 횟수가 크게 갈려요. 가장 적은 곱셈 횟수를
답하는 것이 목표입니다.

```text
행렬 넷을 차원 배열 p = [10, 30, 5, 60, 10] 하나로 적는다

  A1  10×30      A2  30×5      A3  5×60      A4  60×10
        └ 행렬 A_i 의 크기는 p[i-1] × p[i] 다. 이웃한 두 행렬은 만나는 차원이 같다

  10×30 행렬과 30×5 행렬을 곱하면 스칼라 곱셈이 10 · 30 · 5 = 1500 번 일어난다
        └ 왼쪽의 행 수 · 두 행렬이 만나는 차원 · 오른쪽의 열 수
```

행렬 넷을 묶는 방법은 다섯 가지이고, 그 다섯이 내는 곱셈 횟수는 여섯 배 넘게 갈립니다.

```text
괄호 배치 다섯과 각각의 곱셈 횟수

  ((A1A2)(A3A4))    5,000   ← 가장 적다
  (A1(A2(A3A4)))    7,500
  (((A1A2)A3)A4)   10,500
  (A1((A2A3)A4))   30,000
  ((A1(A2A3))A4)   33,000
```

배치를 전부 만들어 견주는 길은 곧 막힙니다. 행렬이 하나 늘 때마다 배치 수가 두 배 이상씩
늘어나(1 · 2 · 5 · 14 · 42 …), 이 문제의 상한인 100 개에서는 57 자리 수가 돼요.

**답이 횟수 하나**라는 것이 이 알고리즘의 관찰입니다. 어느 배치가 그 횟수를 냈는지는 묻지
않으니, **같은 구간을 하나로 곱하는 서로 다른 배치끼리는 구분할 이유가 없어요.** 그래서
배치 대신 「그 구간을 하나로 곱하는 최소 곱셈 횟수」만 기억합니다.

```text
표 한 칸 = "행렬 A_i 부터 A_j 까지를 하나로 곱하는 최소 곱셈 횟수"
           -  = i > j 라 구간이 아니다

         j=1    j=2    j=3    j=4
  i=1      0  1,500  4,500  5,000
  i=2      -      0  9,000  4,500
  i=3      -      -      0  3,000
  i=4      -      -      -      0
           └ 대각선(i = j)은 행렬 하나짜리 구간이라 곱셈이 없다
                            ↑ 오른쪽 위 칸이 답이다
```

`i` 행 `j` 열 칸을 `dp[i][j]` 로 적겠습니다. 한 칸을 정하는 규칙은 둘로 갈려요.

| 구간의 모양 | 그 칸에 적을 값 |
| --- | --- |
| 행렬 하나 (`i = j`) | 0 |
| 그보다 길다 | `i ≤ k < j` 인 자리마다 **왼쪽 조각 + 오른쪽 조각 + 합치는 비용**을 만들어, 그중 가장 작은 값 |

`k` 가 **마지막으로 곱하는 자리**이고 이 알고리즘의 전부입니다. 어느 배치든 맨 마지막 곱셈은
한 번뿐이고, 그 곱셈이 어디를 경계로 삼았는지가 `k` 예요. 경계를 하나 정하면 남은 일이 서로
겹치지 않는 두 구간으로 갈립니다.

```text
dp[1][4] 를 정하는 장면 — 후보가 셋이다

  k=1   A1 | A2A3A4      0 + 4,500 + (10 · 30 · 10) =  7,500
  k=2   A1A2 | A3A4  1,500 + 3,000 + (10 ·  5 · 10) =  5,000   ← 가장 작다
  k=3   A1A2A3 | A4  4,500 +     0 + (10 · 60 · 10) = 10,500
                                           └ 가운데 항은 두 조각이 만나는 차원이다
```

행렬이 `n` 개면 표는 `(n+1) × (n+1)` 칸을 잡고 그중 위쪽 삼각형 `n(n+1)/2` 칸만 씁니다. 칸
하나가 견주는 후보는 구간에 든 행렬 수보다 하나 적으므로, 배치를 전부 만들던 일이 후보
`(n³ − n)/6` 개를 견주는 일로 내려와요. 행렬 100 개면 칸 10,201 개에 후보 166,650 개라
1 초 안에 끝납니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **행렬 곱셈의 크기 규칙.** `10×30` 행렬과 `30×5` 행렬을 곱하면 `10×5` 가 되고, 그때
  스칼라 곱셈이 `10 · 30 · 5` 번 일어납니다. 이 글은 그 횟수만 셉니다.
- **결합 법칙과 교환 법칙이 다르다는 것.** 행렬 곱은 묶는 방식을 바꿔도 결과가 같지만
  (결합), 행렬의 **차례**를 바꾸면 결과가 달라지거나 아예 곱할 수 없습니다.
- **`dp[i][j]` 같은 2차원 첨자 읽기.** 표의 행과 열을 좌표로 가리킵니다.

몰라도 되는 것은 재귀·메모이제이션·그래프 탐색이에요. 표를 대각선부터 오른쪽 위로 채우는
반복문 세 겹만 씁니다. 표를 쓰는 이웃 편들과 **두 축이 다르다**는 것만 미리 적어 둘게요 —
[0/1 배낭](../knapsack01/knapsack01-guide.md) 과
[부분집합 합 판정](../subsetSum/subsetSum-guide.md) 은 행이 「항목 수」이고 열이 「용량」이라
표가 위에서 아래로 진행하는데, 이 편은 행과 열이 둘 다 행렬 번호라 **대각선에서 시작해
오른쪽 위로** 진행합니다.

### 아이디어 상세 — 구간마다 최소 곱셈 횟수를 적는 표를 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function matrixChainMultiplication(dims: number[]): number;
```

- 입력: 차원 배열 `dims`. 길이가 `n + 1` 이고 `i` 번째 행렬의 크기가 `dims[i-1] × dims[i]` 다.
- 출력: **최소 스칼라 곱셈 횟수 하나**. 어느 배치가 그 횟수를 냈는지는 묻지 않아요. 행렬이
  한 개 이하면 곱셈이 없어 0 입니다.
- 제약: 행렬 수 `n ≤ 100`, 차원 각각 1 이상 500 이하. 시간 1 초, 메모리 256 MB.

여기서 눈여겨볼 것이 둘 있어요. **행렬의 차례를 바꿀 수 없다**는 것과, **이웃한 두 행렬이
만나는 차원이 같다**는 것입니다.

```text
차례를 바꿀 수 없다
  묶는 방식만 고르는 문제다  → 답이 "괄호를 어디에 치는가" 하나로 좁혀진다

만나는 차원이 같다
  A_i … A_k 를 하나로 곱하면 크기가 p[i-1] × p[k] 다
  A_(k+1) … A_j 를 하나로 곱하면 크기가 p[k] × p[j] 다
    → 두 조각을 합치는 비용이 두 조각의 내용과 무관하게 p[i-1] · p[k] · p[j] 로 정해진다
```

지금은 그냥 넘어가도 됩니다. 두 성질이 각각 필요해지는 자리가 뒤에 옵니다.

이 글이 끝까지 쓰는 기호는 일곱입니다. 여기서 정한 뜻을 파트 2 까지 그대로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 행렬의 개수 | `n ≤ 100` |
| `p` | 차원 배열. 길이가 `n + 1` 이다 | 각 원소가 1 이상 500 이하 |
| `i` | 구간의 왼쪽 끝 행렬 번호. 표의 행 | `1 ≤ i ≤ n` |
| `j` | 구간의 오른쪽 끝 행렬 번호. 표의 열 | `i ≤ j ≤ n` |
| `k` | 마지막으로 곱하는 자리. 구간을 `A_i … A_k` 와 `A_(k+1) … A_j` 로 가른다 | `i ≤ k < j` |
| `L` | 구간에 든 행렬 수 `j − i + 1`. 표를 채우는 차례를 정한다 | `1 ≤ L ≤ n` |
| `dp[i][j]` | 행렬 `A_i … A_j` 를 하나로 곱하는 최소 스칼라 곱셈 횟수 | 이것이 표의 한 칸 |

차원 배열만 이름이 둘입니다 — 이 글에서 `p` 이고 코드에서는 `dims` 인데, 문제가 정한 인자
이름을 그대로 두었기 때문이에요.

가장 먼저 떠오르는 방법으로 시작합시다. 마지막 곱셈의 경계를 한 자리씩 잡아 보고, 갈린 두
조각을 같은 방법으로 다시 푸는 것입니다.

```ts
function 완전탐색(p: number[], i: number, j: number): number {
  if (i === j) return 0;
  let best = Number.POSITIVE_INFINITY;
  for (let k = i; k < j; k++) {
    const cost =
      완전탐색(p, i, k) + 완전탐색(p, k + 1, j) + p[i - 1]! * p[k]! * p[j]!;
    if (cost < best) best = cost;
  }
  return best;
}
```

이 방법은 **경계를 잡을 때마다 두 갈래로 내려갑니다.** 그러니 호출 수가 곧 일의 양이고,
행렬이 늘면 그 수가 배로 불어나요. 행렬 `n` 개짜리 구간 하나를 푸는 호출 수를 `R(n)` 이라
적으면, 경계가 왼쪽에 `q` 개를 두는 갈래마다 두 조각을 다시 부르므로
`R(n) = 1 + Σ_q (R(q) + R(n−q))` 입니다. 실제로 실행해 세어 보고 그 점화식으로 큰 `n`
까지 이어 봅시다.

```text
행렬 수  실제로 세어 본 호출  점화식이 내는 호출 수  구간 수
2                          3                      3        3
3                          9                      9        6
4                         27                     27       10
6                        243                    243       21
8                      2,187                  2,187       36
10                    19,683                 19,683       55
12                   177,147                177,147       78
100              세지 못했다           1.71 × 10^47    5,050
```

행렬이 하나 늘 때마다 호출 수가 정확히 세 배가 되고, 제약 최대인 100 개에서는 48 자리 수예요
— **아무것도 기억하지 않는 재귀는 여기서 실행이 안 끝납니다.** 오른쪽 끝의 구간 수와 견주면
자릿수 자체가 다릅니다.

```text
경계를 잡을 때마다 두 갈래로 내려간다  → 호출 수가 1.71 × 10^47
                                        └ 답은 횟수 하나인데 일의 양이 이만큼인가?
```

그러면 이 재귀가 무엇을 낭비하는지 봅시다. `A2 … A3` 를 푸는 일은 어느 구간 안에서
내려왔든 **완전히 같은 일**입니다.

```text
행렬 다섯 개짜리 입력에서 A2 … A3 에 이르는 두 걸음짜리 길

  A1 … A5 를 k=3 에서 가른다  →  왼쪽 A1 … A3 을 k=1 에서 가른다   →  A2 … A3
  A1 … A5 를 k=1 에서 가른다  →  오른쪽 A2 … A5 를 k=3 에서 가른다  →  A2 … A3
  더 깊은 길까지 세면 이 구간 하나가 다섯 번 다시 계산된다

  구간의 두 끝이 같으면 그 안에서 할 수 있는 일도, 최소 횟수도 같다
  답이 횟수 하나라서, 바깥에서 어떻게 내려왔는지는 물어보지 않는다
```

같은 입력을 두 방식으로 처리하고 구간마다 횟수를 세 봅니다. 왼쪽은 재귀가 그 구간을 실제로
다시 푼 횟수이고, 오른쪽은 **구간마다 값을 한 번만 정했을 때**의 횟수예요. 행렬 다섯 개로
두면 차이가 확인됩니다.

<!--proof:sameInterval-->

```text
구간     재귀가 그 구간을 푼 횟수  구간마다 한 번만 정하면
A1 … A1                         8                        1
A1 … A2                         4                        1
A1 … A3                         2                        1
A1 … A4                         1                        1
A1 … A5                         1                        1
A2 … A2                        12                        1
A2 … A3                         5                        1
A2 … A4                         2                        1
A2 … A5                         1                        1
A3 … A3                        14                        1
A3 … A4                         5                        1
A3 … A5                         2                        1
A4 … A4                        12                        1
A4 … A5                         4                        1
A5 … A5                         8                        1
합계                           81                       15
```

81 이 15 가 됐습니다. 오른쪽에서 눈여겨볼 것은 **횟수에 상한이 있다**는 점이에요. 행렬을
아무리 늘려도 서로 다른 구간은 두 끝을 고르는 `n(n+1)/2` 가지뿐이고, 이 관찰이 다음 걸음의
재료입니다.

```text
행렬 5 개    구간 15 개    재귀가 푼 횟수 81    →  5.4 배
행렬 100 개  구간 5,050 개  재귀가 푼 횟수 1.71 × 10^47
```

여기가 준비의 끝입니다. 비용은 **서로 다른 구간이 몇 개인지**로 세면 되고, 남은 질문은 「그
값을 어떤 차례로 정해야 읽는 칸이 이미 정해져 있는가」 하나예요. 가장 손이 덜 가는 후보부터
실행해 봅니다 — 구간마다 `k` 를 전부 시험하는 대신 **한 자리로 고정**하는 것입니다. 왼쪽
끝에서 가르는 판(`k = i`)과 오른쪽 끝에서 가르는 판(`k = j−1`)을 같은 입력들에 실행해 봅시다.

<!--proof:splitRule-->

```text
차원 배열             k = i 로 고정  k = j−1 로 고정  k 를 전부 시험
[10, 30, 5, 60, 10]           7,500           10,500           5,000
[10, 30, 5, 60]              27,000            4,500           4,500
[10, 20, 30, 40, 30]         60,000           30,000          30,000
[40, 20, 30, 10, 30]         51,000           48,000          26,000
[2, 3, 4, 2, 5]                 130               60              56
[1, 2, 3, 4]                     32               18              18
[5, 5, 5, 5]                    250              250             250
```

고정 규칙 둘은 **우연히 맞기도 합니다.** `[10, 30, 5, 60]` 과 `[10, 20, 30, 40, 30]` 에서
`k = j−1` 이 최소와 같고, `[5, 5, 5, 5]` 는 세 판이 다 250 이에요. 그런데 같은 규칙이
`[40, 20, 30, 10, 30]` 에서는 48,000 대 26,000 으로 1.8 배 어긋납니다.

```text
k 를 한 자리로 고정하면
  구간 하나에 대해 배치를 하나만 만들어 본 것이다
  그 배치가 그 구간의 최소인지는 아무도 확인하지 않았다

k 를 i 부터 j−1 까지 전부 시험하면
  구간 하나가 만들 수 있는 마지막 곱셈이 j − i 가지뿐이므로 전부 본 것이다
```

**`k` 를 전부 시험합니다.** 그러면 각 상태 변수의 범위도 정해져요. 위 표의 세 번째 열이 그
범위로 채운 결과입니다.

```text
i   1 부터 n 까지        구간의 왼쪽 끝이므로 행이 n 개
j   i 부터 n 까지        구간의 오른쪽 끝이므로 i 보다 왼쪽 칸은 안 쓴다
k   i 부터 j−1 까지      구간 하나가 견주는 후보가 j − i 개
    → 칸은 n(n+1)/2 개, 후보는 다 합쳐 (n³ − n)/6 개
```

**두 조각을 읽어 오는 동작을 값으로 확인해 봅시다.** 읽는 칸이 준비돼 있는 경우와 준비를
따져 봐야 하는 경우를 나눕니다. 앞은 길이 2 인 구간이에요 — 두 조각이 다 길이 1 이라 0 이고,
합치는 비용만 남습니다.

```text
dp[1][2] 를 정한다 (구간 A1 … A2)
  후보는 k=1 하나뿐이다
  왼쪽 dp[1][1] = 0 · 오른쪽 dp[2][2] = 0 · 합치는 비용 10 · 30 · 5 = 1500
  dp[1][2] = 1500
```

불안한 경우는 긴 구간입니다. **두 조각의 값을 읽어야 하는데, 그 두 칸이 이미 정해져 있는지**가
문제예요. 길이 4 인 구간을 정할 때 읽는 칸을 전부 적어 봅니다.

```text
dp[1][4] 를 정할 때 읽는 칸

  k=1   dp[1][1] (길이 1)  dp[2][4] (길이 3)
  k=2   dp[1][2] (길이 2)  dp[3][4] (길이 2)
  k=3   dp[1][3] (길이 3)  dp[4][4] (길이 1)
          └ 여섯 칸의 길이가 전부 4 보다 짧다
```

읽는 칸이 **언제나 더 짧은 구간**이라 건너뛰는 자리가 없습니다. 두 조각을 합치면 원래 구간이
되고 `k` 가 `i` 이상 `j` 미만이라, 두 조각 중 어느 쪽도 빈 구간이 아니고 어느 쪽도 원래 구간
전체가 아니에요. 왜 맞는지를 반복문의 종료 조건으로 말하면, **길이 `L` 인 칸을 정하기 전에
길이 `L−1` 이하인 칸을 전부 지나갔기 때문**입니다.

```text
L = 1  →  L = 2  →  L = 3  →  L = 4
네 칸     세 칸     두 칸     한 칸
  └ 길이 L 인 칸이 읽는 두 조각은 길이가 L−1 이하다
```

마지막으로 **표를 어떤 차례로 채울 것인지**를 값으로 정합니다. 길이가 짧은 구간부터 채우는
것과, 반복문 두 겹을 그냥 `i` 를 1 부터 늘리게 두는 것과, `i` 를 `n` 부터 줄이게 두는 것
셋을 같은 입력들에 실행해 봅시다.

<!--proof:fillOrder-->

```text
채우는 순서                [10, 30, 5, 60, 10]  [10, 20, 30, 40, 30]  [2, 3, 4, 2, 5]
길이가 짧은 구간부터                     5,000                30,000               56
i 를 1 부터 · j 를 i 부터                2,000                 6,000               30
i 를 n 부터 · j 를 i 부터                5,000                30,000               56
```

| 채우는 순서 | 답 | 판정 |
| --- | --- | --- |
| 길이가 짧은 구간부터 | 맞다 | 두 조각이 다 더 짧은 구간이라 언제나 정해져 있다 |
| `i` 를 1 부터 · `j` 를 `i` 부터 | 틀린다 | `dp[i][j]` 가 읽는 `dp[k+1][j]` 는 **아래 행**이라 아직 0 이다 |
| `i` 를 `n` 부터 · `j` 를 `i` 부터 | 맞다 | 아래 행을 먼저 끝내므로 읽는 칸이 정해져 있다 |

**가운데 줄이 최소보다 작게 나온 것**이 이 표에서 눈여겨볼 자리입니다. 5,000 이 나와야 할
칸에서 2,000 이 나왔어요 — 아직 아무 값도 안 들어간 0 을 조각의 값으로 읽었으니, 조각을
공짜로 만든 셈입니다. 답이 커지는 것이 아니라 **작아지는** 쪽으로 틀립니다.

```text
dp[1][4] 의 k=1 후보를 두 차례에서 각각 만들어 보면

  i 를 1 부터 늘리면   dp[2][4] 가 아직 0     →      0 + 3,000 =  3,000
  길이 짧은 쪽부터     dp[2][4] 가 이미 4,500  →  4,500 + 3,000 =  7,500
                         └ 두 조각이 원래 구간보다 짧다는 것이 차례를 정한다
```

세 번째 줄도 맞습니다. `dp[i][j]` 가 읽는 칸은 **같은 행의 왼쪽**(`dp[i][k]`)과 **아래 행**
(`dp[k+1][j]`) 둘인데, 행을 아래에서 위로 올라가면 아래 행이 먼저 끝나거든요. 이 글은 길이
차례를 씁니다 — 표에서 무엇이 언제 정해지는지가 길이로 말할 때 가장 짧게 적히기 때문입니다.

**표 한 장이 나왔습니다.** 행이 `i = 1 … n`, 열이 `j = i … n`, 칸에 최소 곱셈 횟수를 적는
것이고, `n = 4` 면 쓰는 칸이 열 개입니다. 배치를 `2.27 × 10^56` 개까지 만들던 일이, 후보
`(n³ − n)/6` 개를 견주는 표 채우기가 됐어요.

### 수행으로 알아보는 알고리즘 — 표 열 칸으로 괄호 배치 다섯을 대신한다

세운 아이디어를 **실제로 동작하는 코드**로 옮길 차례입니다. 차원 배열 하나를 끝까지 고정해
두고 조각을 셋으로 나눠 세우되, 조각마다 그때까지 채워진 표를 실행해서 확인합니다.

```ts
const dims = [10, 30, 5, 60, 10];
// 이 절이 끝나면 5000 이 나와야 한다 (((A1A2)(A3A4)))
```

차원을 왜 하필 이 값으로 뒀을까요? 셋을 한꺼번에 확인하려는 것입니다. **첫째,** 길이 3 인
구간 둘이 후보 둘에서 각각 27,000 대 4,500 으로 여섯 배 갈려 어느 후보가 왜 골라지는지가
값으로 나와요. **둘째,** 마지막 칸의 후보 셋이 7,500 · 5,000 · 10,500 이라 **가운데 후보가
최소**입니다 — 첫 후보나 마지막 후보가 답이면 고정 규칙과 구분이 안 됩니다. **셋째,** 다섯
배치의 최대와 최소가 33,000 대 5,000 으로 6.6 배라 배치를 잘못 고르면 얼마나 손해인지가
보여요.

```text
표 dp 를 (n+1) × (n+1) 로 만들고 전부 0 으로 둔다        ② 길이 1 구간은 0

L 을 2 부터 n 까지:
    i 를 1 부터 i + L - 1 <= n 인 동안:
        j ← i + L - 1
        best ← 무한
        k 를 i 부터 j-1 까지:
            cost ← dp[i][k] + dp[k+1][j] + p[i-1] · p[k] · p[j]
            cost 가 best 보다 작으면 best ← cost          ③ 작다 · ④ 작지 않다
        dp[i][j] ← best

dp[1][n] 을 돌려준다
```

#### 1. 표를 깔고 대각선을 0 으로 둔다

「아이디어 상세」에서 구간의 길이를 1 부터 셌습니다. 길이 1 인 구간은 행렬 하나라서 곱셈이
일어나지 않고, 그 칸들이 표의 대각선이에요. 표를 0 으로 깔면 대각선이 그대로 옳은 값이 됩니다.

```ts
const n = dims.length - 1;
// ① 행렬이 한 개 이하다 — 곱셈이 일어나지 않는다.
if (n <= 1) return 0;

// dp[i][j] = 행렬 A_i … A_j 를 하나로 곱하는 데 드는 최소 스칼라 곱셈 횟수.
// ② 길이 1 구간은 곱셈이 없다 — 대각선이 0 으로 남는다.
const dp = Array.from({ length: n + 1 }, () =>
  new Array<number>(n + 1).fill(0),
);
```

실행하면 이렇게 나와요. 대각선만 뜻이 있고 나머지 위쪽 칸은 아직 안 정한 자리입니다.

```text
         j=1    j=2    j=3    j=4
  i=1      0      .      .      .    ← T1 에서 정한 대각선
  i=2      -      0      .      .
  i=3      -      -      0      .
  i=4      -      -      -      0
           -  = i > j 라 구간이 아니다
           .  = 아직 안 정했다 (0 으로 깔려 있다)
```

갈래 ①은 `dims` 가 `[10]` 이거나 `[10, 20]` 일 때 실행됩니다. 앞은 행렬이 0 개, 뒤는 1 개라
둘 다 곱셈이 없어 0 이에요. 이 분기가 없으면 `n = 0` 에서 표가 한 칸짜리가 되고 `dp[1][0]`
을 읽어 버립니다.

| 표를 왜 `(n+1) × (n+1)` 로 잡는가 | |
| --- | --- |
| 행이 `n + 1` 개 | 행렬 번호를 1 부터 쓰려고 0 번 행을 비워 둔다 |
| 열이 `n + 1` 개 | 같은 이유로 0 번 열을 비워 둔다 |

첨자를 1 부터 쓰는 것은 편의가 아닙니다. 행렬 `A_i` 의 크기가 `p[i-1] × p[i]` 라서, `i` 를
0 부터 세면 차원 배열의 첨자가 음수가 되는 자리가 생겨요.

#### 2. 길이가 2 인 구간을 채운다

바깥 반복문이 구간 길이, 그 안이 왼쪽 끝입니다. 길이가 2 면 `k` 가 `i` 하나뿐이라 견줄 것이
없고, 대각선 바로 위 세 칸이 곧바로 정해져요.

```ts
for (let L = 2; L <= n; L++) {
  for (let i = 1; i + L - 1 <= n; i++) {
    const j = i + L - 1;
    // 여기서 한 칸이 정해진다
  }
}
```

`i + L - 1 <= n` 이 안쪽 반복문의 조건인 것은 오른쪽 끝이 표를 벗어나지 않게 하려는 것입니다.
길이 `L` 인 구간은 왼쪽 끝을 `1` 부터 `n − L + 1` 까지 둘 수 있어 `n − L + 1` 개예요.

```text
n = 4 일 때 길이별 구간

  L=2   A1 … A2   A2 … A3   A3 … A4      3 개
  L=3   A1 … A3   A2 … A4                2 개
  L=4   A1 … A4                          1 개
          └ 길이가 늘면 구간 수가 하나씩 줄어 대각선과 나란한 줄이 하나씩 위로 간다
```

세 칸을 실제로 채우면 이렇게 나옵니다. 두 조각이 다 0 이므로 합치는 비용이 그대로 칸 값이에요.

```text
T2  dp[1][2]  k=1   0 + 0 + (10 · 30 ·  5) =  1,500
T3  dp[2][3]  k=2   0 + 0 + (30 ·  5 · 60) =  9,000
T4  dp[3][4]  k=3   0 + 0 + ( 5 · 60 · 10) =  3,000

         j=1    j=2    j=3    j=4
  i=1      0  1,500      .      .
  i=2      -      0  9,000      .
  i=3      -      -      0  3,000
  i=4      -      -      -      0
```

#### 멈춤 — 비용이 가장 작은 이웃 쌍부터 곱해도 최소가 안 된다

위 세 값을 보면 `A1 … A2` 가 1,500 으로 가장 적습니다. 그러면 그 쌍을 먼저 곱해 하나로 만들고,
남은 셋에서 다시 가장 적은 쌍을 고르면 되지 않을까요. 사람이 손으로 계산할 때 실제로 그렇게
합니다. 여러 차원 배열에 그 방법과 최소를 나란히 실행해 봅시다.

<!--proof:greedyPairs-->

```text
차원 배열             비용이 작은 이웃 쌍부터    최소
[10, 30, 5, 60, 10]                    10,500   5,000
[10, 30, 5, 60]                         4,500   4,500
[10, 20, 30, 40, 30]                   30,000  30,000
[40, 20, 30, 10, 30]                   36,000  26,000
[2, 3, 4, 2, 5]                            60      56
[1, 2, 3, 4]                               18      18
[5, 5, 5, 5]                              250     250
```

**일곱 줄 중 넷이 같습니다.** 그래서 이 자리가 위험해요 — 몇 가지 입력으로 확인하면 통과하고,
틀린 줄 모르고 넘어갑니다. 전개 입력에서는 10,500 대 5,000 으로 2.1 배 갈리니 그 자리를 따라가
봅시다.

```text
[10, 30, 5, 60, 10] 에서 비용이 가장 작은 쌍부터 곱하면

  1) A1A2 가 1,500 으로 가장 적다 → 곱한다.  차원 배열이 [10, 5, 60, 10] 이 된다
  2) 남은 쌍은 10·5·60 = 3,000 과 5·60·10 = 3,000. 왼쪽을 곱한다 → [10, 60, 10]
  3) 마지막 곱셈 10 · 60 · 10 = 6,000
     합 1,500 + 3,000 + 6,000 = 10,500

최소는 ((A1A2)(A3A4))
  1,500 + 3,000 + (10 · 5 · 10 = 500) = 5,000
     └ 두 조각을 각각 먼저 곱해 10×5 와 5×10 으로 만들면 합치는 비용이 500 뿐이다
```

지금 가장 적은 곱셈을 고르는 결정이 **남은 차원 배열을 바꿉니다.** 2번 걸음에서 왼쪽을 고르면
60 이 남고 오른쪽을 고르면 5 가 남는데, 그 하나가 마지막 곱셈을 6,000 과 500 으로 가릅니다.
한 걸음의 이득만 보는 규칙은 그 영향을 못 셉니다.

#### 3. 길이를 늘려 후보를 전부 견준다

길이가 3 이상이면 `k` 가 둘 이상이라 견주기가 생깁니다. 후보 둘에 이름을 붙여 두고 하나씩
만드는데, `Math.min` 한 줄로 줄이면 **어느 후보가 작아서 그 값이 됐는지**가 코드에 남지 않아요.

```ts
let best = Number.POSITIVE_INFINITY;

for (let k = i; k < j; k++) {
  const left = (dp[i] as number[])[k] as number; // A_i … A_k
  const right = (dp[k + 1] as number[])[j] as number; // A_(k+1) … A_j
  // 두 조각이 만나는 자리의 차원이 dims[k] 다.
  const join =
    (dims[i - 1] as number) * (dims[k] as number) * (dims[j] as number);
  const cost = left + right + join;
  // ③ 지금까지의 최소보다 작다 · ④ 작지 않다
  if (cost < best) best = cost;
}

(dp[i] as number[])[j] = best;
```

`join` 을 만드는 줄이 이 코드에서 가장 중요합니다. 세 항 중 **가운데가 `dims[k]`** 인 것이
두 조각이 만나는 자리라는 뜻이고, 첫 항과 끝 항은 합친 결과의 크기예요.

```text
L=3 인 구간 둘에서 후보가 실제로 어떻게 나오는가

  A1 … A3   k=1   dp[1][1]=0     + dp[2][3]=9,000 + (10 · 30 · 60) = 27,000  (③)
            k=2   dp[1][2]=1,500 + dp[3][3]=0     + (10 ·  5 · 60) =  4,500  (③)
                    → dp[1][3] = 4,500, 고른 k = 2

  A2 … A4   k=2   dp[2][2]=0     + dp[3][4]=3,000 + (30 ·  5 · 10) =  4,500  (③)
            k=3   dp[2][3]=9,000 + dp[4][4]=0     + (30 · 60 · 10) = 27,000  (④)
                    → dp[2][4] = 4,500, 고른 k = 2
```

`best` 를 무한으로 열어 두는 것이 첫 후보를 그냥 받게 합니다. 첫 후보는 무한보다 언제나 작아
갈래 ③으로 들어가고, 그다음부터가 진짜 견주기예요. 두 구간 다 `k=2` 에서 27,000 이 4,500 으로
내려갔고 그 차이는 **두 조각을 각각 얼마나 작게 만들어 두었는가**에서 옵니다.

#### 멈춤 — 가운데에서 가르는 규칙은 답보다 표에서 먼저 갈린다

후보를 전부 견주는 대신 **구간의 가운데를 고르면** 되지 않을까요. 분할 정복이 대개 절반씩
가르니 자연스러운 생각이고, 견주기가 통째로 없어지니 더 빨라집니다. 전개 입력에 그대로
실행해 봅시다.

<!--proof:midSplit-->

```text
무엇                        가운데에서 가른다  전부 시험한다
전개 입력의 dp[2][4]                   27,000          4,500
전개 입력의 답 dp[1][4]                 5,000          5,000
[10, 20, 30, 40, 30] 의 답             51,000         30,000
[40, 20, 30, 10, 30] 의 답             69,000         26,000
[2, 3, 4, 2, 5] 의 답                     104             56
[1, 2, 3, 4] 의 답                         18             18
[5, 5, 5, 5] 의 답                        250            250
```

**전개 입력에서는 답이 안 틀립니다.** 둘째 줄이 5,000 으로 같아요. 그런데 첫째 줄을 보면 표
안의 `dp[2][4]` 는 이미 27,000 대 4,500 으로 여섯 배 어긋나 있습니다. 답이 맞은 것은 마지막
칸이 그 틀린 칸을 **안 읽었기** 때문이에요.

```text
dp[1][4] 를 가운데에서 가르면 k = 2 다
  읽는 칸이 dp[1][2] 와 dp[3][4] — 둘 다 길이 2 라 후보가 하나뿐이고 틀릴 수 없다
  틀린 dp[2][4] 는 k=1 후보가 읽는 칸인데, 그 후보를 아예 만들지 않았다

       j=1    j=2    j=3    j=4
  i=1    0  1,500  4,500  5,000
  i=2    -      0  9,000 27,000   ← 여기가 틀렸는데 답에 안 쓰인다
  i=3    -      -      0  3,000
  i=4    -      -      -      0
```

그래서 이 자리는 **전개 입력만 확인하면 통과합니다.** 아래 세 줄이 그 규칙이 실제로 답을
가르는 입력이에요 — `[40, 20, 30, 10, 30]` 은 69,000 대 26,000 으로 2.7 배 어긋납니다.
구간을 반으로 가르는 것이 좋은 성질을 주는 것은 **가르는 비용이 어디서 갈라도 같을 때**인데,
이 문제는 가르는 자리마다 합치는 비용이 달라요.

#### 4. 표 열 칸을 열두 단계로 채운다

#### 5. 전체 코드

조각 셋을 한 함수로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 마지막 한 줄뿐이에요 —
표의 오른쪽 위 칸을 읽어 돌려줍니다.

```ts
export function matrixChainMultiplication(dims: number[]): number {
  const n = dims.length - 1;
  // ① 행렬이 한 개 이하다 — 곱셈이 일어나지 않는다.
  if (n <= 1) return 0;

  // dp[i][j] = 행렬 A_i … A_j 를 하나로 곱하는 데 드는 최소 스칼라 곱셈 횟수.
  // ② 길이 1 구간은 곱셈이 없다 — 대각선이 0 으로 남는다.
  const dp = Array.from({ length: n + 1 }, () =>
    new Array<number>(n + 1).fill(0),
  );

  for (let L = 2; L <= n; L++) {
    for (let i = 1; i + L - 1 <= n; i++) {
      const j = i + L - 1;
      let best = Number.POSITIVE_INFINITY;

      for (let k = i; k < j; k++) {
        const left = (dp[i] as number[])[k] as number; // A_i … A_k
        const right = (dp[k + 1] as number[])[j] as number; // A_(k+1) … A_j
        // 두 조각이 만나는 자리의 차원이 dims[k] 다.
        const join =
          (dims[i - 1] as number) * (dims[k] as number) * (dims[j] as number);
        const cost = left + right + join;
        // ③ 지금까지의 최소보다 작다 · ④ 작지 않다
        if (cost < best) best = cost;
      }

      (dp[i] as number[])[j] = best;
    }
  }

  return (dp[1] as number[])[n] as number;
}
```

### 알아 두면 좋은 개념 — 볼록 다각형의 삼각분할

파트 1 에서 채운 표의 합치는 비용을 다시 봅시다. `p[i-1] · p[k] · p[j]` 였고, 첨자 셋이 전부
차원 배열의 자리였어요. 그 세 자리를 **꼭짓점 셋**으로 읽으면 표가 도형이 됩니다.

```text
차원 배열 p = [10, 30, 5, 60, 10] 를 꼭짓점 다섯의 볼록 다각형으로 읽는다

  꼭짓점   v0   v1   v2   v3   v4
  값       10   30    5   60   10        ← p 를 그대로 꼭짓점에 적는다

  변 v0–v1 = A1 (10×30)     변 v1–v2 = A2 (30×5)
  변 v2–v3 = A3 (5×60)      변 v3–v4 = A4 (60×10)
  변 v0–v4 = 전부 곱한 결과 (10×10)

  삼각형 (v_(i-1), v_k, v_j) 의 무게 = p[i-1] · p[k] · p[j]
        └ 구간 A_i … A_j 를 k 에서 가를 때 합치는 비용과 글자 그대로 같은 식이다
```

`n + 1` 개의 꼭짓점을 가진 볼록 다각형을 **겹치지 않는 삼각형 `n − 1` 개로 자르는 것**을
삼각분할이라고 합니다. 표가 고른 `k` 셋을 삼각형으로 옮겨 적으면 무게 합이 답과 같아요.

| 표에서 고른 자리 | 그 삼각형 | 무게 |
| --- | --- | --- |
| `dp[1][2]`, `k = 1` | `(v0, v1, v2)` | 10 · 30 · 5 = 1,500 |
| `dp[3][4]`, `k = 3` | `(v2, v3, v4)` | 5 · 60 · 10 = 3,000 |
| `dp[1][4]`, `k = 2` | `(v0, v2, v4)` | 10 · 5 · 10 = 500 |
| 삼각형 셋의 무게 합 | | **5,000** |

같은 이름을 다른 자리에서도 만나게 됩니다. **최적 다각형 삼각분할**은 꼭짓점에 좌표를 두고
삼각형의 넓이나 둘레 합을 최소로 만드는 문제인데, 무게 함수만 바꾸면 이 표가 그대로 답합니다.
삼각분할의 **개수**도 괄호 배치의 개수와 같은 수열이고, 그 값은 뒤에서 닫힌 형태로 냅니다.
행렬 체인을 `O(n log n)` 에 푸는 방법이 알려져 있는데 그것도 이 대응 위에서 만들어졌어요 —
이 글은 표 채우기까지만 다룹니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 전이식과 배치 수가 어떻게
유도되는지, 무엇이 매 순간 참으로 남는지, 그리고 얼마나 드는지 차례로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 항목이 **한 줄로 늘어서 있고 차례를 바꿀 수 없습니다.** 묶는 방식만 고르는 것이라 답이
  「괄호를 어디에 치는가」로 좁혀져요.
- 구간을 한 자리에서 가르면 **겹치지 않는 두 구간**이 됩니다. 조각이 겹치면 두 조각의 값을
  그냥 더할 수 없어요.
- 두 조각을 합치는 비용이 **조각의 내용이 아니라 경계 정보만으로** 정해집니다. 여기서는 세
  차원 `p[i-1]` · `p[k]` · `p[j]` 가 그것이에요.
- 항목 수가 **작습니다.** 후보가 `(n³ − n)/6` 개라 `n` 이 수백을 넘으면 표를 다 못 채웁니다.

```text
위 네 조건이 표의 두 축과 채우는 차례를 그대로 정한다
  차례 고정        → 상태가 구간의 두 끝 (i, j) 하나로 좁혀진다
  겹치지 않는 조각 → 두 칸의 값을 그냥 더한다
  경계만으로 합침  → 합치는 비용이 조각을 안 열어 보고 계산된다
  n 이 작다        → 후보 (n³ − n)/6 개를 전부 견줄 수 있다
```

이 문제의 제약(`n ≤ 100`)은 후보 166,650 개라 1 초 안에 넉넉히 끝납니다. `n` 이 1,000 이면
후보가 166,666,500 개라 같은 코드로는 시간 안에 못 끝내요.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "순서는 바꿀 수 없다"  "결합 방식은 자유롭게"  "어디를 먼저 묶어도 결과는 같다"
  "괄호를 어떻게 치는가"  "합치는 비용이 최소가 되도록"
  "인접한 둘을 합친다"  "하나가 될 때까지"

제약에 이런 모양이 보이면
  항목 수가 100 ~ 500 안팎          ← n³ 을 견딜 수 있다는 신호
  항목마다 값이 아니라 경계가 있다  ← 합치는 비용이 경계에서 나온다
```

반대로 **「항목을 골라 담는다」** 가 보이면 상태의 한 축이 「항목 수」인
[0/1 배낭](../knapsack01/knapsack01-guide.md) 형태이고, **「몇 개든 담는다」** 가 보이면
[최소 동전 개수](../unboundedKnapsack/unboundedKnapsack-guide.md) 형태입니다.

| 무엇을 묻는가 | 상태 축 | 읽는 칸 | 표가 진행하는 방향 |
| --- | --- | --- | --- |
| 행렬 체인 (이 글) | 구간의 두 끝 `(i, j)` | 같은 구간 안의 두 조각 | 대각선에서 오른쪽 위로 |
| [0/1 배낭](../knapsack01/knapsack01-guide.md) | 항목 수와 용량 `(i, c)` | 윗 줄 | 위에서 아래로 |
| [부분집합 합 판정](../subsetSum/subsetSum-guide.md) | 항목 수와 합 `(i, s)` | 윗 줄 | 위에서 아래로 |
| [동전 조합의 경우의 수](../coinChangeWays/coinChangeWays-guide.md) | 액면가 수와 금액 `(i, a)` | 이번 줄 | 위에서 아래로 |

#### 실제로 쓰이는 곳

**NumPy** 는 파이썬의 수치 계산 라이브러리이고, `numpy.linalg.multi_dot` 이 행렬 여러 개를
한 번에 곱하면서 **괄호 배치를 이 표로 고릅니다.** 그 함수가 부르는
`_multi_dot_matrix_chain_order` 의 주석이 이렇게 적어요.

```text
"The implementation CLOSELY follows Cormen, "Introduction to Algorithms",
 Chapter 15.2, p. 370-378.  Note that Cormen uses 1-based indices.

     cost[i, j] = min([
         cost[prefix] + cost[suffix] + cost_mult(prefix, suffix)
         for k in range(i, j)])"

  # p stores the dimensions of the matrices
  # Example for p: A_{10x100}, B_{100x5}, C_{5x50} --> p = [10, 100, 5, 50]

  — numpy/linalg/_linalg.py (조회 2026-09-03)
```

차원 배열을 `p` 로 적는 것도, 한 칸을 두 조각의 합과 합치는 비용으로 정하는 것도 이 글과
같습니다. 인용한 주석의 예시를 이 글의 코드에 그대로 실행해 봅시다.

네 번째 조건(항목 수가 작다)의 반대편 끝이 여기입니다. 표는 항목이 넷 이상일 때부터 값을 합니다.

### 수식 정의와 유도

괄호 배치의 집합으로 답을 정의하고, 그 정의를 작은 값에 넣어 검산하고, 셋을 유도한 다음 제약
규모를 넣습니다. 유도 셋은 전이식과 **배치 수의 닫힌 형태**와 **후보 총수의 닫힌 형태**예요.

```text
정의   구간을 하나로 곱하는 괄호 배치의 집합 B(i, j) 와 그 비용 c
  ↓
검산   그 정의를 [10, 30, 5, 60, 10] 에 넣어 다섯 원소를 손으로 적는다
  ↓
유도   ① 마지막 곱셈으로 집합을 갈라 전이식을 얻는다
       ② 배치 수의 점화식을 닫힌 형태로 푼다
       ③ 표가 견주는 후보 총수를 닫힌 형태로 푼다
  ↓
계수   두 닫힌 형태에 n = 100 을 넣어 수치를 낸다
```

**먼저 집합입니다.** 구간 `A_i … A_j` 의 괄호 배치 하나를 $\beta$ 로 적고, 그런 배치를 모은
집합을 $B(i, j)$ 로 적습니다. 배치는 재귀로 정의돼요.

$$B(i,i) = \{\,A_i\,\},\qquad B(i,j) = \bigcup_{k=i}^{j-1}\ \bigl\{\,(\beta_L\beta_R)\ \bigm|\ \beta_L \in B(i,k),\ \beta_R \in B(k+1,j)\,\bigr\}$$

```text
i = 1 · j = 4 · k = 2 인 갈래가 B(1,4) 에 무엇을 넣는가

  β_L ∈ B(1,2) = { (A1A2) }        한 가지
  β_R ∈ B(3,4) = { (A3A4) }        한 가지
  → 이 갈래가 내놓는 배치는 ((A1A2)(A3A4)) 하나다
```

배치 하나의 비용 $c(\beta)$ 와 그 최솟값 $M(i,j)$ 도 같은 꼴로 정의합니다.

$$c(A_i) = 0,\qquad c\bigl((\beta_L\beta_R)\bigr) = c(\beta_L) + c(\beta_R) + p_{i-1}\,p_k\,p_j,\qquad M(i,j) = \min_{\beta \in B(i,j)} c(\beta)$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $\beta$ | 구간 하나의 괄호 배치 | $\beta \in B(i,j)$ |
| $\beta_L$ · $\beta_R$ | 바깥 괄호가 가른 왼쪽·오른쪽 배치 | $\beta_L \in B(i,k)$, $\beta_R \in B(k+1,j)$ |
| $k$ | $\beta$ 의 바깥 괄호가 가르는 자리 — 파트 1 의 `k` 와 같다 | $i \le k < j$ |
| $p_t$ | 차원 배열의 $t$ 번째 값 — 파트 1 의 `p` 와 같다 | $0 \le t \le n$ |
| $c(\beta)$ | 그 배치대로 곱했을 때의 스칼라 곱셈 횟수 | $c(A_i) = 0$ |
| $M(i,j)$ | 그 구간의 최소 곱셈 횟수 | $M(i,i) = 0$ |
| $q$ | 배치 수를 셀 때 바깥 괄호가 **왼쪽에 두는 행렬 개수** | $1 \le q < n$ |

**정의를 값에 넣어 검산해 봅시다.** $p = [10, 30, 5, 60, 10]$ 이고 $i = 1$, $j = 4$ 면
$B(1,4)$ 의 원소를 손으로 다 적을 수 있습니다.

<!--proof:parenWalk-->

```text
전개 입력의 괄호 배치  곱셈 횟수
((A1A2)(A3A4))             5,000
(A1(A2(A3A4)))             7,500
(((A1A2)A3)A4)            10,500
(A1((A2A3)A4))            30,000
((A1(A2A3))A4)            33,000

배치 수 = 5 · 최솟값 = 5,000
```

파트 1 의 표에서 `dp[1][4]` 가 5,000 이었고, 정의에서 직접 고른 최솟값과 같습니다.

**첫째 유도는 전이식입니다.** $B(i,j)$ 의 정의가 이미 $k$ 로 갈라져 있으므로, 최솟값을 그
갈래마다 따로 구해 다시 최소를 취하면 돼요.

```text
B(i,j) 를 바깥 괄호가 가르는 자리 k 로 나눈다 — 서로 겹치지 않는 j − i 무리다

  한 무리 안에서 c 를 최소로 만들려면
    c(β) = c(β_L) + c(β_R) + p_(i-1)·p_k·p_j 에서 뒤 항이 k 로만 정해지므로
    앞 두 항을 각각 최소로 만들면 된다  →  M(i,k) + M(k+1,j) + p_(i-1)·p_k·p_j

  무리마다 그 값을 구해 최소를 취한 것이 M(i,j) 다
```

$$M(i,j) = \min_{i \le k < j}\ \bigl(M(i,k) + M(k+1,j) + p_{i-1}\,p_k\,p_j\bigr),\qquad M(i,i) = 0$$

```text
i = 1 · j = 4 로 검산한다

  M(1,4) = min( 0 + 4,500 + 3,000 ,  1,500 + 3,000 + 500 ,  4,500 + 0 + 6,000 )
         = min( 7,500 , 5,000 , 10,500 )
         = 5,000        파트 1 의 dp[1][4] 와 같다
```

**둘째 유도는 배치 수입니다.** 행렬 $n$ 개의 배치 수를 $P(n)$ 이라 적습니다. 바깥 괄호가
왼쪽에 $q$ 개를 두는 갈래마다 $P(q)\,P(n-q)$ 가지가 나오고, 갈래끼리는 겹치지 않아요.
**여기서 $q$ 는 개수이고 위의 $k$ 는 자리라 다른 기호를 씁니다** — 구간이 `A_1` 에서
시작할 때만 둘이 같은 수가 됩니다.

$$P(1) = 1,\qquad P(n) = \sum_{q=1}^{n-1} P(q)\,P(n-q)$$

```ts
// 식을 그대로 옮긴 조각. 합의 첨자 q 도 식과 같게 둔다.
const P = (n: number): number => {
  if (n <= 1) return 1;
  let sum = 0;
  for (let q = 1; q < n; q++) sum += P(q) * P(n - q);
  return sum;
};

P(4); // P(1)P(3) + P(2)P(2) + P(3)P(1) = 2 + 1 + 2 = 5
```

이 점화식은 카탈란 수의 점화식이고 닫힌 형태가 알려져 있습니다. 점화식·닫힌 형태·전수 세기
셋이 같은 값을 내는지 확인해 봅시다.

$$P(n) = \frac{1}{n}\binom{2n-2}{n-1}$$

```text
n = 4 로 검산한다
  C(6, 3) / 4 = 20 / 4 = 5        위 조각이 낸 5 와 같다
```

**셋째 유도는 표가 견주는 후보 총수입니다.** 길이 $L$ 인 구간은 $n - L + 1$ 개이고 각각
후보가 $L - 1$ 개예요. $d = L - 1$ 로 두고 더하면 닫힌 형태가 나옵니다.

$$\sum_{L=2}^{n}(n-L+1)(L-1) \;=\; \sum_{d=1}^{n-1} d\,(n-d) \;=\; n\cdot\frac{(n-1)n}{2} - \frac{(n-1)n(2n-1)}{6} \;=\; \frac{n^3-n}{6}$$

```text
왼쪽은 길이별로 (구간 수 × 후보 수) 를 더한 것이고 오른쪽은 닫힌 형태다

  n = 4   3·1 + 2·2 + 1·3        = 10    (4³ − 4)/6 = 60/6  = 10
  n = 5   4·1 + 3·2 + 2·3 + 1·4  = 20    (5³ − 5)/6 = 120/6 = 20
```

**마지막으로 계수입니다.** 두 닫힌 형태에 이 문제의 상한 $n = 100$ 을 넣으면, 배치를 세는
일과 후보를 견주는 일이 얼마나 갈리는지가 나옵니다.

빠르게 늘고 후보 총수는 세제곱으로 늘어서, 제약 상한에서 배수가 52 자리가 됩니다.

### 불변식 — `dp[i][j]` 는 `A_i … A_j` 를 어떤 배치로 묶든 나오는 곱셈 횟수의 최솟값이다

파트 1 에서 코드가 동작하는 것을 열두 자리로 봤습니다. 그것은 행렬 넷의 특정 차원에서 맞았다는
뜻이지, 어떤 입력에서도 맞는다는 뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 한 문장으로
못 박고, 표를 채우는 각 걸음이 그 문장을 지키는지 값으로 따져 봅니다.

> 길이가 `L` 인 구간을 **전부 정하고 난 시점**에, `j − i + 1 ≤ L` 인 모든 칸 `dp[i][j]` 는
> 행렬 `A_i … A_j` 를 **차례를 지키면서** 어떤 배치로 묶었을 때 나올 수 있는 스칼라 곱셈
> 횟수의 **최솟값**입니다.

```text
전부 정하고 난 시점    길이 L 인 칸이 하나라도 남았으면 아직 그 시점이 아니다
차례를 지키면서        행렬의 순서를 바꾼 배치는 세지 않는다
어떤 배치로 묶었을 때  괄호를 어디에 치든 전부 센다
최솟값                 평균도, 아무 배치 하나의 값도 아니다
```

「길이 `L` 을 전부 정하고 난 시점」이라고 적은 것이 이 알고리즘에서는 **칸 하나를 정하고 난
시점**과 다릅니다. 같은 길이의 칸끼리는 서로를 안 읽으므로, 시점을 길이 단위로 잡아야 논증이
한 줄로 적혀요.

```text
길이 L 인 칸이 읽는 두 조각은 길이가 1 이상 L−1 이하다
  → 길이 L−1 까지가 전부 확정된 뒤라면 읽는 칸이 전부 확정돼 있다
  → 같은 길이의 칸끼리는 서로를 안 읽으므로 그 안의 순서는 아무래도 좋다
```

**출발점부터 봅시다.** 길이 1 인 구간은 행렬 하나라서 곱셈이 일어나지 않고 배치도 하나뿐이니
최솟값이 0 인데, 코드가 표를 0 으로 깔았으니 참입니다. 그 뒤로 한 칸이 세 갈래 중 하나로
정해지고, 각 갈래가 읽는 자리는 아래와 같아요.

| 값을 정하는 갈래 | 읽는 자리 | 읽은 값이 뜻하는 것 |
| --- | --- | --- |
| 길이 1 (대각선) | 없다 | 배치가 하나뿐이라 0 |
| 후보가 지금까지의 최소보다 작다 | `dp[i][k]` · `dp[k+1][j]` | 두 조각 각각의 최솟값 |
| 작지 않다 | 같음 | 최소를 안 바꾼다 |

두 번째 갈래가 이 불변식과 맞물리는 자리입니다. `dp[i][k]` 와 `dp[k+1][j]` 가 각각 그 조각의
최솟값이라면, 바깥 괄호를 `k` 에 친 배치 중 가장 적은 것이 그 둘의 합에 합치는 비용을 더한
값이에요. 거꾸로 `A_i … A_j` 의 어떤 배치든 바깥 괄호가 `i` 이상 `j` 미만의 어느 자리에는
있으므로, `k` 를 전부 시험하면 빠지는 배치도 없습니다.

```text
L=4 를 정하는 동안 읽은 자리를 전부 적으면

  k=1   dp[1][1]=0      dp[2][4]=4,500   합치기 10·30·10=3,000   →  7,500
  k=2   dp[1][2]=1,500  dp[3][4]=3,000   합치기 10· 5·10=  500   →  5,000
  k=3   dp[1][3]=4,500  dp[4][4]=0       합치기 10·60·10=6,000   → 10,500
          └ 읽은 여섯 칸의 길이가 1 · 2 · 3 뿐이고 전부 이미 확정돼 있다
```

경계에 있는 입력들도 확인하고 갑시다.

| 차원 배열 | 표에서 일어나는 일 | 돌려주는 값 |
| --- | --- | --- |
| `dims=[10]` (행렬 0 개) | 첫 분기가 잡는다 | `0` |
| `dims=[10, 20]` (행렬 1 개) | 첫 분기가 잡는다 | `0` |
| `dims=[5, 10, 3]` (행렬 2 개) | `L=2` 한 칸, 후보 하나 | `150` |
| 차원이 전부 같다 (`[5,5,5,5]`) | 모든 후보가 같은 값이라 어느 `k` 든 결과가 같다 | `250` |
| 차원이 전부 1 (`[1,1,1,1,1]`) | 곱셈 한 번마다 1 이고 곱셈이 세 번 | `3` |
| 차원이 상한 (`[500,500,500]`) | 후보 하나, `500³` | `125,000,000` |

여섯 다 따로 분기하지 않고 같은 전이식으로 처리됩니다. 넷째 줄이 이 알고리즘의 성질 하나를
말해 줘요 — 차원이 전부 같으면 어느 배치든 곱셈 횟수가 같아서, **그런 입력으로는 배치를 고르는
규칙이 맞는지 확인할 수 없습니다.**

**이제 깨뜨려 봅시다.** 불변식에서 「어떤 배치로 묶었을 때」는 `k` 를 전부 시험하는 반복문이
지키고, 「차례를 지키면서」는 두 조각이 `A_i … A_k` 와 `A_(k+1) … A_j` 로 이어 붙는다는 것이
지킵니다. 그 이어 붙는 자리를 코드에서 지키는 것은 합치는 비용의 **가운데 항** 하나예요.
그 항을 옆 칸에서 읽게 바꿉니다.

```ts
const join =
  (dims[i - 1] as number) * (dims[k + 1] as number) * (dims[j] as number);
//                                      ~~~~~ dims[k] 였다
```

차원 배열을 바꿔 가며 실행하면 이렇게 나옵니다.

<!--proof:mutantJoinDim-->

```text
차원 배열             바른 코드  만나는 차원을 옆 칸에서 읽은 코드
[10, 30, 5, 60, 10]       5,000                              6,750
[10, 30, 5, 60]           4,500                             36,250
[10, 20, 30, 40, 30]     30,000                             34,000
[2, 3, 4, 2, 5]              56                                 78
[5, 5, 5, 5]                250                                250
[10, 20]                      0                                  0
```

**위 넷이 전부 달라졌습니다.** 둘째 줄은 4,500 이 36,250 이라 여덟 배가 넘어요. 왼쪽 조각의
크기가 `p[i-1] × p[k]` 이고 오른쪽이 `p[k] × p[j]` 인데 가운데 항을 `p[k+1]` 로 읽으면, 있지도
않은 크기의 두 행렬을 곱한 비용을 적는 셈입니다.

```text
dp[1][4] 의 k=2 후보에서 합치는 비용

  바른 코드   두 조각이 10×5 와 5×10 이라  →  10 ·  5 · 10 =   500
  바뀐 코드   가운데를 p[3] = 60 으로 읽어  →  10 · 60 · 10 = 6,000
                └ 두 조각의 실제 크기와 아무 관계 없는 수를 더한다
```

**그런데 아래 둘은 답이 같았습니다.** `[5, 5, 5, 5]` 는 차원이 전부 같아 `p[k]` 든 `p[k+1]` 든
5 이고, `[10, 20]` 은 행렬이 하나라 첫 분기가 잡아 반복문에 들어가지도 않아요. 정사각 행렬만
넣어 확인하면 이 변형이 통과합니다 — 위 표 다섯째 줄이 그 상태입니다.

### 비용 계산

#### 비용을 세는 과정

호출 하나가 하는 일을 셋으로 가르고, 셋을 더해 총식을 만듭니다.

| 무슨 일을 하는가 | 몇 번 하는가 |
| --- | --- |
| 표 만들기 | `(n+1)²` 칸을 0 으로 채운다 |
| 후보 견주기 | 구간마다 `j − i` 개. T2~T11 이 그 후보 하나하나다 |
| 읽기 | `dp[1][n]` 한 칸을 읽는다. T12 가 그것이다 |

후보 하나마다 하는 일은 덧셈 둘·곱셈 둘·견주기 하나라 상수예요. T2 처럼 두 조각이 다 0 인
후보든 T11 처럼 두 조각이 다 채워진 후보든 하는 일이 같습니다. 그러니 후보가 몇 개인지만 세면
돼요.

```text
길이 L 인 구간은 n − L + 1 개이고 각각 후보가 L − 1 개다

  L=2   구간 3 개 × 후보 1 개 =  3       T2 · T3 · T4
  L=3   구간 2 개 × 후보 2 개 =  4       T5 · T6 · T7 · T8
  L=4   구간 1 개 × 후보 3 개 =  3       T9 · T10 · T11
                          합 = 10       (4³ − 4)/6 = 10
```

```text
총식 = Θ((n+1)²)  +  Θ((n³ − n)/6)  +  Θ(1)   =  Θ(n³)
        ↑ 표 만들기  ↑ 후보 견주기     ↑ 읽기

n = 100  →  칸 10,201 개 · 후보 166,650 개
```

메모리도 칸 수와 같습니다 — `Θ(n²)` 칸을 실제로 들고 있어요. 쓰는 칸은 위쪽 삼각형
`n(n+1)/2` 개뿐이라 `n = 100` 에서 5,050 개인데, 정사각 배열로 잡으면 10,201 개가 됩니다.
두 배 차이는 같은 `Θ(n²)` 안이고 100 킬로바이트도 안 되므로 이 문제의 메모리 제한에서는
문제가 안 돼요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 $O$ | 타이트 $\Theta$ |
| --- | --- | --- |
| **최선의 경우** (차원이 전부 같다) | $O(n^3)$ | $\Theta(n^3)$ |
| **평균적인 경우** (차원을 아무렇게나 뽑아도) | $O(n^3)$ | $\Theta(n^3)$ |
| **최악의 경우** (어떤 입력이든) | $O(n^3)$ | $\Theta(n^3)$ |

**세 줄이 같습니다.** 이 알고리즘은 입력을 보고 일찍 끝내는 자리가 없어 후보 `(n³ − n)/6` 개를
언제나 한 번씩 견줘요. 안쪽 반복문이 `k = i` 에서 `j−1` 까지 무조건 반복하는 것이 그 이유이고,
차원이 전부 같아 어느 후보를 골라도 결과가 같은 입력에서도 견주기 횟수는 그대로입니다.

**보장의 종류는 최악 보장입니다.** 기댓값이 아닙니다 — 코드에 무작위성이 없고 차원 값의
분포를 가정하는 자리도 없어요. 같은 차원 배열이면 몇 번을 실행해도 견준 후보 수가 같습니다.
위 표의 「평균」 줄이 뜻하는 것도 분포에 대한 기댓값이 아니라 **어떤 분포에서 차원을 뽑아도
같은 값**이라는 것입니다.

```text
n³ 의 n 은 입력의 "값" 이 아니라 "개수" 다

  행렬 100 개를 적는 데 차원이 101 개              →  후보 166,650 개
  차원이 전부 500 이든 전부 1 이든                 →  후보 166,650 개
  차원 값을 키워도 견주기 횟수는 한 번도 안 늘어난다
```

그래서 이 알고리즘은 **의사다항이 아닙니다.** 입력에 적힌 숫자의 크기가 아니라 **항목 수**로
비용이 정해지니, 같은 표 모양을 쓰는 [0/1 배낭](../knapsack01/knapsack01-guide.md) 이나
[부분집합 합 판정](../subsetSum/subsetSum-guide.md) 과 갈리는 자리가 여기예요. 그쪽은 한 축이
「용량」이나 「합」이라 값이 커지면 표가 함께 커집니다.

#### 최악을 만드는 입력

「어떤 입력이 최악인가」라는 물음이 위 코드에 대해서는 **입력의 내용과 무관**합니다. 차원을
어떻게 두어도 견주는 후보 수가 같기 때문이에요. 행렬 100 개짜리 입력 다섯을 실제로 실행해
견주기 횟수를 세 봅시다.

<!--proof:worstFill-->

```text
입력 (행렬 100 개)                    답  견주기 횟수
차원이 전부 1                         99      166,650
차원이 전부 500           12,375,000,000      166,650
1 과 500 이 번갈아                25,049      166,650
(13t mod 50) + 1                  61,701      166,650
1 부터 101 까지 오름차순         343,398      166,650
```

**오른쪽 열이 전부 같습니다.** 답은 1 억 배 넘게 갈리는데 견주기 횟수는 한 번도 안 갈려요.
그래서 시간의 최악은 크기 하나로 정해집니다.

```text
시간 최악 = 행렬 수가 제약 최대일 때
            n = 100  →  후보 (100³ − 100)/6 = 166,650 개 · 칸 101 × 101 = 10,201 개

이때 차원 값은 아무래도 좋다. 위 표의 다섯 입력이 채우는 칸 수와 견주는 후보 수가 정확히 같다.
```

**대신 이 문제에는 시간이 아닌 최악이 하나 더 있습니다** — 답 자체의 크기예요. 곱셈 한 번의
비용이 세 차원의 곱이라 차원이 클수록 답이 커지고, 그 값이 배정밀도 정수가 정확히 셀 수 있는
범위를 넘으면 견주기가 뜻을 잃습니다. 차원을 전부 상한인 500 으로 두고 재 봅시다.

<!--proof:answerScale-->

```text
무엇                                                        값
차원이 전부 500 · 행렬 100 개일 때의 답         12,375,000,000
배정밀도 정수가 정확한 상한              9,007,199,254,740,991
상한이 그 답의 몇 배인가                               727,854
```

차원이 전부 상한이면 곱셈 한 번이 `500³ = 1억 2,500만` 이고 곱셈이 99 번이라 답이 약 124 억
입니다. 배정밀도 정수가 정확한 범위의 **72 만분의 1** 이라 여유가 넉넉해요. 차원 상한이 500
이 아니라 `10^6` 이었다면 답이 `10^20` 규모라 이 코드가 그대로는 못 셉니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 괄호 배치를 하나씩 만드는 대신 **같은 구간에
이른 배치들을 한 칸으로 합쳤고**, 마지막으로 곱하는 자리 `k` 를 전부 시험해 두 조각으로 갈랐고,
그 결과 `2.27 × 10^56` 이 후보 166,650 개로 내려왔습니다.

```text
길이가 짧은 구간부터 → (i, j) 칸에 최소 곱셈 횟수를 적는다 → dp[1][n] 을 읽는다
        └ 두 조각이 언제나 더 짧다      └ k 를 전부 시험해 배치를 빠짐없이 덮는다
```

먼저 답이 붙는 문제 하나입니다. 본문 T8에서 `dp[2][4]` 가 4,500 으로 정해졌고, 그 값을 낸
후보는 `k = 2` 였어요. 그 4,500 은 어떤 괄호 배치를 뜻할까요? 그리고 같은 4,500 인 T6의
`dp[1][3]` 은 왜 다른 배치일까요?

```text
T6 :  dp[1][3] = 1,500 +     0 + (10 ·  5 · 60) = 4,500   고른 k = 2
T8 :  dp[2][4] =     0 + 3,000 + (30 ·  5 · 10) = 4,500   고른 k = 2
      두 4,500 이 각각 뜻하는 배치 = ?     ← 이 자리를 직접 채워 봅시다
```

<!--check:sameValue-->

`dp[1][3] = 4,500` 은 구간 `A1 … A3` 를 `((A1A2)A3)` 로 묶은 것입니다. `k = 2` 라 왼쪽 조각이
`A1 … A2`(1,500)이고 오른쪽 조각이 `A3`(0)이며, 합치는 비용이 `10 · 5 · 60 = 3,000` 이에요.
`dp[2][4] = 4,500` 은 구간 `A2 … A4` 를 `(A2(A3A4))` 로 묶은 것이라 뜻이 다릅니다. 같은
`k = 2` 인데 구간의 왼쪽 끝이 2 라 왼쪽 조각이 `A2` 하나(0)이고 오른쪽 조각이
`A3 … A4`(3,000)이에요.

```text
T6  구간 A1 … A3   k=2   왼쪽 A1A2 (1,500)   오른쪽 A3   (0)      배치 ((A1A2)A3)
T8  구간 A2 … A4   k=2   왼쪽 A2    (0)      오른쪽 A3A4 (3,000)  배치 (A2(A3A4))
      └ k 는 "몇 번째 행렬 뒤에서 가르는가" 이지 "왼쪽에 몇 개를 두는가" 가 아니다
```

여기서 확인할 것은 **`k` 가 구간 안의 상대 위치가 아니라 행렬 번호**라는 점입니다. 두 칸의
`k` 가 똑같이 2 인데도 왼쪽 조각의 크기가 둘과 하나로 다릅니다.

<!--/check-->


- T9~T11에서 `dp[1][4]` 의 후보가 7,500 · 5,000 · 10,500 이었습니다. 차원 배열의 마지막 값
  10 을 100 으로 바꾸면 세 후보가 각각 얼마가 되고 어느 것이 골라질지 예측해 보세요.
- 최소 곱셈 횟수 대신 **그 괄호 배치 자체**를 돌려주려면 표에 무엇을 더 적어야 하고, 불변식의
  어느 낱말이 달라질까요.
- 행렬을 한 줄이 아니라 **고리 모양**으로 이어 붙여 마지막과 첫 번째도 곱할 수 있다면, 구간의
  정의가 어떻게 달라지고 칸 수는 몇 배가 될까요.
- 후보 총수 `(n³ − n)/6` 는 `n` 이 1,000 이면 1.6 억입니다. 같은 표를 그대로 쓰면서 견주는
  후보를 줄일 여지가 어디에 있을지, 파트 1 의 표에서 고른 `k` 들이 행마다 어떻게 움직이는지
  보고 짐작해 보세요.
