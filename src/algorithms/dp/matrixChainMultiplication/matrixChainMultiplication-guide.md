# 행렬 체인 곱셈 최소 비용 — 마지막으로 곱하는 자리 하나가 나머지를 두 조각으로 가른다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 괄호 배치를 전부
시험해 보는 재귀에서 출발해 구간 길이 차례로 채우는 DP 테이블까지 가고, 그 DP 테이블을 단계마다 값으로 푼 뒤,
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

행렬 여러 개를 **주어진 차례 그대로** 곱합니다. 차례는 바꿀 수 없지만 **어느 쪽을 먼저 묶어 곱할지**는 고를 수
있고, 묶는 방식에 따라 스칼라 곱셈 횟수가 크게 갈려요. 가장 적은 곱셈 횟수를 답하는 것이 목표입니다. 행렬 넷을
차원 배열 `p = [10, 30, 5, 60, 10]` 하나로 적으면 이렇습니다.

<!--proof:concept-chain-->

| 행렬 | 행 수 | 열 수 |
| --- | ---: | ---: |
| A1 | 10 | 30 |
| A2 | 30 | 5 |
| A3 | 5 | 60 |
| A4 | 60 | 10 |

행렬 A_t 의 크기는 p[t-1] × p[t] 입니다. A1 과 A2 를 곱하면 10 × 5 행렬이 되고, 스칼라 곱셈이 10 · 30 · 5 = 1,500 번 일어납니다.

<!--/proof-->

이웃한 두 행렬은 만나는 차원이 같아서 곱할 수 있어요. 행렬 넷을 괄호로 묶는 방법을 전부 적고, 방법마다 곱셈
횟수를 세어 보면 이렇습니다.

<!--proof:concept-parens-->

| 괄호 배치 | 곱셈 횟수 |
| --- | ---: |
| ((A1A2)(A3A4)) | 5,000 |
| (A1(A2(A3A4))) | 7,500 |
| (((A1A2)A3)A4) | 10,500 |
| (A1((A2A3)A4)) | 30,000 |
| ((A1(A2A3))A4) | 33,000 |

배치는 5 가지이고, 가장 적은 ((A1A2)(A3A4)) 의 5,000 과 가장 많은 ((A1(A2A3))A4) 의 33,000 은 6.6 배 차이입니다. 정본 matrixChainMultiplication([10, 30, 5, 60, 10]) 도 5,000 을 냅니다.

<!--/proof-->

같은 결과를 내는데 묶는 방식만으로 곱셈 횟수가 여러 배 갈립니다. 그런데 묻는 것은 **곱셈 횟수 하나**예요.
어느 배치가 그 횟수를 냈는지는 묻지 않으니, 같은 구간을 하나로 곱하는 배치끼리는 곱셈이 가장 적은 쪽만
기억하면 됩니다. 그래서 배치를 만들지 않고 **구간마다 가장 적은 곱셈 횟수만 칸에 적어 두는 표**를 씁니다.
작은 입력의 답을 칸에 적어 두고 큰 입력의 답을 그 칸들에서 만드는 이런 표를 **DP 테이블**이라고 부르고, DP 는
동적 계획법(dynamic programming)의 줄임말이에요. 이 글의 DP 테이블은 `i` 번째 줄 `j` 번째 칸 `dp[i][j]` 에
「행렬 `A_i` 부터 `A_j` 까지를 하나로 곱하는 가장 적은 곱셈 횟수」를 적습니다. 전개 입력의 DP 테이블 전체를
그리면 이렇습니다.

<!--fig:concept-table-->
![matrixChainMultiplication([10, 30, 5, 60, 10]) 의 DP 테이블 — 칸 (i, j) 는 구간 A_i … A_j](./figs/concept-table.svg)

줄 번호 `i` 는 구간이 시작하는 행렬이고 열 번호 `j` 는 구간이 끝나는 행렬이라, 표 아래 행렬 줄의 `A_j` 가 열
`j` 와 짝입니다. 대각선(`i = j`)은 행렬 하나짜리 구간이라 곱셈이 없어 0 이고, 오른쪽 위로 갈수록 구간이
길어져요. 대시로 그린 아래쪽 칸은 `i > j` 라 구간이 아니어서 쓰지 않습니다. 답은 행렬 전부를 덮는 오른쪽 위 칸
`dp[1][4]` 예요. 칸 하나를 정하는 규칙은 둘로 갈립니다.

| 구간의 모양 | 그 칸에 적는 값 |
| --- | --- |
| 행렬 하나 (`i = j`) | 0 |
| 행렬 둘 이상 | `i ≤ k < j` 인 자리 `k` 마다 **왼쪽 조각 `dp[i][k]` + 오른쪽 조각 `dp[k+1][j]` + 합치는 비용**을 만들어, 그중 가장 작은 값 |

`k` 는 **마지막으로 곱하는 자리**입니다. 어느 배치든 맨 마지막 곱셈은 한 번뿐이고, 그 곱셈이 `A_k` 와 `A_(k+1)`
사이를 경계로 삼았다면 남은 일이 겹치지 않는 두 구간 `A_i … A_k` 와 `A_(k+1) … A_j` 로 갈려요. `k` 하나로 만든
값을 **후보**라고 부르겠습니다. `dp[1][4]` 를 정하는 자리를 후보마다 그리면 이렇습니다. 강조색 굵은 테가 정하는
칸이고, 진한 테를 두른 두 칸이 그 후보가 읽는 칸이에요. 표 아래 괄호가 구간과 두 조각입니다.

<!--fig:concept-rule-->
![dp[1][4] 을 정하는 자리 — 가르는 자리 k 마다 두 칸을 읽는다](./figs/concept-rule.svg)

왼쪽 조각은 **같은 줄 왼쪽**에, 오른쪽 조각은 **같은 열 아래**에 있습니다. 둘 다 `dp[1][4]` 보다 짧은 구간이라,
짧은 구간부터 채우면 읽는 칸이 언제나 먼저 정해져 있어요. 그래서 이 DP 테이블은 대각선에서 시작해 오른쪽 위로,
**구간 길이 차례로** 채웁니다. 규모에 따라 괄호 배치 수와 DP 테이블의 크기를 세면 이렇습니다.

<!--proof:concept-size-->

```text
행렬 수 n  괄호 배치 수  쓰는 칸 n(n+1)/2  후보 (n³−n)/6
4                     5                10             10
100        2.27 × 10^56             5,050        166,650
```

배치 수는 행렬이 늘수록 자릿수가 불어나는데, DP 테이블이 만드는 후보는 행렬 수의 세제곱을 따라 늘어요. 비용은
결과만 적으면 `O(n³)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **행렬 곱셈의 크기 규칙.** `a×b` 행렬과 `b×c` 행렬을 곱하면 `a×c` 가 되고, 그때 스칼라 곱셈이 `a · b · c`
  번 일어납니다. 이 글은 그 횟수만 셉니다.
- **결합 법칙과 교환 법칙이 다르다는 것.** 행렬 곱은 묶는 방식을 바꿔도 결과가 같지만(결합), 행렬의 **차례**를
  바꾸면 결과가 달라지거나 아예 곱할 수 없습니다.
- **2 차원 배열의 첨자 읽기.** `dp[i][j]` 는 `i` 번째 줄의 `j` 번째 칸입니다.
- **여럿 중 가장 작은 값 고르기.** 칸 하나를 정하는 데 이것과 덧셈만 씁니다.

재귀 · 메모이제이션 · 그래프 탐색은 몰라도 됩니다. DP 테이블을 대각선에서 오른쪽 위로 채우는 반복문 세 겹만
써요. DP 테이블을 쓰는 다른 편을 봤다면 차이는 **채우는 차례와 읽는 칸**에 있습니다.

| 이미 아는 것 | 이 글에서 쓰이는 자리 |
| --- | --- |
| 2 차원 첨자 | DP 테이블의 칸 `dp[i][j]` |
| 가장 작은 값 고르기 | 칸 하나 = 후보 `j − i` 개 중 가장 작은 값 |
| [0/1 배낭](../knapsack01/knapsack01-guide.md) · [최소 동전 개수](../unboundedKnapsack/unboundedKnapsack-guide.md) | 같은 DP 테이블인데 줄이 「항목 수」라 **윗 줄**에서 읽고, 위에서 아래로 줄 차례로 채운다 |
| [최장 공통 부분 수열](../../array/longestCommonSubsequence/longestCommonSubsequence-guide.md) | 두 문자열의 앞부분을 줄과 열로 삼아 **왼쪽 · 위 · 왼쪽 위** 이웃 셋만 읽는다 |

### 아이디어를 떠올리는 과정 — 가르는 자리를 전부 시험하는 재귀에서 구간 길이 차례로 채우는 DP 테이블까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 차원 배열을 받아서, 행렬 전부를 곱하는
데 드는 가장 적은 스칼라 곱셈 횟수를 돌려줍니다.

```ts
function matrixChainMultiplication(dims: number[]): number;
```

- 입력: 차원 배열 `dims`. 길이가 `n + 1` 이고 `t` 번째 행렬 `A_t` 의 크기가 `dims[t-1] × dims[t]` 입니다.
- 출력: **가장 적은 스칼라 곱셈 횟수 하나**. 어느 배치가 그 횟수를 냈는지는 돌려주지 않아요. 행렬이 한 개 이하면
  곱셈이 없어 0 입니다.
- 규모: 행렬 수 `n` 은 100 이하, 차원은 1 이상 500 이하로 둡니다. 비용은 흔한 채점 환경의 예산인 1 초에 대어
  잽니다. 행렬 수를 100 으로 잡은 까닭은 두 방법이 자릿수로 갈리는 것을 보이기 위해서예요 — 이 크기에서 DP
  테이블은 1 초 안에 채워지고, 아무것도 기억하지 않는 방법은 끝나지 않습니다. 차원의 위 끝 500 은 답이 정확히
  셀 수 있는 정수 범위 안에 드는지 재는 데 씁니다.

눈여겨볼 것이 둘 있어요. **행렬의 차례를 바꿀 수 없다**는 것과, **이웃한 두 행렬이 만나는 차원이 같다**는
것입니다.

```text
차례를 바꿀 수 없다
  묶는 방식만 고른다  → 답이 "괄호를 어디에 치는가" 하나로 좁혀진다

만나는 차원이 같다
  A_i … A_k 를 하나로 곱하면 크기가 p[i-1] × p[k] 다
  A_(k+1) … A_j 를 하나로 곱하면 크기가 p[k] × p[j] 다
    → 두 조각을 합치는 비용이 조각 안을 어떻게 묶었든 p[i-1] · p[k] · p[j] 로 정해진다
```

두 성질이 각각 필요해지는 자리가 뒤에 옵니다. 이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로
씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 행렬의 개수 | `n ≤ 100` |
| `p` | 차원 배열. 길이가 `n + 1` 이다. 코드에서는 `dims` | 원소가 1 이상 500 이하 |
| `i` | 구간의 왼쪽 끝 행렬 번호. DP 테이블의 줄 | `1 ≤ i ≤ n` |
| `j` | 구간의 오른쪽 끝 행렬 번호. DP 테이블의 열 | `i ≤ j ≤ n` |
| `k` | 마지막으로 곱하는 자리. 구간을 `A_i … A_k` 와 `A_(k+1) … A_j` 로 가른다 | `i ≤ k < j` |
| `L` | 구간에 든 행렬 수 `j − i + 1`. DP 테이블을 채우는 차례를 정한다 | `1 ≤ L ≤ n` |
| `dp[i][j]` | 행렬 `A_i … A_j` 를 하나로 곱하는 가장 적은 스칼라 곱셈 횟수 | DP 테이블의 칸 하나 |

비용은 이 글 끝까지 **후보 수**로 셉니다. 가르는 자리 `k` 하나로 「왼쪽 조각 + 오른쪽 조각 + 합치는 비용」을 한
번 만드는 일이 후보 하나이고, 후보 하나는 덧셈 둘 · 곱셈 둘 · 비교 하나라 드는 일이 늘 같아요.

가장 먼저 떠오르는 방법으로 시작합시다. 마지막 곱셈의 자리를 하나씩 잡아 보고, 갈린 두 조각을 같은 방법으로
다시 푸는 것입니다.

```ts
function 완전탐색(p: number[], i: number, j: number): number {
  if (i === j) return 0;
  let best = Number.POSITIVE_INFINITY;
  for (let k = i; k < j; k++) {
    const cost =
      완전탐색(p, i, k) + 완전탐색(p, k + 1, j) + p[i - 1]! * p[k]! * p[j]!;
    if (cost < best) best = cost;
  }
  return best;
}
```

이 방법은 답을 틀리지 않습니다. 문제는 자리를 잡을 때마다 **두 조각을 처음부터 다시 푼다**는 것이에요. 행렬
`m` 개짜리 구간 하나가 만드는 후보 수를 `F(m)` 이라 적으면, 자기 자리 `m − 1` 개에 더해 갈린 두 조각이 만드는
후보를 모두 더하므로 `F(m) = (m − 1) + Σ_q (F(q) + F(m − q))` 입니다. 실제로 실행해 세어 보고, 그 점화식으로 큰
`n` 까지 이어 봅시다.

<!--proof:origin-naive-->

| 행렬 수 | 실제로 세어 본 후보 | 점화식이 내는 후보 | DP 테이블의 후보 |
| --- | ---: | ---: | ---: |
| 2 | 1 | 1 | 1 |
| 3 | 4 | 4 | 4 |
| 4 | 13 | 13 | 10 |
| 6 | 121 | 121 | 35 |
| 8 | 1,093 | 1,093 | 84 |
| 10 | 9,841 | 9,841 | 165 |
| 12 | 88,573 | 88,573 | 286 |
| 100 | 세지 못했다 | 8.58 × 10^46 | 166,650 |

행렬 12 개까지는 재귀를 실제로 실행해 세었고 점화식과 같았습니다. 행렬 100 개에서 재귀의 후보는 47 자리 수이고, DP 테이블의 후보는 166,650 개입니다. 초당 1 억 번으로 잡으면 DP 테이블은 0.0017 초예요.

<!--/proof-->

**아무것도 기억하지 않는 재귀는 여기서 막힙니다.** 행렬이 하나 늘 때마다 후보 수가 세 배 가까이 늘고, 오른쪽
끝 열의 DP 테이블 후보와는 자릿수부터 달라요. 그러면 이 재귀가 무엇을 되풀이하는지 봅시다. 행렬 다섯 개에서
`A2 … A3` 에 이르는 길은 하나가 아닙니다.

```text
A1 … A5 를 k=3 에서 가른다  →  왼쪽 A1 … A3 을 k=1 에서 가른다   →  A2 … A3
A1 … A5 를 k=1 에서 가른다  →  오른쪽 A2 … A5 를 k=3 에서 가른다  →  A2 … A3
  └ 두 끝이 같은 구간은 어디서 내려왔든 그 안에서 할 일도, 가장 적은 곱셈 횟수도 같다
```

그 답은 한 번만 구하면 됩니다. 같은 입력을 두 방식으로 세어 봅시다. 왼쪽은 재귀가 그 구간을 실제로 다시 푼
횟수이고, 오른쪽은 **구간마다 값을 한 번만 정했을 때**의 횟수예요.

<!--proof:origin-same-interval-->

| 구간 | 재귀가 그 구간을 푼 횟수 | 구간마다 한 번씩 정한 횟수 |
| --- | ---: | ---: |
| A1 | 8 | 1 |
| A1 … A2 | 4 | 1 |
| A1 … A3 | 2 | 1 |
| A1 … A4 | 1 | 1 |
| A1 … A5 | 1 | 1 |
| A2 | 12 | 1 |
| A2 … A3 | 5 | 1 |
| A2 … A4 | 2 | 1 |
| A2 … A5 | 1 | 1 |
| A3 | 14 | 1 |
| A3 … A4 | 5 | 1 |
| A3 … A5 | 2 | 1 |
| A4 | 12 | 1 |
| A4 … A5 | 4 | 1 |
| A5 | 8 | 1 |
| 합계 | 81 | 15 |

행렬 5 개에서 재귀는 구간 15 개를 모두 합쳐 81 번 풀었습니다. 구간마다 한 번만 정하면 15 번이고, 행렬이 100 개라도 서로 다른 구간은 5,050 개입니다.

<!--/proof-->

오른쪽에서 눈여겨볼 것은 **횟수에 위 끝이 있다**는 점입니다. 행렬을 아무리 늘려도 서로 다른 구간은 두 끝을 고르는
`n(n+1)/2` 가지뿐이에요. 그러니 구간마다 칸 하나를 두고 값을 한 번씩만 정하면 되고, 남은 질문은 둘입니다.

```text
칸 하나를 정할 때 k 를 전부 시험해야 하는가
칸을 어떤 차례로 정해야 읽는 칸이 이미 정해져 있는가
```

가장 손이 덜 가는 후보부터 시험합니다. 구간마다 `k` 를 전부 시험하는 대신 **한 자리로 고정**하는 것이에요. 왼쪽
끝에서 가르는 판(`k = i`)과 오른쪽 끝에서 가르는 판(`k = j−1`)을 같은 입력들에 실행해 봅시다.

<!--proof:origin-split-rule-->

| 차원 배열 | k = i 로 고정 | k = j−1 로 고정 | k 를 전부 시험 |
| --- | ---: | ---: | ---: |
| [10, 30, 5, 60, 10] | 7,500 | 10,500 | 5,000 |
| [10, 30, 5, 60] | 27,000 | 4,500 | 4,500 |
| [10, 20, 30, 40, 30] | 60,000 | 30,000 | 30,000 |
| [40, 20, 30, 10, 30] | 51,000 | 48,000 | 26,000 |
| [2, 3, 4, 2, 5] | 130 | 60 | 56 |
| [1, 2, 3, 4] | 32 | 18 | 18 |
| [5, 5, 5, 5] | 250 | 250 | 250 |

k = j−1 로 고정한 판은 7 입력 가운데 4 입력에서 최소와 같은 값을 냈습니다. [40, 20, 30, 10, 30] 에서는 48,000 대 26,000 으로 1.8 배 어긋나요.

<!--/proof-->

고정 규칙은 **우연히 맞기도 합니다.** 그래서 몇 가지 입력만 넣어 보면 통과한 줄 알게 돼요. 두 판이 본 것을
나란히 적으면 이렇습니다.

```text
k 를 한 자리로 고정하면        구간 하나에 배치를 하나만 만들어 본 것이다 — 그것이 가장 적은지는 모른다
k 를 i 부터 j−1 까지 시험하면  구간 하나의 마지막 곱셈 j − i 가지를 전부 본 것이다
```

구간 하나가 만들 수 있는 마지막 곱셈은 `j − i` 가지뿐이니 **`k` 를 전부 시험합니다.**

다음은 채우는 차례입니다. 다른 DP 테이블에서 하던 대로 줄을 위에서부터 채우는 판 — `i` 를 1 부터 늘리고 그 줄
안에서 `j` 를 `i` 부터 늘리는 것 — 을, 짧은 구간부터 채우는 판과 나란히 실행해 봅시다.

<!--proof:origin-fill-order-->

| 채우는 차례 | [10, 30, 5, 60, 10] | [10, 20, 30, 40, 30] | [2, 3, 4, 2, 5] |
| --- | ---: | ---: | ---: |
| 길이가 짧은 구간부터 | 5,000 | 30,000 | 56 |
| i 를 1 부터 · j 를 i 부터 | 2,000 | 6,000 | 30 |

i 를 1 부터 채운 판은 입력 3 개 가운데 3 개에서 최소보다 작은 값을 냈습니다.

<!--/proof-->

**답이 최소보다 작게 나왔습니다.** 최소보다 작은 곱셈 횟수는 있을 수 없으니, 어딘가에서 곱셈을 공짜로 센
거예요. 전개 입력의 `dp[1][4]` 에서 첫 후보가 무엇을 읽었는지 두 차례로 적어 보면 그 자리가 나옵니다.

<!--proof:origin-fill-why-->

```text
dp[1][4] 의 k=1 후보가 읽는 오른쪽 조각 dp[2][4]

채우는 차례         dp[2][4] 의 값                   k=1 후보
i 를 1 부터 채우면          아직 0      0 + 0 + 3,000 = 3,000
길이가 짧은 쪽부터      이미 4,500  0 + 4,500 + 3,000 = 7,500
  └ dp[2][4] 은 dp[1][4] 보다 아래 줄이라 줄 차례로는 나중에 정해진다
```

칸 `(i, j)` 가 읽는 오른쪽 조각 `dp[k+1][j]` 는 **아래 줄**에 있습니다. 줄을 위에서부터 채우면 그 칸이 아직 깔아
둔 0 이라, 오른쪽 조각을 곱셈 없이 만든 것처럼 셉니다. 반면 두 조각은 언제나 원래 구간보다 짧으니, 짧은 구간부터
채우면 읽는 칸이 반드시 먼저 정해져 있어요. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **구간 길이 차례로 채우는 DP 테이블**입니다. 칸 `dp[i][j]` 에 구간 `A_i … A_j` 의
가장 적은 곱셈 횟수를 적고, 구간 길이가 짧은 칸부터 `k` 를 전부 시험해 채워요. 칸 하나가 어느 칸을 읽는지, 왜
구간을 칸으로 삼는지, 차례를 어떻게 지키는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 구간 길이 차례로 채우는 DP 테이블

이 아이디어를 한 문장으로 줄이면 이렇습니다. **칸 `dp[i][j]` 에 「구간 `A_i … A_j` 를 하나로 곱하는 가장 적은
곱셈 횟수」를 적되, 구간 길이가 짧은 칸부터 가르는 자리 `k` 를 전부 시험해 채우고, 오른쪽 위 칸을 답으로
읽습니다.** 이 방법은 DP 테이블 위에서 동작하는데, 칸 하나가 줄 하나 · 열 하나가 아니라 **구간 하나**를 맡는다는
점이 처음 보는 사람에게는 낯설어요. 그래서 이 DP 테이블을 먼저 따로 설명하고, 그다음 실현하는 순서대로 네 단계를
설명합니다. 앞 단계에서 만든 것을 뒤 단계에서 씁니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 크기와 대각선 정하기 | 칸 `(n+1) × (n+1)` 을 만들고 대각선을 0 으로 둔다 | — |
| 2단계 가르는 자리마다 후보 만들기 | 칸 하나를 `k` 마다 두 조각 + 합치는 비용으로 만들어 가장 작은 값을 고른다 | 1단계의 대각선 · 이미 정한 짧은 칸 |
| 3단계 구간 길이 차례로 채우기 | 길이 2 부터 `n` 까지, 길이마다 왼쪽 끝을 옮기며 칸을 정한다 | 2단계의 한 칸 정하기 |
| 4단계 오른쪽 위 칸 읽기 | `dp[1][n]` 을 돌려준다 | 3단계가 마지막으로 정한 칸 |

#### 먼저 알아 둘 개념 — DP 테이블

이 글의 DP 테이블은 **행렬 체인의 구간 하나마다 칸 하나를 둔 표**입니다. 줄 번호가 구간의 왼쪽 끝, 열 번호가
오른쪽 끝이라 칸 `dp[i][j]` 하나가 구간 `A_i … A_j` 를 맡고, 거기에 그 구간을 하나로 곱하는 가장 적은 곱셈 횟수가
적혀요. 여기서 헷갈리기 쉬운 것이 둘 있습니다. 칸에 적히는 것은 괄호 배치 **자체가 아니라 그 배치의 곱셈
횟수**이고, 칸이 맡는 것은 행렬 하나가 아니라 **이어진 행렬 여러 개**예요.

| 무엇 | 담는 것 | 이 글에서 쓰는 곳 |
| --- | --- | --- |
| 괄호 배치 | 구간을 어떤 차례로 묶는가 하나 | 칸 하나가 어느 배치의 값인지 설명할 때 |
| DP 테이블의 칸 | 그 구간의 배치 중 **가장 적은 곱셈 횟수** | `dp[i][j]` 가 가리킬 때 |

##### 칸마다 적힌 가장 적은 곱셈 횟수

전체 컨셉의 그림에 적힌 열 칸을, 구간마다 배치를 전부 만들어 고른 최소와 나란히 놓으면 이렇습니다.

<!--proof:build-cell-meaning-->

| 칸 | 구간 | 가장 적은 배치 | 칸의 값 | 배치를 전부 만든 최소 |
| --- | --- | --- | ---: | ---: |
| dp[1][1] | A1 | A1 | 0 | 0 |
| dp[2][2] | A2 | A2 | 0 | 0 |
| dp[3][3] | A3 | A3 | 0 | 0 |
| dp[4][4] | A4 | A4 | 0 | 0 |
| dp[1][2] | A1 … A2 | (A1A2) | 1,500 | 1,500 |
| dp[2][3] | A2 … A3 | (A2A3) | 9,000 | 9,000 |
| dp[3][4] | A3 … A4 | (A3A4) | 3,000 | 3,000 |
| dp[1][3] | A1 … A3 | ((A1A2)A3) | 4,500 | 4,500 |
| dp[2][4] | A2 … A4 | (A2(A3A4)) | 4,500 | 4,500 |
| dp[1][4] | A1 … A4 | ((A1A2)(A3A4)) | 5,000 | 5,000 |

10 칸 가운데 10 칸에서 칸의 값과, 배치를 전부 만들어 고른 최소가 같습니다.

<!--/proof-->

대각선 네 칸은 행렬 하나라 배치가 그 행렬 자신뿐이고 곱셈이 없어요. 대각선 바로 위 세 칸은 행렬 둘이라 배치가
하나뿐이고, 그 위로 갈수록 배치가 늘어 그중 가장 적은 것이 칸에 남습니다. 칸은 값 하나만 들고 있으니, 어느
배치였는지는 칸을 정할 때 고른 `k` 를 따라가야 다시 나와요.

##### 칸 하나를 읽는 법

칸은 `dp[i][j]` 처럼 번호 둘로 부릅니다. 앞 번호 `i` 로 구간이 시작하는 행렬을, 뒤 번호 `j` 로 끝나는 행렬을
정해요. `dp[2][4]` 라면 `A2 · A3 · A4` 를 하나로 곱하는 가장 적은 곱셈 횟수입니다. 그림에서 대시로 그린 칸은 이번에
보지 않는 칸이고, 표 아래 괄호가 그 칸이 맡는 구간과 가장 작은 후보를 낸 두 조각이에요.

<!--fig:build-read-cell-->
![dp[2][4] — 구간 A2 … A4 를 하나로 곱하는 최소 곱셈 횟수](./figs/build-read-cell.svg)

같은 값이 적힌 다른 칸 하나와 함께 읽으면 이렇습니다.

<!--proof:build-read-one-->

| 칸 | 구간 | 행렬 크기 | 곱한 결과 | 배치 수 | 가장 적은 배치 | 곱셈 횟수 |
| --- | --- | --- | --- | ---: | --- | ---: |
| dp[2][4] | A2 … A4 | 30×5 · 5×60 · 60×10 | 30×10 | 2 | (A2(A3A4)) | 4,500 |
| dp[1][3] | A1 … A3 | 10×30 · 30×5 · 5×60 | 10×60 | 2 | ((A1A2)A3) | 4,500 |

두 칸의 값이 똑같이 4,500 이지만 구간이 다르고, 그 값을 낸 배치도 dp[2][4] 이 (A2(A3A4)), dp[1][3] 이 ((A1A2)A3) 입니다.

<!--/proof-->

조심할 점이 하나 있습니다. 두 칸의 값이 같아도 **맡은 구간이 다르면 다른 뜻**이에요. 곱한 결과의 크기도
`p[i-1] × p[j]` 로 칸마다 다르고, 이 크기는 그 칸이 더 긴 구간의 조각으로 쓰일 때 합치는 비용을 정합니다.

##### 같은 줄 왼쪽 칸과 같은 열 아래 칸

칸 하나는 짧은 칸 여럿과 이어져 있습니다. 같은 줄의 왼쪽 칸들은 **왼쪽 끝이 같은** 짧은 구간이고, 같은 열의 아래
칸들은 **오른쪽 끝이 같은** 짧은 구간이에요. `dp[1][4]` 를 정할 때 읽는 칸을 모두 그리면 이렇습니다.

<!--fig:build-neighbors-->
![dp[1][4] 이 읽는 칸 — 같은 줄 왼쪽 셋과 같은 열 아래 셋](./figs/build-neighbors.svg)

왜 그 칸들인지는 `A1 … A4` 의 배치 다섯을 **바깥 괄호가 어디서 가르는가**로 무리 지어 보면 나옵니다. 바깥 괄호가
`k` 에서 가르면 왼쪽은 `A1 … A_k` 라 같은 줄의 `dp[1][k]` 이고, 오른쪽은 `A_(k+1) … A4` 라 같은 열의
`dp[k+1][4]` 예요.

<!--proof:build-neighbor-split-->

| 바깥 괄호 자리 | 그 무리의 배치 | 곱셈 횟수 | 두 칸으로 만든 후보 |
| --- | --- | --- | --- |
| k = 1 | (A1(A2(A3A4))) · (A1((A2A3)A4)) | 7,500 · 30,000 | dp[1][1] + dp[2][4] + 10·30·10 = 7,500 |
| k = 2 | ((A1A2)(A3A4)) | 5,000 | dp[1][2] + dp[3][4] + 10·5·10 = 5,000 |
| k = 3 | ((A1(A2A3))A4) · (((A1A2)A3)A4) | 33,000 · 10,500 | dp[1][3] + dp[4][4] + 10·60·10 = 10,500 |

무리 3 개 가운데 3 개에서, 무리 안의 가장 적은 곱셈 횟수가 같은 줄 왼쪽 칸과 같은 열 아래 칸으로 만든 후보와 같습니다. 배치 5 가지는 무리 3 개 중 꼭 하나에 듭니다.

<!--/proof-->

한 무리 안에서는 바깥 괄호의 자리가 같아서 합치는 비용이 같습니다. 그러면 무리 안에서 가장 적은 배치는 두 조각을
각각 가장 적게 묶은 배치이고, 그 값이 곧 같은 줄 왼쪽 칸과 같은 열 아래 칸의 합에 합치는 비용을 더한 후보예요.
무리 셋의 후보 중 가장 작은 값이 `dp[1][4]` 입니다.

##### 대각선 하나가 구간 길이 하나

같은 대각선 위의 칸은 구간 길이 `L = j − i + 1` 이 같습니다. 대각선에서 오른쪽 위로 한 줄 올라갈 때마다 길이가 1
늘고 칸이 하나 줄어요. 길이마다 그 대각선을 강조해 그리면 이렇습니다.

<!--fig:build-diagonals-->
![대각선 하나가 구간 길이 하나 — 길이 L 인 칸은 n − L + 1 개](./figs/build-diagonals.svg)

길이마다 칸을 세면 이렇습니다.

<!--proof:build-diagonal-count-->

```text
구간 길이  칸 수 n−L+1                                         칸
L = 1                4  dp[1][1] · dp[2][2] · dp[3][3] · dp[4][4]
L = 2                3             dp[1][2] · dp[2][3] · dp[3][4]
L = 3                2                        dp[1][3] · dp[2][4]
L = 4                1                                   dp[1][4]
합계                10                              n(n+1)/2 = 10
```

칸 `(i, j)` 가 읽는 두 조각은 둘 다 길이가 `L` 보다 짧아서, 언제나 **아래쪽 대각선**에 있어요. 대각선 하나를 다
채운 뒤 다음 대각선으로 가면 읽는 칸이 늘 준비돼 있다는 것이 이 모양에서 나옵니다.

##### 줄 차례로 채우는 배낭 DP 테이블과의 차이

[0/1 배낭](../knapsack01/knapsack01-guide.md) 이나 [최소 동전 개수](../unboundedKnapsack/unboundedKnapsack-guide.md)
의 DP 테이블을 먼저 봤다면 줄을 위에서 아래로 채우고 싶어집니다. 그쪽은 칸이 **윗 줄**을 읽어서 그 차례가
맞았어요. 여기서는 칸이 **아래 줄**을 읽습니다. 같은 입력을 두 차례로 채운 DP 테이블을 나란히 그리면 이렇습니다.
진한 테를 두른 칸이 두 판의 값이 다른 칸이에요.

<!--fig:build-contrast-->
![같은 입력 [10, 30, 5, 60, 10] — 채우는 차례만 바꾼 두 DP 테이블](./figs/build-contrast.svg)

값이 다른 칸만 뽑으면 이렇습니다.

<!--proof:build-contrast-->

| 칸 | 구간 길이 차례 | i 를 1 부터 채운 판 |
| --- | ---: | ---: |
| dp[2][4] | 4,500 | 1,500 |
| dp[1][4] | 5,000 | 2,000 |

10 칸 가운데 2 칸의 값이 서로 다르고, 그 2 칸 가운데 2 칸에서 줄 차례 쪽이 작습니다.

<!--/proof-->

틀린 칸은 둘 다 **맨 오른쪽 열**에 있습니다. 그 열의 칸은 아래 줄의 같은 열 칸을 오른쪽 조각으로 읽는데, 줄
차례로는 그 아래 칸이 나중에 정해져요. 칸 수도 읽는 칸의 모양도 같고, **읽는 칸이 어느 쪽에 있는가 하나가 채우는
차례를 정하는** 모양입니다.

##### 칸을 구간으로 잡는 까닭

마지막 곱셈 하나를 정하면 남는 두 조각은 **이어진 행렬들**입니다. 왼쪽 조각은 원래 구간과 왼쪽 끝이 같고, 오른쪽
조각은 오른쪽 끝이 같아요. 조각을 또 가르면 양 끝이 모두 안쪽으로 들어온 조각도 생깁니다. 재귀가 실제로 푼
구간을 자리마다 나누어 세면 이렇습니다.

<!--proof:build-why-interval-->

| 구간의 자리 | 구간 수 | 구간 |
| --- | ---: | --- |
| A1 에서 시작 | 4 | A1 · A1 … A2 · A1 … A3 · A1 … A4 |
| A1 이 아닌 곳에서 시작해 A4 에서 끝 | 3 | A4 · A3 … A4 · A2 … A4 |
| 양 끝이 모두 안쪽 | 3 | A2 · A3 · A2 … A3 |

재귀가 한 번이라도 푼 구간은 10 개이고, 그중 3 개는 A1 에서 시작하지도 A4 에서 끝나지도 않습니다.

<!--/proof-->

앞쪽 구간(`A1 … A_j`)만 칸으로 두면 셋째 줄의 구간을 적을 자리가 없습니다. 그래서 상태는 두 끝 `(i, j)` 둘이어야
하고, 두 끝으로 정해지는 구간이 곧 칸이에요. 구간은 항상 이어져 있으니 그 두 수만으로 빠짐없이 적힙니다.

#### 1단계 — DP 테이블의 크기와 대각선 정하기

행렬 번호를 1 부터 쓰려고 칸을 `(n+1) × (n+1)` 로 잡습니다. 행렬 `A_t` 의 크기가 `p[t-1] × p[t]` 라서, 번호를 0
부터 세면 차원 배열의 첨자가 음수가 되는 자리가 생기거든요. 0 번 줄과 0 번 열은 비워 둡니다. 전개 입력과 규모의
끝에서 크기를 세면 이렇습니다.

<!--proof:build-size-->

| 행렬 수 n | 잡는 칸 (n+1)² | 쓰는 칸 n(n+1)/2 | 대각선 칸 n |
| ---: | ---: | ---: | ---: |
| 4 | 5 × 5 = 25 | 10 | 4 |
| 100 | 101 × 101 = 10,201 | 5,050 | 100 |

전개 입력에서 정본이 만든 DP 테이블은 5 줄 × 5 칸이고, 그중 쓰는 칸이 10 개입니다.

<!--/proof-->

대각선은 계산하지 않고 바로 정합니다. 행렬 하나짜리 구간은 곱셈이 없으니 `dp[i][i] = 0` 이고, DP 테이블을 0 으로
깔아 두면 그 값이 이미 들어 있어요. 아래쪽 삼각형(`i > j`)은 구간이 아니라 끝까지 0 인 채로 쓰지 않습니다.

#### 2단계 — 가르는 자리마다 후보를 만들어 가장 작은 값 고르기

길이 2 이상인 칸은 가르는 자리 `k` 마다 후보를 하나씩 만듭니다. 후보는 세 수의 합이에요. 왼쪽 조각 `dp[i][k]`,
오른쪽 조각 `dp[k+1][j]`, 그리고 두 조각을 합치는 비용입니다. 왼쪽 조각을 다 곱하면 `p[i-1] × p[k]` 행렬이 되고
오른쪽 조각은 `p[k] × p[j]` 가 되니, 합치는 비용은 `p[i-1] · p[k] · p[j]` 예요. `dp[1][4]` 의 후보 셋을 모두 만들면
이렇습니다.

<!--proof:build-candidates-->

| 가르는 자리 | 왼쪽 조각 | 오른쪽 조각 | 두 조각의 크기 | 합치는 비용 | 후보 |
| --- | --- | --- | --- | --- | ---: |
| k = 1 | dp[1][1] = 0 | dp[2][4] = 4,500 | 10×30 과 30×10 | 10·30·10 = 3,000 | 7,500 |
| k = 2 | dp[1][2] = 1,500 | dp[3][4] = 3,000 | 10×5 와 5×10 | 10·5·10 = 500 | 5,000 |
| k = 3 | dp[1][3] = 4,500 | dp[4][4] = 0 | 10×60 과 60×10 | 10·60·10 = 6,000 | 10,500 |

가장 작은 후보는 k = 2 의 5,000 이고, dp[1][4] = 5,000 입니다.

<!--/proof-->

가장 쉬운 경우는 길이 2 인 칸입니다. `k` 가 `i` 하나뿐이고 두 조각이 다 대각선이라 0 이어서, 합치는 비용이 곧 칸의
값이에요. 합치는 비용의 **가운데 항 `p[k]`** 가 두 조각이 만나는 차원이라는 것이 이 단계의 요점입니다. 첫 항과 끝
항은 구간의 양 끝이라 `k` 와 상관없이 같고, 가운데 항만 `k` 를 따라 바뀌어요. 위 표의 합치는 비용 열이 `k` 마다
다른 것이 그 가운데 항 때문입니다.

#### 3단계 — 구간 길이 차례로 칸 채우기

칸은 길이 2 부터 `n` 까지, 길이마다 왼쪽 끝 `i` 를 1 부터 `n − L + 1` 까지 옮기며 정합니다. 불안한 자리는 2단계가
읽는 두 조각이에요. 그 칸이 아직 정해지지 않았다면 깔아 둔 0 을 읽고, 떠올리는 과정에서 본 것처럼 최소보다 작은
값을 적게 됩니다. 칸마다 읽은 칸이 언제 정해졌는지 확인해 봅시다.

<!--proof:build-fill-order-->

| 정한 차례 | 칸 | 길이 | 읽은 칸 (그 칸을 정한 차례) |
| --- | --- | ---: | --- |
| 1 번째 | dp[1][2] | 2 | dp[1][1] (대각선) · dp[2][2] (대각선) |
| 2 번째 | dp[2][3] | 2 | dp[2][2] (대각선) · dp[3][3] (대각선) |
| 3 번째 | dp[3][4] | 2 | dp[3][3] (대각선) · dp[4][4] (대각선) |
| 4 번째 | dp[1][3] | 3 | dp[1][1] (대각선) · dp[2][3] (2 번째) · dp[1][2] (1 번째) · dp[3][3] (대각선) |
| 5 번째 | dp[2][4] | 3 | dp[2][2] (대각선) · dp[3][4] (3 번째) · dp[2][3] (2 번째) · dp[4][4] (대각선) |
| 6 번째 | dp[1][4] | 4 | dp[1][1] (대각선) · dp[2][4] (5 번째) · dp[1][2] (1 번째) · dp[3][4] (3 번째) · dp[1][3] (4 번째) · dp[4][4] (대각선) |

읽은 칸 20 개 가운데 20 개가 지금 칸보다 먼저 정해져 있었습니다.

<!--/proof-->

왜 늘 먼저 정해져 있는지는 반복의 차례로 말할 수 있습니다. `k` 는 `i` 이상 `j` 미만이라 왼쪽 조각의 길이
`k − i + 1` 은 1 이상 `L − 1` 이하이고, 오른쪽 조각의 길이 `j − k` 도 1 이상 `L − 1` 이하예요. 바깥 반복이 길이를
오름차순으로 옮기니, 길이 `L` 인 칸을 정하는 순간에는 길이 `L − 1` 이하인 칸이 모두 끝나 있습니다. 한 길이 안의
칸끼리는 서로를 읽지 않아서 그 안의 차례는 답을 바꾸지 않고, 칸마다 한 번씩만 정해져 건너뛰는 칸도 없어요.

#### 4단계 — 오른쪽 위 칸 읽기

마지막 길이 `n` 의 칸은 `dp[1][n]` 하나이고, 행렬 전부를 덮는 구간이 그것뿐이라 그 값이 답입니다. 다른 칸도
버려지는 값이 아니에요. 칸마다 그 구간의 차원만 떼어 따로 호출한 답과 나란히 놓으면 이렇습니다.

<!--proof:build-answer-->

| 칸 | 칸의 값 | 그 구간만 따로 호출 | 반환값 |
| --- | ---: | --- | ---: |
| dp[1][1] | 0 | matrixChainMultiplication([10, 30]) | 0 |
| dp[2][2] | 0 | matrixChainMultiplication([30, 5]) | 0 |
| dp[3][3] | 0 | matrixChainMultiplication([5, 60]) | 0 |
| dp[4][4] | 0 | matrixChainMultiplication([60, 10]) | 0 |
| dp[1][2] | 1,500 | matrixChainMultiplication([10, 30, 5]) | 1,500 |
| dp[2][3] | 9,000 | matrixChainMultiplication([30, 5, 60]) | 9,000 |
| dp[3][4] | 3,000 | matrixChainMultiplication([5, 60, 10]) | 3,000 |
| dp[1][3] | 4,500 | matrixChainMultiplication([10, 30, 5, 60]) | 4,500 |
| dp[2][4] | 4,500 | matrixChainMultiplication([30, 5, 60, 10]) | 4,500 |
| dp[1][4] | 5,000 | matrixChainMultiplication([10, 30, 5, 60, 10]) | 5,000 |

10 칸 가운데 10 칸에서 칸의 값과, 그 구간의 차원만 넘긴 호출의 답이 같습니다.

<!--/proof-->

칸 `dp[i][j]` 는 「행렬 `A_i … A_j` 만 받은 호출」의 답을 들고 있는 셈입니다. 구간 여러 개의 답이 필요하면 한 번
채우고 그 칸들을 읽으면 돼요.

#### 이 방법이 기대는 전제

이 방법은 전제 셋 위에서 성립합니다. 하나라도 빠지면 고른 값이 최소가 아니게 되거나 읽는 칸이 어긋나요.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 어느 배치든 바깥 괄호가 `i` 이상 `j` 미만의 한 자리에서 가른다 | 2단계에서 `k` 를 전부 시험하면 빠지는 배치가 없다 | 어느 무리에도 안 드는 배치를 놓친다 |
| 합치는 비용이 조각 안의 배치와 무관하게 `p[i-1] · p[k] · p[j]` 로 정해진다 | 2단계에서 두 조각의 최소를 따로 골라 더한다 | 조각을 가장 적게 묶어도 합치는 비용이 커져 전체가 최소가 아니게 된다 |
| 행렬의 차례를 바꾸지 않는다 | 조각이 늘 이어진 구간이라 두 끝 `(i, j)` 로 적힌다 | 조각이 구간이 아니게 되어 칸에 적을 수 없다 |

첫째 전제는 앞의 「같은 줄 왼쪽 칸과 같은 열 아래 칸」에서 배치 다섯이 무리 셋 중 꼭 하나에 드는 것으로 봤습니다.
둘째 전제가 행렬 곱셈에서 참인지는 배치마다 마지막 곱셈을 따로 세어 확인할 수 있어요.

<!--proof:build-premise-->

| 배치 | 바깥 괄호 자리 | 마지막에 곱하는 두 행렬 | 마지막 곱셈의 비용 |
| --- | --- | --- | ---: |
| (A1(A2(A3A4))) | k = 1 | 10×30 과 30×10 | 3,000 |
| (A1((A2A3)A4)) | k = 1 | 10×30 과 30×10 | 3,000 |
| ((A1A2)(A3A4)) | k = 2 | 10×5 와 5×10 | 500 |
| ((A1(A2A3))A4) | k = 3 | 10×60 과 60×10 | 6,000 |
| (((A1A2)A3)A4) | k = 3 | 10×60 과 60×10 | 6,000 |

배치 5 가지 모두에서 마지막 곱셈의 비용이 바깥 괄호 자리 k 하나로 정해집니다. 같은 k 인 배치끼리는 조각 안을 어떻게 묶었든 그 비용이 같습니다.

<!--/proof-->

이 전제가 깨졌을 때 무엇이 되는지는 파트 2 「불변식」의 깨뜨리기에서 봅니다 — 합치는 비용의 가운데 항을 옆 칸에서
읽게 바꾸면 합치는 비용이 조각의 실제 크기와 어긋나고, 답이 바뀌어요.

#### 구간 길이 차례로 채우는 까닭

읽는 칸이 먼저 정해져 있기만 하면 차례는 하나가 아닙니다. 줄을 아래에서 위로 채워도(`i` 를 `n` 부터), 열을
왼쪽에서 오른쪽으로 채워도(`j` 를 1 부터, 그 열 안에서 `i` 를 거꾸로) 읽는 칸은 준비돼 있어요. 네 차례를 같은
입력에 실행해 봅시다.

<!--proof:build-orders-->

| 채우는 차례 | [10, 30, 5, 60, 10] | [10, 20, 30, 40, 30] | [2, 3, 4, 2, 5] | 읽을 때 정해져 있던 칸 |
| --- | ---: | ---: | ---: | ---: |
| 구간 길이가 짧은 칸부터 | 5,000 | 30,000 | 56 | 20 / 20 |
| i 를 n 부터 · j 를 i 부터 | 5,000 | 30,000 | 56 | 20 / 20 |
| j 를 1 부터 · i 를 j 부터 거꾸로 | 5,000 | 30,000 | 56 | 20 / 20 |
| i 를 1 부터 · j 를 i 부터 | 2,000 | 6,000 | 30 | 16 / 20 |

차례 4 가지 가운데 3 가지는 읽는 칸이 늘 먼저 정해져 있고, 세 입력의 답도 정본과 같습니다. 칸 수와 후보 수는 네 차례가 모두 같습니다.

<!--/proof-->

**차례는 정답을 위해 하나로 정해진 것이 아닙니다.** 위의 세 차례가 같은 답을 같은 비용으로 내요. 이 글이 구간
길이 차례를 쓰는 까닭은 둘입니다. 하나는 읽는 칸이 준비돼 있는 이유가 「두 조각이 더 짧다」 한 문장으로 적힌다는
것이고, 다른 하나는 파트 2 의 불변식을 「길이 `L` 까지 다 정한 시점」으로 세울 수 있다는 것이에요. 다른 두 차례는
같은 사실을 「아래 줄이 먼저」 · 「왼쪽 열이 먼저」로 따로 따져야 합니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇습니다. 이렇게 하면 후보 수가 자릿수째로 불어나던 재귀가 후보
`(n³ − n)/6` 개를 만드는 DP 테이블 채우기가 돼요.

1. 행렬이 한 개 이하면 0 을 돌려준다
2. DP 테이블을 `(n+1) × (n+1)` 로 만들고 0 으로 채운다 — 대각선이 그대로 답이다
3. 구간 길이 `L` 을 2 부터 `n` 까지 올리며, 왼쪽 끝 `i` 를 옮겨 칸 `(i, i + L − 1)` 을 고른다
4. 그 칸에서 `k` 를 `i` 부터 `j − 1` 까지 옮기며 후보를 만들고, 가장 작은 값을 칸에 적는다
5. `dp[1][n]` 을 돌려준다

### 수행으로 알아보는 알고리즘 — DP 테이블 열 칸을 열두 걸음으로 채운다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그 조각만
실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const dims = [10, 30, 5, 60, 10];
// 이 절이 끝나면 5000 이 나와야 한다 — ((A1A2)(A3A4))
```

차원을 왜 하필 이 값으로 뒀을까요? 이 입력에서 후보와 배치가 내는 값을 모으면 이렇습니다.

<!--proof:walk-input-why-->

| 자리 | 값 | 가장 작은 값 | 가장 큰 값 ÷ 가장 작은 값 |
| --- | --- | --- | ---: |
| dp[1][3] 의 후보 | 27,000 · 4,500 | 2 번째 | 6.0 |
| dp[1][4] 의 후보 | 7,500 · 5,000 · 10,500 | 2 번째 | 2.1 |
| 괄호 배치 다섯 | 7,500 · 30,000 · 5,000 · 33,000 · 10,500 | 3 번째 | 6.6 |

dp[1][4] 에서는 후보 3 개 가운데 2 번째 가 가장 작습니다.

<!--/proof-->

셋을 한꺼번에 확인하려는 것입니다. 길이 3 인 칸에서 두 후보가 여러 배 갈려
어느 후보가 왜 골라지는지가 값으로 나오고, 마지막 칸은 **가운데 후보가 가장 작아서** 첫 후보나 마지막 후보만 보는
고정 규칙과 구분돼요. 배치의 최대와 최소도 여러 배 벌어져, 배치를 잘못 고르면 얼마나 손해인지가 보입니다. 절차
전체를 한 장으로 적으면 이렇습니다.

```text
n ← 행렬 수
만약 n <= 1 이면 0 을 돌려준다                               ① 행렬이 한 개 이하

DP 테이블 dp 를 (n+1) × (n+1) 로 만들고 전부 0 으로 둔다      ② 길이 1 구간은 0

L 을 2 부터 n 까지:
    i 를 1 부터 i + L - 1 <= n 인 동안:
        j ← i + L - 1
        best ← 무한
        k 를 i 부터 j-1 까지:
            cost ← dp[i][k] + dp[k+1][j] + p[i-1] · p[k] · p[j]
            cost 가 best 보다 작으면 best ← cost             ③ 작다 · ④ 작지 않다
        dp[i][j] ← best

dp[1][n] 을 돌려준다
```

#### 1. DP 테이블을 만들고 대각선을 0 으로 둔다

1단계에서 정한 크기대로 DP 테이블을 만듭니다. 0 으로 채우면 대각선이 그대로 옳은 값이 돼요.

```ts
const n = dims.length - 1;
// ① 행렬이 한 개 이하다 — 곱셈이 일어나지 않는다.
if (n <= 1) return 0;

// dp[i][j] = 행렬 A_i … A_j 를 하나로 곱하는 데 드는 최소 스칼라 곱셈 횟수.
// ② 길이 1 구간은 곱셈이 없다 — 대각선이 0 으로 남는다.
const dp = Array.from({ length: n + 1 }, () =>
  new Array<number>(n + 1).fill(0),
);
```

실행하면 이렇게 나옵니다. 행렬이 한 개 이하인 입력도 함께 넣었어요.

<!--proof:walk-init-->

```text
        j=1  j=2  j=3  j=4
  i=1    0    .    .    .
  i=2    -    0    .    .
  i=3    -    -    0    .
  i=4    -    -    -    0
        -  = i > j 라 구간이 아니다
        .  = 아직 안 정했다 (0 이 깔려 있다)

matrixChainMultiplication([10])      →  0   행렬 0 개 — ① 이 바로 돌려준다
matrixChainMultiplication([10, 20])  →  0   행렬 1 개 — ① 이 바로 돌려준다
```

대각선만 뜻이 있고, 위쪽의 나머지 칸은 아직 정하지 않은 자리입니다. 갈래 ①이 없으면 `n = 0` 에서 DP 테이블이 한
칸짜리가 되고 마지막 줄의 `dp[1][0]` 을 읽으려다 없는 줄을 읽어요. 행렬이 하나인 `n = 1` 은 반복에 한 번도 안
들어가 `dp[1][1] = 0` 이 답이 되니 ① 없이도 맞지만, 두 경우를 한 줄로 먼저 걸러 둡니다.

#### 2. 구간 길이 차례로 칸을 고른다

바깥 반복문이 구간 길이, 그 안이 왼쪽 끝입니다. 3단계의 「구간 길이 차례로 칸 채우기」를 코드로 옮기면 이렇게
돼요.

```ts
for (let L = 2; L <= n; L++) {
  for (let i = 1; i + L - 1 <= n; i++) {
    const j = i + L - 1;
    // 여기서 칸 하나가 정해진다
  }
}
```

`i + L - 1 <= n` 이 안쪽 반복의 조건인 것은 오른쪽 끝이 DP 테이블을 벗어나지 않게 하려는 것입니다. 두 반복문이
칸을 고르는 차례는 이렇습니다.

<!--proof:walk-order-->

```text
L = 2   dp[1][2] → dp[2][3] → dp[3][4]
L = 3   dp[1][3] → dp[2][4]
L = 4   dp[1][4]
  └ 길이 L 인 칸을 다 정한 뒤에 길이 L+1 로 간다
```

#### 3. 가르는 자리마다 후보를 만들어 가장 작은 값을 남긴다

후보에 이름을 붙여 두고 하나씩 만듭니다. `Math.min` 한 줄로 줄이면 짧아지지만 **어느 후보가 작아서 그 값이
됐는지**가 코드에 남지 않아, DP 테이블을 따라갈 때 확인할 것이 사라져요.

```ts
let best = Number.POSITIVE_INFINITY;

for (let k = i; k < j; k++) {
  const left = (dp[i] as number[])[k] as number; // A_i … A_k
  const right = (dp[k + 1] as number[])[j] as number; // A_(k+1) … A_j
  // 두 조각이 만나는 자리의 차원이 dims[k] 다.
  const join =
    (dims[i - 1] as number) * (dims[k] as number) * (dims[j] as number);
  const cost = left + right + join;
  // ③ 지금까지의 최소보다 작다 · ④ 작지 않다
  if (cost < best) best = cost;
}

(dp[i] as number[])[j] = best;
```

여기서 가장 중요한 줄은 `join` 을 만드는 줄입니다. 세 항 중 **가운데가 `dims[k]`** 인 것이 두 조각이 만나는 자리라는
뜻이고, 첫 항과 끝 항은 합친 결과의 크기예요. 길이 3 인 칸 둘에서 후보가 실제로 어떻게 나오는지 적으면
이렇습니다.

<!--proof:walk-branch-->

```text
  A1 … A3   k=1   dp[1][1]=0 + dp[2][3]=9,000 + (10·30·60) = 27,000   ③
            k=2   dp[1][2]=1,500 + dp[3][3]=0 + (10·5·60) = 4,500   ③
            → dp[1][3] = 4,500, 고른 k = 2

  A2 … A4   k=2   dp[2][2]=0 + dp[3][4]=3,000 + (30·5·10) = 4,500   ③
            k=3   dp[2][3]=9,000 + dp[4][4]=0 + (30·60·10) = 27,000   ④
            → dp[2][4] = 4,500, 고른 k = 2
```

`best` 를 무한으로 열어 두는 것이 첫 후보를 그냥 받게 합니다. 첫 후보는 무한보다 언제나 작아 갈래 ③으로 들어가고,
그다음부터가 진짜 비교예요. 두 칸 다 `k = 2` 에서 가장 작았고, 그 차이는 **두 조각을 각각 얼마나 작게 만들어
두었는가**에서 옵니다.

#### 짚고 가기 — 비용이 가장 작은 이웃 쌍부터 곱해도 최소가 안 된다

길이 2 인 칸 셋을 보면 `A1 … A2` 가 가장 적습니다. 그러면 그 쌍을 먼저 곱해 하나로 만들고, 남은 행렬에서 다시 가장
적은 쌍을 고르면 되지 않을까요. 사람이 손으로 계산할 때 실제로 그렇게 합니다. 여러 차원 배열에 그 방법과 최소를
나란히 실행해 봅시다.

<!--proof:greedy-systems-->

| 차원 배열 | 비용이 작은 이웃 쌍부터 곱한 판 | 최소 |
| --- | ---: | ---: |
| [10, 30, 5, 60, 10] | 10,500 | 5,000 |
| [10, 30, 5, 60] | 4,500 | 4,500 |
| [10, 20, 30, 40, 30] | 30,000 | 30,000 |
| [40, 20, 30, 10, 30] | 36,000 | 26,000 |
| [2, 3, 4, 2, 5] | 60 | 56 |
| [1, 2, 3, 4] | 18 | 18 |
| [5, 5, 5, 5] | 250 | 250 |

7 입력 가운데 4 입력에서 두 값이 같습니다.

<!--/proof-->

**절반 넘게 답이 같습니다.** 그래서 이 자리가 위험해요 — 몇 가지 입력으로 확인하면 통과하고, 틀린 줄 모르고
넘어갑니다. 전개 입력에서는 두 값이 갈리니 그 방법이 차례로 곱하는 쌍을 적어 봅시다.

<!--proof:greedy-walk-->

```text
[10, 30, 5, 60, 10] 에서 비용이 가장 작은 쌍부터 곱하면

  1) 이웃 쌍의 비용 1,500 · 9,000 · 3,000 가운데 1,500 을 곱한다 → 차원 배열 [10, 5, 60, 10]
  2) 이웃 쌍의 비용 3,000 · 3,000 가운데 3,000 을 곱한다 → 차원 배열 [10, 60, 10]
  3) 이웃 쌍의 비용 6,000 가운데 6,000 을 곱한다 → 차원 배열 [10, 10]
     합 1,500 + 3,000 + 6,000 = 10,500

최소는 ((A1A2)(A3A4))
  1,500 + 3,000 + (10·5·10 = 500) = 5,000
     └ 두 조각을 각각 먼저 곱해 10×5 와 5×10 으로 만들면 합치는 비용이 500 뿐이다
```

지금 가장 적은 곱셈을 고르는 결정이 **남은 차원 배열을 바꿉니다.** 한 쌍을 곱하면 그 쌍이 만나던 차원이
배열에서 빠지고, 어느 차원이 끝까지 남는가가 마지막 곱셈의 크기를 가릅니다. 한 걸음의 이득만 보는 규칙은 그 영향을
세지 못하고, 그래서 DP 테이블이 구간마다 가장 적은 값을 따로 적어 둡니다.

#### 짚고 가기 — 가운데에서 가르면 답보다 DP 테이블에서 먼저 틀린다

후보를 전부 만드는 대신 **구간의 가운데에서 가르면** 되지 않을까요. 절반씩 가르는 방법이 대개 좋으니 자연스러운
생각이고, 비교가 통째로 없어지니 더 빨라집니다. 여러 입력에 실행해 봅시다.

<!--proof:mid-split-->

| 자리 | 가운데에서 가른 판 | k 를 전부 시험한 판 |
| --- | ---: | ---: |
| 전개 입력의 dp[2][4] | 27,000 | 4,500 |
| 전개 입력의 답 dp[1][4] | 5,000 | 5,000 |
| [10, 20, 30, 40, 30] 의 답 | 51,000 | 30,000 |
| [40, 20, 30, 10, 30] 의 답 | 69,000 | 26,000 |
| [2, 3, 4, 2, 5] 의 답 | 104 | 56 |
| [1, 2, 3, 4] 의 답 | 18 | 18 |
| [5, 5, 5, 5] 의 답 | 250 | 250 |

전개 입력의 답은 두 방법 모두 5,000 이지만, 그 안의 dp[2][4] 은 27,000 대 4,500 입니다. [40, 20, 30, 10, 30] 의 답은 69,000 대 26,000 으로 2.7 배 어긋나요.

<!--/proof-->

**전개 입력에서는 답이 안 틀립니다.** 둘째 줄이 같아요. 그런데 첫째 줄을 보면 DP 테이블 안의 `dp[2][4]` 는 이미
여러 배 어긋나 있습니다. 답이 맞은 것은 마지막 칸이 그 틀린 칸을 **안 읽었기** 때문이에요.

<!--proof:mid-table-->

```text
dp[1][4] 을 가운데에서 가르면 k = 2 다
  읽는 칸이 dp[1][2] 과 dp[3][4] — 둘 다 길이 2 라 후보가 하나뿐이다
  dp[2][4] 은 k=1 후보가 읽는 칸인데, 그 후보를 만들지 않았다

           j=1     j=2     j=3     j=4
  i=1       0   1,500   4,500   5,000
  i=2       -       0   9,000  27,000   ← 최소가 아닌 칸 dp[2][4]
  i=3       -       -       0   3,000
  i=4       -       -       -       0
```

그래서 이 자리는 **전개 입력만 확인하면 통과합니다.** 아래 줄들이 그 규칙이 실제로 답을 가르는 입력이에요. 반씩
가르는 것이 좋은 성질을 주는 것은 **가르는 비용이 어디서 갈라도 같을 때**인데, 이 과제는 가르는 자리마다 합치는
비용의 가운데 항이 달라요. 가운데에서 가른 판이 틀리지 않도록 고치는 법은 `k` 를 전부 시험하는 것뿐입니다.

#### 4. DP 테이블 열 칸을 열두 걸음으로 채운다

앞의 세 조각을 이어 `matrixChainMultiplication([10, 30, 5, 60, 10])` 을 실행하면 열두 걸음이 됩니다. 대각선을 까는
한 걸음, 후보 열을 한 걸음에 하나씩, 답을 읽는 한 걸음이에요. 걸음마다 무대의 점선 칸은 아직 안 정한 칸, 강조색
굵은 테가 이번에 정한 칸, 진한 테를 두른 두 칸이 이번 후보가 읽은 칸입니다. 칸의 마지막 후보가 아닌 걸음은 칸을
아직 쓰지 않아서, 열 머리만 반전해 어느 칸의 후보인지 보여요. 표 아래 괄호는 곱의 구간과 두 조각입니다. 먼저

더 커서 ④ 로 지나간 걸음이고, 적은 값은 첫 후보를 만든 T7 에서 이미 `best` 에 들어 있었어요.

#### 5. 전체 코드

조각 셋을 한 함수로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 마지막 한 줄뿐이에요 — DP 테이블의 오른쪽
위 칸을 읽어 돌려줍니다.

```ts
export function matrixChainMultiplication(dims: number[]): number {
  const n = dims.length - 1;
  // ① 행렬이 한 개 이하다 — 곱셈이 일어나지 않는다.
  if (n <= 1) return 0;

  // dp[i][j] = 행렬 A_i … A_j 를 하나로 곱하는 데 드는 최소 스칼라 곱셈 횟수.
  // ② 길이 1 구간은 곱셈이 없다 — 대각선이 0 으로 남는다.
  const dp = Array.from({ length: n + 1 }, () =>
    new Array<number>(n + 1).fill(0),
  );

  for (let L = 2; L <= n; L++) {
    for (let i = 1; i + L - 1 <= n; i++) {
      const j = i + L - 1;
      let best = Number.POSITIVE_INFINITY;

      for (let k = i; k < j; k++) {
        const left = (dp[i] as number[])[k] as number; // A_i … A_k
        const right = (dp[k + 1] as number[])[j] as number; // A_(k+1) … A_j
        // 두 조각이 만나는 자리의 차원이 dims[k] 다.
        const join =
          (dims[i - 1] as number) * (dims[k] as number) * (dims[j] as number);
        const cost = left + right + join;
        // ③ 지금까지의 최소보다 작다 · ④ 작지 않다
        if (cost < best) best = cost;
      }

      (dp[i] as number[])[j] = best;
    }
  }

  return (dp[1] as number[])[n] as number;
}
```

실행하면 이렇게 나옵니다.

```text
matrixChainMultiplication([40, 20, 30, 10, 30])  →  26,000
matrixChainMultiplication([2, 3, 4, 2, 5])       →  56
matrixChainMultiplication([5, 5, 5, 5])          →  250
matrixChainMultiplication([1, 1, 1, 1, 1])       →  3
matrixChainMultiplication([5, 10, 3])            →  150
matrixChainMultiplication([10, 20])              →  0
matrixChainMultiplication([10])                  →  0

```

### 알아 두면 좋은 개념 — 볼록 다각형의 삼각분할

파트 1 에서 채운 DP 테이블의 합치는 비용을 다시 봅시다. `p[i-1] · p[k] · p[j]` 였고, 첨자 셋이 전부 차원 배열의
자리였어요. 차원 배열의 자리 `0 … n` 을 볼록 다각형의 **꼭짓점** `v0 … vn` 으로 두면, 행렬 `A_t` 는 변
`v(t-1)–vt` 이고 전부 곱한 결과는 남은 변 `v0–vn` 입니다. 합치는 비용은 삼각형 `(v(i-1), vk, vj)` 의 세 꼭짓점 값을
곱한 것과 글자 그대로 같은 식이에요. 전개 입력을 다각형으로 그리고, DP 테이블이 고른 자리를 자르는 선으로 그리면
이렇습니다.

<!--fig:related-polygon-->
![차원 배열 [10, 30, 5, 60, 10] 을 꼭짓점 다섯의 볼록 다각형으로 — 굵은 선이 DP 테이블이 고른 자르는 선](./figs/related-polygon.svg)

꼭짓점 `n + 1` 개의 볼록 다각형을 겹치지 않는 삼각형 `n − 1` 개로 자르는 것을 **삼각분할**이라고 합니다. DP
테이블이 고른 자리마다 삼각형 하나가 나오고, 그 무게를 더하면 답과 같아요.

<!--proof:related-triangles-->

| 고른 칸과 가르는 자리 | 삼각형 | 무게 |
| --- | --- | --- |
| dp[1][4], k = 2 | (v0, v2, v4) | 10·5·10 = 500 |
| dp[1][2], k = 1 | (v0, v1, v2) | 10·30·5 = 1,500 |
| dp[3][4], k = 3 | (v2, v3, v4) | 5·60·10 = 3,000 |

삼각형 3 개의 무게를 더하면 5,000 이고, 정본의 답 5,000 과 같습니다.

<!--/proof-->

같은 이름을 다른 자리에서도 만나게 됩니다. **최적 다각형 삼각분할**은 꼭짓점에 좌표를 두고 삼각형의 넓이나 둘레
합을 가장 작게 만드는 과제인데, 무게 함수만 바꾸면 이 DP 테이블이 그대로 답합니다. 삼각분할의 **개수**도 괄호
배치의 개수와 같은 수열이고, 그 값은 파트 2 의 수식 절에서 닫힌 형태로 냅니다. 행렬 체인을 `O(n log n)` 에 푸는
방법(Hu–Shing)이 알려져 있는데 그것도 이 대응 위에서 만들어졌어요 — 이 글은 DP 테이블 채우기까지만 다룹니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 전이식과 배치 수가 어떻게 유도되는지, 무엇이 매
순간 참으로 남는지, 그리고 얼마나 드는지 차례로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- 항목이 **한 줄로 늘어서 있고 차례를 바꿀 수 없습니다.** 묶는 방식만 고르는 것이라 답이 「괄호를 어디에
  치는가」로 좁혀져요.
- 구간을 한 자리에서 가르면 **겹치지 않는 두 구간**이 됩니다. 조각이 겹치면 두 조각의 값을 그냥 더할 수 없어요.
- 두 조각을 합치는 비용이 **조각의 내용이 아니라 경계 정보만으로** 정해집니다. 여기서는 세 차원 `p[i-1]` ·
  `p[k]` · `p[j]` 가 그것이에요.
- 항목 수가 **작습니다.** 후보가 `(n³ − n)/6` 개라 `n` 이 천 단위로 가면 1 초 예산을 넘깁니다.

```text
위 네 조건이 DP 테이블의 두 축과 채우는 차례를 그대로 정한다
  차례 고정        → 상태가 구간의 두 끝 (i, j) 하나로 좁혀진다
  겹치지 않는 조각 → 두 칸의 값을 그냥 더한다
  경계만으로 합침  → 합치는 비용이 조각을 안 열어 보고 계산된다
  n 이 작다        → 후보 (n³ − n)/6 개를 전부 만들 수 있다
```

규모를 열 배로 늘리면 후보는 천 배가 됩니다.

<!--proof:purpose-scale-->

```text
행렬 수 n  후보 (n³−n)/6  초당 1 억 번일 때
100              166,650          0.0017 초
1,000        166,666,500          1.6667 초
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "순서는 바꿀 수 없다"  "결합 방식은 자유롭게"  "어디를 먼저 묶어도 결과는 같다"
  "괄호를 어떻게 치는가"  "합치는 비용이 최소가 되도록"
  "인접한 둘을 합친다"  "하나가 될 때까지"

제약에 이런 모양이 보이면
  항목 수가 수백 안팎                ← n³ 을 견딜 수 있다는 신호
  항목마다 값이 아니라 경계가 있다  ← 합치는 비용이 경계에서 나온다
```

반대로 **「항목을 골라 담는다」** 가 보이면 상태의 한 축이 「항목 수」인
[0/1 배낭](../knapsack01/knapsack01-guide.md) 모양이고, **「몇 개든 담는다」** 가 보이면
[최소 동전 개수](../unboundedKnapsack/unboundedKnapsack-guide.md) 모양입니다. 네 편을 상태 축과 읽는 칸으로 나란히
놓으면 이렇습니다.

| 과제 | 상태 축 | 읽는 칸 | 채우는 차례 |
| --- | --- | --- | --- |
| 행렬 체인 (이 글) | 구간의 두 끝 `(i, j)` | 같은 구간 안의 두 조각 | 구간 길이 차례 — 대각선에서 오른쪽 위로 |
| [0/1 배낭](../knapsack01/knapsack01-guide.md) | 항목 수와 용량 `(i, c)` | 윗 줄 | 줄 차례 — 위에서 아래로 |
| [부분집합 합 판정](../subsetSum/subsetSum-guide.md) | 항목 수와 합 `(i, s)` | 윗 줄 | 줄 차례 — 위에서 아래로 |
| [동전 조합의 경우의 수](../coinChangeWays/coinChangeWays-guide.md) | 액면가 수와 금액 `(i, a)` | 이번 줄 | 줄 차례 — 위에서 아래로 |

#### 실제로 쓰이는 곳

**NumPy** 는 파이썬의 수치 계산 라이브러리이고, `numpy.linalg.multi_dot` 이 행렬 여러 개를 한 번에 곱하면서 **괄호
배치를 이 DP 테이블로 고릅니다.** 그 함수가 부르는 `_multi_dot_matrix_chain_order` 의 주석이 이렇게 적어요.

```text
"The implementation CLOSELY follows Cormen, "Introduction to Algorithms",
 Chapter 15.2, p. 370-378.  Note that Cormen uses 1-based indices.

     cost[i, j] = min([
         cost[prefix] + cost[suffix] + cost_mult(prefix, suffix)
         for k in range(i, j)])"

  # p stores the dimensions of the matrices
  # Example for p: A_{10x100}, B_{100x5}, C_{5x50} --> p = [10, 100, 5, 50]

  — numpy/linalg/_linalg.py (조회 2026-09-03)
```

차원 배열을 `p` 로 적는 것도, 한 칸을 두 조각의 합과 합치는 비용으로 정하는 것도 이 글과 같습니다. 인용한 주석의
예시를 이 글의 코드에 그대로 실행해 봅시다.

<!--proof:multi-dot-->

```text
무엇                                               값
인용한 예시 ((AB)C) 의 비용                     7,500
인용한 예시 (A(BC)) 의 비용                    75,000
이 글의 코드가 [10, 100, 5, 50] 에서 내는 답    7,500
행렬 셋에서 DP 테이블이 만드는 후보 수              4
행렬 셋에서 DP 테이블이 잡는 칸 수                 16
인용한 닫힌 비교가 계산하는 값의 수                 2
행렬 100 개에서 DP 테이블이 만드는 후보 수    166,650
```

**그런데 행렬이 셋일 때는 이 DP 테이블을 안 씁니다.** 같은 파일의 `_multi_dot_three` 가 두 배치의 비용을 직접
계산해 비교하고, 문서가 그것이 *"approximately 15 times faster than `_multi_dot_matrix_chain_order`"* 라고 적어요.
위 표의 넷째 · 다섯째 줄과 여섯째 줄이 그 차이입니다 — 후보와 칸을 만드는 대신 값 둘만 계산하면 되니까요. 「최적인
문제의 모양」에서 적은 네 번째 조건(항목 수가 작다)의 반대편 끝이 여기입니다. DP 테이블은 행렬이 넷 이상일 때부터
값을 합니다.

- 소스: [`numpy/linalg/_linalg.py`](https://raw.githubusercontent.com/numpy/numpy/main/numpy/linalg/_linalg.py) (조회 2026-09-03)
- 문서: [`numpy.linalg.multi_dot`](https://numpy.org/doc/stable/reference/generated/numpy.linalg.multi_dot.html) (조회 2026-09-03)

### 수식 정의와 유도

괄호 배치의 집합으로 답을 정의하고, 그 정의를 작은 값에 넣어 검산하고, 셋을 유도한 다음 규모의 위 끝을 넣습니다.
유도 셋은 전이식과 **배치 수의 닫힌 형태**와 **후보 총수의 닫힌 형태**예요.

```text
정의   구간을 하나로 곱하는 괄호 배치의 집합 B(i, j) 와 그 비용 c
  ↓
검산   그 정의를 [10, 30, 5, 60, 10] 에 넣어 원소를 전부 적는다
  ↓
유도   마지막 곱셈으로 집합을 갈라 전이식을 얻는다
       배치 수의 점화식을 닫힌 형태로 푼다
       DP 테이블이 만드는 후보 총수를 닫힌 형태로 푼다
  ↓
계수   두 닫힌 형태에 n = 100 을 넣어 수치를 낸다
```

**먼저 집합입니다.** 구간 `A_i … A_j` 의 괄호 배치 하나를 $\beta$ 로 적고, 그런 배치를 모은 집합을 $B(i, j)$ 로
적습니다. 배치는 재귀로 정의돼요.

$$B(i,i) = \{\,A_i\,\},\qquad B(i,j) = \bigcup_{k=i}^{j-1}\ \bigl\{\,(\beta_L\beta_R)\ \bigm|\ \beta_L \in B(i,k),\ \beta_R \in B(k+1,j)\,\bigr\}$$

```text
i = 1 · j = 4 · k = 2 인 갈래가 B(1,4) 에 무엇을 넣는가

  β_L ∈ B(1,2) = { (A1A2) }        한 가지
  β_R ∈ B(3,4) = { (A3A4) }        한 가지
  → 이 갈래가 내놓는 배치는 ((A1A2)(A3A4)) 하나다
```

배치 하나의 비용 $c(\beta)$ 와 그 최솟값 $M(i,j)$ 도 같은 꼴로 정의합니다.

$$c(A_i) = 0,\qquad c\bigl((\beta_L\beta_R)\bigr) = c(\beta_L) + c(\beta_R) + p_{i-1}\,p_k\,p_j,\qquad M(i,j) = \min_{\beta \in B(i,j)} c(\beta)$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $\beta$ | 구간 하나의 괄호 배치 | $\beta \in B(i,j)$ |
| $\beta_L$ · $\beta_R$ | 바깥 괄호가 가른 왼쪽 · 오른쪽 배치 | $\beta_L \in B(i,k)$, $\beta_R \in B(k+1,j)$ |
| $k$ | $\beta$ 의 바깥 괄호가 가르는 자리 — 파트 1 의 `k` 와 같다 | $i \le k < j$ |
| $p_t$ | 차원 배열의 $t$ 번째 값 — 파트 1 의 `p` 와 같다 | $0 \le t \le n$ |
| $c(\beta)$ | 그 배치대로 곱했을 때의 스칼라 곱셈 횟수 | $c(A_i) = 0$ |
| $M(i,j)$ | 그 구간의 가장 적은 곱셈 횟수 | $M(i,i) = 0$ |
| $q$ | 배치 수를 셀 때 바깥 괄호가 **왼쪽에 두는 행렬 개수** | $1 \le q < n$ |

**정의를 값에 넣어 검산해 봅시다.** $p = [10, 30, 5, 60, 10]$ 이고 $i = 1$, $j = 4$ 면 $B(1,4)$ 의 원소를 다 적을
수 있습니다.

<!--proof:paren-walk-->

```text
전개 입력의 괄호 배치  곱셈 횟수
((A1A2)(A3A4))             5,000
(A1(A2(A3A4)))             7,500
(((A1A2)A3)A4)            10,500
(A1((A2A3)A4))            30,000
((A1(A2A3))A4)            33,000

배치 수 = 5 · 최솟값 = 5,000
```

파트 1 의 DP 테이블에서 `dp[1][4]` 가 정의에서 직접 고른 최솟값과 같습니다.

**첫째 유도는 전이식입니다.** $B(i,j)$ 의 정의가 이미 $k$ 로 갈라져 있으므로, 최솟값을 그 갈래마다 따로 구해 다시
최소를 취하면 돼요.

```text
B(i,j) 를 바깥 괄호가 가르는 자리 k 로 나눈다 — 서로 겹치지 않는 j − i 무리다

  한 무리 안에서 c 를 최소로 만들려면
    c(β) = c(β_L) + c(β_R) + p_(i-1)·p_k·p_j 에서 뒤 항이 k 로만 정해지므로
    앞 두 항을 각각 최소로 만들면 된다  →  M(i,k) + M(k+1,j) + p_(i-1)·p_k·p_j

  무리마다 그 값을 구해 최소를 취한 것이 M(i,j) 다
```

$$M(i,j) = \min_{i \le k < j}\ \bigl(M(i,k) + M(k+1,j) + p_{i-1}\,p_k\,p_j\bigr),\qquad M(i,i) = 0$$

`i = 1 · j = 4` 로 검산합니다.

<!--proof:math-check-m-->

```text
M(1,4) = min( 0 + 4,500 + 3,000 ,  1,500 + 3,000 + 500 ,  4,500 + 0 + 6,000 )
       = min( 7,500 , 5,000 , 10,500 )
       = 5,000        파트 1 의 dp[1][4] 과 같다
```

**둘째 유도는 배치 수입니다.** 행렬 $n$ 개의 배치 수를 $P(n)$ 이라 적습니다. 바깥 괄호가 왼쪽에 $q$ 개를 두는
갈래마다 $P(q)\,P(n-q)$ 가지가 나오고, 갈래끼리는 겹치지 않아요. **여기서 $q$ 는 개수이고 위의 $k$ 는 자리라 다른
기호를 씁니다** — 구간이 `A_1` 에서 시작할 때만 둘이 같은 수가 됩니다.

$$P(1) = 1,\qquad P(n) = \sum_{q=1}^{n-1} P(q)\,P(n-q)$$

<!--proof:math-code-p-->

```ts
// 식을 그대로 옮긴 조각. 합의 첨자 q 도 식과 같게 둔다.
const P = (n: number): number => {
  if (n <= 1) return 1;
  let sum = 0;
  for (let q = 1; q < n; q++) sum += P(q) * P(n - q);
  return sum;
};

P(4); // P(1)P(3) + P(2)P(2) + P(3)P(1) = 2 + 1 + 2 = 5
```

이 점화식은 카탈란 수의 점화식이고 닫힌 형태가 알려져 있습니다.

$$P(n) = \frac{1}{n}\binom{2n-2}{n-1}$$

<!--proof:math-closed-check-->

```text
n = 4 로 검산한다
  C(6, 3) / 4 = 20 / 4 = 5        위 조각이 낸 5 와 같다
```

점화식 · 닫힌 형태 · 전수 세기 셋이 같은 값을 내는지 여러 `n` 에서 확인해 봅시다.

<!--proof:paren-count-->

```text
행렬 수 n  전수로 세어 본 배치  점화식 P(n)  닫힌 형태 C(2n−2, n−1)/n  후보 총수 (n³−n)/6
2                            1            1                         1                   1
3                            2            2                         2                   4
4                            5            5                         5                  10
5                           14           14                        14                  20
6                           42           42                        42                  35
8                          429          429                       429                  84
10                       4,862        4,862                     4,862                 165
```

**셋째 유도는 DP 테이블이 만드는 후보 총수입니다.** 길이 $L$ 인 구간은 $n - L + 1$ 개이고 각각 후보가 $L - 1$
개예요. $d = L - 1$ 로 두고 더하면 닫힌 형태가 나옵니다.

$$\sum_{L=2}^{n}(n-L+1)(L-1) \;=\; \sum_{d=1}^{n-1} d\,(n-d) \;=\; n\cdot\frac{(n-1)n}{2} - \frac{(n-1)n(2n-1)}{6} \;=\; \frac{n^3-n}{6}$$

<!--proof:math-cand-check-->

```text
행렬 수  길이별 (구간 수 · 후보 수) 의 합                닫힌 형태
n = 4                3·1 + 2·2 + 1·3 = 10   (4³ − 4)/6 = 60/6 = 10
n = 5          4·1 + 3·2 + 2·3 + 1·4 = 20  (5³ − 5)/6 = 120/6 = 20
```

**마지막으로 계수입니다.** 두 닫힌 형태에 규모의 위 끝 $n = 100$ 을 넣으면, 배치를 세는 일과 후보를 만드는 일이
얼마나 갈리는지가 나옵니다.

<!--proof:paren-scale-->

```text
무엇                                                          값
행렬 100 개의 괄호 배치 수                          2.27 × 10^56
그 값의 자릿수                                                57
DP 테이블이 만드는 후보 총수 (n³−n)/6                    166,650
DP 테이블이 잡는 칸 수 (n+1)²                             10,201
배치 수가 후보 총수의 몇 배인가 — 그 배수의 자릿수            52
```

파트 1 은 행렬 넷에서 배치와 후보를 세었을 뿐이라, 두 수가 갈라지는 속도를 값으로는 알 수 없었습니다. 닫힌 형태
둘이 그것을 임의의 `n` 으로 일반화해요 — 배치 수는 지수보다 빠르게 늘고 후보 총수는 세제곱으로 늘어서, 규모의 위
끝에서 그 배수가 수십 자리가 됩니다.

### 불변식 — 길이 L 까지 다 정한 시점에 dp[i][j] 는 A_i … A_j 의 가장 적은 곱셈 횟수다

파트 1 에서 코드가 동작하는 것을 열두 걸음으로 봤습니다. 그것은 행렬 넷의 특정 차원에서 맞았다는 뜻이지, 어떤
입력에서도 맞는다는 뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 한 문장으로 세우고, DP 테이블을 채우는 각
걸음이 그 문장을 지키는지 값으로 따져 봅니다.

> 길이가 `L` 인 구간을 **전부 정하고 난 시점**에, `j − i + 1 ≤ L` 인 모든 칸 `dp[i][j]` 는 행렬 `A_i … A_j` 를
> **차례를 지키면서** 어떤 배치로 묶었을 때 나올 수 있는 스칼라 곱셈 횟수의 **최솟값**입니다.

```text
전부 정하고 난 시점    길이 L 인 칸이 하나라도 남았으면 아직 그 시점이 아니다
차례를 지키면서        행렬의 순서를 바꾼 배치는 세지 않는다
어떤 배치로 묶었을 때  괄호를 어디에 치든 전부 센다
최솟값                 평균도, 아무 배치 하나의 값도 아니다
```

「길이 `L` 을 전부 정하고 난 시점」이 이 알고리즘에서는 **칸 하나를 정하고 난 시점**과 다릅니다. 같은 길이의
칸끼리는 서로를 안 읽으므로, 시점을 길이 단위로 잡아야 논증이 한 줄로 적혀요.

```text
길이 L 인 칸이 읽는 두 조각은 길이가 1 이상 L−1 이하다
  → 길이 L−1 까지가 전부 정해진 뒤라면 읽는 칸이 전부 정해져 있다
  → 같은 길이의 칸끼리는 서로를 안 읽으므로 그 안의 차례는 답을 바꾸지 않는다
```

**출발점부터 봅시다.** 길이 1 인 구간은 행렬 하나라서 곱셈이 일어나지 않고 배치도 하나뿐이니 최솟값이 0 인데,
코드가 DP 테이블을 0 으로 깔았으니 참입니다. 그 뒤로 한 칸은 후보마다 두 갈래 중 하나를 지나고, 각 갈래가 하는 일은
아래와 같아요.

| 값을 정하는 갈래 | 읽는 자리 | 불변식과 맞물리는 곳 |
| --- | --- | --- |
| 길이 1 (대각선) | 없다 | 배치가 하나뿐이라 0 |
| 후보가 지금까지의 최소보다 작다 | `dp[i][k]` · `dp[k+1][j]` | 두 조각 각각의 최솟값에 합치는 비용을 더한 값이 `best` 가 된다 |
| 작지 않다 | 같음 | `best` 를 안 바꾼다 |

두 번째 갈래가 이 불변식과 맞물리는 자리입니다. `dp[i][k]` 와 `dp[k+1][j]` 가 각각 그 조각의 최솟값이라면, 바깥
괄호를 `k` 에 친 배치 중 가장 적은 것이 그 둘의 합에 합치는 비용을 더한 값이에요. 합치는 비용은 조각 안의 배치와
무관하니까요. 거꾸로 `A_i … A_j` 의 어떤 배치든 바깥 괄호가 `i` 이상 `j` 미만의 어느 자리에는 있으므로, `k` 를 전부
시험하면 빠지는 배치도 없습니다. 둘을 합치면 `best` 의 마지막 값이 그 구간의 최솟값이고, 길이 `L` 의 칸을 다 적은
시점에 불변식이 길이 `L` 까지 참이 됩니다. 길이 4 를 정하는 동안 읽은 자리를 적으면 이렇습니다.

<!--proof:invariant-reads-->

```text
L=4 를 정하는 동안 읽은 자리를 전부 적으면

가르는 자리       왼쪽 조각     오른쪽 조각          합치기    후보
k=1              dp[1][1]=0  dp[2][4]=4,500  10·30·10=3,000   7,500
k=2          dp[1][2]=1,500  dp[3][4]=3,000     10·5·10=500   5,000
k=3          dp[1][3]=4,500      dp[4][4]=0  10·60·10=6,000  10,500
          └ 읽은 6 칸의 길이가 1 · 2 · 3 뿐이고 전부 이미 정해져 있다
```

경계에 있는 입력들도 확인하고 갑시다.

<!--proof:invariant-edges-->

| 차원 배열 | DP 테이블에서 일어나는 일 | 반환값 |
| --- | --- | ---: |
| [10] (행렬 0 개) | 첫 분기가 잡는다 | 0 |
| [10, 20] (행렬 1 개) | 첫 분기가 잡는다 | 0 |
| [5, 10, 3] (행렬 2 개) | L=2 한 칸, 후보 하나 | 150 |
| [5, 5, 5, 5] (차원이 전부 같다) | 모든 배치의 곱셈 횟수가 한 가지 | 250 |
| [1, 1, 1, 1, 1] (차원이 전부 1) | 곱셈 한 번마다 1 | 3 |
| [500, 500, 500] (차원이 위 끝) | 후보 하나 | 125,000,000 |

[5, 5, 5, 5] 의 배치 2 가지가 내는 곱셈 횟수는 250 한 가지이고, [1, 1, 1, 1, 1] 은 곱셈 3 번이 한 번마다 1 이라 3 입니다.

<!--/proof-->

여섯 다 따로 분기하지 않고 같은 전이식으로 처리되고, 앞의 둘만 행렬이 한 개 이하라 첫 분기가 먼저 걸러요. 넷째 줄이 이 알고리즘의 성질
하나를 말해 줍니다 — 차원이 전부 같으면 어느 배치든 곱셈 횟수가 같아서, **그런 입력으로는 배치를 고르는 규칙이
맞는지 확인할 수 없습니다.**

**이제 깨뜨려 봅시다.** 불변식에서 「어떤 배치로 묶었을 때」는 `k` 를 전부 시험하는 반복문이 지키고, 「최솟값」이
두 조각의 최소를 더해도 된다는 사실은 합치는 비용이 두 조각의 크기로만 정해진다는 데서 옵니다. 그 크기를 코드에서
지키는 것이 합치는 비용의 **가운데 항** 하나예요. 그 항을 옆 칸에서 읽게 바꿉니다.

```ts
const join =
  (dims[i - 1] as number) * (dims[k + 1] as number) * (dims[j] as number);
//                                      ~~~~~ dims[k] 였다
```

차원 배열을 바꿔 가며 실행하면 이렇게 나옵니다.

<!--proof:mutant-join-dim-->

```text
차원 배열             바른 코드  만나는 차원을 옆 칸에서 읽은 코드
[10, 30, 5, 60, 10]       5,000                              6,750
[10, 30, 5, 60]           4,500                             36,250
[10, 20, 30, 40, 30]     30,000                             34,000
[2, 3, 4, 2, 5]              56                                 78
[5, 5, 5, 5]                250                                250
[10, 20]                      0                                  0
```

**위 넷이 전부 달라졌습니다.** 왼쪽 조각의 크기가 `p[i-1] × p[k]` 이고 오른쪽이 `p[k] × p[j]` 인데 가운데 항을
`p[k+1]` 로 읽으면, 있지도 않은 크기의 두 행렬을 곱한 비용을 적는 셈이에요. 전개 입력의 가장 작은 후보에서 그 수를
적으면 이렇습니다.

<!--proof:invariant-mutant-join-->

```text
dp[1][4] 의 k=2 후보에서 합치는 비용

  바른 코드   두 조각이 10×5 와 5×10 이라    →  10 · 5 · 10 = 500
  바뀐 코드   가운데를 p[3] = 60 으로 읽어   →  10 · 60 · 10 = 6,000
                └ 두 조각의 실제 크기와 아무 관계 없는 수를 더한다
```

**그런데 아래 둘은 답이 같았습니다.** `[5, 5, 5, 5]` 는 차원이 전부 같아 `p[k]` 든 `p[k+1]` 이든 5 이고,
`[10, 20]` 은 행렬이 하나라 첫 분기가 걸러 반복문에 들어가지도 않아요. 정사각 행렬만 넣어 확인하면 이 변형이
통과합니다 — 위 표 다섯째 줄이 그 상태입니다.

### 비용 계산

#### 비용을 세는 과정

호출 하나가 하는 일을 셋으로 가르고, 셋을 더해 총식을 만듭니다.

| 할 일 | 횟수 |
| --- | --- |
| DP 테이블 만들기 | `(n+1)²` 칸을 0 으로 채운다 |
| 후보 만들기 | 구간마다 `j − i` 개. T2~T11 이 그 후보 하나하나다 |
| 읽기 | `dp[1][n]` 한 칸을 읽는다. T12 가 그것이다 |

후보 하나마다 하는 일은 덧셈 둘 · 곱셈 둘 · 비교 하나라 늘 같아요. T2 처럼 두 조각이 다 0 인 후보든 T11 처럼 두
조각이 다 채워진 후보든 하는 일이 같습니다. 그러니 후보가 몇 개인지만 세면 돼요.

<!--proof:perf-derive-->

| 구간 길이 | 구간 수 n − L + 1 | 구간마다 후보 L − 1 | 후보 | 걸음 |
| --- | ---: | ---: | ---: | --- |
| L = 2 | 3 | 1 | 3 | T2 · T3 · T4 |
| L = 3 | 2 | 2 | 4 | T5 · T6 · T7 · T8 |
| L = 4 | 1 | 3 | 3 | T9 · T10 · T11 |
| 합계 |  |  | 10 | (4³ − 4)/6 = 10 |

행렬 100 개면 잡는 칸 10,201 개 · 쓰는 칸 5,050 개 · 후보 166,650 개이고, 칸 하나를 8 바이트 수로 두면 DP 테이블은 81,608 바이트입니다.

<!--/proof-->

메모리는 칸 수와 같습니다 — `Θ(n²)` 칸을 실제로 들고 있어요. 쓰는 칸은 위쪽 삼각형 `n(n+1)/2` 개뿐인데 정사각
배열로 잡아 두 배 가까이 되지만, 같은 `Θ(n²)` 안이고 위 블록의 바이트 수는 흔한 채점 환경의 예산 256 MB 보다
훨씬 작습니다. 시간의 총식은 DP 테이블을 만드는 칸 수와 후보 수의 합이에요.

$$\text{후보 수} + \text{칸 수} = \frac{n^3-n}{6} + (n+1)^2 = \Theta(n^3)$$

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 $O$ | 타이트 $\Theta$ |
| --- | --- | --- |
| **최선의 경우** (차원이 전부 같다) | $O(n^3)$ | $\Theta(n^3)$ |
| **평균적인 경우** (차원을 아무렇게나 뽑아도) | $O(n^3)$ | $\Theta(n^3)$ |
| **최악의 경우** (어떤 입력이든) | $O(n^3)$ | $\Theta(n^3)$ |

**세 줄이 같습니다.** 이 알고리즘은 입력을 보고 일찍 끝내는 자리가 없어 후보 `(n³ − n)/6` 개를 언제나 한 번씩
만들어요. 안쪽 반복문이 `k = i` 에서 `j−1` 까지 무조건 반복하는 것이 그 이유이고, 차원이 전부 같아 어느 후보를
골라도 결과가 같은 입력에서도 후보 수는 그대로입니다.

**보장의 종류는 최악 보장입니다.** 기댓값이 아닙니다 — 코드에 무작위성이 없고 차원 값의 분포를 가정하는 자리도
없어요. 같은 차원 배열이면 몇 번을 실행해도 만든 후보 수가 같습니다. 위 표의 「평균」 줄이 뜻하는 것도 분포에 대한
기댓값이 아니라 **어떤 분포에서 차원을 뽑아도 같은 값**이라는 것입니다.

```text
n³ 의 n 은 입력의 "값" 이 아니라 "개수" 다

  행렬 n 개를 적는 데 차원이 n + 1 개      →  후보 (n³ − n)/6 개
  차원이 전부 500 이든 전부 1 이든          →  후보 수는 같다
  차원 값을 키워도 후보는 한 개도 안 늘어난다
```

그래서 이 알고리즘은 **의사다항이 아닙니다.** 입력에 적힌 숫자의 크기가 아니라 **항목 수**로 비용이 정해지니, 같은
DP 테이블 모양을 쓰는 [0/1 배낭](../knapsack01/knapsack01-guide.md) 이나 [부분집합 합 판정](../subsetSum/subsetSum-guide.md)
과 갈리는 자리가 여기예요. 그쪽은 한 축이 「용량」이나 「합」이라 값이 커지면 DP 테이블이 함께 커집니다.

#### 최악을 만드는 입력

「어떤 입력이 최악인가」라는 물음이 위 코드에 대해서는 **입력의 내용과 무관**합니다. 차원을 어떻게 두어도 만드는
후보 수가 같기 때문이에요. 규모의 위 끝인 행렬 100 개짜리 입력 다섯을 실제로 실행해 후보 수를 세어 봅시다.

<!--proof:worst-fill-->

| 입력 (행렬 100 개) | 답 | 후보 수 |
| --- | ---: | ---: |
| 차원이 전부 1 | 99 | 166,650 |
| 차원이 전부 500 | 12,375,000,000 | 166,650 |
| 1 과 500 이 번갈아 | 25,049 | 166,650 |
| (13t mod 50) + 1 | 61,701 | 166,650 |
| 1 부터 101 까지 오름차순 | 343,398 | 166,650 |

답은 99 부터 12,375,000,000 까지 갈리는데, 후보 수는 다섯 입력 모두 166,650 개입니다. 시간의 최악은 행렬 수 하나로 정해지고, 그때 차원 값은 아무래도 좋습니다.

<!--/proof-->

**대신 이 과제에는 시간이 아닌 최악이 하나 더 있습니다** — 답 자체의 크기예요. 곱셈 한 번의 비용이 세 차원의 곱이라
차원이 클수록 답이 커지고, 그 값이 배정밀도 정수가 정확히 셀 수 있는 범위를 넘으면 비교가 뜻을 잃습니다. 차원을
전부 위 끝인 500 으로 두고 재 봅시다.

<!--proof:answer-scale-->

| 무엇 | 값 |
| --- | ---: |
| 차원이 전부 500 · 행렬 100 개일 때의 답 | 12,375,000,000 |
| 배정밀도 정수가 정확한 상한 | 9,007,199,254,740,991 |
| 상한이 그 답의 몇 배인가 | 727,854 |

곱셈 한 번이 500³ = 125,000,000 이고 곱셈이 99 번이라, 답이 125,000,000 × 99 = 12,375,000,000 입니다.

<!--/proof-->

답이 배정밀도 정수가 정확한 범위보다 훨씬 작아 여유가 넉넉해요. 차원의 위 끝이 훨씬 커서 곱셈 한 번이 그 범위를
넘는다면 이 코드는 그대로는 정확히 못 셉니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 괄호 배치를 하나씩 만드는 대신 **같은 구간에 이른 배치들을 한 칸으로
합쳤고**, 마지막으로 곱하는 자리 `k` 를 전부 시험해 두 조각으로 갈랐고, 두 조각이 늘 더 짧아서 **구간 길이 차례로**
채우면 읽는 칸이 늘 준비돼 있습니다.

```text
구간 길이가 짧은 칸부터 → (i, j) 칸에 가장 적은 곱셈 횟수를 적는다 → dp[1][n] 을 읽는다
        └ 두 조각이 언제나 더 짧다      └ k 를 전부 시험해 배치를 빠짐없이 덮는다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T6 에서 `dp[1][3]` 이, T8 에서 `dp[2][4]` 가 같은 값으로 정해졌어요. 두 값은
각각 어떤 괄호 배치를 뜻할까요? 그리고 고른 `k` 가 같은데 왜 다른 배치일까요?

<!--proof:selfcheck-q-->

```text
T6 :  dp[1][3] = 1,500 + 0 + (10·5·60) = 4,500   고른 k = 2
T8 :  dp[2][4] = 0 + 3,000 + (30·5·10) = 4,500   고른 k = 2
      두 값이 각각 뜻하는 배치 = ?     ← 이 자리를 직접 채워 봅시다
```

<!--check:sameValue-->

<!--proof:selfcheck-a-->

| 구간 | 가르는 자리 | 왼쪽 조각 | 오른쪽 조각 | 배치 |
| --- | --- | --- | --- | --- |
| A1 … A3 | k = 2 | A1 … A2 (1,500) | A3 (0) | ((A1A2)A3) |
| A2 … A4 | k = 2 | A2 (0) | A3 … A4 (3,000) | (A2(A3A4)) |

두 칸의 가르는 자리가 똑같이 k = 2 인데, 왼쪽 조각에 든 행렬 수는 2 개와 1 개로 다릅니다.

<!--/proof-->

여기서 확인할 것은 **`k` 가 구간 안의 상대 위치가 아니라 행렬 번호**라는 점입니다. `k` 는 「몇 번째 행렬 뒤에서
가르는가」이지 「왼쪽에 몇 개를 두는가」가 아니라서, 구간의 왼쪽 끝이 다르면 같은 `k` 라도 왼쪽 조각의 크기가
달라요.

### 행렬 체인 곱셈 최소 비용

풀 파일: [`matrixChainMultiplication.ts`](./matrixChainMultiplication.ts) · 테스트: [`matrixChainMultiplication.test.ts`](./matrixChainMultiplication.test.ts) · 실행: `bun test src/algorithms/dp/matrixChainMultiplication/matrixChainMultiplication.test.ts`

#### 한 줄 요약

> 함수는 행렬 체인의 차원 배열을 받아, 모든 행렬을 곱할 때 필요한 최소 스칼라 곱셈 횟수를 반환한다.

#### 스토리

그래픽스 엔진을 개발하는 채린은 여러 변환 행렬을 순서대로 곱해 최종 좌표를 계산하는 코드를 최적화하고 있다. 수학적으로 결합 법칙이 성립하므로 곱셈 순서를 어떻게 묶느냐에 따라 실제 연산 횟수가 크게 달라진다는 사실을 알게 됐다.

채린은 같은 결과를 내면서도 연산 횟수를 가능한 한 줄이고 싶다. 행렬이 많아질수록 경우의 수도 폭발적으로 늘어나, 눈으로 최적 배열을 찾기는 불가능하다.

두 행렬 $p \times q$와 $q \times r$을 곱하는 비용은 $p \cdot q \cdot r$번의 스칼라 곱셈이다.

#### 함수 인터페이스

```ts
export function matrixChainMultiplication(dims: number[]): number;
```

- `dims` — 길이 $n + 1$의 양의 정수 배열. $i$번째 행렬의 크기는 $dims[i-1] \times dims[i]$이다.
- 반환 — 행렬 체인 전체를 곱할 때 필요한 최소 스칼라 곱셈 횟수

#### 제약 조건

- $1 \leq |dims| \leq 101$ (즉 행렬 수 $n \leq 100$)
- $1 \leq dims[i] \leq 500$
- 행렬은 주어진 순서대로 곱해야 하며, 순서 자체는 바꿀 수 없다.
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

$n$개의 행렬 $A_1, A_2, \ldots, A_n$이 주어지고, 이를 반드시 이 순서로 곱해야 한다. 결합 방식(어느 구간을 먼저 곱할지)은 자유롭게 선택할 수 있다.

행렬 $A_i$의 크기는 $dims[i-1] \times dims[i]$이다.

$|dims| = 1$ (행렬이 없음) 또는 $|dims| = 2$ (행렬 1개)인 경우 곱셈이 발생하지 않으므로 $0$을 반환한다.

#### 예시

```ts
matrixChainMultiplication([10, 20, 30]);
// 6000 — 행렬이 두 개(10×20, 20×30)이므로 결합 방식이 한 가지: 10·20·30 = 6000

matrixChainMultiplication([10, 30, 5, 60]);
// 4500 — 세 가지 결합 중 (A1A2)A3 방식이 10·30·5 + 10·5·60 = 1500 + 3000 = 4500으로 최소

matrixChainMultiplication([10, 20, 30, 40, 30]);
// 30000 — 최적 결합 순서를 선택했을 때의 최솟값

matrixChainMultiplication([10, 20]);
// 0 — 행렬이 한 개뿐이므로 곱셈 없음

matrixChainMultiplication([5, 5, 5, 5]);
// 250 — 세 행렬 모두 5×5이므로 어떤 순서로 묶어도 5·5·5 × 2 = 250
```
