# 분할 정복 최적화 — 최적 가르는 자리가 칸을 따라 뒤로만 가면 가운데 칸 하나가 좌우의 후보를 함께 자르는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 가르는 자리를 전부
계산하는 방법에서 출발해 분할 정복 최적화에 이르고, 그 방법을 단계마다 값으로 푼 뒤, 실제로 동작하는 코드를
한 조각씩 만듭니다.

### 전체 컨셉

한 줄로 늘어선 칸 `n` 개(0 번부터 `n − 1` 번까지)를 **이어진 구역 `k` 개**로 나눕니다. 칸 `i` 부터 `j` 까지를 한
구역으로 묶는 비용 `cost[i][j]` 가 미리 주어지고, 구역마다의 비용을 더한 합이 가장 작아지게 나누는 것이
목표예요. 구역은 겹치지 않고, 빠짐없이, 순서대로 이어집니다. 입력 `a = [1, 2, 3, 4]` 에서 비용을 구간 합의 제곱
`cost[i][j] = (a[i] + … + a[j])²` 으로 두고 세 구역으로 나누는 방법을 전부 적어 보면 이렇습니다.

<!--proof:concept-parts-->

| 구역 셋 | 구역마다의 비용 | 합 |
| --- | --- | ---: |
| [0,0] [1,1] [2,3] | 1 + 4 + 49 | 54 |
| [0,0] [1,2] [3,3] | 1 + 25 + 16 | 42 |
| [0,1] [2,2] [3,3] | 9 + 9 + 16 | 34 |

나누는 방법 3 가지 가운데 가장 작은 합은 34 고, 정본 divideAndConquerDp 도 34 를 돌려줍니다.

<!--/proof-->

나누는 방법이 늘어나면 이렇게 전부 적을 수 없으니, 작은 문제의 답을 칸에 적어 두는 **DP 테이블**을 씁니다.
칸 `dp[g][i]` 에 「칸 `[0,i]` 를 구역 `g` 개로 나눈 가장 작은 비용」을 적어요. 이 칸을 정하려면 마지막 구역이
어디서 시작하는지 골라야 합니다. 마지막 구역이 `[j+1, i]` 이면 그 앞의 `[0,j]` 는 구역 `g − 1` 개로 나뉘므로,
이 `j` 를 **가르는 자리**라 부르고 가르는 자리마다 `dp[g−1][j] + cost[j+1][i]` 를 계산해 가장 작은 값을 칸에
적습니다. 칸 `dp[2][3]` 을 가르는 자리마다 계산하면 이렇습니다.

<!--proof:concept-cell-->

| 가르는 자리 | 나뉜 모양 | dp[1][j] + cost[j+1][3] | 값 |
| --- | --- | --- | ---: |
| j = 0 | 앞 구역 [0,0] · 마지막 구역 [1,3] | 1 + 81 | 82 |
| j = 1 | 앞 구역 [0,1] · 마지막 구역 [2,3] | 9 + 49 | 58 |
| j = 2 | 앞 구역 [0,2] · 마지막 구역 [3,3] | 36 + 16 | 52 |

가장 작은 값은 52 고 그 값을 만든 가르는 자리는 j = 2 입니다.

<!--/proof-->

그 가장 작은 값을 만든 가르는 자리를 그 칸의 **최적 가르는 자리**라 부르고 `opt(g, i)` 로 적습니다. 같은 값을
내는 자리가 여럿이면 가장 작은 `j` 를 고릅니다. 칸마다 값 하나와 최적 가르는 자리 하나가 붙는 셈이에요. 이 입력의
DP 테이블 전체와, 칸마다의 최적 가르는 자리를 한 장에 그렸습니다. 맨 아래 `a` 줄이 입력이고, 대시 칸은 구역
수보다 칸이 적어 만들 수 없는 칸입니다.

<!--fig:concept-table-->
![a = [1, 2, 3, 4] 를 3 구역까지 나누는 DP 테이블 — 칸마다 값과 그 값을 만든 가르는 자리](./figs/concept-table.svg)

`opt(2, i)` 줄을 왼쪽에서 오른쪽으로 읽으면 0 · 1 · 2 로, 칸이 뒤로 갈수록 최적 가르는 자리도 뒤로만 갑니다.
이 성질이 있으면 칸을 왼쪽부터 채울 필요가 없어요. **가운데 칸의 최적 가르는 자리를 먼저 구하면**, 그보다 왼쪽
칸들의 최적 가르는 자리는 그 자리보다 앞에, 오른쪽 칸들의 것은 그 자리보다 뒤에 있습니다. 그래서 왼쪽 절반과
오른쪽 절반에 넣어 볼 가르는 자리의 범위를 한꺼번에 잘라 넘기고, 각 절반에서 같은 일을 되풀이합니다. 이 방법을
**분할 정복 최적화**라고 부릅니다.

```text
DP 테이블의 줄 g 하나를 채우는 차례

  칸 [0, n−1] 의 가운데 칸을 먼저 채운다   → 최적 가르는 자리 p 를 얻는다
  왼쪽 칸들은 가르는 자리를 p 까지만 넣는다
  오른쪽 칸들은 가르는 자리를 p 부터만 넣는다
  두 절반에서 같은 일을 되풀이한다
```

이 「뒤로만 간다」는 아무 비용에서나 성립하지 않습니다. 비용이 **사각 부등식** — 지표 `a ≤ b ≤ c ≤ d` 마다
`cost[a][c] + cost[b][d] ≤ cost[a][d] + cost[b][c]` — 을 만족할 때 성립합니다. 구간 합의 제곱이 그런 비용의
예이고, 이 글은 쓰는 비용 행렬마다 그 부등식을 칸을 전부 확인해서 씁니다.
비용을 결과만 적으면 DP 테이블의 줄 하나가 `O(n log n)`, 줄 `k` 개가 `O(k n log n)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **DP 테이블과 가르는 자리.** 작은 입력의 답을 칸에 적어 두고 큰 입력의 답을 그 칸들에서 만드는 표, 그리고 구간을
  어디서 가를지 후보를 하나씩 넣어 보는 틀입니다. 모르면
  [행렬 체인 곱셈 최소 비용](../../dp/matrixChainMultiplication/matrixChainMultiplication-guide.md)을 먼저 보세요.
  이 글은 거기서 쓴 「DP 테이블」과 「가르는 자리」라는 말을 그대로 씁니다.
- **줄 단위로 채우는 동적 계획법.** 이전 줄만 읽어 다음 줄을 채우므로 두 줄만 들고 가면 되는 모양입니다. 같은
  모양의 이웃 편이 [0/1 배낭](../../dp/knapsack01/knapsack01-guide.md)이에요.
- **범위를 반씩 가르는 재귀.** `mid = (lo + hi) >> 1` 로 가운데를 잡고 양옆으로 내려가는 꼴입니다. 가운데 칸을
  읽어 후보를 절반씩 줄이는 [이진 탐색](../../binary-search/binarySearch/binarySearch-guide.md)이 가까운 모양이에요.
- **구간 합.** 이 글의 비용은 구간 합의 제곱이라 누적합으로 만듭니다. 모르면
  [구간 합 질의](../../array/prefixSumRangeQuery/prefixSumRangeQuery-guide.md)를 보세요.

몰라도 되는 것은 사각 부등식을 증명하는 방법입니다. 이 글은 사각 부등식에서 최적 가르는 자리의 성질이 나오는
유도까지만 파트 2 에서 한 줄씩 풀고, 비용 행렬이 그 부등식을 만족하는지는 칸을 전부 확인해서 봅니다.

### 아이디어를 떠올리는 과정 — 가르는 자리 전부 계산하기에서 분할 정복 최적화까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 비용 행렬과 구역 수를 받아 가장 작은 합을
돌려주는 함수입니다.

```ts
function divideAndConquerDp(cost: number[][], k: number): number;
```

- 입력: `n × n` 비용 행렬 `cost` 와 구역 수 `k`. `cost[i][j]` 는 칸 `[i, j]` 를 한 구역으로 묶는 비용이고 `i ≤ j`
  에서만 뜻이 있습니다. 비용은 0 이상이고, **사각 부등식을 만족한다고 둡니다** — 이 과제가 기대는 전제이고,
  깨지면 무엇이 되는지는 「아이디어 상세」에서 실행으로 봅니다.
- 출력: 칸 `[0, n−1]` 을 정확히 `k` 개의 이어진 구역으로 나눴을 때 비용 합의 최솟값.
- 규모: `1 ≤ n ≤ 2,000`, `1 ≤ k ≤ n` 으로 둡니다. 이 함수는 비용 행렬을 통째로 받으므로 칸이 `n²` 개이고, 흔한
  채점 환경의 예산인 1 초 · 256 MB 에 대어 보면 이렇습니다.

<!--proof:origin-budget-->

| n | 비용 행렬의 칸 | 칸마다 8 바이트 |
| ---: | ---: | ---: |
| 500 | 250,000 | 2 MB |
| 1,000 | 1,000,000 | 8 MB |
| 2,000 | 4,000,000 | 32 MB |
| 5,000 | 25,000,000 | 200 MB |

`n` 이 2,000 이면 비용 행렬이 32 MB 라 예산 안에 넉넉히 들고, 5,000 이면 200 MB 로 예산 끝에 다가갑니다. 그래서
이 글은 `n` 을 2,000 까지로 둡니다. 비용은 이 글 끝까지 **후보 수** 하나로 셉니다. 가르는 자리 `j` 하나를 넣어
`dp[g−1][j] + cost[j+1][i]` 를 만들고 지금까지의 최솟값과 비교한 한 번이 1 이에요. 후보 하나는 읽기 둘 · 덧셈
하나 · 비교 하나로 끝나는 일이라, 1 초에 후보 1 억 개를 처리한다고 어림합니다. 이 글이 끝까지 쓰는 기호는
여덟입니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `n` | 칸의 개수. 코드의 `cost.length` 입니다 | `1 ≤ n ≤ 2,000` |
| `k` | 나눌 구역의 개수 | `1 ≤ k ≤ n` |
| `cost[i][j]` | 칸 `[i, j]` 를 한 구역으로 묶는 비용 | 0 이상. `i ≤ j` |
| `g` | DP 테이블에서 지금 채우는 줄 — 구역이 `g` 개인 줄 | `1` 부터 `k` 까지 |
| `dp[g][i]` | 칸 `[0, i]` 를 정확히 구역 `g` 개로 나눈 가장 작은 비용 | 만들 수 없으면 `INF` |
| `j` | 가르는 자리 — 마지막 구역 `[j+1, i]` 바로 앞의 칸 | `0 ≤ j < i` |
| `opt(g, i)` | 최적 가르는 자리 — `dp[g][i]` 를 만든 가르는 자리 중 가장 작은 것 | 칸마다 하나 |
| `INF` | 그 칸을 만들 수 없다는 표기. 코드의 `Number.POSITIVE_INFINITY` 입니다 | 구역 수보다 칸이 적은 칸 |

가장 먼저 떠오르는 방법은 **나누는 방법을 전부 만들어** 합이 가장 작은 것을 고르는 것입니다. 칸 `n` 개 사이의
틈 `n − 1` 개 가운데 `k − 1` 개를 골라 구역을 가르니 방법의 수는 `C(n−1, k−1)` 이에요. 작은 입력에서 실제로
세고 과제 규모에 식을 넣었습니다.

<!--proof:origin-partitions-->

| n | k | 분할의 개수 | 출처 |
| ---: | ---: | ---: | --- |
| 4 | 3 | 3 | 센 값 |
| 8 | 3 | 21 | 센 값 |
| 12 | 4 | 165 | 센 값 |
| 2,000 | 1,000 | 601 자리 수 | 식 — C(n−1, k−1) |

센 값 세 줄은 C(n−1, k−1) 과 같고, 세 줄 모두 가장 작은 합이 정본의 답과 같습니다.

<!--/proof-->

`n = 2,000` 에 구역이 1,000 개면 방법의 수가 601 자리 수라 하나씩 만들 수 없습니다. 그런데 방법들을 보면 같은 앞
구역을 여러 번 만들고 있어요. 그래서 앞 구역들의 가장 작은 비용을 DP 테이블의 칸에 적어 두고, 칸마다 가르는
자리 `j = 0 … i−1` 을 전부 넣어 봅니다. 그 방법의 후보 수를 세었습니다.

<!--proof:origin-naive-->

| n | k | 후보 수 | 출처 | 시간(초당 1 억 개) |
| ---: | ---: | ---: | --- | ---: |
| 8 | 3 | 56 | 센 값 | 0.00 초 |
| 64 | 64 | 127,008 | 센 값 | 0.00 초 |
| 256 | 256 | 8,323,200 | 센 값 | 0.08 초 |
| 2,000 | 2,000 | 3,996,001,000 | 어림 — (k−1)·n(n−1)/2 | 40 초 |

위 세 줄은 실제로 센 값이고, 세 줄 모두 (k−1)·n(n−1)/2 와 같습니다. 마지막 줄은 그 식에 n = k = 2,000 을 넣어 늘린 어림입니다.

<!--/proof-->

칸이 2,000 개이고 구역도 2,000 개면 어림으로 40 초가 걸려 예산 1 초를 훨씬 넘습니다. 줄 하나에 칸이 `n` 개, 줄이
`k − 1` 개라는 것은 과제가 정하고, 줄일 곳은 **칸 하나가 넣어 보는 가르는 자리의 수** 하나예요. 그 수를
줄이려면 칸마다 최적 가르는 자리가 어디쯤인지 알아야 합니다. `a = [1, 2, …, 8]` 을 세 구역으로 나누며 칸마다
최적 가르는 자리를 전부 구해 봅시다.

<!--proof:origin-opt-->

| 칸 i | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| opt(2, i) | 없음 | 0 | 1 | 2 | 2 | 3 | 4 | 4 |
| opt(3, i) | 없음 | 없음 | 1 | 2 | 3 | 4 | 5 | 5 |

a = [1, 2, 3, 4, 5, 6, 7, 8] 을 k = 3 구역으로 나눌 때입니다. 「없음」은 구역 수보다 칸이 적어 만들 수 없는 칸입니다.

<!--/proof-->

두 줄 다 한 번도 앞으로 되돌아가지 않습니다. 그러면 칸을 왼쪽부터 채우면서 **가르는 자리를 직전 칸의 최적
가르는 자리부터** 넣어도 됩니다. 같은 입력을 두 방식으로 처리해 줄 2 의 칸마다 넣은 후보를 나란히 적었어요.

<!--proof:origin-two-->

| 칸 i | 전부 계산하는 후보 | 하한을 옮긴 후보 | opt(2, i) |
| --- | --- | --- | --- |
| 0 | 없음 | 없음 | 없음 |
| 1 | [0,0] · 1 개 | [0,0] · 1 개 | 0 |
| 2 | [0,1] · 2 개 | [0,1] · 2 개 | 1 |
| 3 | [0,2] · 3 개 | [1,2] · 2 개 | 2 |
| 4 | [0,3] · 4 개 | [2,3] · 2 개 | 2 |
| 5 | [0,4] · 5 개 | [2,4] · 3 개 | 3 |
| 6 | [0,5] · 6 개 | [3,5] · 3 개 | 4 |
| 7 | [0,6] · 7 개 | [4,6] · 3 개 | 4 |

줄 2 하나에서 전부 계산하면 후보 28 개, 하한을 직전 칸의 최적 가르는 자리로 옮기면 16 개입니다. 줄 둘을 합하면 56 개와 29 개입니다.

<!--/proof-->

하한을 옮기자 후보가 56 개에서 29 개로 줄었습니다. 관찰한 것은 하나예요. **잘리는 것은 아래쪽뿐이고 위쪽은
그대로 `i − 1` 입니다.** 칸 7 의 후보가 `[4,6]` 인데 최적 가르는 자리 4 보다 뒤의 5 · 6 은 넣을 필요가 없었어요.
이 방법을 규모를 키워 시험하면 이렇습니다. 마지막 열은 뒤에서 세울 방법의 값이에요.

<!--proof:origin-sweep-->

| 입력 | n | 전부 계산 | 하한만 옮기기 | 전부 계산에 대한 비 | 가운데 칸부터 |
| --- | ---: | ---: | ---: | ---: | ---: |
| a = [1, 2, …, n] | 64 | 4,032 | 1,105 | 27 % | 727 |
| a = [1, 2, …, n] | 256 | 65,280 | 16,124 | 25 % | 4,021 |
| 첫 칸만 큰 배열 | 64 | 4,032 | 3,071 | 76 % | 833 |
| 첫 칸만 큰 배열 | 256 | 65,280 | 49,151 | 75 % | 4,439 |

세 방법 모두 k = 3 입니다. 첫 칸만 큰 배열에서 n = 64 일 때 opt(2, i) 의 마지막 여덟 칸은 0 0 0 0 0 0 0 0 입니다.

<!--/proof-->

**하한만 옮기는 방법은 전부 계산에 대한 비가 규모를 키워도 내려가지 않습니다.** `a = [1, 2, …, n]` 에서 27 %
에서 25 % 로 거의 그대로이고, 첫 칸만 큰 배열에서는 76 % · 75 % 예요. 첫 칸만 큰 배열은 최적 가르는 자리가
0 에 머물러 하한이 올라가지 않기 때문입니다. 위쪽까지 자르려면 **뒤 칸의 최적 가르는 자리**를 먼저 알아야
하는데, 왼쪽부터 채우는 차례에서는 뒤 칸이 늘 나중이에요. 그래서 차례를 바꿔 **가운데 칸을 먼저** 채웁니다. 그
칸의 최적 가르는 자리가 왼쪽 절반에는 상한을, 오른쪽 절반에는 하한을 한꺼번에 줍니다. 위 표의 마지막 열이 그
방법이고, 과제 규모에서 세면 이렇습니다.

<!--proof:origin-scale-->

| 방법 | 후보 수 | 출처 | 시간(초당 1 억 개) |
| --- | ---: | --- | ---: |
| 가르는 자리 전부 계산 | 3,996,001,000 | 어림 — (k−1)·n(n−1)/2 | 40 초 |
| 가운데 칸부터 채우기 | 35,883,450 | 센 값 | 0.36 초 |

a = [1, 2, …, 2,000] 을 k = 2,000 구역으로 나눈 값입니다. 두 수의 비는 111 배입니다.

<!--/proof-->

지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **분할 정복 최적화**입니다. DP 테이블의 줄을 하나씩 채우되, 줄 안에서는 칸 범위의
가운데 칸을 먼저 채우고 그 칸의 최적 가르는 자리로 양옆 칸들의 후보 범위를 잘라 넘겨요. 후보 범위를 어떻게
적는지, 가운데 칸의 후보는 어디까지인지, 재귀가 언제 멈추는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 분할 정복 최적화

이 아이디어를 한 문장으로 줄이면 이렇습니다. **DP 테이블의 줄마다, 칸 범위의 가운데 칸을 넘겨받은 후보 범위
안에서 채우고, 그 칸의 최적 가르는 자리를 왼쪽 절반의 상한과 오른쪽 절반의 하한으로 넘겨 양옆을 같은 방법으로
채웁니다.** 이 방법이 기대는 것은 최적 가르는 자리라는 값인데, 그 값이 입력의 어디를 가르고 왜 칸을 따라 뒤로만
가는지가 처음 보는 사람에게는 낯설어요. 그래서 최적 가르는 자리를 먼저 따로 설명하고, 그다음 실현하는 순서대로
네 단계를 설명합니다.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 칸마다 | 1단계 후보 범위 안에서 칸 채우기 | 넘겨받은 범위의 가르는 자리만 넣어 가장 작은 값과 그 자리를 적는다 | — |
| 호출마다 | 2단계 가운데 칸 먼저 채우기 | 칸 범위의 가운데 칸을 1단계로 채운다 | 1단계의 채우는 법 |
| 호출마다 | 3단계 좌우로 후보 범위 넘기기 | 찾은 자리를 왼쪽의 상한 · 오른쪽의 하한으로 넘겨 양옆을 채운다 | 2단계가 찾은 자리 |
| 줄마다 | 4단계 줄 되풀이하기 | 다 채운 줄을 이전 줄로 삼아 다음 줄을 채운다 | 3단계가 채운 줄 |

#### 먼저 알아 둘 개념 — 최적 가르는 자리

최적 가르는 자리는 **칸 `dp[g][i]` 의 값을 만든 마지막 구역이 어디서 시작하는지를 그 바로 앞 칸 번호로 적은
것**입니다. 식으로는 `dp[g−1][j] + cost[j+1][i]` 를 가장 작게 만드는 `j` 가운데 가장 작은 것이 `opt(g, i)`
예요. 그러면 칸 `dp[g][i]` 는 앞 구역들 `[0, opt(g, i)]` 와 마지막 구역 `[opt(g, i)+1, i]` 로 갈라집니다.

##### 입력 위의 최적 가르는 자리

`a = [1, 2, …, 8]` 을 세 구역까지 나눌 때, 칸마다 최적 가르는 자리가 정하는 **마지막 구역**을 입력 줄 위에
막대로 그렸습니다. 막대 하나가 칸 하나이고, 막대가 덮은 자리가 그 칸의 마지막 구역이에요.

<!--fig:build-opt-bars-->
![a = [1, 2, …, 8] 의 최적 가르는 자리 — 막대가 칸 i 의 마지막 구역 [opt + 1, i]](./figs/build-opt-bars.svg)

줄 2 의 칸들을 표로 옮기면 이렇습니다.

<!--proof:build-opt-cells-->

| 칸 i | opt(2, i) | 앞 구역 | 마지막 구역 | dp[2][i] |
| --- | --- | --- | --- | ---: |
| 0 | 없음 | — | — | INF |
| 1 | 0 | [0,0] | [1,1] | 5 |
| 2 | 1 | [0,1] | [2,2] | 18 |
| 3 | 2 | [0,2] | [3,3] | 52 |
| 4 | 2 | [0,2] | [3,4] | 117 |
| 5 | 3 | [0,3] | [4,5] | 221 |
| 6 | 4 | [0,4] | [5,6] | 394 |
| 7 | 4 | [0,4] | [5,7] | 666 |

막대의 왼쪽 끝이 `opt(2, i) + 1` 이고 오른쪽 끝이 `i` 입니다. 칸이 뒤로 갈수록 막대의 오른쪽 끝이 한 칸씩 뒤로
가고, 왼쪽 끝은 그대로이거나 뒤로 가요. 막대의 왼쪽 끝이 앞으로 되돌아가는 칸은 없습니다.

##### 칸 하나를 읽는 법

칸 `dp[2][5]` 를 골라 읽어 보겠습니다. 가르는 자리 `j` 마다 앞 구역 `[0,j]` 의 값 `dp[1][j]` 와 마지막 구역
`[j+1, 5]` 의 비용을 더합니다.

<!--proof:build-opt-read-->

| 가르는 자리 | dp[1][j] + cost[j+1][5] | 값 | 비교 |
| --- | --- | ---: | --- |
| j = 0 | 1 + 400 | 401 |  |
| j = 1 | 9 + 324 | 333 |  |
| j = 2 | 36 + 225 | 261 |  |
| j = 3 | 100 + 121 | 221 | 가장 작다 |
| j = 4 | 225 + 36 | 261 |  |

dp[2][5] = 221 이고 opt(2, 5) = 3 입니다. 마지막 구역은 [4,5] 이고 앞 구역은 [0,3] 입니다.

<!--/proof-->

칸 하나를 읽는 순서는 늘 같습니다. 이름 `opt(g, i)` 에서 줄 `g` 와 칸 `i` 를 찾고, 그 값 `j` 로 입력을 앞 구역
`[0,j]` 와 마지막 구역 `[j+1, i]` 로 가르면 두 부분의 비용 합이 칸의 값 `dp[g][i]` 가 돼요.

##### 이웃한 칸끼리의 관계

같은 줄의 이웃한 두 칸에서 최적 가르는 자리가 얼마나 달라지는지 세었습니다.

<!--proof:build-opt-neighbors-->

| 줄 | opt(g, i) — i = 0 부터 | 이웃 칸으로 갈 때 늘어난 만큼 |
| --- | --- | --- |
| 줄 2 | 없음 0 1 2 2 3 4 4 | 1 1 0 1 1 0 |
| 줄 3 | 없음 없음 1 2 3 4 5 5 | 1 1 1 1 0 |

이웃한 두 칸 11 쌍 가운데 최적 가르는 자리가 앞으로 되돌아간 쌍은 0 개입니다.

<!--/proof-->

늘어난 만큼이 0 이나 1 뿐이고 음수가 없습니다. **같은 줄에서 칸 `i₁ < i₂` 이면 `opt(g, i₁) ≤ opt(g, i₂)`** 이고,
이 방법이 쓰는 성질은 이것 하나예요. 위아래 줄 사이에도 `opt(2, i) ≤ opt(3, i)` 가 보이지만 이 방법은 그 관계를
쓰지 않습니다. 그 관계까지 쓰는 다른 설계는 파트 2 의 「경쟁 설계와의 대조」에서 봅니다.

##### 값이 커지는 것과의 차이

최적 가르는 자리를 처음 보면 「칸의 값 `dp[g][i]` 가 칸을 따라 커지니 자리도 뒤로 간다」로 읽기 쉽습니다. 두 비용
행렬에서 값과 자리를 나란히 놓았어요. 둘째 행렬은 구간이 넓을수록 비용이 줄지 않는 4 × 4 행렬입니다.

<!--proof:build-opt-contrast-->

| 비용 행렬 | dp[2][i] | 값 | opt(2, i) | 자리 |
| --- | --- | --- | --- | --- |
| a = [1, 2, 3, 4, 5, 6, 7, 8] 의 제곱 비용 | INF 5 18 52 117 221 394 666 | 줄지 않는다 | 없음 0 1 2 2 3 4 4 | 줄지 않는다 |
| 사각 부등식이 깨지는 행렬 | INF 4 5 8 | 줄지 않는다 | 없음 0 1 0 | 되돌아간다 |

두 행렬 모두 `dp[2][i]` 는 칸을 따라 줄지 않습니다. 그런데 둘째 행렬은 최적 가르는 자리가 1 에서 0 으로 되돌아가요.
**값이 줄지 않는다는 것은 자리가 뒤로만 간다는 근거가 아닙니다.** 이 방법이 쓰는 것은 값이 아니라 자리이고,
자리의 성질은 비용 행렬이 따로 보장해야 합니다.

##### 최적 가르는 자리가 이 방법에 쓰이는 까닭

칸의 값은 다른 칸의 후보 범위에 대해 아무것도 말해 주지 않습니다. 최적 가르는 자리는 다릅니다. 칸 `m` 의 최적
가르는 자리가 `p` 이면, 자리가 뒤로만 가므로 `m` 보다 앞의 칸은 `p` 보다 뒤의 가르는 자리를 답으로 가질 수 없고
`m` 보다 뒤의 칸은 `p` 보다 앞을 가질 수 없어요. 칸 하나에서 얻은 자리 하나가 **양쪽 칸들의 후보를 한꺼번에**
자르는 것이 이 성질에서 나옵니다. 그래서 값이 아니라 자리를 적어 두어야 합니다.

```text
칸 m 의 최적 가르는 자리가 p 일 때

  칸 m 보다 왼쪽      가르는 자리를 p 까지만 넣는다   (상한이 p)
  칸 m               p
  칸 m 보다 오른쪽    가르는 자리를 p 부터만 넣는다   (하한이 p)
```

#### 1단계 — 후보 범위 안에서 칸 하나 채우기

칸 하나를 채울 때 가르는 자리를 전부가 아니라 **넘겨받은 범위 `[optLo, optHi]` 안에서만** 넣습니다. 범위 안에 그
칸의 최적 가르는 자리가 들어 있으면, 범위 안의 가장 작은 값이 곧 칸의 값이에요. 범위 밖의 후보는 최적 가르는
자리보다 작은 값을 낼 수 없으니까요. 칸 `dp[2][5]` 를 네 범위로 채워 보았습니다.

<!--proof:build-range-cell-->

| 후보 범위 | 가르는 자리 | 후보 수 | 칸의 값 | 찾은 자리 |
| --- | --- | ---: | ---: | ---: |
| 전부 | [0,4] | 5 | 221 | 3 |
| opt(2, 4) = 2 부터 | [2,4] | 3 | 221 | 3 |
| opt(2, 6) = 4 까지 | [0,4] | 5 | 221 | 3 |
| 두 칸 사이 | [2,4] | 3 | 221 | 3 |

네 범위 모두 칸의 값 221 과 찾은 자리 3 이 같고, 후보 수만 5 개와 3 개로 갈립니다. 이웃 칸의 최적 가르는 자리
`opt(2, 4)` 와 `opt(2, 6)` 을 범위의 양 끝으로 쓰면 3 개만 넣으면 돼요. 이 단계는 값과 함께 **찾은 자리도
적습니다** — 다음 단계들이 그 자리를 이웃 칸의 범위로 넘기기 때문입니다.

#### 2단계 — 가운데 칸 먼저 채우기

한 호출은 칸 범위 `[lo, hi]` 와 후보 범위 `[optLo, optHi]` 를 넘겨받아 `solve(lo, hi, optLo, optHi)` 로 적습니다.
그 가운데 칸 `mid = (lo + hi) >> 1` 을 1단계로 채우는데, 가르는 자리는 `mid` 보다 앞이어야 하므로 — 마지막 구역
`[j+1, mid]` 가 비지 않으려면 `j ≤ mid − 1` — 후보 상한을 `min(optHi, mid − 1)` 로 한 번 더 자릅니다.
`a = [1, 2, …, 8]` 의 줄 2 를 채우는 첫 호출입니다.

<!--proof:build-first-call-->

solve(0, 7, 0, 6) 의 가운데 칸은 3 입니다. 후보 범위의 하한은 넘겨받은 0, 상한은 min(6, 2) = 2 라 후보 범위가 [0,2] 입니다.

| 가르는 자리 | dp[1][j] + cost[j+1][3] | 최솟값과의 비교 |
| --- | ---: | --- |
| j = 0 | 82 | 82 < INF 참 |
| j = 1 | 58 | 58 < 82 참 |
| j = 2 | 52 | 52 < 58 참 |

칸 3 의 값은 52, 찾은 자리는 2 입니다. 왼쪽 칸 [0,2] 는 후보를 [0,2] 로, 오른쪽 칸 [4,7] 은 [2,6] 으로 넘겨받습니다.

<!--/proof-->

첫 호출은 칸 전부 `[0, n−1]` 과 가르는 자리 전부 `[0, n−2]` 를 넘겨받습니다. `n − 2` 가 상한인 것은 마지막 칸
`n − 1` 의 마지막 구역이 비지 않으려면 `j + 1 ≤ n − 1` 이어야 하기 때문이에요. 가운데 칸 하나를 채우는 데
후보가 셋 들었고, 그 결과로 나머지 일곱 칸이 두 무리로 갈렸습니다.

#### 3단계 — 좌우로 후보 범위 넘기기

가운데 칸 `mid` 의 찾은 자리를 `bestOpt` 라 하면, 왼쪽 칸 `[lo, mid−1]` 은 후보 범위 `[optLo, bestOpt]` 로, 오른쪽
칸 `[mid+1, hi]` 는 `[bestOpt, optHi]` 로 같은 일을 되풀이합니다. 칸 범위가 비면(`lo > hi`) 채울 칸이 없으니 곧장
돌아오고, 그것이 재귀가 멈추는 유일한 자리예요. `a = [1, 2, …, 16]` 의 줄 2 하나를 채우는 호출을 깊이마다 묶고,
호출이 넣는 후보 범위를 막대로 그렸습니다.

<!--fig:build-recursion-->
![a = [1, 2, …, 16] 의 줄 2 — 깊이마다 호출이 넣는 후보 범위(가르는 자리 j)](./figs/build-recursion.svg)

같은 호출을 부른 차례대로 적으면 이렇습니다.

<!--proof:build-recursion-->

| 깊이 | 호출 | 가운데 칸 | 후보 범위 | 후보 수 | 찾은 자리 |
| ---: | --- | ---: | --- | ---: | ---: |
| 0 | solve(0, 15, 0, 14) | 7 | [0,6] | 7 | 4 |
| 1 | solve(0, 6, 0, 4) | 3 | [0,2] | 3 | 2 |
| 2 | solve(0, 2, 0, 2) | 1 | [0,0] | 1 | 0 |
| 3 | solve(0, 0, 0, 0) | 0 | 없음 | 0 | 0 |
| 3 | solve(2, 2, 0, 2) | 2 | [0,1] | 2 | 1 |
| 2 | solve(4, 6, 2, 4) | 5 | [2,4] | 3 | 3 |
| 3 | solve(4, 4, 2, 3) | 4 | [2,3] | 2 | 2 |
| 3 | solve(6, 6, 3, 4) | 6 | [3,4] | 2 | 4 |
| 1 | solve(8, 15, 4, 14) | 11 | [4,10] | 7 | 7 |
| 2 | solve(8, 10, 4, 7) | 9 | [4,7] | 4 | 6 |
| 3 | solve(8, 8, 4, 6) | 8 | [4,6] | 3 | 5 |
| 3 | solve(10, 10, 6, 7) | 10 | [6,7] | 2 | 7 |
| 2 | solve(12, 15, 7, 14) | 13 | [7,12] | 6 | 9 |
| 3 | solve(12, 12, 7, 9) | 12 | [7,9] | 3 | 8 |

a = [1, 2, …, 16] 의 줄 2 입니다. 후보 수 합계는 56 이고, 빈 범위로 곧장 돌아온 호출이 17 번입니다. 같은 줄을 전부 계산하면 120 개입니다.

<!--/proof-->

같은 깊이의 막대들은 서로 **많아야 끝점 하나만** 겹칩니다. 왼쪽 절반의 상한과 오른쪽 절반의 하한이 같은
`bestOpt` 이기 때문이에요. 그래서 깊이마다 후보 수를 더하면 칸 수 16 언저리에 머뭅니다.

<!--proof:build-depth-->

| 깊이 | 호출 수 | 후보 수 합 |
| ---: | ---: | ---: |
| 0 | 1 | 7 |
| 1 | 2 | 10 |
| 2 | 4 | 14 |
| 3 | 8 | 19 |
| 4 | 1 | 6 |

깊이는 칸 범위가 반씩 줄어드는 만큼만 생기므로 `log₂ n` 언저리이고, 깊이마다 후보가 `n` 언저리이니 줄 하나가
`n log n` 언저리예요. 이 규모에서는 전부 계산하는 120 개에 대해 56 개입니다. 깊이마다의 합이 넘지 않는 값과
줄 하나의 상한은 파트 2 의 「수식 정의와 유도」에서 식으로 닫습니다.

#### 4단계 — 줄 되풀이하기

줄 `g` 의 칸을 채울 때 읽는 것은 줄 `g − 1` 뿐입니다. 그래서 DP 테이블 전체를 들고 있지 않고 **이전 줄 `prev` 와
이번 줄 `cur` 두 줄**만 둡니다. 줄 1 은 구역이 하나라 `dp[1][i] = cost[0][i]` 이고, 줄 2 부터 `k` 까지 3단계로
이번 줄을 다 채운 뒤 그 줄을 이전 줄로 삼아요. `a = [1, 2, …, 8]` 을 세 구역으로 나누었습니다.

<!--proof:build-layers-->

| 채운 줄 | 읽은 줄 | 값 | 후보 수 |
| --- | --- | --- | ---: |
| 줄 1 | cost[0][i] 를 옮긴다 | 1 9 36 100 225 441 784 1,296 | 0 |
| 줄 2 | 줄 1 | INF 5 18 52 117 221 394 666 | 17 |
| 줄 3 | 줄 2 | INF INF 14 34 77 153 270 446 | 15 |

돌려주는 값은 줄 3 의 마지막 칸 446 이고, 정본도 446 을 돌려줍니다.

<!--/proof-->

줄마다 새 배열 `cur` 를 만드는 것이 중요합니다. 이번 줄을 채우는 동안 이전 줄의 값이 바뀌면 후보 값이 이전 줄이
아닌 값으로 만들어지기 때문이에요. 그 자리를 망가뜨리면 무엇이 되는지는 전개의 「짚고 가기」에서 봅니다.

#### 이 방법이 기대는 전제

분할 정복 최적화는 **같은 줄에서 최적 가르는 자리가 칸을 따라 줄지 않는다**는 전제 위에서만 맞습니다. 그 전제는
비용 행렬이 사각 부등식을 만족하면 성립하고(유도는 파트 2 의 「수식 정의와 유도」), 이 글이 쓰는 비용 행렬들이
실제로 그런지 지표 넷의 조합을 전부 확인했습니다.

<!--proof:build-premise-quad-->

| 비용 행렬 | 확인한 지표 조합 | 어긴 조합 | 첫 위반 (a, b, c, d) |
| --- | ---: | ---: | --- |
| 전개 입력 (n = 4) | 35 | 0 | — |
| a = [1, 2, …, 8] (n = 8) | 330 | 0 | — |
| a = [1, 2, …, 16] (n = 16) | 3,876 | 0 | — |
| 첫 칸만 큰 배열 (n = 9) | 495 | 0 | — |
| 사각 부등식이 깨지는 행렬 (n = 4) | 35 | 2 | 0, 2, 2, 3 |

앞의 넷은 어긴 조합이 없습니다. 이 글이 확인한 것은 이 행렬들뿐이고, 구간 합의 제곱이 언제나 사각 부등식을
만족한다는 일반 증명은 하지 않았어요. 마지막 행렬은 「값이 커지는 것과의 차이」에서 쓴 행렬입니다. 그 행렬에
분할 정복 최적화를 실행하면 이렇게 나옵니다.

<!--proof:build-premise-break-->

opt(2, i) 는 i = 0 부터 없음 0 1 0 입니다. 칸 3 을 채우는 호출 solve(3, 3, 1, 2) 의 후보 범위는 [1,2] 입니다.

| 가르는 자리 | dp[1][j] + cost[j+1][3] | 값 | 분할 정복 최적화 |
| --- | --- | ---: | --- |
| j = 0 | 0 + 8 | 8 | 범위 밖 |
| j = 1 | 4 + 7 | 11 | 넣는다 |
| j = 2 | 8 + 7 | 15 | 넣는다 |

가장 작은 값은 8 인데 분할 정복 최적화는 11 을 돌려줍니다. 지표 조합 35 개 가운데 사각 부등식을 어긴 것이 2 개이고, 첫 조합 (0, 2, 2, 3) 에서는 cost[0][2] + cost[2][3] = 8 + 7 = 15 가 cost[0][3] + cost[2][2] = 9 + 1 = 10 보다 큽니다.

<!--/proof-->

칸 2 의 최적 가르는 자리가 1 이라 오른쪽 칸 3 은 하한 1 을 넘겨받았는데, 칸 3 의 진짜 최적 가르는 자리는 0
이었어요. 가장 작은 값을 내는 후보가 범위 밖으로 나가 이 절차는 틀린 답을 냅니다. 이 행렬은 구간이 넓을수록
비용이 줄지 않고 `dp[2][i]` 도 칸을 따라 줄지 않는, 겉으로는 멀쩡해 보이는 행렬이에요. **비용 행렬이 자연스러워
보이는 것으로는 부족하고, 사각 부등식을 확인하거나 보장받아야 합니다.** 전제가 없으면 가르는 자리를 전부 계산하는
쪽으로 가야 합니다.

#### 가운데 칸을 먼저 채우는 까닭

2단계는 칸 범위의 **가운데**를 먼저 채웁니다. 먼저 채울 칸을 왼쪽 끝 · 4 분의 1 자리 · 가운데 셋으로 바꿔 같은
입력을 채워 보았어요. 나머지 절차는 그대로입니다.

<!--proof:build-pivot-->

| 입력 | n | 왼쪽 끝 · 후보 수 · 재귀 깊이 | 4 분의 1 자리 · 후보 수 · 재귀 깊이 | 가운데 · 후보 수 · 재귀 깊이 |
| --- | ---: | --- | --- | --- |
| a = [1, 2, …, n] | 64 | 1,105 · 깊이 64 | 764 · 깊이 13 | 727 · 깊이 7 |
| a = [1, 2, …, n] | 256 | 16,124 · 깊이 256 | 4,553 · 깊이 17 | 4,021 · 깊이 9 |
| 첫 칸만 큰 배열 | 64 | 3,071 · 깊이 64 | 1,187 · 깊이 13 | 833 · 깊이 7 |
| 첫 칸만 큰 배열 | 256 | 49,151 · 깊이 256 | 6,687 · 깊이 17 | 4,439 · 깊이 9 |

셋 다 k = 3 이고 답은 정본과 같습니다. 첫 칸만 큰 배열에서 n = 256 일 때 왼쪽 끝부터 채우는 판의 후보 수는 49,151, 하한만 옮기는 방법은 49,151 입니다.

<!--/proof-->

**왼쪽 끝부터 채우는 판은 하한만 옮기는 방법과 같은 일을 합니다.** 왼쪽 끝 칸을 채우면 왼쪽 절반이 비어 상한을
넘겨받을 칸이 없고, 오른쪽에 하한만 넘어가기 때문이에요. 후보 수가 하한만 옮기는 방법과 같고 재귀 깊이가 칸
수만큼 됩니다. 4 분의 1 자리는 가운데보다 후보가 많고 깊이도 깊어요. 칸 범위가 한쪽으로 치우치면 긴 쪽이 다시
갈라질 때까지 깊이가 늘기 때문입니다. 가운데를 고르면 양쪽 칸 범위가 반씩이라 깊이가 `log₂ n` 언저리에 머물고,
잰 두 입력 모두에서 후보가 가장 적었습니다.

#### 네 단계를 이은 절차

네 단계를 코드의 차례로 다시 적으면 이렇습니다. 칸과 구역이 2,000 개씩일 때 어림으로 40 초이던 계산이 0.36 초가
돼요.

1. 줄 1 을 `dp[1][i] = cost[0][i]` 로 채운다
2. 줄 `g = 2 … k` 마다 새 배열 `cur` 를 만들고 `solve(0, n−1, 0, n−2)` 를 부른다
3. `solve(lo, hi, optLo, optHi)` 는 `lo > hi` 이면 돌아오고, 아니면 가운데 칸 `mid` 를 후보 범위
   `[optLo, min(optHi, mid−1)]` 에서 채워 가장 작은 값과 그 자리 `bestOpt` 를 적는다
4. 왼쪽 `solve(lo, mid−1, optLo, bestOpt)` 와 오른쪽 `solve(mid+1, hi, bestOpt, optHi)` 를 부른다
5. 줄을 다 채우면 `prev = cur` 로 이전 줄을 바꾸고, 마지막에 `prev[n−1]` 을 돌려준다

### 수행으로 알아보는 알고리즘 — 네 칸을 세 구역으로 나누는 열두 걸음

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력을 끝까지 고정해 두고, 조각마다 그 조각만
실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const a = [1, 2, 3, 4];
const cost = buildCost(a); // cost[i][j] = (a[i] + … + a[j])^2
const k = 3;
// 이 절이 끝나면 34 가 나와야 한다
```

이 입력을 고른 까닭은 갈래 일곱을 모두 실행하게 하려는 것입니다. `k = 3` 이라 줄 교체가 실제로 두 번 일어나고,
`mid = 0` 인 호출이 나와 후보가 하나도 없는 칸이 생기며, 줄 3 에서 `INF` 를 후보로 읽는 자리까지 나와요.

```text
prev ← 줄 1 = cost[0][0 … n−1]                                   ① 줄 1
g = 2 부터 k 까지:
    cur ← INF 로 채운 새 배열                                    ② 이번 줄의 배열
    solve(0, n−1, 0, n−2)
        lo > hi 이면 돌아온다                                    ③ 빈 범위
        mid ← (lo + hi) 의 절반을 내림
        upper ← min(optHi, mid − 1)                              ④ 후보 상한
        j = optLo … upper 마다 prev[j] + cost[j+1][mid] 를 만들고
            지금까지보다 작으면 값과 자리 bestOpt 를 고친다        ⑤ 최솟값 갱신
        cur[mid] ← 가장 작은 값
        solve(lo, mid−1, optLo, bestOpt) · solve(mid+1, hi, bestOpt, optHi)   ⑥ 좌우 재귀
    prev ← cur                                                   ⑦ 줄 교체
prev[n−1] 을 돌려준다
```

#### 1. 줄 1 을 채운다

첫 조각은 준비입니다. 구역이 하나뿐인 줄은 고를 것이 없어요 — `[0,i]` 를 통째로 한 구역으로 묶는 수밖에 없으니
`dp[1][i]` 가 `cost[0][i]` 그대로입니다.

```ts
const n = cost.length;

// ① 줄 1 — 구역이 하나뿐이면 [0,i] 를 통째로 묶는 것 말고 선택이 없다.
const base = cost[0] as number[];
let prev: number[] = new Array<number>(n).fill(INF);
for (let i = 0; i < n; i++) prev[i] = base[i] as number;
```

실행하면 이렇게 나옵니다.

<!--proof:walk-base-->

| T1 뒤의 줄 | 값 | 뜻 |
| --- | --- | --- |
| prev | 1 9 36 100 | dp[1][0] … dp[1][3] |
| a | 1 2 3 4 | prev[3] = (1 + 2 + 3 + 4)² = 100 |

#### 2. 가운데 칸 하나를 채운다

둘째 조각이 본체입니다. 칸 범위 `[lo, hi]` 의 가운데 칸 `mid` 를 후보 범위 안에서 채우고, 가장 작은 값과 그 값을
만든 자리를 함께 적어요.

```ts
// ③ 빈 범위 — 채울 칸이 없으면 여기서 끝낸다. 재귀의 유일한 종료 조건이다.
if (lo > hi) return;
const mid = (lo + hi) >> 1;
let bestCost = INF;
let bestOpt = optLo;
// ④ 후보 상한 — 가르는 자리는 mid 보다 앞이어야 하므로 mid - 1 로 자른다.
const upper = Math.min(optHi, mid - 1);
for (let j = optLo; j <= upper; j++) {
  const row = cost[j + 1] as number[];
  const val = (prev[j] as number) + (row[mid] as number);
  // ⑤ 최솟값 갱신 — 값과 그 값을 만든 가르는 자리를 함께 적는다.
  if (val < bestCost) {
    bestCost = val;
    bestOpt = j;
  }
}
cur[mid] = bestCost;
```

줄 2 의 첫 호출만 실행하면 이렇게 나옵니다.

<!--proof:walk-first-->

```text
T2 — solve(0, 3, 0, 2)
  가운데 칸  mid = (0 + 3) >> 1 = 1
  후보 상한  min(2, 0) = 0
  후보 범위  [0,0]
  j = 0      prev[0] + cost[1][1] = 5

  cur[1] = 5 · bestOpt = 0
```

#### 짚고 가기 — 후보 상한을 mid − 1 로 자르지 않아도 전개 입력의 답은 안 틀린다

여기서 헷갈리기 쉬운 포인트는 `Math.min(optHi, mid - 1)` 의 `mid - 1` 입니다. 「`optHi` 가 이미 범위를 좁혀 두었는데
왜 한 번 더 자르나」로 읽기 쉬워요. 그 자르기를 빼고 세 입력에 실행했습니다.

```ts
const upper = optHi; // ← 원래는 Math.min(optHi, mid - 1)
```

<!--proof:pause-cap-->

| 입력 | k | 정본 | 상한을 안 자른 판 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 | 3 | 34 | 34 | 같다 |
| 값이 모두 같은 배열 | 3 | 9 | 9 | 같다 |
| 다른 비용 행렬 | 2 | 3 | 12 | 다르다 |

**전개 입력에서는 답이 안 틀립니다.** 그래서 이 자리를 빼먹은 채로 전개 입력만 시험하면 통과해요. 그런데 셋째 줄의
다른 비용 행렬에서 3 이 12 가 됩니다. 답이 안 틀리는 것은 입력의 성질이지 그 자르기가 없어도 된다는 뜻이 아니에요.
전개 입력에서도 DP 테이블은 이미 갈려 있습니다.

<!--proof:pause-cap-rows-->

| 줄 | 정본 | 상한을 안 자른 사본 |
| --- | --- | --- |
| 줄 1 | 1 9 36 100 | 1 9 36 100 |
| 줄 2 | INF 5 18 52 | 1 5 18 52 |
| 줄 3 | INF INF 14 34 | 1 5 14 34 |

`dp[2][0]` 은 칸 하나를 두 구역으로 나눌 수 없어 `INF` 여야 하는데 상한을 안 자른 사본은 1 을 적습니다. `mid = 0` 인
호출이 `j = 0` 을 넣어 `cost[1][0]` 을 읽기 때문이에요. 그 칸은 `j + 1 > mid` 라 구간이 아닌 자리이고, 이 글의 비용
행렬이 그 자리를 0 으로 채워 두어서 「없는 구간을 0 에 묶는다」가 후보가 됩니다. 셋째 줄의 행렬에서는 그 가짜
후보가 답까지 바꿉니다.

<!--proof:pause-cap-trace-->

정본의 호출입니다.

| 호출 | 가운데 칸 | 후보 범위 | 후보 값 | 채운 값 | 찾은 자리 |
| --- | ---: | --- | --- | --- | --- |
| solve(0, 3, 0, 2) | 1 | [0,0] | j=0: 14 | 14 | 0 |
| solve(0, 0, 0, 0) | 0 | 없음 | 없음 | INF | — |
| solve(2, 3, 0, 2) | 2 | [0,1] | j=0: 11 · j=1: 12 | 11 | 0 |
| solve(3, 3, 0, 2) | 3 | [0,2] | j=0: 13 · j=1: 3 · j=2: 12 | 3 | 1 |

상한을 안 자른 사본의 호출입니다.

| 호출 | 가운데 칸 | 후보 범위 | 후보 값 | 채운 값 | 찾은 자리 |
| --- | ---: | --- | --- | --- | --- |
| solve(0, 3, 0, 2) | 1 | [0,2] | j=0: 14 · j=1: 3 · j=2: 1 | 1 | 2 |
| solve(0, 0, 0, 2) | 0 | [0,2] | j=0: 5 · j=1: 3 · j=2: 1 | 1 | 2 |
| solve(2, 3, 2, 2) | 2 | [2,2] | j=2: 1 | 1 | 2 |
| solve(3, 3, 2, 2) | 3 | [2,2] | j=2: 12 | 12 | 2 |

<!--/proof-->

**갈리는 자리는 칸 1 을 채우는 첫 호출입니다.** 정본은 후보가 `[0,0]` 이라 `j = 0` 하나만 넣는데, 상한을 안 자른
사본은 `j = 2` 까지 넣고 `cost[3][1] = 0` 을 읽어 1 을 만들어요. 그 1 이 가장 작은 값이 되면서 찾은 자리가 2 로
올라가고, 오른쪽 호출이 하한 2 를 넘겨받아 칸 3 에서 진짜 답을 내는 `j = 1` 을 넣지 못합니다. 구간이 아닌 칸 하나가
후보로 들어와 찾은 자리를 뒤로 옮기고, 그 자리가 뒤 칸들의 범위를 잘못 자르는 거예요.

#### 3. 좌우로 재귀하며 후보 범위를 넘긴다

셋째 조각이 후보 범위를 넘기는 자리입니다. 가운데 칸의 찾은 자리 `bestOpt` 를 왼쪽에는 상한으로, 오른쪽에는
하한으로 넘겨요.

```ts
// ⑥ 좌우 재귀 — 왼쪽 절반의 후보 상한과 오른쪽 절반의 후보 하한이 둘 다 bestOpt 다.
solve(lo, mid - 1, optLo, bestOpt);
solve(mid + 1, hi, bestOpt, optHi);
```

여기서 가장 중요한 줄은 둘째 줄의 `bestOpt` 입니다. 오른쪽 호출이 `optLo` 대신 `bestOpt` 를 하한으로 받는 것이
하한을 자르는 자리의 전부예요. 줄 2 의 오른쪽 절반을 실행하면 이렇게 나옵니다.

<!--proof:walk-right-->

```text
T4  solve(2, 3, 0, 2)   mid = 2   상한 min(2, 1) = 1   후보 [0,1]
      j = 0   prev[0] + cost[1][2] = 26
      j = 1   prev[1] + cost[2][2] = 18
      cur[2] = 18 · bestOpt = 1
T5  solve(3, 3, 1, 2)   mid = 3   상한 min(2, 2) = 2   후보 [1,2]
      j = 1   prev[1] + cost[2][3] = 58
      j = 2   prev[2] + cost[3][3] = 52
      cur[3] = 52 · bestOpt = 2

T5 의 하한 1 이 T4 의 bestOpt 다. j = 0 은 넣지 않는다
```

#### 짚고 가기 — 줄 배열을 새로 안 만들면 이번 줄을 이전 줄로 읽는다

여기서 헷갈리기 쉬운 포인트는 `cur` 를 줄마다 새로 만드는 줄입니다. 「어차피 줄이 끝나면 `prev` 를 버리는데 같은
배열을 계속 쓰면 안 되나」로 읽기 쉬워요. 한 배열을 함께 쓰게 해 봅시다.

```ts
for (let g = 2; g <= k; g++) {
  const cur: number[] = prev; // ← 원래는 new Array<number>(n).fill(INF)
```

만들 수 없다」는 표기예요. 답이 있는 입력에서 `INF` 가 나온 것이니, 절차가 방금 적은 값을 이전 줄의 값으로 읽었다는
뜻입니다. 걸음마다 그 배열을 정본의 같은 줄과 나란히 놓았어요.

52 가 아니라 30 으로 적습니다. 줄 3 이 그 배열을 읽으며 칸이 하나씩 `INF` 로 바뀌어요. 「이번 줄을 채우는 동안 이전 줄은 안 바뀐다」가 깨지면 후보 값 자체가 달라져요.

#### 4. 열두 걸음을 끝까지 실행한다

세 조각을 줄 반복으로 감싸면 절차가 완성됩니다. 줄마다 새 배열을 만들고(②), 첫 호출로 칸 전부와 가르는 자리
전부를 넘기고, 줄을 다 채우면 이전 줄을 바꿔요(⑦).

```ts
for (let g = 2; g <= k; g++) {
  // ② 이번 줄의 배열 — 줄마다 새로 만든다. 이전 줄의 값을 고치지 않는다.
  const cur: number[] = new Array<number>(n).fill(INF);
  // … solve 정의 …
  solve(0, n - 1, 0, n - 2);
  // ⑦ 줄 교체 — 다음 줄이 이번 줄을 이전 줄로 읽는다.
  prev = cur;
}
return prev[n - 1] as number;
```

고정 입력에 실행하면 열두 걸음이 나옵니다. T1 이 줄 1, T2 부터 T5 까지가 줄 2 의 비지 않은 호출 넷, T6 이 줄 교체,
T7 부터 T10 까지가 줄 3 의 호출 넷, T11 이 두 번째 줄 교체, T12 가 반환이에요. 무대의 위 세 줄이 DP 테이블이고,
입력 줄 위 괄호가 호출이 맡은 칸 범위, 아래 괄호가 넣는 후보 범위(가르는 자리 `j`)입니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 앞의 조각들을 줄 반복 안에 모은 것이고, 새로 보는 것은 `solve` 를 줄 반복 안에서
정의하는 자리 하나예요. `solve` 가 그 줄의 `cur` 와 `prev` 를 읽어야 하므로 줄마다 새로 정의합니다.

```ts
// 아직 확정하지 않은 칸의 값. 어떤 유한한 비용보다 크다.
export const INF = Number.POSITIVE_INFINITY;

export function divideAndConquerDp(cost: number[][], k: number): number {
  const n = cost.length;

  // ① 줄 1 — 구역이 하나뿐이면 [0,i] 를 통째로 묶는 것 말고 선택이 없다.
  const base = cost[0] as number[];
  let prev: number[] = new Array<number>(n).fill(INF);
  for (let i = 0; i < n; i++) prev[i] = base[i] as number;

  for (let g = 2; g <= k; g++) {
    // ② 이번 줄의 배열 — 줄마다 새로 만든다. 이전 줄의 값을 고치지 않는다.
    const cur: number[] = new Array<number>(n).fill(INF);

    const solve = (
      lo: number,
      hi: number,
      optLo: number,
      optHi: number,
    ): void => {
      // ③ 빈 범위 — 채울 칸이 없으면 여기서 끝낸다. 재귀의 유일한 종료 조건이다.
      if (lo > hi) return;
      const mid = (lo + hi) >> 1;
      let bestCost = INF;
      let bestOpt = optLo;
      // ④ 후보 상한 — 가르는 자리는 mid 보다 앞이어야 하므로 mid - 1 로 자른다.
      const upper = Math.min(optHi, mid - 1);
      for (let j = optLo; j <= upper; j++) {
        const row = cost[j + 1] as number[];
        const val = (prev[j] as number) + (row[mid] as number);
        // ⑤ 최솟값 갱신 — 값과 그 값을 만든 가르는 자리를 함께 적는다.
        if (val < bestCost) {
          bestCost = val;
          bestOpt = j;
        }
      }
      cur[mid] = bestCost;
      // ⑥ 좌우 재귀 — 왼쪽 절반의 후보 상한과 오른쪽 절반의 후보 하한이 둘 다 bestOpt 다.
      solve(lo, mid - 1, optLo, bestOpt);
      solve(mid + 1, hi, bestOpt, optHi);
    };

    solve(0, n - 1, 0, n - 2);
    // ⑦ 줄 교체 — 다음 줄이 이번 줄을 이전 줄로 읽는다.
    prev = cur;
  }

  return prev[n - 1] as number;
}
```

### 알아 두면 좋은 개념 — 완전 단조 행렬

줄 2 를 채울 때 계산한 후보 값을 행렬 하나로 늘어놓아 봅시다. 행이 칸 `i`, 열이 가르는 자리 `j`, 값이
`M[i][j] = dp[1][j] + cost[j+1][i]` 인 행렬이에요. 굵은 칸이 행마다 가장 작은 값의 자리입니다.

<!--fig:related-matrix-->
![줄 2 의 후보 행렬 M[i][j] = dp[1][j] + cost[j+1][i] — 굵은 칸이 행마다의 최솟값](./figs/related-matrix.svg)

행마다의 값을 적으면 이렇습니다.

<!--proof:related-rows-->

| 행 | M[i][j] — j = 0 부터 | 최솟값의 자리 |
| --- | --- | --- |
| i = 0 | 없음 | 없음 |
| i = 1 | 5 | 0 |
| i = 2 | 26 18 | 1 |
| i = 3 | 82 58 52 | 2 |
| i = 4 | 197 153 117 125 | 2 |
| i = 5 | 401 333 261 221 261 | 3 |
| i = 6 | 730 634 520 424 394 490 | 4 |
| i = 7 | 1,226 1,098 936 776 666 666 848 | 4 |

행마다 가장 작은 값의 자리가 0 · 1 · 2 · 2 · 3 · 4 · 4 로 오른쪽으로만 갑니다. 이런 행렬을 **단조 행렬**이라 부르고,
어느 행 둘 · 열 둘을 골라 만든 2 × 2 부분 행렬에서도 그 성질이 성립하면 **완전 단조 행렬**이라 불러요. 이 편에서 그
행렬은 줄 하나의 후보 행렬이고, 행마다 가장 작은 값의 자리가 곧 최적 가르는 자리입니다. 분할 정복 최적화에는
단조 행렬이면 충분합니다. 파트 2 의 「수식 정의와 유도」가 변끼리 더하는 두 부등식이 이 행렬의 2 × 2 조건이라,
사각 부등식을 만족하는 비용에서는 후보 행렬이 완전 단조 행렬이 돼요.

같은 이름이 이 편 밖에서 다시 나옵니다.

| 다시 만나는 자리 | 행과 열 | 가장 작은 값의 자리로 하는 일 |
| --- | --- | --- |
| 크누스 최적화 | 행은 구간 `[i, j]`, 열은 그 구간을 가르는 자리 | 이웃 두 칸의 자리로 범위를 가둔다 |
| SMAWK 행렬 탐색 | 이 편과 같은 행렬 | 완전 단조를 전제로 행마다의 자리를 한꺼번에 고른다 |
| 1 차원 군집 나누기 | 행은 군집의 끝, 열은 그 앞 군집의 끝 | 이 편과 같은 절차로 행마다의 자리를 찾는다 |

크누스 최적화는 이 저장소에도 있어요 — [크누스 최적화](../knuthOptimization/knuthOptimization-guide.md) 편이 그
자리이고, 구간을 가르는 자리를 이웃 칸 둘로 가두는 점만 다릅니다. 이름을 알아 두면 다시 만났을 때 「무엇이 행이고
무엇이 열인가」부터 물을 수 있어요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 최적 가르는 자리의 성질이 어디서 나오는지, 무엇이 매
호출 참으로 남는지, 그리고 후보 수가 얼마인지 차례로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 이어진 구역으로 나눈다 | 구역 경계를 가르는 자리 하나로 적을 수 있다 | 상태가 줄 `g` 와 칸 `i` 둘이다 |
| 구역 수 `k` 가 정해져 있다 | DP 테이블의 줄 수가 정해진다 | 바깥 반복이 `g = 2 … k` 다 |
| 비용이 사각 부등식을 만족한다 | 같은 줄에서 최적 가르는 자리가 칸을 따라 줄지 않는다 | `bestOpt` 를 좌우 호출에 넘긴다 |
| 칸 수가 커서 `k n²` 을 감당할 수 없다 | 칸 하나가 후보 `n` 개를 넣으면 예산을 넘는다 | 칸마다 후보 범위를 자른다 |

셋째 조건이 이 절차의 자리이자 위험입니다. 조건이 없으면 가르는 자리를 전부 계산해야 해요. 비용이
`dp[g−1][j] + b[j] · x[i]` 꼴처럼 가르는 자리와 칸이 곱 하나로만 엮이면
[볼록 껍질 트릭](../convexHullTrick/convexHullTrick-guide.md)으로 줄 하나를 `O(n log n)` 이나 그보다 적게 채울 수
있고, 그쪽은 사각 부등식 대신 그 곱 꼴을 전제로 합니다.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "일렬로 늘어선" "연속된" "구간으로 나눈다"   ← 가르는 자리 하나로 경계를 적을 수 있다
  "정확히 k 개의 그룹"                         ← DP 테이블의 줄 수가 정해진다
  "구간 [i, j] 를 묶는 비용"                   ← 비용 행렬이 입력이다
  "비용은 구간 합의 제곱" "구간 안 분산"       ← 사각 부등식을 만족하는 전형이다

점화식에 이런 모양이 보이면
  dp[g][i] = min_j (dp[g−1][j] + cost(j+1, i))   ← 줄 하나가 이전 줄만 읽는다
  opt(g, i) 가 i 를 따라 줄지 않는다             ← 후보 범위를 가운데 칸으로 자를 수 있다

반대로 이런 말이 보이면 해당하지 않는다
  "원소를 골라 담는다" "순서를 바꿔도 된다"    ← 가르는 자리라는 개념이 없다
  "그룹 수에 제한이 없다"                      ← 줄 수를 정할 수 없다
  "비용이 구간마다 제멋대로 주어진다"          ← 사각 부등식을 보장할 수 없다
```

마지막 무리가 보이면 다른 절차로 갑니다. 구간을 나누는 것이 아니라 자르는 자리마다 값이 붙으면
[회문 분할 최소 컷](../../dp/palindromePartitioningMinCut/palindromePartitioningMinCut-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **`Ckmeans.1d.dp` 의 `fill_row_q_log_linear`** — 1 차원 자료를 `k` 개 군집으로 최적 분할하는 CRAN 의 R 패키지가
  이 절차를 그대로 씁니다. 소스 파일 첫 줄 주석이 *"fill_log_linear.cpp --- a divide-and-conquer algorithm to
  compute a row in the dynamic programming matrix in O(n lg n) time."* 이고, 함수 본문이 `int i = (imin + imax) / 2;`
  로 가운데 칸을 잡은 다음 `int jhigh = i - 1; // the upper end for j` 로 후보 상한을 자릅니다 — 이 글의 `mid` 와
  `Math.min(optHi, mid - 1)` 이 같은 자리예요. 좌우 호출에 넘기는 값도 같습니다: 왼쪽 앞에서 `jmax = (int)J[q][i];`,
  오른쪽 앞에서 `jmin = (int)J[q][i];` 입니다.
  ([`Ckmeans.1d.dp/src/fill_log_linear.cpp`](https://github.com/cran/Ckmeans.1d.dp/blob/master/src/fill_log_linear.cpp),
  조회 2026-09-05)
- **`kmeans1d` 의 SMAWK 구현** — 같은 문제를 푸는 파이썬 확장인데, 후보 범위를 반씩 자르는 대신 **다른 탐색
  절차**를 씁니다. 주석이 *"Interface for the SMAWK algorithm, for finding the minimum value in each row of an
  implicitly-defined totally monotone matrix."* 라 적고, 알고리즘의 출처를 *"Algorithm as presented in section 2.2
  of (Gronlund et al., 2017)."* 로 밝혀요. 같은 성질(완전 단조)을 쓰면서 탐색 방법만 갈리는 자리입니다.
  ([`kmeans1d/kmeans1d/_core.cpp`](https://github.com/dstein64/kmeans1d/blob/master/kmeans1d/_core.cpp),
  조회 2026-09-05)

두 구현이 이 글과 갈리는 자리를 나란히 놓으면 이렇습니다.

| 구현 | 행마다 가장 작은 값의 자리를 찾는 법 | 복잡도의 근거 |
| --- | --- | --- |
| 이 글 | 가운데 칸을 채우고 좌우로 재귀한다 | 줄 하나가 `n log n` 언저리라고 이 글이 쟀다 |
| Ckmeans | 같은 절차를 C++ 로 적었다 | 파일 첫 줄 주석이 `O(n lg n)` 이라 적는다 |
| kmeans1d | SMAWK | 소스가 적어 두지 않았다 |

**「분할 정복 최적화가 실무에서 널리 쓰인다」를 1 차 출처로 확인하지 못했습니다.** 확인한 것은 위 두 구현이고, 둘 다
1 차원 군집 문제입니다. SMAWK 가 로그 인자를 없앤다는 것도 이 글이 1 차 출처로 확인하지 못했어요.

#### 경쟁 설계와의 대조

같은 목표(이어진 구역 `k` 개로 나눈 가장 작은 비용)를 같은 전제 아래서 노리는 다른 절차로 **크누스 최적화**가
있습니다. 최적 가르는 자리가 같은 줄에서 칸을 따라 줄지 않을 뿐 아니라 **위아래 줄 사이에서도**
`opt(g−1, i) ≤ opt(g, i)` 라는 것까지 써서, 칸 `i` 의 후보를 `[opt(g−1, i), opt(g, i+1)]` 로 가둬요. 하한은 이전
줄에서, 상한은 같은 줄의 오른쪽 이웃에서 오므로 줄 안에서 칸을 뒤에서부터 채웁니다. 줄 하나의 후보 수는 입력에
따라 크게 갈리지만, 줄을 모두 더하면 대각선마다 합이 이어 붙어 전체가 `n²` 규모에 머물러요.

**입력을 왜 전개 입력으로 안 골랐는지 먼저 적습니다.** 전개는 칸 넷에 구역 셋이라 두 설계의 순서가 갈리는 구역
수를 보일 수 없어요. 그래서 대조는 **과제 규모**에서 합니다 — 칸 `n = 2,000` 을 고정하고 **구역 수 `k` 만**
바꿉니다. 전개 입력의 값은 표의 둘째 열에 남겨요.

```text
a      [1, 2, …, 2,000]                     「아이디어를 떠올리는 과정」이 과제 규모에서 쓴 입력
cost   cost[i][j] = (a[i] + … + a[j])²
k      2 부터 2,000 까지 전부

후보 수   두 설계 모두 가르는 자리 하나를 넣어 값을 만들고 비교한 한 번을 1 로 센다
저장 칸   설계가 새로 잡는 칸 수 — 비용 행렬 n × n 은 입력이라 두 설계 모두 세지 않는다
```

### 수식 정의와 유도

`dp[g][i]` 의 점화식과 `opt(g, i)` 를 정의하고, 그 정의를 전개 입력에 넣어 검산하고, 사각 부등식에서 최적 가르는
자리가 칸을 따라 줄지 않는다는 것을 유도한 뒤, 줄 하나의 후보 수를 임의의 `n` 에서 닫습니다.

**먼저 정의입니다.** 칸 `[0, i]` 를 정확히 `g` 개의 이어진 구역으로 나눈 가장 작은 비용을 $dp[g][i]$, 마지막 구역
바로 앞의 칸을 $j$ 라 씁니다. 마지막 구역은 $[j+1, i]$ 이고 그 앞은 $[0, j]$ 를 $g-1$ 개로 나눈 것이에요.

$$
dp[1][i] = cost[0][i], \qquad dp[g][i] = \min_{g-2 \le j < i} \bigl( dp[g-1][j] + cost[j+1][i] \bigr)
$$

```text
점화식이 자르는 자리

  0 ─────────────── j │ j+1 ─────── i
  └─ g−1 개 구역으로 ─┘ │ └ 마지막 구역 ┘
      dp[g−1][j]            cost[j+1][i]

  j 의 아래 끝이 g−2 인 것은 앞을 g−1 개로 나누려면 칸이 g−1 개는 있어야 하기 때문이다
```

그 최솟값을 만드는 $j$ 가운데 가장 작은 것이 $\operatorname{opt}(g, i)$ 입니다.

$$
\operatorname{opt}(g, i) \;=\; \min \Bigl\{\, j \;:\; dp[g-1][j] + cost[j+1][i] = dp[g][i] \,\Bigr\}
$$

**정의를 값에 넣어 검산해 봅시다.** 전개 입력의 칸 하나입니다.

<!--proof:math-check-->

```text
정의를 전개 입력의 칸 하나에 넣는다 — dp[2][3]

  j = 0   dp[1][0] + cost[1][3] = 1 + 81 = 82
  j = 1   dp[1][1] + cost[2][3] = 9 + 49 = 58
  j = 2   dp[1][2] + cost[3][3] = 36 + 16 = 52   ← 최솟값

  dp[2][3] = 52 고 opt(2, 3) = 2 다
```

두 정의로 DP 테이블 전체를 만들어, 후보 범위를 자른 절차와 가르는 자리를 전부 계산한 절차가 같은 값을 내는지
확인했습니다.

<!--proof:math-table-->

| 줄 | 분할 정복 최적화 | 가르는 자리 전부 계산 | 판정 |
| --- | --- | --- | --- |
| dp[1] | 1 9 36 100 | 1 9 36 100 | 같다 |
| dp[2] | INF 5 18 52 | INF 5 18 52 | 같다 |
| dp[3] | INF INF 14 34 | INF INF 14 34 | 같다 |

줄마다의 후보 수는 줄 2: 5 · 줄 3: 5 로 합계 10 이고, 전부 계산하면 12 입니다.

**첫째 유도는 최적 가르는 자리의 성질입니다.** 사각 부등식은 $a \le b \le c \le d$ 인 지표 넷에 대한 조건이에요.

$$
cost[a][c] + cost[b][d] \;\le\; cost[a][d] + cost[b][c]
$$

```text
지표 넷이 만드는 구간 넷

  a ──── b ──── c ──── d

  왼쪽 항    cost[a][c] + cost[b][d]   두 구간이 겹치되 어느 쪽도 다른 쪽을 품지 않는다
  오른쪽 항  cost[a][d] + cost[b][c]   한쪽이 다른 쪽을 통째로 품는다
```

$j_1 < j_2$ 이고 $i_1 < i_2$ 라 두고, 칸 $i_1$ 에서 뒤쪽 가르는 자리 $j_2$ 가 앞쪽 $j_1$ 보다 **작은** 값을
만들었다고 합시다.

$$
dp[g-1][j_2] + cost[j_2+1][i_1] \;<\; dp[g-1][j_1] + cost[j_1+1][i_1]
$$

$j_1 + 1 \le j_2 + 1 \le i_1 \le i_2$ 이므로 사각 부등식의 네 자리에 이 지표들을 넣을 수 있어요.

```text
지표의 차례               j1+1  ≤  j2+1  ≤  i1  ≤  i2
사각 부등식에 넣는 자리   a        b        c      d
```

$$
cost[j_1+1][i_1] + cost[j_2+1][i_2] \;\le\; cost[j_1+1][i_2] + cost[j_2+1][i_1]
$$

두 부등식을 변끼리 더하면 양변에 $cost[j_1+1][i_1] + cost[j_2+1][i_1]$ 이 한 번씩 나타나 지워집니다. 앞 부등식이
엄격하므로 더한 결과도 엄격하고, 남는 것이 칸 $i_2$ 에서의 비교예요.

$$
dp[g-1][j_2] + cost[j_2+1][i_2] \;<\; dp[g-1][j_1] + cost[j_1+1][i_2]
$$

유도가 말하는 것을 한 줄씩 적으면 이렇습니다.

| 걸음 | 뜻 |
| --- | --- |
| 전제 | 칸 `i1` 에서 뒤쪽 자리 `j2` 가 앞쪽 자리 `j1` 보다 작은 값을 낸다 |
| 사각 부등식 | 칸을 `i1` 에서 `i2` 로 늘릴 때 `j2` 의 비용이 `j1` 의 비용보다 덜 커진다 |
| 두 식을 더한 것 | 칸 `i2` 에서도 `j2` 가 `j1` 보다 작은 값을 낸다 |

이것으로 $\operatorname{opt}(g, i_1) \le \operatorname{opt}(g, i_2)$ 가 나옵니다. $j_2 = \operatorname{opt}(g, i_1)$ 로
두면, 그보다 앞의 모든 $j_1$ 은 칸 $i_1$ 에서 $j_2$ 보다 큰 값을 냅니다 — 같은 값을 내면 더 작은 $j_1$ 이 가장 작은
자리로 골라졌을 테니까요. 그래서 전제가 모든 $j_1 < j_2$ 에서 성립하고, 유도로 칸 $i_2$ 에서도 모든 $j_1 < j_2$ 가
$j_2$ 보다 큰 값을 냅니다. 가장 작은 값을 내는 자리는 $j_2$ 보다 앞일 수 없으므로
$\operatorname{opt}(g, i_2) \ge j_2 = \operatorname{opt}(g, i_1)$ 입니다.

**둘째 유도는 줄 하나의 후보 수입니다.** 재귀 깊이 $d$ 의 호출들은 칸 범위가 겹치지 않고, 넘겨받는 후보 범위는
**끝점 하나만** 이웃과 겹칩니다. 깊이 $d$ 의 호출은 많아야 $2^d$ 개이고, 호출 하나가 넣는 후보 수는 그 범위의 길이
이하라서, 깊이 $d$ 의 후보 수 합은 $n$ 에 겹치는 끝점 수를 더한 $n + 2^d$ 를 넘지 않아요. 앞의 주장을 값으로
확인합니다.

| 256 | 4 | 261 | 272 | 넘지 않는다 |
| 256 | 5 | 281 | 288 | 넘지 않는다 |
| 256 | 6 | 315 | 320 | 넘지 않는다 |
| 256 | 7 | 380 | 384 | 넘지 않는다 |
| 256 | 8 | 129 | 512 | 넘지 않는다 |

값이 모두 같은 배열의 줄 2 입니다. 줄 하나의 상한 n⌈log₂(n+1)⌉ + 2n 은 n = 16 에서 112 · 64 에서 576 · 256 에서 2,816 입니다.

<!--/proof-->

칸 범위가 깊이마다 반씩 줄어드므로 깊이는 $0$ 부터 $L - 1$ 까지이고 $L = \lceil \log_2 (n+1) \rceil$ 입니다.
깊이마다의 상한을 전부 더하면 $n$ 이 $L$ 번 더해지고, $2^d$ 를 $d = 0$ 부터 $L - 1$ 까지 더한 값이 $2^L - 1$ 이에요.
$2^L < 2(n+1)$ 이므로 $2^L - 1 \le 2n$ 이고, 줄 하나와 전체의 후보 수가 다음을 넘지 않습니다.

$$
\text{줄 하나의 후보 수} \;\le\; n \lceil \log_2 (n+1) \rceil + 2n, \qquad \text{전체} \;\le\; (k-1)\bigl( n \lceil \log_2 (n+1) \rceil + 2n \bigr)
$$

```ts
// 식을 그대로 옮긴 조각. `n` 이 칸 수이고 `k` 가 구역 수다.
const layerBound = (n: number): number =>
  n * Math.ceil(Math.log2(n + 1)) + 2 * n;
const total = (n: number, k: number): number => (k - 1) * layerBound(n);
```

**마지막으로 계수입니다.** 식에 규모를 넣어, 실제로 센 줄 하나의 후보 수와 나란히 놓았습니다.

<!--proof:math-scale-->

| n | 줄 하나의 후보 수 | n⌈log₂(n+1)⌉ + 2n | 그 비 |
| ---: | ---: | ---: | ---: |
| 250 | 1,929 | 2,500 | 0.772 |
| 500 | 4,370 | 5,500 | 0.795 |
| 1,000 | 9,754 | 12,000 | 0.813 |
| 2,000 | 21,526 | 26,000 | 0.828 |

a = [1, 2, …, n] 의 줄 2 를 센 값입니다. n = k = 2,000 에서 상한 (k−1)(n⌈log₂(n+1)⌉ + 2n) 은 51,974,000 이고 전부 계산하는 (k−1)·n(n−1)/2 는 3,996,001,000 이라 77 배입니다. 같은 규모에서 실제로 센 후보 수는 35,883,450 입니다.

<!--/proof-->

**여기서 본문의 값만으로는 안 나오는 것이 나옵니다.** 앞의 실측은 입력 몇 벌의 값인데, 위 유도는 **임의의 `n` 과
`k` 에 대해** 후보 수가 `(k−1)(n⌈log₂(n+1)⌉ + 2n)` 을 넘지 않는다는 닫힌 형태를 줘요. 비는 규모를 키울수록 1 에
다가가지 않고 0.8 언저리에 머뭅니다.

### 불변식 — 넘긴 후보 범위 안에 진짜 최적 가르는 자리가 있다

파트 1 의 열두 걸음은 입력 하나에서 답이 나왔다는 기록입니다. 그 하나로는 다른 입력에서도 같은 일이 일어난다는
근거가 안 되므로, **호출이 몇 번 실행되든 참으로 남는 문장**을 세우고 그것이 유지되는지를 값으로 확인합니다.

> `solve(lo, hi, optLo, optHi)` 를 **부르는 시점마다** 둘이 참입니다. **앞 문장** — `prev` 는 줄 `g − 1` 의 값을
> 담고 있고 이번 줄의 어떤 호출도 그것을 고치지 않습니다. **뒤 문장** — `lo ≤ i ≤ hi` 인 모든 칸 `i` 의 진짜
> 최적 가르는 자리 `opt(g, i)` 가 `[optLo, optHi]` 안에 있습니다.

```text
앞 문장이 정하는 것   후보 값 prev[j] + cost[j+1][mid] 가 줄 g−1 의 값으로 만들어진다
뒤 문장이 정하는 것   잘라 낸 후보 가운데 답이 없다

둘이 함께 있으면     범위 안의 가장 작은 값이 그 칸의 값이다 → 줄 g 가 통째로 맞다
줄마다 이어 붙이면   줄 1 이 맞고, 줄 g−1 이 맞으면 줄 g 도 맞다 → 줄 k 의 마지막 칸이 답이다
```

**첫 호출에 들어가기 전부터 봅시다.** 줄 `g` 의 첫 호출은 `solve(0, n−1, 0, n−2)` 이고, 그 시점에 `prev` 는 줄
`g − 1` 을 다 채운 배열이며 `cur` 는 전부 `INF` 인 새 배열입니다. 가르는 자리는 `0` 이상 `n − 2` 이하여야 하므로
넘긴 범위가 가능한 가르는 자리 전부라 뒤 문장이 참이에요. 갈래마다 두 문장이 어떻게 유지되는지 적으면 이렇습니다.

| 갈래 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 줄 배열을 만든다 | `cur` 를 `INF` 로 채운다 | `prev` 를 안 건드린다 | 아직 아무 범위도 안 넘겼다 |
| 빈 범위에서 돌아온다 | 아무것도 안 한다 | `prev` 를 안 건드린다 | 맡은 칸이 없다 |
| 후보를 넣는다 | `prev[j] + cost[j+1][mid]` 를 만든다 | `prev` 를 읽기만 한다 | 넘겨받은 범위를 그대로 쓴다 |
| 칸을 채운다 | `cur[mid]` 에 가장 작은 값을 적는다 | `cur` 는 `prev` 와 다른 배열이다 | `mid` 의 진짜 자리가 범위 안이라 값이 맞다 |
| 왼쪽으로 재귀한다 | `[optLo, bestOpt]` 를 넘긴다 | `prev` 를 안 건드린다 | 왼쪽 칸 `i < mid` 는 `opt(g, i) ≤ opt(g, mid)` |
| 오른쪽으로 재귀한다 | `[bestOpt, optHi]` 를 넘긴다 | `prev` 를 안 건드린다 | 오른쪽 칸 `i > mid` 는 `opt(g, i) ≥ opt(g, mid)` |
| 줄을 교체한다 | `prev = cur` | 다음 줄의 `prev` 가 이번 줄이 된다 | 다음 줄의 첫 호출이 범위를 새로 연다 |

「왼쪽으로 재귀한다」 줄이 이 논증에서 가장 좁은 자리예요. `bestOpt` 는 **넘겨받은 범위 안에서** 찾은 가장 작은 값의
자리입니다. 뒤 문장이 `mid` 의 진짜 최적 가르는 자리가 범위 안에 있다고 주고, 상한을 `min(optHi, mid − 1)` 로 줄여도
진짜 자리는 `mid` 보다 앞이라 그대로 남아요. 그래서 넣은 범위 안의 가장 작은 값과 그 자리가 진짜 값과 진짜 자리이고,
`bestOpt` 가 `opt(g, mid)` 와 같습니다. 전개 입력의 호출마다, 가르는 자리를 전부 계산해 따로 구한 진짜 자리가 넘긴
범위 안에 있는지 보았어요.

<!--proof:invariant-watch-->

| 호출 | 줄 | 가운데 칸 | 진짜 opt | 넘긴 범위 | 불변식 |
| --- | ---: | ---: | ---: | --- | --- |
| solve(0, 3, 0, 2) | 2 | 1 | 0 | [0,2] | 지킨다 |
| solve(0, 0, 0, 0) | 2 | 0 | 없음 | [0,0] | 지킨다 |
| solve(2, 3, 0, 2) | 2 | 2 | 1 | [0,2] | 지킨다 |
| solve(3, 3, 1, 2) | 2 | 3 | 2 | [1,2] | 지킨다 |
| solve(0, 3, 0, 2) | 3 | 1 | 없음 | [0,2] | 지킨다 |
| solve(0, 0, 0, 0) | 3 | 0 | 없음 | [0,0] | 지킨다 |
| solve(2, 3, 0, 2) | 3 | 2 | 1 | [0,2] | 지킨다 |
| solve(3, 3, 1, 2) | 3 | 3 | 2 | [1,2] | 지킨다 |

여덟 호출 모두 진짜 자리가 넘긴 범위 안에 있습니다. 줄 2 의 `solve(3, 3, 1, 2)` 는 범위가 `[1,2]` 로 좁아졌는데
진짜 자리가 2 라 안에 들어 있어요. 경계 입력에서도 같은 문장이 유지되는지 봅시다.

<!--proof:invariant-edges-->

| 입력 | n | k | 반환값 | 전부 계산한 답 | 후보 수 | 호출 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 칸 하나, 구역 하나 | 1 | 1 | 49 | 49 | 0 | 0 |
| 구역이 하나 | 4 | 1 | 100 | 100 | 0 | 0 |
| 구역 수가 칸 수와 같다 | 4 | 4 | 30 | 30 | 16 | 27 |
| 값이 모두 같은 배열 | 5 | 3 | 9 | 9 | 17 | 22 |
| 첫 칸만 큰 배열 | 5 | 2 | 1,000,016 | 1,000,016 | 10 | 11 |
| 비용이 전부 0 | 4 | 2 | 0 | 0 | 6 | 9 |

`k = 1` 이면 줄 반복이 한 번도 실행되지 않고 줄 1 을 그대로 돌려주므로 후보 수와 호출이 0 입니다. 「칸 하나, 구역
하나」 줄은 `a = [7]` 의 구간 합 제곱이라 `cost[0][0] = 49` 이고, 비용이 전부 0 이면 어떻게 나누든 0 이에요. 여섯 줄
모두 반환값이 가르는 자리를 전부 계산한 답과 같습니다.

**이제 그 줄을 망가뜨려 봅시다.** 앞 문장을 떠받치는 자리는 줄 끝의 `prev = cur` 한 줄입니다. 「어차피 `cur` 를 줄마다
새로 만드는데 굳이 바꿔 넣어야 하나」라는 생각으로 그 줄만 지웁니다.

```ts
  solve(0, n - 1, 0, n - 2);
  // prev = cur;   ← 줄 교체 줄을 지웠다
}
```

<!--proof:mutant-no-roll-->

| 입력 | k | 정본 | 줄을 안 바꾼 판 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 | 3 | 34 | 100 | 다르다 |
| 값이 모두 같은 배열 | 3 | 9 | 25 | 다르다 |
| 다른 비용 행렬 | 2 | 3 | 8 | 다르다 |

세 입력 모두에서 답이 갈립니다. 전개 입력에서 100 이 나오는데, 이것은 `dp[1][3]` — 네 칸을 한 구역으로 묶은
값이에요. `prev` 가 줄 1 에 머물러 있으니 줄 2 도 줄 3 도 줄 1 을 읽었고, 마지막에 돌려준 것도 줄 1 이라 구역을 하나도
안 나눈 값이 나옵니다.

<!--proof:invariant-no-roll-rows-->

| 줄 3 을 채울 때 | prev 가 담은 것 |
| --- | --- |
| 정본 | 줄 2 — INF 5 18 52 |
| prev = cur 를 지운 판 | 줄 1 — 1 9 36 100 |

범위를 자르는 규칙 자체는 건드리지 않았습니다. 그런데 그 규칙이 쓰는 `bestOpt` 가 줄 `g − 1` 이 아닌 줄에서 나온
자리라, 뒤 문장이 말하는 진짜 최적 가르는 자리와 이어지지 않아요. 앞 문장이 깨지면 뒤 문장이 기대는 근거도 함께
사라집니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 셋입니다. 줄 1 을 채우는 것, 줄마다 `solve` 를 부르는 것, 그리고 호출마다 후보를 넣는
것이에요. 전개의 열두 걸음에서 후보 수를 셉니다.

<!--proof:perf-walk-->

| 걸음 | 채운 칸 | 후보 범위 | 이 걸음의 후보 수 | 누적 |
| --- | --- | --- | ---: | ---: |
| T1 | — | — | 0 | 0 |
| T2 | 칸 1 | [0,0] | 1 | 1 |
| T3 | 칸 0 | 없음 | 0 | 1 |
| T4 | 칸 2 | [0,1] | 2 | 3 |
| T5 | 칸 3 | [1,2] | 2 | 5 |
| T6 | — | — | 0 | 5 |
| T7 | 칸 1 | [0,0] | 1 | 6 |
| T8 | 칸 0 | 없음 | 0 | 6 |
| T9 | 칸 2 | [0,1] | 2 | 8 |
| T10 | 칸 3 | [1,2] | 2 | 10 |
| T11 | — | — | 0 | 10 |
| T12 | — | — | 0 | 10 |

비지 않은 호출 8 번 · 빈 호출 10 번 · 후보 수 10 입니다.

<!--/proof-->

걸음마다 후보 수가 다릅니다. **후보 범위의 길이가 0 부터 2 까지 갈려요.** T3 과 T8 은 `mid = 0` 이라 상한이 −1 이
되어 후보를 하나도 넣지 않았고, T4 · T5 · T9 · T10 은 둘씩 넣었습니다. T1 · T6 · T11 · T12 는 후보를 넣는 걸음이
아니에요. 후보 말고 따로 드는 것은 호출입니다. 호출 하나는 후보를 빼면 상수 번의 일이고, 줄마다 비지 않은 호출이
칸 수 `n` 개, 빈 호출이 `n + 1` 개라 줄마다 `2n + 1` 번이에요.

<!--proof:perf-calls-->

| 입력 | n | k | 센 호출 수 | (k−1)(2n+1) | 후보 수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전개 입력 | 4 | 3 | 18 | 18 | 10 |
| a = [1, 2, …, 8] | 8 | 3 | 34 | 34 | 32 |
| a = [1, 2, …, 16] | 16 | 4 | 99 | 99 | 151 |
| 값이 모두 같은 배열 | 64 | 5 | 516 | 516 | 1,509 |

총식은 줄 1 과 호출과 후보의 합입니다.

| 항 | 횟수 | 세는 것 |
| --- | --- | --- |
| 줄 1 | `n` | `cost[0][i]` 를 한 번씩 옮긴다 |
| 호출 | `(k−1)(2n+1)` | 줄마다 비지 않은 호출 `n` 개와 빈 호출 `n+1` 개 |
| 후보 | `C ≤ (k−1)(n⌈log₂(n+1)⌉ + 2n)` | 「수식 정의와 유도」의 상한 |

`C` 의 상한을 넣으면 총식이 `n + (k−1)(2n+1) + (k−1)(n⌈log₂(n+1)⌉ + 2n)` 을 넘지 않습니다.

줄 1 과 호출은 줄마다 `n` 에 비례하고 후보는 `n log n` 에 비례하므로, 총식의 차수는 후보가 정합니다. 그래서 이 글은
비용을 후보 수 하나로 셌어요. 메모리는 이전 줄 · 이번 줄의 `2n` 칸과 재귀 깊이만큼의 호출 틀이고, 비용 행렬 `n × n`
은 입력이라 따로 셉니다.

#### 케이스별 비용과 그 경계

어떤 입력인가를 말하는 **케이스**와 어떤 종류의 값인가를 말하는 **경계**는 축이 다릅니다. 한 축의 이름을 다른 축에
붙이면 두 정보가 함께 사라져요.

| 케이스 | 상한 $O$ | 타이트 $\Theta$ |
| --- | --- | --- |
| **최선의 경우** (`k = 1`) | $O(n)$ | $\Theta(n)$ — 줄 1 만 채우고 끝난다 |
| **평균적인 경우** (입력 분포를 정의하지 않는다) | $O(k n \log n)$ | 정의하지 않는다 |
| **최악의 경우** (`k ≥ 2` — 비용 행렬이 무엇이든) | $O(k n \log n)$ | $\Theta(k n \log n)$ — 아래에서 잰 무리가 상한의 0.8 배 언저리에 이른다 |

평균을 정의하지 않는 이유는 **입력 분포가 과제에 없기** 때문입니다. 이 절차에는 난수가 하나도 없어서 무작위성이
구현에서 나오지도 않아요. 「평균」이라는 말을 쓰려면 어떤 비용 행렬 무리를 어떤 확률로 뽑는지를 먼저 정해야 하는데,
그런 정의가 이 과제에 없습니다. 배열 모양을 바꿔 가며 줄 하나의 후보 수를 재 보았어요.

<!--proof:perf-observed-->

| 배열 | n | 줄 하나의 후보 수 | 그 값 / n | log₂ n | 전부 계산한 후보 수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 값이 모두 같은 배열 | 128 | 941 | 7.35 | 7 | 8,128 |
| 값이 모두 같은 배열 | 512 | 4,839 | 9.45 | 9 | 130,816 |
| a = [1, 2, …, n] | 128 | 889 | 6.95 | 7 | 8,128 |
| a = [1, 2, …, n] | 512 | 4,629 | 9.04 | 9 | 130,816 |
| 생성식 배열 | 128 | 941 | 7.35 | 7 | 8,128 |
| 생성식 배열 | 512 | 4,839 | 9.45 | 9 | 130,816 |
| 첫 칸만 큰 배열 | 128 | 1,008 | 7.88 | 7 | 8,128 |
| 첫 칸만 큰 배열 | 512 | 5,100 | 9.96 | 9 | 130,816 |

**「그 값 / n」 열이 `n = 128` 에서 6.95 에서 7.88, `n = 512` 에서 9.04 에서 9.96 입니다.** 앞은 `log₂ 128 = 7`
이고 뒤는 `log₂ 512 = 9` 예요. 배열 모양을 바꿔도 그 값이 `log₂ n` 근처에 머뭅니다. 전부 계산하는 쪽은 같은 규모에서
`n²/2` 를 따라 커져요.

```text
「관측」과 「보장」을 가르는 문장

  관측  네 배열 모양에서 줄 하나의 후보 수가 n 의 log₂ n 배 언저리였다
  보장  사각 부등식을 만족하는 어떤 비용 행렬에서도 줄 하나의 후보 수가 n⌈log₂(n+1)⌉ + 2n 을 넘지 않는다

  앞엣것은 배열을 바꾸면 값이 바뀐다. 뒤엣것은 안 바뀐다
  위의 상한은 전부 최악 보장이다 — 기댓값이 아니라 상한이고, 입력 분포를 쓰지 않는다
```

#### 최악을 만드는 입력

후보 수를 크게 만들려면 후보 범위가 되도록 안 좁아져야 합니다. 이 절차는 범위를 좁히는 규칙이 **입력의 값이 아니라
최적 가르는 자리의 배치**에만 달려 있어요. 배치를 바꿔 가며 재 봅시다.

<!--proof:perf-worst-shape-->

| 배열 (n = 256) | 줄 하나의 최대 (k = 8) | k = 8 합계 |
| --- | ---: | ---: |
| 값이 모두 같은 배열 | 2,154 | 14,043 |
| a = [1, 2, …, n] | 2,050 | 13,230 |
| 생성식 배열 | 2,153 | 14,024 |
| 첫 칸만 큰 배열 | 2,286 | 14,415 |
| 마지막 칸만 큰 배열 | 2,154 | 14,043 |

한 칸만 큰 배열을 큰 값의 자리마다 256 벌 만들어 재면 줄 하나의 후보 수가 최소 2,027 · 최대 2,286 입니다. 상한 n⌈log₂(n+1)⌉ + 2n 은 2,816 이고, 같은 규모를 k = 8 로 전부 계산하면 228,480 입니다.

<!--/proof-->

**한 칸만 큰 배열 무리에서 줄 하나의 후보 수가 좁은 폭 안에 있습니다.** 큰 값의 자리를 256 군데로 옮겨 가며 전부
재 봤는데 2,027 에서 2,286 사이였어요. **입력을 나쁘게 골라 상한을 넘기는 자리는 이 절차에 없습니다.** 첫 호출
하나가 이미 후보 `⌊(n−1)/2⌋` 개를 넣으므로 줄 하나가 `n/2` 언저리 아래로는 내려가지 않고, 깊이마다의 합이
`n + 2^d` 를 넘지 못하므로 상한 위로도 가지 않아요. 잰 무리가 그 사이에서 좁게 모인 까닭까지는 이 글이 증명하지
않았습니다. 가장 많았던 첫 칸만 큰 배열로 규모를 4 배씩 늘려 상한에 대한 비를 재면 이렇습니다.

<!--proof:perf-worst-growth-->

| n | 줄 하나의 후보 수 | n⌈log₂(n+1)⌉ + 2n | 그 비 | 전부 계산한 후보 수 |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 180 | 256 | 0.703 | 496 |
| 128 | 1,008 | 1,280 | 0.787 | 8,128 |
| 512 | 5,100 | 6,144 | 0.830 | 130,816 |
| 2,048 | 24,029 | 28,672 | 0.838 | 2,096,128 |

첫 칸만 큰 배열의 줄 2 입니다.

<!--/proof-->

**「그 비」 열이 0.703 에서 0.838 로 올라가고 1 을 넘지 않습니다.** 줄 하나의 후보 수가 `n log n` 과 같은 차수로
늘어난다는 뜻이고, 그래서 최악이 상한과 같은 차수에 실제로 이릅니다.

| 최악으로 만들 축 | 그 축을 크게 만드는 입력 | 값 |
| --- | --- | --- |
| 줄 하나의 후보 수 | 첫 칸만 큰 배열 — 최적 가르는 자리가 0 에 몰린다 | `n = 256` 에서 2,286 |
| 줄 수 | `k = n` — 구역 수를 칸 수까지 올린다 | 줄 `n − 1` 개 |
| 전체 후보 수 | 위 둘을 겹친다 | 「수식 정의와 유도」의 상한 `(k−1)(n⌈log₂(n+1)⌉ + 2n)` 을 넘지 않는다 |

**여기서 잰 무리는 구간 합의 제곱을 비용으로 삼은 배열들입니다.** 사각 부등식을 만족하는 다른 비용 계열에서도 같은
폭이 나오는지는 확인하지 않았어요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. DP 테이블을 줄마다 채우되, 줄 안에서는 가운데 칸의 최적 가르는
자리를 먼저 찾고 그 자리를 왼쪽 절반의 상한과 오른쪽 절반의 하한으로 넘겨 후보 범위를 자릅니다. 잘라도 되는 근거는
「사각 부등식이 성립하면 최적 가르는 자리가 칸을 따라 줄지 않는다」이고, 후보 수의 상한은
`(k−1)(n⌈log₂(n+1)⌉ + 2n)` 이에요.

```text
줄 1 을 cost[0][i] 로 채운다 → 줄마다 새 배열을 만든다 → 가운데 칸을 후보 범위에서 채운다
→ 찾은 자리를 좌우에 넘긴다 → 줄을 다 채우면 이전 줄을 바꾼다 → 마지막 칸을 돌려준다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 는 `dp[2][3]` 을 채우면서 `j = 0` 을 한 번도 넣지 않았어요. `j = 0` 이 진짜
답이 아니라는 것을 이 절차는 어떻게 알았을까요?

<!--check:whyLowerBoundIsSafe-->
**T4 가 찾은 `opt(2, 2) = 1` 과 최적 가르는 자리의 성질 때문입니다.** 칸 3 은 칸 2 보다 뒤에 있으므로
`opt(2, 3) ≥ opt(2, 2) = 1` 이고, 그러면 `j = 0` 은 칸 3 의 최적 가르는 자리일 수 없어요. 넣지 않은 것이 아니라 **넣을
필요가 없다는 것이 이미 정해진** 것입니다. 그 성질이 없으면 `j = 0` 이 가장 작은 값을 낼 수도 있고, 그때 이 절차는
답을 놓쳐요 — 「이 방법이 기대는 전제」의 행렬이 그 경우였습니다. 이 입력에서 실제로 넣어 보면 이렇습니다.

<!--proof:check-lower-->

```text
j = 0 을 실제로 넣어 보면

  j = 0   dp[1][0] + cost[1][3] = 1 + 81 = 82
  j = 1   dp[1][1] + cost[2][3] = 9 + 49 = 58
  j = 2   dp[1][2] + cost[3][3] = 36 + 16 = 52   ← 채운 값

82 가 58 보다 크다
```
<!--/check-->

아래 셋에는 답을 붙이지 않았습니다. 막히면 차례대로 「경쟁 설계와의 대조」, 전개의 T2 · T3, 「가운데 칸을 먼저 채우는
까닭」을 다시 보세요.

- 「경쟁 설계와의 대조」에서 칸 수를 2,000 으로 고정하자 순서가 `k = 148` 에서 뒤집혔습니다. 칸 수를 500 으로 줄이면
  뒤집히는 구역 수가 어느 쪽으로 옮겨 갈지, 두 설계의 후보 수가 칸 수에 어떻게 붙는지로 먼저 예측해 보세요.
- 전개의 T2 와 T3 에서 줄 배열을 함께 쓰면 `prev` 와 `cur` 가 같은 배열입니다. `k = 2` 로 줄이면 반환값이 무엇이 될지,
  T2 · T3 · T4 · T5 가 적는 칸과 읽는 칸의 차례로 따져 적어 보세요.
- 가운데 대신 3 분의 1 자리를 먼저 채우면 후보 수와 재귀 깊이가 가운데와 4 분의 1 자리 사이의 어디쯤에 올지, 칸 범위가
  깊이마다 몇 배로 줄어드는지로 예측해 보세요.

### 최소 비용 $k$-분할

풀 파일: [`divideAndConquerDp.ts`](./divideAndConquerDp.ts) · 테스트: [`divideAndConquerDp.test.ts`](./divideAndConquerDp.test.ts) · 실행: `bun test src/algorithms/advanced/divideAndConquerDp/divideAndConquerDp.test.ts`

#### 한 줄 요약

> 비용 행렬과 분할 수 $k$를 받아, 구간 $[0, n-1]$을 $k$개의 연속 구간으로 나눴을 때 비용 합의 최솟값을 반환한다.

#### 스토리

물류 회사의 배송 구역 설계 담당자 현아는 배송 경로를 여러 구역으로 나누는 일을 맡았다. 배송 노선은 일렬로 늘어선 $n$개의 거점으로 이루어져 있으며, 이 거점들을 $k$개의 연속된 구역으로 묶어야 한다.

각 구역을 담당할 배송 기사를 지정하는 데에는 구역 안에 포함된 거점 조합에 따라 비용이 달라진다. 예를 들어 교통 상황이나 거리 분포에 따라 구간 $[i, j]$를 한 기사에게 맡기는 비용이 사전에 계산된 표로 주어진다.

현아는 이 표를 보고 전체 배송 비용이 가장 적게 드는 구역 분할 방법을 찾아야 한다. 거점 수가 수백 개, 분할 수도 수십 개에 달하더라도 빠르게 답을 구할 수 있어야 한다.

#### 함수 인터페이스

```ts
export function divideAndConquerDp(cost: number[][], k: number): number;
```

- `cost` — $n \times n$ 비용 행렬. `cost[i][j]`는 구간 $[i, j]$를 하나의 그룹으로 묶는 비용 ($i \leq j$)
- `k` — 분할할 연속 구간의 수
- 반환 — $k$개의 연속 구간으로 분할했을 때 비용 합의 최솟값

#### 제약 조건

- $1 \leq n \leq 500$ (여기서 $n$은 `cost`의 한 변의 길이)
- `cost`는 $n \times n$ 정수 행렬이며 $0 \leq \text{cost}[i][j]$
- $1 \leq k \leq n$
- 비용 행렬은 사각 부등식(quadrangle inequality)을 만족한다고 가정한다
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

$n \times n$ 비용 행렬 `cost[i][j]`가 주어진다. 이 값은 구간 $[i, j]$를 하나의 그룹으로 묶었을 때의 비용이다.

배열의 인덱스 구간 $[0, n-1]$을 정확히 $k$개의 **연속 구간**으로 분할할 때, 각 구간에 해당하는 비용들의 합이 최소가 되도록 하는 분할의 비용 총합을 반환하라.

분할은 겹치지 않고, 빠짐없이, 순서대로 이어져야 한다. $k = 1$이면 전체를 하나의 구간으로 묶어 `cost[0][n-1]`이 답이다. $k = n$이면 각 원소를 단독 구간으로 묶어 $\sum_{i=0}^{n-1} \text{cost}[i][i]$가 답이다.

#### 예시

```ts
const c = [
  [0, 2, 5],
  [0, 0, 3],
  [0, 0, 0],
];

divideAndConquerDp(c, 1); // 5 — 전체 구간 [0,2] 하나로 묶음, cost[0][2] = 5
divideAndConquerDp(c, 3); // 0 — 각 원소 단독 구간, cost[0][0]+cost[1][1]+cost[2][2] = 0
divideAndConquerDp(c, 2); // 3 — [0,1]+[2,2] = 2+0=2 또는 [0,0]+[1,2] = 0+3=3, 최솟값 = 2

// 단일 원소
divideAndConquerDp([[7]], 1); // 7 — n=1, k=1, cost[0][0] = 7

// 균등 분할
const c2 = [
  [4, 16, 36, 64],
  [0,  4, 16, 36],
  [0,  0,  4, 16],
  [0,  0,  0,  4],
]; // buildCost([2,2,2,2])
divideAndConquerDp(c2, 2); // 32 — [2,2]+[2,2] = 16+16
```
