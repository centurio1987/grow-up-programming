# 역순쌍 세기 — 오른쪽 값을 먼저 꺼낼 때 왼쪽에 남은 칸 수가 한꺼번에 역순쌍이다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 모든 쌍을
하나씩 비교하는 방법에서 출발해 병합 정렬의 합치기 안에서 세는 방법까지 가고, 그 방법을 단계마다 값으로
푼 뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

배열에서 **앞 자리의 값이 뒤 자리의 값보다 큰 자리 쌍**을 역순쌍이라고 부릅니다. 자리 `p` 가 자리 `q`
보다 앞이고(`p < q`) `A[p] > A[q]` 이면 쌍 `(p, q)` 가 역순쌍이고, 그 개수를 `I(A)` 라고 적을게요. 값이
같은 쌍은 세지 않습니다. 조건이 `>` 이니까요. 배열 `[4 1 5 2 6 3]` 의 칸마다 가로에 자리, 세로에 값을 두고
점을 찍으면 역순쌍이 어디 있는지 그림으로 보입니다.

<!--fig:concept-pairs-->
![[4 1 5 2 6 3] 의 칸을 (자리, 값) 에 놓은 점과 역순쌍을 이은 선](./figs/concept-pairs.svg)

두 점을 이은 선이 **오른쪽 아래로 내려가면** 앞 자리의 값이 더 크다는 뜻이고, 그 쌍이 역순쌍입니다. 오른쪽
위로 올라가는 쌍은 순서가 맞는 쌍이라 그리지 않았어요. 앞 자리마다 그보다 뒤에 있는 더 작은 값을 세면
이렇습니다.

<!--proof:concept-count-->

| 앞 자리 p | A[p] | 뒤에 있는 더 작은 값 | 그 자리에서 시작하는 역순쌍 |
| ---: | ---: | --- | ---: |
| 0 | 4 | 1 2 3 | 3 |
| 1 | 1 | 없음 | 0 |
| 2 | 5 | 2 3 | 2 |
| 3 | 2 | 없음 | 0 |
| 4 | 6 | 3 | 1 |
| 5 | 3 | 없음 | 0 |

더하면 I(A) = 6 이고, 정본이 낸 답도 6 입니다.

<!--/proof-->

정의를 그대로 옮기면 모든 자리 쌍을 하나씩 비교하게 되고, 칸이 `N` 개면 비교가 `N(N−1)/2` 번입니다.
비교 한 번이 쌍 하나만 정하기 때문이에요. 이 글이 세우는 방법은 **비교 한 번으로 여러 쌍을 함께 정합니다.**
그러려면 조건이 하나 필요합니다. 배열을 왼쪽 조각과 오른쪽 조각으로 나눴을 때 **두 조각이 각각 오름차순**이어야
해요. 왼쪽 조각 `[1 4 5]` 와 오른쪽 조각 `[2 3 6]` 에서 4 와 2 를 비교하는 순간을 그리면 이렇습니다.

<!--fig:concept-one-compare-->
![정렬된 두 조각 [1 4 5] · [2 3 6] 에서 4 와 2 를 비교하는 한 번](./figs/concept-one-compare.svg)

4 가 2 보다 크니 오른쪽의 2 를 먼저 꺼냅니다. 이때 왼쪽 조각에서 아직 안 꺼낸 값은 4 와 5 인데, 왼쪽 조각이
오름차순이라 둘 다 4 이상이고 따라서 둘 다 2 보다 커요. 그래서 비교 한 번으로 역순쌍 둘을 한꺼번에 셉니다.
괄호 안의 `i` 와 `j` 는 두 조각에서 다음에 꺼낼 자리이고, 더하는 개수는 왼쪽 조각의 끝 자리 `mid` 와 `i` 로
`mid − i + 1` 이에요.

두 조각을 오름차순으로 만드는 일은 **병합 정렬**이 합니다. 병합 정렬은 배열을 반씩 갈라 칸 하나짜리 조각까지
내려간 다음, 오름차순인 두 조각을 앞에서부터 비교해 작은 쪽을 꺼내는 일로 하나의 오름차순 조각을 만들며
올라와요. 두 조각을 하나로 만드는 이 일을 **합치기**라고 부릅니다. 합치기에서 오른쪽 값을 꺼낼 때마다
왼쪽 조각에 남은 칸 수를 더하면, 정렬이 끝났을 때 더한 값이 `I(A)` 입니다. 이 방법을 **합치며 세기**라고
부르겠습니다.

| 합치며 세기에서 | 무엇인가 |
| --- | --- |
| 세는 자리 | 합치기 하나마다, 오른쪽 값을 꺼내는 순간 |
| 한 번에 더하는 수 | 그 순간 왼쪽 조각에 남은 칸 수 `mid − i + 1` |
| 쌍 하나가 세어지는 곳 | 두 자리가 처음으로 서로 다른 조각에 들어가는 합치기 하나 |
| 필요한 조건 | 합치기가 시작될 때 두 조각이 각각 오름차순이다 |

쌍 하나는 두 자리가 같은 조각에 있는 동안은 안 세어지고, 갈라진 뒤로는 다시 같은 조각에 들어가지 않습니다.
그래서 빠지거나 겹쳐 세는 쌍이 없어요. 비용을 결과만 적으면 `O(N log N)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **병합 정렬과 합치기** — 오름차순인 두 조각을 앞에서부터 비교해 합치는 일, 배열을 반씩 갈라 칸 하나까지
  내려가는 재귀, 가르며 내려간 조각을 깊이마다 모은 층. 이 글은 합치기를 다시 설명하지 않고 그 위에 세는
  줄 하나를 더합니다. 모르면 [병합 정렬 가이드](../../sorting/sortArray/sortArray-guide.md)를 먼저 보세요.
  그 편은 비용을 비교 횟수로 세고, 이 글이 세는 비교 횟수도 그 편과 같은 값입니다.
- **재귀와 종료 조건** — 함수가 자기 자신을 더 작은 입력으로 부르고, 더 줄일 수 없는 크기에서 답을 직접
  내는 것. 이 글은 칸 하나짜리 조각을 그 자리로 씁니다.
- **배열의 자리와 값을 갈라 생각하기** — 이 글에서 `p` · `q` · `i` · `j` 는 전부 **자리**이고 `A[p]` 같은
  표기가 **값**입니다. 역순쌍은 자리와 값의 관계라서 둘을 섞으면 뒤의 표가 안 읽혀요.
- **밑이 2 인 로그** — `log₂ N` 은 `N` 을 2 로 몇 번 나눠야 1 이하가 되는가입니다. 절반씩 줄이는 절차에서
  로그가 나오는 이유는 [이진 탐색 가이드](../../binary-search/binarySearch/binarySearch-guide.md)가 다룹니다.

첫 항목이 흐릿하면 이 글의 절반이 어긋납니다. 합치기가 왜 두 조각의 맨 앞만 비교해도 되는지 모르면, 그 자리에
세는 줄을 더해도 되는 까닭을 확인할 수 없어요. 역순쌍의 개수가 정렬 비용의 한 항으로 쓰이는 자리는
[삽입 정렬 가이드](../../sorting/insertionSort/insertionSort-guide.md)에 있습니다. 꼭 필요하지는 않아요.

### 아이디어를 떠올리는 과정 — 모든 쌍 비교하기에서 합치며 세기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정수 배열을 받아 역순쌍의 개수를
돌려줍니다.

```ts
function countInversions(arr: number[]): number;
```

- 입력: 정수 배열 `arr`. 음수가 있을 수 있고 같은 값이 여럿일 수 있습니다. 값의 범위는 미리 모른다고 둡니다.
- 출력: `p < q` 이면서 `arr[p] > arr[q]` 인 자리 쌍 `(p, q)` 의 개수. 입력 배열은 바꾸지 않습니다.
- 규모: 칸 수 `N` 은 0 이상 100,000 이하입니다. 이웃한 [병합 정렬 가이드](../../sorting/sortArray/sortArray-guide.md)와
  같은 규모로 잡았어요. 그래야 그 편이 센 비교 횟수와 이 글의 비교 횟수를 같은 칸 수에서 그대로 맞대어 볼 수
  있습니다. 시간은 흔한 채점 환경의 예산인 1 초에 대어 잽니다.

비용은 **칸 접근**으로 셉니다. 배열의 칸 하나를 읽거나 쓰면 1 이고, 두 값을 비교하면 두 칸을 읽으니
2 예요. 비교 횟수만 세지 않는 까닭은 파트 2 의 경쟁 설계가 값을 비교하지 않고 트리의 칸을 읽고 쓰는
절차라서, 두 설계를 같은 잣대로 재려면 칸 접근이 필요하기 때문입니다. 시간은 1 초에 칸 접근 1 억 번으로
어림합니다. 이 글이 끝까지 쓰는 기호는 여덟입니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `N` | 배열의 칸 수 | `0 ≤ N ≤ 100,000` |
| `A` | 입력 배열. 코드의 `arr` 이고, 그 사본이 `a` 다 | 정수 |
| `I(A)` | `A` 의 역순쌍 개수. 이 함수의 답이다 | `0 ≤ I(A) ≤ N(N−1)/2` |
| `p` · `q` | 역순쌍을 이루는 두 자리. 언제나 `p < q` 다 | `0 ≤ p < q ≤ N−1` |
| `lo` · `mid` · `hi` | 지금 합치는 조각의 왼쪽 끝 · 왼쪽 조각의 끝 · 오른쪽 끝 | `lo ≤ mid < hi` |
| `i` · `j` | 왼쪽 조각과 오른쪽 조각에서 다음에 볼 자리 | `lo ≤ i ≤ mid+1`, `mid+1 ≤ j ≤ hi+1` |
| `C` | 비교 횟수 | 파트 2 가 경계를 낸다 |
| `M` | 합치기마다의 조각 길이를 다 더한 값 | 파트 2 가 닫힌 형태를 낸다 |

아무 기법 없이 푸는 방법은 정의를 그대로 옮기는 것입니다. 자리 쌍을 전부 만들어 하나씩 비교해요.

```ts
function countInversionsNaive(A: number[]): number {
  let count = 0;
  for (let p = 0; p < A.length; p++) {
    for (let q = p + 1; q < A.length; q++) {
      if ((A[p] as number) > (A[q] as number)) count++;
    }
  }
  return count;
}
```

이 방법은 답을 틀리지 않습니다. 비교는 쌍마다 한 번이라 입력의 값과 상관없이 `N(N−1)/2` 번이에요.

<!--proof:origin-naive-->

| 칸 수 N | 쌍의 개수 N(N−1)/2 | 칸 접근 | 어림 시간 |
| ---: | ---: | ---: | ---: |
| 1,000 | 499,500 | 999,000 | 0.0100 초 |
| 10,000 | 49,995,000 | 99,990,000 | 1.00 초 |
| 100,000 | 4,999,950,000 | 9,999,900,000 | 100.00 초 |

쌍 하나를 비교할 때 두 칸을 읽으므로 칸 접근은 쌍의 개수의 두 배이고, 칸 1 개부터 200 개까지 실제로 세어 이 식과 대조했습니다. 어림 시간은 칸 접근을 1 초에 100,000,000 번으로 나눈 값입니다. 전개 입력 [4 1 5 2 6 3] 에서는 비교 15 번으로 답 6 을 냅니다.

<!--/proof-->

칸 10 만이면 어림 100 초로 예산의 100 배입니다. 칸 1 만에서 이미 예산 1 초에 이르러요. 이 방법이 느린
까닭은 **비교 한 번이 쌍 하나만 정한다**는 데 있습니다. 그러니 줄여야 하는 것은 비교 횟수이고, 그러려면 비교
한 번이 여러 쌍을 정하게 만들어야 해요.

전개 입력 `[4 1 5 2 6 3]` 을 가운데에서 둘로 갈라 봅시다. 쌍은 세 종류로 나뉩니다. 두 자리가 다 왼쪽 조각에
있는 쌍, 다 오른쪽 조각에 있는 쌍, 한 자리씩 나뉜 쌍이에요. 마지막 종류를 **두 조각 사이의 쌍**이라고 부르면,
두 조각 사이의 쌍이 역순인지는 **두 값만** 보고 정해집니다. 왼쪽 값이 어느 자리에 있든 오른쪽 값보다 앞에 있기
때문이에요. 두 조각 안을 각각 정렬해 보고 세 종류를 다시 세면 이렇습니다.

<!--proof:origin-halves-->

| 두 조각 | 값 | 왼쪽 안 | 오른쪽 안 | 두 조각 사이 | 합 |
| --- | --- | ---: | ---: | ---: | ---: |
| 원래 순서 | [4 1 5] · [2 6 3] | 1 | 1 | 4 | 6 |
| 조각마다 정렬 | [1 4 5] · [2 3 6] | 0 | 0 | 4 | 4 |

두 조각 사이의 역순쌍은 조각마다 정렬해도 4 개에서 4 개로 그대로이고, 원래 순서의 합 6 은 정본의 답과 같습니다.

<!--/proof-->

조각 안을 정렬하면 조각 안의 역순쌍은 사라지지만 **두 조각 사이의 역순쌍은 그대로**입니다. 그러니 조각 안의
역순쌍을 먼저 세어 두기만 하면, 그다음에는 조각을 정렬해도 됩니다. 정렬해 둔 두 조각 `[1 4 5]` 와 `[2 3 6]`
사이의 역순쌍을 두 방식으로 세어 봅시다. 하나는 왼쪽 값과 오른쪽 값을 하나씩 짝지어 전부 비교하는 것이고,
다른 하나는 합치기처럼 두 조각의 맨 앞을 비교해 작은 쪽을 꺼내면서, 오른쪽 값을 꺼낼 때 왼쪽에 남은 개수를
더하는 것이에요.

<!--proof:origin-cross-->

| 비교 | 왼쪽 값 | 오른쪽 값 | 판정 | 더한 개수 | 누적 |
| ---: | ---: | ---: | --- | ---: | ---: |
| 1 | 1 | 2 | 왼쪽을 꺼낸다 | 0 | 0 |
| 2 | 4 | 2 | 오른쪽을 꺼낸다 | 2 | 2 |
| 3 | 4 | 3 | 오른쪽을 꺼낸다 | 2 | 4 |
| 4 | 4 | 6 | 왼쪽을 꺼낸다 | 0 | 4 |
| 5 | 5 | 6 | 왼쪽을 꺼낸다 | 0 | 4 |

같은 두 조각을 두 방식으로 센 비용을 나란히 놓으면 이렇습니다. 비교 한 번에 두 칸을 읽습니다.

| 방식 | 비교 | 읽은 칸 | 센 교차 역순쌍 |
| --- | ---: | ---: | ---: |
| 하나씩 비교한다 | 9 | 18 | 4 |
| 합치며 센다 | 5 | 10 | 4 |

왼쪽 [1 4 5] 와 오른쪽 [2 3 6] 은 둘 다 오름차순입니다. 센 개수는 4 로 같고, 비교는 9 번에서 5 번으로 줍니다.

<!--/proof-->

둘째 줄과 셋째 줄에서 오른쪽 값을 꺼낼 때마다 2 를 더했습니다. 왼쪽에 남은 4 와 5 가 오름차순이라 둘 다 꺼낸
오른쪽 값보다 크기 때문이에요. 여기서 관찰한 것은 하나입니다. **조각이 정렬돼 있으면 비교 한 번이 왼쪽에 남은
칸 수만큼의 쌍을 정합니다.**

가장 단순한 후보부터 반박해 보겠습니다. 첫째 후보는 「배열 전체를 먼저 정렬하고 세면 되지 않을까」입니다.
정렬된 배열에서는 무엇이 큰지 금방 알 수 있으니까요.

<!--proof:origin-sorted-->

| 배열 | 값 | 정의대로 센 역순쌍 |
| --- | --- | ---: |
| 입력 그대로 | [4 1 5 2 6 3] | 6 |
| 오름차순으로 놓은 것 | [1 2 3 4 5 6] | 0 |

<!--/proof-->

정렬을 끝낸 배열에는 역순쌍이 하나도 없습니다. 역순쌍은 값이 아니라 **자리와 값의 관계**라서, 자리를 바꿔
버리면 세려던 대상이 사라져요. 정렬은 세는 일과 같은 걸음 안에서 해야 합니다. 둘째 후보는 「반으로 가르기만
하면 되지 않을까」입니다. 조각 안은 같은 방법으로 세고, 두 조각 사이의 쌍은 정렬하지 않은 채 하나씩 비교해요.

<!--proof:origin-divide-->

| 칸 수 N | 모든 쌍 비교하기 | 반으로 갈라 하나씩 세기 | N(N−1)/2 |
| ---: | ---: | ---: | ---: |
| 6 | 15 | 15 | 15 |
| 64 | 2,016 | 2,016 | 2,016 |
| 1,000 | 499,500 | 499,500 | 499,500 |

입력은 A[q] = (q × 37) mod 101 이고, 두 방법의 답은 세 칸 수 모두에서 정본과 같습니다. 칸 1 개부터 200 개까지 전부 세어도 두 방법의 비교 횟수는 N(N−1)/2 와 같았습니다.

<!--/proof-->

반으로 가르기만 해서는 비교가 하나도 줄지 않습니다. 쌍 하나는 두 자리가 처음 갈라지는 자리에서 정확히 한 번
비교되니, 합이 모든 쌍의 수 그대로예요. 비교를 줄인 것은 가르기가 아니라 **두 조각이 정렬돼 있다는 사실**이었습니다.
지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **합치며 세기**입니다. 배열을 반으로 갈라 두 조각을 각각 같은 방법으로 정렬하며 그
안의 역순쌍을 세고, 두 조각을 합칠 때 오른쪽 값을 꺼낼 때마다 왼쪽에 남은 칸 수를 더해요. 어느 쌍이 어느
합치기에서 세어지는지, 합치기 하나가 무엇을 더하는지, 전체 합이 왜 `I(A)` 가 되는지는 다음 절에서 실현하는
순서대로 확인합니다.

### 아이디어 상세 — 합치며 세기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **병합 정렬로 배열을 정렬하면서, 합치기마다 오른쪽 값을 꺼낼 때
왼쪽 조각에 남은 칸 수를 더합니다.** 그 합이 왜 역순쌍의 개수와 같은지를 설명하려면 개념 하나가 먼저
필요하고, 그다음 실현하는 순서대로 세 단계로 나눕니다.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 두 조각 합치며 세기 | 오름차순인 두 조각을 합치면서 두 조각 사이의 역순쌍을 센다 | 먼저 알아 둘 개념의 교차 역순쌍 |
| 2단계 가운데에서 갈라 조각 안부터 세기 | 조각을 반으로 갈라 두 조각 안을 먼저 세고 정렬해 둔다 | 1단계가 요구하는 조건(두 조각이 오름차순) |
| 3단계 층마다 더해 올라가기 | 부름마다 왼쪽 · 오른쪽 · 교차를 더해 돌려주고, 가장 바깥 부름의 값을 답으로 낸다 | 1단계의 셈 · 2단계의 부름 |

#### 먼저 알아 둘 개념 — 교차 역순쌍

##### 교차 역순쌍의 뜻

합치기 하나가 세는 쌍을 **교차 역순쌍**이라고 부릅니다. 앞 자리가 그 합치기의 왼쪽 조각에 있고 뒤 자리가
오른쪽 조각에 있는 역순쌍이에요. 합치기의 조각이 `[lo, hi]` 이고 왼쪽 조각의 끝이 `mid` 이면,
`lo ≤ p ≤ mid < q ≤ hi` 인 역순쌍 `(p, q)` 가 그 합치기의 교차 역순쌍입니다. 자리 `p` · `q` 는 원래 배열의
자리이고, 합치기가 시작될 때 두 조각이 정렬돼 있어도 그 값들이 원래 어느 자리에서 왔는지로 셉니다.

##### 입력 위의 교차 역순쌍

전개 입력 `[4 1 5 2 6 3]` 을 가르며 내려간 조각을 층마다 한 줄씩 그리고, 줄 끝에 그 조각의 합치기가 세는 교차
역순쌍을 적었습니다.

<!--fig:build-cross-->
![[4 1 5 2 6 3] 을 가른 조각마다 그 조각의 합치기가 세는 교차 역순쌍](./figs/build-cross.svg)

한 줄이 조각 하나이고, 조각이 맡은 자리에만 값이 놓여 있어요. 칸이 둘 이상인 조각에는 합치기가 하나씩 있고,
칸 하나짜리 조각에는 합치기가 없습니다.

##### 합치기 하나의 교차 역순쌍을 읽는 법

맨 위 조각 `[0,5]` 를 골라 봅시다. 이 조각은 `lo = 0`, `mid = 2`, `hi = 5` 입니다. 역순쌍 여섯을 차례로 놓고
`lo ≤ p ≤ mid < q ≤ hi` 를 따지면 그 합치기가 세는 쌍이 정해져요.

<!--proof:build-cross-read-->

| 역순쌍 (p, q) | 값 | lo ≤ p ≤ mid < q ≤ hi | [0,5] 의 합치기 |
| --- | --- | --- | --- |
| (0, 1) | 4 > 1 | 0 ≤ 0 ≤ 2 < 1 ≤ 5 | 거짓 — 안 센다 |
| (0, 3) | 4 > 2 | 0 ≤ 0 ≤ 2 < 3 ≤ 5 | 참 — 센다 |
| (0, 5) | 4 > 3 | 0 ≤ 0 ≤ 2 < 5 ≤ 5 | 참 — 센다 |
| (2, 3) | 5 > 2 | 0 ≤ 2 ≤ 2 < 3 ≤ 5 | 참 — 센다 |
| (2, 5) | 5 > 3 | 0 ≤ 2 ≤ 2 < 5 ≤ 5 | 참 — 센다 |
| (4, 5) | 6 > 3 | 0 ≤ 4 ≤ 2 < 5 ≤ 5 | 거짓 — 안 센다 |

합치기 [0,5] 는 lo = 0, mid = 2, hi = 5 이고, 이 합치기가 세는 교차 역순쌍은 4 개입니다. 정본에서 그 합치기가 센 개수도 4 개입니다.

<!--/proof-->

`(0, 1)` 은 두 자리가 다 왼쪽 조각에 있어서 `mid < q` 가 거짓이고, `(4, 5)` 는 다 오른쪽 조각에 있어서
`p ≤ mid` 가 거짓입니다. 두 쌍은 이 합치기가 아니라 더 아래의 합치기가 셉니다.

##### 합치기끼리의 관계

합치기 다섯이 세는 교차 역순쌍을 모두 모으면 이렇습니다.

<!--proof:build-cross-once-->

| 합치기 | 교차 역순쌍 | 개수 |
| --- | --- | ---: |
| [0,1] | (0, 1) | 1 |
| [0,2] | 없음 | 0 |
| [3,4] | 없음 | 0 |
| [3,5] | (4, 5) | 1 |
| [0,5] | (0, 3) (0, 5) (2, 3) (2, 5) | 4 |

다섯 합치기의 개수를 더하면 6 이 되어 정본의 답 6 과 같습니다. 역순쌍 6 개 가운데 두 합치기 이상에 든 쌍은 0 개, 어느 합치기에도 안 든 쌍은 0 개입니다.

<!--/proof-->

같은 층의 합치기는 서로 겹치지 않는 조각을 맡으니 같은 쌍을 함께 셀 수 없어요. 위아래 층 사이에서는, 한
쌍의 두 자리가 아래 조각에서 이미 갈라져 있으면 위 조각에서는 늘 같은 쪽에 있습니다. 두 자리가 처음 갈라지는
합치기가 하나뿐이라, 쌍마다 그 합치기 하나에서만 세어져요.

##### 조각 안 전부를 세는 모양과의 차이

헷갈리기 쉬운 모양은 「합치기마다 그 조각 안의 역순쌍을 전부 센다」입니다. 같은 입력에서 두 모양을 나란히
세면 이렇습니다.

<!--proof:build-cross-overcount-->

| 합치기 | 조각 안의 역순쌍 전부 | 교차 역순쌍 |
| --- | ---: | ---: |
| [0,1] | 1 | 1 |
| [0,2] | 1 | 0 |
| [3,4] | 0 | 0 |
| [3,5] | 1 | 1 |
| [0,5] | 6 | 4 |
| 합 | 9 | 6 |

조각 안의 역순쌍을 전부 세면 합이 9 로 정답 6 보다 크고, 교차 역순쌍만 세면 6 입니다.

<!--/proof-->

조각 안을 전부 세면 아래 합치기가 이미 센 쌍을 위 합치기가 다시 셉니다. `(0, 1)` 은 `[0,1]` · `[0,2]` ·
`[0,5]` 세 합치기에서 모두 세어져요. 교차 역순쌍만 세야 합이 `I(A)` 와 같아집니다.

##### 교차 역순쌍으로 가르는 까닭

교차 역순쌍의 개수는 두 조각의 **값 모임**만으로 정해집니다. 앞 자리가 왼쪽 조각에 있으면 뒤 자리가 오른쪽
조각의 어디에 있든 앞 자리가 더 앞이니, 따질 것이 두 값의 크기뿐이에요. 그래서 조각 안의 순서를 정렬로 바꿔도
교차 역순쌍의 개수는 그대로이고, 이것이 「아이디어를 떠올리는 과정」에서 조각을 정렬해도 두 조각 사이의
개수가 안 바뀐 이유입니다. 조각을 정렬해 둘 수 있으니 합치기의 비교 한 번이 여러 쌍을 정할 수 있어요.

#### 1단계 — 두 조각 합치며 세기

두 조각은 둘 다 오름차순입니다. 병합 정렬의 합치기와 똑같이 두 조각의 맨 앞 `a[i]` 와 `a[j]` 를 비교해
작거나 같은 쪽을 꺼내고, **오른쪽을 꺼낼 때만** `mid − i + 1` 을 더합니다. `mid − i + 1` 은 왼쪽 조각에서
아직 안 꺼낸 칸 수예요. 쉬운 경우는 두 조각에서 값이 번갈아 나오는 합치기이고, 「아이디어를 떠올리는 과정」의
`[1 4 5]` 와 `[2 3 6]` 이 그 모양이었습니다. 불안한 경우는 **한쪽이 일찍 비는 합치기**입니다. 왼쪽 조각의
값이 전부 크면 오른쪽이 먼저 비고, 전부 작으면 왼쪽이 먼저 비어요.

<!--proof:build-merge-cases-->

| 두 조각 | 비교와 판정 | 먼저 빈 쪽 | 비교 없이 옮긴 값 | 센 개수 | 정의대로 센 교차 역순쌍 |
| --- | --- | --- | --- | ---: | ---: |
| [1 4 5] + [2 3 6] | 1 ≤ 2 왼쪽 · 4 > 2 오른쪽 +2 · 4 > 3 오른쪽 +2 · 4 ≤ 6 왼쪽 · 5 ≤ 6 왼쪽 | 왼쪽 | 6 | 4 | 4 |
| [5 6] + [1 2] | 5 > 1 오른쪽 +2 · 5 > 2 오른쪽 +2 | 오른쪽 | 5 6 | 4 | 4 |
| [1 2] + [5 6] | 1 ≤ 5 왼쪽 · 2 ≤ 5 왼쪽 | 왼쪽 | 5 6 | 0 | 0 |

세 모양 모두 합치며 센 개수가 정의대로 센 교차 역순쌍과 같습니다.

<!--/proof-->

오른쪽이 먼저 비는 `[5 6] + [1 2]` 에서는 오른쪽 값 1 과 2 를 꺼낼 때마다 왼쪽에 남은 2 칸을 더했고, 남은 5 와
6 을 옮기는 동안은 더하지 않았습니다. 5 와 6 이 이루는 교차 역순쌍은 그 넷이 전부이고, 이미 오른쪽 값을 꺼낼
때 셌기 때문이에요. 왼쪽이 먼저 비는 `[1 2] + [5 6]` 에서는 오른쪽에 남은 5 와 6 이 왼쪽의 모든 값보다 커서
짝지을 역순쌍이 없습니다.

반복이 끝나는 자리는 둘뿐이고, 어느 쪽이든 남은 값을 옮길 때는 더할 것이 없어요.

| 끝나는 자리 | 조건 | 남은 값을 옮길 때 더하는 수 |
| --- | --- | --- |
| 왼쪽을 다 꺼냈다 | `i = mid + 1` | 0 — 남은 오른쪽 값은 왼쪽의 모든 값 이상이다 |
| 오른쪽을 다 꺼냈다 | `j = hi + 1` | 0 — 남은 왼쪽 값과 이루는 쌍은 오른쪽 값을 꺼낼 때 이미 셌다 |

빠진 쌍이 없는 근거는 반복의 종료 조건에 있습니다. 오른쪽 값 `a[j]` 는 꺼내는 순간에 한 번 셉니다. 그때 왼쪽에서
이미 꺼낸 값은 전에 `a[j]` 와 비교해 작거나 같다고 판정된 값이거나 그보다 작은 값이라 `a[j]` 와 역순쌍을 이루지
않고, 아직 안 꺼낸 값은 `a[i]` 이상이라 전부 `a[j]` 보다 커요. 그래서 `a[j]` 와 역순쌍을 이루는 왼쪽 값의 수가
정확히 `mid − i + 1` 입니다. 오른쪽 값은 모두 반복 안에서 꺼내지거나, 왼쪽을 다 꺼낸 뒤 옮겨지며 셀 것이 0 이라
빠지는 오른쪽 값이 없어요.

#### 2단계 — 가운데에서 갈라 조각 안부터 세기

1단계는 두 조각이 이미 오름차순일 것을 요구합니다. 그런 조각은 같은 절차를 더 작은 조각에 불러서 만들고, 그
부름이 조각 안의 역순쌍도 함께 셉니다. 조각 `[lo, hi]` 를 `mid = ⌊(lo + hi) / 2⌋` 에서 가르고, 왼쪽 부름의 값과
오른쪽 부름의 값과 합치기가 센 교차 역순쌍을 더해 돌려줘요. 칸 하나짜리 조각은 쌍이 없으니 0 을 돌려줍니다.
전개 입력에서 부름이 이어지는 순서대로 적으면 이렇습니다.

<!--proof:build-split-->

| 부른 순서 | 깊이 | 조각 | 왼쪽 + 오른쪽 + 교차 | 돌려준 값 |
| ---: | ---: | --- | --- | ---: |
| 1 | 0 | [0,5] [4 1 5 2 6 3] | 1 + 1 + 4 | 6 |
| 2 | 1 | [0,2] [4 1 5] | 1 + 0 + 0 | 1 |
| 3 | 2 | [0,1] [4 1] | 0 + 0 + 1 | 1 |
| 4 | 3 | [0,0] [4] | 칸 하나 → 0 | 0 |
| 5 | 3 | [1,1] [1] | 칸 하나 → 0 | 0 |
| 6 | 2 | [2,2] [5] | 칸 하나 → 0 | 0 |
| 7 | 1 | [3,5] [2 6 3] | 0 + 0 + 1 | 1 |
| 8 | 2 | [3,4] [2 6] | 0 + 0 + 0 | 0 |
| 9 | 3 | [3,3] [2] | 칸 하나 → 0 | 0 |
| 10 | 3 | [4,4] [6] | 칸 하나 → 0 | 0 |
| 11 | 2 | [5,5] [3] | 칸 하나 → 0 | 0 |

부름은 11 번이고 그중 칸 하나짜리가 6 번, 합치기가 있는 부름이 5 번입니다. 가장 바깥 부름이 돌려준 6 이 정본의 답과 같습니다.

<!--/proof-->

부름 하나가 돌려주는 값은 그 조각 안의 역순쌍 개수입니다. 왼쪽 부름이 왼쪽 조각 안을, 오른쪽 부름이 오른쪽
조각 안을 세고, 합치기가 그 사이를 세니 세 종류가 다 들어가요. 부름이 끝날 때 그 조각은 합치기를 거쳐
오름차순이 되어 있고, 그래서 한 층 위의 합치기가 1단계의 조건을 받습니다. `hi − lo` 가 1 이상인 조각을 가르면
두 조각이 모두 비지 않고 원래보다 작아서, 부름은 반드시 칸 하나짜리 조각에서 멈춰요.

#### 3단계 — 층마다 더해 올라가기

2단계의 부름을 층으로 묶으면 셈이 한 자리에 모입니다. 층은 가르며 내려간 조각을 깊이마다 모은 것이고, 병합
정렬 가이드의 층과 같아요. 층마다 합치기가 센 교차 역순쌍과 옮긴 칸 수를 적으면 이렇습니다.

<!--proof:build-levels-->

| 층 | 그 층의 합치기 | 센 교차 역순쌍 | 옮긴 칸 | 그 층의 칸 수 |
| --- | --- | ---: | ---: | ---: |
| 0 층 | [0,5] | 4 | 6 | 6 |
| 1 층 | [0,2] · [3,5] | 1 | 6 | 6 |
| 2 층 | [0,1] · [3,4] | 1 | 4 | 6 |

합치기가 있는 층은 3 개이고, 센 개수를 층마다 더하면 6 이 됩니다. 어느 층도 옮긴 칸이 그 층의 칸 수 6 을 넘지 않습니다.

<!--/proof-->

같은 층의 조각은 서로 겹치지 않고 합쳐도 배열 전체를 넘지 않으니, 한 층에서 옮기는 칸은 `N` 을 넘지 않습니다.
층 수는 조각이 절반 이하로 줄어드는 횟수라 `⌈log₂ N⌉` 이에요. 그래서 옮긴 칸의 합 `M` 은 `N⌈log₂ N⌉` 을 넘지
않고, 비교 횟수 `C` 도 합치기마다 조각 길이보다 작으니 `M` 을 넘지 않습니다. 센 개수는 층마다 더해 가장 바깥
부름이 돌려주고, 그 값이 `I(A)` 입니다.

#### 이 방법이 기대는 전제

합치며 세기는 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 합칠 두 조각이 오름차순이다 | 1단계에서 왼쪽에 남은 칸 수를 한꺼번에 더한다 | 더한 개수가 교차 역순쌍 수와 달라진다 |
| 두 값의 크기를 비교할 수 있다 | 1단계의 비교 한 줄 | 꺼낼 쪽도 더할지도 정하지 못한다 |
| 칸 `N` 개짜리 버퍼를 따로 잡을 수 있다 | 합친 결과를 적는 자리 | 제자리에서 합치는 다른 절차가 필요하다 |

첫 전제가 깨지면 오류 없이 틀린 값이 나옵니다. 1단계의 합치기에 왼쪽이 오름차순이 아닌 조각을 넣어 보았어요.

<!--proof:build-premise-->

| 두 조각 | 왼쪽 조각 | 합치며 센 개수 | 정의대로 센 교차 역순쌍 |
| --- | --- | ---: | ---: |
| [2 5] + [1 3] | 오름차순 | 3 | 3 |
| [5 2] + [1 3] | 오름차순 아님 | 4 | 3 |

<!--/proof-->

`[5 2]` 에서 5 와 1 을 비교하면 오른쪽을 꺼내며 왼쪽에 남은 2 칸을 더하는데, 그 2 칸 중 2 는 1 보다 크지만 3
보다는 작습니다. 3 을 꺼낼 때 다시 2 를 더하면서 없는 쌍 하나를 셌어요. 반대로 값의 범위는 전제가 아닙니다.
크기 비교만 쓰므로 음수든 큰 수든 같은 규칙으로 셉니다.

#### 가운데에서 가르는 까닭

가르는 자리는 답을 바꾸지 않고 비용만 바꿉니다. 같은 입력에 가르는 규칙만 여섯 가지로 바꿔 계수를 재 보았어요.
전개 입력은 칸 여섯이라 규칙마다 계수가 한두 번밖에 안 갈려서, 칸 64 개짜리 입력을 씁니다.

<!--proof:build-split-choice-->

| 가르는 자리 | 답 | 비교 | 옮긴 칸 | 칸 접근 |
| --- | ---: | ---: | ---: | ---: |
| 1 : 1 (반반) | 961 | 318 | 384 | 2,300 |
| 1 : 3 | 961 | 361 | 447 | 2,638 |
| 3 : 1 | 961 | 362 | 447 | 2,640 |
| 1 : 7 | 961 | 451 | 598 | 3,422 |
| 1 칸 : 나머지 | 961 | 1,021 | 2,079 | 10,486 |
| 나머지 : 1 칸 | 961 | 1,112 | 2,079 | 10,668 |

입력은 칸 64 개짜리 A[q] = (q × 37) mod 101 입니다. 여섯 규칙의 답은 모두 같고, 비교와 옮긴 칸과 칸 접근은 규칙마다 다릅니다. 한 칸씩 떼는 규칙의 칸 접근은 반반의 4.6 배입니다.

<!--/proof-->

반반이 비교 · 옮긴 칸 · 칸 접근 모두 가장 적습니다. 한쪽으로 치우칠수록 짧은 쪽이 금방 비고 긴 쪽을 통째로
다시 옮기는 일이 깊이마다 되풀이돼서 옮긴 칸이 늘어요. 임의의
`N` 에서 반반의 최악 비교가 얼마인지는 병합 정렬 가이드의 「수식 정의와 유도」가 닫힌 식으로 풀었고, 비교 횟수가
같으니 이 글은 그 식을 다시 유도하지 않습니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 다섯 걸음이 됩니다.

1. 칸이 하나 이하면 0 을 돌려준다
2. 입력의 사본 `a` 와 칸 `N` 개짜리 버퍼를 한 번 잡는다
3. 조각 `[lo, hi]` 를 `mid` 에서 갈라 두 조각을 같은 절차로 세고 정렬한다
4. 두 조각을 합치며 오른쪽 값을 꺼낼 때마다 `mid − i + 1` 을 더하고, 남은 쪽을 옮긴 뒤 제자리에 적는다
5. 왼쪽 · 오른쪽 · 교차의 합을 돌려준다

### 수행으로 알아보는 알고리즘 — 여섯 칸을 합치기 다섯 번으로 세어 역순쌍 수를 낸다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walk-input-->

```ts
const A = [4, 1, 5, 2, 6, 3];
// 이 절이 끝나면 6 이 나와야 한다
```

`A` 를 왜 이 여섯 칸으로 뒀을까요? 갈래 다섯을 **모두 실행하게** 하려는 것입니다. 합치기 다섯 번 안에 왼쪽을
꺼내는 비교, 오른쪽을 꺼내며 더하는 비교, 왼쪽이 먼저 비는 합치기, 오른쪽이 먼저 비는 합치기가 다 나오고,
마지막 합치기에서는 같은 `i` 에서 오른쪽을 연달아 두 번 꺼내 비교 한 번에 2 를 더하는 자리가 나와요.

```text
countInversions(arr):
    칸이 1 개 이하면 → 0                                        ① 기저
    사본 a 와 buffer 를 한 번씩 잡는다
    sortAndCount(0, N−1) 을 돌려준다

sortAndCount(lo, hi):
    lo >= hi 면 → 0                                             ① 기저
    mid ← (lo + hi) >> 1
    sortAndCount(lo, mid) + sortAndCount(mid+1, hi) + merge(lo, mid, hi)

merge(lo, mid, hi):
    두 조각이 다 남아 있는 동안
        a[i] <= a[j] 면  왼쪽을 buffer 에 옮긴다                 ② 왼쪽이 작거나 같다
        아니면           mid − i + 1 을 더하고 오른쪽을 옮긴다   ③ 오른쪽이 더 작다
    남은 쪽을 그대로 buffer 에 옮긴다                           ④ 한쪽이 비었다
    buffer 의 [lo, hi] 를 a 에 옮겨 적는다                      ⑤ 제자리에 적는다
```

#### 1. 입력을 복사하고 버퍼를 한 번만 잡는다

세는 도중에 배열을 오름차순으로 바꿔야 하는데, 입력 배열은 바꾸지 않기로 했으니 사본이 필요합니다. 그리고
합치기마다 새 배열을 만들면 합치기 수만큼 배열을 잡게 되니, 칸 `N` 개짜리 버퍼를 처음에 하나만 잡고 모든
합치기가 그것을 함께 써요.

```ts
const N = arr.length;
if (N <= 1) return 0;

const a = arr.slice();
const buffer = new Array<number>(N);
```

이 조각을 실행하면 이렇게 나옵니다.

<!--proof:walk-setup-->

```text
N = 6               N <= 1 이 거짓이라 아래로 간다
a = [4 1 5 2 6 3]   입력의 사본이다. arr 는 끝까지 그대로다
buffer = 칸 6 개    아직 아무것도 안 적었다. 모든 합치기가 이것 하나를 쓴다
```

버퍼를 함께 써도 안전한 이유는 재귀의 순서에 있습니다. 어느 순간에도 실행 중인 합치기는 하나뿐이고, 형제
조각은 하나가 완전히 끝난 뒤에 다음이 시작돼요. 그래서 `buffer` 의 `[lo, hi]` 에 적는 동안 다른 합치기가 같은
칸을 쓰는 일이 없습니다.

#### 2. 합치며 오른쪽을 꺼낼 때 왼쪽에 남은 개수를 더한다

합치기의 반복입니다. 병합 정렬의 합치기와 다른 곳은 `else` 쪽의 한 줄뿐이에요. 여기서 `i` 와 `j` 는 **사본
`a` 의 자리**이고, 세는 쌍의 `p` 와 `q` 는 **원래 배열의 자리**입니다. 합치기가 시작될 때 `a[1] = 4` 는 원래
`A[0]` 에서 온 값이에요.

```ts
while (i <= mid && j <= hi) {
  if ((a[i] as number) <= (a[j] as number)) {
    // ② 왼쪽이 작거나 같으면 그대로 옮긴다. 같은 값은 역순쌍이 아니라 여기로 온다.
    buffer[k] = a[i] as number;
    k++;
    i++;
  } else {
    // ③ 오른쪽을 꺼내는 순간, 왼쪽에 아직 안 옮긴 mid - i + 1 개가 전부 이 값보다 크다.
    count += mid - i + 1;
    buffer[k] = a[j] as number;
    k++;
    j++;
  }
}
```

여기서 가장 중요한 줄은 `count += mid - i + 1;` 입니다. 이 줄이 비교 한 번으로 여러 쌍을 세는 자리이고, 이 줄을
빼면 남는 것은 병합 정렬의 합치기예요. 이 반복을 전개 입력의 마지막 합치기에 실행하면 이렇습니다. 왼쪽 조각은
`[1 4 5]`, 오른쪽 조각은 `[2 3 6]` 이고 `mid = 2` 예요.

<!--proof:walk-merge-loop-->

| 비교 | i | j | 조건 판정 | 갈래 | 더한 개수 | 이 합치기의 누적 |
| ---: | ---: | ---: | --- | --- | --- | ---: |
| 1 | 0 | 3 | `1 <= 2` **참** | ② | 0 | 0 |
| 2 | 1 | 3 | `4 <= 2` **거짓** | ③ | 2 − 1 + 1 = 2 | 2 |
| 3 | 1 | 4 | `4 <= 3` **거짓** | ③ | 2 − 1 + 1 = 2 | 4 |
| 4 | 1 | 5 | `4 <= 6` **참** | ② | 0 | 4 |
| 5 | 2 | 5 | `5 <= 6` **참** | ② | 0 | 4 |

비교 5 번 가운데 오른쪽을 꺼낸 것이 2 번이고, 이 합치기가 센 개수는 4 입니다. 반복이 끝난 시점에 오른쪽 조각에 6 이 남아 있습니다.

<!--/proof-->

둘째와 셋째 비교에서 `i` 가 1 에 머물러 있습니다. 오른쪽 값을 꺼낼 때는 `j` 만 늘고 왼쪽 자리는 그대로라, 같은
왼쪽 자리에서 여러 번 더할 수 있어요. 두 번의 비교로 쌍 넷을 셌습니다.

#### 짚고 가기 — 같은 값을 오른쪽으로 보내도 이 입력에서는 답이 안 틀린다

비교를 `a[i] <= a[j]` 로 쓸지 `a[i] < a[j]` 로 쓸지는 사소해 보입니다. 둘 다 오름차순으로 합치기는 하니까요.
그런데 등호가 어느 쪽에 붙느냐가 **같은 값을 역순쌍으로 세는가**를 정합니다. 등호를 떼면 `a[i] === a[j]` 인
순간에도 오른쪽을 꺼내는 갈래로 가고, 거기서 `mid − i + 1` 이 더해져요. 먼저 사실을 적습니다. **전개 입력에서는
답이 안 틀립니다.**

<!--proof:pause-tie-->

| 입력 | 정본 | 같은 값을 오른쪽으로 보낸 판 | 바꾼 줄을 지나간 횟수 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 [4 1 5 2 6 3] | 6 | 6 | 11 | 같다 |
| 칸 두 개가 같은 [2 2] | 0 | 1 | 1 | 어긋난다 |
| 전부 같은 [2 2 2 2] | 0 | 6 | 4 | 어긋난다 |
| 같은 값이 섞인 [3 1 2 3 1] | 5 | 7 | 8 | 어긋난다 |

<!--/proof-->

전개 입력에서는 바꾼 줄을 11 번 지나가는데 답이 그대로입니다. 이 입력에는 같은 값이 없어서 `<=` 와 `<` 의 판정이
갈릴 자리가 아예 없기 때문이에요. 걸음마다 누적을 맞대어 보아도 전부 같습니다.

<!--proof:pause-tie-steps-->

| 걸음 | 정본의 누적 | 같은 값을 오른쪽으로 보낸 판의 누적 | 판정 |
| --- | ---: | ---: | --- |
| T1 | 0 | 0 | 같다 |
| T2 | 1 | 1 | 같다 |
| T3 | 1 | 1 | 같다 |
| T4 | 1 | 1 | 같다 |
| T5 | 2 | 2 | 같다 |
| T6 | 2 | 2 | 같다 |
| T7 | 4 | 4 | 같다 |
| T8 | 6 | 6 | 같다 |
| T9 | 6 | 6 | 같다 |
| T10 | 6 | 6 | 같다 |
| T11 | 6 | 6 | 같다 |

바꾼 줄을 11 번 지나갔고, 11 걸음 가운데 누적이 같은 걸음이 11 개입니다.

<!--/proof-->

그럼에도 등호를 붙이는 이유는 계약입니다. 값이 같은 쌍은 `A[p] > A[q]` 를 만족하지 않으니 역순쌍이 아니에요.
`[2 2]` 에서 정본은 0 을 내고 등호를 뗀 판은 1 을 냅니다. 같은 값이 넷이면 그 넷으로 만들 수 있는 쌍 여섯을
전부 역순쌍으로 셉니다. **확인에 쓰는 입력에 같은 값이 없으면 이 잘못은 끝까지 보이지 않아요.**

#### 짚고 가기 — 오른쪽을 꺼낼 때마다 1 을 더하고 싶어진다

오른쪽 값을 꺼내는 것이 「역순쌍 하나를 찾았다」로 읽히면, 더하는 값을 `mid − i + 1` 대신 1 로 두고 싶어집니다.
그러면 오른쪽 값 하나가 왼쪽의 여러 값과 이루는 쌍 가운데 하나만 세게 돼요. 먼저 사실을 적습니다. **칸 두 개짜리
입력에서는 답이 안 틀립니다.**

<!--proof:pause-plus-one-->

| 입력 | 정본 | 오른쪽마다 1 을 더하는 판 | 바꾼 줄을 지나간 횟수 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 [4 1 5 2 6 3] | 6 | 4 | 4 | 어긋난다 |
| 이미 오름차순 [1 2 3 4 5 6] | 0 | 0 | 0 | 같다 |
| 칸 두 개 [2 1] | 1 | 1 | 1 | 같다 |
| 내림차순 [6 5 4 3 2 1] | 15 | 7 | 7 | 어긋난다 |

<!--/proof-->

`[2 1]` 은 오른쪽을 꺼낼 때 왼쪽에 남은 칸이 늘 하나라 1 을 더해도 같은 값입니다. 이미 오름차순인 입력은 오른쪽을
꺼내는 갈래로 한 번도 안 가서 같아요. 전개 입력에서는 오른쪽을 네 번 꺼내는데 그중 두 번이 왼쪽에 두 칸이 남은
순간이라 6 이 4 로 줍니다. 비교 한 번이 여러 쌍을 정한다는 것이 이 방법의 전부이니, 그 여러 쌍을 하나로 줄이면
정의대로 세는 방법보다도 적게 셉니다.

#### 3. 한쪽이 비면 남은 값을 옮기고 제자리에 적는다

반복은 한쪽 조각이 비는 순간 끝납니다. 남은 쪽의 값은 이미 오름차순이고 1단계에서 본 대로 더할 것이 없으니 그대로
버퍼에 옮기고, 합친 결과를 `a` 의 제자리에 옮겨 적어요. 이 옮겨 적기가 한 층 위의 합치기에 **정렬된 조각**을
넘겨주는 줄입니다.

```ts
// ④ 한쪽이 비면 남은 쪽을 그대로 옮긴다. 여기서는 더 셀 것이 없다.
while (i <= mid) {
  buffer[k] = a[i] as number;
  k++;
  i++;
}
while (j <= hi) {
  buffer[k] = a[j] as number;
  k++;
  j++;
}
// ⑤ 합친 결과를 제자리에 옮겨 적는다. 위 자리가 기대는 전제를 여기서 세운다.
for (let x = lo; x <= hi; x++) a[x] = buffer[x] as number;
return count;
```

전개 입력의 합치기 다섯에서 이 조각이 한 일을 모으면 이렇습니다.

<!--proof:walk-tails-->

| 합치기 | 먼저 빈 쪽 | 비교 없이 옮긴 값 | buffer 에 적은 조각 | 제자리에 적은 뒤 a |
| --- | --- | --- | --- | --- |
| [0,1] | 오른쪽 | 4 | [1 4] | [1 4 5 2 6 3] |
| [0,2] | 왼쪽 | 5 | [1 4 5] | [1 4 5 2 6 3] |
| [3,4] | 왼쪽 | 6 | [2 6] | [1 4 5 2 6 3] |
| [3,5] | 오른쪽 | 6 | [2 3 6] | [1 4 5 2 3 6] |
| [0,5] | 왼쪽 | 6 | [1 2 3 4 5 6] | [1 2 3 4 5 6] |

5 번의 합치기 모두 반복이 끝난 시점에 한쪽 조각에 값이 남았고, 남은 값을 옮기는 동안 더한 개수는 없습니다.

<!--/proof-->

#### 4. 반으로 갈라 아래에서부터 합친다

재귀는 조각을 반으로 가르다가 칸이 하나가 되면 멈춥니다. 칸 하나짜리 조각에는 쌍이 없으니 0 을 내면 되고, 그것이
갈래 ① 이에요. 그 뒤로는 아래에서 위로 합치기가 실행됩니다.

```ts
function sortAndCount(lo: number, hi: number): number {
  // ① 칸이 하나뿐인 조각에는 쌍이 없다.
  if (lo >= hi) return 0;
  const mid = (lo + hi) >> 1;
  let count = sortAndCount(lo, mid);
  count += sortAndCount(mid + 1, hi);
  count += merge(lo, mid, hi);
  return count;
}
```

이 조각을 실행하면 합치기 다섯이 아래 순서로 실행되고, 각각이 센 개수는 이렇습니다.

<!--proof:walk-tree-->

| 합치기 | 왼쪽 조각 | 오른쪽 조각 | 이 합치기가 센 개수 |
| --- | --- | --- | ---: |
| [0,1] | [0,0] | [1,1] | 1 |
| [0,2] | [0,1] | [2,2] | 0 |
| [3,4] | [3,3] | [4,4] | 0 |
| [3,5] | [3,4] | [5,5] | 1 |
| [0,5] | [0,2] | [3,5] | 4 |

합치기가 5 번이고 센 개수를 다 더하면 6 입니다. 정본의 답도 6 입니다.

왼쪽 부름이 끝나야 오른쪽 부름이 시작되고, 두 부름이 끝나야 합치기가 실행됩니다. 그래서 합치기마다 두 조각이 이미
오름차순이에요.

#### 5. 여섯 칸을 처음부터 끝까지 센다

앞의 조각을 이어 `countInversions([4, 1, 5, 2, 6, 3])` 을 실행합니다. 앞 합치기 넷은 합치기 하나를 한 걸음으로,
마지막 합치기는 비교 하나를 한 걸음으로 보였어요. 무대의 `a` 줄은 그 걸음이 끝난 뒤의 사본이고, 합치는 도중인
걸음에서는 정본이 `buffer` 에만 적으므로 `a` 가 그대로입니다. 괄호가 합치는 조각, 그 아래 두 괄호가 왼쪽 조각과
오른쪽 조각, ▲ 가 이번에 비교한 두 칸이에요. `buffer` 줄에는 지금 합치기가 적은 칸만 그렸습니다.

#### 6. 전체 코드

앞에서 본 조각을 한 파일로 이어 붙이면 이렇게 됩니다. 새로 들어간 것은 반복 앞에서 `i` · `j` · `k` · `count` 를
정하는 네 줄과, 가장 바깥에서 `sortAndCount(0, N - 1)` 을 돌려주는 줄뿐이에요.

```ts
export function countInversions(arr: number[]): number {
  const N = arr.length;
  if (N <= 1) return 0;

  const a = arr.slice();
  const buffer = new Array<number>(N);

  function merge(lo: number, mid: number, hi: number): number {
    let i = lo;
    let j = mid + 1;
    let k = lo;
    let count = 0;
    while (i <= mid && j <= hi) {
      if ((a[i] as number) <= (a[j] as number)) {
        // ② 왼쪽이 작거나 같으면 그대로 옮긴다. 같은 값은 역순쌍이 아니라 여기로 온다.
        buffer[k] = a[i] as number;
        k++;
        i++;
      } else {
        // ③ 오른쪽을 꺼내는 순간, 왼쪽에 아직 안 옮긴 mid - i + 1 개가 전부 이 값보다 크다.
        count += mid - i + 1;
        buffer[k] = a[j] as number;
        k++;
        j++;
      }
    }
    // ④ 한쪽이 비면 남은 쪽을 그대로 옮긴다. 여기서는 더 셀 것이 없다.
    while (i <= mid) {
      buffer[k] = a[i] as number;
      k++;
      i++;
    }
    while (j <= hi) {
      buffer[k] = a[j] as number;
      k++;
      j++;
    }
    // ⑤ 합친 결과를 제자리에 옮겨 적는다. 위 자리가 기대는 전제를 여기서 세운다.
    for (let x = lo; x <= hi; x++) a[x] = buffer[x] as number;
    return count;
  }

  function sortAndCount(lo: number, hi: number): number {
    // ① 칸이 하나뿐인 조각에는 쌍이 없다.
    if (lo >= hi) return 0;
    const mid = (lo + hi) >> 1;
    let count = sortAndCount(lo, mid);
    count += sortAndCount(mid + 1, hi);
    count += merge(lo, mid, hi);
    return count;
  }

  return sortAndCount(0, N - 1);
}
```

<!--proof:final-calls-->

```text
countInversions([4, 1, 5, 2, 6, 3])   →   6
countInversions([2, 4, 1, 3, 5])      →   3
countInversions([2, 2, 2])            →   0
countInversions([-1, -3, 0, -2])      →   3
countInversions([42])                 →   0
countInversions([])                   →   0
```

### 알아 두면 좋은 개념 — 켄달 타우 거리

파트 1 이 값으로 낸 `I(A)` 에는 이름이 있습니다. 두 나열이 얼마나 다른가를 **자리 쌍 중 순서가 반대인 것의 개수**로
재는 것을 **켄달 타우 거리**라고 부르고, 이 글의 답은 입력의 나열과 오름차순 나열 사이의 켄달 타우 거리예요. 이
개수를 달리 말하는 방법이 하나 더 있습니다. **이웃한 두 칸만 맞바꿀 수 있을 때 오름차순으로 만드는 데 필요한 최소
맞바꿈 횟수**와 같은 값이에요.

```text
이웃한 두 칸을 맞바꾸면 무엇이 바뀌는가

  … x y …   →   … y x …          x > y 인 이웃한 두 칸이다

  이 두 칸이 이루는 쌍 하나만 역순에서 정순이 된다
  다른 쌍은 두 자리 사이에 낀 칸이 없어 앞뒤 관계가 그대로다
```

맞바꿈 한 번이 역순쌍을 정확히 하나 줄이니, 역순쌍이 0 이 될 때까지 맞바꾼 횟수가 곧 `I(A)` 입니다. 실제로
맞바꾸며 세어 보면 이렇습니다.

<!--proof:kendall-swaps-->

| 배열 | 역순쌍 개수 | 인접 교환으로 정렬한 횟수 | 판정 |
| --- | ---: | ---: | --- |
| [4 1 5 2 6 3] | 6 | 6 | 같다 |
| [1 2 3 4 5 6] | 0 | 0 | 같다 |
| [6 5 4 3 2 1] | 15 | 15 | 같다 |
| [2 2 2 2] | 0 | 0 | 같다 |
| [3 1 2 3 1] | 5 | 5 | 같다 |
| 칸 64 개짜리 생성식 | 961 | 961 | 같다 |

생성식은 A[q] = (q × 37) mod 101 입니다.

<!--/proof-->

이 이름은 이 편 밖에서 다시 나옵니다. 통계에서는 두 순위 목록의 상관을 재는 **켄달 타우 상관 계수**의 분자가 이
값으로 만들어지고, 정렬에서는 삽입 정렬이 옮기는 값의 총수가 곧 `I(A)` 예요. 「자리 쌍 중 반대인 것의 개수」라는 한
문장이 세 자리에서 같은 뜻으로 쓰입니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 세는 값이 왜 빠짐도 겹침도 없는지를 식으로 어떻게
보이는지, 무엇이 매 순간 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

- **답이 「자리 쌍」의 개수이고, 그 쌍의 조건이 두 값의 순서로만 정해질 때.** 역순쌍이 그 전형이고, 조건이
  「`A[p] > 2 × A[q]`」처럼 바뀌어도 같은 골격이 쓰입니다(세는 줄을 비교와 떼어 따로 두어야 합니다).
- **값에 아무 전제가 없을 때.** 값이 실수든 큰 정수든 문자열이든, 두 값을 비교할 수만 있으면 됩니다. 값의 범위를
  미리 알 필요도, 값을 자리 번호로 바꿀 필요도 없어요.
- **한 번 묻고 끝날 때.** 배열이 주어지고 답 하나를 내는 모양입니다. 배열이 자주 바뀌고 그때마다 답을 다시 묻는
  모양이면 전체를 다시 실행해야 해서 이 절차의 자리가 아닙니다.
- **정렬한 결과도 함께 쓸 데가 있을 때.** 이 절차는 세는 김에 오름차순 사본을 만들어 둡니다.

#### 문제에서 이것을 떠올리게 하는 단서

- 지문에 **「순서가 뒤바뀐 쌍」·「무질서한 정도」·「정렬까지 필요한 인접 교환 횟수」** 가 나옵니다.
- 두 사람의 **선호 순위가 얼마나 다른가**를 수치로 요구합니다.
- 「`i < j` 이고 `A[i] > A[j]`」 같은 **두 조건이 함께 걸린 쌍**을 세라고 적혀 있습니다.
- 칸 수가 `10^5` 언저리인데 정의를 그대로 옮기면 `10^10` 규모가 됩니다.
- 답이 「몇 개인가」이고 **그 쌍을 실제로 나열하라고는 하지 않습니다.** 나열까지 요구하면 답의 개수만큼 시간이 드는
  다른 문제예요.

#### 실제로 쓰이는 곳

- **Apache Commons Math 의 `KendallsCorrelation`** — 켄달 타우 상관 계수를 내는 클래스이고, 클래스 주석이
  *"This implementation uses the O(n log n) algorithm described in William R. Knight's 1966 paper"* 라고
  적습니다. 합치기 반복문 안의 누적 줄이 `swaps += iEnd - i;` 인데, `iEnd` 가 왼쪽 조각의 **끝 다음 자리**라 이
  글의 `count += mid - i + 1` 과 같은 값이에요. 1 차 출처는 소스 파일이고
  [commons-math4-legacy 의 `KendallsCorrelation.java`](https://commons.apache.org/proper/commons-math/commons-math4-legacy/apidocs/src-html/org/apache/commons/math4/legacy/stat/correlation/KendallsCorrelation.html)
  에서 확인했습니다(조회일 2026-09-08). 재귀 대신 조각 길이를 1 부터 두 배씩 늘리는 반복으로 적은 것이 이 글과
  다른 점입니다.
- **SciPy 의 `scipy.stats.kendalltau`** — 같은 값을 내는데 **다른 설계를 골랐습니다.** 실제로 세는 함수
  `_kendall_dis` 가 펜윅 트리를 쓰고, 소스의 주석이 그것을 밝힙니다 — *"Use of `>> 14` improves cache
  performance of the Fenwick tree (see gh-10108)"*. 1 차 출처는
  [scipy/stats/_stats.pyx](https://github.com/scipy/scipy/blob/main/scipy/stats/_stats.pyx) 이고 같은 날
  확인했어요. 아래 「경쟁 설계와의 대조」가 두 설계를 같은 잣대로 잽니다.
- **원래 논문**은 Knight, W. R. (1966), *A Computer Method for Calculating Kendall's Tau with Ungrouped Data*,
  Journal of the American Statistical Association 61(314), 436–439 (doi 10.1080/01621459.1966.10480879)입니다.
  **이 원문은 열지 못했습니다** — 출판사 쪽이 접근을 막아 서지 사항과, 위 Apache 소스가 그 논문을 지목한다는
  사실만 확인했습니다.

#### 경쟁 설계와의 대조

경쟁 설계는 **값 범위를 아는 펜윅 트리 판**입니다. 배열을 오른쪽 끝에서 왼쪽으로 지나가며 「지금까지 본 값 중 이
값보다 작은 것이 몇 개인가」를 펜윅 트리에 물어 더해요. 값이 `0` 이상 `V` 미만인 정수라는 것을 **미리 알아야**
트리를 `V + 1` 칸으로 잡을 수 있습니다. 펜윅 트리 자체는
[펜윅 트리 구간 합 가이드](../../array/fenwickRangeSum/fenwickRangeSum-guide.md)가 다룹니다.

| 설계 | 쌍 하나를 세는 방법 | 알아야 하는 것 |
| --- | --- | --- |
| 합치며 세기 | 두 조각이 오름차순일 때 오른쪽 값을 꺼내며 `mid − i + 1` 을 더한다 | 두 값을 비교하는 법 |
| 펜윅 트리 | 자리 `q` 를 오른쪽부터 보며 「이미 본 값 중 `A[q]` 보다 작은 개수」를 묻는다 | 값의 범위 `V` |

**입력은 칸 4,096 개로 고정하고 값 범위 `V` 만 바꿉니다.** 생성식은 `A[q] = (q × 7,919) mod V` 이고 시드도 난수도
없어요. 전개 입력(칸 여섯)을 그대로 안 쓴 이유는 갈림의 축이 값 범위인데 칸이 여섯이면 `V` 를 키워도 두 계수가 안
갈리기 때문입니다. 잣대는 이 글이 처음부터 쓴 **칸 접근**이고, 두 설계에 같은 규칙을 적용합니다. 초기화 쓰기도 넣어서, 합치며 세는
판은 입력을 사본으로 옮기는 `2N` 을, 펜윅 트리 판은 트리 `V + 1` 칸을 0 으로 채우는 쓰기를 셉니다. **추가 칸**은
합치며 세는 판이 사본과 버퍼, 펜윅 트리 판이 트리의 칸 수예요. 입력 배열과 재귀 스택은 넣지 않았습니다.

<!--proof:alt-counts-->

| 값 범위 V | 합치며 세는 판의 칸 접근 | 펜윅 트리 판의 칸 접근 | 칸 접근이 적은 쪽 | 합치며 세는 판의 추가 칸 | 펜윅 트리 판의 추가 칸 |
| ---: | ---: | ---: | --- | ---: | ---: |
| 2 | 276,480 | 18,435 | 펜윅 트리 | 8,192 | 3 |
| 8,191 | 285,962 | 92,050 | 펜윅 트리 | 8,192 | 8,192 |
| 8,192 | 285,860 | 100,346 | 펜윅 트리 | 8,192 | 8,193 |
| 1,048,576 | 277,918 | 1,183,758 | 합치며 세기 | 8,192 | 1,048,577 |

칸 수는 4,096 으로 고정하고 값 범위만 바꿨습니다. 입력은 A[q] = (q × 7,919) mod V 이고 난수도 시드도 없습니다. 값 범위 2 에서는 펜윅 트리 판의 칸 접근이 15.0 배 적고, 값 범위 1,048,576 에서는 합치며 세는 판의 칸 접근이 4.3 배 적습니다.

<!--/proof-->

**두 축이 각각 다른 자리에서 뒤집힙니다.** 추가 칸은 값 범위 8,191 에서 8,192 대 8,192 로 같아지고 8,192 부터 펜윅
쪽이 더 씁니다. 트리가 `V + 1` 칸이고 이쪽은 값 범위와 무관하게 `2N` 칸이니까요. 칸 접근은 그보다 훨씬 뒤에서
갈립니다. 그 자리는 값 범위 2 부터 한 개씩 올리며 처음 뒤집히는 곳을 찾아 정했고, 사이드카는 대조를 빨리 끝내려고
같은 자리를 이진 탐색으로 좁힌 뒤 두 끝을 다시 잽니다.

<!--proof:alt-boundary-->

| 값 범위 V | 합치며 세는 판 | 펜윅 트리 판 | 펜윅 − 합치며 | 칸 접근이 적은 쪽 |
| ---: | ---: | ---: | ---: | --- |
| 173,193 | 287,802 | 287,421 | -381 | 펜윅 트리 |
| 173,194 | 287,796 | 287,899 | 103 | 합치며 세기 |

값 범위 173,194 에서 칸 접근의 순서가 처음 뒤집힙니다. 이진 탐색으로 좁힌 뒤 두 끝을 다시 잰 값입니다.

<!--/proof-->

**내주는 것과 얻는 것을 적어 둡시다.** 값 범위가 173,193 이하이면 칸 접근이 펜윅 쪽이 적고, 값 범위가 좁을수록 그
차이가 커집니다. 그것이 합치며 세기가 **내주는 축**이에요. 얻는 축은 둘입니다. 값 범위가 넓어져도 비용이 거의 안
늘어서 넓은 값 범위에서는 칸 접근이 오히려 적고, **값 범위를 몰라도 됩니다.**

두 번째가 이 과제의 계약에서 무겁습니다. 값이 「음수를 포함한 정수」이고 범위를 미리 모른다고 두었으니, 펜윅 판을
쓰려면 값을 자리 번호로 바꾸는 좌표 압축이 먼저 필요해요. 그 압축은 값을 정렬하는 일이라 **이 절차가 하는 일을 한 번
더 하는 셈**입니다. SciPy 가 펜윅을 고른 것은 `kendalltau` 가 그 앞에서 이미 순위로 바꿔 두기 때문이고, 그때는 값
범위가 곧 칸 수예요. **우열이 반대가 되는 조건**은 그래서 분명합니다. 값이 이미 좁은 범위의 순위로 주어지면 펜윅
트리, 값의 범위를 모르거나 넓으면 합치며 세기입니다.

### 수식 정의와 유도

자리 쌍 $(p, q)$ 가 $p < q$ 와 $A[p] > A[q]$ 를 함께 만족하면 그 쌍이 역순쌍이고, 역순쌍을 원소로 갖는 집합을
$\mathrm{Inv}(A)$, 그 크기를 $I(A)$ 라 합니다. 합치기 $v$ 의 조각을 $[lo_v,\, hi_v]$, 왼쪽 조각의 끝을 $mid_v$ 라 할
때 그 합치기의 교차 역순쌍 집합을 $\mathrm{cross}(v)$ 라 합니다.

$$
I(A) = \bigl|\mathrm{Inv}(A)\bigr|, \qquad \mathrm{Inv}(A) = \{(p, q) : 0 \le p < q \le N-1,\ A[p] > A[q]\}
$$

$$
\mathrm{cross}(v) = \{(p, q) \in \mathrm{Inv}(A) : lo_v \le p \le mid_v < q \le hi_v\}
$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $v$ | 합치기 하나. 조각 $[lo_v,\, hi_v]$ 와 $mid_v$ 를 갖는다 | 합치기는 $N-1$ 개 |
| $\ell$ · $r$ | 합치기 $v$ 의 왼쪽 조각과 오른쪽 조각의 칸 수 | $\ell + r = hi_v - lo_v + 1$ |
| $x_u$ · $y_w$ | 합치기가 시작될 때 두 조각의 값을 오름차순으로 적은 것 | $0 \le u < \ell$, $0 \le w < r$ |
| $u_w$ | $y_w$ 를 꺼낼 때까지 꺼낸 왼쪽 값의 수 | $0 \le u_w \le \ell$ |

**첫 식은 두 가지를 주장합니다.** 역순쌍마다 그 쌍을 담는 $\mathrm{cross}(v)$ 가 있고, 그런 $v$ 가 하나뿐이라는
것입니다. 그러면 모든 $\mathrm{cross}(v)$ 가 $\mathrm{Inv}(A)$ 의 분할이 되어 다음이 성립합니다.

$$
I(A) = \sum_{v} \bigl|\mathrm{cross}(v)\bigr|
$$

역순쌍 $(p, q)$ 를 하나 잡고 뿌리 조각 $[0,\, N-1]$ 에서 내려갑니다. 두 자리를 다 담은 조각은 칸이 둘 이상이라
합치기 $v$ 를 갖고, 그 $mid_v$ 에 대해 셋 중 하나가 참이에요.

| 조건 | 두 자리가 있는 곳 | 다음 |
| --- | --- | --- |
| $q \le mid_v$ | 둘 다 왼쪽 조각 | 왼쪽 조각으로 내려간다 |
| $mid_v < p$ | 둘 다 오른쪽 조각 | 오른쪽 조각으로 내려간다 |
| $p \le mid_v < q$ | 갈라진다 | 이 $v$ 의 $\mathrm{cross}(v)$ 에 든다 |

앞의 두 줄은 조각의 칸 수를 줄입니다. 칸이 하나인 조각은 서로 다른 두 자리를 담을 수 없으니, 내려가기는 칸 수가
줄어드는 동안 반드시 셋째 줄에서 멈춰요. 멈춘 $v$ 가 하나뿐인 이유는 둘입니다. 그 위의 조각들에서는 첫째나 둘째
줄이 참이었으니 두 자리가 같은 쪽에 있어 교차가 아니고, 그 아래의 조각은 두 자리를 함께 담지 않아요. 전개 입력의
역순쌍마다 내려간 길을 따라가면 이렇습니다.

<!--proof:math-pairs-->

| 역순쌍 | 값 | 내려간 길 | 멈춘 합치기 v |
| --- | --- | --- | --- |
| (0, 1) | 4 > 1 | [0,5] 에서 왼쪽 → [0,2] 에서 왼쪽 | [0,1] |
| (0, 3) | 4 > 2 | 바로 멈춤 | [0,5] |
| (0, 5) | 4 > 3 | 바로 멈춤 | [0,5] |
| (2, 3) | 5 > 2 | 바로 멈춤 | [0,5] |
| (2, 5) | 5 > 3 | 바로 멈춤 | [0,5] |
| (4, 5) | 6 > 3 | [0,5] 에서 오른쪽 | [3,5] |

역순쌍 6 개가 모두 합치기 하나에서 멈췄고, 합치기 [0,1] · [0,2] · [3,4] · [3,5] · [0,5] 의 |cross(v)| 는 차례로 1 · 0 · 0 · 1 · 4 입니다.

<!--/proof-->

**둘째 걸음은 합치기 하나가 $|\mathrm{cross}(v)|$ 를 어떻게 내는가입니다.** 조각 안의 값을 오름차순으로 다시
놓아도 두 조각의 값 모임은 그대로이고, 짝의 조건이 두 값의 크기뿐이라 개수도 그대로예요. 그래서 세려는 것은
왼쪽에서 하나, 오른쪽에서 하나를 골라 왼쪽이 더 큰 짝의 수입니다.

$$
\bigl|\mathrm{cross}(v)\bigr| = \bigl|\{(u, w) : x_u > y_w\}\bigr| = \sum_{w=0}^{r-1} \bigl(\ell - u_w\bigr)
$$

두 번째 등호의 근거는 이렇습니다. $y_w$ 를 꺼낼 때 이미 꺼낸 왼쪽 값 $u_w$ 개는 그 전에 오른쪽 머리와 비교해
작거나 같다고 판정됐고, 그 오른쪽 머리는 $y_w$ 이하라 $x_u \le y_w$ 입니다. 아직 안 꺼낸 $\ell - u_w$ 개는
$x_{u_w}$ 이상인데 $y_w$ 를 꺼냈다는 것은 $x_{u_w} > y_w$ 라는 뜻이라 전부 $y_w$ 보다 커요. 왼쪽을 다 꺼낸 뒤에
옮기는 $y_w$ 는 $u_w = \ell$ 이라 0 을 더합니다. 전개 입력의 마지막 합치기에 넣으면 이렇습니다.

<!--proof:math-uw-->

| w | y_w | u_w | ℓ − u_w |
| ---: | ---: | ---: | --- |
| 0 | 2 | 1 | 3 − 1 = 2 |
| 1 | 3 | 1 | 3 − 1 = 2 |
| 2 | 6 | 3 | 3 − 3 = 0 |

합치기 [0,5] 에서 ℓ = 3 이고, ℓ − u_w 를 다 더하면 4 가 되어 |cross(v)| = 4 와 같습니다.

<!--/proof-->

코드는 $\ell - u_w$ 를 왼쪽 조각의 끝 자리 `mid` 와 다음에 볼 자리 `i` 로 적습니다. $\ell = mid - lo + 1$ 이고
$u_w = i - lo$ 라서 둘의 차가 `mid - i + 1` 이에요.

```ts
// ℓ − u_w = (mid − lo + 1) − (i − lo) = mid − i + 1
count += mid - i + 1;
```

**마지막으로 계수입니다.** 답이 가장 큰 경우는 모든 쌍이 역순인 강한 내림차순이고 그때 $I(A) = N(N-1)/2$ 입니다.
과제 규모를 넣으면 답이 배정밀도 정수로 정확히 표현되는지가 정해져요.

<!--proof:math-limit-->

| 칸 수 N | N(N−1)/2 | 2^53 과의 크기 |
| ---: | ---: | --- |
| 100,000 | 4,999,950,000 | 이하 |
| 134,217,727 | 9,007,199,053,414,401 | 이하 |
| 134,217,728 | 9,007,199,187,632,128 | 이하 |
| 134,217,729 | 9,007,199,321,849,856 | 초과 |

2^53 = 9,007,199,254,740,992 이고 2^27 = 134,217,728 입니다. 과제 규모의 상한 N = 100,000 에서 답의 상한은 4,999,950,000 이고, 이 값에 1,801,457 을 곱해야 2^53 에 이릅니다.

<!--/proof-->

한계는 정확히 $2^{27}$ 입니다. $N(N-1)/2 \le 2^{53}$ 을 풀면 $N^2 - N - 2^{54} \le 0$ 이고, 근의 공식으로
$N \le \bigl(1 + \sqrt{1 + 2^{56}}\bigr)/2$ 입니다. $\sqrt{1 + 2^{56}}$ 은 $2^{28}$ 보다 아주 조금 크니 오른쪽 값이
$2^{27} + 1/2$ 을 조금 넘고, 정수 상한이 $2^{27}$ 이에요. 실행이 낸 첫 넘는 자리 $2^{27} + 1$ 과 맞습니다. 과제 규모의
상한 10 만은 그 한계보다 한참 작아서 정수 표현을 걱정할 필요가 없습니다.

### 불변식 — `sortAndCount(lo, hi)` 가 돌아올 때 그 조각은 오름차순이고 반환값은 원래 그 조각 안 역순쌍의 개수다

**언제 참인지를 먼저 못 박습니다.** `sortAndCount(lo, hi)` 가 값을 돌려주는 그 시점입니다. 그 시점에 둘이 함께
참이에요. 「놓임」은 `a` 의 `[lo, hi]` 가 원래 그 자리에 있던 값들을 오름차순으로 다시 놓은 것이라는 뜻이고,
「셈」은 반환값이 원래 `arr` 의 `[lo, hi]` 안 역순쌍 개수와 같다는 뜻입니다.

**둘은 따로 성립하지 않습니다.** 「셈」을 내는 합치기가 두 조각의 「놓임」을 전제로 하고, 「놓임」을 만드는 것도
그 합치기이기 때문이에요. 조각 크기에 대한 귀납으로 봅니다. 기저는 칸이 하나인 조각입니다. 값 하나라 이미
오름차순이고 쌍이 없으니 0 이 맞아요. 단계는 칸이 둘 이상인 조각입니다. 두 부름은 각각 더 작은 조각이라 귀납
가정으로 둘 다 참이고, 합치기의 갈래마다 둘이 이렇게 유지됩니다.

| 갈래 | 놓임이 유지되는 이유 | 셈이 유지되는 이유 |
| --- | --- | --- |
| 왼쪽을 꺼낸다 | 꺼낸 값이 남은 값 중 가장 작다 | 그 값과 이미 꺼낸 오른쪽 값은 역순이 아니라 0 을 더한다 |
| 오른쪽을 꺼내며 더한다 | 같은 이유로 오름차순이 이어진다 | 왼쪽에 남은 `mid − i + 1` 개가 전부 그 값보다 크다 |
| 남은 쪽을 그대로 옮긴다 | 남은 쪽이 이미 오름차순이고 전부 끝값 이상이다 | 짝지을 상대가 남지 않아 0 을 더한다 |
| 제자리에 옮겨 적는다 | `a` 의 `[lo, hi]` 가 `buffer` 와 같아진다 | 값은 안 바뀌고 자리만 정리된다 |

셈이 유지되면 반환값은 왼쪽 조각 안 · 오른쪽 조각 안 · 교차 역순쌍의 합이고, 셋이 원래 조각 안의 역순쌍을 빠짐도
겹침도 없이 나누므로 조각 안 역순쌍의 개수와 같습니다. **엣지 케이스는 이 자리에서 함께 봅니다.** 빈 배열과 칸
하나짜리 배열은 합치기가 한 번도 없어 0 을 그대로 내고, 칸 둘은 합치기 한 번으로 끝나며, 값이 전부 같은 배열은
비교가 늘 참이라 더하는 갈래로 안 갑니다. 합치기가 끝날 때마다 두 조건을 실행이 판정하면 이렇게 나와요.

<!--proof:inv-holds-->

| 입력 | 판정한 합치기 | 어긋난 합치기 | 답 |
| --- | ---: | ---: | ---: |
| 빈 배열 | 0 | 0 | 0 |
| 칸 하나 [42] | 0 | 0 | 0 |
| 칸 둘 오름 [1 2] | 1 | 0 | 0 |
| 칸 둘 내림 [2 1] | 1 | 0 | 1 |
| 전부 같은 [2 2 2] | 2 | 0 | 0 |
| 전개 입력 [4 1 5 2 6 3] | 5 | 0 | 6 |
| 음수가 섞인 [-1 -3 0 -2] | 3 | 0 | 3 |
| 칸 64 개 생성식 | 63 | 0 | 961 |

합치기가 끝날 때마다 그 조각이 오름차순인지와, 그 부름이 낸 값이 원래 배열의 그 조각 안 역순쌍 수와 같은지를 함께 보았습니다.

<!--/proof-->

**이제 깨뜨려 봅시다.** 「놓임」을 지키는 줄은 합친 결과를 제자리에 옮겨 적는 줄 하나입니다. 그 줄을 지우면 `a` 의
그 조각이 합치기 전 상태로 남고, 위쪽 합치기는 「두 조각이 오름차순이다」라는 전제가 깨진 채로 `mid − i + 1` 을
더해요.

```ts
for (let x = lo; x <= hi; x++) a[x] = buffer[x] as number; // ← 이 줄을 지웠다
```

<!--proof:inv-mutant-->

| 입력 | 정본 | 제자리에 안 적는 판 | 지운 줄을 지나간 횟수 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 [4 1 5 2 6 3] | 6 | 5 | 16 | 어긋난다 |
| 음수가 섞인 [-1 -3 0 -2] | 3 | 2 | 8 | 어긋난다 |
| 칸 두 개 [2 1] | 1 | 1 | 2 | 같다 |
| 칸 네 개 [4 3 2 1] | 6 | 6 | 8 | 같다 |

<!--/proof-->

**아래 두 줄이 이 절의 이유입니다.** 답이 같아서 통과해 버리는 입력이 실제로 있어요. `[2 1]` 과 `[4 3 2 1]` 에서는
지운 판도 정답을 냅니다. 그래서 답이 아니라 **불변식을 봐야** 잘못이 확인돼요.

<!--proof:inv-mutant-steps-->

| 입력 | 합치기 수 | 정본에서 오름차순이 아닌 조각 | 지운 판에서 오름차순이 아닌 조각 | 답 |
| --- | ---: | ---: | ---: | ---: |
| 칸 두 개 [2 1] | 1 | 0 | 1 | 1 |
| 칸 네 개 [4 3 2 1] | 3 | 0 | 3 | 6 |

두 입력 모두 지운 판에서는 합치기가 끝난 조각이 하나도 오름차순이 아닙니다.

<!--/proof-->

`[4 3 2 1]` 에서 답이 우연히 맞는 까닭은 이렇습니다. 모든 쌍이 역순이라 합치기마다 오른쪽 값이 먼저 꺼내지고, 그때
왼쪽에 남은 칸 수가 조각이 정렬돼 있든 아니든 같은 값이 되기 때문이에요. 전개 입력에서는 그 우연이 안 일어나 6 이
5 로 줍니다.

### 비용 계산

#### 비용을 세는 과정

세는 대상은 처음부터 쓴 **칸 접근**입니다. 항이 셋이에요. 입력을 사본으로 옮기는 데 `2N`, 비교마다 두 칸을
읽으므로 `2C`, 그리고 합치기가 값 하나를 옮길 때마다 `buffer` 에 적으며 두 칸(읽기 하나 · 쓰기 하나), 제자리에 옮겨
적으며 두 칸이라 `4M` 입니다. 전개의 걸음마다 세면 이렇습니다.

<!--proof:perf-derive-->

| 걸음 | 조각 | 조각 길이 | 비교 | 칸 접근 |
| --- | --- | ---: | ---: | --- |
| T1 | 사본 | — | 0 | 2 × 6 = 12 |
| T2 | [0,1] | 2 | 1 | 2 × 1 + 4 × 2 = 10 |
| T3 | [0,2] | 3 | 2 | 2 × 2 + 4 × 3 = 16 |
| T4 | [3,4] | 2 | 1 | 2 × 1 + 4 × 2 = 10 |
| T5 | [3,5] | 3 | 2 | 2 × 2 + 4 × 3 = 16 |
| T6~T11 | [0,5] | 6 | 5 | 2 × 5 + 4 × 6 = 34 |

걸음마다 더하면 칸 접근이 98 이고, 값만 세는 판으로 실제로 센 칸 접근도 98 입니다.

<!--/proof-->

T2 · T3 · T4 · T5 는 합치기 하나가 한 걸음이고, T6~T11 이 마지막 합치기 하나예요. 합치기마다 `2 × 비교 + 4 × 조각 길이`
이고 앞에 사본의 `2N` 이 붙으니, 전체는 이 식입니다.

$$
\text{칸 접근} = 2N + 2C + 4M
$$

<!--proof:perf-closed-->

| 입력 | 칸 수 N | 비교 C | 옮긴 칸 M | 실측 칸 접근 | 2N + 2C + 4M | 판정 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| 전개 입력 | 6 | 11 | 16 | 98 | 98 | 같다 |
| 칸 64 개 생성식 | 64 | 318 | 384 | 2,300 | 2,300 | 같다 |
| 칸 1,024 개 오름차순 | 1,024 | 5,120 | 10,240 | 53,248 | 53,248 | 같다 |
| 칸 1,024 개 내림차순 | 1,024 | 5,120 | 10,240 | 53,248 | 53,248 | 같다 |
| 칸 1,024 개 번갈아 꺼내지는 입력 | 1,024 | 9,217 | 10,240 | 61,442 | 61,442 | 같다 |
| 칸 100,000 개 내림차순 | 100,000 | 815,024 | 1,668,928 | 8,505,760 | 8,505,760 | 같다 |
| 칸 100,000 개 번갈아 꺼내지는 입력 | 100,000 | 1,568,929 | 1,668,928 | 10,013,570 | 10,013,570 | 같다 |

옮긴 칸 M 은 합치기마다의 조각 길이를 다 더한 값이고, 칸 수가 같으면 입력이 달라도 같습니다.

<!--/proof-->

**`M` 은 입력에 안 매입니다.** 조각을 어떻게 가르는지가 입력이 아니라 칸 수만으로 정해지기 때문이에요. 칸 수가 2 의
거듭제곱이면 깊이가 정확히 $\log_2 N$ 이고 깊이마다 모든 칸을 한 번씩 옮기니 $M = N \log_2 N$ 이고, 칸 1,024 개에서
10,240 이 그 값입니다. 그래서 입력에 따라 갈리는 것은 `C` 하나뿐이에요.

#### 케이스별 비용과 그 경계

**케이스 축과 경계 축을 따로 둡니다.** 앞은 어떤 입력인가이고, 뒤는 그 입력에서 상한만 아는가 아니면 정확한 값까지
아는가예요. 가르는 자리가 $mid_v = \lfloor (lo_v + hi_v)/2 \rfloor$ 라 왼쪽 조각이 오른쪽보다 짧지 않아서
($\ell_v \ge r_v$), $\sum_v r_v$ 가 작은 쪽의 합이고 $\sum_v \ell_v$ 가 큰 쪽의 합입니다. 비교는 합치기마다 작은
쪽의 칸 수 이상이고(작은 쪽을 다 꺼내야 한쪽이 빈다) 조각 길이보다 작습니다(한쪽이 비는 순간 다른 쪽에 한 칸 이상이
남는다).

| 케이스 | 비교 `C` | 칸 접근 | 경계의 종류 |
| --- | --- | --- | --- |
| 어떤 입력이든 | $\sum_v r_v \le C \le M - (N-1)$ | $2N + 2C + 4M$ | 양 끝 다 실제로 나오는 **정확한 값** |
| 이미 오름차순 | $C = \sum_v \ell_v$ — 왼쪽 조각을 먼저 다 꺼낸다 | 위 식에 그 `C` 를 넣는다 | 정확한 값 |
| 완전한 내림차순 | $C = \sum_v r_v$ — 하한과 같다 | 위 식에 그 `C` 를 넣는다 | 정확한 값 |
| 점근 표기로 | $\Theta(N \log N)$ | $\Theta(N \log N)$ | 위아래가 같은 차수라 **타이트한 값** |

<!--proof:perf-bounds-->

| 칸 수 N | Σ 작은 쪽 | Σ 큰 쪽 | 이미 오름차순 | 완전한 내림차순 | 번갈아 꺼내지는 입력 | 상한 M − (N−1) |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 12 | 12 | 12 | 12 | 17 | 17 |
| 64 | 192 | 192 | 192 | 192 | 321 | 321 |
| 1,024 | 5,120 | 5,120 | 5,120 | 5,120 | 9,217 | 9,217 |
| 100,000 | 815,024 | 853,904 | 853,904 | 815,024 | 1,568,929 | 1,568,929 |

네 칸 수 모두에서 이미 오름차순은 Σ 큰 쪽과, 완전한 내림차순은 Σ 작은 쪽과, 번갈아 꺼내지는 입력은 상한과 같습니다. 칸 100,000 개의 최악 비교 1,568,929 는 병합 정렬 가이드의 닫힌 식이 내는 1,568,929 와 같고, 두 편 모두 값 둘을 한 번 비교한 것을 1 로 세는 같은 잣대로 셌습니다.

<!--/proof-->

**이 글이 보장하는 것은 최악의 값입니다.** 이 절차에는 난수가 없고 가르는 자리도 칸 수만으로 정해지니 같은 입력에는
언제나 같은 계수가 나와요. 「평균」을 말하려면 입력 분포를 정해야 하는데 이 과제의 계약에 분포가 없으므로, 이 글이
내는 것은 **모든 입력에서 성립하는 하한과 상한**이고 어떤 분포에 대한 기댓값이 아닙니다. 상한 `M − (N−1)` 은 병합
정렬 가이드가 닫은 최악 비교 `N⌈log₂ N⌉ − 2^⌈log₂ N⌉ + 1` 과 같은 값이에요. 두 편이 같은 잣대로 센 비교라서 위 표의 값을 그 편의 값과 그대로 이어 볼 수 있고, 이 글의 칸 접근은 그 비교 `C` 를 `2N + 2C + 4M` 에 넣어 얻습니다.

**총식을 한 번 정확히 적어 둡니다.** 칸 접근의 최솟값은 $2N + 2\sum_v r_v + 4M$ 이고 최댓값은
$2N + 2(M - N + 1) + 4M$ 입니다. 칸 10 만이면 「비용을 세는 과정」의 표에 나온 대로 각각 8,505,760 과 10,013,570
이에요. 여기에 추가 칸이 사본 `N` 개와 버퍼 `N` 개로 `2N` 이고, 재귀가 쓰는 자리가 깊이만큼이라
$\lceil \log_2 N \rceil + 1$ 입니다.

#### 최악을 만드는 입력

**내림차순이 최악이라는 통념은 여기서 안 맞습니다.** 답이 가장 커지는 입력과 비용이 가장 커지는 입력이 다르거든요.
내림차순은 답을 최대로 만들지만 비교는 오히려 **가장 적습니다**. 합치기마다 오른쪽 조각의 값이 전부 왼쪽보다 작아서,
오른쪽을 다 꺼내고 나면 왼쪽은 비교 없이 그대로 옮겨지니까요.

비교를 최대로 만들려면 합치기마다 두 조각에서 **번갈아 꺼내지게** 해야 합니다. 그러면 한쪽이 비는 순간이 마지막 값
하나를 남길 때라 비교가 조각 길이보다 1 적어요. 그런 입력은 결과에서 거꾸로 만듭니다. 오름차순 나열을 조각마다 짝수
번째와 홀수 번째로 갈라 내려가면 돼요.

<!--proof:perf-worst-build-->

```text
만들고 싶은 결과   [0 1 2 3 4 5 6 7]
1 번 가른 뒤       [0 2 4 6] [1 3 5 7]
2 번 가른 뒤       [0 4] [2 6] [1 5] [3 7]
3 번 가른 뒤       [0] [4] [2] [6] [1] [5] [3] [7]
이어 붙인 입력     [0 4 2 6 1 5 3 7]
```

칸 64 개에서 세 입력을 나란히 재면 이렇습니다.

<!--proof:perf-worst-->

| 입력 | 앞 여섯 칸 | 답 | 비교 | 칸 접근 |
| --- | --- | ---: | ---: | ---: |
| 이미 오름차순 | 0 1 2 3 4 5 … | 0 | 192 | 2,048 |
| 완전한 내림차순 | 63 62 61 60 59 58 … | 2,016 | 192 | 2,048 |
| 번갈아 꺼내지게 만든 것 | 0 32 16 48 8 40 … | 912 | 321 | 2,306 |

칸 64 개에서 비교의 상한은 321 이고 만든 입력이 그 값을 냅니다. 완전한 내림차순의 비교 192 는 하한 192 와 같고, 답의 최댓값 2,016 은 완전한 내림차순이 냅니다.

<!--/proof-->

**비용이 가장 큰 입력과 답이 가장 큰 입력이 서로 다릅니다.** 만든 입력은 비교가 상한에 이르지만 답은 최댓값의 절반이
안 되고, 답이 최대인 내림차순은 비교가 하한이에요.

### 스스로 점검하기

역순쌍은 자리 쌍의 성질이라 값을 먼저 정렬해 버리면 사라집니다. 그래서 정렬하는 일과 세는 일을 병합 정렬의 합치기
안에서 함께 하고, 쌍은 **두 자리가 처음 갈라지는 합치기**에서 정확히 한 번 세어져요. 오른쪽 값을 꺼내는 순간 왼쪽에
남은 칸 수를 더하는 한 줄이 그 세기의 전부입니다.

```text
무엇을 세는가     p < q 이고 A[p] > A[q] 인 자리 쌍
어디서 세는가     두 자리가 처음 갈라지는 합치기 하나에서
어떻게 세는가     오른쪽 값을 꺼낼 때 mid − i + 1 을 더한다
왜 맞는가         두 조각이 오름차순이라 안 꺼낸 왼쪽 값이 전부 그 값보다 크다
얼마나 드는가     칸 접근 2N + 2C + 4M 이고 C 만 입력에 매인다
```

먼저 답이 붙는 문제입니다. 전개의 T7 에서 `mid − i + 1` 이 2 였어요. T8 에서도 2 인데, `j` 는 한 칸 옮겨 갔는데 왜
더하는 값이 안 바뀔까요?

<!--check:c1-->
답: 더하는 값은 `i` 와 `mid` 로만 정해지고 `j` 와 무관하기 때문입니다. 오른쪽 값을 꺼내면 `j` 만 1 늘고 `i` 는
그대로라, 같은 왼쪽 자리에서 연달아 꺼내는 동안은 `mid − i + 1` 이 같은 값으로 남습니다.

<!--proof:selfcheck-ij-->

| 걸음 | 비교 전 i | 비교 전 j | 판정 | 더한 개수 |
| --- | ---: | ---: | --- | ---: |
| T6 | 0 | 3 | 1 <= 2 참 | 0 |
| T7 | 1 | 3 | 4 <= 2 거짓 | 2 |
| T8 | 1 | 4 | 4 <= 3 거짓 | 2 |

<!--/proof-->
<!--/check-->

하나 더 볼까요? 「빈 배열과 칸 하나짜리 배열에서 답이 0 이다」를 코드의 어느 줄이 보장할까요?

<!--check:c2-->
답: 함수 머리의 한 줄입니다.

```ts
if (N <= 1) return 0;
```

그 줄이 없어도 `sortAndCount(0, N - 1)` 의 첫 조건 `lo >= hi` 가 참이라
0 이 나오지만, 빈 배열이면 `hi` 가 `-1` 이 되어 조각의 뜻이 성립하지 않고 쓰지도 않을 버퍼를 잡는 일도 그대로
남습니다. 계약을 그 자리에서 끝내는 것이 이 줄의 직무예요.
<!--/check-->

### 역순쌍 개수 세기

풀 파일: [`countInversions.ts`](./countInversions.ts) · 테스트: [`countInversions.test.ts`](./countInversions.test.ts) · 실행: `bun test src/algorithms/advanced/countInversions/countInversions.test.ts`

#### 한 줄 요약

> 배열을 받아 앞 원소가 뒤 원소보다 큰 쌍 $(i, j)$의 개수를 반환한다.

#### 스토리

도서관 사서 민준은 반납된 책들이 제자리에 꽂혀있는지 확인하는 일을 맡았다. 책들은 일련번호 순서대로 정렬되어야 하는데, 손님이 책을 뺐다 꽂는 과정에서 순서가 뒤섞인다.

민준은 선반 위 책들을 왼쪽에서 오른쪽으로 훑으며 "이 책보다 앞에 있는데 일련번호가 더 큰 쌍"이 몇 쌍인지 셈으로써 선반이 얼마나 무질서해졌는지를 수치화하려 한다.

이 수치가 0이면 완벽히 정렬된 상태, 클수록 더 뒤섞인 상태를 의미한다. 책 수가 수십만 권에 달해도 빠르게 계산할 수 있어야 한다.

#### 함수 인터페이스

```ts
export function countInversions(arr: number[]): number;
```

- `arr` — 정수 배열
- 반환 — $i < j$이고 $arr[i] > arr[j]$를 만족하는 쌍 $(i, j)$의 개수

#### 제약 조건

- $0 \leq n \leq 10^5$ (여기서 $n$은 `arr`의 길이)
- `arr`의 원소는 정수 (음수 포함 가능)
- 반환값은 $\geq 0$
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

길이 $n$인 정수 배열 $A$가 주어졌을 때, 다음 조건을 동시에 만족하는 쌍 $(i, j)$의 개수를 반환하라.

$$\text{countInversions}(A) = \left|\, \{ (i, j) \;\mid\; 0 \leq i < j < n,\; A[i] > A[j] \} \,\right|$$

- 같은 값끼리($A[i] = A[j]$)는 역순쌍으로 세지 않는다.
- 빈 배열이나 길이 1인 배열은 역순쌍이 존재하지 않으므로 0을 반환한다.

#### 예시

```ts
countInversions([1, 2, 3]);       // 0 — 오름차순으로 역순쌍 없음
countInversions([3, 2, 1]);       // 3 — (3,2), (3,1), (2,1)
countInversions([2, 4, 1, 3, 5]); // 3 — (2,1), (4,1), (4,3)

// 경계 케이스
countInversions([]);              // 0 — 빈 배열
countInversions([42]);            // 0 — 원소 하나
countInversions([2, 2, 2]);       // 0 — 같은 값은 역순쌍이 아님
countInversions([-1, -3, 0, -2]); // 3 — (-1,-3), (-1,-2), (0,-2)
```
