# trie — 같은 앞부분을 한 번만 저장하면 조회가 담긴 단어의 개수를 안 보게 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 단어를 목록에 담고 매번
대조하는 방법에서 글자마다 갈래를 하나씩 만드는 방법까지 가는 경로를 따라갑니다. 마지막에는
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

소문자 단어를 담아 두고 두 가지를 각각 답하는 자료구조를 만드는 문제예요. 하나는 **그 문자열이
담긴 단어인가**(`search`)이고, 다른 하나는 **그 문자열로 시작하는 단어가 하나라도 있는가**
(`startsWith`)입니다. 두 질문이 다르다는 것이 이 문제의 출발점이에요.

```text
사전에 담긴 단어    app   apple   ape

  search("app")        참     담긴 단어 그 자체다
  search("appl")       거짓   담긴 적이 없는 문자열이다
  startsWith("appl")   참     apple 이 이 네 글자로 시작한다
  startsWith("bat")    거짓   b 로 시작하는 단어가 하나도 없다
└ 둘째 줄과 셋째 줄이 이 문제의 요점이다 — 같은 문자열 appl 에 두 연산의 답이 갈린다
```

가장 먼저 떠오르는 방법은 단어를 배열에 그대로 담고 물을 때마다 전부 대조하는 것입니다. 그런데
제약이 **연산 하나가 받은 문자열의 길이에만 비례할 것**을 요구해요. 담긴 단어의 길이 합이
100,000 까지 갈 수 있으니 목록 대조는 그 요구를 못 맞춥니다.

```text
조회 하나를 목록 대조로 답하면
  단어를 하나씩 꺼낸다            담긴 단어의 개수만큼
  단어마다 앞에서부터 대조한다    어긋나는 자리까지
  길이 합 100,000 짜리 사전이면   조회 하나가 최대 100,000 글자
  조회가 100,000 번이면           100 억 글자
└ 제약이 요구하는 것은 조회 하나가 받은 문자열의 길이에만 비례하는 것이다
```

무엇이 되풀이되는지 봅시다. `app` · `apple` · `ape` 를 각각 적어 두면 같은 `a` 를 세 번,
같은 `ap` 를 세 번 적게 돼요. 대조할 때도 그 세 번을 각각 다시 읽습니다.

```text
같은 앞부분이 몇 번 적히는가
  app     a p p
  apple   a p p l e
  ape     a p e
└ a 가 세 번, a p 가 세 번, a p p 가 두 번 적힌다. 글자 11 개가 자리 6 개로 줄어든다
```

여기서 **같은 앞부분을 한 자리에만 적습니다.** 뿌리에서 시작해 글자 하나마다 갈래를 하나씩
만들면, 어떤 노드까지의 경로가 만드는 문자열이 곧 담긴 단어들의 **접두사** 하나가 돼요.
`app` 과 `apple` 은 세 글자를 지나서야 갈라지고, `ape` 는 두 글자를 지나서 갈라집니다.

```text
(root)
`-- a
    `-- p
        +-- p*
        |   `-- l
        |       `-- e*
        `-- e*
```

`*` 는 **단어 끝 표시**입니다. 노드가 있다는 것과 그 노드가 담긴 단어라는 것은 다른 이야기라,
표시 한 칸을 따로 둬요. 그 한 칸이 두 연산을 가릅니다 — `startsWith` 는 도착했는가만 보고,
`search` 는 도착한 노드의 표시까지 봅니다.

| 문자열 | 그 경로의 노드 | 끝 표시 | `search` | `startsWith` |
| --- | --- | --- | --- | --- |
| `app` | 있다 | 있다 | 참 | 참 |
| `appl` | 있다 | 없다 | 거짓 | 참 |
| `apple` | 있다 | 있다 | 참 | 참 |
| `apz` | 없다 | - | 거짓 | 거짓 |
| `bat` | 없다 | - | 거짓 | 거짓 |

이렇게 하면 연산 하나가 하는 일이 **받은 문자열의 글자 수**로 정해집니다. 글자를 하나 읽을
때마다 노드를 한 칸 내려가고, 담긴 단어가 열 개든 만 개든 그 걸음 수가 같아요. 시간은 문자열
길이 `L` 에 비례하는 `O(L)` 이고, 잡는 칸은 노드 수에 비례합니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **접두사가 무엇인지.** 문자열의 앞에서부터 잘라 낸 조각입니다. `apple` 의 접두사는 빈
  문자열 · `a` · `ap` · `app` · `appl` · `apple` 여섯이에요.
- **키로 값을 찾는 표(맵)를 쓰는 법.** 여기서는 글자 하나를 키로 두고 자식 노드를 값으로
  담습니다. 항목 하나를 넣고 꺼내는 데 드는 일이 표에 담긴 항목 수와 상관없다는 것이 필요해요.
- **참조로 이어진 구조.** 노드가 다른 노드를 가리키고, 그 가리킴을 따라가며 자료를 다루는
  모양입니다. 뿌리 하나에서 시작해 아래로 뻗는 것이 트리예요.
- **트리에서 부모와 자식이 무엇인지.** 이 글에서는 자식이 여럿일 수 있고, 몇 개인지 미리
  정해져 있지 않습니다.

이 글이 다루는 것은 **접두사를 묻는 조회**입니다. 자식이 하나뿐인 사슬을 한 노드로 접는 변형은
[`radixTree`](../radixTree/radixTree-problem.md) 가 다루고, 여러 단어를 한 번의 순회로 동시에
찾는 것은 [`ahoCorasick`](../ahoCorasick/ahoCorasick-problem.md) 가 다뤄요.

```text
  담긴 단어의 접두사인지 묻는다              <- 이 글이 다루는 것
  자식이 하나뿐인 사슬을 한 노드로 접는다    <- 다른 글이 다루는 것
  여러 단어를 한 번의 순회로 동시에 찾는다   <- 또 다른 글이 다루는 것
```

### 아이디어 상세 — 접두사를 경로로 삼는 트리를 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
class Trie {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- 입력: 소문자 영문(`a`–`z`)으로만 된 문자열. `insert` 는 담고, 나머지 둘은 묻습니다.
- 출력: `search` 는 그 문자열이 담긴 단어이면 참, `startsWith` 는 그 문자열로 시작하는 단어가
  하나라도 있으면 참입니다. 같은 단어를 여러 번 담아도 답이 달라지지 않아요.
- 제약: 문자열 하나의 길이 `L ≤ 100,000`, 담은 모든 단어의 길이 합 `S ≤ 100,000`,
  각 연산이 `O(L)`. 시간 1 초, 메모리 256 MB.

이 글이 쓰는 기호는 여섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `L` | 이번 연산이 받은 문자열의 길이 | `1 ≤ L ≤ 100,000` |
| `S` | 담은 모든 단어의 길이 합 | `S ≤ 100,000` |
| `N` | 담은 단어의 개수 | `N ≤ S` |
| `V` | 트라이의 노드 개수. 뿌리를 포함합니다 | `1 ≤ V ≤ S + 1` |
| `Σ` | 문자 집합의 크기 | 소문자 영문이라 26 |
| `Q` | 조회 연산의 횟수 | 제약이 따로 정하지 않습니다 |

가장 먼저 떠오르는 방법으로 시작합시다. 단어를 배열에 담고, 물을 때마다 그 배열을 앞에서부터
대조하는 것이에요.

```ts
class WordList {
  private words: string[] = [];
  insert(word: string) { this.words.push(word); }
  search(word: string) { return this.words.includes(word); }              // 단어마다 전체 대조
  startsWith(p: string) { return this.words.some((w) => w.startsWith(p)); } // 단어마다 앞 L 글자
}
```

이 방법이 조회 하나에 읽는 글자 수는 **담긴 단어들의 길이 합**까지 갑니다. 제약이 정한 규모를
그대로 넣어 두 방식을 실행해 보면 이렇게 나와요.

<!--proof:costWorstQuery-->

```text
사전 1,000 단어 · 길이 합 100,000  답    읽은 글자  조회 1,000 번이면
목록에 담고 매번 대조한다          거짓     98,000         98,000,000
접두사를 공유하는 트리를 만든다    거짓         98             98,000

조회는 "aaaaaaaa...zzz" (길이 100) 하나이고 사전에 없다
└ 목록 방식은 단어 1,000 개를 각각 98 글자까지 대조한다. 트리는 98 글자에서 끝난다
```

제약이 요구한 것은 조회 하나가 `L` 에 비례하는 것인데, 목록 대조는 `S` 에 비례합니다. 두 값이
같은 규모라 이 차이가 곧바로 1,000 배로 나타나요. 그러면 이 100,000 글자 안에서 무엇이
되풀이되는지 봅시다.

```text
startsWith("apz") 를 목록 대조로 답할 때
  app 과 대조     a p 까지 맞고 셋째 글자에서 어긋난다   3 글자
  apple 과 대조   a p 까지 맞고 셋째 글자에서 어긋난다   3 글자
  ape 와 대조     a p 까지 맞고 셋째 글자에서 어긋난다   3 글자
└ 같은 a p 를 세 번 읽었다. 세 단어가 그 두 글자를 공유하는데 그것을 쓰지 않고 있다
```

단어가 하나 늘 때마다 **같은 앞부분을 처음부터 다시** 읽고 있습니다. 그런데 조회 하나에 대해
알아야 할 것은 단어마다의 대조 결과가 아니라 「이 글자들을 차례로 따라갈 수 있는가」 하나예요.
같은 조회 넷을 두 방식으로 처리하고 읽은 글자를 나란히 세어 봅시다.

<!--proof:costFourQueries-->

```text
조회                답    목록 대조가 읽은 글자  트리가 읽은 글자
search("app")       참                        3                 3
search("appl")      거짓                     10                 4
startsWith("appl")  참                        7                 4
startsWith("bat")   거짓                      3                 1
합계                                         23                12

└ 목록 대조는 단어가 늘면 함께 늘고, 트리는 조회 문자열의 길이만 따라간다
```

오른쪽 방식이 조회 하나에 읽는 글자가 **조회 문자열의 길이 이하**로 고정됩니다. 여기서 관찰할
것은 그 하나예요 — 조회 하나의 비용이 담긴 단어의 개수와 상관없어집니다.

| 방식 | 조회 하나에 읽는 글자 | 무엇을 따라가는가 |
| --- | --- | --- |
| 목록 대조 | 단어마다 어긋나는 자리까지 | 담긴 단어의 개수와 길이를 따라간다 |
| 앞부분을 공유 | 최대 `L` 글자 | 조회 문자열의 길이만 따라간다 |

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「첫 글자가 같은 것끼리 스물여섯
묶음으로 나눠 담으면 그 안에서만 대조하면 되지 않나」가 그것이에요.

<!--proof:bucketFirstLetter-->

```text
조회                답    목록 대조  첫 글자만 나눔  글자마다 나눔
startsWith("appl")  참            7               8              4
startsWith("apz")   거짓          9              10              3
startsWith("bat")   거짓          3               1              1

└ 세 단어가 전부 a 로 시작해서 첫 글자만 나누면 묶음 하나에 다 들어간다
  첫 줄과 둘째 줄에서 읽은 글자가 오히려 하나 늘었다 — 묶음을 고르는 읽기 한 번이다
  b 로 시작하는 조회에서만 값이 줄고, 그 이득은 첫 글자가 다를 때뿐이다
```

첫 글자만 나누면 **같은 글자로 시작하는 단어들 안에서는 아무것도 줄지 않습니다.** 그러면 그
안에서 둘째 글자로 또 나누고, 그 안에서 셋째 글자로 또 나눠야 해요. 그 되풀이를 끝까지 이어
가면 나오는 것이 트리입니다.

```text
접두사를 경로로 삼는 트리
  노드      담긴 단어들의 접두사 하나        뿌리는 빈 문자열이다
  간선      글자 하나                        부모의 경로 문자열에 그 글자를 붙인다
  경로      뿌리에서 노드까지 이은 글자들    그 노드가 뜻하는 접두사다
  끝 표시   그 경로 문자열이 담긴 단어인가   노드마다 참·거짓 하나
└ 글자 하나를 읽을 때마다 노드를 한 칸 내려간다. 그것이 이 구조가 정하는 이동 범위다
```

개념이 정하는 것은 **연산 하나가 지나는 노드의 개수**입니다. 글자 하나에 한 칸이므로 길이 `L`
짜리 문자열이면 뿌리를 포함해 `L + 1` 개예요.

```text
길이 L 짜리 문자열 하나를 처리할 때
  지나는 노드        L + 1 개            뿌리에서 시작해 글자마다 한 칸
  읽는 자식 맵       L 번                노드 하나에서 한 번
  새로 만드는 노드   0 개부터 L 개까지   이미 있는 경로가 어디까지인가로 정해진다
└ 어느 항에도 담긴 단어의 개수가 들어오지 않는다
```

**쉬운 경우와 불안한 경우를 나눠서 값으로 확인합시다.** 쉬운 경우는 담을 단어의 첫 글자부터
자식이 없을 때예요. 글자 수만큼 노드를 새로 만들고 마지막에 끝 표시를 남기면 끝납니다.

| 담는 단어 | 그 전의 트라이 | 이어 쓰는 자리 | 새로 만드는 노드 | 노드 수 |
| --- | --- | --- | --- | --- |
| `app` | 뿌리 하나 | 없다 | `a` `ap` `app` 셋 | 1 → 4 |
| `apple` | `app` 까지 있다 | `a` `ap` `app` 셋 | `appl` `apple` 둘 | 4 → 6 |
| `ape` | `apple` 까지 있다 | `a` `ap` 둘 | `ape` 하나 | 6 → 7 |

불안한 경우는 **앞부분이 이미 있을 때**입니다. 어디까지 이어 쓰고 어디부터 새로 만들지를
글자마다 정해야 하는데, 그 판단이 「그 글자의 자식이 있는가」 하나로 끝나요. `apple` 을 담을
때 앞 세 글자에서 자식이 셋 다 있으므로 노드가 하나도 안 늘어납니다.

```text
insert("apple") 의 글자별 판단
  a   뿌리에 a 가 있다    이어 쓴다   노드 수 4 그대로
  p   a 에 p 가 있다      이어 쓴다   노드 수 4 그대로
  p   ap 에 p 가 있다     이어 쓴다   노드 수 4 그대로
  l   app 에 l 이 없다    만든다      노드 수 5
  e   appl 에 e 가 없다   만든다      노드 수 6
└ 판단이 글자마다 독립이라 앞부분이 어디까지 같은지 미리 알아 둘 필요가 없다
```

**가장 불안한 경우는 이미 있는 노드에서 문자열이 끝날 때**예요. 새 노드가 하나도 안 생기고
끝 표시 한 칸만 참으로 바뀌는데, 그 한 칸이 `search` 의 답을 거짓에서 참으로 바꿉니다.

```text
apple 만 담긴 상태에서 app 을 담으면
  새로 만드는 노드   0 개                        a p p 이 셋 다 이미 있다
  바뀌는 것          노드 app 의 끝 표시 한 칸   거짓에서 참으로
  search("app")      거짓에서 참으로             앞뒤로 노드 수는 6 그대로
└ 노드가 있다는 것과 담긴 단어라는 것이 다른 이야기라, 표시 한 칸을 따로 둬야 한다
```

빠뜨리는 글자가 없다는 것은 반복문의 종료 조건으로 말할 수 있습니다. 반복문은 문자열의 글자를
앞에서부터 하나씩 소진하고, 한 번 실행할 때마다 노드를 **정확히 한 칸** 내려가요.

```text
반복문이 끝난 시점
  소진한 글자   L 개    문자열의 글자 전부
  내려간 칸     L 칸    글자 하나에 한 칸
  서 있는 노드  하나    그 노드의 경로 문자열이 곧 받은 문자열이다
└ 건너뛰는 자리가 없으므로 도착한 노드가 받은 문자열 그 자체를 뜻한다
```

이제 앞부분을 공유하면 자리가 얼마나 줄어드는지 값으로 확인합니다. 단어 집합 넷에 대해 단어를
따로따로 적었을 때의 자리 수와 트라이의 노드 수를 나란히 셌어요.

<!--proof:nodeCount-->

```text

{app, apple, ape}                   11                    12               7
{app, bat, cup}                      9                    10              10
앞 97 글자가 같은 1,000 단어   100,000               100,001           1,139
앞 3 글자가 갈리는 1,000 단어  100,000               100,001          98,042

└ 둘째 줄은 공유할 접두사가 없어 두 값이 같다 — 트라이가 이득을 못 내는 입력이다
  셋째 줄과 넷째 줄은 길이 합이 똑같이 100,000 인데 노드 수가 86 배 갈린다
```

둘째 줄이 **이 구조가 이득을 못 내는 입력**입니다. 세 단어의 첫 글자가 전부 달라 공유할 앞부분이
없고, 그때 노드 수가 길이 합보다 하나 많은 값 그대로예요. 이득의 크기는 접두사를 얼마나
공유하는가로 정해집니다.

```text
얻은 절차 한 벌
  1.   뿌리에서 시작한다
  2.   글자를 하나씩 읽으며
  3.     그 글자의 자식이 없으면 만들고, 있으면 그대로 이어 쓴다
  4.     그 자식으로 옮긴다
  5.   삽입이면 마지막 노드에 끝 표시를 남긴다
  6.   조회면 도착한 노드를 본다 — 끝 표시까지 보면 search, 도착 여부만 보면 startsWith
└ 조회 하나가 100,000 글자이던 것이 받은 문자열의 길이만큼으로 줄어든다
```

### 수행으로 알아보는 알고리즘 — 세 단어를 담고 네 번 묻는다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각
마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const trie = new Trie();
trie.insert("app");
trie.insert("apple");
trie.insert("ape");
// 그다음 search("app") · search("appl") · startsWith("appl") · startsWith("bat") 를 묻는다
```

왜 하필 이 셋과 이 넷일까요? 삽입의 세 경우가 다 나오기 때문이에요 — 전부 새로 만드는 삽입
(`app`), 앞부분을 이어 쓰고 뒤만 만드는 삽입(`apple`), 도중에 다른 글자로 나뉘는 삽입(`ape`)
입니다. 조회 넷은 답이 참과 거짓으로 둘씩이고, **같은 문자열 `appl` 에 두 연산이 다른 답을 내는
자리**를 포함해요.

```text
절차 전체를 한 장으로
  T1       뿌리 하나로 시작한다
  T2~T7    단어 셋을 담는다
             삽입마다 뿌리에서 출발한다       ① 뿌리에서 출발
             글자마다 자식이 없으면 만든다    ② 없을 때만 만든다
             마지막 노드에 끝 표시를 남긴다   ③ 단어 끝 표시
  T8~T11   네 번 묻는다
             글자를 따라 내려간다             ⑥ 자식이 없으면 없는 것이다
             끝 표시까지 본다                 ④ search 의 마지막 한 줄
             도착 여부만 본다                 ⑤ startsWith 의 마지막 한 줄
```

#### 1. 노드 하나의 모양을 정한다

첫 조각은 노드입니다. 자식을 담는 표 하나와 끝 표시 한 칸이 전부예요.

```ts
class TrieNode {
  readonly children = new Map<string, TrieNode>();   // 글자 하나 -> 자식 노드
  end = false;                                       // 이 노드의 경로 문자열이 담긴 단어인가
}
```

노드가 **자기 글자를 들고 있지 않은 것**이 이 조각의 요점입니다. 글자는 부모에서 이 노드로 오는
간선에 붙어 있고, 그래서 부모의 `children` 에서 그 글자로 찾으면 이 노드가 나와요.

```text
노드 하나가 드는 것
  children   글자 -> 자식 노드             자식이 없으면 빈 맵이다
  end        경로 문자열이 담긴 단어인가   거짓에서 시작한다
└ 자기 글자를 들지 않는다. 글자는 부모에서 이 노드로 오는 간선에 붙어 있다
```

#### 2. 글자를 따라 내려가며 없는 노드만 만든다

둘째 조각은 삽입입니다. 뿌리에서 출발해 글자를 하나씩 읽고, 그 글자의 자식이 없을 때만 새 노드를
만들어 걸어요.

```ts
insert(word: string): void {
  let node = this.root;                    // ① 뿌리에서 출발한다
  for (const ch of word) {
    let next = node.children.get(ch);
    if (next === undefined) {              // ② 그 글자로 가는 자식이 없을 때만 만든다
      next = new TrieNode();
      node.children.set(ch, next);
    }
    node = next;
  }
  node.end = true;                         // ③ 마지막 노드에 단어 끝 표시를 남긴다
}
```

`①` 이 매번 같은 자리에서 시작하는 것이 요점입니다. 어느 단어를 담든 뿌리에서 출발하므로, 앞부분이
같은 단어들은 **저절로 같은 길을 지나가요.** 세 단어를 하나씩 담을 때마다 모양이 이렇게 됩니다.

<!--proof:shapeAfterInserts-->

```text
insert("app") 까지 — 노드 4 개
(root)
`-- a
    `-- p
        `-- p*

insert("app") insert("apple") 까지 — 노드 6 개
(root)
`-- a
    `-- p
        `-- p*
            `-- l
                `-- e*

insert("app") insert("apple") insert("ape") 까지 — 노드 7 개
(root)
`-- a
    `-- p
        +-- p*
        |   `-- l
        |       `-- e*
        `-- e*

└ * 는 단어 끝 표시(end = true)다. 간선의 글자를 위에서 아래로 이으면 그 노드의 경로 문자열이 된다
```

#### 짚고 가기 — 자식이 있는지 보지 않고 만들면 앞서 담은 단어가 사라진다

여기서 헷갈리기 쉬운 포인트는 `②` 의 조건입니다. 「어차피 없는 자리에만 걸리니까 조건 없이 만들어
걸어도 되지 않나」로 읽기 쉬워요. 그 생각대로 자식을 찾는 줄과 그 조건을 걷어내 봅시다.

```ts
for (const ch of word) {
  const next = new TrieNode();     // 자식이 있는지 보지 않고 매번 새로 만든다
  node.children.set(ch, next);
  node = next;
}
```

담은 단어 셋에 앞서 쓴 조회 넷을 그대로 걸어 봅니다.

<!--proof:pauseOverwrite-->

```text
조회                정본이 낸 답  매번 새로 만든 답  판정
search("app")                 참               거짓  틀리다
search("appl")              거짓               거짓  같다
startsWith("appl")            참               거짓  틀리다
startsWith("bat")           거짓               거짓  같다
search("apple")               참               거짓  틀리다

└ 나중에 넣은 단어가 앞서 넣은 단어의 경로를 덮어써서, 마지막 단어 하나만 남는다
```

같은 글자로 `set` 을 다시 부르면 **그 자리에 걸려 있던 자식이 바뀝니다.** 앞서 담은 단어의
경로가 그 순간 사라지고, 그 아래에 있던 끝 표시도 함께 없어져요.

```text
insert("app") 을 마친 뒤 insert("apple") 을 넣을 때
  자식이 있는지 본다   a 가 이미 있다     그 노드를 이어 쓴다
  보지 않는다          a 를 새로 만든다   앞의 a 가 걸려 있던 자리를 덮는다
└ 덮인 쪽 아래에 이어져 있던 app 의 끝 표시가 함께 사라진다
```

#### 3. 같은 내려가기로 두 조회를 답한다

셋째 조각은 조회입니다. 두 연산이 **같은 내려가기**를 쓰므로 그 부분을 따로 떼어 두고, 마지막
한 줄에서만 갈라요.

```ts
search(word: string): boolean {
  const node = this.nodeAt(word);
  return node !== null ? node.end : false;   // ④ 경로가 있고 끝 표시도 있어야 한다
}

startsWith(prefix: string): boolean {
  return this.nodeAt(prefix) !== null;   // ⑤ 경로가 있기만 하면 된다
}

private nodeAt(s: string): TrieNode | null {
  let node = this.root;
  for (const ch of s) {
    const child = node.children.get(ch);
    if (child === undefined) return null;   // ⑥ 자식이 없으면 이 문자열은 어떤 단어의 접두사도 아니다
    node = child;
  }
  return node;
}
```

`⑥` 이 **남은 글자를 읽지 않고 곧바로 끝내는 자리**입니다. 첫 글자부터 없으면 한 번 읽고 끝나요.
세 조각을 이어 담긴 단어 셋에 조회 넷을 걸면 이렇게 갈립니다.

| 조회 | `nodeAt` 이 돌려준 것 | 끝 표시 | `④` 의 값 | `⑤` 의 값 |
| --- | --- | --- | --- | --- |
| `search("app")` | 노드 `app` | 있다 | 참 | - |
| `search("appl")` | 노드 `appl` | 없다 | 거짓 | - |
| `startsWith("appl")` | 노드 `appl` | 안 본다 | - | 참 |
| `startsWith("bat")` | `null` | - | - | 거짓 |

#### 짚고 가기 — 끝 표시를 보지 않으면 두 조회가 같은 것이 된다

여기서 헷갈리기 쉬운 포인트는 `④` 의 뒷항입니다. 「글자를 다 따라가 노드까지 도착했으면 그 단어가
담긴 것 아닌가」로 읽기 쉬워요. 그 생각대로 뒷항을 지워 봅시다.

```ts
search(word: string): boolean {
  const node = this.nodeAt(word);
  return node !== null;   // 끝 표시를 안 보고 도착 여부만 본다
}
```

여섯 조회로 확인해 봅니다. 오른쪽 끝에 `startsWith` 의 답을 나란히 놓았어요.

<!--proof:pauseEndFlag-->

```text
조회             정본이 낸 답  끝 표시를 안 본 답  startsWith 의 답  판정
search("app")              참                  참                참  같다
search("appl")           거짓                  참                참  틀리다
search("ap")             거짓                  참                참  틀리다
search("a")              거짓                  참                참  틀리다
search("apple")            참                  참                참  같다

└ 셋째 열이 넷째 열과 한 줄도 다르지 않다 — 끝 표시를 빼면 두 연산이 같은 것이 된다
  담긴 단어를 그대로 물은 첫 줄과 다섯째 줄에서는 답이 안 틀린다
```

**담긴 단어를 그대로 물으면 답이 안 틀린다는 것**이 이 실수의 성격입니다. `search("app")` 과
`search("apple")` 은 두 방식이 같은 답을 내므로, 담긴 단어만 시험에 넣으면 끝까지 모르고 넘어가요.

```text

  startsWith   도착했는가만 본다              appl 에 도착했으므로 참
  search       도착한 노드의 끝 표시를 본다   appl 은 끝 표시가 없으므로 거짓
└ 두 연산이 같은 내려가기를 쓰고 마지막 한 줄에서만 갈린다
```

#### 짚고 가기 — 글자마다 재귀로 내려가면 제약 최댓값에서 호출 스택이 넘친다

여기서 헷갈리기 쉬운 포인트는 **내려가기를 어떻게 적는가**입니다. 트리를 다루는 코드라 「글자
하나를 처리하고 나머지를 자기 자신에게 넘기면 짧게 적힌다」로 가기 쉬워요.

```ts
function insertRec(node: TrieNode, word: string, k: number): void {
  if (k === word.length) { node.end = true; return; }
  const ch = word[k] as string;
  let next = node.children.get(ch);
  if (next === undefined) { next = new TrieNode(); node.children.set(ch, next); }
  insertRec(next, word, k + 1);      // 글자 하나마다 호출이 한 겹 쌓인다
}
```

만드는 트라이는 반복문 쪽과 같습니다. 갈리는 것은 호출 스택의 깊이예요.

<!--proof:pauseRecursion-->

```text
단어 길이  글자마다 재귀로 내려가면  반복문으로 내려가면
    1,000  끝까지 넣는다             끝까지 넣는다
  100,000  RangeError                끝까지 넣는다

└ 제약이 허용하는 길이 100,000 에서 재귀는 호출 스택이 넘친다
  길이 1,000 은 두 방식 다 끝난다 — 짧은 단어만 시험하면 이 실패를 못 만난다
```

제약이 문자열 길이를 100,000 까지 허용하므로 이 문제에서 재귀는 쓸 수 없습니다. 길이 1,000
짜리 단어로만 시험하면 통과하니, 짧은 입력만 넣어 보고 넘어가면 끝까지 모르는 자리예요.

```text
재귀와 반복문이 갈리는 자리
  재귀     글자 하나마다 호출 한 겹       겹의 개수가 문자열 길이와 같다
  반복문   글자 하나마다 변수 하나 갱신   겹이 하나도 안 쌓인다
└ 두 방식이 만드는 트라이는 같다. 갈리는 것은 호출 스택의 깊이뿐이다
```

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 뿌리를 만들어 두는 한 줄뿐이에요 —
빈 트라이는 뿌리 하나이고, 그때 두 조회는 첫 글자에서 `⑥` 에 걸려 거짓을 냅니다.

```ts
class TrieNode {
  readonly children = new Map<string, TrieNode>();
  end = false;
}

export class Trie {
  private readonly root = new TrieNode();

  insert(word: string): void {
    // ① 뿌리에서 출발한다. 뿌리는 빈 문자열에 해당하는 노드다.
    let node = this.root;
    for (const ch of word) {
      let next = node.children.get(ch);
      // ② 그 글자로 가는 자식이 없을 때만 새 노드를 만든다.
      if (next === undefined) {
        next = new TrieNode();
        node.children.set(ch, next);
      }
      node = next;
    }
    // ③ 마지막 노드에 단어 끝 표시를 남긴다. 같은 단어를 다시 넣어도 결과가 같다.
    node.end = true;
  }

  search(word: string): boolean {
    const node = this.nodeAt(word);
    // ④ 경로가 있고 그 끝에 단어 끝 표시도 있어야 한다.
    return node !== null ? node.end : false;
  }

  startsWith(prefix: string): boolean {
    // ⑤ 경로가 있기만 하면 된다. 끝 표시는 보지 않는다.
    return this.nodeAt(prefix) !== null;
  }

  private nodeAt(s: string): TrieNode | null {
    let node = this.root;
    for (const ch of s) {
      const child = node.children.get(ch);
      // ⑥ 그 글자로 가는 자식이 없으면 이 문자열은 담긴 어떤 단어의 접두사도 아니다.
      if (child === undefined) return null;
      node = child;
    }
    return node;
  }
}
```

### 알아 두면 좋은 개념 — 자리별 분해

이 절차가 한 일에는 이름이 붙어 있습니다. 키를 한 덩어리로 견주지 않고 **자리 하나씩 갈라** 후보를
좁히는 방식을 **자리별 분해**라고 불러요. 여기서 자리는 글자였고, 자리 하나가 갈래 하나였습니다.

| 무엇을 자리로 보는가 | 자리 하나의 갈래 수 | 이 글에서 | 후보가 어떻게 좁혀지는가 |
| --- | --- | --- | --- |
| 글자 | `Σ` = 26 | 노드의 자식 | `a` 를 읽으면 `a` 로 시작하는 단어만 남는다 |
| 십진 자리 | 10 | - | 일의 자리가 3 인 수만 남는다 |
| 비트 | 2 | - | 최상위 비트가 1 인 수만 남는다 |

전개의 T2 부터 T4 가 그 좁힘을 값으로 보인 자리예요. `a` 를 읽고 노드 `a` 로, `p` 를 읽고 노드
`ap` 로 내려갔고, 그때마다 남은 후보가 「그 경로로 시작하는 단어들」로 줄었습니다.

```text
같은 모양이 나오는 다른 자리
  기수 정렬      숫자를 자리마다 갈라 안정 정렬을 되풀이한다
  이진 트라이    정수를 비트마다 갈라 내려가며 XOR 최댓값을 찾는다
  IP 라우팅 표   주소를 비트마다 갈라 가장 긴 일치 접두사를 찾는다
└ 셋 다 키를 한 덩어리로 보지 않고 자리 하나씩 갈라 후보를 좁힌다
```

자리별 분해를 정렬에 쓴 것이 [`radixSort`](../../sorting/radixSort/radixSort-problem.md) 이고,
이 글은 같은 생각을 **조회**에 쓴 것이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 노드 수를 식으로 어떻게 적는지,
무엇이 매 삽입 뒤에 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **키가 자리로 나뉩니다.** 문자열의 글자, 정수의 자리나 비트처럼 앞에서부터 하나씩 떼어 낼 수
  있어야 해요. 자리로 못 나누는 키는 갈래를 만들 기준이 없습니다.
- **접두사 자체를 묻습니다.** 답이 경로 끝의 노드에만 있는 것이 아니라 **경로 도중의 노드**에도
  있어야 해요. 완전 일치만 물으면 해시 표가 더 적은 칸으로 같은 일을 합니다.
- **키가 접두사를 많이 공유합니다.** 공유가 없으면 노드 수가 길이 합과 같아져서, 자리를 아끼려고
  들인 구조가 아무것도 못 줄여요.
- **담는 일과 묻는 일이 섞여 들어옵니다.** 전부 담고 나서 묻기만 한다면 한 번 정렬해 두는 방식이
  칸을 훨씬 적게 씁니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  키가 자리로 나뉜다                  -> 자리 하나마다 갈래를 하나 만든다
  접두사 자체를 묻는다                -> 경로 도중의 노드가 답이 된다
  키가 접두사를 많이 공유한다         -> 노드 수가 길이 합보다 훨씬 적어진다
  담는 일과 묻는 일이 섞여 들어온다   -> 미리 정렬해 둘 수 없다
```

두 번째 줄이 이 구조의 경계입니다. 완전 일치만 필요하면 문자열 하나를 통째로 해시해 표에 넣는
쪽이 노드 하나하나에 맵을 두는 것보다 칸이 적어요.

| 무엇을 묻는가 | 무엇을 쓰는가 | 왜 |
| --- | --- | --- |
| 이 문자열이 담겼는가만 | 해시 집합 | 경로 도중의 노드가 필요 없다 |
| 이 문자열로 시작하는 것이 있는가 | 접두사 트리 | 도중의 노드가 곧 답이다 |
| 가운데 어디든 이 조각이 있는가 | 접미사 구조 | 접두사만으로는 못 답한다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "자동 완성"  "이 글자로 시작하는"  "접두사"   <- startsWith 그 자체다
  "사전에 있는 단어인가"  "정확히 일치"         <- search 그 자체다
  "각 연산이 문자열 길이에 비례"                <- 담긴 단어의 개수를 보면 안 된다
  "삽입과 조회가 섞여 들어온다"                 <- 미리 정렬해 두는 방식을 막는다

반대로 이런 말이 보이면 해당하지 않는다
  "부분 문자열"  "가운데 어디든"                <- 접두사가 아니라 다른 구조가 필요하다
  "단어를 지운다"  "개수를 센다"                <- 노드마다 값을 더 들어야 한다
  "메모리가 아주 빠듯하다"                      <- 노드마다 맵을 드는 비용이 문제가 된다
```

마지막 무리가 보이면 다른 구조로 갑니다. 자식이 하나뿐인 사슬이 길게 이어지는 사전이면
[`radixTree`](../radixTree/radixTree-problem.md) 쪽이고, 접두사가 아니라 문자열 가운데의 조각을
물으면 [`suffixArray`](../suffixArray/suffixArray-problem.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **ICU(International Components for Unicode) 의 `BytesTrie`·`UCharsTrie`.** 유니코드 표준
  구현이 트라이를 이름 그대로 공개 API 로 제공하는 자리입니다. 문서가 이 클래스를
  *"Traverses a byte-serialized data structure with minimal state, for mapping byte sequences to
  non-negative integer values."* 로 정의해요. 한 걸음에 한 바이트씩 내려가는 `next()` 가 이 글의
  `nodeAt` 과 같은 일을 합니다.
  ([`icu::BytesTrie` API 문서](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/classicu_1_1BytesTrie.html),
  [`bytestrie.h` 소스](https://github.com/unicode-org/icu/blob/main/icu4c/source/common/unicode/bytestrie.h),
  조회 2026-08-30)

같은 구현이 **이 글의 끝 표시와 같은 것을 반환값의 종류로** 갈라 둡니다. `ustringtrie.h` 의
`UStringTrieResult` 가 그것이고, 셋이 각각 이 글의 어느 답인지가 그대로 대응해요.

| ICU 의 반환값 | 문서의 정의 | 이 글의 무엇인가 |
| --- | --- | --- |
| `USTRINGTRIE_NO_MATCH` | *"The input unit(s) did not continue a matching string."* | `nodeAt` 이 `null` 을 낸 자리 |
| `USTRINGTRIE_NO_VALUE` | *"...but there is no value for the string so far. (It is a prefix of a longer string.)"* | 노드는 있고 끝 표시가 없다 |
| `USTRINGTRIE_INTERMEDIATE_VALUE` | *"...and there is a value for the string so far... Another input byte/unit can continue a matching string."* | 노드도 끝 표시도 있다 |

- **리눅스 커널의 IPv4 경로 표 `net/ipv4/fib_trie.c`.** 주소를 비트마다 갈라 가장 긴 일치
  접두사를 찾는 자리이고, 파일 첫머리가 *"This work is based on the LPC-trie which is originally
  described in: An experimental study of compression methods for dynamic tries, Stefan Nilsson and
  Matti Tikkanen, Algorithmica, 33(1):19-33, 2002"* 라 적혀 있습니다. **이 글의 트라이를 압축한
  변형**이라는 것을 밝혀 둡니다 — 자리 수를 줄이려고 사슬을 접은 구조라 노드 수의 계산이 달라져요.
  ([`net/ipv4/fib_trie.c`](https://github.com/torvalds/linux/blob/master/net/ipv4/fib_trie.c),
  조회 2026-08-30)

**웹 브라우저나 편집기의 자동 완성이 이 구조를 쓴다는 것은 1 차 출처로 확인하지 못했습니다.**
확인한 것은 유니코드 표준 구현이 트라이를 공개 API 로 제공한다는 것과, 리눅스 커널의 경로 표가
그 압축 변형을 쓴다는 것 둘입니다.

#### 경쟁 설계와의 대조

같은 목표(문자열을 담고 접두사를 묻는 것)를 노리는 다른 절차로 **정렬을 유지하는 배열과 이분
탐색**이 있습니다. 단어를 사전순으로 담아 두면 어떤 문자열로 시작하는 단어가 있는지는 그 문자열이
들어갈 자리 하나만 보면 알 수 있어요 — 있다면 바로 그 자리에서 시작합니다.

```text
두 설계가 같은 일을 어떻게 하는가
  접두사 트리   글자마다 노드를 한 칸 내려간다                 담긴 단어의 개수를 안 본다
  정렬 배열     이분 탐색으로 자리를 찾고 그 단어와 대조한다   비교마다 문자열을 다시 읽는다
└ 삽입은 트리가 노드를 잇기만 하고, 배열은 자리를 만들려고 뒤쪽을 옮긴다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **기본 연산 수**(읽은 글자 + 노드 생성 + 배열 원소
이동)를 셌습니다. 사전은 길이 100 짜리 단어 1,000 개이고 길이 합이 제약의 최댓값 100,000 이에요.
단어는 `"a" × 50 + base26(i) + "z" × 47` 로 만들었어요 — `base26(i)` 는 `i` 를 소문자 세 글자로
적은 것입니다. 조회 1,000 개는 그 단어들의 앞 60 글자예요.
**전개 입력을 그대로 쓰지 않은 이유**는 단어 셋에서는 이분 탐색이 한 번에 끝나 두 설계의 계수가
상수에 묻히기 때문입니다.

| 무엇 | 접두사 트리 | 정렬 배열과 이분 탐색 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 삽입 1,000 개 · 기본 연산 | **149,091** | 417,921 | 트리가 2.8 배 적습니다 |
| 조회 1,000 회 · 기본 연산 | **61,000** | 590,398 | 트리가 9.7 배 적습니다 |
| 공유 47 글자 · 저장 칸 | 102,177 | **101,000** | 배열이 적습니다 |
| 공유 48 글자 · 저장 칸 | **100,179** | 101,000 | **여기서 순서가 뒤집힙니다** |

**연산 수에서는 갈리지 않고 저장 칸에서 갈립니다.** 배열은 글자를 그대로 담으므로 공유의 정도를
아예 안 보고 언제나 101,000 칸이에요. 트리는 노드마다 끝 표시 한 칸과 간선마다 항목 한 칸을 쓰므로
공유가 늘면 함께 줄어듭니다. 길이 합을 100,000 으로 고정한 채 공통 접두사 길이만 바꿔 보면
뒤집히는 자리가 값으로 나와요.

```text

               0         196,083            101,000  배열이 적다
```

**이 절차가 내주는 것은 저장 칸입니다.** 접두사를 47 글자 이하로 공유하는 사전에서는 정렬 배열이
칸을 더 적게 쓰고, 그 차이는 공유가 하나도 없을 때 196,083 대 101,000 까지 갑니다. 그 대신 얻는
것이 둘이에요.

```text
접두사 트리가 얻는 것
  조회 하나의 비용   담긴 단어의 개수를 안 본다      배열은 log N 번의 문자열 비교를 한다
  삽입 하나의 비용   노드를 잇기만 한다              배열은 뒤쪽 원소를 한 칸씩 옮긴다
└ 이 문제는 삽입과 조회가 섞여 들어오므로 앞의 두 줄이 답이다
```

문제가 「담는 일과 묻는 일이 섞여 들어온다」이니 이 문제에서는 접두사 트리가 답입니다. 같은 지문에서
**전부 담고 나서 묻기만 하고 접두사 공유가 47 글자 이하인 사전**이면 이 판정은 다시 해야 해요.

### 수식 정의와 유도

단어 집합 `W` 에 대해 **접두사 집합**을 정의합니다. `w[0..k)` 는 `w` 의 앞 `k` 글자예요.

$$\operatorname{Pref}(W) = \{\, w[0..k) \;:\; w \in W,\ 0 \le k \le |w| \,\} \qquad V = |\operatorname{Pref}(W)|$$

```text
식을 읽는 법
  W         담은 단어들의 집합
  w[0..k)   w 의 앞 k 글자. k = 0 이면 빈 문자열이다
  Pref(W)   W 의 단어들이 내놓는 접두사를 전부 모은 집합
  V         그 집합의 크기. 트라이의 노드 집합이 곧 이 집합이다
└ k 가 0 부터 |w| 까지이므로 단어 자기 자신도 자기 접두사에 든다
```

정의를 전개 입력에 넣어 확인하고 갑시다.

<!--proof:mathPrefixSet-->

```text
원소           어느 단어에서 나왔는가  길이
""(빈 문자열)  app apple ape              0
a              app apple ape              1
ap             app apple ape              2
ape            ape                        3
app            app apple                  3
appl           apple                      4
apple          apple                      5

집합의 크기 7 · 트라이 노드 수 7 · 길이 합 11
└ 두 수가 같다. 노드 하나가 접두사 하나이고 그 역도 성립한다
```

원소 일곱이 노드 일곱과 하나씩 짝지어집니다. 깊이별로 놓으면 트리의 층이 그대로 나와요.

```text
Pref(W) 의 원소를 깊이별로 놓으면
  깊이 0   ""
  깊이 1   a
  깊이 2   ap
  깊이 3   app   ape
  깊이 4   appl
  깊이 5   apple
└ 깊이 k 의 원소가 길이 k 인 접두사다. 원소 하나가 노드 하나이고 그 역도 성립한다
```

이제 상한을 유도합니다. 단어 `w` 하나가 내놓는 접두사는 `k = 0` 부터 `k = |w|` 까지라
`|w| + 1` 개인데, `k = 0` 이 내놓는 빈 문자열은 모든 단어가 같은 것을 내놓아요. 합집합이므로
겹치는 것은 한 번만 셉니다.

$$|\operatorname{Pref}(W)| \le 1 + \sum_{w \in W} |w| = 1 + S$$

```text
상한이 나오는 셈
  단어 w 하나가 내놓는 접두사   |w| + 1 개    k = 0 부터 k = |w| 까지
  빈 문자열                     N 번 나온다   합집합이라 한 번만 센다
  나머지를 다 더하면            S 개 이하     같은 접두사가 겹치면 그만큼 줄어든다
└ 그래서 1 + S 가 상한이고, 겹치는 것이 하나도 없을 때 등호가 성립한다
```

$$|\operatorname{Pref}(W)| \ge 1 + \max_{w \in W} |w|$$

아래 식은 가장 긴 단어 하나가 자기 접두사 `|w| + 1` 개를 혼자 내놓기 때문입니다. 등호가 성립하는
자리도 정해져요 — 위 식은 **어떤 두 단어도 첫 글자부터 다를 때**(빈 문자열 말고는 겹치는 접두사가
없다), 아래 식은 **모든 단어가 가장 긴 단어의 접두사일 때**입니다.

```ts
// 정의를 그대로 옮긴 조각. 집합을 실제로 만들어 크기를 센다.
const prefixCount = (words: string[]): number =>
  new Set(words.flatMap((w) => Array.from({ length: w.length + 1 }, (_, k) => w.slice(0, k)))).size;
```

이 조각은 접두사를 전부 만들어 담으므로 단어 하나마다 그 길이의 제곱에 비례하는 글자를 읽습니다.
트라이는 같은 값을 담는 동안 곁들여 얻으므로 따로 셀 것이 없어요. 제약 규모를 두 식에 넣으면 이렇게 나옵니다.

<!--proof:mathBounds-->

```text
단어 집합                           S  하한 max|w| + 1   실제 V  상한 S + 1  어디인가
{app, apple, ape}                  11                6        7          12  그 사이
{app, bat, cup}                     9                4       10          10  상한과 같다
앞 97 글자가 같은 1,000 단어  100,000              101    1,139     100,001  그 사이
길이 100,000 짜리 단어 하나   100,000          100,001  100,001     100,001  상한이자 하한

제약 규모 S = 100,000 에서 노드 수는 많아야 100,001 개다
  자식을 26 칸 배열로 잡으면 26 × 100,001 = 2,600,026 칸
  자식을 맵으로 잡으면 간선 수만큼이라 많아야 100,000 항목
└ 둘째 줄은 공통 접두사가 하나도 없어 상한과 정확히 같아지는 입력이다
```

여기서 본문의 값만으로는 안 나오는 것이 하나 나옵니다. **자식을 `Σ` 칸 배열로 잡는 구현과 맵으로
잡는 구현이 제약 규모에서 26 배 갈린다**는 것이에요. 노드 수 상한이 `S + 1` 이므로 배열 방식은
`Σ(S + 1)` 칸을 잡는데, 맵 방식은 간선 수만큼이라 `V − 1 ≤ S` 항목입니다.

### 불변식 — 노드의 경로 문자열이 곧 담긴 단어들의 접두사다

파트 1 에서 코드가 동작하는 것을 열한 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 삽입 뒤에 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> `insert` 하나가 끝난 직후, 노드 `v` 까지의 경로가 만드는 문자열을 `path(v)` 라 하면
> `{ path(v) : v 는 트라이의 노드 }` 는 지금까지 담은 단어들의 접두사 집합과 같고, 그중
> `v.end` 가 참인 것만 모으면 담은 단어들의 집합과 같습니다.

```text
삽입 하나를 마친 시점에 참인 것 둘
  앞 문장   노드의 경로 문자열을 모으면       담긴 단어들의 접두사 집합과 같다
  뒤 문장   그중 끝 표시가 참인 것만 모으면   담긴 단어들의 집합과 같다
└ 앞 문장이 startsWith 의 근거이고, 뒤 문장이 search 의 근거다
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 `startsWith` 가 도착 여부만 봐도 되는 근거이고, 뒤
문장은 `search` 가 끝 표시를 봐야 하는 근거예요. 둘 중 하나만 빠져도 두 연산이 왜 마지막 한 줄에서
갈리는지 말할 수 없습니다.

**출발점부터 봅시다.** 아무것도 담지 않은 트라이는 뿌리 하나이고, 뿌리의 경로 문자열은 빈
문자열입니다. 담은 단어가 없으므로 접두사 집합도 빈 문자열 하나뿐이라 앞 문장이 참이고, 끝 표시가
참인 노드가 하나도 없으므로 뒤 문장도 참이에요.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | 뿌리 하나를 만든다 | 접두사가 빈 문자열 하나다 | 담은 단어가 없다 |
| 글자 하나 · 자식이 있다 | 그 자식으로 옮긴다 | 그 경로 문자열이 이미 집합에 있다 | 끝 표시를 건드리지 않는다 |
| 글자 하나 · 자식이 없다 | 만들어 걸고 옮긴다 | 새 단어의 접두사 하나가 집합에 더해진다 | 새 노드의 끝 표시가 거짓이다 |
| 문자열이 끝났다 | 끝 표시를 참으로 둔다 | 노드를 더하지 않는다 | 담은 단어 하나가 집합에 더해진다 |

셋째 줄이 이 논증의 핵심입니다. 새로 만드는 노드의 경로 문자열은 **지금 담는 단어의 접두사**이고,
그것 말고 다른 노드는 생기지 않아요. 그래서 노드 집합이 접두사 집합 밖으로 나가지 않습니다.

| 무엇을 확인하는가 | 근거 |
| --- | --- |
| 접두사인데 노드가 없는 경우가 없다 | 반복문이 글자를 하나도 건너뛰지 않는다 |
| 노드인데 접두사가 아닌 경우가 없다 | 노드는 지금 담는 단어의 글자로만 만들어진다 |
| 끝 표시가 참인데 담은 단어가 아닌 경우가 없다 | 참으로 두는 자리가 문자열이 끝난 그 한 줄뿐이다 |
| 담은 단어인데 끝 표시가 거짓인 경우가 없다 | 반복문이 끝난 노드가 그 단어의 경로 그 자체다 |

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 빈 트라이에 조회한다 | 첫 글자에서 자식이 없다 | 둘 다 거짓이다 |
| 담긴 단어보다 긴 조회 | 마지막 노드에 다음 글자의 자식이 없다 | 둘 다 거짓이다 |
| 같은 단어를 두 번 담는다 | 노드가 하나도 안 늘고 끝 표시가 참에서 참으로 | 답이 그대로다 |
| 짧은 단어를 나중에 담는다 | 새 노드 없이 끝 표시 한 칸만 바뀐다 | `search` 가 참이 된다 |
| 길이 100,000 짜리 단어 하나 | 반복문이 100,000 번 실행된다 | 노드 100,001 개가 만들어진다 |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 삽입에서 **다음 노드로 옮기는 한 줄**이에요.
「어차피 뿌리부터 다시 찾으면 되니 지금 노드를 굳이 이어 가야 하나」라는 생각으로 그 줄을 뿌리
대입으로 바꿔 봅니다.

```ts
for (const ch of word) {
  let next = node.children.get(ch);
  if (next === undefined) { next = new TrieNode(); node.children.set(ch, next); }
  node = this.root;      // 다음 노드로 옮기지 않고 뿌리로 되돌아간다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutantPathReset-->

```text
조회                정본이 낸 답  경로를 안 잇는 답  판정
search("app")                 참               거짓  틀리다
search("appl")              거짓               거짓  같다
startsWith("appl")            참               거짓  틀리다
startsWith("bat")           거짓               거짓  같다
startsWith("e")             거짓                 참  틀리다

정본의 노드 경로 집합   "" a ap app ape appl apple
변이의 노드 경로 집합   "" a p l e
└ 글자가 순서를 잃고 전부 뿌리의 자식이 된다. 변이 쪽 마지막 원소는 어떤 단어의 접두사도 아니다
```

앞 문장이 깨지면 노드의 경로 문자열이 담긴 단어의 접두사가 아니게 되고, 그러면 뒤 문장의 근거도
함께 사라집니다. 끝 표시는 여전히 반복문이 끝난 노드에 남지만, 그 노드가 뿌리라서 「담은 단어」가
아니라 「빈 문자열」을 가리켜요.

```text
변이가 만든 구조
  노드 다섯      뿌리와 그 자식 넷      a p l e 가 전부 뿌리에 걸린다
  경로 문자열    길이 1 짜리 넷         두 글자짜리 접두사가 하나도 없다
  끝 표시        뿌리 하나에 참         담은 단어 셋이 전부 사라진다
└ 글자 하나가 갈래 하나라는 대응이 어긋나면 이 구조가 답할 수 있는 것이 없다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — 자식 맵을 조회하는 것, 노드를 새로 만드는 것, 끝 표시를
읽거나 쓰는 것이에요. 전개의 걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perfCount-->

```text
연산                자식 맵 조회  노드 생성  끝 표시 읽기·쓰기  기본 연산
insert("app")                  3          3                  1          7
insert("apple")                5          2                  1          8
insert("ape")                  3          1                  1          5
search("app")                  3          0                  1          4
search("appl")                 4          0                  1          5
startsWith("appl")             4          0                  0          4
startsWith("bat")              1          0                  0          1
합계                          23          6                  5         34

삽입 쪽 총식   S + (V - 1) + N = 11 + 6 + 3 = 20
조회 쪽 총식   읽은 글자 합 + search 횟수 = 12 + 2 = 14
└ 어느 항에도 담긴 단어의 개수를 곱하는 자리가 없다
```

둘째 줄이 이 표의 요점입니다. `insert("apple")` 은 글자를 다섯 번 읽는데 노드는 둘만 만들어요 —
앞 세 글자를 처리한 T5 에서 하나도 안 만들기 때문입니다. **조회 횟수는 글자 수를 따라가고 생성
횟수는 노드 수를 따라가고**, 두 값이 따로 정해지는 것이 총식을 두 항으로 가르는 이유입니다.

```text
총식 = 담는 쪽 + 묻는 쪽
  담는 쪽   S + (V - 1) + N              자식 맵 조회 + 노드 생성 + 끝 표시 쓰기
  묻는 쪽   읽은 글자 합 + search 횟수   조회 하나가 최대 L 글자
  잡는 칸   2V - 1                       노드마다 끝 표시 하나, 간선마다 항목 하나
└ 어느 항에도 담긴 단어의 개수를 곱하는 자리가 없다
```

제약 규모를 넣으면 담는 쪽이 `100,000 + (V − 1) + N` 이고, `V − 1` 도 `N` 도 `S` 를 넘지 않으므로
세 항의 합이 300,000 을 넘지 않습니다. 목록 대조가 조회 하나에 100,000 글자를 읽던 것과 견주면
조회 `Q` 번의 비용이 `Q · S` 에서 `Q · L` 로 바뀌어요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (조회가 첫 글자에서 끝난다) | `O(L)` | `Θ(1)` — 자식 맵을 한 번만 읽는다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(L)` | 정의되지 않는다 |
| **최악의 경우** (경로가 끝까지 있다) | `O(L)` | `Θ(L)` — 실제로 도달한다 |

가운데 줄의 타이트한 값이 정의되지 않는 것은 **입력 분포가 없기 때문**입니다. 조회 문자열이 어느
자리에서 어긋나는지는 담긴 단어들과 조회 문자열이 함께 정하는 것이라, 분포를 가정하지 않으면
기댓값을 쓸 수 없어요. 삽입은 다릅니다 — 글자를 언제나 끝까지 읽으므로 세 줄이 모두 `Θ(L)` 이에요.

```text
상한과 타이트한 값을 가르는 자리
  그보다 더 읽지 않는다는 것만 말한다   상한이다          O(L)
  실제로 그만큼 읽는다는 것도 말한다    타이트한 값이다   Theta(L)
└ 삽입은 글자를 언제나 끝까지 읽으므로 타이트한 값으로 적을 수 있다. 조회는 도중에 끝날 수 있다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 구조의 특징이에요 —
정렬도, 미리 만드는 표도, 좌표 압축도 하지 않습니다.

```text
총식 = 담기 + 묻기 + 메모리
  담기     Theta(S + N) 시간        자식 맵 조회 S · 노드 생성 V-1 · 끝 표시 쓰기 N
  묻기     O(조회 길이의 합) 시간   조회 하나가 최대 L 글자
  메모리   Theta(V) 칸              노드 V 개 · 간선 V-1 개 · V 는 많아야 S + 1
└ 앞뒤로 붙는 전처리 항이 하나도 없다
```

**보장의 종류를 밝혀 둡니다.** 걸음 수는 최악 보장이지만 **걸음 하나의 비용은 기댓값**이에요.
자식을 `Map` 으로 담았고 그것이 해시 기반이라, 항목 하나를 찾는 데 드는 일이 해시가 흩어지는
정도에 달려 있습니다.

| 무엇 | 보장의 종류 | 무엇에 대한 기댓값인가 |
| --- | --- | --- |
| 지나는 노드 수 | 최악 보장 `L + 1` | - |
| 만드는 노드 수 | 최악 보장 `L` | - |
| 자식 하나를 찾는 일 | 기댓값 상수 | 해시 함수가 글자를 흩는 정도 |
| 자식을 `Σ` 칸 배열로 담으면 | 최악 보장 상수 | - |

마지막 줄이 두 구현을 가르는 자리입니다. `Σ` 칸 배열은 최악 보장을 주지만 노드마다 26 칸을 잡아서
제약 규모에서 2,600,026 칸이 되고, 맵은 기댓값 보장을 주는 대신 간선 수만큼만 잡아요.

#### 최악을 만드는 입력

축이 셋이고 최악을 만드는 입력이 축마다 다릅니다. 값으로 확인해 봅시다.

<!--proof:worstShape-->

```text
입력의 모양                    길이 합  노드 수  그 사전에서 가장 긴 조회가 읽은 글자
길이 100,000 짜리 단어 하나    100,000  100,001                               100,000
앞 97 글자가 같은 1,000 단어   100,000    1,139                                    98
앞 3 글자가 갈리는 1,000 단어  100,000   98,042                                   100
길이 1 짜리 단어 26 개              26       27                                     1

└ 위 세 줄은 길이 합이 똑같이 100,000 인데 노드 수가 여든 배 넘게 갈린다 — 정하는 것은 공유의 정도다
  넷째 줄은 단어가 26 개인데 조회가 1 글자에서 끝난다. 조회 비용은 단어 개수를 안 본다
```

**「담긴 단어가 많으면 조회가 느려진다」는 이 구조에서 성립하지 않습니다.** 물려받은 통념이 여기서는
맞지 않아요 — 넷째 줄은 단어가 26 개인데 조회가 한 번 읽고 끝나고, 첫 줄은 단어가 하나인데 조회가
100,000 번 읽습니다. 조회 비용을 정하는 것은 단어의 개수가 아니라 조회 문자열의 길이예요.

```text
최악은 축마다 다른 입력이 만든다
  연산 하나의 최악        길이 100,000 짜리 문자열             글자를 100,000 번 읽는다
  노드 수의 최악          접두사를 하나도 공유하지 않는 사전   노드 100,001 개
  조회가 가장 짧은 경우   첫 글자부터 없는 조회                1 번 읽고 끝난다
└ 앞의 둘은 길이 합만 보고, 셋째는 사전의 모양을 본다
```

노드 수를 최대로 만들려면 **첫 글자가 서로 다른 단어**를 모아야 하는데, 소문자 영문은 스물여섯
글자뿐이라 단어를 27 개 넘게 담으면 반드시 어느 둘이 첫 글자를 공유합니다. 그래도 상한 `S + 1` 에
도달할 수 있어요 — 길이 100,000 짜리 단어 하나를 담으면 그 하나가 노드 100,001 개를 만듭니다.

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 연산 하나의 읽기 | 길이 100,000 짜리 문자열 | 100,000 |
| 노드 수 | 길이 100,000 짜리 단어 하나 | 100,001 |
| 잡는 칸 | 같은 입력 | 200,001 |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 담긴 단어들의 **접두사 하나를 노드 하나**로 두어
같은 앞부분을 한 자리에만 적었고, 그래서 연산 하나가 받은 문자열의 길이만 따라가며, `search` 와
`startsWith` 는 **끝 표시 한 칸**을 보느냐 마느냐로 갈립니다.

```text
  1.   노드 하나가 접두사 하나다           경로가 곧 문자열이다
  2.   글자를 읽을 때마다 한 칸 내려간다   담긴 단어의 개수를 안 본다
  3.   끝 표시 한 칸이 두 연산을 가른다    search 와 startsWith
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 는 `insert("apple")` 의 앞 세 글자를 처리한 걸음이었고,
자식이 셋 다 이미 있어 새 노드가 0 개였어요. 그런데 이 걸음에서도 자식 맵 조회는 세 번 일어납니다.
이미 있는 것이 뻔한데 그 조회를 왜 건너뛰지 않을까요?

```text
T5   insert("apple") 의 a p p   읽은 글자 3   새 노드 0   노드 수 4 그대로
```

건너뛸 수 있는지 **미리 알 수 없기** 때문입니다. 어디까지 이미 있는지는 그 자리에서 자식 맵을

들고 있으려면 그 값을 어딘가에 적어 두어야 하는데, 적어 두는 비용이 읽는 비용과 같습니다.
