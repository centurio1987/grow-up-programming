# 트라이 — 같은 앞부분을 한 노드에 모으면 조회가 담긴 단어의 개수를 안 보는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 단어를 목록에
담고 매번 대조하는 방법에서 출발해 글자마다 갈래를 나누는 방법까지 가고, 그 방법을 준비되는 차례대로
값으로 푼 뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

소문자 단어를 담아 두고 두 가지를 따로 답하는 구조를 만듭니다. 하나는 **그 문자열이 담긴 단어인가**
(`search`)이고, 다른 하나는 **그 문자열로 시작하는 단어가 하나라도 있는가**(`startsWith`)예요. 문자열의
앞에서부터 잘라 낸 조각을 **접두사**라고 부르니, 둘째 질문은 「이 문자열이 담긴 단어의 접두사인가」와
같습니다.

이 글이 만드는 구조의 이름은 **트라이**(trie)입니다. 트라이는 **담은 단어들의 접두사마다 노드를 하나씩
두고, 접두사에 글자 하나를 붙인 접두사를 그 노드의 자식으로 잇는 나무**예요. 단어 `app` · `apple` ·
`ape` 를 담은 트라이를 그리면 이렇습니다.

<!--fig:concept-trie-->
![app · apple · ape 를 담은 트라이](./figs/concept-trie.svg)

노드 안의 이름은 뿌리에서 그 노드까지 간선의 글자를 차례로 이은 문자열이고, 이것을 그 노드의 **경로
문자열**이라고 부릅니다. 뿌리의 경로 문자열은 빈 문자열이에요. 글자는 노드가 아니라 간선에 붙어 있어서,
세 단어가 함께 가진 `a` · `ap` 는 노드 하나씩으로 한 번만 적힙니다. 노드 안에 「끝 표시」가 적힌 셋은
경로 문자열이 담긴 단어 그 자체인 노드예요. 노드가 있다는 것과 그 노드가 단어라는 것이 다른 이야기라서,
끝 표시 한 칸을 따로 둡니다.

<!--proof:concept-answers-->

| 문자열 | 그 경로의 노드 | 끝 표시 | search | startsWith |
| --- | --- | --- | --- | --- |
| `app` | 있다 | 있다 | 참 | 참 |
| `appl` | 있다 | 없다 | 거짓 | 참 |
| `apple` | 있다 | 있다 | 참 | 참 |
| `apz` | 없다 | - | 거짓 | 거짓 |
| `bat` | 없다 | - | 거짓 | 거짓 |

두 연산의 답이 갈리는 문자열은 `appl` 1 개이고, 그 자리에는 노드가 있지만 끝 표시가 없습니다.

<!--/proof-->

그 한 칸이 두 연산을 가릅니다. `startsWith` 는 글자를 따라 노드에 도착했는가만 보고, `search` 는 도착한
노드의 끝 표시까지 봐요. 어느 쪽이든 글자를 하나 읽을 때마다 노드를 한 칸 내려가므로, 연산 하나가 하는
일은 **받은 문자열의 글자 수**로 정해집니다. 담긴 단어가 열 개든 만 개든 걸음 수가 같아요. 비용을 결과만
적으면 받은 문자열의 길이 `L` 에 비례하는 `O(L)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **접두사가 무엇인지.** 문자열의 앞에서부터 잘라 낸 조각입니다. 빈 문자열과 문자열 자기 자신도
  접두사에 들어요.
- **키로 값을 찾는 맵을 쓰는 법.** 이 글은 글자 하나를 키로, 자식 노드를 값으로 담습니다. 항목 하나를
  넣고 꺼내는 데 드는 일이 맵에 담긴 항목 수와 상관없다는 것이 필요해요.
- **참조로 이어진 구조.** 노드가 다른 노드를 가리키고, 그 가리킴을 따라가며 자료를 다루는 모양입니다.
  뿌리 하나에서 시작해 아래로 뻗고 되돌아오는 길이 없는 것이 트리예요.
- **트리에서 부모 · 자식 · 깊이가 무엇인지.** 이 글의 노드는 자식이 여럿일 수 있고, 몇 개인지 미리
  정해져 있지 않습니다. 깊이는 뿌리에서 그 노드까지 지나는 간선의 수예요.

이름이 비슷한 과제 넷을 나란히 두면 이 글이 다루는 범위가 갈립니다.

| 과제 | 이 글에서 |
| --- | --- |
| 담긴 단어인지, 담긴 단어의 접두사인지 묻는다 | 다룬다 |
| 자식이 하나뿐인 사슬을 노드 하나로 접는다 | 다루지 않는다 — [`radixTree`](../radixTree/radixTree-guide.md) |
| 여러 단어를 긴 글 한 번의 순회로 동시에 찾는다 | 다루지 않는다 — [`ahoCorasick`](../ahoCorasick/ahoCorasick-guide.md) |
| 문자열 가운데 어디든 있는 조각을 찾는다 | 다루지 않는다 — [`suffixArray`](../suffixArray/suffixArray-guide.md) |

### 아이디어를 떠올리는 과정 — 단어 목록 대조에서 글자마다 갈래 나누기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 클래스 하나가 단어를 담고 두 가지 조회에
답합니다.

```ts
class Trie {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- 입력: 소문자 영문(`a`–`z`)으로만 된 길이 1 이상의 문자열. `insert` 는 담고, 나머지 둘은 묻습니다.
- 출력: `search` 는 그 문자열이 담긴 단어이면 참, `startsWith` 는 그 문자열로 시작하는 담긴 단어가
  하나라도 있으면 참입니다. 같은 단어를 여러 번 담아도 답이 달라지지 않아요.
- 규모: 문자열 하나의 길이 `L ≤ 100,000`, 담은 모든 단어의 길이 합 `S ≤ 100,000`. 조회는 여러 번 걸고,
  이 글은 조회 100,000 번으로 잽니다. 비용은 흔한 채점 환경의 예산인 1 초에 대어 봅니다.

이 글이 쓰는 기호는 여섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `L` | 이번 연산이 받은 문자열의 길이 | `1 ≤ L ≤ 100,000` |
| `S` | 담은 모든 단어의 길이 합 | `S ≤ 100,000` |
| `N` | 담은 단어의 개수 | `N ≤ S` |
| `V` | 트라이의 노드 개수. 뿌리를 포함합니다 | 「아이디어 상세」가 값으로 셉니다 |
| `Σ` | 문자 집합의 크기 | 소문자 영문이라 26 |
| `Q` | 같은 구조에 거는 조회 횟수 | 이 글은 `Q = 100,000` 으로 잽니다 |

가장 먼저 떠오르는 방법은 단어를 배열에 그대로 담고, 물을 때마다 그 배열을 앞에서부터 대조하는 것입니다.
답을 틀리지 않는 방법이에요.

```ts
class WordList {
  private words: string[] = [];
  insert(word: string) { this.words.push(word); }
  search(word: string) { return this.words.includes(word); }                // 단어마다 전체 대조
  startsWith(p: string) { return this.words.some((w) => w.startsWith(p)); } // 단어마다 앞 L 글자
}
```

비용은 **읽은 글자 수**로 셉니다. 단어 하나를 대조할 때 어긋나는 자리까지 읽으니, 조회 하나가 읽는
글자는 담긴 단어들의 길이 합까지 갈 수 있어요. 길이 합이 과제 규모의 최댓값인 사전에서 이 방법과, 이 글이
만들 트라이를 함께 세어 보면 이렇습니다.

<!--proof:origin-cost-->

| 조회 횟수 | 목록 대조가 읽은 글자 | 트라이가 읽은 글자 | 목록 대조 시간(초당 1 억 번) |
| ---: | ---: | ---: | ---: |
| 1,000 | 98,000,000 | 98,000 | 0.98 초 |
| 100,000 | 9,800,000,000 | 9,800,000 | 98.00 초 |

사전은 앞 97 글자가 같은 길이 100 짜리 단어 1,000 개(길이 합 100,000)이고, 조회는 앞 97 글자까지 맞고 그다음에서 어긋나는 없는 문자열 하나입니다. 조회 하나에 목록 대조는 98,000 글자, 트라이는 98 글자를 읽었고, 여러 번은 그 값에 조회 횟수를 곱했습니다.

<!--/proof-->

조회가 1,000 번이면 1 초 안에 들지만, 조회가 100,000 번이면 98 초입니다. 예산의 98 배예요. 트라이는 같은
조회에 조회 문자열의 길이만큼만 읽습니다. 그 차이가 어디서 나오는지 보려면 목록 대조가 무엇을
되풀이하는지부터 세어 봐야 해요. 세 단어 `app` · `apple` · `ape` 를 담고 `startsWith("apz")` 를 물어
봅시다.

<!--proof:origin-apz-->

| 담긴 단어 | 맞은 글자 | 어긋난 자리 | 읽은 글자 |
| --- | --- | --- | ---: |
| `app` | a · p | 3 번째 | 3 |
| `apple` | a · p | 3 번째 | 3 |
| `ape` | a · p | 3 번째 | 3 |

목록 대조는 모두 9 글자를 읽었고, 그중 6 글자는 세 단어가 함께 가진 앞부분을 단어마다 다시 읽은 것입니다. 앞부분을 한 번만 읽으면 3 글자로 끝납니다.

<!--/proof-->

세 단어가 앞 두 글자 `a` · `p` 를 함께 가졌는데, 목록 대조는 그것을 쓰지 않고 단어마다 처음부터 다시
읽었습니다. 단어가 하나 늘 때마다 같은 앞부분을 한 번 더 읽는 셈이에요. 조회 하나에 알아야 할 것은
단어마다의 대조 결과가 아니라 「이 글자들을 차례로 따라갈 수 있는가」 하나입니다. 같은 조회 넷을 목록
대조와, 앞부분을 한 번만 읽는 트라이로 처리하고 읽은 글자를 나란히 세었습니다.

<!--proof:origin-four-->

| 조회 | 답 | 목록 대조가 읽은 글자 | 트라이가 읽은 글자 | 조회 길이 |
| --- | --- | ---: | ---: | ---: |
| `search("app")` | 참 | 3 | 3 | 3 |
| `search("appl")` | 거짓 | 10 | 4 | 4 |
| `startsWith("appl")` | 참 | 7 | 4 | 4 |
| `startsWith("bat")` | 거짓 | 3 | 1 | 3 |

읽은 글자의 합은 목록 대조가 23, 트라이가 12 입니다. 트라이 쪽은 네 줄 모두 조회 길이 이하입니다.

<!--/proof-->

목록 대조는 `search("appl")` 에서 10 글자를 읽었어요. `app` 과 `apple` 을 각각 대조하고 `ape` 까지
대조했기 때문입니다. 트라이는 네 줄 모두 조회 길이 이하에서 끝났고, `startsWith("bat")` 는 첫 글자에서
끝났어요. 여기서 관찰한 것은 하나입니다. **같은 앞부분을 한 번만 읽으면 조회 하나의 비용이 담긴 단어의
개수와 상관없어집니다.**

그 관찰을 구조로 세우기 전에 가장 단순한 후보부터 시험합니다. 「첫 글자가 같은 단어끼리 스물여섯 묶음으로
나눠 담으면, 묶음 하나 안에서만 대조하면 되지 않나」예요. 묶음을 고르는 데 글자 하나를 읽고, 그 안에서는
목록 대조를 합니다.

<!--proof:origin-bucket-->

| 조회 | 답 | 목록 대조 | 첫 글자로 나눈 묶음 | 글자마다 나눈 트라이 |
| --- | --- | ---: | ---: | ---: |
| `startsWith("appl")` | 참 | 7 | 8 | 4 |
| `startsWith("apz")` | 거짓 | 9 | 10 | 3 |
| `startsWith("bat")` | 거짓 | 3 | 1 | 1 |

담긴 단어가 모두 a 로 시작해 a 묶음 하나에 3 개가 다 들어갑니다. a 로 시작하는 조회 2 개에서는 첫 글자로 나눈 쪽이 목록 대조보다 1 글자씩 더 읽었습니다.

<!--/proof-->

**후보가 부족합니다.** 첫 글자가 같은 단어들 안에서는 아무것도 줄지 않아요. 줄어드는 것은 `bat` 처럼 첫
글자부터 다른 조회뿐입니다. 과제 규모의 사전에서는 1,000 단어가 앞 97 글자를 함께 가져서 전부 한 묶음에
들어가고, 조회 하나가 목록 대조보다 1 글자 더 읽어요. 첫 글자로 나눈 것처럼 묶음 안을 둘째 글자로 또
나누고, 그 안을 셋째 글자로 또 나눠야 합니다. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **글자마다 갈래 나누기**입니다. 첫 글자로 나누는 일을 모든 글자에서 되풀이하면,
같은 앞부분을 가진 단어들이 끝까지 같은 갈래를 지나고 앞부분은 한 번만 적혀요. 그 갈래를 모은 구조가
「전체 컨셉」에서 본 트라이입니다. 갈래 하나를 어떻게 적는지, 단어를 담을 때 어디까지 이어 쓰고 어디부터
새로 만드는지, 두 조회가 어디서 갈리는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 글자마다 갈래 나누기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **담은 단어들의 접두사마다 노드를 하나 두고, 글자를 하나 읽을
때마다 그 글자의 자식으로 한 칸 내려갑니다.** 이 방법은 트라이라는 구조 위에서 동작하는데, 처음 보는
사람에게는 「노드 하나가 접두사 하나」라는 읽기가 낯설어요. 그래서 트라이를 먼저 따로 설명하고, 그다음
실현하는 순서대로 네 단계를 설명합니다. 앞 단계에서 만든 것을 뒤 단계에서 쓰는 순서예요.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 처음 한 번 | 1단계 노드 모양 정하기 | 자식 맵 하나와 끝 표시 한 칸을 든 노드를 정하고 뿌리를 만든다 | — |
| 담을 때 | 2단계 없는 노드만 만들기 | 글자를 따라 내려가며 자식이 없는 자리에만 노드를 만든다 | 1단계의 뿌리와 자식 맵 |
| 담을 때 | 3단계 끝 표시 남기기 | 마지막으로 도착한 노드의 끝 표시를 참으로 둔다 | 2단계가 도착한 노드 |
| 물을 때 | 4단계 같은 내려가기로 두 조회 답하기 | 글자를 따라 내려간 뒤 끝 표시를 보느냐로 둘을 가른다 | 2단계의 경로 · 3단계의 끝 표시 |

#### 먼저 알아 둘 개념 — 트라이

트라이는 **담은 단어들의 접두사마다 노드를 하나씩 두고, 접두사에 글자 하나를 붙인 접두사를 자식으로 잇는
나무**입니다. 글자는 부모에서 자식으로 가는 간선에 붙고, 노드는 뿌리에서 자기까지 이은 글자들, 곧 경로
문자열 하나를 뜻해요. 노드마다 그 경로 문자열이 담긴 단어인가를 끝 표시 한 칸에 적습니다.

##### 입력 위의 트라이

단어 셋이 노드 일곱을 어떻게 나눠 쓰는지 보겠습니다. 노드마다 그 경로 문자열로 시작하는 담은 단어의 수를
적었어요.

<!--fig:build-trie-share-->
![노드마다 그 경로로 시작하는 담은 단어의 수](./figs/build-trie-share.svg)

뿌리 · `a` · `ap` 는 세 단어가 모두 지나는 노드라 3 이고, `ap` 에서 `app` 쪽과 `ape` 쪽으로 갈라져요.
`app` 은 `app` 과 `apple` 이 지나서 2 이고, 그 아래 `appl` · `apple` 은 `apple` 혼자 지납니다. 단어 하나는
뿌리에서 자기 노드까지 이어진 길 하나이고, 두 단어가 함께 가진 앞부분은 두 길이 겹치는 부분이에요.

##### 노드 하나를 읽는 법

노드 `appl` 을 골라 읽어 보겠습니다. 뿌리에서 출발해 간선의 글자를 하나씩 이으며 내려가요.

<!--fig:build-read-one-->
![노드 appl 을 읽는 길 — 뿌리에서 간선의 글자를 차례로 잇는다](./figs/build-read-one.svg)

<!--proof:build-read-one-->

| 깊이 | 지나온 간선의 글자 | 도착한 노드 | 경로 문자열 | 끝 표시 |
| ---: | --- | --- | --- | --- |
| 0 | - | 뿌리 | 빈 문자열 | 거짓 |
| 1 | a | a | `a` | 거짓 |
| 2 | p | ap | `ap` | 거짓 |
| 3 | p | app | `app` | 참 |
| 4 | l | appl | `appl` | 거짓 |

노드 appl 의 끝 표시는 거짓이라 search("appl") 는 거짓입니다. 노드가 있으니 startsWith("appl") 는 참입니다.

<!--/proof-->

깊이가 한 칸 늘 때마다 경로 문자열이 글자 하나씩 길어지고, 깊이 4 에서 `appl` 이 됩니다. 그 노드의 끝
표시가 거짓이니 `appl` 은 담긴 단어가 아니지만, 노드가 있으니 어떤 담긴 단어의 접두사예요. 노드의 이름을
경로 문자열로 적은 것은 이 때문입니다. 이름만 보면 그 노드까지 가는 길과 그 노드가 뜻하는 접두사가 함께
나와요.

##### 노드끼리의 관계

부모와 자식은 경로 문자열로 이어져 있습니다. 일곱 노드의 부모 · 들어오는 간선의 글자 · 자식을 모두
적었어요.

<!--proof:build-relations-->

| 노드 | 깊이 | 부모 | 들어오는 간선의 글자 | 자식 | 끝 표시 |
| --- | ---: | --- | --- | --- | --- |
| 뿌리 | 0 | 없음 | - | a | 거짓 |
| a | 1 | 뿌리 | a | ap | 거짓 |
| ap | 2 | a | p | app · ape | 거짓 |
| app | 3 | ap | p | appl | 참 |
| ape | 3 | ap | e | 없음 | 참 |
| appl | 4 | app | l | apple | 거짓 |
| apple | 5 | appl | e | 없음 | 참 |

뿌리를 뺀 노드 6 개 가운데 6 개에서 부모의 경로 문자열 뒤에 들어오는 간선의 글자를 붙이면 자기 경로 문자열이 됩니다. 끝 표시가 참인 노드는 app · ape · apple 3 개로 담은 단어와 같습니다.

<!--/proof-->

세 가지 관계가 표에서 그대로 읽힙니다.

| 관계 | 표에서 | 뜻 |
| --- | --- | --- |
| 부모의 경로 문자열 + 글자 = 자식의 경로 문자열 | `ap` 에 `p` 를 붙이면 `app`, `e` 를 붙이면 `ape` | 노드는 자기 글자를 들지 않는다. 글자는 들어오는 간선에 있다 |
| 깊이 = 경로 문자열의 길이 | `apple` 은 깊이 5 | 길이 `L` 인 문자열은 뿌리에서 `L` 칸 내려간 자리다 |
| 형제는 부모의 경로 문자열을 함께 갖고 마지막 글자만 다르다 | `app` 과 `ape` 는 둘 다 `ap` 아래 | 한 부모의 자식은 글자마다 하나뿐이다 |

셋째 관계가 조회를 한 갈래로 만듭니다. 노드 하나에서 글자 하나로 갈 수 있는 자식이 많아야 하나라서, 글자를
읽으면 갈 곳이 정해져요.

##### 단어마다 따로 적은 사슬과의 차이

트라이를 처음 보면 「단어마다 글자를 노드로 늘어놓은 사슬을 뿌리 아래에 여럿 매단 것」으로 읽기 쉽습니다.
같은 세 단어를 그 모양으로 그리면 이렇게 돼요.

<!--fig:build-unshared-->
![단어마다 따로 적은 사슬 — 노드 12 개](./figs/build-unshared.svg)

이 모양에는 이름이 `a` 인 노드가 셋, `ap` 인 노드가 셋 있습니다. 같은 접두사가 노드 여럿으로 흩어져서
`a` 를 읽고 어느 쪽으로 내려가야 할지 정할 수 없고, 결국 사슬마다 따로 대조하는 목록 대조가 돼요. 트라이는
같은 접두사를 노드 하나로 모읍니다. 단어 집합 넷에서 두 모양의 노드 수를 세었습니다.

<!--proof:build-node-count-->

| 단어 집합 | 길이 합 | 단어마다 따로 적은 사슬의 노드 | 트라이의 노드 |
| --- | ---: | ---: | ---: |
| {app, apple, ape} | 11 | 12 | 7 |
| {app, bat, cup} | 9 | 10 | 10 |
| 앞 97 글자가 같은 1,000 단어 | 100,000 | 100,001 | 1,139 |
| 앞 3 글자가 갈리는 1,000 단어 | 100,000 | 100,001 | 98,042 |

둘째 줄은 공유할 앞부분이 없어 두 값이 10 으로 같습니다. 셋째 줄과 넷째 줄은 길이 합이 같은데 트라이의 노드 수가 86 배 넘게 갈립니다.

<!--/proof-->

두 모양의 노드 수가 같아지는 것은 둘째 줄처럼 공유할 앞부분이 하나도 없을 때뿐이에요. 앞부분을 많이 함께
가질수록 트라이 쪽이 줄어듭니다.

##### 노드가 접두사 하나씩인 까닭

이 모양은 두 조회가 요구하는 것에서 나옵니다. `startsWith` 는 담긴 단어의 **어느 접두사든** 물을 수
있으니, 모든 접두사에 도착할 자리가 있어야 해요. 그래서 끝 노드만이 아니라 길 도중의 노드도 전부 둡니다.
글자 하나를 읽고 갈 곳이 하나로 정해지려면 같은 접두사가 노드 하나여야 하고요. 그리고 `search` 는 도착한
접두사가 단어인지를 따로 물으니 끝 표시가 필요합니다.

| 조회가 요구하는 것 | 모양에서 채우는 것 |
| --- | --- |
| 담긴 단어의 어느 접두사든 도착할 자리가 있다 | 길 도중의 노드도 전부 둔다 |
| 글자 하나를 읽으면 갈 곳이 하나로 정해진다 | 같은 접두사는 노드 하나다 |
| 도착한 접두사가 단어인지 가른다 | 노드마다 끝 표시 한 칸을 둔다 |

#### 1단계 — 노드 모양 정하기

노드 하나가 드는 것은 둘입니다. 글자를 키로 자식 노드를 찾는 맵 `children` 과, 경로 문자열이 담긴 단어인가를
적는 끝 표시 `end` 예요. 노드는 자기 글자를 들지 않습니다. 글자는 부모의 `children` 에서 이 노드를 찾는
키로만 있어요.

```ts
class TrieNode {
  readonly children = new Map<string, TrieNode>(); // 글자 하나 → 자식 노드
  end = false;                                     // 경로 문자열이 담긴 단어인가
}
```

처음에는 뿌리 하나만 만듭니다. 뿌리의 경로 문자열은 빈 문자열이고, 자식이 없고, 끝 표시는 거짓이에요.
크기는 담은 단어가 정합니다. 노드 하나가 접두사 하나이므로 노드 수 `V` 는 담은 단어들의 서로 다른 접두사
수이고, 간선은 뿌리를 뺀 노드마다 하나라 `V − 1` 개예요. 「단어마다 따로 적은 사슬과의 차이」의 표에서 전개
입력은 노드 7 개였습니다.

| 칸 | 개수 | 전개 입력에서 |
| --- | --- | --- |
| 노드 | `V` — 서로 다른 접두사 수 | 표의 첫 줄 |
| `children` 의 항목 | `V − 1` — 간선 수 | 노드 수보다 하나 적다 |
| 끝 표시 | `V` 칸 중 참은 서로 다른 담은 단어 수 | `app` · `ape` · `apple` |

#### 2단계 — 없는 노드만 만들기

단어를 담을 때는 뿌리에서 출발해 글자를 하나씩 읽고, 그 글자의 자식이 있으면 그리로 옮기고 없으면 만들어
걸고 옮깁니다. 판단은 글자마다 「그 글자의 자식이 있는가」 하나예요. 세 단어를 차례로 담으면 세 경우가
한 번씩 나옵니다.

<!--proof:build-insert-cases-->

| 담는 단어 | 이어 쓴 노드 | 새로 만든 노드 | 노드 수 |
| --- | --- | --- | --- |
| `app` | 없음 | a · ap · app | 1 → 4 |
| `apple` | a · ap · app | appl · apple | 4 → 6 |
| `ape` | a · ap | ape | 6 → 7 |

<!--/proof-->

쉬운 경우는 `app` 처럼 첫 글자부터 자식이 없을 때입니다. 글자 수만큼 노드를 새로 만들어요. 불안한 경우는
**앞부분이 이미 있을 때**입니다. 어디까지 이어 쓰고 어디부터 만들지를 미리 알아야 할 것 같지만, 글자마다
자식이 있는지만 보면 저절로 갈려요. `apple` 을 담는 걸음을 무대로 보면 이렇습니다. 굵은 테가 이번 걸음에
만든 노드, 옅게 채운 노드와 굵은 간선이 이번 걸음에 지나간 자리, 점선이 아직 없는 노드예요.

<!--fig:build-apple-->
![insert("apple") — 앞 세 글자는 이어 쓰고 뒤 두 글자는 만든다](./figs/build-apple.svg)

<!--proof:build-apple-letters-->

| 차례 | 글자 | 서 있던 노드 | 그 글자의 자식 | 한 일 | 노드 수 |
| ---: | --- | --- | --- | --- | ---: |
| 1 | a | 뿌리 | 있다 | 이어 쓴다 | 4 |
| 2 | p | a | 있다 | 이어 쓴다 | 4 |
| 3 | p | ap | 있다 | 이어 쓴다 | 4 |
| 4 | l | app | 없다 | 만든다 | 5 |
| 5 | e | appl | 없다 | 만든다 | 6 |

<!--/proof-->

앞 세 글자에서는 자식이 셋 다 있어 노드 수가 4 그대로이고, `l` 과 `e` 에서 하나씩 만들어 6 이 됩니다.
`ape` 는 그 둘이 섞여서 `a` · `p` 를 이어 쓰고 `e` 에서 갈라져요. 빠뜨리는 글자가 없다는 것은 반복의
종료 조건으로 말할 수 있습니다. 반복은 단어의 글자를 앞에서부터 하나씩 다 쓰고 끝나고, 한 바퀴에 노드를
**정확히 한 칸** 내려가요. 그래서 반복이 끝났을 때 `L` 칸을 내려와 있고, 서 있는 노드의 경로 문자열이 곧
담는 단어입니다. 건너뛴 글자가 있다면 경로 문자열이 단어보다 짧을 텐데, 그런 자리가 없어요.

#### 3단계 — 끝 표시 남기기

반복이 끝나면 서 있는 노드의 끝 표시를 참으로 둡니다. 2단계가 그 노드의 경로 문자열이 담는 단어라는 것을
보장했으니, 이 한 칸이 「이 단어를 담았다」의 기록 전부예요. 가장 불안한 경우는 **이미 있는 노드에서
문자열이 끝날 때**입니다. `apple` 만 담은 뒤 `app` 을 담아 봅시다.

<!--proof:build-end-only-->

| 상태 | apple 만 담았을 때 | app 을 더 담은 뒤 |
| --- | ---: | ---: |
| 노드 수 | 6 | 6 |
| 노드 app 의 끝 표시 | 거짓 | 참 |
| search("app") | 거짓 | 참 |

새로 만든 노드는 0 개이고, 바뀐 것은 끝 표시 한 칸뿐입니다.

<!--/proof-->

2단계는 노드를 하나도 만들지 않았어요. `a` · `p` · `p` 가 모두 `apple` 을 담을 때 생긴 노드입니다. 그런데도
`search("app")` 의 답이 거짓에서 참으로 바뀌었고, 그 차이를 만든 것은 끝 표시 한 칸이에요. 노드가 있다는
것만으로는 담은 단어인지를 알 수 없다는 것이 여기서 값으로 보입니다. 같은 단어를 다시 담으면 참을 다시
참으로 둘 뿐이라 답이 그대로예요.

#### 4단계 — 같은 내려가기로 두 조회 답하기

조회도 뿌리에서 출발해 글자를 따라 내려갑니다. 2단계와 다른 점은 자식이 없을 때 만들지 않고 그 자리에서
멈춘다는 것뿐이에요. 멈췄다면 그 문자열은 어떤 담긴 단어의 접두사도 아니니 두 조회가 모두 거짓입니다.
끝까지 내려와 노드에 도착했다면 거기서 둘이 갈려요. `startsWith` 는 도착했으니 참이고, `search` 는 도착한
노드의 끝 표시를 답합니다. 경계에 있는 조회를 섞어 여섯을 걸었습니다.

<!--proof:build-queries-->

| 조회 문자열 | 읽은 글자 | 도착한 노드 | 끝 표시 | search | startsWith |
| --- | ---: | --- | --- | --- | --- |
| `ap` | 2 | ap | 거짓 | 거짓 | 참 |
| `appl` | 4 | appl | 거짓 | 거짓 | 참 |
| `apple` | 5 | apple | 참 | 참 | 참 |
| `apz` | 3 | 없음 — 3 번째 글자 z 에서 끊김 | - | 거짓 | 거짓 |
| `bat` | 1 | 없음 — 1 번째 글자 b 에서 끊김 | - | 거짓 | 거짓 |
| `applepie` | 6 | 없음 — 6 번째 글자 p 에서 끊김 | - | 거짓 | 거짓 |

<!--/proof-->

`ap` 와 `appl` 은 노드에 도착했지만 끝 표시가 거짓이라 두 조회의 답이 갈립니다. `apz` · `bat` 는 도중에
끊겨 둘 다 거짓이고, `bat` 는 첫 글자에서 끊겨 한 글자만 읽었어요. `applepie` 는 담긴 단어 `apple` 보다
길어서 `apple` 노드까지 내려온 뒤 여섯째 글자에서 끊깁니다. 어느 경우든 읽은 글자는 조회 길이를 넘지 않아요.

#### 이 방법이 기대는 전제

글자마다 갈래 나누기는 아래 두 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 키를 앞에서부터 글자 하나씩 떼어 읽을 수 있다 | 2단계 · 4단계에서 글자 하나마다 한 칸 내려간다 | 갈래를 나눌 기준이 없다 |
| 노드 하나에서 글자로 자식을 찾는 일이 담긴 단어 수와 상관없다 | 한 칸 내려가는 비용 | 한 칸마다 자식을 하나씩 차례로 읽어야 해서 담긴 단어가 늘면 함께 는다 |

묻는 것이 접두사라는 것도 전제입니다. 트라이는 뿌리에서 시작하는 길만 두므로, 문자열 가운데 어디든 있는
조각을 물으면 답할 자리가 없어요. 그 과제는 「시작하기 전에」의 표가 가리킨 다른 구조가 맡습니다.

#### 자식을 맵으로 두는 까닭

1단계는 자식을 맵에 담았습니다. 소문자 영문은 26 글자뿐이니 노드마다 26 칸 배열을 두고 글자의 순번으로
바로 찾는 방법도 있어요. 두 방식이 자식을 담는 데 쓰는 칸을 단어 집합 넷에서 세었습니다.

<!--proof:build-child-cells-->

| 단어 집합 | 노드 수 V | 26 칸 배열의 칸 26V | 맵의 항목 V − 1 | 배열 칸 ÷ 맵 항목 |
| --- | ---: | ---: | ---: | ---: |
| {app, apple, ape} | 7 | 182 | 6 | 30.3 |
| 앞 97 글자가 같은 1,000 단어 | 1,139 | 29,614 | 1,138 | 26.0 |
| 앞 3 글자가 갈리는 1,000 단어 | 98,042 | 2,549,092 | 98,041 | 26.0 |
| 길이 100,000 짜리 단어 하나 | 100,001 | 2,600,026 | 100,000 | 26.0 |

배열 쪽은 노드마다 26 칸을 잡아 넷째 줄에서 2,600,026 칸이 되고, 맵 쪽은 실제로 있는 간선만 담아 같은 입력에서 100,000 항목입니다.

<!--/proof-->

배열 쪽은 노드마다 26 칸을 잡으므로 칸 수가 노드 수의 26 배이고, 맵 쪽은 실제로 있는 간선만 담아 노드 수보다
하나 적습니다. 과제 규모의 가장 긴 단어 하나에서 두 쪽이 26 배 갈려요. 그 대신 배열은 글자 하나로 자식을
찾는 일이 늘 한 번의 칸 읽기이고, 맵은 해시가 글자를 흩는 정도에 기대는 기댓값 상수입니다. 이 글은 칸을
적게 쓰는 맵을 쓰고, 두 보장의 차이는 「비용 계산」에서 다시 적습니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇게 됩니다. 이렇게 하면 조회 하나가 읽는 글자가 담긴 단어들의 길이
합이 아니라 조회 문자열의 길이만큼으로 줄어요.

1. 뿌리 하나를 만든다
2. 담을 때는 뿌리에서 출발해 글자마다 자식이 없으면 만들고, 그 자식으로 옮긴다
3. 반복이 끝나면 서 있는 노드의 끝 표시를 참으로 둔다
4. 물을 때는 뿌리에서 글자를 따라 내려가다 자식이 없으면 두 조회 모두 거짓이고, 도착하면 `startsWith` 는 참, `search` 는 끝 표시를 답한다

### 수행으로 알아보는 알고리즘 — 세 단어를 담고 네 번 묻는다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const trie = new Trie();
trie.insert("app");
trie.insert("apple");
trie.insert("ape");
// 그다음 search("app") · search("appl") · startsWith("appl") · startsWith("bat") 를 묻는다
```

왜 하필 이 셋과 이 넷일까요? 삽입의 세 경우가 다 나오기 때문이에요. 전부 새로 만드는 삽입(`app`), 앞부분을
이어 쓰고 뒤만 만드는 삽입(`apple`), 도중에 다른 글자로 갈라지는 삽입(`ape`)입니다. 조회 넷은 답이 참과
거짓으로 둘씩이고, **같은 문자열 `appl` 에 두 연산이 다른 답을 내는 자리**와 첫 글자에서 끊기는 자리를
포함해요.

```text
절차 전체를 한 장으로
  T1       뿌리 하나로 시작한다
  T2~T7    단어 셋을 담는다
             삽입마다 뿌리에서 출발한다       ① 뿌리에서 출발
             글자마다 자식이 없으면 만든다    ② 없을 때만 만든다
             마지막 노드에 끝 표시를 남긴다   ③ 단어 끝 표시
  T8~T11   네 번 묻는다
             글자를 따라 내려간다             ⑥ 자식이 없으면 null
             끝 표시까지 본다                 ④ search 의 마지막 한 줄
             도착 여부만 본다                 ⑤ startsWith 의 마지막 한 줄
```

#### 1. 노드 하나의 모양을 정한다

첫 조각은 노드입니다. 자식을 담는 맵 하나와 끝 표시 한 칸이 전부예요. 트라이 자체는 뿌리 노드 하나를 들고
시작합니다.

```ts
class TrieNode {
  readonly children = new Map<string, TrieNode>();
  end = false;
}

export class Trie {
  private readonly root = new TrieNode();
}
```

실행하면 이렇게 나옵니다. 빈 트라이의 뿌리를 열어 보고, 아무것도 안 담은 채로 두 조회를 걸었어요.

<!--proof:walk-node-->

```text
new Trie()        →  노드 1 개(뿌리) · 뿌리의 children 0 개 · end = false
search("a")       →  false
startsWith("a")   →  false
```

<!--/proof-->

빈 트라이가 뿌리 하나라는 것이 이 조각의 두 번째 일입니다. 뿌리에 자식이 없으니 어떤 조회든 첫 글자에서
끊겨 거짓이 나와요. 빈 트라이를 따로 다루는 줄이 필요 없습니다.

#### 2. 글자를 따라 내려가며 없는 노드만 만든다

둘째 조각은 삽입입니다. 뿌리에서 출발해 글자를 하나씩 읽고, 그 글자의 자식이 없을 때만 새 노드를 만들어
걸어요.

```ts
insert(word: string): void {
  let node = this.root;                    // ① 뿌리에서 출발한다
  for (const ch of word) {
    let next = node.children.get(ch);
    if (next === undefined) {              // ② 그 글자로 가는 자식이 없을 때만 만든다
      next = new TrieNode();
      node.children.set(ch, next);
    }
    node = next;
  }
  node.end = true;                         // ③ 마지막 노드에 단어 끝 표시를 남긴다
}
```

여기서 가장 중요한 줄은 `①` 입니다. 어느 단어를 담든 같은 뿌리에서 출발하므로, 앞부분이 같은 단어들은
**저절로 같은 길을 지나가요.** 세 단어를 하나씩 다 담은 걸음을 모으면 모양이 이렇게 자랍니다.

<!--fig:walk-insert-shapes-->
![단어 하나를 다 담은 걸음 셋 — T4 · T6 · T7](./figs/walk-insert-shapes.svg)

T4 에서 노드 넷이던 트라이가 T6 에서 `app` 아래로 둘이 늘고, T7 에서 `ap` 아래로 하나가 늘어요. 이미 있던
노드는 한 번도 다시 만들어지지 않았습니다.

#### 짚고 가기 — 자식이 있는지 보지 않고 만들면 앞서 담은 단어가 사라진다

여기서 헷갈리기 쉬운 포인트는 `②` 의 조건입니다. 「어차피 없는 자리에만 걸리니까 자식을 찾지 않고 만들어
걸어도 되지 않나」로 읽기 쉬워요. 그 생각대로 자식을 찾는 줄을 걷어내 봅시다.

```ts
for (const ch of word) {
  let next = undefined;           // ← 자식이 있는지 보지 않는다. 원래는 node.children.get(ch) 다
  if (next === undefined) {
    next = new TrieNode();
    node.children.set(ch, next);
  }
  node = next;
}
```

담은 단어 셋에 앞서 쓴 조회 넷과 담은 단어 둘을 걸어 봅니다.

<!--proof:pauseOverwrite-->

| 조회 | 정본이 낸 답 | 매번 새로 만든 답 | 판정 |
| --- | --- | --- | --- |
| `search("app")` | 참 | 거짓 | 틀리다 |
| `search("appl")` | 거짓 | 거짓 | 같다 |
| `startsWith("appl")` | 참 | 거짓 | 틀리다 |
| `startsWith("bat")` | 거짓 | 거짓 | 같다 |
| `search("apple")` | 참 | 거짓 | 틀리다 |
| `search("ape")` | 참 | 참 | 같다 |

여섯 조회 가운데 3 개가 틀립니다.

<!--/proof-->

같은 글자로 `set` 을 다시 부르면 **그 자리에 걸려 있던 자식이 새 노드로 바뀝니다.** 단어를 담을 때마다 뿌리의
`a` 자리가 새 노드로 덮이면서, 앞서 담은 단어의 길이 그 아래 끝 표시와 함께 통째로 떨어져 나가요. 마지막에 담은
`ape` 만 남아서 `search("ape")` 는 맞게 나오니, 마지막 단어만 시험하면 이 실수를 못 봅니다.

#### 3. 같은 내려가기로 두 조회를 답한다

셋째 조각은 조회입니다. 두 연산이 **같은 내려가기**를 쓰므로 그 부분을 `nodeAt` 으로 떼어 두고, 마지막 한
줄에서만 갈라요.

```ts
search(word: string): boolean {
  const node = this.nodeAt(word);
  return node !== null ? node.end : false;   // ④ 경로가 있고 끝 표시도 있어야 한다
}

startsWith(prefix: string): boolean {
  return this.nodeAt(prefix) !== null;   // ⑤ 경로가 있기만 하면 된다
}

private nodeAt(s: string): TrieNode | null {
  let node = this.root;
  for (const ch of s) {
    const child = node.children.get(ch);
    if (child === undefined) return null;   // ⑥ 자식이 없으면 이 문자열은 어떤 단어의 접두사도 아니다
    node = child;
  }
  return node;
}
```

`⑥` 이 **남은 글자를 읽지 않고 곧바로 끝내는 자리**입니다. 담은 단어 셋에 조회 넷을 걸면 `nodeAt` 이 돌려준
것과 마지막 한 줄의 값이 이렇게 나와요.

<!--proof:walk-queries-->

| 조회 | nodeAt 이 돌려준 것 | 끝 표시 | ④ 의 값 | ⑤ 의 값 |
| --- | --- | --- | --- | --- |
| `search("app")` | 노드 app | 참 | 참 | - |
| `search("appl")` | 노드 appl | 거짓 | 거짓 | - |
| `startsWith("appl")` | 노드 appl | 안 본다 | - | 참 |
| `startsWith("bat")` | `null` | 안 본다 | - | 거짓 |

<!--/proof-->

`search("appl")` 과 `startsWith("appl")` 은 `nodeAt` 이 같은 노드를 돌려줬는데 답이 갈립니다. `④` 는 끝 표시를
읽고 `⑤` 는 읽지 않기 때문이에요. `startsWith("bat")` 는 `⑥` 에서 `null` 을 받아 거짓입니다.

#### 짚고 가기 — 끝 표시를 보지 않으면 두 조회가 같은 것이 된다

여기서 헷갈리기 쉬운 포인트는 `④` 의 뒷항입니다. 「글자를 다 따라가 노드까지 도착했으면 그 단어가 담긴 것
아닌가」로 읽기 쉬워요. 그 생각대로 끝 표시를 보는 부분을 지워 봅시다.

```ts
search(word: string): boolean {
  const node = this.nodeAt(word);
  return node !== null;   // ← 끝 표시를 안 보고 도착 여부만 본다. 원래는 node !== null ? node.end : false 다
}
```

여섯 조회로 확인해 봅니다. 오른쪽에 `startsWith` 의 답을 나란히 놓았어요.

<!--proof:pauseEndFlag-->

| 조회 | 정본이 낸 답 | 끝 표시를 안 본 답 | startsWith 의 답 | 판정 |
| --- | --- | --- | --- | --- |
| `search("app")` | 참 | 참 | 참 | 같다 |
| `search("appl")` | 거짓 | 참 | 참 | 틀리다 |
| `search("ap")` | 거짓 | 참 | 참 | 틀리다 |
| `search("a")` | 거짓 | 참 | 참 | 틀리다 |
| `search("apple")` | 참 | 참 | 참 | 같다 |
| `search("apz")` | 거짓 | 거짓 | 거짓 | 같다 |

끝 표시를 안 본 답은 여섯 줄 가운데 6 줄에서 startsWith 의 답과 같습니다. 답이 안 틀린 줄은 `app` · `apple` · `apz` 3 개입니다.

<!--/proof-->

**담긴 단어를 그대로 물으면 답이 안 틀립니다.** `search("app")` 과 `search("apple")` 은 두 방식이 같은 답을
내고, 도중에 끊기는 `apz` 도 같아요. 그래서 담긴 단어와 없는 단어만 시험에 넣으면 끝까지 모르고 넘어갑니다.
틀리는 것은 `appl` · `ap` · `a` 처럼 **담긴 단어의 접두사이지만 단어는 아닌** 문자열이고, 그 자리에서 이
`search` 는 `startsWith` 와 한 줄도 다르지 않아요. 끝 표시를 빼면 두 연산이 같은 것이 되니, 고치는 이유는
분명합니다.

#### 4. 열한 걸음을 끝까지 실행해 답 넷을 낸다

세 조각을 이어 고정 입력에 실행하면 열한 걸음이 나옵니다. T1 이 빈 트라이, T2 부터 T7 까지가 삽입, T8 부터
T11 까지가 조회예요. 무대는 완성된 트라이의 자리를 처음부터 두고, 아직 없는 노드를 점선으로 그립니다.
굵은 테가 이번 걸음에 만들었거나 끝 표시를 참으로 둔 노드, 옅게 채운 노드가 이번 걸음에 지나간 노드이고,
무대 아래 띠가 지금 읽는 문자열이에요.

T5 는 `apple` 의 앞 세 글자에서 자식이 셋 다 있어 `②` 가 세 번 거짓인 걸음이고, T7 은 `a` · `p` 에서 거짓,

`⑤` 는 도착만 보고 참을 냈습니다. 마지막 걸음 T11 은 `b` 에서 `⑥` 이 걸려 `false` 를 돌려줘요. 갈래마다
실행된 걸음을 세면 이렇습니다.

<!--/proof-->

**여섯 갈래가 모두 실행됐습니다.** `②` 는 참과 거짓이 둘 다 나왔고, `⑥` 은 T11 에서 처음이자 마지막으로
걸렸어요.

#### 짚고 가기 — 글자마다 재귀로 내려가면 과제 규모에서 호출 스택이 넘친다

여기서 헷갈리기 쉬운 포인트는 **내려가기를 어떻게 적는가**입니다. 트리를 다루는 코드라 「글자 하나를
처리하고 나머지를 자기 자신에게 넘기면 짧게 적힌다」로 가기 쉬워요.

```ts
function insertRec(node: TrieNode, word: string, k: number): void {
  if (k === word.length) { node.end = true; return; }
  const ch = word[k] as string;
  let next = node.children.get(ch);
  if (next === undefined) { next = new TrieNode(); node.children.set(ch, next); }
  insertRec(next, word, k + 1);      // 글자 하나마다 호출이 한 겹 쌓인다
}
```

만드는 트라이는 반복문 쪽과 같습니다. 갈리는 것은 호출 스택의 깊이예요. 한 글자로만 된 단어를 길이 두
가지로 담아 봅니다.

<!--proof:pauseRecursion-->

| 단어 길이 | 글자마다 재귀 | 반복문 |
| ---: | --- | --- |
| 1,000 | 끝까지 담는다 | 끝까지 담는다 |
| 100,000 | RangeError | 끝까지 담는다 |

<!--/proof-->

**길이 1,000 은 두 방식 다 끝납니다.** 짧은 단어만 시험하면 이 실패를 못 만나요. 과제 규모는 문자열 하나를
100,000 글자까지 허용하는데, 그 길이에서 재귀는 호출이 글자 수만큼 쌓여 `RangeError` 를 냅니다. 반복문은
글자 하나마다 변수 하나를 바꿀 뿐이라 겹이 쌓이지 않아요. 그래서 이 글의 코드는 내려가기를 전부 반복문으로
적습니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 없어요. 뿌리를 만드는 한 줄은 1 번 조각에서,
나머지는 2 번과 3 번 조각에서 왔습니다.

```ts
class TrieNode {
  readonly children = new Map<string, TrieNode>();
  end = false;
}

export class Trie {
  private readonly root = new TrieNode();

  insert(word: string): void {
    // ① 뿌리에서 출발한다. 뿌리는 빈 문자열에 해당하는 노드다.
    let node = this.root;
    for (const ch of word) {
      let next = node.children.get(ch);
      // ② 그 글자로 가는 자식이 없을 때만 새 노드를 만든다.
      if (next === undefined) {
        next = new TrieNode();
        node.children.set(ch, next);
      }
      node = next;
    }
    // ③ 마지막 노드에 단어 끝 표시를 남긴다. 같은 단어를 다시 넣어도 결과가 같다.
    node.end = true;
  }

  search(word: string): boolean {
    const node = this.nodeAt(word);
    // ④ 경로가 있고 그 끝에 단어 끝 표시도 있어야 한다.
    return node !== null ? node.end : false;
  }

  startsWith(prefix: string): boolean {
    // ⑤ 경로가 있기만 하면 된다. 끝 표시는 보지 않는다.
    return this.nodeAt(prefix) !== null;
  }

  private nodeAt(s: string): TrieNode | null {
    let node = this.root;
    for (const ch of s) {
      const child = node.children.get(ch);
      // ⑥ 그 글자로 가는 자식이 없으면 이 문자열은 담긴 어떤 단어의 접두사도 아니다.
      if (child === undefined) return null;
      node = child;
    }
    return node;
  }
}
```

<!--proof:finalRun-->

```text
trie.search("app")                  →  true
trie.search("appl")                 →  false
trie.startsWith("appl")             →  true
trie.startsWith("bat")              →  false
trie.startsWith("apple")            →  true
trie.search("applepie")             →  false
new Trie().search("app")            →  false
new Trie().startsWith("app")        →  false
app 을 두 번 담은 뒤 search("app")  →  true
```

<!--/proof-->

아래 다섯 줄은 전개에서 안 나온 자리입니다. 담긴 단어와 같은 접두사, 담긴 단어보다 긴 조회, 빈 트라이의 두
조회, 같은 단어를 두 번 담은 경우예요.

### 알아 두면 좋은 개념 — 자리별 분해

이 절차가 한 일에는 이름이 붙어 있습니다. 키를 한 덩어리로 비교하지 않고 **자리 하나씩 떼어** 후보를 좁히는
방식을 **자리별 분해**라고 불러요. 여기서 자리는 글자였고, 자리 하나를 읽을 때마다 그 글자로 시작하는
후보만 남았습니다. 전개의 T2 부터 T6 까지가 그 좁힘을 값으로 보인 자리예요. 글자를 하나씩 읽을 때 남는 후보
단어를 세면 이렇습니다.

<!--proof:related-narrow-->

| 읽은 접두사 | 남은 후보 단어 | 후보 수 |
| --- | --- | ---: |
| 빈 문자열 | `app` · `apple` · `ape` | 3 |
| `a` | `app` · `apple` · `ape` | 3 |
| `ap` | `app` · `apple` · `ape` | 3 |
| `app` | `app` · `apple` | 2 |
| `appl` | `apple` | 1 |
| `apple` | `apple` | 1 |

<!--/proof-->

트라이의 노드 하나가 곧 「지금까지 읽은 자리가 같은 후보들의 묶음」이에요. 같은 생각이 다른 키에서도 같은
이름으로 나옵니다.

| 다시 나오는 자리 | 자리로 보는 것 | 자리 하나의 갈래 수 |
| --- | --- | --- |
| 이 글의 트라이 | 글자 | `Σ` = 26 |
| 기수 정렬 | 십진 자리 | 10 |
| 이진 트라이(정수를 비트마다 갈라 XOR 최댓값을 찾는다) | 비트 | 2 |
| IP 경로 표(주소를 비트마다 갈라 가장 긴 일치 접두사를 찾는다) | 비트 | 2 |

자리별 분해를 정렬에 쓴 것이 [`radixSort`](../../sorting/radixSort/radixSort-guide.md) 이고, 이 글은 같은
생각을 **조회**에 쓴 것이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 노드 수를 임의의 단어 집합에서 어떻게
어림하는지, 무엇이 매 삽입 뒤에 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 키가 자리로 나뉜다 | 문자열의 글자, 정수의 자리나 비트처럼 앞에서부터 하나씩 떼어 읽는다 | 글자 하나마다 한 칸 내려간다 |
| 접두사 자체를 묻는다 | 답이 길 끝의 노드만이 아니라 길 도중의 노드에도 있다 | `startsWith` 가 도착 여부만 본다 |
| 키가 앞부분을 많이 공유한다 | 공유가 없으면 노드 수가 길이 합과 같아져 줄어드는 것이 없다 | 이어 쓰는 걸음이 많다 |
| 담는 일과 묻는 일이 섞여 들어온다 | 전부 담은 뒤 묻기만 한다면 한 번 정렬해 두는 방식이 칸을 적게 쓴다 | 삽입이 노드를 잇기만 한다 |

두 번째 줄이 이 구조의 경계입니다. 담긴 단어인가만 묻는다면 문자열을 통째로 해시해 해시 집합에 넣는 쪽이
노드마다 맵을 두는 것보다 칸이 적어요.

| 묻는 것 | 쓰는 구조 | 까닭 |
| --- | --- | --- |
| 이 문자열이 담겼는가만 | 해시 집합 | 길 도중의 노드가 필요 없다 |
| 이 문자열로 시작하는 것이 있는가 | 트라이 | 길 도중의 노드가 곧 답이다 |
| 가운데 어디든 이 조각이 있는가 | 접미사 구조 | 접두사만으로는 못 답한다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "자동 완성"  "이 글자로 시작하는"  "접두사"   <- startsWith 그 자체다
  "사전에 있는 단어인가"  "정확히 일치"         <- search 그 자체다
  "각 연산이 문자열 길이에 비례"                <- 담긴 단어의 개수를 보면 안 된다
  "삽입과 조회가 섞여 들어온다"                 <- 미리 정렬해 두는 방식을 막는다

반대로 이런 말이 보이면 해당하지 않는다
  "부분 문자열"  "가운데 어디든"                <- 접두사가 아니라 다른 구조가 필요하다
  "단어를 지운다"  "개수를 센다"                <- 노드마다 값을 더 들어야 한다
  "메모리가 아주 빠듯하다"                      <- 노드마다 맵을 드는 비용이 문제가 된다
```

마지막 무리가 보이면 다른 구조로 갑니다. 자식이 하나뿐인 사슬이 길게 이어지는 사전이면
[`radixTree`](../radixTree/radixTree-guide.md) 쪽이고, 접두사가 아니라 문자열 가운데의 조각을 물으면
[`suffixArray`](../suffixArray/suffixArray-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **ICU(International Components for Unicode) 의 `BytesTrie`·`UCharsTrie`.** 유니코드 표준
  구현이 트라이를 이름 그대로 공개 API 로 제공하는 자리입니다. 문서가 이 클래스를
  *"Traverses a byte-serialized data structure with minimal state, for mapping byte sequences to
  non-negative integer values."* 로 정의해요. 한 걸음에 한 바이트씩 내려가는 `next()` 가 이 글의
  `nodeAt` 과 같은 일을 합니다.
  ([`icu::BytesTrie` API 문서](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/classicu_1_1BytesTrie.html),
  [`bytestrie.h` 소스](https://github.com/unicode-org/icu/blob/main/icu4c/source/common/unicode/bytestrie.h),
  조회 2026-08-30)

같은 구현이 **이 글의 끝 표시와 같은 것을 반환값의 종류로** 갈라 둡니다. `ustringtrie.h` 의
`UStringTrieResult` 가 그것이고, 셋이 각각 이 글의 어느 자리에 대응하는지가 그대로 보여요.

| ICU 의 반환값 | 문서의 정의 | 이 글에서 대응하는 자리 |
| --- | --- | --- |
| `USTRINGTRIE_NO_MATCH` | *"The input unit(s) did not continue a matching string."* | `nodeAt` 이 `null` 을 낸 자리 |
| `USTRINGTRIE_NO_VALUE` | *"...but there is no value for the string so far. (It is a prefix of a longer string.)"* | 노드는 있고 끝 표시가 없다 |
| `USTRINGTRIE_INTERMEDIATE_VALUE` | *"...and there is a value for the string so far... Another input byte/unit can continue a matching string."* | 노드도 끝 표시도 있다 |

- **리눅스 커널의 IPv4 경로 표 `net/ipv4/fib_trie.c`.** 주소를 비트마다 갈라 가장 긴 일치
  접두사를 찾는 자리이고, 파일 첫머리가 *"This work is based on the LPC-trie which is originally
  described in: An experimental study of compression methods for dynamic tries, Stefan Nilsson and
  Matti Tikkanen, Algorithmica, 33(1):19-33, 2002"* 라 적혀 있습니다. **이 글의 트라이를 압축한
  변형**이라는 것을 밝혀 둡니다. 자리 수를 줄이려고 사슬을 접은 구조라 노드 수의 계산이 달라져요.
  ([`net/ipv4/fib_trie.c`](https://github.com/torvalds/linux/blob/master/net/ipv4/fib_trie.c),
  조회 2026-08-30)

**웹 브라우저나 편집기의 자동 완성이 이 구조를 쓴다는 것은 1 차 출처로 확인하지 못했습니다.**
확인한 것은 유니코드 표준 구현이 트라이를 공개 API 로 제공한다는 것과, 리눅스 커널의 경로 표가
그 압축 변형을 쓴다는 것 둘입니다.

#### 경쟁 설계와의 대조

같은 목표(문자열을 담고 접두사를 묻는 것)를 노리는 다른 절차로 **정렬을 유지하는 배열과 이진 탐색**이
있습니다. 단어를 사전순으로 담아 두면, 어떤 문자열로 시작하는 단어가 있는지는 그 문자열이 들어갈 자리 하나만
보면 알 수 있어요. 있다면 바로 그 자리에서 시작합니다.

| 설계 | 조회 하나 | 삽입 하나 |
| --- | --- | --- |
| 트라이 | 글자마다 노드를 한 칸 내려간다. 담긴 단어의 개수를 안 본다 | 없는 노드만 만들어 잇는다 |
| 정렬 배열과 이진 탐색 | 이진 탐색으로 자리를 찾고 그 단어와 대조한다. 비교마다 문자열을 다시 읽는다 | 자리를 만들려고 뒤쪽 원소를 한 칸씩 옮긴다 |

같은 입력 · 같은 작업 목록에 두 설계를 걸고 **자료 접근**과 **추가 칸**을 셌습니다. 자료 접근은 글자 한 자리를
읽어 자식 맵을 조회한 것(배열 쪽은 두 단어의 같은 자리를 대조한 것) · 새 노드를 맵에 건 것 · 끝 표시를 읽거나 쓴
것 · 배열 원소 하나를 한 칸 옮긴 것을 각각 1 로 셉니다. 새 노드의 필드를 채우는 초기화 쓰기는 넣지 않았어요.
추가 칸은 입력 단어 목록 밖에 각 구조가 들고 있는 칸이고, 트라이는 노드마다 끝 표시 한 칸과 간선마다 맵 항목
한 칸, 배열은 담은 글자 한 칸씩과 단어마다 시작 위치 한 칸입니다. 사전은 길이 100 짜리 단어 1,000 개이고 길이 합이 과제 규모의 최댓값 100,000 이에요.
단어는 `"a" × p + base26(i) + "z" × (97 − p)` 로 만들었고, `base26(i)` 는 `i` 를 소문자 세 글자로 적은
것입니다. 작업 목록은 `p = 50` 인 사전이고, 조회 1,000 개는 그 단어들의 앞 60 글자예요. 난수를 쓰지 않아
시드가 없습니다. **전개 입력을 그대로 쓰지 않은 이유**는 단어 셋에서는 이진 탐색이 한 번에 끝나 두 설계의
계수가 상수에 묻히기 때문입니다.

| 측정 | 트라이 | 정렬 배열과 이진 탐색 | 적은 쪽 |
| --- | --- | --- | --- |
| 삽입 1,000 개 · 자료 접근 | **149,091** | 417,921 | 트라이 |
| 조회 1,000 회 · 자료 접근 | **61,000** | 590,398 | 트라이 |
| 공유 47 글자 · 추가 칸 | 102,177 | **101,000** | 정렬 배열 |
| 공유 48 글자 · 추가 칸 | **100,179** | 101,000 | 트라이 — **여기서 순서가 뒤집힌다** |

**자료 접근에서는 갈리지 않고 추가 칸에서 갈립니다.** 배열은 글자를 그대로 담으므로 공유의 정도를 아예 안
보고 언제나 101,000 칸이에요. 트라이는 노드마다 끝 표시 한 칸과 간선마다 항목 한 칸을 쓰므로 공유가 늘면
함께 줄어듭니다. 길이 합을 100,000 으로 고정한 채 공통 접두사 길이 `p` 만 바꿔 보면 뒤집히는 자리가 값으로
나와요.

<!--proof:altCells-->

| 공통 접두사 길이 | 트라이 추가 칸 | 정렬 배열 추가 칸 | 적은 쪽 |
| ---: | ---: | ---: | --- |
| 0 | 196,083 | 101,000 | 정렬 배열 |
| 20 | 156,123 | 101,000 | 정렬 배열 |
| 40 | 116,163 | 101,000 | 정렬 배열 |
| 46 | 104,175 | 101,000 | 정렬 배열 |
| 47 | 102,177 | 101,000 | 정렬 배열 |
| 48 | 100,179 | 101,000 | 트라이 |
| 49 | 98,181 | 101,000 | 트라이 |
| 60 | 76,203 | 101,000 | 트라이 |
| 90 | 16,263 | 101,000 | 트라이 |

아홉 줄 모두 단어 1,000 개 · 길이 100 · 길이 합 100,000 이고 공통 접두사 길이만 바꿨습니다. 47 과 48 사이에서 적은 쪽이 정렬 배열에서 트라이로 바뀝니다.

<!--/proof-->

**트라이가 내주는 것은 추가 칸입니다.** 앞부분을 47 글자 이하로 공유하는 사전에서는 정렬 배열이 칸을 더
적게 쓰고, 그 차이는 공유가 하나도 없을 때 196,083 대 101,000 까지 갑니다. 그 대신 얻는 것이 둘이에요.

| 축 | 트라이 | 정렬 배열과 이진 탐색 |
| --- | --- | --- |
| 조회 하나의 비용 | 조회 문자열의 길이만큼. 담긴 단어의 개수를 안 본다 | 문자열 비교 `log N` 번 |
| 삽입 하나의 비용 | 단어 길이만큼. 노드를 잇기만 한다 | 뒤쪽 원소를 한 칸씩 옮긴다 |
| 추가 칸 | 공유가 적으면 더 많다 | 공유와 상관없이 길이 합 + 단어 수 |

담는 일과 묻는 일이 섞여 들어오면 앞의 두 줄이 답이라 트라이를 씁니다. **전부 담고 나서 묻기만 하고 앞부분
공유가 47 글자 이하인 사전**이면 정렬을 한 번 해 두는 배열 쪽으로 다시 판단해야 해요.

### 수식 정의와 유도

단어 집합 `W` 에 대해 **접두사 집합**을 정의합니다. `w[0..k)` 는 `w` 의 앞 `k` 글자예요.

$$\operatorname{Pref}(W) = \{\, w[0..k) \;:\; w \in W,\ 0 \le k \le |w| \,\} \qquad V = |\operatorname{Pref}(W)|$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $W$ | 담은 단어들의 집합 | $\lvert W \rvert = N$ |
| $w[0..k)$ | $w$ 의 앞 $k$ 글자. $k = 0$ 이면 빈 문자열이다 | $0 \le k \le \lvert w \rvert$ |
| $\operatorname{Pref}(W)$ | $W$ 의 단어들이 내놓는 접두사를 전부 모은 집합 | 빈 문자열을 늘 포함한다 |
| $V$ | 그 집합의 크기. 트라이의 노드 집합이 곧 이 집합이다 | $V \ge 1$ |

**정의를 값에 넣어 검산해 봅시다.** 전개 입력 `{app, apple, ape}` 를 넣고 원소를 길이 순서로 늘어놓았습니다.

<!--proof:mathPrefixSet-->

| 원소 | 길이 | 그 원소를 내놓은 단어 |
| --- | ---: | --- |
| 빈 문자열 | 0 | app · apple · ape |
| `a` | 1 | app · apple · ape |
| `ap` | 2 | app · apple · ape |
| `ape` | 3 | ape |
| `app` | 3 | app · apple |
| `appl` | 4 | apple |
| `apple` | 5 | apple |

집합의 크기는 7, 트라이의 노드 수는 7, 길이 합은 11 입니다.

<!--/proof-->

원소 일곱이 노드 일곱과 하나씩 짝지어지고, 원소의 길이가 그 노드의 깊이입니다. 길이 합은 11 인데 원소는
7 이에요. 세 단어가 빈 문자열 · `a` · `ap` 를 함께 내놓고, `app` 과 `apple` 이 `app` 을 함께 내놓아서
겹친 만큼 줄었습니다.

**이제 유도합니다.** 단어 `w` 하나가 내놓는 접두사는 `k = 0` 부터 `k = |w|` 까지라 `|w| + 1` 개인데, `k = 0`
이 내놓는 빈 문자열은 모든 단어가 같은 것을 내놓아요. 합집합이므로 겹치는 것은 한 번만 셉니다.

| 항 | 개수 | 까닭 |
| --- | --- | --- |
| 빈 문자열 | 1 | 모든 단어가 내놓지만 합집합이라 한 번만 센다 |
| 단어 `w` 가 내놓는 길이 1 이상의 접두사 | $\lvert w \rvert$ | $k = 1$ 부터 $k = \lvert w \rvert$ 까지 |
| 그 합 | $\sum_{w} \lvert w \rvert = S$ 이하 | 두 단어가 같은 접두사를 내놓으면 그만큼 줄어든다 |

$$|\operatorname{Pref}(W)| \le 1 + \sum_{w \in W} |w| = 1 + S$$

아래로는 가장 긴 단어 하나가 자기 접두사 `|w| + 1` 개를 혼자 내놓습니다. 다른 단어가 무엇이든 그 원소들은
집합에 있어요.

$$|\operatorname{Pref}(W)| \ge 1 + \max_{w \in W} |w|$$

등호가 성립하는 자리도 정해집니다. 위 식은 **어떤 두 단어도 첫 글자부터 다를 때**(빈 문자열 말고는 겹치는
접두사가 없다), 아래 식은 **모든 단어가 가장 긴 단어의 접두사일 때**예요. 정의를 그대로 옮긴 조각은
이렇습니다.

```ts
// 정의를 그대로 옮긴 조각. 집합을 실제로 만들어 크기를 센다.
const prefixCount = (words: string[]): number =>
  new Set(words.flatMap((w) => Array.from({ length: w.length + 1 }, (_, k) => w.slice(0, k)))).size;
```

이 조각은 접두사를 전부 만들어 담으므로 단어 하나마다 그 길이의 제곱에 비례하는 글자를 읽습니다. 트라이는
같은 값을 담는 동안 곁들여 얻어요. 두 식에 단어 집합 넷을 넣어 실제 노드 수와 나란히 놓았습니다.

<!--proof:mathBounds-->

| 단어 집합 | S | 하한 max\|w\| + 1 | 실제 V | 상한 S + 1 | 자리 |
| --- | ---: | ---: | ---: | ---: | --- |
| {app, apple, ape} | 11 | 6 | 7 | 12 | 그 사이 |
| {app, bat, cup} | 9 | 4 | 10 | 10 | 상한과 같다 |
| 앞 97 글자가 같은 1,000 단어 | 100,000 | 101 | 1,139 | 100,001 | 그 사이 |
| 길이 100,000 짜리 단어 하나 | 100,000 | 100,001 | 100,001 | 100,001 | 상한이자 하한 |

<!--/proof-->

둘째 줄은 첫 글자가 모두 달라 상한과 같고, 넷째 줄은 단어가 하나라 상한과 하한이 겹칩니다. 식이 주는 것은
**값을 세지 않고도 쓰는 경계**예요. 과제 규모 `S = 100,000` 이면 어떤 단어 집합이든 노드는 많아야 100,001
개이고, 그 수가 「아이디어 상세」에서 자식을 배열로 둘 때와 맵으로 둘 때의 칸을 가른 기준입니다.

### 불변식 — 노드의 경로 문자열이 곧 담긴 단어들의 접두사다

파트 1 에서 코드가 동작하는 것을 열한 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매 삽입 뒤에 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해
봅시다. 불변식은 문장 둘로 세우는데, 두 문장이 기대는 연산이 서로 다릅니다.

> `insert` 하나가 끝난 직후, 노드 `v` 까지의 경로 문자열을 `path(v)` 라 하면
> `{ path(v) : v 는 트라이의 노드 }` 는 지금까지 담은 단어들의 접두사 집합과 같고, 그중
> `v.end` 가 참인 것만 모으면 담은 단어들의 집합과 같습니다.

| 문장 | 참인 것 | 기대는 연산 |
| --- | --- | --- |
| 앞 문장 | 노드의 경로 문자열을 모으면 담긴 단어들의 접두사 집합과 같다 | `startsWith` 가 도착 여부만 봐도 된다 |
| 뒤 문장 | 그중 끝 표시가 참인 것만 모으면 담긴 단어들의 집합과 같다 | `search` 가 끝 표시를 봐야 한다 |

**출발점부터 봅시다.** 아무것도 담지 않은 트라이는 뿌리 하나이고, 뿌리의 경로 문자열은 빈 문자열입니다. 담은
단어가 없으면 접두사 집합도 빈 문자열 하나뿐이라 앞 문장이 참이고, 끝 표시가 참인 노드가 하나도 없으므로 뒤
문장도 참이에요. 그다음 삽입 하나는 아래 넷 중 하나를 되풀이합니다.

| 걸음 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | 뿌리 하나를 만든다 | 접두사가 빈 문자열 하나다 | 담은 단어가 없다 |
| 글자 하나 · 자식이 있다 | 그 자식으로 옮긴다 | 그 경로 문자열이 이미 집합에 있다 | 끝 표시를 건드리지 않는다 |
| 글자 하나 · 자식이 없다 | 만들어 걸고 옮긴다 | 지금 담는 단어의 접두사 하나가 집합에 더해진다 | 새 노드의 끝 표시가 거짓이다 |
| 문자열이 끝났다 | 끝 표시를 참으로 둔다 | 노드를 더하지 않는다 | 담은 단어 하나가 집합에 더해진다 |

셋째 줄이 이 논증의 핵심입니다. 새로 만드는 노드의 경로 문자열은 부모의 경로 문자열에 지금 읽은 글자를
붙인 것이고, 부모까지는 지금 담는 단어의 앞부분을 따라왔으니 그것은 **지금 담는 단어의 접두사**예요. 그것
말고 다른 노드는 생기지 않으므로 노드 집합이 접두사 집합 밖으로 나가지 않습니다. 거꾸로 담는 단어의 접두사는
반복이 글자를 하나도 건너뛰지 않으니 전부 노드가 돼요. 경계에 있는 입력도 정본으로 실행해 확인했습니다.

<!--proof:invariant-edges-->

| 경우 | 담은 단어 | 조회 | search | startsWith | 노드 수 |
| --- | --- | --- | --- | --- | ---: |
| 빈 트라이 | 없음 | app | 거짓 | 거짓 | 1 |
| 담긴 단어보다 긴 조회 | ab | abc | 거짓 | 거짓 | 3 |
| 같은 단어를 두 번 | app · app | app | 참 | 참 | 4 |
| 짧은 단어를 나중에 | apple · app | app | 참 | 참 | 6 |
| 긴 단어 하나 | a × 100,000 | a × 100,000 | 참 | 참 | 100,001 |

<!--/proof-->

같은 단어를 두 번 담아도 노드 수가 4 그대로이고, 짧은 단어를 나중에 담아도 6 그대로입니다. 두 경우 모두
뒤 문장만 움직였어요. 과제 규모의 긴 단어 하나는 노드 100,001 개를 만들고, 그 수는 경로 문자열의 길이 0
부터 100,000 까지 하나씩입니다.

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 삽입에서 **다음 노드로 옮기는 한 줄**이에요. 「어차피 뿌리부터
다시 찾으면 되니 지금 노드를 굳이 이어 가야 하나」라는 생각으로 그 줄을 뿌리 대입으로 바꿔 봅니다.

```ts
for (const ch of word) {
  let next = node.children.get(ch);
  if (next === undefined) { next = new TrieNode(); node.children.set(ch, next); }
  node = this.root;      // ← 다음 노드로 옮기지 않고 뿌리로 되돌아간다. 원래는 node = next 다
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutantPathReset-->

| 조회 | 정본이 낸 답 | 경로를 안 잇는 답 | 판정 |
| --- | --- | --- | --- |
| `search("app")` | 참 | 거짓 | 틀리다 |
| `search("appl")` | 거짓 | 거짓 | 같다 |
| `startsWith("appl")` | 참 | 거짓 | 틀리다 |
| `startsWith("bat")` | 거짓 | 거짓 | 같다 |
| `startsWith("e")` | 거짓 | 참 | 틀리다 |
| `startsWith("pa")` | 거짓 | 거짓 | 같다 |

노드의 경로 문자열을 모으면 정본은 뿌리 · a · ap · app · ape · appl · apple 7 개이고, 바꾼 코드는 뿌리 · a · p · l · e 5 개입니다.

<!--/proof-->

바꾼 코드가 같은 세 단어로 만든 모양을 그리면 이렇습니다.

<!--fig:invariant-mutant-->
![경로를 안 잇는 코드가 같은 세 단어로 만든 모양](./figs/invariant-mutant.svg)

글자가 차례를 잃고 전부 뿌리의 자식이 됐어요. 뿌리 말고는 경로 문자열이 길이 1 짜리뿐이라 `ap` 도 `app` 도 노드가 없고,
그래서 `search("app")` 과 `startsWith("appl")` 이 거짓입니다. 반대로 `e` 는 어떤 담긴 단어의 접두사도 아닌데
노드가 생겨 `startsWith("e")` 가 참이 됐어요. 앞 문장이 두 방향으로 다 깨진 것입니다. 끝 표시는 여전히 반복이
끝난 노드에 남지만 그 노드가 뿌리라서, 담은 단어가 아니라 빈 문자열을 가리켜요. 앞 문장이 깨지면 뒤 문장도
설 자리가 없습니다.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다. 자식 맵을 조회하는 것, 노드를 새로 만드는 것, 끝 표시를 읽거나 쓰는
것이에요. 전개의 삽입 셋(T2 부터 T7)과 조회 넷(T8 부터 T11)으로 세면 이렇게 나뉩니다.

<!--proof:perfCount-->

| 연산 | 자식 맵 조회 | 노드 생성 | 끝 표시 읽기·쓰기 | 자료 접근 |
| --- | ---: | ---: | ---: | ---: |
| `insert("app")` | 3 | 3 | 1 | 7 |
| `insert("apple")` | 5 | 2 | 1 | 8 |
| `insert("ape")` | 3 | 1 | 1 | 5 |
| `search("app")` | 3 | 0 | 1 | 4 |
| `search("appl")` | 4 | 0 | 1 | 5 |
| `startsWith("appl")` | 4 | 0 | 0 | 4 |
| `startsWith("bat")` | 1 | 0 | 0 | 1 |
| 합계 | 23 | 6 | 5 | 34 |

담는 쪽은 S + (V − 1) + N = 11 + 6 + 3 = 20 이고, 묻는 쪽은 읽은 글자 합 + 끝 표시 읽기 = 12 + 2 = 14 입니다.

<!--/proof-->

`insert("apple")` 은 글자를 다섯 번 읽는데 노드는 둘만 만들어요. 앞 세 글자를 처리한 T5 에서 하나도 안 만들기
때문입니다. **자식 맵 조회는 글자 수를 따라가고 노드 생성은 노드 수를 따라가서**, 두 값이 따로 정해져요.
그래서 담는 쪽의 총식이 세 항으로 갈립니다.

| 쪽 | 식 | 항마다의 뜻 |
| --- | --- | --- |
| 담는 쪽 | `S + (V − 1) + N` | 자식 맵 조회 · 노드 생성 · 끝 표시 쓰기 |
| 묻는 쪽 | 읽은 글자 합 + `search` 횟수 | 조회 하나가 많아야 `L` 글자 |
| 추가 칸 | `2V − 1` | 노드마다 끝 표시 하나, 간선마다 항목 하나 |

어느 항에도 담긴 단어의 개수를 곱하는 자리가 없습니다. `V − 1` 과 `N` 은 둘 다 `S` 를 넘지 않으니 담는 쪽은
많아야 `3S` 이고, 조회 `Q` 번의 비용은 목록 대조의 `Q · S` 에서 조회 길이의 합으로 바뀌어요. 한 조회가 `L`
글자면 `Q · L` 입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요. 조회
하나의 비용을 두 축으로 가르면 이렇습니다.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (조회가 첫 글자에서 끊긴다) | `O(1)` | `Θ(1)` — 자식 맵을 한 번만 읽는다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(L)` | 정의되지 않는다 |
| **최악의 경우** (경로가 끝까지 있다) | `O(L)` | `Θ(L)` — 실제로 도달한다 |

가운데 줄의 타이트한 값이 정의되지 않는 것은 **입력 분포가 없기 때문**입니다. 조회 문자열이 어느 자리에서
끊기는지는 담긴 단어들과 조회 문자열이 함께 정하는 것이라, 분포를 가정하지 않으면 기댓값을 쓸 수 없어요.
삽입은 다릅니다. 글자를 언제나 끝까지 읽으므로 세 줄이 모두 `Θ(L)` 이에요.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 구조의 특징이에요. 정렬도,
미리 만드는 표도, 좌표 압축도 하지 않습니다.

| 무엇 | 총식 | 항 |
| --- | --- | --- |
| 담기 | `Θ(S + N)` 시간 | 자식 맵 조회 `S` · 노드 생성 `V − 1` · 끝 표시 쓰기 `N` |
| 묻기 | `O(조회 길이의 합)` 시간 | 조회 하나가 많아야 `L` 글자 |
| 메모리 | `Θ(V)` 칸 | 노드 `V` 개 · 간선 `V − 1` 개, `V ≤ S + 1` |

**보장의 종류를 밝혀 둡니다.** 걸음 수는 최악 보장이지만 **걸음 하나의 비용은 기댓값**이에요. 자식을 `Map`
으로 담았고 그것이 해시 기반이라, 항목 하나를 찾는 데 드는 일이 해시가 글자를 흩는 정도에 달려 있습니다.
입력 분포에 대한 기댓값이 아니라 **구현이 쓰는 해시에 대한 기댓값**이에요.

| 보장하는 것 | 보장의 종류 | 기댓값의 대상 |
| --- | --- | --- |
| 지나는 노드 수 | 최악 보장 `L + 1` | - |
| 만드는 노드 수 | 최악 보장 `L` | - |
| 자식 하나를 찾는 일 | 기댓값 상수 | 해시 함수가 글자를 흩는 정도 |
| 자식을 `Σ` 칸 배열로 담으면 | 최악 보장 상수 | - |

마지막 줄이 두 구현을 가르는 자리입니다. `Σ` 칸 배열은 최악 보장을 주지만 노드마다 26 칸을 잡고, 맵은 기댓값
보장을 주는 대신 간선 수만큼만 잡아요. 그 칸 수는 「아이디어 상세」의 「자식을 맵으로 두는 까닭」이 세었습니다.

#### 최악을 만드는 입력

축이 셋이고 최악을 만드는 입력이 축마다 다릅니다. 입력 네 모양을 만들어 노드 수 · 추가 칸 · 가장 긴 조회가
읽은 글자를 세었어요.

<!--proof:worstShape-->

| 입력의 모양 | 단어 수 | 길이 합 | 노드 수 | 추가 칸 2V − 1 | 가장 긴 조회가 읽은 글자 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 길이 100,000 짜리 단어 하나 | 1 | 100,000 | 100,001 | 200,001 | 100,000 |
| 앞 97 글자가 같은 1,000 단어 | 1,000 | 100,000 | 1,139 | 2,277 | 98 |
| 앞 3 글자가 갈리는 1,000 단어 | 1,000 | 100,000 | 98,042 | 196,083 | 100 |
| 길이 1 짜리 단어 26 개 | 26 | 26 | 27 | 53 | 1 |

<!--/proof-->

**「담긴 단어가 많으면 조회가 느려진다」는 이 구조에서 성립하지 않습니다.** 넷째 줄은 단어가 26 개인데 조회가
한 글자에서 끝나고, 첫 줄은 단어가 하나인데 조회가 100,000 글자를 읽어요. 조회 비용을 정하는 것은 단어의
개수가 아니라 조회 문자열의 길이입니다. 위 세 줄은 길이 합이 같은데 노드 수가 크게 갈려요. 노드 수를 정하는
것은 길이 합이 아니라 앞부분을 얼마나 공유하는가입니다.

| 최악으로 만들 축 | 입력 | 까닭 |
| --- | --- | --- |
| 연산 하나의 읽기 | 과제 규모의 가장 긴 문자열 | 한 글자에 한 칸이라 길이만큼 읽는다 |
| 노드 수 · 추가 칸 | 앞부분을 하나도 공유하지 않는 사전 | 상한 `S + 1` 에 이른다 |
| 조회가 가장 짧은 경우 | 첫 글자부터 없는 조회 | 한 번 읽고 끊긴다 |

노드 수를 상한까지 올리려면 첫 글자가 서로 다른 단어를 모아야 하는데, 소문자 영문은 스물여섯 글자뿐이라
단어를 27 개 넘게 담으면 반드시 어느 둘이 첫 글자를 공유합니다. 그래도 상한 `S + 1` 에 이를 수 있어요. 첫
줄처럼 긴 단어 하나를 담으면 그 하나가 노드 `S + 1` 개를 혼자 만듭니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 담긴 단어들의 **접두사 하나를 노드 하나**로 두어 같은
앞부분을 한 번만 적었고, 그래서 연산 하나가 받은 문자열의 길이만 따라가며, `search` 와 `startsWith` 는 **끝
표시 한 칸**을 보느냐 마느냐로 갈립니다.

```text
뿌리에서 출발 → 글자마다 자식을 찾는다 → 없으면 만들거나(담기) 멈춘다(묻기) → 끝 표시로 두 조회를 가른다
                                         └ 노드 하나가 접두사 하나다. 같은 앞부분은 한 번만 지난다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 는 `insert("apple")` 의 앞 세 글자를 처리한 걸음이었고, 자식이 셋 다
이미 있어 새 노드가 0 개였어요. 그런데 이 걸음에서도 자식 맵 조회는 세 번 일어납니다.

<!--proof:selfcheck-t5-->

```text
T5   insert("apple") 의 app   자식 조회 3 번(a · p · p 있음)   새 노드 0 개   노드 수 4 그대로
```

<!--/proof-->

이미 있는 것이 뻔한데 그 조회를 왜 건너뛰지 않을까요?

<!--check:whyLookupAnyway-->
건너뛸 수 있는지 **미리 알 수 없기** 때문입니다. 어디까지 이미 있는지는 그 자리에서 자식 맵을 읽어 봐야
알 수 있고, 그 읽기가 지금 하는 읽기와 같은 한 번이에요. 「어디까지 같은지」를 따로 들고 있으려면 그 값을
어딘가에 적어 두고 읽어야 하는데, 그 읽기가 자식 맵을 읽는 것과 같은 일입니다. 조건문을 앞에 따로 두지 않는 이유가 그것이에요.

| 따져 볼 것 | 드는 일 |
| --- | --- |
| 앞부분이 어디까지 같은지 미리 안다 | 그것을 알려면 결국 글자마다 무언가를 읽어야 한다 |
| 그 정보를 따로 적어 둔다 | 적는 칸과 읽는 일이 자식 맵과 같은 만큼 든다 |
| 얻는 것 | 없다 — `node.children.get(ch)` 한 번이 「있으면 그것, 없으면 `undefined`」를 이미 함께 돌려준다 |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「불변식」, 「수식 정의와 유도」, 「경쟁 설계와의 대조」를
다시 보세요.

- 담긴 단어를 지우는 연산을 더하려면 노드마다 무엇을 더 들어야 할까요? T7 에서 `ape` 를 담아 노드 `ap` 가
  자식 둘을 갖게 됐는데, 거기서 `apple` 만 지운다면 어느 노드까지 없앨 수 있는지 값으로 적어 보세요. 불변식의
  앞 문장이 무엇을 요구하는지가 실마리입니다.
- 문자 집합이 소문자 영문이 아니라 유니코드 전체로 바뀌면 노드 수의 상한과 추가 칸의 식이 어떻게 달라질까요?
  자식을 `Σ` 칸 배열로 담는 구현과 맵으로 담는 구현을 각각 적어 보세요.
- 담는 일이 전부 끝난 뒤에만 묻는다면, 트라이와 정렬 배열의 추가 칸을 공통 접두사 길이 `p` 로 각각 쓸 수

### 접두사 트리 사전

풀 파일: [`trie.ts`](./trie.ts) · 테스트: [`trie.test.ts`](./trie.test.ts) · 실행: `bun test src/algorithms/string/trie/trie.test.ts`

#### 한 줄 요약

> `Trie`는 단어를 삽입하고, 정확한 단어 존재 여부와 특정 접두사로 시작하는 단어의 존재 여부를 각각 조회할 수 있는 자료구조다.

#### 스토리

모바일 키보드 앱을 만드는 수현은 사용자가 글자를 입력할 때마다 그 접두사로 시작하는 단어가 사전에 있는지 즉시 알아야 한다. 자동 완성 목록을 띄울지 말지 결정하기 위해서다.

동시에 사용자가 입력한 단어가 정확히 사전에 등록된 단어인지도 확인해야 맞춤법 검사가 가능하다. 수현에게는 단어 삽입, 정확 일치 검색, 접두사 검색 세 가지를 각각 단어 길이에 비례하는 시간 안에 처리하는 자료구조가 필요하다.

#### 함수 인터페이스

```ts
export class Trie {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- `insert(word)` — `word`를 자료구조에 삽입한다. 반환값 없음.
- `search(word)` — `word`가 이전에 삽입된 적이 있으면 `true`, 없으면 `false`.
- `startsWith(prefix)` — `prefix`로 시작하는 단어가 하나라도 삽입되어 있으면 `true`, 없으면 `false`.

#### 제약 조건

- 단어/접두사 길이 $L \leq 10^5$
- 삽입된 모든 단어의 길이 합 $\leq 10^5$
- 각 연산의 시간 복잡도: $O(L)$
- 문자 집합: 소문자 영문 알파벳 (`a`–`z`)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

삽입된 적 없는 단어는 `search`에서 `false`를 반환한다. `startsWith`는 삽입된 단어 중 `prefix`로 시작하는 것이 하나라도 있으면 `true`다.

동일한 단어를 중복 삽입해도 오류 없이 동작해야 한다. 같은 단어를 여러 번 `insert`한 뒤 `search`하면 여전히 `true`를 반환한다.

빈 자료구조에서 `search`나 `startsWith`를 호출하면 항상 `false`를 반환한다.

`search`와 `startsWith`의 차이: `insert("apple")` 후 `search("app")`은 `false`이지만 `startsWith("app")`은 `true`다.

#### 예시

```ts
const trie = new Trie();

trie.insert("apple");
trie.search("apple");     // true  — 삽입된 단어
trie.search("app");       // false — 접두사는 단어가 아님
trie.startsWith("app");   // true  — "apple"이 "app"으로 시작함

trie.insert("app");
trie.search("app");       // true  — 이제 "app" 자체도 삽입됨

trie.startsWith("ap");    // true  — "apple"과 "app" 모두 해당
trie.startsWith("b");     // false — "b"로 시작하는 단어 없음
trie.search("appl");      // false — "appl" 자체는 삽입된 적 없음
```
