# radixTree — 갈림이 없는 구간을 라벨 하나로 접으면 노드 수가 단어 수를 따라가는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 글자 하나마다 노드를 하나씩
두는 방법에서 갈림이 없는 구간을 라벨 하나로 접는 방법까지 가는 경로를 따라갑니다. 마지막에는
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

소문자 단어를 담아 두고 두 가지를 각각 답하는 자료구조를 만드는 문제예요. 하나는 **그 문자열이
담긴 단어인가**(`search`)이고, 다른 하나는 **그 문자열로 시작하는 단어가 하나라도 있는가**
(`startsWith`)입니다. 두 질문이 다르다는 것이 이 문제의 출발점이에요.

```text
사전에 담긴 단어    apple   application   app   appl

  search("app")        참     담긴 단어 그 자체다
  search("appli")      거짓   담긴 적이 없는 문자열이다
  startsWith("appli")  참     application 이 이 다섯 글자로 시작한다
  startsWith("bat")    거짓   b 로 시작하는 단어가 하나도 없다
└ 둘째 줄과 셋째 줄이 이 문제의 요점이다 — 같은 문자열 appli 에 두 연산의 답이 갈린다
```

이 두 질문에 답하는 흔한 구조는 **글자 하나마다 노드를 하나씩 두는 트리**이고, 짧게
**트라이**라고 부릅니다. 뿌리에서 시작해 글자를 하나 읽을 때마다 한 칸 내려가면, 어떤 노드까지의 경로가 만드는 문자열이 곧 담긴
단어들의 **접두사**(문자열의 앞에서부터 잘라 낸 조각) 하나가 돼요. 위 네 단어를 그렇게 담으면
노드가 열셋 생깁니다.

```text
글자 하나마다 노드 하나 — 노드 13 개
(root)
`-- a
    `-- p
        `-- p*
            `-- l*
                +-- e*
                `-- i
                    `-- c
                        `-- a
                            `-- t
                                `-- i
                                    `-- o
                                        `-- n*
└ * 는 그 노드까지의 경로 문자열이 담긴 단어라는 표시다
```

열셋 중에서 실제로 무언가를 정하는 자리는 몇 개일까요. 자식이 둘로 나뉘는 **갈림**은 `appl`
하나뿐이고, 단어가 끝나는 자리는 `app` · `appl` · `apple` · `application` 넷이에요. 나머지
아홉은 자식이 하나뿐이면서 단어 끝도 아니라, 다음 글자가 무엇인지 말고는 아무것도 정하지
않습니다.

```text
노드 13 개를 무엇이 있는 자리인지로 나누면
  갈림이 있다               appl                                             1 개
  단어가 끝난다             app  appl  apple  application                    4 개
  둘 중 하나라도 해당된다   appl 이 위 두 줄에 다 있어 합집합이 넷이다       4 개
  둘 다 아니다              (root) a ap appi applic applica applicat …       9 개
└ 넷째 줄의 아홉이 지나가기만 하는 자리다. 4 + 9 = 13 으로 남는 것이 없다
```

**여기서 그 아홉을 없앱니다.** 갈림도 단어 끝도 아닌 자리를 노드로 두지 않고, 그 사이를 지나던
글자들을 간선 하나에 통째로 붙여 두는 거예요. 간선에 붙은 그 글자 묶음을 **라벨**이라고
부릅니다. 뿌리만 예외로 남겨 두면 노드가 열셋에서 다섯으로 줄어요.

```text
갈림이 없는 구간을 라벨 하나로 — 노드 5 개
(root)
`-- app*
    `-- l*
        +-- e*
        `-- ication*
└ 라벨을 위에서 아래로 이으면 그 노드의 경로 문자열이 된다 — app + l + ication = application
```

두 그림이 담은 단어는 같고 답도 같습니다. 갈린 것은 **노드의 개수**예요 — 앞의 그림은 담긴
글자 수를 따라가고 뒤의 그림은 담긴 단어 수를 따라갑니다. 아래 표가 문자열 다섯에
두 연산이 어떻게 답하는지를 **뒤의 구조에서** 보인 것이고, 새로 생긴 칸이 하나 있어요 —
문자열이 **라벨 한가운데서 끝날 수 있다**는 것입니다.

| 문자열 | 도착한 노드의 라벨 | 라벨에 남은 글자 | 단어 끝 표시 | `search` | `startsWith` |
| --- | --- | --- | --- | --- | --- |
| `app` | `app` | 0 | 있다 | 참 | 참 |
| `appl` | `l` | 0 | 있다 | 참 | 참 |
| `appli` | `ication` | 6 | - | 거짓 | 참 |
| `applied` | 없다 | - | - | 거짓 | 거짓 |
| `bat` | 없다 | - | - | 거짓 | 거짓 |

셋째 줄이 이 구조에만 있는 자리예요. `appli` 는 라벨 `ication` 의 첫 글자까지만 쓰고 여섯 글자를
남겼는데, 그 라벨 아래에 `application` 이 있으므로 `startsWith` 은 참이고 `appli` 자체는 담긴
적이 없으므로 `search` 는 거짓입니다. 연산 하나가 하는 일은 여전히 받은 문자열의 길이 `L` 에
비례하는 `O(L)` 이에요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **접두사가 무엇인지.** 문자열의 앞에서부터 잘라 낸 조각입니다. `apple` 의 접두사는 빈
  문자열 · `a` · `ap` · `app` · `appl` · `apple` 여섯이에요.
- **글자 하나마다 노드를 하나씩 두는 접두사 트리.** 이 글은 그 구조를 출발점으로 삼고 거기서
  노드를 줄이는 이야기를 합니다. 모르면 [`trie`](../trie/trie-guide.md) 를 먼저 보세요.
- **키로 값을 찾는 표(맵)를 쓰는 법.** 여기서는 글자 하나를 키로 두고 자식 노드를 값으로
  담습니다. 항목 하나를 넣고 꺼내는 데 드는 일이 표에 담긴 항목 수와 상관없다는 것이 필요해요.
- **트리에서 부모와 자식이 무엇인지.** 이 글에서는 자식이 여럿일 수 있고, 몇 개인지 미리
  정해져 있지 않습니다.

이 글이 다루는 것은 **접두사를 묻는 조회에서 노드 수를 줄이는 것**입니다. 노드를 줄이지 않는
쪽은 [`trie`](../trie/trie-guide.md) 가 다루고, 여러 단어를 한 번의 순회로 동시에 찾는 것은
[`ahoCorasick`](../ahoCorasick/ahoCorasick-problem.md) 가 다뤄요.

```text
  글자마다 노드를 두고 접두사를 묻는다             <- 다른 글이 다루는 것
  같은 질문에 노드를 더 적게 쓴다                  <- 이 글이 다루는 것
  여러 단어를 한 번의 순회로 동시에 찾는다         <- 또 다른 글이 다루는 것
```

### 아이디어 상세 — 갈림이 없는 구간을 라벨 하나로 접는 트리를 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
class RadixTree {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- 입력: 소문자 영문(`a`–`z`)으로만 된 문자열. `insert` 는 담고, 나머지 둘은 묻습니다.
- 출력: `search` 는 그 문자열이 담긴 단어이면 참, `startsWith` 는 그 문자열로 시작하는 단어가
  하나라도 있으면 참입니다. 같은 단어를 여러 번 담아도 답이 달라지지 않아요.
- 제약: 문자열 하나의 길이 `1 ≤ L ≤ 100,000`, 담은 모든 단어의 길이 합 `S ≤ 100,000`,
  각 연산이 `O(L)`. 시간 1 초, 메모리 256 MB.

이 글이 쓰는 기호는 여섯이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `L` | 이번 연산이 받은 문자열의 길이 | `1 ≤ L ≤ 100,000` |
| `S` | 담은 모든 단어의 길이 합 | `S ≤ 100,000` |
| `N` | 담은 서로 다른 단어의 개수 | `N ≤ S` |
| `V` | 이 트리의 노드 개수. 뿌리를 포함합니다 | 단어를 하나도 안 담았으면 `V = 1` |
| `Σ` | 문자 집합의 크기 | 소문자 영문이라 26 |
| `k` | 두 문자열이 앞에서부터 같은 글자 수 | `0 ≤ k ≤ L` |

가장 먼저 떠오르는 방법으로 시작합시다. 단어를 배열에 담고, 물을 때마다 그 배열을 앞에서부터
대조하는 것이에요.

```ts
class WordList {
  private words: string[] = [];
  insert(word: string) { this.words.push(word); }
  search(word: string) { return this.words.includes(word); }              // 단어마다 전체 대조
  startsWith(prefix: string) { return this.words.some((w) => w.startsWith(prefix)); }  // 단어마다 앞 L 글자
}
```

이 방법이 조회 하나에 읽는 글자 수는 **담긴 단어들의 길이 합**까지 갑니다. 제약이 정한 규모를
그대로 넣어 두 방식을 실행해 보면 이렇게 나와요.

<!--proof:costWorstQuery-->

```text
사전 1,000 단어 · 길이 합 100,000  답    읽은 글자  조회 1,000 번이면
목록에 담고 매번 대조한다          거짓     98,000         98,000,000
글자마다 노드를 하나씩 두는 트리   거짓         98             98,000

조회는 "aaaaaaaa...zzz" (길이 100) 하나이고 사전에 없다
└ 목록 방식은 단어 1,000 개를 각각 98 글자까지 대조한다. 트리는 98 글자에서 끝난다
```

제약이 요구한 것은 조회 하나가 `L` 에 비례하는 것인데, 목록 대조는 `S` 에 비례합니다. 그래서
**앞부분을 한 자리에만 적는 트리**가 필요하고, 그 가장 단순한 형태가 글자 하나마다 노드를
하나씩 두는 것이에요. 같은 조회 다섯을 두 방식으로 처리하고 읽은 글자를 나란히 세어 봅시다.

<!--proof:costFiveQueries-->

```text
조회                 답    목록 대조가 읽은 글자  글자마다 노드를 둔 트리가 읽은 글자
search("app")        참                        9                                    3
search("appli")      거짓                     17                                    5
startsWith("appli")  참                       10                                    5
search("applied")    거짓                     18                                    6
startsWith("bat")    거짓                      4                                    1
합계                                          58                                   20

└ 목록 대조는 단어가 늘면 함께 늘고, 트리는 조회 문자열의 길이만 따라간다
```

오른쪽 방식이 조회 하나에 읽는 글자를 **조회 문자열의 길이 이하**로 고정합니다. 여기까지가
[`trie`](../trie/trie-guide.md) 가 세운 것이고, **이 글은 그 트리에서 노드를 줄이는 이야기를
합니다.** 그러려면 먼저 노드 하나하나가 무슨 일을 하는지 봐야 해요.

<!--proof:trieShape-->

```text
노드의 경로  자식 수  단어 끝  이 노드가 정하는 것
(root)             1  아니다   없다 — 지나가기만 한다
a                  1  아니다   없다 — 지나가기만 한다
ap                 1  아니다   없다 — 지나가기만 한다
app                1  그렇다   단어 끝
appl               2  그렇다   갈림
apple              0  그렇다   단어 끝
appli              1  아니다   없다 — 지나가기만 한다
applic             1  아니다   없다 — 지나가기만 한다
applica            1  아니다   없다 — 지나가기만 한다
applicat           1  아니다   없다 — 지나가기만 한다
applicati          1  아니다   없다 — 지나가기만 한다
applicatio         1  아니다   없다 — 지나가기만 한다
application        0  그렇다   단어 끝

노드 13 개 중 지나가기만 하는 것 9 개 · 갈림이거나 단어 끝인 것 4 개
뿌리는 지나가기만 해도 남긴다 — 나머지를 접으면 1 + 4 = 5 개다
└ 지나가기만 하는 노드는 다음 글자가 무엇인지 말고는 아무것도 정하지 않는다
```

아홉 개가 아무것도 정하지 않습니다. 그런데 조회는 그 아홉을 지날 때마다 자식 맵을 한 번씩
읽어요. 같은 조회 다섯을 두 구조로 처리하고 계수를 나란히 적어 봅시다 — 오른쪽은 아직 만들지
않은 구조이지만, 앞의 「전체 컨셉」이 그린 노드 다섯짜리 트리가 그것입니다.

<!--proof:lookupsTwoWays-->

```text
조회                 답    글자마다 노드 · 맵 조회  글자마다 노드 · 글자 대조  접은 트리 · 맵 조회  접은 트리 · 글자 대조
search("app")        참                          3                          3                    1                      3
search("appli")      거짓                        5                          5                    3                      5
startsWith("appli")  참                          5                          5                    3                      5
search("applied")    거짓                        6                          6                    3                      6
startsWith("bat")    거짓                        1                          1                    1                      0
합계                                            20                         20                   11                     19

└ 글자 대조는 20 에서 19 로 거의 그대로인데 맵 조회가 20 에서 11 로 준다
  줄어든 9 는 조회 다섯이 지나가기만 하는 노드를 지나느라 맵을 본 횟수다
```

**글자 대조는 거의 그대로이고 맵 조회만 줄어듭니다.** 여기서 관찰할 것은 그 하나예요 — 읽어야
할 글자는 어차피 조회 문자열의 길이만큼인데, 그 글자들을 읽으려고 자식 맵을 스무 번 보느냐 열한
번 보느냐가 갈립니다.

| 무엇을 세는가 | 글자마다 노드 | 갈림·단어 끝만 노드 | 무엇이 정하는가 |
| --- | --- | --- | --- |
| 읽는 글자 | 20 | 19 | 조회 문자열의 길이 |
| 자식 맵 조회 | 20 | 11 | 경로 위의 노드 개수 |
| 노드 수 | 13 | 5 | 갈림과 단어 끝의 개수 |

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「자식이 하나뿐인 노드는 조건
없이 전부 접으면 되지 않나」가 그것이에요. 접는 조건에서 단어 끝을 빼고 실행해 봅니다.

<!--proof:foldCandidate-->

```text
조회                 단어 끝도 함께 보고 접은 답  단어 끝을 안 보고 접은 답  판정
search("app")                                 참                       거짓  틀리다
search("appl")                                참                         참  같다
search("apple")                               참                         참  같다
startsWith("app")                             참                         참  같다
startsWith("appli")                           참                         참  같다

구조                        노드 수
글자마다 노드 하나               13
단어 끝을 안 보고 접는다          4
단어 끝도 함께 보고 접는다        5

└ 노드가 하나 더 줄지만 app 이 단어라는 사실이 함께 사라진다
  app 은 자식이 하나뿐이면서 단어 끝이라, 접는 조건에 단어 끝을 넣어야 살아남는다
```

**단어 끝을 안 보면 `app` 이 단어라는 사실이 함께 사라집니다.** 노드가 하나 더 줄지만 답이
틀리니 그 하나는 줄일 수 없어요. 그래서 접는 조건이 둘이 됩니다.

```text
갈림이 없는 구간을 라벨 하나로 접는 트리
  노드      뿌리 · 갈림이 있는 자리 · 단어가 끝나는 자리   그 셋만 남긴다
  라벨      부모에서 이 노드로 오는 간선의 글자들          접힌 구간이 통째로 들어간다
  자식 맵   라벨의 첫 글자 -> 그 라벨을 든 자식            같은 부모의 자식들은 첫 글자가 서로 다르다
  끝 표시   그 노드의 경로 문자열이 담긴 단어인가          노드마다 참·거짓 하나
└ 접는 조건이 둘이다 — 갈림이 없고, 단어 끝도 아니어야 접는다
```

개념이 정하는 것은 **연산 하나가 지나는 노드의 개수**입니다. 글자 하나에 한 칸이 아니라 라벨
하나에 한 칸이므로, 길이 `L` 짜리 문자열이면 지나는 노드가 많아야 `L` 개예요. 라벨이 한 글자면
한 칸에 한 글자이고, 라벨이 길면 한 칸에 여러 글자입니다.

```text
길이 L 짜리 문자열 하나를 처리할 때
  대조하는 글자   최대 L 개            라벨을 앞에서부터 맞춰 본다
  자식 맵 조회    지나는 노드 개수     라벨 하나에 한 번, 많아야 L 번
  새로 만드는 노드   0 개부터 2 개까지   자식이 없으면 1 개, 라벨을 가르면 최대 2 개
└ 마지막 줄이 이 구조의 특징이다 — 삽입 하나가 만드는 노드 수가 문자열 길이와 상관없다
```

**쉬운 경우와 불안한 경우를 나눠서 값으로 확인합시다.** 쉬운 경우는 담을 단어의 첫 글자부터
자식이 없을 때예요. 남은 글자 전부를 라벨 하나로 단 잎을 만들면 끝나고, 글자를 한 번도 대조하지
않습니다.

| 담는 단어 | 그 전의 트리 | 무슨 일이 일어나는가 | 새 노드 | 노드 수 |
| --- | --- | --- | --- | --- |
| `apple` | 뿌리 하나 | `a` 로 시작하는 자식이 없다 | 잎 `apple` 하나 | 1 → 2 |
| `application` | `apple` 까지 있다 | 라벨 `apple` 과 `appl` 까지 같다 | 중간 `appl` · 잎 `ication` | 2 → 4 |
| `app` | `application` 까지 있다 | 라벨 `appl` 과 `app` 까지 같다 | 중간 `app` 하나 | 4 → 5 |
| `appl` | `app` 까지 있다 | 라벨 `app` 과 `l` 을 차례로 다 쓴다 | 없다 | 5 → 5 |

불안한 경우는 **라벨 도중에 갈릴 때**입니다. 담을 단어의 남은 글자와 자식의 라벨이 앞에서 `k`
글자까지만 같고 그 뒤가 갈릴 때인데, 그때 라벨을 `k` 글자에서 둘로 가르고 그 자리에 중간 노드를
세워요. 아래가 그 셋째 줄을 걸음마다 펼친 것입니다.

```text
insert("app") 이 하는 일 — 그 전의 트리는 (root) -- appl -- {e*, ication*}
  1. 뿌리의 자식 맵에서 a 를 찾는다        라벨 appl 을 든 자식이 나온다
  2. app 과 appl 을 앞에서부터 대조한다    k = 3 이고 라벨 길이 4 보다 짧다
  3. 라벨을 k 에서 가른다                  앞 조각 app · 뒤 조각 l
  4. 중간 노드 app 을 만든다               뒤 조각 l 을 든 옛 자식을 그 아래에 건다
  5. 뿌리의 a 자리를 중간 노드로 바꾼다    안 바꾸면 뿌리가 옛 자식을 계속 가리킨다
  6. 새 단어에 남은 글자가 없다            중간 노드 app 에 단어 끝 표시를 남긴다
└ 옛 자식의 아래(e* 와 ication*)는 손대지 않는다 — 그 아래 경로는 그대로 유효하다
```

빠뜨리는 글자가 없다는 것은 반복문을 벗어나는 길을 세어서 말할 수 있습니다. 한 바퀴를 더
돌 때마다 남은 글자가 **적어도 하나** 줄어요 — 자식 맵에서 찾은 라벨은 첫 글자가 같으므로
`k ≥ 1` 이기 때문입니다.

```text
반복문을 벗어나는 길은 셋뿐이다
  첫 글자가 같은 자식이 없다   남은 글자를 통째로 라벨로 단 잎을 만들고 끝낸다
  라벨 도중에 갈린다           그 자리에서 라벨을 가르고 끝낸다
  남은 글자가 0 이 됐다        서 있는 노드에 단어 끝 표시를 남긴다
└ 셋 다 남은 글자를 남김없이 처리한다. 한 바퀴마다 적어도 한 글자씩 줄어 언제나 끝난다
```

이제 접는 것이 노드를 얼마나 줄이는지 값으로 확인합니다. 사전 다섯에 대해 글자마다 노드를 둔
트리와 접은 트리의 노드 수를 나란히 셌어요.

```text
단어 집합                        단어 수 N  길이 합 S  글자마다 노드  라벨로 접은 노드
```

넷째 줄과 다섯째 줄이 이 표의 요점입니다. 길이 합이 똑같이 100,000 인데 왼쪽은 98,042 와
100,001 로 갈리고 오른쪽은 1,042 와 2 예요. 왼쪽을 정하는 것은 담긴 글자 수이고 오른쪽을
정하는 것은 담긴 단어 수입니다.

```text
얻은 절차 한 벌
  1.   뿌리에서 시작하고 받은 문자열 전체를 남은 글자로 둔다
  2.   남은 글자의 첫 글자로 자식 맵을 본다
  3.     자식이 없으면 남은 글자 전부를 라벨로 단 잎을 만들고 끝낸다
  4.     라벨과 앞에서부터 대조해 같은 글자 수 k 를 센다
  5.     k 가 라벨 길이와 같으면 그 자식으로 내려가고 남은 글자를 k 만큼 줄인다
  6.     아니면 라벨을 k 에서 가르고 중간 노드를 세운 뒤 끝낸다
  7.   남은 글자가 없어지면 그 자리 노드에 단어 끝 표시를 남긴다
└ 조회는 3 과 6 의 자리에서 「없다」를 내고, 4 에서 k 가 남은 글자 길이와 같아지면 그 자리를 답으로 낸다
```

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각
마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.


왜 하필 이 넷과 이 다섯일까요? 삽입의 네 갈래가 다 나오기 때문이에요 — 자식이 없어 남은 글자
전부를 라벨로 다는 삽입(`apple`), 라벨 도중에 갈려 새 잎이 하나 더 붙는 삽입(`application`),
가른 자리에서 새 단어가 끝나는 삽입(`app`), 라벨을 전부 소비하며 내려가다 남은 글자가 없어지는
삽입(`appl`)입니다. 조회 다섯은 답이 참 둘과 거짓 셋이고, **같은 문자열 `appli` 에 두 연산이
다른 답을 내는 자리**를 포함해요.

#### 1. 노드 하나의 모양과 공통 접두사 길이를 정한다

첫 조각은 노드입니다. 자식을 담는 표 하나와 끝 표시 한 칸에 더해, **라벨 문자열 하나**를
들고 있어요.

```ts
class RadixNode {
  readonly children = new Map<string, RadixNode>();   // 라벨의 첫 글자 -> 자식 노드
  end = false;                                        // 이 노드의 경로 문자열이 담긴 단어인가
  label: string;                                      // 부모에서 이 노드로 오는 간선의 글자들

  constructor(label: string) {
    this.label = label;
  }
}
```

자식 맵의 키가 **라벨 전체가 아니라 첫 글자 하나**인 것이 이 조각의 요점입니다. 같은 부모의
자식들은 첫 글자가 서로 다르므로 그 한 글자로 자식이 하나로 정해져요. 나머지 글자는 라벨 안에
그대로 남아 있고, 그것을 맞춰 보는 일이 다음 조각의 절반입니다.

```ts
function commonPrefixLength(a: string, b: string): number {
  const limit = Math.min(a.length, b.length);
  let k = 0;
  while (k < limit && a[k] === b[k]) k++;
  return k;
}
```

두 문자열이 앞에서부터 몇 글자까지 같은지를 세는 조각이에요. 짧은 쪽 길이에서 멈추므로 돌려주는
값 `k` 는 언제나 `0 ≤ k ≤ min(|a|, |b|)` 입니다.

```text
commonPrefixLength 의 값 몇 개
  ("application", "apple")   4    a p p l 까지 같고 i 와 e 에서 갈린다
  ("app",         "appl")    3    짧은 쪽이 먼저 끝난다
  ("appl",        "app")     3    같은 값이다 — 순서를 바꿔도 결과가 같다
  ("bat",         "apple")   0    첫 글자부터 다르다
└ 둘째 줄과 셋째 줄이 같은 값이라, 어느 쪽을 먼저 넘기는지는 정하지 않아도 된다
```

#### 2. 라벨을 소비하며 내려가고, 없으면 남은 글자 전부를 라벨로 단다

둘째 조각은 삽입의 앞쪽 절반입니다. 뿌리에서 출발해 남은 글자의 첫 글자로 자식을 찾고, 그
자식이 없으면 남은 글자 전부를 라벨 하나로 단 잎을 만들어요.

```ts
insert(word: string): void {
  let node = this.root;                    // ① 뿌리에서 출발한다
  let rest = word;
  while (rest !== "") {
    const head = rest[0] as string;
    const child = node.children.get(head);
    if (child === undefined) {             // ② 첫 글자가 같은 자식이 없다
      const leaf = new RadixNode(rest);
      leaf.end = true;
      node.children.set(head, leaf);
      return;
    }
    const k = commonPrefixLength(rest, child.label);
    if (k === child.label.length) {        // ③ 라벨을 전부 소비했으면 내려간다
      rest = rest.slice(k);
      node = child;
      continue;
    }
    // (가르는 자리는 다음 조각)
  }
  node.end = true;                         // ⑦ 남은 글자가 없어졌다
}
```

`②` 가 이 구조와 트라이가 갈리는 첫 자리예요. 트라이는 글자 하나짜리 노드를 `L` 개 만드는데,
여기서는 남은 글자가 몇이든 **잎 하나**를 만듭니다. 빈 트리에 `apple` 을 담으면 이렇게 돼요.

```text
insert("apple") 을 빈 트리에 — 대조한 글자 0 개
(root)
`-- apple*
└ 자식 맵이 비어 있으므로 라벨을 맞춰 볼 일이 없다. 글자를 한 번도 대조하지 않는다
```

`③` 은 라벨을 남김없이 쓴 경우입니다. `k` 가 라벨 길이와 같다는 것은 그 라벨의 글자가 전부
담을 단어에도 있다는 뜻이라, 그 자식으로 내려가고 남은 글자를 그만큼 줄여요.

```text
insert("appl") 의 두 바퀴 — 그 전의 트리는 (root) -- app* -- l -- {e*, ication*}
  1 바퀴   남은 글자 appl   라벨 app   k = 3 = 라벨 길이   내려간다   남은 글자 l
  2 바퀴   남은 글자 l      라벨 l     k = 1 = 라벨 길이   내려간다   남은 글자 없음
  종료     남은 글자 0                                    ⑦ 로 간다  노드 l 에 끝 표시
└ 새 노드가 하나도 안 생긴다. 대조한 글자는 3 + 1 = 4 개다
```

#### 3. 라벨 도중에 갈리면 그 자리에서 가른다

셋째 조각이 이 구조의 핵심입니다. `k` 가 라벨 길이보다 짧으면 그 라벨은 담을 단어와 도중에
갈리는 것이라, 라벨을 `k` 에서 둘로 가르고 그 자리에 중간 노드를 세워요.

```ts
    // ④ 라벨 도중에 갈리면 공통 부분에서 라벨을 둘로 가른다
    const mid = new RadixNode(child.label.slice(0, k));
    child.label = child.label.slice(k);
    mid.children.set(child.label[0] as string, child);
    node.children.set(head, mid);          // ⑤ 부모가 가리키던 자식 자리를 중간 노드로
    const tail = rest.slice(k);
    if (tail === "") {
      mid.end = true;                      // ⑥ 새 단어가 가른 자리에서 끝난다
    } else {
      const leaf = new RadixNode(tail);
      leaf.end = true;
      mid.children.set(tail[0] as string, leaf);
    }
    return;
```

`⑥` 의 두 갈래가 삽입 넷 중 둘을 하나씩 맡습니다. 새 단어에 남는 글자가 있으면 중간 노드에
잎이 하나 더 붙고, 남는 글자가 없으면 중간 노드 자신이 단어 끝이 돼요. 네 단어를 하나씩 담을 때마다
모양이 이렇게 됩니다.

```text

(root)
`-- apple*

insert("apple") insert("application") 까지 — 노드 4 개
(root)
`-- appl
    +-- e*
    `-- ication*

insert("apple") insert("application") insert("app") 까지 — 노드 5 개
(root)
`-- app*

insert("apple") insert("application") insert("app") insert("appl") 까지 — 노드 5 개
(root)

        `-- ication*

└ * 는 단어 끝 표시(end = true)다. 라벨을 위에서 아래로 이으면 그 노드의 경로 문자열이 된다
```

#### 멈춤 — 부모가 가리키던 자식 자리를 안 바꾸면 방금 담은 단어가 전부 사라진다

여기서 헷갈리기 쉬운 포인트는 `⑤` 입니다. 「중간 노드 아래에 옛 자식을 이미 걸었으니 연결은
끝난 것 아닌가」로 읽기 쉬워요. 그 생각대로 부모 쪽 한 줄을 걷어내 봅시다.

```ts
    const mid = new RadixNode(child.label.slice(0, k));
    child.label = child.label.slice(k);
    mid.children.set(child.label[0] as string, child);
    // node.children.set(head, mid);   <- 이 줄을 지운다
```


**중간 노드를 아무도 안 가리키므로 그 아래가 통째로 사라집니다.** 부모는 여전히 옛 자식을
가리키는데, 그 옛 자식의 라벨은 이미 `k` 글자만큼 짧아진 뒤예요. 그래서 부모에서 그 자식으로
가는 길이 원래 뜻하던 문자열과 달라집니다.

```text
insert("application") 이 라벨 apple 을 appl 과 e 로 가를 때
  부모 자리를 바꾼다    뿌리의 a -> 중간 노드 appl -> {e*, ication*}   경로가 이어진다
  안 바꾼다             뿌리의 a -> 옛 자식(라벨이 e 로 줄었다)        중간 노드는 아무도 안 가리킨다
└ 뿌리의 자식 맵은 키가 a 인데 그 자식의 라벨은 e 다 — 첫 글자부터 어긋난다
```

#### 4. 라벨 단위로 따라 내려가 두 조회를 답한다

넷째 조각은 조회입니다. 두 연산이 **같은 내려가기**를 쓰므로 그 부분을 따로 떼어 두고, 마지막
한 줄에서만 갈라요.

```ts
search(word: string): boolean {
  const hit = this.locate(word);
  return hit !== null && hit.leftover === 0 && hit.node.end;   // ⑪ 남은 글자 0 이고 끝 표시도 있어야 한다
}

startsWith(prefix: string): boolean {
  return this.locate(prefix) !== null;   // ⑫ 따라갈 수 있기만 하면 된다
}

private locate(s: string): Landing | null {
  let node = this.root;
  let rest = s;
  while (rest !== "") {
    const child = node.children.get(rest[0] as string);
    if (child === undefined) return null;   // ⑧ 첫 글자가 같은 자식이 없다
    const k = commonPrefixLength(rest, child.label);
    // ⑨ 문자열이 라벨 도중에 끝났다. 그 노드가 도착이고 라벨이 그만큼 남는다
    if (k === rest.length) return { node: child, leftover: child.label.length - k };
    if (k < child.label.length) return null;   // ⑩ 라벨 도중에 글자가 어긋났다
    rest = rest.slice(child.label.length);
    node = child;
  }
  return { node, leftover: 0 };
}
```

`⑨` 가 트라이에는 없던 자리예요. 트라이는 글자 하나에 노드 하나라 문자열이 언제나 노드 위에서
끝나는데, 여기서는 라벨 한가운데서 끝날 수 있습니다. 그때 `leftover` 가 0 보다 크고, 그 값이
두 연산의 답을 가릅니다.

| 조회 | `locate` 가 돌려준 것 | `leftover` | 끝 표시 | `⑪` 의 값 | `⑫` 의 값 |
| --- | --- | --- | --- | --- | --- |
| `search("app")` | 라벨 `app` 인 노드 | 0 | 있다 | 참 | - |
| `search("appli")` | 라벨 `ication` 인 노드 | 6 | 있다 | 거짓 | - |
| `startsWith("appli")` | 라벨 `ication` 인 노드 | 6 | 안 본다 | - | 참 |
| `search("applied")` | `null` | - | - | 거짓 | - |
| `startsWith("bat")` | `null` | - | - | - | 거짓 |

#### 멈춤 — 라벨 전체를 안 맞춰 보면 담은 적 없는 단어가 참이 된다

여기서 헷갈리기 쉬운 포인트는 `⑩` 입니다. 「자식 맵의 키가 첫 글자이고 그 키로 자식이 하나로
정해지니, 그 자식으로 내려가면 되는 것 아닌가」로 읽기 쉬워요. 그 생각대로 라벨을 맞춰 보는
줄을 걷어내 봅시다.

```ts
    if (k === rest.length) return { node: child, leftover: child.label.length - k };
```

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 둘뿐이에요 — 뿌리를 라벨 빈
문자열로 만들어 두는 한 줄과, 앞 조각이 이름만 쓰던 `Landing` 의 정의입니다.

```ts
export function commonPrefixLength(a: string, b: string): number {
  const limit = Math.min(a.length, b.length);
  let k = 0;
  while (k < limit && a[k] === b[k]) k++;
  return k;
}

class RadixNode {
  readonly children = new Map<string, RadixNode>();
  end = false;
  label: string;

  constructor(label: string) {
    this.label = label;
  }
}

interface Landing {
  node: RadixNode;
  leftover: number;
}

export class RadixTree {
  private readonly root = new RadixNode("");

  insert(word: string): void {
    // ① 뿌리에서 출발한다. `rest` 는 아직 트리에 적지 못한 남은 글자들이다.
    let node = this.root;
    let rest = word;
    while (rest !== "") {
      const head = rest[0] as string;
      const child = node.children.get(head);
      if (child === undefined) {
        // ② 첫 글자가 같은 자식이 없으면 남은 글자 전부를 라벨 하나로 단다.
        const leaf = new RadixNode(rest);
        leaf.end = true;
        node.children.set(head, leaf);
        return;
      }
      const k = commonPrefixLength(rest, child.label);
      if (k === child.label.length) {
        // ③ 라벨을 전부 소비했으면 그 자식으로 내려가고 남은 글자를 그만큼 줄인다.
        rest = rest.slice(k);
        node = child;
        continue;
      }
      // ④ 라벨 도중에 갈리면 공통 부분에서 라벨을 둘로 가른다.
      const mid = new RadixNode(child.label.slice(0, k));
      child.label = child.label.slice(k);
      mid.children.set(child.label[0] as string, child);
      // ⑤ 부모가 가리키던 자식 자리를 새 중간 노드로 바꾼다.
      node.children.set(head, mid);
      const tail = rest.slice(k);
      if (tail === "") {
        // ⑥ 새 단어가 가른 자리에서 끝나면 중간 노드가 단어 끝이다.
        mid.end = true;
      } else {
        const leaf = new RadixNode(tail);
        leaf.end = true;
        mid.children.set(tail[0] as string, leaf);
      }
      return;
    }
    // ⑦ 남은 글자가 다 없어졌으면 지금 서 있는 노드가 그 단어의 끝이다.
    node.end = true;
  }

  search(word: string): boolean {
    const hit = this.locate(word);
    // ⑪ 라벨을 남김없이 소비한 자리여야 하고, 그 노드에 단어 끝 표시도 있어야 한다.
    return hit !== null && hit.leftover === 0 && hit.node.end;
  }

  startsWith(prefix: string): boolean {
    // ⑫ 따라 내려갈 수 있기만 하면 된다. 라벨을 남겼는지도 단어 끝인지도 보지 않는다.
    return this.locate(prefix) !== null;
  }

  private locate(s: string): Landing | null {
    let node = this.root;
    let rest = s;
    while (rest !== "") {
      const child = node.children.get(rest[0] as string);
      // ⑧ 첫 글자가 같은 자식이 없으면 이 문자열은 어떤 단어의 접두사도 아니다.
      if (child === undefined) return null;
      const k = commonPrefixLength(rest, child.label);
      // ⑨ 문자열이 라벨 도중에 끝났다. 그 노드가 도착이고 라벨이 그만큼 남는다.
      if (k === rest.length)
        return { node: child, leftover: child.label.length - k };
      // ⑩ 라벨 도중에 글자가 어긋났다. 이 자식 말고는 갈 곳이 없다.
      if (k < child.label.length) return null;
      rest = rest.slice(child.label.length);
      node = child;
    }
    return { node, leftover: 0 };
  }
}
```

### 알아 두면 좋은 개념 — 경로 압축

이 절차가 한 일에는 이름이 붙어 있습니다. 갈림이 없는 구간의 노드들을 하나로 합쳐 길을 짧게
만드는 방식을 **경로 압축**이라고 불러요. 여기서 합친 것은 「자식이 하나뿐이면서 단어 끝도
아닌」 노드 아홉이었고, 그 결과 열셋이 다섯이 됐습니다.

| 어디에서 | 무엇이 한 줄로 이어져 있는가 | 무엇으로 합치는가 | 무엇이 짧아지는가 |
| --- | --- | --- | --- |
| 이 글 | 갈림이 없는 글자들 | 라벨 문자열 하나 | 조회가 지나는 노드 수 |
| 서로소 집합 | 대표를 향해 이어진 부모 사슬 | 부모를 대표로 다시 걸기 | 다음 `find` 가 지나는 노드 수 |
| 접미사 트리 | 갈림이 없는 접미사 조각 | 원문 문자열의 구간 두 수 | 노드 수와 저장 칸 |

전개의 T2 부터 T5 가 그 합침을 값으로 보인 자리예요. 노드 수가 2 · 4 · 5 · 5 로 늘었는데, 같은
네 단어를 글자마다 노드를 두는 방식으로 담으면 13 개가 됩니다.

```text
같은 이름이 나오는 다른 자리
  서로소 집합   find 가 지나온 노드를 전부 대표에 직접 건다
  접미사 트리   접미사 트라이의 갈림 없는 구간을 라벨로 접는다
  IP 라우팅 표  주소 비트의 갈림 없는 구간을 접어 표를 작게 만든다
└ 셋 다 「갈림이 없는 구간은 노드로 둘 값이 없다」는 같은 관찰을 쓴다
```

경로 압축을 집합 합치기에 쓴 것이
[`unionFind`](../../../data-structures/disjoint-set/unionFind/unionFind-problem.md) 이고,
이 글은 같은 생각을 **문자열 트리**에 쓴 것이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 노드 수의 상한을 식으로 어떻게
닫는지, 무엇이 매 삽입 뒤에 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **키가 자리로 나뉘고 접두사 자체를 묻습니다.** 문자열의 글자, 정수의 자리나 비트처럼 앞에서
  부터 하나씩 떼어 낼 수 있어야 하고, 답이 경로 도중에도 있어야 해요.
- **키가 접두사를 공유하되 갈림이 드뭅니다.** 갈림이 드물수록 접히는 구간이 길어집니다. 갈림이
  글자마다 일어나면 접을 것이 없어요.
- **키가 깁니다.** 길이 합이 같아도 단어가 길고 개수가 적을수록 노드 수가 크게 줄어듭니다.
- **노드 하나하나의 비용이 큽니다.** 노드마다 객체와 맵을 하나씩 두는 구현이면 노드 수가 곧
  비용이에요. 노드가 값싼 표현이면 접어서 얻는 것이 적습니다.

```text
네 조건이 코드의 모양을 그대로 정한다
  키가 자리로 나뉘고 접두사를 묻는다   -> 경로 도중의 노드가 답이 된다
  갈림이 드물다                       -> 라벨이 길어져 노드가 많이 줄어든다
  키가 길다                           -> 같은 길이 합에서 단어 수가 적어진다
  노드 하나의 비용이 크다             -> 노드를 줄이는 것이 곧 이득이다
```

둘째 줄이 이 구조의 경계입니다. 갈림이 글자마다 일어나는 사전이면 라벨이 전부 한 글자가 되고,
그때는 라벨 문자열을 따로 드는 만큼 오히려 칸을 더 써요.

| 사전의 모양 | 라벨의 길이 | 노드 수 | 무엇을 쓰는가 |
| --- | --- | --- | --- |
| 단어가 길고 갈림이 드물다 | 길다 | 단어 수를 따라간다 | 라벨로 접은 트리 |
| 갈림이 글자마다 일어난다 | 1 | 글자 수를 따라간다 | 글자마다 노드를 둔 트리 |
| 접두사를 아예 안 묻는다 | - | - | 해시 집합 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "자동 완성"  "이 글자로 시작하는"  "접두사"   <- startsWith 그 자체다
  "사전에 있는 단어인가"  "정확히 일치"         <- search 그 자체다
  "각 연산이 문자열 길이에 비례"                <- 담긴 단어의 개수를 보면 안 된다
  "단어가 아주 길다"  "URL 경로"  "IP 주소"     <- 갈림이 드물어 접을 구간이 길다
  "노드 수를 줄여라"  "객체 수가 문제다"        <- 접으면 노드 수가 단어 수로 눌린다

반대로 이런 말이 보이면 해당하지 않는다
  "부분 문자열"  "가운데 어디든"                <- 접두사가 아니라 다른 구조가 필요하다
  "단어가 아주 짧다"  "알파벳이 크다"           <- 갈림이 잦아 접을 구간이 없다
  "완전 일치만 묻는다"                          <- 경로 도중의 노드가 필요 없다
  "삽입은 미리 끝나고 조회만 아주 많다"         <- 조회 연산 수는 접지 않은 쪽이 적다
```

마지막 무리가 보이면 다른 구조로 갑니다. 접두사가 아니라 문자열 가운데의 조각을 물으면
[`suffixArray`](../suffixArray/suffixArray-problem.md) 쪽이고, 여러 단어를 한 번의 순회로
동시에 찾으면 [`ahoCorasick`](../ahoCorasick/ahoCorasick-problem.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **Redis 의 `rax`.** 소스 파일 첫 줄이 이 구조를 이름 그대로 밝힙니다 —
  *"Rax -- A radix tree implementation."* 그리고 헤더가 접는 규칙을 한 문장으로 적어요 —
  *"Successive nodes having a single child are 'compressed' into the node itself as a string of
  characters."* 이 글의 「갈림이 없는 구간을 라벨 하나로」와 같은 문장입니다. 쓰이는 자리는
  스트림 자료형이고, `stream.h` 의 구조체가 `rax *rax;` 필드에 *"The radix tree holding the
  stream."* 라는 주석을 달고 있어요.
  ([`src/rax.c`](https://github.com/redis/redis/blob/unstable/src/rax.c),
  [`src/rax.h`](https://github.com/redis/redis/blob/unstable/src/rax.h),
  [`src/stream.h`](https://github.com/redis/redis/blob/unstable/src/stream.h), 조회 2026-08-31)

같은 구현이 **이 글이 라벨이라고 부른 것을 소스의 말로** 적어 둡니다. 셋이 각각 이 글의
무엇인지가 그대로 대응해요.

| Redis 소스의 문장 | 어디에 | 이 글의 무엇인가 |
| --- | --- | --- |
| *"Rax -- A radix tree implementation."* | `rax.c` 첫 줄 | 이 글이 만드는 구조 |
| *"Successive nodes having a single child are 'compressed' into the node itself as a string of characters."* | `rax.h` | 갈림이 없는 구간을 라벨 하나로 접는 규칙 |
| *"The radix tree holding the stream."* | `stream.h` 의 `rax *rax;` 필드 | 담는 키가 스트림 항목의 id 다 |

- **리눅스 커널의 IPv4 경로 표 `net/ipv4/fib_trie.c`.** 주소를 비트마다 갈라 가장 긴 일치
  접두사를 찾는 자리이고, 파일 첫머리가 *"This work is based on the LPC-trie which is originally
  described in: An experimental study of compression methods for dynamic tries, Stefan Nilsson and
  Matti Tikkanen, Algorithmica, 33(1):19-33, 2002"* 라 적혀 있습니다. 그 논문 제목의 compression
  이 이 글이 하는 일이에요 — 다만 커널 쪽은 경로 압축에 **층 압축**(level compression)을 더해
  갈림이 많은 구간을 한 노드가 여러 비트로 받게 합니다.
  ([`net/ipv4/fib_trie.c`](https://github.com/torvalds/linux/blob/master/net/ipv4/fib_trie.c),
  조회 2026-08-31)

**웹 브라우저의 자동 완성이 이 구조를 쓴다는 것은 1 차 출처로 확인하지 못했습니다.** 확인한
것은 Redis 가 스트림 색인에 이 구조를 쓴다는 것과, 리눅스 커널의 경로 표가 여기에 층 압축을
더한 변형을 쓴다는 것 둘입니다.

#### 경쟁 설계와의 대조

같은 목표(문자열을 담고 접두사를 묻는 것)를 노리는 다른 절차가 바로 **글자 하나마다 노드를
하나씩 두는 트리**입니다. 이 글이 파트 1 에서 출발점으로 삼은 그 구조예요 — 접지 않는 대신
노드가 라벨 문자열을 들지 않습니다.

```text
두 설계가 같은 일을 어떻게 하는가
  라벨로 접은 트리   라벨 하나에 노드 한 칸       노드마다 라벨 문자열을 든다
  글자마다 노드      글자 하나에 노드 한 칸       노드가 라벨을 안 든다
└ 접으면 노드가 줄고, 대신 줄어든 노드가 들던 글자를 남은 노드가 라벨로 든다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **저장 칸**과 **기본 연산 수**를 셌습니다. 저장 칸은
글자 하나 · 단어 끝 표시 하나 · 자식 가리킴 하나를 각각 한 칸으로 세고, 기본 연산은 자식 맵
조회 + 글자 대조 + 노드 생성 + 끝 표시 읽기·쓰기예요. 사전은 길이 100 짜리 단어 1,000 개이고
길이 합이 제약의 최댓값 100,000 입니다.

이 판정은 다시 해야 해요.

### 수식 정의와 유도

단어 집합 `W` 에 대해 집합 셋을 차례로 정의합니다. `j` 는 0 부터 `|w|` 까지의 자리 번호이고,
`w[0..j)` 는 `w` 의 앞 `j` 글자이고, `ε` 는 빈 문자열이에요. 기호표의 `k` 와는 다른 것이라
글자를 따로 씁니다 — `k` 는 두 문자열을 실제로 대조해서 나온 값이고, `j` 는 정의를 적으려고
쓰는 자리 번호입니다.

$$\operatorname{Pref}(W) = \{\, w[0..j) \;:\; w \in W,\ 0 \le j \le |w| \,\}$$

```text
첫 집합을 읽는 법
  W          W 에 담은 단어들의 집합
  w[0..j)    w 의 앞 j 글자. j = 0 이면 빈 문자열이다
  Pref(W)    W 의 단어들이 내놓는 접두사를 전부 모은 집합
└ 글자마다 노드를 두는 트리의 노드 집합이 정확히 이 집합이다 — 전개 입력에서 원소가 13 개다
```

그중에서 **다음 글자가 둘 이상으로 갈리는 것**만 골라 낸 것이 둘째 집합입니다. `p` 는
`Pref(W)` 의 원소 하나이고, `pc` 는 그 뒤에 글자 `c` 를 붙인 문자열이에요.

$$\operatorname{Branch}(W) = \{\, p \in \operatorname{Pref}(W) \;:\; \#\{\, c : pc \in \operatorname{Pref}(W) \,\} \ge 2 \,\}$$

```text
둘째 집합을 읽는 법
  p             Pref(W) 의 원소 하나
  pc            p 뒤에 글자 c 를 붙인 문자열
  #{ c : … }    p 다음에 올 수 있는 글자가 몇 가지인가
  Branch(W)     그 가짓수가 2 이상인 접두사만 모은 집합
└ 전개 입력에서는 appl 하나뿐이다 — 다음 글자가 e 와 i 둘로 갈린다
```

빈 문자열과 담은 단어와 갈림 셋을 합친 것이 이 트리의 노드 집합이고, 그 크기가 `V` 입니다.

$$\operatorname{Node}(W) = \{\varepsilon\} \cup W \cup \operatorname{Branch}(W) \qquad V = |\operatorname{Node}(W)|$$

```text
셋째 집합을 읽는 법
  {ε}         뿌리. 어떤 단어 집합에서도 노드로 남는다
  W           단어가 끝나는 자리
  Branch(W)   갈림이 있는 자리
  V           셋을 합친 집합의 크기
└ Node(W) 는 Pref(W) 의 부분집합이다 — 접는다는 것이 곧 원소를 덜어 내는 것이다
```

정의를 전개 입력에 넣어 확인하고 갑시다.

원소 다섯이 노드 다섯과 하나씩 짝지어집니다. 그리고 라벨 글자 합이 `|Pref(W)| − 1` 과 같아요 —
라벨 글자 하나가 글자마다 노드를 두는 트리의 간선 하나에 정확히 대응하고, 그 대응이 빠짐없이
한 번씩 쓰이기 때문입니다.

```text

  라벨 app       -> 간선 (root)-a  a-p  ap-p          3 개
  라벨 l         -> 간선 app-l                        1 개

  합계 12 개 = 13 - 1 = |Pref(W)| - 1
└ 간선 하나가 정확히 한 라벨의 한 글자다. 남는 간선도 겹치는 간선도 없다
```

이제 상한을 유도합니다. 정의에서 $|\operatorname{Node}(W)| \le 1 + N + |\operatorname{Branch}(W)|$
이므로 갈림의 개수만 세면 돼요. 갈림은 이 트리에서 **자식이 둘 이상인 노드**이고, 잎은 전부
담은 단어라 잎의 개수가 `N` 을 넘지 않습니다.

$$|\operatorname{Branch}(W)| \le (\text{잎의 개수}) - 1 \le N - 1$$

```text
왜 자식이 둘 이상인 노드가 잎보다 적은가
  잎이 하나면        갈림이 하나도 없다        0 = 1 - 1
  갈림이 하나 늘면   그 아래로 잎이 하나 는다  갈림 하나마다 잎이 적어도 하나 더 필요하다
  잎이 N 개면        갈림은 많아야 N - 1 개
└ 뿌리도 자식이 둘 이상이면 이 셈에 든다. 잎이 전부 담은 단어라는 것이 N 을 상한으로 만든다
```

두 식을 합치면 상한이 닫힙니다.

$$V \le 1 + N + (N - 1) = 2N$$

```text
상한 둘을 나란히
  글자마다 노드를 둔 트리   원소가 Pref(W) 전부다      상한 S + 1     담긴 글자 수가 정한다
  라벨로 접은 트리          원소가 Node(W) 뿐이다      상한 2N        담긴 단어 수가 정한다
└ 두 상한에 같은 것이 하나도 안 들어간다 — 앞은 S 만 보고 뒤는 N 만 본다
```

**여기가 본문의 값만으로는 안 나오는 자리예요.** 파트 1 은 사전 다섯에서 노드 수를 셌을
뿐인데, 이 식은 **임의의 단어 집합**에 대해 노드 수가 길이 합 `S` 와 무관하게 단어 수 `N` 으로
눌린다고 말합니다. 글자마다 노드를 두는 쪽의 상한 `S + 1` 과 나란히 놓으면 이렇게 돼요.

```ts
// 정의를 그대로 옮긴 조각. 집합을 실제로 만들어 크기를 센다.
const nodeSetSize = (words: string[]): number => {
  const pref = new Set(
    words.flatMap((w) => Array.from({ length: w.length + 1 }, (_, j) => w.slice(0, j))),
  );
  const nextChars = (p: string) =>
    new Set(words.filter((w) => w.length > p.length && w.startsWith(p)).map((w) => w[p.length]));
  const branch = [...pref].filter((p) => nextChars(p).size >= 2);
  return new Set(["", ...words, ...branch]).size;
};
```

이 조각은 접두사를 전부 만들어 담으므로 단어 하나마다 그 길이의 제곱에 비례하는 글자를 읽습니다.
트리는 같은 값을 담는 동안 곁들여 얻으므로 따로 셀 것이 없어요. 두 상한에 제약 규모를 넣으면
이렇게 나옵니다.

### 불변식 — 뿌리가 아닌 노드는 단어 끝이거나 자식이 둘 이상이다

파트 1 에서 코드가 동작하는 것을 열 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 삽입 뒤에 참으로 남는지**를 문장으로 세우고
그것이 실제로 유지되는지 확인해 봅시다.

> `insert` 하나가 끝난 직후, 뿌리가 아닌 모든 노드는 **단어 끝 표시가 있거나 자식이 둘 이상**
> 이고, 한 노드의 자식들이 든 라벨은 **서로 다른 글자로 시작**합니다.

```text
삽입 하나를 마친 시점에 참인 것 둘
  앞 문장   지나가기만 하는 노드가 하나도 없다   접을 것이 남아 있지 않다
  뒤 문장   자식 라벨의 첫 글자가 서로 다르다    첫 글자 하나로 자식이 하나로 정해진다
└ 앞 문장이 노드 수 상한의 근거이고, 뒤 문장이 자식 맵의 키가 첫 글자여도 되는 근거다
```

문장이 둘인 것에 이유가 있습니다. 앞 문장이 깨지면 노드 수가 단어 수를 따라간다는 보장이
없어지고, 뒤 문장이 깨지면 자식 맵의 키 하나에 자식이 여럿 걸려 조회가 어느 쪽으로 갈지 정할 수
없어요.

**출발점부터 봅시다.** 아무것도 담지 않은 트리는 뿌리 하나입니다. 뿌리가 아닌 노드가 없으므로
앞 문장이 참이고, 자식이 하나도 없으므로 뒤 문장도 참이에요.

| 갈래 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 첫 글자가 같은 자식이 없다 | 남은 글자로 잎을 만든다 | 잎에 단어 끝 표시를 함께 남긴다 | 그 첫 글자를 쓰는 자식이 없었다 |
| 라벨을 전부 소비했다 | 그 자식으로 내려간다 | 노드를 만들지도 지우지도 않는다 | 자식 맵을 건드리지 않는다 |
| 라벨 도중에 갈린다 | 중간 노드를 세운다 | 다음 갈래가 자식 둘 또는 끝 표시를 준다 | 두 자식의 첫 글자가 `k` 의 정의상 다르다 |
| 새 단어가 가른 자리에서 끝난다 | 중간 노드에 끝 표시를 남긴다 | 자식 하나에 끝 표시가 붙는다 | 자식 맵을 건드리지 않는다 |
| 남은 글자가 다 없어졌다 | 서 있는 노드에 끝 표시를 남긴다 | 노드를 만들지 않는다 | 자식 맵을 건드리지 않는다 |

셋째 줄과 넷째 줄이 이 논증의 핵심입니다. 가른 뒤 중간 노드의 자식은 옛 자식 하나뿐인데, 새
단어의 남은 글자를 보고 **잎을 하나 더 걸거나 끝 표시를 남깁니다.** 둘 중 어느 쪽이든 앞 문장이
요구하는 조건을 만족해요.

```text
가른 뒤 중간 노드가 어떻게 되는가 — 전개의 T3 과 T4
  T3   새 단어에 ication 이 남는다   잎을 하나 더 건다     자식 둘 (e 와 ication)
  T4   새 단어에 남는 글자가 없다    끝 표시를 남긴다      자식 하나 (l) + 단어 끝
└ 두 줄 다 앞 문장을 만족한다. 자식 하나에 끝 표시도 없는 상태는 이 코드가 만들지 않는다
```

뒤 문장의 근거는 `k` 의 정의에 있습니다. 가른 뒤 옛 자식의 라벨은 **가르기 전 라벨의 `k` 번째
글자**로 시작하고, 새 잎의 라벨은 **담을 단어의 남은 글자 중 `k` 번째 글자**로 시작하는데,
`k` 가 앞에서부터 같은 최대 글자 수이므로 그 두 글자는 다를 수밖에 없어요 — 같았다면 `k` 가
적어도 1 더 컸을 것입니다.

| 무엇을 확인하는가 | 근거 |
| --- | --- |
| 잎에 끝 표시가 빠지는 경우가 없다 | 잎을 만드는 두 자리 모두 다음 줄에서 참으로 둔다 |
| 중간 노드가 아무것도 안 정하는 경우가 없다 | 가른 뒤 두 갈래가 자식 둘 또는 끝 표시를 준다 |
| 자식 맵의 키가 겹치는 경우가 없다 | 가를 때 두 첫 글자가 `k` 의 정의상 다르다 |
| 자식 맵의 키와 그 자식의 라벨 첫 글자가 어긋나는 경우가 없다 | 라벨을 줄인 뒤 줄어든 라벨의 첫 글자로 다시 건다 |

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 빈 트리에 조회한다 | 뿌리의 자식 맵이 비어 있다 | 둘 다 거짓이다 |
| 담긴 단어보다 긴 조회 | 라벨을 다 쓰고 다음 자식이 없다 | 둘 다 거짓이다 |
| 같은 단어를 두 번 담는다 | 노드가 하나도 안 늘고 끝 표시가 참에서 참으로 | 답이 그대로다 |
| 길이 1 짜리 단어 하나 | 라벨 한 글자짜리 잎이 하나 생긴다 | 노드 2 개 |
| 길이 100,000 짜리 단어 하나 | 라벨 100,000 글자짜리 잎이 하나 생긴다 | 노드 2 개 |

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 **가른 자리에서 새 단어가 끝날 때 중간 노드에
끝 표시를 남기는 한 줄**이에요. 「가른 자리에 이미 자식이 하나 있으니 표시까지 남길 것 있나」라는 생각으로 그 줄을
거짓 대입으로 바꿔 봅니다.

```ts
      const tail = rest.slice(k);
      if (tail === "") {

      } else {
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 네 무리입니다 — 자식 맵을 조회하는 것, 라벨과 글자를 대조하는 것,
노드를 새로 만드는 것, 끝 표시를 읽거나 쓰는 것이에요. 전개의 걸음으로 확인하면 이렇게

조회 하나의 비용이 `S` 에서 `L` 로 바뀌어요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (첫 글자가 같은 자식이 없다) | `O(L)` | `Θ(1)` — 자식 맵을 한 번만 읽는다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(L)` | 정의되지 않는다 |
| **최악의 경우** (라벨을 끝까지 맞춰 간다) | `O(L)` | `Θ(L)` — 실제로 도달한다 |

가운데 줄의 타이트한 값이 정의되지 않는 것은 **입력 분포가 없기 때문**입니다. 조회 문자열이 어느
자리에서 어긋나는지는 담긴 단어들과 조회 문자열이 함께 정하는 것이라, 분포를 가정하지 않으면
기댓값을 쓸 수 없어요. **삽입도 조회와 같은 세 줄입니다** — 빈 트리에 담으면 글자를 한 번도
대조하지 않아요(전개의 T2 가 그 걸음이고 대조한 글자가 0 입니다).

```text
상한과 타이트한 값을 가르는 자리
  그보다 더 대조하지 않는다는 것만 말한다   상한이다          O(L)
  실제로 그만큼 대조한다는 것도 말한다      타이트한 값이다   Theta(L)
└ 이 구조는 삽입도 조회도 도중에 끝날 수 있어 타이트한 값이 최악의 경우에만 붙는다
  글자마다 노드를 두는 쪽은 삽입이 글자를 언제나 끝까지 읽어서 세 줄이 모두 Theta(L) 이다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 구조의
특징이에요 — 정렬도, 미리 만드는 표도, 좌표 압축도 하지 않습니다.

```text
총식 = 담기 + 묻기 + 메모리
  담기     O(S + N) 시간            글자 대조 ≤ S · 노드 생성 V-1 · 끝 표시 쓰기 N
  묻기     O(조회 길이의 합) 시간   조회 하나가 글자 최대 L 개
  메모리   Theta(라벨 글자 합 + V) 칸   라벨 글자 합은 많아야 S 이고 V 는 많아야 2N
└ 앞뒤로 붙는 전처리 항이 하나도 없다
```

**보장의 종류를 밝혀 둡니다.** 글자 대조 횟수는 최악 보장이지만 **자식 맵 조회 하나의 비용은
기댓값**이에요. 자식을 `Map` 으로 담았고 그것이 해시 기반이라, 항목 하나를 찾는 데 드는 일이
해시가 흩어지는 정도에 달려 있습니다.

| 무엇 | 보장의 종류 | 무엇에 대한 기댓값인가 |
| --- | --- | --- |
| 대조하는 글자 수 | 최악 보장 `L` | - |
| 지나는 노드 수 | 최악 보장 `min(L, V)` | - |
| 만드는 노드 수 | 최악 보장 2 | - |
| 자식 하나를 찾는 일 | 기댓값 상수 | 해시 함수가 글자를 흩는 정도 |
| 자식을 `Σ` 칸 배열로 담으면 | 최악 보장 상수 | - |

셋째 줄이 글자마다 노드를 두는 쪽과 갈리는 자리입니다. 그쪽은 삽입 하나가 노드를 최대 `L` 개
만드는데, 여기서는 잎 하나와 중간 노드 하나로 **언제나 두 개 이하**예요.

마지막 줄은 두 구현을 가르는 자리인데, 여기서는 그 값이 훨씬 작습니다. 노드마다 `Σ` 칸 배열을
잡으면 잡는 칸이 `Σ` 곱하기 노드 수인데, 노드 수 상한이 `2N` 이라 `S + 1` 인 쪽과 곱해지는 값이
다르기 때문이에요.

```text
노드마다 Σ = 26 칸 배열을 잡으면 — 제약 규모 S = 100,000 · N = 1,000 에서
  라벨로 접은 트리     26 × 2N = 26 × 2,000 = 52,000 칸
  글자마다 노드        26 × (S + 1) = 26 × 100,001 = 2,600,026 칸
└ 둘 다 상한이다. 곱해지는 값이 단어 수인가 글자 수인가로 50 배가 갈린다
```

#### 최악을 만드는 입력

축이 셋인데 **셋을 한꺼번에 최악으로 만드는 입력이 없습니다.** 축마다 따로 구성해서 값으로
확인해 봅시다.

<!--proof:worstShape-->

```text
입력의 모양                               단어 수 N  길이 합  노드 수  그 조회의 맵 조회  그 조회의 글자 대조
길이 100,000 짜리 단어 하나                       1  100,000        2                  1              100,000
a · aa · aaa … 를 446 개                        446   99,681      447                446                  446
길이 3 이하 단어 전부와 길이 4 단어 일부     29,751   99,998   29,752                  4                    4
앞 97 글자가 같은 1,000 단어                  1,000  100,000    1,043                  2                   97

└ 첫 줄이 글자 대조를, 둘째 줄이 맵 조회를, 셋째 줄이 노드 수를 각각 최대로 만든다
  셋을 한꺼번에 최대로 만드는 입력은 없다 — 첫 줄은 노드가 둘이고 셋째 줄은 조회가 네 번 만에 끝난다
  넷째 줄은 노드가 1,043 개인데 조회 하나가 맵을 두 번밖에 안 본다 — 조회 비용을 누르는 것은 단어 개수가 아니라 문자열의 길이다
```

**「담긴 단어가 많으면 조회가 느려진다」는 이 구조에서 성립하지 않습니다.** 물려받은 통념이
여기서는 맞지 않아요 — 셋째 줄은 노드가 29,752 개인데 조회 하나가 자식 맵을 네 번 보고 끝나고,
첫 줄은 노드가 둘인데 글자를 100,000 번 대조합니다. 다만 **사전이 커져도 값이 언제나 그대로**
인 것은 아니에요 — 갈림이 늘면 경로 위 노드가 늘어 맵 조회가 함께 늡니다. 늘어도 문자열 길이
`L` 을 못 넘을 뿐입니다.

```text
축마다 최악을 만드는 입력이 다르다
  글자 대조의 최악   길이 100,000 짜리 단어 하나       라벨 하나를 끝까지 맞춘다        100,000
  맵 조회의 최악     a · aa · aaa … 를 446 개          경로 위 노드가 446 개다              446
  노드 수의 최악     짧은 단어를 예산까지 채운 사전    갈림이 글자마다 일어난다          29,752
└ 첫 줄은 노드가 둘이고 셋째 줄은 조회가 네 번에 끝난다 — 한 입력이 셋을 다 최악으로 못 만든다
```

**맵 조회의 최악이 446 에서 멈추는 데 이유가 있습니다.** 경로 위 노드가 `d` 개이면 그 노드들이
뜻하는 접두사의 길이가 1, 2, … `d` 이상이고, 각 접두사는 담은 단어이거나 갈림이라 그 아래에
길이가 그만큼인 단어가 있어야 해요. 그래서 길이 합이 적어도 `d(d+1)/2` 는 됩니다.

```text
깊이 d 를 만드는 데 드는 길이 합
  d = 100        d(d+1)/2 = 5,050        제약 안이다
  d = 446        d(d+1)/2 = 99,681       제약 안이다
  d = 447        d(d+1)/2 = 100,128      제약 100,000 을 넘는다
└ 그래서 이 제약에서 경로 위 노드는 446 개를 못 넘고, a · aa · aaa … 사전이 그 값에 도달한다
  「수식 정의와 유도」가 쓴 b · ab · aab … 와는 다른 사전이다 — 그쪽은 노드 수를 상한 2N 에 붙인다
```

**노드 수의 최악은 짧은 단어를 최대한 많이 담는 사전입니다.** 길이 1·2·3 짜리 단어를 전부 담고
남은 예산으로 길이 4 짜리를 채우면 단어가 29,751 개이고, 그때 갈림이 글자마다 일어나 접을 구간이
하나도 없어요 — 노드가 29,752 개로 글자마다 노드를 두는 쪽과 같아집니다.

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 연산 하나의 글자 대조 | 길이 100,000 짜리 단어 하나 | 100,000 |
| 연산 하나의 맵 조회 | `a` · `aa` · `aaa` … 를 446 개 | 446 |
| 노드 수 | 길이 3 이하 단어 전부와 길이 4 단어 일부 | 29,752 |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 갈림도 단어 끝도 아닌 자리를 **노드로 두지
않고** 그 사이 글자들을 라벨 하나로 접었고, 그래서 노드 수가 담긴 글자 수 대신 담긴 단어 수를
따라가며, 문자열이 라벨 한가운데서 끝날 수 있게 되면서 `search` 가 **남은 글자까지** 보게 됐습니다.

```text
  1.   노드는 갈림과 단어 끝에만 둔다     그 사이는 라벨 하나로 접는다
  2.   노드 수의 상한이 2N 이 된다        담긴 글자 수를 안 본다
  3.   라벨 한가운데서 끝날 수 있다       search 는 남은 글자가 0 인지도 본다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T4 는 라벨 `appl` 을 `app` 과 `l` 로 가른 걸음이었고,
가른 뒤 중간 노드의 자식 맵에 옛 자식을 걸 때 키로 `l` 을 썼어요. 그런데 그 옛 자식이 원래
걸려 있던 키는 `a` 였습니다. 키를 왜 다시 정해야 할까요?

```text
T4   insert("app")   대조한 글자 3   라벨 appl 을 app 과 l 로 가른다
```

<!--check:whyRekeyChild-->
**자식 맵의 키는 그 자식이 든 라벨의 첫 글자**여야 하는데, 가르면서 라벨이 `appl` 에서 `l` 로
줄었기 때문입니다. 옛 키 `a` 는 라벨 `appl` 의 첫 글자였고, 줄어든 라벨의 첫 글자는 `l` 이에요.
키를 그대로 두면 불변식의 뒤 문장이 깨져서, 조회가 `l` 로 시작하는 남은 글자를 들고 왔을 때
그 자식을 못 찾습니다.

```text
가른 뒤 중간 노드가 옛 자식을 어느 키로 드는가
  줄어든 라벨의 첫 글자로 건다   키 l  -> 라벨 l      조회가 l 을 들고 오면 찾는다
  옛 키를 그대로 쓴다            키 a  -> 라벨 l      조회가 l 을 들고 오면 못 찾는다
└ 뿌리 쪽 키가 a 인 것과 헷갈리기 쉽다 — 그쪽은 중간 노드의 라벨 app 의 첫 글자다
```

키를 정하는 규칙이 한 줄로 고정돼 있어서, 라벨이 바뀌면 키도 함께 바뀌어야 해요.
<!--/check-->
