# 라딕스 트리 — 갈림 없는 구간을 라벨 하나로 접으면 노드 수가 단어 수를 따라가는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 단어를 목록에
담고 매번 대조하는 방법에서 출발해 갈림 없는 구간을 라벨 하나로 접는 방법까지 가고, 그 방법을 준비되는
차례대로 값으로 푼 뒤, 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

소문자 단어를 담아 두고 두 가지를 따로 답하는 구조를 만듭니다. 하나는 **그 문자열이 담긴 단어인가**
(`search`)이고, 다른 하나는 **그 문자열로 시작하는 단어가 하나라도 있는가**(`startsWith`)예요. 문자열의
앞에서부터 잘라 낸 조각을 **접두사**라고 부르니, 둘째 질문은 「이 문자열이 담긴 단어의 접두사인가」와
같습니다.

이 두 질문에 답하는 흔한 구조는 **트라이**(trie)입니다. 트라이는 담은 단어들의 접두사마다 노드를 하나씩
두고, 글자 하나를 붙인 간선으로 부모와 자식을 잇는 나무예요. 네 단어 `apple` · `application` · `app` ·
`appl` 을 트라이에 담으면 이렇게 됩니다.

<!--fig:concept-trie-->
![네 단어를 담은 트라이 — 대시 테 노드는 지나가기만 한다](./figs/concept-trie.svg)

노드 안의 이름은 뿌리에서 그 노드까지 간선의 글자를 차례로 이은 문자열이고, 이것을 그 노드의 **경로
문자열**이라고 부릅니다. 「끝 표시」가 적힌 노드는 경로 문자열이 담긴 단어 그 자체예요. 노드를 무엇이
있는 자리인지로 나누면 이렇습니다. 자식이 둘로 나뉘는 자리를 **갈림**이라고 부릅니다.

<!--proof:concept-roles-->

| 자리 | 노드 | 개수 |
| --- | --- | ---: |
| 자식이 둘 이상인 갈림 | appl | 1 |
| 단어가 끝나는 자리 | app · appl · apple · application | 4 |
| 둘 중 하나 이상 | app · appl · apple · application | 4 |
| 둘 다 아닌 자리 | 뿌리 · a · ap · appli · applic · applica · applicat · applicati · applicatio | 9 |

트라이의 노드 13 개 가운데 9 개는 갈림도 단어 끝도 아닙니다. 뿌리와 셋째 줄의 4 개만 남기면 5 개입니다.

<!--/proof-->

갈림도 단어 끝도 아닌 노드는 자식이 하나뿐이라, 다음 글자가 무엇인지 말고는 아무것도 정하지 않아요.
이 글이 만드는 구조의 이름은 **라딕스 트리**(radix tree)입니다. 라딕스 트리는 **트라이에서 갈림도 단어
끝도 아닌 노드를 없애고, 그 노드들을 지나던 글자를 간선 하나에 이어 붙인 나무**예요. 간선에 붙은 글자
묶음을 **라벨**이라고 부릅니다. 뿌리는 모든 조회가 출발하는 자리라 예외로 남깁니다. 같은 네 단어를
라딕스 트리로 담으면 이렇습니다.

<!--fig:concept-radix-->
![같은 네 단어의 라딕스 트리 — 간선마다 라벨 한 묶음](./figs/concept-radix.svg)

라벨을 위에서 아래로 이으면 그 노드의 경로 문자열이 됩니다. `app` 에 `l` 과 `ication` 을 이으면
`application` 이에요. 두 그림이 담은 단어는 같고 답도 같습니다. 갈린 것은 노드의 개수이고, 새로 생긴
자리가 하나 있어요. **문자열이 라벨 한가운데서 끝날 수 있다**는 것입니다. 문자열 다섯에 두 연산이 어떻게
답하는지 라딕스 트리에서 세었습니다.

<!--proof:concept-answers-->

| 문자열 | 도착한 노드 | 라벨에 남은 글자 | 끝 표시 | search | startsWith |
| --- | --- | ---: | --- | --- | --- |
| `app` | 라벨 app | 0 | 있다 | 참 | 참 |
| `appl` | 라벨 l | 0 | 있다 | 참 | 참 |
| `appli` | 라벨 ication | 6 | 있다 | 거짓 | 참 |
| `applied` | 없다 | - | - | 거짓 | 거짓 |
| `bat` | 없다 | - | - | 거짓 | 거짓 |

라벨 한가운데서 끝나는 문자열은 `appli` 1 개이고, 그 자리에서 search 는 거짓 · startsWith 는 참입니다.

<!--/proof-->

`appli` 는 라벨 `ication` 의 첫 글자까지만 쓰고 여섯 글자를 남깁니다. 그 라벨 아래에 `application` 이
있으니 `startsWith` 는 참이고, `appli` 자체는 담은 적이 없으니 `search` 는 거짓이에요. 그래서 `search` 는
도착한 노드의 끝 표시만이 아니라 **라벨에 남은 글자가 0 인지**까지 봅니다. 연산 하나가 하는 일은 받은
문자열의 글자 수로 정해지고, 결과만 적으면 문자열 길이 `L` 에 비례하는 `O(L)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **접두사가 무엇인지.** 문자열의 앞에서부터 잘라 낸 조각입니다. 빈 문자열과 문자열 자기 자신도
  접두사에 들어요.
- **트라이가 무엇인지.** 「전체 컨셉」에서 본 만큼이면 이 글을 따라올 수 있습니다. 트라이에 단어를 담고
  묻는 과정을 한 걸음씩 보려면 [`trie`](../trie/trie-guide.md) 를 먼저 보세요.
- **키로 값을 찾는 맵을 쓰는 법.** 이 글은 글자 하나를 키로, 자식 노드를 값으로 담습니다. 항목 하나를
  넣고 꺼내는 데 드는 일이 맵에 담긴 항목 수와 상관없다는 것이 필요해요.
- **트리에서 부모 · 자식 · 깊이가 무엇인지.** 이 글의 노드는 자식이 여럿일 수 있고, 몇 개인지 미리
  정해져 있지 않습니다.

이름이 비슷한 과제 넷을 나란히 두면 이 글이 다루는 범위가 갈립니다.

| 과제 | 이 글에서 |
| --- | --- |
| 글자마다 노드를 두고 담긴 단어와 접두사를 묻는다 | 다루지 않는다 — [`trie`](../trie/trie-guide.md) |
| 같은 두 질문에 노드를 갈림과 단어 끝에만 둔다 | 다룬다 |
| 여러 단어를 긴 글 한 번의 순회로 동시에 찾는다 | 다루지 않는다 — [`ahoCorasick`](../ahoCorasick/ahoCorasick-guide.md) |
| 문자열 가운데 어디든 있는 조각을 찾는다 | 다루지 않는다 — [`suffixArray`](../suffixArray/suffixArray-guide.md) |

### 아이디어를 떠올리는 과정 — 단어 목록 대조에서 갈림 없는 구간 접기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 클래스 하나가 단어를 담고 두 가지 조회에
답합니다.

```ts
class RadixTree {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- 입력: 소문자 영문(`a`–`z`)으로만 된 길이 1 이상의 문자열. `insert` 는 담고, 나머지 둘은 묻습니다.
- 출력: `search` 는 그 문자열이 담긴 단어이면 참, `startsWith` 는 그 문자열로 시작하는 담긴 단어가
  하나라도 있으면 참입니다. 같은 단어를 여러 번 담아도 답이 달라지지 않아요.
- 규모: 문자열 하나의 길이 `L ≤ 100,000`, 담은 모든 단어의 길이 합 `S ≤ 100,000`. 조회는 여러 번 걸고,
  이 글은 조회 100,000 번으로 잽니다. 시간은 흔한 채점 환경의 예산인 1 초에 대어 보고, 메모리는
  **노드 수**로 셉니다 — 노드 하나가 객체 하나와 자식 맵 하나를 들기 때문이에요.

이 글이 쓰는 기호는 일곱이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `L` | 이번 연산이 받은 문자열의 길이 | `1 ≤ L ≤ 100,000` |
| `S` | 담은 모든 단어의 길이 합 | `S ≤ 100,000` |
| `N` | 담은 서로 다른 단어의 개수 | `N ≤ S` |
| `V` | 구조의 노드 개수. 뿌리를 포함합니다 | 단어를 하나도 안 담았으면 `V = 1` |
| `Σ` | 문자 집합의 크기 | 소문자 영문이라 26 |
| `k` | 두 문자열이 앞에서부터 같은 글자 수 | `0 ≤ k ≤ L` |
| `Q` | 같은 구조에 거는 조회 횟수 | 이 글은 `Q = 100,000` 으로 잽니다 |

가장 먼저 떠오르는 방법은 단어를 배열에 그대로 담고, 물을 때마다 그 배열을 앞에서부터 대조하는 것입니다.
답을 틀리지 않는 방법이에요.

```ts
class WordList {
  private words: string[] = [];
  insert(word: string) { this.words.push(word); }
  search(word: string) { return this.words.includes(word); }                // 단어마다 전체 대조
  startsWith(p: string) { return this.words.some((w) => w.startsWith(p)); } // 단어마다 앞 L 글자
}
```

비용은 **읽은 글자 수**로 셉니다. 조회 하나가 읽는 글자는 담긴 단어들의 길이 합까지 갈 수 있어요. 길이
합이 과제 규모의 최댓값인 사전에서 이 방법과, 같은 앞부분을 한 번만 적어 두는 트라이를 함께 세어 보면
이렇습니다.

<!--proof:origin-cost-->

| 조회 횟수 | 목록 대조가 읽은 글자 | 트라이가 읽은 글자 | 목록 대조 시간(초당 1 억 번) |
| ---: | ---: | ---: | ---: |
| 1,000 | 98,000,000 | 98,000 | 0.98 초 |
| 100,000 | 9,800,000,000 | 9,800,000 | 98.00 초 |

사전은 앞 97 글자가 같은 길이 100 짜리 단어 1,000 개(길이 합 100,000)이고, 조회는 앞 97 글자까지 맞고 그다음에서 어긋나는 없는 문자열 하나입니다. 조회 하나에 목록 대조는 98,000 글자, 트라이는 98 글자를 읽었습니다.

<!--/proof-->

조회가 100,000 번이면 목록 대조는 98 초로 예산의 98 배입니다. 트라이는 같은 조회에 조회 문자열의
길이만큼만 읽으니 시간은 여기서 풀려요. 그런데 트라이는 **글자 하나마다 노드 하나**를 만듭니다. 노드
하나가 객체 하나와 자식 맵 하나라서, 노드 수가 곧 만들어 두는 객체 수예요. 길이 합이 같은 사전 셋에서
트라이의 노드를 세었습니다.

<!--proof:origin-trie-nodes-->

| 사전 | 단어 수 N | 길이 합 S | 트라이의 노드 |
| --- | ---: | ---: | ---: |
| 앞 97 글자가 같은 1,000 단어 | 1,000 | 100,000 | 1,139 |
| 앞 3 글자에서 갈리는 1,000 단어 | 1,000 | 100,000 | 98,042 |
| 길이 100,000 짜리 단어 하나 | 1 | 100,000 | 100,001 |

세 사전 모두 길이 합이 100,000 이고, 트라이의 노드 수는 1,139 · 98,042 · 100,001 입니다. 단어가 하나뿐인 셋째 사전에서 노드가 가장 많습니다.

<!--/proof-->

단어가 하나뿐인데 노드가 100,001 개입니다. 트라이의 노드 수를 정하는 것은 담긴 단어의 수가 아니라 담긴
글자의 수예요. 그 노드들이 실제로 무슨 일을 하는지 작은 입력에서 봅시다. 네 단어 `apple` ·
`application` · `app` · `appl` 을 담은 트라이의 노드 열셋을 하나씩 적었습니다.

<!--proof:origin-roles-->

| 노드 | 자식 수 | 끝 표시 | 이 노드의 몫 |
| --- | ---: | --- | --- |
| 뿌리 | 1 | 없다 | 지나가기만 한다 |
| a | 1 | 없다 | 지나가기만 한다 |
| ap | 1 | 없다 | 지나가기만 한다 |
| app | 1 | 있다 | 단어 끝 |
| appl | 2 | 있다 | 갈림 |
| apple | 0 | 있다 | 단어 끝 |
| appli | 1 | 없다 | 지나가기만 한다 |
| applic | 1 | 없다 | 지나가기만 한다 |
| applica | 1 | 없다 | 지나가기만 한다 |
| applicat | 1 | 없다 | 지나가기만 한다 |
| applicati | 1 | 없다 | 지나가기만 한다 |
| applicatio | 1 | 없다 | 지나가기만 한다 |
| application | 0 | 있다 | 단어 끝 |

노드 13 개 가운데 지나가기만 하는 노드가 9 개입니다.

<!--/proof-->

지나가기만 하는 노드는 자식이 하나뿐이고 단어 끝도 아니라서, 다음 글자가 무엇인지 말고는 아무것도 정하지
않아요. 그런데 조회는 그 노드를 지날 때마다 자식 맵을 한 번씩 읽습니다. 같은 조회 다섯을 트라이와, 지나가기만
하는 노드를 접은 구조로 처리하고 계수를 나란히 세었습니다. 오른쪽 두 열은 「전체 컨셉」이 그린 라딕스
트리의 값이에요.

<!--proof:origin-lookups-->

| 조회 | 답 | 트라이의 맵 조회(= 글자 대조) | 라딕스 트리의 맵 조회 | 라딕스 트리의 글자 대조 |
| --- | --- | ---: | ---: | ---: |
| `search("app")` | 참 | 3 | 1 | 3 |
| `search("appli")` | 거짓 | 5 | 3 | 5 |
| `startsWith("appli")` | 참 | 5 | 3 | 5 |
| `search("applied")` | 거짓 | 6 | 3 | 6 |
| `startsWith("bat")` | 거짓 | 1 | 1 | 0 |
| 합계 |  | 20 | 11 | 19 |

맵 조회는 20 에서 11 로 줄고, 글자 대조는 20 과 19 로 거의 같습니다.

<!--/proof-->

글자 대조는 조회 문자열의 길이만큼이라 두 구조에서 거의 같고, 줄어든 것은 자식 맵 조회예요. 여기서 관찰한
것은 하나입니다. **읽어야 할 글자는 어차피 조회 문자열의 길이만큼이고, 노드는 무언가가 정해지는 자리에만
있으면 됩니다.**

그 관찰을 구조로 세우기 전에 가장 단순한 후보부터 시험합니다. 「자식이 하나뿐인 노드는 조건 없이 전부
접으면 되지 않나」예요. 단어 끝인지 보지 않고, 자식이 하나뿐인 노드를 부모에서 오는 간선의 라벨로 합쳐
봅니다.

<!--proof:origin-fold-->

| 조회 | 갈림과 단어 끝을 남긴 답 | 단어 끝을 안 보고 접은 답 | 판정 |
| --- | --- | --- | --- |
| `search("app")` | 참 | 거짓 | 틀리다 |
| `search("appl")` | 참 | 참 | 같다 |
| `search("apple")` | 참 | 참 | 같다 |
| `startsWith("app")` | 참 | 참 | 같다 |
| `startsWith("appli")` | 참 | 참 | 같다 |

노드는 트라이 13 개, 단어 끝을 안 보고 접으면 4 개, 갈림과 단어 끝을 남기고 접으면 5 개입니다. 단어 끝을 안 본 쪽은 다섯 조회 가운데 1 개가 틀립니다.

<!--/proof-->

**후보가 부족합니다.** `app` 은 자식이 하나뿐이지만 단어가 끝나는 자리라, 접으면 `app` 이 담은 단어라는
사실이 함께 사라져요. 노드가 하나 더 줄지만 답이 틀리니 그 하나는 줄일 수 없습니다. 접는 조건은 둘이어야
해요 — 갈림이 없고, 단어 끝도 아닐 것. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 넷 — 셋은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **갈림 없는 구간 접기**입니다. 갈림도 단어 끝도 아닌 노드가 이어진 구간을
노드로 두지 않고, 그 구간의 글자를 간선 하나의 라벨로 잇는 거예요. 그렇게 만든 구조가 「전체 컨셉」에서 본
라딕스 트리입니다. 노드 하나를 어떻게 적는지, 단어를 담을 때 라벨을 어디서 가르는지, 두 조회가 라벨
한가운데서 어떻게 갈리는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 갈림 없는 구간 접기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **노드는 뿌리 · 갈림 · 단어 끝에만 두고, 그 사이의 글자는
간선의 라벨 하나에 이어 붙입니다.** 이 방법은 라딕스 트리라는 구조 위에서 동작하는데, 처음 보는 사람에게는
「간선 하나가 글자 여럿」이라는 읽기와 「문자열이 라벨 도중에 끝날 수 있다」는 읽기가 낯설어요. 그래서
라딕스 트리를 먼저 따로 설명하고, 그다음 실현하는 순서대로 네 단계를 설명합니다.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 처음 한 번 | 1단계 노드 모양 정하기 | 라벨 · 자식 맵 · 끝 표시를 든 노드를 정하고, 라벨이 빈 뿌리를 만든다 | — |
| 담을 때 | 2단계 라벨을 다 쓰며 내려가기 | 남은 글자의 첫 글자로 자식을 찾아 라벨을 다 맞추면 내려가고, 자식이 없으면 남은 글자 전부를 라벨로 단 잎을 단다 | 1단계의 뿌리와 공통 접두사 길이 `k` |
| 담을 때 | 3단계 라벨 도중에 가르기 | 라벨과 도중까지만 같으면 그 자리에서 라벨을 둘로 가르고 중간 노드를 세운다 | 2단계가 멈춘 자리와 `k` |
| 물을 때 | 4단계 라벨 단위로 내려가 두 조회 답하기 | 라벨을 따라 내려가 도착한 노드와 라벨에 남은 글자로 두 조회를 가른다 | 2단계 · 3단계가 지킨 모양 |

#### 먼저 알아 둘 개념 — 라딕스 트리

라딕스 트리는 **담은 단어들의 접두사 가운데 뿌리 · 갈림 · 단어 끝만 노드로 두고, 부모에서 자식으로 가는
간선에 그 사이의 글자를 라벨로 붙인 나무**입니다. 노드는 뿌리에서 자기까지 라벨을 이은 경로 문자열 하나를
뜻하고, 그 경로 문자열이 담긴 단어인가를 끝 표시 한 칸에 적어요. 트라이와 다른 점은 간선에 붙은 것이
글자 하나가 아니라 글자 묶음이라는 것 하나입니다.

##### 입력 위의 라딕스 트리

라딕스 트리의 간선 하나가 트라이의 노드 몇 개를 대신하는지 보겠습니다. 네 단어의 트라이 위에, 라딕스
트리의 간선 하나가 덮는 노드마다 테를 둘렀어요. 대시 테 노드가 지나가기만 하는 노드입니다.

<!--fig:build-over-trie-->
![라딕스 트리의 간선 넷이 덮는 트라이의 노드](./figs/build-over-trie.svg)

테 하나가 라딕스 트리의 간선 하나이고, 테의 이름이 그 간선의 라벨이에요. 테마다 맨 아래 노드만 라딕스
트리에 남고(`app` · `appl` · `apple` · `application`), 테 안의 나머지는 노드가 아니라 라벨의 글자가
됩니다. 테가 트라이의 노드를 빠짐없이 한 번씩 덮으니, 라벨 글자를 모두 세면 트라이의 간선 수와 같아요.

##### 노드 하나를 읽는 법

노드 `application` 을 골라 읽어 보겠습니다. 뿌리에서 출발해 간선의 라벨을 하나씩 이으며 내려가요.

<!--fig:build-read-one-->
![노드 application 을 읽는 길 — 뿌리에서 라벨 셋을 차례로 잇는다](./figs/build-read-one.svg)

<!--proof:build-read-one-->

| 차례 | 지나온 라벨 | 도착한 노드 | 경로 문자열 | 끝 표시 |
| ---: | --- | --- | --- | --- |
| 0 | - | 뿌리 | 빈 문자열 | 거짓 |
| 1 | app | app | `app` | 참 |
| 2 | l | appl | `appl` | 참 |
| 3 | ication | application | `application` | 참 |

라벨 3 개를 지나 11 글자짜리 경로 문자열에 도착합니다. 트라이였다면 같은 자리까지 간선 11 개를 지납니다.

<!--/proof-->

라벨 하나를 지날 때마다 경로 문자열이 그 라벨의 길이만큼 길어집니다. 그래서 라딕스 트리에서는 깊이가
경로 문자열의 길이와 같지 않아요. 그리고 문자열이 라벨 도중에 끝나는 읽기가 하나 더 있습니다. `appli` 를
읽으면 라벨 `app` 과 `l` 을 다 쓰고 라벨 `ication` 의 첫 글자에서 문자열이 끝나요. 그때 도착한 자리는
노드 하나가 아니라 **노드 `application` 과 그 라벨에 남은 여섯 글자**의 쌍이고, 그 쌍이 「전체 컨셉」의
셋째 줄이었습니다.

##### 노드끼리의 관계

부모와 자식은 라벨로 이어져 있습니다. 노드 다섯의 부모 · 들어오는 라벨 · 자식 맵을 모두 적었어요.

<!--proof:build-relations-->

| 노드 | 부모 | 들어오는 라벨 | 자식 맵(키 → 자식) | 자식 수 | 끝 표시 |
| --- | --- | --- | --- | ---: | --- |
| 뿌리 | 없음 | - | a → app | 1 | 거짓 |
| app | 뿌리 | app | l → appl | 1 | 참 |
| appl | app | l | e → apple · i → application | 2 | 참 |
| apple | appl | e | 없음 | 0 | 참 |
| application | appl | ication | 없음 | 0 | 참 |

뿌리를 뺀 노드 4 개 가운데 4 개에서 부모의 경로 문자열 뒤에 들어오는 라벨을 붙이면 자기 경로 문자열이 됩니다. 같은 4 개 가운데 끝 표시가 있거나 자식이 둘 이상인 노드는 4 개입니다.

<!--/proof-->

세 가지 관계가 표에서 그대로 읽힙니다.

| 관계 | 표에서 | 뜻 |
| --- | --- | --- |
| 부모의 경로 문자열 + 들어오는 라벨 = 자식의 경로 문자열 | `appl` 에 `ication` 을 붙이면 `application` | 라벨은 자식 노드가 들고, 부모는 자식 맵에 그 자식을 건다 |
| 자식 맵의 키는 그 자식 라벨의 첫 글자다 | `appl` 의 자식 맵은 `e → apple` · `i → application` | 한 부모의 자식은 라벨의 첫 글자가 서로 다르다 |
| 뿌리가 아닌 노드는 끝 표시가 있거나 자식이 둘 이상이다 | `app` 은 끝 표시, `appl` 은 둘 다 | 지나가기만 하는 노드가 남아 있지 않다 |

둘째 관계가 조회를 한 갈래로 만듭니다. 남은 글자의 첫 글자 하나를 보면 갈 수 있는 자식이 많아야 하나로
정해져요. 다만 첫 글자만 맞았다고 그 자식이 맞는 것은 아니라서, 라벨의 나머지 글자는 따로 맞춰 봐야 합니다.

##### 글자마다 노드를 둔 트라이와의 차이

라딕스 트리를 처음 보면 「트라이를 그림에서만 줄여 그린 것」으로 읽기 쉽습니다. 노드가 실제로 줄어드는지
단어 집합 다섯에서 두 구조의 노드를 세었습니다.

<!--proof:build-node-count-->

| 단어 집합 | 단어 수 N | 길이 합 S | 트라이의 노드 | 라딕스 트리의 노드 |
| --- | ---: | ---: | ---: | ---: |
| {apple, application, app, appl} | 4 | 23 | 13 | 5 |
| {app, bat, cup} | 3 | 9 | 10 | 4 |
| 앞 97 글자가 같은 1,000 단어 | 1,000 | 100,000 | 1,139 | 1,043 |
| 앞 3 글자에서 갈리는 1,000 단어 | 1,000 | 100,000 | 98,042 | 1,042 |
| 길이 100,000 짜리 단어 하나 | 1 | 100,000 | 100,001 | 2 |

라딕스 트리의 노드 수는 5 줄 가운데 5 줄에서 단어 수의 두 배 이하입니다.

<!--/proof-->

그림만 줄인 것이 아니라 노드 자체가 줄어듭니다. 둘째 줄처럼 공유하는 앞부분이 없어도 줄고, 다섯째 줄처럼
단어가 하나뿐이면 뿌리와 잎 둘만 남아요. 트라이 쪽은 담긴 글자 수를 따라가고, 라딕스 트리 쪽은 담긴 단어
수를 따라갑니다. 그 상한이 언제나 `2N` 인 까닭은 「수식 정의와 유도」가 세웁니다.

##### 노드를 갈림과 단어 끝에만 두는 까닭

이 모양은 두 조회가 요구하는 것에서 나옵니다. `search` 는 도착한 자리가 단어인지를 물으니 단어가 끝나는
자리에는 끝 표시를 적을 노드가 있어야 하고, 조회가 글자 하나로 갈 곳을 고르려면 갈리는 자리에 노드가
있어야 해요. 그 밖의 자리는 둘 중 어느 것도 요구하지 않습니다.

| 조회가 요구하는 것 | 모양에서 채우는 것 |
| --- | --- |
| 도착한 자리가 담긴 단어인지 가른다 | 단어가 끝나는 자리에 노드와 끝 표시를 둔다 |
| 다음 글자에 따라 갈 곳이 갈리면 그 자리에서 고른다 | 갈림에 노드를 두고, 자식 맵의 키를 라벨의 첫 글자로 둔다 |
| 담긴 단어의 어느 접두사든 도착할 수 있다 | 라벨 도중에서도 도착으로 본다 — 노드 대신 (노드, 남은 글자) 쌍 |

#### 1단계 — 노드 모양 정하기

노드 하나가 드는 것은 셋입니다. 부모에서 이 노드로 오는 간선의 글자들 `label`, 라벨의 첫 글자를 키로 자식을
찾는 맵 `children`, 경로 문자열이 담긴 단어인가를 적는 끝 표시 `end` 예요. 트라이의 노드에 라벨 한 칸이
더해진 모양입니다.

```ts
class RadixNode {
  readonly children = new Map<string, RadixNode>(); // 라벨의 첫 글자 → 자식 노드
  end = false;                                      // 경로 문자열이 담긴 단어인가
  label: string;                                    // 부모에서 이 노드로 오는 간선의 글자들
  constructor(label: string) {
    this.label = label;
  }
}
```

처음에는 라벨이 빈 문자열인 뿌리 하나만 만듭니다. 라벨과 남은 글자를 맞춰 보는 일은 두 문자열이
앞에서부터 몇 글자까지 같은가, 곧 `k` 하나로 줄어들어요. 크기는 담은 단어가 정합니다.

| 칸 | 개수 | 「노드끼리의 관계」 표에서 |
| --- | --- | --- |
| 노드 | `V` — 뿌리 · 갈림 · 단어 끝을 합친 수, 많아야 `2N` | 표의 다섯 줄 |
| `children` 의 항목 | `V − 1` — 뿌리를 뺀 노드마다 하나 | 자식 맵 칸의 화살표 |
| 라벨 글자 | 트라이의 간선 수와 같다 — 많아야 `S` | 들어오는 라벨 칸의 글자 |

#### 2단계 — 라벨을 다 쓰며 내려가기

단어를 담을 때는 뿌리에서 출발하고, 아직 트리에 적지 못한 **남은 글자**를 듭니다. 남은 글자의 첫 글자로
자식을 찾아 자식이 없으면 남은 글자 전부를 라벨로 단 잎을 만들고 끝내요. 자식이 있으면 그 라벨과 `k` 를
세고, `k` 가 라벨 길이와 같으면 그 자식으로 내려가며 남은 글자를 `k` 만큼 줄입니다. 쉬운 경우 둘을 먼저
봅시다. 빈 트리에 `apple` 을 담는 것과, 모양이 다 선 뒤에 `appl` 을 담는 것이에요.

<!--proof:build-descend-->

| 담는 단어 | 바퀴 | 남은 글자 | 자식 | k | 한 일 | 그다음 남은 글자 |
| --- | ---: | --- | --- | --- | --- | --- |
| `apple` | 1 | apple | a 로 가는 자식 없음 | - | 잎 apple 을 단다 | 없음 |
| `appl` | 1 | appl | 라벨 app | 3 = 라벨 길이 | 내려간다 | l |
|  | 2 | l | 라벨 l | 1 = 라벨 길이 | 내려간다 | 없음 |

`apple` 은 글자를 0 번 대조하고 노드를 1 개 만들었고, `appl` 은 글자를 4 번 대조하고 노드를 0 개 만들었습니다.

<!--/proof-->

`apple` 은 트라이였다면 글자 수만큼 노드를 만들었을 자리에서 **잎 하나**를 만들고, 글자를 한 번도 대조하지
않았습니다. 자식 맵이 비어 있어 맞춰 볼 라벨이 없었기 때문이에요. `appl` 은 라벨 `app` 과 `l` 을 차례로 다
쓰고 남은 글자가 없어져, 서 있는 노드 `appl` 의 끝 표시를 참으로 두는 것으로 끝납니다.

#### 3단계 — 라벨 도중에 가르기

가장 불안한 경우는 **라벨 도중에 갈릴 때**입니다. 남은 글자와 자식의 라벨이 앞에서 `k` 글자까지만 같고 그
뒤가 다르면, 라벨을 `k` 에서 둘로 가릅니다. 앞 조각을 라벨로 든 중간 노드를 새로 세우고, 뒤 조각만 남긴
옛 자식을 그 아래에 건 뒤, 부모가 가리키던 자리를 중간 노드로 바꿔요. 새 단어에 글자가 더 남으면 그것을
라벨로 단 잎을 중간 노드 아래에 달고, 남지 않으면 중간 노드에 끝 표시를 남깁니다. 전개 입력에서 두 번
일어나요.

<!--proof:build-split-->

| 담는 단어 | 맞춰 본 라벨 | k | 앞 조각 | 뒤 조각 | 새 단어에 남은 글자 | 그다음 | 노드 수 |
| --- | --- | ---: | --- | --- | --- | --- | --- |
| `application` | apple | 4 | appl | e | ication | 잎 ication | 2 → 4 |
| `app` | appl | 3 | app | l | 없음 | 앞 조각 노드에 끝 표시 | 4 → 5 |

두 삽입 모두 옛 자식의 아래는 건드리지 않았고, 만든 노드는 2 개와 1 개입니다.

<!--/proof-->

두 걸음을 무대로 보면 이렇습니다. 굵은 테와 굵은 간선이 이번 걸음에 새로 만들었거나 라벨이 바뀐 자리,
점선이 아직 없는 노드예요. 무대 아래 「맞춰 본 라벨」 띠에서 옅게 채운 칸이 맞은 글자입니다.

<!--fig:build-split-->
![라벨 도중에 갈리는 삽입 둘 — T3 · T4](./figs/build-split.svg)

T3 에서 뿌리 아래의 라벨 `apple` 이 `appl` 과 `e` 로 갈리고, T4 에서 라벨 `appl` 이 다시 `app` 과 `l` 로
갈려요. 옛 자식 아래에 있던 것은 그대로 따라 내려갑니다. 빠뜨리는 글자가 없다는 것은 반복문을 벗어나는 길을
세어서 말할 수 있어요. 자식 맵에서 찾은 자식은 첫 글자가 같으니 `k ≥ 1` 이고, 그래서 한 바퀴를 더 돌 때마다
남은 글자가 적어도 하나 줄어듭니다.

| 반복을 벗어나는 길 | 그때 하는 일 | 남은 글자가 가는 곳 |
| --- | --- | --- |
| 첫 글자가 같은 자식이 없다 | 남은 글자 전부를 라벨로 단 잎을 만든다 | 잎의 라벨 |
| 라벨 도중에 갈린다 | 라벨을 가르고 잎을 달거나 끝 표시를 남긴다 | 잎의 라벨, 남은 것이 없으면 끝 표시 |
| 남은 글자가 없어졌다 | 서 있는 노드에 끝 표시를 남긴다 | 이미 라벨과 다 맞았다 |

셋 다 남은 글자를 남김없이 처리하고, 셋 중 하나가 반드시 일어납니다. 남은 글자가 바퀴마다 줄어드니
반복은 언제나 끝나요.

#### 4단계 — 라벨 단위로 내려가 두 조회 답하기

조회도 뿌리에서 출발해 남은 글자의 첫 글자로 자식을 찾고, 그 라벨과 `k` 를 셉니다. 2단계와 다른 점은 만들지
않는다는 것이에요. 멈추는 자리가 셋입니다. 첫 글자가 같은 자식이 없거나, 라벨 도중에 글자가 어긋나면 그
문자열은 어떤 담긴 단어의 접두사도 아니니 두 조회가 모두 거짓이에요. 남은 글자가 라벨 끝이나 도중에서
끝나면 도착이고, 도착한 노드와 라벨에 남은 글자가 답을 가릅니다. 경계에 있는 조회를 섞어 일곱을 걸었습니다.

<!--proof:build-queries-->

| 조회 문자열 | 맞춘 글자 | 멈춘 자리 | 라벨에 남은 글자 | search | startsWith |
| --- | ---: | --- | ---: | --- | --- |
| `app` | 3 | 라벨 app 인 노드 | 0 | 참 | 참 |
| `appl` | 4 | 라벨 l 인 노드 | 0 | 참 | 참 |
| `appli` | 5 | 라벨 ication 인 노드 | 6 | 거짓 | 참 |
| `applic` | 6 | 라벨 ication 인 노드 | 5 | 거짓 | 참 |
| `applied` | 5 | 라벨 ication 의 2 번째 글자에서 어긋남 | - | 거짓 | 거짓 |
| `apqle` | 2 | 라벨 app 의 3 번째 글자에서 어긋남 | - | 거짓 | 거짓 |
| `bat` | 0 | b 로 가는 자식 없음 | - | 거짓 | 거짓 |

맞춘 글자는 일곱 줄 모두 조회 문자열의 길이 이하입니다.

<!--/proof-->

`appli` 와 `applic` 은 라벨 `ication` 한가운데서 끝나 도착은 했지만 남은 글자가 있어서, `startsWith` 는
참이고 `search` 는 거짓입니다. `applied` 는 라벨 `ication` 의 둘째 글자에서, `apqle` 는 라벨 `app` 의
셋째 글자에서 어긋나 둘 다 거짓이에요. `apqle` 는 자식 맵의 키 `a` 로는 자식을 찾았는데 라벨을 맞춰 보다가
걸렸습니다. 첫 글자로 찾은 자식이 맞는 자식이라는 보장이 없다는 것이 여기서 값으로 보입니다.

#### 이 방법이 기대는 전제

갈림 없는 구간 접기는 아래 세 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 키를 앞에서부터 글자 하나씩 떼어 읽을 수 있다 | 라벨과 남은 글자의 `k` 를 센다 | 라벨과 맞춰 볼 기준이 없다 |
| 한 부모의 자식은 라벨의 첫 글자가 서로 다르다 | 첫 글자 하나로 자식을 고른다 | 키 하나에 자식이 둘 걸려 갈 곳이 안 정해진다 |
| 자식 하나를 찾는 일이 자식 수와 상관없다 | 한 칸 내려가는 비용 | 한 칸마다 자식을 하나씩 차례로 읽어야 한다 |

둘째 전제는 3단계가 지킵니다. 가를 때 두 자식의 첫 글자가 왜 서로 다른지는 「불변식」에서 `k` 의 정의로
보입니다. 묻는 것이 접두사라는 것도 전제예요. 라딕스 트리도 뿌리에서 시작하는 길만 두므로, 문자열 가운데
어디든 있는 조각을 물으면 답할 자리가 없습니다.

#### 네 단계를 이은 절차

네 단계를 코드의 순서로 다시 적으면 이렇게 됩니다.

1. 라벨이 빈 뿌리 하나를 만든다
2. 담을 때는 뿌리에서 출발해 남은 글자의 첫 글자로 자식을 찾고, 자식이 없으면 남은 글자 전부를 라벨로 단 잎을 만들고 끝낸다
3. 자식이 있으면 그 라벨과 `k` 를 세고, `k` 가 라벨 길이와 같으면 그 자식으로 내려가 남은 글자를 `k` 만큼 줄인다
4. `k` 가 라벨 길이보다 짧으면 라벨을 `k` 에서 가르고 중간 노드를 세운 뒤, 남은 글자가 있으면 잎을 달고 없으면 중간 노드에 끝 표시를 남기고 끝낸다
5. 남은 글자가 없어지면 서 있는 노드에 끝 표시를 남긴다
6. 물을 때는 같은 방식으로 내려가다 자식이 없거나 라벨 도중에 어긋나면 두 조회 모두 거짓, 문자열이 라벨 끝이나 도중에서 끝나면 `startsWith` 는 참이고 `search` 는 라벨에 남은 글자가 0 이며 끝 표시가 참일 때만 참

### 수행으로 알아보는 알고리즘 — 네 단어를 담고 다섯 번 묻는다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const tree = new RadixTree();
tree.insert("apple");
tree.insert("application");
tree.insert("app");
tree.insert("appl");
// 그다음 search("app") · search("appli") · startsWith("appli") · search("applied") · startsWith("bat") 를 묻는다
```

왜 하필 이 넷과 이 다섯일까요? 삽입의 네 갈래가 다 나오기 때문이에요. 자식이 없어 남은 글자 전부를 라벨로
다는 삽입(`apple`), 라벨 도중에 갈려 새 잎이 하나 더 붙는 삽입(`application`), 가른 자리에서 새 단어가
끝나는 삽입(`app`), 라벨을 다 쓰며 내려가다 남은 글자가 없어지는 삽입(`appl`)입니다. 조회 다섯은 답이 참
둘과 거짓 셋이고, **같은 문자열 `appli` 에 두 연산이 다른 답을 내는 자리**를 포함해요.

```text
절차 전체를 한 장으로
  T1       뿌리 하나로 시작한다
  T2~T5    단어 넷을 담는다
             뿌리에서 출발한다                     ①
             첫 글자가 같은 자식이 없으면 잎을 단다 ②
             라벨을 다 쓰면 내려간다                ③
             라벨 도중에 갈리면 가른다              ④ 가르기 · ⑤ 부모 자리 바꾸기 · ⑥ 가른 자리가 단어 끝인가
             남은 글자가 없어지면 끝 표시를 남긴다  ⑦
  T6~T10   다섯 번 묻는다
             라벨 단위로 따라 내려간다              ⑧ 자식이 없다 · ⑨ 라벨 끝이나 도중에서 끝났다 · ⑩ 라벨 도중에 어긋났다
             남은 글자와 끝 표시를 본다             ⑪ search 의 마지막 한 줄
             따라갈 수 있기만 하면 된다             ⑫ startsWith 의 마지막 한 줄
```

#### 1. 노드 하나의 모양과 공통 접두사 길이를 정한다

첫 조각은 노드입니다. 자식을 담는 맵과 끝 표시에 더해 라벨 문자열 하나를 들어요. 트리 자체는 라벨이 빈
뿌리 하나를 들고 시작합니다. 라벨과 남은 글자를 맞춰 보는 함수도 여기서 만들어 둡니다.

```ts
function commonPrefixLength(a: string, b: string): number {
  const limit = Math.min(a.length, b.length);
  let k = 0;
  while (k < limit && a[k] === b[k]) k++;
  return k;
}

class RadixNode {
  readonly children = new Map<string, RadixNode>();   // 라벨의 첫 글자 -> 자식 노드
  end = false;                                        // 이 노드의 경로 문자열이 담긴 단어인가
  label: string;                                      // 부모에서 이 노드로 오는 간선의 글자들

  constructor(label: string) {
    this.label = label;
  }
}

export class RadixTree {
  private readonly root = new RadixNode("");
}
```

실행하면 이렇게 나옵니다. 문자열 쌍 넷에 `commonPrefixLength` 를 걸고, 빈 트리의 뿌리를 열어 봤어요.

<!--proof:walk-node-->

```text
commonPrefixLength("application", "apple")  →  4
commonPrefixLength("app", "appl")           →  3
commonPrefixLength("appl", "app")           →  3
commonPrefixLength("bat", "apple")          →  0
new RadixTree()                             →  노드 1 개(뿌리) · 뿌리의 라벨 길이 0
```

<!--/proof-->

`commonPrefixLength` 는 짧은 쪽 길이에서 멈추므로 돌려주는 `k` 는 언제나 `0 ≤ k ≤ min(|a|, |b|)` 이고,
둘째 줄과 셋째 줄처럼 순서를 바꿔도 같은 값이에요. 그래서 어느 쪽을 먼저 넘기는지 정하지 않아도 됩니다.
자식 맵의 키가 **라벨 전체가 아니라 첫 글자 하나**라는 것도 이 조각의 요점입니다. 나머지 글자를 맞춰 보는
일은 이 함수가 맡아요.

#### 2. 라벨을 다 쓰면 내려가고, 없으면 남은 글자 전부를 라벨로 단다

둘째 조각은 삽입의 앞쪽 절반입니다. 뿌리에서 출발해 남은 글자의 첫 글자로 자식을 찾고, 자식이 없으면 남은
글자 전부를 라벨 하나로 단 잎을 만들어요.

```ts
insert(word: string): void {
  let node = this.root;                    // ① 뿌리에서 출발한다
  let rest = word;
  while (rest !== "") {
    const head = rest[0] as string;
    const child = node.children.get(head);
    if (child === undefined) {             // ② 첫 글자가 같은 자식이 없다
      const leaf = new RadixNode(rest);
      leaf.end = true;
      node.children.set(head, leaf);
      return;
    }
    const k = commonPrefixLength(rest, child.label);
    if (k === child.label.length) {        // ③ 라벨을 다 썼으면 내려간다
      rest = rest.slice(k);
      node = child;
      continue;
    }
    // (가르는 자리는 다음 조각)
  }
  node.end = true;                         // ⑦ 남은 글자가 없어졌다
}
```

여기서 가장 중요한 줄은 `②` 입니다. 트라이는 이 자리에서 글자 하나짜리 노드를 글자 수만큼 만드는데, 여기서는
남은 글자가 몇이든 **잎 하나**를 만들어요. 이 조각을 빈 트리에 건 `apple` 과, 모양이 다 선 트리에 건 `appl`
에 실행하면 이렇게 나옵니다.

<!--proof:walk-descend-->

```text
insert("apple")  →  ② · 대조한 글자 0 · 새 노드 1 · 노드 2 개
insert("appl")   →  ③ ③ ⑦ · 대조한 글자 4 · 새 노드 0 · 노드 5 개
```

<!--/proof-->

`apple` 은 `②` 한 번으로 끝났고, `appl` 은 `③` 을 두 번 지나 `⑦` 에서 끝 표시를 남겼습니다. 둘 다 노드를
만드는 일이 문자열 길이와 상관없어요.

#### 3. 라벨 도중에 갈리면 그 자리에서 가른다

셋째 조각이 이 구조의 핵심입니다. `k` 가 라벨 길이보다 짧으면 그 라벨은 담을 단어와 도중에 갈리는 것이라,
라벨을 `k` 에서 둘로 가르고 그 자리에 중간 노드를 세워요.

```ts
    // ④ 라벨 도중에 갈리면 공통 부분에서 라벨을 둘로 가른다
    const mid = new RadixNode(child.label.slice(0, k));
    child.label = child.label.slice(k);
    mid.children.set(child.label[0] as string, child);
    node.children.set(head, mid);          // ⑤ 부모가 가리키던 자식 자리를 중간 노드로
    const tail = rest.slice(k);
    if (tail === "") {
      mid.end = true;                      // ⑥ 새 단어가 가른 자리에서 끝난다
    } else {
      const leaf = new RadixNode(tail);
      leaf.end = true;
      mid.children.set(tail[0] as string, leaf);
    }
    return;
```

`⑥` 의 두 갈래가 삽입 넷 중 둘을 하나씩 맡습니다. 새 단어에 남는 글자가 있으면 중간 노드에 잎이 하나 더
붙고, 남는 글자가 없으면 중간 노드 자신이 단어 끝이 돼요. 네 단어를 하나씩 다 담은 걸음을 모으면 모양이
이렇게 자랍니다.

<!--fig:walk-insert-shapes-->
![단어 하나를 다 담은 걸음 넷 — T2 · T3 · T4 · T5](./figs/walk-insert-shapes.svg)

T2 에서 뿌리 아래에 라벨 `apple` 하나였던 간선이 T3 에서 `appl` 과 `e` 로 갈리고, T4 에서 `appl` 이 다시
`app` 과 `l` 로 갈려요. 가르기 전의 간선은 가른 뒤 무대에서 사라집니다. T5 에서는 노드가 하나도 늘지 않고
`appl` 의 끝 표시만 참이 됐어요.

#### 짚고 가기 — 부모가 가리키던 자식 자리를 안 바꾸면 담은 단어가 사라진다

여기서 헷갈리기 쉬운 포인트는 `⑤` 입니다. 「중간 노드 아래에 옛 자식을 이미 걸었으니 연결은 끝난 것
아닌가」로 읽기 쉬워요. 그 생각대로 부모 쪽 한 줄을 지워 봅시다.

```ts
    const mid = new RadixNode(child.label.slice(0, k));
    child.label = child.label.slice(k);
    mid.children.set(child.label[0] as string, child);
    // node.children.set(head, mid);   ← 이 줄을 지운다
```

담은 단어 넷에 조회 여섯을 걸어 봅니다.

<!--proof:pauseRelink-->

| 조회 | 정본이 낸 답 | 부모를 안 바꾼 답 | 판정 |
| --- | --- | --- | --- |
| `search("app")` | 참 | 거짓 | 틀리다 |
| `search("appl")` | 참 | 거짓 | 틀리다 |
| `search("apple")` | 참 | 거짓 | 틀리다 |
| `search("application")` | 참 | 거짓 | 틀리다 |
| `startsWith("appli")` | 참 | 거짓 | 틀리다 |
| `startsWith("bat")` | 거짓 | 거짓 | 같다 |

여섯 조회 가운데 5 개가 틀립니다. 노드는 정본이 5 개, 부모를 안 바꾼 쪽이 2 개입니다.

<!--/proof-->

부모를 안 바꾼 코드가 네 단어로 만든 모양을 그리면 이렇습니다.

<!--fig:pause-relink-->
![부모를 안 바꾼 코드가 네 단어로 만든 모양](./figs/pause-relink.svg)

**중간 노드를 아무도 가리키지 않으니 그 아래가 통째로 사라집니다.** 뿌리는 여전히 옛 자식을 가리키는데,
그 옛 자식의 라벨은 이미 `k` 글자만큼 잘린 뒤예요. 그래서 뿌리의 자식 맵은 키가 `a` 인데 그 자식의 라벨은
`e` 로 시작하고, 경로 문자열도 `apple` 이 아니라 `e` 가 됐습니다. 새로 만든 중간 노드와 그 아래에 단
잎은 어디에도 걸리지 않았어요.

#### 4. 라벨 단위로 따라 내려가 두 조회를 답한다

넷째 조각은 조회입니다. 두 연산이 **같은 내려가기**를 쓰므로 그 부분을 `locate` 로 떼어 두고, 마지막 한
줄에서만 갈라요. `locate` 는 도착한 노드와 그 라벨에 남은 글자 수 `leftover` 를 함께 돌려줍니다.

```ts
search(word: string): boolean {
  const hit = this.locate(word);
  return hit !== null && hit.leftover === 0 && hit.node.end;   // ⑪ 남은 글자 0 이고 끝 표시도 있어야 한다
}

startsWith(prefix: string): boolean {
  return this.locate(prefix) !== null;   // ⑫ 따라갈 수 있기만 하면 된다
}

private locate(s: string): Landing | null {
  let node = this.root;
  let rest = s;
  while (rest !== "") {
    const child = node.children.get(rest[0] as string);
    if (child === undefined) return null;   // ⑧ 첫 글자가 같은 자식이 없다
    const k = commonPrefixLength(rest, child.label);
    // ⑨ 문자열이 라벨 끝이나 도중에서 끝났다. 그 노드가 도착이고 라벨이 그만큼 남는다
    if (k === rest.length) return { node: child, leftover: child.label.length - k };
    if (k < child.label.length) return null;   // ⑩ 라벨 도중에 글자가 어긋났다
    rest = rest.slice(child.label.length);
    node = child;
  }
  return { node, leftover: 0 };
}
```

`⑨` 가 트라이에는 없던 자리예요. 트라이는 글자 하나에 노드 하나라 문자열이 언제나 노드 위에서 끝나는데,
여기서는 라벨 한가운데서 끝날 수 있습니다. 담은 단어 넷에 조회 다섯을 걸면 `locate` 가 돌려준 것과 마지막 한
줄의 값이 이렇게 나와요.

<!--proof:walk-queries-->

| 조회 | locate 가 돌려준 것 | leftover | 끝 표시 | ⑪ 의 값 | ⑫ 의 값 |
| --- | --- | ---: | --- | --- | --- |
| `search("app")` | 라벨 app 인 노드 | 0 | 참 | 참 | - |
| `search("appli")` | 라벨 ication 인 노드 | 6 | 참 | 거짓 | - |
| `startsWith("appli")` | 라벨 ication 인 노드 | 6 | 안 본다 | - | 참 |
| `search("applied")` | `null` | - | - | 거짓 | - |
| `startsWith("bat")` | `null` | - | - | - | 거짓 |

`search("appli")` 와 `startsWith("appli")` 는 `locate` 가 같은 노드와 같은 `leftover` 를 돌려줬는데 답이
갈립니다. `⑪` 은 `leftover` 가 0 인지를 먼저 보고, `⑫` 는 보지 않기 때문이에요. 끝 표시가 참인 노드에
도착했는데도 `search` 가 거짓인 것이 이 구조의 새 자리입니다.

#### 짚고 가기 — 라벨 전체를 안 맞춰 보면 담은 적 없는 단어가 참이 된다

여기서 헷갈리기 쉬운 포인트는 `⑩` 입니다. 「자식 맵의 키가 첫 글자이고 그 키로 자식이 하나로 정해지니, 그
자식으로 내려가면 되는 것 아닌가」로 읽기 쉬워요. 그 생각대로 라벨을 맞춰 보는 줄을 지워 봅시다.

```ts
    const k = commonPrefixLength(rest, child.label);
    if (k === rest.length) return { node: child, leftover: child.label.length - k };
    // if (k < child.label.length) return null;   ← 이 줄을 지운다
    rest = rest.slice(child.label.length);
```

담은 단어 넷에 조회 여섯을 걸어 봅니다.

| --- | --- | --- | --- |
| `search("app")` | 참 | 참 | 같다 |
| `search("apple")` | 참 | 참 | 같다 |
| `search("apqle")` | 거짓 | 참 | 틀리다 |
| `search("applied")` | 거짓 | 참 | 틀리다 |
| `startsWith("apqle")` | 거짓 | 참 | 틀리다 |
| `startsWith("bat")` | 거짓 | 거짓 | 같다 |

여섯 조회 가운데 3 개가 틀리고, 틀린 줄은 모두 담은 적 없는 문자열이 참으로 나온 자리입니다.

<!--/proof-->

`apqle` 가 두 방식에서 어느 자리를 지나는지 따라가 보면 틀리는 까닭이 보입니다.

<!--proof:pause-apqle-->

| --- | --- | --- |

라벨을 안 맞춰 본 쪽은 라벨 3 개를 지나 끝 표시가 참인 노드에 도착합니다.

<!--/proof-->

**자식 맵의 키는 라벨의 첫 글자뿐입니다.** 첫 글자가 맞았다는 것은 「이 자식 말고는 후보가 없다」는
뜻이지 「이 자식이 맞다」는 뜻이 아니에요. 라벨을 안 맞춰 본 쪽은 `apqle` 의 `q` 를 한 번도 보지 않고
라벨 길이만큼 잘라 냈고, 남은 `le` 가 우연히 `apple` 의 뒤쪽 라벨과 맞아 담긴 단어의 끝 표시를 읽었습니다.

#### 짚고 가기 — 라벨 도중에 끝난 문자열을 도착으로 안 보면 접두사 조회만 조용히 거짓이 된다

여기서 헷갈리기 쉬운 포인트는 `⑨` 의 조건입니다. 「노드에 도착했다고 하려면 그 라벨을 다 썼어야 하지
않나」로 읽기 쉬워요. 그 생각대로 `⑨` 에 라벨을 다 썼는지를 더해 봅시다.

```ts
    if (k === rest.length && k === child.label.length)   // ← 라벨을 다 써야 도착으로 본다. 원래는 k === rest.length 만 본다
      return { node: child, leftover: child.label.length - k };
    if (k < child.label.length) return null;
```

| `search("app")` | 참 | 참 | 같다 |

**`search` 의 답은 한 줄도 안 틀립니다.** 라벨 한가운데서 끝나는 문자열은 어차피 담긴 단어가 아니라
`search` 가 거짓을 내야 하는데, 이 코드도 거짓을 내기 때문이에요. 그래서 `search` 만 시험하면 끝까지 모르고
넘어갑니다. 틀리는 것은 `appli` · `applic` 처럼 라벨 한가운데서 끝나는 접두사를 물은 `startsWith` 이고,
`application` 이 실제로 담겨 있는데 없다고 답해요. 그러니 `⑨` 는 라벨에 글자가 남아도 도착으로 봐야 합니다.

#### 6. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 하나예요. 앞 조각이 이름만 쓰던 `Landing`
의 정의입니다.

```ts
export function commonPrefixLength(a: string, b: string): number {
  const limit = Math.min(a.length, b.length);
  let k = 0;
  while (k < limit && a[k] === b[k]) k++;
  return k;
}

class RadixNode {
  readonly children = new Map<string, RadixNode>();
  end = false;
  label: string;

  constructor(label: string) {
    this.label = label;
  }
}

interface Landing {
  node: RadixNode;
  leftover: number;
}

export class RadixTree {
  private readonly root = new RadixNode("");

  insert(word: string): void {
    // ① 뿌리에서 출발한다. `rest` 는 아직 트리에 적지 못한 남은 글자들이다.
    let node = this.root;
    let rest = word;
    while (rest !== "") {
      const head = rest[0] as string;
      const child = node.children.get(head);
      if (child === undefined) {
        // ② 첫 글자가 같은 자식이 없으면 남은 글자 전부를 라벨 하나로 단다.
        const leaf = new RadixNode(rest);
        leaf.end = true;
        node.children.set(head, leaf);
        return;
      }
      const k = commonPrefixLength(rest, child.label);
      if (k === child.label.length) {
        // ③ 라벨을 전부 소비했으면 그 자식으로 내려가고 남은 글자를 그만큼 줄인다.
        rest = rest.slice(k);
        node = child;
        continue;
      }
      // ④ 라벨 도중에 갈리면 공통 부분에서 라벨을 둘로 가른다.
      const mid = new RadixNode(child.label.slice(0, k));
      child.label = child.label.slice(k);
      mid.children.set(child.label[0] as string, child);
      // ⑤ 부모가 가리키던 자식 자리를 새 중간 노드로 바꾼다.
      node.children.set(head, mid);
      const tail = rest.slice(k);
      if (tail === "") {
        // ⑥ 새 단어가 가른 자리에서 끝나면 중간 노드가 단어 끝이다.
        mid.end = true;
      } else {
        const leaf = new RadixNode(tail);
        leaf.end = true;
        mid.children.set(tail[0] as string, leaf);
      }
      return;
    }
    // ⑦ 남은 글자가 다 없어졌으면 지금 서 있는 노드가 그 단어의 끝이다.
    node.end = true;
  }

  search(word: string): boolean {
    const hit = this.locate(word);
    // ⑪ 라벨을 남김없이 소비한 자리여야 하고, 그 노드에 단어 끝 표시도 있어야 한다.
    return hit !== null && hit.leftover === 0 && hit.node.end;
  }

  startsWith(prefix: string): boolean {
    // ⑫ 따라 내려갈 수 있기만 하면 된다. 라벨을 남겼는지도 단어 끝인지도 보지 않는다.
    return this.locate(prefix) !== null;
  }

  private locate(s: string): Landing | null {
    let node = this.root;
    let rest = s;
    while (rest !== "") {
      const child = node.children.get(rest[0] as string);
      // ⑧ 첫 글자가 같은 자식이 없으면 이 문자열은 어떤 단어의 접두사도 아니다.
      if (child === undefined) return null;
      const k = commonPrefixLength(rest, child.label);
      // ⑨ 문자열이 라벨 도중에 끝났다. 그 노드가 도착이고 라벨이 그만큼 남는다.
      if (k === rest.length)
        return { node: child, leftover: child.label.length - k };
      // ⑩ 라벨 도중에 글자가 어긋났다. 이 자식 말고는 갈 곳이 없다.
      if (k < child.label.length) return null;
      rest = rest.slice(child.label.length);
      node = child;
    }
    return { node, leftover: 0 };
  }
}
```

```text
tree.search("appli")                →  false
tree.startsWith("appli")            →  true
tree.search("applied")              →  false
tree.startsWith("bat")              →  false
tree.search("apple")                →  true
tree.search("applepie")             →  false
```

아래 일곱 줄은 전개에서 안 나온 자리입니다. 담긴 단어 그 자체, 담긴 단어보다 긴 조회, 단어와 같은 접두사,
빈 트리의 두 조회, 같은 단어를 두 번 담은 경우, 길이 1 짜리 단어예요.

### 알아 두면 좋은 개념 — 경로 압축

이 절차가 한 일에는 이름이 붙어 있습니다. 갈림이 없는 구간의 노드들을 하나로 합쳐 길을 짧게 만드는 방식을
**경로 압축**이라고 불러요. 여기서 합친 것은 「자식이 하나뿐이면서 단어 끝도 아닌」 노드였습니다. 전개의
T2 부터 T5 까지가 그 합침을 값으로 보인 자리예요. 같은 네 단어를 하나씩 담을 때 두 구조의 노드를 세면
이렇습니다.

<!--proof:related-fold-->

| 걸음 | 담은 단어 | 라딕스 트리의 노드 | 트라이의 노드 |
| --- | --- | ---: | ---: |
| T2 | apple | 2 | 6 |
| T3 | apple · application | 4 | 13 |
| T4 | apple · application · app | 5 | 13 |
| T5 | apple · application · app · appl | 5 | 13 |

| 다시 나오는 자리 | 한 줄로 이어진 것 | 합치는 방법 | 짧아지는 것 |
| --- | --- | --- | --- |
| 이 글의 라딕스 트리 | 갈림이 없는 글자들 | 라벨 문자열 하나 | 조회가 지나는 노드 수 |
| 서로소 집합 | 대표를 향해 이어진 부모 사슬 | `find` 가 지나온 노드를 대표에 직접 건다 | 다음 `find` 가 지나는 노드 수 |
| 접미사 트리 | 갈림이 없는 접미사 조각 | 원문 문자열의 구간 두 수 | 노드 수와 추가 칸 |
| IP 경로 표 | 주소 비트의 갈림 없는 구간 | 비트 묶음 하나 | 주소 하나가 지나는 노드 수 |

넷 다 「갈림이 없는 구간은 노드로 둘 값이 없다」는 같은 관찰을 씁니다. 경로 압축을 집합 합치기에 쓴 것이
[`unionFind`](../../../data-structures/disjoint-set/unionFind/unionFind.ts) 이고, 이 글은 같은 생각을
**문자열 트리**에 쓴 것이에요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 노드 수의 상한을 식으로 어떻게 닫는지, 무엇이
매 삽입 뒤에 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 키가 자리로 나뉘고 접두사 자체를 묻는다 | 문자열의 글자, 정수의 자리나 비트처럼 앞에서부터 떼어 읽고, 답이 경로 도중에도 있다 | `startsWith` 가 라벨 도중의 도착도 참으로 본다 |
| 키가 접두사를 공유하되 갈림이 드물다 | 갈림이 드물수록 접히는 구간이 길어진다 | 라벨이 길어져 노드가 줄어든다 |
| 키가 길다 | 길이 합이 같아도 단어가 길고 개수가 적을수록 노드가 크게 준다 | 노드 수 상한 `2N` 이 `S + 1` 보다 훨씬 작다 |
| 노드 하나하나의 비용이 크다 | 노드마다 객체와 맵을 하나씩 두는 구현 | 노드를 줄이는 것이 곧 추가 칸을 줄이는 것이다 |

둘째 줄이 이 구조의 경계입니다. 갈림이 글자마다 일어나는 사전이면 라벨이 전부 한 글자가 되고, 그때는 라벨
문자열을 따로 드는 만큼 오히려 칸을 더 써요.

| 사전의 모양 | 라벨의 길이 | 노드 수 | 알맞은 구조 |
| --- | --- | --- | --- |
| 단어가 길고 갈림이 드물다 | 길다 | 단어 수를 따라간다 | 라딕스 트리 |
| 갈림이 글자마다 일어난다 | 1 | 글자 수를 따라간다 | 트라이 |
| 접두사를 아예 안 묻는다 | - | - | 해시 집합 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "자동 완성"  "이 글자로 시작하는"  "접두사"   <- startsWith 그 자체다
  "사전에 있는 단어인가"  "정확히 일치"         <- search 그 자체다
  "각 연산이 문자열 길이에 비례"                <- 담긴 단어의 개수를 보면 안 된다
  "단어가 아주 길다"  "URL 경로"  "IP 주소"     <- 갈림이 드물어 접을 구간이 길다
  "노드 수를 줄여라"  "객체 수가 문제다"        <- 접으면 노드 수가 단어 수로 눌린다

반대로 이런 말이 보이면 해당하지 않는다
  "부분 문자열"  "가운데 어디든"                <- 접두사가 아니라 다른 구조가 필요하다
  "단어가 아주 짧다"  "알파벳이 크다"           <- 갈림이 잦아 접을 구간이 없다
  "완전 일치만 묻는다"                          <- 경로 도중의 노드가 필요 없다
  "삽입은 미리 끝나고 조회만 아주 많다"         <- 조회 연산 수는 트라이 쪽이 적다
```

마지막 무리가 보이면 다른 구조로 갑니다. 접두사가 아니라 문자열 가운데의 조각을 물으면
[`suffixArray`](../suffixArray/suffixArray-guide.md) 쪽이고, 여러 단어를 한 번의 순회로 동시에 찾으면
[`ahoCorasick`](../ahoCorasick/ahoCorasick-guide.md) 쪽이에요.

#### 실제로 쓰이는 곳

- **Redis 의 `rax`.** 소스 파일 첫 줄이 이 구조를 이름 그대로 밝힙니다 —
  *"Rax -- A radix tree implementation."* 그리고 헤더가 접는 규칙을 한 문장으로 적어요 —
  *"Successive nodes having a single child are 'compressed' into the node itself as a string of
  characters."* 이 글의 「갈림 없는 구간 접기」와 같은 문장입니다. 쓰이는 자리는 스트림 자료형이고,
  `stream.h` 의 구조체가 `rax *rax;` 필드에 *"The radix tree holding the stream."* 라는 주석을 달고 있어요.
  ([`src/rax.c`](https://github.com/redis/redis/blob/unstable/src/rax.c),
  [`src/rax.h`](https://github.com/redis/redis/blob/unstable/src/rax.h),
  [`src/stream.h`](https://github.com/redis/redis/blob/unstable/src/stream.h), 조회 2026-08-31)

같은 구현이 **이 글이 라벨이라고 부른 것을 소스의 말로** 적어 둡니다. 셋이 각각 이 글의 어느 자리에
대응하는지가 그대로 보여요.

| Redis 소스의 문장 | 어디에 | 이 글에서 대응하는 자리 |
| --- | --- | --- |
| *"Rax -- A radix tree implementation."* | `rax.c` 첫 줄 | 이 글이 만드는 라딕스 트리 |
| *"Successive nodes having a single child are 'compressed' into the node itself as a string of characters."* | `rax.h` | 갈림 없는 구간을 라벨 하나로 접는 규칙 |
| *"The radix tree holding the stream."* | `stream.h` 의 `rax *rax;` 필드 | 담는 키가 스트림 항목의 id 다 |

- **리눅스 커널의 IPv4 경로 표 `net/ipv4/fib_trie.c`.** 주소를 비트마다 갈라 가장 긴 일치 접두사를 찾는
  자리이고, 파일 첫머리가 *"This work is based on the LPC-trie which is originally described in: An
  experimental study of compression methods for dynamic tries, Stefan Nilsson and Matti Tikkanen,
  Algorithmica, 33(1):19-33, 2002"* 라 적혀 있습니다. 그 논문 제목의 compression 이 이 글이 하는 일이에요.
  다만 커널 쪽은 경로 압축에 **층 압축**(level compression)을 더해, 갈림이 많은 구간을 한 노드가 여러
  비트로 받게 합니다.
  ([`net/ipv4/fib_trie.c`](https://github.com/torvalds/linux/blob/master/net/ipv4/fib_trie.c),
  조회 2026-08-31)

**웹 브라우저의 자동 완성이 이 구조를 쓴다는 것은 1 차 출처로 확인하지 못했습니다.** 확인한 것은 Redis 가
스트림 색인에 이 구조를 쓴다는 것과, 리눅스 커널의 경로 표가 여기에 층 압축을 더한 변형을 쓴다는 것
둘입니다.

#### 경쟁 설계와의 대조

같은 목표(문자열을 담고 접두사를 묻는 것)를 노리는 다른 절차가 바로 **트라이**입니다. 이 글이 파트 1 에서
출발점으로 삼은 구조예요. 접지 않는 대신 노드가 라벨 문자열을 들지 않습니다.

| 설계 | 한 칸 내려가는 일 | 노드가 드는 것 |
| --- | --- | --- |
| 라딕스 트리 | 라벨 하나를 맞추고 한 칸 내려간다 | 라벨 문자열 · 자식 맵 · 끝 표시 |
| 트라이 | 글자 하나를 읽고 한 칸 내려간다 | 자식 맵 · 끝 표시 |

같은 입력 · 같은 작업 목록에 두 설계를 걸고 **추가 칸**과 **자료 접근**을 셌습니다. 추가 칸은 입력 단어 목록
밖에 구조가 들고 있는 칸이에요. 담기를 다 끝낸 구조에서 라벨 글자 하나 · 끝 표시 하나 · 자식 맵 항목(글자 → 자식)
하나를 각각 한 칸으로 셉니다. 그래서 트라이는 `2V − 1` 칸, 라딕스 트리는 라벨 글자 합 + `2V − 1` 칸이에요. 자료
접근은 글자 한 자리를 읽어 자식 맵을 조회한 것 · 라벨과 글자 한 자리를 대조한 것 · 새 노드를 맵에 건 것 · 끝 표시를
읽거나 쓴 것을 각각 1 로 셉니다. 새 노드의 필드를 채우는 초기화 쓰기는 넣지 않았고, 노드를 가르는 일은 중간 노드를
부모 맵에 건 것 한 번으로 셉니다(「비용 계산」 절의 노드 생성과 같은 셈이에요). **트라이 편과 같은 잣대로 셌습니다.**
예전에는 맵 항목을 키 글자와 가리킴 두 칸으로 갈라 트라이가 `3V − 2` 칸이었고 노드 생성과 맵에 걸기를 따로 셌는데,
트라이 편에 맞추자 공유 96 글자의 추가 칸이 5,264 · 6,412 에서 4,222 · 4,275 로, 삽입이 104,222 · 105,274 에서
103,138 · 103,137 로 바뀌었어요. 노드가 많은 트라이 쪽이 더 줄어 트라이에 유리해졌고, 추가 칸이 뒤집히는 자리는
그대로이지만 삽입이 뒤집히는 자리는 96 과 97 사이에서 95 와 96 사이로 한 칸 앞당겨졌습니다. 사전은 길이 100 짜리 단어 1,000 개이고 길이 합이 과제 규모의 최댓값 100,000 입니다.
단어는 `"a" × share + base26(i) + "z" × (100 − share − 3)` 으로 만들었고(`i = 0 … 999`), `base26(i)` 는 `i` 를
소문자 세 글자로 적은 것이에요. `share` 만 바꾸면 길이 합을 고정한 채 공유의 정도만 움직입니다. 조회
1,000 개는 그 단어들의 앞 60 글자이고, 난수를 쓰지 않아 시드가 없습니다. **전개 입력을 그대로 쓰지 않은
이유**는 네 단어가 사전 하나뿐이라 움직일 값이 없기 때문이에요. 우열이 뒤집히는 자리를 대려면 공유의 정도를
바꿔 가며 재야 합니다.

| 측정 | 라딕스 트리 | 트라이 | 적은 쪽 |
| --- | --- | --- | --- |
| 공유 96 글자 · 추가 칸 | **4,222** | 4,275 | 라딕스 트리 |
| 공유 97 글자 · 추가 칸 | 3,223 | **2,277** | 트라이 — **여기서 순서가 뒤집힌다** |
| 공유 95 글자 · 삽입 자료 접근 | **102,139** | 104,136 | 라딕스 트리 |
| 공유 96 글자 · 삽입 자료 접근 | 103,138 | **103,137** | 트라이 — **한 자리 앞에서 뒤집힌다** |
| 공유 97 글자 · 조회 자료 접근 | 62,000 | **61,000** | 트라이 — 이 축은 안 갈린다 |

**뒤집히는 것은 공유가 아주 클 때입니다.** 공통 접두사가 길어지면 트라이의 노드 수가 먼저 줄어드는데, 그것이
라딕스 트리의 노드 수에 가까워지면 접어서 없앨 노드보다 라벨 문자열을 드는 값이 커져요. 공유 길이를 바꿔 가며
두 노드 수를 나란히 세면 그 자리가 값으로 나옵니다.

**삽입은 한 자리 앞에서 뒤집힙니다.** 트라이가 삽입에서 더 쓰는 것은 갈라진 뒤 남은 꼬리 글자마다 맵을 조회하고
새 노드를 거는 일이고, 라딕스 트리가 더 쓰는 것은 지나는 노드마다의 맵 조회와 어긋난 자리 한 번의 대조예요.
라딕스 트리는 꼬리를 잎 하나의 라벨로 한 번에 겁니다. 공유가 커져 꼬리가 짧아지면 앞의 것이 뒤의 것 아래로
내려가고, 그 자리를 전수로 찾으면 이렇게 나와요.

| 공통 접두사 길이 | 라딕스 트리 삽입 자료 접근 | 트라이 삽입 자료 접근 | 적은 쪽 |

공유 50 글자의 삽입 149,091 은 트라이 편 대조 표의 「삽입 1,000 개」와, 공유 0 글자의 추가 칸 196,083 은 트라이 편
추가 칸 표의 첫 줄과 같은 값이에요.

**이 절차가 내주는 것은 조회의 자료 접근입니다.** 공유 97 글자에서 62,000 대 61,000 이고, 이 축은 공유
길이를 전부 바꿔 재도 한 번도 안 갈려요.

공통 접두사 길이를 0 부터 97 까지 98 가지로 바꿔 쟀고, 라딕스 트리가 더 적었던 경우는 0 가지입니다.

<!--/proof-->

라딕스 트리는 노드마다 자식 맵 조회 한 번과 라벨 글자 대조를 **둘 다** 하는데, 트라이는 맵 조회 한 번이
글자 하나를 함께 처리하기 때문입니다. 그 대신 얻는 것이 둘이에요.

| 축 | 라딕스 트리 | 트라이 |
| --- | --- | --- |
| 노드 수 | 담긴 단어 수를 따라간다 — 상한 `2N` | 담긴 글자 수를 따라간다 — 상한 `S + 1` |
| 삽입의 자료 접근 | 공유 95 글자에서 102,139 | 같은 입력에서 104,136 |
| 조회의 자료 접근 | 공유 97 글자에서 62,000 | 같은 입력에서 61,000 |

단어가 길고 공유가 적당한 사전에서는 앞의 두 줄이 답이라 라딕스 트리를 씁니다. **공통 접두사가 96 글자 이상이면
삽입이, 97 글자 이상이면 추가 칸까지 트라이 쪽이 적으니, 공유가 그만큼 크거나 조회만 아주 많은 작업 목록**이면
트라이 쪽으로 다시 판단해야 해요.

### 수식 정의와 유도

단어 집합 `W` 에 대해 집합 셋을 차례로 정의합니다. 기호표의 `k` 는 두 문자열을 실제로 대조해서 나온 값이라,
여기서는 정의를 적으려고 쓰는 자리 번호를 `j` 로 따로 씁니다. `w[0..j)` 는 `w` 의 앞 `j` 글자이고 `ε` 는
빈 문자열이에요.

$$\operatorname{Pref}(W) = \{\, w[0..j) \;:\; w \in W,\ 0 \le j \le |w| \,\}$$

| 기호 | 뜻 | 범위 |
| --- | --- | --- |
| $W$ | 담은 단어들의 집합 | $\lvert W \rvert = N$ |
| $w[0..j)$ | $w$ 의 앞 $j$ 글자. $j = 0$ 이면 빈 문자열이다 | $0 \le j \le \lvert w \rvert$ |
| $\operatorname{Pref}(W)$ | $W$ 의 단어들이 내놓는 접두사를 전부 모은 집합 | 트라이의 노드 집합이 곧 이 집합이다 |

그중에서 **다음 글자가 둘 이상으로 갈리는 것**만 골라 낸 것이 둘째 집합입니다. `p` 는 `Pref(W)` 의 원소
하나이고, `pc` 는 그 뒤에 글자 `c` 를 붙인 문자열이에요.

$$\operatorname{Branch}(W) = \{\, p \in \operatorname{Pref}(W) \;:\; \#\{\, c : pc \in \operatorname{Pref}(W) \,\} \ge 2 \,\}$$

빈 문자열 · 담은 단어 · 갈림 셋을 합친 것이 라딕스 트리의 노드 집합이고, 그 크기가 `V` 입니다.

$$\operatorname{Node}(W) = \{\varepsilon\} \cup W \cup \operatorname{Branch}(W) \qquad V = |\operatorname{Node}(W)|$$

| 기호 | 뜻 | 라딕스 트리에서 |
| --- | --- | --- |
| $\#\{\, c : pc \in \operatorname{Pref}(W) \,\}$ | $p$ 다음에 올 수 있는 글자의 가짓수 | 노드 $p$ 의 자식 수 |
| $\operatorname{Branch}(W)$ | 그 가짓수가 2 이상인 접두사 | 갈림 |
| $\{\varepsilon\}$ | 빈 문자열 하나 | 뿌리 |
| $\operatorname{Node}(W)$ | 뿌리 · 단어 끝 · 갈림을 합친 집합 | 노드 집합. $\operatorname{Pref}(W)$ 의 부분집합이다 |

**정의를 값에 넣어 검산해 봅시다.** 전개 입력을 넣고 원소를 사전순으로 늘어놓았습니다.

<!--proof:mathNodeSet-->

| 원소 | 빈 문자열 | 담은 단어 | 갈림 |
| --- | --- | --- | --- |
| 빈 문자열 | 그렇다 | - | - |
| `app` | - | 그렇다 | - |
| `appl` | - | 그렇다 | 그렇다 |
| `apple` | - | 그렇다 | - |
| `application` | - | 그렇다 | - |

Node(W) 의 크기는 5, 라딕스 트리의 노드 수는 5, Pref(W) 의 크기는 13 입니다. 라벨 글자 합은 12 이고 Pref(W) 의 크기에서 1 을 뺀 값도 12 입니다.

<!--/proof-->

원소 다섯이 노드 다섯과 하나씩 짝지어집니다. 그리고 라벨 글자 합이 `|Pref(W)| − 1` 과 같아요. 라벨 글자
하나가 트라이의 간선 하나에 정확히 대응하기 때문입니다. 대응을 하나씩 적었습니다.

<!--proof:mathLabelEdges-->

| 라벨 | 대응하는 트라이의 간선(출발 노드–글자) | 개수 |
| --- | --- | ---: |
| app | 뿌리–a · a–p · ap–p | 3 |
| l | app–l | 1 |
| e | appl–e | 1 |
| ication | appl–i · appli–c · applic–a · applica–t · applicat–i · applicati–o · applicatio–n | 7 |

대응하는 간선은 모두 12 개이고, 트라이의 간선 수(노드 13 개에서 뿌리를 뺀 수)도 12 입니다.

<!--/proof-->

**이제 상한을 유도합니다.** 정의에서 $|\operatorname{Node}(W)| \le 1 + N + |\operatorname{Branch}(W)|$
이므로 갈림의 개수만 세면 돼요. 갈림은 라딕스 트리에서 **자식이 둘 이상인 노드**이고, 잎은 자식이 없으니
갈림이 아니고 단어 끝이 아닐 수도 없어서 잎은 전부 담은 단어입니다. 그래서 잎의 개수가 `N` 을 넘지 않아요.

$$|\operatorname{Branch}(W)| \le (\text{잎의 개수}) - 1 \le N - 1$$

첫 부등호는 귀납으로 닫힙니다.

| 걸음 | 내용 | 식 |
| --- | --- | --- |
| 기저 | 잎이 하나뿐인 나무에는 자식이 둘 이상인 노드가 없다 | 갈림 0 = 잎 1 − 1 |
| 단계 | 자식이 둘 이상인 노드 하나는 그 아래로 서로 다른 잎을 적어도 둘 거느린다. 갈림 하나를 더하면 그 갈림의 새 자식 쪽에 잎이 적어도 하나 더 생긴다 | 갈림이 1 늘 때 잎도 1 이상 는다 |
| 결론 | 잎이 `N` 개 이하이면 | 갈림 ≤ `N − 1` |

두 식을 합치면 상한이 닫힙니다.

$$V \le 1 + N + (N - 1) = 2N$$

| 설계 | 노드 집합 | 상한 | 상한을 정하는 것 |
| --- | --- | --- | --- |
| 트라이 | $\operatorname{Pref}(W)$ 전부 | $S + 1$ | 담긴 글자 수 |
| 라딕스 트리 | $\operatorname{Node}(W)$ 뿐 | $2N$ | 담긴 단어 수 |

**여기가 본문의 값만으로는 안 나오는 자리예요.** 파트 1 은 단어 집합 다섯에서 노드 수를 셌을 뿐인데, 이 식은
**임의의 단어 집합**에 대해 노드 수가 길이 합 `S` 와 무관하게 단어 수 `N` 으로 눌린다고 말합니다. 정의를
그대로 옮긴 조각은 이렇습니다.

```ts
// 정의를 그대로 옮긴 조각. 집합을 실제로 만들어 크기를 센다.
const nodeSetSize = (words: string[]): number => {
  const pref = new Set(
    words.flatMap((w) => Array.from({ length: w.length + 1 }, (_, j) => w.slice(0, j))),
  );
  const nextChars = (p: string) =>
    new Set(words.filter((w) => w.length > p.length && w.startsWith(p)).map((w) => w[p.length]));
  const branch = [...pref].filter((p) => nextChars(p).size >= 2);
  return new Set(["", ...words, ...branch]).size;
};
```

이 조각은 접두사를 전부 만들어 담으므로 단어 하나마다 그 길이의 제곱에 비례하는 글자를 읽습니다. 라딕스
트리는 같은 값을 담는 동안 곁들여 얻어요. 두 상한에 과제 규모를 넣으면 이렇게 나옵니다.

<!--proof:mathBounds-->

| 단어 집합 | N | S | 라딕스 트리의 노드 | 상한 2N | 트라이의 노드 | 상한 S + 1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| {apple, application, app, appl} | 4 | 23 | 5 | 8 | 13 | 24 |
| 앞 97 글자가 같은 1,000 단어 | 1,000 | 100,000 | 1,043 | 2,000 | 1,139 | 100,001 |
| 앞 3 글자에서 갈리는 1,000 단어 | 1,000 | 100,000 | 1,042 | 2,000 | 98,042 | 100,001 |
| b · ab · aab … 를 446 개 | 446 | 99,681 | 891 | 892 | 892 | 99,682 |
| 길이 100,000 짜리 단어 하나 | 1 | 100,000 | 2 | 2 | 100,001 | 100,001 |

넷째 줄은 라딕스 트리의 노드가 상한 2N 보다 1 적고, 다섯째 줄은 트라이의 노드가 상한 S + 1 과 같습니다. 단어 1,000 개 · 길이 합 100,000 이면 두 상한은 2,000 과 100,001 이라 50.0 배 갈립니다.

<!--/proof-->

넷째 줄이 상한 `2N` 에 가장 가까운 입력입니다. 단어 하나마다 앞에 `a` 를 하나 더 붙여, 갈림과 단어 끝이
번갈아 나오게 만든 사전이에요. 길이 100,000 짜리 단어 하나는 두 식이 가장 멀리 갈리는 자리이고, 라딕스
트리는 그 단어를 노드 둘로 담습니다.

### 불변식 — 뿌리가 아닌 노드는 단어 끝이거나 자식이 둘 이상이다

파트 1 에서 코드가 동작하는 것을 열 걸음으로 봤습니다. 그건 입력 하나에서 맞았다는 뜻이지 언제나 맞는다는
뜻은 아니에요. 무엇이 **매 삽입 뒤에 참으로 남는지**를 문장으로 세우고 그것이 실제로 유지되는지 확인해
봅시다.

> `insert` 하나가 끝난 직후, 뿌리가 아닌 모든 노드는 **단어 끝 표시가 있거나 자식이 둘 이상**이고, 한
> 노드의 자식들이 든 라벨은 **서로 다른 글자로 시작**합니다.

| 문장 | 참인 것 | 기대는 자리 |
| --- | --- | --- |
| 앞 문장 | 지나가기만 하는 노드가 하나도 없다 | 노드 수 상한 `2N` |
| 뒤 문장 | 자식 라벨의 첫 글자가 서로 다르다 | 자식 맵의 키가 첫 글자 하나여도 되는 근거 |

**출발점부터 봅시다.** 아무것도 담지 않은 트리는 뿌리 하나입니다. 뿌리가 아닌 노드가 없으므로 앞 문장이
참이고, 자식이 하나도 없으므로 뒤 문장도 참이에요. 그다음 삽입 하나는 아래 다섯 갈래를 지납니다.

| 갈래 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 첫 글자가 같은 자식이 없다 | 남은 글자로 잎을 만든다 | 잎에 단어 끝 표시를 함께 남긴다 | 그 첫 글자를 쓰는 자식이 없었다 |
| 라벨을 다 썼다 | 그 자식으로 내려간다 | 노드를 만들지도 지우지도 않는다 | 자식 맵을 건드리지 않는다 |
| 라벨 도중에 갈린다 | 중간 노드를 세운다 | 다음 갈래가 자식 둘 또는 끝 표시를 준다 | 두 자식의 첫 글자가 `k` 의 정의상 다르다 |
| 새 단어가 가른 자리에서 끝난다 | 중간 노드에 끝 표시를 남긴다 | 자식 하나에 끝 표시가 붙는다 | 자식 맵을 건드리지 않는다 |
| 남은 글자가 다 없어졌다 | 서 있는 노드에 끝 표시를 남긴다 | 노드를 만들지 않는다 | 자식 맵을 건드리지 않는다 |

셋째 줄과 넷째 줄이 이 논증의 핵심입니다. 가른 직후 중간 노드의 자식은 옛 자식 하나뿐인데, 새 단어의 남은
글자를 보고 **잎을 하나 더 걸거나 끝 표시를 남겨요.** 전개의 T3 과 T4 가 그 두 갈래입니다.

<!--proof:invariant-split-->

| 걸음 | 새 단어에 남은 글자 | 중간 노드 | 자식의 라벨 | 자식 수 | 끝 표시 |
| --- | --- | --- | --- | ---: | --- |
| T3 | ication | appl | e · ication | 2 | 거짓 |
| T4 | 없음 | app | l | 1 | 참 |

T3 의 중간 노드는 자식이 둘이고, T4 의 중간 노드는 자식이 하나지만 끝 표시가 있어요. 둘 다 앞 문장을
만족합니다. 뒤 문장의 근거는 `k` 의 정의에 있습니다. 가른 뒤 옛 자식의 라벨은 **가르기 전 라벨의 `k` 번째
글자**(0 부터 셉니다)로 시작하고, 새 잎의 라벨은 **남은 글자의 `k` 번째 글자**로 시작하는데, `k` 가 앞에서부터
같은 최대 글자 수이므로 그 두 글자는 다를 수밖에 없어요. 같았다면 `k` 가 적어도 1 더 컸을 것입니다.

| 확인하는 것 | 근거 |
| --- | --- |
| 잎에 끝 표시가 빠지는 경우가 없다 | 잎을 만드는 두 자리 모두 다음 줄에서 끝 표시를 참으로 둔다 |
| 중간 노드가 아무것도 안 정하는 경우가 없다 | 가른 뒤 두 갈래가 자식 둘 또는 끝 표시를 준다 |
| 자식 맵의 키가 겹치는 경우가 없다 | 가를 때 두 첫 글자가 `k` 의 정의상 다르다 |
| 자식 맵의 키와 그 자식의 라벨 첫 글자가 어긋나는 경우가 없다 | 라벨을 줄인 뒤 줄어든 라벨의 첫 글자로 다시 건다 |

경계에 있는 입력도 정본으로 실행해 확인했습니다. 마지막 열이 앞 문장을 어기는 노드의 수예요.

<!--proof:invariant-edges-->

| 경우 | 담은 단어 | 조회 | 답 | 노드 수 | 끝 표시도 없고 자식도 둘 미만인 노드 |
| --- | --- | --- | --- | ---: | ---: |
| 빈 트리에 조회 | 없음 | search("app") | 거짓 | 1 | 0 |
| 담긴 단어보다 긴 조회 | ab | startsWith("abc") | 거짓 | 2 | 0 |
| 같은 단어를 두 번 | app · app | search("app") | 참 | 2 | 0 |
| 짧은 단어를 나중에 | apple · app | search("app") | 참 | 3 | 0 |
| 길이 1 짜리 단어 하나 | a | search("a") | 참 | 2 | 0 |
| 길이 100,000 짜리 단어 하나 | a × 100,000 | search(그 단어) | 참 | 2 | 0 |

같은 단어를 두 번 담아도 노드가 늘지 않고, 길이 100,000 짜리 단어 하나도 라벨 하나짜리 잎 하나로 담겨 노드가
둘입니다. 여섯 경우 모두 앞 문장을 어기는 노드가 없어요.

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 **가른 자리에서 새 단어가 끝날 때 중간 노드에 끝 표시를
남기는 한 줄**이에요. 「가른 자리에 이미 자식이 하나 있으니 표시까지 남길 것 있나」라는 생각으로 그 줄을
거짓 대입으로 바꿔 봅니다.

```ts
      const tail = rest.slice(k);
      if (tail === "") {
        mid.end = false;   // ← 끝 표시를 안 남긴다. 원래는 mid.end = true 다
      } else {
```

실행하면 이렇게 나옵니다.

<!--proof:mutantMidEnd-->

| 조회 | 정본이 낸 답 | 끝 표시를 안 남긴 답 | 판정 |
| --- | --- | --- | --- |
| `search("app")` | 참 | 거짓 | 틀리다 |
| `search("appl")` | 참 | 참 | 같다 |
| `search("apple")` | 참 | 참 | 같다 |
| `startsWith("app")` | 참 | 참 | 같다 |
| `startsWith("bat")` | 거짓 | 거짓 | 같다 |

다섯 조회 가운데 1 개가 틀립니다. 노드는 정본이 5 개, 끝 표시를 안 남긴 쪽이 5 개입니다. 끝 표시도 없고 자식도 둘 미만인 노드는 정본에 0 개, 끝 표시를 안 남긴 쪽에 1 개(app)입니다.

<!--/proof-->

앞 문장이 깨지면 노드 `app` 이 자식 하나에 끝 표시도 없는 상태로 남습니다. 그 노드는 다음 라벨이 `l` 로
시작한다는 것 말고는 아무것도 정하지 않는데, 노드 수는 그대로예요. **접을 것이 남아 있는데 안 접힌
상태**입니다. 노드가 남아 있으니 `startsWith("app")` 은 그대로 참이고, 틀리는 것은 담은 단어 `app` 을 묻는
`search` 하나예요.

| T10 | `startsWith("bat")` | 1 | 0 | 0 | 0 | 1 |
|  | 합계 | 16 | 31 | 4 | 5 | 56 |

담는 쪽은 글자 대조 12 (S = 23 이하) · 노드 생성 4 (V − 1 = 4) · 끝 표시 쓰기 4 (N = 4) 이고, 묻는 쪽은 글자 대조 19 · 맵 조회 11 · 끝 표시 읽기 1 입니다.

<!--/proof-->

T5 가 이 표의 요점입니다. `insert("appl")` 은 글자를 넷 대조하는데 노드는 하나도 안 만들어요. 라벨을 다 쓰며
내려가다 남은 글자가 없어진 걸음이기 때문입니다. T2 는 반대로 글자를 하나도 대조하지 않고 노드를 만들었어요.
T7 은 끝 표시를 읽지 않았습니다. `leftover === 0` 이 거짓이라 `&&` 가 뒤를 보지 않고 멈췄기 때문이에요.
**글자 대조는 글자 수를 따라가고 노드 생성은 노드 수를 따라가서**, 담는 쪽의 총식이 세 항으로 갈립니다.

| 쪽 | 식 | 항마다의 뜻 |
| --- | --- | --- |
| 담는 쪽 | 많아야 `S + (V − 1) + N` | 글자 대조 `S` 이하 · 노드 생성 `V − 1` · 끝 표시 쓰기 `N` |
| 묻는 쪽 | 읽은 글자 합 + 맵 조회 합 + `search` 횟수 | 조회 하나가 글자 많아야 `L` 개 · 맵 많아야 `L` 번 |
| 추가 칸 | 라벨 글자 합 + `2V − 1` | 라벨 글자 · 노드마다 끝 표시 하나 · 간선마다 맵 항목 하나 |

담는 쪽이 등식이 아니라 상한인 것은 T2 처럼 글자를 한 번도 대조하지 않는 삽입이 있기 때문이에요. 어느 항에도
담긴 단어의 개수를 곱하는 자리가 없습니다. `V` 는 `2N` 을 넘지 않으므로 담는 쪽 전체가 `S + 3N` 을 넘지 않고,
조회 `Q` 번의 비용은 목록 대조의 `Q · S` 에서 조회 길이의 합으로 바뀌어요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요. 조회
하나의 비용을 두 축으로 가르면 이렇습니다.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (첫 글자가 같은 자식이 없다) | `O(1)` | `Θ(1)` — 자식 맵을 한 번만 읽는다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(L)` | 정의되지 않는다 |
| **최악의 경우** (라벨을 끝까지 맞춰 간다) | `O(L)` | `Θ(L)` — 실제로 도달한다 |

가운데 줄의 타이트한 값이 정의되지 않는 것은 **입력 분포가 없기 때문**입니다. 조회 문자열이 어느 자리에서
어긋나는지는 담긴 단어들과 조회 문자열이 함께 정하는 것이라, 분포를 가정하지 않으면 기댓값을 쓸 수 없어요.
**삽입도 조회와 같은 세 줄입니다.** 빈 트리에 담으면 글자를 한 번도 대조하지 않아요. 전개의 T2 가 그
걸음입니다.

| 경계 | 뜻 | 이 구조에서 |
| --- | --- | --- |
| 상한 `O(L)` | 그보다 더 대조하지 않는다 | 삽입 · 조회 모두 |
| 타이트 `Θ(L)` | 실제로 그만큼 대조한다 | 최악의 경우에만 — 삽입도 조회도 도중에 끝날 수 있다 |

트라이는 삽입이 글자를 언제나 끝까지 읽어서 삽입의 세 줄이 모두 `Θ(L)` 이에요. 이 구조와 갈리는 자리입니다.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 구조의 특징이에요. 정렬도,
미리 만드는 표도, 좌표 압축도 하지 않습니다.

| 무엇 | 총식 | 항 |
| --- | --- | --- |
| 담기 | `O(S + N)` 시간 | 글자 대조 `S` 이하 · 노드 생성 `V − 1` · 끝 표시 쓰기 `N` |
| 묻기 | `O(조회 길이의 합)` 시간 | 조회 하나가 글자 많아야 `L` 개 |
| 메모리 | `Θ(라벨 글자 합 + V)` 칸 | 라벨 글자 합은 많아야 `S`, `V` 는 많아야 `2N` |

**보장의 종류를 밝혀 둡니다.** 글자 대조 횟수는 최악 보장이지만 **자식 맵 조회 하나의 비용은 기댓값**이에요.
자식을 `Map` 으로 담았고 그것이 해시 기반이라, 항목 하나를 찾는 데 드는 일이 해시가 글자를 흩는 정도에 달려
있습니다. 입력 분포에 대한 기댓값이 아니라 **구현이 쓰는 해시에 대한 기댓값**이에요.

| 보장하는 것 | 보장의 종류 | 기댓값의 대상 |
| --- | --- | --- |
| 대조하는 글자 수 | 최악 보장 `L` | - |
| 지나는 노드 수 | 최악 보장 `min(L, V)` | - |
| 삽입 하나가 만드는 노드 수 | 최악 보장 2 | - |
| 자식 하나를 찾는 일 | 기댓값 상수 | 해시 함수가 글자를 흩는 정도 |
| 자식을 `Σ` 칸 배열로 담으면 | 최악 보장 상수 | - |

셋째 줄이 트라이와 갈리는 자리입니다. 트라이는 삽입 하나가 노드를 많아야 `L` 개 만드는데, 여기서는 중간 노드
하나와 잎 하나로 **언제나 두 개 이하**예요. 마지막 줄의 배열 구현은 노드마다 `Σ` 칸을 잡으니, 노드 수의 상한이
그대로 칸 수의 상한에 곱해집니다.

<!--proof:perf-sigma-->

| 설계 | 노드 수 상한 | Σ = 26 칸 배열의 칸 상한 |
| --- | --- | ---: |
| 라딕스 트리 | 2N = 2,000 | 52,000 |
| 트라이 | S + 1 = 100,001 | 2,600,026 |

단어 1,000 개 · 길이 합 100,000 에서 두 상한은 50.0 배 갈립니다.

<!--/proof-->

#### 최악을 만드는 입력

축이 셋인데 **셋을 한꺼번에 최악으로 만드는 입력이 없습니다.** 축마다 따로 구성해서 값으로 확인해 봅시다.

<!--proof:worstShape-->

| 입력의 모양 | 단어 수 N | 길이 합 | 노드 수 | 그 조회의 맵 조회 | 그 조회의 글자 대조 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 길이 100,000 짜리 단어 하나 | 1 | 100,000 | 2 | 1 | 100,000 |
| a · aa · aaa … 를 446 개 | 446 | 99,681 | 447 | 446 | 446 |
| 길이 3 이하 단어 전부와 길이 4 단어 일부 | 29,751 | 99,998 | 29,752 | 4 | 4 |
| 앞 97 글자가 같은 1,000 단어 | 1,000 | 100,000 | 1,043 | 2 | 97 |

<!--/proof-->

첫 줄이 글자 대조를, 둘째 줄이 맵 조회를, 셋째 줄이 노드 수를 각각 최대로 만듭니다. 첫 줄은 노드가 둘이고
셋째 줄은 조회가 맵을 네 번 보고 끝나서, 한 입력이 셋을 다 최악으로 만들지 못해요. **「담긴 단어가 많으면
조회가 느려진다」는 이 구조에서 성립하지 않습니다.** 셋째 줄은 단어가 가장 많은데 조회가 가장 짧게 끝나고,
넷째 줄은 노드가 1,043 개인데 조회 하나가 맵을 두 번만 봐요. 다만 갈림이 늘면 경로 위 노드가 늘어 맵 조회가
함께 늘 수는 있습니다. 늘어도 문자열 길이 `L` 을 못 넘을 뿐이에요.

| 최악으로 만들 축 | 입력 | 까닭 |
| --- | --- | --- |
| 연산 하나의 글자 대조 | 과제 규모의 가장 긴 단어 하나 | 라벨 하나를 끝까지 맞춘다 |
| 연산 하나의 맵 조회 | `a` · `aa` · `aaa` … 처럼 서로의 접두사인 단어들 | 경로 위의 노드가 가장 많다 |
| 노드 수 | 짧은 단어를 예산까지 채운 사전 | 갈림이 글자마다 일어나 접을 구간이 없다 |

**맵 조회의 최악이 446 에서 멈추는 데는 이유가 있습니다.** 경로 위 노드가 `d` 개이면 그 노드들이 뜻하는
접두사의 길이는 서로 다르고 모두 1 이상이라 1, 2, … `d` 이상이에요. 각 접두사는 담은 단어이거나 갈림이라 그
아래에 길이가 그만큼 이상인 단어가 따로 있어야 하니, 길이 합이 적어도 `d(d+1)/2` 는 됩니다.

<!--proof:worst-depth-->

| 경로 위 노드 d | 필요한 길이 합 d(d+1)/2 | 과제 규모 |
| ---: | ---: | --- |
| 100 | 5,050 | 들어간다 |
| 446 | 99,681 | 들어간다 |
| 447 | 100,128 | 100,000 을 넘는다 |

그래서 과제 규모에서 경로 위 노드는 446 개를 못 넘고, `a` · `aa` · `aaa` … 사전이 그 값에 도달합니다.
「수식 정의와 유도」가 쓴 `b` · `ab` · `aab` … 와는 다른 사전이에요. 그쪽은 노드 수를 상한 `2N` 에 붙이는
사전입니다. **노드 수의 최악은 짧은 단어를 최대한 많이 담는 사전**이고, 그때는 갈림이 글자마다 일어나
노드 수가 트라이와 같아집니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 갈림도 단어 끝도 아닌 자리를 **노드로 두지 않고** 그 사이
글자들을 라벨 하나로 접었고, 그래서 노드 수가 담긴 글자 수 대신 담긴 단어 수를 따라가며, 문자열이 라벨
한가운데서 끝날 수 있게 되면서 `search` 가 **라벨에 남은 글자까지** 보게 됐습니다.

| 바뀐 것 | 트라이 | 라딕스 트리 |
| --- | --- | --- |
| 노드를 두는 자리 | 모든 접두사 | 뿌리 · 갈림 · 단어 끝 |
| 노드 수의 상한 | `S + 1` | `2N` |
| 조회가 끝나는 자리 | 언제나 노드 위 | 노드 위이거나 라벨 한가운데 |

먼저 답이 붙는 문제 하나입니다. 전개의 T4 는 라벨 `appl` 을 `app` 과 `l` 로 가른 걸음이었고, 가른 뒤 중간
노드의 자식 맵에 옛 자식을 걸 때 키로 `l` 을 썼어요. 그런데 그 옛 자식이 원래 걸려 있던 키는 `a` 였습니다.

<!--proof:selfcheck-t4-->

```text
T4  insert("app")  대조한 글자 3  라벨 appl 을 app 과 l 로 가른다
```

<!--/proof-->

키를 왜 다시 정해야 할까요?

<!--check:whyRekeyChild-->
**자식 맵의 키는 그 자식이 든 라벨의 첫 글자**여야 하는데, 가르면서 라벨이 `appl` 에서 `l` 로 줄었기
때문입니다. 옛 키 `a` 는 라벨 `appl` 의 첫 글자였고, 줄어든 라벨의 첫 글자는 `l` 이에요. 키를 그대로 두면
불변식의 뒤 문장이 기대는 규칙이 깨져서, 조회가 `l` 로 시작하는 남은 글자를 들고 왔을 때 그 자식을 못
찾습니다. 뿌리 쪽 키가 `a` 인 것과 헷갈리기 쉬워요. 그쪽은 중간 노드의 라벨 `app` 의 첫 글자라서 맞습니다.

| 옛 자식을 거는 키 | 키 → 라벨 | `l` 로 시작하는 남은 글자 |
| --- | --- | --- |
| 줄어든 라벨의 첫 글자 | `l` → `l` | 찾는다 |
| 옛 키를 그대로 | `a` → `l` | 못 찾는다 |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「불변식」, 「수식 정의와 유도」, 「경쟁 설계와의 대조」를
다시 보세요.

- 담긴 단어를 지우는 연산을 더한다면, 지운 뒤에 불변식의 앞 문장이 깨지는 자리가 어디일까요? 전개의 T5 를
  마친 상태에서 `appl` 만 지운다고 생각하고, 어느 노드를 없애거나 합쳐야 하는지 값으로 적어 보세요.
- 문자 집합이 소문자 영문이 아니라 바이트 256 개로 바뀌면 노드 수의 상한 `2N` 이 달라질까요? 달라지지
  않는다면 왜 그런지를 `Branch(W)` 의 정의로 설명해 보세요.
- 조회만 아주 많고 삽입이 거의 없는 작업 목록이라면 라딕스 트리와 트라이 중 어느 쪽을 골라야 할까요?

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### 압축 접두사 사전

풀 파일: [`radixTree.ts`](./radixTree.ts) · 테스트: [`radixTree.test.ts`](./radixTree.test.ts) · 실행: `bun test src/algorithms/string/radixTree/radixTree.test.ts`

#### 한 줄 요약

> `RadixTree`는 단어를 삽입하고, 정확한 단어 존재 여부와 특정 접두사로 시작하는 단어의 존재 여부를 각각 조회할 수 있는 자료구조다.

#### 스토리

자동 완성 서비스를 개발하는 유진은 수백만 개의 단어를 저장하고 실시간으로 접두사 검색을 처리해야 한다. 단어마다 글자 수만큼 노드를 만드는 방식은 저장 공간이 너무 크게 불어난다.

유진은 공통 접두사를 하나의 묶음으로 저장해 노드 수를 줄이면서도, 삽입과 검색 모두 단어 길이에 비례하는 시간을 유지하는 자료구조가 필요하다.

#### 함수 인터페이스

```ts
export class RadixTree {
  insert(word: string): void;
  search(word: string): boolean;
  startsWith(prefix: string): boolean;
}
```

- `insert(word)` — `word`를 자료구조에 삽입한다. 기존 엣지와 공통 접두사가 있으면 엣지를 분할한다. 반환값 없음.
- `search(word)` — `word`가 이전에 삽입된 적이 있으면 `true`, 없으면 `false`.
- `startsWith(prefix)` — `prefix`로 시작하는 단어가 하나라도 삽입되어 있으면 `true`, 없으면 `false`.

#### 제약 조건

- 단어/접두사 길이 $L \leq 10^5$
- 삽입된 모든 단어의 길이 합 $\leq 10^5$
- 각 연산의 시간 복잡도: $O(L)$
- 문자 집합: 소문자 영문 알파벳 (`a`–`z`)
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

삽입된 적 없는 단어는 `search`에서 `false`를 반환한다. `startsWith`는 삽입된 단어 중 `prefix`로 시작하는 것이 하나라도 있으면 `true`다.

동일한 단어를 중복 삽입해도 오류 없이 동작해야 한다. 같은 단어를 여러 번 `insert`한 뒤 `search`하면 여전히 `true`를 반환한다.

빈 자료구조에서 `search`나 `startsWith`를 호출하면 항상 `false`를 반환한다.

`search`와 `startsWith`의 차이: `insert("apple")` 후 `search("app")`은 `false`이지만 `startsWith("app")`은 `true`다.

#### 예시

```ts
const rt = new RadixTree();

rt.insert("apple");
rt.search("apple");     // true — 삽입된 단어
```
