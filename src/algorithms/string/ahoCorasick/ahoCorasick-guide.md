# ahoCorasick — 패턴 여럿을 상태 하나로 합치면 텍스트를 되돌려 읽지 않아도 되는 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 패턴마다 텍스트를 따로
대조하는 방법에서 패턴 전부를 한 기계로 합치는 방법까지 가는 경로를 따라갑니다. 그 경로의
끝에서 기계를 만드는 코드와 그 기계에 텍스트를 거는 코드를 차례로 세웁니다.

### 전체 컨셉

텍스트 하나와 패턴 여럿을 받아 **각 패턴이 텍스트의 어느 자리에서 시작하는지 전부** 돌려주는
문제예요. 겹쳐 등장하는 자리도 빠뜨리지 않고, 짧은 패턴이 긴 패턴 안에 숨어 있어도 찾아야
합니다.

```text
텍스트   u s h e r s
자리     0 1 2 3 4 5

패턴 0   he     자리 2 에서 시작한다
패턴 1   she    자리 1 에서 시작한다
패턴 2   hers   자리 2 에서 시작한다
└ 세 매칭이 겹쳐 있다. she 안에 he 가 들어 있고, he 와 hers 는 같은 자리에서 시작한다
```

가장 먼저 떠오르는 방법은 패턴을 하나씩 꺼내 텍스트를 처음부터 대조하는 것입니다. 그런데
제약이 텍스트 길이와 패턴 길이의 합을 각각 100,000 까지 허용해요. 패턴마다 텍스트를 새로
읽으면 그 두 수가 곱해집니다.

```text
패턴마다 텍스트를 따로 대조하면
  패턴 하나마다 텍스트의 모든 시작 자리를 본다   자리마다 패턴 길이만큼 글자를 견준다
  텍스트 100,000 · 패턴 길이 합 100,000 이면     견주기가 100 억 번까지 간다
└ 1 초 안에 끝내야 하는 문제에서 100 억은 자리가 두 개 남는다
```

여기서 바꾸는 것은 **텍스트를 읽는 횟수**입니다. 텍스트를 한 글자씩 딱 한 번만 읽고, 그
글자를 읽은 시점에 「지금까지 읽은 것의 끝부분이 어느 패턴의 어디까지 맞았는가」를 **수 하나**로
들고 갑니다. 그 수를 **상태**라고 부를게요.

```text
he · she · hers 를 한 트리에 담으면
                      (뿌리)
                     /      \
                  h /        \ s
                   h          s
                e /            \ h
                he*             sh
              r /                 \ e
              her                 she*
            s /
            hers*
└ 뿌리에서 어떤 상태까지의 글자를 이으면 그 상태의 이름이 된다. 별표는 거기서 패턴이 끝난다는 뜻이다
  he 와 hers 가 앞 두 글자를 함께 쓰므로 상태가 8 개다 — 패턴 길이의 합 9 보다 적다
```

유지하는 값이 상태 하나뿐이라는 것이 요점이에요. 글자를 하나 읽을 때마다 상태를 한 번 옮기면, 그 상태
이름이 곧 **지금까지 읽은 텍스트의 끝에서 잘라 낸 조각 중 어떤 패턴의 앞부분이기도 한 가장 긴
것**입니다. 그 조각을 여기서는 **접미사**(끝에서 잘라 낸 조각)와 **접두사**(앞에서 잘라 낸
조각)라는 말로 적을게요.

| 읽은 것 | 끝에서 잘라 낸 조각 중 어떤 패턴의 앞부분이기도 한 가장 긴 것 | 상태 |
| --- | --- | --- |
| `u` | 없다 | 뿌리 |
| `us` | `s` | `s` |
| `ush` | `sh` | `sh` |
| `ushe` | `she` | `she` |
| `usher` | `her` | `her` |
| `ushers` | `hers` | `hers` |

문제는 **어긋났을 때**입니다. `ushe` 까지 읽고 상태 `she` 에 있는데 다음 글자가 `r` 이면,
`she` 에는 `r` 로 가는 자식이 없어요. 그렇다고 텍스트를 되돌려 읽으면 다시 100 억이 됩니다.

```text
상태 she 에서 글자 r 을 읽으면
  she 에 r 로 가는 자식이 없다        하지만 she 의 끝부분 he 는 패턴 hers 의 앞부분이다
  그러니 he 로 옮겨 놓고 r 을 읽으면  her 로 갈 수 있다
  글자 r 은 자리 4 다. 읽고 나면   다음은 자리 5 이고 되돌려 읽은 글자가 0 개다
└ 이 옮김을 「실패 링크」라고 부른다. she 의 실패 링크가 he 다
```

실패 링크는 **상태 이름의 끝에서 잘라 낸 조각 중 자기 자신을 뺀 것으로서 어떤 패턴의 앞부분인
가장 긴 것**을 가리킵니다. 이것을 미리 계산해 두면, 어긋난 자리마다 실패 링크를 따라가서 갈 수
있는 곳을 찾을 수 있어요. 한 걸음 더 나아가 **그 결과를 상태마다 26 칸짜리 표에 미리 적어
두면** 글자 하나에 표를 한 번 읽는 것으로 끝납니다.

```text
글자 하나를 읽을 때 하는 일
  표를 만들기 전   자식이 없으면 실패 링크를 따라간다        한 글자에 여러 번 옮길 수 있다
  표를 만든 뒤     표에서 그 글자 칸을 읽고 거기로 옮긴다    한 글자에 정확히 한 번이다
└ 표는 상태마다 26 칸이고, 자식이 없는 칸에는 실패 링크가 가리키는 상태의 같은 칸을 옮겨 적는다
```

마지막으로 확인할 것이 하나 남아요. 상태 `she` 에 도착했을 때 끝나는 패턴은 `she` 만이 아닙니다.
`she` 의 끝부분인 `he` 도 패턴이라 **같은 자리에서 함께 끝나요.** 그래서 상태마다 「내 끝부분
중 패턴이 끝나는 가장 가까운 상태」를 하나 더 유지하며, 매칭을 거둘 때 그 사슬을 따라갑니다.

```text
텍스트 자리 3 의 글자 e 를 읽고 상태 she 에 도착하면
  she 에서 끝나는 패턴   she (1 번)   시작 자리는 3 − 3 + 1 = 1
  she 의 끝부분 he       he  (0 번)   시작 자리는 3 − 2 + 1 = 2
└ 한 걸음이 매칭을 둘 낸다. 이 사슬을 「출력 링크」라고 부른다
```

이렇게 하면 텍스트를 읽는 일이 **패턴이 몇 개든 글자 수만큼**입니다. 표를 만드는 일은 패턴
길이의 합과 문자 집합 크기에 비례하고, 매칭을 거두는 일은 찾은 매칭의 개수에 비례해요.
결과값으로 적으면 만들기가 `O(26 · L)`, 읽기가 `O(n)`, 거두기가 `O(z)` 이고, 여기서 `L` 은
패턴 길이의 합, `n` 은 텍스트 길이, `z` 는 매칭 개수입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **접두사와 접미사가 무엇인지.** 앞에서 잘라 낸 조각이 접두사이고 끝에서 잘라 낸 조각이
  접미사예요. `hers` 의 접두사는 빈 문자열 · `h` · `he` · `her` · `hers` 이고, 접미사는 빈
  문자열 · `s` · `rs` · `ers` · `hers` 입니다.
- **글자마다 갈래를 하나 만드는 트리.** 여러 문자열의 같은 앞부분을 한 경로에 담는 구조이고,
  [`trie`](../trie/trie-problem.md) 가 그것만 따로 다룹니다. 이 글은 그 위에 링크 두 종류를
  더합니다.
- **패턴 하나를 찾을 때 이미 맞은 부분을 다시 쓰는 방법.** 텍스트 자리를 되돌리지 않고 맞은
  길이만 줄이는 것이고, [`findAllOccurrences`](../findAllOccurrences/findAllOccurrences-problem.md)
  가 그것을 다룹니다. 이 글의 실패 링크가 그 생각을 패턴 여럿으로 넓힌 것이에요.
- **큐로 하는 너비 우선 순회.** 깊이가 얕은 것부터 차례로 꺼내는 순회입니다. 실패 링크를 어떤
  순서로 채워야 하는지가 여기에 달려 있어요.

```text
  패턴 하나를 텍스트에서 찾는다                 <- 다른 글이 다루는 것
  여러 문자열의 같은 앞부분을 한 경로에 담는다   <- 또 다른 글이 다루는 것
  패턴 여럿을 텍스트 한 번의 순회로 함께 찾는다  <- 이 글이 다루는 것
```

### 아이디어 상세 — 실패 링크를 떠올리는 과정

무엇을 받아 무엇을 돌려주는 함수인지부터 못 박고 갑시다.

```ts
function ahoCorasick(
  text: string,
  patterns: string[],
): Array<{ patternIndex: number; position: number }>;
```

- 입력: 소문자 영문(`a`–`z`)으로 된 텍스트 하나와 패턴 배열 하나. 패턴은 0 번부터 번호가 붙습니다.
- 출력: `{ 패턴 번호, 시작 자리 }` 의 배열. 겹쳐 등장하는 자리도 전부 담고, `position` 오름차순 ·
  같으면 `patternIndex` 오름차순으로 정렬돼 있어야 해요.
- 제약: 텍스트 길이 `1 ≤ n ≤ 100,000`, 패턴 길이의 합 `L ≤ 100,000`, 시간 1 초, 메모리 256 MB.

본문이 끝까지 쓰는 기호는 여섯이에요. 뜻을 여기서 못 박고 뒤에서 바꾸지 않습니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `n` | 텍스트의 길이 | `1 ≤ n ≤ 100,000` |
| `k` | 패턴의 개수 | `1 ≤ k` |
| `L` | 패턴 길이의 합 | `L ≤ 100,000` |
| `S` | 만들어지는 상태의 개수. 뿌리를 포함합니다 | `1 ≤ S ≤ L + 1` |
| `Σ` | 문자 집합의 크기. 전이표의 한 줄이 이만큼입니다 | 소문자 영문이라 26 |
| `z` | 매칭의 개수. 반환 배열의 길이입니다 | 제약이 따로 정하지 않습니다 |

가장 먼저 떠오르는 방법으로 시작합시다. 패턴을 하나씩 꺼내 텍스트의 **모든 시작 자리**에서
글자를 대조하는 것이에요.

```ts
function brute(text: string, patterns: string[]) {
  const found: { patternIndex: number; position: number }[] = [];
  for (const [index, p] of patterns.entries()) {
    for (let j = 0; j + p.length <= text.length; j++) {
      if (text.slice(j, j + p.length) === p) found.push({ patternIndex: index, position: j });
    }
  }
  return found;                       // 시작 자리마다 패턴 길이만큼 글자를 견준다
}
```

제약 최댓값의 50 분의 1 쯤 되는 입력에 두 방식을 실행하면 이렇게 나옵니다. 텍스트는 `a` 를 2,000
번 이어 붙인 것이고, 패턴은 앞 99 글자가 `a` 이고 마지막 글자만 다른 100 글자짜리 20 개예요.

<!--proof:simpleCost-->

```text
텍스트 2,000 글자 · 패턴 20 개 · 길이 합 2,000  글자 견주기  기본 연산   매칭
패턴마다 모든 시작 자리에서 대조한다              3,802,000  7,604,000  1,901
패턴을 한 기계로 합쳐 텍스트를 한 번만 읽는다             0     19,711  1,901

두 방식의 매칭이 같은가: 같다 (1,901 개)
견주기의 상한 = 텍스트 길이 × 패턴 길이 합 = 2,000 × 2,000 = 4,000,000
제약 최댓값에 같은 식을 넣으면 100,000 × 100,000 = 10,000,000,000
└ 실측 견주기가 상한 아래에 있다. 합친 기계 쪽은 글자를 견주는 자리가 없다 — 표를 조회한다
```

견주기가 380 만 번이고, 그 값이 「텍스트 길이 × 패턴 길이 합」이라는 상한 400 만 아래에
있습니다. 제약이 정한 최댓값을 같은 식에 넣으면 100 억이에요. 그러면 이 380 만 번 안에서
무엇이 되풀이되는지 봅시다.

```text
패턴 20 개를 시작 자리 하나에서 각각 대조하면
  0 번 패턴 (a 100 개)  100 글자가 다 맞는다                     100 글자
  1 번 패턴 (a 99 개 b) a 를 99 개 맞히고 100 번째에서 어긋난다  100 글자
  2 번 패턴 (a 99 개 c) a 를 99 개 맞히고 100 번째에서 어긋난다  100 글자
└ 같은 99 글자를 스무 번 읽었다. 패턴들이 그 99 글자를 함께 쓰는데 그것을 쓰지 않고 있다
  시작 자리를 하나 옮기면 그 스무 번을 처음부터 다시 한다
```

되풀이가 두 층입니다. 하나는 **패턴들이 앞부분을 함께 쓰는 것**이고 다른 하나는 **자리를 옮길
때마다 읽은 것을 버리는 것**이에요. 앞의 것은 패턴들을 한 트리에 담으면 사라지고, 뒤의 것은
읽은 결과를 상태 하나로 들고 가면 사라집니다.

```text
두 가지 되풀이
  패턴들이 앞부분을 함께 쓴다     -> 패턴 전부를 한 트리에 담아 그 앞부분을 한 경로로 만든다
  자리를 옮기면 읽은 것을 버린다  -> 어디까지 맞았는지를 상태 하나로 들고 다음 글자를 받는다
└ 앞의 것은 저장을, 뒤의 것은 읽기를 줄인다
```

그러면 같은 입력을 두 방식으로 처리해 **텍스트 글자를 몇 번 읽는지** 나란히 세어 봅시다.
전개에서 끝까지 쓸 작은 입력을 여기서 잡을게요 — 텍스트 `ushers` 와 패턴 `he` · `she` · `hers`
입니다.

<!--proof:readOnceVersusEach-->

```text
텍스트 "ushers" 를 패턴마다 따로 대조하면  텍스트 글자 읽기  찾은 것
0 번 패턴 he 하나로                                       6  0@2
1 번 패턴 she 하나로                                      6  1@1
2 번 패턴 hers 하나로                                     6  2@2
합계                                                     18  1@1 0@2 2@2

같은 텍스트를 한 기계로 합쳐 읽으면  텍스트 글자 읽기  찾은 것
패턴 3 개를 한 번에                                 6  1@1 0@2 2@2

텍스트를 길게 하면  패턴마다 따로  텍스트 길이의 몇 배  한 기계로 합치기  텍스트 길이의 몇 배
                 6             18                 3.00                 6                 1.00
                60            243                 4.05                60                 1.00
               600          2,493                 4.16               600                 1.00
             6,000         24,993                 4.17             6,000                 1.00

└ 답은 두 방식이 같다. 오른쪽은 언제나 텍스트 길이 그대로이고, 왼쪽은 그 네 배를 넘는다
  왼쪽의 그 배수를 정하는 것이 패턴의 개수와 모양이다 — 여기서는 패턴 3 개다
```

오른쪽 방식이 읽는 글자가 **텍스트 길이 그 자체**로 고정됩니다. 여기서 관찰할 것은 그 하나예요 —
패턴이 몇 개든 텍스트를 읽는 횟수가 달라지지 않습니다.

| 방식 | 텍스트를 읽는 횟수 | 무엇을 따라가는가 |
| --- | --- | --- |
| 패턴마다 따로 대조 | 패턴 개수만큼 | 패턴의 개수와 길이를 따라간다 |
| 한 기계로 합치기 | 한 번 | 텍스트의 길이만 따라간다 |

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 시험합시다. 「패턴들을 트리에 담아 두고,
텍스트의 **각 시작 자리마다** 트리를 따라 내려가면 되지 않나」가 그것이에요.

```text
텍스트 ushers 의 시작 자리마다 트리를 따라 내려가면
  자리 0 에서 u   뿌리에 u 가 없다               1 글자를 읽고 그만둔다
  자리 1 에서 s   s -> sh -> she 까지 내려간다   3 글자를 읽는다
  자리 2 에서 h   h -> he -> her -> hers        4 글자를 읽는다
  자리 3 에서 e   뿌리에 e 가 없다               1 글자
  자리 4 에서 r   뿌리에 r 이 없다               1 글자
  자리 5 에서 s   s 까지 내려간다                1 글자
└ 자리 1 과 자리 2 가 같은 글자들을 다시 읽는다. 시작 자리마다 가장 긴 패턴의 길이만큼 읽을 수 있어
  텍스트 100,000 · 가장 긴 패턴 100,000 이면 다시 100 억이다
```

시작 자리마다 뿌리에서 새로 내려가는 것이 문제입니다. 자리 1 에서 `she` 까지 갔으면 그 안에
자리 2 에서 볼 `he` 가 이미 들어 있는데, 뿌리로 되돌아가면서 그 사실을 버려요. **버리지 않고
이어 쓰려면 「지금 상태의 끝부분이면서 어떤 패턴의 앞부분인 것」으로 옮겨야 합니다.** 그것이
실패 링크의 정의예요.

```text
실패 링크의 정의
  자기 자신을 뺀 접미사를 「진 접미사」라고 적는다   hers 의 진 접미사는 ers rs s 와 빈 문자열
  상태 v 의 이름을 name(v) 라 하면
  실패 링크가 가리키는 상태의 이름은
    name(v) 의 진 접미사 중              자기 자신은 빼고
    어떤 패턴의 접두사이기도 한 것 중    가장 긴 것
  그런 것이 없으면 빈 문자열, 곧 뿌리다
└ 「끝부분」과 「앞부분」이 여기서 만난다. 지금까지 읽은 것의 끝을 버리지 않는 유일한 자리다
```

정의를 여덟 상태에 그대로 적용해 봅시다. 왼쪽은 정의대로 손으로 고른 것이고 오른쪽은 코드가
만든 표예요.

<!--proof:failLinkTable-->

```text
상태  경로 문자열  깊이  정의가 말하는 가장 긴 진 접미사  실패 링크  출력 링크  여기서 끝나는 패턴
   0  (뿌리)          0  (뿌리)                           (뿌리)     -          -
   1  h               1  (뿌리)                           (뿌리)     -          -
   2  he              2  (뿌리)                           (뿌리)     -          0 번
   3  s               1  (뿌리)                           (뿌리)     -          -
   4  sh              2  h                                h          -          -
   5  she             3  he                               he         he         1 번
   6  her             3  (뿌리)                           (뿌리)     -          -
   7  hers            4  s                                s          -          2 번

└ 넷째 칸은 정의를 손으로 적용한 것이고 다섯째 칸은 만들어진 표다. 여덟 줄이 다 같다
  she 의 출력 링크만 he 이고 나머지는 없다 — 다른 상태의 진 접미사 중에는 패턴이 없다
```

정의가 두 가지를 함께 정합니다. **실패 링크**는 어긋났을 때 갈 자리를 정하고, **출력 링크**는
한 자리에서 함께 끝나는 패턴들을 정해요. 둘 다 「자기 이름의 진짜 끝부분」을 보는 것이고, 다른
것은 무엇을 찾느냐입니다.

| 링크 | 무엇을 찾는가 | 언제 쓰는가 |
| --- | --- | --- |
| 실패 링크 | 어떤 패턴의 앞부분이기도 한 가장 긴 끝부분 | 글자를 읽었는데 갈 자식이 없을 때 |
| 출력 링크 | 패턴이 끝나는 가장 가까운 끝부분 | 매칭을 거둘 때 |

이 정의가 상태 변수의 이동 범위를 정합니다. 상태는 글자를 하나 읽을 때마다 **깊이가 많아야 1
늘어나고**, 실패 링크를 한 번 따라가면 **적어도 1 줄어들어요.** 그래서 실패 링크를 그때그때
따라가는 방식으로 적어도, 텍스트 전체에서 실패 링크를 따라간 횟수의 합은 `n` 을 넘지 않습니다.

```text
상태의 깊이가 어떻게 움직이는가
  글자를 읽고 자식으로 내려간다   깊이가 정확히 1 늘어난다      n 번 일어난다
  실패 링크를 한 번 따라간다      깊이가 적어도 1 줄어든다      늘어난 만큼만 줄일 수 있다
└ 그래서 텍스트 전체에서 실패 링크를 따라간 횟수의 합은 n 을 넘지 않는다
  다만 「한 글자에 몇 번인가」는 그 상태의 깊이까지 갈 수 있다
```

여기서 고를 것이 하나 남습니다. 실패 링크를 **실행 중에 따라갈 것인가**, 아니면 그 결과를
**상태마다 26 칸짜리 표에 미리 적어 둘 것인가**예요. 미리 적어 두는 깊이를 0 부터 끝까지 여덟
가지로 바꿔 가며 실제로 실행해 봅시다. 전개에서 쓸 패턴 셋은 상태의 깊이가 4 뿐이라 이 축을
네 칸밖에 못 움직여요. 그래서 깊이가 64 까지 가는 패턴 하나를 여기서만 따로 잡습니다.

<!--proof:expandDepth-->

```text
펼친 깊이  저장 칸  텍스트 전체의 표 조회  한 글자에 든 최대 조회
        0      284                    516                      65
        1      309                    512                      64
        2      334                    508                      63
        4      384                    500                      61
        8      484                    484                      57
       16      684                    452                      49
       32    1,084                    388                      33
       64    1,885                    260                       1

패턴은 a 를 64 번 이어 붙인 하나이고 텍스트는 (a×64 다음 b) 를 4 번 이어 붙인 260 글자다
└ 깊이를 깊게 펼칠수록 저장 칸이 늘고 조회가 준다. 전부 펼치면 한 글자에 정확히 한 번이다
  제약 최댓값에서 전부 펼치면 26 × 100,001 + 3 × 100,001 = 2,900,029 칸이다
```

값이 한쪽으로 곧게 갑니다 — 깊게 펼칠수록 저장 칸이 늘고 조회가 줄어요. 중간 어딘가가 가장
적은 모양이 아니라 **두 축을 맞바꾸는** 모양이고, 그러면 고르는 기준은 제약입니다.

| 무엇을 정하는가 | 전혀 안 펼치면 | 전부 펼치면 |
| --- | --- | --- |
| 한 글자에 든 최대 조회 | 그 상태의 깊이까지 (여기서는 65) | 정확히 1 |
| 텍스트 전체의 조회 | 516 | 260 |
| 저장 칸 | 284 | 1,885 |

제약이 정한 최댓값을 넣으면 전부 펼쳤을 때 `26 × 100,001 + 3 × 100,001 = 2,900,029` 칸입니다.
4 바이트짜리 정수로 담으면 12 MB 이 안 되고, 메모리 제한 256 MB 안에 넉넉히 들어와요. 그래서
**전부 펼칩니다** — 칸을 내주고 「한 글자에 정확히 한 번」이라는 최악 보장을 얻습니다.

```text
고른 것과 그 대가
  얻는 것   글자 하나에 표 조회 한 번          되돌아가는 반복문이 코드에서 사라진다
  내주는 것 상태마다 26 칸                     제약 최댓값에서 290 만 칸
└ 반대로 골랐다면 칸은 상태 수에 비례하지만 한 글자가 최대 깊이만큼 걸릴 수 있다
```

### 수행으로 알아보는 알고리즘 — 텍스트 여섯 글자로 매칭 셋을 찾는다

개념을 세웠으니 이제 **실제로 동작하는 코드**를 만듭니다. 텍스트와 패턴 셋을 하나 잡아 끝까지
가되, 조각을 하나 붙일 때마다 그 조각만 실행해 나온 값을 확인하고 넘어갈게요.

```ts
ahoCorasick("ushers", ["he", "she", "hers"]);
```

왜 하필 이 텍스트와 이 패턴 셋일까요? 갈래가 전부 실행되기 때문이에요 — 뿌리에서 아무 데도
못 가는 글자(`u`), 자식을 그대로 따라가는 글자(`s` · `h` · `e`), 자식이 없어 물려받은 칸으로
옮기는 글자(`r`), 그리고 **긴 패턴 안에 짧은 패턴이 끝부분으로 숨어 있는 자리**(`she` 안의
`he`)가 모두 나옵니다.

```text
절차 전체를 한 장으로 — 라벨 여덟이 어디에 붙는가
  T1       패턴 셋을 한 트리에 담는다
             글자마다 자식이 없을 때만 상태를 만든다   ① 없을 때만 만든다
             패턴이 끝난 상태에 번호를 적는다          ② 패턴 끝 표시
  T2       실패 링크와 전이표를 얕은 상태부터 채운다
             뿌리에 없는 글자는 뿌리로                 ③ 뿌리의 빈 칸
             출력 링크는 실패 링크에서 물려받는다      ④ 출력 링크
             자식 없는 칸은 실패 링크에서 물려받는다   ⑤ 전이표의 빈 칸
  T3~T8    텍스트를 한 글자씩 읽는다
             표를 한 번 조회해 상태를 옮긴다           ⑥ 글자 하나에 조회 한 번
             출력 링크를 따라가며 전부 거둔다          ⑦ 겹쳐 끝나는 패턴
  T9       시작 자리 순서로 맞춰 돌려준다              ⑧ 반환 규약의 순서
```

#### 1. 패턴 셋을 한 트리에 담는다

첫 조각은 트리입니다. 상태를 번호로 두고, 전이표 `next` 한 벌에 「상태 번호 × 26 + 글자 번호」로
접근해요. 아직 채우지 않은 칸은 `-1` 입니다.

```ts
for (let i = 0; i < patterns.length; i++) {
  const pattern = patterns[i] as string;
  if (pattern.length === 0) continue;
  let s = 0;
  for (const ch of pattern) {
    const c = codeOf(ch);
    if (next[s * SIGMA + c] === -1) {   // ① 그 글자로 가는 자식이 없을 때만 만든다
      next[s * SIGMA + c] = size;
      depth[size] = (depth[s] as number) + 1;
      size += 1;
    }
    s = next[s * SIGMA + c] as number;
  }
  (endOf[s] as number[]).push(i);       // ② 패턴이 끝난 상태에 번호를 적는다
}
```

`①` 이 앞부분을 함께 쓰게 하는 자리예요. `he` 를 담은 뒤 `hers` 를 담으면 앞 두 글자는 이미 있는
경로라 그대로 이어 쓰고 뒤 두 글자만 새로 만듭니다. 세 패턴을 담은 뒤의 상태는 이렇게 나와요.

<!--proof:trieShape-->

```text
상태  경로 문자열  자식             여기서 끝나는 패턴
   0  (뿌리)       h -> h · s -> s  -
   1  h            e -> he          -
   2  he           r -> her         0 번
   3  s            h -> sh          -
   4  sh           e -> she         -
   5  she          -                1 번
   6  her          s -> hers        -
   7  hers         -                2 번

└ 패턴 길이의 합 9 에서 he 와 hers 가 앞 두 글자를 함께 쓰므로 상태가 8 개다
```

`②` 가 만드는 것이 「여기서 끝나는 패턴」 칸입니다. 상태가 있다는 것과 그 상태에서 패턴이
끝난다는 것은 다른 이야기라, 표시를 따로 둬요. `sh` 는 상태가 있지만 패턴이 아니고 `she` 는
둘 다입니다.

```text
상태 하나가 드는 것
  next    글자 26 칸           아직 안 채운 칸은 -1
  endOf   여기서 끝나는 패턴   없으면 빈 목록
  depth   뿌리에서의 글자 수   그 상태에서 끝나는 패턴의 길이이기도 하다
└ 자기 글자를 들지 않는다. 글자는 부모에서 이 상태로 오는 간선에 붙어 있다
```

#### 2. 실패 링크와 전이표를 얕은 상태부터 채운다

둘째 조각은 링크입니다. 상태 `v` 의 실패 링크는 **부모의 실패 링크에서 한 글자 더 간 자리**로
정해져요 — 부모까지의 답을 알면 자식의 답이 표 조회 한 번으로 나옵니다.

```ts
const queue = new Int32Array(size);
let head = 0;
let tail = 0;
for (let c = 0; c < SIGMA; c++) {
  const child = next[c] as number;
  if (child === -1) {
    next[c] = 0;                        // ③ 뿌리에 없는 글자는 뿌리 자신으로
  } else {
    link[child] = 0;
    queue[tail] = child;
    tail += 1;
  }
}
while (head < tail) {
  const v = queue[head] as number;
  head += 1;
  const f = link[v] as number;
  // ④ 출력 링크는 실패 링크가 가리키는 상태에서 물려받는다.
  outLink[v] = (endOf[f] as number[]).length > 0 ? f : (outLink[f] as number);
  for (let c = 0; c < SIGMA; c++) {
    const u = next[v * SIGMA + c] as number;
    if (u === -1) {
      next[v * SIGMA + c] = next[f * SIGMA + c] as number;   // ⑤ 실패 링크의 같은 칸을 물려받는다
    } else {
      link[u] = next[f * SIGMA + c] as number;
      queue[tail] = u;
      tail += 1;
    }
  }
}
```

큐를 쓰는 것이 이 조각의 요점이에요. `④` 도 `⑤` 도 **실패 링크가 가리키는 상태의 값이 이미
채워져 있어야** 동작하는데, 그 상태는 언제나 깊이가 더 얕습니다. 그러니 깊이가 얕은 것부터
꺼내면 필요한 값이 항상 준비돼 있어요.

```text
무엇이 무엇에 기대는가
  link[u] 를 정하려면    next[f][c] 가 필요하다     f = link[v] 이고 깊이(f) < 깊이(v)
  next[v][c] 를 채우려면 next[f][c] 가 필요하다     같은 f 다
  outLink[v] 를 정하려면 outLink[f] 가 필요하다     같은 f 다
└ 셋 다 「더 얕은 상태」만 본다. 그래서 깊이 0, 1, 2 … 순서로 채우면 어긋나는 자리가 없다
```

이 순서대로 채우면 앞에서 손으로 고른 표와 같은 것이 나옵니다. 상태 `sh` 의 실패 링크는 `h`,
`she` 는 `he`, `hers` 는 `s` 이고 나머지는 뿌리이며, 출력 링크는 `she` 만 `he` 를 가리켜요.

```text
채우는 순서 — 큐에 담기는 차례와 그때 보는 줄
  깊이 1   h      뿌리의 자식이라 실패 링크가 뿌리다
           s      뿌리의 자식이라 실패 링크가 뿌리다
  깊이 2   he     부모 h 의 실패 링크는 뿌리다. 뿌리 줄의 e 칸이 뿌리   -> 실패 링크 뿌리
           sh     부모 s 의 실패 링크는 뿌리다. 뿌리 줄의 h 칸이 h     -> 실패 링크 h
  깊이 3   her    부모 he 의 실패 링크는 뿌리다. 뿌리 줄의 r 칸이 뿌리  -> 실패 링크 뿌리
           she    부모 sh 의 실패 링크는 h 다. h 줄의 e 칸이 he        -> 실패 링크 he
  깊이 4   hers   부모 her 의 실패 링크는 뿌리다. 뿌리 줄의 s 칸이 s   -> 실패 링크 s
└ 보는 줄은 부모의 실패 링크이고 그것은 적어도 두 단 위다. 한 줄 위를 다 끝낸 뒤에 다음 줄을 채운다
```

#### 짚고 가기 — 자식이 없는 칸을 뿌리로 두면 긴 패턴이 사라진다

여기서 헷갈리기 쉬운 포인트는 `⑤` 입니다. 「어차피 맞는 자식이 없으니 처음부터 다시 시작하면
되지 않나」로 읽기 쉬워요. 그 생각대로 물려받는 줄을 뿌리 대입으로 바꿔 봅시다.

```ts
if (u === -1) {
  next[v * SIGMA + c] = 0;     // 물려받지 않고 뿌리를 적는다
}
```

만들어지는 트리와 실패 링크는 정본과 같습니다. 갈리는 것은 자식이 없는 칸의 값이에요.

<!--proof:pauseEmptyCell-->

```text
텍스트      정본이 낸 매칭   빈 칸을 뿌리로 둔 답  판정
"ushers"    1@1 0@2 2@2      1@1 0@2               다르다
"ahishers"  2@1 1@3 0@4 3@4  2@1                   다르다
"aaaa"      0@0 0@1 0@2      0@0                   다르다

└ 첫 줄에서 hers 가 사라진다. she 에서 r 을 읽을 때 her 로 가야 하는데 뿌리로 갔고,
  그다음 s 를 읽어도 hers 를 끝낼 자리가 없다. 둘째 줄도 같은 자리에서 같은 것을 잃는다
```

`she` 에서 `r` 을 읽는 자리가 그 차이입니다. 정본은 `she` 의 `r` 칸에 `her` 이 적혀 있어서 거기로
옮기고 다음 글자 `s` 로 `hers` 를 끝내요. 뿌리로 되돌린 쪽은 `r` 을 읽고 뿌리로 갔으므로,
그다음 `s` 를 읽어도 상태 `s` 에 있을 뿐 `hers` 를 끝낼 자리가 없습니다.

```text
텍스트 자리 4 의 글자 r 을 읽을 때
  물려받으면     she 의 r 칸 = her      다음 s 로 hers 를 끝낸다
  뿌리로 두면    she 의 r 칸 = 뿌리     다음 s 로 상태 s 에 갈 뿐이다
└ 이 한 칸이 정하는 것은 「지금까지 읽은 것의 끝부분을 얼마나 남길 것인가」다
  뿌리로 두는 것은 읽은 것을 통째로 버리는 것이고, 그러면 실패 링크를 만든 이유가 사라진다
```

#### 3. 텍스트를 한 글자씩 읽으며 상태를 옮긴다

셋째 조각은 읽기입니다. 표가 다 채워져 있으므로 글자 하나에 조회 한 번이고, 되돌아가는
반복문이 없어요.

```ts
let s = 0;
for (let pos = 0; pos < text.length; pos++) {
  // ⑥ 글자 하나에 표를 한 번 조회해 다음 상태로 옮긴다.
  s = auto.next[s * SIGMA + codeOf(text[pos] as string)] as number;
  // ⑦ 지금 상태에서 끝나는 패턴부터 출력 링크를 따라가며 전부 거둔다.
  for (let t = s; t !== -1; t = auto.outLink[t] as number) {
    for (const i of auto.endOf[t] as number[]) {
      const length = auto.depth[t] as number;
      found.push({ patternIndex: i, position: pos - length + 1 });
    }
  }
}
```

시작 자리를 내는 식이 `pos - length + 1` 인 것에 이유가 있어요. `depth[t]` 는 뿌리에서 `t` 까지의
글자 수이고, `t` 에서 끝나는 패턴은 그 길이와 같습니다. 그러니 끝 자리 `pos` 에서 길이만큼
되돌아간 자리가 시작 자리예요.

```text
자리 3 에서 상태 she 에 도착하면 (pos = 3)
  t = she    depth 3   패턴 1 (she)   3 − 3 + 1 = 1
  t = he     depth 2   패턴 0 (he)    3 − 2 + 1 = 2
  t = −1     사슬 끝
└ 출력 링크를 한 번 더 따라간 덕에 she 안에 숨어 있던 he 가 나온다
```

#### 짚고 가기 — 출력 링크 대신 실패 링크를 따라가도 답은 같다

여기서 헷갈리기 쉬운 포인트는 **링크가 왜 두 종류나 필요한가**입니다. 실패 링크도 끝부분을
가리키니 그것을 뿌리까지 따라가면서 패턴을 거두면 될 것 같아요. 실제로 그렇게 해 봅시다.

```ts
let t = s;
for (;;) {
  for (const p of auto.endOf[t] as number[]) { /* 거둔다 */ }
  if (t === 0) break;
  t = auto.link[t] as number;          // 출력 링크 대신 실패 링크를 따라간다
}
```

**이 문제에서는 답이 틀리지 않습니다.** 실패 링크를 뿌리까지 따라가면 끝부분을 전부 지나가므로
패턴이 끝나는 상태를 하나도 빠뜨리지 않아요. 갈리는 것은 걸음 수입니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 넷이에요 — 자료의 모양을 적은
인터페이스 둘, 배열의 크기를 잡는 몇 줄, 반환 순서를 정하는 견줌 함수 하나, 그리고 길이 0 인
패턴을 걸러 내는 한 줄입니다. 마지막 것은 뿌리에 패턴 끝이 붙으면 글자를 하나도 읽지 않은
자리까지 매칭이 되어 `position` 의 범위를 벗어나기 때문이에요.

```ts
/** 문자 집합의 크기. 제약이 소문자 영문 `a`–`z` 로 정했다. */
const SIGMA = 26;

/** 소문자 한 글자를 0..25 의 번호로 바꾼다. */
const codeOf = (ch: string): number => ch.charCodeAt(0) - 97;

export interface Match {
  patternIndex: number;
  position: number;
}

export interface Automaton {
  next: Int32Array;      // next[s * SIGMA + c] — 상태 s 에서 글자 c 를 읽었을 때 갈 상태
  link: Int32Array;      // link[s] — 실패 링크
  outLink: Int32Array;   // outLink[s] — 패턴이 끝나는 가장 가까운 진 접미사 상태. 없으면 -1
  endOf: number[][];     // endOf[s] — 상태 s 에서 끝나는 패턴의 번호들
  depth: Int32Array;     // depth[s] — 뿌리에서 s 까지의 글자 수
  size: number;
}

/** 반환 규약의 순서 — `position` 오름차순, 같으면 `patternIndex` 오름차순. */
const byPosition = (a: Match, b: Match): number =>
  a.position - b.position || a.patternIndex - b.patternIndex;

export function buildAutomaton(patterns: readonly string[]): Automaton {
  // 상태 수의 상한은 패턴 길이의 합에 뿌리 하나를 더한 것이다.
  let cap = 1;
  for (const p of patterns) cap += p.length;

  const next = new Int32Array(cap * SIGMA).fill(-1);
  const link = new Int32Array(cap);
  const outLink = new Int32Array(cap).fill(-1);
  const depth = new Int32Array(cap);
  const endOf: number[][] = Array.from({ length: cap }, () => [] as number[]);
  let size = 1;

  for (let i = 0; i < patterns.length; i++) {
    const pattern = patterns[i] as string;
    if (pattern.length === 0) continue;
    let s = 0;
    for (const ch of pattern) {
      const c = codeOf(ch);
      // ① 그 글자로 가는 자식이 없을 때만 상태를 새로 만든다.
      if (next[s * SIGMA + c] === -1) {
        next[s * SIGMA + c] = size;
        depth[size] = (depth[s] as number) + 1;
        size += 1;
      }
      s = next[s * SIGMA + c] as number;
    }
    // ② 패턴이 끝난 상태에 그 패턴의 번호를 적는다.
    (endOf[s] as number[]).push(i);
  }

  // 실패 링크와 전이표를 깊이가 얕은 상태부터 채운다. 큐에 담는 순서가 곧 그 순서다.
  const queue = new Int32Array(size);
  let head = 0;
  let tail = 0;
  for (let c = 0; c < SIGMA; c++) {
    const child = next[c] as number;
    if (child === -1) {
      // ③ 뿌리에 그 글자로 가는 자식이 없으면 그 칸은 뿌리 자신이다.
      next[c] = 0;
    } else {
      link[child] = 0;
      queue[tail] = child;
      tail += 1;
    }
  }

  while (head < tail) {
    const v = queue[head] as number;
    head += 1;
    const f = link[v] as number;
    // ④ 출력 링크는 실패 링크가 가리키는 상태에서 물려받는다. 그 상태에서 패턴이 끝나면
    //    그 상태 자신이고, 아니면 그 상태의 출력 링크다.
    outLink[v] = (endOf[f] as number[]).length > 0 ? f : (outLink[f] as number);
    for (let c = 0; c < SIGMA; c++) {
      const u = next[v * SIGMA + c] as number;
      if (u === -1) {
        // ⑤ 자식이 없는 칸은 실패 링크가 가리키는 상태의 같은 칸을 그대로 물려받는다.
        next[v * SIGMA + c] = next[f * SIGMA + c] as number;
      } else {
        link[u] = next[f * SIGMA + c] as number;
        queue[tail] = u;
        tail += 1;
      }
    }
  }

  return { next, link, outLink, endOf, depth, size };
}

export function ahoCorasick(text: string, patterns: string[]): Match[] {
  const auto = buildAutomaton(patterns);
  const found: Match[] = [];
  let s = 0;
  for (let pos = 0; pos < text.length; pos++) {
    // ⑥ 글자 하나에 표를 한 번 조회해 다음 상태로 옮긴다. 되돌아가는 반복문이 없다.
    s = auto.next[s * SIGMA + codeOf(text[pos] as string)] as number;
    // ⑦ 지금 상태에서 끝나는 패턴부터 출력 링크를 따라가며 전부 거둔다. 짧은 패턴이
    //    긴 패턴의 접미사로 숨어 있는 자리가 여기서 나온다.
    for (let t = s; t !== -1; t = auto.outLink[t] as number) {
      for (const i of auto.endOf[t] as number[]) {
        const length = auto.depth[t] as number;
        found.push({ patternIndex: i, position: pos - length + 1 });
      }
    }
  }
  // ⑧ 찾은 순서는 패턴이 끝난 자리의 순서다. 문제가 요구한 시작 자리 순서로 다시 맞춘다.
  found.sort(byPosition);
  return found;
}
```

```text
같은 패턴 두 벌         "abab"      "ab" "ab"                0@0 1@0 0@2 1@2
길이 1                  "a"         "a"                      0@0

└ 매칭은 `패턴 번호@시작 자리` 다. 아래 일곱은 전개에서 나오지 않은 자리다
```

### 알아 두면 좋은 개념 — 위상 순서

전이표를 채운 순서에는 이름이 붙어 있습니다. 값 하나를 정하려면 다른 값이 먼저 정해져 있어야
할 때, **먼저 정해져야 하는 것이 항상 앞에 오도록 늘어놓은 순서**를 위상 순서라고 불러요.
여기서는 깊이가 그 순서를 만들었습니다.

| 정하려는 것 | 먼저 정해져 있어야 하는 것 | 깊이의 관계 |
| --- | --- | --- |
| `link[u]` | `next[f]` 의 그 글자 칸 | 깊이가 적어도 2 얕다 |
| `next[v]` 의 빈 칸 | `next[f]` 의 같은 칸 | 깊이가 적어도 1 얕다 |
| `outLink[v]` | `outLink[f]` | 깊이가 적어도 1 얕다 |

앞 절의 큐가 그 순서를 값으로 보인 자리예요. 깊이 1 의 `h` · `s` 를 먼저 꺼내고, 깊이 2 의 `he` ·
`sh` 를 그다음에 꺼냈습니다. 그래서 깊이 3 의 `she` 를 꺼낼 때 필요한 `he` 의 26 칸이 이미 채워져
있었어요.

```text
같은 순서가 나오는 다른 자리
  위상 정렬          앞선 작업이 끝나야 시작할 수 있는 작업을 그 순서로 늘어놓는다
  표를 채우는 계산   칸 하나가 왼쪽 칸과 윗 칸에 기대면 왼쪽 위부터 채운다
  빌드 시스템        모듈이 기대는 모듈을 먼저 빌드한다
└ 셋 다 「기대는 것이 먼저」라는 규칙 하나로 순서가 정해진다. 규칙이 순환하면 순서가 없다
```

여기서 순서가 항상 존재하는 이유는 실패 링크가 **언제나 더 얕은 상태**를 가리키기 때문입니다.
깊이가 줄어들기만 하므로 순환이 생길 수 없어요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 매칭 개수를 식으로 어떻게 닫는지,
무엇이 매 걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

다음 네 가지가 함께 맞을 때입니다.

- **패턴이 여럿이고 미리 다 주어집니다.** 기계를 만드는 비용을 한 번만 내고 여러 번 씁니다.
  패턴이 하나면 그 비용을 낼 이유가 없어요.
- **텍스트를 한 번만 읽고 싶습니다.** 텍스트가 이어서 들어오거나 너무 커서 여러 번 읽을 수 없는
  자리가 이것입니다. 글자를 받는 즉시 상태를 옮기고 끝나는 패턴을 그 자리에서 돌려줄 수 있어요.
- **겹치는 등장을 전부 찾아야 합니다.** 짧은 패턴이 긴 패턴 안에 끝부분으로 숨어 있어도 놓치면
  안 되는 문제라야 출력 링크가 값을 합니다.
- **문자 집합이 작습니다.** 상태마다 문자 집합 크기만큼 칸을 잡으므로, 그 크기가 크면 표가
  먼저 메모리를 다 씁니다.

```text
네 조건이 각각 코드의 어느 자리를 정하는가
  패턴이 여럿이고 미리 주어진다    -> 기계를 한 번 만들고 텍스트에 한 번 건다
  텍스트를 한 번만 읽는다          -> 되돌아가는 반복문이 없다
  겹치는 등장을 전부 찾는다        -> 출력 링크 사슬을 따라간다
  문자 집합이 작다                 -> 상태마다 26 칸을 미리 채운다
```

넷째 줄이 이 구조의 경계입니다. 유니코드 전체처럼 문자 집합이 커지면 상태마다 그만큼 칸을
잡을 수 없어요. 그때는 실제로 쓰이는 전이만 맵에 담고 나머지는 실패 링크로 처리하는 쪽으로
돌아가고, 한 글자에 정확히 한 번이라는 보장을 내주게 됩니다.

| 무엇을 찾는가 | 무엇을 쓰는가 | 왜 그런가 |
| --- | --- | --- |
| 패턴 여럿의 모든 등장 | 이 글의 기계 | 텍스트 한 번으로 끝난다 |
| 패턴 하나의 모든 등장 | 실패 함수 하나 | 표를 만드는 비용이 없다 |
| 텍스트는 고정이고 패턴이 계속 들어온다 | 접미사 구조 | 전처리를 텍스트 쪽에 둔다 |

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에서 이 말들이 보이면
  "패턴 수백 개"  "금칙어 목록"  "시그니처 집합"   <- 패턴이 여럿이고 미리 주어진다
  "한 번의 순회로"  "스트리밍"  "로그를 흘려보내며" <- 텍스트를 되돌려 읽을 수 없다
  "겹치는 등장도 모두"  "모든 (패턴, 위치) 쌍"     <- 출력 링크가 필요하다
  "패턴 수와 무관하게 텍스트 길이에 비례"          <- 패턴마다 다시 읽는 방식을 막는다

반대로 이 말들이 보이면 해당하지 않는다
  "패턴이 하나"                                    <- 실패 함수 하나로 충분하다
  "패턴에 와일드카드나 정규식"                     <- 전이가 하나로 정해지지 않는다
  "텍스트가 고정이고 질의가 계속 들어온다"         <- 전처리를 텍스트 쪽에 두는 편이 낫다
  "가장 긴 것 하나만"                              <- 전부 거둘 이유가 없다
```

마지막 무리가 보이면 다른 구조로 갑니다. 패턴이 하나면
[`findAllOccurrences`](../findAllOccurrences/findAllOccurrences-problem.md) 쪽이고, 텍스트가
고정이고 질의가 계속 들어오면 [`suffixArray`](../suffixArray/suffixArray-problem.md) 쪽이에요.

#### 경쟁 설계와의 대조

같은 목표(패턴 여럿의 모든 등장 자리를 찾는 것)를 노리는 다른 절차로 **패턴마다 실패 함수를
따로 만들어 텍스트를 그만큼 다시 읽는 방식**이 있습니다. 패턴 하나짜리 절차를 `k` 번 부르는
것이고, 만드는 비용이 아주 작은 대신 텍스트를 `k` 번 읽어요.

```text
두 설계가 값을 어디에 치르는가
  한 기계로 합치기   상태마다 26 칸을 미리 채운다        텍스트는 한 번만 읽는다
  패턴마다 KMP       패턴 하나의 실패 함수만 만든다      텍스트를 패턴 개수만큼 읽는다
└ 앞은 패턴 길이의 합에, 뒤는 텍스트 길이 곱하기 패턴 개수에 비용이 붙는다
```

같은 입력·같은 작업 목록에 두 설계를 걸고 **기본 연산 수**(텍스트·패턴 글자 읽기 + 표 한 칸
조회·기록 + 글자 견주기)를 셌습니다. 텍스트는 제약 최댓값인 100,000 글자이고 패턴 길이의 합도
최댓값인 100,000 으로 고정한 채 **패턴 개수만** 바꿨어요. 텍스트는
`x ← (x × 48271) mod 2147483647` 로 다음 수를 만들고 그 나머지로 글자를 고른 것이고 시작값은
20,250,903 이며, 패턴은 그 텍스트에서 잘라 냈습니다. **전개 입력을 그대로 쓰지 않은 이유**는
그 크기에서 경계를 볼 수 없기 때문이에요 — 전개 입력은 패턴 길이의 합이 9 라 패턴을 아홉 개보다
많이 만들 수 없는데, 아래에서 순서가 뒤집히는 자리는 패턴 40 개입니다.

**패턴이 40 개 미만이고 메모리가 빠듯한 경우**라면 이 판정은 다시 해야 해요.

### 수식 정의와 유도

텍스트 `T` 와 패턴 집합 `P` 에 대해 **매칭 집합**을 정의합니다. `T[j..j+ℓ)` 는 `T` 의 자리 `j`
에서 `ℓ` 글자를 잘라 낸 것이고, `i` 는 앞에서와 같은 패턴 번호예요.

$$\operatorname{Occ}(T, P) = \{\, (i, j) \;:\; p_i \in P,\ 0 \le j \le |T| - |p_i|,\ T[j..j+|p_i|) = p_i \,\} \qquad z = |\operatorname{Occ}(T, P)|$$

```text
식을 읽는 법
  T            텍스트
  P            패턴 집합. p_i 가 i 번 패턴이다
  (i, j)       i 번 패턴이 자리 j 에서 시작한다는 뜻
  z            그 쌍의 개수. 코드가 돌려주는 배열의 길이다
└ 겹치는 등장을 빼지 않으므로 같은 j 에 여러 i 가, 같은 i 에 여러 j 가 올 수 있다
```

이 `z` 가 얼마나 커질 수 있는지가 이 절의 물음입니다. 본문이 값으로 본 매칭은 셋뿐인데, 제약이
정한 규모에서 이 수가 몇 자리가 되는지는 그 셋으로 나오지 않아요. 먼저 한 자리에서 몇 개가
함께 끝날 수 있는지 봅시다.

```text
끝 자리 하나에서 함께 끝나는 패턴들
  전부 그 자리까지 읽은 것의 접미사다   끝 자리가 같으니 끝에서부터 겹친다
  서로 다른 패턴이면 길이가 다르다      같은 길이의 서로 다른 두 접미사는 없다
└ 그러므로 한 자리에서 끝나는 서로 다른 패턴의 개수는 「패턴 길이의 가짓수」를 넘지 못한다
```

길이의 가짓수를 `m` 이라 두면, 서로 다른 길이 `m` 개의 합이 가장 작은 경우가 `1, 2, …, m` 일
때입니다. 그 합이 제약 안에 들어와야 해요.

$$\sum_{t=1}^{m} t = \frac{m(m+1)}{2} \le L \qquad\Longrightarrow\qquad z \le \sum_{t=1}^{m} (n - t + 1) = m(n+1) - \frac{m(m+1)}{2}$$

```text
두 항이 어디서 왔는가
  왼쪽   길이를 1 2 3 … m 으로 고르면   합이 m(m+1)/2 다      그보다 작게 만들 수 없다
  오른쪽 길이 t 인 패턴이 끝나는 자리   t−1 부터 n−1 까지     n − t + 1 개다
└ 왼쪽이 「제약이 허용하는 가장 큰 m」을 정하고, 오른쪽을 t = 1..m 에 더한 것이 매칭의 상한이다
```

정의를 작은 값에 넣어 검산하고 갑시다. 패턴을 `a` · `aa` · `aaa` … 로 두고 텍스트를 `a` 로만
채우면 위 부등식이 등호가 되고, 그때 실행이 낸 매칭 수와 식이 낸 값이 같아야 합니다.

<!--proof:mathCheck-->

```text
텍스트 길이 n  패턴 수 m  길이 합  식이 낸 값  실행이 낸 매칭 수  판정
           20          5       15          90                 90  같다
           50          9       45         414                414  같다
          200          9       45       1,764              1,764  같다
          200         19      190       3,629              3,629  같다

└ 패턴은 a · aa · aaa … 를 m 개까지이고 텍스트는 a 를 n 번 이어 붙인 것이다
  식은 m(n+1) − m(m+1)/2 이고 네 줄이 다 실행과 같다
```

```ts
// 식을 그대로 옮긴 조각. 길이 t 인 패턴은 자리 t-1 부터 n-1 까지 n-t+1 번 끝난다.
const zMax = (n: number, m: number): number => m * (n + 1) - (m * (m + 1)) / 2;
```

제약 규모를 두 식에 넣으면 이렇게 나옵니다. `m` 은 `m(m+1)/2 ≤ 100,000` 을 만족하는 가장 큰
수예요.

<!--proof:mathBound-->

```text
서로 다른 길이의 개수 m  길이 합 m(m+1)/2  제약 판정  매칭 수 상한
                    445            99,235  제약 안      44,401,210
                    446            99,681  제약 안      44,500,765
                    447           100,128  제약 밖      44,600,319

└ 서로 다른 패턴이면 매칭 수는 많아야 44,500,765 개다
  같은 패턴을 여러 벌 담을 수 있다면 패턴 수가 100,000 까지 가므로
  상한은 100,000 × 100,000 = 10,000,000,000 이 된다
```

**여기서 본문의 값만으로는 나오지 않는 것이 둘 나옵니다.** 하나는 서로 다른 패턴만 담을 때
매칭이 4,450 만 개까지 간다는 것이고, 다른 하나는 **같은 패턴을 여러 벌 담을 수 있다면 상한이
100 억으로 뛴다**는 것입니다. 뒤의 것은 길이가 1 인 패턴을 100,000 벌 담고 텍스트를 그 글자로만
채우면 나와요.

```text
두 상한이 갈리는 이유
  서로 다른 패턴만   한 자리에서 끝나는 개수가 길이의 가짓수로 막힌다   m ≤ 446
  같은 패턴을 여러 벌  길이가 같아도 번호가 다르니 막히지 않는다        k ≤ 100,000
└ 반환 배열의 길이가 곧 z 이므로, 이 수가 절차의 비용에 그대로 들어간다
```

### 불변식 — 글자를 하나 읽을 때마다 상태는 지금까지 읽은 것의 가장 긴 접미사이면서 어떤 패턴의 접두사인 것이다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **글자를 하나 읽을 때마다 참으로 남는지**를 문장으로
세우고 그것이 실제로 유지되는지 확인해 봅시다.

> 텍스트를 자리 `pos` 까지 읽은 직후, 지금 상태의 이름은 `T[0..pos]` 의 접미사이면서 어떤
> 패턴의 접두사이기도 한 것 중 **가장 긴 것**입니다. 그리고 그 상태에서 출력 링크를 따라간
> 상태들이 자리 `pos` 에서 끝나는 패턴의 전부입니다.

```text
글자 하나를 읽은 시점에 참인 것 둘
  앞 문장   상태의 이름은 읽은 것의 가장 긴 접미사이면서 어떤 패턴의 접두사인 것
  뒤 문장   그 상태의 출력 링크 사슬이 이 자리에서 끝나는 패턴의 전부
└ 앞 문장이 「되돌려 읽지 않아도 된다」의 근거이고, 뒤 문장이 「겹친 것도 다 찾는다」의 근거다
```

문장이 둘인 것에 이유가 있습니다. 앞 문장은 상태 하나만 들고 다녀도 되는 근거이고, 뒤 문장은
그 상태에서 매칭을 전부 거둘 수 있다는 근거예요. 앞 문장이 성립하지 않으면 뒤 문장은 물어볼
것도 없어집니다.

**출발점부터 봅시다.** 아무 글자도 읽지 않았을 때 상태는 뿌리이고 그 이름은 빈 문자열입니다.
빈 문자열은 모든 문자열의 접미사이자 모든 패턴의 접두사이고, 그보다 긴 것은 아직 읽은 글자가
없으니 있을 수 없어요. 뿌리에서 끝나는 패턴은 없고 출력 링크도 없으므로 뒤 문장도 참입니다.

| 이 걸음 | 상태가 어떻게 바뀌는가 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작 | 뿌리에서 출발한다 | 읽은 것이 없어 빈 문자열이 가장 길다 | 뿌리에 패턴이 없다 |
| 글자 하나 · 자식이 있다 | 그 자식으로 옮긴다 | 앞의 가장 긴 것에 글자를 붙인 것이 여전히 가장 길다 | 새 상태의 출력 링크를 따라간다 |
| 글자 하나 · 자식이 없다 | 물려받은 칸으로 옮긴다 | 그 칸은 실패 링크가 가리키는 상태에서 같은 글자로 간 자리다 | 같다 |
| 글자 하나 · 갈 데가 없다 | 뿌리로 옮긴다 | 어떤 접미사도 패턴의 접두사가 아니다 | 뿌리에 패턴이 없다 |

셋째 줄이 이 논증의 핵심입니다. 물려받은 칸의 값은 「실패 링크를 따라가서 그 글자로 간 자리」와
같게 정해졌어요. 실패 링크는 **자기 다음으로 긴 후보**를 가리키므로, 자식이 없을 때 그 다음
후보에서 이어 가는 것이 가장 긴 것을 유지하는 유일한 방법입니다.

```text
왜 「가장 긴 것」이 유지되는가
  앞 걸음의 가장 긴 것을 X 라 하고 글자 c 를 읽는다
  이번 걸음의 후보는 Xc 의 접미사들이고 긴 것부터   Xc · (X 의 실패 링크)c · 그다음 …
  그중 상태로 있는 첫 번째가 답이다                 더 긴 후보는 상태가 없어 후보가 아니다
└ 물려받은 칸에는 그 「첫 번째」가 이미 적혀 있다. 표를 채우는 일이 이 탐색을 미리 해 둔 것이다
```

앞 절의 전개 입력에서 이것을 값으로 확인해 봅시다. 왼쪽은 접미사를 전부 만들어 정의대로 고른
것이고 오른쪽은 코드가 옮겨 간 상태예요.

<!--proof:invariantStates-->

```text
걸음  자리  글자  여기까지 읽은 것  정의가 말하는 가장 긴 접미사  상태의 경로 문자열  판정
T3       0  u     "u"               (뿌리)                        (뿌리)              같다
T4       1  s     "us"              s                             s                   같다
T5       2  h     "ush"             sh                            sh                  같다
T6       3  e     "ushe"            she                           she                 같다
T7       4  r     "usher"           her                           her                 같다
T8       5  s     "ushers"          hers                          hers                같다

└ 다섯째 칸은 패턴 셋의 접두사를 전부 만들어 정의대로 고른 것이고 여섯째 칸은 코드가 옮겨 간 상태다
```

경계에 있는 입력들도 확인하고 갑니다.

<!--proof:invariantEdges-->

```text
무엇                    텍스트  패턴            매칭                                 개수
텍스트 한 글자          "a"     "a"             0@0                                     1
패턴이 텍스트보다 길다  "ab"    "abcdef"        (없음)                                  0

└ 다섯째 줄은 자리마다 매칭이 여럿 나오는 경우이고, 여섯째 줄은 같은 자리가 두 번 적히는 경우다
```

**이제 깨뜨려 봅시다.** 앞 문장을 지키던 줄은 실패 링크를 정하는 한 줄이에요. 「어차피 어긋나면
처음부터 다시 하니 실패 링크를 전부 뿌리로 두면 되지 않나」라는 생각으로 그 줄을 바꿔 봅니다.

```ts
link[u] = 0;      // next[f * SIGMA + c] 대신 뿌리를 적는다
```

정본과 나란히 실행하면 이렇게 나옵니다.

```text
  she 의 실패 링크가 he 에서 (뿌리) 로 바뀐다
  hers 의 실패 링크가 s 에서 (뿌리) 로 바뀐다
```

앞 문장이 깨지면 상태의 이름이 「가장 긴 것」이 아니게 되고, 그러면 뒤 문장의 근거도 함께
사라집니다. 출력 링크는 여전히 실패 링크에서 물려받지만, 그 실패 링크가 뿌리를 가리키므로

```text
  출력 링크    she 가 he 를 못 받는다               she 에서 끝나는 패턴이 하나로 준다
└ 세 상태가 어긋나고, 그 어긋남이 매칭 셋 중 둘을 없앤다
```

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 네 무리입니다 — 패턴을 트리에 담는 것, 전이표와 링크를 채우는 것,
텍스트를 읽는 것, 매칭을 거두는 것이에요. 전개의 걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perfCount-->

```text
무리             무엇을 세는가            식                      이 입력에서
패턴을 담는다    패턴 글자마다 표 조회    2L + 새 상태 수 + k              28
표를 채운다      상태마다 26 칸           2·26 + (S−1)(2 + 3·26)          612
텍스트를 읽는다  글자마다 읽기와 조회     2n                               12
매칭을 거둔다    출력 링크를 따라간 걸음  n + 출력 링크 이동                7
합계             -                        -                               659

상태 수 S = 8 · 패턴 길이 합 L = 9 · 텍스트 길이 n = 6 · 매칭 수 z = 3
└ 텍스트를 읽는 무리는 12 이고 걸음 6 개에 고르게 나뉜다 — 패턴이 몇 개든 이 수는 그대로다
```

둘째 줄이 이 표의 요점입니다. 텍스트 여섯 글자짜리 입력에서 연산의 대부분(659 중 612)이 표를
채우는 데 들어가요. 그런데 **표를 채우는 무리는 텍스트 길이를 보지 않습니다** — 텍스트를 읽는
무리는 T3 부터 T8 까지 여섯 걸음에 12 뿐이고, 텍스트가 10 만 글자가 되면 그 무리만 20 만으로
늘어납니다.

```text
총식 = 만들기 + 읽기 + 거두기 + 순서 맞추기
  만들기       2L + (S−1) + k + 2·26 + (S−1)(2 + 3·26)   패턴 길이의 합과 상태 수만 본다
  읽기         2n                                        글자마다 읽기 하나 조회 하나
  거두기       n + 출력 링크 이동                        이동 수는 매칭 개수 z 를 넘지 않는다
  순서 맞추기  z 개를 정렬한다                            반환 규약이 요구하는 값이다
└ 어느 항에도 「패턴 개수 × 텍스트 길이」 자리가 없다. 그것이 처음에 없애려던 항이다
```

`S ≤ L + 1` 이므로 만들기의 크기를 정하는 것은 `L` 과 `26S` 둘뿐입니다. 제약 최댓값에서 실제로
잰 값이 860 만이고, 그것이 앞 절 대조표의 첫 열이에요. 읽기는 20 만이고, 거두기와 순서 맞추기는
`z` 를 따라갑니다 — 앞 절에서 닫은 `z` 의 상한이 여기 그대로 들어와요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 서로 다른 축입니다. 한 축의 이름을
다른 축에 붙이면 안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (매칭이 하나도 없다) | `O(ΣL + n)` | `Θ(ΣL + n)` — 표를 다 채우고 글자를 다 읽는다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(ΣL + n + z log z)` | 정의되지 않는다 |
| **최악의 경우** (매칭이 상한까지 나온다) | `O(ΣL + n + z log z)` | `Θ(ΣL + n + z log z)` |

가운데 줄의 타이트한 값이 정의되지 않는 것은 **입력 분포가 없기 때문**입니다. 매칭이 몇 개
나오는지는 텍스트와 패턴이 함께 정하는 것이라, 분포를 가정하지 않으면 기댓값을 쓸 수 없어요.
최선과 최악은 다릅니다 — 표를 채우는 항과 글자를 읽는 항은 **어떤 입력에서도 정확히 그만큼**
이라 타이트한 값으로 적을 수 있습니다.

```text
상한과 타이트한 값은 무엇이 다른가
  그보다 더 하지 않는다는 것만 말한다   상한이다          O(...)
  실제로 그만큼 한다는 것도 말한다      타이트한 값이다   Theta(...)
└ 표 채우기와 글자 읽기는 입력과 무관하게 그만큼 한다. 갈리는 것은 z 가 든 항뿐이다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 항이 둘 있어요 — 트리를 담는 `L` 과 반환 직전의
정렬입니다.

```text
총식 = 만들기 + 읽기 + 거두기 + 정렬
  만들기   Theta(L + Sigma·S) 시간     Sigma 는 26 이고 S 는 L + 1 이하다
  읽기     Theta(n) 시간               글자마다 표 조회 정확히 한 번
  거두기   Theta(n + z) 시간           출력 링크 이동은 z 를 넘지 않는다
  정렬     O(z log z) 시간             반환 규약이 시작 자리 순서를 요구한다
  메모리   Theta(Sigma·S + z) 칸       전이표 26S · 링크와 깊이 3S · 반환 배열 z
└ 좌표 압축이나 사전 정렬 같은 다른 전처리 항은 없다
```

**보장의 종류를 밝혀 둡니다.** 앞의 세 줄은 **최악 보장**이에요 — 해시가 없고 전부 배열
인덱싱이라 실행마다 같은 값이 나옵니다. 마지막 정렬 한 줄만 언어 런타임이 정해요.

| 무엇 | 보장의 종류 | 무엇이 정하는가 |
| --- | --- | --- |
| 표를 채우는 연산 수 | 최악 보장 `26S` | 상태 수 |
| 글자마다의 표 조회 | 최악 보장 정확히 1 | 표를 다 채웠다 |
| 출력 링크 이동 | 최악 보장 `n + z` | 사슬의 걸음이 곧 매칭이다 |
| 반환 직전의 정렬 | 언어 런타임이 정한다 | 명세는 안정성만 요구하고 최악 비용을 정하지 않는다 |

마지막 줄이 이 절차 밖의 값입니다. 매칭 순서를 문제가 요구하지 않았다면 이 항이 통째로
없어지고, 그때 총식은 `Theta(L + 26S + n + z)` 가 돼요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 패턴 전부를 **한 트리에 담고** 상태마다 「내
이름의 가장 긴 끝부분이면서 어떤 패턴의 앞부분인 것」을 가리키는 **실패 링크**를 달아, 어긋난
자리에서 텍스트를 되돌리지 않고 상태만 옮깁니다. 그 결과를 26 칸짜리 표에 미리 적어 두면 글자
하나에 조회 한 번이고, **출력 링크**가 한 자리에서 함께 끝나는 패턴을 전부 거둬요.

```text
  1.   패턴 전부가 한 트리에 들어간다     상태 하나가 「어디까지 맞았는가」다
  2.   실패 링크가 다음 후보를 가리킨다   텍스트 자리를 되돌리지 않는다
  3.   전이표를 미리 채운다               한 글자에 조회 정확히 한 번
  4.   출력 링크가 겹친 패턴을 거둔다     she 안의 he 가 여기서 나온다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T7 은 상태 `she` 에서 글자 `r` 을 읽고 `her` 로 옮긴
걸음이었어요. 그런데 `her` 의 깊이는 3 이고 `she` 의 깊이도 3 입니다. 깊이가 안 줄었는데 이것을
「실패 링크를 따라간 것」이라고 부를 수 있을까요?

```text
T7   텍스트 자리 4 의 글자 r   she -> her   두 상태 다 깊이 3
```

<!--check:whyDepthSame-->
따라간 것은 **실패 링크가 아니라 그 링크에서 물려받은 칸**이기 때문입니다. `she` 의 `r` 칸에
적힌 값은 「`she` 의 실패 링크 `he` 에서 `r` 로 간 자리」인 `her` 이고, 그 계산에서 깊이는 한 번
줄었다가(`she` 3 → `he` 2) 한 번 늘어납니다(`he` 2 → `her` 3). 결과만 남기고 중간을 지운 것이
표를 미리 채운다는 것의 뜻이에요.

```text
물려받은 칸 하나가 접어 둔 두 걸음
  줄어드는 걸음   she(깊이 3) -> he(깊이 2)    실패 링크를 한 번 따라간다
  늘어나는 걸음   he(깊이 2) -> her(깊이 3)    그 자리에서 글자 r 을 읽는다
  표에 적힌 것    she 의 r 칸 = her            두 걸음의 결과만 남는다
└ 그래서 깊이는 그대로일 수도, 줄 수도, 딱 하나 늘 수도 있다. 하나보다 많이 늘 수는 없다
```

깊이가 하나보다 많이 늘 수 없는 것이 앞 절의 불변식과 같은 이야기입니다. 글자를 하나 읽었는데
「가장 긴 것」이 둘 이상 길어졌다면, 그 하나 짧은 것이 앞 걸음에서 가장 긴 것이었어야 해요.
