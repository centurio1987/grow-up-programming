# SPFA — 값이 줄어든 정점의 간선만 다시 읽어도 답이 같은 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 경로를 전부
나열하는 방법에서 출발해, 간선 목록을 라운드마다 다시 읽는 방법을 거쳐, 값이 줄어든 정점의 간선만 다시 읽는
방법까지 갑니다. 그 방법을 준비되는 차례대로 값으로 풀고, 마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

간선마다 수가 하나씩 붙은 방향 그래프를 생각해 봅시다. 간선에 붙은 수를 **가중치**라고 부르고, 경로 하나의
**비용**은 그 경로가 지나는 간선의 가중치를 모두 더한 값입니다. 시작 정점 `src` 에서 정점 `v` 까지 가는 경로 중
비용이 가장 작은 것의 비용이 `v` 까지의 **최단 거리**예요. 이 글이 다루는 그래프는 가중치에 **음수가 섞일 수
있습니다.** 대신 가중치의 합이 0 보다 작은 순환 경로, 곧 **음수 사이클**은 시작 정점에서 갈 수 있는 자리에 없다고
정해 둡니다. 정점 여섯 · 간선 여덟인 그래프에서 정점 0 을 시작 정점으로 두고 최단 거리를 정점 안에 적으면
이렇습니다.

<!--fig:concept-graph-->
![전개 입력 — 간선 옆 수는 가중치, 정점 안의 수는 정점 0 에서의 최단 거리](./figs/concept-graph.svg)

굵은 실선은 최단 거리를 만든 간선입니다. 정점 5 는 나가는 간선만 있고 들어오는 간선이 없어서 시작 정점에서 갈
길이 없고, 이 글은 그 자리에 `Infinity` 를 적어 「도달할 수 없다」를 나타냅니다. 정점 1 과 3 으로 가는 경로를
전부 늘어놓으면 이렇습니다.

<!--proof:conceptPaths-->

| 도착 정점 | 경로 | 간선 수 | 비용 | 최소 |
| --- | --- | ---: | ---: | --- |
| 1 | 0→1 | 1 | 6 |  |
| 1 | 0→2→1 | 2 | -2 | 가장 작다 |
| 3 | 0→1→3 | 2 | 10 |  |
| 3 | 0→2→1→3 | 3 | 2 | 가장 작다 |
| 3 | 0→2→3 | 2 | 10 |  |
| 3 | 0→3 | 1 | 20 |  |

정본이 낸 거리는 dist[1] = -2 · dist[3] = 2 입니다.

<!--/proof-->

정점 1 로 가는 두 경로를 봐 주세요. 간선을 하나 더 지나는 `0→2→1` 이 곧장 가는 `0→1` 보다 비용이 작습니다.
가중치 −3 인 간선 `2 → 1` 이 있어서 **간선을 더 지나도 합이 줄어들 수 있기** 때문이에요. 그래서 이 절차는
정점마다 **지금까지 찾은 가장 작은 비용** `dist[v]` 를 들고 있다가, 더 작은 비용을 찾을 때마다 고쳐 적습니다.
간선 `u → v` 하나를 보고 `dist[u] + w` 가 `dist[v]` 보다 작으면 `dist[v]` 를 그 값으로 고치는 일을 **완화**라고
불러요.

완화를 되풀이하는 가장 곧은 방법은 벨만-포드입니다. 간선 목록을 처음부터 끝까지 한 번 읽으며 간선마다 완화하는
일을 **라운드**라고 부르고, 한 라운드가 한 칸도 못 고칠 때까지 라운드를 되풀이해요. 위 그래프에 그 방법을
실행하고 라운드마다 세면 이렇습니다.

<!--proof:conceptRounds-->

| 라운드 | 간선 읽기 | 값을 고친 읽기 | 아무것도 안 고친 읽기 | 라운드가 끝난 dist |
| ---: | ---: | ---: | ---: | --- |
| 1 | 8 | 6 | 2 | [0, -2, 1, 10, 12, Infinity] |
| 2 | 8 | 2 | 6 | [0, -2, 1, 2, 4, Infinity] |
| 3 | 8 | 0 | 8 | [0, -2, 1, 2, 4, Infinity] |

라운드 3 번에 간선 읽기 24 번이고, 그중 값을 고친 읽기가 8 번, 아무것도 안 고친 읽기가 16 번입니다.

<!--/proof-->

라운드 3 은 간선 여덟 개를 모두 읽었는데 한 칸도 못 고쳤습니다. 라운드 1 과 2 에도 아무것도 못 고친 읽기가
섞여 있어요. 간선 `u → v` 의 완화가 값을 고치려면 **그 간선을 지난번에 읽은 뒤로 `dist[u]` 가 줄어 있어야**
합니다. `dist[u]` 가 그대로면 `dist[u] + w` 도 그대로이고, `dist[v]` 는 줄기만 하니 비교 결과가 달라질 수 없기
때문입니다.

그래서 이 절차는 **값이 줄어든 정점만 따로 적어 두고, 그 정점에서 나가는 간선만 다시 읽습니다.** 적어 두는
자리가 **큐**예요. 큐는 값이 줄어든 정점을 넣어 두는 줄이고, 먼저 넣은 정점을 먼저 꺼냅니다. 시작 정점 하나를
넣고 시작해서, 정점 하나를 꺼내 그 정점의 간선만 완화하고, 값이 줄어든 정점을 큐 뒤에 넣는 일을 큐가 빌 때까지
되풀이해요. 같은 그래프에서 꺼낸 차례마다 적으면 이렇습니다.

<!--proof:conceptQueue-->

| 꺼낸 차례 | 정점 | 읽은 간선 | 값을 고친 간선 | 꺼낸 뒤 큐 |
| ---: | --- | --- | --- | --- |
| 1 | 0 | 0→1 · 0→2 · 0→3 | 0→1 · 0→2 · 0→3 | [1, 2, 3] |
| 2 | 1 | 1→3 | 1→3 | [2, 3] |
| 3 | 2 | 2→1 · 2→3 | 2→1 | [3, 1] |
| 4 | 3 | 3→4 | 3→4 | [1, 4] |
| 5 | 1 | 1→3 | 1→3 | [4, 3] |
| 6 | 4 | 없다 | 없다 | [3] |
| 7 | 3 | 3→4 | 3→4 | [4] |
| 8 | 4 | 없다 | 없다 | [] |

꺼내기 8 번에 간선 읽기 9 번이고, 그중 값을 고친 읽기가 8 번입니다. 결과 dist 는 [0, -2, 1, 2, 4, Infinity] 입니다.

<!--/proof-->

「꺼낸 뒤 큐」 열이 큐의 내용이고, 왼쪽 정점이 다음에 꺼낼 정점입니다. 정점 5 는 값이 한 번도 줄지 않아 큐에
들어간 적이 없고, 그래서 간선 `5 → 4` 는 한 번도 읽히지 않았어요. 이 절차의 이름이 **SPFA**(Shortest Path
Faster Algorithm)이고, 이 글은 끝까지 그 핵심 구조를 **큐**라고 부릅니다. 할 일을 나누어 보면 이렇습니다.

| 할 일 | 하는 일 | 드는 비용 |
| --- | --- | --- |
| 이웃 목록 만들기 | 간선 목록을 꼬리 정점별로 모아 한 정점의 나가는 간선을 바로 찾게 한다 | 간선마다 한 번 |
| 시작값과 큐 준비 | `dist` 를 `Infinity` 로 채우고 시작 정점만 0 을 적어 큐에 넣는다 | 정점마다 한 번 |
| 꺼내고 완화하기 | 큐에서 정점 하나를 꺼내 그 정점의 간선만 완화하고, 값이 줄어든 정점을 큐에 넣는다 | 꺼낼 때마다 그 정점의 간선 수 |
| 모두 | | `O(V·E)` — `V` 는 정점 수, `E` 는 간선 수 |

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **방향 간선 · 간선 목록 · 이웃 목록.** 간선 하나를 `[u, v, w]` 세 수로 적고 죽 늘어놓은 것이 간선 목록이고,
  그것을 꼬리 정점별로 모아 한 정점의 나가는 간선을 바로 찾게 만든 것이 이웃 목록입니다. `u → v` 로 적힌 간선은
  `u` 에서 `v` 쪽으로만 써요. 두 표현의 차이가 궁금하면
  [`graphAdjList` 가이드](../../../data-structures/graph-repr/graphAdjList/graphAdjList-guide.mdx)를 보세요.
- **완화 · 라운드 · 층.** 벨만-포드가 간선 목록 전체를 라운드마다 읽는 방법과, 「간선을 `k` 개 이하로 쓰는 최단
  비용」 `opt_k(v)` 를 층 `k` 로 부르는 방법은 [`bellmanFord`](../bellmanFord/bellmanFord-guide.md) 가 자세히
  다룹니다. 이 글은 그 방법에서 출발해요.
- **먼저 넣은 것을 먼저 꺼내는 큐.** 배열 하나와 「다음에 꺼낼 자리」를 가리키는 정수 하나면 됩니다. 자료구조
  자체가 궁금하면 [큐 가이드](../../../data-structures/linear/queue/queue-guide.mdx)를 보세요.
- **단순 경로와 음수 사이클.** 같은 정점을 두 번 지나지 않는 경로가 단순 경로이고, 정점이 `V` 개면 단순 경로는
  간선을 많아야 `V − 1` 개 지나요. 음수 사이클이 무엇이고 왜 최단 거리를 정하지 못하게 하는지도
  [`bellmanFord`](../bellmanFord/bellmanFord-guide.md) 가 다룹니다.
- **`Infinity` 와의 비교와 덧셈.** 아직 길을 못 찾은 상태를 `Infinity` 로 두면 「어떤 유한한 값도 그보다
  작다」가 그대로 성립합니다. 그래서 처음 값을 적는 갈래를 따로 쓰지 않아도 돼요.

이름이 비슷한 과제 넷을 나란히 두면 이 글이 다루는 범위가 갈립니다.

| 과제 | 그래프 | 이 글에서 |
| --- | --- | --- |
| 시작 정점 하나에서 모든 정점까지의 최단 거리 | 음수 가중치가 있어도 된다 · 시작 정점에서 갈 수 있는 음수 사이클은 없다 | 다룬다 |
| 같은 최단 거리와 음수 사이클 판정 | 음수 사이클이 있을 수 있다 | 판정은 변형으로만 보인다 — 함께 필요하면 [`bellmanFord`](../bellmanFord/bellmanFord-guide.md) |
| 시작 정점 하나에서 모든 정점까지의 최단 거리 | 가중치가 0 이상 | 다루지 않는다 — [`dijkstra`](../dijkstra/dijkstra-guide.md) |
| 시작 정점 하나에서 모든 정점까지의 최단 거리 | 사이클이 없다 · 음수 가중치가 있어도 된다 | 다루지 않는다 — [`dagShortestPath`](../dagShortestPath/dagShortestPath-guide.md) |

### 아이디어를 떠올리는 과정 — 경로 전부 나열하기에서 값이 줄어든 정점만 큐에 넣기까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 정점 수, 간선 목록, 시작 정점을 받아서
모든 정점까지의 최단 거리를 돌려줍니다.

```ts
function spfa(
  n: number,
  edges: [number, number, number][],
  src: number,
): number[];
```

- 입력: 정점 수 `n`, 원소가 `[u, v, w]` 인 방향 간선 목록 `edges`, 시작 정점 `src`. 정점 번호는 `0` 부터
  `n − 1` 이고, 가중치 `w` 는 음수일 수 있습니다. 간선이 목록에 적힌 차례는 입력이 정하고, 푸는 쪽이 고르지
  않아요.
- 출력: 길이 `n` 인 배열이고 `v` 번째 칸에 `src` 에서 `v` 까지의 최단 거리가 들어갑니다. 갈 수 없으면
  `Infinity` 예요.
- 전제: `src` 에서 갈 수 있는 음수 사이클은 없습니다. 이 전제가 깨지면 어떻게 되는지는 「아이디어 상세」의 「이
  방법이 기대는 전제」에서 봅니다.
- 규모: `1 ≤ V ≤ 500`, `0 ≤ E ≤ V(V−1)`, `−10^9 ≤ w ≤ 10^9`. 간선은 두 정점 사이에 방향마다 하나씩 둘 수 있는
  만큼까지 둡니다. 정점 수 500 은 이 글이 정한 값이에요 — 뒤에서 만들 절차도 최악에는 간선 읽기가 `V × E` 에
  이르러서, 그 곱이 흔한 채점 환경의 예산인 1 초(단순 연산 1 억 번 기준) 언저리에 머무는 정점 수를 골랐습니다.
  벨만-포드 편과 같은 규모라 두 편의 수를 그대로 나란히 놓을 수 있습니다.

이 글이 쓰는 기호는 여덟 개입니다. 여기서 정한 뜻을 글 끝까지 그대로 씁니다.

| 기호 | 무엇인가 | 이 과제에서 |
| --- | --- | --- |
| `V` | 정점의 개수. 코드의 `n` 입니다 | `1 ≤ V ≤ 500` |
| `E` | 간선의 개수. 코드의 `edges.length` 입니다 | `0 ≤ E ≤ V(V−1)` |
| `src` | 시작 정점의 번호 | `0 ≤ src ≤ V−1` |
| `u` · `v` | 정점 번호. 간선 `u → v` 를 읽는 자리에서 `u` 가 꼬리, `v` 가 머리입니다 | `0` 부터 `V−1` |
| `w` | 간선 `u → v` 의 가중치 | `−10^9 ≤ w ≤ 10^9` |
| `dist[v]` | 코드가 지금 들고 있는 값. `src` 에서 `v` 로 가는 **실재하는 경로 하나**의 비용입니다 | 길이 `V` 인 배열 |
| `opt(v)` | `src` 에서 `v` 까지의 **진짜 최단 거리**. `dist[v]` 가 끝내 같아져야 하는 값입니다 | 정점마다 하나 |
| `c(v)` | 정점 `v` 를 큐에 넣은 횟수. 처음 넣는 시작 정점도 한 번으로 셉니다 | `0` 이상의 정수 |

`dist[v]` 와 `opt(v)` 를 가르는 것이 이 글의 뼈대입니다. 앞은 지금까지 찾은 값이고 뒤는 그 값이 결국 같아져야 할
목표예요. 가장 먼저 떠오르는 방법은 정의를 그대로 옮기는 것입니다. 최단 거리는 경로의 비용 중 가장 작은 것이니,
**시작 정점에서 나가는 단순 경로를 전부 만들어** 도착 정점마다 가장 작은 비용을 고릅니다. 음수 가중치가 있어도
답은 맞아요. 간선이 가장 많은 그래프(완전 그래프)에서 그 경로가 몇 개인지 세었습니다.

<!--proof:naiveScale-->

| 정점 V | 간선 E | 단순 경로 수 | 센 방법 |
| ---: | ---: | --- | --- |
| 4 | 12 | 15 | 실행 |
| 6 | 30 | 325 | 실행 |
| 8 | 56 | 13,699 | 실행 |
| 10 | 90 | 986,409 | 실행 |
| 500 | 249,500 | 499! 이상 — 1,132 자리 수 | 식 |

정점 10 개 완전 그래프에서 단순 경로가 986,409 개입니다. 정점이 V 개인 완전 그래프는 출발점을 뺀 V−1 개를 모두 지나는 경로만 해도 (V−1)! 개라, 마지막 줄은 V = 500 을 그 식에 넣은 값입니다.

<!--/proof-->

정점 열 개에서 벌써 백만 개에 가깝고, 규모의 상한에서는 경로 수가 천 자리를 넘습니다. 경로를 하나하나 고르는
대신 **정점마다 값 하나를 들고 완화를 되풀이해야** 해요. 그 방법을 이미 하나 알고 있습니다. 「전체 컨셉」의
라운드 표가 벨만-포드였고, 전개 입력에서 간선 읽기 24 번 가운데 16 번이 아무것도 못 고쳤어요. 마지막 라운드가
간선마다 무엇을 했는지 펼쳐 봅시다.

<!--proof:originRound3-->

| 간선 | dist[u] + w | 그때 dist[v] | 비교 | 한 일 |
| --- | --- | --- | --- | --- |
| 0→1 | 0 + 6 = 6 | -2 | 크다 | 그대로 |
| 0→2 | 0 + 1 = 1 | 1 | 같다 | 그대로 |
| 0→3 | 0 + 20 = 20 | 2 | 크다 | 그대로 |
| 1→3 | -2 + 4 = 2 | 2 | 같다 | 그대로 |
| 2→1 | 1 + (-3) = -2 | -2 | 같다 | 그대로 |
| 2→3 | 1 + 9 = 10 | 2 | 크다 | 그대로 |
| 3→4 | 2 + 2 = 4 | 4 | 같다 | 그대로 |
| 5→4 | dist[5] 가 Infinity | 4 | 이을 경로가 없다 | 그대로 |

라운드 3 은 간선 8 개를 읽었고 그중 값을 고치지 못한 읽기가 8 개입니다.

<!--/proof-->

비교가 전부 「크다」·「같다」로 끝났습니다. 이 여덟 번이 헛수고라는 것을 라운드 3 을 실행하기 전에 알 수 있었을까요?
「전체 컨셉」의 라운드 표에서 라운드 2 가 고친 칸은 `dist[3]` 과 `dist[4]` 둘뿐이었어요. 그러면 라운드 3 에서
결과가 달라질 수 있는 간선은 꼬리가 3 이나 4 인 간선, 곧 `3 → 4` 하나뿐입니다. 나머지 일곱 간선은 꼬리의 값이
라운드 2 와 같으니 비교 결과도 같아요. 같은 입력을 세 방식으로 처리하고 계수를 나란히 놓았습니다.

<!--proof:originWaste-->

| 방식 | 간선 읽기 | 값을 고친 읽기 | 아무것도 안 고친 읽기 | 결과 dist |
| --- | ---: | ---: | ---: | --- |
| 라운드를 V−1 = 5 번 다 읽는다 | 40 | 8 | 32 | [0, -2, 1, 2, 4, Infinity] |
| 못 고친 라운드가 나오면 멈춘다(벨만-포드) | 24 | 8 | 16 | [0, -2, 1, 2, 4, Infinity] |
| 값이 바뀐 정점의 간선만 다시 읽는다 | 9 | 8 | 1 | [0, -2, 1, 2, 4, Infinity] |

세 방식의 결과 dist 는 서로 같고, 값을 고친 읽기는 셋 다 8 번입니다.

<!--/proof-->

값을 고친 읽기는 셋이 같고, 갈리는 것은 아무것도 안 고친 읽기뿐입니다. 벨만-포드는 가운데 줄이에요. 라운드가
끝날 때 **「고친 칸이 있었다」 한 가지만 남기고**(`changed`), 그 한 가지로는 다음 라운드를 멈출지 말지만 정합니다.
멈추지 않기로 하면 다음 라운드는 다시 목록 전체를 읽어요. 그 차이가 입력의 모양에 따라 얼마나 벌어지는지 세
모양에서 재어 봤습니다.

<!--proof:originFlag-->

| 입력 | 간선 E | 라운드 | 벨만-포드의 간선 읽기 | 정점을 남긴 방법의 간선 읽기 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 | 8 | 3 | 24 | 9 |
| 사슬 V = 64, 목록을 내림차순으로 | 63 | 63 | 3,969 | 63 |
| 완전 그래프 V = 64 | 4,032 | 2 | 8,064 | 4,032 |

<!--/proof-->

내림차순으로 적은 사슬에서 차이가 가장 큽니다. 라운드마다 사슬이 한 칸씩만 늘어나 라운드가 63 번 실행되는데,
라운드마다 간선 63 개를 모두 읽어요. 정점을 남긴 방법은 라운드 하나에 바뀐 정점이 하나뿐이니 간선도 하나씩만
읽습니다. 완전 그래프에서도 벨만-포드는 둘째 라운드가 고칠 것이 없다는 것을 확인하느라 간선 4,032 개를 한 번 더
읽고요. **「고친 칸이 있었다」는 멈출 때를 알려 줄 뿐, 다음에 무엇을 읽을지는 알려 주지 않습니다.** 그러니 무엇이
바뀌었는지, 곧 **값이 줄어든 정점 자체**를 남겨 두고 그 정점의 간선만 다시 읽어야 해요. 지금까지 해 본 방법을
차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법에 이름을 붙이면 **값이 줄어든 정점만 큐에 넣어 그 간선만 다시 읽기**입니다. 값이 줄어든 정점을 큐에
넣고, 하나씩 꺼내 그 정점에서 나가는 간선만 완화하며, 큐가 비면 끝내요. 정점을 어떤 차례로 꺼내는지, 같은 정점이
두 번 줄면 어떻게 하는지, 큐가 반드시 비는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 값이 줄어든 정점만 큐에 넣어 그 간선만 다시 읽기

이 아이디어를 한 문장으로 줄이면 이렇습니다. **이웃 목록을 만들어 두고, 시작 정점을 큐에 넣은 뒤, 큐에서 정점
하나를 꺼내 그 정점의 간선만 완화하고 값이 줄어든 정점을 큐 뒤에 넣는 일을 큐가 빌 때까지 되풀이합니다.** 이
방법이 몇 번 만에 끝나는지, 음수 사이클이 있으면 어떻게 알아보는지는 「큐를 꺼내는 동안 한 정점이 몇 번 들어오는가」
에 달려 있는데, 그것을 셀 때 쓰는 **큐의 묶음**이 처음 보면 낯설어요. 그래서 그것을 먼저 따로 설명하고, 그다음
실현하는 순서대로 다섯 단계를 설명합니다.

| 언제 | 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- | --- |
| 시작할 때 한 번 | 1단계 이웃 목록 만들기 | 간선 목록을 꼬리 정점별로 모은다 | — |
| 시작할 때 한 번 | 2단계 시작값 적고 큐 준비하기 | `dist` · `inQueue` · 큐를 만들고 시작 정점을 넣는다 | — |
| 꺼낼 때마다 | 3단계 정점 하나 꺼내 그 간선만 완화하기 | 큐에서 하나 꺼내 표시를 내리고 그 정점의 간선을 완화한다 | 1단계의 이웃 목록 · 2단계의 큐 |
| 값을 고칠 때마다 | 4단계 값이 줄어든 정점을 큐에 넣기 | 큐에 없으면 넣고, 이미 있으면 넣지 않는다 | 3단계가 고친 칸 · 2단계의 `inQueue` |
| 꺼내기 전마다 | 5단계 큐가 비면 끝내기 | 큐가 비었으면 `dist` 를 돌려준다 | 4단계가 넣은 큐 |

#### 먼저 알아 둘 개념 — 큐의 묶음

**큐의 묶음**은 큐에 들어온 정점을 **누가 넣었는가**로 가른 것입니다. 묶음 0 은 처음 넣은 시작 정점 하나이고,
묶음 `k` 의 정점을 꺼내는 동안 큐에 새로 넣은 정점들이 묶음 `k+1` 이에요. 큐는 먼저 넣은 것을 먼저 꺼내므로,
묶음 `k` 를 다 꺼내기 전에는 묶음 `k+1` 의 정점이 나오지 않습니다. 그래서 큐에서는 묶음 0, 1, 2, … 가 차례로
이어서 나와요.

##### 입력 위의 묶음

전개 입력에서 묶음마다 한 장씩 그렸습니다. 무대 아래 띠는 큐에 들어온 정점을 넣은 차례대로 전부 늘어놓은 것이고,
옅은 채움 칸이 이 묶음, 굵은 테 칸이 이 묶음이 넣은 다음 묶음이에요. 정점 안의 값은 이 묶음을 다 꺼낸 뒤의
`dist` 입니다.

<!--fig:build-waves-->
![묶음 k = 0 … 4 — 띠의 옅은 채움 칸이 이 묶음, 굵은 테 칸이 이 묶음이 넣은 다음 묶음](./figs/build-waves.svg)

같은 값을 묶음마다 한 줄로 모으면 이렇습니다.

<!--proof:waveTable-->

| 묶음 k | 꺼낸 정점 | 걸음 | 이 묶음이 큐에 넣은 정점 | 묶음을 다 꺼낸 뒤 dist |
| ---: | --- | --- | --- | --- |
| 0 | 0 | T2 | 1 · 2 · 3 | [0, 6, 1, 20, Infinity, Infinity] |
| 1 | 1 · 2 · 3 | T3 · T4 · T5 | 1 · 4 | [0, -2, 1, 10, 12, Infinity] |
| 2 | 1 · 4 | T6 · T7 | 3 | [0, -2, 1, 2, 12, Infinity] |
| 3 | 3 | T8 | 4 | [0, -2, 1, 2, 4, Infinity] |
| 4 | 4 | T9 | 없다 | [0, -2, 1, 2, 4, Infinity] |

묶음이 5 개이고, 꺼내기 8 번이 그 묶음들에 빠짐없이 나뉘었습니다.

<!--/proof-->

##### 묶음 하나를 읽는 법

묶음 하나를 골라 그 안의 정점이 왜 거기 들었는지 따라가 봅시다. 묶음 2 는 정점 1 과 4 입니다.

<!--proof:waveRead-->

| 정점 | 넣은 걸음 | 넣게 한 완화 | dist 의 변화 | 그 전에 |
| --- | --- | --- | --- | --- |
| 1 | T4 | 2→1 이 1 + (-3) = -2 | 6 → -2 | 이미 꺼냈다 |
| 4 | T5 | 3→4 가 10 + 2 = 12 | Infinity → 12 | 처음 넣는다 |

묶음 2 의 정점 2 개는 모두 묶음 1 의 정점을 꺼내는 동안 값이 줄어 들어왔습니다.

<!--/proof-->

정점 1 은 묶음 1 에서 이미 한 번 꺼낸 정점이에요. 그 뒤에 같은 묶음 1 의 정점 2 가 `2 → 1` 로 값을 6 에서 −2 로
줄였고, 줄어든 값으로 `1 → 3` 을 다시 읽어야 하니 큐에 다시 들어왔습니다. 정점 4 는 처음 값을 얻어 처음 들어온
경우고요. 어느 쪽이든 **묶음 `k+1` 의 정점은 묶음 `k` 의 정점이 간선 하나로 값을 줄인 정점**입니다.

##### 묶음과 묶음 사이

정점마다 어느 묶음에 들었는지 모으면 이렇습니다.

<!--proof:waveMembers-->

| 정점 | 든 묶음 | 넣은 횟수 c(v) |
| --- | --- | ---: |
| 0 | 0 | 1 |
| 1 | 1 · 2 | 2 |
| 2 | 1 | 1 |
| 3 | 1 · 3 | 2 |
| 4 | 2 · 4 | 2 |
| 5 | 없다 | 0 |

한 묶음 안에 같은 정점이 두 번 든 자리는 없고, 넣은 횟수가 가장 큰 정점도 2 번입니다.

<!--/proof-->

한 정점이 **한 묶음에는 많아야 한 번** 듭니다. 묶음 `k` 를 꺼내는 동안 정점 `v` 를 넣으려면 `v` 가 그때 큐에
없어야 하는데, 한 번 넣은 `v` 는 묶음 `k+1` 을 꺼낼 때까지 큐에 남아 있으니 같은 묶음에 두 번 들어갈 수 없어요.
그래서 **`c(v)` 는 `v` 가 든 묶음의 개수와 같습니다.** 정점 1 · 3 · 4 가 묶음 둘에 들어 `c(v) = 2` 이고, 정점 5 는
어느 묶음에도 들지 않아 `c(5) = 0` 이에요.

##### 라운드 · 층과의 차이

묶음을 처음 보면 「묶음 `k` 는 벨만-포드의 라운드 `k+1` 과 같다」고 읽기 쉽습니다. 둘 다 앞 단계에서 바뀐 값을 받아
한 번 더 완화하니까요. 다른 점이 둘 있어요. 하나는 **읽는 간선**입니다. 라운드는 목록의 간선을 모두 읽고, 묶음은 그
묶음에 든 정점의 간선만 읽어요. 다른 하나는 **값이 어디까지 내려가는가**입니다. 간선을 `k` 개 이하로 쓰는 최단 비용
`opt_k(v)`, 곧 층 `k` 와 나란히 놓았습니다.

<!--proof:waveVsLayer-->

| 묶음 k | 묶음 k 를 다 꺼낸 뒤 dist | 층 k+1 의 opt | 층과의 관계 |
| ---: | --- | --- | --- |
| 0 | [0, 6, 1, 20, Infinity, Infinity] | [0, 6, 1, 20, Infinity, Infinity] | 칸마다 같다 |
| 1 | [0, -2, 1, 10, 12, Infinity] | [0, -2, 1, 10, 22, Infinity] | 더 작은 칸이 있다 |
| 2 | [0, -2, 1, 2, 12, Infinity] | [0, -2, 1, 2, 12, Infinity] | 칸마다 같다 |
| 3 | [0, -2, 1, 2, 4, Infinity] | [0, -2, 1, 2, 4, Infinity] | 칸마다 같다 |
| 4 | [0, -2, 1, 2, 4, Infinity] | [0, -2, 1, 2, 4, Infinity] | 칸마다 같다 |

묶음 1 을 다 꺼낸 뒤 dist[4] 는 12, opt_2(4) 는 22 입니다.

<!--/proof-->

묶음 1 이 끝났을 때 `dist[4]` 는 벌써 12 인데, 간선을 둘까지만 쓰는 비용 `opt_2(4)` 는 22 예요. 묶음 1 은 정점 1 ·
2 · 3 을 이 차례로 꺼내는데, 정점 3 을 꺼낼 때 `dist[3]` 은 같은 묶음 안에서 이미 20 에서 10 으로 고쳐져 있었습니다.
그 10 으로 `3 → 4` 를 읽었으니 층보다 한 걸음 더 간 것이에요. 그래서 둘의 관계는 「같다」가 아니라 「**묶음 `k` 를
다 꺼낸 뒤의 `dist[v]` 는 `opt_{k+1}(v)` 보다 크지 않다**」입니다.

이 관계가 모든 입력에서 성립하는 까닭을 귀납으로 적습니다. **기저** — 묶음 0 은 시작 정점 하나이고, 그 정점을
꺼내 나가는 간선을 모두 완화하므로 간선 하나짜리 경로가 모두 반영돼 `dist[v] ≤ opt_1(v)` 입니다. **단계** — 묶음
`k−1` 을 다 꺼낸 뒤 `dist ≤ opt_k` 라고 합시다. `opt_{k+1}(v)` 가 `opt_k(v)` 와 같으면 값은 줄기만 하니 그대로
성립해요. 더 작다면 어떤 간선 `u → v` 가 있어 `opt_{k+1}(v) = opt_k(u) + w` 입니다. `dist[u]` 가 `opt_k(u)` 이하로
마지막으로 줄어든 때는 묶음 `k−1` 을 다 꺼내기 전이고, 그 순간 `u` 는 큐에 새로 들어가거나 이미 큐에 있었으니 묶음
`k` 이하에 들어 있습니다. 그러면 묶음 `k` 를 다 꺼내기 전에 `u` 가 그 값으로 꺼내져 `u → v` 를 완화하고,
`dist[v] ≤ opt_k(u) + w = opt_{k+1}(v)` 가 남아요.

##### 묶음이 끝나는 자리

묶음을 세운 까닭은 **한 정점이 큐에 몇 번까지 들어오는지**를 셀 수 있어서입니다. 음수 사이클이 없으면 최단 경로는
간선을 많아야 `V − 1` 개 쓰므로 `opt_{V−1} = opt` 입니다. 위의 관계에 넣으면 묶음 `V−2` 를 다 꺼낸 뒤 `dist ≤ opt`
이고, `dist` 는 늘 실재하는 경로의 비용이라 `opt` 보다 작아질 수 없으니 `dist = opt` 예요. 그러면 묶음 `V−1` 의
정점을 꺼내도 더 줄 값이 없어 묶음 `V` 는 비어 있습니다. 묶음은 0 부터 `V−1` 까지 많아야 `V` 개이고, 한 정점은 한
묶음에 많아야 한 번 드니 **`c(v) ≤ V − 1`** 입니다(시작 정점은 값 0 이 더 줄지 않아 한 번뿐이에요). 여러 입력에서
재었습니다.

<!--proof:waveStop-->

| 입력 | 정점 V | 묶음 수 | 넣은 횟수의 최댓값 | V − 1 과의 관계 |
| --- | ---: | ---: | ---: | --- |
| 전개 입력 | 6 | 5 | 2 | 넘지 않는다 |
| 사슬 V = 64, 목록을 내림차순으로 | 64 | 64 | 1 | 넘지 않는다 |
| 완전 그래프 V = 64 | 64 | 2 | 1 | 넘지 않는다 |
| 사슬이 허브로 들어가는 모양 V = 64 | 64 | 34 | 16 | 넘지 않는다 |

네 입력 모두 음수 사이클이 없고, 묶음 수가 정점 수 V 를 넘지 않았습니다.

<!--/proof-->

넷 모두 넣은 횟수가 `V − 1` 을 넘지 않았어요. 이 상한이 뒤에서 두 번 쓰입니다. 음수 사이클을 넣은 횟수로 판정하는
자리(「이 방법이 기대는 전제」)와, 간선 읽기의 상한을 닫는 자리(파트 2 의 「수식 정의와 유도」)예요. 그리고 이 상한은
**큐가 먼저 넣은 것을 먼저 꺼낼 때만** 성립합니다. 그 까닭은 「먼저 넣은 정점을 먼저 꺼내는 까닭」에서 값으로
봅니다.

| 묶음의 성질 | 까닭 | 이 절차에서 쓰이는 곳 |
| --- | --- | --- |
| 한 정점은 한 묶음에 많아야 한 번 든다 | 넣은 정점은 다음 묶음을 꺼낼 때까지 큐에 있다 | `c(v)` 는 든 묶음의 개수다 |
| 묶음 `k` 뒤의 `dist` 는 층 `k+1` 보다 크지 않다 | 앞 묶음이 줄인 정점은 다음 묶음까지 꺼내진다 | 묶음 수의 상한 |
| 음수 사이클이 없으면 묶음은 많아야 `V` 개다 | 층 `V−1` 이 `opt` 다 | `c(v) ≤ V − 1` · 넣은 횟수로 하는 판정 |

#### 1단계 — 이웃 목록 만들기

이 절차는 「꺼낸 정점에서 나가는 간선」을 꺼낼 때마다 찾습니다. 간선 목록만 있으면 그때마다 목록 전체를 읽어야
하니, 시작할 때 한 번 간선 목록을 꼬리 정점별로 모아 둡니다. 전개 입력에서 모으면 이렇습니다.

<!--proof:stageAdj-->

| 정점 | adj — (머리, 가중치) | 간선 목록에서의 차례 | 나가는 간선 수 |
| --- | --- | --- | ---: |
| 0 | (1, 6) (2, 1) (3, 20) | 1 · 2 · 3 | 3 |
| 1 | (3, 4) | 4 | 1 |
| 2 | (1, -3) (3, 9) | 5 · 6 | 2 |
| 3 | (4, 2) | 7 | 1 |
| 4 | 없다 | — | 0 |
| 5 | (4, 1) | 8 | 1 |

이웃 목록이 없으면 정점을 꺼낼 때마다 간선 8 개를 모두 읽어야 해서 꺼내기 8 번에 64 번을 읽고, 있으면 9 번을 읽습니다.

<!--/proof-->

`adj[u]` 에는 간선 `u → v` 의 머리 `v` 와 가중치 `w` 만 남기고, 간선 목록에 적힌 차례를 그대로 지켜요. 정점 0 의
세 간선이 목록 앞의 세 칸에서 왔습니다. 이웃 목록을 만드는 데는 간선 `E` 개를 한 번씩 읽어요.

#### 2단계 — 시작값 적고 큐 준비하기

거리 배열 `dist` 를 전부 `Infinity` 로 채우고 시작 정점만 0 을 적습니다. 그리고 큐를 시작 정점 하나로 만들고,
정점마다 「지금 큐 안에 있는가」를 적는 **큐 표시** `inQueue` 를 둬요. 큐는 배열 `queue` 와 다음에 꺼낼 자리 `head`
로 적습니다.

<!--proof:stageStart-->

| 정점 | dist | inQueue |
| ---: | --- | --- |
| 0 | 0 | true |
| 1 | Infinity | false |
| 2 | Infinity | false |
| 3 | Infinity | false |
| 4 | Infinity | false |
| 5 | Infinity | false |

큐는 [0] 이고 head = 0 입니다. 값이 있는 칸은 dist[0] = 0 하나입니다.

<!--/proof-->

`inQueue` 가 필요한 까닭은 4단계에서 「이 정점이 이미 큐에 있는가」를 한 번에 알아야 하기 때문입니다. 큐를 앞에서부터
읽어 찾으면 넣을 때마다 큐 길이만큼 읽어야 해요. `head` 를 둔 까닭은 꺼낼 때 배열 앞을 지우고 나머지를 당기는 대신
정수 하나만 올리려는 것입니다.

#### 3단계 — 정점 하나 꺼내 그 간선만 완화하기

큐에서 `head` 자리의 정점 `u` 를 꺼내고 `head` 를 하나 올립니다. 꺼낸 그 자리에서 `inQueue[u]` 를 거짓으로 내리고,
`adj[u]` 의 간선만 완화해요. 가장 쉬운 경우는 처음 꺼내는 시작 정점입니다. 정점 0 을 꺼낸 걸음이 간선 목록의 각
간선에 한 일을 적으면 이렇습니다.

<!--proof:stagePop-->

| 차례 | 간선 | 정점 0 을 꺼낸 걸음에서 | dist[u] + w | 한 일 |
| ---: | --- | --- | --- | --- |
| 1 | 0→1 | 읽는다 | 0 + 6 = 6 | dist[1] = 6 |
| 2 | 0→2 | 읽는다 | 0 + 1 = 1 | dist[2] = 1 |
| 3 | 0→3 | 읽는다 | 0 + 20 = 20 | dist[3] = 20 |
| 4 | 1→3 | 읽지 않는다 | — | — |
| 5 | 2→1 | 읽지 않는다 | — | — |
| 6 | 2→3 | 읽지 않는다 | — | — |
| 7 | 3→4 | 읽지 않는다 | — | — |
| 8 | 5→4 | 읽지 않는다 | — | — |

간선 8 개 중 3 개를 읽었고, 걸음이 끝난 dist 는 [0, 6, 1, 20, Infinity, Infinity] · 큐는 [1, 2, 3] 입니다.

<!--/proof-->

간선 목록의 나머지 다섯은 **읽지도 않습니다.** 꼬리 정점 1 · 2 · 3 · 5 가 아직 한 번도 꺼내지지 않았기 때문이에요.
라운드 방식이라면 이 다섯도 읽고 「꼬리의 값이 없다」로 넘어갔을 자리입니다. 표시를 꺼낸 그 자리에서 내리는 까닭은
4단계와 맞물려 있어서, 「수행으로 알아보는 알고리즘」의 첫 짚고 가기에서 그 줄을 빼 보고 확인합니다.

#### 4단계 — 값이 줄어든 정점을 큐에 넣기

완화가 `dist[v]` 를 고쳤으면 `v` 에서 나가는 간선을 다시 읽어야 합니다. 그 일을 큐에 예약하는 것이 이 단계예요.
`inQueue[v]` 가 거짓이면 `v` 를 큐 뒤에 넣고 표시를 세우고, 참이면 넣지 않습니다. 쉬운 경우는 처음 값을 얻은 정점이고,
불안한 경우는 **이미 큐에 있는 정점**과 **이미 꺼낸 정점**의 값이 다시 줄 때예요. 전개 입력에서 값을 고친 자리를 모두
적었습니다.

<!--proof:stageReentry-->

| 걸음 | 꺼낸 정점 | 고친 칸 | 그 정점의 자리 | ⑥ | 걸음이 끝난 큐 |
| --- | --- | --- | --- | --- | --- |
| T2 | 0 | dist[1] Infinity → 6 | 넣은 적이 없다 | 넣는다 | [1, 2, 3] |
| T2 | 0 | dist[2] Infinity → 1 | 넣은 적이 없다 | 넣는다 | [1, 2, 3] |
| T2 | 0 | dist[3] Infinity → 20 | 넣은 적이 없다 | 넣는다 | [1, 2, 3] |
| T3 | 1 | dist[3] 20 → 10 | 큐 안에 있다 | 안 넣는다 | [2, 3] |
| T4 | 2 | dist[1] 6 → -2 | 꺼낸 적이 있고 큐 밖이다 | 넣는다 | [3, 1] |
| T5 | 3 | dist[4] Infinity → 12 | 넣은 적이 없다 | 넣는다 | [1, 4] |
| T6 | 1 | dist[3] 10 → 2 | 꺼낸 적이 있고 큐 밖이다 | 넣는다 | [4, 3] |
| T8 | 3 | dist[4] 12 → 4 | 꺼낸 적이 있고 큐 밖이다 | 넣는다 | [4] |

값을 고친 8 번 가운데 이미 큐 안에 있어 넣지 않은 것이 1 번이고, 꺼낸 적이 있는 정점을 다시 넣은 것이 3 번입니다. 큐가 가장 길었을 때는 3 개입니다.

<!--/proof-->

T3 이 이미 큐에 있는 경우입니다. `dist[3]` 이 20 에서 10 으로 줄었는데 정점 3 은 아직 큐 `[2, 3]` 안에 있어요. 넣지
않아도 되는 까닭은 정점 3 이 꺼내질 때 그때의 `dist[3]`, 곧 10 을 읽기 때문입니다. 두 벌을 넣어 봐야 같은 정점을 같은
값으로 두 번 처리할 뿐이에요. T4 가 이미 꺼낸 경우입니다. `dist[1]` 이 6 에서 −2 로 줄었는데 정점 1 은 T3 에서 꺼내
6 으로 `1 → 3` 을 읽은 뒤라 큐에 없어요. 다시 넣지 않으면 −2 로 `1 → 3` 을 읽을 기회가 없으니 넣습니다. 실제로 T6 이
그 정점을 꺼내 `dist[3]` 을 10 에서 2 로 줄여요.

| 값을 고친 정점의 자리 | ⑥ `!inQueue[v]` | 넣는가 | 까닭 |
| --- | --- | --- | --- |
| 넣은 적이 없다 | 참 | 넣는다 | 새 값으로 나가는 간선을 읽어야 한다 |
| 큐 안에 있다 | 거짓 | 넣지 않는다 | 꺼낼 때 그때의 값을 읽는다 |
| 꺼낸 적이 있고 큐 밖이다 | 참 | 넣는다 | 옛 값으로 읽은 간선을 새 값으로 다시 읽어야 한다 |

#### 5단계 — 큐가 비면 끝내기

`head` 가 `queue.length` 에 이르면 큐가 빈 것이고, 거기서 `dist` 를 돌려줍니다. 큐가 비었다는 것은 값이 줄어 아직
간선을 다시 읽지 않은 정점이 하나도 없다는 뜻이에요. 전개 입력에서 큐가 빈 뒤 간선마다 완화 조건을 다시 대 보면
이렇습니다.

<!--proof:stageEnd-->

| 간선 | dist[u] + w | dist[v] | 비교 |
| --- | --- | --- | --- |
| 0→1 | 0 + 6 = 6 | -2 | 크다 |
| 0→2 | 0 + 1 = 1 | 1 | 같다 |
| 0→3 | 0 + 20 = 20 | 2 | 크다 |
| 1→3 | -2 + 4 = 2 | 2 | 같다 |
| 2→1 | 1 + (-3) = -2 | -2 | 같다 |
| 2→3 | 1 + 9 = 10 | 2 | 크다 |
| 3→4 | 2 + 2 = 4 | 4 | 같다 |
| 5→4 | dist[5] 가 Infinity | 4 | 이을 경로가 없다 |

큐가 빈 뒤 dist[u] + w 가 dist[v] 보다 작은 간선은 0 개입니다.

<!--/proof-->

모든 간선이 `dist[u] + w ≥ dist[v]` 를 만족합니다. 이 조건이 모든 간선에서 성립하면 어떤 경로를 따라가도 비용이
`dist[v]` 보다 작아질 수 없어요. 경로의 간선마다 이 부등식을 더하면 가운데 항이 지워지고
`dist[src] + (경로의 비용) ≥ dist[v]` 가 남기 때문입니다. `dist[src] = 0` 이니 `dist[v]` 는 어떤 경로의 비용보다도
크지 않고, `dist[v]` 자체가 실재하는 경로의 비용이니 `dist[v] = opt(v)` 예요. 「값이 줄어든 정점은 반드시 큐에
있다」가 매 걸음 참으로 남는 까닭은 파트 2 의 「불변식」에서 따집니다.

#### 이 방법이 기대는 전제

5단계의 결론은 **큐가 언젠가 빈다**는 데 기대고, 그것은 **시작 정점에서 갈 수 있는 음수 사이클이 없을 때** 성립합니다.
음수 사이클이 있으면 그 순환을 한 번 더 지날 때마다 값이 줄어 고칠 자리가 끝나지 않아요. 음수 사이클 `0 → 1 → 2 → 0`
에 꺼낸 횟수 상한을 두고 실행했습니다.

<!--proof:premiseCycle-->

| 꺼낸 횟수 상한 | 그때의 dist | 큐 | 넣은 횟수의 최댓값 |
| ---: | --- | --- | ---: |
| 3 | [-1, 1, 0] | 남아 있다 | 2 |
| 6 | [-2, 0, -1] | 남아 있다 | 3 |
| 30 | [-10, -8, -9] | 남아 있다 | 11 |
| 300 | [-100, -98, -99] | 남아 있다 | 101 |
| 3,000 | [-1000, -998, -999] | 남아 있다 | 1001 |

음수 사이클 0→1→2→0 을 넣고 꺼낸 횟수에 상한을 두고 멈췄습니다. 상한을 늘릴수록 dist 가 더 내려가고, 큐는 한 번도 비지 않았습니다.

<!--/proof-->

정본은 이 전제를 **확인하지 않습니다.** 과제가 음수 사이클이 없다고 정해 두었기 때문이고, 전제가 깨진 입력을 넣으면
정본의 `while` 은 끝나지 않아요. 전제를 확인해야 하는 쓰임에서는 「큐의 묶음」의 상한 `c(v) ≤ V − 1` 을 거꾸로 씁니다.
음수 사이클이 없으면 넣은 횟수가 `V − 1` 을 넘지 않으니, **넣은 횟수가 `V` 에 이르는 정점이 나오면 음수 사이클이
있다**고 판정해요. 정본의 4단계에 두 줄을 더한 변형입니다.

```ts
if (!inQueue[v]) {
  cnt[v]++;                                            // 넣은 횟수 c(v)
  if (cnt[v] >= n) return { dist, hasNegativeCycle: true };
  inQueue[v] = true;
  queue.push(v);
}
```

`cnt` 는 시작 정점을 넣을 때 1 로 시작합니다. 이 변형을 세 입력에 실행했어요.

<!--proof:premiseDetect-->

| 입력 | 정점 V | 넣은 횟수의 최댓값 | 꺼낸 횟수 | 멈춘 자리 | hasNegativeCycle |
| --- | ---: | ---: | ---: | --- | --- |
| 전개 입력 | 6 | 2 | 8 | 끝까지 비었다 | false |
| 음수 사이클 0→1→2→0 | 3 | 3 | 6 | 정점 0 을 3 번째로 넣으려 할 때 | true |
| 도달할 수 없는 음수 사이클 1→2→1 | 3 | 1 | 1 | 끝까지 비었다 | false |

<!--/proof-->

음수 사이클 입력에서는 정점 0 의 넣은 횟수가 `V = 3` 에 이르는 자리에서 멈췄고, 전개 입력은 넣은 횟수가 가장 큰 정점도
2 번이라 끝까지 비었습니다. 도달할 수 없는 음수 사이클은 그 정점들이 큐에 한 번도 들지 않아 판정에 걸리지 않아요.
벨만-포드가 `V` 번째 라운드가 값을 고치는가로 판정한 것과 같은 상한을, 이 절차는 정점마다 넣은 횟수로 씁니다.

| 전제 | 쓰이는 곳 | 깨지면 |
| --- | --- | --- |
| 시작 정점에서 갈 수 있는 음수 사이클이 없다 | 5단계 — 큐가 언젠가 빈다 | 큐가 비지 않는다 — 넣은 횟수를 세는 변형이 판정으로 바꾼다 |
| 큐가 먼저 넣은 것을 먼저 꺼낸다 | 「큐의 묶음」의 상한 `c(v) ≤ V − 1` | 답은 같지만 넣은 횟수가 `V − 1` 을 넘을 수 있다 — 아래에서 본다 |

#### 먼저 넣은 정점을 먼저 꺼내는 까닭

4단계까지는 정점을 **어떤 차례로 꺼내든** 답이 같습니다. 꺼낼 때마다 그때의 `dist` 를 읽고, 값이 줄면 다시 넣으니까요.
그러면 큐 대신 나중에 넣은 것을 먼저 꺼내는 **스택**을 써도 될까요? 네 입력에서 둘을 나란히 실행해 간선 읽기와 넣은
횟수의 최댓값을 세었습니다. 「번호 차의 제곱 그래프」는 앞 번호에서 뒤 번호로 가는 간선을 모두 두고 가중치를 번호
차의 제곱으로 둔 그래프예요. 간선을 잘게 나눠 갈수록 비용이 작아집니다.

<!--proof:designOrder-->

| 입력 | 간선 E | 큐 — 간선 읽기 · 넣은 횟수 최댓값 | 스택 — 간선 읽기 · 넣은 횟수 최댓값 | V − 1 |
| --- | ---: | --- | --- | ---: |
| 전개 입력 | 8 | 9 · 2 | 9 · 3 | 5 |
| 완전 그래프 V = 64 | 4,032 | 4,032 · 1 | 4,032 · 1 | 63 |
| 번호 차의 제곱 그래프 V = 12 | 66 | 66 · 1 | 356 · 32 | 11 |
| 번호 차의 제곱 그래프 V = 20 | 190 | 190 · 1 | 2,961 · 104 | 19 |

네 입력 모두 두 차례의 답 dist 가 같았습니다.

<!--/proof-->

전개 입력과 완전 그래프에서는 두 차례가 거의 같은데, 번호 차의 제곱 그래프에서는 스택이 정점 20 개에 간선 읽기
2,961 번으로 큐의 190 번보다 열다섯 배 넘게 많습니다. 그리고 **스택에서는 한 정점을 104 번 넣어 `V − 1 = 19` 를
넘었어요.** 음수 사이클이 없는데도 넣은 횟수로 하는 판정이 음수 사이클이 있다고 잘못 말하게 됩니다. 스택은 방금 줄인
정점을 바로 꺼내 그 뒤를 깊이 따라가다가, 앞에서 더 작은 값이 들어오면 같은 길을 처음부터 다시 따라가기 때문이에요.
큐는 묶음 하나를 다 꺼낸 뒤에 다음 묶음으로 가므로 「큐의 묶음」의 상한이 성립합니다. 그래서 이 절차는 먼저 넣은
것을 먼저 꺼냅니다.

#### 다섯 단계를 이은 절차

다섯 단계를 코드의 순서로 다시 적으면 여섯 걸음이 됩니다. 넷째부터 여섯째가 꺼내기 한 번이에요.

1. 간선 목록을 꼬리 정점별로 모아 `adj` 를 만든다
2. `dist` 를 `Infinity` 로 채우고 `dist[src] = 0` 을 적는다
3. `queue = [src]`, `inQueue[src] = true`, `head = 0` 으로 큐를 만든다
4. `head < queue.length` 인 동안 `u = queue[head++]` 를 꺼내 `inQueue[u] = false` 로 내린다
5. `adj[u]` 의 간선 `(v, w)` 마다 `dist[u] + w < dist[v]` 면 `dist[v]` 를 고친다
6. 고친 `v` 가 큐에 없으면 넣고 표시를 세우며, 큐가 비면 `dist` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 정점 여섯을 여덟 번 꺼내 열 걸음으로 끝낸다

아이디어를 확인했으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 그래프 하나를 정해 끝까지 가져가되, 코드 조각을
하나 만들 때마다 그 조각만 실행한 결과를 확인하고 다음으로 넘어갑니다.

<!--proof:walkInput-->

```ts
const n = 6;
const edges: [number, number, number][] = [
  [0, 1, 6], [0, 2, 1], [0, 3, 20], [1, 3, 4],
  [2, 1, -3], [2, 3, 9], [3, 4, 2], [5, 4, 1],
];
const src = 0;
// 이 절이 끝나면 나와야 하는 값: [0, -2, 1, 2, 4, Infinity]
```

왜 이 여덟 간선일까요? 여섯 갈래를 한 입력에서 전부 실행하려고 고른 그래프이기 때문이에요. `0 → 3` 이 있어서 「값이
줄었지만 이미 큐에 있어 넣지 않는」 자리가 나오고, `2 → 1` 이 있어서 「이미 꺼낸 정점이 다시 들어오는」 자리가
나옵니다. 정점 5 는 들어오는 간선이 없어 `Infinity` 로 남고, `5 → 4` 는 한 번도 읽히지 않아요.

```text
절차 전체를 한 장으로

  T1     간선 목록을 꼬리 정점별로 모은다                        ① 이웃 목록
         dist 를 Infinity 로 채우고 dist[src] = 0 을 적는다      ② 시작값
         큐에 src 하나를 넣고 표시를 세운다                      ③ 큐
         큐가 빌 때까지 되풀이한다:
  T2~T9    정점 u 하나를 꺼내고 표시를 내린다                    ④ 꺼내기
             u 에서 나가는 간선 (v, w) 마다
               dist[u] + w 가 dist[v] 보다 작으면 고쳐 적고      ⑤ 완화
               v 가 큐에 없으면 넣는다                           ⑥ 다시 넣기
  T10    dist 를 돌려준다
```

#### 1. 이웃 목록과 시작값과 큐를 만든다

「아이디어 상세」의 1단계와 2단계를 코드로 옮깁니다. 간선 목록을 꼬리 정점별로 모으고, 거리 배열을 `Infinity` 로
채운 다음 `src` 칸에만 `0` 을 적고, 큐에 `src` 하나를 넣어요.

```ts
const adj: [number, number][][] = Array.from({ length: n }, () => []);
for (const [u, v, w] of edges) (adj[u] as [number, number][]).push([v, w]);   // ① 이웃 목록

const dist: number[] = Array.from({ length: n }, () => Number.POSITIVE_INFINITY);
dist[src] = 0;                                                                // ② 시작값

const inQueue: boolean[] = Array.from({ length: n }, () => false);
const queue: number[] = [src];                                                // ③ 큐
inQueue[src] = true;
let head = 0;
```

`T1` 에서 이 조각만 실행하면 이렇게 나옵니다.

<!--proof:walkT1-->

```text
T1 이 끝난 시점
  adj      0:[(1,6),(2,1),(3,20)]  1:[(3,4)]  2:[(1,-3),(3,9)]  3:[(4,2)]  4:[]  5:[(4,1)]
  dist     [0, Infinity, Infinity, Infinity, Infinity, Infinity]
  queue    [0]  head = 0
  inQueue  [true, false, false, false, false, false]
```

`①` 이 없으면 「이 정점에서 나가는 간선」을 찾을 때마다 간선 목록 전체를 읽어야 하고, `③` 의 `inQueue` 가 없으면 「이미
큐에 있는가」를 알려고 큐를 차례로 읽어야 해요. 시작 정점만 0 이고 나머지가 `Infinity` 인 것이 「아직 경로를 못
찾았다」의 표기입니다.

#### 2. 큐에서 정점을 하나 꺼낸다

3단계의 앞 절반을 코드로 옮깁니다. `head` 가 배열 끝에 이르면 큐가 빈 것이고, 그 전까지는 정점을 하나씩 꺼내요. 꺼낸
그 자리에서 표시를 내립니다.

```ts
while (head < queue.length) {
  const u = queue[head++] as number;   // ④ 꺼내기
  inQueue[u] = false;
  // … 이 정점에서 나가는 간선을 완화한다 …
}
```

`queue.length` 는 **넣은 총 횟수**이고 `head` 는 **꺼낸 총 횟수**예요. 둘의 차가 지금 큐에 남은 항목 수입니다. 첫
꺼내기 앞뒤의 두 값을 적으면 이렇습니다.

<!--proof:walkPop-->

```text
T2 가 시작하는 시점  queue [0]           head = 0  꺼낼 것이 1 개
꺼낸 직후            queue [0]           head = 1  꺼낼 것이 0 개 · inQueue[0] = false
T2 가 끝난 시점      queue [0, 1, 2, 3]  head = 1  꺼낼 것이 3 개
```

배열이 한 번 넣은 칸을 지우지 않으므로 꺼낸 차례가 그대로 기록으로 남습니다. 꺼낸 정점 0 의 칸도 배열에는 그대로
있고, `head` 가 그 칸을 지나갔을 뿐이에요.

#### 짚고 가기 — 꺼낸 정점의 표시를 안 내리면 다시 넣어야 할 정점을 놓친다

여기서 헷갈리기 쉬운 포인트는 `inQueue[u] = false` 한 줄입니다. 「이 표시는 넣을 때 중복을 막으려고 두는 것이니
꺼낼 때 안 내려도 같겠지」로 읽기 쉬워요. 그 줄을 통째로 빼 봅시다.

```ts
while (head < queue.length) {
  const u = queue[head++] as number;
  // inQueue[u] = false 가 있던 줄을 지웠다
  for (const [v, w] of adj[u] as [number, number][]) {
    const nd = (dist[u] as number) + w;
    if (nd < (dist[v] as number)) { dist[v] = nd; if (!inQueue[v]) { inQueue[v] = true; queue.push(v); } }
  }
}
```

T4 에서 `dist[1]` 은 두 판 모두 −2 로 줄었습니다. 그런데 표시를 안 내린 판에서는 정점 1 의 표시가 T2 에서 넣을 때의
`true` 그대로라, 이미 큐에 있다고 잘못 읽고 넣지 않아요. 그래서 −2 로 `1 → 3` 을 다시 읽을 기회가 없고, `dist[3]` 이
10 에, 그 값으로 적은 `dist[4]` 가 12 에 멈춥니다. **표시가 뜻하는 것은 「큐 안에 있다」이지 「처리한 적이 있다」가
아닙니다.** 나머지 두 입력에서 답이 안 갈리는 까닭은 서로 달라요. 도달할 수 없는 정점이 있는 입력에는 이미 꺼낸
정점의 값이 다시 줄어드는 자리가 없고, 늦게 찾은 짧은 경로 입력에서는 그 자리가 있지만 값이 다시 준 정점 1 에
나가는 간선이 없어 잃는 것이 없습니다.

#### 3. 꺼낸 정점의 간선만 완화하고 값이 줄면 넣는다

3단계의 뒤 절반과 4단계를 코드로 옮깁니다. 꺼낸 정점의 이웃 목록을 읽으며 완화하고, 값이 줄어든 정점이 큐에 없으면
넣어요.

```ts
for (const [v, w] of adj[u] as [number, number][]) {
  const nd = (dist[u] as number) + w;
  if (nd < (dist[v] as number)) {        // ⑤ 완화
    dist[v] = nd;
    if (!inQueue[v]) {                   // ⑥ 다시 넣기
      inQueue[v] = true;
      queue.push(v);
    }
  }
}
```

첫 꺼내기만 실행하면 이렇게 나옵니다.

```text

  (2, 1)   0 + 1 = 1 < Infinity    ⑤ dist[2] = 1   ⑥ 넣는다
```

정점 0 의 세 간선이 모두 값을 고쳤고, 세 정점 모두 큐에 없어 `⑥` 이 참이 됐습니다. 간선 목록의 나머지 다섯은 이
걸음에서 읽지 않았어요.

#### 짚고 가기 — 큐 중복을 막는 검사를 빼도 답은 안 틀린다

여기서 헷갈리기 쉬운 포인트는 `if (!inQueue[v])` 입니다. 「이미 들어 있는지 확인하지 않고 그냥 넣으면 무엇이
잘못되나」로 읽기 쉬워요. 그 검사를 늘 참으로 두어 봅시다.

```ts
if (nd < (dist[v] as number)) {
  dist[v] = nd;
  if (true) {                            // ← 중복 검사를 늘 참으로 두었다
    inQueue[v] = true;
    queue.push(v);
  }
}
```

```text

전개 입력            [0, -2, 1, 2, 4, Infinity]  [0, -2, 1, 2, 4, Infinity]  같다
늦게 찾은 짧은 경로  [0, 2, 1]                   [0, 2, 1]                   같다
```

**세 입력 모두 답이 한 칸도 안 갈립니다.** 같은 정점이 큐에 여러 벌 들어 있어도 꺼낼 때마다 그때의 `dist` 로 처리하므로
결과가 바뀌지 않아요. 그래서 이 검사를 뺀 채로 시험을 실행해도 전부 통과합니다. 그럼에도 이 검사를 두는 까닭은 계수에

전개 입력에서는 꺼낸 횟수가 하나 늘 뿐이고 완전 그래프에서는 아예 같은데, 허브 모양에서는 넣은 횟수가 거의 갑절이 되고
큐가 가장 길 때도 두 배 가까이 늘었습니다. 허브의 값이 줄 때마다 또 한 벌이 들어가기 때문이에요. 「답이 안 틀린다」가
「빼도 된다」는 아닙니다.

#### 4. 열 걸음을 끝까지 실행한다

세 조각을 이어 고정 입력에 실행하면 열 걸음이 나옵니다. T1 은 준비, T2 부터 T9 까지가 꺼내기 여덟 번, T10 이
반환이에요. 걸음 재생 패널에서 정점 안의 수는 그 걸음이 끝난 뒤의 `dist` 이고, 옅은 채움 정점이 이번에 꺼낸 정점,
굵은 테 정점이 값이 바뀐 정점, 점선 정점이 아직 값이 없는 정점입니다. 굵은 실선은 지금 그 정점의 값을 낸 간선이에요.
무대 아래 세 줄이 간선 목록을 적힌 차례대로 늘어놓은 것, 그 걸음에서 만든 후보 `dist[u] + w`, 그리고 걸음이 끝난 뒤
큐에 남은 정점을 꺼낼 차례대로 늘어놓은 것입니다. 간선 목록에서 이번 걸음이 읽지 않은 간선은 대시 테로 흐리게
그렸어요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 앞에서 확인한 것 말고 새로 들어간 것은 타입 별칭 `Edge` 하나예요 — 간선 하나의 모양을 이름으로
고정한 것이고 동작은 그대로입니다.

```ts
export type Edge = [number, number, number];

export function spfa(n: number, edges: Edge[], src: number): number[] {
  // ① 이웃 목록 — 간선 목록을 꼬리 정점별로 모은다. 꺼낸 정점의 간선만 읽으려면 필요하다.
  const adj: [number, number][][] = Array.from({ length: n }, () => []);
  for (const [u, v, w] of edges) (adj[u] as [number, number][]).push([v, w]);

  // ② 시작값 — 아직 아무 경로도 찾지 못했으므로 전부 `Infinity` 이고 시작 정점만 `0` 이다.
  const dist: number[] = Array.from(
    { length: n },
    () => Number.POSITIVE_INFINITY,
  );
  dist[src] = 0;

  // ③ 큐 — 값이 줄어든 정점만 넣는다. `inQueue` 는 같은 정점이 두 벌 들어가는 것을 막고,
  // `head` 는 다음에 꺼낼 자리를 가리켜 배열 앞을 지우지 않게 한다.
  const inQueue: boolean[] = Array.from({ length: n }, () => false);
  const queue: number[] = [src];
  inQueue[src] = true;
  let head = 0;

  while (head < queue.length) {
    // ④ 꺼내기 — 꺼낸 그 자리에서 표시를 내린다. 이 정점의 값이 뒤에 다시 줄어들면 그때
    // 큐에 다시 들어가야 한다.
    const u = queue[head++] as number;
    inQueue[u] = false;

    for (const [v, w] of adj[u] as [number, number][]) {
      const nd = (dist[u] as number) + w;
      // ⑤ 완화 — 지금 적힌 값보다 작을 때만 고쳐 적는다.
      if (nd < (dist[v] as number)) {
        dist[v] = nd;
        // ⑥ 다시 넣기 — 값이 줄었으니 이 정점에서 나가는 간선을 다시 읽어야 한다.
        if (!inQueue[v]) {
          inQueue[v] = true;
          queue.push(v);
        }
      }
    }
  }

  return dist;
}
```

실행하면 이렇게 나옵니다.

```text
spfa(6, [[0,1,6],[0,2,1],[0,3,20],[1,3,4],[2,1,-3],[2,3,9],[3,4,2],[5,4,1]], 0)  -> [0, -2, 1, 2, 4, Infinity]
spfa(3, [[0,1,10],[0,2,1],[2,1,1]], 0)                                           -> [0, 2, 1]
spfa(4, [[0,1,4],[0,2,5],[1,2,-3]], 0)                                           -> [0, 4, 1, Infinity]
spfa(3, [], 2)                                                                   -> [Infinity, Infinity, 0]

```

### 알아 두면 좋은 개념 — 워크리스트 알고리즘

이 절차가 되풀이를 조직한 방식에는 이름이 붙어 있습니다. 값이 바뀐 항목만 목록에 넣어 두고, 목록에서 하나씩 꺼내
**그 항목에 딸린 것만** 다시 계산하며, 계산 결과가 바뀌면 그 대상도 목록에 넣는 방식을 **워크리스트 알고리즘**이라고
불러요. 목록이 비면 더 바뀔 것이 없다는 뜻입니다. 이 편의 어느 값이 워크리스트의 어느 말이었는지 짝지으면 이렇습니다.

<!--proof:relatedWorklist-->

```text
워크리스트의 말                        이 편에서              전개 입력의 자리
항목                                   정점                   정점 6 개
목록                                   큐                     가장 길 때 3 개
항목에 딸린 값                         dist[v]                줄어드는 쪽으로만 바뀐다
다시 계산하는 범위                     v 에서 나가는 간선     간선 읽기 9 번
이미 든 항목은 또 넣지 않는다          inQueue                T3 의 정점 3
처리한 항목도 값이 바뀌면 다시 넣는다  ⑥                      T4 의 정점 1
목록이 비면 끝난다                     head === queue.length  T9 뒤 큐가 []
```

같은 뼈대가 이 편 밖에서 다시 나옵니다. 셋 다 「무엇이 바뀌었는지 적어 두고 그 범위만 다시 계산한다」와 「목록이 비면
끝난다」를 같은 모양으로 답해요.

| 다른 자리 | 항목과 값 | 목록이 비었을 때의 뜻 |
| --- | --- | --- |
| 컴파일러의 데이터 흐름 분석 | 항목은 기본 블록, 값은 그 지점에 도달하는 정의의 집합 | 더 늘어날 정의가 없다 |
| 제약 전파 (AC-3) | 항목은 변수 쌍, 값은 각 변수에 남은 후보 집합 | 더 지울 후보가 없다 |
| Datalog 의 세미-나이브 평가 | 항목은 술어, 값은 그 술어의 사실 집합 | 새로 유도될 사실이 없다 |

벨만-포드 편의 「고정점 반복」이 「규칙을 되풀이하다 상태가 안 바뀌면 멈춘다」였다면, 워크리스트는 그 되풀이에서
**바뀐 항목에 딸린 계산만** 하는 방식입니다. 답은 같고 계산량만 갈리며, 그 계산량이 얼마나 갈리는지는 자리마다 따로
세어야 해요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 간선 읽기의 상한을 식으로 어떻게 닫는지, 무엇이 매
걸음 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 가중치에 음수가 있다 | 음수가 하나도 없으면 확정 판정이 성립해 `dijkstra` 가 간선을 한 번씩만 읽는다 | 정점을 확정하지 않고 값이 줄면 다시 넣는다 |
| 시작 정점에서 갈 수 있는 음수 사이클이 없거나, 있으면 판정만 하면 된다 | 없으면 큐가 반드시 빈다 | 「큐가 빌 때까지」로 반복을 적는다 · 판정이 필요하면 넣은 횟수를 센다 |
| 값이 여러 번 줄어드는 정점이 적다 | 이 절차가 아끼는 것은 값이 안 바뀐 정점의 간선을 다시 읽는 일이다 | `c(v)` 가 작게 남는다 |
| 최악의 상한 `(V − 1) × E` 를 감당할 수 있다 | 라운드 방식과 같은 상한을 갖는다 | 최악의 보장이 아니라 흔한 입력에서의 계수로 고른다 |

첫 조건이 이 절차의 자리입니다. 가중치가 전부 0 이상이면 [`dijkstra`](../dijkstra/dijkstra-guide.md) 가 같은 답을 최악
보장까지 붙여서 내고, 사이클이 없는 방향 그래프면 [`dagShortestPath`](../dagShortestPath/dagShortestPath-guide.md) 가
위상 순서로 한 번에 끝냅니다. 마지막 조건이 이 절차를 고르는 근거이자 위험이에요. 고르는 근거가 더 나은 보장이
아니라 관측된 계수라서, 그 기대가 어긋나는 입력이 있다는 것을 알고 씁니다.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "손해" "이득" "환급" "할인"                  <- 가중치가 음수일 수 있다
  "비용이 음수일 수 있다"                      <- 확정 판정을 쓰는 절차가 안 된다
  "무한히 이득이 나는 경로는 없다"             <- 음수 사이클이 없다는 전제다
  "한 지점에서 각 지점까지"                    <- 시작 정점이 하나다

제약에 이런 모양이 보이면
  정점이 수백 개이고 간선이 정점 수의 몇 배    <- 라운드 방식보다 적게 읽을 여지가 크다
  간선 목록의 순서를 입력이 정한다             <- 라운드 방식은 순서에 따라 라운드 수가 갈린다

반대로 이런 말이 보이면 해당하지 않는다
  "비용은 항상 0 이상"                         <- 확정 판정을 쓰는 절차가 최악까지 보장한다
  "모든 정점 쌍 사이의 거리"                   <- 시작 정점이 V 개다
  최악을 노린 입력이 나온다고 적혀 있다        <- 최악이 라운드 방식과 같고 큐 연산이 더 붙는다
```

마지막 무리가 보이면 다른 절차로 갑니다. 정점 쌍 전부를 물으면 [`floydWarshall`](../floydWarshall/floydWarshall-guide.md)
처럼 표를 한 번 만드는 쪽이 적고, 음수 사이클 판정이 주된 물음이면 [`bellmanFord`](../bellmanFord/bellmanFord-guide.md)
가 `V` 번째 라운드 하나로 그것을 냅니다.

#### 실제로 쓰이는 곳

- **NetworkX 의 `bellman_ford_predecessor_and_distance`** — 파이썬 그래프 라이브러리의 벨만-포드 함수가 **내부적으로 이
  절차**입니다. 실제 완화 루프인 `_inner_bellman_ford` 의 독스트링이 *"This is an implementation of the SPFA variant."*
  라고 적어 두었고, 코드가 `q = deque(sources)` 와 `in_q = set(sources)` 로 이 글의 큐와 큐 표시를 그대로 둡니다.
  음수 사이클은 이 글의 「이 방법이 기대는 전제」와 같은 방법으로 판정해요 — 정점마다 세는 값이 `n` 에 이르면 음수
  사이클로 봅니다(*"count_v = count.get(v, 0) + 1"* 뒤에 *"if count_v == n:"*).
  ([`networkx/algorithms/shortest_paths/weighted.py`](https://github.com/networkx/networkx/blob/main/networkx/algorithms/shortest_paths/weighted.py),
  조회 2026-09-05)
- **igraph 의 `igraph_bellman_ford_shortest_paths`** — C 로 쓰인 그래프 라이브러리가 같은 방법을 소스 주석에 적어
  두었습니다. *"a vertex is marked clean if its distance from the source did not change during the last phase. Neighbors
  of a clean vertex are not relaxed again, since it would mean no change in the shortest path values. Dirty vertices are
  queued."* 같은 주석이 음수 사이클을 *"by checking whether a vertex has been queued at least n times"* 로 잡는다고
  적고, 같은 파일의 문서 주석이 *"Time complexity: O(s*|E|*|V|)"* 라 적습니다 — 큐를 써도 최악은 라운드 방식과 같다는
  것을 라이브러리 쪽에서도 그렇게 적어 둔 자리예요.
  ([`igraph/src/paths/bellman_ford.c`](https://github.com/igraph/igraph/blob/master/src/paths/bellman_ford.c),
  조회 2026-09-05)

두 라이브러리와 이 글의 정본을 나란히 두면 이렇습니다.

| 쓰이는 곳 | 큐와 큐 표시 | 음수 사이클 |
| --- | --- | --- |
| 이 글의 정본 | 배열 `queue` 와 `inQueue` | 전제로 두고 판정하지 않는다 |
| NetworkX | `deque` 와 `set` | 정점마다 센 값이 `n` 에 이르면 판정한다 |
| igraph | 큐와 「clean · dirty」 표시 | 한 정점이 `n` 번 큐에 들어가면 판정한다 · 복잡도를 시작 정점 수 · 간선 수 · 정점 수의 곱으로 적는다 |

**「이 절차가 평균적으로 빠르다」를 1 차 출처로 확인하지 못했습니다.** 위 두 라이브러리는 큐를 쓴다는 사실과 최악
복잡도만 적고, 평균에 대한 주장은 하지 않아요. 이 글이 평균 쪽으로 내미는 값은 전부 「비용 계산」에서 **생성식을
밝힌 관측**이고 보장이 아닙니다.

#### 경쟁 설계와의 대조

같은 목표(음수 가중치가 있는 그래프에서 한 출발점 최단 거리)를 노리는 다른 절차로 **벨만-포드**가 있습니다. 큐를
버리고, 간선 목록 전체를 처음부터 끝까지 읽는 라운드를 한 칸도 못 고칠 때까지 되풀이하는 방식이에요.

| 설계 | 한 번의 실행에서 읽는 간선 | 비용을 정하는 것 |
| --- | --- | --- |
| 이 가이드의 절차 | 꺼낸 정점에서 나가는 간선 — 그 정점을 여러 번 꺼내면 여러 번 | 한 정점을 몇 번 꺼내는가 |
| 벨만-포드 | 라운드마다 간선 목록 전체 | 라운드 수 |

같은 그래프 · 같은 작업에 두 설계를 적용하고 **기본 연산**을 `tools/bench-alt.ts` 로 세었습니다. 기본 연산은 이 글의
비용 기준인 간선 읽기에 큐에 넣고 꺼낸 횟수를 더한 것이라, 큐가 없는 벨만-포드에서는 간선 읽기와 같아요. 거리 배열을
채우는 초기화 쓰기는 두 설계 모두 세지 않았습니다. 메모리는 입력 밖에 잡은 칸이 가장 많았을 때의 **추가 칸**으로 셉니다.
정점마다 한 칸인 배열의 칸에 큐가 가장 길었을 때의 항목 수(항목 하나를 한 칸)를 더한 것이고, 이웃 목록은 정점별 칸
`V` 만 넣고 옮겨 담은 간선 `E` 개는 넣지 않았어요. 그래프는 사슬 16 개가 허브 하나로 들어가고
그 허브에서 잎 `p` 개로 나가는 모양이에요. 사슬 간선의 가중치는 첫 칸만 100 이고 나머지는 1 이며, 사슬 `i` 에서 허브로
가는 간선의 가중치는 `2(16 − i)` 라 사슬을 더 깊이 지날수록 허브까지의 값이 1 씩 작아집니다. **간선 목록에서 사슬은
내림차순으로 적어요** — 이 순서가 라운드 방식에 가장 불리한 자리입니다. **전개 입력을 그대로 쓰지 않은 이유**는 그
그래프가 정점 여섯이라 한 정점의 나가는 간선을 늘릴 자리가 없기 때문이에요. 벨만-포드 편의 대조와 같은 생성식 · 같은
사슬 길이라 두 편의 기본 연산이 같은 수로 나옵니다.

<!--proof:altTable-->

| 잎 p | 이 가이드의 절차 | 벨만-포드 | 적은 쪽 | 차이 |
| --- | ---: | ---: | --- | ---: |
| 1 개 | 106 | 561 | 이 가이드의 절차 | 455 |
| 65 개 | 1,642 | 1,649 | 이 가이드의 절차 | 7 |
| 66 개 | 1,666 | 1,666 | 같다 | 0 |
| 67 개 | 1,690 | 1,683 | 벨만-포드 | 7 |
| 4,096 개 | 98,386 | 70,176 | 벨만-포드 | 28,210 |

추가 칸은 잎 4,096 개에서 이 가이드의 절차가 16,440 개, 벨만-포드가 4,115 개입니다. 전개 입력에서는 기본 연산이 25 번 대 24 번, 추가 칸이 21 개 대 7 개입니다. 두 계수는 잎 66 개에서 같아지고 67 개부터 벨만-포드가 적습니다.

<!--/proof-->

경계가 그 자리인 까닭은 잎을 하나 더할 때 두 계수가 얼마씩 느는지로 나옵니다.

<!--proof:altBoundary-->

```text
잎을 하나 더할 때 두 설계가 늘어나는 기본 연산
  이 절차    허브를 8 번 꺼낼 때마다 그 잎의 간선을 읽고, 잎을 넣고 꺼낸다  +24
  벨만-포드  라운드 17 번이 그 잎의 간선 1 개를 한 번씩 읽는다              +17

  잎이 하나일 때의 차      561 − 106 = 455
  잎 하나마다 줄어드는 차  24 − 17 = 7
  차가 0 이 되는 잎        1 + 455 ÷ 7 = 66
  실측한 경계              잎 66 개에서 같아지고 67 개부터 벨만-포드가 적다
```

**이 절차가 내주는 것은 추가 칸과, 한 정점이 여러 번 꺼내지는 그래프에서의 계수입니다.** 잎 4,096 개에서 기본 연산이
벨만-포드보다 28,210 번 많고, 추가 칸도 네 배 가까이 씁니다. 정점 여섯짜리 전개 입력에서도 기본 연산이 25 번 대 24 번으로
하나 많아요 — 그래프가 작으면 큐에 넣고 꺼내는 값이 아낀 간선 읽기를 상쇄합니다. 그 대신 얻는 것이 둘이에요.

| 축 | 이 가이드의 절차 | 벨만-포드 |
| --- | --- | --- |
| 값이 몇 번만 줄어드는 그래프 | 바뀐 정점의 간선만 읽는다 — 잎이 하나일 때 기본 연산이 적다 | 고칠 것이 없는 간선도 라운드마다 읽는다 |
| 간선 목록의 순서 | 꺼내는 차례가 큐로 정해져 목록 순서의 영향이 적다 | 목록 순서에 따라 라운드 수가 갈린다 |
| 최악의 보장 | 간선 읽기 `(V − 1) × E` 이하 | 간선 읽기 `V × E` 이하 |
| 추가 칸 | 거리 배열 · 큐 표시 · 이웃 목록 · 큐 | 거리 배열과 `changed` 하나 |

**우열이 뒤집히는 조건은 한 정점의 값이 여러 번 줄고 그 정점의 나가는 간선이 많아지는 순간입니다.** 위 그래프에서는
허브의 나가는 간선이 66 개일 때 두 계수가 같아졌어요. 어느 모양이 올지 입력이 말해 주지 않는 한 이 판정은 다시 해야
합니다.

### 수식 정의와 유도

정점 `v` 에서 나가는 간선의 개수를 $d^{+}(v)$ 라고 씁니다. 한 번 꺼낼 때마다 그 정점의 나가는 간선을 전부 읽고, 정점
`v` 는 큐에 넣은 횟수 $c(v)$ 만큼 꺼내지므로, 실행 전체의 간선 읽기 횟수 $R$ 은 두 값의 곱을 정점마다 더한 것이에요.

$$R = \sum_{v} c(v)\, d^{+}(v), \qquad \sum_{v} d^{+}(v) = E$$

정의를 전개 입력의 값에 넣어 봅니다.

<!--proof:mathCheck-->

```text
정점 v  c(v)  d+(v)  c(v) x d+(v)
0       1     3      3
1       2     1      2
2       1     2      2
3       2     1      2
4       2     0      0
5       0     1      0

합계 9 · 실행이 센 간선 읽기 9
묶음 수 5 · V = 6 · c(v) 의 최댓값 2
```

곱의 합 9 가 실행이 센 간선 읽기 9 와 같습니다. $d^{+}(v)$ 는 그래프가 정하는 값이고 $c(v)$ 는 실행이 정하는 값이에요.
이제 $c(v)$ 의 상한을 식으로 닫습니다. 「큐의 묶음」에서 묶음 `k` 에 든 정점의 집합을 $B_k$ 라고 쓰면, 한 정점은 한 묶음에
많아야 한 번 들고 음수 사이클이 없으면 묶음이 $B_0$ 부터 $B_{V-1}$ 까지라서 이렇게 됩니다.

$$c(v) = \#\{\,k : v \in B_k\,\} \le V - 1 \quad (v \ne src), \qquad c(src) = 1$$

두 식을 이어 간선 읽기의 상한을 닫습니다. 각 항에서 $d^{+}(v) \ge 0$ 이고 $c(v) \le V - 1$ 이므로 곱도 $(V-1)\,d^{+}(v)$
를 넘지 않아요($V \ge 2$ 이면 $c(src) = 1 \le V - 1$ 입니다).

$$R \;=\; \sum_{v} c(v)\, d^{+}(v) \;\le\; \sum_{v} (V-1)\, d^{+}(v) \;=\; (V-1)\sum_{v} d^{+}(v) \;=\; (V-1)\,E$$

```ts
// 식을 그대로 옮긴 조각. 코드에서는 `pushes` 가 c(v) 이고 `outDeg` 가 d+(v) 다.
let reads = 0;
for (let v = 0; v < n; v++) reads += (pushes[v] as number) * (outDeg[v] as number);
```

**여기서 본문의 값만으로는 안 나오는 것이 나옵니다.** 전개 입력은 $c(v)$ 의 최댓값이 2 인 한 벌짜리 값인데, 위 유도는
**임의의 $V$ 와 $E$ 에 대해** 간선 읽기가 $(V-1)E$ 를 넘지 않는다는 닫힌 형태를 줍니다. 규모를 넣어 수치를 내 봅시다.

<!--proof:mathScale-->

```text
정점 V  간선 E = V(V−1)  c(v) 상한 V−1  간선 읽기 상한 (V−1) x E
10      90               9              810
100     9,900            99             980,100
500     249,500          499            124,500,500

규모의 상한에서
  거리 값의 절댓값         (V−1) x 1,000,000,000 = 499,000,000,000 까지
  정수를 정확히 담는 한계  2^53 − 1 = 9,007,199,254,740,991
  둘의 비                  18,050 배 넘게 남는다
```

마지막 줄이 이 절이 함께 주는 것이에요. 단순 경로의 간선이 많아야 `V − 1` 개이니 거리 값의 절댓값도 그 수에 가중치
상한을 곱한 값을 넘지 않고, 그것이 자바스크립트 수가 정수를 정확히 담는 한계보다 만 배 넘게 작아서 이 규모에서는
덧셈이 값을 잃을 자리가 없습니다.

### 불변식 — 완화할 수 있는 간선의 꼬리 정점은 큐 안에 있다

파트 1 의 열 걸음은 그래프 하나에서 답이 나왔다는 기록입니다. 그 하나로는 다른 입력에서도 같은 일이 일어난다는 근거가
안 되므로, **꺼내기가 몇 번 실행되든 참으로 남는 문장**을 세우고 그것이 유지되는 것을 값으로 확인합니다.

> `while` 의 조건을 검사하는 시점마다 둘이 참입니다. **앞 문장** — `dist[v]` 가 유한하면 그 값에 해당하는
> `src → v` 경로가 실제로 존재합니다. **뒤 문장** — 완화할 수 있는 간선 `u → v`(곧 `dist[u] + w < dist[v]` 인
> 간선)가 남아 있으면 그 꼬리 정점 `u` 는 그 시점에 큐 안에 있습니다.

| 문장 | 뜻 | 둘이 함께 주는 것 |
| --- | --- | --- |
| 앞 문장 | `dist` 에 적힌 수는 지어낸 것이 아니라 실제 경로의 비용이다 — 그래서 `opt(v)` 이상이다 | `dist` 가 답보다 아래로 내려가지 않는다 |
| 뒤 문장 | 아직 할 일이 남아 있으면 그 일이 큐에 예약돼 있다 | 큐가 빈 시점에 완화할 간선이 없다 — 5단계의 결론이 된다 |

**첫 꺼내기에 들어가기 전부터 봅시다.** 그 시점의 `dist` 는 `src` 칸만 0 이고 나머지가 전부 `Infinity` 이며, 큐에는 `src`
하나가 있습니다. 간선 0 개짜리 경로의 비용이 0 이라 앞 문장이 참이고, `dist[u]` 가 유한한 정점이 `src` 뿐이므로 완화할 수
있는 간선의 꼬리도 `src` 뿐이라 뒤 문장도 참이에요. 그 뒤로 상태를 바꾸는 갈래는 넷입니다.

| 갈래 | 하는 일 | 앞 문장이 유지되는 근거 | 뒤 문장이 유지되는 근거 |
| --- | --- | --- | --- |
| 시작값 | `dist[src] = 0`, 나머지 `Infinity` | `0` 은 길이 0 인 경로의 비용이다 | `src` 가 큐에 들어 있다 |
| 정점을 꺼낸다 | 표시를 내리고 그 정점의 간선을 읽는다 | `dist` 를 안 바꾼다 | 아래 문단 |
| 완화가 값을 고친다 | `dist[v]` 를 `dist[u] + w` 로 고친다 | `u` 까지의 실재하는 경로에 간선 하나를 이었다 | 값이 줄어 새로 완화될 수 있는 것은 `v` 의 나가는 간선뿐이다 |
| 큐에 넣는다 | `v` 를 넣고 표시를 세운다 | `dist` 를 안 바꾼다 | `v` 의 나가는 간선이 완화될 수 있고, 그 꼬리 `v` 가 큐에 있다 |

「정점을 꺼낸다」 줄이 이 논증에서 가장 좁은 자리예요. 정점 `u` 를 꺼내면 큐 표시가 내려가니, 그 걸음이 끝날 때 `u` 를
꼬리로 하는 완화할 간선이 남아 있으면 뒤 문장이 깨집니다. 그 걸음은 `u` 의 나가는 간선을 전부 완화하므로 걸음이 끝나면
`u` 의 간선은 모두 `dist[u] + w ≥ dist[v]` 를 만족해요. 단 걸음 도중 `dist[u]` 자체가 줄면 다시 어긋나는데, 그러려면
`u` 로 들어오는 간선을 이 걸음이 읽어야 하고, 이 걸음이 읽는 것은 `u` 에서 **나가는** 간선뿐이라 그런 간선은 `u → u`
하나뿐입니다. 그 간선이 `dist[u]` 를 줄이려면 가중치가 음수여야 하는데, 그것은 간선 하나짜리 음수 사이클이라 전제에서
빠져요. 전개 입력에서 검사 시점마다 확인하면 이렇습니다.

<!--proof:invariantWatch-->

| 검사 시점 | 큐 | 완화할 수 있는 간선 | 두 문장 |
| --- | --- | --- | --- |
| T1 | [0] | 0→1 · 0→2 · 0→3 | 지킨다 |
| T2 | [1, 2, 3] | 1→3 · 2→1 · 2→3 · 3→4 | 지킨다 |
| T3 | [2, 3] | 2→1 · 3→4 | 지킨다 |
| T4 | [3, 1] | 1→3 · 3→4 | 지킨다 |
| T5 | [1, 4] | 1→3 | 지킨다 |
| T6 | [4, 3] | 3→4 | 지킨다 |
| T7 | [3] | 3→4 | 지킨다 |
| T8 | [4] | 없다 | 지킨다 |
| T9 | [] | 없다 | 지킨다 |

검사 시점 9 곳 가운데 두 문장을 지킨 곳이 9 곳입니다.

<!--/proof-->

T4 를 봐 주세요 — 완화할 수 있는 간선이 `1→3` 과 `3→4` 인데 큐가 `[3, 1]` 이라 두 꼬리가 다 들어 있어요. T8 에서 완화할
수 있는 간선이 없어지고 T9 에서 큐가 비면서 두 조건이 함께 끝납니다. **엣지 케이스를 함께 봅시다.** 경계에 있는 입력
여덟에 정본을 실행했어요.

<!--proof:invariantEdges-->

| 경계 입력 | src | dist | 꺼낸 횟수 | 간선 읽기 |
| --- | ---: | --- | ---: | ---: |
| 정점 하나, 간선 없음 | 0 | [0] | 1 | 0 |
| 정점 셋, 간선 없음 | 2 | [Infinity, Infinity, 0] | 1 | 0 |
| 도달할 수 없는 정점 | 0 | [0, 4, 1, Infinity] | 3 | 3 |
| 같은 두 정점 사이의 다중 간선 | 0 | [0, -2] | 2 | 3 |
| 가중치가 0 인 간선 | 0 | [0, 0, 0] | 3 | 2 |
| 가중치 합이 0 인 사이클 | 0 | [0, 2, 1] | 3 | 3 |
| 가중치의 절댓값이 10^9 | 0 | [0, 1000000000, 0] | 3 | 2 |
| 자기 자신을 가리키는 양수 간선 | 0 | [0, 2] | 2 | 2 |

<!--/proof-->

간선이 하나도 없으면 시작 정점 하나를 꺼내고 바로 끝나고, 도달할 수 없는 정점은 큐에 들어간 적이 없어 `Infinity` 로
남습니다. 다중 간선은 세 간선을 차례로 읽어 가장 작은 −2 가 남고, 가중치 합이 0 인 사이클은 한 번 더 지나 봐야 같은
값이라 고칠 자리를 만들지 않아요. 마지막 줄이 위에서 좁혀 둔 자리입니다 — 자기 자신을 가리키는 가중치 5 짜리 간선은
`0 + 5 < 0` 이 거짓이라 `dist[0]` 을 못 고치고, 그래서 정점 0 을 꺼내는 동안 그 정점의 값이 바뀌지 않아요.

**이제 그 줄을 망가뜨려 봅시다.** 뒤 문장을 떠받치는 자리는 `queue.push(v)` 한 줄입니다. 「값만 고쳐 두면 언젠가 그
정점을 볼 텐데 굳이 넣어야 하나」라는 생각으로 그 줄만 빼 봅니다.

```ts
if (nd < (dist[v] as number)) {
  dist[v] = nd;
  if (!inQueue[v]) {
    inQueue[v] = true;
    // queue.push(v) 가 있던 줄을 지웠다
  }
}
```

<!--proof:mutantNoPush-->

```text
입력                 정본                        큐에 안 넣는 판                    판정
전개 입력            [0, -2, 1, 2, 4, Infinity]  [0, 6, 1, 20, Infinity, Infinity]  다르다
늦게 찾은 짧은 경로  [0, 2, 1]                   [0, 10, 1]                         다르다
도달할 수 없는 정점  [0, 4, 1, Infinity]         [0, 4, 5, Infinity]                다르다
```

세 입력에서 모두 답이 갈립니다. 전개 입력에서 돌려준 값은 시작 정점 하나를 꺼내고 큐가 비어 끝난 결과예요. 그 걸음이
끝난 시점을 펼치면 뒤 문장이 어디서 깨지는지 보입니다.

<!--proof:mutantNoPushWhere-->

```text
정점 0 을 꺼낸 걸음이 끝난 시점
  dist                    [0, 6, 1, 20, Infinity, Infinity]
  완화할 수 있는 간선     1→3 · 2→1 · 2→3 · 3→4
  큐                      []
  큐 밖에 있는 꼬리 정점  1 · 2 · 3

큐에 안 넣는 판은 꺼내기 1 번 만에 [0, 6, 1, 20, Infinity, Infinity] 을 돌려준다
```

값이 줄어든 정점이 큐에 안 들어가니 할 일이 예약되지 않고, 뒤 문장이 첫 걸음에서 거짓이 됩니다. 앞 문장은 그대로
참이에요 — 안 적는 것은 틀리게 적는 것이 아니기 때문입니다. 뒤 문장이 깨지면 「큐가 빈 시점의 `dist` 가 답」이라는
결론도 함께 사라져요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 셋입니다. 이웃 목록을 만드는 것, 거리 배열과 큐 표시를 만드는 것, 그리고 큐에서 정점을 꺼낼
때마다 그 정점의 나가는 간선을 읽는 것이에요. 비용은 벨만-포드 편과 같은 기준인 **간선 읽기**(간선 하나를 읽고 완화를
시도한 한 번)로 셉니다. 전개의 걸음마다 세면 이렇습니다.

<!--proof:perfCount-->

| 걸음 | 꺼낸 정점 | 간선 읽기 | 여기까지 누적 |
| --- | --- | ---: | ---: |
| T2 | 0 | 3 | 3 |
| T3 | 1 | 1 | 4 |
| T4 | 2 | 2 | 6 |
| T5 | 3 | 1 | 7 |
| T6 | 1 | 1 | 8 |
| T7 | 4 | 0 | 8 |
| T8 | 3 | 1 | 9 |
| T9 | 4 | 0 | 9 |

꺼내기 8 번에 간선 읽기가 9 번이고, 한 번도 큐에 들지 않은 정점 5 가 나가는 간선은 한 번도 읽지 않았습니다.

<!--/proof-->

걸음마다 읽는 간선 수가 다르다는 것을 봐 주세요. **꺼낸 정점이 무엇인가에 따라 0 부터 3 까지 갈립니다.** T7 과 T9 는
정점 4 를 꺼냈는데 나가는 간선이 없어 한 번도 안 읽었고, T2 는 정점 0 을 꺼내 셋을 읽었어요. 그래서 간선 읽기는 라운드
수와 간선 수의 곱이 아니라 「수식 정의와 유도」의 $R = \sum_v c(v)\,d^{+}(v)$ 입니다. 그 밖의 일을 같은 한 번으로 더해
총식을 적으면 이렇습니다.

| 항 | 횟수 | 근거 |
| --- | --- | --- |
| 거리 배열 · 큐 표시 만들기 | `2V` | 정점마다 칸 두 개 |
| 이웃 목록 만들기 | `E` | 간선을 한 번씩 꼬리 정점별로 옮긴다 |
| 꺼내기 | `Σ c(v)` | 넣은 것은 모두 한 번씩 꺼낸다 · `V(V−1)` 이하 |
| 간선 읽기 `R` | `Σ c(v) d+(v)` | `(V−1) × E` 이하 |
| 합 | `2V + E + Σ c(v) + R` | `2V + E + V(V−1) + (V−1)E` 이하 |

두 규모에 넣으면 이렇습니다.

<!--proof:perfTotal-->

```text
  V = 6 · E = 8          2 x 6 + 8 + 8 + 9 = 37
  V = 500 · E = 249,500  2 x 500 + 249,500 + 499 x 500 + 499 x 249,500 = 125,000,500 이하
```

메모리는 벨만-포드 편과 같은 기준인 **추가 칸**(정점마다 한 칸인 배열의 칸과 큐가 가장 길었을 때의 항목 수)으로 셉니다.

<!--proof:perfMemory-->

| 저장하는 것 | 칸 수 |
| --- | ---: |
| 거리 배열 dist | 6 |
| 큐 표시 inQueue | 6 |
| 이웃 목록의 정점별 칸 adj | 6 |
| 큐에 함께 든 항목이 가장 많을 때 | 3 |
| 추가 칸 | 21 |

이웃 목록이 옮겨 담은 간선 8 개와, 꺼낸 칸을 지우지 않는 정본의 queue 배열이 끝까지 자란 길이 8 칸은 추가 칸에 넣지 않았습니다.

<!--/proof-->

정점마다 한 칸인 배열이 셋이고 큐는 많아야 정점 수만큼 차므로 추가 칸은 `Θ(V)` 이고, 이웃 목록이 간선 `E` 개를 한 벌 더
들어 메모리 전체는 `Θ(V + E)` 입니다. 정본의 `queue` 배열은 꺼낸 칸을 지우지 않아 넣은 횟수만큼 자라는데, 꺼낸 칸을 다시
쓰는 원형 큐로 바꾸면 추가 칸에 적은 길이로 충분해요.

#### 케이스별 비용과 그 경계

어떤 입력인가를 말하는 **케이스**와 어떤 종류의 값인가를 말하는 **경계**는 서로 다른 갈래입니다. 한 갈래의 이름을 다른
갈래에 붙이면 두 정보가 함께 사라져요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (모든 정점이 한 번씩만 들어온다) | `O(V·E)` | `Θ(V + E)` — 이웃 목록을 만들고 간선을 한 번씩 읽는다 |
| **평균적인 경우** (입력 분포를 정의하지 않는다) | `O(V·E)` | 정의하지 않는다 |
| **최악의 경우** (한 정점이 `V−1` 번까지 들어온다) | `O(V·E)` | `Θ(V·E)` — 「최악을 만드는 입력」의 허브 무리가 상한과 같은 차수로 는다 |

평균을 정의하지 않는 이유는 **입력 분포를 과제가 주지 않기** 때문입니다. 이 절차에는 난수가 하나도 없어서 무작위성이
구현에서 나오지도 않아요. 그래서 「평균」이라는 말을 쓰려면 어떤 그래프 무리를 어떤 확률로 뽑는지를 먼저 정해야 하는데,
그런 정의가 과제에 없습니다. 흔히 붙는 「평균이 `E` 의 몇 배」라는 말은 경계가 아니라 특정 그래프 무리에서의 관측이에요.
두 무리를 생성식과 함께 재었습니다.

<!--proof:perfObserved-->

| 생성식 | 정점 V | 간선 E | 간선 읽기 | 간선 읽기 / E | 넣은 횟수의 최댓값 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 무작위 | 125 | 249 | 279 | 1.12 | 2 |
| 무작위 | 250 | 488 | 612 | 1.25 | 4 |
| 무작위 | 500 | 993 | 1,203 | 1.21 | 4 |
| 허브 | 125 | 184 | 2,044 | 11.11 | 31 |
| 허브 | 250 | 372 | 7,936 | 21.33 | 62 |
| 허브 | 500 | 747 | 31,623 | 42.33 | 125 |

무작위 줄은 사슬 하나에 앞으로만 가는 간선을 덧붙인 생성식(시드 987654321)이고, 허브 줄은 사슬이 허브로 들어가는 모양입니다.

<!--/proof-->

**같은 계수의 이름으로 두 값이 갈립니다.** 무작위 무리에서는 간선 읽기 나누기 `E` 가 1 과 2 사이에 머무는데, 허브
무리에서는 정점 수가 두 배가 될 때마다 그 값도 대략 두 배가 되어 V = 500 에서 40 을 넘어요 — **그 무리에서는 상수가
아니라 `V` 에 비례합니다.** 관측과 보장을 가르면 이렇습니다.

| 종류 | 문장 | 입력이 바뀐 경우 |
| --- | --- | --- |
| 관측 | 이 생성식의 무작위 그래프에서 간선 읽기가 `E` 의 한두 배였다 | 값이 바뀐다 |
| 보장 | 어떤 입력에서도 간선 읽기가 `(V − 1) × E` 를 넘지 않는다 | 바뀌지 않는다 |

**위의 상한은 전부 최악 보장입니다.** 기댓값이 아니라 상한이라는 뜻이고, 어떤 그래프와 어떤 간선 순서를 넣어도 간선
읽기가 `(V − 1) × E` 를 넘지 않아요. 이 절차를 고르는 근거가 관측이면, 입력이 바뀔 때 그 근거가 함께 사라집니다.

#### 최악을 만드는 입력

연산 수를 최대로 만들려면 두 가지가 한 정점에서 겹쳐야 합니다. **값이 여러 번 줄어들어 여러 번 들어오는 것**과 **나가는
간선이 많은 것**이에요. 정점 64 개로 모양 넷을 실제로 만들어 재 봤습니다. 오른쪽 끝 열은 같은 입력에서 벨만-포드의
간선 읽기입니다.

<!--proof:worstShape-->

| 모양 (V = 64) | 간선 E | 간선 읽기 | 목록을 뒤집은 간선 읽기 | 넣은 횟수의 최댓값 | 벨만-포드의 간선 읽기 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 사슬, 오름차순으로 적음 | 63 | 63 | 63 | 1 | 126 |
| 사슬, 내림차순으로 적음 | 63 | 63 | 63 | 1 | 3,969 |
| 완전 그래프 | 4,032 | 4,032 | 4,032 | 1 | 8,064 |
| 사슬이 허브로 들어가는 모양 | 93 | 558 | 1,023 | 16 | 186 |

간선이 가장 많은 완전 그래프에서 넣은 횟수의 최댓값이 1 입니다.

<!--/proof-->

**「간선이 많으면 느려진다」는 이 절차에서 성립하지 않습니다.** 완전 그래프는 간선이 4,032 개인데 정점마다 한 번씩만
들어와서 간선 읽기가 `E` 와 같아요. **간선 목록의 순서는 앞의 세 모양에서 계수를 안 바꿉니다** — 사슬을 오름차순으로
적든 내림차순으로 적든 63 이고, 같은 입력에서 벨만-포드는 126 과 3,969 로 서른 배 넘게 갈립니다. 다만 허브 모양에서는
간선 목록을 뒤집으면 558 이 1,023 으로 늘어나요. 목록의 순서가 이웃 목록 안의 차례를 정하고, 그 차례가 어느 간선을 먼저
완화하는지를 바꿔 `c(v)` 를 움직이기 때문입니다. 두 절차의 최악 입력은 서로 달라요. 벨만-포드는 내림차순 사슬에서
3,969 번인데 이 절차는 63 번이고, 이 절차는 허브 모양에서 558 번인데 벨만-포드는 186 번입니다.

허브 모양을 키우면서 `(V − 1) × E` 에 대한 비를 재면 그 모양이 상한과 같은 차수로 느는지 알 수 있어요. 정점 수를 두 배씩
늘려 규모의 상한까지 가 봅시다.

<!--proof:worstGrowth-->

| 정점 V | 간선 E | 간선 읽기 | (V−1) x E | 그 비 |
| ---: | ---: | ---: | ---: | ---: |
| 32 | 45 | 150 | 1,395 | 0.108 |
| 64 | 93 | 558 | 5,859 | 0.095 |
| 128 | 189 | 2,142 | 24,003 | 0.089 |
| 256 | 381 | 8,382 | 97,155 | 0.086 |
| 500 | 747 | 31,623 | 372,753 | 0.085 |

마지막 줄이 규모의 상한 V = 500 입니다.

<!--/proof-->

**마지막 열이 0.108 에서 0.085 로 내려가다 멈춥니다.** 규모를 열다섯 배 넘게 늘려도 한 값 언저리에 머물러요 — 이
모양의 간선 읽기가 `(V − 1) × E` 와 **같은 차수로** 늘어난다는 뜻이고, 그래서 이 절차의 최악이 상한의 차수에 실제로
이릅니다. **여기서 잰 무리는 `E` 가 `V` 의 1.5 배 언저리인 모양입니다.** 간선이 훨씬 촘촘한 무리에서도 같은 비가 나오는지는
확인하지 않았어요 — 확인한 것은 「이 무리에서 상한의 차수에 이른다」까지입니다. 축마다 최악으로 만든 입력과 그 값을
모으면 이렇습니다.

<!--proof:worstAxes-->

| 최악으로 만들 축 | 그 축을 크게 만드는 입력 | V = 64 | V = 500 |
| --- | --- | ---: | ---: |
| 한 정점의 넣은 횟수 | 사슬 V/2 개가 허브로 들어간다 | 16 | 125 |
| 간선 읽기 ÷ ((V − 1) × E) | 그 허브에서 잎 V/2 개로 나간다 | 0.095 | 0.085 |

넣은 횟수의 최댓값은 V = 64 에서 64 ÷ 4 = 16 과 같고, V = 500 에서 500 ÷ 4 = 125 와 같습니다.

<!--/proof-->

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 값이 줄어든 정점을 큐에 넣고, 하나씩 꺼내 그 정점에서 나가는 간선만
완화하며, 큐가 비면 끝냅니다. 답이 맞는 근거는 「완화할 수 있는 간선의 꼬리는 큐 안에 있다」이고, 간선 읽기의 상한은
큐의 묶음에서 나온 `c(v) ≤ V − 1` 로 닫은 `(V − 1) × E` 예요.

```text
1. 이웃 목록을 만든다
2. dist 를 Infinity 로 채우고 dist[src] = 0 을 적은 뒤 큐에 src 를 넣는다
3. 큐에서 하나 꺼내 표시를 내리고, 그 정점의 간선만 완화한다
4. 값이 줄어든 정점이 큐에 없으면 넣는다
5. 큐가 비면 dist 를 돌려준다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T5 는 `dist[4]` 를 12 로 적었는데 T8 에서 그것이 4 로 바뀌었어요. 「한 번 적힌
값이 다시 바뀐다」가 이 절차에서 왜 문제가 되지 않을까요?

<!--proof:selfcheckStale-->

```text
T5 의 dist             [0, -2, 1, 10, 12, Infinity]
T8 의 dist             [0, -2, 1, 2, 4, Infinity]
값이 있다가 바뀐 자리  dist[4] 가 12 에서 4 로
```

<!--check:whyRewriteIsFine-->
`dist[4]` 가 **줄어드는 방향으로만** 바뀌기 때문입니다. 불변식의 앞 문장이 「유한한 값이면 그 값에 해당하는 경로가 실제로
있다」이므로 12 도 4 도 실재하는 경로의 비용이에요. 두 값이 어느 경로의 비용이었는지 적으면 이렇습니다.

<!--proof:selfcheckPaths-->

| 걸음 | dist[4] 에 적힌 값 | 경로의 정점 차례 | 간선 수 |
| --- | --- | --- | ---: |
| T5 | 12 | 0→1→3→4 | 3 |
| T8 | 4 | 0→2→1→3→4 | 4 |

두 값 모두 실재하는 경로의 비용이고, 정점 4 로 가는 단순 경로 4 개 가운데 가장 작은 비용은 4 입니다.

<!--/proof-->

T5 의 12 는 `dist[3]` 이 아직 10 이던 때 적은 값이고, T6 이 `dist[3]` 을 2 로 줄이며 정점 3 을 큐에 다시 넣었기 때문에 T8
이 그것을 꺼내 4 로 고쳤어요. 값이 줄어든 정점은 반드시 큐에 들어가므로, 낡은 값을 근거로 적은 자리는 그 정점이 다시
꺼내질 때 고쳐집니다.

| 걸음이 지날 때 | 값의 방향 | 뜻 |
| --- | --- | --- |
| 값이 줄어든다 | 아래로만 | 더 작은 비용의 경로가 새로 이어졌다 |
| 값이 그대로다 | 없음 | 그 정점에서 할 일이 없다 — 큐가 비면 끝난다 |
| 값이 늘어난다 | 위로 | 앞 문장이 깨졌다 — 이 절차의 어느 갈래도 값을 늘리지 않는다 |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「경쟁 설계와의 대조」, 「수행으로 알아보는 알고리즘」의 큐 중복
검사를 빼는 짚고 가기, 「아이디어 상세」의 「먼저 넣은 정점을 먼저 꺼내는 까닭」을 다시 보세요.

- 잎이 66 개일 때 두 설계의 기본 연산이 1,666 으로 같았습니다. 사슬 길이를 16 에서 8 로 줄이면 허브를 꺼내는 횟수와
  벨만-포드의 라운드 수가 각각 어떻게 되는지 예측하고, 두 계수가 같아지는 잎 수가 어느 쪽으로 옮겨질지 따져 보세요.
- 큐 중복 검사를 빼면 답은 그대로인데 넣은 횟수가 늘었어요. 그 판에서 한 정점이 큐에 들어갈 수 있는 횟수는 무엇과
  같아질까요? 「완화가 그 정점의 값을 고친 횟수」와의 관계를 먼저 적고, 전개의 T3 에서 무엇이 달라지는지 답해 보세요.
- 스택으로 꺼내면 번호 차의 제곱 그래프에서 한 정점이 `V − 1` 보다 많이 들어왔습니다. 정점 넷짜리 번호 차의 제곱 그래프
  (간선 `0→1` · `0→2` · `0→3` · `1→2` · `1→3` · `2→3`)에서 스택이 정점 3 을 몇 번 넣는지 손으로 따라가 예측하고, 그
  예측이 맞는지 세어 보세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### SPFA (Shortest Path Faster Algorithm)

풀 파일: [`spfa.ts`](./spfa.ts) · 테스트: [`spfa.test.ts`](./spfa.test.ts) · 실행: `bun test src/algorithms/shortest-path/spfa/spfa.test.ts`

#### 한 줄 요약

> 함수는 음수 간선을 포함할 수 있는 그래프 (음수 사이클 없음)와 시작 정점을 받아 각 정점까지의 최단 거리 배열을 반환한다.

#### 스토리

게임 개발자 준서는 플레이어가 맵을 이동할 때 최소 이동 비용을 실시간으로 계산하는 시스템을 만들고 있다. 맵에는 이동 비용을 줄여주는 부스터 구간이 있어 일부 경로의 비용이 음수다. 단, 부스터만 무한히 순환하며 비용을 무한정 줄이는 경로는 없도록 맵이 설계되어 있다.

준서는 음수 간선이 포함된 그래프에서도 효율적으로 최단 경로를 계산하고 싶다. 단순히 모든 간선을 반복해서 완화하는 방식은 너무 느리다.

핵심 아이디어는 거리가 실제로 갱신된 정점의 이웃만 다시 검사하는 것이다. 갱신이 없으면 그 이웃들은 더 이상 검사할 필요가 없으므로 불필요한 연산을 크게 줄일 수 있다.

#### 함수 인터페이스

```ts
export function spfa(
  n: number,
  edges: [number, number, number][],
  src: number,
): number[];
```

- `n` — 정점 수. 정점 번호는 $0$부터 $n - 1$.
- `edges` — 방향 간선 목록. 각 원소는 $[u, v, w]$ 형태이며 가중치 $w$ (음수 허용)인 방향 간선 $u \to v$.
- `src` — 시작 정점 번호.
- 반환 — 길이 $n$인 배열. 인덱스 $v$에는 $\text{src} \to v$의 최단 거리. 도달할 수 없는 정점은 `Infinity`.

#### 제약 조건

- $1 \leq V \leq 10^5$ (정점 수)
- $0 \leq E \leq 2 \cdot 10^5$ (간선 수)
- $-10^9 \leq w(u, v) \leq 10^9$ (가중치; 음수 허용)
- $0 \leq \text{src} < V$
- $\text{src}$에서 도달 가능한 음수 사이클은 존재하지 않는다
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

음수 가중치를 포함할 수 있는 방향 그래프 $G = (V, E)$가 주어진다. 시작 정점 $\text{src}$에서 모든 정점 $v$까지의 최단 거리 $d(\text{src}, v)$를 구하라.

$\text{src}$에서 도달 가능한 음수 사이클은 없다고 보장된다. 음수 사이클 검출이 필요한 경우에는 이 함수를 사용하지 않는다.

- $\text{src}$ 자신까지의 거리는 $0$이다.
- 도달할 수 없는 정점의 거리는 `Infinity`다.
- 동일한 두 정점 사이에 다중 간선이 있으면 모두 고려해야 한다.
- 거리가 갱신된 정점만 재처리한다. 한 번 대기열에 등록된 정점도 거리가 다시 갱신되면 재등록될 수 있다.

#### 예시

```ts
// 음수 간선이 있지만 음수 사이클 없음
const edges: [number, number, number][] = [
  [0, 1, 4],
  [0, 2, 5],
  [1, 2, -3],
  [2, 3, 4],
];
spfa(4, edges, 0);
// [0, 4, 1, 5]
// — 0→2 최단: 0→1→2 = 1 (직접 간선 5보다 짧음)

// 도달 불가능한 정점은 Infinity
spfa(3, [[0, 1, 2]], 0);
// [0, 2, Infinity] — 정점 2로 가는 간선 없음

// 늦게 발견된 더 짧은 경로가 전파됨
spfa(3, [[0, 1, 10], [0, 2, 1], [2, 1, 1]], 0);
// [0, 2, 1]
// — 0→1: 먼저 10이 등록되지만 이후 0→2→1 = 2로 갱신됨

// 시작점이 중간 정점인 경우
spfa(4, [[0, 1, 1], [1, 2, 1], [2, 3, 1]], 1);
// [Infinity, 0, 1, 2] — src=1 기준; 정점 0은 도달 불가
```
