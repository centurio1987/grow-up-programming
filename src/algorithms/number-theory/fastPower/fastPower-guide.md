# fastPower — 지수를 반으로 접을 때마다 곱셈이 많아야 두 번인 이유

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 밑을 지수만큼 차례로 곱하는
방법에서 지수의 비트 수만큼만 곱하는 방법까지 가는 경로를 따라갑니다. 마지막에는 실제로
동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

정수 셋을 받아 **밑을 지수만큼 거듭제곱한 값을 법으로 나눈 나머지**를 돌려주는 문제예요.
「법으로 나눈 나머지」에서 법은 나누는 수를 말하고, 답은 언제나 `0` 이상 법 미만입니다.

```text
입력 셋
  base   밑        임의의 정수. 음수여도 된다
  exp    지수      0 이상
  mod    법        1 이상
  답     base 를 exp 번 곱한 값을 mod 로 나눈 나머지. 범위는 0 이상 mod 미만이다

  fastPower(3, 26, 1000) 이면 3 을 26 번 곱한 2,541,865,828,329 을 1,000 으로 나눈 나머지 329
```

가장 정직한 방법은 밑을 지수만큼 차례로 곱하는 것입니다. 그런데 이 문제의 지수는 `10^18`
까지 올 수 있어서, 곱셈을 `10^18` 번 하면 초당 1 억 번을 처리해도 300 년이 넘게 걸려요.

```text
차례로 곱하면 곱셈이 지수만큼이다
  exp = 26                          곱셈 26 번
  exp = 1,000,000                   곱셈 1,000,000 번
  exp = 1,000,000,000,000,000,000   곱셈 1,000,000,000,000,000,000 번
  └ 아래로 갈수록 지수의 크기를 그대로 따라간다. 제한 시간 1 초 안에 못 끝낸다
```

여기서 쓰는 것은 **지수의 이진 표현**입니다. 어떤 자연수든 2 의 거듭제곱들의 합으로 딱 한
가지 방법으로 적히고, 그 합에 어느 자리가 들어갔는지를 0 과 1 로 늘어놓은 것이 이진 표현이에요.

```text
26 을 2 의 거듭제곱의 합으로 적는다

  자리 i        4   3   2   1   0
  2^i          16   8   4   2   1
  들어갔는가    1   1   0   1   0
  고른 값      16   8   -   2   -
  └ 셋째 줄을 왼쪽부터 읽으면 26 의 이진 표현 11010 이고, 넷째 줄을 더하면 16 + 8 + 2 = 26 이다
```

지수가 합으로 적히면 거듭제곱은 곱으로 갈라집니다. `base` 를 26 번 곱한 것은 16 번 곱한 것과
8 번 곱한 것과 2 번 곱한 것을 서로 곱한 것과 같아요.

```text
지수의 합이 거듭제곱의 곱이 된다

  base^26 = base^(16 + 8 + 2) = base^16 · base^8 · base^2
  └ 오른쪽에 필요한 것은 「자리마다의 base^(2^i)」 셋뿐이다
```

그 `base^(2^i)` 들이 **직전 값의 제곱**으로 하나씩 나옵니다. `base^1` 을 제곱하면 `base^2`,
그것을 제곱하면 `base^4`, 이런 식으로 자리 하나에 곱셈이 한 번씩 들어요.

| 자리 `i` | 0 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- | --- |
| `base^(2^i)` | `base^1` | `base^2` | `base^4` | `base^8` | `base^16` |
| 직전 값에서 하는 일 | 시작값 | 제곱 | 제곱 | 제곱 | 제곱 |
| 밑이 3, 법이 1,000 이면 | 3 | 9 | 81 | 561 | 721 |
| 26 에서 이 자리가 켜졌는가 | 아니요 | 예 | 아니요 | 예 | 예 |

그래서 지수의 비트를 아래에서 위로 한 번 지나가면 끝납니다. 자리마다 제곱을 한 번 하고, 그
자리가 켜져 있으면 누적값에 한 번 더 곱해요.

```text
지수 26, 밑 3, 법 1,000 을 아래에서 위로

  자리 0   비트 0   밑 3 을 제곱해 9       누적값 1
  자리 1   비트 1   밑 9 를 제곱해 81      누적값 1 · 9 = 9
  자리 2   비트 0   밑 81 을 제곱해 561    누적값 9
  자리 3   비트 1   밑 561 을 제곱해 721   누적값 9 · 561 = 5,049 를 줄이면 49
  자리 4   비트 1   밑 721 을 제곱해 841   누적값 49 · 721 = 35,329 를 줄이면 329
  └ 마지막 열의 누적값은 법 1,000 으로 줄인 값이다. 답 329 가 마지막 줄에 있고,
    마지막 줄이 만든 밑 841 은 쓸 자리가 없다
```

곱셈 횟수는 **지수의 비트 수**와 **그중 1 인 비트의 개수**를 더한 값입니다. 지수가 `10^18`
이면 비트가 60 개이고 1 인 비트가 24 개라 곱셈이 84 번이에요 — `10^18` 번이던 것과 견주면
자릿수가 열아홉에서 둘로 줄어듭니다.

```text
같은 답을 내는 데 드는 곱셈

  차례로 곱한다     1,000,000,000,000,000,000 번
  비트를 지나간다                          84 번
  └ 위는 지수의 크기를 따라가고 아래는 지수의 자릿수를 따라간다
```

한 번 지나가는 동안 들고 있는 값은 누적값과 밑과 남은 지수 셋뿐이라 추가로 잡는 메모리가
`O(1)` 이고, 곱셈 횟수가 지수의 자릿수에 비례하므로 시간은 `O(log exp)` 입니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **나머지 연산의 성질.** 곱한 뒤에 나머지를 구하는 것과, 각각 나머지를 구한 뒤에 곱하고 다시
  나머지를 구하는 것이 같은 값을 냅니다. 이 성질이 없으면 중간값을 법 안에 묶어 둘 수 없어요.
- **자연수의 이진 표현.** 어떤 자연수든 2 의 거듭제곱의 합으로 딱 한 가지 방법으로 적힌다는
  것과, 그 표현의 자릿수가 수의 크기의 로그에 비례한다는 것입니다.
- **지수법칙 두 줄.** `x^(u+v) = x^u · x^v` 와 `(x^u)^2 = x^(2u)` 입니다. 이 글의 절차 전체가
  이 둘에서 나옵니다.
- **JavaScript 의 `bigint`.** 이 문제는 값이 커서 `number` 로 담을 수 없습니다. 왜 담을 수
  없는지는 첫 번째 「짚고 가기」에서 값으로 확인합니다.

비트를 하나씩 보는 도구가 필요하면
[`lowestSetBit`](../../bit-manipulation/lowestSetBit/lowestSetBit-problem.md) 이 그 자리이고,
이 글이 구하는 값을 재료로 쓰는 문제로는
[`millerRabin`](../millerRabin/millerRabin-problem.md) 과
[`binomialModP`](../binomialModP/binomialModP-problem.md) 가 있습니다.

```text
이 글이 다루는 것과 이웃한 것

  base^exp mod mod 를 한 번 구한다           <- 이 글이 다루는 것
  밑과 거듭제곱 결과를 알 때 지수를 찾는다   <- 다른 글이 다루는 것 (babyStepGiantStep)
  n 번째 피보나치 수를 행렬로 구한다         <- 또 다른 글이 다루는 것 (matrixPowerFibonacci)
```

### 아이디어 상세 — 지수를 반으로 접는 방법을 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function fastPower(base: bigint, exp: bigint, mod: bigint): bigint;
```

- 입력: 밑 `base` 는 임의의 정수, 지수 `exp` 는 `0` 이상, 법 `mod` 는 `1` 이상입니다.
- 출력: `base` 를 `exp` 번 곱한 값을 `mod` 로 나눈 나머지. 범위는 `0` 이상 `mod` 미만입니다.
- 제약: `0 ≤ exp ≤ 10^18`, `mod ≥ 1`, 밑은 음수를 포함합니다. 시간 1 초, 메모리 256 MB.

이 글이 쓰는 기호는 여덟입니다. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `base` | 입력으로 받는 밑 | 임의의 정수, 음수를 포함한다 |
| `exp` | 입력으로 받는 지수 | `0 ≤ exp ≤ 10^18` |
| `mod` | 입력으로 받는 법. 나누는 수다 | `mod ≥ 1` |
| `b` | 코드가 들고 있는 밑. 바퀴 `i` 를 시작하는 시점에 `base^(2^i)` 를 법으로 줄인 값이다 | 값 하나 |
| `e` | 코드가 들고 있는 남은 지수. 바퀴마다 절반으로 준다 | 값 하나 |
| `result` | 코드가 누적하는 값. 마지막에 이 값이 답이 된다 | 값 하나 |
| `n` | `exp` 의 비트 수 | `exp = 10^18` 이면 60 |
| `s` | `exp` 의 이진 표현에서 1 인 비트의 개수 | `exp = 10^18` 이면 24 |

「바퀴」는 반복문 본문을 한 번 실행하는 것을 말합니다. 바퀴 하나가 비트 하나를 처리하므로
바퀴 수와 `n` 이 같고, **`i` 번째 바퀴가 지수의 `i` 번째 비트 자리를 처리합니다** — 그래서
아래에서 `i` 는 바퀴 번호이자 비트 자리 번호이고, 둘 다 `0` 부터 셉니다.

가장 먼저 떠오르는 방법으로 시작합시다. `result` 를 `1` 에서 출발시켜 `base` 를 `exp` 번
곱하는 것입니다.

```ts
function repeatedMultiply(base: bigint, exp: bigint, mod: bigint): bigint {
  let acc = 1n % mod;
  const b = ((base % mod) + mod) % mod;
  for (let i = 0n; i < exp; i++) {
    acc = (acc * b) % mod;      // 지수 하나마다 곱셈 한 번
  }
  return acc;
}
```

이 방법이 하는 일의 양은 **지수 그 자체**입니다. 제약 규모를 넣어 보면 몇 번인지 나옵니다.

<!--proof:costNaive-->

```text
                 지수 exp                  곱셈 횟수   초당 1 억 번이면
                       26                         26      0.00000026 초
                    1,000                      1,000         0.00001 초
                1,000,000                  1,000,000            0.01 초
            1,000,000,000              1,000,000,000              10 초
1,000,000,000,000,000,000  1,000,000,000,000,000,000  10,000,000,000 초

마지막 줄의 10,000,000,000 초는 약 317 년이다
└ 제약이 지수 10^18 을 허용하므로 이 방법은 후보가 아니다
```

317 년입니다. 그러면 이 `10^18` 번의 곱셈 안에서 무엇이 되풀이되는지 봅시다. 지수법칙
`(x^u)^2 = x^(2u)` 를 쓰면 **한 번의 곱셈이 지수를 두 배로 만듭니다.**

```text
곱셈 한 번이 지수에 하는 일

  차례로 곱한다   x^u 에 x 를 곱한다     지수가 u 에서 u + 1 이 된다
  제곱한다        x^u 를 자기와 곱한다   지수가 u 에서 2u 가 된다
  └ 아래는 곱셈 한 번으로 지수를 두 배로 만든다. 그러면 위로 올라가는 대신 아래로 내려가 본다
```

지수 26 을 반으로 접어 내려가 봅시다. 26 은 짝수라 13 의 두 배이고, 13 은 홀수라 6 의 두 배에
1 을 더한 것이며, 6 은 3 의 두 배, 3 은 1 의 두 배에 1 을 더한 것, 1 은 0 의 두 배에 1 을
더한 것입니다.

```text
26 을 반으로 접어 내려간다

  26 = 13 · 2
  13 =  6 · 2 + 1
   6 =  3 · 2
   3 =  1 · 2 + 1
   1 =  0 · 2 + 1
  └ 다섯 걸음에 0 이 된다. 오른쪽에 붙는 1 은 그 자리의 비트가 1 이라는 뜻이다
```

이제 가장 아래에서부터 거슬러 올라가면서 실제 값을 잇습니다. `3^0 = 1` 에서 출발해, 한 걸음
올라갈 때마다 직전 값을 제곱하고 홀수 자리면 밑 3 을 한 번 더 곱해요.

<!--proof:foldChain-->

```text
구하는 값  직전 값으로 하는 일                   값  누적 곱셈
3^0        -                                      1          0
3^1        제곱 뒤 밑을 한 번 더                  3          2
3^3        제곱 뒤 밑을 한 번 더                 27          4
3^6        제곱                                 729          5
3^13       제곱 뒤 밑을 한 번 더          1,594,323          7
3^26       제곱                   2,541,865,828,329          8

└ 3^26 을 8 번의 곱셈으로 얻었다. 차례로 곱하면 26 번이다
```

**여기가 준비의 끝입니다.** 이 절차의 비용이 무엇인지가 정해졌어요 — 반으로 접는 걸음의 수와,
그 걸음 중 홀수였던 걸음의 수입니다.

```text
비용이 무엇으로 정해졌는가
  반으로 접는 걸음의 수   다섯 걸음     걸음마다 제곱 한 번
  그중 홀수였던 걸음      13, 3, 1 셋   걸음마다 밑을 한 번 더
  └ 이 둘의 합이 8 이고, 그것이 위 표의 마지막 줄이다
```

이제 같은 지수를 두 방식으로 처리하고 실제 곱셈 횟수를 나란히 세어 봅시다. 왼쪽은 차례로
곱하는 방식이고, 오른쪽은 반으로 접는 방식이에요.

<!--proof:costTwoWays-->

```text
                 지수 exp              차례로 곱한다  절반씩 접는다  비트 수 n  1 인 비트 s
                       26                         26              8          5            3
                    1,000                      1,000             16         10            6
                1,000,000                  1,000,000             27         20            7
            1,000,000,000              1,000,000,000             43         30           13
1,000,000,000,000,000,000  1,000,000,000,000,000,000             84         60           24

└ 셋째 열은 지수의 크기가 아니라 자릿수를 따라간다. 넷째 열과 다섯째 열을 더한 값이다
```

여기서 관찰할 것은 하나입니다 — **셋째 열이 넷째 열과 다섯째 열의 합**이고, 그 둘은 지수의
크기가 아니라 지수를 2 로 적었을 때의 모양에서 나옵니다.

| 방식 | 곱셈 횟수 | 무엇을 따라가는가 |
| --- | --- | --- |
| 차례로 곱한다 | `exp` | 지수의 크기를 따라간다 |
| 절반씩 접는다 | `n + s` | 지수의 자릿수를 따라간다 |

그 관찰을 개념으로 세우기 전에, 더 단순한 후보부터 실행해 봅시다. 「반으로 접는 것이 요점이니
제곱만 되풀이하면 되지 않나」가 그것이에요. 홀수 보정을 빼고 제곱만 반복하는 것입니다.

<!--proof:squaringOnly-->

```text
입력                     정본이 낸 답  제곱만 반복한 답  실제로 구한 지수  판정
전개 입력 3^26 mod 1000           329               721                16  틀리다
3^16 mod 1000                     721               721                16  같다
2^10 mod 1000                      24               256                 8  틀리다
5^7 mod 100                        25                25                 4  같다
3^13 mod 1000                     323               561                 8  틀리다

└ 지수가 2 의 거듭제곱이면 같은 값이 나온다. 넷째 줄은 5^4 와 5^7 이 법 100 에서
  우연히 같은 자리라 판정이 「같다」로 나온 것이고, 후보가 옳아서가 아니다
```

이 후보가 어긋나는 이유는 하나입니다. 제곱만 반복하면 도달하는 지수가 **2 의 거듭제곱**뿐이고,
26 처럼 그 사이에 있는 지수는 만들 수 없어요.

```text
제곱만 반복하면 어디까지 가는가

  3^1 -> 3^2 -> 3^4 -> 3^8 -> 3^16 -> 3^32
  └ 26 은 이 줄에 없다. 16 과 32 사이에 있고, 모자란 10 을 채울 방법이 이 후보에는 없다
```

그러니 **모자란 부분을 자리마다 채운다**는 것이 절차에 있어야 합니다. 여기서 진짜 개념이
나와요. `exp` 를 2 의 거듭제곱의 합으로 적고, 그 합에 들어간 자리의 `base^(2^i)` 만 곱하는
것입니다.

```text
개념 — 켜진 자리만 곱한다

  exp 를 이진수로 적는다          26 = 11010
  자리 i 가 1 이면 base^(2^i) 를 곱한다
  자리 i 가 0 이면 아무것도 곱하지 않는다
  base^(2^i) 는 직전 자리의 값을 제곱해서 얻는다
  └ 자리 하나에 제곱 한 번, 켜진 자리에 곱셈 한 번이 더 든다
```

이 개념이 각 상태 변수의 이동 범위를 정합니다. `e` 는 바퀴마다 절반이 되므로 **정확히 `n`
바퀴**에 0 이 되고, `b` 는 바퀴마다 한 번 제곱되며, `result` 는 **켜진 자리에서만** 바뀌어
`s` 번 갱신돼요.

| 변수 | 바퀴마다 하는 일 | 전체에서 몇 번 바뀌는가 | 지수 26 에서 |
| --- | --- | --- | --- |
| `e` | 절반으로 줄인다 | `n` 번 | 5 번 |
| `b` | 한 번 제곱한다 | `n` 번 | 5 번 |
| `result` | 비트가 1 일 때만 곱한다 | `s` 번 | 3 번 |

**쉬운 경우와 불안한 경우를 나눠서 값으로 확인합시다.** 쉬운 경우는 비트가 1 인 바퀴예요.
`result` 에 그 자리의 값이 곱해지고, 곱한 결과를 법으로 줄입니다.

```text
비트가 1 인 바퀴 — 자리 1 과 자리 3

  자리 1   result 1 에 b = 9 를 곱한다      9 를 1,000 으로 줄이면 9
  자리 3   result 9 에 b = 561 을 곱한다    5,049 를 1,000 으로 줄이면 49
  └ 그 자리의 base^(2^i) 가 답에 들어간다. 이 두 줄이 26 의 16 과 8 과 2 중 8 과 2 를 채운다
```

불안한 경우는 **비트가 0 인 바퀴**입니다. `result` 가 그대로라 아무 일도 일어나지 않은 것처럼
보이는데, 그 바퀴에서도 `b` 는 반드시 제곱돼야 해요.

```text
비트가 0 인 바퀴 — 자리 0 과 자리 2

  자리 0   result 1 그대로   b 를 3 에서 9 로 제곱한다      이 9 를 자리 1 이 쓴다
  자리 2   result 9 그대로   b 를 81 에서 561 로 제곱한다   이 561 을 자리 3 이 쓴다
  └ 비트가 0 이어도 다음 자리의 값을 만들어야 하므로 제곱은 건너뛸 수 없다
```

빠뜨리는 자리가 없다는 것은 반복문의 종료 조건으로 말할 수 있습니다. `e` 는 바퀴마다 절반으로
줄어들고, 0 이 되는 순간 멈춰요.

```text
반복문이 끝난 시점

  검사한 자리   자리 0 부터 자리 n-1 까지   n 개, 각각 정확히 한 번
  안 본 자리    없다                        e 가 0 이 되어야 멈춘다
  └ 비트 n 개가 빠짐없이 한 번씩 검사되고, 그중 켜진 s 개가 result 에 들어간다
```

이제 「반으로 접는 것」이 정말 최선인지 값으로 확인합니다. 접는 비율 `k` 를 여러 개로 두고 같은
지수에 실행했어요. `k` 로 접는 절차는 자리마다 밑을 `k` 제곱하고(곱셈 `k − 1` 번) 그 자리의
숫자만큼 누적합니다.

<!--proof:foldRadix-->

```text
접는 방법                지수 26 의 곱셈         지수 10^18 의 곱셈
접지 않고 차례로 곱한다               26  1,000,000,000,000,000,000
k = 2                                  8                         84
k = 3                                 12                        116
k = 4                                 14                        127
k = 8                                 19                        197
k = 10                                26                        172

└ 첫 줄은 접지 않는 방법이라 k 의 식에 들어가지 않고, 견줄 기준으로만 둔다.
  나머지 다섯 줄 중 두 지수 모두 k = 2 가 가장 적다. k = 10 이 k = 8 보다 적은 것은
  10^18 이 십진법에서 1 뒤에 0 이 열여덟 개라 자리 보정 곱셈이 한 번뿐이기 때문이다
```

`k` 를 키우면 자리 수는 줄지만 자리 하나를 만드는 데 드는 곱셈이 `k − 1` 로 늘어납니다. 두
힘이 맞물려 `k = 2` 에서 가장 적어지고, 그 이유의 일반식은 뒤에서 따로 세웁니다.

```text
얻은 절차 한 벌
  1. result 를 1 을 mod 로 나눈 나머지로, b 를 base 를 mod 로 나눈 나머지로 둔다
  2. e 를 exp 로 두고, e 가 0 보다 큰 동안
  3.   e 의 최하위 비트가 1 이면 result 에 b 를 곱하고 mod 로 줄인다
  4.   b 를 제곱하고 mod 로 줄인다
  5.   e 를 오른쪽으로 한 칸 옮긴다
  6. result 를 돌려준다
     └ 곱셈이 지수만큼이던 것이 지수의 자릿수만큼이 된다
```

### 수행으로 알아보는 알고리즘 — 비트 다섯 개로 3^26 을 법 1,000 에서 구한다

아이디어를 세웠으니 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각
마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const [base, exp, mod] = [3n, 26n, 1000n];
// 이 절이 끝나면 329n 이 나와야 한다
```

왜 하필 이 셋일까요? 지수 26 의 이진 표현이 `11010` 이라 **0 인 비트와 1 인 비트가 둘 다
나오고**, 최하위 비트가 0 이라 누적을 건너뛰는 갈래가 첫 바퀴에서 먼저 실행됩니다. 밑 3 과 법
1,000 은 중간값이 세 자리 안에 들어와 표로 읽혀요.

```text
절차 전체를 한 장으로

  T1      result 를 1 % mod 로, b 를 base % mod 로, e 를 exp 로 둔다   ① 초기화
          e 가 0 보다 큰 동안:                                         ② 남은 비트가 있는가
  T2~T6     최하위 비트가 1 이면 result 에 b 를 곱한다                 ③ 누적
            b 를 제곱한다                                              ④ 다음 자리의 값
            e 를 오른쪽으로 한 칸 옮긴다                               ⑤ 다음 비트로
  T7      result 를 돌려준다
```

#### 1. 두 값을 법 안으로 옮기고 시작한다

첫 조각은 준비입니다. 누적값을 `1` 에서 출발시키고 밑을 법 안으로 옮기며, 아직 반복문에는
들어가지 않아요.

```ts
let result = 1n % mod;                 // ① 1 도 mod 로 나눈 나머지로 둔다
let b = ((base % mod) + mod) % mod;    // ① 밑을 [0, mod) 안으로 옮긴다
let e = exp;
```

`①` 의 두 줄이 각각 경계 하나씩을 맡습니다. 첫 줄의 `1n % mod` 는 `mod` 가 `1` 일 때 `0` 을
만들고, 둘째 줄은 음수 밑을 `0` 이상으로 옮겨요.

```text
T1 이 끝난 시점 — base = 3, exp = 26, mod = 1000
  result = 1    1 을 1,000 으로 나눈 나머지다
  b      = 3    3 을 1,000 으로 나눈 나머지다
  e      = 26   아직 아무 비트도 처리하지 않았다
```

| 입력이 이럴 때 | `1n % mod` | `((base % mod) + mod) % mod` |
| --- | --- | --- |
| `mod = 1` | `0` — 어떤 정수든 1 로 나눈 나머지는 0 이다 | `0` |
| `base = -3`, `mod = 5` | `1` | `-3 % 5` 가 `-3` 이라 5 를 더해 `2` 로 만든다 |
| `base = 1005`, `mod = 1000` | `1` | `5` |
| `base = 3`, `mod = 1000` | `1` | `3` |

둘째 줄에 `+ mod` 가 붙은 이유가 표의 `base = -3` 줄에 있습니다. JavaScript 의 `%` 는 나머지의 부호를
왼쪽 값에 맞추므로 밑이 음수면 결과도 음수이고, 그대로 두면 답이 `[0, mod)` 를 벗어나요.

#### 짚고 가기 — 나머지를 마지막에 한 번만 구해도 이 문제에서는 답이 안 틀린다

여기서 헷갈리기 쉬운 포인트는 **나머지를 언제 구하는가**입니다. 「곱셈을 다 하고 마지막에 한
번만 나머지를 구해도 같은 값 아닌가」로 읽기 쉬워요. 그 생각대로 적어 봅시다.

```ts
function lastModOnly(base: bigint, exp: bigint, mod: bigint): bigint {
  let acc = 1n;
  for (let i = 0n; i < exp; i++) acc = acc * base;   // 나머지를 안 구하고 계속 곱한다
  return ((acc % mod) + mod) % mod;                  // 마지막에 한 번만
}
```

**`bigint` 로 적으면 답이 한 번도 안 틀립니다.** 그런데 중간값의 자릿수가 지수를 따라 커지고,
같은 코드를 `number` 로 옮기면 그때는 답이 어긋나요.

<!--proof:pauseLastMod-->

```text
bigint 으로 곱셈을 다 한 뒤 마지막에 한 번만 나머지를 구한다
입력                     정본이 낸 답  마지막에 한 번만  중간값의 자릿수  판정
전개 입력 3^26 mod 1000           329               329               13  같다
3^40 mod 1000                     801               801               20  같다
2^64 mod 1000                     616               616               20  같다
7^50 mod 13                        10                10               43  같다

중간값의 자릿수는 지수를 따라 커진다 — 밑이 3 일 때
                 지수 exp  3^exp 의 자릿수
                       26               13
                    1,000              478
                  100,000           47,713
1,000,000,000,000,000,000    약 4.7712e+17

같은 방법을 number 로 하면 답이 어긋난다
입력             정본이 낸 답  number 로 마지막에 한 번만  판정
3^33 mod 1000             523                         523  같다
3^34 mod 1000             569                         568  틀리다
3^40 mod 1000             801                         768  틀리다
2^1023 mod 1000           608                         608  같다
2^1024 mod 1000           216                         NaN  틀리다

└ 밑이 3 일 때 2^53 = 9,007,199,254,740,992 보다 커지는 첫 지수가 34 이고,
  2^1024 에서 number 가 Infinity 가 된다
```

첫 표에서 답이 안 틀린다는 것을 먼저 적어 둡니다. `bigint` 는 자릿수를 필요한 만큼 늘리므로
값이 정확하고, 그래서 작은 입력만 시험하면 이 자리를 끝까지 모르고 넘어가요.

```text
그래도 고쳐야 하는 이유 둘
  자릿수   지수가 10^18 이면 중간값이 4.7712e+17 자리다      메모리에 담을 수 없다
  형변환   같은 코드를 number 로 옮기면 3^34 부터 어긋난다   2^1024 에서는 Infinity 가 된다
  └ 매 곱셈마다 나머지를 구하면 중간값이 mod 미만으로 묶여 두 문제가 함께 없어진다
```

`2^1023` 줄이 「같다」로 나온 것에도 이유가 있습니다. 2 의 거듭제곱은 `number` 로도 정확히
담기는 값이라 자릿수와 무관하게 어긋나지 않고, 그다음 한 걸음에서 표현 범위를 넘어요.

#### 2. 최하위 비트를 보고 누적한 뒤 밑을 제곱한다

둘째 조각은 반복문입니다. 바퀴 하나가 비트 하나를 처리해요 — 최하위 비트가 1 이면 누적하고,
그다음 밑을 제곱하고, 지수를 한 칸 옮깁니다.

```ts
while (e > 0n) {                       // ② 남은 비트가 있는가
  if ((e & 1n) === 1n) {               // ③ 최하위 비트가 1 이면
    result = (result * b) % mod;       // ③ 그 자리의 값을 누적한다
  }
  b = (b * b) % mod;                   // ④ 다음 자리의 값을 만든다
  e >>= 1n;                            // ⑤ 다음 비트로 옮긴다
}
```

`②` 는 `e` 가 26, 13, 6, 3, 1 일 때 참이고 0 에서 처음 거짓이 됩니다. `③` 은 그 다섯 바퀴 중
세 번만 실행되고 `④` 와 `⑤` 는 다섯 번 다 실행돼요. 앞 세 바퀴만 실행하면 이렇게 나옵니다.

| 걸음 | 바퀴 시작 `e` | 이번 비트 | 바퀴 시작 `b` | `③` 뒤 `result` | `④` 뒤 `b` | `⑤` 뒤 `e` |
| --- | --- | --- | --- | --- | --- | --- |
| T2 | 26 | 0 | 3 | 1 | 9 | 13 |
| T3 | 13 | 1 | 9 | 9 | 81 | 6 |
| T4 | 6 | 0 | 81 | 9 | 561 | 3 |

T3 이 이 세 줄의 핵심입니다. 비트가 1 이라 `result` 가 처음으로 `1` 에서 `9` 가 된 자리이고,
그 `9` 는 T2 가 만들어 둔 값이에요.

```text
T3 이 하는 일
  들고 있던 값   b = 9 다. T2 의 ④ 가 3 을 제곱해 만들었다
  이번 비트      13 의 최하위 비트가 1 이라 ③ 이 실행된다
  누적           result 가 1 · 9 = 9 가 된다
  제곱           ④ 가 9 · 9 = 81 을 만들어 다음 자리의 값으로 둔다
  └ ③ 이 쓰는 b 와 ④ 가 만드는 b 는 자리가 하나 다르다. 그 순서가 다음 「짚고 가기」의 주제다
```

#### 짚고 가기 — 제곱을 먼저 하면 한 자리 앞선 값을 곱하게 된다

여기서 헷갈리기 쉬운 포인트는 `③` 과 `④` 의 순서입니다. 「어차피 같은 바퀴 안이니 밑을 먼저
제곱하고 비트를 봐도 되지 않나」로 읽기 쉬워요. 두 줄의 자리를 바꿔 봅시다.

```ts
while (e > 0n) {
  b = (b * b) % mod;                   // 제곱을 먼저 했다
  if ((e & 1n) === 1n) result = (result * b) % mod;
  e >>= 1n;
}
```

다섯 입력에 실행해 봅니다.

<!--proof:pauseSquareFirst-->

```text
입력                     정본이 낸 답  제곱을 먼저 한 답  판정
전개 입력 3^26 mod 1000           329                241  틀리다
2^10 mod 7                          2                  4  틀리다
2^13 mod 5                          2                  4  틀리다
7^0 mod 13                          1                  1  같다
10^4 mod 9                          1                  1  같다

└ 지수가 0 이면 바퀴가 없어 같고, 10^4 mod 9 는 밑이 법에서 1 이라 몇 제곱을 해도 1 이다
```

어긋나는 이유는 하나입니다. 바퀴 `i` 를 시작하는 시점의 `b` 가 `base^(2^i)` 인데, 제곱을 먼저
하면 그 자리에서 `base^(2^(i+1))` 을 곱하게 돼요.

```text
전개 입력에서 자리 1 을 처리할 때 곱해지는 값

  정상 순서   자리 1 의 비트를 볼 때 b = 9      base^2 다        26 의 2 를 채운다
  바꾼 순서   자리 1 의 비트를 볼 때 b = 81     base^4 다        26 에 없는 4 를 채운다
  └ 자리마다 한 칸씩 어긋나 답이 329 가 아니라 241 이 된다
```

#### 3. 다섯 비트를 끝까지 실행해 답을 낸다

두 조각을 이어 고정 입력에 실행하면 일곱 걸음이 나옵니다. T1 은 준비, T2 부터 T6 까지가
반복문, T7 이 반환이에요.

**다섯 갈래가 모두 실행됐습니다.** T6 이 만든 `b = 841` 이 어디에도 안 쓰이는 것에도 이유가
있어요 — `④` 는 다음 자리를 위해 값을 만드는데 T6 이 마지막 자리라 그다음 자리가 없습니다.

| 라벨 | 무엇 | 전개에서 |
| --- | --- | --- |
| `①` | 초기화 | T1 에서 한 번 |
| `②` | 남은 비트가 있는가 | T2 부터 T6 까지 참 · T7 에서 거짓 |
| `③` | 비트가 1 이면 누적 | T3 T5 T6 에서 실행 · T2 T4 에서 건너뜀 |
| `④` | 다음 자리의 값을 만든다 | T2 부터 T6 까지 다섯 번 |
| `⑤` | 다음 비트로 옮긴다 | T2 부터 T6 까지 다섯 번 |

답이 정말 그 세 자리의 곱인지 확인하고 갑니다. `result` 를 만든 것은 자리 1 과 자리 3 과 자리
4 이고, 그 세 값을 직접 곱하면 같은 수가 나와야 해요.

| 무엇 | 값 |
| --- | --- |
| 켜진 자리 | 1, 3, 4 |
| 그 자리의 `base^(2^i)` | 9 · 561 · 721 |
| 직접 곱한 값을 법으로 줄이면 | `9 · 561 · 721 mod 1000 = 329` |
| 마지막 걸음 T6 의 `result` | 329 |

#### 4. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `result` 를 돌려주는 마지막 한
줄뿐이에요 — 지수가 `0` 이면 반복문이 한 번도 실행되지 않아 `1n % mod` 가 그대로 답이 됩니다.

```ts
export function fastPower(base: bigint, exp: bigint, mod: bigint): bigint {
  // ① 두 값을 법 안으로 옮기고 시작한다 — result 는 1 을 mod 로 나눈 나머지이고(mod 가 1
  //    이면 이 값이 0 이다), b 는 base 를 [0, mod) 로 옮긴 값이다.
  let result = 1n % mod;
  let b = ((base % mod) + mod) % mod;
  let e = exp;

  while (e > 0n) {
    // ② 아직 처리할 비트가 남았는가 — 남아 있으면 아래 세 줄을 한 번 실행한다.
    if ((e & 1n) === 1n) {
      // ③ 이번 비트가 1 이면 그 자리의 값을 result 에 곱해 둔다.
      result = (result * b) % mod;
    }
    // ④ 밑을 제곱해 다음 비트 자리의 값으로 만든다.
    b = (b * b) % mod;
    // ⑤ 지수를 오른쪽으로 한 칸 옮겨 다음 비트를 최하위로 보낸다.
    e >>= 1n;
  }

  return result;
}
```

```text
fastPower(3n, 26n, 1000n)          -> 329n
fastPower(2n, 10n, 1000n)          -> 24n
fastPower(123n, 0n, 1000n)         -> 1n
fastPower(5n, 100n, 1n)            -> 0n
fastPower(-3n, 3n, 5n)             -> 3n
fastPower(1005n, 2n, 1000n)        -> 25n
```

### 알아 두면 좋은 개념 — 결합법칙만 요구하는 거듭제곱

이 절차가 밑에 대해 쓴 성질은 둘뿐입니다 — `(x · y) · z = x · (y · z)` 인 **결합법칙**과, 곱해도
값이 안 바뀌는 **항등원** 1 이에요. 교환법칙도, 역원도, 값이 수인지도 한 번도 쓰지 않았습니다.

```text
절차가 밑에 대해 실제로 요구한 것

  결합법칙   (x · y) · z = x · (y · z) 라야 어떤 순서로 묶어도 같은 값이다
  항등원     1 · x = x 라야 result 의 시작값을 1 로 둘 수 있다
  안 쓴 것   교환법칙, 역원, 크기 비교
  └ 결합법칙과 항등원만 있는 구조를 모노이드라고 부른다
```

그래서 같은 절차가 **수가 아닌 대상**에도 그대로 적용됩니다. 곱셈 자리에 다른 결합 연산을
끼우면 되고, 이 저장소 안에도 그 사례가 있어요.

| 밑이 무엇인가 | 곱셈 자리에 오는 연산 | 무엇을 구하는가 |
| --- | --- | --- |
| 법 `mod` 의 정수 | 곱한 뒤 나머지 | 이 글이 구하는 `base^exp mod mod` |
| 2×2 정수 행렬 | 행렬 곱 | 피보나치 수열의 임의의 항 |
| 문자열 | 이어 붙이기 | 같은 문자열을 여러 번 이어 붙인 것 |
| 그래프의 인접 행렬 | min-plus 곱 | 간선을 정확히 몇 개 쓰는 최단 거리 |

행렬로 바꾼 사례는
[`matrixPowerFibonacci`](../../bit-manipulation/matrixPowerFibonacci/matrixPowerFibonacci-problem.md)
가 다룹니다. 지수를 거꾸로 찾는 문제인
[`babyStepGiantStep`](../babyStepGiantStep/babyStepGiantStep-guide.md) 의 정본은 같은 절차를
`power` 라는 이름으로 싣고, 큰 걸음의 보폭을 구하는 데 씁니다.

```text
같은 그림, 다른 곱셈 — 지수 26 을 그대로 옮기면

  정수     3^26 mod 1000 을 9 · 561 · 721 mod 1000 으로 만든다
  행렬     M^26 을 M^2 · M^8 · M^16 으로 만든다
  문자열   "ab" 를 26 번 이어 붙인 것을 "ab"^2 · "ab"^8 · "ab"^16 으로 만든다
  └ 켜진 자리 1, 3, 4 는 밑이 무엇이든 그대로다. 바뀌는 것은 곱셈의 뜻 하나뿐이다
```

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 곱셈 횟수를 식으로 어떻게 닫는지,
무엇이 매 바퀴 참으로 남는지, 그리고 곱셈이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다.

- **같은 값을 여러 번 곱하는 것이 목표입니다.** 서로 다른 값을 곱하는 것이면 자리마다의 제곱을
  재사용할 수 없어요.
- **곱셈이 결합법칙을 지킵니다.** 이 조건만 있으면 밑이 수가 아니어도 됩니다.
- **곱셈 한 번의 비용이 값의 크기와 상관없이 일정합니다.** 법으로 줄여 값을 `mod` 미만으로 묶는
  것이 그 조건을 만듭니다.
- **답이 한 번 필요합니다.** 같은 밑에 여러 지수를 반복해서 물으면 미리 표를 만드는 설계가
  따로 있어요.

```text
네 조건이 코드의 모양을 그대로 정한다
  같은 값을 곱한다        -> 자리마다의 제곱을 재사용한다
  결합법칙만 쓴다         -> 밑을 행렬이나 문자열로 바꿔도 코드가 같다
  곱셈 비용이 일정하다    -> 매 곱셈 뒤에 나머지를 구한다
  답이 한 번 필요하다     -> 미리 만드는 표가 없다
```

셋째 줄이 이 절차의 경계입니다. 법이 없어 값이 계속 커지는 문제에서는 곱셈 한 번의 비용이
자릿수를 따라 커지므로, 곱셈 횟수만 세는 이 계산이 그대로 성립하지 않아요.

```text
법이 있을 때와 없을 때
  법이 있다   값이 mod 미만으로 묶인다           곱셈 한 번의 비용이 일정하다
  법이 없다   값의 자릿수가 지수를 따라 커진다   곱셈 한 번의 비용도 함께 커진다
  └ 이 글이 세는 것은 곱셈의 횟수이고, 그 횟수가 곧 시간이 되는 것은 법이 있을 때다
```

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "거듭제곱을 법으로 나눈 나머지를 구하라"   <- 법이 붙은 거듭제곱이다
  "지수가 10^18 까지"  "매우 큰 지수"        <- 지수를 차례로 소모할 수 없다
  "역원"  "1,000,000,007 로 나눈 나머지"     <- 페르마의 소정리로 a^(p-2) 를 구한다
  "수열의 먼 항을 구하라"  "선형 점화식"     <- 행렬로 바꿔 같은 절차를 쓴다

제약에 이런 모양이 보이면
  지수가 32 비트를 넘어 64 비트 정수로 들어온다
  법이 소수이고 10^9 언저리다

반대로 이런 말이 보이면 해당하지 않는다
  "지수가 음수일 수 있다"                    <- 역원이 있어야 하고 법이 소수여야 한다
  "밑이 매번 바뀐다"  "지수가 매번 바뀐다"   <- 미리 만드는 표를 재사용할 수 없다
  "법 없이 정확한 값을 출력하라"             <- 값의 자릿수가 지수를 따라 커진다
```

첫 무리의 셋째 줄이 이 절차가 가장 자주 쓰이는 자리입니다. 법이 소수 `p` 일 때 `a` 의 역원이
`a^(p−2) mod p` 이므로, 나눗셈이 거듭제곱 한 번으로 바뀌어요.

```text
역원을 거듭제곱으로 바꾸는 자리
  구하고 싶은 것    1 / a 를 법 p 에서 구한다. 이것이 a 의 역원이다
  페르마의 소정리   p 가 소수이고 a 가 p 의 배수가 아니면 a^(p-1) ≡ 1 (mod p)
  그러면            a · a^(p-2) ≡ 1 이므로 역원이 a^(p-2) 다
  └ 지수 p-2 가 10^9 언저리라 이 글의 절차가 그대로 필요하다
```

#### 실제로 쓰이는 곳

- **CPython 의 세 인자 `pow`.** `Objects/longobject.c` 의 `long_pow` 가 이 절차를 그대로
  싣습니다. 주석이 *"For exponentiation, use the binary left-to-right algorithm unless the
  exponent contains more than HUGE_EXP_CUTOFF bits. In that case, do (no more than)
  EXP_WINDOW_SIZE bits at a time."* 라고 적고, `#define EXP_WINDOW_SIZE 5` 와
  `#define HUGE_EXP_CUTOFF 60` 이 그 아래 있어요. 지수가 60 비트 아래면 이 글의 절차를 그대로
  쓰고, 그보다 크면 다음 절이 다루는 설계로 갈아탑니다.
  ([`Objects/longobject.c`](https://raw.githubusercontent.com/python/cpython/main/Objects/longobject.c),
  조회 2026-08-30)

```text
CPython 이 남긴 계산 (같은 파일의 주석)
  "Suppose the exponent has bit length e. All ways of doing this need e squarings."
  "The binary method also needs a multiply for each bit set."
  "the binary method needs about e/2 extra mults and the window method about 16 + e/5"
  └ 앞의 두 줄이 이 글이 센 n + s 와 같은 계산이다
```

- **Go 표준 라이브러리 `math/big`.** `src/math/big/nat.go` 의 `expNN` 이 같은 일을 하고,
  주석이 *"If m != 0 (i.e., len(m) != 0), expNN sets z to x\*\*y mod m; otherwise it sets z to
  x\*\*y."* 로 이 함수가 구하는 값을 적습니다. 인용문의 `m` 이 이 글의 `mod` 이고 `y` 가
  `exp` 예요. 큰 지수에서는 `expNNWindowed` 로 갈아타는데, 그 주석이
  *"expNNWindowed calculates x\*\*y mod m using a fixed, 4-bit window, where m = 2\*\*logM."* 입니다.
  ([`src/math/big/nat.go`](https://raw.githubusercontent.com/golang/go/master/src/math/big/nat.go),
  조회 2026-08-30)

| 무엇 | 이 글 | CPython | Go |
| --- | --- | --- | --- |
| 작은 지수의 절차 | 비트 하나씩 | binary left-to-right | `expNN` 의 기본 경로 |
| 큰 지수의 절차 | 없다 | `EXP_WINDOW_SIZE` 5 비트 창 | `expNNWindowed` 의 4 비트 창 |
| 갈아타는 기준 | 없다 | `HUGE_EXP_CUTOFF` 60 비트 | 주석으로 확인하지 못했습니다 |

Go 쪽의 갈아타는 기준은 소스의 조건문에 있고 주석 문장으로 적혀 있지 않아 **원문 인용으로
옮기지 못했습니다.** CPython 쪽은 주석과 매크로 값이 둘 다 있어 그대로 옮겼어요.

**둘 다 지수가 작을 때는 이 글의 절차를 쓰고 클 때만 창 방식으로 갈아탑니다.** 그 갈림이 다음
절의 주제예요.

#### 경쟁 설계와의 대조

같은 목표(같은 밑의 거듭제곱을 법에서 구하는 것)를 노리는 다른 절차로 **5 비트 슬라이딩 창**이
있습니다. 밑의 홀수 거듭제곱 `base^1, base^3, …, base^31` 을 미리 표로 만들어 두고, 지수의
비트를 최상위부터 최대 다섯 개씩 묶어 표의 칸 하나를 한 번에 곱하는 방식이에요.

```text
두 설계가 지수 하나를 처리하는 방법
  비트 하나씩   자리마다 제곱 한 번, 켜진 자리마다 곱셈 한 번   미리 만드는 표가 없다
  5 비트 창     자리마다 제곱 한 번, 묶음마다 곱셈 한 번        표를 만드는 데 곱셈 16 번
  └ 창 방식은 곱셈을 묶음 단위로 줄이는 대신 표를 만드는 값을 먼저 낸다
```

같은 밑(`3`)과 같은 법(`1,000,000,007`)에 두 설계를 실행하고 **모듈러 곱셈 횟수**를 셌습니다.
지수는 다섯이에요 — 전개 입력 `26`, 40 비트, 41 비트, 제약 규모 `10^18`, 그리고 1,024 비트입니다.
전개 입력이 아닌 넷은 생성식 `exp(n) = (3^n mod 2^n) | 2^(n−1)` 로 만들었고, 최상위 비트를
세워 정확히 `n` 비트가 되게 한 것이에요. **전개 입력만으로 재지 않은 이유**는 그 지수가 비트
다섯이라 표를 만드는 곱셈 16 번이 전체를 덮어 두 설계의 계수가 갈리지 않기 때문입니다.

| 지수 | 비트 하나씩 | 5 비트 창 | 어느 쪽이 적은가 |
| --- | --- | --- | --- |
| 전개 입력 26 | **8** | 17 | 비트 하나씩이 절반 이하입니다 |
| 40 비트 | **58** | 58 | 같습니다 |
| 41 비트 | 68 | **59** | **여기서 순서가 뒤집힙니다** |
| `10^18` (60 비트) | 84 | **78** | 창 쪽이 6 번 적습니다 |
| 1,024 비트 | 1,503 | **1,206** | 창 쪽이 약 20% 적습니다 |

**저장 칸은 3 개 대 19 개입니다.** 메모리에서는 갈리지 않고 비트 하나씩이 계속 적어요 —
갈리는 것은 곱셈 횟수이고, 그 경계가 이 생성식에서 **지수 41 비트**입니다.

```text
경계가 그 자리인 이유

  창 방식이 먼저 내는 곱셈     표 만들기 16 번. 지수의 비트 수와 상관없이 고정이다
  비트 하나씩이 더 내는 곱셈   켜진 비트마다 한 번
  창 방식이 더 내는 곱셈       묶음마다 한 번. 비트 다섯에 하나꼴이다
  └ 비트 수가 늘어도 첫 줄의 16 은 그대로라, 둘째 줄과 셋째 줄의 차이가 16 을 넘는 자리에서
    순서가 뒤집힌다. 이 생성식에서는 그 자리가 41 비트다
```

**이 절차가 내주는 것은 큰 지수에서의 곱셈 횟수입니다.** 지수가 1,024 비트면 297 번을 더 하고,
그 대신 얻는 것이 셋이에요.

```text
비트 하나씩이 얻는 것
  저장 칸   값 3 개로 끝난다        창 방식은 표 16 칸을 더 든다
  전처리    없다                    표를 만드는 데만 곱셈 16 번이 든다
  구현      반복문 하나             창의 아래 끝을 찾는 규칙을 따로 맞춰야 한다
  └ 지수가 41 비트 아래면 첫 열이 답이다
```

이 문제의 제약이 지수 `10^18`, 곧 60 비트까지라 **경계를 넘습니다.** 그래서 곱셈 횟수만 보면
창 방식이 84 대 78 로 앞서요. 판정이 뒤집히는 조건은 둘입니다.

```text
어느 쪽을 고르는가

  지수가 41 비트 아래   비트 하나씩이 곱셈도 적고 저장 칸도 적다   40 비트에서 58 대 58 로 같다
  지수가 41 비트 위     창 방식이 곱셈이 적다                      저장 칸은 3 대 19 로 뒤진다
  └ 이 문제의 제약은 60 비트라 아랫줄이고, 저장 칸을 얼마나 아끼려는가가 남은 갈림이다
```

CPython 이 갈아타는 기준을 60 비트로 둔 것이 이 판정과 같은 자리입니다. 이 글이 비트 하나씩을
가르치는 이유는 그 절차가 창 방식의 **본체**이기도 해서예요 — 창 너비를 1 로 두면 표가 한 칸이
되고 두 절차가 같아집니다.

### 수식 정의와 유도

지수의 이진 표현과 이 절차의 곱셈 횟수를 기호로 정의합니다. `c_i` 는 `exp` 의 `i` 번째 비트이고,
`n` 은 비트 수, `s` 는 1 인 비트의 개수예요. `n` 의 식은 `exp` 가 `1` 이상일 때의 것이고,
`exp = 0` 이면 비트가 하나도 없어 `n` 도 `s` 도 `0` 입니다.

$$\text{exp} = \sum_{i=0}^{n-1} c_i 2^i, \quad c_i \in \{0, 1\}, \qquad n = \lfloor \log_2 \text{exp} \rfloor + 1, \qquad s = \sum_{i=0}^{n-1} c_i$$

```text
정의를 값에 넣어 봅니다 — exp = 26
  c_0 = 0   c_1 = 1   c_2 = 0   c_3 = 1   c_4 = 1
  n         자리가 0 부터 4 까지라 5
  s         c 를 다 더하면 3
```

자리마다의 값도 기호로 적습니다. 이 값을 `β_i` 라 적고, 코드에서는 바퀴 `i` 를 시작하는 시점의
`b` 가 그 값입니다.

$$\beta_i = \text{base}^{2^i} \bmod \text{mod}, \qquad \beta_0 = \text{base} \bmod \text{mod}, \qquad \beta_{i+1} = \beta_i^2 \bmod \text{mod}$$

```text
정의를 값에 넣어 봅니다 — base = 3, mod = 1,000
  β_0   3 mod 1,000                       3
  β_1   3 을 제곱해 1,000 으로 줄이면     9
  β_2   9 를 제곱해 1,000 으로 줄이면     81
  β_3   81 을 제곱해 1,000 으로 줄이면    561
  β_4   561 을 제곱해 1,000 으로 줄이면   721
```

정의 셋을 전개 입력에 넣어 검산하고 갑시다.

<!--proof:mathCheck-->

```text
비트 자리  2^i  c_i  base^(2^i) mod 1000
i = 0        1    0                    3
i = 1        2    1                    9
i = 2        4    0                   81
i = 3        8    1                  561
i = 4       16    1                  721

켜진 자리의 값만 곱한다   9 · 561 · 721 mod 1000 = 329
켜진 자리의 합            2 + 8 + 16 = 26
n = 5   s = 3   n + s = 8
└ 정본이 낸 답 329 와 같다
```

이제 유도합니다. 지수법칙 `x^(u+v) = x^u · x^v` 를 이진 표현에 적용하면 거듭제곱이 자리마다의
값들의 곱으로 갈라져요.

$$\text{base}^{\text{exp}} = \text{base}^{\sum_i c_i 2^i} = \prod_{i=0}^{n-1} \bigl(\text{base}^{2^i}\bigr)^{c_i} = \prod_{i : c_i = 1} \beta_i \pmod{\text{mod}}$$

```text
변형 셋이 무엇을 했는가
  첫째   exp 를 이진 표현으로 바꿔 적었다        정의를 그대로 넣은 것이다
  둘째   지수의 합을 거듭제곱의 곱으로 갈랐다    x^(u+v) = x^u · x^v
  셋째   c_i 가 0 인 항은 1 이라 지웠다          x^0 = 1
  └ 남은 것이 켜진 자리의 β_i 들의 곱이다
```

곱셈 횟수도 같은 식에서 나옵니다. `β` 를 자리 하나 올리는 데 곱셈이 한 번, 켜진 자리를 누적하는
데 곱셈이 한 번이에요.

$$M(\text{exp}) = \underbrace{n}_{\beta \text{ 를 올린다}} + \underbrace{s}_{\text{누적한다}}, \qquad n + 1 \le M(\text{exp}) \le 2n$$

```text
경계 둘이 어디서 나오는가
  s 가 가장 작을 때   s = 1    exp 가 2 의 거듭제곱일 때다        M = n + 1
  s 가 가장 클 때     s = n    exp 의 비트가 전부 1 일 때다       M = 2n
  └ s 는 1 이상 n 이하다. 최상위 비트는 정의상 1 이므로 s = 0 인 경우가 없다
```

여기서 본문의 값만으로는 안 나오는 것이 나옵니다. **접는 비율 `k` 를 임의로 두었을 때 `k = 2`
가 최소라는 것**이에요. `k` 로 접으면 자리 수가 `log_k(\text{exp})` 이고 자리 하나에 드는 곱셈이
`k − 1` 에 그 자리의 숫자를 더한 값입니다.

$$M_k(\text{exp}) \approx \left(\frac{\ln \text{exp}}{\ln k}\right)\left(k - 1 + \frac{k-1}{2}\right) = \frac{3}{2} \cdot \frac{k-1}{\ln k} \cdot \ln \text{exp}$$

```text
식의 두 조각이 어디서 왔는가
  자리 수            ln exp / ln k   k 로 나눠 내려가는 걸음의 수다
  자리 하나의 곱셈   k - 1           밑을 k 제곱하는 데 드는 곱셈이다
  자리 보정          (k - 1) / 2     자리의 숫자가 0 부터 k-1 까지 고르다고 본 평균이다
  └ k = 2 를 넣으면 1 + 0.5 = 1.5 이고, 실제로 n + s 에서 s 가 n 의 절반 언저리다
```

`ln exp` 는 `k` 와 상관없는 값이라, 최소가 되는 `k` 는 `(k − 1) / ln k` 하나로 정해집니다.

<!--proof:mathRadix-->

```text
 k  k - 1    ln k  (k - 1) / ln k
 2      1  0.6931          1.4427
 3      2  1.0986          1.8205
 4      3  1.3863          2.1640
 8      7  2.0794          3.3663
10      9  2.3026          3.9087

└ k = 2 에서 가장 작다. 이 값이 지수 하나를 처리하는 데 드는 곱셈의 비율이다
```

이 비율을 그대로 옮긴 조각이 아래입니다. `k = 2` 를 넣으면 `k − 1` 이 1 이 되어 제곱 한 번이
되고, 그것이 파트 1 의 `④` 예요.

```ts
// 자리 하나를 올리는 데 드는 곱셈. k = 2 면 1 번, k = 4 면 3 번이다.
const perPlace = (k: number): number => k - 1;
// 자리 수. k 가 커질수록 줄지만 perPlace 가 그보다 빨리 커진다.
const places = (exp: number, k: number): number => Math.log(exp) / Math.log(k);
```

```text
                1,000,000  20   7         27     27          21       40

  차례로 곱하는 방법은 1,000,000,000,000,000,000 번이다 — 자릿수가 19 에서 2 로 줄어든다
```

### 불변식 — 바퀴를 시작할 때마다 result 와 b^e 의 곱이 처음 값의 거듭제곱과 법에서 같다

파트 1 에서 코드가 동작하는 것을 일곱 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 문장으로 세우고 그것이
실제로 유지되는지 확인해 봅시다.

> 반복문의 각 바퀴를 시작하는 시점에 `result · b^e ≡ base^exp (mod mod)` 가 참입니다. 여기서
> `base` 와 `exp` 는 처음 받은 입력이고 `result`·`b`·`e` 는 그 시점의 값입니다.

```text
  왼쪽이 뜻하는 것     이미 처리한 자리들의 곱(result)과 아직 처리 못 한 몫(b^e)
  오른쪽이 뜻하는 것   구하려는 값 그 자체

  둘 다 「바퀴를 시작하는 시점」에 참이다   바퀴 도중에는 세 줄 사이에서 잠깐 어긋난다
```

문장 하나에 두 몫이 들어 있습니다. `result` 는 이미 확정된 답의 일부이고, `b^e` 는 아직 남은
부분이에요. 바퀴가 하는 일은 남은 쪽에서 자리 하나를 떼어 확정된 쪽으로 옮기는 것입니다.

**출발점부터 봅시다.** 반복문에 들어가기 전 `result` 는 `1 % mod`, `b` 는 `base % mod` 를
`[0, mod)` 로 옮긴 값, `e` 는 `exp` 입니다. 그러면 왼쪽이 `1 · base^exp` 라 오른쪽과 같아요.

| 시점 | 하는 일 | 불변식이 유지되는 근거 |
| --- | --- | --- |
| 시작 | `result = 1 % mod`, `b = base % mod`, `e = exp` | `1 · base^exp = base^exp` 다 |
| `e` 가 짝수인 바퀴 | 누적 `result = (result * b) % mod` 을 건너뛰고 밑 제곱과 지수 옮김만 | `b^e = (b^2)^(e/2)` 다 |
| `e` 가 홀수인 바퀴 | 누적 · 밑 제곱 · 지수 옮김을 다 | `b^e = b · (b^2)^((e−1)/2)` 다 |
| 종료 | `e = 0` 이 되어 멈춘다 | `b^0 = 1` 이라 `result` 자체가 답이다 |

가운데 두 줄이 이 논증의 핵심입니다. 정수 `e` 는 짝수이거나 홀수이고 그 사이의 다른 경우가
없으므로, 두 줄이 갈래를 빠짐없이 덮어요.

| 바퀴 시작의 `e` | 바퀴가 하는 일 | 바퀴 끝의 왼쪽 |
| --- | --- | --- |
| 짝수 | `b` 를 `b^2` 로, `e` 를 `e/2` 로 | `result · (b^2)^(e/2)` = 바퀴 시작의 왼쪽 |
| 홀수 | `result` 를 `result·b` 로, 나머지는 위와 같이 | `(result·b) · (b^2)^((e−1)/2)` = 바퀴 시작의 왼쪽 |

홀수 줄의 등식은 지수 하나를 떼어 낸 것입니다. `b^e` 에서 `b` 를 하나 빼면 남는 지수가
`e − 1` 이고 그것이 짝수라, 짝수 줄과 같은 모양이 돼요.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| `exp = 0` | 반복문이 한 번도 실행되지 않는다 | `1 % mod` 가 그대로 답이다 |
| `mod = 1` | `result` 의 시작값이 `0` 이다 | 어떤 곱셈을 해도 `0` 이다 |
| `base = 0`, `exp = 0` | 반복문이 없다 | `1` 이다 |
| `base = 0`, `exp > 0` | 첫 켜진 자리에서 `result` 가 `0` 이 된다 | `0` 이다 |
| `base` 가 음수 | 시작에서 `[0, mod)` 로 옮긴다 | 같은 나머지의 양수와 답이 같다 |
| `base` 가 `mod` 보다 크다 | 시작에서 `mod` 로 줄인다 | 줄인 값으로 계산한 것과 같다 |
| `exp` 가 2 의 거듭제곱 | 켜진 자리가 하나뿐이다 | 곱셈이 `n + 1` 번으로 가장 적다 |

**이제 깨뜨려 봅시다.** 불변식에서 `b^e` 를 유지하던 줄은 밑을 제곱하는 그 한 줄이에요.
「비트가 0 인 바퀴는 아무 일도 안 하니 제곱도 필요 없지 않나」라는 생각으로 그 줄을 지워
봅니다.

```ts
while (e > 0n) {
  if ((e & 1n) === 1n) result = (result * b) % mod;
  b = b % mod;                     // 제곱을 없애 b 가 처음 값에 머문다
  e >>= 1n;
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutantNoSquare-->

```text
입력                     정본이 낸 답  제곱을 없앤 답  판정
전개 입력 3^26 mod 1000           329              27  틀리다
2^10 mod 1000                      24               4  틀리다
3^5 mod 100                        43               9  틀리다
2^1 mod 7                           2               2  같다
7^0 mod 13                          1               1  같다

전개 입력에서 b 가 지켜야 할 값 3 9 81 561 721 이 3 3 3 3 3 으로 바뀐다
└ b^e 를 유지하던 줄이 사라지면 result 는 1 인 비트 수만큼 밑을 곱한 값이 된다
```

제곱이 없어지면 `b` 는 제자리인데 `e` 는 그대로 절반이 됩니다. 그러면 남은 몫이
`(b^2)^(e/2)` 가 아니라 `b^(e/2)` 가 되어, 바퀴마다 남은 지수의 절반이 사라져요.

```text
전개 입력에서 두 값이 갈리는 자리
  정본의 b         3 9 81 561 721   바퀴마다 자리를 하나 올라간다
  변이의 b         3 3 3 3 3        자리 0 에 머문다
  변이가 내는 답   3^3 = 27         1 인 비트가 셋이라 밑을 세 번 곱한 값이다
```

마지막 두 줄이 「같다」로 나온 것에도 이유가 있습니다. 지수가 1 이면 바퀴가 한 번뿐이라 제곱한
값을 쓸 자리가 없고, 지수가 0 이면 바퀴 자체가 없어요.

### 비용 계산

#### 비용을 세는 과정

한 번의 실행이 하는 일은 세 무리입니다 — 두 값을 법 안으로 옮기는 것, 바퀴마다 비트 하나를
처리하는 것, 답을 돌려주는 것이에요. 전개의 걸음으로 확인하면 이렇게 나뉩니다.

<!--proof:perfCount-->

```text
무리    어느 걸음인가    걸음 수  걸음마다 제곱  걸음마다 누적  이 입력에서
초기화  T1                     1              0              0            0
바퀴    T2 부터 T6 까지        5              1       0 또는 1            8
반환    T7                     1              0              0            0
합계                                                                      8

└ 제곱 5 번과 누적 3 번이다. 앞은 비트 수 n 이고 뒤는 1 인 비트 s 다
```

T1 과 T7 은 값을 옮기기만 하는 자리라 곱셈이 없습니다. `1n % mod` 와 `((base % mod) + mod) % mod`
는 나머지 연산이지 곱셈이 아니에요.

```text
총식 = 초기화 + 바퀴 + 반환

  초기화        곱셈 0
  바퀴          제곱 n + 누적 s
  반환          곱셈 0
  모듈러 곱셈   n + s
  exp = 26 이면 5 + 3 = 8 로 위 표와 같다
  잡는 칸       result · b · e 셋
```

**곱셈 횟수가 지수의 크기가 아니라 비트 모양으로 정해집니다.** 비트 수가 바퀴 수를 정하고, 1 인
비트의 개수가 누적 횟수를 정해요.

```text
여기서 센 것은 모듈러 곱셈 전부다
  추가로 잡는 메모리   값 3 개 (result · b · e)
  안 센 것             나머지 연산 n + s 번과 비트 검사 n 번
                       둘 다 곱셈 횟수에 비례하므로 총식의 차수는 그대로다
                       └ bigint 하나의 곱셈 비용까지 세면 여기에 법의 자릿수가 곱해진다
```

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면
안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (`exp` 가 2 의 거듭제곱) | `O(log exp)` | `Θ(log exp)` — 곱셈이 `n + 1` 번이다 |
| **평균적인 경우** (비트가 무작위라면 `s ≈ n/2`) | `O(log exp)` | `Θ(log exp)` |
| **최악의 경우** (`exp` 의 비트가 전부 1) | `O(log exp)` | `Θ(log exp)` — 곱셈이 `2n` 번이다 |

세 줄이 같은 차수인 것이 이 절차의 성질입니다. 최선과 최악의 곱셈 횟수가 `n + 1` 과 `2n` 이라
**두 배 안에서만 갈리고**, 두 값 다 `n` 에 비례해요.

```text
상한과 타이트한 값을 가르는 자리
  O(log exp)   이 절차의 곱셈 횟수가 그보다 크지 않다는 것만 말한다    상한이다
  Θ(log exp)   위아래로 같은 차수라 실제로 그만큼 든다는 것도 말한다   타이트한 값이다
  └ 최선에서도 곱셈이 n + 1 번이라 아래로도 n 에 비례한다. 그래서 Θ 로 적을 수 있다
```

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 하나도 없다는 것이 이 절차의
특징이에요 — 표도, 정렬도, 미리 만드는 값도 없습니다.

```text
총식 = 모듈러 곱셈 (n + s) 번 + 잡는 칸 3 개

  n = ⌊log2 exp⌋ + 1        exp = 10^18 이면 60
  s 는 1 이상 n 이하        exp = 10^18 이면 24
  곱셈                      exp = 10^18 이면 84 번
  └ 여기서 세는 단위는 「법이 붙은 곱셈 한 번」이다
```

**보장의 종류는 전부 최악 보장입니다.** 해시도, 무작위성도, 분할 상환도 쓰지 않아요 — 어떤
입력을 넣어도 곱셈이 `2n` 번을 넘지 않습니다.

```text
기댓값이 끼어들 자리가 없다
  바퀴 수      지수의 비트 수로 정해진다     입력 분포를 가정하지 않는다
  누적 횟수    1 인 비트의 개수다            그 지수를 보면 바로 세어진다
  한 바퀴      제곱 1 과 누적 0 또는 1       평균이 아니라 상수다
  └ 평균적인 경우의 s ≈ n/2 는 「비트가 무작위라면」이라는 가정이 붙은 값이고,
    최악 보장 2n 은 가정 없이 성립한다
```

#### 최악을 만드는 입력

곱셈 횟수를 최대로 만들려면 **비트 수와 1 인 비트의 개수를 함께 최대로** 해야 합니다. 지수를
제약의 상한으로 두는 것만으로는 부족해요. 그것을 값으로 확인해 봅시다.

<!--proof:worstShape-->

```text
지수의 모양                           지수 exp  비트 수 n  1 인 비트 s  곱셈 n + s
2^59                   576,460,752,303,423,488         60            1          61
10^18 (제약의 상한)  1,000,000,000,000,000,000         60           24          84
2^59 - 1               576,460,752,303,423,487         59           59         118
2^59 + 2^58 - 1        864,691,128,455,135,231         60           59         119

└ 제약 안에서 곱셈이 가장 많은 지수는 마지막 줄의 864,691,128,455,135,231 이고 119 번이다.
  상한인 10^18 보다 작은 지수가 더 많은 곱셈을 쓴다
```

**「지수가 클수록 느리다」는 이 절차에서 성립하지 않습니다.** 물려받은 통념이 여기서는 맞지
않아요 — 셋째 줄의 지수는 상한의 약 58% 인데 곱셈이 118 번으로 상한의 84 번보다 많습니다.

```text
최악은 축마다 다른 입력이 만든다
  곱셈 횟수의 최악   2^59 + 2^58 - 1        119 번. 비트 60 개 중 59 개가 1 이다
  잡는 칸의 최악     어떤 입력이든 같다     값 3 개
  값 크기의 최악     mod 가 클 때           반환값이 mod - 1 까지 간다
  └ 첫 줄은 지수의 비트 모양만 보고, 셋째 줄은 지수를 아예 안 본다
```

마지막 줄의 지수를 만드는 방법은 하나입니다. 상한 아래에서 1 인 비트를 최대한 세우는 것이고,
그것이 `2^59 + 2^58 − 1` 이에요.

| 최악으로 만들 축 | 입력 | 값 |
| --- | --- | --- |
| 곱셈 횟수 | `exp = 864,691,128,455,135,231` | 119 번 |
| 잡는 칸 | 어떤 입력이든 | 3 개 |
| 반환값의 크기 | `mod` 를 제약의 최댓값으로 | `mod − 1` |

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 지수를 이진수로 적어 **켜진 자리의 `base^(2^i)`
만 곱했고**, 그 값들은 직전 자리를 제곱해 하나씩 나오며, 곱셈 횟수는 지수의 크기가 아니라
비트 수와 1 인 비트의 개수의 합입니다.

```text
1.   지수를 2 의 거듭제곱의 합으로 적는다   자리마다 0 또는 1 이다
2.   자리마다 밑을 제곱해 올린다            곱셈 n 번
3.   켜진 자리에서만 result 에 곱한다       곱셈 s 번
```

먼저 답이 붙는 문제 하나입니다. 전개의 T6 은 마지막 바퀴였고, 거기서 `④` 가 `b` 를 721 에서
841 로 제곱했어요. 그런데 그 841 은 어디에도 쓰이지 않습니다. 그러면 마지막 바퀴에서 `④` 를
건너뛰도록 조건을 붙이는 것이 나을까요?

```text
T6   e = 1   비트 1   b = 721   result 49 에서 329 로   ④ 가 b 를 841 로 만든다
```

<!--check:whySquareAlways-->
붙일 수 있지만 얻는 것이 적습니다. 마지막 바퀴인지 판단하려면 바퀴 안에서 `e` 가 1 인지
검사해야 하고, 그 검사는 바퀴마다 한 번씩 늘어나요. 그렇게 해서 아끼는 곱셈은 호출
하나마다 **정확히 한 번**입니다.

```text
마지막 제곱을 건너뛰면
  아끼는 것   곱셈 1 번        지수의 비트 수와 상관없이 언제나 1 번이다
  드는 것     조건 검사 n 번   바퀴마다 「마지막인가」를 물어야 한다
  전체에서    84 번이 83 번    exp = 10^18 에서 1.2% 다
  └ 조건 없이 매번 제곱하는 쪽이 코드도 짧고 차수도 같다
```

곱셈 횟수의 차수는 `n + s` 로 그대로이고, 아끼는 1 번은 상수항입니다. 그래서 이 저장소의
정본은 조건을 붙이지 않습니다.
<!--/check-->

- 지수가 음수일 수도 있다고 요구가 바뀌면 무엇이 더 필요할까요? 법이 소수 `p` 일 때
  `a^(−1) ≡ a^(p−2) (mod p)` 라는 것을 쓸 수 있는데, 그러려면 `a` 에 어떤 조건이 붙어야
  하는지와 `p` 가 소수가 아니면 왜 이 방법이 성립하지 않는지를 적어 보세요.
- `③` 과 `④` 의 순서를 바꾼 코드가 T3 에서 어떤 값을 곱하게 되는지, 그리고 그 값이 정상 순서의
  값과 몇 자리 어긋나는지 손으로 채워 보세요. 두 번째 「짚고 가기」이 답을 값으로 보였으니, 걸음
  하나하나의 `b` 를 T2 부터 T6 까지 두 줄로 나란히 적어 대조하면 됩니다.
- 밑이 고정이고 지수만 `Q` 번 바뀌는 문제로 바꾸면, 5 비트 창 방식의 표 16 칸을 한 번만 만들어
  `Q` 번 재사용할 수 있습니다. 두 설계의 곱셈 횟수를 `Q` 와 지수의 비트 수로 각각 쓰고, 어느
  `Q` 부터 순서가 뒤집히는지 따져 보세요.
