# 유클리드 호제법 — 큰 수를 나머지로 바꿔도 공약수 집합은 그대로다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 1 부터 전부
나눠 보는 방법에서 출발해 두 수를 나머지로 줄여 가는 방법까지 가고, 그 방법을 단계마다 값으로 푼 뒤,
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

두 정수를 **둘 다 나누어떨어지게 하는 수**를 공약수라고 부르고, 그중 가장 큰 것이 **최대공약수**입니다.
공약수는 부호와 상관이 없어서, 음수가 들어오면 절댓값으로 봐요. 이 글의 전개 입력 하나를 먼저 값으로
보겠습니다.

<!--proof:conceptTask-->
```text
gcd(-273n, 441n)
  부호를 뗀 두 수   273 · 441
  공약수 집합       {1, 3, 7, 21}
  가장 큰 것        21
```

두 수의 약수를 값 순서로 늘어놓으면 공약수가 어느 칸인지 확인할 수 있습니다. 두 줄에 모두 값이 있는
칸이 공약수이고, 그런 칸 가운데 가장 오른쪽이 최대공약수예요.

<!--fig:concept-divisors-->
![273 과 441 의 약수 — 둘 다 나누는 수 넷 가운데 가장 큰 21 이 최대공약수](./figs/concept-divisors.svg)

정의를 그대로 옮기면 1 부터 작은 쪽까지 모든 수로 두 수를 나눠 보는 방법이 됩니다. 나눠 볼 후보가
작은 쪽의 **값**만큼 있어서, 수가 커지면 후보도 그만큼 늘어요. 이 글이 세우는 방법은 후보를 하나씩 찾지
않고 **두 수를 줄여 갑니다.** 그 방법의 이름이 **유클리드 호제법**(Euclidean algorithm)이고, 이 글은 끝까지
이 이름 하나로 부릅니다.

유클리드 호제법이 기대는 관찰은 등식 하나입니다. `x` 를 `y` 로 나눈 몫을 `q`, 나머지를 `r` 이라 하면
`x = q·y + r` 이고, 이때 **`(x, y)` 의 공약수 집합과 `(y, r)` 의 공약수 집합이 같습니다.** 전개 입력의 둘째
걸음으로 확인하면 이렇습니다.

<!--proof:conceptStep-->
```text
441 = 1 × 273 + 168
  (441, 273) 의 공약수   {1, 3, 7, 21}
  (273, 168) 의 공약수   {1, 3, 7, 21}
```

그래서 두 수를 `(y, r)` 로 바꿔도 답이 그대로이고, 나머지는 나누는 수보다 작으니 두 수가 계속 작아져요.
나머지가 0 이 되는 순간 남은 수가 답입니다.

이렇게 바꿔 나가며 나온 수를 차례로 적은 줄을 **나머지 수열**이라고 부르겠습니다. 부호를 뗀 두 입력이 첫
두 칸 `r₀` · `r₁` 이고, 그 뒤의 칸은 모두 **바로 앞 두 칸을 나눈 나머지**예요. 이웃한 두 칸이 한 걸음의
`(x, y)` 이고, 0 이 나온 칸에서 수열이 끝납니다.

<!--fig:concept-chain-->
![gcd(-273, 441) 의 나머지 수열 — 이웃한 두 칸이 한 걸음의 (x, y) 이고 모든 쌍의 공약수가 같다](./figs/concept-chain.svg)

칸 하나를 골라 이름에서 값까지 따라가 봅시다. `r₄` 는 바로 앞 두 칸 `r₂` · `r₃` 을 나눈 나머지이고, 코드가
그 값을 실제로 만든 자리와 같습니다.

<!--proof:conceptRead-->
```text
r₄ = r₂ mod r₃ = 273 mod 168 = 105
정본 기록   바퀴 2 에서 x = 273, y = 168, r = 105
```

그림의 모든 쌍은 공약수 집합이 같고, 마지막 쌍 `(21, 0)` 의 공약수 집합은 21 의 약수 전체입니다. 0 은
어떤 수로도 나누어떨어지기 때문이에요. 그래서 마지막에 남은 21 이 처음 두 수의 최대공약수가 됩니다. 두
방법의 비용을 결과만 비교하면 이렇습니다.

<!--proof:conceptCost-->
| 입력 | 1 부터 전부 나눠 보기의 나머지 연산 | 유클리드 호제법의 나머지 연산 |
| --- | ---: | ---: |
| 전개 입력 -273 · 441 | 546 | 7 |
| 이웃 피보나치 F(87) · F(86) | 840,392,281,454,979,346 | 85 |

둘째 줄의 작은 쪽은 18 자리 수이고, 유클리드 호제법은 그 쌍에서 나머지 연산 85 번으로 끝났습니다.

<!--/proof-->

들고 있는 값은 두 수와 나머지 하나뿐이라 추가로 쓰는 메모리가 `O(1)` 입니다. 나머지 연산 횟수는 작은 쪽
입력의 자릿수를 따라가므로 `O(log min(|a|, |b|))` 번이에요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **나머지 있는 나눗셈.** 양의 정수 `y` 로 `x` 를 나누면 `x = q·y + r`, `0 ≤ r < y` 를 만족하는 몫 `q` 와
  나머지 `r` 이 하나씩 정해진다는 것. 이 글의 등식이 이 사실에 기댑니다.
- **약수와 배수**, 그리고 「`d` 가 `m` 과 `n` 을 나누면 `m + n` 과 `m − n` 도 나눈다」는 성질. 공약수 집합이
  그대로라는 논증이 이 성질 하나만 씁니다.
- **JavaScript 의 `bigint`.** 자릿수 제한이 없는 정수 타입입니다. `%` 와 `/` 가 정수 나눗셈으로 동작하고,
  리터럴 끝에 `n` 을 붙여요.
- **`bigint` 의 `%` 는 나누어지는 수의 부호를 따른다는 것.** 음수를 나누면 나머지도 음수로 나옵니다. 값은
  「아이디어 상세」의 「이 방법이 기대는 전제」에서 확인해요.

마지막 항목이 흐릿하면 뒤가 어긋납니다. 음수를 그대로 넣으면 답이 음수로 나올 수 있고, 그 자리를 첫 번째
「짚고 가기」에서 값으로 확인합니다. 이 글의 절차가 버리는 몫까지 살려 두면 [`extendedEuclidean`](../extendedEuclidean/extendedEuclidean-guide.md)
이 되고, 그 결과로 [`crt`](../crt/crt-guide.md)(중국인의 나머지 정리)가 연립 합동식을 풉니다.
[`pollardRho`](../pollardRho/pollardRho-guide.md) 는 같은 호제법을 음이 아닌 두 수만 받는 판으로 따로 두고, 그것으로 인수를 찾아요.

### 아이디어를 떠올리는 과정 — 1 부터 전부 나눠 보기에서 유클리드 호제법까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 두 정수를 받아 최대공약수를
돌려줍니다.

```ts
function gcd(a: bigint, b: bigint): bigint;
```

- 입력: 두 정수 `a`, `b`. 음수와 0 이 들어올 수 있습니다.
- 출력: `|a|` 와 `|b|` 의 최대공약수. 언제나 0 이상이고, 둘 다 0 이면 0 입니다.
- 규모: `bigint` 는 자릿수에 상한이 없지만, 이 글은 두 수의 절댓값이 `10^18` 이하라고 두고 잽니다. 64 비트
  정수 안의 어림수라 흔히 받는 폭이고, 그 안에서 가장 불리한 입력까지 실제로 실행할 수 있어서예요. 비용은
  흔한 채점 환경의 예산인 1 초(단순 연산 1 초에 1 억 번)에 대어 잽니다.

한쪽이 0 인 경우도 여기서 정해 둡니다. 0 은 모든 수의 배수라 `(x, 0)` 의 공약수 집합이 `x` 의 약수
전체이고, 그래서 `gcd(x, 0)` 은 `x` 예요. 둘 다 0 이면 공약수가 끝없이 많아 가장 큰 것이 없으므로, 관례대로
0 을 돌려줍니다. 이 함수가 쓸 수 있는 것은 셋이에요.

| 쓸 수 있는 것 | 알려 주는 것 |
| --- | --- |
| 나머지 있는 나눗셈 `x % y` | 나머지. 몫은 따로 `x / y` 로 구한다 |
| 두 값의 크기 비교 | 어느 쪽이 큰가 |
| 0 과의 비교 | 멈출 때가 되었는가 |

이 글이 쓰는 기호는 아홉입니다. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 뜻 | 이 과제에서 |
| --- | --- | --- |
| `a` | 첫째 입력 | 음수·0·양수, 절댓값 `≤ 10^18` |
| `b` | 둘째 입력 | 음수·0·양수, 절댓값 `≤ 10^18` |
| `x` | 코드가 들고 있는 나누어지는 수 | 처음 값은 `a` 의 절댓값 |
| `y` | 코드가 들고 있는 나누는 수 | 처음 값은 `b` 의 절댓값. 0 이 되면 멈춘다 |
| `q` | `x` 를 `y` 로 나눈 몫 | 코드에는 안 나온다 |
| `r` | `x` 를 `y` 로 나눈 나머지 | `0 ≤ r < y` |
| `r_k` | 나머지 수열의 `k` 번째 칸 | `r_0` · `r_1` 이 두 입력의 절댓값. 바퀴 `k` 의 `(x, y)` 가 `(r_k, r_{k+1})` 이고 그 바퀴의 `r` 이 `r_{k+2}` |
| `N` | 한 번 호출할 때의 나머지 연산 횟수 | 바퀴 수와 같다 |
| `d` | 작은 쪽 입력의 십진 자릿수 | `d ≤ 19` |

「바퀴」는 반복문 본문을 한 번 실행하는 것을 말합니다. 비용은 끝까지 **연산 횟수**로 셉니다. 두 수를 바꾸는
산술 연산 — 나머지 `%` 한 번이나 뺄셈 한 번 — 을 하나로 세고, 유클리드 호제법에서는 이 값이 나머지 연산
횟수 `N` 이에요. 메모리는 **저장 칸**(들고 있는 값의 개수)으로 셉니다.

가장 먼저 떠오르는 방법으로 시작합시다. 1 부터 작은 쪽까지 모든 수로 두 수를 나눠 보고, 둘 다
나누어떨어지는 가장 큰 수를 남기는 것입니다.

```ts
function tryAll(a: bigint, b: bigint): bigint {
  const x = a < 0n ? -a : a;
  const y = b < 0n ? -b : b;
  if (x === 0n || y === 0n) return x === 0n ? y : x;
  let best = 1n;
  for (let d = 1n; d <= (x < y ? x : y); d++) {
    if (x % d === 0n && y % d === 0n) best = d; // 후보 하나에 나머지 연산 두 번
  }
  return best;
}
```

이 방법은 답을 틀리지 않습니다. 전개 입력에 실행하면 이렇게 나와요.

<!--proof:bruteWalk-->
```text
나눠 본 후보              1 부터 273 까지 273 개
나머지 연산               546 번
둘 다 나누는 가장 큰 수   21
```

하는 일의 양이 작은 쪽의 **값**을 따라갑니다. 규모를 넣어 보면 몇 번인지 바로 나와요.

<!--proof:naiveScale-->
| 작은 쪽의 자릿수 | 작은 쪽의 값 | 나머지 연산 | 초당 1 억 번일 때 시간 |
| ---: | ---: | ---: | ---: |
| 3 | 999 | 1,998 | 0.001 초 미만 |
| 6 | 999,999 | 1,999,998 | 0.020 초 |
| 9 | 999,999,999 | 1,999,999,998 | 20.0 초 |
| 12 | 999,999,999,999 | 1,999,999,999,998 | 5.6 시간 |
| 18 | 999,999,999,999,999,999 | 1,999,999,999,999,999,998 | 약 634 년 |

자릿수마다 그 자릿수의 가장 큰 값을 작은 쪽으로 두고 셌습니다. 후보 하나에 나머지 연산이 두 번입니다.

<!--/proof-->

아홉 자리에서 이미 예산의 스무 배이고, 열여덟 자리면 수백 년입니다. 후보를 값만큼 보는 한 이 벽을 넘을 수
없어요. 방향을 바꿔 봅시다. 약수를 찾는 대신 **공약수 집합을 그대로 둔 채 두 수를 작게 만들 수 있다면**,
작아진 두 수의 최대공약수가 곧 답입니다.

그런 바꿈 가운데 가장 단순한 것이 **큰 쪽에서 작은 쪽을 빼는 것**입니다. `d` 가 `x` 와 `y` 를 나누면
`x − y` 도 나누고, 거꾸로 `d` 가 `x − y` 와 `y` 를 나누면 그 합인 `x` 도 나누므로 공약수 집합이 그대로예요.
전개 입력에서 한쪽이 0 이 될 때까지 빼 보면 이렇습니다.

<!--proof:subtractChain-->
| 뺄셈 횟수 | 두 수 | 한 일 | 공약수 집합 |
| ---: | --- | --- | --- |
| 0 | (273, 441) | — | {1, 3, 7, 21} |
| 1 | (273, 168) | y 에서 273 을 뺐다 | {1, 3, 7, 21} |
| 2 | (105, 168) | x 에서 168 을 뺐다 | {1, 3, 7, 21} |
| 3 | (105, 63) | y 에서 105 를 뺐다 | {1, 3, 7, 21} |
| 4 | (42, 63) | x 에서 63 을 뺐다 | {1, 3, 7, 21} |
| 5 | (42, 21) | y 에서 42 를 뺐다 | {1, 3, 7, 21} |
| 6 | (21, 21) | x 에서 21 을 뺐다 | {1, 3, 7, 21} |
| 7 | (21, 0) | y 에서 21 을 뺐다 | {1, 3, 7, 21} |

뺄셈 7 번 뒤에 한쪽이 0 이 됐고, 남은 수 21 이 정본의 답과 같습니다. 공약수 집합은 8 줄 모두 {1, 3, 7, 21} 하나입니다.

<!--/proof-->

두 수가 줄어도 공약수 집합은 한 번도 안 바뀌었습니다. 이 입력에서는 연산 7 번이라 1 부터 전부 나눠 보는
방법보다 훨씬 적어요. 그러면 연산 횟수가 무엇에 달렸는지, 같은 입력을 뺄셈과 나머지 두 방식으로 처리해 세어
봅시다. 나머지 방식은 `(x, y)` 를 한 번에 `(y, x mod y)` 로 바꿉니다.

<!--proof:subtractVsRemainder-->
| 입력 | 뺄셈만 쓸 때의 연산 | 나머지를 쓸 때의 연산 | gcd |
| --- | ---: | ---: | ---: |
| 전개 입력 -273 과 441 | 7 | 7 | 21 |
| 1 과 1,000,000 | 1,000,000 | 2 | 1 |
| 이웃 피보나치 F(31) · F(30) | 30 | 29 | 1 |
| 1,000,000 과 999,999 | 1,000,000 | 2 | 1 |

네 줄 모두 두 방법의 답이 같습니다. 뺄셈 횟수는 나머지를 쓸 때 나온 몫을 다 더한 값과도 같습니다.

<!--/proof-->

첫 줄과 셋째 줄에서는 두 값이 거의 같고, 둘째 줄과 넷째 줄에서 크게 갈립니다. 둘째 줄을 두 방식으로
나란히 놓으면 차이가 어디서 나오는지 확인할 수 있어요.

<!--proof:subtractRepeat-->
```text
뺄셈     (1,000,000, 1) → (999,999, 1) → (999,998, 1) → … → (1, 0)   1,000,000 번
나머지   1,000,000 mod 1 = 0  → (1, 0)   1 번
```

뺄셈은 같은 수 1 을 몇 번이고 되풀이해 뺀 뒤에야 나머지 방식이 한 번에 만든 쌍에 이릅니다. 되풀이하는 횟수가
그 걸음의 몫이에요. 여기서 관찰한 것은 하나입니다. **나머지 한 번은 같은 수를 몫만큼 되풀이해 뺀 결과**이고,
그래서 몫이 클수록 두 방식의 차이가 커집니다. 첫 줄과 셋째 줄은 몫이 거의 다 1 이라 되풀이할 것이 없었어요.

가장 단순한 후보였던 뺄셈만 쓰는 방법을 과제 규모에서 반박해 봅시다. 몫이 큰 입력을 넣으면 뺄셈이 몫만큼
쌓입니다.

<!--proof:subtractScale-->
| 입력 | 뺄셈 | 나머지 연산 | 뺄셈의 시간(초당 1 억 번) |
| --- | ---: | ---: | ---: |
| 1 과 10^9 | 1,000,000,000 | 2 | 10.0 초 |
| 1 과 10^18 | 1,000,000,000,000,000,000 | 2 | 약 317 년 |
| 이웃 피보나치 F(87) · F(86) | 86 | 85 | 0.001 초 미만 |

뺄셈 횟수는 되풀이하지 않고 나머지 연산마다의 몫을 더해 셌습니다. 앞 표의 네 줄에서 실제로 되풀이한 횟수와 같았던 셈법입니다.

<!--/proof-->

한쪽이 1 이고 다른 쪽이 `10^18` 이면 뺄셈만으로는 수백 년이 걸립니다. 공약수 집합을 지키며 두 수를 줄인다는
방향은 맞았고, 막힌 자리는 같은 뺄셈을 되풀이하는 것이었어요. 지금까지 해 본 방법을 차례로 놓으면
이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법이 **유클리드 호제법**입니다. 두 수를 `(x, y)` 로 적고, `(y, x mod y)` 로 바꾸는 일을 `y` 가 0 이
될 때까지 되풀이해요. 이 바꿈이 왜 공약수 집합을 지키는지, 두 수가 얼마나 빨리 줄어드는지, 어디서 멈추고
무엇을 답으로 읽는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 유클리드 호제법

이 아이디어를 한 문장으로 줄이면 이렇습니다. **두 수 `(x, y)` 를 공약수 집합이 같은 `(y, x mod y)` 로 바꾸는
일을 `y` 가 0 이 될 때까지 되풀이하고, 그때 남은 `x` 를 답으로 읽습니다.** 이 방법이 쓰는 구조는 전체
컨셉에서 본 나머지 수열 하나이고, 미리 만들어 두는 것이 없어서 세 단계 모두 호출 한 번 안에서 해요.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 공약수 집합을 지키는 바꿈 정하기 | `(x, y)` 를 `(y, x mod y)` 로 바꿔도 공약수 집합이 같다는 것을 세운다 | — |
| 2단계 나머지 수열 이어 쓰기 | 1단계의 바꿈을 되풀이해 수열을 한 칸씩 늘리고, 칸이 얼마나 빨리 줄어드는지 확인한다 | 1단계의 바꿈 |
| 3단계 0 에서 멈추고 답 읽기 | 나머지가 0 이 된 칸에서 멈추고 그 앞 칸을 답으로 읽는다 | 2단계의 수열 · 1단계의 집합 보존 |

#### 1단계 — 공약수 집합을 지키는 바꿈 정하기

바꿈 하나가 공약수 집합을 그대로 두려면 두 방향이 다 성립해야 합니다. `(x, y)` 의 공약수가 전부
`(y, r)` 의 공약수이고, 그 반대도 참이어야 해요. 쓰는 것은 등식 `x = q·y + r`, 곧 `r = x − q·y` 하나입니다.

| 방향 | 쓰는 등식 | 근거 |
| --- | --- | --- |
| `d` 가 `x` · `y` 를 나누면 `r` 도 나눈다 | `r = x − q·y` | `q·y` 는 `y` 의 배수라 `d` 로 나누어떨어지고, `x` 에서 그 배수를 뺀 값도 `d` 로 나누어떨어진다 |
| `d` 가 `y` · `r` 을 나누면 `x` 도 나눈다 | `x = q·y + r` | 더하는 두 항 `q·y` 와 `r` 이 모두 `d` 의 배수다 |

둘째 바퀴의 쌍 `(441, 273)` 에서 나머지는 168 입니다. 공약수인 수와 아닌 수를 몇 개 골라 세 값을 각각
나눠 보면 이렇습니다.

<!--proof:stage1Both-->
| d | x = 441 | y = 273 | r = 168 |
| ---: | --- | --- | --- |
| 7 | 나눈다 | 나눈다 | 나눈다 |
| 21 | 나눈다 | 나눈다 | 나눈다 |
| 13 | — | 나눈다 | — |
| 8 | — | — | 나눈다 |

공약수 7 · 21 은 셋 다 나눕니다. 13 은 `y` 만 나누고 `x` 는 못 나누니 처음부터 공약수가 아니었고, `r` 도 못
나눠서 바꾼 뒤에도 공약수가 아니에요. 8 은 `r` 을 나누지만 `y` 를 못 나누니 바꾼 뒤에도 공약수가 아닙니다.
공약수가 아니던 수가 새로 들어오는 일도, 공약수가 빠지는 일도 없어요. 전개 입력의 모든 바퀴에서 두 집합을
직접 구해 비교하면 이렇습니다.

<!--proof:stage1Keep-->
| 바퀴 | (x, y) | r = x mod y | (x, y) 의 공약수 | (y, r) 의 공약수 | 두 집합의 일치 |
| ---: | --- | ---: | --- | --- | --- |
| 0 | (273, 441) | 273 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 1 | (441, 273) | 168 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 2 | (273, 168) | 105 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 3 | (168, 105) | 63 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 4 | (105, 63) | 42 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 5 | (63, 42) | 21 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |
| 6 | (42, 21) | 0 | {1, 3, 7, 21} | {1, 3, 7, 21} | 예 |

7 바퀴 가운데 두 집합이 같은 바퀴가 7 개입니다.

<!--/proof-->

바퀴 0 은 `x` 가 `y` 보다 작은 경우입니다. 그때 몫이 0 이라 나머지가 `x` 자신이고, 바꿈은 두 값의 자리를
바꾸기만 해요. 그래서 이 바꿈은 어느 쪽이 큰지 미리 따지지 않아도 성립합니다.

#### 2단계 — 나머지 수열 이어 쓰기

1단계의 바꿈을 되풀이하면 나머지 수열이 한 칸씩 늘어납니다. 바퀴 `k` 가 칸 `r_k` · `r_{k+1}` 을 나눠 칸
`r_{k+2}` 를 채우고, 그다음 바퀴는 한 칸 오른쪽의 쌍을 나눠요. 칸마다 `0 ≤ r < y` 이므로 `r_2` 부터는 칸이
엄격하게 작아집니다.

얼마나 빨리 작아지는지가 비용을 정합니다. 칸 하나 건너의 값을 비교하면 규칙이 보여요. 전개 입력의 수열에서
`r_{k+2}` 와 `r_k` 의 절반을 나란히 놓아 봅시다.

<!--proof:stage2Halve-->
| k | r_k | r_(k+2) | r_k / 2 | r_(k+2) < r_k / 2 |
| ---: | ---: | ---: | ---: | --- |
| 0 | 273 | 273 | 136.5 | 아니요 |
| 1 | 441 | 168 | 220.5 | 예 |
| 2 | 273 | 105 | 136.5 | 예 |
| 3 | 168 | 63 | 84 | 예 |
| 4 | 105 | 42 | 52.5 | 예 |
| 5 | 63 | 21 | 31.5 | 예 |
| 6 | 42 | 0 | 21 | 예 |

7 줄 가운데 6 줄에서 두 칸 뒤의 값이 절반 아래이고, 아닌 줄은 k = 0 하나입니다. 그 줄의 첫 나눗셈은 몫이 0 이라 두 값을 뒤바꾸기만 했습니다.

<!--/proof-->

**첫 바퀴 뒤로는 두 칸마다 값이 절반 아래로 줄어듭니다.** 까닭은 `x ≥ y` 인 바퀴의 나머지가 늘 `x` 의
절반보다 작다는 데 있어요. `y` 가 `x` 의 절반보다 크면 몫이 1 이라 `r = x − y` 이고, `y` 가 절반보다 크니
`x − y` 는 절반보다 작습니다. `y` 가 `x` 의 절반 이하이면 `r < y ≤ x / 2` 입니다. 두 경우가 전개 입력에
하나씩 있어요.

<!--proof:stage2Why-->
| 경우 | (x, y) | 몫 | 나머지 r | x / 2 | r < x / 2 |
| --- | --- | ---: | ---: | ---: | --- |
| y 가 x 의 절반보다 크다 | (441, 273) | 1 | 168 | 220.5 | 예 |
| y 가 x 의 절반 이하다 | (42, 21) | 2 | 0 | 21 | 예 |

바퀴 `k` 의 `x` 가 `r_k` 이고 그 나머지가 `r_{k+2}` 이므로, 위 부등식이 곧 `r_{k+2} < r_k / 2` 입니다. 두
바퀴마다 절반 아래로 줄어드니 바퀴 수는 값이 아니라 작은 쪽 입력의 비트 수를 따라갑니다. 정확한 상한은
「수식 정의와 유도」가 자릿수로 닫고, 가장 느리게 줄어드는 입력 — 몫이 계속 1 인 입력 — 은 「최악을 만드는
입력」에서 실제로 구성해요.

크기도 여기서 정해집니다. 코드가 들고 있는 값은 `x` · `y` · `r` 셋이고, 셋 다 처음 입력의 절댓값을 넘지
않아요. 칸을 모두 적어 둘 필요도 없습니다. 다음 바퀴가 쓰는 것은 바로 앞 두 칸뿐이라서요.

#### 3단계 — 0 에서 멈추고 답 읽기

나머지가 0 인 칸이 나오면 멈춥니다. 그 순간의 쌍은 `(x, 0)` 이고, 0 은 모든 수로 나누어떨어지므로 이 쌍의
공약수 집합은 `x` 의 약수 전체예요. 1단계의 바꿈이 공약수 집합을 한 번도 안 바꿨으니 그 집합이 처음 두 수의
공약수 집합이고, 그중 가장 큰 것이 `x` 자신입니다. 한쪽이나 둘 다 0 인 입력도 같은 자리에서 처리돼요.

<!--proof:stage3Stop-->
| 입력 | 나머지 연산 | 마지막 쌍 | 반환값 |
| --- | ---: | --- | ---: |
| gcd(-273n, 441n) | 7 | (21, 0) | 21 |
| gcd(21n, 0n) | 0 | (21, 0) | 21 |
| gcd(7n, 0n) | 0 | (7, 0) | 7 |
| gcd(0n, 9n) | 1 | (9, 0) | 9 |
| gcd(0n, 0n) | 0 | (0, 0) | 0 |

둘째 입력이 0 이면 나머지를 한 번도 구하지 않고 곧바로 멈춥니다. `gcd(0n, 9n)` 은 첫 바퀴에서 `0 mod 9` 가
0 이라 `(9, 0)` 이 되고, `gcd(0n, 0n)` 은 처음부터 `(0, 0)` 이라 관례대로 0 을 돌려줘요. 반드시 멈춘다는 것도
여기서 확인됩니다. `y` 는 바퀴마다 엄격하게 줄어드는 0 이상의 정수라서, 끝없이 줄어들 수 없어요.

#### 이 방법이 기대는 전제

유클리드 호제법은 아래 두 전제가 있어야 성립합니다.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 나머지가 `0 ≤ r < y` 에 든다 | 2단계에서 칸이 엄격하게 작아지고 3단계에서 반드시 멈춘다 | 나머지가 음수로 나오면 멈춘 자리의 `x` 가 음수일 수 있다 |
| 두 입력이 0 이상이다 | 3단계에서 `x` 를 답으로 읽는다 | 최대공약수는 0 이상인데 음수를 돌려줄 수 있다 |

`bigint` 의 `%` 는 첫째 전제를 스스로 지키지 않습니다. 나머지의 부호가 나누어지는 수를 따르기 때문이에요.

<!--proof:premiseSign-->
| x | y | x % y | 0 이상이고 y 의 절댓값 미만 |
| ---: | ---: | ---: | --- |
| 12 | 18 | 12 | 예 |
| -12 | 18 | -12 | 아니요 |
| 12 | -18 | 12 | 예 |
| -18 | 12 | -6 | 아니요 |

그래서 코드는 반복에 들어가기 전에 두 입력의 부호를 뗍니다. 두 수가 0 이상이면 나머지도 늘 `0 ≤ r < y` 에
들어요. 부호를 한쪽만 떼면 어떤 값이 나오는지는 첫 번째 「짚고 가기」에서 확인합니다.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 다섯 걸음이 됩니다. 2 · 3 · 4 가 반복 한 바퀴이고, 3 · 4 가 1단계와
2단계, 5 가 3단계예요. 1부터 전부 나눠 보면 작은 쪽의 값만큼이던 연산이, 이렇게 하면 두 바퀴마다 값이 절반
아래로 줄어드는 만큼만 듭니다.

1. `x` 를 `a` 의 절댓값, `y` 를 `b` 의 절댓값으로 둔다
2. `y` 가 0 이 아닌 동안 아래를 되풀이한다
3. `r` 을 `x` 를 `y` 로 나눈 나머지로 둔다
4. `x` 를 `y` 로, `y` 를 `r` 로 옮긴다
5. `x` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 나머지 연산 일곱 번으로 -273 과 441 의 최대공약수를 구한다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walkInput-->
```ts
const a = -273n;
const b = 441n;
// 이 절이 끝나면 21n 이 나와야 한다
```

왜 하필 이 둘일까요? 첫 인자가 **음수**라 부호를 떼는 갈래가 실제로 값을 바꾸고, 그 절댓값이 둘째보다
**작아서** 첫 바퀴가 두 값을 뒤바꾸며, 몫이 1 인 바퀴가 이어져 바퀴 수가 많은 모양까지 함께 확인되기
때문입니다.

```text
gcd(a, b):
    x ← a 의 절댓값,  y ← b 의 절댓값                ① 부호를 뗀다
    y 가 0 이 아닌 동안:
        r ← x 를 y 로 나눈 나머지
        x ← y,  y ← r                                ② 나머지로 옮긴다
    x 를 반환한다                                    ③ y 가 0 이 된 순간의 x 가 답이다
```

#### 1. 부호를 뗀다

첫 조각은 준비입니다. 공약수는 부호와 상관이 없으니 두 입력을 절댓값으로 바꿔 두고, 아직 반복문에는
들어가지 않아요.

```ts
let x = a < 0n ? -a : a; // ① 부호를 뗀다
let y = b < 0n ? -b : b;
```

실행하면 이렇게 나옵니다.

<!--proof:walkInit-->
```text
T1 이 끝난 시점 — a = -273, b = 441
  x = 273
  y = 441
```

#### 짚고 가기 — 둘째 인자의 절댓값은 안 씌워도 될 것 같다

여기서 헷갈리기 쉬운 포인트는 **부호를 두 입력 모두 떼야 하는가**입니다. 첫 값만 양수이면 나머지 연산이
알아서 정리해 줄 것처럼 보여요. 그 생각대로 둘째 줄의 절댓값을 지워 봅시다.

```ts
let y = b; // ← 절댓값을 안 씌웠다
```

이 코드는 예외를 내지 않습니다. 네 입력에 실행하면 이렇게 나와요.

<!--proof:mutant-no-abs-->
| 입력 | 정본의 답 | 절댓값을 안 씌운 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 -273 과 441 | 21 | 21 | 같다 |
| 둘 다 음수인 -12 와 -18 | 6 | -6 | 틀리다 |
| 둘째만 음수인 12 와 -18 | 6 | -6 | 틀리다 |
| 한쪽이 0 인 7 과 0 | 7 | 7 | 같다 |

**전개 입력에서는 답이 안 틀립니다.** 둘째 인자가 양수라 지운 줄이 원래 하던 일이 없었기 때문이에요. 그래서
둘째 인자가 양수인 입력만 시험하면 이 자리를 모르고 넘어갑니다. 둘째 인자가 음수이면 최대공약수가 음수로
나와요.

<!--proof:pauseNoAbsTrace-->
```text
gcd(-12n, -18n) 에서 y 의 절댓값을 안 씌우면
  x = 12, y = -18   12 % -18 = 12   → (-18, 12)
  x = -18, y = 12   -18 % 12 = -6   → (12, -6)
  x = 12, y = -6    12 % -6 = 0     → (-6, 0)
  y 가 0 이라 x = -6 을 돌려준다
```

첫 바퀴가 음수 `y` 를 `x` 자리로 옮기고, 둘째 바퀴에서 `bigint` 의 `%` 가 나누어지는 수의 부호를 따라 음수
나머지를 냅니다. 그 음수가 마지막에 남은 `x` 예요. 「이 방법이 기대는 전제」의 첫째 줄이 깨진 모습이고,
그래서 **두 입력 모두** 부호를 뗍니다.

#### 2. 나머지로 옮긴다

둘째 조각은 반복문입니다. 바퀴 하나가 나머지 수열을 한 칸 늘려요 — 나머지를 구하고, 두 값을 한 칸씩
옮깁니다.

```ts
while (y !== 0n) {
  const r = x % y;
  x = y;
  y = r; // ② 나머지로 옮긴다
}
```

앞 세 바퀴만 실행하면 이렇게 나옵니다.

<!--proof:walkLoopHead-->
| 걸음 | x | y | r = x % y | 바퀴 끝 (x, y) |
| --- | ---: | ---: | ---: | --- |
| T2 | 273 | 441 | 273 | (441, 273) |
| T3 | 441 | 273 | 168 | (273, 168) |
| T4 | 273 | 168 | 105 | (168, 105) |

T2 가 이 세 줄의 핵심입니다. `x` 가 `y` 보다 작아 나머지가 `x` 자신이고, 두 줄의 대입이 두 값을 뒤바꿔
놓아요. `x = y` 가 먼저이고 `y = r` 이 나중인 순서가 곧 수열의 칸 순서입니다 — 옛 `y` 가 한 칸 왼쪽으로 가고,
새 나머지가 오른쪽 칸을 채워요.

#### 짚고 가기 — 큰 쪽을 먼저 앞에 두어야 할 것 같다

여기서 헷갈리기 쉬운 포인트는 T2 같은 바퀴입니다. 나눗셈은 큰 수를 작은 수로 하는 것이니, 반복에 들어가기
전에 두 값을 비교해 큰 쪽을 `x` 로 두어야 할 것 같아요. 그 생각대로 비교 한 줄을 넣은 판을 만들어 봅시다.

```ts
function sortFirst(a: bigint, b: bigint): bigint {
  let x = a < 0n ? -a : a;
  let y = b < 0n ? -b : b;
  if (x < y) [x, y] = [y, x]; // 큰 쪽을 x 로 둔다
  while (y !== 0n) {
    const r = x % y;
    x = y;
    y = r;
  }
  return x;
}
```

**비교를 넣지 않아도 답은 한 번도 안 틀립니다.** 네 입력에 두 판을 실행하면 이렇게 나와요.

<!--proof:orderFirst-->
| 입력 | 정본의 답 | 먼저 정렬한 답 | 정본의 나머지 연산 | 먼저 정렬한 판의 나머지 연산 |
| --- | ---: | ---: | ---: | ---: |
| gcd(-273n, 441n) | 21 | 21 | 7 | 6 |
| gcd(441n, -273n) | 21 | 21 | 6 | 6 |
| gcd(1n, 1000000n) | 1 | 1 | 2 | 1 |
| gcd(0n, 9n) | 9 | 9 | 1 | 0 |

네 줄 모두 두 판의 답이 같고, 나머지 연산의 차이는 많아야 1 번입니다. 먼저 정렬한 판은 입력마다 비교를 한 번 더 합니다.

<!--/proof-->

작은 쪽이 앞이면 정본은 첫 바퀴를 두 값 뒤바꾸기에 씁니다. 정렬하는 판은 그 바퀴를 비교 한 번으로 대신할
뿐이에요. 몫이 0 인 바퀴는 첫 바퀴에서만 나올 수 있습니다. 첫 바퀴가 끝나면 `y` 자리에 늘 `x` 보다 작은
나머지가 오기 때문이에요. 그래서 아끼는 것이 호출마다 많아야 나머지 연산 한 번이고, 이 글의 정본은 비교를
넣지 않습니다.

#### 3. 나머지가 0 이 되면 끝난다

마지막 조각은 반환입니다. 반복이 끝나는 것은 `y` 가 0 이 된 순간이고, 그때의 `x` 를 돌려줘요.

```ts
return x; // ③ y 가 0 이 된 순간의 x 가 답이다
```

전개 입력에서는 T8 의 나머지가 0 이라 T9 에서 반복 조건이 거짓이 되고, 그때 `x` 가 21 입니다. 조각 셋을 이어
끝까지 실행한 모습은 다음 걸음에서 봅니다.

#### 4. 아홉 걸음을 처음부터 끝까지 본다

세 조각을 이어 고정 입력에 실행하면 아홉 걸음이 나옵니다. T1 은 반복문 앞, T2 부터 T8 까지가 바퀴 일곱,
T9 가 반환이에요. 무대의 칸 `k` 가 나머지 수열의 `r_k` 이고, 괄호 `(x, y)` 가 바퀴를 시작할 때의 쌍, ▲ 가
이번에 나눈 두 칸, 새로 채운 칸이 이번 나머지입니다. 칸 줄 곁말은 그 쌍의 공약수 집합이에요.

한 걸음마다 조건이 어떻게 판정되는지 전부 적으면 아래 아홉 단계입니다.

<!--proof:walkTrace-->
| 걸음 | ② y ≠ 0 | x = q·y + r | 걸음 끝 x | 걸음 끝 y | 다음 쌍 |
| --- | --- | --- | ---: | ---: | --- |
| T1 | — | — | 273 | 441 | — |
| T2 | 441 ≠ 0 **참** | 273 = 0 × 441 + 273 | 441 | 273 | (441, 273) |
| T3 | 273 ≠ 0 **참** | 441 = 1 × 273 + 168 | 273 | 168 | (273, 168) |
| T4 | 168 ≠ 0 **참** | 273 = 1 × 168 + 105 | 168 | 105 | (168, 105) |
| T5 | 105 ≠ 0 **참** | 168 = 1 × 105 + 63 | 105 | 63 | (105, 63) |
| T6 | 63 ≠ 0 **참** | 105 = 1 × 63 + 42 | 63 | 42 | (63, 42) |
| T7 | 42 ≠ 0 **참** | 63 = 1 × 42 + 21 | 42 | 21 | (42, 21) |
| T8 | 21 ≠ 0 **참** | 42 = 2 × 21 + 0 | 21 | 0 | (21, 0) |
| T9 | 0 ≠ 0 **거짓** | — | 21 | 0 | — |

나머지 연산은 모두 7 번이고, 돌려주는 값은 21 입니다.

<!--/proof-->

**세 갈래가 모두 실행됐습니다.** 라벨마다 어느 걸음에서 실행됐는지 모으면 이렇습니다.

<!--proof:walkBranches-->
| 라벨 | 하는 일 | 전개에서 |
| --- | --- | --- |
| ① | 부호를 뗀다 | T1 에서 한 번 |
| ② | 나머지로 옮긴다 | T2 · T3 · T4 · T5 · T6 · T7 · T8 에서 7 번 · T9 에서 조건이 거짓 |
| ③ | y 가 0 이 된 순간의 x 를 돌려준다 | T9 에서 한 번 |

무대의 곁말은 아홉 걸음 내내 `{1, 3, 7, 21}` 입니다. 쌍은 걸음마다 바뀌었는데 공약수 집합은 한 번도 안
바뀌었고, T9 에서 남은 21 이 그 집합의 가장 큰 값이에요. T8 이 쓴 0 은 반복을 끝내는 표지이고, 답은 그
왼쪽 칸에 있습니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 없어요 — 조각 셋을 이어 붙인 것이
전부이고, 둘 다 0 이면 반복이 한 번도 실행되지 않아 `x` 인 0 이 그대로 답이 됩니다.

```ts
export function gcd(a: bigint, b: bigint): bigint {
  // ① 부호를 떼어 낸다. 공약수는 부호와 무관하다.
  let x = a < 0n ? -a : a;
  let y = b < 0n ? -b : b;

  // ② 나머지가 0 이 될 때까지 두 값을 (y, x mod y) 로 옮긴다.
  while (y !== 0n) {
    const r = x % y;
    x = y;
    y = r;
  }

  // ③ 나머지가 0 이 된 순간의 x 가 답이다. 둘 다 0 이면 반복이 한 번도 실행되지 않는다.
  return x;
}
```

<!--proof:finalCalls-->
```text
gcd(-273n, 441n)   → 21n
gcd(12n, 18n)      → 6n
gcd(-12n, -18n)    → 6n
gcd(17n, 5n)       → 1n
gcd(0n, 9n)        → 9n
gcd(0n, 0n)        → 0n
```

### 알아 두면 좋은 개념 — 연분수

전개의 T2 ~ T8 에서 몫만 차례로 읽으면 `0 1 1 1 1 1 2` 입니다. 이 수열에 이름이 붙어 있어요 —
`273 / 441` 의 **연분수** 전개입니다. 연분수는 분수를 「정수 + 1 / (정수 + 1 / (…))」 꼴로 적는 방법이고,
그 정수들이 곧 유클리드 호제법의 몫입니다.

<!--proof:continuedFraction-->
| 분수 | 차례로 나온 몫 | 연분수 표기 | 분수의 값 |
| --- | --- | --- | ---: |
| 273 / 441 | 0 1 1 1 1 1 2 | [0; 1, 1, 1, 1, 1, 2] | 0.619048 |
| 441 / 273 | 1 1 1 1 1 2 | [1; 1, 1, 1, 1, 2] | 1.615385 |
| 355 / 113 | 3 7 16 | [3; 7, 16] | 3.141593 |

몫을 안쪽부터 끼워 넣으면 원래 분수가 되돌아옵니다. 셋째 줄로 확인해 봅시다.

<!--proof:continuedFractionBack-->
```text
[3; 7, 16] 을 안쪽부터 되돌려 계산하면
  16               = 16
  7 + 1/16         = 7.062500
  3 + 1/7.0625     = 3.141593
  355 / 113        = 3.141593
```

이 글의 값과 연분수의 이름을 나란히 놓으면 이렇습니다.

| 이 글의 것 | 연분수의 이름 |
| --- | --- |
| 한 바퀴의 몫 `q` | 연분수의 한 항 |
| 바퀴 수 `N` | 연분수 항의 개수 |
| 몫이 계속 1 인 입력 | 항이 전부 1 인 연분수 — 황금비의 전개 |
| 마지막 나머지 0 | 유리수의 연분수가 유한 번에 끝난다는 것 |

같은 이름을 다시 만나는 자리가 셋 있습니다. 유리수로 실수를 근사할 때(위의 `355 / 113` 이 원주율의 이름난
근삿값입니다), 펠 방정식을 풀 때, 그리고 [`extendedEuclidean`](../extendedEuclidean/extendedEuclidean-guide.md)
이 베주 계수를 만들 때예요. 셋 다 이 글이 버린 몫 `q` 를 다시 씁니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 나머지 연산 횟수를 임의의 입력으로 어떻게
막는지, 무엇이 매 바퀴 참으로 남는지, 그리고 연산이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 두 수의 최대공약수 하나만 필요하다 | 베주 계수(`ax + by = gcd`)까지 필요하면 몫을 살려 두는 확장 판을 쓴다 | 몫을 변수로 두지 않는다 |
| 수가 크다 | 작은 수라면 어느 방법이든 예산 안에 든다 | 바퀴 수가 값이 아니라 자릿수를 따른다 |
| 나머지 연산 한 번의 비용이 작다 | 수가 하드웨어 워드 안에 들면 한 번이 상수 시간이다 | 반복 한 바퀴에 `%` 가 한 번이다 |
| 부호와 0 을 따로 거르지 않아도 된다 | 음수와 0 이 섞여 들어오는 입력이다 | 절댓값 두 줄과 반복 조건 하나가 흡수한다 |

셋째 줄이 이 절차의 경계입니다. `bigint` 처럼 자릿수가 워드를 넘으면 나머지 연산 한 번의 비용이 자릿수를
따라 커지고, 그때는 나눗셈을 쓰지 않는 설계가 더 적은 일을 할 수 있어요. 그 갈림을 「경쟁 설계와의 대조」가
값으로 봅니다.

#### 문제에서 이것을 떠올리게 하는 단서

- 「**빈틈없이** 나누어떨어지는 가장 큰 단위」 — 타일·묶음·주기를 묻는 표준 문형입니다.
- 「두 주기가 **다시 같아지는** 시점」 — 그쪽은 최소공배수이고 `a·b / gcd(a, b)` 로 나옵니다. 최대공약수를
  먼저 구하는 형태예요.
- 「분수를 **기약분수로**」 — 분자와 분모를 최대공약수로 나눕니다.
- 「두 수가 **서로소인가**」 — 최대공약수가 1 인지만 보면 됩니다.
- 「격자에서 `(0,0)` 과 `(a,b)` 를 잇는 선분이 지나는 격자점 수」 — `gcd(a, b) + 1` 입니다.

반대로 아래 신호는 이 함수 하나로는 부족하다는 뜻입니다.

| 신호 | 필요한 것 |
| --- | --- |
| 「`ax + by = c` 의 정수해」 | 몫을 버리지 않는 확장 유클리드 호제법 |
| 「소인수분해」 | 최대공약수는 소인수분해 없이 구하지만, 그 반대는 성립하지 않는다 |
| 「세 수 이상의 최대공약수」 | 둘씩 접어 간다 — `gcd(a, b, c) = gcd(gcd(a, b), c)` |

#### 실제로 쓰이는 곳

- **Python 표준 라이브러리** — `math.gcd` 가 이 글의 과제와 **같은 계약**을 씁니다. 공식 문서가
  *"Return the greatest common divisor of the specified integer arguments. If any of the
  arguments is nonzero, then the returned value is the largest positive integer that is a
  divisor of all arguments. If all arguments are zero, then the returned value is `0`."*
  라고 적어요 — 「언제나 양수」와 「둘 다 0 이면 0」이 그대로입니다.
  ([공식 문서](https://docs.python.org/3/library/math.html), 조회일 2026-08-31)
- **Java 표준 라이브러리** — `BigInteger.gcd` 가 절댓값 규약까지 같습니다. 공식 문서가
  *"Returns a BigInteger whose value is the greatest common divisor of abs(this) and
  abs(val). Returns 0 if this == 0 && val == 0."* 로 적고 반환값을 `GCD(abs(this), abs(val))`
  로 정해요.
  ([공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigInteger.html), 조회일 2026-08-31)

두 문서에서 확인한 것을 같은 기준으로 놓으면 이렇습니다.

| 기준 | 이 글 | Python `math.gcd` | Java `BigInteger.gcd` |
| --- | --- | --- | --- |
| 음수 입력 | 절댓값으로 본다 | 양수를 돌려준다 | `abs(this)` 와 `abs(val)` 로 본다 |
| 둘 다 0 | 0 | 0 | 0 |
| 안에서 쓰는 절차 | 유클리드 호제법 | 이 글이 확인하지 못했다 | 이 글이 확인하지 못했다 |

**이 글의 계약이 두 표준 라이브러리의 계약과 같다는 것**이 이 절의 값입니다. 부호와 0 을 다루는 방식이
관례로 굳어 있고, 이 글의 코드 첫 두 줄과 마지막 한 줄이 그 관례를 그대로 지킵니다.

#### 경쟁 설계와의 대조

경쟁 설계는 **이진 GCD(스타인 알고리즘)** 입니다. 나눗셈을 하나도 안 쓰고 **2 로 나누기(시프트)와 빼기**만으로
같은 답을 내요. 두 수가 함께 갖는 2 의 거듭제곱을 먼저 떼어 두고, 남은 쪽을 계속 빼 나가며 짝수가 생길
때마다 2 로 나눕니다. 두 설계가 한 걸음에 쓰는 연산이 이렇게 갈립니다.

| 설계 | 한 걸음의 연산 | 한 걸음에 줄어드는 양 |
| --- | --- | --- |
| 유클리드 호제법 | 나머지(`%`) | 같은 수를 몫만큼 되풀이해 뺀 만큼 |
| 이진 GCD | 시프트(`>>`)와 뺄셈 | 절반이나 두 수의 차이만큼 |

`bigint` 나머지 연산은 자릿수를 따라 비용이 커지고 시프트는 그보다 가볍습니다. 그래서 **이 절만 기준을 둘로
가릅니다.** 앞 절들의 연산 횟수로 세면 이진 GCD 는 시프트와 비교가 일의 대부분이라 나머지 연산이 0 으로 나와
비교가 안 되기 때문이에요. 벤치 하네스(`gcd-guide.alt.ts`)가 나눗셈·시프트·뺄셈·비교·대입을 각각 하나로 센
**기본 연산**과, 그중 나눗셈만 따로 센 값을 함께 냅니다.

입력은 전개 입력을 그대로 두고 성질이 다른 셋을 더했습니다. 두 설계가 갈리는 자리가 입력에 든 2 의 거듭제곱과
자릿수인데, 전개 입력은 둘 다 작아 폭이 안 보여요. 그래서 나머지 연산이 가장 많이 필요한 이웃 피보나치 쌍
`F(91) · F(90)`, 나눗셈 한 번에 끝나는 2 의 거듭제곱 쌍 `2^60 · 2^30`, 공통 인수가 2 의 거듭제곱인 짝수 쌍
`2^40·3 · 2^40·5` 를 더합니다. 넷 다 `.alt.ts` 에 적힌 상수라 몇 번을 실행해도 같은 값이 나와요. 전개 입력은
부호를 뗀 `273 · 441` 로 넣었습니다.

<!--proof:breakeven-->
| 입력 | 호제법 기본 연산 | 그중 나눗셈 | 이진 기본 연산 | 이진 나눗셈 | 손익분기 배수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 전개 입력 | 29 | 7 | 35 | 0 | 1.86 |
| 피보나치 이웃 | 357 | 89 | 410 | 0 | 1.60 |
| 2 의 거듭제곱 | 5 | 1 | 158 | 0 | 154.00 |
| 공통 인수가 2 의 거듭제곱 | 17 | 4 | 143 | 0 | 32.50 |

손익분기 배수는 나눗셈 한 번을 기본 연산 몇 번으로 칠 때 두 설계의 합이 같아지는가이고, 호제법의 두 칸과 이진 기본 연산 한 칸으로 계산했습니다. 가장 작은 줄은 「피보나치 이웃」의 1.60 배, 가장 큰 줄은 「2 의 거듭제곱」의 154.00 배입니다.

<!--/proof-->

**기본 연산 수만 보면 네 줄 다 호제법이 적습니다.** 그런데 그 계수는 나눗셈 한 번과 시프트 한 번을 같은 값으로
센 것이고, 나눗셈 횟수에서는 네 줄 다 이진 쪽이 적어요. 어느 쪽이 적은지는 나눗셈 한 번이 기본 연산 몇 번
값인가로 정해지고, 그 경계가 마지막 칸입니다. 축마다 적은 쪽을 모으면 이렇습니다.

| 축 | 유클리드 호제법 | 이진 GCD | 적은 쪽 |
| --- | --- | --- | --- |
| 기본 연산 수 | 네 입력 모두 더 적다 | 네 입력 모두 더 많다 | 유클리드 호제법 |
| 나눗셈 횟수 | 나머지 연산 횟수만큼 | 0 | 이진 GCD |
| 나눗셈 한 번이 손익분기 배수보다 무거운 기계 | 나눗셈 비용이 쌓인다 | 시프트와 뺄셈만 쓴다 | 이진 GCD |
| 입력에 2 의 거듭제곱이 많이 든 경우 | 나눗셈 한 번으로 건너뛴다 | 한 비트씩 시프트로 뗀다 | 유클리드 호제법 |
| 구현 | 반복문 하나에 대입 셋 | 2 의 거듭제곱을 떼는 반복이 셋 | 유클리드 호제법 |

**우열이 반대가 되는 조건은 입력에 든 2 의 거듭제곱입니다.** 마지막 칸이 입력마다 두 자릿수 넘게 갈리므로,
나눗셈 한 번을 기본 연산 열 번쯤으로 치는 같은 기계에서도 피보나치 이웃과 전개 입력에서는 이진 쪽이, 2 의
거듭제곱이 많이 든 두 입력에서는 호제법이 적습니다. 이진 GCD 는 2 의 거듭제곱을 한 비트씩 시프트로 떼어야
하고, 호제법은 나눗셈 한 번으로 그만큼을 건너뛰기 때문이에요.

**이 절차가 내주는 것은 나눗셈에 대한 의존입니다.** 나눗셈이 없는 하드웨어나 나눗셈 비용이 특히 큰 큰 수
라이브러리에서는 이진 쪽이 적은 일을 해요. 얻는 것은 **절차의 짧음과 몫**입니다. 반복문 하나에 대입 셋이고,
버린 몫을 살리면 그대로 확장 유클리드 호제법이 됩니다.

### 수식 정의와 유도

파트 1 이 값으로 보인 것은 「이 입력에서 나머지 연산 몇 번」입니다. **임의의 입력에서 몇 번을 넘지 않는가**는
값으로 못 얻어요. 여기서 자릿수로 닫습니다. 입력은 `|a| ≥ |b| ≥ 1` 이라고 둡니다. 작은 쪽이 앞이면 첫 바퀴가
두 값을 뒤바꾸기만 하므로 나머지 연산이 한 번 늘어날 뿐이에요. 이 절이 쓰는 기호는 이렇습니다.

| 기호 | 정의 |
| --- | --- |
| $N(a, b)$ | 입력 $(a, b)$ 에서 나머지 연산이 실행되는 횟수 |
| $x_i$ | 이 절에서 쓰는 나머지 수열의 번호. $x_1$ 이 큰 쪽 입력, $x_2$ 가 작은 쪽 입력, $x_{N+2} = 0$ |
| $q_i$ | $x_i$ 를 $x_{i+1}$ 로 나눈 몫 |
| $F(k)$ | 피보나치 수. $F(0) = 0$, $F(1) = 1$, $F(k) = F(k-1) + F(k-2)$ |
| $\varphi$ | 황금비 $(1 + \sqrt5) / 2$ |

나머지 연산이 `N` 번 실행되면 바퀴마다 이 등식이 성립합니다.

$$x_{i} \;=\; q_i \, x_{i+1} + x_{i+2}, \qquad q_i \ge 1, \qquad x_{N} \ge 2, \qquad x_{N+1} \ge 1$$

`q_i ≥ 1` 인 것은 `x_i > x_{i+1}` 이라서입니다. `|a| ≥ |b|` 로 두었고, 둘째 바퀴부터는 나머지가 나누는 수보다
작아요. 마지막 두 조건은 `x_{N+1}` 이 0 이 아닌 마지막 칸이고 `x_N` 은 그보다 크다는 뜻입니다. 등식에 `q_i ≥ 1`
을 넣으면 `x_i ≥ x_{i+1} + x_{i+2}` 이고, 이것이 피보나치 점화식과 같은 모양이라 뒤에서부터 채운 최솟값이
피보나치 수가 됩니다. 뒤에서부터 채우는 조각이 아래예요.

```ts
// 마지막 쌍이 가장 작을 때(x_{N+1} = 1, x_N = 2) 앞의 값들이 어떻게 정해지는가
let next = 1n; // x_{N+1}
let cur = 2n; // x_N — 마지막 나눗셈의 몫이 2 이상이라 1 보다 크다
for (let i = 0; i < N - 1; i++) {
  const before = cur + next; // 몫이 1 일 때의 최솟값
  next = cur;
  cur = before;
}
// cur 가 x_1, next 가 x_2 의 최솟값이다
```

**정의를 값에 넣어 검산해 봅시다.** `N = 6` 을 넣고, 채운 두 값을 실제로 실행합니다.

<!--proof:mathMinChain-->
```text
N = 6 일 때 뒤에서부터 채운 최솟값
  자리     x_8  x_7  x_6  x_5  x_4  x_3  x_2  x_1
  최솟값     0    1    2    3    5    8   13   21
  x_2 = 13 = F(7),  x_1 = 21 = F(8)
  gcd(21n, 13n) 의 나머지 연산   6 번
```

일반으로 적으면 **나머지 연산이 `N` 번 실행되면 작은 쪽 입력이 `F(N + 1)` 이상**입니다. 이웃 피보나치 쌍은 몫이
마지막을 빼고 전부 1 이라 등호가 되고, 그래서 나머지 연산이 가장 많아요.

$$N(a, b) = N \quad\Longrightarrow\quad |b| \;\ge\; F(N+1) \qquad (|a| \ge |b| \ge 1)$$

<!--proof:fibBound-->
| k | F(k) | F(k−1) | 나머지 연산 N | 작은 쪽 자릿수 d | 4.785d + 1 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 21 | 13 | 6 | 2 | 10.6 |
| 12 | 144 | 89 | 10 | 2 | 10.6 |
| 20 | 6,765 | 4,181 | 18 | 4 | 20.1 |
| 40 | 102,334,155 | 63,245,986 | 38 | 8 | 39.3 |
| 87 | 679,891,637,638,612,258 | 420,196,140,727,489,673 | 85 | 18 | 87.1 |

5 줄에서 나머지 연산 횟수가 k − 2 인가: 예. 4.785d + 1 을 넘는 줄이 있는가: 없습니다.

<!--/proof-->

전개 입력은 작은 쪽이 앞인 입력이라, 첫 바퀴를 떼고 확인합니다.

<!--proof:mathWalkCheck-->
```text
전개 입력의 나머지 연산   7 번 — 첫 번은 몫이 0 이라 두 값을 뒤바꾸기만 한다
뒤바꾼 (441, 273)   N = 6   F(N + 1) = F(7) = 13
작은 쪽 273 ≥ 13 인가: 예
몫 1 1 1 1 1 2 가운데 1 이 아닌 몫 1 개
(441, 273) = 21 × (21, 13) — (21, 13) 은 이웃 피보나치 쌍 F(8) · F(7)
```

부등식이 헐거운 것은 마지막 줄 때문입니다. 이 입력은 이웃 피보나치 쌍에 최대공약수를 곱한 쌍이라, 몫은
피보나치 쌍과 같고 칸 값만 그 배수만큼 커요.

**이제 유도합니다.** 피보나치 수를 아래에서 막습니다. `F(k) ≥ φ^{k−2}` 이고, 이것은 `φ` 가 `φ^2 = φ + 1` 을
만족한다는 것에서 귀납으로 나옵니다. 기저 두 개는 이렇습니다.

<!--proof:phiBase-->
```text
k = 2   F(2) = 1   φ^0 = 1.000   1 ≥ 1.000 인가: 예
k = 3   F(3) = 2   φ^1 = 1.618   2 ≥ 1.618 인가: 예
```

단계는 `k − 1` 과 `k − 2` 에서 성립한다고 두고 `k` 로 가는 것입니다. 두 항을 각각 아래로 막고 `φ^{k−4}` 로
묶은 뒤, `φ + 1 = φ^2` 을 넣어요.

$$F(k) = F(k-1) + F(k-2) \;\ge\; \varphi^{k-3} + \varphi^{k-4} = \varphi^{k-4}(\varphi + 1) = \varphi^{k-4} \cdot \varphi^{2} = \varphi^{k-2}$$

<!--proof:phiBound-->
| k | F(k) | φ^(k−2) | F(k) ≥ φ^(k−2) |
| ---: | ---: | ---: | --- |
| 2 | 1 | 1 | 예 |
| 5 | 5 | 4 | 예 |
| 10 | 55 | 47 | 예 |
| 20 | 6,765 | 5,778 | 예 |
| 40 | 102,334,155 | 87,403,803 | 예 |
| 87 | 679,891,637,638,612,258 | 5.807e+17 | 예 |

6 줄 가운데 6 줄에서 부등식이 참입니다. φ^(k−2) 는 반올림한 값입니다.

<!--/proof-->

두 부등식을 이으면 상한이 나옵니다. 작은 쪽 `|b|` 의 십진 자릿수가 `d` 이면 `|b| < 10^d` 이고, 위에서
`|b| ≥ F(N + 1) ≥ φ^{N−1}` 이므로 양변에 상용로그를 취해 정리해요.

$$\varphi^{\,N-1} \le |b| < 10^{d} \quad\Longrightarrow\quad N - 1 < \frac{d}{\log_{10}\varphi} \quad\Longrightarrow\quad N < 4.785\,d + 1$$

상수 4.785 는 `1 / log₁₀ φ` 입니다.

<!--proof:mathConst-->
```text
log10 φ = log10 1.618034 = 0.208988
1 / 0.208988 = 4.7850
```

**계수를 냅니다.** 과제 규모와 그보다 큰 자릿수를 넣으면 이렇습니다.

<!--proof:mathScale-->
| 작은 쪽 자릿수 d | 상한 4.785d + 1 | 실측 | 1 부터 전부 나눠 보기 |
| ---: | ---: | --- | --- |
| 18 | 87.1 | 85 (F(87) · F(86)) | 2 × 10^18 번 안팎 |
| 100 | 479.5 | — | 2 × 10^100 번 안팎 |
| 1,000 | 4,786.0 | — | 2 × 10^1000 번 안팎 |

나머지 연산 횟수는 **값이 아니라 자릿수에 비례**합니다. 자릿수가 하나 늘 때마다 상한이 4.785 씩 늘고, 1 부터
전부 나눠 보는 방법은 같은 자리에서 열 배씩 늘어요.

### 불변식 — 바퀴가 끝날 때마다 (x, y) 의 공약수 집합이 처음 두 수의 공약수 집합과 같다

파트 1 에서 코드가 동작하는 것을 아홉 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 문장으로 세우고, 그것이 실제로 유지되는지 확인해
봅시다.

> **부호를 뗀 직후와 반복 한 바퀴가 끝날 때마다**, `(x, y)` 의 공약수 집합은 처음 두 수 `(|a|, |b|)` 의
> 공약수 집합과 정확히 같습니다. 그리고 `y` 는 바퀴마다 엄격하게 줄어듭니다.

<!--proof:invariantPairs-->
| 시점 | (x, y) | 공약수 집합 | 처음 집합과 일치 |
| --- | --- | --- | --- |
| T1 이 끝난 뒤 | (273, 441) | {1, 3, 7, 21} | 예 |
| T2 가 끝난 뒤 | (441, 273) | {1, 3, 7, 21} | 예 |
| T3 이 끝난 뒤 | (273, 168) | {1, 3, 7, 21} | 예 |
| T4 가 끝난 뒤 | (168, 105) | {1, 3, 7, 21} | 예 |
| T5 가 끝난 뒤 | (105, 63) | {1, 3, 7, 21} | 예 |
| T6 이 끝난 뒤 | (63, 42) | {1, 3, 7, 21} | 예 |
| T7 이 끝난 뒤 | (42, 21) | {1, 3, 7, 21} | 예 |
| T8 이 끝난 뒤 | (21, 0) | {1, 3, 7, 21} | 예 |

8 시점 가운데 8 시점에서 공약수 집합이 {1, 3, 7, 21} 입니다. y 는 441 → 273 → 168 → 105 → 63 → 42 → 21 → 0 으로 시점마다 줄었습니다.

<!--/proof-->

「바퀴가 끝날 때마다」가 문장에 꼭 들어가야 합니다. 바퀴 도중, `x = y` 를 실행하고 `y = r` 을 아직 실행하지
않은 순간에는 쌍이 `(y, y)` 라 공약수 집합이 잠깐 달라져요. 반복이 다 끝난 뒤 한 번만 참인 것이 아니라 바퀴
경계마다 참이어야 다음 바퀴가 그 성질을 그대로 이어받습니다.

**출발점부터 봅시다.** 부호를 뗀 직후 `(x, y)` 는 `(|a|, |b|)` 이고, 공약수는 부호와 상관이 없으니 그 집합이
`(a, b)` 의 공약수 집합과 같습니다. 그 뒤로 상태를 바꾸는 갈래는 반복 조건 하나가 가릅니다.

| 바퀴 시작의 `y` | 바퀴가 하는 일 | 공약수 집합이 유지되는 근거 | `y` 가 줄어드는 근거 |
| --- | --- | --- | --- |
| 0 이 아니다 | `(x, y)` 를 `(y, x mod y)` 로 | 1단계의 양쪽 포함 — `r = x − q·y` 와 `x = q·y + r` | 새 `y` 는 `x mod y` 라 옛 `y` 보다 작다 |
| 0 이다 | 아무것도 안 바꾸고 반복을 끝낸다 | 바뀐 것이 없다 | 바뀐 것이 없다 |

`y` 는 0 이거나 0 이 아니고 그 사이의 경우가 없으므로, 두 줄이 갈래를 빠짐없이 덮어요. 반복이 끝나면 쌍이
`(x, 0)` 이고 그 공약수 집합은 `x` 의 약수 전체라, 불변식이 말하는 「처음 두 수의 공약수 집합」의 가장 큰
값이 `x` 입니다. 그리고 `y` 가 0 이상의 정수이면서 매 바퀴 줄어드니 반복은 반드시 끝나요.

**경계에 있는 입력도 확인하고 갑시다.** 아래 여덟 줄이 이 함수가 받을 수 있는 모양의 끝입니다.

<!--proof:invariantEdges-->
| 입력 | 나머지 연산 | 정본의 답 | 정의로 구한 값 |
| --- | ---: | ---: | ---: |
| 둘 다 0 gcd(0n, 0n) | 0 | 0 | 0 |
| 한쪽이 0 gcd(7n, 0n) | 0 | 7 | 7 |
| 앞이 0 gcd(0n, 9n) | 1 | 9 | 9 |
| 같은 값 gcd(7n, 7n) | 1 | 7 | 7 |
| 둘 다 음수 gcd(-12n, -18n) | 3 | 6 | 6 |
| 둘째만 음수 gcd(12n, -18n) | 3 | 6 | 6 |
| 한쪽이 1 gcd(1n, 1000000n) | 2 | 1 | 1 |
| 작은 쪽이 앞 gcd(273n, 441n) | 7 | 21 | 21 |

8 입력 가운데 8 입력에서 정본의 답이 정의로 구한 값과 일치합니다. 정의로 구할 때 둘 다 0 이면 0 으로 둡니다.

<!--/proof-->

`gcd(0n, 9n)` 이 이 절차의 경계입니다. `x` 가 0 이어도 `0 mod 9` 가 0 이라 한 바퀴 만에 `(9, 0)` 이 되고,
크기를 미리 비교하는 코드가 없어도 답이 나와요. 같은 값 `gcd(7n, 7n)` 은 첫 나머지가 0 이라 한 바퀴에 끝납니다.

**이제 깨뜨려 봅시다.** 불변식의 「공약수 집합이 그대로」를 지키던 줄은 `x = y` 입니다 — 이 줄이 옛 `y` 를 한 칸
왼쪽으로 옮겨야 새 쌍이 `(y, r)` 이 돼요. 「새로 구한 것은 나머지이니 그것을 두 자리에 다 넣으면 되지 않나」라는
생각으로 그 **한 줄만** 고쳐 봅니다.

```ts
while (y !== 0n) {
  const r = x % y;
  x = r; // ← y 였다
  y = r;
}
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-keep-remainder-->
| 입력 | 정본의 답 | 나머지를 남긴 답 | 판정 |
| --- | ---: | ---: | --- |
| 전개 입력 -273 과 441 | 21 | 0 | 틀리다 |
| 둘 다 음수인 -12 와 -18 | 6 | 0 | 틀리다 |
| 둘째만 음수인 12 와 -18 | 6 | 0 | 틀리다 |
| 한쪽이 0 인 7 과 0 | 7 | 7 | 같다 |

앞의 세 줄에서 0 이 나옵니다. 전개 입력에서 쌍이 어떻게 되는지 따라가 보면 불변식이 첫 바퀴에서 깨져요.

<!--proof:mutantKeepTrace-->
```text
gcd(-273n, 441n) 에서 x 에 y 대신 r 을 넣으면
  x = 273, y = 441   273 % 441 = 273   → (273, 273)
  x = 273, y = 273   273 % 273 = 0     → (0, 0)
  y 가 0 이라 x = 0 을 돌려준다
  첫 바퀴 뒤의 쌍 (273, 273) 의 공약수   {1, 3, 7, 13, 21, 39, 91, 273}
  처음 쌍의 공약수                       {1, 3, 7, 21}
```

첫 바퀴 뒤의 쌍 `(r, r)` 의 공약수 집합은 `r` 의 약수 전체이고, 처음 집합에 없던 13 · 39 · 91 · 273 이
들어왔습니다. 한 바퀴 더 가면 나머지가 0 이 되어 두 값이 모두 0 이 되고, 그때 0 을 돌려줘요. 넷째 줄이
「같다」로 나온 것에도 이유가 있습니다. 둘째 인자가 0 이면 반복이 한 번도 실행되지 않아 바꾼 줄을 지나지
않아요.

### 비용 계산

#### 비용을 세는 과정

한 번의 호출이 하는 일은 세 무리입니다 — 부호를 떼는 것, 바퀴마다 나머지를 구해 두 값을 옮기는 것, 답을
돌려주는 것이에요. 전개의 걸음으로 세면 이렇게 나뉩니다.

<!--proof:perfCount-->
| 일 | 걸음 | 횟수 |
| --- | --- | ---: |
| 부호 판정과 절댓값 | T1 | 2 |
| 나머지 연산 | T2 ~ T8 | 7 |
| 두 값 옮기기 | T2 ~ T8 | 14 |
| 반복 조건 판정 | T2 ~ T9 | 8 |

나머지 연산 7 번에 옮기기가 14 번, 반복 조건 판정이 8 번 따라붙었습니다.

<!--/proof-->

T1 은 인자마다 부호를 한 번씩 보는 자리라 입력과 상관없이 두 번입니다. 바퀴 하나는 T3 에서 보듯 나머지 연산
한 번에 옮기기 두 번이 붙고, 반복 조건 판정은 바퀴마다 한 번에 반복을 끝낼 때(T9) 한 번이 더 붙어요. 그래서 옮기기와 조건
판정은 둘 다 나머지 연산 횟수 `N` 에 비례하고, 차수를 정하는 것은 `N` 하나입니다.

여기서 세지 않은 것도 적어 둡니다. `bigint` 나머지 연산 한 번의 비용까지 세면 여기에 두 수의 자릿수에 따른
값이 곱해지는데, 수가 하드웨어 워드 안에 들면 그 값이 상수예요. 이 글의 과제 규모(`10^18` 이하)가 그
경우입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (한쪽이 다른 쪽의 배수이고 큰 쪽이 앞) | `O(1)` | `Θ(1)` — 나머지 연산이 한 번이다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(d)` | 정하지 않았다 |
| **최악의 경우** (이웃 피보나치 쌍) | `O(d)` | `Θ(d)` — `N = k − 2` 가 자릿수에 비례한다 |

**최선과 최악이 갈리는 절차입니다.** 한쪽이 다른 쪽의 배수면 첫 나머지가 0 이라 한 번에 끝나고, 이웃 피보나치
쌍이면 자릿수에 비례하는 횟수가 필요해요. 평균은 타이트 경계를 적지 않았습니다. 입력 분포를 정하지 않았기
때문이고, 분포를 정하면 그 분포에 대한 기댓값을 따로 셀 수 있어요.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 없다는 것이 이 절차의 특징이에요 — 정렬도, 표도,
미리 만드는 값도 없습니다. 나머지 연산은 `N` 번이고 `|a| ≥ |b| ≥ 1` 이면 `N < 4.785d + 1`, 작은 쪽이 앞이면
그보다 한 번 더이며, 저장 칸은 `x` · `y` · `r` 셋입니다. 과제 규모에 넣으면 이렇습니다.

<!--proof:perfTotal-->
```text
두 수가 10^18 이하일 때
  작은 쪽 자릿수 d             18 이하
  나머지 연산 N ≤ 4.785d + 1   87.1
  규모 안의 최악               85   (F(87), F(86))
  저장 칸                      x · y · r 셋
```

첫 줄의 18 은 두 수가 다를 때의 자릿수이고, 두 수가 모두 `10^18` 이면 작은 쪽이 19 자리지만 첫 나머지가 0
이라 한 번에 끝납니다. **보장의 종류는 최악 보장입니다.** 코드에 난수가 하나도 없고 입력 분포에 대한 가정도
없어요. 같은 입력을 두 번 넣으면 반환값도 나머지 연산 횟수도 똑같이 나옵니다.

#### 최악을 만드는 입력

「큰 수가 최악」이라는 통념부터 확인합시다. 과제 상한 언저리의 다섯 모양을 실제로 실행하면 값이 크게
갈립니다.

<!--proof:shapeValues-->
| 입력 모양 | 작은 쪽 자릿수 | 나머지 연산 | gcd |
| --- | ---: | ---: | ---: |
| 이웃 피보나치 F(87) · F(86) | 18 | 85 | 1 |
| 서로소인 큰 두 수 | 18 | 5 | 1 |
| 한쪽이 다른 쪽의 배수 | 10 | 1 | 1,000,000,000 |
| 둘 다 같은 값 | 19 | 1 | 1,000,000,000,000,000,000 |
| 한쪽이 1 | 1 | 1 | 1 |

첫 줄과 둘째 줄은 작은 쪽이 18 자리와 18 자리인데 나머지 연산이 85 번과 5 번입니다.

<!--/proof-->

**통념은 이 절차에서 절반만 맞습니다.** 자릿수가 상한을 정하지만 실제 횟수는 몫이 정해요. 몫이 크면 한 바퀴에
많이 줄고, 몫이 1 이면 `x` 가 `y` 로, `y` 가 `x − y` 로 바뀔 뿐이라 조금만 줍니다. 몫이 계속 1 이 되려면 두
수의 비가 황금비에 가까워야 하고, 그런 쌍이 이웃 피보나치 수예요. 같은 144 에서 시작하는 두 수열을 나란히
놓으면 칸 수가 어떻게 갈리는지 확인할 수 있습니다.

<!--fig:worst-fib-->
![나머지 수열 둘 — 이웃 피보나치 쌍 (144, 89) 은 몫이 거의 전부 1 이라 칸이 가장 많다](./figs/worst-fib.svg)

이웃 피보나치 쌍의 나머지 수열은 한 칸 뒤가 곧 한 단계 아래 피보나치 수라, 수열이 피보나치 수를 하나씩
거꾸로 지나갑니다. 과제 상한 아래에서 최악을 만드는 방법은 그래서 하나예요. `10^18` 을 넘지 않는 가장 큰 이웃
피보나치 쌍 `F(87) · F(86)` 을 고르고, 그 쌍이 상한 표의 85 번입니다. 가장 적은 일을 하는 입력은 반대쪽이에요.
큰 쪽이 앞이고 한쪽이 다른 쪽의 배수면 첫 나머지가 0 이라 자릿수와 상관없이 한 번에 끝납니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 약수를 하나씩 찾던 것을 **공약수 집합을 지키며 두 수를 줄이는
것**으로 바꿨고, 줄이는 방법이 나머지이며, 그 근거는 `x = q·y + r` 에서 두 방향의 나눗셈 성질이 모두 성립한다는
것 하나입니다. 두 바퀴마다 값이 절반 아래로 줄어서 나머지 연산 횟수가 자릿수를 따라갑니다.

```text
부호를 뗀다 → (x, y) 를 (y, x mod y) 로 옮긴다 → y 가 0 이면 x 를 돌려준다
               └ 공약수 집합이 그대로다            └ (x, 0) 의 최대공약수는 x 다
```

먼저 답이 붙는 문제 하나입니다. `gcd(144n, 89n)` 은 이웃 피보나치 쌍이라 나머지 연산이 가장 많은 모양이었어요.
그러면 **두 수에 각각 21 을 곱한 `gcd(3024n, 1869n)`** 은 나머지 연산이 몇 번이고 답은 무엇일까요?

<!--check:scaledPair-->
나머지 연산은 그대로이고, 답만 21 배가 됩니다. 등식 `x = q·y + r` 의 양변에 21 을 곱하면
`21x = q·(21y) + 21r` 이고 `0 ≤ 21r < 21y` 라, 몫은 같고 나머지만 21 배가 돼요. 바퀴마다 같은 일이 되풀이되니
수열의 칸이 전부 21 배이고, 칸 수와 몫은 그대로입니다. 그래서 답이 1 이 아닌 입력도 최악이 될 수 있어요.
최악을 만드는 것은 몫의 모양이지 답의 크기가 아닙니다.

<!--proof:selfcheckScaled-->
| 입력 | 나머지 연산 | 몫 | gcd |
| --- | ---: | --- | ---: |
| gcd(144n, 89n) | 10 | 1 1 1 1 1 1 1 1 1 2 | 1 |
| gcd(3024n, 1869n) | 10 | 1 1 1 1 1 1 1 1 1 2 | 21 |
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「불변식」, 「수식 정의와 유도」, 두 번째 「짚고 가기」를 다시
보세요.

- 불변식은 「`y` 가 바퀴마다 엄격하게 줄어든다」고 말합니다. 그러면 `x` 는 어떻습니까 — 전개의 T2
  에서 `x` 가 273 에서 441 로 커졌는데, 그 뒤의 바퀴에서도 `x` 가 커지는 일이 있습니까. 있다면 어떤 입력에서,
  없다면 왜 없는지 적어 보세요.
- 상한 `4.785d + 1` 은 `|a| ≥ |b|` 일 때의 것이었습니다. 자릿수 `d` 를 하나 고정했을 때 그 상한에 가장 가까운
  입력을 어떻게 만들겠습니까. 그리고 그 입력의 두 수를 뒤바꿔 넣으면 나머지 연산이 몇 번이 되는지 따져 보세요.
- 세 수의 최대공약수를 `gcd(gcd(a, b), c)` 로 구하면, 나머지 연산 횟수의 상한은 세 수의 자릿수로 어떻게
  적힙니까. 첫 호출의 답이 둘째 호출의 입력이 된다는 것을 쓰세요.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### 최대공약수 (Greatest Common Divisor)

풀 파일: [`gcd.ts`](./gcd.ts) · 테스트: [`gcd.test.ts`](./gcd.test.ts) · 실행: `bun test src/algorithms/number-theory/gcd/gcd.test.ts`

#### 한 줄 요약

> 함수는 두 정수 `a`, `b`를 받아 두 수의 최대공약수를 반환한다.

#### 스토리

타일 공장에서 가로 `a`cm, 세로 `b`cm 크기의 직사각형 바닥을 정사각형 타일로 빈틈없이 채우려 한다. 사용하는 타일은 모두 같은 크기여야 하고 자르지 않아야 한다. 가능한 가장 큰 정사각형 타일의 한 변 길이가 얼마인지 구해야 한다.

예를 들어 바닥이 12cm × 18cm라면 6cm 타일로 채울 수 있다. 7cm 타일은 12와 18을 나누어 떨어지게 할 수 없으므로 불가능하다.

한 쪽 치수가 0이면 다른 쪽 치수가 곧 답이 된다. 두 치수가 모두 0이면 어떤 크기의 타일도 조건을 만족하므로 관례상 0을 반환한다.

#### 함수 인터페이스

```ts
export function gcd(a: bigint, b: bigint): bigint;
```

- `a` — 첫 번째 정수, bigint (음수 가능)
- `b` — 두 번째 정수, bigint (음수 가능)
- 반환 — $\gcd(|a|, |b|)$, 항상 $\geq 0$

#### 제약 조건

- $a$, $b$는 임의의 bigint (음수·0·양수 모두 허용)
- 결과는 항상 음이 아닌 값: $\gcd(a, b) \geq 0$
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

두 정수 $a$, $b$의 최대공약수를 반환한다.

- 두 인자 중 한쪽이 $0$이면 나머지의 절댓값을 반환한다.
- $a = b = 0$이면 $0$을 반환한다.
- 음수 입력도 절댓값 기준으로 처리한다.

$$\gcd(a, b) = \gcd(|a|, |b|) \geq 0$$

#### 예시

```ts
gcd(12n, 18n);    // 6n   — 12와 18의 공약수 중 최대값
gcd(100n, 75n);   // 25n  — 100 = 4·25, 75 = 3·25
gcd(17n, 5n);     // 1n   — 17과 5는 서로소
gcd(0n, 9n);      // 9n   — 한쪽이 0이면 나머지 절댓값
gcd(9n, 0n);      // 9n   — 순서 무관하게 동일
gcd(0n, 0n);      // 0n   — 둘 다 0
gcd(-12n, 18n);   // 6n   — 음수는 절댓값 처리
gcd(-12n, -18n);  // 6n   — 양쪽 음수도 동일
```
