# 확장 유클리드 호제법 — 나머지를 만든 몫 하나가 계수 갱신까지 정한다

## 파트 1 — 아이디어에서 동작하는 코드까지

이 파트에서는 전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 지식을 확인합니다. 그다음 계수를 하나씩
대입해 찾는 방법에서 출발해 나머지와 함께 계수를 만들어 가는 방법까지 가고, 그 방법을 단계마다 값으로 푼 뒤,
실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

두 정수 `a`, `b` 의 최대공약수 `g` 는 언제나 `a·x + b·y` 꼴로 적을 수 있습니다. 이렇게 적어 주는 정수 쌍
`(x, y)` 를 **베주 계수**라고 부르고, 이 글의 함수가 만드는 것은 `g` 와 그 쌍, 셋입니다. 전개 입력 하나를 먼저
값으로 보겠습니다.

<!--proof:conceptTask-->
```text
extendedEuclidean(-510n, 183n)
  g           3   510 과 183 의 최대공약수
  (x, y)      (-14, -39)
  a·x + b·y   -510 × (-14) + 183 × (-39) = 7,140 - 7,137 = 3
```

`g` 만 필요하면 앞 편의 [유클리드 호제법](../gcd/gcd-guide.md)으로 끝납니다. 두 수를 `(x, y)` 에서
`(y, x mod y)` 로 바꿔 가며 나온 수를 차례로 적은 줄이 **나머지 수열**이고, 0 이 나온 칸의 바로 앞 칸이
최대공약수예요. 그 절차는 나눌 때마다 나온 몫을 쓰고 나서 버립니다. **버린 몫이 이 글의 재료입니다.**

이 글이 더하는 것은 나머지 수열 아래의 두 줄입니다. 부호를 뗀 두 입력을 `A = |a|`, `B = |b|` 라 하면, 나머지
수열의 칸마다 그 칸의 값을 `A·s + B·t` 로 적어 주는 정수 두 개 `s`, `t` 가 있어요. 칸마다 `s` 를 적은 줄을
`s` 줄, `t` 를 적은 줄을 `t` 줄이라 하고, 둘을 함께 **계수 두 줄**이라고 부르겠습니다. 전개 입력에서 세 줄을
나란히 그리면 이렇습니다.

<!--fig:concept-chain-->
![나머지 수열 아래 계수 두 줄 — 칸마다 510 × s + 183 × t 가 그 칸의 값이고, 0 앞 칸의 계수가 답이다](./figs/concept-chain.svg)

0 이 나온 칸 바로 앞 칸의 값이 최대공약수이고, 그 칸의 두 계수가 `510 × s + 183 × t` 로 그 값을 만듭니다.
첫 인자의 부호를 `s` 에 다시 붙이면 위의 `(x, y)` 예요. 계수 두 줄을 채우는 규칙은 나머지 수열을
채우는 규칙과 같은 모양이라서, 나머지를 만드는 그 자리에서 같은 몫으로 두 줄도 한 칸씩 늘릴 수 있습니다.
이 방법의 이름이 **확장 유클리드 호제법**(extended Euclidean algorithm)이고, 이 글은 끝까지 이 이름 하나로
부릅니다.

두 방법의 비용을 결과만 비교하면 이렇습니다. 가장 단순한 방법은 `g` 를 먼저 구해 두고 `x` 를 0 부터 하나씩
대입해 보는 것이에요.

<!--proof:conceptCost-->
| 입력 | x 를 대입해 찾기의 나눗셈 | 확장 유클리드 호제법의 나눗셈 |
| --- | ---: | ---: |
| 전개 입력 -510 · 183 | 35 | 6 |
| 이웃 피보나치 F(87) · F(86) | 321,001,287,632,734,262 | 85 |

둘째 줄의 작은 쪽은 18 자리 수이고, 확장 유클리드 호제법은 그 쌍에서 나눗셈 85 번으로 g 와 계수 둘을 함께 냈습니다.

<!--/proof-->

나눗셈 횟수는 유클리드 호제법과 똑같습니다. 들고 있는 값은 나머지 수열의 이웃 두 칸과 그 두 칸의 계수라서
추가로 쓰는 메모리가 `O(1)` 이고, 나눗셈 횟수는 작은 쪽 입력의 자릿수를 따라가므로 `O(log min(|a|, |b|))`
번이에요.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **유클리드 호제법과 나머지 수열.** 두 수를 `(y, x mod y)` 로 바꿔 가며 최대공약수를 구하는 절차와, 그때 나온
  수를 차례로 적은 줄입니다. 이 글은 그 수열을 그대로 쓰고 몫을 더 씁니다. 나눗셈 횟수의 상한도 그 편이
  닫았어요 — [유클리드 호제법 가이드](../gcd/gcd-guide.md).
- **나머지 있는 나눗셈.** 양의 정수 `y` 로 `x` 를 나누면 `x = q·y + r`, `0 ≤ r < y` 를 만족하는 몫 `q` 와
  나머지 `r` 이 하나씩 정해진다는 것. 이 글의 갱신식이 이 등식을 `r = x − q·y` 로 옮겨 씁니다.
- **정수 조합.** 두 수에 정수를 곱해 더한 값, 곧 `A·s + B·t` 꼴의 수입니다. 두 조합을 빼거나 정수배 하면 다시
  같은 꼴이 된다는 것만 쓰입니다.
- **JavaScript 의 `bigint`.** 자릿수 제한이 없는 정수 타입입니다. 리터럴 끝에 `n` 을 붙이고, 계수가 입력만큼
  커져도 넘치지 않아요.
- **`bigint` 의 `/` 와 `%` 는 0 쪽으로 자르고, 나머지가 나누어지는 수의 부호를 따른다는 것.** 음수를 나누면
  나머지도 음수로 나옵니다. 값은 「아이디어 상세」의 「이 방법이 기대는 전제」에서 확인해요.

마지막 항목이 흐릿하면 뒤가 어긋납니다. 이 글의 코드는 부호를 먼저 떼어 두고 마지막에 계수에만 다시 붙이는데,
그 까닭이 이 성질이에요. 이 글의 결과로 [`crt`](../crt/crt-guide.md)(중국인의 나머지 정리)가 두 합동식을 합치고,
[`binomialModP`](../binomialModP/binomialModP-guide.md) 가 나눗셈 자리에 쓸 역원을 구합니다.

### 아이디어를 떠올리는 과정 — x 를 대입해 찾기에서 확장 유클리드 호제법까지

아이디어를 찾기 전에 무엇을 만들어야 하는지부터 정해 둡시다. 함수 하나가 두 정수를 받아 최대공약수와 베주
계수를 돌려줍니다.

```ts
function extendedEuclidean(
  a: bigint,
  b: bigint,
): { g: bigint; x: bigint; y: bigint };
```

- 입력: 두 정수 `a`, `b`. 음수와 0 이 들어올 수 있습니다.
- 출력: `{ g, x, y }`. `g` 는 `|a|` 와 `|b|` 의 최대공약수로 언제나 0 이상이고, `a·x + b·y = g` 를 정확히
  만족해야 합니다.
- 경계: `a = b = 0` 이면 셋 다 0 입니다. `b = 0` 이면 `g = |a|` 이고 `a·x = g` 를 만족하는 `x` 를,
  `a = 0` 이면 `g = |b|` 이고 `b·y = g` 를 만족하는 `y` 를 냅니다.
- 규모: 앞 편과 같이 두 수의 절댓값이 `10^18` 이하라고 두고 잽니다. 64 비트 정수 안의 어림수라 흔히 받는
  폭이고, 앞 편이 센 나눗셈 횟수의 상한을 그대로 이어 쓸 수 있어서예요. 비용은 흔한 채점 환경의 예산인 1 초
  (단순 연산 1 초에 1 억 번)에 대어 잽니다.

이 글이 쓰는 기호를 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 뜻 | 이 과제에서 |
| --- | --- | --- |
| `a` · `b` | 두 입력 | 음수·0·양수, 절댓값 `≤ 10^18` |
| `A` · `B` | 두 입력의 절댓값 | 나머지 수열의 첫 두 칸 |
| `g` | 최대공약수 | 반환값의 첫 자리, 언제나 0 이상 |
| `x` · `y` | 베주 계수 | `a·x + b·y = g` 를 만족하는 정수 쌍 |
| `q` | 이번 바퀴의 몫 | 나누는 두 칸 `r0` 를 `r1` 로 나눈 몫 |
| `r_k` | 나머지 수열의 `k` 번째 칸 | `r_0 = A`, `r_1 = B`, 마지막 칸이 0 |
| `s_k` · `t_k` | 계수 두 줄의 `k` 번째 칸 | `r_k = A·s_k + B·t_k` |
| `r0` · `r1` | 코드가 들고 있는 나머지 수열의 이웃 두 칸 | 처음 값은 `A` 와 `B` |
| `s0` · `s1` · `t0` · `t1` | 코드가 들고 있는 그 두 칸의 계수 | 처음 값은 `(1, 0)` 과 `(0, 1)` |
| `signA` · `signB` | 두 입력의 부호 | `-1` 이나 `1` |
| `N` | 한 번 호출할 때의 나눗셈 횟수 | 바퀴 수와 같다 |
| `d` | 작은 쪽 입력의 십진 자릿수 | `d ≤ 19` |

「바퀴」는 반복문 본문을 한 번 실행하는 것을 말합니다. 비용은 끝까지 **나눗셈 횟수**로 셉니다. 몫 `/` 이나
나머지 `%` 를 구하는 나눗셈 한 번을 하나로 세고, 확장 유클리드 호제법에서는 이 값이 바퀴 수 `N` 과 같아요.
메모리는 **저장 칸**(들고 있는 값의 개수)으로 셉니다.

가장 먼저 떠오르는 방법으로 시작합시다. `g` 는 유클리드 호제법으로 먼저 구해 두고, `x` 를 `0, 1, -1, 2, -2, …`
순서로 대입해 보는 것이에요. `g − a·x` 가 `b` 로 나누어떨어지는 순간 그 몫이 `y` 입니다. 정의를 그대로 옮긴
풀이예요.

```ts
function trySearch(a: bigint, b: bigint, g: bigint): { x: bigint; y: bigint } {
  for (let i = 0n; ; i++) {
    for (const x of i === 0n ? [0n] : [i, -i]) {
      if ((g - a * x) % b === 0n) return { x, y: (g - a * x) / b }; // 후보 하나에 나머지 한 번
    }
  }
}
```

`b` 가 0 이면 나눌 수 없으니 이 방법은 `b ≠ 0` 에서만 씁니다. 전개 입력에 실제로 실행하면 이렇게 나와요.

<!--proof:searchWalk-->
```text
g 를 구하는 나눗셈   6 번
대입한 후보          0, 1, -1, 2, -2, …, 14, -14 까지 29 개
멈춘 자리            x = -14   (3 - (-510) × (-14)) / 183 = -39
나눗셈 합            6 + 29 = 35 번
세기만 하는 판       멈출 후보의 순번 29 — 실제로 대입한 개수와 같다
```

답은 맞습니다. 그런데 대입하는 후보의 개수가 `|x|` 를 따라가고, `|x|` 는 입력의 **값**만큼 커질 수 있어요.
큰 입력은 끝까지 대입하면 끝나지 않으므로, 몇 번째 후보에서 멈추는지를 셈으로 냈습니다(`x` 의 해는
`|b| / g` 씩 떨어져 있어서, 그중 절댓값이 가장 작은 것의 순번이 곧 대입 횟수예요). 전개 입력에서 그 셈이 실제로
대입한 개수와 같았던 것이 마지막 줄입니다. 규모를 넣어 봅시다. 이웃한 두 피보나치 수 `F(k) · F(k − 1)`
(`F(0) = 0`, `F(1) = 1`, `F(k) = F(k − 1) + F(k − 2)`)는 앞 편에서 나눗셈이 가장 많았던 쌍이에요.

<!--proof:naiveScale-->
| 두 수의 상한 | 그 아래 가장 큰 이웃 피보나치 쌍 | \|x\| | 나눗셈 | 초당 1 억 번일 때 시간 |
| --- | --- | ---: | ---: | ---: |
| 10^3 | F(16) · F(15) | 233 | 480 | 0.001 초 미만 |
| 10^6 | F(30) · F(29) | 196,418 | 392,864 | 0.004 초 |
| 10^9 | F(44) · F(43) | 165,580,141 | 331,160,324 | 3.3 초 |
| 10^12 | F(59) · F(58) | 225,851,433,717 | 451,702,867,492 | 1.3 시간 |
| 10^18 | F(87) · F(86) | 160,500,643,816,367,088 | 321,001,287,632,734,262 | 약 102 년 |

나눗셈은 g 를 구하는 몫과 후보마다의 나머지를 더해 셌습니다. 후보 수는 끝까지 대입하지 않고 멈출 후보의 순번으로 셌습니다.

<!--/proof-->

아홉 자리에서 이미 예산의 세 배이고, 열여덟 자리면 백 년이 넘습니다. `g` 자체는 나눗셈 수십 번에 나오는데
계수를 찾는 데 값에 비례하는 일을 하면 앞뒤가 안 맞아요. 방향을 바꿔 봅시다. `g` 를 만든 나눗셈들은 등식
`r_k = q·r_{k+1} + r_{k+2}` 를 하나씩 남기고, 그 등식들이 처음 두 수와 `g` 를 잇고 있습니다. **그 등식을
이용해 `g` 를 처음 두 수로 적을 수 있다면**, 후보를 찾지 않아도 됩니다.

손으로 풀 때 흔히 쓰는 길은 끝에서부터 거슬러 대입하는 것입니다. 마지막 등식에서 `g` 를 앞 두 칸으로 적고,
그 식의 뒤 칸 자리에 한 칸 앞의 등식을 넣어 한 칸씩 앞으로 옮겨요. 전개 입력에서 적어 둔 몫은
`2 1 3 1 2 4` 입니다.

<!--proof:backHand-->
```text
3 = 1 × 3 + 0 × 0            r₇ = 0 에서 출발
3 = 0 × 12 + 1 × 3           0 = 12 - 4 × 3 을 넣었다
3 = 1 × 27 + (-2) × 12       3 = 27 - 2 × 12 를 넣었다
3 = (-2) × 39 + 3 × 27       12 = 39 - 1 × 27 을 넣었다
3 = 3 × 144 + (-11) × 39     27 = 144 - 3 × 39 를 넣었다
3 = (-11) × 183 + 14 × 144   39 = 183 - 1 × 144 를 넣었다
3 = 14 × 510 + (-39) × 183   144 = 510 - 2 × 183 을 넣었다
부호를 붙이면 x = -14, y = -39 — 정본의 답과 같다
```

한 줄 내려갈 때마다 식의 두 수가 나머지 수열에서 한 칸씩 앞으로 옮겨 가고, 일곱째 줄에서 처음 두 수 510 ·
183 에 이릅니다. 대입이 모두 몫 하나로 되니, 비용은 몫의 개수, 곧 나눗셈 횟수 `N` 을 따라가요. 그러면 비용이
무엇에 달렸는지, 대입 탐색과 거슬러 대입을 몫의 모양이 다른 입력에서 나란히 세어 봅시다. 넷째 입력의 펠 수
`P(k)` 는 `P(0) = 1`, `P(1) = 2`, `P(k + 1) = 2·P(k) + P(k − 1)` 이라 이웃한 두 수를 나눈 몫이 전부 2 예요.

<!--proof:searchVsBack-->
| 입력 | 작은 쪽 자릿수 | \|x\| | 대입 탐색의 나눗셈 | 거슬러 대입의 나눗셈 |
| --- | ---: | ---: | ---: | ---: |
| 전개 입력 -510 과 183 | 3 | 14 | 35 | 6 |
| 몫이 거의 다 1 — F(87) · F(86) | 18 | 160,500,643,816,367,088 | 321,001,287,632,734,262 | 85 |
| 몫이 전부 2 — P(47) · P(46) | 18 | 143,263,821,649,299,118 | 286,527,643,298,598,284 | 47 |
| 몫 하나가 아주 큼 — 10^18 · 10^18 - 1 | 18 | 1 | 4 | 2 |

거슬러 대입의 나눗셈은 나머지 수열을 만드는 몫 N 번이 전부입니다. 네 줄 모두 거슬러 대입한 (g, x, y) 가 정본의 답과 같습니다. 작은 쪽이 18 자리인 세 줄에서 대입 탐색의 나눗셈은 4 번부터 321,001,287,632,734,262 번까지 갈립니다.

<!--/proof-->

아래 세 줄은 작은 쪽의 자릿수가 같은데 대입 탐색의 나눗셈이 크게 갈리고, 거슬러 대입은 세 줄 모두 백 번
안쪽입니다. 대입 탐색은 `|x|` 를, 거슬러 대입은 나눗셈 횟수 `N` 을 따라가요. 여기서 관찰한 것은 하나입니다. **`g` 를 만든 나눗셈 `N`
번의 몫에 계수를 만드는 데 필요한 것이 다 들어 있습니다.** 몫을 버리지 않으면 값이 아니라 자릿수만큼의 일로
계수가 나와요.

거슬러 대입은 가장 단순한 후보라 먼저 시험해 볼 만합니다. 답과 나눗셈 횟수는 위 표대로 문제가 없어요. 걸리는
것은 방향입니다. 몫을 쓰는 순서가 몫이 나온 순서의 거꾸로라서, 나머지 수열을 끝까지 만들며 몫을 모두 적어
두었다가 한 번 더 거꾸로 지나가야 합니다.

<!--proof:backMemory-->
| 입력 | 나눗셈 N | 적어 두는 몫 |
| --- | ---: | ---: |
| 전개 입력 -510 과 183 | 6 | 6 |
| 몫이 거의 다 1 — F(87) · F(86) | 85 | 85 |
| 몫이 전부 2 — P(47) · P(46) | 47 | 47 |
| 몫 하나가 아주 큼 — 10^18 · 10^18 - 1 | 2 | 2 |

몫은 네 줄 모두 나눗셈 수만큼 적어 둡니다. 가장 많은 줄도 85 칸이라 메모리가 모자라지는 않습니다.

<!--/proof-->

이 규모에서 적어 두는 칸이 모자라지는 않습니다. 다만 수열을 두 번 지나가고, 몫을 담을 칸이 걸음 수를 따라
늘어요. 대입을 앞에서 뒤로 할 수 있으면 둘 다 없어집니다. 그래서 첫 두 나머지부터 처음 두 수로 적어 봅시다.

<!--proof:forwardTwo-->
```text
144      = 510 - 2 × 183                  나머지를 만든 등식
144      = 510 × 1 + 183 × (-2)           계수 (1, -2)
39       = 183 - 1 × 144                  나머지를 만든 등식
39       = 183 - 1 × (510 - 2 × 183)      144 자리에 위 식을 넣었다
39       = 510 × (-1) + 183 × 3           계수 (-1, 3)
계수만   (0, 1) - 1 × (1, -2) = (-1, 3)   앞 두 칸의 계수에 나머지와 같은 식
```

둘째 나머지 39 의 계수가 앞 두 칸 183 · 144 의 계수에서 **나머지와 같은 식**으로 나왔습니다. 나머지가
`183 − 1 × 144` 이면 계수도 `(0, 1) − 1 × (1, -2)` 예요. 칸마다 그 칸을 처음 두 수로 적는 계수를 붙여 두면,
몫을 얻은 그 바퀴에서 새 칸의 계수까지 정해집니다. 지금까지 해 본 방법을 차례로 놓으면 이렇습니다.

<!--fig:origin-approaches-->
![시도한 방법 셋 — 둘은 버렸고 하나가 남았다](./figs/origin-approaches.svg)

남은 방법이 **확장 유클리드 호제법**입니다. 나머지 수열의 칸마다 `A·s + B·t` 의 두 계수를 함께 적고, 새 칸을
만들 때 쓴 몫으로 두 계수도 같은 식으로 만들어요. 첫 두 칸의 계수를 어떻게 정하는지, 같은 식이 왜 늘 맞는지,
어디서 멈추고 무엇을 답으로 읽는지는 다음 절에서 실현하는 순서대로 확인합니다.

### 아이디어 상세 — 확장 유클리드 호제법

이 아이디어를 한 문장으로 줄이면 이렇습니다. **나머지 수열을 한 칸씩 늘릴 때마다, 그 칸을 만든 몫 하나로 계수
두 줄도 같은 식으로 한 칸씩 늘리고, 나머지가 0 이 된 칸 바로 앞의 계수에 입력의 부호를 붙여 답으로
읽습니다.** 미리 만들어 두는 것이 없어서 세 단계 모두 호출 한 번 안에서 해요.

| 단계 | 하는 일 | 앞 단계에서 받아 쓰는 것 |
| --- | --- | --- |
| 1단계 첫 두 칸의 계수 정하기 | 부호를 뗀 두 입력을 첫 두 칸으로 두고, 그 두 칸의 계수를 `(1, 0)` · `(0, 1)` 로 정한다 | — |
| 2단계 같은 몫으로 세 줄 이어 쓰기 | 이웃 두 칸을 나눈 몫으로 나머지 수열과 계수 두 줄에 새 칸을 하나씩 채운다 | 1단계의 첫 두 칸 |
| 3단계 0 에서 멈추고 부호 붙여 읽기 | 나머지가 0 이 된 칸 바로 앞 칸의 값과 계수를 읽고, 계수에 입력의 부호를 붙인다 | 2단계가 채운 세 줄 · 1단계에서 떼어 둔 부호 |

#### 먼저 알아 둘 개념 — 계수 두 줄

이 아이디어의 한 문장이 기대는 이름은 **계수 두 줄**입니다. 나머지 수열은 앞 편에서 익숙하지만, 칸마다 수 두
개가 딸려 있다는 모양은 처음이라 한 칸씩 읽는 법부터 잡고 가겠습니다.

##### 쉬운 말 정의

계수 두 줄은 **나머지 수열의 칸마다, 그 칸의 값을 부호를 뗀 두 입력으로 적어 주는 두 수를 적은 줄**입니다.
칸 `k` 의 두 수가 `s_k`, `t_k` 이고, 식으로는 `r_k = A·s_k + B·t_k` 예요. 나머지 수열의 칸이 몇 개이든 두 줄의
칸도 그만큼 있습니다.

##### 전개 입력 위의 모양

전체 컨셉의 그림을 칸마다 값으로 풀면 이렇습니다. 여덟 칸 모두 두 계수로 칸의 값을 계산했어요.

<!--proof:buildRows-->
| 칸 | 나머지 수열 | s 줄 | t 줄 | A·s + B·t |
| --- | ---: | ---: | ---: | --- |
| r₀ | 510 | 1 | 0 | 510 × 1 + 183 × 0 = 510 |
| r₁ | 183 | 0 | 1 | 510 × 0 + 183 × 1 = 183 |
| r₂ | 144 | 1 | -2 | 510 × 1 + 183 × (-2) = 144 |
| r₃ | 39 | -1 | 3 | 510 × (-1) + 183 × 3 = 39 |
| r₄ | 27 | 4 | -11 | 510 × 4 + 183 × (-11) = 27 |
| r₅ | 12 | -5 | 14 | 510 × (-5) + 183 × 14 = 12 |
| r₆ | 3 | 14 | -39 | 510 × 14 + 183 × (-39) = 3 |
| r₇ | 0 | -61 | 170 | 510 × (-61) + 183 × 170 = 0 |

8 칸 가운데 A·s + B·t 가 그 칸의 나머지 수열 값과 같은 칸이 8 개입니다.

<!--/proof-->

마지막 칸 `r₇` 은 값이 0 인데도 계수가 `(-61, 170)` 으로 0 이 아닙니다. 0 을 만드는 조합도 계수가 있다는
뜻이고, 이 쌍은 「알아 두면 좋은 개념」에서 다시 씁니다.

##### 칸 하나를 읽는 법

칸 하나를 골라 이름에서 값까지 따라가 봅시다. `r₄` 를 고르면 두 계수를 두 입력에 곱해 더한 값이 그 칸의 값이고,
코드가 그 칸을 실제로 채운 자리와도 같습니다.

<!--proof:buildRead-->
```text
칸          r₄ — 나머지 수열 값 27
계수        s = 4, t = -11
읽으면      510 × 4 + 183 × (-11) = 2,040 - 2,013 = 27
정본 기록   바퀴 2 가 (144, 39) 를 몫 3 으로 나눠 채운 칸
```

##### 이웃 칸끼리의 관계

칸 `k + 2` 는 바로 앞 두 칸 `k`, `k + 1` 에서 만들어지고, 세 줄 모두 같은 몫 `q` 로 **(앞 칸) − q × (바로 앞
칸)** 을 계산합니다. 그림의 ▲ 두 칸이 읽는 칸이고 강조한 칸이 새 칸이에요.

<!--fig:build-neighbors-->
![칸 r₄ 는 앞 두 칸 r₂ · r₃ 에서 몫 3 으로 — 세 줄 모두 (앞 칸) − 3 × (바로 앞 칸)](./figs/build-neighbors.svg)

<!--proof:buildNeighbor-->
```text
몫            q = ⌊144 / 39⌋ = 3
나머지 수열   144 - 3 × 39 = 27
s 줄          1 - 3 × (-1) = 4
t 줄          -2 - 3 × 3 = -11
```

몫은 나머지 수열의 두 칸에서만 정하고, 두 계수 줄은 그 몫을 받아 쓰기만 합니다. 그래서 계수 두 줄을 더해도
나눗셈이 늘지 않아요.

##### 헷갈리기 쉬운 모양과의 비교

처음 보면 계수를 입력 그대로의 `a`, `b` 로 적는 줄을 떠올리기 쉽습니다. 답이 `a·x + b·y = g` 이니까요. 같은
계수를 두 방식으로 읽어 나란히 놓아 봅시다.

<!--proof:buildSigned-->
| 칸 | 나머지 수열 | 510·s + 183·t | -510·s + 183·t | 입력 그대로 읽은 값의 일치 |
| --- | ---: | ---: | ---: | --- |
| r₀ | 510 | 510 | -510 | 아니요 |
| r₁ | 183 | 183 | 183 | 예 |
| r₂ | 144 | 144 | -876 | 아니요 |
| r₃ | 39 | 39 | 1,059 | 아니요 |
| r₄ | 27 | 27 | -4,053 | 아니요 |
| r₅ | 12 | 12 | 5,112 | 아니요 |
| r₆ | 3 | 3 | -14,277 | 아니요 |
| r₇ | 0 | 0 | 62,220 | 아니요 |

입력 그대로 읽어도 맞는 칸은 8 칸 가운데 r₁ 의 1 칸이고, 모두 s 가 0 이라 a 의 부호가 곱해질 자리가 없는 칸입니다.

<!--/proof-->

계수 두 줄은 **부호를 뗀** 두 수 `A`, `B` 로 적는 줄입니다. 나머지 수열 자체가 부호를 뗀 두 수에서 시작하니,
그 칸을 적는 계수도 같은 두 수에 맞춰야 해요. 입력 그대로의 `a` 로 적은 답은 3단계에서 부호를 붙여 얻습니다.

##### 이렇게 생긴 까닭

새 칸 하나를 만드는 식이 **앞 두 칸**을 쓰기 때문에, 계수도 칸마다 하나씩 따로 있어야 합니다. 한 칸의 계수만
들고 있으면 `(앞 칸) − q × (바로 앞 칸)` 의 앞 칸 몫을 계산할 수 없어요. 그리고 계수가 두 개인 것은 조합이
`A` 쪽과 `B` 쪽 두 수로 이루어지기 때문입니다. 끝으로, 줄의 모든 칸이 `A·s + B·t` 를 지키므로 어느 칸에서
멈추든 그 칸의 계수가 그 칸을 적는 답이에요. 0 앞 칸에서 멈추면 그것이 `g` 의 계수입니다.

#### 1단계 — 첫 두 칸의 계수 정하기

나머지 수열의 첫 두 칸은 부호를 뗀 두 입력 `A`, `B` 입니다. 자기 자신을 두 입력으로 적는 가장 쉬운 방법은
자기 쪽에 1, 다른 쪽에 0 을 곱하는 것이라, 첫 칸의 계수는 `(1, 0)`, 둘째 칸의 계수는 `(0, 1)` 이에요.

<!--proof:stage1Init-->
| 칸 | 나머지 수열 | 계수 (s, t) | A·s + B·t |
| --- | ---: | --- | --- |
| r₀ | 510 | (1, 0) | 510 × 1 + 183 × 0 = 510 |
| r₁ | 183 | (0, 1) | 510 × 0 + 183 × 1 = 183 |

두 칸 모두 식이 맞으니 2단계가 받아 쓸 재료가 갖춰졌습니다. 부호는 이 단계에서 따로 적어 두고, 3단계에서
다시 씁니다.

#### 2단계 — 같은 몫으로 세 줄 이어 쓰기

1단계의 두 칸에서 시작해, 바퀴마다 이웃 두 칸 `(r0, r1)` 을 나눈 몫 `q` 하나로 세 줄에 새 칸을 채웁니다.

$$r_{\text{새}} = r_0 - q\,r_1,\qquad s_{\text{새}} = s_0 - q\,s_1,\qquad t_{\text{새}} = t_0 - q\,t_1$$

새 칸이 식 `r = A·s + B·t` 를 지키는 까닭은 두 식의 차에 있습니다. 앞 칸이 `r0 = A·s0 + B·t0`, 바로 앞 칸이
`r1 = A·s1 + B·t1` 이면, 앞 식에서 뒤 식의 `q` 배를 빼 `r0 − q·r1 = A·(s0 − q·s1) + B·(t0 − q·t1)` 이 됩니다.
왼쪽이 새 나머지이고 오른쪽 괄호 둘이 새 계수예요. 전개 입력의 모든 바퀴에서 새 칸을 확인하면 이렇습니다.

<!--proof:stage2Keep-->
| 바퀴 | 읽은 두 칸 (r0, r1) | 몫 q | 새 칸 r | 새 칸 (s, t) | 새 칸의 A·s + B·t |
| ---: | --- | ---: | ---: | --- | ---: |
| 0 | (510, 183) | 2 | 144 | (1, -2) | 144 |
| 1 | (183, 144) | 1 | 39 | (-1, 3) | 39 |
| 2 | (144, 39) | 3 | 27 | (4, -11) | 27 |
| 3 | (39, 27) | 1 | 12 | (-5, 14) | 12 |
| 4 | (27, 12) | 2 | 3 | (14, -39) | 3 |
| 5 | (12, 3) | 4 | 0 | (-61, 170) | 0 |

6 바퀴 가운데 새 칸의 A·s + B·t 가 새 나머지와 같은 바퀴가 6 개입니다.

<!--/proof-->

쉬운 바퀴는 몫이 1 인 바퀴이고, 불안한 바퀴는 나머지가 0 이 되는 마지막 바퀴입니다. 바퀴 5 는 값이 0 인 칸을
만들었는데도 계수가 `(-61, 170)` 으로 채워졌고, 식 `510 × (-61) + 183 × 170 = 0` 도 그대로 맞았어요. 차를
세우는 논증에 칸의 값이 0 이 아니어야 한다는 조건이 없어서입니다. 칸을 건너뛰는 일도 없습니다. 바퀴 `k` 가
칸 `k`, `k + 1` 을 읽어 칸 `k + 2` 를 채우고, 다음 바퀴는 한 칸 오른쪽의 두 칸을 읽으므로 칸 2 부터 마지막 칸까지
정확히 한 번씩 채워져요.

크기도 여기서 정해집니다. 나머지는 칸마다 줄고, 계수는 반대로 커집니다.

<!--proof:stage2Size-->
| 칸 | 나머지 수열 | \|s\| | \|t\| |
| --- | ---: | ---: | ---: |
| r₀ | 510 | 1 | 0 |
| r₁ | 183 | 0 | 1 |
| r₂ | 144 | 1 | 2 |
| r₃ | 39 | 1 | 3 |
| r₄ | 27 | 4 | 11 |
| r₅ | 12 | 5 | 14 |
| r₆ | 3 | 14 | 39 |
| r₇ | 0 | 61 | 170 |

나머지 수열은 칸마다 줄어 0 에서 끝났고, |s| 와 |t| 는 r₂ 부터 한 번도 줄지 않았습니다. 답으로 읽는 r₆ 의 |s| = 14 는 B / (2g) = 183 / 6 = 30.5 이하이고, |t| = 39 는 A / (2g) = 510 / 6 = 85 이하입니다.

<!--/proof-->

계수가 커지기만 하는데도 답의 계수는 입력의 절반보다 작습니다. 이 상한이 임의의 입력에서 참인지는 「수식
정의와 유도」가 닫아요. 들고 있는 값은 이웃 두 칸의 세 줄, 곧 여섯이고, 새 칸을 채우면 가장 왼쪽 칸은 다시
쓰이지 않으니 모든 칸을 적어 둘 필요가 없습니다.

#### 3단계 — 0 에서 멈추고 부호 붙여 읽기

나머지 수열에 0 이 나오면 멈춥니다. 그 바로 앞 칸의 값이 `g` 이고, 2단계가 모든 칸에서 `r = A·s + B·t` 를
지켰으니 그 칸의 계수가 `g = A·s + B·t` 의 계수예요. 입력은 `a = signA·A`, `b = signB·B` 이므로
`x = signA·s`, `y = signB·t` 로 부호를 붙이면 `a·x + b·y = A·s + B·t = g` 가 됩니다. 한쪽이나 둘 다 0 인
입력도 같은 자리에서 처리돼요.

<!--proof:stage3Stop-->
| 입력 | 나눗셈 | 0 앞 칸 | 그 칸의 (s, t) | 반환 (g, x, y) |
| --- | ---: | --- | --- | --- |
| extendedEuclidean(-510n, 183n) | 6 | r₆ = 3 | (14, -39) | (3, -14, -39) |
| extendedEuclidean(7n, 0n) | 0 | r₀ = 7 | (1, 0) | (7, 1, 0) |
| extendedEuclidean(-7n, 0n) | 0 | r₀ = 7 | (1, 0) | (7, -1, 0) |
| extendedEuclidean(0n, 9n) | 1 | r₁ = 9 | (0, 1) | (9, 0, 1) |
| extendedEuclidean(0n, -9n) | 1 | r₁ = 9 | (0, 1) | (9, 0, -1) |
| extendedEuclidean(0n, 0n) | 0 | r₀ = 0 | (1, 0) | (0, 0, 0) |

둘째 입력이 0 이면 나눗셈을 한 번도 하지 않고 첫 칸에서 멈춥니다. `(0n, 9n)` 은 첫 바퀴의 몫이 0 이라 두 칸이
자리를 바꿔 `r₁ = 9` 에서 멈춰요. 마지막 줄은 계약이 따로 정한 자리입니다. 0 앞 칸의 계수는 `(1, 0)` 인데,
`0·x + 0·y = 0` 은 어떤 계수로도 맞으므로 계약은 셋 다 0 을 내라고 정했어요. 그래서 코드는 `g` 가 0 인 경우를
따로 걸러 `(0, 0, 0)` 을 돌려줍니다. 반드시 멈춘다는 것도 여기서 확인됩니다. 둘째 칸 `r1` 은 바퀴마다
엄격하게 줄어드는 0 이상의 정수라서, 끝없이 줄어들 수 없어요.

| 전제 | 쓰이는 곳 | 없을 때 |
| --- | --- | --- |
| 나머지가 `0 ≤ r < r1` 에 든다 | 2단계에서 칸이 엄격하게 작아지고 3단계에서 반드시 멈춘다 | 나머지가 음수로 나오면 `g` 가 음수로 읽힐 수 있다 |
| 계수 두 줄이 부호를 뗀 두 입력으로 적힌다 | 3단계에서 부호를 계수에만 붙인다 | 부호를 붙일 자리가 어긋나 `a·x + b·y` 가 `g` 가 아니다 |

`bigint` 의 `/` 와 `%` 는 첫째 전제를 스스로 지키지 않습니다. 0 쪽으로 잘라서, 나누어지는 수가 음수이면 나머지도
음수로 나오기 때문이에요.

<!--proof:premiseDiv-->
| x | y | x / y | x % y | 0 ≤ x % y < \|y\| |
| ---: | ---: | ---: | ---: | --- |
| 12 | 5 | 2 | 2 | 예 |
| -12 | 5 | -2 | -2 | 아니요 |
| 12 | -5 | -2 | 2 | 예 |
| -12 | -5 | 2 | -2 | 아니요 |

그래서 코드는 반복에 들어가기 전에 두 입력의 부호를 떼어 따로 적어 둡니다. 두 수가 0 이상이면 나머지도 늘
`0 ≤ r < r1` 에 들어요. 둘째 전제가 깨지는 모습은 「계수 두 줄」의 「헷갈리기 쉬운 모양과의 비교」 표가
보였습니다 — 입력 그대로 읽으면 여덟 칸 가운데 한 칸만 맞았어요.

#### 세 단계를 이은 절차

세 단계를 코드의 순서로 다시 적으면 여섯 걸음이 됩니다. 1 이 1단계, 3 · 4 가 2단계이고 반복 한 바퀴예요.
5 · 6 이 3단계입니다. 계수를 하나씩 대입해 찾으면 `|x|` 만큼이던 일이, 이렇게 하면 `g` 를 구하는 나눗셈
`N` 번 한 벌로 끝납니다.

1. 두 입력의 부호를 `signA` · `signB` 로 적고, `(r0, r1)` 을 두 절댓값, `(s0, s1)` 을 `(1, 0)`,
   `(t0, t1)` 을 `(0, 1)` 로 둔다
2. `r1` 이 0 이 아닌 동안 아래를 되풀이한다
3. `q` 를 `r0` 를 `r1` 로 나눈 몫으로 둔다
4. 세 쌍을 모두 `(둘째, 첫째 − q × 둘째)` 로 옮긴다
5. `r0` 가 0 이면 `(0, 0, 0)` 을 돌려준다
6. `g = r0`, `x = signA·s0`, `y = signB·t0` 를 돌려준다

### 수행으로 알아보는 알고리즘 — 나눗셈 여섯 번으로 -510 과 183 의 베주 계수를 만든다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되, 조각마다 그
조각만 실행해서 나온 값을 확인하고 넘어갑니다.

<!--proof:walkInput-->
```ts
const a = -510n;
const b = 183n;
// 이 절이 끝나면 { g: 3n, x: -14n, y: -39n } 이 나와야 한다
```

왜 하필 이 둘일까요? 첫 인자가 **음수**라 부호를 떼고 다시 붙이는 갈래가 실제로 값을 바꾸고, 몫이
`2 1 3 1 2 4` 로 섞여 있어 몫이 1 인 바퀴와 큰 바퀴가 함께 나오며, 최대공약수가 1 이 아닌 3 이라 계수와 `g`
의 관계까지 함께 확인되기 때문입니다.

```text
extendedEuclidean(a, b):
    부호를 따로 적고 r0 ← |a|, r1 ← |b|                  ① 부호를 떼고 첫 두 칸을 정한다
    (s0, s1) ← (1, 0),  (t0, t1) ← (0, 1)
    r1 이 0 이 아닌 동안:
        q ← r0 를 r1 로 나눈 몫
        (r0, r1) ← (r1, r0 - q·r1)
        (s0, s1) ← (s1, s0 - q·s1)                        ② 몫 하나로 세 줄을 갱신한다
        (t0, t1) ← (t1, t0 - q·t1)
    g ← r0,  x ← signA × s0,  y ← signB × t0               ③ 부호를 다시 붙여 셋을 낸다
```

#### 1. 부호를 떼고 첫 두 칸을 정한다

첫 조각은 준비입니다. 최대공약수는 부호와 상관이 없지만 계수는 부호를 탑니다. 그래서 부호를 따로 적어 두고
절댓값으로 나머지 수열을 시작하며, 계수 두 줄의 첫 두 칸을 1단계대로 둬요.

```ts
const signA = a < 0n ? -1n : 1n; // ① 부호를 떼고 첫 두 칸을 정한다
const signB = b < 0n ? -1n : 1n;
let r0 = a < 0n ? -a : a;
let r1 = b < 0n ? -b : b;
let s0 = 1n;
let s1 = 0n;
let t0 = 0n;
let t1 = 1n;
```

실행하면 이렇게 나옵니다.

<!--proof:walkInit-->
```text
T1 이 끝난 시점 — a = -510, b = 183
  signA · signB   -1 · 1
  (r0, r1)        (510, 183)
  (s0, s1)        (1, 0)
  (t0, t1)        (0, 1)
```

`r0` 에 붙는 계수가 `(s0, t0)`, `r1` 에 붙는 계수가 `(s1, t1)` 입니다. 변수 이름의 0 과 1 이 이웃 두 칸 가운데
앞 칸과 뒤 칸을 가리켜요.

#### 2. 몫 하나로 세 줄을 함께 갱신한다

둘째 조각은 반복문입니다. 바퀴 하나가 세 줄에 새 칸을 하나씩 더해요 — 몫을 한 번 구하고, 그 값을 세 쌍에 모두
씁니다.

```ts
while (r1 !== 0n) {
  const q = r0 / r1;
  [r0, r1] = [r1, r0 - q * r1];
  [s0, s1] = [s1, s0 - q * s1]; // ② 몫 하나로 세 줄을 갱신한다
  [t0, t1] = [t1, t0 - q * t1];
}
```

앞 두 바퀴만 실행하면 이렇게 나옵니다.

<!--proof:walkLoopHead-->
| 걸음 | q | r0 = q·r1 + 나머지 | 바퀴 끝 (r0, r1) | 바퀴 끝 (s0, s1) | 바퀴 끝 (t0, t1) | 새 칸의 A·s + B·t |
| --- | ---: | --- | --- | --- | --- | --- |
| T2 | 2 | 510 = 2 × 183 + 144 | (183, 144) | (0, 1) | (1, -2) | 510 × 1 + 183 × (-2) = 144 |
| T3 | 1 | 183 = 1 × 144 + 39 | (144, 39) | (1, -1) | (-2, 3) | 510 × (-1) + 183 × 3 = 39 |

여기서 가장 중요한 줄은 세 줄의 대입이 **같은 모양**이라는 것입니다. 오른쪽이 글자 하나(`r` · `s` · `t`)만
다르고, 세 쌍 모두 옛 뒤 칸이 앞 칸 자리로 가고 새 칸이 뒤 칸 자리를 채워요. 그래서 바퀴가 끝날 때마다 세
쌍이 늘 같은 두 칸을 가리킵니다.

#### 짚고 가기 — 계수를 한 줄씩 대입해도 될 것 같다

여기서 헷갈리기 쉬운 포인트는 `[s0, s1] = [s1, s0 - q * s1]` 가 두 값을 **동시에** 바꾸는 문장이라는 것입니다.
익숙한 모양으로 두 문장으로 나누고 싶어져요. 그 생각대로 `s` 쪽만 풀어 써 봅시다.

```ts
s0 = s1;
s1 = s0 - q * s1; // ← s0 가 이미 새 값이라 옛 s0 가 사라졌다
```

이 코드는 예외를 내지 않습니다. 네 입력에 실행하면 이렇게 나와요.

<!--proof:mutant-alias-->
| 입력 | 정본 (g, x, y) | 한 줄씩 대입한 판 (g, x, y) | a·x + b·y | 판정 |
| --- | --- | --- | ---: | --- |
| 전개 입력 -510 과 183 | (3, -14, -39) | (3, 0, -39) | -7,137 | 틀리다 |
| 서로소인 17 과 5 | (1, -2, 7) | (1, 0, 7) | 35 | 틀리다 |
| 한쪽이 0 인 7 과 0 | (7, 1, 0) | (7, 1, 0) | 7 | 같다 |
| 둘 다 0 | (0, 0, 0) | (0, 0, 0) | 0 | 같다 |

g 는 네 줄 모두 두 판에서 값이 하나입니다. 나머지 수열을 만드는 줄은 손대지 않았기 때문입니다.

<!--/proof-->

**아래 두 줄에서는 답이 안 틀립니다.** 둘째 입력이 0 이라 반복이 한 번도 실행되지 않아 바꾼 줄을 지나지
않았어요. 그래서 0 이 든 입력만 시험하면 이 자리를 모르고 넘어갑니다. 반복이 실행되면 `x` 가 0 으로 나오고,
`g` 는 맞는데 `a·x + b·y` 가 `g` 가 아닌 값이 돼요. 전개 입력에서 `s` 가 어떻게 되는지
따라가 보면 첫 바퀴에서 이미 옛 값이 사라집니다.

<!--proof:aliasTrace-->
```text
extendedEuclidean(-510n, 183n) 에서 s 를 한 줄씩 대입하면
  q = 2   s0 ← s1 = 0   s1 ← s0 - 2 × s1 = 0 - 2 × 0 = 0   (1, 0) → (0, 0)
  q = 1   s0 ← s1 = 0   s1 ← s0 - 1 × s1 = 0 - 1 × 0 = 0   (0, 0) → (0, 0)
  둘째 문장의 s0 는 이미 옛 s1 이라, 두 값이 0 에 머문다
```

둘째 문장이 읽는 `s0` 는 첫 문장이 덮어쓴 값이라, 옛 `s0` 인 1 이 계산에 한 번도 들어가지 못합니다. 두 문장으로
나누려면 옛 값을 임시 변수에 먼저 적어 두어야 하고, 정본은 한 줄 대입으로 그 일을 대신해요.

#### 3. 나머지가 0 이 되면 부호를 붙여 돌려준다

마지막 조각은 반환입니다. 반복이 끝나는 것은 `r1` 이 0 이 된 순간이고, 그때 `r0` 가 `g` 이며 `(s0, t0)` 가
그 칸의 계수예요. 둘 다 0 인 입력만 계약대로 따로 거릅니다.

```ts
if (r0 === 0n) return { g: 0n, x: 0n, y: 0n };
return { g: r0, x: signA * s0, y: signB * t0 }; // ③ 부호를 다시 붙여 셋을 낸다
```

전개 입력에서는 T7 의 나머지가 0 이라 T8 에서 반복 조건이 거짓이 되고, 그때 `r0` 가 3, `(s0, t0)` 가
`(14, -39)` 입니다. 조각 셋을 이어 끝까지 실행한 모습은 다음 걸음에서 봅니다.

#### 짚고 가기 — y 는 마지막에 나눗셈 한 번으로 되찾아도 될 것 같다

여기서 헷갈리기 쉬운 포인트는 계수 두 줄을 다 갱신하는 것이 낭비로 보인다는 것입니다. `a·x + b·y = g` 에서
`x` 만 있으면 `y = (g − a·x) / b` 로 나오니까, `t` 쪽 세 줄을 지우고 마지막에 나눗셈 한 번만 하면 될 것
같아요.

```ts
// t0, t1 을 아예 두지 않고
const y = (g - a * x) / b; // ← b 가 0 이면 여기서 0 으로 나눈다
```

**이 판은 `b` 가 0 이 아닌 입력에서는 정본과 같은 값을 냅니다.** `b ≠ 0` 이면 `y` 가 식 하나로 정해지기
때문이에요. 네 입력에 실행하면 이렇게 나옵니다.

<!--proof:halfTrack-->
| 입력 | 정본 (g, x, y) | y 를 나중에 구하는 판 |
| --- | --- | --- |
| 전개 입력 -510 과 183 | (3, -14, -39) | (3, -14, -39) |
| 서로소인 17 과 5 | (1, -2, 7) | (1, -2, 7) |
| 한쪽이 0 인 7 과 0 | (7, 1, 0) | 0 으로 나눈다는 예외 |
| 둘 다 0 | (0, 0, 0) | (0, 0, 0) |

셋째 줄이 그 자리입니다. 계약이 `b = 0` 을 허용하고 그때 `g = |a|`, `y = 0` 을 내라고 정했는데, 이 판은 그
자리에서 `0n` 으로 나누다 예외를 냅니다. 넷째 줄은 둘 다 0 이라 나눗셈 전에 돌아가서 무사했어요. `b = 0` 을
따로 거르면 고칠 수 있지만 그러면 갈래가 하나 늘고, `t` 쪽 줄을 그냥 두면 `b = 0` 일 때 `t0 = 0` 이 그대로
답이라 갈래가 늘지 않습니다. 나눗셈 한 번을 아끼려고 경계 하나를 떠안는 교환이에요.

#### 4. 여덟 걸음을 처음부터 끝까지 본다

세 조각을 이어 고정 입력에 실행하면 여덟 걸음이 나옵니다. T1 은 반복문 앞, T2 부터 T7 까지가 바퀴 여섯,
T8 이 반환이에요. 무대의 칸 `k` 가 나머지 수열의 `r_k` 이고, 그 아래 두 줄이 그 칸의 계수입니다. 괄호
`(r0, r1)` 이 바퀴를 시작할 때의 이웃 두 칸, ▲ 가 이번에 읽은 두 칸, 새로 채운 칸이 이번 나머지와 그 두
계수예요. 값 줄 곁말은 채운 칸 가운데 `510·s + 183·t = r` 이 맞는 칸의 수입니다.

T8 에서 `r0 === 0n` 은 거짓입니다. `r0` 가 3 이기 때문이고, 이 조건이 참이 되는 입력은 두 인자가 모두 0 인
경우뿐이에요. **세 갈래가 모두 실행됐습니다.** 라벨마다 어느 걸음에서 실행됐는지 모으면 이렇습니다.

<!--proof:walkBranches-->
| 라벨 | 하는 일 | 전개에서 |
| --- | --- | --- |
| ① | 부호를 따로 적고 첫 두 칸을 정한다 | T1 에서 한 번 |
| ② | 몫 하나로 세 줄을 갱신한다 | T2 · T3 · T4 · T5 · T6 · T7 에서 6 번 · T8 에서 조건이 거짓 |
| ③ | 부호를 다시 붙여 셋을 낸다 | T8 에서 한 번 |

무대의 곁말은 여덟 걸음 내내 채운 칸 전부가 맞았다고 적습니다. 칸은 걸음마다 하나씩 늘었는데 식
`510·s + 183·t = r` 은 한 칸에서도 어긋나지 않았고, T8 에서 읽은 칸 `r₆` 의 계수가 답이에요. T7 이 채운 0 의
칸은 반복을 끝내는 표지이고, 답은 그 왼쪽 칸에 있습니다.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 없어요 — 조각 셋을 순서대로 이어 붙인 것이
전부입니다.

```ts
export function extendedEuclidean(
  a: bigint,
  b: bigint,
): { g: bigint; x: bigint; y: bigint } {
  // ① 부호를 따로 적어 두고 절댓값으로 시작한다. 계수 두 벌의 처음 값도 여기서 정한다.
  const signA = a < 0n ? -1n : 1n;
  const signB = b < 0n ? -1n : 1n;
  let r0 = a < 0n ? -a : a;
  let r1 = b < 0n ? -b : b;
  let s0 = 1n;
  let s1 = 0n;
  let t0 = 0n;
  let t1 = 1n;

  // ② 나머지를 만든 몫 q 로 계수 두 벌을 같은 식으로 갱신한다.
  while (r1 !== 0n) {
    const q = r0 / r1;
    [r0, r1] = [r1, r0 - q * r1];
    [s0, s1] = [s1, s0 - q * s1];
    [t0, t1] = [t1, t0 - q * t1];
  }

  // ③ r1 이 0 이 된 순간의 r0 가 g 다. 절댓값으로 계산했으므로 계수에 부호를 다시 붙인다.
  if (r0 === 0n) return { g: 0n, x: 0n, y: 0n };
  return { g: r0, x: signA * s0, y: signB * t0 };
}
```

<!--proof:finalCalls-->
```text
extendedEuclidean(-510n, 183n)   → { g: 3n, x: -14n, y: -39n }   a·x + b·y = 3
extendedEuclidean(30n, 18n)      → { g: 6n, x: -1n, y: 2n }      a·x + b·y = 6
extendedEuclidean(17n, 5n)       → { g: 1n, x: -2n, y: 7n }      a·x + b·y = 1
extendedEuclidean(3n, 11n)       → { g: 1n, x: 4n, y: -1n }      a·x + b·y = 1
extendedEuclidean(0n, 9n)        → { g: 9n, x: 0n, y: 1n }       a·x + b·y = 9
extendedEuclidean(0n, 0n)        → { g: 0n, x: 0n, y: 0n }       a·x + b·y = 0
```

### 알아 두면 좋은 개념 — 일차 디오판토스 방정식

전개의 T8 에서 반복이 끝날 때 계수 두 줄에는 칸이 하나 더 있었습니다. 답으로 쓴 것은 `r₆` 의 계수
`(14, -39)` 이고, 0 의 칸 `r₇` 의 계수는 쓰지 않았어요. 그 버린 쌍을 읽으면 이렇습니다.

<!--proof:relatedLast-->
```text
r₇ 의 계수   s = -61, t = 170
|s|          61 = 183 / 3 = B / g
|t|          170 = 510 / 3 = A / g
A·s + B·t    510 × (-61) + 183 × 170 = 0
```

0 을 만드는 조합이라, 답에 이 쌍을 몇 번 더해도 식이 그대로 남습니다. 그래서 `a·x + b·y = g` 의 해는 하나가
아니에요. 미지수가 정수여야 하는 방정식을 **디오판토스 방정식**이라 하고, `a·x + b·y = c` 꼴이 그중 **일차**
디오판토스 방정식입니다. 이 방정식은 `g` 가 `c` 를 나눌 때만 해가 있고, 해가 있으면 무한히 많아요.

<!--proof:generalSolution-->
| k | x = -14 + 61k | y = -39 + 170k | a·x + b·y |
| ---: | ---: | ---: | ---: |
| -1 | -75 | -209 | 3 |
| 0 | -14 | -39 | 3 |
| 1 | 47 | 131 | 3 |
| 2 | 108 | 301 | 3 |

네 줄 모두 a·x + b·y 가 3 입니다. x 는 61 씩, y 는 170 씩 옮겨 갑니다.

<!--/proof-->

이 글의 값과 일차 디오판토스 방정식의 이름을 나란히 놓으면 이렇습니다.

| 이 글의 것 | 일차 디오판토스 방정식의 이름 |
| --- | --- |
| 반환하는 `(x, y)` | `a·x + b·y = g` 의 한 해 |
| 0 의 칸의 계수 `(s, t)` | 해와 해 사이의 간격, 곧 `a·x + b·y = 0` 의 기본 해 |
| `g` 가 `c` 를 나누는가 | `a·x + b·y = c` 에 해가 있는지의 판정 |
| `g = 1` 인 경우 | `a·x ≡ 1 (mod b)` 의 해, 곧 모듈러 역원 |

같은 이름을 다시 만나는 자리가 셋 있습니다. [중국인의 나머지 정리](../crt/crt-guide.md)에서 두 합동식을
합칠 때, 두 종류의 단위로 정확히 만들 수 있는 양을 셀 때, 그리고 격자에서 `a·x + b·y = c` 위의 정수점을 셀
때예요. 셋 다 「해가 있는가」와 「간격이 얼마인가」 둘만 있으면 풀립니다.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 과제에 이것을 쓰는지, 계수가 임의의 입력에서 얼마나 커지는지, 무엇이
매 바퀴 참으로 남는지, 그리고 나눗셈이 몇 번인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

네 조건이 함께 맞을 때입니다. 조건마다 그 조건이 코드의 어느 모양으로 나타나는지 함께 적었어요.

| 조건 | 풀어 쓴 뜻 | 코드에 나타나는 모양 |
| --- | --- | --- |
| 최대공약수와 함께 그것을 만드는 계수가 필요하다 | `g` 만 필요하면 계수 두 줄이 하는 일이 없다 | 계수 네 칸의 처음 값과 갱신 두 줄 |
| 법이 소수가 아닐 수 있다 | 역원을 거듭제곱으로 구하려면 법이 소수여야 하고, 이 방법은 서로소이기만 하면 된다 | 반환한 `g` 가 1 인지로 역원이 있는지까지 알려 준다 |
| 수가 크다 | 나눗셈 횟수가 값이 아니라 자릿수를 따른다 | 바퀴 수가 유클리드 호제법과 같다 |
| 부호와 0 을 따로 거르지 않아도 된다 | 음수와 0 이 섞여 들어오는 입력이다 | 부호를 적는 두 줄 · 절댓값 두 줄 · 마지막 두 줄이 흡수한다 |

반대로 이 방법이 잘 맞지 않는 모양은 이렇습니다.

| 모양 | 더 맞는 것 |
| --- | --- |
| `g` 만 필요하다 | [유클리드 호제법](../gcd/gcd-guide.md) — 계수를 위한 칸이 없다 |
| 법이 고정된 소수이고 역원만 필요하다 | [이진 거듭제곱](../fastPower/fastPower-guide.md)으로 `a^(p−2)` 를 구한다. 분기가 입력 값에 기대지 않아 고정 시간 구현이 쉽다 |
| 수가 셋 이상이다 | 둘씩 접는다. 계수는 접을 때마다 다시 합성해야 한다 |

셋째 줄이 이 방법의 한계입니다. 세 수의 최대공약수를 한 번에 만드는 계수 셋을 직접 내지는 않아요.

#### 문제에서 이것을 떠올리게 하는 단서

- 「`a·x + b·y = c` 를 만족하는 **정수** `x`, `y`」 — 일차 디오판토스 방정식의 표준 문형입니다.
- 「`a` 의 `mod m` **역원**」 — `a·x + m·y = 1` 의 `x` 가 그 역원이고, `m` 이 소수가 아니어도 됩니다.
- 「나머지 조건 두 개를 **동시에** 만족하는 수」 — 중국인의 나머지 정리이고, 두 합동식을 합칠 때 이 방법의
  계수를 씁니다.
- 「두 종류의 단위로 **정확히** 만들 수 있는 가장 작은 양과 그 조합」 — `g` 가 그 가장 작은 양이고 `(x, y)` 가
  조합입니다.
- 「분수 `p/q` 를 분모가 작은 분수로 근사」 — 계수 두 줄의 칸이 근사 분수의 분자와 분모를 줍니다.

반대로 아래 신호는 이 방법의 자리가 아니라는 뜻입니다.

| 신호 | 필요한 것 |
| --- | --- |
| 「최대공약수만 구하라」 | 유클리드 호제법. 계수를 만들 이유가 없다 |
| 「`a^k mod m` 을 구하라」 | 지수를 반으로 줄여 가는 이진 거듭제곱 |
| 「소인수분해하라」 | 계수는 소인수를 알려 주지 않는다 |

#### 실제로 쓰이는 곳

- **Go 표준 라이브러리** — `math/big` 의 `(*Int).GCD` 가 이 글의 과제와 **같은 계약**을 씁니다.
  공식 문서가 *"GCD sets z to the greatest common divisor of a and b and returns z. If x or
  y are not nil, GCD sets their value such that z = a*x + b*y."* 라고 적고, 0 이 들어오는
  경우까지 정해 둡니다 — *"If a == b == 0, GCD sets z = x = y = 0."* ·
  *"If a == 0 and b != 0, GCD sets z = |b|, x = 0, y = sign(b) * 1."* ·
  *"If a != 0 and b == 0, GCD sets z = |a|, x = sign(a) * 1, y = 0."*
  ([공식 문서](https://pkg.go.dev/math/big#Int.GCD), 조회일 2026-09-03)
- **Java 표준 라이브러리** — `BigInteger.modInverse` 가 이 방법이 푸는 과제의 대표적인 소비자입니다.
  공식 문서가 *"Returns a BigInteger whose value is (this^-1 mod m)."* 로 적고, 던지는 조건을
  *"m ≤ 0, or this BigInteger has no multiplicative inverse mod m (that is, this BigInteger
  is not relatively prime to m)."* 로 밝혀요 — 「서로소일 때만 역원이 있다」가 그대로입니다.
  ([공식 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/math/BigInteger.html), 조회일 2026-09-03)

두 문서에서 확인한 것을 같은 기준으로 놓으면 이렇습니다.

| 기준 | 이 글 | Go `(*Int).GCD` | Java `BigInteger.modInverse` |
| --- | --- | --- | --- |
| 돌려주는 것 | `g` 와 `a·x + b·y = g` 의 `x`, `y` | `z` 와 `z = a*x + b*y` 의 `x`, `y` | `this^-1 mod m` |
| 둘 다 0 | `g = x = y = 0` | `z = x = y = 0` | — |
| 한쪽이 0 | 다른 쪽의 절댓값과 그 부호 | 다른 쪽의 절댓값과 그 부호 | — |
| 서로소가 아닐 때 | `g` 가 1 보다 크다 | — | 예외를 던진다 |
| 안에서 쓰는 절차 | 확장 유클리드 호제법 | 이 글이 확인하지 못했다 | 이 글이 확인하지 못했다 |

**이 글의 계약이 Go 의 계약과 같다는 것**이 이 절의 값입니다. 0 과 부호를 다루는 방식이 관례로 굳어 있고,
이 글의 코드 첫 네 줄과 마지막 두 줄이 그 관례를 그대로 지킵니다.

#### 경쟁 설계와의 대조

경쟁 설계는 **최소 절댓값 나머지 판**입니다. 몫을 내림 대신 **반올림**해서, 나머지의 절댓값을 나누는 수의 절반
이하로 잡아요. 나머지가 음수가 될 수 있어서 나머지 수열 자체가 정본과 다릅니다. 두 판이 한 바퀴에서 하는
일이 이렇게 갈립니다.

| 판 | 몫 | 나머지 | 한 바퀴에 붙는 일 |
| --- | --- | --- | --- |
| 나머지 판(이 글) | `⌊r0 / r1⌋` | 0 이상 `r1` 미만 | 나눗셈 · 곱셈 셋 · 뺄셈 셋 · 대입 여섯 · 판정 하나 |
| 중심 판 | `r0 / r1` 을 반올림 | 절댓값이 `r1` 의 절반 이하 | 위에 더해 절댓값 · 절반 비교, 몫을 옮기는 바퀴에는 보정 넷 |

중심 판은 바퀴마다 값이 적어도 절반으로 줄어 바퀴 수가 정본 이하입니다. 대신 바퀴마다 할 일이 늘어요. 그래서
이 절만 기준을 둘로 가릅니다. 나눗셈 횟수(= 바퀴 수, 표의 「나눗셈」)만 세면 바퀴마다 늘어난 일이 안 보이기
때문이에요. 벤치 하네스(`extendedEuclidean-guide.alt.ts`)가 나눗셈·곱셈·뺄셈·덧셈·비교·대입·절댓값을 각각
하나로 센 **기본 연산**과 **나눗셈**을 함께 냅니다.

입력은 전개 입력을 그대로 두고 몫의 모양이 다른 셋을 더했습니다. 두 판이 갈리는 자리가 몫의 모양인데 전개 입력의
몫은 `2 1 3 1 2 4` 로 섞여 있어 치우친 자리가 안 보여요. 그래서 몫이 마지막만 빼고 전부 1 인 피보나치 이웃
`F(91)` · `F(90)`, 몫이 전부 2 인 펠 수열 이웃 `P(49)` · `P(48)`, 몫이 섞이고 값이 큰 `1,000,000,007` ·
`998,244,353` 을 더합니다. 앞의 두 쌍은 19 자리라 과제 규모 `10^18` 을 조금 넘지만, 두 판이 갈리는 모습은 몫의
모양에서 나오므로 그대로 둡니다. 넷 다 `.alt.ts` 에 적힌 상수라 몇 번을 실행해도 같은 값이 나와요.

<!--proof:alt-counts-->
| 입력 | 나머지 판 나눗셈 | 중심 판 나눗셈 | 나머지 판 기본 연산 | 중심 판 기본 연산 | 기본 연산이 적은 쪽 |
| --- | ---: | ---: | ---: | ---: | --- |
| 전개 입력 | 6 | 4 | 85 | 78 | 중심 판 |
| 피보나치 이웃 | 89 | 45 | 1,247 | 943 | 중심 판 |
| 펠 수열 이웃 | 49 | 49 | 687 | 835 | 나머지 판 |
| 큰 소수 쌍 | 9 | 8 | 127 | 142 | 나머지 판 |

계수의 절댓값은 네 입력 모두 두 판에서 하나로 나왔습니다.

<!--/proof-->

**위 두 줄과 아래 두 줄에서 순서가 뒤집힙니다.** 나눗셈은 네 줄 다 중심 판이 적거나 같은데, 기본 연산은 위
둘에서 중심 판이 적고 아래 둘에서 나머지 판이 적어요. 뒤집히는 조건을 값으로 풀기 위해, 두 판의 기본 연산을
나눗셈 횟수로 적어 봅시다. 나머지 판은 바퀴마다 14 연산에 끝의 판정 하나라 `14N + 1` 이고, 중심 판은 바퀴마다
17 연산에 몫을 옮긴 바퀴 `J` 개마다 4 연산이 붙고 끝에 판정과 부호 보정이 하나씩이라 `17M + 4J + 2` 예요.

<!--proof:altFormula-->
| 입력 | 나머지 판 나눗셈 N | 중심 판 나눗셈 M | M / N | 몫을 옮긴 바퀴 J | 14N + 1 | 17M + 4J + 2 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 전개 입력 | 6 | 4 | 0.67 | 2 | 85 | 78 |
| 피보나치 이웃 | 89 | 45 | 0.51 | 44 | 1,247 | 943 |
| 펠 수열 이웃 | 49 | 49 | 1.00 | 0 | 687 | 835 |
| 큰 소수 쌍 | 9 | 8 | 0.89 | 1 | 127 | 142 |

네 줄 모두 두 식이 벤치의 기본 연산과 같습니다. 중심 판이 적은 줄의 M / N 은 0.67 · 0.51 이고, 나머지 판이 적은 줄의 M / N 은 1.00 · 0.89 입니다.

<!--/proof-->

**우열이 반대가 되는 조건은 나눗셈이 얼마나 줄어드는가입니다.** 중심 판은 바퀴 하나가 나머지 판보다 3 연산 이상
무거우니, 나눗셈이 충분히 줄어야 합이 적어져요. 몫이 거의 다 1 인 피보나치 이웃은 나눗셈이 크게
줄어 중심 판이 적고, 몫이 이미 전부 2 인 펠 수열 이웃은 나머지가 처음부터 절반 이하라 나눗셈이 하나도 안
줄어 늘어난 판정만 남습니다. 표 아래 문장이 두 무리의 `M / N` 을 모았어요.

**이 방법이 내주는 것은 나눗셈 횟수입니다.** 네 입력에서 한 번도 중심 판보다 적지 않았고, 몫이 거의 다 1 인
입력에서는 위 표의 M / N 만큼 벌어져요. 얻는 것은 **바퀴마다의 단순함과 부호**입니다. 나머지가 언제나 0 이상이라
마지막에 `g` 의 부호를 맞추는 자리가 없고, 반올림 판정과 보정이 통째로 빠집니다. 계수의 절댓값은 네 입력에서
두 판이 같았으므로 그 기준에서는 갈리지 않아요.

### 수식 정의와 유도

파트 1 이 값으로 보인 것은 「전개 입력에서 답의 `|s|` 가 14 이고 `B / (2g)` 가 30.5」입니다. **임의의
입력에서 계수가 얼마나 커지는가**는 값으로 못 얻어요. 여기서 닫힌 형태로 냅니다. 입력은 `A > B ≥ 1` 이라고
둡니다. 이 절이 쓰는 기호는 이렇습니다.

| 기호 | 정의 |
| --- | --- |
| $r_i$ | 나머지 수열의 $i$ 번째 칸. $r_0 = A$, $r_1 = B$ |
| $q_i$ | $r_{i-1}$ 을 $r_i$ 로 나눈 몫 |
| $s_i, t_i$ | 계수 두 줄의 $i$ 번째 칸 |
| $N$ | $r_{N+1} = 0$ 이 되는 첫 지표. 나눗셈 횟수다 |
| $g$ | $r_N$, 곧 최대공약수 |
| $D_i$ | $s_i\,t_{i+1} - s_{i+1}\,t_i$ |

나머지 수열부터 정의합니다.

$$r_0 = A,\quad r_1 = B,\qquad q_i = \left\lfloor \frac{r_{i-1}}{r_i} \right\rfloor,\qquad r_{i+1} = r_{i-1} - q_i\, r_i$$

$i = 1$ 에 넣어 계산하면 이렇습니다.

<!--proof:mathQ1-->
```text
q_1 = ⌊510 / 183⌋ = 2
r_2 = r_0 - q_1 · r_1 = 510 - 2 × 183 = 144
```

계수 두 줄은 **같은 점화식**을 쓰고 처음 값만 다릅니다.

$$s_0 = 1,\ s_1 = 0,\qquad s_{i+1} = s_{i-1} - q_i\, s_i \qquad\qquad t_0 = 0,\ t_1 = 1,\qquad t_{i+1} = t_{i-1} - q_i\, t_i$$

```ts
// 위 세 점화식을 그대로 옮긴 조각. 세 줄의 오른쪽이 글자 하나만 다르다.
const q = r0 / r1;
[r0, r1] = [r1, r0 - q * r1];
[s0, s1] = [s1, s0 - q * s1];
[t0, t1] = [t1, t0 - q * t1];
```

**정의를 값에 넣어 검산해 봅시다.** 전개 입력의 절댓값 `A = 510`, `B = 183` 이고 `N = 6` 입니다.

<!--proof:mathCheck-->
| i | r_i | s_i | t_i | A·s_i + B·t_i | D_i |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 0 | 510 | 1 | 0 | 510 | 1 |
| 1 | 183 | 0 | 1 | 183 | -1 |
| 2 | 144 | 1 | -2 | 144 | 1 |
| 3 | 39 | -1 | 3 | 39 | -1 |
| 4 | 27 | 4 | -11 | 27 | 1 |
| 5 | 12 | -5 | 14 | 12 | -1 |
| 6 | 3 | 14 | -39 | 3 | 1 |
| 7 | 0 | -61 | 170 | 0 | — |

A = 510, B = 183 입니다. 8 줄 모두 A·s_i + B·t_i 가 r_i 와 같은가: 예. D_i 가 i 가 짝수면 1, 홀수면 -1 인가: 예.

<!--/proof-->

다섯째 칸이 말하는 것을 식으로 적으면 다음과 같고, 귀납으로 확인됩니다.

$$A\,s_i + B\,t_i = r_i \qquad (0 \le i \le N+1)$$

기저 둘은 처음 값에서 바로 나옵니다.

<!--proof:mathBase-->
```text
i = 0   510 × 1 + 183 × 0 = 510 = r_0 인가: 예
i = 1   510 × 0 + 183 × 1 = 183 = r_1 인가: 예
```

단계는 $i - 1$ 과 $i$ 에서 식이 성립한다고 두고 $i + 1$ 로 가는 것입니다. 점화식을 넣고 $A$ 가 든 항과 $B$ 가 든
항을 앞의 두 칸끼리 다시 묶으면, 괄호 둘이 각각 가정한 식의 왼쪽이 돼요.

$$A\,s_{i+1} + B\,t_{i+1} = A(s_{i-1} - q_i s_i) + B(t_{i-1} - q_i t_i) = (A s_{i-1} + B t_{i-1}) - q_i (A s_i + B t_i) = r_{i-1} - q_i r_i = r_{i+1}$$

$i = 1$ 에서 이 변형을 값으로 확인하면 이렇습니다.

<!--proof:mathStep-->
```text
A·s_2 + B·t_2 = (A·s_0 + B·t_0) - q_1 × (A·s_1 + B·t_1)
              = 510 - 2 × 183
              = 144 = r_2 인가: 예
```

여섯째 칸 $D_i$ 도 같은 방법으로 닫힙니다. 기저는 $D_0 = s_0 t_1 - s_1 t_0 = 1 \cdot 1 - 0 \cdot 0 = 1$ 입니다.
단계는 $D_{i+1}$ 을 정의대로 편 다음 $s_{i+2}$ 와 $t_{i+2}$ 에 점화식을 넣는 것이고, 그러면 $q_{i+1}$ 이 든 두
항이 부호만 달라 서로 지워져 $D_{i+1} = -D_i$ 가 됩니다. 기저가 1 이고 한 칸마다 부호가 바뀌니 $D_i = (-1)^i$ 이고,
검산 표의 여섯째 칸이 그 값이었어요.

$$\begin{aligned} D_{i+1} &= s_{i+1}\,t_{i+2} - s_{i+2}\,t_{i+1} \\ &= s_{i+1}\,(t_i - q_{i+1} t_{i+1}) - (s_i - q_{i+1} s_{i+1})\,t_{i+1} \\ &= s_{i+1} t_i - q_{i+1} s_{i+1} t_{i+1} - s_i t_{i+1} + q_{i+1} s_{i+1} t_{i+1} \\ &= -(s_i\,t_{i+1} - s_{i+1}\,t_i) = -D_i \end{aligned}$$

이제 **계수의 상한**을 냅니다. 먼저 0 의 칸의 계수부터 정해요. $r_{N+1} = 0$ 이므로 $A s_{N+1} + B t_{N+1} = 0$
이고, 양변을 $g$ 로 나누면 $(A/g)\,s_{N+1} = -(B/g)\,t_{N+1}$ 입니다. $A/g$ 와 $B/g$ 는 서로소라서 $B/g$ 가
$s_{N+1}$ 을 나누고, $s_{N+1} = k\,(B/g)$ 로 두면 $t_{N+1} = -k\,(A/g)$ 예요. 그러면 $k$ 는 $s_{N+1}$ 과
$t_{N+1}$ 을 둘 다 나눕니다. 한편 $D_N = s_N t_{N+1} - s_{N+1} t_N = \pm 1$ 이라, 두 수를 함께 나누는 수는
$\pm 1$ 을 나눠야 해요. 그래서 $|k| = 1$ 이고, 남는 것은 하나뿐입니다.

$$|s_{N+1}| = \frac{B}{g}, \qquad |t_{N+1}| = \frac{A}{g}$$

<!--proof:mathLast-->
```text
|s_7| = 61    B / g = 183 / 3 = 61    같은가: 예
|t_7| = 170   A / g = 510 / 3 = 170   같은가: 예
```

다음은 두 가지입니다. 첫째, $|s_{i+1}| = |s_{i-1}| + q_i\,|s_i|$ 입니다. $i = 1$ 에서는 $s_1 = 0$ 이라
$s_2 = s_0 = 1$ 로 곧바로 맞아요. $i \ge 2$ 에서는 $s_{i-1}$ 과 $s_i$ 의 부호가 반대입니다 — $s_2 = 1$ 이고
$s_3 = s_1 - q_2 s_2 = -q_2$ 가 음수라 처음 두 칸의 부호가 반대이고, 부호가 반대인 두 칸 뒤의
$s_{i+1} = s_{i-1} - q_i s_i$ 는 $-q_i s_i$ 가 $s_{i-1}$ 과 같은 부호라 두 항의 절댓값이 더해지며 $s_{i-1}$ 의
부호를 받으므로, 다음 쌍 $s_i$ · $s_{i+1}$ 도 부호가 반대예요. $A > B$ 라 모든 몫이 1 이상이니, 이 식에서 $|s_i|$
는 $i \ge 1$ 에서 줄지 않습니다. 둘째, **마지막 몫은 2 이상**입니다 — $r_{N-1} = q_N r_N$ 인데
$r_{N-1} > r_N$ 이므로 $q_N = 1$ 일 수 없어요. 둘을 이으면 상한이 나옵니다.

$$|s_{N+1}| = |s_{N-1}| + q_N |s_N| \;\ge\; q_N |s_N| \;\ge\; 2|s_N| \quad\Longrightarrow\quad |x| = |s_N| \le \frac{B}{2g}, \qquad |y| = |t_N| \le \frac{A}{2g}$$

$t$ 쪽도 같은 논증입니다. 부호가 $t_1 = 1$, $t_2 = -q_1$ 에서 반대로 시작하고 점화식이 같아요. 전개 입력의
마지막 바퀴에서 확인하면 이렇습니다.

<!--proof:mathLastStep-->
```text
q_6     4 ≥ 2 인가: 예
|s_7|   61 = |s_5| + q_6 × |s_6| = 5 + 4 × 14 인가: 예
|s_6|   14 ≤ |s_7| / 2 = 30.5 인가: 예
```

**계수를 냅니다.** 과제 규모와 그보다 큰 입력에서 계수가 몇 자리가 되는지를 실제로 재면 이렇게 나와요. 마지막
줄은 암호에서 흔히 쓰는 2,048 비트 법(십진 617 자리) 규모입니다.

<!--proof:coefBound-->
| A 와 B | A 자릿수 | g | \|x\| | ⌊B / (2g)⌋ | \|y\| | ⌊A / (2g)⌋ |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 510 과 183 | 3 | 3 | 14 | 30 | 39 | 85 |
| 6,765 과 4,181 | 4 | 1 | 1,597 | 2,090 | 2,584 | 3,382 |
| 1,000,000,007 과 998,244,353 | 10 | 1 | 4,915,446 | 499,122,176 | 4,924,091 | 500,000,003 |
| 18 자리 이웃 피보나치 쌍 | 18 | 1 | 18 자리 | 18 자리 | 18 자리 | 18 자리 |
| 617 자리 이웃 피보나치 쌍 | 617 | 1 | 616 자리 | 616 자리 | 616 자리 | 617 자리 |

5 줄 모두 |x| ≤ B / (2g) 이고 |y| ≤ A / (2g) 인가: 예. A = B 인 13 과 13 은 (g, x, y) = (13, 0, 1) 이라 |y| = 1 이 A / (2g) = 0.5 보다 큽니다.

<!--/proof-->

**계수가 입력보다 커지지 않습니다.** 617 자리 입력에서 `|x|` 가 616 자리예요. 계수를 담을 칸을 입력을 담을
칸과 같은 규모로 잡으면 되고, 바퀴 수를 미리 몰라도 넘칠 걱정이 없습니다. `A = B` 는 이 상한 밖입니다. 첫
바퀴에서 나머지가 0 이 되어 마지막 몫이 1 이고, 「마지막 몫은 2 이상」이 `r_{N−1} > r_N` 에 기댔는데 이 입력은
두 칸이 같기 때문이에요.

### 불변식 — 바퀴가 끝날 때마다 이웃 두 칸 모두 A·s + B·t 가 그 칸의 나머지다

파트 1 에서 코드가 동작하는 것을 여덟 걸음으로 봤습니다. 그런데 그건 입력 하나에서 맞았다는 뜻이지 언제나
맞는다는 뜻은 아니에요. 무엇이 **매 바퀴 참으로 남는지**를 문장으로 세우고, 그것이 실제로 유지되는지 확인해
봅시다.

> **부호를 뗀 직후와 반복 한 바퀴가 끝날 때마다**, `A·s0 + B·t0 = r0` 과 `A·s1 + B·t1 = r1` 이 **둘 다**
> 참입니다. 그리고 `r1` 은 바퀴마다 엄격하게 줄어듭니다.

<!--proof:invariantPairs-->
| 시점 | (r0, r1) | A·s0 + B·t0 | A·s1 + B·t1 | 두 식의 성립 |
| --- | --- | --- | --- | --- |
| T1 이 끝난 뒤 | (510, 183) | 510·1 + 183·0 = 510 | 510·0 + 183·1 = 183 | 예 |
| T2 가 끝난 뒤 | (183, 144) | 510·0 + 183·1 = 183 | 510·1 + 183·(-2) = 144 | 예 |
| T3 이 끝난 뒤 | (144, 39) | 510·1 + 183·(-2) = 144 | 510·(-1) + 183·3 = 39 | 예 |
| T4 가 끝난 뒤 | (39, 27) | 510·(-1) + 183·3 = 39 | 510·4 + 183·(-11) = 27 | 예 |
| T5 가 끝난 뒤 | (27, 12) | 510·4 + 183·(-11) = 27 | 510·(-5) + 183·14 = 12 | 예 |
| T6 이 끝난 뒤 | (12, 3) | 510·(-5) + 183·14 = 12 | 510·14 + 183·(-39) = 3 | 예 |
| T7 이 끝난 뒤 | (3, 0) | 510·14 + 183·(-39) = 3 | 510·(-61) + 183·170 = 0 | 예 |

7 시점 가운데 두 식이 모두 성립한 시점이 7 개입니다. r1 은 183 → 144 → 39 → 27 → 12 → 3 → 0 으로 시점마다 줄었습니다.

<!--/proof-->

**두 식이 함께 참이라는 것이 중요합니다.** 하나만 참이면 다음 바퀴의 새 식을 만들 재료가 모자라요 — 새 식은
옛 식 **둘의 차**로 만들어지기 때문입니다. 그리고 「바퀴가 끝날 때마다」이지 바퀴 도중이 아닙니다. 세 쌍의 대입
가운데 `r` 쌍만 끝나고 `s` 쌍이 아직인 순간에는 `r0` 와 `s0` 가 서로 다른 칸을 가리켜요.

**출발점부터 봅시다.** 부호를 뗀 직후 `(r0, r1)` 은 `(A, B)` 이고 계수는 `(1, 0)` 과 `(0, 1)` 이라, 두 식이
`A = A·1 + B·0` 과 `B = A·0 + B·1` 로 곧바로 참입니다. 그 뒤로 상태를 바꾸는 갈래는 반복 조건 하나가 가릅니다.

| 바퀴 시작의 `r1` | 바퀴가 하는 일 | 두 식이 유지되는 근거 | `r1` 이 줄어드는 근거 |
| --- | --- | --- | --- |
| 0 이 아니다 | 세 쌍이 전부 `(둘째, 첫째 − q × 둘째)` 가 된다 | 새 첫째 식은 옛 둘째 식 그대로이고, 새 둘째 식은 옛 첫째 식에서 옛 둘째 식의 `q` 배를 뺀 것이다 | 새 `r1` 이 `r0 − q·r1` 이라 옛 `r1` 보다 작다 |
| 0 이다 | 아무것도 안 바꾸고 반복을 끝낸다 | 바뀐 것이 없다 | 바뀐 것이 없다 |

`r1` 은 0 이거나 0 이 아니고 그 사이의 경우가 없으므로, 두 줄이 갈래를 빠짐없이 덮어요. 반복이 끝나면
`r1 = 0` 이고 `r0` 가 `g` 라, 첫째 식이 곧 `A·s0 + B·t0 = g` 입니다. 그리고 `r1` 이 0 이상의 정수이면서 매
바퀴 줄어드니 반복은 반드시 끝나요.

**경계에 있는 입력도 확인하고 갑시다.** 아래 여덟 줄이 이 함수가 받을 수 있는 모양의 끝입니다.

<!--proof:edge-values-->
| 입력 | 나눗셈 | g | x | y | a·x + b·y |
| --- | ---: | ---: | ---: | ---: | ---: |
| 둘 다 0 | 0 | 0 | 0 | 0 | 0 |
| 뒤가 0 인 7 과 0 | 0 | 7 | 1 | 0 | 7 |
| 앞이 0 인 0 과 9 | 1 | 9 | 0 | 1 | 9 |
| 같은 값 13 과 13 | 1 | 13 | 0 | 1 | 13 |
| 앞이 더 작은 5 와 17 | 4 | 1 | 7 | -2 | 1 |
| 둘 다 음수인 -510 과 -183 | 6 | 3 | -14 | 39 | 3 |
| 뒤만 음수인 510 과 -183 | 6 | 3 | 14 | 39 | 3 |
| 한쪽이 1 인 1 과 10^18 | 2 | 1 | 1 | 0 | 1 |

8 입력 가운데 g 가 정의로 구한 최대공약수와 같고 a·x + b·y = g 인 입력이 8 개입니다.

<!--/proof-->

`0 과 9` 가 이 방법의 경계입니다. `r0` 가 0 이어도 첫 바퀴의 몫이 0 이라 두 칸이 `(9, 0)` 으로 자리를 바꾸고,
`r0` 에 붙는 계수가 `(0, 1)` 이 되어 `0 × 0 + 9 × 1 = 9` 로 답이 나와요. 크기를 미리 비교하는 코드가 없어도
되는 까닭이 여기 있습니다. 둘째 입력만 음수인 줄은 계수 두 줄이 첫째 줄과 같고, 부호만 `y` 에 붙었어요.

**이제 깨뜨려 봅시다.** 불변식의 「새 둘째 식은 옛 첫째 식에서 옛 둘째 식의 `q` 배를 뺀 것」을 지키던 줄은
계수 갱신 두 줄입니다. 그중 `t` 쪽 한 줄에서 뺄셈을 덧셈으로 바꿉니다.

```ts
[t0, t1] = [t1, t0 + q * t1]; // ← 뺄셈이었다
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-t-plus-->
| 입력 | 정본 (g, x, y) | 뺄셈을 덧셈으로 바꾼 판 (g, x, y) | a·x + b·y | 판정 |
| --- | --- | --- | ---: | --- |
| 전개 입력 -510 과 183 | (3, -14, -39) | (3, -14, 39) | 14,277 | 틀리다 |
| 서로소인 17 과 5 | (1, -2, 7) | (1, -2, 7) | 1 | 같다 |
| 한쪽이 0 인 7 과 0 | (7, 1, 0) | (7, 1, 0) | 7 | 같다 |
| 둘 다 0 | (0, 0, 0) | (0, 0, 0) | 0 | 같다 |

나눗셈 횟수는 전개 입력이 6 번, 17 과 5 가 3 번입니다.

<!--/proof-->

첫 줄에서 `y` 의 부호가 뒤집혀 `a·x + b·y` 가 `g` 가 아닌 값을 냅니다. 덧셈으로 바꾸면 `t` 가 부호를 바꾸지
않고 커지기만 해서 `|t|` 는 정본과 같은데 부호가 전부 양수가 되고, 옛 두 식의 차가 아니라 합이 세워져요. 둘째
줄에서 답이 같은 것에도 이유가 있습니다. 큰 쪽이 앞인 입력에서 정본의 `t` 는 칸 1 에서 양수로 시작해 칸마다 부호가
바뀌므로, 나눗셈이 홀수 번이면 답으로 읽는 칸의 `t` 가 원래 양수예요. 나눗셈 횟수는 표 아래 문장에 있고, 홀수 번인
17 과 5 에서 두 판이 같았고 짝수 번인 전개 입력에서 부호가 갈렸습니다. 아래 두 줄은 반복이 실행되지 않아 바꾼 줄을 지나지 않았어요.

<!--/proof-->

T1 은 인자마다 부호를 한 번 보고 절댓값을 한 번 구하는 자리라 입력과 상관없이 네 번입니다. 바퀴 하나는 T3 에서
보듯 나눗셈 한 번에 곱셈 셋, 뺄셈 셋, 대입 여섯이 붙고, 반복 조건 판정은 바퀴마다 한 번에 반복을 끝낼 때(T8)
한 번이 더 붙어요. 그래서 곱셈 · 뺄셈 · 대입 · 판정은 모두 나눗셈 횟수 `N` 에 비례하고, 차수를 정하는 것은 `N`
하나입니다. `N` 의 상한은 유클리드 호제법의 것을 그대로 씁니다. 나머지 수열이 같으므로 나눗셈 횟수도 같아요. 작은 쪽 입력의
십진 자릿수가 `d` 이고 `|a| ≥ |b|` 이면 `N < 4.785·d + 1` 이고, 작은 쪽이 앞이면 첫 바퀴가 두 칸을 뒤바꾸기만
해서 한 번이 더 붙습니다. 그 유도는 [유클리드 호제법 가이드](../gcd/gcd-guide.md)의 「수식 정의와 유도」에
있어요.

여기서 세지 않은 것도 적어 둡니다. `bigint` 연산 한 번의 비용까지 세면 피연산자의 자릿수에 따른 값이 곱해지는데,
나머지는 `A` 이하이고 계수는 「수식 정의와 유도」대로 입력의 절반 이하라 피연산자가 입력의 자릿수를 넘지 않아요.
수가 하드웨어 워드 안에 들면 그 값이 상수이고, 과제 규모(`10^18` 이하)가 그 경우입니다.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| 케이스 | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (한쪽이 다른 쪽의 배수이고 큰 쪽이 앞) | `O(1)` | `Θ(1)` — 나눗셈이 한 번이다 |
| **평균적인 경우** (입력 분포를 정하지 않았다) | `O(d)` | 정하지 않았다 |
| **최악의 경우** (이웃 피보나치 쌍) | `O(d)` | `Θ(d)` — `N` 이 자릿수에 비례한다 |

**최선과 최악이 갈리는 방법입니다.** 한쪽이 다른 쪽의 배수면 첫 나머지가 0 이라 한 번에 끝나고, 이웃 피보나치
쌍이면 자릿수에 비례하는 횟수가 필요해요. 평균은 타이트 경계를 적지 않았습니다. 입력 분포를 정하지 않았기
때문이고, 분포를 정하면 그 분포에 대한 기댓값을 따로 셀 수 있어요.

**총식을 한 번은 정확히 적습니다.** 앞뒤로 붙는 전처리가 없다는 것이 이 방법의 특징이에요 — 정렬도, 표도, 미리
만드는 값도 없습니다. 나눗셈은 `N` 번이고 `|a| ≥ |b| ≥ 1` 이면 `N < 4.785d + 1`, 작은 쪽이 앞이면 그보다 한 번
더이며, 그 밖의 연산이 바퀴마다 13 번과 앞뒤로 상수 번 붙고, 저장 칸은 여섯과 몫 하나입니다. 과제 규모에 넣으면
이렇습니다.

<!--proof:perfTotal-->
```text
두 수가 10^18 이하일 때
  작은 쪽 자릿수 d        18 이하
  나눗셈 N ≤ 4.785d + 1   87.1
  규모 안의 최악          85   (F(87), F(86))
  그때 계수의 자릿수      |x| 18 자리 · |y| 18 자리
  저장 칸                 r0 · r1 · s0 · s1 · t0 · t1 여섯과 몫 q
```

첫 줄의 18 은 두 수가 다를 때의 자릿수이고, 두 수가 모두 `10^18` 이면 작은 쪽이 19 자리지만 첫 나머지가 0 이라
한 번에 끝납니다. **보장의 종류는 최악 보장입니다.** 코드에 난수가 하나도 없고 입력 분포에 대한 가정도 없어요.
같은 입력을 두 번 넣으면 반환값도 나눗셈 횟수도 똑같이 나옵니다.

#### 최악을 만드는 입력

「큰 수가 최악」이라는 통념부터 확인합시다. 과제 상한 언저리의 다섯 모양을 실제로 실행하면 값이 크게 갈립니다.

<!--proof:shape-values-->
| 입력 모양 | 작은 쪽 자릿수 | 나눗셈 | \|x\| | g |
| --- | ---: | ---: | ---: | ---: |
| 몫이 거의 다 1 — F(87) · F(86) | 18 | 85 | 160,500,643,816,367,088 | 1 |
| 몫이 전부 2 — P(47) · P(46) | 18 | 47 | 143,263,821,649,299,118 | 1 |
| 몫 하나가 아주 큼 — 10^18 · 10^18 - 1 | 18 | 2 | 1 | 1 |
| 한쪽이 다른 쪽의 배수 — 10^18 · 10^9 | 10 | 1 | 0 | 1,000,000,000 |
| 둘 다 같은 값 — 10^18 · 10^18 | 19 | 1 | 0 | 1,000,000,000,000,000,000 |

첫 줄과 셋째 줄은 작은 쪽이 18 자리와 18 자리인데 나눗셈이 85 번과 2 번입니다.

<!--/proof-->

**통념은 이 방법에서 절반만 맞습니다.** 자릿수가 상한을 정하지만 실제 횟수는 몫이 정해요. 몫이 크면 한 바퀴에
많이 줄고, 몫이 1 이면 조금만 줍니다. 몫이 계속 1 이 되려면 두 수의 비가 황금비에 가까워야 하고, 그런 쌍이
이웃 피보나치 수예요. 같은 144 에서 시작하는 두 수열을 나란히 놓으면 칸 수와 계수가 어떻게 갈리는지 확인할 수
있습니다.

<!--fig:worst-fib-->
![나머지 수열 둘 — 이웃 피보나치 쌍 (144, 89) 은 몫이 거의 전부 1 이라 칸이 가장 많고, 0 앞 칸의 계수도 더 크다](./figs/worst-fib.svg)

이웃 피보나치 쌍은 몫이 마지막만 빼고 전부 1 이라, 계수 두 줄의 칸도 피보나치 수를 하나씩 거슬러 지나가며
커집니다. 과제 상한 아래에서 최악을 만드는 방법은 그래서 하나예요. `10^18` 을 넘지 않는 가장 큰 이웃 피보나치
쌍 `F(87) · F(86)` 을 고르면, 나눗셈 횟수와 `|x|` 가 함께 규모 안의 가장 큰 값에 이릅니다. 몫을 전부 1 로 만들
수는 없습니다 — 마지막 몫은 2 이상이라는 것을 「수식 정의와 유도」가 보였어요. 가장 적은 일을 하는 입력은
반대쪽입니다. 큰 쪽이 앞이고 한쪽이 다른 쪽의 배수면 첫 나머지가 0 이라 자릿수와 상관없이 한 번에 끝나고,
`|x|` 는 0 이에요.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 계수를 대입해 **찾던** 것을 나머지와 함께 **만드는** 것으로
바꿨고, 만드는 방법은 나머지를 만든 몫을 계수 두 줄에 그대로 다시 쓰는 것이며, 그 근거는 두 식의 차가 다시
같은 꼴의 식이라는 것 하나입니다. 계수 두 줄을 더해도 나눗셈은 유클리드 호제법의 `N` 번 그대로예요.

```text
부호를 떼고 (1,0)·(0,1) 로 시작 → 몫 하나로 세 줄을 갱신 → r1 이 0 이면 부호를 다시 붙인다
                                    └ A·s + B·t = r 이 그대로다     └ s0 가 x, t0 가 y 다
```

먼저 답이 붙는 문제 하나입니다. 전개의 T8 에서 반복이 끝날 때 0 의 칸 `r₇` 에도 계수 `(-61, 170)` 이 있었어요.
**이 쌍으로 `-510·x + 183·y = 3` 의 다른 해를 만들 수 있습니까** — 만들 수 있다면 어떻게 합니까?

<!--check:lastPair-->
답: 만들 수 있습니다. `510 × (-61) + 183 × 170 = 0` 이라 이 쌍은 **0 을 만드는 조합**이고, 입력의 부호를 붙인
`(61, 170)` 은 `-510 × 61 + 183 × 170 = 0` 을 만듭니다. 답 `(-14, -39)` 에 이 쌍을 몇 배 더해도 식의 값이 3
그대로예요.

<!--proof:selfcheckPair-->
```text
k = 0   x = -14   y = -39   -510 × (-14) + 183 × (-39) = 3
k = 1   x = 47    y = 131   -510 × 47 + 183 × 131 = 3
k = 2   x = 108   y = 301   -510 × 108 + 183 × 301 = 3
```
<!--/check-->

아래 셋은 답을 싣지 않았습니다. 막히면 차례대로 「불변식」, 「수식 정의와 유도」, 「최악을 만드는 입력」을 다시
보세요.

- 불변식은 「`r1` 이 바퀴마다 엄격하게 줄어든다」고 말합니다. 그러면 `|s1|` 은 어떻습니까 — 바퀴마다 커집니까,
  아니면 그대로인 바퀴가 있습니까. 전개의 T2 와 T3 의 `s1` 값을 보고 답해 보세요.
- 유도가 낸 상한은 `|x| ≤ B / (2g)` 였고 전개 입력에서 실측이 14, 상한이 30.5 였습니다. `B` 를 고정했을 때 그
  상한에 가장 가까운 입력을 어떻게 만들겠습니까. 마지막 몫이 몇이어야 하는지부터 따져 보세요.
- 최악 입력에서 `g` 가 1 이었습니다. `g` 가 3 이면서 나눗셈이 가장 많은 입력을 과제 규모 안에서 어떻게 만들 수
  있습니까. 그때 나눗셈 횟수와 `|x|` 는 `g` 가 1 일 때와 비교해 어떻게 됩니까.

## 실습 — 직접 풀어 보기

이 글의 알고리즘으로 풀어 볼 문제입니다. 스텁을 채운 뒤 테스트로 확인하세요.

### 확장 유클리드 호제법 (Extended Euclidean Algorithm)

풀 파일: [`extendedEuclidean.ts`](./extendedEuclidean.ts) · 테스트: [`extendedEuclidean.test.ts`](./extendedEuclidean.test.ts) · 실행: `bun test src/algorithms/number-theory/extendedEuclidean/extendedEuclidean.test.ts`

#### 한 줄 요약

> 함수는 두 정수 `a`, `b`를 받아 $a \cdot x + b \cdot y = \gcd(a, b)$를 만족하는 정수 해 $(g, x, y)$를 반환한다.

#### 스토리

두 공장이 각각 `a`개, `b`개 단위로만 부품을 생산한다. 조달 담당자는 정확히 `g`개의 부품을 맞추기 위해 첫 번째 공장에 `x`배치, 두 번째 공장에 `y`배치를 주문해야 한다. 여기서 `x`나 `y`가 음수이면 그 공장 물량을 되돌려 보내는 것을 의미한다.

이러한 조합이 가능한 가장 작은 단위 `g`가 바로 두 공장 생산량의 최대공약수다. 조달 담당자는 `g`, `x`, `y`를 동시에 구해야 한다.

이 계산은 암호 시스템에서 모듈러 역원을 구할 때도 핵심적으로 쓰인다. 예를 들어 $3^{-1} \pmod{11}$은 $3x + 11y = 1$의 정수해 $x$를 구하면 된다.

#### 함수 인터페이스

```ts
export function extendedEuclidean(
  a: bigint,
  b: bigint,
): { g: bigint; x: bigint; y: bigint };
```

- `a` — 첫 번째 정수, 음수·0·양수 모두 가능한 bigint
- `b` — 두 번째 정수, 음수·0·양수 모두 가능한 bigint
- 반환 — `{ g, x, y }` 형태로 $a \cdot x + b \cdot y = g = \gcd(a, b)$를 만족

#### 제약 조건

- `a`, `b`는 임의의 bigint (음수, 0 포함)
- $g = \gcd(|a|, |b|)$ (항상 음이 아닌 값)
- 반환된 $x$, $y$는 $a \cdot x + b \cdot y = g$를 정확히 만족해야 함
- 시간 제한: 1초, 메모리 제한: 256 MB

#### 문제 상세

두 정수 $a$, $b$에 대해 다음 **베주 항등식**을 만족하는 $g$, $x$, $y$를 반환한다.

$$a \cdot x + b \cdot y = g = \gcd(a, b)$$

- $g$는 항상 음이 아닌 값이다 ($g \geq 0$).
- $a = b = 0$이면 $g = 0$이며 $x = 0$, $y = 0$을 반환한다.
- $b = 0$이면 $g = |a|$이며 $a \cdot x = g$를 만족하는 $x$를 반환한다.
- $a = 0$이면 $g = |b|$이며 $b \cdot y = g$를 만족하는 $y$를 반환한다.

#### 예시

```ts
extendedEuclidean(30n, 18n);
// { g: 6n, x: -1n, y: 2n } (또는 동일 항등식을 만족하는 다른 해)
// 검증: 30 * (-1) + 18 * 2 = -30 + 36 = 6 ✓

extendedEuclidean(7n, 5n);
// { g: 1n, x: -2n, y: 3n } (또는 동일 항등식을 만족하는 다른 해)
// 검증: 7 * (-2) + 5 * 3 = -14 + 15 = 1 ✓

extendedEuclidean(0n, 9n);
// { g: 9n, x: 0n, y: 1n }
// 검증: 0 * 0 + 9 * 1 = 9 ✓

extendedEuclidean(0n, 0n);
// { g: 0n, x: 0n, y: 0n }

extendedEuclidean(17n, 5n);
// g=1n, a*x + b*y = 1 — 17과 5는 서로소
```
