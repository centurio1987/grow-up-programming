# BFS Shortest Path 솔루션 분석 보고서

## 1. 방향성 분석

문제는 무가중치 무향 그래프에서 단일 출발점으로부터 모든 정점까지의 최단 간선 수를 구하는 표준 BFS(너비 우선 탐색) 문제이다. 솔루션의 큰 그림은 다음과 같이 표준 BFS 절차를 그대로 따른다.

- 간선 목록 `edges`로부터 인접 리스트 `adj`를 구성한다(무향 그래프이므로 양방향 모두 추가).
- 거리 배열 `distanceList`를 길이 `n`, 모든 값 `-1`로 초기화하고, `distanceList[source] = 0`으로 설정한다.
- 큐에 `source`를 넣고, 큐가 빌 때까지 정점을 꺼내 인접 정점을 확장하며 거리를 `distanceList[node] + 1`로 채운다.

이 구조 자체는 방향이 옳다. 그러나 "이미 방문/큐에 들어간 정점"을 판정하는 방식으로 **불리언 배열이 아니라 정수 하나(`onPath`)에 정점 번호를 비트로 대응시키는 비트마스크**를 사용한다. 이 설계는 두 가지 문제를 낳는다.

1. 비트 판정 비교 연산자 자체가 잘못되어 있다(2장에서 다룸).
2. 설령 비교 연산자를 고치더라도, 정점 하나당 비트 하나를 정수 하나에 욱여넣는 방식은 문제의 제약 $1 \leq V \leq 10^{5}$ 앞에서 근본적으로 성립하지 않는다(3장에서 다룸).

## 2. 정확성 분석 (테스트 결과 기반)

`bun test src/algorithms/graph/bfsShortestPath/bfsShortestPath.test.ts` 실행 결과:

```
2 pass
7 fail
Ran 9 tests across 1 file. [57.00ms]
```

실패한 7개 테스트는 모두 `source`를 제외한 모든 정점의 값이 `-1`로 반환되는 동일한 증상을 보인다(예: 기대값 `[0, 1, 2, 3]` vs 수신값 `[0, -1, -1, -1]`).

### 결함 A. 방문 판정 비교 연산자 오류 (치명적, 전체 실패의 직접 원인)

```ts
if ((onPath & (1 << neighbor)) === 1) {
```

`onPath`는 "아직 방문하지 않은 정점 집합"을 비트로 표현한 정수이다. 정점 `neighbor`가 아직 방문되지 않았다면 `onPath`의 `neighbor`번째 비트는 1이고, 그 경우 `onPath & (1 << neighbor)`의 값은 $2^{\text{neighbor}}$이지 $1$이 아니다. $2^{\text{neighbor}} = 1$이 성립하는 경우는 `neighbor = 0`뿐이다. 즉 이 비교식은 `neighbor`가 정확히 $0$일 때를 제외하면 항상 `false`를 반환한다.

그 결과 `distanceList[neighbor]`와 `onPath`의 갱신, `queue.push(neighbor)`가 사실상 한 번도 일어나지 않는다. BFS 큐는 `source`를 꺼낸 뒤 어떤 이웃도 새로 추가하지 못하고 바로 빈 상태가 되어 종료된다. `source` 이외 모든 정점의 거리가 초기값 `-1`로 남는다.

**왜 2개 테스트는 통과했는가**: 통과한 두 테스트("간선이 전혀 없는 경우", "V=1, 자기 자신만 source인 경우")는 모두 `edges = []`이다. 인접 리스트가 전부 빈 배열이므로 `for (let neighbor of adj[node])` 반복문 자체가 한 번도 실행되지 않고, 결함 A가 있는 조건문에 도달하지 않는다. 즉 이 두 테스트는 결함 A를 우회해서 우연히 통과한 것이지, 로직이 옳아서가 아니다.

**수정 방향(1차)**: 조건을 `!== 0`으로 바꾸면 "해당 비트가 켜져 있는가(=아직 방문 안 함)"라는 원래 의도와 일치한다.

```ts
if ((onPath & (1 << neighbor)) !== 0) {
```

이 수정만 적용해 나머지 8개 테스트(성능 테스트 제외)를 재현 검증한 결과 전부 통과했다. 다만 성능 테스트(V=10^5)는 여전히 실패한다 — 그 이유는 결함 A와 별개인 구조적 결함 B 때문이며, 3장에서 다룬다.

## 3. 최적화 분석

### 3.1. 개선 가능한 핵심 이슈

#### 3.1.1. 알고리즘 원형에서 최종 구현으로의 전개

**원형: 표준 BFS 최단 거리(불리언 방문 배열)**

무가중치 그래프에서 단일 출발점 최단 거리를 구하는 표준 절차는 다음과 같다. `visited[v]`는 정점 $v$가 큐에 들어간 적이 있는지를 나타내는 불리언 값이다.

```
dist[v] ← -1 (모든 v)
visited[v] ← false (모든 v)

dist[source] ← 0
visited[source] ← true
큐 ← [source]

while 큐가 비어있지 않다:
    u ← 큐에서 제거
    u의 각 이웃 v에 대하여:
        if visited[v] = false:
            visited[v] ← true
            dist[v] ← dist[u] + 1
            큐에 v 추가
```

각 정점은 큐에 정확히 한 번만 들어가고, 각 간선은 양 끝 정점의 인접 리스트 순회에서 각각 한 번씩, 총 두 번 검사된다. 따라서 시간 복잡도는 $O(V + E)$이고 이는 이 문제에서 달성 가능한 최적 복잡도이다. 방문 여부를 저장하는 `visited`는 정점 하나당 값 하나를 갖는 길이 $V$의 배열이면 충분하다.

**현재 솔루션이 시도한 변형: 정수 하나에 비트로 방문 집합을 압축**

```ts
let onPath: number = 2 ** n - 1;
...
onPath &= ~(1 << source);
...
if ((onPath & (1 << neighbor)) !== 0) { ... }
```

이 방식은 정점 번호를 정수 하나의 이진 자릿수(비트)에 대응시켜, 정점 $v$가 미방문이면 $v$번째 비트를 1로, 방문했으면 0으로 관리하려는 시도이다. 정점 수가 충분히 작을 때(대략 $V \leq 30$)는 이러한 비트마스크가 방문 집합을 정수 하나로 표현할 수 있어 메모리상 이점이 있고, 부분집합을 다루는 다른 유형의 문제(예: 방문 순서의 모든 부분집합을 열거해야 하는 문제)에서는 실제로 유용한 기법이다. 그러나 이 문제의 제약은 $1 \leq V \leq 10^{5}$이며, 이 규모에서는 다음 두 가지 이유로 비트마스크 방식 자체가 성립하지 않는다.

**이유 1 — 자바스크립트 비트 연산자는 32비트 정수로 동작한다.**

ECMA-262 명세에 따르면 `<<`, `&`, `~` 같은 비트 연산자는 피연산자를 먼저 `ToInt32`로 변환한 뒤 연산한다. `ToInt32`는 32비트 부호 있는 정수로 값을 접어 넣으며, 특히 `<<`의 시프트 자릿수는 32로 나눈 나머지만 사용한다. 즉 `1 << neighbor`는 `neighbor`가 32 이상이면 `1 << (neighbor % 32)`와 같은 값이 된다. 다시 말해 정점 32와 정점 0은 같은 비트를 공유하고, 정점 33과 정점 1도 같은 비트를 공유한다. 서로 다른 정점이 같은 비트에 대응되면, 먼저 처리된 정점이 그 비트를 0으로 만들어 버려 나중 정점이 "이미 방문됨"으로 잘못 판정된다.

이를 직접 검증하기 위해 결함 A만 수정한 함수로 정점 35개짜리 사슬 그래프(`0-1-2-...-34`, source=0)를 실행했다.

```
n=35 chain result[34] (expect 34): -1
full: [0, 1, 2, ..., 30, 31, -1, -1, -1]
```

정점 0부터 31까지(정확히 32개, 비트 0~31)는 올바르게 계산되지만, 정점 32 이후로는 전부 `-1`로 멈춘다. `1 << 32`가 `1 << 0`으로 접혀 정점 0의 비트와 충돌하고, 정점 0은 이미 방문 처리되어 그 비트가 0이므로 정점 32가 "이미 방문됨"으로 오판되어 큐에 들어가지 못하기 때문이다. 이 지점부터 그래프의 나머지 부분 전체가 탐색되지 않는다.

**이유 2 — 정점 수가 크면 `2 ** n`이 부동소수점 표현 범위를 넘어 `Infinity`가 된다.**

`onPath`의 초기값은 `2 ** n - 1`이다. 자바스크립트의 `Number`는 IEEE 754 배정밀도 부동소수점이며 표현 가능한 최댓값은 약 $1.8 \times 10^{308}$, 즉 $2^{1024}$ 부근이다. `n`이 그보다 훨씬 작더라도, 이미 `n = 100000`이면 $2^{100000}$은 유한한 부동소수점으로 표현할 수 없는 수이므로 `2 ** 100000`은 `Infinity`로 평가된다. `Infinity - 1`도 `Infinity`이다.

이후 `onPath &= ~(1 << source)`처럼 `Infinity`에 비트 연산자를 적용하면, 명세상 `ToInt32(Infinity) = 0`이므로 `onPath`는 즉시 `0`이 된다. `onPath`가 `0`이면 어떤 `neighbor`에 대해서도 `onPath & (1 << neighbor)`는 항상 `0`이 되어, 결함 A를 고친 조건(`!== 0`)조차 항상 거짓이 된다. 즉 `source`를 제외한 어떤 정점도 방문 처리되지 않는다.

이를 결함 A만 수정한 함수로 실제 성능 테스트 입력(정점 10만 개 사슬 그래프)에 대해 검증했다.

```
V=1e5 perf test FAIL result[0]: 0  result[V-1]: -1
```

예측한 대로 `source`(거리 0)만 채워지고 나머지는 전부 `-1`로 남는다. 즉 결함 A만 고쳐서는 8/9 테스트가 통과하지만, $V = 10^5$ 규모의 성능 테스트는 여전히 실패한다. 이는 타이밍 초과가 아니라 **값 자체가 틀리는 정확성 실패**이다 — BFS가 `source`를 처리한 직후 큐가 비어 즉시 종료되므로 오히려 실행 시간은 매우 짧게(수 ms) 측정된다.

정리하면, 결함 A(비교 연산자)와 결함 B(비트마스크의 32비트 한계 및 `Infinity` 붕괴)는 서로 다른 결함이며, 이 문제의 제약 조건 $V \leq 10^5$ 안에서는 결함 A만 고쳐도 소규모 그래프에서만 정답이 나오고 대규모 그래프에서는 결함 B가 별도로 발동한다.

#### 3.1.2. 구체적 개선안

비트마스크를 정점 하나당 원소 하나를 갖는 방문 배열로 교체하면 결함 A, B가 동시에 사라진다. `Uint8Array`는 정점당 1바이트만 사용하므로 $V = 10^5$에서도 메모리 부담이 없다.

```ts
export function bfsShortestPath(
  n: number,
  edges: [number, number][],
  source: number,
): number[] {
  const distanceList = Array.from({ length: n }, () => -1);
  const adj: number[][] = Array.from({ length: n }, () => []);
  const visited = new Uint8Array(n);
  const queue: number[] = [];

  for (const [u, v] of edges) {
    adj[u]!.push(v);
    adj[v]!.push(u);
  }

  distanceList[source] = 0;
  visited[source] = 1;
  queue.push(source);

  while (queue.length !== 0) {
    const node = queue.shift()!;
    for (const neighbor of adj[node]!) {
      if (!visited[neighbor]) {
        visited[neighbor] = 1;
        distanceList[neighbor] = distanceList[node]! + 1;
        queue.push(neighbor);
      }
    }
  }

  return distanceList;
}
```

이 형태로 앞서 실패했던 정점 35개 사슬 그래프와 정점 10만 개 사슬 그래프를 재검증한 결과, 각각 `result[34] = 34`, `result[99999] = 99999`로 정확히 계산됨을 확인했다. 시간/공간 복잡도는 인접 리스트 구성 $O(V+E)$, BFS 순회 $O(V+E)$, 방문 배열 $O(V)$로 전체 $O(V+E)$이며, 이는 이 문제에서 달성 가능한 이론적 최적과 일치한다.

#### 3.1.3. 참고 — `queue.shift()`의 성능 영향은 이 런타임에서 실측상 유의미하지 않음

BFS 큐 구현에서 `Array.prototype.shift()`를 반복 호출하는 방식은 일반적으로 매 호출마다 나머지 원소를 앞으로 당기는 $O(k)$ 비용이 든다고 알려져 있어, 프런티어(한 번에 큐에 쌓이는 정점 수)가 큰 그래프에서 전체 $O(V^2)$로 악화될 위험이 있는 패턴으로 종종 지적된다. 이 솔루션에서도 잠재적 개선 후보로 검토했으나, 이 프로젝트가 사용하는 Bun(JavaScriptCore) 런타임에서 직접 측정한 결과 해당 규모에서는 실질적 병목이 아니었다.

- `Array.prototype.shift()`만으로 배열을 끝까지 비우는 벤치마크: 원소 10,000개 0.33ms, 100,000개 2.16ms, 400,000개 8.25ms로 원소 수 대비 거의 선형에 가깝게 증가했다(제곱으로 증가한다면 400,000개는 10,000개의 $40^2 = 1600$배가 되어야 하나, 실제로는 약 25배에 그쳤다).
- 위 3.1.2의 방문 배열 기반 구현을 프런티어가 가장 넓어지는 최악 형태인 별 모양 그래프(허브 정점 하나에 나머지 99,999개 정점이 모두 직접 연결)에 대해 실행한 결과 약 13ms로 측정되어, 테스트의 100ms 기준을 여유 있게 만족했다.

따라서 이 문제의 제약 범위($V, E \leq 10^5$) 안에서는 `queue.shift()`를 인덱스 기반 큐(head 포인터로 앞을 건너뛰는 방식)로 바꾸는 것이 필수 개선 사항은 아니다. 다만 이식성(다른 자바스크립트 엔진에서는 `shift()`가 실제로 $O(n)$일 수 있음)을 고려한다면 안전한 선택지로 남겨둘 수 있다.

## 4. 재분석 — 컨셉 변경: 비트마스크 제거, `Uint8Array` 방문 배열 + `CircularQueue` 도입

솔루션이 1~3장에서 분석한 비트마스크(`onPath`) 버전에서, 정점 하나당 값 하나를 갖는 `Uint8Array` 방문 배열과 별도 클래스 `CircularQueue`를 사용하는 버전으로 전면 교체되었다. 제약 조건("컨셉이 바뀐 경우, 보고서 내용을 변경하지 말고, 추가해 달라")에 따라 1~3장은 그대로 두고, 새 구현에 대한 분석을 이 장에 추가한다.

### 4.1. 방향성 분석

새 구현의 골격은 다음과 같다.

- 간선 목록으로부터 인접 리스트 `adj`를 구성한다(무향이므로 양방향 추가) — 1~3장과 동일.
- 방문 판정을 비트마스크가 아니라 정점 하나당 1바이트를 쓰는 `Uint8Array` 배열 `visited`로 관리한다.
- 큐를 자바스크립트 내장 배열이 아니라, 고정 크기 배열 위에 `head`/`tail` 두 인덱스를 두고 `(index + 1) % capacity` 형태로 순환시키는 `CircularQueue` 클래스로 직접 구현한다.

`visited`를 정점당 값 하나의 배열로 되돌린 것은 2~3장에서 지적된 결함(32비트 시프트 한계, `2 ** n`의 `Infinity` 붕괴)을 근본적으로 제거하는 올바른 방향이다. 또한 `CircularQueue`는 1~3장의 3.1.3에서 "이식성을 고려한다면 안전한 선택지로 남겨둘 수 있다"고 언급했던 인덱스 기반 큐(포인터로 앞을 건너뛰는 방식)를 실제로 구현한 형태로 볼 수 있다. `Array.prototype.shift()`의 잠재적 $O(n)$ 비용을 원천적으로 피한다는 점에서 방향성은 옳다.

### 4.2. 정확성 분석 (테스트 결과 기반)

```
bun test src/algorithms/graph/bfsShortestPath/bfsShortestPath.test.ts

9 pass
0 fail
11 expect() calls
Ran 9 tests across 1 file. [49.00ms]
```

성능 테스트를 포함해 9개 테스트 전부 통과한다. 다만 테스트를 통과한다는 사실과 별개로, `CircularQueue`의 `length` 게터 구현 자체에는 아래와 같은 결함이 있다.

```ts
get length() {
  return this.tail - this.head;
}
```

`head`와 `tail`은 모두 `[0, capacity)` 범위를 순환하는 인덱스이다. 이 게터는 두 인덱스의 값을 순환(모듈러) 관계를 고려하지 않고 그대로 뺄셈한다. 그 결과 `tail`이 `head`보다 앞쪽 인덱스로 넘어가 있으면(순환으로 한 바퀴 돌았으면) `length`는 실제 원소 개수가 아니라 음수나 뒤죽박죽인 값을 반환한다. 직접 재현한 결과는 다음과 같다.

```
실제 원소 개수(counter): 3   length 게터 값: -1
```

이는 정점 4개짜리 별 모양 그래프에서 `source`를 큐에서 뺀 뒤 나머지 3개 정점을 큐에 넣은 상태를 재현한 것이다. 실제 큐 안에는 원소가 3개 있는데 `length` 게터는 `-1`을 반환한다.

더 심각한 경계 사례는 `n = 1`이다.

```
n=1: 실제 원소 개수(counter): 1   length 게터 값: 0 (0이면 while 루프가 원소가 있어도 실행되지 않음)
```

`capacity = 1`일 때는 `enqueue`를 단 한 번 호출하기만 해도 `tail`이 `(0 + 1) % 1 = 0`으로 즉시 `head`(=0)와 같은 값으로 돌아온다. `bfsShortestPath` 본문의 `while (queue.length !== 0)` 조건은 이 값을 `0`으로 읽어, 큐 안에 `source` 정점이 실제로 들어있는데도 반복문 몸체를 단 한 번도 실행하지 않는다.

**왜 현재 테스트는 실패하지 않는가**: `n = 1`인 테스트("V=1, 자기 자신만 source인 경우")는 애초에 탐색할 이웃 정점이 없다. `distanceList[source] = 0`은 반복문 진입 전에 이미 설정해 두었으므로, 반복문이 한 번도 실행되지 않아도 기대값 `[0]`과 결과가 우연히 일치한다. 즉 이 테스트는 `length` 게터의 결함을 드러내지 못하고 통과한 것이지, 그 게터가 옳아서 통과한 것이 아니다.

$n \geq 2$인 나머지 테스트들에서는 다른 이유로 결함이 드러나지 않는다. `source` 정점은 반복문의 첫 번째 `dequeue` 호출에서 큐를 완전히 빠져나간 뒤 다시는 `enqueue`되지 않는다. 따라서 큐에 동시에 들어있을 수 있는 정점의 최대 개수는 `source`를 제외한 $n - 1$개를 넘을 수 없다. `capacity`는 `n`으로 설정되어 있으므로, 큐가 가득 차는 경우(`counter === capacity`, 즉 `enqueue`가 `this.capacity === this.counter` 조건으로 막는 경우)는 이 문제의 사용 방식 안에서는 결코 발생하지 않는다. 그 결과 `tail`과 `head`가 우연히 같은 값을 가리키는 경우는 오직 큐가 진짜로 비어 있을 때(`counter = 0`)뿐이며, `length !== 0` 판정 자체는 참/거짓 여부만 놓고 보면 우연히 항상 옳게 나온다. `n = 1`은 `capacity = 1`이라 이 여유분(`capacity`가 최대 동시 재고보다 1 커야 한다는 조건)이 애초에 성립하지 않는 유일한 경계이고, 마침 이웃이 없어 결과에 영향을 주지 않았을 뿐이다.

### 4.3. 최적화 분석

#### 4.3.1. 개선 가능한 핵심 아이디어: 이미 존재하는 `counter`를 사용한다

`CircularQueue` 클래스는 `enqueue`에서 원소를 추가할 때마다 `this.counter`를 1 증가시키고, `dequeue`에서 원소를 뺄 때마다 1 감소시킨다. 즉 이 클래스는 이미 정확한 원소 개수를 `counter` 필드에 실시간으로 유지하고 있다. 그런데 `length` 게터는 이 값을 쓰지 않고, `tail - head`를 다시 계산한다. 원소 개수를 구하는 데 필요한 정보는 이미 `counter`에 있으므로, 다음과 같이 바꾸면 4.2절의 결함이 사라진다.

```ts
get length() {
  return this.counter;
}
```

#### 4.3.1.1. 원형(circular buffer의 길이 계산 표준 기법)에서 문제 해결책을 유도하는 과정

원형 큐(순환 버퍼, ring buffer)는 고정 크기 배열 하나를 재사용하기 위해 `head`(다음에 꺼낼 위치)와 `tail`(다음에 넣을 위치) 두 인덱스를 두고, 배열 끝에 도달하면 인덱스를 나머지 연산(`% capacity`)으로 처음으로 되돌리는 자료구조이다. 이 자료구조에서 "현재 들어있는 원소 개수"를 구하는 방법은 정확히 두 갈래로 나뉜다.

1. **모듈러 보정을 포함한 인덱스 뺄셈**: `(tail - head + capacity) % capacity`. 두 인덱스의 뺄셈이 음수가 될 수 있으므로 `capacity`를 한 번 더해 준 뒤 나머지 연산으로 값을 `[0, capacity)` 범위로 되돌리는 방식이다. 다만 이 식은 `tail === head`일 때 `counter`가 `0`인지 `capacity`인지(완전히 빈 상태인지 완전히 가득 찬 상태인지)를 구분하지 못하는 근본적인 한계가 있다. 이 한계를 없애려면 `capacity - 1`개까지만 채우도록 강제하거나, "가득 참" 여부를 나타내는 별도 불리언 플래그를 두는 등의 추가 장치가 필요하다.
2. **원소 개수를 별도 변수로 직접 관리**: `enqueue` 시 `+1`, `dequeue` 시 `-1`을 적용하는 카운터 변수를 두고, 길이 조회는 그 변수를 그대로 반환한다. 인덱스의 순환 여부와 무관하게 항상 정확하며, 위 1번 방식의 "가득 참/빈 상태 구분 불가" 문제도 애초에 발생하지 않는다.

현재 `CircularQueue` 구현은 `enqueue`/`dequeue`에서 이미 2번 방식(`counter` 필드)을 갱신하고 있으면서도, `length` 게터에서만 1번 방식을 모듈러 보정 없이(`% capacity` 없이) 적용하는 상태이다. 즉 "가득 참을 구분할 수 없다"는 1번 방식의 근본적 한계에 더해, 모듈러 보정조차 빠뜨려 순환 한 바퀴만 돌아도 값이 음수로 어긋나는 이중의 결함을 갖고 있다. 이미 정확한 2번 방식의 값(`counter`)이 같은 클래스 안에 존재하므로, `length` 게터가 그 값을 그대로 반환하도록 고치는 것이 별도의 상태나 연산을 추가하지 않는 가장 직접적인 수정이다.

#### 4.3.2. 성능 확인

수정 여부와 무관하게(4.2절에서 설명한 대로 이 문제의 사용 방식 안에서는 우연히 결과가 틀리지 않으므로) 현재 구현의 실행 시간을 측정했다.

```
체인 그래프 V=1e5:   result[0]=0  result[99999]=99999  elapsed=11.33ms
별 모양 그래프 V=1e5: result[0]=0  result[1]=1          elapsed=9.93ms
```

두 경우 모두 정답을 정확히 반환하며, 테스트 기준(100ms) 대비 여유 있게 통과한다. 시간 복잡도는 인접 리스트 구성과 BFS 순회 모두 $O(V + E)$로 1~3장에서 분석한 이론적 최적과 동일하고, `CircularQueue`를 쓰더라도 공간 복잡도는 방문 배열 $O(V)$, 큐 자체도 크기 $n$의 배열 하나 $O(V)$로 동일한 점근 복잡도를 유지한다.

## 5. 버그 수정 확인 — `CircularQueue.length` 게터 수정

4.3.1절에서 제안한 수정이 실제 코드에 그대로 반영되었다.

```ts
get length() {
  return this.counter;
}
```

### 5.1. 개선된 내용

4.2절에서 결함을 재현했던 두 케이스를 수정된 코드로 다시 실행한 결과, `length`가 실제 원소 개수와 정확히 일치하게 되었다.

```
별 모양 재현: length = 3 (기대값 3)   ← 수정 전에는 -1이었다
n=1: length = 1 (기대값 1)            ← 수정 전에는 0이었다
```

여러 번 순환(wraparound)시켜도 항상 정확하다.

```
round 0: enqueue 2개 후 length = 2, dequeue 2개 후 length = 0
round 1: enqueue 2개 후 length = 2, dequeue 2개 후 length = 0
...(5회 반복 모두 동일)
```

`length` 게터 자체는 4.3.1절에서 제안한 대로 완전히 올바르게 고쳐졌다.

### 5.2. 남아있는 버그: `dequeue()`의 "비어있음" 판정에 동일한 결함이 남아 있다

`length`를 고친 뒤 전체 테스트를 다시 실행하면, 이전에는 통과하던 테스트가 오히려 실패한다.

```
bun test src/algorithms/graph/bfsShortestPath/bfsShortestPath.test.ts

(fail) bfsShortestPath > V=1, 자기 자신만 source인 경우 [0.33ms]
TypeError: undefined is not an object (evaluating 'adj[node]')
  at bfsShortestPath (bfsShortestPath.ts:23:26)

8 pass
1 fail
```

원인은 `dequeue()`에 있다.

```ts
dequeue() {
  if (this.head === this.tail) return null;
  ...
}
```

이 판정은 4.2절에서 지적한 `length` 게터의 결함과 근본적으로 같은 문제를 갖고 있다. `head === tail`은 "큐가 비어 있다"는 의미도 되지만, "인덱스가 정확히 한 바퀴 순환해서 우연히 같은 위치로 되돌아왔다"는 의미도 될 수 있어, 이 두 상태를 인덱스만으로는 구분할 수 없다.

`n = 1`(`capacity = 1`)인 경우를 정식으로 따라가면 다음과 같다.

1. `enqueue(source)` 호출 전: `head = 0`, `tail = 0`, `counter = 0`.
2. `enqueue(source)` 호출: `tail = (0 + 1) % 1 = 0`, `counter = 1`. 이 시점에 `head`와 `tail`은 여전히 둘 다 `0`이다. 즉 원소가 1개 들어있는데도 인덱스만 보면 "비어 있음"과 구분되지 않는 상태가 된다.
3. `bfsShortestPath` 본문의 `while (queue.length !== 0)`은 (수정된 `length` 덕분에) `counter = 1`을 정확히 읽어 참으로 판정하고 반복문에 진입한다.
4. 반복문 안에서 `queue.dequeue()`를 호출하면, `head === tail`(둘 다 `0`) 조건이 참이 되어 `dequeue()`는 실제로 원소가 있음에도 `null`을 반환한다.
5. `node = null`이 되고, `adj[node]`는 배열의 `null`이라는 존재하지 않는 프로퍼티에 접근하는 것과 같아 `undefined`가 되며, `for (let neighbor of adj[node])`에서 `TypeError`가 발생한다.

`capacity = 1`일 때 이 결함이 반드시 드러나는 이유는 나머지 연산의 성질 때문이다. 모듈로 1 연산에서는 어떤 정수 $k$에 대해서도 $k \bmod 1 = 0$이 성립한다. 즉 `capacity = 1`인 원형 큐는 원소를 몇 개 `enqueue`하든 `tail` 값이 항상 `0`으로 고정되고, `head` 역시 같은 방식으로 움직이므로, `head`와 `tail`만으로는 "비어 있음"과 "원소 1개가 있음"을 원천적으로 구분할 수 없다.

**왜 수정 전에는 이 버그가 드러나지 않았는가**: 4.2절에서 설명한 대로, 수정 전 `length` 게터(`tail - head`)는 `n = 1`일 때 `enqueue` 직후 이미 `0`을 반환했다. 그 값 때문에 `while (queue.length !== 0)`이 처음부터 거짓으로 평가되어 반복문 몸체가 한 번도 실행되지 않았고, `dequeue()`는 아예 호출되지 않았다. 즉 `length` 게터의 결함이 `dequeue()`의 결함을 가려서, 서로 다른 두 결함이 우연히 상쇄되어 테스트를 통과시키고 있었다. 이번에 `length` 게터만 정확하게 고치자, 가려져 있던 `dequeue()`의 결함이 그제서야 실제 테스트 실패로 드러난 것이다.

**수정 방향**: `dequeue()`도 인덱스 비교 대신, 이미 정확하게 유지되고 있는 `counter`를 사용해야 한다.

```ts
dequeue() {
  if (this.counter === 0) return null;

  const item = this.arr[this.head] as number;
  this.head = (this.head + 1) % this.capacity;
  this.counter--;

  return item;
}
```

이 형태로 별도 검증한 결과, `n = 1`(`bfsShortestPath(1, [], 0)`)은 `[0]`을, 체인 그래프 `bfsShortestPath(4, [[0,1],[1,2],[2,3]], 0)`은 `[0, 1, 2, 3]`을 정확히 반환하는 것을 확인했다. `length`와 `dequeue()` 양쪽 모두 원시 인덱스 뺄셈이나 인덱스 비교 대신 이미 존재하는 `counter` 필드 하나로 판정을 일원화하면, 4장과 5장에서 다룬 결함이 모두 동시에 사라진다.
