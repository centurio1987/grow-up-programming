# 모든 단순 경로 열거 — 되돌아갈 때 표시를 지워야 다음 경로가 만들어진다

## 파트 1 — 아이디어에서 동작하는 코드까지

전체 그림을 먼저 보고, 그 그림을 읽는 데 필요한 것을 확인한 다음, 정점 나열을 전부 만들어
놓고 거르던 방법에서 간선을 따라가며 하나씩 만드는 방법까지 가는 경로를 따라갑니다.
마지막에는 실제로 동작하는 코드를 한 조각씩 만듭니다.

### 전체 컨셉

**방향 그래프**는 정점들과, 한쪽으로만 지나갈 수 있는 간선으로 이루어집니다. `u → v` 간선이
있어도 `v → u` 로는 못 가요. 이 글이 만드는 것은 출발 정점에서 도착 정점까지 가는 **모든 단순
경로**이고, 단순 경로란 같은 정점을 두 번 담지 않는 경로입니다.

```text
간선 일곱 개 — 화살표 방향으로만 지나간다

          0                 0 → 1    0 → 2
        ↙   ↘               1 → 2    1 → 4
       1 ──→ 2 ──→ 5        2 → 0    2 → 4    2 → 5
        ↘   ↙
          4                 정점 3 은 간선이 하나도 없다
                            정점 2 에서 정점 0 으로 되돌아가는 간선이 있다
```

정점 0 에서 정점 4 까지 가는 길을 전부 적으면 셋입니다. 답이 하나가 아니라 **목록 하나**인
것이 이 문제의 모양이에요.

```text
0 에서 4 까지 가는 단순 경로 셋

  0 → 1 → 2 → 4      [0, 1, 2, 4]
  0 → 1 → 4          [0, 1, 4]
  0 → 2 → 4          [0, 2, 4]
                     └ 0 → 2 → 0 → 1 → 4 는 정점 0 을 두 번 담아 단순 경로가 아니다
                       정점 5 로 가는 길은 정점 4 로 이어지지 않아 답이 아니다
```

경로들을 내놓는 순서도 정해져 있습니다. **사전식 순서** — 두 경로를 앞에서부터 정점 번호끼리
비교해, 처음으로 다른 자리에서 번호가 작은 쪽이 앞섭니다.

```text
[0, 1, 2, 4] 와 [0, 1, 4] 를 견주면

  첫 자리   0 = 0      같다
  둘째 자리 1 = 1      같다
  셋째 자리 2 < 4      여기서 갈린다 → [0, 1, 2, 4] 가 앞선다
```

이 순서는 따로 정렬하지 않아도 얻을 수 있어요. 정점마다 나가는 이웃 목록을 **번호 오름차순**
으로 두고 그 순서대로 내려가면, 먼저 완성되는 경로가 곧 사전식으로 앞선 경로입니다.

「같은 정점을 두 번 담지 않는다」를 지키는 장치는 **지금 만들고 있는 경로 안에 있는가**를
정점마다 적어 두는 표시 하나입니다. 여기가 이 글의 결정적인 자리예요 — 그 표시는 **되돌아
나오는 자리에서 반드시 지워야** 합니다.

```text
표시를 지우는가에 따라 결과가 달라진다

  0 → 1 → 4 를 담은 뒤 정점 1 로 되돌아간다
    표시를 지운다      정점 4 가 다시 열린다   → 0 → 2 → 4 도 담긴다
    표시를 안 지운다   정점 4 가 막혀 있다     → 0 → 2 → 4 를 못 담는다
                       └ 정점 4 는 첫 경로에 한 번 담겼을 뿐인데 나머지가 사라진다
```

비용은 두 조각입니다. 이웃 목록을 만들고 정렬하는 앞부분이 `V + E · log V` 규모이고, 그
뒤의 탐색은 **경로를 만들려고 들어간 재귀 횟수**에 비례해요. 그 횟수는 정점 수나 간선 수가
아니라 **그래프의 모양**이 정합니다.

### 시작하기 전에 — 이미 알고 있어야 하는 것

- **그래프를 정점과 간선으로 적는 방식.** 특히 **인접 리스트** — 정점마다 나가는 이웃 목록
  하나를 두는 표현입니다. 모르면 [`graphAdjList` 가이드](../../../data-structures/graph-repr/graphAdjList/graphAdjList-guide.mdx)를 보세요.
- **깊이 우선 방문** — 갈 수 있는 데까지 들어갔다가 더 갈 곳이 없으면 마지막 갈림길로
  되돌아가는 절차입니다. 이 글은 그 절차 위에 「경로를 적어 둔다」를 더합니다. 모르면
  [`dfsTraversal` 가이드](../dfsTraversal/dfsTraversal-guide.md)를 보세요.
- **재귀 호출이 쌓이는 방식.** 함수가 자기 자신을 부르면 부른 자리가 쌓이고, 돌아올 때
  그 자리부터 이어집니다. 이 글은 그 「돌아오는 자리」에 표시를 지우는 두 줄을 둡니다.
- **배열의 얕은 복사.** `slice()` 가 원소를 담은 새 배열을 만든다는 것. 결과에 담는 것이
  복사본이 아니면 나중에 그 배열이 바뀝니다.
- **비교 정렬의 비용이 원소 `m` 개에 `m · log m` 규모**라는 것. 이웃 목록을 정렬하는 데
  이 값을 그대로 씁니다. 모르면 [`sortArray` 가이드](../../sorting/sortArray/sortArray-guide.md)를 보세요.

앞의 셋이 흐릿하면 뒤가 어긋납니다. 이 글의 핵심은 **재귀에서 돌아오는 그 자리에서 무엇을
지우는가** 하나이고, 그 자리를 알아보려면 재귀가 어떻게 쌓이고 어떻게 풀리는지가 먼저
확인돼 있어야 해요.

### 아이디어 상세 — 되돌아갈 때 지우는 표시를 떠올리는 과정

먼저 무엇을 만드는지 고정하고 갑시다.

```ts
function dfsAllPaths(
  n: number,
  edges: [number, number][],
  source: number,
  target: number,
): number[][];
```

- 입력: 정점 수 `n`, 방향 간선 목록 `edges`, 출발 정점 `source`, 도착 정점 `target`.
  정점 번호는 0 부터 `n - 1` 까지예요.
- 출력: `source` 에서 `target` 까지의 모든 단순 경로를 사전식 순서로 담은 목록. 경로가
  하나도 없으면 빈 배열이고, `source` 와 `target` 이 같으면 길이 1 짜리 경로 하나입니다.
- 제약: 정점 1,000 개 이하, 간선 10,000 개 이하, **단순 경로 수 10,000 개 이하**, 시간 1초.
  자기 루프(`[v, v]`)와 같은 방향의 중복 간선이 들어올 수 있어요.

제약 셋째 줄이 이 문제에서만 보이는 줄입니다. 답의 개수 자체에 상한이 걸려 있어요 — 그래야
결과를 적는 것만으로 시간이 끝나지 않습니다.

```text
쓸 수 있는 정보가 셋뿐이다
  ┗ 어떤 정점에서 어디로 나갈 수 있는가      간선 목록에서 이웃 목록을 만들어 둔다
  ┗ 지금 만들고 있는 경로가 무엇인가          정점 번호를 순서대로 담은 배열 하나
  ┗ 어떤 정점이 그 경로 안에 있는가           정점마다 참·거짓 한 칸
```

이 글이 쓰는 기호는 아홉이에요. 여기서 정하고 끝까지 같은 뜻으로 씁니다.

| 기호 | 무엇인가 | 이 문제에서 |
| --- | --- | --- |
| `V` | 정점 수 | `1 ≤ V ≤ 1,000` |
| `E` | 간선 목록의 길이 | `0 ≤ E ≤ 10,000` |
| `s` | 출발 정점 번호 | `0 ≤ s < V` |
| `t` | 도착 정점 번호 | `0 ≤ t < V` |
| `adj[v]` | 정점 `v` 에서 나가는 이웃 목록 | 번호 오름차순으로 정렬해 둔다 |
| `path` | 지금 만들고 있는 경로 | 길이는 `V` 이하 |
| `onPath[v]` | 정점 `v` 가 지금 `path` 안에 있는가 | 참 또는 거짓 |
| `result` | 다 만든 경로들을 담는 목록 | 길이는 `N` |
| `N` | `s` 에서 `t` 까지의 단순 경로 수 | 제약이 10,000 이하로 묶는다 |

정점 수 `V` 와 두 끝 정점 `s`·`t` 는 코드에서 `n`·`source`·`target` 입니다.

가장 먼저 떠오르는 방법으로 시작합시다. **간선을 따라가지 않고**, 중간에 지날 정점의 나열을
가능한 순서대로 전부 만들어 놓은 다음, 그 나열이 실제로 간선으로 이어지는지 하나씩 확인하는
것이에요.

```text
정점 넷(0 · 1 · 2 · 3)에서 0 → 3 후보를 만든다. 중간에 올 수 있는 정점은 1 과 2 다

  중간이 없다      [0, 3]         간선 0 → 3 이 있는가
  중간이 하나      [0, 1, 3]      0 → 1 과 1 → 3 이 둘 다 있는가
                   [0, 2, 3]
  중간이 둘        [0, 1, 2, 3]   간선 셋이 다 있는가
                   [0, 2, 1, 3]
                   └ 후보 다섯. 정점이 하나 늘 때마다 후보가 계승만큼 늘어난다
```

이 방법은 답이 맞습니다. 그런데 후보 수가 **그래프의 모양과 상관없이** 정점 수만으로 정해져요.
정점이 `n` 개면 두 끝을 뺀 `n - 2` 개로 만들 수 있는 나열이 전부 후보가 됩니다. 제약 규모를
넣어 봅시다.

<!--proof:naive-scale-->

```text
정점 n   정점 나열 후보        간선 확인   초당 1억 번 기준
     6               65              261            0.000초
     8            1,957           11,743            0.000초
    10          109,601          876,809            0.009초
    12        9,864,101       98,641,011            0.986초
    14    1,302,061,345   15,624,736,141          156.247초
```

정점 열넷에서 벌써 156 초입니다. 제약은 정점 **1,000 개**예요. 그러면 이 156 초 안에 헛일이
얼마나 섞여 있는지 봅시다. 앞의 여섯 정점 그래프를 두 방식으로 실제로 처리해서 간선을 몇 번
확인했는지 세는 것이에요.

<!--proof:follow-vs-generate-->

```text
                            만든 것   간선 확인   결과
후보를 전부 만들어 거른다   나열 65   109         [[0,1,2,4], [0,1,4], [0,2,4]]
간선을 따라가며 만든다      진입 9    10          [[0,1,2,4], [0,1,4], [0,2,4]]
```

답은 같은데 109 가 10 이 됐습니다. 후보 65 개 중 실제로 경로가 된 것은 셋뿐이고, 나머지
62 개는 「이 나열은 간선으로 안 이어진다」를 확인하는 데만 쓰였어요. 갈라진 자리는 하나입니다.

```text
후보를 만들어 거른다      [0, 1, 3, 5, 4] 를 만들어 놓고 0 → 1 부터 확인한다
                          └ 0 → 1 은 있는데 1 → 3 이 없다. 만든 것이 통째로 버려진다

간선을 따라가며 만든다    0 에서 갈 수 있는 곳이 1 과 2 다. 1 로 간다
                          1 에서 갈 수 있는 곳이 2 와 4 다. 2 로 간다
                          └ 「갈 수 없는 곳」이 후보로 만들어지지도 않는다
```

여기서 관찰한 것은 하나예요. **경로를 앞에서부터 한 칸씩 늘려 가면, 늘리는 후보가 언제나
지금 정점의 이웃 목록 안에 있습니다.** 그러면 비용이 「후보 수」가 아니라 「실제로 내려간
횟수」가 돼요.

그런데 한 칸씩 늘리는 것만으로는 단순 경로가 보장되지 않습니다. 정점 2 에서 정점 0 으로
되돌아가는 간선이 있으면 0 → 2 → 0 → 2 → … 로 끝없이 늘어나요. **지금 경로 안에 이미 있는
정점**을 걸러야 하고, 그 「이미 있는가」를 어떻게 적을지가 다음 갈림입니다.

```text
거르지 않으면 경로가 이렇게 자란다 — 전개가 쓰는 여섯 정점 입력이다

  [0]              0 의 이웃은 2 와 1 이다.  2 로 간다
  [0, 2]           2 의 이웃은 0 과 4 와 5 다.  0 으로 간다
  [0, 2, 0]        0 의 이웃은 2 와 1 이다.  2 로 간다
  [0, 2, 0, 2]     └ 위의 두 줄이 그대로 되풀이된다. 끝나는 조건이 없다
```

가장 단순한 후보를 먼저 시험해 봅시다. 깊이 우선 방문이 쓰는 표시를 그대로 가져오는 것이에요 —
정점을 한 번 담으면 그 표시를 **끝까지 지우지 않는** 방식입니다. 순회에서는 그것이 정석이에요.

<!--proof:global-mark-->

```text
입력                    되돌아갈 때 표시를 지운다       표시를 안 지운다
다이아몬드              [[0,1,3], [0,2,3]]              [[0,1,3]]
전개가 쓰는 여섯 정점   [[0,1,2,4], [0,1,4], [0,2,4]]   [[0,1,2,4]]
```

**답이 하나만 남습니다.** 다이아몬드에서 두 경로 중 하나가, 전개 입력에서 세 경로 중 둘이
사라졌어요. 왜 그런지는 다이아몬드에서 단계별로 확인됩니다.

```text
다이아몬드 0 → 1 → 3 과 0 → 2 → 3 에서, 표시를 안 지우면

  0 을 담는다          표시 {0}         path [0]
  1 을 담는다          표시 {0, 1}      path [0, 1]
  3 을 담는다          표시 {0, 1, 3}   path [0, 1, 3]   → 결과에 담는다
  1 로 되돌아간다      표시 {0, 1, 3}   path [0, 1]      ← 표시가 그대로다
  0 으로 되돌아간다    표시 {0, 1, 3}   path [0]
  2 를 담는다          표시 {0,1,2,3}   path [0, 2]
  2 의 이웃 3 을 본다  표시돼 있다      막힌다            ← 여기서 두 번째 경로가 없어진다
```

정점 3 은 **첫 경로에 한 번 담겼을 뿐**인데 그 뒤로 영영 막혔습니다. 순회에서는 그것이 옳아요 —
정점 하나를 한 번만 처리하는 것이 순회의 정의니까요. 그런데 이 문제에서 막아야 하는 것은
「이미 처리한 정점」이 아니라 **「지금 만들고 있는 경로 안에 있는 정점」**입니다.

> 표시는 정점이 **`path` 안에 있는 동안에만** 켜져 있어야 한다. 그러면 표시를 켜는 자리는
> `path` 에 담는 그 자리이고, 지우는 자리는 `path` 에서 빼는 그 자리다.

```text
두 표시가 뜻하는 것이 다르다

  순회의 표시     "이 정점은 이미 처리했다"          한 번 켜면 안 지운다
  이 글의 표시    "이 정점은 지금 경로 안에 있다"    경로에서 빠질 때 지운다
                  └ 켜져 있는 정점의 모임이 path 안의 정점 모임과 언제나 같다
```

이 정의가 각 상태의 크기를 그대로 정합니다.

```text
각 상태가 얼마나 커지는가

  path 의 길이           같은 정점을 두 번 못 담는다              V 이하
  표시가 켜진 정점 수    path 의 길이와 언제나 같다               V 이하
  재귀 깊이              path 의 길이와 언제나 같다               V 이하
  result 의 길이         경로 하나가 완성될 때마다 하나씩 늘어난다  N
```

**상태가 실제로 유지되는지를 값으로 확인해 봅시다.** 쉬운 경우는 갈림이 없는 자리예요 —
정점 5 처럼 나가는 이웃이 없으면 담았다가 바로 빼는 것으로 끝납니다. 불안한 경우는 같은
정점이 여러 경로에 함께 들어 있는 자리예요. 전개 입력의 정점 4 가 세 경로에 전부 들어 있습니다.

```text
정점 4 가 세 번 담기는 과정 — 표시를 지우는 자리를 함께 적는다

  0 → 1 → 2 → 4     담는다   표시 {0,1,2,4}   결과 [[0,1,2,4]]
  4 에서 되돌아간다  뺀다     표시 {0,1,2}     ← 여기서 4 가 다시 열린다
  2 에서 되돌아간다  뺀다     표시 {0,1}
  0 → 1 → 4         담는다   표시 {0,1,4}     결과 둘
  4 에서 되돌아간다  뺀다     표시 {0,1}
  1 에서 되돌아간다  뺀다     표시 {0}
  0 → 2 → 4         담는다   표시 {0,2,4}     결과 셋
                              └ 4 를 세 번 담았고 그 사이마다 정확히 한 번씩 지웠다
```

왜 이것이 맞는지는 재귀가 끝나는 조건이 말해 줍니다. `walk(u)` 한 겹은 자기 이웃 목록을 한
번 확인하면 반드시 반환하고, 반환 직전에 자기가 켠 표시 하나를 지웁니다. 그러니 한 겹이 켜고
지우는 것이 정확히 한 개씩이라 `path` 와 표시가 어긋날 자리가 없어요.

```text
남은 갈림 — 표시를 어디서 지우는가
  지우지 않는다                 순회의 방식 그대로다
  표시를 아예 하지 않는다       걸러야 할 것을 안 거른다
  지우지만 경로에서 안 뺀다     표시와 path 가 어긋난다
  되돌아가는 자리에서 지운다    켠 자리와 지우는 자리가 짝을 이룬다
```

넷을 같은 두 입력에 실제로 실행해 결과를 냅니다.

<!--proof:unmark-placement-->

```text
표시를 어디서 지우는가       다이아몬드               전개가 쓰는 여섯 정점
지우지 않는다                [[0,1,3]]                [[0,1,2,4]]
표시를 아예 하지 않는다      [[0,1,3], [0,2,3]]       RangeError
지우지만 경로에서 안 뺀다    [[0,1,3], [0,1,3,2,3]]   [[0,1,2,4], [0,1,2,4,5,4], [0,1,2,4,5,4,2,4]]
되돌아가는 자리에서 지운다   [[0,1,3], [0,2,3]]       [[0,1,2,4], [0,1,4], [0,2,4]]
```

**두 입력에서 모두 맞는 것은 마지막 줄 하나뿐입니다.** 둘째 줄이 특히 볼 만해요 — 다이아몬드
에서는 표시를 아예 안 해도 `[[0,1,3], [0,2,3]]` 이 그대로 나옵니다. 그 그래프에는 되돌아가는
간선이 없어서 같은 정점을 두 번 담을 길 자체가 없기 때문이에요. 전개 입력에는 정점 2 에서
정점 0 으로 가는 간선이 있고, 거기서 재귀가 끝나지 않아 `RangeError` 가 납니다.

```text
셋째 줄이 내는 값도 함께 보자 — 「지우지만 경로에서 안 뺀다」

  다이아몬드에서   [[0,1,3], [0,1,3,2,3]]
                   └ 두 번째 경로 앞에 첫 경로의 흔적 [0,1,3] 이 남아 있다
                     표시는 지웠으니 막히지는 않는데, path 가 줄지 않아 앞부분이 섞인다
```

**절차가 나왔습니다.** 간선 목록을 이웃 목록으로 옮기면서 자기 루프를 빼고 같은 이웃을 한 번만
담고 번호 오름차순으로 정렬한 뒤, 출발 정점부터 재귀로 내려가되 한 겹에 들어갈 때 표시를 켜고
경로에 담고, 도착 정점이면 경로를 복사해 결과에 담고, 되돌아가는 자리에서 표시를 지우고
경로에서 빼는 것이에요.

### 수행으로 알아보는 알고리즘 — 여섯 정점에서 경로 셋을 만든다

아이디어를 세웠으니 이제 **실제로 동작하는 코드**로 옮겨 봅시다. 입력 하나를 잡고 끝까지 가되,
조각마다 그 조각만 실행해서 나온 값을 확인하고 넘어갑니다.

```ts
const n = 6;
const edges: [number, number][] = [
  [0, 2], [0, 1], [1, 2], [1, 4], [2, 0], [2, 4], [2, 5], [5, 5],
];
const source = 0;
const target = 4;
// 이 절이 끝나면 [[0,1,2,4], [0,1,4], [0,2,4]] 가 나와야 한다
```

이 입력을 고른 이유는 넷입니다. `[0,2]` 가 `[0,1]` 보다 먼저 적혀 있어 **정렬이 실제로 일하는
것**이 확인되고, 정점 2 에서 정점 0 으로 **되돌아가는 간선**이 있어 표시가 막는 갈래가 실행되며,
정점 5 는 나가는 간선이 없어 **도착 정점에 도달하지 못하고 되돌아오는 갈래**가 실행되고, 자기
루프 `[5,5]` 가 들어 있어 그것을 빼는 자리도 함께 보입니다.

```text
dfsAllPaths(n, edges, source, target):
    간선 [u, v] 마다 u ≠ v 면 u 의 이웃 모임에 v 를 넣는다
    이웃 모임마다 번호 오름차순 목록으로 만든다
    onPath 를 전부 거짓으로, path 와 result 를 빈 배열로 둔다

    walk(u):
        onPath[u] ← 참, path 뒤에 u 를 담는다
        u 가 target 이면  path 를 복사해 result 에 담는다        ① 도착 정점
        아니면 adj[u] 의 v 마다:
            onPath[v] 가 참이면 건너뛴다                          ② 경로 안에 있는 이웃
            아니면 walk(v)                                        ③ 경로에 없는 이웃
        onPath[u] ← 거짓, path 끝에서 하나를 뺀다

    walk(source) 를 부르고 result 를 반환한다
```

#### 1. 간선 목록을 오름차순 이웃 목록으로 만든다

간선 목록은 「누가 누구로 가는가」를 담고 있지만 「정점 2 에서 어디로 갈 수 있는가」를 묻기에는
불편합니다. 정점마다 나가는 이웃 목록을 하나씩 만들고, 그 목록에서 자기 루프를 빼고 같은
이웃을 한 번만 담은 뒤 번호 오름차순으로 정렬해 둡니다.

```ts
const sets: Set<number>[] = Array.from({ length: n }, () => new Set<number>());
for (const [u, v] of edges) {
  if (u === v) continue;
  (sets[u] as Set<number>).add(v);
}
const adj: number[][] = sets.map((s) => [...s].sort((a, b) => a - b));
```

실행하면 이렇게 나옵니다. `adj[0]` 이 만들어질 때는 `[2, 1]` 이었다가 정렬 뒤에 `[1, 2]` 가
되는 것과, 자기 루프 `[5,5]` 가 빠져 `adj[5]` 가 비는 것이 함께 확인돼요.

<!--proof:adj-build-->

```text
         정렬 전     정렬 후     칸 수
adj[0]   [2, 1]      [1, 2]          2
adj[1]   [2, 4]      [2, 4]          2
adj[2]   [0, 4, 5]   [0, 4, 5]       3
adj[3]   []          []              0
adj[4]   []          []              0
adj[5]   []          []              0
합                                   7
```

같은 이웃을 한 번만 담아도 되는 이유는 반환하는 것이 **간선이 아니라 정점 나열**이기
때문입니다. 같은 `u → v` 간선이 몇 개든 그것으로 만들어지는 정점 나열은 하나예요.

#### 멈춤 — 정렬을 빼도 경로의 모임은 그대로다

`sort` 를 빼면 어떻게 될까요? 코드는 그대로 실행되고 예외도 안 납니다. 그리고 **경로를 하나도
잃지 않아요** — 이웃을 어떤 순서로 보든 그 이웃으로 갈라지는 가지는 전부 실행되기 때문입니다.

<!--proof:unsorted-order-->

```text
                           정렬한다                        정렬하지 않는다
결과                       [[0,1,2,4], [0,1,4], [0,2,4]]   [[0,2,4], [0,1,2,4], [0,1,4]]
사전식으로 다시 정렬하면   [[0,1,2,4], [0,1,4], [0,2,4]]   [[0,1,2,4], [0,1,4], [0,2,4]]
경로의 모임이 같은가       —                               같다
```

셋째 줄이 그 자리입니다. 두 결과를 사전식으로 다시 정렬하면 **글자 그대로 같아요**. 갈리는
것은 순서뿐이고, 그래서 「경로를 다 찾았는가」만 확인하는 테스트는 `sort` 를 지워도 통과합니다.

```text
정렬을 빼면 왜 순서만 갈리는가

  adj[0] = [2, 1]   먼저 2 로 내려간다   → [0, 2, 4] 가 첫 번째로 담긴다
  adj[0] = [1, 2]   먼저 1 로 내려간다   → [0, 1, 2, 4] 가 첫 번째로 담긴다
                    └ 두 갈래 다 실행되므로 담기는 경로의 모임은 같다
```

문제 지문이 「사전식 순서로 정렬해 돌려준다」고 못 박은 것이 이 자리예요. 끝나고 결과 목록을
따로 정렬해도 되지만, 이웃 목록을 한 번 정렬해 두면 그 비용이 `N` 개 경로가 아니라 `E` 개
간선에만 붙습니다.

#### 2. 경로와 표시와 결과를 준비한다

「이 정점이 지금 경로 안에 있는가」를 배열 한 칸으로 담습니다. 경로 자체는 정점 번호를 순서대로
담는 배열이고, 다 만든 경로는 따로 모아요.

```ts
const onPath: boolean[] = Array.from({ length: n }, () => false);
const path: number[] = [];
const result: number[][] = [];
```

실행하면 이렇게 나옵니다. 출발 정점은 아직 표시가 꺼져 있어요 — 표시는 재귀 한 겹에 **들어갈
때** 켭니다.

```text
onPath = [false, false, false, false, false, false]
path   = []
result = []
         └ 아직 walk 를 부르지 않았다. onPath[0] 도 거짓이다
```

배열 셋을 처음에 한 번 만들고 그 뒤로는 새로 잡지 않습니다. 재귀 한 겹이 쓰는 것은 `path` 의
끝 한 칸과 `onPath` 의 한 칸뿐이라, 깊이가 아무리 깊어져도 새로 잡는 칸이 늘지 않아요.

#### 3. 재귀 한 겹을 진입 · 갈래 · 되돌아가기로 적는다

여기가 경로를 만드는 자리입니다. 한 겹에 들어가면 표시를 켜고 경로에 담고, 갈래 셋 중 하나를
실행한 뒤, 켠 표시를 지우고 경로에서 뺍니다.

```ts
const walk = (u: number): void => {
  onPath[u] = true;
  path.push(u);

  if (u === target) {
    // ① 도착 정점이다 — 지금 경로를 복사해 담고 여기서 더 내려가지 않는다.
    result.push(path.slice());
  } else {
    for (const v of adj[u] as number[]) {
      // ② 지금 경로 안에 있는 정점이다 — 다시 담으면 단순 경로가 아니다.
      if (onPath[v] === true) continue;

      // ③ 아직 경로에 없는 정점이다 — 한 칸 내려간다.
      walk(v);
    }
  }

  onPath[u] = false;
  path.pop();
};
```

가장 중요한 것은 **맨 위 두 줄과 맨 아래 두 줄이 짝을 이룬다**는 것입니다. 위에서 켠 것을
아래에서 지우고, 위에서 담은 것을 아래에서 빼요. 넷 중 하나라도 빠지면 다음 경로가 어긋납니다.

```text
walk(u) 한 겹의 생애

  들어간다              onPath[u] ← 참        path 뒤에 u 를 담는다
      갈래 ①           u 가 target 이다      path 를 복사해 result 에 담는다
      갈래 ②           이웃이 경로 안에 있다 건너뛴다
      갈래 ③           이웃이 경로에 없다    walk(v) 로 한 칸 내려간다
  되돌아간다            onPath[u] ← 거짓      path 끝에서 하나를 뺀다
                        └ 켠 것 하나와 지우는 것 하나가 정확히 맞물린다
```

갈래 ① 에서 **더 내려가지 않는 것**도 규칙입니다. 도착 정점을 지나 더 가면 마지막 정점이
`target` 이 아니게 되어 우리가 세는 경로가 아니에요. `if` 와 `else` 로 갈라 두는 이유가 그것입니다.

#### 멈춤 — 경로를 복사하지 않고 담으면 결과가 전부 빈 배열이 된다

`path.slice()` 대신 `path` 를 그대로 담으면 어떻게 될까요? 타입도 맞고 실행도 되고, 담기는
개수까지 정확히 맞습니다. 경로가 셋이면 결과의 길이도 셋이에요.

<!--proof:shared-array-->

```text
입력                    복사해서 담는다                 그대로 담는다
다이아몬드              [[0,1,3], [0,2,3]]              [[], []]
전개가 쓰는 여섯 정점   [[0,1,2,4], [0,1,4], [0,2,4]]   [[], [], []]
```

**길이는 맞는데 내용이 전부 비어 있습니다.** `path` 는 재귀가 진행되는 동안 계속 바뀌는 배열
하나이고, 그것을 그대로 담으면 결과의 모든 칸이 **같은 배열**을 가리켜요. 재귀가 다 끝나면
그 배열은 비어 있으므로 결과가 `[[], [], []]` 가 됩니다.

```text
같은 배열을 가리키는 것과 복사본을 담는 것

  그대로 담는다   result = [ path, path, path ]     세 칸이 같은 배열이다
                  path 가 마지막에 [] 가 된다        세 칸이 다 [] 로 확인된다
  복사해 담는다   result = [ [0,1,2,4], [0,1,4], [0,2,4] ]
                  └ 담는 순간의 내용을 새 배열로 떠 둔다. 뒤에 path 가 바뀌어도 그대로다
```

이 실수가 잘 안 잡히는 이유는 **개수가 맞기 때문**이에요. 「경로를 세 개 찾았는가」만 확인하는
테스트는 통과하고, 내용을 확인해야 그때 갈립니다.

| T15 | 5 | `onPath[5]` 가 **거짓** → ③ | `[0,2,5]` | 셋 |
| T16 | 5 · 2 · 0 | 이웃을 다 확인했다 → 되돌아간다 | `[]` | 셋 |

**세 갈래가 모두 나왔습니다.** `walk` 에 들어간 것은 아홉 번이고, 그중 ① 이 세 번, ② 가 두 번,
③ 이 다섯 번이에요. 반환값은 `[[0,1,2,4], [0,1,4], [0,2,4]]` 입니다.

```text
①  도착 정점이다             T5 · T9 · T13         세 번 = 경로 수
②  경로 안에 있는 이웃이다   T4 · T12              두 번 = 되돌아가는 간선 2 → 0 을 본 횟수
③  경로에 없는 이웃이다      T2 · T3 · T7 · T11 · T15   다섯 번

walk 진입 9 = 1(출발) + ③ 다섯 번 + ① 이 만든 내려가기 세 번
```

여기서 눈여겨볼 것은 T7 과 T15 입니다. 정점 5 에 두 번 들어갔는데 두 번 다 아무것도 담지 못하고
되돌아왔어요. 정점 5 에서 정점 4 로 가는 간선이 없기 때문인데, **그것을 미리 알 방법이 이
절차에는 없습니다.** 들어가 봐야 알아요.

#### 멈춤 — 형제 편은 재귀를 버렸는데 이 편은 왜 재귀로 적는가

같은 저장소의 [`dfsTraversal` 가이드](../dfsTraversal/dfsTraversal-guide.md)는 깊이 우선 방문을
**반복문과 스택 배열**로 적습니다. 재귀로 적으면 호출 깊이가 정점 수만큼 쌓이고, 그 편의 제약이
정점 100,000 개라 실행 환경의 호출 한도를 넘기 때문이에요. 그런데 이 편은 재귀로 적습니다.

<!--proof:recursion-depth-->

```text
정점 수   경로 수      경로 길이
  1,000   1            1,000
100,000   RangeError   —
```

갈리는 것은 **제약의 정점 수 상한** 하나입니다. 이 문제는 한 경로가 같은 정점을 두 번 담지
못하므로 `path` 의 길이가 곧 재귀 깊이이고, 그 길이는 정점 수를 넘지 못해요. 정점 수 상한이
1,000 이니 깊이도 1,000 이하입니다.

```text
깊이의 상한이 어디서 오는가

  dfsTraversal   깊이 = 지금 들어가 있는 경로의 길이   제약이 정점 100,000 개다
  이 편          깊이 = path 의 길이 ≤ 정점 수         제약이 정점 1,000 개다
                 └ 같은 절차인데 제약이 달라서 구현이 갈린다
```

한도가 정확히 몇인지는 실행 환경이 정하고, 위 표의 두 줄 사이 어딘가에 있습니다. 제약이
바뀌어 정점 수가 100,000 까지 늘어난다면 이 편도 반복문으로 옮겨야 해요.

#### 5. 전체 코드

조각을 하나로 잇습니다. 위에서 확인한 것 말고 새로 들어간 것은 `walk(source)` 를 부르고
`result` 를 그대로 반환하는 마지막 두 줄뿐이에요.

```ts
export function dfsAllPaths(
  n: number,
  edges: [number, number][],
  source: number,
  target: number,
): number[][] {
  // 자기 루프는 단순 경로에 쓸 수 없고, 같은 이웃이 여러 번 있어도 정점 나열은 하나다.
  const sets: Set<number>[] = Array.from(
    { length: n },
    () => new Set<number>(),
  );
  for (const [u, v] of edges) {
    if (u === v) continue;
    (sets[u] as Set<number>).add(v);
  }

  // 이웃을 번호 오름차순으로 둔다. 이 순서가 그대로 결과의 사전식 순서가 된다.
  const adj: number[][] = sets.map((s) => [...s].sort((a, b) => a - b));

  // `onPath[v]` 는 정점 `v` 가 **지금 만들고 있는 경로 안에** 있는가다.
  const onPath: boolean[] = Array.from({ length: n }, () => false);
  const path: number[] = [];
  const result: number[][] = [];

  const walk = (u: number): void => {
    // 진입 — 표시를 켜고 경로 끝에 붙인다.
    onPath[u] = true;
    path.push(u);

    if (u === target) {
      // ① 도착 정점이다 — 지금 경로를 복사해 담고 여기서 더 내려가지 않는다.
      result.push(path.slice());
    } else {
      for (const v of adj[u] as number[]) {
        // ② 지금 경로 안에 있는 정점이다 — 다시 담으면 단순 경로가 아니다.
        if (onPath[v] === true) continue;

        // ③ 아직 경로에 없는 정점이다 — 한 칸 내려간다.
        walk(v);
      }
    }

    // 되돌아가는 자리 — 켠 표시를 지우고 경로 끝에서 뺀다. 진입과 정확히 짝을 이룬다.
    onPath[u] = false;
    path.pop();
  };

  walk(source);
  return result;
}
```

실행하면 이렇게 나옵니다.

<!--proof:walk-result-->

```text
dfsAllPaths(6, [[0,2],[0,1],[1,2],[1,4],[2,0],[2,4],[2,5],[5,5]], 0, 4)   →   [[0,1,2,4], [0,1,4], [0,2,4]]
dfsAllPaths(4, [[0,1],[0,2],[1,3],[2,3]], 0, 3)                           →   [[0,1,3], [0,2,3]]
dfsAllPaths(4, [[0,1],[0,2],[1,2],[1,3],[2,3]], 0, 3)                     →   [[0,1,2,3], [0,1,3], [0,2,3]]
dfsAllPaths(3, [[0,1],[1,2],[2,0],[0,2]], 0, 2)                           →   [[0,1,2], [0,2]]
dfsAllPaths(3, [[0,1]], 0, 2)                                             →   []
dfsAllPaths(3, [[0,1],[1,2]], 1, 1)                                       →   [[1]]
dfsAllPaths(1, [], 0, 0)                                                  →   [[0]]
```

### 알아 두면 좋은 개념 — 출력 민감 알고리즘

파트 1 에서 센 값 둘을 나란히 놓아 봅시다. 전개 입력은 정점 여섯에 간선 일곱인데 답이 세
줄이었고, 7×7 격자는 정점 예순넷에 간선 112 개인데 답이 3,432 줄입니다. **입력은 조금 커졌는데
출력이 천 배 커졌어요.**

| | 정점 수 | 간선 수 | 경로 수 `N` | 출력에 적는 정점 번호 수 |
| --- | --- | --- | --- | --- |
| 전개가 쓰는 그래프 | 6 | 7 | 3 | 10 |
| 3×3 격자 | 16 | 24 | 20 | 140 |
| 7×7 격자 | 64 | 112 | 3,432 | 51,480 |

이런 문제에서 비용을 입력 크기만으로 적으면 아무것도 말하지 못합니다. 정점 예순넷짜리 그래프가
5 만 개가 넘는 숫자를 적어야 하니까요. **비용을 입력 크기와 출력 크기 둘로 적는 알고리즘**을
출력 민감 알고리즘이라고 부릅니다.

```text
비용을 무엇으로 적는가

  보통의 알고리즘     f(입력 크기)              정렬은 n log n
  출력 민감 알고리즘  f(입력 크기, 출력 크기)   이 편은 V + E log V + (탐색) + L
                      └ L 은 출력에 적는 숫자의 개수. 어떤 절차도 L 아래로 못 내려간다
```

같은 이름이 이 편 밖에서도 그대로 쓰입니다. 볼록 껍질을 구하는 문제에서 껍질 위의 점이 `h` 개일
때 `n log h` 로 끝내는 절차가 그렇고, 데이터베이스가 조인 결과를 하나씩 내보내는 절차도
그렇습니다. 셋 다 **답을 적는 데 드는 비용이 바닥**이고, 그 바닥 위에 무엇이 얼마나 더 붙는지가
절차를 가르는 자리예요.

## 파트 2 — 적용 조건 · 보장 · 비용

파트 1 에서 만든 것을 따져 봅니다. 어떤 문제에 이것을 쓰는지, 식으로 무엇이 나오는지, 무엇이
매 순간 참으로 남는지, 그리고 비용이 얼마인지 순서로 봅니다.

### 이 알고리즘이 최적의 솔루션인 경우

#### 최적인 문제의 모양

세 조건이 함께 맞을 때입니다.

- **답이 하나가 아니라 목록입니다.** 「경로가 있는가」나 「가장 짧은 경로가 무엇인가」가 아니라
  「경로를 전부 적어라」를 묻는 문제예요. 하나만 필요하면 훨씬 적은 비용으로 끝납니다.
- **답의 개수에 상한이 걸려 있습니다.** 이 문제는 경로 수를 10,000 개 이하로 묶었어요. 그
  상한이 없으면 출력만으로 시간이 끝납니다.
- **경로가 단순 경로여야 합니다.** 같은 정점을 두 번 담아도 된다면 답이 무한히 많아지고,
  그때는 열거가 아니라 다른 문제가 돼요.

```text
세 조건이 코드의 모양을 그대로 정한다
  답이 목록이다        → result 배열 하나를 두고 완성될 때마다 담는다
  개수에 상한이 있다   → 결과를 다 모아 두고 마지막에 반환해도 된다
  단순 경로다          → onPath 한 칸으로 「지금 경로 안에 있는가」를 판정한다
```

가장 짧은 경로 하나만 필요한 문제에 이 절차를 쓰면 무엇이 어긋나는지는 값으로 확인됩니다.
7×7 격자에서 최단 경로의 길이는 열다섯인데, 이 절차는 그 길이의 경로를 3,432 개 전부 만들어요.

```text
같은 격자에서 두 질문의 답
  모든 단순 경로       3,432 줄, 숫자 51,480 개    전부 길이 15 로 같다
  가장 짧은 경로 하나  1 줄, 숫자 15 개            너비 우선 탐색이 정점 64 개만 보고 끝낸다
                       └ 앞은 답을 다 적는 것이고 뒤는 하나만 적는 것이다
```

하나만 필요하면 꺼내는 순서를 거리 오름차순으로 만드는 절차를 씁니다.
[`bfsShortestPath` 가이드](../bfsShortestPath/bfsShortestPath-guide.md)가 그 절차예요.

#### 문제에서 이것을 떠올리게 하는 단서

```text
지문에 이런 말이 보이면
  "모든 경로를 출력"   "가능한 모든 방법을 나열"   "빠짐없이 뽑아"
  "같은 지점을 두 번 지나지 않는다"               "사전식 순서로 정렬해"

제약에 이런 모양이 보이면
  답의 개수 자체에 상한이 있다        ← 열거 문제라는 뜻이다
  정점 수가 1,000 규모로 작다         ← 정점 수가 아니라 경로 수가 비용을 정한다는 뜻이다
  경로 수 상한이 정점 수보다 훨씬 크다 ← 답을 적는 것이 비용의 바닥이라는 뜻이다
```

반대로 **「최소 몇 번 만에」·「경로가 존재하는가」** 가 보이면 이 단서는 해당하지 않습니다.
그때는 경로를 하나만 만들거나 도달 가능성만 판정하면 되고, 둘 다 `V + E` 규모로 끝나요.
「경로 수만 세어라」도 이 절차의 자리가 아닙니다 — 방향 그래프에서 단순 경로의 수를 세는 것은
경로를 만들지 않고는 알 수 없는 어려운 문제이지만, 사이클이 없는 그래프라면 정점마다 값을
하나씩 쌓는 것으로 `V + E` 에 끝납니다.

#### 실제로 쓰이는 곳

- **NetworkX `all_simple_paths`** — 이 글이 만든 것과 같은 함수입니다. 문서 문자열이
  *"This algorithm uses a modified depth-first search to generate the paths. A single path
  can be found in $O(V+E)$ time but the number of simple paths in a graph can be very large."*
  라 적어 「깊이 우선 탐색을 고쳐 쓴다」와 「경로 수가 매우 커질 수 있다」를 함께 밝힙니다.
  실제 열거는 `_all_simple_edge_paths` 가 하는데, 재귀가 아니라 **명시 스택**이고
  (`stack = [iter([(None, source)])]`), 지금 경로를 `current_path` 라는 사전 하나로 담아
  되돌아갈 때 `stack.pop()` 과 `current_path.popitem()` 을 짝지어 실행합니다 — 이 글의
  `path.pop()` 과 `onPath[u] = false` 가 하는 일을 한 자료구조가 겸하는 모양이에요.
  ([networkx/algorithms/simple_paths.py](https://raw.githubusercontent.com/networkx/networkx/main/networkx/algorithms/simple_paths.py), 조회 2026-08-29)
- **igraph `igraph_get_all_simple_paths`** — C 로 쓰인 그래프 라이브러리의 같은 기능입니다.
  문서 주석이 *"A path is simple if its vertices are unique, i.e. no vertex is visited more
  than once."* 로 단순 경로를 정의하고, *"Note that potentially there are exponentially many
  paths between two vertices of a graph, and you may run out of memory when using this
  function when the graph has many cycles."* 로 경로 수가 지수적으로 커진다는 것을 경고합니다.
  표시는 비트 배열 하나이고 `IGRAPH_BIT_SET(added, nei)` 로 켰다가
  `IGRAPH_BIT_CLEAR(added, up)` 로 지웁니다.
  ([src/paths/simple_paths.c](https://raw.githubusercontent.com/igraph/igraph/master/src/paths/simple_paths.c), 조회 2026-08-29)

두 곳 다 **표시를 켜는 자리와 지우는 자리를 짝지어** 두었고, 둘 다 재귀가 아니라 명시 스택으로
깊이를 관리합니다. 라이브러리는 입력 크기를 미리 알 수 없어서 호출 한도에 걸리는 구현을 둘 수
없기 때문이에요.

#### 경쟁 설계와의 대조

같은 목표를 노리는 **다른 절차**가 있어요 — **도달 가능성 가지치기**입니다. 재귀 한 겹에 들어갈
때마다, 지금 경로 위의 정점을 뺀 그래프에서 도착 정점에 도달할 수 있는 정점을 역방향 간선으로
전부 표시하고, 표시되지 않은 이웃으로는 아예 내려가지 않아요.

```text
이 가이드            정점 5 로 내려간다 → adj[5] 가 비어 있다 → 되돌아간다
                     └ 들어가 봐야 막다른 자리인 것을 안다

도달 가능성 가지치기 정점 2 에서 역방향 탐색을 한 번 실행한다
                     → 정점 4 에 도달할 수 있는 것은 {0, 1, 2} 뿐이다
                     → 정점 5 로는 내려가지 않는다
```

같은 세 그래프에 둘을 걸고 **진입한 노드 · 이웃 검사 · 새로 잡는 칸**을 셌습니다. 전개가 쓰는
여섯 정점 그래프에서는 진입한 노드가 9 대 7 이라 둘밖에 안 갈리는데, 그 차이가 설계의 성질에서
온 것인지 그래프가 작아서 그런 것인지 구분되지 않아요. 그래서 간선 수를 맞춘 두 그래프를 더
씁니다 — 5×5 격자(정점 36 · 간선 60)와 덫 그래프(정점 10 · 간선 58)입니다.

```text
덫 그래프 — 정점 0 에서 두 갈래가 갈린다

  0 → 9              도착 정점으로 바로 간다        경로는 이것 하나뿐이다
  0 → 1              정점 1 … 8 이 서로 전부 이어진 무리로 들어간다
                     └ 그 무리에서 정점 9 로 가는 간선은 하나도 없다
                       무리 안의 단순 경로는 계승만큼 많은데 그중 답은 0 개다
```

| 설계 | 격자 · 진입한 노드 | 격자 · 이웃 검사 | 덫 · 진입한 노드 | 덫 · 이웃 검사 | 새로 잡는 칸 |
| --- | --- | --- | --- | --- | --- |
| 이 가이드의 절차 | 923 | **922** | 13,702 | 95,902 | **0** |
| 도달 가능성 가지치기 | 923 | 26,456 | **2** | **3** | 24,156 |

**순서가 뒤집힙니다.** 격자에서는 이 가이드가 이웃 검사 922 대 26,456 으로 스물여덟 배 적은데,
덫 그래프에서는 진입한 노드가 13,702 대 2 이고 이웃 검사가 95,902 대 3 이에요. 격자에서 뒤집히는
이유는 그 그래프에 **막다른 자리가 하나도 없기** 때문입니다 — 어느 정점에서 오른쪽·아래로
계속 가도 오른쪽 아래 끝에 도달하므로, 역방향 탐색이 매번 「전부 갈 수 있다」만 확인하고 끝나요.

```text
축을 넷으로 갈라 적으면
                        이 가이드      도달 가능성 가지치기
  격자 · 진입한 노드    923            923            ← 같다. 막다른 자리가 없다
  격자 · 이웃 검사      922            26,456         ← 이쪽이 적다
  덫 · 진입한 노드      13,702         2              ← 저쪽이 적다
  덫 · 이웃 검사        95,902         3              ← 저쪽이 적다
  새로 잡는 칸          0              24,156         ← 이쪽이 적다
```

**우열이 반대가 되는 조건은 「막다른 가지의 비율」입니다.** 진입한 노드 중 경로를 하나도 못
만드는 것이 몇 퍼센트인가로 갈려요. 격자에서는 그 비율이 0 이라 역방향 탐색이 통째로 헛일이
되고, 덫 그래프에서는 99.98% 라 한 번의 역방향 탐색이 13,700 번의 진입을 없앱니다. 이 가이드가
받는 축은 두 가지예요 — 노드마다 표시 배열을 새로 잡지 않아 **새로 잡는 칸이 0** 이고, 코드가
스무 줄 남짓으로 끝납니다.

### 수식 정의와 유도

방향 그래프 $G=(V,E)$ 에서 정점 $u$ 가 나가는 간선으로 이어지는 정점들의 모임을 $N^{+}(u)$ 라
적고, 그 크기를 $\deg^{+}(u)$ 라 적습니다. 출발 정점 $s$ 에서 도착 정점 $t$ 까지의 단순 경로
모임은 아래와 같아요.

$$\mathcal{P}(s,t)=\{(v_0,v_1,\dots,v_k)\;:\;v_0=s,\;v_k=t,\;(v_i,v_{i+1})\in E,\;i\neq j \Rightarrow v_i\neq v_j\}$$

| 이름 | 정의 | 무엇을 재는가 |
| --- | --- | --- |
| $N$ | $\lvert\mathcal{P}(s,t)\rvert$ | 답의 줄 수 |
| $L$ | $\sum_{p\in\mathcal{P}(s,t)}\lvert p\rvert$ | 출력에 적는 정점 번호의 개수 |
| $R$ | `walk` 에 진입한 횟수 | 절차가 실제로 만든 부분 경로의 수 |

셋을 전개 입력에 넣어 검산해 봅시다.

<!--proof:math-verify-->

```text
이름   무엇                                            전개 입력에서
N      단순 경로의 수                                  3
L      경로 길이의 합 = 출력에 적는 정점 번호의 개수   10
R      walk 에 진입한 횟수                             9
```

$N=3$ 은 경로 셋이고 $L=4+3+3=10$ 입니다. $R=9$ 는 그보다 크고, 그 차이가 정점 5 로 두 번
내려갔다 되돌아온 T7·T15 와 출발 정점의 진입에서 옵니다. **$N$ 과 $L$ 은 답이 정하지만 $R$ 은
그래프의 모양이 정한다** — 이것이 아래 두 유도가 갈라 보이는 것이에요.

먼저 $N$ 이 얼마나 커질 수 있는지를 닫힌 형태로 냅니다. 서로 다른 두 정점 사이에 양쪽 방향
간선이 전부 있는 그래프를 잡으면, $s$ 에서 $t$ 로 가는 단순 경로 하나는 **나머지 $n-2$ 개
정점 중 몇 개를 골라 순서까지 정한 나열** 하나와 일대일로 대응합니다.

```text
n = 5, s = 0, t = 4 — 가운데에 올 수 있는 정점이 1·2·3 셋이다

  [0, 4]         ↔  ()        중간을 하나도 안 고른 나열
  [0, 2, 4]      ↔  (2)
  [0, 3, 1, 4]   ↔  (3, 1)    순서가 다르면 다른 경로다
  [0, 1, 3, 4]   ↔  (1, 3)
                 └ 양쪽 방향 간선이 다 있으니 어떤 나열이든 실제 경로가 된다
```

$$N(n)=\sum_{k=0}^{n-2}\frac{(n-2)!}{(n-2-k)!}$$

```text
n = 6 에서 이 합을 손으로 센다 — 두 끝을 뺀 정점이 넷이다

  중간 0 개   4!/4! = 1     경로 [s, t]
  중간 1 개   4!/3! = 4     중간에 올 정점을 넷 중 하나 고른다
  중간 2 개   4!/2! = 12    고른 둘의 순서까지 다르면 다른 경로다
  중간 3 개   4!/1! = 24
  중간 4 개   4!/0! = 24
              └ 합 65. 앞 절의 후보 나열 수와 같은 값이다
```

합의 첨자를 $j=n-2-k$ 로 바꾸면 분모가 $j!$ 이 되고, $(n-2)!$ 을 합 밖으로 뺄 수 있어요.

$$N(n)=\sum_{j=0}^{n-2}\frac{(n-2)!}{j!}=(n-2)!\sum_{j=0}^{n-2}\frac{1}{j!}$$

```text
남은 합은 e 의 급수를 n-2 항에서 끊은 것이다

  e = 1/0! + 1/1! + 1/2! + 1/3! + …          무한히 이어진다
  위 합 = 그 급수의 앞 (n-1) 항                뒤가 잘려 있다
          └ 그러니 N(n) 은 e·(n-2)! 보다 잘린 만큼 작다
```

잘린 꼬리에 $(n-2)!$ 을 곱한 값이 1 보다 작다는 것을 보이면 내림으로 값이 정해집니다. 꼬리의
첫 항이 $\frac{1}{n-1}$ 이고 그 뒤로 각 항이 $\frac{1}{n}$ 배보다 작게 줄어드므로, 등비급수로
묶어 위에서 눌러요.

$$(n-2)!\sum_{j=n-1}^{\infty}\frac{1}{j!}<\frac{1}{n-1}\cdot\frac{1}{1-\frac{1}{n}}=\frac{n}{(n-1)^2}\le 1 \quad (n\ge 3)$$

```text
맨 오른쪽 n/(n-1)² 을 실제 값으로 본다 — 이것이 1 을 넘지 않아야 내림이 정해진다

  n = 2    2 / 1  = 2        1 보다 크다.  그래서 조건이 n ≥ 3 이다
  n = 3    3 / 4  = 0.75     경계에서 가장 큰 값이다
  n = 4    4 / 9  ≈ 0.444
  n = 6    6 / 25 = 0.24
           └ n 이 커질수록 줄어든다. 꼬리는 1 을 되찾지 못한다
```

$$N(n)=\left\lfloor e\,(n-2)!\right\rfloor$$

식을 그대로 코드로 옮기면 한 줄짜리 반복문입니다. 항을 곱해 가며 더하면 계승을 따로 구할
필요가 없어요.

```ts
function pathCount(n: number): bigint {
  let term = 1n; // k = 0 일 때의 (n-2)!/(n-2)! = 1
  let sum = 1n;
  for (let k = 1; k <= n - 2; k++) {
    term *= BigInt(n - 1 - k); // (n-2)!/(n-2-k)! 를 한 항씩 늘린다
    sum += term;
  }
  return sum;
}
```

제약 규모를 넣어 봅시다. 경로 수 상한이 10,000 개니까, 이 모양의 그래프는 정점이 몇 개까지
허용되는지가 나옵니다.

<!--proof:math-complete-->

```text
정점 n   ⌊e·(n−2)!⌋   제약 10⁴ 이하인가
     4            5   그렇다
     5           16   그렇다
     6           65   그렇다
     7          326   그렇다
     8        1,957   그렇다
     9       13,700   아니다
    10      109,601   아니다
```

**정점 아홉 개면 벌써 제약을 넘습니다.** 정점이 1,000 개까지 허용되는 문제인데 이 모양으로는
여덟 개가 한계예요. 제약의 셋째 줄이 실제로 막고 있는 것이 이것입니다.

같은 계산을 격자에서도 해 봅시다. $m\times m$ 격자에서 오른쪽과 아래로만 가는 그래프를 잡으면,
왼쪽 위에서 오른쪽 아래까지 가는 경로 하나는 오른쪽 이동 $m$ 번과 아래 이동 $m$ 번을 늘어놓은
길이 $2m$ 짜리 나열 하나와 일대일로 대응합니다.

```text
m = 2 격자 — 오른쪽과 아래로만 간선을 놓는다

  (0,0) → (0,1) → (0,2)        정점은 (m+1)² = 9 개다
    ↓       ↓       ↓
  (1,0) → (1,1) → (1,2)        왼쪽 위에서 오른쪽 아래까지 가려면
    ↓       ↓       ↓          오른쪽으로 2 번 아래로 2 번이 반드시 필요하다
  (2,0) → (2,1) → (2,2)        └ 경로를 가르는 것은 그 넷의 순서뿐이다
```

$$N=\binom{2m}{m}$$

```text
m = 2 에서 확인한다 — 오른쪽 R 두 번과 아래 D 두 번을 늘어놓는다

  RRDD   RDRD   RDDR   DRRD   DRDR   DDRR
  └ 여섯 가지. C(4, 2) = 6 과 같다
```

정점 수는 $V=(m+1)^2$ 이므로 $m=\sqrt V-1$ 이고, 스털링 근사
$\binom{2m}{m}\sim 4^m/\sqrt{\pi m}$ 을 쓰면 $N$ 이 $\sqrt V$ 에 대해 지수적으로 커지는 것이
확인됩니다. 여기에도 제약 규모를 넣어 보죠.

<!--proof:math-grid-->

```text
격자 m   정점 수 (m+1)²   C(2m, m)   제약 10⁴ 이하인가
     1                4          2   그렇다
     2                9          6   그렇다
     3               16         20   그렇다
     4               25         70   그렇다
     5               36        252   그렇다
     6               49        924   그렇다
     7               64      3,432   그렇다
     8               81     12,870   아니다
```

**격자는 한 변이 여덟 칸이면 제약을 넘습니다.** 그때 정점은 여든한 개뿐이에요. 두 표가 같은
것을 말합니다 — 이 문제의 제약에서 정점 수 상한 1,000 은 거의 아무것도 막지 않고, 실제로 입력의
크기를 정하는 것은 경로 수 상한 10,000 하나입니다.

### 불변식 — 되돌아간 뒤의 상태가 들어가기 직전과 같다

파트 1 에서 코드가 동작하는 것을 열여섯 단계로 봤습니다. 그런데 그건 입력 하나에서 맞았다는
뜻이지 언제나 맞는다는 뜻은 아니에요. 무엇이 **매 순간 참으로 남는지**를 문장으로 세우고,
그것이 실제로 유지되는지 확인해 봅시다.

> `walk(u)` 호출 하나가 반환한 직후, `path` 와 `onPath` 는 그 호출 직전과 글자 그대로 같습니다.
> 그리고 `walk` 안의 어느 지점에서도 `onPath[v]` 가 참인 정점의 모임은 `path` 에 담긴 정점의
> 모임과 같습니다.

```text
두 문장이 각각 무엇을 보장하는가

  반환 직후가 직전과 같다     형제 갈래가 서로 영향을 주지 않는다  → 경로를 잃지 않는다
  표시 = path 안의 정점       같은 정점을 두 번 담지 않는다        → 단순 경로만 나온다
                              └ 앞이 깨지면 경로가 사라지고, 뒤가 깨지면 사이클이 나온다
```

「반환한 직후」가 중요합니다. 재귀가 다 끝난 뒤 한 번만 참인 것이 아니라 **한 겹이 반환할
때마다** 참이라는 뜻이에요. 그래야 형제 갈래가 그 상태를 그대로 이어받습니다.

**출발점부터 봅시다.** `walk(source)` 를 부르기 직전에 `path` 는 비어 있고 `onPath` 는 전부
거짓이라 두 모임이 둘 다 공집합으로 같습니다. 그 뒤로 상태를 바꾸는 자리는 넷이에요.

| 무슨 일 | 상태가 어떻게 바뀌는가 | 두 문장이 유지되는 근거 |
| --- | --- | --- |
| 진입 | `onPath[u]` 가 참이 되고 `path` 뒤에 `u` 가 붙는다 | 한 정점이 양쪽에 동시에 더해진다. `u` 는 갈래 ③ 을 지나온 것이라 직전에 두 모임 어디에도 없었다 |
| 도착 정점이다 | `result` 에 복사본 하나가 더해진다 | `path` 와 `onPath` 를 건드리지 않는다 |
| 이웃을 건너뛴다 | 아무것도 안 바뀐다 | 판정만 하고 지나간다 |
| 되돌아간다 | `onPath[u]` 가 거짓이 되고 `path` 끝에서 하나가 빠진다 | 진입에서 더한 그 정점을 양쪽에서 하나씩 뺀다. `path` 는 스택이라 끝에 있는 것이 `u` 다 |

첫 줄과 넷째 줄이 정확히 맞물리는 것을 값으로 확인해 봅시다. 전개의 T5 와 T6 이 그 자리예요.

```text
T3 반환 직전   path [0, 1, 2]      표시 {0, 1, 2}      두 모임이 같다
T5 진입 직후   path [0, 1, 2, 4]   표시 {0, 1, 2, 4}   정점 4 가 양쪽에 함께 더해졌다
T6 반환 직후   path [0, 1, 2]      표시 {0, 1, 2}      T5 직전과 글자 그대로 같다
T7 진입 직후   path [0, 1, 2, 5]   표시 {0, 1, 2, 5}   같은 자리에서 다른 이웃으로 내려간다
               └ T5 가 남긴 것이 하나도 없어서 T7 이 정점 4 를 다시 쓸 수 있다
```

이 불변식이 답의 정확성을 그대로 줍니다. 표시가 켜진 정점이 `path` 안의 정점과 언제나 같으므로
갈래 ② 가 막는 것은 **정확히 지금 경로 안에 있는 정점**이고, 그래서 담기는 것이 전부 단순
경로예요. 그리고 한 겹이 반환할 때 상태를 원래대로 두므로, 같은 정점을 지나는 서로 다른 경로가
서로를 막지 않습니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 최소 입력 `dfsAllPaths(1, [], 0, 0)` | 진입하자마자 도착 정점이라 복사 하나로 끝난다 | `[[0]]` |
| 출발과 도착이 같다 `dfsAllPaths(3, [[0,1],[1,2]], 1, 1)` | 이웃 목록을 한 번도 확인하지 않는다 | `[[1]]` |
| 경로가 없다 `dfsAllPaths(3, [[0,1]], 0, 2)` | 갈래 ① 이 한 번도 실행되지 않는다 | `[]` |
| 간선 방향이 반대다 `dfsAllPaths(2, [[1,0]], 0, 1)` | `adj[0]` 이 비어 있어 바로 되돌아간다 | `[]` |
| 자기 루프 `dfsAllPaths(2, [[0,0],[0,1]], 0, 1)` | 이웃 목록을 만들 때 `u === v` 로 빠진다 | `[[0,1]]` |
| 중복 간선 `dfsAllPaths(3, [[0,1],[0,1],[1,2]], 0, 2)` | 같은 이웃이 모임에 한 번만 들어간다 | `[[0,1,2]]` |
| 사이클 `dfsAllPaths(3, [[0,1],[1,2],[2,0],[0,2]], 0, 2)` | 갈래 ② 가 `2 → 0` 을 막는다 | `[[0,1,2], [0,2]]` |

자기 루프와 중복 간선이 이 절차의 경계입니다. 둘 다 이웃 목록을 만드는 자리에서 처리되고 그
뒤로는 없는 것과 같아요. 사이클은 다릅니다 — 간선이 그대로 남아 있고, 갈래 ② 가 매번 판정해서
막습니다.

**이제 깨뜨려 봅시다.** 「반환 직후가 직전과 같다」를 지키던 줄이 어느 것인지는 바꿔 보면
확인됩니다. 되돌아가는 자리의 표시를 지우는 줄 **하나만** 지웁니다.

```ts
  // onPath[u] = false;   ← 이 한 줄만 지웠다. path.pop() 은 그대로 둔다
  path.pop();
```

실행하면 이렇게 나옵니다.

<!--proof:mutant-no-unmark-->

```text
                        지운다(정본)                    지우지 않는다
전개가 쓰는 여섯 정점   [[0,1,2,4], [0,1,4], [0,2,4]]   [[0,1,2,4]]
다이아몬드              [[0,1,3], [0,2,3]]              [[0,1,3]]
한 줄로 이은 네 정점    [[0,1,2,3]]                     [[0,1,2,3]]
```

전개 입력에서 세 경로가 하나로, 다이아몬드에서 두 경로가 하나로 줄었습니다. 첫 경로를 담고
되돌아간 뒤에도 그 경로 위의 정점들이 전부 표시된 채로 남아, 그 정점을 지나는 다른 경로가
갈래 ② 에 막히기 때문이에요.

```text
전개 입력에서 무엇이 언제 막히는가

  [0,1,2,4] 를 담는다           표시 {0, 1, 2, 4}
  되돌아가도 표시가 그대로다     표시 {0, 1, 2, 4}
  정점 1 에서 이웃 4 를 본다     표시돼 있다 → 막힌다   [0,1,4] 가 없어진다
  정점 0 에서 이웃 2 를 본다     표시돼 있다 → 막힌다   [0,2,4] 가 없어진다
```

**한 줄로 이은 네 정점에서는 두 값이 같다는 것**도 함께 보세요. 경로가 하나뿐인 그래프에서는
첫 경로를 담은 뒤에 갈 곳이 없어 표시가 남든 안 남든 결과가 같습니다. 이 입력만 시험하면
지워 놓고도 통과해서, 잘못된 코드를 그대로 두게 돼요.

### 비용 계산

#### 비용을 세는 과정

한 번의 `walk` 진입이 하는 일은 표시 한 칸을 켜고, 경로에 하나를 담고, 도착 정점이면 경로를
복사하고 아니면 자기 이웃 목록을 한 번 확인하고, 마지막에 표시를 지우고 경로에서 하나를
빼는 것뿐입니다. 전개의 값으로 확인하면 이렇게 나와요.

<!--proof:perf-count-->

```text
단계   진입한 정점   이웃 목록 길이
T1     0                          2
T2     1                          2
T3     2                          3
T5     4                          0
T7     5                          0
T9     4                          0
T11    2                          3
T13    4                          0
T15    5                          0
합     진입 9                    10
```

진입 아홉 번에 이웃 목록에서 읽은 원소가 열 개입니다. 갈래 ① 로 들어간 T5·T9·T13 은 이웃
목록을 아예 확인하지 않고, 막다른 정점 5 로 들어간 T7·T15 는 목록이 비어 있어 0 이에요.

```text
진입 횟수 R 이 무엇으로 정해지는가

  walk(u) 가 불리는 횟수 = s 에서 u 까지의 단순 경로 중 t 를 중간에 안 지나는 것의 수
  그러니 R = 그런 부분 경로의 총수이고, 그중 t 에서 끝나는 것이 N 개다
            └ 전개 입력에서 R = 9, N = 3. 나머지 6 은 답이 되지 못한 부분 경로다
```

총식을 적으면 네 항입니다. 앞의 두 항은 그래프 크기로 정해지고, 뒤의 두 항은 답과 그래프
모양으로 정해져요.

```text
총식 = 이웃 목록 만들기 + 목록 정렬        + 탐색                        + 결과 복사
        Θ(V + E)          O(E · log Δ)      Θ(R + Σ_{진입한 u} deg⁺(u))   Θ(L)
                          ↑ Δ 는 deg⁺ 의 최댓값                            ↑ L 은 출력 숫자 수
     = Θ(V + E) + O(E · log V) + Θ(R + E·R/V) + Θ(L)

메모리 = 이웃 목록 Θ(V + E) + onPath·path Θ(V) + 재귀 스택 Θ(V) + 결과 Θ(L)
```

여기서 센 것은 **이웃 목록의 원소 읽기, 정렬 비교, 그리고 결과에 적는 숫자**입니다. 자기 루프를
빼고 중복을 접는 자리는 해시 집합이라 간선 하나에 상수 번이고, `Array.prototype.sort` 가 실제로
몇 번 비교하는지는 실행 환경이 정하므로 `O(E · log Δ)` 는 **비교 정렬의 상한**을 적은 것이에요.

#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최선의 경우** (`source` 에서 나가는 간선이 없다) | `O(V + E log V)` | `Θ(V + E log V)` |
| **평균적인 경우** (그래프 분포를 정하지 않았다) | `O(V + E log V + R·V + L)` | 정의되지 않는다 |
| **최악의 경우** (막다른 무리가 크다) | `O(V + E log V + R·V + L)` | `Θ(R·V)` |

`R` 이 식에 그대로 남아 있는 것이 이 문제의 특징입니다. `R` 을 `V` 와 `E` 만으로 적을 수가
없어요 — 같은 정점 수와 간선 수에서 `R` 이 두 자릿수부터 다섯 자릿수까지 갈립니다.

<!--proof:grid-count-->

```text
격자 m   정점 수   경로 수   진입한 노드   이웃 검사
     2         9         6            19          18
     3        16        20            69          68
     4        25        70           251         250
     5        36       252           923         922
```

격자에서는 진입한 노드가 전부 경로의 앞부분이 되고, 그래서 `R` 이 경로 수 `N` 과 같은 규모예요.
5×5 격자에서 `N = 252` 이고 `R = 923` 입니다. 막다른 자리가 없는 그래프의 모습이 그것이고,
「최악을 만드는 입력」이 그 반대쪽을 보입니다.

**평균이 정의되지 않는 이유**를 적어 둡니다. 이 문제는 간선이 어떻게 놓이는지에 대한 분포를
주지 않아요. `R` 이 그래프의 모양에 통째로 달려 있는데 그 모양의 분포가 정해지지 않으면
기댓값을 계산할 대상이 없습니다.

```text
정점 수와 간선 수가 비슷해도 R 이 갈린다

  5×5 격자     정점 36 · 간선 60   경로 252 개   진입 923 회
  덫 그래프    정점 10 · 간선 58   경로 1 개     진입 13,702 회
               └ 간선 수는 거의 같은데 진입 횟수가 열다섯 배 갈린다
```

**보장의 종류는 최악 보장입니다.** 코드에 난수가 하나도 없고 입력 분포에 대한 가정도 없어요.
같은 입력을 두 번 넣으면 진입 횟수까지 똑같이 나옵니다. 다만 그 최악 보장의 값이 `V` 와 `E` 의
식이 아니라 `R` 을 담고 있고, `R` 자체는 입력마다 재야 하는 값이에요.

경계의 종류도 갈라 적습니다. 하한은 `Ω(L)` 이고 이것은 **어떤 절차에도 걸립니다** — 답을 적는
데 숫자 `L` 개를 써야 하니까요. 최선의 `Θ(V + E log V)` 는 이웃 목록을 만드는 비용만 남은
값이고, 이때 `R = 1` 이며 `L = 0` 입니다.

#### 최악을 만드는 입력

`R` 을 최대로 만드는 입력을 실제로 구성해 봅시다. 제약이 묶고 있는 것은 정점 1,000 개 · 간선
10,000 개 · **경로 10,000 개**인데, 셋 다 지키면서 `R` 을 마음껏 키울 수 있어요.

```text
덫 그래프를 만드는 법 — 정점 k + 2 개

  0 → k+1                      경로가 되는 유일한 간선
  0 → 1                        막다른 무리로 들어가는 입구
  a → b  (1 ≤ a, b ≤ k, a ≠ b) 정점 1 … k 를 서로 전부 잇는다
                               └ 그 무리에서 k+1 로 나가는 간선은 하나도 없다
                                 경로 수는 1 로 고정인데 진입 횟수는 k 로 정해진다
```

`k` 를 키우면서 실제로 실행해 보면 경로 수는 그대로인데 진입 횟수만 늘어납니다.

<!--proof:worst-input-->

```text
막다른 무리 k   정점 수   간선 수   경로 수   진입한 노드
            6         8        32         1           328
            7         9        44         1         1,959
            8        10        58         1        13,702
            9        11        74         1       109,603
```

**경로 수는 계속 1 인데 진입 횟수가 계승만큼 늘어납니다.** `k` 가 하나 늘 때마다 진입이 약 `k`
배가 되는 것이 표의 마지막 열에서 확인돼요. 간선 수 상한 10,000 을 다 쓰면 `k(k-1) ≤ 10,000`
에서 `k` 를 100 까지 키울 수 있고, 그때 진입 횟수는 99 의 계승 규모입니다.

```text
제약이 무엇을 묶고 무엇을 안 묶는가

  정점 1,000 개 이하   묶는다      V 가 1,000 을 못 넘는다
  간선 10,000 개 이하  묶는다      E 가 10,000 을 못 넘는다
  경로 10,000 개 이하  묶는다      N 과 L 이 묶인다 → 출력 크기가 묶인다
  진입 횟수 R          안 묶는다   위 셋을 다 지키면서 R 을 우주적으로 키울 수 있다
```

「경로 수에 상한이 있으니 시간도 묶인다」는 통념은 이 절차에서 거짓입니다. 출력 크기는 묶여
있는데 그 출력을 찾아가는 비용은 안 묶여 있어요. 그것이 「경쟁 설계와의 대조」의 도달 가능성
가지치기가 존재하는 이유이고, 그 절차는 진입한 노드가 **전부 경로 하나 이상을 만들도록** 만들어
`R` 을 `L` 규모로 눌러 놓습니다.

### 스스로 점검하기

여기까지 다룬 것을 한 줄로 정리하면 이렇습니다. 정점 나열을 전부 만들어 놓고 거르던 것을
**간선을 따라가며 한 칸씩 늘리는 것**으로 바꿨고, 「지금 경로 안에 있는가」를 표시 한 칸이
판정하며, 그 표시는 **되돌아가는 자리에서 반드시 지워야** 다음 경로가 만들어집니다.

```text
간선 목록 → 이웃 목록(자기 루프 제외 · 중복 제거 · 오름차순) → walk(source)
                                                                  ↓
  진입: 표시를 켜고 경로에 담는다 → 갈래 ①②③ → 되돌아가기: 표시를 지우고 경로에서 뺀다
    └ 켠 것 하나와 지우는 것 하나가 짝을 이룬다        └ 비용은 V + E log V + R + L
```

먼저 답이 붙는 문제 하나입니다. 전개의 T6 에서 정점 4 를 결과에 담고 되돌아가며 `onPath[4]` 를
지웠어요. 그 한 걸음에서 **표시는 지우고 `path.pop()` 만 하지 않았다면** 최종 결과가 무엇이
되었을까요?

```text
T6   되돌아간다   4 를 뺀다   path [0, 1, 2]   ← 이 빼기를 안 하면?
```

<!--check:nopop-->
결과는 `[[0,1,2,4], [0,1,2,4,5,4], [0,1,2,4,5,4,2,4]]` 가 됩니다. 표시를 지웠으니 막히지는
않는데, `path` 가 줄지 않아 앞 경로의 흔적이 그대로 남아요.

```text
path 가 줄지 않으면 무엇이 쌓이는가

  T5 에서   path [0, 1, 2, 4]        첫 경로를 담는다
  T6 에서   path [0, 1, 2, 4]        빼지 않았다
  T7 에서   path [0, 1, 2, 4, 5]     정점 5 가 그 뒤에 붙는다
  그다음    path [0, 1, 2, 4, 5, 4]  정점 4 가 다시 붙어 두 번째 경로가 된다
            └ 정점 4 가 두 번 들어 있는데도 표시는 지워져 있어 갈래 ② 가 못 막는다
```

「아이디어 상세」의 마지막 표 셋째 줄이 같은 것을 다이아몬드에서 보인 자리입니다. 표시와
`path` 는 **같은 것을 두 방식으로 적은 것**이라, 되돌아갈 때 한쪽만 지우고 다른 쪽을 그대로
두면 그 순간부터 서로 어긋나요.
<!--/check-->

```text
아래 셋은 답을 싣지 않았습니다. 막히면 이 절들을 다시 보세요
  1 → 수행으로 알아보는 알고리즘 의 T7 과 T15     3 → 최악을 만드는 입력
  2 → 불변식
```

- T7 과 T15 에서 정점 5 로 두 번 내려갔다가 두 번 다 아무것도 담지 못하고 되돌아왔습니다.
  전개 입력의 간선 하나를 지워서 그 헛걸음을 없애려면 어느 간선을 지워야 할까요. 그리고 그때
  진입 횟수가 아홉에서 몇으로 줄어드는지 세어 보세요.
- 불변식은 「반환 직후가 직전과 같다」고 말합니다. 그러면 `result` 는 왜 이 문장에 안 들어갈까요.
  `result` 를 넣어 문장을 다시 쓰면 무엇이라고 적어야 하는지 생각해 보세요.
- 덫 그래프에서 진입 횟수가 계승만큼 늘어났습니다. 그 그래프에 간선을 **하나만** 더해서 진입
  횟수는 그대로 두고 경로 수만 늘리려면 어디에 더해야 할까요. 반대로 간선을 하나만 지워서 진입
  횟수를 크게 줄이려면 어디를 지워야 합니까.
