## 0. 이 명세는 델타다

**base 는 `sandbox/algo-guide-v2/SPEC.md`(이하 `algo SPEC`)이고, 이 문서는 갈리는 것만
적는다.** 공통 조항을 여기 옮겨 적지 않는다 — *"한 사실이 두 곳에 적히면 둘이 갈라진다"* 가
ORD-006 과 algo-guide-v2 가 함께 쓰는 규약이고, 갈라진 자리에서 가이드가 코드보다 낙관적인
복잡도를 주장한 것이 자료구조 트랙을 한 번 재설계하게 만든 결함이다.

**예외는 §2 의 id↔헤딩 매핑 하나다** — `tools/section.ts` 가 기계로 읽으므로 완전해야 한다.

읽는 순서는 `algo SPEC` → 이 문서다. 이 문서가 말하지 않는 것은 전부 `algo SPEC` 그대로다.

### 알고리즘과 무엇이 다른가 — 셋이다

| | 알고리즘 | 자료구조 |
| --- | --- | --- |
| 대상 | **문제를 푸는 절차** 하나 | **계약** 하나와 그것을 지키는 구현 |
| 진입점 | 문제 지문 | `<name>.ts` 헤더 JSDoc 의 계약 명세 |
| 실행 단위 | 함수 하나를 끝까지 굴린다 | **연산이 복수다** — 묶음마다 굴린다 |

**셋째가 분량을 늘린다. 그것을 줄이지 않는다** — 요청서가 *"편당 분량이 방대해질 수 있으나,
신경 쓰지 말아라"* 로 면제했다. `algo SPEC` 의 `L1`(분량을 이유로 단계를 접지 않는다)이
그대로, 더 강하게 적용된다.

### 계약 층은 이 명세 밖이다

자료구조에는 원고 위에 **계약 층**이 따로 있고, 그 정본과 판정 장치는 ORD-006 이다.

| 층 | 정본 | 판정 |
| --- | --- | --- |
| 계약·구현 | `<name>.ts` 헤더 JSDoc · `_reference/<name>.ts` | 계약 스위트 4축 · `tools/check-contract.ts` · `tools/emit-vectors.ts` · Rust 축4 |
| **원고 (이 명세)** | `<name>-guide.md` | `tools/check-v2.ts` · `tools/check-proof.ts` · `tools/check-metaphor.ts` |

**이 명세는 계약을 정의하지 않는다.** 계약을 어떻게 적는지는
`docs/ORD-006-conventions.md` §규약1 이고, 가이드는 조건이 아니라 **조건의 이유**를 쓴다.

### 폐기된 이름 — 되살아나면 위반이다

ds-guide 8단계 골격의 항목 이름이 헤딩에 나오면 `P3` 이 잡는다
(`RETIRED_HEADING_WORDS` 에 넣는다).

```
이 구조가 필요한 이유 · 쓰이는 자리 · 단순한 구현의 한계 · 순진한 설계는 어디서 상한을 넘는가
실패에서 끌어내는 설계 규칙 · 불변식과 연산별 복잡도 조건 · 구현 (TypeScript) · 단계별 동작 확인
```

**이름이 남으면 직무도 남는다** — algo v1 이 세 항목을 `####` 로 내려 담기만 했다가 유저에게
다시 지적받은 자리다(`algo SPEC` §1). `이 구조가 필요한 이유` 의 직무는 `concept` 와
`purpose.fit` 이 나눠 받고, `단순한 구현의 한계` 는 `deep.build` ②가 받는다.

## 3. 갈리는 절의 작성법

**여기 없는 절은 `algo SPEC` §3 그대로다.**

### `title` — 부제는 설계 핵심을 예고한다

algo 의 부제는 **돌파 관찰**(*"질의를 정렬하면 포인터 이동이 √n배 줄어드는 이유"*)이다.
자료구조에는 돌파할 문제가 없으므로 **이 구조의 설계 핵심을 한 구절로** 예고한다.

### `deep.build` — 설계 상세 (직무 여섯 중 ①만 갈린다)

`algo SPEC` §3 `deep.build` 의 직무 ②~⑥ 은 **그대로 적용된다.** ①만 갈린다.

**① 계약을 읽는다 — 고정하지 않는다.** algo 는 여기서 문제를 고정한다(시그니처 + 입출력
계약 + 제약 규모 + 기호표). 자료구조는 **계약이 이미 정본으로 서 있다**(`<name>.ts` 헤더
JSDoc 여섯 항목). 그러므로 이 걸음이 하는 일은 셋이다.

1. **계약이 무엇을 배제하는지 적는다.** 표를 복사하지 않는다(`L42`). 연산 목록과 상한을
   그대로 옮겨 적는 것은 정본을 두 곳에 두는 일이고, 갈라지면 가이드가 진다.
   쓸 것은 *"이 상한을 풀어 주면 무엇이 되는가"* 다 — `docs/ORD-006-conventions.md` 의
   필요충분조건 항목이 같은 물음을 계약 쪽에서 답한다.
2. **기호표**는 algo 와 같이 여기서 한 번에 낸다(`L21`). 자료구조에서 끝까지 쓰는 것은
   원소 수 `n` · 연산 횟수 · 보조 구조의 크기다.
3. **제약 규모 대신 호출 패턴을 적는다.** 자료구조에는 「입력 크기 상한」이 아니라 「어떤
   연산이 몇 번 섞여 들어오는가」가 비용을 정한다. `n` 회 삽입 뒤 `q` 회 질의인지, 삽입과
   질의가 교대인지에 따라 상각 설계의 성립 여부가 갈린다.

②(가장 단순한 구현을 수치로 반박한다)는 그대로다. 후보는 실재하는 것으로 — 정렬 배열,
연결 리스트, 해시맵, 단순 이진 탐색 트리. **형용사 서술을 쓰지 않는다.**

### `deep.walk` — 수행으로 알아보는 자료구조

도입부는 algo 와 같이 둘만 한다 — 끝까지 쓸 **고정 입력 하나**와 절차 전체를 한 장으로 보인
그림. 자료구조에서 「고정 입력」은 **연산 열**이다(`pushBack(1) · pushFront(2) · popBack()` …).
그 열을 왜 그것으로 골랐는지 한 문장을 붙인다 — 모든 연산을 최소 한 번 실행하게 하려는 것이면
그렇게 적는다.

#### `deep.walk.step` — 연산 묶음마다 한 벌 (`L41`)

**한 벌의 뼈대는 algo 와 같다** — 왜 → 코드 → 그 조각만 실행한 결과.

**갈리는 것은 하한이다.** algo 는 `≥3` 벌인데 자료구조는 **계약 헤더의 연산 표를 전수
피복**해야 한다. 연산 여덟이면 여덟 번 굴린다 — 요청서가 분량을 면제한 자리가 여기다.

**묶는 단위는 「같은 상태 전이를 공유하는 연산」이다.** 대칭 연산(`pushFront`/`pushBack`)은
한 벌에 담아 차이만 짚고, 상태를 안 바꾸는 조회(`peek`·`size`·`isEmpty`)는 한 벌로 묶는다.
**묶었으면 묶은 근거를 그 벌의 첫 문장에 적는다** — 근거 없이 묶으면 피복을 건너뛴 것과
구별되지 않는다.

**전수 피복의 판정은 기계가 한다**(`P17`). 계약 헤더의 연산 표에서 연산 이름을 뽑아
`deep.walk.step` 본문에 그 이름이 나오는지 센다. **이 검사는 이름의 등장만 본다** — 그
연산을 실제로 굴렸는가는 사람이 본다.

algo 와 같이 **한 벌은 고정 입력으로 끝까지 실행하는 벌**이어야 하고, 거기에 (a) 단계별
상태값 (b) 분기 조건의 참/거짓을 실제 값으로 (c) 모든 분기 최소 1회 피복이 들어간다.
단계에 `T1`·`T2` … 를 단다.

#### `deep.walk.final` — 전체 코드 (`L43`)

**출처가 갈린다.** algo 는 `<name>-guide.ref.ts` 에서 옮기는데, 자료구조의 정본은
**`_reference/<name>.ts` 이고 그것이 이미 서 있다.** 사이드카 `.ref.ts` 를 새로 만들지
않는다 — 정본을 둘로 만드는 일이다.

싣는 것은 그 파일의 **`#region guide:core` 구간 추출본**이다.

````
```ts guide-core=src/data-structures/<카테고리>/<이름>/_reference/<이름>.ts#class
(추출본. 손으로 고치지 않는다)
```
````

- **손으로 옮겨 적지 않는다.** `bun run tools/guide-core.ts check` 가 한 글자 차이도 잡는다.
  코드를 고쳐야 하면 정본을 고치고 다시 추출한다.
- **계측(`__cost`)은 추출 과정에서 걷힌다**(`stripInstrumentation`). 본문에 계측이 보이면
  옮겨 적었다는 뜻이다.
- **정본이 없으면 위반이다.** algo 의 `P16` 은 `.ref.ts` 가 없을 때 「미실행」으로 빠지는데,
  그 처리를 자료구조에 그대로 두면 **안 잰 것이 통과로 읽힌다.** ds 에서 `P16` 은
  `guide-core` 경로로 판정하고 정본 부재를 위반으로 올린다.

### `purpose.fit` · `purpose.cue` — 문제를 다루지 않는다

**이 두 절이 이 명세에서 가장 크게 갈리는 자리다.** 자료구조 가이드는 문제를 다루지 않는다 —
ORD-006 의 핵심 결정이고, 그 결정이 진단된 A급 결함 4건을 낳은 원인의 반대편이다.

- **fit** — 어떤 **요구**에 최적인가. 문장의 주어는 문제가 아니라 **연산**이다.
  연산 두셋을 **동시에** 요구할 때 무엇이 어려워지는지 적는다. 하나만 필요하면 대개 더
  단순한 구조로 충분하고, 그렇다면 이 구조는 필요하지 않다.
- **cue** — algo 의 *"문제 지문에서 이 알고리즘을 떠올리게 하는 신호"* 를 **연산 조합**으로
  바꾼 것이다. 독자가 다음에 만나는 것은 문제 지문이 아니라 **자기 코드의 요구**다.

  **쓰지 않는 문형**: *"문제에 ~라는 조건이 보이면"* · *"~를 묻는 문제에서"* · *"출제 유형은"*.
  이 셋이 나오면 `P2` 가 잡는다.

  **쓰는 형태**: 필요한 연산 집합과 각각의 호출 빈도, 그리고 그 조합에서 상한이 어디서
  깨지는가. *"윈도우가 한 칸 밀릴 때마다 하나 넣고 하나 빼고 중앙값을 읽는다"* →
  `add`·`delete`·`min` 이 각 1회씩, 스트림 길이만큼 반복. 세 연산이 모두 계약에 있고
  상한이 `O(log n)` 이므로 전체가 `O(n log n)` 이다.

  **번역이 없으면 사례가 아니라 스토리다.** 번역한 연산이 계약에 없으면 그 사례는 이 구조의
  사례가 아니다 — 그것이 이 규격을 검사 가능하게 만드는 자리다.

### `invariant` — 정본은 계약 헤더다

**세 걸음의 구조는 `algo SPEC` 그대로다**(① 문장 하나로 세운다 ② 상태값으로 유지를 보인다
③ 깨뜨려서 확인한다). 갈리는 것은 **불변식이 어디서 오는가**다.

- 불변식의 정본은 **`<name>.ts` 헤더의 불변식 항목**이다. 절은 그것을 **복사하지 않고**
  왜 그 조건인지, 그리고 **못 지키면 무엇이 되는지**를 이름으로 적는다.
  (*"순서를 버리면 값→개수 맵이고, 다중도를 버리면 정렬 집합이다."*)
- **계약의 불변식 항목이 「없다」인 구조가 있다.** 그때 이 절은 비지 않는다 — **왜 없는지**를
  적는 자리가 된다. `linear/deque` 가 그 사례다: *"각 연산의 의미가 각각 옳으면 따로 깨질 수
  있는 상태 성질이 남지 않는다."* 그 문장이 왜 참인지가 이 절의 ①이다.
- ② 의 「각 연산이 불변식을 어떻게 지키는가」는 **연산 표 전수**다. `deep.walk.step` 의 피복과
  같은 근거를 쓴다.
- ③ 에서 바꾸는 자리는 **①의 불변식을 지키던 그 줄**이다. 자료구조에서는 그 줄이 대개
  `_reference/` 정본에 있다 — 스텁이 아니라 정본을 변이시킨다.

**내부 표현의 성질을 불변식으로 적지 않는다**(런북 불변 사실 36). 균형·높이는 계약에 없고,
적는 순간 그것이 처방이다. 균형이 깨진 구현은 축3 의 성장률이 잡는다.

### `perf.*` — 축3 성장률을 인용한다 (`L44`)

- **derive** — algo 와 같이 전개의 `T#` 를 인용해 센다.
- **bounds** — 케이스와 경계를 두 축으로 가르는 것은 같다. 갈리는 것은 **한정자가 계약에서
  온다**는 것이다. `worst`·`amortized`·`expected` 는 집필자가 고르는 값이 아니라 계약 헤더에
  연산마다 적혀 있다. 절이 하는 일은 **그 한정자가 왜 그것인지** 한 번 설명하는 것이다.

  **셋은 줄 세워지지 않는다** — `worst` 는 나머지 둘을 함의해 가장 강하고, `amortized` 와
  `expected` 는 서로를 함의하지 않는다. `worst` 를 적은 구조에서는 **배제되는 계열이
  무엇이고 왜 배제해도 되는지**를 적는다(`docs/ORD-006-conventions.md` §규약1 · 런북 불변
  사실 59).
- **worst** — **적대적 입력은 하나로 부족하다**(런북 불변 사실 24). 적대성은 계약이 아니라
  구현에 대해 정의된다 — 오름차순 삽입은 탐색 트리에 최악이고 정렬 배열에는 최선이다.
  이 절이 겨누는 것은 **본문에 실린 그 구현**이고, 다른 정당한 구현에는 다른 입력이 최악이라는
  사실을 한 문장으로 적는다.

**벽시계를 쓰지 않는다.** 인용하는 수치는 계약 스위트 축3 의 성장률
$r = C(4n)/C(n)$ 실측값이다. 벽시계는 그 기계의 상수를 잴 뿐이라 근거가 되지 않고,
`tools/check-contract.ts` 가 `performance.now` 호출을 구문 트리로 센다.

### `perf.escalation` — TypeScript 의 한계와 대체 언어 (조건부 · `L45`)

**규격의 정본은 `docs/ORD-006-conventions.md` §규약3 6단계(`docs/ORD-006-conventions.md:1171`)와 §규약4(`docs/ORD-006-conventions.md:1253-1273`)다.**
여기서는 v2 절 체계 안의 자리와 판정만 적는다.

- **조건은 판단이 아니라 등급이다.** 규약4 에스컬레이션 등급이 **(가)·(나)일 때만** 절을 둔다.
  `(-)` 면 절 자체를 생략하고 "해당 없음" 을 적지 않는다. **집필자가 고르지 않는다.**
- 내용 셋은 `docs/ORD-006-conventions.md:1253-1273` 가 확정했다 — 왜 (가)가 아닌가 / 왜 (-)가 아닌가 / 대체 언어에서
  어떻게 되는가.
- **「Rust 코드를 붙이는 절」로 읽지 않는다**(`docs/ORD-006-conventions.md:1272-1273` 의 교정). (나)에서 Rust 포트는
  선택이고, *"옮겨도 안 된다"* 도 완결된 답이다.

`algo SPEC` §8 의 셋에 `perf.escalation` 이 붙는다. **「있으면 더 좋다」가 아니라 「없으면
빼라」** 인 것은 같다.

| 절 | 싣는 조건 | 생략하면 함께 할 일 |
| --- | --- | --- |
| `related` | 본문이 값으로 보인 것에 붙일 이름이 있고, 그 개념이 이 편 밖에서도 쓰이는가 | 없다 |

## 6. `L` 조항 — ds 신설분

**번호는 `L41` 부터다.** `algo SPEC` §6 의 마지막이 `L40` 이고, *"번호는 재부여하지
않는다"* 가 두 명세에 함께 걸린다.

| code | 내용 | 판정 |
| --- | --- | --- |
| `L41` | **`deep.walk.step` 은 계약 헤더의 연산 표를 전수 피복한다.** 연산 이름이 본문에 하나도 안 나오는 연산이 있으면 위반. 묶어서 다룬 경우 묶은 근거를 그 벌의 첫 문장에 적는다(근거는 사람이 본다) | **`P17`** |
| `L42` | **계약 표를 복사하지 않는다.** 연산 목록·상한·한정자를 그대로 옮긴 표가 원고에 있으면 위반이다 — 정본은 `<name>.ts` 헤더 한 곳이고, 가이드는 조건이 아니라 조건의 이유를 쓴다 | **`P18`** |
| `L43` | **`deep.walk.final` 은 `_reference/<name>.ts` 의 `#region guide:core` 추출본이다.** 사이드카 `.ref.ts` 를 만들지 않는다. 정본이 없으면 **위반**이다(「미실행」으로 빠지지 않는다) | **`P16`**(ds 경로) + `guide-core` |
| `L44` | **`perf.*` 는 축3 성장률 $r = C(4n)/C(n)$ 실측을 인용하고 벽시계를 쓰지 않는다.** 한정자는 계약에서 오고, 절은 그것이 왜 그것인지를 적는다 | `check-contract` + 검토 |
| `L45` | **`perf.escalation` 은 규약4 등급이 켠다.** `(-)` 인 구조에 절이 있으면 위반이고, (가)·(나)인 구조에 절이 없어도 위반이다. 집필자가 고르지 않는다 | **`P19`** |
| `L46` | **`deep.build` ①은 계약을 읽는다 — 고정하지 않는다.** 계약이 무엇을 배제하는지 · 기호표 · **호출 패턴**(어떤 연산이 몇 번 섞여 들어오는가) 셋을 낸다. 제약 규모 하나로 대신하지 않는다 | 검토 |

**`P17`~`P19` 는 이 명세가 요구하는 신설 스캐너 조항이다.** 구현은 `tools/check-v2.ts` 이고
`S3` 이 진다. `P16` 은 신설이 아니라 ds 경로 추가다.

## 7. 파일 구성 — 사이드카는 다섯이다

```
src/data-structures/<카테고리>/<이름>/
  <이름>.ts                계약(헤더 JSDoc 여섯 항목) + 실습 스텁      ← ORD-006, 존치
  <이름>.contract.ts       계약을 기계가 읽는 형태                      ← ORD-006, 존치
  <이름>.test.ts           runContract 호출부                          ← ORD-006, 존치
  _reference/<이름>.ts     정본 구현. 축3 계측(__cost)의 의무를 진다     ← ORD-006, 존치
  <이름>-guide.md          원천. <!--viz:--> 마커가 md↔web 갈림점        ← 이 명세
  <이름>-guide.sim.ts      { view, steps, title, result }               ← 이 명세
  <이름>-guide.proof.ts    증명 블록의 출처. **_reference/<이름>.ts 를 import 해야 한다**
  <이름>-guide.alt.ts      경쟁 설계 구현 (purpose.alt 를 실은 편에만)
  <이름>-guide.bench.json  같은 조건
```

**algo 와 다른 것 둘이다.**

1. **`.ref.ts` 가 없다** — 정본이 `_reference/<이름>.ts` 다(`L43`).
2. **`-guide.test.ts` 가 없다** — 자료구조의 입출력 검증은 계약 스위트(`<이름>.test.ts` 의
   `runContract`)가 이미 지고, 그것이 축1~축3 을 함께 본다. algo 의 `L9` 가 하던 일을
   여기서는 ORD-006 이 한다.

`<이름>-problem.md` 는 **없다** — 자료구조는 문제를 풀지 않는다(런북 불변 사실 2).

## 8. 이 명세가 대체하는 것

`.claude/authoring/specs/ds-guide/`(8단계 골격)를 대체한다. 그 spec 과 `-guide.mdx` 69편은
전개 카드가 걷는다. **`tools/check-guide-rhythm.ts` 와 `tools/_baseline/guide-rhythm.tsv` 도
함께 걷힌다** — 그 도구의 대상 집합이 `src/**/*-guide.mdx` 뿐이라 `.mdx` 가 0 이 되면
`exit 2` 로 CI 를 멈춘다. 규칙은 `P1`·`P2` 가 이미 받았다.

## 9. 시뮬 이관 — `.mdx` 의 `export const steps` 에서 `.sim.ts` 로

**69/69 가 시뮬을 쓴다**(실측 2026-09-11). 규격 없이는 전개가 막히는 자리라 절차를 못 박는다.

### 무엇이 어디로 가는가

옛 `.mdx` 는 셋을 한 파일에 담았다 — `#guide-sim` import · `export const steps` 배열 ·
`<AlgorithmSimulation view={…} steps={steps} title="…" />` 호출부.

| 옛 `.mdx` | 새 자리 |
| --- | --- |
| `export const steps = [ … ]` | `<name>-guide.sim.ts` 의 `steps` — **인라인 배열 리터럴 그대로** |
| `<AlgorithmSimulation view={…}>` 의 `view` | 같은 파일의 `view` |
| 같은 태그의 `title` | 같은 파일의 `title` |
| `import { AlgorithmSimulation }` · 호출부 | **없어진다.** md 는 `<!--viz:{id}-->` 마커만 둔다 |
| (없음) | **`result` 를 새로 정한다** — 마지막 프레임이 뜻하는 실제 반환값(`P9`) |
| (없음) | **ascii 펜스를 새로 그린다** — 마커 아래에 둔다 |

**뒤의 둘이 이관의 실제 비용이다.** 앞의 셋은 옮기는 일이지만 `result` 와 ascii 는 옛
문서에 없다 — `.mdx` 는 웹에서만 렌더됐으므로 md 쪽 대응물을 가질 이유가 없었다.
`L19`(웹 동등성)가 그것을 요구하는 것이 v2 로 오면서 생긴 차이다.

### 자료구조에서 갈리는 것 — 시뮬이 여럿일 수 있다

알고리즘은 절차 하나라 시뮬도 대개 하나인데, 자료구조는 **연산 묶음마다 `deep.walk.step`
이 서므로** 그 묶음이 각자 보일 것을 가질 수 있다. `.sim.ts` 는 export 를 여럿 둘 수 있고
(`export const {id}`), 마커 id 가 그것을 가른다.

**하나로 묶을지 나눌지는 상태가 정한다** — 한 연산 열을 이어서 굴리는 것이면 시뮬 하나에
프레임을 잇고, 서로 다른 초기 상태에서 출발하면 나눈다. 억지로 하나에 담으면 프레임 사이에
설명 없는 점프가 생긴다.

### 절차 다섯

1. **`.mdx` 에서 `steps` 배열을 통째로 옮긴다.** 이미 인라인 리터럴이라 그대로 간다 —
   `algo SPEC` §5 가 금지하는 변수 참조·함수 호출·spread 가 옛 문서에도 없다(실측).
2. **`view` 와 `title` 을 호출부에서 가져온다.** `view` 를 빠뜨리면 렌더가 실패한다
   (런북 불변 사실 37 — 기본값이 없다).
3. **`result` 를 정하고 실제로 실행해 확인한다.** 마지막 프레임이 뜻하는 반환값이고,
   본문에 `<!--result:{id}-->` 로 같은 값을 적어 `P9` 가 대조한다.
4. **ascii 펜스를 그린다.** 마커 바로 아래에 두고, 비어 있으면 `P6` 이 잡는다.
   md 독자가 보는 것이 이것이고 web 은 이 자리를 대화형 패널로 덮는다.
5. **`.mdx` 를 지운다.** 지우기 전에 `bun run tools/check-links.ts refs <경로>` 로 참조를
   전수 확인하고, `tools/_baseline/guide-rhythm.tsv` 의 그 행도 함께 지운다.

### 판정

- 마커 id ↔ `.sim.ts` export 키 ↔ ascii 펜스가 **3자로 맞는다**(`L11` · `P6`).
- `result` ↔ `<!--result:{id}-->` 가 같다(`L14` · `P9`).
- `bun test src/_guide-sim` 이 통과한다 — 그 모듈은 두 트랙이 함께 쓰므로, 이관 중에
  뷰 프리셋을 건드리면 **살아 있는 편이 런타임에서만 깨진다**(`tools/ci.ts` SELF 가
  그 자리를 지킨다).
