> 인용: "같은 목표를 노리는 **완전히 다른 절차**가 있어요 — **오프라인 + 펜윅 트리(BIT)** 입니다. 창을 이동시키는 대신 배열을 왼쪽부터 **한 번만** 읽습니다. 값 `v` 를 만나면 그 값의 직전 등장 자리를 지우고 지금 자리에 1을 더해요. 그러면 각 값이 **가장 오른쪽 등장에서만** 세지므로, 시점 `i` 에서 구간합 `[l, i]` 이 곧 그 구간의 서로 다른 값 수가 됩니다. 질의를 `r` 로만 정렬하면 한 번 순회로 전부 답할 수 있어요.

같은 입력(`n = 400`, `q = 200`, 고정 시드)에 둘을 걸고 **기본 연산 횟수**를 셌습니다. Mo 는 포인터가 이동한 칸 수(칸마다 맵을 한 번 조회합니다), 펜윅은 트리 노드 방문 수입니다.

| 입력 | Mo · 포인터 이동 칸 | 펜윅 · 트리 노드 방문 |
| --- | --- | --- |
| 전개용 `n = 5`, `q = 5` | **11** | 25 |
| 대조용 `n = 400`, `q = 200` | 6,895 | **4,850** |

**크기를 키우면 순서가 뒤집힙니다.** 작은 입력에서는 펜윅의 트리 높이 상수가 그대로 나와 Mo 쪽이 적고, `n = 400` 에서는 증가 차수 차이(`O((n+q)\log n)` 대 `O((n+q)\sqrt{n})`)가 그 상수를 덮어 펜윅이 1.4배 적어요. **대조에 큰 쪽을 쓰는 이유가 이것입니다** — 전개 입력을 그대로 쓰면 Mo 가 적게 나오지만, 그건 측정한 것이 아니라 유리한 자리를 고른 것이니까요.

그러면 왜 Mo 를 쓸까요? **일반성 때문입니다.** 펜윅 쪽 방법은 「각 값을 가장 오른쪽 등장에서만 센다」는 성질에 통째로 기대고 있어서, 그 성질이 없는 양으로는 **옮겨지지 않습니다.**

| 묻는 양 | 펜윅 트릭 | Mo |
| --- | --- | --- |
| 서로 다른 개수 | 된다 (가장 오른쪽 등장) | 된다 |
| 구간의 최빈값 | 안 된다 | 된다 |
| 구간 내 같은 값 쌍의 수 | 안 된다 | 된다 |
| 구간 내 값의 제곱합 | 누적합이 더 쉽다 | 된다 |

Mo 가 요구하는 것은 **「창을 한 칸 늘리거나 줄일 때 `O(1)` 로 갱신되는가」** 하나뿐이에요. 그 조건만 맞으면 답이 무엇이든 같은 구조가 그대로 동작합니다. 문제마다 새 자료구조를 설계하는 대신 `add`·`remove` 두 함수만 바꿔 끼우면 된다는 것, 그것이 이 알고리즘이 주는 값입니다."

[V3] PASS
> 인용: "어느 시점에나 `count[v]` 는 창 `[curL, curR]` 안에 값 `v` 가 몇 개 있는지이고, `distinct` 는 그중 개수가 1 이상인 `v` 의 가짓수입니다.

```text
넓히기   add(v)     count[v] 0→1 이면 distinct++     (없던 값이 처음 들어왔다)
좁히기   remove(v)  count[v] 1→0 이면 distinct--     (마지막 하나가 빠졌다)
```

「어느 시점에나」가 중요합니다. 질의를 끝낸 시점만이 아니라 **창이 한 칸 이동한 직후마다** 참이라는 뜻이에요. 그래야 답을 아무 때나 읽어도 맞습니다.

**출발점부터 봅시다.** 창이 비어 있을 때(`curL = 0`, `curR = −1`) 맵도 비어 있고 `distinct = 0` 이므로 두 문장이 참입니다. 그 뒤로 창은 **한 칸씩만** 바뀌고, 한 칸이 바뀔 때 `add` 나 `remove` 가 정확히 한 번 불려요. `add` 는 개수를 1 늘리고 그 값이 0에서 1이 될 때만 가짓수를 늘립니다. `remove` 는 개수를 1 줄이고 1에서 0이 될 때만 가짓수를 줄여요. 개수가 정확하면 「0 이 아닌 키의 수」도 정확하니, 매 칸 이동 뒤에도 두 문장이 함께 유지 됩니다.

그러면 여기서 질문 하나. 같은 창에 **다른 경로로** 도착하면 답이 달라질까요?

```text
arr = [1, 1, 2, 1, 3] 에서 같은 창 [1,3] 에 도착하는 두 경로
  경로 A   [0,2] → [1,3]    L− 1번, R+ 1번
  경로 B   [0,4] → [1,3]    L− 1번, R− 1번
둘 다 창 [1,3] 의 값은 1 2 1  →  count{1:2, 2:1}  →  distinct = 2
```

달라지지 않습니다. 불변식이 창 `[curL, curR]` 의 **내용**만 말하고 도착 경로를 말하지 않기 때문이에요. **질의를 재정렬해도 되는 근거가 바로 이것입니다** — 순서를 어떻게 바꿔도 각 질의를 읽는 시점의 창 내용은 같고, 답을 원래 자리 `i` 에 넣어 돌려주므로 호출한 쪽이 받는 결과도 같습니다.

경계에 있는 입력들도 확인하고 갑시다.

| 입력 | 어디서 처리되는가 | 결과 |
| --- | --- | --- |
| 질의 0개 | 첫 줄에서 바로 반환 | `[]` |
| `l = r` | 창이 한 칸. `add` 한 번 | 항상 `1` |
| 모든 값이 같음 | `count` 에 키가 하나뿐 | 항상 `1` |
| `n = 1` | `B = max(1, ⌊√1⌋) = 1` | 0으로 나누는 일이 없다 |"

> 인용: "#### 멈춤 — `Set` 하나로 바꾸고 싶어지는 자리

`count` 맵과 `distinct` 를 따로 유지하는 것이 번거로워 보이지 않나요? 창에 든 값의 집합만 유지하면 크기가 곧 답이니 `Set` 하나면 될 것 같습니다.

```ts
const seen = new Set<number>();
// 넓힐 때 seen.add(v), 좁힐 때 seen.delete(v), 답은 seen.size
```

넓히는 쪽은 실제로 맞아요 — `Set.add` 는 이미 있는 값을 넣어도 아무 일도 하지 않으므로 중복이 알아서 처리됩니다. **좁히는 쪽에서 잘못됩니다.** `Set.delete(v)` 는 창에 `v` 가 **아직 남아 있는지**를 모르기 때문이에요.

```text
창 [0,2] 의 값 1 1 2    Set = {1, 2}        size 2  ✓
curL 을 1 로 좁힌다 → arr[0] = 1 을 delete
창 [1,2] 의 값 1 2      Set = {2}           size 1  ✗  (답은 2)
                        └ 창에 1 이 아직 있는데 지웠다
```

다섯 질의를 끝까지 실행하면 결과가 이렇게 달라집니다. **뒤 세 개가 틀렸어요.**

```text
count 맵   [3, 2, 3, 2, 2]      ← 정답
Set        [3, 2, 2, 1, 1]      ← 좁히기가 시작되는 지점부터 어긋난다
```"

const add = (value: number): void => {

  distinct++;            // ← `if (next === 1)` 을 지웠다
};
```

`mosAlgorithm([1,1,2,1,3], [[0,4],[0,2],[2,4],[1,3],[2,3]])` 을 실행하면 이렇게 나옵니다.

```text
바른 코드   [3, 2, 3, 2, 2]
조건 지움   [6, 3, 6, 4, 5]      ← 전부 부풀었다

> 인용: "#### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축입니다. 섞어서 짝지으면 안 돼요.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최악의 경우** | `O((n+q)\sqrt{n})` | `Θ((n+q)\sqrt{n})` — 이동 상한을 실제로 채우는 질의 집합이 있다 |
| **평균적인 경우** | `O((n+q)\sqrt{n})` | 같다 — **분포와 무관하게 같은 증가 차수**다 |

퀵 정렬 같은 알고리즘과 달리 여기서는 최악과 평균이 **갈리지 않습니다.** 블록 정렬이 이동 상한을 입력과 무관하게 제한하기 때문이에요. 평균이 더 좋아 보이는 것은 상수뿐입니다.

**보장의 종류가 하나 섞여 있습니다.** 창 이동 상한은 **최악 보장**이지만, 셈 갱신에 쓰는 해시 맵의 한 번 조회는 **평균 `O(1)`** 이에요. 그러니 위 표의 값은 엄밀히 말해 「해시가 평균대로 동작한다는 가정 아래의 최악」입니다. 최악까지 확정하고 싶으면 값을 좌표압축해 배열로 세면 되고, 그때는 전처리에 `O(n \log n)` 이 더 붙어요."
