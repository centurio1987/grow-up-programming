# 퀵 정렬 — 피벗 하나를 제자리에 놓으면 나머지가 둘로 갈라진다

## 시작하기 전에 — 이미 알고 있어야 하는 것

- **배열의 자리 바꾸기**가 O(1)이라는 것. `a[i]`와 `a[j]`를 맞바꾸는 데 배열 길이는 상관없다.
- **재귀 호출**이 자기와 같은 모양의 더 작은 문제를 푼다는 것.
- **정렬됐다**는 말의 뜻 — 모든 이웃 쌍 `a[k] ≤ a[k+1]`.

세 번째가 흐릿하면 여기서부터가 헛돈다. 정렬의 정의를 "작은 게 앞"으로만 잡고 있으면
아래에서 나올 "피벗이 제자리를 찾았다"는 말이 무엇을 보장하는지 안 잡힌다.

## 전체 컨셉

값 하나를 골라 **그 값보다 작은 것을 전부 왼쪽, 크거나 같은 것을 전부 오른쪽**으로 밀어 두면,
고른 값은 정렬이 끝난 뒤에 있을 자리에 이미 도착해 있다. 그 자리는 다시는 안 건드린다.

```text
고르기 전        [5 2 3 1]
2 를 기준으로     [1] 2 [5 3]
                  ↑  ↑   ↑
                작은  제자리  큰
```

남은 것은 왼쪽 덩어리와 오른쪽 덩어리인데, 둘 다 원래와 **같은 모양의 더 작은 문제**다.
그래서 같은 절차를 그대로 다시 건다. 한 번 훑을 때마다 값 하나가 확정되고, 운이 좋으면
덩어리가 절반씩 줄어 훑는 횟수가 `n`이 아니라 `log n`번이 된다.

## 아이디어 상세

### 제자리 분할 — 생각이 닿는 경로

**① 문제를 고정한다.**

```ts
function quickSort(nums: number[]): number[];
```

- 입력: 정수 배열 `nums`. **길이 1 이상 50,000 이하**, 각 값은 −50,000 이상 50,000 이하.
- 출력: 같은 원소를 오름차순으로 담은 배열. **입력 배열을 제자리에서 고친다.**

**② 아무 기법 없이 하면 어떻게 되는가.** 가장 단순한 방법은 "가장 작은 것을 찾아 맨 앞에 놓기"를 되풀이하는 것이다. 매번 남은
구간을 전부 훑어야 하므로 비교 횟수가 이렇게 쌓인다.

```text
n-1 + (n-2) + … + 1 = n(n-1)/2
n = 50,000 → 1,249,975,000 번
```

12억 번이다. 단순 연산을 초당 1억 번으로 잡아도 **10초가 넘는다.** 제약이 5만인데
이 방법으로는 못 들어간다.

| 입력 크기 | 비교 횟수 | 초당 1억 번 기준 |
| --- | --- | --- |
| 1,000 | 499,500 | 0.005초 |
| 10,000 | 49,995,000 | 0.5초 |
| **50,000** | **1,249,975,000** | **12.5초** |

**③ 그럼 무엇을 줄일 수 있는가.**

12억이 나온 이유는 **한 번 훑어서 값 하나만 확정**하기 때문이다. 훑기 한 번에 더 많은 것을
알아낼 수 없을까.

```text
훑기 1회 → 확정 1개   :  n 번 훑어야 끝난다      → n × n
훑기 1회 → 구역 2개    :  덩어리가 반씩 줄면      → log n × n
```

여기서 관찰 하나가 생긴다. 값 `p`를 하나 정하고 배열을 한 번만 훑으면서 "`p`보다 작은가"만
물으면, 훑기가 끝났을 때 배열은 이미 **두 구역**으로 갈라져 있다. `p`의 자리도 그때 정해진다 —
왼쪽 구역의 크기가 곧 `p`의 인덱스다. `[5 2 3 1]`에서 `p = 2`로 해 보자.

```text
훑기 전   [5 1 3 | 2]      2 를 끝으로 빼 둔다
j=0  5<2 거짓 → 그대로
j=1  1<2 참   → 작은 구역으로  [1 5 3 | 2]
j=2  3<2 거짓 → 그대로
훑은 뒤   작은 구역 크기 1 → 2 의 자리는 인덱스 1
결과      [1 2 3 5]
```

훑기 **한 번**에 `2`가 확정됐고, 남은 일이 `[1]`과 `[3 5]` 둘로 쪼개졌다. 이것이 12억을
줄이는 지렛대다.

### 수식 정의와 유도

한 번의 분할이 배열을 크기 `k`와 `n−k−1` 두 덩어리로 가른다고 하자. 분할 자체는 구간을
한 번 훑으므로 `n−1`번 비교한다. 그러면 전체 비교 횟수 `T(n)`이 아래처럼 서고, `k`가
무엇이 되느냐가 전부다 — `n = 8`을 넣어 두 극단을 직접 세어 보자.

$$T(n) = T(k) + T(n-k-1) + (n-1), \qquad T(0)=T(1)=0$$

```text
절반씩 갈릴 때                    한쪽이 빌 때
        8 (7번)                          8 (7번)
      /   \                            /   \
     3     4                          0     7 (6번)
    (2)   (3)                              /   \
   /  \   /  \                            0     6 (5번)
  1    1 1    2                                 …
                                                1 (0번)
  합 7+2+3 = 12                        합 7+6+5+…+1 = 28
```

| 갈림 | 점화식 | 닫힌 형태 |
| --- | --- | --- |
| 절반씩 `k = (n−1)/2` | $T(n) = 2T\!\left(\frac{n-1}{2}\right) + (n-1)$ | $\Theta(n \log n)$ |
| 한쪽이 빔 `k = 0` | $T(n) = T(n-1) + (n-1)$ | $\frac{n(n-1)}{2} = \Theta(n^2)$ |

아래쪽 값은 낯익다 — ②에서 본 "가장 작은 것 찾기"의 비교 횟수와 **정확히 같다.**
분할이 한쪽으로만 쏠리면 퀵 정렬은 그 단순한 방법으로 되돌아간다.

### 왜 항상 옳은가

분할이 끝난 시점에 성립하는 것 하나만 보이면 된다.

**주장.** 분할 루프가 끝나면 `arr[lo..i-1]`의 모든 값이 `pivot`보다 작고, `arr[i..hi-1]`의
모든 값이 `pivot` 이상이다.

```text
lo        i          j        hi
 |--- 작음 ---|--- 큼 ---|--- 아직 안 봄 ---| pivot |
```

**논증.** 루프가 도는 동안 위 그림의 두 구역이 계속 그 성질을 지킴을 보인다.

1. **루프 시작 전** — `i = lo`이고 `j = lo`다. 두 구역이 모두 비어 있으니 "모든 원소가 …"는
   공허하게 참이다.
2. **한 바퀴 돌 때** — `arr[j]`를 본다.
   - `arr[j] < pivot`이면 `arr[i]`와 맞바꾸고 `i`를 하나 늘린다. 새로 작은 구역에 들어간 값은
     `arr[j]`이고 조건상 `pivot`보다 작다. 밀려난 `arr[i]`는 큰 구역의 첫 자리로 가는데,
     그 값은 직전까지 큰 구역에 있었으므로 `pivot` 이상이다. 둘 다 유지된다.
   - `arr[j] ≥ pivot`이면 아무것도 안 바꾼다. 큰 구역이 오른쪽으로 한 칸 늘어날 뿐이다.
3. **루프가 끝났을 때** — `j`가 `hi`에 닿았으니 `arr[lo..hi-1]` 전부를 봤고, 위 두 문장이
   그 전체에 대해 참이다.

```text
루프 끝    [작음…][큼…][pivot]      i 가 두 구역의 경계
맞바꾼 뒤  [작음…][pivot][큼…]      pivot 의 최종 자리
```

`arr[i]`와 `arr[hi]`(=`pivot`)를 맞바꾸는 순간 위 그림의 아래 줄이 된다.
**피벗은 최종 위치에 도착했고 다시 옮길 이유가 없다.** 남은 두 구간을 각각 정렬하면
전체가 정렬된다.

**엣지 케이스.**

| 입력 | 어디서 걸리는가 | 결과 |
| --- | --- | --- |
| 빈 배열 `[]` | `hi = -1`, `lo = 0` → `hi - lo = -1 < 1` | 즉시 반환 |
| 원소 하나 `[7]` | `hi - lo = 0 < 1` | 즉시 반환 |
| 원소 둘 `[2 1]` | `pivotIdx = lo + ⌊1/2⌋ = lo` | 분할 한 번으로 끝 |
| 전부 같음 `[2 2 2 2 2]` | `arr[j] < pivot`이 한 번도 참이 아님 | **정답이나 가장 느림** |

마지막 줄이 이 절차의 약한 자리다. `i`가 `lo`에 머무르니 피벗이 맨 앞으로 가고 오른쪽
구간이 `n−1`이 된다 — 한쪽이 완전히 비는 갈림이다.

### 흔한 오해와 그것이 거짓인 이유

**오해: "이미 정렬된 배열이 퀵 정렬의 최악이다."**

이 말은 **첫 원소를 피벗으로 고르는 구현**에서만 참이다. 그때는 분할할 때마다 왼쪽이 비어
`T(n) = T(n−1) + (n−1)`이 된다. 그런데 이 구현은 **중앙**을 고른다. 정렬된 입력
`[0 1 2 3 4 5 6 7]`을 그대로 넣고 비교 횟수를 세어 보면 이렇다.

```text
n = 8 일 때 비교 횟수
  정렬된 [0 1 2 3 4 5 6 7]        13
  역순   [7 6 5 4 3 2 1 0]        15
  최악   [0 3 5 7 1 4 2 6]        28   ← n(n-1)/2 상한
```

정렬된 입력은 13번인데 진짜 최악은 28번이다. **두 배 넘게 차이가 난다.**

```text
정렬된 [0 1 2 3 4 5 6 7]
        중앙 = 3        → [0 1 2] 3 [4 5 6 7]    거의 반씩
        중앙 = 5        → [4] 5 [6 7]            또 반씩
```

정렬된 배열에서 중앙 피벗은 매번 정확히 중앙값이라 오히려 **가장 좋은** 갈림을 만든다.
오해를 그대로 받아들이면 "중앙 피벗을 쓰니 최악이 사라졌다"는 결론까지 가기 쉬운데,
그것도 거짓이다. 28번을 만드는 입력이 실제로 있고, 어떻게 생겼는지는 아래 「최악을 만드는
입력」에서 본다.

### 이해 점검

## 이 알고리즘이 최적인 자리

### 최적인 문제의 모양

- 원소를 **둘씩 비교할 수 있고**, 그 비교가 싸다.
- **추가 메모리를 쓰기 어렵다.** 입력이 이미 메모리를 거의 다 쓰고 있거나, 할당 자체가 비싸다.
- **평균이 중요하고 최악 한 번을 감당할 수 있다.** 응답 시간에 엄격한 상한이 필요하면 다른 선택이다.
- 안정성(같은 값의 원래 순서 유지)이 **필요 없다.** 이 절차는 안정 정렬이 아니다.

### 문제에서 이것을 떠올리게 하는 단서

- "제자리에서 정렬하라" 또는 "추가 배열을 쓰지 말라"는 제약
- 입력 크기가 수만~수백만이고 **평균 성능**만 요구할 때
- "k번째로 작은 값"만 필요할 때 — 분할을 한쪽만 따라가면 그대로 선택 알고리즘이 된다
- 반대로 **"최악에도 몇 초 안에"** 같은 문구가 있으면 이 단서는 꺼진다

### 실제로 쓰이는 곳

- **Go 표준 라이브러리 `sort`** — pdqsort(pattern-defeating quicksort)를 쓴다.
  분할이 나빠지는 것을 감지하면 힙 정렬로 갈아탄다.
  ([`src/sort/zsortfunc.go`](https://cs.opensource.google/go/go/+/master:src/sort/zsortfunc.go), 조회 2026-08-19)
- **C 표준 라이브러리 `qsort`** — 이름 그대로다. glibc 구현은 재귀 대신 명시적 스택을 쓴다.
  ([glibc `stdlib/qsort.c`](https://sourceware.org/git/?p=glibc.git;a=blob;f=stdlib/qsort.c), 조회 2026-08-19)

`Array.prototype.sort`는 V8에서 **TimSort**(병합 정렬 계열)라 여기 들지 않는다 — 안정성을
명세가 요구하기 때문이다.

### 경쟁 설계와의 대조

같은 목표를 노리는 다른 절차로 **병합 정렬**이 있다. 오히려 더 강한 약속을 한다 —
최악에도 `Θ(n log n)`이고, 안정 정렬이다. 그러면 왜 퀵인가.

같은 입력 `[23 4 91 8 15 42 7 66 30 1 58 12 77 25 3 49]`(n=16)에 둘을 걸고 센 값이다.

| | 비교 횟수 | 새로 잡는 칸 |
| --- | --- | --- |
| 퀵 정렬 | 52 | **0** |
| 병합 정렬 | **49** | 64 |

**비교는 병합이 이긴다.** 49 대 52다. 퀵이 이기는 자리는 그 옆 칸이다 — 병합은 합치는
단계마다 새 배열을 잡아 **64칸**을 쓰고, 퀵은 **0칸**으로 끝낸다. 입력이 5만이면 병합은
5만 칸 남짓을 추가로 잡는다.

그래서 선택은 "어느 쪽이 빠른가"가 아니라 **"메모리를 더 쓸 수 있는가, 최악을 감당할 수
있는가"** 다. 둘 다 아니오면 답은 병합이다.

## 코드로 옮기기

### 수도 코드로 본 전체

```text
sort(arr, lo, hi):
    원소가 1개 이하면 반환
    중앙을 피벗으로 골라 끝으로 옮긴다
    i ← lo
    j 를 lo 부터 hi-1 까지:
        arr[j] < pivot 이면 arr[i] 와 맞바꾸고 i 를 늘린다
    피벗을 i 자리로 되돌린다
    sort(arr, lo, i-1)
    sort(arr, i+1, hi)
```

### 피벗을 끝으로 빼 둔다

분할 루프는 "작은 것"과 "나머지" 두 구역만 관리하고 싶다. 피벗이 구간 한가운데 있으면
그 자리를 매번 비켜 가야 하므로, **먼저 끝으로 옮겨** 루프가 `hi` 앞까지만 보게 만든다.

```ts
const pivotIdx = lo + Math.floor((hi - lo) / 2);
[arr[pivotIdx], arr[hi]] = [arr[hi] as number, arr[pivotIdx] as number];
const pivot = arr[hi] as number;
```

```text
[5 2 3 1]  pivotIdx=1
     ↓ 끝과 맞바꾼다
[5 1 3 2]  pivot=2 가 hi=3 에
```

중앙을 고르는 것은 **정렬된 입력에서 한쪽이 비는 사고를 피하려는** 선택이다.
첫 원소를 고르면 정렬된 입력이 곧바로 `Θ(n²)`가 된다.

### 한 번 훑으며 두 구역을 키운다

`i`는 "작은 값이 놓일 다음 자리"이고 `j`는 훑는 자리다. 둘 사이가 큰 구역이다.

```ts
let i = lo;
for (let j = lo; j < hi; j++) {
  if ((arr[j] as number) < pivot) {
    // ① 작은 쪽으로 보내고 그 구역을 한 칸 넓힌다
    [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
    i++;
  }
  // ② 크거나 같다 — 그대로 둔다. j 만 나아간다
}
```

`①`에서 밀려나는 `arr[i]`가 왜 안전한지는 위 「왜 항상 옳은가」의 2번이 답한다 — 그 값은
직전까지 큰 구역에 있었으므로 `pivot` 이상이다.

### 피벗을 두 구역 사이로 되돌린다

루프가 끝나면 `i`가 곧 작은 구역의 크기이고, 그 자리가 피벗의 최종 위치다.

```ts
[arr[i], arr[hi]] = [arr[hi] as number, arr[i] as number];
sort(arr, lo, i - 1);
sort(arr, i + 1, hi);
```

`i`를 양쪽 어디에도 넣지 않는 것이 핵심이다. 피벗은 확정됐으므로 다시 볼 필요가 없고,
넣으면 구간이 줄지 않아 재귀가 끝나지 않을 수 있다.

### 완성 코드

```ts
export function quickSort(nums: number[]): number[] {
  sort(nums, 0, nums.length - 1);
  return nums;
}

function sort(arr: number[], lo: number, hi: number): void {
  if (hi - lo < 1) return;

  const pivotIdx = lo + Math.floor((hi - lo) / 2);
  [arr[pivotIdx], arr[hi]] = [arr[hi] as number, arr[pivotIdx] as number];
  const pivot = arr[hi] as number;

  let i = lo;
  for (let j = lo; j < hi; j++) {
    if ((arr[j] as number) < pivot) {
      [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
      i++;
    }
  }

  [arr[i], arr[hi]] = [arr[hi] as number, arr[i] as number];

  sort(arr, lo, i - 1);
  sort(arr, i + 1, hi);
}
```

## 한 입력으로 끝까지 굴려 보기

`quickSort([5, 2, 3, 1])`을 끝까지 따라간다.

## 비용 계산

### 비용을 세는 과정

한 번의 `sort(lo, hi)` 호출이 하는 비교는 분할 루프뿐이고, 그 횟수는 `hi - lo`다.
T1의 호출은 구간 크기 4에서 **3번**(T3·T4·T5), T8의 호출은 구간 크기 2에서 **1번**(T10)이다.
T7·T12·T13은 즉시 반환이라 0번이다. 합이 4번이고 위에서 센 것과 맞는다.

그러니 전체 비교 횟수는 **재귀 호출들의 구간 크기를 다 더한 값**이다. 그 합이 갈림에 따라
어떻게 달라지는지가 「수식 정의와 유도」의 두 극단이다.

```text
좋은 갈림   구간이 절반씩       → 층이 log n 개, 층마다 n 번   → n log n
나쁜 갈림   한쪽이 매번 빈다     → 층이 n 개, 층마다 n, n-1, … → n²/2
```

여기서 센 것은 **비교 횟수만**이다. 자리 바꾸기와 재귀 호출 자체의 비용은 비교 횟수보다
크지 않은 상수배라 지배항이 바뀌지 않는다. 추가로 잡는 메모리는 없고, **재귀 깊이**가
따로 든다 — 좋은 갈림이면 `Θ(log n)`, 나쁜 갈림이면 `Θ(n)`이다.

### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축이다. 둘을 갈라 적는다.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최악의 경우** | `O(n²)` | `Θ(n²)` — 실제로 도달한다 |
| **평균적인 경우** | `O(n log n)` | `Θ(n log n)` |

최악에서 `Θ(n²)`라고 쓸 수 있는 것은 그 값을 **실제로 내는 입력이 있기** 때문이다.
n=8에서 `[0 3 5 7 1 4 2 6]`이 정확히 `28 = 8·7/2`번 비교한다.

**"평균"이 무엇에 대한 평균인지가 중요하다.** 이 구현에는 난수가 하나도 없다 — 피벗을
중앙에서 결정적으로 고른다.

```text
무작위 피벗   같은 입력을 두 번 넣으면 → 횟수가 다를 수 있다   (구현의 동전 던지기)
중앙 피벗     같은 입력을 두 번 넣으면 → 항상 같은 횟수        (입력 분포의 평균)
```

그러니 여기서 말하는 평균은 **입력 순열이 고르게 분포한다는 가정 아래의 평균**이지,
구현이 만드는 무작위성에 대한 기댓값이 **아니다.** 이 구분이 실무에서 갈리는 자리는
**공격**이다 — 결정적 피벗은 절차를 아는 사람이 최악 입력을 **계산해서** 넣을 수 있다.

### 최악을 만드는 입력

n=8에서 모든 순열 40,320개를 전부 돌려 비교 횟수를 센 결과다.

```text
[0 3 5 7 1 4 2 6]  → 28 번 = 8·7/2   ← 상한에 도달
[7 6 5 4 3 2 1 0]  → 15 번
[0 1 2 3 4 5 6 7]  → 13 번           ← 정렬된 입력은 최악이 아니다
```

이 입력이 하는 일은 하나다 — **매번 중앙 자리에 그 구간의 최솟값 또는 최댓값이 오도록**
배치돼 있다. 그러면 분할이 한쪽으로 완전히 쏠려 구간이 하나씩만 줄어든다.

일반의 `n`에 대해서도 같은 방식으로 만들 수 있다. 절차가 어느 자리를 피벗으로 고르는지
알고 있으면, 그 자리에 놓일 값을 매 단계 역산해 채워 넣으면 된다. **중앙 피벗은 우연한
정렬 입력을 막을 뿐, 의도적으로 만든 입력은 못 막는다.**

## 한 곳을 바꿔 보면

분할 루프의 `i++` **한 줄만** 지워 보자. "작은 쪽으로 보낸다"는 동작은 그대로 두고,
그 구역을 넓히는 것만 안 한다.

```ts
if ((arr[j] as number) < pivot) {
  [arr[i], arr[j]] = [arr[j] as number, arr[i] as number];
  // i++;   ← 이 줄만 지운다
}
```

돌리면 이렇게 나온다.

```text
quickSort([5, 2, 3, 1])           → [2, 3, 5, 1]      (옳은 답 [1, 2, 3, 5])
quickSort([5, 1, 1, 2, 0, 0])     → [1, 2, 1, 0, 0, 5]
quickSort([-10, 5, -3, 0, 8, -1]) → [-3, 0, -1, 8, 5, -10]
```

`i`가 `lo`에 머무르니 작은 값을 찾을 때마다 **같은 자리에** 덮어쓴다. 앞서 넣어 둔 값이
밀려나고, 분할이 끝났을 때 왼쪽 구역이 "작은 값들"이 아니게 된다. 「왜 항상 옳은가」의
2번에서 유지된다고 했던 문장이 바로 여기서 깨진다.

## 스스로 점검하기

- 병합 정렬이 비교를 더 적게 하는데도 이 문제에서 퀵을 고르는 근거는 무엇이었는가?
- 최악 입력을 만들 수 있다는 사실이 실무에서 왜 문제가 되는가?
