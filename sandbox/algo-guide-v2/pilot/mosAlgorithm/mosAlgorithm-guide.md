# Mo's 알고리즘 — 질의를 다시 줄 세우면 창이 √n배 덜 움직인다

## 시작하기 전에 — 이미 알고 있어야 하는 것

- **해시 맵의 넣기·빼기가 평균 O(1)** 이라는 것. 값마다 몇 개 있는지 세는 데 쓴다.
- **정렬이 O(q log q)** 라는 것. 질의를 다시 줄 세울 때 그 비용이 붙는다.
- **오프라인 질의**의 뜻 — 질의를 **전부 미리 받아** 두고 아무 순서로나 처리해도 되는 상황.
  답만 원래 순서로 돌려주면 된다.

세 번째가 이 알고리즘의 전제다. 질의가 하나씩 도착해서 그때그때 답해야 하는 상황이라면
아래 이야기는 아무 쓸모가 없다.

## 전체 컨셉

구간 `[l, r]` 을 훑는 **창** 하나를 들고 다닌다. 창 안에 무엇이 몇 개 있는지 세어 두면
"서로 다른 값의 개수"는 그 셈에서 바로 나온다. 다음 질의로 갈 때는 창을 **처음부터 다시
만들지 않고 양 끝을 밀어서** 옮긴다.

```text
지금 창   [1 1 2]        curL=0 curR=2
다음 질의 [1,3] 로 가려면
          [1 1 2 1]      오른쪽 한 칸 넓히고
            [1 2 1]      왼쪽 한 칸 좁힌다      → 두 칸만 움직였다
```

여기서 값이 나뉜다 — **창을 옮기는 총 비용은 질의를 어떤 순서로 처리하느냐에 달려 있다.**
질의 순서를 그대로 따르면 창이 배열을 왔다 갔다 하며 헛걸음한다. 그래서 질의를 먼저
**다시 줄 세운다.** 왼쪽 끝을 크기 √n 짜리 구역으로 묶고, 같은 구역 안에서는 오른쪽 끝
순으로 놓으면 창의 총 이동이 확 줄어든다.

```text
줄 세우기 전   Q0[0,4]  Q1[0,2]  Q2[2,4]  Q3[1,3]
줄 세운 뒤     Q1[0,2]  Q3[1,3]  Q0[0,4]  Q2[2,4]
               └───── 왼쪽 끝이 같은 구역 ─────┘  └ 다음 구역 ┘
```

답은 원래 질의 자리에 넣어 돌려주므로, 처리 순서를 바꿔도 호출한 쪽은 아무것도 눈치채지 못한다.

## 아이디어 상세

### 창 옮기기 — 생각이 닿는 경로

**① 문제를 고정한다.**

```ts
function mosAlgorithm(arr: number[], queries: [number, number][]): number[];
```

- 입력: 정수 배열 `arr`(길이 `n`), 폐구간 질의 목록 `queries`(길이 `q`). `0 ≤ l ≤ r < n`.
- 출력: 각 구간의 **서로 다른 원소 수**를 담은 배열. 길이는 `q` 이고 **순서는 입력 그대로**.
- 제약: `n ≤ 10^4`, `q ≤ 10^4`. 시간 1초.

**② 아무 기법 없이 하면 어떻게 되는가.** 질의마다 그 구간을 처음부터 다시 훑어 집합에 넣는다.
구간 하나가 최대 `n` 칸이니 이렇게 쌓인다.

```text
질의 하나에 최대 n 칸  →  q × n = 10^4 × 10^4 = 100,000,000 칸
```

1억 칸이다. 칸마다 해시 맵을 한 번씩 두드리므로 실제 상수는 1보다 꽤 크고, 1초 제한에
들어간다고 장담할 수 없다. 게다가 **질의끼리 겹치는 부분을 매번 다시 센다** — `[0,4]` 를
세고 나서 `[1,3]` 을 다시 처음부터 세는 것이 그 낭비다.

**③ 그럼 무엇을 줄일 수 있는가.** 겹치는 부분을 다시 안 세려면 앞 질의의 창을 **그대로 물려받아**
차이만큼만 밀면 된다. 그러면 비용이 "구간 길이의 합"이 아니라 **"창이 움직인 칸 수의 합"** 이 된다.

```text
다시 세기   비용 = 구간 길이의 합       (겹침을 매번 다시 센다)
창 옮기기   비용 = 창이 움직인 칸 수    (차이만 센다)
```

그런데 창 옮기기의 비용은 **질의 순서에 따라 달라진다.** 질의가 `[0,4] [0,2] [2,4] [1,3]`
순으로 오면 오른쪽 끝이 4 → 2 → 4 → 3 으로 요동쳐 헛걸음이 쌓인다. 순서를 우리가 정할 수
있으니(오프라인이다) **덜 움직이는 순서로 다시 줄 세우는 것**이 남은 일이다.

### 수식 정의와 유도

질의를 왼쪽 끝 기준으로 크기 `B` 짜리 구역으로 묶고, 같은 구역 안에서는 오른쪽 끝 순으로
놓는다고 하자. 두 포인터의 이동을 따로 세면 이렇게 서고, `B` 를 어떻게 잡느냐가 전부다.

$$
\text{이동} \;\le\; \underbrace{q \cdot B}_{\text{왼쪽 끝}} \;+\; \underbrace{\frac{n}{B} \cdot n}_{\text{오른쪽 끝}}
$$

```text
왼쪽 끝   같은 구역 안에서는 최대 B 칸씩만 움직인다     → 질의당 B,  합 qB
오른쪽 끝  한 구역 안에서는 한 방향으로만 흐른다(최대 n)
          구역이 n/B 개이므로                          → 합 (n/B)·n
```

두 항의 합을 가장 작게 만드는 `B` 는 둘이 같아질 때다. 아래 식을 푼 뒤 `n = q = 10^4` 에
몇 가지 `B` 를 넣어 보면 왜 √n 인지가 눈에 보인다.

$$q B = \frac{n^2}{B} \;\Rightarrow\; B = \frac{n}{\sqrt{q}} \;\xrightarrow{\;n = q\;}\; B = \sqrt{n}$$

| `B` | 왼쪽 끝 `qB` | 오른쪽 끝 `n²/B` | 합 |
| --- | --- | --- | --- |
| 10 | 100,000 | 10,000,000 | 10,100,000 |
| **100** = √n | **1,000,000** | **1,000,000** | **2,000,000** |
| 1,000 | 10,000,000 | 100,000 | 10,100,000 |

`B = √n` 에서 총 이동이 `O((n + q)\sqrt{n})` 이 되고, 1억이 200만 규모로 내려온다.

### 왜 항상 옳은가

**주장.** 각 질의를 처리한 시점에 `count` 맵은 창 `[curL, curR]` 안의 값별 개수를 정확히 담고,
`distinct` 는 그중 개수가 1 이상인 값의 가짓수와 같다.

```text
넓히기   add(v)     count[v] 0→1 이면 distinct++     (없던 값이 처음 들어왔다)
좁히기   remove(v)  count[v] 1→0 이면 distinct--     (마지막 하나가 빠졌다)
```

**논증.** 창이 비어 있을 때(`curL = 0`, `curR = -1`) 맵도 비어 있고 `distinct = 0` 이라
성립한다. 그 뒤 창은 **한 칸씩만** 바뀌고, 한 칸이 바뀔 때 `add` 나 `remove` 가 정확히 한 번
불린다. `add` 는 개수를 1 늘리고 그 값이 0에서 1이 될 때만 가짓수를 늘리며, `remove` 는
반대다. 그러니 매 칸 이동 뒤에도 두 문장이 유지된다.

**순서가 중요하다.** 코드는 **넓히기를 먼저, 좁히기를 나중에** 한다. 반대로 하면 `curL` 이
`curR` 을 앞질러 **담지도 않은 값을 빼는** 일이 생긴다.

```text
arr=[1 2 3 1 2 3]  queries=[[0,1],[4,5]]  block=2
창 [0,1] 에서 [4,5] 로 갈 때 좁히기를 먼저 하면
  curL=2 에서 값 3 을 뺀다 → count[3] = -1   (창 밖이다)
  curL=3 에서 값 1 을 뺀다 → count[1] = -1
```

**다만 이 문제에서는 그것으로 답이 갈리지 않는다.** 무작위 입력 30,000회를 돌려 두 순서를
대조했더니 **답이 달라진 경우는 0건**이었고, 카운트가 음수가 된 경우만 4,200건이었다.
distinct 세기는 `0 ↔ 1` 경계만 보므로 음수로 내려간 값이 다시 0을 지나며 상쇄되기 때문이다.
그래도 **불변식을 깨는 코드는 남기지 않는다** — 창을 다른 양(합·최댓값·구간 내 쌍의 수)에
쓰는 순간 상쇄가 성립하지 않는다.

**엣지 케이스.**

| 입력 | 어디서 걸리는가 | 결과 |
| --- | --- | --- |
| 질의 0개 | 첫 줄에서 바로 반환 | `[]` |
| `l = r` | 창이 한 칸. `add` 한 번 | 항상 `1` |
| 모든 값이 같음 | `count` 에 키가 하나뿐 | 항상 `1` |
| `n = 1` | `block = max(1, ⌊√1⌋) = 1` | 0으로 나누는 일이 없다 |

마지막 줄이 `Math.max(1, …)` 가 있는 이유다. `n` 이 0이나 1일 때 `block` 이 0이 되면
`⌊l / 0⌋` 이 `Infinity` 가 되어 정렬이 무너진다.

### 흔한 오해와 그것이 거짓인 이유

**오해: "서로 다른 개수를 세는 거니까 `Set` 하나면 된다. 넓힐 때 `add`, 좁힐 때 `delete`,
답은 `set.size`."**

그럴듯하다. 창에 든 값의 집합을 그대로 들고 다니면 크기가 곧 답이니까. 넓히는 쪽은 실제로
맞다 — `Set.add` 는 이미 있는 값을 넣어도 아무 일도 안 하므로 중복이 알아서 흡수된다.
**좁히는 쪽에서 무너진다.** `Set.delete(v)` 는 창에 `v` 가 **아직 남아 있는지**를 모른다.

```text
arr = [1 1 2 1 3]
창 [0,2] = [1 1 2]      Set = {1, 2}        size 2  ✓
curL 을 1 로 좁힌다 → arr[0]=1 을 delete
창 [1,2] = [1 2]        Set = {2}           size 1  ✗  (답은 2)
                        └ 창에 1 이 아직 있는데 지웠다
```

같은 질의 묶음을 끝까지 돌리면 이렇게 갈린다.

```text
count 맵  [3, 2, 3, 2]      ← 정답
Set       [3, 2, 2, 1]      ← 뒤 두 개가 틀렸다
```

**개수를 세야 하는 이유가 여기 있다.** `count[v]` 가 `1 → 0` 이 될 때만 가짓수를 줄이면
"마지막 하나가 빠졌는가"를 정확히 알 수 있다. `Set` 은 그 정보를 애초에 안 들고 있다.

### 이해 점검

`block` 을 `√n` 이 아니라 **1로** 두면 이동 상한이 얼마가 될까? `n = q = 10^4` 로 계산해 보라.

<!--check:blockone-->
「수식 정의와 유도」의 상한 `qB + (n/B)·n` 에 `B = 1` 을 넣으면
`10^4 · 1 + 10^4 · 10^4 = 10^4 + 10^8 ≈ 10^8` 이다. `B = √n = 100` 일 때의 `2 × 10^6` 보다
**50배** 크고, ②에서 본 순진한 방법(1억 칸)과 같은 자리로 되돌아간다.
`B` 를 1로 두면 구역이 `n` 개가 되어 `curR` 이 `n` 번 되감기기 때문이다.
<!--/check-->

## 이 알고리즘이 최적인 자리

### 최적인 문제의 모양

- 질의가 **오프라인**이다 — 전부 미리 받아 두고 순서를 내가 정할 수 있다.
- 답이 **구간에서 정의되고**, 창을 **한 칸 늘리거나 줄일 때 O(1)로 갱신**된다.
- 배열이 **안 바뀐다.** 중간에 값이 갱신되면 창을 물려받는 전제가 깨진다.
- `n` 과 `q` 가 비슷한 규모이고 `n\sqrt{n}` 이 제한에 들어간다.

### 문제에서 이것을 떠올리게 하는 단서

- "질의를 **모두 입력받은 뒤**" · "질의 순서와 같은 순서로 출력"
- 구간에 대해 묻는데 **누적합으로는 안 되는** 양 — 서로 다른 개수, 최빈값, 구간 내 쌍의 수
- 갱신이 없고 질의만 많다
- 반대로 **"질의가 온라인으로 들어온다"** 거나 **"중간에 값을 바꾼다"** 는 문구가 있으면
  이 단서는 꺼진다

### 실제로 쓰이는 곳

이 이름 그대로 표준 라이브러리에 들어간 사례는 **찾지 못했다.** 지어내지 않고 그대로 적는다.
쓰이는 자리는 경쟁 프로그래밍과 오프라인 분석 배치 쪽이다.

- 원 출처는 Mo Tao 가 소개한 것으로 알려져 있으나 **1차 문헌을 확인하지 못했다.**
  널리 인용되는 정리는 Codeforces 블로그다
  ([Codeforces #340134](https://codeforces.com/blog/entry/340134), 조회 2026-08-19).

### 경쟁 설계와의 대조

같은 목표를 노리는 **완전히 다른 절차**가 있다 — **오프라인 + 펜윅 트리(BIT)**다.
창을 옮기는 대신 배열을 왼쪽부터 **한 번만** 훑는다. 값 `v` 를 만나면 그 값의 직전 등장
자리를 지우고 지금 자리에 1을 세운다. 그러면 각 값이 **가장 오른쪽 등장에서만** 세지므로,
시점 `i` 에서 구간합 `[l, i]` 이 곧 그 구간의 서로 다른 값 수다. 질의를 `r` 로만 정렬하면
훑기 한 번으로 전부 답한다.

같은 입력(`n = 400`, `q = 200`, 고정 시드)에 둘을 걸고 **기본 연산 횟수**를 셌다.
Mo 는 포인터가 움직인 칸 수(칸마다 맵을 한 번 두드린다), 펜윅은 트리 노드 방문 수다.

| 설계 | 기본 연산 | 값 |
| --- | --- | --- |
| Mo (블록 + `r`) | 포인터 이동 칸 | 6,895 |
| **펜윅 트리** | 트리 노드 방문 | **4,850** |

**이 문제에서는 펜윅이 이긴다.** 1.4배 적다. 계급도 `O((n+q)\log n)` 으로 Mo 의
`O((n+q)\sqrt{n})` 보다 좋다.

그러면 왜 Mo 인가. **일반성이다.** 펜윅 쪽 트릭은 "각 값을 가장 오른쪽 등장에서만 센다" 는
성질에 통째로 기대고 있어서, 그 성질이 없는 양으로는 **옮겨지지 않는다.**

| 묻는 양 | 펜윅 트릭 | Mo |
| --- | --- | --- |
| 서로 다른 개수 | 된다 (가장 오른쪽 등장) | 된다 |
| 구간의 최빈값 | 안 된다 | 된다 |
| 구간 내 같은 값 쌍의 수 | 안 된다 | 된다 |
| 구간 내 값의 제곱합 | 누적합이 더 쉽다 | 된다 |

Mo 가 요구하는 것은 **"창을 한 칸 늘리거나 줄일 때 O(1)로 갱신되는가"** 하나뿐이다.
그 조건만 맞으면 답이 무엇이든 같은 틀이 그대로 돈다. 문제마다 새 자료구조를 설계하는 대신
`add`·`remove` 두 함수만 갈아 끼우면 된다는 것이 이 알고리즘이 파는 값이다.

## 코드로 옮기기

### 수도 코드로 본 전체

```text
mosAlgorithm(arr, queries):
    질의가 없으면 [] 반환
    block ← max(1, ⌊√n⌋)
    질의에 원래 인덱스를 붙여 (⌊l/block⌋, r) 로 정렬
    curL ← 0, curR ← -1, distinct ← 0
    각 질의 q 에 대해:
        넓히기: curL 을 q.l 까지 내리고, curR 을 q.r 까지 올린다
        좁히기: curL 을 q.l 까지 올리고, curR 을 q.r 까지 내린다
        out[q.원래인덱스] ← distinct
    out 반환
```

### 원래 순서를 잃지 않게 인덱스를 붙인다

질의를 재배열하면 답이 나오는 순서도 뒤섞인다. 그래서 정렬 **전에** 각 질의에 원래 자리를
달아 두고, 답을 그 자리에 넣는다.

```ts
const order = queries.map((q, i) => ({ l: q[0], r: q[1], i }));
```

```text
Q0[0,4]  Q1[0,2]  Q2[2,4]  Q3[1,3]      ← 원래 순서 (i 를 달아 둔다)
Q1[0,2]  Q3[1,3]  Q0[0,4]  Q2[2,4]      ← 처리 순서
   ↓2       ↓2       ↓3       ↓3
out[1]=2  out[3]=2  out[0]=3  out[2]=3  ← i 자리에 넣는다 → [3,2,3,2]
```

### 두 키로 줄을 세운다

왼쪽 끝은 **구역 번호**로, 같은 구역 안에서는 **오른쪽 끝**으로 정렬한다.

```ts
const block = Math.max(1, Math.floor(Math.sqrt(arr.length)));
order.sort((x, y) => {
  const bx = Math.floor(x.l / block);
  const by = Math.floor(y.l / block);
  if (bx !== by) return bx - by;
  return x.r - y.r;
});
```

```text
n=5 → block=2
Q0[0,4] blk=0   Q1[0,2] blk=0   Q2[2,4] blk=1   Q3[1,3] blk=0
정렬 후: Q1[0,2]  Q3[1,3]  Q0[0,4]   |   Q2[2,4]
         └── blk 0, r 오름차순 ──┘       └ blk 1 ┘
```

`Math.max(1, …)` 이 없으면 `n ≤ 1` 일 때 `block = 0` 이 되고 `⌊l/0⌋` 이 `Infinity` 라
정렬이 무너진다.

### 창을 한 칸씩 밀며 셈을 갱신한다

넓힐 때는 `add`, 좁힐 때는 `remove` 를 부른다. 가짓수는 **0↔1 경계에서만** 바뀐다.

```ts
while (curL > q.l) add(arr[--curL] as number);   // ① 넓히기 — 왼쪽
while (curR < q.r) add(arr[++curR] as number);   // ① 넓히기 — 오른쪽
while (curL < q.l) remove(arr[curL++] as number); // ② 좁히기 — 왼쪽
while (curR > q.r) remove(arr[curR--] as number); // ② 좁히기 — 오른쪽
```

**넓히기가 먼저다.** 좁히기를 먼저 하면 `curL` 이 `curR` 을 앞질러 담지도 않은 값을 빼게 된다.
「왜 항상 옳은가」에서 짚은 자리다.

### 완성 코드

```ts
export function mosAlgorithm(
  arr: number[],
  queries: [number, number][],
): number[] {
  if (queries.length === 0) return [];

  const block = Math.max(1, Math.floor(Math.sqrt(arr.length)));
  const order = queries.map((q, i) => ({ l: q[0], r: q[1], i }));
  order.sort((x, y) => {
    const bx = Math.floor(x.l / block);
    const by = Math.floor(y.l / block);
    if (bx !== by) return bx - by;
    return x.r - y.r;
  });

  const count = new Map<number, number>();
  let distinct = 0;
  const add = (value: number): void => {
    const next = (count.get(value) ?? 0) + 1;
    count.set(value, next);
    if (next === 1) distinct++;
  };
  const remove = (value: number): void => {
    const next = (count.get(value) as number) - 1;
    count.set(value, next);
    if (next === 0) distinct--;
  };

  const out = new Array<number>(queries.length);
  let curL = 0;
  let curR = -1;

  for (const q of order) {
    while (curL > q.l) add(arr[--curL] as number);
    while (curR < q.r) add(arr[++curR] as number);
    while (curL < q.l) remove(arr[curL++] as number);
    while (curR > q.r) remove(arr[curR--] as number);
    out[q.i] = distinct;
  }

  return out;
}
```

`n = 5` 이므로 `block = ⌊√5⌋ = 2` 다.

`①`은 T1·T2·T3·T5·T8·T9에서, `②`는 T6·T11·T12에서 밟았다. 창이 움직인 칸은 모두 **9칸**이고,
반환값은 `[3, 2, 3, 2]` 다 — 원래 질의 순서 그대로다.

T2와 T6이 이 알고리즘의 미묘한 자리다. 둘 다 값 `1` 을 건드리는데 `distinct` 가 안 바뀐다 —
개수가 `1→2` 이거나 `2→1` 이라 0↔1 경계를 안 넘기 때문이다.

## 비용 계산

### 비용을 세는 과정

한 번의 호출이 하는 일은 셋이고, 셋을 다 더해야 총식이 된다.
- **질의 정렬** — `q` 개를 정렬한다. `O(q \log q)`.
- **창 이동** — T1~T13 에서 실제로 움직인 칸이 9칸이었다. 일반의 상한은 「수식 정의와 유도」의
  `qB + (n/B)n` 이고, `B = √n` 에서 `O((n + q)\sqrt{n})` 이다.
- **셈 갱신** — 창이 한 칸 움직일 때마다 해시 맵을 한 번 두드린다. 이동 칸 수에 비례한다.

```text
총식 = O(q log q)  +  O((n + q)√n)  +  O(이동 칸 수 × 맵 1회)
                ↑ 전처리        ↑ 지배항
n = q = 10^4 이면   10^4·14 ≈ 1.4×10^5   +   2×10^4·100 = 2×10^6
```

정렬 항은 지배항의 1/14 쯤이라 흔히 생략되지만, **총식에 한 번은 정확히 적는다.**
`q` 가 `n` 보다 훨씬 크면 `q \log q` 가 앞설 수도 있다.

### 케이스별 비용과 그 경계

**케이스**(어떤 입력인가)와 **경계**(어떤 종류의 값인가)는 다른 축이다.

| | 상한 `O` | 타이트 `Θ` |
| --- | --- | --- |
| **최악의 경우** | `O((n+q)\sqrt{n})` | `Θ((n+q)\sqrt{n})` — 이동 상한을 실제로 채우는 질의 집합이 있다 |
| **평균적인 경우** | `O((n+q)\sqrt{n})` | 같다 — **분포와 무관하게 같은 계급**이다 |

퀵 정렬 같은 알고리즘과 달리 여기서는 최악과 평균이 **갈리지 않는다.** 블록 정렬이 이동
상한을 입력과 무관하게 눌러 두기 때문이다. 평균이 더 좋아 보이는 것은 상수뿐이다.

**보장의 종류가 하나 섞여 있다.** 창 이동 상한은 **최악 보장**이지만, 셈 갱신에 쓰는 해시
맵의 한 번 두드리기는 **평균 O(1)** 이다. 그러니 위 표의 값은 엄밀히 말해 "해시가 평균대로
동작한다는 가정 아래의 최악" 이다. 최악까지 확정하고 싶으면 값을 좌표압축해 배열로 세면
되고, 그때는 전처리에 `O(n \log n)` 이 더 붙는다.

### 최악을 만드는 입력

이동 상한을 실제로 채우려면 **왼쪽 끝은 한 구역 안에 몰아 두고 오른쪽 끝을 양극단으로**
흔들면 된다. 같은 구역 안이라 `r` 로 정렬되지만, 구역이 바뀌는 순간 `curR` 이 되감긴다.

```text
n=400, block=20 일 때
  구역 0 의 질의들:  [0,399] [1,398] [2,397] …   r 이 큰 값에 몰려 있다
  구역 1 로 넘어가며  curR 이 399 → 작은 값으로 되감긴다
  구역이 n/B = 20 개  →  되감기가 20번, 매번 최대 n=400 칸
```

`n`·`q` 를 최대(`10^4`)로 잡고 이 모양을 만들면 이동이 `2 \times 10^6` 칸 규모가 된다.
1초 제한에는 들어가지만 **여유가 크지 않다** — `n` 이 한 자릿수만 더 커져도 위험하다.

## 한 곳을 바꿔 보면

`add` 의 조건 **한 줄만** 지워 보자. 개수를 늘리는 것은 그대로 두고, 가짓수를 **0↔1 경계에서만**
늘리던 조건을 없앤다.

```ts
const add = (value: number): void => {
  const next = (count.get(value) ?? 0) + 1;
  count.set(value, next);
  distinct++;            // ← `if (next === 1)` 을 지웠다
};
```

`mosAlgorithm([1,1,2,1,3], [[0,4],[0,2],[2,4],[1,3]])` 을 돌리면 이렇게 나온다.

```text
바른 코드   [3, 2, 3, 2]
조건 지움   [6, 3, 6, 4]      ← 전부 부풀었다
```

`[0,4]` 의 답이 3 이 아니라 6 이다. 배열 `[1 1 2 1 3]` 에 값은 세 가지뿐인데 6이 나온 것은
**같은 값을 넣을 때마다 가짓수를 늘렸기** 때문이다 — `1` 이 세 번 들어가며 3을 더했다.

`remove` 쪽 조건(`next === 0`)은 그대로라 빼는 쪽만 정상이고, 그래서 값이 일관되게 부풀지도
않는다. 「한 입력으로 끝까지 굴려 보기」의 T2와 T6이 정확히 이 조건이 일하는 자리였다 —
둘 다 값 `1` 을 건드렸는데 `distinct` 가 안 바뀌었다.

## 스스로 점검하기

- T2와 T6에서 `distinct` 가 안 바뀐 이유를 `count` 맵의 값으로 설명해 보라.
