## 불변 사실 (매 배치 공통)

1. 적용 범위는 `src/data-structures/` 69종뿐이다. `src/algorithms/` 107종은 현행 유지.
2. `<name>-problem.md`는 제거한다. 대체물은 `<name>.ts` 헤더 JSDoc의 계약 명세다.
3. `<name>.ts` 본문은 실습 스텁(`Not implemented`)으로 유지한다.
4. 명세에 **내부 표현·알고리즘을 처방하지 않는다.** 진단된 A급 결함 4건의 직접 원인이 이것이다.
5. 테스트는 3축이다 — 축1 동작 / 축2 불변식 / 축3 복잡도 계약.
6. 축3은 절대 카운트가 아니라 **성장률** $r = C(4n)/C(n)$ 로 판정한다. 특정 구현을 강제하지 않기 위해서다.
7. 축3은 **벽시계를 쓰지 않는다.** 구현이 노출하는 `__cost` 누적 카운터로만 잰다. 벽시계는 `_bench/`로 격리하고 CI 판정에서 제외한다. **B10 이 강제 지점을 붙였다** — `tools/check-contract.ts` 가 계약을 적은 구조의 `<name>.test.ts` 에서 `performance.now` 호출을 구문 트리로 센다(산문 언급은 세지 않는다).
8. 언어 우선순위는 TypeScript → Rust → Python. Python은 정의만 두고 산출물 요구는 보류한다.
9. 언어 에스컬레이션은 2등급이다 — (가) TS로 계약 충족 불가 → Rust 필수 / (나) 점근 계약은 되나 실측 불가 → Rust 선택.
10. 가이드는 문제가 아니라 자료구조를 다룬다. 캔버스 8단계, 문제 스토리 금지.
11. 가이드 코드는 복제하지 않는다. `// #region guide:core` 로 `_reference/`에서 추출한다.
12. 집필은 `Skill(authoring-kit:authoring-write) --spec ds-guide` 로만 한다. **구 경로 폴백은 없다** — 플러그인이 안 잡히면 거기서 멈춘다.
13. 집필 규칙의 정본은 이 저장소가 아니라 `authoring-kit` 플러그인의 spec·voice다. 규칙을 스킬 문서에 다시 쓰지 않는다.
14. 과장·구어 표현을 쓰지 않는다. 지어낸 은유 동사(무너지다·버티다·밟다)와 가짜 질문 부정 도입도 금지다(principles D5·F5).
15. 확인하지 않은 수치를 쓰지 않는다. 본문에 싣는 값은 실제로 돌려 본 것만.
16. 카테고리는 **계약(ADT)** 으로 가른다. 구현으로 가르지 않는다(B1 확정). 구현이 자유로우면 구현으로 나눈 분류는 정해지지 않는다.
17. 확정된 규약의 정본은 `docs/ORD-006-conventions.md`다. 전략과 어긋나면 conventions 가 이긴다.
18. 기계가 읽는 파일(TSV 등)의 값은 **ASCII 로 쓴다.** `en_US.UTF-8` 로케일의 `awk`·`uniq`는 한글 자모를 서로 같다고 판정한다.
19. 계약 명세는 `<name>.ts` 헤더 JSDoc **한 곳**이다. 메서드별 JSDoc 을 두지 않는다. 여섯 항목(목적·불변식·연산 계약·주입 정책·검증 등급·필요충분조건) 고정이고, 빈 항목은 지우지 않고 "없다 + 이유"로 남긴다.
20. **스텁 클래스 본문에는 공개 계약 표면만 둔다.** private 필드·메서드는 산문보다 강한 처방이다 — 구현자가 채워야 할 빈칸으로 읽힌다.
21. 복잡도는 연산마다 `worst`/`amortized`/`expected` 중 하나를 달고, **가장 약한 한정자**를 적는다. 강한 한정자는 정당한 구현을 배제하는 우회 처방이다.
22. **전 등급이 축3을 돈다.** 등급은 축을 켜고 끄지 않고 엄격도(회귀/판별)를 가른다. 축2가 `basic` 에서 비는 것은 끄기 때문이 아니라 불변식 절이 비어 검사할 성질이 공집합이기 때문이다.
23. `__cost` 는 **계약이 아니라 `_reference/` 의 의무다.** 스텁에 요구하지 않고 헤더에 적지 않는다. 축3의 대상은 정본이다 — 진단된 A급 결함이 "명세와 정본이 서로 다른 복잡도를 주장한 것"이었기 때문이다.
24. **적대적 입력은 하나로 부족하다.** 적대성은 계약이 아니라 구현에 대해 정의된다 — 오름차순 삽입은 탐색 트리에 최악이고 정렬 배열에는 최선이다. 시나리오를 구현 종류만큼 둔다.
25. 인용은 **파일 경로를 붙여 적는다.** `` `:82` `` 같은 상대 인용은 검색으로 찾지 못해 조용히 썩는다. `bun run tools/check-citations.ts` 가 경로 있는 인용을 전부 검증한다. **B11 이 그 "전부"를 넓혔다** — 그전에는 재집필 구조를 손으로 등록하는 목록이었고 `.mdx` 가 확장자에 없어서 B7~B9 산출물 셋과 가이드 전부가 검사 밖이었다. 이제 `src/data-structures` 전체와 `.mdx` 를 본다.
26. 린트는 `bunx --bun @biomejs/biome check` 다. **`bunx biome` 은 다른 패키지이고 아무것도 검사하지 않는다**(`CLAUDE.md` 검증 명령).
27. 가이드 골격의 정본은 `.claude/authoring/specs/ds-guide/spec.json` 의 `sections[]` 다. 캔버스는 렌더 템플릿이고, 둘이 어긋나면 spec 이 이긴다 — 집필기가 읽는 것이 spec 이다.
28. **가이드는 계약 표를 복사하지 않는다.** 계약 정본은 `<name>.ts` 헤더 한 곳이고(규약1) 가이드는 조건이 아니라 **조건의 이유**를 쓴다.
29. 가이드 본문 코드는 `bun run tools/guide-core.ts check` 가 `_reference/` 추출본과 대조한다. 손으로 옮겨 적으면 한 글자 차이도 걸린다.
30. `함정`·`덫`·`지뢰` 를 **명사째로** 쓰지 않는다(원칙 D12). D5(은유 동사)와 별개 조항이다.
31. **집필 원칙(`~/.claude/authoring/principles`)은 배치 도중에도 전진한다.** B4 한 세션 동안 두 번 움직였다. 배치 시작에 `authoring.py lock` 을 보고, 끝낼 때 다시 본다.
32. 검증은 **`bun run tools/ci.ts all` 하나**로 돈다. CI 가 도는 것과 같은 3모드 + 게이트다. 이 저장소의 테스트는 일부러 실패하므로(스텁) `bun test` 하나로는 판정이 안 된다.
33. 파일을 **지우거나 옮기기 전에 `bun run tools/check-links.ts refs <경로>`** 를 돌린다. 손 grep 은 패턴을 빠뜨리고, 빠뜨린 것을 본인이 알 수 없다. **B11 이 그 도구 자체의 구멍을 메웠다** — 저장소 기준 경로 문자열만 봐서 `../hash/multiset/…` 꼴의 상대 import 를 통째로 놓쳤고, 스윕이 완전하다고 보고한 뒤 `tsc` 가 잡았다. 이제 상대 경로를 그 파일 위치 기준으로 풀어 대조하고(확장자를 뗀 import 포함) `tools/check-links.test.ts` 가 회귀를 막는다.
34. `_scratch/`·`_deprecated/` 는 **타입 검사 대상이 아니다**(`tsconfig.json` exclude). 살아 있는 코드가 그 둘을 참조하지 않는 것을 확인하고 뺐다 — 오류 1048건이 상시로 뜨면 그 검사는 판정에 못 쓰인다.
35. **불변식은 상태의 성질이다.** 한 연산의 반환값에 대한 조건은 그 연산의 의미이므로 축1(참조 모델 대조)의 몫이고, 축2에 두면 같은 것을 두 곳에서 검사한다. 축2에 넣을 것은 **연산 사이의 정합**뿐이다.
36. **균형·높이 같은 내부 표현의 성질을 검사하지 않는다.** 계약에 적혀 있어야 검사할 수 있는데, 적는 순간 그것이 처방이다. 균형이 깨진 구현은 축3의 성장률이 잡는다.
37. 가이드의 `<AlgorithmSimulation>` 에는 **`view` 를 반드시 적는다.** 기본값이 없어 빠뜨리면 렌더가 죽고, MDX 는 빌드 때 렌더되지 않아 조용히 지나간다. `entries` 를 쓰면 `view={["...", "keyValue"]}` 다. `bun run tools/guide-core.ts check` 가 전수로 본다.
38. **계약의 모든 문장은 그 계약을 만족하는 모든 구현에 대해 참이어야 한다.** 구현 하나를 지목해야만 참인 진술(메모리 이득·캐시 지역성·할당 횟수·상수 배수)은 계약이 아니다. 지우지 말고 가이드로 옮긴다.
39. **불변식 판별은 두 물음이다(B10 통합).** ① 그 성질이 말하는 양을 읽는 공개 연산이 하나면 불변식이 아니다 — 대조할 상대가 없고, 그 조건은 축1이 본다. ② 둘 이상이면 그 정합을 어느 계약 줄이 이미 적고 있는지 본다. 적고 있으면 그 연산의 의미다(`isEmpty()` 의 의미가 `size() === 0`). 안 적고 있으면 불변식이다. 흩어져 있던 B2·B8·B9 기준 셋이 이 둘의 특수 사례였다.
40. **축이 못 보는 결함이 있고, 축을 늘려 받지 않는다.** 네 축이 전부 통과시키는데 진단이 참일 수 있다. 그 자리는 규약4 (나)가 받고 가이드 6단계가 서술한다. **(나)는 Rust 산출물을 강제하지 않는다** — "옮겨도 안 된다"도 완결된 답이다. 다만 (나)가 받지 않는 경우가 있다(불변 사실 45).
41. **규격을 고치면 그 규격의 실물 예도 같은 배치에서 고친다.** 규칙만 고치고 예시를 두면 다음 집필이 예시를 따른다 — 두 번 물렸다(B7 모범 예시가 5단계 문형이었던 것, B10 이 `tree/multiset` 의 불변식을 소급 교정한 것). 규약1 「계약 명세 실물 예」·`paths.json` 의 `exemplars` 가 그 목록이다.
42. **산문으로 적은 기준은 강제 지점이 없으면 샌다.** B2 의 불변식 기준이 같은 파일의 계약 표와 어긋나 있었는데 세 배치가 지나도록 아무도 못 봤다. 기계가 셀 수 있는 부분만이라도 게이트로 내린다 — 셀 수 없는 부분은 한계를 규격에 적는다.
43. **두 구조가 하나인 것은 두 계약을 만족하는 구현 집합이 같을 때다.** 연산이 겹치는 것도, 한쪽 연산이 다른 쪽으로 유도되는 것도 근거가 아니다. **포섭은 "같다"가 아니라 "다르다"의 증거다** — 계약이 더 많이 약속하면 만족하는 구현이 줄어든다. 판정 방법은 반례 하나이고, 그 반례를 **정본에서 찾지 않는다**(정본끼리 비교하면 계약이 아니라 구현을 비교하게 된다).
44. **계약 스위트의 시나리오는 계약을 겨눈다.** 특정 구현의 내부를 읽어야 만들 수 있는 입력은 시나리오가 아니다 — 그 스위트는 다른 정당한 구현을 통과시키지 못하고, 명세가 구현을 처방하지 않기로 한 전제가 스위트 쪽에서 무너진다. B11 에서 실제로 그런 입력을 만들었고(정본 트립의 결정론적 우선순위) 넣지 않았다.
45. **축이 못 보는 결함의 처분은 셋으로 갈린다.** 언어가 계약 자체를 막으면 규약4 (가), 근거만 막으면 (나), **아무것도 안 막으면 등급이 아니라 가이드다.** 규약4 는 언어의 한계를 재는 등급이지 구현의 교환을 재는 등급이 아니다.
46. **가이드 재집필은 외부 검토를 돌린다.** `ds-guide` spec 이 `hard-fail` 로 켜 뒀다(`review-external.sh` — codex + agy). B11 에서 그것이 **네 축과 집필이 모두 통과시킨 정본의 약점**을 잡았고, B12 에서는 **계약 헤더에 적힌 거짓 명제**를 잡았다. 지적을 전부 받지는 않는다 — 받은 것과 기각한 것을 배치 결과에 적는다.
47. **연산 집합은 계약의 결과가 아니라 계약의 일부다.** 재집필은 연산 표면을 그대로 두고 상한만 고쳐 적는 일이 아니다. 물려받은 표면이 이미 계약을 망가뜨려 놓았으면 정직한 문장으로 적힌 쓸모없는 구조가 남는다. **판별은 필요충분조건 항목이 한다** — 비용 조건을 "못 지키면 무엇이 되는가"로 끝내지 못하면 연산 집합이 모자란 것이다. 다만 근거는 "있으면 쓸모 있겠다"가 아니라 **그 연산이 없으면 계약이 자기 목적을 진술하지 못한다**뿐이다(§규약1 B12 확정).
48. **상한은 규칙에서 따라 나오지 않는다 — 고르는 값이고 근거를 명세에 적는다.** 「가장 약한 쪽을 적는다」는 한정자 셋에 대한 규칙이고 상한으로 확장되지 않는다. 어떤 배제 조건에 대해서도 **가장 약한 상한은 존재하지 않기 때문이다**($O(n^{0.9})$ 아래로 끝없이 약해진다). B12 가 이 확장을 시도했다가 외부 검토에 걸렸다. 규칙이 옮겨 붙는지는 **대상의 순서 구조**가 정한다.
49. **축3은 상한이 아니라 성장 계급을 판정한다.** 계약보다 **빠른** 구현도 실패한다 — 계약을 어긴 것이 아니다. 따라 나오는 것 둘: 계약의 상한이 정본의 계급과 같아야 하고(느슨하게 적어 두고 빠른 정본을 두는 조합은 성립하지 않는다), 결함 fixture 의 실패를 "계약 위반"으로 보고하지 않는다. 아래쪽 허용치를 없애지 않는 이유는 **아무것도 재지 않는 시나리오가 통과하기 때문**이다.
50. **준비 비용이 측정 크기의 상수배를 넘는 성질은 축3이 못 본다.** 크기 사다리 $\{2^{10},2^{12},2^{14}\}$ 가 측정 시점의 원소 수이므로, 크게 채웠다 크게 줄인 뒤에야 드러나는 성질은 시나리오가 되지 못한다(준비가 $n^2$). 시나리오를 못 지은 것이 아니라 사다리가 고정된 데서 오는 한계다 — 자리는 가이드다.

## 배치 규약

    일곱 중 넷에서, `spliceArrayList`(배열 하나)는 셋에서 걸리고 겹치는 자리가 둘뿐이다.
    **배열을 계약 위반으로 잡는 것은 `insert`·`remove` 둘뿐이다**
  - **축3이 상한이 아니라 성장 계급을 판정한다는 것이 실물로 드러났다**(불변 사실 49).
    배열의 `get` 이 $r = 1.00$ 으로 **실패하는데 계약을 어기지 않았다** — 느려서가 아니라
    계급 아래라서다. 한쪽만 보게 고치지 않았다: 아래쪽 허용치가 **아무것도 재지 않는
    시나리오**를 잡는다
  - **줄어들 때 재구성(`halved`)을 겨누는 시나리오를 만들지 못했다**(불변 사실 50).
    지워도 일곱 시나리오가 전부 통과한다. 드러나는 형태는 있지만 준비가 $n^2$ 이라
    사다리에 얹히지 않는다. 자리는 가이드이고, 가이드가 실측 표와 함께 그 사실을 적는다
  - **외부 검토가 계약 헤더의 거짓 명제를 잡았다.** *"배열과 사슬을 배제하는 가장 약한 상한이
    $O(\sqrt n)$"* 은 거짓이다 — $O(n^{0.9})$ 아래로 끝없이 약해진다. **「가장 약한 쪽을
    적는다」는 한정자 셋에 대한 규칙이고 상한으로 확장되지 않는다**(불변 사실 48). 헤더를
    고쳤다. 받은 것 11 · 기각 3(덧셈 문턱 조건은 이미 붙어 있었고, 끝 원소 우회의 상수
    불균형은 계약이 상수를 말하지 않으며, ±30% 로 다항식을 못 가른다는 것은 축3이 증명이
    아니라 판정이라는 규격이 이미 밝힌 바다 — 다만 겹침 구간은 받아 §규약2에 적었다)
  - **집필기가 브리핑의 미검증 단정 둘을 실측으로 되돌렸다.** `push` 문턱의 `× 2` 를 떼도
    일곱 행의 수치가 정본과 **완전히 같고**, *"시나리오 하나만 뒀다면 어느 것을 골랐든
    한쪽은 통과한다"* 는 문자 그대로는 거짓이다(`get` 하나면 둘 다 실패한다). 둘 다 제가
    따로 재서 확인했다
  - **수치**: 테스트 **482 pass / 2420 fail**(B11 의 457 / 2424 에서 +25 / −4). 실패가 준 것은
    옛 스위트의 스텁 테스트 수가 줄어서이지 스텁을 구현했기 때문이 아니다.
    `bun run tools/ci.ts all` 통과(10단계, ③ 제외). 인용 35건 · 링크 255건 · vector 6종.
    가이드 650줄, 손댄 파일 biome 경고 0(스텁의 미사용 인자 경고는 재집필 6종 공통 기준선이다)

### B13 — suffixArray·suffixTree 구성 복잡도 정합 (다음)

- **읽을 것**: 이 문서, `docs/ORD-006-conventions.md` §규약1·§규약2·§규약3·§규약4,
  `KANBAN.md` 의 KAN-021 메모, 모범 예시 `src/data-structures/linear/deque/deque-guide.mdx`
- **카드**: KAN-021. 진단은 **C급** — naive `O(n² log n)`/`O(n²)` 를 명시하기는 했으나
  스토리가 30억 염기 BLAST 다. 내건 규모와 처방한 복잡도가 어긋난다
- **이 카드가 앞의 열둘과 다른 점**: 구조가 **둘**이고, 카드 제목이 "정합"이라 재집필이
  아닌 것처럼 읽힌다. 그렇지 않다 — ORD-006 은 69종 전부를 규약1~3으로 옮기므로 이 카드도
  `-problem.md` 삭제 · 계약 명세 · 계약 스위트 · `_reference/` · 가이드 8단계를 전부 진다.
  정합은 그 안에서 판정할 항목 하나다
- **할 것**
  1. **두 구조의 계약이 같은지부터 판정한다**(불변 사실 43). 접미사 배열과 접미사 트리는
     연산이 겹치지만 **포섭은 근거가 아니다.** 반례를 찾되 `_reference/` 에서 찾지 않는다
  2. 계약 명세를 규약1 여섯 항목으로 쓴다. **구성 알고리즘 이름(Ukkonen·SA-IS·배가법)을
     계약에 적지 않는다** — 이름이 곧 처방이다. 계약이 말할 수 있는 것은 구성 비용의 상한뿐
  3. **카드가 내건 택1(naive 유지 + 스토리 축소 / `O(n log n)`·Ukkonen 승격)은 계약을 적기
     전에는 결정할 수 없다.** 상한을 정하는 일이 곧 계약을 정하는 일이고, 스토리는 계약이
     아니라 가이드 2단계의 소관이다. 순서를 뒤집지 않는다
  4. **등급을 계약에서 유도한다.** 구성 비용이 계약에 들어가면 `complexity` 가 유력하지만
     미리 정하지 않는다. 판정 절차는 §규약1 「검증 등급 4종」
  5. 계약 스위트를 붙이고 정본을 쓴다. **축3이 문자열 길이에 대한 성장률을 재는 첫 자리다**
     — 지금까지 n 은 전부 원소 수였다. 시나리오의 n 이 무엇인지를 `.contract.ts` 주석에 적는다
  6. **상한이 셋 중 하나로 안 떨어지면 `Bound` 를 늘리기 전에 겹침부터 본다**(불변 사실 49·§규약2).
     `O(n log n)` 의 기대 비율은 $4\log(4n)/\log n$ 이라 n 에 기대고, `O(n)` 의 4.0 과 가깝다
  7. `-problem.md` 둘을 지운다. 지우기 전에 `bun run tools/check-links.ts refs`
  8. 가이드를 8단계로 재집필한다. 규약4 판정이 (-) 면 6단계를 절째로 생략한다
  9. **외부 검토를 돌린다**(불변 사실 46). 받은 것과 기각한 것을 배치 결과에 적는다
- **경계**: 두 구조를 한 배치에 넣는 것이 부담이면 **계약 둘을 먼저 확정하고 나머지를
  B14 로 넘긴다.** 나누는 자리는 계약 뒤이지 계약 앞이 아니다 — 계약이 갈리지 않은 채로
  나누면 두 배치가 서로 다른 계약을 가정한다
- **끝낼 때**: `bun run tools/ci.ts all` 통과 + KAN-021 메모 + 이 문서의 B14 진입 카드
