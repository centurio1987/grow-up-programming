# 알고리즘 문제 — 항목별 작성 방법

> **층: L2 (글 명세)** · 적용 voice: `ppangtolab-teacher` (빵토랩 선생님)
> 출처: `gen-problem/SKILL.md` §2.1(문제 골격, 변경 금지) + `PROBLEM_QUALITY_CHECKLIST.md`

## 이 글의 목적 — 가이드와 정반대다

가이드는 **이해시키는** 글이고, 문제는 **풀게 하는** 글이다.
그래서 같은 코드(`D축`)가 정반대 요구를 담는다.

| | 가이드 | 문제 |
| --- | --- | --- |
| D축 | 여러 관점으로 **비추라** | 풀이를 **암시하지 마라** |

**가장 중요한 제약은 힌트 누출 금지**다. 스토리·예시 설명·용어 선택 어디에서도
알고리즘·자료구조·풀이 절차·복잡도 트릭이 새면 안 된다. 문제가 스스로 답을 흘리면
그 문제는 죽은 문제다.

> 목소리는 그대로 `ppangtolab-teacher` 다 — 존댓말 설명체로 명료하게 쓴다.
> 다만 **가르치지 않는다.** 규칙을 정확히 말하는 것까지가 이 글의 일이다.

---

## 항목별 작성 방법

### 스토리 & 한 줄 요약 (`story`)

간단한 상황/등장인물로 동기를 주고, **곧바로** "이 함수는 X를 받아 Y를 반환한다"는 한 줄 요약을 붙인다.

- 첫 1~2문단에서 **"이 함수가 무엇을 입력받아 무엇을 반환하는지"** 가 잡혀야 한다.
- 스토리는 **이해를 돕는 선에서 간결하게**. 세계관을 짓지 않는다.
- 스토리가 말하는 목표와 아래 시그니처가 **반드시 일치**해야 한다 —
  스토리는 정렬 얘기인데 시그니처는 개수를 반환하면 그 자체로 실패다.
- **스토리에서 풀이가 새기 쉽다.** "우선순위가 높은 순서로 처리하다 보면" 같은 서술은
  힙을 지목하는 것이다. 상황만 말하고 처리 방식은 말하지 않는다.

### 함수 인터페이스 (`interface`)

시그니처(이름·파라미터·반환 타입)를 **코드블록으로** 명시한다.

- **파라미터명에 언더바 prefix 를 쓰지 않는다.** (`_arr` 금지)
- 입출력 계약을 시그니처만으로 못 담으면 한 줄 덧붙인다.
- 타입이 애매한 자리(정수 범위, null 허용)는 여기서 못 박는다.

### 제약 조건 (`limits`)

입력 크기·값 범위·시간/공간 상한·특수 규칙을 **정량적으로** 나열한다.

- **모호어 금지**: "적당히", "큰 수", "빠르게", "너무 많지 않은".
- 인덱스 0/1 기준, 정렬 안정성 요구, 부동소수 오차 허용 범위처럼
  **해석이 갈릴 수 있는 것**을 여기서 고정한다.
- 제약이 곧 목표 복잡도의 근거가 되지만, **목표 복잡도를 적지는 않는다** — 그게 힌트다.

### 문제 상세 (`detail`)

무엇을 계산/변환해야 하는지 규칙을 **산문으로** 푼다.

**경계·예외 동작을 빠짐없이 규정한다:**

- 빈 입력, 원소 1개
- 동점 처리
- 음수·0
- 오버플로 경계
- 중복 원소
- 조건을 만족하는 답이 없을 때

> 여기서 규정하지 않은 경우가 테스트에 나오면 **문제의 결함**이지 푸는 사람의 잘못이 아니다.
> "한 가지 해석만 남는가"를 기준으로 다시 읽는다.

### 예시 (`examples`)

(입력 → 출력) 예시 **2~3개**. **경계 케이스 예시가 최소 1개** 포함돼야 한다.

각 예시에 **왜 그 출력인지** 한 줄 설명을 붙이되 — 여기가 힌트가 가장 잘 새는 자리다.

| 쓴다 | 쓰지 않는다 |
| --- | --- |
| **규칙의 적용** — "3과 5는 둘 다 조건에 맞지만 인덱스가 작은 3이 먼저다" | **푸는 절차** — "왼쪽부터 훑으며 최댓값을 갱신하면" |
| 왜 그 값이 답인지 | 어떻게 그 값에 도달하는지 |

- **모든 예시의 출력이 실제 정답 동작과 일치**해야 한다. 손으로 계산하지 말고 **돌려서 확인**한다.
- 본문 예시의 기대값과 **테스트 파일의 기대값이 같아야** 한다. 둘이 갈라지면 둘 다 못 믿는다.

## 함께 만드는 것 — 테스트

문제 문서만으로는 끝나지 않는다. 테스트가 문제의 **집행 장치**다.

| 축 | 내용 |
| --- | --- |
| **바운더리** | 빈 / 단일 / 최소 / 최대 입력 |
| **엣지** | 동점 · 음수 · 중복 · 특수값 — `detail` 이 규정한 예외를 전부 |
| **성능** | 제약 상한 입력 (CPU 1초 ≈ 10^8 연산 가정) |

- 테스트는 **함수의 외부 계약만** 검증한다. 풀이 구현 세부에 기대면 다른 풀이가 실패한다.
- 본문이 요구하는 동작 중 **테스트로 표현할 수 없는 것**이 있으면, 그 요구가 모호한 것이다.

## 힌트 누출 자가 점검

발행 전에 이 넷을 훑는다.

1. **스토리** — 처리 순서·자료구조를 연상시키는 서술이 있는가.
2. **용어** — 문제 도메인 밖의 알고리즘 용어(그리디·메모이제이션·슬라이딩)를 썼는가.
3. **예시 설명** — "훑으며", "갱신하면", "쌓아 두면" 같은 절차 동사가 있는가.
4. **제약** — 목표 복잡도를 적었는가.

하나라도 걸리면 그 문장을 **상황 서술로 되돌린다.**
