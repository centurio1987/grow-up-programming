# gen-problem 스킬 (문제 집필 진입점)

`src/$ARGUMENTS.ts`의 주석(미완성 문제 단서)·함수 시그니처를 입력으로,
독자가 **쉽고 빠르게 이해할 수 있는 풍성한 문제 문서** `src/$ARGUMENTS-problem.md`
(스토리·예시·다이어그램에 JSX가 필요하면 `.mdx`)와, 그 문제를 **정확히 반영하고 충분히 커버하는
테스트 코드** `src/$ARGUMENTS.test.ts`를 작성한다.

> **집필 규칙은 이 파일에 없다.** 문제 골격·금기·품질 기준은 `authoring-kit` 플러그인의
> `problem` 명세에 산다. 이 스킬은 **입력을 모아 넘기고 결과를 발행하는 일**만 한다.

## 명세

| | |
| --- | --- |
| spec | `problem` — 스토리 · 함수 인터페이스 · 제약 조건 · 문제 상세 · 예시 (5항목, 전부 필수) |
| voice | `ppangto-teacher` (빵토 선생님) |
| 최대 제약 | **풀이 힌트 금지.** 스토리·용어·예시 설명 어디에서도 알고리즘·자료구조·절차·복잡도 트릭이 새면 안 된다 |

> 가이드 spec 과 **D축이 정반대**다. 가이드는 "여러 관점으로 비추라", 문제는 "암시하지 마라".
> 같은 루브릭을 쓰면 반드시 한쪽이 틀린다 — 그래서 명세를 나눴다.

## 동작

### 0. 사전 확인

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/authoring.py status
python3 ${CLAUDE_PLUGIN_ROOT}/scripts/authoring.py lock
```

플러그인이 없으면 **여기서 멈춘다.** 구 경로로 조용히 돌아가지 않는다 —
그러면 어떤 규칙으로 쓰였는지 알 수 없게 된다.

### 1. 리서치

- **입력 정독** — `src/$ARGUMENTS.ts` 전체(특히 문제 주석)와 함수 시그니처.
  주석이 말하는 의도와 시그니처가 어긋나면 **그것부터 사용자에게 확인**한다.
- **정답 동작 확인** — 구현이 있으면 `bun test src/$ARGUMENTS.test.ts 2>&1; true`,
  없으면 작은 입력을 직접 돌려 본다. **예시에 실을 출력은 여기서 확정한다** —
  손으로 계산한 값을 그대로 싣지 않는다.
- **도메인 사실 수집** — 표준 정의·단위·제약(정수 범위, 인덱스 0/1 기준, 정렬 안정성).
  해석이 갈릴 수 있는 것을 찾아 둔다. 그게 `제약 조건`·`문제 상세`에서 못 박을 대상이다.
- **앵글 확정** — 한 줄 정체: **누가, 무엇을 입력받아, 무엇을 반환해야 하는가.**

### 2. 집필 — `authoring-write` 에 위임

```
Skill(authoring-kit:authoring-write) --spec problem
```

넘길 것: 대상 파일 경로 · 1단계에서 확정한 정답 동작과 예시 출력 · 도메인 제약 · 앵글.

문제 문서와 **테스트 코드를 함께** 만든다. 테스트는 문제의 집행 장치다.

- `import { test, expect } from "bun:test";` (Bun 테스트 API)
- **본문 예시 = 테스트 케이스.** 모든 예시를 그대로 테스트로 옮겨 기대값을 일치시킨다.
- `checklist.md` 의 세 축을 채운다 — **바운더리** / **성능**(CPU 1초 ≈ 10^8 연산 가정으로
  제약 상한 입력) / **엣지 케이스**. 각 기대값은 1단계에서 확인한 **정답 동작**에 근거한다(추정 금지).
- 테스트는 **풀이 구현에 의존하지 않고** 함수의 외부 계약만 검증한다.

`.mdx` 는 이해에 실제로 기여할 때만 쓴다(억지 컴포넌트 금지).
`{`·`<` 처럼 JSX와 충돌하는 원문은 코드블록에 두거나 이스케이프한다.

### 3. 발행

품질 게이트 PASS 후:

1. **테스트 통과 확인** — 구현이 있을 때 `bun test src/$ARGUMENTS.test.ts`.
2. **빌드 확인** — `.mdx` 로 썼으면 빌드 통과 확인(JSX 문법 오류 하나가 빌드 전체를 깬다).
3. **목록 등록(해당 시)** — 문제 목록·인덱스를 생성하는 도구가 있으면 실행한다.
4. **완료 보고** — 문제 문서·테스트 경로 · 테스트 통과 여부 · 게이트 판정(PASS/라운드 수) ·
   `resolve` 해시(어떤 규칙 조합으로 쓰였는지).

## 주의

- **구성 항목·금기를 이 파일에 다시 쓰지 않는다.** spec 이 정본이다.
  바꾸려면 spec 을 고친다.
- **스토리는 힌트가 아니다.** 동기·맥락만 준다 — 처리 순서나 자료구조를 연상시키면 풀이 누출이다.
- **글과 테스트는 같은 계약을 말한다.** 예시 출력과 테스트 기대값이 어긋나면 둘 다 못 믿는다.
- **자동 통과 금지** — 3라운드를 다 써도 미통과면 그대로 보고한다.
  외부 검토가 둘 다 실패한 상태를 "완성"으로 보고하지 않는다.
