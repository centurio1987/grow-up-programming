# guide-for-problem 스킬 (가이드 집필 워크플로우)

`src/$ARGUMENTS.ts`의 **문제 주석**을 입력으로, 문제를 푸는 **깊은 해설서**
`src/$ARGUMENTS-guide.mdx`를 작성한다. 가이드는 sibling `.ts`(학습자 실습 공간)와 **독립적으로
집필·검증**된다 — 본문에 싣는 코드는 가이드 자체로 실행·검증한다.

집필은 `~/centurio1987.github.io`의 기술 글 워크플로우(**리서치 → 집필 → 품질 게이트웨이 → 발행**)를
알고리즘 가이드에 맞게 옮겨 온 **4단계 파이프라인**으로 진행한다. 산출물의 **골격과 문체는 ORD-003
템플릿**을 따르며, 대상에 따라 캔버스가 둘로 나뉜다:

- **알고리즘 가이드** (`src/algorithms/**`) → `algorithm-guide-canvas.md` (10단계 골격)
- **자료구조 가이드** (`src/data-structures/**`) → `data-structure-guide-canvas.md` (5단계 골격 —
  문제 대응이 아니라 **자료구조 그 자체의 독립 가이드**)

```
[1. 리서치]  src/<name>.ts 문제 주석 + 사실 수집 + 본문 코드 자기 검증 + 재사용 자산(시뮬·mermaid) 확인 → 가이드 앵글
  → [2. 집필]  src/<name>-guide.mdx (대상별 canvas + TONE_REFERENCE 강제 + 시뮬·mermaid copy·검증 + 외부 검토)
  → [3. 품질 게이트]  QUALITY_CHECKLIST.md로 채점 → 보완 → 재채점 (≤3회, PASS까지)
  → [4. 발행]  빌드·시뮬·다이어그램 확정 → 가이드 인덱스 등록(중요도 구조 보존 — 수동 삽입)
```

## 이 가이드가 반드시 충족해야 하는 것 (ORDER 원칙)

집필 내내 아래를 기준으로 삼는다. 어기면 가이드를 고친다. (블로그 워크플로우의 집필 원칙을 알고리즘
가이드에 맞춰 옮긴 것이다.)

- **독자 = 고객.** 독자가 끝까지 이해하지 못하면 실패다. "어떻게든 이해시킨다"는 태도로 쓴다.
- **점진적 공개.** 쉬운 것 → 어려운 것 순서로 쌓는다. 뒤 내용이 앞에서 설명하지 않은 전제에 기대지 않는다.
- **해부학적 깊이.** 표면 설명에서 멈추지 않는다. "5 Whys" 정신에 입각하여 끝까지 파고든다. 무언가를 주장할 때는 근거(증명·복잡도 유도·반례)를 가급적 동반한다. 파생되는 원리도 자세히 소개한다. (예: knapsack01 최적화 과정에서 1D 롤링이 나오면, 차원 압축에 대한 이론인 동적 계획법의 상태 공간 최적화(State Space Optimization), 마르코프 속성에 대해서도 자세히 다뤄야 한다.)
- **유도 생략 없음.** 원천 아이디어·알고리즘을 먼저 설명하고, **거기서 솔루션으로 유도하는 과정을 생략 없이**
  제공한다. 원형 알고리즘이 있으면 원형 → 관찰 → 개선의 전개를 단계별로 보인다.
- **정식 표기.** 핵심 아이디어는 초등학생도 따라올 만큼 꼼꼼하게
  사용한다(수식 $…$ 포함). 이는 `analyze-solution`의 서술 원칙과 일치한다.
- **다관점.** 한 개념을 정의·수식·트레이스·다이어그램·시뮬레이션 등 여러 각도로 비춘다.
- **톤 앤 매너 강제 (ORD-003).** 집필 시작 전 `assets/TONE_REFERENCE.md`를 읽고 문체 규칙 10을 본문
  전체에 적용한다(존댓말 설명체, 오해 지점 명시 호출, 기억법, 확인 문제). 친절하되, 학습자가
  간과·오해할 수 있는 부분을 빠트림 없이 커버한다.
- **ascii art 적극 활용 (ORD-003).** 직관적 이해를 높이는 1급 수단이다. 모든 핵심 개념·상태 변화는
  ```text 블록 그림으로 보이고, 상태가 변하는 연산은 Before/After 도식으로 보인다.
- **시뮬레이션·mermaid는 새로 작성하지 않는다 (ORD-003).** 같은 주제의 기존 가이드 구현부를 copy한다.
  단 **copy는 검증 면제가 아니다** — steps는 본문 서사와 1:1 대조, mermaid는
  `bun run tools/guide-preview/check-mermaid.ts` 파서 검증을 통과시킨다(기존 블록에 구문 오류가
  있던 실제 사례: houseRobber, mosAlgorithm).
- **한국어 본문 + 기술 용어 원어** 유지(예: pivot, partition, $O(N \log N)$).
- **코드 설명은 친절하게 + 핵심 포인팅.** 본문 코드는 의미 단위로 친절하게 설명하고, 학습자가
  오해하거나 놓치기 쉬운 구현부는 "가장 중요한/실수가 잦은 부분은 ~입니다" 문형으로 직접
  포인팅해 추가 설명한다(캔버스 4.1). 주어가 코드 조각이고 서술어가 그 직역인 나열은 금지.

## 1단계 — 리서치 (research)

> 블로그 `research` 스킬의 대응 단계. 집필 에이전트가 다시 찾지 않아도 될 만큼 **사실을 먼저 굳힌다.**
> 알고리즘 가이드의 "사실"은 문제 정의·실제 구현 동작·표준 알고리즘 지식(원형·복잡도·정확성)이다.

1. **문제 맥락 정독**: `Read`로 `src/$ARGUMENTS.ts`의 **문제 주석**과 `-problem.md`(있으면)를 읽어
   제약·예시·요구사항을 파악한다. 여기서 얻는 것은 **문제 맥락**이지, 가이드가 맞춰야 할 정답 구현이
   아니다(가이드 코드는 §1.2에서 본문 자체로 검증한다).
2. **본문 코드 자기 검증**: 가이드에 실을 코드는 **가이드 자신이 진실의 원천**이다. 그 코드를 스크래치
   파일로 추출해 `bun`으로 실행하고, 본문의 모든 수치 예시·시뮬 프레임 값·엣지 케이스를 실측으로
   검증한다(대표 예시 + 반례성 입력 + 무작위 브루트포스 교차 검증 권장). 이 실측 기록이 E3 채점의 근거다.
   - **`src/$ARGUMENTS.ts`는 학습자의 실습 공간**일 뿐, 가이드의 검증 기준(oracle)이 아니다. `.ts`(주석)·
     `-problem.md`는 **문제 맥락**을 파악하려 읽되, 그 구현/테스트를 가이드 정확성의 기준으로 삼지 않는다.
     가이드는 `.ts`와 **독립적으로 집필·검증**된다(스텁이든 구현이든 무관 — 트레이스·복잡도는 본문 코드의
     실제 실행에 근거한다).
3. **알고리즘 사실 수집**: 이 문제가 기대하는 목표 복잡도, 원형 알고리즘, 정확성 근거(불변식·증명 골자)를
   정리한다. 표준 사실(예: 비교 정렬 하한 $O(N \log N)$)은 단정하지 말고 근거를 확인한다 — 불확실하면
   `WebSearch`/`WebFetch`로 1차 자료(교과서·표준·공식 문서)를 확인하고 **검증한 사실만** 쓴다.
   - **skip 조건**: 원형·복잡도가 자명한 표준 알고리즘이면 외부 조사는 건너뛸 수 있다(블로그의 "외부 자료
     불필요 시 skip"과 동일). 단 건너뛴 사실도 본문에서 근거 없이 단정하지는 않는다.
4. **앵글 확정**: 이 가이드의 핵심 주장 = "**원천 아이디어 → 솔루션 유도의 경로**"를 한 문단으로 정리한다.
   이것이 2단계 집필의 입력이며 `## 핵심 아이디어` 섹션의 뼈대가 된다. 부족한 자료는 open question으로
   남겨 집필 시 주의한다.

   **앵글 확정 시 반드시 함께 답해야 하는 핵심 아이디어 설계도 (개념 수준, 코드는 2단계에서 작성)**:

   a) **코드 진화 사다리** — 이 알고리즘에 자연스러운 발전 단계가 있으면 나열한다(복잡도 포함).
   예: 브루트포스 O(2^n) → Top-Down DP O(n·W) → 2D 바텀업 O(n·W) → 1D 롤링 O(W).
   자연스러운 진화가 없는 문제(그리디·단순 BFS 등)면 "진화 사다리 없음 — [기술적 근거]" 명시.

   b) **직관 1문장** — 수식·기호 없이 핵심을 전달하는 한 문장.
   예: "각 물건을 담을지 말지 결정할 때, 나머지 용량에서의 최선은 앞선 선택과 무관하다."

   c) **의존성 범위** — 공간 최적화가 있으면 현재 상태가 어느 이전 상태에만 의존하는지 1줄.
   예: "dp[i][w]는 dp[i-1][w]와 dp[i-1][w-wi]만 참조 → 이전 행 1개로 충분."
   공간 최적화가 없으면 "해당 없음" 명시.

   d) **함정 목록** (코드 없이 개념만, 코드는 2단계에서 작성) — 독자가 빠지기 쉬운 실수 1~3가지.
   예: "1D 배열 오름차순 순회 → 무한 배낭 버그", "초기화 누락 → 경계 케이스 오답".
   문제 특성상 함정이 없으면 "주요 함정 없음 — [기술적 근거]" 명시.

   e) **재사용 자산 목록** — 같은 주제의 기존 가이드(`*-guide.mdx`)에서 copy할 시뮬 `steps`·mermaid
   블록의 위치(파일:행)와 사전 검증 결과(mermaid 파서 통과 여부, 프레임 값 실측 일치 여부).
   기존 시뮬이 없으면 "신규 작성 필요" 명시.

## 2단계 — 집필 (writing)

> 블로그 `tech-deepdive` 대응 단계. 산출물은 `src/$ARGUMENTS-guide.mdx` — `src/$ARGUMENTS.ts`와 나란히 둔다.

### 2.1 골격 (ORD-003 canvas — 변경 금지)

1. **필독 2건**: `assets/TONE_REFERENCE.md`(문체 규격 — 강제 적용), 그리고 대상에 맞는 모범 예시 —
   알고리즘이면 `src/algorithms/array/mosAlgorithm/mosAlgorithm-guide.mdx`,
   자료구조면 `src/data-structures/tree/bPlusTree/bPlusTree-study-guide.mdx`.
2. 경로로 캔버스를 고른다: `src/algorithms/**` → `algorithm-guide-canvas.md`,
   `src/data-structures/**` → `data-structure-guide-canvas.md`.
3. 캔버스의 `##` 헤딩 **문구·순서를 그대로** 따르고, 각 절의 직무 주석을 집필 규격으로 삼는다.
   - 알고리즘(10단계): 한눈에 보는 컨셉 → 출발점: 가장 순진한 방법부터 → 아이디어 자세히
     들여다보기(수식·그림 / 이론 / 자료구조 링크 / 정당성) → 아이디어를 코드로 옮기기 →
     더 빠르게 만들 단서 찾기 → 단서를 최적화로 연결하기 → 최적화 코드(+반복 또는 종료 선언) →
     실행 시각화 → 흐름 한눈에 보기(mermaid) → 스스로 점검하기.
   - 자료구조(5단계): 한눈에 보는 컨셉 → 언제, 왜 쓰는가(단서 / 사례) → 자료구조 자세히
     들여다보기(전체 스펙 / 정당성) → 아이디어를 코드로 옮기기 → 실행 시각화 → 스스로 점검하기.
     **특정 문제에 종속되지 않는 독립 가이드**로 쓴다.
4. **조건부 절 규칙**: 캔버스가 "조건부"로 표시한 절(알고리즘 3.2 이론 / 3.3 자료구조 링크 / 5~8
   최적화 반복 등)은 해당 없으면 **문서에서 절 자체를 생략**하고, 생략 사유 한 줄을 품질 게이트
   보고에 기록한다 — 독자용 문서 안에 "해당 없음" 같은 집필 메타를 남기지 않는다.

MDX에서 markdown·수식(`$…$`)·코드블록은 그대로 유효하다. 단 `{`, `<` 등 JSX와 충돌하는 원문은 코드블록
안에 두거나 이스케이프한다.

**집필 직후 문체 자가 점검** (초고 완료 후, 외부 검토 전):
- `assets/TONE_REFERENCE.md`의 문체 규칙 10 + 금지 목록을 본문 검색으로 훑고, 걸리면 즉시 교정한다.
- `../_shared/NATURAL_KOREAN_GUIDE.md` Part C의 10항목을 본문 검색으로 훑는다. 영어투·이중 피동·무생물 주어 등이 걸리면 즉시 교정한다.

### 2.2 시뮬레이션 위탁 (`#guide-sim`)

알고리즘 전개를 단계별로 조작·재생하는 React 시뮬레이션을 `## 실행 시각화` 섹션에 넣되,
**문제별 JSX 컴포넌트/Hook을 직접 작성하지 않고** 공용 모듈에 위탁한다(블로그가 시뮬을 `react-sim`에
위탁하는 것과 같은 경계).

- MDX 상단에 `import { AlgorithmSimulation } from "#guide-sim";` 한 줄만 추가한다. `#guide-sim` 외 import 금지.
- **copy 우선 (ORD-003)**: 같은 주제의 기존 가이드에 있는 `export const steps` + 호출부를 그대로
  가져온다(1단계 재사용 자산 목록). copy 후 프레임 값·순서가 본문 서사와 1:1로 맞는지 대조한다 —
  불일치하면 서사를 steps에 맞춘다(steps 쪽 수치가 실측 검증본이다).
- 기존 시뮬이 없을 때만 새로 작성한다: 적합한 프리셋 `view`를 고르고, 작은 고정 입력의 **실제 실행
  단계**를 선언형 `steps` 데이터로 나열한다. 프레임 스키마·프리셋 목록·예시는 `simulation-scaffold.md`를 따른다.
- **정확성**: `steps`는 1단계에서 확인한 **본문 코드의 실제 실행**(스크래치 실측)을 따른다. 사용한 고정 입력과
  실제 반환값을 본문에 명시하고, 마지막 프레임의 결과 상태가 그 값과 일치하게 한다.
- 시뮬레이션 호출부 바로 위에 정적 뷰어용 안내 한 줄("대화형 시뮬레이션은 MDX 런타임에서 표시됩니다.")을 둔다.

### 2.3 외부 검토 (누락·모순·사실성)

집필을 마치면 외부 모델(codex/agy)에 검토를 받아 보강한다. 블로그 `tech-deepdive`의 외부 검토 단계를
알고리즘 가이드에 맞춘 것이다(축: 누락/생략, 모순/충돌, **사실 정확성 — 복잡도·정확성 증명·표준 알고리즘**).

```bash
bash .claude/skills/guide-for-problem/scripts/review-guide.sh "src/$ARGUMENTS-guide.mdx"
```

- 스크립트 stdout을 **요약하지 말고 그대로, 일반 텍스트로 먼저** 사용자에게 보여준다(모델이 짚은
  표현이 핵심). 선택 질문(AskUserQuestion)과 같은 턴에 묶지 않는다 — 본문을 보여준 뒤에 선택을 받는다.
- 종료코드 2(둘 다 `[skip]`/실패)면 외부 검토 미통과다 — 가이드를 "완성"으로 보고하지 말고 원인(미설치/미인증:
  `codex login`, 터미널에서 `agy` 1회 실행)을 안내하고 재시도 여부를 묻는다. 한쪽만 성공하면 진행하되 알린다.
- 지적 중 **실제로 유효한 것**을 사용자와 함께 골라(외부 모델은 이 가이드의 의도/맥락을 모른다) 본문을 보강한다.

## 3단계 — 품질 게이트웨이 (quality gate)

> 블로그 `quality-gate` 대응 단계. `assets/QUALITY_CHECKLIST.md`로 **PASS/FAIL을 판정**하고, 미통과면
> **보완 → 재채점**을 PASS까지(최대 3라운드) 반복한다.

1. `assets/QUALITY_CHECKLIST.md`의 모든 항목을 순서대로 **충족 / 미흡 / 해당없음** + **본문 인용 근거**로
   평가한다(인용 못 하면 미흡). 해당없음은 "왜 뺐는지 메모가 있는가"로 검증한다.
2. 판정 규칙: **PASS = MUST 전부 충족 · SHOULD 미흡 ≤ 2 · IF-APPLICABLE은 충족 또는 정당한 생략 메모.**
   그 외는 FAIL. 빌드 항목(G1)은 `bun run build`로 실제 확인한다. 사실성(E2/E3)은 필요 시 `WebSearch`로 확인.
3. **FAIL이면 보완 루프**: 미흡 항목마다 "어디·무엇·어떻게"의 보완 지시를 내고, 단순 문장 교정은 직접 `Edit`,
   **누락 섹션·유도 부족·시나리오 보강처럼 새 집필이 필요한 보완은 2단계로 되돌아가** 해당 섹션만 다시 쓴다.
   재채점하고 라운드를 올린다. **PASS면 종료**. 3라운드를 채워도 FAIL이면 **멈추고** 남은 미흡과 자동 보완이
   어려운 이유를 보고한다 — 기준을 낮춰 임의 통과시키지 않는다.
   빌드·다이어그램 게이트는 명령으로 실제 확인한다:
   `bun run tools/guide-preview/compile-check.ts <guide.mdx>` (G1),
   `bun run tools/guide-preview/check-mermaid.ts <guide.mdx>` (G4 — mermaid 블록이 있는 경우).
4. 호출 맥락:
   - **사용자 직접 호출**: 라운드 1 결과를 보여준 뒤 "(a) PASS까지 자동 보완 / (b) 항목 골라 보완 / (c) 여기까지"를 묻는다.
   - **파이프라인 안에서**: 루프를 자동으로 돌리되 라운드마다 무엇을 고쳤는지 남기고, PASS 전에는 발행으로 넘어가지 않는다.

## 4단계 — 발행 (publishing)

> 블로그 `publish-post` 대응 단계. 알고리즘 가이드는 별도 콘텐츠 컬렉션 발행 대신 **프로젝트 인덱스 등록**으로
> 발행을 마친다(사이드바 수동 등록 없음 — 블로그가 콘텐츠 컬렉션 자동 탐색인 것과 동일한 정신).

PASS한 뒤에만 진행한다.

1. **최종 점검**: 가이드가 `src/$ARGUMENTS-guide.mdx`에 있고, import 경로·시뮬 컴포넌트가 올바른지
   확인한다. `bun run tools/guide-preview/compile-check.ts` + (mermaid 블록이 있으면)
   `bun run tools/guide-preview/check-mermaid.ts`가 통과하는지 마지막으로 확인한다.
2. **인덱스 등록 — 중요도 구조 보존**: `문제_가이드_목록.md`는 사용자가 **중요도별로 구성**한 문서다.
   인덱스 갱신은 `./tools/generate-guides-index.sh`(구조 보존형 — 이미 링크된 항목은 건드리지 않고
   누락분만 "중요도 미분류" 절에 추가)에 맡기되, 새 가이드는 가능하면 알맞은 기법 줄로 **수동
   이동**시킨다. 중요도 판단이 필요하면 `알고리즘 중요도 기준 문제 목록.md`를 참조하고, 판단이
   안 서면 사용자에게 묻는다. **인덱스 전체를 알파벳순으로 재생성하는 방식은 금지**(중요도 구조 파괴).
3. **완료 보고**: 생성된 가이드 경로, 인덱스 삽입 위치, 품질 게이트 최종 판정(PASS/라운드 수),
   조건부 절 생략 사유를 한 번에 보고한다.

## 주의

- **골격은 ORD-003 캔버스가 정한다.** `##` 헤딩 문구·순서를 바꾸지 않는다. 기존 `*-guide.mdx`
  (구 템플릿)는 재집필 지시가 있을 때까지 그대로 둔다 — 구 가이드에 구 골격이 남아 있는 것은
  위반이 아니다.
- **조건부 절 생략은 문서 밖에 기록한다.** 독자용 문서 안 "해당 없음" 메모 금지 — 생략 사유는
  품질 게이트 보고에 남긴다.
- **copy는 검증 면제가 아니다.** 기존 가이드에서 가져온 mermaid·steps도 파서 검증·서사 대조를 통과해야 한다.
- **인덱스 전체 알파벳순 재생성 금지.** 중요도 구조 보존 — 스크립트는 누락분 추가만 한다.
- **자동 통과 금지**: 품질 게이트 3라운드를 다 써도 미통과면 그대로 보고한다.
- **외부 검토 미통과(둘 다 실패)** 상태를 "완성"으로 보고하지 않는다.
- 시뮬레이션은 `#guide-sim`에만 위탁한다 — 문제별 JSX/Hook 직접 작성·외부 라이브러리 import 금지.
- MDX 작성 후 빌드 통과를 확인한다(JSX 문법 오류 1건이 빌드 전체를 깰 수 있다).
