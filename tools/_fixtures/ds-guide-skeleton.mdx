# Stack — 한쪽 끝만 여닫는 통

## 개요

한쪽 끝(top)에서만 넣고 빼는 컨테이너입니다. 접근을 그 한 점으로 제한하는 것이 설계
핵심이고, 그 대가로 넣고 빼기가 `amortized O(1)`에 끝납니다.

## 이 구조가 필요한 이유

"가장 최근에 넣은 것을 원소 수와 무관한 비용으로 꺼낸다"를 약속하는 구조입니다. 넣기와
꺼내기 **둘 다** 상수 비용이어야 한다는 것이 요구의 전부이고, 위치 기반 접근이나 탐색이
필요하면 이 구조로는 부족합니다.

### 쓰이는 자리

- **괄호 짝 검사** — 여는 괄호마다 `push` 1회, 닫는 괄호마다 `pop`·`peek` 각 1회. 입력
  길이만큼 반복하므로 전체가 `O(n)`입니다. 세 연산이 모두 계약에 있습니다.
- **함수 호출 프레임** — 호출마다 `push`, 반환마다 `pop`. 깊이와 무관하게 프레임 하나를
  다루는 비용이 상수여야 재귀가 성립합니다.

## 단순한 구현의 한계

### 순진한 설계는 어디서 상한을 넘는가

배열의 **앞쪽**을 top 으로 잡으면 넣고 빼기가 매번 뒤 원소 전부를 밀어냅니다. `n`이 4배가
될 때 연산당 비용이 4배로 늘어, 실측 성장률이 $r = 4.00$ 이 나옵니다. 계약이 요구하는
값은 $1.0$ 입니다.

이 실패는 가끔이 아니라 구조적입니다. 어떤 입력을 넣어도 앞쪽 삽입은 뒤 전부를 옮깁니다.

### 실패에서 끌어내는 설계 규칙

관찰은 하나입니다 — **원소를 옮기지 않는 끝이 있어야 합니다.** 배열에서 그런 끝은 뒤쪽
하나뿐이고, 그래서 top 을 뒤쪽으로 잡습니다. "왼쪽이 top" 은 관례가 아니라 비용의 문제이므로
반대로 잡을 수 없습니다.

## 불변식과 연산별 복잡도 조건

불변식 절은 비어 있습니다. 각 연산의 의미가 각각 옳으면 따로 깨질 수 있는 상태 성질이
남지 않기 때문입니다 — LIFO 순서는 `pop`·`peek` 의 의미가 그대로 정의합니다.

한정자는 연산마다 갈립니다. `push`·`pop` 은 `amortized`, `peek`·`isEmpty`·`size` 는
`worst` 입니다. 계약이 **가장 약한 한정자**를 적는 이유는 강한 한정자가 우회로 낸 처방이기
때문입니다 — `push` 를 `worst O(1)` 로 적으면 용량을 배로 늘리는 배열 구현이 배제됩니다.

검증 등급은 `basic` 입니다. 상한이 자명한 구현으로 달성되고 불변식 절이 비어 있습니다.

## 구현 (TypeScript)

```ts guide-core=src/data-structures/linear/stack/_reference/stack.ts
export class Stack<T> {
  #items: T[] = [];

  push(item: T): void {
    this.#items.push(item);
  }

  pop(): T | null {
    if (this.#items.length === 0) return null;
    return this.#items.pop() as T;
  }

  peek(): T | null {
    if (this.#items.length === 0) return null;
    return this.#items[this.#items.length - 1] as T;
  }

  isEmpty(): boolean {
    return this.#items.length === 0;
  }

  size(): number {
    return this.#items.length;
  }
}
```

가장 중요한 부분은 `pop` 과 `peek` 이 **같은 끝**을 본다는 것입니다. 둘이 다른 끝을 보면
`pop` 직전의 `peek` 이 다른 값을 돌려줍니다.

성장률로 조건 충족을 확인합니다 — `push`·`pop` 시나리오의 실측 비율은 $r = 1.00$ 이고
계약이 요구하는 값과 같습니다.

사용 조건이 달라지면 다른 구현이 적합합니다. 계약은 구현을 처방하지 않으므로 연결 리스트로
만든 스택도 이 계약을 만족합니다.
