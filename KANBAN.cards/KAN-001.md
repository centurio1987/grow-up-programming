### KAN-001 실행 계획 — ORD-006 봉인까지의 배치 전략

#### Context

`KAN-001`은 "ORD-006 봉인 — 지시 원문·진단 9건 표 이관" 카드다. **이관분은 이미 끝나 있다.**

- `ORDER.md:13-24` — 사용자 지시 원문 verbatim 4블록
- `ORDER.md:39-63` — 진단 9건 표 (A급 4 · B급 2 · C급 3) + ternarySearchTree 각주
- `docs/ORD-006-strategy.md` 361줄 — 전략 전문 (rev4)

남은 실체는 카드 메모의 한 문장뿐이다: **"전 카드 완료 시 COMMITTED로 봉인."** 즉 KAN-001은
작업 카드가 아니라 **ORD-006 전체의 종료 게이트**다. 그래서 이 카드의 실행 계획은 곧
"나머지 27장을 어떤 순서와 크기로 돌려서 봉인 조건에 도달하는가"다.

산출물 쪽은 착수 전 상태다 — `_reference/` 0개, `*.contract.ts` 0개, `_bench/` 0개,
`*-problem.md` 69개 전부 생존. 규약 1~4도 아직 문서로 존재하지 않는다.

문제는 규모다. 카드 28장이지만 **실제 실행 단위(세션)는 60~90개**로 추정된다(§7). 세션마다
`ORDER.md`(21KB) + `KANBAN.md`(18KB) + `strategy.md`(27KB) = 66KB ≈ **2만 토큰**을 재적재하면
그것만 100만 토큰을 넘긴다. 이 계획의 핵심은 **배치 진입 비용을 고정 상수로 깎는 것**이다.

#### 1. KAN-001 카드 자체 — 지금 할 일과 봉인 절차

##### 1-1. 지금 (배치 B0에서)

카드 메모에 확인 사실을 못 박는다. 안 하면 다음 세션이 이관을 다시 한다.

```
KAN-001 메모 추가:
이관분 완료 확인(2026-08-04) — ORDER.md:13-24 원문 verbatim, :39-63 진단 9건 표,
docs/ORD-006-strategy.md 전문. **잔여 작업 = 봉인뿐.** 선행조건은 KAN-002~029 전 카드 완료
(KAN-030 신설이 승인되면 030 포함).
```

##### 1-2. 봉인 (마지막 배치)

**선행조건 체크리스트** — 하나라도 미달이면 봉인하지 않는다.

1. `KANBAN.md` 완료 열에 KAN-002~029 전부. **KAN-030(§2-3)을 신설하면 봉인 조건이 28장→29장으로 늘어난다** — 종료 조건을 스스로 확대하는 변경이므로 사용자 승인 없이 진행하지 않는다
2. `docs/ORD-006-strategy.md` §검증 전 항목 통과 (모드①②, `tsc --noEmit`, MDX 빌드, region 추출 일치, `comprehension-gate.sh` 종료코드 0, `authoring.py status`/`lock` 클린). **`cargo test --workspace`는 조건부** — B1에서 (가) 판정 구조가 0건이면 `rust/`가 존재하지 않으므로 이 항목은 "해당 없음"으로 기록하고 넘어간다
3. `find src/data-structures -name "*-problem.md"` 결과 0건 + 링크 무결성 broken 0 (KAN-015가 만드는 체커로 판정)

**봉인 실행** — ORD-001~005 관례(`ORDER.md:81-104`)를 그대로 따른다.

1. ORD-006 항목을 `## 처리 완료 (COMMITTED)` 최하단으로 이동
2. 앞뒤에 봉인 주석: `<!-- ORDER:COMMITTED id=ORD-006 status=done committed=YYYY-MM-DD -->` · `<!-- 봉인 구획: 편집 금지... -->` · 닫는 `<!-- /ORDER:COMMITTED id=ORD-006 -->`
3. **원문 verbatim 블록과 진단 9건 표는 요약하지 않고 그대로 옮긴다.** 뒤에 `- 결과:` 절을 붙여 산출물을 나열
4. `## 신규 지시` 영역에서 제거 (비면 안내 문구만 남김)
5. `KAN-001` 완료 이동 + `KANBAN.log.md` 기록 (manage-kanban 스킬 경유)
6. 메모리 `ds-track-ord006.md`·`guide-quality-standard.md` 갱신 (KAN-018과 짝)

##### 2-1. 절감 축 셋

| 축 | 지금 | 바꾸는 것 |

가이드 집필이 가장 비싼데 압축이 안 된다. 그러니 **다른 데서 새는 것을 막는 것이 유일한 레버**다.

##### 2-2. 배치 = 세션 = 커밋 경계

- 배치 하나가 세션 하나. 세션 중간에 끊으면 다음 세션이 diff를 읽어야 하므로 비용이 배로 든다
- 배치 **시작** 시 `git status`로 워킹트리가 깨끗한지 확인한다. 다른 세션·사용자 변경이 섞인 채 시작하면 배치 경계가 무너진다
- 배치 **종료** 시 **반드시** 셋을 남긴다:
  1. `KANBAN.md` 카드 메모에 결과 1~3줄 (결정·수치·미해결) + 변경 파일 요약
  2. 규약이 바뀌었으면 `docs/ORD-006-conventions.md` 갱신
  3. `docs/ORD-006-runbook.md`의 다음 배치 필독 목록 갱신
- 이 셋이 없으면 다음 세션이 이전 대화를 복원하려고 토큰을 쓴다. **이것이 배치 전략의 전부다.**

##### 2-3. 신설 산출물 2종 (신규 카드 `KAN-030` 제안)

> **카드 신설은 범위 변경이다.** `manage-kanban` 스킬을 경유해 `할 일` 상태로 생성하고,

- **여기서 반드시 풀어야 하는 모순**: "내부 표현을 처방하지 않는다"와 "축2가 불변식을 매 연산 후 검사한다"는 그대로 두면 충돌한다. 높이·균형·버킷 상태를 밖에서 재려면 무언가를 들여다봐야 하기 때문이다. 규격을 둘로 가른다 —

  - **test-only introspection 훅** — `__height()`·`__cost` 등. **이름·시그니처·의미만 계약이 정하고 무엇을 세는지·어떻게 재는지는 구현이 정한다.** 훅 목록을 명세에 적되 내부 표현은 적지 않는다
  이 구분이 없으면 균형 트리 검증이 곧 구현 처방이 되어 A급 결함을 방향만 바꿔 반복한다

- **`tools/check-spec-conformance.ts`는 여기서 만들지 않는다.** 규약1이 파일럿으로 검증되기 전에 범용 checker를 만들면 B9 회고에서 규약이 바뀔 때 통째로 다시 쓴다. checker 착수는 B9 이후(B10에 붙인다)

##### B3 — 규약2 (L · 리스크 상) · 카드 KAN-003
- **최대 난제.** 단독 세션. 다른 것을 섞지 않는다
- **할 것**: `runContract(factory, opts)` 골격 · 축1(참조 모델 교차검증 + JSON vector) · 축2(불변식) · 축3(성장률 판정: n∈{2^10,2^12,2^14}, ±30%, worst=단일 최대 / amortized=시퀀스 평균 / expected=seed 5 중앙값, 균형 구조는 높이 직접 검사) · 적대적 입력 생성기 · seed 재현
- **축3은 벽시계를 쓰지 않는다.** 구현이 노출하는 `__cost` 누적 카운터로만 판정하므로 JIT warmup·GC·머신 편차의 영향을 받지 않고, 그래서 hard-fail로 둘 수 있다. 벽시계는 `_bench/`로 격리하고 CI 판정에서 제외한다(`strategy.md:133`). **이 둘을 섞는 순간 축3은 advisory로 강등된다**
- 다만 **expected 계약(`treap`·`skipList`)의 분산은 실제 리스크**다. seed 5개 중앙값으로 부족하면 seed 수를 늘리되 그 수를 규격에 고정한다 — 실패할 때마다 seed를 바꾸는 것은 게이트 무력화다
- **배치 안에서 즉시 반증**: `deque`를 두 배열 구현과 링 버퍼 구현 둘로 만들어 `_fixtures/broken/`에 넣는다. fixture는 **기대 판정을 각각 명시**한다 — 어느 축에서든 실패하기만 하면 통과가 아니다

  | fixture | 축1 | 축2 | 축3 |
  |---|---|---|---|
  | 두 배열 deque (동작은 정상, 복잡도만 위반) | 통과 | 통과 | **실패** |
  | 순서 뒤집힌 deque (동작 결함) | **실패** | — | — |

  첫 행이 핵심이다. 축1·2를 통과하면서 축3만 실패해야 "동작은 맞는데 계약을 배신하는" A급 결함을 잡는다는 증명이 된다. 안 갈리면 규약2로 회귀 — 판별 마진이 좁다는 것을 전략이 이미 인정하고 있다(`strategy.md:118`)
- **산출**: conventions §규약2 + `src/data-structures/_contract/runContract.ts` + broken fixture(기대 판정표 포함)

##### B4 — 규약3 (M) · 카드 KAN-004

#### 5. P4가 실제 규모다 — 지금 결정할 것은 아니지만 지금 알아야 한다

카드는 3장(026·027·028)인데 대상은 60종이다. 현재 규격(공통 DoD 10항목 × 구조 1종)대로면:

- **코드·계약 배치** — A군 4종/세션, B군 2종/세션, C군 1종/세션 → **약 28세션** (분포 추정 A30·B20·C10, 확정은 KAN-025)
- **가이드 배치** — 1종/세션 고정 → **약 60세션**
- 합 **80세션 이상.** 전체 계획 세션 수의 압도적 다수

**B18(KAN-025) 진입 전에 결정해야 할 것 셋** — B9 회고에서 다룬다:

1. **스캐폴딩 러너**(권장) — 명세에서 스텁 헤더·`contract.ts` 골격·`_reference/` 뼈대·가이드 캔버스 초안을 기계 생성. 모델은 판단만. B10(013 region 추출 파이프라인)에 붙이는 것이 자연스럽다
2. **계열 묶음 가이드** — 힙 4종처럼 공통 유도를 공유하는 계열은 가이드 1편 + 차이 절로 갈 것인가. 규약3 변경이므로 회고에서만 결정
3. **A군 게이트 감면 + waiver 절차** — `gate.external_review`가 `hard-fail`이라 감면하려면 spec 변경이 필요하다. 감면 여부와 별개로 **가용성 대비가 필요하다** — 외부 모델 장애·rate limit·네트워크 단절이면 가이드 60편이 전부 막힌다. retry·timeout·waiver(사유를 게이트 보고에 남기고 통과) 절차를 규격으로 정한다. 단 `comprehension-gate.sh` 종료코드 2(미실행)를 통과로 바꾸는 것은 waiver가 아니라 게이트 무력화다 — 그 선은 넘지 않는다

이 셋 없이 P4에 진입하면 예산이 감당되지 않는다. **계획서에 이 문장을 남기는 것이 목적이다.**

셋 중 1·2는 규약3 설계(B4) 때부터 **가능성을 열어두는 방식으로만** 반영한다 — 캔버스 8단계를
계열 공유가 불가능한 형태로 굳히지 않는다. 확정은 B9다.

#### 8. 리스크

- **B3 축3 판별 마진** — O(1)(r≈4.0)과 O(log n)(r≈4.8)을 가르기엔 좁다. 1차 목표는 A급 4건의 "O(log n) 주장 vs 실제 O(n)"(4.8 대 16)이고, 그것도 안 갈리면 규약2 회귀. **B3에서 즉시 반증하는 이유**
- **규약1↔축2 충돌을 B2에서 못 풀면** 균형 트리 검증이 곧 구현 처방이 되어, 이번에 진단한 A급 결함을 방향만 바꿔 재생산한다. introspection 훅 구분(§B2)이 그 방화벽이다
- **B4 spec 개정 누락** — 4개 중 lock을 빠뜨리면 다음 집필이 stale로 멈추고, 캔버스만 고치면 spec이 이겨서 반영이 안 된다
- **deque 실측 유실** — 큐 패턴 이동 2.95 vs 0.55, 지연 스파이크 7.7ms vs 0.015ms는 지금 세션 산물이다. B6a에서 `_bench/`로 이관할 때 **수치만이 아니라 재현 명령·입력·환경(bun 버전·머신)까지** 고정한다
- **배치 종료 규약 미준수** — 이 계획이 무너지는 가장 흔한 경로. 메모를 안 남긴 세션 하나가 다음 세션에 2만 토큰을 물린다
